1 The story

“Use XGBoost, it always wins”

Before you start: pipelines, estimators and the churn data in 10.1.

The TiffinGo data team argued for a week: one engineer wanted gradient-boosted trees “because they win every Kaggle competition”, another wanted logistic regression “because the business can understand it”. Nobody had compared them on the same features.

K> Sir, aren’t tree ensembles always more accurate? A> Often, when the data has complex interactions. But if the signal is mostly simple, a linear model can match them, train faster and explain itself. The only honest answer is to measure on the same features and the same test set. R> And the features? A> They matter more than the algorithm. Today we fill missing values, scale numbers, create tenure bands, train four classifiers, and read what each one learned. All outputs are real (PySpark 4.3.0).
2 Definition

Feature engineering and classification

Formal definition (write this in exams)

Feature engineering transforms raw attributes into numeric features suitable for a learning algorithm: imputing missing values, encoding categories, scaling numeric ranges (StandardScaler to zero mean and unit variance), discretising continuous values into buckets, and assembling everything into a feature vector. A classifier learns a function from features to a discrete label. MLlib provides logistic regression (a linear model producing class probabilities through the logistic function, with optional L1/L2 regularization), decision trees (recursive binary splits), and tree ensembles: random forests (many trees on bootstrapped samples and random feature subsets, averaged) and gradient-boosted trees (trees trained sequentially on the errors of the previous ones). All are Estimators that train in a distributed way and output rawPrediction, probability and prediction.

In simple words

Features are the numbers a model learns from; good features are complete, comparable and meaningful. A classifier learns to predict a category such as churn yes/no. Logistic regression weighs each feature, trees ask questions, forests average many trees, and boosting adds trees that fix earlier mistakes.

LEVELS> Features and classifiers at three levels L1> Judging a cooking contest
  • Feature engineering is preparing the score sheet: same units, no blanks, useful groupings.
  • Classifiers are different judges: one uses a simple weighted checklist (logistic regression), one asks yes/no questions (a tree), one is a panel of many tree judges (forest), one is a chain of judges each fixing the last one’s mistakes (boosting).
L2> The API
  • Features: Imputer, StandardScaler(withMean, withStd), Bucketizer(splits=…), QuantileDiscretizer, OneHotEncoder, VectorAssembler.
  • Classifiers: LogisticRegression, DecisionTreeClassifier, RandomForestClassifier, GBTClassifier (also LinearSVC, NaiveBayes, MultilayerPerceptron).
  • Inspect: coefficients, featureImportances, toDebugString.
L3> What the lab showed
  • Logistic regression had the best AUC (0.8105) and GBT came close (0.8069) at 4.5x the training time.
  • Both models agreed: days since last order, orders in 30 days and complaints drive churn.
  • With regularization, unscaled features lost AUC (0.8028 vs 0.8104).
/LEVELS EXAM> “Which classifier would you use in Spark MLlib?” Start with a simple, fast baseline such as logistic regression on well-engineered, scaled features; then try tree ensembles (random forest, GBT) when relationships are non-linear or interactions matter. Compare on the same held-out data with AUC/F1, and weigh training time and explainability. In our data the linear model matched GBT because the true signal was mostly linear.

WARN> A model’s weights and importances describe what it used, not cause and effect. Logistic regression coefficients are comparable only when features are on the same scale; tree importances favour features with many possible split points. And watch for leakage features: a column like “cancellation_reason” would give near-perfect churn accuracy because it only exists after the customer churned.
4 Step by step

Features, then four classifiers

All outputs are real: PySpark 4.3.0, local[4], the 200,000-customer churn data from Lesson 10.1 with the same 80/20 split (cached). AUC is computed on the test split from the probability column.

  1. Step 1 · Imputing missing values

    im = Imputer(inputCols=["avg_amount", "late_pct"], outputCols=["avg_amount", "late_pct"], strategy="median").fit(train)
im.surrogateDF.first()     # the learned medians
    == 1) Imputer: what it filled medians: {'avg_amount': 293.9, 'late_pct': 18.0} nulls before: 4797 | after: 0
    The Imputer learned the training medians (₹293.9 and 18.0%) and filled all 4,797 missing amounts. Median is safer than mean for skewed values like order amounts. The same medians are reused at scoring time, because they are stored in the fitted model.

  2. Step 2 · Scaling

    va = VectorAssembler(inputCols=["orders_30d", "avg_amount", "days_since_last"], outputCol="raw")
StandardScaler(inputCol="raw", outputCol="scaled", withMean=True, withStd=True)
    == 2) StandardScaler raw : [9.0, 216.4, 18.0] scaled: [1.22, -0.65, -0.67] std of inputs: [2.4, 157.6, 17.3]
    Raw features live on very different scales: orders around 6 (std 2.4), amounts around 300 (std 157.6). After scaling each is “standard deviations from the mean”: 9 orders is +1.22, ₹216 is −0.65. Now a weight of 1.0 means the same thing for every feature.

  3. Step 3 · Bucketizing tenure

    Bucketizer(splits=[0, 6, 12, 24, 48], inputCol="tenure_months", outputCol="tenure_band")
    == 3) Bucketizer: tenure bands +-----------+---------+----------+ |tenure_band|customers|churn_rate| +-----------+---------+----------+ | 0.0| 17161| 0.477| | 1.0| 20428| 0.455| | 2.0| 40602| 0.405| | 3.0| 81647| 0.312| +-----------+---------+----------+
    Bands make a pattern visible and give linear models a way to treat ranges differently: customers in their first 6 months churn at 47.7%, those over 2 years at 31.2%. Use QuantileDiscretizer when you want equal-sized bands instead of fixed cut points.

    == 4) four classifiers, same features LogisticRegression : fit 5.8 s | AUC 0.8105 | accuracy 0.7517 DecisionTree(depth 5) : fit 2.7 s | AUC 0.7447 | accuracy 0.7244 RandomForest(50 trees) : fit 10.4 s | AUC 0.7867 | accuracy 0.7336 GBT(50 iters) : fit 22.3 s | AUC 0.8069 | accuracy 0.7475

Our churn signal was generated mostly linearly, so a linear model fits it well; on data with strong interactions the ensembles usually win. Measure; do not assume.

  5. Step 5 · What the models learned

    lr = fitted["LogisticRegression"].stages[-1]; lr.coefficients
rf = fitted["RandomForest(50 trees)"].stages[-1]; rf.featureImportances
dt.toDebugString
    == 5) what the models learned LR coefficients (scaled): [('days_since_last', 1.03), ('orders_30d', -0.61), ('complaints', 0.44), ('late_pct', 0.42), ('tenure_months', -0.41), ('plan=Gold', -0.11)] RF importances: [('days_since_last', 0.636), ('orders_30d', 0.15), ('complaints', 0.083), ('tenure_months', 0.06), ('late_pct', 0.059), ('plan=Free', 0.007)] tree root: If (feature 2 <= 33.5)
    Both agreed: days since last order is the strongest churn signal, then orders in 30 days, complaints, late deliveries and tenure. The signs of the scaled coefficients are readable: more recent orders lower churn (−0.61), complaints raise it (+0.44). The tree’s first question was also about feature 2, days since last order.

  6. Step 6 · Scaling matters with regularization

    LogisticRegression(labelCol="churned", regParam=0.1, standardization=False)      # raw features
LogisticRegression(featuresCol="sfeatures", labelCol="churned", regParam=0.1)   # scaled
    == 6) without scaling, LR with regularization regParam 0.1, scaled=False: AUC 0.8028 regParam 0.1, scaled=True: AUC 0.8104
    Regularization penalises large weights. On raw features, a variable measured in big units (amounts) needs a tiny weight and one in small units needs a big one, so the penalty hits them unfairly: AUC fell to 0.8028. Scaled, the same penalty kept 0.8104. (MLlib’s LogisticRegression standardises internally by default; we turned that off to show the effect.)

Payment→GBT→Fraud flag

Predict whether an order will be late from zone, time, weather and rider load.

Order→random forest→Risk

4. Credit scoring

Regulated lenders prefer logistic regression for explainable decisions.

Applicant→logistic→Score + reasons

Restaurant sign-up leads are ranked by probability to convert.

Leads→probability→Sales queue
