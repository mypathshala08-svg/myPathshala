1 The story

“Build us a revenue and churn pipeline”

Before you start: this capstone uses the whole course, especially nulls and duplicates (4.4), CSV/JSON (5.1), joins (6.2) and skew (8.3).

TiffinGo’s leadership wants two things every morning: revenue per city per day, and a churn-risk score for every customer. The raw data is what it always is: daily CSV exports of orders, a customer file from the CRM, and a restaurant list from the partner app. Nobody has checked its quality.

K> Sir, this is the capstone. Shall we start writing the pipeline? A> Not yet. Senior engineers spend the first hour profiling: how many rows, which keys repeat, which values are broken, how skewed the data is. Every surprise you find now is a bug you do not ship later. R> And then? A> Then we design the layers: landing, silver, gold, and a quarantine for bad rows, using everything from the course: schemas, try_cast, dedup, joins, partitioning, tests, spark-submit. This lesson is the problem and the data; the next builds it; the last reviews it like an interview. All outputs are real (PySpark 4.3.0).
2 Definition

The capstone problem

Formal definition (write this in exams)

The capstone is a batch data pipeline in the medallion architecture. Raw files arrive in a landing zone unchanged. A silver layer applies explicit schemas, converts types safely, normalises values, removes duplicates and resolves the latest version of each entity, writing partitioned Parquet; rows that cannot be repaired go to a quarantine table with a reason. A gold layer builds business-level aggregates and features for consumers. Data profiling (row counts, key uniqueness, referential integrity, invalid and out-of-range values, distributions and skew) precedes design, and its findings become explicit data-quality rules enforced as gates in the pipeline.

In simple words

We build a pipeline that turns messy daily files into trusted tables: raw files stay as they arrived, a cleaned layer fixes types and duplicates and sets aside bad rows, and a business layer produces revenue reports and customer features. First we measure what is wrong with the data, then we design rules to handle it.

LEVELS> The capstone at three levels L1> Opening a restaurant kitchen
  • Before cooking for 800 restaurants’ worth of orders, the chef inspects deliveries: rotten vegetables (bad values), double deliveries (duplicates), boxes with no label (orphans).
  • Good ingredients go to the kitchen (silver); bad ones are set aside with a note (quarantine).
L2> The deliverables
  • silver.orders: typed, deduplicated, partitioned by order_date; silver.customers: one row per customer.
  • gold.daily_city_revenue: orders, revenue, average order per city per day; gold.customer_features: 14-day orders, spend, recency for churn scoring (Module 10).
  • quarantine.orders: every rejected row with a reason; a quality gate that stops the run if too many rows are bad.
L3> What profiling found
  • 842,587 order rows in 14 files; 2,587 rows repeat an order_id (retries).
  • 3,279 amounts are not numbers (empty, “N/A”, “12O” with a letter O) and 1,665 are negative; a plain CAST fails under ANSI.
  • One restaurant has 30% of all orders: a skew risk for joins (Module 8).
/LEVELS EXAM> “How do you start a new data pipeline?” Profile the sources first: volumes, schemas, key uniqueness, referential integrity, invalid values, distributions and skew. Turn findings into explicit rules (types, dedup keys, quarantine reasons, thresholds), define the grain and owners of each output table, then design layers (landing/raw, silver/cleaned, gold/business) and tests before writing transformation code.

WARN> Do not “fix” bad data silently. Turning “N/A” into 0 makes revenue wrong, and dropping rows hides an upstream bug. Keep the bad rows with a reason, count them every run, and stop the pipeline when the share jumps. Also decide the grain before coding: here one silver row = one order, one gold row = one city per day.
4 Step by step

Profiling the raw data

All outputs are real: PySpark 4.3.0, local[4]. The raw data was generated by the lab’s generate.py with realistic problems (it is synthetic, but nothing below was edited by hand). Everything is read as text first so that nothing is lost while profiling.

  1. Step 1 · Sizes and schemas

    o = spark.read.option("header", True).csv(f"{R}/orders")      # all columns as string
c = spark.read.option("header", True).csv(f"{R}/customers")
r = spark.read.json(f"{R}/restaurants")
print(o.count(), len(o.inputFiles()), c.count(), r.count()); o.printSchema()
    == 1) sizes and schemas orders rows: 842587 | files: 14 | customers rows: 20100 | restaurants rows: 800 root |-- order_id: string (nullable = true) |-- customer_id: string (nullable = true) |-- rest_id: string (nullable = true) |-- order_ts: string (nullable = true) |-- amount: string (nullable = true) |-- status: string (nullable = true)
    842,587 order rows in 14 daily files, 20,100 customer rows, 800 restaurants. Reading CSV without a schema gives all-string columns: perfect for profiling, because nothing is converted or dropped yet.

  2. Step 2 · Keys: duplicates and orphans

    o.count() - o.select("order_id").distinct().count()
c.count() - c.select("customer_id").distinct().count()
o.join(c.select("customer_id").distinct(), "customer_id", "left_anti").count()
    == 2) keys: duplicates and orphans duplicate order_id rows: 2587 duplicate customer_id rows: 100 orders whose customer_id is not in customers: 20639
    2,587 extra rows repeat an existing order_id (app retries), and 100 customers appear twice. A left_anti join finds 20,639 orders whose customer is missing from the CRM export. Each number becomes a rule: dedup keys, “latest row wins”, and a decision on orphans.

  3. Step 3 · Bad values

    amt = F.col("amount").try_cast("int")
o.select(F.sum(amt.isNull().cast("int")), F.sum((amt < 0).cast("int")), F.min(amt), F.max(amt)).show()
o.filter(amt.isNull()).groupBy("amount").count().show()
o.select(F.col("amount").cast("int")).agg(F.sum("amount")).collect()     # plain CAST
    == 3) bad values +-------------------+---------------+----------+----------+ |amount_not_a_number|amount_negative|min_amount|max_amount| +-------------------+---------------+----------+----------+ | 3279| 1665| -1500| 1500| +-------------------+---------------+----------+----------+ +------+-----+ |amount|count| +------+-----+ | NULL| 1073| | 12O| 1140| | N/A| 1066| +------+-----+ +-------------+ |phone_invalid| +-------------+ | 194| +-------------+ plain CAST under ANSI -> [CAST_INVALID_INPUT]
    try_cast (Lesson 12.3) shows 3,279 amounts that are not numbers: empty (read as NULL), “N/A”, and “12O” with a capital letter O. Another 1,665 are negative. A plain CAST on this column fails with CAST_INVALID_INPUT under Spark 4’s ANSI mode, so the pipeline must handle these explicitly. Customers also have 194 invalid phone numbers.

  4. Step 4 · Distributions and skew

    o.groupBy("status").count().orderBy(F.desc("count")).show()
o.groupBy("rest_id").count().orderBy(F.desc("count")).limit(3).collect()
o.groupBy(F.to_date("order_ts").alias("day")).count().orderBy("day").show(3)
    == 4) distribution and skew +---------+------+ | status| count| +---------+------+ |DELIVERED|716556| |CANCELLED| 84207| | PLACED| 41824| +---------+------+ top restaurants by orders: [('1', 253012), ('792', 810), ('462', 808)] | share of #1: 30.0 % +----------+-----+ | day|count| +----------+-----+ |2026-10-20|60188| |2026-10-21|60161| |2026-10-22|60156| +----------+-----+ only showing top 3 rows
    85% of orders are DELIVERED, which is what revenue counts. Restaurant 1 (“Cloud Kitchen Co”) has 30% of all orders: any shuffle on rest_id would put a third of the data in one task (Lesson 8.3), so the restaurant join must be a broadcast. About 60,000 orders per day: a natural partition column.

6 Real-world use

This pattern at work

1. Retail sales

Store POS exports land daily; silver dedups receipts, gold builds sales by store and day.

POS files→silver/gold→Sales cube

2. Banking transactions

Transactions with invalid amounts are quarantined for operations review.

Core banking→quarantine→Ops queue

3. Insurance claims

Claims from many partners are profiled and normalised before fraud models.

Partner files→rules→Clean claims

4. Telecom usage

Call records are partitioned by day; subscriber features feed churn models.

CDRs→daily partitions→Churn features

5. EdTech engagement

Course events become daily engagement tables and dropout-risk features.

Events→gold features→Risk scores

The capstone data is synthetic and generated by the lab script.
