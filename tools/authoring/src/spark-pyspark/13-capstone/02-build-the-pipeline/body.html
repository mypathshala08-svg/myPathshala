K> Sir, it works in my notebook. Can we schedule it? A> A notebook is a draft. Production code has pure transform functions in a module, unit tests for each one, a thin pipeline script that does the reading and writing, and quality gates that stop the run when data is wrong. R> Why separate transforms from reading and writing? A> Because a function that takes a DataFrame and returns a DataFrame can be tested on four hand-made rows in seconds. The pipeline script then just wires them together, and spark-submit ships the module to the cluster. All outputs below are real (PySpark 4.3.0).
2 Definition

A production batch pipeline

Formal definition (write this in exams)

A production Spark batch job separates pure transformations (functions from DataFrames to DataFrames, free of I/O) from an orchestration script that reads sources with explicit schemas, applies the transformations, writes outputs idempotently (overwrite of the run’s partitions), and evaluates data-quality gates whose failure aborts the run. Transformations are covered by unit tests on small in-memory DataFrames; the job is packaged (e.g. a zip passed with --py-files) and launched with spark-submit on a cluster manager, emitting run metrics for monitoring.

In simple words

Write the cleaning and business logic as small functions you can test on a few rows, keep reading and writing in one short script, check the results before publishing them, and run the same code on a cluster with spark-submit.

LEVELS> The pipeline at three levels L1> A kitchen line
  • Each station does one job (wash, cut, cook, plate) and can be checked on its own: those are the transforms and their tests.
  • The head chef checks every plate before it leaves; a bad batch stops service: that is the quality gate.
L2> The code layout
  • tiffingo/transforms.py: clean_orders, clean_customers, daily_city_revenue, customer_features. No I/O.
  • tiffingo/pipeline.py: reads landing, calls transforms, writes silver/quarantine/gold, runs gates, prints metrics as JSON.
  • tiffingo/tests/: pytest with a shared spark fixture (Lesson 11.4).
L3> Engineering choices
  • An explicit DDL schema reads every column as string; try_cast converts, and a single problem column records the first failed rule.
  • Validation happens before dropDuplicates, so a bad copy never “wins” over a good one; repartition("order_date") before partitionBy gives one file per day.
  • Gates: zero NULL amounts, unique order ids, quarantine share under 2%; otherwise assert fails the job and the scheduler alerts.
/LEVELS EXAM> “How do you make a Spark job production-ready?” Put logic in pure, unit-tested functions; read with explicit schemas; handle bad records explicitly (quarantine, not silent drops); make writes idempotent; add data-quality gates that fail the job; emit metrics; package dependencies and run with spark-submit under a scheduler with retries and alerts.

Where each check lives

A transform is wrongUnit test (pytest, CI)Merge blocked; never reaches production

Too many rows are badGate: quarantine_pct < 2%Job fails; scheduler alerts; gold not overwritten
Output broken (NULLs, dup ids)Gate: assert on silverJob fails before gold
Job slow or skewedRun metrics, Spark UI, event logInvestigate (Lesson 13.3)
WARN> Gates must run before gold is written, otherwise dashboards read yesterday’s bad data as truth. And never catch the gate’s exception just to “keep the job green”: a failed run that alerts is far cheaper than a wrong revenue number in a board meeting.
4 Step by step

Building the pipeline

All outputs are real: PySpark 4.3.0, local[4] and a standalone cluster (Lesson 11.1). Full code is in the lab folder jobs/m13/tiffingo/.

  1. Step 1 · Silver: clean and quarantine

    def clean_orders(raw):
    typed = raw.select(F.col("order_id").try_cast("long").alias("order_id"), ...,
                       F.col("amount").try_cast("int").alias("amount"),
                       F.upper(F.trim("status")).alias("status"), F.col("amount").alias("amount_raw"))
    problem = (F.when(F.col("order_id").isNull(), "bad_order_id")
                .when(F.col("order_ts").isNull(), "bad_timestamp")
                .when(F.col("amount").isNull(), "bad_amount")
                .when(F.col("amount") < 0, "negative_amount"))
    typed = typed.withColumn("problem", problem)
    quarantine = typed.filter(F.col("problem").isNotNull())
    valid = (typed.filter(F.col("problem").isNull()).dropDuplicates(["order_id"])
             .withColumn("order_date", F.to_date("order_ts")).drop("problem", "amount_raw"))
    return valid, quarantine
    == quarantine sample +--------+----------+---------------+ |order_id|amount_raw| problem| +--------+----------+---------------+ | 720082| N/A| bad_amount| | 720477| -93|negative_amount| | 720815| NULL| bad_amount| | 720955| NULL| bad_amount| +--------+----------+---------------+ only showing top 4 rows
    One function returns two DataFrames. try_cast never throws; the first failing rule fills problem, and the original text is kept in amount_raw so the source team can see exactly what arrived. Deduplication runs only on valid rows.

  2. Step 2 · Unit tests

    def test_bad_rows_go_to_quarantine(spark):
    df = raw(spark, [("1", "7", "1", "2026-10-20 10:00:00", "250", "delivered"),
                     ("2", "7", "1", "2026-10-20 11:00:00", "N/A", "DELIVERED"),
                     ("3", "7", "1", "2026-10-20 12:00:00", "-90", "DELIVERED"),
                     ("4", "7", "1", "not a time", "100", "DELIVERED")])
    valid, quar = clean_orders(df)
    assert [r.order_id for r in valid.collect()] == [1]
    assert sorted((r.order_id, r.problem) for r in quar.collect()) == \
        [(2, "bad_amount"), (3, "negative_amount"), (4, "bad_timestamp")]
# + duplicates, latest customer, delivered-only revenue (assertDataFrameEqual), no-order features

6 Real-world use

This pattern at work

1. Daily sales close

Nightly job builds store revenue; a gate blocks publishing if receipts are missing.

POS files→gated job→Finance BI

2. Payments reconciliation

Transactions are typed and deduplicated; unmatched ones are quarantined for review.

Ledger + PSP→quarantine→Ops

3. Driver features

Daily features feed incentive and churn models (Module 10).

Trips→gold features→ML

4. Usage billing

Tested transforms guarantee each call record is billed exactly once.

CDRs→dedup + tests→Invoices

5. Claims pipeline

Partner claims files with bad codes are quarantined, not dropped.

Partners→rules→Adjudication

The capstone data is synthetic and generated by the lab script.
