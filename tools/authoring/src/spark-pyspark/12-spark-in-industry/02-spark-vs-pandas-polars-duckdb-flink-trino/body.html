1 The story

“Do we really need Spark for this?”

Before you start: what Spark is in 1.2, toPandas and Arrow in 4.6, Parquet in 5.2.

A new TiffinGo analyst asked why a simple report on 5 million orders took a Spark cluster and 10 seconds, when her laptop answered it in a blink with DuckDB. A senior engineer replied that the nightly job processes billions of rows from 40 sources. Both were right.

K> Sir, if DuckDB is 100 times faster, why did we learn Spark for 12 modules? A> Because “faster” depends on the size and shape of the work. Single-machine engines avoid all distribution overhead, so on data that fits one machine they usually win. Spark pays that overhead to scale out to many machines, many hours and many teams. R> And Flink and Trino? A> Different jobs again: Flink for low-latency streaming, Trino for interactive SQL over many sources. Today we benchmark the single-machine tools against PySpark on our own data, then map out where each one fits. All benchmark outputs are real.
2 Definition

Spark and the alternatives

Formal definition (write this in exams)

Data engines differ in execution scope (single process vs distributed cluster), processing model (eager vs lazy/optimised, batch vs streaming-first) and interface (DataFrame vs SQL). pandas is an eager in-memory DataFrame library; Polars is a multi-threaded columnar DataFrame engine with lazy query optimisation; DuckDB is an in-process analytical SQL database with vectorised execution and out-of-core processing. They avoid network and coordination overhead and excel when data fits one machine. Apache Spark distributes batch, streaming and ML workloads across a cluster with fault tolerance. Apache Flink is a distributed stream processor built around continuous, event-at-a-time processing with managed state and low latency. Trino is a distributed massively parallel SQL query engine for interactive analytics that federates many data sources without loading them.

In simple words

pandas, Polars and DuckDB run on one computer and are very fast when the data fits there. Spark spreads big jobs over many computers and survives failures. Flink is built for always-on streaming with very low delay, and Trino for fast SQL questions across many databases and lakes.

LEVELS> Choosing an engine at three levels L1> Vehicles
  • pandas is a bicycle: easy, everywhere, but not for heavy loads. Polars and DuckDB are sports cars: very fast on one road. Spark is a fleet of trucks: slow to start, but it moves a city’s goods.
  • Flink is an ambulance (always on, lowest latency); Trino is a taxi network (go anywhere, ask questions fast).
L2> The tools
  • pandas: eager, in-memory, single-threaded mostly; huge ecosystem.
  • Polars: Rust, multi-threaded, lazy query plans (scan_parquet … collect()).
  • DuckDB: embedded columnar SQL engine, vectorised, streams from Parquet, spills to disk.
  • Spark: distributed batch + streaming + ML; Flink: distributed stream-first; Trino: distributed interactive SQL over many sources.
L3> What the benchmark showed
  • 5M rows: DuckDB 0.03 s, Polars 0.07 s, pandas 0.23 s, PySpark 3.2 s for the same groupBy.
  • 50M rows: pandas was killed by the OS (out of memory); DuckDB used 386 MB, Polars 4.9 GB, Spark’s JVM 3.6 GB.
  • Top-3 per city on 50M rows: DuckDB 1.3 s, Polars 8.6 s, PySpark 48.7 s on 2 local cores.
/LEVELS EXAM> “When would you not use Spark?” When data fits comfortably on one machine and latency matters: DuckDB or Polars are often 10–100× faster there because they avoid cluster start-up, serialization and shuffles. Use Spark when data or compute exceed one machine, when you need fault-tolerant long jobs, unified batch/streaming/ML, or a shared platform; Flink for millisecond-level stateful streaming; Trino for interactive federated SQL.

WARN> Benchmarks are easy to misread. Ours ran on 2 CPUs and 8 GB with other services running, Spark in local[4] with its ~6-second start-up, and a 431 MiB Parquet dataset: the home ground of single-node engines. On a 2 TB dataset none of the single-node tools would finish on that machine, while Spark would simply use more executors. Benchmark your own workload at your own size, and include start-up, memory and reliability, not just one query time.
4 Step by step

Benchmarking four engines

All outputs are real: pandas 3.0.5, Polars 2.1.0, DuckDB 2.0.0, PySpark 4.3.0 (local[4], 3 GB driver). Each engine ran in a fresh process; peak memory from getrusage (and the Spark JVM’s high-water mark). Data: the course’s 5M-row orders (34.6 MiB Parquet) and a 50M-row copy (431 MiB), joined with 4,000 customers.

  1. Step 1 · The three queries

    # q1 groupBy:       revenue per city
# q2 join+groupBy:  orders ⋈ customers, revenue per tier
# q3 top-3 per city: window / sort + head(3)
# DuckDB example:
con.sql(f"SELECT city, sum(amount) FROM '{P}/*.parquet' GROUP BY city").fetchall()
con.sql(f"SELECT * FROM '{P}/*.parquet' QUALIFY row_number() OVER (PARTITION BY city ORDER BY amount DESC) <= 3")
    The same logical queries written idiomatically in each tool. pandas loads the data first (eager); Polars and DuckDB scan Parquet lazily and only read needed columns; Spark builds a plan and runs it on its executors.

  2. Step 2 · 5 million rows

    for e in pandas polars duckdb pyspark; do python bench.py $e 5m; done
    # machine: 2 CPUs, 8 GB RAM (other lab services running); data: 5M rows (34.6 MiB Parquet), 50M rows (431 MiB Parquet) pandas 5m | load/start 2.4 s | q1 groupBy 0.23 s | q2 join+groupBy 0.35 s | q3 top-3 per city 1.27 s | peak RSS 1118 MB polars 5m | load/start 0.0 s | q1 groupBy 0.07 s | q2 join+groupBy 0.08 s | q3 top-3 per city 0.70 s | peak RSS 979 MB duckdb 5m | load/start 0.0 s | q1 groupBy 0.03 s | q2 join+groupBy 0.04 s | q3 top-3 per city 0.13 s | peak RSS 140 MB pyspark 5m | load/start 6.5 s | q1 groupBy 3.20 s | q2 join+groupBy 1.39 s | q3 top-3 per city 6.53 s | peak RSS 108 MB (+JVM 1631 MB)
    DuckDB answered the groupBy in 0.03 s with 140 MB of memory; Polars in 0.07 s; pandas in 0.23 s after a 2.4 s load. PySpark needed 6.5 s just to start and 3.2 s for the first query (JVM warm-up), using a 1.6 GB JVM. For this size Spark is the wrong tool.

  3. Step 3 · 50 million rows

    for e in pandas polars duckdb pyspark; do python bench.py $e 50m; done
    pandas 50m | Killed by the OS (out of memory): anon-rss 5966748 kB while loading/processing polars 50m | load/start 0.0 s | q1 groupBy 0.58 s | q2 join+groupBy 0.68 s | q3 top-3 per city 8.64 s | peak RSS 4912 MB duckdb 50m | load/start 0.0 s | q1 groupBy 0.23 s | q2 join+groupBy 0.33 s | q3 top-3 per city 1.27 s | peak RSS 386 MB pyspark 50m | load/start 5.8 s | q1 groupBy 6.26 s | q2 join+groupBy 3.03 s | q3 top-3 per city 48.73 s | peak RSS 109 MB (+JVM 3622 MB)
    pandas tried to hold all 50M rows as Python-friendly columns and the OS killed it at about 6 GB. Polars finished but peaked at 4.9 GB. DuckDB stayed at 386 MB by streaming through the files and was fastest everywhere. Spark’s JVM peaked at 3.6 GB within its 3 GB heap plus overhead and completed every query, but slowly on 2 cores, especially the full sort for top-3 (48.7 s).

  4. Step 4 · Where Spark wins (and Flink, Trino)

    data > one machine (TB–PB)       -> Spark (or Trino for interactive SQL)
long ETL with retries, many joins  -> Spark
batch + streaming + ML, one API    -> Spark
millisecond stateful streaming     -> Flink (Spark Real-Time Mode is catching up)
SQL across Postgres + lake + Kafka -> Trino (federation)
fits in RAM, one user              -> DuckDB / Polars
    Our lab cannot show Spark’s strengths, because they start where one machine ends: 10 TB jobs that need 200 executors, tasks retried on failure, and one engine for ETL, streaming (Module 9) and ML (Module 10). Flink and Trino were not run here; the guidance comes from their design. Many teams combine tools: DuckDB/Polars for local work, Spark for the platform, Trino for BI.
