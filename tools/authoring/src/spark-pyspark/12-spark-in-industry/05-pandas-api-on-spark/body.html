1 The story

Your pandas code, on a cluster

Before you start: 4.6 toPandas and Arrow.

🤔 Your analyst knows pandas, not Spark. Can the same pandas code run on a cluster?

Mostly, yes: import pyspark.pandas as ps. The same read_csv → groupby → mean gave identical numbers in pandas and in pandas-on-Spark. But on 300,000 rows pandas took 0.12 s and pandas-on-Spark 14.6 s on the first run (2.3 s warm). Spark pays off when data no longer fits one machine, not before. We also hit a ValueError when mixing two frames, and saw that the safety option is now True by default.

2 Definition

pandas API on Spark

Formal definition (write this in exams)

pandas API on Spark (pyspark.pandas, formerly Koalas, part of PySpark since 3.2) implements the pandas DataFrame and Series API on top of Spark DataFrames. Each pandas-on-Spark DataFrame holds a Spark DataFrame plus index metadata; operations are translated to Spark SQL plans and executed lazily across the cluster.

In simple words

Write pandas-style code; Spark does the work on many machines; bring back only small results as real pandas.

Why, how, where

Why

Teams have years of pandas code and pandas skills. pandas-on-Spark (formerly Koalas) lets that code scale out with few changes.

the problem it solves

How

A pandas-on-Spark DataFrame wraps a Spark DataFrame plus an index. Each pandas call is translated into Spark operations, run lazily, and only to_pandas()/printing brings rows to the driver.

the mechanism

Where

Scaling notebooks that outgrew one machine, migrating pandas jobs to a cluster, analysts working on lakehouse tables with a familiar API.

in real systems

When not

Small data is slower than pandas; a global row order (index) is expensive; some pandas features are missing or costly; to_pandas() can crash the driver on big data.

Dissect one line

LEVELS> pandas-on-Spark at three levels L1> Same recipe, bigger kitchen
  • You keep your recipe (pandas code) but cook in a big hotel kitchen with many cooks (Spark). For two plates, your home stove is quicker.
L2> The API
  • import pyspark.pandas as ps; ps.read_csv, ps.read_parquet, ps.read_table, ps.DataFrame(…), ps.sql("… {df} …", df=psdf).
  • psdf.to_spark() → Spark DataFrame; sdf.pandas_api() → pandas-on-Spark; psdf.to_pandas() → real pandas on the driver.
  • Options: ps.set_option("compute.default_index_type", …), "compute.ops_on_diff_frames".
L3> Practical details
  • Default index distributed-sequence gives 0, 1, 2… but needs extra work; distributed is cheapest (ids not consecutive); pass index_col when reading to avoid it.
  • Combining columns from two different frames needs a join on the index; in Spark 4 compute.ops_on_diff_frames is True by default (it was False in 3.x).
  • len(), iloc[n], .values and printing all trigger Spark jobs; .values and to_pandas() collect everything to the driver.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: pandas-on-Spark is always faster.
    Reality (Spark 4.3): 0.12 s vs 14.6 s on small data.
    Proof: Step 1.
  • Myth: It is a pandas DataFrame.
    Reality (Spark 4.3): Class is pyspark.pandas.frame.
    Proof: Step 2.
  • Myth: to_pandas() is free.
    Reality (Spark 4.3): Collects all rows to the driver.
    Proof: Warning.
EXAM> “What is pandas API on Spark?” pyspark.pandas (ex-Koalas, 3.2+); ps.read_csv/parquet; to_spark(), pandas_api(), to_pandas(); default index types (sequence, distributed-sequence, distributed); compute.ops_on_diff_frames; small data → pandas is faster.

4 Step by step

pandas vs pandas-on-Spark

All outputs are real: PySpark 4.3.0, local[2], a 300,000-row CSV generated with a fixed seed.

  1. Step 1 · Same code, two engines

    pd.read_csv(path).groupby("city")["amount"].mean()
ps.read_csv(path).groupby("city")["amount"].mean().to_pandas()
    == 1) same pandas code, two engines pandas : {'Delhi': 475.6, 'Mumbai': 474.6, 'Pune': 474.2} 0.12 s pyspark.pandas: {'Delhi': 475.6, 'Mumbai': 474.6, 'Pune': 474.2} 14.57 s
    Identical answers. Spark’s start-up and job overhead make it far slower on 300,000 rows.

  2. Step 2 · Type and default index

    psdf = ps.read_csv(path)
type(psdf); ps.get_option("compute.default_index_type"); psdf.head(3)
    == 2) type and index type: pyspark.pandas.frame.DataFrame default index type: distributed-sequence head(3): city amount 0 Mumbai 873 1 Delhi 164 2 Delhi 332
    It looks like pandas, but the class lives in pyspark.pandas, and the 0, 1, 2… index is generated for you.

  3. Step 3 · Moving between worlds

    sdf = psdf.to_spark()
back = sdf.pandas_api()
small = psdf.head(5).to_pandas()
    == 3) moving between worlds to_spark() -> pyspark.sql.classic.dataframe ['city', 'amount'] pandas_api() -> pyspark.pandas.frame to_pandas() -> pandas (collects to driver!)
    Use Spark for heavy lifting and pandas for the small final result.

  4. Step 4 · Two different frames

    ps.set_option("compute.ops_on_diff_frames", False)
psdf["amount"] + other["amount"]
    == 4) combining two different pandas-on-Spark frames compute.ops_on_diff_frames default: True ValueError: Cannot combine the series or dataframe because it comes from a different dataframe with True (joins on the index): [1746, 328]
    Spark 4 default is True (an index join happens silently); set False to catch accidental expensive joins.

  5. Step 5 · SQL and hidden costs

    ps.sql("SELECT city, count(*) AS n FROM {df} GROUP BY city", df=psdf)
len(psdf); psdf.iloc[5]; psdf.values

    Everything works, but each line starts a Spark job; .values collects to NumPy on the driver.
