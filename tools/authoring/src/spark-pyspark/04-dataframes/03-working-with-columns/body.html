1 The story

“The feature job takes ten minutes before it reads anything”

Before you start: DataFrames and plans in 4.1, schemas in 4.2.

Riya’s feature job adds 300 columns to the orders DataFrame, one withColumn per feature in a loop. The Spark UI shows no jobs for the first minutes; the driver CPU is at 100%. Then a colleague’s change to the amount column fails the whole job with CAST_INVALID_INPUT.

R> Sir, nothing is even running yet. What is the driver doing? A> Analysing your plan, 300 times. Every withColumn creates a new DataFrame whose plan must be analysed again. Build the columns in one call and the waiting disappears. K> And the cast error? The same code ran on Spark 3. A> Spark 4 runs with ANSI mode on: a bad cast is an error, not a silent null. Today: naming columns, select and expressions, casts and try_cast, adding and renaming, when/otherwise, filters and their traps, and the 300-column timing. All outputs are real (PySpark 4.3.0).
2 Definition

Column expressions

Formal definition (write this in exams)

A Column in PySpark is an expression evaluated for every row of a DataFrame: a reference to an input column, a literal (F.lit), or a combination built with operators and functions from pyspark.sql.functions. Column expressions are used in projections (select, withColumn, withColumns), in predicates (where/filter) and in aggregations. Each such transformation returns a new DataFrame whose logical plan must be analysed by Catalyst; projections built in one call produce one plan node, while repeated withColumn calls add one node and one analysis each. Under ANSI mode (default since Spark 4.0), invalid casts and arithmetic overflow raise errors; try_cast and other try_* functions return null instead.

In simple words

A column in your code is a small formula, like amount * 0.05, that Spark applies to every row. You use these formulas to choose, add, change and filter columns. Add many columns in one step, and use try_cast when some values might be bad.

LEVELS> Columns at three levels L1> A spreadsheet
  • Selecting is hiding the columns you do not need; adding is a new column with a formula; filtering is hiding rows.
  • A formula like =B2*0.05 describes every row at once; a Column expression does the same.
  • Typing a formula into each cell one by one is slow; writing it once for the whole column is fast.
L2> The API
  • Name a column: "city", df.city, df["city"], F.col("city"); build expressions with operators and pyspark.sql.functions.
  • select, selectExpr, withColumn, withColumns, withColumnRenamed, drop, cast/try_cast, F.when().otherwise(), where/filter.
  • Combine conditions with &, |, ~ and brackets, never Python and/or.
L3> What the lab showed
  • With ANSI on, cast("int") failed on 'abc'; try_cast gave null and a sum over 50,001 values.
  • Missing brackets and Python and both raised CANNOT_CONVERT_COLUMN_INTO_BOOL; a typo got a “Did you mean” suggestion.
  • 300 columns: withColumn loop 6.87 s to build, withColumns 0.98 s, one select 0.83 s.
/LEVELS EXAM> “withColumn in a loop: what is wrong?” Each call returns a new DataFrame and adds a projection to the plan, which Catalyst re-analyses every time; with hundreds of columns this costs seconds to minutes on the driver and can cause StackOverflowError. Use withColumns or a single select (300 columns: 6.87 s vs 0.98 s vs 0.83 s in our lab).
3 Types and ways to use it

Four ways to refer to a column

FormWorks whenWatch out
"city"Most methods accept namesNot for expressions like "amount" * 2
df.cityName is a valid Python identifierFails for order-id; clashes with DataFrame methods (df.count)
df["city"]Any nameBound to that DataFrame: useful to disambiguate joins
F.col("city")Anywhere, even before the DataFrame existsRecommended default
WARN> Python’s and, or and not do not work on Columns, and & binds tighter than ==. Always write (F.col("city") == "Pune") & (F.col("amount") > 500) with brackets around each comparison, or use a SQL string: df.where("city = 'Pune' AND amount > 500").

    when conditions are checked in order, like CASE WHEN in SQL. Note that a row whose hour is null (the bad timestamp) matches no condition and lands in otherwise: one of these 4,154 “late-night” orders is really unknown. Handle nulls explicitly when it matters (Lesson 4.4).

    Column and SQL-string filters gave the same 860 Pune orders above ₹500.   6. Step 6 · 300 columns: loop vs one call

    d = base
for i in range(300):
    d = d.withColumn(f"c{i}", F.col("id") + i)                      # 300 plans
d = base.withColumns({f"c{i}": F.col("id") + i for i in range(300)})   # one call
d = base.select("*", *[(F.col("id") + i).alias(f"c{i}") for i in range(300)])
    == 8) withColumn in a loop vs one select (300 new columns) withColumn loop : build 6.87 s, count 0.36 s, columns 301 withColumns (one call) : build 0.98 s, count 0.16 s, columns 301 select (one call) : build 0.83 s, count 0.20 s, columns 301
    The loop needed 6.87 s on the driver just to build the DataFrame, before any data was read; withColumns needed 0.98 s and one select 0.83 s. The data work (count) was tiny in all three. Riya’s minutes of waiting were plan analysis. The PySpark docs warn about exactly this: loops of withColumn can also end in StackOverflowError.

6 Real-world use

Column work at companies

1. Type cleaning

Raw string feeds are converted with try_cast and try_to_timestamp; rows that become null go to a quarantine table.

Raw strings→try_cast→Typed table

2. Feature engineering

Hundreds of ratio and flag columns are generated from a config and added with one withColumns call.

Config→withColumns→Features

3. Business rules

Segments such as meal slot, order size band or customer tier are when/otherwise columns.

Order→when/otherwise→Segment

4. Masking personal data

Phone and email columns are hashed or dropped before data leaves the secure zone.

Raw→sha2 / drop→Shared data

5. Naming standards

Columns from source systems are renamed to company standards (snake_case, units in names) in one step.

Source names→withColumnsRenamed→Standard names
