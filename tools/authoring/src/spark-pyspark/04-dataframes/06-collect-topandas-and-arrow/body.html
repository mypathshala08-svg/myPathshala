1 The story

“It worked on the sample”

Before you start: the driver’s role in 1.3 and actions in 2.2.

Riya built a chart in her notebook with orders.toPandas() on a 10,000-row sample. In production the same line ran on the whole table. The driver ran out of memory, the notebook kernel died, and the scheduled report never arrived.

R> Sir, toPandas is the easiest way to plot. Is it forbidden? A> Not forbidden, just dangerous on big data. collect and toPandas copy every row into the single driver process. Aggregate in Spark first, then bring the small result to pandas. K> I read that Arrow makes it faster. Do we need to switch it on? A> Since Spark 4.2 it is on by default. Today we look at every way to bring rows to the driver, time collect and toPandas with and without Arrow, see how types change on the way, go back from pandas to Spark, and let the driver’s safety limit stop a 5-million-row collect. All outputs are real (PySpark 4.3.0).
2 Definition

Moving data between Spark and Python

Formal definition (write this in exams)

Actions such as collect(), take(n) and toPandas() transfer the rows of a distributed DataFrame from the executors to the driver, where they are materialised in the Python process: as a list of Row objects, a pandas DataFrame, or (with toArrow(), Spark 4.0+) a PyArrow Table. The data must fit in driver memory; spark.driver.maxResultSize (default 1g) aborts jobs whose serialized results exceed the limit. Apache Arrow is a columnar in-memory format that PySpark uses to transfer data in batches between the JVM and Python without per-row serialization, for toPandas, createDataFrame from pandas, and pandas UDFs. It is controlled by spark.sql.execution.arrow.pyspark.enabled, enabled by default since Spark 4.2, with automatic fallback to the row-based path when a type is not supported.

In simple words

collect and toPandas copy the data from all machines into your one Python program. That is fine for small results and dangerous for big tables. Arrow is a fast format for moving columns between Spark and pandas; in Spark 4.2 and later it is used automatically.

LEVELS> Bringing data to the driver at three levels L1> A warehouse and one desk
  • The cluster is a warehouse; the driver is one office desk. You can bring a summary sheet to the desk, not the whole warehouse.
  • take(5) is asking for five boxes; collect() is asking for every box.
  • Arrow is moving boxes on pallets instead of one by one.
L2> The API
  • To Python objects: first, head(n), take(n), tail(n), collect() (list of Row), toLocalIterator() (one partition at a time).
  • To pandas and Arrow: toPandas(), toArrow() (Spark 4.0+); back: spark.createDataFrame(pdf).
  • Settings: spark.sql.execution.arrow.pyspark.enabled (true since 4.2), …fallback.enabled, spark.driver.maxResultSize (1g), spark.driver.memory.
L3> What the lab showed
  • 1M rows: collect 8.4 s; toPandas 9.9 s without Arrow, 1.4 s with Arrow; toArrow 0.65 s.
  • An integer column with a null became float64 in pandas (450 → 450.0, None → NaN).
  • createDataFrame(pandas) of 1M rows: 11.8 s without Arrow, 2.6 s with. A 5M-row collect stopped at maxResultSize (63.9 MiB > 50 MiB).
/LEVELS EXAM> “Why avoid collect() on large DataFrames?” It moves every row to the single driver process; the driver can run out of memory or hit spark.driver.maxResultSize, and all parallelism is lost. Aggregate or filter in Spark first, use take/limit to look at samples, and write large results to storage.

Put the aggregation, filter or limit in Spark, right before the call, and keep spark.driver.maxResultSize at a safe value so a mistake fails fast instead of killing the driver.
4 Step by step

From the cluster to pandas and back

All outputs are real: PySpark 4.3.0 with pandas 3.0 and PyArrow 26, local mode, driver memory 2 GB, orders_big (5M rows). Timings vary by a second or two between runs.

  1. Step 1 · The defaults

    for k in ("spark.sql.execution.arrow.pyspark.enabled",
          "spark.sql.execution.arrow.pyspark.fallback.enabled",
          "spark.sql.execution.arrow.maxRecordsPerBatch"):
    print(k, spark.conf.get(k))
spark.sparkContext.getConf().get("spark.driver.maxResultSize", "(not set: 1g)")
    == 1) defaults spark.sql.execution.arrow.pyspark.enabled : true spark.sql.execution.arrow.pyspark.fallback.enabled : true spark.sql.execution.arrow.maxRecordsPerBatch : 10000 spark.driver.maxResultSize : (not set: 1g)
    Arrow is on by default: the PySpark 4.2 migration guide changed arrow.pyspark.enabled to true. If a type cannot be converted, Spark falls back to the slow path instead of failing. Arrow batches hold 10,000 records. The driver accepts up to 1 GB of collected results unless configured otherwise.

  2. Step 2 · Small amounts of data

    d = big.orderBy("order_id")
d.first(); d.head(2); d.take(2); d.tail(1)
d.limit(3).collect()
it = big.toLocalIterator(); next(it)
    == 2) the ways to bring rows to the driver first() : Row(order_id=1000000, customer_id=1806, city='Delhi', order_date=datetime.date(2026, 9, 1), amount=766, status='CANCELLED') head(2) : 2 | take(2): 2 | tail(1): 5999999 collect(): list of Row toLocalIterator first: 4125000
    first, head, take and tail return a few Row objects. collect() returns a Python list of Rows, all of them. toLocalIterator() fetches one partition at a time, so the driver holds only the largest partition, not the whole DataFrame: useful to stream rows into another system from Python.

  3. Step 3 · One million rows: collect, toPandas, toArrow

    m = big.limit(1_000_000).cache(); m.count()
rows = m.collect()
for arrow in ("false", "true"):
    spark.conf.set("spark.sql.execution.arrow.pyspark.enabled", arrow)
    pdf = m.toPandas()
tbl = m.toArrow()
    == 3) collect vs toPandas, 1M rows collect() : 8.37 s, 1,000,000 Row objects toPandas arrow=false: 9.89 s, shape (1000000, 6), 84 MiB in pandas toPandas arrow=true : 1.42 s, shape (1000000, 6), 84 MiB in pandas toArrow() : 0.65 s, 1,000,000 rows, 42 MiB pandas dtypes (arrow): {'order_id': 'int64', 'customer_id': 'int32', 'city': 'str', 'order_date': 'object', 'amount': 'int32', 'status': …
    collect() created a million Python Row objects: 8.4 s. toPandas without Arrow went through the same rows: 9.9 s. With Arrow the data crossed as columnar batches: 1.4 s, 7x faster. toArrow(), new in Spark 4.0, skipped pandas entirely: 0.65 s and 42 MiB, half the pandas size, ready for DuckDB or Polars.

  4. Step 4 · An int with a null becomes a float

    n = spark.createDataFrame([(1, 450), (2, None)], "id INT, amount INT")
for arrow in ("false", "true"):
    spark.conf.set("spark.sql.execution.arrow.pyspark.enabled", arrow)
    p = n.toPandas(); print(p.amount.dtype, p.amount.tolist())
    == 4) types change on the way: nulls in int columns arrow=false: amount dtype float64, values [450.0, nan] arrow=true : amount dtype float64, values [450.0, nan]
    pandas’ classic int64 cannot hold a missing value, so both paths turned the column into float64: 450 became 450.0 and null became NaN. Code that checks dtype == int or writes the data back can break. Fill or cast before converting, or convert to nullable Int64 in pandas.

  5. Step 5 · pandas back to Spark

    pdf = pd.DataFrame({"id": np.arange(1_000_000), "amount": rng.integers(50, 900, 1_000_000)})
for arrow in ("false", "true"):
    spark.conf.set("spark.sql.execution.arrow.pyspark.enabled", arrow)
    s = spark.createDataFrame(pdf); s.count()
    == 5) pandas -> Spark createDataFrame(pandas) arrow=false: 11.82 s createDataFrame(pandas) arrow=true : 2.58 s
    Going the other way, Arrow cut 11.8 s to 2.6 s. This matters when a Python model scores data in pandas and the results go back into a Spark table. For big data, though, prefer pandas UDFs (Lesson 6.6), which run pandas code on the executors in parallel.

  6. Step 6 · The driver’s safety limit

    spark = SparkSession.builder.config("spark.driver.maxResultSize", "50m").getOrCreate()
big.collect()                     # 5 million rows
big.groupBy("city").agg(F.sum("amount").alias("rev")).toPandas()
    == 6) maxResultSize protects the driver collect() of 5M rows failed after 1.1 s: Total size of serialized results of 1 tasks (63.9 MiB) is bigger than spark.driver.maxResultSize (50.0 MiB) aggregate first, then collect: (8, 2)
    Collecting 5 million rows failed after 1.1 s: the serialized result of one task, 63.9 MiB, was bigger than the 50 MiB limit, and Spark aborted the job before the driver could run out of memory. That is what maxResultSize is for; do not raise it to “fix” a collect. The right fix is on the last line: aggregate first, then bring back 8 rows.

6 Real-world use

Driver-side data at work

1. Charts and reports

Notebooks aggregate in Spark and convert the small result with toPandas for matplotlib or Plotly.

Spark aggregate→toPandas→Chart

2. Arrow-native tools

Results move to DuckDB or Polars through toArrow without a pandas copy.

Spark→toArrow→DuckDB / Polars

3. Small lookups for code

Lists of active cities or thresholds are collected (a few rows) to drive the rest of the job.

Tiny table→collect→Python logic

4. Single-node model training

A sampled or aggregated training set is converted to pandas for scikit-learn when it fits on one machine.

Sample→toPandas→scikit-learn

5. Pushing rows to an API

toLocalIterator streams rows partition by partition to an external service without holding all of them.

DataFrame→toLocalIterator→API calls
