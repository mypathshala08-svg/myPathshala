1 The story

“It worked yesterday”

Before you start: the SparkSession and a first DataFrame in 4.1.

TiffinGo’s nightly job reads a CSV export of 2 million orders with inferSchema=True. One night a partner sent amounts like 450.5 instead of 450. Spark quietly inferred double instead of int, the table write failed on a type mismatch, and the dashboard stayed empty until noon.

R> Sir, inference saves so much typing. Why not always use it? A> Because the data decides your types, and the data changes. Inference also costs an extra pass over the file. In production we declare the schema: in a DDL string or a StructType. K> And when I build small DataFrames in tests from Python lists? A> Same rules apply, with a few surprises. Today we create DataFrames every common way, break inference on purpose, declare schemas with nested types, save a schema as JSON, and time inference on 2 million rows. All outputs are real (PySpark 4.3.0).
2 Definition

Creating DataFrames and schemas

Formal definition (write this in exams)

A DataFrame’s schema is a StructType: an ordered list of StructFields, each with a name, a data type and a nullable flag. Types include atomic types (IntegerType, LongType, DoubleType, DecimalType(p,s), StringType, BooleanType, DateType, TimestampType) and complex types (ArrayType, MapType, nested StructType). SparkSession.createDataFrame() builds a DataFrame from local data (tuples, Rows, dicts, pandas, NumPy) or an RDD; when no types are given, PySpark infers them from the data, otherwise the data is verified against the supplied schema. Data sources infer schemas from files (for CSV only with inferSchema, which requires an extra pass over the data) or use a schema supplied with .schema().

In simple words

Every DataFrame has a list of column names and types. You can let Spark guess them from the data, or write them yourself. Guessing is handy for exploring but slow on big files and unsafe when the data changes; writing the schema makes jobs fast and predictable.

LEVELS> Schemas at three levels L1> A form with labelled boxes
  • A schema is the printed form: each box has a name and says what may go in it (a number, a date, text).
  • Inference is guessing the form by looking at the answers people wrote; one odd answer changes the guess.
  • Declaring the schema is printing the form first, so wrong answers are noticed.
L2> The API
  • spark.createDataFrame(data, schema): data is a list of tuples, Rows or dicts, a pandas DataFrame or an RDD; schema is a list of names, a DDL string ("id INT, city STRING") or a StructType.
  • Files: spark.read.schema(…).csv(…), or inferSchema=True (CSV) and automatic inference (JSON).
  • df.schema, df.printSchema(), df.schema.json(), StructType.fromJson().
L3> What the lab showed
  • Python ints became bigint; [1, 2.5] failed with CANNOT_MERGE_TYPE; [1, "two"] silently became strings; dict keys came out sorted.
  • A declared DECIMAL refused Python int and float; nullable=False rejected None.
  • On 2M CSV rows, inferSchema ran 2 jobs and took 4.6 s before any query; an explicit schema took 0 jobs.
/LEVELS EXAM> “Why define a schema instead of inferSchema?” Inference needs an extra pass over the data (2 jobs and 4.6 s on our 2M-row CSV, 0 jobs with a schema), and the inferred types depend on the data, so one unusual value changes them. A declared schema is faster, stable across runs and documents the data contract.

4 Step by step

Every way in, and where inference breaks

All outputs are real: PySpark 4.3.0, local mode. Step 6 reads a 2-million-row CSV export of TiffinGo orders.

  1. Step 1 · From Python objects

    spark.createDataFrame([(1, "Idli", 60.0), (2, "Dosa", 90.5)], ["id", "dish", "price"])
spark.createDataFrame([Row(id=1, dish="Idli", veg=True)])
spark.createDataFrame([{"id": 1, "dish": "Idli", "on": dt.date(2026, 11, 4)}])
spark.createDataFrame(pd.DataFrame({"id": [1, 2], "price": [60.0, 90.5]}))
sc.parallelize([(1, "a")]).toDF(["id", "code"])
spark.range(0, 10, 2)
    == 1) list of tuples, column names only [('id', 'bigint'), ('dish', 'string'), ('price', 'double')] == 2) Row objects / dicts / pandas / RDD / range Row : [('id', 'bigint'), ('dish', 'string'), ('veg', 'boolean')] dict : [('dish', 'string'), ('id', 'bigint'), ('on', 'date')] pandas: [('id', 'bigint'), ('price', 'double')] RDD : [('id', 'bigint'), ('code', 'string')] range : [('id', 'bigint')] 5 rows
    Every route gives a DataFrame with a schema. Python int always became bigint. Look at the dict: the columns came out sorted by name (dish, id, on), not in the order we wrote them. Use tuples with names, or Rows, when column order matters.

  2. Step 2 · Breaking inference

    spark.createDataFrame([(1,), (2.5,)], ["v"])
spark.createDataFrame([(1,), ("two",)], ["v"])
spark.createDataFrame([(None,), (None,)], ["v"])
    == 3) inference problems int then float : PySparkTypeError: [CANNOT_MERGE_TYPE] Can not merge type `LongType` and `DoubleType`. int then string : [('v', 'string')] -> ['1', 'two'] all None : PySparkValueError: [CANNOT_DETERMINE_TYPE] Some of types cannot be determined after inferring.
    Three outcomes, only two of them loud. An int and a float could not be merged; a column with only None had no type at all. But an int and a string were silently turned into strings: 1 became "1". Silent changes are the dangerous ones.

  3. Step 3 · A DDL schema is checked

    ddl = "order_id INT, city STRING, amount DECIMAL(10,2), order_ts TIMESTAMP"
for v in (450, 450.75, Decimal("450.75")):
    spark.createDataFrame([(1, "Pune", v, dt.datetime(2026, 11, 4, 20, 15))], ddl)
    == 4) DDL string schema int -> PySparkTypeError: [FIELD_DATA_TYPE_UNACCEPTABLE_WITH_NAME] field amount: DecimalType(10,2) can not accept object 450 in type <class 'int'>. float -> PySparkTypeError: [FIELD_DATA_TYPE_UNACCEPTABLE_WITH_NAME] field amount: DecimalType(10,2) can not accept object 450.75 in type <class 'float'>. Decimal -> OK 450.75 root |-- order_id: integer (nullable = true) |-- city: string (nullable = true) |-- amount: decimal(10,2) (nullable = true) |-- order_ts: timestamp (nullable = true)
    A DDL string is the shortest way to declare a schema. PySpark verifies local data against it: a DECIMAL column accepted only Python Decimal, not int or float. Money belongs in DECIMAL, never double, so this strictness protects you.

  4. Step 4 · StructType and nullable

    schema = StructType([StructField("order_id", IntegerType(), nullable=False),
                     StructField("city", StringType(), True)])
spark.createDataFrame([(1, "Pune"), (None, "Delhi")], schema)
spark.createDataFrame([("x", "Pune")], schema)
    == 5) StructType with nullable=False None in non-nullable: PySparkValueError [FIELD_NOT_NULLABLE_WITH_NAME] field order_id: This field is not nullable, but got None. wrong type : PySparkTypeError [FIELD_DATA_TYPE_UNACCEPTABLE_WITH_NAME] field order_id: IntegerType() can not accept object 'x' in type <class 'str'>.
    StructType says the same as DDL in Python objects, plus nullable. For local data both a None in a non-nullable column and a wrong type were rejected immediately. (For files, Spark treats read columns as nullable; checks on nulls belong in your data-quality step, Lesson 4.4.)

  5. Step 5 · Nested types and schema as JSON

    nested = StructType([StructField("restaurant_id", IntegerType()),
    StructField("tags", ArrayType(StringType())),
    StructField("contact", StructType([StructField("phone", StringType()), StructField("email", StringType())])),
    StructField("prices", MapType(StringType(), IntegerType()))])
n.select("restaurant_id", n.tags[0], "contact.email", n.prices["thali"])
StructType.fromJson(json.loads(n.schema.json())) == n.schema
    == 6) nested types root |-- restaurant_id: integer (nullable = true) |-- tags: array (nullable = true) | |-- element: string (containsNull = true) |-- contact: struct (nullable = true) | |-- phone: string (nullable = true) | |-- email: string (nullable = true) |-- prices: map (nullable = true) | |-- key: string | |-- value: integer (valueContainsNull = true) +-------------+----------+------+-----+ |restaurant_id| tag0| email|thali| +-------------+----------+------+-----+ | 2|late-night|k@t.in| 180| +-------------+----------+------+-----+ == 7) schema as JSON and DDL json chars: 560 | {"fields":[{"metadata":{},"name":"restaurant_id","nullable":true,"type":"integer"},{"metad ... round trip equal: True simpleString: struct<restaurant_id:int,tags:array<string>,contact:struct<phone:string,email:string>,prices:map<string,int>> DDL via spark.sql: restaurant_id INT,tags ARRAY<STRING>,contact STRUCT<phone: STRING, email: STRING>,prices MAP<STRING, INT> == 8) empty DataFrame with a schema 0 [('id', 'int'), ('city', 'string')]
    Arrays, structs and maps let one row hold a restaurant’s tags, contact and price list, like the JSON in restaurants.json. Reach inside with tags[0], contact.email and prices["thali"]. A schema can be saved as JSON and loaded back unchanged: keep it in your repository as the data contract. An empty DataFrame with a schema is handy as a starting point for unions.

  6. Step 6 · What inference costs on 2M rows

    spark.read.options(header=True).csv(path)                       # no schema
spark.read.options(header=True, inferSchema=True).csv(path)     # guess types
spark.read.options(header=True).csv(path, schema=big_schema)    # declared
spark.read.options(header=True, inferSchema=True, samplingRatio=0.01).csv(path)
    == 9) reading CSV: inferSchema vs explicit schema (2M rows) no schema : read() 1.4 s, jobs at read: 1 | types ['string', 'string', 'string', 'string'] inferSchema : read() 4.6 s, jobs at read: 2 | types ['int', 'int', 'string', 'date'] explicit schema : read() 0.0 s, jobs at read: 0 | types ['int', 'int', 'string', 'date'] == 10) samplingRatio inferSchema with samplingRatio=0.01: 0.8 s, same types: True
    Without a schema every column is a string, and Spark still ran 1 job to read the header. inferSchema ran 2 jobs and 4.6 s before our query even started, because it read the whole file to guess. The declared schema: 0 jobs, instant. samplingRatio cut inference to 0.8 s and guessed right here, but a sample can miss the one odd value that matters.

6 Real-world use

Schemas at work

1. Data contracts

Teams keep schemas as JSON or DDL in the repository and load them in every job that reads a feed.

schema.json→fromJson→read.schema()

2. Money columns

Payments and invoices use DECIMAL(p,s), never double, so totals do not drift by paise.

amount→DECIMAL(12,2)→Exact sums

3. Nested events

App events with arrays and objects keep their shape as array, struct and map columns.

Event JSON→struct/array→Query fields

4. Test fixtures

Unit tests build small DataFrames from tuples with the production schema.

Tuples→PROD_SCHEMA→Assertions

5. Small lookup tables

Code lists such as city to region are created in code and joined to large tables.

Python list→createDataFrame→Join

Examples are simplified.
