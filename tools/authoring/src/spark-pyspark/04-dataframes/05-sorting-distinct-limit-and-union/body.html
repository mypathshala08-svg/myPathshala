1 The story

“Why is Card a city?”

Before you start: shuffles in 2.4, duplicates in 4.4.

TiffinGo merged orders from its app and from a partner. Both feeds had order_id, city, payment, but the partner wrote payment before city. After app.union(partner) the city report showed thousands of orders from “Card” and “UPI”. No error, no warning.

R> Sir, the columns have the same names. Why did Spark mix them? A> Because union matches columns by position, like SQL UNION ALL. Names are ignored. unionByName matches by name. K> And Riya’s top-5 query takes a second, but sorting the full table takes much longer. Isn’t it the same sort? A> No. Spark knows it only needs five rows and never sorts the rest. Today: sorting and its shuffle, nulls in sort order, limit, distinct counts and every kind of union, with timings on 5 million orders. All outputs are real (PySpark 4.3.0).
2 Definition

Ordering and combining DataFrames

Formal definition (write this in exams)

orderBy (alias sort) returns a DataFrame totally ordered by the given expressions; Spark implements it with a range-partitioning shuffle (sampling the data to choose partition boundaries) followed by a sort within each partition. Ascending order places nulls first and descending order places them last unless specified. sortWithinPartitions sorts each partition without a shuffle. limit(n) returns at most n rows; combined with orderBy it is planned as a top-k operator (TakeOrderedAndProject) that keeps only n rows per partition. distinct removes duplicate rows via an aggregation (a shuffle). union returns all rows of two DataFrames with the same number of columns, resolving columns by position and keeping duplicates (SQL UNION ALL); unionByName resolves by name. intersect, subtract (EXCEPT DISTINCT) and exceptAll implement set operations.

In simple words

A full sort moves data between machines and is expensive; sorting within partitions or taking a top-N is cheap. distinct also needs a shuffle. union simply stacks two DataFrames by column position, so columns must be in the same order; unionByName lines them up by name.

LEVELS> Sort, distinct, limit and union at three levels L1> Exam answer sheets
  • Sorting all sheets of a whole school by marks means collecting them from every class (a shuffle). Sorting inside each class is quick.
  • Finding the top 5 does not need a full sort: each class sends its own top 5 and you pick from those.
  • Stacking two piles of sheets works only if both forms have their boxes in the same order.
L2> The API
  • orderBy/sort (global, shuffle), sortWithinPartitions (no shuffle); F.desc, asc_nulls_last etc.
  • limit(n), distinct(), F.countDistinct, F.approx_count_distinct.
  • union (by position, keeps duplicates), unionByName(allowMissingColumns=True), intersect, subtract, exceptAll.
L3> What the lab showed
  • Sorting 5M orders: 6.7 s and 120 MiB of shuffle; sortWithinPartitions: 2.0 s and no shuffle.
  • orderBy().limit(5) became TakeOrderedAndProject: 0.8 s, no shuffle.
  • Same-typed columns in a different order were unioned silently into the wrong columns; unionByName fixed it.
/LEVELS EXAM> “union vs unionByName?” union matches columns by position and keeps duplicates (UNION ALL); with same-typed columns in a different order it silently puts values in the wrong columns. unionByName matches by name and, with allowMissingColumns=True, fills missing columns with null. Use distinct() after union for SQL UNION semantics.

4 Step by step

Sorting 5 million orders and merging two feeds

All outputs are real: PySpark 4.3.0, local mode with 2 cores, orders_big (5,000,000 rows in Parquet, 2 partitions), 8 shuffle partitions. Timings write to the noop sink so that no output cost is included.

  1. Step 1 · A global sort is a shuffle

    big.orderBy(F.desc("amount")).write.format("noop").mode("overwrite").save()
big.sort("amount").write.format("noop").mode("overwrite").save()
big.sortWithinPartitions(F.desc("amount")).write.format("noop").mode("overwrite").save()
# stages and shuffle bytes from the REST API
    == 1) orderBy vs sort vs sortWithinPartitions (write to noop) orderBy(amount desc) : 6.7 s, new stages 4, shuffle write 120.1 MiB sort('amount') : 7.0 s, new stages 4, shuffle write 120.1 MiB sortWithinPartitions : 2.0 s, new stages 1, shuffle write 0.0 MiB
    orderBy and sort are the same operation: 4 new stages (a sampling job to choose range boundaries, then the shuffle) and 120 MiB written to shuffle files, 6.7–7.0 s. sortWithinPartitions kept every row on its executor: one stage, no shuffle, 2.0 s. Use it when each output file only needs to be sorted inside, for example before writing Parquet for better compression.

  2. Step 2 · Where nulls go

    d = spark.createDataFrame([(1, 300), (2, None), (3, 120)], "id INT, amount INT")
d.orderBy("amount"); d.orderBy(F.desc("amount")); d.orderBy(F.asc_nulls_last("amount"))
df.orderBy("city", F.desc("n"))
    == 2) nulls in sort order asc : [None, 120, 300] desc : [300, 120, None] asc_nulls_last : [120, 300, None] multi-column : [('Delhi', 9), ('Pune', 7), ('Pune', 5)]
    Ascending puts nulls first, descending puts them last: a “cheapest orders” report would start with the unknown ones. asc_nulls_last, desc_nulls_first and friends make it explicit. Multiple columns sort left to right, each with its own direction.

  3. Step 3 · limit and top-N

    top = big.orderBy(F.desc("amount")).limit(5)
top.collect()
big.limit(5).collect()
top.explain()      # TakeOrderedAndProject
    == 3) limit orderBy+limit(5): 0.8 s, shuffle 0.0 MiB limit(5) only : 0.12 s
    Top 5 of 5 million took 0.8 s with no shuffle: the plan is TakeOrderedAndProject, which keeps the 5 largest rows per partition and merges them on the driver. A plain limit(5) (plan CollectLimit) read just enough to return five rows: 0.12 s. Compare with the 6.7 s full sort in Step 1.

  4. Step 4 · distinct and counting distinct values

    big.select("customer_id").distinct().count()
big.select(F.countDistinct("customer_id")).first()
big.select(F.approx_count_distinct("customer_id")).first()
    == 4) distinct and countDistinct distinct().count() : 3999 in 0.89 s countDistinct : 3999 in 0.57 s approx_count_distinct : 3985 in 0.77 s
    Both exact methods found 3,999 customers; both need a shuffle. approx_count_distinct (HyperLogLog, default 5% maximum error) said 3,985, 0.35% off. On billions of rows and in streaming the approximate version is much cheaper, because it shuffles small sketches instead of values.

  5. Step 5 · union matches by position

    a = spark.createDataFrame([(1, "Pune", 450)], "order_id INT, city STRING, amount INT")
b2 = spark.createDataFrame([(2, 380, "Delhi")], "order_id INT, amount INT, city STRING")
a.union(b2).show()                            # types differ
s1 = …"order_id INT, city STRING, payment STRING"
s2 = …"order_id INT, payment STRING, city STRING"
s1.union(s2).show(); s1.unionByName(s2).show(); a.unionByName(b2).show()
a.unionByName(c); a.unionByName(c, allowMissingColumns=True)
    == 5) union is by position union: NumberFormatException [CAST_INVALID_INPUT] The value 'Pune' of the type "STRING" cannot be cast to "BIGINT" because it is malforme … same types, different order -> no error: +--------+----+-------+ |order_id|city|payment| +--------+----+-------+ | 1|Pune| UPI| | 2|Card| Delhi| +--------+----+-------+ +--------+-----+-------+ |order_id| city|payment| +--------+-----+-------+ | 1| Pune| UPI| | 2|Delhi| Card| +--------+-----+-------+ +--------+-----+------+ |order_id| city|amount| +--------+-----+------+ | 1| Pune| 450| | 2|Delhi| 380| +--------+-----+------+ unionByName missing col: AnalysisException [UNRESOLVED_COLUMN_AMONG_FIELD_NAMES] Cannot resolve column name "amount" among (order_id, cit … +--------+----+------+ |order_id|city|amount| +--------+----+------+ | 1|Pune| 450| | 3|Pune| NULL| +--------+----+------+
    When the types clash, union tried to cast Pune to a number and ANSI mode stopped it. When the types match, there is no error: Card landed in city and Delhi in payment, exactly the bug in our story. unionByName put every value in the right column; a missing column was an error until allowMissingColumns=True filled it with null.

  6. Step 6 · Duplicates and set operations

    x = spark.range(0, 6, 1, 2); y = spark.range(3, 9, 1, 3)
u = x.union(y); u.count(), u.distinct().count(), u.rdd.getNumPartitions()
x.intersect(y); x.subtract(y)
z.subtract(w); z.exceptAll(w)
    == 6) union keeps duplicates; partitions add up union rows: 12 | distinct: 9 | partitions: 5 intersect: [3, 4, 5] | subtract: [0, 1, 2] subtract : [2] | exceptAll: [1, 2]
    union kept the overlapping 3, 4, 5 twice: 12 rows, 9 distinct. It did not shuffle; it simply concatenated the partitions, so 2 + 3 = 5 partitions. Repeated unions of many small DataFrames therefore create many partitions (and long lineages, Lesson 3.3). subtract removed duplicates as well, exceptAll removed one copy per match.

6 Real-world use

Sorting and combining at work

1. Leaderboards

Top restaurants, top cities and top customers are orderBy + limit: cheap top-k plans.

Aggregate→orderBy + limit→Top 10

2. Merging feeds

Data from apps, partners and regions is combined with unionByName and allowMissingColumns.

Feeds→unionByName→One table

3. Active-user metrics

Product dashboards use approx_count_distinct for daily and monthly active users.

Events→approx distinct→DAU

4. Reconciliation

exceptAll between yesterday’s and today’s snapshots lists added and removed records.

Two snapshots→exceptAll→Differences

5. Better compressed files

Data is sorted within partitions before writing Parquet so similar values compress well and min/max stats skip more.

DataFrame→sortWithinPartitions→Parquet
