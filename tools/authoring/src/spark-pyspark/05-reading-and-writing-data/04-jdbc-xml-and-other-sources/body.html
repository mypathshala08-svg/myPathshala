1 The story

“A 32-core cluster, and the database load is one task”

Before you start: partitions in 2.1, nested data in 5.1.

TiffinGo’s order service runs on PostgreSQL. Every night a Spark job copies the orders table into the lake. The job runs on 32 cores, yet the Spark UI shows a single task reading for an hour. When Arjun Sir added a partitioned read, three tasks finished in seconds and one ran as long as before.

K> Sir, Spark is parallel. Why does it read a database with one task? A> Because Spark cannot guess how to split an SQL table. Unless you give a numeric partition column, bounds and a number of partitions, it opens one connection and runs one query. R> And the one slow task after partitioning? A> The bounds you give only decide where the ranges are cut; they do not filter rows. If the bounds do not match the data, one range gets almost everything. Today we write and read PostgreSQL, watch the SQL Spark sends, test pushdown, then read XML, text and binary files. All outputs are real (PySpark 4.3.0, PostgreSQL 16).
2 Definition

JDBC and other built-in sources

Formal definition (write this in exams)

The JDBC data source reads tables or query results from relational databases into DataFrames and writes DataFrames to tables, using the database’s JDBC driver. A read is a single partition and a single connection unless partitionColumn, lowerBound, upperBound and numPartitions are given; Spark then issues one query per partition with a range predicate on the partition column, where the bounds only define the partition stride and do not filter the rows. numPartitions also caps concurrent connections for reads and writes. Filters, column selections, and in the V2 path aggregates and limits, are pushed down into the generated SQL when possible. Spark 4.0 added a built-in XML source (rowTag selects the element that forms a row, attributes become _-prefixed fields); other built-in sources include text (one row per line) and binaryFile (one row per file with path, modification time, length and content).

In simple words

JDBC lets Spark talk to databases like PostgreSQL and MySQL. Tell Spark how to split the table, or it reads with one connection. Filters are sent to the database. Spark 4 can also read XML directly, plus plain text and whole binary files.

LEVELS> Databases and other sources at three levels L1> Copying a library catalogue
  • One clerk copying the whole catalogue is slow. Four clerks can split it: A–F, G–M, N–S, T–Z.
  • If you say “split from A to F” but most books start with Z, the last clerk does all the work.
  • Asking the librarian for “only Pune books” is faster than copying all and throwing most away.
L2> The API
  • spark.read.jdbc(url, table, properties=…) or format("jdbc") with dbtable or query; parallel: column/partitionColumn, lowerBound, upperBound, numPartitions; also fetchsize, batchsize.
  • The JDBC driver jar must be on the classpath (--jars or --packages).
  • XML is built in since Spark 4.0: spark.read.option("rowTag", "restaurant").xml(path). Also text, binaryFile.
L3> What the lab showed
  • The first connection failed: PostgreSQL 16 rejected the JVM time zone Asia/Calcutta; -Duser.timezone=Asia/Kolkata fixed it.
  • A plain read was 1 partition. With bounds 1M–6M and 4 partitions the rows split [0, 375,000, 625,000, 0]; with bounds 1M–2M all 1,000,000 rows went to the last partition.
  • A filter became WHERE ("city" = 'Pune') AND ("amount" > 800) in PostgreSQL’s log.
/LEVELS EXAM> “How do you read a large table from a database in parallel?” Use a numeric, evenly distributed column as partitionColumn, set lowerBound/upperBound to its real min and max (query them first) and numPartitions to what the database can handle; remember the bounds do not filter, so wrong bounds create skewed partitions. Push filters down and consider reading from a replica.

4 Step by step

PostgreSQL, XML and friends

All outputs are real: PySpark 4.3.0 in local mode with 4 cores, postgresql-42.7.4.jar, PostgreSQL 16 in Docker with log_statement = 'all' so we can read the SQL Spark sends.

  1. Step 1 · Writing 1M orders to PostgreSQL

    URL = "jdbc:postgresql://localhost:5433/tiffingo"
PROPS = {"user": "postgres", "password": "…", "driver": "org.postgresql.Driver"}
for bs in (1000, 10000):
    orders.repartition(4).write.mode("overwrite").jdbc(URL, "orders", properties={**PROPS, "batchsize": str(bs)})
    == 1) write 1M orders to PostgreSQL first try (JVM time zone Asia/Calcutta): FATAL: invalid value for parameter "TimeZone": "Asia/Calcutta" fixed with -Duser.timezone=Asia/Kolkata batchsize 1000: 34.1 s batchsize 10000: 27.9 s rows in Postgres: 1000000 table created by Spark: order_id bigint, customer_id integer, city text, order_date date, amount integer, status text
    The first attempt failed before writing a row: the JVM reported the old time-zone name Asia/Calcutta and PostgreSQL 16 refused it. Starting the driver with -Duser.timezone=Asia/Kolkata fixed it, a real problem on Indian machines. Then 4 tasks inserted 1M rows; larger batches saved 18%. Spark created the table itself (text for strings): create tables yourself when types and indexes matter.

  2. Step 2 · A plain read is one partition

    d = spark.read.jdbc(URL, "orders", properties=PROPS)
d.rdd.getNumPartitions()
d.agg(F.sum("amount")).first()
    == 2) a plain read is ONE partition partitions: 1 sum: 508841283 in 1.4 s
    One partition means one task, one connection, one query (SELECT … FROM orders), whatever the cluster size. Fine for small tables; for big ones this is the one-hour single task of our story.

  3. Step 3 · A parallel read, and its SQL

    p = spark.read.jdbc(URL, "orders", column="order_id", lowerBound=1_000_000,
                   upperBound=6_000_000, numPartitions=4, properties=PROPS)
p.agg(F.sum("amount")).first()
# WHERE clauses from the PostgreSQL log
p.rdd.glom().map(len).collect()
    == 3) a parallel read partitions: 4 sum: 508841283 in 1.0 s SQL: WHERE "order_id" < 2250000 or "order_id" is null SQL: WHERE "order_id" >= 2250000 AND "order_id" < 3500000 SQL: WHERE "order_id" >= 3500000 AND "order_id" < 4750000 SQL: WHERE "order_id" >= 4750000 rows per partition: [0, 375000, 625000, 0]
    Spark divided 1M–6M into four strides of 1.25M and sent four queries. The first range also takes values below the lower bound and nulls, the last everything above the upper bound. Our million orders had ids between 2.25M and 4.75M, so two partitions were empty and the work split 375,000 / 625,000. Query min and max first and use them as bounds.

  4. Step 4 · Bounds do not filter

    narrow = spark.read.jdbc(URL, "orders", column="order_id", lowerBound=1_000_000,
                        upperBound=2_000_000, numPartitions=4, properties=PROPS)
narrow.count(); narrow.rdd.glom().map(len).collect()
    == 4) bounds do not filter rows: 1000000 | per partition: [0, 0, 0, 1000000]
    Many people expect bounds to filter. They do not: all 1,000,000 rows came back, but every one landed in the last partition (order_id >= 1,750,000), so the “parallel” read was serial again. This is the slow last task of our story. To filter, use where (pushed down) or a subquery in dbtable.

  5. Step 5 · Pushdown and the query option

    f = d.where("city = 'Pune' AND amount > 800").select("order_id", "amount")
f.explain(); f.count()
# SQL from the PostgreSQL log
spark.read.format("jdbc").option("query", "SELECT city, sum(amount) AS revenue FROM orders GROUP BY city")…

With the query option the database did the whole aggregation and returned 8 rows. Push work to the database when it has indexes and the result is small.

6 Real-world use

Databases and other sources at work

1. Database to lake

Order, payment and customer tables are copied nightly or incrementally from replicas into Parquet/Delta.

Replica→parallel JDBC→Lake

2. Results back to apps

Aggregated recommendations or risk scores are written to PostgreSQL/MySQL tables that apps read.

Spark result→JDBC write→App DB

3. XML feeds

Banks, insurers and governments still exchange XML; Spark 4 reads it without extra packages.

XML feed→rowTag→Table

4. Log files

Plain-text logs are read with spark.read.text and parsed with regexp_extract.

Logs→text + regex→Structured

5. Images and documents

binaryFile loads menu photos or invoices with their paths for ML models and OCR.

Files→binaryFile→Model input
