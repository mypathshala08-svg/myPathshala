1 The story

“Seven orders came in, eight went out”

Before you start: schemas in 4.2 and nulls in 4.4.

A new partner sends TiffinGo a daily CSV. On day one Kabir’s job loaded it with the defaults: the report showed eight orders though the partner sent seven, one review was cut in half, and a Delhi order had no amount. Nobody got an error.

K> Sir, Spark read the file. Why is the data wrong? A> Because a CSV is just text, and Spark only knows what you tell it: is there a header, how are quotes escaped, can a value contain a line break, what does a date look like, and what should happen to a bad line? R> And JSON? It has types already. A> JSON has its own traps: one object per line by default, inference that reads everything, and nested data. Today we read the real partner file six ways, keep the bad rows instead of losing them, read JSON lines and a JSON array, flatten nested items, and see why a gzip file is read by one core. All outputs are real (PySpark 4.3.0).
2 Definition

The CSV and JSON data sources

Formal definition (write this in exams)

The CSV and JSON sources are built-in, text-based file data sources of Spark SQL, accessed with spark.read.csv() / .json() or format("csv"|"json"). Both are configured by options: for CSV, among others header, sep, quote, escape, multiLine, nullValue, dateFormat, timestampFormat, inferSchema, enforceSchema; for JSON, multiLine, primitivesAsString, dropFieldIfAllNull. Malformed input is handled by the parse mode: PERMISSIVE (default) sets unparsable fields to null and, if a string field named by columnNameOfCorruptRecord exists in the schema, stores the raw record there; DROPMALFORMED drops such records; FAILFAST raises an exception. JSON is read as JSON Lines (one object per line) unless multiLine is set, and its schema is inferred from all records unless one is supplied. Files compressed with a non-splittable codec such as gzip are processed by a single task per file.

In simple words

CSV and JSON are text, so Spark needs to be told how to read them: header, quotes, line breaks, dates, nulls, and what to do with bad lines. Give a schema, keep bad lines in a corrupt-record column, and remember that one gzip file is read by one core.

Words you’ll meet in this lesson

LEVELS> Reading text files at three levels L1> A handwritten register
  • A CSV is a register where commas separate the columns. If someone writes a comma inside a name, you need quotes to know it is one name.
  • If a note continues on the next line, you must know it is still the same entry.
  • Some entries are unreadable: decide whether to keep them aside, skip them, or stop.
L2> The API
  • spark.read.csv(path, header=True, schema=…, multiLine=True, escape='"', mode=…, dateFormat=…, nullValue=…).
  • Modes: PERMISSIVE (default, bad fields → null, raw line in _corrupt_record if it is in the schema), DROPMALFORMED, FAILFAST.
  • spark.read.json(path) expects JSON Lines; use multiLine=True for a JSON array or pretty-printed file.
L3> What the lab showed
  • Defaults turned 7 orders into 8 rows; multiLine and escape='"' gave 7 correct rows.
  • DROPMALFORMED kept 6 rows for count() but 4 when all columns were read: CSV parsing depends on the columns you select.
  • A gzip CSV was read as one partition: 3.4 s against 2.0 s for the plain file split into 7.
/LEVELS EXAM> “How do you handle corrupt records in CSV?” Read with an explicit schema that includes a string column _corrupt_record in PERMISSIVE mode, cache the result, split good rows from rows where _corrupt_record is not null, and write the bad rows to a quarantine table with a count. Use FAILFAST when any bad row must stop the pipeline; avoid DROPMALFORMED because rows disappear without a trace.

WARN> _corrupt_record has two traps. Spark refuses queries that reference only that column on a raw file (UNSUPPORTED_FEATURE.QUERY_ONLY_CORRUPT_RECORD_COLUMN), so cache or save the parsed data first. And the CSV parser only converts the columns your query needs, so which rows count as “bad” depends on the columns you select (Step 4).

  4. Step 4 · DROPMALFORMED, FAILFAST, and a surprise

    dm = spark.read.csv(path, schema=schema, mode="DROPMALFORMED", **opts)
dm.count(); len(dm.collect())
spark.read.csv(path, schema=schema, mode="FAILFAST", **opts).collect()

    == 5) DROPMALFORMED and FAILFAST DROPMALFORMED count() : 6 DROPMALFORMED all columns : 4 FAILFAST: [MALFORMED_RECORD_IN_PARSING.WITHOUT_SUGGESTION] Malformed records are detected in record parsing: [9003,Delhi,null,20759,Late] == 5b) bad rows depend on the columns you read select order_id, city, _corrupt_record: 1 select all columns : 3
    FAILFAST stopped at order 9003. DROPMALFORMED is stranger: count() said 6, but collecting all columns gave 4. The CSV reader only converts the columns a query needs (column pruning), so a bad amount is not noticed when amount is not read. The same happened with the corrupt-record column: 1 bad row when reading three columns, 3 when reading all. Decide bad rows on the full schema, once, then work from the cached or written result.

6 Real-world use

CSV and JSON at work

1. Partner and bank files

Settlement and partner feeds arrive as CSV; jobs read them with a fixed schema, a corrupt-record column and control totals.

CSV drop→schema + PERMISSIVE→Clean + quarantine

2. App events

Mobile and web events land as JSON Lines in object storage and are flattened with explode and struct access.

JSON Lines→explode→Event tables

3. API exports

Pretty-printed JSON arrays from APIs are read with multiLine and a schema.

API dump→multiLine→DataFrame

4. Raw to columnar

Text files are read once in a “bronze” step and written as Parquet or Delta for every later job (Lesson 5.2).

CSV / JSON→read once→Parquet

5. Spreadsheet exports

Exports from Excel use doubled quotes and local date formats: escape and dateFormat options are standard.

Excel CSV→escape='"'→Correct values
