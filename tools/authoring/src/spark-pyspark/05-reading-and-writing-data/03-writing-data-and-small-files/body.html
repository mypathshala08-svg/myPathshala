1 The story

“Where did Delhi go?”

Before you start: partitions and shuffles in 2.4, formats in 5.2.

A bug in Pune’s prices had to be fixed in the daily revenue table, partitioned by city. Riya recomputed Pune and wrote it with mode("overwrite"). The Pune numbers were right the next morning. Every other city was gone.

R> Sir, I only wrote Pune rows. Why were the other folders deleted? A> Because by default an overwrite replaces the whole table path, not just the partitions in your DataFrame. That is “static” partition overwrite. With partitionOverwriteMode=dynamic Spark replaces only the partitions you write. K> And why does the same table have 421 tiny files? A> That is the other classic: every task writes its own file into every folder it touches. 2 Definition

Writing DataFrames

Formal definition (write this in exams)

DataFrameWriter (df.write) saves a DataFrame through a data source. Each task writes its partition of the data to one or more part files in the output directory, and a commit protocol makes the result visible atomically, marked by a _SUCCESS file. The save mode defines behaviour when the target exists: errorifexists (default), append, overwrite or ignore. partitionBy(cols) writes a directory hierarchy col=value/, and readers prune directories that do not satisfy filters on those columns (partition pruning). Because every task writes a separate file for every partition directory it holds rows for, the number of files can grow to tasks × partition values (the small-files problem). With overwrite, static mode (default) deletes all existing partitions of the target first, whereas dynamic mode overwrites only partitions present in the data being written.

In simple words

When Spark writes, each task writes its own file, and partitionBy makes a folder per value. Plan the number of files, partition by columns you filter on, and use dynamic overwrite when you replace only some partitions.

LEVELS> Writing data at three levels L1> Filing papers
  • Each worker puts their own pile of papers in the cabinet; ten workers make ten files.
  • Folders per city let you open only the Pune folder later.
  • If every worker drops one sheet into every folder, you get thousands of single sheets: hard to find anything.
L2> The API
  • df.write.mode(m).format(f).option(…).partitionBy(cols).save(path) or .saveAsTable(name); modes: errorifexists (default), append, overwrite, ignore.
  • File count = number of tasks that write × partition folders each task touches. Control it with repartition/coalesce and maxRecordsPerFile.
  • spark.sql.sources.partitionOverwriteMode: static (default) or dynamic.
L3> What the lab showed
  • A groupBy result written with partitionBy("city") made 421 files of about 1 KiB; repartition("city") first made 8, read back 4.8x faster.
  • Partition pruning read 498,646 of 5,000,000 rows for a Pune query.
  • Static overwrite of one city deleted the others; dynamic overwrite replaced only Pune.
/LEVELS EXAM> “What is the small-files problem and how do you fix it?” Each write task creates one file per partition folder it touches, so a shuffle with 200 partitions written with partitionBy can produce thousands of tiny files; listing and opening them makes reads slow and stresses the NameNode or object store. Fix it with repartition(partition_cols) or coalesce before writing, AQE partition coalescing, maxRecordsPerFile, and periodic compaction (OPTIMIZE in Delta).

Set spark.sql.sources.partitionOverwriteMode=dynamic (per session or per write with .option("partitionOverwriteMode", "dynamic")) for jobs that rewrite only some days or cities, or use a table format with replaceWhere/MERGE.
4 Step by step

Writes, folders and files

All outputs are real: PySpark 4.3.0, local mode with 4 cores, the 5-million-row orders table, default 200 shuffle partitions (AQE partition coalescing switched off so the effect is visible).

  1. Step 1 · What a write produces

    small = orders.limit(1000).repartition(3)
small.write.parquet(f"{O}/first")
sorted(os.listdir(f"{O}/first"))
    == 1) what a write produces ._SUCCESS.crc .part-00000-36b64a16-f017-4372-82ed-099b6761e8d2…appy.parquet.crc .part-00001-36b64a16-f017-4372-82ed-099b6761e8d2…appy.parquet.crc .part-00002-36b64a16-f017-4372-82ed-099b6761e8d2…appy.parquet.crc _SUCCESS part-00000-36b64a16-f017-4372-82ed-099b6761e8d2-…0.snappy.parquet part-00001-36b64a16-f017-4372-82ed-099b6761e8d2-…0.snappy.parquet part-00002-36b64a16-f017-4372-82ed-099b6761e8d2-…0.snappy.parquet
    Three partitions became three part files named part-0000N-<job uuid>-c000.snappy.parquet, plus _SUCCESS, written last when the job committed. Readers ignore files starting with _ or .; the .crc checksums are added by Hadoop’s local file system. On S3 or HDFS you will see only the part files and _SUCCESS.

  2. Step 2 · Save modes

    small.write.parquet(path)                    # again: default mode
small.write.mode("ignore").parquet(path)
small.write.mode("append").parquet(path)
small.write.mode("overwrite").parquet(path)
    == 2) save modes default (errorifexists): AnalysisException [PATH_ALREADY_EXISTS] Path file:/root/lab/spark/data/m5/out/first already exists. Set mode as … ignore : 1000 rows append : 2000 rows, 6 files overwrite: 1000 rows, 3 files
    The default refused to touch an existing path. ignore silently did nothing, append added 3 more files (2,000 rows), overwrite replaced everything. Re-running an append job after a failure duplicates data: design jobs to be safely re-runnable (overwrite a partition, or MERGE in a table format).

  3. Step 3 · partitionBy and pruning

    orders.write.partitionBy("city").parquet(f"{O}/by_city")
p = spark.read.parquet(f"{O}/by_city"); p.columns
p.where("city = 'Pune'").select("amount").explain()
# same query on the flat table vs the partitioned one
    == 3) partitionBy: folders per value ['._SUCCESS.crc', '_SUCCESS', 'city=Bengaluru', 'city=Chennai'] … 10 entries columns: ['order_id', 'customer_id', 'order_date', 'amount', 'status', 'city'] == Physical Plan == *(1) Project [amount] +- *(1) ColumnarToRow +- FileScan parquet [amount,city] … PartitionFilters: [isnotnull(city), (city = Pune)] == 4) partition pruning not partitioned : 0.47 s, rows read 5,000,000 partitioned by city : 0.19 s, rows read 498,646
    Spark created a folder per city. The city values now live in folder names, not in the files, and come back as the last column when read. The plan shows PartitionFilters: the Pune query listed and read only city=Pune/, 498,646 rows instead of 5 million, 2.5x faster.

  4. Step 4 · The small-files problem

    agg = orders.groupBy("city", "order_date").agg(F.sum("amount").alias("revenue"), F.count("*").alias("orders"))
agg.write.partitionBy("city").parquet(f"{O}/daily")              # 200 tasks after the shuffle
agg.repartition("city").write.partitionBy("city").parquet(f"{O}/daily2")
    == 5) the small-files problem after groupBy (200 shuffle partitions): 421 files, avg 1.0 KiB, write 10.9 s read back: 1.33 s repartition('city') first : 8 files, avg 1.8 KiB, write 5.4 s read back: 0.28 s
    After the groupBy, the data sat in 200 shuffle partitions, each holding a few dates of every city, so each task wrote a file into every city folder: 421 files of 1 KiB, 10.9 s to write and 1.33 s to read back a tiny table. repartition("city") put each city in one task: 8 files, 5.4 s to write and 0.28 s to read. On object stores, where listing and opening files is slow, the gap is far bigger.

  5. Step 5 · Capping file size

    orders.repartition(1).write.option("maxRecordsPerFile", 1_000_000).parquet(f"{O}/capped")
    == 6) maxRecordsPerFile 5 files: [6.9, 6.9, 6.9, 6.9, 6.9] MiB
    One task wrote 5 million rows but rolled over to a new file every million: five files of 6.9 MiB. Use it to keep files in a sensible size range when one partition is large, without an extra shuffle. Aim for roughly 128 MB to 1 GB per file in big tables.

  6. Step 6 · Overwriting one partition, and tables

    base.write.partitionBy("city").parquet(path)          # Pune, Delhi, Mumbai
spark.conf.set("spark.sql.sources.partitionOverwriteMode", mode)
fix.write.mode("overwrite").partitionBy("city").parquet(path)   # only Pune rows
agg.repartition("city").write.mode("overwrite").partitionBy("city").saveAsTable("daily_city")
    == 7) overwrite one partition: static vs dynamic static : folders ['._SUCCESS.crc', '_SUCCESS', 'city=Pune'] -> rows [('Pune', 999)] dynamic : folders ['._SUCCESS.crc', '_SUCCESS', 'city=Delhi', 'city=Mumbai', 'city=Pune'] -> rows [('Delhi', 380), ('Mumbai', 610), ('Pun … == 8) tables instead of paths 8 partitions | 61 Pune rows ['Type: MANAGED', 'Provider: parquet', 'Location: file:/root/lab/spark/data/m5/warehouse/daily_city']
    Riya’s accident, reproduced: in static mode the Pune fix wiped Delhi and Mumbai. In dynamic mode only city=Pune was replaced. Finally, saveAsTable registered a managed, partitioned table in the catalog: other jobs and SQL users refer to daily_city by name, and Spark knows its partitions (Module 7).

6 Real-world use

Writing data at work

1. Daily partitioned tables

Fact tables are partitioned by date; each run writes only its day with dynamic overwrite, so re-runs are safe.

Day’s data→dynamic overwrite→dt=2026-11-04

2. File-size control

Writers repartition by partition columns and cap records per file so tables keep 128 MB–1 GB files.

DataFrame→repartition + cap→Healthy files

3. Compaction jobs

Streaming tables collect small files all day; a nightly job rewrites them into large files.

Small files→compaction→Large files

4. Tables, not paths

Outputs are saved as catalog tables so analysts query names and the platform tracks schemas and partitions.

DataFrame→saveAsTable→SQL by name

5. Single-file exports

Small partner exports use coalesce(1) to produce one CSV; never for large data.

Small result→coalesce(1)→One CSV
