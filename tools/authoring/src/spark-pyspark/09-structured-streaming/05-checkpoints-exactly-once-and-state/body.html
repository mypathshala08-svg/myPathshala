1 The story

“Finance found 600 extra orders”

Before you start: sources, sinks and foreachBatch in 9.2, watermarks in 9.3, RDD checkpointing in 3.3.

A TiffinGo streaming job crashed at 2 a.m. and restarted automatically. Nothing was lost, but the next morning the PostgreSQL city totals were higher than the orders in the lake. The difference was exactly one micro-batch.

K> Sir, Spark promises exactly-once. How did one batch get written twice? A> Spark guarantees that each batch’s data is processed exactly once into its state and committed exactly once in its checkpoint. But if your sink wrote the batch and the job died before the commit, Spark replays that batch. A plain append then writes it again. R> So the sink must cope with replays? A> Yes: idempotent writes keyed by batch_id. Today we restart a Kafka query from its checkpoint, open the checkpoint folder, crash a sink on purpose, deduplicate replayed events with state, and break a checkpoint by changing the query. All outputs are real (PySpark 4.3.0, Kafka 3.9).
2 Definition

Checkpoints, exactly-once and state

Formal definition (write this in exams)

The checkpoint location is a fault-tolerant directory (HDFS, S3, ADLS…) where a streaming query records, before each micro-batch, the source offsets it will process (write-ahead log), and after it the batch commit, together with versioned state store files for stateful operators. On restart Spark reads the last offsets and commits: an uncommitted batch is re-executed with the same offsets and batch id, and processing continues. Structured Streaming therefore provides end-to-end exactly-once semantics when the source is replayable and the sink is idempotent (it ignores or overwrites a batch it has already written, as the file sink does with its _spark_metadata log). Stateful operators keep data across batches in a state store (HDFS-backed by default, or RocksDB for large state), bounded by watermarks. The checkpoint is tied to the query: incompatible changes to stateful operators, such as a new grouping key schema, cannot reuse it.

In simple words

The checkpoint is the query’s memory: what it planned to read, what it finished, and its running state. After a crash Spark redoes any unfinished batch with exactly the same input. That gives exactly-once results only if the output can safely receive the same batch twice; file sinks can, your own foreachBatch code must be written to.

LEVELS> Fault tolerance at three levels L1> A cashier’s register book
  • Before counting a bundle, the cashier writes “bundle 7: notes 101–200” (offsets). After putting it in the safe, she ticks “bundle 7 done” (commit).
  • After a power cut she redoes any bundle without a tick. If the safe already had that bundle, she must check the bundle number first (idempotent) or the money is counted twice.
L2> The pieces
  • option("checkpointLocation", path): offsets, commits, state, sources, metadata.
  • Sources must be replayable (Kafka, files); sinks idempotent (file/table sinks, or foreachBatch keyed by batch_id).
  • State: dropDuplicatesWithinWatermark, aggregations, joins; RocksDB via spark.sql.streaming.stateStore.providerClass.
L3> What the lab showed
  • Restart read only batch 1 (500 new rows); the file sink had 1,500 distinct orders.
  • Crash after writing batch 1: append wrote 2,099 rows for 1,500; idempotent writes kept 1,500.
  • Changing the grouping key type on an old checkpoint failed with STATE_STORE_KEY_SCHEMA_NOT_COMPATIBLE.
/LEVELS EXAM> “How does Structured Streaming achieve exactly-once?” Replayable sources (Kafka offsets, file lists) + a checkpoint with a write-ahead log of offsets and commit log + deterministic re-execution of uncommitted batches with the same batch id + idempotent sinks (file/table sinks, or foreachBatch writes keyed by batch_id/MERGE). State is checkpointed per batch. Without an idempotent sink you get at-least-once.

What you can change on a checkpoint

WARN> Never share one checkpoint between two queries, never copy a checkpoint to “restart from yesterday”, and never delete the _spark_metadata folder of a file sink: readers use it to ignore files of uncommitted batches. Keep checkpoints on durable storage (not a local disk of a driver that can disappear), and treat them as part of the job: version the path when the logic changes.
4 Step by step

Breaking a stream on purpose

All outputs are real: PySpark 4.3.0, local[2], Kafka 3.9 in Docker with a 2-partition topic pay. Queries use trigger(availableNow=True) so “stop” and “restart” are just two runs on the same checkpoint.

  1. Step 1 · Restart from the checkpoint

    produce(0, 1000)
stream().writeStream.format("parquet").option("path", OUT) \
        .option("checkpointLocation", CK + "/files").trigger(availableNow=True).start().awaitTermination()
produce(1000, 500)
# same query, same checkpoint
    == 1) run, stop, produce more, restart from the checkpoint run 1: batches [0] | rows in sink: 1000 run 2: batches [1] | rows in sink: 1500 | distinct order_id: 1500
    Run 1 read the 1,000 events as batch 0. After 500 more events, the restarted query ran only batch 1 with the new rows: 1,500 rows in the sink and 1,500 distinct order ids. No duplicates and nothing missed.

  2. Step 2 · Inside the checkpoint

    for d in sorted(os.listdir(CK + "/files")): print(d, os.listdir(…))
print(open(CK + "/files/offsets/1").read().splitlines()[-1])
    == 2) what is in a checkpoint commits ['0', '1'] metadata offsets ['0', '1'] sources ['0'] offsets/1: {"pay":{"0":762,"1":738}} sink log: ['0', '1']
    offsets/1 was written before batch 1 ran: “read partition 0 up to 762 and partition 1 up to 738”. commits/1 was written after it succeeded. If a crash happens between the two, Spark replays batch 1 with exactly those offsets. The Parquet sink keeps its own log (_spark_metadata/0, 1) to skip a batch it already wrote.

  3. Step 3 · A crash inside foreachBatch

    def fb(df, bid):
    rows = df.count()
    if kind == "append": store["append"].append((bid, rows))      # INSERT
    else:                store["idempotent"][bid] = rows          # upsert by batch_id
    if bid == 1 and first_attempt:
        raise RuntimeError("simulated crash after writing batch 1")
# maxOffsetsPerTrigger=600 → batches of 599, 599, 302; start, crash, start again
    == 3) a crash inside foreachBatch: replay = at-least-once append attempt 1: FAILED (simulated crash) append attempt 2: finished append: writes [(0, 599), (1, 599), (1, 599), (2, 302)] -> total rows 2099 (source has 1500) idempotent attempt 1: FAILED (simulated crash) idempotent attempt 2: finished idempotent: writes [(0, 599), (1, 599), (2, 302)] -> total rows 1500 (source has 1500)
    Both sinks wrote batch 1 and then “crashed” before Spark could commit it. On restart Spark replayed batch 1 (same id, same 599 rows). The append sink now has batch 1 twice: 2,099 rows for 1,500 orders, exactly the finance bug. The idempotent sink stored by batch_id, so the replay overwrote itself: 1,500. In a database, use MERGE/upsert or delete-then-insert by batch id in one transaction.

  4. Step 4 · Deduplicating with state (RocksDB)

    spark.conf.set("spark.sql.streaming.stateStore.providerClass",
               "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
produce(0, 300)      # the producer re-sends 300 old orders
ded = events.withWatermark("timestamp", "10 minutes").dropDuplicatesWithinWatermark(["order_id"])
    == 4) stateful dedup with watermark + RocksDB state store input rows: 1800 | output rows: 1500 | state rows: 1500 | provider: RocksDB
    Producers retry, so Kafka often contains duplicates. 1,800 events came in, 1,500 unique orders came out: each order id is remembered in the state store and later copies are dropped. With the watermark, ids older than 10 minutes are forgotten, so state stays bounded. RocksDB keeps state off the JVM heap, the usual choice for millions of keys.

  5. Step 5 · Changing a stateful query

    agg1 = stream().groupBy((F.col("order_id") % 3).alias("k")).count()                    # run once
agg2 = stream().groupBy((F.col("order_id") % 3).cast("string").alias("k")).count()   # same checkpoint
    == 5) changing a stateful query on an old checkpoint ERROR: [STATE_STORE_KEY_SCHEMA_NOT_COMPATIBLE] Provided key schema does not match existing state key schema. Please check number and type of fields. Existing key_schema=StructType(StructField(_groupingexpression,LongType,true)) and new k
    The state store holds keys with the old schema (a long). The new query’s key is a string, so restarting on the same checkpoint failed with STATE_STORE_KEY_SCHEMA_NOT_COMPATIBLE as soon as a batch ran. Changing stateful logic means a new checkpoint (and usually reprocessing from the source), so plan it like a migration.

6 Real-world use

Reliable streaming at work

1. Payments and finance

Totals are upserted by batch id or business key so restarts never double-count.

Payments→idempotent MERGE→Correct totals

2. Event deduplication

Retried app events are deduplicated within a watermark before analytics.

Raw events→dedup within watermark→Unique events

3. Large state

Per-user features over millions of users run on the RocksDB state store.

Users→RocksDB→Stable memory

4. Safe deployments

Checkpoint paths carry a version; incompatible changes go to v2 with a backfill.

New logic→ck/v2→Backfill

5. Durable checkpoints

Checkpoints live on S3/ADLS/HDFS so a new driver on any node can resume.

Driver dies→same checkpoint→Resume
