1 The story

“Which orders were not delivered in 30 minutes?”

Before you start: watermarks in 9.3, joins in 6.2, batch windows in 6.3.

TiffinGo promises delivery in 30 minutes. Orders and delivery confirmations arrive on two different Kafka topics. Operations wants a live list of late orders, plus app usage per user session and orders per 5 minutes.

K> Sir, joining two tables is easy. Why is joining two streams special? A> When an order arrives, its delivery has not happened yet. Spark must keep the order in state until a matching delivery comes, or until it is sure none will. Without limits, it would remember every order forever. R> And the windows? A> Tumbling, sliding and session windows answer different questions. Today we compute all three on the same clicks, then do a stream-static join and a stream-stream join with watermarks, including an outer join that reports the undelivered orders. All outputs are real (PySpark 4.3.0).
2 Definition

Windowed aggregations and stream joins

Formal definition (write this in exams)

A windowed aggregation groups a stream by event-time buckets. Tumbling windows are fixed, non-overlapping intervals (window(ts, "5 minutes")); sliding windows have a length and a slide, so each event belongs to several windows (window(ts, "10 minutes", "5 minutes")); session windows (session_window(ts, gap)) grow while events keep arriving within the gap and close after a period of inactivity. A stream-static join joins each micro-batch with a static DataFrame and is stateless; inner and left outer (stream on the left) are supported. A stream-stream join buffers rows of both streams in state so future rows can match past ones; to bound that state and to emit outer-join results, both inputs need watermarks and the join condition needs an event-time range constraint.

In simple words

Windows put events into time buckets: fixed boxes (tumbling), overlapping boxes (sliding) or activity-based boxes (sessions). Joining a stream with a fixed table is simple. Joining two streams means keeping rows from both sides until matches arrive; watermarks and a time limit in the join tell Spark when it can forget them.

LEVELS> Windows and joins at three levels L1> A restaurant’s day
  • Tumbling: “orders per hour”, each hour its own box. Sliding: “orders in the last hour, checked every 15 minutes”. Session: “one visit = until the guest leaves for more than 30 minutes”.
  • Stream-stream join: the waiter keeps each order slip on the counter until the dish is served, and throws away slips older than the kitchen’s promise.
L2> The API
  • F.window(ts, "5 minutes"), F.window(ts, "10 minutes", "5 minutes"), F.session_window(ts, "5 minutes").
  • Stream-static: stream.join(static_df, key, how).
  • Stream-stream: watermarks on both sides + a time-range condition, e.g. deliver_ts BETWEEN order_ts AND order_ts + INTERVAL 30 MINUTES.
L3> What the lab showed
  • 5 clicks: tumbling 3/1/1, sliding 3/4/2/1 (each click in 2 windows), 4 sessions for 2 users.
  • Stream-static left join kept order 103 with a null restaurant.
  • Stream-stream left outer join emitted orders 2 and 3 with null delivery once the watermark passed; without watermarks state grew 4 → 7 → 9.
/LEVELS EXAM> “How do stream-stream joins work in Spark?” Both streams are buffered in a state store so rows can match rows that arrive later. For inner joins, watermarks plus an event-time range condition let Spark drop old state; for outer joins they are required, because unmatched rows are emitted with nulls only when the watermark guarantees no match can still arrive. Stream-static joins need no state; the static side is re-read per batch unless cached.

WARN> A stream-stream join without watermarks works, and that is the trap: results look right in testing while state grows with every row (4 → 7 → 9 rows in our tiny lab, millions in production) until batches slow down and executors run out of memory. Always add withWatermark on both inputs and a time bound in the join condition. Outer results also arrive late by design: an unmatched order appears only after the watermark has passed its 30-minute limit.
4 Step by step

Windows, then joins

All outputs are real: PySpark 4.3.0, local[2], UTC. Inputs are JSON files read as streams; for the stream-stream join each file is one micro-batch (maxFilesPerTrigger=1) so the order of arrival is controlled.

  1. Step 1 · Tumbling and sliding windows

    c = spark.readStream.schema("ts timestamp, user string").json(clicks)
c.groupBy(F.window("ts", "5 minutes")).count()                 # tumbling
c.groupBy(F.window("ts", "10 minutes", "5 minutes")).count()   # sliding
    == 1) tumbling 5 min [('10:00', '10:05', 3), ('10:05', '10:10', 1), ('10:10', '10:15', 1)] == 2) sliding 10 min every 5 min (each event in 2 windows) [('09:55', '10:05', 3), ('10:00', '10:10', 4), ('10:05', '10:15', 2), ('10:10', '10:20', 1)]
    Tumbling: each click lands in exactly one 5-minute box: 3, 1, 1. Sliding windows of 10 minutes every 5 minutes overlap, so each click is counted twice (3 + 4 + 2 + 1 = 10 = 5 × 2). Note the 09:55 window: sliding windows start before the first event. Sliding is for “last 10 minutes, updated every 5”.

  2. Step 2 · Session windows

    c.groupBy("user", F.session_window("ts", "5 minutes")).count()
    == 3) session window, gap 5 min, per user [('u1', '10:00', '10:07', 2), ('u1', '10:09', '10:14', 1), ('u2', '10:03', '10:08', 1), ('u2', '10:12', '10:17', 1)]
    u1 clicked at 10:00 and 10:02, so the session runs from 10:00 to 10:07 (last event + 5-minute gap). The 10:09 click came after the gap closed, so it opened a new session. Session windows have no fixed length; they follow user activity.

  3. Step 3 · Stream-static join

    rest = spark.createDataFrame([(1, "Biryani House", "Mumbai"), (2, "Dosa Point", "Pune")], …)
o.join(rest, "rest_id")            # inner
o.join(rest, "rest_id", "left")    # left outer, stream on the left
    == 4) stream-static join: orders stream + restaurants table inner: [(101, 'Biryani House'), (102, 'Dosa Point')] left : [(101, 'Biryani House'), (102, 'Dosa Point'), (103, None)]
    Each micro-batch of orders is joined with the restaurant table like a normal batch join: no state, no watermark. Order 103 has an unknown restaurant: dropped by the inner join, kept with None by the left join. If the static table changes, re-read it per batch (it is not cached unless you cache it).

  4. Step 4 · Stream-stream join with watermarks

    os_ = orders_stream.withWatermark("order_ts", "10 minutes")
ds  = deliveries_stream.withWatermark("deliver_ts", "10 minutes")
cond = F.expr("d_order_id = order_id AND deliver_ts BETWEEN order_ts AND order_ts + INTERVAL 30 MINUTES")
os_.join(ds, cond, "inner")  /  os_.join(ds, cond, "leftOuter")
    == 5) stream-stream join: orders x deliveries within 30 min, with watermarks [inner] batch 0: [(1, '10:25')] [inner] batch 1: [(4, '10:30')] [inner] batch 2: [(5, '11:40')] [inner] batch 3: [] state rows at end: 2 [leftOuter] batch 0: [(1, '10:25')] [leftOuter] batch 1: [(4, '10:30')] [leftOuter] batch 2: [(5, '11:40')] [leftOuter] batch 3: [(2, None), (3, None)] state rows at end: 2
    Order 1 matched its 10:25 delivery as soon as it arrived. Order 2 was delivered at 10:50, more than 30 minutes after 10:05, so it does not match. Orders 2 and 3 found no delivery and stayed in state, waiting, while later orders 4 and 5 matched in their batches. The left outer join emitted orders 2 and 3 with null in batch 3, only after the watermark (from 11:40 events) proved no delivery could still qualify. State ended at 2 rows.

  5. Step 5 · Without watermarks

    orders.join(deliveries, F.expr("d_order_id = order_id"))   # no watermark, no time bound
    == 6) stream-stream join without watermark: state never cleaned state rows per batch: [4, 7, 9]
    Same data, no watermarks: the join still produces matches, but state rows only grow, 4 → 7 → 9, because Spark can never be sure an old order will not get a delivery. In production this is a slow memory leak.

6 Real-world use

Windows and joins at work

1. Delivery SLAs

Orders joined with deliveries within 30 minutes; unmatched orders become alerts.

Orders ⋈ deliveries→left outer→Late list

2. Ad attribution

Clicks joined with impressions within an hour to compute click-through rates.

Impressions ⋈ clicks→1 h range→CTR

3. Session analytics

Session windows measure visit length and pages per visit.

Clicks→session_window→Sessions

4. Moving averages

Sliding windows give “orders in the last 15 minutes, every minute” for surge pricing.

Orders→sliding window→Surge signal

5. Enrichment

Events are joined with dimension tables (restaurants, zones) as stream-static joins.

Event stream→⋈ dimension→Enriched
