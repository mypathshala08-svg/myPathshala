1 The story

“The 10:00 numbers changed at 10:25”

Before you start: streaming basics in 9.1, sources and foreachBatch in 9.2, dates and timestamps in 6.4.

TiffinGo’s live dashboard showed revenue per 5-minute window. Rider phones without network uploaded orders late, so the 10:00 window kept changing long after 10:05. Finance asked a simple question: when is a window final?

K> Sir, why not group by the time the event reaches Kafka? Then nothing is late. A> Then a phone that was offline would put a 10:02 order into the 10:25 window: wrong revenue. We group by event time, the time inside the record. Late data is normal; the question is how long to wait for it. R> And Spark waits forever? A> Without a watermark, yes: it keeps every window in state and can update any of them. With a watermark it can finalise windows, drop data that is too late, and free memory. Today we see this batch by batch, in all three output modes. All outputs are real (PySpark 4.3.0).
2 Definition

Output modes, event time and watermarks

Formal definition (write this in exams)

Event time is the timestamp embedded in a record, as opposed to processing time when Spark sees it. Event-time aggregations such as groupBy(window("event_time", "5 minutes")) keep per-window state across micro-batches so late, out-of-order records update the right window. A watermark, defined with withWatermark(col, delay), is computed as the maximum event time seen minus the delay; Spark guarantees that records newer than the watermark are processed, may drop records older than it, and removes state for windows that end before it. The output mode controls what each micro-batch writes: complete rewrites the whole result table, update writes only rows changed in this batch, and append writes only rows that will never change again, which for aggregations requires a watermark.

In simple words

Event time is when something really happened. Spark keeps window results in memory so late events can still be added. A watermark says “I will wait this long for late data”: after that a window is final, it can be written once, and its memory is freed. Output modes decide whether you write everything, only changes, or only final rows.

LEVELS> Event time at three levels L1> Exam papers by post
  • Papers are dated when written (event time) but arrive by post over days (processing time).
  • The examiner announces: “I will accept papers up to 5 days after the latest date I have seen.” That rule is the watermark. Results are published once a date is safely past it.
L2> The API
  • df.withWatermark("event_time", "5 minutes") before a stateful operation.
  • groupBy(F.window("event_time", "5 minutes")) for event-time windows.
  • writeStream.outputMode("append" | "update" | "complete").
L3> What the lab showed
  • append on an aggregation without watermark: STREAMING_OUTPUT_MODE.UNSUPPORTED_OPERATION.
  • With the watermark, each window was emitted once, when the watermark passed its end; state shrank to 2 rows.
  • A 10:03 order arriving after the 10:00 window was finalised was dropped (numRowsDroppedByWatermark = 1); without a watermark it changed 1419 to 9196.
/LEVELS EXAM> “What is a watermark?” A threshold on event time, max(event_time) − allowed delay, that tells Spark how long to wait for late data. Windows ending before it are finalised: emitted in append mode and removed from state; records older than it may be dropped. It bounds state for streaming aggregations, deduplication and stream-stream joins, and is required for append mode with aggregations.

WARN> A watermark is a lower bound on what is kept, not an exact cut-off. In our run a 10:02 order arrived in the same batch that closed its window and was still counted, but a 10:03 order arriving one batch later was dropped. And append mode adds latency: a window is written only after the watermark passes its end, so the 10:00 window appeared two batches after its last event. Pick the delay from how late your data really is, not from how fast you want results.
4 Step by step

Five batches, three output modes

All outputs are real: PySpark 4.3.0, local[2], UTC. One JSON file per micro-batch (maxFilesPerTrigger=1, files ordered by time) so every run sees the same batches. foreachBatch prints what each mode writes; progress shows the watermark and the state store.

  • Batch 0: 10:01 (100), 10:02 (200), 10:04 (50)
  • Batch 1: 10:06 (300), 10:03 (70) late, 10:11 (20)
  • Batch 2: 10:16 (10), 10:02 (999) late, 10:12 (40)
  • Batch 3: 10:22 (5)
  • Batch 4: 10:03 (7777) very late, 10:24 (1)

plain = ev.groupBy(w5).agg(F.sum("amount").alias("revenue"))
plain.writeStream.outputMode("complete").foreachBatch(show).start()

    Every batch rewrites all windows. Late rows land in the right window: 10:03 (70) raised 10:00 from 350 to 420. Without a watermark the very late 7777 also went in: 1419 → 9196. State rows only grow (1 → 5): fine for 5 windows, fatal for a stream that runs for months.

  2. Step 2 · update mode

    plain.writeStream.outputMode("update").foreachBatch(show).start()
    == 2 update (outputMode=update) [update] batch 0: [('10:00', 350)] [update] batch 1: [('10:00', 420), ('10:05', 300), ('10:10', 20)] [update] batch 2: [('10:00', 1419), ('10:10', 60), ('10:15', 10)] [update] batch 3: [('10:20', 5)] [update] batch 4: [('10:00', 9196), ('10:20', 6)] progress batch 0: watermark None | state rows 1 | dropped late 0 progress batch 1: watermark None | state rows 3 | dropped late 0 progress batch 2: watermark None | state rows 4 | dropped late 0 progress batch 3: watermark None | state rows 5 | dropped late 0 progress batch 4: watermark None | state rows 5 | dropped late 0
    Same state, but each batch writes only the windows that changed: batch 3 wrote just 10:20. Good for sinks that can upsert (a database keyed by window). Still no watermark, so state still grows and very late data is still accepted.

  3. Step 3 · append without a watermark

    plain.writeStream.outputMode("append").foreachBatch(show).start()
    == 3 append-no-watermark (outputMode=append) ERROR: [STREAMING_OUTPUT_MODE.UNSUPPORTED_OPERATION] Invalid streaming output mode: append. This output mode is not supported for streaming aggregations without watermark on str
    Refused before any data is read. Append means “write a row once, never change it”, but without a watermark Spark can never know a window is final.

  4. Step 4 · append with a 5-minute watermark

    wm = ev.withWatermark("event_time", "5 minutes").groupBy(w5).agg(F.sum("amount").alias("revenue"))
wm.writeStream.outputMode("append").foreachBatch(show).start()
    == 4 append-watermark (outputMode=append) [append] batch 0: [] [append] batch 1: [] [append] batch 2: [('10:00', 1419)] [append] batch 3: [('10:05', 300)] [append] batch 4: [('10:10', 60)] [append] batch 5: [] progress batch 0: watermark 1970-01-01T00:00:00.000Z | state rows 1 | dropped late 0 progress batch 1: watermark 2026-11-05T09:59:00.000Z | state rows 3 | dropped late 0 progress batch 2: watermark 2026-11-05T10:06:00.000Z | state rows 3 | dropped late 0 progress batch 3: watermark 2026-11-05T10:11:00.000Z | state rows 3 | dropped late 0 progress batch 4: watermark 2026-11-05T10:17:00.000Z | state rows 2 | dropped late 1 progress batch 5: watermark 2026-11-05T10:19:00.000Z | state rows 2 | dropped late 0
    Batches 0 and 1 wrote nothing: no window was final yet. After batch 1 the max event time was 10:11, so the watermark became 10:06 and the 10:00–10:05 window was emitted in batch 2 as 1419, once. Each later batch finalised one more window. In batch 4 the 7777 order (10:03) was older than the watermark (10:17) and its window was gone: dropped late 1. State stayed at 2–3 rows.

    == 5 update-watermark (outputMode=update) [update] batch 0: [('10:00', 350)] [update] batch 1: [('10:00', 420), ('10:05', 300), ('10:10', 20)] [update] batch 2: [('10:00', 1419), ('10:10', 60), ('10:15', 10)] [update] batch 3: [('10:20', 5)] [update] batch 4: [('10:20', 6)] [update] batch 5: [] progress batch 0: watermark 1970-01-01T00:00:00.000Z | state rows 1 | dropped late 0 progress batch 1: watermark 2026-11-05T09:59:00.000Z | state rows 3 | dropped late 0 progress batch 2: watermark 2026-11-05T10:06:00.000Z | state rows 3 | dropped late 0 progress batch 3: watermark 2026-11-05T10:11:00.000Z | state rows 3 | dropped late 0 progress batch 4: watermark 2026-11-05T10:17:00.000Z | state rows 2 | dropped late 1 progress batch 5: watermark 2026-11-05T10:19:00.000Z | state rows 2 | dropped late 0

6 Real-world use

Event time at work

1. Live dashboards

Per-minute counts in update mode, upserted into a serving table.

Events→update mode→Upsert

2. Final hourly tables

Append mode with a watermark writes each hour once to the lake.

Events→append + watermark→Hourly table

3. Device telemetry

Sensors buffer readings offline; event time keeps them in the right minute.

Buffered readings→event time→Correct minutes

4. Delivery SLAs

Late-delivery rates per 15-minute window feed operations alerts.

Deliveries→windows→Alerts

5. Late-data audits

Dropped-row metrics are tracked to tune the watermark delay.

Progress metrics→dropped rows→Tune delay
