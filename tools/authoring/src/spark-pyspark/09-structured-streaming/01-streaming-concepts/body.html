1 The story

“Can the dashboard update every few seconds?”

Before you start: DataFrames in 4.1, groupBy in 6.1, reading files in 5.1.

TiffinGo’s city dashboard was refreshed by a batch job every hour. During a festival sale, operations wanted live order counts per city, within seconds, and asked the data team to “make the batch job run every 5 seconds”.

K> Sir, can’t we just run the same Spark job in a loop? A> You would re-read everything each time and lose track of what was already counted. Structured Streaming does the loop for you: it remembers what it has read, processes only new rows in each micro-batch, and keeps the running totals. R> Do we need a new API? A> Almost the same DataFrame API: readStream instead of read, writeStream.start() instead of write. Today we start our first streaming queries and read their progress. All outputs are real (PySpark 4.3.0).
2 Definition

Structured Streaming

Formal definition (write this in exams)

Structured Streaming is Spark’s stream processing engine built on the Spark SQL engine. A data stream is modelled as an unbounded input table to which new rows are appended; a query on it is written with the same DataFrame/SQL API as a batch query, and Spark runs it incrementally, by default as a series of micro-batches. Each micro-batch reads new data from the source (tracked as offsets), updates any state such as running aggregates, and writes results to a sink according to the output mode. A trigger decides when micro-batches run (as fast as possible, at fixed intervals, once over all available data, or continuously). Progress and offsets are stored in a checkpoint location, which allows end-to-end exactly-once results with replayable sources and idempotent sinks.

In simple words

Structured Streaming lets you write a normal DataFrame query and run it on data that keeps arriving. Spark treats the stream as a growing table, processes the new rows in small batches, remembers where it stopped, and keeps running totals up to date.

LEVELS> Streaming at three levels L1> A bank passbook
  • You do not reprint the whole passbook after every deposit. The clerk prints only the new entries and the new balance.
  • The last printed line is the bookmark (checkpoint); the balance is the state.
L2> The API
  • spark.readStream.format(...).load() gives a streaming DataFrame (isStreaming = True).
  • Transform it like any DataFrame, then df.writeStream.format(...).outputMode(...).trigger(...).option("checkpointLocation", ...).start() returns a StreamingQuery.
  • Monitor with q.status, q.lastProgress, q.recentProgress; stop with q.stop() or wait with awaitTermination().
L3> What the lab showed
  • An action like count() on a streaming DataFrame fails; only writeStream.start() runs it.
  • With a 2 s trigger and 50 rows/s, each batch read 100 rows and took about 0.4 s.
  • availableNow processed 3 files in 3 batches and stopped; rerun with the same checkpoint read only the new file.
/LEVELS EXAM> “What is Structured Streaming?” A stream-processing engine on Spark SQL that treats a stream as an unbounded table and runs a DataFrame/SQL query on it incrementally in micro-batches (or continuous mode). You define source, transformations, sink, output mode and trigger; progress and state are saved in a checkpoint, giving fault tolerance and exactly-once results with replayable sources and idempotent sinks.

Triggers

TriggerCodeBehaviourUse
Default(none)Next batch as soon as the previous endsLow latency
Fixed intervaltrigger(processingTime="2 seconds")One batch every intervalSteady load

WARN> trigger(once=True) is deprecated; use availableNow=True, which respects rate limits such as maxFilesPerTrigger and splits the work into several batches. And always set a checkpointLocation on real sinks: without it Spark uses a temporary folder and a restart reprocesses everything from the start.
4 Step by step

Your first streaming queries

All outputs are real: PySpark 4.3.0, local[2]. The rate source generates rows with a timestamp and an increasing value, ideal for testing; later lessons use Kafka and files.

  1. Step 1 · A streaming DataFrame

    s = spark.readStream.format("rate").option("rowsPerSecond", 50).load()
print("isStreaming:", s.isStreaming); s.printSchema()
s.count()     # a batch action
    == 1) a streaming DataFrame isStreaming: True root |-- timestamp: timestamp (nullable = true) |-- value: long (nullable = true) ERROR: Queries with streaming sources must be executed with writeStream.start(), or from a streaming table or flow definition within a Spark Declarative Pipe
    readStream returns a DataFrame with a schema, but nothing has been read yet. Calling a batch action like count() fails, because a stream has no end to count to. Streaming queries only run through writeStream…start().

  2. Step 2 · Micro-batches and progress

    orders = s.select("timestamp", (F.col("value") % 4).alias("city_id"), (F.col("value") % 500).alias("amount"))
agg = orders.groupBy("city_id").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue"))
q = (agg.writeStream.format("memory").queryName("rev").outputMode("complete")
        .trigger(processingTime="2 seconds").option("checkpointLocation", CK + "/a").start())
# every 2.2 s: q.lastProgress
    == 2) micro-batches with a 2 s trigger (memory sink) batch 0: numInputRows 0 | inputRows/s 0.0 | processedRows/s 0.0 | triggerExecution 1909 ms batch 2: numInputRows 50 | inputRows/s 47.4 | processedRows/s 119.6 | triggerExecution 418 ms batch 3: numInputRows 100 | inputRows/s 50.0 | processedRows/s 274.7 | triggerExecution 364 ms batch 4: numInputRows 100 | inputRows/s 50.0 | processedRows/s 181.2 | triggerExecution 552 ms +-------+------+-------+ |city_id|orders|revenue| +-------+------+-------+ | 0| 88| 15312| | 1| 88| 15400| | 2| 87| 15138| | 3| 87| 15225| +-------+------+-------+ status: Waiting for next trigger | isActive: True after stop isActive: False
    The groupBy is exactly the batch code. Spark ran a micro-batch every 2 s: at 50 rows per second each batch read 100 rows and took about 0.4 s, so the query keeps up (processed rows/s > input rows/s). The memory sink holds the running totals, readable with SQL. q.status shows “Waiting for next trigger” between batches.

  3. Step 3 · availableNow and the checkpoint

    fs = spark.readStream.schema("order_id long, amount long").option("maxFilesPerTrigger", 1).json(src)
q2 = fs.writeStream.format("parquet").option("path", OUT) \
       .option("checkpointLocation", CK + "/b").trigger(availableNow=True).start()
q2.awaitTermination()
# add f3.json, start the same query again
    == 3) trigger availableNow over files batches: [(0, 100), (1, 100), (2, 100)] | rows: 300 | stopped by itself: True rerun with same checkpoint: [(3, 50)] -> only the new file | total rows: 350
    Three JSON files, one per batch (maxFilesPerTrigger=1), and the query stopped by itself. After adding a fourth file, the same query with the same checkpoint ran batch 3 with only the 50 new rows: total 350, nothing read twice. This is how many teams run “streaming” jobs on a schedule: incremental, cheap, and restartable.
