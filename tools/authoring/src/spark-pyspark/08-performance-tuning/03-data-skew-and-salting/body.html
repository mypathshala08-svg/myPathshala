1 The story

“199 tasks done, 1 task running”

Before you start: partitions in 8.1, join strategies in 8.2, windows in 6.3, AQE in 7.4.

TiffinGo signed a cloud-kitchen chain that now takes 60% of all orders. Overnight, the restaurant ranking job went from minutes to hours. The Spark UI showed 199 finished tasks and one task still running.

K> Sir, Spark has 200 cores. Why is only one working? A> Because all rows with the same key must go to the same partition after a shuffle. If one restaurant has 60% of the rows, one task gets 60% of the work. That is data skew. R> Can we just add more machines? A> No: one task runs on one core, however big the cluster. We have to spread the hot key. Today we measure skew in task metrics, see why groupBy survives it, and fix joins and windows with salting, AQE and splitting the hot key. All outputs are real (PySpark 4.3.0).
2 Definition

Data skew and salting

Formal definition (write this in exams)

Data skew is an uneven distribution of rows across partitions, usually because a few join or grouping keys are far more frequent than the rest. Since a hash shuffle sends all rows of a key to one partition, a hot key creates a straggler task that dominates the stage’s runtime and may spill or run out of memory. Skew is diagnosed from the task summary metrics of a stage (max vs median duration, shuffle read size and records). Salting adds a random or derived component to the key so a hot key is spread over several partitions: for joins the other side is replicated once per salt value, and for aggregations results are combined in a second stage. Adaptive Query Execution can split skewed sort-merge join partitions automatically.

In simple words

Skew is when one key has many more rows than others, so one task does most of the work and the whole stage waits for it. Salting adds a random number to the hot key so its rows are spread across many tasks, and then the results are combined.

LEVELS> Skew at three levels L1> One busy billing counter
  • A supermarket opens 8 counters, but everyone with a loyalty card must use counter 4. Seven cashiers wait while one queue never ends.
  • Salting: give loyalty customers a random counter number 1–8 and let every counter handle them.
L2> The tools
  • Detect: Spark UI task summary (max vs median duration and shuffle read), groupBy(key).count().
  • Fix joins: AQE skew join (spark.sql.adaptive.skewJoin.*), broadcast the other side, or salt: (F.rand() * S).cast("int") on the big side, F.explode(F.sequence(0, S-1)) on the small side.
  • Fix aggregations: partial aggregation (automatic), or two-stage salted aggregation. Fix windows: handle the hot key separately.
L3> What the lab showed
  • Window by restaurant: one task read 3.9M rows vs 0.28M, 5.5 s vs 0.7 s.
  • groupBy on the same key: max task 73 ms, because map-side partial aggregation shrank the shuffle to ~800 rows per task.
  • Salting evened rows per task (min/max 819K/864K); AQE split the hot join partition (max 2.8 s → 1.3 s).
/LEVELS EXAM> “How do you handle data skew in Spark?” First confirm it in the Spark UI task summary (max far above median). For joins, broadcast the small side if possible, rely on AQE skew-join splitting, or salt: add a random salt 0..S-1 to the skewed side and explode the other side over all salts, then join on (key, salt). For aggregations, aggregate on (key, salt) then on key. For hot keys like nulls or defaults, filter or handle them separately.

WARN> Salting multiplies the other side by S. In our lab the menu side became 16x larger, so the salted join read about 850K records per task and was not faster on our 2-CPU machine (5.66 s vs 5.16 s), even though tasks were perfectly even. Salting pays off on a real cluster where idle cores can take the extra tasks. Choose S from the skew ratio (hot partition ÷ median), salt only the hot keys if you can, and try AQE or a broadcast first.
4 Step by step

Measuring and fixing skew

All outputs are real: PySpark 4.3.0, local[4] (2 physical CPUs), AQE off unless stated, 8 shuffle partitions. 6,000,000 orders where restaurant 1 has 60%. Task durations and shuffle records come from the REST API task list of the reduce stage.

  1. Step 1 · A skewed window

    o = spark.range(N).select(F.col("id").alias("order_id"),
      F.when(F.col("id") % 10 < 6, F.lit(1)).otherwise((F.col("id") % 4000) + 2).alias("rest_id"), …)
w = Window.partitionBy("rest_id").orderBy("amount")
run("window by rest_id", sink(heavy(o).withColumn("rk", F.row_number().over(w)))); tasks(st)
    top keys: +-------+-------+ |rest_id| count| +-------+-------+ | 1|3600000| | 51| 1500| | 71| 1500| +-------+-------+ only showing top 3 rows == 1) skewed window (per restaurant ranking) window by rest_id : 17.22 s, tasks 12, spill mem 0.0 MiB disk 0.0 MiB stage 5: 8 tasks | duration ms min 740 median 2652 max 5504 | records read min 279000 max 3897000
    Restaurant 1 has 3.6 million orders; the next has 1,500. In the window stage one task read 3,897,000 records while the smallest read 279,000, and ran 5.5 s vs 0.74 s. The median task was done in 2.7 s and then waited. On a 200-core cluster this is 199 idle cores.

  2. Step 2 · Why the groupBy did not suffer

    run("groupBy rest_id sum", sink(o.groupBy("rest_id").agg(F.sum("amount")))); tasks(st)
    == 2) groupBy is fine: partial aggregation before shuffle groupBy rest_id sum : 1.01 s, tasks 12, spill mem 0.0 MiB disk 0.0 MiB stage 7: 8 tasks | duration ms min 38 median 64 max 73 | records read min 744 max 852
    Same hot key, but each reduce task read only about 800 records: every map task first summed its own rows per restaurant (partial aggregation), so restaurant 1 arrived as one row per map task, not 3.6 million. Sums and counts are naturally skew-resistant. collect_list, countDistinct and windows are not.

  3. Step 3 · A skewed join

    spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)
menu = spark.range(400000).select(F.when(F.col("id") < 200, F.lit(1))
          .otherwise(F.col("id") % 4000 + 2).alias("rest_id"), F.col("id").alias("item"))
j = o.sample(0.05, 7).join(menu, "rest_id")
    == 3) skewed join (hot key both sides, no broadcast) skewed join (5% sample) : 5.16 s, tasks 16, spill mem 0.0 MiB disk 0.0 MiB stage 10: 8 tasks | duration ms min 556 median 1027 max 2830 | records read min 61896 max 244169
    Restaurant 1 is hot on both sides (200 menu items), so its partition produces 36 million output rows. The hot task read 244K records vs a minimum of 62K and ran 2.8 s vs median 1.0 s.

  4. Step 4 · Salting the join

    S = 16
os_ = o_s.withColumn("salt", (F.rand(1) * S).cast("int"))
ms  = menu.withColumn("salt", F.explode(F.sequence(F.lit(0), F.lit(S - 1))))
js  = os_.join(ms, ["rest_id", "salt"]).drop("salt")
print(j.count() == js.count())
    == 4) salting the join: explode menu side, random salt on orders same row count: True salted join, S=16 : 5.66 s, tasks 16, spill mem 0.0 MiB disk 0.0 MiB stage 21: 8 tasks | duration ms min 1189 median 1889 max 2482 | records read min 819245 max 864318
    Each order picks a random salt 0–15; each menu row is copied 16 times, once per salt. Every order still meets every matching menu item exactly once (same row count: True), but restaurant 1 is now spread over 16 keys. Records per task became nearly equal: 819K to 864K. The price: the menu side is 16x bigger, so on our 2 CPUs the total time did not improve. With idle cores on a cluster, even tasks finish together.

  5. Step 5 · Let AQE split it

    spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "1m")   # small lab
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "2")
run("AQE skew join", sink(o_s.join(menu, "rest_id")))
    == 5) AQE skew join does it automatically AQE skew join : 2.91 s, tasks 19, spill mem 0.0 MiB disk 0.0 MiB stage 26: 11 tasks | duration ms min 197 median 403 max 1293 | records read min 61896 max 97624
    No code change: AQE saw the hot partition after the shuffle and split it, so the stage ran 11 tasks instead of 8, max records per task fell from 244K to 98K, and the slowest task from 2.8 s to 1.3 s. Total 2.91 s, the best of all join runs. Defaults (5x median and 256 MB) are much higher than our lab values.

  6. Step 6 · Handle the hot key separately

    hot, cold = o.filter("rest_id = 1"), o.filter("rest_id <> 1")
# hot key: sort in parallel by amount using range partitioning
run("hot key alone", sink(heavy(hot).repartitionByRange(8, "amount").sortWithinPartitions("amount")))
run("cold keys window", sink(heavy(cold).withColumn("rk", F.row_number().over(w))))
    == 6) two-stage salted window alternative: split hot key hot key alone, range-partitioned : 7.00 s, tasks 16, spill mem 0.0 MiB disk 0.0 MiB stage 34: 8 tasks | duration ms min 241 median 458 max 483 | records read min 420000 max 504000 cold keys window : 3.77 s, tasks 12, spill mem 0.0 MiB disk 0.0 MiB stage 36: 8 tasks | duration ms min 376 median 553 max 797 | records read min 279000 max 319500
    Windows cannot be salted directly, because a rank needs all rows of the key. But a single hot key can be ordered with range partitioning on the order column: each of 8 tasks sorts one range (420K–504K records, max 0.48 s), and the rank is the range offset plus the position inside it. The remaining keys are balanced. Together 10.8 s vs 17.2 s, and no task above 0.8 s.

6 Real-world use

Skew at work

1. Marketplaces

A few big sellers or restaurants dominate orders; joins on seller_id need AQE or salting.

Big seller→salt / AQE→Even tasks

2. Guest users

Events without a user_id share one NULL key; filtering them before joins removes the skew.

NULL keys→filter→Balanced join

3. Clickstreams

A bot generating millions of clicks becomes a hot session; handle it separately or drop it.

Bot session→isolate→Normal sessions

4. City-level reports

Metro cities dominate; aggregations stay fast thanks to partial aggregation.

City key→partial agg→Fast groupBy

5. Monitoring

Alerts fire when a stage’s max task time exceeds 5x its median.

Task metrics→ratio > 5→Alert
