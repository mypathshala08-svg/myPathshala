2 Definition

Profiling and tracking from code

Formal definition (write this in exams)

Profiling measures where a program spends time or memory. PySpark provides a session-level UDF profiler (Spark 4.0+; spark.sql.pyspark.udf.profiler = perf or memory) that runs cProfile or memory_profiler inside Python workers and aggregates results on the driver, and an older RDD profiler enabled with spark.python.profile. The StatusTracker is a low-level API exposing weakly consistent information about active jobs and stages.

In simple words

A profiler tells you which Python lines are slow inside Spark; the StatusTracker tells your program how far a running job has got.

Why, how, where

Why

The Spark UI shows stages and tasks, not which Python line is slow. Long jobs also need progress reporting in schedulers, notebooks or custom dashboards.

the problem it solves

How

Set spark.sql.pyspark.udf.profiler to perf (cProfile) or memory (memory_profiler); run the query; read the results with spark.profile.show() or dump(). For RDD code, the older spark.python.profile=true + sc.show_profiles(). For progress, sc.statusTracker() returns job and stage info; sc.setJobGroup labels jobs.

the mechanism

Where

Slow UDF investigations, code reviews before production, notebook progress bars, orchestration that reports progress or cancels a job group.

in real systems

When not

Profiling adds overhead: use it on samples, not in production runs. StatusTracker is weakly consistent and keeps only recent jobs (spark.ui.retainedJobs).

Dissect a profile line

LEVELS> Profiling and tracking at three levels L1> A stopwatch per cook
  • The restaurant board (Spark UI) shows which orders are late. To know why, you time each cook’s steps (profiler). The manager’s tablet shows live “4 of 8 dishes done” (StatusTracker).
L2> The settings and calls
  • spark.conf.set("spark.sql.pyspark.udf.profiler", "perf") (or "memory", needs memory_profiler); run; spark.profile.show(type="perf"), spark.profile.dump(path), spark.profile.clear(). Works for Python, pandas and Arrow UDFs, also with Spark Connect.
  • Classic: spark.python.profile=true at startup, then sc.show_profiles() / sc.dump_profiles(path); custom classes via SparkContext(profiler_cls=…) (BasicProfiler by default).
  • st = sc.statusTracker(): getActiveJobsIds(), getActiveStageIds(), getJobIdsForGroup(g), getJobInfo(id) (status, stageIds), getStageInfo(id) (numTasks, numActiveTasks, numCompletedTasks, numFailedTasks).
L3> Gotchas
  • On Python 3.12+ the classic profiler and the UDF profiler cannot run in the same session: we got ValueError: tool 2 is already in use. Use one at a time.
  • cProfile columns: ncalls, tottime (inside the function), cumtime (including callees). Look for huge call counts first.
  • Job groups also allow sc.cancelJobGroup(g); spark.addTag/interruptTag do the same for Spark Connect.

  • Myth: The Spark UI shows slow Python lines.
    Reality (Spark 4.3): It stops at the worker; use the profiler.
    Proof: Step 1.
  • Myth: UDFs are fine if they are short.
    Reality (Spark 4.3): 10.2 M hidden calls in one line.
    Proof: Step 1.
  • Myth: Progress needs the UI.
    Reality (Spark 4.3): StatusTracker from code.
    Proof: Step 3.
EXAM> “How do you profile PySpark?” Spark 4 UDF profiler (spark.sql.pyspark.udf.profiler = perf or memory; spark.profile.show or dump); classic spark.python.profile with sc.show_profiles (BasicProfiler, cProfile); StatusTracker (getJobInfo, getStageInfo, getActiveJobsIds) and job groups; fix hot spots with built-in functions.

Profile, fix, track

All outputs are real: PySpark 4.3.0, local[2], Python 3.13.

band = udf(slow_band, "string")

    29.5 s for 400,000 rows. 12.6 million Python calls; 10.2 million of them are the generator on line 11.

  2. Step 2 · Fix with built-ins

    n = F.split("item", "-").getItem(1).cast("int")
F.when(((n - 1) * n * (2 * n - 1) / 6) % 3 == 0, "hot").otherwise("cold")
    == 2) after the fix: built-in functions, no Python UDF job took 0.85 s (sum of squares 0..n-1 = (n-1)n(2n-1)/6)
    A closed formula in Spark expressions: 0.85 s, about 35× faster, and no Python workers at all.

  3. Step 3 · Watch a job with StatusTracker

    st = sc.statusTracker()
sc.setJobGroup("nightly-report", "orders per item")   # in the worker thread
for j in st.getActiveJobsIds(): st.getJobInfo(j); st.getStageInfo(s)

    Live progress from code: stage 8 went 0 → 1 → 4 of 8 tasks. The group lists all its jobs.
