1 The story

“Our cluster is full, but nothing is running”

Before you start: architecture in 1.3, the lab cluster in 1.5, memory in 8.4.

TiffinGo’s shared cluster kept rejecting new jobs. The UI showed every core taken, yet most applications were notebooks sitting idle for hours, each holding the executors it got at start-up.

K> Sir, an idle notebook is not running anything. Why does it keep the machines? A> Because by default an application keeps the executors it asked for until it ends. Dynamic allocation lets Spark request executors when tasks are waiting and release them after they have been idle for a while. R> And how big should each executor be? A> That is the other half: cores, memory and how many executors. Today we run on a real standalone cluster: static vs dynamic, a cores.max cap, and an executor too big to fit anywhere. 2 Definition

Executor resources and dynamic allocation

Formal definition (write this in exams)

A Spark application’s capacity is the number of executors times their cores (task slots), each with a fixed heap (spark.executor.memory) and off-heap overhead. The cluster manager (standalone, YARN or Kubernetes) launches executors only on nodes with enough free cores and memory. With static allocation, the application keeps a fixed set of executors for its lifetime. With dynamic allocation (spark.dynamicAllocation.enabled=true), Spark requests more executors when tasks have been pending longer than schedulerBacklogTimeout, growing exponentially up to maxExecutors, and removes executors idle for executorIdleTimeout. Because removed executors may hold shuffle files, dynamic allocation needs an external shuffle service or shuffle tracking, which keeps executors with live shuffle data until shuffleTracking.timeout.

In simple words

An application runs tasks on executors; executors × cores is how many tasks run at once. Normally an app keeps its executors until it ends. With dynamic allocation, Spark asks for executors when work is waiting and gives them back when they sit idle, so shared clusters are used better.

LEVELS> Resources at three levels L1> Hiring delivery riders
  • Static: hire 50 riders for the whole day, even at 3 pm when nobody orders.
  • Dynamic: call riders in when orders queue up, send them home after 10 idle minutes. Cheaper, but the first orders of the dinner rush wait a bit.
L2> The settings
  • Size: spark.executor.cores, spark.executor.memory, spark.executor.instances (static), spark.cores.max (standalone cap).
  • Dynamic: spark.dynamicAllocation.enabled, …minExecutors, …maxExecutors, …executorIdleTimeout (60 s), …schedulerBacklogTimeout (1 s), plus …shuffleTracking.enabled or an external shuffle service.
L3> What the lab showed
  • Static: 4 one-core executors held from start to end (job 1 30.9 s, job 2 16.0 s).
  • Dynamic: 0 → 4 executors in 6 s once tasks queued, back to 0 after ~15 idle seconds, up again for job 2.
  • Asking for 3 GB executors on 2 GB workers: “Initial job has not accepted any resources”.
/LEVELS EXAM> “What is dynamic allocation?” Spark scales the number of executors of an application with its workload: it requests executors when tasks are backlogged (up to maxExecutors) and removes executors idle longer than executorIdleTimeout (default 60 s). It requires an external shuffle service or spark.dynamicAllocation.shuffleTracking.enabled so shuffle files are not lost. It improves utilisation of shared clusters at the cost of ramp-up latency.
3 Types and ways to use it

Sizing executors

ShapeExampleProsCons
Tiny (1 core)1 core, 1–2 GBFine-grainedNo sharing of broadcasts/cache; JVM overhead per core
Balanced4–5 cores, 16–32 GBGood I/O throughput, shared broadcastCommon default
Fat (whole node)32+ cores, 200 GBFew JVMsLong GC pauses, HDFS client contention
WARN> An executor must fit on one worker: cores and memory plus overhead. Ask for more than any node has and Spark does not fail, it waits forever, logging “Initial job has not accepted any resources”. Also, cores are only as real as the hardware: our 2 workers advertise 4 cores on a host with 2 physical CPUs, which is why 4 executors were not faster than 2 in the lab.
4 Step by step

Executors on a real cluster

All outputs are real: Spark 4.3.0 standalone cluster in Docker, 1 master and 2 workers with 2 cores and 2 GB each (host: 2 physical CPUs). Each run submits the same application: wait 6 s, job 1 (30M SHA hashes), idle 40 s, job 2. A thread polls /api/v1/applications/…/executors every 2 s.

  1. Step 1 · Static allocation

    spark-submit --master spark://spark-master:7077 \
  --conf spark.executor.cores=1 --conf spark.executor.memory=1g \
  /jobs/l85_resources.py
    ### --conf spark.executor.cores=1 --conf spark.executor.memory=1g spark.executor.cores = 1 spark.executor.memory = 1g spark.cores.max = (default) spark.dynamicAllocation.enabled = (default) spark.dynamicAllocation.maxExecutors = (default) [ 37s] job 1: 30.9 s [ 37s] idle 40 s ... [ 93s] job 2: 16.0 s executors over time (t s, executors, cores): [(6, 4, 4)]
    With 1-core executors, the standalone master started 4 executors (2 per worker) and the app kept all 4 for its whole life, including the 40 idle seconds. Job 1 (30.9 s) includes JVM warm-up; job 2 took 16.0 s.

  2. Step 2 · Capping with cores.max

    spark-submit … --conf spark.cores.max=2 --conf spark.executor.cores=1 /jobs/l85_resources.py
    ### --conf spark.cores.max=2 --conf spark.executor.cores=1 spark.cores.max = 2 [ 31s] job 1: 24.5 s [ 31s] idle 40 s ... [ 85s] job 2: 14.1 s executors over time (t s, executors, cores): [(2, 2, 2)]
    On standalone, an app takes all free cores unless capped. With cores.max=2 it got 2 executors, leaving 2 cores for other apps, and was not slower (24.5 s / 14.1 s), because our host has only 2 physical CPUs. Advertised cores beyond the real CPUs only add contention.

  3. Step 3 · Dynamic allocation

    spark-submit … --conf spark.executor.cores=1 --conf spark.executor.memory=1g \
  --conf spark.dynamicAllocation.enabled=true \
  --conf spark.dynamicAllocation.shuffleTracking.enabled=true \
  --conf spark.dynamicAllocation.executorIdleTimeout=10s \
  --conf spark.dynamicAllocation.shuffleTracking.timeout=10s \
  --conf spark.dynamicAllocation.minExecutors=0 --conf spark.dynamicAllocation.maxExecutors=4 \
  /jobs/l85_resources.py
    spark.executor.cores = 1 spark.executor.memory = 1g spark.cores.max = (default) spark.dynamicAllocation.enabled = true spark.dynamicAllocation.maxExecutors = 4 [ 51s] job 1: 45.0 s [ 51s] idle 40 s ... [132s] job 2: 41.3 s executors over time (t s, executors, cores): [(2, 0, 0), (20, 1, 1), (22, 3, 3), (26, 4, 4), (65, 2, 2), (67, 0, 0), (101, 1, 1), (103, 2, 2), (105, 3, 3), (107, 4, 4)]
    The timeline tells the story. At 2 s: 0 executors. Job 1 queued tasks, so Spark requested 1, then 3, then 4 executors (20–26 s). After job 1 finished, idle executors were released (2 at 65 s, 0 at 67 s). Job 2 brought them back (101–107 s). The cost: every job started cold, so job 1 took 45.0 s and job 2 41.3 s instead of 30.9 s and 16.0 s. Production idle timeouts are longer (60 s default) to avoid that churn.

  4. Step 4 · An executor that does not fit

    spark-submit … --conf spark.executor.memory=3g /jobs/l85_resources.py   # workers have 2g
    ### --conf spark.executor.memory=3g (workers have 2g each) TaskSchedulerImpl: Initial job has not accepted any resources; check your cluster UI to ensure that workers are registered and have sufficient resources
    No error, no executors. The app waited, logging this warning every 15 s, until we killed it. In the master UI its state was WAITING with 0 cores. Always check executor size against node size, including memory overhead on YARN and Kubernetes.

6 Real-world use

Resource management at work

1. Shared analytics clusters

Dynamic allocation with min 0 lets dozens of notebooks share one cluster.

Idle session→release→Free cores

2. SLA pipelines

Critical nightly jobs use static executors or a high minExecutors for predictable runtimes.

Nightly job→static→On time

3. Kubernetes autoscaling

Dynamic allocation with shuffle tracking adds executor pods; the node autoscaler adds nodes.

Backlog→more pods→More nodes

4. Executor shapes

Platform teams publish standard small/medium/large executor shapes that fit their nodes.

Node size→shape→Fits

5. Cost reports

Executor-hours per application from the history server show which jobs hold idle resources.

History server→executor-hours→Cost owner
