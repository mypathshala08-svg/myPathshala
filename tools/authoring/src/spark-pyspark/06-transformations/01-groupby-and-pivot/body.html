“One row per city, one column per status”

2 Definition

Grouping, pivoting and unpivoting

Formal definition (write this in exams)

groupBy returns a GroupedData object whose agg computes aggregate functions over the rows of each group of equal key values; null keys form a group of their own. Spark executes most aggregations in two phases: a partial aggregation within each input partition, a shuffle by the grouping keys, and a final merge, so only partial results cross the network. rollup and cube compute additional grouping sets (hierarchical subtotals, or all combinations) with nulls marking the rolled-up columns. pivot(col, values) rotates distinct values of a column into output columns of an aggregation; if values are not given, Spark first computes them with a separate query and limits them to spark.sql.pivotMaxValues (10,000). unpivot (also melt) performs the reverse, turning columns into rows.

In simple words

groupBy puts rows with the same key together and computes totals, counts or averages per group. Spark adds things up inside each partition first, so the shuffle is small. pivot turns values into columns, unpivot turns columns back into rows. Give pivot its list of values.

LEVELS> Aggregation at three levels L1> Counting votes
  • Each polling booth counts its own votes first, then sends only totals to the centre. That is partial aggregation.
  • A pivot is turning the result list (party, votes) into a table with one column per party.
  • Blank ballots still form a pile of their own: nulls are a group.
L2> The API
  • df.groupBy(cols).agg(F.count, F.sum, F.avg, F.countDistinct, F.collect_list…); rollup and cube add subtotals.
  • groupBy(k).pivot(col, [values]).agg(…); unpivot(ids, values, name, value) (alias melt, Spark 3.4+).
  • Conditional counts: F.sum(F.when(cond, 1).otherwise(0)) or F.count_if(cond).
L3> What the lab showed
  • The plan aggregated twice: partial_sum per partition, shuffle, final sum.
  • Pivot without values ran 4 extra jobs and took 2.72 s; with values, 0 extra jobs and 1.30 s, and the empty REFUNDED column existed.
  • Pivot on order_id failed: more than 10,000 distinct values (spark.sql.pivotMaxValues).
/LEVELS EXAM> “Why should you pass values to pivot?” Without them Spark runs an extra query over the data to find distinct values (4 extra jobs in our lab, 2.72 s vs 1.30 s), the output columns depend on the data (a missing status means a missing column), and more than 10,000 values fails. With a list, the schema is fixed and the extra pass disappears.

  5. Step 5 · The pivot limit

    o.groupBy("city").pivot("customer_id").count()          # 4,000 columns
o.limit(20000).groupBy("city").pivot("order_id").count()
    == 6) pivot limit pivot on customer_id: 4000 columns AnalysisException The pivot column order_id has more than 10000 distinct values, this could indicate an error. If this was intended, set …
    Pivoting on customers produced a 4,000-column DataFrame without complaint; on order ids Spark stopped at 10,000 distinct values. Wide pivots are slow to plan and hard to use; if a column has thousands of values, keep the data long and aggregate.

6 Real-world use

Aggregations at work

1. Daily KPI tables

Orders, revenue, average bill and cancellations per city and day are one groupBy over the fact table.

Orders→groupBy + agg→KPI table

2. Spreadsheet-style reports

Status or month columns for finance sheets are pivots with a fixed value list.

Long table→pivot(values)→Wide sheet

3. Hierarchical totals

Region → city → restaurant totals for management reports come from rollup or GROUPING SETS.

Facts→rollup→Subtotals

4. Customer features

Per-customer counts, sums and favourite cities feed churn and recommendation models.

Orders→groupBy customer→Features

5. Tidying wide files

Wide spreadsheets from partners (one column per month) are unpivoted into long tables.

Wide CSV→unpivot→Long table
