1 The story

“The new year started on 28 December”

Before you start: columns and try_cast in 4.3.

A year-end report at TiffinGo grouped orders by date_format(order_date, "YYYY"). In an older system that produced “2027” for orders on 28–31 December 2026, and the yearly totals were wrong. In Spark 4 the same pattern stops the job with an error. Meanwhile the support team found phone numbers like “+91 98200-11122” that matched nothing.

K> Sir, YYYY and yyyy look the same to me. A> They are not. yyyy is the calendar year; YYYY is the week-based year, which can differ in the last days of December. Spark 3+ refuses YYYY in formatting to protect you. R> And the phone numbers? A> Text needs normalising before you compare or join on it. Today: trimming and case, regular expressions to extract and clean, parsing dates in several formats with try_to_date, date arithmetic, week-year traps and time zones. All outputs are real (PySpark 4.3.0).
2 Definition

String and datetime functions

Formal definition (write this in exams)

pyspark.sql.functions provides built-in, JVM-executed functions for strings (case, trimming, padding, substring, splitting, concatenation, regular expressions via Java regex syntax) and for datetimes. Dates (DATE) have no time zone; timestamps (TIMESTAMP, i.e. TIMESTAMP_LTZ) store an instant and are displayed in the session time zone spark.sql.session.timeZone, which defaults to the JVM time zone; TIMESTAMP_NTZ stores a wall-clock time without zone. Parsing and formatting use datetime patterns (e.g. yyyy-MM-dd HH:mm:ss); since Spark 3.0 the patterns follow java.time and some ambiguous letters such as week-based year Y are rejected for formatting. Under ANSI mode, to_date/to_timestamp raise errors on invalid input, while try_to_date/try_to_timestamp return null.

In simple words

Spark has ready-made functions to clean text and work with dates. They run fast inside Spark, unlike your own Python code. Always parse dates with a known format, use try_ versions for messy data, and be clear about time zones.

LEVELS> String and date functions at three levels L1> Filling a form neatly
  • Names written in random capitals, phone numbers with spaces and dashes, dates written in different ways: before filing, you rewrite them in one standard form.
  • A date written 04/11/2026 could be 4 November or 11 April; you need to know the format.
  • 3:30 pm in India is 10:00 in London: the same moment, different clock readings.
L2> The API
  • Text: trim, lower/upper/initcap, regexp_replace, regexp_extract, split, split_part, substring_index, concat_ws, like/ilike/rlike.
  • Dates: to_date/try_to_date(col, fmt), to_timestamp, date_format, datediff, date_add, add_months, last_day, date_trunc, dayofweek, weekofyear.
  • Time zones: spark.sql.session.timeZone, to_utc_timestamp, from_utc_timestamp.
L3> What the lab showed
  • to_date("04/11/2026") failed under ANSI; coalesce(try_to_date(s), try_to_date(s, "dd/MM/yyyy")) parsed both formats and gave null for 2026-02-30.
  • "YYYY" raised INCONSISTENT_BEHAVIOR_CROSS_VERSION; 1 January 2027 is ISO week 53 of 2026.
  • The session time zone (default from the JVM: Asia/Calcutta) changed how the same instant is displayed: 15:30 vs 10:00.
/LEVELS EXAM> “How do you parse dates arriving in several formats?” Read the column as a string and use coalesce(try_to_date(c, fmt1), try_to_date(c, fmt2), …); values that match no format become null and can be counted and quarantined. Under ANSI mode to_date would fail the whole job on the first unexpected value.

WARN> The session time zone defaults to the JVM’s, so the same code can print different timestamps on a laptop in India and a cluster in UTC. Set spark.sql.session.timeZone explicitly (often UTC) in every job, store instants in UTC, and convert for display at the edge.
4 Step by step

Cleaning sign-ups and taming dates

All outputs are real: PySpark 4.3.0, local mode, ANSI mode on (the default).

  1. Step 1 · Cleaning text

    r.select(F.initcap(F.trim("name")).alias("name"), F.lower("email").alias("email"),
         F.regexp_replace("phone", r"[^0-9]", "").alias("digits"),
         F.right(F.regexp_replace("phone", r"[^0-9]", ""), F.lit(10)).alias("phone10"))
    == 1) cleaning text +----------+----------------+------------+----------+ |name |email |digits |phone10 | +----------+----------------+------------+----------+ |Ravi Kumar|ravi.k@mail.in |919820011122|9820011122| |Asha Nair |asha@tiffingo.in|9820011133 |9820011133| +----------+----------------+------------+----------+
    trim + initcap fixed “ Ravi KUMAR ”; lower made emails comparable. Removing every non-digit left 919820011122 for the number with a country code, so we keep the last 10 digits: now both phones match the format used elsewhere and can be joined on.

  2. Step 2 · Extracting parts

    r.select(F.split("address", ",")[0].alias("city"), F.regexp_extract("address", r"(\d{6})", 1).alias("pin"),
         F.split_part("ref", F.lit("-"), F.lit(3)).cast("int").alias("ref_no"),
         F.substring_index("email", "@", -1).alias("domain"), F.concat_ws(" / ", "name", "ref").alias("label"))
    == 2) extracting parts +-----------+------+------+-----------+------------------------------+ |city |pin |ref_no|domain |label | +-----------+------+------+-----------+------------------------------+ |Pune |411001|781 |Mail.in | Ravi KUMAR / TG-2026-000781| |Navi Mumbai|400703|1902 |tiffingo.IN|asha nair / TG-2026-001902 | +-----------+------+------+-----------+------------------------------+
    split gave an array (index 0 = city), regexp_extract found the 6-digit PIN anywhere in the address, split_part took the third piece of the reference and cast removed leading zeros. Note the uncleaned name and mixed-case domain: clean first, extract after.

  3. Step 3 · Parsing dates safely

    d.select("s", F.try_to_date("s").alias("iso"), F.try_to_date("s", "dd/MM/yyyy").alias("dmy"),
         F.coalesce(F.try_to_date("s"), F.try_to_date("s", "dd/MM/yyyy")).alias("either"))
d.select(F.to_date("s")).collect()
    == 3) parsing dates and timestamps +----------+----------+----------+----------+ | s| iso| dmy| either| +----------+----------+----------+----------+ |2026-11-04|2026-11-04| NULL|2026-11-04| |04/11/2026| NULL|2026-11-04|2026-11-04| |2026-02-30| NULL| NULL| NULL| +----------+----------+----------+----------+ to_date under ANSI: DateTimeException [CAST_INVALID_INPUT] The value '04/11/2026' of the type "STRING" cannot be cast to "DATE" because i …
    Each try_to_date recognised one format and returned null for the others; coalesce combined them. 30 February is not a date in any format and stayed null: count such rows. The strict to_date stopped the job at the first non-ISO value, as ANSI mode should.

  4. Step 4 · Date arithmetic

    t.select(F.datediff("today", "ts"), F.date_add("today", 30), F.add_months("today", 1), F.last_day("today"),
         F.date_trunc("week", "ts"), F.dayofweek("ts"), F.date_format("ts", "EEE, d MMM HH:mm"))
    == 4) date arithmetic +----------+----------+----------+----------+-------------------+---+-----------------+ |days_since|plus30 |next_month|month_end |week_start |dow|pretty | +----------+----------+----------+----------+-------------------+---+-----------------+ |6 |2026-12-04|2026-12-04|2026-11-30|2026-10-26 00:00:00|5 |Thu, 29 Oct 20:49| +----------+----------+----------+----------+-------------------+---+-----------------+
    Six days since the order; 30 days and one month later happen to give the same date here, but not in general. date_trunc("week") rounded down to Monday 26 October; dayofweek counts Sunday as 1, so Thursday is 5. date_format made a readable label.

  5. Step 5 · YYYY vs yyyy, and ISO weeks

    y.select("d", F.date_format("d", "yyyy"))
y.select(F.date_format("d", "YYYY"))
y.select("d", F.year("d"), F.weekofyear("d"))
    == 5) week-based year: YYYY vs yyyy +----------+----+ | d|yyyy| +----------+----+ |2026-12-28|2026| |2026-12-31|2026| |2027-01-01|2027| +----------+----+ YYYY: SparkUpgradeException [INCONSISTENT_BEHAVIOR_CROSS_VERSION.DATETIME_PATTERN_RECOGNITION] You may get a different result due to the … +----------+----+--------+ | d|year|iso_week| +----------+----+--------+ |2026-12-28|2026| 53| |2026-12-31|2026| 53| |2027-01-01|2027| 53| +----------+----+--------+
    yyyy is the calendar year. YYYY was rejected with INCONSISTENT_BEHAVIOR_CROSS_VERSION, because week-based years silently gave wrong years in older systems. The ISO week column shows why: 28 December 2026 to 1 January 2027 all belong to week 53 of 2026. Weekly reports that use weekofyear must pair it with the ISO week year, not year().

    == 6) time zones session time zone: Asia/Calcutta +-------------------+----------+-------------------+-------------------+ |ts |epoch |as_utc |in_new_york | +-------------------+----------+-------------------+-------------------+ |2026-11-04 15:30:00|1793786400|2026-11-04 10:00:00|2026-11-04 05:00:00| +-------------------+----------+-------------------+-------------------+ same epoch, session UTC: 1793786400 | shown as 2026-11-04 10:00:00 same rows, session Asia/Kolkata: 2026-11-04 15:30:00 == 7) like, rlike, contains names starting with A: 311 | like 'A%': 311 | rlike '^(Aarav|Ananya) ': 163 | ilike '%iyer': 138
    The session zone came from the JVM: Asia/Calcutta (the old name again, Lesson 5.4). The stored instant (epoch 1793786400) never changed; switching the session to UTC changed only how it is displayed: 15:30 became 10:00. Finally, like, ilike (case-insensitive) and rlike (regex) filter text without any Python.

Week, month and fiscal-year buckets with date_trunc, last_day and add_months.

Timestamps→date_trunc→Periods

Minutes between order and delivery from unix_timestamp differences.
