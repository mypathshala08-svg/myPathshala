1 The story

“The running total jumped”

Before you start: groupBy in 6.1, deterministic dedup in 4.4.

Riya built a running revenue chart per city with sum().over(Window.partitionBy("city").orderBy("day")). On days with two identical entries the line jumped straight to the day’s total on both rows. The finance team asked why the running total was the same on two consecutive rows.

R> Sir, a running total should grow row by row. Why did it skip? A> Because with orderBy and no frame, Spark uses RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: all rows with the same day are “current” together. For a row-by-row total you must say rowsBetween. K> And windows are the way to get top N per group? A> Yes, and Spark 4 optimises exactly that pattern. Today: ranking functions and ties, lag and lead, running totals and frames, moving averages and shares, top-N per city on 5 million rows, and what happens without partitionBy. All outputs are real (PySpark 4.3.0).
2 Definition

Window functions

Formal definition (write this in exams)

A window function computes a value for each input row from a set of rows related to it, its window, without collapsing rows as groupBy does. The window is defined by a partitioning (rows with the same partition keys), an ordering within the partition, and a frame relative to the current row: ROWS frames count physical rows, RANGE frames include all rows whose ordering value lies in a range, so peers with equal ordering values are treated together. When an ordering is specified without a frame, the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW; without ordering it is the whole partition. Spark executes windows by shuffling on the partition keys and sorting; a window without partition keys moves all data to a single partition.

In simple words

A window function looks at a group of rows around each row and writes a result on that row: its rank, the previous value, a running total. You choose the group (partitionBy), the order (orderBy) and how many rows to include (the frame). Rows are not merged, so you keep all details.

LEVELS> Window functions at three levels L1> A class marks list
  • Each student keeps their own row, and you write next to it their rank within their section.
  • “Previous test’s marks” is lag; a running total adds all earlier tests.
  • The window is which rows you look at: same section (partition), in date order (order), and how far back (frame).
L2> The API
  • w = Window.partitionBy(...).orderBy(...), optional .rowsBetween(a, b) or .rangeBetween(a, b); then F.func().over(w).
  • Ranking: row_number, rank, dense_rank, percent_rank, ntile. Offset: lag, lead. Aggregates: sum, avg, min, max, count over a window.
  • Window.unboundedPreceding, Window.currentRow, Window.unboundedFollowing, or integer offsets.
L3> What the lab showed
  • For tied revenue, row_number gave 1, 2; rank 1, 1, 3; dense_rank 1, 1, 2.
  • The default frame gave 1210 on both rows of 2 November; rowsBetween gave 830 then 1210.
  • Top 2 per city on 5M rows used WindowGroupLimit; a window with no partition moved everything to 1 partition (12.0 s vs 7.1 s).
/LEVELS EXAM> “Why does my running total repeat a value?” With orderBy and no frame Spark uses RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which includes all peers with the same ordering value. Use .rowsBetween(Window.unboundedPreceding, Window.currentRow) and a unique ordering (add a tiebreaker column) for a row-by-row running total.

WARN> Window.orderBy(...) without partitionBy moves all rows into one partition on one executor (Spark logs “No Partition Defined for Window operation”). In our lab the 4 input partitions became 1 and the job took 12.0 s instead of 7.1 s; on a cluster with 5 billion rows it simply fails. Partition by something, or compute global ranks differently (e.g. sort + zipWithIndex, or approximate percentiles).
4 Step by step

Ranks, offsets, frames and top-N

All outputs are real: PySpark 4.3.0, local mode with 4 cores. Steps 1–4 use daily revenue for Pune and Delhi (with ties on purpose); Steps 5–6 use 5,000,000 orders.

  1. Step 1 · Ranking and ties

    w = Window.partitionBy("city").orderBy(F.desc("revenue"))
d.select("city", "day", "revenue", F.row_number().over(w).alias("row_number"),
         F.rank().over(w).alias("rank"), F.dense_rank().over(w).alias("dense_rank"))
    == 1) ranking with ties +-----+----------+-------+----------+----+----------+ | city| day|revenue|row_number|rank|dense_rank| +-----+----------+-------+----------+----+----------+ |Delhi|2026-11-02| 610| 1| 1| 1| |Delhi|2026-11-03| 610| 2| 1| 1| |Delhi|2026-11-01| 300| 3| 3| 2| | Pune|2026-11-03| 520| 1| 1| 1| | Pune|2026-11-01| 450| 2| 2| 2| | Pune|2026-11-02| 380| 3| 3| 3| | Pune|2026-11-02| 380| 4| 3| 3| +-----+----------+-------+----------+----+----------+
    Each city is ranked separately. Delhi’s two 610 days got row_number 1 and 2 (in an arbitrary order), but rank 1 and 1; the next day got rank 3 and dense_rank 2. If you use row_number to pick one row, add a tiebreaker to the orderBy, or the chosen row can change between runs (Lesson 4.4).

  2. Step 2 · lag and lead

    w2 = Window.partitionBy("city").orderBy("day")
d.select("city", "day", "revenue", F.lag("revenue").over(w2).alias("prev"),
         (F.col("revenue") - F.lag("revenue").over(w2)).alias("change"), F.lead("day").over(w2).alias("next_day"))
    == 2) lag and lead +-----+----------+-------+----+------+----------+ | city| day|revenue|prev|change| next_day| +-----+----------+-------+----+------+----------+ |Delhi|2026-11-01| 300|NULL| NULL|2026-11-02| |Delhi|2026-11-02| 610| 300| 310|2026-11-03| |Delhi|2026-11-03| 610| 610| 0| NULL| | Pune|2026-11-01| 450|NULL| NULL|2026-11-02| | Pune|2026-11-02| 380| 450| -70|2026-11-02| | Pune|2026-11-02| 380| 380| 0|2026-11-03| | Pune|2026-11-03| 520| 380| 140| NULL| +-----+----------+-------+----+------+----------+
    lag took the previous row’s revenue in the same city, so day-over-day change is one expression, without a self-join. The first row of each partition has no previous row (null), the last no next. Partitions never leak: Delhi’s first day does not see Pune’s last.

  3. Step 3 · Running totals: the frame trap

    run_default = F.sum("revenue").over(Window.partitionBy("city").orderBy("day"))
run_rows = F.sum("revenue").over(Window.partitionBy("city").orderBy("day")
                                .rowsBetween(Window.unboundedPreceding, Window.currentRow))
    == 3) running total: default frame vs rowsBetween +----------+-------+-------------+----------+ | day|revenue|default_frame|rows_frame| +----------+-------+-------------+----------+ |2026-11-01| 450| 450| 450| |2026-11-02| 380| 1210| 830| |2026-11-02| 380| 1210| 1210| |2026-11-03| 520| 1730| 1730| +----------+-------+-------------+----------+
    Riya’s bug, reproduced. The default RANGE frame treats both 2 November rows as “the current row”, so both show 1210. The ROWS frame adds one row at a time: 830, then 1210. Both end at 1730. Whenever ordering values can repeat, decide which you mean and write the frame explicitly.

  4. Step 4 · Moving average and share of total

    F.avg("revenue").over(Window.partitionBy("city").orderBy("day").rowsBetween(-1, 0))
F.col("revenue") / F.sum("revenue").over(Window.partitionBy("city")) * 100
    == 4) moving average and share of total +-----+----------+-------+-----+--------+ | city| day|revenue|avg_2|pct_city| +-----+----------+-------+-----+--------+ |Delhi|2026-11-01| 300|300.0| 19.7| |Delhi|2026-11-02| 610|455.0| 40.1| |Delhi|2026-11-03| 610|610.0| 40.1| | Pune|2026-11-01| 450|450.0| 26.0| | Pune|2026-11-02| 380|415.0| 22.0| | Pune|2026-11-02| 380|380.0| 22.0| | Pune|2026-11-03| 520|450.0| 30.1| +-----+----------+-------+-----+--------+
    rowsBetween(-1, 0) averaged the current and previous row. A window with only partitionBy covers the whole partition, so each row can be divided by its city total: Pune’s 3 November was 30.1% of Pune’s revenue. Without windows this needs a groupBy and a join.

    top = (o.withColumn("rn", F.row_number().over(

    The classic top-N-per-group pattern, with order_id as tiebreaker (many orders have the maximum 959). The plan shows a Spark 3.5+ optimisation: WindowGroupLimit … Partial before the shuffle keeps only the top 2 rows per city in each partition, so almost nothing is shuffled, then a final limit after it.

  6. Step 6 · A window without partitionBy

    r = o.withColumn("global_rank", F.row_number().over(Window.orderBy(F.desc("amount"), "order_id")))
r.rdd.getNumPartitions()
r.write.format("noop").mode("overwrite").save()
o.withColumn("city_rank", F.row_number().over(Window.partitionBy("city").orderBy(…))).write.format("noop")…
    == 6) a window without partitionBy partitions before: 4 | after: 1 global row_number over 5M rows: 12.0 s row_number per city: 7.1 s
    A global row_number collapsed 4 partitions into 1: one task sorted all 5 million rows (12.0 s). Ranking within cities kept the work parallel (7.1 s). On a real cluster the difference is one core against hundreds, plus the risk of running one executor out of memory.

6 Real-world use

Windows at work

1. Latest version of records

Change logs are reduced to the current row per key with row_number.

Changes→row_number = 1→Current table

2. Trends

7-day moving averages and day-over-day changes for dashboards.

Daily KPIs→avg over rows→Smoothed line

3. Leaderboards per group

Top restaurants per city, best-selling dishes per restaurant.

Scores→rank per city→Top 10

4. Sessionisation

lag on click times finds gaps over 30 minutes; a running sum of “new session” flags numbers sessions.

Clicks→lag + running sum→Sessions

5. Time-based features

Orders in the last 30 days, days since last order and running spend per customer.

Orders→range frames→Features
