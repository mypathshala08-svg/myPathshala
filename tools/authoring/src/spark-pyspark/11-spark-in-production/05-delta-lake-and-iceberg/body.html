1 The story

“We need to fix one order in a 2 TB folder”

Before you start: Parquet in 5.2, writing and small files in 5.3, tables and catalogs in 7.2.

A customer asked TiffinGo to correct one order’s status. The orders lived in plain Parquet files: to change one row, the team rewrote a whole day’s partition, and a reader ran during the rewrite and saw half the data. The same month, a job appended amounts as strings and broke every dashboard.

K> Sir, Parquet is great. Why does it not support UPDATE? A> Parquet files are immutable, and a folder of them has no idea which files belong together. Table formats like Delta Lake and Apache Iceberg add a log of commits: each change writes new files and then atomically records “these files are now the table”. R> And readers never see half a change? A> Exactly: ACID transactions on a data lake, plus history, time travel and schema checks. Today we try both formats. Neither supports Spark 4.3 yet, so this lab runs PySpark 4.1.1 with delta-spark 4.3.1 and Iceberg 1.12.0. All outputs are real.
2 Definition

Delta Lake and Apache Iceberg

Formal definition (write this in exams)

Open table formats store table data as Parquet files in object storage and add metadata that defines which files form each version of the table. Delta Lake keeps an ordered transaction log (_delta_log/ JSON commits with periodic checkpoints); Apache Iceberg keeps a tree of metadata files, manifest lists and manifests, referenced by a catalog. Writers commit new versions atomically with optimistic concurrency, giving ACID transactions, row-level UPDATE/DELETE/MERGE (by rewriting or marking affected files), time travel to earlier versions or snapshots, schema enforcement and controlled schema evolution. Iceberg adds hidden partitioning (partition transforms such as days(ts) derived from columns) and partition evolution. Both integrate with Spark through connector packages and SQL extensions.

In simple words

Delta Lake and Iceberg turn folders of Parquet files into real tables. A log records every change, so you can update and delete rows safely, readers never see half-finished writes, you can read older versions, and wrong data types are rejected.

LEVELS> Table formats at three levels L1> A register at the library
  • Books (Parquet files) never change; a register lists which books are on the shelf right now.
  • To “edit” a book, you add a corrected copy and change the register in one stroke. Old register pages let you see the shelf as it was last week (time travel).
L2> The API
  • Delta: df.write.format("delta").save(path), DeltaTable.forPath(spark, path) with .update(), .delete(), .merge(), .history(); read option("versionAsOf", n).
  • Iceberg: catalog config, then SQL: CREATE TABLE … USING iceberg PARTITIONED BY (days(ts)), UPDATE, DELETE, MERGE INTO, VERSION AS OF, metadata tables like t.snapshots.
  • Schema: Delta mergeSchema; Iceberg ALTER TABLE … ADD/RENAME COLUMN, ADD PARTITION FIELD.
L3> What the lab showed
  • Delta recorded WRITE, UPDATE, DELETE and MERGE as versions 0–3; version 0 is still readable.
  • Appending amount as a string was rejected; a new column needed mergeSchema.
  • Iceberg created ts_day=… folders from days(ts), travelled back to a snapshot, and changed its partitioning without rewriting old data.
/LEVELS EXAM> “Why use Delta Lake or Iceberg instead of plain Parquet?” They add a transactional metadata layer: atomic commits (no partial reads), row-level updates/deletes/merges, time travel, schema enforcement and evolution, and efficient metadata-based pruning. Delta uses an ordered JSON transaction log; Iceberg uses snapshots with manifests and a catalog, and adds hidden partitioning and partition evolution.

WARN> Table formats are tied to Spark versions. When we built this lesson, the newest Delta (4.4.1) supported Spark 4.2 and the newest Iceberg runtime targeted Spark 4.1, while PySpark was at 4.3. Platforms usually lag the newest Spark for this reason; check the compatibility matrix before upgrading Spark. Also, time travel only works while old files exist: VACUUM (Delta) and expire_snapshots (Iceberg) delete them.

Delta, then Iceberg

All outputs are real: PySpark 4.1.1 in a separate virtualenv, delta-spark 4.3.1 and iceberg-spark-runtime-4.1 1.12.0 (Iceberg Hadoop catalog on local disk), local[2].

  1. Step 1 · A Delta table is Parquet + a log

    o.write.format("delta").save(P)
print(sorted(os.listdir(P)))
print(sorted(os.listdir(P + "/_delta_log")))
    PySpark 4.1.1 | delta-spark 4.3.1 == 1) write a Delta table files: ['_delta_log', 'part-00000-730dbdb7-f670-42e7-95ec-9d941ef1c1ba-c000.snappy.parquet', 'part-00001-6877bb39-596e-4cb1-abf0-71f112e4d854-c000.snappy.parquet'] _delta_log: ['00000000000000000000.crc', '00000000000000000000.json', '_staged_commits']
    The data is ordinary Parquet; what makes it a table is _delta_log/00000000000000000000.json, commit number 0, listing those files. Any reader that understands Delta reads the log first and then only the files it names.

  2. Step 2 · UPDATE, DELETE and MERGE

    t = DeltaTable.forPath(spark, P)
t.update("order_id = 1", {"status": F.lit("DELIVERED")})
t.delete("order_id = 2")
(t.alias("t").merge(upd.alias("u"), "t.order_id = u.order_id")
  .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())
    == 2) UPDATE, DELETE, MERGE +--------+-----+------+---------+ |order_id| city|amount| status| +--------+-----+------+---------+ | 1| Pune| 450|DELIVERED| | 3|Delhi| 800|DELIVERED| | 4|Thane| 120| PLACED| +--------+-----+------+---------+
    Row-level changes on a data lake: order 1 delivered, order 2 deleted, order 3 updated and order 4 inserted by one MERGE (an upsert). Each operation wrote new files and one new commit; readers saw either the old or the new table, never a mix.

  3. Step 3 · History and time travel

    t.history().select("version", "operation", "operationParameters.predicate").show()
spark.read.format("delta").option("versionAsOf", 0).load(P)
    == 3) history and time travel +-------+---------+------------------------------------+ |version|operation|predicate | +-------+---------+------------------------------------+ |0 |WRITE |NULL | |1 |UPDATE |["(order_id = 1)"] | |2 |DELETE |["(order_id = 2)"] | |3 |MERGE |["(order_id = order_id)"]| +-------+---------+------------------------------------+ version 0 rows: 3 | latest rows: 3
    Four versions, each with its operation and predicate: an audit trail for free. versionAsOf 0 reads the table before any change (all three orders PLACED). Both versions have 3 rows, but different ones.

  4. Step 4 · Schema enforcement and evolution

    bad.write.format("delta").mode("append").save(P)            # amount as string
extra.write.format("delta").mode("append").save(P)          # new column payment
extra.write.format("delta").mode("append").option("mergeSchema", "true").save(P)
    == 4) schema enforcement append with amount as string -> [DELTA_FAILED_TO_MERGE_FIELDS] Failed to merge fields 'amount' and 'amount' append with new column -> [DELTA_METADATA_MISMATCH] A metadata mismatch was detected when writing to the Delta table. with mergeSchema: ['order_id', 'city', 'amount', 'status', 'payment'] == 5) a commit in the log 00000000000000000004.json actions: ['commitInfo', 'metaData', 'add']
    The string amount was rejected: exactly the dashboard-breaking append from the story. A new column was also refused until we said mergeSchema; then the table gained payment and commit 4 recorded the new metadata.

  5. Step 5 · Iceberg: hidden partitioning

    CREATE TABLE lake.db.orders (order_id BIGINT, city STRING, amount BIGINT, ts TIMESTAMP)
  USING iceberg PARTITIONED BY (days(ts));
SELECT * FROM lake.db.orders WHERE ts >= TIMESTAMP'2026-11-02 00:00:00';
    == 1) a table with hidden partitioning data folders: ['ts_day=2026-11-01', 'ts_day=2026-11-02'] metadata files: ['8a17c8d0-7a24-410f-a441-128ee8fcefea-m0.avro', 'snap-1143674350049614565-1-8a17c8d0-7a24-410f-a441-128ee8fcefea.avro', 'v1.metadata.json', 'v2.metadata.json', 'version-hint.text'] == 2) filter on ts prunes partitions (no extra column needed) rows: 1 data files in table: 2 | files in partition 2026-11-02: 1
    We partitioned by a transform of ts; Iceberg created ts_day=… folders itself. Queries filter on ts as usual, with no extra date column to remember, and Iceberg uses partition metadata to read only the matching file (1 of 2).

    UPDATE lake.db.orders SET amount = 500 WHERE order_id = 1;
DELETE FROM lake.db.orders WHERE order_id = 2;
SELECT … FROM lake.db.orders.snapshots;
SELECT * FROM lake.db.orders VERSION AS OF <first snapshot>;
ALTER TABLE lake.db.orders ADD COLUMN payment STRING;
ALTER TABLE lake.db.orders RENAME COLUMN amount TO amount_rs;

    Every change is a snapshot, queryable as a table. Time travel showed order 1 at ₹450 before the update. Then we added and renamed columns and added city to the partitioning without rewriting old files: old data stays under spec 0, new data (Thane) lands under ts_day=…/city=… with spec 1.

Request→DELETE + VACUUM→Compliant

Debezium→MERGE→Lake copy

Spark writes, Trino and Snowflake read the same Iceberg tables.

Spark write→Iceberg catalog→Trino read

Model v3→VERSION AS OF→Same data
