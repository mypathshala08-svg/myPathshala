1 The story

“Every analyst’s laptop runs a Spark driver”

Before you start: SparkSession in 4.1, UDFs in 6.6, deploy modes in 11.1.

TiffinGo’s 40 analysts each started PySpark in their notebooks. Every notebook started its own driver JVM, needed Java installed, and crashed the laptop when someone collected a big table. Upgrading Spark meant upgrading 40 laptops.

K> Sir, can’t the notebook just talk to a Spark that runs somewhere else? A> That is Spark Connect. The notebook only has a thin Python client. It turns your DataFrame code into a plan and sends it over gRPC to a Spark Connect server, which runs it and streams results back. R> Same DataFrame API? A> Almost all of it. Today we start a server, connect a client, compare it with classic PySpark, and find the gaps: no SparkContext, no RDDs, lazy error reporting, isolated sessions. All outputs are real (Spark 4.3.0).
2 Definition

Spark Connect

Formal definition (write this in exams)

Spark Connect (Spark 3.4+, central in Spark 4) is a client-server architecture for Spark. A thin client library implements the DataFrame and SQL APIs by building unresolved logical plans encoded as protocol buffers and sending them over gRPC to a Spark Connect server running inside a Spark driver. The server analyses, optimises and executes the plans and streams results back as Arrow batches. Each client gets its own isolated session (temporary views, configuration, UDFs), the client needs no JVM, and client and server can be upgraded independently within compatible versions. APIs that expose the driver’s JVM, such as SparkContext and RDDs, are not available; analysis errors surface when the server analyses a plan (on actions or schema access) rather than when the DataFrame is defined.

In simple words

With Spark Connect your Python program does not run Spark itself. It describes queries and sends them to a Spark server, which runs them and returns the results. Clients are light (no Java), each user has a separate session, and the DataFrame API stays the same, but low-level things like RDDs and SparkContext are not available.

LEVELS> Spark Connect at three levels L1> Ordering food by phone
  • Classic PySpark: you bring a kitchen home and cook yourself. Spark Connect: you phone the restaurant with your order (the plan); the kitchen cooks and delivers the result.
  • Each caller gets their own order slip (session), so two customers never mix their orders.
L2> The API
  • Server: $SPARK_HOME/sbin/start-connect-server.sh (port 15002), or a managed endpoint.
  • Client: SparkSession.builder.remote("sc://host:15002").getOrCreate(), or SPARK_REMOTE; lightweight package pyspark-client.
  • Not available: spark.sparkContext, RDD APIs, direct JVM access (_jdf, py4j).
L3> What the lab showed
  • The Connect client process started 0 JVMs; a classic local session started 1.
  • A missing column raised no error until the plan was analysed on the server.
  • A temp view created in session 1 did not exist in session 2.
/LEVELS EXAM> “What is Spark Connect?” A client-server protocol where a lightweight client sends unresolved logical plans over gRPC to a Spark Connect server that executes them and returns Arrow results. Benefits: no JVM on clients, isolation between sessions, independent upgrades, Spark from any language or app. Limits: no RDD or SparkContext APIs and no direct JVM access; errors appear when plans are analysed on the server.

4 Step by step

A server and a thin client

All outputs are real: Spark 4.3.0. The server was started with sbin/start-connect-server.sh on port 15002; the client is a separate Python process. Data: the 5,000,000-order Parquet table used in Module 8.

  1. Step 1 · Connect

    from pyspark.sql import SparkSession
spark = SparkSession.builder.remote("sc://localhost:15002").getOrCreate()
print(type(spark), spark.version)
# count JVM processes started by this Python process
    == 1) a remote session session class: pyspark.sql.connect.session.SparkSession | server version: 4.3.0 | connect + first query: 0.52 s JVM processes started by this Python client: 0 classic local session JVM children: 1
    The session is a pyspark.sql.connect session, talking to a Spark 4.3.0 server. Connecting and running a first query took about half a second, and this Python process started no JVM. For comparison, a classic SparkSession.builder.master("local[1]") started one Java child process.

  2. Step 2 · Normal DataFrame code

    o = spark.read.parquet("/root/lab/spark/data/orders_big")
o.groupBy("city").agg(F.sum("amount").alias("revenue")).orderBy(F.desc("revenue")).limit(3).collect()
    == 2) normal DataFrame code works [('Mumbai', 510290994), ('Bengaluru', 508795383), ('Chennai', 255491091)] | 1.09 s on the server
    Unchanged code. The client sent a plan; the server read 5 million rows, aggregated and returned only 3 rows. Note the path is read by the server: files must be reachable from the server, not from the client laptop.

  3. Step 3 · What is not there

    spark.sparkContext
o.rdd
    == 3) what is not available spark.sparkContext -> PySparkAttributeError: [JVM_ATTRIBUTE_NOT_SUPPORTED] Attribute `sparkContext` is not supported in Spark Connect as it depends on the df.rdd -> PySparkNotImplementedError: [NOT_IMPLEMENTED] rdd is not implemented.
    Both depend on the driver JVM living in your process. Under Connect there is no such JVM, so sparkContext raises JVM_ATTRIBUTE_NOT_SUPPORTED and df.rdd is not implemented. Libraries and old code that use RDDs need rewriting before moving to Connect.

  4. Step 4 · When errors appear

    bad = o.select("no_such_column")    # only a plan on the client
bad.columns                          # the server analyses it now
    == 4) errors appear when the plan is analysed on the server built a DataFrame with a missing column: no error yet on .columns -> AnalysisException [UNRESOLVED_COLUMN.WITH_SUGGESTION]
    Defining bad succeeded: the client does not know the table’s columns. The error came when we asked for .columns, which sends the plan to the server for analysis: UNRESOLVED_COLUMN.WITH_SUGGESTION. In classic PySpark the same line fails immediately.

  5. Step 5 · Sessions and UDFs

    s2 = SparkSession.builder.remote("sc://localhost:15002").create()
spark.range(3).createOrReplaceTempView("my_view")
spark.catalog.tableExists("my_view"), s2.catalog.tableExists("my_view")
@F.udf("double")
def gst(a): return round(a * 1.05, 2)
    == 5) sessions are isolated session 1 sees my_view: True | session 2 sees my_view: False session ids differ: True == 6) Python UDFs run on the server side [Row(a=100, with_gst=105.0), Row(a=200, with_gst=210.0), Row(a=300, with_gst=315.0)]
    Two clients on one server got two sessions: session 2 cannot see session 1’s temp view, which is what you want for 40 analysts sharing a server. Python UDFs still work: the function is serialised and runs on the server’s executors, so the libraries it uses must be installed there.

6 Real-world use

Spark Connect at work

1. Local IDE, remote cluster

Developers debug in VS Code while queries run on the shared cluster (e.g. Databricks Connect).

IDE→Connect→Cluster

2. Shared notebook servers

JupyterHub users share Connect servers instead of starting their own drivers.

Notebook→sc://→Shared server

3. Applications

Internal services query Spark without bundling a JVM.

Service→thin client→Results

4. Independent upgrades

Platform teams upgrade the server while clients stay on compatible versions.

New Spark→server→Clients unchanged

5. Other languages

Community clients for Go, Rust and Swift speak the same protocol.

Any language→gRPC→Spark
