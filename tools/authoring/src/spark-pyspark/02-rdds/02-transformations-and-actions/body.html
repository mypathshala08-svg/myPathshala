1 The story

“My counter says zero”

Before you start: Lesson 2.1 (creating RDDs) and the lambda patterns in 1.1.

Kabir is reading the old RDD job. It splits order notes into dishes, counts the most popular ones and adds up revenue. One function is supposed to add every amount to a Python variable called total. On the cluster, total is always 0, and the job’s print() lines never appear. Riya bets it is a bug in Spark.

K> Sir, the code clearly adds to total. Why is it zero? A> Because that code did not run in your Python process. Functions passed to RDD operations are shipped to the executors with a copy of the variables they use. The executors added to their copies; your driver’s total never changed. Spark has a tool for exactly this: the accumulator. R> And the missing prints? A> They went to the executors’ logs. Today we go through the transformations and actions you will use most, on TiffinGo’s order notes and amounts, and reproduce both surprises. All outputs are real (PySpark 4.3.0).
2 Definition

Transformations, actions and closures

Formal definition (write this in exams)

RDDs support two kinds of operations. Transformations (such as map, flatMap, filter, distinct, union, mapPartitions) create a new RDD from an existing one and are evaluated lazily. Actions (such as collect, count, take, reduce, fold, aggregate, foreach, saveAsTextFile) trigger a job and return a value to the driver or write to storage. Functions passed to these operations, together with the variables they reference (their closure), are serialised and sent to executors; each task works on its own copy, so changes to driver variables inside them are not visible to the driver. Shared state must use accumulators (add-only, read on the driver) or broadcast variables (read-only).

In simple words

Transformations make a new RDD and wait; actions run the work and give you an answer. The functions you pass run on other machines with their own copies of your variables, so changing a normal variable inside them does nothing on your side.

Words you’ll meet in this lesson

mapOne output per input element.
flatMapZero or more outputs per input; results are flattened.
mapPartitionsYour function gets a whole partition (an iterator) at once.
reduce / foldCombine all elements with a function (fold has a start value).
aggregateLike fold, but the result type can differ from the elements.
ClosureA function plus the outside variables it uses.
AccumulatorA shared counter tasks can add to; the driver reads it.
foreachAction that runs a function on every element, for side effects.

LEVELS> Transformations and actions at three levels L1> Recipes and serving
  • Transformations are recipe steps: “split the notes”, “keep only hot orders”. Writing them down cooks nothing.
  • Actions are “serve it now”: count, collect, save. Only then does the kitchen work.
  • Cooks work in their own kitchens: a note you change on your desk does not change theirs.
L2> The common operations
  • Element-wise: map (one in, one out), flatMap (one in, zero or more out), filter.
  • Set-like: distinct, union, intersection, subtract; sampling: sample.
  • Per partition: mapPartitions, glom. Actions: collect, count, first, take, top, takeOrdered, reduce, fold, aggregate, countByValue, foreach, saveAsTextFile.
L3> What the lab showed
  • flatMap turned 5,000 order lines into 12,671 dish names; distinct found 32 dishes.
  • A driver variable updated in foreach stayed 0; an accumulator gave 2670. On the cluster, print output was in the executors’ stderr files.
  • map ran a setup step 100,000 times; mapPartitions ran it 4 times (once per partition).
/LEVELS EXAM> “Difference between map and flatMap?” map returns exactly one element per input; flatMap can return zero or more and flattens them, e.g. splitting lines into words. “Why does updating a variable in foreach not work?” The closure is copied to each executor; use an accumulator for counters.

4 Step by step

Every common operation, with real results

All outputs are real: PySpark 4.3.0 in local mode (Steps 1–7) and on our standalone cluster (Step 8). Data: order_items.txt, 5,000 lines like 100001|Chole Bhature,Aloo Paratha,Lassi,Rajma Chawal|spice:medium,cutlery:yes, and six order amounts.

  1. Step 1 · map and flatMap

    lines = sc.textFile("order_items.txt")
parts = lines.map(lambda l: l.split("|"))
print("map       :", parts.first())
dishes = lines.flatMap(lambda l: l.split("|")[1].split(","))
print("flatMap   :", dishes.take(5), "| elements:", dishes.count())
    map : ['100001', 'Chole Bhature,Aloo Paratha,Lassi,Rajma Chawal', 'spice:medium,cutlery:yes'] flatMap : ['Chole Bhature', 'Aloo Paratha', 'Lassi', 'Rajma Chawal', 'Veg Hakka Noodles'] | elements: 12671
    map turned each line into one list of three fields. flatMap returned the dish names of each line as separate elements: 5,000 lines became 12,671 dishes, about 2.5 per order. Whenever one input should become several outputs (words, items, events), use flatMap.

  2. Step 2 · filter, distinct, union, sample

    spicy = lines.filter(lambda l: "spice:hot" in l)
menu = dishes.distinct()
both = sc.parallelize(["Poha", "Idli"]).union(sc.parallelize(["Idli", "Dosa"]))
lines.sample(False, 0.001, seed=7).count()
    filter : 1695 orders asked for hot distinct : 32 different dishes union : ['Poha', 'Idli', 'Idli', 'Dosa'] (duplicates kept) sample : 2 lines (about 0.1%)
    filter kept 1,695 orders that asked for hot food. distinct found 32 different dishes; it needs a shuffle, because duplicates can sit in different partitions. union just appends, keeping duplicates. sample(False, 0.001) returned 2 lines, not exactly 5: sampling is random per element, so the size is only approximate.

  3. Step 3 · mapPartitions: once per partition

    setups = sc.accumulator(0)
def per_element(x):
    setups.add(1)                 # e.g. open a DB connection for every element
    return x * 2
def per_partition(it):
    setups.add(1)                 # once per partition
    return (x * 2 for x in it)
big = sc.parallelize(range(100_000), 4)
big.map(per_element).count()
big.mapPartitions(per_partition).count()
    map -> setup calls: 100000 mapPartitions -> setup calls: 4 lines.mapPartitions(lambda it: [sum(1 for _ in it)]).collect() mapPartitions: [2517, 2483] lines per partition
    With map, any setup inside the function runs for every element: 100,000 times. With mapPartitions, the function receives an iterator over a whole partition and the setup runs 4 times. That is how you open one database connection or load one model per partition. The function must return an iterator or list.

  4. Step 4 · Actions that return elements

    amounts = sc.parallelize([530, 210, 480, 990, 120, 340], 3)
amounts.collect(); amounts.count(); amounts.first(); amounts.take(2)
amounts.top(2); amounts.takeOrdered(2)
    collect : [530, 210, 480, 990, 120, 340] count : 6 | first: 530 | take(2): [530, 210] top(2) : [990, 530] | takeOrdered(2): [120, 210]
    take(2) returns the first elements in partition order; top(2) the largest; takeOrdered(2) the smallest (or by a key you give). take and first can stop after the first partitions, so they are cheap even on huge RDDs.

  5. Step 5 · reduce, fold, aggregate

    amounts.reduce(lambda a, b: a + b)
amounts.fold(0, lambda a, b: a + b)
amounts.aggregate((0, 0),
                  lambda acc, x: (acc[0] + x, acc[1] + 1),      # within a partition
                  lambda a, b: (a[0] + b[0], a[1] + b[1]))     # across partitions
    reduce : 2670 fold : 2670 aggregate : (2670, 6) (sum, count)
    reduce combines elements pairwise; the function must be associative and commutative, because Spark reduces each partition first and then combines the partial results. fold adds a neutral start value (0 for sums). aggregate can build a different type: here a (sum, count) pair in one pass, so the average is 2670 / 6 = 445.

  6. Step 6 · countByValue and saveAsTextFile

    sorted(dishes.countByValue().items(), key=lambda kv: -kv[1])[:3]
menu.saveAsTextFile("out_menu")
sorted(os.listdir("out_menu"))
    countByValue: [('Sambar Rice', 502), ('Curd Rice', 494), ('Idli', 484)] saveAsTextFile: ['._SUCCESS.crc', '.part-00000.crc', '.part-00001.crc', '_SUCCESS', 'part-00000', 'part-00001']
    countByValue returned a Python dict of all 32 dishes to the driver; Sambar Rice is the most ordered (502). saveAsTextFile wrote one file per partition (2 here), a _SUCCESS marker and hidden checksum files. Spark refuses to write into an existing folder, so remove it or choose a new name.

  7. Step 7 · The closure trap, and the fix

    counter = 0
def add(x):
    global counter
    counter += x
amounts.foreach(add)
print("driver variable after foreach:", counter)

acc = sc.accumulator(0)
amounts.foreach(lambda x: acc.add(x))
print("accumulator after foreach    :", acc.value)
    driver variable after foreach: 0 accumulator after foreach : 2670
    Exactly Kabir’s bug. add and the variable it uses were pickled and sent to each task, which updated its own copy of counter; the driver’s copy stayed 0, even in local mode. An accumulator is designed for this: tasks can only add to it and the driver reads the total (2670). Lesson 3.2 covers accumulators and broadcast variables in depth.

  8. Step 8 · Where print() goes on a cluster

    sc.parallelize(["poha", "idli", "dosa"], 2).foreach(lambda x: print("EXECUTOR SAYS:", x))
print("driver: foreach finished")
    driver output: driver: foreach finished $ docker exec sparklab-spark-worker-1-1 grep EXECUTOR work/app-20261104053842-0000/1/stderr EXECUTOR SAYS: poha $ docker exec sparklab-spark-worker-2-1 grep EXECUTOR work/app-20261104053842-0000/0/stderr EXECUTOR SAYS: idli EXECUTOR SAYS: dosa
    On the cluster, the driver printed only its own line. The prints ran inside executor processes, so they landed in each executor’s log under the worker’s work/ folder, also reachable from the Executors tab (stdout/stderr links). In local mode you see them in your terminal, which hides the problem. To look at data, bring a little back with take() and print on the driver.

6 Real-world use

These operations at work

1. Exploding records

One order with many items, one log line with many fields: flatMap turns them into one record each.

Order→flatMap→Items

2. One client per partition

Calling APIs, caches or ML models with one client per partition instead of one per record.

Partition→mapPartitions→Batch call

3. Data-quality counters

Accumulators count malformed lines while a job runs, for logs and alerts.

Parse→accumulator→Alert

4. Top-N reports

top and takeOrdered find the largest orders or busiest dishes without sorting everything.

RDD→top(10)→Report

5. Safe debugging

Engineers inspect data with take() on the driver instead of print() inside executors.

RDD→take(5)→Driver print
