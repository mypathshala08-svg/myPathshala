1 The story

“The report showed every city”

Before you start: SparkSession and plans in 4.1.

TiffinGo’s internal report page let managers type a city name. A Python function built the query with an f-string: f"... WHERE city = '{city}'". One curious manager typed Pune' OR '1'='1 and got all 5 million orders, including cities he was not allowed to see.

K> Sir, Spark is not a website database. Does SQL injection even apply? A> Any time you paste user text into SQL, yes. Spark supports parameter markers, so the value is never parsed as SQL. We will reproduce the attack and the fix. R> And the analysts say their view “did not see” today’s data. A> A temp view is a saved query, but Spark caches the file listing behind it. Today: SQL and DataFrames together, temp and global views, refreshing, parameters, Spark 4’s pipe syntax and SQL errors. All outputs are real (PySpark 4.3.0).
2 Definition

Spark SQL and views

Formal definition (write this in exams)

Spark SQL is Spark’s module for structured data; its SQL interface (spark.sql) parses ANSI-style SQL into the same logical plans as the DataFrame API, optimised by Catalyst and returned as DataFrames. A temporary view registers a logical plan under a name for the lifetime of a SparkSession; a global temporary view is registered in the system database global_temp and is shared by all sessions of the application until it ends. Views store no data: each query re-executes the plan, though file-based relations may reuse cached file listings until refreshed. Since Spark 3.4, spark.sql accepts named (:name) and positional (?) parameter markers bound as literals, which prevents SQL injection.

In simple words

You can write SQL against DataFrames by giving them a name with a temp view. SQL and DataFrame code run on the same engine. A view is a stored query, not stored data, and user input should always be passed as parameters, never pasted into the SQL text.

LEVELS> Spark SQL at three levels L1> Two languages, one kitchen
  • Some cooks read recipes in Hindi, others in English; the kitchen is the same. SQL and DataFrames are two languages for the same engine.
  • A view is a name on a recipe card, not a cooked dish.
  • Filling a blank on a form (a parameter) is safe; letting a customer rewrite the recipe is not.
L2> The API
  • df.createOrReplaceTempView("orders"), createOrReplaceGlobalTempView (global_temp.name), spark.sql(...) returns a DataFrame.
  • Parameters: spark.sql("… WHERE city = :city", args={"city": v}) or ? with a list; DataFrames as {t} keyword arguments.
  • REFRESH TABLE name or spark.catalog.refreshTable after files change; pipe syntax FROM t |> WHERE … |> AGGREGATE … (Spark 4).
L3> What the lab showed
  • A temp view was invisible to a new session; a global temp view returned 5,000,000 rows there.
  • After appending 5 rows to the files, the view still counted 3 until REFRESH TABLE (then 8).
  • The injected f-string matched 5,000,000 rows; the same text as a named parameter matched 0.
/LEVELS EXAM> “Temp view vs global temp view?” A temp view is scoped to the SparkSession that created it; a global temp view lives in the global_temp database and is visible to all sessions of the same application. Neither stores data or survives the application; for that, create a table.
3 Types and ways to use it

Passing values into SQL

MethodExampleSafe?
f-string / concatenationspark.sql(f"… city = '{c}'")No: injection, quoting bugs
Named parameterspark.sql("… city = :c", args={"c": c})Yes
Positional parameterspark.sql("… city = ?", args=[c])Yes
DataFrame / Column as argumentspark.sql("SELECT * FROM {t}", t=df)Yes (objects, not text)
DataFrame APIdf.where(F.col("city") == c)Yes
WARN> Python’s {t} formatting in spark.sql(query, **kwargs) is safe for DataFrames and Columns, but plain strings passed that way are still inserted as SQL text. For values that come from users, files or APIs, always use parameter markers (:name, ?).
4 Step by step

SQL on the orders table

All outputs are real: PySpark 4.3.0, local mode, 5,000,000 orders registered as a temp view.

  1. Step 1 · A temp view and a SQL query

    o.createOrReplaceTempView("orders")
spark.sql("""SELECT city, count(*) AS orders, sum(amount) AS revenue FROM orders
             WHERE status = 'DELIVERED' GROUP BY city ORDER BY revenue DESC LIMIT 3""").show()
type(spark.sql("SELECT 1"))
    == 1) a temp view and SQL +---------+------+---------+ | city|orders| revenue| +---------+------+---------+ | Mumbai|951430|484935971| |Bengaluru|949842|483166030| | Chennai|476038|242708114| +---------+------+---------+ type: DataFrame == 2) DataFrame <-> SQL [Row(city='MUMBAI'), Row(city='BENGALURU')]
    Registering a view costs nothing: it only names the DataFrame’s plan. spark.sql returned an ordinary DataFrame, so DataFrame methods continued on the SQL result. Mix freely: SQL for readable aggregations, Python for logic around them.

  2. Step 2 · Temp vs global temp views

    o.createOrReplaceGlobalTempView("orders_g")
s2 = spark.newSession()
s2.sql("SELECT count(*) FROM orders")
s2.sql("SELECT count(*) FROM global_temp.orders_g")
    == 3) temp views belong to a session; global temp views do not orders in new session: AnalysisException [TABLE_OR_VIEW_NOT_FOUND] The table or view `orders` cannot be found. Verify the … global_temp.orders_g in new session: 5000000
    The new session (as a notebook gateway or Thrift Server gives each user, Lesson 4.1) could not see orders, but read the global view through the global_temp database. Both disappear when the application stops.

  3. Step 3 · A view does not always see new files

    spark.range(3).write.parquet(p)
spark.read.parquet(p).createOrReplaceTempView("live")
spark.sql("SELECT count(*) FROM live")
spark.range(100, 105).write.mode("append").parquet(p)
spark.sql("SELECT count(*) FROM live")
spark.sql("REFRESH TABLE live"); spark.sql("SELECT count(*) FROM live")
    == 4) a view is a saved query, not saved data count: 3 after appending 5 rows, same view: 3 after REFRESH TABLE: 8
    The view stores the query, but the DataFrame behind it had already listed the files. After 5 rows were appended by another writer, the view still counted 3. REFRESH TABLE live dropped the cached listing: 8. Long-running notebooks and servers need refreshes (or re-reading) when data changes underneath them.

  4. Step 4 · Views on views

    spark.sql("""CREATE OR REPLACE TEMP VIEW city_daily AS
  SELECT city, order_date, sum(amount) AS revenue, count(*) AS n FROM orders GROUP BY city, order_date""")
spark.sql("SELECT city, round(avg(revenue)) AS avg_daily FROM city_daily GROUP BY city ORDER BY avg_daily DESC LIMIT 3")
    == 5) SQL views over SQL +---------+---------+ | city|avg_daily| +---------+---------+ | Mumbai|8365426.0| |Bengaluru|8340908.0| | Chennai|4188379.0| +---------+---------+
    SQL views can build on each other, like steps of a pipeline. Catalyst expands them into one plan and optimises the whole thing, so layering views costs nothing extra at run time.

  5. Step 5 · SQL injection and parameters

    city = "Pune' OR '1'='1"
spark.sql(f"SELECT count(*) FROM orders WHERE city = '{city}'")
spark.sql("SELECT count(*) FROM orders WHERE city = :city", args={"city": city})
spark.sql("SELECT count(*) FROM orders WHERE city = :city", args={"city": "Pune"})
spark.sql("SELECT count(*) FROM {t} WHERE amount > {m}", t=o, m=900)
    == 6) parameters, not string concatenation f-string query : 5000000 named parameter : 0 good value : 498646 DataFrame in SQL: 326698
    The f-string turned the input into SQL: city = 'Pune' OR '1'='1', true for all 5,000,000 rows. As a named parameter the same text was just a strange city name: 0 rows. Real values worked normally (498,646 for Pune). DataFrames can be passed to SQL as objects with {t}.

  6. Step 6 · Pipe syntax and SQL errors

    spark.sql("""FROM orders
  |> WHERE status = 'CANCELLED'
  |> AGGREGATE count(*) AS cancelled GROUP BY city
  |> ORDER BY cancelled DESC
  |> LIMIT 3""").show()
spark.sql("SELECT cty FROM orders"); spark.sql("SELECT city, sum(amount) FROM orders")
spark.catalog.listTables()

Did y … AnalysisException [MISSING_GROUP_BY] The query does not include a GROUP BY clause. Add GROUP BY or turn it into the window functions usin … == 9) the catalog [('city_daily', True, 'TEMPORARY'), ('live', True, 'TEMPORARY'), ('orders', True, 'TEMPORARY')]
    Spark 4’s pipe syntax writes SQL in the order it runs, like a chain of DataFrame calls. Mistakes are AnalysisExceptions raised before any job: a misspelt column (with a suggestion) and a missing GROUP BY. The catalog lists our three temp views.

Spark SQL at work

1. BI over the lake

Dashboards send SQL to Spark through the Thrift Server or Databricks SQL.

Dashboard→Spark SQL→Lake tables

Transformations written as SQL views and executed by Spark (dbt-spark, Declarative Pipelines).

SQL models→views→Tables

3. Internal tools

Report pages pass user filters as SQL parameters, never as concatenated text.

User input→:param→Safe query

4. Notebooks

Analysts mix %sql cells and PySpark cells on the same temp views.

DataFrame→temp view→SQL cell

5. Migrating Hive jobs

HiveQL scripts move to Spark SQL with few changes and run much faster.
