1 The story

“Should I filter before or after the join?”

Before you start: plans in 4.1, join strategies in 6.2.

During code review Riya rewrote a colleague’s query to filter orders before the join instead of after it, select columns early and precompute constants, “for performance”. Arjun Sir asked her to compare the two plans first.

R> Sir, filtering first must be faster. Fewer rows to join. A> Of course, and Catalyst already does it for you: it pushes filters down, prunes columns and folds constants before running anything. Both versions produced exactly the same optimized plan. K> Then how do we know what Spark will really do? A> With explain(). Today we read all four plans of a join query, the formatted and cost views, whole-stage code generation, prove that two styles give the same plan, and see the one thing Catalyst cannot optimise. All outputs are real (PySpark 4.3.0).
2 Definition

The Catalyst optimizer

Formal definition (write this in exams)

Catalyst is Spark SQL’s extensible query optimizer. A query from SQL or the DataFrame API passes through four phases: an unresolved (parsed) logical plan; analysis, which resolves names and types against the catalog; logical optimization, which applies rule-based rewrites such as predicate pushdown, column pruning, constant folding and filter combination (and cost-based join reordering when statistics are available); and physical planning, which chooses operators such as broadcast hash or sort-merge joins. The physical plan is then compiled by whole-stage code generation (Tungsten) into Java bytecode that fuses operators. With Adaptive Query Execution the physical plan can be revised at run time (Lesson 7.4). explain() displays these plans.

In simple words

Catalyst rewrites your query into the fastest plan it can find: it moves filters to the data, reads only needed columns, simplifies expressions and picks join methods. explain() shows you the result, so you can check what Spark will really do.

LEVELS> Catalyst at three levels L1> A route planner
  • You tell the map app where to go; it reads the request (parse), checks the places exist (analyze), finds shortcuts (optimize) and picks roads and vehicles (physical plan).
  • Two people describing the same trip in different words get the same route.
  • A stop the app knows nothing about (a UDF) cannot be optimised around.
L2> The API
  • df.explain() (physical), explain(mode="extended") (all four), "formatted" (numbered operators with details), "cost" (statistics), "codegen" (generated Java).
  • In SQL: EXPLAIN [EXTENDED | FORMATTED | COST | CODEGEN] SELECT ….
  • Look for: PushedFilters, ReadSchema, join strategy, Exchange (shuffles), *(n) code-generated stages.
L3> What the lab showed
  • Two filters written after a join were moved below it and into both scans; (1 + 1) + 798 became 800.
  • Parquet received 5 pushed filters and read 4 of 6 columns; the 2,000-row customer table was broadcast.
  • A “bad” and a “good” version of a query had identical optimized plans; a UDF filter pushed nothing.
/LEVELS EXAM> “What does Catalyst do?” It turns DataFrame/SQL queries into an optimized physical plan in four phases: parse, analyze (resolve names via the catalog), optimize logically with rules (predicate pushdown, column pruning, constant folding, CBO join reordering with stats) and plan physically (choose join and aggregation strategies), then whole-stage code generation compiles it. 4 Step by step

Four plans for one join

All outputs are real: PySpark 4.3.0, local mode. The query joins 5,000,000 orders (Parquet) with 2,000 customers (CSV), adds GST, keeps Gold customers’ delivered orders above ₹800. Plan ids (#12) are removed for readability.

q = (o.join(c, "customer_id")
      .withColumn("gst", F.col("amount") * F.lit(5) / F.lit(100))
      .where((F.col("plan") == "Gold") & (F.col("status") == "DELIVERED"))
      .where(F.col("amount") > F.lit(1) + F.lit(1) + F.lit(798))
      .select("order_id", "name", "amount", "gst"))
q.explain(mode="extended")
