1 The story

“We tuned shuffle partitions for every job”

Before you start: shuffles in 2.4, join strategies in 6.2, plans in 7.3.

Before Spark 3, TiffinGo’s platform team kept a spreadsheet of spark.sql.shuffle.partitions values per job: 200 was too many for small days and too few for festival days. One restaurant chain with most of the orders made a join run for an hour on a single task.

K> Sir, why can’t Spark choose the right number of partitions itself? A> Before running, it can only estimate. Adaptive Query Execution waits until each shuffle has finished, looks at the real sizes, and re-plans the rest: it merges small partitions, switches joins to broadcast when a side turns out small, and splits skewed partitions. R> Is it on by default? A> Since Spark 3.2. Today we switch it off and on and measure all three features, and learn to read the final plan. All outputs are real (PySpark 4.3.0).
2 Definition

Adaptive Query Execution

Formal definition (write this in exams)

Adaptive Query Execution (AQE) re-optimises a query at run time using statistics collected from completed query stages, which are delimited by shuffles and broadcasts. After each stage materialises, Spark re-plans the remaining query with the actual output sizes. Its main optimisations are coalescing post-shuffle partitions into fewer partitions close to an advisory size, switching join strategies (sort-merge to broadcast hash join, or to shuffled hash join) when a side is found to be small, and optimising skew joins by splitting oversized partitions and replicating the matching partition of the other side. AQE is enabled by default since Spark 3.2 (spark.sql.adaptive.enabled).

In simple words

AQE lets Spark change its plan while the query runs. After each shuffle it knows the real data sizes, so it can merge tiny partitions, use a broadcast join when a table turns out small, and split a partition that is much bigger than the rest.

LEVELS> AQE at three levels L1> Packing parcels
  • You booked 200 trucks before knowing the parcels. When they turn out to be few, you send 5 full trucks instead (coalescing).
  • A parcel you expected to be heavy is light: hand-carry it instead of booking a truck (switch to broadcast).
  • One giant parcel: split it across several trucks (skew join).
L2> The API
  • spark.sql.adaptive.enabled (true), …coalescePartitions.enabled, …advisoryPartitionSizeInBytes (64 MB).
  • spark.sql.adaptive.autoBroadcastJoinThreshold (defaults to the normal threshold), …skewJoin.enabled, …skewedPartitionFactor (5), …skewedPartitionThresholdInBytes (256 MB).
  • Plans show AdaptiveSparkPlan isFinalPlan=…, AQEShuffleRead coalesced, SortMergeJoin(skew=true).
L3> What the lab showed
  • groupBy city: AQE off ran 204 tasks, on ran 5; 1.74 s → 0.62 s.
  • With static broadcast disabled, AQE still turned the join into a broadcast at run time: 0.89 s → 0.05 s.
  • A key with 60% of rows: 3.67 s without AQE, 2.57 s with coalescing only, 1.92 s with skew-join splitting.
/LEVELS EXAM> “What does AQE do?” It re-optimises queries at run time using statistics from completed shuffle stages: it coalesces small shuffle partitions, converts sort-merge joins to broadcast joins when a side is small, and splits skewed partitions in joins. It is on by default since Spark 3.2; it reduces the need to hand-tune shuffle partitions but cannot fix every skew or bad data layout.

AQE off and on

  1. Step 1 · Coalescing shuffle partitions

    spark.conf.set("spark.sql.adaptive.enabled", aqe)
    o.groupBy("city").agg(F.sum("amount")).collect()
# then the final plan after running
    == 1) coalescing shuffle partitions groupBy city, AQE false : 2.00 s, stages 2, tasks 204 groupBy city, AQE true : 0.61 s, stages 2, tasks 5 ['AdaptiveSparkPlan isFinalPlan=true', '+- AQEShuffleRead coalesced']
    Without AQE the reduce stage ran all 200 tasks (plus 4 map tasks) for just 8 cities, most of them empty. With AQE, after the map stage Spark saw a few kilobytes of shuffle data and read it with one task: 5 tasks in total, about 3x faster. The final plan shows isFinalPlan=true and AQEShuffleRead coalesced.

  2. Step 2 · A join switched at run time

    spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)             # static planner: no broadcast
spark.conf.set("spark.sql.adaptive.autoBroadcastJoinThreshold", "10485760")
j = o.join(c.where("plan = 'Gold' AND state = 'KA'"), "customer_id").groupBy("plan").count()
    == 2) switching to a broadcast join at runtime AQE false: ['SortMergeJoin'], 0.97 s AQE true : ['BroadcastHashJoin', 'SortMergeJoin'], 0.06 s
    The static planner was not allowed to broadcast, so both runs started as a sort-merge join. Without AQE it stayed that way: 0.89 s. With AQE, once the filtered customer side had been materialised and turned out tiny, Spark replaced the join with a broadcast hash join (the final plan contains both: initial and final): 0.05 s.

                     .otherwise((F.rand(8) * 2000).cast("int") + 2).cast("long"))
rests = spark.range(1, 2002).withColumnRenamed("id", "rest_id")…

    == 3) a skewed join top key share: 0.599838 AQE off : 3.67 s, stages 4, tasks 209 AQE on, skewJoin off : 2.57 s, stages 4, tasks 15 AQE on, skewJoin on : 1.92 s, stages 4, tasks 18 ['+- *(5) SortMergeJoin(skew=true) [rest_id], [rest_id], Inner', ': +- AQEShuffleRead coalesced and skewed']

With skew-join handling the final plan shows SortMergeJoin(skew=true) and AQEShuffleRead coalesced and skewed: the big partition was split into several tasks, each joined with a copy of restaurant 1: 1.92 s.

6 Real-world use

AQE at work

1. Jobs with changing volumes

Daily jobs whose input varies 10x between normal and festival days run well without per-day tuning.

Any day→AQE coalesce→Right task count

2. Ad-hoc SQL

Analyst queries with unpredictable filters get broadcast joins chosen from real sizes.

Ad-hoc query→runtime switch→Fast join

3. Marketplace data

Big sellers or restaurants create hot keys; AQE splits their join partitions.

Hot key→skew join→Balanced tasks

4. Fewer output files

Coalesced shuffle partitions also mean fewer, larger output files.

Shuffle→coalesce→Fewer files

5. Performance reviews

Engineers read final plans in the Spark UI to see which AQE rules fired.

Spark UI→final plan→Insight
