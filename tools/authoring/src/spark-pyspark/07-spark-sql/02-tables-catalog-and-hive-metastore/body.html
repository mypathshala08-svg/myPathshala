1 The story

“I only dropped the table”

Before you start: views in 7.1, partitioned writes in 5.3.

Kabir cleaned up old tables with DROP TABLE. One was the raw partner archive, created with saveAsTable. The next morning its two years of files were gone from storage, not just the name. A colleague’s table over the same kind of data survived the same command: it was external.

K> Sir, the two tables looked identical in SQL. Why did one delete the data? A> Spark owns the files of a managed table, so dropping it deletes them. For an external table Spark only knows the location; dropping it removes the name. The catalog knows which is which. R> And the catalog is the Hive metastore we used in the Hive course? A> Exactly. Spark can use it to remember tables between applications. Today: catalogs, managed vs external, partitions, statistics, the catalog API, reopening from a new application, DROP, and MSCK REPAIR. All outputs are real (PySpark 4.3.0 with an embedded Hive metastore).
2 Definition

Tables, the catalog and the metastore

Formal definition (write this in exams)

Spark SQL resolves table names through a catalog. The default in-memory catalog lives only as long as the application; with enableHiveSupport() (spark.sql.catalogImplementation=hive) Spark uses a Hive metastore, a database that persistently stores databases, tables, schemas, storage locations, partitions and statistics, shared by Spark, Hive, Trino and other engines. A managed table has its data under the warehouse directory and is owned by Spark: DROP TABLE deletes the data. An external table points to a user-specified LOCATION; dropping it removes only the metadata. Partition metadata of Hive-format partitioned tables is stored in the metastore, so partitions added outside Spark must be registered (MSCK REPAIR TABLE or ALTER TABLE ADD PARTITION). Spark 3+ also supports pluggable catalogs (spark.sql.catalog.*) such as Unity Catalog, Iceberg and Glue.

In simple words

A table is files plus a catalog entry with its name, columns and location. The Hive metastore keeps these entries between applications. Managed tables belong to Spark (dropping deletes files), external tables only point to files (dropping keeps them).

LEVELS> Tables and the catalog at three levels L1> A library catalogue
  • Books (files) sit on shelves; the catalogue card says title, author and shelf (name, schema, location).
  • A library-owned book is thrown away when its card is removed (managed). A borrowed book goes back to its owner (external).
  • A temp view is a sticky note on your desk: gone when you leave.
L2> The API
  • SparkSession.builder.enableHiveSupport() (Hive metastore) or the default in-memory catalog; spark.sql.warehouse.dir for managed tables.
  • df.write.saveAsTable("db.t") (managed), CREATE TABLE t USING parquet LOCATION '…' (external), partitionBy, ANALYZE TABLE … COMPUTE STATISTICS, MSCK REPAIR TABLE.
  • spark.catalog.listDatabases/listTables/listColumns/tableExists/refreshTable.
L3> What the lab showed
  • A second application found all three tables (orders_m, orders_p, orders_x); the temp view was gone.
  • DROP TABLE: managed files 1 → 0; external files kept.
  • A partition folder added by hand was invisible (0 rows) until MSCK REPAIR TABLE (10 rows).
/LEVELS EXAM> “Managed vs external tables?” For a managed table Spark controls both metadata and data under the warehouse directory, and DROP TABLE deletes the files. For an external table the catalog stores only metadata pointing to an existing location; DROP removes the entry and leaves the data. Use external tables for data that other systems own or that must survive table changes.

4 Step by step

Two applications, one metastore

All outputs are real: PySpark 4.3.0 with enableHiveSupport() and an embedded Derby metastore. Steps 1–5 run in one application; Step 6 in a second, separate Python process.

  1. Step 1 · A Hive catalog and a database

    spark = (SparkSession.builder.config("spark.sql.warehouse.dir", W)
         .enableHiveSupport().getOrCreate())
spark.conf.get("spark.sql.catalogImplementation")
spark.sql("CREATE DATABASE IF NOT EXISTS tiffingo")
    == 1) catalog implementation: hive databases: ['default', 'tiffingo']
    With Hive support the catalog implementation is hive, and a metastore_db folder appeared beside the script. Databases are namespaces; tables are named tiffingo.orders.

  2. Step 2 · Managed and external tables

    o.write.mode("overwrite").saveAsTable("tiffingo.orders_m")
o.write.parquet(ext)
spark.sql(f"CREATE TABLE tiffingo.orders_x USING parquet LOCATION '{ext}'")
spark.sql("DESCRIBE TABLE EXTENDED tiffingo.orders_m")
    == 2) managed table files under warehouse: 1 == 3) external table orders_m | Type: MANAGED | Location: file:/root/lab/spark/data/m7/warehouse/tiffingo.db/orders_m orders_x | Type: EXTERNAL | Location: file:/root/lab/spark/data/m7/ext_orders
    saveAsTable wrote the data under the warehouse directory and registered a MANAGED table. CREATE TABLE … LOCATION registered existing files as an EXTERNAL table without copying anything. Same SQL to query both.

  3. Step 3 · Partitions and statistics

    o.write.mode("overwrite").partitionBy("city").saveAsTable("tiffingo.orders_p")
spark.sql("SHOW PARTITIONS tiffingo.orders_p")
spark.sql("ANALYZE TABLE tiffingo.orders_m COMPUTE STATISTICS FOR COLUMNS city, amount")
spark.sql("DESCRIBE TABLE EXTENDED tiffingo.orders_m city")
    == 4) partitioned table and partitions 8 partitions == 5) statistics before ANALYZE: ['1466559 bytes, 0 rows'] after ANALYZE : ['1466559 bytes, 200000 rows'] +--------------+----------+ |info_name |info_value| +--------------+----------+ |col_name |city | |data_type |string | |comment |NULL | |min |NULL | |max |NULL | |num_nulls |0 | |distinct_count|8 | |avg_col_len |8 | |max_col_len |11 | |histogram |NULL | +--------------+----------+
    The metastore recorded 8 partitions. Before ANALYZE the catalog knew only the size; afterwards it knew 200,000 rows and per-column statistics (8 distinct cities, no nulls). The optimizer uses these numbers to choose join strategies (Lesson 7.3).

  4. Step 4 · The catalog API

    spark.catalog.listTables("tiffingo")
spark.catalog.listColumns("tiffingo.orders_p")
o.createOrReplaceTempView("tmp_orders")
    == 6) catalog API [('orders_m', 'MANAGED', False), ('orders_p', 'MANAGED', False), ('orders_x', 'EXTERNAL', False)] [('status', 'string', False), ('city', 'string', True)] temp view listed: ['tmp_orders']
    The catalog API answers questions in Python: which tables exist, of which type, which columns are partition columns. Temp views appear in the same listing, marked temporary.

  5. Step 5 · A new application

    # separate process: python l72_catalog.py reopen
spark.catalog.listTables("tiffingo")
spark.catalog.tableExists("tmp_orders")
spark.table("tiffingo.orders_m").count()
    == 7) a NEW application tables: [('orders_m', 'MANAGED'), ('orders_p', 'MANAGED'), ('orders_x', 'EXTERNAL')] temp view survives? False orders_m rows: 200000
    A brand-new process found all three tables and read 200,000 rows by name, with no paths in the code. The temp view did not survive. This is the point of a metastore: tables outlive applications and can be shared by jobs, notebooks and other engines.

  6. Step 6 · DROP and MSCK REPAIR

    spark.sql("DROP TABLE tiffingo.orders_m"); spark.sql("DROP TABLE tiffingo.orders_x")
# write files into …/orders_p/city=Surat directly
spark.table("tiffingo.orders_p").where("city='Surat'").count()
spark.sql("MSCK REPAIR TABLE tiffingo.orders_p")
    == 8) DROP managed vs external managed files left : 0 external files left: 1 == 9) new files in a partition folder are invisible until repaired Surat rows before: 0 Surat rows after MSCK REPAIR: 10 metastore files: ['README_DO_NOT_TOUCH_FILES.txt', 'db.lck', 'dbex.lck', 'log']
    Kabir’s accident, reproduced: dropping the managed table deleted its files; dropping the external table left them. Files written straight into a new city=Surat folder were invisible because the metastore did not know the partition; MSCK REPAIR TABLE scanned the folders and registered it: 10 rows.

6 Real-world use

Catalogs at work

1. One metastore, many engines

Spark writes tables; Hive, Trino and BI tools read them through the same metastore.

Spark→metastore→Trino / BI

2. Raw zones as external tables

Landing data is registered externally so table changes never delete source files.

Landing files→EXTERNAL→Safe DROP

3. Glue Data Catalog

EMR Spark uses Glue as its metastore so Athena sees the same tables.

EMR Spark→Glue→Athena

4. Statistics jobs

Nightly ANALYZE TABLE keeps optimizer statistics fresh after loads.

Load→ANALYZE→Better plans

5. Governance

Unity Catalog and Lake Formation add permissions and lineage on top of table names.

Tables→grants→Controlled access
