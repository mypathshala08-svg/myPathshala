1 The story

“Spark says there are no orders”

Before you start: ACID tables (7.1), Iceberg (7.3) and the metastore (10.1).

TiffinGo’s data scientists use Spark, the BI team wants Trino for dashboards, and the warehouse is built in Hive. Everyone points their engine at the same Hive metastore. On Monday, a data scientist reports that the orders table is empty. In Hive it has five million rows.

K> Sir, if all three engines read the same metastore, how can the answers differ? A> The metastore only says where a table is and what format it has. Each engine reads the files with its own code. Plain ORC or Parquet tables are easy. Hive’s own transactional tables, Hive-specific views, and Iceberg tables created through Hive each need special support, and the metastore API itself changes between versions. R> So we test? A> We test. Today we connect Spark 3.5.6 and Trino 476 to our Hive 4.2.1 metastore and run the same queries everywhere. The first attempt fails, one table gives three different counts, and the SQL dialects disagree on details. All outputs are real.
2 Definition

One metastore, many engines

Formal definition (write this in exams)

The Hive Metastore (HMS) has become the shared catalogue of the open data stack: Spark SQL, Trino/Presto, Impala, Flink and many cloud services read and write table definitions through its Thrift API. Sharing the catalogue lets each engine see the same databases, tables, schemas, partitions and locations, but each engine reads and writes the data files with its own readers. Compatibility therefore depends on the metastore API version, the file formats and SerDes, Hive-specific features (ACID tables, views in HiveQL, storage handlers such as Iceberg’s) and SQL dialect differences.

In simple words

Hive, Spark and Trino can all use the same Hive metastore, so a table created in one is visible in the others. Whether they return the same answer depends on whether each engine understands the table’s format and Hive-specific features.

LEVELS> Many engines at three levels L1> One library catalogue, several readers
  • The metastore is a shared catalogue. Hive, Spark and Trino are different readers using it.
  • Each reader must understand the book’s language (file format) and any special rules (transactions, Iceberg).
  • Same catalogue, but a reader that does not know the rules may read the wrong pages.
L2> How each engine connects
  • Spark SQL: Hive support plus hive.metastore.uris; its built-in Hive client is 2.3.x, configurable with spark.sql.hive.metastore.version and .jars.
  • Trino: a catalog file with connector.name=hive and hive.metastore.uri; Iceberg tables through a separate iceberg catalog.
  • Hive: native; the only engine that writes Hive ACID tables with all features (MERGE, compaction, materialized views).
L3> What the lab showed
  • Spark’s built-in 2.3.9 client failed on Hive 4’s metastore (Invalid method name: 'get_table'); a 3.1.3 client worked.
  • ORC, text and Parquet tables and the views gave identical answers in all engines. The ACID table: Hive 5,000,001 rows, Trino 5,000,004 (deleted and old versions included), Spark 0, with no error.
  • Trino’s native local file system silently returned 0 rows for file: locations; Spark could not open the Iceberg table through Hive’s storage handler or its own Hive catalog.
/LEVELS EXAM> “Can Spark and Trino use Hive tables?” Yes, through the Hive metastore: Spark with Hive support and hive.metastore.uris, Trino with a hive catalog. Plain ORC/Parquet tables work well. Check Hive ACID tables, HiveQL views and Iceberg tables per engine and version; metastore client versions must also be compatible.

4 Step by step

Three engines, one metastore, real answers

All outputs are real: Hive 4.2.1, Spark 3.5.6 (apache/spark image) and Trino 476 (trinodb/trino), all connected to the lab metastore and the same warehouse volume. Scripts are in the course lab folder (lab/engines).

  1. Step 1 · Spark’s first attempt fails

    spark-sql --conf spark.hadoop.hive.metastore.uris=thrift://metastore:9083 \
  -e "SHOW DATABASES; USE tiffingo; SELECT COUNT(*) FROM orders;"
    default tiffingo org.apache.hadoop.hive.ql.metadata.HiveException: Unable to fetch table orders. Invalid method name: 'get_table' org.apache.spark.sql.AnalysisException: org.apache.hadoop.hive.ql.metadata.HiveException: Unable to fetch table orders. Invalid method name: 'get_table'
    Spark listed the databases, then failed on the first table: Spark 3.5 ships a Hive 2.3.9 metastore client, which calls the Thrift method get_table; the Hive 4 metastore no longer offers it. Same catalogue, incompatible client.

  2. Step 2 · Use a newer metastore client

    #!/bin/bash
# spark-sql with a Hive 3.1.3 metastore client (downloaded by Spark from Maven), host network
docker run --rm --network host -u 0 \
  -e JAVA_TOOL_OPTIONS="$JAVA_TOOL_OPTIONS" -v /etc/ssl/certs/java/cacerts:/etc/ssl/certs/java/cacerts:ro \
  -v hivelab_warehouse:/opt/hive/data/warehouse -v /root/lab/hive/data:/data -v /root/lab/engines/ivy:/root/.ivy2 \
  apache/spark:3.5.6 /opt/spark/bin/spark-sql \
  --conf spark.hadoop.hive.metastore.uris=thrift://localhost:9083 \
  --conf spark.sql.hive.metastore.version=3.1.3 --conf spark.sql.hive.metastore.jars=maven \
  --conf spark.sql.warehouse.dir=file:/opt/hive/data/warehouse \
  --conf spark.ui.enabled=false $EXTRA \
  -e "$1" 2>&1 | grep -vE "^[0-9]{2}/[0-9]{2}/[0-9]{2} [0-9:]+ (INFO|WARN)|^WARNING|^Setting default log level|^To adjust logging|SLF4J|^Spark Web UI|^Spark master|^\s*$|^Picked up JAVA_TOOL"
    Spark can load a different Hive client: spark.sql.hive.metastore.version=3.1.3 with .jars=maven downloaded 209 JAR files (236 MB) on the first run, then SELECT COUNT(*) FROM orders returned 50,000, as in Hive. In production you pin these JARs locally (.jars=path) instead of downloading at start-up.

  3. Step 3 · The same report in Spark and Trino

    -- Spark
SELECT c.city, COUNT(*) AS n, SUM(o.amount) AS rev FROM orders o JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date = '2026-10-05' AND c.plan = 'Gold' GROUP BY c.city ORDER BY rev DESC LIMIT 3;
SELECT COUNT(*) AS gold_orders FROM v_gold_orders;          -- the Hive view from Lesson 9.2

-- Trino
SELECT … FROM hive.tiffingo.orders o JOIN hive.tiffingo.customers c … WHERE o.order_date = DATE '2026-10-05' …;
SELECT COUNT(*) AS gold_orders FROM hive.tiffingo.v_gold_orders;
    -- Spark Bengaluru 100 26600.00 Mumbai 71 19270.00 Pune 60 18090.00 13014 -- Trino city | n | rev -----------+-----+---------- Bengaluru | 100 | 26600.00 Mumbai | 71 | 19270.00 Pune | 60 | 18090.00 (3 rows) gold_orders ------------- 13014 (1 row)
    Identical to Hive’s answer from Lesson 8.1 (Bengaluru 100, 26,600.00), and the Hive view gave 13,014 Gold orders in both engines. Trino needed hive.hive-views.enabled=true to read Hive views (off by default) and three-part names catalog.schema.table.

  4. Step 4 · Trino’s catalog files, and a silent zero

    connector.name=hive
hive.metastore.uri=thrift://metastore:9083
fs.hadoop.enabled=true
hive.hive-views.enabled=true

# iceberg.properties
connector.name=iceberg
iceberg.catalog.type=hive_metastore
hive.metastore.uri=thrift://metastore:9083
fs.hadoop.enabled=true
    Our first Trino configuration used the new native local file system (fs.native-local.enabled=true). Every table returned 0 rows, with no error, because our tables have file: locations: trino> SELECT COUNT(*) FROM hive.tiffingo.customers; → 0. Switching to fs.hadoop.enabled=true gave 2,000 and 50,000. On HDFS or S3 you configure the matching file system; the lesson is to verify counts, not just connectivity.

  5. Step 5 · The transactional table: three engines, three answers

    -- Hive
SELECT COUNT(*) AS n FROM orders_tx;
SELECT order_id, status FROM orders_tx WHERE order_id > 999000000 ORDER BY order_id;
-- Trino
SELECT COUNT(*) AS rows FROM hive.tiffingo.orders_tx;
SELECT order_id, status FROM hive.tiffingo.orders_tx WHERE order_id > 999000000 ORDER BY order_id, status;
-- Spark
SELECT COUNT(*) FROM orders_tx;
    -- Hive +----------+ | n | +----------+ | 5000001 | +----------+ +------------+------------+ | order_id | status | +------------+------------+ | 999000010 | CANCELLED | +------------+------------+ -- Trino rows --------- 5000004 (1 row) order_id | status -----------+----------- 999000001 | DELIVERED 999000002 | DELIVERED 999000010 | CANCELLED 999000010 | NEW (4 rows) -- Spark 0
    orders_tx is the full-ACID table from Modules 9 and 10, with rows inserted, deleted and updated since. Hive: 5,000,001 rows, order 999000010 once, CANCELLED. Trino 476: 5,000,004: it ignored the delete deltas and returned two deleted orders and the old NEW version of the updated one. Spark: 0 rows, because Spark does not read Hive ACID tables. None of the wrong answers raised an error.

  6. Step 6 · Iceberg tables: format first, engine second

    -- Spark through the Hive table definition
SELECT COUNT(*) FROM orders_ice;
-- Spark through its Iceberg catalog (iceberg-spark-runtime 1.9.1, type=hive)
SELECT COUNT(*) AS rows FROM ice.tiffingo.orders_ice;

-- Trino: hive catalog, then iceberg catalog
SELECT COUNT(*) FROM hive.tiffingo.orders_ice;
SELECT COUNT(*) AS rows FROM iceberg.tiffingo.orders_ice;
SELECT snapshot_id, operation FROM iceberg.tiffingo."orders_ice$snapshots" ORDER BY committed_at;
    -- Spark Caused by: java.lang.ClassNotFoundException: org.apache.iceberg.mr.hive.HiveIcebergStorageHandler Caused by: org.apache.thrift.TApplicationException: Invalid method name: 'get_table' -- Trino Query 20261030_052214_00005_7jd7u failed: Cannot query Iceberg table 'tiffingo.orders_ice' rows ------ 4886 (1 row) snapshot_id | operation ---------------------+----------- 4523378673848349691 | append 303231479046229805 | overwrite 4541262957374694773 | delete 484475520336695239 | append (4 rows)
    Through the Hive definition, Spark needs Hive’s Iceberg storage handler class; through its own Iceberg catalog, it hit the same get_table incompatibility as in Step 1, because Iceberg’s Hive catalog uses Spark’s built-in client. Trino refused it in the hive catalog but read it through the iceberg catalog: 4,886 rows, as in Hive, and the same four snapshots from Lesson 7.3. For Iceberg, engines should use an Iceberg catalog (Hive metastore, REST, Glue), not Hive’s table definition.

    Both Spark tables were readable in Hive with identical numbers. The Spark “data source” table carries Spark-only properties (spark.sql.sources.provider = parquet, the schema as JSON), and Hive 4’s metastore turned it into an EXTERNAL table with purge. Writing simple Parquet or ORC tables from Spark for Hive and Trino to read is the safest direction.

  8. Step 8 · Dialects and speed

    -- Hive: 'rows' is a reserved word
SELECT COUNT(*) AS rows FROM orders_tx;
-- Trino: no implicit string → date cast
SELECT COUNT(*) FROM hive.tiffingo.orders WHERE order_date = '2026-10-05';

-- same aggregation on orders_big (5,000,000 rows, ORC), three runs each
SELECT city, status, COUNT(*) AS n, SUM(amount) AS rev, AVG(amount) AS avg_amt
FROM tiffingo.orders_big WHERE amount > 100 GROUP BY city, status;
    Error: Error while compiling statement: FAILED: ParseException line 1:19 cannot recognize input near 'AS' 'rows' 'FROM' in selection target Query 20261030_052433_00014_7jd7u failed: line 1:60: Cannot apply operator: date = varchar(10) LINE 1: SELECT COUNT(*) FROM hive.tiffingo.orders WHERE order_date = '2026-10-05' ^ engine run 1 run 2 run 3 measured as Trino 1.60 s 0.79 s 0.75 s server-side elapsed (system.runtime.queries) Hive 2.01 s 1.64 s 1.60 s HiveServer2 "Completed executing … Time taken" (results cache off) Spark 7.77 s 2.24 s 2.10 s spark-sql "Time taken" (same session; JVM start excluded)
    SQL that runs in one engine may not parse in another: rows is reserved in Hive but fine in Trino; Trino will not compare a DATE with a string literal, which Hive casts silently. On our single-node lab, Trino answered in about 0.75 s once warm, Hive in about 1.6 s and Spark in about 2.1 s. Treat these as indicative only: one machine, tiny data, different ways of measuring.
