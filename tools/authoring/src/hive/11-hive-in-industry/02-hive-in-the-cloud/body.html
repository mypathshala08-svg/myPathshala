1 The story

“Shut the cluster down at night”

Before you start: external tables (2.2), MSCK (5.2), small files (5.4) and the metastore (10.1).

TiffinGo’s finance team sees the Hadoop cluster bill: twelve machines run all night for a load that takes forty minutes. The new plan is to keep the data in cloud object storage, start a cluster for the load, and shut it down afterwards. Kabir is asked to prove it works with Hive.

K> Sir, if Hive just reads files, does it matter whether they are on HDFS or on S3? A> The SQL is the same; the table location changes from hdfs:// to s3a://. But object storage is not a file system. A “rename” is a copy plus a delete, a “folder” is only a key prefix, every listing is an HTTP request, and permissions come from cloud credentials, not from Linux users. R> So the same query can behave differently? A> It answers the same, but it fails differently, costs differently and is slower in different places. Today we connect our Hive 4.2.1 lab to an S3-compatible server, write a partitioned table there, count every request Hive makes, and compare the managed cloud services. All outputs are real.
2 Definition

Hive with object storage and managed services

Formal definition (write this in exams)

In the cloud, Hive usually runs with separated storage and compute: table data lives in object storage (Amazon S3, Google Cloud Storage, Azure Data Lake Storage Gen2) accessed through a Hadoop file-system connector, the metastore runs as a managed database or catalogue service (AWS Glue Data Catalog, Dataproc Metastore, Azure SQL Database), and compute runs on managed clusters (Amazon EMR, Google Dataproc, Azure HDInsight) that can be resized or deleted without losing data. Object stores offer strong read-after-write consistency but no atomic rename and no real directories, so Hive’s staging-and-move commit, partition discovery and listing-heavy planning cost more requests and time than on HDFS.

In simple words

In the cloud, Hive tables usually live in object storage such as S3, the metastore is a managed service, and the cluster is temporary. The SQL stays the same; renames, folders, credentials and costs behave differently.

LEVELS> Hive in the cloud at three levels L1> Kitchen and warehouse
  • The cluster is the kitchen; object storage is the warehouse across the road.
  • You can close the kitchen at night; the food in the warehouse stays.
  • Moving a box inside the warehouse is slow: you copy it to a new shelf and throw the old one away.
L2> The pieces you configure
  • A file-system connector: S3A (s3a://, open source), EMRFS on Amazon EMR (s3://), the Cloud Storage connector on Dataproc (gs://), ABFS on Azure (abfs://).
  • Credentials for every process that touches data: HiveServer2, the metastore and the Tez tasks (an IAM role or service account in production).
  • A metastore outside the cluster: a managed database, AWS Glue Data Catalog or Dataproc Metastore, so the catalogue survives when clusters are deleted.
L3> What the lab showed
  • Tasks without credentials failed with NoAuthWithAWSException; the session itself had connected fine.
  • One partition overwrite wrote 1 object and made 4 server-side copies through staging folders: 85 requests in total.
  • A folder added with an S3 tool stayed invisible to Hive (0 rows) until MSCK REPAIR TABLE; staging on another file system was refused (Wrong FS).
/LEVELS EXAM> “How does Hive work on S3?” Through a Hadoop connector (S3A, or EMRFS on EMR) with tables at s3a:// or s3:// locations, credentials from IAM roles, and usually an external metastore such as Glue. S3 has no atomic rename, so commits copy data and listings cost requests; use fewer, larger files, partition pruning, and table formats such as Iceberg that avoid renames.

4 Step by step

A Hive table on S3, request by request

Our lab uses an S3-compatible server (moto) on the lab machine, so every request can be logged and nothing costs money. Hive 4.2.1 talks to it through the standard S3A connector, exactly as it would to Amazon S3. Configuration files are in the course lab folder (lab/cloud).

  1. Step 1 · Point Hadoop at the object store

    <?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <property><name>fs.s3a.endpoint</name><value>http://172.18.0.1:5050</value></property>
  <property><name>fs.s3a.access.key</name><value>lab</value></property>
  <property><name>fs.s3a.secret.key</name><value>labsecret</value></property>
  <property><name>fs.s3a.path.style.access</name><value>true</value></property>
  <property><name>fs.s3a.connection.ssl.enabled</name><value>false</value></property>
  <property><name>fs.s3a.endpoint.region</name><value>us-east-1</value></property>
  <property><name>fs.s3a.impl</name><value>org.apache.hadoop.fs.s3a.S3AFileSystem</value></property>
</configuration>
    services:
  metastore:
    environment:
      HADOOP_OPTIONAL_TOOLS: hadoop-aws
      AWS_ACCESS_KEY_ID: lab
      AWS_SECRET_ACCESS_KEY: labsecret
    volumes:
      - ./cloud/core-site.xml:/opt/hive/conf/core-site.xml:ro
  hiveserver2:
    environment:
      HADOOP_OPTIONAL_TOOLS: hadoop-aws
      AWS_ACCESS_KEY_ID: lab
      AWS_SECRET_ACCESS_KEY: labsecret
    volumes:
      - ./cloud/core-site.xml:/opt/hive/conf/core-site.xml:ro
    HADOOP_OPTIONAL_TOOLS=hadoop-aws puts the S3A connector and the AWS SDK on Hive’s classpath. path.style.access and the endpoint are only needed for S3-compatible servers; on AWS you set the region. Never put keys in core-site.xml in production: on EC2/EMR the instance’s IAM role provides credentials automatically.

  2. Step 2 · The first write fails in the tasks

    INSERT OVERWRITE TABLE orders_s3 PARTITION (order_date)
SELECT order_id, customer_id, city, amount, status, order_date
FROM orders WHERE order_date BETWEEN '2026-10-01' AND '2026-10-07';
    Caused by: org.apache.hadoop.fs.s3a.auth.NoAuthWithAWSException: No AWS Credentials provided by TemporaryAWSCredentialsProvider SimpleAWSCredentialsProvider EnvironmentVariableCredentialsProvider IAMInstanceCredentialsProvider : software.amazon.awssdk.core.exception.SdkClientException: Unable to load credentials from system settings.
    Creating the table worked: the metastore and HiveServer2 could reach the bucket. The INSERT failed inside a Tez task, which did not see the keys we had first put only in the session. Every process that reads or writes data needs credentials. We added AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY to both containers (Step 1); in the cloud an instance role covers all processes.

  3. Step 3 · A partitioned Parquet table on S3

    CREATE EXTERNAL TABLE orders_s3 (
  order_id INT, customer_id INT, city STRING, amount DECIMAL(10,2), status STRING)
PARTITIONED BY (order_date DATE)
STORED AS PARQUET
LOCATION 's3a://tiffingo-lake/warehouse/orders_s3';

-- the INSERT from Step 2, then:
SELECT order_date, COUNT(*) AS n FROM orders_s3 GROUP BY order_date ORDER BY order_date;
    +-------------+-------+ | order_date | n | +-------------+-------+ | 2026-10-01 | 1641 | | 2026-10-02 | 1617 | | 2026-10-03 | 1668 | | 2026-10-04 | 1744 | | 2026-10-05 | 1621 | | 2026-10-06 | 1678 | | 2026-10-07 | 1662 | +-------------+-------+
    The same counts as the source orders table for each day. Nothing in the SQL is cloud-specific except the LOCATION. External tables on object storage are the most common cloud pattern: dropping the table or deleting the cluster leaves the data in the bucket.

  4. Step 4 · What is really in the bucket

    s3.list_objects_v2(Bucket='tiffingo-lake', Prefix='warehouse/orders_s3/')
    $ aws s3 ls --recursive s3://tiffingo-lake/warehouse/orders_s3/ (via boto3) 0 warehouse/orders_s3/ 23724 warehouse/orders_s3/order_date=2026-10-01/000000_0 23407 warehouse/orders_s3/order_date=2026-10-02/000000_0 24119 warehouse/orders_s3/order_date=2026-10-03/000000_0 25115 warehouse/orders_s3/order_date=2026-10-04/000000_0 23419 warehouse/orders_s3/order_date=2026-10-05/000000_0 24236 warehouse/orders_s3/order_date=2026-10-06/000000_0 24025 warehouse/orders_s3/order_date=2026-10-07/000000_0 objects: 8
    Seven Parquet objects, one per partition, and a 0-byte object warehouse/orders_s3/: a directory marker, because S3 has no folders. order_date=2026-10-01/ is only part of each key. Tools that “list a folder” send LIST requests with a prefix, page by page.

  5. Step 5 · One partition overwrite, every request counted

    INSERT OVERWRITE TABLE orders_s3 PARTITION (order_date = '2026-10-08')
SELECT order_id, customer_id, city, amount, status FROM orders_s3 WHERE order_date = '2026-10-07';
    S3 requests for one INSERT OVERWRITE of a single partition (1,6xx rows, 1 file): GET 38 HEAD 32 PUT 9 DELETE 4 POST 2 total 85 Write path of ONE output file (S3 server log, staging prefix shortened to .hive-staging_…/): PUT …/order_date=2026-10-08/.hive-staging_…/_task_tmp.-ext-10000/-tmp.000000_0 PUT …/order_date=2026-10-08/.hive-staging_…/-tmp.-ext-10000/000000_0 DELETE …/order_date=2026-10-08/.hive-staging_…/_task_tmp.-ext-10000/-tmp.000000_0 PUT …/order_date=2026-10-08/.hive-staging_…/-tmp.-ext-10000.moved/000000_0 POST /tiffingo-lake?delete PUT …/order_date=2026-10-08/.hive-staging_…/-ext-10000/000000_0 DELETE …/order_date=2026-10-08/.hive-staging_…/-tmp.-ext-10000.moved/000000_0 PUT …/order_date=2026-10-08/000000_0 DELETE …/order_date=2026-10-08/.hive-staging_…/-ext-10000/000000_0 POST /tiffingo-lake?delete
    One output file, but 85 requests. The task wrote the data once (_task_tmp…), then Hive “renamed” it three times through its staging folders and once into the partition. On S3 each rename is a server-side copy plus a delete. With one small file it is quick; with thousands of large files the commit can take longer than the query. A second run made 93 requests.

  6. Step 6 · Staging must stay on the table’s file system

    SET hive.exec.stagingdir=file:///tmp/hstage;
INSERT OVERWRITE TABLE orders_s3 PARTITION (order_date = '2026-10-08') SELECT …;
    Error: Error while compiling statement: FAILED: IllegalArgumentException Wrong FS file://null//tmp/hstage_hive_2026-10-30_05-41-21_280_7636308618137132838-10 -expected s3a://tiffingo-lake
    Moving staging off S3 to avoid the copies does not work: the final move must happen inside one file system. The real fixes are writers that commit without renames: EMR’s S3-optimised committer for its engines, the S3A magic/staging committers for Spark and MapReduce, or table formats such as Iceberg, which write files once and commit by swapping a metadata pointer (Lesson 11.3).

  7. Step 7 · Files added outside Hive stay invisible

    -- copy a partition object with an S3 tool
s3.copy_object(..., Key='warehouse/orders_s3/order_date=2026-10-09/000000_0')

SELECT COUNT(*) AS n FROM orders_s3 WHERE order_date = '2026-10-09';
SHOW PARTITIONS orders_s3;
MSCK REPAIR TABLE orders_s3;
SELECT COUNT(*) AS n FROM orders_s3 WHERE order_date = '2026-10-09';
    +----+ | n | +----+ | 0 | +----+ +------------------------+ | partition | +------------------------+ | order_date=2026-10-01 | | order_date=2026-10-02 | | order_date=2026-10-03 | | order_date=2026-10-04 | | order_date=2026-10-05 | | order_date=2026-10-06 | | order_date=2026-10-07 | | order_date=2026-10-08 | +------------------------+ -- after MSCK REPAIR +-------+ | n | +-------+ | 1662 | +-------+
    The object was in the bucket, but the metastore knew only eight partitions, so Hive answered 0 without an error. MSCK REPAIR TABLE listed the prefixes and added the partition: 1,662 rows. In the cloud, upstream jobs often drop files straight into buckets; either they register partitions (ALTER TABLE … ADD PARTITION), you run MSCK on a schedule, or, on Athena, partition projection computes partitions without listing.

  8. Step 8 · Reading from S3 versus local storage

    CREATE TABLE orders_loc STORED AS PARQUET AS SELECT * FROM orders_s3;   -- local copy, 14,950 rows
SELECT city, SUM(amount) FROM orders_loc GROUP BY city;
SELECT city, SUM(amount) FROM orders_s3  GROUP BY city;
    SELECT city, SUM(amount) FROM <t> GROUP BY city (9 partitions, ~14,900 rows, wall time incl. Beeline start) table storage run1 run2 S3 requests per run orders_loc local warehouse (Parquet) 5.29 s 5.02 s 0 orders_s3 s3a://tiffingo-lake (Parquet) 5.93 s 6.38 s 90 (HEAD 45, GET 45)
    Same answers. The S3 table took slightly longer and made 90 requests (45 HEAD, 45 GET) for nine small files; the local table made none. Our S3 server runs on the same machine, so each request takes about a millisecond. Real S3 requests take tens of milliseconds and are billed per thousand, which is why small files hurt more in the cloud than on HDFS. Treat the times as indicative.

6 Real-world use

Hive in the cloud at work

1. Clusters per job

Schedulers create EMR or Dataproc clusters for nightly Hive loads and delete them after; data and catalogue persist.

Schedule→cluster→S3 tables

2. One catalogue for many services

Hive on EMR, Athena, Redshift Spectrum and Glue jobs share table definitions in the Glue Data Catalog.

Hive DDL→Glue→Athena SQL

3. Lift-and-shift of on-prem Hive

Companies copy HDFS data to buckets with DistCp and run the same HiveQL on Dataproc or HDInsight.

HDFS→DistCp→Bucket

4. Landing zones with partition repair

Upstream systems drop daily files into prefixes; a job runs ADD PARTITION or MSCK so Hive and Athena see them.

Files land→MSCK→Queryable

5. Cost control

Teams track request counts and small files per table, because object stores bill per request.

Many files→compact→Lower bill
