1 The story

“Can we make the join stop shuffling?”

Before you start: joins (3.3), bucketing (5.3), plans (8.1) and statistics (8.2).

TiffinGo’s biggest nightly job joins orders with customers. Kabir read the plan (Lesson 8.1) and fixed the statistics (Lesson 8.2). Now the team wants to know which join methods Hive has and how to get the fast ones.

K> Sir, Lesson 5.3 said bucketing gives faster joins. But my plan still broadcasts. A> Hive has four join methods. A shuffle join sends both tables across the network by key. A map join copies the small table to every task and skips the shuffle. A bucket map join loads only the matching bucket. An SMB join merges sorted buckets without any hash table. Each has conditions, and Hive is strict about them. R> And skew? One corporate customer has 40% of the orders. A> We will build that table, see what Hive’s skew settings do on Tez (in our lab: nothing), and fix it by hand. Every plan and counter today is real, from Hive 4.2.1, including the conditions that made bucket joins finally appear.
2 Definition

Join optimisations in Hive

Formal definition (write this in exams)

Hive executes an equi-join with one of several physical algorithms. The shuffle (common) join repartitions both inputs by the join key and joins them in reducers. A map join (broadcast join) loads the smaller input into an in-memory hash table on every task processing the larger input, avoiding the shuffle; Hive converts joins automatically when the estimated size of the small inputs is below hive.auto.convert.join.noconditionaltask.size. When both tables are bucketed on the join key, a bucket map join sends each task only the matching bucket of the small table, and when they are also sorted on the key with the same number of buckets, a sort-merge-bucket (SMB) join merges the buckets directly. Skew join handling separates heavily repeated keys so they do not overload one task.

In simple words

Hive can join tables in different ways. The slow, general way sends both tables over the network. Faster ways copy a small table to every worker, or use matching buckets so each worker only needs a slice. The plan shows which one Hive picked.

LEVELS> Join optimisation at three levels L1> Matching two lists
  • To join orders with customers, Hive must bring each order and its customer to the same place.
  • Shuffle join: both lists are sorted into piles by customer_id and sent over the network. Works for any size, but moves a lot of data.
  • Map join: if one list is small, give a full copy to every worker. No piles needed.
L2> The four methods and their conditions
  • Shuffle (common / merge) join: default fallback. Both sides go through SIMPLE_EDGE to a reducer running Merge Join Operator.
  • Map (broadcast) join: small side under hive.auto.convert.join.noconditionaltask.size (10,000,000 bytes in our lab); BROADCAST_EDGE, Map Join Operator.
  • Bucket map join: both tables bucketed on the join key with compatible counts; each big-table task gets only its bucket of the small table (CUSTOM_EDGE, BucketMapJoin:true).
  • SMB join: both bucketed and sorted on the key, same bucket count: merge bucket i with bucket i inside the map task (Merge Join Operator + Dummy Store).
L3> What the lab showed
  • Bucketed, sorted external tables never got a bucket map or SMB join; managed transactional tables did.
  • Full ACID tables cannot be SORTED BY (“cannot support full ACID functionality since it is sorted”); SMB worked with insert-only tables.
  • Shuffle join moved 342,929 bytes vs 31,867 for the map join. /*+ MAPJOIN */ hints are ignored by default. Skew settings did not change the Tez plan; splitting the hot key did the job.
/LEVELS EXAM> “Explain map join, bucket map join and SMB join.” Map join: small table copied to every task, no shuffle; automatic below a size threshold. Bucket map join: both tables bucketed on the join key (compatible counts); each task loads only its bucket of the small table. SMB: both bucketed and sorted on the key with the same bucket count; buckets are merged, so neither side must fit in memory. Verify in EXPLAIN.

4 Step by step

Four join methods, real plans and counters

All outputs are real, from the Hive 4.2.1 lab. Plans keep the lines that identify the join; counters come from SET hive.tez.exec.print.summary=true.

  1. Step 1 · Shuffle (merge) join

    SET hive.auto.convert.join=false;
EXPLAIN SELECT c.city, COUNT(*), SUM(o.amount)
FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.city;
    Reducer 2 <- Map 1 (SIMPLE_EDGE), Map 4 (SIMPLE_EDGE) Reducer 3 <- Reducer 2 (SIMPLE_EDGE) <-Reducer 2 [SIMPLE_EDGE] Merge Join Operator [MERGEJOIN_19] (rows=50000 width=203) <-Map 1 [SIMPLE_EDGE] vectorized TableScan [TS_0] (rows=50000 width=116) <-Map 4 [SIMPLE_EDGE] vectorized TableScan [TS_3] (rows=2000 width=95)
    Both tables are read by their own map vertex (Map 1, Map 4) and shuffled by customer_id (SIMPLE_EDGE) into Reducer 2, where the Merge Join Operator joins rows with the same key. A third vertex groups by city. This works for any size, but every row of both tables crosses the network.

  2. Step 2 · Map join (the default here)

    EXPLAIN SELECT c.city, COUNT(*), SUM(o.amount)
FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.city;
    Map 1 <- Map 3 (BROADCAST_EDGE) Reducer 2 <- Map 1 (SIMPLE_EDGE) <-Map 1 [SIMPLE_EDGE] vectorized Map Join Operator [MAPJOIN_26] (rows=50000 width=203) <-Map 3 [BROADCAST_EDGE] vectorized TableScan [TS_3] (rows=2000 width=95) <-Select Operator [SEL_25] (rows=50000 width=116) TableScan [TS_0] (rows=50000 width=116)
    With the default settings customers (2,000 rows) is under the 10,000,000-byte limit, so Map 3 broadcasts it to every task of Map 1, which joins in memory. The join needs no reducer; one shuffle remains for GROUP BY.

    This is why Lesson 5.3 never saw a bucket join. With default settings the bucketed tables got an ordinary broadcast; with a small threshold and every bucket setting on, a shuffle merge join. In Hive 4.2.1 our external bucketed tables were never joined bucket by bucket, most likely because Hive cannot guarantee that files written outside it follow the bucketing.

  8. Step 8 · A skewed key

    CREATE TABLE orders_skew STORED AS ORC AS SELECT order_id,
  CASE WHEN order_id % 10 < 4 THEN 7 ELSE customer_id END AS customer_id, amount FROM orders;
SELECT customer_id, COUNT(*) AS n FROM orders_skew GROUP BY customer_id ORDER BY n DESC LIMIT 3;

Behind the screen
  1. Both inputs are repartitioned by key so equal keys meet in one reducer.
  2. Every map task builds a hash table of the small side and streams the big side through it.
  3. Bucket i of the big table only needs bucket i of the small one.
  4. Sorted buckets are merged like two sorted lists.
  5. Hash partitioning sends every row of a key to the same task.

  2. The estimate says small, the table is big.

Skewed join 5 steps
Animated example
  1. One straggler task is the symptom.
  2. Count rows per key to find it.
  3. A map join avoids the shuffle on the key.
  4. Split the hot key into a separate join.

6 Real-world use

Join optimisation at work

1. Fact-to-dimension joins

Reports join a huge fact table with small dimensions (stores, plans, dates); map joins keep them shuffle-free.

Fact + dims→broadcast→Fast report

2. Large-to-large joins

Orders with payments or clicks with sessions: tables bucketed (and sorted) on the key avoid repeated full shuffles.

Same buckets→bucket / SMB→Less shuffle

3. Marketplaces and telecom

A few sellers or cell towers dominate the data; hot keys are split out or salted so one task does not hold up the job.

Hot key→split / salt→Even tasks

4. Incident response

Map-join memory failures are traced to stale statistics or a grown dimension, fixed with ANALYZE or a threshold change.

Failure→EXPLAIN + stats→Stable job

5. Code review

Reviewers check the join type in the plan and ask why a large shuffle join is needed before a job goes live.

New job→join check→Approved
