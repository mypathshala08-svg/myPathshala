1 The story

“The query works. But what is Hive actually doing?”

Before you start: recall how a query becomes a job (1.4), joins (3.3) and GROUP BY (3.2).

Marketing wants the top three cities by revenue from Gold customers on 5 October. Kabir’s query returns the right answer, but on the production cluster a similar query takes twenty minutes. Before changing anything, Arjun Sir asks him to read the plan.

K> Sir, the plan is 50 lines of operators. Where do I even start? A> At the bottom. A Hive plan is a tree: data enters at the TableScans at the leaves and flows up to the File Output at the top. The “Vertex dependency” lines at the start tell you how the Tez stages connect. Then look at the row counts: Hive’s guesses decide the join strategy and the number of reducers. R> And if the guesses are wrong? A> EXPLAIN ANALYZE runs the query and prints estimated/actual rows next to each operator. Today we read one real plan line by line, then use EXPLAIN’s other forms: CBO, COST, the classic stage view, VECTORIZATION, DEPENDENCY and LOCKS. All outputs are real, from Hive 4.2.1.
2 Definition

EXPLAIN and the query plan

Formal definition (write this in exams)

EXPLAIN displays the execution plan Hive generates for a statement without running it: the stages (on Tez, a DAG of vertices connected by edges) and, for each vertex, the tree of operators (TableScan, Filter, Select, Join, Group By, Reduce Output, Limit, File Output) with estimated row counts and data sizes derived from table and column statistics. Variants add information: ANALYZE executes the query and shows actual row counts, CBO shows the cost-based optimiser’s logical plan, VECTORIZATION explains vectorised execution, DEPENDENCY lists inputs, LOCKS lists the locks a statement would take, and EXTENDED adds physical details.

In simple words

EXPLAIN prints Hive’s plan for your query: which tables it reads, how it joins and groups, how the work is split into Tez stages, and how many rows it expects at each step. It is the first thing to look at when a query is slow.

Words you’ll meet in this lesson

LEVELS> Reading plans at three levels L1> A recipe card
  • SQL says what you want; the plan says how Hive will cook it: which tables to read, in which order to join, where to group and sort.
  • EXPLAIN + your query prints the plan without running it. Read it from the bottom up: tables at the bottom, final result at the top.
  • Each step is an operator: TableScan (read), Filter (WHERE), Select (columns), Join, Group By, Limit, File Output.
L2> Vertices, edges and estimates
  • Hive on Tez runs a DAG of vertices: Map n (read files) and Reducer n (after a shuffle). Map 1 <- Map 4 (BROADCAST_EDGE) means Map 4’s output is sent whole to every Map 1 task: a map join.
  • Edges: SIMPLE_EDGE (shuffle by key), BROADCAST_EDGE (copy to all), CUSTOM_SIMPLE_EDGE / CUSTOM_EDGE (special routing).
  • (rows=25000 width=172) are estimates from statistics. Tbl:COMPLETE, Col:NONE says table stats exist but column stats do not.
  • A map-side Group By (partial, hash mode) feeds a reducer-side Group By (mergepartial): aggregation in two phases.
L3> Every EXPLAIN form we used
  • EXPLAIN ANALYZE runs the query: rows=estimate/actual. Our plan guessed 3 Gold customers (actual 517) and 25,000 orders on one day (actual 1,621).
  • EXPLAIN CBO [COST] shows the Calcite logical plan the cost-based optimiser chose, with its own row estimates and costs.
  • SET hive.explain.user=false switches to the classic stage view with full Statistics lines and Group By modes.
  • EXPLAIN VECTORIZATION [ONLY] SUMMARY|DETAIL, EXPLAIN DEPENDENCY, EXPLAIN LOCKS, EXPLAIN EXTENDED, EXPLAIN AST answer narrower questions.
/LEVELS EXAM> “How do you analyse a slow Hive query?” Start with EXPLAIN: read vertices and edges, find the join type (map join vs shuffle join), compare estimated rows with reality (EXPLAIN ANALYZE), check statistics (Col:NONE is a warning), partition pruning (EXPLAIN DEPENDENCY) and vectorisation. Then change one thing and compare.

4 Step by step

One query, every kind of EXPLAIN

All outputs are real, from the Hive 4.2.1 lab (database tiffingo). Long lines are shortened with “…”.

  1. Step 1 · The query and its answer

    SELECT c.city, COUNT(*) AS n, SUM(o.amount) AS rev
FROM orders o JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date = '2026-10-05' AND c.plan = 'Gold'
GROUP BY c.city ORDER BY rev DESC LIMIT 3;
    +------------+------+-----------+ | c.city | n | rev | +------------+------+-----------+ | Bengaluru | 100 | 26600.00 | | Mumbai | 71 | 19270.00 | | Pune | 60 | 18090.00 | +------------+------+-----------+
    Bengaluru leads with 100 Gold orders that day. We will now see how Hive produced these three rows.

  2. Step 2 · Plain EXPLAIN: the DAG

    EXPLAIN SELECT c.city, COUNT(*) AS n, SUM(o.amount) AS rev … LIMIT 3;
    Plan optimized by CBO. Vertex dependency in root stage Map 1 <- Map 4 (BROADCAST_EDGE) Reducer 2 <- Map 1 (SIMPLE_EDGE) Reducer 3 <- Reducer 2 (SIMPLE_EDGE) Stage-0 Fetch Operator limit:3 …
    Three things before any operator: the plan was optimized by CBO; there are four vertices; and Map 1 <- Map 4 (BROADCAST_EDGE) means customers (Map 4) are broadcast to the tasks reading orders (Map 1): a map join. Reducer 2 groups by city after a shuffle, Reducer 3 sorts and keeps the top 3. The final Fetch Operator has limit:3.

5 See it happen

Reading a real plan

Left: real EXPLAIN output. Right: how to read it.

From SQL to a Tez DAG 5 steps
What you see
  1. The plan starts with the vertex dependencies: four Tez vertices.
  2. At the bottom, the scans and filters, with row estimates.
  3. The join, the two-phase aggregation and the top-3 limit.
  4. EXPLAIN ANALYZE shows estimates that are far from reality.
  5. EXPLAIN CBO shows the logical plan chosen by Calcite.
Behind the screen
  1. Map vertices read files; reducers receive shuffled rows; the broadcast edge copies a small input to every task.
  2. Data enters at the TableScans; filters are pushed as close to the scans as possible.
  3. The map join probes a hash table; partial aggregates shrink data before the shuffle.
  4. Estimates come from statistics; missing or uniform-assumption stats produce big errors.
  5. Hive parses SQL, Calcite optimises the logical plan, then Hive builds the physical Tez plan.

6 Real-world use

EXPLAIN at work

1. Performance investigations

Platform teams ask for the EXPLAIN output before looking at any slow-query complaint; most problems are visible in the plan.

Slow query→EXPLAIN→Root cause

2. Code review of pipelines

Plans of new ETL jobs are reviewed for pruning, join strategy and shuffle size before they reach production.

New job→plan review→Safe deploy

3. Upgrades and migrations

Before upgrading Hive, teams capture plans of critical queries on the old and new versions and compare them.

Old plans→diff→No surprises

4. Lineage and impact analysis

EXPLAIN DEPENDENCY output tells which tables and partitions a report reads, helping governance and change planning.

Report SQL→inputs list→Lineage

5. Planning concurrent writes

EXPLAIN LOCKS shows whether two ACID jobs would block each other, so they can be scheduled or partitioned apart.

Two jobs→lock check→No blocking
