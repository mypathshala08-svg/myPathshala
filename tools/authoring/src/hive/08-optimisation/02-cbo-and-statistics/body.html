1 The story

“Why does Hive think there are only 3 Gold customers?”

Before you start: read 8.1 EXPLAIN in depth; recall partitions (5.1) and the metastore (2.2).

In Lesson 8.1, EXPLAIN ANALYZE showed Kabir that Hive expected 3 Gold customers when there were 517. Riya wants to know where such numbers come from, and whether a wrong guess can really make a query slow.

R> Sir, Hive scans the table anyway. Why does it need to guess? A> Because it decides the plan before reading any data: join order, map join or shuffle join, number of reducers. For that it uses statistics stored in the metastore: row counts, sizes, and per column the number of distinct values, nulls, minimum and maximum. The cost-based optimiser (CBO, built on Apache Calcite) turns them into estimates for every operator. K> And our customers table had none? A> Only the file size. We will run ANALYZE TABLE, watch the estimates change, then do two experiments the tutorials skip: stale statistics that still say COMPLETE, and a join that changes strategy just because the statistics changed. All outputs are real, from Hive 4.2.1.
2 Definition

The cost-based optimiser and statistics

Formal definition (write this in exams)

Hive’s cost-based optimiser (CBO), enabled by hive.cbo.enable=true, uses Apache Calcite to rewrite a query’s logical plan and to choose join order and join algorithms by comparing estimated costs. The costs are derived from statistics kept in the Hive Metastore at table, partition and column level: row counts and sizes (basic statistics) and, per column, number of distinct values, nulls, minimum and maximum. Statistics are collected automatically when data is written through Hive (hive.stats.autogather, hive.stats.column.autogather) or explicitly with ANALYZE TABLE … COMPUTE STATISTICS [FOR COLUMNS], and can also answer some queries directly (hive.compute.query.using.stats).

In simple words

Before running a query, Hive estimates how many rows each step will produce, using facts about the data stored in the metastore. The optimiser picks the plan with the lowest estimated cost. If the facts are missing or old, the estimates and the plan can be badly wrong; ANALYZE TABLE refreshes them.

LEVELS> Statistics at three levels L1> A shopkeeper’s guess
  • Before packing for a trip, you guess how many bags you need. Hive does the same before running a query: it guesses how many rows each step will produce.
  • The guesses come from statistics: facts about each table saved in the metastore, like “50,000 rows” or “30 different dates”.
  • Good statistics → good plan. Missing or old statistics → Hive can pick a slow plan.
L2> What is stored and how it is used
  • Table / partition (basic) stats: numRows, numFiles, totalSize, rawDataSize. Seen with DESCRIBE FORMATTED or SHOW TBLPROPERTIES.
  • Column stats: distinct_count (NDV), num_nulls, min/max, avg_col_len/max_col_len, true/false counts. Seen with DESCRIBE FORMATTED t col.
  • Gathered automatically on INSERT (hive.stats.autogather, hive.stats.column.autogather) or by hand with ANALYZE TABLE … COMPUTE STATISTICS [FOR COLUMNS].
  • Selectivity rules of thumb: col = v → rows / NDV; ranges → interpolated between min and max; values are assumed evenly spread.
L3> What the lab showed
  • Tbl:COMPLETE means statistics exist, not that they are correct: after an INSERT with autogather off, Hive said COMPLETE with 100 rows for a 2,000-row table.
  • Statistics alone flipped a join: stale stats → map join; fresh stats → shuffle (merge) join, same SQL, same threshold.
  • Even complete stats mislead: equality on our DATE column was estimated at half the table (25,000 for 1,621), and skewed values (Pune) are under-estimated. A partition gave an exact 1,621.
/LEVELS EXAM> “What is CBO in Hive and why does it need statistics?” CBO (Calcite) chooses join order and join types by estimated cost; costs come from row counts and column statistics in the metastore. Collect them with ANALYZE TABLE … COMPUTE STATISTICS and … FOR COLUMNS, or automatically on INSERT. Check with DESCRIBE FORMATTED and in EXPLAIN (Tbl:/Col: COMPLETE, PARTIAL or NONE).

From a bad estimate to a different join

  2. Step 2 · No column statistics → a guess of 3

    DESCRIBE FORMATTED customers plan;
-- and from Lesson 8.1, EXPLAIN ANALYZE:
    +------------------+--------------------+ | column_property | value | +------------------+--------------------+ | col_name | plan | | data_type | string | | min | | | max | | | num_nulls | | | distinct_count | | | avg_col_len | | | max_col_len | | | num_trues | | | num_falses | | | bit_vector | | | comment | from deserializer | +------------------+--------------------+ Filter Operator [FIL_25] (rows=3/517 width=346) TableScan [TS_3] (rows=1413/2000 width=346) tiffingo@customers,c,Tbl:COMPLETE,Col:NONE,Output:["customer_id","city","plan"]

  3. Step 3 · ANALYZE TABLE

    ANALYZE TABLE customers COMPUTE STATISTICS;

    The first command counts rows; the second computes column statistics for every column. Now plan has 3 distinct values and 0 nulls, and COLUMN_STATS_ACCURATE lists every column as true.

    customers: 2000/2000 exact, Col:COMPLETE. Gold: 667/517 (2,000 / 3 distinct plans). Join: 8,338/427, group by: 8/8. Huge improvement, from 172× off to 1.3× off on Gold. But the date filter is still 25000/1621 although orders has full column statistics. Next step looks at that.

  5. Step 5 · Complete statistics, still wrong estimates

    -- estimates from EXPLAIN vs real COUNT(*) on orders (50,000 rows, Col:COMPLETE)
EXPLAIN SELECT COUNT(*) FROM orders_by_day WHERE order_date = '2026-10-05';   -- partitioned copy
    filter on orders (50,000 rows, column stats COMPLETE) estimated rows actual rows city = 'Pune' 6,250 7,930 customer_id = 1492 24 41 amount > 500 22,619 5,642 order_date = '2026-10-05' 25,000 1,621 TableScan [TS_0] (rows=1621 width=112) tiffingo@orders_by_day,orders_by_day,Tbl:COMPLETE,Col:COMPLETE,Output:["amount"]
    Equality on a normal column uses rows / NDV: city = 'Pune' → 50,000 / 8 = 6,250, but Pune really has 7,930 (data is skewed). amount > 500 interpolates between min and max assuming an even spread: 22,619 vs 5,642. Equality on our DATE column was estimated at half the table in Hive 4.2.1, while a range on the same column used min/max (> '2026-10-28' → 3,448). On the partitioned copy the estimate is exact, 1,621, because each partition has its own numRows.

  6. Step 6 · Stale statistics that say COMPLETE

    CREATE TABLE cust_stale STORED AS ORC AS SELECT * FROM customers WHERE customer_id <= 100;
SET hive.stats.autogather=false;
INSERT INTO cust_stale SELECT * FROM customers WHERE customer_id > 100;
SELECT COUNT(*) AS real_rows FROM cust_stale;
SHOW TBLPROPERTIES cust_stale;
EXPLAIN SELECT city, COUNT(*) FROM cust_stale WHERE plan = 'Gold' GROUP BY city;
    +------------+ | real_rows | +------------+ | 2000 | +------------+ +-------------------------+-------------+ | prpt_name | prpt_value | +-------------------------+-------------+ | EXTERNAL | TRUE | | TRANSLATED_TO_EXTERNAL | TRUE | | bucketing_version | 2 | | external.table.purge | TRUE | | numFiles | 2 | | numFilesErasureCoded | 0 | | numRows | 100 | | rawDataSize | 41900 | | totalSize | 11936 | | transient_lastDdlTime | 1793099659 | +-------------------------+-------------+ Filter Operator [FIL_9] (rows=33 width=180) TableScan [TS_0] (rows=100 width=180) tiffingo@cust_stale,cust_stale,Tbl:COMPLETE,Col:COMPLETE,Output:["city","plan"]
    The table really has 2,000 rows, but numRows still says 100, and EXPLAIN shows Tbl:COMPLETE,Col:COMPLETE with rows=100. Nothing warns you. After ANALYZE TABLE cust_stale COMPUTE STATISTICS and … FOR COLUMNS, the same EXPLAIN shows 2,000 and Gold 667. In real platforms this happens when files are copied in by Spark, DistCp or hdfs dfs -put, or autogather is switched off for speed.

  7. Step 7 · Statistics alone change the join

    SET hive.auto.convert.join.noconditionaltask.size=20000;   -- small, to show the effect
EXPLAIN SELECT c.city, SUM(o.amount) FROM orders o JOIN cust_stale2 c   -- stale: numRows 100
  ON o.customer_id = c.customer_id WHERE c.plan = 'Gold' GROUP BY c.city;
EXPLAIN … JOIN cust_stale c …                                            -- fresh: 2,000
    -- stale statistics Map 1 <- Map 3 (BROADCAST_EDGE) Reducer 2 <- Map 1 (SIMPLE_EDGE) <-Map 1 [SIMPLE_EDGE] vectorized Map Join Operator [MAPJOIN_26] (rows=802 width=203) <-Map 3 [BROADCAST_EDGE] vectorized Filter Operator [FIL_21] (rows=33 width=184) TableScan [TS_3] (rows=100 width=184) <-Select Operator [SEL_25] (rows=50000 width=116) -- fresh statistics Reducer 2 <- Map 1 (SIMPLE_EDGE), Map 4 (SIMPLE_EDGE) Reducer 3 <- Reducer 2 (SIMPLE_EDGE) <-Reducer 2 [SIMPLE_EDGE] Merge Join Operator [MERGEJOIN_19] (rows=16675 width=203) <-Map 1 [SIMPLE_EDGE] vectorized <-Map 4 [SIMPLE_EDGE] vectorized Filter Operator [FIL_23] (rows=667 width=184) TableScan [TS_3] (rows=2000 width=184)
    Same SQL, same data, same threshold. With stale statistics Hive believes the Gold side is 33 rows (about 3 KB) and broadcasts it: map join. With fresh statistics it is 667 rows (about 63 KB), above our 20,000-byte limit, so Hive picks a shuffle (merge) join with an extra reducer stage. At production scale the dangerous case is the first: a table believed small but really huge gets broadcast and tasks run out of memory.

  8. Step 8 · Answers straight from statistics

    EXPLAIN SELECT COUNT(*) FROM orders;        -- external table
EXPLAIN SELECT COUNT(*) FROM orders_acid;   -- managed ACID table
SELECT COUNT(*) FROM orders_acid;
    Plan optimized by CBO. Vertex dependency in root stage Reducer 2 <- Map 1 (CUSTOM_SIMPLE_EDGE) Stage-0 … Plan optimized by CBO. Stage-0 Fetch Operator limit:1 +-------+ | _c0 | +-------+ | 4886 | +-------+ INFO : Completed executing command(…); Time taken: 0.0 seconds
    With hive.compute.query.using.stats=true, COUNT(*) on the ACID table is answered from the metastore: the plan is only a Fetch Operator and the query took 0.0 seconds of execution (4,886 rows). On the external orders table Hive still runs a Map and a Reducer, because files of an external table can change without Hive knowing. Hive trusts statistics for answers only where it controls every write.

From metastore numbers to a plan 5 steps
What you see
  1. customers has no row count and no column statistics.
  2. The plan guessed 3 Gold customers; there are 517.
  3. ANALYZE TABLE computes basic and column statistics.
  4. Estimates are now close; the date filter is still far off.
  5. Stale statistics made Hive broadcast; fresh ones made it shuffle.
Behind the screen
  1. The optimiser reads statistics from the metastore before any data is read.
  2. With nothing to go on, Hive applies default selectivities.
  3. Statistics are stored in the metastore and reused by every query.
  4. Equality filters use rows divided by distinct values, assuming an even spread.
  5. Join type and reducer counts follow from the estimated sizes.

6 Real-world use

Statistics at work

1. ETL pipelines

Load jobs end with ANALYZE on the new partition, so downstream reports are planned with current numbers.

Load→ANALYZE→Fresh plans

2. Stable join plans

Accurate sizes keep map joins for truly small tables and shuffle joins for big ones, avoiding memory failures.

Stats→join choice→No OOM

3. Instant metadata answers

On managed (ACID) tables, COUNT(*), MIN and MAX can be answered from statistics without running a job.

Query→stats→Instant

4. Cheap data profiling

Column statistics (nulls, distinct counts, min and max) give data quality teams a quick profile of every column.

Column stats→profile→Quality checks

5. Platform health checks

Platform teams flag tables whose numRows is missing or far from reality before users notice slow queries.

Metastore→check→Alerts
