1 The story

“The plan is right. Why is it still slow?”

Before you start: how a query becomes a Tez job (1.4), ORC (6.2) and reading plans (8.1).

Kabir has a good plan now: right statistics, right join. But the platform team says many queries still waste CPU, start too few or too many tasks, and wait for containers. Arjun Sir builds a 5-million-row copy of orders to measure what the execution engine itself can do.

R> Sir, what does “vectorized” in the plan actually change? A> Instead of pushing one row at a time through every operator, Hive pushes a batch of 1,024 rows stored column by column. Each operator runs a tight loop over arrays, which modern CPUs love. On our 5-million-row table it made the map work about 6× faster. K> And Tez tuning? I see dozens of settings online. A> Most of them control three things: how many map tasks (split grouping), how many reducers (bytes per reducer, auto parallelism), and how much memory each container gets. We will change each and count the tasks. And LLAP, the long-lived daemons with a cache, we will try to switch on and see exactly what it needs. All outputs are real, from Hive 4.2.1.
2 Definition

Vectorisation, Tez tuning and LLAP

Formal definition (write this in exams)

Vectorised query execution processes rows in batches (VectorizedRowBatch, 1,024 rows by default) stored as column vectors, so operators such as scans, filters, expressions and aggregations run as loops over primitive arrays instead of per-row object calls; it is enabled with hive.vectorized.execution.enabled and works best with ORC and Parquet input. Tez tuning adjusts how the DAG is executed: input split grouping (number of map tasks), reducer parallelism, container memory and container reuse. LLAP (Live Long and Process) is an optional layer of persistent daemons that execute query fragments with an in-memory columnar cache and fast start-up, coordinated by Tez and discovered through ZooKeeper.

In simple words

Vectorisation makes each task faster by handling 1,024 rows at a time. Tez tuning decides how many tasks run and how much memory they get. LLAP keeps worker processes running all the time, with a data cache, so interactive queries start and finish quickly.

LEVELS> Execution speed at three levels L1> Carrying bricks
  • Carrying one brick at a time is slow; carrying a stack of 1,024 bricks at once is much faster. Vectorisation does that with rows.
  • Tez decides how many workers (tasks) to use. Too few: slow. Too many: time wasted starting them.
  • LLAP keeps workers always running and remembers recent data, so short queries start instantly.
L2> The settings behind them
  • hive.vectorized.execution.enabled (map) and hive.vectorized.execution.reduce.enabled: process VectorizedRowBatches of 1,024 rows. Best with ORC and Parquet; check EXPLAIN VECTORIZATION.
  • Map tasks: Tez groups input splits between tez.grouping.min-size and tez.grouping.max-size.
  • Reducers: estimated shuffle bytes / hive.exec.reducers.bytes.per.reducer (256 MB default), capped by hive.exec.reducers.max (1,009); hive.tez.auto.reducer.parallelism lowers the count at run time; mapreduce.job.reduces forces it.
  • Memory: hive.tez.container.size and hive.tez.java.opts (heap about 80% of the container).
L3> What the lab showed
  • Vectorised vs row mode on 5,000,000 rows: Map 1 about 300–400 ms vs 2,250–2,400 ms; whole query about 1.0 s vs 3.0 s, three runs each.
  • A UDF without a vector version still ran through the VectorUDFAdaptor (2.1 s); forbidding the adaptor made the map side non-vectorised (3.4 s) with an explicit notVectorizedReason.
  • Split grouping changed Map 1 from 1 to 8 tasks; bytes-per-reducer changed Reducer 2 from 1 to 8, auto parallelism cut it to 2. LLAP mode failed without a ZooKeeper registry.
/LEVELS EXAM> “What is vectorisation in Hive?” Processing 1,024 rows at a time as column vectors instead of row by row, which cuts per-row overhead and uses the CPU efficiently. Enable with hive.vectorized.execution.enabled=true, best with ORC/Parquet, verify with EXPLAIN VECTORIZATION (look for Execution mode: vectorized and notVectorizedReason).

4 Step by step

Measuring the execution engine

All outputs are real, from the Hive 4.2.1 lab. Timings are HiveServer2’s “Completed executing … Time taken” and the Tez vertex summary.

  1. Step 1 · A bigger table to measure

    CREATE TABLE orders_big STORED AS ORC AS
SELECT o.order_id * 100 + r.n AS order_id, o.customer_id, o.city, o.amount, o.order_date, o.status
FROM orders o CROSS JOIN
  (SELECT pos AS n FROM (SELECT posexplode(split(space(99), ' ')) AS (pos, x)) t) r;
SELECT COUNT(*) FROM orders_big;
    +----------+ | _c0 | +----------+ | 5000000 | +----------+
    50,000 orders × 100 copies = 5,000,000 rows in one ORC file of about 10 MB (totalSize 10,195,843 bytes). space(99) gives 100 empty strings to explode: a handy way to generate rows in pure HiveQL.

  2. Step 2 · Is the query vectorised?

    EXPLAIN VECTORIZATION SUMMARY
SELECT city, status, COUNT(*) AS n, SUM(amount) AS rev, AVG(amount) AS avg_amt
FROM orders_big WHERE amount > 100 GROUP BY city, status;

  3. Step 3 · Vectorised vs row mode, three runs each

    SET hive.vectorized.execution.enabled=true;    -- then false
SET hive.tez.exec.print.summary=true;
SELECT city, status, COUNT(*) AS n, SUM(amount) AS rev, AVG(amount) AS avg_amt
FROM orders_big WHERE amount > 100 GROUP BY city, status;
    run 1 vectorized=true query 0.973 seconds Map 1 302.00 ms run 1 vectorized=false query 3.035 seconds Map 1 2360.00 ms run 2 vectorized=true query 1.081 seconds Map 1 404.00 ms run 2 vectorized=false query 3.101 seconds Map 1 2400.00 ms run 3 vectorized=true query 1.01 seconds Map 1 344.00 ms run 3 vectorized=false query 2.938 seconds Map 1 2254.00 ms
    Map 1 (scan, filter, partial aggregation of 5,000,000 rows) took 302–404 ms vectorised and 2,254–2,400 ms in row mode: about 6–7×. The whole query went from about 3.0 s to 1.0 s; the rest is fixed overhead (planning, starting tasks). Same result, 24 groups, in every run.

  4. Step 4 · A UDF without a vector version

    SET hive.vectorized.adaptor.usage.mode;          -- all
EXPLAIN VECTORIZATION EXPRESSION SELECT md5(city) AS x, COUNT(*) FROM orders_big GROUP BY md5(city);

SET hive.vectorized.adaptor.usage.mode=none;
EXPLAIN VECTORIZATION ONLY SUMMARY SELECT md5(city) AS x, COUNT(*) FROM orders_big GROUP BY md5(city);
-- and timing both
    hive.vectorized.adaptor.usage.mode=all selectExpressions: VectorUDFAdaptor(md5(city)) -> 8:string usesVectorUDFAdaptor: true usesVectorUDFAdaptor: false -- adaptor.usage.mode=none notVectorizedReason: Select expression for SELECT operator: UDF GenericUDFBridge ==> md5 (Column[city]) not supported vectorized: false vectorized: true run 1 adaptor.usage.mode=all 2.081 seconds run 1 adaptor.usage.mode=none 3.47 seconds run 2 adaptor.usage.mode=all 2.21 seconds run 2 adaptor.usage.mode=none 3.424 seconds
    md5 has no vector implementation, so Hive wrapped it: VectorUDFAdaptor(md5(city)) converts each batch to rows for that one expression and keeps everything else vectorised (about 2.1 s). With the adaptor forbidden, EXPLAIN says exactly why the map side fell back: notVectorizedReason: … UDF GenericUDFBridge ==> md5 … not supported, and the query took about 3.4 s. Custom Java UDFs are the most common reason for row mode in real plans.

  5. Step 5 · The Tez knobs and their defaults

    SET hive.tez.container.size; SET hive.exec.reducers.bytes.per.reducer; SET hive.exec.reducers.max;
SET hive.tez.auto.reducer.parallelism; SET mapreduce.job.reduces; SET hive.execution.mode;
SET hive.llap.execution.mode; SET hive.fetch.task.conversion; SET hive.fetch.task.conversion.threshold;
SET hive.server2.tez.initialize.default.sessions;
    hive.tez.container.size=-1 hive.exec.reducers.bytes.per.reducer=256000000 hive.exec.reducers.max=1009 hive.tez.auto.reducer.parallelism=false mapreduce.job.reduces=-1 hive.execution.mode=container hive.llap.execution.mode=all hive.fetch.task.conversion=more hive.fetch.task.conversion.threshold=209715200 hive.server2.tez.initialize.default.sessions=false
    Container size -1 means Hive takes the MapReduce map memory setting. One reducer per 256 MB of estimated shuffle data, at most 1,009. Auto reducer parallelism is off. Execution mode is container, not llap. Simple queries up to 200 MB of input can run as a fetch task.

  6. Step 6 · Changing the number of tasks

    -- orders_big_txt: the same 5,000,000 rows as one 246 MB text file
SELECT customer_id, COUNT(*) AS n, SUM(amount) FROM orders_big_txt GROUP BY customer_id;
-- run once per setting below, with hive.tez.exec.print.summary=true
    -- defaults Map 1 tasks: 1 Reducer 2 tasks: 1 query time: 3.394 seconds SET tez.grouping.max-size=16777216; SET tez.grouping.min-size=8388608; Map 1 tasks: 8 Reducer 2 tasks: 1 query time: 4.824 seconds SET hive.exec.reducers.bytes.per.reducer=100000; Map 1 tasks: 1 Reducer 2 tasks: 8 query time: 4.82 seconds SET hive.exec.reducers.bytes.per.reducer=100000; SET hive.tez.auto.reducer.parallelism=true; Map 1 tasks: 1 Reducer 2 tasks: 2 query time: 3.714 seconds SET mapreduce.job.reduces=6; Map 1 tasks: 1 Reducer 2 tasks: 6 query time: 4.483 seconds
    The 246 MB file has 8 input splits of up to 32 MB. By default Tez grouped them into 1 map task; with tez.grouping.max-size at 16 MB no two splits could be grouped, so 8 map tasks ran (grouping merges splits, it never cuts them). Bytes per reducer at 100,000 gave 8 reducers (the estimated shuffle is about 765 KB: 6,171 rows × 124 bytes). With auto reducer parallelism on as well, Tez lowered the reducer count at run time after seeing the real data, ending with 2. mapreduce.job.reduces=6 forced 6. On one machine every extra task cost time; on a cluster it buys parallelism.

  7. Step 7 · No job at all: fetch tasks

    EXPLAIN SELECT order_id, city, amount FROM orders_big WHERE city = 'Pune' LIMIT 5;
SET hive.fetch.task.conversion=none;
EXPLAIN SELECT order_id, city, amount FROM orders_big WHERE city = 'Pune' LIMIT 5;
    Plan optimized by CBO. Stage-0 Fetch Operator limit:5 Select Operator [SEL_2] Output:["_col0","_col1","_col2"] Limit [LIM_3] Number of rows:5 Filter Operator [FIL_5] predicate:(city = 'Pune') TableScan [TS_0] Output:["order_id","city","amount"] -- with conversion=none Stage-0 Fetch Operator Stage-1 Map 1 vectorized
    With hive.fetch.task.conversion=more the whole query is a Fetch Operator: HiveServer2 reads the file itself and stops after 5 rows, with no Tez DAG. With none the same query gets Stage-1 and a vectorised Map 1. This is why SELECT … LIMIT 10 feels instant even on large tables; aggregations always need a job.

    SET hive.execution.mode=llap;
SELECT COUNT(*) FROM orders_big WHERE amount > 100;

How tasks run 5 steps
What you see
  1. EXPLAIN VECTORIZATION: both vertices run vectorised.
  2. Vectorised map work took 300–400 ms instead of about 2,300 ms.
  3. md5 had no vector form: the adaptor wrapped it, or the map fell back.
  4. Grouping and reducer settings changed the task counts.
  5. LLAP mode failed: no ZooKeeper registry in the lab.
Behind the screen
  1. Row mode calls every operator once per row.
  2. Vectorised operators loop over column arrays of 1,024 values.
  3. The adaptor turns one batch into rows for a single expression.
  4. Map tasks come from grouped input splits; reducers from estimated shuffle bytes.
  5. LLAP fragments run in daemons the Tez AM discovers via ZooKeeper.

6 Real-world use

Execution tuning at work

1. CPU savings on ETL

Keeping heavy ETL on ORC/Parquet with vectorisation cuts CPU hours, which on cloud clusters is directly money.

ORC + vector→fewer CPU s→Lower bill

2. Right-sized parallelism

Auto reducer parallelism and split grouping keep tasks large enough to be efficient and many enough to finish on time.

Estimates→task counts→On-time SLAs

3. Interactive analytics

Distributions such as Cloudera Data Warehouse offer LLAP-based virtual warehouses for BI tools.

BI tool→LLAP→Seconds

4. Fixing container failures

Tasks killed for exceeding memory are fixed with container size and heap settings, or by reducing map-join sizes.

Killed task→memory tuning→Stable job

5. Fast data previews

Fetch-task conversion lets analysts preview tables with SELECT … LIMIT instantly, without using cluster resources.

Preview→fetch task→Instant
