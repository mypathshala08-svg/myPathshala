1 The story

“Give us Parquet, and make it smaller”

Before you start: read Lessons 6.1 and 6.2.

TiffinGo’s data science team works in Spark and asks for the orders table in Parquet. Kabir runs one CTAS and sends it. The next day the platform team complains about storage: the Parquet copy is 2.5 times larger than the ORC table. Kabir checks the file and finds it was written with no compression at all.

K> Sir, ORC compressed itself. Why didn’t Parquet? A> Each format has its own codec setting. ORC defaults to ZLIB; in our Hive 4.2.1 the Parquet writer defaulted to UNCOMPRESSED. You set parquet.compression on the table or the session. The real question is which codec: Snappy and LZ4 are fast, ZLIB, GZIP and ZSTD are small, and bzip2 is very small and very slow. R> And is Parquet different from ORC inside? A> Same idea, different details: row groups instead of stripes, pages inside column chunks, statistics in the footer. Today we open a real Parquet file, measure five codecs on our data, and find three things that differ from ORC in Hive 4.2.1: no compression by default, INT96 timestamps, and a range filter that ORC skipped but Parquet did not. All outputs are real.
2 Definition

Parquet and compression codecs

Formal definition (write this in exams)

Apache Parquet is an open, self-describing columnar file format. A file is divided into row groups; each row group contains one column chunk per column, made of pages that are encoded (dictionary, plain, run-length/bit-packed) and compressed with a codec. The footer holds the schema and per-column-chunk statistics (min, max, null count) used for predicate pushdown. A compression codec is an algorithm applied to blocks of data: Snappy and LZ4 favour speed, GZIP/ZLIB and ZSTD favour compression ratio, and BZip2 gives the highest ratio at much lower speed. Codecs applied inside container formats keep files splittable.

In simple words

Parquet is a columnar format like ORC, used by almost every big data tool. Inside both formats you choose a compression codec: fast ones (Snappy, LZ4) for data you read all the time, small ones (ZSTD, GZIP) for data you store long. In Hive you set it per table.

LEVELS> Parquet and codecs at three levels L1> Zip files for columns
  • Parquet, like ORC, stores data column by column and keeps a summary of each column so tools can skip data.
  • A codec is the zip method used inside the file. Faster codecs save less space; stronger codecs save more space but cost more CPU.
  • Parquet is the most widely shared format: Spark, Trino, Impala, Athena, BigQuery and pandas all read it.
L2> Parquet’s structure and Hive settings
  • File = row groups + footer. A row group (target size parquet.block.size, typically 128 MB) holds a column chunk per column; each chunk is split into pages (about 1 MB). The footer (schema, row group list, statistics) ends with the magic bytes PAR1, which also start the file.
  • Encodings: dictionary for repeated values, PLAIN otherwise, plus RLE / bit-packing for levels and dictionary ids.
  • Codec per table: TBLPROPERTIES ('parquet.compression'='SNAPPY') (UNCOMPRESSED, SNAPPY, GZIP, ZSTD, LZ4…). ORC: 'orc.compress'.
  • Hive matches Parquet columns by name by default, so files written by other engines with a different column order still read correctly.
L3> What Hive 4.2.1 did in our lab
  • CTAS STORED AS PARQUET wrote UNCOMPRESSED column chunks (1.09 MB); ORC used ZLIB (0.44 MB).
  • Hive wrote timestamps as legacy INT96 (hive.parquet.write.int64.timestamp=false); with the setting on, INT64 microseconds, which newer readers prefer.
  • The Parquet writer stored sorted order_id PLAIN: 200 KB, against 161 bytes in ORC’s RLE.
  • amount > 900 (above the file max) skipped the whole ORC file, but the Parquet table read all 50,000 rows. On a Parquet file sorted by customer with small row groups, a lookup read 1,458 rows: Parquet row-group statistics work, but test each data type.
  • On 50,000 rows every format answered a GROUP BY in about 3.1–3.4 s: fixed job overhead hides format differences on small data. Benchmark on realistic sizes.
/LEVELS EXAM> “ORC vs Parquet” and “Which compression codec would you choose?” are frequent. For the codec, answer with the trade-off: Snappy/LZ4 for hot, frequently read data (fast); ZSTD or ZLIB/GZIP for warm and cold data (smaller); bzip2 only for archives of text. Always compress inside a container format so files stay splittable.

4 Step by step

Parquet inside out, then five codecs

All outputs are real, from the Hive 4.2.1 lab (database tiffingo). Parquet metadata was read with Python’s pyarrow library.

  1. Step 1 · A Parquet table, and its default codec

    CREATE TABLE f_parquet STORED AS PARQUET AS SELECT * FROM orders;
$ ls -l …/f_parquet/       # then read the footer with pyarrow
    f_parquet/000000_0 1,093,857 bytes starts and ends with PAR1 created_by: parquet-mr version 1.15.2 (build 859eac16…) num_rows: 50000 num_row_groups: 1 column order_id: compression: UNCOMPRESSED encodings: PLAIN, RLE, BIT_PACKED statistics: min 100001 max 150000 null_count 0
    Hive 4.2.1 uses the parquet-mr (Java) writer and, unless you set parquet.compression, writes uncompressed pages. Statistics are still written, per column chunk. Always set the codec explicitly for Parquet tables.

  2. Step 2 · Inside: encodings and sizes per column

    # column-chunk metadata of a SNAPPY Parquet copy (c_pq_snappy)
    created_by: parquet-mr version 1.15.2 num_rows: 50000 num_row_groups: 1 column physical type encodings compressed uncompressed order_id INT32 PLAIN, RLE, BIT_PACKED 200,134 200,110 customer_id INT32 PLAIN_DICTIONARY, RLE, … 77,008 76,986 restaurant_id INT32 PLAIN_DICTIONARY, RLE, … 44,488 44,466 city BYTE_ARRAY (String) PLAIN_DICTIONARY, RLE, … 19,085 19,067 order_ts INT96 PLAIN_DICTIONARY, RLE, … 267,267 446,305 order_date INT32 (Date) PLAIN_DICTIONARY, RLE, … 31,621 31,603 amount FIXED_LEN_BYTE_ARRAY(5) (Decimal 10,2) PLAIN 99,702 250,111 payment BYTE_ARRAY (String) PLAIN_DICTIONARY, RLE, … 12,800 12,783 status BYTE_ARRAY (String) PLAIN_DICTIONARY, RLE, … 7,883 9,959
    Low-cardinality columns use dictionary encoding, so Snappy finds little left to squeeze (compressed ≈ uncompressed). The sorted order_id is stored PLAIN: 200 KB, where ORC needed 161 bytes. Timestamps are the biggest column, written as 12-byte INT96 values.

  3. Step 3 · Same rows, five codecs, two formats

    CREATE TABLE c_orc_zstd  STORED AS ORC     TBLPROPERTIES ('orc.compress'='ZSTD')        AS SELECT * FROM orders;
CREATE TABLE c_pq_snappy STORED AS PARQUET TBLPROPERTIES ('parquet.compression'='SNAPPY') AS SELECT * FROM orders;
-- … one table per codec, then ls -l
    table format codec bytes c_orc_none ORC NONE 674,283 c_orc_snappy ORC SNAPPY 570,494 c_orc_lz4 ORC LZ4 572,490 f_orc ORC ZLIB (Hive default) 437,536 c_orc_zstd ORC ZSTD 436,490 f_parquet PARQUET UNCOMPRESSED (default) 1,093,857 c_pq_snappy PARQUET SNAPPY 762,424 c_pq_zstd PARQUET ZSTD 582,505 c_pq_gzip PARQUET GZIP 536,505
    For both formats ZSTD and ZLIB/GZIP give the smallest files; Snappy and LZ4 save less. ORC is smaller than Parquet with every codec on this data, mainly because of its integer encodings. ORC with no compression at all (674 KB) is only a little bigger than Parquet with ZSTD (583 KB): encoding matters as much as the codec.

  4. Step 4 · Speed: what each codec costs

    # compress / decompress the 3.7 MB text file of 50,000 orders with each codec
# (cramjam library, best of 5 runs, one CPU core)
    codec compressed bytes ratio compress MB/s decompress MB/s snappy 1,232,657 3.0x 655 1,385 lz4 1,184,237 3.2x 670 2,593 zstd-3 739,460 5.1x 303 1,162 gzip-6 712,143 5.2x 40 622 bzip2-9 468,562 8.0x 18 38 (input: the 3,735,865-byte text file of 50,000 orders; best of 5 runs, one CPU core of our cloud machine)
    The trade-off in numbers: Snappy and LZ4 compress about 16 times faster than gzip, and LZ4 decompresses fastest. ZSTD gets gzip’s ratio while decompressing about twice as fast. bzip2 has the best ratio but decompresses at 38 MB/s, roughly 36 times slower than Snappy. Your hardware gives different absolute numbers; the order stays the same.

  5. Step 5 · Statistics-based skipping: Parquet vs ORC

    SET hive.tez.exec.print.summary=true;
SELECT COUNT(*) AS n FROM c_pq_snappy WHERE amount > 900;          -- ORC: 0 splits
SELECT COUNT(*) AS n FROM c_pq_snappy WHERE customer_id = 1492;

SET parquet.block.size=100000;    -- small row groups, for the demo only
CREATE TABLE pq_sorted STORED AS PARQUET TBLPROPERTIES ('parquet.compression'='SNAPPY')
  AS SELECT * FROM orders ORDER BY customer_id;
SELECT COUNT(*) AS n FROM pq_sorted WHERE customer_id = 1492;
    SELECT COUNT(*) AS n FROM c_pq_snappy WHERE amount > 900; result 0 · RECORDS_IN 50000 · RAW_INPUT_SPLITS 1 SELECT COUNT(*) AS n FROM c_pq_snappy WHERE customer_id = 1492; result 41 · RECORDS_IN 50000 · RAW_INPUT_SPLITS 1 SELECT COUNT(*) AS n FROM pq_sorted WHERE customer_id = 1492; result 41 · RECORDS_IN 1458 · RAW_INPUT_SPLITS 1 (pq_sorted: 35 row groups of about 1,460 rows; first ones: customer 1–57, 57–114, 114–173 …)
    On the decimal amount filter Hive read every Parquet row, while the same filter skipped the whole ORC file (6.2). Row-group statistics did work on a sorted integer column: 1,458 rows read instead of 50,000. Lesson: Parquet skipping depends on the column type and the reader version, so check counters for your important filters.

  6. Step 6 · Files from another engine: Parquet reads by name

    -- written by Python/pyarrow, not Hive:
--   part-v1.parquet (snappy): customer_id, name, city
--   part-v2.parquet (zstd):   customer_id, plan, city, name   (new column, new order)
CREATE EXTERNAL TABLE cust_pq (customer_id INT, name STRING, plan STRING, city STRING)
STORED AS PARQUET LOCATION 'file:///data/tiffingo/pq_ext';
SELECT * FROM cust_pq ORDER BY customer_id;
    +----------------------+---------------+---------------+---------------+ | cust_pq.customer_id | cust_pq.name | cust_pq.plan | cust_pq.city | +----------------------+---------------+---------------+---------------+ | 1 | Aarav Desai | NULL | Bengaluru | | 2 | Ananya Iyer | NULL | Mumbai | | 3 | Arjun Nair | NULL | Mumbai | | 4 | Diya Patil | Gold | Pune | | 5 | Ishaan Khan | Basic | Thane | +----------------------+---------------+---------------+---------------+
    Hive matched Parquet columns by name, so the different column order did not matter, and two codecs in the same table are fine because each file records its own. A column missing from old files came back as NULL (Parquet has no defaults, unlike Avro in 6.1).

  7. Step 7 · Timestamps: INT96 vs INT64

    SET hive.parquet.write.int64.timestamp;          -- false
SET hive.parquet.write.int64.timestamp=true;
CREATE TABLE pq_ts64 STORED AS PARQUET AS
  SELECT order_id, order_ts FROM orders WHERE order_id < 100004;
SELECT * FROM pq_ts64;
$ pyarrow schema of pq_ts64
    +-------------------+------------------------+ | pq_ts64.order_id | pq_ts64.order_ts | +-------------------+------------------------+ | 100001 | 2026-10-29 20:49:00.0 | | 100002 | 2026-10-17 20:25:00.0 | | 100003 | 2026-10-20 09:08:00.0 | +-------------------+------------------------+ optional int64 order_ts (Timestamp(isAdjustedToUTC=false, timeUnit=microseconds)) (default tables: optional int96 order_ts)
    INT96 is a deprecated encoding that some newer tools read differently or not at all. With the setting on, Hive writes standard INT64 microsecond timestamps marked as local time (not UTC). When Parquet tables are shared with Spark or Trino, agree on the timestamp encoding and time zone (Lesson 4.1).

  8. Step 8 · Does the format change query time on small data?

    SELECT city, SUM(amount) FROM <table> GROUP BY city;   -- each table, 5 runs
    f_text TEXTFILE 3.27 s f_avro AVRO 3.43 s f_orc ORC ZLIB 3.13 s c_orc_snappy ORC SNAPPY 3.21 s c_pq_snappy PARQUET SNAPPY 3.17 s c_pq_gzip PARQUET GZIP 3.31 s
    All within 0.3 s of each other. On 50,000 rows, starting the job costs far more than reading 0.4–3.7 MB. Format and codec differences show up when tables are gigabytes or larger, where bytes read dominate. Benchmark with realistic volumes before deciding, and use counters (rows and bytes read) rather than stopwatch time on toy data.

Behind the screen
  1. A Parquet file is row groups of column chunks and pages, with the footer at the end.
  2. Encodings shrink data before the codec; PLAIN columns rely on the codec alone.
  3. Each codec trades CPU for space differently; encodings decide the rest.
  4. Fast codecs suit hot data; strong codecs suit data that is stored long and read rarely.
  5. Readers compare filters with each row group’s min and max, where the type supports it.

6 Real-world use

Parquet and codecs at work

1. The shared format of the lake

Cloud data lakes keep most curated tables in Parquet so that Spark jobs, SQL engines, notebooks and BI tools all read the same files.

Hive / Spark write→Parquet→Every engine reads

2. ZSTD as the new default

Many platforms have moved from Snappy or GZIP to ZSTD, because it gives gzip-like size with much faster reads.

Old codec→rewrite with ZSTD→Smaller, fast

3. Table formats on Parquet

Apache Iceberg and Delta Lake usually store their data files as Parquet and add a metadata layer for snapshots and updates (Module 7).

Parquet files→table metadata→Lakehouse tables

4. Handing data to data scientists

A Parquet extract with a few columns opens directly in pandas or Polars, typed and compressed, unlike a CSV dump.

Hive query→Parquet extract→Notebook

5. Storage and scan costs

On cloud engines that charge per byte scanned, columnar formats plus a good codec reduce both the storage bill and the query bill.

Raw data→columnar + codec→Lower bills
