1 The story

“The table is ORC. Why does a lookup still read everything?”

Before you start: read Lesson 6.1 (formats) and partition pruning (5.1).

Every few minutes TiffinGo’s support tool asks Hive for one customer’s orders. The table is already ORC, the format everyone recommends, yet Hive’s counters show it reading all 50,000 rows to return 41. Kabir wants to understand what is inside an ORC file and how Hive decides what it can skip.

K> Sir, I thought ORC was supposed to be fast. It reads every row for one customer! A> ORC is fast at skipping, but it can only skip what its statistics rule out. It stores min and max for every column of every 10,000 rows. Our orders are in time order, so every group of 10,000 rows contains customers from 1 to 2000, and nothing can be ruled out. R> So we sort the data by customer? A> That is one answer; a bloom filter is another. Today we open a real ORC file with hive --orcfiledump, read its stripes, statistics, encodings and indexes, and then measure exactly how many rows Hive reads with each trick. All outputs are real, from Hive 4.2.1.
2 Definition

ORC (Optimized Row Columnar)

Formal definition (write this in exams)

ORC is a self-describing, typed, columnar file format for Hadoop workloads. An ORC file consists of stripes of rows, each containing an index section (row-group statistics and stream positions, optionally bloom filters), the column data streams and a stripe footer, followed by a file footer (schema, stripe locations, column statistics) and a postscript (compression parameters and footer length). Light-weight encodings (run-length, dictionary) and a general-purpose codec (ZLIB, Snappy, LZ4, ZSTD) reduce size. Column statistics at file, stripe and row-group level, plus optional bloom filters, allow predicate pushdown: skipping data that cannot match a query’s filter.

In simple words

ORC stores a table column by column, compresses each column, and writes a summary (min, max, count, sum) for every 10,000 rows. When your WHERE clause cannot match a summary, Hive skips those rows entirely.

Words you’ll meet in this lesson

StripeA big block of rows (default target 64 MB) with its own index and data.
Row groupEvery 10,000 rows of a stripe; the unit of skipping.
PostscriptThe last bytes of the file: how to read the footer. Ends with “ORC”.
Column statisticscount, hasNull, min, max, sum per column, per file / stripe / row group.
RLE v2Run-length encoding for integers: sorted ids shrink to a few bytes.
Dictionary encodingStore each distinct string once and refer to it by number.
Predicate pushdown (PPD)Passing WHERE conditions to the reader so it skips data.
Bloom filterA compact bit set that says “definitely not here” or “maybe here”.

LEVELS> ORC at three levels L1> A book with a contents page and an index
  • An ORC file stores each column separately and compresses it, so reading two columns does not touch the other seven.
  • It also writes a “contents page”: for each column, the smallest and largest value, the count and the sum, for the whole file and for every block of 10,000 rows.
  • When you ask for amount > 900 and the contents page says the maximum is 880, Hive skips the whole file without reading a single row.
L2> The structure of an ORC file
  • Stripes: large horizontal slices of rows (default target 64 MB). Each stripe has an index section, a data section (one or more streams per column) and a stripe footer.
  • Row groups: every 10,000 rows (orc.row.index.stride) the row index records min/max/count/sum per column and positions to jump to.
  • File footer (schema, stripe list, file statistics) and postscript (compression, footer length, ends with “ORC”) sit at the end, so a reader starts from the last bytes.
  • Encodings: integers use run-length encoding v2 (sorted ids compress to almost nothing); low-cardinality strings use a dictionary.
  • Predicate pushdown: with hive.optimize.index.filter=true (default) Hive passes WHERE conditions to the ORC reader, which skips files, stripes and row groups.
L3> What helps skipping, measured in our lab
  • Statistics only help when values are clustered. Unsorted customer_id: every row group has min 1 max 2000 → 50,000 rows read. Sorted: 10,000.
  • Bloom filters (orc.bloom.filter.columns) answer “is this value possibly here?” per row group. With 1,000-row groups they cut a lookup from 50,000 to 30,000 rows, and grew the index from 890 bytes to 65,439 bytes.
  • A smaller orc.row.index.stride alone did nothing for an unsorted column.
  • amount > 900 was eliminated before any task ran (0 splits): split generation read the file statistics.
  • ORC is also the format for Hive ACID tables (Module 7) and enables vectorised reading in batches of rows.
/LEVELS EXAM> “Explain the ORC file structure” is a classic. Draw stripes (index data, row data, stripe footer), then the file footer and postscript. Mention the three levels of statistics (file, stripe, row group of 10,000 rows), lightweight encodings plus compression, predicate pushdown and bloom filters, and that ORC is required for Hive ACID tables.

4 Step by step

Open an ORC file, then make Hive skip

All outputs are real, from the Hive 4.2.1 lab (database tiffingo). f_orc is the 50,000 orders written with CTAS in Lesson 6.1.

  1. Step 1 · Look inside the file

    hive --orcfiledump /opt/hive/data/warehouse/tiffingo.db/f_orc/000000_0
    Structure for /opt/hive/data/warehouse/tiffingo.db/f_orc/000000_0 File Version: 0.12 with ORC_14 by ORC Java 2.1.2 Rows: 50000 Compression: ZLIB Compression size: 262144 Calendar: Julian/Gregorian Type: struct<order_id:int,customer_id:int,restaurant_id:int,city:string,order_ts:timestamp,order_date:date,amount:decimal(10,2),payment:string,status:string>

  3. Step 3 · Stripes and encodings

    # … same dump, Stripes section
    Stripe: offset: 3 data: 435805 rows: 50000 tail: 171 index: 890 … Encoding column 0: DIRECT Encoding column 1: DIRECT_V2 Encoding column 2: DIRECT_V2 Encoding column 3: DIRECT_V2 Encoding column 4: DICTIONARY_V2[8] Encoding column 5: DIRECT_V2 Encoding column 6: DIRECT_V2 Encoding column 7: DIRECT_V2 Encoding column 8: DICTIONARY_V2[4] Encoding column 9: DICTIONARY_V2[3] … File length: 437536 bytes File raw data size: 24650000 bytes
    50,000 rows fit in one stripe (data 435,805 bytes, index 890 bytes). Integer columns use DIRECT_V2 (run-length encoding v2), and the strings city, payment and status use DICTIONARY_V2 with 8, 4 and 3 distinct values: each row stores a small number, not the text. Hive estimates the raw data at 24.6 MB; on disk it takes 0.44 MB.

  4. Step 4 · Row-group indexes: where skipping happens

    hive --orcfiledump --rowindex 2,7 …/f_orc/000000_0      # columns 2 = customer_id, 7 = amount
    Row group indices for column 2: Entry 0: count: 10000 hasNull: false min: 1 max: 2000 … Entry 1: count: 10000 hasNull: false min: 1 max: 2000 … … (entries 2–4 also 1 … 2000) Row group indices for column 7: Entry 0: count: 10000 hasNull: false min: 40 max: 840 … Entry 1: count: 10000 hasNull: false min: 40 max: 880 … Entry 2: count: 10000 hasNull: false min: 40 max: 840 … Entry 3: count: 10000 hasNull: false min: 40 max: 880 … Entry 4: count: 10000 hasNull: false min: 40 max: 880 …
    One entry per 10,000 rows. For customer_id every group covers the full range 1–2000, so no customer can ever be ruled out. For amount, groups 0 and 2 never go above 840: a filter amount > 870 can skip them.

  5. Step 5 · Predicate pushdown in action (and switched off)

    SET hive.tez.exec.print.summary=true;
SELECT COUNT(*) AS n FROM f_orc WHERE amount > 870;
SELECT COUNT(*) AS n FROM f_orc WHERE amount > 900;

SET hive.optimize.index.filter=false;    -- turn PPD off and repeat
    SELECT COUNT(*) AS n FROM f_orc WHERE amount > 870; result 4 · RECORDS_IN 30000 SELECT COUNT(*) AS n FROM f_orc WHERE amount > 900; result 0 · RECORDS_IN 0 · RAW_INPUT_SPLITS 0 (whole file skipped) SELECT COUNT(*) AS n FROM f_orc WHERE amount > 870; -- hive.optimize.index.filter=false result 4 · RECORDS_IN 50000 SELECT COUNT(*) AS n FROM f_orc WHERE amount > 900; -- hive.optimize.index.filter=false result 0 · RECORDS_IN 50000 · RAW_INPUT_SPLITS 1
    Exactly as the index predicted: 3 of 5 row groups read (30,000 rows) for 4 matching orders. For amount > 900 the file maximum is 880, so Hive created no splits at all. With pushdown off, both queries read all 50,000 rows and return the same answers, only slower.

  6. Step 6 · The customer lookup: unsorted vs sorted

    CREATE TABLE orders_sorted STORED AS ORC AS
  SELECT * FROM orders ORDER BY customer_id;

SELECT COUNT(*) AS n FROM f_orc         WHERE customer_id = 1492;
SELECT COUNT(*) AS n FROM orders_sorted WHERE customer_id = 1492;
    SELECT COUNT(*) AS n FROM f_orc WHERE customer_id = 1492; result 41 · RECORDS_IN 50000 SELECT COUNT(*) AS n FROM orders_sorted WHERE customer_id = 1492; result 41 · RECORDS_IN 10000
    Same 41 orders. Sorted, each row group covers a narrow range of customers (real min–max: 1–404, 404–800, 800–1205, 1205–1604, 1604–2000), so only the group whose min–max includes 1492 is read. Sorting is free at query time but costs a sort when writing, and you can sort by only one order, so pick the column your filters use most.

  7. Step 7 · Bloom filters for lookups on unsorted data

    CREATE TABLE orders_stride STORED AS ORC
  TBLPROPERTIES ('orc.row.index.stride'='1000') AS SELECT * FROM orders;
CREATE TABLE orders_bloom STORED AS ORC
  TBLPROPERTIES ('orc.bloom.filter.columns'='customer_id',
                 'orc.row.index.stride'='1000') AS SELECT * FROM orders;

SELECT COUNT(*) AS n FROM orders_stride WHERE customer_id = 1492;
SELECT COUNT(*) AS n FROM orders_bloom  WHERE customer_id = 1492;

$ hive --orcfiledump --rowindex 2 …/orders_bloom/000000_0
    SELECT COUNT(*) AS n FROM orders_stride WHERE customer_id = 1492; result 41 · RECORDS_IN 50000 SELECT COUNT(*) AS n FROM orders_bloom WHERE customer_id = 1492; result 41 · RECORDS_IN 30000 Stripe: offset: 3 data: 435805 rows: 50000 tail: 186 index: 65439 Stream: column 2 section BLOOM_FILTER_UTF8 start: 1508 length 59891 Bloom filters for column 2: Entry 0: numHashFunctions: 7 bitCount: 9600 popCount: 4199 loadFactor: 0.4374 …
    Smaller row groups alone changed nothing (still 1–2000 in each). With a bloom filter per 1,000-row group, Hive could prove that 20 of the 50 groups do not contain customer 1492 and read 30,000 rows. The customer has 41 orders spread across the month, so most groups “maybe” contain it. The price: the index grew from 890 bytes to 65,439 bytes.

    CREATE TABLE orders_smallstripe STORED AS ORC
  TBLPROPERTIES ('orc.stripe.size'='131072') AS SELECT * FROM orders;

5 See it happen

How the ORC reader decides what to read

Left: real orcfiledump and Beeline output. Right: what the ORC reader does.

Footer, stripes, statistics and skipping 5 steps
What you see
  1. orcfiledump shows the writer, compression, row count and stripes.
  2. Sorted ids take 161 bytes; small text columns use dictionaries.
  3. Pushdown read 30,000 rows for amount > 870 and nothing for amount > 900.
  4. Sorting by customer cut a lookup from 50,000 rows to 10,000.
  5. A bloom filter cut the unsorted lookup to 30,000 rows.
Behind the screen
  1. A reader starts at the postscript, reads the footer, then jumps to the stripes it needs.
  2. Each stripe has index, data and footer; each column is a separate compressed stream.
  3. The reader compares the filter with each row group’s min and max and skips impossible groups.
  4. When data is sorted, each group covers a narrow range, so most groups are ruled out.
  5. Each group’s bloom filter can prove a value is absent; groups that might contain it are read.

Three live scenarios follow: sorting at write time, a bloom filter decision, and a tuning checklist.

Real-time scenario 1

Sort at write time for fast lookups

A table read by customer many times a day should be written sorted by customer. Counts are real.

Sorted writes 5 steps
Animated example
  1. The table is loaded once a night and read by customer all day.
  2. Write it sorted with DISTRIBUTE BY and SORT BY.
  3. Lookups then skip most row groups.
  4. Sorted columns also compress better.
  5. You get one sort order per file, so choose it carefully.
Real-time scenario 2

A bloom filter for a column you cannot sort by

When the data must stay sorted by time, a bloom filter still speeds up lookups on another column. Result is real.

Bloom filters 5 steps
Animated example
  1. Lookups on a column the data is not sorted by.
  2. Add a bloom filter on that column.
  3. In our lab: 30,000 rows read instead of 50,000.
  4. Bloom filters shine when a value appears in only a few groups.
  5. Tune the false-positive rate and stride.
Real-time scenario 3 · advanced

Debugging a slow ORC query

A practical checklist that uses the tools from this lesson.

ORC tuning checklist 5 steps
Animated example
  1. Start from the counters: how many rows were read?
  2. Make sure predicate pushdown is enabled.
  3. Inspect min/max per row group with orcfiledump.
  4. Write filters the reader can evaluate.
  5. Check for small files and tiny stripes.
6 Real-world use

ORC at work

1. The default for Hive warehouses

Large Hive warehouses store curated tables in ORC with ZLIB or ZSTD; many vendor distributions make ORC the default for managed tables.

Curated data→STORED AS ORC→Fast scans

2. Transactional tables

Hive’s UPDATE, DELETE and MERGE work on ORC tables: base and delta files are ORC, and compaction rewrites them (Module 7).

Changes→ORC deltas→Compaction

3. Point lookups on big tables

Telecom and payments teams add bloom filters on phone numbers, card ids or transaction ids so investigation queries skip most of the data.

Id lookup→bloom filter→Few row groups

4. Layout tuned for queries

Teams write partitions sorted by the main filter column (customer, device, store) so ORC statistics skip most row groups.

Nightly load→sorted write→Selective stats

5. Shared with other engines

Spark, Trino and Presto read ORC natively and use the same statistics and bloom filters, so a well-written ORC table speeds up every engine.

ORC files→same statistics→Any engine
