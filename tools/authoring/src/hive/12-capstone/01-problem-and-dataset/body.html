2 Definition

A data warehouse capstone: requirements, profiling and design

Formal definition (write this in exams)

A data warehouse is a subject-oriented, integrated, time-variant and non-volatile collection of data that supports analysis and decision making. In a Hive warehouse, source files land in raw (external) tables, are cleaned, typed and de-duplicated into silver tables, and are modelled as a star schema: fact tables holding measurable events at a declared grain, surrounded by dimension tables holding descriptive context, some kept as slowly changing dimensions. Aggregated gold tables answer the business questions. Data profiling is the systematic measurement of the source data (volumes, keys, duplicates, nulls, invalid values, late and changing records) that the design must handle.

In simple words

Before building, measure the data: what is duplicated, late, broken or changing. Then design layers (raw → silver → gold), a star schema (facts + dimensions) and rules so that the final numbers are right.

LEVELS> The capstone at three levels L1> A kitchen before service
  • A good cook first checks the delivery: what arrived, what is spoiled, what is missing. That is profiling.
  • Then the cook plans the shelves: raw items, washed and cut items, ready dishes. Those are the raw, silver and gold layers.
  • Only then does the cooking (the code) start, in Lesson 12.2.
L2> What a data engineer delivers in this lesson
  • A requirements list: the questions (KPIs) and how fresh, correct and fast the answers must be.
  • A source inventory and a profile of each source: rows, keys, duplicates, late data, bad values, changes over time.
  • A design: layers, star schema with the grain of each fact, partitioning, file formats, slowly changing dimensions and data-quality rules.
L3> Decisions the profile forced on us
  • 1,206 extra rows (546 copies + 660 refund versions) → the fact table needs a key and an upsert (MERGE), not an append.
  • 2,078 rows for older dates → load by load_date, partition the fact by order_date, and rebuild every date a load touches.
  • 469 customers changed city or plan → dim_customer is SCD type 2, joined “as of” the order time.
  • 112 broken rows → a quarantine table with a reason, never silent drops.
/LEVELS EXAM> Bill Inmon’s classic definition of a data warehouse has four words: subject-oriented, integrated, time-variant, non-volatile. In a star schema, always state the grain of a fact table first (“one row per order”), then its measures and its dimension keys.

4 Step by step

Profiling October’s landing files in Hive

The generator make_capstone.py (in the course’s lab folder) wrote 31 nightly drops the way a source system would. Every output below is real, from Hive 4.2.1 with Beeline.

  1. Step 1 · Look at the landing zone

    find landing -type f | sort | head -6

du -sh landing/*
    landing/customers/load_date=2026-10-01/customers_20261001.csv landing/customers/load_date=2026-10-02/customers_20261002.csv landing/customers/load_date=2026-10-03/customers_20261003.csv landing/customers/load_date=2026-10-04/customers_20261004.csv landing/customers/load_date=2026-10-05/customers_20261005.csv landing/customers/load_date=2026-10-06/customers_20261006.csv … 94 404K landing/customers 8.3M landing/deliveries 3.9M landing/orders 32K landing/restaurants
    One folder per source and per nightly load, named load_date=YYYY-MM-DD. That naming is deliberate: Hive can register each folder as a partition. 31 order files, 31 customer files, 31 event files and one restaurant file: 94 in total, 12.6 MB. Small for Hive, but every real-world problem is inside.

  2. Step 2 · Raw tables over the files

    CREATE DATABASE IF NOT EXISTS tiffingo_dw COMMENT 'TiffinGo capstone warehouse';
USE tiffingo_dw;
-- raw layer: every column is STRING, so no row is ever lost at read time
CREATE EXTERNAL TABLE raw_orders (
  order_id STRING, customer_id STRING, restaurant_id STRING, order_ts STRING,
  amount STRING, payment STRING, status STRING, updated_at STRING)
PARTITIONED BY (load_date STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE
LOCATION 'file:///data/capstone/landing/orders'
TBLPROPERTIES ('skip.header.line.count'='1');
-- raw_customers: same pattern (CSV, header, load_date folders)
CREATE EXTERNAL TABLE raw_deliveries (order_id BIGINT, event STRING, event_ts STRING, rider_id INT)
PARTITIONED BY (load_date STRING) STORED AS JSONFILE
LOCATION 'file:///data/capstone/landing/deliveries';
CREATE EXTERNAL TABLE raw_restaurants (restaurant_id INT, name STRING, city STRING,
  cuisine STRING, rating DECIMAL(2,1), tags ARRAY<STRING>, onboarded STRING)
STORED AS JSONFILE LOCATION 'file:///data/capstone/landing/restaurants';
MSCK REPAIR TABLE raw_orders;      -- registers the 31 load_date folders
MSCK REPAIR TABLE raw_customers;
MSCK REPAIR TABLE raw_deliveries;
SELECT COUNT(DISTINCT load_date) AS order_loads, MIN(load_date) AS first_load, MAX(load_date) AS last_load
FROM raw_orders;
    +--------------+-------------+-------------+ | order_loads | first_load | last_load | +--------------+-------------+-------------+ | 31 | 2026-10-01 | 2026-10-31 | +--------------+-------------+-------------+
    Raw tables are external (dropping them never deletes source files) and every CSV column is STRING. If amount were DECIMAL, the row with NA would silently become NULL and we would not know what the source sent. MSCK REPAIR found the 31 folders and added them as partitions.

  3. Step 3 · Volumes per source and per load

    SELECT 'raw_orders' AS tbl, COUNT(*) AS n FROM raw_orders
UNION ALL SELECT 'raw_customers', COUNT(*) FROM raw_customers
UNION ALL SELECT 'raw_deliveries', COUNT(*) FROM raw_deliveries
UNION ALL SELECT 'raw_restaurants', COUNT(*) FROM raw_restaurants;

SELECT load_date, COUNT(*) AS n FROM raw_orders
WHERE load_date BETWEEN '2026-10-01' AND '2026-10-07'
GROUP BY load_date ORDER BY load_date;
    +------------------+--------+ | tbl | n | +------------------+--------+ | raw_customers | 4167 | | raw_restaurants | 150 | | raw_orders | 48871 | | raw_deliveries | 88462 | +------------------+--------+ +-------------+-------+ | load_date | n | +-------------+-------+ | 2026-10-01 | 1508 | | 2026-10-02 | 1573 | | 2026-10-03 | 1775 | | 2026-10-04 | 1799 | | 2026-10-05 | 1544 | | 2026-10-06 | 1521 | | 2026-10-07 | 1488 | +-------------+-------+
    About 1,500 order rows per night, more on 3 and 4 October (a Saturday and Sunday). The header line of every file was skipped by skip.header.line.count. These counts become the first data-quality check: a nightly load with 0 or 15,000 rows is an alarm, not a load. (UNION ALL does not promise row order.)

  4. Step 4 · Is order_id really a key?

    SELECT COUNT(*) AS raw_rows, COUNT(DISTINCT order_id) AS distinct_orders,
       COUNT(DISTINCT order_id, status, updated_at) AS distinct_versions
FROM raw_orders;

SELECT n_versions, COUNT(*) AS orders FROM (
  SELECT order_id, COUNT(DISTINCT CONCAT(status, '|', updated_at)) AS n_versions
  FROM raw_orders GROUP BY order_id) v
GROUP BY n_versions ORDER BY n_versions;
    +-----------+------------------+--------------------+ | raw_rows | distinct_orders | distinct_versions | +-----------+------------------+--------------------+ | 48871 | 47665 | 48325 | +-----------+------------------+--------------------+ +-------------+---------+ | n_versions | orders | +-------------+---------+ | 1 | 47005 | | 2 | 660 | +-------------+---------+
    48,871 rows but only 47,665 orders. 48,871 − 48,325 = 546 rows are exact copies (duplicates in a file plus rows the source re-sent the next night). And 660 orders have two versions: same order_id, different status and updated_at. So order_id is the business key, but the raw table is a log of versions. Summing it double-counts.

  5. Step 5 · What the second version is

    SELECT load_date, order_id, status, updated_at FROM raw_orders
WHERE order_id IN (SELECT order_id FROM raw_orders
                   WHERE status = 'REFUNDED' AND load_date = '2026-10-09')
ORDER BY order_id, updated_at LIMIT 4;
    +-------------+-----------+------------+----------------------+ | load_date | order_id | status | updated_at | +-------------+-----------+------------+----------------------+ | 2026-10-05 | 5006782 | DELIVERED | 2026-10-05 22:59:00 | | 2026-10-09 | 5006782 | REFUNDED | 2026-10-09 14:47:00 | | 2026-10-05 | 5007134 | DELIVERED | 2026-10-05 14:43:00 | | 2026-10-09 | 5007134 | REFUNDED | 2026-10-09 14:40:00 | +-------------+-----------+------------+----------------------+
    Order 5006782 was DELIVERED on 5 October and REFUNDED on 9 October, and the refund arrived in the 9 October file. The newest version (largest updated_at) is the truth. This is change data capture in its simplest form, and it means the fact table must be updated, not just appended: a job for ACID tables and MERGE (Module 7).

  6. Step 6 · Late rows: when did it happen versus when did it arrive?

    SELECT CASE WHEN TO_DATE(order_ts) = load_date THEN 'same day'
            WHEN TO_DATE(order_ts) < load_date THEN 'older order'
            WHEN order_ts IS NULL OR TO_DATE(order_ts) IS NULL THEN 'bad timestamp' END AS arrival,
       status, COUNT(*) AS n
FROM raw_orders
GROUP BY CASE WHEN TO_DATE(order_ts) = load_date THEN 'same day'
              WHEN TO_DATE(order_ts) < load_date THEN 'older order'
              WHEN order_ts IS NULL OR TO_DATE(order_ts) IS NULL THEN 'bad timestamp' END, status
ORDER BY arrival, status;
    +----------------+------------+--------+ | arrival | status | n | +----------------+------------+--------+ | bad timestamp | DELIVERED | 11 | | older order | CANCELLED | 121 | | older order | DELIVERED | 1294 | | older order | REFUNDED | 663 | | same day | CANCELLED | 3281 | | same day | DELIVERED | 43501 | +----------------+------------+--------+
    2,078 rows describe orders from an earlier day: 663 are refund versions, the rest are orders placed late at night or delayed by the source, plus re-sent rows. So a load on 10 October changes the numbers of 9 October. Two dates matter for every row: load_date (when we received it, for raw partitions and re-runs) and order_date (when it happened, for the fact table and every report).

  7. Step 7 · Broken rows, measured per rule

    SELECT SUM(IF(CAST(o.amount AS DECIMAL(10,2)) IS NULL, 1, 0)) AS bad_amount,
       SUM(IF(CAST(o.amount AS DECIMAL(10,2)) <= 0, 1, 0))  AS non_positive,
       SUM(IF(CAST(o.order_ts AS TIMESTAMP) IS NULL, 1, 0)) AS bad_ts,
       SUM(IF(o.customer_id = '' OR o.customer_id IS NULL, 1, 0)) AS no_customer,
       SUM(IF(r.restaurant_id IS NULL, 1, 0)) AS unknown_restaurant
FROM raw_orders o
LEFT JOIN raw_restaurants r ON CAST(o.restaurant_id AS INT) = r.restaurant_id;

SELECT load_date, order_id, customer_id, restaurant_id, order_ts, amount FROM raw_orders
WHERE load_date = '2026-10-01' AND (CAST(amount AS DECIMAL(10,2)) IS NULL
   OR CAST(amount AS DECIMAL(10,2)) <= 0 OR CAST(order_ts AS TIMESTAMP) IS NULL
   OR customer_id = '' OR restaurant_id = '999');
    +-------------+---------------+---------+--------------+---------------------+ | bad_amount | non_positive | bad_ts | no_customer | unknown_restaurant | +-------------+---------------+---------+--------------+---------------------+ | 31 | 8 | 11 | 31 | 31 | +-------------+---------------+---------+--------------+---------------------+ +-------------+-----------+--------------+----------------+----------------------+---------+ | load_date | order_id | customer_id | restaurant_id | order_ts | amount | +-------------+-----------+--------------+----------------+----------------------+---------+ | 2026-10-01 | 5901539 | 2453 | 7 | 2026-10-01 11:50:00 | NA | | 2026-10-01 | 5901540 | | 9 | 2026-10-01 12:00:00 | 180.00 | | 2026-10-01 | 5901541 | 2029 | 11 | 01/10/2026 12:05 | 150.00 | | 2026-10-01 | 5901538 | 2493 | 999 | 2026-10-01 11:40:00 | 240.00 | +-------------+-----------+--------------+----------------+----------------------+---------+
    Five kinds of broken rows: NA amounts, negative amounts, a date in dd/MM/yyyy format, an empty customer and restaurant 999, which does not exist. CAST returns NULL instead of failing, which is useful for measuring and dangerous for loading. Over the month that is 31 + 8 + 11 + 31 + 31 = 112 broken rows, each failing exactly one rule (a negative amount is a valid number, so it is not in bad_amount). Each rule becomes a reject reason in Lesson 12.2, and broken rows go to a quarantine table instead of disappearing.

    Day 1 is a full snapshot of 3,000 customers; after that each file holds only new sign-ups and changes. 469 customers have 2–4 versions. Rohan Gupta moved from Bengaluru to Navi Mumbai on 11 October and upgraded to Silver on 25 October. If we overwrite (type 1), his early-October orders would be credited to Navi Mumbai and to Silver.   9. Step 9 · Delivery events and the order they belong to

FROM raw_deliveries GROUP BY event;

SELECT COUNT(DISTINCT d.order_id) AS delivered_without_order_same_load
FROM raw_deliveries d
LEFT JOIN raw_orders o ON CAST(o.order_id AS BIGINT) = d.order_id AND o.load_date = d.load_date

    +------------+--------+---------+----------------------+----------------------+ | event | n | orders | first_ts | last_ts | +------------+--------+---------+----------------------+----------------------+ | DELIVERED | 44231 | 44231 | 2026-10-01 00:43:00 | 2026-11-01 00:13:00 | | PICKED_UP | 44231 | 44231 | 2026-10-01 00:31:00 | 2026-10-31 23:50:00 | +------------+--------+---------+----------------------+----------------------+ +------------------------------------+ | delivered_without_order_same_load | +------------------------------------+ | 998 | +------------------------------------+

  10. Step 10 · Why the old report was wrong

    SELECT r.city, COUNT(*) AS orders,
       ROUND(SUM(CAST(o.amount AS DECIMAL(10,2))), 0) AS amount
FROM raw_orders o JOIN raw_restaurants r
  ON CAST(o.restaurant_id AS INT) = r.restaurant_id
GROUP BY r.city ORDER BY orders DESC;

    This is the analyst’s query. Mumbai shows ₹42,77,880 from 12,119 “orders”, but the total includes duplicate rows, re-sent rows, both versions of refunded orders and cancelled orders, while a broken NA amount simply vanished from the sum. Every one of these errors is invisible in the result. In Lesson 12.2 the same question, asked of the gold table, gives the correct and lower number.

Why these choices: the fact is partitioned by order_date because every report filters by it, and a month gives 31 partitions of about 1,500 rows (in production you might partition by month at this size; Lesson 5.4). No bucketing: the largest table has under 50,000 rows. ORC because Hive ACID requires it and it compresses well (Module 6). Plain ORC, not ACID, wherever a load can simply overwrite a partition, because overwrite is cheaper and needs no compaction.

6 Real-world use

Where this first phase happens at work

1. Starting any analytics project

Teams write a KPI definition sheet (name, formula, grain, owner, freshness) before building tables, so finance and product get the same number.

Business question→KPI definition→Design

2. Onboarding a new source system

Before a new payment or partner feed is connected, engineers profile a sample: key uniqueness, null rates, formats, volumes per day.

Sample files→profiling queries→Rules

3. Customer and product history

Banks, insurers and retailers keep customer segment, branch or price history so old transactions are reported with the values valid at the time.

Change feed→SCD type 2→As-of reports

4. Late and corrected data

Telecom usage records, delivery events and payment settlements often arrive days late; warehouses re-compute the affected days.

Late rows→touched dates→Rebuilt reports

5. Regulated reporting

Regulators and auditors ask how many records arrived, how many were rejected and why. Quarantine and audit tables answer that.

Load→audit + quarantine→Evidence
