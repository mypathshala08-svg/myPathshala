1 The story

“I only dropped the table. Where did the data go?”

Before you start: finish Lesson 2.1, where a plain CREATE TABLE turned into an EXTERNAL_TABLE. This lesson explains why.

Kabir and Riya each clean up a test table on the TiffinGo lab. Both type DROP TABLE. Riya re-creates hers a minute later and all 50,002 orders are still there. Kabir re-creates his and gets zero rows: the folder in the warehouse is gone.

K> Sir, we ran the same command. Why did my data disappear and hers did not? A> Because Hive has two kinds of ownership. For Riya’s table Hive owns only the label: the metadata. The files belong to someone else, so DROP removes the label and leaves the files. That is an external table. For your table Hive owned the label and the box: DROP removed both. R> So I should always use external tables to be safe? A> Not always. Hive can only offer some features when it owns the files: UPDATE, DELETE, MERGE, TRUNCATE, automatic clean-up. And Hive 4 adds a twist: your plain CREATE TABLE was stored as an external table with a purge flag, which makes DROP delete files anyway. K> Three kinds, then. How do I tell them apart before I drop something? A> DESCRIBE FORMATTED: look at Table Type, external.table.purge and transactional. Today we will create all three over the same orders, change one row, drop them and look at the folders after each step.
2 Definition

Managed and external tables

Formal definition (write this in exams)

A managed (internal) table is a table whose data files Hive owns: they are stored under the warehouse directory, written only through Hive, and deleted with the table on DROP TABLE; in Hive 3 and later managed tables are transactional (ACID). An external table is a table for which Hive owns only the metadata: its LOCATION may be any path, other tools may write the files, and DROP TABLE removes only the metadata unless the property external.table.purge is true.

In simple words

Managed: Hive owns the table and the files, so dropping the table deletes the data. External: Hive only describes files that belong to someone else, so dropping the table leaves the data. In Hive 4 a plain CREATE TABLE gives an external table with “purge” switched on, which also deletes data on DROP.

LEVELS> Managed and external at three levels L1> A rented flat and your own house
  • External table = a flat you rent. You put your name on the door (the metadata). When you leave, you take the name plate; the flat and its furniture (the files) stay for the owner.
  • Managed table = your own house. When you sell it, everything inside goes too.
  • Hive can renovate a house it owns (UPDATE, DELETE), but it must not change someone else’s flat.
L2> The three kinds you will meet in Hive 4
  • MANAGED_TABLE (transactional): created with TBLPROPERTIES ('transactional'='true'), usually ORC. Lives in the warehouse; supports INSERT, UPDATE, DELETE, MERGE; DROP deletes metadata and files.
  • EXTERNAL_TABLE with external.table.purge=TRUE: what a plain CREATE TABLE becomes (marked TRANSLATED_TO_EXTERNAL). Lives in the warehouse; INSERT and TRUNCATE work, UPDATE/DELETE do not; DROP deletes the files.
  • EXTERNAL_TABLE (plain): created with CREATE EXTERNAL TABLE … LOCATION. Files anywhere; DROP keeps them; TRUNCATE, UPDATE and DELETE are refused.
L3> Why Hive 3 and 4 work this way
  • Since Hive 3, “managed” means Hive controls every write, so it can offer transactions: each write creates a delta_… folder, deletes create delete_delta_… folders, and readers see a consistent snapshot. Other tools must not write there directly.
  • Non-transactional tables cannot give those guarantees, so the metastore stores them as external (hive.create.as.acid=false is the default in our lab; with it set to true, plain CREATE TABLE makes ACID tables).
  • DROP is a metastore operation that then deletes files as the metastore’s user. If that user lacks permission, the table disappears but the files stay (we reproduced this: “Failed to delete … it still exists” in the metastore log).
  • external.table.purge can be changed with ALTER TABLE … SET TBLPROPERTIES: flipping it to true on a shared folder is a classic way to delete someone else’s data.

3 Types and ways to use it

Choosing a table type, and changing it later

External for landing data

Files dropped by an ingestion tool, Kafka connector or partner. Many tools read and write them; Hive must never delete them by accident.

Raw layer

Managed ACID for curated data

Tables that need corrections: refunds, cancelled orders, customer address changes. MERGE and UPDATE work; compaction tidies files.

Curated layer

External + purge for work tables

Intermediate results only Hive uses. DROP cleans up the files, no ACID overhead.

Scratch

External on object storage

Tables over S3, GCS or ADLS paths shared with Spark and Trino, often in ORC, Parquet or Iceberg.

4 Step by step

Three tables over the same orders, then three DROPs

All outputs are real (Hive 4.2.1 lab). The 50,002 orders file sits in /data/tiffingo/orders_ext.

  1. Step 1 · An external table over existing files

    CREATE EXTERNAL TABLE orders_ext (
  order_id INT, customer_id INT, restaurant_id INT, city STRING,
  order_ts TIMESTAMP, amount INT, payment STRING, status STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION 'file:///data/tiffingo/orders_ext';
    Hive records the definition and the folder; the 3 MB file is not moved. From now on Hive, and any other tool, can read it.

  2. Step 2 · A plain table and an ACID table, filled from it

    CREATE TABLE orders_plain (order_id INT, city STRING, amount INT);
CREATE TABLE orders_acid  (order_id INT, city STRING, amount INT)
  STORED AS ORC TBLPROPERTIES ('transactional'='true');
INSERT INTO orders_plain SELECT order_id, city, amount FROM orders_ext WHERE city = 'Thane';
INSERT INTO orders_acid  SELECT order_id, city, amount FROM orders_ext WHERE city = 'Thane';
SELECT 'ext' AS t, COUNT(*) FROM orders_ext
UNION ALL SELECT 'plain', COUNT(*) FROM orders_plain
UNION ALL SELECT 'acid', COUNT(*) FROM orders_acid;
    +--------+--------+ | t | _c1 | +--------+--------+ | acid | 4820 | | plain | 4820 | | ext | 50002 | +--------+--------+
    Both new tables hold the 4,820 Thane orders. The INSERT … SELECT ran as a Tez job and wrote new files into each table’s warehouse folder.

  3. Step 3 · Ask each table what it is

    DESCRIBE FORMATTED orders_ext;    -- and orders_plain, orders_acid
    orders_ext | Location: | file:/data/tiffingo/orders_ext | Table Type: | EXTERNAL_TABLE | | EXTERNAL TRUE orders_plain | Location: | file:/opt/hive/data/warehouse/tiffingo.db/orders_plain | Table Type: | EXTERNAL_TABLE | | TRANSLATED_TO_EXTERNAL TRUE | | external.table.purge TRUE orders_acid | Location: | file:/opt/hive/data/warehouse/tiffingo.db/orders_acid | Table Type: | MANAGED_TABLE | | transactional true (lines picked from three outputs)
    Three answers: plain external, external with purge (translated by Hive 4), and a true managed transactional table. These three lines decide what DROP will do.

  4. Step 4 · Look at the files

    cd /opt/hive/data/warehouse/tiffingo.db
find orders_plain orders_acid -type f -not -name ".*"
    orders_acid/delta_0000001_0000001_0000/bucket_00000_0 orders_acid/delta_0000001_0000001_0000/_orc_acid_version orders_plain/000000_0
    The plain table got one ordinary file. The ACID table got a delta folder named after transaction 1 (delta_<min txn>_<max txn>_<statement>) containing an ORC bucket file.

  5. Step 5 · Change one row

    UPDATE orders_acid  SET amount = 999 WHERE order_id = 100010;
UPDATE orders_plain SET amount = 999 WHERE order_id = 100010;
    +-----------------------+-------------------+---------------------+ (SELECT after the update) | orders_acid.order_id | orders_acid.city | orders_acid.amount | +-----------------------+-------------------+---------------------+ | 100012 | Thane | 300 | | 100010 | Thane | 999 | +-----------------------+-------------------+---------------------+ Error: Error while compiling statement: FAILED: SemanticException [Error 10297]: Attempt to do update or delete on table orders_plain that is not transactional
    The ACID table accepts the UPDATE (order 100010 now shows 999); the plain table refuses at compile time. Behind the screen the update wrote two new folders (Step 6 in the animation): orders_acid, orders_acid/delete_delta_0000002_0000002_0000, orders_acid/delta_0000001_0000001_0000, orders_acid/delta_0000002_0000002_0001.

  6. Step 6 · Try TRUNCATE on the external table

    TRUNCATE TABLE orders_ext;
    Error: Error while compiling statement: FAILED: SemanticException [Error 10146]: Cannot truncate non-managed table orders_ext.
    Hive refuses to empty files it does not own. TRUNCATE on orders_plain (purge) worked in our lab and left 0 rows.

  7. Step 7 · Drop all three and look again

    DROP TABLE orders_ext;
DROP TABLE orders_plain;
DROP TABLE orders_acid;
SHOW TABLES;
    +------------+ | tab_name | +------------+ | customers | +------------+ $ ls /opt/hive/data/warehouse/tiffingo.db customers $ ls -la /data/tiffingo/orders_ext -rw-r--r-- 1 root root 3085976 Oct 26 10:30 orders.csv
    The warehouse folders of orders_plain and orders_acid are gone. orders.csv in the external location is untouched; re-running the CREATE EXTERNAL TABLE from Step 1 returned 50,002 rows immediately.

Three live scenarios follow: the purge flag, orphan files after a failed delete, and choosing a type.

Real-time scenario 1

The purge flag that deleted a shared folder

External tables protect shared files only while purge is off. Follow a realistic incident and the guard rails that prevent it.

Shared folders 5 steps
Animated example
  1. A connector writes event files to a landing folder; a Hive external table reads them.
  2. Someone sets external.table.purge to true so that DROP “cleans up”.
  3. Months later a clean-up script drops the table and the folder is deleted, connector files included.
  4. We reproduced this in the lab: after the property change and DROP, the folder no longer existed.
  5. Keep purge off on shared folders, restrict ALTER, protect landing data with snapshots, and check before dropping.
Real-time scenario 2

DROP succeeded, but the files stayed

This happened in our lab before we fixed folder permissions. It also happens on real clusters.

Orphan files 5 steps
Animated example
  1. DROP first removes the table from the metastore, then deletes the folder as the metastore’s user.
  2. If the user may not delete the files, the second step fails but the client still sees success.
  3. Only the metastore log tells the truth: Failed to delete … it still exists.
  4. The files are now orphans: no table uses them, and a future table on the same path would read them.
  5. Fix permissions, monitor the logs and run a regular orphan check.

Three questions decide the type. See them applied to four real situations.

Choosing a type 5 steps
Animated example
  1. Ask: who else touches the files, will rows change, and should DROP delete data?
  2. Partner files that other systems use: external, purge off.
  3. Orders that need refunds and corrections: managed ACID ORC.
  4. A temporary step in a nightly job: plain CREATE TABLE (external with purge in Hive 4).
  5. Data written by Spark and read by several engines with updates: an external Iceberg table.
6 Real-world use

Where each type is used

1. Landing zones

Files arriving from apps, payment gateways or partners land in a folder that ingestion tools own. Hive external tables let analysts query them the same day without copying.

Source system→External table→Analysts

2. Tables that get corrected

Order status changes from DELIVERED to REFUNDED days later. A managed ACID table takes a nightly MERGE of changes instead of rewriting the whole table.

Changes→MERGE into ACID→Current orders

3. Multi-engine data lakes

When Spark writes Parquet and Hive, Trino and BI tools read it, the tables are external so no single engine can delete the data by accident. Newer lakes use Iceberg tables for safe concurrent writes.

Spark writes→External / Iceberg→Many readers

4. Work tables in pipelines

A nightly job builds intermediate tables and drops them at the end. Because they are purge tables, DROP removes the files and storage does not fill up.

Step 1→Work table→DROP at end

5. Pre-upgrade audits

Before moving to Hive 3 or 4, platform teams list every table’s type, purge flag and location, because the meaning of “managed” changed and DROP behaviour must stay what users expect.

Inventory→Check types→Safe upgrade

Examples are simplified. Policies differ between companies.
