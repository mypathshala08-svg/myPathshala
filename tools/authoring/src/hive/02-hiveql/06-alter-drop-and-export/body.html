1 The story

“I removed the price column and now category says 40”

Before you start: you will reuse city_sales and upi_orders from Lesson 2.5.

The menu table needs changes: a new category column, a clearer name for price, a new table name, and finally a CSV export for the finance team. Kabir also wants to drop the price column. After his REPLACE COLUMNS, the category of Poha shows 40.

K> Sir, I only changed the table definition. Where did 40 come from? A> From the file. ALTER TABLE changes metadata; it does not rewrite data files. For a text table, columns are matched to the file by position. You told Hive the third column is now category, so Hive reads the third value on each line, the old price, as the category. R> So which ALTER statements are safe? A> Adding columns at the end, renaming a column, widening a type (INT to BIGINT), changing properties: all metadata-only and safe. Removing or reordering columns, or narrowing types, can scramble or lose data; Hive refuses some of them and silently allows others. Today we try each, then rename, truncate, drop and export, with the files in view.
2 Definition

Changing, removing and exporting tables

Formal definition (write this in exams)

ALTER TABLE modifies a table’s metadata in the metastore: its name, columns (ADD, CHANGE, REPLACE COLUMNS), properties, SerDe or location; it does not rewrite existing data files, so columns of existing files are interpreted according to the new definition (for delimited text, by position). TRUNCATE TABLE removes all rows of a managed-style table while keeping its definition; DROP TABLE removes the definition and, for managed or purge tables, the data. Data leaves Hive with INSERT OVERWRITE [LOCAL] DIRECTORY … SELECT (files in a chosen format) or EXPORT TABLE (data plus metadata for a later IMPORT).

In simple words

ALTER changes the table’s description, not its files, so Hive reads old files with the new column list in column order. TRUNCATE empties a table, DROP removes it, and you can write query results to a folder or export a whole table to import elsewhere.

Words you’ll meet in this lesson

Schema evolutionChanging a table’s columns over time while old data stays readable.
Positional mappingColumn 3 of the definition reads value 3 of each record, whatever its name.
WideningChanging to a type that holds every old value (INT → BIGINT, INT → DECIMAL with room).
NarrowingA type that cannot hold every old value (BIGINT → INT, STRING → INT). Risky or refused.
REPLACE COLUMNSSwap the whole column list; used to remove columns, dangerous for positional formats.
PURGEWith DROP: delete files immediately instead of moving them to the HDFS trash.
EXPORT / IMPORTCopy a table’s data and metadata to a path, and recreate it from there.
DIRECTORY exportINSERT OVERWRITE DIRECTORY: write any query result as files in a folder.

LEVELS> Changing tables at three levels L1> Relabelling boxes
  • ALTER TABLE rewrites the label on the box. The things inside (files) are not touched.
  • Adding a new heading at the end is fine: old items simply have nothing under it (NULL).
  • Crossing out a heading in the middle makes every heading after it point at the wrong item.
  • TRUNCATE empties the box; DROP throws the box away; EXPORT packs a copy to send elsewhere.
L2> The statements
  • ALTER TABLE t RENAME TO t2: for warehouse tables (managed or purge) the folder is renamed too; for plain external tables only the name changes.
  • ALTER TABLE t ADD COLUMNS (c TYPE): added at the end; existing rows read NULL.
  • ALTER TABLE t CHANGE old new TYPE [COMMENT …]: rename and/or retype one column.
  • ALTER TABLE t REPLACE COLUMNS (…): replace the whole column list (the way to “drop” columns).
  • ALTER TABLE t SET TBLPROPERTIES (…), SET LOCATION '…', ALTER DATABASE d SET DBPROPERTIES (…).
  • TRUNCATE TABLE t, DROP TABLE [IF EXISTS] t [PURGE].
  • Export: INSERT OVERWRITE [LOCAL] DIRECTORY '…' ROW FORMAT … SELECT …; backup/move: EXPORT TABLE … TO / IMPORT TABLE … FROM.
L3> Rules confirmed in the lab
  • Positional mapping: delimited text maps columns by position; our REPLACE COLUMNS put prices into category. For an ORC table Hive refused the same kind of change: “Replacing columns cannot drop columns … SerDe may be incompatible”.
  • Type checks: CHANGE city city INT on an ORC table was refused (“types incompatible with the existing columns”); INT → BIGINT was accepted.
  • CHANGE INT → DECIMAL(8,2) on text worked: 40 became 40.00, because text is re-parsed on every read.
  • Rename moves the folder for warehouse tables (menu_t/ became menu_items/); an external table kept file:/data/tiffingo/menu_csv.
  • EXPORT writes a _metadata file plus a data/ folder; IMPORT can create the table under a new name.
/LEVELS EXAM> “Write ALTER TABLE commands for: rename a table, add a column, rename a column.” ALTER TABLE menu RENAME TO menu_items; ALTER TABLE menu_items ADD COLUMNS (category STRING); ALTER TABLE menu_items CHANGE price price_rs INT; Then state that ALTER changes metadata only.

Getting data out of Hive

WARN> INSERT OVERWRITE DIRECTORY first deletes everything in the target folder. Never point it at a folder that holds anything else, and especially not at a table’s location.
4 Step by step

Change a table, then take data out

All outputs are real, from the Hive 4.2.1 lab.

  1. Step 1 · Add a column at the end

    CREATE TABLE menu_t (item_id INT, name STRING, price INT)
  ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';
INSERT INTO menu_t VALUES (1,'Poha',40),(2,'Misal Pav',80);
ALTER TABLE menu_t ADD COLUMNS (category STRING COMMENT 'meal type');
INSERT INTO menu_t VALUES (3,'Masala Chai',15,'Beverage');
SELECT * FROM menu_t ORDER BY item_id;
    +-----------------+--------------+---------------+------------------+ | menu_t.item_id | menu_t.name | menu_t.price | menu_t.category | +-----------------+--------------+---------------+------------------+ | 1 | Poha | 40 | NULL | | 2 | Misal Pav | 80 | NULL | | 3 | Masala Chai | 15 | Beverage | +-----------------+--------------+---------------+------------------+
    Old lines have only three values, so the new fourth column is NULL for them. New rows fill it. No file was rewritten.

  2. Step 2 · Rename a column and the table

    ALTER TABLE menu_t CHANGE price price_rs INT COMMENT 'price in rupees';
ALTER TABLE menu_t RENAME TO menu_items;
SELECT item_id, name, price_rs, category FROM menu_items ORDER BY item_id;
    +----------+--------------+-----------+-----------+ | item_id | name | price_rs | category | +----------+--------------+-----------+-----------+ | 1 | Poha | 40 | NULL | | 2 | Misal Pav | 80 | NULL | | 3 | Masala Chai | 15 | Beverage | +----------+--------------+-----------+-----------+ $ ls /opt/hive/data/warehouse/tiffingo.db | grep menu menu_items $ cat …/menu_items/* 1,Poha,40 2,Misal Pav,80 3,Masala Chai,15,Beverage
    The column keeps its position, so values are unchanged. Renaming moved the warehouse folder menu_t/ to menu_items/. The files still contain only raw values: the names live in the metastore.

  3. Step 3 · REPLACE COLUMNS shifts data

    CREATE TABLE menu_shift LIKE menu_items;
INSERT INTO menu_shift SELECT * FROM menu_items;
ALTER TABLE menu_shift REPLACE COLUMNS (item_id INT, name STRING, category STRING);
SELECT * FROM menu_shift ORDER BY item_id;
    +---------------------+------------------+----------------------+ | menu_shift.item_id | menu_shift.name | menu_shift.category | +---------------------+------------------+----------------------+ | 1 | Poha | 40 | | 2 | Misal Pav | 80 | | 3 | Masala Chai | 15 | +---------------------+------------------+----------------------+
    Hive accepted the change without a warning. The third value on each line was the price, so “category” now shows 40, 80 and 15. For an ORC table Hive refused this change (“Replacing columns cannot drop columns”). To really remove a column, create a new table and INSERT … SELECT the columns you keep.

  4. Step 4 · Type changes: widen yes, incompatible no

    ALTER TABLE upi_orders CHANGE city city INT;        -- ORC table
ALTER TABLE upi_orders CHANGE amount amount BIGINT;
ALTER TABLE menu_items CHANGE price_rs price_rs DECIMAL(8,2);   -- text table
SELECT * FROM menu_items ORDER BY item_id;
    Error: Error while compiling statement: FAILED: Execution Error, return code 40013 from org.apache.hadoop.hive.ql.ddl.DDLTask. Unable to alter table. The following columns have types incompatible with the existing columns in their respective positions : … (amount → BIGINT: accepted) +---------------------+------------------+----------------------+----------------------+ | menu_items.item_id | menu_items.name | menu_items.price_rs | menu_items.category | +---------------------+------------------+----------------------+----------------------+ | 1 | Poha | 40.00 | NULL | | 2 | Misal Pav | 80.00 | NULL | | 3 | Masala Chai | 15.00 | Beverage | +---------------------+------------------+----------------------+----------------------+
    Turning a STRING into an INT was refused for the ORC table. Widening INT to BIGINT and INT to DECIMAL were accepted; on the text table 40 now reads as 40.00, because text is converted again on every read.

  5. Step 5 · Properties, TRUNCATE and DROP … PURGE

    ALTER TABLE menu_items SET TBLPROPERTIES ('owner_team'='menu');
SHOW TBLPROPERTIES menu_items ('owner_team');
TRUNCATE TABLE menu_items;
SELECT COUNT(*) AS after_truncate FROM menu_items;
DROP TABLE menu_items PURGE;
    +-------------+-------------+ | prpt_name | prpt_value | +-------------+-------------+ | owner_team | menu | +-------------+-------------+ +-----------------+ | after_truncate | +-----------------+ | 0 | +-----------------+
    Properties are free-form labels useful for ownership and tooling. TRUNCATE kept the four columns but removed all rows. DROP … PURGE removed the table and its files without using a trash folder.

  6. Step 6 · Export a query result as CSV

    INSERT OVERWRITE LOCAL DIRECTORY '/data/exports/city_sales_csv'
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
SELECT city, orders, revenue FROM city_sales ORDER BY revenue DESC;
    $ ls /data/exports/city_sales_csv 000000_0 $ head -3 /data/exports/city_sales_csv/000000_0 Mumbai,9250,2712820 Bengaluru,8535,2499060 Pune,7269,2148270
    The result is written as ordinary files named like task outputs. Without ROW FORMAT Hive would use its default separator (Ctrl-A, \001), which surprises spreadsheet users. There is no header line; add one in the tool that consumes the file.

  7. Step 7 · EXPORT, DROP, IMPORT

    EXPORT TABLE city_sales TO 'file:///data/exports/city_sales_bkp';
DROP TABLE city_sales;
IMPORT TABLE city_sales_restored FROM 'file:///data/exports/city_sales_bkp';
SELECT COUNT(*) AS restored_rows FROM city_sales_restored;
    +----------------+ | restored_rows | +----------------+ | 8 | +----------------+ $ find /data/exports/city_sales_bkp -not -name ".*" …/city_sales_bkp/_metadata …/city_sales_bkp/data …/city_sales_bkp/data/000000_0
    EXPORT wrote the table definition (_metadata) and the data files. After the DROP, IMPORT recreated it, under a new name, with all 8 rows. This also works between clusters when the folder is copied across.

Six changes, one unchanged file

The file stays, the label changes 6 steps
What you see
  1. A category column is added. Old rows show NULL, the new row shows Beverage.
  2. A column and the table are renamed. Queries use the new names.
  3. REPLACE COLUMNS removes price from the definition; category now shows prices.
  4. An incompatible type change is refused; widening a type is accepted.
  5. A query result is exported as a comma-separated file.
  6. The table is exported, dropped and imported again with all 8 rows.
Behind the screen
  1. ALTER only changed the metastore. Lines with three values have no fourth value, so category is NULL.
  2. CHANGE keeps the position; RENAME of a warehouse table also renames its folder.
  3. Text columns are matched by position. The third value of each line is still the price.
  4. Hive checks types against existing data positions for formats like ORC and refuses unsafe changes.
  5. INSERT OVERWRITE DIRECTORY clears the folder and writes task output files, without a header.
  6. EXPORT copies the metadata and the data files; IMPORT rebuilds the table from them.

Real-time scenario 1

Removing a sensitive column the right way

A privacy request asks to remove phone numbers from a customer table. ALTER alone is wrong twice.

Column removal 5 steps
Animated example
  1. The privacy team asks to remove the phone column from customers.
  2. REPLACE COLUMNS would shift later columns and leave phone numbers in the files.
  3. The safe method writes a new table with only the wanted columns.
  4. After checking counts, swap the names and drop the old table with PURGE.
  5. Also clean copies, backups, trash and snapshots, and update dependent jobs.
Real-time scenario 2

Schema evolution: what is safe in which format

App data changes shape. Learn which changes every format survives.

Schema evolution 5 steps
Animated example
  1. New fields appear in app data every month.
  2. Adding columns at the end works for all formats: old files return NULL.
  3. Delimited text matches by position, so removing a column scrambles data; for ORC, Hive refused to drop the column.
  4. Parquet and Avro can resolve columns by name, which is more forgiving.
  5. Iceberg tracks columns by id, so renames, drops and reorders are safe.
Real-time scenario 3 · advanced

Delivering data to people outside Hive

Choose the export method by size and audience, and protect the target folder.

Exports 5 steps
Animated example
  1. Finance needs a monthly CSV that opens in a spreadsheet.
  2. For small results, Beeline with csv2 output is simplest and includes a header.
  3. For large results, INSERT OVERWRITE DIRECTORY writes files in parallel, without a header.
  4. OVERWRITE deletes the target folder’s contents first, so always use a fresh, dated folder.
  5. To move a whole table with its definition, use EXPORT and IMPORT.
6 Real-world use

Changes and exports at work

1. Growing event schemas

When the app starts sending a new field, engineers add a column at the end of the event table. Old data reads NULL; no rewrite needed.

New field→ADD COLUMNS→Reports use it

2. Data protection requests

Removing personal data means rewriting tables without it and purging old files and copies, documented for audit. ALTER alone does not delete anything.

Request→Rewrite table→Purge copies

3. Zero-downtime rebuilds

A new version of a table is built beside the old one, verified, then swapped in with two RENAMEs, so readers never see a half-built table.

Build v2→RENAME swap→Drop old

4. Extracts for other teams

Monthly settlement and GST extracts are written with INSERT OVERWRITE DIRECTORY into dated folders and picked up by a transfer job.

Query→DIRECTORY export→SFTP / email

5. Moving tables between clusters

EXPORT writes data and metadata to a folder; after copying it (for example with DistCp), IMPORT recreates the table on the other cluster.

Cluster A→EXPORT / IMPORT→Cluster B
