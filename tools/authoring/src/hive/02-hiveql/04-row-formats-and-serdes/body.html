1 The story

“Why did ‘Dal, Rice combo’ break my menu table?”

Before you start: know column types and delimiters from Lesson 2.3. A little regular-expression knowledge helps for Step 6 (each (…) captures one column).

The TiffinGo menu team exports a CSV. One dish is called "Dal, Rice combo", with a comma inside quotes. Kabir’s table shows "Dal as the name, NULL as the price and 120 as the category. The restaurant data arrives as JSON, and the operations team wants to query the web server’s access log, where nothing is separated by commas at all.

K> Sir, a comma is a comma. How is Hive supposed to know which commas are inside quotes? A> It isn’t, unless you choose a reader that understands quotes. Every Hive table has a SerDe, short for Serializer/Deserializer: the code that turns bytes into columns when reading and columns into bytes when writing. The default one splits on a character and knows nothing about quotes. R> So there is a different SerDe for CSV, for JSON and for logs? A> Exactly. OpenCSVSerde understands quotes, the JsonSerDe maps JSON keys to columns, and RegexSerDe cuts a line with a regular expression. Each has habits you must know: one returns every column as a string, one fails the whole query on a single broken line. We will hit each of them in the lab.
2 Definition

Row formats and SerDes

Formal definition (write this in exams)

A SerDe (Serializer/Deserializer) is the Hive component that converts between the bytes of a stored record and Hive’s row representation: the deserializer parses records into columns when data is read, and the serializer converts rows into records when data is written. A table’s row format names its SerDe and SerDe properties, either with the shorthand ROW FORMAT DELIMITED … (LazySimpleSerDe) or with ROW FORMAT SERDE 'class' WITH SERDEPROPERTIES (…); the file format (STORED AS) names the input and output formats that split files into records.

In simple words

The file format decides how a file is cut into records (usually lines). The SerDe decides how one record is cut into columns. Choose a SerDe that understands your file: delimited text, CSV with quotes, JSON, or a pattern for logs.

Words you’ll meet in this lesson

SerializeTurn a row into bytes for writing to a file.
DeserializeTurn bytes from a file into a row with columns.
InputFormatSplits a file into records (for text: one record per line).
SERDEPROPERTIESSettings for a SerDe, such as separator, quote character or regex.
LazySimpleSerDeThe default text SerDe. “Lazy” because it parses a column only when a query uses it.
Quote characterMarks text that may contain the separator: "Dal, Rice combo".
Capturing groupA part of a regular expression in brackets; RegexSerDe maps group 1 to column 1, and so on.
NULL markerText that means NULL in a file: \N by default for delimited text.

LEVELS> SerDes at three levels L1> Translators at the door
  • Files speak different “languages”: CSV, JSON, log lines.
  • A SerDe is the translator Hive puts at the door of a table. Reading: file language → rows and columns. Writing: rows → file language.
  • Pick the wrong translator and Hive misunderstands: columns shift, values become NULL.
L2> The SerDes you will use
  • LazySimpleSerDe (the default for ROW FORMAT DELIMITED): splits on single characters; no quote handling; empty text stays an empty string; \N means NULL.
  • OpenCSVSerde: handles quotes and escaped quotes; but it returns every column as STRING, whatever you declare.
  • JsonSerDe (STORED AS JSONFILE): one JSON object per line; nested objects map to STRUCT and MAP, lists to ARRAY; extra keys ignored, missing keys NULL.
  • RegexSerDe: one capturing group per column; lines that do not match give a row of NULLs.
  • Binary formats (ORC, Parquet, Avro) have their own SerDes chosen by STORED AS (Module 6).
L3> What the lab showed about edge cases (Hive 4.2.1)
  • OpenCSVSerde: typeof(price) was string although we declared INT; SUM(price) returned 395.0 (string → DOUBLE).
  • JsonSerDe: one line with a missing } made the whole query fail with JsonEOFException. A string where an INT was expected gave 0, not NULL. A key written CITY still matched column city.
  • RegexSerDe: in HiveQL string literals a backslash must be doubled: write \\S+ in the DDL to get the regex \S+.
  • LazySimpleSerDe: serialization.null.format changes the NULL marker (we set it to NA); an empty field is still '', not NULL.
/LEVELS EXAM> “What is a SerDe in Hive?” Expand the name, say it converts records to rows (deserialize, on read) and rows to records (serialize, on write), name the default LazySimpleSerDe and two others (OpenCSVSerde, JsonSerDe, RegexSerDe, ORC/Parquet/Avro SerDes), and show ROW FORMAT SERDE … WITH SERDEPROPERTIES.

Keep raw, publish clean

Read awkward files with the SerDe they need in a raw table, then INSERT into an ORC table with proper types. Other queries never touch the awkward SerDe.

Best practice

Fix at the source

Ask the producer for a safer format (JSON, Parquet, or a separator that cannot appear). Cheaper than clever SerDes forever.

Long term

Custom SerDe

For truly unusual formats you can write a Java SerDe and add its JAR. Rarely needed today.

4 Step by step

Four files, four SerDes

All outputs are real, from the Hive 4.2.1 lab. The files are in the course dataset.

  1. Step 1 · The default SerDe meets quoted commas

    -- menu.csv:  1,"Dal, Rice combo",120,Thali
CREATE EXTERNAL TABLE menu_naive (item_id INT, name STRING, price INT, category STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION 'file:///data/tiffingo/menu_csv'
TBLPROPERTIES ('skip.header.line.count'='1');
SELECT * FROM menu_naive;
    +---------------------+-----------------------------
    Row 1 is split at every comma: "Dal becomes the name, Rice combo" lands in price (NULL, not a number) and 120 lands in category. Row 3’s doubled quotes are kept literally.

  2. Step 2 · OpenCSVSerde understands quotes

    CREATE EXTERNAL TABLE menu_csv (item_id INT, name STRING, price INT, category STRING)
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.OpenCSVSerde'
WITH SERDEPROPERTIES ('separatorChar'=',', 'quoteChar'='"', 'escapeChar'='\\')
LOCATION 'file:///data/tiffingo/menu_csv'
TBLPROPERTIES ('skip.header.line.count'='1');
SELECT * FROM menu_csv;
    +-------------------+-------------------------+-----------------+--------------------+ | menu_csv.item_id | menu_csv.name | menu_csv.price | menu_csv.category | +-------------------+-------------------------+-----------------+--------------------+ | 1 | Dal, Rice combo | 120 | Thali | | 2 | Poha | 40 | Breakfast | | 3 | Paneer "Special" Thali | 220 | Thali | | 4 | Masala Chai | 15 | Beverage | +-------------------+-------------------------+-----------------+--------------------+
    The quoted comma stays inside the name, and ""Special"" becomes "Special". Correct rows at last, but read on.

  3. Step 3 · The OpenCSVSerde surprise: everything is a string

    SELECT SUM(price) AS total FROM menu_csv;
SELECT typeof(price) AS t, price + 1 AS p1 FROM menu_csv LIMIT 1;
    +--------+ | total | +--------+ | 395.0 | +--------+ +---------+--------+ | t | p1 | +---------+--------+ | string | 121.0 | +---------+--------+
    We declared price INT, yet the values arrive as strings, so arithmetic converts them to DOUBLE (395.0, 121.0). Cast explicitly (CAST(price AS INT)) or copy the data into a typed ORC table.

  4. Step 4 · JSON with nested fields

    CREATE EXTERNAL TABLE restaurants (restaurant_id INT, name STRING, city STRING,
  cuisine STRING, rating DECIMAL(2,1), tags ARRAY<STRING>,
  contact STRUCT<phone:STRING, email:STRING>)
STORED AS JSONFILE
LOCATION 'file:///data/tiffingo/restaurants';
SELECT restaurant_id, name, city, rating, tags, contact.email FROM restaurants LIMIT 3;
    +----------------+------------------+---------+---------+---------------------------------------+-----------------------+ | restaurant_id | name | city | rating | tags | email | +----------------+------------------+---------+---------+---------------------------------------+-----------------------+ | 1 | Desai Mess | Thane | 4.8 | ["late-night"] | kitchen1@tiffingo.in | | 2 | Nair Bhojanalay | Mumbai | 4.2 | ["late-night","office-lunch","jain"] | kitchen2@tiffingo.in | | 3 | Gupta Mess | Thane | 3.8 | ["jain","veg","budget"] | kitchen3@tiffingo.in | +----------------+------------------+---------+---------+---------------------------------------+-----------------------+
    JSON keys map to columns by name; the JSON list becomes an ARRAY and the nested object a STRUCT, read with contact.email. SHOW CREATE TABLE shows the SerDe chosen: org.apache.hadoop.hive.serde2.JsonSerDe.

  5. Step 5 · JSON edge cases

-- {"restaurant_id": 900, "name": "Good Line", "city": "Pune"}

    Extra keys are ignored, missing keys give NULL, key case does not matter (CITY matched city), and a text value in an INT field became 0, a silent wrong value. One truncated line failed the whole query. Validate JSON before it lands.

  6. Step 6 · RegexSerDe for web server logs

    CREATE EXTERNAL TABLE access_log (
  ip STRING, ts STRING, method STRING, path STRING, status INT, bytes INT)
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.RegexSerDe'
WITH SERDEPROPERTIES (
  'input.regex' = '^(\\S+) \\S+ \\S+ \\[([^\\]]+)\\] "(\\S+) (\\S+) \\S+" (\\d{3}) (\\d+)$')
LOCATION 'file:///data/tiffingo/access_log';
SELECT status, COUNT(*) AS hits FROM access_log GROUP BY status ORDER BY status;
    +---------+-------+ | status | hits | +---------+-------+ | 200 | 2531 | | 304 | 257 | | 404 | 143 | | 500 | 69 | +---------+-------+
    Six capturing groups → six columns. Backslashes are doubled because the regex is inside a HiveQL string literal. 2,531 + 257 + 143 + 69 = 3,000 lines: every line matched.

  7. Step 7 · Lines that do not match, and NULL markers

    -- access_bad has two log lines and 'health-check ping from load balancer'
SELECT ip, status, path FROM access_bad;
    +----------------+---------+--------------+ | ip | status | path | +----------------+---------+--------------+ | 10.165.39.83 | 200 | /api/orders | | 10.114.24.225 | 304 | /cart | | NULL | NULL | NULL | +----------------+---------+--------------+
    A line that does not match the pattern gives a row of NULLs (no error). Filter them with WHERE ip IS NOT NULL and count them as a quality metric. For delimited text, \N means NULL and an empty field is an empty string; serialization.null.format changes the marker (PCRUN 3).
5 See it happen

One line, many readers

Left: Beeline’s real output. Right: what the SerDe does with the bytes.

Bytes to columns, six frames 6 steps
What you see
  1. The menu file has a dish name with a comma inside quotes.
  2. The default table splits that line wrongly: the name is cut and the price is NULL.
  3. With OpenCSVSerde the row is right, but typeof(price) says string.
  4. JSON keys become columns, including an array and a nested object.
  5. One unfinished JSON line makes the whole query fail.
  6. A log line that does not match the regex becomes a row of NULLs.
Behind the screen
  1. The text InputFormat has already split the file into lines. Now the SerDe must split one line into columns.
  2. LazySimpleSerDe splits on every comma: five pieces for four columns. Values land in the wrong columns.
  3. OpenCSVSerde respects quotes but returns all values as strings, so arithmetic converts them to DOUBLE.
  4. The JsonSerDe matches keys to column names, ignoring case; nested values map to complex types.
  5. The JSON parser reaches the end of the input inside an object and throws an exception for the whole read.
  6. RegexSerDe maps capturing group 1 to column 1, and so on. If the line does not match, nothing is captured.

Three live scenarios follow: raw-to-curated pipelines, log analytics and JSON schema drift.

Real-time scenario 1

Raw table with the right SerDe, curated table with real types

The professional answer to awkward files: parse once, publish clean.

Raw to curated 5 steps
Animated example
  1. A partner sends a quoted CSV every day. A raw table reads it with OpenCSVSerde; all columns are strings.
  2. A daily INSERT casts each column to its real type into an ORC table.
  3. The same job counts values the CAST turned into NULL and alerts if any appear.
  4. Querying the raw table directly would repeat casts and parsing in every report.
  5. File → raw table with the right SerDe → curated typed table: the standard shape.

Real-time scenario 3 · advanced

JSON that changes shape

JSON is flexible, which is exactly why it breaks quietly. Both behaviours shown were reproduced in the lab.

JSON schema drift 5 steps
Animated example
  1. An app release changes restaurant_id from a number to a string.
  2. The JsonSerDe returned 0 for the text value in our lab: no error, wrong data.
  3. A truncated line fails the entire query with JsonEOFException.
  4. Validate at ingestion, keep raw ids as STRING, quarantine bad lines and agree a data contract.
  5. Run a simple check after each load and alert on suspicious values.
6 Real-world use

SerDes in real pipelines

1. Partner and government CSV exports

Bank statements, GST reports and partner catalogues often quote fields with commas. A raw OpenCSVSerde table reads them correctly before a typed copy is made.

Export→OpenCSVSerde→Typed ORC

2. App and API events

Mobile apps and APIs emit JSON. Landing tables use STORED AS JSONFILE with ARRAY, MAP and STRUCT columns that mirror the payload.

App events→JsonSerDe→Event tables

3. Server and security logs

Web, firewall and application logs follow fixed patterns. RegexSerDe tables let operations and security teams query them with SQL during an incident.

Log files→RegexSerDe→Incident queries

4. Exports between systems

Data moved between databases is often exported as tab- or pipe-separated text with \N for NULL, which LazySimpleSerDe reads quickly with no extra settings.

DB export→Delimited text→Hive

5. Curated warehouse tables

Once data is clean it is stored as ORC or Parquet, whose SerDes keep types, compress well and let Hive skip data. Text SerDes stay at the edges of the pipeline.

Raw text→INSERT … SELECT→ORC tables
