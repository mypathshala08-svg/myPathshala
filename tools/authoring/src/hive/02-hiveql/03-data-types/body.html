1 The story

“Why is the cutlery column NULL for every order?”

Before you start: you should be able to create a table (Lesson 2.1). The order items file is in the course dataset (order_items.txt and the faulty order_items_v1.txt).

TiffinGo’s app writes one line per order: the order id, the dishes and the customer’s preferences (spice level, cutlery yes or no). Kabir defines a table with an ARRAY and a MAP column and asks for prefs['cutlery']. Every row says NULL. Meanwhile Riya’s revenue total is off by a few paise, and a TINYINT column shows -128 where it should say 128.

K> The file clearly says cutlery:yes. Why can’t Hive see it? A> Because Hive reads text through the types and delimiters you declare. A file has no types; it is just characters. If you tell Hive the wrong separator for map entries, the whole rest of the line becomes one value. We will reproduce your bug exactly. R> And my paise? And the -128? A> Those are type choices too. DOUBLE cannot store 0.1 exactly, so money belongs in DECIMAL. TINYINT holds only −128 to 127, and in Hive arithmetic that goes past the limit wraps around silently. Today you will see every type Hive has, what happens when a value does not fit, and how to work with arrays, maps and structs.
2 Definition

Hive data types

Formal definition (write this in exams)

Hive supports primitive types: integers (TINYINT, SMALLINT, INT, BIGINT), floating point (FLOAT, DOUBLE), exact DECIMAL(p,s), text (STRING, VARCHAR(n), CHAR(n)), BOOLEAN, BINARY and date/time types (DATE, TIMESTAMP, INTERVAL); and complex types: ARRAY<T>, MAP<K,V>, STRUCT<name:T, …> and UNIONTYPE<T1, T2, …>. Because Hive applies the schema when data is read, a value that cannot be interpreted as the declared type is returned as NULL.

In simple words

Every column has a type that tells Hive how to read and compute with the text in the files. Simple types hold one value; complex types hold a list, a key–value lookup or a small record inside one column. Values that do not fit the type turn into NULL.

LEVELS> Data types at three levels L1> Containers of the right size
  • A type is a container: a small cup (TINYINT) holds small numbers, a bucket (BIGINT) holds huge ones. Pour too much in and it spills.
  • STRING holds any text; DATE and TIMESTAMP hold calendar values; BOOLEAN holds true or false.
  • Complex types hold many values in one column: a list (ARRAY), a lookup table (MAP) or a mini-record (STRUCT).
  • If Hive cannot read a value as the declared type, it shows NULL instead of failing.
L2> Choosing types
  • Counts and ids: INT (up to about 2.1 billion) or BIGINT (up to about 9.2 × 1018).
  • Money: DECIMAL(p,s), for example DECIMAL(12,2). Never DOUBLE for rupees.
  • Text: STRING almost always; VARCHAR(n) cuts longer text; CHAR(n) pads.
  • Dates: DATE needs yyyy-MM-dd; TIMESTAMP needs yyyy-MM-dd HH:mm:ss[.fff]. Other layouts become NULL; convert them with functions (Module 4).
  • Nested data: ARRAY<T>, MAP<K,V>, STRUCT<a:T, b:U>; rarely UNIONTYPE.
L3> Exact behaviour in Hive 4.2.1 (all checked in the lab)
  • Overflow wraps: CAST(127 AS TINYINT) + CAST(1 AS TINYINT) = −128; INT 2147483647 + 1 = −2147483648; CAST(300 AS TINYINT) = 44 (low 8 bits kept).
  • Literals: 1 is INT, 1L BIGINT, 1.5 is DECIMAL(2,1), 'a' STRING (checked with typeof()).
  • Division: 7 / 2 = 3.5 (always a fractional result); 7 DIV 2 = 3.
  • Implicit conversion: '10' + 5 = 15.0 (the string becomes DOUBLE). Invalid text in CAST gives NULL; CAST('2026-02-30' AS DATE) is NULL.
  • DECIMAL overflow gives NULL: CAST(123456.78 AS DECIMAL(7,2)) is NULL because only 5 digits fit before the point.
  • Strict timestamps: CAST(1793010170 AS TIMESTAMP) is refused (hive.strict.timestamp.conversion); use from_unixtime().
  • Delimiters: in a delimited text table, array items and map entries both use COLLECTION ITEMS TERMINATED BY; map keys use MAP KEYS TERMINATED BY.
/LEVELS EXAM> “List Hive data types.” Write two groups. Primitive: numeric (TINYINT, SMALLINT, INT, BIGINT, FLOAT, DOUBLE, DECIMAL), string (STRING, VARCHAR, CHAR), date/time (DATE, TIMESTAMP, INTERVAL), misc (BOOLEAN, BINARY). Complex: ARRAY, MAP, STRUCT, UNIONTYPE, each with a one-line example such as ARRAY<STRING> → dishes[0].

4 Step by step

Test every type rule in the lab

All outputs are real, from Hive 4.2.1.

  1. Step 1 · Integers wrap, decimals are exact

    SELECT CAST(127 AS TINYINT) + CAST(1 AS TINYINT) AS tiny_overflow,
       CAST(300 AS TINYINT) AS cast_300,
       7 / 2 AS int_div, 7 DIV 2 AS div_op,
       CAST('abc' AS INT) AS bad_int, '10' + 5 AS str_plus_int,
       CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE) AS dbl_sum,
       CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2)) AS dec_sum;
    +----------------+-----------+----------+---------+----------+---------------+----------------------+----------+ | tiny_overflow | cast_300 | int_div | div_op | bad_int | str_plus_int | dbl_sum | dec_sum | +----------------+-----------+----------+---------+----------+---------------+----------------------+----------+ | -128 | 44 | 3.5 | 3 | NULL | 15.0 | 0.30000000000000004 | 0.30 | +----------------+-----------+----------+---------+----------+---------------+----------------------+----------+
    Five lessons in one row: overflow wraps (−128), a narrowing CAST keeps only the low bits (300 → 44), / gives a fraction while DIV gives a whole number, bad text becomes NULL, and DOUBLE cannot hold 0.3 exactly while DECIMAL can.

  2. Step 2 · Bigger limits

    SELECT CAST(2147483647 AS INT) + 1 AS int_over,
       CAST(2147483647 AS BIGINT) + 1 AS big_ok,
       CAST(12345.678 AS DECIMAL(7,2)) AS d72,
       CAST(123456.78 AS DECIMAL(7,2)) AS d72_over,
       from_unixtime(1793010170) AS fu;
    +--------------+-------------+-----------+-----------+----------------------+ | int_over | big_ok | d72 | d72_over | fu | +--------------+-------------+-----------+-----------+----------------------+ | -2147483648 | 2147483648 | 12345.68 | NULL | 2026-10-26 10:22:50 | +--------------+-------------+-----------+-----------+----------------------+
    INT wraps too; BIGINT has room. DECIMAL(7,2) rounds 12345.678 to 12345.68 but cannot hold 123456.78 at all, so it returns NULL. from_unixtime converts epoch seconds (output in the server time zone, UTC in our lab).

  3. Step 3 · Dates, text and booleans

    SELECT CAST('2026-10-31' AS DATE) AS d, CAST('31/10/2026' AS DATE) AS bad_d,
       CAST('2026-02-30' AS DATE) AS feb30,
       CAST('2026-10-31 21:15:00' AS TIMESTAMP) AS ts,
       CAST('Kharghar Navi Mumbai' AS VARCHAR(8)) AS vc,
       CAST('yes' AS BOOLEAN) AS b2;
    +-------------+--------+--------+------------------------+-----------+-------+ | d | bad_d | feb30 | ts | vc | b2 | +-------------+--------+--------+------------------------+-----------+-------+ | 2026-10-31 | NULL | NULL | 2026-10-31 21:15:00.0 | Kharghar | true | +-------------+--------+--------+------------------------+-----------+-------+
    Only yyyy-MM-dd becomes a DATE; an Indian-style date and an impossible date are NULL. VARCHAR(8) silently cuts the text. For BOOLEAN, our tests showed 'false', 'no', 'off', '0' and the empty string become false, and anything else, even 'n' or 'abc', becomes true.

  4. Step 4 · Ask Hive for the type

    SELECT typeof(1), typeof(1L), typeof(1.5), typeof(1.5BD), typeof('a');
    +------+---------+---------------+---------------+---------+ | _c0 | _c1 | _c2 | _c3 | _c4 | +------+---------+---------------+---------------+---------+ | int | bigint | decimal(2,1) | decimal(2,1) | string | +------+---------+---------------+---------------+---------+
    1.5 is a DECIMAL literal in Hive 4, not a DOUBLE. typeof() is the quickest way to check what an expression really is.

  5. Step 5 · The delimiter bug, reproduced

    CREATE EXTERNAL TABLE order_items_bad (order_id INT,
  dishes ARRAY<STRING>, prefs MAP<STRING,STRING>)
ROW FORMAT DELIMITED FIELDS TERMINATED BY '|'
  COLLECTION ITEMS TERMINATED BY ','
  MAP KEYS TERMINATED BY ':'
LOCATION 'file:///data/tiffingo/order_items_bad';
-- file line: 100001|Chole Bhature,…|spice:medium;cutlery:yes
SELECT order_id, prefs, prefs['cutlery'] AS cutlery FROM order_items_bad LIMIT 2;
    +-----------+---------------------------------+----------+ | order_id | prefs | cutlery | +-----------+---------------------------------+----------+ | 100001 | {"spice":"medium;cutlery:yes"} | NULL | | 100002 | {"spice":"mild;cutlery:yes"} | NULL | +-----------+---------------------------------+----------+
    Map entries are split by the collection delimiter (a comma). The file used a semicolon, so Hive saw one entry whose value was medium;cutlery:yes, and the key cutlery does not exist: NULL. Kabir’s bug, explained.

  6. Step 6 · The fixed file: arrays and maps at work

    -- file line: 100001|Chole Bhature,Aloo Paratha,Lassi,Rajma Chawal|spice:medium,cutlery:yes
SELECT order_id, dishes[0] AS first_dish, size(dishes) AS n_dishes,
       prefs['spice'] AS spice, prefs['cutlery'] AS cutlery
FROM order_items LIMIT 3;
SELECT prefs['spice'] AS spice, COUNT(*) AS orders,
       ROUND(AVG(size(dishes)),2) AS avg_dishes
FROM order_items GROUP BY prefs['spice'] ORDER BY orders DESC;
    +-----------+--------------------+-----------+---------+----------+ | order_id | first_dish | n_dishes | spice | cutlery | +-----------+--------------------+-----------+---------+----------+ | 100001 | Chole Bhature | 4 | medium | yes | | 100002 | Veg Hakka Noodles | 3 | mild | yes | | 100003 | Poha | 3 | mild | yes | +-----------+--------------------+-----------+---------+----------+ +---------+---------+-------------+ | spice | orders | avg_dishes | +---------+---------+-------------+ | hot | 1695 | 2.51 | | medium | 1689 | 2.53 | | mild | 1616 | 2.57 | +---------+---------+-------------+
    Indexing ([0]), size() and map lookup work like ordinary columns, even inside GROUP BY. 5,000 orders: hot 1,695, medium 1,689, mild 1,616.

  7. Step 7 · A STRUCT column in a table

    CREATE TABLE cust_addr (customer_id INT,
  addr STRUCT<city:STRING, state:STRING, pin:INT>, tags ARRAY<STRING>);
INSERT INTO cust_addr
SELECT customer_id, named_struct('city', city, 'state', state, 'pin', 400000 + customer_id),
       array(plan, state)
FROM customers WHERE customer_id <= 3;
SELECT customer_id, addr, addr.city, tags FROM cust_addr;
    +--------------+-------------------------------------------------+------------+------------------+ | customer_id | addr | city | tags | +--------------+-------------------------------------------------+------------+------------------+ | 1 | {"city":"Bengaluru","state":"KA","pin":400001} | Bengaluru | ["Silver","KA"] | | 2 | {"city":"Mumbai","state":"MH","pin":400002} | Mumbai | ["Basic","MH"] | | 3 | {"city":"Mumbai","state":"MH","pin":400003} | Mumbai | ["Gold","MH"] | +--------------+-------------------------------------------------+------------+------------------+
    A STRUCT keeps related fields together and is read with a dot: addr.city. (The pin numbers here are made up from the id, only to fill the field.)
5 See it happen

Six type rules, two views

Left: the real result in Beeline. Right: what happens to the value inside Hive.

Six rules, six frames 6 steps
What you see
  1. TINYINT arithmetic past 127 wraps to −128; casting 300 into a TINYINT gives 44.
  2. DOUBLE gives 0.30000000000000004; DECIMAL gives exactly 0.30.
  3. Only yyyy-MM-dd text becomes a DATE. The other two values are NULL.
  4. With the wrong map-entry delimiter, prefs has one strange entry and cutlery is NULL.
  5. With the fixed file, array and map functions return the expected values.
  6. A STRUCT column shows as JSON-like text, and addr.city reads one field.
Behind the screen
  1. 128 needs the 8th bit, which TINYINT uses for the sign, so the value is read as −128. 300 keeps only its lowest 8 bits: 44.
  2. Binary floating point cannot represent 0.1 exactly; DECIMAL stores digits, so money adds up.
  3. DATE parsing is strict: wrong layouts and impossible days quietly become NULL.
  4. Fields split on |, entries on the collection delimiter (a comma), keys on a colon. The semicolon was never a delimiter.
  5. Three delimiter levels map the text to INT, ARRAY and MAP. Indexing and lookups work in SELECT and GROUP BY.
  6. A STRUCT stores named fields with their own types inside one column.

Three live scenarios follow: money in DOUBLE, an id column that overflows, and nested app data.

Real-time scenario 1

Money in DOUBLE: the payout that did not match

A finance report sums order amounts stored as DOUBLE. The bank’s total differs in the last digits. (Amounts illustrative.)

DOUBLE vs DECIMAL 5 steps
Animated example
  1. The DOUBLE total is off by a fraction of a paisa; the bank statement is exact.
  2. Binary floating point cannot store 0.1 exactly; errors accumulate and depend on the order of addition.
  3. Using DECIMAL(12,2) stores exact paise and gives the same total every time.
  4. Choose precision to fit the largest value; values that do not fit become NULL.
  5. DECIMAL for money, DOUBLE for measurements, INT/BIGINT for counts and ids.
Real-time scenario 2

The day order_id went negative

INT is fine for years, until it is not. Watch an id column hit the limit and how teams fix and prevent it. (Growth numbers illustrative.)

INT overflow 5 steps
Animated example
  1. Order ids grow every year and approach the INT maximum of 2,147,483,647.
  2. In Hive the next value wraps to −2,147,483,648, a real result from our lab.
  3. BIGINT has room for about 9.2 quintillion values.
  4. Widening a column type is a metadata change; narrowing can create NULLs.
  5. Monitor how close ids are to their limit and alert early.

6 Real-world use

Types in real data work

1. Payments and settlements

UPI and card settlement tables use DECIMAL for amounts, fees and GST so totals match bank statements to the paisa.

Transactions→DECIMAL(12,2)→Reconciled totals

2. App analytics events

Click events carry different properties per screen. A MAP<STRING,STRING> column holds them without a schema change for every new property.

App event→MAP column→props['screen']

3. Raw-to-curated typing

Raw tables keep every column as STRING. The curated job CASTs to proper types and reports how many values became NULL, which catches broken files early.

Raw STRING→CAST + NULL count→Curated types

4. Shopping carts and orders

E-commerce and food-delivery orders store items as an ARRAY (or an ARRAY of STRUCTs with name, quantity and price) and explode it when item-level analysis is needed.

Order→ARRAY<STRUCT>→Item analysis

5. Event ids and timestamps

Event ids and epoch milliseconds exceed INT range, so logs and clickstreams use BIGINT and convert epochs with functions such as from_unixtime.

Raw epoch→BIGINT→TIMESTAMP
