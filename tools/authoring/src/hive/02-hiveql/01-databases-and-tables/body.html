1 The story

“Which of these five orders tables is the real one?”

Before you start: have the lab from Lesson 1.5 running and Beeline connected. The customers file comes from the course dataset.

On his second week at TiffinGo, Kabir runs SHOW TABLES and gets 140 names: orders, orders_v2, orders_final, orders_final_new, kabir_tmp… Everyone created tables in default. Nobody knows which orders the finance report reads.

K> Sir, can I just call my table orders? Someone already took that name. A> In one database a name can exist only once. Hive lets you make many databases: think of them as shelves in a library. The raw files on one shelf, the cleaned company tables on another, your experiments on your own. R> Is a database a real thing on disk, or only a name? A> Both. K> And how do I see what a table really is, its columns, its format, where its files are? A> Three commands: DESCRIBE, DESCRIBE FORMATTED and SHOW CREATE TABLE. Today you will create the TiffinGo database, a customers table, load 2,000 customers and read everything Hive knows about it. You will also meet a Hive 4 surprise: the table you create may not be the type you asked for.
2 Definition

Databases and tables in Hive

Formal definition (write this in exams)

In Hive a database (synonym: schema) is a named namespace for tables, recorded in the metastore and mapped by default to the directory <warehouse>/<database>.db. A table is a metastore entry that describes data files by their columns and data types, row format (SerDe and delimiters), storage format (input/output format), location, table type (managed or external) and table properties. Tables are created with CREATE TABLE and inspected with DESCRIBE [FORMATTED] and SHOW CREATE TABLE.

In simple words

A database is a named folder for tables. A table is a description, kept in the metastore, of how to read some files as rows and columns: which columns, what types, how lines are split, what format the files have and where they are.

Words you’ll meet in this lesson

DDLData Definition Language: statements that create, change or drop objects (CREATE, ALTER, DROP).

LEVELS> Databases and tables at three levels L1> Shelves and labelled boxes
  • A database is a shelf with a name, like tiffingo.
  • A table is a labelled box on that shelf: the label lists the columns (name, city, plan…), the box holds the data files.
  • Two shelves can each have a box called orders; you say which one with shelf.box, for example tiffingo.orders.
  • USE tiffingo; means “I am standing at this shelf now”, so you can write just orders.
L2> What Hive records
  • CREATE DATABASE adds a row in the metastore table DBS and a folder <warehouse>/<name>.db, for us file:/opt/hive/data/warehouse/tiffingo.db.
  • CREATE TABLE records the columns and types, the row format (how a line becomes columns: a SerDe and a delimiter), the file format (TEXTFILE, ORC, Parquet…), the location and table properties.
  • Without LOCATION the table folder is <db folder>/<table>.
  • Names are not case-sensitive and are stored in lower case; Customers and customers are the same table.
L3> Details that matter at work
  • Hive 4 table translation: with the default hive.create.as.acid=false, a plain CREATE TABLE that is not transactional is stored as EXTERNAL_TABLE with external.table.purge=TRUE and TRANSLATED_TO_EXTERNAL=TRUE. It behaves like a managed table (DROP deletes data) but is not ACID. Lesson 2.2 explains why.
  • Table properties (TBLPROPERTIES) carry behaviour: skip.header.line.count, transactional, compression, statistics such as numFiles and totalSize.
  • Patterns: in Hive 4 SHOW TABLES LIKE uses SQL wildcards: 'cust%' matched, 'tif*' matched nothing in our run.
  • Safety: DROP DATABASE refuses a non-empty database unless you add CASCADE, which drops every table in it. IF EXISTS / IF NOT EXISTS make scripts safe to re-run.
  • Temporary tables live only for your session and are invisible to others.
/LEVELS EXAM> “Write the syntax of CREATE TABLE in Hive.” CREATE [EXTERNAL] [TEMPORARY] TABLE [IF NOT EXISTS] [db.]name (col type [COMMENT '…'], …) [COMMENT '…'] [PARTITIONED BY (…)] [ROW FORMAT DELIMITED FIELDS TERMINATED BY ','] [STORED AS format] [LOCATION 'path'] [TBLPROPERTIES (…)]; Then name what goes to the metastore (schema, format, location) and that no data is moved by CREATE.
3 Types and ways to use it

Ways to create databases and tables

CREATE TABLE (columns)

You list the columns and types, and optionally row format, file format, location and properties. The most common form.

Everyday

CREATE TABLE … LIKE

Copies another table’s definition (columns, format, properties) without any data. CREATE TABLE customers_copy LIKE customers.

Same shape

CREATE TABLE … AS SELECT

CTAS: creates the table from a query’s result, columns and data together. Lesson 2.5.

From a query

CREATE EXTERNAL TABLE

Describes files that something else owns; DROP leaves the files. Lesson 2.2.

Shared files

CREATE TEMPORARY TABLE

Lives only for your session, visible only to you. Good for intermediate steps.

Scratch

CREATE DATABASE … LOCATION

Puts a database folder somewhere other than the warehouse, for example a team bucket.

4 Step by step

Create the TiffinGo database and its first table

All outputs are real, from the Hive 4.2.1 lab of Lesson 1.5.

  1. Step 1 · Create a database with a comment and an owner

    CREATE DATABASE IF NOT EXISTS tiffingo
  COMMENT 'TiffinGo food delivery data'
  WITH DBPROPERTIES ('owner_team'='data-eng');
SHOW DATABASES;
    +----------------+ | database_name | +----------------+ | default | | tiffingo | +----------------+
    IF NOT EXISTS makes the statement safe to run twice. The comment and properties are stored in the metastore and help the next person understand what the database is for.

  2. Step 2 · See where it lives

    DESCRIBE DATABASE EXTENDED tiffingo;
    | db_name | comment | location | owner_name | parameters | | tiffingo | TiffinGo food delivery data | file:/opt/hive/data/warehouse/tiffingo.db | hive | {owner_team=data-eng} | (columns trimmed)
    The location is <warehouse>/tiffingo.db. On a real cluster it would start with hdfs:// or s3a://. Hive 4 also prints a managedlocation column (same folder here).

  3. Step 3 · Create the customers table

    USE tiffingo;
CREATE TABLE customers (
  customer_id INT COMMENT 'unique id',
  name STRING, city STRING, state STRING,
  joined_on DATE,
  plan STRING COMMENT 'Gold, Silver or Basic')
COMMENT 'TiffinGo customers'
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE
TBLPROPERTIES ('skip.header.line.count'='1');
DESCRIBE customers;
    +--------------+------------+------------------------+ | col_name | data_type | comment | +--------------+------------+------------------------+ | customer_id | int | unique id | | name | string | | | city | string | | | state | string | | | joined_on | date | | | plan | string | Gold, Silver or Basic | +--------------+------------+------------------------+
    Three parts: the columns, how a line is split (ROW FORMAT DELIMITED with commas), and the file format. skip.header.line.count=1 tells readers to ignore the CSV header line.

  4. Step 4 · Put data in and query it

    LOAD DATA LOCAL INPATH '/data/tiffingo/customers/customers.csv' INTO TABLE customers;
SELECT plan, COUNT(*) AS n FROM customers GROUP BY plan ORDER BY n DESC;
    +---------+------+ | plan | n | +---------+------+ | Basic | 999 | | Gold | 517 | | Silver | 484 | +---------+------+
    999 + 517 + 484 = 2,000 customers, so the header line was skipped correctly. LOAD DATA copied the file into the table folder (Lesson 2.5 covers loading in depth).

  5. Step 5 · Read everything Hive knows

    DESCRIBE FORMATTED customers;
    | # Detailed Table Information | | | Database: | tiffingo | | Owner: | hive | | Location: | file:/opt/hive/data/warehouse/tiffingo.db/customers | | Table Type: | EXTERNAL_TABLE | | Table Parameters: | | | | TRANSLATED_TO_EXTERNAL TRUE | | | external.table.purge TRUE | | | numFiles 1 | | | skip.header.line.count 1 | | | totalSize 91618 | | # Storage Information | | | SerDe Library: | org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe | | InputFormat: | org.apache.hadoop.mapred.TextInputFormat | (trimmed)
    Surprise: we wrote CREATE TABLE, but the type is EXTERNAL_TABLE with TRANSLATED_TO_EXTERNAL and external.table.purge=TRUE. Hive 4 stores non-transactional “managed” tables this way; DROP still deletes the files. Details in Lesson 2.2.

  6. Step 6 · Get the full DDL

    SHOW CREATE TABLE customers;
    CREATE EXTERNAL TABLE `customers`( `customer_id` int COMMENT 'unique id', `name` string, … , `plan` string COMMENT 'Gold, Silver or Basic') COMMENT 'TiffinGo customers' ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe' WITH SERDEPROPERTIES ( 'field.delim'=',', 'serialization.format'=',') STORED AS INPUTFORMAT 'org.apache.hadoop.mapred.TextInputFormat' OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat' LOCATION 'file:/opt/hive/data/warehouse/tiffingo.db/customers' TBLPROPERTIES ( 'TRANSLATED_TO_EXTERNAL'='TRUE', 'external.table.purge'='TRUE', 'skip.header.line.count'='1', …)
    ROW FORMAT DELIMITED … STORED AS TEXTFILE is shorthand: Hive expands it into a SerDe class, an input format and an output format. Save this output in Git; it recreates the table exactly.

  7. Step 7 · Copy a shape and see the guard rails

    CREATE TABLE customers_copy LIKE customers;
CREATE TABLE customers (id INT);
SELECT * FROM tiffingo.customer;
DROP DATABASE tiffingo;
    Error: Error while compiling statement: FAILED: Execution Error, return code 40000 from org.apache.hadoop.hive.ql.ddl.DDLTask. AlreadyExistsException(message:Table hive.tiffingo.customers already exists) Error: Error while compiling statement: FAILED: SemanticException [Error 10001]: Line 1:14 Table not found 'customer' Error: Error while compiling statement: FAILED: Execution Error, return code 40000 from org.apache.hadoop.hive.ql.ddl.DDLTask. InvalidOperationException(message:Database tiffingo is not empty. One or more tables exist.)
    LIKE copies the definition, not the rows. A duplicate name fails with AlreadyExistsException, a typo with Table not found at compile time, and a non-empty database cannot be dropped without CASCADE.
5 See it happen

Six commands, two views

Left: Beeline and its real output. Right: the rows in the metastore and the folders in the warehouse that each command creates.

From CREATE DATABASE to DESCRIBE FORMATTED 6 steps
What you see
  1. Kabir creates the tiffingo database with a comment, and SHOW DATABASES lists it next to default.
  2. He creates the customers table: columns, a comma delimiter and a property to skip the header line.
  3. DESCRIBE answers instantly with the six columns, their types and comments.
  4. He loads the CSV file and counts customers per plan: 999 + 517 + 484 = 2,000.
  5. DESCRIBE FORMATTED reveals the table type: EXTERNAL_TABLE, translated, with purge.
  6. A duplicate CREATE and a DROP of a non-empty database are both refused.
Behind the screen
  1. The metastore gets a row in DBS and the warehouse gets a folder tiffingo.db.
  2. Rows are added in TBLS, SDS (location and format), COLUMNS_V2 and TABLE_PARAMS, and an empty folder customers is made.
  3. DESCRIBE is a metadata-only command: it reads the column rows from the metastore. No files are opened.
  4. LOAD DATA copies the file into the table folder and updates numFiles and totalSize. Queries skip line 1.
  5. Because the table is not transactional and hive.create.as.acid is false, Hive 4 stores it as an external table with purge on.
  6. The metastore enforces a unique table name per database and refuses to drop a database that still has tables.

Real-time scenario 2

Reading DESCRIBE FORMATTED like an engineer

Its output is long. Learn its three sections and the four questions it answers. The values are from our lab.

DESCRIBE FORMATTED 5 steps
Animated example
  1. DESCRIBE FORMATTED prints a long table with three sections marked by #.
  2. Section 1 lists the columns with types and comments.
  3. Section 2 gives the location, table type, owner and table parameters such as numFiles and purge.
  4. Section 3 shows the SerDe, input format, buckets and delimiter.
  5. Use it to answer four questions before touching a table: type, location, format and size.
Real-time scenario 3 · advanced

Four real errors and what they teach

Every message here was produced by our lab. Learn to read them; they tell you exactly what is wrong.

Errors 5 steps
Animated example
  1. A typo in a table name fails at compile time with SemanticException 10001. No cluster time is used.
  2. Creating a table that exists fails with AlreadyExistsException. IF NOT EXISTS avoids it.
  3. In Hive 4 the pattern tif* matched nothing; the SQL wildcard tif% matched tiffingo.
  4. DROP DATABASE refuses a database that has tables. CASCADE drops them all, so use it with great care.
  5. beeline -f stops at the first failing statement. Re-runnable DDL makes recovery easy.
6 Real-world use

Databases and tables in daily work

1. Layered warehouses

Most companies keep raw landing data, cleaned tables and report tables in separate databases. A table’s database tells you how much you can trust it.

Files arrive→raw → curated → mart→Reports

2. DDL in version control

Teams keep every CREATE TABLE in Git (often taken from SHOW CREATE TABLE). Changes are reviewed like code and the same file builds dev, test and production.

Pull request→Review DDL→Deploy

3. One database per environment

On a shared cluster, dev_tiffingo, test_tiffingo and tiffingo hold the same tables. A --hivevar db=… switch points the same script at each.

Script→${db}.orders→Right environment

4. Data discovery

Data catalogue tools read databases, tables, column comments and properties from the metastore. Good comments written at CREATE time become documentation everyone can search.

COMMENT→Metastore→Catalogue search

5. Scratch work without clutter

Analysts use CREATE TEMPORARY TABLE for intermediate steps. The table disappears when the session ends, so shared databases stay clean.

Big query→Temp table→Final result

Examples are simplified. Naming conventions differ between companies.
