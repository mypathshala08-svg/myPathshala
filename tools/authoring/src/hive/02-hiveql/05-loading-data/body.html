1 The story

“Why does the customers table have 4,000 customers?”

Before you start: you need the orders_ext table from Lesson 2.2 and the SerDe ideas from Lesson 2.4.

TiffinGo has exactly 2,000 customers. Kabir’s nightly script loads the customer file into Hive, but one night the job is retried after a network blip. Next morning the dashboard shows 4,000 customers, and Riya notices that a file in the landing folder has vanished after a different load.

K> Sir, I only ran LOAD DATA twice. Shouldn’t Hive notice it is the same file? A> No. LOAD DATA … INTO simply puts the file into the table’s folder. The second time, a file with that name already exists, so Hive keeps both and renames the new one customers_day1_copy_1.csv. Two files, 4,000 rows. Hive does not check contents, schema or duplicates. R> And my file that disappeared? A> Without the word LOCAL, LOAD moves the file from the source path into the table; with LOCAL it copies from the server’s local disk. Today you will learn every way to fill a table: LOAD (copy or move), INSERT INTO and OVERWRITE, CREATE TABLE AS SELECT and the multi-insert that writes three tables in one scan. And how to make loads safe to re-run.
2 Definition

Loading data into Hive tables

Formal definition (write this in exams)

Data enters a Hive table in two ways. LOAD DATA [LOCAL] INPATH 'path' [OVERWRITE] INTO TABLE t is a pure file operation: it copies (LOCAL) or moves files into the table’s location without parsing or validating them. INSERT INTO | OVERWRITE TABLE t SELECT …, INSERT INTO t VALUES …, CREATE TABLE … AS SELECT (CTAS) and the multi-table form FROM src INSERT … INSERT … run a query whose results are serialized in the target table’s format and written as new files; OVERWRITE replaces existing data, INTO appends.

In simple words

LOAD just puts files into the table’s folder: quick, but nothing is checked. INSERT and CTAS run a query and write fresh files in the table’s own format. OVERWRITE replaces, INTO adds.

Words you’ll meet in this lesson

LOCALWith LOAD: the path is on HiveServer2’s local disk and the file is copied. Without: the path is in the cluster file system and the file is moved.
OVERWRITEDelete the existing data of the table (or partition) before writing.
CTASCREATE TABLE … AS SELECT: new table with the query’s columns and rows.
Multi-insertFROM src INSERT … INSERT …: read the source once, write several tables.
IdempotentRunning it twice gives the same result as once. Essential for retried jobs.
Staging directory.hive-staging_…: where INSERT writes before moving files into place.
Small filesMany tiny files in a table: slow to list and read. Each INSERT … VALUES adds one.
copy_NSuffix Hive adds when a file of the same name already exists in the table folder.

LEVELS> Loading data at three levels L1> Putting groceries in a cupboard
  • LOAD DATA = putting the bags in the cupboard as they are. Fast, no checking. Put the same bag twice and you have two.
  • INSERT … SELECT = cooking: take ingredients from one cupboard, prepare them, store the dish in another.
  • OVERWRITE = empty the shelf first, then put the new food in. Running it twice gives the same result.
  • CTAS = buy a new box and fill it in one step.
L2> What each statement does
  • LOAD DATA LOCAL INPATH 'p' INTO TABLE t: copies files from the HiveServer2 machine’s local disk into the table folder.
  • LOAD DATA INPATH 'p' INTO TABLE t: moves files that are already in the table’s file system (HDFS, or here the local FS).
  • … OVERWRITE INTO TABLE: removes the old files first.
  • INSERT INTO t SELECT … appends query results; INSERT OVERWRITE TABLE t SELECT … replaces them. Both run a Tez job and write new files (000000_0, …).
  • INSERT INTO t VALUES (…): a few literal rows; each statement makes a new small file.
  • CREATE TABLE t STORED AS ORC AS SELECT … (CTAS): creates the table from the query’s columns and fills it.
  • FROM src INSERT … INSERT …: one scan of src, several targets.
L3> The details that bite in production
  • LOAD does not validate anything: loading a JSON file into a CSV table succeeded and produced NULL ids.
  • skip.header.line.count applies to every file in the folder: the first line of the JSON file was silently dropped (2,119 rows, not 2,120).
  • File names: a second file with the same name becomes …_copy_1; repeated INSERTs make 000000_0_copy_1, _copy_2: the start of the small-files problem.
  • Staging: INSERT writes to a .hive-staging_… folder first and moves the files in at the end, so readers never see half-written results.
  • Statistics: CTAS and INSERT update numRows automatically (8 rows for city_sales), which helps the optimiser.
  • Idempotency: INSERT OVERWRITE and LOAD … OVERWRITE give the same result when re-run; INSERT INTO and LOAD … INTO do not.
/LEVELS EXAM> “Difference between LOAD DATA LOCAL and LOAD DATA.” LOCAL copies a file from the local file system of the HiveServer2 host; without LOCAL the file is moved within HDFS. Add: LOAD does not validate the data, OVERWRITE replaces existing files, and INSERT … SELECT is used when data must be transformed or converted to another format.
3 Types and ways to use it

Loading patterns in a real pipeline

Landing → raw

Files are dropped into a folder by an ingestion tool. An external raw table simply points at the folder; nothing is loaded at all.

No LOAD needed

Raw → curated

INSERT OVERWRITE TABLE curated SELECT CAST(…) … FROM raw. Parses, types, cleans and writes ORC. Re-run safe.

Most common

Curated → mart

CTAS or INSERT OVERWRITE of aggregates such as daily city sales for dashboards.

Reports

Fan-out

A multi-insert splits one large source into several tables (by payment type, region…) in one scan.

Efficient

WARN> A retried job that uses INSERT INTO or LOAD … INTO duplicates data silently. Write loads so that a re-run produces the same result: OVERWRITE a table or a partition (Module 5), or MERGE on a key (Module 7).
4 Step by step

Every way to load, tested

All outputs are real, from the Hive 4.2.1 lab.

  1. Step 1 · LOAD the same file twice

    CREATE TABLE cust_load (customer_id INT, name STRING, city STRING, state STRING,
  joined_on DATE, plan STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
TBLPROPERTIES ('skip.header.line.count'='1');
LOAD DATA LOCAL INPATH '/data/tiffingo/incoming/customers_day1.csv' INTO TABLE cust_load;
SELECT COUNT(*) AS after_first FROM cust_load;
LOAD DATA LOCAL INPATH '/data/tiffingo/incoming/customers_day1.csv' INTO TABLE cust_load;
SELECT COUNT(*) AS after_same_file_again FROM cust_load;
    +--------------+ | after_first | +--------------+ | 2000 | +--------------+ +------------------------+ | after_same_file_again | +------------------------+ | 4000 | +------------------------+
    No warning, just double the rows. The table folder now holds customers_day1.csv and customers_day1_copy_1.csv. This is Kabir’s 4,000 customers.

  2. Step 2 · LOAD without LOCAL moves the file; OVERWRITE replaces

    LOAD DATA INPATH 'file:///data/tiffingo/incoming/customers_day2.csv'
  OVERWRITE INTO TABLE cust_load;
SELECT COUNT(*) AS after_overwrite FROM cust_load;
    +------------------+ | after_overwrite | +------------------+ | 2000 | +------------------+ $ ls /data/tiffingo/incoming customers_day1.csv ← customers_day2.csv has gone
    OVERWRITE removed both old files, so the count is right again: 2,000. And the source file was moved into the table folder, which is what surprised Riya. On HDFS this is a cheap rename.

  3. Step 3 · LOAD checks nothing

    LOAD DATA LOCAL INPATH '/data/tiffingo/restaurants/restaurants.json' INTO TABLE cust_load;
SELECT COUNT(*) AS rows_total, COUNT(customer_id) AS with_id FROM cust_load;
SELECT customer_id, name, city FROM cust_load WHERE customer_id IS NULL LIMIT 2;
    +-------------+----------+ | rows_total | with_id | +-------------+----------+ | 2119 | 2000 | +-------------+----------+ +--------------+-----------------------------+--------------------+ | customer_id | name | city | +--------------+-----------------------------+--------------------+ | NULL | "name": "Nair Bhojanalay" | "city": "Mumbai" | | NULL | "name": "Gupta Mess" | "city": "Thane" | +--------------+-----------------------------+--------------------+
    A JSON file loaded happily into a CSV table: 119 junk rows with NULL ids. Why 119, not 120? skip.header.line.count is applied to every file, so the first restaurant was dropped as a “header”.

  4. Step 4 · CREATE TABLE AS SELECT

    CREATE TABLE city_sales STORED AS ORC AS
SELECT city, COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders_ext WHERE status = 'DELIVERED' GROUP BY city;
SELECT * FROM city_sales ORDER BY revenue DESC LIMIT 3;
DESCRIBE city_sales;
    +------------------+--------------------+---------------------+ | city_sales.city | city_sales.orders | city_sales.revenue | +------------------+--------------------+---------------------+ | Mumbai | 9250 | 2712820 | | Bengaluru | 8535 | 2499060 | | Pune | 7269 | 2148270 | +------------------+--------------------+---------------------+ +-----------+------------+----------+ | col_name | data_type | comment | +-----------+------------+----------+ | city | string | | | orders | bigint | | | revenue | bigint | | +-----------+------------+----------+
    Columns and types come from the query: COUNT(*) and SUM(int) are BIGINT. The text orders became an ORC file 000000_0, and Hive recorded numRows 8 automatically.

  5. Step 5 · One scan, three tables

    FROM orders_ext o
INSERT OVERWRITE TABLE upi_orders  SELECT o.order_id, o.city, o.amount WHERE o.payment = 'UPI'
INSERT OVERWRITE TABLE cod_orders  SELECT o.order_id, o.city, o.amount WHERE o.payment = 'COD'
INSERT OVERWRITE TABLE payment_mix SELECT o.payment, COUNT(*) GROUP BY o.payment;
    Map 1 .......... container SUCCEEDED 1 1 … Reducer 2 ...... container SUCCEEDED 1 1 … Reducer 3 ...... container SUCCEEDED 1 1 … Reducer 4 ...... container SUCCEEDED 1 1 … Reducer 5 ...... container SUCCEEDED 1 1 … VERTICES: 05/05 [==========================>>] 100% ELAPSED TIME: 2.19 s INFO : RECORDS_IN_Map_1: 50002 INFO : RECORDS_OUT_1_tiffingo.upi_orders: 30011 INFO : RECORDS_OUT_2_tiffingo.cod_orders: 5005 INFO : RECORDS_OUT_3_tiffingo.payment_mix: 4 35,020 rows affected (2.655 seconds)
    One Map vertex read the 50,002 rows once and fed three outputs. Three separate INSERTs would have scanned the source three times.

  6. Step 6 · INSERT … VALUES and the small-files trap

    INSERT INTO payment_mix VALUES ('BNPL', 0), ('Gift card', 0);
INSERT INTO payment_mix (payment) VALUES ('Crypto');
SELECT * FROM payment_mix ORDER BY orders DESC;
    +----------------------+---------------------+ | payment_mix.payment | payment_mix.orders | +----------------------+---------------------+ | Crypto | NULL | | UPI | 30011 | | Card | 9894 | | Wallet | 5092 | | COD | 5005 | | BNPL | 0 | | Gift card | 0 | +----------------------+---------------------+ $ find …/payment_mix -type f -not -name '.*' 000000_0 000000_0_copy_1 000000_0_copy_2
    A column list lets you omit columns (orders is NULL for Crypto). Each INSERT statement created a new file: three files for seven rows. A loop that inserts one row at a time would create thousands. Notice too that the NULL sorted first in this DESC order.
5 See it happen

Six loads, two views

Left: Beeline’s real output. Right: the files in the table folder after each statement.

Six loads and what they did to the folder 6 steps
What you see
  1. Kabir loads the customer file: 2,000 rows.
  2. The job is retried and loads the same file again: 4,000 rows, no warning.
  3. He switches to LOAD without LOCAL and with OVERWRITE: 2,000 rows again, but the source file is gone from incoming.
  4. A JSON file loads into the CSV table without any error, and the counts no longer add up.
  5. A multi-insert writes three tables from one read of the orders: 35,020 rows written.
  6. Two small INSERT … VALUES statements leave three files in the table folder.
Behind the screen
  1. LOCAL copies the file from HiveServer2’s disk into the table folder.
  2. The name already exists, so the copy is renamed customers_day1_copy_1.csv. Both files are read.
  3. OVERWRITE deletes the old files; without LOCAL the source file is moved (renamed), not copied.
  4. LOAD never parses. The JSON lines become rows with NULL ids, and the header rule removes one line from each file.
  5. One Map vertex reads the source once and routes rows to three outputs, staged and then moved into place.
  6. Each INSERT writes at least one new file. Many tiny files slow down listing and reading.

Three live scenarios follow: retry-safe loads, raw-to-curated pipelines and the small-files problem.

Real-time scenario 1

The retried job that doubled revenue

Retries are normal in schedulers. Loads must be written so that a retry is harmless. (Row counts illustrative.)

Idempotent loads 5 steps
Animated example
  1. The nightly job appends one day of orders with INSERT INTO.
  2. A retry appends the same day again. Revenue for that day doubles silently.
  3. INSERT OVERWRITE of exactly the day being loaded makes a retry replace the data.
  4. Tables that receive updates use MERGE on the business key.
  5. A count vs distinct-key check after each load catches duplicates immediately.
Real-time scenario 2

From raw text to a curated ORC table

The workhorse of Hive pipelines is INSERT OVERWRITE … SELECT from a raw table.

Raw to curated 5 steps
Animated example
  1. The raw external text table is fine for landing but slow and untyped for reports.
  2. One INSERT OVERWRITE casts, filters and writes the data in ORC.
  3. Readers get typed, compressed data, and the job is safe to re-run.
  4. The same job counts rows it rejects: in our data, 2 orders (an amount “abc” and a date in the wrong layout).
  5. A typical night: files land, curation runs, then mart tables are rebuilt.
Real-time scenario 3 · advanced

How INSERT … VALUES creates a small-files problem

One file per statement is harmless three times and disastrous a hundred thousand times. (Volumes illustrative.)

Small files 5 steps
Animated example
  1. A job inserts a few rows every minute with INSERT … VALUES.
  2. After 90 days the table has 129,600 tiny files; queries spend their time opening files.
  3. Batch the writes so each insert writes large files.
  4. Rewrite existing small files into large ones, or rely on compaction for ACID and Iceberg tables.
  5. Hive is a batch engine; streams should be landed and compacted, not inserted row by row.
6 Real-world use

Loading in daily pipelines

1. Nightly curated tables

Most warehouse jobs are INSERT OVERWRITE … SELECT from raw into curated tables, partition by partition. A failed night is simply re-run.

Raw→INSERT OVERWRITE→Curated ORC

2. Splitting a big feed

A payments feed is split into UPI, card and wallet tables in one multi-insert, reading terabytes once instead of three times.

Payments feed→Multi-insert→3 tables

3. Analyst working tables

Analysts create a filtered copy with CTAS (“orders of the Diwali week”) in their sandbox and explore it quickly, without touching shared tables.

Big table→CTAS→Sandbox table

4. Moving landed files

When a transfer tool drops a ready-made file in HDFS, LOAD DATA INPATH … OVERWRITE moves it into the table in milliseconds, with no job.

Transfer tool→LOAD (move)→Table

5. Post-load quality checks

After every load a job compares row counts with the source and with distinct keys, and stops the pipeline if they differ.

Load→Checks→Publish or stop
