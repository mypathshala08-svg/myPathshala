1 The story

“Analysts can see customers’ names”

Before you start: views (9.2), ACID updates (7.1) and the metastore (10.1).

An internal audit at TiffinGo found that every Beeline user can read every table, including customer names. Riya’s analysts should see cities and plans, not names; Kabir’s loaders should write orders, not drop tables. Arjun Sir has a week to fix it.

R> Sir, can’t we just make a view without the names and tell analysts to use it? A> Telling is not enforcing. Hive needs authorization: rules about who may SELECT, INSERT, UPDATE or DELETE on which table or view. The built-in option is SQL-standard based authorization with GRANT, REVOKE and roles. Large platforms use Apache Ranger for central policies, column masking and audit. K> And how does Hive know that I am Kabir? A> That is authentication: Kerberos or LDAP in production. We will switch authorization on in our lab, build roles, collect the real error messages, discover two surprises, and then show why our lab, with authentication set to NONE, is still not secure. All outputs are real, from Hive 4.2.1.
2 Definition

Authentication, authorization and Hive security

Formal definition (write this in exams)

Authentication establishes the identity of a client connecting to HiveServer2 (Kerberos, LDAP, PAM, custom providers, or none). Authorization decides which operations that identity may perform. Hive’s SQL-standard based authorization (SQLStdHiveAuthorizerFactory) enforces SELECT, INSERT, UPDATE and DELETE privileges and object ownership on databases, tables and views, managed with GRANT, REVOKE and roles, and disables risky commands (dfs, ADD JAR, TRANSFORM, changing security settings) for non-admin users. Apache Ranger replaces it in most enterprise platforms with centrally managed policies, column masking, row-level filtering and audit logs, while Kerberos secures identities across Hadoop services.

In simple words

Authentication answers “who are you?”, authorization answers “what are you allowed to do?”. Hive can enforce table permissions with GRANT and REVOKE, or with Apache Ranger policies, but both only work if users are properly authenticated, usually with Kerberos or LDAP.

Words you’ll meet in this lesson

doAsRun file access as the end user (true) or the Hive service user (false).

LEVELS> Hive security at three levels L1> A building with guards
  • Authentication is the ID card at the entrance: proving who you are.
  • Authorization is which rooms your card opens: what you may read or change.
  • Audit is the visitor log: who entered which room, and when.
L2> The options in Hive
  • Authentication (HiveServer2): hive.server2.authentication = NONE, LDAP, KERBEROS, PAM, CUSTOM; plus TLS for the connection.
  • Authorization: SQL-standard based (GRANT/REVOKE, roles public and admin), storage-based (file permissions), or Apache Ranger (central policies, masking, row filters, audit).
  • doAs: with hive.server2.enable.doAs=false queries access files as the Hive service user, which is required for SQL-standard and Ranger authorization to be meaningful.
L3> What the lab showed
  • Listing hive in hive.users.in.admin.role on HiveServer2 was not enough: “hive doesn’t belong to role admin” until the metastore had the setting too.
  • Analysts were blocked from dfs, ADD JAR, TRANSFORM, CREATE TABLE and from switching authorization off; a permanent UDF still worked.
  • UPDATE on an ACID table asked for the DELETE privilege (Hive 4 splits updates into delete + insert). With authentication NONE, anyone typing -n hive became admin.
/LEVELS EXAM> “How do you secure Hive?” Authenticate users at HiveServer2 (Kerberos or LDAP, with TLS), authorize with SQL-standard GRANT/REVOKE and roles or with Ranger policies (column masking, row filters, audit), set doAs=false so access goes through the authorizer, and expose sensitive data through views or masks.

WARN> In SQL-standard mode there are no column-level grants. Hide columns with views (as here) or use Ranger’s column policies and masking. And because Hive checks privileges on the view, analysts can read a view without any privilege on its base table.
4 Step by step

Switching authorization on, role by role

All outputs are real, from Hive 4.2.1. Users connect with beeline -n riya, -n kabir or -n hive. Long error prefixes are shortened to “FAILED:”.

  1. Step 1 · Turn authorization on

    services:
  hiveserver2:
    environment:
      SERVICE_OPTS: >-
        -Xmx1G -Dhive.metastore.uris=thrift://metastore:9083
        -Djavax.jdo.option.ConnectionDriverName=org.postgresql.Driver
        -Djavax.jdo.option.ConnectionURL=jdbc:postgresql://postgres:5432/metastore_db
        -Djavax.jdo.option.ConnectionUserName=hive -Djavax.jdo.option.ConnectionPassword=hivepw
        -Dhive.security.authorization.enabled=true
        -Dhive.security.authorization.manager=org.apache.hadoop.hive.ql.security.authorization.plugin.sqlstd.SQLStdHiveAuthorizerFactory
        -Dhive.security.authenticator.manager=org.apache.hadoop.hive.ql.security.SessionStateUserAuthenticator
        -Dhive.users.in.admin.role=hive
        -Dhive.server2.enable.doAs=false
  metastore:
    environment:
      SERVICE_OPTS: >-
        -Xmx1G -Djavax.jdo.option.ConnectionDriverName=org.postgresql.Driver
        -Djavax.jdo.option.ConnectionURL=jdbc:postgresql://postgres:5432/metastore_db
        -Djavax.jdo.option.ConnectionUserName=hive -Djavax.jdo.option.ConnectionPassword=hivepw
        -Dhive.compactor.initiator.on=true -Dhive.compactor.cleaner.on=true
        -Dhive.users.in.admin.role=hive
    HiveServer2 gets four settings: authorization enabled, the SQL-standard authorizer, an authenticator that takes the session user name, and hive.users.in.admin.role=hive. doAs=false makes HiveServer2 read files as its own service user, so the authorizer, not file permissions, decides. In a real cluster these lines go into hive-site.xml.

  2. Step 2 · Surprise: the admin role lives in the metastore

    SET hive.security.authorization.enabled;
SHOW CURRENT ROLES;
SET ROLE ADMIN;

-- after adding -Dhive.users.in.admin.role=hive to the METASTORE too and restarting it:
SET ROLE ADMIN;
SHOW CURRENT ROLES;
    +-------------------------------------------+ | set | +-------------------------------------------+ | hive.security.authorization.enabled=true | +-------------------------------------------+ +---------+ | role | +---------+ | public | +---------+ FAILED: Execution Error, return code 40000 from org.apache.hadoop.hive.ql.ddl.DDLTask. hive doesn't belong to role admin +--------+ | role | +--------+ | admin | +--------+
    Roles and memberships are stored in the metastore (ROLES, ROLE_MAP). The metastore adds the users of hive.users.in.admin.role to the admin role from its own configuration; with the setting only on HiveServer2, ROLE_MAP stayed empty and SET ROLE ADMIN failed. Even admins start every session in the public role and must SET ROLE ADMIN explicitly.

  3. Step 3 · Deny by default

    SELECT COUNT(*) FROM customers;
    FAILED: HiveAccessControlException Permission denied: Principal [name=riya, type=USER] does not have following privileges for operation QUERY [[SELECT] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.customers]]
    With authorization on, a new user has only the public role and no privileges: the query is refused at compile time, naming the principal, the missing privilege and the object (hive.tiffingo.customers: catalog, database, table).

  4. Step 4 · A safe view, a role and grants

    SET ROLE ADMIN;
CREATE OR REPLACE VIEW v_customers_safe AS SELECT customer_id, city, plan, joined_on FROM customers;
CREATE ROLE analyst;
GRANT SELECT ON TABLE v_customers_safe TO ROLE analyst;
GRANT SELECT ON TABLE orders TO ROLE analyst;
GRANT ROLE analyst TO USER riya;
SHOW ROLE GRANT USER riya;
SHOW GRANT ROLE analyst ON TABLE v_customers_safe;
    +----------+---------------+----------------+----------+ | role | grant_option | grant_time | grantor | +----------+---------------+----------------+----------+ | analyst | false | 1793279573000 | hive | | public | false | 0 | | +----------+---------------+----------------+----------+ +-----------+-------------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+ | database | table | partition | column | principal_name | principal_type | privilege | grant_option | grant_time | grantor | +-----------+-------------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+ | tiffingo | v_customers_safe | | | analyst | ROLE | SELECT | false | 1793279573000 | hive | +-----------+-------------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+
    The view drops name, the personal column. Privileges go to the role, and people join roles: when Riya’s team grows, nobody touches table grants. SHOW GRANT lists who has what, with grantor and time, which is handy for access reviews.

  5. Step 5 · The analyst’s view of the world

    SHOW CURRENT ROLES;
SELECT city, COUNT(*) AS customers FROM v_customers_safe GROUP BY city ORDER BY customers DESC LIMIT 3;
SELECT name FROM customers LIMIT 1;
    +----------+ | role | +----------+ | analyst | | public | +----------+ +------------+------------+ | city | customers | +------------+------------+ | Mumbai | 405 | | Bengaluru | 377 | | Pune | 316 | +------------+------------+ FAILED: HiveAccessControlException Permission denied: Principal [name=riya, type=USER] does not have following privileges for operation QUERY [[SELECT] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.customers]]
    Riya’s session has analyst and public. She can aggregate through the view (Mumbai 405 customers) even though she has no privilege on the base table: Hive checks the view. A direct query for names is denied.

    Every escape hatch is closed: writing without INSERT, file-system commands and ADD JAR need the ADMIN PRIVILEGE, security settings cannot be changed at run time, admin cannot be self-assigned, creating tables needs ownership of the database, and TRANSFORM is disallowed (Lesson 9.3). Permanent functions registered by an admin remain usable.

  7. Step 7 · Write privileges, and a Hive 4 surprise

    -- hive:  GRANT SELECT, INSERT ON TABLE orders_tx TO USER kabir;  SHOW GRANT USER kabir ON TABLE orders_tx;
-- kabir: INSERT INTO orders_tx VALUES (999000010, 7, 'Pune', 10.00, DATE '2026-10-29', 'NEW');
--        SELECT COUNT(*) FROM orders_tx WHERE order_id = 999000010;
-- kabir: UPDATE orders_tx SET status = 'CANCELLED' WHERE order_id = 999000010;
-- hive:  GRANT UPDATE ON TABLE orders_tx TO USER kabir;     → kabir's UPDATE still fails
-- hive:  GRANT DELETE ON TABLE orders_tx TO USER kabir;     → kabir's UPDATE works
    +-----------+------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+ | database | table | partition | column | principal_name | principal_type | privilege | grant_option | grant_time | grantor | +-----------+------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+ | tiffingo | orders_tx | | | kabir | USER | INSERT | false | 1793279674000 | hive | | tiffingo | orders_tx | | | kabir | USER | SELECT | false | 1793279674000 | hive | +-----------+------------+------------+---------+-----------------+-----------------+------------+---------------+----------------+----------+ +------+ | _c0 | +------+ | 1 | +------+ FAILED: HiveAccessControlException Permission denied: Principal [name=kabir, type=USER] does not have following privileges for operation QUERY [[DELETE] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.orders_tx]] -- after UPDATE + DELETE grants: +------------+ | status | +------------+ | CANCELLED | +------------+
    Kabir could insert and check his row. His UPDATE was refused for missing DELETE, and still refused after an UPDATE grant. Hive 4 executes ACID updates as delete + insert (hive.split.update=true in our lab), and authorization checks those operations. Grant writers INSERT, UPDATE and DELETE together on tables they maintain.

  8. Step 8 · Why authentication matters

    SET hive.server2.authentication;              -- NONE in our lab
SET ROLE ADMIN;
SELECT current_user() AS who, COUNT(*) AS customers FROM customers;

-- clean-up: REVOKE ROLE analyst FROM USER riya;  then riya queries the view again
    hive.server2.authentication=NONE +-------+------------+ | who | customers | +-------+------------+ | hive | 2000 | +-------+------------+ +---------+---------------+-------------+----------+ | role | grant_option | grant_time | grantor | +---------+---------------+-------------+----------+ | public | false | 0 | | +---------+---------------+-------------+----------+ FAILED: HiveAccessControlException Permission denied: Principal [name=riya, type=USER] does not have following privileges for operation QUERY [[SELECT] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.v_customers_safe]]
    With hive.server2.authentication=NONE, HiveServer2 believes any user name a client sends. Anyone who types -n hive becomes admin and reads all 2,000 customers. Every grant above is only as strong as authentication: production clusters use Kerberos or LDAP (with TLS). Revoking the role took effect at once: Riya’s next query on the view was denied.

6 Real-world use

Hive security at work

1. Protecting personal data

Names, phones and addresses are hidden behind views or Ranger masks to meet privacy laws such as India’s DPDP Act and GDPR.

PII columns→view / mask→Compliant access

2. Team-based access

Analyst, engineer and data-science roles map to directory groups, so joining a team grants the right access automatically.

LDAP group→role→Privileges

3. Audit trails

Ranger audit logs record every allowed and denied access, used in security investigations and compliance reports.

Access→audit log→Evidence

4. Multi-tenant platforms

Different business units share one cluster but only see their own databases, enforced by policies.

Shared cluster→policies→Isolated tenants

5. Safer operations

Disabling dfs, ADD JAR and TRANSFORM for normal users prevents accidental or malicious use of cluster resources.

User→restricted→Stable cluster
