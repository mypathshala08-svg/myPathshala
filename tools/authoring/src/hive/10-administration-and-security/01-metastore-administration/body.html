1 The story

“Who looks after the metastore?”

Before you start: architecture and the metastore (1.3), managed vs external tables (2.2), partition design (5.4). Basic SQL on PostgreSQL helps.

TiffinGo’s platform team is preparing a Hive upgrade. The checklist has one scary line: “Back up the metastore”. Kabir realises nobody on the team has ever looked inside it.

K> Sir, the metastore is just a service, right? If it breaks, we restart it. A> The service you can restart. The database behind it is different: every table name, column, partition, location, statistic and function of every database lives there. Hive, Spark and Trino all depend on it. The data files without the metastore are just folders. R> So administering it means…? A> Knowing its schema version (schematool), being able to read it with SQL for health checks, backing it up and proving the restore works, and knowing what users see when it is down. We will do all four on our lab’s PostgreSQL metastore. All outputs are real, from Hive 4.2.1.
2 Definition

Metastore administration

Formal definition (write this in exams)

The Hive Metastore (HMS) is the service that stores and serves metadata for Hive and other engines: databases, tables, columns, partitions, storage descriptors (location, format, SerDe), statistics, constraints, functions, transactions and locks. It persists this metadata in a relational database through JDO/DataNucleus. Metastore administration covers creating and upgrading that database schema with schematool, configuring clients (hive.metastore.uris) and the warehouse locations, running housekeeping (compaction initiator, statistics, partition management), monitoring and scaling the service, and backing up and restoring the database.

In simple words

The metastore is Hive’s catalogue: a service plus a normal relational database that remembers every table and partition. Administering it means keeping its schema at the right version, checking its health, backing it up and keeping it running, because every Hive query and many other engines depend on it.

LEVELS> Metastore administration at three levels L1> The library catalogue
  • The data files are the books; the metastore is the catalogue that says what each book is and on which shelf it stands.
  • Without the catalogue the books still exist, but nobody can find them by name.
  • Administrators keep the catalogue correct, backed up and available.
L2> The parts you administer
  • The service: Hive Metastore (HMS), Thrift on port 9083; clients find it through hive.metastore.uris.
  • The database: MySQL, PostgreSQL, Oracle or SQL Server (Derby only for tests). Tables such as DBS, TBLS, SDS, PARTITIONS, TABLE_PARAMS, FUNCS.
  • schematool: -info, -validate, -initSchema, -upgradeSchema [-dryRun].
  • Backups: the database’s own tools (pg_dump, mysqldump), taken before every upgrade and regularly.
L3> What the lab showed
  • The Hive 4.2.1 image reported distribution and schema version 4.2.0; -upgradeSchema -dryRun: “No schema upgrade required”.
  • 84 metastore tables held 74 Hive objects and 2,100 partitions; a SQL health check found orders_by_cust with 2,000 files of 0.8 KB on average.
  • A 1.2 MB pg_dump restored into a new database and passed -validate. With the metastore stopped, HiveServer2 could not even open a session.
/LEVELS EXAM> “What is stored in the Hive metastore and how do you back it up?” Databases, tables, columns, partitions, locations, formats, statistics, functions, transactions and locks, in a relational database (MySQL/PostgreSQL in production). Back it up with the database’s tools (pg_dump, mysqldump), always before upgrades, and test restores with schematool -validate.

WARN> Never edit metastore tables by hand on a running system except in a documented emergency, with a backup. Use HiveQL (ALTER TABLE, MSCK REPAIR) or the HMS API so that caches, events and other engines stay consistent. Reading them with SQL for reports and health checks is fine.
4 Step by step

A metastore health check, a backup and an outage

All outputs are real: schematool ran in the metastore container, SQL in the PostgreSQL container (metastore_db), HiveQL in Beeline.

  1. Step 1 · Which schema version?

    schematool -dbType postgres -info \
  -url jdbc:postgresql://postgres:5432/metastore_db -driver org.postgresql.Driver \
  -userName hive -passWord ********
    Metastore connection URL: jdbc:postgresql://postgres:5432/metastore_db Metastore connection Driver : org.postgresql.Driver Metastore connection User: hive Hive distribution version: 4.2.0 Metastore schema version: 4.2.0
    The schema is at 4.2.0, and so is the “distribution version” this tool reports, even though the image is Hive 4.2.1: patch releases usually do not change the metastore schema. Always run -info before and after an upgrade.

  2. Step 2 · Validate, and preview an upgrade

    schematool -dbType postgres … -validate
schematool -dbType postgres … -upgradeSchema -dryRun
    Starting metastore validation Validating schema version [SUCCESS] Validating sequence number for SEQUENCE_TABLE [SUCCESS] Validating metastore schema tables [SUCCESS] Validating DFS locations [SUCCESS] Validating columns for incorrect NULL values. [SUCCESS] Done with metastore validation: [SUCCESS] Upgrading from the version 4.2.0 No schema upgrade required from version 4.2.0
    -validate checks the version row, internal sequences, the presence of every expected table, the locations, and columns that must not be NULL. -dryRun lists the SQL upgrade scripts without running them: here none were needed. On a real upgrade you would read those scripts, back up, then run without -dryRun.

  3. Step 3 · Inside the metastore database

    SELECT COUNT(*) AS metastore_tables FROM information_schema.tables WHERE table_schema = 'public';
SELECT "DB_ID", "NAME", "DB_LOCATION_URI", "DB_MANAGED_LOCATION_URI", "OWNER_NAME" FROM "DBS";
SELECT "TBL_TYPE", COUNT(*) FROM "TBLS" GROUP BY 1 ORDER BY 2 DESC;
    metastore_tables ------------------ 84 (1 row) DB_ID | NAME | DB_LOCATION_URI | DB_MANAGED_LOCATION_URI | OWNER_NAME -------+----------+-------------------------------------------+-------------------------+------------ 1 | default | file:/opt/hive/data/warehouse | | public 2 | tiffingo | file:/opt/hive/data/warehouse/tiffingo.db | | hive (2 rows) TBL_TYPE | count -------------------+------- EXTERNAL_TABLE | 61 MANAGED_TABLE | 10 VIRTUAL_VIEW | 2 MATERIALIZED_VIEW | 1 (4 rows)
    An ordinary PostgreSQL schema of 84 tables. DBS has our two databases with their locations; TBLS holds 74 objects from this course: 61 external tables, 10 managed (transactional) tables, 2 views and 1 materialized view. Column names are upper case and quoted, a DataNucleus convention.

  4. Step 4 · Where a table lives

    SELECT t."TBL_NAME", t."TBL_TYPE", s."LOCATION", s."INPUT_FORMAT"
FROM "TBLS" t JOIN "SDS" s ON t."SD_ID" = s."SD_ID" JOIN "DBS" d ON t."DB_ID" = d."DB_ID"
WHERE d."NAME" = 'tiffingo' AND t."TBL_NAME" IN ('orders', 'orders_by_day', 'orders_tx');

SELECT t."TBL_NAME", COUNT(p."PART_ID") AS partitions
FROM "TBLS" t JOIN "PARTITIONS" p ON p."TBL_ID" = t."TBL_ID" GROUP BY 1 ORDER BY 2 DESC LIMIT 5;
    TBL_NAME | TBL_TYPE | LOCATION | INPUT_FORMAT ---------------+----------------+---------------------------------------------------------+------------------------------------------------- orders | EXTERNAL_TABLE | file:/opt/hive/data/warehouse/tiffingo.db/orders | org.apache.hadoop.hive.ql.io.orc.OrcInputFormat orders_by_day | EXTERNAL_TABLE | file:/opt/hive/data/warehouse/tiffingo.db/orders_by_day | org.apache.hadoop.hive.ql.io.orc.OrcInputFormat orders_tx | MANAGED_TABLE | file:/opt/hive/data/warehouse/tiffingo.db/orders_tx | org.apache.hadoop.hive.ql.io.orc.OrcInputFormat (3 rows) TBL_NAME | partitions ----------------+------------ orders_by_cust | 2000 orders_by_day | 30 orders_dyn | 30 cust_by_ref | 9 orders_dc | 8 (5 rows)
    A table row points to a storage descriptor (SDS) with its location, input format and SerDe; each partition has its own storage descriptor too. The partition count per table is a key health number: orders_by_cust, the over-partitioned example from Lesson 5.4, has 2,000 partitions for 50,000 rows.

  5. Step 5 · A small-files report straight from the metastore

    WITH f AS (
  SELECT t."TBL_NAME" AS tbl, pp."PARAM_KEY" AS k, pp."PARAM_VALUE"::bigint AS v
  FROM "TBLS" t JOIN "PARTITIONS" p ON p."TBL_ID" = t."TBL_ID"
  JOIN "PARTITION_PARAMS" pp ON pp."PART_ID" = p."PART_ID"
  WHERE pp."PARAM_KEY" IN ('numFiles', 'totalSize'))
SELECT tbl, SUM(v) FILTER (WHERE k = 'numFiles') AS files,
       ROUND(SUM(v) FILTER (WHERE k = 'totalSize') / 1024.0 / 1024, 1) AS mb,
       ROUND(SUM(v) FILTER (WHERE k = 'totalSize') / 1024.0 / NULLIF(SUM(v) FILTER (WHERE k = 'numFiles'), 0), 1) AS kb_per_file
FROM f GROUP BY tbl ORDER BY files DESC LIMIT 5;
    tbl | files | mb | kb_per_file ----------------+-------+-----+------------- orders_by_cust | 2000 | 1.6 | 0.8 orders_by_day | 30 | 0.4 | 13.3 orders_dyn | 30 | 0.4 | 13.3 cust_by_ref | 9 | 0.0 | 0.4 orders_dc | 8 | 0.0 | 2.0 (5 rows)
    Statistics stored per partition (numFiles, totalSize) let you scan the whole warehouse for small files without touching HDFS. orders_by_cust: 2,000 files of 0.8 KB each. Platform teams run such reports nightly; remember that the numbers are only as fresh as the statistics (Lesson 8.2).

  6. Step 6 · Back up, and prove the restore

    pg_dump -U hive -Fc metastore_db -f /tmp/hms_2026-10-29.dump
createdb -U hive metastore_restore_test
pg_restore -U hive -d metastore_restore_test /tmp/hms_2026-10-29.dump
schematool -dbType postgres -url jdbc:postgresql://postgres:5432/metastore_restore_test … -validate
    $ pg_dump -U hive -Fc metastore_db -f /tmp/hms_2026-10-29.dump 1226478 bytes /tmp/hms_2026-10-29.dump $ createdb -U hive metastore_restore_test && pg_restore -U hive -d metastore_restore_test /tmp/hms_2026-10-29.dump restored $ schematool -info / -validate against the restored copy Validating schema version Done with metastore validation: [SUCCESS] $ psql: tables in the copy 74 tables, 2100 partitions
    The whole lab catalogue is a 1.2 MB dump. Restored into a fresh database, it passed schematool validation and contained the same 74 tables and 2,100 partitions. A backup you have never restored is only a hope. Note that the dump contains metadata only: data files need their own protection (HDFS snapshots, object-store versioning).

  7. Step 7 · The metastore seen from Hive

    SET hive.metastore.uris;
SET hive.metastore.warehouse.dir;
SET hive.metastore.warehouse.external.dir;
SET metastore.schema.verification;
DESCRIBE DATABASE EXTENDED tiffingo;
ALTER DATABASE tiffingo SET DBPROPERTIES ('owner_team' = 'data-platform', 'pii' = 'yes');
DESCRIBE DATABASE EXTENDED tiffingo;      -- selected columns
    hive.metastore.uris=thrift://metastore:9083 hive.metastore.warehouse.dir=/opt/hive/data/warehouse hive.metastore.warehouse.external.dir is undefined metastore.schema.verification is undefined db_name | location | owner_name | parameters tiffingo | file:/opt/hive/data/warehouse/tiffingo.db | hive | -- after ALTER DATABASE … SET DBPROPERTIES tiffingo | file:/opt/hive/data/warehouse/tiffingo.db | hive | {owner_team=data-platform, pii=yes}
    HiveServer2 reaches the metastore at thrift://metastore:9083; managed tables go under /opt/hive/data/warehouse. Settings that live only in the metastore’s own configuration (metastore.schema.verification) show as undefined in a Hive session. Database properties are a cheap way to record ownership and data classification where every engine can read them.

  8. Step 8 · What users see when the metastore is down

    docker stop metastore
-- Beeline: connect and run SELECT COUNT(*) FROM customers;
docker start metastore      -- the same query works again after ~25 s
    Error: Could not open client transport with JDBC Uri: jdbc:hive2://localhost:10000/tiffingo: Failed to open new session: org.apache.hadoop.hive.ql.metadata.HiveException: MetaException(message:Could not connect to meta store using any of the URIs provided. Caused by: java.net.UnknownHostException: metastore
    With the metastore stopped, HiveServer2 could not even open a session: every query, by every user, failed with “Could not connect to meta store using any of the URIs provided”. After a restart everything worked again without touching HiveServer2. In production, run at least two metastore instances behind hive.metastore.uris and keep the database highly available.

6 Real-world use

Metastore administration at work

1. Backup and restore drills

Nightly dumps of the metastore database and quarterly restore drills are standard on production platforms.

Dump→restore test→Confidence

2. Version upgrades

Every Hive upgrade starts with schematool -info and a dry run against a restored copy of the metastore.

Copy→dry run→Safe upgrade

3. Platform reports

SQL on the metastore database lists tables per owner, partition counts, small-file hot spots and stale statistics.

Metastore DB→SQL→Dashboards

4. One catalogue for many engines

Spark, Trino, Impala and Flink use the same HMS, so its availability is a platform-wide service level.

Engines→HMS→One truth

5. Data governance

Database and table properties record owners and classifications that catalog tools such as Atlas or DataHub read.

Properties→catalog tool→Lineage
