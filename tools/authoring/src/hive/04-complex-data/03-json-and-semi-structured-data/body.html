1 The story

“The app team sends us JSON. Can Hive read it?”

Before you start: you need SerDes (2.4) and LATERAL VIEW (4.2).

TiffinGo’s mobile app writes every action as a JSON line: app opens, searches, coupons and orders. Each order event has a nested user object and an items list with dish, quantity and price. The product team wants revenue per city and the order rate on Android vs iOS. One upload was cut off half-way, so one line is broken JSON.

K> Sir, the file is 2,000 lines of JSON. Do I need to convert it to CSV first? A> No. There are two ways. Keep each line as one STRING column and pull fields out at query time with get_json_object or json_tuple. Or define a typed table with the JsonSerDe, where nested objects become STRUCT and lists become ARRAY columns. R> And the broken line? A> That is where the two ways differ, and we will see it fail for real. Today: path syntax and its limits, json_tuple, JsonSerDe, quarantining bad lines, turning JSON into an ORC table, and a quick look at URLs and XML. All outputs are real.
2 Definition

Semi-structured data in Hive

Formal definition (write this in exams)

Semi-structured data carries its own structure in the data itself (field names, nesting, optional fields), as in JSON or XML, rather than in a fixed table schema. Hive handles it in two ways: schema-on-read functions that parse a string column at query time (get_json_object, json_tuple, xpath, parse_url_tuple), and SerDes that map each record to typed columns when the table is read (JsonSerDe, including nested STRUCT and ARRAY types).

In simple words

JSON is text that describes itself: each value has a name, and values can sit inside other values. Hive can either look up one value at a time from the text, or read the text as a proper table with columns.

LEVELS> JSON in Hive at three levels L1> A form with boxes inside boxes
  • JSON stores data as name: value pairs. A value can be another object ("user": {"id": 1376}) or a list ("items": [ … ]).
  • To read a value you give its path: $.user.city means “start at the top, open user, take city”.
  • Hive can read the path in a query, or read the whole file as a table whose columns follow the JSON.
L2> Three tools
  • get_json_object(json, '$.path'): one value per call; supports .key, [index] and [*]; returns a STRING (lists come back as JSON text).
  • json_tuple(json, 'k1', 'k2', …): several top-level keys in one parse, used with LATERAL VIEW; nested objects need a second json_tuple.
  • JsonSerDe (org.apache.hive.hcatalog.data.JsonSerDe): a table definition where each JSON field is a typed column, including STRUCT and ARRAY<STRUCT>.
  • Missing keys, wrong case and broken JSON all give NULL with the functions.
L3> Production choices
  • Parse once. Functions re-parse the JSON text for every call and every query. Land raw JSON, then build a typed ORC table (CTAS) and query that.
  • Schema on read is strict with the SerDe: one malformed line made a full scan of the JsonSerDe table fail (JsonEOFException). Quarantine bad lines first using a raw STRING table.
  • Path limits (official docs): no recursive .., no filters ?(), no slices or unions; keys with special characters are a problem.
  • Reserved words: a JSON key such as user needs back-ticks as a column name.
  • Hive 4 additions listed by SHOW FUNCTIONS LIKE '%json%': json_read(json, type) parses into a typed value, plus parse_json, to_json and variant_get for the VARIANT type. In our Docker lab json_read worked in a quick fetch query but failed inside a Tez job (a Java 17 module-access error), so test new functions on your cluster before building pipelines on them.
/LEVELS EXAM> “get_json_object vs json_tuple vs JsonSerDe.” get_json_object: one path per call, nested paths allowed, re-parses each call. json_tuple: many top-level keys in one parse with LATERAL VIEW, no nested paths. JsonSerDe: typed table with STRUCT/ARRAY columns; strict about malformed lines. Production: land raw, quarantine bad lines, CTAS into ORC.

WARN> A single malformed line can stop a whole JsonSerDe query. In our lab LIMIT 3 on the SerDe table worked (it read only the first lines), but COUNT(*) failed on line 1,500 with a JsonEOFException. Validate or quarantine raw files before pointing a typed table at them.
4 Step by step

From raw app events to revenue per city

All outputs are real, from the Hive 4.2.1 lab (2,000 generated events, one deliberately truncated).

  1. Step 1 · Land the raw JSON as one STRING column

    CREATE EXTERNAL TABLE events_raw (line STRING) LOCATION '/data/events';
SELECT COUNT(*) AS lines FROM events_raw;
SELECT line FROM events_raw LIMIT 1;
    +--------+ | lines | +--------+ | 2000 | +--------+ +----------------------------------------------------+ | line | +----------------------------------------------------+ | {"event":"app_open","ts":"2026-10-02T09:01:00+05:30","user":{"id":586,"city":"Chennai"},"device":{"os":"Android","app_ver":"5.3.1"}} | +----------------------------------------------------+
    With the default text format, each line becomes one row, whatever it contains. Nothing can fail at this stage.

  2. Step 2 · Pull fields with get_json_object

    SELECT get_json_object(line, '$.event') AS event,
  get_json_object(line, '$.user.id') AS user_id,
  get_json_object(line, '$.user.city') AS city,
  get_json_object(line, '$.items[0].dish') AS first_dish,
  get_json_object(line, '$.items[*].dish') AS all_dishes,
  get_json_object(line, '$.coupon') AS coupon
FROM events_raw LIMIT 3;
    +---------------+----------+----------+---------------+---------------------------------+---------+ | event | user_id | city | first_dish | all_dishes | coupon | +---------------+----------+----------+---------------+---------------------------------+---------+ | app_open | 586 | Chennai | NULL | NULL | NULL | | order_placed | 1376 | Chennai | Rajma Chawal | ["Rajma Chawal","Chai","Idli"] | NULL | | order_placed | 1279 | Delhi | Poha | ["Poha","Idli"] | NULL | +---------------+----------+----------+---------------+---------------------------------+---------+
    Nested paths and list indexes work. Fields that an event does not have (items on app_open, coupon on orders) come back NULL. [*] returns JSON text, not a Hive array.

  3. Step 3 · Traps: case, lists as text, broken JSON

    SELECT get_json_object(line, '$.User.id') AS wrong_case,
  get_json_object(line, '$.items') AS items_text,
  get_json_object('{"a":1', '$.a') AS broken,
  get_json_object(line, '$.items[9].dish') AS no_item
FROM events_raw WHERE get_json_object(line, '$.event') = 'order_placed' LIMIT 1;
    +-------------+----------------------------------------------------+---------+----------+ | wrong_case | items_text | broken | no_item | +-------------+----------------------------------------------------+---------+----------+ | NULL | [{"dish":"Rajma Chawal","qty":3,"price":120},{"dish":"Chai","qty":2,"price":20},{"dish":"Idli","qty":3,"price":60}] | NULL | NULL | +-------------+----------------------------------------------------+---------+----------+
    All silent: a wrong-case key, a missing element and invalid JSON all return NULL. The items list comes back as a plain string.

  4. Step 4 · Find the bad line

    SELECT COUNT(*) AS lines, COUNT(get_json_object(line, '$.event')) AS parsed,
  SUM(IF(get_json_object(line, '$.event') IS NULL, 1, 0)) AS unparsed
FROM events_raw;

SELECT get_json_object(line, '$.event') AS event, COUNT(*) AS n
FROM events_raw GROUP BY get_json_object(line, '$.event') ORDER BY n DESC;
    +--------+---------+-----------+ | lines | parsed | unparsed | +--------+---------+-----------+ | 2000 | 1999 | 1 | +--------+---------+-----------+ +-----------------+------+ | event | n | +-----------------+------+ | order_placed | 779 | | coupon_applied | 411 | | search | 410 | | app_open | 399 | | NULL | 1 | +-----------------+------+
    One line could not be parsed. With functions it only shows up as a NULL group, which is easy to miss unless you count it.

  5. Step 5 · json_tuple: several keys in one parse

    SELECT j.event, j.ts, u.id, u.city
FROM events_raw r
LATERAL VIEW json_tuple(r.line, 'event', 'ts', 'user') j AS event, ts, user_json
LATERAL VIEW json_tuple(j.user_json, 'id', 'city') u AS id, city
LIMIT 3;

SELECT j.user_json FROM events_raw r
LATERAL VIEW json_tuple(r.line, 'user') j AS user_json LIMIT 1;
SELECT j.uid FROM events_raw r
LATERAL VIEW json_tuple(r.line, 'user.id') j AS uid LIMIT 1;
    +---------------+----------------------------+-------+----------+ | j.event | j.ts | u.id | u.city | +---------------+----------------------------+-------+----------+ | app_open | 2026-10-02T09:01:00+05:30 | 586 | Chennai | | order_placed | 2026-10-03T10:02:00+05:30 | 1376 | Chennai | | order_placed | 2026-10-04T11:03:00+05:30 | 1279 | Delhi | +---------------+----------------------------+-------+----------+ +------------------------------+ | j.user_json | +------------------------------+ | {"id":586,"city":"Chennai"} | +------------------------------+ +--------+ | j.uid | +--------+ | NULL | +--------+
    json_tuple takes key names, not paths. The nested user object comes back as JSON text, so a second json_tuple opens it. A dotted key like user.id just returns NULL.

  6. Step 6 · A typed JsonSerDe table, and how one bad line breaks it

    CREATE EXTERNAL TABLE events_json (
  event STRING, ts STRING,
  `user` STRUCT<id:INT, city:STRING>,
  device STRUCT<os:STRING, app_ver:STRING>,
  items ARRAY<STRUCT<dish:STRING, qty:INT, price:INT>>,
  coupon STRING, query STRING)
ROW FORMAT SERDE 'org.apache.hive.hcatalog.data.JsonSerDe'
LOCATION '/data/events';

SELECT event, `user`.city AS city, size(items) AS n_items FROM events_json LIMIT 3;
SELECT COUNT(*) AS n FROM events_json WHERE event = 'order_placed';
    +---------------+----------+----------+ | event | city | n_items | +---------------+----------+----------+ | app_open | Chennai | -1 | | order_placed | Chennai | 3 | | order_placed | Delhi | 2 | +---------------+----------+----------+ Error: … TezTask. Vertex failed … Hive Runtime Error while processing row (root cause in the HiveServer2 log) SerDeException: … JsonEOFException: Unexpected end-of-input in field name
    The first three lines read fine (size is -1 where there is no items list). The full scan fails when it reaches the truncated line. user is a reserved word, so it needs back-ticks: without them the query fails with “cannot recognize input near 'user' '.' 'city'”.

  7. Step 7 · Quarantine bad lines, then parse once into ORC

    INSERT OVERWRITE DIRECTORY '/data/events_good'
SELECT line FROM events_raw WHERE get_json_object(line, '$.event') IS NOT NULL;
INSERT OVERWRITE DIRECTORY '/data/events_bad'
SELECT line FROM events_raw WHERE get_json_object(line, '$.event') IS NULL;
-- recreate events_json with LOCATION '/data/events_good'
SELECT COUNT(*) AS n FROM events_json;

CREATE TABLE events_clean STORED AS ORC AS
SELECT event, CAST(substr(ts, 1, 10) AS DATE) AS event_date,
       `user`.id AS user_id, `user`.city AS city, device.os AS os, items, coupon
FROM events_json;
DESCRIBE events_clean;
    +-------+ | n | +-------+ | 1999 | +-------+ +-------------+-----------------------------------------------+----------+ | col_name | data_type | comment | +-------------+-----------------------------------------------+----------+ | event | string | | | event_date | date | | | user_id | int | | | city | string | | | os | string | | | items | array<struct<dish:string,qty:int,price:int>> | | | coupon | string | | +-------------+-----------------------------------------------+----------+
    The raw STRING table acts as a safety net: good lines go to one folder, the single bad line to another for investigation. The typed ORC table keeps items as an array of structs, so it is parsed once and queried many times.

  8. Step 8 · Answer the product team

    SELECT city, COUNT(DISTINCT user_id) AS buyers, SUM(it.qty * it.price) AS revenue
FROM events_clean LATERAL VIEW inline(items) it
WHERE event = 'order_placed'
GROUP BY city ORDER BY revenue DESC;

SELECT os, COUNT(*) AS events, SUM(IF(event = 'order_placed', 1, 0)) AS orders,
  ROUND(100 * SUM(IF(event = 'order_placed', 1, 0)) / COUNT(*), 1) AS order_pct
FROM events_clean GROUP BY os;
    +------------+---------+----------+ | city | buyers | revenue | +------------+---------+----------+ | Chennai | 119 | 39330 | | Mumbai | 110 | 38750 | | Thane | 115 | 36795 | | Pune | 112 | 36415 | | Hyderabad | 98 | 32380 | | Delhi | 100 | 30930 | | Bengaluru | 108 | 28655 | +------------+---------+----------+ +----------+---------+---------+------------+ | os | events | orders | order_pct | +----------+---------+---------+------------+ | Android | 1334 | 508 | 38.1 | | iOS | 665 | 271 | 40.8 | +----------+---------+---------+------------+
    inline (Lesson 4.2) turns each item struct into dish, qty and price columns. iOS events turned into orders slightly more often (40.8% vs 38.1%) in this generated data.

  9. Step 9 · URLs and XML

    SELECT parse_url('https://tiffingo.in/menu/pune?dish=poha&src=ad', 'HOST') AS host,
  parse_url('https://tiffingo.in/menu/pune?dish=poha&src=ad', 'QUERY', 'src') AS src;
SELECT t.* FROM (SELECT 1) x LATERAL VIEW parse_url_tuple(
  'https://tiffingo.in/menu/pune?dish=poha&src=ad', 'HOST', 'PATH', 'QUERY:dish') t AS host, path, dish;

SELECT xpath_string('<order><id>100001</id><city>Pune</city>…</order>', '/order/city') AS city,
  xpath_int('<order><id>100001</id></order>', '/order/id') AS id,
  xpath('<order><dish>Poha</dish><dish>Chai</dish></order>', '/order/dish/text()') AS dishes;
    +--------------+------+ | host | src | +--------------+------+ | tiffingo.in | ad | +--------------+------+ +--------------+-------------+---------+ | t.host | t.path | t.dish | +--------------+-------------+---------+ | tiffingo.in | /menu/pune | poha | +--------------+-------------+---------+ +-------+---------+------------------+ | city | id | dishes | +-------+---------+------------------+ | Pune | 100001 | ["Poha","Chai"] | +-------+---------+------------------+
    parse_url and parse_url_tuple split web links into host, path and query parameters, useful for campaign tracking. The xpath family reads XML stored in a string column; xpath returns an array of all matches.
5 See it happen

Reading the JSON tree

Left: real Beeline output. Right: which part of the JSON is read.

Paths, tuples and SerDes 5 steps
What you see
  1. get_json_object reads a nested field.
  2. An index picks one list element; [*] returns all of them as JSON text.
  3. Two json_tuple calls read the top level, then the nested user object.
  4. A full scan of the JsonSerDe table fails on the truncated line.
  5. The cleaned data is stored once as typed ORC and queried with inline.
Behind the screen
  1. The path starts at the root ($) and follows keys down the tree.
  2. Array positions start at 0; [*] collects every element.
  3. json_tuple only reads one level, so nested objects need another call.
  4. The SerDe must parse every line into columns; one broken line stops the task.
  5. Raw data is split into good and bad lines, then converted once to ORC.

6 Real-world use

JSON and semi-structured data at work

1. App and web clickstream

Mobile apps and websites send JSON events; Hive tables over the landing folders feed funnels, retention and A/B test reports.

JSON events→Raw → ORC→Funnels

2. API and payment logs

Payment gateways and partner APIs return JSON responses that are stored as-is for audit and parsed into tables for reconciliation.

API responses→get_json_object→Reconciliation

3. Device telemetry

Delivery bikes, smart meters and machines send nested JSON readings; SerDe tables with STRUCT columns make them queryable.

Telemetry→JsonSerDe→Health dashboards

4. Campaign tracking

parse_url_tuple extracts utm_source and utm_campaign from landing-page URLs to attribute orders to ads.

Page URLs→parse_url_tuple→Attribution

5. Legacy XML feeds

Banks and government systems still exchange XML; xpath functions read fields from XML strings during migration to modern formats.

XML files→xpath_string→Tables
