1 The story

“Every daily report reads the whole month”

Before you start: you need managed vs external tables (2.2), loading data (2.5) and how a query becomes a job (1.4).

TiffinGo’s operations team runs the same question every morning: yesterday’s orders and revenue per city. The orders table holds a month of data and keeps growing. Kabir notices that a query for a single day reads all 50,000 rows, every time. At 50 lakh orders a month, that would be 50 lakh rows read to answer a one-day question.

K> Sir, the WHERE clause says one day. Why does Hive still read everything? A> Because the table is one folder of files, and Hive cannot know which file holds which day without opening it. If we store each day in its own sub-folder, order_date=2026-10-05/, Hive reads the folder name and skips the others. That is partitioning. R> So the date is in the folder name, not inside the file? A> Exactly. The partition column lives in the metastore and the path; the data files hold only the other columns. Today we build orders_by_day, prove with Hive’s own counters that a one-day query reads 1,621 rows instead of 50,000, and find two ways to lose that benefit without noticing. All outputs are real, from Hive 4.2.1.
2 Definition

Partitioning in Hive

Formal definition (write this in exams)

Partitioning divides a table into parts based on the values of one or more partition columns, declared with PARTITIONED BY (col type, …). Each distinct combination of values is a partition, stored as a separate sub-directory of the table location named col=value and registered in the metastore. Partition columns are virtual: they are not stored inside the data files, but can be queried like normal columns. When a query filters on partition columns, Hive reads only the matching partitions; this is called partition pruning.

In simple words

You tell Hive to keep each day (or city, or month) in its own folder. When you ask for one day, Hive opens only that folder and skips the rest, so the query reads much less data.

LEVELS> Partitioning at three levels L1> Files sorted into labelled boxes
  • Imagine a month of bills in one big box. To find 5 October’s bills you must look at every bill.
  • Now keep one box per day, with the date written on it. You open only the “5 October” box.
  • In Hive the box is a folder like order_date=2026-10-05, and the label is the partition column. You choose it with PARTITIONED BY when you create the table.
L2> How Hive uses partitions
  • Every partition is a row in the metastore (table PARTITIONS) pointing to its folder. SHOW PARTITIONS t; lists them.
  • When WHERE filters on the partition column, the planner asks the metastore for the matching partitions only. This is partition pruning; EXPLAIN DEPENDENCY shows which partitions a query will read.
  • Static partition: you name the value: INSERT … PARTITION (order_date='2026-10-05') SELECT … or LOAD DATA … PARTITION (dt='…'). Dynamic: Hive takes the value from the data (Lesson 5.2).
  • Partitions can nest: PARTITIONED BY (order_date DATE, city STRING) creates order_date=…/city=…/.
L3> What the planner can and cannot prune
  • In our lab Hive 4.2.1 pruned even through functions on the partition column: date_format(order_date,'EEE')='Sat' read 4 partitions, order_date >= date_sub(current_date, 3) read 7.
  • It cannot prune on a different column that “means the same”: to_date(order_ts)='2026-10-05' read all 30 folders and 50,000 rows, although the answer was identical. It also cannot prune when the filter is OR-ed with a non-partition condition.
  • Static partitions are trusted, not checked: loading 3 October’s file into dt='2026-10-04' succeeded and duplicated 1,668 orders.
  • Safety switch: SET hive.strict.checks.no.partition.filter=true rejects queries on partitioned tables without a partition filter (Error 10056). Default in 4.2.1: false.
/LEVELS EXAM> “What is partitioning and why is it used?” Say: it splits a table into sub-directories by the value of a column; queries that filter on that column read only the matching directories (partition pruning), so they scan less data. Partition columns are not stored in the data files. Then name static vs dynamic partitions.

4 Step by step

Kabir builds orders_by_day

All outputs are real, from the Hive 4.2.1 lab (database tiffingo).

  1. Step 1 · Create the table and load two days with static partitions

    CREATE TABLE orders_by_day (
  order_id INT, customer_id INT, city STRING, order_ts TIMESTAMP,
  amount DECIMAL(10,2), payment STRING, status STRING)
PARTITIONED BY (order_date DATE)
STORED AS ORC;

INSERT INTO orders_by_day PARTITION (order_date='2026-10-01')
SELECT order_id, customer_id, city, order_ts, amount, payment, status
FROM orders WHERE order_date = '2026-10-01';
-- same for 2026-10-02

SHOW PARTITIONS orders_by_day;
SELECT order_date, COUNT(*) AS n FROM orders_by_day GROUP BY order_date;
    +------------------------+ | partition | +------------------------+ | order_date=2026-10-01 | | order_date=2026-10-02 | +------------------------+ +-------------+-------+ | order_date | n | +-------------+-------+ | 2026-10-01 | 1641 | | 2026-10-02 | 1617 | +-------------+-------+
    order_date is not in the column list; it appears only in PARTITIONED BY. In a static insert the SELECT returns only the 7 data columns, and the PARTITION clause supplies the date.

  2. Step 2 · The partition column is in the folder name, not the file

    DESCRIBE orders_by_day;
    +--------------------------+----------------+----------+ | col_name | data_type | comment | +--------------------------+----------------+----------+ | order_id | int | | | customer_id | int | | | city | string | | | order_ts | timestamp | | | amount | decimal(10,2) | | | payment | string | | | status | string | | | order_date | date | | | | NULL | NULL | | # Partition Information | NULL | NULL | | # col_name | data_type | comment | | order_date | date | | +--------------------------+----------------+----------+ $ find …/tiffingo.db/orders_by_day -type f …/orders_by_day/order_date=2026-10-01/000000_0 …/orders_by_day/order_date=2026-10-02/000000_0
    DESCRIBE lists order_date twice: as a queryable column, and under “# Partition Information”. On disk each day is a folder order_date=… with its own ORC file. The rest of October was loaded with one dynamic insert (Lesson 5.2), giving 30 partitions.

  3. Step 3 · Ask Hive which partitions it will read

    EXPLAIN DEPENDENCY SELECT COUNT(*) FROM orders_by_day
WHERE order_date = '2026-10-05';

EXPLAIN DEPENDENCY SELECT COUNT(*) FROM orders_by_day
WHERE order_date BETWEEN '2026-10-05' AND '2026-10-07';
    +----------------------------------------------------+ | Explain | +----------------------------------------------------+ | {"input_tables":[{"tablename":"tiffingo@orders_by_day","tabletype":"EXTERNAL_TABLE"}],"input_partitions":[{"partitionName":"tiffingo@orders_by_day@order_date=2026-10-05"}]} | +----------------------------------------------------+
    input_partitions lists exactly one folder for one day and three for a three-day range. Pruning happens at planning time, from the metastore, before any file is opened.

  4. Step 4 · Prove it with Tez counters

    SET hive.tez.exec.print.summary=true;
SELECT COUNT(*) AS n FROM orders_by_day WHERE order_date='2026-10-05' AND city='Pune';
SELECT COUNT(*) AS n FROM orders        WHERE order_date='2026-10-05' AND city='Pune';
    SELECT COUNT(*) AS n FROM orders_by_day WHERE order_date='2026-10-05' AND city='Pune'; result 230 · RECORDS_IN 1621 · INPUT_DIRECTORIES 1 · INPUT_FILES 1 SELECT COUNT(*) AS n FROM orders WHERE order_date='2026-10-05' AND city='Pune'; result 230 · RECORDS_IN 50000 · INPUT_DIRECTORIES 1 · INPUT_FILES 1
    Both queries answer 230 (Pune, 5 October, the same as Lesson 3.6). The partitioned table read 1,621 rows; the flat table read all 50,000. That is 31 times less work for one day, and the gap grows with every month of history.

  5. Step 5 · Trap 1: filtering on the wrong column

    SELECT COUNT(*) AS n FROM orders_by_day
WHERE to_date(order_ts) = '2026-10-05' AND city = 'Pune';

-- EXPLAIN DEPENDENCY, number of input partitions (real):
--   no WHERE                                        30
--   city = 'Pune'                                   30
--   order_date = '2026-10-05' OR city = 'Pune'      30
--   date_format(order_date, 'EEE') = 'Sat'           4
--   order_date >= date_sub(current_date, 3)          7
--   to_date(order_ts) = '2026-10-05'                30
    SELECT COUNT(*) AS n FROM orders_by_day WHERE to_date(order_ts)='2026-10-05' AND city='Pune'; result 230 · RECORDS_IN 50000 · INPUT_DIRECTORIES 30 · INPUT_FILES 30
    order_ts holds the same day, but it is an ordinary column, so Hive must open all 30 folders. Functions on the partition column itself still pruned in 4.2.1 (4 Saturdays, the last 7 days). An OR with a non-partition condition disables pruning. Always filter on the partition column directly.

  6. Step 6 · Trap 2: static partitions are trusted, not checked

    CREATE TABLE orders_daily_txt (order_id INT, customer_id INT, restaurant_id INT,
  city STRING, amount INT, payment STRING, status STRING)
PARTITIONED BY (dt STRING) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';

LOAD DATA LOCAL INPATH '/data/stage/orders_2026-10-03.csv'
  INTO TABLE orders_daily_txt PARTITION (dt='2026-10-03');
-- the next morning, a copy-paste mistake:
LOAD DATA LOCAL INPATH '/data/stage/orders_2026-10-03.csv'
  INTO TABLE orders_daily_txt PARTITION (dt='2026-10-04');

SELECT dt, COUNT(*) AS n, SUM(amount) AS rev FROM orders_daily_txt GROUP BY dt ORDER BY dt;
SELECT COUNT(*) AS same_orders_twice FROM orders_daily_txt a JOIN orders_daily_txt b
  ON a.order_id = b.order_id AND a.dt = '2026-10-03' AND b.dt = '2026-10-04';
    +-------------+-------+---------+ | dt | n | rev | +-------------+-------+---------+ | 2026-10-03 | 1668 | 493530 | | 2026-10-04 | 1668 | 493530 | +-------------+-------+---------+ +--------------------+ | same_orders_twice | +--------------------+ | 1668 | +--------------------+
    Hive moved the file into dt=2026-10-04/ without looking inside: the CSV has no date column, so there is nothing to check. 1,668 orders now count twice. The fix was ALTER TABLE orders_daily_txt DROP PARTITION (dt='2026-10-04'). Add a check in daily jobs, such as comparing MIN/MAX(order_ts) with the partition value.

  7. Step 7 · Manage partitions and switch on the safety check

    ALTER TABLE orders_by_day ADD PARTITION (order_date='2026-10-31');
ALTER TABLE orders_by_day PARTITION (order_date='2026-10-31')
  RENAME TO PARTITION (order_date='2026-11-01');
ALTER TABLE orders_by_day DROP IF EXISTS PARTITION (order_date >= '2026-11-01');

SET hive.strict.checks.no.partition.filter=true;
SELECT COUNT(*) FROM orders_by_day;
    Error: Error while compiling statement: FAILED: SemanticException [Error 10056]: Queries against partitioned tables without a partition filter are disabled for safety reasons …
    ADD creates an empty partition (a query on it returns 0 rows), RENAME moves it, and DROP accepts a range. With the strict check on, a query without a partition filter is refused (Error 10056): useful on shared clusters, where one forgotten filter can read years of data.

Behind the screen
  1. Each partition is a row in the metastore and a folder named order_date=….
  2. The planner matches the WHERE clause against partition values and drops the rest.
  3. Fewer folders opened means fewer rows read for the same answer.
  4. order_ts is an ordinary column; only the partition column can prune.
  5. In a static load Hive trusts the value you write and never looks inside the file.

Three live scenarios follow: a safe nightly load, a safety switch for shared clusters, and two-level partitions.

Real-time scenario 1

A nightly load that is safe to re-run

Most production tables are loaded one partition per run. INSERT OVERWRITE on that partition makes re-runs safe. (Typical pattern.)

Daily partition load 5 steps
Animated example
  1. The scheduler passes yesterday’s date into the job.
  2. If the job is re-run, OVERWRITE replaces the partition instead of doubling it.
  3. Only the named partition changes.
  4. A quick check confirms the data really belongs to that day.
  5. Retention is one DROP PARTITION with a range.
Real-time scenario 2

Stopping full-table scans on a shared cluster

One missing WHERE clause on a partitioned table can read years of data. Hive can refuse such queries. Results are real.

Strict partition filter 5 steps
Animated example
  1. A dashboard query forgot the date filter.
  2. With the strict check on, Hive refuses it with error 10056.
  3. The same query with a partition filter runs normally.
  4. Admins set it cluster-wide; users can set it per session.
  5. Costly mistakes now fail in a second.

6 Real-world use

Partitioning at work

1. Daily event and transaction tables

Payment, click and order tables in data lakes are almost always partitioned by date, so daily reports and nightly jobs read one day.

Events→PARTITIONED BY dt→Daily reports

2. Data retention and privacy rules

Policies such as “keep raw logs for 90 days” are applied by dropping old partitions, a quick metadata operation instead of a DELETE over billions of rows.

Old partitions→DROP PARTITION→Compliant lake

3. Safe re-processing

When late data arrives or a bug is fixed, teams rebuild only the affected days with INSERT OVERWRITE … PARTITION, without touching the rest of the table.

Fix→OVERWRITE one day→Corrected history

4. Regional data

Companies operating in several countries often add a region or country level, so local teams and local data rules work on their own folders.

Global table→region partition→Local queries

5. Shared by many engines

The same partitioned folders in the metastore are pruned by Spark, Trino and Impala too, so one good layout speeds up every tool.

Metastore→partition list→Any engine
