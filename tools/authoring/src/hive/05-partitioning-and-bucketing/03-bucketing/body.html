1 The story

“Can we partition by customer?”

Before you start: finish partitioning (5.1) and joins (3.3); DISTRIBUTE BY and CLUSTER BY (3.4) explain the shuffle behind bucketing.

The CRM team asks Kabir for two things: a quick 1-in-8 sample of customers to test a new loyalty rule, and faster joins between orders and customers on customer_id. Kabir’s first idea, after Lesson 5.1, is to partition by customer.

K> Sir, if date partitions work so well, why not PARTITIONED BY (customer_id)? A> Two thousand customers today, two lakh next year: that is two lakh folders with a few rows each. Partitioning is for columns with a modest number of values. For high-cardinality columns like ids we use bucketing: CLUSTERED BY (customer_id) INTO 8 BUCKETS. Hive hashes each id and writes it into one of exactly 8 files. R> And the same customer always lands in the same file? A> Always. That is what makes bucket sampling and bucket-aware joins possible. Today we look inside the 8 files, prove that the hash is not simply id mod 8 in Hive 4, sample one bucket while reading one file, and hit two surprises: bucketed CTAS is refused, and a LOAD into a bucketed table lost three customers. All outputs are real, from Hive 4.2.1.
2 Definition

Bucketing (clustering) in Hive

Formal definition (write this in exams)

Bucketing divides the data of a table, or of each partition, into a fixed number of files called buckets, declared with CLUSTERED BY (col, …) [SORTED BY (col [ASC|DESC], …)] INTO n BUCKETS. Each row is written to bucket hash(bucketing columns) mod n, so equal values always go to the same bucket. Bucketing columns remain ordinary columns of the data. Bucketing enables efficient sampling (TABLESAMPLE), bucket pruning on equality filters and, when tables are bucketed compatibly on the join key, bucket map joins and sort-merge-bucket (SMB) joins.

In simple words

Bucketing splits a table into a fixed number of files using a hash of a column such as customer_id. The same id always goes to the same file, so Hive can read just one file for a sample or for one id, and can join matching files of two tables.

Words you’ll meet in this lesson

BucketOne of the n files of a bucketed table or partition, e.g. 000005_0.
CLUSTERED BYThe bucketing column(s). Not the same as the CLUSTER BY query clause (3.4).
Murmur3The hash used by bucketing_version 2 tables (Hive 3+).
TABLESAMPLETABLESAMPLE(BUCKET x OUT OF y ON col): a sample by bucket.
Bucket pruningReading only the bucket that can hold the value in WHERE col = v.
Bucket map joinEach task loads only the matching bucket of the small table.
SMB joinSort-merge-bucket join: both tables bucketed and sorted on the key; merge bucket by bucket.
INPUT__FILE__NAMEVirtual column: the file each row was read from.

LEVELS> Bucketing at three levels L1> Roll numbers into sections
  • A school splits 2,000 students into 8 sections by a fixed rule on the roll number. Every student is always in the same section, and each section has roughly the same size.
  • In Hive the sections are files. CLUSTERED BY (customer_id) INTO 8 BUCKETS creates 8 files per table (or per partition).
  • Unlike a partition, the bucket column stays in the data, and the number of buckets never grows with the data.
L2> How rows are placed and what it enables
  • Bucket number = hash(bucket column) mod number of buckets. Hive 3+ tables have bucketing_version=2 and use the Murmur3 hash. Our lab confirmed it: customer 1 is in bucket 5, which is pmod(murmur_hash(1), 8), not 1 % 8. Older articles that say “for INT the hash is the value” describe version 1.
  • SORTED BY sorts rows inside each bucket file.
  • Sampling: TABLESAMPLE(BUCKET x OUT OF y ON col) reads only the matching bucket files when y divides the bucket count.
  • Bucket pruning: WHERE customer_id = 1 read 5,649 rows instead of 50,000 (hive.tez.bucket.pruning=true).
  • hive.enforce.bucketing is no longer needed: since Hive 2.x inserts always write the declared buckets.
L3> Joins, loads and limits in Hive 4.2.1
  • Bucket map join / SMB join: when both tables are bucketed (and sorted) on the join key with compatible bucket counts, the optimiser can join bucket i with bucket i without a full shuffle. It is a cost-based choice: on our small lab tables Hive picked a broadcast map join or a shuffle merge join instead. Always check EXPLAIN.
  • CTAS into a bucketed table was refused (Error 10068); create the table, then INSERT.
  • LOAD DATA into a bucketed table is rewritten into an insert job. With skip.header.line.count=1 it lost customers 1, 3 and 5: the header became a data row, and then the first line of every bucket file was skipped. Load into a staging table, then INSERT … SELECT.
  • TABLESAMPLE(10 PERCENT) was refused on Tez in our lab; TABLESAMPLE(100 ROWS) and bucket sampling worked.
/LEVELS EXAM> “Partitioning vs bucketing” is one of the most asked Hive questions. Say: partitioning makes folders by value and suits low-cardinality filter columns; bucketing hashes a column into a fixed number of files and suits high-cardinality columns, sampling and joins; they can be combined. Mention CLUSTERED BY … INTO n BUCKETS and TABLESAMPLE.

WARN> Choosing the bucket count: aim for bucket files of a healthy size (tens to hundreds of MB in production), and for joins use the same count, or multiples, on both tables. Too many buckets on a small table just creates small files: our 8 buckets hold only 44–53 KB each, fine for learning but far too many for 50,000 rows in real life.
4 Step by step

Kabir buckets orders by customer

All outputs are real, from the Hive 4.2.1 lab (database tiffingo).

  1. Step 1 · Create a bucketed, sorted table and fill it

    CREATE TABLE orders_bkt (
  order_id INT, customer_id INT, city STRING, order_ts TIMESTAMP,
  amount DECIMAL(10,2), payment STRING, status STRING)
CLUSTERED BY (customer_id) SORTED BY (customer_id) INTO 8 BUCKETS
STORED AS ORC;

INSERT OVERWRITE TABLE orders_bkt
SELECT order_id, customer_id, city, order_ts, amount, payment, status FROM orders;

DESCRIBE FORMATTED orders_bkt;   -- selected lines
$ ls …/tiffingo.db/orders_bkt
    | bucketing_version | 2 | | Num Buckets: | 8 | | Bucket Columns: | [customer_id] | | Sort Columns: | [Order(col:customer_id, order:1)] | 000000_0 000001_0 000002_0 000003_0 000004_0 000005_0 000006_0 000007_0
    Exactly 8 files, one per bucket, named by bucket number. No SET hive.enforce.bucketing was needed; that setting only mattered before Hive 2. bucketing_version=2 tells every engine which hash to use.

  2. Step 2 · Which file holds which customer?

    SELECT customer_id,
       regexp_extract(INPUT__FILE__NAME, '[^/]+$', 0) AS file,
       customer_id % 8                  AS mod8,
       pmod(hash(customer_id), 8)       AS legacy_hash,
       pmod(murmur_hash(customer_id), 8) AS murmur
FROM orders_bkt WHERE customer_id IN (1, 2, 3, 4, 5, 6, 7, 8)
GROUP BY customer_id, INPUT__FILE__NAME ORDER BY customer_id;
    +--------------+-----------+-------+--------------+---------+ | customer_id | file | mod8 | legacy_hash | murmur | +--------------+-----------+-------+--------------+---------+ | 1 | 000005_0 | 1 | 1 | 5 | | 2 | 000004_0 | 2 | 2 | 4 | | 3 | 000006_0 | 3 | 3 | 6 | | 4 | 000005_0 | 4 | 4 | 5 | | 5 | 000007_0 | 5 | 5 | 7 | | 6 | 000004_0 | 6 | 6 | 4 | | 7 | 000000_0 | 7 | 7 | 0 | | 8 | 000001_0 | 0 | 0 | 1 | +--------------+-----------+-------+--------------+---------+
    The real file number matches the murmur column every time, not id % 8. Many tutorials still teach “bucket = id mod n”; that was version 1. The INPUT__FILE__NAME virtual column is the quickest way to check where rows really are.

  3. Step 3 · How even are the buckets?

    SELECT regexp_extract(INPUT__FILE__NAME, '[^/]+$', 0) AS file,
       COUNT(*) AS rows_in_file, COUNT(DISTINCT customer_id) AS customers
FROM orders_bkt GROUP BY INPUT__FILE__NAME ORDER BY file;
    +-----------+---------------+------------+ | file | rows_in_file | customers | +-----------+---------------+------------+ | 000000_0 | 6210 | 247 | | 000001_0 | 5961 | 244 | | 000002_0 | 6754 | 269 | | 000003_0 | 5922 | 237 | | 000004_0 | 6689 | 262 | | 000005_0 | 5649 | 230 | | 000006_0 | 6276 | 250 | | 000007_0 | 6539 | 261 | +-----------+---------------+------------+
    Between 230 and 269 customers per bucket, close to 2,000 ÷ 8 = 250. Rows vary more (5,649 to 6,754), because some customers order more. A customer who orders 100 times more than others would make one bucket much bigger: bucketing spreads keys, not rows (skew, Lesson 5.4).

  4. Step 4 · Sample one bucket, read one file

    SET hive.tez.exec.print.summary=true;
SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c
FROM orders_bkt TABLESAMPLE(BUCKET 6 OUT OF 8 ON customer_id) s;

SELECT … FROM orders_bkt TABLESAMPLE(BUCKET 2 OUT OF 4 ON customer_id) s;
SELECT … FROM orders     TABLESAMPLE(BUCKET 6 OUT OF 8 ON customer_id) s;  -- not bucketed
    SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c FROM orders_bkt TABLESAMPLE(BUCKET 6 OUT OF 8 ON customer_id) s; result | 5649 | 230 | · RECORDS_IN 5649 · INPUT_FILES 1 SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c FROM orders_bkt TABLESAMPLE(BUCKET 2 OUT OF 4 ON customer_id) s; result | 11610 | 474 | · RECORDS_IN 11610 · INPUT_FILES 2 SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c FROM orders TABLESAMPLE(BUCKET 6 OUT OF 8 ON customer_id) s; result | 5649 | 230 | · RECORDS_IN 50000 · INPUT_FILES 1
    Bucket numbers in TABLESAMPLE start at 1, so BUCKET 6 is file 000005_0: 5,649 rows, 230 customers, one file read. 2 OUT OF 4 takes buckets 2 and 6 (files 1 and 5). On the unbucketed table the same sample gives the same answer but reads all 50,000 rows, because Hive must hash every row.

  5. Step 5 · Bucket pruning on an equality filter

    SET hive.tez.bucket.pruning;
SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c
FROM orders_bkt WHERE customer_id = 1;
    +-------------------------------+ | hive.tez.bucket.pruning=true | +-------------------------------+ SELECT COUNT(*) AS n, COUNT(DISTINCT customer_id) AS c FROM orders_bkt WHERE customer_id = 1; result | 26 | 1 | · RECORDS_IN 5649 · INPUT_FILES 8
    Customer 1 has 26 orders. Hive computed customer 1’s bucket and read only that bucket’s 5,649 rows, not 50,000. It also worked for IN (1, 2): 12,338 rows, exactly buckets 5 and 4. A wide range such as BETWEEN 1 AND 1000 touches every bucket, so it saves nothing.

  6. Step 6 · Other samples: ROWS, rand() and PERCENT

    SELECT COUNT(*) AS n  FROM orders TABLESAMPLE(100 ROWS) s;
SELECT COUNT(*) AS n1 FROM orders TABLESAMPLE(BUCKET 1 OUT OF 10 ON rand()) s;
SELECT COUNT(*) AS n2 FROM orders TABLESAMPLE(BUCKET 1 OUT OF 10 ON rand()) s;
SELECT COUNT(*) AS n  FROM orders TABLESAMPLE(10 PERCENT) s;
    +------+ | n | +------+ | 100 | +------+ +-------+ | n1 | Error: Error while compiling statement: FAILED: SemanticException 1:45 Percentage sampling is not supported in org.apache.hadoop.hive.ql.io.HiveInputFormat. Error encountered near token '10'
    ON rand() gives about 10% but a different sample each run (5,057, then 4,981), so results cannot be reproduced. Sample on a column (or hash(col)) for repeatable tests. Block sampling by PERCENT was refused on our Tez setup.

  7. Step 7 · Two surprises: CTAS and LOAD DATA

    CREATE TABLE customers_bkt CLUSTERED BY (customer_id) INTO 8 BUCKETS
STORED AS ORC AS SELECT * FROM customers;

CREATE TABLE cust_bkt_load (customer_id INT, name STRING, city STRING, state STRING,
  joined_on DATE, plan STRING)
CLUSTERED BY (customer_id) INTO 4 BUCKETS
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
TBLPROPERTIES ('skip.header.line.count'='1');
LOAD DATA LOCAL INPATH '/data/tiffingo/customers/customers.csv' INTO TABLE cust_bkt_load;
SELECT COUNT(*) AS loaded, MIN(customer_id) AS min_id, MAX(customer_id) AS max_id FROM cust_bkt_load;
    Error: Error while compiling statement: FAILED: SemanticException [Error 10068]: CREATE-TABLE-AS-SELECT does not support partitioning in the target table +---------+---------+---------+ | loaded | min_id | max_id |
    Bucketed CTAS is refused (the message says “partitioning”, but bucketing triggers it too). LOAD into a bucketed table ran an insert job and wrote 4 bucket files, but only 1,997 of 2,000 customers came back: the header line was stored as a row, and skip.header.line.count then skipped the first line of each of the 4 files, hiding customers 1, 3 and 5. Load into a plain staging table and INSERT … SELECT instead.

Hash, files, sampling and the LOAD surprise 5 steps
What you see
  1. Kabir creates and fills an 8-bucket table: 8 files appear.
  2. The real bucket of each customer matches murmur_hash, not id mod 8.
  3. Sampling one bucket reads one file: 5,649 rows.
  4. A filter on one customer reads only that customer’s bucket.
  5. LOAD into a bucketed table with a header lost three customers.
Behind the screen
  1. The insert shuffles rows by the hash so each writer produces one bucket file.
  2. Hive 3+ tables use Murmur3 for the bucket number.
  3. TABLESAMPLE maps bucket 6 of 8 to file 000005_0 and skips the rest.
  4. Hive hashes the literal 1, finds bucket 5 and reads only it.
  5. The rewritten load stored the header as a row; then the first line of each bucket file was skipped.

Bucket sampling 5 steps

  2. Sampling on customer_id always selects the same customers.
  3. On a bucketed table this reads a single file.
  4. Tables bucketed the same way share the same groups.

Real-time scenario 3 · advanced

Bucket joins: possible, not guaranteed

Both tables were bucketed and sorted on customer_id. Here is what Hive 4.2.1 actually chose on our small tables.

Join planning 5 steps
Animated example
  1. Both tables are bucketed the same way on the join key.
  2. In a bucket map join each task joins bucket i with bucket i only.
  3. With 2,000 customers, Hive simply broadcast the whole small table.
  4. With map joins turned off, it used a normal shuffle merge join.
  5. Bucket joins help when both sides are too large to broadcast; always confirm with EXPLAIN.
6 Real-world use

Bucketing at work

1. Repeatable samples and experiments

Data scientists test queries and models on one bucket of a huge table, and product teams pick experiment groups by user bucket, so the same users are in the group every day.

Huge table→TABLESAMPLE bucket→Fast, stable sample

2. Joining two large tables

When two fact-sized tables are joined every day on the same key (orders and payments on order_id), bucketing both on that key lets the engine join matching buckets instead of shuffling everything.

Two big tables→bucketed on key→Bucket / SMB join

3. Customer look-ups

Support tools that pull one customer’s history benefit from bucket pruning: only that customer’s bucket inside each date partition is read.

Customer id→bucket pruning→One file per day

4. Transactional tables

Older Hive versions required ACID tables to be bucketed; Hive 3+ does not, but bucketing still organises delta files by key in many existing warehouses (Module 7).

Updates→bucketed ACID→Organised deltas

5. Shared tables across engines

Spark and Trino can read Hive-bucketed tables. The bucketing_version property tells them which hash Hive used, so bucket pruning and joins stay correct across engines.

Hive writes→bucketing_version→Spark / Trino read
