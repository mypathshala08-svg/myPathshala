1 The story

“Every night the app database sends changed customers. Apply them.”

Before you start: finish ACID tables (7.1), joins (3.3) and window functions (3.6).

TiffinGo’s app runs on PostgreSQL. Every night a job exports the customers that changed: plan upgrades, address moves, closed accounts and new sign-ups. Kabir must apply them to the Hive customer table. Writing a separate UPDATE, DELETE and INSERT would mean three transactions and three chances to fail half-way.

K> Sir, can one statement insert new customers and update existing ones? A> That is MERGE: compare a source with a target on a key, then WHEN MATCHED … UPDATE or DELETE, and WHEN NOT MATCHED … INSERT. One statement, one transaction. People call it an upsert. R> And the finance team wants history: what plan was the customer on when they ordered? A> Then you keep old versions with dates: a slowly changing dimension type 2. MERGE can do that too, with a small trick. Today: a type 1 MERGE, the error you get with duplicate keys, a type 2 MERGE that keeps history, a re-run to prove it is safe, and a point-in-time join. All outputs are real, from Hive 4.2.1.
2 Definition

MERGE and slowly changing dimensions

Formal definition (write this in exams)

MERGE is a DML statement that synchronises a target transactional table with a source relation using a join condition. For each source row that matches a target row, the first applicable WHEN MATCHED clause updates or deletes the target row; for each source row without a match, a WHEN NOT MATCHED clause inserts a new row. The whole statement executes as one transaction. A slowly changing dimension (SCD) is a dimension table whose attributes change over time: type 1 overwrites old values, type 2 keeps full history by adding a new row per change with validity dates and a current flag, and type 3 keeps a limited history in additional columns.

In simple words

MERGE compares new data with a table by key and, in one statement, updates the rows that changed, deletes the ones marked for removal and inserts the new ones. SCD is the name for the ways of keeping (or not keeping) old values of things like a customer’s city or plan.

LEVELS> MERGE and SCD at three levels L1> Updating an address book
  • You get a list of changes. For each person: if they are already in your book, change their entry; if not, add them; if they asked to be removed, cross them out.
  • MERGE does exactly this for a whole table in one go.
  • Sometimes you must not lose the old entry (“where did she live last year?”). Then you close the old entry with an end date and add a new one: that is SCD type 2.
L2> The MERGE statement
  • MERGE INTO target t USING source s ON t.key = s.key, then up to three clauses: WHEN MATCHED [AND cond] THEN UPDATE SET …, WHEN MATCHED [AND cond] THEN DELETE, WHEN NOT MATCHED [AND cond] THEN INSERT VALUES (…).
  • The target must be a full ACID table (7.1); the source can be any table, view or subquery.
  • SCD type 1: overwrite the old value (no history). Type 2: keep every version with eff_from, eff_to, is_current. Type 3: keep the previous value in an extra column.
  • Add a change condition (t.plan <> s.plan OR …) so unchanged rows are not rewritten.
L3> Hive specifics we verified
  • Cardinality check: if two source rows match one target row, Hive fails the MERGE (“Cardinality Violation in Merge statement”, hive.merge.cardinality.check=true). The target stayed unchanged. De-duplicate the source first.
  • One MERGE wrote two delete_deltas and two deltas under one write id: atomic. Untouched rows kept their old ROW__ID.
  • SCD2 in one MERGE: a changed row must both close the old version (MATCHED) and insert a new one (NOT MATCHED). The trick: feed changed rows twice, once with the real key and once with a NULL join key, which can never match.
  • Re-running the same SCD2 MERGE changed nothing (9 rows, 7 current): it is idempotent, so a failed night can simply be re-run.
/LEVELS EXAM> “What is SCD type 2 and how do you implement it in Hive?” Explain the validity columns, then the MERGE: match current rows on the key and close them when attributes differ; insert new versions using a NULL join key for changed rows plus the real key for new rows. Mention that the target must be an ACID table and that duplicate source keys cause a cardinality violation.

Type 1, a failure, then type 2

    The target is an ACID table; the staging table is an ordinary table. op says what happened in the source system: U(pdate), D(elete), I(nsert). Customer 4 is in the feed although nothing changed, which is common in real exports.

  2. Step 2 · One MERGE: update, delete and insert

    MERGE INTO dim_customer t USING stg_customer s ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED AND (t.city <> s.city OR t.plan <> s.plan)
  THEN UPDATE SET city = s.city, plan = s.plan
WHEN NOT MATCHED THEN INSERT VALUES (s.customer_id, s.name, s.city, s.plan);
SELECT * FROM dim_customer ORDER BY customer_id;
    +---------------------------+--------------------+--------------------+--------------------+ | dim_customer.customer_id | dim_customer.name | dim_customer.city | dim_customer.plan | +---------------------------+--------------------+--------------------+--------------------+ | 1 | Aarav Desai | Bengaluru | Silver | | 2 | Ananya Iyer | Mumbai | Gold | | 3 | Arjun Nair | Pune | Gold | | 4 | Gurpreet Das | Bengaluru | Basic | | 5 | Aarav Singh | Bengaluru | Basic | | 7 | Kavya Reddy | Hyderabad | Silver | +---------------------------+--------------------+--------------------+--------------------+
    Ananya is Gold, Arjun moved to Pune, Diya (6) is deleted and Kavya (7) is new. The DELETE clause is listed first so that a “D” row is never treated as an update. This is SCD type 1: the old values are gone.

  4. Step 4 · Duplicate keys in the source: cardinality violation

    INSERT INTO stg_customer VALUES (2, 'Ananya Iyer', 'Mumbai', 'Silver', 'U');   -- a second row for customer 2
-- run the same MERGE again
SELECT customer_id, plan FROM dim_customer WHERE customer_id = 2;
    Error: … Vertex failed … Reducer 4 … Caused by: org.apache.hadoop.hive.ql.metadata.HiveException: Error evaluating cardinality_violation(_col0) Caused by: java.lang.RuntimeException: Cardinality Violation in Merge statement: [2, 536870914, 0 … +--------------+-------+ | customer_id | plan | +--------------+-------+ | 2 | Gold | +--------------+-------+
    Two source rows (Gold and Silver) matched customer 2, so Hive could not know which one wins and failed the whole statement. The table was not changed at all. Fix: keep one row per key in the source, e.g. the latest with ROW_NUMBER() (Lesson 3.6).

  5. Step 5 · A type 2 table and the changes

    CREATE TABLE dim_customer_hist (customer_id INT, name STRING, city STRING, plan STRING,
  eff_from DATE, eff_to DATE, is_current BOOLEAN)
STORED AS ORC TBLPROPERTIES ('transactional'='true');
INSERT INTO dim_customer_hist SELECT customer_id, name, city, plan,
  DATE '2026-10-01', DATE '9999-12-31', true FROM customers WHERE customer_id <= 6;

CREATE TABLE stg2 (customer_id INT, name STRING, city STRING, plan STRING);
INSERT INTO stg2 VALUES (2,'Ananya Iyer','Mumbai','Gold'), (3,'Arjun Nair','Pune','Gold'),
  (4,'Gurpreet Das','Bengaluru','Basic'), (7,'Kavya Reddy','Hyderabad','Silver');
    -- 6 rows, all current, valid from 2026-10-01 to 9999-12-31
    Every version has a validity range. “9999-12-31” is a common convention for “still valid”, so a simple BETWEEN works in joins. The staging table holds the same changes as before, without the delete.

  6. Step 6 · The SCD2 MERGE with a NULL join key

    MERGE INTO dim_customer_hist t
USING (
  SELECT s.customer_id AS join_key, s.customer_id, s.name, s.city, s.plan FROM stg2 s
  UNION ALL
  SELECT CAST(NULL AS INT) AS join_key, s.customer_id, s.name, s.city, s.plan
  FROM stg2 s JOIN dim_customer_hist d ON s.customer_id = d.customer_id AND d.is_current
  WHERE s.city <> d.city OR s.plan <> d.plan
) u
ON t.customer_id = u.join_key AND t.is_current
WHEN MATCHED AND (t.city <> u.city OR t.plan <> u.plan)
  THEN UPDATE SET eff_to = DATE '2026-10-26', is_current = false
WHEN NOT MATCHED THEN INSERT VALUES (u.customer_id, u.name, u.city, u.plan,
  DATE '2026-10-27', DATE '9999-12-31', true);
SELECT * FROM dim_customer_hist ORDER BY customer_id, eff_from;
    +--------------------------------+-------------------------+-------------------------+-------------------------+-----------------------------+---------------------------+-------------------------------+ | dim_customer_hist.customer_id | dim_customer_hist.name | dim_customer_hist.city | dim_customer_hist.plan | dim_customer_hist.eff_from | dim_customer_hist.eff_to | dim_customer_hist.is_current | +--------------------------------+-------------------------+-------------------------+-------------------------+-----------------------------+---------------------------+-------------------------------+ | 1 | Aarav Desai | Bengaluru | Silver | 2026-10-01 | 9999-12-31 | true | | 2 | Ananya Iyer | Mumbai | Basic | 2026-10-01 | 2026-10-26 | false | | 2 | Ananya Iyer | Mumbai | Gold | 2026-10-27 | 9999-12-31 | true | | 3 | Arjun Nair | Mumbai | Gold | 2026-10-01 | 2026-10-26 | false | | 3 | Arjun Nair | Pune | Gold | 2026-10-27 | 9999-12-31 | true | | 4 | Gurpreet Das | Bengaluru | Basic | 2026-10-01 | 9999-12-31 | true | | 5 | Aarav Singh | Bengaluru | Basic | 2026-10-01 | 9999-12-31 | true | | 6 | Diya Nair | Pune | Basic | 2026-10-01 | 9999-12-31 | true | | 7 | Kavya Reddy | Hyderabad | Silver | 2026-10-27 | 9999-12-31 | true | +--------------------------------+-------------------------+-------------------------+-------------------------+-----------------------------+---------------------------+-------------------------------+
    Changed customers 2 and 3 appear twice in the source. With their real key they match the current row, which is closed (eff_to 10-26, is_current false). With a NULL key they can never match, so they are inserted as new current versions. Customer 4 matched but nothing changed; customer 7 had no match and was inserted. Old values are kept.

  7. Step 7 · Re-run it: nothing changes

    -- run exactly the same MERGE again
SELECT COUNT(*) AS rows_after_rerun, SUM(IF(is_current, 1, 0)) AS current_rows
FROM dim_customer_hist;
    +-------------------+---------------+ | rows_after_rerun | current_rows | +-------------------+---------------+ | 9 | 7 | +-------------------+---------------+
    Still 9 rows with 7 current. The current rows now equal the staging values, so the change condition is false everywhere and the NULL-key branch selects nothing. An idempotent job can be safely re-run after a failure, which matters for nightly pipelines.

  8. Step 8 · Why type 2: the plan at order time

    -- point in time: the version valid on the order date
SELECT h.plan AS plan_then, COUNT(*) AS orders FROM orders o
JOIN dim_customer_hist h ON o.customer_id = h.customer_id
 AND o.order_date BETWEEN h.eff_from AND h.eff_to
WHERE o.customer_id = 2 GROUP BY h.plan;

-- current version only
SELECT h.plan AS plan_now, COUNT(*) AS orders FROM orders o
JOIN dim_customer_hist h ON o.customer_id = h.customer_id AND h.is_current
WHERE o.customer_id = 2 GROUP BY h.plan;
    +------------+---------+ | plan_then | orders | +------------+---------+ | Basic | 14 | | Gold | 5 | +------------+---------+ +-----------+---------+ | plan_now | orders | +-----------+---------+ | Gold | 19 | +-----------+---------+
    Ananya placed 14 orders as a Basic customer and 5 after upgrading. A report joined on the current row only would say all 19 orders were Gold, overstating Gold revenue. This is why finance and analytics teams ask for SCD2.
5 See it happen

How MERGE decides what to do with each row

Left: real Beeline output. Right: how MERGE routes each row.

Upserts, cardinality and SCD2 5 steps
What you see
  1. A single MERGE with DELETE, UPDATE and INSERT clauses.
  2. The result: two updates, one insert, one delete, one row untouched.
  3. Duplicate keys in the source make the MERGE fail; nothing changes.
  4. SCD2 keeps the old versions with closed date ranges.
  5. A point-in-time join splits Ananya’s orders by the plan she had then.
Behind the screen
  1. Hive joins source and target on the key, then routes each row to a clause.
  2. The first clause whose condition is true decides the action; all actions commit together.
  3. A target row may be changed by only one source row.
  4. A NULL join key forces the second copy of a changed row into the INSERT branch.
  5. Each order is matched to the version whose eff_from–eff_to range contains its date.

6 Real-world use

MERGE and SCD at work

1. Syncing OLTP databases

Change data from MySQL, PostgreSQL or Oracle is merged into the warehouse every night or hour, keeping Hive tables close to the source.

Change events→MERGE→Synced table

2. Customer and product history

Banks, insurers and retailers keep SCD2 dimensions for customers, branches and products so that reports use the attributes valid at transaction time.

Attribute change→close + insert→Point-in-time reports

3. De-duplicated event loads

When a source re-sends events, a MERGE with only WHEN NOT MATCHED THEN INSERT adds new event ids and ignores repeats.

Re-sent events→NOT MATCHED → INSERT→No duplicates

4. Audits and regulators

Auditors ask what a customer’s risk category or address was on a given date; SCD2 answers without restoring old backups.

Question about the past→BETWEEN eff dates→Answer

5. Closed accounts

Instead of deleting closed accounts, many teams MERGE an is_deleted flag, so history and joins stay complete.

op = D→UPDATE flag→History kept
