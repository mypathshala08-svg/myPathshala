1 The story

“A customer upgraded to Gold. Do we rewrite the whole table?”

Before you start: you need managed vs external tables (2.2), partitions (5.1) and ORC (6.2).

TiffinGo’s support team changes customer plans, refunds cancelled orders and deletes test accounts every day. Kabir’s tables are plain Hive tables, and his first UPDATE fails with “table … is not transactional”. The old workaround was to rewrite a whole table or partition for every correction.

K> Sir, HDFS files cannot be edited. How can Hive UPDATE anything? A> It never edits a file. On a transactional (ACID) table, an UPDATE writes two small new folders: a delete_delta that says “row 1 of write 1 is gone”, and a delta with the new version. A reader opens the base data plus all deltas and merges them. Each statement is its own transaction, so readers see either all of it or none. R> Then the folder fills up with deltas? A> Yes, and a background compactor merges them (Lesson 7.3). Today we create ACID tables, run INSERT, UPDATE and DELETE, read the real delta files, see the hidden ROW__ID, and collect the errors you will meet: non-transactional tables, partition columns, external tables, BEGIN TRANSACTION and insert-only tables. All outputs are real, from Hive 4.2.1.
2 Definition

ACID (transactional) tables in Hive

Formal definition (write this in exams)

A transactional table (ACID table) is a managed table, stored as ORC for full support, declared with TBLPROPERTIES ('transactional'='true'), on which Hive supports INSERT, UPDATE, DELETE and MERGE with atomicity, consistency, isolation (snapshot isolation) and durability. Each statement runs in its own transaction managed by the metastore. Changes are written as new delta and delete_delta directories identified by write ids; readers merge the base and delta files at read time, and a compactor periodically rewrites them into fewer files.

In simple words

An ACID table is a Hive table you can UPDATE and DELETE. Hive never changes old files; it adds small files describing the changes, and every reader combines them. Each statement either fully happens or not at all.

LEVELS> ACID tables at three levels L1> A notebook you never erase
  • Imagine a register written in pen. To change an entry you do not erase it: you add a note at the end, “entry 2 is cancelled, new entry: …”.
  • Whoever reads the register reads the original pages and all the notes, and works out the current state.
  • That is how Hive ACID tables work on HDFS, where files cannot be edited.
L2> What ACID means in Hive
  • Atomic: a statement is all or nothing. Consistent and Isolated: readers see a snapshot of committed writes (snapshot isolation). Durable: committed data stays.
  • Create with TBLPROPERTIES ('transactional'='true') on a managed ORC table. Needs hive.support.concurrency=true and hive.txn.manager=…DbTxnManager (already set in our lab).
  • Every write gets a write id; data goes into delta_<from>_<to>_<stmt>, deletes into delete_delta_…, and after major compaction into base_<writeid>.
  • Each row has a hidden ROW__ID (writeid, bucketid, rowid) that deletes refer to.
  • Insert-only tables ('transactional_properties'='insert_only') work with any format but allow only INSERT.
L3> What Hive 4.2.1 did (and refused) in our lab
  • An ACID table needed no buckets (Num Buckets −1). Old documentation saying “must be bucketed” describes Hive 1.x/2.x.
  • UPDATE = delete_delta (old row, by ROW__ID) + delta (new row) in the same write id; only the touched partitions got new folders.
  • Each statement auto-commits: START TRANSACTION → “not supported yet”.
  • Refused: UPDATE on a non-ACID table (10297), on a partition column (10292), on an insert-only table (10414), and an EXTERNAL transactional table.
  • DELETE … WHERE id IN (SELECT …) worked: subqueries are allowed in the WHERE of UPDATE and DELETE.
/LEVELS EXAM> “How does Hive support UPDATE and DELETE when HDFS files are immutable?” Answer: ACID tables write changes as new delta and delete_delta directories tagged with write ids; readers merge base and deltas using the hidden ROW__ID; compaction later merges them. Mention the requirements: managed ORC table, transactional=true, DbTxnManager, and that each statement auto-commits.

4 Step by step

Kabir’s first transactional table

All outputs are real, from the Hive 4.2.1 lab (database tiffingo).

  1. Step 1 · The settings behind ACID

    SET hive.support.concurrency;
SET hive.txn.manager;
SET hive.create.as.acid;
    | hive.support.concurrency=true | | hive.txn.manager=org.apache.hadoop.hive.ql.lockmgr.DbTxnManager | | hive.create.as.acid=false |
    The transaction manager keeps transactions, write ids and locks in the metastore database. Our lab image has it switched on. hive.create.as.acid=false means tables are not transactional unless you ask (some vendor distributions make every managed table ACID by default).

  2. Step 2 · Create a transactional table and insert

    CREATE TABLE cust_acid (customer_id INT, name STRING, city STRING, plan STRING)
STORED AS ORC TBLPROPERTIES ('transactional'='true');
INSERT INTO cust_acid SELECT customer_id, name, city, plan FROM customers WHERE customer_id <= 5;
SELECT * FROM cust_acid ORDER BY customer_id;
DESCRIBE FORMATTED cust_acid;     -- selected lines
    +------------------------+-----------------+-----------------+-----------------+ | cust_acid.customer_id | cust_acid.name | cust_acid.city | cust_acid.plan | +------------------------+-----------------+-----------------+-----------------+ | 1 | Aarav Desai | Bengaluru | Silver | | 2 | Ananya Iyer | Mumbai | Basic | | 3 | Arjun Nair | Mumbai | Gold | | 4 | Gurpreet Das | Bengaluru | Basic | | 5 | Aarav Singh | Bengaluru | Basic | +------------------------+-----------------+-----------------+-----------------+ | Table Type: | MANAGED_TABLE | | | transactional | true | | | transactional_properties | default | | Num Buckets: | -1 |
    Unlike our earlier plain CREATE TABLEs, which Hive 4 turned into external tables, this one is MANAGED: Hive must own the files to manage deltas. transactional_properties=default means full ACID. No buckets were needed.

  3. Step 3 · UPDATE, DELETE and another INSERT

    UPDATE cust_acid SET plan = 'Gold' WHERE customer_id = 2;
DELETE FROM cust_acid WHERE customer_id = 5;
INSERT INTO cust_acid VALUES (6, 'Diya Patil', 'Pune', 'Silver');
SELECT * FROM cust_acid ORDER BY customer_id;
    +------------------------+-----------------+-----------------+-----------------+ | cust_acid.customer_id | cust_acid.name | cust_acid.city | cust_acid.plan | +------------------------+-----------------+-----------------+-----------------+ | 1 | Aarav Desai | Bengaluru | Silver | | 2 | Ananya Iyer | Mumbai | Gold | | 3 | Arjun Nair | Mumbai | Gold | | 4 | Gurpreet Das | Bengaluru | Basic | | 6 | Diya Patil | Pune | Silver | +------------------------+-----------------+-----------------+-----------------+
    Ananya is now Gold, Aarav Singh (5) is gone, Diya (6) is new. Each statement committed on its own; there is no BEGIN … COMMIT around them.

  4. Step 4 · What changed on disk

    find /opt/hive/data/warehouse/tiffingo.db/cust_acid | sort
    delete_delta_0000002_0000002_0000/bucket_00000_0 ← UPDATE (write 2): old version of customer 2 deleted delete_delta_0000003_0000003_0000/bucket_00000_0 ← DELETE (write 3): customer 5 delta_0000001_0000001_0000/bucket_00000_0 ← INSERT (write 1): customers 1–5 delta_0000002_0000002_0001/bucket_00000_0 ← UPDATE (write 2): new version of customer 2 delta_0000004_0000004_0000/bucket_00000_0 ← INSERT (write 4): customer 6 (each folder also holds _orc_acid_version)
    Four statements, five folders, and no existing file was modified. The folder names carry the write id twice (a range, so compaction can merge several) and a statement number. The UPDATE produced a delete_delta and a delta with the same write id 2: it is one transaction.

  5. Step 5 · Read the delta files

    hive --orcfiledump -d <folder>/bucket_00000_0
    $ hive --orcfiledump -d delete_delta_0000002_0000002_0000/bucket_00000_0 {"operation":2,"originalTransaction":1,"bucket":536870912,"rowId":1,"currentTransaction":2,"row":null} $ hive --orcfiledump -d delete_delta_0000003_0000003_0000/bucket_00000_0 {"operation":2,"originalTransaction":1,"bucket":536870912,"rowId":4,"currentTransaction":3,"row":null} $ hive --orcfiledump -d delta_0000002_0000002_0001/bucket_00000_0 {"operation":0,"originalTransaction":2,"bucket":536870913,"rowId":0,"currentTransaction":2, "row":{"customer_id":2,"name":"Ananya Iyer","city":"Mumbai","plan":"Gold"}}
    A delete record stores no data, only which row it kills: “row 1 of write 1” (customer 2’s old version) and “row 4 of write 1” (customer 5). Operation 0 is an insert, 2 a delete. The new version of customer 2 is a fresh row created by write 2. This is how Hive “updates” immutable files.

  6. Step 6 · The hidden ROW__ID

    SELECT ROW__ID, customer_id, plan FROM cust_acid ORDER BY customer_id;
    +-----------------------------------------------+--------------+---------+ | row__id | customer_id | plan | +-----------------------------------------------+--------------+---------+ | {"writeid":1,"bucketid":536870912,"rowid":0} | 1 | Silver | | {"writeid":2,"bucketid":536870913,"rowid":0} | 2 | Gold | | {"writeid":1,"bucketid":536870912,"rowid":2} | 3 | Gold | | {"writeid":1,"bucketid":536870912,"rowid":3} | 4 | Basic | | {"writeid":4,"bucketid":536870912,"rowid":0} | 6 | Silver | +-----------------------------------------------+--------------+---------+
    Customers 1, 3 and 4 still come from write 1 (rows 0, 2, 3). Customer 2 now comes from write 2 and customer 6 from write 4. Readers drop any row whose (writeid, bucketid, rowid) appears in a delete_delta. The bucketid value also encodes the statement number, which is why the updated row shows 536870913.

  7. Step 7 · Partitioned ACID: refunds in one day

    CREATE TABLE orders_acid (order_id INT, customer_id INT, amount DECIMAL(10,2), status STRING)
PARTITIONED BY (order_date DATE) STORED AS ORC TBLPROPERTIES ('transactional'='true');
INSERT INTO orders_acid PARTITION (order_date)
  SELECT order_id, customer_id, amount, status, order_date FROM orders WHERE order_date <= '2026-10-03';

UPDATE orders_acid SET status = 'REFUNDED' WHERE order_date = '2026-10-02' AND status = 'CANCELLED';
DELETE FROM orders_acid WHERE order_id IN
  (SELECT order_id FROM orders WHERE order_date = '2026-10-03' AND amount < 50);

SELECT order_date, status, COUNT(*) AS n FROM orders_acid GROUP BY order_date, status;
$ find …/orders_acid -maxdepth 2 -type d
    +-------------+------------+-------+ | order_date | status | n | +-------------+------------+-------+ | 2026-10-01 | CANCELLED | 98 | | 2026-10-01 | DELIVERED | 1511 | | 2026-10-01 | REFUNDED | 32 | | 2026-10-02 | DELIVERED | 1476 | | 2026-10-02 | REFUNDED | 141 | | 2026-10-03 | CANCELLED | 106 | | 2026-10-03 | DELIVERED | 1527 | | 2026-10-03 | REFUNDED | 35 | +-------------+------------+-------+ ./order_date=2026-10-01/delta_0000001_0000001_0000 ./order_date=2026-10-02/delete_delta_0000002_0000002_0000 ./order_date=2026-10-02/delta_0000001_0000001_0000 ./order_date=2026-10-02/delta_0000002_0000002_0001 ./order_date=2026-10-03/delete_delta_0000003_0000003_0000 ./order_date=2026-10-03/delta_0000001_0000001_0000
    All 102 cancelled orders of 2 October became refunds (39 + 102 = 141), and 40 cheap orders of 3 October were deleted (1,668 → 1,628). Partition pruning works for DML too: 1 October was not touched, and each change landed only in its own partition folder.

  8. Step 8 · What ACID refuses

    UPDATE customers …;  START TRANSACTION;  CREATE EXTERNAL TABLE … transactional …;
UPDATE orders_acid SET order_date = …;  UPDATE events_mm …;
    > UPDATE customers SET plan = 'Gold' WHERE customer_id = 2; Error: … [Error 10297]: Attempt to do update or delete on table customers that is not transactional > START TRANSACTION; Error: … IllegalStateException START_TRANSACTION is not supported yet. > CREATE EXTERNAL TABLE ext_acid (id INT) STORED AS ORC TBLPROPERTIES ('transactional'='true'); Error: … MetaException(message:tiffingo.ext_acid cannot be declared transactional because it's an external table) > UPDATE orders_acid SET order_date = '2026-10-02' WHERE order_id = 100013; Error: … [Error 10292]: Updating values of partition columns is not supported > UPDATE events_mm SET event = 'x' WHERE id = 1; -- insert-only table Error: … [Error 10414]: Attempt to do update or delete on table events_mm that is insert-only transactional
    Five real refusals: the table must be transactional and managed; there are no multi-statement transactions; you cannot move a row to another partition with UPDATE (delete and insert it instead); and insert-only tables accept only INSERT.
5 See it happen

How an UPDATE becomes two small folders

Left: real Beeline output. Right: what the metastore and the folders record.

Deltas, delete deltas and ROW__ID 5 steps
What you see
  1. UPDATE fails on a plain table; a transactional table is managed.
  2. The first INSERT creates a delta folder for write 1.
  3. UPDATE writes a delete_delta and a delta in the same write.
  4. DELETE writes only the id of the dead row.
  5. ROW__ID shows which write produced each visible row.
Behind the screen
  1. The metastore tracks transactions, write ids and locks for transactional tables.
  2. Each row is identified by its write id and row number.
  3. The old version is marked deleted and a new version is written; old files stay untouched.
  4. A delete record points at (write, bucket, row) with no data.
  5. Readers combine all folders, skipping rows listed in delete deltas.

Three live scenarios follow: deleting a customer’s data, correcting a day of orders, and choosing a table type.

Real-time scenario 1

Deleting one customer’s data on request

Data-protection requests are a classic reason for ACID tables. (Typical process; the DELETE pattern ran in our lab.)

Right to erasure 5 steps
Animated example
  1. A customer requests deletion of their data.
  2. One DELETE per table marks the rows.
  3. The old row versions remain in files until compaction.
  4. Major compaction rewrites the data without them.
  5. Batch daily requests into one statement.
Real-time scenario 2

Correcting a day of orders safely

A set-based UPDATE on one partition, with real results.

Data corrections 5 steps
Animated example
  1. The payments team sends a correction.
  2. One UPDATE fixes all 102 orders.
  3. Only that day’s partition gets new delta folders.
  4. Readers see either the old or the new state, never a mix.
  5. Avoid row-by-row updates.
Real-time scenario 3 · advanced

Choosing between external, insert-only, ACID and Iceberg

A design decision every Hive warehouse faces. (Typical guidance.)

Table type choice 5 steps
Animated example
  1. ACID has costs, so use it where needed.
  2. Append-only facts do not need UPDATE.
  3. Changing dimensions are the classic ACID use.
  4. If other engines must write the table, consider Iceberg.
  5. Use transactional tables only where rows change.
6 Real-world use

ACID tables at work

1. Privacy deletions

Data-protection laws such as India’s DPDP Act and Europe’s GDPR give people rights over their personal data; ACID DELETE plus compaction removes a person’s rows without rebuilding tables.

Request→DELETE + compact→Data removed

2. Late corrections

Refunds, chargebacks and status changes arrive after the original load; a set-based UPDATE fixes them in the right partitions.

Correction feed→UPDATE→Accurate reports

3. Nightly upserts from databases

Changes from MySQL or PostgreSQL (CDC) are merged into Hive dimension tables every night with MERGE (Lesson 7.2).

CDC changes→MERGE→Current dimensions

4. Atomic loads

Insert-only transactional tables guarantee that a failed load leaves no partial files visible to readers.

Load job→insert-only ACID→All or nothing

5. Streaming ingestion

Hive’s streaming API writes micro-batches as transactions into ACID tables, so data is queryable within minutes (with compaction keeping deltas in check).

Events→transactions→Fresh table
