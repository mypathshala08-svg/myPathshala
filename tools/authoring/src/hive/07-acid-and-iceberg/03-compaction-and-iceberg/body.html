1 The story

“The customer table has 11 delta folders, and data science wants last week’s data back”

Before you start: finish 7.1 and 7.2; partitioning (5.1) and Parquet (6.3) help too.

After a week of updates, Kabir’s ACID tables are full of small delta folders. At the same time the data science team, which works in Spark, asks two things Hive ACID cannot easily give: a table they can also write from Spark, and “the orders table exactly as it was before yesterday’s correction”.

K> Sir, who cleans up all these delta folders? A> The compactor. Minor compaction merges deltas into one delta; major compaction rewrites everything into a new base. It runs on its own when thresholds are crossed, or when you ask with ALTER TABLE … COMPACT. R> And the request for last week’s data? A> That is what Apache Iceberg is built for. Hive 4 creates Iceberg tables with STORED BY ICEBERG. Every change becomes a snapshot you can query (time travel) or return to (rollback), partitions can change without rewriting data, and Spark, Trino and Flink read and write the same table. Today we do both, on real data, including two things Hive 4.2.1 refused. All outputs are real.
2 Definition

Compaction and Apache Iceberg

Formal definition (write this in exams)

Compaction is the background process that rewrites a transactional table’s delta and delete-delta files into fewer files: minor compaction combines deltas into a single delta per bucket, and major compaction combines the base and all deltas into a new base, physically removing deleted rows. Apache Iceberg is an open table format for large analytic tables: a table is a set of immutable data files described by versioned metadata (metadata files, manifest lists and manifests). Each committed change creates a new snapshot, which enables time travel, rollback, schema evolution and partition evolution, with hidden partitioning and concurrent access from multiple engines.

In simple words

Compaction tidies an ACID table by merging its many small change files. Iceberg is a newer way to store tables: it records every change as a snapshot, so you can look at the table as it was, go back to an earlier version, change partitions or columns safely, and share the table with Spark and Trino.

LEVELS> Compaction and Iceberg at three levels L1> Tidying up and keeping photos
  • Compaction is tidying a drawer full of sticky notes: you copy everything onto one clean page and throw the notes away.
  • Iceberg keeps a photo of the table after every change. You can look at an old photo (time travel) or decide the old photo is the truth again (rollback).
  • Both exist because files in a data lake are never edited, only added.
L2> How each works
  • Hive ACID compaction: minor merges delta (and delete_delta) folders into one; major merges base + deltas into a new base_N, physically removing deleted rows. The metastore’s initiator queues compactions when thresholds are crossed (for example more than 10 deltas, hive.compactor.delta.num.threshold), workers run them, and a cleaner removes the old folders.
  • Iceberg table: data files (Parquet by default in Hive 4) plus a metadata tree: metadata.json (schema, partition specs, snapshots) → manifest list per snapshot → manifests listing data files and their statistics.
  • Hidden partitioning: PARTITIONED BY SPEC (day(order_date)). Queries filter on order_date, and Iceberg prunes; no extra partition column.
  • Iceberg v2 tables support UPDATE, DELETE and MERGE with merge-on-read delete files.
L3> What we saw in Hive 4.2.1
  • ACID compaction needed the compactor configured on HiveServer2 and the metastore (in our Docker lab we had to give HiveServer2 the metastore database connection). Then the initiator compacted an 11-delta table on its own; a manual MINOR on the same table was refused (“None of the compaction thresholds met”).
  • Iceberg defaults: format version 2, Parquet with ZSTD, merge-on-read, Iceberg 1.9.1.
  • Snapshot summaries count rows in data files: after deleting 40 rows total-records stayed 5,028 because the delete is a separate position-delete file.
  • Partition evolution worked without rewriting old files, but afterwards INSERT OVERWRITE was refused until data is rewritten to the new spec.
  • Hive’s built-in Iceberg compaction refused our small test tables (“doesn’t meet requirements for compaction”); a manual rewrite with INSERT OVERWRITE merged 16 files into 1.
  • EXPIRE_SNAPSHOTS removed old snapshots (and with them, time travel to those points).
/LEVELS EXAM> Two frequent questions. “Minor vs major compaction”: minor merges deltas into one delta; major rewrites base + deltas into a new base and removes deleted rows; both are triggered by thresholds or ALTER TABLE … COMPACT. “What is Iceberg and why use it?”: an open table format with snapshot-based metadata giving ACID commits, time travel, rollback, schema and partition evolution, hidden partitioning and multi-engine access.

4 Step by step

Compacting ACID tables, then a full Iceberg tour

All outputs are real, from the Hive 4.2.1 lab (database tiffingo). File names are shortened.

  1. Step 1 · Automatic compaction after too many deltas

    -- cust_acid from Lesson 7.1, after six more single-row INSERTs: 11 delta / delete_delta folders
-- (initiator enabled on the metastore, worker on HiveServer2)
$ ls …/cust_acid
SHOW COMPACTIONS;
ALTER TABLE cust_acid COMPACT 'minor' AND WAIT;
    $ ls …/cust_acid base_0000010_v0000045 > SHOW COMPACTIONS; (selected columns) | id | table | type | state | initiatorid | errormessage | | 2 | cust_acid | MINOR | refused | manual | None of the compaction thresholds met, compaction request is refused! | | 1 | cust_acid | MAJOR | succeeded | 60 | |
    With 11 delta folders the table crossed the default threshold of 10, and the initiator queued a MAJOR compaction by itself (initiator id 60, not “manual”). All folders became one base_0000010 (data up to write 10). Our manual MINOR request afterwards was refused: there was nothing worth compacting.

  2. Step 2 · Minor compaction by hand

    ALTER TABLE dim_customer_hist COMPACT 'minor' AND WAIT;
    $ ls …/dim_customer_hist (before) delete_delta_0000002_0000002_0000 delta_0000001_0000001_0000 delta_0000002_0000002_0002 delta_0000002_0000002_0005 delta_0000002_0000002_0006 > ALTER TABLE dim_customer_hist COMPACT 'minor' AND WAIT; $ ls …/dim_customer_hist (after) delete_delta_0000001_0000003_v0000052 delta_0000001_0000003_v0000052
    The four delta folders of writes 1–2 became one delta covering writes 1 to 3, and the delete delta was merged the same way. A minor compaction leaves deletes as delete records; it makes reads cheaper by reducing the number of folders. The _v0000052 suffix is the compaction’s own transaction id.

  3. Step 3 · Major compaction of one partition

    ALTER TABLE orders_acid PARTITION (order_date='2026-10-02') COMPACT 'major' AND WAIT;
    $ ls …/orders_acid/order_date=2026-10-02 (before) delete_delta_0000002_0000002_0000 delta_0000001_0000001_0000 delta_0000002_0000002_0001 > ALTER TABLE orders_acid PARTITION (order_date='2026-10-02') COMPACT 'major' AND WAIT; > SELECT status, COUNT(*) AS n FROM orders_acid WHERE order_date = '2026-10-02' GROUP BY status; | DELIVERED | 1476 | | REFUNDED | 141 | $ ls …/orders_acid/order_date=2026-10-02 (after) base_0000003_v0000049
    The three folders of 2 October (original insert, refund update) became one base. The 102 superseded rows are now physically gone, the counts are identical, and the other partitions were not touched. Major compaction is what finally removes deleted personal data from disk (Lesson 7.1, scenario 1).

  4. Step 4 · An Iceberg table with hidden partitioning

    CREATE TABLE orders_ice (order_id INT, customer_id INT, city STRING,
  amount DECIMAL(10,2), status STRING, order_date DATE)
PARTITIONED BY SPEC (day(order_date))
STORED BY ICEBERG;
INSERT INTO orders_ice SELECT order_id, customer_id, city, amount, status, order_date
FROM orders WHERE order_date <= '2026-10-03';
DESCRIBE FORMATTED orders_ice;       -- selected lines
    +-------------+-------+ | order_date | n | +-------------+-------+ | 2026-10-01 | 1641 | | 2026-10-02 | 1617 | | 2026-10-03 | 1668 | +-------------+-------+ | Table Type: | EXTERNAL_TABLE | | | table_type | ICEBERG | | | format-version | 2 | | | storage_handler | org.apache.iceberg.mr.hive.HiveIcebergStorageHandler | | | write.delete.mode | merge-on-read | | | write.update.mode | merge-on-read | | | write.merge.mode | merge-on-read | | | parquet.compression | zstd | | | default-partition-spec | {"spec-id":0,"fields":[{"name":"order_date_day","transform":"day",…}]} | | | metadata_location | file:/…/orders_ice/metadata/00003-57d22a3d-….metadata.json | | | current-snapshot-summary | {"added-data-files":"3","added-records":"4926",…,"iceberg-version":"Apache Iceberg 1.9.1 …"} |
    order_date stays an ordinary column; the partition order_date_day is derived by the day() transform. Our lab’s defaults: Iceberg 1.9.1, format version 2, Parquet with ZSTD, and merge-on-read for updates and deletes. The metastore stores only a pointer, metadata_location, to the current metadata file.

  5. Step 5 · UPDATE and DELETE create snapshots

    UPDATE orders_ice SET status = 'REFUNDED' WHERE order_date = '2026-10-02' AND status = 'CANCELLED';
DELETE FROM orders_ice WHERE order_date = '2026-10-03' AND amount < 50;
SELECT snapshot_id, parent_id, operation,
  summary['added-records'] AS added_rows, summary['added-position-deletes'] AS pos_deletes,
  summary['total-records'] AS total_rows
FROM tiffingo.orders_ice.snapshots ORDER BY committed_at;
$ find …/orders_ice -type f | sort
    +----------------------+----------------------+------------+-------------+--------------+-------------+ | snapshot_id | parent_id | operation | added_rows | pos_deletes | total_rows | +----------------------+----------------------+------------+-------------+--------------+-------------+ | 4523378673848349691 | NULL | append | 4926 | NULL | 4926 | | 303231479046229805 | 4523378673848349691 | overwrite | 102 | 102 | 5028 | | 4541262957374694773 | 303231479046229805 | delete | NULL | 40 | 5028 | +----------------------+----------------------+------------+-------------+--------------+-------------+ ./data/order_date_day=2026-10-01/…-00001.parquet ./data/order_date_day=2026-10-02/…-00002.parquet ./data/order_date_day=2026-10-02/…-00001-pos-deletes.parquet ← UPDATE: old rows ./data/order_date_day=2026-10-02/…-00001.parquet ← UPDATE: new rows ./data/order_date_day=2026-10-03/…-00003.parquet ./data/order_date_day=2026-10-03/…-00001-pos-deletes.parquet ← DELETE ./metadata/00000-….metadata.json … 00007-….metadata.json ← table versions ./metadata/snap-4523378673848349691-1-….avro ← manifest lists ./metadata/…-m0.avro ← manifests
    Three commits, three snapshots, each pointing to its parent. The UPDATE wrote 102 new rows and a position-delete file for the 102 old ones; the DELETE wrote only a position-delete file. Note total-records stays 5,028: it counts rows in data files, and deleted rows are hidden by delete files until compaction. A real COUNT(*) gives 4,886.

  6. Step 6 · Time travel

    SELECT COUNT(*) AS rows_v1, SUM(IF(status = 'CANCELLED', 1, 0)) AS cancelled_v1
FROM orders_ice FOR SYSTEM_VERSION AS OF 4523378673848349691;
SELECT COUNT(*) AS rows_now, SUM(IF(status = 'CANCELLED', 1, 0)) AS cancelled_now FROM orders_ice;

SELECT COUNT(*) AS rows_at_10_07_10 FROM orders_ice FOR SYSTEM_TIME AS OF '2026-10-27 10:07:10';
    +----------+---------------+ | rows_v1 | cancelled_v1 | +----------+---------------+ | 4926 | 306 | +----------+---------------+ +-----------+----------------+ | rows_now | cancelled_now | +-----------+----------------+ | 4886 | 198 | +-----------+----------------+ +-------------------+ | rows_at_10_07_10 | +-------------------+ | 4926 | +-------------------+
    The first snapshot still shows 4,926 rows and 306 cancelled orders; today there are 4,886 rows and 198 cancelled orders. A timestamp works too: at 10:07:10 (UTC) only the first snapshot existed. This is how data science gets “the table before yesterday’s correction” without a backup.

  7. Step 7 · Schema and partition evolution without rewriting

    ALTER TABLE orders_ice ADD COLUMNS (payment STRING);
ALTER TABLE orders_ice SET PARTITION SPEC (month(order_date));
INSERT INTO orders_ice SELECT order_id, customer_id, city, amount, status, order_date, payment
FROM orders WHERE order_date BETWEEN '2026-10-04' AND '2026-10-05';
SELECT order_date, COUNT(*) AS n, COUNT(payment) AS with_payment FROM orders_ice
GROUP BY order_date ORDER BY order_date;
SELECT spec_id, COUNT(*) AS files FROM tiffingo.orders_ice.files GROUP BY spec_id;
$ ls …/orders_ice/data
    +-------------+-------+---------------+ | order_date | n | with_payment | +-------------+-------+---------------+ | 2026-10-01 | 1641 | 0 | | 2026-10-02 | 1617 | 0 | | 2026-10-03 | 1628 | 0 | | 2026-10-04 | 1744 | 1744 | | 2026-10-05 | 1621 | 1621 | +-------------+-------+---------------+ +----------+--------+ | spec_id | files | +----------+--------+ | 0 | 6 | | 1 | 1 | +----------+--------+ order_date_day=2026-10-01 order_date_day=2026-10-02 order_date_day=2026-10-03 order_date_month=2026-10
    Old rows read NULL for the new column. New data was written by month while old files stayed in day folders; Iceberg keeps both partition specs (spec 0 and 1) and prunes each correctly. In a plain Hive table either change would mean creating a new table and copying everything (Module 5). A query on 2 October still read only that day’s 1,617 rows.

  8. Step 8 · Rollback and expiring snapshots

    ALTER TABLE orders_ice EXECUTE ROLLBACK(4541262957374694773);
SELECT COUNT(*) AS after_rollback FROM orders_ice;
SELECT made_current_at, snapshot_id, is_current_ancestor FROM tiffingo.orders_ice.history;

-- on events_ice (17 snapshots):
ALTER TABLE events_ice EXECUTE EXPIRE_SNAPSHOTS('<current UTC time + 1 minute>');
SELECT COUNT(*) AS snapshots FROM tiffingo.events_ice.snapshots;
SELECT COUNT(*) FROM events_ice FOR SYSTEM_TIME AS OF '2026-10-27 10:12:00';
    +------------------+ | before_rollback | +------------------+ | 8251 | +------------------+ +-----------------+ | after_rollback | +------------+ | snapshots | Error: Error while compiling statement: FAILED: IllegalArgumentException Cannot find a snapshot older than 2026-10-27T10:12:00+00:00
    Rollback made the snapshot before the 5 October load current again: 8,251 → 4,886 rows, instantly, without copying data. The history shows the abandoned snapshot as no longer an ancestor. Expiring snapshots kept only the latest one, and time travel to an expired point now fails.

  9. Step 9 · Compacting Iceberg in Hive 4.2.1

    -- events_ice: 15 small INSERTs and one DELETE → 15 data files + 1 delete file
ALTER TABLE events_ice COMPACT 'major' AND WAIT;
INSERT OVERWRITE TABLE events_ice SELECT * FROM events_ice;

-- orders_ice after partition evolution:
INSERT OVERWRITE TABLE orders_ice SELECT * FROM orders_ice;
    > SHOW COMPACTIONS; (selected columns) | 11 | events_ice | MAJOR | refused | | 8 | orders_ice | SMART_OPTIMIZE | refused | HiveServer2 log: IcebergCompactionService: Table=events_ice doesn't meet requirements for compaction > INSERT OVERWRITE TABLE events_ice SELECT * FROM events_ice; -- manual rewrite > SELECT content, COUNT(*) AS files, SUM(record_count) FROM tiffingo.events_ice.files GROUP BY content; | 0 | 1 | 24236 | (before: 15 data files + 1 delete file) Error: … Cannot perform insert overwrite query on Iceberg table where partition evolution happened. In order to successfully carry out any insert overwrite operation on this table, the data has to be rewritten conforming to the latest spec.
    Hive 4.2.1 has built-in Iceberg compaction (COMPACT and OPTIMIZE TABLE), but its evaluator decides whether a table is worth compacting, and it refused our small tables. Rewriting with INSERT OVERWRITE worked on events_ice: 16 files became one with the same 24,236 rows. On orders_ice the overwrite was refused after partition evolution. In production, check SHOW COMPACTIONS, or run Iceberg’s rewrite_data_files from Spark.
5 See it happen

Merging deltas and travelling in time

Left: real Beeline output. Right: what the compactor and Iceberg metadata do.

Merging deltas and travelling in time 5 steps
What you see
  1. The initiator compacted an 11-delta table into one base, on its own.
  2. A manual minor compaction merged four deltas into one.
  3. Each Iceberg commit adds a snapshot; deletes are separate files.
  4. Time travel reads the table as it was at an earlier snapshot.
  5. Rollback restores an older snapshot; expired snapshots are gone for good.
Behind the screen
  1. The metastore’s initiator queues work when thresholds are crossed; workers rewrite; the cleaner deletes old folders.
  2. Minor compaction combines deltas; deleted rows remain as delete records.
  3. metadata.json points to a manifest list, which points to manifests, which list data and delete files.
  4. A query AS OF a snapshot uses that snapshot’s manifest list and ignores newer files.
  5. The table’s current pointer moves back; later snapshots are kept until expired.

6 Real-world use

Compaction and Iceberg at work

1. Keeping ACID tables fast

Warehouses with nightly MERGEs rely on the compactor; platform teams tune thresholds and watch SHOW COMPACTIONS like any other job.

Many deltas→compactor→Few files

2. Reproducible ML training data

Data scientists record the snapshot id used to train a model, so the exact training data can be read again months later.

Model training→snapshot id→Same data later

3. Safe pipelines

If a load is wrong, teams roll the table back to the previous snapshot in seconds instead of restoring backups.

Bad load→rollback→Good data

4. The open lakehouse

Iceberg tables in a shared catalog are written by Spark and Flink and queried by Hive, Trino and cloud engines without copies.

Many engines→Iceberg→One table

5. Changing partitioning as data grows

A table partitioned by month when small can move to day partitions when it grows, without rewriting history.

Growth→SET PARTITION SPEC→New layout
