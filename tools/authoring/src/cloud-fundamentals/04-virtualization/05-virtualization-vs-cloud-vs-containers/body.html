2 Definition

Virtualization vs cloud computing vs containers

Formal definition (write this in exams)

Virtualization is a technology that creates virtual instances of computing resources — servers, storage, networks — on physical hardware, typically through a hypervisor. Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources that can be rapidly provisioned and released with minimal management effort (NIST SP 800-145); it usually relies on virtualization plus automation, self-service and metering. A container is a lightweight, OS-level virtualization unit that packages an application with its dependencies and runs as isolated processes sharing the host kernel.

In simple words

Virtualization splits hardware. Cloud sells those pieces as a self-service, pay-per-use utility. Containers package an app so it runs the same anywhere, sharing the machine’s kernel.

Say it in an interview

30-second answer you can speak:

  • “Virtualization is a technology — a hypervisor splitting one server into VMs. Cloud computing is a delivery model with self-service, broad network access, pooling, rapid elasticity and measured service; it is usually built on virtualization plus automation and billing.”
  • “A virtualized data centre where admins create VMs after a ticket is not a cloud; it becomes a private cloud only with self-service, automation and metering.”
  • “VMs have their own kernel and are GBs; containers share the host kernel, are MBs and start in milliseconds; serverless hides servers entirely — Lambda and Fargate run each workload in a Firecracker micro-VM.”

Type 1 · Virtualized data centre

Definition (say it in an interview): A virtualized data centre runs its workloads as virtual machines on hypervisor clusters owned and operated by the organization, but VMs are requested, approved and created by administrators rather than through on-demand self-service, and usage is not metered per consumer.

In plain words (no jargon): The company owns its servers and uses virtual machines, but to get one you must ask the IT team and wait. It is efficient hardware with a slow, manual process.

Analogy: A restaurant kitchen with modern equipment but only one chef taking orders on paper: the stoves are efficient, yet every dish waits in the order queue.

How it works internally, step by step

  1. Hosts and hypervisors. The company buys servers and runs a hypervisor cluster.
  2. Request. A user asks for a VM through a ticket or email.
  3. Approval. A manager approves capacity and cost.
  4. Manual build. An admin creates the VM, asks for an IP, installs software.
  5. Hand-over. The user gets credentials; costs stay in one shared IT budget.

Words used above, in simple terms: vCenter = VMware’s management console · ticket = a tracked request in a help-desk system · chargeback / showback = billing (or showing) each team its usage

Use it when: workloads are stable, regulations require on-premises hosting and demand rarely changes.
Avoid / be careful when: teams need servers quickly or often — the ticket process, not the technology, becomes the bottleneck.

Type 2 · Private cloud

Definition (say it in an interview): A private cloud provides cloud characteristics — on-demand self-service, resource pooling, rapid elasticity within its capacity, broad network access and measured service — on infrastructure used exclusively by one organization, whether hosted on its premises or by a third party.

In plain words (no jargon): Your company keeps its own servers but runs them like a cloud: teams create servers themselves through a website or command, and each team can see how much it uses.

Analogy: A company canteen with a self-service counter and a swipe card: same kitchen the company owns, but employees serve themselves and each department sees its monthly bill.

How it works internally, step by step

  1. Pool hardware. Hypervisor hosts, storage and networks are pooled.
  2. Add a cloud control plane. Software such as OpenStack provides APIs for compute, network, storage and identity.
  3. Projects and quotas. Each team gets a project with limits.
  4. Self-service. Users create VMs, networks and volumes through portal/API/Terraform.
  5. Schedule. The scheduler places VMs on hosts with capacity.
  6. Meter. Usage is collected per project for showback/chargeback.

Words used above, in simple terms: OpenStack = open-source software to build private clouds · control plane = the software brain that takes API requests and orchestrates · quota = a usage limit per team · showback = showing each team its usage without billing

Type 3 · Public cloud virtual machines (IaaS)

Definition (say it in an interview): A public cloud VM is a virtual machine rented on demand from a cloud provider’s shared, multi-tenant infrastructure through self-service APIs, billed per second or hour, with the provider operating the hardware and hypervisor and the customer managing the guest OS and everything above it.

In plain words (no jargon): You rent a virtual computer from a company like AWS over the internet, start it in about a minute, and pay only while it runs. They look after the hardware; you look after what runs inside.

Analogy: Renting a fully furnished flat by the night through an app: you pick size and city, get the key instantly, pay per night; the owner maintains the building, you keep your flat clean.

How it works internally, step by step

  1. Self-service API call. Console, CLI or Terraform calls RunInstances.
  2. Identity check. IAM verifies you may launch that type.
  3. Quota and capacity. Account limits and AZ capacity are checked.
  4. Placement. A scheduler picks a physical host.
  5. Virtualization. The hypervisor creates the VM; Nitro attaches EBS and network.
  6. Metering. Per-second billing starts while it is running.

Words used above, in simple terms: IaaS = infrastructure as a service: rented VMs, disks, networks · multi-tenant = many customers share the same hardware · per-second billing = you pay for the exact seconds used (with a minimum)

Type 4 · Containers with an orchestrator (Kubernetes, ECS)

Definition (say it in an interview): Containers package an application with its dependencies and run as isolated processes sharing a host kernel; a container orchestrator such as Kubernetes or Amazon ECS schedules them across a cluster of machines (usually VMs), keeps the desired number running, connects them and rolls out new versions.

In plain words (no jargon): Programs are packed in small boxes (containers). A manager program (like Kubernetes) decides which computer runs which box, keeps the right number running, and restarts boxes that fail.

Analogy: A food court manager: stalls (containers) are placed in free spaces (nodes); if one counter breaks, the manager immediately sets the stall up at another counter, and adds more counters at lunchtime.

How it works internally, step by step

  1. Build an image. Dockerfile → image pushed to a registry (ECR, Docker Hub).
  2. Declare desired state. YAML/JSON says: image, replicas, CPU/memory, ports.
  3. Schedule. The scheduler picks nodes with enough free resources.
  4. Run. On each node the container runtime creates namespaces and cgroups and starts the container.
  5. Connect. Services and load balancers give the pods a stable address.
  6. Reconcile forever. Controllers compare actual vs desired state and fix differences (restart, reschedule, scale).

Words used above, in simple terms: orchestrator = software that runs containers across many machines · node = a machine (usually a VM) in the cluster · pod = Kubernetes’ smallest unit: one or more containers · Deployment = a declaration of how many copies of which image to run · reconcile = continuously make reality match the declaration

Type 5 · Serverless containers (Fargate, Cloud Run, Container Apps)

Definition (say it in an interview): Serverless containers run container images on infrastructure fully managed by the cloud provider: you specify the image and the CPU/memory per task, and the platform provisions, isolates, scales and patches the underlying servers, billing per resource-second.

In plain words (no jargon): You hand the cloud a packaged app (a container) and say how much CPU and memory it needs. The cloud runs it somewhere and charges you only for that time — you never see or manage a server.

Analogy: Ordering from a cloud kitchen instead of running your own: you give the recipe (image) and portion size; where and on which stove it is cooked is not your concern.

How it works internally, step by step

  1. Register a task/service. Image, CPU, memory, ports, IAM role, network.
  2. Request to run. A service or schedule asks for N tasks.
  3. Capacity found. The provider selects hosts in its fleet.
  4. Isolation. Fargate runs each task in its own Firecracker micro-VM; Cloud Run uses its own sandboxing.
  5. Networking. Each task gets an ENI/IP in your VPC (Fargate awsvpc mode).
  6. Bill and scale. Per vCPU-second and GB-second; scale on CPU, requests or schedule.

Words used above, in simple terms: task definition = ECS’s description of how to run a container · task = one running copy · awsvpc mode = each task gets its own network card in your VPC · GB-second = one GB of memory for one second — a billing unit

Type 6 · Serverless functions (FaaS)

Definition (say it in an interview): Function as a Service (FaaS) runs small units of code in response to events, with the provider managing all servers, runtimes and scaling; functions are short-lived and stateless, scale automatically including to zero, and are billed per request and per unit of execution time.

In plain words (no jargon): You upload only a small piece of code. It runs automatically whenever something happens — a web request, a file upload — and you pay only for those few milliseconds. When nothing happens, nothing runs.

Analogy: A taxi instead of owning a car: it comes when you call, you pay per ride, and when you do not need it, it costs nothing — but you cannot keep your luggage in it overnight.

How it works internally, step by step

  1. Upload code. A zip or container image with a handler function, runtime and memory size.
  2. Connect a trigger. API Gateway/function URL, S3 event, queue, schedule.
  3. Event arrives. The service finds a warm execution environment or creates one (cold start: micro-VM + runtime + init code).
  4. Run handler. Your function runs with the event; one environment handles one request at a time.
  5. Scale. More concurrent events → more environments, up to account limits.
  6. Freeze and reuse. Idle environments are frozen, reused for later calls, then removed.

Words used above, in simple terms: FaaS = function as a service · handler = the function the platform calls · cold start = the extra time to prepare a new environment · stateless = keeps nothing between calls — store state in a database · concurrency = how many copies run at the same time

Type 7 · Micro-VMs (Firecracker)

Definition (say it in an interview): A micro-VM is a lightweight virtual machine with a minimal device model and a stripped-down monitor, designed to boot in around a hundred milliseconds with very small memory overhead, combining the hardware-level isolation of VMs with the speed and density of containers. Firecracker is AWS’s open-source micro-VM monitor used by Lambda and Fargate.

In plain words (no jargon): A tiny virtual machine that starts almost as fast as a container. Each piece of customer code gets its own, so different customers are separated by a real VM wall.

Analogy: A capsule hotel: each guest gets a real private locked capsule (own walls, unlike a hostel bunk), but it is tiny, cheap and ready in seconds compared with a full hotel room.

How it works internally, step by step

  1. Bare-metal host with KVM. Firecracker runs as a normal Linux process using KVM for hardware-assisted virtualization.
  2. Jailer. Each Firecracker process is locked down (cgroups, namespaces, seccomp) before it starts a VM.
  3. Minimal devices. Only virtio-net, virtio-block, a serial console and a minimal keyboard controller (used to reset) are emulated.
  4. Fast boot. A small guest kernel boots in about 125 ms; memory overhead under 5 MiB per micro-VM.
  5. Run the workload. The function runtime or container starts inside.
  6. Dense packing. Thousands of micro-VMs can run on one host.

Words used above, in simple terms: micro-VM = a very small, fast-booting VM · VMM = virtual machine monitor — the program that runs a VM · jailer = Firecracker’s helper that sandboxes each VMM process · device model = the set of virtual hardware a VM sees

7 Deep dive

Necessary vs sufficient, containers on VMs, Firecracker in numbers, decision guide

Is virtualization necessary for cloud?

Not strictly. AWS sells bare-metal instances (for example m7i.metal-24xl) with no hypervisor at all — yet they are still “cloud”, because you get them by API, in minutes, metered per second. On Nitro, even bare metal gets virtual networking and storage from the Nitro cards. So the cloud needs automation, self-service and metering; virtualization is the most common way to pool hardware, not the definition.

Is virtualization sufficient for cloud?

No. The NIST test above shows a ticket-driven VMware cluster fails self-service, elasticity and metering. Adding a portal, an API, quotas, automation and chargeback makes it a private cloud.

Containers on VMs, VMs in containers

  • In every public cloud, containers usually run on VMs (EKS worker nodes are EC2 instances) — VM isolation between customers, container density inside.
  • KubeVirt runs VMs as Kubernetes objects — a team can manage both with one tool.
  • Docker Desktop on Windows/macOS runs Linux containers inside a hidden Linux VM (Lesson 4.2).

9 Real proof

Real proof: same kernel, milliseconds, megabytes

All outputs are real, from our Ubuntu 24.04 lab machine on 10 Nov 2026 (image sizes read live from the Alpine and Ubuntu download servers).

  1. Step 1 · Container kernel = host kernel

    echo "host kernel:      $(uname -r)"
echo "inside container: $(unshare --pid --uts --mount --fork --mount-proc uname -r)"
    == 1) a container shares the host kernel: compare kernel versions host kernel: 6.18.44-fc-v338 inside container: 6.18.44-fc-v338
    Identical. A VM would show its own kernel; a container cannot.

  2. Step 2 · Container start time

    for i in 1 2 3; do
  s=$(date +%s%N); unshare --pid --uts --mount --fork --mount-proc true; e=$(date +%s%N)
  echo "run $i: $(( (e-s)/1000000 )) ms"
done
    == 2) start time: isolated container-style process run 1: 4 ms run 2: 3 ms run 3: 3 ms
    No OS to boot: creating an isolated process takes a few milliseconds. A VM boots a kernel and init system first.

  3. Step 3 · What you ship: container base vs VM image

    curl -sI https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img | grep -i content-length
curl -s https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/x86_64/latest-releases.yaml | grep -A8 minirootfs
    == 3) image sizes (real downloads, HTTP headers) Alpine minimal root filesystem (container base): 3.5 MB Ubuntu 24.04 cloud VM image (full OS + kernel): 593 MB
    About 170× smaller. That difference is why containers are pulled and started on demand while VM images are cached and cloned (Lesson 4.4).
10 Hands-on

Do it yourself, step by step

Part A compares a container with its host on your machine. Part B deploys the same menu API in AWS three ways — VM, container, function — each with the console (UI) and the CLI. Part B outputs come from the moto AWS emulator; on a real account the Lambda function and the task definition cost nothing while idle, and t3.micro is Free-Tier eligible.

  1. A1 · Prove the shared kernel

    UI way — Docker Desktop

    1. Docker Desktop: run the alpine image (Lesson 4.2, A1) → Containers → the container → Exec → type uname -r.
    2. Compare with the kernel of Docker Desktop’s VM: Settings → General shows the WSL 2 / VM backend in use.

    CLI way — the same thing with commands

    uname -r
sudo unshare --pid --fork --mount-proc uname -r
docker run --rm alpine uname -r          # if Docker is installed
    == 1) a container shares the host kernel: compare kernel versions host kernel: 6.18.44-fc-v338 inside container: 6.18.44-fc-v338
    All print the same kernel: containers share it. A VM would show its own.

  2. A2 · Feel the start-time difference

    UI way — Docker Desktop vs VirtualBox

    1. Docker Desktop: Images → alpine → Run — the container is “Running” almost instantly.
    2. Compare with starting the VirtualBox VM from Lesson 4.1: Start and wait for the login prompt.

    CLI way — the same thing with commands

    time sudo unshare --pid --fork --mount-proc true
time docker run --rm alpine true
    == 2) start time: isolated container-style process run 1: 4 ms run 2: 3 ms run 3: 3 ms
    Milliseconds vs tens of seconds — no OS to boot.

  3. B1 · As a VM (EC2)

    UI way — AWS Management Console

    1. EC2 → Launch instances → name menu-vm → Amazon Linux 2023 → t3.micro → key pair → Launch instance.
    2. You now own a whole server: patch it, install Python, run the app, keep it alive.

    CLI way — the same thing with commands

    aws ec2 run-instances --image-id $AMI --instance-type t3.micro \
  --query 'Instances[0].InstanceId' --output text
    == 1) as a VM (EC2): you choose OS image and size; you manage the OS i-c71e4d6f84e75b642 t3.micro running
    Type 3: you manage the OS and everything above it.

  4. B2 · As a container (ECS on Fargate)

    UI way — AWS Management Console

    1. Elastic Container Service → Clusters → Create cluster → name tiffingo → infrastructure AWS Fargate (serverless) → Create.
    2. Task definitions → Create new task definition → family menu-api → launch type AWS Fargate → CPU .25 vCPU, memory .5 GB.
    3. Container: name menu, image URI public.ecr.aws/nginx/nginx:alpine, port 80 → Create.
    4. To run it: cluster → Services or Tasks → Run new task → choose subnets and a security group allowing port 80.

    CLI way — the same thing with commands

    aws ecs create-cluster --cluster-name tiffingo
aws ecs register-task-definition --family menu-api --requires-compatibilities FARGATE \
  --network-mode awsvpc --cpu 256 --memory 512 --execution-role-arn $ROLE \
  --container-definitions '[{"name":"menu","image":"public.ecr.aws/nginx/nginx:alpine",
    "portMappings":[{"containerPort":80}],"essential":true}]'
    == 2) as a container (ECS on Fargate): you give an image + CPU/memory; AWS runs the host tiffingo ACTIVE menu-api 1 256 512 FARGATE
    Type 5: you describe an image and its size; there is no EC2 instance to manage. Running tasks costs per vCPU-second and GB-second.

  5. B3 · As a function (Lambda)

    UI way — AWS Management Console

    1. Lambda → Create function → Author from scratch → name menu-fn → runtime Python 3.12 → Create function.
    2. Code tab: replace the code with the handler on the right → Deploy.
    3. Test → create a test event (any JSON) → Test: the response shows the menu; note “Init duration” on the first run (cold start).
    4. Configuration → General configuration: memory 128 MB, timeout 5 s.

    cat > app.py <<'PY'

    return {"statusCode": 200, "body": "TiffinGo menu: dal, roti, paneer"}
PY
zip fn.zip app.py

  --role $ROLE --zip-file fileb://fn.zip --memory-size 128 --timeout 5
aws lambda invoke --function-name menu-fn out.json && cat out.json   # real account
    == 3) as a function (Lambda): you give only code; it runs per request menu-fn python3.12 128 5 214

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Calling a ticket-driven VMware cluster a “private cloud”.Both use VMs.Check the five NIST characteristics; add self-service, automation and metering.
Saying “containers replace VMs”.Containers are lighter.In the cloud, containers usually run on VMs; choose per workload.
Running a Windows app in a Linux container.Containers look like mini-OSes.Containers share the host kernel: Windows apps need Windows containers or a VM.
Putting a 20-minute job in Lambda.Serverless sounds universal.Lambda stops at 15 minutes; use Fargate/ECS, Batch or Step Functions.
Ignoring cold starts for a latency-critical API.Tests hit warm functions.Measure p99; use provisioned concurrency, smaller packages, or containers.
Lift-and-shifting to VMs and expecting cloud savings automatically.VMs in the cloud billed 24×7.Right-size, schedule off-hours, use Auto Scaling or move to containers/serverless.

Exam-style questions with explanations

1. Which statement is correct?
  1. Virtualization and cloud computing are the same
  2. ✔ Cloud computing is a service model usually built on virtualization plus automation
  3. Containers are a type of hypervisor
  4. Cloud requires containers

Why: Virtualization is the technology; cloud adds self-service, elasticity and metering and delivers it as a service.

2. A team wants to run containers without managing any EC2 instances. Which AWS service?
  1. Amazon EC2
  2. ✔ AWS Fargate
  3. Amazon EBS
  4. AWS Outposts

Why: Fargate is serverless compute for ECS and EKS containers.

3. Which compute option charges nothing when there are no requests?
  1. EC2 on-demand
  2. ✔ AWS Lambda
  3. Dedicated Hosts
  4. Reserved Instances

Why: Lambda bills per request and duration; idle costs nothing.

4. Why can a Linux container not run a Windows application?
  1. Too little memory
  2. ✔ It shares the Linux host kernel
  3. No network
  4. Licensing only

Why: Containers share the host kernel; Windows binaries need a Windows kernel.

5. A VMware cluster where VMs are created by admins after a ticket is missing which NIST characteristics?
  1. Resource pooling only
  2. ✔ On-demand self-service, rapid elasticity and measured service
  3. Broad network access only
  4. None

Why: Virtualization provides pooling; the others need automation and metering.
