2 Definition

What are virtualization and a hypervisor?

Formal definition (write this in exams)

Virtualization is the creation of a software-based (virtual) version of a computing resource — such as a server, storage device, network or operating system — so that one physical resource can be divided into multiple isolated execution environments. A hypervisor (virtual machine monitor, VMM) is the software that creates and runs virtual machines, allocating CPU, memory, storage and I/O to each and isolating them from one another.

In simple words

Virtualization makes one real computer behave like several separate computers; the hypervisor is the referee that shares the hardware and keeps them apart.

Say it in an interview

30-second answer you can speak:

  • “Virtualization creates virtual versions of hardware so one physical server can run many isolated virtual machines, each with its own OS.”
  • “The hypervisor, or virtual machine monitor, allocates CPU, memory, disk and network to each VM. Type 1 runs on bare metal — ESXi, Hyper-V, Xen, KVM; Type 2 runs on a host OS — VirtualBox, VMware Workstation.”
  • “Modern hypervisors use hardware-assisted virtualization, Intel VT-x or AMD-V. For example, AWS EC2 runs on the KVM-based Nitro hypervisor.”

Type 1 · Server virtualization

Definition (say it in an interview): Server virtualization is the partitioning of one physical server into multiple isolated virtual machines, each with its own operating system and applications, by a software layer called a hypervisor that allocates and isolates CPU, memory, storage and network.

In plain words (no jargon): One powerful computer is divided into several smaller “pretend computers” (virtual machines). Each pretend computer has its own Windows or Linux and its own programs, and cannot see the others. A special program called the hypervisor does the dividing — like a building manager who decides which flat gets which rooms.

Analogy: An apartment building: one plot and foundation, many flats. Each family has its own lock and kitchen and cannot enter the next flat — but all share the land, walls and water. The building rules and the guard are the hypervisor.

How it works internally, step by step

  1. The hypervisor takes the hardware. A Type 1 hypervisor (ESXi, KVM, Hyper-V, Nitro) boots first, directly on the server. With VT-x/AMD-V it runs in the CPU’s most privileged “root mode”, so nothing else can control the hardware.
  2. A VM is defined. An admin or an API call describes the VM: 2 vCPUs, 4 GB RAM, a 20 GB virtual disk (a file or a volume), one virtual network card. This is just a configuration record.
  3. Resources are reserved. The hypervisor sets aside memory, builds the VM’s memory map (EPT/NPT — see type 3), creates the virtual disk and connects the virtual NIC to a virtual switch.
  4. The guest boots. The VM starts from virtual firmware (BIOS/UEFI) and loads its own kernel — Windows or Linux — which believes it owns a real computer.
  5. Normal instructions run directly. Ordinary CPU instructions of the guest run straight on the physical CPU in “non-root mode” at almost full speed — no translation.
  6. Sensitive actions trap to the hypervisor. When the guest touches hardware (I/O, interrupts, special registers) the CPU performs a VM exit; the hypervisor handles it (often via fast virtio/ENA drivers) and returns with a VM entry.
  7. The scheduler shares the cores. vCPUs are scheduled on physical cores like threads; memory isolation (EPT) and device isolation (IOMMU) make sure no VM can read another’s data.

Words used above, in simple terms: CPU / core = the worker chip that runs instructions · vCPU = a share of a real CPU core given to a VM · kernel = the core part of an operating system that talks to hardware · VT-x / AMD-V = features built into Intel/AMD chips to help hypervisors · VM exit / entry = the CPU pausing the VM to let the hypervisor act, then resuming it · virtio / ENA = fast “virtual-aware” drivers for disk and network · IOMMU = a hardware guard so devices touch only their own VM’s memory

Type 2 · OS-level virtualization (containers)

Definition (say it in an interview): OS-level virtualization lets one operating-system kernel run multiple isolated user-space instances called containers; the kernel isolates what each can see (namespaces) and limits what each can use (cgroups), so containers share the host kernel instead of running their own.

In plain words (no jargon): Instead of making many pretend computers, the operating system makes many separate rooms for programs. Each program gets its own files, its own name and its own network address, but all rooms share the same engine underneath (the kernel). That makes containers tiny and very fast to start.

Analogy: A hostel: each student gets a private, lockable room (own files, own address), cheap and quick to move into — but everybody shares one kitchen and water tank (the kernel). If the kitchen breaks, every room suffers.

How it works internally, step by step

  1. Get the image. The runtime pulls the image: a stack of read-only layers (base OS files + libraries + app) from a registry such as Docker Hub or Amazon ECR.
  2. Build the root filesystem. overlayfs stacks the layers and adds a thin writable layer. Ten containers can share one image on disk; each only stores its own changes.
  3. Create namespaces. The runtime calls the Linux clone()/unshare() system calls with flags for new PID, network, mount, UTS (hostname), IPC and user namespaces. The process will now see only its own processes, files, hostname and network.
  4. Apply cgroup limits. A control group is created with limits such as cpu.max (0.5 CPU) and memory.max (256 MB); the process is placed in it. If it exceeds memory the kernel kills only that container.
  5. Connect the network. A veth pair (virtual cable) links the container’s network namespace to a bridge on the host; a NAT rule maps host port 8080 to container port 80.
  6. Lock it down and start. Dangerous kernel capabilities are dropped and a seccomp filter blocks risky system calls; then the app is started as PID 1. Every system call it makes goes directly to the shared host kernel — there is no second OS.

Words used above, in simple terms: image = a ready-made package of files for a container · registry = an online store of images (Docker Hub, ECR) · overlayfs = stacks read-only image layers with one writable layer · namespace = gives a process its own private view (processes, network, files, name) · cgroup = a limit on how much CPU/memory a group of processes may use · veth / bridge = a virtual cable / virtual switch · PID 1 = the first process in a container

Type 3 · Memory virtualization

Definition (say it in an interview): Memory virtualization abstracts physical RAM so that each virtual machine (and each process) sees its own contiguous address space starting at zero; the hypervisor, helped by CPU features such as Intel EPT and AMD NPT, maps guest-physical memory to real host memory, enforcing isolation and enabling techniques such as overcommit, ballooning and page sharing.

In plain words (no jargon): Every virtual machine believes it has its own RAM starting from the first address. The hypervisor secretly keeps a list of which real memory chip area each VM is actually using, so VMs never write over each other — and it can lend unused memory from a sleeping VM to a busy one.

Analogy: Hotel room numbers: two guests both hold a key that says “Room 101” on their own floor plan, but the reception register maps one to real room 704 and the other to 312. Neither can open the other’s room, and empty rooms are handed to new guests.

How it works internally, step by step

  1. Memory is promised, not given. When a VM with 4 GB starts, the hypervisor records the promise but usually allocates real RAM page by page, only when the guest first touches it.
  2. The guest builds its own page tables. Inside the VM, the guest OS maps each process’s virtual addresses to what it thinks are physical addresses: guest-virtual → guest-physical.
  3. The hypervisor builds a second table. For each VM the hypervisor keeps an EPT (Intel) or NPT (AMD) table: guest-physical → host-physical (real RAM frames).
  4. The CPU walks both tables. On every memory access the CPU’s MMU translates through both tables in hardware (a “two-dimensional walk”) and caches the result in the TLB, tagged per VM, so it stays fast.
  5. First touch causes a fault. If a guest-physical page has no real frame yet, the CPU raises an EPT violation; the hypervisor picks a free frame, fills the table and resumes the VM — invisible to the guest.
  6. Reclaiming memory. When RAM is tight the hypervisor (a) asks a balloon driver inside idle VMs to hand back unused pages, (b) shares identical pages (KSM / transparent page sharing) as one copy-on-write page, and (c) as a last resort swaps VM memory to disk.

Words used above, in simple terms: RAM = fast working memory, emptied when power goes off · page = a small 4 KB block of memory · page table = a list mapping one kind of address to another · EPT / NPT = the hypervisor’s extra page table, used by Intel/AMD chips · MMU / TLB = the chip part that translates addresses / its small fast cache · balloon driver = a helper inside the VM that hands back unused memory · KSM / page sharing = keeping one copy of identical memory pages

Products and cloud services

For the experienced — did you know? With two levels of page tables, one TLB miss can cost up to 24 memory reads instead of 4 (a 4-level guest walk inside a 4-level host walk). That is why huge pages (2 MB / 1 GB) give VMs such a large speed-up, and why databases on VMs are tuned to use them.

Use it when: you want isolation between VMs (always on) and higher density on hosts with many idle VMs.
Avoid / be careful when: overcommitting memory heavily: when every VM wants its RAM at once, the host swaps and everything slows down. Clouds do not overcommit memory on most instance types.

Type 4 · Desktop virtualization (VDI and DaaS)

Definition (say it in an interview): Desktop virtualization separates a user’s desktop environment — operating system, applications and data — from the physical device by running it on a central server or cloud and delivering it over the network, so the device only displays the screen and sends keyboard and mouse input. Self-hosted, it is called VDI (Virtual Desktop Infrastructure); bought as a cloud service, DaaS (Desktop as a Service).

In plain words (no jargon): Your computer screen shows a desktop that is really running on a big server somewhere else. Only the picture comes to you, and only your typing and clicks go back. So any cheap laptop can be used, and if it is lost, no company data is lost with it.

Analogy: Watching a cricket match on TV: the match happens in the stadium; your TV only shows it. Change or break the TV and the match goes on. Your desktop “plays” in the data centre; your laptop is just the TV.

How it works internally, step by step

  1. Build a golden desktop. IT prepares one Windows image with Office, the CRM client and security agents (Lesson 4.4).
  2. Create a pool. Desktop VMs are cloned from it: persistent (one per user, kept) or non-persistent (shared pool, reset at logout). Multi-session hosts (Azure Virtual Desktop, RDS) let many users share one Windows server VM.
  3. User signs in. The client app or a browser contacts a gateway and connection broker; identity is checked (Active Directory / Entra ID / MFA).
  4. Broker assigns a desktop. It picks a free desktop, powers it on if needed, and gives the client a short-lived connection ticket.
  5. Display protocol streams the screen. RDP, HDX, PCoIP/Blast or DCV encodes only screen changes (often as compressed video) and sends them down; keystrokes, mouse, and optionally USB, printer and audio go up. Files stay in the data centre.
  6. Profile and logout. The user’s profile and documents are mounted from central storage at login (e.g. FSLogix containers); at logout a non-persistent desktop is reset to the clean image.

Words used above, in simple terms: golden image = a master copy of a perfectly set-up desktop · persistent / non-persistent = desktop kept per user / reset after every logout · connection broker = the service that decides which desktop you get · gateway = the secure front door from the internet · display protocol (RDP, HDX, PCoIP, DCV) = the method that sends screen pictures and receives clicks · profile = your settings and documents, stored centrally

Type 5 · Application virtualization

Definition (say it in an interview): Application virtualization runs an application isolated from the underlying operating system, without a traditional local installation — either by packaging it with its own virtual file system and registry so it runs in a sandbox on the device, or by publishing (streaming) it from a server so that it executes remotely and only its user interface is shown on the device.

In plain words (no jargon): You use a program without installing it in the normal way. Either the program comes in its own sealed box with everything it needs (so it never disturbs other programs), or it runs on a server and only its window appears on your screen.

Analogy: A food truck: it brings its own stove, gas, water and menu, so it can park on any street without needing a kitchen there — and two trucks never fight over one stove. A packaged app brings its own files and settings in the same way.

How it works internally, step by step

  1. Packaging: capture the install. A packaging tool (MSIX Packaging Tool, App-V sequencer) watches the app being installed and records every file and registry key into one package.
  2. Packaging: a virtual layer at launch. When the user starts the app, a filter driver puts it in a “bubble”: its file and registry calls are redirected to the package’s virtual file system and registry.
  3. Packaging: merged view. The app sees the OS plus its own files, as if installed; other apps cannot see its files, so two Java versions never meet. Writes go to a per-user layer.
  4. Publishing: install once on a server. For streamed apps, the app is installed on a Windows session host (or WorkSpaces Applications fleet instance) in the data centre or cloud.
  5. Publishing: user clicks an icon. The broker starts a session on the server that runs only that app — no full desktop.
  6. Publishing: only the window travels. The app’s window is remoted (RemoteApp, HDX) and appears on the user’s device like a local window; files are saved to central storage.

Words used above, in simple terms: package = one file holding the app with all its files and settings · registry = Windows’ settings database · filter driver = a small piece of Windows that redirects an app’s file and settings requests · session host = a Windows server where many users run apps · published / RemoteApp = only the app window is shown on your device

Type 6 · Network virtualization

Definition (say it in an interview): Network virtualization creates logical, software-defined networks — virtual NICs, switches, routers, firewalls and load balancers — that are decoupled from the physical network hardware, typically by encapsulating traffic in overlays (such as VXLAN) and controlling it centrally with software-defined networking (SDN).

In plain words (no jargon): Many private networks are created with software on top of one set of real cables. Each company or team gets its own network, with its own rules on who may talk to whom, and nobody has to plug in a single new cable.

Analogy: One highway shared by many courier companies. Each company’s vans are sealed and labelled, so parcels never mix even though every van uses the same road. The road is the physical network; the seal and label are encapsulation and the network tag.

How it works internally, step by step

  1. Desired state in a controller. The SDN controller / cloud control plane stores what you created by API: VPCs, subnets, route tables, security groups and where every VM lives.
  2. State pushed to every host. Each host’s virtual switch (Open vSwitch, VMware vSwitch, or the AWS Nitro card) receives only the rules and mappings for VMs it hosts.
  3. VM sends a frame. The VM’s vNIC hands an ordinary Ethernet frame to the virtual switch.
  4. Rules and route lookup. The virtual switch checks firewall rules (security groups), looks up the route, and asks “which physical host has this destination IP in this virtual network?”
  5. Encapsulate. It wraps the frame: outer Ethernet + IP (host → host) + UDP + a header with the 24-bit network ID (VXLAN VNI, UDP port 4789). AWS uses its own encapsulation on Nitro.
  6. Underlay delivers, remote host unwraps. Physical routers forward the outer packet. The receiving host removes the wrapper, checks the network ID and inbound rules, and delivers to the right VM.

Words used above, in simple terms: vNIC = a virtual network card · virtual switch = software that passes traffic between VMs · security group = a virtual firewall: a list of allowed traffic · route table = a list that says where traffic for each address range goes · encapsulation = putting a packet inside another packet, like a letter in a courier envelope · VXLAN / VNI = a common wrapping method / the network ID written on the envelope · underlay = the real physical network underneath

Type 7 · Storage virtualization

Definition (say it in an interview): Storage virtualization pools physical storage from multiple devices — often of different types and vendors — into a single logical resource managed centrally, from which virtual disks (block), file shares or object stores are presented independently of where the data is physically kept.

In plain words (no jargon): All the hard disks are poured into one big common pool. When a computer needs space, it gets a “virtual disk” from the pool, which can grow later. It never knows — or cares — which real disk holds its files.

Analogy: A bank account: your passbook shows one balance, but the notes sit in many vaults and branches. You never choose a vault; the bank moves money around without you noticing. Your virtual disk is the balance; the physical disks are the vaults.

How it works internally, step by step

  1. Disks join a pool. Physical disks (local, SAN or on many servers) are registered with the storage layer: in LVM as physical volumes in a volume group; in Ceph/EBS-style systems spread across many storage nodes.
  2. A virtual volume is a map. Creating a 100 GB volume creates a mapping table: logical block → physical location. With thin provisioning nothing is allocated yet.
  3. The volume is presented. The host sees it as a normal block device (iSCSI, NVMe-over-Fabrics, virtio-blk; on AWS via the Nitro EBS card as NVMe).
  4. Write path. The VM writes block 5,000. The layer looks up the map, allocates space on first write, writes it to two or three replicas (or erasure-coded pieces) and only then acknowledges.
  5. Snapshots by copy-on-write. A snapshot freezes the map. New writes go to new blocks; the snapshot keeps pointing at the old ones. Next snapshot stores only changed blocks.
  6. Background work. The layer rebalances data when disks are added, moves hot data to SSD and cold to HDD (tiering), and rebuilds replicas when a disk fails — the VM never notices.

Words used above, in simple terms: block = a small fixed-size piece of a disk · physical volume / volume group = a real disk / a pool made of real disks (LVM words) · iSCSI, NVMe-oF = ways to reach a disk over a network · replica = an extra copy kept for safety · erasure coding = splitting data with extra recovery pieces, cheaper than full copies · tiering = keeping busy data on fast disks and old data on cheap disks

Type 8 · Data virtualization

Definition (say it in an interview): Data virtualization is an approach to data management that lets applications retrieve and combine data from multiple heterogeneous sources — files, databases, SaaS systems, clouds — through a single unified virtual view, without needing to know where or in what format the data is stored and without physically copying it.

In plain words (no jargon): Data stays where it already lives — in files, databases and online apps. A smart layer lets you ask one question across all of them, as if they were one database, and fetches only what is needed at that moment. Nothing is copied.

Analogy: A travel booking site: you type “Mumbai → Delhi” once and see fares from every airline. The site owns no planes and copies no airline databases; it asks each airline live and combines the answers.

How it works internally, step by step

  1. Connect the sources. Connectors are configured for each source: a CSV/Parquet location, a MySQL or Oracle database, a SaaS API.
  2. Build the catalog. The layer reads metadata — table names, columns, types, statistics — and shows everything as virtual tables, often with friendly business names.
  3. Parse and plan the query. A user’s SQL is parsed into a plan: which tables come from which source, and what can be done where.
  4. Push work down. Filters, column choices and even joins are translated into each source’s own language (SQL dialect, API call) so the source returns as little data as possible.
  5. Combine. Partial results are fetched in parallel, joined and aggregated in the engine’s memory; hot results may be cached.
  6. Secure and return. Masking (hide card numbers) and row-level rules are applied in one place, and one result set is returned to the dashboard or app.

Words used above, in simple terms: source = any place data lives: a file, a database, an app · connector = a plug-in that knows how to talk to one kind of source · catalog = the list of all tables and columns and where they are · query plan = the step-by-step recipe the engine makes for your question · pushdown = sending filters to the source so it returns less data · masking = hiding sensitive values such as card numbers

6 Explained part by part

Every term: what it is, why it exists, where it is used

Virtualization

What it is: Creating software versions of hardware (computer, disk, network) so one physical resource can serve many users.

Why it exists: Servers were expensive and 85–95% idle; IT was slow to provision.

Where it is used: Every data centre and cloud; your laptop for test VMs.

Hypervisor (VMM)

What it is: The software layer that creates, runs and isolates VMs and shares the hardware among them.

Why it exists: Someone must be the referee between many operating systems on one machine.

Where it is used: KVM (AWS, Google), Hyper-V (Azure), ESXi (companies), VirtualBox (laptops).

Host and guest

What it is: Host = the physical machine (and its OS for Type 2). Guest = the OS running inside a VM.

Why it exists: Two words to say “which side” of the hypervisor something runs on.

Where it is used: Logs, drivers, commands: “run this on the host, not in the guest”.

vCPU

What it is: A virtual CPU given to a VM; it is scheduled onto a hardware thread of a real core.

Why it exists: Lets you size VMs independently of physical CPUs.

Where it is used: EC2 t3.micro = 2 vCPUs; overcommit in private clouds.

Virtual memory mapping (EPT / NPT)

What it is: CPU feature that translates guest memory addresses to real host memory in hardware.

Why it exists: Software translation was slow and complex.

Where it is used: Every modern hypervisor; keeps VMs’ memory separate.

Virtual disk

What it is: A file (qcow2, vmdk, vhdx, raw) or network volume that the guest sees as a disk.

Why it exists: Disks become portable files you can copy, snapshot and move.

Where it is used: VirtualBox .vdi, VMware .vmdk, Hyper-V .vhdx, KVM .qcow2, AWS EBS.

Virtual NIC and switch

What it is: A software network card in the VM plugged into a software switch on the host.

Why it exists: Many VMs must share a few physical network ports safely.

Where it is used: Linux bridge, Open vSwitch, Hyper-V switch, AWS Nitro VPC card.

VT-x / AMD-V

What it is: CPU extensions that add a special mode for hypervisors.

Why it exists: Make unmodified guests run at near-native speed and safely.

Where it is used: Must be “Enabled” in BIOS/UEFI for VirtualBox, Hyper-V, WSL2, KVM.

7 Deep dive

Overcommit, nesting, the theory, and the timeline

Overcommit: selling more than you have

Because most VMs are idle most of the time, a hypervisor can give out more vCPUs (and sometimes memory) than physically exist — for example 64 vCPUs on a 32-thread server. It works until many VMs get busy together; then they wait for CPU (“steal time”, visible as st in top). Public clouds sell fixed sizes and avoid heavy overcommit; private clouds tune it carefully.

Nested virtualization

Running a hypervisor inside a VM (our lab machine is a VM; Docker inside it would be a third layer). Useful for labs and testing; usually slower. Some cloud instance types allow it, and bare-metal instances (*.metal) give direct hardware access instead.

Popek and Goldberg (1974): when can a CPU be virtualized?

A classic result: a CPU is easy to virtualize if every “sensitive” instruction (one that touches hardware state) traps when run in user mode. Old x86 broke this rule for 17 instructions — the reason for binary translation and paravirtualization until VT-x/AMD-V fixed it. A favourite viva question.

9 Real proof

Proof on a real Linux machine

All outputs are real, from our cloud lab machine on 10 Nov 2026 (QEMU tools 8.x).

  1. Step 1 · Does the CPU have VT-x/AMD-V? Are we inside a VM?

    grep -c -E -w 'vmx|svm' /proc/cpuinfo
grep -c -w hypervisor /proc/cpuinfo
lscpu | grep -E 'Hypervisor vendor|Virtualization type'
    == 1) does this CPU support hardware virtualization? (vmx = Intel VT-x, svm = AMD-V) vmx/svm flags: 0 hypervisor flag: 2 (non-zero = we are already inside a VM) Hypervisor vendor: KVM Virtualization type: full
    Our lab machine is a KVM virtual machine (hypervisor flag present). It shows 0 vmx/svm because the cloud does not pass VT-x into this VM — so we cannot run another fast VM inside it. On your laptop you will usually see a number > 0.

  2. Step 2 · A virtual disk is just a file

    qemu-img create -f qcow2 web1.qcow2 10G
    == 2) a virtual disk is just a file: create a 10 GiB qcow2 disk Formatting 'web1.qcow2', fmt=qcow2 cluster_size=65536 extended_l2=off compression_type=zlib size=10737418240 lazy_refcounts=off refcount_bits=16
    This is the hard disk of a future VM.

  3. Step 3 · Thin provisioning

    qemu-img info web1.qcow2
ls -lh web1.qcow2
    == 3) thin provisioning: virtual size vs space really used file format: qcow2 virtual size: 10 GiB (10737418240 bytes) disk size: 196 KiB file on host: 193K
    The guest will see 10 GiB, but the file uses only 196 KiB until data is written. This is how clouds and private clouds “give” big disks cheaply.
10 Hands-on

Do it yourself, step by step

Make your own first VM — on your laptop, and then the same thing in the cloud. Every step shows two ways: clicking in the tool’s window (UI) and typing commands (CLI). Use whichever you like; the result is identical. Screens and versions on your computer may look slightly different.

  1. 1 · Check that your CPU can virtualize

    UI way — click by click

    1. Windows: press Ctrl+Shift+Esc to open Task Manager.
    2. Click Performance → CPU.
    3. Bottom right should say Virtualization: Enabled.
    4. If it says Disabled: restart, enter BIOS/UEFI setup, turn on Intel VT-x / AMD SVM, save.

    CLI way — the same thing with commands

    grep -c -E -w "vmx|svm" /proc/cpuinfo      # Linux: > 0 means supported

# Windows PowerShell:
(Get-CimInstance Win32_Processor).VirtualizationFirmwareEnabled
    Without these CPU features VirtualBox offers only 32-bit guests or refuses to start a 64-bit VM.

  2. 2 · Create the VM with VirtualBox

    UI way — click by click

    1. Open VirtualBox → click New.
    2. Name: tiffingo-lab; ISO Image: choose ubuntu-24.04-live-server-amd64.iso; tick Skip Unattended Installation if you want to install by hand.
    3. Hardware: Base Memory 2048 MB, Processors 2.
    4. Hard Disk: Create a virtual hard disk now, 20 GB (leave “Pre-allocate Full Size” unticked = thin disk).
    5. Click Finish → select the VM → Start and follow the Ubuntu installer.

    CLI way — the same thing with commands

    VBoxManage createvm --name tiffingo-lab --ostype Ubuntu_64 --register
VBoxManage modifyvm tiffingo-lab --cpus 2 --memory 2048 --nic1 nat
VBoxManage createmedium disk --filename tiffingo-lab.vdi --size 20480
VBoxManage storagectl tiffingo-lab --name SATA --add sata
VBoxManage storageattach tiffingo-lab --storagectl SATA --port 0 --device 0 \
  --type hdd --medium tiffingo-lab.vdi
VBoxManage storageattach tiffingo-lab --storagectl SATA --port 1 --device 0 \
  --type dvddrive --medium ubuntu-24.04-live-server-amd64.iso
VBoxManage startvm tiffingo-lab
    The UI simply calls the same engine as VBoxManage. “Not pre-allocated” is thin provisioning — the 20 GB file grows only as Ubuntu writes data.

  3. 3 · Or create it with KVM on Linux

    UI way — virt-manager

    1. Install and open Virtual Machine Manager (virt-manager).
    2. Click Create a new virtual machine → Local install media → choose the Ubuntu ISO.
    3. Memory 2048, CPUs 2 → disk 20 GB → Name tiffingo-lab → Finish.

    CLI way — the same thing with commands

    sudo apt install -y qemu-kvm libvirt-daemon-system virtinst virt-manager
sudo usermod -aG libvirt $USER    # log out and back in
virt-install --name tiffingo-lab --memory 2048 --vcpus 2 \
  --disk size=20 --cdrom ubuntu-24.04-live-server-amd64.iso --os-variant ubuntu24.04
virsh list --all
    virt-manager and virt-install both talk to libvirt, which drives QEMU + KVM — a Type 1-style hypervisor inside the Linux kernel.

  4. 4 · Look from inside the guest

    UI way — click by click

    1. Windows guest: open Task Manager → Performance → CPU: it shows Virtual machine: Yes.
    2. Linux desktop guest: Settings → About shows the hardware model (e.g. “VirtualBox”).

    CLI way — the same thing with commands

    lscpu | grep -E 'Hypervisor vendor|Virtualization type'
systemd-detect-virt
    VirtualBox shows “Oracle”/oracle, KVM shows “KVM”/kvm, an EC2 Nitro instance shows “amazon” — the guest knows it is virtual.

  5. 5 · Take a snapshot and roll back

    UI way — click by click

    1. VirtualBox: select the VM → Snapshots (or the ☰ menu next to it) → Take → name fresh-install.
    2. Break something inside the VM.
    3. Power off → select fresh-install → Restore.

    CLI way — the same thing with commands

    VBoxManage snapshot tiffingo-lab take fresh-install

Clean up and cost check

VirtualBox: right-click the VM → Remove → Delete all files (CLI: VBoxManage unregistervm tiffingo-lab --delete). KVM: virsh destroy tiffingo-lab; virsh undefine tiffingo-lab --remove-all-storage. AWS: Instance state → Terminate instance (CLI: aws ec2 terminate-instances --instance-ids i-…) so it stops billing.

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
VirtualBox shows only 32-bit options / “VT-x is not available”.Virtualization is disabled in BIOS, or Hyper-V/WSL2 is holding VT-x on Windows.Enable VT-x/SVM in BIOS; on Windows turn on “Windows Hypervisor Platform” or use VirtualBox 7+ which can run alongside Hyper-V.
VM is very slow.No hardware acceleration, too little RAM, or emulated (not virtio) disk/network.Enable VT-x, give enough RAM, install guest additions / virtio drivers.
Host freezes when VMs start.Gave VMs more RAM than the host has.Leave at least 25–30% of RAM for the host; overcommit carefully.
Confusing host and guest.Commands typed in the wrong window.Check the prompt/hostname; name VMs clearly.
“Virtualization = cloud.”Both use VMs.Cloud adds self-service, metering and broad network access on top (Lesson 1.2).

Exam-style questions with explanations

1. Which of these is a Type 2 hypervisor?
  1. VMware ESXi
  2. ✔ Oracle VirtualBox
  3. Microsoft Hyper-V
  4. Xen

Why: VirtualBox installs as an application on a host OS. ESXi, Hyper-V and Xen run directly on the hardware (Type 1).

2. In paravirtualization the guest operating system…
  1. is unmodified
  2. ✔ is modified to call the hypervisor through hypercalls
  3. runs without a hypervisor
  4. must be Windows

Why: The guest kernel knows it is virtual and asks the hypervisor directly — faster, but needs a changed or enlightened OS.

3. Intel VT-x and AMD-V provide…
  1. GPU acceleration
  2. ✔ hardware support for running hypervisors and unmodified guests
  3. disk encryption
  4. faster internet

Why: They add a root/non-root CPU mode so guests run at near-native speed while the hypervisor keeps control.

4. Which component isolates the memory of two VMs on the same host?
  1. The guest OS
  2. ✔ The hypervisor (with EPT/NPT hardware support)
  3. The application
  4. DNS

Why: The hypervisor maps each guest’s memory to separate real memory; the CPU’s second-level page tables enforce it.

5. AWS EC2 instances today run on…
  1. VMware ESXi
  2. ✔ the Nitro Hypervisor (KVM-based)
  3. VirtualBox
  4. no hypervisor at all

Why: Nitro is a lightweight KVM-based hypervisor with I/O offloaded to Nitro cards; *.metal instances skip the hypervisor.

13 Mini project

Build something with what you learned

Mini project: a two-VM home lab

Goal: Build two VMs on your laptop (web and db), connect them on a private virtual network, and prove they can talk — the same idea as an EC2 web server and database in a VPC.

Combines: Virtualization + Linux + networking + databases.

  1. Create VM web and VM db (2 GB RAM each) with VirtualBox or KVM.
  2. Attach both to an internal / host-only network (VirtualBox) or the default libvirt network (KVM).
  3. In each guest run ip -brief addr and note the IPs.
  4. From web: ping -c 3 <db-ip>. On db: sudo apt install -y postgresql; from web connect with psql -h <db-ip> (allow it in pg_hba.conf).
  5. Snapshot both VMs; break something; restore the snapshot.
  6. Write down which parts map to cloud: VM → EC2, virtual network → VPC, snapshot → EBS snapshot.

You should see: Two VMs talking privately, and snapshots you can roll back to.
