2 Definition

Network, storage and data virtualization

Formal definition (write this in exams)

Network virtualization combines physical network resources and functionality into software-based logical networks — virtual NICs, switches, routers and firewalls — decoupled from the underlying hardware, typically using overlays and software-defined networking. Storage virtualization pools physical storage from multiple devices into what appears to be a single storage resource, from which logical volumes, file systems or object stores are presented, independent of physical location. Data virtualization provides an abstraction layer that lets applications retrieve and manipulate data from multiple heterogeneous sources through a unified view, without requiring technical details about format or physical location and without copying it.

In simple words

Put software between users and the physical network, disks or data sources, so they get private networks, virtual disks and one combined view of data — while the real hardware and files stay hidden underneath.

Say it in an interview

30-second answer you can speak:

  • “Network virtualization creates logical networks in software on top of a shared physical network. VMs get virtual NICs, a virtual switch forwards traffic, and overlays like VXLAN wrap each packet with a network ID so many private networks — like AWS VPCs — share one physical fabric.”
  • “Storage virtualization pools many physical disks and presents virtual volumes, adding thin provisioning, snapshots, replication and tiering. EBS, SAN arrays and Linux LVM are examples.”
  • “Data virtualization lets you query many sources as one without copying them — for example Athena federated query, or DuckDB joining a CSV, a Parquet file and a database in one SQL statement, which I did in a lab.”

Type 1 · VLAN (virtual LAN)

Definition (say it in an interview): A VLAN divides one physical layer-2 switched network into multiple isolated logical networks by assigning switch ports to VLAN IDs and tagging Ethernet frames with a 12-bit identifier (IEEE 802.1Q), so devices in different VLANs cannot communicate without a router.

In plain words (no jargon): One real network switch is set up so that it behaves like several separate switches. Computers in one group cannot see traffic of another group, even though they are plugged into the same box.

Analogy: One office floor with coloured badges: kitchen staff with blue badges can only enter blue rooms, billing staff with violet badges only violet rooms — same building, same corridors, separate access.

How it works internally, step by step

  1. Assign ports. The admin sets switch port 1–20 to VLAN 10 (kitchen) and 21–40 to VLAN 20 (billing).
  2. Forward within a VLAN only. The switch keeps a separate MAC-address table per VLAN and floods broadcasts only to ports of the same VLAN.
  3. Tag on trunks. Links that carry several VLANs (switch-to-switch, switch-to-hypervisor) add a 4-byte 802.1Q tag with the 12-bit VLAN ID to each frame.
  4. Hypervisor reads tags. The virtual switch on a host delivers tagged frames only to VMs in the matching port group.
  5. Route between VLANs. To talk across VLANs, traffic must go through a router or firewall, where rules apply.

Words used above, in simple terms: layer 2 = the Ethernet level: switching by MAC address · MAC address = a network card’s hardware address · broadcast = a message sent to every device on the network · trunk = a link carrying several VLANs at once · 802.1Q = the standard for VLAN tags

For the experienced — did you know? The 4,094 limit is why public clouds abandoned VLANs for customer networks: a cloud with a million customers would run out of IDs on day one. VXLAN’s 24-bit VNI was designed exactly for that.

Use it when: separating departments, guest Wi-Fi, voice phones or hypervisor management traffic inside one site.
Avoid / be careful when: you need thousands of tenants or networks that span data centres — 4,094 IDs and one layer-2 domain are not enough.

Type 2 · Overlay networks (VXLAN, Geneve, cloud VPCs)

Definition (say it in an interview): An overlay network is a virtual network built on top of an existing IP network (the underlay) by encapsulating each packet — wrapping the original frame inside a new UDP/IP packet with a virtual-network identifier — so that many isolated layer-2 or layer-3 networks can share the same physical infrastructure and span racks and data centres.

In plain words (no jargon): Each company or team gets its own private network made purely of software. When a message travels between two servers, it is put inside a sealed envelope with the network’s name on it, carried over the shared cables, and opened only at the other end.

Analogy: Courier vans on a highway: each company’s parcels go into sealed vans labelled with the company’s name. The highway only sees vans going from depot A to depot B; at the depot the van is opened and parcels go to the right company.

How it works internally, step by step

  1. Control plane knows everything. The cloud or SDN controller stores every VPC, subnet and which host each VM is on.
  2. VM sends an ordinary packet. The guest sends to a private IP as if on a normal LAN.
  3. Look up the destination host. The host’s virtual switch (or Nitro card) asks “which physical host has 10.10.2.7 in this VPC?”
  4. Encapsulate. Wrap: outer Ethernet + IP (host 1 → host 2) + UDP (port 4789 for VXLAN) + VXLAN header with a 24-bit VNI.
  5. Underlay routes it. Physical routers see only host-to-host UDP traffic.
  6. Decapsulate and deliver. Host 2 removes the wrapper, checks the VNI and security rules, delivers to the VM.

Words used above, in simple terms: underlay = the real physical network · overlay = the virtual network carried on top · encapsulation = putting one packet inside another · VNI = VXLAN network identifier, 24 bits · VTEP = the endpoint that wraps/unwraps (a host or switch) · UDP 4789 = the standard port used by VXLAN

For the experienced — did you know? An AWS VPC has no broadcast or multicast: ARP requests never reach other instances — the Nitro card answers them from the mapping service. That is why gratuitous-ARP failover from on-premises clusters does not work in AWS.

Use it when: many tenants or teams share hardware, networks are created by API, or a network must span racks and sites.
Avoid / be careful when: MTU is forgotten (the wrapper adds ~50 bytes) or troubleshooting tools only look at the underlay.

Type 3 · SDN (software-defined networking)

Definition (say it in an interview): Software-defined networking separates the network’s control plane (decisions about where traffic should go) from its data plane (forwarding packets), centralising control in software controllers that program network devices through open interfaces and APIs.

In plain words (no jargon): Instead of configuring every network box by hand, one central program decides how traffic should flow and sends instructions to all boxes automatically. The boxes just follow orders.

Analogy: A metro rail system: trains (data plane) just follow signals; one central control room (control plane) decides routes and sets all signals at once — no driver decides alone.

How it works internally, step by step

  1. Describe the desired network. An admin or tool (console, API, Terraform) declares networks, routes and rules.
  2. Controller stores the state. The SDN controller keeps the full picture: topology, policies, where each workload is.
  3. Compute forwarding rules. It converts policy into match → action rules (e.g. “dst 10.10.2.0/24, port 443 → allow, send to host 7”).
  4. Program the data plane. Rules are pushed to switches or virtual switches via southbound APIs (OpenFlow, OVSDB, vendor APIs).
  5. Devices forward. Each device forwards packets at line rate using those rules.
  6. Feedback. Devices report status and events back so the controller can react (link down, VM moved).

Words used above, in simple terms: control plane = the part that decides routes and rules · data plane = the part that actually moves packets · controller = central software holding the network’s plan · southbound API = how the controller talks to devices · northbound API = how apps and admins talk to the controller

Type 4 · NFV (network functions virtualization)

Definition (say it in an interview): Network functions virtualization implements network functions — firewalls, load balancers, routers, NAT, VPN gateways, even mobile-network cores — as software running on standard servers (as VMs or containers) instead of on dedicated proprietary hardware appliances.

In plain words (no jargon): Network devices like firewalls and load balancers used to be special boxes you had to buy. Now they are just programs running on normal servers or provided by the cloud, so you can create more of them in minutes.

Analogy: Instead of buying a separate calculator, camera and music player, you install apps on one smartphone. The functions are the same; the hardware is general-purpose.

How it works internally, step by step

  1. Pick the function. Firewall, load balancer, router, NAT, VPN, 5G core function…
  2. Package as software. The vendor ships it as a VM image or container image (a VNF/CNF).
  3. Deploy on standard servers. It runs on a hypervisor or Kubernetes, often with SR-IOV/DPDK for fast packet processing.
  4. Chain functions. Traffic is steered through several functions in order (service chaining), usually programmed by SDN.
  5. Orchestrate. An orchestrator (e.g. ETSI MANO, Kubernetes) starts, scales and heals the functions.

Words used above, in simple terms: appliance = a dedicated hardware box for one job · VNF / CNF = virtual / cloud-native (container) network function · DPDK = a library for very fast packet processing in software · service chaining = sending traffic through several functions in order

Type 5 · Block storage virtualization

Definition (say it in an interview): Block storage virtualization pools physical disks and presents virtual block devices (volumes) — raw sequences of fixed-size blocks that a server formats with its own file system — mapping each logical block to physical locations that the server never sees.

In plain words (no jargon): Many real hard disks are combined into one pool, and each computer is given a “virtual hard disk” cut from the pool. The computer formats and uses it exactly like a real disk, never knowing which physical disks hold its data.

Analogy: A bank account: your passbook shows a balance; the bank decides which vault holds the notes and moves them without telling you.

How it works internally, step by step

  1. Pool the disks. Physical disks are added to a pool (LVM volume group, SAN array, or a distributed cluster).
  2. Create a volume. A volume of N GB is a mapping table: logical block → physical place; thin volumes map nothing yet.
  3. Present it. The server sees a block device (iSCSI, NVMe-oF, virtio-blk; on EC2 an NVMe device from the Nitro card).
  4. Server formats it. The guest OS creates its own file system (ext4, XFS, NTFS) on the blocks.
  5. Write path. Each write is mapped, allocated if new, written to replicas, then acknowledged.
  6. Snapshots and growth. Copy-on-write snapshots freeze the map; volumes can be enlarged online.

Words used above, in simple terms: block = a small fixed-size chunk of a disk (often 4 KB) · volume = a virtual disk · file system = the way an OS organizes files on a disk (ext4, NTFS) · IOPS = input/output operations per second — disk speed · replica = an extra copy for safety

Type 6 · File storage virtualization (NAS, shared file systems)

Definition (say it in an interview): File storage virtualization presents storage as a shared, hierarchical file system — folders and files — accessed over the network with protocols such as NFS or SMB, so many servers and users can read and write the same files while the physical location of the data is hidden and can change.

In plain words (no jargon): A shared folder that lives on the network. Many computers can open, change and save the same files at the same time, as if the folder were on each of their own disks.

Analogy: A shared office cupboard with labelled folders: everyone takes and returns files from the same cupboard, and the office manager can move the cupboard to a bigger room without anyone changing how they find a folder.

How it works internally, step by step

  1. Create a file system. The storage system (NAS or cloud service) creates a file system on its pooled disks.
  2. Export it. It is shared over the network via NFS (Linux) or SMB (Windows), with access rules.
  3. Mount on clients. Each server mounts it at a path, e.g. /var/www/menu or drive Z:.
  4. Open, read, write. File operations travel over the network; the server handles locks so two writers do not corrupt a file.
  5. Grow and protect behind the scenes. Capacity grows automatically (EFS), snapshots and replication run without clients noticing.

Words used above, in simple terms: NAS = network-attached storage: a file server appliance · NFS / SMB = the file-sharing languages of Linux / Windows · mount = attach a file system to a folder path · lock = a rule that stops two programs writing the same file at once

Use it when: many servers or users need the same files at once (web content, home folders, shared datasets, legacy apps).
Avoid / be careful when: a single database needs the lowest latency (use block) or you store billions of objects for the web (use object).

Type 7 · Object storage virtualization

Definition (say it in an interview): Object storage virtualizes storage as a flat namespace of objects — each the data itself plus metadata and a unique key — stored in buckets and accessed over HTTP APIs, with the system hiding all disks, servers and replicas behind the key.

In plain words (no jargon): Each file is stored as a single “object” with a unique name (key). You put it in and get it back using that name over the internet. You never see disks or folders — the service handles where and how many copies are kept.

Analogy: A cloakroom with tokens: you hand over a coat and get token 274. You don’t know or care which rack it hangs on; show the token and you get the coat back.

How it works internally, step by step

  1. Create a bucket. A named container in a Region.
  2. PUT an object. Send the bytes, a key and metadata over HTTPS.
  3. Durably store. The service splits or replicates the object across many disks and (for S3 Standard) multiple Availability Zones before confirming.
  4. Index by key. A metadata index maps key → locations; there is no real folder tree (“/” in keys is just part of the name).
  5. GET / list. Clients fetch by key or list keys by prefix.
  6. Lifecycle. Rules move old objects to cheaper classes or delete them.

Words used above, in simple terms: object = the data + its metadata + a key · bucket = a named container for objects · key = the object’s unique name · REST API = a web interface using HTTP verbs (PUT, GET, DELETE) · storage class = a price/performance tier

Type 8 · Data virtualization (federated query)

Definition (say it in an interview): Data virtualization provides a logical layer that lets applications query and combine data from multiple heterogeneous sources — files, databases, SaaS systems, clouds — through one unified view, without copying the data and without needing to know its location or format.

In plain words (no jargon): Data stays where it already lives. A smart layer lets you ask one question across many places as if they were one database, and fetches only what is needed. Nothing is copied.

Analogy: A travel booking site: one search shows fares from every airline, fetched live; the site owns no planes and copies no airline databases.

How it works internally, step by step

  1. Connect sources. Connectors are set up for files, databases and SaaS APIs.
  2. Catalog. Table and column metadata is collected into one catalog.
  3. Plan. A SQL query is parsed into a plan naming which source serves which table.
  4. Push down. Filters and column choices are sent to each source in its own language.
  5. Combine. Partial results are fetched in parallel, joined and aggregated.
  6. Govern. Masking and row-level rules are applied before the result is returned.

Words used above, in simple terms: connector = a plug-in that talks to one kind of source · catalog = the list of tables and where they live · pushdown = letting the source filter so less data moves · federated = spread across several independent systems

7 Deep dive

Nitro cards, VLAN vs VXLAN, MTU, how EBS works, and virtualization vs ETL

Nitro Card for VPC: where AWS does network virtualization

Nitro Card for VPC

What it is: A PCIe card in every modern EC2 host that contains the virtual switch, security groups, route lookup and encapsulation logic. The instance sees it as an ENA network device.

Why it exists: Doing this in hypervisor software used CPU that customers paid for and added jitter. Moving it to dedicated hardware frees the CPU and gives 25–200 Gbps.

Where it is used: Every Nitro-based instance (all current families). It is why security groups are enforced even if the VM is hacked — the rules are outside the VM.

Nitro Card for EBS

What it is: A second card that turns network storage into an NVMe disk for the instance and encrypts data on the way.

Why it exists: An EBS volume is far away on the network; the instance must still see a fast local-looking disk.

Where it is used: Every EBS volume on Nitro instances shows up as /dev/nvme…

Mapping service

What it is: A control-plane database of “which VPC IP lives on which physical host”.

Why it exists: Overlays have no switches to learn addresses, so someone must know where every VM is.

Where it is used: Consulted when a host first sends to a destination; answers cached on the Nitro card.

Why MTU matters: the wrapper adds bytes. If a physical network allows 1,500-byte packets and the overlay adds 50, either the VM uses a smaller MTU or the physical network uses jumbo frames. AWS supports 9,001-byte MTU inside a VPC, but traffic leaving through an internet gateway uses 1,500 — a classic cause of “small requests work, big ones hang”.

How an EBS volume actually works

An EBS volume is not a disk in your server. It is a virtual block device whose blocks are spread over many storage servers in the same Availability Zone and replicated inside that AZ. Your instance reaches it over the network through the Nitro card. Consequences you must remember:

  • An EBS volume lives in one AZ — it can attach only to instances in that AZ. To move it, snapshot it and create a new volume in the other AZ (our AWS lab does exactly this).
  • Snapshots are incremental and stored in S3, which is regional — so a snapshot can be restored in any AZ, or copied to another Region for disaster recovery.
  • Performance is a setting: gp3 gives 3,000 IOPS and 125 MB/s baseline whatever the size, and you can buy more; on old gp2 IOPS grew with size.

Real proof: virtual network, pool, thin disk and federated query

All outputs are real, from our Ubuntu 24.04 lab machine on 10 Nov 2026 (iproute2, LVM2, qemu-img, DuckDB).

  1. Step 1 · Two virtual networks and a virtual cable

    ip netns add kitchen; ip netns add billing
ip link add veth-k type veth peer name veth-b
ip link set veth-k netns kitchen; ip link set veth-b netns billing
ip -n kitchen addr add 10.10.0.1/24 dev veth-k
ip -n billing addr add 10.10.0.2/24 dev veth-b
ip -n kitchen link set veth-k up; ip -n billing link set veth-b up
ip netns list; ip -n kitchen -brief addr show veth-k
ip netns exec kitchen ping -c 2 -W 1 10.10.0.2 | tail -3
    == 1) network virtualization: two isolated network namespaces joined by a virtual cable (veth) kitchen (id: 0) billing (id: 1) veth-k@if7 UP 10.10.0.1/24 --- 10.10.0.2 ping statistics --- 2 packets transmitted, 2 received, 0% packet loss, time 1022ms rtt min/avg/max/mdev = 0.039/0.043/0.048/0.004 ms
    Two isolated network stacks, joined by a veth pair — a virtual cable with one end in each. 0% loss at 0.04 ms: no hardware moved a single bit; the kernel did it.

  2. Step 2 · The host cannot see them

    ip -brief link | grep -c veth
    == 2) the host cannot see those interfaces 0
    Zero. The interfaces exist only inside their namespaces — isolation, the first promise of network virtualization. Docker and Kubernetes connect every container exactly like this.

    Two separate 196 MB “disks” became one 392 MB pool. From here you would cut logical volumes of any size (lvcreate), even bigger than any single disk.

  4. Step 4 · A 10 GiB disk that uses 196 KiB

    qemu-img create -f qcow2 base.qcow2 10G
qemu-img create -f qcow2 -b base.qcow2 -F qcow2 clone1.qcow2

    Thin provisioning and copy-on-write together: the clone promises 10 GiB, stores only its own changes and reads the rest from base.qcow2.

  5. Step 5 · One query, three sources (DuckDB)

    INSTALL sqlite; LOAD sqlite; ATTACH 'crm.db' AS crm (TYPE sqlite);

Thinking a security group is a box you can “see” in the network.On-premises firewalls are physical.It is a rule set enforced at each instance’s virtual NIC. Think “per-instance stateful firewall”.
Big transfers hang while small requests work.MTU mismatch after encapsulation or VPN (jumbo 9,001 inside, 1,500 outside).Check path MTU; lower the MTU on the interface or allow ICMP “fragmentation needed”.
Overcommitting thin disks and running the pool out of space.Thin disks look free until they fill.Monitor real pool usage; set alerts at 70–80%; know your overcommit ratio.

Treating snapshots as free.They are incremental but accumulate.Use Amazon Data Lifecycle Manager / retention rules to delete old ones.

Exam-style questions with explanations

1. Which technology lets millions of isolated customer networks share one physical data-centre network?
  1. VLAN
  2. ✔ Overlay networks with encapsulation (VXLAN-like)
  3. RAID
  4. DNS

Why: VLANs have only 4,094 IDs. Overlays wrap packets with a 24-bit (or larger) network ID and carry them over the physical underlay.

2. An EBS volume in ap-south-1a must be used by an instance in ap-south-1b. What do you do?
  1. Attach it directly
  2. ✔ Create a snapshot and restore it as a new volume in 1b
  3. Change the volume’s AZ attribute
  4. Use a security group

Why: EBS volumes are AZ-scoped; snapshots live in S3 (regional) and can be restored in any AZ of the Region.

3. A 10 GiB virtual disk uses only 196 KiB on the host. This is…
  1. compression
  2. ✔ thin provisioning
  3. RAID 0
  4. deduplication only

Why: Space is allocated only when blocks are written.

4. Which is an example of data virtualization?
  1. Copying tables nightly into a warehouse
  2. ✔ Querying S3 and an RDS database together with Athena Federated Query without moving data
  3. Taking an EBS snapshot
  4. Creating a VLAN

Why: Data virtualization queries data in place across sources; ETL copies it.

5. Why does a /24 subnet in AWS show 251 available addresses?
  1. AWS bug
  2. ✔ AWS reserves 5 addresses per subnet
  3. Only 251 instances are allowed per VPC
  4. IPv6 takes 5

Why: The first four (network, VPC router, DNS, future use) and the last (broadcast) are reserved.

6. Where are AWS security group rules enforced on Nitro instances?
  1. Inside the guest OS firewall
  2. ✔ On the Nitro networking card / virtualization layer, outside the instance
  3. In the internet gateway
  4. In Route 53

Why: That is why a compromised OS cannot simply turn them off.

13 Mini project

Build something with what you learned

Mini project: a mini virtual data centre on one Linux machine

Goal: Combine all three kinds of virtualization: two isolated “VM rooms” on a virtual switch, disks from a pool, and one report over three data sources.

Combines: This lesson + Linux networking + SQL.

  1. Network: create namespaces kitchen, billing and ops; create a Linux bridge br0 (ip link add br0 type bridge) and connect each namespace to it with a veth pair — a virtual switch with three ports. Give them 10.10.0.1–3/24.
  2. Firewall: in billing, allow ICMP only from 10.10.0.3 (ops) with iptables. Prove kitchen → billing fails and ops → billing works.
  3. Storage: make three 200 MB loop disks, put them in volume group pool, check vgs shows ~588 MB.
  4. Images: make a 20 GiB qcow2 base and three linked clones (kitchen.qcow2, billing.qcow2, ops.qcow2); record real sizes with du -h.
  5. Data: extend l43_data.py with a fourth source (a JSON file of delivery times) and produce revenue and average delivery time per zone in one query.
  6. Report: write README.md with a diagram, the outputs, and one sentence per step naming the AWS service that does the same job (bridge → VPC, iptables → security group, LVM → EBS, qcow2 clone → AMI, DuckDB → Athena).
  7. Clean up: delete namespaces, bridge, volume group, loop devices and files.

You should see: Ping matrix (who can reach whom), vgs output, du sizes of clones, and the federated report table.
