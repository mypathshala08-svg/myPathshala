2 Definition

VM provisioning, lifecycle and migration

Formal definition (write this in exams)

VM provisioning is the process of creating a virtual machine and allocating and configuring its resources — CPU, memory, storage, network, operating system and software — typically from a template or image, manually or automatically on demand. The VM lifecycle is the sequence of states a VM passes through, from definition and provisioning to running, suspension, stopping and deletion. VM migration is the transfer of a virtual machine — its storage, memory and execution state — from one physical host or platform to another; it is cold when the VM is powered off and live when it continues running with only a brief pause.

In simple words

Provisioning = creating ready-to-use VMs quickly from a prepared image. Migration = moving a VM to another machine or platform — either switched off (cold) or while running (live).

Say it in an interview

30-second answer you can speak:

  • “VM provisioning means creating and configuring VMs with CPU, memory, storage, network and software. In the cloud we provision from golden images like AMIs, personalize with cloud-init user data, and automate with launch templates and Auto Scaling.”
  • “Live migration moves a running VM to another host: memory is copied in rounds while it runs, then the VM is paused for milliseconds to copy the last dirty pages and CPU state, and resumes on the new host with the same IP.”
  • “For moving to the cloud I would use the 7 Rs; for rehosting, AWS Application Migration Service replicates disks continuously so cutover takes only minutes.”

Type 1 · Manual provisioning

Definition (say it in an interview): Manual provisioning is creating a server by installing the operating system from installation media and then installing and configuring software step by step by hand.

In plain words (no jargon): Someone sits at the computer, installs the operating system from a disc or USB, then installs every program and changes every setting by hand.

Analogy: Cooking every tiffin from scratch, separately, each morning: possible for one or two, impossible for two hundred — and no two taste exactly the same.

How it works internally, step by step

  1. Attach installer media. Boot the (virtual) machine from an ISO image.
  2. Install the OS. Choose language, disk layout, users; wait for files to copy.
  3. Patch. Download and install updates.
  4. Install software. nginx, runtime, monitoring agent, the app.
  5. Configure. Edit config files, firewall, users, services.
  6. Document (hopefully). Write down what was done — often skipped, so nobody can rebuild it exactly.

Words used above, in simple terms: ISO = a file containing an installation disc · configuration drift = servers that should be identical slowly becoming different · snowflake server = a unique hand-built server nobody can rebuild exactly

For the experienced — did you know? Even a perfect manual runbook drifts, because package repositories change daily. Pinning versions in an image (type 3) is what makes a build reproducible, not the care of the person typing.

Use it when: learning how an OS installs, or a one-off lab machine.
Avoid / be careful when: anything you need twice — drift, slowness and human error make manual builds the main cause of “works on server 1, fails on server 2”.

Type 2 · Template-based provisioning (full and linked clones)

Definition (say it in an interview): Template-based provisioning creates new VMs by copying a prepared master VM (a template). A full clone copies the entire disk and is independent; a linked clone shares the template’s disk and stores only its own changes using copy-on-write.

In plain words (no jargon): Instead of installing a new computer from scratch, you copy a ready one. A full copy is independent; a linked copy shares the original and saves only what is different.

Analogy: A photocopier with a master sheet: you fill in the master once and copy it. A full photocopy is your own sheet; a “linked” copy is a transparent overlay on the master where you only write your changes.

How it works internally, step by step

  1. Prepare a master VM. Install OS, patches and software; generalize it (e.g. Sysprep on Windows, clear machine IDs on Linux).
  2. Convert to template. Mark it read-only so nobody runs or changes it by mistake.
  3. Full clone. Copy all disk blocks to a new disk file; attach to a new VM definition.
  4. Linked clone. Create a small new disk whose “backing file” is the template disk; reads of unchanged blocks go to the template.
  5. Customize. Give the clone a new name, IP and unique IDs (guest customization).
  6. Start. The new VM boots in seconds.

Words used above, in simple terms: template = a read-only master VM used only for copying · Sysprep = Windows tool that removes unique IDs before cloning · backing file = the base disk a linked clone reads from · copy-on-write = copy a block only when it is first changed

Use it when: on-premises virtualization, labs, VDI pools, test environments.
Avoid / be careful when: linked clones depend on the base — delete or corrupt the template and every linked clone breaks; also changes to the template do not flow into existing clones.

Type 3 · Golden image + cloud-init (image-based provisioning)

Definition (say it in an interview): Image-based provisioning launches VMs from a tested, versioned golden image (such as an AMI) that already contains the OS and software, and applies the last per-instance settings at first boot with an initialization tool such as cloud-init using user data.

In plain words (no jargon): You prepare one perfect copy of a server once, save it as an “image”, and start every new server from it. A small script runs at first start-up to give each server its own name and settings.

Analogy: A ready-to-heat meal kit: the kitchen prepares 200 identical kits (bake), and each customer adds their own spice at home (fry). Fast, identical, still personal.

How it works internally, step by step

  1. Start from a base image. Vendor OS image (Amazon Linux 2023, Ubuntu 24.04).
  2. Bake. A builder instance installs software and patches; tests run.
  3. Capture. The disk is snapshotted and registered as an AMI with a version name.
  4. Distribute. Copy the image to other Regions/accounts if needed.
  5. Launch. Instances start from the image; root volumes are created from its snapshot (lazily loaded).
  6. cloud-init personalizes. At first boot cloud-init reads user data and metadata: hostname, SSH keys, packages, scripts.

Words used above, in simple terms: AMI = Amazon Machine Image: what an EC2 instance boots from · bake / fry = put it in the image / do it at boot · cloud-init = first-boot setup program in cloud Linux images · user data = a script or settings you pass at launch · metadata = facts about the instance (ID, IP, Region) it can read

Use it when: servers must be identical, fast to launch and rebuilt often — the normal cloud case.
Avoid / be careful when: secrets or environment-specific values are baked into the image — fetch them at boot instead.

Type 4 · Infrastructure as code + Auto Scaling

Definition (say it in an interview): Infrastructure as code (IaC) defines servers, networks and their settings in declarative files that a tool applies through cloud APIs; combined with Auto Scaling, the platform automatically provisions, replaces and removes VMs to keep a desired count or follow load.

In plain words (no jargon): You write down, in a file, what servers you want and how many. A tool reads the file and creates them. Another service then watches the load and adds or removes servers by itself.

Analogy: A standing order with the dairy: you write once “2 litres every day, 4 on festival days” and the milk simply arrives — no daily phone call, and a spoiled packet is replaced automatically.

How it works internally, step by step

  1. Write the desired state. A file lists the launch template (image, type, network) and the Auto Scaling group: min, max, desired, scaling policy.
  2. Plan. The tool reads current cloud state and shows the difference.
  3. Apply. It calls cloud APIs to create what is missing, in dependency order.
  4. Scale. CloudWatch metrics (CPU, requests) trigger the group to change the desired count.
  5. Heal. Health checks fail → the instance is terminated and a new one launched.
  6. Change by commit. A new image version = change one line, apply, instance refresh rolls servers.

Words used above, in simple terms: declarative = you say what you want, not each step · Terraform plan / apply = preview changes / make them · Auto Scaling group = a managed set of identical instances · instance refresh = replace instances gradually with a new version · drift = real resources differing from the code

Type 5 · Cold migration

Definition (say it in an interview): Cold migration moves a virtual machine that is powered off: its disk and configuration files are copied (and converted if needed) to another host, datastore or platform, and the VM is started there.

In plain words (no jargon): Turn the virtual machine off, copy its files to the new place, and turn it on again there.

Analogy: Moving house on a holiday: the shop is closed, everything is packed, moved and unpacked. Simple and safe, but customers cannot come that day.

How it works internally, step by step

  1. Plan a window. Agree a time when downtime is acceptable.
  2. Shut down cleanly. Stop the guest OS so the disk is consistent.
  3. Copy files. Disk images and VM config move to the new host or storage.
  4. Convert if needed. Change disk format (qcow2 ↔ vmdk ↔ vhdx) and drivers for a new hypervisor.
  5. Register and start. Create/import the VM on the target and boot it.
  6. Verify, then delete the source. Keep the old copy until the new one is proven.

Words used above, in simple terms: maintenance window = an agreed time when downtime is allowed · datastore = where a hypervisor keeps VM files · OVA / OVF = a package format for exporting VMs

Type 6 · Live migration

Definition (say it in an interview): Live migration moves a running virtual machine — its memory, CPU and device state — from one physical host to another with only a brief pause, typically by iteratively pre-copying memory while the VM runs and then pausing it to transfer the last changed pages; network connections and the guest OS continue without reboot.

In plain words (no jargon): A running virtual machine is moved to another physical computer without switching it off. Its memory is copied over while it keeps working; it pauses for a blink at the end and then continues on the new computer.

Analogy: Shifting a running stall from one corner of a fair to another while still serving customers: helpers copy the stock across in rounds; for the final few seconds the stall-keeper pauses, hands over the last items, and continues at the new spot.

How it works internally, step by step

  1. Check the target. Compatible CPU features, enough RAM, same networks; disk on shared storage (or move it first).
  2. Pre-copy round 1. All memory pages are sent while the VM runs; the hypervisor tracks pages the VM changes (dirty pages).
  3. More rounds. Only dirty pages are sent each round; the set shrinks.
  4. Stop-and-copy. The VM is paused for milliseconds; the last dirty pages, CPU registers and device state are sent.
  5. Move the network identity. Switches/SDN learn the new location (gratuitous ARP or mapping update).
  6. Resume. The VM continues on the new host; the old host frees its memory.

Words used above, in simple terms: dirty page = a memory page changed since it was copied · pre-copy / post-copy = copy memory before / after switching hosts · converge = the remaining dirty set becomes small enough to finish · gratuitous ARP = a broadcast saying “this IP is now here”

For the experienced — did you know? When memory is dirtied faster than the link can send it, KVM’s “auto-converge” deliberately slows the guest’s vCPUs until the copy catches up — the VM gets slower so the migration can finish.

Use it when: host maintenance, load balancing across hosts, evacuating a failing host — when downtime is not acceptable.
Avoid / be careful when: VMs with passthrough devices (GPU, SR-IOV), or very write-heavy VMs whose dirty pages outrun the network.

Type 7 · Storage migration

Definition (say it in an interview): Storage migration moves a running VM’s virtual disks from one storage location (datastore, array, volume type) to another while the VM continues to run on the same host, by copying blocks in the background and mirroring new writes until the copies are identical.

In plain words (no jargon): The computer keeps running while its hard disk is moved to a new storage system behind the scenes.

Analogy: Changing a running train’s fuel tank from the old one to a new one at the station without stopping the engine: fuel is pumped across while the engine runs, then the valve is switched.

How it works internally, step by step

  1. Start mirror. The hypervisor creates the target disk and starts copying blocks.
  2. Mirror new writes. Every new write goes to both old and new disks.
  3. Converge. When all blocks are copied, both are identical.
  4. Switch. The VM’s disk pointer moves to the new disk atomically.
  5. Clean up. The old disk is removed.

Words used above, in simple terms: datastore = a storage location for VM disks · mirror = write the same data to two places · Elastic Volumes = EBS feature to change a volume while in use

Type 8 · P2V and V2V conversion

Definition (say it in an interview): P2V (physical-to-virtual) converts a running physical server’s disks, OS and applications into a virtual machine; V2V (virtual-to-virtual) converts a VM from one hypervisor or format to another (e.g. VMware → KVM/Hyper-V), changing disk formats and drivers so the guest boots on the new platform.

In plain words (no jargon): An old physical computer — or a VM made for one virtualization product — is turned into a VM that runs on a different system, without reinstalling its software.

Analogy: Transferring a family recipe from an old handwritten notebook into a digital recipe app (P2V), or from one app to another (V2V): the recipe stays the same, the format changes.

How it works internally, step by step

  1. Prepare. Inventory the server; clean up disks; note licences tied to hardware.
  2. Capture. Copy disks with an agent while running, or boot a converter and copy offline.
  3. Convert format. Raw disk → vmdk/vhdx/qcow2 (our lab converted qcow2 to vmdk, vhdx and raw).
  4. Inject drivers. Add virtio/VMware/Hyper-V storage and network drivers; remove hardware agents.
  5. Boot and fix. Start the VM, check IP, services and time sync.
  6. Retire the source. After testing, switch off the old system.

Words used above, in simple terms: P2V / V2V = physical-to-virtual / virtual-to-virtual · driver injection = adding drivers to an OS that is not running · vmdk / vhdx / qcow2 = disk formats of VMware / Hyper-V / KVM

Avoid / be careful when: the OS lacks drivers for the virtual hardware, or licences are tied to physical hardware IDs.

Type 9 · Cloud migration — rehost with replication

Definition (say it in an interview): Rehost (lift-and-shift) migration moves servers to the cloud largely unchanged, typically by installing a replication agent that continuously copies the source disks at block level into the cloud, allowing test launches and a short final cutover.

In plain words (no jargon): A copy of the old server is kept continuously updated in the cloud. When ready, you test the copy, then switch users over to it in a few minutes.

Analogy: Moving a shop to a new mall while it stays open: stock is copied to the new shop every evening; on opening day you only bring the last day’s sales and change the signboard.

How it works internally, step by step

  1. Discover and assess. Inventory servers, dependencies and sizes (Migration Hub / Azure Migrate).
  2. Install the agent. A replication agent is installed on each source server.
  3. Initial sync. Full disk copy into low-cost staging volumes in the target Region.
  4. Continuous replication. Every block change is sent within seconds.
  5. Test launch. Launch test instances from the replica (drivers converted automatically); verify the app.
  6. Cutover. Stop the app, let final writes replicate, launch production, switch DNS, keep the source for rollback.

Words used above, in simple terms: rehost / lift-and-shift = move as-is · staging area = cheap resources holding the replica · cutover = the moment users switch to the new system · DNS TTL = how long clients cache a DNS answer — lower it before cutover

7 Deep dive

What moves in a live migration, cloud host maintenance, lazy AMI loading, bake vs fry

What exactly moves in a live migration

PieceHow it movesSize
Memory (RAM)pre-copy rounds, then last dirty pagesGBs (the bulk)
CPU stateregisters copied during the pauseKBs
Device statevirtual NIC/disk queues serializedKBs
Diskusually not moved (shared storage); otherwise storage migration first0 or GBs–TBs
Network identitysame MAC/IP; switches/SDN told the new locationone message

Will it finish? If the VM writes memory at 2 GB/s and the migration link sends 1.2 GB/s, the dirty set never shrinks. Hypervisors then slow the VM’s CPU (“auto-converge”) or switch to post-copy. That is why live migration needs fast dedicated links (10–100 Gbps) and why huge, write-heavy databases are the hardest VMs to move.

How the big clouds handle host maintenance

CloudWhat happens to your VM
Google Compute EngineLive-migrates most VMs by default (onHostMaintenance = MIGRATE); GPU and some special VMs are stopped instead.
AzureMost platform updates are memory-preserving (VM paused ~seconds) or live-migrated; others are announced as scheduled maintenance you can trigger yourself.
AWS EC2Nitro lets AWS update much host software without rebooting you. When hardware must be retired, you get a scheduled event (instance retirement / system reboot); a stop and start of an EBS-backed instance moves it to healthy hardware.

Why AMIs launch so fast

An AMI is a pointer to EBS snapshots stored in S3. A new instance’s root volume is created from the snapshot lazily: blocks are fetched from S3 the first time they are read. The VM boots immediately, but the first read of each block is slower. For databases that need full speed from the first second, AWS offers Fast Snapshot Restore or you pre-read (“initialize”) the volume.

Bake vs fry

Bake = put it in the image (slow-changing: OS, runtime, agents). Fry = do it at boot with cloud-init (fast-changing: config, secrets fetched from a secrets manager). Bake too little and boots are slow and fragile; bake too much (passwords, environment names) and you need a new image for every change.

  3. Step 3 · Snapshot before a risky change

    == 3) snapshot a VM disk before an upgrade, then list snapshots snapshot: before-upgrade

    == 4) convert a disk for another hypervisor (cold migration) file format: vmdk file format: vhdx file format: raw disk size: 4 KiB
    The disk is now readable by VMware and Hyper-V — the file part of a cold V2V migration (drivers inside the guest may also need changing).

    == 5) size of a real cloud OS image (Ubuntu 24.04 server, cloud-images.ubuntu.com) updated: 17 Oct 2026 593 MB
