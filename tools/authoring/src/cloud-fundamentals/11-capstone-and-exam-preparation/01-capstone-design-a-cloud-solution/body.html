1 The story

The canteen queue

Before you start: Modules 1–10.

🤔 Your college canteen loses 30 minutes every lunch break to queues. The principal asks your batch: “Design a cloud system so 3,000 students can pre-order and pick up in 5 minutes — safely, within ₹5,000 a month.” Where do you start?

With a design document, not with a console. This capstone brings the whole course together: requirements, architecture, service choices, security, reliability, cost and operations — seven deliverables explained one by one with a worked example. The animation walks the capstone week by week, and on your own account you deploy a reference version from code (CloudFormation, Bicep or Terraform), test it, watch it, and tear it down cleanly.

  • Graders (and interviewers) mark the reasons behind choices, not the logo count.
  • Non-functional requirements decide most of the architecture.
  • Deploying from a template is the difference between a demo and an engineering project.

Every lunch break the college canteen had a 30-minute queue. The principal challenged the cloud batch to design a pre-order system for 3,000 students — safe, fast and within ₹5,000 a month.

K> Sir, can we start with Kubernetes? It looks great on a CV. A> For 3,000 orders a day and a ₹5,000 budget? Show me which requirement needs it. R> None, honestly. 2 Definition

Capstone: design a cloud solution

Formal definition (write this in exams)

A cloud solution design translates business needs into a documented, justified and deployable architecture: measurable requirements and constraints, an architecture with data flows and trust boundaries, service selections with trade-offs, security and compliance controls, reliability and recovery plans, a cost model with guard-rails, and an operating model with infrastructure as code, CI/CD and monitoring — validated by building, testing and tearing down a working version.

In simple words

Plan a real cloud system from the needs to the running version: what it must do, how it is built, why, how safe and reliable it is, what it costs, and how it is run.

Say it in an interview

30-second answer you can speak:

  • “I start from requirements in numbers — the canteen peak was only 2 orders per second — then compare two designs, pick serverless with NoSQL for idle cost and team size, and document why I rejected Kubernetes.”
  • “I deploy from CloudFormation/Bicep/Terraform, prove it with a load burst and alarms, and tear it down from code.”

Type 1 · Requirements

Definition (say it in an interview): The requirements deliverable states what the system must do (functional requirements), how well it must do it (non-functional: load, latency, availability, security, RPO/RTO) and the constraints it must respect (budget, data residency, regulations, skills, deadlines), expressed as measurable numbers.

In plain words (no jargon): A clear list of what the system must do, how well, and within which limits.

Analogy: A tailor’s order slip: not “a nice shirt” but chest 40, sleeve 25, cotton, ready by Friday, under ₹1,500.

How it works internally, step by step

  1. Interview. Students, kitchen, admin.
  2. Quantify. Users, peaks, data size.
  3. NFRs. Latency, uptime, RPO/RTO.
  4. Constraints. Budget, India, DPDP.
  5. Prioritise. Must / should / could.

Words used above, in simple terms: NFR = non-functional requirement · p95 latency = 95% of requests are faster than this · MoSCoW = must, should, could, won’t prioritisation

Type 2 · Architecture diagram and data flow

Definition (say it in an interview): The architecture deliverable is a clear diagram of components, numbered data flows and trust boundaries (internet, private network, Region, accounts), with a short narrative of how the main requests travel and where data is stored, at a level a reviewer can understand in two minutes.

In plain words (no jargon): A drawing that shows the parts of the system and how data moves between them.

Analogy: A metro map: stations (components), lines (flows) and zone boundaries — not the wiring inside each train.

How it works internally, step by step

  1. Context. Users and external systems.
  2. Containers. Apps, APIs, DBs.
  3. Flows. Numbered steps.
  4. Boundaries. Trust and network zones.
  5. Legend. Explain symbols.

Words used above, in simple terms: C4 model = context, containers, components, code levels · trust boundary = where trust changes, e.g. internet → private network · data flow = path data takes through the system

Type 3 · Service selection and trade-offs

Definition (say it in an interview): The service selection deliverable explains, for each component, which cloud service was chosen, which alternatives were considered and why — tied to requirements such as cost at idle, peak scaling, operational effort, skills, portability and Regional availability — usually captured as architecture decision records.

In plain words (no jargon): Explaining which cloud services you picked, what else you considered, and why.

Analogy: Choosing a vehicle for a school trip: bus, vans or trains compared on cost, seats, time and driver availability — and writing down why you chose the bus.

How it works internally, step by step

  1. Shortlist. 2–3 options.
  2. Criteria. From requirements.
  3. Score. Simple matrix.
  4. ADR. Decision + consequences.
  5. Revisit. When requirements change.

Words used above, in simple terms: ADR = architecture decision record · decision matrix = scored comparison table · lock-in = cost of moving later

Type 4 · Security and compliance design

Definition (say it in an interview): The security and compliance deliverable describes identities and access (people and workloads), network exposure, data classification and protection (encryption, minimisation, retention), logging and detection, and how legal duties — DPDP for students’ personal data, CERT-In logging — are met, using the shared responsibility model.

In plain words (no jargon): How you keep the system and students’ data safe and follow the law.

Analogy: The safety plan for a school event: who gets which pass, where valuables are kept, which areas are CCTV-covered, and who to call if something goes wrong.

How it works internally, step by step

  1. Classify. What personal data, how sensitive.
  2. Identity. SSO + roles.
  3. Network. Public only where needed.
  4. Data. Encrypt, minimise, retain.
  5. Detect. Logs, alarms, threat detection.

Words used above, in simple terms: data minimisation = collect only what is needed · least privilege = only needed permissions · guard-rail = preventive policy

Type 5 · Reliability and disaster recovery

Definition (say it in an interview): The reliability and DR deliverable sets service-level objectives and recovery targets (RPO/RTO), lists failure modes (zone outage, database failure, bad deployment, quota limits, dependency failure) and describes the design responses — multi-AZ managed services, backups with point-in-time recovery, safe deployment and rollback, graceful degradation — and how they are tested.

In plain words (no jargon): Planning how the system keeps working, and how it recovers when parts fail.

Analogy: A wedding plan B: if it rains, the tent; if the cook falls ill, the backup caterer; if the power fails, the generator — all checked the day before.

How it works internally, step by step

  1. SLO. Per critical journey.
  2. Failure modes. Table with impact.
  3. Design. Redundancy, backups.
  4. Degrade. Fallback behaviour.
  5. Test. Game day / restore test.

Words used above, in simple terms: graceful degradation = keep core function when parts fail · PITR = point-in-time recovery · game day = planned failure test

Type 6 · Cost estimate and FinOps

Definition (say it in an interview): The cost deliverable estimates monthly spend from a usage model (requests, compute time, storage, data transfer) using provider calculators, states assumptions and free-tier effects, compares options, and defines guard-rails — budgets, anomaly alerts, tags and clean-up — so the estimate holds in practice.

In plain words (no jargon): Working out how much the system will cost each month, and setting alerts so it stays that way.

Analogy: A trip budget: number of people × days × meals × prices, plus a 10% buffer and a rule that nobody books a five-star hotel without asking.

How it works internally, step by step

  1. Usage. From requirements.
  2. Calculator. Per service.
  3. Compare. Option A vs B.
  4. Guard. Budget + anomaly alerts.
  5. Review. Actual vs estimate monthly.

Words used above, in simple terms: usage model = expected quantities per month · free tier = free monthly allowance · unit cost = cost per order

Type 7 · Operations and delivery

Definition (say it in an interview): The operations and delivery deliverable shows how the solution is built and run: infrastructure as code, CI/CD with tests and safe releases, monitoring with dashboards and alarms on golden signals, logging, runbooks for common incidents and a clean teardown — demonstrated live.

In plain words (no jargon): How the system is built from code, released safely, watched and fixed.

Analogy: A restaurant’s kitchen manual: standard recipes (IaC), how new dishes are introduced (pipeline), what to watch during service (monitoring) and what to do if the gas fails (runbook).

How it works internally, step by step

  1. IaC. All resources in code.
  2. Pipeline. Test → deploy.
  3. Observe. Golden signals.
  4. Runbook. Top 3 incidents.
  5. Teardown. Delete from code.

Words used above, in simple terms: IaC = infrastructure as code · runbook = step-by-step incident guide · teardown = deleting all resources cleanly

Peak maths worked out

3,000 students × 80% ordering in a 20-minute window = 2,400 orders in 1,200 s = 2 orders per second on average in the peak; allow 5× burst → design for 10 requests/second. A single small function or PaaS instance handles this; serverless auto scaling covers bursts.

Presentation structure (10 minutes)

  1. The problem and numbers (1 min).
  2. Architecture and one key trade-off (3 min).
  3. Live demo: order → kitchen screen → metrics (3 min).
  4. Security, cost and reliability in one slide each (2 min).
  5. Teardown proof and what you’d do next (1 min).

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You deploy a reference version of the capstone from a template, load it with a lunch-rush burst, observe it, and delete everything from code. Expected cost: zero to a few rupees.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Starting with services.Excitement.Requirements and numbers first.
Over-engineering (Kubernetes, multi-region) for 3,000 users.CV value.Size to the peak maths and budget.
No rejected alternatives.Only one idea.One ADR per major choice.
Security as a last slide.Time pressure.Design identity and data protection from week 1.
Cost without assumptions.Guessing.Usage model + calculator + budget.
Hand-built resources.Console is quicker once.Everything in IaC; prove teardown.
