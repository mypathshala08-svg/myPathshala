2 Definition

Public, private, hybrid and community cloud

Formal definition (write this in exams)

A cloud deployment model describes how cloud infrastructure is provisioned and who may use it. NIST SP 800-145 defines four: public (open use by the general public, on the provider’s premises), private (exclusive use by a single organisation, on or off premises), community (exclusive use by a community of organisations with shared concerns) and hybrid (a composition of two or more distinct cloud infrastructures bound together by technology that enables data and application portability).

In simple words

Public = shared cloud anyone can rent; private = a cloud only your organisation uses; community = shared by a group with the same rules; hybrid = two of these joined together.

Say it in an interview

30-second answer you can speak:

  • “A deployment model says who uses the cloud and where it runs: public, private, community or hybrid (NIST). Private means exclusive use — it can even be hosted by a provider.”
  • “For example, we keep patient data in the hospital’s private cloud and run the planning app on AWS, connected by a site-to-site VPN with shared SSO — a hybrid design.”

Type 1 · Public cloud

Definition (say it in an interview): A public cloud is cloud infrastructure provisioned for open use by the general public; it is owned, managed and operated by a cloud provider and exists on the provider’s premises, with resources shared among many customers (tenants) who are isolated from each other.

In plain words (no jargon): Cloud services anyone can sign up for, run by a big provider on shared machines.

Analogy: A city bus or metro: anyone can ride, you pay per trip, and the transport company maintains the vehicles.

How it works internally, step by step

  1. Sign up. Account + payment method.
  2. Choose Region. Where resources run.
  3. Provision. Console, CLI or API.
  4. Isolation. Hypervisor, VPC, IAM separate tenants.
  5. Billing. Metered per second / request / GB.

Words used above, in simple terms: tenant = one customer sharing the provider’s infrastructure · Region = a geographic area with data centres · self-service = you create resources yourself, no ticket to a vendor

Use it when: you want speed, global reach, elasticity and no capital spending.
Avoid / be careful when: a law or contract requires exclusive hardware or a specific location the provider cannot offer.

Type 2 · Private cloud (on-premises)

Definition (say it in an interview): A private cloud is cloud infrastructure provisioned for exclusive use by a single organisation; it may be owned, managed and operated by the organisation, a third party or both, and may exist on or off premises. An on-premises private cloud runs in the organisation’s own data centre with a cloud platform providing pooling, self-service and metering.

In plain words (no jargon): Your own cloud, used only by your organisation, usually in your own building.

Analogy: Owning a car: it is only yours and you choose everything — but you pay for it, park it, insure and service it.

How it works internally, step by step

  1. Buy & rack. Servers, storage, network.
  2. Virtualize. Hypervisor cluster.
  3. Cloud layer. Portal, API, quotas, metering.
  4. Automate. Templates and IaC.
  5. Operate. Patching, capacity, DR — all yours.

Words used above, in simple terms: on-premises = in your own building / data centre · capex = capital expenditure — buying assets up front · OpenStack = open-source software to build a cloud

Type 3 · Hosted / dedicated private cloud

Definition (say it in an interview): A hosted (managed or dedicated) private cloud is a private cloud whose hardware is located in, and often operated by, a third-party provider’s data centre but dedicated to a single customer — for example dedicated hosts, VMware-based clouds on provider bare metal, or provider-installed racks.

In plain words (no jargon): A private cloud on machines reserved only for you, but kept and run in someone else’s data centre.

Analogy: Renting a whole floor of an office building: only your company works there, but the landlord handles power, lifts and security.

How it works internally, step by step

  1. Order. Dedicated hosts / private cloud nodes.
  2. Provision. Provider racks and connects them.
  3. Connect. Private links to your network.
  4. Operate. Split duties: provider hardware, you workloads.
  5. Exit. Contracts often 1–3 years.

Words used above, in simple terms: dedicated host = a physical server used only by one customer · single tenant = no other customer on the hardware · managed = the provider does the operations work

Type 4 · Community cloud

Definition (say it in an interview): A community cloud is cloud infrastructure provisioned for exclusive use by a specific community of organisations that have shared concerns — such as mission, security requirements, policy or compliance; it may be owned and operated by one or more members, a third party, or a combination, on or off premises.

In plain words (no jargon): A cloud shared only by a group of organisations that follow the same rules, like government departments.

Analogy: A housing society’s shared gym: only residents can use it, they agree the rules together and share the cost.

How it works internally, step by step

  1. Define community. Who may join.
  2. Agree policies. Security, data location, audits.
  3. Choose operator. A member or a provider.
  4. Onboard. Vetted members and vendors.
  5. Govern. Shared board, shared costs.

Words used above, in simple terms: empanelled = officially approved to supply (e.g. by MeitY) · compliance = following laws and rules · GovCloud = a cloud area restricted to government users and vetted staff

Use it when: several organisations share strict, identical rules and want to share cost and effort.
Avoid / be careful when: members’ needs differ a lot — governance becomes slow and the platform pleases nobody.

Type 5 · Hybrid cloud

Definition (say it in an interview): A hybrid cloud is a composition of two or more distinct cloud infrastructures (private, community or public) that remain unique entities but are bound together by standardised or proprietary technology that enables data and application portability — for example cloud bursting for load balancing between clouds.

In plain words (no jargon): Using your own private systems and a public cloud together, connected safely as one setup.

Analogy: Living in your own house but renting a banquet hall for the wedding: everyday life at home, extra capacity rented when needed — with one family managing both.

How it works internally, step by step

  1. Network. VPN or dedicated link, no overlapping IPs.
  2. Identity. One directory / SSO.
  3. Management. One tool for both (Arc, SSM, GKE Enterprise).
  4. Data. Decide what stays and what syncs.
  5. Operate. Monitoring and security across both.

Words used above, in simple terms: cloud bursting = sending overflow load to the public cloud · site-to-site VPN = encrypted tunnel between two networks · SSO = single sign-on — one login for many systems

Type 6 · Sovereign cloud

Definition (say it in an interview): A sovereign cloud is a cloud deployment designed so that data, operations and control remain under the jurisdiction of a specific country or region — through data residency, local operations staff, customer-held encryption keys and legal and technical guarantees against foreign access.

In plain words (no jargon): A cloud set up so that a country’s data stays in that country and is controlled under its laws.

Analogy: A bank locker in your own city’s branch with your own key: the bank runs the vault, but the box, the key and the law are local.

How it works internally, step by step

  1. Residency. Data stored only in-country.
  2. Keys. Customer- or locally-held keys (HSM).
  3. Operations. Local staff and support.
  4. Legal. Contracts against foreign access.
  5. Audit. Independent verification.

Words used above, in simple terms: data residency = where data is physically stored · jurisdiction = which country’s laws apply · HSM = hardware security module that guards encryption keys

6 Explained part by part

Six factors behind every deployment model

Ownership

What it is: Who owns the hardware.

Why it exists: Decides capex vs opex and who refreshes servers.

Where it is used: Own DC vs provider.

Tenancy

What it is: Who shares the hardware.

Why it exists: Shared (multi-tenant) vs dedicated (single-tenant).

Where it is used: Dedicated hosts cost more.

Location

What it is: Where data physically lives.

Why it exists: Residency rules (DPDP Act, RBI, sector rules).

Where it is used: Choose Region; restrict others.

Operations

What it is: Who patches, monitors, repairs.

Why it exists: Ops skills and cost.

Where it is used: Provider vs your team.

Connectivity

What it is: How environments connect.

Why it exists: Hybrid needs private, reliable links.

Where it is used: VPN, Direct Connect, ExpressRoute, Interconnect.

Governance

What it is: Who sets the rules.

Why it exists: Community clouds share governance.

Where it is used: Policies, audits, access.

Myth vs reality: things many websites still say

  • Myth: Private cloud = on-premises.
    Reality: Private means exclusive use; it can be hosted.
    Proof: NIST definition.
  • Myth: Public cloud is insecure because it is shared.
    Reality: Isolation is engineered and audited.
    Proof: Type 1.
  • Myth: A VPC is a private cloud.
    Reality: It is a private network in a public cloud.
    Proof: Step 2.
7 Deep dive

NIST wording, hybrid building blocks, choosing, private-cloud cost

NIST’s exact wording, and why it matters in exams

NIST SP 800-145 lists four deployment models — private, community, public, hybrid — and says private and community clouds “may exist on or off premises”. Exams test this: a private cloud hosted by a provider is still private. “Virtual private cloud” (AWS/Google VPC) is not a private cloud — it is an isolated network inside the public cloud.

Choosing: a quick scoring method

  1. List rules: residency, exclusivity, audit, latency to local equipment.
  2. If no rule forbids it → public (fastest, cheapest to start).
  3. If a sector community exists with your rules → community.
  4. If something must stay on-prem → hybrid, keeping only that part private.
  5. If exclusive hardware is required → hosted/dedicated private before building your own.
  6. If foreign legal access is a concern → sovereign options and customer-held keys.

Cost reality of private clouds

A private cloud has to be sized for peak plus failures (N+1), refreshed every 4–6 years, and run by skilled staff around the clock. It is cheapest only when utilisation stays high and steady for years — which is why most organisations end up hybrid.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. Everything here is free: no VMs, no VPN tunnels. You will see the public-cloud footprint, build a private network inside it, enforce India-only residency, and register an on-premises site for a hybrid link.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · See where the public cloud can put your data

    Pick your cloud.

    UI way — AWS Management Console

    1. Click the Region selector (top right) — note Mumbai and Hyderabad.
    2. Account menu → Account → AWS Regions: newer Regions such as Hyderabad must be Enabled before use.

    UI way — Azure portal

    1. Search Subscriptions → your subscription → Resource providers / any Create blade → the Region list shows India Regions.

    CLI way — the same thing with commands

    az account list-locations --query "[?metadata.geographyGroup=='Asia Pacific' && contains(displayName,'India')].{name:name,display:displayName}" -o table

    You should see: centralindia, southindia, westindia (and others where available).

    UI way — Google Cloud console

    1. Any Create page → Region dropdown: asia-south1 (Mumbai), asia-south2 (Delhi).

  3. 2 · Build a private network inside the public cloud

    Pick your cloud.

    UI way — AWS Management Console

    1. VPC → Create VPC → VPC only, name private-only, CIDR 10.50.0.0/16 → Create VPC.
    2. Add a subnet. Do not attach an internet gateway — nothing in it can reach or be reached from the internet.

    CLI way — the same thing with commands

    VPC=$(aws ec2 create-vpc --cidr-block 10.50.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=private-only}]' --query Vpc.VpcId --output text)
aws ec2 create-subnet --vpc-id $VPC --cidr-block 10.50.1.0/24 --availability-zone ap-south-1a --query Subnet.SubnetId --output text
aws ec2 describe-internet-gateways --filters Name=attachment.vpc-id,Values=$VPC --query 'length(InternetGateways)'

    You should see: a vpc-… and subnet-… ID, then 0 internet gateways. This is a virtual private cloud — isolated, but still public-cloud infrastructure (not a “private cloud”).

    UI way — Azure portal

    1. Virtual networks → Create → resource group rg-deploy, name private-only, Central India.
    2. IP addresses: 10.50.0.0/16, subnet app 10.50.1.0/24 with Private subnet enabled (no default outbound internet).

    CLI way — the same thing with commands

    az group create -n rg-deploy -l centralindia
az network vnet create -g rg-deploy -n private-only --address-prefixes 10.50.0.0/16 \
  --subnet-name app --subnet-prefixes 10.50.1.0/24
az network vnet subnet update -g rg-deploy --vnet-name private-only -n app --default-outbound false
az network vnet subnet show -g rg-deploy --vnet-name private-only -n app --query defaultOutboundAccess

    You should see: JSON for the VNet, then false — the subnet has no implicit internet access.

    UI way — Google Cloud console

    1. VPC network → Create VPC network → name private-only, Custom subnets → app, asia-south1, 10.50.1.0/24 → Create.
    2. Add no firewall rule allowing ingress and no Cloud NAT — the network is private.

    CLI way — the same thing with commands

    gcloud compute networks create private-only --subnet-mode=custom
gcloud compute networks subnets create app --network=private-only --region=asia-south1 --range=10.50.1.0/24 --enable-private-ip-google-access
gcloud compute firewall-rules list --filter="network:private-only"

    You should see: the network and subnet created, and no firewall rules listed (implied deny-all ingress).

    Exam trap: a VPC/VNet is an isolated network in the public cloud — not a private cloud.

  4. 3 · Keep data inside India (residency guard-rail)

    Pick your cloud.

    UI way — AWS Management Console

    1. IAM → Users → your admin user (not root) → Add permissions → Create inline policy → JSON → paste the policy on the right → name india-only.
    2. Test: switch the console to N. Virginia and open EC2 — you get “not authorized”.

    CLI way — the same thing with commands

    cat > india-only.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Sid":"IndiaOnly","Effect":"Deny",
 "NotAction":["iam:*","sts:*","organizations:*","account:*","support:*","budgets:*","ce:*","cloudfront:*","route53:*","health:*"],
 "Resource":"*","Condition":{"StringNotEquals":{"aws:RequestedRegion":["ap-south-1","ap-south-2"]}}}]}
EOF
ME=$(aws sts get-caller-identity --query Arn --output text | awk -F/ '{print $NF}')
aws iam put-user-policy --user-name $ME --policy-name india-only --policy-document file://india-only.json
sleep 10; aws ec2 describe-vpcs --region us-east-1 2>&1 | tail -1
aws ec2 describe-vpcs --region ap-south-1 --query 'length(Vpcs)'

    You should see: An error occurred (UnauthorizedOperation)… for us-east-1, and a number for ap-south-1. Companies apply the same rule to every account with an Organizations SCP. Global services (IAM, billing, CloudFront, Route 53) are excluded so the console still works.

    UI way — Azure portal

    1. Policy → Assignments → Assign policy → scope rg-deploy → definition Allowed locations → Parameters: Central India, South India, West India → Review + create.

    CLI way — the same thing with commands

    az policy assignment create --name india-only --resource-group rg-deploy \
  --policy e56962a6-4747-49cd-b67b-bf8b01975c4c \
  --params '{"listOfAllowedLocations":{"value":["centralindia","southindia","westindia"]}}'
sleep 60; az network vnet create -g rg-deploy -n test-us -l eastus --address-prefixes 10.60.0.0/16 2>&1 | grep -o RequestDisallowedByPolicy

    You should see: RequestDisallowedByPolicy — creating anything outside India in this resource group is blocked (new assignments can take a few minutes to apply).

    UI way — Google Cloud console

    1. IAM & Admin → Organization policies → Resource Location Restriction → allow in:asia-south1-locations and in:asia-south2-locations.
    2. This needs an organisation (company Google Workspace / Cloud Identity). On a personal account, just set India defaults and check the effective policy.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud config set compute/region asia-south1
gcloud config set compute/zone asia-south1-a
gcloud org-policies describe gcp.resourceLocations --project=$P --effective

    You should see: the region/zone set, then the effective constraint (empty spec on a personal project = no restriction; with an organisation you would see the India value groups).

    Residency guard-rails turn “please use Mumbai” into a rule nobody can break by mistake — the basis of community and sovereign requirements.

  5. 4 · Register your “office” for a hybrid link (free objects only)

    Pick your cloud.

    UI way — AWS Management Console

    1. VPC → Customer gateways → Create customer gateway: name office-pune, BGP ASN 65000, IP 203.0.113.10 (a documentation address standing in for your office router).
    2. Do not create the Site-to-Site VPN connection — that part is billed per hour.

    CLI way — the same thing with commands

    CGW=$(aws ec2 create-customer-gateway --type ipsec.1 --bgp-asn 65000 --public-ip 203.0.113.10 \
  --tag-specifications 'ResourceType=customer-gateway,Tags=[{Key=Name,Value=office-pune}]' --query CustomerGateway.CustomerGatewayId --output text)
aws ec2 describe-customer-gateways --customer-gateway-ids $CGW --query 'CustomerGateways[0].[CustomerGatewayId,IpAddress,State]' --output text

    You should see: cgw-… 203.0.113.10 available. The next (paid) steps would be a virtual private gateway on the VPC and a VPN connection between them.

    UI way — Azure portal

    1. Local network gateways → Create: name office-pune, IP 203.0.113.10, address space 192.168.10.0/24 → Create.
    2. Do not create a Virtual network gateway in the lab — it bills hourly and takes 30+ minutes.

    CLI way — the same thing with commands

    az network local-gateway create -g rg-deploy -n office-pune --gateway-ip-address 203.0.113.10 \
  --local-address-prefixes 192.168.10.0/24
az network local-gateway show -g rg-deploy -n office-pune --query "{ip:gatewayIpAddress,prefix:localNetworkAddressSpace.addressPrefixes[0],state:provisioningState}"

    You should see: 203.0.113.10, 192.168.10.0/24, Succeeded. Note the office range does not overlap the VNet’s 10.50.0.0/16 — essential for hybrid routing.

    UI way — Google Cloud console

    1. Network Connectivity → VPN → Peer VPN gateways → Create: name office-pune, one interface 203.0.113.10.
    2. Do not create HA VPN tunnels in the lab — tunnels bill hourly.

    CLI way — the same thing with commands

    gcloud compute external-vpn-gateways create office-pune --interfaces=0=203.0.113.10
gcloud compute external-vpn-gateways describe office-pune --format="value(name,interfaces[0].ipAddress,redundancyType)"

    You should see: office-pune 203.0.113.10 SINGLE_IP_INTERNALLY_REDUNDANT.

    Hybrid starts with describing the other side: its public IP and private address range — no overlap with your cloud network.

Clean up and cost check

AWS: aws ec2 delete-customer-gateway --customer-gateway-id $CGW; delete the subnet (aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC → delete-subnet) and aws ec2 delete-vpc --vpc-id $VPC; aws iam delete-user-policy --user-name $ME --policy-name india-only (or keep it as a guard-rail). Azure: az policy assignment delete --name india-only --resource-group rg-deploy, then az group delete -n rg-deploy --yes --no-wait. Google Cloud: gcloud compute external-vpn-gateways delete office-pune --quiet, gcloud compute networks subnets delete app --region=asia-south1 --quiet, gcloud compute networks delete private-only --quiet.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Calling a VPC/VNet a “private cloud”.The word “private”.A VPC is an isolated network in a public cloud; private cloud = exclusive infrastructure.
Thinking private cloud must be on-premises.Everyday meaning.NIST: private and community clouds may be on or off premises.
Choosing private cloud “for security” by default.Fear of sharing.Compare controls and certifications; public clouds are often more secure than small private ones.
Overlapping IP ranges between office and cloud.Everyone uses 10.0.0.0/16.Plan an IP address map before building the first network.
Residency by policy document only.No technical guard-rail.Enforce with SCPs/IAM, Azure Policy, org policies (step 3).
Hybrid without shared identity and monitoring.Network-only thinking.Plan identity, management and security across both sides.
