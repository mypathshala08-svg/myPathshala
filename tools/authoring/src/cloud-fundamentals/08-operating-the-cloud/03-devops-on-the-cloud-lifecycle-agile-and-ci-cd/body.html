1 The story

Twelve days for a one-line fix

Before you start: 8.1 (monitoring) and 8.2 (deployment strategies).

🤔 TiffinGo’s developers finish features on Monday. Testers get them on Thursday. Operations deploys “when there is a window” — every second Saturday. A one-line price fix takes 12 days to reach customers. Where do the 12 days go?

Into hand-offs and waiting. DevOps removes them: one team owns the whole lifecycle (plan → code → build → test → release → deploy → operate → monitor), works in short Agile iterations, and lets a CI/CD pipeline do the repetitive steps on every commit. This lesson explains seven practices one by one — Scrum, Kanban, continuous integration, continuous delivery, continuous deployment, infrastructure as code and GitOps — animates one commit travelling through a pipeline, and on your own account you build a pipeline that tests, deploys and creates infrastructure from code.

  • Continuous delivery vs continuous deployment: one approval button apart.
  • Why a failing test should stop the pipeline in minutes, not days.
  • How infrastructure becomes code that is reviewed like any other change.

At TiffinGo, developers, testers and operations worked in separate teams with separate queues. A one-line price correction needed 12 days to reach customers — almost all of it spent waiting.

R> Sir, the developers say testing is slow; testers say code arrives broken; ops says deployments are risky. A> Three teams, three queues, and nobody owns the whole path. DevOps makes one team responsible from idea to production. K> But someone still has to test and deploy. A> A pipeline does it — on every commit, in minutes. People review code and decide what to build; machines repeat the boring steps. R> And planning? A> Short Agile iterations: small changes, shipped often, measured in production. Let’s go practice by practice.
2 Definition

DevOps on the cloud: lifecycle, Agile and CI/CD

Formal definition (write this in exams)

DevOps is a set of cultural practices and tools that unify software development and IT operations so one team owns the full lifecycle — plan, code, build, test, release, deploy, operate, monitor — delivering small changes frequently and reliably. It builds on Agile methods (iterative, incremental delivery such as Scrum and Kanban) and is implemented through CI/CD pipelines (continuous integration, continuous delivery/deployment) and infrastructure as code, which cloud providers offer as managed services.

In simple words

Developers and operations working as one team, shipping small changes often, with an automatic pipeline that tests and deploys every change.

Say it in an interview

30-second answer you can speak:

  • “DevOps is culture plus automation across the lifecycle. CI merges and tests every change; continuous delivery keeps it always releasable with a manual production gate; continuous deployment removes that gate.”
  • “On AWS I use CodeBuild, CodePipeline, CodeDeploy and CloudFormation; on Azure, GitHub Actions or Azure Pipelines with Bicep; on Google Cloud, Cloud Build, Cloud Deploy and Terraform via Infrastructure Manager — with OIDC instead of stored keys.”

Type 1 · Scrum (Agile in sprints)

Definition (say it in an interview): Scrum is an Agile framework in which a small cross-functional team delivers working increments of a product in fixed time-boxes called sprints (usually 1–4 weeks), using defined roles (Product Owner, Scrum Master, Developers), events (planning, daily scrum, review, retrospective) and artifacts (product backlog, sprint backlog, increment).

In plain words (no jargon): Working in short fixed periods, finishing a few useful features each time and improving after each one.

Analogy: Cooking a wedding menu in rounds: each round you finish a few complete dishes, let the family taste them, and adjust the next round.

How it works internally, step by step

  1. Backlog. Ordered list by the Product Owner.
  2. Planning. Choose items for the sprint goal.
  3. Daily scrum. 15 minutes: progress and blockers.
  4. Review. Show working increment.
  5. Retrospective. Improve the way of working.

Words used above, in simple terms: sprint = a fixed time-box, often two weeks · backlog = ordered list of work · increment = working, usable product piece at sprint end

Use it when: work can be planned in short cycles and the team benefits from a regular rhythm.
Avoid / be careful when: work is mostly unplanned interrupts (support, ops) — Kanban fits better.

Type 2 · Kanban (Agile as a flow)

Definition (say it in an interview): Kanban is a flow-based method that visualises work on a board, limits work in progress (WIP) in each stage, and has team members pull new work only when capacity is free, aiming to reduce waiting and improve cycle time continuously without fixed iterations.

In plain words (no jargon): A board showing all work, with a limit on how many things are in progress, so tasks get finished faster.

Analogy: A restaurant kitchen ticket rail: orders hang in a line, each cook takes the next ticket only after finishing one, and nobody starts ten dishes at once.

How it works internally, step by step

  1. Map stages. Columns for each step.
  2. Set WIP. Limits per column.
  3. Pull. Take work only when free.
  4. Measure. Cycle time, throughput.
  5. Improve. Fix bottlenecks.

Words used above, in simple terms: WIP = work in progress · cycle time = time from start to done for one item · throughput = items finished per week

Use it when: work arrives unpredictably (support, operations) or you want continuous flow.
Avoid / be careful when: the team never limits WIP — then it is just a to-do list on a wall.

Type 3 · Continuous integration (CI)

Definition (say it in an interview): Continuous integration is the practice of merging every developer’s changes into a shared main branch frequently (at least daily), with each merge automatically built and tested, so integration problems are found within minutes and the main branch always stays in a working state.

In plain words (no jargon): Automatically building and testing the code every time someone adds a change, so mistakes are found quickly.

Analogy: Several cooks tasting the shared curry after every ingredient they add, instead of all adding their spices separately and tasting only at the end.

How it works internally, step by step

  1. Trunk. Short-lived branches, merge daily.
  2. Trigger. Webhook on push / PR.
  3. Build. Clean environment each time.
  4. Test. Unit, lint, security scan.
  5. Report. Status on the pull request.

Words used above, in simple terms: main / trunk = the shared branch everyone integrates into · pull request = a request to merge a change, with review · flaky test = a test that sometimes fails without a real bug

Type 4 · Continuous delivery

Definition (say it in an interview): Continuous delivery extends CI so that every change that passes the automated pipeline is deployed to staging environments and is always in a releasable state; releasing to production is a business decision made with a single manual approval rather than a technical project.

In plain words (no jargon): Keeping the software always ready to go live, so releasing is just pressing an approve button.

Analogy: A packed tiffin on the counter, ready to go: delivery happens the moment someone says “send it”.

How it works internally, step by step

  1. Stages. Build → test → staging → prod.
  2. Environments. Staging mirrors production.
  3. Tests. Integration, smoke, performance.
  4. Approval. Manual gate for prod.
  5. Release. Same artifact, safe strategy.

Words used above, in simple terms: staging = production-like environment for final checks · gate = a check that must pass before the next stage · promotion = moving the same artifact to the next environment

Type 5 · Continuous deployment

Definition (say it in an interview): Continuous deployment goes one step beyond continuous delivery: every change that passes all automated stages — tests, security checks, canary analysis — is released to production automatically with no manual approval, relying on strong automated testing, progressive delivery and monitoring with automatic rollback.

In plain words (no jargon): Every change that passes all automatic checks goes live by itself, without anyone pressing a button.

Analogy: A conveyor belt that sends each finished tiffin straight to the delivery rider — quality checks are built into the belt itself.

How it works internally, step by step

  1. Small PRs. Reviewed, behind flags if needed.
  2. Full automation. Tests at every level.
  3. Progressive. Canary in production.
  4. Auto-rollback. Alarms revert.
  5. Observe. DORA metrics.

Words used above, in simple terms: progressive delivery = releasing gradually with automated checks · auto-rollback = reverting automatically on bad metrics · change failure rate = % of releases causing problems

Use it when: tests and monitoring are trustworthy and changes are small.
Avoid / be careful when: test coverage is weak or rollback is manual — you would automate outages.

Type 6 · Infrastructure as code (IaC)

Definition (say it in an interview): Infrastructure as code manages cloud resources — networks, servers, databases, permissions — through machine-readable definition files kept in version control, so environments are created, changed and reproduced by tools (declaratively) rather than by manual console clicks.

In plain words (no jargon): Creating cloud resources from written files instead of clicking, so it can be repeated and reviewed.

Analogy: A recipe card instead of “cook from memory”: anyone can make the same dish again, and changes to the recipe are written down and discussed.

How it works internally, step by step

  1. Write. Declarative template.
  2. Version. Commit to Git.
  3. Plan. Change set / what-if / plan.
  4. Apply. Create/update.
  5. Detect drift. Compare real vs code.

Words used above, in simple terms: declarative = describe the end state, the tool works out the steps · drift = real resources differ from the code · state file = Terraform’s record of what it manages

Type 7 · GitOps

Definition (say it in an interview): GitOps is an operating model in which the desired state of systems (typically Kubernetes manifests or IaC) is stored declaratively in Git, and software agents continuously pull from Git and reconcile the running environment to match it, so every change is a reviewed commit and drift is corrected automatically.

In plain words (no jargon): Keeping the whole system’s settings in Git, and letting a tool make the real system match it automatically.

Analogy: A thermostat set from a written schedule: whatever someone does to the window, the system keeps bringing the room back to what the schedule says.

How it works internally, step by step

  1. Repo. Environment manifests in Git.
  2. PR. Every change reviewed.
  3. Agent. Pulls and applies.
  4. Reconcile. Fixes drift continuously.
  5. Rollback. git revert.

Words used above, in simple terms: reconcile = bring reality back to the desired state · pull-based = the agent fetches changes instead of a pipeline pushing them · manifest = a YAML file describing a Kubernetes resource

6 Explained part by part

Six parts of every cloud pipeline

Source repository

What it is: Where code and IaC live.

Why it exists: Single source of truth, reviews, history.

Where it is used: GitHub, GitLab, Azure Repos, Bitbucket.

Pipeline definition

What it is: The pipeline as a file in the repo.

Why it exists: Versioned and reviewed like code.

Where it is used: buildspec.yml, azure-pipelines.yml / workflow YAML, cloudbuild.yaml.

Build runner

What it is: Clean machine that runs the steps.

Why it exists: Repeatable builds, no “works on my laptop”.

Where it is used: CodeBuild, hosted agents/runners, Cloud Build workers.

Artifact registry

What it is: Stores built packages and images.

Why it exists: Build once, deploy many.

Where it is used: ECR, ACR, Artifact Registry.

Pipeline identity

What it is: How the pipeline logs in to the cloud.

Why it exists: No long-lived keys: use roles/OIDC.

Where it is used: IAM roles, workload identity federation.

Approvals and policies

What it is: Gates before production.

Why it exists: Compliance and safety.

Where it is used: Manual approval, branch protection, policy checks.

Myth vs reality: things many websites still say

  • Myth: DevOps is a job title or a tool.
    Reality: It is a way of working; tools support it.
    Proof: CALMS.
  • Myth: Releasing often is riskier.
    Reality: Small frequent changes fail less and recover faster.
    Proof: DORA.
  • Myth: Continuous delivery means auto-deploy to prod.
    Reality: That is continuous deployment.
    Proof: Types 4–5.
7 Deep dive

DORA, pipeline security, test pyramid, 2026 tool notes

The DORA four, and what “good” looks like

MetricElite teams (DORA research)What improves it
Deployment frequencyon demand, multiple per daysmall batches, CI/CD
Lead time for changesless than a dayfast CI, automated delivery
Change failure ratelow (around 5% or less)tests, canaries, reviews

Pipeline security (DevSecOps)

  • No stored cloud keys: pipelines assume IAM roles or use OIDC federation (GitHub → AWS/Azure/Google) for short-lived tokens.
  • Scan early: dependency (SCA), code (SAST), container image and IaC scans in CI.
  • Protect main: required reviews and passing checks before merge.
  • Supply chain: pin action/image versions, sign artifacts, generate SBOMs (software bill of materials).

Test pyramid

Many fast unit tests at the bottom, fewer integration tests in the middle, a handful of end-to-end tests at the top. Inverting it (mostly slow UI tests) makes pipelines slow and flaky.

Tool notes for 2026

AWS CodeBuild, CodePipeline and CodeDeploy remain the native AWS CI/CD services and integrate with GitHub/GitLab sources. Azure offers Azure Pipelines (Azure DevOps) and GitHub Actions, both with OIDC login to Azure. Google Cloud Build and Cloud Deploy cover CI and progressive delivery; Infrastructure Manager runs Terraform now that Deployment Manager is retired.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You build the DevOps loop yourself: tests, a CI build in the cloud, automatic deployment only when tests pass, and infrastructure from code. Everything fits free tiers; the Azure path also needs a free GitHub account.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  3. 2 · Run CI in the cloud’s build service

    Pick your cloud.

    UI way — AWS Management Console

    1. CodeBuild → Create build project: name tiffingo-menu-ci, source Amazon S3 (or connect GitHub), image aws/codebuild/standard:7.0, Use a buildspec file, new service role → Create → Start build.

    CLI way — the same thing with commands

    cat > buildspec.yml <<'EOF'
version: 0.2

  install:
    runtime-versions:
      python: 3.12

      - pip install -r requirements.txt pytest
  build:
    commands:
      - python -m pytest -q
EOF
B=tiffingo-ci-$RANDOM; aws s3 mb s3://$B
zip -qr src.zip app.py test_app.py requirements.txt buildspec.yml && aws s3 cp src.zip s3://$B/
ROLE=$(aws iam create-role --role-name tiffingo-cb-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"codebuild.amazonaws.com"},"Action":"sts:AssumeRole"}]}' --query Role.Arn --output text)
aws iam put-role-policy --role-name tiffingo-cb-role --policy-name ci --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":[\"logs:*\",\"s3:GetObject\",\"s3:GetObjectVersion\"],\"Resource\":\"*\"}]}"

  4. 3 · Add continuous deployment (only when tests pass)

    Pick your cloud.

    UI way — AWS Management Console

    1. Create the Lambda function tiffingo-menu as in Lesson 8.2 step 1 if you deleted it.
    2. Add a post_build phase that zips and updates the function only if the build phase succeeded; give the CodeBuild role lambda:UpdateFunctionCode.

    CLI way — the same thing with commands

    cat >> buildspec.yml <<'EOF'
  post_build:
    commands:
      - '[ "$CODEBUILD_BUILD_SUCCEEDING" = "1" ] || exit 1'
      - mkdir -p pkg && cp lambda_function.py pkg/ && cd pkg && zip -q ../fn.zip lambda_function.py && cd ..
      - aws lambda update-function-code --function-name tiffingo-menu --zip-file fileb://fn.zip --publish
EOF
aws iam put-role-policy --role-name tiffingo-cb-role --policy-name deploy --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"lambda:UpdateFunctionCode","Resource":"*"}]}'
cp ../menu/lambda_function.py . 2>/dev/null || echo 'copy lambda_function.py from Lesson 8.2'
zip -qr src.zip app.py test_app.py requirements.txt buildspec.yml lambda_function.py && aws s3 cp src.zip s3://$B/
ID=$(aws codebuild start-build --project-name tiffingo-menu-ci --query build.id --output text)
sleep 100; aws codebuild batch-get-builds --ids $ID --query 'builds[0].phases[].[phaseType,phaseStatus]' --output text

    You should see: POST_BUILD SUCCEEDED and a new Lambda version published. With a failing test, BUILD fails and POST_BUILD never deploys. In real projects, CodePipeline chains source → CodeBuild → deploy with an optional approval stage.

    UI way — Azure portal

    1. Microsoft Entra ID → App registrations → New registration gh-deployer → Certificates & secrets → Federated credentials → GitHub Actions, your repo, branch main.
    2. Give it Contributor on rg-devops; add repo secrets AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID; append the deploy job.

    CLI way — the same thing with commands

    az group create -n rg-devops -l centralindia
APP=tiffingo-ci-$RANDOM; az appservice plan create -g rg-devops -n plan-ci --is-linux --sku F1
az webapp create -g rg-devops -p plan-ci -n $APP --runtime 'PYTHON:3.12'
az webapp config appsettings set -g rg-devops -n $APP --settings SCM_DO_BUILD_DURING_DEPLOYMENT=true
CID=$(az ad app create --display-name gh-deployer --query appId -o tsv); az ad sp create --id $CID
az ad app federated-credential create --id $CID --parameters '{"name":"gh-main","issuer":"https://token.actions.githubusercontent.com","subject":"repo:YOUR-USER/menu-ci:ref:refs/heads/main","audiences":["api://AzureADTokenExchange"]}'
az role assignment create --assignee $CID --role Contributor --scope $(az group show -n rg-devops --query id -o tsv)
cat >> .github/workflows/ci.yml <<EOF
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { id-token: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: \${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: \${{ secrets.AZURE_TENANT_ID }}
          subscription-id: \${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - uses: azure/webapps-deploy@v3
        with: { app-name: $APP }
EOF
git add . && git commit -qm 'deploy job' && git push

    You should see: in Actions, test ✔ then deploy ✔; https://APP.azurewebsites.net/ shows “5 thalis: Rs 675”. No password is stored anywhere — GitHub gets a short-lived token through OIDC.

    UI way — Google Cloud console

    1. Grant the Cloud Build service account permission to deploy (the CLI on the right), create an Artifact Registry repo, and add build, push and deploy steps.
    2. Cloud Run then shows a new revision created by Cloud Build.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project); N=$(gcloud projects describe $P --format='value(projectNumber)')
SA=$N-compute@developer.gserviceaccount.com
for r in run.admin iam.serviceAccountUser artifactregistry.writer logging.logWriter; do gcloud projects add-iam-policy-binding $P --member=serviceAccount:$SA --role=roles/$r --condition=None -q >/dev/null; done

printf 'FROM python:3.12-slim\nWORKDIR /app\nCOPY . .\nRUN pip install -r requirements.txt\nCMD exec gunicorn -b :$PORT app:app\n' > Dockerfile
cat >> cloudbuild.yaml <<'EOF'
- id: build
  name: gcr.io/cloud-builders/docker
  args: ['build', '-t', 'asia-south1-docker.pkg.dev/$PROJECT_ID/menu/app:$BUILD_ID', '.']

  5. 4 · Create infrastructure from code (IaC)

    Pick your cloud.

AWSTemplateFormatVersion: '2010-09-09'

param location string = resourceGroup().location

}

EOF
az deployment group what-if -g rg-devops --template-file main.bicep
az deployment group create -g rg-devops --template-file main.bicep --query properties.outputs.accountName.value -o tsv

    You should see: what-if lists “+ Create” for the storage account; then the account name. Re-running what-if shows no changes.

    UI way — Google Cloud console

    1. Cloud Shell has Terraform installed. Write the file on the right, then terraform init, plan, apply.
    2. (Infrastructure Manager runs the same Terraform as a managed service; Deployment Manager is retired.)

    CLI way — the same thing with commands

    mkdir iac && cd iac
cat > main.tf <<EOF
provider "google" {
  project = "$(gcloud config get-value project)"
  region  = "asia-south1"
}

  name     = "tiffingo-reports-$RANDOM"

    You should see: Plan: 1 to add, 0 to change, 0 to destroy. then Apply complete! Resources: 1 added. Run plan again: “No changes”.

    Commit these files next to the app and run plan in the pipeline — infrastructure changes get the same review and history as code.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Calling a CI server “DevOps”.Tool-first thinking.Change ownership and hand-offs (CALMS); tools support it.
Long-lived cloud keys in pipeline secrets.Easy setup.IAM roles / OIDC federation — short-lived tokens.
Slow, flaky pipelines.Too many end-to-end tests.Test pyramid; keep CI under 10 minutes.
Console changes after IaC.Quick fixes.Change only through code; detect drift.
Big-bang releases every month.Fear of releasing.Small batches, canary, feature flags.
Agile as meetings only.Ceremonies without delivery.Ship working, deployed increments every sprint.
