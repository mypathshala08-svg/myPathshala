1 The story

Same services, different results

Before you start: Module 5 (core concepts) and Module 6 (building blocks).

🤔 Two teams build the same TiffinGo app on the same cloud. One survives Diwali, a data-centre power cut and a security audit at half the cost; the other does not. Same services — what was different?

The architecture. Cloud architecture is how you arrange the provider’s infrastructure (Regions, AZs, networks, servers, the control plane) and services into a system — and every major cloud judges “good” architecture with the same yardstick: the Well-Architected pillars — operational excellence, security, reliability, performance, cost and sustainability. This lesson explains the classic cloud architecture layers, what is physically and logically inside a cloud, the difference between the control plane and the data plane, and each pillar — then you run a real architecture review on your own account.

Two teams used the same cloud services; one design survived failures and cost half as much. The difference was architecture — and the cloud providers have written down how to judge it.

R> Sir, the investor asked for our “cloud architecture”. I sent the list of services we use. A> A list of ingredients is not a recipe. Architecture is how they are arranged — and why. K> How do we know if our arrangement is good? A> AWS, Azure and Google each publish a Well-Architected Framework with the same pillars: run it well, keep it secure, keep it up, keep it fast, keep it affordable, waste less energy. 2 Definition

Cloud architecture and infrastructure

Formal definition (write this in exams)

Cloud architecture is the structured arrangement of cloud components — front-end clients, the network, and back-end services built on the provider’s infrastructure (global Regions, availability zones, data centres, servers, storage and networking, managed by a control plane and serving traffic through a data plane) — designed to meet functional requirements and the quality attributes of operational excellence, security, reliability, performance efficiency, cost optimisation and sustainability.

In simple words

Cloud infrastructure is what the provider owns and runs; cloud architecture is how you arrange its services into an app that is safe, reliable, fast and affordable.

Say it in an interview

30-second answer you can speak:

  • “Cloud architecture has a front end — browsers, apps, SDKs — and a back end of provider services on global infrastructure: Regions, AZs, data centres, with a control plane for APIs and a data plane that serves traffic.”
  • “I evaluate designs with the Well-Architected pillars — operational excellence, security, reliability, performance efficiency, cost optimisation and sustainability — and record trade-offs.”

Type 1 · Operational excellence

Definition (say it in an interview): The operational excellence pillar covers the ability to run and monitor systems to deliver business value and to continually improve processes: performing operations as code, making frequent small reversible changes, anticipating failure, observing everything and learning from operational events.

In plain words (no jargon): Running the system smoothly: automate routine work, change things in small safe steps, watch everything, and learn from every problem.

Analogy: A railway station that runs on a timetable, a control room and an incident register — not on one station master’s memory.

How it works internally, step by step

  1. Organise. Clear ownership, on-call, runbooks.
  2. Prepare. Operations as code; dashboards and alarms before launch.
  3. Operate. Small, frequent, reversible deployments; health checks.
  4. Observe. Metrics, logs, traces tied to business outcomes.
  5. Evolve. Post-incident reviews and game days drive improvements.

Words used above, in simple terms: runbook = step-by-step instructions for a routine task · rollback = going back to the previous version · blameless review = studying what failed without punishing people · game day = a planned practice of failures

For the experienced — did you know? “Operations as code” includes the response: AWS Systems Manager Automation, Azure Automation runbooks and Google Cloud Workflows let an alarm trigger the fix itself — the runbook becomes a program, not a PDF.

Use it when: always — it is what makes every other pillar sustainable over time.
Avoid / be careful when: operations depend on manual console clicks and one person’s knowledge (the “bus factor” of one).

Type 2 · Security

Definition (say it in an interview): The security pillar covers protecting data, systems and assets: a strong identity foundation with least privilege, traceability, security at every layer (defence in depth), protecting data in transit and at rest, automating security controls and preparing for security events — all within the shared responsibility model.

In plain words (no jargon): Keeping the bad guys out and the data safe: only the right people get in, everything is locked (encrypted), and every action is recorded.

Analogy: A bank: ID checks at the door, separate keys for each locker, CCTV everywhere, alarms connected to the police — and the bank, not the customer, guards the building.

How it works internally, step by step

  1. Identity first. Central identity, MFA, roles, least privilege.
  2. Layers. Network, host, app and data controls — each assumes the others may fail.
  3. Data protection. Classification, encryption, backups, access logs.
  4. Detection. Audit logs, threat detection, alerts.
  5. Response. Prepared playbooks and automated containment.

Words used above, in simple terms: least privilege = only the permissions needed · defence in depth = several layers of protection · shared responsibility = provider secures the cloud; you secure what you put in it · encryption = scrambling data so only key holders can read it

For the experienced — did you know? Most cloud breaches come from the customer side of shared responsibility — leaked keys, public buckets, over-broad roles — not from broken provider infrastructure. That is why every framework puts identity as the first security design principle.

Use it when: from the first day — retrofitting security is much harder.
Avoid / be careful when: security is treated as one firewall at the edge, or as only the provider’s job.

Type 3 · Reliability

Definition (say it in an interview): The reliability pillar covers a workload’s ability to perform its intended function correctly and consistently, recover automatically from failure, scale to meet demand and mitigate disruptions — through redundancy, health-based self-healing, managed change and regularly tested recovery.

In plain words (no jargon): Keeping the app working even when parts break — with spare copies, automatic repairs and practised recovery.

Analogy: A hospital with two power lines, a diesel generator and monthly generator tests: patients never notice a power cut.

How it works internally, step by step

  1. Set targets. Availability SLO, RTO and RPO per workload.
  2. Remove single points. Redundant components across fault domains (AZs, Regions).
  3. Detect. Health checks and alarms.
  4. Recover automatically. Replace, fail over, retry with backoff.
  5. Test. Backup restores, chaos experiments, DR drills.

Words used above, in simple terms: single point of failure = one part whose failure stops everything · RTO = how long recovery may take · RPO = how much data may be lost · chaos engineering = breaking things on purpose to learn

For the experienced — did you know? Retries can cause outages: when every client retries a slow service at once, load multiplies and it never recovers (a “retry storm”). Exponential backoff with jitter and circuit breakers (Lesson 7.5) are reliability features, not optimisations.

Use it when: the service matters to customers — set SLOs (Lesson 5.4) and design to them.
Avoid / be careful when: you copy the provider’s SLA as your own or assume backups work without restoring them.

Type 4 · Performance efficiency

Definition (say it in an interview): The performance efficiency pillar covers using computing resources efficiently to meet requirements and maintaining that efficiency as demand changes and technologies evolve: selecting the right resource types and sizes, using managed and serverless services, going global with edges and Regions, and experimenting and measuring continuously.

In plain words (no jargon): Making the app fast without wasting resources — using the right tool for each job, putting content near users, and measuring what is slow.

Analogy: Choosing the right vehicle: a scooter for a tiffin, a tempo for a wedding order, a train for 5,000 meals — not one big truck for everything.

How it works internally, step by step

  1. Select. Instance family, storage type, database model per need.
  2. Use managed/serverless. Let the provider handle scaling and tuning.
  3. Go global. Regions near users, CDN, global load balancing.
  4. Monitor. Latency percentiles (p95/p99), throughput, saturation.
  5. Experiment. Load tests, A/B different types, adopt new generations.

Words used above, in simple terms: latency = time for one request · throughput = how much work per second · p99 = the time within which 99% of requests finish · benchmark = a standard test to compare options

For the experienced — did you know? Average latency hides pain: an API with 50 ms average can still have a p99 of 2 seconds. All three frameworks recommend designing and alarming on percentiles, not averages.

Use it when: latency or throughput matter to users, or costs grow with load.
Avoid / be careful when: you tune before measuring — optimise the slowest step, not the one you like.

Type 5 · Cost optimisation

Definition (say it in an interview): The cost optimisation pillar covers running systems to deliver business value at the lowest price point: practising cloud financial management, measuring and attributing spend, adopting a consumption model, using the right pricing models, removing waste and analysing cost against business outcomes.

In plain words (no jargon): Getting the most value for the money: knowing what you spend, paying only for what you use, and choosing cheaper options where they are good enough.

Analogy: Running a kitchen: buy rice in bulk because you use it daily, rent the extra tandoor only for weddings, and switch off the gas when nobody is cooking.

How it works internally, step by step

  1. Own it. Finance + engineering share responsibility (FinOps).
  2. Measure. Tags, cost allocation, dashboards, budgets.
  3. Consume. Scale to demand; turn off idle; serverless where it fits.
  4. Buy smart. Savings Plans/reservations for baseline, Spot for flexible work.
  5. Unit economics. Cost per customer/order; review trends.

Words used above, in simple terms: FinOps = shared financial accountability for cloud spend · right-sizing = choosing the smallest size that does the job · unit cost = cost per order/customer/request · waste = resources paid for but not used

Avoid / be careful when: cost is checked once a quarter from the invoice, or optimisation removes redundancy that reliability needs.

Type 6 · Sustainability

Definition (say it in an interview): The sustainability pillar covers minimising the environmental impact of cloud workloads — energy use and emissions — by understanding your footprint, maximising utilisation, choosing efficient hardware and services, reducing data and downstream impact, and selecting Regions by their carbon intensity where business needs allow.

In plain words (no jargon): Making the cloud app use less electricity and create less pollution — mostly by not wasting resources.

Analogy: Sharing a bus instead of each person driving: the same journey, far less fuel per person — the cloud’s high utilisation already helps; your design decides the rest.

How it works internally, step by step

  1. Measure. Use the provider’s carbon footprint tool.
  2. Set goals. e.g. CO₂e per 1,000 orders.
  3. Maximise utilisation. Right-size, autoscale, delete idle.
  4. Efficient tech. ARM chips, managed/serverless services, efficient code and formats.
  5. Reduce data. Lifecycle rules, compression, fewer copies.

Words used above, in simple terms: CO₂e = carbon dioxide equivalent — a standard emissions unit · carbon intensity = emissions per unit of electricity in a grid · utilisation = how much of a resource is actually used · ESG = environmental, social and governance reporting

Use it when: you want to report or reduce emissions — increasingly asked by investors and large customers (ESG).
Avoid / be careful when: you move data to a far-away “green” Region against latency or data-residency rules (e.g. RBI data localisation).

6 Explained part by part

Six terms every architecture discussion uses

Front end

What it is: What users touch: browsers, apps, SDKs, CLIs.

Why it exists: Where experience and security begin.

Where it is used: Web/mobile apps, CloudShell, SDKs.

Back end

What it is: Provider-run services and infrastructure.

Why it exists: Where data is stored and processed.

Where it is used: Compute, storage, databases, networking.

Network

What it is: Connects front end and back end.

Why it exists: Latency, security and cost all depend on it.

Where it is used: Internet, CDN, VPN, private links.

Control plane

What it is: APIs that create, change and delete resources.

Why it exists: Automation and IaC call it; changes are logged.

Where it is used: EC2 API, Azure Resource Manager, Google Cloud APIs.

Data plane

What it is: The running service handling your traffic and I/O.

Why it exists: Must stay up even when the control plane is impaired.

Where it is used: Instance networking, LB nodes, storage I/O.

Landing zone

What it is: A pre-built multi-account foundation with guardrails.

Why it exists: Every new project starts secure and governed.

Where it is used: AWS Control Tower, Azure landing zones, Google Cloud foundation blueprint.

Myth vs reality: things many websites still say

  • Myth: Architecture is the list of services.
    Reality: It is how they are arranged, and why.
    Proof: Story.
  • Myth: If the console is down, my app is down.
    Reality: Data planes keep running; design for static stability.

    Reality: It balances six pillars.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. These steps create nothing that costs money (the Well-Architected workload, recommendations and logs are free).

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Run an architecture review on your workload

    Pick your cloud.

    UI way — AWS Management Console

    1. Search Well-Architected Tool → Define workload → name tiffingo-orders, environment, Region Mumbai, lens AWS Well-Architected Framework → Define workload.
    2. Start reviewing → answer 5 questions of the Reliability pillar honestly (e.g. “How do you design for failure?”).
    3. Save and exit → the dashboard shows high/medium-risk items and links to improvement plans.

  --query WorkloadId --output text)
aws wellarchitected list-answers --workload-id $WID --lens-alias wellarchitected --pillar-id reliability \
  --query 'AnswerSummaries[].QuestionTitle' --output text | tr '\t' '\n' | head -5

    You should see: a workload ID and the first reliability questions (e.g. “How do you manage service quotas and constraints?”). The tool is free.

    UI way — Azure portal

    1. Search Advisor → Advisor score — a score per category that maps to the Well-Architected pillars.
    2. Open Reliability and Security recommendations; click one to see the affected resources and the fix.
    3. For a full questionnaire use the Microsoft Learn “Azure Well-Architected Review” assessment (free, in the browser).

    CLI way — the same thing with commands

    az advisor recommendation list --category HighAvailability --output table
az advisor recommendation list --category Security --query "[].shortDescription.problem" --output tsv | head

    You should see: a list (possibly empty on a new subscription) of recommendations with impact High/Medium/Low.

    UI way — Google Cloud console

    1. Search Recommendations (Active Assist) → overview by category: cost, security, performance, reliability, sustainability.
    2. Open the Well-Architected Framework page from the Architecture Center and go through the reliability checklist for your design.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud services enable recommender.googleapis.com
gcloud recommender recommendations list --project=$P --location=global \
  --recommender=google.iam.policy.Recommender --format="table(name.basename(),description)"

    You should see: IAM role recommendations (least privilege) once the project has some history; empty on a brand-new project.

    Reviews are only useful if you answer honestly — every “no” is an item for the improvement plan.

  3. 2 · See the physical infrastructure you rent

    Pick your cloud.

    UI way — AWS Management Console

    1. EC2 → Settings → Zones: the three Mumbai AZs with their zone IDs and any Local Zones.
    2. Top-right Region menu: count the Regions.

    CLI way — the same thing with commands

    aws ec2 describe-availability-zones --region ap-south-1 --query 'AvailabilityZones[].[ZoneName,ZoneId,State]' --output table
aws ec2 describe-regions --query 'length(Regions)'

    You should see: ap-south-1a/b/c with IDs like aps1-az1 (the mapping differs per account — Lesson 5.1) and the number of Regions enabled for you.

    UI way — Azure portal

    1. Subscriptions → your subscription → Usage + quotas → provider Compute, location Central India: your vCPU quota.
    2. Search Azure regions documentation or run the CLI to list Regions and paired Regions.

    CLI way — the same thing with commands

    az account list-locations --query "[?metadata.regionType=='Physical'] | length(@)"
az account list-locations --query "[?name=='centralindia'].{name:name, pair:metadata.pairedRegion[0].name}" --output table
az vm list-usage --location centralindia --query "[?name.value=='cores']" --output table

    You should see: the number of physical Regions, Central India paired with South India, and your regional vCPU limit.

    UI way — Google Cloud console

    1. Compute Engine → Zones: asia-south1-a, -b, -c.
    2. IAM & Admin → Quotas & System Limits → filter “CPUs” and Region asia-south1.

    CLI way — the same thing with commands

    gcloud compute regions list --format="value(name)" | wc -l
gcloud compute zones list --filter="region:asia-south1" --format="table(name,status)"
gcloud compute regions describe asia-south1 --format="table(quotas.metric,quotas.limit)" | head

    You should see: the number of Regions, three UP zones in Mumbai, and regional quotas such as CPUS.

    Quotas are part of infrastructure design: a DR plan that needs 200 vCPUs in another Region fails if the quota there is 32.

  4. 3 · Watch the control plane: who changed what

    Pick your cloud.

    UI way — AWS Management Console

    1. CloudTrail → Event history → filter Event name = CreateSecurityGroup (or any action you did in Module 6).
    2. Open an event: user, source IP, time, request parameters — the control plane’s record.

    CLI way — the same thing with commands

    aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=CreateSecurityGroup \
  --max-results 5 --query 'Events[].[EventTime,Username,EventName]' --output table

    You should see: your own earlier API calls with time and user. Data-plane activity (packets, S3 reads) is not in this history.

    UI way — Azure portal

    1. Monitor → Activity log → timespan 24 hours → filter resource group rg-tiffingo.
    2. Open an entry → JSON: caller, operation, status.

    CLI way — the same thing with commands

    az monitor activity-log list --offset 1d --query "[].{time:eventTimestamp, op:operationName.localizedValue, who:caller}" --output table | head -15

    You should see: create/update/delete operations you made, with the caller’s e-mail.

    UI way — Google Cloud console

    1. Logging → Logs Explorer → query logName:"cloudaudit.googleapis.com%2Factivity" → Run query.
    2. Expand an entry: protoPayload.methodName and authenticationInfo.principalEmail.

    CLI way — the same thing with commands

    gcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity"' --freshness=1d --limit=10 \
  --format="table(timestamp,protoPayload.methodName,protoPayload.authenticationInfo.principalEmail)"

    You should see: Admin Activity audit entries such as v1.compute.instances.insert with your e-mail.

    Every control-plane action is recorded for free (CloudTrail event history 90 days, Activity Log 90 days, Admin Activity audit logs 400 days).

Clean up and cost check

AWS: Well-Architected Tool → workload → Delete; CLI aws wellarchitected delete-workload --workload-id $WID. Azure and Google Cloud: nothing was created (only read).

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Calling a list of services an architecture.Confusing parts with design.Show arrangement, data flow, failure domains and the reasons.
Optimising one pillar only.Pressure on cost or speed.Review all pillars; record trade-offs.
Recovery that depends on the control plane.Assuming you can launch capacity during an outage.Pre-provision capacity; design for static stability.
Never doing a design review.“We are too small.”Run a free review on each important workload once a year.
Ignoring quotas in DR plans.Quotas are invisible until hit.Check and raise quotas in the DR Region in advance.
Security and cost as afterthoughts.Feature pressure.Make them requirements from day one.
