1 The story

A one-line change that broke payments

Before you start: 7.3 Multi-tier and 6.4 (integration services).

🤔 TiffinGo has 25 developers working in one big codebase. A one-line change to the SMS text needs a full release of the whole app — and last week it broke payments. Should they split everything into 40 microservices tomorrow?

Probably not. A monolith is one deployable application; microservices are many small services, each owning one business capability and its data; serverless builds the app from managed services and functions that run on events. Each style trades simplicity against independence and scale — and most successful companies move gradually. This lesson explains seven architecture styles from monolith to event-driven, shows how one order flows through microservices, and on your own account you wire services together with events — the glue that makes microservices and serverless work.

2 Definition

Monolith vs microservices vs serverless

Formal definition (write this in exams)

A monolithic architecture deploys an application as a single unit; a microservices architecture composes it from small, independently deployable services aligned to business capabilities, each owning its data and communicating via APIs or events; a serverless architecture builds it from fully managed services and event-triggered functions where the provider handles servers, scaling and per-use billing.

In simple words

Monolith = one big app. Microservices = many small apps working together. Serverless = an app built from cloud services and small functions, with no servers to manage.

Say it in an interview

30-second answer you can speak:

  • “A monolith is one deployable unit — simple to build and run. Microservices split by business capability with their own data and deployments — independent teams and scaling, but more network, data-consistency and operational complexity.”
  • “Serverless uses managed services and functions — no servers, pay per use. I usually start with a modular monolith and extract services with the strangler fig pattern, connecting them with events.”

Type 1 · Monolith

Definition (say it in an interview): A monolithic architecture builds an application as a single deployable unit in which all features — user interface, business logic and data access — share one codebase, one process (or tightly coupled processes) and usually one database, and are built, tested, deployed and scaled together.

In plain words (no jargon): The whole app is one big program. Simple to build and run, but every change means releasing everything.

Analogy: A joint family kitchen: one big kitchen cooks everything; easy to coordinate — but renovating the stove means nobody eats that day.

How it works internally, step by step

  1. Code. All modules in one repository and one runtime.
  2. Call. Modules call each other as functions (fast, transactional).
  3. Store. One shared database, ACID transactions across features.
  4. Deploy. Build and release the whole app.
  5. Scale. Run more identical copies behind a load balancer.

Words used above, in simple terms: deployable unit = what you release as one piece · in-process call = a function call inside the same program · ACID transaction = changes that all succeed or all fail

Products and cloud services

For the experienced — did you know? “Monolith” is a deployment property, not a quality grade. A monolith with clean module boundaries is easier to split later than “microservices” that share one database — the dreaded distributed monolith.

Use it when: small teams, new products, simple domains — start here.
Avoid / be careful when: many teams change different parts at different speeds, or one part needs very different scaling.

Type 2 · Modular monolith

Definition (say it in an interview): A modular monolith is a single deployable application internally divided into well-defined modules aligned to business capabilities, each with a clear public interface and ownership of its own data, with dependency rules enforced in code — combining monolith simplicity with microservice-style boundaries.

In plain words (no jargon): Still one program, but neatly divided into separate parts that do not mess with each other — easy to split later if needed.

Analogy: One building divided into separate flats with their own doors and meters: one address, one roof, but neighbours do not walk through each other’s kitchens.

How it works internally, step by step

  1. Find boundaries. Business capabilities (bounded contexts).
  2. Hide internals. Modules talk through interfaces.
  3. Own data. Separate schemas/tables per module.
  4. Enforce. Build-time dependency checks.
  5. Extract later. A module can become a service with little rework.

Words used above, in simple terms: module = a self-contained part of the code · bounded context = a business area with its own model and words · interface = the agreed way to call a module

For the experienced — did you know? Microsoft’s and Google’s architecture guides now recommend starting with a modular monolith (“monolith first”) unless team scale already demands independent deployment.

Use it when: you want independence between teams but not yet the operational cost of microservices — often the best default.
Avoid / be careful when: parts truly need separate scaling, technology or release cadence — then extract them as services.

Type 3 · Service-oriented architecture (SOA)

Definition (say it in an interview): Service-oriented architecture (SOA) structures enterprise systems as coarse-grained, reusable services with formal contracts (often SOAP/WSDL), typically connected and orchestrated through a central enterprise service bus (ESB) that handles routing, transformation and protocol mediation, under central governance.

In plain words (no jargon): An older style where big shared services are connected through one central message system that controls everything.

Analogy: A government office with a central inward-section clerk: every file passes through one desk that stamps, translates and forwards it to the right department.

How it works internally, step by step

  1. Define services. Business functions with formal contracts.
  2. Register. In a service registry.
  3. Connect via ESB. The bus routes and transforms messages.
  4. Orchestrate. Business processes call multiple services.
  5. Govern. Central standards and versioning.

Words used above, in simple terms: ESB = enterprise service bus — a central integration hub · SOAP = an XML-based web-service protocol · orchestration = a central controller calling services in order

For the experienced — did you know? Microservices are often described as “SOA done right”: the key change is smart endpoints, dumb pipes — logic moves out of the central bus into the services, and the bus becomes simple messaging.

Use it when: large enterprises integrating many existing systems with shared business services.
Avoid / be careful when: you need rapid independent releases — the central bus and governance become bottlenecks.

Type 4 · Microservices

Definition (say it in an interview): A microservices architecture builds an application as a suite of small, independently deployable services, each aligned to a business capability, owning its own data, communicating over lightweight APIs or asynchronous events, and typically developed and operated by a small autonomous team.

In plain words (no jargon): The app is split into many small programs, each doing one job with its own data, built by its own team and updated on its own.

Analogy: A food court instead of one restaurant: each stall has its own cooks, menu and stock; one stall closing does not close the court.

How it works internally, step by step

  1. Split by capability. Bounded contexts → services.
  2. Own data. Database per service; no shared tables.
  3. Communicate. REST/gRPC for queries, events for changes.
  4. Deploy independently. Pipeline per service; containers or functions.
  5. Operate. Tracing, centralised logs, per-service SLOs, resilience patterns (7.5).

Words used above, in simple terms: service = a separately deployed program with an API · database per service = each service keeps its own data · gRPC = a fast service-to-service protocol · distributed tracing = following a request across services

For the experienced — did you know? The hardest part is data: a business transaction spanning services (pay + reserve kitchen slot) cannot use one ACID transaction — teams use the saga pattern (a series of local steps with compensating actions) and accept eventual consistency.

Use it when: large or fast-growing teams, parts with very different scaling or release needs, strong DevOps maturity.
Avoid / be careful when: a small team or unclear domain — you pay network, consistency and operations costs without the benefits.

Type 5 · Serverless architecture

Definition (say it in an interview): A serverless architecture builds applications primarily from fully managed services — functions (FaaS), API gateways, managed databases, queues, event buses, authentication — so that developers write only business logic and the platform handles provisioning, scaling, availability and per-use billing.

In plain words (no jargon): You build the app by connecting ready-made cloud services, and write only small pieces of code. No servers to manage; you pay per use.

Analogy: Hosting a wedding entirely with hired services — caterer, decorator, DJ, valet — you plan and coordinate; you do not own a single plate.

How it works internally, step by step

  1. Choose services. Auth, API, data, messaging, workflow — all managed.
  2. Write functions. Small handlers for events and API routes.
  3. Wire with events. Triggers connect services.
  4. Configure. Permissions (IAM), limits, retries in IaC (SAM, CDK, Bicep, Terraform).
  5. Observe. Per-function metrics, traces and costs.

Words used above, in simple terms: FaaS = function as a service · trigger = what starts a function · cold start = delay when a new function copy starts · vendor lock-in = dependence on one provider’s services

Type 6 · Event-driven architecture

Definition (say it in an interview): An event-driven architecture lets components communicate by producing and consuming events — immutable records that something happened (e.g. “OrderPlaced”) — through brokers such as topics, queues, event buses or streams, so producers and consumers are decoupled in time, location and knowledge of each other.

In plain words (no jargon): Parts of the app announce “this happened” and other parts react to it on their own — nobody waits for anybody.

Analogy: A temple bell: the priest rings it once; devotees, flower sellers and the prasad counter each react in their own way — the priest does not phone each of them.

How it works internally, step by step

  1. Define events. Name (past tense), schema, version.
  2. Publish. Producer sends to a topic/bus/stream.
  3. Route. Rules or subscriptions deliver copies.
  4. Consume. Each consumer processes at its pace; idempotently.
  5. Handle failure. Retries, dead-letter queues, replay from streams.

Words used above, in simple terms: event = a record that something happened · producer / consumer = who sends / who reacts · broker = the service that stores and delivers events · eventual consistency = all parts agree after a short delay

Use it when: several parts must react to the same change, workloads are spiky, or you want to add features without touching existing services.
Avoid / be careful when: you need an immediate answer from the other side (use a request/response API) or strict global ordering everywhere.

Type 7 · Strangler fig migration

Definition (say it in an interview): The strangler fig pattern incrementally migrates a legacy system by placing a routing façade in front of it and redirecting one capability at a time to new services, until the old system can be retired — avoiding a risky “big bang” rewrite.

In plain words (no jargon): Moving from an old app to a new design one piece at a time, with a traffic router deciding which part handles each request.

Analogy: Renovating a house room by room while the family keeps living in it, instead of demolishing it and living on the street for a year.

How it works internally, step by step

  1. Façade. Route all traffic through a gateway/proxy.
  2. Pick a seam. A feature with clear boundaries and high change rate.
  3. Build new. New service + its data (sync data during transition).
  4. Redirect. Change routing rules; monitor; roll back if needed.
  5. Retire. Remove dead code; repeat.

Words used above, in simple terms: façade = a front that hides what is behind it · seam = a natural place to cut a system apart · big bang rewrite = replacing everything at once

Avoid / be careful when: the old system cannot be put behind a proxy, or data cannot be separated feature by feature (plan data migration first).

6 Explained part by part

Six building blocks of service-based systems

API gateway

What it is: Single entry point for clients.

Why it exists: Auth, routing, rate limits, versioning.

Where it is used: API Gateway, APIM, Apigee.

Service discovery

What it is: How services find each other.

Why it exists: Addresses change as containers move.

Where it is used: Cloud Map, Kubernetes DNS, Consul.

Event bus / broker

What it is: Delivers events and messages.

Why it exists: Decouples producers and consumers.

Where it is used: EventBridge, Service Bus, Pub/Sub, Kafka.

Distributed tracing

What it is: Follows one request across services.

Why it exists: Debugging across 20 services needs it.

Where it is used: X-Ray, Application Insights, Cloud Trace, OpenTelemetry.

Saga

What it is: A multi-step business transaction with compensations.

Why it exists: Replaces cross-service ACID transactions.

Where it is used: Step Functions, Durable Functions, Workflows.

Conway’s law

What it is: Systems mirror the communication structure of the organisation.

Why it exists: Design services around teams.

Where it is used: “Two-pizza teams” owning services.

Myth vs reality: things many websites still say

  • Myth: Microservices are always better.
    Reality: They trade simplicity for independence.
    Proof: Trade-offs figure.
  • Myth: Serverless means no architecture.
    Reality: You design events, limits, permissions and costs.
    Proof: Type 5.
  • Myth: Splitting fixes bad code.
    Reality: Bad boundaries become a distributed monolith.
    Proof: Type 1 expert note.
7 Deep dive

When to split, hidden costs, choreography vs orchestration

When to split: a checklist

  • Different parts need different release speeds (SMS text changes daily, payments monthly).
  • Different parts need different scaling (search at Diwali ×20, admin ×1).
  • Teams block each other in one codebase.
  • You have CI/CD, monitoring, tracing and on-call maturity.

If fewer than two boxes are ticked, improve the modular monolith first.

The costs nobody puts on the slide

CostWhy
Network latency and failuresevery call can be slow or fail; needs timeouts, retries, circuit breakers (7.5)
Data consistencyno cross-service transactions; sagas and eventual consistency
Observabilitylogs and traces across many services
Platform workpipelines, service mesh, secrets, versioning for each service
Testingcontract tests between services

Choreography vs orchestration

Choreography: services react to events with no central controller (flexible, harder to see the whole flow). Orchestration: a workflow service (Step Functions, Durable Functions, Google Workflows) calls each step and handles failures (visible, central). Many systems use events between domains and orchestration inside one workflow.

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

  2. 1 · Fan-out: one event, two independent services

    Pick your cloud.

    UI way — AWS Management Console

    1. Simple Notification Service → Topics → Create topic → Standard, name tiffingo-order-placed.
    2. SQS → create queues tiffingo-kitchen and tiffingo-sms; for each: Subscribe to Amazon SNS topic → choose the topic (the console adds the queue policy).
    3. Topic → Publish message → body {"order":101}; each queue → Send and receive messages → Poll for messages: both got it.

    CLI way — the same thing with commands

    T=$(aws sns create-topic --name tiffingo-order-placed --query TopicArn --output text)
for q in kitchen sms; do
  U=$(aws sqs create-queue --queue-name tiffingo-$q --query QueueUrl --output text)
  A=$(aws sqs get-queue-attributes --queue-url $U --attribute-names QueueArn --query Attributes.QueueArn --output text)
  aws sqs set-queue-attributes --queue-url $U --attributes "$(python3 -c "import json,sys; q,s,src=sys.argv[1:4]; print(json.dumps({'Policy': json.dumps({'Version':'2012-10-17','Statement':[{'Effect':'Allow','Principal':{'Service':s},'Action':'sqs:SendMessage','Resource':q,'Condition':{'ArnEquals':{'aws:SourceArn':src}}}]})}))" $A sns.amazonaws.com $T)"
  aws sns subscribe --topic-arn $T --protocol sqs --notification-endpoint $A --attributes RawMessageDelivery=true
done
aws sns publish --topic-arn $T --message '{"order":101}'
for q in kitchen sms; do aws sqs receive-message --queue-url $(aws sqs get-queue-url --queue-name tiffingo-$q --query QueueUrl --output text) --wait-time-seconds 5 --query 'Messages[0].Body' --output text; done

    You should see: {"order":101} printed twice — once from the kitchen queue and once from the SMS queue. The publisher did not know either of them.

    UI way — Azure portal

    1. Subscriptions → Resource providers → register Microsoft.EventGrid.
    2. Event Grid Topics → Create → tiffingo-orders-<n>, Central India. In your storage account create queues kitchen and sms.
    3. Topic → + Event Subscription → endpoint type Storage Queues → queue kitchen; repeat for sms. Publish with the CLI (the portal has no publish button) and look at both queues in Storage browser.

    CLI way — the same thing with commands

    az provider register --namespace Microsoft.EventGrid
TOPIC=tiffingo-orders-$RANDOM
az eventgrid topic create --resource-group rg-tiffingo --name $TOPIC --location centralindia
TID=$(az eventgrid topic show --resource-group rg-tiffingo --name $TOPIC --query id --output tsv)
SAID=$(az storage account show --name $SA --query id --output tsv)
for q in kitchen sms; do
  az storage queue create --account-name $SA --name $q --auth-mode key
  az eventgrid event-subscription create --name $q --source-resource-id $TID \
    --endpoint-type storagequeue --endpoint $SAID/queueservices/default/queues/$q
done
EP=$(az eventgrid topic show --resource-group rg-tiffingo --name $TOPIC --query endpoint --output tsv)
KEY=$(az eventgrid topic key list --resource-group rg-tiffingo --name $TOPIC --query key1 --output tsv)
curl -s -X POST -H "aeg-sas-key: $KEY" -H 'Content-Type: application/json' $EP \
  -d '[{"id":"1","eventType":"OrderPlaced","subject":"orders/101","eventTime":"'$(date -u +%Y-%m-%dT%H:%M:%SZ)'","data":{"order":101},"dataVersion":"1.0"}]'
for q in kitchen sms; do az storage message get --account-name $SA --queue-name $q --auth-mode key --query "[0].content" --output tsv; done

    You should see: two messages (base64-encoded event JSON with OrderPlaced) — one per queue.

    UI way — Google Cloud console

    1. Pub/Sub → Create topic tiffingo-order-placed (untick default subscription).
    2. Subscriptions → Create subscription kitchen-sub and sms-sub on that topic, pull delivery.
    3. Topic → Messages → Publish message {"order":101}; each subscription → Messages → Pull.

    CLI way — the same thing with commands

    gcloud pubsub topics create tiffingo-order-placed
for s in kitchen-sub sms-sub; do gcloud pubsub subscriptions create $s --topic=tiffingo-order-placed; done
gcloud pubsub topics publish tiffingo-order-placed --message='{"order":101}'
for s in kitchen-sub sms-sub; do gcloud pubsub subscriptions pull $s --auto-ack --limit=1 --format='value(message.data)'; done

    You should see: {"order":101} twice — each subscription gets its own copy.

    This is the backbone of microservices and serverless: add a third subscriber tomorrow without touching the publisher.

  3. 2 · A storage upload becomes an event (no code)

    Pick your cloud.

    UI way — AWS Management Console

    1. Create queue tiffingo-photo-worker; edit its Access policy to allow s3.amazonaws.com to SendMessage from your bucket ARN.
    2. Bucket → Properties → Event notifications → Create event notification → all object create events → destination SQS queue → tiffingo-photo-worker → Save changes.
    3. Upload any file → poll the queue: an S3 event with the object key.

    CLI way — the same thing with commands

    B=tiffingo-photos-$RANDOM$RANDOM; aws s3 mb s3://$B --region ap-south-1
U=$(aws sqs create-queue --queue-name tiffingo-photo-worker --query QueueUrl --output text)
A=$(aws sqs get-queue-attributes --queue-url $U --attribute-names QueueArn --query Attributes.QueueArn --output text)
aws sqs set-queue-attributes --queue-url $U --attributes "$(python3 -c "import json,sys; q,s,src=sys.argv[1:4]; print(json.dumps({'Policy': json.dumps({'Version':'2012-10-17','Statement':[{'Effect':'Allow','Principal':{'Service':s},'Action':'sqs:SendMessage','Resource':q,'Condition':{'ArnEquals':{'aws:SourceArn':src}}}]})}))" $A s3.amazonaws.com arn:aws:s3:::$B)"
aws s3api put-bucket-notification-configuration --bucket $B --notification-configuration \
  '{"QueueConfigurations":[{"QueueArn":"'$A'","Events":["s3:ObjectCreated:*"]}]}'
echo thali > thali.jpg && aws s3 cp thali.jpg s3://$B/
aws sqs receive-message --queue-url $U --wait-time-seconds 10 --query 'Messages[].Body' --output text | head -c 400

    You should see: a JSON body with "eventName":"ObjectCreated:Put" and "key":"thali.jpg" (the first message may be an s3:TestEvent).

    UI way — Azure portal

    1. Storage account → Queues → create photo-worker.
    2. Events → + Event Subscription → name photo-upload, event types Blob Created, endpoint Storage Queues → photo-worker → Create.
    3. Upload a blob to any container → Storage browser → queue photo-worker: one message.

    CLI way — the same thing with commands

    SAID=$(az storage account show --name $SA --query id --output tsv)
az storage queue create --account-name $SA --name photo-worker --auth-mode key
az eventgrid event-subscription create --name photo-upload --source-resource-id $SAID \
  --endpoint-type storagequeue --endpoint $SAID/queueservices/default/queues/photo-worker \
  --included-event-types Microsoft.Storage.BlobCreated
az storage container create --account-name $SA --name photos --auth-mode key
echo thali > thali.jpg && az storage blob upload --account-name $SA --container-name photos --name thali.jpg --file thali.jpg --auth-mode key
sleep 10; az storage message get --account-name $SA --queue-name photo-worker --auth-mode key --query "[0].content" --output tsv | base64 -d | head -c 400

    You should see: an Event Grid event with "eventType":"Microsoft.Storage.BlobCreated" and the blob URL.

    UI way — Google Cloud console

    1. Create a bucket and a topic photo-uploads.
    2. Bucket notifications are set from the CLI (no console page): run the commands on the right.
    3. Upload a file → Pub/Sub → subscription photo-worker → Pull.

    CLI way — the same thing with commands

    B=tiffingo-photos-$RANDOM$RANDOM
gcloud storage buckets create gs://$B --location=asia-south1
gcloud pubsub topics create photo-uploads
gcloud storage buckets notifications create gs://$B --topic=photo-uploads --event-types=OBJECT_FINALIZE
gcloud pubsub subscriptions create photo-worker --topic=photo-uploads
echo thali > thali.jpg && gcloud storage cp thali.jpg gs://$B/
sleep 10; gcloud pubsub subscriptions pull photo-worker --auto-ack --limit=1 --format='table(message.attributes.eventType,message.attributes.objectId)'

    You should see: OBJECT_FINALIZE thali.jpg. The Cloud Storage service agent is granted publish rights on the topic automatically.

    A photo-resizing microservice or function would read this queue — the upload code never needs to know it exists.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Starting a new product with dozens of microservices.Hype; copying Netflix.Modular monolith first; extract when a checklist says so.
Services sharing one database.Easier than moving data.Database per service; integrate via APIs/events.
Chains of synchronous calls (A→B→C→D).Feels like function calls.Use events; add timeouts, retries, circuit breakers.
Big-bang rewrites.Old code feels hopeless.Strangler fig, feature by feature.
Events named as commands (“SendSMS”).Thinking of one consumer.Publish facts (“OrderPlaced”).
Non-idempotent consumers.Assuming exactly-once delivery.Deduplicate by event ID; make handlers idempotent.
No tracing across services.Logging per service only.OpenTelemetry + X-Ray / App Insights / Cloud Trace from day one.
