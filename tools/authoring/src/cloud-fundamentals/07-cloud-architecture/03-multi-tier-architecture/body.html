1 The story

The server that did everything

Before you start: 6.3 Networking and 7.2.

🤔 TiffinGo’s first version was one PHP server with the database on the same machine. It was cheap and simple — until Diwali, when the database ate all the memory and the website died with it. Why did splitting it into “tiers” fix this?

Because tiers separate jobs that grow, fail and are secured differently: the presentation tier (what users see), the application tier (business logic) and the data tier (storage). Each tier can scale on its own, sit in its own network zone and be replaced without touching the others. This lesson explains 1-, 2-, 3- and n-tier designs, how they look in the cloud (including serverless and static front ends), how a request passes through the tiers — and you build a small three-tier app on your own account.

2 Definition

Multi-tier architecture

Formal definition (write this in exams)

A multi-tier (n-tier) architecture divides an application into physically separate tiers — typically a presentation tier, an application (business logic) tier and a data tier — each running on its own infrastructure, communicating through defined interfaces with only adjacent tiers, so that each can be developed, scaled, secured and maintained independently.

In simple words

Split the app into layers that run separately: the screens, the brain and the storage — so each can grow and be protected on its own.

Say it in an interview

30-second answer you can speak:

  • “A three-tier app has presentation, application and data tiers. In AWS: CloudFront/S3 or an ALB in public subnets, app servers or Lambda in private subnets, and RDS or DynamoDB in isolated subnets reachable only from the app tier.”
  • “Tiers scale independently, contain failures and allow defence in depth; n-tier adds caches, queues and workers.”

Type 1 · Single-tier (one-tier) architecture

Definition (say it in an interview): A single-tier architecture places the user interface, business logic and data storage in one application on one machine or process, with no network separation between them.

In plain words (no jargon): One computer does everything: shows the screens, does the work and stores the data.

Analogy: A roadside tea stall run by one person: takes the order, makes the tea and keeps the stock under the counter — perfect until 200 customers arrive.

How it works internally, step by step

  1. Install. Web server, app and database on one machine.
  2. Call locally. Code calls the database on localhost.
  3. Scale. Only vertically (bigger machine).
  4. Back up. The whole machine.
  5. Fail. Everything together.

Words used above, in simple terms: tier = a separately run part of an app · localhost = the same machine · LAMP = Linux, Apache, MySQL, PHP — a classic one-box stack

For the experienced — did you know? A single-tier app can still be cloud-friendly: keep the database on a separate disk, take snapshots, and design the code so the database connection string can later point to a managed service — the first step to a two-tier split.

Use it when: prototypes, personal tools, learning — or tiny internal apps.
Avoid / be careful when: anything customer-facing that must grow, stay up or be secured properly.

Type 2 · Two-tier (client–server) architecture

Definition (say it in an interview): A two-tier architecture splits an application into a client that contains the user interface (and often the business logic) and a server — usually a database — that the client connects to directly over the network.

In plain words (no jargon): Each user’s computer runs the program, and all of them talk straight to one shared database.

Analogy: A grocery shop where every customer walks into the godown and picks items themselves: fine for a few regulars, chaos with hundreds — and every customer needs the godown key.

How it works internally, step by step

  1. Client. UI + business logic, installed on each machine.
  2. Connect. Direct database connection (SQL over TCP).
  3. Store. The database server keeps shared data.
  4. Update. New rules = new client version everywhere.
  5. Secure. Credentials live on every client — the weak point.

Words used above, in simple terms: client = the program the user runs · server = the shared machine/service that answers clients · connection pool = reused database connections

Use it when: small internal apps with a few trusted users on a private network.
Avoid / be careful when: clients run on the internet or untrusted devices — never expose a database directly to them.

Type 3 · Three-tier architecture

Definition (say it in an interview): A three-tier architecture separates an application into a presentation tier (user interface), an application (logic) tier (business rules and processing) and a data tier (databases and storage), each running on its own infrastructure, communicating only with the adjacent tier, and scaled, secured and deployed independently.

In plain words (no jargon): Three separate layers: the screens users see, the brain that does the work, and the store where data is kept — each on its own machines.

Analogy: A restaurant: the dining hall and waiters (presentation), the kitchen (application) and the store room (data). Customers never walk into the store room.

How it works internally, step by step

  1. Presentation. Static content via CDN; dynamic pages via web servers or a SPA.
  2. Application. Stateless API servers or functions; sessions in a cache/DB.
  3. Data. Managed database, cache and object storage.
  4. Connect. Each tier calls only the next one (LB, private DNS).
  5. Scale/secure per tier. Different subnets, firewall rules, scaling policies and teams.

Words used above, in simple terms: presentation tier = the part users see · application tier = where business rules run · data tier = where data is stored · stateless = keeps no user data between requests

Products and cloud services

For the experienced — did you know? Keep the app tier stateless: store sessions in Redis/DynamoDB, not in server memory. Otherwise the load balancer needs sticky sessions, scale-in logs users out and an instance failure loses carts.

Use it when: almost any web or mobile application — it is the default cloud design.
Avoid / be careful when: you put business rules in the front end or let the presentation tier query the database directly.

Type 4 · N-tier architecture

Definition (say it in an interview): An n-tier architecture extends the three-tier model with additional specialised tiers — such as caching, messaging/queues with background workers, search, content delivery and analytics — each running and scaling independently.

In plain words (no jargon): The three-tier design plus extra specialist layers — like a fast memory store, a to-do queue for slow jobs, and a search engine.

Analogy: A big hotel: reception, kitchen and store room — plus a laundry, a bakery and a delivery desk, each with its own staff.

How it works internally, step by step

  1. Identify the bottleneck. Repeated reads? slow jobs? full-text search?
  2. Add a tier. Cache, queue+workers, search, CDN.
  3. Define contracts. APIs or messages between tiers.
  4. Scale separately. Each tier with its own metrics.
  5. Observe. Distributed tracing across tiers.

Words used above, in simple terms: cache = fast memory copy of frequently read data · worker = a process that takes jobs from a queue · asynchronous = done later, not while the user waits · distributed tracing = following one request across many services

Use it when: one tier is doing work it is bad at (search in SQL, slow jobs in requests, repeated reads).
Avoid / be careful when: you add tiers before you need them — each one adds latency, cost and operations.

Type 5 · Serverless three-tier

Definition (say it in an interview): A serverless three-tier architecture implements the same three tiers with fully managed, per-request services: a static front end in object storage behind a CDN, an application tier of API gateway plus functions or serverless containers, and a serverless or autoscaling data tier — with no servers to provision or patch.

In plain words (no jargon): The same three layers, but every layer is rented per use from the cloud — no servers to manage at all.

Analogy: A cloud kitchen on an aggregator app: no dining hall, no permanent kitchen staff — space and cooks are paid per order.

How it works internally, step by step

  1. Build front end. SPA files uploaded to a bucket; CDN in front.
  2. Expose API. API Gateway routes to functions.
  3. Store data. Serverless DB with on-demand capacity.
  4. Authenticate. Cognito / Entra External ID / Identity Platform tokens.
  5. Scale. Each tier scales per request automatically.

Words used above, in simple terms: SPA = single-page application — the browser runs the UI · API gateway = a managed front door for APIs · on-demand capacity = pay per request, no sizing

Use it when: spiky or unpredictable traffic, small teams, new products.
Avoid / be careful when: steady very high load (VMs/containers with commitments may be cheaper) or long-running connections.

Type 6 · Static front end + API (SPA / JAMstack)

Definition (say it in an interview): A static front end with APIs (single-page application or JAMstack) delivers the presentation tier as pre-built static files — HTML, JavaScript, CSS — from object storage and a CDN, while all dynamic behaviour comes from the browser calling back-end APIs; there are no web servers in the presentation tier.

In plain words (no jargon): The website is a set of ready-made files delivered by a fast worldwide network; anything live (like today’s menu or your cart) is fetched separately from the server.

Analogy: A printed menu card handed out everywhere (static), with a phone number to call for today’s specials (API).

How it works internally, step by step

  1. Build. A framework (React, Next.js export, Hugo) creates static files.
  2. Upload. To a bucket/static host in the pipeline.
  3. Cache. CDN caches files worldwide; versioned file names.
  4. Call APIs. Browser JavaScript calls the API tier with tokens.
  5. Invalidate. New deploy → CDN cache invalidation or new file names.

Words used above, in simple terms: static file = a file that is the same for every visitor · JAMstack = JavaScript, APIs and Markup — pre-built front ends · cache invalidation = telling the CDN to fetch a new version

Type 7 · Tier isolation (network and identity)

Definition (say it in an interview): Tier isolation enforces the separation between tiers with infrastructure: separate subnets (public, private, isolated), firewall rules that allow each tier to be reached only from the previous tier, separate least-privilege identities per tier, and no direct internet path to the data tier.

In plain words (no jargon): Putting walls between the layers: each layer may only talk to the one next to it, and the data layer is completely hidden from the internet.

Analogy: A bank branch: customers stay in the banking hall, cashiers work behind glass, and the vault opens only for the manager with two keys.

How it works internally, step by step

  1. Subnets. Public (LB), private (app), isolated (DB, no NAT route).
  2. Firewall chain. SG/NSG rules reference the previous tier’s group or service account.
  3. Identity. Separate roles; data access only from the app role.
  4. Private access. Endpoints for S3/KMS so the app tier needs no internet.
  5. Monitor. Flow logs show any unexpected cross-tier traffic.

Words used above, in simple terms: isolated subnet = a subnet with no route to or from the internet · defence in depth = several protective layers · managed identity = an automatic identity for an Azure resource

6 Explained part by part

Six ideas that make tiers work

Layer vs tier

What it is: Layer = logical code organisation; tier = separately deployed physical/runtime unit.

Why it exists: Interview favourite: a 3-layer app can still be 1-tier.

Where it is used: MVC layers inside one server vs three tiers on three subnets.

Load balancer

What it is: Front door of the presentation or app tier.

Why it exists: Spreads load, checks health.

Where it is used: ALB, Application Gateway, Cloud LB.

Session store

What it is: Where user sessions live outside servers.

Why it exists: Keeps the app tier stateless.

Where it is used: Redis, DynamoDB, Cosmos DB, Firestore.

Connection pool / proxy

What it is: Reuses database connections.

Why it exists: Protects the data tier from connection storms.

Where it is used: RDS Proxy, PgBouncer, Cloud SQL connector.

API contract

What it is: The agreed request/response format between tiers.

Why it exists: Lets tiers change independently.

Where it is used: OpenAPI specs, versioned APIs.

Isolated subnet

What it is: Subnet with no internet route.

Why it exists: Home of the data tier.

Where it is used: DB subnets in every VPC design.

Myth vs reality: things many websites still say

  • Myth: Layers and tiers are the same.
    Reality: Layers are code; tiers are deployment.
    Proof: Deep dive.
  • Myth: More tiers is always better.
    Reality: Each tier adds latency and operations.
    Proof: Type 4.
  • Myth: Serverless has no tiers.
    Reality: It has the same three tiers, managed.
    Proof: Type 5.
7 Deep dive

Layers vs tiers, latency budget, 12-factor apps

Layers vs tiers (often confused)

Layers are how code is organised (presentation layer, business layer, data-access layer — e.g. MVC). Tiers are where parts run. A Django app with three layers on one VM is three-layer, one-tier. Splitting the database onto RDS makes it two-tier; adding a separate API service makes it three-tier.

Latency budget across tiers

HopTypical time
Browser → CDN edge (India)10–30 ms
Edge → load balancer (same Region)5–20 ms
LB → app (same AZ)< 1 ms
App → cache≈ 0.5 ms
App → database query2–20 ms
App → another Region20–60 ms

Every tier adds hops; keep chatty calls inside one AZ, cache aggressively and avoid cross-Region calls in the request path.

The 12-factor app

The 12-factor principles (config in environment, stateless processes, backing services as attached resources, disposable processes…) describe how to write app-tier code that scales cleanly in any cloud tier design.

  2. 1 · Presentation tier: a static website

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → Create bucket tiffingo-web-<yourname> (Mumbai). Untick Block all public access for this lab bucket only and acknowledge.
    2. Upload an index.html. Properties → Static website hosting → Enable, index document index.html → Save changes.
    3. Permissions → Bucket policy: allow s3:GetObject on arn:aws:s3:::BUCKET/* for Principal * → open the Bucket website endpoint.

    CLI way — the same thing with commands

    W=tiffingo-web-$RANDOM$RANDOM
echo '<!doctype html><title>TiffinGo</title><h1>TiffinGo menu</h1><p>Today: thali ₹249</p>' > index.html
aws s3 mb s3://$W --region ap-south-1
aws s3api put-public-access-block --bucket $W --public-access-block-configuration BlockPublicPolicy=false,RestrictPublicBuckets=false,BlockPublicAcls=true,IgnorePublicAcls=true
aws s3api put-bucket-policy --bucket $W --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":\"*\",\"Action\":\"s3:GetObject\",\"Resource\":\"arn:aws:s3:::$W/*\"}]}"
aws s3 website s3://$W --index-document index.html
aws s3 cp index.html s3://$W/ --content-type text/html
curl http://$W.s3-website.ap-south-1.amazonaws.com

    You should see: your HTML from the s3-website endpoint. In production keep the bucket private and serve it through CloudFront with Origin Access Control instead (HTTPS).

    UI way — Azure portal

    You should see: an HTTPS URL like https://tiffingo1234.z29.web.core.windows.net/ showing your page.

    UI way — Google Cloud console

  3. 2 · Data tier: a serverless table

    Pick your cloud.

    UI way — AWS Management Console

    1. DynamoDB → Create table → name tiffingo-menu, partition key dish (String), On-demand capacity → Create table.
    2. Explore items → Create item → dish = thali, add attribute price (Number) = 249 → Create item.

    CLI way — the same thing with commands

  --key-schema AttributeName=dish,KeyType=HASH --billing-mode PAY_PER_REQUEST

    You should see: one item with dish thali and price 249. On-demand tables cost nothing when idle (pay per request; 25 GB storage free tier).

    You should see: one entity with PartitionKey pune, RowKey thali, price 249.

    The data tier is a managed service — no server, no OS, nothing reachable except through its API and permissions.

  4. 3 · Application tier: an HTTPS API

    Pick your cloud.

    UI way — AWS Management Console

    1. Lambda → Create function → Author from scratch → name tiffingo-menu-api, runtime Python 3.12 → Create function.
    2. Paste the code on the right into lambda_function.py → Deploy. Configuration → Permissions → open the role → Add permissions → AmazonDynamoDBReadOnlyAccess.
    3. Configuration → Function URL → Create function URL → auth type NONE → Save → open the URL.

    CLI way — the same thing with commands

    cat > lambda_function.py <<'EOF'
import json, boto3
table = boto3.resource('dynamodb').Table('tiffingo-menu')
def lambda_handler(event, context):
    items = table.scan()['Items']
    return {'statusCode': 200, 'headers': {'Content-Type': 'application/json'}, 'body': json.dumps(items, default=str)}
EOF
zip fn.zip lambda_function.py
aws iam create-role --role-name tiffingo-menu-role --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"lambda.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name tiffingo-menu-role --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
aws iam attach-role-policy --role-name tiffingo-menu-role --policy-arn arn:aws:iam::aws:policy/AmazonDynamoDBReadOnlyAccess
sleep 15
ACCT=$(aws sts get-caller-identity --query Account --output text)
aws lambda create-function --function-name tiffingo-menu-api --runtime python3.12 --handler lambda_function.lambda_handler \
  --zip-file fileb://fn.zip --role arn:aws:iam::$ACCT:role/tiffingo-menu-role
aws lambda wait function-active --function-name tiffingo-menu-api
URL=$(aws lambda create-function-url-config --function-name tiffingo-menu-api --auth-type NONE --query FunctionUrl --output text)
aws lambda add-permission --function-name tiffingo-menu-api --statement-id url --action lambda:InvokeFunctionUrl \
  --principal '*' --function-url-auth-type NONE
aws lambda add-permission --function-name tiffingo-menu-api --statement-id invoke --action lambda:InvokeFunction --principal '*'
curl $URL

    You should see: [{"dish": "thali", "price": "249"}] — read live from the data tier. A complete three-tier app: S3 site → Lambda API → DynamoDB.

    UI way — Azure portal

    1. Function App → Create → Flex Consumption → name tiffingo-api-<n>, Python 3.12, Central India, storage account from step 1 → Review + create.
    2. In Cloud Shell create the code with Core Tools (commands on the right) and publish.
    3. Open https://APP.azurewebsites.net/api/menu.

    CLI way — the same thing with commands

    APP=tiffingo-api-$RANDOM
az functionapp create --resource-group rg-tiffingo --name $APP --storage-account $SA \
  --flexconsumption-location centralindia --runtime python --runtime-version 3.12
func init tiffingo-api --python && cd tiffingo-api
func new --name menu --template "HTTP trigger" --authlevel anonymous
func azure functionapp publish $APP
curl "https://$APP.azurewebsites.net/api/menu?name=TiffinGo"

    You should see: “Hello, TiffinGo. This HTTP triggered function executed successfully.” Reading the table needs the azure-data-tables library and an app setting — the same idea as the AWS code.

    UI way — Google Cloud console

    1. Cloud Run → Write a function → name tiffingo-menu-api, asia-south1, Python 3.12, Allow public access.
    2. Replace main.py with the code on the right, entry point menu → Save and redeploy → open the URL.

    CLI way — the same thing with commands

    mkdir menu && cd menu
cat > main.py <<'EOF'
import functions_framework, json
@functions_framework.http
def menu(request):
    return (json.dumps([{'dish': 'thali', 'price': 249}]), 200, {'Content-Type': 'application/json'})
EOF
echo 'functions-framework==3.*' > requirements.txt
gcloud functions deploy tiffingo-menu-api --gen2 --region=asia-south1 --runtime=python312 \
  --source=. --entry-point=menu --trigger-http --allow-unauthenticated
curl $(gcloud functions describe tiffingo-menu-api --region=asia-south1 --format='value(url)')

    You should see: [{"dish": "thali", "price": 249}]. Reading Firestore needs the google-cloud-firestore library — same pattern.

    Three tiers, three services, zero servers to patch: static site → function → serverless table.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Database reachable from the internet.Easier to connect from a laptop.Isolated subnet; connect via bastion/Session Manager or VPN.
Business logic in the front end.Faster to build.Rules in the app tier; the browser is untrusted.
Sessions stored in app server memory.Framework default.External session store; stateless app tier.
Public S3 website buckets in production.Tutorial shortcut.Private bucket + CloudFront OAC + HTTPS.
Too many tiers too early.Copying big companies.Add tiers when a bottleneck appears.
Functions opening a new DB connection per request.Simple code.Connection reuse, RDS Proxy, or serverless databases.
