1 The story

Learn it once, use it three times

Before you start: 10.1 and Module 6.

🤔 Kabir learned AWS. His new client runs on Azure, and his friend’s start-up uses Google Cloud. Does he have to learn everything again?

No. Most cloud services come in matching families: VMs, Kubernetes, functions, object storage, managed SQL, NoSQL and data warehouses exist on all three under different names. The skill is knowing the mapping — and the differences that matter (limits, pricing units, defaults). This lesson compares seven service families one by one, animates the same web app built on three clouds, and on your own accounts you benchmark object storage, compare managed databases and inspect serverless runtimes and limits.

  • The translation table every multi-cloud engineer keeps in their head.
  • Where “the same” services really differ: limits, defaults and pricing units.
  • Why Kubernetes control planes are priced differently on each cloud.

Kabir had spent a year learning AWS. A new consulting client ran on Azure and a friend’s start-up on Google Cloud. He worried he would have to start from zero.

K> Sir, Azure has “resource groups”, Google has “projects”. My AWS notes are useless. A> Your notes are fine. A VM is a VM; object storage is object storage. Same file, three buckets; same database engine, three managed services. Let’s compare family by family.
2 Definition

Comparing cloud web services

Formal definition (write this in exams)

Comparing cloud web services means mapping equivalent services across providers — compute, containers, functions, storage, databases, analytics, messaging and AI — and evaluating their real differences in limits and quotas, defaults, performance, availability SLAs, Regional availability, pricing units and APIs, so that designs and skills can be transferred and the best service chosen for each need.

In simple words

Most cloud services exist on every major cloud with different names; compare their limits, prices and defaults to choose well.

Say it in an interview

30-second answer you can speak:

  • “S3, Blob Storage and Cloud Storage are equivalent object stores; Lambda, Azure Functions and Cloud Run functions are FaaS; DynamoDB, Cosmos DB and Firestore are NoSQL — but limits, consistency options and pricing units differ.”
  • “I compare services by limits, pricing unit, defaults, SLA and Region availability, then run a small test.”

Type 1 · Virtual machines

Definition (say it in an interview): All three providers offer virtual machines in comparable families (general purpose, burstable, compute-, memory-, storage-optimised, GPU) on Intel, AMD and their own ARM chips (AWS Graviton, Azure Cobalt, Google Axion), with network block storage, per-second billing (with short minimums) and commitment and spot discounts.

In plain words (no jargon): Rented virtual servers — nearly the same on every cloud.

Analogy: Renting the same model of car from three agencies: same seats and engine, different contract terms and loyalty schemes.

How it works internally, step by step

  1. Family. Purpose letter/series.
  2. Size. vCPU, RAM.
  3. Image. OS image.
  4. Disk. Network block storage.
  5. Discount. Savings Plans / reservations / CUDs / Spot.

Words used above, in simple terms: ARM instance = VM on ARM chips — usually cheaper · sustained use discount = Google’s automatic discount on some families · spot VM = cheap interruptible capacity

Use it when: you need OS control — the family is nearly identical everywhere.
Avoid / be careful when: you compare names instead of vCPU/RAM/generation/Region.

Type 2 · Managed Kubernetes

Definition (say it in an interview): Managed Kubernetes services — Amazon EKS, Azure Kubernetes Service and Google Kubernetes Engine — run conformant Kubernetes control planes for you and integrate with each cloud’s networking, load balancers, storage and identity; they differ in control-plane pricing, upgrade cadence, node automation (GKE Autopilot, EKS Auto Mode/Fargate, AKS Automatic) and default networking.

In plain words (no jargon): Kubernetes run for you by each cloud — the same Kubernetes, with different extras.

Analogy: Three franchises of the same restaurant chain: the recipes (Kubernetes) are identical, the building, staff contracts and delivery partners are local.

How it works internally, step by step

  1. Create. Cluster + node pool.
  2. Identity. IRSA/Pod Identity, Workload ID.
  3. Ingress. Cloud load balancer controller.
  4. Storage. CSI drivers.
  5. Upgrade. Release channels.

Words used above, in simple terms: control plane = Kubernetes API server and scheduler · node pool = group of worker VMs · release channel = automatic upgrade track

Use it when: you already use Kubernetes or need portability across clouds.
Avoid / be careful when: a simpler serverless container service (Cloud Run, Container Apps, ECS) would do.

Type 3 · Functions (FaaS)

Definition (say it in an interview): Function services — AWS Lambda, Azure Functions and Google Cloud Run functions — run event-triggered code without servers, billed per invocation and compute time with monthly free grants; they differ in maximum run time, memory, triggers, hosting plans (Azure Consumption, Flex Consumption, Premium) and how they relate to containers (Cloud Run functions run on Cloud Run).

In plain words (no jargon): Small pieces of code that run only when something happens — each cloud has slightly different limits.

Analogy: Three taxi apps: you only pay for rides, but the maximum trip length and surge rules differ.

How it works internally, step by step

  1. Trigger. Event source.
  2. Runtime. Python, Node, Java, .NET…
  3. Limits. Time, memory, payload.
  4. Scale. Concurrency controls.
  5. Bill. Requests + GB-seconds.

Words used above, in simple terms: GB-second = memory × duration billing unit · cold start = delay when a new instance starts · hosting plan = Azure Functions pricing/limits option

Avoid / be careful when: long-running or constantly busy work — containers or VMs are cheaper.

Type 4 · Object storage

Definition (say it in an interview): Object storage — Amazon S3, Azure Blob Storage and Google Cloud Storage — stores unlimited objects in buckets/containers with HTTP APIs, 11-nines durability designs, storage tiers from hot to archive, lifecycle rules, versioning and private-by-default access; differences include Azure’s extra storage-account level, tier names and minimum storage durations, request pricing and redundancy options.

In plain words (no jargon): Online storage for files of any size — all clouds offer it, with different tier names.

Analogy: Three godown companies: all store your boxes safely and charge by space and handling, but their cold-storage rules and paperwork differ.

How it works internally, step by step

  1. Create. Bucket / storage account + container.
  2. Upload. API, CLI, SDK.
  3. Protect. Private, encryption, versioning.
  4. Tier. Lifecycle rules.
  5. Serve. Signed URLs, CDN.

Words used above, in simple terms: storage account = Azure’s top-level storage resource that holds containers · minimum storage duration = billed minimum time for cold tiers · redundancy = how many copies, where (LRS, ZRS, GRS…)

Type 5 · Managed relational databases

Definition (say it in an interview): Managed relational databases — Amazon RDS and Aurora, Azure SQL Database/Managed Instance and Azure Database for PostgreSQL/MySQL, Google Cloud SQL, AlloyDB and Spanner — run standard SQL engines with provider-managed patching, backups and high availability; they differ in supported engines, high-availability architecture, storage design (e.g. Aurora and AlloyDB’s separated storage), global options (Spanner) and pricing.

In plain words (no jargon): Databases using normal SQL, run for you by the cloud — the same SQL on every cloud.

Analogy: Three hospitals with the same medicines: the treatment (SQL) is the same, but rooms, specialists and billing differ.

How it works internally, step by step

  1. Engine + version. Match your app.
  2. Size. vCPU/RAM, storage.
  3. HA. Multi-AZ / zone-redundant / regional.
  4. Backups. PITR retention.
  5. Access. Private networking, IAM auth.

Words used above, in simple terms: PITR = point-in-time recovery · read replica = copy for read traffic · Multi-AZ = standby in another zone

Type 6 · NoSQL databases

Definition (say it in an interview): Managed NoSQL databases — Amazon DynamoDB, Azure Cosmos DB and Google Firestore/Bigtable — store key-value, document or wide-column data with horizontal scaling and millisecond latency; they differ in data model, query capability, consistency options (DynamoDB strong/eventual reads, Cosmos DB five consistency levels, Firestore strong), multi-Region writes and pricing units (capacity units, request units, operations).

In plain words (no jargon): Very fast databases that look up data by key and grow automatically — each cloud has its own.

Analogy: Locker rooms with numbered lockers: you can fetch any locker instantly by number, but searching for “all red bags” is slow unless you planned an index.

How it works internally, step by step

  1. Access patterns. Design keys first.
  2. Partition key. Spread load.
  3. Indexes. Secondary indexes.
  4. Capacity. On-demand vs provisioned.
  5. Replication. Global tables / multi-region.

Words used above, in simple terms: partition key = key that decides where data is stored · RU = Cosmos DB request unit · global table = multi-Region replicated DynamoDB table

Type 7 · Data warehouses

Definition (say it in an interview): Cloud data warehouses — Amazon Redshift (provisioned and Serverless), Microsoft Fabric Warehouse (successor path for Synapse dedicated pools) and Google BigQuery — run analytical SQL on columnar storage at petabyte scale and integrate with data lakes; their main differences are architecture (clusters vs serverless), pricing units (node-hours/RPU-hours, capacity units, bytes scanned or slot reservations) and ecosystem integration.

In plain words (no jargon): Huge SQL databases for analysing data — each cloud charges in a different way.

Analogy: Three printing presses for very large newspapers: all print fast, but one charges per hour of press time and another per page printed.

How it works internally, step by step

  1. Ingest. Batch/stream.
  2. Model. Star schemas, partitions.
  3. Query. SQL, BI tools.
  4. Optimise. Partition/cluster, materialised views.
  5. Control cost. Quotas, reservations.

Words used above, in simple terms: columnar = stores data by column for fast scans · slot = BigQuery unit of compute capacity · RPU = Redshift Serverless processing unit

6 Explained part by part

Six things to compare for any service

Limits and quotas

What it is: Max sizes, durations, rates.

Why it exists: Decide whether a design fits.

Where it is used: Function timeouts, object sizes.

Pricing units

What it is: What you are billed for.

Why it exists: Same workload, different bills.

Where it is used: Requests, GB-s, RU/s, TiB scanned.

Defaults

What it is: What is on/off out of the box.

Why it exists: Security and cost surprises.

Where it is used: Private storage, encryption, public IPs.

SLAs

What it is: Promised availability.

Why it exists: Design for the real number.

Where it is used: Zone vs Region SLAs (5.4).

APIs and SDKs

What it is: How code talks to the service.

Why it exists: Portability and lock-in.

Where it is used: S3 API widely copied; NoSQL APIs differ.

Regional availability

What it is: Is the service in your Region?

Why it exists: Residency and latency.

Where it is used: Check India Regions per service.

Myth vs reality: things many websites still say

  • Myth: Equivalent services behave identically.
    Reality: Limits, defaults and pricing differ.
    Proof: Types.
  • Myth: NoSQL is easy to move.
    Reality: APIs and models differ.
    Proof: Type 6.
  • Myth: Cheapest list price wins.
    Reality: Pricing units and usage decide.
    Proof: Type 7.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. Side-by-side tests: storage speed, managed PostgreSQL options and serverless limits. Only the storage benchmark creates resources (a few paise).

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Benchmark object storage from your own Cloud Shell

    Pick your cloud.

    UI way — AWS Management Console

    1. Create a bucket in Mumbai → Upload a test file → download it; note the time.

    CLI way — the same thing with commands

    head -c 50M /dev/urandom > bench-50mb.bin
B=tiffingo-bench-$RANDOM; aws s3 mb s3://$B --region ap-south-1
/usr/bin/time -f 'upload %e s' aws s3 cp bench-50mb.bin s3://$B/ --only-show-errors
/usr/bin/time -f 'download %e s' aws s3 cp s3://$B/bench-50mb.bin /tmp/b.bin --only-show-errors

    You should see: two timings in seconds. CloudShell runs in the console’s Region, so this measures intra-Region throughput; from your laptop it measures your internet link.

    UI way — Azure portal

    1. Create a storage account (Central India) → container bench → Upload → download.

    CLI way — the same thing with commands

    head -c 50M /dev/urandom > bench-50mb.bin
az group create -n rg-cmp -l centralindia >/dev/null
SA=tgbench$RANDOM; az storage account create -n $SA -g rg-cmp -l centralindia --sku Standard_LRS >/dev/null
KEY=$(az storage account keys list -n $SA -g rg-cmp --query [0].value -o tsv)
az storage container create --account-name $SA --account-key $KEY -n bench >/dev/null
/usr/bin/time -f 'upload %e s' az storage blob upload --account-name $SA --account-key $KEY -c bench -f bench-50mb.bin -n bench-50mb.bin --only-show-errors >/dev/null
/usr/bin/time -f 'download %e s' az storage blob download --account-name $SA --account-key $KEY -c bench -n bench-50mb.bin -f /tmp/b.bin --only-show-errors >/dev/null

    You should see: upload and download timings. Azure Cloud Shell may run in a different Region from your storage account — note where it is (echo $ACC_LOCATION).

    UI way — Google Cloud console

    1. Create a bucket in asia-south1 → Upload files → download.

    CLI way — the same thing with commands

    head -c 50M /dev/urandom > bench-50mb.bin
B=tiffingo-bench-$RANDOM; gcloud storage buckets create gs://$B --location=asia-south1 --quiet
/usr/bin/time -f 'upload %e s' gcloud storage cp bench-50mb.bin gs://$B/ --no-user-output-enabled
/usr/bin/time -f 'download %e s' gcloud storage cp gs://$B/bench-50mb.bin /tmp/b.bin --no-user-output-enabled

    You should see: upload and download timings. Cloud Shell VMs are in a Region near you but not necessarily Mumbai.

    Benchmarks only compare fairly when the client location is the same — write down where each test ran.

  3. 2 · Compare managed PostgreSQL offerings (read-only)

    Pick your cloud.

    UI way — AWS Management Console

    1. RDS → Create database → PostgreSQL → look at engine versions, instance classes, Multi-AZ options and the Free tier template — then cancel.

    CLI way — the same thing with commands

    aws rds describe-db-engine-versions --engine postgres --region ap-south-1 --query 'DBEngineVersions[-5:].EngineVersion' --output text
aws rds describe-orderable-db-instance-options --engine postgres --db-instance-class db.t4g.micro --region ap-south-1 --query 'OrderableDBInstanceOptions[0].[DBInstanceClass,MultiAZCapable,StorageType]' --output text

    You should see: the latest PostgreSQL versions and that db.t4g.micro supports Multi-AZ with gp-class storage.

    UI way — Azure portal

    1. Azure Database for PostgreSQL flexible servers → Create → look at versions, compute tiers (Burstable, General Purpose, Memory Optimized) and zone-redundant HA — then cancel.

    CLI way — the same thing with commands

    az postgres flexible-server list-skus --location centralindia --query "[0].supportedServerEditions[].{tier:name,skus:length(supportedServerSkus)}" -o table
az postgres flexible-server list-skus --location centralindia --query "[0].supportedServerVersions[].name" -o tsv | tail -5

    You should see: tiers with SKU counts and the supported PostgreSQL versions in Central India.

    UI way — Google Cloud console

    1. SQL → Create instance → PostgreSQL → look at versions, editions (Enterprise / Enterprise Plus) and multi-zone availability — then cancel.

    CLI way — the same thing with commands

    gcloud sql tiers list --format="table(tier,RAM,DiskQuota)" | head -8
gcloud sql instances create x --database-version=POSTGRES_99 --region=asia-south1 2>&1 | grep -oE "POSTGRES_[0-9]+" | grep -v _99 | sort -t_ -k2 -n -u | tail -5

    You should see: machine tiers with RAM, and (from the deliberate error message) the list of valid PostgreSQL versions. Nothing is created.

    Same engine, three managed wrappers: compare versions, HA design and price — not the SQL.

  4. 3 · Inspect serverless runtimes and limits

    Pick your cloud.

    UI way — AWS Management Console

    1. Lambda → Dashboard shows account concurrency; Create function lists runtimes. Configuration shows timeout up to 15 minutes and memory up to 10,240 MB.

    CLI way — the same thing with commands

    aws lambda get-account-settings --query 'AccountLimit.[ConcurrentExecutions,CodeSizeZipped,TotalCodeSize]' --output text

    You should see: your concurrent-execution limit (new accounts can be lower than the default 1,000) and code-size limits.

    UI way — Azure portal

    1. Function App → Create → compare hosting options (Flex Consumption, Premium, App Service) and their limits in the info boxes.

    CLI way — the same thing with commands

    az functionapp list-runtimes --os linux --query "[].{runtime:runtime,version:version}" -o table | head -12

    You should see: supported Linux runtimes and versions for Azure Functions.

    UI way — Google Cloud console

    1. Cloud Run → Write a function → runtime list; Container, Networking, Security → request timeout up to 3600 s.

    CLI way — the same thing with commands

    gcloud functions runtimes list --region=asia-south1 --format="table(name,stage)" | head -12

    You should see: available runtimes (python312, nodejs22 …) and their stage.

    Before porting a function, compare limits first — they decide whether code moves unchanged.

Clean up and cost check

AWS: aws s3 rb s3://$B --force. Azure: az group delete -n rg-cmp --yes --no-wait. Google Cloud: gcloud storage rm -r gs://$B. Delete bench-50mb.bin from each Cloud Shell.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Assuming same name = same behaviour.Translation tables hide details.Read limits, defaults and SLAs.
Porting functions without checking time limits.Lambda habits.Compare max duration, memory, payload.
Comparing warehouse list prices only.Different units.Model a real query workload.
Benchmarks from different locations.Convenience.Same client location for every test.
Ignoring Azure’s storage-account level.S3 mental model.Plan account → container → blob.
Expecting NoSQL to be portable.“It’s just JSON.”Treat NoSQL choice as long-term.
