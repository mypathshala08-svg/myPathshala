1 The story

Fast in Virginia, slow in Pune

Before you start: 1.1 What is cloud computing and 4.3 (VPC) help.

🤔 Why did TiffinGo’s app feel slow in Pune even though AWS is “in the cloud”?

Because the cloud is not a fog — it is real buildings in real cities. TiffinGo had launched in us-east-1 (Virginia), the console’s default. From a home connection in Maharashtra we measured a TCP connection to Virginia at 285 ms, to Mumbai at 55 ms — and to the Mumbai CloudFront edge (BOM78) in just 15 ms. 2 Definition

Regions, Availability Zones and edge locations

Formal definition (write this in exams)

A Region is a physical location in the world where a cloud provider clusters data centres; each Region is isolated from others and consists of multiple Availability Zones — one or more discrete data centres with redundant power, networking and connectivity, physically separated but linked by low-latency networks. Edge locations (points of presence) are separate sites in many cities that run latency-sensitive services such as content delivery and DNS close to end users.

In simple words

A Region is a city-area where the cloud has data centres; Availability Zones are separate buildings inside it so one failure does not stop you; edge locations are small sites in many cities that deliver content quickly.

Say it in an interview

30-second answer you can speak:

  • “AWS organises its infrastructure into Regions — isolated geographic areas — each with multiple Availability Zones, which are separate data centres with independent power and networking, connected by low-latency links. I deploy across at least two AZs for high availability and choose the Region by compliance, latency, service availability and cost.”
  • “Edge locations are separate points of presence in many cities that run CloudFront, Route 53 and Global Accelerator to serve users with low latency.”
  • “For example, from Maharashtra I measured about 55 ms to Mumbai and 285 ms to Virginia, and CloudFront served our static files from the Mumbai PoP BOM78 in 15 ms.”

Type 1 · Region

Definition (say it in an interview): A Region is a separate geographic area where a cloud provider operates a cluster of data centres, organised into multiple isolated Availability Zones; most resources are created in a specific Region, and data stays in that Region unless you explicitly move or replicate it.

In plain words (no jargon): A Region is a city-sized area where the cloud company has several data centres. You pick the Region when you create something, and your data stays there unless you copy it somewhere else.

Analogy: A country branch of a bank: the Mumbai branch keeps Mumbai accounts. Each branch is independent; moving money to another branch is a deliberate transfer.

How it works internally, step by step

  1. Pick a Region per resource. Console Region selector, --region in the CLI, or provider default.
  2. Independent control plane. Each Region has its own API endpoints (ec2.ap-south-1.amazonaws.com) and is isolated from others, so a failure in one Region does not spread.
  3. Data stays put. Objects, volumes and databases stay in the Region; copying to another Region is explicit (S3 replication, AMI copy, snapshots).
  4. Opt-in Regions. Regions launched after March 2019 (like Hyderabad) must be enabled per account before use.
  5. Prices differ. The same instance costs differently per Region; data transfer between Regions is billed.

Words used above, in simple terms: data residency = a rule that data must be stored in a particular country · endpoint = the web address of a service’s API in one Region · opt-in Region = a Region you must enable before using · DR = disaster recovery: a second site to recover in

For the experienced — did you know? Region counts disagree between sources: AWS’s infrastructure page lists 39 geographic Regions (Nov 2026), while the public ip-ranges.json we parsed in Lesson 1.1 contains 42 region codes — it also includes GovCloud, China and Regions that are announced or opt-in. Always say which list you mean.

Use it when: deciding where any workload and its data will live — always choose deliberately.
Avoid / be careful when: accepting the console’s default Region, or assuming every service and instance type exists in every Region.

Type 2 · Availability Zone (AZ)

Definition (say it in an interview): An Availability Zone is one or more discrete data centres within a Region, with redundant power, cooling and networking, physically separated from the other AZs of the Region but connected to them by high-bandwidth, low-latency links, so that applications can be designed to survive the failure of a single location.

In plain words (no jargon): Inside each Region there are several separate data-centre sites, a few kilometres apart, each with its own electricity and cooling. If one site has a problem, your app can keep running from another.

Analogy: Three separate kitchens of one restaurant chain in different parts of the same city: a fire or power cut in one kitchen does not stop the others, and they are close enough to deliver to the same customers quickly.

How it works internally, step by step

  1. Separate sites. Each AZ has independent power, cooling and network; AWS says AZs are a meaningful distance apart but within 100 km of each other.
  2. Fast links. AZs in a Region are joined by redundant fibre with single-digit-millisecond latency, so synchronous replication is practical.
  3. You place resources. Subnets, VMs and volumes live in one AZ; load balancers and Multi-AZ databases span several.
  4. Names are shuffled per account. ap-south-1a in your account may be a different physical AZ from ap-south-1a in mine; the AZ ID (aps1-az1) is the true, shared identifier.
  5. Fail over. Health checks detect a failed AZ and route traffic to healthy ones.

Words used above, in simple terms: subnet = a slice of a VPC’s addresses, always in one AZ · Multi-AZ = running a copy in a second AZ that takes over automatically · synchronous replication = every write is saved in both places before it is confirmed · AZ ID = the fixed identifier of a physical AZ, e.g. aps1-az1

For the experienced — did you know? Because AZ letters are mapped per account, two companies cannot coordinate “both use ap-south-1a” for low latency — share AZ IDs (aps1-az1) instead. Our lab shows ap-south-1b mapped to aps1-az3.

Use it when: any production workload — spread servers, load balancers and databases across at least two AZs.
Avoid / be careful when: you pin everything to one AZ “to save on data transfer”, or assume your “ap-south-1a” is the same physical place as another account’s “ap-south-1a”.

Type 3 · Edge location (point of presence)

Definition (say it in an interview): An edge location (point of presence, PoP) is a smaller site in a major city, separate from Regions, where the provider runs latency-sensitive global services — content caching (CDN), DNS, DDoS protection and network acceleration — so that users are served from a location close to them.

In plain words (no jargon): Small cloud sites in many cities keep copies of popular files (pictures, videos, web pages) so they reach you quickly from nearby, instead of travelling from a faraway data centre every time.

Analogy: A local delivery hub for an online store: popular items are stocked in a hub in your city, so they reach you in hours; rare items still come from the main warehouse.

How it works internally, step by step

  1. DNS steers the user. The CDN’s DNS returns the address of a nearby PoP.
  2. Check the cache. If the file is cached and fresh, it is returned at once (hit).
  3. Miss: ask upstream. If not, the PoP asks a regional edge cache, then the origin.
  4. Store with TTL. The response is cached for its time-to-live.
  5. Dynamic traffic. Uncacheable requests still enter the provider’s backbone at the edge, which is often faster than the public internet.
  6. Protect. DDoS protection and web-application firewalls run at the edge, far from your servers.

Words used above, in simple terms: CDN = content delivery network · PoP = point of presence: an edge site · origin = where the original content lives · cache hit / miss = found / not found in the cache · TTL = how long a cached copy stays valid

Use it when: serving images, video, downloads, websites and APIs to users spread over many cities; protecting against DDoS.
Avoid / be careful when: content changes every second or must never be cached (set cache rules carefully), or you expect to run your own VMs at an edge — edge locations run provider services only.

Type 4 · Local Zone

Definition (say it in an interview): A Local Zone is an extension of a Region placed in a large metropolitan area, providing selected services such as compute, block storage and load balancing close to end users for single-digit-millisecond latency, while connecting back to the parent Region for other services.

In plain words (no jargon): A small piece of a cloud Region placed inside a big city, so people in that city get very fast responses, while it stays connected to the main Region.

Analogy: A branch counter of your bank opened inside your office complex: you get quick service for common tasks; complex work is still done at the main branch.

How it works internally, step by step

  1. Opt in. Enable the Local Zone group for your account (EC2 settings or CLI).
  2. Extend the VPC. Create a subnet in the Local Zone (it appears as an extra AZ-like zone).
  3. Launch resources. Run supported instance types, EBS volumes, load balancers there.
  4. Traffic stays local. Users in the city connect to nearby infrastructure.
  5. Back to the Region. Other services (S3, DynamoDB…) are reached through the parent Region.

Words used above, in simple terms: parent Region = the Region a Local Zone belongs to · opt-in = switched off until you enable it · metro = a big city area

Avoid / be careful when: you need every AWS service — Local Zones offer only a subset; and they are usually a single zone, so design for failover to the Region.

Type 5 · Wavelength Zone

Definition (say it in an interview): A Wavelength Zone embeds cloud compute and storage inside a telecommunications provider’s 5G network, so traffic from mobile devices reaches the application without leaving the carrier network, giving ultra-low latency for mobile and connected-device applications.

In plain words (no jargon): Cloud servers placed inside a mobile company’s 5G network, so phones and devices connected to that network get extremely fast responses.

Analogy: A food stall set up inside a railway station: travellers do not even need to step out of the station to eat.

How it works internally, step by step

  1. Carrier hosts the zone. The telecom operator houses AWS infrastructure in its 5G network edge.
  2. Extend the VPC. Create a subnet in the Wavelength Zone and a carrier gateway.
  3. Device traffic stays in the network. Phones reach the app through the carrier network without internet hops.
  4. Region for the rest. Databases and other services stay in the parent Region.

Words used above, in simple terms: 5G = the fifth generation of mobile networks · carrier gateway = the connection between the zone and the mobile network · MEC = multi-access edge computing: compute inside telecom networks

A future TiffinGo feature — live AR menus on phones at a food festival — would benefit from processing inside the 5G network, if a Wavelength Zone exists with the local carrier.

For the experienced — did you know? A Wavelength subnet gets carrier IP addresses, not public internet IPs — devices on other networks may not reach it directly, which surprises teams that test from office Wi-Fi.

Use it when: connected cars, AR/VR on phones, live video analytics, industrial IoT over 5G.
Avoid / be careful when: users are not on the partner carrier’s 5G network — then there is no benefit.

Type 6 · Outposts (on-premises extension)

Definition (say it in an interview): AWS Outposts is a fully managed service that installs AWS-designed racks or servers in a customer’s own data centre or site, running AWS compute, storage and selected services locally with the same APIs, tools and console as the parent Region, which provides the control plane.

In plain words (no jargon): The cloud company puts its own computers inside your building. They work exactly like the cloud — same tools — but the data and processing stay in your premises.

Analogy: A bank installing its own ATM inside your office: the machine and its software belong to and are run by the bank, but it sits on your premises for convenience.

How it works internally, step by step

  1. Order. Choose a configuration; AWS delivers and installs the rack.
  2. Service link. The rack connects to its parent Region over your network or Direct Connect.
  3. Same APIs. Launch EC2/EBS on the Outpost from the normal console, selecting the Outpost subnet.
  4. AWS operates it. Hardware monitoring, patching and replacement are handled by AWS.
  5. Local data. Data on the Outpost stays on-premises; control-plane calls go to the Region.

Words used above, in simple terms: on-premises = in your own building or data centre · control plane = the management side: APIs, console · service link = the network connection back to the Region

7 Deep dive

Global vs regional vs zonal services, data-transfer costs, Azure and Google differences

Global vs regional vs zonal services

ScopeMeaningAWS examples
Globalone instance worldwideIAM, Route 53, CloudFront, Organizations
Regionallives in a Region, spread over its AZs automaticallyS3, DynamoDB, Lambda, SQS, VPC
Zonallives in one AZ — you must spread it yourselfEC2 instance, EBS volume, subnet

Data transfer: location costs money too

  • Data into AWS from the internet is free; data out to the internet is billed (the first 100 GB per month across services is free).
  • Traffic between AZs in a Region is billed in each direction (a small per-GB charge) — a reason chatty services are placed carefully, but never a reason to give up multi-AZ.
  • Traffic between Regions is billed per GB — replicate deliberately.
  • Edge delivery (CloudFront) often costs less per GB than serving directly from the Region.

Azure and Google: the same ideas, different words

  • Azure region pairs: most regions are paired with another in the same geography at least 300 miles away; platform updates roll out one region of a pair at a time, and one region per pair is prioritised for recovery in a large outage.
  • Azure availability zones: every zone-enabled region has at least three.
  • Google Cloud lists 43 regions and 130 zones (Nov 2026); a Google VPC is global — one network spans all regions, with regional subnets.

10 Hands-on

Do it yourself, step by step

Every step shows a UI way and a CLI way. Steps 1–2 work from any computer with a browser and curl. Steps 3–5 use the AWS console or CLI; CLI outputs marked “emulator” come from the moto AWS emulator. None of these steps costs money.

  1. 1 · Measure latency from your own location

    UI way — browser

    1. Open a browser and visit an online “AWS latency test” page that pings Region endpoints (many free ones exist), or use the CLI on the right.
    2. Note your three fastest Regions — they may not be the nearest on the map.

    CLI way — the same thing with commands

    for r in ap-south-1 ap-south-2 me-central-1 ap-southeast-1 us-east-1; do
  printf "%-15s " $r
  curl -s -o /dev/null -w "%{time_connect}\n" https://ec2.$r.amazonaws.com/
done
    == 1) TCP connect time from a home broadband connection in Maharashtra, India (median of 5, 10 Nov 2026) ap-south-1 55 ms ap-south-2 64 ms ap-southeast-1 70 ms me-central-1 42 ms eu-west-1 165 ms eu-central-1 162 ms us-east-1 285 ms us-west-2 293 ms sa-east-1 324 ms ap-southeast-2 402 ms
    Our surprise: UAE beat Mumbai from a Maharashtra ISP. Measure from where your users are.

  2. 2 · See which edge location serves you

    UI way — browser developer tools

    1. Open https://aws.amazon.com in Chrome/Edge → press F12 → Network tab → reload.
    2. Click the first request → Headers → Response Headers: find x-amz-cf-pop (e.g. BOM78) and x-cache.

    CLI way — the same thing with commands

    curl -sI https://d1.awsstatic.com/ | grep -i -E 'x-amz-cf-pop|x-cache|age'
    == 2) Which CloudFront edge served us? (HTTP response headers, from the same computer in India) https://aws.amazon.com/ x-cache: Miss from cloudfront x-amz-cf-pop: BOM78-P4 https://d1.awsstatic.com/ x-cache: Hit from cloudfront x-amz-cf-pop: BOM78-P9 age: 74627
    The first three letters are an airport code: BOM = Mumbai, DEL = Delhi, MAA = Chennai.

  3. 3 · List Regions and choose one

    UI way — AWS Management Console

    1. AWS Console → top-right Region selector (e.g. “N. Virginia”) → choose Asia Pacific (Mumbai) ap-south-1.
    2. At the bottom of the list, Manage Regions (or Account → AWS Regions) shows which opt-in Regions such as Asia Pacific (Hyderabad) are enabled.

    CLI way — the same thing with commands

    aws ec2 describe-regions --all-regions \
  --query 'Regions[].[RegionName,OptInStatus]' --output table
aws configure set region ap-south-1      # make Mumbai your CLI default
    Set the default once and you will never launch in Virginia by accident again.

  4. 4 · AZ names and AZ IDs

    UI way — AWS Management Console

    1. EC2 → Dashboard → panel Zones (or Settings → Zones): lists each zone’s name and Zone ID.
    2. Compare with a colleague’s account: the same name may show a different ID.

    CLI way — the same thing with commands

    aws ec2 describe-availability-zones --region ap-south-1 \
  --query 'AvailabilityZones[].[ZoneName,ZoneId,State]' --output table
    == 1) AZ names vs AZ IDs in Mumbai ------------------------------------------ | DescribeAvailabilityZones | +-------------+------------+-------------+ | ap-south-1a| aps1-az1 | available | | ap-south-1b| aps1-az3 | available | | ap-south-1c| aps1-az2 | available | +-------------+------------+-------------+
    Output from the moto emulator. Use Zone IDs when coordinating across accounts.

  5. 5 · Opt in to a Region or a Local Zone (look, do not necessarily enable)

    UI way — AWS Management Console

    1. Region: Account menu → AWS Regions → select Asia Pacific (Hyderabad) → Enable (takes minutes).
    2. Local Zone: EC2 → Settings → Zones → filter Local Zones → select a zone group → Manage → Enabled.

    CLI way — the same thing with commands

    aws account enable-region --region-name ap-south-2
aws account get-region-opt-status --region-name ap-south-2

aws ec2 describe-availability-zones --all-availability-zones --region ap-south-1 \
  --filters Name=zone-type,Values=local-zone --query 'AvailabilityZones[].[ZoneName,GroupName,OptInStatus]'
aws ec2 modify-availability-zone-group --region ap-south-1 --group-name <group-name> --opt-in-status opted-in
    Enabling is free; you pay only for resources you create there. Needs account-level permissions (not available on every learner account).

Clean up and cost check

Nothing to clean up — these steps only read information or change account settings. If you enabled a Region or Local Zone only for practice, you may disable it again from the same screen (or aws account disable-region).

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Launching in the console’s default Region (often N. Virginia).Nobody looked at the Region selector.Set your default Region in the console and in aws configure; check it before every launch.
Everything in one AZ “to keep it simple”.Default subnet choices, cost worries.Use at least two AZs for anything in production; the Region-level SLA requires it.
“My resource disappeared!”Looking at a different Region in the console.Resources are regional — switch the Region selector.
Assuming every service/instance type exists everywhere.New features launch Region by Region.Check the Regional Services List or describe-instance-type-offerings before designing.
Copying data between Regions without noticing the bill.Cross-Region replication and transfers are billed per GB.Replicate only what DR needs; watch Cost Explorer “data transfer”.
Choosing a Region only by map distance.Internet routes are not straight lines.Measure latency from real user locations (our UAE vs Mumbai surprise).
Thinking an edge location can run your VM.Confusing PoPs with Local Zones.Edges run provider services (CDN, DNS); use Local Zones for your own compute near a city.

Exam-style questions with explanations

1. Which statement about Availability Zones is correct?
  1. An AZ is a CloudFront cache
  2. ✔ An AZ is one or more isolated data centres within a Region
  3. An AZ spans several Regions
  4. Each account has one AZ

Why: AZs are isolated locations inside a Region with independent power and networking.

2. What is the main purpose of an edge location?
  1. Run RDS databases
  2. ✔ Cache and deliver content close to users (CloudFront), DNS
  3. Store EBS snapshots
  4. Host IAM

Why: Edges serve CloudFront, Route 53 and similar latency-sensitive global services.

3. A company must keep data in its own data centre but wants AWS APIs. Which service?
  1. Local Zones
  2. ✔ AWS Outposts
  3. Wavelength
  4. CloudFront

Why: Outposts runs AWS infrastructure on-premises.

4. Which factor should usually be checked FIRST when selecting a Region?
  1. Colour of the console
  2. ✔ Compliance / data residency requirements
  3. Number of AZs only
  4. Alphabetical order

Why: Legal requirements can rule Regions out entirely; then latency, services, price.

5. To achieve high availability for EC2, you should…
  1. use a bigger instance
  2. ✔ deploy across multiple Availability Zones
  3. use one AZ with backups
  4. use edge locations

Why: Multiple AZs protect against the failure of one location.

6. In Azure, which feature pairs regions at least 300 miles apart for disaster recovery?
  1. Availability sets
  2. ✔ Region pairs
  3. Resource groups
  4. Front Door

Why: Region pairs get sequential updates and prioritised recovery.

13 Mini project

Build something with what you learned

Mini project: choose and design TiffinGo’s Region strategy

Goal: Produce a one-page, evidence-based Region decision and a multi-AZ layout — the kind of document architects present.

Combines: This lesson + 4.3 (VPC) + 5.4 (SLAs) + 5.5 (pricing).

  1. Requirements: write TiffinGo’s constraints — users in Maharashtra, Delhi NCR and Bengaluru; payment data must stay in India; budget sensitive.
  2. Measure: run the latency script (practical step 1) from at least two cities (ask friends/colleagues), and record the medians.
  3. Check services: aws ec2 describe-instance-type-offerings --region ap-south-1 --filters Name=instance-type,Values=m7i.large and the same for ap-south-2; check that RDS and the services you need exist in both.
  4. Compare prices: look up the same instance’s On-Demand price in both Indian Regions (AWS Pricing Calculator).
  5. Decide: fill a scorecard (compliance, latency, services, price, DR) and pick primary + DR Regions.
  6. Design: draw a diagram: CloudFront → ALB in 2 AZs → app servers in 2 AZs → RDS Multi-AZ; S3 with cross-Region replication to the DR Region for backups.
  7. Estimate cost of the design in the AWS Pricing Calculator and attach the link.

You should see: A one-page decision with measured latency, a scorecard, a multi-AZ diagram and a cost estimate.
