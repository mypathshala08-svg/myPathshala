1 The story

Three days to set up a server

Before you start: 2.1 IaaS.

🤔 TiffinGo’s developer spent three days setting up a server — OS, Python, Nginx, SSL certificate, firewall, monitoring — before writing a single line of the new feedback app. Could those three days have been three minutes?

Yes, with Platform as a Service (PaaS): you bring the code, the platform brings the operating system, runtime, web server, load balancer, HTTPS, scaling and patching. PaaS is not one product but a family — app platforms, container platforms, managed databases (DBaaS), integration platforms (iPaaS), mobile back ends, data and AI platforms, and private PaaS you run yourself. This lesson explains each type, shows what happens between git push and a live URL, and you deploy a web app, read its logs and create a managed database on your own AWS, Azure or Google Cloud account.

2 Definition

What is PaaS?

Formal definition (write this in exams)

Platform as a Service (PaaS) is a cloud service model in which the provider delivers a complete development and runtime platform — operating system, language runtimes, middleware, databases and supporting services on managed infrastructure — so that customers deploy and manage their own applications and data without managing the underlying servers, storage, network or OS (NIST SP 800-145).

In simple words

You bring the code and data; the cloud gives you a ready-made place to run them, and looks after everything underneath.

Say it in an interview

30-second answer you can speak:

  • “PaaS gives a managed platform to deploy applications — the provider manages OS, runtime, scaling and patching; I manage code, configuration and data. Examples: Elastic Beanstalk, Azure App Service, App Engine, and managed databases like RDS.”
  • “PaaS types include application platforms, container platforms, DBaaS, iPaaS, mobile back ends, data and AI platforms, and private PaaS like OpenShift.”

Type 1 · Application PaaS (aPaaS)

Definition (say it in an interview): Application PaaS (aPaaS) runs web applications and APIs directly from source code in supported languages, with the provider managing the operating system, language runtime, web server, load balancing, TLS, scaling and patching; the customer manages the code, configuration and data.

In plain words (no jargon): You upload your website’s code; the cloud runs it for you, with everything underneath handled.

Analogy: A furnished paying-guest room with meals: you bring your clothes (code) and live there; the owner handles the building, cooking and repairs.

How it works internally, step by step

  1. Pick runtime. e.g. Python 3.12.
  2. Deploy. Source zip, git, or pipeline.
  3. Build. Buildpack installs dependencies.
  4. Run. Instances behind a managed LB with HTTPS.
  5. Operate. Scaling rules, slots/versions, logs.

Words used above, in simple terms: runtime = the language engine, e.g. Python 3.12 · buildpack = a script that turns source code into a runnable app · deployment slot = a second live copy for testing before swapping

For the experienced — did you know? Elastic Beanstalk is the transparent kind of PaaS: it creates EC2, an Auto Scaling group and a load balancer in your account, so you still see — and pay for — every resource; App Engine standard and App Service hide them.

Use it when: standard web apps and APIs in mainstream languages, where speed of delivery matters more than OS control.
Avoid / be careful when: you need custom OS packages, special networking or long-lived background processes the platform does not support.

Type 2 · Container-based PaaS

Definition (say it in an interview): Container-based PaaS runs containerised applications without the customer operating a cluster: you supply a container image (or source the platform builds into one), and the platform provides scaling, revisions, HTTPS endpoints and managed infrastructure — combining PaaS simplicity with container flexibility.

In plain words (no jargon): Like app PaaS, but you can bring any packed app (a container), so any language or library works.

Analogy: A food-truck park with power and water: bring any truck (container) with any kitchen inside; the park provides space, electricity and customers.

How it works internally, step by step

  1. Package. Dockerfile or buildpacks → image.
  2. Deploy. Service with CPU, memory, port, env vars.
  3. Revisions. Each deploy is a revision; split traffic between them.
  4. Scale. Requests/concurrency drive instances, often to zero.
  5. Integrate. Secrets, VPC access, custom domains.

Words used above, in simple terms: container image = a packaged app with its libraries · revision = one deployed version of a service · traffic splitting = sending a share of users to a new version

Type 3 · Database PaaS (DBaaS)

Definition (say it in an interview): Database as a Service (DBaaS) provides managed database engines — relational and NoSQL — where the provider handles provisioning, OS and engine patching, backups and point-in-time restore, replication and failover, and monitoring, while the customer manages schemas, queries, indexes, access and data.

In plain words (no jargon): A database the cloud company installs, backs up, updates and keeps running for you. You just create tables and store data.

Analogy: A bank locker: the bank guards the vault, cameras and backups; you decide what to keep inside and who gets a key.

How it works internally, step by step

  1. Provision. Engine, version, size, storage, network.
  2. Secure. Private networking, IAM/SQL users, encryption.
  3. Protect. Automated backups, point-in-time restore, Multi-AZ/HA.
  4. Maintain. Patching in maintenance windows.
  5. Scale. Bigger instance, read replicas, serverless capacity.

Words used above, in simple terms: DBaaS = database as a service · point-in-time restore = restore to any second within the backup window · read replica = a read-only copy to share load · maintenance window = the time slot for patches

Type 4 · Integration PaaS (iPaaS)

Definition (say it in an interview): Integration Platform as a Service (iPaaS) is a cloud service for building and running integration flows between applications, data sources and APIs — on-premises and SaaS — using prebuilt connectors, visual workflow designers, data mapping and managed execution.

In plain words (no jargon): A cloud tool that connects different apps and moves data between them automatically, mostly by drag and drop.

Analogy: A professional courier and translator in one: picks up a parcel from one office, repacks and labels it the way the next office wants, and delivers it.

How it works internally, step by step

  1. Trigger. Schedule, webhook, or event in a connected app.
  2. Connectors. Prebuilt authentication and operations for 100s of apps.
  3. Map and transform. Change formats and fields.
  4. Control flow. Conditions, loops, retries, error paths.
  5. Run and monitor. Managed execution with run history.

Words used above, in simple terms: connector = a ready-made link to an app’s API · workflow = a series of automated steps · webhook = a URL that receives event notifications

Type 5 · Mobile back end as a service (MBaaS)

Definition (say it in an interview): Mobile Backend as a Service (MBaaS) provides ready-made back-end capabilities for mobile and web apps — user authentication, databases with real-time sync, file storage, push notifications, analytics, hosting and serverless functions — consumed through client SDKs and protected by declarative security rules.

In plain words (no jargon): A complete ready-made back end for apps — login, data, files and notifications — so app developers do not have to build servers.

Analogy: A ready-made shop counter with billing machine, CCTV and storage: you just arrange your products and open the shutter.

How it works internally, step by step

  1. Create project. Register Android/iOS/web apps.
  2. Add SDK. Client libraries in the app.
  3. Use services. Auth, database, storage, messaging.
  4. Write rules. Who can read/write each document or file.
  5. Extend. Functions for server-side logic.

Words used above, in simple terms: SDK = software development kit — libraries for an app · real-time sync = data changes appear on all devices instantly · push notification = a message sent to a phone even when the app is closed

Type 6 · Data and AI PaaS

Definition (say it in an interview): Data and AI platforms as a service provide managed environments for analytics and machine learning — serverless data warehouses and SQL engines, managed Spark, notebooks, model training, AutoML, model hosting and foundation-model APIs — so teams work with data and models instead of clusters and GPUs.

In plain words (no jargon): Ready-made cloud tools for analysing big data and building AI models, without setting up servers or clusters.

Analogy: A fully equipped laboratory you rent by the hour: instruments, chemicals and safety are provided; you run the experiments.

How it works internally, step by step

  1. Ingest. Load or stream data into managed storage.
  2. Explore. SQL editors, notebooks.
  3. Process/train. Serverless SQL, Spark, ML training jobs.
  4. Deploy. Dashboards, scheduled queries, model endpoints.
  5. Govern. Catalogues, access policies, cost controls.

Words used above, in simple terms: data warehouse = database optimised for analysis · notebook = an interactive document mixing code and results · model endpoint = a URL that returns predictions

Type 7 · Private and hybrid PaaS

Definition (say it in an interview): Private (or hybrid) PaaS is platform software that an organisation installs and operates on its own infrastructure — on-premises or on IaaS in any cloud — to give its developers a PaaS experience (self-service deploys, routing, scaling) while keeping control over location, security and data.

In plain words (no jargon): A company runs its own “PaaS” software on its own servers, so its developers get the easy deploy experience while data stays in-house.

Analogy: A company canteen run by your own staff: the same self-service counter experience as a restaurant, but inside your building and under your rules.

How it works internally, step by step

  1. Provide infrastructure. VMs or bare metal on-premises or in clouds.
  2. Install platform. Kubernetes-based or Cloud Foundry.
  3. Offer self-service. Templates, pipelines, catalogue.
  4. Operate. Upgrades, security, capacity by the platform team.
  5. Span locations. Same tooling everywhere.

Words used above, in simple terms: platform team = engineers who run the internal platform for other teams · data residency = rules about where data must physically stay · hybrid = combining on-premises and public cloud

6 Explained part by part

Six settings you meet on every PaaS

Runtime stack

What it is: Supported language versions.

Why it exists: Defines what code can run and when you must upgrade.

Where it is used: Python 3.12, Node 22, Java 21, .NET 8.

Plan / tier

What it is: The size and features you pay for.

Why it exists: Free tiers lack scaling, slots, custom domains.

Where it is used: App Service F1/B1/S1/P1v3, EB instance types, App Engine instance classes.

Deployment slots / versions

What it is: Parallel versions of an app.

Why it exists: Safe releases and instant rollback.

Where it is used: App Service slots, App Engine versions, EB environments.

App settings / env vars

What it is: Configuration outside the code.

Why it exists: 12-factor apps; secrets via key vaults.

Where it is used: App settings, EB environment properties, app.yaml env_variables.

Scale settings

What it is: Manual or automatic instance counts.

Why it exists: The platform scales; you set limits.

Where it is used: Autoscale rules, EB ASG, App Engine automatic scaling.

Platform limits

What it is: Timeouts, file system, ports, background work.

Why it exists: Decide whether PaaS fits.

Where it is used: Request timeouts, read-only or ephemeral disks.

7 Deep dive

NIST definition, shared responsibility in PaaS, lock-in

NIST definition of PaaS

NIST SP 800-145: “The capability provided to the consumer is to deploy onto the cloud infrastructure consumer-created or acquired applications created using programming languages, libraries, services, and tools supported by the provider. The consumer does not manage or control the underlying cloud infrastructure including network, servers, operating systems, or storage, but has control over the deployed applications and possibly configuration settings for the application-hosting environment.”

Shared responsibility in PaaS

AreaProviderYou
Physical, network, hypervisor✔
OS and runtime patching✔choose supported versions
Application code and dependencies✔ (including vulnerable libraries)
Identity, access, secretstools✔
Data and its classification✔
Network exposure of the appoptions✔ choose private endpoints, WAF

Lock-in: real but manageable

Code on PaaS is usually portable (plain Flask/Spring apps); lock-in comes from platform-specific services (proprietary queues, auth, config). Keep business logic framework-standard, wrap provider SDKs behind small interfaces, and prefer container PaaS when portability matters most.

  2. 1 · Deploy a web app from code

    Pick your cloud.

    UI way — AWS Management Console

    1. Elastic Beanstalk → Create application → web server environment, name tiffingo-feedback, platform Python, application code Sample application, preset Single instance (free tier eligible).

aws iam add-role-to-instance-profile --instance-profile-name aws-elasticbeanstalk-ec2-role --role-name aws-elasticbeanstalk-ec2-role

  3. 2 · Operate it: logs, health and versions

    Pick your cloud.

    UI way — AWS Management Console

    1. Environment → Health: Green/OK with instance details.
    2. Logs → Request logs → Last 100 lines → download.
    3. Configuration → Instance traffic and scaling: change to load balanced, min 1 / max 2 (creates an ALB — optional, it costs money).

    CLI way — the same thing with commands

    aws elasticbeanstalk describe-environment-health --environment-name tiffingo-feedback-env --attribute-names All \
  --query '[HealthStatus,Color]' --output text
aws elasticbeanstalk request-environment-info --environment-name tiffingo-feedback-env --info-type tail
sleep 20
aws elasticbeanstalk retrieve-environment-info --environment-name tiffingo-feedback-env --info-type tail --query 'EnvironmentInfo[0].Message' --output text

    You should see: Ok Green and a pre-signed URL to the last 100 log lines (nginx and web.stdout logs).

    UI way — Azure portal

    1. App → App Service logs → Application logging File System → Save.
    2. Log stream → refresh the site in another tab and watch requests arrive.
    3. Deployment Center → Logs shows each deployment and its build output.

    CLI way — the same thing with commands

    az webapp log config --name $APP --resource-group rg-tiffingo --application-logging filesystem --web-server-logging filesystem
az webapp log tail --name $APP --resource-group rg-tiffingo     # Ctrl+C to stop
az webapp deployment list-publishing-profiles --name $APP --resource-group rg-tiffingo --query "[].publishMethod" --output tsv

    You should see: live log lines with your requests, and the available publish methods (MSDeploy, FTP, ZipDeploy).

    UI way — Google Cloud console

    1. Change the text in main.py and deploy as v2 without moving traffic: gcloud app deploy --version=v2 --no-promote.
    2. Versions → select both → Split traffic → 50/50 by IP → Save.
    3. Logs Explorer → resource “GAE Application” for request logs.

    CLI way — the same thing with commands

    sed -i 's/Running on PaaS/Version 2/' main.py
gcloud app deploy --quiet --version=v2 --no-promote
gcloud app services set-traffic default --splits=v1=0.5,v2=0.5 --split-by=ip --quiet
gcloud app versions list
gcloud app logs read --limit=10

    You should see: two versions each with TRAFFIC_SPLIT 0.5 — a canary release with one command.

    Operating PaaS is about settings — logs, scaling, versions — not servers.

  4. 3 · Create a managed database (DBaaS)

    Pick your cloud.

    UI way — AWS Management Console

    1. RDS → Create database → Easy create → PostgreSQL → template Free tier → identifier tiffingo-db → Manage master credentials in AWS Secrets Manager → Create database.
    2. After ~5–10 minutes: note Endpoint, Backups (automated, 1 day retention on free tier) and Maintenance window — the provider does these for you.

    CLI way — the same thing with commands

    aws rds create-db-instance --db-instance-identifier tiffingo-db --engine postgres --db-instance-class db.t4g.micro \
  --allocated-storage 20 --master-username tiffingo --manage-master-user-password --no-publicly-accessible \
  --backup-retention-period 1
aws rds wait db-instance-available --db-instance-identifier tiffingo-db
aws rds describe-db-instances --db-instance-identifier tiffingo-db \
  --query 'DBInstances[0].[DBInstanceStatus,Engine,EngineVersion,Endpoint.Address,PreferredMaintenanceWindow]' --output text

    You should see: available postgres 17.x tiffingo-db.xxxx.ap-south-1.rds.amazonaws.com …; the password is in Secrets Manager, not in your shell history.

    UI way — Azure portal

    1. Azure Database for PostgreSQL flexible servers → Create → rg-tiffingo, name tiffingo-pg-<n>, Central India, version 16, workload Development (Burstable B1ms).
    2. Networking: Public access with no firewall rules (or private access) → Review + create (~5–10 minutes).
    3. Open it → Backup and restore, Server parameters, Maintenance.

    CLI way — the same thing with commands

    PG=tiffingo-pg-$RANDOM
az postgres flexible-server create --resource-group rg-tiffingo --name $PG --location centralindia \
  --tier Burstable --sku-name Standard_B1ms --storage-size 32 --version 16 --admin-user tiffingo --public-access None
az postgres flexible-server show --resource-group rg-tiffingo --name $PG --query "[state,version,fullyQualifiedDomainName,backup.backupRetentionDays]" --output tsv

    You should see: Ready 16 tiffingo-pg-1234.postgres.database.azure.com 7; the CLI prints a generated admin password once — store it in Key Vault in real projects.

    UI way — Google Cloud console

    1. SQL → Create instance → PostgreSQL → edition Enterprise, preset Sandbox, ID tiffingo-db, generate password, region asia-south1, single zone, smallest shared-core machine → Create instance (~5–10 minutes).
    2. Open it → Backups (automated daily), Maintenance.

    CLI way — the same thing with commands

    gcloud services enable sqladmin.googleapis.com
gcloud sql instances create tiffingo-db --database-version=POSTGRES_16 --edition=ENTERPRISE \
  --tier=db-f1-micro --region=asia-south1 --storage-size=10GB
gcloud sql instances describe tiffingo-db --format="value(state,databaseVersion,settings.backupConfiguration.enabled)"

    You should see: RUNNABLE POSTGRES_16 True. Set the postgres password with gcloud sql users set-password postgres --instance=tiffingo-db --prompt-for-password.

    You never installed PostgreSQL or patched an OS — that is DBaaS. A managed database costs money every hour it exists: delete it right after the lab.

Clean up and cost check

AWS: aws rds delete-db-instance --db-instance-identifier tiffingo-db --skip-final-snapshot --delete-automated-backups; aws elasticbeanstalk delete-application --application-name tiffingo-feedback --terminate-env-by-force; the IAM role/instance profile can stay (free) or be deleted.
Azure: az group delete --name rg-tiffingo --yes --no-wait (web app, plan and PostgreSQL server).
Google Cloud: gcloud sql instances delete tiffingo-db --quiet; gcloud app versions delete v2 --quiet. An App Engine application cannot be deleted — disable it under App Engine → Settings → Disable application, or delete the whole lab project.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Choosing PaaS, then fighting it for OS access.Not checking platform limits.Check runtimes, timeouts, file system and networking first; use container PaaS if needed.
Secrets in code or app settings in plain text.Convenience.Key Vault / Secrets Manager / Secret Manager references.
Assuming the provider secures your code.Misreading shared responsibility.You patch dependencies and fix app vulnerabilities.
Free tier in production.Cheap start.Free tiers lack SLAs, scaling and custom domains with TLS.
Forgetting App Engine’s region is permanent.Quick setup.Pick the region carefully; use a separate project for labs.
Leaving DBaaS instances running after labs.They look idle.Delete or stop; check the bill next day.
