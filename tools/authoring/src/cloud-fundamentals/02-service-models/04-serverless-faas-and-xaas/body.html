1 The story

A 4-second job on a 24-hour server

Before you start: 2.2 PaaS and 2.3 SaaS.

🤔 TiffinGo’s “send the daily menu at 7 a.m.” job runs for 4 seconds a day on a server that costs money 24 hours a day. Its laptops need Windows for 6 interns for 3 months. Its office files need disaster recovery. Is there an “as a service” for all of these?

Yes — and that is what XaaS (“anything as a service”) means. Serverless computing runs your code only when an event happens (FaaS) on top of fully managed back-end services (BaaS), billed per use and scaling to zero. Around it a whole family of services grew: CaaS (containers), DaaS (desktops), DRaaS (disaster recovery), SECaaS (security), AIaaS (AI models). This lesson explains each, shows what happens inside a function invocation including cold starts, and on your own account you deploy a function, run it on a schedule and read its cold-start time.

TiffinGo paid for a server all day to run a 4-second job once a morning. The fix was not a cheaper server — it was no server at all.

R> Sir, our menu-mailer server costs ₹700 a month to run a 4-second job once a day. A> Make it a function. It wakes at 7 a.m., runs 4 seconds, and the monthly bill rounds to zero — Lambda’s free tier alone covers a million requests a month. K> And the interns’ Windows laptops? But the core idea is serverless: no servers to manage, pay per use. Let’s see how it works inside.
2 Definition

Serverless, FaaS and XaaS

Formal definition (write this in exams)

Serverless computing is a cloud execution model in which the provider dynamically manages the allocation of servers, applications are built from functions (FaaS) triggered by events and fully managed back-end services (BaaS), resources scale automatically to zero, and billing is based on actual usage. XaaS (“anything as a service”) is the umbrella for delivering any IT capability — containers, desktops, disaster recovery, security, AI — as an on-demand service.

In simple words

Serverless: you write small pieces of code that run only when needed, and pay only for that time. XaaS: almost any IT need can now be rented as a service.

Say it in an interview

30-second answer you can speak:

  • “Serverless means no server management, automatic scaling including to zero, and pay-per-use — FaaS like Lambda for code plus BaaS like DynamoDB, S3 and Cognito for the back end.”
  • “XaaS extends the service models: CaaS for containers, DaaS for desktops, DRaaS for recovery, SECaaS for security, AIaaS for models.”

Type 1 · FaaS (Function as a Service)

Definition (say it in an interview): Function as a Service (FaaS) executes small, stateless pieces of code in response to events on fully managed infrastructure, creating execution environments on demand, scaling automatically from zero to many parallel instances, and billing per invocation and execution time.

In plain words (no jargon): You write one small piece of code; the cloud runs it only when something happens, and you pay only for those seconds.

Analogy: A pressure cooker’s whistle: it acts only when the steam builds up, then goes quiet — no one stands by it all day.

How it works internally, step by step

  1. Package. Code + dependencies (zip or container image).
  2. Configure. Runtime, memory, timeout, permissions role.
  3. Trigger. Connect an event source.
  4. Invoke. Cold or warm start; handler runs (see “How it works”).
  5. Observe. Logs, metrics, traces per invocation.

Words used above, in simple terms: handler = the function the platform calls · invocation = one run of a function · cold start = first-call delay to create an environment · concurrency = how many copies run at the same time

Lambda bills in 1 ms increments, and its always-free tier includes 1 million requests and 400,000 GB-seconds per month — why small scheduled jobs often cost nothing.

For the experienced — did you know? Memory is also the CPU knob: Lambda allocates CPU in proportion to memory (a full vCPU at about 1,769 MB). Raising memory can make a CPU-bound function so much faster that it becomes cheaper.

Use it when: short, event-driven, bursty work: webhooks, file processing, schedules, glue between services.
Avoid / be careful when: long-running jobs (Lambda max 15 min), steady high traffic, or latency-critical paths sensitive to cold starts.

Type 2 · BaaS (serverless Backend as a Service)

Definition (say it in an interview): Backend as a Service (BaaS) in the serverless sense means building application back ends from fully managed, per-use services — authentication, databases, storage, messaging, APIs, search — that scale automatically and require no server management, typically combined with FaaS for custom logic.

In plain words (no jargon): Instead of building your own login system, database server and file server, you use ready-made cloud services for each and pay per use.

Analogy: Ordering a ready-made wedding package — tent, lights, sound — instead of buying the equipment: you configure it; the vendor runs it.

How it works internally, step by step

  1. Choose services. Auth, data, storage, messaging, API.
  2. Configure. Tables, buckets, user pools, permissions.
  3. Connect. Clients or functions call them via SDK/API.
  4. Secure. IAM roles, tokens, fine-grained rules.
  5. Scale. Automatic; watch limits and costs.

Words used above, in simple terms: back end = the server side of an app · user pool = a managed directory of app users · per-use pricing = pay per request/GB, not per server

Use it when: building new apps quickly with small teams; most of the back end is standard capability.
Avoid / be careful when: you need features or performance a service cannot provide, or strict portability across clouds.

Type 3 · CaaS (Containers as a Service)

Definition (say it in an interview): Containers as a Service (CaaS) provides managed container orchestration and runtime — clusters, scheduling, networking, scaling and health management — so customers deploy and operate containerised applications without building orchestration infrastructure themselves; it sits between IaaS and PaaS.

In plain words (no jargon): A cloud service that runs and manages lots of packed apps (containers) for you.

Analogy: A shipping port with cranes and berths ready: you bring standard containers; the port moves, stacks and tracks them.

How it works internally, step by step

  1. Build images. Push to a registry.
  2. Define. Task definitions / Kubernetes manifests.
  3. Run. Managed control plane schedules containers.
  4. Connect. Service discovery, load balancers.
  5. Operate. Autoscaling, rolling updates, logs.

Words used above, in simple terms: orchestrator = software that decides where containers run and keeps them healthy · registry = storage for container images · manifest = a file describing what to run

Avoid / be careful when: one simple app — serverless containers or PaaS are simpler.

Type 4 · DaaS (Desktop as a Service)

Definition (say it in an interview): Desktop as a Service (DaaS) delivers complete virtual desktops (Windows or Linux) hosted in the cloud and streamed to users’ devices, with the provider managing the virtual desktop infrastructure and the customer managing images, applications, users and policies; billed per user or per hour.

In plain words (no jargon): A full computer desktop that runs in the cloud and appears on any laptop or tablet through the internet.

Analogy: Streaming a movie instead of buying the DVD: you watch on any screen, and nothing is stored on your device.

How it works internally, step by step

  1. Directory. Connect to Active Directory/Entra ID.
  2. Bundle/image. OS + apps + size.
  3. Provision. Desktop per user or pooled.
  4. Connect. Client app or browser streams pixels (PCoIP/DCV/RDP).
  5. Manage. Patching images, policies, auto-stop.

Words used above, in simple terms: virtual desktop = a desktop running on a server, shown remotely · BYOD = bring your own device · pooled desktop = shared desktops reset after use

Type 5 · DRaaS (Disaster Recovery as a Service)

Definition (say it in an interview): Disaster Recovery as a Service (DRaaS) continuously replicates servers, applications and data from a primary site (on-premises or another cloud/Region) to a provider’s cloud, and orchestrates failover and failback, so organisations get a recovery site without building or paying for a second data centre.

In plain words (no jargon): A cloud service that keeps a live copy of your servers and can start them in the cloud quickly if your main site is destroyed.

Analogy: A spare house on rent that is kept furnished as a copy of yours and updated every night — you only move in if your house floods.

How it works internally, step by step

  1. Agent/replication. Block-level replication of disks.
  2. Staging. Low-cost staging area with tiny instances/storage.
  3. Plan. Recovery order, network settings.
  4. Fail over. Launch recovery instances on demand.
  5. Fail back. Reverse replication when the primary returns.

Words used above, in simple terms: replication = continuously copying changes · failover = switching to the recovery site · failback = returning to the original site · drill = a practice recovery

Type 6 · SECaaS (Security as a Service)

Definition (say it in an interview): Security as a Service (SECaaS) delivers security capabilities — web application firewalls, DDoS protection, secure web gateways and zero-trust access, email security, threat detection, vulnerability scanning, identity and SIEM — as cloud services, without customers installing and running security appliances.

In plain words (no jargon): Security tools — firewalls, virus and attack detection — rented from the cloud instead of buying and running security machines.

Analogy: Hiring a security agency with guards, CCTV control room and patrol vans instead of building your own security department.

How it works internally, step by step

  1. Onboard. Enable the service or route traffic/logs to it.
  2. Policies. Rules, managed rule sets, baselines.
  3. Detect. Signals from traffic, logs and threat intelligence.
  4. Respond. Block automatically; alert humans.
  5. Report. Dashboards and compliance reports.

Words used above, in simple terms: WAF = web application firewall · SIEM = system that collects and analyses security events · zero trust = verify every access, trust no network by default

Type 7 · AIaaS (AI as a Service)

Definition (say it in an interview): AI as a Service (AIaaS) provides artificial-intelligence capabilities — foundation models for text, code and images, speech, vision, translation, document extraction, and managed ML platforms — through APIs and managed services, so applications use AI without owning GPUs or training infrastructure.

In plain words (no jargon): Renting artificial intelligence from the cloud: send a question, text or picture to an online service and get an intelligent answer back.

Analogy: Hiring a translator or designer by the hour from an agency instead of employing one full-time.

How it works internally, step by step

  1. Access. Enable models/services; check Region availability.
  2. Call. API/SDK with prompts or files.
  3. Ground. Add your data (RAG) and guardrails.
  4. Control. Quotas, logging, content filters.
  5. Pay. Per token/call; provisioned throughput for steady load.

Words used above, in simple terms: foundation model = a large AI model usable for many tasks · token = a piece of a word; the billing unit for text models · guardrail = a rule that filters unsafe or off-topic output

Six settings of every function

Trigger / event source

What it is: What starts a function.

Why it exists: Defines the architecture.

Where it is used: HTTP, schedule, storage, queue, stream.

Execution role / identity

What it is: Permissions the function uses.

Why it exists: Least privilege per function.

Where it is used: Lambda execution role, managed identity, service account.

Timeout and memory

What it is: Limits per invocation.

Why it exists: Cost and CPU depend on memory.

Where it is used: Lambda 1–900 s, 128 MB–10 GB.

Concurrency

What it is: Parallel executions.

Why it exists: Protects downstream systems; account limits apply.

Where it is used: Reserved/provisioned concurrency, max instances.

Cold start mitigations

What it is: Ways to avoid init delay.

Why it exists: Latency-sensitive APIs.

Where it is used: Provisioned concurrency, SnapStart, min instances, Premium plan.

Dead-letter / retry policy

What it is: What happens when async calls fail.

Why it exists: No lost events.

Where it is used: Lambda DLQ/destinations, Functions retry, Pub/Sub DLQ.

Myth vs reality: things many websites still say

  • Myth: Serverless means no servers.
    Reality: Servers exist; you do not manage them.
    Proof: Definition.
  • Myth: Serverless is always cheaper.
    Reality: At steady high load containers/VMs can be cheaper.
    Proof: Deep dive.
  • Myth: Cold starts make serverless unusable.
    Reality: They are milliseconds to a second and can be mitigated.
    Proof: How it works.

Serverless economics: break-even

FaaS cost = requests × price + GB-seconds × price. A function at 1 request/second all month costs very little; at 1,000 requests/second steadily, a container fleet with a Savings Plan is usually cheaper. Calculate both (Lesson 5.5) — serverless wins on spiky and low traffic.

XaaS and the NIST model

NIST defines only three service models (IaaS, PaaS, SaaS). FaaS, CaaS, DaaS and the rest are industry terms that fit inside them: FaaS and CaaS sit between IaaS and PaaS, DaaS is delivered like SaaS on IaaS, and SECaaS/AIaaS are mostly SaaS/PaaS. Exams use both vocabularies.

  2. 1 · Deploy and invoke a function (FaaS)

    Pick your cloud.

    UI way — AWS Management Console

    1. Lambda → Create function → Author from scratch → name tiffingo-menu-mailer, runtime Python 3.12, Create a new role with basic Lambda permissions → Create function.
    2. Replace the code with the snippet on the right → Deploy → Test → create a test event → Test.
    3. Read the execution result: duration, billed duration, memory used.

    CLI way — the same thing with commands

    cat > lambda_function.py <<'EOF'
import json, datetime
def lambda_handler(event, context):
    print('Sending today\'s menu', datetime.datetime.utcnow().isoformat())
    return {'statusCode': 200, 'body': json.dumps({'sent': True})}
EOF
zip fn.zip lambda_function.py
aws iam create-role --role-name tiffingo-fn-role --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"lambda.amazonaws.com"},"Action":"sts:AssumeRole"}]}'

sleep 15

  --zip-file fileb://fn.zip --role arn:aws:iam::$ACCT:role/tiffingo-fn-role --memory-size 256 --timeout 10

  3. 2 · Run it every morning (scheduled event)

    Pick your cloud.

    UI way — AWS Management Console

    1. Amazon EventBridge → Schedules → Create schedule → name menu-7am, recurring, cron 30 1 * * ? * (07:00 IST = 01:30 UTC).

  4. 3 · Read the cold start and the cost

    Pick your cloud.

    UI way — AWS Management Console

    1. CloudWatch → Log groups → /aws/lambda/tiffingo-menu-mailer → search REPORT.
    2. Invoke twice quickly: the first REPORT has Init Duration (cold), the second does not (warm).
    3. Bill: Cost Explorer → service Lambda — at this volume ₹0 (always-free tier).

    CLI way — the same thing with commands

    for i in 1 2; do aws lambda invoke --function-name tiffingo-menu-mailer --log-type Tail out.json --query LogResult --output text | base64 -d | grep REPORT; done

    You should see: two REPORT lines; usually only the first contains Init Duration. Change memory to 1024 MB and compare Duration.

    UI way — Azure portal

    1. Function App → Log stream (or Application Insights → Live metrics).
    2. Call the URL after 15+ idle minutes and again immediately: the first response is slower (cold start on Flex Consumption unless always-ready instances are set).

    CLI way — the same thing with commands

    for i in 1 2; do curl -s -o /dev/null -w "%{time_total}s\n" "https://$APP.azurewebsites.net/api/menu?name=x"; done

    You should see: the first time noticeably longer than the second.

    UI way — Google Cloud console

    1. Cloud Run → service → Logs; Metrics → container startup latency.
    2. Edit & deploy new revision → Minimum number of instances = 1 removes cold starts (but costs money while idle).

    CLI way — the same thing with commands

    for i in 1 2; do curl -s -o /dev/null -w '%{time_total}s\n' -H "Authorization: bearer $(gcloud auth print-identity-token)" $URL; done

    You should see: a slower first call after idle, faster second call, and the log lines.

    Cold starts are the price of scale-to-zero; pay for minimum/provisioned instances only where latency matters.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Running a VM for a job that runs minutes a day.Habit.Scheduled functions or jobs.
Long tasks in functions.Functions feel simple.Use containers/batch for > 15 min; or Step Functions/Durable Functions to orchestrate.
Opening DB connections inside the handler.Simple code.Create clients outside the handler to reuse in warm starts; use proxies/pools.
One huge role for all functions.Convenience.Least-privilege role per function.
Ignoring concurrency limits.Assuming infinite scale.Set reserved/max concurrency to protect databases; request quota increases.
Calling everything “serverless”.Marketing.Check: no servers, scale to zero, pay per use.
