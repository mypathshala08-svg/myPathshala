1 The story

An admin key for a read-only job

Before you start: 9.1–9.3.

🤔 TiffinGo’s reporting job needs to read one folder of one bucket. Today it runs with an admin access key that never expires. If that key leaks, what can an attacker do — and even if they copy the files, could encryption still save the data?

With an admin key: everything. With a role that can only read that folder: almost nothing. And if the data is encrypted with a key you control, disabling that key makes stolen copies unreadable. This lesson covers the seven basics of cloud identity and encryption — identities, authentication & MFA, authorisation policies, federation & SSO, encryption at rest, encryption in transit and key management — animates how one request is checked and decrypted, and on your own account you build a least-privilege identity, encrypt and “shred” data with a managed key, and enforce TLS.

  • Explicit deny beats allow — and “no rule” means no.
  • Envelope encryption: why KMS never encrypts your 5 GB file directly.
  • Why roles and managed identities beat access keys.

TiffinGo’s nightly reporting job only needed to read one folder of one bucket — yet it ran with an administrator access key that never expired. After Lesson 9.2’s incident, the team asked how to make the next leak harmless.

K> Sir, admin was quicker. Every time I gave fewer permissions, something broke. A> That pain is temporary; a leaked admin key is permanent damage. Start with what the job really calls, then add only what fails. R> And encryption? S3 already encrypts everything. A> Yes, by default. But with our own KMS key, we decide who can decrypt — and we can turn the key off in an emergency. K> So identity says who may ask, encryption decides who can read. A> Exactly. Let’s go one by one.
2 Definition

Identity, access and encryption basics

Formal definition (write this in exams)

Identity and access management (IAM) establishes who or what is making a request (identity), verifies it (authentication, ideally with MFA or federation) and determines what it may do (authorisation through policies and roles, following least privilege), with all actions audited. Encryption protects data at rest and in transit (and, with confidential computing, in use) using keys managed in key management services, where key policies, rotation and the ability to disable keys add a separate layer of control over who can read data.

In simple words

Make sure every person and app has its own identity, proves who it is, and can only do its own job — and lock the data itself with keys you control.

Say it in an interview

30-second answer you can speak:

  • “Authentication proves identity, authorisation decides permissions. I use SSO with MFA for people, roles or managed identities for workloads, least-privilege policies with default deny, and guard-rails like SCPs.”
  • “Encryption at rest is default; I add customer-managed KMS keys for sensitive data — envelope encryption, rotation, separate key admins and users — and enforce TLS 1.2+ in transit.”

Type 1 · Identities: users, groups, roles and service identities

Definition (say it in an interview): An identity (principal) is anything that can make requests: human users (ideally from a central directory), groups that collect users for permission assignment, and workload identities — IAM roles, Azure managed identities, Google service accounts — that applications assume to receive short-lived credentials without stored secrets. The root/owner account is a special identity to lock away.

In plain words (no jargon): Accounts for people and apps, so the cloud always knows who is asking.

Analogy: An office: each employee has a personal ID card, departments get floor access, and the delivery robot has its own badge that only opens the store room.

How it works internally, step by step

  1. Root. MFA, no keys, lock away.
  2. People. From SSO directory.
  3. Groups. Permissions via groups.
  4. Workloads. Roles/managed identities.
  5. Lifecycle. Remove leavers automatically.

Words used above, in simple terms: principal = any identity that can make a request · role = an identity assumed temporarily, with its own permissions · managed identity = Azure identity for a resource, credentials handled by Azure

Type 2 · Authentication and multi-factor authentication (MFA)

Definition (say it in an interview): Authentication verifies that an identity is who it claims to be; multi-factor authentication (MFA) requires two or more independent factors — something you know (password), have (authenticator app, hardware security key, passkey) or are (biometrics) — greatly reducing the risk from stolen passwords. Phishing-resistant MFA (FIDO2 keys, passkeys) is strongest.

In plain words (no jargon): Logging in with a password plus a second proof, like a code from your phone.

Analogy: An ATM: the card (have) and the PIN (know) — neither alone is enough.

How it works internally, step by step

  1. Enrol. Authenticator or security key.
  2. Enforce. Policies require MFA.
  3. Root. Hardware key on root/owner.
  4. Conditional. Stronger checks for risky sign-ins.
  5. Recover. Backup methods, break-glass.

Words used above, in simple terms: factor = one type of proof · phishing-resistant = cannot be tricked into giving codes to fake sites · passkey = device-bound credential replacing passwords

Type 3 · Authorisation: policies, RBAC and least privilege

Definition (say it in an interview): Authorisation decides what an authenticated identity may do. Cloud platforms evaluate policies — identity-based, resource-based, permission boundaries, organisation guard-rails — with default deny and explicit deny overriding allow; Azure and Google use role-based access control (RBAC) assignments at a scope; conditions enable attribute-based control (ABAC). Least privilege grants only the permissions a task needs.

In plain words (no jargon): Rules that decide exactly what each person or app is allowed to do.

Analogy: Hotel key cards: your card opens your room and the gym, not other rooms — and the manager can block a card instantly.

How it works internally, step by step

  1. Default deny. Nothing unless allowed.
  2. Allow narrowly. Specific actions + resources.
  3. Guard-rails. SCPs/Azure Policy/org policies.
  4. Review. Unused-permission findings.
  5. Elevate JIT. Time-bound admin (PIM).

Words used above, in simple terms: least privilege = only the permissions needed · scope = where a role applies: account, subscription, project, resource · JIT access = just-in-time, temporary elevation

Type 4 · Federation and single sign-on (SSO)

Definition (say it in an interview): Federation lets a cloud or application trust identities from an external identity provider (IdP) using standards such as SAML 2.0 and OpenID Connect; single sign-on lets users authenticate once (with MFA) and access many systems. Workload identity federation applies the same idea to machines — for example GitHub Actions obtaining cloud tokens via OIDC without stored keys.

In plain words (no jargon): One company login that works for all cloud accounts and apps.

Analogy: A national ID card accepted by banks, airports and telecoms — each trusts the issuer instead of issuing its own card.

How it works internally, step by step

  1. Pick IdP. Entra ID, Google, Okta.
  2. Connect. SAML/OIDC trust.
  3. Map. Groups → roles/permission sets.
  4. Enforce. MFA and conditional access at IdP.
  5. Automate. SCIM provisioning and de-provisioning.

Words used above, in simple terms: IdP = identity provider · SAML / OIDC = standards for federated login · SCIM = standard for automatic user provisioning

Type 5 · Encryption at rest

Definition (say it in an interview): Encryption at rest protects stored data — block volumes, object storage, databases, backups — by encrypting it (typically AES-256) with keys held in a key management service; all three major providers encrypt stored data by default with provider-managed keys, and customers can choose customer-managed keys (CMKs) for control over key policy, rotation, disabling and audit.

In plain words (no jargon): Scrambling stored data so a stolen copy cannot be read without the key.

Analogy: Valuables in a locker: even if someone carries the locker away, they still need the key.

How it works internally, step by step

  1. Default. Provider keys, automatic.
  2. CMK. Your key in KMS.
  3. Policy. Who may use the key.
  4. Rotate. Automatic yearly rotation.
  5. Shred. Disable/schedule deletion of key.

Words used above, in simple terms: AES-256 = standard strong symmetric encryption · CMK = customer-managed key · crypto-shredding = making data unreadable by destroying its key

Type 6 · Encryption in transit (TLS)

Definition (say it in an interview): Encryption in transit protects data moving between clients and services or between services, normally with TLS (1.2 or 1.3): the server proves its identity with a certificate, keys are exchanged, and traffic is encrypted and integrity-protected; cloud APIs require HTTPS, and customers enforce TLS on their own endpoints, storage and databases (including mutual TLS between services).

In plain words (no jargon): Scrambling data while it travels over the network, like the padlock in your browser.

Analogy: A sealed, tamper-evident courier bag: nobody on the way can read or change the contents unnoticed.

How it works internally, step by step

  1. Certificates. Managed, auto-renewing.
  2. Minimum version. TLS 1.2+.
  3. Enforce. HTTPS-only policies.
  4. Internal. TLS/mTLS between services.
  5. Monitor. Expiry alerts.

Words used above, in simple terms: TLS = Transport Layer Security · certificate = signed proof of a server’s identity · mTLS = mutual TLS — both sides present certificates

Type 7 · Key management (KMS, CMK, HSM, envelope encryption)

Definition (say it in an interview): Key management covers creating, storing, using, rotating and destroying cryptographic keys. Cloud KMS services keep master keys inside hardware security modules (HSMs), perform envelope encryption (data encrypted with data keys; data keys encrypted by a KMS key), enforce key-use policies separate from data permissions, rotate keys and log every use; options range from provider-managed keys to customer-managed, customer-supplied/external keys and dedicated HSMs.

In plain words (no jargon): Looking after the secret keys that lock your data — where they live, who can use them, and when they change.

Analogy: A bank vault holds the master key; each locker has its own small key, kept in an envelope sealed by the master key. Lose the master key — or lock it away — and no envelope can be opened.

How it works internally, step by step

  1. Create. Symmetric/asymmetric keys.
  2. Policy. Key users vs key admins.
  3. Use. Encrypt/decrypt via API.
  4. Rotate. Automatic versions.
  5. Retire. Disable, then scheduled deletion.

Words used above, in simple terms: HSM = tamper-resistant hardware that protects keys · envelope encryption = encrypting data keys with a master key · BYOK / HYOK = bring / hold your own key

6 Explained part by part

Six controls around identity and keys

Root / owner account

What it is: The all-powerful first identity.

Why it exists: If lost, everything is lost.

Where it is used: Hardware MFA, no keys, break-glass only.

Permission boundary / guard-rail

What it is: Maximum permissions possible.

Why it exists: Limits damage of mistakes.

Where it is used: SCPs, permission boundaries, Azure Policy, org policies.

Temporary credentials

What it is: Tokens that expire.

Why it exists: Leaks age out quickly.

Where it is used: STS, managed identity tokens, OAuth.

Key policy

What it is: Who may use/manage a key.

Why it exists: Second lock on encrypted data.

Where it is used: KMS key policy, Key Vault RBAC, KMS IAM.

Secrets manager

What it is: Stores passwords and API keys.

Why it exists: No secrets in code or images.

Where it is used: Secrets Manager, Key Vault, Secret Manager.

Access reviews

What it is: Periodic check of who has what.

Why it exists: Removes creep and leavers.

Where it is used: Access Analyzer, Entra access reviews, IAM recommender.

Myth vs reality: things many websites still say

  • Myth: Encryption protects data from anyone with access.
    Reality: Authorised identities decrypt transparently.
    Proof: Type 5.
  • Myth: Allow beats deny if it is more specific.
    Reality: Explicit deny always wins.
    Proof: Step 1 + 3.
  • Myth: Access keys are fine if rotated.
    Reality: Temporary credentials and roles are far safer.
    Proof: Type 1.
7 Deep dive

Zero Trust, policy evaluation, confidential computing, hygiene checklist

Zero Trust in one paragraph

Zero Trust means never trusting a request because of where it comes from (inside the office network); every request is authenticated, authorised with least privilege and continuously evaluated using identity, device health and context. Cloud identity, MFA, conditional access and fine-grained policies are its building blocks.

AWS policy evaluation, precisely

  1. Start with implicit deny.
  2. Any explicit deny in any applicable policy (SCP, resource, identity, boundary, session) → final deny.
  3. Organisations SCPs/RCPs must allow the action.
  4. Resource-based policy allow may grant access (same account).
  5. Identity-based policy must allow (and permission boundary and session policy, if present, must also allow).
  6. Otherwise → implicit deny.

Encryption in use (confidential computing)

Data must be decrypted to be processed — unless it runs in a hardware-protected trusted execution environment. AWS Nitro Enclaves, Azure confidential VMs/containers and Google Confidential VMs keep data encrypted in memory and isolated even from cloud operators, for very sensitive workloads.

Key and secret hygiene checklist

  • No long-lived access keys for humans; workloads use roles/managed identities/service account attachment.
  • Secrets in a secrets manager with rotation.
  • CMKs for regulated data, automatic rotation on, key admins ≠ key users.
  • TLS 1.2+ everywhere with managed certificates.
  • Alert on: root sign-in, MFA disabled, key disabled/scheduled for deletion, policy attached with “*”.

  2. 1 · Build a least-privilege identity and test allow vs deny

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → create bucket tiffingo-reports-… with folders reports/ and private/.
    2. IAM → Roles → Create role → trusted entity AWS account (this account) → inline policy allowing s3:GetObject on reports/* only → name report-reader.
    3. Use the role (switch role in the console, or assume-role in the CLI) and try both folders.

    CLI way — the same thing with commands

    B=tiffingo-reports-$RANDOM; aws s3 mb s3://$B --region ap-south-1
echo 'october totals' > oct.csv; aws s3 cp oct.csv s3://$B/reports/oct.csv; aws s3 cp oct.csv s3://$B/private/salaries.csv
ACC=$(aws sts get-caller-identity --query Account --output text)
aws iam create-role --role-name report-reader --assume-role-policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":{\"AWS\":\"arn:aws:iam::$ACC:root\"},\"Action\":\"sts:AssumeRole\"}]}" >/dev/null
aws iam put-role-policy --role-name report-reader --policy-name read-reports --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":\"s3:GetObject\",\"Resource\":\"arn:aws:s3:::$B/reports/*\"}]}"
sleep 10
read AK SK ST < <(aws sts assume-role --role-arn arn:aws:iam::$ACC:role/report-reader --role-session-name riya --duration-seconds 900 \
  --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]' --output text)
AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN=$ST aws s3 cp s3://$B/reports/oct.csv - 
AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN=$ST aws s3 cp s3://$B/private/salaries.csv - 2>&1 | tail -1

    You should see: october totals for reports/, then An error occurred (403) … Forbidden for private/ — implicit deny. The temporary credentials expire in 15 minutes.

    UI way — Azure portal

    1. Managed Identities → Create id-report-reader.
    2. Storage account → container reports → Access control (IAM) → Add role assignment → Storage Blob Data Reader → the managed identity → scope = this container only.
    3. Check access → select the identity → it shows read on reports, nothing on private.

    CLI way — the same thing with commands

    az group create -n rg-iam -l centralindia
SA=tgiam$RANDOM; az storage account create -n $SA -g rg-iam -l centralindia --sku Standard_LRS --allow-blob-public-access false
az identity create -g rg-iam -n id-report-reader
PID=$(az identity show -g rg-iam -n id-report-reader --query principalId -o tsv)
SCOPE=$(az storage account show -n $SA -g rg-iam --query id -o tsv)/blobServices/default/containers/reports
az storage container create --account-name $SA -n reports --auth-mode login; az storage container create --account-name $SA -n private --auth-mode login
az role assignment create --assignee-object-id $PID --assignee-principal-type ServicePrincipal --role 'Storage Blob Data Reader' --scope $SCOPE
az role assignment list --assignee $PID --all --query "[].{role:roleDefinitionName,scope:scope}" -o table

    You should see: one assignment: Storage Blob Data Reader scoped to …/containers/reports. An app running with this identity (VM, App Service, Function) reads reports and gets 403 on private — with no password anywhere. (If container creation is denied, give yourself “Storage Blob Data Contributor” on the account.)

    UI way — Google Cloud console

    1. IAM & Admin → Service accounts → Create report-reader (no project role).
    2. Bucket tiffingo-reports-… → Permissions → Grant access → the service account → Storage Object Viewer (bucket level only).
    3. Test with impersonation from Cloud Shell (right).

    CLI way — the same thing with commands

    P=$(gcloud config get-value project); ME=$(gcloud config get-value account)

gcloud storage buckets create gs://$B gs://$B2 --location=asia-south1

sleep 30
gcloud storage cat gs://$B/reports/oct.csv --impersonate-service-account=$SA
gcloud storage cat gs://$B2/salaries.csv --impersonate-service-account=$SA 2>&1 | tail -1

    You should see: october totals, then a 403 … does not have storage.objects.get access error for the other bucket (IAM changes can take a minute to apply).

    Least privilege in practice: the identity can do exactly one job. Everything else is denied by default.

  3. 2 · Encrypt with your own key — then “shred” access by disabling it

    Pick your cloud.

    UI way — AWS Management Console

    1. Key Management Service → Customer managed keys → Create key → symmetric → alias tiffingo-reports → enable automatic rotation.
    2. Encrypt a small secret, decrypt it, then Key actions → Disable and try again.

    CLI way — the same thing with commands

    KEY=$(aws kms create-key --description 'tiffingo reports' --query KeyMetadata.KeyId --output text)
aws kms create-alias --alias-name alias/tiffingo-reports --target-key-id $KEY
aws kms enable-key-rotation --key-id $KEY
aws kms encrypt --key-id alias/tiffingo-reports --plaintext fileb://oct.csv --query CiphertextBlob --output text | base64 -d > oct.enc
aws kms decrypt --ciphertext-blob fileb://oct.enc --query Plaintext --output text | base64 -d
aws kms disable-key --key-id $KEY
aws kms decrypt --ciphertext-blob fileb://oct.enc 2>&1 | tail -1

    You should see: october totals after decrypt, then DisabledException … is disabled. Any data (S3 objects, EBS, RDS) encrypted under this key becomes unreadable until you re-enable it. A KMS key costs about $1 a month, prorated.

    UI way — Azure portal

    1. Key vaults → Create kv-tiffingo-… (Standard, RBAC permission model) → give yourself Key Vault Crypto Officer → Keys → Generate reports-key (RSA 2048).
    2. Encrypt a small value, decrypt it, then set the key Enabled = No and try again.

    CLI way — the same thing with commands

    KV=kv-tiffingo-$RANDOM; az keyvault create -n $KV -g rg-iam -l centralindia --enable-rbac-authorization true
az role assignment create --assignee $(az ad signed-in-user show --query id -o tsv) --role 'Key Vault Crypto Officer' --scope $(az keyvault show -n $KV --query id -o tsv)
sleep 30; az keyvault key create --vault-name $KV -n reports-key --kty RSA --size 2048 >/dev/null
CT=$(az keyvault key encrypt --vault-name $KV -n reports-key --algorithm RSA-OAEP-256 --value $(echo -n 'data-key-123' | base64) --query result -o tsv)
az keyvault key decrypt --vault-name $KV -n reports-key --algorithm RSA-OAEP-256 --value $CT --query result -o tsv | base64 -d; echo
az keyvault key set-attributes --vault-name $KV -n reports-key --enabled false >/dev/null
az keyvault key decrypt --vault-name $KV -n reports-key --algorithm RSA-OAEP-256 --value $CT 2>&1 | tail -1

    You should see: data-key-123 (a wrapped data key — envelope encryption), then an error that the operation is not allowed on a disabled key. Key Vault Standard charges per operation — a few paise here.

    UI way — Google Cloud console

    1. Security → Key Management → Create key ring tiffingo-ring (asia-south1) → Create key reports-key, rotation 365 days.
    2. Encrypt, decrypt, then disable the key version and try again.

    CLI way — the same thing with commands

    gcloud services enable cloudkms.googleapis.com
gcloud kms keyrings create tiffingo-ring --location=asia-south1
gcloud kms keys create reports-key --keyring=tiffingo-ring --location=asia-south1 --purpose=encryption --rotation-period=365d --next-rotation-time=$(date -u -d '+365 days' +%Y-%m-%dT%H:%M:%SZ)
gcloud kms encrypt --key=reports-key --keyring=tiffingo-ring --location=asia-south1 --plaintext-file=oct.csv --ciphertext-file=oct.enc
gcloud kms decrypt --key=reports-key --keyring=tiffingo-ring --location=asia-south1 --ciphertext-file=oct.enc --plaintext-file=-
gcloud kms keys versions disable 1 --key=reports-key --keyring=tiffingo-ring --location=asia-south1
gcloud kms decrypt --key=reports-key --keyring=tiffingo-ring --location=asia-south1 --ciphertext-file=oct.enc --plaintext-file=- 2>&1 | tail -1

    You should see: october totals, then FAILED_PRECONDITION … is not enabled. Key rings cannot be deleted (they are free); key versions cost a few cents a month until destroyed.

    Two locks: identity decides who may ask; the key decides who can read. Disabling the key is your emergency brake.

  4. 3 · Enforce encryption in transit (TLS only)

    Pick your cloud.

    UI way — AWS Management Console

    1. Bucket → Permissions → Bucket policy → add a statement denying any request where aws:SecureTransport is false → Save changes.

    CLI way — the same thing with commands

    aws s3api put-bucket-policy --bucket $B --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Sid\":\"TLSOnly\",\"Effect\":\"Deny\",\"Principal\":\"*\",\"Action\":\"s3:*\",\"Resource\":[\"arn:aws:s3:::$B\",\"arn:aws:s3:::$B/*\"],\"Condition\":{\"Bool\":{\"aws:SecureTransport\":\"false\"}}}]}"
aws s3 ls s3://$B/reports/
aws s3 ls s3://$B/reports/ --endpoint-url http://s3.ap-south-1.amazonaws.com 2>&1 | tail -1
curl -sv https://s3.ap-south-1.amazonaws.com -o /dev/null 2>&1 | grep -m1 -E 'SSL connection using|TLSv1'

    You should see: the listing over HTTPS, AccessDenied over plain HTTP (explicit deny wins), and a line such as SSL connection using TLSv1.3.

    UI way — Azure portal

    1. Storage account → Configuration → Secure transfer required = Enabled, Minimum TLS version = 1.2 → Save. (Both are defaults for new accounts — verify.)

    CLI way — the same thing with commands

    az storage account update -n $SA -g rg-iam --https-only true --min-tls-version TLS1_2
az storage account show -n $SA -g rg-iam --query "{httpsOnly:enableHttpsTrafficOnly,minTls:minimumTlsVersion}"
curl -s -o /dev/null -w '%{http_code}\n' http://$SA.blob.core.windows.net/reports?restype=container

    You should see: httpsOnly: true, minTls: TLS1_2, and an HTTP 4xx code for the plain-HTTP request.

    UI way — Google Cloud console

    1. Cloud Storage always uses HTTPS. For your own load-balanced apps: Network security → SSL policies → Create tls12-modern, minimum TLS 1.2, profile Modern → attach to the HTTPS load balancer.

    CLI way — the same thing with commands

    gcloud compute ssl-policies create tls12-modern --profile=MODERN --min-tls-version=1.2
gcloud compute ssl-policies describe tls12-modern --format='value(minTlsVersion,profile)'
curl -sv https://storage.googleapis.com -o /dev/null 2>&1 | grep -m1 -E 'SSL connection using|TLSv1'

    You should see: TLS_1_2 MODERN and a TLS 1.3 connection to Google’s endpoint. SSL policies are free; attach them to HTTPS/SSL proxy load balancers.

    Explicit deny for non-TLS traffic is a one-line control auditors love — and it shows deny precedence in action.

Clean up and cost check

AWS: aws kms schedule-key-deletion --key-id $KEY --pending-window-in-days 7; aws kms delete-alias --alias-name alias/tiffingo-reports; aws s3 rb s3://$B --force; aws iam delete-role-policy --role-name report-reader --policy-name read-reports; aws iam delete-role --role-name report-reader. Azure: az group delete -n rg-iam --yes --no-wait; then az keyvault purge -n $KV (soft-deleted vaults keep the name for 90 days). Google Cloud: gcloud kms keys versions destroy 1 --key=reports-key --keyring=tiffingo-ring --location=asia-south1; gcloud storage rm -r gs://$B gs://$B2; gcloud iam service-accounts delete $SA --quiet; gcloud compute ssl-policies delete tls12-modern --quiet.

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Admin access for apps “to make it work”.Permission errors are annoying.Start minimal; add only what fails; use policy generators.
Long-lived access keys for people.Habit from on-prem.SSO + temporary credentials.
Root/owner used daily.Convenience.Hardware MFA, no keys, break-glass only.
Thinking encryption replaces access control.Default encryption is transparent.Identity decides who reads; keys add a second lock.
Deleting a KMS key with data under it.Cleanup zeal.Disable first; deletion is irreversible after the waiting period.

Mini project: TiffinGo identity and encryption design

Goal: Redesign TiffinGo’s access and encryption from “admin keys everywhere” to least privilege.

Combines: 9.1–9.4 + 8.3 (OIDC).
