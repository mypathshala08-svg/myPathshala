2 Definition

cp, mv and rsync

Formal definition (write this in exams)

cp (copy) copies files, and with -r or -a whole directory trees, creating new files at the destination. mv (move) moves or renames files and directories; on the same file system it only changes directory entries, so the data is not copied. rsync (remote sync) copies files locally or between computers and, on later runs, transfers only files that are new or changed; it can also delete extra files at the destination to make an exact mirror.

In simple words

cp = make a copy, mv = move or rename, rsync = copy only what changed.

Copying, moving and syncing at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: photocopier, label, smart copier

Three everyday ideas.

  • cp is a photocopier: after it, you have two of the same thing.
  • mv just changes where a thing is or what it is called. Renaming a file is “moving” it to a new name.
  • rsync looks at the copy you already have and only adds what is new or changed.

Basic The commands you will type every day

  • cp a.txt b.txt copies a file; cp a.txt backup/ copies it into a folder, keeping its name.
  • cp -r project backup/: folders need -r (recursive).
  • mv old.txt new.txt renames; mv file.txt archive/ moves. mv works on folders without any option.
  • Both cp and mv overwrite an existing target without asking. Add -i to be asked.
  • rsync -av src/ dest/ copies a folder and, next time, only the changes.

Intermediate Attributes, safety and the trailing slash

  • Plain cp gives the copy a new date and makes you the owner. -p keeps date and permissions; -a (archive) keeps everything and copies folders, links included. Use -a for backups.
  • No overwrite: -i asks, --update=none skips (older -n), -u only replaces if the source is newer, --backup=numbered keeps the old one as file.~1~.
  • rsync’s slash rule: rsync -a src/ dest/ copies the contents of src; rsync -a src dest/ creates dest/src.
  • --delete removes files from the destination that are no longer in the source: an exact mirror. Always -n (--dry-run) first.

Advanced Behind the screen: why mv is instant

  • A folder is a list of names → inode numbers. On the same file system, mv calls rename(): it moves the name to another list. The data and inode do not move at all, which is why a 5 GB mv takes milliseconds (the inode number stays the same).
  • Across file systems (laptop → USB disk), rename() is impossible, so mv copies then deletes: just as slow as cp.
  • cp creates a new inode and copies the data block by block. Modern cp can use copy_file_range() or reflinks (--reflink=auto on Btrfs/XFS) to share blocks.
  • rename() is atomic: other programs see either the old or the new name, never half. That is why programs write file.tmp and then mv file.tmp file.
  • rsync decides “changed?” by size and modification time (quick check). With -c it compares checksums. Over a network it sends only the changed parts of a file (delta transfer).

Did you know? The rsync algorithm was the subject of Andrew Tridgell’s PhD thesis at the Australian National University. Its trick: the receiver sends checksums of blocks it already has, so the sender only transmits the blocks that differ. That is why rsync can update a huge file over a slow link by sending a few kilobytes.

EXAM> “Difference between cp and mv” → cp creates a copy and the original stays; mv moves or renames and the original name disappears; cp needs -r for directories, mv does not; on the same file system mv only changes directory entries (fast), across file systems it copies and deletes.
Quick check After cp report.txt backup/, how many report.txt files exist? After mv report.txt backup/?
Answer: cp: two (original and copy). mv: one, now inside backup/.

cp copy

🟡 Changes filesno sudo

Copies files. With -r it copies folders and everything inside; with -a it also keeps dates, permissions and links. The original is never changed.

✓ Use it when
  • you need a second copy and the original must stay
  • you take a quick backup before editing a file
  • you copy a whole folder once (-a or -r)
✗ Don’t use it when
  • you copy the same big folder again and again (use rsync)
  • you only want to move or rename (mv is instant)
  • you copy to another server (rsync or scp)

cp in software development

  1. Situation: Take a safety copy of a config file before editing it.

    echo "port=80" > app.conf
cp -v app.conf app.conf.bak
    'app.conf' -> 'app.conf.bak'

    Why this way: A .bak copy next to the file lets you undo your edit with cp app.conf.bak app.conf. -v confirms what was copied.

  2. Situation: Start a new project from a template folder.

    mkdir -p template/{src,tests} && touch template/README.md
cp -r template newapp && find newapp | sort
    newapp newapp/README.md newapp/src newapp/tests

    Why this way: -r copies the folder with everything inside. The new folder name is the destination.

cp in data administration

  1. Situation: Copy a dump into the backup folder, keeping its original date (so “newest backup” stays correct).

    echo 'dump' > night.sql && touch -d '2026-11-05 23:00' night.sql
cp night.sql b1.sql; cp -p night.sql b2.sql
for f in night b1 b2; do echo "$f.sql $(date -r $f.sql '+%F %H:%M')"; done
    night.sql 2026-11-05 23:00 b1.sql 2026-11-06 11:51 b2.sql 2026-11-05 23:00

    Why this way: Plain cp gives the copy the current time; -p keeps 23:00 of last night. Backup tools and clean-up scripts rely on these dates.

cp in system info / admin

  1. Situation: Copy a folder with all its permissions and dates, e.g. a home folder or website.

    mkdir -p site && echo hi > site/index.html && chmod 640 site/index.html
cp -a site site_copy && stat -c "%A %n" site/index.html site_copy/index.html
    -rw-r----- site/index.html -rw-r----- site_copy/index.html

    Why this way: -a keeps rw-r----- exactly. With plain cp -r, permissions are recalculated with your umask.

cp in data analysis / engineering

  1. Situation: Copy today’s CSV files into the input folder of a pipeline.

    touch sales_{north,south}.csv
mkdir -p input && cp -v sales_*.csv input/
    'sales_north.csv' -> 'input/sales_north.csv' 'sales_south.csv' -> 'input/sales_south.csv'

    Why this way: Several sources and a folder at the end. The wildcard is expanded by bash (Lesson 3.4).

cp in testing / qa

  1. Situation: Refresh test fixtures without destroying files a tester already changed by hand.

    mkdir -p fixtures && echo 'edited' > fixtures/users.csv
echo 'fresh' > users.csv
cp --update=none users.csv fixtures/
cat fixtures/users.csv
    edited

    Why this way: --update=none skips files that already exist. Old guides write -n; on Ubuntu 24.04 cp now warns that -n is non-portable.

cp in security

  1. Situation: Overwrite a config but keep every previous version for audit.

    echo v1 > fw.rules; echo v2 > new.rules
cp --backup=numbered new.rules fw.rules
echo v3 > new.rules; cp --backup=numbered new.rules fw.rules
ls fw.rules*
    fw.rules fw.rules.~1~ fw.rules.~2~

    Why this way: Each overwrite saves the previous file as .~1~, .~2~: you can see and restore exactly what changed.

cp in devops / cloud

  1. Situation: Copy a release into a numbered folder on the server.

    mkdir -p build && echo jar > build/app.jar
mkdir -p releases/v42 && cp -a build/. releases/v42/ && ls releases/v42
    app.jar

    Why this way: build/. means “the contents of build”, so files land directly in v42 (no extra build/ folder inside).

Common mistake
✗cp -n test_info.txt backup/ (Ubuntu 24.04 prints a warning)
✓cp --update=none test_info.txt backup/

Many notes still teach cp -n. It works, but coreutils 9.x warns: “behavior of -n is non-portable and may change in future; use --update=none instead”.

mv move

Moves files and folders to another place, or gives them a new name. The original name disappears. Folders need no option.

mv in system info / admin

  1. Situation: Rename a log file before the application starts a new one (manual log rotation).

    echo "old lines" > app.log
mv app.log app.log.1 && touch app.log
ls app.log*
    app.log app.log.1

    Why this way: This is what logrotate does every night (Lesson 18.1). The running program keeps writing to the renamed file until it reopens.

mv in devops / cloud

  1. Situation: Deploy a new config without any moment where the file is half-written.

    printf 'port=8080\nworkers=4\n' > app.conf.tmp
mv app.conf.tmp app.conf && cat app.conf

    Why this way: rename() is atomic: the app sees the old file or the new one, never a half-written one. Write to a temp name, then mv.

mv in data analysis / engineering

  1. Situation: Move processed files out of the incoming folder so they are not processed twice.

    mkdir -p incoming done && touch incoming/{a,b,c}.csv
mv incoming/*.csv done/ && ls incoming done
    done: a.csv b.csv c.csv incoming:

    Why this way: A classic pipeline pattern: incoming → processing → done (or failed). Moving is instant, even for big files.

mv in software development

  1. Situation: Rename a folder in a project.

    mkdir -p src/utils && touch src/utils/helpers.py

    src src/common src/common/helpers.py

    Why this way: Folders need no option. (In a git project use git mv so git records it as a rename.)

mv in testing / qa

  1. Situation: Check what mv does when the target exists, safely.

    echo a > a.txt; echo b > b.txt

mv in security

  1. Situation: Quarantine a suspicious file: take it out of the web folder without deleting the evidence.

    Why this way: Moving keeps the original data and inode for investigation; renaming to .txt and chmod 000 stop it from running or being served.

rsync remote sync

🟡 Changes filesno sudo

Copies files and folders like cp, but on every later run it sends only what is new or changed. It can mirror (delete extras), exclude patterns, show a preview, and work between computers.

✓ Use it when
  • you copy the same folder again and again (backups)
  • you need an exact mirror (--delete)
  • you copy to or from another server over SSH
✗ Don’t use it when
  • a one-time copy of a few files (cp is simpler)
  • rsync is not installed (sudo apt install rsync)
  • you are not sure about --delete and skipped --dry-run

Undo and safety net

What if a copy or move went wrong?

  • Overwrote a file with cp or mv: no undo. Only a backup, git or a snapshot helps. Prevent it with -i, --update=none, or --backup=numbered; many people add alias cp="cp -i" and alias mv="mv -i" to ~/.bashrc.
  • Moved something and cannot find it: mv into an existing folder puts it inside; into a new name renames it. Look with ls -lt in the target, or find ~ -name "name" (Lesson 7.1). Next time use mv -v.
  • Copied into the wrong place: just delete the copy (Lesson 3.3); the original is untouched.
  • rsync --delete removed files: they are gone from the destination. Restore from the source or another backup. Prevent with --dry-run, or --backup --backup-dir=../deleted, which keeps deleted files.
  • Preview before running: cp/mv: put echo in front to see the expanded names; rsync: -n.

    Fix: Add -r (or -a): cp -r test_data backup/.

  2. cp missing.txt backup/
    cp: cannot stat 'missing.txt': No such file or directory exit status: 1

    What it means: The source does not exist (typo, or wrong folder).

    Fix: Check with ls; use Tab completion so names are always right.

  3. touch a.txt
cp a.txt nofolder/
    cp: cannot create regular file 'nofolder/': Not a directory exit status: 1

    What it means: The destination ends with / but the folder does not exist.

    Fix: Create it first: mkdir -p nofolder.

  4. touch a.txt
cp a.txt a.txt
    cp: 'a.txt' and 'a.txt' are the same file exit status: 1

    What it means: Source and destination are the same file.

    Fix: Give a different name or folder.

  5. touch f.txt
mv f.txt /etc/
    mv: cannot move 'f.txt' to '/etc/f.txt': Permission denied exit status: 1

    What it means: You may not write into /etc.

    Fix: Use your own folders, or sudo if it is your server and really needed.

  6. mkdir -p d/sub
mv d d/sub/
    mv: cannot move 'd' to a subdirectory of itself, 'd/sub/d' exit status: 1

    What it means: A folder cannot be moved inside itself.

    Fix: Choose a destination outside the folder.

  1. 1. Look first

    ls -l source/ and ls -l dest/: what exists where?

    Behind the screen: reading folder entries only.

  2. 2. Choose the tool

    Need two copies → cp. Need it elsewhere → mv. Same copy again and again → rsync.

    Behind the screen: cp writes data; mv changes names; rsync compares first.

  3. 3. Add safety

    -i for cp and mv, --dry-run for rsync.

    Behind the screen: the tool checks before calling open() with truncation or unlink().

  4. 4. Run with -v

    cp -av, mv -v, rsync -av: you see every file.

    Behind the screen: the same work, with a line printed per file.

  5. 5. Check the result

    ls -l dest/, diff -r source dest (Lesson 6.3) or run rsync again: no files listed = identical.

    Behind the screen: a second rsync is a free verification.
Quick check What does cp -a keep that plain cp -r does not?
Answer: Timestamps, permissions, ownership (when allowed) and symbolic links as links. cp -r gives copies the current time and default permissions.
5 See it happen

What really moves when you copy, move and sync

Left: what Riya sees (times are illustrations). Right: what happens on the disk.

What really moves on the disk? 5 steps
What you see
  1. A big file has an inode number (shown by ls -i).
  2. cp reads and writes every byte, and the copy is a new file with a new inode.
  3. mv on the same disk finishes instantly and the inode number is unchanged.
  4. mv to a different disk is as slow as cp.
  5. Times are illustrations; the inode behaviour matches real runs.
Behind the screen
  1. A folder is a list of names pointing to inode numbers.
  2. cp creates a new inode and copies all data blocks.
  3. mv calls rename(): the name is removed from one list and added to another.
  4. Inodes belong to one file system, so across disks mv must copy, then delete.
  5. That is also why mv is atomic on one disk.

Under the hood: one system call for mv

The real file-related system calls of mv f d/ on our build machine. Three lines, and none of them reads or writes the data.

strace -e trace=%file,%desc mv f d/
renameat2(AT_FDCWD, "f", AT_FDCWD, "d/", RENAME_NOREPLACE) = -1 EEXIST (File exists) openat(AT_FDCWD, "d/", O_RDONLY|O_PATH|O_DIRECTORY) = 3 renameat2(AT_FDCWD, "f", 3, "f", RENAME_NOREPLACE) = 0

Recorded with strace on our Ubuntu build machine; library loading lines are hidden. You can run the same on your PC after sudo apt install strace.

First mv tries to rename f to the name d/ itself with RENAME_NOREPLACE (never overwrite); the kernel answers EEXIST because d already exists. So mv opens the folder d and renames f into it: renameat2(…, "f", 3, "f") = 0, done. No read or write of the data: the kernel only moves the name. Run the same with cp f d/ and you will see the file opened, the target created and the data copied.

Quick check Why is mv to a USB disk as slow as cp?
Answer: Inodes belong to one file system. Across file systems rename() is impossible, so mv copies the data and then deletes the original.
6 Real-world use

Copying, moving and syncing at work

1. Nightly backups

Servers sync data folders to a backup disk or server every night; only changes travel.

Night→rsync -a→fresh backup

2. Safe publishing

Programs write a temp file and mv it into place, so readers never see half a file. Data pipelines move files from incoming/ to done/.

Write tmp→mv→complete file

3. Deployments

Static sites and app releases are pushed with rsync over SSH; a release folder is switched with a link or mv.

Build→rsync -z→live

4. Before every edit

Admins copy a config to .bak before changing it, so a bad change is undone in one command.

Copy→edit→undo ready

5. Incident response

Security teams move suspicious files to quarantine instead of deleting them, keeping evidence intact.

Find→mv→investigate

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

One-liner corner

Small commands that save time. cp and mv lines were really run on our build machine.

Beginner

Quick backup with a date

Scenario: Copy a file with today’s date in the name before editing it.

echo x > app.conf && cp app.conf "app.conf.$(date +%Y)" && ls app.conf*
app.conf app.conf.2026

The shell builds the name; real scripts use %F for the full date.

Beginner

Swap two files

Scenario: Exchange the contents of a.txt and b.txt.

echo A > a.txt; echo B > b.txt; mv a.txt tmp && mv b.txt a.txt && mv tmp b.txt; cat a.txt b.txt
B A

A third, temporary name is needed; && stops if a step fails.

Intermediate

Copy only the folder structure

Scenario: Recreate the folders of a project without any files.

mkdir -p p/{a,b/c} && touch p/a/x p/b/c/y && (cd p && find . -type d -exec mkdir -p ../skeleton/{} \;) && find skeleton | sort
skeleton skeleton/a skeleton/b skeleton/b/c

find lists folders; mkdir -p recreates each one (Lesson 13.2).

Intermediate

Move everything except one file

Scenario: Archive all files but keep README.md.

touch a b README.md && mkdir -p old && shopt -s extglob
mv !(README.md|old) old/ && ls; ls old
README.md old a b

extglob’s !(…) = everything except (Lesson 3.4). It must be enabled on its own line first.

Advanced

Copy only newer files

Scenario: Update a folder with newer versions, leave the rest.

mkdir -p src dst && echo old > dst/a && sleep 1 && echo new > src/a && echo x > src/b && cp -uv src/* dst/
'src/a' -> 'dst/a' 'src/b' -> 'dst/b'

-u copies a only because src/a is newer, and b because it is missing.

Beginner

Build it step by step: a safe config update

Scenario: Riya must change the port in app.conf without any risk.

  1. 1. Backup first.

    printf 'port=80\n' > app.conf && cp -v app.conf app.conf.bak
    'app.conf' -> 'app.conf.bak'

  2. 2. Write the change to a temp file (sed: Lesson 6.4).

    printf 'port=80\n' > app.conf && cp app.conf app.conf.bak && sed 's/80/8080/' app.conf > app.conf.tmp && cat app.conf.tmp
    port=8080

  3. 3. Atomic switch with mv.

    printf 'port=80\n' > app.conf && cp app.conf app.conf.bak && sed 's/80/8080/' app.conf > app.conf.tmp && mv app.conf.tmp app.conf && cat app.conf
    port=8080

  4. 4. And the undo, if needed.

    printf 'port=80\n' > app.conf && cp app.conf app.conf.bak && sed 's/80/8080/' app.conf > app.conf.tmp && mv app.conf.tmp app.conf && cp app.conf.bak app.conf && cat app.conf
    port=80

Script it: backup.sh

A small but real backup script: dated folder, rsync with a preview, and a summary. (rsync is replaced by cp -a here because our browser runner has no rsync; the rsync line is in the comment.)

#!/bin/bash
# backup.sh SRC DEST: dated copy of SRC inside DEST
src=${1:-project}; dest=${2:-backups}
mkdir -p "$src/data" && echo "id,name" > "$src/data/students.csv"   # demo data
stamp=2026-11-06                     # real script: stamp=$(date +%F)
target="$dest/$stamp"
mkdir -p "$target"
cp -a "$src"/. "$target"/            # real script: rsync -a --delete "$src"/ "$target"/
echo "backed up $(find "$target" -type f | wc -l) file(s) to $target"
ls -R "$dest"
backed up 1 file(s) to backups/2026-11-06 backups: 2026-11-06 backups/2026-11-06: data backups/2026-11-06/data: students.csv

Copying "$src"/. means “the contents of src”, the same idea as rsync’s trailing slash.

Puzzle answer Remember the question from the story? Open to check your guess.

On the same disk, mv does not move any data. A folder is just a list of names pointing to inodes; mv calls rename(), which removes the name from one list and adds it to another. The 5 GB of data blocks and the inode stay exactly where they are (the inode number does not change). cp must read and write all 5 GB to make a new file. Across different disks, mv has to copy too.

Quick check You need yesterday’s backup folder updated with today’s changes. Which command, and how do you check before deleting anything?
Answer: rsync -av --delete --dry-run src/ backup/ to preview, then the same without --dry-run.
