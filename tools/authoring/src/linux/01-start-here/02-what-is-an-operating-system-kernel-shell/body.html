2 Definition

Operating system, kernel and shell

Formal definition (write this in exams)

An operating system (OS) is the system software that manages a computer’s hardware and provides common services to programs. Its core is the kernel, which runs with full hardware privileges and is responsible for process scheduling, memory management, file systems, device drivers, networking and security; programs request these services through system calls. A shell is a user-space program that provides an interface to the operating system, reading commands from a user or a script and executing them.

In simple words

The kernel is the boss of the hardware; everything else must ask it. The shell is the program that takes your typed commands to the kernel. The operating system is the kernel plus all the basic programs around it.

The operating system at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: an onion of layers

Think of every computer, phone or server as an onion. You only ever touch the outer skin. Every request you make travels inwards, and the answer comes back out.

  • Hardware (centre): the physical machine.
  • Kernel: the one program allowed to control the hardware.
  • Shell: the program that takes your typed request to the kernel.
  • Apps: browsers, games, Excel, the commands you run.
  • All of it together is the operating system plus your apps.

Basic A restaurant

  • Hardware is the kitchen equipment: stove, fridge, store room.
  • The kernel is the head chef who alone controls the kitchen. No customer walks into the kitchen; every order goes through the chef, who decides what is cooked when and keeps orders from mixing up.
  • The shell is the waiter: you tell it what you want, it carries the order in and brings the result back.
  • Programs (apps, commands) are the dishes on the menu. The operating system is the whole restaurant working together.

Intermediate The kernel’s five jobs, and where the shell fits

  • Process management: starts and stops programs and shares the CPU between them many times a second (scheduling).
  • Memory management: gives each program its own private memory and stops one program from reading another’s.
  • File systems: turns names like /home/riya/notes.txt into blocks on a disk, and checks permissions.
  • Devices: drivers for disks, keyboards, network cards, USB, GPUs.
  • Networking and security: TCP/IP, firewall rules, users and permissions.
  • The shell (usually bash) is not part of the kernel. It is an ordinary program that reads your commands and asks the kernel to run them. You can switch shells (bash, zsh, fish) without changing the kernel.

Advanced User space, kernel space and system calls

  • The CPU has privilege levels. The kernel runs in kernel space with full access to hardware; every program, including the shell and even programs run by root, runs in user space.
  • A program asks the kernel for anything (open a file, allocate memory, start a process, send a packet) through a system call: openat, read, write, fork/clone, execve, socket. A few hundred exist.
  • Linux is a monolithic kernel: drivers and file systems run inside the kernel for speed, but they can be loaded at run time as modules (lsmod, modprobe).
  • You can watch system calls live with strace and read kernel data in the virtual folder /proc. The “Run on your PC” panel below shows both.
  • Protection rings: on x86 the kernel runs in ring 0 and programs in ring 3 (ARM calls them exception levels EL1 and EL0). A system call is the controlled jump from ring 3 to ring 0 and back.
  • Interrupts: hardware (a key press, a network packet, a disk finishing a read, the timer) interrupts the CPU; the kernel runs a short handler in interrupt context, then usually wakes a waiting process. Code running for a process (for example inside a system call) runs in process context. See /proc/interrupts.
  • One address space, two halves: the kernel is mapped into the top of every process’s virtual address space, protected so that user mode cannot touch it; that makes system calls fast.
  • Preemption and SMP: Linux is a preemptive multitasking kernel: the scheduler can take the CPU away from a task at any time. It is also SMP: the kernel runs on all cores at once, which is why it uses locks such as spinlocks internally.

Did you know? The Linux kernel is one of the largest collaborative software projects ever: tens of millions of lines of code, with thousands of developers from hundreds of companies contributing to every release, and a new release roughly every nine to ten weeks.

Inside the Linux kernel: the architecture map

Linux is monolithic, but it is not a single blob. It is built from well-defined subsystems, each in its own folder of the source code. Programs reach all of them only through the system call interface.

Inside the Linux kernel: explore its subsystems

The diagram above is the classic map of the Linux kernel. Click each part to see what problem it solves, how it works, where its code lives in the kernel source tree, and a real window into it through /proc or /sys (recorded on our build machine).

Click a subsystem of the kernel.

Process scheduler who runs next

Why does it exist?

Hundreds of tasks want a few CPU cores. Someone must decide, thousands of times a second, which one runs and for how long.

How does it work?

Each runnable task waits in a per-CPU queue; the scheduler picks the next one by fairness and priority (nice). Since Linux 6.6 the default algorithm is EEVDF, which replaced the older CFS. Each switch is a context switch.

Where is it, really?

Source folder kernel/sched/. Counters in /proc/stat; tasks are task_struct objects inside the kernel.

Where is it used?

Explains load average, CPU-hungry jobs and why nice matters (Modules 11 and 18).

See this layer yourself (real output)

grep ctxt /proc/stat
ctxt 575692

Memory management who gets which RAM

Why does it exist?

Every program must believe it has its own private memory, and must not read or damage anyone else’s.

How does it work?

The kernel gives each process a virtual address space and maps it to real RAM in 4 KB pages using the CPU’s MMU. It uses spare RAM as a file cache, swaps rarely used pages to disk, and as a last resort runs the OOM killer.

Where is it, really?

Source folder mm/; page tables are set up by architecture code. Numbers in /proc/meminfo.

Where is it used?

Out-of-memory crashes, sizing servers, reading free correctly (Lesson 15.4).

See this layer yourself (real output)

grep -E '^(MemTotal|MemAvailable)' /proc/meminfo
MemTotal: 8214984 kB MemAvailable: 7673816 kB

Virtual file system (VFS) one interface for all disks

Why does it exist?

Disks use different formats (ext4, xfs, FAT, network shares). Programs should not care which.

How does it work?

Programs call open/read/write; the VFS translates them into calls to the right file-system driver, and keeps caches of names (dentries), inodes and file data (page cache).

Where is it, really?

Source folder fs/ (with fs/ext4/, fs/xfs/ …). Supported file systems are listed in /proc/filesystems.

Where is it used?

Mounting disks, USB sticks and network shares (Module 15); “everything is a file” (Lesson 2.1).

See this layer yourself (real output)

grep -v nodev /proc/filesystems
ext3 ext2 ext4 squashfs fuseblk xfs erofs btrfs

Block I/O layer queues disk requests

Why does it exist?

Disks are slow compared with the CPU. Requests should be merged and ordered so the disk works efficiently.

How does it work?

File-system requests become block requests; the layer merges neighbours, schedules them and hands them to the disk driver.

Where is it, really?

Source folder block/. Per-disk statistics in /proc/diskstats; disks listed by lsblk.

Where is it used?

Diagnosing slow disks with iostat (Lesson 18.3).

See this layer yourself (real output)

lsblk -d -o NAME,SIZE,TYPE | head -3
NAME SIZE TYPE zram0 0B disk vda 256G disk

Networking stack TCP/IP inside the kernel

Why does it exist?

Every web request, SSH session and database connection needs reliable delivery of packets.

How does it work?

Programs use sockets; the kernel implements TCP, UDP and IP, routes packets, applies firewall rules (netfilter) and talks to network-card drivers.

Where is it, really?

Source folder net/. Interface counters in /proc/net/dev.

Where is it used?

Ports, firewalls, slow-network debugging (Modules 16 and 19).

IPC processes talking to each other

Why does it exist?

Programs need to cooperate: pass data, send notifications, share memory.

How does it work?

The kernel provides pipes (|), signals (Ctrl+C), sockets, shared memory and message queues.

Source folders ipc/ and kernel/ (signals); pipes live in fs/pipe.c.

Security modules (LSM) extra rules on every access

Why does it exist?

Normal file permissions are not always enough; some systems need mandatory rules even for root.

How does it work?

The kernel calls security “hooks” before sensitive actions; modules such as SELinux or AppArmor answer allow or deny.

Where is it, really?

Source folder security/ (security/selinux/, security/apparmor/).

Where is it used?

SELinux on RHEL, AppArmor on Ubuntu (Lesson 19.2).

Device drivers talk to each piece of hardware

Why does it exist?

Thousands of different devices exist; each speaks its own language.

How does it work?

A driver translates generic kernel requests into commands for one kind of device. The kernel’s device model organises devices by bus (PCI, USB) and can load drivers as modules.

Where is it, really?

Source folder drivers/, the biggest part of the kernel. Buses visible in /sys/bus/.

Where is it used?

Why new hardware sometimes needs a newer kernel; lsmod and lspci (Lessons 18.5, 20.1).

See this layer yourself (real output)

acpi clockevents clocksource container cpu

Architecture code CPU-specific glue

Why does it exist?

Intel/AMD, ARM and RISC-V CPUs start, handle interrupts and manage page tables differently.

How does it work?

A thin layer per CPU family does boot set-up, interrupt entry, context switches and page-table handling, so everything above can stay generic.

Where is it, really?

Source folder arch/ (arch/x86/, arch/arm64/, arch/riscv/).

Where is it used?

The reason one kernel runs on laptops, phones and Raspberry Pis.

x86_64

4 Step by step

From Unix to Linux in six steps

Linux makes much more sense once you know where its ideas came from. Each step says why it still matters to you.

  1. 1969 · Unix at Bell Labs

    Bell Labs had left Multics, a large and ambitious operating system project. Ken Thompson and Dennis Ritchie wrote a much smaller system on a spare computer and called it Unix. Ideas: small tools that do one thing well, everything is a file, a shell to join tools together. Unix measures time in seconds since 1 January 1970, the “Unix epoch”, still used by every Linux system today (date +%s).

    Why it matters: pipes (|), files for everything and small commands are exactly what you will use in Modules 2–6.

  2. 1973 · Rewritten in C

    Unix is rewritten in the new C language, so it can be moved to other kinds of computers. Universities get the source code.

    Why it matters: portability is why the same Linux runs on phones, laptops and supercomputers today.

  3. 1970s–80s · Many Unixes

    Universities create BSD; companies sell their own versions (Solaris, HP-UX, AIX). Unix is powerful but expensive and closed.

    Why it matters: banks and telecoms still run some of these. The POSIX standard keeps them similar, so your skills carry over.

  4. 1983 · The GNU project

    Richard Stallman starts GNU to build a completely free Unix-like system and the GPL licence to keep it free. By 1991 GNU has a compiler, a shell (bash, 1989) and core tools, but no finished kernel.

    Why it matters: bash, ls, grep and gcc on your Linux come from GNU.

  5. 1991 · Linus writes a kernel

    Linus Torvalds, a student in Helsinki who had been using Andrew Tanenbaum’s teaching system MINIX, announces a “hobby” kernel on 25 August 1991. Combined with the GNU tools, it becomes a complete free OS. In 1992 the kernel is released under the GPL, and version 1.0 arrives in March 1994.

    Why it matters: thousands of volunteers and companies can improve the same kernel, which is why it grew so fast.

  6. Today · Linux everywhere

    Distributions (Debian 1993, Red Hat 1994, Ubuntu 2004), Android (2008) and the cloud put the Linux kernel on billions of devices.

    Why it matters: whatever IT role you take, from data engineering to DevOps, you will work on Linux machines.
Quick check Linux was written in 1991. Does it contain the original Unix code from Bell Labs?
Answer: No. Linux was written from scratch. It follows Unix’s design and the POSIX standard, which is why it is called Unix-like.
5 See it happen

What the kernel does while ls runs

Left: the terminal. Right: bash and ls (user space) asking the kernel (kernel space) for everything. The dashed line is the wall between them.

User space asks, kernel space does 6 steps
What you see
  1. Riya types ls and presses Enter.
  2. Nothing visible yet.
  3. Still nothing visible: this all takes microseconds.
  4. Still working behind the screen.
  5. Three names appear.
  6. The command is over and bash is ready again.
Behind the screen
  1. bash looks at the first word. ls is not built into bash, so it searches the folders in PATH and finds the program file /usr/bin/ls.
  2. bash asks the kernel to create a child process (clone, the modern fork) and to run ls in it (execve). Only the kernel can start programs.
  3. ls cannot read the disk itself. It makes system calls: open the current directory, then getdents64 = “get the directory entries”.
  4. The kernel’s file-system code reads the directory from disk, or from RAM if it was read recently (the page cache), and copies the names into ls’s memory.
  5. ls sorts the names and calls write on file descriptor 1 (its output). The kernel passes the bytes to the terminal, which draws them.
  6. ls exits. The kernel frees its memory and tells bash, which was waiting. You can see every one of these calls with strace ls.

Four real-time scenarios: the scheduler sharing one CPU, memory protection when an app crashes, one kernel powering very different devices, and a hardware interrupt.

Real-time scenario 1

Music, browser and a download on one CPU core

Riya plays music while browsing and downloading. Each coloured block is a tiny time slice of one CPU core. Simplified, but this is really how the kernel shares a CPU.

The kernel’s scheduler at work 5 steps
Animated example
  1. With one program, it can use every slice of CPU time.
  2. When the browser starts, the kernel alternates between the two, switching every few milliseconds.
  3. A download joins. Now three programs take turns on one core. To Riya, all three seem to run at once.
  4. The scheduler is fair but smart: the music player wakes up often enough that sound never stutters.
  5. Sharing the CPU is the kernel’s job. No program can grab the CPU forever, which is why one busy program does not freeze a well-run Linux machine.
Real-time scenario 2

One program crashes, the others carry on

Why does a crashing app not take down your whole computer? Because the kernel gives each process its own memory and enforces the walls.

Memory protection 5 steps
Animated example
  1. Every process gets its own private memory. It cannot even see the others’ memory.
  2. A bug (for example a bad pointer in C) makes one program try to write somewhere it does not own.
  3. The CPU detects it and hands control to the kernel, which kills that one process. You see “Segmentation fault”.
  4. The other programs keep running untouched. Restart the buggy app and carry on.
  5. This isolation is why one bad service rarely brings down a Linux server. A bug in the kernel is different: it can stop everything (a kernel panic).
Real-time scenario 3 · advanced

One kernel, very different systems

The same Linux kernel is compiled for servers, phones, routers and supercomputers. What changes is the user space on top and the drivers built in.

One kernel, many user spaces 5 steps
Animated example
  1. The Linux kernel is one open-source project, developed at kernel.org by thousands of people.
  2. A server distribution such as Ubuntu adds the GNU tools, bash and a package manager.
  3. Android adds its own very different user space (apps, Java/Kotlin runtime). There is no bash in the user’s view, but the kernel is Linux.
  4. Routers, smart TVs and supercomputers build the kernel with the drivers they need and add a small or specialised user space.
  5. This is why “Linux” can mean a kernel or a whole system. In this course we work with server distributions, mostly Ubuntu and RHEL-family.
Real-time scenario 4 · advanced

You press a key: an interrupt, step by step

How does bash notice your key press when another program is using the CPU? Hardware interrupts. Simplified, but this is the real sequence.

Hardware interrupts 5 steps
Animated example
  1. A game is running on the CPU core. bash is not running at all: it is asleep in the kernel, waiting for input.
  2. You press a key. The keyboard controller raises an interrupt, a hardware signal to the CPU.
  3. The CPU saves what the game was doing and jumps to the kernel’s interrupt handler, which quickly reads the key code. This runs in interrupt context: fast and short.
  4. The kernel passes the key to the terminal layer and marks bash as runnable. The scheduler will give it a turn.
  5. The CPU returns to the game. Moments later bash runs and shows your character. The same mechanism handles network packets, disk completions and the timer tick. Count them in /proc/interrupts.

Why does it exist?

Someone has to understand the text you typed and decide which program to run.

How does it work?

Program: ls the tool that lists

Why does it exist?

Each job is done by a small specialised program, the Unix idea from 1969.

How does it work?

ls asks for the names in a folder, sorts them and prints them. It never reads the disk directly.

Where is it, really?

/usr/bin/ls from GNU coreutils, a compiled C program.

Where is it used?

Many thousands of times a day by every Linux user.

C library (glibc) the polite translator

Why does it exist?

Making raw system calls is fiddly. Almost every program uses a shared library of ready-made functions that make the calls for it.

How does it work?

ls calls library functions such as opendir() and readdir(); glibc turns them into the real system calls.

Where is it, really?

libc.so.6 in /lib/x86_64-linux-gnu/, shared by nearly every program. ldd shows which libraries a program needs.

Where is it used?

Under almost every Linux program. (Alpine Linux uses a different one, musl: Lesson 1.3.)

System call interface the only door into the kernel

Why does it exist?

User programs must never control hardware directly. One guarded doorway keeps them safe from each other.

How does it work?

The CPU switches from user mode to kernel mode, the kernel does the work, and switches back. ls passes through this door well over a hundred times.

Where is it, really?

Part of the kernel: a table of a few hundred numbered calls (openat, getdents64, write, execve…).

Where is it used?

Debugging with strace: “which file is this program actually opening?”

Kernel: file-system code turns names into disk blocks

Why does it exist?

Different disks use different formats (ext4, xfs, FAT). Programs should not need to know which.

How does it work?

The kernel’s virtual file system (VFS) passes the request to the right file-system driver, here ext4, which knows where the folder’s entries sit on disk, often already cached in RAM.

Where is it, really?

Inside the kernel image /boot/vmlinuz-…, or as a module in /lib/modules/.

Where is it used?

Every file operation on every Linux machine. Admins choose and tune file systems in Module 15.

Why does it exist?

Data has to physically live somewhere and instructions have to run on something.

Real or virtual devices; the kernel shows them as block devices such as /dev/vda or /dev/nvme0n1.

6 Real-world use

Why this knowledge pays off at work

1. “My job was killed!”: reading the kernel’s mind

A data pipeline on a server suddenly dies with the word “Killed”. A developer who knows the kernel checks its log and sees the out-of-memory killer stopped the job. Fix: more memory or a smaller batch, not random restarts.

Job dies→Kernel log (dmesg)→OOM found→Right fix

2. Which config file is this program reading?

An app ignores your settings. strace shows every file it asks the kernel to open, revealing it reads a different path. A classic production debugging trick.

App misbehaves→strace system calls→Wrong path seen

3. Choosing the right server size

Knowing that the kernel shares CPU cores and RAM between processes helps you size cloud servers sensibly: how many cores for parallel jobs, how much RAM so nothing is killed.

Workload→cores + RAM→Cloud VM size

4. Containers are a kernel feature

Docker containers are not small virtual machines. They are ordinary processes that the Linux kernel isolates (namespaces) and limits (cgroups). Module 20 shows how.

docker run→kernel namespaces + cgroups→isolated app

5. Phones, cars and IoT

Embedded engineers configure and build the Linux kernel for devices such as phones, car dashboards and smart meters, choosing only the drivers the hardware needs.

Device hardware→custom kernel build→Product

One-liner corner

Commands that ask the kernel and the shell about themselves. All were really run; on your machine names and numbers will differ.

Beginner

Which kernel am I running?

Scenario: A bug report asks for your kernel version. You need it in one line.

uname -sr
Linux 6.18.44-fc-v236

uname prints system information from the kernel: -s kernel name, -r kernel release. Add -m for the CPU architecture.

Beginner

Is this command part of the shell or a separate program?

Scenario: You wonder why cd has no file in /usr/bin while ls does.

type cd ls
cd is a shell builtin ls is /usr/bin/ls

type asks bash how it would run a name. Builtins live inside bash; others are program files that the kernel must start.

Intermediate

How many CPU cores and how much RAM, straight from the kernel

Scenario: Before running a heavy job you want to know the machine’s size without any GUI.

echo "cores: $(nproc), RAM: $(awk '/MemTotal/ {printf "%.1f GB", $2/1048576}' /proc/meminfo)"
cores: 2, RAM: 7.8 GB

/proc/meminfo is not a real file: the kernel generates it when you read it. awk picks the MemTotal line and converts kB to GB.

Advanced

Count the system calls a command makes

Scenario: You want proof that even a tiny command talks to the kernel a lot.

strace -c ls 2>&1 >/dev/null | tail -1
100.00 0.002447 16 146 17 total

strace -c counts every system call and prints a summary on stderr; 2>&1 >/dev/null sends that summary into the pipe and throws away ls’s own output. Here ls made well over a hundred calls to list one folder. (strace must be installed: sudo apt install strace.)

Intermediate

Build it step by step: how many processes are running right now?

Scenario: Kabir wants to know how busy the machine is, using only what the kernel shows in /proc. Build the answer one stage at a time.

  1. Look first: /proc is a virtual folder made by the kernel. Each numbered folder is one running process.

    ls /proc | head -5
    1 10 13 14 15

  2. Keep only names made of digits: those are process IDs.

    ls /proc | grep -E '^[0-9]+$' | head -3
    1 10 13

  3. Count them.

    ls /proc | grep -E '^[0-9]+$' | wc -l
    74

  4. Label it: a finished health-check line. (Your number will be different every time.)

    echo "Processes running: $(ls /proc | grep -E '^[0-9]+$' | wc -l)"
    Processes running: 75

The kernel reads the folder. bash asks the kernel to start ls; ls asks the kernel (through the C library and system calls such as openat and getdents64) for the folder’s entries; the kernel’s file-system code fetches them from the disk or its cache. The proof is one command: strace ls prints every request ls makes to the kernel, as you saw in the dissection above.
