The problem

Every night at 1 a.m. Riya’s report job compresses gigabytes of logs and uses all the CPU. Customers in other time zones complain that the website is slow at that hour. She does not want to kill the job, only make it polite: run at full speed when the machine is idle, and step aside when the web server needs the CPU. Linux lets every process have a nice value from −20 (greedy) to 19 (very polite). nice starts a command with a value, renice changes it for a running process, and ionice does the same for disk access. This lesson shows the real effect with measured numbers.

By the end of this page you will be able to:
  • explain nice values (−20 to 19), priority (PRI/PR) and who may raise or lower them
  • start commands with nice -n, change running processes with renice -n -p / -u / -g
  • read NI and PR in ps and top, and measure the effect when two processes compete for one CPU
  • use ionice classes for disk-heavy jobs and know when to use cgroups, chrt or taskset instead

2 Definition

Nice values, nice, renice and ionice

Formal definition (write this in exams)

The nice value (niceness) of a process, from −20 to 19, tells the CPU scheduler how large a share of CPU time the process should get when processes compete; higher values mean a smaller share. nice runs a command with a given niceness, renice changes the niceness of running processes, users or groups, and ionice sets the I/O scheduling class and priority for disk access.

In simple words

A politeness number for the CPU (nice) and the disk (ionice).

Basic What you will type

  • nice -n 19 ./backup.sh: start politely.
  • renice -n 15 -p 4120: change a running process.
  • ps -o pid,ni,cmd -p 4120: check the NI column.
  • In top, press r to renice.

Intermediate Rules and numbers

  • Range −20 … 19; default 0; children inherit the parent’s value.
  • nice cmd without -n adds 10.
  • Normal users may only increase niceness, and cannot decrease it again (even back to the old value). Root may do both. Limits can be relaxed in /etc/security/limits.conf (nice item).
  • ps shows NI and PRI (PRI = 19 − NI with -o pri); top shows PR = 20 + NI.
  • ionice classes: 1 realtime (root), 2 best-effort with levels 0–7 (default derived from nice), 3 idle (only when the disk is free).

Advanced Behind the screen: weights in the scheduler

  • The Linux scheduler (CFS, and EEVDF since kernel 6.6) gives each runnable task a weight from its nice value: nice 0 = 1024, each step is about ×1.25. Nice 19 = 15, nice −20 = 88761.
  • CPU time is shared in proportion to weights: nice 0 vs nice 19 on one CPU ≈ 1024 : 15, about 98.5% vs 1.5%. That is what we measure below.
  • With autogroup (desktop kernels), nice works only between processes of the same session/group; across groups, groups are shared fairly.
  • Real-time policies (SCHED_FIFO, SCHED_RR via chrt) run before all normal tasks; nice does not apply to them.
  • For hard limits use cgroups v2: cpu.max (quota) and cpu.weight; systemd exposes them as CPUQuota= and CPUWeight=.
  • ionice only has an effect with I/O schedulers that support classes (BFQ; partly mq-deadline). On many NVMe disks with “none” it does little.

Did you know? A nice-19 process competing with a nice-0 process on one CPU gets about 1.5% of the time, not 50% less: the weights are 15 vs 1024. We measured 1.3% vs 97.3% on our build machine.

EXAM> “What is the range of nice values and the default?” → −20 (highest priority) to 19 (lowest); default 0. Only root can set negative values.
Quick check A user ran renice -n 19 on her job. Can she set it back to 0?
Answer: No. Unprivileged users may only increase niceness; going back down needs root (or a limits.conf rule).
Common mistake
✗expecting nice to make a job slower on an idle machine
✓nice only changes the share when others compete; for a hard cap use systemd-run -p CPUQuota=20% or cgroups

On an idle server a nice-19 job still uses ~100% CPU (the puzzle). That is correct: unused CPU is not wasted.

Common mistake
✗nice for disk-heavy jobs only
✓ionice -c3 nice -n 19 cmd (both CPU and disk)

nice affects the CPU scheduler; disk I/O needs ionice (and a scheduler that supports it).

renice -n N -p PID · -u user · -g pgrp change a running process

🟡 Changes filesno sudo

✓ Use it when

ionice [-c class] [-n level] cmd · ionice -p PID disk priority

🟢 Read-onlyno sudo

Undo and safety net

Niceness can always be raised; lowering it needs root.

  • Made my job too slow: ask root: sudo renice -n 0 -p PID, or restart it without nice.
  • A user’s jobs hurt the server: sudo renice -n 15 -u user; long term: cgroups / systemd slices.
  • Disk still busy: add ionice -c3; check the scheduler.
  • Need a hard limit: systemd-run --scope -p CPUQuota=20% cmd.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. renice -n -5 -p $$
    renice: failed to set priority for 27373 (process ID): Permission denied exit status: 1

    What it means: Lower values need root.

    Fix: sudo, or a limits.conf rule.

  2. nice -n -5 true
    nice: cannot set niceness: Permission denied exit status: 0

    What it means: Warning only: the command still runs at the current value.

    Fix: sudo nice -n -5 cmd.

  3. renice -n 5 -p 999999
    renice: failed to get priority for 999999 (process ID): No such process exit status: 1

    What it means: No such process.

    Fix: Find the PID with pgrep.

  4. ionice -c1 true
    ionice: ioprio_set failed: Operation not permitted exit status: 1

    What it means: Realtime I/O class needs root.

    Fix: Use -c2 or -c3.

for n in 10 19; do taskset -c 0 timeout 3 sh -c "while :; do :; done" & taskset -c 0 nice -n $n timeout 3 sh -c "while :; do :; done" & sleep 2.5; ps -o ni=,%cpu=,args= -u riya | grep '[w]hile' | grep -v timeout | awk '{printf "  nice %2s: %5s%%\n", $1, $2}'; wait; done
nice 0: 89.6% nice 10: 9.6% nice 0: 97.2% nice 19: 1.2%

Each extra step of nice shrinks the share by about 1.25×.

renice

V6

Renice several PIDs at once

sleep 30 & a=$!; sleep 31 & b=$!; renice -n 8 -p $a $b | sed -E 's/[0-9]{3,}/PID/'; kill $a $b
PID (process ID) old priority 0, new priority 8 PID (process ID) old priority 0, new priority 8

V7

Renice your own user

sleep 30 & p=$!; renice -n 4 -u riya > /dev/null 2>&1; ps -o ni= -p $p; kill $p
4

-u riya changes all of riya’s processes (including this shell).

V8

Renice a process group (a whole pipeline)

set -m; sleep 30 | sleep 31 & sleep 0.2; g=$(ps -o pgid= -p $! | tr -d ' '); renice -n 6 -g $g > /dev/null; ps -o ni= -g $g | sort -u | tr -d ' '; kill %1

-g: every process in the job.

ionice and friends

V10

Default I/O class follows nice

for n in 0 19; do nice -n $n bash -c 'ionice -p $$' | sed "s/^/nice $n: /"; done
nice 0: none: prio 0 nice 19: none: prio 0

ionice -p shows only a class that was set explicitly (none here); the kernel then derives a best-effort level from the nice value.

V11

Idle I/O for a copy

cd ~/nc; ionice -c3 cp big.bin copy.bin && cmp -s big.bin copy.bin && echo 'copied at idle I/O priority'
copied at idle I/O priority

Same result, lower priority.

V13

Scheduling policy

chrt -p $$ | sed -E 's/[0-9]{3,}/PID/'

SCHED_OTHER = normal; nice applies only here.

V14

A hard limit needs cgroups (shown)

echo 'systemd-run --user --scope -p CPUQuota=20% ./report.sh   # never more than 20% of one CPU'
systemd-run --user --scope -p CPUQuota=20% ./report.sh # never more than 20% of one CPU

Nice is soft; CPUQuota is a cap (Lesson 20.3).

Script it: politeness.sh

Report every process of the current user with a non-zero nice value or non-default I/O class, then make all running sleep processes of the user polite (nice 15, idle I/O).

pkill -u "$USER" -x sleep; nice -n 6 sleep 20 & ionice -c3 sleep 21 & sleep 0.2      # demo processes
printf '%4s  %-14s %s\n' NI IO COMMAND
for p in $(pgrep -u "$USER"); do
  ni=$(ps -o ni= -p "$p" 2>/dev/null | tr -d ' ') || continue
  io=$(ionice -p "$p" 2>/dev/null | cut -d: -f1)
  [ "$ni" != 0 ] || [ "$io" != none ] && [ -n "$ni" ]  && printf '%4s  %-14s %s\n' "$ni" "$io" "$(ps -o comm= -p "$p")"
done
for p in $(pgrep -u "$USER" -x sleep); do renice -n 15 -p "$p" > /dev/null 2>&1; ionice -c3 -p "$p"; done
echo "sleep processes now: $(ps -o ni= -p "$(pgrep -d, -u "$USER" -x sleep)" | sort -u | tr -d ' \n' | sed 's/^/nice /')"
pkill -u "$USER" -x sleep
NI IO COMMAND 4 none sleep 6 none sleep 0 idle sleep sleep processes now: nice 15

It starts two demo sleep processes first.

Puzzle answer Remember the question from the story? Open to check your guess.

1. Nice is a share under competition, not a speed limit: on an idle server nothing else wants the CPU, so the nice-19 job correctly gets almost 100% (we measured it). When the web server is busy, the job gets ~1.5%. 2. Normal users may only raise niceness; going from 19 back to 5 is lowering it, which needs root (or a nice limit in limits.conf). 3. nice is for the CPU scheduler; the tar job was limited by the disk. Use ionice -c3 nice -n 19 tar …, and for real caps use cgroups (systemd IOWeight=, CPUQuota=).
