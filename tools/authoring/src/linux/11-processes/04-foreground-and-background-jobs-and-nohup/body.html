The problem

Riya starts a 40-minute backup over SSH, then needs her terminal for something else. She presses Ctrl+Z by accident and the progress freezes. Later she closes the laptop lid, the SSH session drops and the backup dies with it. The shell has job control for exactly this: run a command in the background with &, pause it with Ctrl+Z, list jobs with jobs, continue them with bg and fg. To survive logout she needs nohup, disown or setsid (or tmux, Lesson 11.6). This lesson shows each one on real terminal screens.

By the end of this page you will be able to:
  • run commands in the background with &, and see them with jobs, jobs -l and $!
  • pause with Ctrl+Z, continue with bg and fg, and refer to jobs with %1, %+, %- and %name
  • explain why closing a terminal kills its jobs (SIGHUP), and keep work alive with nohup, disown and setsid
  • handle background output, wait for jobs in scripts, and avoid the common traps

2 Definition

Jobs, job control and nohup

Formal definition (write this in exams)

A job is a command or pipeline started from an interactive shell, tracked by a job number. Job control lets the user run jobs in the foreground (attached to the keyboard) or the background (&), stop them (Ctrl+Z) and move them with bg, fg and jobs. nohup runs a command immune to SIGHUP, and disown removes a job from the shell so it survives logout.

In simple words

Several jobs per terminal; one in front, the others behind; keep the ones that must outlive you away from the hang-up.

Very basic No jargon: a kitchen

One dish in front of you, others simmering behind.

Basic What you will type

  • sleep 100 &: start in the background; you get [1] 4120 (job 1, PID 4120).
  • jobs: list jobs of this terminal.
  • Ctrl+Z then bg: continue a job in the background.
  • fg: bring the last job back to the front.

Intermediate Job numbers and logout

  • Refer to jobs as %1, %2, %+ (current, also %%), %- (previous) or %sle (name starts with).
  • $! is the PID of the last background job; wait waits for jobs; kill %1 signals a job.
  • On logout or terminal close, bash sends SIGHUP to its jobs (and SIGCONT to stopped ones so they can die).
  • nohup cmd sets HUP to “ignore” and redirects output to nohup.out if it is a terminal.
  • disown removes a job from the shell’s table so it is not sent HUP; disown -h keeps it listed but skips the HUP.

Advanced Behind the screen: sessions and process groups

  • Each pipeline you start is a process group. The terminal has one foreground process group: only it may read the keyboard, and Ctrl+C / Ctrl+Z go to the whole group.
  • A background job that tries to read the terminal gets SIGTTIN and stops (“Stopped (tty input)”); writing is allowed unless stty tostop.
  • The shell, its jobs and the terminal form a session; the shell is the session leader. When the terminal hangs up, the kernel sends SIGHUP to the leader, and bash forwards it to its jobs.
  • setsid cmd starts cmd in a new session with no terminal: it never receives the terminal’s HUP.
  • Scripts run with job control off (set +m): no %job notifications, and fg/bg fail with “no job control”, but &, $!, jobs and wait work.
  • systemd-logind can also kill user processes at logout (KillUserProcesses=); on Ubuntu it is off by default.

Did you know? “Hang-up” is a real telephone word: Unix terminals were connected by modems, and when the phone line dropped the modem signalled a hang-up. The signal kept the name for 50 years; today it fires when an SSH connection drops or a terminal window closes.

EXAM> “What is the difference between nohup and &?” → & runs a job in the background but it still receives SIGHUP on logout; nohup makes the command ignore SIGHUP (usually combined: nohup cmd &).
Quick check Does Ctrl+Z end a program?
Answer: No. It stops (pauses) it; fg or bg continues it. Ctrl+C is the one that interrupts.
Common mistake
✗cmd & then log out, expecting it to keep running
✓nohup cmd > cmd.log 2>&1 & · or cmd & disown · or run it inside tmux

A plain background job still gets SIGHUP when the terminal closes (real run: the sleep died).

Common mistake
✗kill 1 to stop job 1
✓kill %1

Without %, 1 is PID 1 (systemd): “Operation not permitted” as a user, a disaster as root.

cmd & · $! · jobs [-l|-p] · wait background jobs

🟢 Read-onlyno sudo

A & at the end runs the command in the background; the shell prints the job number and PID and returns the prompt. $! holds the PID. Background jobs still write to the terminal, so redirect their output. wait waits for all background jobs (or one PID) and returns its exit status.

✓ Use it when
  • long commands you do not need to watch
  • starting several tasks at once
✗ Don’t use it when
  • commands that ask for input
  • forgetting where the output goes

Syntax: cmd > log 2>&1 & · pid=$! · wait $pid

sleep 300the command> log 2>&1keep output off the screen&run in the background

The & comes last. Redirect output so it does not mix with your typing.

Ctrl+Z · bg [%n] · fg [%n] · %+ %- %name stop, continue and switch

🟢 Read-onlyno sudo

✓ Use it when
  • moving between tasks in one terminal
  • pausing something to free the terminal
✗ Don’t use it when
  • scripts (job control is off)
  • stopping jobs that hold locks for others

nohup cmd & · disown [-h] [%n] · setsid cmd surviving logout

🟢 Read-onlyno sudo

nohup makes the command ignore SIGHUP and, if output is a terminal, appends it to nohup.out. disown works on a job that is already running. setsid starts the command in a new session without a terminal. In all cases, redirect output to a log file yourself.

✓ Use it when
  • long downloads, builds, backups over SSH
  • a job you forgot to start with nohup
✗ Don’t use it when
  • services that should restart on failure (use systemd)
  • work you want to watch later (use tmux)

Undo and safety net

A job killed by logout is gone; rerun it properly.

  • Stopped with Ctrl+Z by mistake: fg (or bg).
  • Job died at logout: restart with nohup … &, or inside tmux.
  • nohup.out is huge: : > nohup.out empties it; next time redirect to a log you rotate.
  • “There are stopped jobs” when exiting: type jobs, then fg/kill them; exiting again kills them.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. fg
    /home/riya/script.sh: line 1: fg: no job control exit status: 1

    What it means: No job control in a script (or no jobs).

    Fix: Use an interactive shell; in scripts use wait.

  2. set -m; fg %3
    /home/riya/script.sh: line 1: fg: %3: no such job exit status: 1

    What it means: There is no job 3.

    Fix: jobs to see the numbers.

  3. kill %1
    /home/riya/script.sh: line 1: kill: %1: no such job exit status: 1

    What it means: No job 1 in this shell.

    Fix: jobs -l; or kill the PID.

  4. wait 999999
    /home/riya/script.sh: line 1: wait: pid 999999 is not a child of this shell exit status: 127

    What it means: Not a child of this shell.

    Fix: wait only for your own background jobs.

Anything that should always run (an API, a worker) becomes a systemd service, not a nohup job (Lesson 17.3).

Prototype nohup→systemd→production

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

One-liner corner

Small, useful commands. All really run on our build machine.

Beginner

Start and remember the PID

Scenario: Stop it later.

sleep 30 & echo $! > ~/job.pid; kill "$(cat ~/job.pid)"; rm ~/job.pid; echo stopped
stopped

$! right after &.

Beginner

How many jobs?

Scenario: Before exit.

sleep 10 & sleep 11 & jobs | wc -l; kill $(jobs -p)
2

2.

Intermediate

Safe long job

Scenario: Over SSH.

cd ~/jb; nohup bash -c 'sleep 0.2; echo ok' > long.log 2>&1 & wait; cat long.log
ok

nohup + log + &.

Intermediate

Fail if any part fails

Scenario: CI.

pids=(); for c in true false true; do $c & pids+=($!); done; fail=0; for p in "${pids[@]}"; do wait $p || fail=$((fail+1)); done; echo "$fail failed"
1 failed

wait each PID.

Advanced

Detach completely

Scenario: Fire and forget.

setsid -f bash -c 'sleep 0.1' < /dev/null > /dev/null 2>&1; echo "returned at once, status $?"
returned at once, status 0

setsid -f forks into a new session.

Beginner

Build it step by step: a parallel backup

Scenario: Riya turns a slow serial backup into a parallel, logout-safe one.

  1. 1. One after another (sleep stands in for a slow disk).

    cd ~/jb; s=$SECONDS; for d in a b c; do tar czf $d.tgz -C src $d; sleep 1; done; echo "serial: $((SECONDS-s)) s"
    serial: 3 s

  2. 2. In parallel with & and wait.

    cd ~/jb; s=$SECONDS; for d in a b c; do ( tar czf $d.tgz -C src $d; sleep 1 ) & done; wait; echo "parallel: $((SECONDS-s)) s"
    parallel: 1 s

  3. 3. A log of each part.

    cd ~/jb; for d in a b c; do ( tar czf $d.tgz -C src $d && echo "$d ok" || echo "$d FAILED" ) >> backup.log 2>&1 & done; wait; sort backup.log
    a ok b ok c ok

  4. 4. The whole thing under nohup: safe to log out.

    cd ~/jb; rm -f backup.log; nohup bash -c 'for d in a b c; do tar czf $d.tgz -C src $d & done; wait; echo all done' > backup.log 2>&1 & wait; cat backup.log
    all done

More examples and variations

Sixteen more experiments with jobs, wait and nohup. All were really run on our build machine.

Background and wait

V1

Two downloads at once (simulated)

( sleep 0.4; echo 'a.iso done' ) & ( sleep 0.2; echo 'b.iso done' ) & wait; echo 'both finished'
b.iso done a.iso done both finished

Output appears in the order the jobs finish.

V2

wait -n: react to the first finisher

( sleep 0.5; exit 1 ) & ( sleep 0.1; exit 0 ) & wait -n; echo "first finished with $?"; wait
first finished with 0

Useful for a pool of workers.

V3

Limit to N jobs at a time

for i in 1 2 3 4 5 6; do ( sleep 0.2; echo "task $i" ) & (( $(jobs -rp | wc -l) >= 2 )) && wait -n; done; wait
task 1 task 2 task 3 task 4 task 5 task 6

At most two jobs run at the same time.

V4

A spinner while a job works

( sleep 1 ) & p=$!; n=0; while kill -0 $p 2>/dev/null; do n=$((n+1)); sleep 0.2; done; echo "job done after about $n checks"
job done after about 5 checks

kill -0 polls the job (Lesson 11.3).

V5

Background output mixed with yours

( for i in 1 2 3; do echo "  bg line $i"; sleep 0.1; done ) & echo 'you keep typing...'; wait
you keep typing... bg line 1 bg line 2 bg line 3

The reason to redirect background output.

V6

Kill all my jobs at the end

sleep 30 & sleep 31 & echo "jobs: $(jobs -p | wc -l)"; kill $(jobs -p); wait 2>/dev/null; echo "left: $(jobs -rp | wc -l)"
jobs: 2 left: 0

jobs -p gives PIDs for kill.

Job control (set -m)

V7

Current and previous job

set -m; sleep 30 & sleep 31 & sleep 32 & jobs | cut -c1-4; kill %1 %2 %3
[1] [2]- [3]+

+ is the newest, - the one before.

V8

Refer to a job by name

set -m; sleep 30 & yes > /dev/null & jobs %yes; kill %yes %sleep
[2]+ Running yes > /dev/null &

%yes = job whose command starts with yes.

V9

Stop and continue by job number

set -m; timeout 20 yes > /dev/null & sleep 0.2; kill -STOP %1; sleep 0.1; jobs; kill -CONT %1; sleep 0.1; jobs; kill %1
[1]+ Stopped timeout 20 yes > /dev/null [1]+ Running timeout 20 yes > /dev/null &

The script version of Ctrl+Z and bg.

V10

A background job that reads the keyboard

tmux -f /dev/null new-session -d -s q 'bash --norc -i'; sleep 0.4; tmux send-keys -t q 'bash ~/ask.sh &' Enter; sleep 0.6; tmux send-keys -t q 'jobs' Enter; sleep 0.4; tmux capture-pane -t q -p | grep -E 'Stopped|Running|\[1\]' | sed -E 's/[0-9]{3,}/PID/'; tmux kill-server
[1] PID [1]+ Stopped bash ~/ask.sh

It wanted input while in the background, so the kernel stopped it (SIGTTIN).

Surviving logout

V11

nohup with your own log

cd ~/jb; nohup bash -c 'echo started; sleep 0.3; echo finished' > job.log 2>&1 & wait; cat job.log; ls nohup.out 2>&1
started finished ls: cannot access 'nohup.out': No such file or directory

With a redirect, no nohup.out is created.

V12

nohup and its exit codes

nohup false > /dev/null 2>&1; echo "false: $?"; nohup nosuchcmd > /dev/null 2>&1; echo "missing: $?"
false: 1 missing: 127

nohup returns the command’s status, or 127 if it cannot run it.

V13

setsid has no terminal

setsid bash -c 'tty; ps -o tty= -p $$' 2>&1 | head -2; true
not a tty ?

“not a tty” and ? : fully detached.

V14

huponexit is off by default

shopt huponexit; true
huponexit off

bash sends HUP to jobs when a login shell exits only if this is on; the terminal hang-up still sends it.

V15

timeout + nohup for a safe long job

cd ~/jb; nohup timeout 1 sleep 5 > t.log 2>&1 & p=$!; wait $p; echo "status $? (124 = stopped by timeout)"
status 124 (124 = stopped by timeout)

A limit so a forgotten job cannot run forever.

V16

What runs without a terminal?

ps -u riya -o tty=,comm= | awk '$1=="?"' | sort | uniq -c | head -3 | sed -E 's/^ +//'
1 ? awk 1 ? bash 1 ? head

Processes with TTY ? have no terminal: daemons, nohup/setsid jobs.

Script it: runpool.sh

Run a list of tasks in the background with at most 3 at a time, log each result with its duration, and report how many failed. Safe to start with nohup.

max=3; fail=0; log=~/pool.log; : > "$log"
tasks=("sleep 0.3" "sleep 0.1" false "sleep 0.2" "ls /nope" "sleep 0.1")
run(){ local s=$SECONDS; if bash -c "$1" > /dev/null 2>&1; then r=ok; else r=FAIL; fi; echo "$r  $1  ($((SECONDS-s))s)" >> "$log"; [ $r = ok ]; }
for t in "${tasks[@]}"; do
  while (( $(jobs -rp | wc -l) >= max )); do wait -n || fail=$((fail+1)); done
  run "$t" &
done
while (( $(jobs -rp | wc -l) > 0 )); do wait -n || fail=$((fail+1)); done
sort "$log"; echo "${#tasks[@]} tasks, $fail failed"
FAIL false (0s) FAIL ls /nope (0s) ok sleep 0.1 (0s) ok sleep 0.1 (0s) ok sleep 0.2 (0s) ok sleep 0.3 (1s) 6 tasks, 2 failed

Six sample tasks, two of which fail.

Puzzle answer Remember the question from the story? Open to check your guess.

1. & only puts the job in the background; it is still a job of that shell, so when SSH dropped, bash got SIGHUP and passed it on. 2. nohup ignores HUP, and because its output was still the terminal it appended everything to nohup.out: redirect it, nohup ./backup.sh > backup.log 2>&1 &. 3. disown removes the job from the shell’s table, so bash does not send it HUP. 4. Scripts run without job control; fg/bg only work in an interactive shell (or after set -m). In scripts, use wait and kill.

Quick check Which survives a dropped SSH connection: cmd & or nohup cmd &?
Answer: nohup cmd & (or disown, setsid, tmux).
