The problem

Riya double-clicks nothing, types one word, ls, and a program starts, runs and disappears in 3 milliseconds. Behind that word, Linux made a copy of her shell, turned the copy into ls, waited for it, and collected its exit status. Every running program, from your shell to a web server with 200 workers, is a process: a program in memory with a number (PID), a parent (PPID), an owner, a state and its own resources. Understanding this one idea explains “zombie processes”, why cd cannot be a separate program, why a server keeps running after you close the terminal (or does not), and what you are really killing with kill.

By the end of this page you will be able to:
  • explain program vs process vs thread, and read PID, PPID, UID, state and command for any process
  • describe how every command starts: fork (copy the parent) then exec (load a new program), then wait and the exit status
  • recognise process states R, S, D, T, Z and I, and what zombies and orphans really are
  • find information about your own shell: $$, $PPID, $!, /proc/PID, and see fork/exec happen with strace

2 Definition

Process: a running program

Formal definition (write this in exams)

A process is an instance of a program being executed, with its own process ID (PID), parent process ID (PPID), owner (UID/GID), memory, open files, current directory, environment and state. New processes are created by fork (a copy of an existing process) and usually load a different program with exec; when a process exits, its parent collects the exit status with wait.

In simple words

A program is a file. A process is that file running, with a number and a parent.

Processes at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: recipes and cooks

A program is a recipe; a process is someone cooking it right now.

Basic What you will see every day

  • PID: the process ID, a number unique while it runs. echo $$ shows your shell’s.
  • PPID: the parent’s PID. Your commands’ parent is your shell.
  • USER: whose permissions it has (Lesson 8.1).
  • STAT: R running, S sleeping (waiting), T stopped, Z zombie, D waiting for disk.
  • When it ends, it leaves an exit status for its parent: $? (Lesson 5.4).

Intermediate fork, exec, wait, exit

  • fork() (on Linux: clone()) creates a child that is a copy of the parent: same code, memory (copy-on-write), open files, current folder, environment.
  • exec() (execve()) replaces the program inside the process: same PID, new code. exec cmd in bash does this to the shell itself.
  • exit() ends the process with a status 0–255; the kernel keeps a small entry (a zombie) until the parent calls wait().
  • That is why cd must be a shell builtin: a child’s current folder dies with the child. Same for export, source, exit.

Advanced Behind the screen: the kernel’s view

  • The kernel keeps a task_struct per task: PID, parent, credentials (real/effective UID), state, memory map, open file table, signal handlers, CPU time, cgroup and namespaces.
  • Threads are tasks that share memory: each has its own TID; the PID of a process is its main thread’s ID (TGID). ps -L shows them.
  • PID 1 (systemd on most distributions) is the ancestor of all user processes and adopts orphans; it reaps them so they do not stay zombies. Process trees can also set a “subreaper”.
  • Kernel threads ([kthreadd], [kworker/…]) have PPID 2 and no command line; state I means idle kernel thread.
  • PIDs are reused after a process ends; the maximum is /proc/sys/kernel/pid_max (often 4194304). A PID alone does not prove it is the same process later.

Did you know? You cannot kill a zombie: it is already dead. kill -9 does nothing to it. You fix zombies by making the parent call wait (or by ending the parent, so PID 1 adopts and reaps them).

EXAM> “Difference between a program and a process?” → A program is a passive file on disk; a process is an active instance of it in memory with a PID, state and resources. One program can run as many processes.
Quick check Why is cd built into the shell instead of being a program like /usr/bin/ls?
Answer: A program runs in a child process. A child’s current folder disappears when it exits, so the shell’s folder would never change.
Common mistake
✗kill -9 the zombie’s PID
✓Find its parent (ps -o ppid= -p ZPID) and fix or restart the parent

A zombie has already exited. Only its parent can remove it (by calling wait); if the parent ends, PID 1 adopts and reaps it.

zombies and orphans Z and PPID 1

🟢 Read-onlyno sudo

A zombie is a child that exited while its parent did not call wait: ps shows Z and <defunct>. An orphan is a running child whose parent exited: it is adopted by PID 1 (or a subreaper), so its PPID changes.

✓ Use it when
  • understanding zombies and orphans
  • debugging services that leave <defunct> entries
✗ Don’t use it when
  • kill -9 on a zombie (it is already dead)

zombies and orphans in system info / admin

  1. Situation: An orphan is adopted.

    cd ~/pr; bash -c 'sleep 30 & echo $! > child.pid'; sleep 0.2
ps -o pid,ppid,stat,cmd -p $(cat child.pid); kill $(cat child.pid)
    PID PPID STAT CMD 2687 1 S sleep 30

    Why this way: The parent bash ended right away; its child sleep now has PPID 1. That is how daemons detach on purpose.

zombies and orphans in devops / cloud

  1. Situation: Zombies cannot be killed.

    cd ~/pr; z=$(ps -o pid= --ppid $(cat parent.pid) | tr -d ' ')
kill -9 $z; sleep 0.2; ps -o pid,stat,cmd -p $z
    PID STAT CMD 2707 Z [sleep] <defunct>

    Why this way: Still Z after kill -9. In containers, run a tiny init (docker run --init, tini) as PID 1 so zombies get reaped.

Undo and safety net

Process mistakes are fixed by ending or restarting the right process.

  • Ran exec in your login shell: the terminal closes when that program ends; just open a new terminal.
  • A script’s cd/export “did nothing”: run it with source script.sh.
  • Zombies piling up: find the parent (ps -o ppid= -p Z), restart it; in containers add an init (--init).
  • Started something in the background and lost it: jobs -l or pgrep -a NAME, then kill it (Lesson 11.3).

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. ps -p 999999
    PID TTY TIME CMD exit status: 1

    What it means: No process with that PID (ps prints only the header).

    Fix: Check the PID; it may have ended.

  2. ./report.sh
    /home/riya/script.sh: line 3: ./report.sh: Permission denied exit status: 126

    What it means: exec failed: the file is not executable (exit 126).

    Fix: chmod +x or bash report.sh.

  3. repot.sh
    /home/riya/script.sh: line 1: repot.sh: command not found exit status: 127

    What it means: exec could not find it in PATH (exit 127).

    Fix: Check the name; use ./ for the current folder.

  4. kill 1
    /home/riya/script.sh: line 1: kill: (1) - Operation not permitted exit status: 1

    What it means: You may not signal another user’s process (here PID 1, root).

    Fix: Only your own processes, or sudo if appropriate.

6 Real-world use

Processes at work

1. Web servers

nginx, Apache and Gunicorn start a master process that forks workers; the master restarts any worker that dies.

Start→fork→serve

2. Containers

The first process in a container is PID 1: it must reap zombies and forward signals, or use --init / tini.

Run→PID 1→reap

3. Start scripts

Entrypoint scripts prepare the environment then exec the real program, so it gets the PID and the signals.

Prepare→exec→run

4. Security

Analysts check who started a process: a shell whose parent is a web server is a classic sign of an attack.

Alert→ps -o ppid→investigate

5. CI pipelines

Each build step is a child process; its exit status decides whether the pipeline continues.

Step→wait→pass/fail

    cd ~/pr; sleep 2 & echo $! > s.pid; ps -o pid,ppid,stat,cmd -p $(cat s.pid) | sed 's/[0-9]\+/N/g'
    PID PPID STAT CMD N N S sleep N

  2. 2. The kernel’s view.

    cd ~/pr; grep -E "^(Name|State|Threads)" /proc/$(cat s.pid)/status
    Name: sleep State: S (sleeping) Threads: 1

  3. 3. It ends; nothing is left.

    cd ~/pr; wait $(cat s.pid) 2>/dev/null; sleep 2.2; ps -p $(cat s.pid) >/dev/null || echo "exited and reaped"
    exited and reaped

Script it: family.sh

Print the chain of parents from a PID up to PID 1 (the process’s ancestry), using only ps.

p=${1:-$$}
while [ "$p" -gt 0 ]; do
  ps -o pid=,stat=,comm= -p "$p" | awk '{printf "%-7s %-5s %s\n", $1, $2, $3}'
  [ "$p" -eq 1 ] && break
  p=$(ps -o ppid= -p "$p" | tr -d ' ')
done
2857 S bash 2856 S runuser 2567 S python3 2566 S bash 2565 S bash 2561 Ss bash 100 Sl claude 93 Sl environment-man 86 S sh 1 SLl process_api

Run for the script’s own shell. On your PC the last line is 1 Ss systemd.

Puzzle answer Remember the question from the story? Open to check your guess.

./go.sh runs the script in a child process (fork + exec of bash). The child changed its own folder and then exited, so Riya’s shell never moved. Run it in the current shell instead: source go.sh (or . go.sh), or make it a shell function/alias.

Quick check A process shows PPID 1. Is something wrong?
Answer: Not necessarily: services and orphans have PID 1 (systemd) as parent. It only matters if you expected a different parent.
