2 Definition

What a one-liner is, and the patterns behind the 100

Formal definition (write this in exams)

A one-liner is a complete solution to a task written as a single command line, usually by combining small tools with pipes, lists, substitutions and loops. Good one-liners are short, read-only by default, quote their file names, and follow a small set of reusable patterns: filter-and-count, group with awk, bulk actions with find, loops over files, comparing outputs, and safe chains.

In simple words

One line, one task: a few patterns applied to different data.

Intermediate The six patterns

  1. Filter → field → count: grep X | cut -dD -fN | sort | uniq -c | sort -rn | head.
  2. Group in awk: awk -F, '{t[$k]+=$v} END{for(x in t) print x, t[x]}'.
  3. Bulk on files: find DIR tests -exec cmd {} + or -print0 | xargs -0.
  4. Loop over files: for f in *.x; do cmd "$f"; done, or while read -r for lines.
  5. Compare: diff/comm <(cmd1) <(cmd2).
  6. Chain safely: step1 && step2 || alert.

Advanced Behind the screen: portability and safety

  • GNU-specific options (sed -i without a suffix, find -printf, ls --sort, date -d) differ on macOS/BSD; check --version on a new system.
  • Tools may be missing (ss, rsync, locate on minimal images): command -v tool before relying on one in scripts.
  • Locale affects sort order and character classes: LC_ALL=C makes results reproducible and faster.
  • Quote every variable and file name ("$f") and use -- before file names that may start with a dash.
  • For scripts, add set -euo pipefail so a failing part stops the script (Lesson 12.6).

Did you know? Many classic one-liner collections (“sed one-liners”, “awk one-liners”) date from the 1990s Usenet era. They still work because the tools kept their interfaces for 30 years: a one-liner learned today will likely still work when you retire.

EXAM> “Write a one-liner to find the 5 most frequent words in a file.” → tr -s ' ' '\n' < file | sort | uniq -c | sort -rn | head -5.

6 Real-world use

The 100 at work

1. Team runbooks

Operations teams keep their own tested one-liner lists for incidents: disk full, top IPs, stuck processes.

Incident→runbook line→answer

2. Personal aliases and functions

The one-liners you use weekly become aliases or functions in ~/.bashrc (Lesson 12.3).

Repeat→alias→one word

3. Small automations

A one-liner in cron cleans temp files or mails a daily count; when it grows, it becomes a script.

Daily→cron→done

4. Interviews

Linux and DevOps interviews ask for exactly these: top 5 words, sum a column, find big files, count status codes.

Question→pattern→one line

5. Quick data checks

Analysts check a CSV with head, wc, uniq -c and an awk sum before loading it anywhere.

File→one-liners→trust

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

Build it step by step: adapting a one-liner

Scenario: Riya turns one known one-liner into answers for three new questions.

  1. 1. Known: the top IP.

    cd ~/h; awk '{print $1}' logs/access.log | sort | uniq -c | sort -rn | head -1
    3 10.0.0.5

  2. 2. Change the column: the top URL.

    cd ~/h; awk '{print $3}' logs/access.log | sort | uniq -c | sort -rn | head -1
    2 /login

  3. 3. Add a condition: the IP with most errors.

    cd ~/h; awk '$4>=400{print $1}' logs/access.log | sort | uniq -c | sort -rn | head -1
    2 10.0.0.7

  4. 4. Change the file and separator: the biggest department.

    cd ~/h; awk -F, 'NR>1{print $2}' staff.csv | sort | uniq -c | sort -rn | head -1
    2 IT

Script it: oneliner-quiz.sh

A tiny self-test: five tasks on the sample data, each solved two different ways; the script checks that both answers agree.

mkdir -p ~/h/logs ~/h/src && cd ~/h || exit 1
[ -f words.txt ] || printf 'alpha\nbeta\ngamma\nbeta\ndelta\n' > words.txt
[ -f staff.csv ] || printf 'name,dept,salary\nRiya,IT,72000\nAman,HR,51000\n' > staff.csv
[ -f logs/app.log ] || printf 'INFO a\nERROR b\nERROR c\n' > logs/app.log
touch src/a.py src/b.py
check(){ local want got; want=$(bash -c "$2" 2>/dev/null); got=$(bash -c "$3" 2>/dev/null); [ "$want" = "$got" ] && echo "PASS  $1 ($got)" || echo "FAIL  $1 (want: $want, got: $got)"; }
check 'unique words'     "sort -u words.txt | wc -l"                       "sort words.txt | uniq | wc -l"
check 'sum of salaries'  "awk -F, 'NR>1{s+=\$3} END{print s}' staff.csv"   "tail -n +2 staff.csv | cut -d, -f3 | paste -sd+ | bc"
check 'python files'     "find src -name '*.py' | wc -l"                  "ls src/*.py | wc -l"
check 'ERROR lines'      "grep -c ERROR logs/app.log"                     "awk '/ERROR/{n++} END{print n}' logs/app.log"
check 'biggest word'     "awk '{print length, \$0}' words.txt | sort -rn | head -1 | cut -d' ' -f2" "while read -r w; do echo \"\${#w} \$w\"; done < words.txt | sort -rn | head -1 | cut -d' ' -f2"
PASS unique words (4) PASS sum of salaries (322000) PASS python files (5) PASS ERROR lines (2) PASS biggest word (gamma)

Each task is solved two ways; if both agree, it passes.

Puzzle answer Remember the question from the story? Open to check your guess.

1. Check the tool exists: command -v netstat would have shown it is missing (use ss or lsof -i). 2. Read it part by part: running uniq -c on its own shows repeated values split up; the fix is sort | uniq -c. 3. Run the read-only version first: without -delete, the find would have listed every file, revealing that the order was wrong; tests come first, the action last (find … -mtime +30 -delete).

Quick check Which three habits make internet one-liners safe?
Answer: Check the tools exist, read/run it stage by stage, and run a read-only version on sample data first.
