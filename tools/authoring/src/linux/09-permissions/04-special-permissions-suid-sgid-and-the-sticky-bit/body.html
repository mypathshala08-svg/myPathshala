The problem

/etc/shadow is readable only by root, yet every user can change their own password, which means writing to /etc/shadow. /tmp is writable by everyone, yet nobody can delete your files there. In a team folder, files created by Aman should belong to the team, not to Aman. Three puzzles, three special bits: SUID, the sticky bit and SGID. They are the 4th octal digit (4755, 1777, 2770), they show up as s and t in ls -l, and SUID is also a favourite target for attackers.

  • build a team folder where new files keep the team group (SGID) and a shared upload folder where users cannot delete each other’s files (sticky)
  • find SUID/SGID programs for a security audit and explain why SUID shell scripts are ignored

2 Definition

SUID, SGID and the sticky bit

Formal definition (write this in exams)

SUID (set user ID, 4000) on an executable makes it run with the privileges of the file’s owner. SGID (set group ID, 2000) on an executable makes it run with the file’s group; on a directory it makes new files inherit the directory’s group. The sticky bit (1000) on a directory allows only a file’s owner, the directory’s owner or root to delete or rename files inside it.

In simple words

Let normal users do one privileged job safely, keep team files in the team group, and protect shared folders.

Very basic No jargon: teller, team room, lockers

Three special rules.

Basic What you will see and type

  • -rwsr-xr-x root … passwd: s in the owner part = SUID.
  • drwxrwsr-x … team: s in the group part = SGID.
  • drwxrwxrwt … /tmp: t in the others part = sticky.
  • chmod g+s /srv/team, chmod +t /srv/drop, chmod u+s prog.

Intermediate What each bit does, and the 4th digit

  • SUID (4) on an executable: the process runs with the file owner’s UID (effective UID). On folders: ignored on Linux.
  • SGID (2) on an executable: runs with the file’s group. On a folder: new files and subfolders get the folder’s group, and new subfolders get SGID too.
  • Sticky (1) on a folder: a file inside can be deleted or renamed only by its owner, the folder’s owner, or root. On files: ignored today.
  • 4-digit modes: first digit = 4 SUID + 2 SGID + 1 sticky: 4755, 2770, 1777, 3770 (SGID + sticky).
  • Capital S/T = the special bit is set but the x under it is not (usually a mistake).

Advanced Behind the screen: effective UID, scripts and nosuid

  • On execve() of an SUID file the kernel sets the process’s effective UID to the file owner; the real UID stays yours, so the program knows who called it (getuid() vs geteuid()). sudo, su, passwd, mount and ping-like tools work this way.
  • Linux ignores SUID/SGID on interpreted scripts (#! files) because of race conditions; only binaries honour them. That is the puzzle.
  • Writing to an SUID file, or a chgrp by a normal user, clears the bits. Mounts with nosuid (often /tmp, USB disks) ignore them entirely.
  • Modern systems replace many SUID programs with capabilities (getcap /usr/bin/ping → cap_net_raw), which grant one privilege instead of full root.
  • Every SUID-root program is an attack surface: a bug in it is a root exploit. Audits list them (find -perm -4000) and compare with a baseline.

Did you know? The sticky bit got its name from early Unix, where it told the system to keep (“stick”) a program’s code in swap memory for faster starts. Linux ignores that meaning; only the folder meaning survives.

EXAM> “Create /shared owned by group devs so that new files get group devs and users cannot delete each other’s files.” → chgrp devs /shared; chmod 3770 /shared (2 SGID + 1 sticky).
Quick check What does drwxrwxrwt allow, and forbid?
Answer: Everyone may create files; only the owner of a file (or the folder owner or root) may delete or rename it.

    Why this way: Keep this list as a baseline; a new entry (for example in /tmp or /home) is a red flag.

  2. Situation: SUID on a copied binary: it runs as the owner (here riya, so harmless).

    cd ~/sp; chmod u+s myid; ls -l myid
sudo -u aman ./myid
    -rwsr-xr-x 1 riya riya 39432 Nov 11 13:36 myid uid=1001(aman) gid=1001(aman) euid=1000(riya) groups=1001(aman),1005(finance)

    Why this way: aman runs it, but euid=1000(riya): the effective UID comes from the file owner. Owned by root this would be a root shell risk.

SUID (u+s, 4xxx) in system info / admin

  1. Situation: Why can a normal user change their password?

    ls -l /etc/shadow /usr/bin/passwd
    -rw-r----- 1 root shadow 820 Nov 11 13:12 /etc/shadow -rwsr-xr-x 1 root root 64152 May 30 2024 /usr/bin/passwd

    Why this way: shadow is root-only; passwd is SUID root and checks your old password before writing only your line.

SUID (u+s, 4xxx) in software development

  1. Situation: SUID on a script is ignored (the puzzle).

    cd ~/sp; printf '#!/bin/sh\nid -u\n' > whoami.sh; sudo chown root: whoami.sh; sudo chmod 4755 whoami.sh
ls -l whoami.sh; ./whoami.sh; sudo rm whoami.sh
    -rwsr-xr-x 1 root root 16 Nov 11 13:36 whoami.sh 1000

    Why this way: Root-owned, 4755, and still prints 1000. Use a sudo rule instead (Lesson 8.4).

  1. Situation: An upload folder for several apps: without and with the sticky bit.

  1. Situation: Find world-writable folders without the sticky bit (risky).

    sudo find /srv -xdev -type d -perm -0002 ! -perm -1000

    Why this way: Every hit lets users delete each other’s files. On a real server search / (with -xdev). Fix with chmod +t (or remove o+w).

Common mistake
✗chmod 777 /shared (for a folder many users write to)
✓chmod 1777 /shared (or better: a group + 3770)

Without the sticky bit, write permission on a folder lets every user delete or replace every file in it.

Undo and safety net

Special bits are removed like any other bit.

  • Unwanted SUID/SGID on a file: chmod u-s,g-s FILE (or a 3-digit mode, which clears them for files).
  • A folder lost SGID: chmod g+s DIR, then fix existing files: chgrp -R TEAM DIR.
  • Capital S or T: add the x (chmod u+x / o+x) or remove the special bit.
  • Unknown SUID file found: do not run it; check dpkg -S FILE (package?), remove the bit, investigate.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. sudo -u aman touch /tmp/aman_x; rm /tmp/aman_x
    rm: cannot remove '/tmp/aman_x': Operation not permitted exit status: 1

    What it means: Sticky folder: only the owner may delete (EPERM).

    Fix: Ask the owner, or root.

  2. chmod u+s /usr/bin/passwd
    chmod: changing permissions of '/usr/bin/passwd': Operation not permitted exit status: 1

    What it means: Not your file (EPERM).

    Fix: Only root changes special bits on system files (and should not).

  3. sudo -u aman touch /srv/team/x
    touch: cannot touch '/srv/team/x': Permission denied exit status: 1

    What it means: SGID does not give write permission: the group has no w.

    Fix: chmod g+w (2770).

6 Real-world use

Special bits at work

1. Team folders

SGID folders keep every file in the team group; with umask 002 everyone can edit.

Team→chmod g+s→shared

2. Shared scratch

/tmp, /var/tmp and upload folders use the sticky bit.

Users→chmod +t→safe

3. Security audits

SUID/SGID lists are compared with a baseline; unknown entries are investigated.

Scan→find→baseline

4. Hardening

/tmp, /home and USB mounts use nosuid so planted SUID files do nothing.

fstab→nosuid→contained

5. Capabilities

Programs needing one privilege (bind port 80, raw sockets) get a capability, not SUID root.

Need→setcap→least privilege

Puzzle answer Remember the question from the story? Open to check your guess.

SUID is not broken: Linux ignores SUID on scripts, so the root-owned 4755 script runs as riya (uid 1000); use a sudo rule instead. The capital S means SUID is set but the owner has no x on report.txt, so it is meaningless: SUID only makes sense on executable programs.
