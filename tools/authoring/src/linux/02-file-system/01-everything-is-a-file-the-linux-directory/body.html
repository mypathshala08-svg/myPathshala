1 The story

“Where is the C: drive?”

Before you start: Lesson 1.6: you can type a command and read its output.

Think first

On Linux you can cat a text file, but also your CPU’s details, your disk and even the program that is reading. How can a running program or a piece of hardware be “a file”?

Keep your guess in mind. The answer is at the end of part 6.

Neha asks Riya to “check the nginx config and the error log on app-01”. Riya logs in and types cd C:. Nothing. She lists the top of the system and sees short, strange names: etc, var, usr, proc, dev. No drives, no “Program Files”, no “My Documents”.

R> Sir, there is no C: drive! Where are the programs? Where did nginx put its settings? A> Linux has a single tree that starts at /, called root. K> That’s the best part. Once you know the map, every Linux server feels familiar. nginx’s config is in /etc/nginx, its log in /var/log/nginx, on almost any distro. R> And what are proc and dev? 2 Definition

The Linux directory hierarchy and “everything is a file”

Formal definition (write this in exams)

The Linux directory hierarchy is a single tree of directories rooted at /, whose top-level layout is defined by the Filesystem Hierarchy Standard (FHS): for example /etc for host configuration, /home for user data, /usr for installed software, /var for variable data and /tmp for temporary files. Additional storage devices and virtual file systems are mounted onto directories of this tree. “Everything is a file” is the Unix design principle that files, directories, devices, pipes, sockets and kernel interfaces are all accessed through the same file operations and permission model.

In simple words

Linux keeps everything in one tree that starts at /. Each top-level folder has a standard job. And almost everything, even devices and running programs, shows up as a file you can read with ordinary commands.

The Linux tree at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a school building with one gate

Picture the whole Linux system as one school building. There is only one main gate, and every room has a fixed job, the same in every school.

  • The main gate is / (“root”). Everything is somewhere inside it. There is no second building called D:.
  • Settings live in the staff room (/etc); each person’s own things in their locker (/home/riya); records and logs in the store room (/var); programs in the library (/usr).
  • Because every Linux “school” uses the same rooms, you can walk into any Linux server and find things.

Basic The main folders and their jobs

  • /etc: configuration files, as plain text. /etc/hostname, /etc/passwd, /etc/nginx/nginx.conf.
  • /home: one folder per user (/home/riya); /root is the administrator’s home.
  • /var: data that grows: /var/log (logs), /var/lib (databases, package lists), /var/cache.
  • /usr: installed programs and libraries: /usr/bin (commands), /usr/lib, /usr/share (docs, icons).
  • /tmp: temporary files for everyone, may be cleared at reboot.
  • /dev: devices (disks, terminals); /proc and /sys: live information from the kernel; /boot: the kernel itself.

Intermediate The FHS, merged /usr and why /var fills up

  • The layout follows the Filesystem Hierarchy Standard (FHS), so tools, packages and admins agree where things go.
  • Merged /usr: on current Ubuntu, Debian, Fedora and RHEL, /bin, /sbin and /lib are links to /usr/bin, /usr/sbin and /usr/lib. Old scripts using /bin/bash still work.
  • Rule of thumb: /usr is changed only by the package manager; /etc by admins; /var by running programs; /home by users. /usr/local and /opt hold software installed by hand.
  • “Disk full” on a server is usually /var: logs (/var/log), Docker images (/var/lib/docker) or package caches.
  • /tmp is writable by everyone but has the sticky bit: you can delete only your own files there (Lesson 9.4).

Advanced One tree, many file systems, all through the VFS

  • The tree is assembled from mounts: the root file system (ext4 or xfs on disk) plus others attached on folders: /proc (procfs), /sys (sysfs), /dev (devtmpfs), /run and often /tmp (tmpfs, in RAM), USB sticks (vfat), network shares (nfs). findmnt shows the mount tree.
  • The kernel’s virtual file system (VFS, Lesson 1.2) gives all of them the same operations, so cat works the same on a disk file, a kernel statistic or a device.
  • Everything is a file means: one interface (open, read, write, close, permissions) for documents, directories, devices (/dev/sda, /dev/null), pipes, sockets and kernel data. What is behind each name is decided by its inode type and the file system it lives on.
  • /proc/self always points to the process that is reading it: ls -l /proc/self/exe shows the program running that very command.

Did you know? /proc/self is a link that points to whichever process is reading it. Run ls -l /proc/self/exe and it shows /usr/bin/ls, because ls is the process that asked. Run cat /proc/self/status | head -1 and it says Name: cat.

EXAM> “Explain the Linux file system hierarchy” → draw the tree from / with at least 10 directories and one line each (/bin, /boot, /dev, /etc, /home, /lib, /media, /mnt, /opt, /proc, /root, /tmp, /usr, /var); mention the FHS, that there are no drive letters (devices are mounted), and the meaning of “everything is a file”.
Quick check Your colleague says “I put the file in root.” Which two places could that mean?
Answer: /, the root directory at the top of the tree, or /root, the home folder of the root user. Always ask, and say “slash” for /.

Real files and virtual files

Files on disk

Your documents, configs in /etc, programs in /usr. Stored in blocks on an SSD, kept after power-off.

ext4, xfs

Kernel windows

Files in /proc and /sys are generated by the kernel the moment you read them. They take no disk space.

procfs, sysfs

Device files

Names in /dev that lead to drivers: reading /dev/sda reads the disk; writing to /dev/null throws data away.

devtmpfs

RAM-only folders

/run (and on many systems /tmp) live in memory and start empty at every boot.

tmpfs

Did you know? The Linux tree is one tree, but its branches can live on very different things: an SSD, RAM, the kernel itself, a USB stick or a server in another city. You cannot tell from the path; findmnt or df -T tells you.

Quick check A teammate filled the disk with logs. Which top-level folder will you check first?
Answer: /var, especially /var/log (and /var/lib/docker if Docker is used). sudo du -sh /var/* shows which part is big.
4 Step by step

Find where an application keeps everything

A routine you will use on every server: map one application (here nginx) onto the tree.

  1. 1. Where is the program?

    command -v nginx → /usr/sbin/nginx.

    Behind the screen: the shell searches the folders in PATH; package-managed programs live under /usr.

  2. 2. Where is its configuration?

    ls /etc/nginx → nginx.conf, sites-available/…

    Behind the screen: by FHS rules, host-specific settings go to /etc, as plain text you can read and back up.

  3. 3. Where are its logs?

    ls /var/log/nginx → access.log, error.log.

    Behind the screen: logs grow, so they belong in /var; logrotate keeps them small (Lesson 18.2).

  4. 4. Where is its data?

    Web pages in /var/www/html (or /srv); a database such as MySQL keeps data in /var/lib/mysql.

    Behind the screen: /var/lib holds the state programs need to keep between restarts.

  5. 5. Where is it at run time?

    Its process ID file in /run/nginx.pid; the process itself under /proc/<PID>.

    Behind the screen: /run is a RAM file system emptied at each boot; /proc is generated by the kernel.

  6. 6. Which package put it there?

    dpkg -S /usr/sbin/nginx (Ubuntu) or rpm -qf (RHEL).

    Behind the screen: the package database records every file each package installed (Lesson 14.2).
Quick check Riya edited /usr/share/nginx/html/index.html by hand, and the next package update overwrote her changes. Which folder rule did she break?
Answer: /usr belongs to the package manager. Her own content should go in /var/www or /srv, and her settings in /etc.
5 See it happen

A real file and a virtual file, side by side

Left: what Riya sees. Right: how the kernel’s VFS sends each request to a different file system.

Same command, two very different files 5 steps
What you see
  1. cat /etc/hostname prints the machine name. An ordinary text file.
  2. /proc/cpuinfo is read the same way and prints CPU details.
  3. But ls -l says /proc/cpuinfo has size 0. How can a file with nothing in it print so much?
  4. df -T shows why: /etc is on the disk (ext4), /proc is a different file system called proc.
  5. /proc/self points to whichever process reads it, here ls. (Outputs shortened; host name is an example.)
Behind the screen
  1. cat asks the kernel to open and read /etc/hostname. The VFS sees it lives on ext4 and lets the ext4 driver read 7 bytes from the SSD.
  2. For /proc/cpuinfo the VFS hands the request to procfs, which asks the kernel for CPU information and writes it as text, right now.
  3. Nothing is stored anywhere, so the file’s size is reported as 0. The content exists only while you read it.
  4. The tree is built from several mounted file systems. Programs never need to know which one they are using: “everything is a file”.
  5. Because procfs generates content per reader, /proc/self can be different for every process. ps, top and free are built on these files.

Real-time scenario 2

One application, five places in the tree

Neha’s request was “check nginx’s config and error log”. The FHS says exactly where each part of an application goes, on almost every distro.

An application mapped onto the tree 5 steps
Animated example
  1. The program file sits in /usr/sbin, put there by the package manager.
  2. Its configuration is in /etc/nginx: plain text files the admin edits.
  3. Its logs go to /var/log/nginx: access.log and error.log.
  4. The website itself is in /var/www/html by default on Ubuntu.
  5. While it runs, its process ID is in /run/nginx.pid and the kernel shows the process under /proc. MySQL, SSH and Docker follow the same pattern.
Real-time scenario 3 · advanced

A new disk becomes a folder, not a drive letter

The database needs more space. Watch how Linux adds a whole disk to the tree. Device names and sizes are examples; Module 15 does it hands-on.

Mounting a disk into the tree 5 steps
Animated example
  1. A new 500 GB cloud disk appears as the device /dev/vdb.
  2. The admin creates an ext4 file system on it.
  3. mount /dev/vdb /data attaches it to the empty folder /data.
  4. df -h /data confirms: everything under /data is now stored on the new disk.
  5. Applications only see paths, so storage can be added or moved without changing them. An entry in /etc/fstab keeps the mount after reboot.

Layer by layer: one tree, many file systems

The tree looks like one thing, but each branch can be a different file system. Click each one: why it exists, how it works, where it is, where you meet it, and a real check of which file system the folder really is (recorded on our build machine).

Each branch of the tree can be a different file system. Click one.

/ on disk ext4 or xfs

Why does it exist?

Programs, configs and your files must survive a reboot.

How does it work?

A disk partition (or cloud disk) formatted with ext4 or xfs is mounted as / during boot.

Where is it, really?

A block device such as /dev/vda or /dev/nvme0n1p2.

Where is it used?

Everything that is not one of the special folders below.

See this layer yourself (real output)

findmnt -n -o SOURCE,FSTYPE /
/dev/vda ext4

/proc procfs: processes and kernel

Why does it exist?

Tools like ps, top and free need live information from the kernel without special system calls.

How does it work?

procfs creates files when they are read; one numbered folder per process.

Where is it, really?

The kernel’s procfs (fs/proc/ in the kernel source); takes no disk space.

Where is it used?

ps, top, free, uptime and your own scripts (Lesson 20.2).

See this layer yourself (real output)

findmnt -n -o FSTYPE /proc; ls -l /proc/self/exe
proc lrwxrwxrwx 1 riya riya 0 Nov 5 18:41 /proc/self/exe -> /usr/bin/ls

/sys sysfs: devices and drivers

Why does it exist?

The kernel’s view of devices and drivers should be browsable and, in places, changeable.

How does it work?

sysfs mirrors the kernel’s device model as folders: buses, classes, devices.

Where is it, really?

The kernel’s sysfs; cgroup v2 is mounted inside it at /sys/fs/cgroup.

Where is it used?

udev, systemd, container runtimes, hardware tools.

See this layer yourself (real output)

findmnt -n -o FSTYPE /sys; ls /sys/class | head -4
sysfs bdi block bsg cpuid

/dev devtmpfs: device files

Why does it exist?

Programs need names for hardware: disks, terminals, random numbers.

How does it work?

The kernel creates device files as hardware appears; udev adds friendly names and permissions.

Where is it, really?

devtmpfs, a RAM file system managed by the kernel and udev.

Where is it used?

/dev/null in scripts, /dev/sda for disks, /dev/pts/0 for terminals.

See this layer yourself (real output)

findmnt -n -o FSTYPE /dev; ls -l /dev/null
devtmpfs crw-rw-rw- 1 root root 1, 3 Nov 5 05:14 /dev/null

/run and /dev/shm tmpfs: files in RAM

Why does it exist?

Some files are only needed while the system is running and must be fast.

How does it work?

tmpfs keeps files in memory (and swap); they disappear at reboot.

Where is it, really?

tmpfs mounts; on many distros /tmp is tmpfs too (not on this build machine).

Where is it used?

PID files, sockets, shared memory between processes.

See this layer yourself (real output)

findmnt -n -o FSTYPE /dev/shm | head -1
tmpfs

/media and /mnt whatever you attach

Why does it exist?

USB sticks, extra disks and network shares must appear somewhere in the one tree.

How does it work?

mount attaches their file system (vfat, ntfs, ext4, nfs) to a folder.

Where is it, really?

Mount points: ordinary empty folders until something is mounted.

Where is it used?

Data disks on servers, USB sticks on laptops, Windows drives on WSL (/mnt/c).

See this layer yourself (real output)

ls -ld /mnt /media
drwxr-xr-x 2 root root 4096 Oct 24 19:35 /media drwxr-xr-x 6 root root 4096 Nov 5 14:40 /mnt
Quick check ls -l /proc/meminfo shows size 0, yet cat /proc/meminfo prints many lines. Why?
Answer: Files in /proc are generated by the kernel when read; nothing is stored, so the size shown is 0.
6 Real-world use

The tree in a working day

1. Disk-full alerts

Operations teams follow the tree from / to the folder that grew, almost always under /var.

Alert→du on the tree→culprit found

2. Backing up configuration

Because all settings are text in /etc, teams back it up or keep it in Git (tools such as etckeeper) to see exactly what changed.

/etc→Git history→easy rollback

3. Containers and volumes

Docker containers have their own tree; data folders from the host are mounted into it (for example -v /srv/data:/data).

Host folder→mount into container→data survives

4. Monitoring agents

Monitoring tools read /proc and /sys every few seconds to report CPU, memory, disk and network usage.

/proc, /sys→agent→dashboard

5. Moving data to a bigger disk

DBAs mount a new disk and move a database’s folder onto it; applications keep using the same path.

New disk→mount at /var/lib/mysql→same path

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

One-liner corner

Short explorations of the tree. All were really run on our Ubuntu 24.04 build machine (as a normal user, so some folders are not readable).

Beginner

See the merged /usr for yourself

Scenario: A tutorial says /bin/bash, another says /usr/bin/bash. Are they the same?

ls -ld /bin /sbin /lib
lrwxrwxrwx 1 root root 7 Apr 22 2024 /bin -> usr/bin lrwxrwxrwx 1 root root 7 Apr 22 2024 /lib -> usr/lib lrwxrwxrwx 1 root root 8 Apr 22 2024 /sbin -> usr/sbin

The l at the start and the arrow show these are symbolic links into /usr (Lesson 10.2).

Beginner

How many configuration entries are there?

Scenario: Kabir wonders how much there is to configure on a fresh server.

ls /etc | wc -l
166

Every name in /etc is a config file or folder. Plain text means you can read, search and back them up with normal tools.

Intermediate

Which file system is each folder on?

Scenario: You want to know which folders are on the disk and which live in RAM or the kernel.

for d in / /proc /sys /dev /dev/shm; do printf "%-9s %s\n" "$d" "$(findmnt -n -o FSTYPE --target $d | head -1)"; done
/ ext4 /proc proc /sys sysfs /dev devtmpfs /dev/shm tmpfs

findmnt --target finds the mount that contains a path; -o FSTYPE prints just its type.

Advanced

Who is reading /proc/self?

Scenario: Prove that /proc/self is different for every process.

ls -l /proc/self/exe; cat /proc/self/status | head -1
lrwxrwxrwx 1 riya riya 0 Nov 5 18:41 /proc/self/exe -> /usr/bin/ls Name: cat

The first command is run by ls, the second by cat: each sees itself. Tools such as ps read exactly these per-process files.

Intermediate

Build it step by step: which part of /usr is the biggest?

Scenario: Before building a slim server image, find what takes the space inside /usr.

  1. Look at the branches first.

    ls /usr
    bin games include lib lib64 libexec local sbin share src

  2. du -sh = disk usage, summary, human units. 2>/dev/null hides “permission denied” noise.

    du -sh /usr/* 2>/dev/null
    671M /usr/bin 4.0K /usr/games 51M /usr/include 2.4G /usr/lib 4.0K /usr/lib64 241M /usr/libexec 2.6G /usr/local 6.8M /usr/sbin 1.2G /usr/share 88K /usr/src

  3. sort -h understands sizes like 671M and 2.4G.

    du -sh /usr/* 2>/dev/null | sort -h
    4.0K /usr/games 4.0K /usr/lib64 88K /usr/src 6.8M /usr/sbin 51M /usr/include 241M /usr/libexec 671M /usr/bin 1.2G /usr/share 2.4G /usr/lib 2.6G /usr/local

  4. Keep the two biggest: the answer.

    du -sh /usr/* 2>/dev/null | sort -h | tail -2
    2.4G /usr/lib 2.6G /usr/local
