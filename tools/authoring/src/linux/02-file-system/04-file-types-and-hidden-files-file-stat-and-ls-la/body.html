2 Definition

File types, file, stat and hidden files

Formal definition (write this in exams)

Every file system object has a file type stored in its inode: regular file, directory, symbolic link, character device, block device, named pipe (FIFO) or socket. ls -l shows it as the first character of the mode. A file’s name, including any extension, carries no type information for the kernel. The file command classifies a file’s content by testing it against known signatures (magic numbers); stat displays the inode’s metadata. A hidden file is one whose name begins with a dot; listing tools omit such names unless asked.

In simple words

The kernel knows the kind of object; file guesses the format from the bytes; the extension is just a name.

File types at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: jars with labels

Think of jars in a kitchen.

  • A file name, including .txt or .jpg, is just a label on the jar. Labels can be wrong or missing.
  • The file command opens the jar and looks at the first bytes to tell you what is really inside.
  • Some things in the kitchen are not jars at all: a cupboard (a folder), a note saying “see the other shelf” (a link), a tap (a device). Linux has those too.
  • Jars pushed to the back of the shelf are hidden files: their names start with a dot.

Basic What you need every day

  • The first letter in ls -l is the type: - regular file, d directory, l symbolic link (plus c, b, p, s for special files).
  • file name tells you the format: “ASCII text”, “PNG image data”, “ELF 64-bit executable”, “gzip compressed data”.
  • Names starting with . are hidden from plain ls; ls -a shows them (and ., ..), ls -A shows them without . and ...
  • Settings live in hidden files in your home: .bashrc, .profile, .ssh/, .gitconfig.

Intermediate stat and the three times

  • stat file shows everything the inode stores: size, blocks, inode number, links, permissions, owner, and the times.
  • atime = last read (Access), mtime = content last changed (Modify), ctime = inode last changed (Change: content, permissions, owner, rename). ctime is not creation time.
  • Newer file systems also record Birth (creation) time, shown by stat on ext4 and xfs.
  • stat -c prints only what you ask for: stat -c '%F %s %n' file = type, size, name.
  • file -i prints a MIME type (image/jpeg), as web servers use; file often adds “with CRLF line terminators” for Windows text files, but not for every format (recent versions just say “CSV ASCII text”), so for data files check with grep -c $'\r'.

Advanced Behind the screen: mode bits and magic

  • The type is stored in the top bits of the inode’s 16-bit st_mode field, next to the permission bits. ls and stat read it with the statx() system call.
  • Device files (c, b) hold no data: they carry a major, minor number pair (shown by ls -l instead of a size) that tells the kernel which driver to call. /dev/null is 1, 3.
  • Named pipes (p, created with mkfifo) and Unix sockets (s) are meeting points between processes; their data passes through kernel memory, never the disk.
  • file uses the libmagic database: it compares the first bytes (and more) against thousands of signatures, e.g. FF D8 FF = JPEG, 89 50 4E 47 = PNG, 7F 45 4C 46 = ELF.
  • atime updates are expensive, so Linux mounts with relatime by default: atime is updated only if it is older than mtime or more than a day old.

Did you know? The dot rule for hidden files started as a bug. In early Unix, ls skipped . and .. by checking only whether a name began with a dot. That accidentally hid every name starting with a dot, and programmers began using it on purpose for configuration files. The “feature” has stayed for about fifty years.

4 Step by step

Investigating an unknown file

  1. 1. What kind of object?

    ls -l mystery: look at the first letter.

    Behind the screen: ls calls statx() and decodes the type bits of st_mode.

  2. 2. If it is a link, where to?

    ls -l shows name -> target; file -L describes the target.

    Behind the screen: lstat() looks at the link itself, stat() follows it.

  3. 3. What format is the content?

    file mystery (or file -i for a MIME type).

    Behind the screen: libmagic reads the first bytes and tests them against its signature database.

  4. 4. Look at the bytes yourself

    head -c 16 mystery | od -An -tx1

    Behind the screen: od prints the raw bytes in hexadecimal; compare with the magic-bytes table.

  5. 5. Size, owner and times

    stat mystery

    Behind the screen: every line of stat is a field of the inode.

  6. 6. Safe to view?

    Text: less. Binary: do not cat it (it can mess up your terminal; type reset if that happens).

    Behind the screen: binary bytes can be terminal control codes.
Quick check file report says “gzip compressed data”. How would you read it?
Answer: zcat report | less (or gunzip -c report): it is compressed, whatever its name says.

How Linux knows what a file is

Left: Riya’s terminal. Right: the directory entry, the bytes and the inode behind each answer.

Name, inode and magic bytes 5 steps
What you see
  1. Riya renames photo.jpg to photo.txt.
  2. cat prints the raw bytes, which are not text.
  3. file still reports a JPEG: it ignored the name.
  4. file -i gives the MIME type image/jpeg.
  5. To the kernel it is simply a regular file.
Behind the screen
  1. A rename only changes the name stored in the directory. The inode and the bytes are untouched.
  2. The file’s content is a series of bytes; the first ones of a JPEG are FF D8 FF E0.
  3. file compares those bytes with known signatures, the “magic numbers”.
  4. The signatures come from the compiled magic database installed with the tool.
  5. The inode’s mode says “regular file” plus permissions. That is all the kernel needs.

Real-time scenario 2

Three clocks on every file: atime, mtime, ctime

An auditor asks: “When was this file changed, and when were its permissions changed?” stat answers both. Times are examples.

atime, mtime and ctime 5 steps
Animated example
  1. When the file is created, all three times are the same.
  2. Writing new content updates mtime; because the inode changed too (new size), ctime moves as well.
  3. chmod changes only the inode, so only ctime moves. mtime keeps the real content time.
  4. Reading updates atime, but with the default relatime only if atime was older than mtime (or a day old).
  5. Remember: ctime is change time. The creation time is “Birth”, shown by stat on modern file systems.

Layer by layer: dissect the output of stat

Open each line of stat notes: what it means, why it exists, where it is stored, and when you will use it. Each comes with the real value for a fresh file on our build machine.

Six lines of stat, six fields of one inode. Click a line.

File / Size / Blocks name, bytes, space used

Why does it exist?

The size is what you see; Blocks is the disk space really used, which can differ.

How does it work?

Size = bytes of content (6 for “hello” + newline). Blocks counts 512-byte units allocated: 8 = 4 KiB, the smallest piece ext4 gives out.

Where is it, really?

Size and block count fields of the inode. “IO Block” is the preferred read size.

Where is it used?

Explaining why du and ls -l disagree; sparse files.

See this layer yourself (real output)

stat -c 'File: %n  Size: %s  Blocks: %b  IO Block: %o  %F' notes
File: notes Size: 6 Blocks: 8 IO Block: 4096 regular file

Device / Inode / Links where the inode is

Why does it exist?

A file is really identified by (device, inode number), not by its name.

How does it work?

Device = which file system; Inode = the record number inside it; Links = how many names point to it.

Where is it, really?

The inode table of the file system (Lesson 10.1).

Where is it used?

Hard links, finding files by inode, “disk full but df shows space” (out of inodes).

See this layer yourself (real output)

stat -c 'Device: %D  Inode: %i  Links: %h' notes
Device: fe00 Inode: 796575 Links: 1

Access (0644/-rw-r--r--) type and permissions

Why does it exist?

Who may read, write or run the file.

How does it work?

The mode in octal and letters. The type bits sit in the same field (here: regular file).

Where is it, really?

st_mode in the inode.

Where is it used?

Every permission problem (Module 9).

See this layer yourself (real output)

stat -c 'Access: (%a/%A)  type: %F' notes
Access: (644/-rw-r--r--) type: regular file

Uid / Gid owner and group

Why does it exist?

Permissions are applied to one user and one group.

How does it work?

Stored as numbers; stat also prints the names from /etc/passwd and /etc/group.

Where is it, really?

uid and gid fields of the inode.

Where is it used?

Files owned by a deleted user show only a number; chown fixes it.

See this layer yourself (real output)

stat -c 'Uid: (%u/%U)  Gid: (%g/%G)' notes
Uid: (30033/riya) Gid: (30033/riya)

Access / Modify / Change the three times

Why does it exist?

When was it read, when did its content change, when did its inode change?

How does it work?

atime, mtime and ctime with nanoseconds and time zone. A chmod one second later moves only Change.

Where is it, really?

Three timestamp fields of the inode, in seconds since 1970 (the Unix epoch) plus nanoseconds.

Where is it used?

Backups (mtime), audits (ctime), cleanup of unused files (atime).

See this layer yourself (real output)

sleep 1; chmod 600 notes; stat --printf 'Modify: %y\nChange: %z\n' notes
Modify: 2026-11-05 19:02:12.934380880 +0530 Change: 2026-11-05 19:02:13.936080121 +0530

Birth creation time

Why does it exist?

The question everyone asks: “when was this created?”

How does it work?

Recorded by newer file systems (ext4, xfs, btrfs); shown as “-” when unknown.

Where is it, really?

The crtime field of the inode, read through statx().

Where is it used?

Forensics, “which file appeared first?”.

See this layer yourself (real output)

stat -c 'Birth: %w' notes
Birth: 2026-11-05 19:02:13.952080122 +0530
Quick check After chmod 600 notes, which of atime, mtime and ctime changes?
Answer: Only ctime: the inode changed, the content did not.
6 Real-world use

File types at work

1. Upload checks

Web apps should check uploads by content (as file -i does), not by extension: a script renamed cat.jpg is still a script.

Upload→check bytes→reject fakes

2. Data engineering: check before loading

Before loading a file, file -i reveals the real format and encoding (a “CSV” that is really a ZIP, or UTF-16 text) that would break a pipeline.

File arrives→file -i→clean first

3. Developers: dotfiles

Project settings and secrets live in hidden files (.env, .git). ls -A before copying or zipping a project avoids leaking them.

Package→ls -A→no leaks

4. Security audits

Investigators compare mtime and ctime: a file whose ctime is recent but mtime old had its permissions or owner changed.

Alert→stat times→timeline

5. Containers and services

Docker, databases and systemd talk through socket files in /run; their permissions decide who may control them.

docker ps→socket→daemon

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.
