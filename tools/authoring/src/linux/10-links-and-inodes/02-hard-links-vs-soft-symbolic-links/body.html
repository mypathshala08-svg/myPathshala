2 Definition

Hard links and symbolic links

Formal definition (write this in exams)

A hard link is an additional directory entry that points to an existing inode; every hard link is an equal name for the same file, and the file’s data exists until the last link is removed. A symbolic (soft) link is a separate file of type link whose content is a path to another file or directory; the system follows that path each time the link is used, so the link breaks if the path no longer exists.

In simple words

Hard link: another name for the same file. Soft link: a pointer to a name.

Links at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: name tags and notes

Two ways to reach the same box.

Basic What you will type every day

  • ln -s /opt/app/bin/run ~/bin/run: a shortcut (symbolic link). ls -l shows run -> /opt/app/bin/run.
  • ln report.txt backup.txt: a second name (hard link). ls -li shows the same inode number and link count 2.
  • readlink -f run: where does it really point?
  • rm run: removes only the link, never the target.

Intermediate The rules, from inodes

  • Hard link = a new directory entry with the same inode number. All names are equal: there is no “original”. The data is freed when the last name is removed (and nobody has it open).
  • Hard links work only inside one filesystem (inode numbers are per disk) and not for folders (that could create loops).
  • Symbolic link = its own inode of type l, whose content is a path (its size is the path length). The path is resolved every time you use the link, relative to the folder the link is in.
  • Symlinks can point to folders, to other disks and to things that do not exist (yet): a dangling link.

Advanced Behind the screen: syscalls and kernel rules

  • ln calls linkat(); ln -s calls symlinkat(); readlink calls readlink(). open() follows symlinks automatically, up to 40 in a chain (then “Too many levels of symbolic links”, ELOOP).
  • Short symlink targets are stored inside the inode (“fast symlinks”), so they use no data block.
  • Symlink permissions are always lrwxrwxrwx and ignored: access is checked on the target. chmod on a link changes the target.
  • fs.protected_symlinks and fs.protected_hardlinks (on by default) stop classic /tmp attacks: you cannot follow another user’s symlink in a sticky folder, or hard-link a file you cannot read or write.
  • Renaming a symlink over another (mv -T new current) is atomic: zero-downtime deploys rely on it.

Did you know? Every folder already uses hard links: . is a hard link to the folder itself and .. to its parent. That is why a new folder has link count 2, and only the kernel may make such links to folders.

EXAM> “Order of arguments in ln?” → Like cp: first what exists (the target), then the new name. ln -s TARGET LINK_NAME.
Quick check A hard link and the original: which one is the “real” file?
Answer: Neither and both: they are two equal names for the same inode. There is no original once the link exists.
Common mistake
✗ln -s report.txt docs/report-link (run in ~/ln)
✓ln -s ../report.txt docs/report-link · or ln -sr report.txt docs/report-link · or an absolute path

A relative target is resolved from the link’s own folder (docs/), not from where you typed the command. -r computes the right relative path for you.

ln -sfn · mv -T in devops / cloud

  1. Situation: Zero-downtime release switch.

    cd ~/ln
ln -s releases/v2 current.tmp && mv -T current.tmp current

Common mistake
✗rm current/ · rm -r current/
✓rm current (no slash)

With a trailing slash the path means the folder behind the link. rm refuses or, with -r, deletes the folder’s contents. Without the slash only the link goes.

Undo and safety net

Links are cheap to remove and recreate; the danger is removing what is behind them.

  • Made a link in the wrong place: rm LINK (no trailing slash) and make it again.
  • Link points to the wrong target: ln -sfn RIGHT LINK.
  • Deleted the target of a symlink: restore the file at that path; the link works again automatically.
  • Deleted one hard link: the data is still there under the other names: find / -xdev -inum N.
  • ln -sf created v1/v2: rm releases/v1/v2, then use -sfn.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. ln docs docs-hard
    ln: docs: hard link not allowed for directory exit status: 1

    What it means: Hard links to folders are forbidden.

    Fix: ln -s docs docs-link.

  2. ln report.txt /mnt/tiny/r.txt
    ln: failed to create hard link '/mnt/tiny/r.txt' => 'report.txt': Invalid cross-device link exit status: 1

    What it means: Hard link across filesystems.

    Fix: Use ln -s, or copy.

  3. ln -s report.txt latest; ln -s report.txt latest
    ln: failed to create symbolic link 'latest': File exists exit status: 1

    What it means: The link name exists.

    Fix: ln -sf (or -sfn for folders).

  4. ln -s nothing.txt dead; cat dead
    cat: dead: No such file or directory exit status: 1

    What it means: Dangling link: target missing.

    Fix: readlink dead, then create the target or fix the link.

Quick check ln -s never complains about a missing target. Why is that a feature?
Answer: You can create links before the target exists (a config that will be installed later, a mount point), and links survive the target being replaced.

Build it step by step: a versioned release

Scenario: Riya deploys v1, then v2, then rolls back.

  1. 1. Live on v1.

    cd ~/ln; ln -sfn releases/v1 current; cat current/app.txt
    version 1

  2. 2. Atomic switch to v2.

    cd ~/ln; ln -s releases/v2 current.tmp && mv -T current.tmp current; cat current/app.txt
    version 2

  3. 3. Rollback.

    cd ~/ln; ln -sfn releases/v1 current; readlink current; cat current/app.txt
    releases/v1 version 1

Script it: deploy.sh

A tiny release switcher: checks the release exists, switches current atomically, prints the result. Rollback = run it with the old version.

cd ~/ln || exit 1
rel=releases/${1:-v2}
[ -d "$rel" ] || { echo "no such release: $rel" >&2; exit 1; }
ln -sfn "$rel" current.tmp && mv -T current.tmp current
echo "current -> $(readlink current)"
cat current/app.txt
current -> releases/v2 version 2

Run with v2 on the sample folder.

The text “report.txt” is resolved from the link’s own folder, docs/, so the link means docs/report.txt, which does not exist. Fix 1: ln -sfr report.txt docs/report-link (stores ../report.txt). Fix 2: an absolute target, ln -sf ~/ln/report.txt docs/report-link.

Quick check Does rm latest delete report.txt if latest is a symlink to it?
