The problem

Riya needs a tool called tree on a new server. On Windows she would search a website, download an installer and click Next five times. On Linux she types sudo apt install tree and two seconds later it is there, already in the PATH, with its manual page, and it will be updated together with the rest of the system. That is the package idea: software is shipped as signed archives (packages) that list what they need (dependencies), from trusted online stores (repositories), installed and tracked by a package manager. This lesson explains the moving parts and lets you build, inspect, install and remove a real package yourself.

By the end of this page you will be able to:
  • explain packages, repositories, package managers, dependencies and versions in plain words
  • tell the two big families apart (.deb with dpkg/apt, .rpm with rpm/dnf) and the universal formats (snap, flatpak, AppImage)
  • find out which package owns a file, what a package contains and what it depends on
  • build a tiny .deb package and install, upgrade and remove it, and see a dependency error happen

2 Definition

Packages, repositories and package managers

Formal definition (write this in exams)

A package is an archive containing a program’s files together with metadata (name, version, architecture, description, dependencies on other packages) and install scripts. A repository is a signed collection of packages served over the network. A package manager installs, upgrades and removes packages, resolves dependencies and keeps a database of every installed file. Debian and Ubuntu use .deb packages with dpkg and apt; Red Hat, Fedora and Rocky use .rpm with rpm and dnf.

In simple words

Signed boxes of software from trusted shops, installed and remembered by one tool.

Packages at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a shop, a box and a shopkeeper

You ask for a box; the shopkeeper brings it and everything it needs.

Basic What you will type

  • sudo apt install tree: install (Ubuntu/Debian).
  • sudo dnf install tree: install (Fedora/RHEL).
  • dpkg -S /usr/bin/ls: which package owns a file.
  • apt show tree: what a package is.

Intermediate The parts

  • A package (.deb or .rpm) is an archive of files plus metadata (name, version, architecture, dependencies, description) and optional maintainer scripts (run before/after install or removal).
  • A repository is a web server with many packages and a signed index; your system lists repositories in /etc/apt/sources.list.d/ or /etc/yum.repos.d/.
  • The low-level tool (dpkg, rpm) installs one package file and keeps the database; the high-level tool (apt, dnf) reads repositories, solves dependencies and calls the low-level tool.
  • Versions like 3.4-1ubuntu0.2 are “upstream version 3.4, Debian revision 1, Ubuntu’s 0.2 update”.

Advanced Behind the screen: indexes, signatures and the database

  • apt update downloads each repository’s InRelease file (signed with GPG) and Packages indexes into /var/lib/apt/lists/; the signature is checked against keys in /usr/share/keyrings/. A package whose checksum does not match the signed index is refused.
  • The installed-package database is /var/lib/dpkg/status plus per-package file lists /var/lib/dpkg/info/NAME.list (rpm: an SQLite database in /var/lib/rpm).
  • Dependency solving is a real constraint problem (versions, conflicts, “provides”); apt and dnf use solvers to choose a consistent set.
  • Downloaded package files are cached in /var/cache/apt/archives/ until apt clean.
  • A .deb is an ar archive with control.tar (metadata, scripts) and data.tar (the files); an .rpm is a header plus a cpio archive.

Did you know? Debian’s package archive has more than 60,000 source packages, maintained by about a thousand volunteers. Ubuntu builds on it, and many other distributions (Mint, Pop!_OS, Kali) build on Ubuntu or Debian: the same .deb format everywhere.

EXAM> “What is the difference between dpkg and apt?” → dpkg installs a single local .deb and does not resolve dependencies; apt uses repositories, downloads packages and resolves dependencies (and calls dpkg).

Undo and safety net

Package managers are designed to undo: remove, purge, reinstall.

  • Installed the wrong package: sudo apt remove NAME (or purge); apt autoremove for leftovers.
  • Broke dependencies with dpkg -i: sudo apt -f install fixes or removes the half-installed package.
  • Changed a packaged config file badly: sudo apt install --reinstall -o Dpkg::Options::=--force-confask PKG, or restore from /etc backup.
  • Added a bad repository: delete its file in /etc/apt/sources.list.d/ and its key, then apt update.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. dpkg -S /usr/bin/nosuchprog
    dpkg-query: no path found matching pattern /usr/bin/nosuchprog exit status: 1

    What it means: No package owns that path.

    Fix: Check the path; it may come from pip, snap or a manual install.

  2. dpkg -L nosuchpkg
    dpkg-query: package 'nosuchpkg' is not installed Use dpkg --contents (= dpkg-deb --contents) to list archive files contents. exit status: 1

    What it means: Not installed.

    Fix: apt search NAME to find the right name.

  3. dpkg -i /tmp/x.deb
    dpkg: error: requested operation requires superuser privilege exit status: 2

    What it means: Installing needs root.

    Fix: sudo dpkg -i, or better sudo apt install ./x.deb.

  4. apt-get -s install tree
    NOTE: This is only a simulation! apt-get needs root privileges for real execution. Keep also in mind that locking is deactivated, so don't depend on the relevance to the real current situation! Reading package lists... Building dependency tree... Reading state information... E: Unable to locate package tree exit status: 100

    What it means: Unknown package: the indexes are empty (no apt update yet) or the name is wrong.

    Fix: sudo apt update, then try again.

6 Real-world use

Packages at work

1. Building servers

Every server build (by hand, Ansible or a Dockerfile) is mostly “install these packages, change these configs”.

Base image→apt/dnf install→ready

2. Security updates

A vulnerability in OpenSSL is fixed once in the libssl package; every program using it is fixed by one upgrade (Lesson 19.3).

CVE→apt upgrade→patched

3. Vendor software

Docker, PostgreSQL, Grafana and Microsoft ship their own signed repositories so updates come through apt/dnf too.

Add repo→key + list→apt install

4. Troubleshooting

“Which package broke this file?” dpkg -S and dpkg --verify answer it; reinstalling the package repairs it.

Broken file→dpkg -S→reinstall

5. Internal packages

Companies package their own tools as .deb/.rpm and host a private repository, so deployment is apt install company-tool.

Code→dpkg-deb / rpmbuild→private repo

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

Scenario: Riya packages a one-line tool and installs it, step by step.

  1. 1. The files, in their final paths.

    cd ~/pk; mkdir -p uptime-mp_1.0/usr/local/bin; printf '#!/bin/sh\nuptime -p\n' > uptime-mp_1.0/usr/local/bin/uptime-mp; chmod 755 uptime-mp_1.0/usr/local/bin/uptime-mp; find uptime-mp_1.0 -type f
    uptime-mp_1.0/usr/local/bin/uptime-mp

  2. 2. The control file (metadata).

    cd ~/pk; mkdir -p uptime-mp_1.0/DEBIAN; printf 'Package: uptime-mp\nVersion: 1.0\nArchitecture: all\nMaintainer: Riya <riya@example.com>\nDescription: friendly uptime\n' > uptime-mp_1.0/DEBIAN/control; cat uptime-mp_1.0/DEBIAN/control | head -2
    Package: uptime-mp Version: 1.0

  3. 3. Build and inspect.

    cd ~/pk; dpkg-deb --build --root-owner-group uptime-mp_1.0 > /dev/null && dpkg-deb -I uptime-mp_1.0.deb | grep -E 'Package|Version'
    Package: uptime-mp Version: 1.0

  4. 4. Install and run.

    cd ~/pk; pdpkg -i uptime-mp_1.0.deb > /dev/null && pdpkg -l uptime-mp | tail -1 | awk '{print $1, $2, $3}'; ~/pk/root/usr/local/bin/uptime-mp | sed -E 's/[0-9]+/N/g'
    ii uptime-mp 1.0 up N hour, N minutes

V11

Compare versions the dpkg way

for p in '1.0 1.1' '1.0~rc1 1.0' '2:1.0 3.0'; do set -- $p; dpkg --compare-versions $1 lt $2 && echo "$1 < $2" || echo "$1 >= $2"; done
1.0 < 1.1 1.0~rc1 < 1.0 2:1.0 >= 3.0

~ sorts first; an epoch (2:) beats everything without one.

V12

Downgrade needs a deliberate step

cd ~/pk; pdpkg -i greet_1.1.deb > /dev/null; pdpkg -i greet_1.0.deb 2>&1 | grep -i -E 'downgrad' | head -1; ~/pk/root/usr/local/bin/greet
dpkg: warning: downgrading greet from 1.1 to 1.0 greet 1.0 says hello

dpkg warns but allows it; apt needs an explicit version.

V13

Purge vs remove

cd ~/pk; pdpkg -i greet_1.0.deb > /dev/null; pdpkg -r greet > /dev/null; pdpkg -l greet 2>/dev/null | tail -1 | cut -c1-3; pdpkg -P greet > /dev/null; pdpkg -l greet 2>&1 | tail -1 | cut -c1-40
dpkg: warning: ignoring request to remove greet which isn't installed dpkg-query: no packages found matching g

greet has no config files, so -r already removed it completely and -P has nothing left to do. Packages with config files in /etc stay as rc after -r until you purge.

Script it: whatpkg.sh

Explain where commands come from: for each command name, find its real path, the package that owns it, the package version and how many other installed packages depend on that package.

[ $# -eq 0 ] && set -- ls tmux awk python3
for c in "$@"; do
  p=$(command -v "$c") || { printf '%-8s not found\n' "$c"; continue; }
  real=$(readlink -f "$p")
  owner=$(dpkg -S "$real" 2>/dev/null | head -1 | cut -d: -f1)
  if [ -n "$owner" ]; then
    v=$(dpkg-query -W -f='${Version}' "$owner")
    n=$(apt-cache rdepends --installed "$owner" 2>/dev/null | tail -n +3 | wc -l)
    printf '%-8s %-28s %-14s %-18s needed by %s\n' "$c" "$real" "$owner" "$v" "$n"
  else
    printf '%-8s %-28s (not from a package)\n' "$c" "$real"
  fi
done
ls /usr/bin/ls coreutils 9.4-3ubuntu6.3 needed by 0 tmux /usr/bin/tmux tmux 3.4-1ubuntu0.2 needed by 1 awk /usr/bin/mawk mawk 1.3.4.20240123-1build1 needed by 0 python3 /usr/local/bin/python3.13 (not from a package)

Run without arguments, so it explains ls, tmux, awk and python3.

Both colleagues are right. A dependency is another package this one needs; report needs greet (version 1.0 or newer). dpkg -i only installs the file you give it, so report stayed “unpacked, not configured”. sudo apt install ./report_2.0.deb would read the repositories and install greet first (here greet is our own demo package, so it would have to be in a repository). And a .deb from a chat message runs its install scripts as root: install only from trusted repositories or sources, and inspect unknown packages with dpkg-deb -I and -c first.
