2 Definition

snap, flatpak and building from source

Formal definition (write this in exams)

snap and flatpak are distribution-independent package systems: each package bundles the application with the libraries it needs and runs it in a sandbox, so the same package works on Ubuntu, Fedora or Debian. Building from source means downloading the program’s source code (usually a .tar.gz tarball), checking it, and compiling and installing it yourself, typically with ./configure, make and make install.

snap, flatpak and source at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: who keeps it up to date?

The further right, the more work for you.

Basic What you will type

  • sudo snap install firefox, snap list, sudo snap remove firefox.
  • flatpak install flathub org.gimp.GIMP, flatpak run org.gimp.GIMP.
  • tar -xzf app-1.0.tar.gz; cd app-1.0; ./configure; make; sudo make install.

Intermediate The differences that matter

  • Snap channels: latest/stable, candidate, beta, edge; sudo snap refresh --channel=5.21/stable lxd. snap revert goes back one revision.
  • Confinement: strict (sandboxed), classic (full access, like a normal program, needs --classic), devmode (testing).
  • Flatpak runtimes (org.freedesktop.Platform, org.gnome.Platform) are shared between apps; permissions are changed with Flatseal or flatpak override.
  • Source: --prefix chooses where files go (default /usr/local); make install into /usr/local needs sudo, into $HOME/.local does not.

Advanced Behind the screen: squashfs, OSTree and Makefiles

  • A snap is a compressed squashfs image mounted read-only under /snap/NAME/REV (look at mount | grep snap); snapd is a systemd service; the sandbox uses AppArmor, seccomp and cgroups.
  • Flatpak stores apps in an OSTree repository (Git-like, deduplicated) under /var/lib/flatpak and runs them through bubblewrap with namespaces (Lesson 20.3).
  • ./configure (usually generated by GNU Autoconf) tests the system and writes the Makefile; CMake (cmake -B build; cmake --build build) and Meson are modern alternatives.
  • DESTDIR=/tmp/stage make install installs into a staging tree: how packagers turn source into .deb/.rpm, and how you can see exactly which files will be installed.

Did you know? Snaps update themselves automatically, by default up to four times a day. sudo snap refresh --hold=24h pauses updates, and snap refresh --time shows the schedule.

EXAM> “What does make install do, and where do files go?” → It copies the built files to the directories under the prefix chosen by ./configure (default /usr/local: bin, lib, share), which is why it usually needs sudo; no package manager records them.
Quick check Why install source builds under /usr/local and not /usr?
Answer: /usr belongs to the package manager; /usr/local is reserved for locally built software, so the two never overwrite each other.
Common mistake
✗sudo make install straight into /usr
✓./configure --prefix=/usr/local (default) or --prefix=$HOME/.local

Files in /usr can overwrite or be overwritten by distro packages, and nothing records them for removal.

Common mistake
✗building a downloaded tarball without checking it
✓sha256sum -c SHA256SUMS (and gpg --verify if a .asc signature is published)

A tampered or truncated download would be compiled and installed, often as root.

sha256sum -c · tar -tzf · tar -xzf verify and unpack

Undo and safety net

Every way has an undo; source builds need you to plan it.

  • Bad snap update: sudo snap revert NAME (previous revision is kept).
  • Flatpak: flatpak uninstall ID; --delete-data also removes its ~/.var/app data.
  • Source build: make uninstall from the same source tree, or delete the prefix directory (~/.local/opt/NAME) if you used one per program.
  • Wrong prefix: make clean, rerun ./configure --prefix=…, make again.

6 Real-world use

Where each way is used

1. Ubuntu desktops and LXD

Firefox and LXD ship as snaps on Ubuntu; servers hold refreshes to maintenance windows.

Install→snap→auto-update

2. Fedora and Steam Deck

Fedora Silverblue and SteamOS install desktop apps as flatpaks on a read-only base system.

Read-only OS→flatpak→apps

3. Research clusters

HPC centres build scientific software from source into versioned prefixes (/opt/app/1.2), loaded with environment modules.

Tarball→prefix→module load

4. Making packages

Package builders run make DESTDIR=… install and wrap the staged files into a .deb or .rpm.

Build→stage→.deb/.rpm

5. Newest tool versions

When a team needs a newer version than the LTS repos have, a source build into ~/.local avoids touching the system.

Old in repo→~/.local→new version

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

V8

Record a manifest with DESTDIR

cd ~/src/greet-1.2; make DESTDIR=$HOME/stage install > /dev/null; (cd ~/stage && find . -type f) | sed 's|^\.||' > ~/greet.manifest; cat ~/greet.manifest | sed "s|$HOME|~|"
~/.local/opt/greet/share/doc/greet/README ~/.local/opt/greet/bin/greet

A list to delete later.

V9

Uninstall from the manifest

xargs rm -v < ~/greet.manifest | sed "s|$HOME|~|"
removed '~/.local/opt/greet/share/doc/greet/README' removed '~/.local/opt/greet/bin/greet'

Works even without make uninstall.

Script it: build-from-source.sh

Verify, unpack, configure into a per-program prefix, build, install, and print how to uninstall: the whole safe routine for a tarball, stopping at the first failure.

set -e
tarball=~/dl/greet-1.2.tar.gz
name=$(basename "$tarball" .tar.gz)
prefix=$HOME/.local/opt/$name
cd "$(dirname "$tarball")" && sha256sum -c SHA256SUMS
mkdir -p ~/src && tar -xzf "$tarball" -C ~/src
cd ~/src/"$name"
./configure --prefix="$prefix" > /dev/null
make -j"$(nproc)" > /dev/null
make install > /dev/null
echo "installed: $(find "$prefix" -type f | wc -l) files under ${prefix/#$HOME/\~}"
"$prefix"/bin/greet script
echo "uninstall: rm -r ${prefix/#$HOME/\~}"
greet-1.2.tar.gz: OK installed: 2 files under ~/.local/opt/greet-1.2 Hello, script! (greet 1.2) uninstall: rm -r ~/.local/opt/greet-1.2

Each program gets its own prefix, so uninstalling is deleting one directory.

Puzzle answer Remember the question from the story? Open to check your guess.

1. VS Code is a classic snap (it needs full access to your files and tools): sudo snap install code --classic. 2. The default prefix /usr/local belongs to root, so make install as a normal user fails; use sudo make install, or better, ./configure --prefix=$HOME/.local and install without sudo. 3. Keep the source directory for make uninstall, install each program into its own prefix (delete the directory to remove it), or record a manifest with make DESTDIR=… install first.

Quick check Which command removes a source-built program installed with --prefix=$HOME/.local/opt/greet?
Answer: rm -r ~/.local/opt/greet (or make uninstall in its source tree).
