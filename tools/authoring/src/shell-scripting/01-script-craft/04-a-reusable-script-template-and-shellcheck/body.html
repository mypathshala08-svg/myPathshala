2 Definition

A script template and ShellCheck

Formal definition (write this in exams)

A script template is a ready-made starting file that contains a team’s standard structure (header, safe mode, option parsing, logging, clean-up, main) so every new script begins complete and consistent. ShellCheck is a static analysis tool (a linter) for shell scripts: it reads a script without running it and reports likely bugs and bad practices, each with a code such as SC2086 and an explanation.

In simple words

Start from the same skeleton; let a tool proof-read it.

Templates and linting at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a form and a proof-reader

A printed form makes sure nobody forgets a field; a proof-reader catches the typos you no longer see. The template is the form, ShellCheck the proof-reader.

Basic What you will type

  • bin/newscript sync.sh "sync reports to the share"
  • write the work inside main(), wrap risky commands in run
  • bash -n bin/sync.sh && shellcheck bin/sync.sh
  • bin/sync.sh -n ARG (dry run) before the real run

Intermediate The differences that matter

  • run cmd args executes cmd, or with -n only logs it: one switch makes every risky step previewable.
  • trap cleanup EXIT runs on every exit (success, die, set -e, Ctrl+C), so temp files never pile up.
  • ShellCheck severities: error, warning, info, style; -S warning hides the rest; # shellcheck disable=SC2086 on the line before silences one rule on purpose.
  • bash -n only checks syntax; ShellCheck checks meaning; only a test run checks behaviour. You need all three.

Advanced Behind the screen: static analysis

  • ShellCheck (written in Haskell) parses the script into a syntax tree and runs over 300 checks on it, without executing anything; it knows how word splitting, globbing and quoting really work in sh, bash, dash and ksh.
  • It reads the shebang (or # shellcheck shell=bash) to choose the dialect, so [[ ]] in a #!/bin/sh script is flagged (SC3010).
  • -f gcc and -f json outputs feed editors (VS Code extension) and CI annotations; -x follows sourced files.
  • shfmt is the matching formatter (indentation, spacing), often run next to ShellCheck in pre-commit hooks.

Did you know? ShellCheck’s wiki has a page for every rule (for example SC2086) explaining the problem, the fix, and rare exceptions. Reading the page for each warning you meet is one of the fastest ways to really understand quoting and word splitting.

EXAM> “What is the most common ShellCheck warning?” → SC2086, “Double quote to prevent globbing and word splitting”: an unquoted $variable that would break on spaces or wildcards.
Quick check Why does the template use trap cleanup EXIT instead of rm at the end of main?
Answer: EXIT runs on every exit, including errors, die and Ctrl+C; a line at the end of main runs only on success.

SC2164 · SC2115 · SC2154 fix: cd and rm

🔴 Can destroy datano sudo

Undo and safety net

Template and linter mistakes are easy to undo; the bugs they prevent are not.

  • Generated the wrong name: mv bin/old.sh bin/new.sh and fix the header line.
  • Template changed badly: it is in git: git checkout -- templates/script.sh.
  • False positive: # shellcheck disable=SC2086 # reason on the line before, never for the whole file.
  • A risky script already ran: that is why -n exists: always dry-run first next time.

Templates and linting at work

1. Team script repositories

Ops teams keep a scripts repo with a template and a generator; every script has the same options and logs.

GitHub Actions and GitLab run ShellCheck on every pull request; warnings block the merge.

PR→shellcheck→merge

The ShellCheck extension underlines problems while typing, long before review.

type→underline→fix

Cleanup and migration scripts are always run with -n first; reviewers ask for the dry-run output.

-n→review→real run

The pre-commit framework runs shellcheck and shfmt before every git commit.

commit→hook→clean

Script it: lint-all.sh

Check every script in bin/: syntax with bash -n, ShellCheck if it is installed, and a warning for scripts without safe mode. Exit 1 if anything fails.

#!/usr/bin/env bash
set -uo pipefail
mkdir -p demo/bin && cd demo        # two sample scripts to check
printf '#!/usr/bin/env bash
set -euo pipefail
echo ok
' > bin/good.sh
printf '#!/bin/bash
for f in $(ls); do echo $f
' > bin/broken.sh
fails=0
have_sc=0; command -v shellcheck >/dev/null && have_sc=1
for f in bin/*; do
  if ! bash -n "$f" 2>/dev/null; then echo "FAIL syntax   $f"; ((++fails)); continue; fi
  if (( have_sc )) && ! shellcheck -S warning "$f" >/dev/null; then echo "FAIL lint     $f"; ((++fails)); continue; fi
  grep -q 'set -euo pipefail' "$f" || { echo "WARN no safe mode  $f"; ((++fails)); continue; }
  echo "ok            $f"
done
(( have_sc )) || echo "(shellcheck not installed: syntax and safe-mode checks only)"
echo "problems: $fails"
exit $(( fails > 0 ))
FAIL syntax bin/broken.sh ok bin/good.sh (shellcheck not installed: syntax and safe-mode checks only) problems: 1
