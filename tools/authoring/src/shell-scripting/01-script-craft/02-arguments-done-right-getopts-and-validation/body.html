2 Definition

Options, operands and getopts

Formal definition (write this in exams)

Command-line options are named arguments, usually a dash and a letter (-c) or two dashes and a word (--city), that change how a program behaves; some take a value. Operands are the remaining arguments, the things the program works on. getopts is a Bash built-in that reads short options one by one according to an option string, putting the letter in a variable and any value in OPTARG.

In simple words

Named, optional, any order, checked: options. What you work on: operands.

Options and getopts at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a food order

“One masala dosa, extra chutney, no onion, to take away.” The dish is the operand; the rest are options, in any order, each optional.

Basic What you will type

  • Option string ':c:s:n:o:vh': a letter followed by : needs a value.
  • while getopts ':c:vh' opt; do case $opt in c) city=$OPTARG ;; v) verbose=1 ;; esac; done
  • shift $((OPTIND - 1)), then $1 is the first operand.

Intermediate The differences that matter

  • A leading : in the option string switches on silent mode: getopts prints nothing and gives you ? (unknown option) or : (missing value) with the letter in OPTARG, so your own message and exit code 2 are used.
  • getopts handles grouped flags (-vh) and attached values (-cPune) for free.
  • getopts stops at the first operand: options must come before the file. -- ends options explicitly.
  • Long options are not supported by getopts; use a while (( $# )) loop with case "$1".

Advanced Behind the screen: OPTIND and the external getopt

  • OPTIND is the index of the next argument to look at (starts at 1). Each call to getopts reads one option and moves OPTIND on; when it meets an operand or -- it returns non-zero and the loop ends.
  • OPTIND is a global variable: in a function that parses options, set local OPTIND=1 or a second call parses nothing.
  • The separate getopt program (util-linux, one word, no s) does support long options and reordering, but it differs between Linux and macOS; getopts is POSIX and works everywhere Bash and sh do.
  • GNU convention (followed by most Linux tools): -h/--help exits 0, --version prints a version, errors exit 2 and print usage to stderr.

Did you know? POSIX’s “Utility Syntax Guidelines” are why almost every Unix tool feels the same: single-letter options with one dash, groupable (-la), options before operands, and -- to end options. getopts implements exactly these rules.

EXAM> “What do OPTARG and OPTIND hold?” → OPTARG holds the value of the option just read (or the bad letter in silent mode); OPTIND is the index of the next argument to process, used with shift $((OPTIND-1)) to reach the operands.
Quick check In the option string ':c:vh', which options need a value?
Answer: Only c (it is followed by a colon); v and h are flags. The first colon switches on silent mode.

while (( $# )); case $1 in --city=*) … ; shift long options

🟢 Read-onlyno sudo

getopts cannot read --city. A while (( $# > 0 )) loop looks at $1, matches it with case, takes the value from $2 (then shift 2) or from ${1#*=} for the --city=Pune form, and stops at -- or the first operand.

✓ Use it when
  • GNU-style tools
  • --dry-run, --help
✗ Don’t use it when
  • when short options are enough

Syntax: case $1 in -c|--city) city=$2; shift 2 ;; --city=*) city=${1#*=}; shift ;; --) shift; break ;; esac

parse() {
  local city="" dry=0 files=()
  while (( $# > 0 )); do
    case $1 in
      -c|--city) city=$2; shift 2 ;;
      --city=*) city=${1#*=}; shift ;;
      --dry-run) dry=1; shift ;;
      --) shift; files+=("$@"); break ;;
      -*) echo "unknown option $1" >&2; return 2 ;;
      *) files+=("$1"); shift ;;
    esac
  done
  echo "city=${city:-all} dry=$dry files=${files[*]}"
}
parse --city=Pune --dry-run a.csv
parse a.csv -c Mumbai b.csv
parse -- -odd-name.csv
city=Pune dry=1 files=a.csv city=Mumbai dry=0 files=a.csv b.csv city=all dry=0 files=-odd-name.csv

Unlike getopts, this loop also accepts options after operands.

Undo and safety net

Option parsing mistakes are fixed by rerunning; prevent the expensive ones:

  • Option after the file ignored: put options first, or switch to a while/case loop.
  • Destructive script got a wrong value: validate first, act second; add -n/--dry-run to preview.
  • File name starting with -: ./script.sh -- -file.csv or ./-file.csv.
  • getopts in a function parses nothing the 2nd time: local OPTIND=1 at the start of the function.

Script it: opts-skeleton.sh

The getopts block from this lesson, ready to paste into the Lesson 1.1 skeleton.

#!/usr/bin/env bash
set -euo pipefail
readonly PROG=${0##*/}
name=world loud=0
usage() { echo "Usage: $PROG [-l] [-n NAME] [-h]"; }
bad()   { echo "$PROG: $*" >&2; usage >&2; exit 2; }

while getopts ':n:lh' opt; do
  case $opt in
    n) name=$OPTARG ;;
    l) loud=1 ;;
    h) usage; exit 0 ;;
    :) bad "option -$OPTARG needs a value" ;;
    \?) bad "unknown option -$OPTARG" ;;
  esac
done
shift $((OPTIND - 1))
(( $# == 0 )) || bad "unexpected argument '$1'"

msg="Hello, $name"
(( loud )) && msg=${msg^^}
echo "$msg"
Hello, world

Run with no options it prints Hello, world.

Puzzle answer Remember the question from the story? Open to check your guess.

1. Positions break as soon as an argument is optional: leaving the city out shifts “failed” into $1. Named options with defaults fix it. 2. getopts stops at the first operand; data/orders.csv -c Pune leaves -c Pune unread (orders.sh then complains about 3 operands). Put options first, or use a while/case loop that accepts both orders. 3. Without a leading colon in the option string, Bash prints its own “option requires an argument -- c”. With ':c:…' getopts is silent and gives you : with the letter in OPTARG, so you print your own message, the usage and exit 2.

Quick check Which variable holds the value of -c inside the loop?
Answer: OPTARG.
