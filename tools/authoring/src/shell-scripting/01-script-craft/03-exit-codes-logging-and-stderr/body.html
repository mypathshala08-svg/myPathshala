The problem

Every night at 2 a.m. Riya’s import.sh loads the day’s orders. One morning the dashboard is empty, cron says nothing, and the script’s only trace is a line “done” in a file nobody reads. Did it fail? Why? When? A script talks to the world in exactly three ways: its exit code (did it work?), its standard output (the result) and its standard error (messages for humans and logs). This lesson gives Riya’s job a clear exit-code contract, log lines with time and level, a log file, and the system log, all with real runs.

By the end of this page you will be able to:
  • design exit codes for a script (0, 1, 2 and your own) and check them with $?, &&, ||, if and PIPESTATUS
  • keep results on stdout and every message on stderr, and redirect each where it belongs
  • write timestamped, levelled log lines (DEBUG, INFO, WARN, ERROR) with a small reusable library
  • log to a file and to the system log with logger, and read them back

2 Definition

Exit codes, stderr and log lines

Formal definition (write this in exams)

An exit code (exit status) is the number from 0 to 255 a program returns when it ends: 0 means success, anything else a kind of failure. Standard error (stderr, file descriptor 2) is the output stream for diagnostics, kept separate from standard output (the result). A log line is a diagnostic message with at least a timestamp, a severity level and the program name, written to stderr, a file or the system log.

In simple words

Code for machines, log lines for humans, stdout for the result.

Exit codes and logging at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a courier delivery

The parcel is the result (stdout). The tracking messages are the log (stderr). “Delivered” or “Failed: address not found” is the exit code: the one thing the sender’s system checks.

Basic What you will type

  • exit 0 success, exit 1 error, exit 2 wrong usage.
  • echo "…" >&2 for every message.
  • echo "$(date '+%F %T') [INFO] started" >&2.
  • ./job.sh >> job.log 2>&1 in cron.

Intermediate The differences that matter

  • $? is overwritten by the very next command: save it at once (rc=$?).
  • In a pipeline, $? is the last command’s status; ${PIPESTATUS[@]} holds each one, and set -o pipefail uses the worst.
  • Levels: DEBUG < INFO < WARN < ERROR; a LOG_LEVEL variable decides what is printed.
  • logger -t name "msg" writes to syslog/journald; read with journalctl -t name.

Advanced Behind the screen: 8 bits and file descriptors

  • An exit status is one byte: exit 256 becomes 0, exit -1 becomes 255. Codes above 125 are reserved by the shell (126 not executable, 127 not found, 128+N killed by signal N).
  • stdout is file descriptor 1 and stderr 2; both point at the terminal by default. 2>&1 copies fd 1 into fd 2 at that moment, which is why order matters.
  • stdout to a file or pipe is block-buffered, stderr is unbuffered, so in a shared log file their lines can appear out of order.
  • logger sends to /dev/log; journald stores it with time, host, PID and priority; -p user.err sets the priority.

Did you know? grep uses three exit codes on purpose: 0 = found, 1 = not found, 2 = error (such as a missing file). That is why grep -q pattern file works perfectly in if, and why a script should also give different failures different codes.

EXAM> “How do you get the exit status of each command in a pipeline?” → ${PIPESTATUS[@]} right after the pipeline, or set -o pipefail to make $? the last non-zero status.
Quick check Why must rc=$? come immediately after the command?
Answer: Every command, even echo or [[, replaces $?.
Common mistake
✗job.sh | tee job.log in cron
✓set -o pipefail; job.sh 2>&1 | tee -a job.log (or job.sh >> job.log 2>&1)

The pipeline’s status is tee’s (0), so cron never sees the failure, and stderr is not in the log.

Common mistake
✗echo "ERROR: disk full"
✓log_error "disk full"; exit 1 (time, level, stderr, a code)

A message on stdout pollutes the result, has no time, and the exit code still says success.

Undo and safety net

Logging mistakes are cheap to fix; lost information is not.

  • Lost a failure in a pipe: add set -o pipefail or check ${PIPESTATUS[0]}.
  • Messages missing from the log: you captured stdout only: add 2>&1 after the file.
  • Log file filled the disk: truncate it (: > job.log) and add logrotate (Linux 18.2).
  • Secrets in logs: never log passwords or tokens; mask them (${TOKEN:0:4}****).

Error messages decoded

Errors students see most (really run on our build machine).

  1. bash -c 'exit 256'; echo "reported as $?"
    reported as 0 exit status: 0

    What it means: Codes wrap around at 256: this is reported as 0, a “success”.

    Fix: Use 0–125 for your own codes.

  2. false; echo "checked"; echo "rc=$?"
    checked rc=0 exit status: 0

    What it means: $? now belongs to the first echo, so it says 0.

    Fix: rc=$? immediately after the command.

  3. cd ~/ops && bash -c 'source bin/log.sh; LOG_LEVEL=TRACE; log_info hi'
    bin/log.sh: line 7: ((: 20 >= : syntax error: operand expected (error token is ">= ") exit status: 0

    What it means: Unknown level: the associative-array lookup gives an empty value and the (( )) test breaks.

    Fix: Validate LOG_LEVEL against DEBUG|INFO|WARN|ERROR.

6 Real-world use

Exit codes and logs at work

1. Cron jobs

cron mails stderr to MAILTO and monitoring checks the exit code; a script with clear codes pages the right person.

job→exit code→alert

2. CI pipelines

Any non-zero exit fails the step; good log lines make the failed build readable.

step→non-zero→red build

3. systemd services and timers

stderr of a service goes straight into the journal; journalctl -u job -p err shows only failures.

service→stderr→journal

4. Data pipelines

Airflow’s BashOperator fails a task on non-zero; a separate code for “bad data” lets the DAG retry only real outages.

task→exit 3→no retry

5. Central logging

Timestamped, levelled lines ship to Elasticsearch/Loki and become searchable dashboards.

line→fields→dashboard

Script it: run-and-log.sh

A wrapper that runs any command, logs start, end, duration and exit code, and passes the code on, so any job becomes observable without changing it.

#!/usr/bin/env bash
set -uo pipefail
log() { echo "$(date -d "${LOG_NOW:-now}" '+%F %T') [$1] run: ${*:2}" >&2; }

run() {
  local start rc
  start=$(date +%s)
  log INFO "start: $*"
  "$@"; rc=$?
  if (( rc == 0 )); then log INFO "ok in $(( $(date +%s) - start ))s"
  else log ERROR "failed with exit $rc: $*"; fi
  return $rc
}

LOG_NOW='2026-11-12 02:00'
run ls /etc/hostname
run ls /nonexistent
echo "wrapper passed on: $?"
2026-11-12 02:00:00 [INFO] run: start: ls /etc/hostname /etc/hostname 2026-11-12 02:00:00 [INFO] run: ok in 0s 2026-11-12 02:00:00 [INFO] run: start: ls /nonexistent ls: cannot access '/nonexistent': No such file or directory 2026-11-12 02:00:00 [ERROR] run: failed with exit 2: ls /nonexistent wrapper passed on: 2

No set -e here: the wrapper must survive the failure to log it.

Puzzle answer Remember the question from the story? Open to check your guess.

1. In import.sh | tee run.log, $? is tee’s status (0). Use set -o pipefail, check ${PIPESTATUS[0]}, or avoid the pipe: import.sh >> run.log 2>&1. 2. The pipe carries only stdout; messages on stderr went straight to the screen (or cron’s mail). Add 2>&1 before the pipe. 3. Any number from 0 to 255 is allowed; 0 is success, 1 and 2 are conventions, and your own codes such as 3 = “bad data” tell the caller which failure happened. Document them at the top of the script.
