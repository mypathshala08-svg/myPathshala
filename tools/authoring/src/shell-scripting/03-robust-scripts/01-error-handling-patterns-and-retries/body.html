The problem

Riya’s nightly sync calls a partner API, copies files and loads a database. Some failures are permanent (a wrong password, a missing file) and the job should stop at once with a clear error. Others are temporary (the API answers “service unavailable”, the network blinks) and the right reaction is to wait and try again. In Lesson 1.1 she learned set -euo pipefail; this lesson shows where it silently does not stop a script, how an ERR trap reports exactly which line failed, and how a small retry function with back-off turns a flaky step into a reliable one.

By the end of this page you will be able to:
  • know exactly when set -e stops a script and the cases where it does not (if, &&, ||, !, local x=$(…), subshells)
  • report failures with an ERR trap: line number, command and exit code, with set -E for functions
  • handle errors explicitly with || die, if ! cmd, and fallbacks with ||
  • write a retry function with a limit and exponential back-off, retrying only temporary errors

Riya’s script has set -euo pipefail at the top. Yet local total=$(compute_total) fails and the script happily continues with an empty total. And the nightly API call fails roughly one night in ten with “503 service unavailable”, waking her up for nothing because it would have worked a minute later. Keep your guess in mind. The answer is at the end of part 6.

In ~/ops (every run in this lesson is real). bin/flaky NAME N is a stand-in for a flaky API: it fails the first N calls with exit 75 (“try again later”), then succeeds.

K> Isn’t set -e enough? A> It is a safety net with holes. Bash deliberately ignores failures in places where a failure is part of the logic: the test of an if or while, the left side of &&/||, after !. 2 Definition

Error handling in Bash

Formal definition (write this in exams)

Error handling is deciding, for every command that can fail, what the script does next: stop with a message, use a fallback, ignore it on purpose, or try again. Bash offers set -e (exit on unhandled failures), explicit checks (if, ||), the ERR trap (run code whenever a command fails) and loops for retries.

In simple words

Every failure gets a decision: stop, fall back, ignore on purpose, or retry.

Error handling at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a delivery driver

Wrong address: stop and report. Customer not home: come back later, a few times. Doorbell broken: knock instead. Three different reactions to “it did not work”.

Basic What you will type

  • cp config.yml /etc/app/ || die "cannot install config"
  • curl -fsS "$url" -o out.json || retry 5 curl -fsS "$url" -o out.json
  • trap 'echo "line $LINENO: $BASH_COMMAND failed" >&2' ERR
  • local x; x=$(cmd) (two lines, never local x=$(cmd))

Intermediate The differences that matter

  • set -e ignores failures in if/while/until tests, in a && b except the last command, after !, and inside functions called from those places.
  • The ERR trap fires on the same failures set -e would act on; set -E makes it work inside functions and subshells too.
  • Retry with a limit, growing waits (exponential back-off) and a little jitter so 100 servers do not retry at the same second.
  • Decide by exit code what is temporary: curl 6/7/28 (DNS, connect, timeout), HTTP 429/503, sysexits 75 (EX_TEMPFAIL).

Advanced Behind the screen: errexit’s rules

  • POSIX defines errexit as “exit if a simple command fails, unless it is part of a condition”; the condition context is inherited by everything called from it, so if myfunc; then disables set -e for the whole body of myfunc.
  • local, export, declare and readonly are commands with their own status (0 when the assignment works): the $( ) status is lost. ShellCheck flags it as SC2155.
  • Command substitution runs in a subshell that inherits set -e only with shopt -s inherit_errexit (Bash 4.4+).
  • $LINENO in an ERR trap is the line of the failing command; ${BASH_SOURCE[1]}, ${FUNCNAME[1]} and caller give a small stack trace.

Did you know? The Bash manual itself warns that set -e’s rules are complicated, and many experienced scripters use it only together with explicit checks. The pattern in this lesson (set -euo pipefail + ERR trap + explicit || die on important steps) gives you both: a safety net and clear intent.

EXAM> “Why didn’t set -e stop my script when local x=$(false) failed?” → local is a separate command whose own status (0) replaces the substitution’s status; declare first, then assign: local x; x=$(cmd).
Quick check Inside if myfunc; then …, does set -e work in myfunc?
Answer: No: the condition context is inherited by the whole function body.
Common mistake
✗local result=$(compute)
✓local result; result=$(compute)

The failure of compute is hidden by local’s own exit status 0.

Common mistake
✗for i in 1 2 3 4 5; do curl … && break; done (retry with no pause)

trap 'on_err $LINENO' ERR · set -E · $BASH_COMMAND report where it failed

🟢 Read-onlyno sudo

An ERR trap runs whenever a command fails (where set -e would act). Print the line ($LINENO passed in), the command ($BASH_COMMAND) and the status. set -E makes the trap work inside functions and subshells.

✗ Don’t use it when

retry MAX cmd args · back-off · RETRY_ON retry with back-off

🟢 Read-onlyno sudo

The retry function runs the command; on success it returns 0. On a temporary exit code (listed in RETRY_ON, default 75, 6, 7, 28) it waits 1 s, 2 s, 4 s… and tries again, up to MAX attempts. Any other code is permanent: it gives up at once and passes the code on.

✓ Use it when
  • network calls
  • APIs
  • locks
✗ Don’t use it when
  • permanent errors
  • non-idempotent steps

Syntax: retry 5 curl -fsS "$url" -o data.json

retry MAX cmd args · back-off · RETRY_ON in security

  1. Situation: Permanent errors are not retried.

    cd ~/ops; source bin/retry.sh; retry 5 bash -c 'echo "auth: invalid password" >&2; exit 77'; echo "exit $?"
    auth: invalid password retry: permanent error (77), not retrying exit 77

    Why this way: Retrying a wrong password would only lock the account.

  2. Situation: Read the function.

    cd ~/ops; cat bin/retry.sh
    retry() { # retry MAX CMD ARGS... (exponential back-off; retries only exit codes listed in RETRY_ON) local max=$1 n=1 rc wait; shift while true; do "$@" && return 0 rc=$? if [[ " ${RETRY_ON:-75 6 7 28} " != *" $rc "* ]]; then echo "retry: permanent error ($rc), not retrying" >&2; return "$rc"; fi (( n >= max )) && { echo "retry: giving up after $n attempts" >&2; return "$rc"; } wait=$(( 2 ** (n - 1) )) echo "retry: attempt $n failed ($rc), waiting ${wait}s" >&2 sleep "$(awk -v w="$wait" -v s="${RETRY_SLEEP_SCALE:-1}" 'BEGIN{print w*s}')" (( n++ )) done }

    Why this way: 15 lines you can paste into the template.

Undo and safety net

Error handling is about recovery; plan the undo for each step:

  • Half-done job: make steps idempotent (safe to run again) and write results atomically (Lesson 2.3).
  • Retried a step that should not repeat (a payment, an email): only retry idempotent steps, or check “already done?” first.
  • Script stopped too early (|| true missing): decide per step; never sprinkle set +e.
  • Silent failure found later: add the ERR trap and the split local x; x=$(…), then rerun.

Error messages decoded

Errors students see most (really run on our build machine).

  1. bash -c 'set -e; f(){ local x=$(false); echo "got [$x], status hidden"; }; f'
    got [], status hidden exit status: 0

    What it means: local hid the failure of the substitution.

    Fix: local x; x=$(false)

  2. bash -c 'set -e; trap "echo line $LINENO" ERR; false'
    line 1 exit status: 1

    What it means: Double quotes expanded $LINENO when the trap was set (line 1), not when it ran.

    Fix: Single quotes: trap 'echo line $LINENO' ERR

  3. for i in 1 2 3; do curl -fsS http://127.0.0.1:9 -o /dev/null 2>/dev/null && break; echo "try $i failed"; done
    try 1 failed try 2 failed try 3 failed exit status: 0

    What it means: Retries with no pause and no limit check: all three fail within milliseconds.

    Fix: retry with back-off; check the final status.

Quick check Which exit codes should a retry function retry?
Answer: Only temporary ones (timeouts, connection refused, 429/503, EX_TEMPFAIL 75), never permanent ones such as bad credentials or missing files.

6 Real-world use

Error handling at work

1. Partner APIs

Nightly jobs retry 503/429 with back-off before paging anyone; most “incidents” disappear.

503→retry→success

2. Deploy pipelines

set -euo pipefail plus an ERR trap that prints the step and line makes failed deploys readable in CI logs.

3. Cloud provisioning

A new VM or DNS record is not ready instantly; scripts poll with a deadline instead of failing at once.

create→poll→ready

4. Data loads

Missing source files are permanent errors (stop, alert); a busy database lock is temporary (retry).

classify→stop / retry→load

Kubernetes restarts failed pods with back-off too; exit codes decide whether a Job is retried.

Script it: sync.sh

A nightly sync step with every pattern: safe mode with errtrace, an ERR trap that names the line, a fallback, a harmless step, a permanent check and a retried flaky call.

#!/usr/bin/env bash
set -eEuo pipefail
cd ~/ops
die() { echo "sync: error: $*" >&2; exit 1; }
trap 'echo "sync: failed at line $LINENO: $BASH_COMMAND" >&2' ERR
source bin/retry.sh
export RETRY_SLEEP_SCALE=0.1

[[ -r data/orders.csv ]] || die "orders.csv missing"           # permanent: stop
extra=$(cat data/extra.csv 2>/dev/null || echo "")               # optional: fallback
rm -f state/sync.lock || true                                     # harmless
retry 5 bin/flaky partner 2                                       # temporary: retry
echo "sync: done, $(( $(wc -l < data/orders.csv) - 1 )) orders, extra rows: ${#extra}"
flaky: partner attempt 1: service unavailable retry: attempt 1 failed (75), waiting 1s flaky: partner attempt 2: service unavailable retry: attempt 2 failed (75), waiting 2s flaky: partner attempt 3: ok sync: done, 2 orders, extra rows: 0

Run it twice: the second time the partner call succeeds at once (the counter remembers).
