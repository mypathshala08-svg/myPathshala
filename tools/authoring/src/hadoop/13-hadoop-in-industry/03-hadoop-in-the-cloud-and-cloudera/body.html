1 The story

A cluster that exists for three hours a night

Kabir's new company streams cricket and films. Every night a job crunches the day's viewing logs into recommendations. Their old Hadoop cluster ran 24 hours a day for a job that needed three. Now the logs sit in cloud object storage. At 1 AM a script creates 20 machines, runs the job, writes the results back and deletes the machines. The data stays; the cluster does not.

K> Sir, so is Hadoop dead in the cloud? We don't even have HDFS there. A> The storage moved, not the ideas. Their job still runs on YARN with Spark, reads splits in parallel, shuffles by key and uses the same Hive tables. What changed is that data lives in object storage like S3, GCS or ADLS, and clusters come and go around it. R> And companies that can't move everything, like banks? A> Many run Cloudera on their own servers, or a mix: sensitive data on-premises, burst work in the cloud. Today we compare the options using the numbers from our own lab, and look at what each cloud offers in October 2026.
2 Definition

Hadoop in the cloud

Formal definition (write this in exams)

Hadoop in the cloud means running Hadoop-ecosystem engines (YARN, Spark, Hive, Trino, HBase and others) on rented virtual machines or containers, usually as a managed service such as Amazon EMR, Google Cloud Dataproc or Azure HDInsight, with data kept in object storage (Amazon S3, Google Cloud Storage, Azure Data Lake Storage) accessed through Hadoop file-system connectors (s3a://, gs://, abfs://) instead of HDFS. This separation of compute and storage allows clusters to be created per job (transient), resized automatically (autoscaling) and run partly on discounted interruptible capacity (spot or preemptible instances), while table metadata lives in a shared catalog. Cloudera provides a commercial distribution of the same open-source stack for on-premises data centres and public clouds, with central management, security and governance.

In simple words

The data sits in cheap cloud storage that never switches off. When there is work, you rent a cluster for an hour, point it at the data, and delete it afterwards. Cloudera sells the same Hadoop tools, packaged and supported, for companies that run their own servers.

Architecture at a glance

Left: the classic cluster, where every worker stores blocks and runs containers. Right: the cloud pattern, where storage is a service and clusters are temporary.

LEVELS> The cloud at three levels L1> Renting a kitchen by the hour
  • An always-on cluster is like owning a big kitchen that you use for three hours a day. Rent, electricity and staff are paid all day.
  • In the cloud the ingredients (data) stay in a cold store that never closes. You rent a kitchen (a cluster) when it is time to cook, and hand it back after.
  • The recipes (Spark, Hive, MapReduce) are the same. Only the kitchen is temporary.
L2> What changes when storage leaves the cluster
  • Paths: hdfs://namenode/data becomes s3a://bucket/data, gs://bucket/data or abfs://container@account.dfs.core.windows.net/data. Jobs barely change.
  • Locality: blocks are no longer on the worker, so every read crosses the network. Cloud networks are fast, and engines read columnar files (Lesson 10.2), so this is usually fine.
  • Renames are slow: in object stores a "rename" copies the data. Classic MapReduce output commit renames folders, so use the cloud-aware committers (for example the S3A "magic" committer) or table formats like Iceberg that commit by writing metadata.
  • Metadata must be shared: because clusters are deleted, the metastore or catalog runs outside them (Glue, a managed Hive metastore, an Iceberg REST catalog).
L3> Elasticity, interruption and governance
  • Autoscaling watches pending YARN containers (Lesson 11.3) and adds workers; it removes them when the queue is empty, after graceful decommissioning (Lesson 6.4 idea).
  • Spot/preemptible workers are much cheaper but can disappear. MapReduce and Spark rerun lost tasks (Lesson 8.6), so put them on task-only nodes and keep the AM and driver on regular nodes.
  • Security moves from Kerberos keytabs (Lesson 12.5) to cloud identity (IAM roles), though Kerberos and Ranger still appear on long-running clusters and in Cloudera.
  • Cost governance becomes engineering: tags, budgets, auto-termination of idle clusters, lifecycle rules that move old objects to colder storage classes.

Animated example: one night on a transient cluster

A streaming company's nightly job 6 steps
Animated example
  1. 01:00: a scheduler (Airflow, say) asks the cloud for a cluster; four workers boot from a managed image.
  2. 01:06: Spark reads the day's logs directly from object storage; the shared catalog tells it where the table lives.
  3. 01:20: YARN has many pending containers, so autoscaling adds four cheaper spot workers.
  4. 03:40: results are committed as an Iceberg table. One spot worker was reclaimed; its tasks reran elsewhere.
  5. 04:00: the job is done and the cluster is terminated. Data and table definitions remain in storage and the catalog.
  6. The bill: only the hours the machines existed, plus storage. (Illustrative story; times and sizes are examples.)
TIP> The most common cloud waste is a cluster nobody remembered to stop. Every managed service has an auto-termination or idle-timeout setting; turn it on before the first job, and tag clusters with an owner and a cost centre.
4 Step by step

Deciding with numbers

We did not create cloud resources for this lesson, so there is no cloud lab output here. Instead we feed numbers we measured on our own cluster into a small calculator, cloud_vs_onprem.py, with prices clearly marked as illustrative.

  1. Measure your own throughput first

    DistCp, 5 files, 162 MB, prod → DR          25.5 s   (Lesson 12.2)
TestDFSIO write, 1 task                     113 MB/s (Lesson 12.3)
TestDFSIO write, 6 tasks, aggregate         ~210 MB/s on one shared laptop disk
Spark on YARN, item revenue, wall time      ~46–50 s incl. executor start (Lesson 13.2)
    Cloud sizing starts with how fast your jobs and copies really are. Our laptop numbers are small, but the method is the same on a 200-node cluster.

  2. Compare compute: always-on vs per-night

    always_on = workers * 24 * 30 * NODE_HOUR
transient = workers * (job_hours + 0.25) * 30 * NODE_HOUR
    always-on 20 workers : Rs 576,000 transient, 3h15m a night : Rs 78,000 (14% of always-on) transient, 4 core + 16 spot: Rs 40,560 (7%)
    The ratio is what matters: 3 h 15 min of 24 h is 14%. Spot workers cut it further. Prices are placeholders: check the provider's price page.

  3. Compare storage: three copies on disks vs object storage

    hdfs = data_tb * 3 / 0.7 * DISK_TB_MONTH   # x3 copies, disks at most 70% full
obj  = data_tb * OBJECT_TB_MONTH
    HDFS: 429 TB of raw disk : Rs 385,714 object storage, 100 TB : Rs 170,000
    100 TB in HDFS needs about 429 TB of raw disk (three copies, 30% headroom, Lesson 12.3). Erasure coding (Lesson 7.3) or Parquet compression (Lesson 10.2) shrink both sides.

  4. Estimate the move

    mb_s = gbps * 1000 / 8 * 0.7      # 70% of the link usable
    at our lab's DistCp speed (6.4 MB/s): 191 days over a 1 Gbps link at 70% use (88 MB/s): 13.9 days over a 10 Gbps link at 70% use (875 MB/s): 1.4 days
    Migration is often limited by the network link, not by Hadoop. Large moves use dedicated links or physical transfer appliances, and DistCp with -update catches up the changes made during the copy.

  5. Change the paths, not the logic

    spark-submit job.py hdfs://namenode/user/hadoop/data/student_orders.csv   # our lab
spark-submit job.py s3a://canteen-data/orders/                              # AWS
spark-submit job.py gs://canteen-data/orders/                               # Google Cloud
    The Hadoop FileSystem API (Lesson 6.5) hides the store behind a URI scheme. What changes is configuration: credentials come from cloud roles, and output commit uses a cloud-aware committer.
WARN> Copying data to the cloud is easy; copying it back can cost a lot (data egress is usually billed) and take weeks. Decide early which copy is the master and keep the other in sync with DistCp -update or snapshot-diff (Lesson 12.2).
5 See it happen

The same job, two lifecycles

Six steps of one nightly job: on a long-running on-premises cluster (left in each picture) and on a transient cloud cluster.

On-prem vs cloud job lifecycle 6 steps
What you see
  1. On-prem the cluster is always running; in the cloud the job starts by creating one with auto-termination on.
  2. The job itself is the same; only the input URI changes from hdfs:// to s3a://.
  3. On-prem most maps read local blocks; in the cloud every read crosses the network.
  4. When work piles up, on-prem jobs wait in the queue; the cloud cluster grows with spot workers.
  5. Committing output differs: an HDFS rename is cheap, an object-store rename is a copy, so cloud jobs use special committers or table formats.
  6. Afterwards the on-prem cluster idles and the cloud cluster is deleted. (Costs illustrative.)
Behind the screen
  1. On-prem the workers are already up; in the cloud a few workers boot from a managed image.
  2. Both run YARN and Spark; one reads HDFS, the other object storage through the s3a connector.
  3. On-prem tasks find their blocks on the same node; cloud tasks stream data over the network.
  4. On-prem a full queue means waiting; the cloud cluster adds spot workers for the peak.
  5. On-prem the committer renames a temporary folder; in the cloud the commit writes metadata instead of renaming.
  6. On-prem the machines idle until the next run; the cloud cluster is gone and only storage remains.
6 Real-world use

Cloud and Cloudera at work

1. Streaming and media: nightly transient clusters

OTT platforms process the day's viewing logs on a cluster created at night over object storage, scaling out on match days and deleting the cluster afterwards.

Viewing logs→Transient Spark cluster→Recommendations

2. Banking: hybrid Cloudera

Banks often keep customer and transaction data on Cloudera clusters in their own data centres, governed by Ranger and Atlas, and use the cloud for masked or aggregated data in analytics experiments.

Core data on-prem→Masked copies→Cloud sandbox

3. Retail: autoscaling for sale days

An e-commerce company's clickstream jobs need five times the usual compute during festival sales. Autoscaling with spot workers covers the peak without buying servers that sit idle the rest of the year.

Clickstream→Autoscaling cluster→Hourly dashboards

4. Telecom: migrating a 2 PB estate

An operator moves call-record history to object storage in waves: DistCp for the bulk, -update runs to catch up changes, then jobs switch their URIs table by table.

HDFS history→DistCp waves→Object storage tables

5. Research and government data: serverless Spark

Small teams processing survey or scheme data run occasional Spark jobs on serverless offerings, paying per job and never managing a cluster at all.

Files in storage→Serverless Spark→Reports
