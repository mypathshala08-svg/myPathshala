1 The story

A price was wrong for a month

Kabir has joined a fintech in Bengaluru as a data engineer. On his first Monday the canteen app team calls: chai was billed at ₹15 all of September, but the real price was ₹18, and a coffee supplier's orders turned out to be test data. "Fix the table, but finance must still be able to see what the report said last week." On a folder of CSV files that would mean rewriting everything and losing the old version. Arjun Sir shows him a table format that keeps both.

K> In the Hadoop course we only ever wrote whole files. How do I change a few rows without breaking the September report? A> With a table format like Apache Iceberg. The data still lives in HDFS as Parquet files, but Iceberg keeps a list of which files make up the table at each moment: a snapshot. DELETE and UPDATE write new files and a new snapshot; the old snapshot stays readable. That is the lakehouse idea: warehouse features on cheap lake storage. R> And that's Kabir's whole job? Fixing tables? A> That's one hour of it. Today we follow a data engineer through a real day: night jobs, a failed pipeline, a schema change, a backfill, a migration task. And we run the Iceberg part on our own cluster.
2 Definition

Pipelines, migrations and the lakehouse

Formal definition (write this in exams)

A data pipeline is an automated, scheduled sequence of steps that ingests data from sources, validates and transforms it through stages (commonly raw/bronze, cleaned/silver and aggregated/gold) and publishes it for consumers, run by an orchestrator such as Apache Airflow that manages dependencies, retries, backfills and SLAs. A migration moves data, metadata and workloads from one platform to another (for example from an on-premises Hadoop cluster to cloud object storage or to a lakehouse), through inventory, copy, dual-running and reconciliation, cut-over and decommissioning. A lakehouse stores data in open file formats on low-cost storage (HDFS or object stores) and adds warehouse capabilities through an open table format (Apache Iceberg, Delta Lake, Apache Hudi): ACID transactions, row-level updates and deletes, snapshots and time travel, schema and partition evolution, all exposed through a catalog to several engines (Spark, Trino, Flink, Hive).

In simple words

A data engineer builds and runs the machines that move data every day, moves them to new platforms when the company changes, and today usually stores the results in tables that behave like a database but live as files in the lake.

LEVELS> The job at three levels L1> A day in the life
  • A data engineer is the plumber of a company's data: makes sure every morning's reports and models get fresh, correct data.
  • Mornings start with checking last night's jobs. Days fill with fixing breaks, building new pipelines and answering "why is this number different?".
  • The tools change (Hadoop, Spark, cloud, lakehouse), the job stays: move data reliably, prove it is right, keep costs sane.
L2> Pipelines that survive Monday
  • Layers: bronze keeps raw data exactly as received (so you can always rebuild), silver cleans and types it, gold aggregates for the business.
  • Idempotent steps: each run overwrites its own partition (e.g. dt=2026-09-14) instead of appending, so a retry or backfill never doubles numbers.
  • Orchestration: Airflow DAGs declare dependencies, retries and SLAs; airflow dags backfill re-runs a date range. Oozie, the old Hadoop scheduler, was retired to the Apache Attic in February 2025.
  • Quality gates: row counts, null checks and reconciliations against the source fail the DAG before bad data reaches gold (counters from Lesson 9.4 are the MapReduce version of this).
L3> Migrations and the lakehouse
  • Migration path: inventory (tables, jobs, users, sizes) → copy (DistCp and snapshot-diff, Lesson 12.2) → dual-run old and new → reconcile counts and sums → cut over consumers → decommission.
  • Hive tables to Iceberg: migrate in place (Iceberg reads the existing Parquet/ORC files and only writes metadata) or rewrite with CREATE TABLE AS SELECT to fix partitioning and file sizes (Lesson 7.5).
  • Jobs: MapReduce, Pig and Hive jobs are usually rewritten as Spark SQL or dbt models; the logic (keys, joins, aggregations from Modules 8–9) carries over.
  • Table formats: Iceberg, Delta Lake and Hudi all give ACID commits, snapshots, time travel and schema evolution; Iceberg's hidden partitioning (days(ts)) means queries filter on ts and never name the partition column.
/LEVELS EXAM> For "What is a lakehouse?", write: open files (Parquet) on cheap storage + an open table format (Iceberg/Delta/Hudi) that adds ACID transactions, row-level changes, snapshots/time travel and schema evolution, read by several engines through a catalog. 4 Step by step

A lakehouse table on our Hadoop cluster

Spark 4.0.4 (Lesson 13.2) with the Iceberg runtime jar from Maven Central, on our YARN, writing to HDFS. The catalog is the simplest kind, a folder in HDFS (type=hadoop).

  1. Create a partitioned Iceberg table and load it

    q("CREATE TABLE lake.canteen.orders (order_id BIGINT, student STRING, ts TIMESTAMP, item STRING, amount INT) "
  "USING iceberg PARTITIONED BY (days(ts))")
src.writeTo("lake.canteen.orders").append()
    -- 1. loaded +------+--------+ |orders|revenue | +------+--------+ |500000|12852002| +------+--------+
    days(ts) is hidden partitioning: Iceberg derives the day from the timestamp. Queries filter on ts and Iceberg prunes days on its own.

  2. Change rows with SQL

    DELETE FROM lake.canteen.orders WHERE item = 'coffee';
UPDATE lake.canteen.orders SET amount = 18 WHERE item = 'chai';
    -- 2. after DELETE coffee + UPDATE chai price +------+--------+ |orders|revenue | +------+--------+ |459636|12493729| +------+--------+
    12,852,002 − 40,364 × 20 (coffee) + 149,669 × 3 (chai +₹3) = 12,493,729. On a plain folder of CSV or Parquet files this needs a full rewrite job.

  3. Every change is a snapshot

    SELECT snapshot_id, operation, summary['added-records'], summary['deleted-records']
FROM lake.canteen.orders.snapshots ORDER BY committed_at
    |6640816061555354185|append |500000|NULL | |4428609581335996210|overwrite|459636|500000 | |1149537224652247478|overwrite|459636|459636 |
    Copy-on-write: the DELETE rewrote every data file without the coffee rows (500,000 out, 459,636 in), and the UPDATE rewrote them again. Old files stay until the snapshots that use them are expired.

  4. Time travel

    SELECT count(*), sum(amount) FROM lake.canteen.orders VERSION AS OF 6640816061555354185
    +------+--------+ |orders|revenue | +------+--------+ |500000|12852002| +------+--------+
    Finance's request from the story: last week's report can be reproduced exactly, while today's table is corrected.

  5. Evolve the schema

    ALTER TABLE lake.canteen.orders ADD COLUMN payment STRING
    |order_id|item |amount|payment| |1 |dosa |45 |NULL | |2 |samosa|18 |NULL |
    A metadata-only change: no data file is rewritten. Iceberg tracks columns by ID, so rename and drop are safe too (compare Avro's rules in Lesson 10.1).

  6. Look inside HDFS

    hdfs dfs -count /lakehouse/canteen/orders/data /lakehouse/canteen/orders/metadata
    31 90 7617041 /lakehouse/canteen/orders/data 1 14 75103 /lakehouse/canteen/orders/metadata v1.metadata.json v2.metadata.json v3.metadata.json snap-….avro (×3)
    It is still just HDFS: day folders of Parquet files plus JSON and Avro metadata. A commit is one atomic swap of the current metadata.json; that is where the transaction comes from.
WARN> Our first run on YARN failed with "IllegalArgumentException: Self-suppression not permitted", which hides the real cause. The next attempt showed it: "could only be written to 0 of the 1 minReplication nodes". The laptop disk was 97% full and the DataNodes had 1.4–1.8 GB left. Freeing space fixed it. Monitor DataNode free space (Lesson 12.4) and read past the first exception (Lesson 12.6).
5 See it happen

SQL on the left, files in HDFS on the right

Six steps of our Iceberg run. Watch which files each statement adds and which snapshot the table points to.

An Iceberg table, commit by commit 6 steps
What you see
  1. The table is created with hidden day partitions and 500,000 orders are appended.
  2. One SQL DELETE removes the 40,364 coffee orders.
  3. One SQL UPDATE fixes the chai price; revenue becomes ₹12,493,729.
  4. The snapshots table shows three commits: an append and two overwrites.
  5. Time travel to the first snapshot still gives the original numbers.
  6. A new column appears instantly; existing rows read it as NULL.
Behind the screen
  1. The append writes the first set of Parquet files, one folder per day, and v1.metadata.json points to snapshot 1.
  2. The DELETE writes a second set without coffee and commits v2: snapshot 2 is now current.
  3. The UPDATE writes a third set with the new chai price and commits v3.
  4. Manifest lists (snap-*.avro) record which files belong to each snapshot.
  5. Time travel reads snapshot 1's files, which are still in HDFS.
  6. Adding a column only writes new metadata; data files are untouched. (File squares are symbolic.)
6 Real-world use

Data engineering at work

1. Payments: daily settlement

A payments company builds the next-day settlement files for partner banks from the previous day's transactions, with reconciliation against bank statements before anything is sent.

Transactions (Kafka)→Airflow + Spark + checks→Bank files by 11:00

2. Telecom: migrating years of call records

An operator moves petabytes of Hive tables on HDFS to Iceberg: old partitions are migrated in place (metadata only), new data is written by Spark, and both run side by side for a month.

Hive tables→migrate + dual-run→Iceberg lakehouse

3. E-commerce: live sale dashboards

During a festival sale, clickstream flows through Kafka and Flink into Iceberg every minute, and Trino dashboards show orders per city while the batch layer keeps the full history.

Clicks→Kafka + Flink→Minute-fresh tables

4. Insurance: audit-ready reports

An insurer tags the snapshot used for each regulatory filing, so auditors can query exactly the data behind a report months later, even after corrections.

Corrected tables→snapshot tags + time travel→Reproducible filings

5. Ed-tech: deleting a learner's data

When a learner asks for their data to be erased, a row-level DELETE runs on every table that holds it, and old snapshots are expired so the deleted rows really leave storage.

Erasure request→DELETE + expire snapshots→Data gone everywhere

Simplified; organisations differ in tools and policies.
