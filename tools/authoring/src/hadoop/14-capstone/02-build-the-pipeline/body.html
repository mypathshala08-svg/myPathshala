2 Definition

A batch pipeline, stage by stage

Formal definition (write this in exams)

A batch data pipeline is a sequence of jobs that turns raw input into trusted outputs. Each stage reads the previous stage's output and writes its own: bronze (raw, immutable), a staging or cleansing step that applies data quality rules and deduplication, silver (cleaned, typed, conformed, partitioned by business date) and gold (aggregated tables for consumers). A production pipeline is idempotent (re-running a stage for the same input gives the same output), observable (counters and logs for every rule) and verified by automated acceptance checks before results are published.

In simple words

Each stage does one job and leaves its result in its own folder. If something is wrong you re-run that stage, it overwrites its old output, and the checks tell you whether the numbers are right.

LEVELS> The pipeline at three levels L1> What each stage does
  • Clean: reads every raw line, throws out broken and test lines (but counts them), and keeps one copy of each order.
  • Silver: stores the clean orders in a compact, typed format, one folder per day.
  • Gold: small summary tables: money per canteen per day, item sales, busy hours, UPI check.
L2> How the clean job works
  • The mapper parses each line; a good line becomes order_id TAB file_day TAB raw; a broken line gets the key ~BAD.
  • The shuffle brings every copy of an order_id to the same reducer, sorted by key (Lesson 8.4).
  • The reducer keeps the copy from the earliest file, adds the category and price check from menu.csv, and writes OK lines; ~BAD lines pass through as BAD.
  • Every rule increments a counter by printing reporter:counter:capstone,NAME,n to stderr (Lesson 9.8).
L3> Production details that matter
  • Schema on read, explicitly: Spark reads the TSV with a 14-column string schema. Without it Spark guesses the column count from a sample, and a file that starts with a 3-column BAD line breaks the table.
  • Dynamic partition overwrite: spark.sql.sources.partitionOverwriteMode=dynamic lets silver_gold.py 2026-09-14 replace only that day.
  • Left join for reconciliation: UPI orders LEFT JOIN gateway SUCCESS; rows with no match are the gaps. An inner join would hide exactly the problem we look for.
  • Gold is small: coalesce(1) writes one file per gold table, so consumers don't read 200 tiny files.
/LEVELS EXAM> For "explain a MapReduce job you wrote", describe key and value: "Mapper emits order_id as key so all copies of an order meet in one reducer; the reducer keeps the earliest copy (dedupe) and counts DUPLICATE, LATE and other rules with counters. 104 maps, 3 reducers, 357,215 records shuffled, 354,135 orders out."

Animated example: three copies of one order meet in a reducer

Deduplication as a shuffle 6 steps
Animated example
  1. A map task reading the file of 12 September emits order …00377 with its file day.
  2. The same order also sits in another split and in the file of 14 September, so two more copies are emitted.
  3. The partitioner sends every record with the same key to the same reducer, whichever mapper produced it.
  4. The reducer receives keys in sorted order, so all three copies come one after another.
  5. It keeps the copy with the earliest file day and adds 2 to DUPLICATE.
  6. On the full data: 357,215 records shuffled into 354,136 keys (354,135 orders plus the ~BAD key). (Simplified to one order; real splits hold thousands.)
TIP> Test the shuffle logic with a tiny file that contains the hard cases (two copies in one file, a copy in the next file, a broken line) and know the expected output by heart. When the big run disagrees, run the tiny file first.

Building and verifying the pipeline

    Silver orders: 26 dt= folders, 7.2 MB of Parquet instead of 29.7 MB of text. Types are now real: timestamps, dates, integers, booleans.

  5. Reconcile UPI

    == gold.upi_recon ==            == gold.upi_gaps ==
    |college|pos_upi|gateway_success|refunds|failed_attempts| gap| | KHR|2707150| 2707150| -11240| 766| 0| | NRL|1319845| 1312991| -4500| 351|6854| | PNL|1759014| 1759014| -7378| 542| 0| | VSH|2290453| 2290453| -8693| 722| 0| |2026-09-22| NRL| 13| 201| 6854|
    Only Nerul has a gap, and upi_gaps pins it to one hour: the gateway's outage window. Failed attempts are not a gap: those students paid again.

  6. Run the acceptance checks

    spark-submit --master yarn check.py
    PASS orders = truth got 354,135 expected 354,135 PASS revenue = truth got 11,524,009 expected 11,524,009 PASS order_id is unique got 354,135 expected 354,135 … PASS UPI gap = unconfirmed got 6,854 expected 6,854 10/10 checks passed
    Only now are the gold tables "published". In production the scheduler runs check.py as the last task and fails the run on any FAIL.

  7. Prove idempotency

    spark-submit … silver_gold.py 2026-09-14     # twice
spark-submit … append_demo.py
    files in dt=2026-09-14 before: 3 files in dt=2026-09-14 after two backfills: 3 append run 1: orders 13,007 revenue 417,578 append run 2: orders 26,014 revenue 835,156 overwrite run 1: orders 13,007 revenue 417,578 overwrite run 2: orders 13,007 revenue 417,578
    The backfill replaced one day and left the month's totals at 354,135 / ₹11,524,009. The append demo shows the bug that a retry would cause without overwrite.
WARN> Our first version read the cleaned TSV without a schema. Spark takes the number of columns from the first line it samples; if that line is a 3-field BAD line, every OK line is cut to 3 columns. Always give an explicit schema for text inputs that mix record types, or split them into separate outputs.
5 See it happen

One late order through the whole pipeline

Order KHR-0912-04461 (one idli, ₹30, UPI), a real row from our data: sold on Saturday 12 September at 18:25, arrived in Monday's file. Left: the row as you would see it at each stage. Right: where the work happens on the cluster.

From raw line to gold 6 steps
What you see
  1. The raw line sits in Monday's Kharghar file, exactly as the till sent it.
  2. The mapper emits the order_id as key, plus the file day and the raw line.
  3. The reducer keeps it (no other copy), adds category breakfast, and flags it late because it arrived on the 14th.
  4. Spark writes it with real types into the folder of the day it was sold: dt=2026-09-12.
  5. Gold counts it on Saturday, not Monday, and matches its UPI payment.
  6. The checks confirm all 2,100 late orders were kept on their own days.
Behind the screen
  1. The file is one small block with three replicas, so YARN can run its map task on any worker: all 104 maps were data-local.
  2. Each map container starts a JVM that pipes lines into our Python mapper; Hadoop tells it the file name through an environment variable.
  3. Each of the 3 reducers pulls its share from every map (104 × 3 = 312 shuffles) and writes one part file.
  4. Spark's executors read the parts, cast types and write one folder per business day.
  5. Aggregations shuffle by day and canteen; the UPI check is a left join; gold tables are tiny.
  6. The checks read everything back and compare with truth.json. Nothing is published on a FAIL.
6 Real-world use

The same pipeline shape at work

1. Food delivery: restaurant payouts

Orders from the app are deduplicated, matched with payment-gateway settlements and refunds, and turned into a weekly payout per restaurant. A left join finds orders with no settlement before money is paid out.

Orders + gateway files→dedupe, reconcile→Payout file

2. Electricity: smart-meter billing

Meters re-send readings after network outages. The pipeline dedupes on meter ID + reading time, bills on the reading date, and quarantines impossible values for field engineers.

Meter batches→dedupe on key, event time→Monthly bills

3. Retail: price-compliance reports

Every sale is compared with the price valid that day. Stores billing old prices (like our Panvel till) appear in a gold table with the rupee gap, and the store systems team gets a ticket.

Sales + price history→date-range join, flag→Compliance table

4. Ed-tech: daily learning dashboards

App events are cleaned, stored by day in Parquet and aggregated into lessons watched per course per day. A backfill after a tracking bug overwrites only the affected days.

App events→silver by dt, overwrite→Dashboards

5. Banking: regulatory returns

Before a report goes to the regulator, automated checks compare its totals with the general ledger. A single FAIL stops publication, the same gate as our check.py.

Transactions→aggregate + reconcile + checks→Filed report

Simplified; organisations differ in tools and policies. Kadak Canteens and its data are fictional.
