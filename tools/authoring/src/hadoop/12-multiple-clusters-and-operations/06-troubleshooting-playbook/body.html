1 The story

Four alerts, one morning

Kabir has just joined the platform team. On his first on-call morning four messages arrive within an hour: an analyst gets “Connection refused”, the ingestion job can't create a folder, a report fails with “No live nodes contain current block”, and a second report has been sitting in ACCEPTED for twenty minutes while the cluster is half empty. He wants to restart everything. Arjun Sir asks him to open the playbook instead.

K> Shall I just restart the NameNode and the ResourceManager? That fixes most things, right? A> A restart hides the evidence and sometimes makes things worse: a restarted NameNode spends minutes in safe mode. Read each message first. Every one of them names a layer: the network, HDFS, YARN, or the job itself. Find the layer, then run the one command that confirms it. R> So the four alerts are four different problems? A> Yes, and none of them needs a restart. Today we reproduce all four on our lab, then build a playbook from every real failure we met in this course, so that next time the message itself tells you where to look.
2 Definition

A troubleshooting playbook

Formal definition (write this in exams)

A troubleshooting playbook (or runbook) is a documented, repeatable procedure for diagnosing and resolving operational incidents in a system. For Hadoop it combines a method (establish the symptom, its scope and recent changes; gather evidence from logs and metrics; form and test a hypothesis; apply the smallest safe fix; verify; record the incident) with a layered checklist that follows the dependency order of the platform: network and name resolution, HDFS (NameNode state and safe mode, DataNodes, block health), YARN (ResourceManager, NodeManagers, queues and limits), the application (ApplicationMaster, task attempts, input data) and security (authentication and authorisation). Each known symptom is mapped to its likely causes and the first command that confirms or rules them out. Incidents are closed with a blameless postmortem that improves the playbook, monitoring and automation.

In simple words

A doctor doesn't operate on everyone who says “it hurts”. They ask where, since when, what changed, look at test results, and then treat. A playbook is that routine written down for Hadoop: read the message, find the layer, run one command to confirm, fix the smallest thing, and write down what you learned.

LEVELS> Troubleshooting at three levels L1> Read the message, find the layer
  • Every Hadoop error message contains a clue word. Connection refused, UnknownHost: network or address. safe mode, block, replica: HDFS. queue, container, ACCEPTED: YARN. Exception at YourClass.java:27: your job.
  • Ask three questions before touching anything: what exactly fails, who else is affected, and what changed recently.
  • Never “just restart”. Look first, then change one thing.
L2> The method, step by step
  • Symptom: copy the exact message and time. Scope: one job, one user, one node, one queue, everyone?
  • Changes: a deploy, a config edit, a new data source, a node added or removed. Most incidents follow a change.
  • Evidence: hdfs dfsadmin -report, fsck, yarn node -list -all, yarn application -status, yarn logs, JMX metrics.
  • Hypothesis and one test that proves or disproves it. Then the smallest safe fix, then verify with the same command that showed the problem.
L3> Operating like a platform team
  • Turn every incident into a playbook entry and, where possible, an alert (Lesson 12.4) or an automated check.
  • Separate mitigation (get the report out) from root cause (why the queue was too small). Track the second as a ticket.
  • Write blameless postmortems with a timeline, the detection gap (our stale-DataNode alert came 296 s late), and concrete follow-ups.
  • Practise: game days and DR drills (Lesson 12.2) find gaps before real incidents do.
/LEVELS EXAM> For “How do you troubleshoot a failed Hadoop job?”, give the method (symptom → scope → recent changes → logs and metrics → hypothesis → smallest fix → verify → postmortem), the layer order (network, HDFS, YARN, application, security) and two real examples with their first command, e.g. safe mode → hdfs dfsadmin -safemode get; stuck in ACCEPTED → yarn application -status.

4 Step by step

Four incidents on our lab

Run with trouble_lab.sh on the Module 8 lab (in “Run it on your PC”). Each step creates one incident, shows the exact message, and undoes it.

  1. A. Connection refused

    hdfs dfs -ls hdfs://namenode:9000/
    Call From namenode/172.22.0.2 to namenode:9000 failed on connection exception: java.net.ConnectException: Connection refused
    The machine answered, but nothing listens on port 9000. “Refused” means the host exists and the port is wrong or the daemon is down; “UnknownHost” would mean the name itself is wrong. Check hdfs getconf -confKey fs.defaultFS (8020 here) and jps.

  2. B. Safe mode

    hdfs dfsadmin -safemode enter
hdfs dfs -mkdir /incident_b
hdfs dfs -cat /user/hadoop/data/menu.csv | head -1
hdfs dfsadmin -safemode leave
    Safe mode is ON Cannot create directory /incident_b. Name node is in safe mode. chai,drink,15,A Safe mode is OFF
    Writes fail, reads work: HDFS is read-only. Before leaving safe mode by hand, find out why it's on (-safemode get, NameNode log): after a restart it waits for enough block reports, and forcing it off with missing DataNodes can expose missing blocks.

  3. C. The only replica is on a stopped DataNode

    hdfs dfs -D dfs.replication=1 -put -f menu.csv /incident_c.csv
hdfs fsck /incident_c.csv -files -blocks -locations
docker exec lab8-worker2-1 hdfs --daemon stop datanode
hdfs dfs -cat /incident_c.csv
    DatanodeInfoWithStorage[172.22.0.6 the only replica is on worker2; stopping its DataNode No live nodes contain current block the read gave up after 16 s DataNode back: chai,drink,15,A
    fsck … -locations showed the one replica's address. With replication 1 there is no second copy, so the client tries, waits and gives up. Starting the DataNode made the block available again: no data was lost, only unavailable. With replication 3 this read would have succeeded.

  4. D. A job stuck in ACCEPTED on a half-empty cluster

    yarn application -list
yarn application -status application_…_0019
curl -s http://resourcemanager:8088/ws/v1/cluster/scheduler
    application_1792661456575_0018 RUNNING application_1792661456575_0019 ACCEPTED Diagnostics : … Application is added to the scheduler and is not yet activated. Queue's AM resource limit exceeded. queue default | AM limit 768 MB | AM used 512 MB
    yarn.scheduler.capacity.maximum-am-resource-percent is 0.1 by default: 10% of 6,144 MB ≈ 614 MB, which the scheduler rounds up to 768 MB. One 512 MB ApplicationMaster fits; a second would need 1,024 MB. The cluster had memory free, but the queue had no ApplicationMaster room.

  5. Write it down

    Title       Nightly report stuck in ACCEPTED (incident D)
Impact      report 48 min late, 1 queue, no data loss
Timeline    01:00 submitted · 06:05 noticed · 06:09 diagnosed · 06:16 mitigated
Root cause  queue AM limit (10%) filled by a long-running job
Detection   no alert for "ACCEPTED too long"  ← gap
Actions     alert on ACCEPTED > 15 min · AM percent 0.1 → 0.3 for reports · job timeout
    Blameless: it records what the system allowed, not who submitted the long job. The detection gap and the actions are the most valuable lines.
WARN> Under pressure, change one thing at a time and verify with the command that showed the problem. Two changes at once and you won't know which fixed it, or which made it worse.
5 See it happen

From message to layer to fix

Six steps through the four real incidents and the method that solved each one.

Four incidents 6 steps
What you see
  1. A: the client gets “Connection refused” for port 9000.
  2. B: a mkdir fails in safe mode while a read still works.
  3. C: the only replica sits on worker2; with its DataNode stopped the read gives up after 16 s.
  4. D: the second job waits in ACCEPTED because of the queue's ApplicationMaster limit.
  5. The fixes are small: leave safe mode on purpose, start the DataNode.
  6. Every incident ends with a written entry that makes the next one faster.
Behind the screen
  1. The problem is in front of everything: the client is knocking on a port where nothing listens.
  2. The NameNode is up but in safe mode: it serves reads and refuses changes.
  3. worker2 holds the only replica; once it's down no DataNode can serve the block.
  4. The queue's ApplicationMaster budget (10% → 768 MB) is used by one AM; the second AM would exceed it.
  5. Leaving safe mode and starting the DataNode fix B and C; D waits for the first job or a bigger AM percent.
  6. Each incident lived in exactly one layer. Finding the layer is most of the work.
6 Real-world use

Playbooks at work

1. On-call in a payments company

Every alert links to a runbook entry: what it means, the first command, the safe mitigation, and whom to call. The on-call engineer follows it before improvising.

Alert→Runbook entry→Mitigate, then root cause

2. Blameless postmortems at an e-commerce company

After a festive-sale incident, the team writes a timeline and actions without naming a culprit. The actions (an alert, a quota, a test) are tracked like features.

Incident→Timeline + causes→Tracked actions

3. Game days at a telecom operator

The platform team breaks things on purpose in staging (stop a DataNode, fill a queue, expire a ticket) and times how long the on-call team needs to diagnose each one with the playbook.

Planned failure→Diagnose with playbook→Fix the gaps

4. Automated health checks at a government data platform

Steps that are always the same (safe mode? missing blocks? lost NodeManagers? apps stuck in ACCEPTED?) run as a script every few minutes and post a summary, so humans start with the evidence.

Script→Same first commands→Summary in chat

5. Support tickets in a university research cluster

Students must attach the application ID, the exact message and the output of yarn application -status. Most tickets are solved from that alone, without logging in.

Student ticket→App ID + message→Answer from the table

Simplified; organisations differ in tools and policies.
