1 The story

One cluster was never going to be enough

The canteen project has grown. The college now wants a second cluster in another city, so that the billing data survives if the main campus loses power for a week. Riya joins the two lab clusters on one Docker network and runs a job. It hangs, retries ten times and fails with Connection refused. The client had asked for resourcemanager and reached the right machine through the wrong network. Both clusters also had a machine called namenode.

R> Sir, why not one giant cluster? We learnt that Hadoop scales to thousands of nodes. A> It does. But a bank cannot test a Hadoop upgrade on the cluster that settles UPI payments tonight. It needs a copy in another city in case a data centre floods. Its data scientists should not be able to slow the regulator's report. And some data may have to stay in one country. Each of those is a reason for another cluster. K> At my internship we had seven: prod, DR, staging, dev, two analytics sandboxes, and a tiny one just for upgrade tests. A> Today we look at why fleets happen, what the clusters share, what they cost, and how a platform team keeps track of them, starting with the tiny fleet in our own lab.
2 Definition

A cluster fleet

Formal definition (write this in exams)

A multi-cluster deployment (or cluster fleet) is a set of independently operated Hadoop clusters, each with its own NameNode(s), ResourceManager and failure domain, run by one organisation for different purposes such as production, disaster recovery, staging and development, tenant or business-unit isolation, data residency and scale. Clusters exchange data through replication tools such as DistCp and share cross-cutting services: identity (Kerberos realms with trust), authorization policies (Apache Ranger), metadata (Hive Metastore, data catalog) and monitoring. Unlike HDFS federation, where several NameNodes share one set of DataNodes and one cluster ID, separate clusters share no storage and fail independently.

In simple words

Companies keep several Hadoop clusters for the same reasons a hospital keeps a backup generator and a separate training room: safety, testing, isolation and rules. The clusters copy data to each other and share logins, permissions and monitoring.

Architecture at a glance

A typical fleet of an Indian bank or marketplace. Clusters are separate failure domains; the services along the bottom are shared by all of them.

Sizes are illustrative. Shared services are what make a fleet manageable; without them every cluster becomes its own island.

LEVELS> Many clusters at three levels L1> A school with several buildings
  • The main building holds the exam papers (prod). Nobody practises chemistry experiments there.
  • A lab building lets students break things (dev), and a copy of the records sits in the district office (DR).
  • All buildings use the same ID cards (Kerberos), the same rules about who opens which room (Ranger) and the same register of what is stored where (catalog).
L2> The reasons, one by one
  • Safety: a DR cluster in another region survives a data-centre loss. HA (Lesson 7.1) protects against a dead NameNode, not a flooded building.
  • Change control: upgrades, new configs and new jobs are tried on staging first.
  • Isolation: queues (Lesson 11.3) share one cluster's CPU, but a runaway job can still fill HDFS or overload the NameNode. A separate cluster cannot.
  • Rules: some data must stay in a country or a network zone. In India, for example, the RBI requires payment-system data to be stored in India, so a global company may keep a separate Indian cluster (check the current rules with your compliance team).
  • Scale and organisation: one NameNode's memory limits the number of files (Lesson 7.5); mergers and separate budgets bring their own clusters.
L3> Running a fleet
  • Shared identity: each cluster can have its own Kerberos realm, with cross-realm trust so a user's ticket works everywhere (Lesson 12.5).
  • Shared metadata: one Hive Metastore or catalog per environment so a table means the same thing on prod and DR.
  • Fleet inventory: a script or tool that asks every NameNode and ResourceManager for version, cluster ID, capacity and health (our fleet.py), feeding one dashboard (Lesson 12.4).
  • Configuration as code: generate every cluster's *-site.xml from one repository to stop drift.
  • Unique names: host names, nameservice IDs and cluster IDs must differ across clusters, or clients reach the wrong one, exactly as ours did.

Animated example: from one cluster to a fleet

A payments company grows a fleet 6 steps
Animated example
  1. Year 1: a single production cluster runs reports, ETL and developers' experiments.
  2. Year 2: a test job deletes a production folder, so developers get their own small cluster.
  3. Year 3: the regulator wants a recovery plan; a DR cluster in another city receives hourly DistCp copies.
  4. Year 4: an upgrade breaks a production job; upgrades are now rehearsed on a staging cluster first.
  5. Year 5: model training competes with settlement, so data scientists get a sandbox with curated copies.
  6. Today: five clusters share one Kerberos setup, one set of Ranger rules and one catalog. (Illustrative story.)
TIP> A rule of thumb: add a cluster when you need a separate failure domain, a separate change schedule or a separate legal boundary. If you only need fair sharing of CPU and memory, queues (Lesson 11.3) are cheaper.
4 Step by step

Building a two-cluster fleet in the lab

Our “prod” is the Module 8 cluster (lab8, with YARN). Our “DR” is the federation cluster of Lesson 7.2 (lab72). Scripts are in “Run it on your PC”.

  1. First attempt: connect everything

    for c in namenode worker1 worker2 worker3 resourcemanager historyserver; do
  docker network connect lab5_default lab8-$c-1
done
hadoop distcp /prod/canteen hdfs://lab5-namenode-1:8020/dr/
    Retrying connect to server: resourcemanager/172.19.0.10:8032. Already tried 9 time(s) java.net.ConnectException: Call From namenode/172.22.0.2 to resourcemanager:8032 failed on connection exception: java.net.ConnectException: Connection refused
    A container on two networks answers to its name on both. The client got the ResourceManager's address on the second network, where nothing listens. Both clusters also had a host called namenode.

  2. Fix: unique names, only workers join

    docker compose -p lab72 start                     # DR: nn-canteen, nn-hostel
for c in worker1 worker2 worker3; do docker network connect lab72_default lab8-$c-1; done
docker exec lab8-worker1-1 getent hosts namenode resourcemanager nn-canteen
    172.22.0.2 namenode 172.22.0.3 resourcemanager 172.21.0.2 nn-canteen
    The DR cluster's names (nn-canteen, nn-hostel) do not clash with prod's. Prod names still resolve to prod's network.

  3. Take inventory of the fleet

    python3 /tmp/fleet.py
    cluster version clusterId live DNs files used prod (lab8) 3.5.0 CID-01fef50a-2caf-4bfb-9422-ad32ed9b0cb4 3 1680 4769 MB dr (lab72) ns canteen 3.5.0 campus-cluster 3 15 541 MB dr (lab72) ns hostel 3.5.0 campus-cluster 3 4 541 MB
    Two clusters, three NameNodes. The two DR namespaces share a cluster ID because they are federated over the same DataNodes (Lesson 7.2); prod has its own, so it fails independently.

  4. What the fleet needs next

    copy data prod → DR            DistCp, snapshots           Lesson 12.2
size each cluster              measured throughput          Lesson 12.3
watch every cluster            JMX/REST + alerts            Lesson 12.4
one identity, one rule book    Kerberos, Ranger             Lesson 12.5
known fixes for known faults   runbooks                     Lesson 12.6
    The rest of this module turns our two-cluster lab into a small but properly operated fleet.
WARN> Never let two clusters share a host name, nameservice ID or cluster ID by accident. Clients, DistCp and DataNodes will happily talk to the wrong one, and the error (if any) points somewhere else.
5 See it happen

Two clusters, one network mistake

Six steps from our lab: the wrong way to join clusters, the fix, and the first fleet report.

Joining two clusters 6 steps
What you see
  1. We connect every prod container to the other cluster's network.
  2. The next job retries ten times and fails: Connection refused.
  3. We undo it and use the DR cluster with distinct names instead.
  4. Only the three workers join; prod names still resolve to prod.
  5. The fleet report lists both clusters and all three NameNodes.
  6. The first real copy to DR succeeds: 5 files, 170 MB (Lesson 12.2).
Behind the screen
  1. Joining a network gives each container a second address and makes its names visible there.
  2. The client resolved resourcemanager to the RM's second address; the RM only listens on its first.
  3. The DR cluster uses names that don't exist in prod.
  4. Only workers, where copy tasks run, sit on both networks.
  5. fleet.py reads each NameNode's JMX: version, cluster ID, nodes, files.
  6. DistCp's map tasks on the workers read from prod and write to DR.
6 Real-world use

Fleets at work

1. Banking: prod and DR in two cities

Banks keep a recovery copy of critical data in a second region and rehearse failover regularly; auditors ask for proof of the drills.

Prod (Mumbai)→Hourly DistCp→DR (Hyderabad)

2. E-commerce: isolating the sale-day pipeline

During a big sale, order and inventory pipelines run on a cluster that analysts cannot touch; experiments go to a sandbox fed with curated copies.

Orders→Prod cluster→Sandbox copies

3. Payments: data residency

Global payment companies keep Indian payment data on clusters in India to meet RBI's storage rule, while other regions run their own clusters.

Indian payments→India cluster→Aggregates only abroad

4. Telecom: blue-green upgrades

An operator builds a new cluster on the new Hadoop version, copies data and moves jobs one by one, keeping the old cluster as a fallback for a month.

Old cluster→Copy + move jobs→New cluster

5. Media and research: ephemeral clusters

Video and genomics teams start a cloud cluster for a nightly batch over data in object storage and delete it after, paying only for hours used.

Object storage→Cluster for 3 hours→Results, cluster gone

Simplified; organisations differ in tools, policies and regulations.
