1 The story

A line cut in half

Riya stores the canteen file again, this time with tiny 1 MB blocks, so her job gets five map tasks instead of one. Then a doubt hits her. HDFS cuts blocks at exactly 1,048,576 bytes; it has no idea where a line ends. She looks at the bytes around the cut: the order 71484,poha,25 starts at byte 1,048,564 and ends at byte 1,048,578. Fourteen bytes, twelve in block 1 and two in block 2. Will map task 1 see 71484,poha,2 and map task 2 see a lonely 5?

A> Good doubt, and the answer is no. Blocks are cut by bytes; records are not. The piece of code that reads a split, the RecordReader, follows one rule: finish the line you started, even if it means reading a few bytes from the next block, and skip the half line you start in, because the previous reader already took it. R> So the split boundary is just a suggestion? K> It's a byte range. The records are decided by the reader. We checked it on the cluster: map 0's last line was 71484,poha,25, complete, and map 1's first record started at byte 1,048,578. Five maps, 300,001 records in total, not one lost or doubled. A> Today: who decides how many splits a job gets (the InputFormat), how big they are, why a 2-block file got only 1 map task, and how each record is read.
2 Definition

Input splits, InputFormat and RecordReader

Formal definition (write this in exams)

An InputFormat describes how a MapReduce job reads its input. It has two responsibilities: getSplits(), run by the client at job submission, divides the input into InputSplits, logical byte ranges (for files, a FileSplit of path, start offset, length and the hosts that store the data), each processed by exactly one map task; and createRecordReader(), run inside each map task, returns a RecordReader that turns the bytes of one split into key-value records for the mapper. For FileInputFormat the split size is max(minSize, min(maxSize, blockSize)), and a final piece of up to 10% extra (the split slop, 1.1) is merged into the previous split. The default TextInputFormat uses a LineRecordReader that yields the byte offset of each line as key (LongWritable) and the line as value (Text); it completes a line that crosses the end of the split and skips the partial first line of a split that does not start at offset 0, so every line is read exactly once.

In simple words

Before the job starts, Hadoop divides the input into pieces (splits), one per map task, usually one per block. Inside each map task a reader cuts its piece into records, carefully handling lines that cross the edges.

LEVELS> Splits and readers at three levels L1> Cutting a notebook for five friends
  • You tear a 100-page register into five bundles by page number: that's the split. You didn't read it, you just counted pages.
  • A sentence can run from page 20 onto page 21. Friend 1 reads on until the sentence ends; friend 2 ignores the half sentence at the top of page 21 and starts at the next full one: that's the RecordReader.
  • Nobody misses a sentence and nobody reads one twice.
L2> What the client and the task each do
  • Client, at submit time: InputFormat.getSplits() lists files, asks the NameNode for block locations and builds FileSplits. Our log: “Total input files to process : 1”, “number of splits:5”. The split list is uploaded with the job, and the MRAppMaster requests one container per split, preferring its hosts.
  • Map task: createRecordReader() opens the file, seeks to the split's start and calls map() once per record.
  • TextInputFormat records: key = byte offset of the line (LongWritable), value = the line without the newline (Text). The offsets in our SplitPeek output are exactly these keys.
  • Size: splitSize = max(minSize, min(maxSize, blockSize)). Default minSize 1 byte, maxSize unlimited, so splitSize = block size.
L3> Edge rules that explain odd counts
  • Slop 1.1: while the remaining bytes are more than 1.1 × splitSize, cut a full split; the rest becomes the last split. 140,759,640 / 134,217,728 = 1.049, so orders_x30's two blocks gave one split, reading 6.2 MB of block 2 remotely or locally wherever the split ran.
  • maxsize smaller than a block gives more maps than blocks (more parallelism, more overhead). minsize bigger than a block gives fewer, bigger maps that span blocks and lose some locality.
  • LineRecordReader: a split not starting at 0 throws away everything up to the first newline; every reader keeps reading while the line it is about to start begins at or before its end offset. Together this assigns each line to exactly one split.
  • Non-splittable input (gzip, or isSplitable() returning false): one split per file, whatever its size. Module 10 compares codecs and splittability.
  • Splits are computed per file: 10,000 small files give at least 10,000 splits (Lesson 7.5), unless you use CombineTextInputFormat.
/LEVELS EXAM> For “Difference between a block and an input split”, write: a block is the physical unit HDFS stores (128 MB, replicated); a split is the logical unit one map task processes, computed by the InputFormat, usually equal to a block but adjustable by min/max split size, and records that cross a block boundary are read whole by the RecordReader of the split where they start.

TIP> You cannot set the number of map tasks directly in the new API: it follows the splits. To change it, change the split size or the block size. The number of reduce tasks, on the other hand, is simply mapreduce.job.reduces (Lesson 8.5).
4 Step by step

Watching splits with SplitPeek

SplitPeek.java is a map-only job whose mapper counts the records it gets and, in cleanup(), writes one line per split: its start and length, the first and last record offsets, the last line and the host it ran on. Run with splits_lab.sh on the Module 8 lab (in “Run it on your PC”).

  1. One small file, one split

    hadoop jar mr.jar SplitPeek /user/hadoop/data/canteen_orders.csv /out/peek_a
hdfs dfs -cat /out/peek_a/part-m-*
    number of splits:1 split start=0 length=4692009 | records=300001 first_offset=0 last_offset=4691994 last_line=301000,idli,30 | ran_on=worker2
    4.7 MB is less than one 128 MB block, so one split covers the whole file. The last line starts at byte 4,691,994: 301000,idli,30 plus the newline is 15 bytes, ending exactly at 4,692,009.

  2. Same data, 1 MB blocks

    hdfs dfs -D dfs.blocksize=1048576 -put -f canteen_orders.csv /user/hadoop/data/orders_1mb_blocks.csv
hadoop jar mr.jar SplitPeek /user/hadoop/data/orders_1mb_blocks.csv /out/peek_b
    Total blocks (validated): 5 (avg. block size 938401 B) number of splits:5 split start=0 length=1048576 | records=70485 first_offset=0 last_offset=1048564 last_line=71484,poha,25 | ran_on=worker2 split start=1048576 length=1048576 | records=67321 first_offset=1048578 last_offset=2097145 last_line=138805,idli,30 | ran_on=worker3 split start=2097152 length=1048576 | records=65498 first_offset=2097160 last_offset=3145721 last_line=204303,chai,15 | ran_on=worker1 split start=3145728 length=1048576 | records=65574 first_offset=3145736 last_offset=4194301 last_line=269877,samosa,18 | ran_on=worker2 split start=4194304 length=497705 | records=31123 first_offset=4194318 last_offset=4691994 last_line=301000,idli,30 | ran_on=worker1
    Five blocks, five splits, five maps on all three workers. No split's first record starts exactly at its start: each began by skipping a partial line. The record counts add up to 300,001.

  3. Read the boundary

    split 0 ends at        1,048,576
its last line starts   1,048,564   "71484,poha,25\n" = 14 bytes
so that line ends at   1,048,578   (2 bytes inside block 2)
split 1 first record   1,048,578
    Map 0 read 2 bytes past its split to finish the line; map 1 threw away those 2 bytes (“5” and the newline) and started at the next line. The same happens at every boundary: 2,097,145 + 15 = 2,097,160, the first record of split 2.

  4. Splits without changing blocks

    hadoop jar mr.jar SplitPeek -D mapreduce.input.fileinputformat.split.maxsize=1048576 \
    /user/hadoop/data/canteen_orders.csv /out/peek_c
    number of splits:5 split start=0 length=1048576 | records=70485 first_offset=0 last_offset=1048564 last_line=71484,poha,25 | ran_on=worker3 … split start=4194304 length=497705 | records=31123 first_offset=4194318 last_offset=4691994 last_line=301000,idli,30 | ran_on=worker3
    The file is still one 4.7 MB block, yet the job got the same 5 splits with identical record counts. A split is only a byte range; it does not need to match a block.

  5. Two blocks, one split

    hdfs fsck /user/hadoop/data/orders_x30.csv -files -blocks
hadoop jar mr.jar SplitPeek /user/hadoop/data/orders_x30.csv /out/peek_d
    0. …blk_1073741827_1003 len=134217728 Live_repl=3 1. …blk_1073741828_1004 len=6541912 Live_repl=3 number of splits:1 split start=0 length=140759640 | records=9000000 first_offset=0 last_offset=140759625 last_line=301000,idli,30 | ran_on=worker1
    140,759,640 bytes is only 1.049 times the 128 MB split size, below the 1.1 slop, so FileInputFormat makes one split instead of a 128 MB split plus a 6.2 MB one. A tiny second map task would cost more than it saves.

  6. Fewer, bigger splits

    hadoop jar mr.jar SplitPeek /user/hadoop/data/orders_x90.csv /out/peek_e
hadoop jar mr.jar SplitPeek -D mapreduce.input.fileinputformat.split.minsize=268435456 \
    /user/hadoop/data/orders_x90.csv /out/peek_f
    number of splits:4 number of splits:2
    With minSize 256 MB, splitSize = max(256 MB, min(∞, 128 MB)) = 256 MB: two map tasks, each reading two blocks. Fewer task start-ups, but part of each split may be read from another node.
WARN> Don't “fix” a slow job by setting split.maxsize very low. Our 4.7 MB file in five 1 MB splits started five JVMs for work one map does in seconds. Smaller splits help only when each map does heavy work per record.
5 See it happen

From a file to records

Six steps: the client computes splits, two map tasks read across the boundary at byte 1,048,576.

Splits and the boundary line 6 steps
What you see
  1. The client lists the input and computes 5 splits before anything runs.
  2. YARN starts 5 map tasks, one per split.
  3. Map 0 starts at byte 0, so its first record is at offset 0.
  4. Map 0's last record starts 12 bytes before the end of its split.
  5. Map 1 starts 2 bytes after its split's start.
  6. Every line was read exactly once: 300,001 records in total.
Behind the screen
  1. getSplits() turns the file into byte ranges with their hosts. Nothing is read yet.
  2. Each map task creates a LineRecordReader for its own split.
  3. Map 0 starts at byte 0. Keys are byte offsets: the header at 0, the first order at 21.
  4. The line 71484,poha,25 starts inside split 0, so map 0 reads it fully, crossing into block 2.
  5. Map 1 discards the partial line before its first newline and starts with 71485.
  6. The rule: a line is read by the split in which it starts.
6 Real-world use

Splits at work

1. The single giant gzip file

A vendor sends a 40 GB .gz file daily. The job gets one map task that runs for hours while the rest of the cluster sits idle. Teams recompress to a splittable format (bzip2, or Parquet/ORC with block compression) or ask for many smaller files.

40 GB .gz→1 split→Recompress

2. NLineInputFormat for heavy rows

A file of 5,000 lines, each naming a large image or a model to score. As one 50 KB split it would be one map; NLineInputFormat with N = 50 gives 100 maps working in parallel.

5,000 lines→N = 50→100 maps

3. Combining small files

Daily folders with thousands of small log files are read with CombineTextInputFormat and a max split size of 256 MB, so a job runs a few dozen maps instead of thousands.

8,000 files→CombineTextInputFormat→~40 maps

4. Tuning map count for CPU-heavy jobs

A parsing job spends 90% of its time on CPU. Lowering split.maxsize to 64 MB doubles the number of maps and uses every core; for an I/O-bound job the same change only adds overhead.

128 MB splits→maxsize 64 MB→2× maps

Simplified; organisations differ in tools and policies.
