1 The story

The sorting room between two teams

Riya runs the same item-revenue job three times on the 140 MB orders file. Same input, same code, same answer each time. Only one setting changes: the size of the map task's sort buffer. With 16 MB the map task writes its output to disk 18 times and then has to merge those 18 files in two passes. With 200 MB it writes twice. Kabir asks the obvious question: why does a map task write anything to disk at all, if the answer is just six lines?

A> In Lesson 8.1 we said “Hadoop groups by key for you”. Today we open that box. It is called the shuffle and sort, and it is usually the most expensive part of a job: the map output is sorted, written to the worker's local disk, copied over the network to the reducers, and merged again. R> So the map writes to disk because the buffer is too small to hold everything? A> Partly. Even with a huge buffer the output must land on disk, because the reducers run later, maybe on other machines, and the map task's JVM exits when it is done. The NodeManager keeps serving that file to whichever reducer asks for it. K> And if the buffer is small, the map writes many little sorted files and has to merge them. That's our 18 spills and the extra 4.35 million records in “Spilled Records”. A> Exactly. Let's follow one pair, (“chai”, 15), from context.write() to reduce().
2 Definition

Shuffle and sort

Formal definition (write this in exams)

The shuffle and sort is the phase of a MapReduce job, carried out by the framework, that moves intermediate key-value pairs from map tasks to reduce tasks so that each reducer receives all values of its keys, sorted by key. On the map side, output pairs are assigned a partition by the Partitioner (by default HashPartitioner: (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks), collected in an in-memory circular buffer (mapreduce.task.io.sort.mb), sorted by partition and key, optionally passed through a combiner, and spilled to local disk whenever the buffer reaches mapreduce.map.sort.spill.percent (0.80); spill files are merged (mapreduce.task.io.sort.factor streams at a time) into one partitioned, sorted output file per map task. On the reduce side, fetcher threads copy the reducer's partition from every map over HTTP from the NodeManager's ShuffleHandler, merge the segments in memory and on disk, and present each key with an iterator over its values to the reduce() method.

In simple words

Each map sorts its output into labelled piles, one pile per reducer, and leaves them on its worker's disk. Each reducer collects its pile from every map, merges them into one sorted stream, and then calls your reduce once per key.

LEVELS> Shuffle and sort at three levels L1> The post office sorting room
  • Every map is a post office collecting letters. It doesn't send them one by one: it drops them into bags, one bag per destination city (a partition per reducer), sorted by street (key).
  • When the counter table is full, the clerk ties up a bundle and puts it in the back room (a spill). At closing time all bundles for a city are combined into one sorted bag (the merge).
  • Each city's van (a reducer) visits every post office and picks up only its own bag (the fetch), then merges the bags so the postman walks each street once (reduce).
L2> The steps and the settings
  • Partition: every context.write(k, v) gets a partition number from the Partitioner, immediately.
  • Buffer: pairs go into the io.sort.mb buffer. At 80% full a background thread sorts it by (partition, key), runs the combiner if any, and spills one file. The map keeps writing into the remaining 20% meanwhile.
  • Merge: at the end the spills are merged, at most io.sort.factor (10) at a time, into file.out plus an index of where each partition starts. 18 spills needed an extra pass; 5 or 2 did not.
  • Fetch: after 5% of maps finish, reducers start; 5 fetchers per reducer download their partition from each finished map over HTTP (port 13562).
  • Merge and reduce: fetched segments are merged (in memory first, spilling to disk when needed); the final merge feeds reduce() directly, one key at a time.
L3> Reading the counters like an engineer
  • Spilled Records counts records written to local disk anywhere in the job. Ideal is 2 × map output (map writes once, reducer once): 18,000,000 here, only possible when the map spills exactly once.
  • With 2–10 spills the map writes each record twice (spill + final merge) and the reducer once: 3 × 9,000,000 = 27,000,000, our 64 MB and 200 MB runs.
  • With 18 spills the merge needed an intermediate pass that rewrote 9 of the 18 segments: 31,354,091 − 27,000,000 = 4,354,091 extra records, about half the data written a third time.
  • Materialized bytes (108 MB) exceed raw map output bytes (90 MB for this file) because each record carries key and value lengths in the intermediate file format.
  • Fixes in order of effect: emit less (filter, combiner, compact types), compress map output (mapreduce.map.output.compress, Module 10), then tune io.sort.mb so a map spills once or twice.

The hooks you can plug into the shuffle

Partitioner

Decides which reducer gets a key. Default: hash of the key modulo reducers. Custom ones in Lesson 9.2.

which reducer

Sort comparator

Decides the order of keys. Default: the key type's natural order (Text compares bytes).

which order

Combiner

A mini-reduce run on each spill on the map side, to shrink the data before it travels. Lesson 9.1.

less data

Grouping comparator

Decides which consecutive keys share one reduce() call. Used for secondary sort, Lesson 9.7.

which group
TIP> The shuffle is all-to-all: with M maps and R reducers there are M × R pieces to copy. 1,000 maps and 200 reducers mean 2 lakh small HTTP fetches. That is why the number of reducers and the size of map output matter so much for big jobs.
4 Step by step

Watching the shuffle on a real cluster

Run on the Module 8 lab with shuffle_lab.sh (in “Run it on your PC”). It runs ItemRevenue (Lesson 8.1) three times on orders_x30.csv (140 MB, one split) with different sort buffers and reads the task logs with yarn logs.

  1. Run the same job with three buffer sizes

    for mb in 16 64 200; do
  hadoop jar mr.jar ItemRevenue -D mapreduce.task.io.sort.mb=$mb \
      /user/hadoop/data/orders_x30.csv /out/shuf_$mb
done
    == io.sort.mb=16 job took 39 s == io.sort.mb=64 job took 37 s == io.sort.mb=200 job took 36 s
    -D sets a property for this job only (the driver uses GenericOptionsParser). Each map task now gets a different buffer.

  2. The buffer fills and spills

    yarn logs -applicationId <app> -log_files syslog | grep MapTask
    MapTask: mapreduce.task.io.sort.mb: 16 MapTask: soft limit at 13421773 MapTask: Spilling map output MapTask: Finished spill 0
    13,421,773 bytes is 80% of 16 MB (16,777,216 × 0.8). At that point a SpillThread sorts the buffer by partition and key and writes it to the worker's local disk, while the map keeps filling the rest.

  3. Many spills, merged in passes

    MapTask: Finished spill 17
Merger: Merging 18 sorted segments
Merger: Merging 9 intermediate segments out of a total of 18
Merger: Down to the last merge-pass, with 10 segments left of total size: 107999642 bytes
    18 spill files (0 to 17), but only 10 may be merged at once. So Hadoop first merges 9 of them into one file, leaving 9 + 1 = 10, then does the final pass into one sorted file.out.

  4. Compare the counters

    io.sort.mb  spills  Spilled Records  map time
16          18      31,354,091       18.6 s
64           5      27,000,000       16.3 s
200          2      27,000,000       16.4 s
(Map output records = 9,000,000 and Reduce shuffle bytes = 107,999,586 in all three)
    Map output and shuffle size never change: the data is the same. What changes is how many times it is written to local disk. 27,000,000 = 3 × 9,000,000 (spill, merge, reducer); the 16 MB run wrote 4,354,091 records a third time in the extra pass.

  5. Where each key goes

    hadoop jar mr.jar ItemRevenue -D mapreduce.job.reduces=3 canteen_orders.csv /out/red_3
    part-r-00000 (0 bytes): part-r-00001 (79 bytes): chai dosa samosa vada pav part-r-00002 (38 bytes): idli poha
    HashPartitioner: (hash("chai") & MAX) % 3 = 1. With only 6 keys, hashing happened to give nothing to reducer 0 and four items to reducer 1. The Python runner below reproduces these numbers.

  6. The reducer sees sorted keys

    hdfs dfs -cat /out/shuf_16/part-r-00000
    chai 1505100 22576500 dosa 1498440 67429800 idli 1499520 44985600 poha 1496730 37418250 samosa 1500630 27011340 vada pav 1499580 29991600
    The input was in random item order; the output is alphabetical because the reducer reads one merged stream sorted by key and calls reduce() each time the key changes. Keys are sorted within each reducer, not across reducers.
WARN> A bigger io.sort.mb is not free: the buffer lives inside the map task's heap. Our maps had -Xmx300m; setting io.sort.mb close to or above that makes the task die with an OutOfMemoryError (values above 2047 MB are rejected outright as invalid). Raise the container memory and the heap together.
5 See it happen

From context.write() to reduce()

Six steps of the shuffle for the 16 MB run: fill, spill, merge, serve, fetch, reduce.

Shuffle and sort 6 steps
What you see
  1. The map task starts with a 16 MB buffer; a spill starts at 80% full.
  2. The buffer fills and spills 18 times during the map.
  3. 18 spill files are too many for one 10-way merge: one extra pass first.
  4. The map finishes with one sorted output file of 108 MB on its local disk.
  5. The reducer fetches exactly those bytes.
  6. The reducer writes six lines; Spilled Records shows the cost of the extra merge pass.
Behind the screen
  1. Every context.write() goes into the circular buffer with its partition number.
  2. At 80% a background thread sorts the buffer by partition and key and writes a spill file to local disk.
  3. The merger combines at most 10 files per pass: first 9 into 1, then the final 10.
  4. The result is one file per map, sorted, with an index of where each reducer's partition starts.
  5. The reducer's fetchers download their partition from each map's NodeManager.
  6. The fetched pieces are merged into one sorted stream; reduce() is called once per key.
6 Real-world use

The shuffle at work

1. Tuning slow nightly jobs

Platform teams compare Spilled Records with map output records. A ratio well above 3 means extra merge passes; raising the sort buffer (with container memory) or compressing map output often cuts minutes from big jobs.

Counters→io.sort.mb, compression→Fewer disk writes

2. Diagnosing skew

One reducer runs for hours while the others finish in minutes: one key (a popular product, a null customer ID) got most of the shuffle. Our 3-reducer run showed the small version: 4 items to one reducer, none to another.

Hot key→one huge partition→Salting / custom partitioner

3. Sorting benchmarks

TeraSort, the classic Hadoop benchmark, is almost pure shuffle: map reads, the framework sorts and shuffles terabytes, reduce writes. Clusters are tuned and compared on it.

teragen→terasort (shuffle)→teravalidate

4. The same shuffle in Spark

Spark's groupBy and join also write sorted, partitioned shuffle files to local disk, and on YARN they can be served by an external shuffle service in the NodeManager, just like mapreduce_shuffle.

Stage 1 tasks→shuffle files→Stage 2 tasks
