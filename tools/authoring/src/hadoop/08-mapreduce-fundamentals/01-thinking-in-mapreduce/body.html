1 The story

Counting votes the way India does

The college wants one number per item: how many orders and how much money, for every canteen on every campus, for five years. Riya's Python script finishes the 4.7 MB file of one canteen in a tenth of a second. Then Kabir shows her the real folder: 30 campuses, five years, one file per day. Several terabytes. Her laptop would need days just to read it, and the files are spread over hundreds of DataNodes anyway.

R> Sir, can't I just copy all the files to one big server and run my script? A> Think of election counting day. Crores of votes are not carried to Delhi. Every counting table counts its own machines, the totals for each candidate are collected, and then added. MapReduce is the same three steps: map where the data lives, shuffle the partial results so each key ends up in one place, and reduce each key to its answer. K> And the part that really matters: you only write the map and the reduce. Hadoop moves the data between them, runs your code on every node, and reruns whatever fails. A> Today we write our first real MapReduce job, run it on a cluster with HDFS and YARN, and read what Hadoop tells us about it: 1 map task for the small file, 4 for the big one, and one task that Hadoop quietly ran twice.
2 Definition

MapReduce

Formal definition (write this in exams)

MapReduce is a programming model and an execution framework for processing large data sets in parallel on a cluster. The programmer supplies two functions: a map function, applied independently to every input record, that turns a key-value pair (k1, v1) into zero or more intermediate pairs list(k2, v2); and a reduce function that receives each intermediate key with all its values, (k2, list(v2)), and produces the output list(k3, v3). Between them the framework performs the shuffle and sort: it partitions the intermediate pairs by key, transfers them to the reducers and sorts them so all values of a key arrive together. The framework also splits the input, schedules map tasks close to their data (data locality), re-executes failed tasks and writes the output to a distributed file system. In Hadoop 2 and later, MapReduce jobs run on YARN, with one MRAppMaster per job.

In simple words

You describe what to do with one record (map) and how to combine everything that shares a key (reduce). Hadoop runs the map on every block in parallel, groups the results by key, and runs the reduce once per key.

LEVELS> MapReduce at three levels L1> Counting day
  • Every counting table (a worker) counts only the machines on its own table: that is map. Nobody carries all votes to one hall.
  • Partial totals are sorted by candidate and sent to the right desk: that is the shuffle.
  • Each desk adds the partial totals of one candidate: that is reduce. Ten tables or a thousand, the method doesn't change.
  • If one table's counter falls ill, another counter recounts that table only. Hadoop does the same with a failed task.
L2> What you write, what Hadoop does
  • You write: a Mapper (map(key, value, context)), a Reducer (reduce(key, values, context)) and a small driver that sets input, output and classes.
  • Hadoop does: splits the input (Lesson 8.2), starts one map task per split on a node that holds the block, sorts and spills map output, copies it to reducers, merges and groups by key (Lesson 8.4), writes part-r-NNNNN files and _SUCCESS.
  • Map tasks never talk to each other, and neither do reduce tasks. That independence is what lets Hadoop run them anywhere and rerun any one of them.
  • For our job: map turns “1002,vada pav,20” into (“vada pav”, 20); reduce turns (“vada pav”, [20, 20, …]) into vada pav 49986 999720.
L3> Thinking in keys
  • The design question is always: what is the key? Everything that must be combined has to share a key, because only values with the same key ever meet.
  • Map output is the expensive part: it is sorted, written to local disk, and sent over the network. Emit as little as possible (filter early, use compact types, add a combiner in Lesson 9.1).
  • Reducers see each key once, with its values in no guaranteed order. Anything that needs order inside a key needs a secondary sort (Lesson 9.7).
  • MapReduce fits batch jobs that scan everything once. Iterative work (machine learning, graph algorithms) and interactive queries pay the disk write between steps on every pass, which is why Spark and Tez took over those jobs.
/LEVELS EXAM> For “Explain MapReduce with an example”, write the two signatures map(k1, v1) → list(k2, v2) and reduce(k2, list(v2)) → list(k3, v3), name the shuffle and sort in between, and show one record passing through all three (e.g. “1002,vada pav,20” → (vada pav, 20) → vada pav 49986 999720).

your terminal

Runs in the first container. Requests one container per task, preferring nodes that hold each split, and tracks progress, failures and speculation.

Map and reduce tasks

Each runs in its own container (a YarnChild JVM) on a NodeManager. Our lab: map containers of 384 MB.

many per job

JobHistory Server

after the job

TIP> The same model lives on in newer tools. A Hive GROUP BY or a Spark reduceByKey still does map, shuffle by key, reduce; they just keep more in memory and chain steps without writing to HDFS in between.
4 Step by step

Our first MapReduce job, on a real cluster

This module uses a new lab cluster with YARN: a NameNode, a ResourceManager, a JobHistory Server and three workers, each running a DataNode and a NodeManager, so map tasks can run where their blocks are. The setup is in “Run it on your PC”.

  1. Write the map and the reduce

    // map: one CSV line in, one (item, amount) pair out
String[] f = line.toString().split(",");
if (f.length != 3 || f[0].equals("order_id")) return;
item.set(f[1]);  amount.set(Integer.parseInt(f[2]));
ctx.write(item, amount);

// reduce: one item and ALL its amounts in, one line out
for (IntWritable a : amounts) { orders++; revenue += a.get(); }
ctx.write(item, new Text(orders + "\t" + revenue));
    Neither function knows how big the file is or how many machines exist. That is the whole point: the same code runs on 4.7 MB or 4.7 TB.

  2. Submit the job

    hadoop jar mr.jar ItemRevenue /user/hadoop/data/canteen_orders.csv /out/item_revenue

    The client computed one split (the file is a single 4.7 MB block), uploaded the jar, and YARN started an MRAppMaster, one map container and one reduce container.

  4. Look at the output

    One file per reducer, named part-r-00000, and an empty _SUCCESS marker. The keys come out sorted because the shuffle sorted them.

  5. Feed it 90 times more data

    number of splits:4 Killed map tasks=1 Launched map tasks=5 Data-local map tasks=5 attempt_…_m_000000_0 SUCCEEDED worker2 43.9 s attempt_…_m_000000_1 KILLED worker3 11.7 s Speculation: attempt_…_m_000000_0 succeeded first! attempt_…_m_000001_0 SUCCEEDED worker3 30.6 s attempt_…_m_000002_0 SUCCEEDED worker1 29.1 s attempt_…_m_000003_0 SUCCEEDED worker2 28.6 s attempt_…_r_000000_0 SUCCEEDED worker1 25.1 s
    Four blocks, four map tasks running at the same time on three workers, each next to its block. Map 0 lagged, so the MRAppMaster launched a speculative copy on worker3; the original finished first and the copy was killed. Same code, no change.

  6. Be honest about speed

    4.7 MB  plain Python, one process        0.1 s
4.7 MB  MapReduce job on 3 workers       25 s
403 MB  one Java process reading HDFS    5.9 s   (Lesson 6.5)
422 MB  MapReduce job, 4 maps            68 s
    On a laptop-sized cluster, MapReduce is slower: starting containers, sorting, writing map output to disk and copying it costs tens of seconds. It wins when the data is far bigger than one machine can read in time: 10 TB at 200 MB/s is 14 hours for one machine, but under 2 minutes for 500 machines reading their own blocks in parallel.
WARN> The output folder must not exist. Hadoop refuses to start a job whose output directory is already there, so it can never overwrite results by accident. Delete it first (hdfs dfs -rm -r /out/item_revenue) or write to a new folder.
5 See it happen

One job across three workers

Six steps of the 422 MB job: submit, map where the blocks are, a speculative copy, shuffle, reduce, output.

Map, shuffle, reduce 6 steps
What you see
  1. The client splits the 422 MB file into 4 pieces and submits the job to YARN.
  2. Map progress climbs as four map tasks run at the same time.
  3. Three maps finish around 29–31 s; map 0 is slower and holds the job back.
  4. Maps are done; the reducer has fetched their output and is adding up.
  5. Done. Five map attempts were launched for four maps: one was killed.
  6. The output: one line per item, keys in sorted order.
Behind the screen
  1. The MRAppMaster asks YARN for one container per split, preferring the nodes that store each block.
  2. Each map runs next to a copy of its block: Data-local map tasks=5 in the counters.
  3. Map 0 runs slower, so a speculative backup starts on worker3. Whichever finishes first is used.
  4. The reducer copies the sorted map outputs from every worker: this is the shuffle.
  5. The reducer gets each item once with all its amounts and adds them.
  6. The reducer writes its file to HDFS and the job marks the folder with _SUCCESS.

6 Real-world use

MapReduce at work

1. Building a search index

MapReduce was created at Google to rebuild its web index: map emits (word, page) for every page, reduce builds the list of pages per word. Hadoop's first users (Nutch, Yahoo!) did the same.

Crawled pages→map: (word, page)→reduce: posting lists

2. Telecom and bank batch jobs

Nightly jobs summarise billions of call detail records or card transactions per customer: a classic summarization with the customer number as key.

Records (HDFS)→key = customer→Totals per customer

3. Log analytics

Web and app logs from thousands of servers land in HDFS; jobs count errors, users and page views per hour. Facebook and Yahoo! ran tens of thousands of such jobs a day in the 2010s.

Logs→key = (hour, page)→Dashboards

4. Under SQL engines

Hive originally compiled every SQL query into MapReduce jobs; a GROUP BY item is our job. Today Hive runs on Tez and most new work uses Spark, but the map → shuffle → reduce shape is the same.

GROUP BY→map + shuffle + reduce→Result table

Simplified; organisations differ in tools and policies.
