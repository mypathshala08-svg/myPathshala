1 The story

Three desks, one of them empty

Riya's item revenue job works, but it has one reducer doing all the adding. “Let's use three,” says Kabir, and reruns it with -D mapreduce.job.reduces=3. Three output files appear. The first one is empty. The second holds four items, the third holds two. Then Riya writes a small reducer that lists the first three order IDs of each item, and every item shows the same ID three times. Two surprises, both caused by how a reducer really works.

R> Sir, three reducers and one of them did nothing? Isn't Hadoop supposed to divide the work equally? A> Hadoop divides keys, not work. Each key goes to reducer hash(key) % 3. With only six keys, the dice fell four, two and zero. With crores of keys it evens out; with a few keys, or one huge key, it doesn't. K> And the repeated IDs? I saved the values in a list, just like in any Java program. A> The reducer gives you an Iterable that reads the values off a sorted stream, and it puts each one into the same Text object. You saved three references to one object, which ended up holding the last value. Copy what you keep. Today: how the reducer is called, how many to run, where its output goes, and these two traps.
2 Definition

The Reducer

Formal definition (write this in exams)

In Hadoop MapReduce, a Reducer is the user class, extending org.apache.hadoop.mapreduce.Reducer<KEYIN, VALUEIN, KEYOUT, VALUEOUT>, whose reduce(key, Iterable<VALUEIN> values, Context context) method is called once for every distinct intermediate key in its partition, in sorted key order, with all the values for that key. A job has mapreduce.job.reduces reduce tasks (default 1); the Partitioner (by default HashPartitioner, (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks) decides which reduce task receives each key. Each reduce task runs setup() once, reduce() per key and cleanup() once, and writes its output through the job's OutputFormat to one file, part-r-NNNNN, which the output committer moves into the output directory when the task succeeds. The values are delivered as a single-pass iterator that reuses one value object, and their order within a key is not defined.

In simple words

A reducer gets one key at a time, with every value for that key, and writes the answer for that key. The number of reducers decides how many output files you get, and the hash of each key decides which reducer it lands on.

LEVELS> The Reducer at three levels L1> Counting desks
  • On counting day each desk is responsible for some candidates. A rule fixed in advance says which desk gets which candidate, so every slip for a candidate reaches the same desk.
  • A desk takes one candidate's pile at a time, adds it up, writes one line, and moves to the next candidate in alphabetical order.
  • With few candidates, some desks may get none. That desk still opens, and still files an empty result sheet.
L2> How reduce() is called
  • setup(context) runs once, then reduce(key, values, context) once per key, in sorted key order, then cleanup(context) once.
  • values is an Iterable over a merged, sorted stream on disk and in memory. You can loop over it once; there is no going back.
  • Each step of the loop overwrites the same Text or IntWritable object. Use the value immediately, or copy it (new Text(v), v.get()) if you keep it.
  • The order of values inside one key is not guaranteed: our correct run listed chai's IDs as 104221, 150350, 113456. If you need them ordered, that is a secondary sort (Lesson 9.7).
L3> How many reducers, and what they write
  • Default is 1. Set it with job.setNumReduceTasks(n) or -D mapreduce.job.reduces=n. Hadoop's own guideline: about 0.95 or 1.75 × (nodes × containers per node): 0.95 finishes in one wave, 1.75 lets fast nodes take a second wave for better balance.
  • Too few: each reducer is huge and slow. Too many: many tiny output files (Lesson 7.5) and task overhead.
  • Partitioning is by key, so one hot key (say 60% of all orders are chai) goes to one reducer no matter how many you add. Fixes: combiners (9.1), custom partitioners (9.2), salting keys.
  • Each reduce task writes to _temporary/…/attempt_…; when it succeeds the FileOutputCommitter (algorithm version 2 in our logs) moves the file into the output folder. After all tasks, _SUCCESS is written. Output goes to HDFS with normal replication (3 here).
  • With 0 reducers there is no shuffle and no sort: map output is written straight to HDFS as part-m-NNNNN.
/LEVELS EXAM> For “What is the role of the Reducer?” write: receives each key with all its values (after shuffle and sort), called once per key in sorted order, output written to HDFS as part-r-NNNNN, number set by setNumReduceTasks (default 1), keys assigned by the Partitioner (hash % n). Mention that 0 reducers gives a map-only job.

4 Step by step

Reducers on a real cluster

All runs use the Module 8 lab and reducer_lab.sh (in “Run it on your PC”). Input: canteen_orders.csv, 3 lakh orders, 6 items.

  1. The reducer we are running

    public static class SumReducer extends Reducer<Text, IntWritable, Text, Text> {
  protected void reduce(Text item, Iterable<IntWritable> amounts, Context ctx) … {
    long orders = 0, revenue = 0;
    for (IntWritable a : amounts) { orders++; revenue += a.get(); }
    ctx.write(item, new Text(orders + "\t" + revenue));
  }
}
    The four type parameters: input key Text, input value IntWritable (they must match the map output), output key Text, output value Text. a.get() copies the number out at once, so object reuse does no harm here.

  2. Run with 3 reducers

    hadoop jar mr.jar ItemRevenue -D mapreduce.job.reduces=3 /user/hadoop/data/canteen_orders.csv /out/red_3
    Launched reduce tasks=3 Reduce input groups=6 Reduce output records=6 part-r-00000 (0 bytes): part-r-00001 (79 bytes): chai dosa samosa vada pav part-r-00002 (38 bytes): idli poha
    The default HashPartitioner sent chai, dosa, samosa and vada pav to partition 1, idli and poha to 2, and nothing to 0. Reducer 0 still started, found no keys and wrote an empty file. Each file is sorted on its own.

  3. Check the partitions yourself

    def text_hash(s):                     # Hadoop Text.hashCode()
    h = 1
    for b in s.encode():
        h = (31 * h + b) & 0xffffffff
    return h
for item in ["chai", "dosa", "idli", "poha", "samosa", "vada pav"]:
    print(item, (text_hash(item) & 0x7fffffff) % 3)
    chai 1 dosa 1 idli 2 poha 2 samosa 1 vada pav 1
    Exactly the files Hadoop wrote. The partition depends only on the key and the number of reducers, so the same key always lands on the same reducer.

  4. Run with 10 reducers

    hadoop jar mr.jar ItemRevenue -D mapreduce.job.reduces=10 /user/hadoop/data/canteen_orders.csv /out/red_10
    Launched reduce tasks=11 part-r-00000 (0 bytes): part-r-00001 (0 bytes): part-r-00002 (22 bytes): vada pav part-r-00003 (0 bytes): part-r-00004 (19 bytes): dosa part-r-00005 (19 bytes): poha part-r-00006 (18 bytes): chai part-r-00007 (20 bytes): samosa part-r-00008 (0 bytes): part-r-00009 (19 bytes): idli
    Ten tasks, ten files, four empty: you can never use more reducers than you have keys. “Launched reduce tasks=11” is one extra speculative attempt, the same mechanism we saw for maps in Lesson 8.1.

  5. Run with 0 reducers

    hadoop jar mr.jar ItemRevenue -D mapreduce.job.reduces=0 /user/hadoop/data/canteen_orders.csv /out/red_0
hdfs dfs -cat /out/red_0/part-m-00000 | head -3
    Launched map tasks=1 2699986 /out/red_0/part-m-00000 samosa 18 vada pav 20 poha 25
    The reducer class is ignored. Map output goes straight to HDFS, in input order, one pair per order: the shuffle, sort and reduce simply don't happen.

  6. The object-reuse trap

    for (Text id : ids) {
  first3.add(copy ? new Text(id) : id);   // without a copy: the SAME object 3 times
  if (first3.size() == 3) break;
}
    -- copy (correct) -- no copy (-D sample.copy=false) chai [104221, 150350, 113456] chai [113456, 113456, 113456] dosa [78778, 213441, 200658] dosa [200658, 200658, 200658] idli [101007, 50991, 101001] idli [101001, 101001, 101001]
    The iterator reuses one Text; after three steps it holds the third ID, and all three list entries point to it. Notice too that the correct IDs are not in order: values arrive in no defined order within a key.
WARN> Never collect all values of a key into a list unless you know the key is small. A hot key with crores of values will exhaust the reducer's heap (ours had 300 MB). Aggregate as you iterate, or keep only what you need.
5 See it happen

Three reducers and one reused object

Six steps: keys are partitioned, each reducer is called per key, files are committed, then the object-reuse bug in slow motion.

Inside the reduce phase 6 steps
What you see
  1. The job is submitted with three reduce tasks.
  2. All three reducers finish; together they saw 6 key groups.
  3. Three output files: one is empty.
  4. File 1 holds four items, sorted by key.
  5. The sampling reducer without copies prints the same ID three times per item.
  6. With a copy of each value, the three IDs are different (and in no particular order).
Behind the screen
  1. Every map output pair gets a partition number from the hash of its key.
  2. Each reducer fetches only its own partition from every map: reducer 0's partition is empty.
  3. Each reducer calls reduce() once per key, in sorted key order.
  4. Each task writes one file under _temporary; the committer moves it into /out/red_3 and _SUCCESS is written.
  5. The iterator fills ONE Text object again and again; a list of references sees only the last value.
  6. Copying each value keeps three different objects.
6 Real-world use

Reducers at work

1. Sizing reducers for nightly aggregates

Teams set the reducer count from cluster capacity and output size, aiming for output files of a few hundred MB each, so the result is neither one giant file nor thousands of tiny ones.

Output size→reduces ≈ size / 256 MB→Healthy files

2. Hunting skewed reducers

When a job sits at “reduce 99%” for an hour, one reducer usually has a hot key (a default city, a null customer ID). Engineers find it from the reducer counters and fix it with combiners, salting or a custom partitioner.

One slow reducer→Reduce input records per task→Find the hot key

3. Map-only ETL

Cleaning, filtering and format conversion jobs set reducers to 0 and skip the whole shuffle, often halving the run time. DistCp is a map-only job too.

Raw files→map-only job→part-m-* files

4. Code reviews catch object reuse

“Copy Writables you keep” is a standard review check in Hadoop teams; the same reuse appears in Hive UDFs and in Spark when reading Hadoop input formats.

list.add(value)→review→list.add(new Text(value))

Simplified; organisations differ in tools and policies.
