1 The story

Four counters, four reducers, one empty

The canteen has four counters: A for drinks, B for snacks, C for breakfast and D for meals. Riya runs the item-revenue job on 5 lakh orders with 4 reducers, hoping for one output file per counter. She gets four files, but one is completely empty, one holds four items from three different counters, and one does more than three times the work of another. Nobody told Hadoop about counters. It sent each item wherever its hash number pointed.

R> Sir, I asked for 4 reducers. Why does one get nothing? A> Because only 8 different keys exist, and the default HashPartitioner sends each key to hash(key) mod 4. With 8 keys and 4 buckets, it is quite possible that no key lands in bucket 0. It's like 8 students choosing 4 rows by their roll number: nobody planned it to be fair. K> And chai alone is 30% of all orders, so whichever reducer gets chai is always the busiest. A> Today we write our own Partitioner: one reducer per canteen counter. We'll also see what happens when a partitioner returns a number that doesn't exist: every map task fails.
2 Definition

Partitioner

Formal definition (write this in exams)

A Partitioner decides, for every intermediate key-value pair produced by a map task, which reduce task will receive it. It implements int getPartition(KEY key, VALUE value, int numReduceTasks), which must return a number from 0 to numReduceTasks − 1 and must return the same number for equal keys, so that all values of a key reach one reducer. It runs inside the map task (and before the combiner), on every map output record, and is only used when the job has more than one reducer. The default, HashPartitioner, computes (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks. A custom partitioner is set with job.setPartitionerClass(), for example to group related keys, to balance load, or (with TotalOrderPartitioner) to produce globally sorted output.

In simple words

The partitioner is the sorting clerk at the end of every map task: for each pair it writes a reducer number on the envelope. By default the number comes from the key's hash. Write your own when you want to choose which keys travel together.

LEVELS> Partitioners at three levels L1> The letter sorter
  • A post office has 4 delivery vans. A clerk stamps each letter with a van number before it leaves the counter. That clerk is the partitioner.
  • The default clerk uses a formula on the PIN code. Letters with the same PIN always go in the same van, but some vans may get many more letters, and one may get none.
  • A smarter clerk can be told: “all letters for Kharghar go in van 2”. That is a custom partitioner.
L2> How the default works
  • For each map output pair, the map task calls getPartition(key, value, 4) and stores the pair in that partition of its sort buffer (Lesson 8.4).
  • HashPartitioner: (key.hashCode() & Integer.MAX_VALUE) % 4. The & Integer.MAX_VALUE clears the sign bit, because Java's % of a negative number is negative.
  • For Text, hashCode starts at 1 and does h = 31 × h + byte over the UTF-8 bytes. “chai” → 2, “samosa” → 3, “coffee” → 1. No item gives 0.
  • With millions of different keys (student IDs, words) hashing spreads load well. With a handful of keys it is a lottery.
L3> Designing partitioners
  • Correctness: equal keys must always get the same number, from every map task. Never use randomness or the value alone unless that's the plan (salting changes the key itself).
  • Balance: the job ends when the slowest reducer ends. Estimate key sizes (counters or a sample) and pack big keys apart.
  • Hot keys: one key can't be split by any partitioner, because all its values must meet in one reduce call. Split it in the key: chai#0 … chai#3, then add the four partial results in a second step.
  • Composite keys: with a (student, time) key, partition on the student only, or one student's records scatter over reducers (Lesson 9.7).
  • Global sort: TotalOrderPartitioner with a sampled partition file gives reducer 0 the smallest keys, reducer 1 the next range and so on.

4 Step by step

Hash vs counter partitioner on 5 lakh orders

Run on the Module 8 lab cluster with partitioner_lab.sh (in “Run it on your PC”). The input is student_orders.csv (Lesson 9.1), stored in 3 blocks.

  1. Run with the default partitioner

    hadoop jar mr9.jar ItemPartition -D part.mode=hash student_orders.csv /out/part_hash
    part-r-00000: part-r-00001: coffee(40364) idli(44774) poha(45336) thali(30292) part-r-00002: chai(149669) dosa(49927) vada pav(69754) part-r-00003: samosa(69884)
    The job asked for 4 reducers and got 4 files, but the hash of no item came out as 0. Reducer 0 started a container, fetched nothing and wrote an empty file.

  2. Measure each reducer

    bash reduce_tasks.sh job_1792643020992_…
    r_000000 reduce input records 0 groups 0 r_000001 reduce input records 160766 groups 4 r_000002 reduce input records 269350 groups 3 r_000003 reduce input records 69884 groups 1
    Reducer 2 gets chai (149,669 orders on its own) plus two more items: 54% of all records. In a big job, this reducer alone would decide how long you wait.

  3. Write the counter partitioner

    public static class CounterPartitioner extends Partitioner<Text, IntWritable> {
  // A: chai, coffee  B: samosa, vada pav  C: poha, idli  D: dosa, thali
  public int getPartition(Text item, IntWritable amount, int numReduceTasks) {
    Integer c = COUNTER.get(item.toString());
    if (c == null) return 0;                // unknown items go to the first reducer
    return c % numReduceTasks;              // always 0 .. numReduceTasks-1
  }
}
job.setPartitionerClass(CounterPartitioner.class);
    Two safety habits: a fixed answer for unexpected keys, and % numReduceTasks so the same code still works if someone runs it with 2 or 3 reducers.

  4. Run with the counter partitioner

    hadoop jar mr9.jar ItemPartition -D part.mode=counter student_orders.csv /out/part_counter
    part-r-00000: chai(149669) coffee(40364) part-r-00001: samosa(69884) vada pav(69754) part-r-00002: idli(44774) poha(45336) part-r-00003: dosa(49927) thali(30292) r_000000 reduce input records 190033 groups 2 r_000001 reduce input records 139638 groups 2 r_000002 reduce input records 90110 groups 2 r_000003 reduce input records 80219 groups 2
    One file per counter, every reducer busy. Still not perfectly even: counter A carries chai. The partitioner can choose where chai goes, but never split it.

  5. Return a partition that doesn't exist

    return item.toString().length();   // "vada pav" -> 8, but there are only 4 reducers
    Error: java.io.IOException: Illegal partition for chai (4) Error: java.io.IOException: Illegal partition for dosa (4) Error: java.io.IOException: Illegal partition for idli (4) Failed map tasks=10 Job … failed with state FAILED due to: Task failed task_…_m_000001
    The check happens in the map task, on the first bad record. Every attempt failed, Hadoop retried each map up to 4 times, then gave up: 10 failed attempts before the job was killed. Even 4 (“chai”) is illegal: valid numbers are 0 to 3.
WARN> Changing the number of reducers changes where every key goes with HashPartitioner. Don't build anything that assumes “samosa is always in part-r-00003”; read the files by content, or use a partitioner that defines the layout.
5 See it happen

Stamping a reducer number on every pair

Six steps: one map task's output passing through the default partitioner, then the custom one.

Which reducer? 6 steps
What you see
  1. The job starts with 3 map tasks and 4 reducers, using the default partitioner.
  2. Each map task sorts its output into 4 partitions, one per reducer.
  3. The default result: one empty file and an uneven split.
  4. With the counter partitioner, each file holds one canteen counter.
  5. Every reducer now gets two items and real work.
  6. A partitioner that returns 4 for 4 reducers fails every map task.
Behind the screen
  1. The map task produces (item, amount) pairs. Each one must be given a reducer number.
  2. HashPartitioner computes the number from the key's hash: chai 2, samosa 3, coffee 1, dosa 2, idli 1.
  3. All 8 items land in buckets 1, 2 and 3. Reducer 0 receives nothing.
  4. The custom partitioner looks up each item's counter instead.
  5. Every reducer gets work, but counter A with chai is still the biggest.
  6. A partitioner returning numbers 4 and above crashes the map task with “Illegal partition”.
6 Real-world use

Partitioners at work

1. Globally sorted output (TeraSort)

The famous TeraSort benchmark samples the input and uses a total-order partitioner, so reducer 0 gets the smallest keys and the part files read in order form one sorted data set.

Sample keys→Range partitioner→Sorted part files

2. One output file per business unit

Reports split by region, store or product line: a custom partitioner sends each unit's keys to a fixed reducer so each team reads only its own file.

Sales records→Partition by region→File per region

3. Taming hot keys

Click logs where one page or one big customer dominates: teams salt the hot key into several sub-keys, spread them with the partitioner, then merge the partial results.

Hot key→key#0 … key#9→Merge partials

4. Bucketed tables

Hive and Spark bucketing is the same idea made permanent: rows are written into a fixed number of files by hash of a column, so later joins on that column can skip a shuffle.

CLUSTERED BY (student)→hash % buckets→Bucket files

Simplified; organisations differ in tools and policies.
