1 The story

The “efficient” version that was bigger

Kabir wants, for every student and every day, three numbers: how many orders, how much money, and the biggest single order. His first version glues everything into strings: the key is "S0001\t2026-09-01", the value "1,20,20". Riya says strings are wasteful and writes proper Java types instead: a key class with two fields and a value class with an int, a long and an int. They run both on 5 lakh orders. Riya's version moves 40% more bytes through the shuffle.

R> Sir, I used real types instead of strings. How can mine be bigger? A> Look at what your write() does. writeUTF("2026-09-10") writes a 2-byte length and 10 characters: 12 bytes for a date. Then writeInt is always 4 bytes and writeLong always 8, even when the number is 1 or 45. Kabir's text "1,45,45" is only 7 characters. K> So Writable is just “you decide the bytes”. Decide badly and you pay in the shuffle. A> Exactly. Today we write a composite key and a value type, see what Hadoop needs from them (and what happens when you forget the empty constructor), then shrink the same record to 8 bytes with variable-length numbers: 4.3 times smaller than the first try.
2 Definition

Writable and WritableComparable

Formal definition (write this in exams)

Writable (org.apache.hadoop.io.Writable) is Hadoop's serialization interface. A type implements write(DataOutput out), which writes its fields as bytes, and readFields(DataInput in), which reads them back in the same order into an existing object. MapReduce uses Writables for all keys and values that are transferred between tasks or stored in SequenceFiles. Keys must implement WritableComparable, which adds compareTo(): it defines the order in which keys are sorted during the shuffle. The default partitioner uses the key's hashCode() to choose a reducer, so equal keys must have equal hash codes. Because the framework creates instances by reflection and reuses them for many records, a Writable must have a public no-argument constructor and readFields() must overwrite every field. A RawComparator can compare keys directly in their serialized form, avoiding deserialization during sorting.

In simple words

A Writable is a class that knows how to turn itself into bytes and back. You choose which bytes. A key also needs to know how to compare itself, because the shuffle sorts by it.

LEVELS> Writables at three levels L1> Packing a parcel
  • Sending a parcel by courier: you decide how to pack it. Every map output record is packed (write), sent through the shuffle, and unpacked (readFields) on the other side.
  • The receiver unpacks in the same order you packed: first the student, then the day. Change the order on one side only and you get nonsense.
  • A big box for a small thing still costs postage. A 4-byte int for the number 1 is a big box.
L2> What Hadoop needs from your class
  • Value types implement Writable: write() and readFields().
  • Key types implement WritableComparable: also compareTo() (sort order), and override hashCode() and equals() (partitioning).
  • A public no-argument constructor. Without it the map task cannot even start its output collector: our job failed on every attempt.
  • toString() decides how the type looks in TextOutputFormat output: our key prints S0001<TAB>2026-09-01.
  • Objects are reused: readFields() must set every field, and never store the object itself (Lesson 8.5).
L3> Making records small and sorting fast
  • Shuffle cost is per byte: map output is buffered, spilled, compressed, copied and merged. Smaller records mean fewer spills (Lesson 8.4).
  • Encode the information, not the text: an ID like S1413 is the number 1413; a date in one month is a day-of-year number; small counts fit in a VInt.
  • Fixed sizes (writeInt) are simpler and slightly faster to decode; VInts are smaller for small numbers. Our compact job used a little more CPU (8,600 ms vs 8,360) for 4.3× fewer bytes.
  • Sorting calls compareTo() millions of times. The default WritableComparator deserializes both keys first; a RawComparator that compares the bytes directly (as Text and IntWritable do) is faster. Register it with WritableComparator.define() or job.setSortComparatorClass().
/LEVELS EXAM> For “Why does Hadoop use Writable instead of Java Serializable?”, give three points: compact (no class names or metadata per object, only the fields), fast (objects are reused, no new object per record), and comparable in serialized form (RawComparator for sorting). Mention that keys must be WritableComparable.

4 Step by step

A composite key, a value type, and three sizes

Run on the Module 8 lab cluster with writable_lab.sh and student_orders.csv (5 lakh orders, 2,000 students, September 2026). Files are in “Run it on your PC”.

  1. The key: (student, day)

    public static class StudentDayKey implements WritableComparable<StudentDayKey> {
  private String student = "", day = "";
  public StudentDayKey() { }                       // Hadoop needs this
  public void write(DataOutput out) throws IOException { out.writeUTF(student); out.writeUTF(day); }
  public void readFields(DataInput in) throws IOException { student = in.readUTF(); day = in.readUTF(); }
  public int compareTo(StudentDayKey o) {
    int c = student.compareTo(o.student);
    return c != 0 ? c : day.compareTo(o.day);       // sort by student, then day
  }
  public int hashCode() { return student.hashCode() * 31 + day.hashCode(); }
  public String toString() { return student + "\t" + day; }
}
    compareTo makes the output come out sorted by student and then by day. hashCode decides the reducer. Both must agree with equals: equal keys, equal hash.

  2. The value: orders, total, max

    public static class SpendWritable implements Writable {
  private int orders; private long total; private int max;
  public SpendWritable() { }
  public void write(DataOutput out) throws IOException { out.writeInt(orders); out.writeLong(total); out.writeInt(max); }
  public void readFields(DataInput in) throws IOException { orders = in.readInt(); total = in.readLong(); max = in.readInt(); }
}
    The reducer adds orders and totals and keeps the maximum, which is also safe as a combiner (Lesson 9.1). Combine output records: 151,475 instead of 500,000.

  3. Run the Writable version and the Text version

    hadoop jar mr9.jar StudentDay     /user/hadoop/data/student_orders.csv /out/StudentDay
hadoop jar mr9.jar StudentDayText /user/hadoop/data/student_orders.csv /out/StudentDayText
    == StudentDay 24815 ms Map output records=500000 Map output bytes=17500000 Map output materialized bytes=5604593 == StudentDayText 24363 ms Map output records=500000 Map output bytes=12500000 Map output materialized bytes=4132541
    17,500,000 / 500,000 = 35 bytes per record for the Writable, 25 for Text. Key: 2+5 (S1413) + 2+10 (the date) = 19 bytes; value: 4+8+4 = 16 bytes. Text: 1+16 for the key and 1+7 for "1,45,45".

  4. Shrink it: numbers instead of strings, VInts instead of fixed sizes

    private int student;   // "S1413" -> 1413
private int day;       // 2026-09-10 -> day of year 253
public void write(DataOutput out) throws IOException {
  WritableUtils.writeVInt(out, student);   // 1413 -> 3 bytes
  WritableUtils.writeVInt(out, day);       // 253  -> 2 bytes (256 and above need 3)
}
// value: writeVInt(orders), writeVLong(total), writeVInt(max) -> 1 + 1 + 1 bytes for small amounts
    == StudentDayCompact 25126 ms Map output records=500000 Map output bytes=4068724 Map output materialized bytes=1601326
    About 8 bytes per record (6 to 9, depending on the student number and the date): 4.3 times smaller than the first Writable and 3 times smaller than Text. Students S0001–S0127 even fit in 1 byte. CPU time barely moved (8,600 ms).

  5. Check that all three agree

    hdfs dfs -cat /out/StudentDay/part-r-00000 | head -3
diff <(hdfs dfs -cat /out/StudentDay/part-r-00000) <(hdfs dfs -cat /out/StudentDayCompact/part-r-00000)
    S0001 2026-09-01 124 3224 80 S0001 2026-09-02 134 3411 80 S0001 2026-09-03 124 3064 80 compact: same rows text: same rows
    Same 59,946 rows. The compact key's toString() turns the numbers back into S0001 and a date, so the output looks identical.

  6. Forget the no-argument constructor

    # replace  public StudentDayKey() { }  with  public StudentDayKey(String s, String d) { … }
hadoop jar nc.jar StudentDayNoCtor /user/hadoop/data/student_orders.csv /out/nc

    It compiles fine; it fails only on the cluster. The map output collector creates key objects by reflection (ReflectionUtils.newInstance), which needs new StudentDayKey().
WARN> write() and readFields() must handle the same fields in the same order and with the same methods. If write uses writeVInt and readFields uses readInt, nothing fails at compile time; the reducer silently reads wrong numbers or crashes with an EOFException.
5 See it happen

One record, packed and unpacked

Six steps: one record from map() to reduce(), first in the naive Writable, then in the compact one.

write() and readFields() 6 steps
What you see
  1. The mapper fills its reusable key and value and calls ctx.write.
  2. The framework calls key.write(): two writeUTF calls, 19 bytes.
  3. Then value.write(): 16 bytes of fixed-size numbers. 35 in total.
  4. On the reduce side, readFields() refills the same objects for each record.
  5. The compact version writes the same information in 8 bytes.
  6. Over 5 lakh records: 17.5 MB, 12.5 MB, 4.1 MB of map output.
Behind the screen
  1. Before writing, the key and value are just Java objects in the map task.
  2. writeUTF writes a 2-byte length and then each character: 19 bytes for the key.
  3. Fixed-size numbers are mostly zero bytes: 16 bytes for 1, 45 and 45.
  4. The reducer reads the bytes back into reused objects, in exactly the same order.
  5. Variable-length encoding stores 1413, 253, 1, 45, 45 in 8 bytes.
  6. Per record: 35, 25 or about 8 bytes. Multiply by every record of the job.
6 Real-world use

Custom types at work

1. Composite keys for daily aggregates

Telecom and payments jobs aggregate per (customer, day) or (merchant, hour). A composite WritableComparable keeps the key typed and sorts output by customer and then by time.

Transactions→key = (customer, day)→Daily totals

2. Statistics values for combiners

A value type holding sum, count, min and max lets one job compute several statistics with a correct combiner, instead of one job per statistic.

(1, amount, amount)→combine: add, max→avg, max per key

3. Intermediate data between chained jobs

When one job feeds another, output is often written as a SequenceFile of the same Writables, so the next job reads binary records without parsing text.

Job 1→SequenceFile of Writables→Job 2

4. Inside the ecosystem

Hive, HBase and Mahout define their own Writables (HBase's ImmutableBytesWritable, Hive's row Writables). Knowing the interface helps when reading their code or their errors.

Your job→Writable interface→Hive, HBase types
