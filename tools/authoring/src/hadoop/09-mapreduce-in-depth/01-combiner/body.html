1 The story

Two crore ones on the network

Kabir runs word count on the 102 MB feedback file and opens the counters. “Reduce shuffle bytes = 225,867,818.” The map tasks emitted 2 crore 6 lakh pairs, and nearly all of them were (“was”, 1), (“the”, 1), (“chai”, 1): the same few words, each with a 1, copied one by one to a single reducer. Riya adds one line to the driver and runs it again. Same answer, 29 seconds instead of 53, and the shuffle shrinks to 1,083 bytes.

R> One line, and the shuffle went from 226 MB to one kilobyte? What did it do? A> job.setCombinerClass(IntSumReducer.class). It runs your reducer's logic on each map task's output before the shuffle. Instead of sending “chai, 1” a lakh times, every map sends “chai, its total”. The reducer then adds three totals instead of lakhs of ones. K> Then let's use it everywhere. My average-spend job could use the same trick. A> Try it. Your averages will come out wrong for all 2,000 students, and Hadoop won't say a word. Today we see why a combiner may run zero, one or several times, which kinds of logic survive that, and how to fix the average with a (sum, count) pair.
2 Definition

Combiner

Formal definition (write this in exams)

A combiner is an optional, user-supplied function in a MapReduce job that performs local aggregation of the intermediate key-value pairs produced by a map task, before they are transferred to the reducers. It is set with job.setCombinerClass() and is implemented as a Reducer whose input and output key and value types are both equal to the map output types. The framework applies it to sorted map output when spilling the sort buffer and may apply it again when merging spill files (when there are at least mapreduce.map.combine.minspills = 3 spills), and on the reduce side during merges; it may therefore be executed zero, one or many times on any subset of a key's values. Consequently the combining operation must be commutative and associative and must not change the final result, regardless of how often it runs. Its purpose is to reduce the volume of data written to local disk and transferred in the shuffle.

In simple words

A combiner is a mini-reducer that each map task runs on its own output, so it sends “chai: 1,33,000” instead of 1,33,000 lines of “chai: 1”. Hadoop decides when, and how many times, to run it, so it is only safe for logic like adding, counting, max and min.

LEVELS> The combiner at three levels L1> Tally sheets at counting tables
  • Without a combiner, every counting table sends a slip for each single vote to the central desk: lakhs of slips saying “Party X: 1”.
  • With a combiner, each table first writes one tally sheet: “Party X: 4,312”. The central desk adds a handful of sheets.
  • Adding is safe to do in pieces: the total is the same however the votes were grouped. That is the whole rule.
L2> Where it runs and what the counters say
  • The combiner runs inside the map task, on sorted map output, each time the sort buffer spills (Lesson 8.4).
  • With 3 or more spills it runs again while those spills are merged. That is why Combine input records (20,665,132) was larger than Map output records (20,664,760): 372 records produced by earlier combines were combined a second time.
  • The arithmetic: 12 spills × 31 words = 372 records, merged and combined into 3 maps × 31 words = 93 records. Combine output 372 + 93 = 465. The reducer received exactly 93.
  • Its input and output types must both equal the map output types, because its output is fed to the reducer as if the map had written it, and may even be fed to the combiner again.
L3> What is safe to combine
  • Safe: sum, count, max, min, logical AND/OR, set union. Applying them to partial results gives the same final answer.
  • Not safe as-is: average, median, percentiles, “count distinct” by counting, “top-N” on partial counts. An average of partial averages ignores how many values each one stood for.
  • The fix: make the map emit a partial aggregate that can be merged again: (sum, count) for average, (min, max), a set of IDs for distinct. Divide or finish only in the reducer.
  • Hadoop gives no guarantee that the combiner runs at all, so the reducer must produce the right answer whether or not it ran. Never put side effects (writing files, external calls) in a combiner.
/LEVELS EXAM> For “What is a combiner? When can't you use one?”, write: local mini-reducer on map output, set with setCombinerClass, reduces shuffle data; may run 0, 1 or many times, so the function must be commutative and associative with input type = output type = map output type. Example that works: word count (sum). Example that fails: average (use sum and count instead).

4 Step by step

A combiner that helps, and one that lies

Module 9 runs on the Module 8 lab cluster (Lesson 8.1) with a new, bigger dataset made by make_student_orders.py: 5 lakh orders by 2,000 students over September 2026, with the time of each order and 8 items including coffee and thali. Twenty “regulars” (S0001 to S0020) order far more than everyone else, which will matter for partitioning and skew.

  1. Turn the combiner on

    job.setMapperClass(TokenizerMapper.class);
if (conf.getBoolean("wc.combiner", true)) job.setCombinerClass(IntSumReducer.class);
job.setReducerClass(IntSumReducer.class);
    The reducer itself works as the combiner because its input (Text, IntWritable) and output (Text, IntWritable) are both the map output types, and summing is safe to do in pieces.

  2. Run word count without and with it

    hadoop jar mr9.jar WordCountCombiner -D wc.combiner=false /user/hadoop/data/feedback_x20.txt /out/wc_nocomb
hadoop jar mr9.jar WordCountCombiner -D wc.combiner=true  /user/hadoop/data/feedback_x20.txt /out/wc_comb
    == wc_nocomb 52918 ms Map output records=20664760 Combine input records=0 Reduce shuffle bytes=225867818 Reduce input records=20664760 Spilled Records=61994280 == wc_comb 29249 ms Map output records=20664760 Combine input records=20665132 Combine output records=465 Reduce shuffle bytes=1083 Reduce input records=93 Spilled Records=558
    The maps did exactly the same work (20,664,760 pairs each time). What changed is everything after: 93 records instead of 2 crore reached the reducer, and the job was 45% faster.

  3. Check the answer didn't change

    diff <(hdfs dfs -cat /out/wc_nocomb/part-r-00000) <(hdfs dfs -cat /out/wc_comb/part-r-00000) && echo "identical output"
    identical output
    Always compare a run with and without the combiner once. A correct combiner never changes the output.

  4. Notice the combiner ran twice

    Combine input records  20,665,132 = 20,664,760 map pairs + 372
spill combines   : 20,664,760 pairs → 372 records (12 spills × 31 words)
merge combine    :        372       →  93 records (3 maps × 31 words)
Combine output   : 372 + 93 = 465
    Each 102 MB map filled its sort buffer several times. The combiner ran on every spill, and because each map had at least 3 spills, it ran again while merging them. Your combiner must give the same result however many times it runs.

  5. Now the dangerous one: average spend per student

    hadoop jar mr9.jar AvgSpend -D avg.combiner=none  /user/hadoop/data/student_orders.csv /out/avg_none
hadoop jar mr9.jar AvgSpend -D avg.combiner=wrong /user/hadoop/data/student_orders.csv /out/avg_wrong
    S0001 none: 25.90 (3899 orders) | wrong: 26.05 (3 orders) S0007 none: 25.64 (3934 orders) | wrong: 25.50 (3 orders) S1413 none: 25.13 (184 orders) | wrong: 25.30 (3 orders) -- students whose answer differs from the no-combiner run wrong: 2000 of 2000
    The wrong combiner averaged each map's values and passed the average on as if it were a single order. The reducer then averaged three averages, one per map. No error, no warning: every one of the 2,000 answers is slightly wrong.

  6. Fix it with a (sum, count) pair

    // map emits "amount,1"; the combiner adds sums and counts, never divides
for (Text v : vals) { String[] p = v.toString().split(",");
  sum += Double.parseDouble(p[0]); n += Long.parseLong(p[1]); }
ctx.write(s, new Text(sum + "," + n));
    == avg_right 23559 ms Combine input records=500000 Combine output records=6000 Reduce shuffle bytes=107140 S1413 none: 25.13 (184 orders) | right: 25.13 (184 orders) right: 0 of 2000
    6,000 records (2,000 students × 3 maps) instead of 5 lakh, 61 times fewer shuffle bytes, and every answer correct. The division happens once, in the reducer.
WARN> Hadoop never checks whether your combiner is mathematically safe. A wrong combiner produces plausible numbers, not errors. Test with and without it on a sample, and compare the outputs.
5 See it happen

Inside one map task with a combiner

Six steps: spills get combined, merged spills get combined again, then the same idea applied to an average, wrongly and rightly.

Combine, merge, combine again 6 steps
What you see
  1. Without a combiner: 2 crore pairs and 226 MB cross to the reducer.
  2. With a combiner the map emits exactly the same 2 crore pairs.
  3. But the combiner shrinks them: 20,665,132 in, 465 out.
  4. The reducer gets 93 records. Same answer, 45% faster.
  5. The averaging reducer as a combiner: every student's average is a little wrong.
  6. A (sum, count) combiner: small shuffle and every answer right.
Behind the screen
  1. Without a combiner every (word, 1) pair is written to disk and sent to the reducer.
  2. With a combiner, each time the sort buffer spills, its sorted contents are combined before being written.
  3. With 3 or more spills, merging them runs the combiner a second time.
  4. Only one line per word per map leaves the map task.
  5. Wrong: partial averages are passed on as if each were one order, so the counts are lost. (Per-map numbers illustrative.)
  6. Right: partial (sum, count) pairs can be merged any number of times; the reducer divides once. (Illustrative numbers.)
6 Real-world use

Combiners at work

1. Counting events in logs

Page views, errors or clicks per URL per hour: billions of (key, 1) pairs collapse to a few lakh partial totals per map before the shuffle.

(url, 1) × billions→combiner: sum→(url, partial total)

2. Metrics with partial aggregates

Average transaction value per merchant, average latency per API: the map emits (sum, count, min, max) so a combiner can merge them safely; the reducer finishes the averages.

Transactions→(sum, count) combiner→Averages per merchant

3. Inside SQL engines

Hive's hive.map.aggr and Spark's reduceByKey do the same thing automatically: a partial aggregation on the map side, then the final one after the shuffle. A GROUP BY with SUM or COUNT gets it for free.

GROUP BY item→partial aggregate→final aggregate

4. Approximate distinct counts

“Unique users per day” can't be added from partial counts. Teams combine HyperLogLog sketches instead: small structures that can be merged any number of times and give a close estimate.

(day, user)→merge sketches→≈ unique users

Simplified; organisations differ in tools and policies.
