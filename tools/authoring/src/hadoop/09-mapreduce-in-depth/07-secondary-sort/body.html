1 The story

The first and the last order

The canteen manager wants three facts for every one of 2,000 students: the first order of September, the last one, and the longest break between two orders. Riya writes a reducer that loops over a student's orders. The answers are nonsense: the “first” order it prints is from 14 September and the “last” from the 7th. In Lesson 8.5 she had already seen why: inside one key, values arrive in no particular order (chai [104221, 150350, 113456]).

R> Easy fix, Sir: I'll put the 184 orders in an ArrayList and sort them in the reducer. A> For S1413, fine. Our heaviest student has 3,899 orders; a web user can have millions of clicks. Sorting in the reducer means holding all of them in a 300 MB heap. Hadoop is already sorting terabytes for you in the shuffle, on disk if needed. Let it sort by time as well. K> But the shuffle sorts by key, and the key is the student. A> So we make the time part of the key: (student, time). Then we tell Hadoop two things: send all keys of one student to the same reducer, and treat them as one group. That's secondary sort. Our job gave 2,000 correct lines; without the grouping part it gave 490,794 useless ones.
2 Definition

Secondary sort

Formal definition (write this in exams)

Secondary sort is a MapReduce design pattern that delivers the values of each key to the reducer in a defined order, using the framework's shuffle sort instead of sorting in memory. The mapper emits a composite key made of the natural key (the grouping field, e.g. student) and the secondary field (e.g. time) — the value-to-key conversion. Three settings complete it: the sort comparator (the composite key's compareTo, or setSortComparatorClass) orders keys by natural key and then secondary field; a custom partitioner that uses only the natural key, so all records of one natural key reach the same reducer; and a grouping comparator (setGroupingComparatorClass) that compares only the natural key, so consecutive keys with the same natural key form one reduce() call whose values are already in secondary order.

In simple words

Put the field you want sorted (time) into the key next to the field you want grouped (student). Hadoop sorts by both, but you tell it to send and group by the student only. Each reduce() call then gets one student's orders, oldest first.

LEVELS> Secondary sort at three levels L1> The attendance register
  • The office sorts all canteen slips by roll number and then by time, in one big pile. That's the sort comparator.
  • All slips of roll number S1413 go to the same clerk, whatever the time on them. That's the partitioner.
  • The clerk treats all consecutive S1413 slips as one bundle, not one bundle per time. That's the grouping comparator.
  • The clerk only has to read the top slip (first order) and keep reading to the last one; nothing to sort by hand.
L2> The three pieces in code
  • Key: StudentTime implements WritableComparable; compareTo compares student, then time.
  • Partitioner: (k.student.hashCode() & Integer.MAX_VALUE) % n. If it used the whole key, S1413's orders would be spread over every reducer.
  • Grouping comparator: a WritableComparator subclass comparing student only, set with job.setGroupingComparatorClass(StudentGrouping.class).
  • Leave out the partitioner and you get wrong answers once there are 2+ reducers. Leave out the grouping comparator and every distinct (student, minute) becomes its own call: 490,794 in our lab.
L3> What really happens while you iterate
  • The framework reuses one key object. As you step through the values, it deserializes the next record's key into the same object: key.time changes on every step, while key.student stays the same within the group.
  • That is why our mapper also puts the time in the value: reading the value is the clear, safe way. You can read key.time inside the loop, but never keep a reference to the key and expect it to stay put.
  • For descending order (latest first) add a sort comparator with setSortComparatorClass that reverses the time part, keeping the grouping on student.
  • For speed, production code often uses a raw comparator that compares serialized bytes without creating objects. Correctness first, then that optimisation.
/LEVELS EXAM> For “What is secondary sort in MapReduce?”, list the four parts: composite key (natural key + secondary field), sort comparator, partitioner on the natural key, grouping comparator on the natural key. Then say why: values are otherwise unordered and sorting them in reducer memory does not scale.

4 Step by step

Building FirstLastOrder

Run on the Module 8 lab cluster with secondary_sort_lab.sh (in “Run it on your PC”). Input: student_orders.csv, 5 lakh orders order_id,student_id,time,item,amount.

  1. Move the time into the key

    public static class StudentTime implements WritableComparable<StudentTime> {
  String student = "", time = "";
  public int compareTo(StudentTime o) {            // sort: student, then time
    int c = student.compareTo(o.student);
    return c != 0 ? c : time.compareTo(o.time);
  }
}
// in map():
key.student = f[1]; key.time = f[2];
val.set(f[2] + " " + f[3]);                        // "2026-09-01 14:18 vada pav"
ctx.write(key, val);
    The time “2026-09-01 14:18” sorts correctly as text because it is written year-month-day hour:minute. A format like 1/9/2026 would sort wrongly.

  2. Partition by student only

    public int getPartition(StudentTime k, Text v, int n) {
  return (k.student.hashCode() & Integer.MAX_VALUE) % n;
}
    The time must not influence the partition, or one student's orders would land on several reducers. The key's hashCode() also uses only the student, as a second guard.

  3. Group by student only

    public static class StudentGrouping extends WritableComparator {
  public StudentGrouping() { super(StudentTime.class, true); }
  public int compare(WritableComparable a, WritableComparable b) {
    return ((StudentTime) a).student.compareTo(((StudentTime) b).student);
  }
}
job.setPartitionerClass(StudentPartitioner.class);
job.setGroupingComparatorClass(StudentGrouping.class);
    The true in super(…, true) tells the comparator to create key instances so it can deserialize and compare them.

  4. Read the values in order

    for (Text v : vals) {                  // arrives in time order thanks to the sort
  if (first == null) first = s;
  // gap = minutes between prev and s; remember the largest
  prev = s; last = s; n++;
}
    One pass, three variables. Nothing is stored, whether the student has 184 orders or 18 lakh.

  6. Remove the grouping comparator

    hadoop jar mr9.jar FirstLastOrder -D ss.grouping=false /user/hadoop/data/student_orders.csv /out/ss_false
    Reduce input groups=490794 Reduce output records=490794 S0001 1 orders | first 2026-09-01 08:09 poha | last 2026-09-01 08:09 poha | longest gap 0 h (null -> null) S0001 2 orders | first 2026-09-01 08:15 poha | last 2026-09-01 08:15 thali | longest gap 0 h (2026-09-01 08:15 -> 2026-09-01 08:15) S0001 1 orders | first 2026-09-01 08:18 vada pav | last 2026-09-01 08:18 vada pav | longest gap 0 h (null -> null)
    Now the full key decides the groups: every distinct (student, minute) is its own reduce() call. Only orders in the very same minute (S0001's poha and thali at 08:15) share a call. The job still “succeeds”, with 490,794 wrong lines.
WARN> Secondary sort does not fail loudly when a piece is missing. Without the partitioner, results are wrong only when there are 2+ reducers; without the grouping comparator the output just gets bigger. Always check Reduce input groups: it must equal the number of natural keys (2,000 here).
5 See it happen

From mixed-up orders to one sorted group

Six steps for two students: map emits composite keys, the partitioner routes by student, the shuffle sorts by (student, time), grouping makes one call per student.

Composite key, partition, sort, group 6 steps
What you see
  1. The job starts: three map tasks read the orders.
  2. Every order becomes one map output record with a (student, time) key.
  3. The reducer merges the sorted outputs of the three maps.
  4. 500,000 records arrive in only 2,000 groups: one per student.
  5. Each student's line is computed in a single pass.
  6. Without the grouping comparator, there is a group per (student, minute).
Behind the screen
  1. The mapper emits (student, time) keys; the time has moved from the value into the key.
  2. The custom partitioner looks only at the student, so S1413 goes to one reducer.
  3. The shuffle sorts keys by student, then time, using the key's compareTo.
  4. The grouping comparator compares only the student, so all S1413 keys form one group.
  5. The reducer walks the group once; the shared key object's time changes as it goes.
  6. Without grouping, each (student, minute) is a separate call: 490,794 of them.
6 Real-world use

Secondary sort at work

1. Web and app sessionization

Clickstream jobs sort each user's events by timestamp and cut a new session whenever the gap exceeds 30 minutes, to count sessions, session length and bounce rate.

Click logs→key (user, time)→Sessions per user

2. Running balances in banking

Transactions of each account, sorted by posting time, give the running balance and the first overdraft moment without loading an account's full history into memory.

Transactions→key (account, time)→Statements

3. Top-N per group

Best-selling products per store or top scorers per exam centre: sort by (group, value descending) and keep the first N values of each group.

Sales→key (store, −revenue)→Top 10 per store

4. Memory-safe reduce-side joins

Adding a tag to the key so the small table's row sorts first lets the reducer stream the big side without buffering it, the fix for the buffering seen in Lesson 9.5.

Menu + orders→key (item, tag)→Streamed join
