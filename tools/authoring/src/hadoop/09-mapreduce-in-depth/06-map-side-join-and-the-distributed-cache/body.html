1 The story

Give every worker a copy of the menu card

The reduce-side join from Lesson 9.5 worked, but Riya keeps looking at one counter: 24,448,645 bytes shuffled. Five lakh orders crossed the network just so each could meet one line of a menu that has seven lines. Kabir laughs: “It's like sending every customer to the head office to ask what category a samosa is. Just print the menu card and stick it on every counter.”

A> When one side of a join is small, don't move the big side to meet it. Move the small side to every map task instead. Hadoop has a built-in delivery service for exactly that: the distributed cache. R> So each map task loads the menu into memory once, and then looks up every order as it reads it? A> Exactly. A map-only job: no shuffle, no sort, no reducer. Today we ran it on the same 5 lakh orders and got the same 459,636 joined rows, about six seconds faster, with nothing crossing the network. K> And the catch, I'm guessing, is that the menu must fit in memory. A> That is the one rule. A seven-line menu fits anywhere. A 50 GB customer table does not, and then you are back to the reduce-side join.
2 Definition

Map-side join and the distributed cache

Formal definition (write this in exams)

A map-side join combines records from two data sets inside the map phase, without a shuffle. In its most common form, the replicated (or broadcast) join, the smaller data set is copied to every map task, loaded into an in-memory hash table in setup(), and each record of the larger data set is joined by a lookup as it is read; the job can be map-only. The copy is delivered by the distributed cache: files registered with Job.addCacheFile() or the -files, -archives and -libjars generic options are downloaded from HDFS by each NodeManager once per node into a local cache, and made available to every container of the job, optionally under a symlink name given after #. A second form, the composite (sort-merge) map-side join, needs no memory but requires both inputs to be sorted by the join key and partitioned identically into the same number of files.

In simple words

Give every worker its own copy of the small table, keep it in a dictionary, and add the matching column to each big-table row while reading it. Nothing is sent to a reducer, so it is fast, as long as the small table really is small.

LEVELS> Map-side join at three levels L1> A menu card on every counter
  • Each counter (map task) gets a printed copy of the menu card (the small table).
  • When an order comes in, the counter reads the category off its own card and writes the bill at once. No one walks to the head office.
  • This only works because the card is small. If the “card” were a phone book of every student, you couldn't print one for every counter.
L2> How the job is built
  • Driver: job.addCacheFile(new URI("/user/hadoop/data/menu.csv#menu")) and job.setNumReduceTasks(0).
  • setup(): open ./menu (the symlink), read every line into a HashMap<item, category>. It runs once per map task, not once per record.
  • map(): look up the item; if found, write the order plus its category; if not, increment a counter. Each line is handled on its own, so the output keeps the input order.
  • Output: one part-m-NNNNN per map task, unsorted. Our three files were 9.0 MB, 9.0 MB and 2.8 MB because the third split was the short tail of the file.
L3> Where it breaks and what else exists
  • Memory: the hash table lives in the map JVM's heap (300 MB in our lab, -Xmx300m). Java objects take several times the file size, so a 100 MB file can need 300–500 MB of heap. Measure, and raise mapreduce.map.memory.mb and -Xmx together if needed.
  • Inner vs outer: unmatched big-side rows can be dropped (inner) or written with an empty value (left outer). Unmatched small-side rows can't be reported, because no single task sees all big-side rows.
  • Composite join: if both inputs are already sorted by the key and split into the same number of identically partitioned files (for example, outputs of two jobs with the same partitioner and reducer count), CompositeInputFormat merges them in the map with no memory limit.
  • Today: Hive converts joins with a small table into a map join automatically (hive.auto.convert.join), and Spark does a broadcast hash join below spark.sql.autoBroadcastJoinThreshold (10 MB by default). Same idea, same memory rule.
/LEVELS EXAM> For “Explain map-side join”, give: small table shipped with the distributed cache, loaded into a hash map in setup(), lookup in map(), no reducer and no shuffle; the condition (small side fits in memory); and the alternative for two big tables (reduce-side join, or a composite join when both are sorted and identically partitioned).

code

4 Step by step

A replicated join on the lab cluster

Same data as Lesson 9.5: student_orders.csv (5 lakh orders, 3 splits) and a menu with “coffee” removed on purpose. Full scripts are in “Run it on your PC”.

  1. Register the small file and switch off reducers

    job.addCacheFile(new URI(rest[1] + "#menu"));   // ship the menu, linked as ./menu
job.setMapperClass(JoinMapper.class);
job.setNumReduceTasks(0);                       // no reducer, so no shuffle at all
    The client records the HDFS path in the job configuration. Before any map container starts on a node, that node's NodeManager downloads the file once into its local file cache.

  2. Load it once per task, in setup()

    try (BufferedReader r = new BufferedReader(new FileReader("menu"))) {
  String line;
  while ((line = r.readLine()) != null) {
    String[] f = line.split(",");
    category.put(f[0], f[1]);
  }
}
    cache files: [/user/hadoop/data/menu_nocoffee.csv#menu] menu loaded in setup(): 7 items, working dir = /tmp/hadoop-hadoop/nm-local-dir/usercache/hadoop/appcache/application_1792643020992_0040/container_1792643020992_0040_01_000003/.
    The file is opened by its plain name menu: YARN placed a symlink with that name in the container's working directory, pointing to the localized copy. No HDFS client code is needed.

  3. Join while reading

    String cat = category.get(line.toString().split(",")[3]);
if (cat == null) { ctx.getCounter(Join.ORDERS_WITHOUT_MENU).increment(1); return; }
out.set(line + "," + cat);
ctx.write(out, NullWritable.get());
    One hash lookup per order. Orders with no menu row (all coffee orders) are counted and dropped: an inner join. Writing them with an empty category instead would make it a left outer join.

  4. Run it

    hadoop jar mr9.jar JoinMapSide /user/hadoop/data/student_orders.csv /user/hadoop/data/menu_nocoffee.csv /out/JoinMapSide
    number of splits:3 Launched map tasks=3 Map input records=500000 Map output records=459636 ORDERS_JOINED=459636 ORDERS_WITHOUT_MENU=40364 Bytes Written=20851062 took 18943 ms
    No “Launched reduce tasks”, no shuffle counters, no Spilled Records: map output goes straight to HDFS. The reduce-side join of the same data needed a reducer and moved 24,448,645 bytes.

  5. Look at the output

    hdfs dfs -ls /out/JoinMapSide
hdfs dfs -cat /out/JoinMapSide/part-m-00000 | head -2
    9020852 /out/JoinMapSide/part-m-00000 8993924 /out/JoinMapSide/part-m-00001 2836286 /out/JoinMapSide/part-m-00002 1,S1413,2026-09-14 15:30,dosa,45,meal 2,S0973,2026-09-26 20:11,samosa,18,snack
    One file per map task, rows in the same order as the input (order 1, then order 2). The reduce-side output came out grouped by item instead, because the reducer received it sorted by key.

  6. Check it against the reduce-side join

    diff <(hdfs dfs -cat /out/JoinReduceSide/part-* | sort) <(hdfs dfs -cat /out/JoinMapSide/part-* | sort)
    identical (459,636 rows each, compared after sorting)
    Same answer, different route. Always verify a rewritten join this way before trusting its speed.
WARN> A replicated join that works on test data can fail in production when the “small” table grows: every map task holds its own full copy in heap, so the job dies with OutOfMemoryError or containers are killed for exceeding memory. Check the small side's size in the driver (or in your scheduler) and fall back to a reduce-side join above a limit.
5 See it happen

From HDFS to every container, then a lookup per order

Six steps of the JoinMapSide job: register, localize, symlink, load, join, write.

A broadcast join 6 steps
What you see
  1. The job is submitted with the menu registered as a cache file.
  2. Before tasks start, each worker's NodeManager fetches the menu.
  3. The task log shows the cache file the task received, with its #menu link name.
  4. setup() reads ./menu into a HashMap: 7 items.
  5. Every order is joined during the map; coffee orders are only counted.
  6. Joined rows land in part-m files, in input order. 18.9 s in total.
Behind the screen
  1. addCacheFile only writes the HDFS path into the job's configuration.
  2. The NodeManager downloads the file to its local filecache once, for all containers on that node.
  3. Each container gets a symlink ./menu pointing at the local copy.
  4. setup() reads the file into a HashMap that lives in the task's heap.
  5. map() joins each order with one lookup; unknown items only increment a counter.
  6. Joined rows are written directly to HDFS as part-m files.
6 Real-world use

Map-side joins at work

1. Enriching transactions with a code table

Billions of UPI or card transactions get the bank name and branch city from a few-MB IFSC or merchant-category table, joined in memory on every mapper.

Transactions→broadcast lookup→Enriched rows

2. Geo-tagging web logs

A GeoIP range file shipped with -files lets each mapper convert client IPs to city and state while parsing log lines.

Access logs→-files geoip.csv→Visits per city

3. Hive and Spark do it for you

A Hive query joining a fact table with a small dimension table becomes a map join automatically; Spark SQL broadcasts tables under 10 MB by default. Knowing the idea helps you read their plans and fix out-of-memory errors.

SQL JOIN→small table broadcast→No shuffle of the big side

4. Bucketed tables for big-big joins

Two large tables bucketed and sorted on the same key into the same number of files (Hive sort-merge-bucket join) can be joined file by file in the map phase: the composite join idea.

Bucket 7 of A+Bucket 7 of B→Merged in one map
