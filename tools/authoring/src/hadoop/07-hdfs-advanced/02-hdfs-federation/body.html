1 The story

When one NameNode's memory is not enough

The university cluster is a success. The canteen project, the hostel system, exam results and research labs all store data in it. Now there are hundreds of millions of files. The NameNode keeps every file and block in RAM, its heap is already huge, garbage-collection pauses are getting longer, and every team's jobs queue up behind the same NameNode. Adding DataNodes adds disk, but not a single extra byte of NameNode memory. HA (Lesson 7.1) gave the NameNode a spare, but the spare has exactly the same limits.

A> The answer is HDFS federation. Instead of one NameNode for everything, we run several independent NameNodes, each owning part of the namespace: one for /canteen, one for /hostel. They don't talk to each other at all. R> Then each one needs its own DataNodes? A> No, that's the clever part. The same DataNodes serve all of them. Each NameNode gets its own block pool on every DataNode, so storage is shared and grows for everyone. Clients see one tree through a mount table. Today we start two NameNodes on the same three DataNodes, look inside a DataNode's disk, try to move a file between them, and switch one NameNode off.
2 Definition

HDFS federation

Formal definition (write this in exams)

HDFS federation scales the namespace layer horizontally by running multiple independent NameNodes, each managing its own namespace volume: a namespace (directory tree and file metadata) plus a block pool (the set of blocks belonging to that namespace). NameNodes do not coordinate with each other. All NameNodes share one cluster ID and the same set of DataNodes; each DataNode registers with every NameNode, stores blocks of each pool in a separate directory (current/BP-…), and sends heartbeats and block reports per pool. Clients obtain a unified view through a client-side mount table (ViewFS, viewfs://) or through Router-Based Federation (RBF), where stateless routers forward requests according to a shared mount table. Each nameservice may itself be highly available.

In simple words

Several NameNodes split the folder tree between them, like several librarians each responsible for different sections, while all the bookshelves (DataNodes) are shared. A map tells clients which librarian to ask for which folder.

LEVELS> Federation at three levels L1> A library with several librarians
  • One librarian can only remember so many books. So the library hires a second: one for science, one for arts.
  • Both use the same shelves. Each shelf has a science corner and an arts corner (block pools).
  • A signboard at the entrance says which librarian to ask for which section (mount table). If the arts librarian is on leave, science books can still be borrowed.
L2> How it is set up and used
  • Format each NameNode with the same cluster ID (hdfs namenode -format -clusterId campus-cluster); list all nameservices in dfs.nameservices so DataNodes register with every NameNode.
  • Each NameNode only knows its own files: hdfs dfs -ls -R hdfs://nn-canteen:8020/ showed only /canteen.
  • With a ViewFS mount table, hdfs dfs -ls / shows /canteen, /hostel, /tmp as one tree.
  • Moving a file between namespaces is a copy (distcp or cp) plus delete, not a rename.
L3> What architects weigh
  • Why: NameNode heap grows with objects (files, folders, blocks); a common rule of thumb is roughly 150 bytes per object, so hundreds of millions of objects need very large heaps. RPC load also concentrates on one process. Federation splits both.
  • ViewFS vs RBF: ViewFS puts the mount table in every client's configuration (changes must reach every client); RBF keeps it in a shared state store behind routers, so clients use one address and admins can move mount points centrally.
  • Federation + HA: independent. A large cluster may have 4 nameservices, each with an active and standby NameNode.
  • Costs: more NameNodes to run and monitor, uneven growth between namespaces, and no atomic rename across them. Choosing the split (by team, by data domain) matters.
/LEVELS EXAM> For “Explain HDFS federation”, draw two NameNodes with separate namespaces and block pools, shared DataNodes with one folder per block pool, and a mount table on top. Contrast with HA: HA = availability of one namespace; federation = scalability of the namespace.

Unifying the namespaces

ViewFS

Mount table in the client's core-site.xml (fs.viewfs.mounttable.*). Simple, no extra servers; every client needs the same config.

client-side

Router-Based Federation

hdfs dfsrouter processes with a shared state store; hdfs dfsrouteradmin -add /canteen nsc /canteen. Clients talk to routers.

server-side

Direct URIs

hdfs://nn-hostel:8020/hostel: works, but hard-codes which namespace holds the data.

avoid

Split by

Team, business domain or data type (e.g. /user vs /warehouse vs /tmp), so each namespace grows predictably.

design
TIP> Putting /tmp and other small-file-heavy, high-churn folders on their own namespace is a classic use of federation: their constant creates and deletes no longer slow down the NameNode that serves production data.
4 Step by step

Two NameNodes, three shared DataNodes

Our lab: NameNodes nn-canteen (nameservice nsc) and nn-hostel (nsh), and 3 DataNodes, all apache/hadoop:3.5.0. Commands run on datanode-1; full script in “Run it on your PC”.

  1. Configure two nameservices, format with one cluster ID

    HDFS-SITE.XML_dfs.nameservices=nsc,nsh
HDFS-SITE.XML_dfs.namenode.rpc-address.nsc=nn-canteen:8020
HDFS-SITE.XML_dfs.namenode.rpc-address.nsh=nn-hostel:8020
# on each NameNode, once:
hdfs namenode -format -nonInteractive -clusterId campus-cluster
    nn-canteen: blockpoolID=BP-1200013783-172.21.0.3-1792598083981 clusterID=campus-cluster nn-hostel: blockpoolID=BP-343349822-172.21.0.2-1792598083339 clusterID=campus-cluster
    Same cluster ID, different block pool IDs. A DataNode accepts NameNodes only from its own cluster ID, so getting this right at format time is essential.

  2. One tree for the client

    <name>fs.defaultFS</name><value>viewfs://campus</value>
<name>fs.viewfs.mounttable.campus.link./canteen</name><value>hdfs://nn-canteen:8020/canteen</value>
<name>fs.viewfs.mounttable.campus.link./hostel</name><value>hdfs://nn-hostel:8020/hostel</value>
    $ hdfs dfs -ls / Found 3 items -r-xr-xr-x - hadoop users 0 2026-10-21 15:58 /canteen -r-xr-xr-x - hadoop users 0 2026-10-21 15:58 /hostel -r-xr-xr-x - hadoop users 0 2026-10-21 15:58 /tmp $ hdfs dfs -ls /canteen /hostel -rw-r--r-- 3 hadoop supergroup 2488895 2026-10-21 15:58 /canteen/orders.csv -rw-r--r-- 3 hadoop supergroup 538894 2026-10-21 15:58 /hostel/rooms.csv
    The root / is not stored anywhere: ViewFS builds it from the mount table (hence the read-only r-x entries). Each mount point leads to a different NameNode.

  3. Each NameNode knows only its own files

    hdfs dfs -ls -R hdfs://nn-canteen:8020/ ; echo ---; hdfs dfs -ls -R hdfs://nn-hostel:8020/
    drwxr-xr-x - hadoop supergroup 0 2026-10-21 15:58 hdfs://nn-canteen:8020/canteen -rw-r--r-- 3 hadoop supergroup 2488895 2026-10-21 15:58 hdfs://nn-canteen:8020/canteen/orders.csv --- drwxr-xr-x - hadoop supergroup 0 2026-10-21 15:58 hdfs://nn-hostel:8020/hostel -rw-r--r-- 3 hadoop supergroup 538894 2026-10-21 15:58 hdfs://nn-hostel:8020/hostel/rooms.csv drwxr-xr-x - hadoop supergroup 0 2026-10-21 15:55 hdfs://nn-hostel:8020/tmp
    Two completely separate directory trees, each in its own NameNode's memory.

  4. Inside a DataNode: one folder per block pool

    ls /tmp/hadoop-hadoop/dfs/data/current/ ; du -sh /tmp/hadoop-hadoop/dfs/data/current/BP-*
for nn in nn-canteen nn-hostel; do hdfs dfsadmin -fs hdfs://$nn:8020 -report | grep -m1 'Live datanodes'; done
    BP-1200013783-172.21.0.3-1792598083981 BP-343349822-172.21.0.2-1792598083339 VERSION 2.5M /tmp/hadoop-hadoop/dfs/data/current/BP-1200013783-172.21.0.3-1792598083981 572K /tmp/hadoop-hadoop/dfs/data/current/BP-343349822-172.21.0.2-1792598083339 nn-canteen: Live datanodes (3): nn-hostel: Live datanodes (3):
    The same disk holds both pools: 2.5 MB of canteen orders, 572 KB of hostel rooms. Both NameNodes see all three DataNodes, which heartbeat to each separately.

  5. No rename across namespaces

    hdfs dfs -mv /canteen/orders.csv /hostel/orders.csv
    mv: Renames across Mount points not supported
    A rename is a metadata change inside one NameNode. Two NameNodes can't do it atomically together, so you must copy and delete. Plan the namespace split so that jobs don't need to move data across it.

  6. Switch one NameNode off

    docker stop lab72-nn-canteen-1
hdfs dfs -ls /hostel
hdfs dfs -ls /canteen
    -rw-r--r-- 3 hadoop supergroup 538894 2026-10-21 15:58 /hostel/rooms.csv -ls: java.net.UnknownHostException: nn-canteen
    Failure isolation: the hostel namespace keeps working. The canteen namespace is unavailable (in our Docker lab the stopped container's name no longer resolves). In production, each nameservice would also be HA.
WARN> Federation does not make one namespace bigger or faster: a single folder tree still lives in one NameNode. If one team's namespace outgrows its NameNode, you must split that tree further (or reduce small files, Lesson 7.5).
5 See it happen

One client, two NameNodes, shared DataNodes

Six steps from our lab: writing to two mount points, looking at the DataNode, and losing one NameNode.

Federation in action 6 steps
What you see
  1. The client writes the orders file to /canteen.
  2. It writes the rooms file to /hostel, with the same command style.
  3. Listing / shows one tree with three mount points.
  4. On a DataNode's disk, there are two block pool folders, one per NameNode.
  5. Moving a file from /canteen to /hostel is refused.
  6. With the canteen NameNode stopped, /hostel still works and /canteen fails.
Behind the screen
  1. The mount table routes /canteen to nn-canteen, which places blocks in its pool on the DataNodes.
  2. /hostel goes to nn-hostel; its blocks go to the other pool on the same DataNodes.
  3. The root listing is built by the client from the mount table.
  4. Each DataNode stores both pools in separate folders and sends a block report per pool to the right NameNode.
  5. The NameNodes share nothing but DataNodes and the cluster ID, so a cross-namespace rename can't be done.
  6. One NameNode stopping affects only its own namespace.
6 Real-world use

Federation at work

1. Very large clusters

Organisations whose HDFS holds hundreds of millions to billions of files have publicly described running many NameNodes with federation, often behind routers, because no single NameNode heap could hold their namespace.

Billions of files→Many nameservices→One view via routers

2. Isolating noisy workloads

Scratch and staging folders with millions of short-lived files get their own namespace, so their churn doesn't slow the NameNode that serves production tables.

/tmp, /staging→Separate NameNode→Stable prod latency

3. Moving data without changing paths

With Router-Based Federation, admins can copy a folder to a less loaded namespace and then repoint its mount entry. Users keep using the same path.

distcp→Update mount table→Same path, new NameNode

4. Multi-tenant platforms

Shared enterprise clusters give big business units their own namespace for isolation and capacity planning, while sharing DataNodes, YARN and operations.

Business units→One namespace each→Shared storage

Simplified; organisations differ in tools and policies.
