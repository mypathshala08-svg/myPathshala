1 The story

The file that was deleted on purpose, by mistake

Result day. A tired operator cleaning old folders deletes /user/hadoop/results/2026/sem1.csv with -skipTrash. Ten minutes later the portal shows “file not found” to thousands of students. Two weeks earlier, a research student's script filled 40 TB of the shared cluster with temporary files overnight, and every other team's jobs failed with “disk full”. Replication protects against broken disks, not against people and runaway scripts. HDFS has three different tools for that, and today Riya tries all three.

A> Trash catches ordinary deletes, but only if it's switched on and nobody uses -skipTrash. Snapshots are the real safety net: a read-only picture of a folder at a moment in time, taken in about a second however big the folder is, from which you can copy back anything. And quotas stop a single folder from eating the cluster's disk or the NameNode's memory. R> If a snapshot keeps everything, doesn't it double the space? A> No, that's the beauty. A snapshot stores no copies at creation; it only remembers what changed afterwards. Today we delete a file and bring it back from a snapshot, hit both kinds of quota (one of them in a very surprising way), and use the trash properly.
2 Definition

Snapshots, quotas and trash

Formal definition (write this in exams)

An HDFS snapshot is a read-only, point-in-time image of a directory subtree, created on a directory that an administrator has made snapshottable (hdfs dfsadmin -allowSnapshot). Creation is an O(1) metadata operation in the NameNode; no blocks are copied, and later changes are recorded as differences so that the snapshot's view (under dir/.snapshot/name) is preserved. Quotas limit a directory tree: the name quota caps the number of files and directories (including the directory itself), and the space quota caps raw bytes consumed including all replicas, with a full block's worth of space charged when a block is allocated. The trash is a client-side feature enabled by fs.trash.interval (minutes, default 0 = off): deleted paths are moved to /user/<name>/.Trash/Current, periodically rolled into timestamped checkpoints, and permanently removed after the interval.

In simple words

Snapshot: a photo of a folder you can always look back at. Quota: a limit on how many files or how many bytes a folder can have. Trash: a recycle bin for deleted files, if it is switched on.

LEVELS> Protection at three levels L1> Your phone's photos
  • Trash is the “Recently deleted” album: deleted photos wait there for a while. But “Delete permanently” skips it.
  • Snapshot is like a backup of the album at 9 am: whatever you do afterwards, you can open the 9 am version.
  • Quota is the storage limit on your cloud plan: you can't add more once it's full.
L2> How to use each one
  • Snapshots: hdfs dfsadmin -allowSnapshot /dir (admin, once), then hdfs dfs -createSnapshot /dir name. Restore by copying from /dir/.snapshot/name/…. Compare with hdfs snapshotDiff /dir s1 s2.
  • Quotas: hdfs dfsadmin -setQuota N /dir, -setSpaceQuota 1g /dir; check with hdfs dfs -count -q -h -v /dir; remove with -clrQuota, -clrSpaceQuota.
  • Trash: set fs.trash.interval (e.g. 1440 = 1 day) in core-site.xml; restore with -mv from .Trash/Current/….
L3> Details that surprise people
  • Snapshots pin blocks: deleting a file doesn't free its space while any snapshot still refers to it. Old snapshots must be deleted (-deleteSnapshot) to reclaim disk.
  • Snapshots are not backups: they live on the same cluster. A lost cluster loses them too; use DistCp to another cluster (Module 12) for disaster recovery. DistCp can even use snapshot diffs to copy only changes.
  • Space quota and blocks: while a block is being written, the full block size × replication is reserved. A 10 MB quota with 128 MB blocks can't accept even one tiny file.
  • Trash is client-side: the Java API's delete(), many tools, and -skipTrash bypass it. Only a snapshot reliably protects against all deletes.
  • Name quotas protect the NameNode: they cap object counts in a tree, which matters more than bytes for small-file-heavy teams (Lesson 7.5).
/LEVELS EXAM> Answer “HDFS snapshots” with: definition (read-only point-in-time copy of a directory), how to enable and create (-allowSnapshot, -createSnapshot), where they appear (.snapshot), that no data is copied at creation, and uses (accidental delete recovery, backups/DR via DistCp, consistent reads).

4 Step by step

Delete, restore, limit, recycle

All commands ran on the namenode container of the lab cluster; the full script is in “Run it on your PC”.

  1. Make a folder snapshottable and take a snapshot

    hdfs dfsadmin -allowSnapshot /user/hadoop/results
time hdfs dfs -createSnapshot /user/hadoop/results before_results
    Allowing snapshot on /user/hadoop/results succeeded Created snapshot /user/hadoop/results/.snapshot/before_results real 0m1.727s
    The NameNode only records the snapshot; no blocks are copied, so a folder with a million files snaps just as fast. The 1.7 s is the Java client starting.

  2. Delete for good, then restore

    hdfs dfs -rm -skipTrash /user/hadoop/results/2026/sem1.csv
hdfs dfs -ls /user/hadoop/results/.snapshot/before_results/2026
hdfs dfs -cp /user/hadoop/results/.snapshot/before_results/2026/sem1.csv /user/hadoop/results/2026/
hdfs dfs -cat /user/hadoop/results/2026/sem1.csv
    Deleted /user/hadoop/results/2026/sem1.csv -rw-r--r-- 3 hadoop supergroup 25 2026-10-21 16:22 /user/hadoop/results/.snapshot/before_results/2026/sem1.csv roll,marks 101,78 102,91
    Even -skipTrash couldn't destroy the data: the snapshot still referenced the file's blocks. Restoring is a normal copy out of the read-only .snapshot view.

  3. What changed between two snapshots?

    printf '103,66\n' | hdfs dfs -appendToFile - /user/hadoop/results/2026/sem1.csv
hdfs dfs -createSnapshot /user/hadoop/results after_append
hdfs snapshotDiff /user/hadoop/results before_results after_append
    Difference between snapshot before_results and snapshot after_append under directory /user/hadoop/results: M ./2026 + ./2026/sem1.csv - ./2026/sem1.csv
    The folder was modified (M); the old sem1.csv was deleted (−) and a new one created (+), because our restore made a new file with the same name. DistCp uses exactly these diffs to copy only changes to a backup cluster.

  4. Snapshots protect themselves

    hdfs dfs -rm -r -skipTrash /user/hadoop/results/.snapshot/before_results
hdfs dfs -rm -r -skipTrash /user/hadoop/results
hdfs lsSnapshottableDir
    rm: Modification on a read-only snapshot is disallowed rm: The directory /user/hadoop/results cannot be deleted since /user/hadoop/results is snapshottable and already has snapshots drwxr-xr-x 0 hadoop supergroup 0 2026-10-21 16:22 2 65536 /user/hadoop/results
    Nobody can edit a snapshot, and a folder with snapshots can't be removed. lsSnapshottableDir shows 2 snapshots and the limit of 65,536. To free space, an admin must explicitly -deleteSnapshot.

  5. Name quota: count the folder too

    hdfs dfsadmin -setQuota 3 /user/hadoop/quota_lab/names
for i in 1 2 3; do echo x | hdfs dfs -put - /user/hadoop/quota_lab/names/f$i.txt; done
    put f1 ok put f2 ok put: The NameSpace quota (directories and files) of directory /user/hadoop/quota_lab/names is exceeded: quota=3 file count=4
    The folder itself is one of the 3 names, so only 2 files fit. Name quotas protect the NameNode's memory from tree explosions.

  6. Space quota: the 384 MB surprise

    hdfs dfsadmin -setSpaceQuota 10m /user/hadoop/quota_lab/space
echo x | hdfs dfs -put - /user/hadoop/quota_lab/space/tiny.txt
hdfs dfsadmin -setSpaceQuota 1g /user/hadoop/quota_lab/space
hdfs dfs -put /tmp/canteen_orders.csv /user/hadoop/quota_lab/space/
hdfs dfs -count -q -h -v /user/hadoop/quota_lab/names /user/hadoop/quota_lab/space
    put: The DiskSpace quota of /user/hadoop/quota_lab/space is exceeded: quota = 10485760 B = 10 MB but diskspace consumed = 402653184 B = 384 MB put ok QUOTA REM_QUOTA SPACE_QUOTA REM_SPACE_QUOTA DIR_COUNT FILE_COUNT CONTENT_SIZE PATHNAME 3 0 none inf 1 2 4 /user/hadoop/quota_lab/names none inf 1 G 1010.6 M 1 1 4.5 M /user/hadoop/quota_lab/space
    A 2-byte file failed a 10 MB quota: when a block is allocated, HDFS reserves a full block (128 MB) × replication (3) = 384 MB until the block is finished. With 1 GB, the 4.5 MB file fits and uses 13.4 MB of quota (3 replicas), leaving 1010.6 M.

  7. Trash: move, restore, expunge

    hdfs getconf -confKey fs.trash.interval
hdfs dfs -D fs.trash.interval=1440 -rm /user/hadoop/quota_lab/names/f1.txt
hdfs dfs -mv /user/hadoop/.Trash/Current/user/hadoop/quota_lab/names/f1.txt /user/hadoop/quota_lab/names/
hdfs dfs -D fs.trash.interval=1440 -rm /user/hadoop/quota_lab/names/f2.txt
hdfs dfs -D fs.trash.interval=1440 -expunge -immediate
    0 Moved: 'hdfs://namenode/user/hadoop/quota_lab/names/f1.txt' to trash at: hdfs://namenode/user/hadoop/.Trash/Current/user/hadoop/quota_lab/names/f1.txt -rw-r--r-- 3 hadoop supergroup 2 2026-10-21 16:22 /user/hadoop/quota_lab/names/f1.txt -rw-r--r-- 3 hadoop supergroup 2 2026-10-21 16:22 /user/hadoop/quota_lab/names/f2.txt Moved: 'hdfs://namenode/user/hadoop/quota_lab/names/f2.txt' to trash at: hdfs://namenode/user/hadoop/.Trash/Current/user/hadoop/quota_lab/names/f2.txt Created trash checkpoint: /user/hadoop/.Trash/261021162255 Deleted trash checkpoint: /user/hadoop/.Trash/261021162255
    With trash on, -rm is a rename into .Trash/Current, so restoring is another rename. -expunge rolls Current into a timestamped checkpoint (yyMMddHHmmss) and deletes expired checkpoints; -immediate deletes them now.
WARN> A snapshot of a busy folder can quietly keep terabytes alive: data deleted from the live folder still counts on disk while snapshots refer to it. Monitor snapshot counts and ages, and delete old snapshots on a schedule.
5 See it happen

How a snapshot keeps a deleted file alive

Six steps inside the NameNode: the live tree, a snapshot, a delete, and a restore.

Snapshots in the NameNode 6 steps
What you see
  1. The results folder holds sem1.csv.
  2. A snapshot is created in about a second.
  3. The file is deleted permanently, bypassing trash. The live folder is empty.
  4. The snapshot still lists the file.
  5. Copying it back restores the results.
  6. The snapshot itself can't be changed or deleted with rm.
Behind the screen
  1. The NameNode tree has sem1.csv pointing to block A, stored on three DataNodes.
  2. Creating a snapshot adds a marker. Nothing is copied.
  3. On delete, the NameNode moves the old entry into the snapshot's difference list, so block A is still referenced and not deleted.
  4. Reading under .snapshot shows the folder as it was.
  5. Restoring copies the data into a new file (block B). That is why snapshotDiff later showed − and + for sem1.csv.
  6. Block A stays on disk until the snapshot is deleted. Snapshots cost space only for data changed or deleted after them.
6 Real-world use

Protection at work

1. Scheduled snapshots of critical folders

Warehouse and results folders get a snapshot every night (named by date) from a scheduler, and a cleanup job deletes snapshots older than a week. Accidental deletes are fixed with a copy.

Nightly→createSnapshot + delete old→7 days of undo

2. Incremental copies to a DR cluster

DistCp can copy only the differences between two snapshots to a backup cluster, so daily DR copies of a 500 TB folder transfer just the day's changes (Module 12).

snapshot s1, s2→distcp -diff s1 s2→DR cluster

3. Quotas for every team

Shared clusters give each team's project folder a space quota and a name quota. A runaway job fails in its own folder instead of filling the cluster for everyone.

New project→setSpaceQuota + setQuota→Isolated growth

4. Trash on by default

Most production clusters set fs.trash.interval to a day or more in core-site.xml and discourage -skipTrash except for scripted cleanup of temporary data.

rm→.Trash/Current→mv back if needed

Simplified; organisations differ in tools and policies.
