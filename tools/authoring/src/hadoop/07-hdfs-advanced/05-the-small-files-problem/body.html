1 The story

Ten thousand files, three hundred kilobytes

The canteen billing app was changed to write one CSV file per order into HDFS. It looked tidy: o_1.csv, o_2.csv, … After one busy morning there are 10,000 files with only 339 KB of data between them. Uploading them took almost five minutes, reading them back took 15 seconds, and the cluster admin calls Riya: the NameNode just gained 20,000 new objects to keep in memory. The same data as one file uploads in 2 seconds and costs the NameNode 2 objects.

A> This is the famous small files problem. HDFS was designed for a few million large files. Every file, folder and block is an object in the NameNode's memory, and every file needs its own calls to the NameNode and its own pipeline to DataNodes. A 33-byte file costs the NameNode about as much as a 128 MB one. R> Then the data size doesn't matter at all? A> For the NameNode, hardly. For jobs, small files also mean one map task per file, so 10,000 tiny tasks that spend more time starting than working. Today we measure all of it, and then fix it: pack the files into a Hadoop Archive, and see why the real fix is to never write them in the first place.
2 Definition

The small files problem

Formal definition (write this in exams)

The small files problem refers to the degradation of HDFS and processing performance when data is stored as a large number of files significantly smaller than the HDFS block size. Because the NameNode keeps every file, directory and block as an object in memory (commonly estimated at roughly 150 bytes each), the number of files rather than the volume of data determines NameNode heap use, RPC load and the time for listings, block reports and restarts. Each small file also requires separate metadata operations and a separate block write and read, and frameworks typically create at least one input split (and task) per file, so job overhead grows with file count. Mitigations include writing larger files at the source, periodic compaction, container formats (SequenceFile, Avro, Parquet), Hadoop Archives (HAR), and input formats that combine files (CombineFileInputFormat).

In simple words

HDFS keeps a catalogue card for every file and block. Millions of tiny files mean millions of cards, endless trips to the catalogue, and thousands of tiny jobs, even if all the files together are small. Store fewer, bigger files.

LEVELS> Small files at three levels L1> A library that registers every page
  • Imagine a library that makes a catalogue card for every book. Fine. Now someone donates 10,000 single-page leaflets: 10,000 cards, 10,000 shelf slots.
  • The librarian's card box (NameNode memory) fills up, and finding anything takes longer, even though the leaflets together are thinner than one book.
  • Binding the leaflets into one volume (compaction or an archive) needs one card.
L2> Where the cost comes from
  • NameNode memory: each file + block ≈ 2 objects. Our 10,000 files added 20,000 objects; the big file added 2.
  • RPCs: each file needs create, addBlock, complete, plus a DataNode pipeline. That is why the upload took 281 s instead of 2 s, even in one JVM.
  • Reading: one getBlockLocations and one DataNode connection per file: 15.2 s vs 1.9 s.
  • Jobs: MapReduce and Spark create about one split per file. 10,000 files → about 10,000 tasks, each lasting milliseconds after seconds of start-up.
L3> How teams fix it
  • At the source: buffer and write larger files (e.g. a file per hour per partition, not per event); streaming sinks with sensible flush intervals.
  • Compaction jobs: Spark coalesce/repartition, Hive merge settings, or table-format commands (Delta OPTIMIZE, Iceberg rewrite_data_files) on a schedule.
  • Containers: SequenceFile or Avro with filename as key; Parquet tables instead of per-record files.
  • HAR: for archives that must keep file names but are rarely read. HAR files are immutable and add an index lookup on read.
  • Guardrails: name quotas (Lesson 7.4) on landing folders, monitoring of average file size per folder, and federation for unavoidable churn (Lesson 7.2).
/LEVELS EXAM> For “What is the small files problem in Hadoop and how do you solve it?”, give the two costs (NameNode memory, roughly 150 bytes per object; one map task per file), one number (e.g. 10,000 files vs 1 file), and three solutions: HAR, SequenceFile/combining, CombineFileInputFormat, plus “write bigger files at source”.

4 Step by step

Measuring and fixing small files

Run on the Module 5 lab cluster with small_files_lab.sh (in “Run it on your PC”).

  1. Create the same data two ways

    seq 1 10000 | while read i; do printf 'order_id,item,amount\n%d,chai,20\n' $i > o_$i.csv; done
cat /tmp/small/*.csv > /tmp/big.csv
    10000 40M /tmp/small 338894 bytes in big.csv
    Even the local disk wastes space: 339 KB of data occupy 40 MB because each tiny file takes a 4 KB block (Big Data Fundamentals, Lesson 2.3).

  2. Upload both and watch the NameNode

    hdfs dfs -put /tmp/small/*.csv /small/
hdfs dfs -put /tmp/big.csv /big/
curl -s 'http://localhost:9870/jmx?qry=Hadoop:service=NameNode,name=FSNamesystem'   # FilesTotal, BlocksTotal
    NameNode before : FilesTotal 41 BlocksTotal 31 put 10000 files: 281026 ms NameNode after small files: FilesTotal 10043 BlocksTotal 10031 put 1 file: 2133 ms
    4 minutes 41 seconds vs 2 seconds for the same bytes. The NameNode gained 10,002 files (10,000 + two folders) and 10,000 blocks. (Its JMX counters refresh with a delay, so they didn't show the single big file's +1 within our 6 s wait; fsck below confirms it.)

  3. Same bytes, very different object counts

    hdfs dfs -count -v /small /big
hdfs dfs -du -s /small /big
hdfs fsck /small ; hdfs fsck /big
    DIR_COUNT FILE_COUNT CONTENT_SIZE PATHNAME 1 10000 338894 /small 1 1 338894 /big 338894 1016682 /small 338894 1016682 /big Total blocks (validated): 10000 (avg. block size 33 B) Total blocks (validated): 1 (avg. block size 338894 B)
    Identical bytes on DataNode disks (HDFS blocks are only as big as their data, so no disk is wasted there). The difference is entirely in the NameNode: 10,000 blocks averaging 33 bytes.

  4. Read everything back

    hdfs dfs -cat '/small/*.csv' | wc -l
hdfs dfs -cat /big/big.csv | wc -l
    20000 read 10000 files: 15168 ms 20000 read 1 file: 1892 ms
    Same 20,000 lines. The small files needed 10,000 location lookups and 10,000 DataNode connections: 8 times slower, and that's with one client and no job framework.

  5. Fix: pack them into a Hadoop Archive

    hadoop archive -archiveName orders.har -p /small /archives
hdfs dfs -ls /archives/orders.har
hdfs dfs -count -v har:///archives/orders.har ; hdfs dfs -cat har:///archives/orders.har/o_42.csv
    archive job took 24 s -rw-r--r-- 3 hadoop supergroup 0 2026-10-21 16:39 /archives/orders.har/_SUCCESS -rw-r--r-- 3 hadoop supergroup 834555 2026-10-21 16:39 /archives/orders.har/_index -rw-r--r-- 3 hadoop supergroup 388 2026-10-21 16:39 /archives/orders.har/_masterindex -rw-r--r-- 3 hadoop supergroup 338894 2026-10-21 16:39 /archives/orders.har/part-0 1 10000 338894 har:///archives/orders.har order_id,item,amount 42,chai,20
    The archive job (a MapReduce job, here in local mode) packed all data into one part-0 file plus an index. Through har:// the 10,000 names still exist and can be read individually.

  6. Delete the originals and check the NameNode

    hdfs dfs -rm -r -skipTrash /small
    removed /small NameNode after HAR, without /small: FilesTotal 49 BlocksTotal 35
    From over 10,000 files and blocks back to 49 and 35: the archive costs the NameNode 4 files. The trade-off: archives are immutable, and each read first consults the index.
WARN> A compaction or archive job must finish and be verified before deleting the originals, and readers must be switched to the new location. Delete first and a failed job means lost data.
5 See it happen

What the NameNode does for each tiny file

Six steps comparing one small-file upload with one big-file upload, then the archive fix.

Objects and RPCs 6 steps
What you see
  1. 10,000 tiny files start uploading in one command.
  2. It takes 281 s, and the NameNode now tracks about 10,000 more files and blocks.
  3. The same bytes as one file: 2.1 s, one file, one block.
  4. Reading all small files takes 15.2 s; the big file 1.9 s.
  5. A Hadoop Archive packs the small files into a few files, still readable by name.
  6. With the originals removed, the NameNode is back to a few dozen objects.
Behind the screen
  1. Every small file needs create, addBlock and complete calls to the NameNode and its own write pipeline.
  2. Repeated 10,000 times: about 30,000 NameNode calls and 20,000 objects in its memory.
  3. One big file: the same three calls and two objects, then one efficient stream of bytes.
  4. Reading costs one location lookup and one DataNode connection per file.
  5. A HAR stores the file names in its own index file, so the NameNode only sees a few files.
  6. Removing the originals returns the NameNode to a small object count. (Squares are symbolic.)
6 Real-world use

Small files at work

1. Nightly compaction of streaming data

Streaming jobs write small files all day for freshness; a nightly Spark or table-format job rewrites yesterday's partitions into files of a few hundred MB.

Stream: many small files→Compaction job→Few large files

2. Monitoring average file size

Platform teams scan the namespace (from fsimage with the Offline Image Viewer, Lesson 5.4) to rank folders by file count and average size, and ask the owners of the worst offenders to fix their writers.

fsimage → oiv→Files per folder→Owners fix writers

3. Archiving old logs and documents

Years of small log or document files that must stay individually retrievable are packed into HAR archives (or containers) so they stop costing NameNode memory.

Old small files→hadoop archive→har:// access

4. IoT and per-event uploads redesigned

Systems that once wrote one file per sensor reading switch to a message queue (Kafka) and write hourly files per device group, cutting file counts by orders of magnitude.

Per-event files→Kafka + batching→Hourly files

Simplified; organisations differ in tools and policies.
