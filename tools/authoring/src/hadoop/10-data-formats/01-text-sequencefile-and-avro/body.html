1 The story

The day someone added a column

The canteen's 5 lakh orders live in HDFS as student_orders.csv. On Monday the billing team added a payment column at the end of each new line. On Tuesday Kabir's monthly report crashed: his job expected five fields and found six. Riya's Python script didn't crash, but it read "cash" as the amount. Nothing in a CSV file says what its columns are called or what type they have. Arjun Sir pulls up a different version of the same data.

A> A file format is a contract between whoever writes the data and everyone who will ever read it. CSV's contract is “some text with commas”. That is easy to read with your eyes, and that is all it promises. R> So binary formats are smaller, and they also remember the column names? A> Some of them. A SequenceFile stores binary keys and values and writes their Java classes in its header. An Avro file stores a full schema, field names and types, in its header, so a reader in Java, Python or anything else knows exactly what each record contains. And Avro has rules for changing that schema without breaking old files. K> Today we convert the same orders into all of these, compare the sizes, read them back with one job, and then add Monday's payment column the safe way.
2 Definition

Row-oriented file formats in Hadoop

Formal definition (write this in exams)

A file format defines how records are encoded into bytes in a file. In Hadoop it is read by an InputFormat and written by an OutputFormat. Text files (TextInputFormat) store one record per line as characters with no schema. A SequenceFile is Hadoop's flat binary file of key-value pairs: a header names the key and value classes (Writables) and the compression codec, records may be stored uncompressed, record-compressed or block-compressed, and periodic sync markers let a reader start in the middle of the file, making it splittable. Apache Avro is a language-neutral data serialization system: an Avro data file (object container file) stores its schema as JSON in the header, followed by blocks of compactly encoded binary records separated by sync markers, each block optionally compressed. Avro supports schema evolution: data written with one schema (the writer's schema) can be read with a different but compatible schema (the reader's schema). All three are row-oriented: the fields of one record are stored together.

In simple words

Text is human-readable but has no types. SequenceFile is Hadoop's own compact key-value box. Avro is a compact box that carries its own label (the schema), works in any language, and lets the label change over time without breaking old boxes.

LEVELS> File formats at three levels L1> Three ways to keep a register
  • Text is a notebook where each order is written as one line. Anyone can read it, but nothing says which number is the amount and which is the roll number.
  • SequenceFile is a register with two columns, key and value, printed in Hadoop's own shorthand. Compact, but you need Hadoop (or Java) to read it.
  • Avro is a register with the column headings printed on the first page, in a shorthand every language understands. When a new column is added, old pages still make sense.
L2> What the bytes look like
  • Text: numbers as characters (“45” is 2 bytes, “1000001” is 7), commas, a newline. Our CSV: about 39 bytes per order.
  • SequenceFile NONE: every record stores its record length and key length (4 + 4 bytes), the key as an 8-byte LongWritable, then the value as Text, plus a 20-byte sync entry about every 100 KB. That's why it was bigger than the CSV: 24.0 MB vs 19.4 MB.
  • SequenceFile RECORD: each value compressed on its own. A 30-byte value can't shrink, and each one pays the deflate overhead: 27.9 MB, the worst of all. BLOCK compresses many records together: 4.7 MB.
  • Avro: no field names or separators per record (the schema says what comes next), numbers as variable-length zig-zag integers, strings as length + bytes. Without compression already 16.6 MB, smaller than the CSV.
L3> Splitting, compression and evolution
  • Both binary formats put a 16-byte sync marker between blocks. A map task given bytes 128 MB–256 MB scans forward to the next marker and starts there, like LineRecordReader does with newlines (Lesson 8.2). So they stay splittable even when compressed, unlike a gzip'd CSV (Lesson 10.3).
  • Avro schema resolution matches fields by name: a field in the reader's schema but not in the file needs a default; a field in the file but not the reader's schema is skipped; renames use aliases; types can be promoted (int → long, float → double).
  • Compatibility is directional: backward = new readers can read old data (add fields with defaults); forward = old readers can read new data (remove only fields that had defaults). Kafka's Schema Registry enforces exactly these rules.
  • SequenceFile's types are Java class names, so other languages struggle with it. It is best for Hadoop-internal data: intermediate job output, or packing small files (Lesson 7.5).

Choosing

Exchanging data or expecting schema changes: Avro. Hadoop-only intermediate data: SequenceFile. Analytics on a few columns: Parquet or ORC (next lesson).

rule of thumb
TIP> Row formats are fast to write one record at a time, which is why streaming pipelines (Kafka → HDFS) usually land data as Avro. Analytical tables are then rewritten into columnar formats, which are faster to read when a query needs only a few columns. Lesson 10.2 measures that difference.
4 Step by step

Converting the orders and reading them back

We use the Module 8 lab cluster and Module 9's student_orders.csv. Hadoop ships the Avro core library but not avro-mapred (the Avro InputFormat and OutputFormat), so get_jars.sh downloads it from Maven Central, and formats_env.sh passes it to the job with -libjars.

  1. Write SequenceFiles three ways

    hadoop jar mr10.jar ToSequenceFile -libjars $LIBJARS -D seq.compress=NONE   $D /out/f_seq_none
hadoop jar mr10.jar ToSequenceFile -libjars $LIBJARS -D seq.compress=RECORD $D /out/f_seq_record
hadoop jar mr10.jar ToSequenceFile -libjars $LIBJARS -D seq.compress=BLOCK  $D /out/f_seq_block
    text 19418699 seq_none 24034722 seq_record 27878984 seq_block 4683378
    A map-only job turns each line into (order_id as LongWritable, rest of the line as Text). Uncompressed it grows by about 9 bytes per order (lengths, the 8-byte key). Compressing each tiny value separately makes it even bigger; compressing blocks of records shrinks it to a quarter of the CSV.

  2. Look at the first bytes

    hdfs dfs -cat /out/f_seq_block/part-m-00000 | head -c 150
    SEQ.!org.apache.hadoop.io.LongWritable.org.apache.hadoop.io.Text..*org.apache.hadoop.io.compress.DefaultCodec....P...........8`......P...........8`...
    The header: magic bytes SEQ, a version byte, the key class, the value class, the compression flags and codec, then a 16-byte sync marker. Any reader learns the types from the file itself.

  3. Write Avro three ways

    hadoop jar mr10.jar ToAvro -libjars $LIBJARS -D avro.codec=null    $D /out/f_avro_null
hadoop jar mr10.jar ToAvro -libjars $LIBJARS -D avro.codec=deflate $D /out/f_avro_deflate
hadoop jar mr10.jar ToAvro -libjars $LIBJARS -D avro.codec=snappy  $D /out/f_avro_snappy
    avro_null 16558165 avro_deflate 4793471 avro_snappy 7791915
    Even with no codec, Avro is smaller than the CSV: no commas, no field names per record, and numbers stored as variable-length integers. Deflate compresses better; snappy is faster but larger (Lesson 10.3).

  4. Read the binary files as text

    hdfs dfs -text /out/f_seq_block/part-m-00000 | head -2
hdfs dfs -text /out/f_avro_deflate/part-m-00000.avro | head -2
java -jar lib/avro-tools-1.11.5.jar getmeta orders.avro
    1 S1413,2026-09-14 15:30,dosa,45 2 S0973,2026-09-26 20:11,samosa,18 {"order_id":1,"student":"S1413","time":"2026-09-14 15:30","item":"dosa","amount":45} {"order_id":2,"student":"S0973","time":"2026-09-26 20:11","item":"samosa","amount":18} avro.schema {"type":"record","name":"Order","namespace":"in.myphatshala","fields":[{"name":"order_id","type":"long"},… avro.codec deflate
    -text (unlike -cat) recognises SequenceFiles and Avro files and decodes them. The Avro file's metadata holds the whole schema and the codec name.

  5. Add Monday's column the safe way

    {"name":"payment","type":"string","default":"cash"}
    {"order_id":432369,"student":"S0454","time":"2026-09-20 12:05","item":"chai","amount":15,"payment":"cash"} {"order_id":432370,"student":"S1436","time":"2026-09-18 18:50","item":"chai","amount":15,"payment":"cash"} -- and a new field WITHOUT a default: AvroTypeException: Found in.myphatshala.Order, expecting in.myphatshala.Order, missing required field payment
    The old file was written without payment. Reading it with the new schema, Avro fills the default. Without a default there is no value to fill, so Avro refuses instead of guessing, a loud failure rather than Riya's silent one.

  6. Read all three with the same job

    hadoop jar mr10.jar ItemCountAny -libjars $LIBJARS -D in.format=text $D /out/r_text
hadoop jar mr10.jar ItemCountAny -libjars $LIBJARS -D in.format=seq  /out/f_seq_block /out/r_seq
hadoop jar mr10.jar ItemCountAny -libjars $LIBJARS -D in.format=avro /out/f_avro_deflate /out/r_avro
    text 25221 ms HDFS bytes read 19427239 map input records 500000 chai=149669 seq_block 25073 ms HDFS bytes read 4683705 map input records 500000 chai=149669 avro_deflate 25813 ms HDFS bytes read 4818410 map input records 500000 chai=149669
    Same answer, a quarter of the bytes read from HDFS. The times are equal here because 19 MB is tiny and job start-up dominates; on terabytes, reading 4× fewer bytes is the difference that matters, paid for with CPU to decompress.
WARN> Don't use RECORD compression for small records: our SequenceFile grew from 24.0 MB to 27.9 MB. Use BLOCK compression (or Avro with a codec), which compresses many records together.
5 See it happen

One order, three encodings

Six steps: the same order as text, as a SequenceFile record, compressed record by record and in blocks, as Avro, and read with a newer schema.

Inside the files 6 steps
What you see
  1. The CSV: 19.4 MB, one readable line per order.
  2. The uncompressed SequenceFile is larger than the CSV: 24.0 MB.
  3. Compressing record by record makes it worse (27.9 MB); compressing blocks gives 4.7 MB.
  4. Avro without a codec is already smaller than the CSV; deflate brings it to 4.8 MB.
  5. An old file read with a new schema: the default fills the gap; with no default, Avro refuses.
  6. One job reads all three formats and gets the same answer from a quarter of the bytes.
Behind the screen
  1. CSV stores everything as characters with commas in between; types are a guess.
  2. A SequenceFile record adds a record length, a key length and an 8-byte key; a sync marker follows about every 100 KB.
  3. RECORD compression deflates each tiny value alone; BLOCK compression deflates many records together.
  4. Avro writes the schema once in the header, then bare values: small numbers become single bytes.
  5. When reading, Avro matches the file's fields to yours by name and fills defaults for new ones.
  6. The binary formats let the same job read about a quarter of the bytes.
6 Real-world use

Row formats at work

1. Event streams with a schema registry

Payment, order and click events are published to Kafka as Avro, with schemas stored in a schema registry that rejects incompatible changes. Connectors then land them in HDFS or a data lake as Avro files.

App events→Kafka + Avro schema→HDFS landing zone

2. Packing small files

Images, PDFs or tiny logs are packed into SequenceFiles with the file name as key and the bytes as value, so the NameNode tracks one file instead of thousands (Lesson 7.5).

Small files→(name, bytes) records→One splittable file

3. Data between chained jobs

When one MapReduce job feeds another, the middle data is written as block-compressed SequenceFiles: binary Writables need no parsing, and Hive, Pig and Mahout used them this way.

Job 1→SequenceFile (BLOCK)→Job 2

4. Raw zone, then curated tables

Data lakes keep the raw, append-only zone in Avro (fast writes, full records, schema history), then nightly jobs rewrite it into Parquet or ORC tables for analysts (Lesson 10.2).

Raw (Avro)→nightly rewrite→Curated (Parquet/ORC)

Simplified; organisations differ in tools and policies.
