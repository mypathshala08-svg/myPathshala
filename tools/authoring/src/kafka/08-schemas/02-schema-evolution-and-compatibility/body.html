2 Definition

Schema evolution and compatibility

Formal definition (write this in exams)

Schema evolution is changing a schema over time while existing data and programs keep working. A registry compatibility mode defines the allowed relation between versions: BACKWARD (consumers using the new schema can read data written with the previous one), FORWARD (consumers using the previous schema can read data written with the new one), FULL (both), each optionally TRANSITIVE (against all earlier versions), or NONE. Avro achieves this by resolving writer and reader schemas by field name, using reader defaults for missing fields.

In simple words

Every change to a message shape must still let old and new programs read each other’s messages. Adding a field with a default value is almost always safe; renaming or changing a type is not.

Why, how, where

Why

Topics keep old messages for days or forever (compaction), and producers and consumers upgrade at different times. Every new schema must be readable alongside the old ones, or someone breaks.

the problem it solves

How

Avro decodes with two schemas: the writer schema (by id in the message) and the consumer’s reader schema. Fields are matched by name: missing fields in the data take the reader’s default; extra fields are skipped. The registry simulates this for every new version and refuses (409) incompatible ones.

the mechanism

Where

Every long-lived topic with more than one team; CDC topics when tables change; event-sourced systems that replay history.

in real systems

When not

BACKWARD (default) only checks against the previous version; use *_TRANSITIVE if consumers may read very old data. Renames are never safe without aliases; changing meaning (price in rupees → paise) is “compatible” but still breaks people.

The matrix at a glance

LEVELS> Compatibility at three levels L1> Old and new phone apps
  • BACKWARD: the new app can open files saved by the old app. FORWARD: the old app can open files saved by the new app (it ignores what it doesn’t understand). FULL: both. Upgrade order follows from that.
L2> The modes
  • BACKWARD (default): new schema reads data of the previous one. Allowed: delete fields, add fields with defaults. Upgrade consumers first.
  • FORWARD: previous schema reads data of the new one. Allowed: add fields, delete fields that had defaults. Upgrade producers first.
  • FULL: both directions: only add/delete fields that have defaults. Any order. NONE: no checks. *_TRANSITIVE: checked against all earlier versions, not just the last.
L3> Details that bite
  • Avro type promotion: int → long/float/double, long → float/double, float → double, string ↔ bytes. So a reader can widen (BACKWARD OK) but an old int reader cannot read long data (FORWARD fails), as our matrix shows.
  • Renames break by-name matching; Avro aliases on the reader field can map an old name. Unions with null first and default null are the usual way to make optional fields.
  • Protobuf: fields are matched by number; never reuse or change a number, use reserved. JSON Schema: compatibility depends on open/closed content models (additionalProperties).
  • Big breaking changes: create a new topic (orders-v2), dual-write or migrate with a stream job, then retire the old topic.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Adding a field is always safe.
    Reality (Kafka 4.4): Not without a default under BACKWARD.
    Proof: Step 1: 409.
  • Myth: Widening int → long is safe everywhere.
    Reality (Kafka 4.4): Old int readers fail: FORWARD no.
    Proof: Matrix.
  • Myth: Compatible means meaning is unchanged.
    Reality (Kafka 4.4): Registry checks types, not semantics.
    Proof: Scenario 3.
EXAM> “Explain schema compatibility.” BACKWARD: new reader reads old data (add with default, delete), consumers first; FORWARD: old reader reads new (add, delete with default), producers first; FULL both; TRANSITIVE all versions; renames/type changes break; Avro resolves by name with defaults.

Test the rules

All outputs are real: Confluent Schema Registry 8.1.0 REST API and fastavro schema resolution.

  1. Step 1 · The 409

    curl -X POST localhost:8081/subjects/menu-82-value/versions \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" -d '{"schema": "<v1 + city:string>"}'

    Under BACKWARD, a new reader would find no city in old data and has no default: error READER_FIELD_MISSING_DEFAULT_VALUE.

  2. Step 2 · With a default

    {"name": "spicy", "type": "boolean", "default": false}
    == 2) the same subject, a v2 WITH a default: accepted HTTP 200 {'id': 6, 'version': 2, 'schemaType': 'AVRO'} -> versions [1, 2]
    Accepted as version 2 of the subject (with a new global id).

  3. Step 3 · Six changes × four modes

    PUT  /config/{subject}   {"compatibility": "FORWARD"}
POST /compatibility/subjects/{subject}/versions/latest?verbose=true
    == 3) compatibility matrix: each change checked against v1 in each mode (Y = allowed) change BACKWARD FORWARD FULL NONE add field WITH default (spicy=false) Y Y Y Y add field WITHOUT default (city) - Y - Y delete field price (no default) Y - - Y rename qty -> quantity - - - Y widen qty int -> long Y - - Y change price double -> string - - - Y
    Only adding a field with a default passes everywhere. Deleting a field or widening int → long is fine for new readers (BACKWARD) but breaks old readers (FORWARD). Renames and real type changes fail in every checked mode.

  4. Step 4 · Why, on real bytes

    fastavro.schemaless_reader(io.BytesIO(data), writer_schema, reader_schema)
    == 4) why: old and new readers on real Avro bytes (fastavro schema resolution) new reader (v2) on old data (v1): {'id': 1, 'item': 'idli', 'qty': 2, 'price': 40.0, 'spicy': False} <- default filled: BACKWARD old reader (v1) on new data (v2): {'id': 9, 'item': 'vada', 'qty': 3, 'price': 60.0} <- extra field ignored: FORWARD reader without default on old data: SchemaResolutionError No default value for field city in in.tiffingo.Order
    New reader on old data: spicy filled with False. Old reader on new data: spicy skipped. A reader with a field without default fails with SchemaResolutionError: the exact reason for the 409.

  5. Step 5 · Other formats

    POST /subjects/riders-82-value/versions {"schemaType": "PROTOBUF", "schema": "syntax = \"proto3\"; ..."}
    == 5) other formats: Protobuf and JSON Schema in the same registry riders-82-value PROTOBUF -> id 7 zones-82-value JSON -> id 8 GET /schemas/types -> ['JSON', 'PROTOBUF', 'AVRO']
    The same registry stores Protobuf and JSON Schema with their own compatibility rules.
