2 Definition

Kafka architecture

Formal definition (write this in exams)

A Kafka cluster consists of brokers that store topic partitions as replicated logs, and a controller quorum that manages cluster metadata using the KRaft protocol (Raft-based consensus, mandatory since Kafka 4.0). Each partition has a replication factor; one replica is the leader, serving produce and fetch requests, and the others are followers that replicate from it. Clients (producers, consumers, admin tools, Connect, Streams) discover leaders through the Metadata API and communicate with brokers over a versioned binary protocol on TCP.

In simple words

Kafka is a team of servers. Each partition is copied to several servers; one copy is in charge and the rest follow. A small built-in committee keeps track of who is in charge and replaces a failed leader automatically.

Why, how, where

Why

One server can fail or fill up. A cluster spreads partitions and keeps copies so no single machine matters.

the problem it solves

How

Brokers store partition replicas; one replica leads, others follow. A Raft quorum of controllers stores the cluster metadata and moves leadership on failure.

the mechanism

Where

Every Kafka deployment: on-premise, Kubernetes, and managed services such as Amazon MSK or Confluent Cloud.

in real systems

When not

A single broker is fine for learning, never for production: no copies, no failover.

Zoom in, layer by layer

Dissect a broker’s disk

LEVELS> Architecture at three levels L1> A dabbawala network
  • Three stations (brokers) each keep a copy of every route book (partition). For each route one station is in charge (leader); the others copy its updates (followers).
  • A small committee (controllers) decides who is in charge. If a station closes, the committee picks another one at once.
L2> The parts
  • Broker: a server that stores partition replicas and serves clients. Cluster: brokers sharing one cluster.id.
  • Leader replica handles all reads and writes of a partition; followers fetch from it. Copies that are up to date form the ISR (in-sync replicas).
  • Controllers (KRaft) keep the metadata: topics, partitions, leaders, configs. In our lab each node is broker and controller (“combined mode”).
L3> Under the hood
  • Metadata is itself a replicated log, __cluster_metadata, managed with the Raft consensus algorithm; one controller is the active leader (our lab: node 3, epoch 2).
  • Consumer offsets live in the internal topic __consumer_offsets (50 partitions by default); share-group state in __share_group_state.
  • Clients talk to brokers over a binary TCP protocol with versioned APIs (Produce, Fetch, Metadata …).
/LEVELS

Myth vs reality: things many websites still say

  • Myth: ZooKeeper stores offsets and elects leaders.
    Reality (Kafka 4.4): Offsets live in __consumer_offsets; KRaft controllers elect leaders.
    Proof: Step 1 (quorum) and Step 3 (internal topics).
  • Myth: Brokers are stateless.
    Reality (Kafka 4.4): Brokers store partition data on disk; only metadata is handled by controllers.
    Proof: Step 4: 117 partition folders on one broker.
  • Myth: Producers ask ZooKeeper for broker IDs.
    Reality (Kafka 4.4): Clients get metadata from any broker via the Metadata API.
    Proof: the “find the leader” peel animation below.
EXAM> “Explain Kafka architecture.” Brokers form a cluster and store partitions; each partition is replicated (RF) with one leader and followers; the ISR is the set of caught-up replicas. Since 4.0, KRaft controllers (a Raft quorum) store metadata in __cluster_metadata and handle leader election, replacing ZooKeeper. Clients bootstrap, fetch metadata, then talk directly to partition leaders.

    docker stop k1

    == 8) stop broker 1 (docker stop k1) Topic: order-events Partition: 0 Leader: 2 Replicas: 2,3,1 Isr: 2,3 Topic: order-events Partition: 1 Leader: 3 Replicas: 3,1,2 Isr: 3,2 Topic: order-events Partition: 2 Leader: 2 Replicas: 1,2,3 Isr: 2,3 -- produce + read still works: order-events:0:3 order-events:1:1 order-events:2:3
    Partition 2 lost its leader (broker 1). Within seconds broker 2 became leader and the ISR shrank to 2,3. A new order was still accepted: partition 0 grew from 2 to 3 events.

  6. Step 6 · Bring it back

    docker start k1
kafka-topics.sh --bootstrap-server k2:9092 --describe --topic order-events
    == 9) start broker 1 again Topic: order-events Partition: 0 Leader: 2 Replicas: 2,3,1 Isr: 1,2,3 Topic: order-events Partition: 1 Leader: 3 Replicas: 3,1,2 Isr: 1,2,3 Topic: order-events Partition: 2 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3
    Broker 1 caught up and rejoined the ISR (1,2,3), then took back leadership of partition 2: Kafka prefers the first replica in the list (“preferred leader”) to keep load balanced.

6 Real-world use

Architecture choices in practice

1. Managed clusters

Cloud services run brokers and controllers for you; you choose brokers and storage (Lesson 11.1).

You→managed Kafka→Topics

2. Kafka on Kubernetes

Operators such as Strimzi run brokers and controllers as pods with rolling upgrades.

YAML→operator→Cluster

3. Multi-zone clusters

Replicas spread across availability zones (rack awareness) so a zone outage loses no data.

3 zones→rack-aware→Survives zone

4. Rolling upgrades

Brokers are restarted one at a time; ISR checks gate each step.

Broker 1→ISR full?→Next broker

5. Disaster recovery

A second cluster in another region receives a copy via MirrorMaker 2 (Lesson 10.4).

Primary→mirror→DR site
