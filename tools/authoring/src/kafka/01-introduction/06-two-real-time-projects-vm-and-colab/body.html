2 Definition

A real-time pipeline

Formal definition (write this in exams)

A real-time (streaming) pipeline processes events continuously as they arrive rather than in periodic batches. In Kafka it is composed of producers that publish events to topics, stream processors (consumers that transform, aggregate or filter events and may publish results to further topics), and sinks that act on the results. Each stage is an independent consumer group, so stages scale, fail and evolve independently, and intermediate topics decouple them.

In simple words

Events flow through small programs connected by topics. Each program reads one topic, does one job and, if needed, writes to the next topic. You can add, restart or change one program without touching the others.

The two projects

LEVELS> The projects at three levels L1> Just run them
  • Open the Colab notebook, press Run all, and watch both projects print results.
L2> Understand the moving parts
  • Project 1: one topic, one producer, one consumer group that keeps state (running totals) in memory.
  • Project 2: two topics chained by a service that is both a consumer and a producer. The SMS notifier depends only on the fraud-alerts topic, not on the detector’s code.
L3> What would change in production
  • In-memory state is lost on restart; Kafka Streams keeps state in fault-tolerant stores (Lesson 9.2).
  • Detector writes and offset commits are separate; a crash can duplicate an alert. Transactions make read-process-write exactly-once (Lesson 3.5).
  • Rules need tuning: in our run a genuine user with 5 small payments in a minute was also flagged.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: You need Docker or a big server to learn Kafka.
    Reality (Kafka 4.4): Kafka runs on any machine with Java 17+; even free Colab works.
    Proof: the notebook ran end to end; Kafka started in about 15 seconds.
  • Myth: Kafka itself detects fraud or computes totals.
    Reality (Kafka 4.4): Kafka stores and moves events; your consumers (or Kafka Streams) compute.
    Proof: p2_fraud_detector.py holds the rules.
  • Myth: A pipeline means one big program.
    Reality (Kafka 4.4): Small services connected by topics, each in its own consumer group.
    Proof: the notifier only reads fraud-alerts.
EXAM> “Design a real-time alert system with Kafka.” Producers publish raw events keyed by entity; a processor group consumes, applies rules (often with windowed state) and publishes alerts to a separate topic; notification services consume alerts. Discuss partitioning by key, lag monitoring, state recovery and duplicate handling (idempotence/transactions).

  4. Step 4 · Project 1: the producer

    """Project 1 · TiffinGo live order tracker: producer. Sends one order every 0.2 s."""
import json, random, time, sys
from confluent_kafka import Producer
random.seed(7)
N = int(sys.argv[1]) if len(sys.argv) > 1 else 50
p = Producer({"bootstrap.servers": "localhost:9092", "partitioner": "murmur2_random"})
cities = ["Mumbai", "Pune", "Delhi", "Bengaluru"]
for i in range(1, N + 1):
    order = {"order_id": f"o{i:04d}", "city": random.choice(cities),
             "amount": random.choice([120, 180, 250, 320, 480, 1500]), "ts": time.time()}
    p.produce("orders", key=order["city"], value=json.dumps(order))
    p.poll(0)
    time.sleep(0.2)
p.flush()
print(f"sent {N} orders")
    sent 50 orders
    Each order is JSON with a key = city. partitioner: murmur2_random makes Python place keys exactly like Java clients (Lesson 1.4). poll(0) serves delivery callbacks; flush() waits until all are sent.

  5. Step 5 · Project 1: the live dashboard

    """Project 1 · TiffinGo live order tracker: consumer. Running revenue per city + big-order alert."""
import json, time
from collections import defaultdict
from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers": "localhost:9092", "group.id": "live-dashboard", "auto.offset.reset": "earliest"})
c.subscribe(["orders"])
revenue, count, seen, idle = defaultdict(int), defaultdict(int), 0, 0
while idle < 10:                                   # stop after 10 s with no data (demo)
    m = c.poll(1.0)
    if m is None or m.error():
        idle += 1; continue
    idle = 0
    o = json.loads(m.value()); seen += 1
    revenue[o["city"]] += o["amount"]; count[o["city"]] += 1
    if o["amount"] >= 1000:
        print(f"  ALERT big order {o['order_id']} {o['city']} Rs {o['amount']} (partition {m.partition()}, offset {m.offset()})")
    if seen % 10 == 0:
        board = "  ".join(f"{k}: {count[k]} / Rs {revenue[k]}" for k in sorted(revenue))
        print(f"[{seen:3} orders] {board}")
c.close()

  7. Step 7 · Project 2: payments and the fraud detector

    """Project 2 · UPI fraud alert: reads payments, applies 2 rules, writes alerts to another topic."""
import json, time
from collections import defaultdict, deque
from confluent_kafka import Consumer, Producer
c = Consumer({"bootstrap.servers": "localhost:9092", "group.id": "fraud-detector", "auto.offset.reset": "earliest"})
p = Producer({"bootstrap.servers": "localhost:9092"})
c.subscribe(["payments"])
recent = defaultdict(deque)                          # vpa -> timestamps in the last 60 s
checked, alerts, idle = 0, 0, 0
while idle < 8:
    m = c.poll(1.0)
    if m is None or m.error():
        idle += 1; continue
    idle = 0; checked += 1
    t = json.loads(m.value()); q = recent[t["vpa"]]
    q.append(t["ts"])
    while q and t["ts"] - q[0] > 60: q.popleft()
    reason = "amount over Rs 50,000" if t["amount"] > 50000 else ("more than 4 payments in 60 s" if len(q) > 4 else None)
    if reason:
        alerts += 1
        p.produce("fraud-alerts", key=t["vpa"], value=json.dumps({**t, "reason": reason}))
        print(f"  FLAG {t['txn']} {t['vpa']} Rs {t['amount']}: {reason}")
p.flush(); c.close()
print(f"checked {checked} payments, raised {alerts} alerts")
    $ python p2_fraud_detector.py FLAG t034 user9@upi Rs 4999: more than 4 payments in 60 s FLAG t035 user9@upi Rs 4999: more than 4 payments in 60 s FLAG t016 user1@upi Rs 50: more than 4 payments in 60 s FLAG t021 user1@upi Rs 50: more than 4 payments in 60 s FLAG t045 user3@upi Rs 75000: amount over Rs 50,000 FLAG t051 user3@upi Rs 120: more than 4 payments in 60 s checked 60 payments, raised 6 alerts
    The detector keeps, per UPI id, the timestamps of the last 60 seconds (a sliding window) and checks two rules. Flagged payments are produced to fraud-alerts: this program is a consumer and a producer. user9’s burst and user3’s Rs 75,000 payment were caught; user1 was also flagged for 5 small payments in a minute, a false positive you would tune.

  8. Step 8 · Project 2: the notifier

    """Project 2 · UPI fraud alert: a second service that reads the alerts topic and 'sends SMS'."""
import json
from confluent_kafka import Consumer
c = Consumer({"bootstrap.servers": "localhost:9092", "group.id": "sms-notifier", "auto.offset.reset": "earliest"})
c.subscribe(["fraud-alerts"]); idle = 0
while idle < 6:
    m = c.poll(1.0)
    if m is None or m.error():
        idle += 1; continue
    idle = 0; a = json.loads(m.value())
    print(f"  SMS to {a['vpa']}: payment {a['txn']} of Rs {a['amount']} held for review ({a['reason']})")
c.close()
