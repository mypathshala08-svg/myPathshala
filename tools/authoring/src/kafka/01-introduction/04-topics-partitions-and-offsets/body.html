2 Definition

Topics, partitions and offsets

Formal definition (write this in exams)

A topic is a named, logical stream of records divided into one or more partitions. Each partition is an ordered, immutable, append-only sequence of records, and each record in it is identified by a monotonically increasing 64-bit offset. Ordering is guaranteed only within a partition. The producer’s partitioner chooses the partition: for keyed records the default (Java) partitioner computes toPositive(murmur2(key)) % numPartitions; records with the same key therefore go to the same partition as long as the partition count is unchanged. Partitions are the unit of parallelism, replication and storage.

In simple words

A topic is split into partitions; each partition is a numbered list that only grows. The key decides which list an event joins, so events with the same key stay in order. Offsets are the numbers in each list.

Why, how, where

Why

One log on one machine cannot grow forever or be read by many workers at once. Partitions split a topic so it scales.

the problem it solves

How

The producer hashes the key (murmur2) and takes it modulo the partition count; the leader appends and assigns the next offset.

the mechanism

Where

Order IDs, user IDs, device IDs as keys; partitions as the unit of parallelism and of ordering.

in real systems

When not

Do not expect order across partitions, and do not change partition count of keyed topics casually.

Dissect the partition formula

LEVELS> Partitions and offsets at three levels L1> Railway platforms
  • A topic is a station; partitions are its platforms. Every train for “Mumbai” always uses the same platform, so Mumbai trains leave in order.
  • An offset is a train’s serial number on its platform: 0, 1, 2 … Numbers on different platforms are unrelated.
L2> The rules
  • Offsets are per partition, start at 0 and only grow; they are never reused.
  • Order is guaranteed within a partition only. Consumers can start from the beginning, the end, or any offset.
  • With a key, the default partitioner uses murmur2(key) % partitions (Java client). Without a key, records are spread in “sticky” batches.
L3> Sharp edges
  • Adding partitions changes % n, so existing keys can move (Mumbai: 1 → 4), breaking per-key order across the change. Partitions can never be reduced.
  • Different client libraries can use different default partitioners: librdkafka’s default (consistent_random, CRC32) differs from Java’s murmur2, so set partitioner=murmur2_random when Python and Java produce to the same keyed topic.
  • Few or skewed keys create hot partitions that limit throughput.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Without a key, Kafka picks a random partition for every message.
    Reality (Kafka 4.4): Since Kafka 2.4 the producer uses sticky partitioning: it fills a batch for one partition, then switches.
    Proof: keyless sends are covered with real batches in Lesson 2.2.
  • Myth: Kafka keeps the whole topic in order.
    Reality (Kafka 4.4): Order is guaranteed only within a partition.
    Proof: Step 2: offsets restart at 0 in every partition.
  • Myth: You can reduce partitions later.
    Reality (Kafka 4.4): Partitions can only be increased.
    Proof: Step 6: InvalidPartitionsException.
EXAM> “How does Kafka decide the partition and guarantee order?” Keyed records: hash(key) % partitions (murmur2 in the Java client), so same key → same partition → ordered by offset. No key: sticky/round-robin spreading. Order holds only within a partition, and increasing partitions remaps keys.

4 Step by step

Keys, offsets, seek, and the remap

All outputs are real: Kafka 4.4.0, 3 brokers, Java console tools (default murmur2 partitioner). Hash check: lab jobs/m1/murmur2.py.

  1. Step 1 · Create and produce keyed orders

    kafka-topics.sh --bootstrap-server k1:9092 --create --topic city-orders --partitions 3 --replication-factor 3
printf 'Mumbai:o1\nPune:o2\nDelhi:o3\n...' | kafka-console-producer.sh --bootstrap-server k1:9092 \
  --topic city-orders --reader-property parse.key=true --reader-property key.separator=:
    == 1) create topic city-orders with 3 partitions Created topic city-orders. == 2) produce 10 keyed orders (key = city)
    Ten orders, keys = city. The console producer splits each line at “:” into key and value.

  2. Step 2 · See partition and offset of every event

    kafka-console-consumer.sh --bootstrap-server k1:9092 --topic city-orders --from-beginning \
  --formatter-property print.key=true --formatter-property print.partition=true --formatter-property print.offset=true
    == 3) read back with partition and offset Partition:0 Offset:0 Pune o2 Partition:0 Offset:1 Delhi o3 Partition:0 Offset:2 Chennai o5 Partition:0 Offset:3 Pune o6 Partition:0 Offset:4 Delhi o8 Partition:0 Offset:5 Chennai o9 Partition:1 Offset:0 Mumbai o1 Partition:1 Offset:1 Mumbai o4 Partition:1 Offset:2 Mumbai o7 Partition:1 Offset:3 Mumbai o10
    Mumbai’s 4 orders are partition 1, offsets 0–3, in the order sent. Pune, Delhi and Chennai share partition 0. Partition 2 is empty: a hot/cold split caused by only 4 keys.

  3. Step 3 · Prove the hash by hand

    def partition(key, n):
    return (murmur2(key.encode()) & 0x7fffffff) % n
for city in ["Mumbai", "Pune", "Delhi", "Chennai"]: ...
    Mumbai murmur2=2542653612 3 partitions -> 1 6 partitions -> 4 Pune murmur2=1038389049 3 partitions -> 0 6 partitions -> 3 Delhi murmur2= 913835919 3 partitions -> 0 6 partitions -> 3 Chennai murmur2= 532687110 3 partitions -> 0 6 partitions -> 0
    Our 20-line murmur2 gives exactly the broker’s choices: Mumbai → 1, the others → 0. Nothing magic: just a hash and a modulo.

  4. Step 4 · End offsets and seeking

    kafka-get-offsets.sh --bootstrap-server k1:9092 --topic city-orders
kafka-console-consumer.sh --bootstrap-server k1:9092 --topic city-orders --partition 1 --offset 2 ...
    == 4) end offsets per partition city-orders:0:6 city-orders:1:4 city-orders:2:0 == 5) read only partition 1 starting at offset 2 Offset:2 Mumbai o7 Offset:3 Mumbai o10
    city-orders:0:6 means partition 0’s next offset is 6. Reading partition 1 from offset 2 returns exactly o7 and o10: you can replay any slice.

  5. Step 5 · Add partitions: the key moves

    kafka-topics.sh --bootstrap-server k1:9092 --alter --topic city-orders --partitions 6
echo "Mumbai:o11" | kafka-console-producer.sh ...
    == 6) add partitions 3 -> 6, same key may move Partition:4 Mumbai o11 Partition:1 Mumbai o1 Partition:1 Mumbai o4 Partition:1 Mumbai o7 Partition:1 Mumbai o10
    The new Mumbai order went to partition 4, exactly as murmur2 % 6 predicted, while older Mumbai orders remain in partition 1. Per-key ordering is broken across the change.

  6. Step 6 · You can never reduce partitions

    kafka-topics.sh --bootstrap-server k1:9092 --alter --topic city-orders --partitions 2
    == 7) partitions can never be reduced Error while executing topic command : The topic city-orders currently has 6 partition(s); 2 would not be an increase. [2026-11-05 11:36:33,656] ERROR org.apache.kafka.common.errors.InvalidPartitionsException: The topic city-orders currently has 6 partition(s); 2 would not be an increase.
    InvalidPartitionsException: partitions only grow. To shrink you create a new topic and copy data. Choose the count carefully up front (Lesson 10.2).

6 Real-world use

Keys in practice

1. Account transactions

Key = account id keeps each account’s debits and credits in order.

Txn→key account→Ordered ledger

2. Trip updates

Key = trip id keeps location and status updates of one trip in order.

GPS→key trip→Live map

3. Device telemetry

Key = device id; millions of devices spread evenly.

Sensors→key device→Even load

4. Shopping carts

Key = user id so add/remove events apply in order.

Clicks→key user→Cart state

5. Application logs

No key: best spread, order not needed.

Logs→sticky→Search
