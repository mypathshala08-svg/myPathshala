2 Definition

Installing Kafka and the CLI tools

Formal definition (write this in exams)

Apache Kafka is distributed as a Java binary archive and as the official apache/kafka container image. A node is configured through server.properties (or KAFKA_* environment variables in the image): process.roles, node.id, controller.quorum.voters, listeners, advertised.listeners and log.dirs. Storage must be formatted with a cluster ID before first start (the image does this automatically). The distribution includes command-line tools in bin/, built on the Admin, Producer and Consumer APIs, for managing topics and configurations, producing and consuming, inspecting groups and logs, and benchmarking.

In simple words

Run the official Docker image to get a working Kafka node. Use the scripts in its bin folder to create topics, change settings, and send and read events.

Dissect the tool box

LEVELS> Installing Kafka at three levels L1> Just run it
  • Install Docker Desktop, run one command, and you have Kafka. Stop it with docker stop kafka.
L2> What the image sets up
  • process.roles=broker,controller, node.id=1, one controller voter, listeners on 9092 (clients) and 9093 (controller).
  • log.dirs=/tmp/kraft-combined-logs inside the container: data disappears with the container unless you mount a volume.
  • num.partitions=1, log.retention.hours=168 (7 days) as defaults for new topics.
L3> Beyond one node
  • For a 3-node lab set KAFKA_* environment variables (node id, controller voters, advertised listeners) per container, like our start_cluster.sh.
  • advertised.listeners must be an address clients can reach; most “cannot connect” problems come from this.
  • Without Docker: download the binary from kafka.apache.org (Java 17+), run kafka-storage.sh format, then kafka-server-start.sh.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Start ZooKeeper first, then Kafka.
    Reality (Kafka 4.4): Kafka 4.x has no ZooKeeper; one KRaft node starts alone.
    Proof: Step 1: the node elects itself controller.
  • Myth: Use --zookeeper localhost:2181 with kafka-topics.
    Reality (Kafka 4.4): Every tool uses --bootstrap-server.
    Proof: all commands in this lesson.
  • Myth: The Docker defaults are fine for production.
    Reality (Kafka 4.4): RF 1 and data in /tmp are for learning only.
    Proof: Step 2: the default server.properties.
EXAM> “How do you create a topic and check it?” kafka-topics.sh --bootstrap-server host:9092 --create --topic t --partitions 3 --replication-factor 3, then --describe to see partitions, leaders, replicas and ISR. Replication factor cannot exceed the number of brokers.

4 Step by step

Start, explore, use, break

All outputs are real: Docker, image apache/kafka:4.4.0, container solo. Commands are run with docker exec solo /opt/kafka/bin/…; we show the script names only.

  1. Step 1 · Start Kafka

    docker run -d --name solo -p 9092:9092 apache/kafka:4.4.0
docker logs solo | grep RaftManager
    $ docker run -d --name solo apache/kafka:4.4.0 ee1ecc07ed0f $ docker logs solo | grep RaftManager (shortened) INFO [RaftManager id=1] Completed transition to Leader(... epoch=1 ...) INFO [ControllerServer id=1] Loaded new metadata FinalizedFeatures(metadataVersion=4.4-IV2, share.version=2, ...)
    The node formats its storage, elects itself leader of the controller quorum (epoch 1) and finalises features: metadata version 4.4 and share groups enabled. No ZooKeeper.

  2. Step 2 · What is inside

    docker exec solo ls /opt/kafka
docker exec solo grep -E "^(process.roles|node.id|...)" /opt/kafka/config/server.properties
    $ docker exec solo ls /opt/kafka LICENSE NOTICE bin config kafka.jsa libs licenses logs site-docs storage.jsa $ cat config/server.properties (key lines) process.roles=broker,controller node.id=1 controller.quorum.voters=1@localhost:9093 listeners=PLAINTEXT://:9092,CONTROLLER://:9093 advertised.listeners=PLAINTEXT://localhost:9092 log.dirs=/tmp/kraft-combined-logs num.partitions=1 log.retention.hours=168
    The default config: combined broker + controller, data in /tmp, 1 partition per new topic, 7-day retention. Perfect for learning, wrong for production.

  3. Step 3 · Create, list, describe

    kafka-topics.sh --bootstrap-server localhost:9092 --create --topic menu-updates --partitions 2
kafka-topics.sh --bootstrap-server localhost:9092 --list
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic menu-updates
    == topic CRUD $ kafka-topics.sh --create --topic menu-updates --partitions 2 Created topic menu-updates. $ kafka-topics.sh --list menu-updates $ kafka-topics.sh --describe --topic menu-updates Topic: menu-updates TopicId: xkW8s2fzR8ClIrKFeh6cow PartitionCount: 2 ReplicationFactor: 1 Configs: min.insync.replicas=1,segment.bytes=1073741824 Topic: menu-updates Partition: 0 Leader: 1 Replicas: 1 Isr: 1 Topic: menu-updates Partition: 1 Leader: 1 Replicas: 1 Isr: 1
    Two partitions, replication factor 1 (only one broker), leader 1. Every tool needs --bootstrap-server.

  4. Step 4 · Change a setting live

    kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name menu-updates \
  --alter --add-config retention.ms=86400000
kafka-configs.sh ... --describe
    $ kafka-configs.sh --alter --add-config retention.ms=86400000 Completed updating config for topic menu-updates. $ kafka-configs.sh --describe Dynamic configs for topic menu-updates are: retention.ms=86400000 sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=86400000}
    Retention for this topic is now 1 day instead of 7, with no restart: a dynamic topic config.

  5. Step 5 · Produce and consume

    kafka-console-producer.sh --bootstrap-server localhost:9092 --topic menu-updates
>Paneer Tikka price 220
>Dosa back in stock
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic menu-updates --from-beginning
    $ kafka-console-producer.sh (typed 2 lines) $ kafka-console-consumer.sh --from-beginning The consumer rebalance protocol (KIP-848) is production-ready! Set group.protocol=consumer to try it out. See https://kafka.apache.org/documentation/#consumer_rebalance_protocol Paneer Tikka price 220 Dosa back in stock [2026-11-05 11:37:27,209] ERROR Error processing message, terminating consumer process: (org.apache.kafka.tools.consumer.ConsoleConsumer) org.apache.kafka.common.errors.TimeoutException Processed a total of 2 messages
    Both events come back. Note the hint about the new consumer rebalance protocol (KIP-848), now production-ready (Lesson 3.2). The final TimeoutException is just the consumer’s --timeout-ms ending the demo.

  6. Step 6 · Three errors on purpose

    kafka-topics.sh ... --create --topic menu-updates          # again
kafka-topics.sh ... --create --topic x3 --replication-factor 3
kafka-topics.sh ... --delete --topic menu-updates; kafka-topics.sh ... --list
    $ kafka-topics.sh --create --topic menu-updates (again) Error while executing topic command : Topic 'menu-updates' already exists. $ kafka-topics.sh --create ... --replication-factor 3 (1 broker) Error while executing topic command : Unable to replicate the partition 3 time(s): The target replication factor of 3 cannot be reached because only 1 broker(s) are registered or some brokers have all their log directories cordoned. $ kafka-topics.sh --delete --topic menu-updates __consumer_offsets (empty list)
    Duplicate topic: already exists. RF 3 on one broker: cannot be reached because only 1 broker(s) are registered. Delete works and only the internal __consumer_offsets remains.

Developers run Kafka in Docker to test producers and consumers.

Alert→kafka-configs→Fixed

Bug→console consumer→Evidence
