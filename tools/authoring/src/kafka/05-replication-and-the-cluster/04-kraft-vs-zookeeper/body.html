2 Definition

KRaft vs ZooKeeper

Formal definition (write this in exams)

KRaft (Kafka Raft, KIP-500) is Kafka’s built-in metadata quorum. Controller nodes replicate the __cluster_metadata topic with a Raft-based protocol; the quorum leader is the active controller, which serialises all metadata changes as records. Brokers fetch this log and maintain a metadata image. It replaced Apache ZooKeeper, the external coordination service Kafka used until 3.x; ZooKeeper mode was removed in Kafka 4.0.

In simple words

Kafka used to need a separate system, ZooKeeper, to remember which broker leads what. Now Kafka keeps that information in its own special log, copied among a few controller nodes that vote on a leader. One system, faster failover, many more partitions.

Why, how, where

Why

ZooKeeper was a second distributed system to run, secure and tune; metadata had to be copied from it to brokers, limiting partitions (~200k) and slowing controller failover.

the problem it solves

How

A few nodes run process.roles=controller and form a Raft quorum (controller.quorum.voters / bootstrap servers). The leader of that quorum is the active controller; it appends every change to __cluster_metadata. Brokers fetch the log and apply it, like followers.

the mechanism

Where

Every Kafka 4.x cluster (ZooKeeper mode was removed in 4.0, March 2025). Small clusters use combined nodes (broker+controller, like our lab); production uses 3 or 5 dedicated controllers.

in real systems

When not

A quorum of N voters survives (N−1)/2 failures: 3 voters → 1, 5 → 2. Lose the majority and no metadata changes (no elections) can happen.

know the limits

How we got here

LEVELS> Cluster metadata at three levels L1> The minutes book
  • A committee (the voters) keeps one official minutes book. The chairperson (active controller) writes every decision; members copy it; a decision counts once most members have it. If the chair leaves, members vote a new chair. Everyone else (brokers) reads the book to know the rules.
L2> How KRaft works
  • process.roles: broker, controller, or both (combined). Controllers listed in controller.quorum.voters (static) or discovered via controller.quorum.bootstrap.servers (dynamic quorum, KIP-853, kraft.version 1).
  • Raft: voters elect a leader per epoch (our lab: epoch 17, leader 2). The leader appends records; a record is committed when a majority has it (the quorum high watermark, 24618 in our lab, same idea as Lesson 5.2).
  • Brokers are observers: they fetch the metadata log and keep an in-memory image. Brokers register and send heartbeats; a broker without heartbeats for broker.session.timeout.ms is fenced.
L3> Snapshots, features, migration
  • The log is periodically compacted into snapshots (metadata.log.max.record.bytes.between.snapshots), so a restarting node loads a snapshot plus a short tail.
  • Feature levels (metadata.version, kraft.version, group.version, eligible.leader.replicas.version …) are agreed by the quorum and upgraded with kafka-features.sh upgrade after all nodes run the new binary.
  • Migration: ZooKeeper clusters had to move to KRaft on Kafka 3.x (3.9 is the bridge release) using the dual-write migration mode, then upgrade to 4.x. You cannot upgrade a ZooKeeper cluster directly to 4.0.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka needs ZooKeeper.
    Reality (Kafka 4.4): Not since 4.0; KRaft is the only mode.
    Proof: Our lab has none.
  • Myth: The controller is a separate product.
    Reality (Kafka 4.4): It is a Kafka process role.
    Proof: process.roles.
  • Myth: Metadata is in a database.
    Reality (Kafka 4.4): It is a Kafka log you can dump.
    Proof: Step 2.
EXAM> “KRaft vs ZooKeeper?” KRaft stores metadata in __cluster_metadata replicated by Raft among controller voters; active controller = quorum leader; brokers fetch the log; faster failover, more partitions, one system. ZooKeeper removed in 4.0; migrate on 3.x (3.9 bridge).

4 Step by step

Open the cluster’s brain

All outputs are real: Kafka 4.4.0, 3 combined KRaft nodes, cluster TiffinGoKafkaLab0001A.

  1. Step 1 · Ask the quorum

    kafka-metadata-quorum.sh --bootstrap-server k1:9092 describe --status
    == 1) the controller quorum ClusterId: TiffinGoKafkaLab0001A LeaderId: 2 LeaderEpoch: 17 HighWatermark: 24618 CurrentVoters: [1, 2, 3]
    Node 2 is the active controller in Raft epoch 17. 24,618 metadata records are committed on a majority. Voters are 1, 2, 3.

  2. Step 2 · Read the metadata log

    kafka-dump-log.sh --cluster-metadata-decoder --files 00000000000000000000.log | grep -o '"type":"[A-Z_]*"' | sort | uniq -c | sort -rn
    == 2) metadata is a Kafka log too: record types in __cluster_metadata (kafka-dump-log --cluster-metadata-decoder) 14399 "type":"NO_OP_RECORD" 9488 "type":"PARTITION_CHANGE_RECORD" 389 "type":"PARTITION_RECORD" 88 "type":"TOPIC_RECORD" 76 "type":"BROKER_REGISTRATION_CHANGE_RECORD" 40 "type":"REMOVE_TOPIC_RECORD" 36 "type":"CONFIG_RECORD" 20 "type":"REGISTER_CONTROLLER_RECORD" payload: {"type":"PARTITION_CHANGE_RECORD","version":2,"data":{"partitionId":0,"topicId":"QJapXCqRT2m0z3kWabiYsg","isr":[3,1],"leader":3}}
    The log is ordinary records. NO_OP records are the leader’s heartbeat-like appends; 9,488 PARTITION_CHANGE records are every ISR shrink/expand and election from Lessons 5.1–5.3. The payload shown is the preferred election from 5.3: leader 3, ISR [3,1]. (We ran it on a copy of the file because the live directory is locked.)

  3. Step 3 · Browse the image

    kafka-metadata-shell.sh --snapshot meta.log
ls /image; ls /image/cluster/brokers; cat /image/topics/byName/rides-51/0
    == 3) kafka-metadata-shell: the cluster image $ ls /image acls clientQuotas cluster configs delegationToken features producerIds provenance scram topics $ ls /image/cluster/brokers 1 2 3 $ cat /image/topics/byName/rides-51/0 PartitionRegistration(replicas=[1, 2, 3], isr=[1, 2, 3], removingReplicas=[], addingReplicas=[], elr=[], lastKnownElr=[], leader=2, leaderRecoveryState=RECOVERED, leaderEpoch=1, partitionEpoch=6)
    The image is the result of replaying the log: brokers, topics, configs, ACLs, quotas. The partition registration shows replicas, isr, elr, leader 2, leaderEpoch and partitionEpoch.

  4. Step 4 · Feature levels

    kafka-features.sh --bootstrap-server k1:9092 describe
    == 4) feature levels the quorum agreed on eligible.leader.replicas.version 1 group.version 1 kraft.version 0 metadata.version 4.4-IV2 share.version 2 streams.version 1 transaction.version 2
    metadata.version 4.4-IV2, ELR on (eligible.leader.replicas.version 1), new consumer protocol (group.version 1), share groups (share.version 2). kraft.version 0 means a static voter set.
