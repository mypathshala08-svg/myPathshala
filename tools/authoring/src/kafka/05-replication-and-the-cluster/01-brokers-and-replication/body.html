2 Definition

Brokers and replication

Formal definition (write this in exams)

Each partition is replicated to replication.factor brokers. The ordered replica list is chosen by the controller at topic creation (round-robin with shifted starting points, rack-aware when broker.rack is set) or given explicitly; the first replica is the preferred leader. The leader handles all produce and fetch requests; followers replicate by fetching from the leader. Replica placement can be changed online with kafka-reassign-partitions, which adds new replicas, waits for them to catch up, and removes old ones.

In simple words

Kafka keeps several copies of each partition on different brokers. One copy is in charge (leader); the others keep copying it. Kafka spreads copies and leaders evenly when you create a topic, and you can move copies later with a reassignment.

Why, how, where

Why

A single copy dies with its disk. Several copies on different machines (and racks) keep data safe and readable through failures.

the problem it solves

How

Each partition has replication.factor replicas on different brokers; the first live one in the list leads, the others fetch from it. The controller places replicas and you can move them with kafka-reassign-partitions.

the mechanism

Where

Every production topic (RF 3 is standard); multi-zone clusters with broker.rack; adding brokers and moving load.

in real systems

When not

RF cannot exceed the number of brokers; replicas cost disk and network (RF 3 = 3× storage).

Dissect a partition line

LEVELS> Replication at three levels L1> Photocopies in three branches
  • Every important register is copied to three branch offices. One branch is “in charge” of writing in it; the others copy its new pages. If that branch closes, another one takes charge.
L2> The rules
  • replication.factor (topic setting; broker default default.replication.factor, 1 unless changed) = number of copies.
  • The replica list order matters: the first replica is the preferred leader. Followers send Fetch requests to the leader, like consumers.
  • Placement: round-robin with a shifting start so leaders and followers spread evenly; with broker.rack set, copies go to different racks/zones.
L3> Moving and balancing
  • kafka-reassign-partitions.sh: generate or write a JSON plan, --execute, then --verify (which also clears throttles). New replicas copy data, join the ISR, and old ones are removed.
  • Use --throttle (bytes/s) to protect production traffic while copying large partitions.
  • Reassignment does not change the leader immediately: run a preferred-leader election (Lesson 5.3). Tools such as Cruise Control automate balancing.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Adding brokers rebalances data automatically.
    Reality (Kafka 4.4): Partitions stay until you reassign them.
    Proof: Step 4 was a manual move.
  • Myth: Followers are pushed data by the leader.
    Reality (Kafka 4.4): Followers pull with Fetch requests, like consumers.
    Proof: Peel animation.
  • Myth: Reassignment also moves leadership.
    Reality (Kafka 4.4): Leadership changes only on election.
    Proof: Step 4: leader stayed 1.
EXAM> “How does Kafka replication work?” Each partition has RF replicas on different brokers; first replica = preferred leader; leader serves reads/writes, followers fetch; placement round-robin and rack-aware; move replicas with kafka-reassign-partitions (execute, verify, throttle).

4 Step by step

Place, count, move

All outputs are real: Kafka 4.4.0, 3 brokers (KRaft). Topics rides-51 (6 partitions, RF 3) and small-51 (2 partitions, RF 2).

  1. Step 1 · Create a replicated topic

    kafka-topics.sh --bootstrap-server k1:9092 --create --topic rides-51 --partitions 6 --replication-factor 3
kafka-topics.sh --bootstrap-server k1:9092 --describe --topic rides-51
    == 1) create rides-51: 6 partitions, replication factor 3 Created topic rides-51. Topic: rides-51 PartitionCount: 6 ReplicationFactor: 3 Configs: min.insync.replicas=1 Topic: rides-51 Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3 Topic: rides-51 Partition: 1 Leader: 2 Replicas: 2,3,1 Isr: 2,3,1 Topic: rides-51 Partition: 2 Leader: 3 Replicas: 3,1,2 Isr: 3,1,2 Topic: rides-51 Partition: 3 Leader: 1 Replicas: 1,3,2 Isr: 1,3,2 Topic: rides-51 Partition: 4 Leader: 3 Replicas: 3,2,1 Isr: 3,2,1 Topic: rides-51 Partition: 5 Leader: 2 Replicas: 2,1,3 Isr: 2,1,3
    Six partitions, each with copies on all three brokers. The replica lists start at a different broker each time (1,2,3 / 2,3,1 / 3,1,2 …), so each broker is first, and therefore preferred leader, for two partitions.

  2. Step 2 · Count

    Counter(leader per partition), Counter(each broker in replica lists)
    == 2) count leaders and replicas per broker leaders : {'1': 2, '2': 2, '3': 2} replicas: {'1': 6, '2': 6, '3': 6}
    2-2-2 leaders and 6-6-6 replicas: perfectly balanced load for reads, writes and disk.

  3. Step 3 · Choose placement yourself

    kafka-topics.sh --bootstrap-server k1:9092 --create --topic small-51 --replica-assignment 1:2,2:3
    == 3) RF 2 topic and a manual placement Created topic small-51. Topic: small-51 Partition: 0 Leader: 1 Replicas: 1,2 Isr: 1,2 Topic: small-51 Partition: 1 Leader: 2 Replicas: 2,3 Isr: 2,3
    --replica-assignment lists replicas per partition: partition 0 on brokers 1 and 2, partition 1 on 2 and 3 (RF 2).

  4. Step 4 · Move a partition

    echo '{"version":1,"partitions":[{"topic":"small-51","partition":0,"replicas":[3,1]}]}' > /tmp/plan.json
kafka-reassign-partitions.sh --bootstrap-server k1:9092 --reassignment-json-file /tmp/plan.json --execute
kafka-reassign-partitions.sh --bootstrap-server k1:9092 --reassignment-json-file /tmp/plan.json --verify
    == 4) move partition 0 of small-51 from brokers 1,2 to 3,1 (kafka-reassign-partitions) Save this to use as the --reassignment-json-file option during rollback Successfully started partition reassignment for small-51-0 Status of partition reassignment: Reassignment of partition small-51-0 is completed. Clearing broker-level throttles on brokers 1,2,3 Clearing topic-level throttles on topic small-51 Topic: small-51 Partition: 0 Leader: 1 Replicas: 3,1 Isr: 1,3 Topic: small-51 Partition: 1 Leader: 2 Replicas: 2,3 Isr: 2,3
    Broker 3 copied the partition, joined the ISR, and broker 2’s replica was removed. The leader is still 1, although 3 is now first in the list: leadership does not move until a preferred election (Lesson 5.3).

  5. Step 5 · Proof on disk

    for i in 1 2 3; do docker exec k$i ls -d /var/lib/kafka/data/small-51-0; done
    == 5) the replica on disk: which brokers hold small-51-0 now k1: /var/lib/kafka/data/small-51-0 k2: - k3: /var/lib/kafka/data/small-51-0
    The partition folder now exists on brokers 1 and 3 and is gone from broker 2.
