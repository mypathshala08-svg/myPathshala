1 The story

A stream processor without a cluster

Before you start: 3.1 Consumer groups.

🤔 Read a topic, clean each order, split big and small orders into two topics, and scale it across machines. How many servers do you need besides Kafka?

Zero. Kafka Streams is a Java library, not a cluster: your app is a normal program that reads, transforms and writes topics. Scaling works like a consumer group: one task per input partition, spread over threads and instances. 2 Definition

Kafka Streams

Formal definition (write this in exams)

Kafka Streams is a client library for building applications that process records from Kafka topics and write results to Kafka. A program defines a topology of processors using the high-level DSL (KStream, KTable) or the Processor API. At runtime instances sharing an application.id form a consumer group; the topology is split into tasks (one per input partition per sub-topology) executed by stream threads, with fault tolerance, state management and optional exactly-once processing.

In simple words

Kafka Streams is a Java library: you write a small program that says “read this topic, change records like this, write them there”, and the library handles splitting the work, restarts and offsets.

Why, how, where

Why

Hand-written consume-process-produce loops must solve partition assignment, offsets, retries, state, scaling and exactly-once. Kafka Streams gives all of that as a library inside your app.

the problem it solves

How

You describe a topology with the DSL (stream → filter → mapValues → split → to). At start the library joins a consumer group named application.id, gets partitions, creates one task per partition, runs tasks on stream threads, and commits offsets (and output) together.

the mechanism

Where

Microservices that enrich, route, aggregate or join events: fraud checks, order routing, real-time counters, alerting. Runs anywhere Java runs: containers, Kubernetes, a laptop.

in real systems

When not

Java/Scala (JVM) only; input and output must be Kafka. For SQL, Python or multi-source pipelines look at Flink, Spark (Lesson 9.4) or ksqlDB.

Dissect the topology

LEVELS> Kafka Streams at three levels L1> A sorting conveyor
  • Parcels arrive on a belt (topic). Workers check each parcel (filter), relabel it (map), and push it onto the right outgoing belt (split/to). Add more workers and the belts are shared out among them.
L2> The DSL
  • KStream: an unbounded stream of key–value records. Stateless operations: filter, map/mapValues, flatMap, peek, split().branch(), merge, selectKey, to.
  • Serdes turn bytes into objects (String, Long, JSON, Avro with the registry).
  • topology.describe() prints sources, processors and sinks: read it to see what your code really does.
L3> Runtime
  • application.id = consumer group id and prefix for internal topics. Each input partition → one task (0_0, 0_1, 0_2 = sub-topology 0, partition n). Tasks are spread over num.stream.threads and instances; max parallelism = number of input partitions.
  • Lifecycle states: CREATED → REBALANCING → RUNNING → PENDING_SHUTDOWN → NOT_RUNNING (also ERROR).
  • processing.guarantee=exactly_once_v2 uses transactions (Lesson 3.5) to commit input offsets and outputs atomically. The lower-level Processor API gives full control (custom state, punctuations).
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka Streams needs its own cluster.
    Reality (Kafka 4.4): It is a library inside your app.
    Proof: Step 2: java -cp.
  • Myth: More threads always help.
    Reality (Kafka 4.4): Max parallelism = input partitions.
    Proof: 3 tasks.
  • Myth: Streams runs on the brokers.
    Reality (Kafka 4.4): It runs in your app, brokers only store.
    Proof: Peel.
EXAM> “What is Kafka Streams?” Java library; DSL KStream/KTable; topology of processors; application.id = consumer group; tasks per partition over threads/instances; stateless ops filter/map/split; state stores with changelogs; exactly_once_v2.

4 Step by step

Build, run, route

All outputs are real: Kafka Streams 4.4.0 (Java 21) against the 3-broker lab.

  1. Step 1 · The app and its topology

    KStream<String, String> orders = b.stream("orders-91");          // key city, value item,qty,price
KStream<String, String> valid = orders
    .filter((k, v) -> Integer.parseInt(v.split(",")[1]) > 0)
    .mapValues(v -> v.toUpperCase());
valid.split()
    .branch((k, v) -> v.startsWith("THALI"), Branched.withConsumer(s -> s.to("big-orders-91")))
    .defaultBranch(Branched.withConsumer(s -> s.to("small-orders-91")));
System.out.println(b.build().describe());
    == run the app with 2 stream threads (topology, state changes, records) == topology Topologies: Sub-topology: 0 Source: KSTREAM-SOURCE-0000000000 (topics: [orders-91]) --> KSTREAM-PEEK-0000000001 Processor: KSTREAM-PEEK-0000000001 (stores: []) --> KSTREAM-FILTER-0000000002 <-- KSTREAM-SOURCE-0000000000 Processor: KSTREAM-FILTER-0000000002 (stores: []) --> KSTREAM-MAPVALUES-0000000003 <-- KSTREAM-PEEK-0000000001 Processor: KSTREAM-MAPVALUES-0000000003 (stores: []) --> KSTREAM-BRANCH-0000000004 <-- KSTREAM-FILTER-0000000002 Processor: KSTREAM-BRANCH-0000000004 (stores: []) --> KSTREAM-BRANCH-00000000040, KSTREAM-BRANCH-00000000041 <-- KSTREAM-MAPVALUES-0000000003 Processor: KSTREAM-BRANCH-00000000040 (stores: []) --> KSTREAM-SINK-0000000008 <-- KSTREAM-BRANCH-0000000004 Processor: KSTREAM-BRANCH-00000000041 (stores: []) --> KSTREAM-SINK-0000000006 <-- KSTREAM-BRANCH-0000000004 Sink: KSTREAM-SINK-0000000006 (topic: big-orders-91) <-- KSTREAM-BRANCH-00000000041 Sink: KSTREAM-SINK-0000000008 (topic: small-orders-91) <-- KSTREAM-BRANCH-00000000040
    One sub-topology: source → peek → filter → mapValues → branch → two sinks.

  2. Step 2 · Run with 2 threads

    java -cp "out:libs/*" Kitchen91 2 15000     # num.stream.threads = 2
    state CREATED -> REBALANCING state REBALANCING -> RUNNING in Pune -> thali,1,150 in Mumbai -> idli,2,40 in Delhi -> dosa,0,90 in Pune -> vada,3,60 in Mumbai -> thali,2,300 in Delhi -> lassi,1,45 == tasks StreamThread-2 task 0_1 partitions [orders-91-1] StreamThread-1 task 0_2 partitions [orders-91-2] StreamThread-1 task 0_0 partitions [orders-91-0] state RUNNING -> PENDING_SHUTDOWN state PENDING_SHUTDOWN -> NOT_RUNNING
    States CREATED → REBALANCING → RUNNING. 3 input partitions → 3 tasks (0_0, 0_1, 0_2) spread over 2 threads. Six orders came in; Delhi’s dosa had qty 0.

  3. Step 3 · Outputs

    kafka-console-consumer.sh --bootstrap-server k1:9092 --topic big-orders-91 --from-beginning --formatter-property print.key=true
    == outputs big-orders-91: Pune THALI,1,150 Mumbai THALI,2,300 small-orders-91: Mumbai IDLI,2,40 Pune VADA,3,60 Delhi LASSI,1,45
    Two thalis went to big-orders, three to small-orders, values upper-cased, keys (cities) unchanged. The qty-0 order was filtered out.

  4. Step 4 · It is a consumer group

    kafka-consumer-groups.sh --bootstrap-server k1:9092 --describe --group kitchen-91
    == the app is a consumer group named after application.id orders-91 p0 offset 4 lag 0 orders-91 p2 offset - lag - orders-91 p1 offset 2 lag 0
    application.id kitchen-91 is the group. Offsets 4 and 2 committed on partitions 0 and 1 (partition 2 got no data), lag 0.
