1 The story

Counting by time when events arrive late

Before you start: 9.2 KTables.

🤔 An order stamped 12:00:08 arrives after one stamped 12:00:12. Which 10-second window does it count in, and what if it arrives a minute late?

Streams work in event time. Windows group records by their timestamps; a grace period decides how late a record may still be counted. In our lab a record 4 s late updated its window from 3 to 4; one that arrived after the grace was silently dropped. We also built hopping and session windows, enriched orders with a menu table, and matched orders with payments within 5 minutes.

2 Definition

Windows and joins

Formal definition (write this in exams)

Windowing groups records with the same key by their timestamps into finite buckets: tumbling (fixed, non-overlapping), hopping (fixed, overlapping), sliding (by time difference) and session (separated by inactivity gaps). A grace period bounds how late an out-of-order record is accepted, measured against stream time. Joins combine streams and tables by key: stream–table joins look up the current table value; stream–stream joins match records whose timestamps lie within a join window.

In simple words

Windows cut time into buckets so you can count “per 10 seconds”. Late events still land in the right bucket if they are not too late. Joins match records with the same key, like an order with its price or its payment.

Why, how, where

Why

Business questions are about time (“orders per minute”, “payment within 5 minutes”) and about combining streams (“order + latest price”). Networks and phones deliver events late and out of order.

the problem it solves

How

Each record carries a timestamp. Streams tracks stream time (max timestamp seen per task). A window closes when stream time passes window end + grace; later records for it are dropped. Joins keep windowed or table state so matching records can meet.

the mechanism

Where

Per-minute dashboards, rate limits and fraud (N events per window), user sessions, enrichment with reference data, order–payment and click–impression matching.

in real systems

When not

Time only moves when new records arrive (no wall-clock closing by default). Joins need co-partitioned inputs (same key, same partition count), except GlobalKTable and foreign-key joins.

Window types side by side

LEVELS> Windows and joins at three levels L1> Train coaches
  • Tumbling windows are coaches of fixed length; hopping windows are overlapping coaches; a session is a group of friends who keep sitting together while they keep talking (gap). Grace is how long the door stays open after the train leaves the platform.
L2> The DSL
  • TimeWindows.ofSizeAndGrace(10 s, 5 s) (tumbling), .advanceBy(5 s) (hopping), SlidingWindows (by time difference), SessionWindows.ofInactivityGapWithNoGrace(5 s).
  • Windowed keys look like Mumbai@[0s,10s): start inclusive, end exclusive. Results are updates; suppress(untilWindowCloses(...)) emits one final result per window.
  • Joins: stream–table (join/leftJoin, lookup latest value, table updates don’t emit), stream–stream (JoinWindows, both sides buffered), table–table, and foreign-key table joins.
L3> Time internals
  • Timestamps come from the record (CreateTime) or a TimestampExtractor (e.g. a field). Stream time = max timestamp seen by the task; window close = end + grace.
  • Session windows merge: a new event within the gap of two sessions joins them; old session results are deleted (null) and a merged one emitted, as our lab shows.
  • Suppress needs the right serdes on the materialized store; otherwise a ClassCastException appears (we hit it in the lab and fixed it with Materialized.with(String, Long)).

4 Step by step

Six time experiments

All outputs are real, produced with Kafka Streams 4.4.0 TopologyTestDriver (exact, repeatable event times; same engine as a live app).

  1. Step 1 · Tumbling with grace

    stream.groupByKey()
  .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofSeconds(10), Duration.ofSeconds(5)))
  .count()
    == 1) tumbling window 10 s, grace 5 s (count per city) event Mumbai t=1s -> [KeyValue(Mumbai@[0s,10s), 1)] event Mumbai t=4s -> [KeyValue(Mumbai@[0s,10s), 2)] event Mumbai t=9s -> [KeyValue(Mumbai@[0s,10s), 3)] event Mumbai t=12s -> [KeyValue(Mumbai@[10s,20s), 1)] event Mumbai t=8s (late, within grace) -> [KeyValue(Mumbai@[0s,10s), 4)] event Mumbai t=21s -> [KeyValue(Mumbai@[20s,30s), 1)] event Mumbai t=7s (late, after grace) -> no output
    Each event updates its window. At t=8 (stream time 12) window [0,10) closes at 10+5=15, so it is still open: count 4. At t=7 after stream time 21, the window is closed: dropped.

  2. Step 2 · Only final results

    .count(Materialized.with(Serdes.String(), Serdes.Long()))
.suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()))
    == 2) same with suppress(untilWindowCloses): one final result per window event Mumbai t=1s -> no output event Mumbai t=4s -> no output event Mumbai t=9s -> no output event Mumbai t=12s -> no output event Mumbai t=8s (late, within grace) -> no output event Mumbai t=21s -> [KeyValue(Mumbai@[0s,10s), 4)] event Mumbai t=7s (late, after grace) -> no output
    No intermediate updates. When stream time reached 21 (≥ 15), the final [0,10) = 4 was emitted once. [10,20) will be emitted when stream time passes 25.

  3. Step 3 · Hopping

    TimeWindows.ofSizeWithNoGrace(Duration.ofSeconds(10)).advanceBy(Duration.ofSeconds(5))
    == 3) hopping window 10 s advancing 5 s: one event, two windows event Pune t=7s -> [KeyValue(Pune@[0s,10s), 1), KeyValue(Pune@[5s,15s), 1)]
    One event at 7 s lands in two overlapping windows.

  4. Step 4 · Sessions

    SessionWindows.ofInactivityGapWithNoGrace(Duration.ofSeconds(5))
    == 4) session window, inactivity gap 5 s event Delhi t=0s -> [KeyValue(Delhi@[0s,0s), 1)] event Delhi t=3s -> [KeyValue(Delhi@[0s,0s), deleted (merged)), KeyValue(Delhi@[0s,3s), 2)] event Delhi t=20s -> [KeyValue(Delhi@[20s,20s), 1)] event Delhi t=6s (late, no grace) -> no output
    Events at 0 and 3 are within 5 s: the session [0,0] is deleted and replaced by [0,3] with count 2. Event at 20 starts a new session. The late event at 6 arrives after stream time 20: dropped.

  5. Step 5 · Stream-table join

    KTable<String,String> menu = b.table("menu");
orders.leftJoin(menu, (qty, price) -> price == null ? "?" : qty * price)
    == 5) stream-table join: orders enriched with the latest menu price menu: idli=40 dosa=90 orders idli x2, pizza x1 -> [KeyValue(idli, qty 2 x 40 = 80), KeyValue(pizza, qty 1 x ? (not on menu))] menu update idli=45 -> no output (table updates do not trigger) order idli x2 -> [KeyValue(idli, qty 2 x 45 = 90)]
    Each order uses the price at that moment. leftJoin keeps pizza with a missing price. A price change alone emits nothing; the next order sees 45.

  6. Step 6 · Stream-stream join

    orders.join(payments, (o, p) -> o + " PAID " + p, JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5)))
    == 6) stream-stream join: order + payment within 5 minutes order-1 paid after 2 min -> [KeyValue(order-1, idli x2 PAID Rs 80 UPI)] order-2 paid after 10 min -> no output (outside window)
    A payment 2 minutes after the order matched. One 10 minutes later did not: outside the join window.
