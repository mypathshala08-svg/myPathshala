2 Definition

Kafka with Spark and Flink

Formal definition (write this in exams)

Spark Structured Streaming and Apache Flink are distributed stream-processing engines with Kafka connectors. Spark models a Kafka topic as an unbounded table processed in micro-batches, tracking source offsets and operator state in a checkpoint and handling late data with watermarks. Flink processes records continuously with keyed state and consistent distributed snapshots. Both can provide exactly-once results with suitable sinks.

In simple words

Instead of putting stream logic inside a Java app, you can hand it to an engine like Spark or Flink. Spark reads Kafka every few seconds like a growing table, in Python or SQL, and remembers where it stopped in a checkpoint folder.

Why, how, where

Why

Kafka Streams is Java-only and Kafka-to-Kafka. Data teams need Python/SQL, joins with files and databases, and writes to lakes and warehouses, at very large scale.

the problem it solves

How

Spark treats the topic as an unbounded table: each micro-batch reads new offset ranges per partition, runs the query incrementally with state, and records progress in a checkpoint. Flink runs continuous operators with distributed snapshots (checkpoints) for exactly-once state.

the mechanism

Where

Streaming ETL into Delta/Iceberg lakehouses, ML feature pipelines, large joins, real-time analytics; Flink for low-latency event processing and Flink SQL; managed services (Databricks, Confluent Cloud for Flink, AWS Managed Flink).

in real systems

When not

A cluster to run and tune. Spark adds micro-batch latency (seconds); Flink is lower latency but more operational depth. Offsets live in checkpoints, so standard lag tools see no consumer group unless you add monitoring.

Dissect the checkpoint

LEVELS> Engines at three levels L1> Factory vs workshop tool
  • Kafka Streams is a power tool you carry into your own workshop (your app). Spark and Flink are factories: you send them the job, they bring many machines, and they connect to many kinds of input and output.
L2> Spark + Kafka
  • spark.readStream.format("kafka") with kafka.bootstrap.servers, subscribe, startingOffsets. Columns: key, value (binary), topic, partition, offset, timestamp, timestampType. Parse value with from_json (or from_avro with the registry).
  • withWatermark("ts", "1 minute") = max event time seen − 1 min; windows older than that are finalized and late rows dropped (same idea as grace in 9.3).
  • Output modes: append (final rows only), update (changed rows), complete (whole table). Package: spark-sql-kafka-0-10 (+ kafka-clients, commons-pool2).
L3> Guarantees and choices
  • Spark: offsets per batch are written to checkpoint/offsets before processing and commits after; with idempotent or transactional sinks (Delta, foreachBatch upserts) you get exactly-once end to end. The Kafka sink itself is at-least-once.
  • Flink: KafkaSource/KafkaSink, event-time watermarks, keyed state, checkpoint barriers; exactly-once Kafka sink via transactions. Flink SQL: CREATE TABLE … WITH ('connector'='kafka').
  • ksqlDB: SQL server built on Kafka Streams (Confluent Community License). Choose by language, latency, sources/sinks and who operates it.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Spark commits offsets to a consumer group.
    Reality (Kafka 4.4): It stores them in the checkpoint.
    Proof: Step 5.
  • Myth: Late data always counts.
    Reality (Kafka 4.4): Behind the watermark it is dropped.
    Proof: Step 3.
  • Myth: One engine is best for everything.
    Reality (Kafka 4.4): Choose by language, latency, sinks.
    Proof: Table.

4 Step by step

PySpark on Kafka

All outputs are real: Spark 4.3.0 (PySpark, local[2]) with spark-sql-kafka-0-10 4.3.0 against the 3-broker Kafka 4.4 lab. Flink is described, not run in our lab.

  1. Step 1 · Kafka as a DataFrame

    raw = (spark.readStream.format("kafka")
       .option("kafka.bootstrap.servers", "k1:9092,k2:9092,k3:9092")
       .option("subscribe", "orders-94").option("startingOffsets", "earliest").load())
raw.printSchema()
    == 1) Spark 4.3.0 reading topic orders-94 as a streaming DataFrame root |-- key: binary (nullable = true) |-- value: binary (nullable = true) |-- topic: string (nullable = true) |-- partition: integer (nullable = true) |-- offset: long (nullable = true) |-- timestamp: timestamp (nullable = true) |-- timestampType: integer (nullable = true)
    Every Kafka record becomes a row with binary key and value plus topic, partition, offset and timestamp.

  2. Step 2 · Windowed revenue

    orders = raw.select(F.from_json(F.col("value").cast("string"), schema).alias("o")).select("o.*")
agg = (orders.withWatermark("ts", "1 minute")
       .groupBy(F.window("ts", "5 minutes"), "city")
       .agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")))
    == 2) 5-minute revenue per city (watermark 1 minute) +-----+-----+------+------+-------+ |from |to |city |orders|revenue| +-----+-----+------+------+-------+ |12:00|12:05|Mumbai|2 |230 | |12:00|12:05|Pune |1 |90 | |12:05|12:10|Mumbai|1 |60 | |12:05|12:10|Pune |1 |45 | +-----+-----+------+------+-------+
    Five orders, two 5-minute windows. Mumbai 12:00–12:05: idli 80 + thali 150 = 230.

  3. Step 3 · A late record

    write to orders-94: chai at 12:03 and poha at 12:08
    == 3) two more records: chai at 12:03 (behind the watermark) and poha at 12:08 +-----+------+------+-------+ |from |city |orders|revenue| +-----+------+------+-------+ |12:00|Mumbai|2 |230 | |12:00|Pune |1 |90 | |12:05|Mumbai|1 |60 | |12:05|Pune |1 |45 | |12:05|Pune |2 |75 | <- update: poha added; chai (12:03) dropped +-----+------+------+-------+ rows dropped by watermark: 1
    The watermark was 12:07:30 − 1 min = 12:06:30, so window 12:00–12:05 was already closed: chai (12:03) was dropped (1 row). Poha updated Pune 12:05 to 2 orders, 75. The memory sink in update mode appends each update, which is why Pune 12:05 appears twice.

  4. Step 4 · Progress

    p = query.lastProgress
print(p["batchId"], p["numInputRows"], p["eventTime"]["watermark"], p["sources"][0]["endOffset"])
    == 4) last micro-batch progress batchId 3 | numInputRows 0 | watermark 2026-11-06T12:07:00.000Z source offsets {"orders-94": {"0": 6, "1": 1}}
    Batch 3, watermark now 12:07 (12:08 − 1 min), end offsets 6 and 1 per partition.

  5. Step 5 · The checkpoint

    os.listdir("/tmp/chk94"); open("/tmp/chk94/offsets/3").read()
    == 5) the checkpoint keeps Kafka offsets (Spark does not commit to a consumer group) ['.metadata.crc', 'commits', 'metadata', 'offsets', 'sources', 'state'] | offsets/: ['.0.crc', '.1.crc', '.2.crc', '.3.crc'] {"orders-94":{"0":6,"1":1}}
    The offsets live here, not in a Kafka consumer group: restart with the same checkpoint and the query continues exactly where it stopped.
