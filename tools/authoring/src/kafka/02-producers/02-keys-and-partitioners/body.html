1 The story

Same key, two partitions

Before you start: 2.1 and 1.4 (murmur2).

🤔 The same key went to two different partitions. Same Kafka, same topic. How?

A Java service and a Python service wrote the key Mumbai to the same topic, and Kafka stored it in partition 1 for one and partition 0 for the other. Nothing was broken: they used different partitioners. This lesson shows every way a partition is chosen, and how to fix hot keys.

  • How records without a key are spread (and why it is not random).
  • Which client libraries agree on key placement, and which do not.
  • How one restaurant with 70% of orders overloads one partition, and a 1-line fix.

TiffinGo added a Python service that publishes city offers into the same topic as the Java order service. Riya notices Mumbai offers sometimes arrive before older Mumbai events.

R> Sir, our Java order service and the new Python offers service both use key = city. Why are Mumbai events in two partitions? A> Each client library has a default partitioner. The Java client uses murmur2; Python’s confluent-kafka (librdkafka) defaults to consistent_random, which uses a different hash (CRC32). K> So ordering per city is broken? A> Yes, across the two services. The fix is one line: "partitioner": "murmur2_random" in Python. Today we test every partitioning mode on the cluster, including records with no key and a very hot key.
2 Definition

Keys and partitioners

Formal definition (write this in exams)

The partitioner is the producer component that selects the target partition of each record. If the record specifies a partition, it is used. Otherwise, for a non-null key, the partition is derived from a hash of the serialized key modulo the number of partitions (the Java client uses murmur2; librdkafka-based clients use the configured partitioner). For a null key, the producer uses sticky partitioning, sending a whole batch to one partition before switching (adaptive in the Java client since 3.3). Custom partitioners may implement other rules.

In simple words

Give a key when events must stay in order: same key, same partition. Give no key when order does not matter: the producer fills one partition’s batch at a time. Make sure all your apps hash keys the same way.

Why, how, where

Why

The partition decides ordering, parallelism and load. A wrong key choice causes out-of-order events or one overloaded consumer.

the problem it solves

How

With a key: hash(key) % partitions. Without a key: fill one partition’s batch, then move on (sticky). You can also name a partition or plug in your own partitioner.

the mechanism

Where

Order and account ids for ordering; no key for logs and metrics; compound keys for very active entities.

in real systems

When not

Do not salt a key when you need strict per-key order, and do not mix partitioners across clients on one topic.

Dissect the partition decision

LEVELS> Partitioning at three levels L1> Sorting parcels
  • Parcels with an address (key) always go to the same counter for that area. Parcels without an address go to whichever counter is filling a sack right now, until the sack is full.
L2> The rules
  • Explicit partition in produce(..., partition=2) wins over everything.
  • Key: the partitioner hashes the key bytes. Java: murmur2 % n. librdkafka: chosen by partitioner (default consistent_random = CRC32 for keyed, random for null keys).
  • No key: sticky partitioning: one partition until a batch is sent, then another (Java since 2.4, KIP-480; librdkafka with sticky.partitioning.linger.ms).
L3> Advanced details
  • Since Kafka 3.3 the Java producer’s built-in partitioner is adaptive (KIP-794) for keyless records: it sends more to faster brokers and can avoid unavailable ones (partitioner.adaptive.partitioning.enable, partitioner.availability.timeout.ms). partitioner.ignore.keys=true spreads even keyed records.
  • A custom Java partitioner implements org.apache.kafka.clients.producer.Partitioner (method partition(...)) and is set with partitioner.class.
  • librdkafka partitioners: random, consistent, consistent_random, murmur2, murmur2_random, fnv1a, fnv1a_random. The _random variants spread null keys randomly; only murmur2* match Java placement.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Records without a key are spread randomly, one by one.
    Reality (Kafka 4.4): They are sent in sticky batches to one partition at a time.
    Proof: Step 1: batches of 4 per partition.
  • Myth: All Kafka clients put a key in the same partition.
    Reality (Kafka 4.4): Only clients using murmur2 match the Java client.
    Proof: Step 2: Mumbai → P1 vs P0.
  • Myth: More partitions always fix a hot key.
    Reality (Kafka 4.4): A hot key still maps to one partition; you must change the key.
    Proof: Step 3: 792 of 1,000 on P1.
EXAM> “How does the Kafka producer choose a partition?” Explicit partition if given; else hash(key) % numPartitions (murmur2 in Java); else sticky (adaptive since 3.3). Same key → same partition → ordered; mixed clients need the same hash; hot keys need compound keys or salting.

Every partitioning mode, measured

All outputs are real: Kafka 4.4.0, 3 brokers; Java console producer for Step 1, Python confluent-kafka 2.16.1 for Steps 2–4. Script: jobs/m2/l22_keys.py.

    The Java console producer sent 30 keyless lines. With a tiny batch.size of 300 bytes each batch held 4 records, and each batch went to one partition before the producer moved on: P0, P1 and P2 received whole batches, not one record each. Totals 6 / 16 / 8: sticky is fair over time, not per record.

  2. Step 2 · Two partitioners, same keys

    run("k-murmur", {"partitioner": "murmur2_random"}, keys)     # Java-compatible
run("k-crc",    {"partitioner": "consistent_random"}, keys)  # librdkafka default
    == 2) same keys, two partitioners o101 murmur2 (Java default) -> P2 consistent_random (librdkafka default) -> P2 o102 murmur2 (Java default) -> P0 consistent_random (librdkafka default) -> P0 o103 murmur2 (Java default) -> P1 consistent_random (librdkafka default) -> P1 Mumbai murmur2 (Java default) -> P1 consistent_random (librdkafka default) -> P0 Pune murmur2 (Java default) -> P0 consistent_random (librdkafka default) -> P0 user9@upi murmur2 (Java default) -> P2 consistent_random (librdkafka default) -> P0
    Four keys happened to agree, but Mumbai and user9@upi landed in different partitions. Our hand-written murmur2 (Lesson 1.4) confirms the left column exactly. Agreement on some keys makes this bug easy to miss in testing.

  3. Step 3 · A hot key

    items = [("rest-1" if i % 10 < 7 else f"rest-{i}", "o") for i in range(1000)]
Counter(partition for _, partition in run("hot-22", {"partitioner": "murmur2_random"}, items))
    == 3) a hot key: 70% of traffic from one restaurant records per partition: {0: 95, 1: 792, 2: 113}
    Restaurant 1 sends 70% of orders, so partition 1 got 792 of 1,000 records. Its consumer does 8× the work of the others: lag grows on one partition only.

  4. Step 4 · Fix with a compound key

    key = f"rest-1#{i % 4}"     # 4 sub-keys for the hot restaurant
    == 4) fix: compound key rest-1#<order_id % 4> spreads the hot restaurant records per partition: {0: 445, 1: 442, 2: 113}
    Splitting restaurant 1 into 4 sub-keys spreads it over partitions 0 and 1 (445 / 442). Order is now kept per sub-key, not per restaurant: fine for independent orders, wrong if the restaurant’s events must be strictly ordered.

6 Real-world use

Key choices at work

1. Bank transactions

Key = account id: debits and credits stay in order.

Txn→key account→Ordered

2. Application logs

No key: sticky batches give the best throughput.

Logs→sticky→Fast

3. Marketplace sellers

Very large sellers get compound keys to avoid hot partitions.

Orders→seller#n→Balanced

4. Trip events

Key = trip id across Java and Go services with the same hash.

Apps→murmur2→Consistent

5. Device telemetry

Key = device id: millions of keys spread evenly.

Devices→key→Even
