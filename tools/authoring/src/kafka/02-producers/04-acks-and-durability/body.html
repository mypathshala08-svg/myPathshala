K> Sir, the payments team wants maximum speed. Can we set acks=0? A> Then the producer never waits for any answer. If the broker crashes, payments vanish and nobody knows. 2 Definition

acks and durability

Formal definition (write this in exams)

The producer configuration acks defines when a write is acknowledged: 0 (no acknowledgement), 1 (after the leader appends the record) or all/-1 (after all members of the partition’s in-sync replica set have it). The topic/broker setting min.insync.replicas is the minimum ISR size required for acks=all writes; below it the leader rejects writes with NOT_ENOUGH_REPLICAS. Together with the replication factor and disabled unclean leader election, these settings determine durability and availability.

In simple words

acks is how many copies must confirm before the producer hears “saved”. min.insync.replicas is the minimum number of healthy copies Kafka requires before it even accepts an acks=all write.

Why, how, where

Why

Brokers fail. If a write is confirmed after only one copy exists and that broker dies, the “confirmed” record is gone.

the problem it solves

How

acks says how many replicas must have the record before the producer hears “OK”; min.insync.replicas sets how many in-sync copies must exist for acks=all to be accepted at all.

the mechanism

Where

Payments and orders: acks=all + RF 3 + min.insync 2. Metrics and telemetry: acks=1 or 0 for speed.

in real systems

When not

acks=all does not help if min.insync.replicas=1 and only the leader is in sync: then it behaves like acks=1.

Dissect the durability recipe

LEVELS> acks at three levels L1> Courier receipts
  • acks=0: drop the parcel at the gate and walk away. acks=1: the reception desk signs. acks=all: reception and the two backup stores all sign before you get the receipt.
L2> The rules
  • acks=0: no response; offset unknown (-1); fastest, may lose data silently.
  • acks=1: the leader wrote it to its log; lost if the leader dies before followers copy it.
  • acks=all (= -1, default since Kafka 3.0): every replica currently in the ISR has it. With min.insync.replicas=2 at least 2 copies exist before success.
L3> Deeper details
  • If ISR size < min.insync.replicas, the leader rejects acks=all writes with NOT_ENOUGH_REPLICAS (retriable): writes stop, reads continue. This trades availability for durability.
  • Consumers only see records below the high watermark (replicated to all ISR members), so acks=1 data that was never replicated is never shown to consumers before a leader change.
  • unclean.leader.election.enable=false (default) prevents an out-of-sync replica from becoming leader and silently dropping data. Kafka 4.x adds Eligible Leader Replicas (KIP-966, the Elr column in --describe) to pick a safe leader after failures.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: The default is acks=1.
    Reality (Kafka 4.4): Since Kafka 3.0 the default is acks=all (with idempotence).
    Proof: our producers used all by default.
  • Myth: acks=all means all 3 replicas, always.
    Reality (Kafka 4.4): It means all replicas currently in the ISR; min.insync.replicas sets the floor.
    Proof: Step 3: ISR of 2.
  • Myth: acks=0 records are dropped.
    Reality (Kafka 4.4): They are usually stored; you just never know.
    Proof: Step 4: offsets 2–3 used by acks=0 records.
EXAM> “acks=0, 1, all?” 0 = no ack (fast, may lose), 1 = leader only (lost if leader dies before replication), all = all ISR (safe with RF 3 and min.insync.replicas=2). Below min ISR, acks=all writes fail with NOT_ENOUGH_REPLICAS. Keep unclean leader election off.

4 Step by step

Speed and safety, measured

All outputs are real: Kafka 4.4.0, 3 brokers. Step 1 uses the Java kafka-producer-perf-test.sh; Steps 3–4 use Python confluent-kafka (jobs/m2/l24_fail.py).

  1. Step 1 · Speed of acks=0, 1, all

    for a in 0 1 all; do
  kafka-producer-perf-test.sh --topic pay-24 --num-records 200000 --record-size 200 \
    --throughput -1 --producer-props bootstrap.servers=k1:9092 acks=$a linger.ms=5
done
    == 1) throughput and latency for acks=0, 1, all (200,000 records x 200 bytes) -- acks=0 200000 records sent, 58004.640371 records/sec (11.06 MB/sec), 879.61 ms avg latency, 1542.00 ms max latency, 902 ms 50th, 1504 ms 95th, 1535 ms 99th, 1542 ms 99.9th. -- acks=1 200000 records sent, 48899.755501 records/sec (9.33 MB/sec), 1472.54 ms avg latency, 2452.00 ms max latency, 1607 ms 50th, 2427 ms 95th, 2444 ms 99th, 2451 ms 99.9th. -- acks=all 200000 records sent, 37133.308578 records/sec (7.08 MB/sec), 1643.73 ms avg latency, 3053.00 ms max latency, 1634 ms 50th, 3029 ms 95th, 3041 ms 99th, 3050 ms 99.9th.
    200,000 records of 200 bytes, sending as fast as possible. acks=0 reached 58k records/s, acks=1 49k, acks=all 37k: the safest level cost about 36% throughput here. The high latencies are queueing in an unthrottled test on a small Docker lab, not normal per-record latency.

  2. Step 2 · The topic’s safety floor

    kafka-topics.sh --bootstrap-server k1:9092 --create --topic pay-24 --partitions 3 \
  --replication-factor 3 --config min.insync.replicas=2
    == 2) topic setting min.insync.replicas=2 Topic: pay-24 Configs: min.insync.replicas=2
    min.insync.replicas is a topic (or broker default) setting. It only affects producers that use acks=all.

  3. Step 3 · Break it: too few in-sync copies

    # topic pay-24b: RF 3, min.insync.replicas=3; broker 3 stopped
send("all", retries=0); send("all", retries=5)
send("1", 0); send("0", 0)
    == 3) topic pay-24b requires 3 in-sync copies (min.insync.replicas=3); stop broker 3 Created topic pay-24b. Topic: pay-24b PartitionCount: 3 ReplicationFactor: 3 Configs: min.insync.replicas=3 Topic: pay-24b Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2 Topic: pay-24b Partition: 1 Leader: 2 Replicas: 2,3,1 Isr: 2,1 Topic: pay-24b Partition: 2 Leader: 1 Replicas: 3,1,2 Isr: 1,2 acks=all (no retries): ['Broker: Not enough in-sync replicas', 'Broker: Not enough in-sync replicas'] acks=all (retries on): ['Broker: Not enough in-sync replicas', 'Broker: Not enough in-sync replicas'] acks=1 : ['P0 offset 0', 'P0 offset 1'] acks=0 : ['P0 offset None', 'P0 offset None']
    ISR shrank to 2. acks=all was refused with Not enough in-sync replicas, even with retries. acks=1 got offsets 0 and 1 from the leader alone. acks=0 got offset None: the producer never learns what happened. (In a 3-node combined lab, stopping 2 nodes would also stop the controller majority, so we raised the floor to 3 instead.)

  4. Step 4 · Recovery

    docker start k3        # wait for it to rejoin the ISR
python l24_fail.py
    == 4) start broker 3 again: acks=all works acks=all (no retries): ['P0 offset 4', 'P0 offset 5']
    With 3 copies in sync again, acks=all succeeds. Notice the offsets jumped to 4 and 5: offsets 2 and 3 were taken by the acks=0 records, which were stored even though the producer was never told.

6 Real-world use

acks choices at work

1. Payments and orders

acks=all, RF 3, min ISR 2: no acknowledged loss.

Payment→acks=all→Safe

2. Application logs

acks=1: fast, a rare loss is acceptable.

Logs→acks=1→Fast

3. Live GPS pings

acks=0: a missing ping is replaced in seconds.

GPS→acks=0→Fastest

4. Core ledgers

Plus transactions and no unclean election.

Ledger→strict→Audited

5. Maintenance windows

min ISR 2 lets brokers restart without blocking writes.

Restart→ISR 2→No outage
