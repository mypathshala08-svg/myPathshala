2 Definition

Building the pipeline

Formal definition (write this in exams)

The capstone pipeline implements consume-transform-produce with exactly-once semantics: a transactional producer writes enriched or dead-letter records and the consumer’s offsets in one atomic transaction, while downstream consumers (including the Connect sink) read with read_committed. Reference data comes from a compacted topic, records are Avro-encoded with a schema registry, and correctness is verified by reconciliation of record counts and consumer lag.

In simple words

We built the full system and counted: everything that went in came out exactly once, either as a priced order or as a problem record with a reason.

Why, how, where

Why

A design is only a claim until a working pipeline shows the counts add up. Building it end to end also reveals glue problems (serializers, isolation levels, connector configs) that single lessons hide.

the problem it solves

How

One Python script creates the topics, loads the menu, produces 3,000 Avro orders, runs a transactional processor that writes either enriched or DLQ records and commits offsets in the same transaction, then registers a Connect sink and checks counts and lag.

the mechanism

Where

A template for real projects and for your portfolio; run it on the course VM or in Colab against a local cluster (see Lesson 1.6).

in real systems

When not

The processor here is a single Python process with the menu in memory; at scale you would run several instances (consumer group) or use Kafka Streams/Flink.

Reconcile like an auditor

LEVELS> Building at three levels L1> An assembly line
  • Raw orders arrive, a worker checks and prices each, good ones go to the kitchen shelf, bad ones to the problem tray, and a copy of the shelf goes to the office. At the end of the day, shelf + tray must equal what arrived.
L2> The pieces
  • Producer: acks=all, enable.idempotence=true, AvroSerializer (schema auto-registered).
  • Processor: consumer with isolation.level=read_committed, enable.auto.commit=false; transactional producer (transactional.id); per batch: begin → produce enriched/DLQ → send_offsets_to_transaction → commit.
  • Sink: FileStreamSink with StringConverter and consumer.override.isolation.level=read_committed so it never sees aborted data.
L3> Details that matter
  • End offsets of transactional topics include commit markers, so enriched shows 1,849 offsets for 1,841 records: count records, not offsets.
  • The menu topic is compacted; the processor loads the latest value per item (idli updated 40 → 45).
  • DLQ records keep the order and add x-error and x-original-offset headers, so you can group by reason and replay after a fix.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: End offsets = record counts.
    Reality (Kafka 4.4): Markers take offsets on transactional topics.
    Proof: Step 4.
  • Myth: EOS needs Kafka Streams.
    Reality (Kafka 4.4): Plain clients can do it with transactions.
    Proof: Step 3.
  • Myth: A DLQ means data loss.
    Reality (Kafka 4.4): Records kept with reasons, replayable.
    Proof: Step 4.
EXAM> “Build an exactly-once enrichment pipeline.” Idempotent Avro producer; transactional processor (read_committed, send_offsets_to_transaction); DLQ with headers; compacted lookup topic; Connect sink with read_committed; reconcile counts; lag 0.

4 Step by step

Five steps, one script

All outputs are real: Kafka 4.4.0 (3 brokers), Schema Registry 8.1, Kafka Connect 4.4, Python confluent-kafka 2.16. Script: lab/jobs/m12/l122.py.

  1. Step 1 · Topics

    for k, t in T.items():
    cfg = {'cleanup.policy': 'compact'} if k == 'menu' else {'min.insync.replicas': '2'}
    a.create_topics([NewTopic(t, 6 if k == 'orders' else 3, 3, config=cfg)])
    == 1) topics created (orders 6 partitions, RF 3, min ISR 2; menu compacted) cap-orders partitions 6 cap-menu partitions 3 cap-orders-enriched partitions 3 cap-orders-dlq partitions 3
    Exactly the topic plan from 12.1.

  2. Step 2 · Produce Avro orders

    p = Producer({'bootstrap.servers': BS, 'acks': 'all', 'enable.idempotence': True})
for k, v in menu.items(): p.produce('cap-menu', key=k, value=str(v))
p.produce('cap-menu', key='idli', value='45')   # price update
for i in range(1, 3001): p.produce('cap-orders', key=o['city'], value=ser(o, ctx))
    == 2) producer: 3000 Avro orders (idempotent, acks=all) in 0.2 s; schema id 9
    3,000 orders in 0.2 s; the schema was registered (id 9 in our registry). About a quarter have qty 0 and a sixth order “pizza”, which is not on the menu.

  3. Step 3 · Exactly-once processor

    tp.begin_transaction()
for m in msgs:
    o = de(m.value(), ctx)
    if bad(o): tp.produce('cap-orders-dlq', …, headers=[('x-error', reason), ('x-original-offset', str(m.offset()))])
    else:      tp.produce('cap-orders-enriched', …)
tp.send_offsets_to_transaction(c.position(c.assignment()), c.consumer_group_metadata())
tp.commit_transaction()
    == 3) processor (transactions, read_committed): 1841 enriched + 1159 to DLQ = 3000 in 9.9 s menu used (compacted, latest wins): idli = 45 revenue by city: {'Delhi': 91005, 'Mumbai': 92475, 'Pune': 101310}
    Every order went to exactly one output; idli used the latest compacted price 45; revenue per city computed on the way.

  4. Step 4 · Reconcile

    end offsets · consumer-groups lag · DLQ grouped by x-error
    == 4) reconciliation and health end offsets: orders 3000, enriched 1849 (+ commit markers), dlq 1167 (+ markers) processor group lag: 0 DLQ by reason: {'unknown item': 395, 'qty must be > 0': 764}
    Lag 0. DLQ reasons: 764 quantity, 395 unknown item. End offsets include transaction markers (see warning).

  5. Step 5 · Sink

    requests.put('http://localhost:8083/connectors/cap-sink/config', json={'connector.class': 'org.apache.kafka.connect.file.FileStreamSinkConnector', 'topics': 'cap-orders-enriched', 'consumer.override.isolation.level': 'read_committed', …})
    == 5) sink: Kafka Connect writes enriched orders to a file connector RUNNING | lines in file: 1841 sample: {"id": 1, "city": "Delhi", "item": "idli", "qty": 1, "price": 45, "amount": 45}
    The connector is RUNNING and the file has 1,841 lines, one per enriched order.
