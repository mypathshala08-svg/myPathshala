1 The story

One bad order should not stop the kitchen

Before you start: 6.1 Share groups.

🤔 One broken order arrives. Your consumer throws, restarts, reads the same order, throws again… and 10,000 good orders wait behind it. How do real teams stop this?

They split failures into transient (retry later) and permanent (never works). Transient ones go to retry topics with growing delays; permanent ones and exhausted retries go to a dead letter queue (DLQ) with headers explaining why. 2 Definition

Retry topics and dead letter queues

Formal definition (write this in exams)

A retry topic holds records whose processing failed with a transient error, to be re-processed after a delay by a separate consumer; several retry topics with increasing delays form a retry ladder. A dead letter queue (DLQ) is a topic that stores records that cannot be processed (permanent errors or exhausted retries), with headers describing the failure, for inspection and replay. The pattern gives non-blocking error handling at the cost of per-key ordering.

In simple words

When an order fails, don’t keep hitting it. If the problem may pass, put it in a “try again later” topic. If it can never work, or still fails after a few tries, put it in a “problem” topic with a note. Everyone else keeps moving.

Why, how, where

Why

Kafka has no built-in “retry this one record later” for consumer groups: offsets are per partition, so one failing record stops everything behind it (head-of-line blocking).

the problem it solves

How

Catch the error, classify it, and produce the record to the next topic in a ladder (retry-5s → retry-30s → dlq) with headers (attempt, error, original topic/offset, retry-at). Separate consumers read retry topics and wait until the record is due. Commit the original offset so the main flow continues.

the mechanism

Where

Payments, orders, webhooks, any consumer calling external APIs; Kafka Connect sinks (errors.deadletterqueue.topic.name); Spring Kafka @RetryableTopic; Uber’s and many fintechs’ published designs.

in real systems

When not

Retried records lose their original order relative to newer records with the same key. If order matters per key, block that key (or the partition) instead, or park all later records of that key too.

Dissect a DLQ record

LEVELS> Error handling at three levels L1> The “problem tray”
  • A cashier with a cheque that won’t clear does not stop the queue. She puts it in a “try again at 3 pm” tray. If it fails again, it goes to the manager’s “problem” file with a note. Torn cheques go straight to the file.
L2> The pattern
  • Classify: transient (timeouts, 503, lock conflicts) vs permanent (bad JSON, schema mismatch, validation failure).
  • Retry topics with increasing delays (e.g. 5 s, 30 s, 5 min). A retry consumer reads a record, and if x-retry-at is in the future it waits (pause/seek or sleep) before processing.
  • DLQ gets permanent failures and exhausted retries. Always add headers: error class and message, attempt count, original topic, partition, offset, timestamp. Commit the original offset after producing to the next topic.
L3> Production details
  • Producing the retry record and committing the offset are two actions: use transactions (Lesson 3.5) or make processing idempotent, or a crash between them can duplicate.
  • Ordering per key breaks with non-blocking retries. Options: blocking retries with backoff for strictly ordered streams, or park a key (route all its later records to retry while one is pending).
  • Built-in options: Kafka Connect errors.tolerance=all + errors.deadletterqueue.topic.name + errors.deadletterqueue.context.headers.enable; Spring Kafka @RetryableTopic/DeadLetterPublishingRecoverer; share groups (6.1) RELEASE with delivery-count limit. Monitor DLQ size and build a replay tool that re-publishes fixed records to the main topic.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka retries failed consumer records for you.
    Reality (Kafka 4.4): Producer retries yes; consumer processing no (except share groups).
    Proof: You build the ladder.
  • Myth: Retry everything.
    Reality (Kafka 4.4): Permanent errors never succeed; DLQ them now.
    Proof: Order 3.
  • Myth: A DLQ means the record is lost.
    Reality (Kafka 4.4): It is parked with context and can be replayed.
    Proof: Step 3 headers.
EXAM> “How do you handle failures in a Kafka consumer?” Classify transient vs permanent; non-blocking retry topics with backoff and headers; DLQ with error/origin headers; commit original offset; idempotent processing; monitor and replay DLQ; ordering trade-off; Connect errors.deadletterqueue.
