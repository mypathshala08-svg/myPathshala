1 The story

Ten prices in, three prices out

Before you start: 4.1 Segments.

🤔 We wrote 10 menu price changes. A minute later Kafka kept only 3. Nothing was lost.

Kafka has two ways to clean up. Retention deletes whole old segments by time or size: we watched four segments vanish and the log start jump from 0 to 301. Compaction keeps only the latest value for each key: thali went 120 → 130 → 140 → 150 and only 150 remained, and a “deleted” dish disappeared completely.

R> Sir, if Kafka never deletes on read, won’t the disk fill up? A> It deletes by retention: whole old segments, by age or size. Orders older than 7 days simply vanish, read or not. K> But for our menu prices we only care about the current price of each dish. A> Then use compaction: Kafka keeps the latest value per key and throws away older versions. 2 Definition

Retention and compaction

Formal definition (write this in exams)

Kafka bounds log growth with a per-topic cleanup.policy. With delete, closed segments whose newest timestamp is older than retention.ms, or that exceed retention.bytes, are removed and the log start offset advances. With compact, the log cleaner rewrites closed segments to retain at least the last record for every key, deleting keys whose latest record is a tombstone (null value) after delete.retention.ms. Offsets of retained records never change.

In simple words

Retention throws away old files by age or size. Compaction keeps just the newest value for each key, like a table of current prices, and a record with an empty value deletes that key.

Why, how, where

Why

Disks are finite, and some topics represent “current state” (prices, profiles) where old versions are noise.

the problem it solves

How

delete policy: remove closed segments older than retention.ms or beyond retention.bytes. compact policy: a cleaner rewrites old segments keeping the newest record per key; null values (tombstones) delete keys.

the mechanism

Where

Event streams (orders, clicks): delete. State/changelog topics (prices, user profiles, Kafka Streams changelogs, __consumer_offsets): compact.

in real systems

When not

Compaction needs keys and does not keep history; retention deletes even unread data, so slow consumers can lose records.

Dissect a compaction

LEVELS> Clean-up at three levels L1> Two kinds of cupboards
  • Retention: a newspaper rack that throws out papers older than a week. Compaction: a price board where writing a new price wipes the old one; erasing a dish removes its line.
L2> The settings
  • cleanup.policy=delete (default): retention.ms (7 days) and/or retention.bytes (unlimited) per partition. Only closed segments are deleted; the log start offset moves forward.
  • cleanup.policy=compact: keeps the last record for every key; a record with a null value is a tombstone that deletes the key.
  • cleanup.policy=compact,delete: compact and also drop old segments by retention.
L3> The log cleaner
  • Background cleaner threads pick partitions whose “dirty” (uncleaned) share exceeds min.cleanable.dirty.ratio (0.5) and whose records are older than min.compaction.lag.ms; max.compaction.lag.ms forces cleaning.
  • The active segment is never cleaned. Tombstones are kept for delete.retention.ms (1 day) so slow consumers see the deletion, then removed.
  • Retention checks run every log.retention.check.interval.ms (5 min) on the broker; deleted files are first renamed .deleted and removed after file.delete.delay.ms (1 min).
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Retention deletes records exactly at retention.ms.
    Reality (Kafka 4.4): It deletes whole closed segments at the next check, judged by the newest record.
    Proof: Steps 1–3.
  • Myth: Compaction changes offsets.
    Reality (Kafka 4.4): Offsets stay; there are just gaps.
    Proof: Step 5: 6, 7, 8.
  • Myth: A tombstone stays forever.
    Reality (Kafka 4.4): It is removed after delete.retention.ms.
    Proof: Step 5: vada fully gone.
EXAM> “Retention vs compaction?” delete policy removes closed segments older than retention.ms or above retention.bytes (log start moves); compact keeps the latest record per key via the log cleaner, tombstones delete keys after delete.retention.ms; compact,delete combines them; active segment never cleaned.

6 Real-world use

Clean-up policies at work

1. Event streams

7–30 days retention for orders and clicks.

Events→delete→Bounded disk

2. Reference data

Latest price, stock or profile per key.

Updates→compact→Table

3. __consumer_offsets

Compacted: latest commit per group-partition.

Commits→compact→Bookmarks

4. Kafka Streams changelogs

State stores restore from compacted topics (Module 9).

Store→changelog→Restore

5. Database change streams

Compacted CDC topics hold the latest row per primary key.

DB rows→compact→Snapshot
