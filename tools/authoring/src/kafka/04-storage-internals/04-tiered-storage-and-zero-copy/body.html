1 The story

Fast reads, cheap history

Before you start: 4.1–4.3.

🤔 Our tiny lab broker read 286 MB to a consumer at about 63 MB/s. Where did the CPU go? Mostly nowhere.

Kafka is fast for boring reasons: it appends sequentially, lets the operating system cache files in memory, and for plaintext connections sends file bytes straight to the network socket without copying them through Java (zero-copy). And since Kafka 3.9, old segments can move to cheap object storage (tiered storage) so retention can be months instead of days.

2 Definition

Tiered storage and zero-copy

Formal definition (write this in exams)

Kafka achieves high throughput by appending sequentially to segment files, relying on the operating system page cache instead of an in-process cache, transferring record batches unchanged end to end, and using zero-copy transfer (FileChannel.transferTo, i.e. sendfile) from page cache to socket for plaintext connections. Tiered storage (KIP-405, production-ready since Kafka 3.9) extends a partition’s log to a remote object store through a pluggable RemoteStorageManager: closed segments are copied remotely, local copies are deleted after local.retention.ms/bytes, and fetches below the local log start are served from remote storage until retention.ms.

In simple words

Kafka is fast because it writes files in order, lets the operating system keep recent data in memory, and sends stored batches straight to the network without copying them through Java. With tiered storage, old data moves to cheap cloud storage while new data stays on the brokers.

Why, how, where

Why

Kafka must move huge volumes cheaply, and keeping months of data on broker SSDs is expensive and slows recovery.

the problem it solves

How

Sequential appends + page cache + batch-level transfer (sendfile for plaintext) keep CPU low; tiered storage uploads closed segments to object storage and serves old reads from there.

the mechanism

Where

High-throughput clusters (logs, clicks, CDC) and long-retention topics (audit, ML training data, replay).

in real systems

When not

TLS disables zero-copy (encryption needs user-space copies); tiered storage needs a plugin, does not support compacted topics, and remote reads are slower.

Dissect the read test

Tiered storage at a glance

LEVELS> Speed and storage at three levels L1> A godown and a shop counter
  • Fresh stock sits on the counter (page cache) and is handed out in sealed boxes (batches) without opening them (zero-copy). Old stock moves to a cheap far-away godown (object storage) and is fetched only when someone asks.
L2> Why Kafka is fast
  • Sequential I/O: only appends to the active segment; disks and SSDs love this.
  • Page cache: Kafka keeps little in the JVM; the OS caches recently written segments, so tailing consumers read from RAM.
  • Batches end to end: producer batch = stored batch = fetched batch, compressed once (Lesson 2.3).
  • Zero-copy: for plaintext listeners, FileChannel.transferTo (Linux sendfile) moves bytes from page cache to socket.
L3> Tiered storage (KIP-405, GA in Kafka 3.9)
  • Broker: remote.log.storage.system.enable=true plus a RemoteStorageManager plugin (open-source plugins exist for S3, GCS and Azure) and the built-in topic-based RemoteLogMetadataManager (__remote_log_metadata).
  • Topic: remote.storage.enable=true, local.retention.ms/bytes (hot data on broker) and retention.ms (total, including remote).
  • Closed segments (with indexes) are copied to remote storage; reads below the local log start are served from remote. Not supported for compacted topics.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka caches data in its own memory.
    Reality (Kafka 4.4): It relies on the OS page cache; the JVM heap stays small.
    Proof: Step 3: 1.9 GB cached outside the JVM.
  • Myth: Zero-copy always works.
    Reality (Kafka 4.4): TLS listeners disable it.
    Proof: Scenario 1.
  • Myth: Kafka cannot keep data for a year affordably.
    Reality (Kafka 4.4): Tiered storage keeps history in object storage.
    Proof: Scenario 2.
EXAM> “Why is Kafka fast?” Sequential appends, OS page cache, batching + compression end to end, zero-copy sendfile for plaintext, partition parallelism. “What is tiered storage?” KIP-405 (GA 3.9): closed segments uploaded via a RemoteStorageManager plugin; local.retention for hot data, retention.ms for total; not for compacted topics.

4 Step by step

Measure the read path

All outputs are real: Kafka 4.4.0, 3 brokers in Docker on one small VM; topic big-44, 3 partitions, RF 3. Tiered storage needs a storage plugin and object store, so it is explained, not run, here.

  1. Step 1 · Write about 290 MB

    kafka-producer-perf-test.sh --topic big-44 --num-records 300000 --record-size 1000 --throughput -1 \
  --producer-props bootstrap.servers=k1:9092 linger.ms=10 batch.size=262144
    == 1) write 300,000 records x 1 KB (about 293 MB) 300000 records sent, 48748.781280 records/sec (46.49 MB/sec), 583.40 ms avg latency, 1412.00 ms max latency, 531 ms 50th, 949 ms 95th, 1329 ms 99th, 1411 ms 99.9th.
    300,000 records of 1 KB at about 46 MB/s with acks=all to 3 replicas on our small lab machine.

  2. Step 2 · Read it back twice

    kafka-consumer-perf-test.sh --bootstrap-server k1:9092 --topic big-44 --messages 300000 --group perf-1
    == 2) read them back twice (data served from the OS page cache with sendfile) run 1: 62.9073 MB/sec, 65963.0607 msg/sec over 286.1023 MB run 2: 64.7730 MB/sec, 67919.4023 msg/sec over 286.1023 MB
    About 63–65 MB/s for a single consumer. The two runs are the same because the data was already in the page cache after writing: nothing had to come from disk.

  3. Step 3 · Where the data was

    grep -E "^(MemTotal|Cached)" /proc/meminfo
du -sh /var/lib/kafka/data/big-44-*
    == 3) broker memory: page cache holds the log MemTotal: 8214984 kB Cached: 1906992 kB 87M /var/lib/kafka/data/big-44-0 87M /var/lib/kafka/data/big-44-1 116M /var/lib/kafka/data/big-44-2
    The OS page cache held about 1.9 GB, more than the 290 MB topic. This memory is not in the Kafka JVM, which is why a Kafka heap stays small.
