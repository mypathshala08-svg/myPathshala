1 The story

Finding order 5,000 without reading 4,999

Before you start: 4.1 The commit log and segments.

🤔 A consumer asked for order 5,000 out of 10,000. Kafka found it without reading the first 4,999. How?

Kafka uses three cheap lookups: compare file names to pick the segment, jump with a sparse index to a nearby byte position, then scan a few batches. We performed each step by hand on a real partition and then let a consumer do it.

  • Why Kafka’s index has only one entry every few KB, not one per record.
  • How “give me orders from 10:00” works without a database.
  • Why reading old data is still fast.

2 Definition

Indexes and how a read works

Formal definition (write this in exams)

Each log segment has a sparse offset index (.index) mapping relative offsets to physical byte positions in the .log, and a time index (.timeindex) mapping timestamps to offsets; entries are added after every index.interval.bytes of appended data. To serve a fetch, the broker selects the segment with the greatest base offset not exceeding the target, binary-searches the memory-mapped offset index for the greatest entry not exceeding the target, and scans forward through record batches. Time-based lookups first resolve a timestamp to an offset through the time index.

In simple words

Kafka finds data in three cheap steps: pick the right file by its name, use a small table of “offset → byte position” to jump close, then read forward a little. To search by time, a second small table turns a time into an offset first.

Why, how, where

Why

Consumers start at arbitrary offsets (restarts, replays, lagging groups) and by time (“since 10:00”). Scanning gigabytes for each request would be far too slow.

the problem it solves

How

Pick the segment by base offset, binary-search its sparse offset index for the nearest entry at or before the target, then scan forward a few KB in the .log. Time lookups go through the time index first.

the mechanism

Where

Every fetch, every consumer seek, offset resets --to-datetime, retention by time, follower replication.

in real systems

When not

Indexes are rebuilt on unclean shutdown; very large index intervals mean longer scans; indexes do not help search by key or value.

Dissect the offset index

LEVELS> Indexes at three levels L1> A book’s index
  • The library has many volumes named by first page number (segments). Each volume has an index listing every 20th page (sparse). To find page 5000: pick the volume, look up the nearest listed page, flip a few pages.
L2> The two indexes
  • .index: entries (relative offset, byte position), added every index.interval.bytes (4 KB default) of appended data.
  • .timeindex: entries (timestamp, offset) giving the earliest offset with a timestamp ≥ that time.
  • Lookup: binary search for the largest entry ≤ target, then scan the log forward batch by batch.
L3> Implementation details
  • Each offset entry is 8 bytes (4-byte relative offset + 4-byte position); time entries 12 bytes. 185 entries ≈ 1.5 KB: our closed index was exactly 1,480 bytes.
  • Index files are memory-mapped; lookups touch the most recent pages first (good for tailing consumers).
  • Batches are the unit: the index points to batch starts, and fetches return whole batches; the client discards records before the requested offset.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka scans the partition to find an offset.
    Reality (Kafka 4.4): It uses file names and a sparse index, then scans only a few KB.
    Proof: Step 3.
  • Myth: Kafka indexes every record.
    Reality (Kafka 4.4): One entry per ~4 KB of data (sparse).
    Proof: Step 2: 185 entries for ~1 MiB.
  • Myth: You can look up a record by key in Kafka.
    Reality (Kafka 4.4): Only by offset or time; use a store for keys.
    Proof: Scenario 3.
EXAM> “How does Kafka find an offset quickly?” Segment chosen by base-offset file names; sparse memory-mapped .index binary search → byte position; short scan in .log. Time lookups use .timeindex (timestamp → offset). index.interval.bytes controls sparseness.

4 Step by step

Do the lookup by hand

All outputs are real: Kafka 4.4.0; topic seg-41 from Lesson 4.1 (10,000 orders, 3 segments, index.interval.bytes=4096). Script: jobs/m4/l42_index.py.

  1. Step 1 · Pick the segment by name

    bases = [int(s.split(".")[0]) for s in segment_files]
seg = bases[bisect.bisect_right(bases, 5000) - 1]
    == 1) step 1: pick the segment whose base offset is the largest <= 5000 segments: [0, 3413, 6830] -> segment 3413
    Three files; the largest base offset not above 5000 is 3413. No data was read.

  2. Step 2 · Look in the sparse index

    kafka-dump-log.sh --files /var/lib/kafka/data/seg-41-0/00000000000000003413.index
    == 2) step 2: the sparse offset index of that segment (first 6 of 185 entries) offset: 3442 position: 6022 offset: 3462 position: 12044 offset: 3482 position: 18066 offset: 3499 position: 24088 offset: 3522 position: 30293 offset: 3542 position: 36315
    185 entries cover about 1 MiB of log: one entry per ~6 KB. Each says “around this offset, the batch starts at this byte”.

  3. Step 3 · Floor entry, then scan

    floor = max(p for p in pairs if p[0] <= 5000)     # binary search in Kafka
# read the .log from that byte position
    == 3) floor entry for 5000: offset 4999 -> byte position 488000; scan forward from there baseOffset 4999 lastOffset 4999 position 488000 baseOffset 5000 lastOffset 5000 position 488356
    The index entry for 4999 points to byte 488,000. Reading from there, the very next batch is offset 5000. Kafka read a few hundred bytes instead of almost half a megabyte.

  4. Step 4 · The time index

    kafka-dump-log.sh --files /var/lib/kafka/data/seg-41-0/00000000000000003413.timeindex
    == 4) the time index: timestamp -> offset (first 4 entries) timestamp: 1793896851338 offset: 3422 timestamp: 1793896851366 offset: 3501 timestamp: 1793896851415 offset: 3600 timestamp: 1793896851438 offset: 3700
    Each entry maps a timestamp (ms) to an offset. “Orders since 10:00” becomes: find the timestamp in the time index, get an offset, then do Steps 1–3.

  5. Step 5 · A consumer does it for real

    c.assign([TopicPartition("seg-41", 0, 5000)])
m = c.poll(1.0)
    == 5) a consumer asks for offset 5000 directly got offset 5000 value {"order": "o5000", "city": "Pune", "amou ...
    The broker performed exactly this lookup and returned offset 5000 (order o5000).

6 Real-world use

Indexes at work

1. Time-based replays

Reset groups to a time in seconds.

Timestamp→.timeindex→Offsets

2. Catching up

Lagging consumers jump straight to their offset.

Commit→.index→Fetch

3. Replication

Followers fetch from the leader with the same lookup.

Follower→fetch→Copy

4. Time retention

The time index tells which segments are old.

Segments→max time→Delete

5. Audit windows

Read exactly the records between two times.

Start/end→offsetsForTimes→Slice
