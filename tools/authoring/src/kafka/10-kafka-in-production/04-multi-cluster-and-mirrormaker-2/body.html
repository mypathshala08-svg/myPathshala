2 Definition

Multi-cluster and MirrorMaker 2

Formal definition (write this in exams)

Multi-cluster architectures replicate data between independent Kafka clusters for disaster recovery, geo-locality, aggregation or migration. MirrorMaker 2 (KIP-382) is Apache Kafka’s Connect-based replicator: it copies topics (data, partitions and configs) to remote topics named by a replication policy, emits heartbeats, and records checkpoints that translate consumer-group offsets between clusters, optionally syncing them into target groups. Replication is asynchronous.

In simple words

MirrorMaker 2 keeps a copy of your topics in another cluster, a few seconds behind, and remembers roughly where each consumer group was, so after a disaster consumers can continue there (with some repeats).

Why, how, where

Why

Replication inside a cluster survives broker or zone failures, not a region outage, a cloud account loss, or a bad operator command. Some data must also live near users or in separate clusters for compliance and isolation.

the problem it solves

How

MM2 runs as Kafka Connect source connectors: MirrorSourceConnector copies records and configs into prefixed remote topics; MirrorCheckpointConnector maps group offsets using offset-sync records and can sync them into the target; MirrorHeartbeatConnector proves the link is alive.

the mechanism

Where

Disaster recovery (active-passive), aggregation from edge/regional clusters to a central one, migrations between clusters or to the cloud, and geo-local reads.

in real systems

When not

Asynchronous: the DR copy is slightly behind (RPO > 0). Offsets differ between clusters; translation is conservative, so expect re-processing. Active-active needs care to avoid loops (MM2’s prefixes prevent them).

know the limits

The topics MirrorMaker 2 creates

LEVELS> Multi-cluster at three levels L1> A photocopy in another city
  • Every page of the register is photocopied to a branch in another city, a few seconds later. If the main office burns, the branch continues, re-checking the last few pages because it is not sure which were already handled.
L2> MirrorMaker 2 pieces
  • Config: clusters = primary, dr, bootstrap servers per cluster, primary->dr.enabled, primary->dr.topics / .groups (regex). Run with connect-mirror-maker.sh mm2.properties or as connectors on a Connect cluster.
  • Remote topics get the source alias as prefix (DefaultReplicationPolicy): primary.orders-104. Internal: heartbeats, primary.checkpoints.internal, mm2-offset-syncs…, plus mm2 configs/offsets/status.
  • sync.group.offsets.enabled=true writes translated offsets into the DR cluster’s group, so a consumer can just start there.
L3> Design for failure
  • RPO = data you can lose (replication lag); RTO = time to switch (DNS, configs, consumer restarts). Measure both in drills.
  • Offset translation uses periodic offset-sync points (offset.lag.max, 100 by default), so the translated offset is at or before the true one: plan for duplicates (idempotent consumers, Lesson 3.4).
  • Failback: mirror DR → primary for the period of the outage, or use an identity replication policy for migrations. Alternatives: Confluent Cluster Linking (offset-preserving byte copy), Redpanda/WarpStream replication features, or dual writes (rarely good).

Myth vs reality: things many websites still say

  • Myth: Offsets are identical across clusters.
    Reality (Kafka 4.4): They differ; MM2 translates.
    Proof: Step 4.
  • Myth: Failover is exactly-once.
    Reality (Kafka 4.4): Translated offsets are earlier: duplicates.
    Proof: Step 5: from 406.
  • Myth: RF 3 covers region loss.
    Reality (Kafka 4.4): Only within the cluster’s zones.

4 Step by step

A failover drill

All outputs are real: primary = our 3-broker Kafka 4.4 cluster, DR = single broker dr1, MirrorMaker 2 from Kafka 4.4.0.

  1. Step 1 · Primary state

    seq 1 1000 | … kafka-console-producer.sh --topic orders-104
kafka-console-consumer.sh --topic orders-104 --group kitchen-104 --max-messages 600
    == 1) primary: topic orders-104 (1,000 orders) and group kitchen-104 (read 600) p0 committed 0 end 0 lag 0 p1 committed 0 end 0 lag 0 p2 committed 600 end 1000 lag 400
    1,000 orders (keyless, so all landed in p2), group kitchen-104 committed 600.

  2. Step 2 · Start MirrorMaker 2

    clusters = primary, dr
primary.bootstrap.servers = k1:9092,k2:9092,k3:9092
dr.bootstrap.servers = dr1:9092
primary->dr.enabled = true
primary->dr.topics = orders-104
primary->dr.groups = kitchen-104
primary->dr.sync.group.offsets.enabled = true
    == 2) DR cluster after MirrorMaker 2 started: topics heartbeats mm2-configs.primary.internal mm2-offsets.primary.internal mm2-status.primary.internal primary.checkpoints.internal primary.heartbeats primary.orders-104
    One command: connect-mirror-maker.sh mm2.properties. MM2 created the remote topic and its internal topics on DR.

  3. Step 3 · The copy

    kafka-get-offsets.sh --bootstrap-server dr1:9092 --topic primary.orders-104
    == 3) the remote topic has the same records primary.orders-104:0:0 primary.orders-104:1:0 primary.orders-104:2:1000 NO_HEADERS order-1 NO_HEADERS order-2
    All 1,000 records, same partition layout.

  4. Step 4 · Translated offset

    kafka-consumer-groups.sh --bootstrap-server dr1:9092 --describe --group kitchen-104
    == 4) the group offset, translated and synced on DR primary.orders-104 p2 committed 405 end 1000 lag 595
    The group exists on DR at 405, not 600: translation steps back to the last offset-sync point it can prove.

  5. Step 5 · Failover

    kafka-console-consumer.sh --bootstrap-server dr1:9092 --topic primary.orders-104 --group kitchen-104
    == 5) failover: a consumer on DR with the same group continues, no re-read from 0 first records read on DR: order-406 first records read on DR: order-407 first records read on DR: order-408
    The consumer continued at order-406: no restart from 0, but orders 406–600 are processed a second time.

  6. Step 6 · Still mirroring

    seq 1001 1010 | … producer on primary; sleep 12; kafka-get-offsets on dr1
    == 6) new orders on primary keep flowing to DR primary.orders-104:0:0 primary.orders-104:1:10 primary.orders-104:2:1000
    Ten new orders arrived on DR within seconds (this time in p1).
