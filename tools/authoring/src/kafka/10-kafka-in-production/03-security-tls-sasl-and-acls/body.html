1 The story

Locking down the cluster

Before you start: 1.3 Architecture.

🤔 Out of the box, anyone who can reach port 9092 can read every payment and delete every topic. How many locks does a production Kafka need?

Three: TLS (nobody can read or fake traffic), SASL (who are you?) and ACLs (what may you do?). We built a broker that only accepts SASL_SSL with SCRAM, and tried four ways in: plaintext timed out, a wrong password was rejected, an untrusted certificate failed the handshake, and only the admin got through. Then billing could write but not read, kitchen could read but not write, and neither could use another group.

  • Encryption with TLS: keystores, truststores, certificates.
  • Authentication with SASL: SCRAM, OAUTHBEARER, mTLS, GSSAPI.
  • Authorization with ACLs and least privilege.

An auditor asks whether the kitchen app can read TiffinGo’s payments. On the current cluster, every app can read and write everything.

K> Sir, the auditor asks: can the kitchen app read payment data? Honestly… yes, everyone can read everything. A> Then we add three locks. TLS so nobody can sniff the wire, SASL so every app has a name, ACLs so each name gets only what it needs. R> Will apps need code changes? A> Mostly configuration: a few client properties. 2 Definition

Security: TLS, SASL and ACLs

Formal definition (write this in exams)

Kafka security has three layers configured per listener: encryption and server identity with TLS; client authentication with SASL mechanisms (SCRAM, OAUTHBEARER, GSSAPI, PLAIN) or TLS client certificates, which yields a principal; and authorization by an authorizer that evaluates ACLs (principal, host, operation, resource, pattern, allow/deny) for every request. Quotas additionally limit resource use per principal or client.

In simple words

Encrypt the connection (TLS), make every app log in (SASL), and give each login only the permissions it needs (ACLs). Nothing else changes for apps except a few connection settings.

Why, how, where

Why

Kafka carries payments, personal data and business events. Without security, any app (or attacker) on the network can read, write or delete them, and audits fail.

the problem it solves

How

Each listener has a security protocol: PLAINTEXT, SSL, SASL_PLAINTEXT or SASL_SSL. TLS encrypts and proves the broker’s identity with certificates; SASL proves the client’s identity and gives a principal (User:billing); the authorizer (StandardAuthorizer in KRaft) checks ACLs for every request.

the mechanism

Where

Every shared or regulated cluster; multi-tenant platforms; managed services (which force SASL_SSL or IAM/OAuth).

in real systems

When not

TLS costs some CPU and disables zero-copy for TLS traffic. Certificates expire; passwords leak if stored in plain files. ACLs need maintenance as apps change.

Dissect an ACL

LEVELS> Security at three levels L1> A bank branch
  • Tinted, locked glass (TLS) so nobody sees inside; ID check at the door (SASL); and each employee’s card opens only certain rooms (ACLs). The manager has a master key (super user) used rarely.
L2> Configuration
  • Broker: listeners=SECURE://:9095, listener.security.protocol.map=SECURE:SASL_SSL, sasl.enabled.mechanisms=SCRAM-SHA-512, ssl.keystore.*, ssl.truststore.*, authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer, super.users.
  • Client: security.protocol=SASL_SSL, sasl.mechanism=SCRAM-SHA-512, sasl.jaas.config=… username password, ssl.truststore.location.
  • SCRAM users: kafka-configs --alter --entity-type users --add-config SCRAM-SHA-512=[password=…]; the first admin is added at format time with kafka-storage format --add-scram.
L3> Choices and details
  • Mechanisms: SCRAM-SHA-256/512 (passwords stored salted in metadata), OAUTHBEARER (tokens from an identity provider, common in clouds), mTLS (certificate = identity), GSSAPI/Kerberos (enterprises), PLAIN (only over TLS, with external checks).
  • ACLs: principal, host, operation (Read, Write, Create, Describe, Alter…), resource (Topic, Group, Cluster, TransactionalId), pattern (literal or prefixed), allow/deny. Deny wins. Consumers need Read on the topic and the group.
  • Keep secrets out of files with config providers, rotate certificates before expiry, and use quotas (produce/fetch bytes per second, request %) to protect tenants from each other.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: TLS alone is enough.
    Reality (Kafka 4.4): TLS encrypts; SASL and ACLs decide who does what.
    Proof: Step 4.
  • Myth: A consumer needs only topic Read.
    Reality (Kafka 4.4): Also Read on its group.
    Proof: Step 6.
  • Myth: SCRAM sends the password.
    Reality (Kafka 4.4): Challenge/response; stored salted.
    Proof: Peel.
EXAM> “How do you secure Kafka?” SASL_SSL listeners: TLS for encryption/identity (keystore/truststore, CA), SASL SCRAM/OAUTHBEARER/mTLS for authentication, StandardAuthorizer ACLs for least privilege (topic + group for consumers), super users minimal, quotas, secret providers, cert rotation.

4 Step by step

Build a locked broker

All outputs are real: a separate Kafka 4.4.0 broker (sec1) with a SASL_SSL listener, SCRAM-SHA-512 and StandardAuthorizer.

  1. Step 1 · Certificates

    keytool -genkeypair -alias ca … -ext bc:c          # lab CA
keytool -genkeypair -alias sec1 … -ext SAN=dns:sec1   # broker key
keytool -certreq … | keytool -gencert -alias ca …     # CA signs it
keytool -importcert … -keystore trust.p12             # clients trust the CA
    == 1) the broker certificate (signed by our lab CA) Owner: CN=sec1 Issuer: CN=TiffinGo Lab CA Valid from: Fri Nov 06 06:36:26 GMT 2026 until: Sat Nov 06 06:36:26 GMT 2027 DNSName: sec1
    The broker certificate names the host (SAN dns:sec1) and is signed by our CA. Clients trust the CA, not each broker.

  2. Step 2 · Four ways in

    security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-512
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required username="admin" password="admin-secret";
ssl.truststore.location=/s/trust.p12
    == 2) three wrong ways in, one right way a) plaintext client on the TLS port: TimeoutException: The AdminClient thread has exited b) wrong password: SaslAuthenticationException: Authentication failed during authentication due to invalid credentials with SASL mechanism SCRAM-SHA-512 c) client that does not trust the CA: SslAuthenticationException: SSL handshake failed (certificate not signed by a CA the client trusts) d) admin with SCRAM over TLS: sec1:9095 (id: 1 rack: null isFenced: false) -> (
    Plaintext to a TLS port just times out; a wrong password fails SASL; a client that trusts another CA fails the TLS handshake; the right config works.

  3. Step 3 · Users and a topic

    kafka-configs.sh --bootstrap-server sec1:9095 --command-config admin.properties --alter --entity-type users --entity-name billing --add-config "SCRAM-SHA-512=[iterations=8192,password=billing-secret]"
    == 3) create SCRAM users and a topic (as admin) Completed updating config for user billing. Completed updating config for user kitchen. SCRAM credential configs for user-principal 'admin' are SCRAM-SHA-512=iterations=4096 SCRAM credential configs for user-principal 'kitchen' are SCRAM-SHA-512=iterations=8192 SCRAM credential configs for user-principal 'billing' are SCRAM-SHA-512=iterations=8192 Created topic payments-103.
    Credentials are stored salted in the KRaft metadata, never as plain passwords.

  4. Step 4 · Denied by default

    echo … | kafka-console-producer.sh --bootstrap-server sec1:9095 --producer.config billing.properties --topic payments-103
    == 4) no ACLs yet: everyone except admin is denied billing write: TopicAuthorizationException: Not authorized to access topics: [payme
    With an authorizer and no ACLs, only super users can act.

  5. Step 5 · Least privilege

    kafka-acls.sh … --add --allow-principal User:billing --operation Write --operation Describe --topic payments-103
kafka-acls.sh … --add --allow-principal User:kitchen --operation Read --topic payments-103 --group kitchen-103
    == 5) grant least privilege Current ACLs for resource `ResourcePattern(resourceType=TOPIC, name=payments-103, patternType=LITERAL)`: (principal=User:billing, host=*, operation=WRITE, permissionType=ALLOW) (principal=User:billing, host=*, operation=DESCRIBE, permissionType=ALLOW) (principal=User:kitchen, host=*, operation=READ, permissionType=ALLOW) Current ACLs for resource `ResourcePattern(resourceType=GROUP, name=kitchen-103, patternType=LITERAL)`: (principal=User:kitchen, host=*, operation=READ, permissionType=ALLOW)
    Billing may write; kitchen may read, using only the group kitchen-103.

  6. Step 6 · Try again

    billing writes · kitchen reads · kitchen writes · kitchen uses another group
    == 6) try again billing write: exceptions = 0 kitchen read: {"order":7,"amount":80} kitchen write: ClusterAuthorizationException: Cluster authorization failed. (no Write ACL, so its idempotent producer cannot even get a producer id) kitchen with another group: GroupAuthorizationException: Not authorized to access group: other-group
    Exactly as granted. Kitchen’s write failed even earlier, at ClusterAuthorization: its idempotent producer could not get a producer id without Write on the topic.
