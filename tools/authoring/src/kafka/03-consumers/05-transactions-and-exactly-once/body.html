2 Definition

Transactions and exactly-once

Formal definition (write this in exams)

A Kafka transaction lets a producer with a transactional.id write records to multiple partitions and commit consumer offsets atomically: either all writes become visible to read_committed consumers, or none do. A transaction coordinator persists transaction state in __transaction_state and, on commit or abort, writes control markers to each involved partition. Combined with the idempotent producer, transactions provide exactly-once semantics for consume-transform-produce applications within Kafka, and the producer epoch fences zombie instances sharing a transactional.id.

In simple words

A transaction groups several writes (and the “I have read up to here” offset) into one unit. Kafka writes them, then stamps them approved or cancelled. Careful readers see only approved data. An old copy of your app can’t sneak in writes after a new copy starts.

Why, how, where

Why

A processor that reads payments and writes ledger entries must never write the entries without moving its offset, or move the offset without the entries.

the problem it solves

How

A transactional producer writes records to many partitions and the consumer offsets, then commits or aborts all of them together; read_committed consumers only see committed data.

the mechanism

Where

Kafka Streams with exactly_once_v2, Flink/Spark Kafka sinks, ledger and balance pipelines, CDC fan-out.

in real systems

When not

It covers Kafka. Writes to a database or an email gateway from the same code are not part of the transaction.

Dissect the markers

LEVELS> Transactions at three levels L1> A bank transfer slip
  • The clerk writes debit and credit in pencil (records written), then either inks them with a stamp “APPROVED” (commit marker) or stamps “CANCELLED” (abort marker). Auditors (read_committed) read only approved entries.
L2> The API
  • Set a stable transactional.id; call init_transactions() once.
  • Loop: begin_transaction() → produce() to any topics → send_offsets_to_transaction(offsets, consumer_group_metadata) → commit_transaction() (or abort_transaction() on error).
  • Consumers set isolation.level=read_committed (librdkafka default) to see only committed records; Java consumers default to read_uncommitted.
L3> Under the hood
  • A transaction coordinator (leader of a partition of __transaction_state) tracks state: Ongoing → PrepareCommit/PrepareAbort → CompleteCommit/CompleteAbort.
  • On commit/abort it writes control batches (markers) into every partition the transaction touched. Each marker takes an offset, so offsets have gaps for consumers.
  • read_committed consumers read only up to the last stable offset (LSO): an open transaction holds back readers until it ends (bounded by transaction.timeout.ms, 60 s).
  • init_transactions() bumps the producer epoch; an older instance with the same transactional.id is fenced. Kafka 4.x adds transaction protocol v2 (KIP-890, transaction.version=2) for stronger fencing per transaction.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Aborted records are deleted.
    Reality (Kafka 4.4): They stay on disk; read_committed consumers skip them.
    Proof: Step 2: read_uncommitted still sees B1, B2.
  • Myth: Offsets are always consecutive for consumers.
    Reality (Kafka 4.4): Transaction markers take offsets, so there are gaps.
    Proof: Step 2: offsets 3 and 6 never delivered.
  • Myth: Exactly-once needs no consumer setting.
    Reality (Kafka 4.4): Downstream consumers must use read_committed (Java default is read_uncommitted).
    Proof: Types table.
EXAM> “How does Kafka achieve exactly-once?” Idempotent producer + transactions: begin, produce to many partitions, send_offsets_to_transaction, commit/abort; coordinator writes COMMIT/ABORT markers; read_committed consumers read up to the LSO; transactional.id epoch fences zombies. Kafka Streams: processing.guarantee=exactly_once_v2.

Commit, abort, fence

All outputs are real: Kafka 4.4.0, 3 brokers; Python confluent-kafka 2.16.1; topic ledger-35 with 1 partition. Scripts: jobs/m3/l35_tx.py, l35_fence.py.

  1. Step 1 · Three transactions: commit, abort, commit

    p = Producer({"bootstrap.servers": BS, "transactional.id": "ledger-writer-1"})
p.init_transactions()
p.begin_transaction(); [p.produce(T, value=f"A{i} ...") for i in (1, 2, 3)]; p.commit_transaction()
p.begin_transaction(); [p.produce(T, value=f"B{i} ...") for i in (1, 2)]; p.flush(); p.abort_transaction()

    == 1) transaction A: 3 entries, committed committed == 2) transaction B: 2 entries, aborted (e.g. payment gateway said no) aborted == 3) transaction C: 1 entry, committed committed
    Transaction B was flushed to the broker before we aborted, so its records really are on disk. The question is who sees them.

    The transaction coordinator (broker 1 here) knows the transactional.id, its producer id 8000 and the last state, CompleteCommit.

  5. Step 5 · Fencing a zombie

    old = Producer({..., "transactional.id": "alert-writer"}); old.init_transactions(); old.begin_transaction(); old.produce(...)
new = Producer({..., "transactional.id": "alert-writer"}); new.init_transactions()   # epoch bumped
old.commit_transaction()
    == 7) zombie fencing with the same transactional.id old instance: transaction open, epoch assigned new instance: init_transactions() -> epoch bumped, old transaction aborted old instance commit: Failed to end transaction: Local: This instance has been fenced by a newer instance
    The new instance’s init_transactions() bumped the epoch and aborted the old open transaction. The old instance’s commit failed: “fenced by a newer instance”. A stuck pod can never write half-finished results after its replacement starts.
