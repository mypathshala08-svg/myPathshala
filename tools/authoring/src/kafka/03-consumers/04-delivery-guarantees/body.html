2 Definition

Delivery guarantees

Formal definition (write this in exams)

Delivery semantics describe how many times a record’s processing takes effect in the presence of failures. At-most-once: offsets are committed before processing, so a failure may skip records. At-least-once: offsets are committed after processing, so a failure may repeat records. Exactly-once: each record’s effect occurs once; in Kafka it is provided for read-process-write pipelines within Kafka by idempotent producers and transactions with read_committed consumers, and for external systems by idempotent writes or by atomically storing results with offsets.

In simple words

If you save progress before doing the work, a crash can lose work. If you save after, a crash can repeat work. To get “once”, make repeats harmless or save the work and the progress together.

Why, how, where

Why

Crashes happen between “do the work” and “save progress”. Which one you do first decides whether you can lose or repeat work.

the problem it solves

How

Commit first → at-most-once. Work first, then commit → at-least-once. Make the work idempotent, or put output and offsets in one transaction → effectively exactly-once.

the mechanism

Where

Payments and invoices (at-least-once + dedup), metrics (at-most-once is fine), Kafka-to-Kafka pipelines (transactions).

in real systems

When not

No setting gives exactly-once for side effects outside Kafka (an SMS, an HTTP call) by itself: the external action must be idempotent.

Dissect the duplicate

LEVELS> Delivery guarantees at three levels L1> Ticking the register
  • At-most-once: tick “done” first, then deliver. If you faint in between, the parcel is never delivered. At-least-once: deliver first, then tick. If you faint, someone delivers it again.
L2> In consumer code
  • At-most-once: commit, then process. Crash after commit → those records are skipped.
  • At-least-once: process, then commit (the usual choice; also what auto-commit gives in the normal case, though auto-commit can drift into at-most-once if processing is async).
  • Exactly-once (effectively): at-least-once + idempotent processing (dedup by a business id, upserts), or Kafka transactions for Kafka-to-Kafka pipelines.
L3> Where each layer stands
  • Producer → broker: idempotence removes retry duplicates (2.5).
  • Consume → process → produce within Kafka: transactions commit output records and input offsets atomically; downstream consumers use isolation.level=read_committed (3.5). Kafka Streams enables this with processing.guarantee=exactly_once_v2.
  • Kafka → external system (DB, email): needs an idempotent sink or storing offsets in the same database transaction as the result.
/LEVELS

Myth vs reality: things many websites still say

  • Myth: Kafka is exactly-once by default.
    Reality (Kafka 4.4): Default consumers are at-least-once (or at-most-once by mistake).
    Proof: Steps 2–3: 5 lost or 5 doubled.
  • Myth: Exactly-once means the SMS is sent once.
    Reality (Kafka 4.4): It covers Kafka outputs and offsets, not external calls.
    Proof: Scenario 2.
  • Myth: At-least-once means lots of duplicates.
    Reality (Kafka 4.4): Only the uncommitted work since the last commit repeats.
    Proof: Step 3: exactly 5 (21–25).
EXAM> “Explain at-most/at-least/exactly-once in Kafka.” Commit before processing = at-most-once; process then commit = at-least-once; exactly-once = idempotent producer + transactions + read_committed (Kafka to Kafka) or idempotent/atomic sinks for external systems.

4 Step by step

Crash a worker, count the invoices

All outputs are real: Kafka 4.4.0; Python confluent-kafka; topic with 50 invoices; batches of 10; the worker hard-crashes (os._exit) after 25 invoices, then a second run continues. Scripts: jobs/m3/l34_worker.py, l34_run.py.

  1. Step 1 · The worker

    while idle < 20:
    msgs = c.consume(10, 1.0)
    if mode == "atmost": c.commit(asynchronous=False)      # commit BEFORE processing
    for m in msgs:
        out.write(m.value().decode() + "\n")                # "send the invoice"
        done += 1
        if done == crash_after: os._exit(1)                 # crash
    if mode == "atleast": c.commit(asynchronous=False)     # commit AFTER processing
    One worker, two modes. It reads batches of 10, writes each invoice to a log file (our “sent invoices”), and crashes hard after the 25th. Then a new run of the same group continues.

  2. Step 2 · At-most-once

    python l34_run.py      # mode atmost: 50 invoices, crash after 25, restart
    == at-most-once: 50 invoices, worker crashes after 25, then restarts first run exit code 1, second run exit code 0 invoices processed: 45 unique: 45 missing: 5 processed twice: 0 missing: ['invoice-26', 'invoice-27', 'invoice-28', 'invoice-29', 'invoice-30'] duplicates: []
    Batch 3 (21–30) was committed before processing. The crash happened at 25, so on restart the group began at 30: invoices 26–30 were never sent. 45 of 50.

  3. Step 3 · At-least-once

    python l34_run.py      # mode atleast
    == at-least-once: 50 invoices, worker crashes after 25, then restarts first run exit code 1, second run exit code 0 invoices processed: 55 unique: 50 missing: 0 processed twice: 5 missing: [] duplicates: ['invoice-21', 'invoice-22', 'invoice-23', 'invoice-24', 'invoice-25']
    The last commit was after batch 2 (offset 20). On restart the group re-read 21–30: invoices 21–25 were sent twice, none lost. 55 sends, 50 unique.
