1 The story

Five people, one login, deleted photos

Before you start: Module 1 (an admin user with MFA, CloudShell).

🤔 On a Monday, TiffinGo’s menu photos vanished from S3. Five people used the same “admin” login. Nobody could say who deleted them.

The fix was not a better password. It was IAM — Identity and Access Management: one identity per person, people placed in groups, each group given only the permissions its job needs, and roles for software. This lesson explains users, groups, roles and policies from zero, shows exactly how AWS decides Allow or Deny, and on your own account (or in the simulator) you will read a real policy, give an intern read-only access to one folder, prove what he can and cannot do, and use a role’s temporary credentials.

  • Who (identity) + what (action) + on which thing (resource) = a permission.
  • Default answer is No; an explicit Deny beats any Allow.
  • People get users/SSO; software gets roles — never keys in code.

TiffinGo’s menu photos were deleted. Five people shared the admin login, so CloudTrail could only say “admin did it”. Arjun Sir rebuilt access with IAM: one identity per person, groups by job, roles for software.

R> Sir, we changed the admin password. Is that enough? A> No. Five people still share it. AWS logs show “admin” deleted the photos — not which person. K> So everyone gets their own login? A> Yes — an IAM user each (or, better, single sign-on). Then put people in groups: Admins, Developers, Interns. Attach permissions to groups, not to people. R> And our order app that reads from S3 — does it get a login too? A> Software gets a role — like a visitor badge with temporary keys that expire. No passwords, no keys in code. Let’s see how AWS decides yes or no.
2 Definition

IAM: users, groups, roles and policies

Formal definition (write this in exams)

AWS Identity and Access Management (IAM) is the global, no-cost service that controls authentication and authorisation in an AWS account: it defines principals (IAM users, groups of users, and roles assumed for temporary access) and evaluates policies — JSON documents allowing or denying actions on resources under conditions — for every request, denying by default and letting an explicit deny override any allow.

In simple words

IAM is AWS’s security desk: it gives people and programs identities, and written rules decide exactly what each one may do.

Say it in an interview

30-second answer you can speak:

  • “IAM authenticates and authorises every AWS request: users or SSO for people, roles with temporary credentials for applications, and JSON policies with least privilege; default deny, explicit deny wins.”
  • “For an app on EC2 reading S3 I attach a role through an instance profile with a customer managed policy scoped to the exact bucket prefix — no keys anywhere.”

3 The big picture

IAM: who, what, on which resource

New to computers? Start here. Think of AWS as a big office building. IAM is the security desk. It gives every person an ID card (user), puts people in departments (groups), hands visitors temporary badges (roles), and keeps a rulebook of which doors each card opens (policies). If the rulebook does not say “yes”, the door stays shut.

Jargon buster:

  • Identity / principal — who is asking (a person or a program)
  • Permission — a “yes” for one action on one thing
  • Policy — a written list of permissions (in JSON text)
  • Action — what they want to do, e.g. read a file, delete a file
  • Resource — the thing, e.g. one storage bucket
  • ARN — the full address of a thing in AWS

IAM answers one question for every request to AWS: is this principal allowed to do this action on this resource right now?

Type 1 · IAM user

Definition (say it in an interview): An IAM user is an identity inside one AWS account that represents a person or application, with long-term credentials — a console password and/or up to two access keys — and permissions from policies attached directly or through groups.

In plain words (no jargon): A login for one person inside the account.

Analogy: An employee ID card: one per person, with their name on it.

How it works internally, step by step

  1. Name. Unique in the account.
  2. Password. Console sign-in.
  3. MFA. Second factor.
  4. Groups. Up to 10 per user.
  5. Keys. Max 2; avoid.

Words used above, in simple terms: access key = long-term CLI/SDK credential (AKIA…) · console password = for the web console · credential report = CSV of all users and their credentials

Type 2 · IAM group

Definition (say it in an interview): An IAM group is a collection of IAM users; policies attached to the group apply to every member, so permissions are managed by job function. Groups cannot be nested, cannot sign in, and cannot be named as a principal in a resource policy.

In plain words (no jargon): A team folder for users that share the same permissions.

Analogy: A department: join Accounts and you get the Accounts keys; move to Sales and you swap keys.

How it works internally, step by step

  1. Name. By job.
  2. Policies. Up to 10 managed.
  3. Members. Users only.
  4. Change. Edit once, applies to all.
  5. Audit. List group members.

Words used above, in simple terms: job function = what a person does · membership = being in a group · inheritance = members get the group’s policies

Type 3 · IAM role

Definition (say it in an interview): An IAM role is an identity with permission policies but no long-term credentials; trusted principals (users, AWS services such as EC2 or Lambda, other accounts, federated users) assume it through AWS STS and receive temporary credentials that expire (15 minutes to 12 hours).

In plain words (no jargon): A temporary set of permissions that people or programs can borrow.

Analogy: A visitor badge at reception: borrowed for a while, returned automatically at the end of the day.

How it works internally, step by step

  1. Trust policy. Who may assume.
  2. Permissions. What it can do.
  3. Assume. sts:AssumeRole.
  4. Session. 1 h default, up to 12 h.
  5. Audit. CloudTrail shows who assumed.

Words used above, in simple terms: STS = Security Token Service · trust policy = resource policy on the role · session = the temporary credentials period

Type 4 · AWS managed policy

Definition (say it in an interview): An AWS managed policy is a standalone policy created and maintained by AWS (ARN arn:aws:iam::aws:policy/…), such as AdministratorAccess, ReadOnlyAccess or AmazonS3ReadOnlyAccess, including job-function policies; you can attach but not edit it.

In plain words (no jargon): Ready-made permission lists written by AWS.

Analogy: A ready-made uniform from the shop: fits most people, but you cannot tailor it.

  4. Watch. Version changes.

Words used above, in simple terms: job-function policy = e.g. Billing, DatabaseAdministrator · policy version = AWS keeps versions · ARN account “aws” = marks AWS managed

Type 5 · Customer managed policy

Definition (say it in an interview): A customer managed policy is a standalone policy you create in your account, with exactly the actions, resources and conditions you choose; it keeps up to five versions and can be attached to many users, groups and roles — the main tool for least privilege.

In plain words (no jargon): Your own permission list, written exactly for a job.

Analogy: A tailored uniform: made for your job, reused by everyone with the same job.

  2. Validate. Access Analyzer checks.
  3. Version. Up to 5.
  4. Attach. Many identities.
  5. Review. Last-accessed info.

Words used above, in simple terms: least privilege = only what is needed · policy validation = Access Analyzer finds errors and risks · default version = the active version

Type 6 · Inline policy

Definition (say it in an interview): An inline policy is embedded directly in a single user, group or role and has a strict one-to-one relationship with it; it is deleted with the identity and cannot be attached elsewhere — useful when a permission must never be accidentally reused.

In plain words (no jargon): A permission list stuck to one identity only.

Analogy: A note written on one person’s ID card: it travels with that card only.

How it works internally, step by step

  1. Create. On the identity.
  2. Size. Small limits.
  3. Review. Per identity.
  4. Delete. With identity.
  5. Prefer. Managed policies.

Words used above, in simple terms: embedded = part of the identity · one-to-one = one policy, one identity · policy size limit = inline ones are smaller

Type 7 · Resource-based policy

Definition (say it in an interview): A resource-based policy is attached to a resource — an S3 bucket policy, SQS queue policy, KMS key policy, Lambda resource policy or a role’s trust policy — and includes a Principal element naming who may act on it, enabling cross-account and service access and resource-wide rules such as “deny any request not using HTTPS”.

In plain words (no jargon): A rulebook stuck on the resource itself.

Analogy: A notice on a room door: “Only Accounts staff and the auditor may enter; no entry without ID.”

How it works internally, step by step

  1. Attach. Resource.
  2. Principal. Who.
  3. Action/Resource. What.
  4. Condition. HTTPS, IP, org…
  5. Evaluate. Together with identity policies.

Words used above, in simple terms: Principal = the who in a resource policy · bucket policy = resource policy on S3 · key policy = resource policy on a KMS key

5 How it works, step by step

How IAM decides: Allow or Deny

One request, evaluated step by step.

Animated

How IAM decides: Allow or Deny

Kabir the intern tries to delete the menu file, then to read it. Watch IAM evaluate both requests.

Policy evaluation 6 steps
Watch what happens
  1. Step 1 · Authenticate — the request is signed; AWS confirms it really comes from the IAM user intern-kabir.
  2. Step 2 · Collect every policy — policies attached to the user and his groups, the bucket’s own policy, and any permissions boundary or organisation SCP.
  3. Step 3 · Look for an explicit Deny — one Deny anywhere ends the evaluation with “No”, whatever Allows exist. There is none here.
  4. Step 4 · Look for an Allow — the Interns policy allows only GetObject and ListBucket. Nothing allows DeleteObject, so the answer is an implicit deny — AWS’s default.
  5. Step 5 · AccessDenied — the CLI shows AccessDenied with the action name; the menu file is untouched and CloudTrail records the failed attempt.
  6. Step 6 · The same file, a different action — GetObject is allowed by the group policy and nothing denies it, so reading works. Give people exactly what their job needs.
6 Explained part by part

Six parts of a policy statement

Effect

What it is: Allow or Deny.

Why it exists: Deny always wins.

Where it is used: "Effect": "Allow"

Action

What it is: service:Operation.

Why it exists: What is permitted.

Where it is used: "s3:GetObject", wildcards s3:Get*

Resource

What it is: ARN(s).

Why it exists: On which thing.

Where it is used: arn:aws:s3:::menu/notes/*

Principal

What it is: who (resource policies only).

Why it exists: Who may act on this resource.

Where it is used: {"AWS": "arn:aws:iam::111122223333:root"}

Condition

What it is: when/how (optional).

Why it exists: MFA, IP, HTTPS, tags, time.

Where it is used: "Bool": {"aws:SecureTransport": "false"}

Sid / Version

What it is: statement ID; language version.

Why it exists: Readability; always "2012-10-17".

Where it is used: "Version": "2012-10-17"

Myth vs reality: things many websites still say

  • Myth: A strong shared password is fine.
    Reality: Sharing removes accountability.
    Proof: Situation 1.
  • Myth: Allow beats Deny if it is more specific.
    Reality: Explicit Deny always wins.
    Proof: Animation.
  • Myth: Roles are only for AWS services.
    Reality: People and other accounts assume roles too.
    Proof: Type 3.
7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: IAM is like the security guard of a big office. Every person gets their own ID card, and a rule book says which rooms each card opens. If the rule book does not say “yes”, the door stays locked.

Try: Write down three “people” in a small shop (owner, cashier, helper) and what each should be able to do with the cash box (open, count, take out).

Check yourself: If the rule book says nothing about a door, is it open or locked?

Locked. In AWS the default answer is always “no” (implicit deny).

Level 1 · Beginner first steps on AWS

Understand: A user is a login for one person; a group is a team; a policy lists allowed actions; a role is a temporary badge for programs.

Try: Do Step 1 of the hands-on (read AmazonS3ReadOnlyAccess) and point to Effect, Action and Resource.

Check yourself: Should you give each person their own user or share one?

Their own — so every action can be traced to a person and removed without affecting others.

Level 2 · Intermediate can do it alone

Understand: Write a customer managed policy scoped to one bucket folder; attach it to a group; prove allowed and denied actions with the Policy Simulator.

Try: Do Step 2 of the hands-on and change the folder to finance/ — check the results flip.

Check yourself: Which ARN does s3:ListBucket need — bucket or object?

The bucket ARN (arn:aws:s3:::name). Get/Put/DeleteObject need object ARNs (arn:aws:s3:::name/key).

Level 3 · Advanced designs for others

Understand: Combine identity and resource policies; use conditions (aws:SecureTransport, aws:MultiFactorAuthPresent, aws:SourceIp, tags); design roles for apps and cross-account access.

Try: Add a Deny statement to S3ReadMenu that blocks requests without MFA; test with the simulator’s context keys.

Check yourself: Cross-account: Account B’s user has an Allow, but Account A’s bucket policy says nothing. Result?

Denied. Cross-account access needs an Allow on both sides (identity policy in B and resource policy in A).

Level 4 · Expert architect / interviewer

Understand: Design guard-rails at scale: permissions boundaries for delegated admins, SCPs and RCPs in Organizations, ABAC with tags, Access Analyzer unused-access findings, and Identity Center permission sets.

Try: Write an SCP that denies all actions outside ap-south-1 and ap-south-2 except global services, and explain the exceptions you needed.

Check yourself: An SCP allows s3:*, the identity policy allows s3:GetObject, a boundary allows only ec2:*. Can the user read S3?

No. The effective permission is the intersection of SCP, boundary and identity policy; the boundary has no S3, so S3 is denied.

8 Deep dive

A complete policy line by line; identity + resource policies together

A complete policy, line by line

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyMenuFolder",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::tiffingo-menu",
      "Condition": {"StringLike": {"s3:prefix": ["menu/*"]}}
    },
    {
      "Sid": "ReadMenuObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::tiffingo-menu/menu/*"
    },
    {
      "Sid": "NoPlainHttp",
      "Effect": "Deny",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::tiffingo-menu", "arn:aws:s3:::tiffingo-menu/*"],
      "Condition": {"Bool": {"aws:SecureTransport": "false"}}
    }
  ]
}
  • ListBucket applies to the bucket ARN; GetObject applies to object ARNs (bucket/key). Mixing them up is the #1 S3 policy bug.
  • s3:prefix limits what folder names can be listed.
  • The Deny statement wins over any Allow when the request is not HTTPS.

9 Under the hood

Full evaluation logic, boundaries, SCPs, STS, propagation, limits

How IAM really evaluates a request — the full logic professionals use to debug AccessDenied.

1 · The complete evaluation order (single account)

  1. Explicit Deny in any applicable policy → denied. Stop.
  2. Organizations SCPs / RCPs (if the account is in an organisation): the action must be allowed by every SCP level and RCP; otherwise denied.
  3. Resource-based policy that allows the principal → can allow (same account).
  4. Identity-based policy must allow the action…
  5. …and, if set, the permissions boundary must allow it too…
  6. …and, for assumed-role sessions, any session policy must allow it.
  7. Nothing allowed it → implicit deny.

Effective permissions are therefore an intersection of guard-rails (SCP, boundary, session) with the union of grants (identity + resource policies).

2 · Guard-rails that only limit, never grant

Guard-railSet onPurpose
Permissions boundarya user or rolemaximum permissions — lets a team lead create roles without escalating privilege
Service control policy (SCP)OU or account in Organizationsmaximum for every principal in member accounts (not the management account)
Resource control policy (RCP)OU or accountmaximum permissions on resources (e.g. S3, KMS) whoever calls
Session policypassed at AssumeRolenarrow a role for one session

3 · What STS does when a role is assumed

sts:AssumeRole checks the role’s trust policy (is this caller allowed?) and the caller’s own permission to call AssumeRole, then returns an AccessKeyId (ASIA…), SecretAccessKey, SessionToken and Expiration. Default duration is 1 hour; a role can allow up to 12 hours. Role chaining (a role assuming another role) is limited to 1 hour. EC2 and Lambda call STS for you and refresh credentials before they expire.

4 · How the policy language matches

  • Actions are case-insensitive, service:Operation; wildcards * and ? allowed (s3:Get*).
  • Resources are ARNs; wildcards in the resource part.
  • NotAction / NotResource invert the match — powerful and easy to misuse.
  • Policy variables: ${aws:username} lets one policy give each user their own folder: arn:aws:s3:::home/${aws:username}/*.
  • Global condition keys: aws:SourceIp, aws:MultiFactorAuthPresent, aws:SecureTransport, aws:PrincipalTag, aws:RequestedRegion, aws:PrincipalOrgID.

10 By role

How developers, data, ML, DevOps and security people use IAM

IAM touches every role; here is what each one actually does with it.

Software developer (backend)

Never handles keys; asks for precise permissions for the app.

Uses: Lambda execution roles, ECS task roles, EC2 instance profiles, SDK credential chain.

A real task: The order service needs sqs:SendMessage on one queue — request exactly that, scoped to the queue ARN.

Skill to build: Reading AccessDenied messages and asking for the exact action/ARN.

App / mobile developer

End users never get IAM users.

Uses: Amazon Cognito identity pools → temporary IAM roles for app users; pre-signed URLs.

A real task: Each app user may upload only to uploads/${cognito-identity.amazonaws.com:sub}/*.

Skill to build: Policy variables, Cognito, pre-signed URLs.

Data analyst

Gets read access to curated data only.

Uses: Group/permission set with Athena + read on curated S3 prefixes or Lake Formation grants.

A real task: Can query sales_curated, cannot see raw customer PII.

Skill to build: Understanding why a query fails with AccessDenied on S3 vs Glue catalog.

Data engineer

Builds pipelines that run as roles.

Uses: Glue job roles, EMR roles, Lake Formation permissions, cross-account data sharing roles.

A real task: Glue job role: read raw/, write curated/, decrypt with one KMS key — nothing else.

Skill to build: Prefix-scoped S3 policies, KMS key policies, cross-account roles.

ML / AI engineer

Notebooks and endpoints run as execution roles.

Uses: SageMaker execution roles, Bedrock model access, S3 dataset prefixes.

A real task: Notebook role may read training-data/ and invoke one Bedrock model; cannot read HR data.

Skill to build: Scoping data access; separating training vs inference roles.

DevOps / cloud engineer

Owns identity design.

Uses: Identity Center permission sets, CI/CD roles via OIDC (no keys in GitHub), boundaries, SCPs.

A real task: GitHub Actions deploys with a role trusted through OIDC; no long-term key exists anywhere.

Skill to build: Trust policies, OIDC federation, guard-rails.

Security engineer

Audits and tightens.

Uses: IAM Access Analyzer (external + unused access), credential reports, CloudTrail, policy validation.

A real task: Monthly: remove permissions unused for 90 days; flag any role trusted by an unknown account.

Skill to build: Evaluation logic, Access Analyzer, least-privilege reviews.

IAM production checklist

  • ☐ No IAM users with access keys older than 90 days (or none at all).
  • ☐ People via Identity Center or users-in-groups with MFA.
  • ☐ Apps use roles; no keys in code, images or CI variables (use OIDC).
  • ☐ Customer managed policies scoped to exact ARNs; validated with Access Analyzer.
  • ☐ Explicit Deny for dangerous patterns (non-HTTPS, Regions, disabling CloudTrail).
  • ☐ Quarterly review with last-accessed data; unused permissions removed.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. You will create a bucket, a policy, a group, a user and a role, then delete everything. Cost: zero.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Read a real AWS policy (anatomy)

    UI way — AWS Management Console

    1. IAM → Policies → search AmazonS3ReadOnlyAccess → Permissions tab → switch to JSON.
    2. Note: Version, Statement, Effect, Action (with wildcards), Resource.

    CLI way — the same thing with commands

    ARN=arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
V=$(aws iam get-policy --policy-arn $ARN --query Policy.DefaultVersionId --output text)
aws iam get-policy-version --policy-arn $ARN --version-id $V --query PolicyVersion.Document
aws iam list-entities-for-policy --policy-arn $ARN

    You should see: the JSON document with "Effect": "Allow", actions like s3:Get* and s3:List* and "Resource": "*", then which users/groups/roles use it (probably none).

    Every permission in AWS — whoever wrote it — is this same JSON shape. Learn to read it and you can read any policy.

  3. 2 · Give an intern read-only access to one folder — and prove both sides

    UI way — AWS Management Console

    1. S3: create bucket iam-lab-ACCOUNTID with folders menu/ and finance/.
    2. IAM → Policies → Create policy → JSON from the Deep dive (change the bucket name) → name S3ReadMenu.
    3. User groups → create Interns → attach S3ReadMenu; Users → create intern-kabir (no console access needed) → add to Interns.
    4. Users → intern-kabir → Permissions → Simulate (Policy Simulator) → test GetObject on menu/ and finance/, DeleteObject on menu/.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text); B=iam-lab-$ACC
aws s3 mb s3://$B --region ap-south-1
echo menu > m.txt; echo secret > f.txt
aws s3 cp m.txt s3://$B/menu/m.txt; aws s3 cp f.txt s3://$B/finance/f.txt
cat > s3readmenu.json <<EOF
{"Version":"2012-10-17","Statement":[
 {"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::$B","Condition":{"StringLike":{"s3:prefix":["menu/*"]}}},
 {"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::$B/menu/*"}]}
EOF
POL=$(aws iam create-policy --policy-name S3ReadMenu --policy-document file://s3readmenu.json --query Policy.Arn --output text)
aws iam create-group --group-name Interns >/dev/null
aws iam attach-group-policy --group-name Interns --policy-arn $POL
aws iam create-user --user-name intern-kabir >/dev/null
aws iam add-user-to-group --group-name Interns --user-name intern-kabir
sleep 10
U=arn:aws:iam::$ACC:user/intern-kabir
for a in "s3:GetObject arn:aws:s3:::$B/menu/m.txt" "s3:GetObject arn:aws:s3:::$B/finance/f.txt" "s3:DeleteObject arn:aws:s3:::$B/menu/m.txt"; do
  set -- $a
  aws iam simulate-principal-policy --policy-source-arn $U --action-names $1 --resource-arns $2 \
    --query 'EvaluationResults[0].[EvalActionName,EvalResourceName,EvalDecision]' --output text
done

    You should see: three lines: s3:GetObject …/menu/m.txt allowed, s3:GetObject …/finance/f.txt implicitDeny, s3:DeleteObject …/menu/m.txt implicitDeny — proof of both what he can and cannot do.

    The Policy Simulator evaluates the real policies attached to intern-kabir (through the Interns group) without needing his password or keys — the professional way to prove permissions.

  4. 3 · Use a role: temporary credentials in action

    UI way — AWS Management Console

    1. IAM → Roles → Create role → Trusted entity AWS account → This account → attach S3ReadMenu → name MenuReader.
    2. Top-right account menu → Switch role → your account ID + MenuReader → open S3: menu/ works, finance/ shows Access Denied.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text)
cat > trust.json <<EOF
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::$ACC:root"},"Action":"sts:AssumeRole"}]}
EOF
aws iam create-role --role-name MenuReader --assume-role-policy-document file://trust.json --query Role.Arn --output text
aws iam attach-role-policy --role-name MenuReader --policy-arn arn:aws:iam::$ACC:policy/S3ReadMenu
sleep 10
CREDS=$(aws sts assume-role --role-arn arn:aws:iam::$ACC:role/MenuReader --role-session-name lab --query Credentials --output json)
echo "$CREDS" | python3 -c "import sys,json; c=json.load(sys.stdin); print(c['AccessKeyId'][:4]+'…', 'expires', c['Expiration'])"
export AWS_ACCESS_KEY_ID=$(echo $CREDS | python3 -c "import sys,json;print(json.load(sys.stdin)['AccessKeyId'])")
export AWS_SECRET_ACCESS_KEY=$(echo $CREDS | python3 -c "import sys,json;print(json.load(sys.stdin)['SecretAccessKey'])")
export AWS_SESSION_TOKEN=$(echo $CREDS | python3 -c "import sys,json;print(json.load(sys.stdin)['SessionToken'])")
aws sts get-caller-identity --query Arn --output text
aws s3 cp s3://iam-lab-$ACC/menu/m.txt - ; aws s3 cp s3://iam-lab-$ACC/finance/f.txt - ; unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN

    You should see: ASIA… expires 2026-… (temporary key, one hour), the identity assumed-role/MenuReader/lab, the word menu, then AccessDenied for finance — the role can do exactly what its policy says, and nothing more.

    Temporary keys start with ASIA (long-term ones with AKIA) and need a session token. When they expire, they are useless to anyone who copied them.

Clean up and cost check

ACC=$(aws sts get-caller-identity --query Account --output text); aws iam detach-role-policy --role-name MenuReader --policy-arn arn:aws:iam::$ACC:policy/S3ReadMenu; aws iam delete-role --role-name MenuReader; aws iam remove-user-from-group --group-name Interns --user-name intern-kabir; aws iam delete-user --user-name intern-kabir; aws iam detach-group-policy --group-name Interns --policy-arn arn:aws:iam::$ACC:policy/S3ReadMenu; aws iam delete-group --group-name Interns; aws iam delete-policy --policy-arn arn:aws:iam::$ACC:policy/S3ReadMenu; aws s3 rb s3://iam-lab-$ACC --force

15 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Sharing one login across a team.Convenience.One identity per person; groups for permissions.
Attaching policies directly to users.Fastest click.Attach to groups/roles; users inherit.
Access keys in code or on EC2.Old tutorials.Roles: instance profiles, Lambda execution roles.
Using AdministratorAccess for everyone.Avoids AccessDenied.Start narrow; widen from real AccessDenied messages.
Wrong ARN form for S3 (bucket vs object).Looks similar.ListBucket → bucket ARN; Get/Put/DeleteObject → bucket/key ARN.

Try exam-style questions

An application on EC2 needs to read S3. Most secure option?
  1. store access keys on the instance
  2. ✔ IAM role attached to the instance
  3. root credentials
  4. make the bucket public

Why: Role → temporary credentials.

A user has an Allow from a group and a Deny from a bucket policy for the same action. Result?
  1. allowed
  2. ✔ denied
  3. depends on order
  4. allowed only in the console

Why: Explicit deny always wins.

Best way to give 20 developers the same permissions?
  1. attach policies to each user
  2. ✔ IAM group with the policy
  3. share one user
  4. inline policy on each user

Why: Groups.

What does an IAM role’s trust policy define?
  1. what the role can do
  2. ✔ who can assume the role
  3. the role’s password
  4. the Region

Why: Trust = who.

17 Mini project

Build something with what you learned

Three projects, each a little harder. Do them on your own account (or plan them on paper first). Each lists what to hand in, so a teacher can mark it.

BasicAccess plan for a coaching institute

Scenario: An institute has an owner, 4 faculty, 2 accountants and 1 auditor sharing one AWS login.

  1. List each person and what they must do (upload notes, read invoices, view everything).
  2. Design groups (Owners, Faculty, Accountants, Auditors) and which AWS managed or custom policy each gets.
  3. Explain how a new faculty member is added in one action.
  4. Explain what changes for the shared login.

Hand in: A table of groups → policies → members, and five sentences on why.

Stretch goal: Add MFA enforcement with a Deny-without-MFA statement.

IntermediateFolder-level permissions with proof

Scenario: Faculty may upload to notes/; students’ submissions/ must be invisible to them.

  1. Create a bucket with notes/ and submissions/.
  2. Write a customer managed policy for Faculty (ListBucket with s3:prefix notes/*, PutObject/GetObject on notes/*).
  3. Create the Faculty group and two users.
  4. Prove with the Policy Simulator: PutObject notes/ allowed; GetObject submissions/ denied; DeleteObject notes/ denied (if you chose so).

Hand in: The policy JSON, simulator output for 4 actions, and a screenshot of a console upload as a faculty user.

Stretch goal: Use ${aws:username} to give each faculty member a private drafts/ folder.

AdvancedCross-account auditor role

Scenario: An external auditor (another AWS account) must read logs in your account for one month, with MFA.

  1. Create role AuditorRead with ReadOnlyAccess (or narrower) and a trust policy naming the auditor’s account, requiring aws:MultiFactorAuthPresent and an ExternalId.
  2. Limit max session duration to 1 hour.
  3. From a second account (or a classmate’s), assume the role and list logs.
  4. Show the AssumeRole event in your CloudTrail.

Hand in: Trust policy, permission policy, the CloudTrail event, and a removal plan for when the audit ends.

Stretch goal: Add a permissions boundary so even an admin cannot widen AuditorRead beyond read-only.
