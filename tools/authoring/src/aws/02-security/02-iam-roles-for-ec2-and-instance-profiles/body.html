1 The story

A key in a copied server image

Before you start: Lesson 2.1 (policies, roles) and Module 1.

🤔 A developer copied TiffinGo’s server image to a test account — with an AWS access key inside a config file. Six months later the key was still working, from someone else’s computer.

Keys on servers get copied into images, backups, Git and logs, and they never expire on their own. The professional answer is an IAM role attached to the EC2 instance through an instance profile: the server asks the instance metadata service for temporary credentials that rotate automatically. This lesson shows exactly how that works, how to scope the role to folders (“read notes, write logs, never touch submissions”), and on your own account (or in the simulator) you will launch a server that tests its own permissions and writes the proof to S3 — without you ever logging in.

  • Software on AWS gets a role, never keys.
  • Instance profile = how a role is attached to EC2; IMDSv2 = how the app fetches the keys.
  • Prove both sides: what the server can do and what it cannot.

A developer copied TiffinGo’s server image to a test account with an access key inside a config file; months later the key still worked from outside. Arjun Sir replaced it with an instance role: nothing on disk, keys that rotate, folder-level limits.

K> Sir, the app needs to read S3. Without keys, how does it log in? A> The server itself gets an identity — a role. Inside every EC2 instance there is a special address, 169.254.169.254, that hands the app temporary keys for that role. R> And if someone hacks the server and copies them? A> They expire within hours, and the role can only do what its policy says — read notes, write logs. With IMDSv2 it is also much harder to trick the server into revealing them. K> How do we prove that in the lab exam? A> From the server: one command that works, one that fails with AccessDenied. Save both outputs. Let’s build it.
2 Definition

IAM roles for EC2 and instance profiles

Formal definition (write this in exams)

An IAM role for EC2 is a role whose trust policy allows ec2.amazonaws.com to assume it; it is attached to an instance through an instance profile, and software on the instance obtains automatically rotated temporary credentials for the role from the instance metadata service (IMDSv2 recommended), so no long-term access keys are stored on the server.

In simple words

Give the server a role instead of keys: it borrows temporary keys that expire, and can only do what the role allows.

Say it in an interview

30-second answer you can speak:

  • “For EC2 apps I create a role trusted by ec2.amazonaws.com, put it in an instance profile, require IMDSv2, and scope the policy to exact prefixes with explicit denies for anything that must never happen.”
  • “To prove it, I run one allowed and one denied call from the server and keep the AccessDenied output as evidence.”

3 The big picture

From role to running server

New to computers? Start here. Think of a company car. The car (server) does not carry the owner’s house keys. Instead, every morning the car gets a day pass from the security office (temporary keys from the role), which opens only the gates it needs. If the pass is stolen, it stops working tonight.

Jargon buster:

  • EC2 instance — a virtual computer (server) in AWS
  • Role — a set of permissions a server can “wear”
  • Instance profile — the clip that attaches the role to the server
  • Metadata service — a private help desk inside the server that hands out the day pass
  • Temporary credentials — keys that expire automatically

Type 1 · EC2 instance profile

Definition (say it in an interview): An instance profile is a container for one IAM role that you attach to an EC2 instance; EC2 then assumes the role on the instance’s behalf and exposes its temporary credentials to software through the instance metadata service. The console creates a profile with the same name as the role automatically; with the CLI you create it and add the role yourself.

In plain words (no jargon): The attachment that gives a server its role.

Analogy: A lanyard clip: the badge (role) hangs on it, and the clip attaches the badge to one person (server).

How it works internally, step by step

  1. Create role. Trust ec2.amazonaws.com.
  2. Create profile. create-instance-profile.
  3. Add role. add-role-to-instance-profile.
  4. Attach. --iam-instance-profile Name=…
  5. Verify. aws sts get-caller-identity on the server.

Words used above, in simple terms: instance profile = role container for EC2 · association = link between profile and instance · iam:PassRole = permission needed to give a role to a service

Type 2 · IMDSv2 (instance metadata service v2)

Definition (say it in an interview): The instance metadata service at 169.254.169.254 gives software on an instance information about itself — including its role credentials; IMDSv2 requires a session token obtained with a PUT request, which defends against server-side request forgery and open-proxy attacks that could steal credentials with IMDSv1’s simple GETs.

In plain words (no jargon): A private address inside the server that hands out its role keys — safely.

Analogy: A help desk that first asks for your staff token before handing anything over.

How it works internally, step by step

  1. PUT. /latest/api/token.
  2. Header. X-aws-ec2-metadata-token-ttl-seconds.
  3. GET. with X-aws-ec2-metadata-token.
  4. Require. HttpTokens=required.
  5. Hop limit. 1 (2 for containers).

Words used above, in simple terms: SSRF = tricking a server into making requests for an attacker · hop limit = how many network hops the token may travel · link-local = 169.254.x.x, reachable only from the instance

Type 3 · EC2 service role trust policy

Definition (say it in an interview): A role for EC2 has a trust policy allowing the service principal ec2.amazonaws.com to call sts:AssumeRole; without it, the role cannot be used by instances (the console’s “AWS service → EC2” choice writes it for you).

In plain words (no jargon): The rule saying which service may use the role.

Analogy: The visitor badge says “valid for company cars only”.

How it works internally, step by step

  1. Principal. Service: ec2.amazonaws.com.
  2. Action. sts:AssumeRole.
  3. Condition. optional SourceAccount.
  4. Profile. Wraps the role.
  5. PassRole. Launcher needs it.

Words used above, in simple terms: service principal = an AWS service named in a policy · AssumeRole = STS action to borrow a role · confused deputy = a service tricked into acting for the wrong party

How an EC2 server gets AWS permissions without any keys

The app on the server asks the instance metadata service for temporary credentials of its role — watch the full path.

Instance role 6 steps
Watch what happens
  1. Step 1 · Launch with an instance profile — the instance profile is the container that attaches role LabAppRole to the instance; its trust policy lets ec2.amazonaws.com assume it.
  2. Step 2 · The SDK asks IMDSv2 for a token — boto3 finds no keys in env vars or files, so it reaches chain step 6: a PUT to 169.254.169.254 returns a short-lived session token.
  3. Step 3 · IMDS returns temporary keys — with the token, a GET on /latest/meta-data/iam/security-credentials/LabAppRole returns ASIA… keys, a session token and an expiry time.
  4. Step 4 · Allowed calls succeed — requests are signed with the role’s keys; IAM allows GetObject on notes/* and PutObject on logs/*.
  5. Step 5 · Forbidden calls fail — submissions/ is not in the role’s policy (and can be explicitly denied), so S3 answers AccessDenied — proof the server cannot read it.
  6. Step 6 · Keys rotate themselves — AWS refreshes the credentials before they expire; the SDK picks up new ones automatically. A copied key dies within hours.
6 Explained part by part

Six parts of a secure server identity

Trust policy

What it is: ec2.amazonaws.com may assume.

Why it exists: Without it, EC2 cannot use the role.

Where it is used: Console: AWS service → EC2.

Permission policy

What it is: exact S3 prefixes/actions.

Why it exists: What the server can do.

Where it is used: notes/ read, logs/ write.

Explicit Deny

What it is: for what must never happen.

Why it exists: Survives future Allows.

Where it is used: Deny submissions/*, Deny s3:Delete*.

Instance profile

What it is: role container.

Why it exists: Attaches role to instance.

Where it is used: --iam-instance-profile Name=…

IMDSv2 required

What it is: token-based metadata.

Why it exists: Stops credential theft via SSRF.

Where it is used: HttpTokens=required.

Proof

What it is: allowed + denied outputs.

Why it exists: Evidence for audits and exams.

Where it is used: Saved to logs/ automatically.

8 Deep dive

The server policy with explicit denies; talking to IMDSv2

The server policy used in this lesson

{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "ListNotesAndLogs", "Effect": "Allow", "Action": "s3:ListBucket",
     "Resource": "arn:aws:s3:::BUCKET",
     "Condition": {"StringLike": {"s3:prefix": ["notes/*", "logs/*"]}}},
    {"Sid": "ReadNotes", "Effect": "Allow", "Action": "s3:GetObject",
     "Resource": "arn:aws:s3:::BUCKET/notes/*"},
    {"Sid": "WriteLogs", "Effect": "Allow", "Action": "s3:PutObject",
     "Resource": "arn:aws:s3:::BUCKET/logs/*"},
    {"Sid": "NeverSubmissions", "Effect": "Deny", "Action": "s3:*",
     "Resource": "arn:aws:s3:::BUCKET/submissions/*"},
    {"Sid": "NeverDelete", "Effect": "Deny",
     "Action": ["s3:DeleteObject", "s3:DeleteObjectVersion", "s3:DeleteBucket"],
     "Resource": ["arn:aws:s3:::BUCKET", "arn:aws:s3:::BUCKET/*"]}
  ]
}

Why the two Deny statements? Allows can be added later by mistake (someone attaches a broad policy). An explicit Deny keeps “never read submissions” and “never delete, even if hacked” true forever.

9 Under the hood

Credential rotation, PassRole, hop limits, CloudTrail session names

The mechanics behind instance credentials — what really happens on the host.

1 · Rotation and expiry

EC2 obtains credentials for the role from STS and makes them available through IMDS; they are refreshed automatically well before they expire (typically valid for a few hours; new ones appear at least five minutes before the old ones expire). SDKs cache them and re-read IMDS when needed — your code never handles refresh.

2 · iam:PassRole — the anti-escalation lock

To attach a role to an instance (or a Lambda function, ECS task, Glue job…), the caller needs iam:PassRole on that role. Without this, any developer could launch a server with an admin role and borrow admin power. Grant it narrowly: "Resource": "arn:aws:iam::ACCOUNT:role/app-*", optionally with iam:PassedToService = ec2.amazonaws.com.

3 · IMDSv2 details

SettingMeaningRecommendation
HttpTokensoptional (v1+v2) or required (v2 only)required

4 · How it looks in CloudTrail

Calls made by the server appear with userIdentity.type = AssumedRole and an ARN like arn:aws:sts::ACCOUNT:assumed-role/LabAppRole/i-0abc123… — the session name is the instance ID, so you can trace every action to one server. Credential use from an unexpected IP is what GuardDuty’s credential-exfiltration findings detect.

5 · Data perimeter conditions

Even valid role keys can be limited to where they are used: aws:SourceVpc / aws:SourceVpce (request must come through your VPC endpoint), aws:ec2InstanceSourceVPC and aws:ec2InstanceSourcePrivateIPv4 (credentials must be used from the instance’s own VPC/IP), aws:PrincipalOrgID and aws:ResourceOrgID (only identities/resources of your organisation). Together they make stolen credentials far less useful.

Skill to build: Asking for access to the right role, not personal keys.

Data engineer

Every job runs as a role.

Uses: Glue job roles, EMR instance profiles (EC2 role for EMR nodes), Airflow (MWAA) execution role.

A real task: EMR nodes read raw/ and write curated/ through the cluster’s instance profile.

Skill to build: Per-job roles, prefix scoping, KMS permissions.

Training jobs and endpoints assume execution roles.

Uses: SageMaker execution role, Bedrock access via role, GPU instances with instance profiles.

A real task: Training job reads datasets/ and writes models/; cannot read HR data.

DevOps / cloud engineer

Designs roles, PassRole, IMDS defaults.

Detects misuse.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. You launch one t3.micro for a few minutes (Free Tier / credits cover it) and delete everything at the end.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Bucket with three areas + a role scoped to them

    UI way — AWS Management Console

    1. S3 → create edu-lab-ACCOUNTID; upload a file to notes/ and one to submissions/.
    2. IAM → Policies → Create policy → JSON from the Deep dive (replace BUCKET) → LabAppPolicy.
    3. Roles → Create role → AWS service → EC2 → attach LabAppPolicy → name LabAppRole (the console also creates the instance profile).

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text); B=edu-lab-$ACC
aws s3 mb s3://$B --region ap-south-1
echo 'Lecture 1 notes' > l1.txt; echo 'Roll 101 answer' > a1.txt
aws s3 cp l1.txt s3://$B/notes/l1.txt; aws s3 cp a1.txt s3://$B/submissions/a1.txt
cat > trust.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}
EOF
cat > policy.json <<EOF
{"Version":"2012-10-17","Statement":[
{"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::$B","Condition":{"StringLike":{"s3:prefix":["notes/*","logs/*"]}}},
{"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::$B/notes/*"},
{"Effect":"Allow","Action":"s3:PutObject","Resource":"arn:aws:s3:::$B/logs/*"},
{"Effect":"Deny","Action":"s3:*","Resource":"arn:aws:s3:::$B/submissions/*"},
{"Effect":"Deny","Action":["s3:DeleteObject","s3:DeleteObjectVersion","s3:DeleteBucket"],"Resource":["arn:aws:s3:::$B","arn:aws:s3:::$B/*"]}]}
EOF
aws iam create-role --role-name LabAppRole --assume-role-policy-document file://trust.json >/dev/null
aws iam put-role-policy --role-name LabAppRole --policy-name LabAppPolicy --policy-document file://policy.json
aws iam create-instance-profile --instance-profile-name LabAppRole >/dev/null
aws iam add-role-to-instance-profile --instance-profile-name LabAppRole --role-name LabAppRole
aws iam get-instance-profile --instance-profile-name LabAppRole --query 'InstanceProfile.Roles[].RoleName' --output text

    You should see: LabAppRole printed as the role inside the instance profile. (The CLI uses an inline policy here for brevity; in production prefer a customer managed policy.)

    With the CLI you must create the instance profile yourself — a frequent “role not showing in the launch wizard” cause.

  3. 2 · Launch a server that tests its own permissions (no login)

    UI way — AWS Management Console

    1. EC2 → Launch instance → Amazon Linux 2023, t3.micro → Advanced details: IAM instance profile LabAppRole, Metadata version V2 only, paste the user data script below (replace BUCKET).
    2. Wait ~2 minutes after the instance is running.

    CLI way — the same thing with commands

    cat > proof.sh <<EOF
#!/bin/bash
export AWS_DEFAULT_REGION=ap-south-1
B=$B; I=\$(TOKEN=\$(curl -s -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 300'); curl -s -H "X-aws-ec2-metadata-token: \$TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
R=/tmp/proof.txt; date > \$R; aws sts get-caller-identity --query Arn --output text >> \$R
t(){ if eval "\$2" >/dev/null 2>&1; then echo "\$1: ALLOWED" >> \$R; else echo "\$1: DENIED" >> \$R; fi; }
t 'read notes'        "aws s3 cp s3://\$B/notes/l1.txt -"
t 'read submissions'  "aws s3 cp s3://\$B/submissions/a1.txt -"
t 'delete notes'      "aws s3 rm s3://\$B/notes/l1.txt"
echo "IMDSv1 call: \$(curl -s -o /dev/null -w '%{http_code}' http://169.254.169.254/latest/meta-data/)" >> \$R
aws s3 cp \$R s3://\$B/logs/proof-\$I.txt
EOF
AMI=resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64
ID=$(aws ec2 run-instances --image-id $AMI --instance-type t3.micro --iam-instance-profile Name=LabAppRole \
  --metadata-options HttpTokens=required,HttpEndpoint=enabled --user-data file://proof.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=role-lab}]' --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --instance-ids $ID; echo $ID; sleep 120

    You should see: the instance ID; after two minutes the server has run the tests itself using only its role.

    You never logged in and never typed a key: the server proved its own permissions — exactly what “self-configuring” lab requirements ask.

  4. 3 · Read the proof the server wrote

    UI way — AWS Management Console

    1. S3 → bucket → logs/ → open proof-i-….txt.
    2. Optional: EC2 → instance → Actions → Security → Modify IAM role to see the attached role.

    CLI way — the same thing with commands

    aws s3 ls s3://$B/logs/
aws s3 cp s3://$B/logs/proof-$ID.txt -
aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].[IamInstanceProfile.Arn,MetadataOptions.HttpTokens]' --output text

    You should see: the date, arn:aws:sts::…:assumed-role/LabAppRole/i-0…, then read notes: ALLOWED, read submissions: DENIED, delete notes: DENIED, IMDSv1 call: 401; and the profile ARN with required.

    The identity line shows the server acted as an assumed role session named after the instance — that is what CloudTrail records too.

Clean up and cost check

aws ec2 terminate-instances --instance-ids $ID; aws ec2 wait instance-terminated --instance-ids $ID; aws iam remove-role-from-instance-profile --instance-profile-name LabAppRole --role-name LabAppRole; aws iam delete-instance-profile --instance-profile-name LabAppRole; aws iam delete-role-policy --role-name LabAppRole --policy-name LabAppPolicy; aws iam delete-role --role-name LabAppRole; aws s3 rb s3://$B --force — note: the role’s own Deny blocks deletes only for the server; you (admin) can still delete.
