2 Definition

Security best practices

Formal definition (write this in exams)

AWS security best practices combine the shared responsibility model with defence in depth: strong identity (MFA, SSO, least privilege, no long-term keys), network and data protection (private networking, encryption, blocked public access), continuous recording and detection (CloudTrail, Config, GuardDuty, Inspector, Macie, Security Hub), automated response (EventBridge, Lambda, SNS) and practised incident response — applied as a baseline to every account.

In simple words

Lock the doors (prevent), switch on the CCTV and the guard (record and detect), and make the alarm call someone automatically (respond).

Say it in an interview

30-second answer you can speak:

  • “My baseline: root MFA, SSO, roles not keys, CloudTrail in all Regions, GuardDuty and Security Hub on, default encryption, Block Public Access, budgets — then EventBridge rules that route high findings to on-call and automation.”
  • “Incident response: contain (disable keys, isolate), investigate (CloudTrail, snapshots), eradicate, recover, and learn with guard-rails.”

3 The big picture

Layers, baseline and responsibility

New to computers? Start here. Security is like protecting a shop: locks on doors (prevention), CCTV (logging), a guard watching the CCTV for suspicious people (detection), and an alarm that calls the police automatically (response). AWS gives you all four; you must switch them on.

Jargon buster:

  • Shared responsibility — AWS secures the building; you secure what you keep inside
  • Finding — a security problem a tool has detected
  • Baseline — the minimum settings every account should have
  • Incident — a security event that needs action
  • Automation — a response that runs without waiting for a person

Security on AWS is shared: AWS protects the cloud (data centres, hardware, hypervisor); you protect what you put in it — identities, data, configuration. You do it in layers:

Type 1 · AWS CloudTrail

Definition (say it in an interview): CloudTrail records API activity in your account — who, what action, when, from which IP, on which resource, success or failure; event history keeps 90 days of management events free, and a trail delivers events from all Regions to S3 (optionally CloudWatch Logs) with log-file integrity validation.

In plain words (no jargon): A record of every action in your AWS account.

Analogy: CCTV with a time-stamped recording of every door opened.

How it works internally, step by step

  1. Event history. 90 days, free.
  2. Trail. All Regions → S3.
  3. Validation. Digest files.
  4. Data events. S3 object/Lambda level (extra cost).
  5. Lake. CloudTrail Lake for SQL queries.

Words used above, in simple terms: management event = control-plane action like CreateBucket · data event = object-level action like GetObject · log file validation = proof logs were not altered

Type 2 · Amazon GuardDuty

Definition (say it in an interview): GuardDuty is a managed threat-detection service that continuously analyses CloudTrail events, VPC Flow Logs and DNS logs (plus optional S3, EKS, RDS, Lambda, malware and runtime protection) using threat intelligence and machine learning, producing findings such as compromised credentials, crypto-mining or communication with known malicious IPs.

In plain words (no jargon): An automatic guard that spots attacks in your account.

Analogy: A trained security guard who watches all CCTV screens and knows the faces of known thieves.

How it works internally, step by step

  1. Enable. One click per Region.
  2. Sources. Trail, flow, DNS.
  3. Findings. Type + severity.
  4. Samples. Generate to test alerts.
  5. Route. EventBridge.

Words used above, in simple terms: finding = detected threat · severity = low/medium/high/critical · threat intelligence = lists of known bad IPs/domains

Type 3 · AWS Security Hub (and Security Hub CSPM)

Definition (say it in an interview): AWS Security Hub (new version generally available since December 2025) unifies findings from GuardDuty, Inspector, Macie and Security Hub CSPM, correlating them into prioritised exposures; Security Hub CSPM (the original Security Hub) runs posture checks against standards such as AWS Foundational Security Best Practices and CIS benchmarks.

In plain words (no jargon): One place that gathers and ranks all security problems.

Analogy: A control room that combines CCTV, fire alarms and door sensors into one screen, sorted by danger.

How it works internally, step by step

  2. Standards. FSBP, CIS.
  3. Findings. ASFF/OCSF format.
  4. Automation rules. Suppress/route.
  5. Integrations. Ticketing, SIEM.

Words used above, in simple terms: CSPM = cloud security posture management · control = one automated check · standard = a set of controls, e.g. CIS

Type 4 · AWS Config

Definition (say it in an interview): AWS Config records the configuration of resources over time and evaluates them against rules (for example s3-bucket-ssl-requests-only, encrypted-volumes, restricted-ssh), showing compliance history and optionally auto-remediating with Systems Manager Automation.

In plain words (no jargon): A history of every setting and a checker for rules.

Analogy: A building inspector’s logbook: what changed, when, and whether it meets the code.

How it works internally, step by step

  1. Recorder. Choose resource types.
  2. Rules. Managed/custom.
  3. Conformance packs. Bundles.
  4. Remediation. SSM docs.
  5. Aggregator. Multi-account.

Words used above, in simple terms: configuration item = snapshot of a resource · conformance pack = set of rules · remediation = automatic fix

Type 5 · Amazon Inspector

Definition (say it in an interview): Amazon Inspector continuously scans EC2 instances, container images in ECR and Lambda functions for software vulnerabilities (CVEs) and unintended network exposure, scoring findings by severity and exploitability.

In plain words (no jargon): A scanner that finds unpatched software.

Analogy: A mechanic checking every car in the fleet for known recalls.

  3. Findings. CVE + score.
  4. Fix. Patch Manager.
  5. Report. SBOM export.

Words used above, in simple terms: CVE = public ID of a known vulnerability · SBOM = software bill of materials · exploitability = how easy to attack

Type 6 · Amazon Macie

Definition (say it in an interview): Amazon Macie discovers and protects sensitive data in S3: it inventories buckets (public, shared, unencrypted) and uses machine learning and pattern matching — including custom data identifiers — to find personal data, financial data and credentials inside objects.

In plain words (no jargon): A tool that finds personal or secret data hidden in your files.

Analogy: A librarian who checks every shelf for documents that should be in the locked cabinet.

  2. Inventory. Bucket posture.
  3. Discovery. Automated sampling.
  4. Jobs. Targeted scans.
  5. Identifiers. Custom regex.

Words used above, in simple terms: PII = personally identifiable information · data identifier = pattern for a data type · sensitive data discovery = Macie’s scanning

Detection chain 6 steps
Watch what happens
  1. Step 1 · The attack — a leaked access key is used from an unfamiliar country to launch 20 instances at 11:40 pm.
  2. Step 2 · Everything is recorded — CloudTrail logs each RunInstances call with the access key ID, source IP and time — the raw evidence.
  3. Step 3 · GuardDuty notices — machine learning and threat intelligence flag anomalous API use from an unusual location — a HIGH-severity finding within minutes.
  4. Step 4 · Findings are routed — the finding appears in Security Hub with others, and an EventBridge rule matching severity ≥ 7 triggers automation.

  6. Step 6 · Learn — the incident review follows contain → investigate → eradicate → recover → learn, and adds guard-rails so it cannot repeat.
6 Explained part by part

Six parts of security on AWS

Prevent

What it is: identity, network, encryption.

Why it exists: Stops most attacks.

Where it is used: Lessons 1.2–2.4.

Record

What it is: CloudTrail trail, Config.

Why it exists: Evidence for everything.

Where it is used: All Regions, 180+ days.

Detect

What it is: GuardDuty, Inspector, Macie.

Why it exists: See problems early.

Where it is used: Every Region.

Prioritise

What it is: Security Hub.

Why it exists: Fix what matters first.

Where it is used: One list.

Respond

What it is: EventBridge + Lambda + SNS.

Why it exists: Minutes, not days.

Where it is used: Auto-disable keys.

Learn

What it is: incident reviews, guard-rails.

Why it exists: Never the same incident twice.

Where it is used: Blameless postmortems.

9 Under the hood

How GuardDuty, Config and Security Hub work; costs; multi-account

How the detection services work internally — and what they cost.

1 · Where GuardDuty gets its data

GuardDuty reads CloudTrail management events, VPC Flow Logs and Route 53 DNS query logs directly from AWS’s internal streams — you do not need to enable flow logs or pay for them separately for GuardDuty. Optional protection plans add S3 data events, EKS audit logs and runtime monitoring, RDS login activity, Lambda network activity and malware scanning of EBS volumes and S3 objects.

2 · Finding types read like sentences

ThreatPurpose:ResourceType/ThreatFamily.Detail!Artifact — e.g. CryptoCurrency:EC2/BitcoinTool.B!DNS means “an EC2 instance queried a domain associated with Bitcoin mining”. Severity 7.0–8.9 = High, 9.0–10 = Critical (newer attack-sequence findings), 4.0–6.9 = Medium.

3 · Config vs CloudTrail vs Security Hub CSPM

ServiceStoresTypical question
CloudTrailAPI eventswho changed the security group at 3 pm?
Configresource configuration snapshotswhat did it look like before, and is it compliant?
Security Hub CSPMresults of controls (many built on Config rules)how many best-practice checks fail?

4 · Organisation-wide security

In AWS Organizations you designate a delegated administrator account for GuardDuty, Security Hub, Inspector, Macie and Config aggregation; new accounts are enrolled automatically. A separate log archive account receives the organisation CloudTrail, with SCPs preventing anyone in member accounts from stopping or deleting it.

10 By role

Security duties of developers, data, ML, DevOps and security people

Security is everyone’s job — here is each role’s part.

Software developer (backend)

Writes secure code and responds to findings in their services.

Uses: Secrets Manager, Inspector findings for their images, CodeGuru/linters, dependency updates.

A real task: Inspector flags a vulnerable library in the order-service image; developer bumps the version and redeploys.

Skill to build: Dependency hygiene, secret handling.

App / mobile developer

Protects front ends and APIs.

Uses: WAF on CloudFront/API Gateway, Cognito, HTTPS, Shield Standard (automatic).

A real task: Add a WAF rate-based rule after a login brute-force attempt.

Skill to build: WAF rules, auth flows.

Data analyst

Handles sensitive data carefully.

Uses: Macie findings, Lake Formation permissions, masked datasets.

A real task: Uses the masked customer table, not raw PII.

Skill to build: Data classification awareness.

Data engineer

Keeps data platforms secure and auditable.

Uses: CloudTrail data events for S3, Macie on landing zones, KMS per zone, Lake Formation.

A real task: Macie flags PAN-like values in raw/ — pipeline adds masking before curated/.

Skill to build: Data security controls in pipelines.

ML / AI engineer

Secures training data, models and AI endpoints.

Uses: GuardDuty for SageMaker/EKS, Bedrock Guardrails, private endpoints, KMS.

A real task: A chatbot uses Bedrock Guardrails to block personal data in responses.

Skill to build: AI-specific risks (prompt injection, data leakage).

DevOps / cloud engineer

Builds the baseline and automation.

Uses: Organizations, Control Tower, org-wide GuardDuty/Security Hub, EventBridge, SSM.

A real task: New accounts are born with the baseline via Control Tower; findings flow to a central account.

Skill to build: Security automation at scale.

Security engineer

Detects, responds, reports.

Uses: Security Hub, GuardDuty, Detective, Athena on CloudTrail, incident runbooks.

A real task: Runs the Monday incident review and files the CERT-In report within 6 hours when required.

Skill to build: Investigation, playbooks, regulation.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. GuardDuty has a 30-day free trial; CloudTrail’s first management-event trail is free (you pay small S3 storage). Disable what you do not keep.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · A CloudTrail trail for all Regions, with integrity validation

    UI way — AWS Management Console

    1. CloudTrail → Trails → Create trail → name baseline → new S3 bucket → Log file validation enabled → (multi-Region is the default) → Create trail.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text); TB=trail-$ACC
aws s3 mb s3://$TB --region ap-south-1
cat > tp.json <<EOF
{"Version":"2012-10-17","Statement":[
{"Sid":"AclCheck","Effect":"Allow","Principal":{"Service":"cloudtrail.amazonaws.com"},"Action":"s3:GetBucketAcl","Resource":"arn:aws:s3:::$TB"},
{"Sid":"Write","Effect":"Allow","Principal":{"Service":"cloudtrail.amazonaws.com"},"Action":"s3:PutObject","Resource":"arn:aws:s3:::$TB/AWSLogs/$ACC/*","Condition":{"StringEquals":{"s3:x-amz-acl":"bucket-owner-full-control"}}}]}
EOF
aws s3api put-bucket-policy --bucket $TB --policy file://tp.json
aws cloudtrail create-trail --name baseline --s3-bucket-name $TB --is-multi-region-trail --enable-log-file-validation >/dev/null
aws cloudtrail start-logging --name baseline
aws cloudtrail get-trail-status --name baseline --query '[IsLogging,LatestDeliveryTime]' --output text

    You should see: True and, after a few minutes, a delivery time — events from every Region now land in your bucket, with digest files proving they were not altered.

    Add an S3 lifecycle rule (Lesson 4.4) to keep logs at least 180 days for CERT-In; move older ones to cheaper storage.

  3. 2 · GuardDuty with sample findings

    UI way — AWS Management Console

    1. GuardDuty → Get started → Enable GuardDuty (30-day free trial).
    2. Settings → Generate sample findings → Findings: filter High severity and open one.

    CLI way — the same thing with commands

    DET=$(aws guardduty create-detector --enable --query DetectorId --output text 2>/dev/null || aws guardduty list-detectors --query 'DetectorIds[0]' --output text)
aws guardduty create-sample-findings --detector-id $DET
sleep 20
aws guardduty list-findings --detector-id $DET --finding-criteria '{"Criterion":{"severity":{"Gte":7}}}' --max-results 5 --query FindingIds --output text | tr '\t' '\n' | head -3 > ids.txt
aws guardduty get-findings --detector-id $DET --finding-ids $(cat ids.txt) --query 'Findings[].[Type,Severity,Title]' --output table

    You should see: a table of high-severity sample findings (types like CryptoCurrency:EC2/BitcoinTool.B!DNS or UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration…), each marked as a sample.

    Sample findings are labelled [SAMPLE] and safe — perfect for testing alert pipelines without being attacked.

  4. 3 · Alert on high-severity findings (EventBridge → SNS)

    UI way — AWS Management Console

    1. SNS → Create topic security-alerts → Create subscription e-mail → confirm from your inbox.
    2. EventBridge → Rules → Create rule → pattern from the Deep dive → target SNS topic.
    3. Generate sample findings again and watch your inbox.

    CLI way — the same thing with commands

    TOPIC=$(aws sns create-topic --name security-alerts --query TopicArn --output text)
aws sns subscribe --topic-arn $TOPIC --protocol email --notification-endpoint you@example.com
cat > pattern.json <<'EOF'
{"source":["aws.guardduty"],"detail-type":["GuardDuty Finding"],"detail":{"severity":[{"numeric":[">=",7]}]}}
EOF
aws events put-rule --name guardduty-high --event-pattern file://pattern.json >/dev/null
aws sns set-topic-attributes --topic-arn $TOPIC --attribute-name Policy --attribute-value "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":{\"Service\":\"events.amazonaws.com\"},\"Action\":\"sns:Publish\",\"Resource\":\"$TOPIC\"}]}"
aws events put-targets --rule guardduty-high --targets Id=sns,Arn=$TOPIC
aws guardduty create-sample-findings --detector-id $DET --finding-types 'CryptoCurrency:EC2/BitcoinTool.B!DNS'

    You should see: a confirmation e-mail (click it), then within a few minutes an alert e-mail with the finding JSON — your detection → notification chain works.

    Replace you@example.com with your address. In production the target is often a Lambda function that also deactivates keys or isolates instances.

Clean up and cost check

Keep the CloudTrail trail (good permanent practice) or delete it: aws cloudtrail delete-trail --name baseline; aws s3 rb s3://$TB --force. Alerts: aws events remove-targets --rule guardduty-high --ids sns; aws events delete-rule --name guardduty-high; aws sns delete-topic --topic-arn $TOPIC. GuardDuty after the trial: aws guardduty delete-detector --detector-id $DET (or keep it — recommended for real accounts).

15 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Only prevention, no detection.MFA feels enough.CloudTrail + GuardDuty + alerts on day one.
GuardDuty in one Region only.Only Mumbai is used.Attackers use the Regions you ignore — enable everywhere (or block Regions by SCP).
Alerts to an inbox nobody reads.Set and forget.Route high severity to on-call (SMS/chat) and automation.
Deleting evidence while cleaning up.Panic.Contain first, snapshot, collect logs, then eradicate.
Secrets in code or user data.Convenience.Secrets Manager / Parameter Store + roles.
Never practising incident response.“It will not happen to us.”Run a sample-finding drill each quarter.

Three projects, each a little harder. Do them on your own account (or plan them on paper first). Each lists what to hand in, so a teacher can mark it.

BasicBaseline audit of your learning account

IntermediateDetection-to-alert pipeline

  1. CloudTrail trail + GuardDuty.

  3. Generate a sample finding; time how long the e-mail takes.

AdvancedAutomated key containment

Scenario: If a key is used anomalously, disable it automatically and preserve evidence.

  1. Lambda (role: iam:UpdateAccessKey, cloudtrail:LookupEvents) triggered by GuardDuty IAM findings.
  2. Deactivate the key named in the finding; store the last 50 events of that key in S3.
  3. Notify via SNS with a summary.
  4. Test with a sample finding and a test user’s key.

Hand in: Code, IAM policy, test evidence, and risks of auto-remediation.
