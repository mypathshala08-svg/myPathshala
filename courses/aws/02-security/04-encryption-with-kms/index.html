1 The story

“Who can decrypt the sales data?”

Before you start: Lessons 2.1–2.3.

🤔 CityBite’s auditor asked two questions: “Is the sales data encrypted?” and “Who can decrypt it?” The IT head could answer the first. Not the second.

Encryption is easy to switch on in AWS; controlling who can decrypt is the real skill. This lesson explains encryption in transit and at rest, how AWS KMS keys work, why S3 uses envelope encryption, the difference between SSE-S3, SSE-KMS and other options, and how a key policy becomes a second lock next to IAM. On your own account (or in the simulator) you will create a key, encrypt a message, make a bucket encrypt everything with your key, refuse plain-HTTP requests, and watch a disabled key lock the data instantly.

  • In transit = HTTPS; at rest = encrypted storage with keys in KMS.
  • SSE-KMS adds a second lock: reading needs kms:Decrypt too.
  • Disable a key and every object it protects becomes unreadable at once.

CityBite’s auditor asked whether sales data was encrypted and who could decrypt it. Default encryption answered the first; only a customer managed KMS key with a key policy and CloudTrail logs answered the second.

2 Definition

Encryption with KMS

Formal definition (write this in exams)

AWS Key Management Service (KMS) creates and controls cryptographic keys in hardware security modules that never export them, and performs encryption, decryption and data-key generation under key policies and IAM, logging every use in CloudTrail; AWS services such as S3, EBS and RDS use KMS keys through envelope encryption to protect data at rest, while TLS protects data in transit.

In simple words

KMS keeps the keys locked away and only uses them for people and services on the key’s list; S3 and other services use those keys to lock your data on disk.

Say it in an interview

30-second answer you can speak:

  • “I encrypt at rest with SSE-KMS using a customer managed key whose key policy separates administrators from users, enable Bucket Keys for cost, and enforce TLS with an aws:SecureTransport Deny.”
  • “S3 uses envelope encryption: a per-object data key encrypts the data, and the KMS key encrypts the data key — the KMS key never leaves KMS.”

3 The big picture

In transit, at rest, and who holds the keys

New to computers? Start here. Encryption turns readable data into scrambled text that only someone with the right key can unscramble. KMS is a bank locker room for keys: the keys never leave the locker; you send things in to be locked or unlocked, and the locker room checks your ID every time and writes it in a register.

Jargon buster:

  • Encryption — scrambling data so only key-holders can read it
  • Key — the secret used to scramble/unscramble
  • At rest — data sitting on a disk
  • In transit — data travelling over the network
  • HTTPS / TLS — the padlock in your browser — encryption in transit
  • KMS — AWS service that stores and uses keys safely

Type 1 · SSE-S3 (Amazon S3 managed keys)

Definition (say it in an interview): SSE-S3 encrypts each object at rest with AES-256 using keys that S3 creates and manages entirely; it is applied by default to all new objects (since January 2023), costs nothing, and decryption needs only S3 read permission.

In plain words (no jargon): S3 locks your files automatically with its own keys.

Analogy: A building where every flat’s door locks automatically — but the building manager holds all keys.

How it works internally, step by step

  1. Default. On for new objects.
  2. Algorithm. AES-256.
  3. Keys. Managed by S3.
  4. Cost. Free.
  5. Header. x-amz-server-side-encryption: AES256.

Words used above, in simple terms: AES-256 = standard strong encryption · at rest = stored data · SSE = server-side encryption

Type 3 · SSE-KMS with a customer managed key

Definition (say it in an interview): SSE-KMS with a customer managed key uses a KMS key you create and control — its key policy, rotation, enable/disable and deletion — so reading objects requires S3 permission and kms:Decrypt on the key; every use is logged, and S3 Bucket Keys reduce KMS request costs by up to 99%.

In plain words (no jargon): Encryption with your own key and your own list of who may unlock.

Analogy: Your own locker in the bank with your own access register: the bank opens it only for people on your list.

How it works internally, step by step

  1. Create. aws kms create-key.
  2. Alias. alias/name.
  3. Key policy. Root + admins + users.
  4. Bucket. Default SSE-KMS.
  5. Bucket Key. Fewer KMS calls.

Words used above, in simple terms: customer managed key = KMS key you create and control · key policy = resource policy on the key — required · S3 Bucket Key = bucket-level data key to cut KMS calls

In plain words (no jargon): S3 encrypts your file twice.

Type 5 · SSE-C (customer-provided keys)

Definition (say it in an interview): SSE-C lets you supply your own encryption key in request headers on every PUT and GET; S3 encrypts/decrypts with it and stores only a salted hash to validate later requests — if you lose the key, the data is unrecoverable.

In plain words (no jargon): You give S3 the key every time; S3 never keeps it.

Analogy: You bring your own padlock and keep the only key; the warehouse locks and unlocks only when you hand it over.

How it works internally, step by step

  1. Generate. Your key.
  2. PUT. Key in headers.
  3. GET. Same key again.
  4. HTTPS. Required.
  5. Store. Yourself.

Words used above, in simple terms: customer-provided key = your own key sent per request · salted hash = fingerprint to check the key, not the key · key loss = permanent data loss

Type 6 · Client-side encryption

Definition (say it in an interview): Client-side encryption encrypts data inside your application before sending it to AWS (for example with the AWS Encryption SDK or the Amazon S3 Encryption Client, often with keys from KMS), so storage services hold only ciphertext and never the plaintext.

In plain words (no jargon): Scramble the data yourself before it goes to the cloud.

Analogy: Writing your letter in a secret code before posting it — the post office only carries gibberish.

How it works internally, step by step

  1. Library. Encryption SDK.
  2. Key. KMS or your own.
  3. Encrypt. Before upload.
  4. Store. Ciphertext.
  5. Decrypt. In app.

Words used above, in simple terms: Encryption SDK = AWS library for envelope encryption · ciphertext = scrambled data · plaintext = readable data

Type 7 · Encryption in transit (TLS) and HTTPS-only policies

Definition (say it in an interview): Encryption in transit protects data moving between clients and AWS (and between services) using TLS; AWS endpoints support HTTPS, and a bucket or resource policy that denies requests where aws:SecureTransport is false enforces it — you can also require a minimum TLS version with s3:TlsVersion.

In plain words (no jargon): The padlock that protects data while it travels.

Analogy: A sealed envelope instead of a postcard: the postman can carry it but not read it.

How it works internally, step by step

  1. TLS. Encrypted channel.
  2. Policy. Deny SecureTransport=false.
  3. Version. s3:TlsVersion ≥ 1.2.
  4. Test. http endpoint → denied.
  5. Certificates. ACM for your sites.

Words used above, in simple terms: TLS = Transport Layer Security · HTTPS = HTTP over TLS · ACM = AWS Certificate Manager

5 How it works, step by step

Envelope encryption, step by step

One file into S3 with SSE-KMS, and two people trying to read it.

Animated

Envelope encryption: what happens when S3 encrypts with KMS

Follow one sales file into S3 with SSE-KMS, then two people trying to read it.

SSE-KMS 6 steps
Watch what happens
  1. Step 1 · Upload over HTTPS — the file travels encrypted in transit (TLS). At rest, the bucket’s default encryption says: SSE-KMS with key alias/citybite-sales.
  2. Step 2 · S3 asks KMS for a data key — GenerateDataKey for that KMS key. KMS first checks the key policy: may this request (via S3, for this account) use the key?
  3. Step 3 · Two copies of one data key — KMS returns a 256-bit data key in plaintext and the same key encrypted under the KMS key. The KMS key itself never leaves KMS.
  4. Step 4 · Encrypt, store, forget — S3 encrypts the file with the plaintext data key (AES-256-GCM), stores the ciphertext next to the encrypted data key and erases the plaintext key from memory.
  5. Step 5 · Authorised download — the accountant’s GetObject makes S3 send the encrypted data key to KMS Decrypt; the key policy/IAM allow kms:Decrypt, so S3 can decrypt and return the file.
  6. Step 6 · Two locks — an intern with s3:GetObject but no kms:Decrypt gets AccessDenied — reading encrypted data needs permission on the bucket and on the key.
6 Explained part by part

Six parts of a KMS key

KMS key

What it is: symmetric AES-256 key inside KMS (HSM-backed).

Why it exists: Never leaves KMS.

Where it is used: alias/citybite-sales.

Key policy

What it is: resource policy on the key — mandatory.

Why it exists: Decides who may administer/use.

Where it is used: admins vs users.

Data keys

What it is: per-object keys from GenerateDataKey.

Why it exists: Envelope encryption, fast.

Where it is used: stored encrypted with the object.

Rotation

What it is: new key material on a schedule.

Why it exists: Limits exposure; old data still readable.

Where it is used: yearly default.

Enable / disable / delete

What it is: key states.

Why it exists: Instant lock; deletion is permanent.

Where it is used: 7–30 day waiting period.

Logs

What it is: every API use in CloudTrail.

Why it exists: Answers “who decrypted?”.

Where it is used: Decrypt events per object read.

Myth vs reality: things many websites still say

  • Myth: Encrypted data is safe from anyone with S3 access.
    Reality: With SSE-S3, S3 permission is enough to read.
    Proof: Situation.
  • Myth: KMS sends your key to S3.
    Reality: The KMS key never leaves KMS; only data keys do.
    Proof: Animation step 3.
  • Myth: Deleting a key is a harmless cleanup.
    Reality: It makes all data under it unreadable forever.
    Proof: Mistakes.
7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: Encryption scrambles data so only someone with the key can read it. The padlock in your browser is encryption while data travels; encrypted disks protect data while it rests.

Try: Look at the padlock next to a website address in your browser and click it — that is TLS, encryption in transit.

Check yourself: If someone steals an encrypted hard disk without the key, can they read it?

No — they see only scrambled data.

Level 1 · Beginner first steps on AWS

Understand: S3 encrypts every new object by default (SSE-S3). KMS is the AWS key service; your own key adds a second lock.

Try: Upload a file to S3 and look at its Properties → Server-side encryption.

Check yourself: What is the difference between “in transit” and “at rest”?

In transit = moving over the network (HTTPS); at rest = stored on disk.

Level 2 · Intermediate can do it alone

Understand: Create a customer managed key, set bucket default SSE-KMS with Bucket Key, enforce HTTPS-only and prove it.

Try: Do the hands-on Steps 1–3 (or the simulator).

Check yourself: A user has s3:GetObject but gets AccessDenied on an SSE-KMS object. Why?

They lack kms:Decrypt on the key (key policy or IAM).

Level 3 · Advanced designs for others

Understand: Design key policies with separation of duties, grants for services, rotation, cross-account keys and multi-Region keys.

Try: Write a key policy where SecurityAdmin manages the key but cannot decrypt, and DashboardRole can decrypt but not manage.

Check yourself: Why does rotation not require re-encrypting old data?

KMS keeps old key material versions to decrypt existing data; new data uses the new material.

Level 4 · Expert architect / interviewer

Understand: Plan encryption architecture: data classification, key hierarchy per data domain, BYOK/external key stores, CloudHSM, crypto-shredding by key deletion, and audit evidence.

Try: Design a key strategy for a bank: which keys, which accounts, who administers, how deletion is approved.

Check yourself: How can deleting a key be used deliberately?

“Crypto-shredding”: deleting the only key makes all data encrypted under it permanently unreadable — a fast, verifiable erasure (with care for retention laws).

9 Under the hood

HSMs, data keys, grants, rotation, multi-Region keys, quotas

What KMS does internally — and the limits you design around.

1 · Where keys live

KMS keys are generated and used inside FIPS 140-validated hardware security modules (HSMs) operated by AWS; the key material never leaves them in plaintext. You never see or download a KMS key (except asymmetric public keys). Applications get data keys instead, for local encryption.

2 · The three calls behind envelope encryption

APIWhat it does
GenerateDataKeyreturns a new data key in plaintext + encrypted under the KMS key
Decrypttakes an encrypted data key (ciphertext) and returns the plaintext data key if allowed
Encryptencrypts up to 4 KB directly with the KMS key (small secrets only)

The ciphertext includes which KMS key was used, so Decrypt does not need a key id for symmetric keys.

3 · Who may use a key

The key policy is the primary control — every key has one. IAM policies grant KMS permissions only if the key policy allows the account to use IAM (the default root statement does). Grants give temporary, narrow permissions (used by services like EBS to decrypt a volume for an instance). Encryption context — key/value pairs bound to the ciphertext — adds integrity and appears in CloudTrail; conditions can require it.

4 · Rotation, deletion and multi-Region keys

  • Automatic rotation creates new key material on a schedule (default 365 days, configurable 90–2,560); old material is kept to decrypt older data.
  • Deletion requires a 7–30 day waiting period; during it the key cannot be used — a safety net to notice mistakes.
  • Multi-Region keys share key material across Regions for DR/replication; each replica has its own policy.

Shared request quotathousands of cryptographic requests per second per account per Region (varies by Region/type)

High-volume S3 workloads without Bucket Keys can hit the KMS request quota (ThrottlingException) and run up request charges — enable Bucket Keys.

10 By role

Encryption work for developers, data, ML, DevOps and security

Who works with encryption, and how.

Software developer (backend)

Encrypts secrets and sensitive fields.

Uses: Secrets Manager (KMS-encrypted), KMS Encrypt for small values, AWS Encryption SDK.

A real task: Store the payment gateway API key in Secrets Manager; the app role has secretsmanager:GetSecretValue and kms:Decrypt on that key.

Skill to build: Never logging decrypted values; encryption context.

App / mobile developer

Protects data on devices and in transit.

Uses: HTTPS everywhere, pre-signed URLs, client-side encryption for very sensitive uploads.

A real task: Upload ID documents with a pre-signed PUT URL to an SSE-KMS bucket.

Skill to build: TLS, certificate pinning basics.

Data analyst

Needs kms:Decrypt to query encrypted data.

Uses: Athena/QuickSight roles with Decrypt on the data lake key.

A real task: Query fails with KMS AccessDenied → ask for key access, not bucket access.

Skill to build: Recognising KMS errors.

Data engineer

Designs encryption for the lake.

Uses: SSE-KMS per data zone, Bucket Keys, Glue/EMR encryption settings, cross-account key sharing.

A real task: raw/ and curated/ use different keys; analytics account gets Decrypt on curated only.

Skill to build: Key per domain; cost control.

ML / AI engineer

Encrypts training data, models and endpoints.

Uses: SageMaker volume/output KMS keys, encrypted S3 datasets, Bedrock with customer managed keys where supported.

A real task: Fine-tuned model artefacts encrypted with the team key.

Skill to build: Passing KMS key ids to training jobs.

DevOps / cloud engineer

Makes encryption the default.

Uses: EBS encryption by default, S3 default encryption, RDS encrypted, SCPs denying unencrypted resources.

A real task: An SCP denies creating unencrypted RDS instances.

Skill to build: Guard-rails, key lifecycle.

Security engineer

Owns key policies and evidence.

Uses: KMS key policies, CloudTrail Decrypt events, Config rules (s3-bucket-ssl-requests-only, encrypted-volumes).

A real task: Answer “who decrypted customer data in March?” from CloudTrail.

Skill to build: Key policy design, audit.

Encryption checklist

  • ☐ S3 default encryption on (SSE-S3 minimum; SSE-KMS for sensitive data).
  • ☐ HTTPS-only bucket policies on sensitive buckets.
  • ☐ EBS encryption by default enabled in every Region you use.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. A customer managed key costs about USD 1 per month (prorated); schedule its deletion at the end. Everything else is free-tier.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Create a KMS key and encrypt a message

    UI way — AWS Management Console

    1. KMS → Customer managed keys → Create key → Symmetric, Encrypt and decrypt → alias citybite-sales → you as administrator and user → Finish.

    CLI way — the same thing with commands

    KID=$(aws kms create-key --description 'CityBite sales lab' --query KeyMetadata.KeyId --output text)
aws kms create-alias --alias-name alias/citybite-sales --target-key-id $KID
echo 'Outlet 3 sold 120 thalis' > secret.txt
aws kms encrypt --key-id alias/citybite-sales --plaintext fileb://secret.txt --query CiphertextBlob --output text | base64 -d > secret.enc
head -c 60 secret.enc | od -c | head -3
aws kms decrypt --ciphertext-blob fileb://secret.enc --query Plaintext --output text | base64 -d
aws kms get-key-rotation-status --key-id $KID

    You should see: unreadable bytes for secret.enc, then the original sentence after decrypt (no key id needed — the ciphertext says which key), and KeyRotationEnabled: false (turn it on with enable-key-rotation).

    Direct KMS encrypt works only for up to 4 KB; larger data uses data keys (envelope encryption) — exactly what S3 does for you.

  3. 2 · Bucket that encrypts with your key and refuses plain HTTP

    UI way — AWS Management Console

    1. S3 → create citybite-sales-ACCOUNTID → Properties → Default encryption → SSE-KMS, key alias/citybite-sales, Bucket Key enabled.
    2. Permissions → Bucket policy → paste the HTTPS-only policy from the Deep dive (change the bucket name).

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text); B=citybite-sales-$ACC
aws s3 mb s3://$B --region ap-south-1
aws s3api put-bucket-encryption --bucket $B --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms","KMSMasterKeyID":"alias/citybite-sales"},"BucketKeyEnabled":true}]}'
aws s3api put-bucket-policy --bucket $B --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Deny\",\"Principal\":\"*\",\"Action\":\"s3:*\",\"Resource\":[\"arn:aws:s3:::$B\",\"arn:aws:s3:::$B/*\"],\"Condition\":{\"Bool\":{\"aws:SecureTransport\":\"false\"}}}]}"
printf 'outlet,item,amount\nAndheri,thali,120\n' > day1.csv
aws s3 cp day1.csv s3://$B/sales/day1.csv
aws s3api head-object --bucket $B --key sales/day1.csv --query '[ServerSideEncryption,SSEKMSKeyId,BucketKeyEnabled]' --output text
aws s3 cp s3://$B/sales/day1.csv - --endpoint-url http://s3.ap-south-1.amazonaws.com

    You should see: aws:kms arn:aws:kms:ap-south-1:…:key/… True — encrypted with your key — and then An error occurred (AccessDenied) for the plain-HTTP request: proof that non-HTTPS access is refused.

    The same command without --endpoint-url (HTTPS) works — keep both outputs as evidence for “any request without HTTPS must be refused”.

  4. 3 · Disable the key — watch everything lock

    UI way — AWS Management Console

    1. KMS → key → Key actions → Disable → try to download day1.csv in the S3 console → error → Enable again.

    CLI way — the same thing with commands

    aws kms disable-key --key-id $KID
aws s3 cp s3://$B/sales/day1.csv - 2>&1 | tail -1
aws kms enable-key --key-id $KID
aws s3 cp s3://$B/sales/day1.csv -
aws kms enable-key-rotation --key-id $KID
aws ec2 get-ebs-encryption-by-default --region ap-south-1
aws ec2 enable-ebs-encryption-by-default --region ap-south-1

    You should see: a KMS error (KMS.DisabledException) while disabled, the CSV again after enabling, rotation turned on, and EBS encryption by default switched on for the Region (new disks are encrypted automatically).

    Disabling a key is an emergency brake: every object encrypted with it becomes unreadable instantly, without touching the data.

Clean up and cost check

aws s3 rb s3://$B --force; aws kms delete-alias --alias-name alias/citybite-sales; aws kms schedule-key-deletion --key-id $KID --pending-window-in-days 7. Keep EBS encryption by default on — it is a good permanent setting. Delete secret.txt, secret.enc, day1.csv.

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Thinking SSE-S3 answers “who can decrypt?”.Encrypted = controlled.Use SSE-KMS with a customer managed key + key policy.
Removing the root statement from a key policy.Trying to tighten.Keep the account root statement or you may lock yourself out.
Deleting a key “to clean up”.Tidy habits.Deleted keys = unreadable data; disable first, delete only when sure.
Huge KMS bills from S3.One KMS call per object.Enable S3 Bucket Keys.

Granting s3:GetObject and wondering why reads fail.Forgot the key.Grant kms:Decrypt on the key (key policy or IAM).

Quick revision

Lesson 2.4 in one screen

  • In transit = TLS/HTTPS; at rest = SSE with keys in KMS.
  • SSE-KMS with your key = second lock + audit trail.

Interview and viva questions

Is SSE-S3 enough for exams?

It meets “encrypted at rest”; SSE-KMS shows key control.

Can I encrypt an existing unencrypted RDS database in place?

No — snapshot, copy encrypted, restore.

Does rotation re-encrypt my data?

No — old key material stays available for decryption.
