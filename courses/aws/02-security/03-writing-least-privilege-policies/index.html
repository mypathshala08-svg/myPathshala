1 The story

2 Definition

Writing least-privilege policies

Formal definition (write this in exams)

Least privilege is the practice of granting each identity only the permissions required to perform its tasks — specific actions on specific resources under specific conditions — and no more; in AWS it is implemented with precisely scoped IAM policies, explicit deny guard-rails, conditions, policy variables and attribute-based access control, and maintained through validation, testing and periodic removal of unused permissions.

In simple words

Give exactly what the job needs — specific actions, on specific folders, under the right conditions — and write down what must never happen.

Say it in an interview

30-second answer you can speak:

  • “I write policies from five questions — who, what action, which resource, under what condition, what must never happen — validate them with Access Analyzer and prove allow and deny with the simulator.”
  • “For faculty: ListBucket with an s3:prefix condition, Get/PutObject on notes/*, an explicit Deny on submissions/*, and a group so new members are one action.”

3 The big picture

Five questions that write any policy

New to computers? Start here. A policy is like the instructions you give a house-sitter: “You may water the plants in the balcony and use the kitchen, only during the day. Never open the bedroom cupboard.” Each part — who, what, where, when, never — becomes one part of the written policy.

Jargon buster:

  • Least privilege — giving only the access needed, nothing extra
  • Action — a specific thing you can do, like upload or delete
  • Prefix — a folder-like path inside a storage bucket, e.g. notes/
  • Condition — an extra rule like “only with OTP” or “only over a secure connection”
  • Explicit deny — a written “never”, which always wins

Type 1 · Exact actions (no service:*)

Definition (say it in an interview): List the specific API actions the job requires (for example s3:GetObject, s3:PutObject, s3:ListBucket) instead of wildcards like s3:*; the Service Authorization Reference lists every action, its resource types and condition keys.

In plain words (no jargon): Allow only the exact things the person must do.

Analogy: A shopping list with items, not “buy whatever is in the shop”.

How it works internally, step by step

  1. Job. Plain sentence.
  2. Actions. From the reference.
  3. Test. AccessDenied names gaps.
  4. Add. One by one.
  5. Avoid. service:*.

Words used above, in simple terms: API action = one operation, e.g. s3:PutObject · wildcard = * matches anything · Service Authorization Reference = AWS list of actions per service

Type 2 · Exact resources (ARNs and prefixes)

Definition (say it in an interview): Replace "Resource": "*" with the exact ARNs: bucket-level actions (ListBucket) on arn:aws:s3:::bucket, object-level actions on arn:aws:s3:::bucket/prefix/*, and the s3:prefix condition to limit what can be listed.

In plain words (no jargon): Point the permission at the exact bucket and folder.

Analogy: A key that opens one cupboard in one room, not the whole building.

How it works internally, step by step

  1. Bucket ARN. ListBucket.
  2. Object ARN. Get/Put/Delete.
  3. Prefix. folder/*.
  4. List limit. s3:prefix.
  5. Check. Simulator.

Words used above, in simple terms: ARN = Amazon Resource Name · prefix = start of an object key, like a folder · s3:prefix = condition key for listing

Type 3 · Conditions

Definition (say it in an interview): A Condition block makes a statement apply only when request context matches: e.g. aws:MultiFactorAuthPresent, aws:SecureTransport, aws:SourceIp, aws:RequestedRegion, aws:PrincipalTag, s3:prefix — using operators like StringEquals, StringLike, Bool, IpAddress, DateLessThan.

In plain words (no jargon): Extra “only if” rules inside a permission.

Analogy: A rule “you may enter the lab only with your ID card and only between 9 and 6”.

How it works internally, step by step

  1. Operator. StringEquals, Bool…
  2. Key. aws:… or service:…
  3. Value. what to match
  4. Multiple. AND between keys
  5. Lists. OR within values

Words used above, in simple terms: condition key = a fact about the request · operator = how to compare · IfExists = apply only if the key is present

Type 4 · Explicit Deny guards

Definition (say it in an interview): An explicit Deny statement records what must never happen (delete data, read submissions, disable logging, leave approved Regions); because Deny overrides every Allow from any policy, it keeps the rule true even if broader permissions are attached later by mistake.

In plain words (no jargon): A written “never” that beats every “yes”.

Analogy: A sign on the cupboard: “never open — even if someone gave you a master key”.

How it works internally, step by step

  1. Identify. Must-never actions.
  2. Write. Effect Deny.
  3. Scope. Exact resources.
  4. Condition. Optional (no MFA, no HTTPS).
  5. Test. explicitDeny in simulator.

Words used above, in simple terms: explicitDeny = simulator result for a Deny match · implicitDeny = no Allow found · guard-rail = rule that limits, not grants

Type 5 · Policy variables

Definition (say it in an interview): Policy variables such as ${aws:username}, ${aws:userid} or ${aws:PrincipalTag/department} are replaced with request values at evaluation time, so one policy can give each user their own folder or scope by tag.

In plain words (no jargon): Placeholders that become each user’s own name.

Analogy: One rule for the hostel: “each student may open only the locker with their own roll number”.

How it works internally, step by step

  1. Variable. ${aws:username}.
  2. Resource. path with variable.
  3. Version. 2012-10-17.
  4. Test. simulate two users.
  5. Roles. use tags instead.

Words used above, in simple terms: ${aws:username} = the IAM user name · ${aws:PrincipalTag/x} = a tag on the caller · runtime substitution = filled at each request

Type 6 · Tags — attribute-based access control (ABAC)

Definition (say it in an interview): ABAC grants access when attributes match — typically a tag on the principal and the same tag on the resource (aws:ResourceTag/project equals ${aws:PrincipalTag/project}) — so new projects and people need new tags, not new policies.

In plain words (no jargon): Access decided by matching labels on people and things.

Analogy: Coloured wristbands at an event: green-band people enter green-band areas.

How it works internally, step by step

  1. Tag people. Identity Center / IAM.
  2. Tag resources. At creation.
  3. Policy. Match condition.
  4. Protect tags. Deny tag changes.
  5. Scale. No new policies.

Words used above, in simple terms: ABAC = attribute-based access control · RBAC = role-based access control · aws:ResourceTag = tag on the target resource

How professionals write a policy: start from nothing, let real AccessDenied messages tell you what to add, validate, prove, and trim.

Least privilege 6 steps
Watch what happens
  1. Step 1 · Start from nothing — a new user, group or role has no permissions; every request is an implicit deny.
  2. Step 2 · Try the real task — Meena tries to list notes/; the AccessDenied message names the exact action (s3:ListBucket) and resource.
  3. Step 3 · Add exactly that — add s3:ListBucket on the bucket ARN with an s3:prefix condition for notes/* — not s3:* on *.
  4. Step 4 · Validate — IAM Access Analyzer policy validation catches typos (s3:GetObjects), wrong ARNs and risky patterns before deployment.
  5. Step 5 · Prove both sides — the Policy Simulator shows uploads to notes/ allowed, submissions/ explicitly denied, deletes implicitly denied.
  6. Step 6 · Trim over time — last-accessed information and Access Analyzer unused-access findings show permissions nobody uses — remove them.

Myth vs reality: things many websites still say

  • Myth: Least privilege slows teams down.
    Reality: The AccessDenied loop is fast; incidents are slow.
    Proof: Animation.
  • Myth: Implicit deny is enough for must-never rules.
    Reality: A future Allow can open it; explicit Deny cannot be overridden.

  • Myth: Wildcards are fine if the bucket is private.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: Least privilege means giving people only what their job needs — like a house-sitter who may water plants but not open your cupboard.

Try: Write a “house-sitter rule” for your home in five lines: who, may do what, where, when, never.

Check yourself: Is it safer to give “all access, just in case”?

No — extra access turns small mistakes or stolen passwords into big losses.

Level 1 · Beginner first steps on AWS

Understand: A policy lists actions (upload, read) on resources (one folder) — no wildcards like s3:*.

Try: Read the FacultyNotes policy in the Deep dive and mark each answer to the five questions.

Check yourself: Which part of the policy says “which folder”?

The Resource (an ARN such as arn:aws:s3:::edu-content/notes/*).

Level 2 · Intermediate can do it alone

Understand: Write prefix-scoped S3 policies, validate with Access Analyzer, prove four actions with the simulator.

Try: Do the hands-on Steps 1–2 (or the simulator).

Check yourself: What is the difference between implicitDeny and explicitDeny?

implicitDeny: nothing allowed it; explicitDeny: a Deny statement matched — no Allow can override it.

Level 3 · Advanced designs for others

Understand: Use conditions (MFA, HTTPS, IP, Region), policy variables and explicit Deny guard-rails; understand NotAction risks.

Try: Add an MFA-required Deny for uploads and test with the simulator’s context key aws:MultiFactorAuthPresent.

Check yourself: Why does aws:SourceIp fail for traffic through a VPC endpoint?

Requests via VPC endpoints carry private addresses; use aws:SourceVpce/aws:SourceVpc instead.

Level 4 · Expert architect / interviewer

Understand: Scale with ABAC, permission sets, SCP/RCP guard-rails, automated policy checks in CI and unused-access reviews.

Try: Write a custom policy check (Access Analyzer CheckNoNewAccess) that fails if a policy change adds s3:DeleteObject.

Check yourself: A team keeps re-tagging resources to gain access under ABAC. Fix?

Deny changing the controlling tag (aws:TagKeys / ResourceTag conditions) except for an admin role.

The faculty policy line by line; condition operators

The faculty policy (lab-exam pattern)

{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "SeeTheBucketInConsole", "Effect": "Allow",
     "Action": ["s3:ListAllMyBuckets", "s3:GetBucketLocation"], "Resource": "*"},
    {"Sid": "ListNotesAndOwnDrafts", "Effect": "Allow", "Action": "s3:ListBucket",
     "Resource": "arn:aws:s3:::edu-content",
     "Condition": {"StringLike": {"s3:prefix": ["", "notes/*", "drafts/${aws:username}/*"]}}},
    {"Sid": "ReadWriteNotes", "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"],
     "Resource": ["arn:aws:s3:::edu-content/notes/*", "arn:aws:s3:::edu-content/drafts/${aws:username}/*"]},
    {"Sid": "NeverSubmissions", "Effect": "Deny", "Action": "s3:*",
     "Resource": "arn:aws:s3:::edu-content/submissions/*"},
    {"Sid": "HttpsOnly", "Effect": "Deny", "Action": "s3:*", "Resource": "*",
     "Condition": {"Bool": {"aws:SecureTransport": "false"}}}
  ]
}

9 Under the hood

How conditions and variables are evaluated; limits; NotAction traps

Details that decide whether a policy really does what you think.

1 · How conditions are combined

  • Multiple keys in one Condition block → all must match (AND).
  • Multiple values for one key → any can match (OR).
  • Multiple operators → AND.
  • A missing key makes most operators false — use …IfExists when a key may be absent (e.g. MFA for CLI calls).
  • Multi-valued keys (tag lists) need ForAnyValue: or ForAllValues:.

2 · NotAction and NotResource traps

"Effect": "Allow", "NotAction": "iam:*" allows everything except IAM — including deleting databases. Use NotAction mostly with Deny: “Deny NotAction [list of allowed services]” builds a service allow-list. Always simulate both a forbidden and an allowed action.

3 · The S3 permission families

FamilyExamplesResource
BucketListBucket, GetBucketPolicy, PutBucketVersioningarn:aws:s3:::bucket
ObjectGetObject, PutObject, DeleteObjectarn:aws:s3:::bucket/key
Object versionsGetObjectVersion, DeleteObjectVersionarn:aws:s3:::bucket/key
AccountListAllMyBuckets, GetAccountPublicAccessBlock*

Versioned buckets: “never delete” must deny s3:DeleteObject and s3:DeleteObjectVersion; recovering a deleted file needs DeleteObject on the delete marker version or a copy of an older version.

4 · Where least privilege is enforced besides IAM

  • Bucket policies (resource side): HTTPS-only, VPC-only, organisation-only.
  • KMS key policies: who may encrypt/decrypt with each key (Lesson 2.4).
  • S3 Block Public Access: account/bucket guard against public policies and ACLs.
  • SCPs/RCPs: organisation-wide maximums.
  • Permissions boundaries: let teams create roles safely.

5 · Size and readability

Managed policies are limited to 6,144 characters (whitespace excluded); split by purpose, use Sids, and keep one statement per idea. Readable policies are reviewable policies.

Separate training data and model access.

Uses: SageMaker execution roles scoped to datasets/ and models/; Bedrock model-level permissions.

A real task: Fine-tuning job cannot read the HR bucket even if a path is mistyped.

Skill to build: Scoping data and model access.

DevOps / cloud engineer

Owns policy templates and guard-rails.

Uses: Permission sets, boundaries, SCPs, policy checks in CI.

A real task: PR fails automatically if a policy adds iam:* or s3:Delete* without approval.

Skill to build: Policy-as-code.

Security engineer

Measures and shrinks privilege.

Uses: Access Analyzer unused access, last accessed, external access findings.

A real task: Quarterly report: 30% of permissions unused → removed.

Skill to build: Least-privilege metrics.

Least-privilege checklist for any policy

  • ☐ Requirement written as a plain sentence and five answers.
  • ☐ No service:* and no "Resource": "*" except for actions that require it.
  • ☐ Bucket vs object ARNs correct; prefixes scoped.
  • ☐ Must-never rules as explicit Deny (incl. DeleteObjectVersion for versioned buckets).
  • ☐ Validated with Access Analyzer; simulated allow and deny.
  • ☐ Attached to a group/role, never directly to users.
  • ☐ Reviewed quarterly with last-accessed data.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. You will create a bucket, a policy, a group and two users, then delete everything. Cost: zero.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Write the policy and validate it before use

    UI way — AWS Management Console

    1. IAM → Policies → Create policy → JSON → paste FacultyNotes (Deep dive), change the bucket name.
    2. Look at the validation panel under the editor: errors, warnings, suggestions. Introduce a typo (s3:GetObjects) and watch it appear.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text); B=edu-lp-$ACC
aws s3 mb s3://$B --region ap-south-1
for k in notes/l1.txt submissions/a1.txt; do echo x | aws s3 cp - s3://$B/$k; done
cat > faculty.json <<EOF
{"Version":"2012-10-17","Statement":[
{"Effect":"Allow","Action":["s3:ListAllMyBuckets","s3:GetBucketLocation"],"Resource":"*"},
{"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::$B","Condition":{"StringLike":{"s3:prefix":["","notes/*","drafts/\${aws:username}/*"]}}},
{"Effect":"Allow","Action":["s3:GetObject","s3:PutObject"],"Resource":["arn:aws:s3:::$B/notes/*","arn:aws:s3:::$B/drafts/\${aws:username}/*"]},
{"Effect":"Deny","Action":"s3:*","Resource":"arn:aws:s3:::$B/submissions/*"}]}
EOF
aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY --policy-document file://faculty.json --query 'findings[].[findingType,issueCode]' --output text
sed 's/s3:GetObject"/s3:GetObjects"/' faculty.json > bad.json
aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY --policy-document file://bad.json --query 'findings[].[findingType,issueCode]' --output text

    You should see: little or nothing for the good policy (maybe a SUGGESTION), then an ERROR finding such as INVALID_ACTION for the typo — caught before anyone used it.

    Validation is free and takes a second — run it on every policy, ideally in your CI pipeline.

  3. 2 · Faculty group with two members — prove four actions

    UI way — AWS Management Console

    1. Policies → create FacultyNotes; User groups → create Faculty → attach it; Users → create meena and arjun → add to Faculty.
    2. Policy Simulator → choose user meena → S3 → test the four actions below.

    CLI way — the same thing with commands

    POL=$(aws iam create-policy --policy-name FacultyNotes --policy-document file://faculty.json --query Policy.Arn --output text)
aws iam create-group --group-name Faculty >/dev/null; aws iam attach-group-policy --group-name Faculty --policy-arn $POL
for u in meena arjun; do aws iam create-user --user-name $u >/dev/null; aws iam add-user-to-group --group-name Faculty --user-name $u; done
sleep 10; U=arn:aws:iam::$ACC:user/meena
sim(){ aws iam simulate-principal-policy --policy-source-arn $U --action-names $1 --resource-arns $2 --query 'EvaluationResults[0].EvalDecision' --output text; }
echo "PutObject notes/l2.txt:        $(sim s3:PutObject arn:aws:s3:::$B/notes/l2.txt)"
echo "GetObject submissions/a1.txt:   $(sim s3:GetObject arn:aws:s3:::$B/submissions/a1.txt)"
echo "DeleteObject notes/l1.txt:      $(sim s3:DeleteObject arn:aws:s3:::$B/notes/l1.txt)"
echo "PutObject drafts/meena/d.txt:   $(sim s3:PutObject arn:aws:s3:::$B/drafts/meena/d.txt)"

    You should see: allowed, explicitDeny, implicitDeny, allowed — the policy does exactly what the requirement says. Adding a third faculty member next semester = one add-user-to-group.

    explicitDeny (a written never) and implicitDeny (simply not allowed) are different — explain both in your evidence.

  4. 3 · Per-user folders with one policy (${aws:username})

    UI way — AWS Management Console

    1. Policy Simulator: test user arjun on drafts/meena/d.txt and drafts/arjun/d.txt.

    CLI way — the same thing with commands

    U2=arn:aws:iam::$ACC:user/arjun
for k in drafts/meena/d.txt drafts/arjun/d.txt; do
  echo "arjun PutObject $k: $(aws iam simulate-principal-policy --policy-source-arn $U2 --action-names s3:PutObject --resource-arns arn:aws:s3:::$B/$k --query 'EvaluationResults[0].EvalDecision' --output text)"
done

    You should see: implicitDeny for meena’s drafts and allowed for arjun’s own — one policy, private folders for every member.

    The simulator substitutes ${aws:username} with the user being simulated — exactly what happens at runtime.

Clean up and cost check

for u in meena arjun; do aws iam remove-user-from-group --group-name Faculty --user-name $u; aws iam delete-user --user-name $u; done; aws iam detach-group-policy --group-name Faculty --policy-arn $POL; aws iam delete-group --group-name Faculty; aws iam delete-policy --policy-arn $POL; aws s3 rb s3://$B --force

Common mistakes, why they happen, how to fix them

  1. s3:* on *
  2. ✔ s3:PutObject on bucket/folder/*

  4. SCP

Do I need to memorise action names?

No — use the Service Authorization Reference and AccessDenied messages.

Is AmazonS3ReadOnlyAccess least privilege?

Only if the person truly needs to read every bucket — usually not.

How often should policies be reviewed?

At least quarterly, using last-accessed and unused-access data.
