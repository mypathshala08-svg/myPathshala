1 The story

Private servers, four new problems

Before you start: Lessons 6.1 and 6.2.

🤔 TiffinGo moved its app servers into private subnets (6.1). Next morning: “yum update failed”, “can’t reach S3”, “analytics team can’t pull reports”, and “how do we SSH in now?”. Each problem has a different AWS answer — and picking the wrong one either breaks security or adds thousands to the bill.

Private subnets are safe because nothing routes to them from the internet. This lesson gives them controlled ways out: a NAT gateway for outbound internet, VPC endpoints to reach AWS services privately (gateway endpoints for S3/DynamoDB are free), VPC peering (and when to use Transit Gateway) to reach other VPCs, and Session Manager instead of a bastion host for admin access.

  • NAT gateway = outbound-only internet for private subnets.
  • Endpoints keep AWS-service traffic private (and off the NAT bill).
  • Peering is 1:1 and not transitive; prefer Session Manager to bastions.

2 Definition

NAT, endpoints, peering and bastion hosts

Formal definition (write this in exams)

A NAT gateway enables instances in private subnets to initiate outbound connections while blocking unsolicited inbound connections. VPC endpoints privately connect a VPC to supported AWS services — gateway endpoints (S3, DynamoDB) via route tables and interface endpoints via AWS PrivateLink ENIs. VPC peering is a non-transitive networking connection between two VPCs. A bastion host is a hardened jump server for administrative access, increasingly replaced by Systems Manager Session Manager.

In simple words

NAT lets private servers go out to the internet; endpoints let them reach AWS services privately; peering connects two VPCs; Session Manager lets you log in without opening any port.

Say it in an interview

30-second answer you can speak:

  • “Private subnets get outbound via per-AZ NAT gateways, S3/DynamoDB via free gateway endpoints, other AWS APIs via interface endpoints, and admins use Session Manager — no bastions.”
  • “Peering is one-to-one and non-transitive with no overlapping CIDRs; beyond a few VPCs or with on-prem I use Transit Gateway.”

3 The big picture

Pick the right door for each kind of traffic

New to computers? Start here. Your private subnet is a back office with no street door. A NAT gateway is the outgoing courier desk: staff can send letters out and get replies, but no stranger can walk in. A gateway endpoint is a private tunnel to the company warehouse (S3) — no street traffic, no courier fee. Peering is a corridor to the neighbouring office. Session Manager is a video call into the office instead of handing out keys to the back door (bastion).

Jargon buster:

  • NAT gateway — outbound internet for private subnets
  • Elastic IP — fixed public IP the NAT uses
  • Gateway endpoint — free private route to S3/DynamoDB
  • Interface endpoint — private ENI for other AWS APIs (PrivateLink)
  • VPC peering — private link between two VPCs
  • Bastion / Session Manager — jump host / port-less admin access

Type 1 · NAT gateway

Definition (say it in an interview): A NAT gateway is a managed, highly available (within one AZ) service that lets instances in private subnets start outbound IPv4 connections to the internet (public NAT, with an Elastic IP) or to other networks (private NAT), while preventing inbound connections. It scales to 100 Gbps; billing is per hour plus per GB processed.

In plain words (no jargon): Lets private servers reach the internet without being reachable from it.

Analogy: The outgoing courier desk: letters out, replies back, no visitors in.

How it works internally, step by step

  1. Placement. Public subnet.
  2. EIP. Required (public).
  3. Route. Private RT → nat.
  4. HA. Within one AZ.
  5. Cost. Hourly + per GB.

Words used above, in simple terms: SNAT = source address translation · EIP = Elastic IP — static public IPv4 · private NAT = NAT to other private networks

Type 2 · Designing NAT: per-AZ and NAT instances

Definition (say it in an interview): A NAT gateway lives in one AZ. For resilience, create one per AZ and give each AZ’s private subnets their own route table pointing to the local NAT — an AZ failure then affects only that AZ, and you avoid cross-AZ data charges. A NAT instance (EC2 with source/destination check disabled) is the legacy alternative: cheaper at tiny scale, but you manage patching, scaling and failover.

In plain words (no jargon): Put a NAT in each AZ so one AZ outage does not cut everyone’s internet.

Analogy: One courier desk per building, so a closed desk in one building does not stop the others.

How it works internally, step by step

  1. Scope. One AZ.
  2. Prod. One per AZ.
  3. Routes. Per-AZ RTs.
  4. Cross-AZ. Avoid charges.
  5. NAT instance. Disable src/dst check.

Words used above, in simple terms: src/dst check = EC2 setting that must be off for NAT instances · blast radius = how much breaks when one part fails · cross-AZ charge = data between AZs is billed

Type 3 · Gateway endpoints (S3, DynamoDB)

Definition (say it in an interview): A gateway VPC endpoint provides private connectivity to Amazon S3 and DynamoDB in the same Region by adding a route for the service’s prefix list (pl-…) to selected route tables. There is no hourly or data charge. An endpoint policy can limit which buckets/actions are allowed, and bucket policies can require aws:SourceVpce so data is reachable only from your VPC.

In plain words (no jargon): A free, private shortcut from your VPC to S3 and DynamoDB.

Analogy: A private tunnel straight to the company warehouse.

How it works internally, step by step

  1. Services. S3, DynamoDB.
  2. Mechanism. Route table entry.
  3. Cost. Free.
  4. Scope. Same Region.
  5. Policies. Endpoint + bucket.

Words used above, in simple terms: prefix list = managed list of a service’s IP ranges · aws:SourceVpce = condition key for endpoint ID · endpoint policy = IAM-style policy on the endpoint

Type 4 · Interface endpoints (AWS PrivateLink)

Definition (say it in an interview): An interface VPC endpoint creates elastic network interfaces with private IPs in your subnets for an AWS service (SSM, ECR, KMS, Secrets Manager, CloudWatch, STS…) or a partner/your own service exposed via PrivateLink. With private DNS, the normal service hostname resolves to these private IPs, so SDKs need no changes. Endpoints have security groups and are billed per AZ-hour plus per GB.

In plain words (no jargon): Private network doors to AWS services inside your own subnets.

Analogy: A private phone extension to each department instead of calling through the public exchange.

How it works internally, step by step

  1. Form. ENIs.
  2. DNS. Private DNS.
  3. Filter. Security group.
  4. Reach. From peered/on-prem too.
  5. Cost. Hourly + GB.

Words used above, in simple terms: PrivateLink = technology behind interface endpoints · private DNS = service name → endpoint IP · endpoint service = your own PrivateLink service

Type 5 · VPC peering

Definition (say it in an interview): VPC peering is a private, one-to-one connection between two VPCs (same or different account, same or different Region) using the AWS backbone. CIDRs must not overlap; peering is not transitive (A–B and B–C does not give A–C) and does not allow edge-to-edge routing (no using B’s NAT, IGW or VPN). Each side adds routes to the other’s CIDR and SG rules. No hourly charge; data across AZs/Regions is billed.

In plain words (no jargon): A private link between exactly two VPCs.

Analogy: A private corridor between two neighbouring offices.

How it works internally, step by step

  1. Scope. Two VPCs.
  2. Cross-account. Yes.
  3. Cross-Region. Yes.
  4. Transitive. No.
  5. CIDRs. No overlap.

Words used above, in simple terms: pcx = peering connection ID prefix · transitive = A→B→C forwarding — not allowed · edge-to-edge = using the peer’s gateways — not allowed

Type 6 · Transit Gateway (when peering is not enough)

Definition (say it in an interview): AWS Transit Gateway is a regional hub that connects thousands of VPCs and on-premises networks (Site-to-Site VPN, Direct Connect) in a hub-and-spoke model with its own route tables for segmentation. It is transitive by design, supports centralised egress (shared NAT) and inspection, and peers with TGWs in other Regions. Billed per attachment-hour and per GB processed.

In plain words (no jargon): A central router that connects many networks at once.

Analogy: A metro interchange station instead of a direct train between every pair of towns.

How it works internally, step by step

  1. Scope. Regional.
  2. Transitive. Yes.
  3. Attachments. VPC, VPN, DX, peering.
  4. Segmentation. TGW route tables.
  5. Cost. Hourly + GB.

Words used above, in simple terms: attachment = a network connected to the TGW · hub-and-spoke = star topology · central egress = shared NAT VPC

Type 7 · Bastion hosts vs Session Manager

Definition (say it in an interview): A bastion host is an EC2 instance in a public subnet that admins SSH into, then hop to private instances — it needs a public IP, an open port 22 (ideally restricted), and SSH key management. AWS Systems Manager Session Manager gives shell (and port-forwarding) access to instances through the SSM agent and IAM, with no inbound ports, no bastion and no keys, and logs sessions to S3/CloudWatch. Private subnets need NAT or SSM interface endpoints for the agent.

In plain words (no jargon): Log in to private servers without opening any port.

Analogy: Handing out back-door keys vs a recorded video call into the office.

How it works internally, step by step

  1. Bastion. Public, port 22.
  2. SSM. Agent + IAM role.
  3. Ports. None inbound.
  4. Logging. S3/CloudWatch.
  5. Needs. NAT or SSM endpoints.

Words used above, in simple terms: jump host = another name for bastion · SSM agent = preinstalled on Amazon Linux · port forwarding = tunnel a remote port to localhost

9 Under the hood

Hyperplane NAT, prefix lists, PrivateLink

What happens behind these paths.

1 · NAT gateways run on Hyperplane

A NAT gateway is not one EC2 box — it is built on AWS Hyperplane, the same distributed state-tracking layer behind NLB and PrivateLink. It rewrites the source IP/port to its own Elastic IP and tracks up to 55,000 simultaneous connections to each unique destination (IP, port, protocol); more EIPs raise that limit. ErrorPortAllocation metrics reveal exhaustion.

2 · Prefix lists make gateway endpoints work

A gateway endpoint inserts a route whose destination is an AWS-managed prefix list (e.g. pl-78a54011 for S3 in Mumbai) containing S3’s IP ranges. Because those ranges are more specific than 0.0.0.0/0, longest-prefix match sends S3 traffic to the endpoint automatically.

3 · PrivateLink is one-way by design

An interface endpoint’s ENI can only initiate connections to the service behind it (an NLB or AWS service). The provider can never reach into the consumer VPC — which is why PrivateLink works even with overlapping CIDRs, unlike peering.

4 · Session Manager connects outbound

The SSM agent on the instance opens an outbound HTTPS (443) WebSocket to the ssmmessages endpoint. Your session rides that connection — so the instance needs outbound 443 (via NAT or interface endpoints) but no inbound rules at all.

Interview and viva questions

Is a NAT gateway expensive?

In Mumbai about USD 0.056 per hour (≈ USD 41/month) plus per-GB processing. Use endpoints for AWS-service traffic and one NAT per AZ only in production.

Do I need interface endpoints if I have NAT?

No — they are for private-only subnets, compliance, or avoiding NAT data charges for heavy AWS API traffic.

Can I peer VPCs in different accounts?

Yes, and across Regions. The other account accepts the request.
