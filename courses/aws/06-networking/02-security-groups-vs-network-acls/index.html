1 The story

The site that went blank

Before you start: Lessons 3.4 and 6.1.

🤔 After 6.1, TiffinGo’s web server loaded fine. Then the network team added a “tight” network ACL — inbound 443, outbound 443 — and the site went blank for every customer. Nothing was wrong with the security group. The NACL had forgotten that replies do not go back to port 443.

AWS gives you two packet filters. Security groups wrap each instance (ENI): stateful, allow-only, and they can reference other security groups. Network ACLs guard each subnet: stateless, numbered allow and deny rules, first match wins. This lesson follows one packet through both, builds a three-tier SG chain with no IP addresses in it, writes a correct NACL with ephemeral ports, and blocks a scanner IP.

  • Traffic passes the NACL (subnet) and then the SG (instance).
  • SG = stateful allow-list; NACL = stateless numbered allow/deny.
  • Reference SGs, not IPs; use NACLs for guard rails and blocking.

A “tight” network ACL allowed 443 in and out — and every customer saw a blank page, because replies go back to random high ports and NACLs remember nothing.

Riya

Sir, the security group allows 443 and the NACL allows 443 both ways. Why is the site blank?

Arjun Sir

Where does the reply go — to port 443 on the customer’s phone?

Kabir

No… to a random high port the phone opened, like 51234.

Arjun Sir

Exactly. The security group remembers the connection and lets the reply out. The NACL has no memory — it sees a new packet to port 51234 and its rules say deny.

Riya

So we add outbound 1024–65535?

Arjun Sir

Yes. And while we are here: use security groups for real access rules, referencing each other, and keep NACLs simple — broad guard rails and blocking bad IPs.

2 Definition

Security groups and network ACLs

Formal definition (write this in exams)

A security group is a stateful virtual firewall associated with elastic network interfaces that evaluates allow rules for inbound and outbound traffic by protocol, port and source/destination (CIDR, prefix list or security group). A network ACL is an optional stateless layer of security for subnets with numbered allow and deny rules evaluated in order, applied separately to inbound and outbound traffic crossing the subnet boundary.

In simple words

Security groups are smart, memory-keeping allow lists on each instance; network ACLs are simple numbered gate rules on each subnet that check traffic both ways.

Say it in an interview

30-second answer you can speak:

  • “I put access rules in security groups, chained by reference — alb-sg to web-sg to db-sg — and keep NACLs broad, with explicit denies when needed.”
  • “NACLs are stateless, so they need ephemeral ports 1024–65535 for return traffic; SGs are stateful and need no rule for replies.”

3 The big picture

Two filters, compared — and chained

New to computers? Start here. Think of an apartment society. The NACL is the society gate guard with a numbered rule book: he checks every person entering and leaving, and has no memory — a guest leaving is checked again like a stranger. The security group is the flat’s own door lock with a smart guard: he only has an allow list, and once he lets a guest in he remembers them and lets them out without asking.

Jargon buster:

  • Security group (SG) — stateful firewall on an instance/ENI
  • Network ACL (NACL) — stateless firewall on a subnet
  • Stateful — remembers connections; replies allowed
  • Stateless — checks every packet independently
  • Ephemeral ports — 1024–65535 used by clients for replies
  • Rule number — NACL order — lowest first, first match wins

Type 1 · Security groups

Definition (say it in an interview): A security group is a stateful virtual firewall attached to elastic network interfaces (instances, load balancers, RDS, Lambda in VPC, endpoints). It has inbound and outbound allow rules only (protocol, port range, source/destination); everything not allowed is denied, and return traffic for allowed connections is automatically permitted. An ENI can have up to 5 SGs (adjustable); rules from all of them are combined.

In plain words (no jargon): An allow list on each instance that remembers conversations.

Analogy: The flat’s door guard with an allow list — and a good memory.

How it works internally, step by step

  1. Scope. ENI.
  2. Rules. Allow only.
  3. State. Stateful.
  4. Evaluation. All rules, union.
  5. Changes. Immediate.

Words used above, in simple terms: ENI = elastic network interface · inbound/outbound = into / out of the ENI · stateful = connection tracking

Type 2 · Security group references (tier chains)

Definition (say it in an interview): An SG rule’s source (or destination) can be another security group: “allow 3306 from sg-web” means any ENI that has sg-web attached may connect, whatever its IP. This builds tier chains (alb-sg → web-sg → db-sg) that survive scaling and IP changes, and works across peered VPCs in the same Region. Managed prefix lists similarly group CIDRs (e.g. office ranges, CloudFront origin-facing ranges).

In plain words (no jargon): Allow traffic from “whoever is in that group”.

Analogy: A society rule: “residents of Tower B may use the gym” — not a list of flat numbers.

How it works internally, step by step

  1. Source. SG ID.
  2. Scaling. Automatic.
  3. Self-ref. Clusters.
  4. Prefix lists. Named CIDR sets.
  5. Peering. Same-Region refs.

Words used above, in simple terms: SG reference = SG ID as source · prefix list = named set of CIDRs · self-referencing = SG allows itself

Type 3 · Network ACLs

Definition (say it in an interview): A network ACL is a stateless filter at the subnet boundary. Each subnet is associated with exactly one NACL (a NACL can serve many subnets). Rules have a number (1–32766), protocol, port range, CIDR and ALLOW/DENY, for inbound and outbound separately; they apply to all traffic entering or leaving the subnet — not traffic between instances in the same subnet.

In plain words (no jargon): A numbered allow/deny list at the edge of each subnet.

Analogy: The society gate guard with a numbered rule book and no memory.

How it works internally, step by step

  1. Scope. Subnet.
  2. Rules. Allow + deny.
  3. State. Stateless.
  4. Sources. CIDR only.
  5. Intra-subnet. Not filtered.

Words used above, in simple terms: NACL = network access control list · association = subnet ↔ NACL · stateless = no connection memory

Type 4 · NACL rule numbers and evaluation

Definition (say it in an interview): NACL rules are evaluated in ascending rule number; the first rule that matches the packet is applied and evaluation stops. The * rule (cannot be removed) denies anything that matched nothing. Number in steps of 10 or 100 so you can insert rules later; put specific DENY rules before broad ALLOW rules.

In plain words (no jargon): Rules are read from the smallest number; first match wins.

Analogy: A rule book read from the top — the first matching line decides.

How it works internally, step by step

  1. Range. 1–32766.
  2. Order. Ascending.
  3. Stop. First match.
  4. *. Implicit deny.
  5. Limits. 20 rules each way (adjustable to 40).

Words used above, in simple terms: rule number = priority (lower = first) · first match = evaluation stops · implicit deny = the * rule

Type 5 · Ephemeral ports and the return path

Definition (say it in an interview): Every TCP/UDP connection has a client ephemeral port (Linux 32768–60999, Windows 49152–65535, NAT gateways and ELB 1024–65535). Because NACLs are stateless, a subnet that serves clients needs an outbound rule to 1024–65535, and a subnet whose instances start connections (updates, API calls) needs an inbound rule for 1024–65535 for the replies. Security groups need neither.

In plain words (no jargon): Replies come back on random high ports — stateless rules must allow them.

Analogy: A courier must be allowed back out through the gate to the same house he came from — the gate guard doesn’t remember him.

How it works internally, step by step

  1. Client side. Random high port.
  2. Linux. 32768–60999.
  3. Windows. 49152–65535.
  4. Safe range. 1024–65535.
  5. SG. Not needed.

Words used above, in simple terms: ephemeral port = temporary client port · 5-tuple = src/dst IP + ports + protocol · return traffic = replies

Type 6 · Defaults: default SG, default NACL, new resources

Definition (say it in an interview): Every VPC has a default security group (inbound: from itself; outbound: all) and a default NACL (allows all inbound and outbound) that new subnets use. A newly created custom security group has no inbound and all outbound; a newly created custom NACL denies everything until you add rules — associating it with a subnet instantly cuts traffic.

In plain words (no jargon): What each filter does before you change anything.

Analogy: Default NACL = an open society gate; custom NACL = a gate that is locked shut until you write the rule book.

How it works internally, step by step

  1. Default SG in. Self only.
  2. Custom SG in. Nothing.
  3. SG out. All.
  4. Default NACL. Allow all.
  5. Custom NACL. Deny all.

Words used above, in simple terms: default SG = created with the VPC · default NACL = used by new subnets · CIS benchmark = security best-practice checklist

Type 7 · Layered defence and troubleshooting

Definition (say it in an interview): Use security groups as the primary, fine-grained control (per tier, referencing each other); keep NACLs simple — mostly allow-all or broad subnet rules plus explicit DENYs — and add AWS WAF / Network Firewall for application-layer or deep inspection. To debug, read VPC Flow Logs (REJECT records show which side blocked) and run Reachability Analyzer, which names the exact SG or NACL rule blocking a path.

In plain words (no jargon): Security groups do the real work; NACLs add a coarse outer fence.

Analogy: Door locks for each flat, a simple gate rule book for the society, and the CCTV log to see what happened.

How it works internally, step by step

  1. Primary. SGs.
  2. Outer. NACLs.
  3. L7. WAF.
  4. Inspect. Network Firewall.
  5. Debug. Flow Logs, Reachability.

Words used above, in simple terms: defence in depth = multiple layers · WAF = web application firewall · Reachability Analyzer = static path analysis

5 How it works, step by step

One packet through two filters

NACL in → SG in → server → SG out → NACL out → block an IP.

Animated

One request through two filters

Follow a request from a user to a web server and back: first the subnet’s network ACL, then the instance’s security group — and see why one is stateful and the other is not.

Two filters, one packet 6 steps
Watch what happens
  1. Step 1 · NACL inbound — the packet first meets the subnet’s network ACL. Rules are checked from the lowest number; rule 100 allows TCP 443, so it passes.
  2. Step 2 · Security group — next the instance’s security group: web-sg allows 443 from anywhere, so the packet reaches the web server.
  3. Step 3 · Reply leaves the SG — security groups are stateful — they remember the connection, so the reply is allowed out without any outbound rule.
  4. Step 4 · NACL blocks the reply — NACLs are stateless — the reply is a new packet to the user’s ephemeral port (e.g. 51234). Outbound allows only 443, so it is dropped.
  5. Step 5 · Fix: ephemeral ports — allow outbound TCP 1024-65535 on the NACL. The reply leaves the subnet and the page loads.
  6. Step 6 · Block one IP — a scanner keeps probing. Security groups can only allow, so add NACL rule 50 DENY 203.0.113.9/32 — it is checked before rule 100.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: AWS checks network traffic twice: once at the edge of the subnet (network ACL) and once at the instance (security group).

Try: At a hostel, the main-gate guard checks everyone with a printed list; the warden at your floor knows who is visiting you. That is NACL and SG.

Check yourself: If the warden lets your friend in, does the floor guard ask again when your friend leaves?

No — he remembers (stateful). The main-gate guard does ask (stateless).

Level 1 · Beginner first steps on AWS

Understand: SGs: allow-only, stateful, per ENI, can reference SGs. NACLs: numbered allow/deny, stateless, per subnet, first match wins.

Try: Do the simulator, then write the NACL rules for a public web subnet on paper including ephemeral ports.

Check yourself: Rule 100 ALLOW 0.0.0.0/0 and rule 200 DENY 1.2.3.4 — is 1.2.3.4 blocked?

No. Rule 100 matches first.

Level 2 · Intermediate can do it alone

Understand: Build an SG chain, a custom NACL, reproduce the ephemeral-port outage, block an IP, and read REJECTs in Flow Logs.

Try: Do the hands-on and capture the inbound ACCEPT / outbound REJECT pattern in Logs Insights.

Check yourself: Web can’t reach the DB: SG db-sg allows 3306 from web-sg. Two other things to check?

The DB subnet’s NACL (both directions, ephemeral ports) and whether the web ENI really has web-sg attached.

Level 3 · Advanced designs for others

Understand: Design SG strategies for many teams (per-tier SGs, prefix lists, Firewall Manager policies), keep NACLs minimal, and automate IP blocks from detections.

Try: Write a Firewall Manager / Config policy that flags 0.0.0.0/0 on ports 22/3389 across all accounts.

Check yourself: When are NACLs worth the complexity?

For subnet-wide guard rails (e.g. data subnets accept only from app CIDRs), emergency IP blocks, and compliance requirements for a second layer.

Level 4 · Expert architect / interviewer

Understand: Own network security architecture: SGs + NACLs + WAF + Network Firewall + Shield, central inspection VPCs, and evidence for auditors.

Try: Design layered controls for a payments platform and map each to a regulatory requirement.

Check yourself: How would you prove to an auditor that the DB is unreachable from the internet?

Reachability Analyzer results, SG/NACL configs from Config history, and Flow Logs showing only app-subnet sources.

Same-subnet traffic

NACLs filter only traffic crossing the subnet boundary. Two instances in the same subnet are filtered only by their security groups — which is why SGs, not NACLs, provide micro-segmentation.

9 Under the hood

Connection tracking and where filtering happens

Where filtering actually happens.

1 · Both filters live in the Nitro host

Neither filter is a box in the path. Security group and NACL rules are pushed to the hypervisor (Nitro card) of every host and enforced as packets leave or enter your ENI — so they add no latency hop and scale with your instances.

2 · Connection tracking

Security groups are stateful through connection tracking: the host records each allowed flow (5-tuple) and permits its replies. Some flows are “untracked” (e.g. when inbound and outbound rules both allow 0.0.0.0/0 for all ports) — then they are not limited by tracking tables. Very high connection counts can hit conntrack allowances; ENA metrics like conntrack_allowance_exceeded reveal it.

3 · Rule changes apply instantly — mostly

Adding a rule takes effect immediately. Removing a rule may not cut an already-tracked connection right away; tracked flows can continue until they go idle. NACL changes, being stateless, apply to the very next packet.

4 · Limits

Default limits: 60 inbound + 60 outbound rules per SG, 5 SGs per ENI (product ≤ 1,000), 20 rules per NACL direction (up to 40). Prefix lists count as their max-entries toward SG rule limits.

    CLI way — the same thing with commands

    MY=$(curl -s https://checkip.amazonaws.com)

1 Block function

IAM: ec2:DescribeNetworkAcls, ec2:CreateNetworkAclEntry on the NACL; dynamodb:PutItem on the table.

import boto3, os, time
ec2 = boto3.client('ec2'); ddb = boto3.client('dynamodb')
ACL, TABLE = os.environ['ACL'], os.environ['TABLE']
def handler(event, _):
    ip = event['ip'] + '/32'
    entries = ec2.describe_network_acls(NetworkAclIds=[ACL])['NetworkAcls'][0]['Entries']
    used = {e['RuleNumber'] for e in entries if not e['Egress']}
    if any(e.get('CidrBlock') == ip and e['RuleAction'] == 'deny' for e in entries):
        return {'status': 'already blocked'}
    n = next(i for i in range(1, 50) if i not in used)
    ec2.create_network_acl_entry(NetworkAclId=ACL, RuleNumber=n, Protocol='-1', RuleAction='deny', Egress=False, CidrBlock=ip)
    ddb.put_item(TableName=TABLE, Item={'ip': {'S': ip}, 'rule': {'N': str(n)}, 'expires': {'N': str(int(time.time()) + 86400)}})
    return {'status': 'blocked', 'rule': n}

2 Unblock function (runs every 15 min via EventBridge Scheduler)

import boto3, os, time
ec2 = boto3.client('ec2'); ddb = boto3.client('dynamodb')
ACL, TABLE = os.environ['ACL'], os.environ['TABLE']
def handler(event, _):
    now = int(time.time()); done = []
    for it in ddb.scan(TableName=TABLE)['Items']:
        if int(it['expires']['N']) <= now or event.get('force'):
            ec2.delete_network_acl_entry(NetworkAclId=ACL, RuleNumber=int(it['rule']['N']), Egress=False)
            ddb.delete_item(TableName=TABLE, Key={'ip': it['ip']}); done.append(it['ip']['S'])
    return {'unblocked': done}

  • Reference SGs, not IPs.
  • NACL: numbered, both ways, ephemeral ports.
  • Deny before allow; prove with Flow Logs.

Interview and viva questions

Do I need NACLs at all?

Many teams keep the default allow-all NACL and rely on security groups. Add custom NACLs for subnet guard rails, compliance, or blocking IPs.

Can an instance have several security groups?

Yes — up to 5 per network interface by default; their rules are combined.

Do rule changes need a restart?

No. Both apply immediately to running instances.

Real-world scenario questions (asked in company interviews)

Interview and viva questions.

Any companyFresher

“Difference between SG and NACL?”

Basics.

The interviewer is checking: Four differences.

Show a strong answer

“SG: instance level, stateful, allow only, all rules evaluated. NACL: subnet level, stateless, allow and deny, numbered first-match.”

Avoid: Saying SGs can deny.

Service companyJunior

“Site broke after adding a NACL — why?”

Debugging.

The interviewer is checking: Ephemeral ports.

Show a strong answer
  • NACL is stateless; outbound replies to client ports 1024–65535 must be allowed; confirm with Flow Logs.

Avoid: Blaming the security group.

Product companyMid-level

“Secure a three-tier app’s network.”

Design.

The interviewer is checking: SG chain + NACL rails.

Show a strong answer
  • alb-sg → web-sg → db-sg references, data subnet NACL accepting only app CIDRs, WAF on ALB, Flow Logs, Reachability Analyzer proofs.

Avoid: One SG with everything open.
