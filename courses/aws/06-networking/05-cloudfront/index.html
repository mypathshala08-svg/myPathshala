1 The story

A slow, costly, public menu site

Before you start: Lessons 4.1, 4.2 and 6.4.

🤔 TiffinGo’s menu site lived in an S3 bucket in Mumbai with public read access. Students in Guwahati waited 2–3 seconds for photos, the S3 data-transfer bill grew every month, and a security review flagged the public bucket. One service fixed all three.

Amazon CloudFront is AWS’s content delivery network (CDN): 600+ edge locations cache your content close to users, so repeat requests never reach your origin. This lesson follows a cache miss and a cache hit, builds a distribution in front of a private S3 bucket with Origin Access Control, routes /api/* to a load balancer without caching, and handles deployments with invalidations and versioned file names.

  • CloudFront caches at edge locations near users; origins stay in one Region.
  • Behaviors map path patterns to origins and cache policies.
  • OAC keeps S3 private; versioned names beat invalidations.

A public S3 site in Mumbai was slow far away, costly at scale and flagged by security — CloudFront with a private origin fixed all three.

Riya

Sir, our site is in Mumbai. Why is it slow in Guwahati?

Every photo crosses the country, every time. Distance is latency.

Kabir

Arjun Sir

2 Definition

Amazon CloudFront

Formal definition (write this in exams)

Amazon CloudFront is a global content delivery network that delivers content through a worldwide network of edge locations and regional edge caches. A distribution defines origins (Amazon S3, Elastic Load Balancing, API Gateway or custom HTTP servers) and ordered cache behaviors that apply cache, origin-request and response-headers policies by path pattern; Origin Access Control restricts S3 origins to the distribution, and integrations with ACM, AWS WAF and Shield secure delivery at the edge.

In simple words

CloudFront keeps copies of your website’s files in cities near your users, so pages load fast, your servers do less work, and your storage can stay private.

Say it in an interview

30-second answer you can speak:

  • “Static assets on a private S3 origin with OAC, hashed file names with one-year TTLs, index.html with a short TTL and an invalidation per deploy.”
  • “/api/* goes to the ALB with caching disabled; ACM cert in us-east-1, WAF managed rules and a rate-based rule on the distribution.”

3 The big picture

Paths to origins — and a private bucket

New to computers? Start here. CloudFront is like a chain of local kirana stores stocking items from a central warehouse. The first customer who asks for a new item waits while the shop orders it from the warehouse (cache miss); after that it is on the shelf for everyone (cache hit) until its expiry date (TTL). The warehouse (your origin) only deals with the shops, never directly with customers (OAC).

Jargon buster:

  • CDN — network of caches near users
  • Edge location — a CloudFront site in a city
  • Origin — where the real content lives (S3, ALB…)
  • Distribution — your CloudFront configuration + domain
  • Cache hit / miss — served from edge / fetched from origin
  • TTL — how long the edge keeps a copy

Type 1 · Edge locations and regional edge caches

Definition (say it in an interview): CloudFront has 600+ edge locations (points of presence) in 100+ cities — including Mumbai, Chennai, Delhi, Hyderabad, Bengaluru and Kolkata — plus larger regional edge caches that sit between edges and origins. DNS routes each user to a nearby edge; misses go to the regional cache, then to the origin over the AWS backbone. Origin Shield adds one more central caching layer to protect the origin.

In plain words (no jargon): A worldwide network of caches close to your users.

Analogy: Local shops, then the district depot, then the central warehouse.

How it works internally, step by step

  1. Edges. 600+ PoPs.
  2. Regional caches. Second tier.
  3. Origin Shield. Optional third.
  4. Routing. DNS to nearest.
  5. Scope. Global service.

Words used above, in simple terms: PoP = point of presence · regional edge cache = larger mid-tier cache · Origin Shield = central cache in front of origin

Type 2 · Distributions and origins

Definition (say it in an interview): A distribution is a CloudFront configuration with a domain (dxxxx.cloudfront.net, plus alternate domain names with an ACM certificate) and one or more origins: S3 buckets, ALBs, API Gateway, MediaStore, or any HTTP(S) server (EC2, on-prem). Origin groups give origin failover (primary/secondary). Changes take a few minutes to deploy globally.

In plain words (no jargon): Your CloudFront setup: which sources to fetch from and under which domain.

Analogy: One chain of shops that can stock from several warehouses.

How it works internally, step by step

  1. Domain. d…cloudfront.net.
  2. Alternate names. ACM cert in us-east-1.
  3. Origins. S3, ALB, custom.
  4. Origin groups. Failover.
  5. Deploy. Minutes, global.

Words used above, in simple terms: alternate domain (CNAME) = your domain on the distribution · origin group = primary + secondary origins · price class = which edges are used (cost)

Type 3 · Cache behaviors and path patterns

Definition (say it in an interview): A distribution has an ordered list of cache behaviors, each with a path pattern (/api/*, *.jpg), a target origin, allowed HTTP methods, viewer protocol policy (redirect HTTP→HTTPS), and policies: cache policy, origin request policy and response headers policy, plus optional functions (CloudFront Functions / Lambda@Edge). The default (*) behavior catches the rest.

In plain words (no jargon): Rules that send each URL path to the right origin with the right caching.

Analogy: Shop rules: fresh vegetables from the farm daily, packaged goods from the warehouse monthly.

How it works internally, step by step

  1. Order. First match.
  2. Default. * last.
  3. Methods. GET/HEAD or all.
  4. HTTPS. Redirect.
  5. Functions. Edge code.

Words used above, in simple terms: path pattern = URL path match like /api/* · viewer protocol policy = HTTP/HTTPS rules for users · CloudFront Functions = lightweight JS at the edge

Type 4 · Cache policies, cache keys and TTL

Definition (say it in an interview): A cache policy defines the cache key (URL path plus any query strings, headers and cookies you include) and TTLs (minimum, default, maximum) that bound the origin’s Cache-Control/Expires. Every value in the key creates separate cached copies, so include only what changes the response. Managed policies: CachingOptimized (no query/headers/cookies, 1 day default), CachingDisabled.

In plain words (no jargon): Rules for what counts as “the same request” and how long copies last.

Analogy: Shelf labels: if the label includes the customer’s name, nobody else can take that packet.

How it works internally, step by step

  1. Key. Path + chosen values.
  2. TTL bounds. Min/default/max.
  3. Origin headers. Cache-Control.
  4. Managed. Optimized/Disabled.
  5. Compression. gzip/brotli.

Words used above, in simple terms: cache key = what identifies a cached object · Cache-Control = origin header with caching rules · origin request policy = what is forwarded but not in the key

Type 5 · Origin Access Control (private S3 origins)

Definition (say it in an interview): Origin Access Control (OAC) makes CloudFront sign requests to S3 with SigV4. The bucket stays private (Block Public Access on) and its bucket policy allows s3:GetObject for the service principal cloudfront.amazonaws.com only when AWS:SourceArn equals your distribution’s ARN. OAC supports SSE-KMS buckets (with a key policy grant) and replaces the older Origin Access Identity (OAI).

In plain words (no jargon): Keeps your S3 bucket private while CloudFront serves its files.

Analogy: The warehouse ships only to its own shops, verified by a signed order form.

How it works internally, step by step

  1. Bucket. Private.
  2. Signing. SigV4.
  3. Principal. cloudfront.amazonaws.com.
  4. Condition. AWS:SourceArn.
  5. Legacy. OAI.

Words used above, in simple terms: OAC = origin access control · OAI = older origin access identity · SourceArn = which distribution made the request

Type 6 · Invalidations and versioned file names

Definition (say it in an interview): Edges keep copies until the TTL ends. An invalidation (/index.html, /img/*) removes cached copies across all edges within minutes; the first 1,000 paths per month are free, then USD 0.005 per path (a wildcard counts as one). The better pattern is versioned file names (app.3f9c.js) with long TTLs, plus a short TTL or invalidation only for index.html.

In plain words (no jargon): How to make users see new files after you change them.

Analogy: Recalling old stock from all shops vs simply giving the new product a new barcode.

How it works internally, step by step

  1. Invalidation. Drop copies.
  2. Free. 1,000 paths/month.
  3. Wildcard. Counts as one.
  4. Versioning. New URLs.
  5. Browsers. Need versioning.

Words used above, in simple terms: invalidation = removing objects from edge caches · cache busting = changing URLs to force new fetches · immutable = Cache-Control hint: never changes

Type 7 · Security at the edge: HTTPS, WAF, geo and signed URLs

Definition (say it in an interview): CloudFront terminates TLS at the edge using an ACM certificate in us-east-1 for your alternate domains, with HTTP→HTTPS redirect and modern TLS policies. Attach an AWS WAF web ACL for managed rule groups and rate-based rules; AWS Shield Standard DDoS protection is automatic. Geo restriction allows/blocks countries; signed URLs/cookies (with key groups) limit private content to paying users.

In plain words (no jargon): Protect your site where users connect — before traffic reaches your servers.

Analogy: Shop security: guarded entrance, ID checks, and members-only shelves.

How it works internally, step by step

  1. Certificate. ACM us-east-1.
  2. TLS. Security policy.
  3. WAF. Rules + rate limits.
  4. Shield. Standard free.
  5. Private content. Signed URLs/cookies.

Words used above, in simple terms: ACM = AWS Certificate Manager · rate-based rule = block IPs above a request rate · signed URL = time-limited URL signed with your key

How CloudFront serves a page from 10 km away

Two students in Chennai open TiffinGo. Watch the first request travel to Mumbai, the second come straight from the edge, the API bypass the cache, and a deployment refresh it.

Cache at the edge 6 steps
Watch what happens
  1. Step 1 · Nearest edge, cache miss — DNS sends Priya to the closest of 600+ CloudFront edge locations (Chennai). It has never seen menu.jpg — a miss.
  2. Step 2 · Fetch from origin — the edge asks the regional edge cache in Mumbai, then the origin. The S3 bucket is private; it accepts the request only because it is signed by the distribution’s Origin Access Control.
  3. Step 3 · Cache and return — the edge stores the object for the cache policy’s TTL (here 24 h) and returns it. First load ≈ 180 ms.
  4. Step 4 · Cache hit — Arjun asks for the same file. The Chennai edge already has it: 12 ms, and the origin sees no request at all.
  5. Step 5 · Dynamic paths — a behavior for /api/* forwards to the ALB with caching disabled — CloudFront still helps with TLS, connection reuse and the AWS backbone.
  6. Step 6 · New deployment — old copies can live until the TTL ends. Invalidate changed paths — or better, put a content hash in file names so new versions are new URLs.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: A CDN keeps copies of a website’s files in many cities, so people get them from nearby instead of from one far-away server. CloudFront is AWS’s CDN.

Try: When a new phone launches, shops in every city stock it — you don’t travel to the factory. Same idea for website files.

Check yourself: Who waits longest: the first visitor in a city or the hundredth?

The first — their request fetches the file from the origin (a cache miss). Later visitors get the cached copy.

Level 1 · Beginner first steps on AWS

Understand: Distributions, origins (S3, ALB), behaviors by path, cache policies and TTL, OAC for private S3, invalidations.

Try: Do the simulator, then explain from the headers whether a response was a hit or miss and which city served it.

Check yourself: Why put a content hash in JS file names?

Each version gets a new URL, so caches never serve old code and no invalidation is needed.

Level 2 · Intermediate can do it alone

Understand: Build a distribution on a private bucket, prove Miss→Hit with X-Cache, prove direct S3 is 403, and deploy with invalidation.

Try: Do the hands-on, then add an /api/* behavior to an ALB with caching disabled.

Check yourself: Hit ratio is 4%. First three things to check?

Cache key (headers/cookies/query strings), origin Cache-Control headers (no-cache/max-age=0), and whether URLs include random parameters.

Level 3 · Advanced designs for others

Understand: Design multi-origin distributions, cache key strategy, origin shield, origin failover groups, WAF and signed cookies for paid content.

Try: Design CloudFront for a course platform: public site, private videos via signed cookies, API behind ALB, WAF.

Check yourself: How do you stop users from bypassing CloudFront to hit the ALB directly?

ALB SG allows only the CloudFront origin-facing prefix list, plus a secret custom header checked by an ALB listener rule (or WAF).

Level 4 · Expert architect / interviewer

Understand: Own edge strategy: multi-CDN decisions, real-user monitoring, cost/price classes, edge compute, and security posture for all public endpoints.

Try: Build a dashboard of hit ratio, 4xx/5xx, origin latency and cost per GB across distributions.

Check yourself: When would you use Lambda@Edge over CloudFront Functions?

When you need network calls, body access, longer runtime or origin-request/response triggers; Functions are for tiny, very fast viewer-request/response logic.

Hit ratio maths

If 95% of 10 million monthly requests are hits, the origin serves only 500,000. Data transfer from S3/ALB to CloudFront is free, and CloudFront-to-internet pricing is lower than S3-to-internet at volume — so the bill often drops while speed improves.

Static site deploy order

aws s3 sync dist/static s3://tiffingo-site/static --cache-control 'max-age=31536000,immutable'
aws s3 cp dist/index.html s3://tiffingo-site/index.html --cache-control 'max-age=60'
aws cloudfront create-invalidation --distribution-id $DIST --paths /index.html
9 Under the hood

Request collapsing, TLS at the edge, functions

What CloudFront does that you never see.

1 · Request collapsing

If 500 users in Chennai ask for the same uncached file at the same moment, the edge sends one request to the origin and answers all 500 from it. That protects origins during traffic spikes — results day, a sale, a viral post.

2 · TLS and TCP at the edge

The TLS handshake happens with the nearby edge (short round trips), and the edge keeps warm, reused connections to your origin over the AWS backbone. That is why even uncacheable API calls often get faster through CloudFront.

3 · Two kinds of edge code

CloudFront Functions run lightweight JavaScript on viewer request/response in under a millisecond at every edge (URL rewrites, header changes, redirects). Lambda@Edge runs Node.js/Python at regional edge caches with network access and more time (auth, A/B logic, origin selection).

4 · Eviction

TTL is a maximum, not a promise: rarely requested objects can be evicted before their TTL to make room. That is normal — the next request is simply a miss.

CloudFront checklist

  • ☐ S3 origins private with OAC.
  • ☐ Alias records (apex + www) to the distribution.
  • ☐ ACM cert in us-east-1; HTTP → HTTPS.
  • ☐ Behaviors: /api uncached; static long TTL.
  • ☐ Minimal cache keys; hit ratio monitored.
  • ☐ Versioned assets; invalidate only index.html.
  • ☐ WAF + rate-based rule; logs enabled.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. CloudFront has a free tier (1 TB transfer and 10 million requests per month); this lab costs nothing beyond tiny S3 storage.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Private bucket + distribution with OAC

    UI way — AWS Management Console

    1. S3 → create tiffingo-site-<account-id> (Block Public Access ON) → upload index.html and img/menu.jpg → CloudFront → Create distribution → origin = the bucket → Origin access control → create new OAC → default root object index.html → Redirect HTTP to HTTPS → cache policy CachingOptimized → create → Copy policy from the banner → paste it into the bucket’s policy.

    CLI way — the same thing with commands

    B=tiffingo-site-$ACCT; aws s3 mb s3://$B --region ap-south-1 >/dev/null
echo '<h1>TiffinGo menu v1</h1><img src=img/menu.jpg width=300>' > index.html; aws s3 cp index.html s3://$B/ --cache-control max-age=60 >/dev/null
head -c 200000 /dev/urandom > menu.jpg   # any file works; upload a real photo if you have one
aws s3 cp menu.jpg s3://$B/img/menu.jpg >/dev/null
OAC=$(aws cloudfront create-origin-access-control --origin-access-control-config Name=tiffingo-oac,SigningProtocol=sigv4,SigningBehavior=always,OriginAccessControlOriginType=s3 --query OriginAccessControl.Id --output text)
cat > dist.json <<EOF
{"CallerReference":"lab-$(date +%s)","Comment":"tiffingo lab","Enabled":true,"DefaultRootObject":"index.html",
 "Origins":{"Quantity":1,"Items":[{"Id":"s3","DomainName":"$B.s3.ap-south-1.amazonaws.com","OriginAccessControlId":"$OAC","S3OriginConfig":{"OriginAccessIdentity":""}}]},
 "DefaultCacheBehavior":{"TargetOriginId":"s3","ViewerProtocolPolicy":"redirect-to-https","CachePolicyId":"658327ea-f89d-4fab-a63d-7e88639e58f6"}}
EOF
read DIST DOM < <(aws cloudfront create-distribution --distribution-config file://dist.json --query 'Distribution.[Id,DomainName]' --output text); echo $DIST $DOM
cat > policy.json <<EOF
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"cloudfront.amazonaws.com"},"Action":"s3:GetObject","Resource":"arn:aws:s3:::$B/*","Condition":{"StringEquals":{"AWS:SourceArn":"arn:aws:cloudfront::$ACCT:distribution/$DIST"}}}]}
EOF
aws s3api put-bucket-policy --bucket $B --policy file://policy.json
aws cloudfront wait distribution-deployed --id $DIST && echo deployed

    You should see: the distribution ID and a domain like d1a2b3c4d5e6f7.cloudfront.net, then deployed after a few minutes.

    The CachePolicyId is the managed CachingOptimized policy. Open https://DOMAIN in a browser — the menu page loads over HTTPS.

  3. 2 · Prove caching — and prove the bucket is private

    UI way — AWS Management Console

    1. Open the image URL twice with browser dev tools → Network → response headers: x-cache goes from Miss to Hit, and x-amz-cf-pop shows your edge. Then open the S3 object URL directly: AccessDenied.

    CLI way — the same thing with commands

    for i in 1 2 3; do curl -sI https://$DOM/img/menu.jpg | grep -iE '^(x-cache|x-amz-cf-pop|age):' | tr -d '\r' | paste -sd' '; done
curl -s -o /dev/null -w 'direct S3: %{http_code}\n' https://$B.s3.ap-south-1.amazonaws.com/img/menu.jpg

    You should see: first line x-cache: Miss from cloudfront, then Hit from cloudfront with a growing age; and direct S3: 403.

    The POP code (e.g. BOM, MAA, DEL) tells you which city served you.

  4. 3 · Deploy a change: see stale content, then invalidate

    UI way — AWS Management Console

    1. Edit index.html to say v2 and upload it → reload: still v1 (cached, max-age 60 — or longer if you wait less) → Invalidations → Create invalidation /index.html → reload: v2.

    CLI way — the same thing with commands

    sed -i 's/v1/v2/' index.html; aws s3 cp index.html s3://$B/ --cache-control max-age=60 >/dev/null
curl -s https://$DOM/ | head -c 40; echo
I=$(aws cloudfront create-invalidation --distribution-id $DIST --paths /index.html / --query Invalidation.Id --output text)
aws cloudfront wait invalidation-completed --distribution-id $DIST --id $I
curl -s https://$DOM/ | head -c 40; echo

    You should see: <h1>TiffinGo menu v1 first, then v2 after the invalidation completes.

    We invalidated both / and /index.html because the root URL is cached separately from /index.html.

Clean up and cost check

Disable the distribution (get-distribution-config, set Enabled=false, update-distribution with the ETag), wait until Deployed, then delete-distribution with the new ETag; delete the OAC; empty and delete the bucket.

Practice without an account: simulator

Create an OAC and a distribution, lock the bucket to it, test caching, and invalidate after a deploy.

3 Issue cookies (login API side)

Uses the cryptography library; CloudFront wants URL-safe base64 with -, _, ~ substitutions.

import json, time, base64
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
def cf_b64(b): return base64.b64encode(b).decode().replace('+','-').replace('=','_').replace('/','~')
def signed_cookies(domain, key_id, pem_path, hours=2):
    policy = json.dumps({'Statement':[{'Resource':f'https://{domain}/videos/*','Condition':{'DateLessThan':{'AWS:EpochTime':int(time.time())+hours*3600}}}]}, separators=(',',':'))
    key = serialization.load_pem_private_key(open(pem_path,'rb').read(), password=None)
    sig = key.sign(policy.encode(), padding.PKCS1v15(), hashes.SHA1())
    return {'CloudFront-Policy': cf_b64(policy.encode()), 'CloudFront-Signature': cf_b64(sig), 'CloudFront-Key-Pair-Id': key_id}
c = signed_cookies('d1a2b3c4d5e6f7.cloudfront.net', 'K2ABC…', 'cf-private.pem')
print('; '.join(f'{k}={v}' for k, v in c.items())[:80] + '…')
