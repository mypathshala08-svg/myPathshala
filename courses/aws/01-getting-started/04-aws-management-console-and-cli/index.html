2 Definition

AWS Management Console and CLI

Formal definition (write this in exams)

The AWS Management Console is AWS’s web-based interface for managing services; the AWS Command Line Interface (CLI) is a unified tool for calling AWS service APIs from a terminal. Both — like CloudShell, the SDKs, infrastructure-as-code tools and IDE toolkits — send authenticated API requests that IAM authorises and CloudTrail records.

In simple words

The console is the AWS website you click through; the CLI is the same power as typed commands you can save and repeat.

Say it in an interview

30-second answer you can speak:

  • “I use the console to explore and verify, the CLI for repeatable tasks and scripts, SDKs inside applications, and CloudFormation or Terraform for whole environments — they all call the same APIs.”
  • “On laptops I use aws configure sso for short-lived credentials; on AWS compute the SDK picks up the role automatically, so no keys are stored anywhere.”

3 The big picture

Seven doors, one set of APIs

New to computers? Start here. There are two ways to order food: tap buttons in an app (the console) or send a typed message with your exact order (the CLI). Both reach the same kitchen. Typing is faster when you order the same thing every day — you can copy and resend it.

Jargon buster:

  • Console — AWS’s website with buttons and forms
  • CLI — typing commands instead of clicking
  • CloudShell — a ready-made place in the browser to type commands
  • Command — one typed instruction, e.g. aws s3 ls
  • Script — a saved list of commands you can run again

There is only one way into AWS: its APIs. Everything else is a client that calls them for you:

Type 5 · AWS SDKs

Definition (say it in an interview): AWS SDKs are language libraries (Python boto3, Java, JavaScript/TypeScript, .NET, Go, Rust, PHP, Ruby, C++, Kotlin, Swift) that wrap the AWS APIs with clients, paginators, waiters, automatic retries and the same credential provider chain as the CLI, so applications can use AWS services from code.

Words used above, in simple terms: client = low-level API object · paginator = iterates all pages · ClientError = exception with AWS error code

5 How it works, step by step

What happens when you run an AWS CLI command

From keyboard to table.

Animated

What happens when you run one CLI command

From keyboard to table — each step lights up the part of the CLI or AWS doing the work.

CLI flow 6 steps
Watch what happens
  1. Step 1 · You type a command — aws + service + operation + options. The CLI parses it before contacting AWS.
  2. Step 2 · Find credentials — the provider chain is checked in order; in CloudShell the first one present is the container role from your console session.
  3. Step 3 · Read configuration — Region and output come from options, environment variables or ~/.aws/config. No Region → “You must specify a region”.
  4. Step 4 · Build and sign — the CLI builds the HTTPS request and signs it with SigV4. Your secret key is used locally and never sent.
  5. Step 5 · AWS answers — the S3 endpoint verifies the signature, IAM allows s3:ListAllMyBuckets, S3 lists buckets, CloudTrail logs the call, JSON comes back.
  6. Step 6 · Shape the output — --query (JMESPath) keeps only bucket names and --output table formats them — on your machine, after the full response arrived.

Myth vs reality: things many websites still say

  • Myth: The CLI can do things the console cannot (and vice versa).
    Reality: Both call the same APIs; coverage is near-identical.
    Proof: Big picture.
  • Myth: --query reduces API calls.

Pagination: three switches

  • Default: the CLI fetches all pages for you.
  • --max-items N stops after N items and prints a NextToken; continue with --starting-token.
  • --page-size N asks AWS for smaller pages (fewer timeouts on huge lists); --no-paginate returns only the first page.
9 Under the hood

Provider chain, SSO token flow, retries, CloudShell internals, --debug

What the CLI and SDKs do before a single byte reaches AWS — the knowledge that solves 80% of “it works on my machine” problems.

1 · The credential provider chain, in order

The CLI (and every SDK) checks these sources in order and uses the first it finds:

#SourceExampleTypical use
1Command-line options--profile dev, --regionone-off override
2Environment variablesAWS_ACCESS_KEY_ID, AWS_SESSION_TOKEN, AWS_PROFILECI pipelines, containers
3Web identity / SSO / assume-role profiles in ~/.aws/configsso_session, role_arndevelopers (recommended)
4Shared credentials file~/.aws/credentialslegacy long-term keys
5Container credentialsECS task role endpoint; CloudShellcontainers, CloudShell
6EC2 instance metadata (IMDSv2)instance profile roleapps on EC2

Classic bug: an old AWS_ACCESS_KEY_ID exported in .bashrc silently overrides your SSO profile. Run aws configure list — the Type column shows which source won.

2 · How SSO sign-in works on a laptop

  1. aws sso login opens a browser to your IAM Identity Center portal (device-authorisation flow).
  2. You sign in with password + MFA once; a token is cached in ~/.aws/sso/cache/ (typically valid for hours).
  3. For each command the CLI exchanges the token for temporary role credentials for the chosen account and permission set.
  4. When the session expires you see Token has expired and refresh failed — just run aws sso login again.

No long-term secret ever lands on the laptop — a lost laptop is a much smaller incident.

3 · Retries, timeouts and what --debug shows

The CLI retries throttling and transient errors automatically (standard mode: up to 3 attempts with exponential backoff; adaptive adds client-side rate limiting). aws s3 ls --debug 2>&1 | less shows: which credential source was used, the endpoint, the signed headers (not the secret), retries and the raw response. Learn to read it — it ends most debugging sessions.

4 · High-level vs low-level commands

Command familyExampleBehaviour
High-level aws s3aws s3 sync ./site s3://b/many API calls for you: multipart upload, parallel transfers, compares sizes/timestamps
Low-level aws s3apiaws s3api put-object …exactly one API operation; full control of every parameter
Waitersaws ec2 wait instance-runningpolls a Describe call until a state is reached or times out
Dry run--dry-run (EC2)checks permissions; returns DryRunOperation if allowed

5 · CloudShell internals

Each CloudShell session is a small Linux compute environment managed by AWS in the Region you opened it from, with your console credentials delivered through a container credential endpoint. $HOME (1 GB) persists per Region; data there is deleted if you do not use CloudShell in that Region for a long period (120 days). It has outbound internet access by default; a VPC environment option places it in your VPC to reach private resources.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. Everything is created and deleted inside the lab. Cost: zero (a few S3 requests are within the Free Tier).

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Know your CLI and where it gets credentials

    UI way — AWS Management Console

    1. Console: search box → type S3 → star it as a favourite; check the Region is Mumbai.
    2. Open CloudShell from the toolbar.

    CLI way — the same thing with commands

    aws --version
aws configure list
aws sts get-caller-identity --query Arn --output text
ls -la ~ && df -h ~

    You should see: aws-cli/2.x, credentials of type container-role (CloudShell), your user ARN, and your 1 GB home directory.

    On a laptop you would instead run aws configure sso once and aws sso login each day — temporary credentials, nothing to leak.

  3. 2 · Shape output with --query and --output

    UI way — AWS Management Console

    1. No console equivalent — this is the CLI’s superpower. Compare the console’s EC2 → Global View with the commands.

    CLI way — the same thing with commands

    aws ec2 describe-regions --output json | head -20
aws ec2 describe-regions --query 'Regions[].RegionName' --output text
aws ec2 describe-regions --query 'Regions[?starts_with(RegionName, `ap-`)].[RegionName,Endpoint]' --output table
aws ec2 describe-availability-zones --query 'length(AvailabilityZones)'
aws ssm get-parameters-by-path --path /aws/service/global-infrastructure/services --max-items 5 --query 'Parameters[].Value'

    You should see: raw JSON, then a single tab-separated line of Region names, a neat table of only Asia-Pacific Regions, the number 3, and five service names plus a NextToken for the next page.

    --query runs on your machine after the response arrives; it saves screen space, not API calls.

  4. 3 · A full create → use → share → delete cycle from the CLI

    UI way — AWS Management Console

    1. Console equivalent: S3 → Create bucket → upload hello.txt → Actions → Share with a presigned URL → empty and delete the bucket.

    CLI way — the same thing with commands

    B=cli-lab-$(date +%s); echo $B
aws s3 mb s3://$B --region ap-south-1
echo "Hello from $(aws sts get-caller-identity --query Arn --output text)" > hello.txt
aws s3 cp hello.txt s3://$B/
aws s3 ls s3://$B/
URL=$(aws s3 presign s3://$B/hello.txt --expires-in 300); curl -s "$URL"
aws ec2 run-instances --dry-run --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --instance-type t3.micro
aws s3 rb s3://$B --force

    You should see: make_bucket, upload, the object listed, your text printed via the presigned URL, then An error occurred (DryRunOperation) … Request would have succeeded, but DryRun flag is set. (permission check without launching) and remove_bucket.

    Eight lines did what takes about twenty console clicks — and you can paste them into a file and run them again tomorrow.

Clean up and cost check

Step 3 already deleted the bucket (aws s3 rb --force). Check: aws s3 ls | grep cli-lab prints nothing. Remove hello.txt from CloudShell with rm hello.txt.

Type the real commands — the simulator answers like CloudShell and shows what each one touches.

17 Mini project

Build something with what you learned

Three projects, each a little harder. Do them on your own account (or plan them on paper first). Each lists what to hand in, so a teacher can mark it.

BasicConsole vs CLI race

Scenario: Do the same task both ways and time yourself.

  1. Console: create a bucket, upload 3 files, share one with a presigned URL, delete everything.
  2. CLI: the same with the Step 3 commands.
  3. Record time, number of clicks/commands, and mistakes.

Hand in: A small table and two sentences on when you would use each.

Stretch goal: Turn the CLI version into a reusable script with the bucket name as an argument.

IntermediateBatch onboarding script

Scenario: A new batch of 30 students needs a folder each in a shared bucket.

  1. Create students.csv with roll numbers.
  2. Write a Bash loop that creates s3://BUCKET/batch-2026/ROLL/ markers and uploads a welcome file to each.
  3. Make it idempotent (running twice does not duplicate or fail).
  4. Print a summary with --query/wc -l.

Hand in: The script, its output and the S3 listing.

Stretch goal: Add a --dry-run flag to your own script that only prints what it would do.

AdvancedMulti-Region inventory in Python (SDK)

Scenario: Ops wants a daily list of running instances and unattached volumes in every Region.

  1. boto3: loop over enabled Regions; use paginators for describe_instances and describe_volumes.
  2. Collect running instances (id, type, AZ, Name tag) and volumes with state available (unattached, still billed).
  3. Write a CSV and upload it to S3 with a dated key.
  4. Handle ClientError and throttling gracefully.

Hand in: Code, a sample CSV and the S3 object key.

Stretch goal: Schedule it with EventBridge Scheduler + Lambda (Module 7/9).
