2 Definition

Creating an AWS account and free tier

Formal definition (write this in exams)

An AWS account is the container that holds AWS resources and is the unit of billing and isolation; it is created with a root user that has unrestricted access. The AWS Free Tier lets new customers explore services at no or low cost through a Free or Paid account plan with credits, always-free monthly offers and short-term trials (accounts created before 15 July 2025 use the earlier 12-month model).

In simple words

Open an account, protect the all-powerful root login, do your work as a separate admin user, and set a budget so learning stays free.

Say it in an interview

30-second answer you can speak:

  • “On a new account I enable root MFA, never create root keys, create admin access through Identity Center or an IAM user with MFA, and set budget alerts before building anything.”
  • “New AWS accounts choose a Free plan — credits for six months with no charges — or a Paid plan with all services; always-free offers apply to both.”

3 The big picture

From sign-up to a safe account

New to computers? Start here. Opening an AWS account is like opening a bank account: you get a master key (root user) that can do everything — so you lock it in a safe and use a normal card (admin user) every day. A budget alert is like an SMS from your bank when you spend too much.

Jargon buster:

  • Account — your own private space in AWS, with its own bill
  • Root user — the master login created at sign-up
  • MFA — a second check, like an OTP on your phone
  • Free Tier — free credits and limits for learning
  • Budget — a spending limit that sends you alerts

An AWS account is the container for everything you create and the unit AWS bills. It comes with one all-powerful root user. A safe start is five steps:

Type 1 · Free account plan

Definition (say it in an interview): The Free account plan (for new accounts since 15 July 2025) gives access to select services with sign-up credits and no charges, for six months or until credits are used; features that could drain credits are restricted, and at the end the account closes unless you upgrade within 90 days.

In plain words (no jargon): A free, time-limited AWS account for learning.

Analogy: A prepaid phone SIM with a fixed talk-time: you cannot overspend, and it stops when the balance or validity ends.

Words used above, in simple terms: credits = money-value applied to usage · upgrade = switch to the Paid plan · account closure = access stops; data kept 90 days

8 Deep dive

Root-only tasks, root keys, IAM user vs Identity Center, sign-up checklist

Tasks only the root user can do

  • Change account name, root e-mail or root password.
  • Close the AWS account.
  • Change or cancel the support plan.
  • Restore permissions when an IAM admin locks everyone out.
  • Some billing tasks and tax settings.

Everything else should be done as a user or role. Keep root credentials and the MFA device safe and offline.

Why not root access keys?

Access keys are long-term secrets used by the CLI/SDK. Root keys cannot be limited by IAM policies, so a leak means total compromise. Use CloudShell (temporary credentials), IAM Identity Center (short-lived SSO credentials) or, if you must, an IAM user’s keys with least privilege and rotation.

9 Under the hood

Sign-in doors, MFA codes, credential types, billing pipeline, account closure

What happens behind the sign-up, sign-in and billing screens.

1 · Root sign-in vs IAM user sign-in

Root signs in with the e-mail address used at sign-up. IAM users sign in at an account-specific URL: https://ACCOUNT_ID.signin.aws.amazon.com/console, or a friendlier alias you create (aws iam create-account-alias --account-alias tiffingo → https://tiffingo.signin.aws.amazon.com/console). Two different doors: if a user tries the root door with their user name, sign-in fails.

2 · How an authenticator-app MFA code works

When you scan the QR code, AWS and your phone share a secret. Every 30 seconds both compute a 6-digit code from that secret and the current time (the TOTP standard, RFC 6238). AWS accepts the code if it matches its own calculation — nothing is sent to your phone. That is why the phone clock must be correct, and why AWS asks for two consecutive codes when you set it up. Passkeys / security keys use public-key cryptography (FIDO2) instead: the private key never leaves the device, so they resist phishing.

Rule of thumb: prefer anything temporary. Long-term keys are the #1 cause of leaked-credential incidents.

4 · How billing really works

Every service emits usage records (hours, GB-months, requests). The billing system rates them with that day’s price list, applies Free Tier allowances, then credits, and adds the result to the month’s bill. Cost data refreshes a few times a day, so budgets and Cost Explorer are hours behind real usage — a budget is an early warning, not a real-time brake. The invoice is issued in the first days of the next month.

5 · What “closing an account” does

A closed account enters a post-closure period of 90 days during which you can reopen it; after that the account and its content are permanently deleted. Resources may still exist in that window, which is why you should delete resources first, then close. The account’s e-mail cannot be reused for a new AWS account.

10 By role

How developers, data, ML, DevOps and security people use it

Every role needs an identity — but not the same one. Getting access right on day one avoids both blocked engineers and over-powered accounts.

Software developer

Needs to deploy and debug in dev, read-only in prod.

Uses: Identity Center permission set “Developer” in the dev account; “ReadOnly” in prod; CLI via aws configure sso.

A real task: Runs aws sso login each morning; gets 8-hour temporary credentials; no access keys on the laptop.

Skill to build: SSO profiles, never committing credentials, using roles in code.

App / mobile developer

Needs Amplify/Cognito/API Gateway in dev; never needs root or billing.

Uses: Developer permission set scoped to app services; separate sandbox account for experiments.

A real task: Creates a Cognito user pool in the sandbox, deletes it at the end of the sprint.

Skill to build: Working inside a budgeted sandbox.

Data analyst

Needs to query data, not create infrastructure.

Uses: Read access to specific S3 prefixes / Lake Formation tables, Athena and QuickSight permissions.

A real task: Signs in through SSO to an analytics account; queries only the curated tables.

Skill to build: Understanding that access is per dataset, not per account.

Data engineer

Builds pipelines in dev; deploys to prod through CI/CD.

Uses: Data-engineering permission set (Glue, EMR, S3 prefixes); prod changes only via pipeline role.

A real task: Tests a Glue job in dev; merges to main; the pipeline deploys it to prod.

Skill to build: Separating human access from deployment roles.

ML / AI engineer

Needs SageMaker/Bedrock and GPU quota; GPU costs are high.

Uses: ML permission set; service quota requests for GPU instances; strict budgets and budget actions.

A real task: Requests a quota increase for g-series instances before a training run; sets a budget action to stop notebooks at a threshold.

Skill to build: Quotas, budgets and stopping idle notebooks.

DevOps / cloud engineer

Owns the account structure itself.

Uses: Administrator in management/security accounts (rarely used, MFA-enforced), break-glass procedure for root.

A real task: Creates new accounts for a new project from a template with guard-rails already on.

Skill to build: Organizations, SCPs, Identity Center, account vending.

Accounts are the strongest isolation boundary AWS has: a mistake in a sandbox cannot touch production. 14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. In this lab you create the safe foundation for the whole course: root locked, an admin user, budgets. Cost: free.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Lock the root user (MFA, no keys)

    UI way — AWS Management Console

    1. Sign in as root (your sign-up e-mail) → account menu (top right) → Security credentials.
    2. Assign MFA device → choose a passkey or an authenticator app → follow the prompts.
    3. Under Access keys confirm there are none — delete any you created.

    CLI way — the same thing with commands

    # run in CloudShell while signed in as root (only this once)
aws iam get-account-summary --query 'SummaryMap.{rootMFA:AccountMFAEnabled,rootKeys:AccountAccessKeysPresent}'

    You should see: rootMFA: 1 and rootKeys: 0. If rootKeys is 1, delete the key in Security credentials now.

    Root MFA is set in the console only. This is the single most important security step in AWS.

  3. 2 · Create an admin user for daily work

    UI way — AWS Management Console

    1. IAM → User groups → Create group Admins → attach AdministratorAccess.
    2. Users → Create user riya-admin → Provide user access to the AWS Management Console → custom password, must change at next sign-in → add to Admins.
    3. Copy the sign-in URL, sign out of root, sign in as riya-admin → Security credentials → Assign MFA device.

    CLI way — the same thing with commands

    aws iam create-group --group-name Admins
aws iam attach-group-policy --group-name Admins --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
aws iam create-user --user-name riya-admin
aws iam add-user-to-group --group-name Admins --user-name riya-admin
read -s -p "Temporary password: " PW; echo
aws iam create-login-profile --user-name riya-admin --password "$PW" --password-reset-required
ACC=$(aws sts get-caller-identity --query Account --output text)
echo "Sign in at: https://$ACC.signin.aws.amazon.com/console"
aws iam list-groups-for-user --user-name riya-admin --query 'Groups[].GroupName' --output text

    You should see: the sign-in URL and Admins. Sign out of root, sign in as riya-admin, change the password and add MFA. From now on, root stays locked away.

    The password is typed with read -s so it never appears on screen or in shell history. Companies use IAM Identity Center instead (it needs AWS Organizations, which moves a Free plan to Paid).

  4. 3 · Budget alerts and your plan

    UI way — AWS Management Console

    1. Signed in as riya-admin: Billing and Cost Management → Budgets → Create budget → Zero spend budget (alerts on the first cent) — and a monthly cost budget of $5.
    2. Billing home: note your plan (Free/Paid), remaining credits and end date.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text)
aws budgets create-budget --account-id $ACC \
  --budget '{"BudgetName":"monthly-5usd","BudgetLimit":{"Amount":"5","Unit":"USD"},"TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[{"Notification":{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":80,"ThresholdType":"PERCENTAGE"},"Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]},{"Notification":{"NotificationType":"FORECASTED","ComparisonOperator":"GREATER_THAN","Threshold":100,"ThresholdType":"PERCENTAGE"},"Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]}]'
aws budgets describe-budgets --account-id $ACC --query 'Budgets[].[BudgetName,BudgetLimit.Amount,CalculatedSpend.ActualSpend.Amount]' --output table
aws freetier get-account-plan-state --region us-east-1 --query '{plan:accountPlanType,status:accountPlanStatus,credits:accountPlanRemainingCredits.amount,ends:accountPlanExpirationDate}'

    You should see: a table with monthly-5usd (and the zero-spend budget if you made it in the console), current spend near 0, and your plan, credits and end date. Replace the e-mail with yours before running.

    Simple budget alerts like these are enough for learning; AWS checks spend a few times a day, so alerts arrive within hours of crossing a threshold.

Clean up and cost check

Keep the admin user and budgets — every later lesson uses them. If you created any access keys while experimenting, delete them: aws iam list-access-keys --user-name riya-admin then aws iam delete-access-key --user-name riya-admin --access-key-id KEY_ID. Sign out of root and store its MFA device safely.

Three projects, each a little harder. Do them on your own account (or plan them on paper first). Each lists what to hand in, so a teacher can mark it.

BasicSafe personal learning account

Scenario: You will use AWS for this whole course.

  2. Root MFA (passkey or app), no root keys.

IntermediateCredential report audit

Scenario: Your college lab account has 40 IAM users created by different faculty over two years.

  1. Generate the credential report and open it as CSV.
  2. Find users with a password but no MFA.
  3. Find access keys older than 90 days or never used.
  4. Write a one-page remediation list (who, what, by when).

Hand in: The filtered CSV and the remediation list.

Stretch goal: Automate it: a script that prints the three lists from the report.

AdvancedMulti-account design for an institute

  1. Draw an Organizations tree: management, security, shared-services, one OU for centres, one for student sandboxes.

  3. Describe how a faculty member signs in once and reaches the right account (Identity Center permission sets).
