2 Definition

Elastic Beanstalk

Formal definition (write this in exams)

AWS Elastic Beanstalk is a platform-as-a-service that deploys and manages web applications on AWS: from an uploaded application version it provisions an environment through CloudFormation — EC2 instances on a managed platform, load balancer, Auto Scaling group, security groups and monitoring — and handles deployments (all at once, rolling, immutable, traffic splitting), health reporting, log access and managed platform updates, while leaving all resources visible and configurable.

In simple words

Elastic Beanstalk takes your code and builds the servers, load balancer and scaling around it, then deploys new versions safely — you focus on the app.

Say it in an interview

30-second answer you can speak:

  • “Beanstalk is EC2-based PaaS: I upload versions, run them in environments on a platform like Python on AL2023, configure with .ebextensions and environment properties, and choose immutable or traffic-splitting deployments for production.”
  • “I keep the database outside the environment, use blue/green with URL swaps for platform changes, and rely on enhanced health and eb logs for troubleshooting.”

Type 1 · Applications and application versions

Definition (say it in an interview): An application is a logical container for application versions (labelled source bundles — zip or WAR — stored in an S3 bucket Beanstalk creates) and environments; any stored version can be deployed to any environment, which makes rollback a redeploy of an older label. A version lifecycle policy limits how many are kept.

In plain words (no jargon): Your project and every uploaded copy of its code.

Analogy: Every edition of a recipe book kept on the shelf — cook any edition again.

How it works internally, step by step

  1. App. Container.
  2. Version. Zip + label.
  3. S3. elasticbeanstalk-region-acct bucket.
  4. Deploy any. Rollback.
  5. Lifecycle. Max count/age.

Words used above, in simple terms: source bundle = zip of the project · version label = name like v2 or a commit ID · lifecycle policy = auto-delete old versions

Type 2 · Environments and tiers

Definition (say it in an interview): An environment runs one version on a set of resources with its own URL (name.region.elasticbeanstalk.com): web server tier (ALB + ASG, or a cheap single instance with an Elastic IP) or worker tier (an SQS queue and a daemon that POSTs each message to your app, with cron.yaml for scheduled jobs). Typical set-up: dev, staging, prod environments of one application.

In plain words (no jargon): A running copy of your app with its own address.

Analogy: Separate kitchens for practice, tasting and the real party — same recipe book.

How it works internally, step by step

  1. Web tier. ALB + ASG.
  2. Single. One instance + EIP.
  3. Worker. SQS daemon.
  4. URL. CNAME.
  5. Many envs. dev/stage/prod.

Words used above, in simple terms: tier = type of environment · CNAME = environment URL · cron.yaml = scheduled tasks for workers

Type 3 · Platforms

Definition (say it in an interview): A platform is a managed stack — OS (Amazon Linux 2023), language runtime (Python, Node.js, Java/Corretto, Tomcat, .NET on Linux/Windows, PHP, Ruby, Go) or Docker, and a web server (nginx) — with conventions: Python looks for application.py exposing application (or a Procfile), Node runs npm start, Docker uses your Dockerfile/compose.

In plain words (no jargon): The ready-made language setup Beanstalk runs your code on.

Analogy: Choosing the catering menu style: North Indian, South Indian or custom — the kitchen is set up accordingly.

How it works internally, step by step

  1. Branch. Language + OS.
  2. Proxy. nginx.
  3. Entry. application / Procfile.
  4. Docker. Anything.
  5. Retirement. Old branches retire.

Words used above, in simple terms: platform branch = e.g. Python 3.12 on AL2023 · Procfile = command to start the app · reverse proxy = server in front of the app

Type 4 · Deployment policies

Definition (say it in an interview): All at once (fast, downtime risk), rolling (batches, reduced capacity), rolling with additional batch (launch extra first, full capacity), immutable (new temporary Auto Scaling group with v2, swap in when healthy — safest in-place), traffic splitting (canary percentage for an evaluation time), and blue/green via a second environment and URL swap.

In plain words (no jargon): Ways to replace the old version with the new one.

Analogy: Replacing cooks during dinner: all at once, a few at a time, add extra cooks first, or open a whole new kitchen.

How it works internally, step by step

  1. All at once. Fast, risky.
  2. Rolling. Batches.
  3. + batch. Keep capacity.
  4. Immutable. New ASG.
  5. Traffic split. Canary.

Words used above, in simple terms: canary = small share of traffic first · batch = group of instances updated together · rollback = return to previous version

Type 6 · Enhanced health and logs

Definition (say it in an interview): Enhanced health reporting uses an agent on each instance plus load-balancer data to report per-instance and environment status (OK, Warning, Degraded, Severe) with causes (5xx rate, latency, CPU, failing deployments); eb health shows it live, eb logs fetches web server and app logs, and logs can stream to CloudWatch Logs.

In plain words (no jargon): How Beanstalk tells you if the app is healthy, and where its logs are.

Analogy: A dashboard showing which cook is slow and which dishes are being sent back.

How it works internally, step by step

  1. Agent. Per instance.
  2. Colours. OK…Severe.
  3. Causes. Explained.
  4. eb logs. Bundle/tail.
  5. CloudWatch. Streaming.

Words used above, in simple terms: 5xx = server-side error codes · p99 latency = slowest 1% of requests · events = timeline of environment actions

Type 7 · Blue/green deployments and managed platform updates

Definition (say it in an interview): Blue/green: clone the environment (green), deploy and test there, then swap environment URLs (CNAMEs) so traffic moves at once — and swap back to roll back. Managed platform updates apply minor/patch platform versions automatically in a weekly maintenance window using immutable deployments.

In plain words (no jargon): Running a second copy and switching users over in one step.

Analogy: Prepare a second hall fully; when guests arrive, just change the sign at the gate.

How it works internally, step by step

  1. Clone. eb clone.
  2. Test. Green URL.
  3. Swap. eb swap.
  4. Rollback. Swap back.
  5. Managed updates. Weekly window.

Words used above, in simple terms: blue/green = two environments, switch traffic · CNAME swap = exchange environment URLs · maintenance window = scheduled update time

What Beanstalk does when you deploy

Animated

What Elastic Beanstalk does when you deploy

Upload code; Beanstalk builds the whole stack, runs your app, watches health, rolls out new versions and rolls back bad ones.

From zip to running app 6 steps
Watch what happens
  1. Step 1 · Upload and create — eb create zips the project, stores it in S3 as application version v1, and starts a CloudFormation stack for the environment.
  2. Step 2 · Infrastructure appears — the stack creates the load balancer, Auto Scaling group, EC2 instances, security groups and CloudWatch alarms — you did not write any of it.
  3. Step 3 · Platform runs your code — the Python platform installs requirements.txt and runs nginx → gunicorn → application:application on each instance.
  4. Step 4 · Healthy and live — enhanced health reports OK; users reach tiffingo-prod.ap-south-1.elasticbeanstalk.com.
  5. Step 5 · Deploy v2 safely — eb deploy uploads v2 and the rolling policy updates one batch at a time so the app stays up.
  6. Step 6 · Roll back — v3 has a bug: 5xx errors turn health Severe. Deploying the previous version label (v2) restores service — versions are kept in S3.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

9 Under the hood

CloudFormation, deploy stages, platform hooks

What happens underneath an environment.

1 · CloudFormation underneath

Each environment is a CloudFormation stack (named awseb-e-…-stack). Beanstalk translates your option settings into resource properties and runs stack updates. Manual edits to those resources cause drift and may be reverted.

2 · A deployment, stage by stage

StageOn each instance
Downloadnew version bundle from S3
prebuild hooks.platform/hooks/prebuild
Buildpip install -r requirements.txt (Python), npm install (Node)
predeploy hooks.platform/hooks/predeploy
Switchstaging dir becomes current app; app server restarted
postdeploy hooks.platform/hooks/postdeploy
Healthagent reports; next batch starts only if healthy

3 · Immutable deployments

Beanstalk creates a temporary second Auto Scaling group with the new version, adds its instances to the load balancer, waits for health, then moves them into the original group and terminates old instances. If health fails, the temporary group is terminated — the old instances never changed.

4 · Enhanced health agent

A health daemon on each instance reads web server logs and system metrics every 10 seconds and sends them to Beanstalk, which combines them with load balancer metrics to compute status and causes.

5 · Managed platform updates

Within a weekly maintenance window, Beanstalk applies patch/minor platform versions using an immutable deployment. Major branch changes (e.g. Python 3.11 → 3.12) need you — usually via blue/green.

Real cases

College placement cell

Problem: Student team needed a public demo URL for a Flask project in one day.

On AWS: eb init + eb create --single, terminated after the presentation.

Small SaaS

Problem: Manual deployments broke production twice a month.

On AWS: Immutable deployments + health-based rollback + version labels from Git.

Agency

Problem: Twelve client sites on hand-built EC2, each different.

On AWS: One saved configuration, Beanstalk per client, managed updates.

Result: Patching effort near zero; identical setups.

Beanstalk checklist

  • ☐ Code at zip root: application.py/Procfile + requirements.txt; .ebignore set.
  • ☐ Instance profile and service role exist.
  • ☐ Production: load-balanced, ≥ 2 instances, immutable or traffic splitting.
  • ☐ Database outside the environment.
  • ☐ Config in .ebextensions/eb setenv — no manual EC2 edits.
  • ☐ Enhanced health + log streaming; managed updates on.
  • ☐ Version lifecycle policy; terminate unused environments.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. One single-instance environment (one t3.micro + public IP) for about 30–45 minutes. Single-instance avoids load balancer cost.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · App files and the instance profile

    UI way — AWS Management Console

    1. Create a folder with application.py and requirements.txt from above. IAM → Roles → Create role → AWS service → EC2 → AWSElasticBeanstalkWebTier → name aws-elasticbeanstalk-ec2-role (the Beanstalk console can also create it for you).

    CLI way — the same thing with commands

    mkdir tiffingo-eb && cd tiffingo-eb
# save application.py and requirements.txt from above here
pip install --user awsebcli --quiet; export PATH=$HOME/.local/bin:$PATH; eb --version
aws iam create-role --role-name aws-elasticbeanstalk-ec2-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null
aws iam attach-role-policy --role-name aws-elasticbeanstalk-ec2-role --policy-arn arn:aws:iam::aws:policy/AWSElasticBeanstalkWebTier
aws iam create-instance-profile --instance-profile-name aws-elasticbeanstalk-ec2-role >/dev/null
aws iam add-role-to-instance-profile --instance-profile-name aws-elasticbeanstalk-ec2-role --role-name aws-elasticbeanstalk-ec2-role

    You should see: an EB CLI version like EB CLI 3.x (Python 3.x) and no IAM errors (if the role exists already, that is fine).

    CloudShell can install the EB CLI with pip; on your laptop use pip or the official installer.

  3. 2 · Create the environment

    UI way — AWS Management Console

    1. Elastic Beanstalk → Create application tiffingo-eb → Web server environment → Platform Python 3.12 → Upload your code (zip of the folder) → Preset: Single instance → Service role: create/use default, EC2 instance profile: aws-elasticbeanstalk-ec2-role → Create. Wait for Health OK and open the URL.

    CLI way — the same thing with commands

    eb init tiffingo-eb -p python-3.12 --region ap-south-1
eb create tiffingo-prod --single --instance_profile aws-elasticbeanstalk-ec2-role --envvars NAME=Riya,ROLL=101 --timeout 20
eb status | grep -E 'Status|Health|CNAME|Deployed Version'
curl -s http://$(eb status | awk '/CNAME/ {print $2}')

    You should see: events streaming for a few minutes, then Health: Green, a CNAME like tiffingo-prod.ap-south-1.elasticbeanstalk.com, and <h1>TiffinGo v1</h1><p>Deployed by Riya (101) on ip-172-…</p>.

    If create fails with an instance-profile error, create the profile (Step 1) or let the console create it.

  4. 3 · Deploy v2, break v3, roll back

    UI way — AWS Management Console

    1. Change VERSION to "v2" → zip → Upload and deploy label v2 → open the URL. Change to v3 and add a typo (e.g. retrun) → deploy v3 → Health turns red → Application versions → select v2 → Deploy.

    CLI way — the same thing with commands

    sed -i 's/VERSION = "v1"/VERSION = "v2"/' application.py; eb deploy -l v2; curl -s http://$(eb status | awk '/CNAME/ {print $2}')
sed -i 's/VERSION = "v2"/VERSION = "v3"/; s/return "ok"/retrun "ok"/' application.py; eb deploy -l v3; eb health --refresh 2>/dev/null | head -5 || eb status | grep Health
eb deploy --version v2; eb status | grep -E 'Health|Deployed Version'
eb logs | grep -i -m3 error

    You should see: v2 page; then v3 fails (SyntaxError in logs, Health Red/Severe); after eb deploy --version v2 the environment returns to Green running v2.

    This is the whole point of versions: rollback is a redeploy, not a rebuild.

Clean up and cost check

eb terminate tiffingo-prod --force (wait until terminated), then eb appversion --delete v3 etc. or delete the application in the console; empty the elasticbeanstalk-ap-south-1-ACCT bucket if you no longer need it.

1 Create the project

application.py exposes application; requirements.txt sits next to it.

import os, socket
from flask import Flask, request
application = Flask(__name__)
NAME, ROLL, STAGE = os.environ.get("NAME", "?"), os.environ.get("ROLL", "?"), os.environ.get("STAGE", "dev")
FEEDBACK = []          # in memory on purpose — see step 6

@application.get("/")
def home():
    return (f"<h1>Campus Feedback ({STAGE})</h1><p>Deployed by {NAME} ({ROLL}) on {socket.gethostname()}</p>"
            f"<form method=post action=/feedback><input name=msg><button>Send</button></form><p>{len(FEEDBACK)} messages</p>")

@application.post("/feedback")
def feedback():
    FEEDBACK.append(request.form.get("msg", "")[:200]); return "thanks", 201

@application.get("/health")
def health(): return "ok"

1 Configuration as code

Create .ebextensions/01-prod.config.

option_settings:
  aws:elasticbeanstalk:environment:

5 Release v3 (broken)

A typo makes the app crash on start. The new instances fail health; Beanstalk deletes them and keeps v2.

sed -i 's/return "ok"/retrun "ok"/' application.py

6 Read the evidence

The monitor shows no non-200 codes; logs in CloudWatch show the v3 SyntaxError.

grep -o '[0-9]\{3\}' monitor.log | sort | uniq -c
aws logs filter-log-events --log-group-name /aws/elasticbeanstalk/feedback-prod/var/log/web.stdout.log --filter-pattern SyntaxError --max-items 1 --query 'events[].message' --output text
612 200 SyntaxError: invalid syntax (application.py, line 22)

7 Why the message counter resets

FEEDBACK lives in memory on each instance — with two instances and deployments, counts differ and vanish. Real state belongs in DynamoDB or RDS (Module 5). This is the “stateless” rule from 3.5.

Open the step-by-step solution (6 steps, with expected output)

1 Add an nginx security header as code

Files in .platform/nginx/conf.d are included by the platform’s nginx.

mkdir -p .platform/nginx/conf.d
echo 'add_header X-Env-Colour green always;' > .platform/nginx/conf.d/colour.conf
sed -i 's/retrun "ok"/return "ok"/' application.py

2 Clone prod to green and deploy there

The clone copies settings; then deploy the new bundle to green only.

eb clone feedback-prod -n feedback-green --timeout 25
eb use feedback-green; eb deploy -l v4-green
curl -sI http://feedback-green.ap-south-1.elasticbeanstalk.com | grep -i x-env-colour
X-Env-Colour: green

3 Test green on its own URL

Users still hit prod (blue).

curl -sI http://feedback-prod.ap-south-1.elasticbeanstalk.com | grep -ic x-env-colour
0

4 Swap URLs

Beanstalk exchanges the CNAMEs of the two environments.

eb swap feedback-prod -n feedback-green
sleep 60; curl -sI http://feedback-prod.ap-south-1.elasticbeanstalk.com | grep -i x-env-colour
… INFO Completed swapping CNAMEs for environments … X-Env-Colour: green

5 Roll back in seconds (if needed)

Swap again — no rebuild, no redeploy. Keep blue running until DNS caches expire.

eb swap feedback-green -n feedback-prod
… INFO Completed swapping CNAMEs …

6 Retire blue

After a safe period, terminate the old environment.

eb terminate feedback-prod --force   # the env that no longer owns the main URL

Interview and viva questions

Is Beanstalk outdated?

It is mature and still maintained; containers/serverless are alternatives, but Beanstalk is the fastest way to run a classic web app on EC2.

Can I SSH into Beanstalk instances?

Yes (eb ssh with a key pair) or Session Manager — but change config through Beanstalk, not by hand.

Docker apps?

Use the Docker platform with a Dockerfile or docker-compose.yml.
