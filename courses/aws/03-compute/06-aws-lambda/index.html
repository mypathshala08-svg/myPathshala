1 The story

A server for a 40-second job

Before you start: Lessons 2.1–2.3 (IAM) and basic Python.

🤔 Every evening Riya logged in to a server just to run one script that summarised the day’s orders file — 40 seconds of work, a server billed all month, and a missed report whenever she was on leave.

AWS Lambda runs your code only when an event happens — a file lands in S3, an HTTP request arrives, a schedule fires — with no server to create, patch or scale. You upload a function, give it a role, connect a trigger, and pay per request and per millisecond. This lesson shows what happens inside Lambda (cold starts, execution environments, concurrency), the ways to trigger it, memory/timeout/limits, packaging, and builds an S3-triggered report function on your own account or in the simulator.

  • Function + trigger + execution role = serverless job.
  • Pay per request and GB-second; nothing when idle.
  • Limits: 15 minutes, 10 GB memory, stateless.

2 Definition

AWS Lambda

Formal definition (write this in exams)

AWS Lambda is a serverless, event-driven compute service that runs functions in managed execution environments (Firecracker micro-VMs) in response to synchronous, asynchronous or polled events, scaling concurrency automatically, with permissions from an execution role, configurable memory (128 MB–10 GB, proportional CPU) and timeout (up to 15 minutes), billed per request and per GB-second.

In simple words

Lambda runs your code only when something happens — a file upload, a web request, a schedule — and you pay only for the milliseconds it runs.

Say it in an interview

30-second answer you can speak:

  • “Lambda runs stateless functions on events; I give it a least-privilege execution role, connect triggers like S3, API Gateway, EventBridge or SQS, size memory with power tuning, and handle async failures with retries and DLQs/destinations.”
  • “Limits drive design: 15 minutes, 10 GB memory, payload sizes and concurrency quotas; for long or constant heavy work I use Fargate or EC2, and Step Functions to orchestrate.”

3 The big picture

Triggers, cost, and the function

New to computers? Start here. Lambda is like an electrician on call: you do not hire him full-time. When a switch trips (an event), he comes, fixes it in minutes, and leaves; you pay for the visit and the minutes. If ten switches trip at once, ten electricians come. If nothing trips all month, you pay nothing.

Jargon buster:

  • Function — your code plus settings
  • Handler — the function Lambda calls first
  • Event — the message describing what happened
  • Trigger — the service that sends events (S3, API, schedule)
  • Execution role — permissions the code runs with
  • Cold start — extra delay when a new environment starts
  • GB-second — memory × time, the unit you pay for

One function, many triggers

Situation — a small job: server vs Lambda

The function used in this lesson

import json, urllib.parse
import boto3

s3 = boto3.client("s3")          # created once per environment (outside the handler)

def lambda_handler(event, context):
    rec = event["Records"][0]["s3"]
    bucket = rec["bucket"]["name"]
    key = urllib.parse.unquote_plus(rec["object"]["key"])      # e.g. uploads/orders.csv
    body = s3.get_object(Bucket=bucket, Key=key)["Body"].read().decode("utf-8", "replace")
    rows = max(body.count("\n") - 1, 0)                         # minus header line
    out = "reports/" + key.split("/")[-1] + ".summary.txt"
    report = f"file={key}\nrows={rows}\nbytes={len(body)}\nprocessed_by={context.function_name}\nrequest_id={context.aws_request_id}\n"
    s3.put_object(Bucket=bucket, Key=out, Body=report.encode())
    print(json.dumps({"in": key, "out": out, "rows": rows}))   # goes to CloudWatch Logs
    return {"out": out, "rows": rows}

Definition (say it in an interview): A function is code plus configuration; Lambda calls the handler (e.g. lambda_function.lambda_handler) with an event (JSON describing what happened) and a context (request ID, remaining time, function name) on a managed runtime — Python, Node.js, Java, .NET, Ruby, or an OS-only runtime for Go/Rust/custom.

  5. Init code. Outside handler.

Words used above, in simple terms: runtime = language environment AWS manages · event = JSON input · context = metadata object

Type 2 · Triggers and invocation types

Definition (say it in an interview): Lambda is invoked synchronously (API Gateway, function URL, CLI invoke — caller gets the response), asynchronously (S3, SNS, EventBridge — Lambda queues the event, retries up to 2 times and can send failures to a destination or DLQ), or by an event source mapping that polls SQS, Kinesis, DynamoDB Streams, Kafka in batches.

In plain words (no jargon): The different ways something can start your function.

Analogy: Phone call (sync), WhatsApp message (async), or the electrician checking a job board (poll).

How it works internally, step by step

  1. Sync. Response returned.
  2. Async. Retries, destinations.
  3. Poll. Batch size, window.
  4. Filters. Prefix/suffix, patterns.
  5. Loops. Detect recursion.

Words used above, in simple terms: DLQ = dead-letter queue for failed events · destination = where async results go · event source mapping = poller config

Type 3 · Permissions: execution role and resource policy

Definition (say it in an interview): The execution role (trust: lambda.amazonaws.com) grants what the code may call — at minimum CloudWatch Logs (AWSLambdaBasicExecutionRole), plus e.g. s3:GetObject on uploads/*; the function’s resource-based policy says who may invoke it (e.g. s3.amazonaws.com from your bucket, added with lambda add-permission).

In plain words (no jargon): What the function may touch, and who may run it.

Analogy: The electrician’s tool-kit (role) and the list of people allowed to call him (resource policy).

How it works internally, step by step

  1. Role trust. lambda.amazonaws.com.
  2. Logs. Basic execution role.
  3. Data. Prefix-scoped.
  4. Invoke. add-permission.
  5. Conditions. SourceArn/Account.

Words used above, in simple terms: resource-based policy = policy attached to the function · confused deputy = service tricked into acting for another account · PassRole = needed to create the function with a role

Type 4 · Memory, timeout and concurrency

Definition (say it in an interview): Memory (128 MB–10,240 MB) also allocates CPU proportionally (one full vCPU at about 1,769 MB, up to 6 vCPUs); timeout is 1 s–15 min; /tmp storage 512 MB–10 GB; concurrency = in-flight environments, with a Regional quota (often 1,000, lower for new accounts) shared by all functions — reserved concurrency caps or guarantees a function’s share.

In plain words (no jargon): How big, how long, and how many copies at once.

Analogy: How strong each electrician is, how long he may stay, and how many can come at once.

How it works internally, step by step

  1. Memory. 128 MB–10 GB.
  2. CPU. Scales with memory.
  3. Timeout. ≤ 900 s.
  4. Concurrency. Shared quota.
  5. Reserved. Cap/guarantee.

Words used above, in simple terms: throttle = rejected because concurrency is full · reserved concurrency = dedicated slice · ephemeral storage = /tmp space

Type 5 · Cold starts, SnapStart and provisioned concurrency

Definition (say it in an interview): A cold start happens when Lambda creates a new execution environment: download code, start the runtime, run initialisation; it adds from ~100 ms (small Python/Node) to seconds (large Java). Environments are reused while warm. Reduce cold starts with small packages and lazy imports, SnapStart (snapshot of initialised environment; Java, Python, .NET) or provisioned concurrency (pre-initialised environments, billed while configured).

In plain words (no jargon): Why the first call can be slower and how to avoid it.

Analogy: The electrician’s first visit takes longer — he has to find the house; next time he knows the way.

How it works internally, step by step

  1. Cold. New env.
  2. Init. Imports, clients.
  3. Warm. Reused.
  4. SnapStart. Snapshot.
  5. Provisioned. Pre-warmed.

Words used above, in simple terms: Init duration = cold-start time shown in logs · SnapStart = restore from snapshot · provisioned concurrency = always-ready environments

5 How it works, step by step

What happens when a file lands in S3

Event, cold start, handler, scale, sleep.

Animated

What happens when a file lands in S3 and Lambda runs

Upload one file, watch a function wake up, do its job, scale to fifty copies, and go back to sleep.

Event to result 6 steps
Watch what happens
  1. Step 1 · A file arrives — Riya uploads orders.csv to uploads/. S3 notices the new object.
  2. Step 2 · Event invokes the function — S3 invokes the function asynchronously with an event describing the bucket and key; Lambda finds or creates an execution environment.
  3. Step 3 · Cold start (first time only) — Lambda downloads the code, starts the Python runtime and runs code outside the handler (imports, clients). Later invocations skip this.
  4. Step 4 · The handler runs — with temporary credentials from the execution role it reads the CSV, writes a summary to reports/, and print() lines go to CloudWatch Logs.
  5. Step 5 · Automatic scaling — many events at once → many environments in parallel, one event each, up to your concurrency limit. No Auto Scaling group to configure.
  6. Step 6 · Sleep and pay per use — idle environments are kept warm for a while, then reclaimed. You pay per request and per GB-second of run time — nothing while idle.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: Some jobs are tiny and happen now and then — like sending an SMS when an order arrives. Instead of keeping a computer on all day, AWS can run that small piece of code only at that moment.

Try: List three “when X happens, do Y” jobs from daily life (doorbell → light on). Each is a Lambda function: X is the trigger, Y is the code.

Check yourself: If nobody rings the doorbell all month, how much do you pay for the light-switching job?

Nothing for compute — Lambda bills only when it runs.

Level 1 · Beginner first steps on AWS

Understand: Function = code + handler + runtime; triggers start it; the execution role gives permissions; logs go to CloudWatch; max 15 minutes.

Try: Do the simulator, then read a REPORT line and calculate GB-seconds.

Check yourself: Where do print() messages from a function go?

CloudWatch Logs, log group /aws/lambda/<function-name>.

Level 2 · Intermediate can do it alone

Understand: Build S3-triggered processing with prefix filters, add-permission, prefix-scoped role, idempotent output, and test cold vs warm.

Try: Do the full hands-on; then upload 20 files at once and check ConcurrentExecutions in CloudWatch.

Check yourself: Your function writes to the same bucket and the bill explodes — why?

Recursive trigger: output objects triggered the function again. Filter by prefix or use another bucket.

Level 3 · Advanced designs for others

Understand: Use async destinations/DLQs, reserved and provisioned concurrency, SnapStart, layers, container images, aliases with weighted traffic, Powertools for structured logs and tracing.

Try: Add an on-failure destination (SQS) and force an error; inspect the failed event. Then publish v1, v2 and shift 10% traffic via an alias.

Check yourself: SQS-triggered function keeps reprocessing the same message — why?

The handler fails (or times out) so the message returns after the visibility timeout; fix the error, use partial batch responses and a DLQ, and make visibility timeout ≥ 6× function timeout.

Level 4 · Expert architect / interviewer

Understand: Design event-driven systems: EventBridge buses, Step Functions orchestration, idempotency keys, back-pressure with SQS, cost models comparing Lambda vs Fargate vs EC2 at scale, multi-account deployment with SAM/CDK pipelines.

Try: Model cost at 1, 10 and 100 million requests/month for a 200 ms, 512 MB function vs Fargate tasks; find the crossover.

Check yourself: Why put SQS between API Gateway and a Lambda that calls a slow partner API?

To absorb spikes, control concurrency, and retry safely without losing requests (back-pressure).

8 Deep dive

REPORT lines, pricing, stateless and idempotent

Read a REPORT line

START RequestId: 8c1f… Version: $LATEST
{"in": "uploads/orders.csv", "out": "reports/orders.csv.summary.txt", "rows": 142}
END RequestId: 8c1f…
REPORT RequestId: 8c1f… Duration: 412.55 ms  Billed Duration: 413 ms  Memory Size: 256 MB  Max Memory Used: 88 MB  Init Duration: 381.20 ms

Billed Duration × Memory = GB-seconds: 0.413 s × 0.25 GB ≈ 0.10 GB-s. Init Duration appears only on cold starts. Max Memory Used (88 MB) says 256 MB is plenty — maybe even 128 MB (test speed first).

Stateless means…

  • Nothing in memory or /tmp is guaranteed to exist on the next call (it might, if warm — use it only as a cache).
  • Keep state in S3, DynamoDB, RDS, ElastiCache.
  • Make handlers idempotent: async events can arrive twice — processing the same file twice must not double-count.
9 Under the hood

Firecracker, environment lifecycle, scaling rate, networking

What actually runs your function.

1 · Firecracker micro-VMs

Each execution environment runs inside a Firecracker micro-VM on a Lambda worker host — strong isolation between customers with a boot measured in milliseconds. One environment processes one event at a time; concurrency = number of environments.

2 · Environment lifecycle

PhaseWhat happens
Initextensions start, runtime starts, your init code (imports, clients) runs — up to 10 s, billed (for on-demand functions, init is now billed like invoke)
Invokehandler runs for each event; environment reused while warm
Shutdownafter idle time (not fixed, minutes) or for maintenance; a SIGTERM-style shutdown phase for extensions

3 · How fast it scales

Each function can add up to 1,000 concurrent executions every 10 seconds (until the account concurrency quota is reached). Bursty traffic beyond that is throttled briefly — queues (SQS) smooth it out.

4 · Networking

By default functions reach the internet and AWS public endpoints. Attached to a VPC (to reach RDS in private subnets), they use Hyperplane ENIs shared across environments; they then need a NAT gateway or VPC endpoints to reach the internet/S3. Old “VPC cold start of 10+ seconds” advice is outdated.

5 · Credentials

Lambda assumes the execution role and puts temporary credentials into environment variables (AWS_ACCESS_KEY_ID, AWS_SESSION_TOKEN…) of the environment; the SDK picks them up. Never log os.environ.

2 Updated function code

Header must be order_id,item,amount. head_object checks whether a report already exists (idempotency).

import json, os, urllib.parse, boto3
from botocore.exceptions import ClientError
s3, sns = boto3.client("s3"), boto3.client("sns")
TOPIC = os.environ["TOPIC_ARN"]

def lambda_handler(event, context):
    r = event["Records"][0]["s3"]; b = r["bucket"]["name"]; k = urllib.parse.unquote_plus(r["object"]["key"])
    name = k.split("/")[-1]; out = f"reports/{name}.summary.txt"
    try:
        s3.head_object(Bucket=b, Key=out); print(json.dumps({"skip": k})); return {"skipped": k}
    except ClientError:
        pass
    lines = s3.get_object(Bucket=b, Key=k)["Body"].read().decode("utf-8", "replace").splitlines()
    if not lines or lines[0].strip() != "order_id,item,amount":
        s3.copy_object(Bucket=b, Key=f"rejected/{name}", CopySource={"Bucket": b, "Key": k}); s3.delete_object(Bucket=b, Key=k)
        sns.publish(TopicArn=TOPIC, Subject="Rejected upload", Message=f"{k} has a wrong header: {lines[0] if lines else 'empty'}")
        return {"rejected": k}
    total = sum(float(l.split(",")[2]) for l in lines[1:] if l.count(",") == 2)
    s3.put_object(Bucket=b, Key=out, Body=f"file={k}\nrows={len(lines)-1}\ntotal_rs={total:.2f}\n".encode())
    return {"out": out}

import os, json, boto3
ec2 = boto3.client("ec2")
DRY = os.environ.get("DRY_RUN", "true") == "true"

def lambda_handler(event, context):
    res = ec2.describe_instances(Filters=[{"Name": "tag:env", "Values": ["lab"]}, {"Name": "instance-state-name", "Values": ["running"]}])
    ids = [i["InstanceId"] for r in res["Reservations"] for i in r["Instances"]]
    if ids and not DRY:
        ec2.stop_instances(InstanceIds=ids)
    print(json.dumps({"dry_run": DRY, "stopped": ids}))
    return {"dry_run": DRY, "stopped": ids}

Interview and viva questions

Is Lambda free?

The always-free allowance covers 1 million requests and 400,000 GB-seconds a month — enough for most learning.

Can Lambda host a website?

APIs yes (with API Gateway or function URLs); static pages belong on S3 + CloudFront.

Which language should I use?

Python or Node.js for quick starts; Java with SnapStart for enterprise code.

Real-world scenario questions (asked in company interviews)

Interview and viva questions.

Any companyFresher

“What is serverless?”

Basics.

The interviewer is checking: Events, no servers.

Show a strong answer

“You run code without managing servers: AWS creates environments on events, scales automatically and bills per request and milliseconds — Lambda is the core service.”

Avoid: “There are no servers at all.”

Service companyJunior

“A Lambda times out reading S3. Debug?”

Debug.

The interviewer is checking: Logs.

Show a strong answer
  • Check timeout (default 3 s), memory, VPC networking (no S3 endpoint/NAT), permissions; read REPORT and error lines.

Avoid: “Increase timeout to 15 min.”

Product companyMid-level

“Lambda or containers for our API?”

Trade-off.

The interviewer is checking: Load shape.

Show a strong answer
  • Spiky/low traffic and event glue → Lambda; constant high throughput, long requests or special runtimes → Fargate/ECS; compare cost per million requests and latency needs.

Avoid: “Always Lambda.”
