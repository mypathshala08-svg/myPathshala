Half the bill for the same work

2 Definition

AMIs, instance types and pricing

Formal definition (write this in exams)

An AMI is the image (EBS snapshots + launch permissions + block-device mapping) an instance boots from; the instance type defines vCPU, memory, storage, network and accelerators, named by family, generation, processor attributes and size; EC2 pricing combines On-Demand per-second billing with commitment discounts (Savings Plans, Reserved Instances), spare-capacity Spot pricing (interruptible with a two-minute notice), and dedicated or reserved-capacity options.

In simple words

The AMI is what is on the disk, the instance type is how big and what kind of server, and the pricing option is how you pay — per second, with a commitment, or cheaply on spare capacity.

Say it in an interview

30-second answer you can speak:

  • “I read a type like c7gn.2xlarge as compute-optimised, 7th generation, Graviton, network-enhanced, 8 vCPU — and pick the family by the bottleneck: CPU, memory, disk or accelerator.”
  • “Rightsize first, cover the steady base with a Compute Savings Plan, run interruptible work on diversified Spot, keep peaks On-Demand with Auto Scaling, and bake golden AMIs with Image Builder.”

3 The big picture

Read a type name, bake an image, choose a price

New to computers? Start here. An instance type is like choosing a vehicle: scooter (t-family) for short city trips, family car (m) for everything, sports car (c) for speed, a truck with a huge boot (r / x) for heavy memory, a delivery van full of shelves (i / d) for disks, and a crane (g / p) for heavy lifting like AI. Pricing is how you pay for it: pay-per-ride (On-Demand), a monthly pass (Savings Plan), or standby seats that can be taken back (Spot). An AMI is the vehicle delivered already packed with your luggage.

Jargon buster:

  • Instance type — size and kind of server (CPU, memory, extras)
  • Family — the letter: what the server is good at
  • vCPU — a virtual processor core
  • GiB — gibibyte, ≈ 1.07 GB of memory
  • Graviton — Amazon’s own Arm processors, cheaper per unit of work
  • Spot — spare capacity sold cheap; can be taken back
  • AMI — the saved disk image a server starts from

Type 1 · AMI — base, golden and custom images

Definition (say it in an interview): An AMI bundles one or more EBS snapshots (root and data volumes), launch permissions and a block-device mapping; you can use AWS-maintained, Marketplace or community AMIs, or create your own from an instance (create-image), copy it to other Regions (copy-image, optionally re-encrypting), share it with accounts or an organisation, and deprecate or deregister it.

In plain words (no jargon): A saved copy of a server’s disk that new servers start from.

Analogy: A photocopy master: once the master page is perfect, every copy is identical and quick.

How it works internally, step by step

  1. Snapshot. Disk copy behind the AMI.
  2. Permissions. Private, shared, public.
  3. Region. Copy to use elsewhere.
  4. Encryption. Copy with a KMS key.
  5. Deprecate. Hide old versions.

Words used above, in simple terms: golden AMI = your approved, pre-configured image · EC2 Image Builder = service that builds and tests AMIs on a schedule · deregister = delete the AMI record (snapshots remain until deleted)

Type 2 · Burstable — t3, t3a, t4g

Definition (say it in an interview): The t-family gives a baseline CPU share (e.g. 10% per vCPU for t3.micro) and earns CPU credits while below it; it can burst to 100% by spending credits. In unlimited mode (default for t3/t4g) it keeps bursting and you pay for surplus credits; in standard mode it is throttled to the baseline when credits run out.

In plain words (no jargon): Cheap servers that save up CPU when idle and spend it during spikes.

Analogy: A prepaid mobile plan: unused data rolls over; heavy use eats the balance; then you are slowed or pay extra.

How it works internally, step by step

  1. Baseline. Guaranteed share.
  2. Credits. Earned when idle.
  3. Burst. Up to 100%.
  4. Unlimited. Pay surplus.
  5. Watch. CPUCreditBalance.

Words used above, in simple terms: baseline = CPU % you can use forever · CPU credit = one vCPU at 100% for one minute · t4g = Graviton version — cheapest

Type 3 · General purpose — m7i, m7g, m7i-flex

Definition (say it in an interview): The m-family balances compute, memory and networking at about 1 vCPU : 4 GiB; variants by processor (i Intel, a AMD, g Graviton) and extras (d local NVMe, n network). Flex types (m7i-flex) cost less and deliver full CPU most of the time — fine for workloads that are not CPU-bound all day.

In plain words (no jargon): Balanced servers — the safe default.

Analogy: The family car — not the fastest or the biggest, but right for most trips.

How it works internally, step by step

  1. Ratio. 1:4.
  2. Processors. i / a / g.
  3. Extras. d, n.
  4. Flex. Cheaper.
  5. Upgrade. Newer gen.

Words used above, in simple terms: m7g = Graviton3 general purpose · m7i-flex = cheaper Intel variant · metal = whole physical server

Type 4 · Compute optimised — c7i, c7g, c7gn

Definition (say it in an interview): The c-family gives more CPU per GiB (about 1 vCPU : 2 GiB) on high-performance processors, for workloads where CPU is the bottleneck: busy APIs, video encoding, batch processing, game servers, scientific modelling, ML inference on CPU.

In plain words (no jargon): Servers with lots of processing power.

Analogy: A sports car: fast engine, small boot.

How it works internally, step by step

  1. Ratio. 1:2.
  2. Uses. Encoding, APIs, HPC.
  3. n. Network heavy.
  4. Graviton. c7g/c8g.
  5. Measure. CPU% high, RAM low.

Words used above, in simple terms: HPC = high-performance computing · transcoding = converting video formats · c7gn = Graviton + enhanced network

Type 5 · Memory optimised — r7i, r7g, x2, u

Definition (say it in an interview): The r-family (about 1 vCPU : 8 GiB) and x-family (16 GiB per vCPU or more) suit workloads that keep large data in memory: databases, caches (Redis), in-memory analytics (Spark, pandas), SAP; high-memory u types reach multiple terabytes.

In plain words (no jargon): Servers with lots of memory.

Analogy: A truck with an enormous boot: not the fastest, but carries everything at once.

How it works internally, step by step

  1. r. 1:8.
  2. x. 1:16+.
  3. Uses. DB, cache, Spark.
  4. Signals. OOM, swap.
  5. Graviton. r7g/r8g.

Words used above, in simple terms: in-memory = data kept in RAM for speed · OOM = out of memory error · SAP HANA = in-memory enterprise database

Type 6 · Storage optimised — i4i, i4g, d3

Definition (say it in an interview): The i-family (local NVMe SSD) and d-family (dense local HDD) attach large, very fast instance store disks for workloads with heavy sequential or random I/O: NoSQL databases (Cassandra, MongoDB), Kafka, Elasticsearch/OpenSearch, data warehousing, HDFS. Instance store data is lost on stop or terminate, so the software must replicate it.

In plain words (no jargon): Servers with very fast built-in disks.

Analogy: A delivery van lined with shelves: very fast to load and unload, but empties when returned.

How it works internally, step by step

  1. i. NVMe SSD.
  2. d. Dense HDD.
  3. IOPS. Millions.
  4. Ephemeral. Lost on stop.
  5. Replicate. Software does it.

Words used above, in simple terms: IOPS = input/output operations per second · NVMe = fast SSD interface · ephemeral = temporary, not kept

Type 7 · Accelerated computing — g, p, inf, trn

Definition (say it in an interview): Accelerated instances add hardware accelerators: NVIDIA GPUs (g5/g6 for inference, graphics and small training; p4d/p5 for large-scale training), AWS Inferentia (inf2, low-cost inference) and Trainium (trn1/trn2, training); GPU capacity is scarce, so new accounts often have a 0 vCPU quota and teams reserve with Capacity Blocks for ML.

In plain words (no jargon): Servers with graphics cards or AI chips.

  3. inf/trn. AWS chips.
  4. Quota. Request early.
  5. Spot. Big savings for training.

Words used above, in simple terms: GPU = graphics processor, great for parallel maths · inference = using a trained model · Capacity Blocks = reserve GPUs for a future date range

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: Servers come in sizes, like T-shirts (small, medium, large), and in kinds, like vehicles (scooter, car, truck). You pay by the second, or cheaper if you promise to use one for a year, or very cheap if you accept being asked to leave.

Try: Write down three apps you use (a game, a bank app, a video app). Guess which matters most for each: speed of the processor, memory, disk or graphics.

Check yourself: Why is a “standby seat” (Spot) cheaper than a confirmed seat?

Because it can be taken back when someone else needs it — you trade certainty for price.

Level 1 · Beginner first steps on AWS

Understand: Read a type name (family, generation, processor, size); match t/m/c/r/i/g to workloads; know On-Demand vs Savings Plans vs Spot; an AMI is a saved disk image.

Try: Decode five type names from the EC2 console without looking at the table, then check.

Check yourself: r7g.large — family, processor, vCPU?

Memory optimised, Graviton (Arm), 2 vCPU (16 GiB).

Level 2 · Intermediate can do it alone

Understand: Rightsize with CloudWatch metrics and Compute Optimizer; compare prices in the calculator; bake and launch a custom AMI; use t-family credits correctly.

Try: Do the full hands-on; then compute a monthly cost for t3.medium On-Demand vs 1-year Savings Plan in the Pricing Calculator.

Check yourself: CPUCreditBalance is always 0 on a t3 web server — what does it mean?

The workload is not bursty; it needs a non-burstable type (m/c) or unlimited mode (and you are paying surplus).

Level 3 · Advanced designs for others

Understand: Design a pricing mix (Savings Plans coverage, Spot diversification with price-capacity-optimised allocation, On-Demand for peaks); Graviton migration; AMI pipelines with Image Builder, cross-Region copies and deprecation.

Try: Create an EC2 Image Builder pipeline (AL2023 + nginx component + a test) and distribute the output AMI to ap-south-2.

Check yourself: Savings Plan utilisation 60% for three months — what went wrong and what next?

Over-committed; usage dropped below the commitment. You still pay the full commitment — reduce future purchases, move workloads onto covered usage, buy smaller layered plans.

Level 4 · Expert architect / interviewer

Understand: Run FinOps: unit economics (cost per order/student), commitment laddering, Spot interruption handling at scale, licence-optimised Dedicated Hosts, capacity planning for GPUs (Capacity Blocks, ODCRs).

Try: Build a Cost Explorer report grouped by tag “project” and a cost-per-1,000-requests metric for one service.

Check yourself: Why might a company still pay On-Demand for a steady database?

Uncertain future (migration planned, growth unknown), or covered by RDS Reserved Instances instead — commitments only pay off if usage stays.

How a Savings Plan is applied every hour

You commit, say, USD 0.50/hour. Each hour AWS applies the discounted rates to your usage until the USD 0.50 is used (EC2 Instance SP first, then Compute SP, highest discount first). Usage beyond that is charged On-Demand. Unused commitment is not refunded — commit only to the steady base you are sure about (Cost Explorer recommends a number from your history).

Spot, without fear

  • Price changes slowly with long-term supply and demand; you pay the current Spot price (no bidding needed).
  • Interruption: a 2-minute warning in instance metadata (/latest/meta-data/spot/instance-action) and an EventBridge event; a rebalance recommendation may come earlier.
  • Diversify: allow many types and AZs (price-capacity-optimised allocation) so one pool running dry does not stop the job.
  • Good fits: CI runners, batch ETL, rendering, ML training with checkpoints, stateless web workers behind a load balancer. Bad fits: single databases, long jobs that cannot restart.

9 Under the hood

Nitro, vCPUs, credits, Spot pools, AMI storage

What sits behind instance types, credits, Spot and AMIs.

1 · What a vCPU really is

On most x86 types a vCPU is one hyper-thread of a physical core (2 vCPU = 1 core). On Graviton a vCPU is a full physical core — one reason Graviton does more work per vCPU for many workloads. You can disable hyper-threading (CPU options) for licences that count cores.

2 · How burstable credits are counted

One CPU credit = one vCPU at 100% for one minute. A t3.micro (baseline 10% per vCPU, 2 vCPUs) earns 12 credits per hour and can bank up to 288 (24 hours’ worth). In unlimited mode, if the 24-hour average stays above baseline, surplus credits are billed per vCPU-hour (around USD 0.05 for Linux t3).

3 · Spot pools and interruptions

Each combination of instance type + AZ is a separate Spot capacity pool with its own price. When On-Demand demand rises in a pool, AWS reclaims Spot instances there: you get a rebalance recommendation (early signal) and an interruption notice two minutes before stop/terminate/hibernate. Using many pools (types × AZs) with the price-capacity-optimized allocation strategy makes interruptions rare and cheap to absorb.

4 · Where an AMI lives

An EBS-backed AMI is a registry entry (ID, name, architecture, permissions, block-device mapping) pointing to EBS snapshots stored in S3 (managed by AWS, you do not see the bucket). Launching restores the snapshot lazily — blocks load on first read — so the first boot from a fresh AMI can be slower; Fast Snapshot Restore or a warm-up read removes the delay for large fleets.

5 · How Savings Plans are billed

HourUsage at On-DemandCommitment USD 0.50/h at SP ratesBilled

6 · Nitro and bare metal

Because Nitro offloads networking and storage to cards, AWS can sell .metal sizes — the whole physical server with no hypervisor — for workloads needing hardware features (nested virtualisation, special licensing, performance counters).

2 The job script

Save as job.sh and put your bucket name in B.

#!/bin/bash
# runs as user data on a Spot instance: process 20 "chunks", checkpoint each to S3, stop cleanly on interruption
B="spot-lab-123456789012"; export AWS_DEFAULT_REGION=ap-south-1
TOKEN() { curl -s -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60"; }
START=$(aws s3 cp s3://$B/checkpoint.txt - 2>/dev/null || echo 0)
for i in $(seq $((START+1)) 20); do
  CODE=$(curl -s -o /dev/null -w '%{http_code}' -H "X-aws-ec2-metadata-token: $(TOKEN)" http://169.254.169.254/latest/meta-data/spot/instance-action)
  if [ "$CODE" = "200" ]; then echo "interruption notice at chunk $i" | aws s3 cp - s3://$B/log/interrupted.txt; exit 0; fi
  sleep 30                                   # "work" on chunk $i
  echo $i | aws s3 cp - s3://$B/checkpoint.txt
done
echo "all 20 chunks done" | aws s3 cp - s3://$B/log/done.txt

3 Launch on Spot

sed -i "s/^B=.*/B=\"$B\"; export AWS_DEFAULT_REGION=ap-south-1/" job.sh
ID=$(aws ec2 run-instances --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --instance-type t3.micro \
  --instance-market-options 'MarketType=spot,SpotOptions={SpotInstanceType=one-time,InstanceInterruptionBehavior=terminate}' \
  --iam-instance-profile Name=SpotJobRole --metadata-options HttpTokens=required --user-data file://job.sh --query 'Instances[0].InstanceId' --output text)
aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].InstanceLifecycle' --output text

Remember these
  • Pick the family by the bottleneck, not by size.
  • Rightsize before committing.
  • Spot only for interruptible work.
  • Deregistering an AMI leaves its snapshot billing.

Interview and viva questions

Is Graviton always cheaper?

Usually better price-performance, but your software needs Arm builds — test first.

Should students buy a Savings Plan?

No — learning usage is not steady. Use the Free plan, budgets and terminate after labs.

Are prices the same in every Region?

No — they differ by Region and OS; always check Mumbai/Hyderabad prices.
