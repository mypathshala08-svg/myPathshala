1 The story

Too small at lunch, too big at 3 am

Before you start: Lessons 3.1–3.4.

🤔 Diwali lunch, 1:05 pm: TiffinGo’s single server hit 100% CPU and orders failed for 14 minutes. At 3 am the same server sat idle, still billed. One server is both too small and too big.

Two services fix that together. Elastic Load Balancing gives users one stable address and spreads requests over many healthy servers in several AZs. EC2 Auto Scaling keeps the right number of servers running — adding them when load rises, removing them when it falls, and replacing failed ones automatically. This lesson builds both: a launch template, an Application Load Balancer with a target group, and an Auto Scaling group with a target-tracking policy — then you kill a server and watch it heal.

  • Load balancer = one front door, many healthy servers.
  • Auto Scaling group = min / desired / max, across AZs.
  • Target tracking keeps a metric (e.g. CPU 50%) steady.

TiffinGo’s single server failed during the Diwali lunch rush and idled all night. A load balancer and an Auto Scaling group let the fleet grow, heal and shrink by itself.

2 Definition

Auto Scaling and Elastic Load Balancing

Formal definition (write this in exams)

Elastic Load Balancing distributes incoming traffic across healthy targets in multiple Availability Zones (Application Load Balancer at layer 7, Network Load Balancer at layer 4, Gateway Load Balancer for appliances). Amazon EC2 Auto Scaling maintains a group of instances launched from a launch template between minimum and maximum sizes, adjusting desired capacity with scaling policies and replacing unhealthy instances.

In simple words

The load balancer is one front door that shares visitors among servers; Auto Scaling keeps the right number of healthy servers behind it, adding, removing and replacing them automatically.

Say it in an interview

30-second answer you can speak:

  • “I put stateless servers in an Auto Scaling group across two or more AZs, behind an ALB with ELB health checks, scale with target tracking plus scheduled capacity for known peaks, and roll out changes with launch template versions and instance refresh.”
  • “ALB for HTTP routing, NLB for TCP/UDP or static IPs, GWLB for inline appliances; web servers only accept traffic from the ALB’s security group.”

3 The big picture

Inside the load balancer, and a day of scaling

New to computers? Start here. A load balancer is the token counter at a busy bank: customers queue at one counter, and the token system sends each to a free cashier. Auto Scaling is the branch manager who opens more cashier windows when the queue grows, closes them when it shrinks, and replaces a cashier who falls ill — always keeping at least two open.

Jargon buster:

  • Load balancer — one address that spreads visitors over many servers
  • Target group — the list of servers a load balancer sends to
  • Health check — a regular “are you OK?” request to each server
  • Auto Scaling group — a team of identical servers that grows and shrinks
  • Launch template — the recipe for each new server
  • Scale out / in — add / remove servers

Type 1 · Launch templates

Definition (say it in an interview): A launch template stores instance settings — AMI, instance type(s), security groups, IAM instance profile, user data, storage, metadata options, tags — as numbered, immutable versions (with a $Default and $Latest); Auto Scaling groups, EC2 Fleet and run-instances launch from it (launch configurations are the legacy predecessor).

In plain words (no jargon): A saved recipe for creating identical servers.

Analogy: A recipe card in the kitchen: every new cook makes the dish the same way.

How it works internally, step by step

  1. Settings. All of launch.
  2. Versions. Immutable.
  3. Default. Which version ASG uses.
  4. Mixed types. Overrides.
  5. IMDSv2. Set here.

Words used above, in simple terms: version = saved snapshot of settings · $Latest = newest version · override = alternative instance types

Type 2 · Auto Scaling groups

Definition (say it in an interview): An Auto Scaling group keeps desired capacity instances running between a minimum and maximum, launched from a launch template into subnets in several AZs and kept balanced across them; it can mix On-Demand and Spot and multiple instance types, and registers instances with load-balancer target groups.

In plain words (no jargon): A self-managing group of identical servers.

Analogy: The bank manager’s rule: at least 2 counters, at most 6, as many as the queue needs.

How it works internally, step by step

  1. Min/Max. Floor/ceiling.
  2. Desired. Current target.
  3. Subnets. Multi-AZ.
  4. Mixed. Spot + On-Demand.
  5. Balance. Across AZs.

Words used above, in simple terms: stateless = keeps no unique data on the server · AZ rebalancing = evening out across zones · mixed instances policy = several types / Spot

Type 3 · Scaling policies

Definition (say it in an interview): Target tracking keeps a metric (average CPU, ALB requests per target, network) near a target value like a thermostat; step scaling adds/removes amounts by alarm breach size; scheduled actions set capacity at fixed times; predictive scaling forecasts daily/weekly patterns and launches ahead of time. A warm-up period stops new instances’ metrics distorting decisions.

In plain words (no jargon): Rules that decide when to add or remove servers.

Analogy: A thermostat for servers.

How it works internally, step by step

  1. Target. Thermostat.
  2. Step. Bigger jumps.
  3. Scheduled. Calendar.
  4. Predictive. Forecast.
  5. Warm-up. Ignore new instances briefly.

Words used above, in simple terms: cooldown/warm-up = waiting time after scaling · ALBRequestCountPerTarget = requests per server metric · predictive = ML forecast of load

Type 4 · Health checks and self-healing

Definition (say it in an interview): The load balancer health-checks each target (protocol, path such as /health, interval, healthy/unhealthy thresholds) and stops routing to unhealthy ones; the Auto Scaling group uses EC2 status checks by default and, when ELB health checks are enabled, also replaces instances the load balancer marks unhealthy — after a grace period that lets user data finish.

In plain words (no jargon): Automatic checks that remove and replace broken servers.

Analogy: The token counter skips a cashier who stops answering; the manager sends a replacement.

How it works internally, step by step

  1. Path. /health.
  2. Thresholds. Healthy/unhealthy.
  3. Grace period. Boot time.
  4. ELB type. Enable on ASG.
  5. Replace. Automatic.

Words used above, in simple terms: grace period = time before health checks count · deregistration delay = connection draining time · HealthyHostCount = CloudWatch metric

Type 5 · Application Load Balancer (ALB)

Definition (say it in an interview): An ALB works at layer 7 (HTTP/HTTPS/gRPC/WebSocket): listeners terminate TLS with ACM certificates, rules route by path, host, header, method or query to target groups (instances, IPs, Lambda), with sticky sessions, redirects, fixed responses, OIDC/Cognito authentication and WAF integration; it spans subnets in at least two AZs and is reached by a DNS name.

In plain words (no jargon): A load balancer that understands web requests.

Analogy: A smart receptionist who reads each visitor’s request and sends them to the right department.

How it works internally, step by step

  1. Listeners. Ports/TLS.
  2. Rules. Routing.
  3. Target groups. Backends.
  4. Health. Per group.
  5. Extras. WAF, auth, redirects.

Words used above, in simple terms: layer 7 = application level (HTTP) · TLS termination = decrypt HTTPS at the LB · sticky session = same user → same target

Type 6 · Network and Gateway Load Balancers

Definition (say it in an interview): A Network Load Balancer works at layer 4 (TCP, UDP, TLS) with ultra-low latency, one static IP (or Elastic IP) per AZ, client IP preservation and PrivateLink support; a Gateway Load Balancer (GENEVE, port 6081) transparently inserts fleets of firewall/inspection appliances into traffic. The Classic Load Balancer is legacy.

In plain words (no jargon): Load balancers for non-web traffic and for security appliances.

Analogy: NLB: a fast toll gate counting vehicles; GWLB: a security checkpoint every vehicle must pass.

How it works internally, step by step

  1. NLB. L4, static IPs.
  2. UDP. Supported.
  3. Client IP. Preserved.
  4. GWLB. Firewalls.
  5. CLB. Legacy.

Words used above, in simple terms: layer 4 = transport level (TCP/UDP) · PrivateLink = private service sharing · GENEVE = encapsulation protocol for GWLB

Type 7 · Rolling updates: instance refresh and lifecycle hooks

Definition (say it in an interview): Instance refresh replaces instances in batches to apply a new launch template version while keeping a minimum healthy percentage (with checkpoints and automatic rollback); lifecycle hooks pause instances in Pending:Wait or Terminating:Wait so you can run actions (install agents, upload logs before termination); warm pools keep pre-initialised stopped instances for faster scale-out.

In plain words (no jargon): Safely replacing all servers with a new version.

Analogy: Replacing cashiers one counter at a time so the bank never closes.

How it works internally, step by step

  1. Template v2. Change.
  2. Refresh. Batches.
  3. Min healthy. Keeps capacity.
  4. Hooks. Custom actions.
  5. Warm pool. Faster scale-out.

Words used above, in simple terms: rolling update = replace a few at a time · rollback = go back to the previous version · warm pool = stopped, ready instances

Watch what happens

  2. Step 2 · The spike — lunch rush: average CPU across the group hits 82%; the target-tracking policy’s CloudWatch alarm fires (target 50%).

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: When many people visit a website at once, one computer gets tired. A load balancer shares the visitors among several computers, and Auto Scaling adds or removes computers as the crowd changes.

Try: Watch a railway reservation counter: count open windows at 9 am vs 3 pm. How does the station decide? Map it to min, desired and max.

Check yourself: Why keep at least two servers even at night?

If one fails (or its AZ has a problem), the other keeps the site up.

Level 1 · Beginner first steps on AWS

Understand: ALB = one DNS name, listener → target group; ASG = min/desired/max from a launch template across AZs; health checks replace broken servers.

Try: Do the simulator; then explain the request path from browser to instance in five steps.

Check yourself: ALB returns 503 — what does it usually mean?

No healthy targets in the target group (none registered yet, or all failing health checks).

Level 2 · Intermediate can do it alone

Understand: Build the full stack: alb-sg/web-sg chaining, target tracking on CPU, ELB health checks with a grace period, prove self-healing.

Try: Do the hands-on; generate load (e.g. stress or a loop of curl) and watch desired capacity rise.

Check yourself: New instances keep getting terminated right after launch — why?

Health check grace period shorter than boot + user data, or the /health path returns 404.

Level 3 · Advanced designs for others

Understand: Use mixed instances (Spot + On-Demand), predictive + scheduled scaling, instance refresh with checkpoints, lifecycle hooks, warm pools, HTTPS with ACM and redirects, WAF.

Try: Add an HTTPS listener with an ACM certificate (needs a domain), redirect 80 → 443, and roll out template v2 with instance refresh.

Check yourself: Why use ALBRequestCountPerTarget instead of CPU?

For I/O-bound apps CPU stays low while requests queue; requests per target tracks real load.

Level 4 · Expert architect / interviewer

Understand: Design multi-AZ, multi-Region resilience: zonal shift, cross-zone settings, Global Accelerator, Route 53 failover, capacity reservations for events, cost per request.

Try: Run a game day with AWS FIS: stop instances in one AZ and measure recovery; document RTO.

Check yourself: An AZ is impaired; how do you stop the ALB sending traffic there quickly?

Use ARC zonal shift on the load balancer (and let ASG launch capacity in healthy AZs).

9 Under the hood

ALB nodes, cross-zone, draining, AZ rebalancing

How load balancers and Auto Scaling really behave.

1 · An ALB is a fleet too

Behind the DNS name, AWS runs load balancer nodes in each enabled AZ and scales them automatically. The DNS name returns several IPs that change over time — the reason you never hard-code them. Sudden huge spikes (e.g. 10× in seconds) can need pre-warming via AWS Support for very large events.

2 · Cross-zone load balancing

With cross-zone on (default for ALB), each node spreads requests across targets in all AZs, so uneven instance counts per AZ do not overload anyone. For NLB it is off by default (and cross-AZ data may be charged).

3 · Connection draining (deregistration delay)

When a target is deregistered (scale-in, refresh), the ALB stops new requests to it but lets in-flight ones finish for up to the deregistration delay (default 300 s; often lowered to 30–60 s for fast APIs).

4 · How Auto Scaling chooses whom to terminate

Default termination policy: first balance AZs (pick the AZ with most instances), then prefer instances using the oldest launch template/configuration, then those closest to the next billing hour, then random. You can choose policies like OldestInstance or protect instances from scale-in.

5 · AZ rebalancing

If AZs become uneven (an AZ had a problem, or Spot capacity moved), the ASG launches in the short AZ first and then terminates in the long AZ — it can temporarily exceed desired by up to 10%.

6 · Metrics behind target tracking

ASGAverageCPUUtilization comes from EC2 basic monitoring (5-minute) unless detailed monitoring (1-minute) is enabled in the launch template — enable it for faster reactions. Memory needs the CloudWatch agent.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. Two t3.micro instances and one ALB for about 30–45 minutes — a few rupees (the ALB has an hourly charge plus usage).

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Security groups and launch template

    UI way — AWS Management Console

    1. EC2 → Security Groups: create alb-sg (HTTP 80 from Anywhere) and change web-sg’s HTTP rule source to alb-sg. Launch templates → Create launch template web-lt: AL2023, t3.micro, web-sg, Advanced: Metadata V2 only, user data from the Deep dive.

    CLI way — the same thing with commands

    VPC=$(aws ec2 describe-vpcs --filters Name=is-default,Values=true --query 'Vpcs[0].VpcId' --output text)
SUBNETS=$(aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC Name=availability-zone,Values=ap-south-1a,ap-south-1b --query 'Subnets[].SubnetId' --output text)
ALBSG=$(aws ec2 create-security-group --group-name alb-sg --description 'alb public' --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $ALBSG --protocol tcp --port 80 --cidr 0.0.0.0/0 >/dev/null
WEBSG=$(aws ec2 create-security-group --group-name asg-web-sg --description 'web from alb' --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $WEBSG --protocol tcp --port 80 --source-group $ALBSG >/dev/null
# save the Deep-dive script as asg-web.sh
aws ec2 create-launch-template --launch-template-name web-lt --launch-template-data "{\"ImageId\":\"resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64\",\"InstanceType\":\"t3.micro\",\"SecurityGroupIds\":[\"$WEBSG\"],\"MetadataOptions\":{\"HttpTokens\":\"required\"},\"UserData\":\"$(base64 -w0 asg-web.sh)\"}" --query 'LaunchTemplate.LaunchTemplateId' --output text

    You should see: a launch template ID lt-0… and two security groups: alb-sg (public) and asg-web-sg (only from alb-sg).

    Launch templates take user data base64-encoded — the CLI does not encode it for you here, hence base64 -w0.

  3. 2 · Target group and Application Load Balancer

    UI way — AWS Management Console

    1. Target groups → Create web-tg: Instances, HTTP 80, health check path /health. Load balancers → Create → Application Load Balancer tiffingo-alb, internet-facing, subnets 1a + 1b, alb-sg, listener HTTP:80 → web-tg.

    CLI way — the same thing with commands

    TG=$(aws elbv2 create-target-group --name web-tg --protocol HTTP --port 80 --vpc-id $VPC --health-check-path /health --query 'TargetGroups[0].TargetGroupArn' --output text)
ALB=$(aws elbv2 create-load-balancer --name tiffingo-alb --subnets $SUBNETS --security-groups $ALBSG --query 'LoadBalancers[0].LoadBalancerArn' --output text)
aws elbv2 create-listener --load-balancer-arn $ALB --protocol HTTP --port 80 --default-actions Type=forward,TargetGroupArn=$TG >/dev/null
DNS=$(aws elbv2 describe-load-balancers --load-balancer-arns $ALB --query 'LoadBalancers[0].DNSName' --output text); echo $DNS

    You should see: a DNS name such as tiffingo-alb-1234567890.ap-south-1.elb.amazonaws.com. It returns 503 until targets are healthy.

    503 Service Temporarily Unavailable = the ALB works but has no healthy targets yet.

  4. 3 · Auto Scaling group, policy, and self-healing

    UI way — AWS Management Console

    1. Auto Scaling groups → Create tiffingo-asg: web-lt, subnets 1a + 1b, attach web-tg, turn on ELB health checks (grace 120 s), desired 2 / min 2 / max 4, target tracking CPU 50% → open http://DNS and refresh: the instance ID and AZ change. Then terminate one instance and watch a replacement appear in Activity.

    CLI way — the same thing with commands

    aws autoscaling create-auto-scaling-group --auto-scaling-group-name tiffingo-asg --launch-template LaunchTemplateName=web-lt,Version='$Latest' \
  --min-size 2 --max-size 4 --desired-capacity 2 --vpc-zone-identifier "$(echo $SUBNETS | tr ' ' ',')" \
  --target-group-arns $TG --health-check-type ELB --health-check-grace-period 120
aws autoscaling put-scaling-policy --auto-scaling-group-name tiffingo-asg --policy-name cpu50 --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{"PredefinedMetricSpecification":{"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50}' >/dev/null
sleep 180; for i in 1 2 3 4; do curl -s http://$DNS | grep -o 'Served by[^<]*'; done
VICTIM=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names tiffingo-asg --query 'AutoScalingGroups[0].Instances[0].InstanceId' --output text)
aws ec2 terminate-instances --instance-ids $VICTIM >/dev/null; sleep 90
aws autoscaling describe-scaling-activities --auto-scaling-group-name tiffingo-asg --max-items 2 --query 'Activities[].Description' --output text

    You should see: four lines alternating between two instance IDs in ap-south-1a and ap-south-1b, then an activity “Launching a new EC2 instance … in response to an unhealthy/terminated instance”.

    You just watched self-healing. Clean up promptly: an ALB is billed per hour.

Clean up and cost check

aws autoscaling delete-auto-scaling-group --auto-scaling-group-name tiffingo-asg --force-delete; aws elbv2 delete-load-balancer --load-balancer-arn $ALB; sleep 60; aws elbv2 delete-target-group --target-group-arn $TG; aws ec2 delete-launch-template --launch-template-name web-lt; when instances are gone delete asg-web-sg, then alb-sg.
