2 Definition

User data and bootstrapping

Formal definition (write this in exams)

Bootstrapping is automatic configuration of a server at launch. On EC2, user data (up to 16 KB, shell script or cloud-config) is delivered through the instance metadata service and executed by cloud-init as root once at first boot; persistent behaviour is provided by systemd (enabled services, timers) and cron, with AWS access through the instance role and configuration from Parameter Store or Secrets Manager.

In simple words

User data is a setup script you hand to EC2; the server runs it on its first start, so it installs, deploys, and schedules everything without anyone logging in.

Say it in an interview

30-second answer you can speak:

  • “I bootstrap with user data: install packages, deploy the artefact, enable services with systemd, schedule jobs, fetch secrets via the instance role, and write a deployment report — servers are disposable and identical.”
  • “User data runs once per instance; for every-boot behaviour I rely on systemd units or per-boot scripts, and for fleet-wide changes later I use SSM Run Command or a new launch template version.”

3 The big picture

Once, every boot, every hour

New to computers? Start here. User data is like leaving a to-do list on the kitchen table for a new house-helper who arrives while you are away: “switch on the geyser, cook dal, put the plant outside every morning, leave me a note when done.” cloud-init is the helper who reads the list on day one; systemd is the habit of switching the geyser on every morning; cron is the alarm that repeats the plant task; the note is the deployment report.

Jargon buster:

  • User data — a script you give EC2 at launch
  • cloud-init — the program that runs it at first boot
  • Bootstrapping — a server setting itself up automatically
  • systemd — Linux’s service manager (start/stop/enable)
  • cron — Linux scheduler that repeats commands
  • Git clone — copy a code repository from GitHub
  • Deployment report — a small file proving who deployed what, when

The single most important idea — what runs once, every boot, and on a schedule:

Situation — “must configure itself” in a lab exam

The complete script used in this lesson

#!/bin/bash
# deploy.sh — user data for a self-configuring web server (Amazon Linux 2023)
set -euxo pipefail
NAME="Riya"; ROLL="101"
BUCKET="tiffingo-lab-123456789012"          # ← your bucket
REPO="https://github.com/cloudacademy/static-website-example.git"   # ← or your own repo
export AWS_DEFAULT_REGION=ap-south-1

# 1. packages
dnf install -y nginx git cronie

# 2. deploy the site from Git and add the banner
git clone --depth 1 "$REPO" /opt/site
cp -r /opt/site/. /usr/share/nginx/html/
sed -i "s|</body>|<p style='background:#ffd;padding:8px'>Deployed by $NAME ($ROLL)</p></body>|" /usr/share/nginx/html/index.html

# 3. services that must come back after every reboot or stop/start
systemctl enable --now nginx crond

# 4. hourly log upload (cron.d needs \% for %)
cat > /etc/cron.d/upload-logs <<EOF
0 * * * * root aws s3 cp /var/log/nginx/access.log s3://$BUCKET/logs/\$(hostname)/access-\$(date +\%F-\%H).log --only-show-errors
EOF

# 5. deployment report → reports/
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
md() { curl -s -H "X-aws-ec2-metadata-token: $TOKEN" "http://169.254.169.254/latest/meta-data/$1"; }
ID=$(md instance-id)
cat > /tmp/report.txt <<EOF
deployed_by=$NAME ($ROLL)
time_utc=$(date -u +%FT%TZ)
instance=$ID az=$(md placement/availability-zone)
repo=$REPO commit=$(git -C /opt/site rev-parse --short HEAD)
nginx=$(systemctl is-active nginx) enabled=$(systemctl is-enabled nginx)
EOF
aws s3 cp /tmp/report.txt "s3://$BUCKET/reports/deploy-$ID.txt"
aws s3 cp /var/log/nginx/access.log "s3://$BUCKET/logs/$(hostname)/first-boot.log"   # prove the log path works now

Read it top to bottom: set -euxo pipefail stops at the first error and prints each command into the log; then packages → Git deploy + banner → enable services → cron → report. The next sections explain every block.

Type 1 · Shell script user data

Definition (say it in an interview): User data is up to 16 KB of data passed at launch; if it starts with #! cloud-init runs it as a script as root, once, at the end of the first boot. The CLI base64-encodes file:// input for you; output goes to /var/log/cloud-init-output.log.

In plain words (no jargon): A script that runs automatically when the server starts for the first time.

  4. Log. cloud-init-output.log.

Type 3 · systemd services

Definition (say it in an interview): systemd manages services: start runs one now, enable creates the boot-time link so it starts on every boot (the piece that survives stop/start), and a custom unit file with Restart=always keeps your own app (Flask, Node, Spring Boot) running even if it crashes.

In plain words (no jargon): The Linux tool that starts programs at boot and restarts them if they crash.

Analogy: A habit: switching on the geyser every morning without being told.

How it works internally, step by step

  1. start. Now.
  2. enable. At boot.
  3. status. Is it running?
  4. unit file. Your app.
  5. journalctl. Logs.

Words used above, in simple terms: unit = systemd’s description of a service · daemon-reload = reload after editing units · journalctl -u x = service logs

Type 5 · Scheduled jobs: cron and systemd timers

In plain words (no jargon): A timer that runs a command again and again.

Analogy: An alarm clock that repeats every hour.

  2. cron.d. User field.

  4. cronie. Install on AL2023.
  5. Timers. systemd alternative.

Words used above, in simple terms: crontab = a schedule table · cron.d = folder of system schedules · timer = systemd’s scheduler

Type 6 · Configuration and secrets at boot

Definition (say it in an interview): User data is readable by anyone with ec2:DescribeInstanceAttribute and from inside the instance via IMDS, so never put passwords or tokens in it; store them in SSM Parameter Store (SecureString) or Secrets Manager, grant the instance role read access, and fetch at boot into a root-only file or environment.

In plain words (no jargon): Getting passwords and settings safely when the server starts.

Analogy: Leaving the house key with the guard, not taped to the to-do list.

How it works internally, step by step

  1. Parameter Store. Config + SecureString.
  2. Secrets Manager. Rotation.
  3. Role. Read permission.
  4. File. chmod 600.
  5. Trace off. set +x.

Words used above, in simple terms: SecureString = encrypted parameter · rotation = automatic password change · EnvironmentFile = systemd reads variables from a file

Type 7 · Debugging and re-running user data

Definition (say it in an interview): Check cloud-init status --long (done / error / running), read /var/log/cloud-init-output.log on the instance or aws ec2 get-console-output from outside; user data does not re-run on reboot or stop/start — to change it, stop the instance, edit user data, and either launch a fresh instance (preferred) or run sudo cloud-init clean --logs --reboot.

In plain words (no jargon): How to find out why the setup script failed and run it again.

First boot, step by step 6 steps
Watch what happens
  1. Step 1 · cloud-init reads user data — at first boot cloud-init asks the instance metadata service for the user data and runs it as root, once.
  2. Step 2 · Install packages — dnf installs nginx, git and cronie. Output goes to /var/log/cloud-init-output.log.

7 Learn at your level

Level 1 · Beginner first steps on AWS

Try: Run the simulator using hints, then explain each line of deploy.sh to a friend.

Level 2 · Intermediate can do it alone

Understand: Deploy from Git with a banner, schedule hourly S3 uploads with an instance role, write a deployment report, debug with get-console-output.

Try: Do the full hands-on and collect the four pieces of evidence (page, report, logs, page after restart).

Level 3 · Advanced designs for others

Understand: Use cloud-config and multi-part user data, custom systemd units with Restart=always, Parameter Store secrets, per-boot scripts, launch templates and SSM Run Command for changes after launch.

Try: Convert deploy.sh to cloud-config + a systemd unit for a Flask app; store a fake API key in Parameter Store and read it at boot.

Level 4 · Expert architect / interviewer

Understand: Design immutable delivery: golden AMI for slow parts + thin user data, Auto Scaling instance refresh, CodeDeploy/containers, drift-free fleets, and bootstrap evidence in central logging.

Try: Build a pipeline: Image Builder bakes nginx; a launch template’s user data only pulls the release from S3; roll out with instance refresh (Lesson 3.5).

Check yourself: Why do mature teams keep user data small?

Faster, more reliable boots (fewer downloads at launch), fewer failure points, secrets and heavy installs handled elsewhere.

Once, every boot, or every instance?

  • Per-instance (default): your user data, keyed on the instance ID — runs once in the instance’s life.
  • Per-boot: put scripts in /var/lib/cloud/scripts/per-boot/ (or a systemd unit) to run at every boot.
  • Per-once: /var/lib/cloud/scripts/per-once/ — once ever, even if the image is reused.
  • An AMI baked from a bootstrapped instance carries cloud-init state; new instances from it get a new instance ID, so their own user data still runs.

9 Under the hood

How user data travels, base64, IMDS, Windows

How user data actually reaches and runs on your instance.

1 · Travel path

You pass user data with RunInstances (the CLI base64-encodes file:// content; the raw API expects base64). EC2 stores it with the instance; inside, it is served at http://169.254.169.254/latest/user-data (IMDSv2 token required if enforced). cloud-init’s EC2 data source fetches it early in boot and saves it under /var/lib/cloud/instance/.

2 · Format detection

Starts withTreated as
#!shell (or any interpreter) script, run in the final stage
#cloud-configYAML for cloud-init modules
#includelist of URLs to fetch and process
Content-Type: multipart/mixedMIME multi-part — several parts of different types
gzip datadecompressed first (fits more under 16 KB)

3 · Once per instance — how it knows

cloud-init records completed modules in /var/lib/cloud/instances/<instance-id>/sem/. On the next boot, same instance ID → skip. A new instance from a baked AMI has a new ID, so its user data runs. cloud-init clean deletes this state.

4 · Windows instances

Windows uses EC2Launch v2: wrap commands in <powershell>…</powershell> (or a YAML task document); add <persist>true</persist> to run on every boot.

5 · Network dependencies

Every dnf install or git clone needs outbound internet (public subnet with IGW, or NAT gateway for private subnets) and DNS. Private subnets without NAT need VPC endpoints (S3 gateway endpoint for S3; package repos for Amazon Linux are reachable through the S3 endpoint) — a classic reason scripts hang (Module 6).

6 · Viewing and changing user data

Read it back: describe-instance-attribute --attribute userData (base64). Change it only while the instance is stopped (modify-instance-attribute --user-data) — and it still will not re-run unless cloud-init state is cleaned.

4 The cloud-config

Save as api.yaml. Read it: files are written first, then runcmd installs Flask, fetches the secret and enables the service. Nothing secret is inside.

#cloud-config

  - path: /opt/api/app.py
    content: |
      import os, socket
      from flask import Flask
      app = Flask(__name__)
      KEY = os.environ.get("API_KEY", "")
      @app.get("/health")
      def health(): return "ok"
      @app.get("/key-check")
      def key_check(): return f"key loaded: {'****' + KEY[-4:] if KEY else 'NO'} on {socket.gethostname()}"
  - path: /etc/systemd/system/tiffingo-api.service
    content: |
      [Unit]
      Description=TiffinGo API
      After=network-online.target
      [Service]
      WorkingDirectory=/opt/api
      EnvironmentFile=/etc/api.env
      ExecStart=/usr/local/bin/gunicorn --bind 0.0.0.0:8080 --workers 2 app:app
      Restart=always
      RestartSec=2
      [Install]
      WantedBy=multi-user.target
  - path: /usr/local/bin/fetch-secret
    permissions: "0700"
    content: |
      #!/bin/bash
      set -e
      KEY=$(aws ssm get-parameter --name /tiffingo/api_key --with-decryption --query Parameter.Value --output text --region ap-south-1)
      install -m 600 /dev/null /etc/api.env
      echo "API_KEY=$KEY" > /etc/api.env
runcmd:
  - pip3 install flask gunicorn
  - /usr/local/bin/fetch-secret
  - systemctl daemon-reload
