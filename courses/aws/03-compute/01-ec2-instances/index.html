1 The story

Stopped on Friday, a new address on Monday

Before you start: Modules 1–2 (account, roles, CloudShell).

🤔 TiffinGo’s first AWS server took Riya 40 minutes in the console. When the IT intern stopped it “to save money” over the weekend, the customers’ bookmarked address stopped working on Monday.

An EC2 instance is a virtual server: you choose its operating system, size, disk, network and firewall, and AWS runs it on a physical machine in the AZ you pick. This lesson takes you from zero: what an instance is made of, the seven settings you choose at launch, what happens inside AWS when it boots, the lifecycle (and why the public IP changed on Monday), and how billing works. On your own account (or in the simulator) you will launch a web server that configures itself, open it in a browser, stop and start it, and terminate it cleanly.

  • Instance = type (CPU/RAM) + AMI (OS) + EBS (disk) + ENI (network) + security group (firewall).
  • Stop keeps the disk but changes the public IP; terminate deletes the root disk.
  • Pay per second while running; stopped costs only storage.

Riya launched TiffinGo’s first web server. The intern stopped it over the weekend to save money; on Monday it came back with a different public IP and customers’ bookmarks broke.

Riya

Sir, an EC2 instance is just a computer in AWS, right?

Arjun Sir

A virtual one, yes — a slice of a physical server. But it is assembled from parts: the type gives CPU and memory, the AMI gives the operating system, EBS gives the disk, a network card gives IP addresses, and a security group is the firewall.

Kabir

Then why did the address change after I stopped it?

Arjun Sir

The automatic public IP is released when an instance stops. The disk and private IP stay. For a fixed address you attach an Elastic IP — Lesson 3.4.

Riya

And the website came back by itself?

Arjun Sir

Only because the user data script enabled nginx at boot. Let’s launch one and watch each part.

2 Definition

EC2 instances

Formal definition (write this in exams)

An Amazon EC2 instance is a virtual server running on AWS-managed hardware (the Nitro System) in one Availability Zone, launched from an AMI with a chosen instance type (vCPU, memory, network), attached EBS storage, a network interface in a VPC subnet, security groups, optional IAM role and user data; it is billed per second while running and moves through the states pending, running, stopping, stopped, shutting-down and terminated.

In simple words

An EC2 instance is a computer you rent in AWS: pick its size and operating system, give it a disk, an address and firewall rules, and pay while it runs.

Say it in an interview

30-second answer you can speak:

  • “An EC2 instance is a virtual server from an AMI and an instance type, with EBS storage, an ENI in a subnet, security groups, and optionally an IAM role and user data; billing is per second while running.”
  • “Stop keeps EBS and the private IP but releases the auto public IP; terminate deletes the root volume by default — for a fixed address use an Elastic IP or a load balancer.”

3 The big picture

What an instance is made of

New to computers? Start here. An EC2 instance is like renting a furnished flat by the hour: you choose the size (instance type), the furniture (operating system from an AMI), the storage cupboard (EBS disk), the address (IP), and the door lock rules (security group). Type 1 · AMI (Amazon Machine Image)

Definition (say it in an interview): An AMI is the template an instance boots from — an operating system plus any pre-installed software, stored as EBS snapshot(s) with launch permissions; AMI IDs are specific to a Region, so scripts usually look up the latest one through public SSM parameters.

In plain words (no jargon): The ready-made disk image the server starts from.

Analogy: A pre-furnished flat template: every new flat built from it looks the same on day one.

How it works internally, step by step

  1. Source. AWS, Marketplace, community, your own.
  2. Region. IDs differ per Region.
  3. Arch. x86_64 or arm64.
  4. Root. EBS snapshot.
  5. Custom. Create your own (3.2).

Words used above, in simple terms: golden image = your own pre-configured AMI · Marketplace = AMIs sold by vendors · architecture = x86_64 vs arm64 (Graviton)

Type 2 · Instance type

Definition (say it in an interview): The instance type sets vCPU, memory, network and storage capabilities; its name encodes family (t = burstable, m = general, c = compute, r = memory…), generation, optional attributes (g = Graviton, d = local NVMe, n = network) and size — e.g. t3.micro = 2 vCPU, 1 GiB.

In plain words (no jargon): The size and kind of the virtual computer.

Analogy: Choosing a car: hatchback for city trips, truck for heavy loads, sports car for speed.

How it works internally, step by step

  1. Family. Purpose.
  2. Generation. Newer is cheaper per performance.
  3. Attributes. g, d, n, a, i.
  4. Size. vCPU/RAM.
  5. Resize. Stop → change → start.

Words used above, in simple terms: vCPU = virtual CPU (usually one hyper-thread) · burstable = t-family: earns CPU credits when idle · Graviton = AWS Arm processors

Type 3 · Key pair and login options

Definition (say it in an interview): To log in you can use a key pair (AWS stores the public key; you keep the private .pem), EC2 Instance Connect (pushes a one-minute key for SSH from the console/CLI), or Systems Manager Session Manager (browser/CLI shell through the SSM agent and an IAM role — no inbound port, every session logged).

In plain words (no jargon): The ways to get a command prompt on the server.

Analogy: A house key (key pair), a one-time guest code (Instance Connect), or a guard who opens the door after checking your ID (Session Manager).

How it works internally, step by step

  1. Key pair. Create/import.
  2. SSH rule. Your IP /32.
  3. Instance Connect. Console button.
  4. Session Manager. Role + agent.
  5. Audit. SSM logs sessions.

Words used above, in simple terms: .pem = private key file · /32 = exactly one IP address · SSM agent = pre-installed on Amazon Linux

Type 4 · Network settings (VPC, subnet, public IP)

Definition (say it in an interview): Every instance lives in a subnet of a VPC; the subnet fixes its Availability Zone and private IP range, and a public IPv4 can be auto-assigned (changes on stop/start) or replaced by an Elastic IP (fixed); each account has a default VPC with public subnets in every AZ.

In plain words (no jargon): Which network and street the server lives on.

Analogy: Choosing the colony (VPC), the street (subnet/AZ), and whether the house has a public door number.

How it works internally, step by step

  1. VPC. Default/custom.
  2. Subnet. AZ.
  3. Private IP. Kept on stop.
  4. Public IP. Released on stop.
  5. Elastic IP. Fixed (3.4).

Words used above, in simple terms: default VPC = ready-made network in each Region · public subnet = route to an internet gateway · Elastic IP = static public IPv4

Type 5 · Security group

Definition (say it in an interview): A security group is a stateful virtual firewall attached to the instance’s network interface: inbound rules allow specific protocols/ports from sources (CIDR ranges or other security groups); everything else inbound is denied, outbound is allowed by default, and responses to allowed traffic are automatically allowed.

In plain words (no jargon): The firewall that decides who may connect to the server.

Analogy: A guard with a guest list per door: door 80 is open to everyone, door 22 only to the owner.

How it works internally, step by step

  1. Inbound. Allow rules.
  2. Outbound. Default allow all.
  3. Source. CIDR or another SG.
  4. Stateful. Replies allowed.
  5. Change. Takes effect immediately.

Words used above, in simple terms: CIDR = IP range like 0.0.0.0/0 (anyone) · stateful = remembers connections · port = door number: 80 HTTP, 443 HTTPS, 22 SSH

Type 6 · Storage (EBS volumes)

Definition (say it in an interview): Instances boot from an EBS root volume (network-attached, persistent, in the same AZ) and may have extra EBS volumes; you choose size, type (gp3 by default), encryption and whether each volume is deleted on termination (root: yes by default; extra volumes: no). Some types also have fast, temporary instance store.

In plain words (no jargon): The server’s hard disk(s).

Analogy: The flat’s cupboard: it stays when you check out temporarily (stop), but the landlord empties it when you leave for good (terminate) — unless you said “keep it”.

How it works internally, step by step

  1. Root. gp3 8 GiB default.
  2. Extra. Attach more.
  3. Encrypt. KMS.
  4. DeleteOnTermination. Root true.
  5. Snapshot. Backups (4.5).

Words used above, in simple terms: EBS = Elastic Block Store · gp3 = general purpose SSD · instance store = local disk, lost on stop

What happens when you launch an EC2 instance

From one command to a web page — watch every part of the instance being assembled.

Launch to web page 6 steps
Watch what happens
  1. Step 1 · Ask for an instance — RunInstances names an AMI, an instance type, a subnet (AZ), a security group, a key pair or role, and optional user data.
  2. Step 2 · Find capacity — the EC2 control plane picks a physical Nitro host in the chosen AZ with room for a t3.micro (2 vCPU, 1 GiB) — state “pending”.
  3. Step 3 · Attach the pieces — an EBS root volume is created from the AMI’s snapshot, a network interface gets a private IP (and a public IP if enabled), and the security group is applied to that interface.
  4. Step 4 · Boot and configure — the OS boots from the EBS volume; cloud-init runs your user data script once — installing nginx and writing the page.
  5. Step 5 · Running and healthy — state becomes “running”; two status checks (system and instance) confirm the host and the OS are reachable. Billing has started.
  6. Step 6 · Serving users — the security group lets port 80 in from anywhere, so a browser on the public IP shows the page.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: A cloud server is a computer you rent by the second in an AWS building. You never see it; you reach it over the internet and switch it off when you are done.

Understand: An instance = AMI + instance type + EBS disk + network card + security group. Launch, open its public IP in a browser, terminate.

Try: Run the simulator below once using only the Hint button, then once without it.

The subnet you launch into.

Level 2 · Intermediate can do it alone

Understand: Launch self-configuring servers with user data, read status checks and console output, know exactly what survives stop/start/terminate.

Try: Do the full hands-on: user data web server → curl → stop/start → compare IPs → terminate.

nginx not enabled at boot (systemctl enable), or you are using the old public IP.

Level 3 · Advanced designs for others

Level 4 · Expert architect / interviewer

9 Under the hood

Nitro, placement, capacity, status checks, metadata

What AWS actually does when you press “Launch instance”.

1 · The Nitro System

Modern instances run on the AWS Nitro System: dedicated Nitro cards handle networking (ENA), EBS storage (NVMe) and security, and a lightweight Nitro hypervisor gives almost all of the host’s CPU and memory to instances. Nitro has no interactive operator access — AWS staff cannot log in to the host to read your memory. That is why EBS volumes appear as NVMe devices (/dev/nvme0n1) even though they are network storage.

2 · Placement and capacity

RunInstances goes to the EC2 control plane in the Region; the placement service finds a host with free capacity of that type in the chosen AZ. If none is free you get InsufficientInstanceCapacity — rare for small types, common for big GPU types. Placement groups change the rule: cluster (same rack, lowest latency for HPC/ML), spread (each instance on different hardware, max 7 per AZ), partition (groups of racks for Kafka/HDFS/Cassandra).

3 · Status checks

CheckWhat failsWho fixes
System statushost hardware, power, network to hostAWS — stop/start moves you to healthy hardware (or auto-recovery)
Instance statusyour OS: kernel panic, full disk, wrong network configyou — read console output, fix, reboot
Attached EBS statusEBS volume I/O impairedAWS / restore from snapshot

CloudWatch alarm on StatusCheckFailed_System with the action “Recover instance” keeps the instance ID, IPs and EBS on new hardware. Many types also recover automatically by default.

4 · Boot sequence

Host prepares → root EBS volume created from the AMI snapshot (blocks load lazily on first read, so the first boot can be slower) → ENI attached with private IP (+ public IP mapped at the internet gateway — the OS never sees the public IP, which is NAT-ed) → firmware/kernel boots → cloud-init reads metadata and user data from IMDS → runs your script once → instance status check passes.

5 · The public IP is not on the server

Run ip addr on an instance: you see only the private IP (e.g. 172.31.5.20). The internet gateway translates public ↔ private one-to-one. This is why the public IP can change on stop/start without touching the OS — and why apps should never bind to the public IP.

6 · Instance metadata (IMDS)

Every instance can reach 169.254.169.254 for its own ID, AZ, IPs, tags (if enabled), user data and role credentials. Require IMDSv2 (token via PUT) to stop SSRF attacks from stealing credentials — covered deeply in Lesson 2.2.

Runs APIs and workers on instances or behind load balancers.

Uses: Launch templates, user data, systemd services, CloudWatch agent logs.

A real task: Spring Boot / Node API on t3.small behind an ALB; deployed by user data pulling a release from S3.

Skill to build: Never hard-coding the IP; health endpoints for load balancers.

App / mobile developer

Backend for an app (or a test server) before moving to serverless.

Uses: One instance + Elastic IP, nginx reverse proxy, Let’s Encrypt or ALB + ACM.

A real task: Firebase-like API for a student app on a single t4g.small.

Skill to build: Knowing when Lambda/Amplify would be cheaper.

Data analyst

Occasionally runs Jupyter/RStudio or a BI server on EC2.

Uses: Larger-memory types (r-family) for pandas; stop when idle.

A real task: r7i.large with 16 GiB RAM to process a 6 GB CSV that crashes a laptop.

Skill to build: Stopping instances after work; using S3 rather than the root disk for data.

Data engineer

EC2 underneath EMR, self-managed Kafka/Airflow, and ETL servers.

Uses: i-family/instance store for shuffle, placement groups, Spot for batch.

A real task: EMR core nodes on r6g with Spot task nodes for nightly Spark jobs.

Skill to build: Choosing storage-optimised types; handling Spot interruptions.

ML / AI engineer

GPU instances for training and inference.

Uses: g5/g6 (inference), p4d/p5 (training), Deep Learning AMIs, capacity blocks, cluster placement.

A real task: Fine-tune a 7B model on g5.2xlarge for a few hours, save checkpoints to S3, terminate.

Skill to build: GPU quotas (vCPU limits) — request before the deadline; stop paying for idle GPUs.

DevOps / cloud engineer

Owns fleets: images, patching, scaling, cost.

Uses: Launch templates, Auto Scaling, Image Builder, SSM Patch Manager, Compute Optimizer.

A real task: Golden AMI rebuilt weekly, rolled out by instance refresh.

Skill to build: Immutable infrastructure; tagging; rightsizing.

Security engineer

Hardens and watches instances.

Uses: IMDSv2, no public SSH, Inspector vulnerability scans, GuardDuty runtime monitoring, EBS encryption default.

A real task: SCP that denies RunInstances unless IMDSv2 is required.

Skill to build: Prevent-by-default guardrails instead of per-instance fixes.

Small food-delivery start-up

Problem: The team put the auto public IP in DNS; a weekend stop/start changed it and the site vanished.

Engineering college hackathon

Ed-tech API

Problem: Server “randomly” slow at noon every day.

Launch checklist

  • ☐ Name tag + project/owner tags.
  • ☐ AMI resolved from SSM parameter (latest, correct architecture).
  • ☐ Smallest type that passes a load test.
  • ☐ Private subnet unless it must face the internet directly.
  • ☐ Security group: only needed ports; SSH from your /32 or none (Session Manager).
  • ☐ gp3, encrypted root; data off the root disk.
  • ☐ IAM role, IMDSv2 required, user data without secrets.
  • ☐ Termination protection for important servers; budget alert set.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. One t3.micro for about 15 minutes — covered by Free Tier/credits; a few paise otherwise.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Launch a self-configuring web server

    UI way — AWS Management Console

    1. EC2 → Launch instance → Name tiffingo-web → Amazon Linux 2023 → t3.micro → key pair: none (we will not log in) → Network settings → Create security group, allow HTTP from the internet → Advanced details → Metadata V2 only, paste the user data from the Deep dive → Launch instance.

    CLI way — the same thing with commands

    SG=$(aws ec2 create-security-group --group-name web-sg --description 'web: http from anywhere' --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr 0.0.0.0/0 >/dev/null
cat > web.sh <<'EOF'
#!/bin/bash
dnf install -y nginx
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
AZ=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone)
echo "<h1>Deployed by Riya (101)</h1><p>Served from $AZ</p>" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
EOF
ID=$(aws ec2 run-instances --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --instance-type t3.micro --security-group-ids $SG --user-data file://web.sh --metadata-options HttpTokens=required \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=tiffingo-web}]' --query 'Instances[0].InstanceId' --output text)
echo $ID; aws ec2 wait instance-running --instance-ids $ID

    You should see: an instance ID such as i-0abc…, and the command returns once the state is running.

    You never needed a key pair: the server configures itself through user data, and the security group only opens port 80.

  3. 2 · Check health and open the page

    UI way — AWS Management Console

    1. Instances list → select tiffingo-web → Status and alarms: checks passed → copy the public IPv4 → open http://IP (http, not https).
    2. Actions → Monitor and troubleshoot → Get system log to see the boot log.

    CLI way — the same thing with commands

    aws ec2 wait instance-status-ok --instance-ids $ID
IP=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text); echo $IP
curl -s http://$IP
aws ec2 describe-instance-status --instance-ids $ID --query 'InstanceStatuses[0].[InstanceStatus.Status,SystemStatus.Status]' --output text
aws ec2 get-console-output --instance-id $ID --latest --output text | tail -5

    You should see: the public IP, the HTML <h1>Deployed by Riya (101)</h1><p>Served from ap-south-1a</p>, ok ok for both checks, and the last lines of the boot log.

    If the page does not load: check the security group has port 80, the instance has a public IP, and you used http:// — 9 out of 10 first-day problems.

  4. 3 · Stop, start — watch the public IP change — then terminate

    UI way — AWS Management Console

    1. Instance state → Stop instance → wait → Start instance → compare the public IPv4 with before → open it again (nginx comes back by itself).
    2. Instance state → Terminate instance.

    CLI way — the same thing with commands

    OLD=$IP
aws ec2 stop-instances --instance-ids $ID >/dev/null; aws ec2 wait instance-stopped --instance-ids $ID
aws ec2 start-instances --instance-ids $ID >/dev/null; aws ec2 wait instance-running --instance-ids $ID
NEW=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)
echo "before: $OLD  after: $NEW"; sleep 30; curl -s http://$NEW | head -1
aws ec2 terminate-instances --instance-ids $ID --query 'TerminatingInstances[0].CurrentState.Name' --output text

    You should see: two different IP addresses — proof that the auto-assigned public IP is released on stop — and the page served again from the new IP (because nginx is enabled), then shutting-down.

    This is exactly why lab requirements ask for a “fixed address even after stop/start” → Elastic IP (Lesson 3.4).

Clean up and cost check

Step 3 terminated the instance. Then: aws ec2 wait instance-terminated --instance-ids $ID; aws ec2 delete-security-group --group-id $SG. Check nothing is left: aws ec2 describe-instances --filters Name=instance-state-name,Values=running --query 'Reservations[].Instances[].InstanceId' → empty.

Remember these
  • Stop keeps EBS and private IP; the public IP changes.
  • Terminate deletes the root volume by default.
  • Pay per second while running; storage and IPv4 always.
  • Never open SSH to 0.0.0.0/0.

Interview and viva questions

Is EC2 free?

Small types are covered by the Free plan / credits within limits; check your plan and set a budget.

Do I need a key pair?

Not for this lab — user data configures the server. Use Session Manager when you need a shell.

Why http and not https?

The lab nginx serves port 80 only; HTTPS comes with a load balancer and ACM certificate.

Real-world scenario questions (asked in company interviews)

Interview and viva questions.

Any companyFresher

“What is EC2 and how is it billed?”

Basics.

The interviewer is checking: Parts + billing.

Show a strong answer

“A virtual server launched from an AMI with a chosen instance type, EBS storage and security groups; Linux is billed per second while running with a 60-second minimum; storage and public IPv4 are billed separately.”

Avoid: “EC2 is a free server.”

Service companyJunior

“The website stopped working after the server was restarted. Why?”

Lifecycle.

The interviewer is checking: Two causes.

Show a strong answer
  • Public IP changed (use Elastic IP/ALB + DNS).
  • Service not enabled at boot (systemctl enable).
  • Check SG, status checks, console output.

Avoid: “AWS is down.”

Product companyMid-level

“How do you make instance launches repeatable and secure?”

Practice.

The interviewer is checking: Templates.

Show a strong answer
  • Launch templates/golden AMIs, IMDSv2 required, encrypted gp3, roles not keys, no public SSH, tags, budgets.

Avoid: Clicking the console by hand each time.
