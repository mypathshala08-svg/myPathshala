1 The story

2 Definition

Security groups, key pairs and Elastic IP

Formal definition (write this in exams)

A security group is a stateful, allow-only virtual firewall attached to network interfaces, with inbound and outbound rules whose sources may be CIDRs, prefix lists or other security groups; a key pair is a public/private key pair whose public key is installed on the instance for SSH authentication (alternatives: EC2 Instance Connect and Systems Manager Session Manager); an Elastic IP is a static public IPv4 address allocated to an account and associated with an instance or network interface.

In simple words

The security group decides who may connect on which port, the key pair (or Session Manager) decides how admins log in, and the Elastic IP gives the server an address that does not change.

Say it in an interview

30-second answer you can speak:

  • “I open only required ports: 80/443 from anywhere via a load balancer, app ports only from the load balancer’s security group, databases only from the app group, and no SSH — Session Manager instead.”
  • “Security groups are stateful and allow-only; NACLs are stateless with deny rules at the subnet. For a fixed address I prefer a DNS name on a load balancer; an Elastic IP is for single servers or allow-lists.”

3 The big picture

Rules that follow servers, an address that stays

New to computers? Start here. A security group is the society gate guard with a list: “anyone may enter the shop on the ground floor (port 80); only the owner, coming from her own house, may use the staff door (port 22).” A key pair is a lock and key: the lock (public key) is fixed on the staff door, the only key (private key, the .pem file) stays in your pocket. An Elastic IP is a permanent address on your visiting card that stays the same even if the shop shuts for the weekend.

Jargon buster:

  • Security group — firewall attached to the server’s network card
  • Port — a numbered door: 80 web, 443 secure web, 22 SSH
  • CIDR /32 — exactly one IP address
  • 0.0.0.0/0 — every IPv4 address on the internet
  • Key pair — public key on server + private key with you
  • Elastic IP — a public IPv4 address that stays yours

Type 1 · Inbound rules

Definition (say it in an interview): Each inbound rule allows one protocol and port range from one source — an IPv4/IPv6 CIDR, a prefix list, or another security group; there are only allow rules, evaluated together (no order), and anything not allowed is dropped. Changes apply immediately to all attached interfaces.

In plain words (no jargon): Rules that say which doors are open and for whom.

Analogy: The guest list at the gate: name of the door, and who may use it.

How it works internally, step by step

  1. Protocol. TCP/UDP/ICMP.
  2. Port. Number or range.
  3. Source. CIDR/SG/prefix list.
  4. Allow only. No deny.
  5. Immediate. No restart.

Words used above, in simple terms: CIDR = IP range notation like 10.0.0.0/16 · /32 = a single IPv4 address · prefix list = named list of CIDRs

Type 2 · Outbound rules and statefulness

Definition (say it in an interview): A new security group allows all outbound traffic; you can restrict it (e.g. only 443 to the internet). Security groups are stateful: once a connection is allowed in either direction, its return traffic is allowed automatically — unlike network ACLs (subnet level, stateless, have deny rules, Lesson 6.2).

In plain words (no jargon): Outgoing traffic rules, and why replies need no extra rule.

Analogy: The guard remembers who you let in, so their reply can go out without a new check.

How it works internally, step by step

  1. Default. All out.
  2. Restrict. Only needed.
  3. Stateful. Replies auto.
  4. NACL. Stateless, subnet.
  5. Tracking. Per connection.

Words used above, in simple terms: stateful = remembers connections · stateless = checks every packet both ways · NACL = network access control list

Type 3 · Security group references (chaining)

Definition (say it in an interview): A rule’s source can be another security group: traffic is allowed from any network interface that has that group attached, whatever its IP — so tiers (load balancer → web → database) stay protected as servers are added, replaced or scaled.

In plain words (no jargon): Rules that say “allow from servers in that group”.

Analogy: A staff badge: anyone wearing the “web team” badge may enter the server room, whoever they are.

How it works internally, step by step

  1. Source. sg-…
  2. Tiers. ALB → web → DB.
  3. Scaling. No rule changes.
  4. Self. Group to itself for clusters.
  5. Scope. Same VPC / peered.

Words used above, in simple terms: tier = layer of an application · self-reference = members of a group talk to each other · peering = connection between VPCs

Type 4 · Key pairs (SSH)

Definition (say it in an interview): A key pair has a public key (AWS stores it and cloud-init copies it into ~/.ssh/authorized_keys of the default user at first boot) and a private key (.pem, downloaded once, never stored by AWS); SSH proves possession of the private key by signing a challenge. Types: ED25519 (recommended for Linux) or RSA (required for Windows password decryption).

In plain words (no jargon): A pair of matching keys used to log in without a password.

Analogy: A padlock fixed to the door and the only key in your pocket.

How it works internally, step by step

  1. Create. Console/CLI.
  2. Download. Once.
  3. chmod 400. Protect.
  4. User. ec2-user / ubuntu.
  5. Lost. Replace, not recover.

Words used above, in simple terms: authorized_keys = file of allowed public keys · fingerprint = short ID of a key · ED25519 = modern, short, fast key type

Type 6 · Systems Manager Session Manager

Definition (say it in an interview): Session Manager gives an interactive shell (and port forwarding) through the SSM agent, which connects outward over HTTPS; the instance needs the agent (pre-installed on Amazon Linux/Windows AMIs), an instance role with AmazonSSMManagedInstanceCore, and outbound access (internet/NAT or VPC endpoints) — no inbound port, no key, IAM-controlled, every session logged to CloudTrail and optionally S3/CloudWatch.

In plain words (no jargon): A logged, keyless way to get a command prompt on a server.

Analogy: A security desk that calls you in after checking your company ID — the staff door does not even exist.

How it works internally, step by step

  1. Agent. On AMI.
  2. Role. SSMManagedInstanceCore.
  3. Network. 443 out / endpoints.
  4. IAM. Who may start.
  5. Logs. CloudTrail, S3.

Words used above, in simple terms: SSM = AWS Systems Manager · managed node = instance registered with SSM · port forwarding = tunnel a remote port to your laptop

Type 7 · Elastic IP addresses

Definition (say it in an interview): An Elastic IP is a static public IPv4 address allocated to your account in a Region; associated with an instance (or ENI) it replaces the auto-assigned public IP and stays the same across stop/start, and can be moved to another instance in seconds; it is billed hourly (≈ USD 0.005) whether in use or idle, with a default limit of 5 per Region.

In plain words (no jargon): A public internet address that stays yours and does not change.

Analogy: A permanent phone number you can move from one handset to another.

How it works internally, step by step

  1. Allocate. Account-level.
  2. Associate. Instance/ENI.
  3. Move. Fail over fast.
  4. Billing. Hourly.
  5. Release. Avoid idle cost.

Words used above, in simple terms: static = does not change · reverse DNS = name for an IP, for mail servers · BYOIP = bring your own IP range

8 Deep dive

Packet decision order, the exact R7/R8 rules, proof, Windows

How AWS decides to let a packet in

  1. The packet reaches the subnet: the network ACL is checked (stateless, numbered rules, allow/deny).
  2. It reaches the instance’s network interface: all security groups on that interface are combined; if any rule allows it, it passes.
  3. The OS firewall (firewalld/iptables) — usually off on Amazon Linux.
  4. The service must be listening on that port (nginx on 80, sshd on 22).

Debug in the same order: “timed out” = steps 1–2 (rule, route, IP); “connection refused” = step 4 (nothing listening).

The exact lab-exam rules (R7/R8)

MYIP=$(curl -s https://checkip.amazonaws.com)       # run on YOUR laptop, not CloudShell
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 22 --cidr $MYIP/32
aws ec2 describe-security-group-rules --filters Name=group-id,Values=$SG \
  --query 'SecurityGroupRules[?!IsEgress].[IpProtocol,FromPort,CidrIpv4]' --output table

Proving “only me” — the evidence

  • From your laptop: ssh -i tiffingo.pem ec2-user@EIP hostname → prints the hostname.
  • From CloudShell (a different IP): the same command → Connection timed out.
  • Rules table output showing 22 only from your /32.

Windows users

Windows 10/11 have OpenSSH built in (ssh in PowerShell). Protect the key: icacls tiffingo.pem /inheritance:r /grant:r "%USERNAME%:R". For Windows instances, use RDP (3389 from your /32) and decrypt the Administrator password with the RSA key.

9 Under the hood

Connection tracking, SSH handshake, EIP mapping

What happens below the console for SGs, SSH and EIPs.

1 · Connection tracking

Security groups are enforced on the Nitro card outside your instance. For each allowed flow, a tracked connection entry lets replies through. Rules open to everyone in both directions (0.0.0.0/0 all ports) may be untracked; changing a rule does not break already-tracked connections immediately — that is why removing a rule sometimes seems not to “kick out” a live SSH session.

2 · Silent drops

Denied packets are dropped without a reply, so clients see timeouts, not “refused”. Port scanners learn nothing. VPC Flow Logs (Module 6) record REJECT entries if you need evidence.

3 · The SSH handshake

  1. TCP to port 22 (SG must allow).
  2. Server proves its identity with its host key (the “fingerprint” prompt on first connect).
  3. Client offers the public key; server finds it in authorized_keys.
  4. Server sends a challenge; client signs it with the private key; server verifies with the public key. The private key never leaves your laptop.

4 · How a public IP or EIP really works

The instance only has a private IP. The VPC’s internet gateway keeps a one-to-one mapping public ↔ private. Associating an EIP changes that mapping (the old auto IP is released). Moving an EIP to another instance updates the mapping in seconds — useful for simple failover.

5 · Session Manager channel

The SSM agent polls the Systems Manager endpoints over HTTPS using the instance role, and opens a WebSocket channel (ssmmessages) when you start a session. Your CLI connects to the same service with your IAM identity; the service joins the two. No inbound connection to the instance ever exists.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. One t3.micro and one Elastic IP for about 30 minutes — a few rupees at most. Needs web-sg and web.sh from Lesson 3.1.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Firewall: web for everyone, SSH only for you

    UI way — AWS Management Console

    1. On your laptop open https://checkip.amazonaws.com and note your IP. EC2 → Security Groups → web-sg → Edit inbound rules → keep HTTP 80 Anywhere → Add rule SSH, source My IP → Save rules.

    CLI way — the same thing with commands

    SG=$(aws ec2 describe-security-groups --group-names web-sg --query 'SecurityGroups[0].GroupId' --output text)
MYIP=49.36.12.7          # ← paste YOUR laptop's IP (CloudShell's IP is different!)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 22 --cidr $MYIP/32
aws ec2 describe-security-group-rules --filters Name=group-id,Values=$SG --query 'SecurityGroupRules[?!IsEgress].[IpProtocol,FromPort,CidrIpv4]' --output table

    You should see: a table with tcp 80 0.0.0.0/0 and tcp 22 49.36.12.7/32 (your IP).

    If web-sg does not exist, create it as in Lesson 3.1.

  3. 2 · Key pair, launch, log in from your laptop

    UI way — AWS Management Console

    1. EC2 → Key pairs → Create key pair tiffingo-key, ED25519, .pem → it downloads once. Launch AL2023 t3.micro with this key, web-sg and the 3.1 user data. On your laptop: ssh -i tiffingo-key.pem ec2-user@PUBLIC-IP.

    CLI way — the same thing with commands

    aws ec2 create-key-pair --key-name tiffingo-key --key-type ed25519 --query KeyMaterial --output text > tiffingo-key.pem; chmod 400 tiffingo-key.pem
ID=$(aws ec2 run-instances --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --instance-type t3.micro \
  --key-name tiffingo-key --security-group-ids $SG --user-data file://web.sh --metadata-options HttpTokens=required --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-status-ok --instance-ids $ID
# copy tiffingo-key.pem to your laptop (CloudShell: Actions → Download file), then ON THE LAPTOP:
#   ssh -i tiffingo-key.pem ec2-user@<public-ip> hostname
# and from CloudShell (different IP) — expect a timeout:
ssh -o ConnectTimeout=8 -i tiffingo-key.pem ec2-user@$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text) hostname

    You should see: from the laptop: a hostname like ip-172-31-5-20.ap-south-1.compute.internal; from CloudShell: ssh: connect to host … port 22: Connection timed out — proof that only your IP may log in.

    Keep the .pem out of Git and chat. Delete it after the lab.

  4. 3 · Elastic IP: same address after stop/start

    UI way — AWS Management Console

    1. EC2 → Elastic IPs → Allocate Elastic IP address → Actions → Associate with tiffingo-web → stop and start the instance → the Public IPv4 is still the EIP → open http://EIP.
    2. Clean up: Disassociate → Release Elastic IP address.

    CLI way — the same thing with commands

    ALLOC=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text)
aws ec2 associate-address --allocation-id $ALLOC --instance-id $ID >/dev/null
EIP=$(aws ec2 describe-addresses --allocation-ids $ALLOC --query 'Addresses[0].PublicIp' --output text); echo $EIP; curl -s http://$EIP | head -1
aws ec2 stop-instances --instance-ids $ID >/dev/null; aws ec2 wait instance-stopped --instance-ids $ID
aws ec2 start-instances --instance-ids $ID >/dev/null; aws ec2 wait instance-running --instance-ids $ID; sleep 30
aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text; curl -s http://$EIP | head -1

    You should see: the same EIP printed before and after, and the page served both times — the requirement proven.

    Release the EIP at the end: an idle Elastic IP keeps costing about USD 3.6 a month.

Clean up and cost check

aws ec2 disassociate-address --association-id $(aws ec2 describe-addresses --allocation-ids $ALLOC --query 'Addresses[0].AssociationId' --output text); aws ec2 release-address --allocation-id $ALLOC; aws ec2 terminate-instances --instance-ids $ID; aws ec2 delete-key-pair --key-name tiffingo-key; rm -f tiffingo-key.pem — and revoke the SSH rule.

ALLOC=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text); aws ec2 associate-address --allocation-id $ALLOC --instance-id $ID >/dev/null
EIP=$(aws ec2 describe-addresses --allocation-ids $ALLOC --query 'Addresses[0].PublicIp' --output text); echo $EIP

Quick overview — what we did in this lesson

  1. 1
    Followed four visitors to one server

    Customer allowed on 80, bot dropped on 22, admin allowed from /32 with a key, replies allowed (stateful).

  2. 2
    Wrote inbound rules

    Protocol + port + source; allow-only; anything else dropped silently.

    aws ec2 authorize-security-group-ingress --port 22 --cidr $MYIP/32
  3. 3
    Chained tiers

    Rules whose source is another security group follow servers as they change.

    --source-group sg-web
  4. 4
    Used keys safely

    Public key on the server, private .pem with you, chmod 400.

    aws ec2 create-key-pair --key-type ed25519
  5. 5
    Compared login options

    Key pair vs Instance Connect (60-s keys) vs Session Manager (no port).

    aws ssm start-session --target $ID
  6. 6
    Fixed the address

    Elastic IP survived stop/start; release it when done.

    aws ec2 allocate-address · associate-address
  7. 7
    Proved the exam rules

    Laptop SSH works, CloudShell times out.

Remember these
  • Never 0.0.0.0/0 on 22, 3389 or databases.
  • Timeout = network/firewall; refused = service.
  • Session Manager beats SSH.
  • Idle Elastic IPs cost money.

19 Quiz and revision

Check yourself

Quick revision

Lesson 3.4 in one screen

  • Open 80 to all, 22 only to your /32 — or not at all.
  • Chain tiers with SG references.
  • Private key with you; prefer Session Manager.
  • Elastic IP for a fixed address; release when done.

Interview and viva questions

My home IP keeps changing — what now?

Update the /32 rule each time, or use Session Manager / Instance Connect so no IP rule is needed.

Is an Elastic IP free?

No — about USD 0.005 per hour, attached or idle.

Can a security group deny one IP?

No — SGs only allow. Use a network ACL or AWS WAF to deny.

Real-world scenario questions (asked in company interviews)

Interview and viva questions.

Any companyFresher

“What is a security group?”

Basics.

The interviewer is checking: Stateful allow.

Show a strong answer

“A stateful virtual firewall on an instance’s network interface with allow rules for protocol, port and source; everything else inbound is denied and replies are automatic.”

Avoid: “It is the same as a NACL.”

Service companyJunior

“Users can view the site but you cannot SSH. Why?”

Debug.

The interviewer is checking: Layered.

Show a strong answer
  • 22 not allowed from your current IP (or CloudShell IP), wrong user/key, key permissions; timeout vs refused tells which layer.

Avoid: “Restart the server.”

Product companyMid-level

“Design admin access for 200 servers.”

Practice.

The interviewer is checking: No SSH.

Show a strong answer
  • Session Manager with IAM, private subnets with endpoints, session logs to S3, SG chaining, Config rule against open admin ports.

Avoid: Bastion with shared keys.
