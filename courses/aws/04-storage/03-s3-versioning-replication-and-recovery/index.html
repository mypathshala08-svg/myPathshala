1 The story

2 Definition

S3 versioning, replication and recovery

Formal definition (write this in exams)

S3 Versioning keeps multiple variants of an object in a bucket, giving each write a version ID and turning simple deletes into delete markers, so overwritten or deleted objects can be recovered; permanent deletion requires a version ID and can be restricted by policies, MFA Delete or Object Lock (WORM retention). S3 Replication asynchronously copies objects between versioned buckets in the same or different Regions/accounts using an IAM role.

In simple words

Versioning is an undo button for your bucket; replication keeps a copy somewhere else; Object Lock makes copies impossible to delete for a while.

Say it in an interview

30-second answer you can speak:

  • “I enable versioning on every important bucket, recover overwrites by copying the old version and deletes by removing the delete marker, and add noncurrent-version lifecycle to control cost.”
  • “For resilience I replicate cross-Region and cross-account with delete-marker replication off, and use Object Lock or deny policies to stop version deletion — that also defeats ransomware.”

3 The big picture

Delete with and without versioning; choosing replication

New to computers? Start here. Versioning is like the “version history” in Google Docs: every save is kept, and you can bring back any older one. A delete is like moving a file to the recycle bin — it is hidden, not destroyed. Replication is like keeping a photocopy of the register in another city.

Jargon buster:

  • Version — one saved copy of an object, with its own ID
  • Current version — the one you get by default
  • Noncurrent version — an older copy kept underneath
  • Delete marker — a placeholder that hides the object
  • Replication — automatic copying to another bucket
  • Object Lock — a rule that blocks deletes for a set time

Type 1 · Versioning states

Definition (say it in an interview): A bucket is Unversioned (default), Enabled, or Suspended; once enabled it can never return to unversioned. With versioning enabled, every PUT, POST or COPY of a key creates a new version with a unique version ID; objects that existed before have version ID null. Suspending stops new versions but keeps existing ones.

In plain words (no jargon): Whether S3 keeps old copies of files.

Analogy: Turning on “keep all edits” in a notebook app — you can pause it, but old pages stay.

How it works internally, step by step

  1. Default. Off.
  2. Enable. One call.
  3. Version ID. Per write.
  4. Suspend. Pause.
  5. No going back. Never unversioned.

Words used above, in simple terms: version ID = unique ID of one version · null version = version created while versioning was off/suspended · noncurrent = not the latest version

Type 2 · Recovering an overwritten object

Definition (say it in an interview): To undo an overwrite, list the versions (list-object-versions), pick the good version ID, and copy that version onto the same key (copy-object --copy-source bucket/key?versionId=…); it becomes the newest version and history is preserved. (Alternatively delete the bad version by ID so the previous one becomes current.)

In plain words (no jargon): How to get back the correct file after it was replaced.

Analogy: Reopening yesterday’s saved draft and saving it again as today’s version.

How it works internally, step by step

  1. List. Versions + times.
  2. Pick. Good ID.
  3. Copy. Onto same key.
  4. Check. head-object.
  5. Evidence. Keep history.

Words used above, in simple terms: copy-source = bucket/key?versionId=… to copy from · IsLatest = marks the current version · LastModified = when that version was written

Type 3 · Delete markers and undelete

Definition (say it in an interview): In a versioned bucket a DELETE without a version ID inserts a delete marker (a zero-byte placeholder with its own version ID) as the latest version; GET returns 404 and listings hide the key, but every version remains. Deleting the delete marker by its version ID “undeletes” the object.

In plain words (no jargon): How a “deleted” file is really kept and how to bring it back.

Analogy: Moving a file to the recycle bin; restoring it puts it back.

How it works internally, step by step

  1. Simple delete. Marker.
  2. GET. 404.
  3. List versions. Shows marker.
  4. Undelete. Delete marker.
  5. Expired markers. Lifecycle cleanup.

Words used above, in simple terms: delete marker = placeholder that hides an object · expired object delete marker = marker with no versions under it · 404 = not found response

Type 4 · Permanent deletes, MFA Delete and deny policies

Definition (say it in an interview): A DELETE with a version ID permanently removes that version. Protect history by denying s3:DeleteObjectVersion (and PutBucketVersioning, PutLifecycleConfiguration) in the bucket policy for everyone except a break-glass role, or enable MFA Delete (root user with MFA, via API/CLI only) so deleting versions or suspending versioning needs a code.

In plain words (no jargon): How to stop anyone from permanently destroying old versions.

Analogy: Shredding a page from the version history needs the principal’s key and a one-time code.

How it works internally, step by step

  1. Version delete. Permanent.
  2. MFA Delete. Root + code.
  3. Deny. Bucket policy.
  4. Break-glass. Exception role.
  5. Audit. CloudTrail.

Words used above, in simple terms: MFA Delete = MFA required to delete versions · break-glass role = emergency admin role · WORM = write once, read many

Type 5 · Object Lock (WORM)

Definition (say it in an interview): S3 Object Lock stores versions in write-once-read-many mode: governance mode blocks deletes/overwrites except for users with s3:BypassGovernanceRetention; compliance mode blocks everyone, including root, until the retain-until date; legal holds block deletion indefinitely. It requires versioning and is assessed for SEC 17a-4 style retention.

In plain words (no jargon): A setting that makes files impossible to delete for a set time.

Analogy: A sealed ballot box: once a vote goes in, nobody can take it out until counting day.

How it works internally, step by step

  1. Versioning. Required.
  2. Governance. Bypassable with permission.
  3. Compliance. Nobody.
  4. Legal hold. Until removed.
  5. Default retention. Bucket setting.

Words used above, in simple terms: retain-until date = when deletion becomes possible · governance mode = protects against most users · compliance mode = protects against everyone

Type 6 · Replication: SRR, CRR, RTC, Batch

Definition (say it in an interview): S3 Replication copies new objects (and optionally delete markers) asynchronously from a source to one or more destination buckets — same-Region or cross-Region, same or different account — using an IAM role, filtered by prefix/tag, optionally changing storage class or ownership; RTC adds a 15-minute SLA; Batch Replication copies existing objects. Versioning is required on both sides.

In plain words (no jargon): Automatically copying new files to another bucket.

Analogy: An automatic photocopier that sends every new page to the branch office.

Type 7 · Lifecycle for noncurrent versions

Definition (say it in an interview): Old versions are stored and billed like any object, so pair versioning with lifecycle rules: transition noncurrent versions to cheaper classes, expire them after N days (NoncurrentVersionExpiration, optionally keeping the newest N), and clean up expired delete markers and incomplete multipart uploads (Lesson 4.4 covers lifecycle fully).

In plain words (no jargon): Automatic clean-up of old versions so storage does not grow forever.

Analogy: Keeping the last three drafts of each document and shredding older drafts after a month.

How it works internally, step by step

  1. Noncurrent days. After N days.
  2. Newer versions. Keep N.
  3. Transition. Cheaper class.
  4. Delete markers. Clean up.
  5. Multipart. Abort.

Words used above, in simple terms: NoncurrentVersionExpiration = lifecycle action for old versions · NewerNoncurrentVersions = how many to keep · ExpiredObjectDeleteMarker = remove lonely markers

Versions, markers, replicas 6 steps
Watch what happens
  1. Step 1 · Versioning on — each upload of the same key keeps its own version ID. Nothing is ever silently replaced.
  2. Step 2 · Accidental overwrite — the wrong file becomes current; the correct v1 is still there as a noncurrent version.
  3. Step 3 · Restore by copy — copy the old version ID onto the same key — the good content becomes the newest version (v3). History is kept.
  4. Step 4 · Accidental delete — a simple delete only adds a delete marker on top. GET returns 404, but all versions are still stored.
  5. Step 5 · Undelete — delete the delete marker (by its version ID) and the previous version is current again.
  6. Step 6 · A copy in another Region — cross-Region replication (CRR) copies new versions to a versioned bucket in Hyderabad — protection against a Regional problem or bad actors.

Level 3 · Advanced designs for others

9 Under the hood

Version IDs, null versions, replication internals

How S3 keeps versions and copies.

1 · Version IDs

Version IDs are opaque strings (up to 1,024 bytes) generated by S3 — not timestamps or counters. Objects stored while versioning was off have version ID null; with versioning suspended, a new PUT replaces the null version.

2 · What “latest” means

The latest version is the most recently written — which can be a delete marker. LIST without versions skips keys whose latest is a marker; GET without a version ID returns 404 (with header x-amz-delete-marker: true).

3 · How replication works

When an object is written, S3 queues a replication task. The replication role reads the version (and tags/ACL) and writes a replica with the same version ID in the destination; status moves PENDING → COMPLETED or FAILED. Replicas are not replicated again (no loops) unless you configure bi-directional replication with replica modification sync.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. Tiny objects in two buckets — practically free (a small cross-Region transfer charge per GB).

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Enable versioning, overwrite, restore

    UI way — AWS Management Console

    1. Create bucket results-ACCOUNTID → Properties → Bucket Versioning → Enable → upload results.pdf (correct) → upload a different file with the same name → Show versions: two versions → select the older one → Actions → Copy to the same key.

    CLI way — the same thing with commands

    ACCT=$(aws sts get-caller-identity --query Account --output text); B=results-$ACCT
aws s3 mb s3://$B; aws s3api put-bucket-versioning --bucket $B --versioning-configuration Status=Enabled
echo 'roll 101: 86 (correct)' > good.pdf; echo 'OLD SHEET 2025 (wrong)' > bad.pdf
aws s3 cp good.pdf s3://$B/results.pdf; aws s3 cp bad.pdf s3://$B/results.pdf
aws s3api list-object-versions --bucket $B --prefix results.pdf --query 'Versions[].[VersionId,IsLatest,Size]' --output table
GOOD=$(aws s3api list-object-versions --bucket $B --prefix results.pdf --query 'Versions[?IsLatest==`false`]|[0].VersionId' --output text)
aws s3api copy-object --bucket $B --key results.pdf --copy-source "$B/results.pdf?versionId=$GOOD" --query VersionId --output text
aws s3 cp s3://$B/results.pdf -

    You should see: a table with two versions, a new version ID from copy-object, and roll 101: 86 (correct) — the overwrite is undone and three versions now exist.

    Nothing was deleted: the wrong upload is still there as evidence.

  3. 2 · Delete, see the marker, undelete

    UI way — AWS Management Console

    1. Select results.pdf (versions hidden) → Delete → type “delete” → Show versions: a Delete marker is on top → select the delete marker → Delete → permanently delete → the file is back.

    CLI way — the same thing with commands

    aws s3 rm s3://$B/results.pdf
aws s3 cp s3://$B/results.pdf - 2>&1 | tail -1
MARK=$(aws s3api list-object-versions --bucket $B --prefix results.pdf --query 'DeleteMarkers[?IsLatest].VersionId' --output text); echo marker=$MARK
aws s3api delete-object --bucket $B --key results.pdf --version-id $MARK --query DeleteMarker
aws s3 cp s3://$B/results.pdf -

    You should see: delete: s3://…/results.pdf, then a 404 (Not Found), the marker’s version ID, true (a delete marker was removed) and finally the correct content again.

    Deleting the marker by version ID is the “undelete”. Deleting a real version by ID would be permanent.

  4. 3 · Cross-Region replication to Hyderabad

    UI way — AWS Management Console

    1. Create bucket results-dr-ACCOUNTID in Asia Pacific (Hyderabad), enable versioning → source bucket → Management → Create replication rule → all objects → destination the DR bucket → Create new role → Save → upload a new file → open it in the DR bucket.

    CLI way — the same thing with commands

    D=results-dr-$ACCT; aws s3 mb s3://$D --region ap-south-2; aws s3api put-bucket-versioning --bucket $D --versioning-configuration Status=Enabled --region ap-south-2
aws iam create-role --role-name S3ReplicationRole --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"s3.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null
# save the Deep-dive permissions as repl.json with your bucket names, then:
aws iam put-role-policy --role-name S3ReplicationRole --policy-name repl --policy-document file://repl.json; sleep 10
aws s3api put-bucket-replication --bucket $B --replication-configuration "{\"Role\":\"arn:aws:iam::$ACCT:role/S3ReplicationRole\",\"Rules\":[{\"ID\":\"to-hyd\",\"Status\":\"Enabled\",\"Priority\":1,\"Filter\":{},\"DeleteMarkerReplication\":{\"Status\":\"Disabled\"},\"Destination\":{\"Bucket\":\"arn:aws:s3:::$D\"}}]}"
echo 'roll 102: 91' > r2.pdf; aws s3 cp r2.pdf s3://$B/results-102.pdf; sleep 30
aws s3api head-object --bucket $B --key results-102.pdf --query ReplicationStatus; aws s3 cp s3://$D/results-102.pdf - --region ap-south-2

    You should see: "COMPLETED" on the source object and roll 102: 91 read from the Hyderabad bucket. results.pdf (uploaded before the rule) is NOT in the DR bucket — Batch Replication would copy it.

    Delete-marker replication is disabled on purpose: a delete in Mumbai does not hide the copy in Hyderabad.

Clean up and cost check

Versioned buckets need all versions deleted: aws s3api delete-bucket-replication --bucket $B; for b in $B $D; do aws s3api list-object-versions --bucket $b --query '{Objects: [Versions,DeleteMarkers][][].{Key:Key,VersionId:VersionId}}' --output json > v.json; aws s3api delete-objects --bucket $b --delete file://v.json >/dev/null; aws s3 rb s3://$b; done; aws iam delete-role-policy --role-name S3ReplicationRole --policy-name repl; aws iam delete-role --role-name S3ReplicationRole (the console’s Empty button does the same).

3 The restore script

Save as restore-key.sh. JMESPath compares ISO timestamps as strings, which works because they share one format.

#!/bin/bash
# restore-key.sh BUCKET KEY "YYYY-MM-DDTHH:MM"  → restores the newest version written before that time
B=$1; K=$2; T=$3
V=$(aws s3api list-object-versions --bucket "$B" --prefix "$K" \
  --query "Versions[?Key=='$K' && LastModified<'$T'] | sort_by(@,&LastModified)[-1].VersionId" --output text)
[ "$V" = "None" ] && { echo "no version before $T"; exit 1; }
aws s3api copy-object --bucket "$B" --key "$K" --copy-source "$B/$K?versionId=$V" --query VersionId --output text >/dev/null
echo "restored $K to version $V (written before $T)"

4 Restore the whole prefix

chmod +x restore-key.sh
for k in $(aws s3api list-objects-v2 --bucket $B --prefix notes/sem5/ --query 'Contents[].Key' --output text); do ./restore-key.sh $B $k $T; done
aws s3 cp s3://$B/notes/sem5/u2.txt -

4 Attack drill: try to destroy

As your admin (not BreakGlass): delete the version, bypass governance, suspend versioning.

V=$(aws s3api list-object-versions --bucket $S --prefix 2026/r.txt --query 'Versions[0].VersionId' --output text)
