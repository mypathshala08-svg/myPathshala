1 The story

Two years of notes, one dead disk

Before you start: Modules 1–2; Lesson 3.6 helps but is not required.

🤔 Mehta Sir’s college kept all lecture notes on one lab PC. The day its disk died, two years of PDFs vanished — the week before exams.

Amazon S3 (Simple Storage Service) stores files as objects in buckets, keeps each one in at least three Availability Zones, and lets you reach them from anywhere over HTTPS — with 99.999999999% durability and no disk to manage. This lesson explains buckets, keys and prefixes (why S3 has no real folders), what happens on an upload, consistency, sizes and limits, sharing with presigned URLs, and the tools for moving data — then you build a notes store on your own account or in the simulator.

2 Definition

Amazon S3

Formal definition (write this in exams)

Amazon Simple Storage Service (S3) is a regional object storage service that stores data as objects (data, metadata and a key) in buckets with globally unique names, designed for 99.999999999% durability by storing data redundantly across multiple Availability Zones, with strong read-after-write consistency, access through HTTPS APIs controlled by IAM and bucket policies, and pay-as-you-go pricing for storage, requests and data transfer.

In simple words

S3 is AWS’s safe, unlimited file store: you put files (objects) into buckets, each kept in several data centres, and decide exactly who can read them.

Say it in an interview

30-second answer you can speak:

  • “S3 is regional object storage: buckets with global names, objects up to 5 TB addressed by keys, 11 nines durability across three AZs, strong consistency, private by default with IAM/bucket policies and Block Public Access.”
  • “I design prefixes around access and lifecycle, share with presigned URLs, move data with sync/multipart, and serve websites through CloudFront rather than public buckets.”

3 The big picture

Buckets, keys, and where files belong

New to computers? Start here. S3 is like a huge, safe locker room: a bucket is your locker (its name must be unique in the whole world), each object is a packet inside with a label (the key). The locker company keeps copies in three different buildings, so a fire in one does not lose your packet. Only people you give a key to can open it — or you can give a guest a pass that expires in an hour.

Jargon buster:

  • Bucket — a named container for files (globally unique name)
  • Object — one file plus its information (metadata)
  • Key — the object’s full name, like sem1/notes.pdf
  • Prefix — the part of a key that looks like a folder
  • Durability — how unlikely it is to lose data
  • Presigned URL — a temporary link to one object

Type 1 · Buckets

Definition (say it in an interview): A bucket is a container for objects with a globally unique name (3–63 lowercase letters, numbers, dots, hyphens) created in one Region; data never leaves that Region unless you copy or replicate it. New buckets have Block Public Access on, ACLs disabled (bucket owner enforced) and SSE-S3 default encryption.

In plain words (no jargon): A named storage container in one AWS Region.

Analogy: Your named locker in a locker company — the name is unique across all branches worldwide.

How it works internally, step by step

  1. Name. Global.
  2. Region. Fixed.
  3. BPA. On.
  4. ACLs. Disabled.
  5. Encryption. SSE-S3.

Words used above, in simple terms: Block Public Access = switch preventing public access · bucket owner enforced = ACLs off; policies decide · data residency = data stays in a country

Type 2 · Objects and keys

Definition (say it in an interview): An object = data (0 bytes to 5 TB) + metadata (Content-Type, size, last modified, storage class, your own x-amz-meta-* headers) + optional tags, identified by its key (up to 1,024 bytes) within the bucket; objects are replaced as a whole — there is no editing in place.

In plain words (no jargon): A file in S3 plus information about it.

Analogy: A sealed packet with a label and a tag listing its contents.

How it works internally, step by step

  1. Key. Full name.
  2. Size. ≤ 5 TB.
  3. Metadata. Headers.
  4. Tags. Up to 10.
  5. Replace. Whole object.

Words used above, in simple terms: ETag = hash-like identifier of the content · Content-Type = what kind of file it is · object tag = key=value label for rules

Type 3 · Prefixes (“folders”)

Definition (say it in an interview): S3’s namespace is flat: “folders” are just key prefixes grouped by the “/” delimiter in listings and the console. Prefixes matter a lot: permissions (arn:…:bucket/sem1/*), lifecycle rules, replication filters, event triggers and performance (each prefix supports at least 3,500 writes and 5,500 reads per second) all work by prefix.

In plain words (no jargon): Folder-like names at the start of keys.

Analogy: Labels on packets that start with “Sem1-”: the locker has no shelves, you just sort by label.

How it works internally, step by step

  1. Flat. No directories.
  2. Delimiter. / grouping.
  3. Policies. By prefix.
  4. Lifecycle. By prefix.
  5. Performance. Per prefix.

Words used above, in simple terms: delimiter = character that groups keys · CommonPrefixes = the “folders” in a list response · rename = copy + delete in S3

Type 4 · Durability, availability and consistency

Definition (say it in an interview): S3 Standard is designed for 99.999999999% durability (store 10 million objects, expect to lose one every 10,000 years) and 99.99% availability by storing data across at least three AZs and continuously checking and repairing it; since December 2020 all requests are strongly consistent — a successful PUT is immediately visible to GET and LIST.

In plain words (no jargon): How safe your files are, and how quickly changes show.

Analogy: Three photocopies in three buildings, checked every night and re-copied if one fades.

How it works internally, step by step

  1. Durability. 11 nines.
  2. Availability. 99.99%.
  3. AZs. ≥ 3.
  4. Consistency. Strong.
  5. Human error. Versioning.

Words used above, in simple terms: durability = probability data is not lost · availability = probability it can be accessed · strong consistency = reads see the latest write

Type 5 · Access basics and presigned URLs

Definition (say it in an interview): Only the bucket owner’s account can access objects until a policy says otherwise: IAM policies (what a user/role may do), bucket policies (who may use this bucket — Lesson 4.2), with Block Public Access overriding any public grant. A presigned URL embeds a temporary signature so anyone holding it can GET (or PUT) one object until it expires — up to 7 days with IAM user credentials, shorter with role credentials.

In plain words (no jargon): Who can see your files, and how to share one temporarily.

Analogy: A guest pass to one locker, valid until 5 pm.

How it works internally, step by step

  1. Default. Private.
  2. IAM. Identity side.
  3. Bucket policy. Resource side.
  4. BPA. Override.
  5. Presign. Temporary.

Words used above, in simple terms: presigned URL = link with a built-in temporary signature · SigV4 = AWS request-signing method · expiry = how long a link works

Type 6 · Moving data: cp, sync, multipart and more

Definition (say it in an interview): The CLI’s aws s3 cp copies files (add --recursive for folders), aws s3 sync copies only new/changed files (and with --delete removes extras) — the “one-command refresh”; uploads above a threshold use multipart upload automatically (parallel parts, retry per part). For bulk/far transfers: S3 Transfer Acceleration, DataSync, Snowball, and the console for small uploads.

In plain words (no jargon): Commands that copy files to and from S3.

Analogy: Moving house: carry one box (cp), move only new things (sync), or send a truck in many trips (multipart).

How it works internally, step by step

  1. cp. Copy.
  2. sync. Changes only.
  3. --delete. Mirror.
  4. --dryrun. Preview.
  5. multipart. Automatic.

Words used above, in simple terms: multipart upload = big file in parallel parts · Transfer Acceleration = faster uploads via edge locations · DataSync = managed bulk transfer

Type 7 · Static website hosting

Definition (say it in an interview): A bucket can serve a static website (HTML, CSS, JS, images — no server code) from a website endpoint like http://bucket.s3-website.ap-south-1.amazonaws.com with index and error documents; the endpoint is HTTP-only and requires public read, so production sites use CloudFront with Origin Access Control in front of a private bucket (Lesson 6.5), adding HTTPS and caching.

In plain words (no jargon): Serving a simple website directly from S3.

Analogy: Pinning your poster on a public notice board vs. giving it to a courier network that delivers copies everywhere.

How it works internally, step by step

  3. Error. error.html.
  4. Public. Needed for endpoint.
  5. CloudFront. HTTPS + private.

Words used above, in simple terms: static site = only files, no server code · SPA = single-page app · OAC = Origin Access Control for CloudFront → S3

Animated

What happens when you upload a file to S3

One command: the request is checked, the object is stored in three AZs, and it is readable by anyone you allow — for as long as you allow.

Upload to download 6 steps
Watch what happens
  1. Step 1 · A signed PUT request — the CLI turns cp into an HTTPS PUT to the Mumbai S3 endpoint, signed with your credentials (SigV4).
  2. Step 2 · S3 checks — IAM and bucket policies must allow s3:PutObject; Block Public Access and encryption defaults apply (SSE-S3 on every new object).
  3. Step 3 · Stored in three AZs — S3 Standard writes the object redundantly across at least three Availability Zones before saying “success”.
  4. Step 4 · 200 OK + ETag — you get an ETag (fingerprint). The object is immediately visible to reads and lists — strong read-after-write consistency.
  5. Step 5 · Read by key — anyone with permission downloads it by bucket + key. There are no real folders — sem1/ is just part of the key (a prefix).
  6. Step 6 · Share for a limited time — a presigned URL carries a temporary signature: the guest can GET this one object until it expires, then gets 403.

Level 2 · Intermediate can do it alone

Understand: Use sync with --dryrun, head-object metadata, presigned URLs, and plan prefixes for permissions and lifecycle.

Try: Do the full hands-on; then share a file for 10 minutes and prove it stops working.

Level 3 · Advanced designs for others

Level 4 · Expert architect / interviewer

Understand: Run a data platform: data lake zones (raw/curated), S3 Inventory and Storage Lens, Access Points, Object Lambda, Express One Zone for ML/analytics hot data, cost allocation by tags.

Try: Turn on S3 Storage Lens and an Inventory report for the bucket; query the inventory with Athena (Module 8).

Check yourself: When choose S3 Express One Zone?

Latency-critical, very high request-rate workloads (ML training, analytics) in one AZ, accepting single-AZ durability for re-creatable data.

9 Under the hood

Partitions, request rates, checksums, endpoints

What S3 does behind each request.

1 · Partitions and request rates

S3 automatically splits busy key ranges into partitions. Each prefix supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second, and scaling continues as load grows; a sudden jump can briefly return 503 SlowDown — SDKs retry with backoff.

2 · Integrity checks

Uploads can carry checksums (CRC32, CRC64NVME, SHA-1, SHA-256); S3 verifies and stores them, and newer SDKs add CRC checksums by default. Background processes re-verify stored data and repair from redundant copies.

3 · Endpoints

EndpointExample
Virtual-hosted (default)https://bucket.s3.ap-south-1.amazonaws.com/key

Dual-stack (IPv6)https://bucket.s3.dualstack.ap-south-1.amazonaws.com/key
VPC gateway endpointprivate route from your VPC, no NAT (Module 6)

4 · Multipart upload

Large files are split into parts (5 MB–5 GB each, up to 10,000 parts), uploaded in parallel and assembled by CompleteMultipartUpload. Failed uploads leave invisible parts that are billed — add a lifecycle rule to abort incomplete uploads after 7 days.

5 · Requests are API calls

Every console click is an API call (ListBuckets, ListObjectsV2, PutObject…) recorded by CloudTrail management events; object-level reads/writes are data events (enable them for audit — Lesson 2.5).

2 Function code

The URL is signed with the function role, so it can only do what the role can (PutObject in submissions/).

import json, os, uuid, boto3
s3 = boto3.client("s3", region_name="ap-south-1")
B = os.environ["BUCKET"]

def lambda_handler(event, context):
    roll = (event.get("queryStringParameters") or {}).get("roll", "unknown")
    key = f"submissions/{roll}/{uuid.uuid4().hex[:8]}.pdf"
    url = s3.generate_presigned_url("put_object", Params={"Bucket": B, "Key": key, "ContentType": "application/pdf"}, ExpiresIn=600)
    return {"statusCode": 200, "headers": {"Content-Type": "application/json"}, "body": json.dumps({"upload_url": url, "key": key})}

  • Bucket → object → key; prefixes, not folders.
  • 11 nines across ≥ 3 AZs; strong consistency.
  • Private by default; presigned URLs.
  • sync for “only changes”; dry-run first.

Interview and viva questions

Is S3 the same as Google Drive?

Similar idea, but built for apps and APIs; Drive is a user app.

How much does a small notes bucket cost?

A few rupees for storage; downloads (data out) usually cost more.

Can I edit a file inside S3?

No — upload a new version of the whole object.

Real-world scenario questions (asked in company interviews)

Interview and viva questions.

Any companyFresher

“What is S3?”

Basics.

The interviewer is checking: Objects.

Show a strong answer

“Regional object storage: objects in buckets addressed by keys, 11 nines durability, strong consistency, private by default.”

Avoid: “A database.”

Service companyJunior

“Share a private file with a client for a day?”

Practice.

The interviewer is checking: Presign.

Show a strong answer
  • Presigned URL generated server-side with short expiry; never make the bucket public.

Avoid: “Make it public.”

Product companyMid-level

“Users upload 2 GB videos — design?”

Design.

The interviewer is checking: Direct upload.

Show a strong answer
  • Presigned multipart upload from the browser to S3, events to processing, CloudFront for playback, lifecycle for old files.

Avoid: Proxying files through the API server.
