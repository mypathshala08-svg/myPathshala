2 Definition

AWS Backup and disaster recovery

Formal definition (write this in exams)

AWS Backup is a centralised, policy-based service that backs up supported AWS resources according to backup plans (schedules, windows, retention, copy actions) applied through tag- or ARN-based selections, storing encrypted recovery points in vaults protected by access policies and Vault Lock, with cross-Region/cross-account copies and restore testing. Disaster recovery strategies — backup & restore, pilot light, warm standby, multi-site active/active — are chosen to meet recovery point (RPO) and recovery time (RTO) objectives.

In simple words

AWS Backup makes scheduled, locked backups of your resources and copies them to another Region or account; disaster recovery is choosing how much data and time you can afford to lose, and preparing accordingly.

Say it in an interview

30-second answer you can speak:

  • “I run AWS Backup plans by tag with daily/weekly/monthly rules, copies to a DR Region and a separate backup account, Vault Lock in compliance mode for critical data, and restore testing to measure RTO.”
  • “DR strategy follows RPO/RTO: backup & restore for internal apps, pilot light or warm standby for customer-facing ones, active-active for payments — with IaC and Route 53 failover.”

3 The big picture

RPO, RTO and DR strategies

New to computers? Start here. Backups are like photocopies of important documents. AWS Backup is the clerk who makes copies every night, keeps them in a locked cupboard (vault), sends one copy to another city (Region), and once a month checks the copies can actually be read. Disaster recovery is the plan for continuing work if your office is closed.

Jargon buster:

  • Backup plan — when to back up and how long to keep
  • Recovery point — one backup you can restore
  • Backup vault — locked container for recovery points
  • Vault Lock — rule that stops deletion
  • RPO — how much data you can afford to lose
  • RTO — how long you can afford to be down

Type 1 · Backup plans and rules

Definition (say it in an interview): A backup plan holds one or more rules: schedule (cron/rate with time zone, or continuous backup for point-in-time restore of RDS/S3), start and completion windows, target vault, lifecycle (delete after N days, move to cold storage after N days for supported resources), copy actions and tags for recovery points.

In plain words (no jargon): The schedule and keep-time for backups.

Analogy: A timetable on the clerk’s desk: copy at 2 am, keep a week, send one copy to Hyderabad.

How it works internally, step by step

  1. Rule. Schedule.
  2. Windows. Start/complete.
  3. Lifecycle. Delete/cold.
  4. Copy. Other vault.
  5. Continuous. PITR.

Words used above, in simple terms: recovery point = one completed backup · PITR = point-in-time recovery · cold storage = cheaper tier for long retention

Type 2 · Resource assignment (selections)

Definition (say it in an interview): A backup selection assigns resources to a plan by tags (e.g. backup=daily), resource types or ARNs, using an IAM role (AWSBackupDefaultServiceRole) that AWS Backup assumes to create and restore backups. Tag-based selection means new resources are protected as soon as they are tagged.

In plain words (no jargon): Choosing which resources are backed up, usually by tag.

Analogy: The clerk copies every file with a red sticker — new files with a red sticker are included automatically.

How it works internally, step by step

  1. Tags. backup=daily.
  2. Role. Default service role.
  3. Types. Filter by service.
  4. Conditions. And/Not.
  5. Opt-in. Service opt-in per Region.

Words used above, in simple terms: selection = set of resources in a plan · service opt-in = enable resource types in Backup settings · tag policy = org rule for tags

Type 3 · Backup vaults

Definition (say it in an interview): A backup vault is a Regional container for recovery points, encrypted with a KMS key (AWS-managed or customer managed — CMK needed for cross-account copies), with an optional vault access policy (e.g. deny backup:DeleteRecoveryPoint for everyone except a break-glass role). Logically air-gapped vaults add isolation and sharing to a recovery account.

In plain words (no jargon): The locked storage place for backups.

Analogy: A locked strongroom for copies, whose key is held by the KMS office.

How it works internally, step by step

  1. Regional. One per Region.
  2. KMS. Encrypt.
  3. Policy. Deny delete.
  4. Air-gapped. Extra isolation.
  5. Tags. Ownership.

Words used above, in simple terms: vault access policy = resource policy on the vault · logically air-gapped vault = isolated vault type · recovery account = separate account for backups

Type 4 · AWS Backup Vault Lock

Definition (say it in an interview): Vault Lock enforces WORM retention on a vault: minimum/maximum retention for all recovery points and no early deletion. Governance mode can be removed by users with permission; compliance mode becomes immutable after a cooling-off period (≥ 3 days) — nobody, including root or AWS, can delete recovery points or remove the lock afterwards. Assessed for regulations such as SEC 17a-4.

In plain words (no jargon): A lock that stops anyone from deleting backups early.

Analogy: A time-lock safe: once set, not even the owner can open it before the date.

How it works internally, step by step

  1. Governance. Removable.
  2. Compliance. Immutable.
  3. Min/max. Retention bounds.
  4. Cooling-off. ≥ 3 days.
  5. Scope. Whole vault.

Words used above, in simple terms: WORM = write once, read many · cooling-off period = time to undo before lock is final · immutable = cannot be changed

Type 5 · Cross-Region and cross-account copies

Definition (say it in an interview): Copy actions in a rule (or on-demand copy jobs) duplicate recovery points to a vault in another Region (Regional disaster) and/or another account in your organisation (compromised account), each with its own retention; cross-account copies require a customer managed KMS key and vault policies allowing the copy.

In plain words (no jargon): Automatically sending backup copies to another Region or account.

Analogy: Sending a copy of the documents to a branch office and to the head office’s own strongroom.

How it works internally, step by step

  1. Region. DR.
  2. Account. Isolation.
  3. Retention. Per copy.
  4. KMS. CMK for cross-account.
  5. Cost. Transfer + storage.

Words used above, in simple terms: copy job = one copy operation · recovery account = dedicated backup account · blast radius = how far damage spreads

Type 6 · Restore and restore testing

Definition (say it in an interview): A restore job creates a new resource (volume, instance, DB, file system, S3 objects…) from a recovery point using metadata you can override (AZ, instance type, encryption); restore testing plans pick recovery points on a schedule, restore them, optionally validate with a Lambda/EventBridge hook, record the time (your measured RTO), and delete the test resources.

In plain words (no jargon): Bringing data back from a backup — and practising it.

Analogy: A monthly fire drill: actually use the photocopies to see if they are readable.

How it works internally, step by step

  1. Metadata. Restore settings.
  2. New resource. Always.
  3. Validate. Hook.
  4. Testing plan. Scheduled.
  5. Measure. Restore time.

Words used above, in simple terms: restore metadata = settings used to recreate a resource · restore testing = scheduled automated restores · validation = proof the restore is usable

Type 7 · Disaster recovery strategies

Definition (say it in an interview): Four patterns trade cost for recovery speed: backup & restore (RPO/RTO hours), pilot light (data continuously replicated — RDS read replica, S3 CRR — with infrastructure as code ready; RTO tens of minutes), warm standby (scaled-down full stack running; minutes), multi-site active/active (both Regions serve; near zero). AWS Elastic Disaster Recovery continuously replicates servers for low RPO/RTO at modest cost.

In plain words (no jargon): Ways to keep running if a whole Region has a problem.

Analogy: Spare keys at a neighbour’s (backup), a second shop with stock but closed (pilot light), a small second shop open (warm), two full shops (active-active).

How it works internally, step by step

  1. B&R. Hours.
  2. Pilot light. Tens of minutes.
  3. Warm standby. Minutes.
  4. Active-active. ≈ 0.
  5. DRS. Server replication.

Words used above, in simple terms: pilot light = minimal always-on core in DR · warm standby = scaled-down running copy · failover = switching traffic to DR

Animated

What AWS Backup does before, during and after a disaster

Nightly backups, copies in another Region that nobody can delete, then a real restore when Mumbai has a problem.

Backup to recovery 6 steps
Watch what happens
  1. Step 1 · Nightly backups by tag — a backup plan rule runs at 02:00 IST and backs up every resource tagged backup=daily (EBS, EC2, RDS, EFS, DynamoDB, S3…) into a vault as recovery points.
  2. Step 2 · Copy to another Region — the same rule copies each recovery point to a vault in Hyderabad (and could also copy to another account).
  3. Step 3 · Lock the vault — Vault Lock (compliance mode) makes recovery points undeletable until retention ends — ransomware or a careless admin cannot remove them.
  4. Step 4 · Disaster — an impairment makes the primary Region unusable for your application.
  5. Step 5 · Restore in the DR Region — restore jobs create the volume/instance/database from the copied recovery point in Hyderabad.
  6. Step 6 · Measure RPO and RTO — data loss is bounded by the last backup (RPO); time to recover by how fast you restore and switch traffic (RTO). Test this before you need it.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: Backups are copies of important things kept somewhere safe; disaster recovery is the plan to keep working when something big goes wrong.

Try: Where are the backups of your phone photos? What if your house and phone were both lost — would the backup survive? That question is “another Region”.

Check yourself: Is a backup useful if you have never checked it opens?

You do not know — that is why restore tests exist.

Level 1 · Beginner first steps on AWS

Understand: AWS Backup plans (schedule + retention) select resources by tag; vaults store recovery points; copies go to another Region; RPO = data loss, RTO = downtime.

Try: Do the simulator, then calculate RPO for “daily at 2 am, disaster at 3 pm”.

Check yourself: What does RPO 1 hour mean?

At most one hour of data can be lost — you need backups/replication at least hourly.

Level 2 · Intermediate can do it alone

Understand: Build plan + selection + cross-Region copy, run on-demand backups, restore in another Region, read job states.

Try: Do the full hands-on and time the restore.

Check yourself: Backup job FAILED with “Insufficient privileges” — likely cause?

The selection’s IAM role lacks the backup policy, or the resource type is not opted in for the Region.

Level 3 · Advanced designs for others

Understand: Design cross-account backups with Organizations backup policies, Vault Lock compliance, restore testing with validation, and DR strategies per application with IaC + Route 53 failover.

Try: Write a DR runbook for one app: strategy, RPO/RTO, steps, owners, and a monthly drill schedule.

Check yourself: Why is Multi-AZ not a backup?

It copies corruption and deletions instantly; backups keep earlier points in time.

Level 4 · Expert architect / interviewer

Understand: Run business continuity: application tiers by criticality, budgets for DR, chaos/game days (AWS FIS, ARC zonal shift), regulator evidence, and continuous improvement from drills.

Try: Run a game day: impair one AZ with FIS for a pilot-light app and measure actual RTO vs target.

Check yourself: What evidence would an RBI/CERT-In auditor expect?

Documented RPO/RTO, backup policies, immutable copies, restore test reports with timings, and incident procedures.

9 Under the hood

How Backup uses service snapshots and roles

What AWS Backup does behind the scenes.

1 · Backups are service-native

AWS Backup orchestrates each service’s own mechanism: EBS/EC2 → snapshots/AMIs, RDS → snapshots (and continuous backups for PITR), DynamoDB → backups, EFS → incremental file-level backups, S3 → continuous or periodic backups. It adds central policy, vaults, locks and reporting.

2 · The service role

Backup assumes the role in your selection (AWSBackupDefaultServiceRole) to call CreateSnapshot, CopySnapshot, etc. Restores also need iam:PassRole for roles attached to restored resources (e.g. an EC2 instance profile).

3 · Cold storage and costs

For supported resources (e.g. EFS, DynamoDB, some EC2/EBS through Backup), lifecycle can move recovery points to cold storage after ≥ 90 days of retention planning (minimum 90 days in cold). Copies across Regions are billed for transfer and storage in the destination.

4 · Audit Manager and reporting

AWS Backup Audit Manager evaluates frameworks (e.g. “resources are backed up daily”, “recovery points encrypted”, “cross-Region copy exists”) and produces daily compliance reports to S3 — useful evidence for auditors.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. A 1 GiB volume and its backups for about an hour — a few rupees (cross-Region copy is charged per GB).

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Vaults in two Regions and a plan with copy

    UI way — AWS Management Console

    1. AWS Backup → Backup vaults → create tiffingo-vault (Mumbai); switch to Hyderabad → create tiffingo-dr-vault → back to Mumbai → Backup plans → Build a new plan daily-7-copy-hyd as in plan.json → Assign resources → tag backup=daily, default role.

    CLI way — the same thing with commands

    ACCT=$(aws sts get-caller-identity --query Account --output text)
aws backup create-backup-vault --backup-vault-name tiffingo-vault --query BackupVaultArn --output text
aws backup create-backup-vault --backup-vault-name tiffingo-dr-vault --region ap-south-2 --query BackupVaultArn --output text
# save plan.json from above (replace 123456789012 with $ACCT), then:
sed -i "s/123456789012/$ACCT/" plan.json
PLAN=$(aws backup create-backup-plan --backup-plan file://plan.json --query BackupPlanId --output text)
aws iam create-role --role-name AWSBackupDefaultServiceRole --path /service-role/ --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"backup.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null 2>&1
for p in AWSBackupServiceRolePolicyForBackup AWSBackupServiceRolePolicyForRestores; do aws iam attach-role-policy --role-name AWSBackupDefaultServiceRole --policy-arn arn:aws:iam::aws:policy/service-role/$p; done
ROLE=arn:aws:iam::$ACCT:role/service-role/AWSBackupDefaultServiceRole
aws backup create-backup-selection --backup-plan-id $PLAN --backup-selection "{\"SelectionName\":\"tag-daily\",\"IamRoleArn\":\"$ROLE\",\"ListOfTags\":[{\"ConditionType\":\"STRINGEQUALS\",\"ConditionKey\":\"backup\",\"ConditionValue\":\"daily\"}]}" --query SelectionId --output text

    You should see: two vault ARNs (ap-south-1 and ap-south-2), a plan ID and a selection ID.

    From now on anything tagged backup=daily is backed up at 02:00 IST and copied to Hyderabad.

  3. 2 · Tag a volume, run an on-demand backup, see the copy

    UI way — AWS Management Console

    1. Tag an EBS volume (e.g. from 4.5) with backup=daily → Protected resources → Create on-demand backup → vault tiffingo-vault → Jobs: backup job COMPLETED → Copy jobs: run an on-demand copy to tiffingo-dr-vault.

    CLI way — the same thing with commands

    VOL=$(aws ec2 create-volume --availability-zone ap-south-1a --size 1 --volume-type gp3 --tag-specifications 'ResourceType=volume,Tags=[{Key=backup,Value=daily}]' --query VolumeId --output text); aws ec2 wait volume-available --volume-ids $VOL
JOB=$(aws backup start-backup-job --backup-vault-name tiffingo-vault --resource-arn arn:aws:ec2:ap-south-1:$ACCT:volume/$VOL --iam-role-arn $ROLE --query BackupJobId --output text)
sleep 120; aws backup describe-backup-job --backup-job-id $JOB --query '[State,RecoveryPointArn]' --output text
RP=$(aws backup describe-backup-job --backup-job-id $JOB --query RecoveryPointArn --output text)
aws backup start-copy-job --recovery-point-arn $RP --source-backup-vault-name tiffingo-vault --destination-backup-vault-arn arn:aws:backup:ap-south-2:$ACCT:backup-vault:tiffingo-dr-vault --iam-role-arn $ROLE --query CopyJobId --output text

    You should see: COMPLETED arn:aws:ec2:ap-south-1::snapshot/snap-… and a copy job ID. A few minutes later aws backup list-recovery-points-by-backup-vault --backup-vault-name tiffingo-dr-vault --region ap-south-2 shows the copy.

    Scheduled runs need no commands at all — the plan does this every night.

  4. 3 · Restore in Hyderabad (the DR drill)

    UI way — AWS Management Console

    1. Switch to Hyderabad → tiffingo-dr-vault → select the recovery point → Restore → AZ ap-south-2a → default role → Restore backup → Jobs → Restore jobs: COMPLETED → the new volume appears in EC2 → Volumes (Hyderabad).

    CLI way — the same thing with commands

    RP2=$(aws backup list-recovery-points-by-backup-vault --backup-vault-name tiffingo-dr-vault --region ap-south-2 --query 'RecoveryPoints[0].RecoveryPointArn' --output text)
R=$(aws backup start-restore-job --region ap-south-2 --recovery-point-arn $RP2 --iam-role-arn $ROLE --resource-type EBS --metadata availabilityZone=ap-south-2a,volumeType=gp3,encrypted=true --query RestoreJobId --output text)
sleep 90; aws backup describe-restore-job --region ap-south-2 --restore-job-id $R --query '[Status,CreatedResourceArn]' --output text

    You should see: COMPLETED arn:aws:ec2:ap-south-2:…:volume/vol-… — your data now exists in Hyderabad, created only from the copied backup.

    Time this step: it is the core of your RTO for backup-and-restore DR.

Clean up and cost check

Delete restored/test volumes in both Regions; delete recovery points: aws backup delete-recovery-point --backup-vault-name tiffingo-vault --recovery-point-arn $RP (and in tiffingo-dr-vault with --region ap-south-2); delete the selection and plan (aws backup delete-backup-selection --backup-plan-id $PLAN --selection-id …; aws backup delete-backup-plan --backup-plan-id $PLAN); then delete both vaults. Do NOT enable Vault Lock compliance mode in this lab.

Interview and viva questions

Is AWS Backup free?

You pay for backup storage, restores (some services) and cross-Region transfer; the service orchestration itself has no separate fee.

Do I still need EBS snapshots/DLM?

AWS Backup can replace them with central policy; DLM is fine for simple EBS-only needs.

How often should we test restores?

At least monthly for critical systems, and after major changes.
