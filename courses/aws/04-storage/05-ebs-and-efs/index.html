EBS and EFS

1 The story

Photos that disappeared on the second server

Before you start: Lessons 3.1, 3.4 and 2.4.

🤔 TiffinGo added a second web server for Diwali. Customers uploading meal photos complained: half the time their photo “disappeared”. It had been saved on the other server’s disk.

Servers need two kinds of storage. Amazon EBS is a network disk for one instance in one AZ — the root disk and data disks, with types for every workload, snapshots for backup and moving between AZs, and encryption. Amazon EFS is a shared NFS file system that many Linux servers across AZs mount at the same time. This lesson shows a disk’s life (create, attach, format, mount, snapshot, move), every volume type, encryption by default, and a shared folder for two servers.

  • EBS = one instance’s disk, one AZ; snapshots back up and move it.
  • EFS = shared folder for many Linux servers across AZs.
  • Encrypt both; for app uploads S3 is often better than either.

With two web servers, customers’ uploaded photos “disappeared” because each server saved them on its own EBS disk. EBS is one server’s disk; EFS is a folder many servers share.

2 Definition

EBS and EFS

Formal definition (write this in exams)

Amazon Elastic Block Store (EBS) provides persistent, AZ-scoped block volumes (gp3, io2, st1, sc1) attached to EC2 instances, with incremental snapshots, KMS encryption and live modification. Amazon Elastic File System (EFS) is a managed, elastic NFS file system for Linux that many instances across Availability Zones mount concurrently through per-AZ mount targets, with lifecycle storage classes and access points.

In simple words

EBS is a disk for one server in one AZ; EFS is a shared folder that many Linux servers in different AZs use at the same time.

Say it in an interview

30-second answer you can speak:

  • “EBS is block storage in one AZ: gp3 by default, io2 for critical IOPS, encrypted by default, backed up with incremental snapshots (DLM/Backup) and resized live with Elastic Volumes.”
  • “For shared Linux files I use EFS with mount targets in each AZ, SG on 2049, TLS mounts, lifecycle to IA and access points per app; Windows shares go to FSx; web uploads usually go straight to S3.”

3 The big picture

Volume types and sharing files

New to computers? Start here. EBS is like a pen drive plugged into one laptop: fast, only that laptop can use it, and it stays in that room (AZ); a snapshot is a photocopy you can use to make a new pen drive in another room. EFS is like a shared network drive in the office: everyone’s computer sees the same folders, and it grows as you add files.

Jargon buster:

  • Volume — a virtual disk
  • Attach / mount — connect the disk / make its files visible in a folder
  • IOPS — how many small reads/writes per second
  • Throughput — how many MB per second
  • Snapshot — a backup copy of a volume
  • NFS — protocol for shared network folders (Linux)

Type 1 · EBS volumes: the basics

Definition (say it in an interview): An EBS volume is block storage over the network, created in one AZ and attached to an instance in the same AZ (one instance at a time, except io1/io2 Multi-Attach); it persists independently of the instance, is replicated within its AZ, and is billed per GB provisioned (plus IOPS/throughput above baseline).

In plain words (no jargon): A virtual hard disk for one server.

Analogy: A pen drive for one laptop in one room.

How it works internally, step by step

  1. AZ. Fixed.
  2. Attach. Same AZ.
  3. Persist. Beyond instance.
  4. mkfs. Once.
  5. fstab. Mount at boot.

Words used above, in simple terms: block storage = raw disk the OS formats · mount point = folder where a disk appears · fstab = list of disks to mount at boot

Type 2 · Volume types: gp3, io2, st1, sc1

Definition (say it in an interview): gp3 (default SSD: 3,000 IOPS and 125 MiB/s included at any size, up to 16,000 IOPS / 1,000 MiB/s, 1 GiB–16 TiB), io2 Block Express (up to 256,000 IOPS, 64 TiB, 99.999% durability, Multi-Attach), st1 throughput HDD and sc1 cold HDD (not bootable); gp2/io1 are previous generation.

In plain words (no jargon): The different kinds of EBS disks.

Analogy: Choosing a two-wheeler, a sports bike or a goods truck for the job.

How it works internally, step by step

  1. gp3. Balanced.
  2. io2. Provisioned IOPS.
  3. st1. Throughput HDD.
  4. sc1. Cold HDD.
  5. gp2. Migrate.

Words used above, in simple terms: IOPS = I/O operations per second · throughput = MiB per second · Multi-Attach = one volume, several instances (io1/io2)

Type 3 · Snapshots

Definition (say it in an interview): An EBS snapshot is a point-in-time, incremental backup stored in S3-managed storage; deleting an older snapshot keeps any blocks newer ones need. Create volumes from snapshots in any AZ of the Region, copy snapshots to other Regions (DR) or accounts, archive them (Snapshot Archive, 75% cheaper, 90-day minimum), protect them with Recycle Bin, and automate with Data Lifecycle Manager or AWS Backup (4.6).

In plain words (no jargon): Backup copies of a disk that you can restore anywhere in the Region.

Analogy: Photocopies of a register: the first time everything, later only new pages.

How it works internally, step by step

  1. Incremental. Changed blocks.
  2. Restore. New volume.
  3. Copy. Cross-Region.
  4. Archive. Cheaper tier.
  5. Automate. DLM / Backup.

Words used above, in simple terms: point-in-time = state at one moment · DLM = Data Lifecycle Manager · Fast Snapshot Restore = no lazy-loading delay

Type 4 · EBS encryption

Definition (say it in an interview): EBS encryption uses KMS keys (AWS-managed aws/ebs or customer managed) to encrypt data at rest on the volume, all snapshots, volumes created from them, and data moving between the instance and the volume — with no performance impact on Nitro; turn on encryption by default per Region so every new volume is encrypted. Unencrypted volumes are encrypted by snapshot → copy with encryption → new volume.

In plain words (no jargon): Automatic encryption of server disks and their backups.

Analogy: Every pen drive locks itself automatically; only laptops holding the right key can read it.

How it works internally, step by step

  1. Default. Per Region.
  2. KMS. aws/ebs or CMK.
  3. Snapshots. Inherit.
  4. Convert. Snapshot copy.
  5. Performance. No impact.

Words used above, in simple terms: encryption by default = account/Region setting · aws/ebs = AWS-managed EBS key · re-encrypt = copy with a new key

Type 5 · Elastic Volumes: resize and retune live

Definition (say it in an interview): Elastic Volumes let you increase size, change type (e.g. gp2 → gp3) or adjust IOPS/throughput of an in-use volume without detaching; then extend the partition (growpart) and file system (xfs_growfs or resize2fs). You can only grow size, not shrink, and must wait (up to 6 hours) between modifications.

In plain words (no jargon): Making a disk bigger or faster while the server keeps running.

Analogy: A pen drive that becomes bigger while plugged in — you just tell the laptop it grew.

How it works internally, step by step

  1. Size. Grow only.
  2. Type. Change.
  3. IOPS. Adjust.
  4. Wait. 6 h between.
  5. OS. growpart + grow FS.

Words used above, in simple terms: growpart = extend a partition · xfs_growfs = grow an XFS file system · optimizing = background modification state

Type 6 · Amazon EFS: shared file system

Definition (say it in an interview): Amazon EFS is a fully managed, elastic NFS v4.1 file system for Linux that thousands of instances, containers and Lambda functions can mount concurrently; Regional file systems store data across multiple AZs with a mount target (an ENI with a security group allowing TCP 2049) in each AZ; you pay per GB used — no provisioning.

In plain words (no jargon): A shared network folder that many Linux servers use at once.

Analogy: The office shared drive: everyone sees the same folders; it grows as you add files.

How it works internally, step by step

  1. NFS. v4.1.
  2. Mount target. Per AZ.
  3. SG. TCP 2049.
  4. Elastic. No size to set.
  5. TLS. -o tls.

Words used above, in simple terms: NFS = network file system protocol · mount target = EFS network endpoint in a subnet · POSIX = Linux file permissions model

Type 7 · EFS storage classes, throughput and access points (and FSx)

Definition (say it in an interview): EFS lifecycle management moves files not accessed for N days to Infrequent Access or Archive (cheaper storage, per-GB access fee) and back on access; Elastic throughput (default) scales automatically, Provisioned sets a fixed level; access points enforce a root directory and POSIX user per application. For Windows/SMB, Lustre (HPC) or NetApp ONTAP, use Amazon FSx.

In plain words (no jargon): Features that make EFS cheaper and safer to share.

Analogy: Old files in the shared drive move to the back room automatically; each team gets its own door.

How it works internally, step by step

  1. IA. Cheaper, access fee.
  2. Archive. Rarely used.
  3. Elastic. Auto throughput.
  4. Access point. Root + user.
  5. FSx. Windows/Lustre/ONTAP.

Words used above, in simple terms: access point = app-specific entry into EFS · SMB = Windows file sharing protocol · Lustre = high-performance file system for HPC

What happens with a disk (EBS) and a shared folder (EFS)

Create a disk, attach it, use it, back it up, move it to another AZ — then share one folder between two servers.

Disks and shared folders 6 steps
Watch what happens
  1. Step 1 · Create a volume — an EBS volume is created in one AZ — the same AZ as the instance that will use it (gp3, 20 GiB, encrypted).
  2. Step 2 · Attach — attach it as /dev/sdf; on Nitro instances Linux sees it as an NVMe device (/dev/nvme1n1).
  3. Step 3 · Format and mount — a new volume is raw blocks: create a file system once (mkfs) and mount it at /data (add to /etc/fstab to survive reboots).
  4. Step 4 · Snapshot — a snapshot copies the volume’s blocks to S3-backed storage; later snapshots copy only changed blocks (incremental).
  5. Step 5 · New volume elsewhere — volumes cannot move between AZs — create a new volume from the snapshot in ap-south-1b (or copy the snapshot to another Region).
  6. Step 6 · Shared folder with EFS — when many servers in different AZs need the same files, mount one EFS file system over NFS — it grows and shrinks automatically.

7 Learn at your level

From curious beginner to expert — pick your level

Find your level, read that card, do the “Try” and answer the check. Then move one level up. Everyone starts somewhere — Level 0 needs no computer background at all.

Level 0 · Curious no computer background

Understand: A server needs a disk like a laptop needs a hard drive. Some files also need to be shared by many computers, like an office shared drive. AWS has both.

Try: Think of a pen drive vs a shared Google Drive folder: which would you use for your own laptop files, which for a group project?

Check yourself: Can two laptops use the same pen drive at the same moment?

No — like EBS; a shared drive (EFS) is the tool for that.

Level 1 · Beginner first steps on AWS

Understand: EBS: one AZ, one instance, types gp3/io2/st1/sc1, snapshots; EFS: NFS shared across AZs, mount targets with SG 2049.

Try: Do the simulator, then explain why a snapshot is needed to move a disk to another AZ.

Check yourself: Which EBS type is the sensible default?

gp3.

Level 2 · Intermediate can do it alone

Understand: Create/attach/format/mount, fstab with nofail, snapshot and restore in another AZ, Elastic Volumes, encryption by default, EFS with TLS.

Try: Do the full hands-on; then reboot the instance and prove /data mounts automatically.

Check yourself: After reboot the instance hangs at boot — what did you probably do?

Added the disk to /etc/fstab without nofail (or wrong UUID) and the disk was missing.

Level 3 · Advanced designs for others

Understand: Tune performance (IOPS vs throughput vs instance EBS limits), DLM/AWS Backup policies, Fast Snapshot Restore, EFS access points/lifecycle/replication, FSx choices.

Try: Benchmark gp3 at 3,000 vs 6,000 IOPS with fio; record the difference and the cost change.

Check yourself: gp3 set to 16,000 IOPS but you see 10,000 — why?

The instance type’s EBS bandwidth/IOPS limit is lower — check EBS-optimised limits.

Level 4 · Expert architect / interviewer

Understand: Design storage tiers for platforms: database volumes with io2 + multi-AZ replication at app level, EFS for shared content, S3 for objects; cross-Region snapshot DR; cost governance of orphan volumes/snapshots.

Try: Write a Config/Lambda job that reports unattached volumes and snapshots older than 90 days with their monthly cost.

Check yourself: Why not just use EFS for everything?

Higher per-GB price and NFS latency; databases and boot disks belong on EBS, objects on S3.

8 Deep dive

Format/mount, EFS with TLS, prices

Format and mount a data volume (Amazon Linux 2023)

lsblk                                   # find the new disk, e.g. nvme1n1 (no mount point)
sudo file -s /dev/nvme1n1               # 'data' = empty → safe to format
sudo mkfs -t xfs /dev/nvme1n1
sudo mkdir -p /data && sudo mount /dev/nvme1n1 /data
UUID=$(sudo blkid -s UUID -o value /dev/nvme1n1)
echo "UUID=$UUID /data xfs defaults,nofail 0 2" | sudo tee -a /etc/fstab
df -h /data

Never run mkfs on a disk that already has data (file -s shows a file system) — it erases it.

Mount EFS with TLS

sudo dnf install -y amazon-efs-utils
sudo mkdir -p /mnt/shared
sudo mount -t efs -o tls fs-0a1b2c3d4e5f60789:/ /mnt/shared
echo 'fs-0a1b2c3d4e5f60789:/ /mnt/shared efs _netdev,tls 0 0' | sudo tee -a /etc/fstab

9 Under the hood

Replication, lazy loading, NFS internals

What happens below EBS and EFS.

1 · EBS replication and durability

Each volume is replicated within its AZ across multiple servers. gp3/gp2/io1/st1/sc1 are designed for 99.8–99.9% annual durability; io2 for 99.999%. That is why snapshots (stored redundantly across AZs) are still essential.

2 · Lazy loading from snapshots

A volume created from a snapshot is usable immediately, but blocks are fetched from S3 on first access, so the first read of each block is slower. Initialise with fio/dd reads, or enable Fast Snapshot Restore per AZ for full performance at once (extra cost).

3 · NVMe on Nitro

On Nitro instances, EBS volumes are exposed as NVMe devices; the console name /dev/sdf maps to /dev/nvme1n1 (check with lsblk or sudo nvme list — the serial shows the volume ID).

4 · EFS internals

Regional EFS stores data and metadata redundantly across multiple AZs; each mount target is an ENI in a subnet. Clients use NFS v4.1; amazon-efs-utils adds TLS via a local stunnel and IAM authorisation if configured.

14 Hands-on

Do it yourself, step by step

These labs run on your own AWS account — we cannot run them for you. Every step shows the UI way (console clicks) and the CLI way (commands for AWS CloudShell or your terminal), plus what you should see. Work as an IAM/Identity Center user, never root; use the Mumbai Region (ap-south-1); stay inside Free Tier/credits; and always do the Clean up step at the end. One or two t3.micro, a 20–40 GiB gp3 volume, a snapshot and a tiny EFS for about an hour — a few rupees.

  1. 0 · Get ready: signed in, budget, Region, CloudShell

    UI way — AWS Management Console

    1. Sign in as your admin user (not root) — Lesson 1.2 shows how to create it.
    2. Billing and Cost Management → Budgets → check a monthly cost budget with e-mail alerts exists (e.g. $5).
    3. Top-right Region menu → Asia Pacific (Mumbai).
    4. Click the CloudShell icon (>_) in the top bar — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity --query Arn --output text   # must NOT end in :root
aws configure set region ap-south-1
aws configure list | grep region

    You should see: an ARN ending in :user/… or :assumed-role/… and region ap-south-1.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · Create, attach, format and mount an encrypted volume

    UI way — AWS Management Console

    1. EC2 → launch a t3.micro (AL2023) with role LabSSMRole in ap-south-1a → Volumes → Create volume gp3, 20 GiB, same AZ, encrypted → Actions → Attach volume → instance, /dev/sdf → connect with Session Manager → run the Deep-dive format/mount commands.

    CLI way — the same thing with commands

    aws iam create-role --role-name LabSSMRole --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null 2>&1
aws iam attach-role-policy --role-name LabSSMRole --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
aws iam create-instance-profile --instance-profile-name LabSSMRole >/dev/null 2>&1; aws iam add-role-to-instance-profile --instance-profile-name LabSSMRole --role-name LabSSMRole 2>/dev/null; sleep 10
aws ec2 enable-ebs-encryption-by-default --query EbsEncryptionByDefault
ID=$(aws ec2 run-instances --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --instance-type t3.micro --iam-instance-profile Name=LabSSMRole --placement AvailabilityZone=ap-south-1a --query 'Instances[0].InstanceId' --output text); aws ec2 wait instance-status-ok --instance-ids $ID
VOL=$(aws ec2 create-volume --availability-zone ap-south-1a --size 20 --volume-type gp3 --query VolumeId --output text); aws ec2 wait volume-available --volume-ids $VOL
aws ec2 attach-volume --volume-id $VOL --instance-id $ID --device /dev/sdf --query State --output text
run(){ C=$(aws ssm send-command --instance-ids $ID --document-name AWS-RunShellScript --parameters "commands=[\"$1\"]" --query Command.CommandId --output text); sleep 6; aws ssm get-command-invocation --command-id $C --instance-id $ID --query StandardOutputContent --output text; }
run 'mkfs -t xfs /dev/nvme1n1 >/dev/null && mkdir -p /data && mount /dev/nvme1n1 /data && echo TiffinGo-orders > /data/orders.txt && df -h /data | tail -1'

    You should see: true (encryption by default), attaching, then a df line like /dev/nvme1n1 20G 175M 20G 1% /data.

    The volume was encrypted automatically because encryption-by-default is now on for ap-south-1.

  3. 2 · Snapshot, restore in another AZ, grow live

    UI way — AWS Management Console

    1. Volume → Actions → Create snapshot → Snapshots → select → Create volume from snapshot in ap-south-1b. Original volume → Modify volume → 40 GiB → then grow the file system with Session Manager.

    CLI way — the same thing with commands

    SNAP=$(aws ec2 create-snapshot --volume-id $VOL --description data-v1 --query SnapshotId --output text); aws ec2 wait snapshot-completed --snapshot-ids $SNAP
V2=$(aws ec2 create-volume --snapshot-id $SNAP --availability-zone ap-south-1b --volume-type gp3 --query VolumeId --output text)
aws ec2 describe-volumes --volume-ids $VOL $V2 --query 'Volumes[].[VolumeId,AvailabilityZone,Size,Encrypted,State]' --output table
aws ec2 modify-volume --volume-id $VOL --size 40 --query 'VolumeModification.ModificationState' --output text; sleep 20
run 'xfs_growfs -d /data >/dev/null; df -h /data | tail -1'

    You should see: two volumes (1a in-use, 1b available, both encrypted), modifying, and df now showing 40G — grown with the file system mounted.

    The copy in 1b holds orders.txt as of the snapshot — that is how you move or clone disks across AZs.

  4. 3 · A shared EFS folder for two servers

    UI way — AWS Management Console

    1. EFS → Create file system tiffingo-shared (Regional) → Customize → mount targets in 1a and 1b with security group efs-sg (NFS 2049 from the instances’ SG) → on each instance: install amazon-efs-utils and mount with TLS → write a file on one, read it on the other.

    CLI way — the same thing with commands

    VPC=$(aws ec2 describe-vpcs --filters Name=is-default,Values=true --query 'Vpcs[0].VpcId' --output text)
ISG=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].SecurityGroups[0].GroupId' --output text)
ESG=$(aws ec2 create-security-group --group-name efs-sg --description nfs --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $ESG --protocol tcp --port 2049 --source-group $ISG >/dev/null
FS=$(aws efs create-file-system --encrypted --tags Key=Name,Value=tiffingo-shared --query FileSystemId --output text); sleep 20
for s in $(aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC Name=availability-zone,Values=ap-south-1a,ap-south-1b --query 'Subnets[].SubnetId' --output text); do aws efs create-mount-target --file-system-id $FS --subnet-id $s --security-groups $ESG >/dev/null; done; sleep 90
run "dnf install -y amazon-efs-utils >/dev/null && mkdir -p /mnt/shared && mount -t efs -o tls $FS:/ /mnt/shared && echo photo-from-web-a > /mnt/shared/meal1.txt && ls -l /mnt/shared"

    You should see: the file listed in /mnt/shared. Launch a second instance in ap-south-1b with the same role and SG, mount the same FS ID, and cat /mnt/shared/meal1.txt prints photo-from-web-a.

    Both servers see one folder — the fix for TiffinGo’s “disappearing photos”.

Clean up and cost check

for m in $(aws efs describe-mount-targets --file-system-id $FS --query 'MountTargets[].MountTargetId' --output text); do aws efs delete-mount-target --mount-target-id $m; done; sleep 60; aws efs delete-file-system --file-system-id $FS; aws ec2 terminate-instances --instance-ids $ID; aws ec2 wait instance-terminated --instance-ids $ID; aws ec2 delete-volume --volume-id $VOL; aws ec2 delete-volume --volume-id $V2; aws ec2 delete-snapshot --snapshot-id $SNAP; aws ec2 delete-security-group --group-id $ESG — data volumes are not deleted with the instance (DeleteOnTermination=false).

Interview and viva questions

Does stopping an instance delete EBS?

No — EBS persists; terminate deletes only volumes with DeleteOnTermination=true (root by default).

Can EFS be used from Windows?

No — use FSx for Windows File Server.

Is EBS faster than EFS?

Usually lower latency for a single server; EFS trades some latency for sharing.
