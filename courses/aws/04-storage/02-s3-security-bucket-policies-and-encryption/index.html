2 Definition

S3 security: bucket policies and encryption

Formal definition (write this in exams)

S3 access is decided by Block Public Access, identity-based (IAM) and resource-based (bucket) policies — where an explicit Deny overrides any Allow, a same-account request needs one Allow and a cross-account request needs both — plus KMS key policies for SSE-KMS objects; data is encrypted at rest by default with SSE-S3 (optionally SSE-KMS/DSSE-KMS with Bucket Keys) and in transit when a policy denies requests where aws:SecureTransport is false.

In simple words

Keep buckets non-public, write deny rules for things that must never happen (like plain http), allow exactly what each role needs, and encrypt with your own key when you need control.

Say it in an interview

30-second answer you can speak:

  • “Every bucket has BPA on and ACLs disabled; the bucket policy carries organisation-wide denies — HTTPS-only and VPC-endpoint or org-only conditions — while IAM policies grant per-role prefix access.”
  • “Sensitive prefixes use SSE-KMS with a customer managed key and Bucket Key; cross-account readers need both bucket-policy and key-policy grants; Access Analyzer and CloudTrail data events monitor access.”

3 The big picture

Policy logic and encryption choices

New to computers? Start here. Think of the bucket as an exam-cell strongroom: a sign at the gate says “no public entry” (Block Public Access); a rule says “nobody enters without the escort” (Deny unless HTTPS); a list says who may enter which shelf (policies); and the cupboard inside has its own lock whose key is kept by another office (KMS). Every visit is written in a register (CloudTrail).

Jargon buster:

  • Bucket policy — rules attached to the bucket: who may do what
  • Explicit deny — a rule that says NO — it always wins
  • Block Public Access — master switch that stops public access
  • SSE-S3 / SSE-KMS — encryption at rest with S3 keys / your KMS key
  • aws:SecureTransport — true when the request used HTTPS
  • Access Analyzer — tool that finds external/public access

Type 1 · Block Public Access (BPA)

Definition (say it in an interview): Block Public Access has four settings — BlockPublicAcls, IgnorePublicAcls, BlockPublicPolicy, RestrictPublicBuckets — at account and bucket level (and access points); when on, S3 refuses to save public policies/ACLs and ignores existing public grants. New buckets have all four on.

In plain words (no jargon): A master switch that stops anything in S3 from being made public.

Analogy: A “No public entry” order from the principal that overrides any teacher’s note.

How it works internally, step by step

  1. Account. s3control.
  2. Bucket. s3api.
  3. ACL switches. Two.
  4. Policy switches. Two.
  5. Override. Wins over grants.

Words used above, in simple terms: public = accessible by anyone / any account · ACL = old per-object permission list · s3control = account-level S3 settings API

Type 2 · Bucket policies

Definition (say it in an interview): A bucket policy is a resource-based JSON policy (up to 20 KB) on the bucket with statements of Effect, Principal, Action, Resource (bucket ARN for bucket actions, bucket/* for object actions) and Conditions (aws:SecureTransport, aws:SourceIp, aws:SourceVpce, aws:PrincipalOrgID, s3:x-amz-server-side-encryption…). It is where cross-account grants and bucket-wide denies live.

In plain words (no jargon): Rules attached to the bucket itself.

Analogy: The rule board on the strongroom door, applying to everyone who comes.

How it works internally, step by step

  1. Effect. Allow/Deny.
  2. Principal. Who.
  3. Resource. bucket or bucket/*.
  4. Condition. Context.
  5. Size. 20 KB.

Words used above, in simple terms: resource-based policy = policy attached to the resource · condition key = context value like SecureTransport · ARN = Amazon Resource Name

Type 3 · IAM policies, bucket policies and cross-account access

Definition (say it in an interview): Within one account, a request is allowed if the IAM policy or the bucket policy allows it (and nothing denies); across accounts, the caller’s IAM policy and the bucket policy must both allow. Session policies, permission boundaries and SCPs can further limit (Lesson 2.3).

In plain words (no jargon): Which permissions are needed for a request to succeed.

Analogy: Inside the college, either the HoD or the exam cell can authorise you; a visitor from another college needs both their principal’s letter and our exam cell’s permission.

How it works internally, step by step

  1. Same account. OR.
  2. Cross-account. AND.
  3. Deny. Wins.
  4. SCP. Org limit.
  5. KMS. Separate gate.

Words used above, in simple terms: cross-account = between two AWS accounts · implicit deny = no allow found · SCP = organisation-level guardrail

Type 4 · Object Ownership and ACLs

Definition (say it in an interview): Object Ownership = Bucket owner enforced (default for new buckets since April 2023) disables ACLs: the bucket owner automatically owns every object, even those uploaded by other accounts, and all access is controlled with policies. Older buckets may still use ACLs — migrate them.

In plain words (no jargon): Who owns uploaded files, and why ACLs are switched off.

Analogy: All files submitted to the exam cell belong to the exam cell, not to whoever dropped them in.

How it works internally, step by step

  2. Preferred. Owner preferred.
  3. Writer. Uploader owns (legacy).
  4. Default. Enforced.
  5. Migrate. Old buckets.

Words used above, in simple terms: ACL = access control list · object writer = account that uploaded · canned ACL = preset like public-read

Type 5 · Encryption at rest: SSE-S3, SSE-KMS, Bucket Keys

Definition (say it in an interview): Every new object is encrypted at rest: SSE-S3 (AES-256, S3-managed keys) by default; set SSE-KMS default encryption with a customer managed key to control and audit decryption through the key policy (Lesson 2.4); enable an S3 Bucket Key to reduce KMS requests (and cost) by using a bucket-level key; DSSE-KMS adds a second layer.

In plain words (no jargon): How S3 encrypts stored files, and who holds the keys.

Analogy: The cupboard is always locked (SSE-S3); with SSE-KMS the key lives in another office that writes down every time it is used.

How it works internally, step by step

  1. Default. SSE-S3.
  2. KMS. Key policy.
  3. Bucket Key. Cost.
  4. Existing objects. Re-copy.
  5. Enforce. Deny unencrypted PUTs (optional).

Words used above, in simple terms: CMK = customer managed KMS key · envelope encryption = data key encrypted by a KMS key · Bucket Key = bucket-level data key

Type 6 · Encryption in transit: the HTTPS-only policy

Definition (say it in an interview): S3 accepts both HTTP and HTTPS endpoints; to guarantee encryption in transit add a bucket-policy Deny for all actions when aws:SecureTransport is false, and optionally when s3:TlsVersion < 1.2. Prove it by sending a request to http://s3.ap-south-1.amazonaws.com — it must return AccessDenied.

In plain words (no jargon): Making sure data is always encrypted while moving over the network.

Analogy: A rule that the strongroom opens only when the escorted van arrives — never for a walk-in.

How it works internally, step by step

  1. Deny. Effect.
  2. Principal. "*".
  3. Action. s3:*.
  4. Resource. bucket + bucket/*.
  5. Condition. SecureTransport false.

Words used above, in simple terms: TLS = protocol behind HTTPS · aws:SecureTransport = true for HTTPS requests · endpoint-url = CLI option to force a URL

Four gates 6 steps
Watch what happens
  1. Step 1 · Anonymous visitor — any grant to “everyone” is ignored or refused because Block Public Access is on — the first gate.
  2. Step 2 · Script over http:// — the bucket policy has an explicit Deny when aws:SecureTransport is false. An explicit Deny beats every Allow.
  3. Step 3 · Student reading submissions/ — no IAM or bucket policy statement allows it, so the default is Deny (implicit deny).

8 Deep dive

Evaluation order, deny non-KMS uploads, access points

Evaluation order, precisely

  1. Block Public Access (account → bucket → access point) can refuse public grants.
  2. All applicable policies are gathered: SCPs, resource policy (bucket), identity policy (IAM), permission boundary, session policy.
  3. Any matching explicit Deny → denied.
  4. An Allow is needed: identity or resource policy for the same account; both for cross-account; and SCP/boundary/session must also allow.
  5. For SSE-KMS objects, KMS evaluates the key policy (+ grants, IAM) for kms:Decrypt / GenerateDataKey.

Deny uploads that are not SSE-KMS (optional hardening)

{
  "Sid": "DenyNonKmsUploads",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::tiffingo-sec-123456789012/*",
  "Condition": {"StringNotEquals": {"s3:x-amz-server-side-encryption": "aws:kms"}}
}

Careful: with default encryption set, many clients do not send the header, so this Deny would block them. Most teams rely on default encryption and check with AWS Config instead.

Access points (for big shared buckets)

An S3 Access Point is a named entry with its own policy and optionally VPC-only access — e.g. faculty-ap for notes/, analytics-ap for reports/. It keeps one huge bucket policy from becoming unmanageable.

2 · SSE-KMS under the hood

On PUT, S3 asks KMS for a data key (GenerateDataKey), encrypts the object, stores the encrypted data key with it. On GET, S3 calls KMS Decrypt for that data key. With a Bucket Key, S3 gets a bucket-level key from KMS for a period and derives object keys from it — far fewer KMS calls and CloudTrail entries.

3 · Why public policies are detected

S3 analyses a policy as “public” when it grants to * (or broad principals) without restricting conditions such as specific aws:SourceVpce, aws:PrincipalOrgID or aws:SourceIp ranges. BlockPublicPolicy refuses saving such policies; RestrictPublicBuckets blocks cross-account use of already-public ones.

4 · Logs you can enable

CloudTrail data events (per object API, JSON, near real-time, priced per event) vs server access logs (best-effort log files to a bucket, free except storage). Many teams use data events for sensitive buckets only.

    CloudShell is free, runs in your browser and is already signed in as the user you logged in with.

  2. 1 · HTTPS-only bucket policy — and prove it

    UI way — AWS Management Console

    1. Create bucket tiffingo-sec-ACCOUNTID → upload notes/a.txt → Permissions → Bucket policy → Edit → paste https-only.json (your bucket name) → Save changes.

    CLI way — the same thing with commands

    ACCT=$(aws sts get-caller-identity --query Account --output text); B=tiffingo-sec-$ACCT
aws s3 mb s3://$B --region ap-south-1; echo hello > a.txt; aws s3 cp a.txt s3://$B/notes/a.txt
# save the policy above as https-only.json, then:
sed -i "s/tiffingo-sec-123456789012/$B/g" https-only.json
aws s3api put-bucket-policy --bucket $B --policy file://https-only.json
aws s3 ls s3://$B/notes/                                                      # HTTPS (default)
aws s3 ls s3://$B/notes/ --endpoint-url http://s3.ap-south-1.amazonaws.com    # plain HTTP

    You should see: the first listing shows a.txt; the second fails with An error occurred (AccessDenied) when calling the ListObjectsV2 operation: Access Denied — your proof that data cannot travel unencrypted.

    Same user, same permissions, same bucket — only the transport changed. That is the explicit Deny working.

  3. 2 · SSE-KMS default encryption with a Bucket Key

    UI way — AWS Management Console

    1. KMS → Create key symmetric, alias tiffingo-results. Bucket → Properties → Default encryption → Edit → SSE-KMS, choose the key, Bucket Key Enable → upload results/r.txt → open it → Properties shows the KMS key.

    CLI way — the same thing with commands

    KEY=$(aws kms create-key --description 'tiffingo results' --query KeyMetadata.KeyId --output text); aws kms create-alias --alias-name alias/tiffingo-results --target-key-id $KEY
aws s3api put-bucket-encryption --bucket $B --server-side-encryption-configuration "{\"Rules\":[{\"ApplyServerSideEncryptionByDefault\":{\"SSEAlgorithm\":\"aws:kms\",\"KMSMasterKeyID\":\"$KEY\"},\"BucketKeyEnabled\":true}]}"
echo 'roll 101: A+' > r.txt; aws s3 cp r.txt s3://$B/results/r.txt
aws s3api head-object --bucket $B --key results/r.txt --query '[ServerSideEncryption,SSEKMSKeyId,BucketKeyEnabled]'
aws s3api head-object --bucket $B --key notes/a.txt --query ServerSideEncryption

    You should see: ["aws:kms", "arn:aws:kms:ap-south-1:…:key/…", true] for the new object and "AES256" for the old one — default encryption applies only to new uploads.

    A customer managed key costs about USD 1/month (prorated) — schedule it for deletion in cleanup.

  4. 3 · BPA refuses a public policy; a faculty role reads only notes/

    UI way — AWS Management Console

    1. Try to add a statement with Principal "*" and Allow s3:GetObject → the console refuses (Block Public Access). IAM → Roles → Create role (trusted: this account) FacultyReader with an inline policy: s3:GetObject on notes/* → Switch role → open notes/a.txt (works) and results/r.txt (denied).

    CLI way — the same thing with commands

    aws s3api put-bucket-policy --bucket $B --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":\"*\",\"Action\":\"s3:GetObject\",\"Resource\":\"arn:aws:s3:::$B/*\"}]}" 2>&1 | tail -1

CREDS=$(aws sts assume-role --role-arn arn:aws:iam::$ACCT:role/FacultyReader --role-session-name mehta --query Credentials --output json)
export AWS_ACCESS_KEY_ID=$(echo $CREDS | python3 -c 'import sys,json;print(json.load(sys.stdin)["AccessKeyId"])') AWS_SECRET_ACCESS_KEY=$(echo $CREDS | python3 -c 'import sys,json;print(json.load(sys.stdin)["SecretAccessKey"])') AWS_SESSION_TOKEN=$(echo $CREDS | python3 -c 'import sys,json;print(json.load(sys.stdin)["SessionToken"])')
aws s3 cp s3://$B/notes/a.txt -; aws s3 cp s3://$B/results/r.txt - 2>&1 | grep -o 'Forbidden\|AccessDenied'
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN

    You should see: An error occurred (AccessDenied) when calling the PutBucketPolicy operation: … because public policies are blocked by the BlockPublicPolicy block public access setting., then hello for notes/ and Forbidden for results/ as the faculty role.

    These temporary role credentials live only in this shell and expire automatically — never paste such values into chat or files.

Clean up and cost check

  • Endpoint ID and route table entries (describe-route-tables).

Stretch goal: Add aws:PrincipalOrgID to also stop requests from other organisations, and test with Access Analyzer “check no public access”.

    Followed five requests through four gates

    BPA → explicit Deny → Allow (IAM/bucket) → KMS key policy; all logged.

  2. 2
    Learned policy logic

    Same account: one Allow; cross-account: both; Deny always wins.

  3. 3
    Wrote the HTTPS-only policy

    Deny when aws:SecureTransport is false (+ TLS < 1.2).

    aws s3api put-bucket-policy --bucket $B --policy file://https-only.json

    Proved it

    Same command over http:// → AccessDenied.

    aws s3 ls s3://$B --endpoint-url http://s3.ap-south-1.amazonaws.com

    Set SSE-KMS with a Bucket Key

    New objects show aws:kms; old ones stay AES256 until re-copied.

    aws s3api put-bucket-encryption …

Remember these
  • Private ≠ protected: deny unsafe paths explicitly.
  • Allow on SecureTransport=true does not block http.
  • SSE-KMS readers need kms:Decrypt.
  • Keep BPA on at account level.

Interview and viva questions

Does HTTPS-only break the console?

No — the console and CLI use HTTPS.

Is SSE-S3 “real” encryption?

Yes, AES-256 at rest; SSE-KMS adds your control and audit of the key.

Can I lock myself out?

A Deny can block admins too; the root user can always delete a bucket policy.
