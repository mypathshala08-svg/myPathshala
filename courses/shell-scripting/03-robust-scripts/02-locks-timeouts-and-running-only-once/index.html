The problem

Riya’s report job runs every 5 minutes from cron. One day the database is slow, a run takes 7 minutes, the next run starts while the first is still working, and both write the same file: the report ends up with half of each. Another night a network copy simply hangs, and the job never finishes. Two failures that set -e and retries cannot fix: two copies at once and steps that never end. This lesson adds a lock with flock so only one copy runs, timeout so nothing runs forever, and the patterns behind them: lock files, PID files, stale locks and idempotent steps.

By the end of this page you will be able to:
  • show how two copies of a job corrupt shared data (a race condition) and prevent it with flock
  • use flock -n (skip), flock -w (wait with a limit) and the exec 9>file pattern, and know why mkdir also works as a lock
  • limit any command’s run time with timeout, -k and exit code 124, and set a deadline for a whole script
  • avoid stale-lock and PID-file traps, and make steps idempotent so a rerun is always safe

Two copies, one file

Think first

Five copies of append.sh each read a counter, add 1 and write it back. Run one after another, the counter ends at 5. Started at the same moment, it ends at 1. Riya first “fixes” it with [[ -e job.lock ]] && exit; touch job.lock; …; rm job.lock: it still breaks sometimes, and after one crash the job never runs again. Why does the check-then-create lock fail, and why does a crash leave the job stuck?

Keep your guess in mind. The answer is at the end of part 6.

In ~/ops (every run in this lesson is real). bin/append.sh reads out/counter, waits 0.2 s (the “work”), and writes counter+1. bin/job.sh is the same job protected by flock.

Kabir

Why does the counter end at 1?

Arjun Sir

All five read 0 before any of them wrote. Each writes 0+1. This is a race condition: the result depends on timing. The check-then-create lock has the same race: two copies can both see “no lock” before either creates it.

Riya

So a lock must be checked and taken in one step.

Arjun Sir

Exactly. The kernel’s flock does that atomically, and it releases the lock automatically when the process ends, even after a crash or kill -9. No stale lock files.

2 Definition

Locks, timeouts and idempotence

Formal definition (write this in exams)

A lock makes sure only one process at a time runs a critical section; flock takes a kernel-managed lock on a file atomically and releases it automatically when the process exits. A timeout limits how long a command may run; the timeout command stops it with a signal and exits 124. A step is idempotent when running it again produces the same result, so reruns and retries are safe.

In simple words

One copy at a time, nothing runs forever, reruns change nothing extra.

Locks and timeouts at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a single-person changing room

The door locks from inside. The next person either waits or comes back later. When you leave, the door unlocks by itself, even if you ran out in a hurry.

Basic What you will type

  • flock -n /run/lock/report.lock ./report.sh in cron
  • inside a script: exec 9>/run/lock/report.lock; flock -n 9 || exit 0
  • timeout 300 rsync -a src/ dst/
  • timeout -k 10 300 ./step.sh

Intermediate The differences that matter

  • -n fails at once if locked (skip this run); -w N waits up to N seconds; no option waits forever.
  • flock locks belong to the open file: they disappear when the process (and its children holding fd 9) exit. A lock file left on disk is harmless; only a held lock blocks.
  • timeout sends TERM (exit 124 if it fired); -k 5 sends KILL 5 s later if the command ignores TERM; -s INT chooses another signal.
  • An idempotent step gives the same result if run twice: mkdir -p, ln -sfn, “create user if missing”.

Advanced Behind the screen: flock(2) and atomic operations

  • flock(2) is an advisory lock on an open file description, kept by the kernel: only programs that also call flock respect it. Exclusive (-x, default) vs shared (-s) locks allow one writer or many readers.
  • mkdir is atomic (create-or-fail in one system call), so mkdir lockdir is a portable lock, but it is not released on crash: you need a trap and stale-lock handling.
  • PID files can lie: after a crash and reboot the PID may belong to another process (PID reuse). Check /proc/PID/cmdline or prefer flock.
  • flock does not work reliably on some network file systems (older NFS); keep lock files on local disk, e.g. /run/lock or /var/lock.

Did you know? The flock man page has a ready-made line for the top of any script: [ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :. It re-runs the script under a lock on the script file itself, so no separate lock file is needed.

Exam tip: “How do you make sure a cron job never runs twice at the same time?” → Run it under flock: flock -n /var/lock/job.lock /path/job.sh (or take the lock inside the script with exec 9>file; flock -n 9 || exit). The kernel releases it automatically when the job ends.

Quick check Why does [[ -e lock ]] || touch lock not work as a lock?
Answer: Check and create are two steps: two copies can both pass the check before either creates the file.
Common mistake
✗[[ -e /tmp/job.lock ]] && exit; touch /tmp/job.lock; …; rm /tmp/job.lock
✓exec 9>/run/lock/job.lock; flock -n 9 || exit 0

The check-then-create has a race, and a crash leaves the file forever: the job never runs again.

Common mistake
✗rsync -a big/ remote:/backup/ with no limit in a nightly job
✓timeout -k 60 3600 rsync -a big/ remote:/backup/

A hung network copy blocks the job, and with a lock, every later run too.

🟡 Changes filesno sudo

flock -n FILE CMD · exec 9>FILE; flock -n 9 one copy with flock

🟡 Changes filesno sudo

flock takes the lock and runs the command in one atomic step. -n means “if busy, give up now” (exit 1); in a script, open the lock file on fd 9 with exec 9>file and lock that fd, so the whole script is protected and the lock ends with the process.

✓ Use it when
  • cron jobs
  • any shared file or resource
✗ Don’t use it when
  • network file systems (old NFS)

Syntax: exec 9> ~/ops/run/job.lock; flock -n 9 || { echo "already running"; exit 0; }

mkdir LOCKDIR · trap rmdir · stale check mkdir as a portable lock

🟡 Changes filesno sudo

mkdir creates a folder or fails if it exists, in one atomic system call, on every Unix and on NFS. Remove it with a trap on EXIT. Because a crash leaves it behind, store the owner’s PID inside and treat the lock as stale if that process no longer exists.

✓ Use it when
  • NFS, portability
  • when flock is missing
✗ Don’t use it when
  • forgetting the trap

Syntax: mkdir run/job.lockdir 2>/dev/null || { echo busy; exit 0; }; trap 'rm -rf run/job.lockdir' EXIT

Undo and safety net

Concurrency bugs corrupt data quietly; recover and prevent:

  • Corrupted shared file: restore from backup or rebuild from source data; add flock before the next run.
  • Job never runs (stale lock): with flock this cannot happen; with mkdir/PID locks check the owner (kill -0) and remove the stale lock.
  • Killed by timeout mid-write: write to a temp file and mv (Lesson 2.3) so a stop never leaves half a file.
  • Duplicates after a rerun: deduplicate, then make the step idempotent.

Error messages decoded

Errors students see most (really run on our build machine).

  1. cd ~/ops && exec 9> run/held.lock && flock -n 9 && echo 'got it' && flock -n run/held.lock true; echo "second flock: exit $?"
    got it second flock: exit 1 exit status: 0

    What it means: The same lock file is already held (by fd 9 of this shell): -n fails with 1.

    Fix: Wait (-w), skip, or find the holder: fuser run/held.lock.

  2. timeout 1 sleep 3; echo "exit $?"
    exit 124 exit status: 0

    What it means: 124 is not an error of sleep: it means timeout stopped it.

    Fix: Check for 124 separately.

  3. flock -n /nonexistent/dir/x.lock true
    flock: cannot open lock file /nonexistent/dir/x.lock: No such file or directory exit status: 66

    What it means: The lock file’s folder does not exist.

    Fix: mkdir -p the folder (e.g. /run/lock/myapp) first.

Quick check timeout returns 124. What happened?
Answer: The time limit was reached and timeout stopped the command.

6 Real-world use

Locks and timeouts at work

1. Overlapping cron jobs

Every */5 cron job that can run longer than 5 minutes is wrapped in flock -n; slow nights skip a run instead of piling up.

/5→flock -n→one copy

2. Deploys

Two engineers deploying at once is a classic outage; deploy scripts hold a lock for the whole release.

deploy→lock→serial

3. Backups over the network

rsync/scp steps run under timeout -k so a dead link does not block the next night.

rsync→timeout→next night ok

4. Package managers

apt and dpkg take locks (/var/lib/dpkg/lock-frontend): the “could not get lock” message you meet in Linux 14.2.

apt→lock→one at a time

5. Infrastructure as code

Ansible, Terraform and Puppet are built on idempotence: run them again and only differences change.

rerun→no change→safe

Examples are simplified and generic. They describe common patterns, not the internal systems of any particular company.

Script it: safe-job.sh

A cron-safe job: a flock on the whole script (skip quietly if already running), a timeout on the slow step, and idempotent setup, so overlaps, hangs and reruns are all harmless.

#!/usr/bin/env bash
set -euo pipefail
mkdir -p run out
exec 9> run/safe-job.lock
flock -n 9 || { echo "safe-job: already running, skipping" >&2; exit 0; }

mkdir -p out/reports                                   # idempotent
grep -qxF 'retention=30' out/settings 2>/dev/null || echo 'retention=30' >> out/settings

if timeout -k 1 2 bash -c 'sleep 0.3; echo "report built"'; then
  echo "safe-job: ok"
else
  rc=$?
  (( rc == 124 )) && echo "safe-job: report step timed out" >&2 || echo "safe-job: report step failed ($rc)" >&2
  exit "$rc"
fi
report built safe-job: ok

Run it twice at once and the second copy only says it is skipping.

Puzzle answer Remember the question from the story? Open to check your guess.

1. The check ([[ -e job.lock ]]) and the create (touch job.lock) are two separate steps: two copies can both see “no lock” before either creates it, which is the same race as the counter. 2. The rm job.lock at the end never runs after a crash or kill -9, so the file stays and every later run thinks the job is still running. flock fixes both: checking and taking the lock is one atomic kernel operation, and the kernel releases it when the process ends, however it ends.

Quick check Where should lock files live?
Answer: On a local disk, e.g. /run/lock or /var/lock (or a folder of your own), not on network file systems.

Quick revision

Lesson 3.2 in one screen

  • Race condition: copies read the same old value and overwrite each other’s updates; check-then-create locks race too.
  • flock does check-and-take atomically and the kernel releases it on exit (even kill -9).
  • flock -n (skip), -w N (wait with a limit), -s/-x (shared/exclusive), -u (unlock early); exec 9>file; flock -n 9 for a whole script.
  • mkdir and set -C are atomic portable locks but need a trap and stale checks (kill -0 PID).
  • timeout N cmd → 124 on timeout; -k adds KILL; SECONDS for whole-script deadlines.
  • Make steps idempotent: mkdir -p, ln -sfn, add-once, done-markers, > not >>.

Interview and viva questions

How do I prevent a cron job from running twice?

Wrap it with flock: flock -n /run/lock/job.lock /path/job.sh.

What is flock in Linux?

A command (and system call) that takes an advisory lock on a file; the kernel releases it when the process exits.

How do I make a script run only one instance?

At the top: exec 9>/run/lock/name.lock; flock -n 9 || exit 0.

How do I stop a command after a time limit?

timeout 30 cmd; it exits 124 if the limit was reached; add -k to force KILL.

Why is my lock file not removed after a crash?

File-existence locks are not released automatically; use flock, or check the owner PID and remove stale locks.

What is a race condition?

A bug where the result depends on timing between processes, such as two copies updating the same file.

What does idempotent mean in scripting?

Running the step again gives the same result, so reruns are safe.
