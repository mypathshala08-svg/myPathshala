Comments, keywords and naming conventions

Code is read far more often than it is written. Good names and useful comments make a program easy to understand; bad ones make even correct code hard to work with. In this lesson you'll learn the three kinds of comments, which words Java reserves, the rules for naming things, and the conventions every Java team expects.

2 Definition

Comments, keywords and identifiers

Formal definition (write this in exams)

A comment is text in source code that the compiler ignores; Java has single-line (//), multi-line (/* */) and documentation (/** */) comments. A keyword is a word reserved by the language with a predefined meaning, which cannot be used as an identifier. An identifier is a name given to a class, interface, method, variable, constant or package; it must start with a letter, _ or $, may contain digits after that, is case-sensitive, and must not be a reserved keyword or the literals true, false or null.

In simple words

Comments are notes for people. Keywords are Java's own words, like class and int, which you can't borrow as names. Identifiers are the names you choose, and conventions are the team habits for how those names should look.

Exam tip: true, false and null are literals, not keywords, but you still can't use them as names. goto and const are reserved keywords that Java doesn't use. Identifiers are case-sensitive: total, Total and TOTAL are three different names.

3 Types and ways to use it

Kinds of comments and keywords

Single-line //

From // to the end of the line. Best for short notes explaining why: // GST is added after the discount, as per policy.

Most used

Multi-line /* */

Spans several lines. Useful for a longer explanation. Can't be nested: /* /* */ */ breaks.

Longer notes

Javadoc /** */

Above a class or method. Tags like @param, @return and @throws describe the method. The javadoc tool and IDEs read them.

Why contextual keywords? When Java added var (Java 10) and record (Java 16), making them fully reserved would have broken old programs that used them as variable names. So int var = 5; still compiles, but a class can no longer be named record.

4 Step by step

How javac reads names and comments

  1. Unicode escapes are translated first

    Before anything else, javac turns \uXXXX sequences into characters, everywhere, even inside comments.

    That's why the famous trick // \u000a System.out.println("hi"); actually runs: \u000a becomes a newline, ending the comment early.

  2. Comments and whitespace are removed

    The lexer skips spaces, tabs, newlines and all three kinds of comments.

    Nothing from a comment reaches the .class file. Comments cost nothing at run time, so there's no performance reason to avoid them.

  3. Each word is classified

    Is it a keyword, a literal (42, "hi", true), an operator, or an identifier?

    Reserved keywords always win. int new = 5; fails because new is read as the keyword, and the grammar then doesn't make sense.

  4. Identifiers are checked against the rules

    Must not start with a digit; may use letters from any language (int नाम = 7; is legal), _ and $.

    Names are stored in the class file's constant pool (for classes, methods and fields), so renaming a public method changes the bytecode other classes link to.

  5. Conventions are checked by people and tools

    javac doesn't enforce PascalCase or camelCase. Code reviewers, IDE inspections and tools like Checkstyle do.

    The javadoc tool reads /** */ comments separately and generates HTML pages, like the official Java API documentation.

  1. A few lines of code with a single-line and a multi-line comment.

  3. Names can't start with a digit, and can't be a reserved keyword like new.

Behind the screen
  1. javac's lexer reads the source one character at a time.
  2. Comments and whitespace are discarded. The rest becomes tokens: keywords, identifiers, literals and symbols.
  3. A name starting with a digit splits into a number and a word; a reserved keyword can't be a name.
  4. Contextual keywords are only special in certain positions. Identifiers may use Unicode letters.
  5. The javadoc tool turns /** */ comments and their tags into HTML documentation.
  6. Each kind of name has its own convention, so readers can tell what something is from its shape.
6 Real-world use

Names and comments in real teams

In companies, readable code is a requirement, not a preference. Here's how it's enforced and why.

Watch it with an example: a code review on a fee program

The code works but nobody can read it. Watch a reviewer fix one problem per step using Java's naming conventions.

Same code, readable names 6 steps
Animated example
  1. Before: this compiles and gives the right answer, but a teammate has to guess what fee, m, a and x mean.
  2. Class name: class names start with a capital letter and are nouns: FeeCalculator.
  3. Constant: static final values use capitals with underscores: MAX_INSTALMENTS.
  4. Method and parameter: camelCase, and say what they are: monthlyFee(int annualFee).
  5. Comment: say why the code does something. The compiler throws comments away; they are only for humans.
  6. Package: lowercase, often a reversed domain such as in.college.fees, so names never clash with other teams' classes. Tools like Checkstyle check these rules automatically in code review.

1. Code reviews

Every change is reviewed by teammates before merging. Unclear names and missing explanations for tricky logic are among the most common review comments.

Pull request→“Rename x1 to retryCount”→Merged

2. Automated style checks

Tools like Checkstyle, SonarQube and IDE inspections flag naming violations and missing Javadoc automatically in the build, so humans can focus on logic.

git push→Checkstyle / Sonar→Naming warnings

3. Library and API documentation

The official Java API docs, and the docs of libraries like Spring, are generated from Javadoc comments. Companies publish internal API docs the same way.

/** … */→mvn javadoc:javadoc→HTML docs site

4. TODO and FIXME markers

Developers mark unfinished work with // TODO and known problems with // FIXME. IDEs list them, and teams track them so they don't stay forever.

// TODO: add retry→IDE TODO list→Ticket in the backlog

5. Package names that never clash

Using your organisation's domain in reverse (com.myphatshala…) keeps package names unique worldwide, so two libraries can both have a class called Utils without conflict.

myphatshala.in→com.myphatshala.billing→Unique names

Examples are simplified. Each team has its own style guide; many follow Google's or Oracle's Java conventions.

7 Run the code

Riya's bill calculator, written properly

/**
 * Calculates a canteen bill.
 */
public class Main {
    static final int GST_PERCENT = 5;   // constant: UPPER_SNAKE_CASE

    public static void main(String[] args) {
        int chaiCount = 3;               // variable: camelCase
        int billAmount = calculateBill(chaiCount);
        System.out.println("Bill: Rs " + billAmount);
    }

    /** Returns the bill for the given number of cups, including GST. */
    static int calculateBill(int cups) {
        int base = cups * 20;
        return base + base * GST_PERCENT / 100;
    }
}
Bill: Rs 63
  • /** Calculates a canteen bill. */A Javadoc comment for the class.
  • GST_PERCENTA static final constant, so UPPER_SNAKE_CASE.
  • chaiCount, billAmountVariables in camelCase that say what they hold.
  • calculateBill(int cups)A method named with a verb, in camelCase.
  • // constant: …Single-line comments. Real code should explain why, not repeat what; these are here for learning.

9 Quiz and revision

Check yourself

Quick revision

Lesson 2.7 in one screen

  • Comments: // single-line, /* */ multi-line, /** */ Javadoc (@param, @return, @throws). javac discards them.
  • About 50 reserved keywords; goto/const unused; var, record, yield are contextual.
  • Identifiers: letters, digits, _, $; no digit first; no keywords or true/false/null; case-sensitive.
  • Conventions: PascalCase classes, camelCase methods and variables, UPPER_SNAKE_CASE constants, lowercase packages (reverse domain).
  • Comment the why; let names explain the what.

Interview and viva questions

What are the types of comments in Java?

Single-line (//), multi-line (/* … */) and documentation comments (/** … */). Documentation comments are processed by the javadoc tool to generate HTML API documentation.

Is main a keyword?

No. main is an ordinary identifier; it's just the name the launcher looks for. You could even have a variable called main.

Why does Java reserve goto if it doesn't use it?

To prevent programmers coming from C and C++ from using it, and to keep the option open. Using goto in Java gives a compile error.

What makes a good comment?

It explains intent, reasons or non-obvious constraints (“rounding is done per line item, as required by the tax rules”) rather than repeating what the code says (“add 1 to i”). Outdated comments are worse than none, so update them with the code.

Can identifiers contain Unicode letters?

Yes. Java identifiers may use letters from any language, such as Devanagari or Chinese. Team code usually sticks to English ASCII names for readability and tooling.

P6Business problem

Clear invoice calculation

Compute an invoice: unit price 250, quantity 6, discount 5%, GST 18%, with clear names and constants.

Input
250, 6
Expected output
Invoice total: Rs 1682
Show solution and explanation 
public class Main {
    static final double DISCOUNT_RATE = 0.05;
    static final double GST_RATE = 0.18;

    public static void main(String[] args) {
        double unitPrice = 250;
        int quantity = 6;
        double subtotal = unitPrice * quantity;
        double afterDiscount = subtotal * (1 - DISCOUNT_RATE);
        double invoiceTotal = afterDiscount * (1 + GST_RATE);
        System.out.println("Invoice total: Rs " + Math.round(invoiceTotal));
    }
}
Invoice total: Rs 1682

P7Business problem

Document a rule

Add a comment explaining why late fees are capped, and compute the fee: Rs 10/day, at most Rs 100, for 14 days late.

Input
14 days
Expected output
Late fee: Rs 100
Show solution and explanation 
public class Main {
    static final int FEE_PER_DAY = 10;
    // Library rule: late fees are capped so students aren't charged more than a book's typical cost.
    static final int MAX_LATE_FEE = 100;

    public static void main(String[] args) {
        int daysLate = 14;

Real-world scenario questions (asked in company interviews)

Readability problems are maintenance problems, and maintenance is most of a developer's job. Decide your answer first, then open the model answer.

Tax software · bug investigationFresher

The comment says 18%, the code says 12%

While fixing a bug, you find // apply 18% GST directly above amount * 0.12. Finance says the correct rate for this product is 12%. What does this tell you, and what would you do?

The interviewer is checking: do you understand that comments can go stale, and how to make code self-explaining?

Show a strong answer

The code was updated but the comment wasn't, so the comment is now actively misleading. javac never checks comments, so this happens easily.

  • Confirm the correct behaviour with finance (here, the code is right).
  • Replace the magic number and the comment with a named constant or configuration value, e.g. GST_RATE_REDUCED, so the code explains itself.
  • Keep only comments that explain why (for example, the rule or notification behind the rate), and update comments in the same change as the code.

Avoid: “fixing” the code to match the comment without checking.

Any company · code reviewFresher

200 lines of commented-out code

A class contains large blocks of old code commented out “in case we need it later”. Your reviewer asks you to delete them. A teammate is nervous that the code will be lost. How do you respond?

The interviewer is checking: do you know that version control keeps history, and why dead code hurts?

Show a strong answer
  • Git already keeps every old version. The code can be found with git log or the IDE's history, so deleting it loses nothing.
  • Commented-out code confuses readers (is it important? is it a bug?), goes stale as the rest of the code changes, and clutters searches.
  • If something might be needed, link the commit or create a ticket explaining why, instead of keeping the code inline.

Avoid saying: “Comments don't affect the program, so it's harmless.”

Enterprise · Java upgrade1–3 years

Old code stopped compiling after the upgrade

While upgrading a legacy project from Java 8 to Java 21, the build fails in a few files: one uses _ as a variable name, another has a class named record. The code was fine for years. Why, and how would you handle it?

The interviewer is checking: do you know that new Java versions add keywords, and how to fix this safely?

Show a strong answer

Newer Java versions reserved new words. _ became a keyword in Java 9 (and is now used for unnamed variables), and record became a restricted name for types in Java 16. Old code using them as names no longer compiles.

  • Rename them with the IDE's Rename refactoring, so every usage is updated.
  • If the class is part of a public API used by other systems, coordinate the rename with those teams.
  • Compile with the target JDK early in the upgrade to find all such issues at once.

Avoid: staying on Java 8 just because of a few names.

Product company · internal library1–3 years

Nobody uses your library correctly

You wrote a shared payment-validation library. Other teams keep calling validate(String s, int t) with the wrong arguments and asking you questions on chat. What would you improve?

The interviewer is checking: do you treat names and Javadoc as part of an API's design?

Show a strong answer
  • Rename for clarity: validateUpiId(String upiId, int maxLength), or better, use types that can't be mixed up.
  • Add Javadoc to every public method: what it does, each @param, the @return value and every @throws, with an example.
  • Publish the generated Javadoc (and a short README) so IDEs show it on hover.
  • Deprecate the old method with @Deprecated and point to the new one, rather than breaking callers suddenly.

Avoid saying: “They should read the source.”
