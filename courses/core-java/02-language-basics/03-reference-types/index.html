Reference types and how they differ

Primitive variables hold their value directly. Everything else in Java (strings, arrays, lists, your own classes) is a reference type: the variable holds an arrow to an object somewhere on the heap. This one idea explains shared changes, == vs equals, and Java's most famous error, NullPointerException.

1 The story

The shared shopping list

Riya and Kabir are organising snacks for the class party. Riya makes a list and gives Kabir “her list” in the program. Kabir adds samosas. When Riya prints her list, the samosas are there too, even though she never touched it. She's confused.

Riya

Sir, I wrote kabirList = list. Shouldn't Kabir get his own copy?

Arjun Sir

For an int, yes: the number is copied. But a list is an object. Your variable doesn't hold the list; it holds the address of the list, like a WhatsApp location pin. When you copied the variable, you copied the pin, not the house.

Riya

So we both have pins to the same house, and Kabir put samosas inside it!

Arjun Sir

Exactly. That's a reference. Let's see where the house and the pins live in memory.

2 Definition

What is a reference type?

Formal definition (write this in exams)

A reference type is any type that is not one of the eight primitives: classes (such as String), interfaces, arrays, enums and records. A variable of a reference type stores a reference to an object allocated on the heap, or the special value null, meaning it refers to no object. Assigning one reference variable to another copies the reference, not the object, so both refer to the same object.

In simple words

Primitive box: the value is inside. Reference box: an arrow is inside, pointing to an object that lives elsewhere (the heap). Copying the box copies the arrow. null means the arrow points nowhere.

Words you'll meet in this lesson

ObjectA bundle of data and behaviour created with new, stored on the heap.
ReferenceA value that identifies an object, like an address or pin. You can't see or do arithmetic on it.
HeapThe JVM memory area where all objects live, shared by the whole program.
AliasingTwo or more variables referring to the same object.
nullA reference to nothing. Using it like an object causes NullPointerException.
equals()A method that compares the contents of objects, unlike ==, which compares references.

Exam tip: Java is always pass-by-value, even for objects: what gets copied is the value of the reference (the arrow). That's why two variables can share an object. Also: use equals(), not ==, to compare the text of two Strings.

4 Step by step

From new to garbage: the life of an object

  1. Declare a reference variable

    StringBuilder list;
    A slot is created on the stack that can hold a reference. No object exists yet.

  2. Create an object with new

    list = new StringBuilder("chai");
    new asks the JVM for memory on the heap, builds the object (running its constructor) and returns its reference, which is stored in list.

  3. Use it through the reference

    list.append(", samosa");
    The dot means “follow the arrow, then call the method on that object”. The object on the heap changes; the reference in list stays the same.

  4. Share it

    StringBuilder kabirList = list;
    Only the reference is copied. Now two arrows point to one object. A change through either variable is visible through both.

  5. Let it go

    list = null;
kabirList = null;
    Once no reference points to the object, it's unreachable. The garbage collector frees its memory later. You never delete objects yourself.
5 See it happen

Values vs arrows: both views

Left: the code and what prints. Right: the stack and the heap.

Riya's shared list 6 steps
What you see
  1. With primitives, b = a copies the number. Changing b leaves a at 10.
  2. new StringBuilder("chai") creates an object; list refers to it.
  3. kabirList = list looks like a copy, but no new object is created.
  4. Kabir appends “samosa”, and printing Riya's list shows it too.
  5. Two Strings with the same text: == says false, equals says true.
  6. After list = null, calling list.length() throws a NullPointerException.
Behind the screen
  1. Two primitive variables are two separate boxes on the stack. The heap isn't involved.
  2. new puts a StringBuilder object (#1) on the heap. list on the stack holds an arrow to it.
  3. kabirList = list copies the arrow. Two variables now alias one object.
  4. append follows the arrow and changes object #1. Both variables see the change.
  5. Each new String makes a separate object. == compares the arrows; equals compares the contents.
  6. list now holds null. There's nothing to follow, so the JVM throws NullPointerException.
6 Real-world use

References in real applications

Almost every value in a business application is an object. Understanding references prevents some of the most common production bugs.

Watch it with an example: a customer with no address

A delivery app stores each customer as an object. One customer skipped the address field. Follow the references and see where the famous NullPointerException comes from.

Following a reference to nowhere 5 steps
Animated example
  1. Create: new Customer("Kabir") makes object #1 on the heap. The variable c on the stack holds a reference (an arrow) to it.
  2. Missing data: the address field is a reference too, but nobody set it, so it holds null: an arrow that points to no object.
  3. Crash: c.address.city follows c to #1 (fine), then tries to follow address, which leads nowhere. Java throws NullPointerException and names the null part.
  4. Fix: check c.address != null before following it.
  5. Result: the app shows “Add address” instead of crashing. Null checks at the edges (forms, APIs, database rows) prevent most NPEs in production.

1. One customer object, many screens

An app loads a Customer object once. The profile screen, order screen and support screen all hold references to the same object, so an address update is seen everywhere without copying.

Load customer→many references, one object→Consistent screens

2. NullPointerException in production

A missing middle name, an absent coupon or an unlinked bank account often arrives as null. Calling a method on it is one of the most common causes of crashes in Java services, which is why teams check for null, use Optional (Module 14) and validate inputs.

API request without coupon→coupon == null?→Handle safely

3. Comparing text from users and APIs

Strings arriving from a web form or a JSON request are new objects. Comparing them with == fails even when the text matches, so code always uses equals (or equalsIgnoreCase).

paymentMode from request→"UPI".equals(paymentMode)→Correct branch

4. Caches

Caches store references to frequently used objects (like product details) so they don't need to be loaded from the database again. If code modifies a cached object by accident, every user sees the wrong data, which is why cached objects are often made immutable.

Product request→cache returns same object→Fast response

5. Memory leaks through forgotten references

The garbage collector frees only objects that nothing refers to. A list that keeps references to every old session “just in case” keeps them alive forever, and memory slowly fills up. That's a memory leak, even in Java.

static list keeps adding→objects stay reachable→OutOfMemoryError

Examples are simplified to show where references matter. Real designs vary.

7 Run the code

Shared objects, == and equals

public class Main {
    public static void main(String[] args) {
        StringBuilder list = new StringBuilder("chai");
        StringBuilder kabirList = list;          // same object
        kabirList.append(", samosa");
        System.out.println("Riya's list: " + list);

        String s1 = new String("hi");
        String s2 = new String("hi");
        System.out.println(s1 == s2);            // same object?
        System.out.println(s1.equals(s2));       // same text?

        String coupon = null;
        System.out.println("Coupon present: " + (coupon != null));
    }
}
Riya's list: chai, samosa false true Coupon present: false
  • new StringBuilder("chai")Creates an object on the heap. list holds its reference.
  • StringBuilder kabirList = list;Copies the reference: no new object.
  • kabirList.append(…)Changes the shared object, so list sees the change.
  • s1 == s2Are they the same object? No: two new calls, two objects.
  • s1.equals(s2)Is the text the same? Yes.
  • coupon != nullChecking for null before using a reference is a common safety habit.

9 Quiz and revision

Check yourself

Quick revision

Lesson 2.3 in one screen

  • Reference types: classes, interfaces, arrays, enums, records. Everything except the 8 primitives.
  • Variable holds an arrow; the object lives on the heap.
  • b = a copies the arrow → aliasing: changes through one are seen by the other.
  • == = same object? equals() = same contents?
  • null = no object. Calling a method on it → NullPointerException.
  • Unreachable objects are freed by the GC; you never delete objects yourself.
  • Java is always pass-by-value; for objects, the reference is the value.

Interview and viva questions

What is the difference between primitive and reference types?

Primitives hold their value directly and have no methods; there are exactly eight. Reference types hold a reference to an object on the heap (or null), objects can have fields and methods, and assignment copies the reference rather than the object.

Does Java have pointers?

Java has references, which are like safe pointers: you can store, copy and compare them, but you can't see the address, do arithmetic on it, or turn a number into a reference. The JVM manages the actual addresses and can move objects during garbage collection.

Why does "a" == "a" sometimes return true?

Identical string literals are stored once in the string pool, so both refer to the same object and == is true. Strings built at run time (new String, user input, concatenation of variables) are usually separate objects. Never rely on == for text; use equals().

How do you avoid NullPointerException?

Initialise variables, validate inputs, check x != null before use, call equals on the known non-null side ("UPI".equals(mode)), return empty collections instead of null, and use Optional for values that may be absent.

How do you make a real copy of an object?

Create a new object with the same contents: a copy constructor (new StringBuilder(list)), clone() for arrays, or copy methods such as List.copyOf. For objects containing other objects, decide between a shallow and a deep copy.

Real-world scenario questions (asked in company interviews)

Reference bugs are subtle: the code compiles and often works in testing. Decide your answer first, then open the model answer.

Payments · production bugFresher

UPI payments routed to the wrong handler

A payment service checks if (request.getMode() == "UPI"). In unit tests with hard-coded strings, it works. In production, every UPI payment goes to the “unsupported mode” branch. Why?

The interviewer is checking: do you know the difference between == and equals for Strings, and why tests passed?

Show a strong answer

In tests, both sides were string literals, which share one pooled object, so == happened to be true. In production, the mode comes from parsed JSON: a new String object with the same text. == compares references, so it's false.

  • Fix: "UPI".equals(request.getMode()). Putting the literal first also avoids a NullPointerException if the mode is missing.
  • Better still, convert the input to an enum (PaymentMode.UPI) at the API boundary.
  • Static analysis tools flag == on Strings; enable them in the build.

Avoid saying: “Java compares strings by value with ==.”

Travel booking · APIFresher

NullPointerException for some bookings

A booking API crashes for about 2% of requests with NullPointerException: Cannot invoke "java.lang.String.trim()" because the return value of "Passenger.getMiddleName()" is null. What would you do?

The interviewer is checking: can you read a modern NPE message and fix the root cause sensibly?

Show a strong answer

The message says exactly what happened: getMiddleName() returned null (many passengers have no middle name) and the code called trim() on it.

  • Decide what “no middle name” should mean: usually an empty value. Handle it where the name is read, for example middleName == null ? "" : middleName.trim().
  • Look for the same pattern elsewhere: any optional field from the client can be null.
  • Validate at the API boundary and document which fields are optional.
  • Add a test with a passenger who has no middle name.

Avoid: wrapping the whole method in catch (NullPointerException e).

E-commerce · pricing1–3 years

A discount that leaked to every customer

Product objects are cached in memory. For a VIP customer, a developer wrote Product p = cache.get(id); p.setPrice(p.getPrice() * 0.9); before showing the price. Soon all customers see the discounted price, and it keeps dropping. What's wrong?

The interviewer is checking: do you understand aliasing with shared cached objects?

Show a strong answer

cache.get(id) returns a reference to the shared cached object, not a copy. Calling setPrice changes that object for everyone, and every VIP request applies another 10% on top.

  • Never modify shared objects for one request. Calculate the VIP price in a local variable or a separate price object.
  • Make cached objects immutable (no setters, or records), so this mistake can't compile.
  • If a modified version is needed, create a copy explicitly.

Avoid: “Clear the cache every few minutes.” That hides the bug instead of fixing it.

SaaS · operations1–3 years

Memory keeps growing until the server crashes

A service's memory use grows slowly all week until it crashes with OutOfMemoryError. A developer says, “Impossible, Java has a garbage collector.” You find a static List<Session> allSessions that adds every user session and never removes any. Explain.

The interviewer is checking: do you know that the GC only frees unreachable objects?

Show a strong answer

The garbage collector frees objects only when nothing refers to them. The static list lives as long as the application and holds a reference to every session, so none of them can ever be collected. That's a memory leak.

  • Remove sessions when they end, or don't keep them in a long-lived list at all.
  • Use a cache with size limits and expiry (for example Caffeine) if keeping them is really needed.
  • Confirm with a heap dump: tools like Eclipse MAT show which objects keep others alive.

Avoid saying: “Just increase the heap size.” That only delays the crash.
