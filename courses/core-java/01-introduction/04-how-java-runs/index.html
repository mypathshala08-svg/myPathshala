How Java code runs: source → bytecode → JVM

You type javac, then java, and text appears. Between those two commands, your program is checked, turned into bytecode, loaded, verified, interpreted and finally compiled to machine code while it runs. This lesson follows one small program through every stage, using the real bytecode that javac produces.

Module 1 · Introduction to Java⏱ 18 minBeginnerNo install needed8 practice problems
1 The story

What happens to ₹20 × 3?

At the college canteen, Riya buys three cups of chai at ₹20 each and writes a tiny Java program to print the bill. It prints Total: Rs 60, as expected. Then Arjun Sir asks her a question she's never thought about.

Arjun Sir

Riya, your CPU understands only machine code: tiny instructions like “multiply these two registers”. It has never heard of int or println. So who turned price * cups into something the CPU could do?

Riya

Hmm… javac? It turns my code into bytecode.

Arjun Sir

That's half the answer. Bytecode isn't machine code either. Two more translators work behind the screen: the JVM's interpreter, and its JIT compiler. Today we'll look at the real bytecode of your chai bill, instruction by instruction.

Riya

We can actually see bytecode?

Arjun Sir

With one JDK command: javap -c. Let's go.

2 Definition

How does a Java program run?

Formal definition (write this in exams)

A Java program runs in two stages. At compile time, the Java compiler (javac) checks the source code (.java) and translates it into platform-independent bytecode stored in .class files. At run time, the JVM's class loader loads the class files, links them (verification, preparation, resolution) and initialises them, and the execution engine runs the bytecode by interpreting it and JIT-compiling frequently used parts into native machine code.

In simple words

Step 1: javac checks your code and writes it in a simpler universal language, bytecode. Step 2: java starts the JVM, which loads the bytecode, checks it's safe, and runs it. At first it reads instructions one by one (interpreting). If some code runs again and again, the JVM translates it into your CPU's own machine code so it runs much faster (JIT).

Words you'll meet in this lesson

Compile timeEverything javac does, before the program runs. Errors here are compile-time errors.
Run timeEverything that happens while the JVM is executing the program. Errors here are exceptions.
OpcodeOne bytecode instruction, such as iload, imul or return. Each takes one byte.
Operand stackA small scratch stack inside each method's frame, where bytecode pushes and pops values while calculating.
Constant poolA table inside every .class file holding names, strings and numbers the bytecode refers to.
JIT compilerJust-In-Time compiler: turns frequently run bytecode into machine code while the program runs.

Exam tip: “Java is both compiled and interpreted.” Write it with the two stages: compiled by javac into bytecode, then interpreted and JIT-compiled by the JVM. Also list the three class-loading phases in order: loading, linking, initialization, and the three parts of linking: verify, prepare, resolve.

Four ways to run Java code

javac + java

The classic two steps: compile to .class, then run. Used for real projects (via build tools like Maven and Gradle).

Standard

java Main.java

Since Java 11, single-file programs can be run directly. Java compiles in memory, without writing a .class file.

Quick practice

java -jar app.jar

Many .class files packed into one .jar with a manifest naming the main class. This is how most applications ship.

Deployment

jshell

An interactive prompt (Java 9+). Type one line, see the result immediately. Great for trying things out.

4 Step by step

Follow the chai bill through every stage

  1. Write the source

    public class Main {
    public static void main(String[] args) {
        int price = 20;
        int cups = 3;
        int total = price * cups;
        System.out.println("Total: Rs " + total);
    }
}
    Total: Rs 60
    On disk this is just characters. Nothing has been checked yet.

  2. Compile it

    javac Main.java
    javac runs its four phases: tokens → syntax tree → type and name checks → bytecode. Silence means success, and Main.class (861 bytes with JDK 21) appears.

  3. Look at the bytecode

    javap -c Main
    public static void main(java.lang.String[]); Code: 0: bipush 20 2: istore_1 3: iconst_3 4: istore_2 5: iload_1 6: iload_2 7: imul 8: istore_3 9: getstatic #7 // Field java/lang/System.out 12: iload_3 13: invokedynamic #13 // makeConcatWithConstants 18: invokevirtual #17 // Method java/io/PrintStream.println 21: return
    Each line is one instruction. bipush 20 pushes 20 onto the operand stack, istore_1 stores it in local variable slot 1 (price), imul multiplies the top two values. The numbers on the left are byte offsets. javap also shows a Main() constructor that javac added for you.

  4. Run it

    java Main
    Total: Rs 60
    The JVM starts and loads hundreds of core classes (about 540 for this program on JDK 21) before Main itself. You can watch them with java -Xlog:class+load Main. Then Main is linked, initialised and main is interpreted.

  5. Hot code gets compiled

    Our chai bill runs once, so it is simply interpreted. But if a method runs thousands of times, as in a server handling requests, the JIT steps in.

    HotSpot uses tiered compilation: a quick compiler (C1) compiles warm methods first, and an optimising compiler (C2) recompiles the hottest ones with deeper optimisations. You can watch it with java -XX:+PrintCompilation Main.
5 See it happen

From keyboard to CPU: both views

Step through each stage. Left: what Riya sees. Right: what javac and the JVM are doing.

The life of the chai bill program 6 steps
What you see
  1. Riya writes the chai bill program and saves it as Main.java.
  2. She runs javac Main.java. No message appears, which means it compiled.
  3. javap -c Main shows the bytecode: simple instructions like bipush, istore and imul.
  4. She runs java Main. For a moment nothing visible happens.
  5. Total: Rs 60 is printed.
  6. If the same code runs crores of times, later rounds get much faster even though nothing in the code changed.
Behind the screen
  1. The saved file is just a sequence of characters. Neither the CPU nor the JVM can run it yet.
  2. javac splits it into tokens, builds a syntax tree, checks names and types, and generates bytecode.
  3. The .class file has a fixed layout: the CAFEBABE magic number, the version (65 = Java 21), the constant pool and the methods' bytecode.
  4. The JVM loads core classes and then Main, links it (verify, prepare, resolve) and initialises it.
  5. The interpreter executes each opcode using the method's local variables and operand stack: push 20, push 3, multiply, store 60.
  6. Code that runs often is JIT-compiled, first by C1 and then by C2, into real machine code that is cached and reused.

6 Real-world use

Where this pipeline matters at work

Knowing what happens between javac and the CPU helps you build, deploy and speed up real systems.

Watch it with an example: the JIT warms up a busy method

A billing server calls gst(price) again and again. Watch the JVM start by interpreting it, then compile it to machine code once it becomes “hot”.

Interpreter first, JIT later 5 steps
Animated example
  1. First call: the JVM's interpreter runs the bytecode of gst() instruction by instruction. It starts quickly but runs slowly.
  2. Counting: the JVM counts how often each method runs. After thousands of calls, gst() is marked as a hot method.
  3. JIT: the Just-In-Time compiler translates the bytecode of gst() into native machine code for this CPU, in the background.
  4. From now on: calls go straight to the machine code. Each call is many times faster than interpreting.
  5. Result: servers often run slower in the first minutes (warm-up) and then speed up. Numbers here are illustrative; real thresholds depend on the JVM.

1. Build tools: Maven and Gradle

In real projects nobody types javac for each file. Maven or Gradle compile hundreds of classes, run tests, and pack the .class files into a .jar. Underneath, they use the same compiler.

src/*.java→mvn package (javac inside)→app.jar

2. Warm-up before traffic

A freshly started Java service is slower for its first requests, because the code is still being interpreted. Teams often send some warm-up requests, or roll out new versions gradually, before full traffic arrives.

Deploy→Interpreted, then JIT-compiled→Full speed

3. Reading bytecode to debug libraries

When a library behaves strangely and you don't have its source, javap or the IDE's decompiler shows what its bytecode really does. Developers also check bytecode versions when they see “class file version” errors.

Unknown .class→javap -c / decompiler→Understand the bug

4. Tools that rewrite bytecode

Frameworks such as Spring and Hibernate, and monitoring agents used by observability tools, generate or modify bytecode at run time, for example to add logging or timing around your methods. This works because bytecode is a well-defined format.

Your class→Agent adds timing bytecode→Dashboards

5. Fast start-up for cloud functions

Serverless functions start and stop often, so JIT warm-up matters a lot. Options include Class Data Sharing (pre-processed core classes, shown as “sharing” in java -version) and GraalVM native image, which compiles ahead of time.

Cold start→CDS / native image→Faster first response

Examples are simplified to show where each stage fits. Real setups vary by company.

9 Quiz and revision

Check yourself

Quick revision

Lesson 1.4 in one screen

  • Compile time: javac: lexical analysis → parsing → semantic analysis → bytecode generation → .class.
  • .class file: CAFEBABE, version (65 = Java 21), constant pool, fields, methods. View with javap -c.
  • Run time: class loader loads → links (verify, prepare, resolve) → initialises (static blocks).
  • Execution: interpreter runs opcodes using local variable slots and the operand stack.
  • JIT: hot methods → C1 (quick) → C2 (optimised) machine code. That's warm-up.
  • Compile-time errors stop javac (no .class). Run-time errors are exceptions thrown by the JVM.
  • Ways to run: javac+java, java Main.java, java -jar, jshell.

Interview and viva questions

Explain the steps of executing a Java program.

Write source in a .java file → compile with javac into bytecode in a .class file → run with java: the class loader loads the class, the verifier checks it, statics are prepared and initialised → the execution engine interprets bytecode and JIT-compiles hot code into machine code → the garbage collector manages memory throughout.

What is the difference between the interpreter and the JIT compiler?

The interpreter executes bytecode one instruction at a time, which starts quickly but runs slower. The JIT compiler translates a whole frequently used method into native machine code once and caches it, so later calls run at near-native speed. HotSpot uses both: interpret first, then compile what's hot.

What is bytecode, and why not compile straight to machine code?

Bytecode is a compact instruction set for the JVM. Because it isn't tied to any CPU, the same .class file runs on every platform, and the JVM can optimise it for the actual machine at run time, using information (such as which code is hot) that isn't known at compile time.

What does the bytecode verifier check?

That the class file is well-formed, that instructions use values of the right types (no treating an int as an object reference), that the operand stack never overflows or underflows, that jumps go to valid instructions, and that access rules are respected. It runs during linking, before any code executes.

Can we run a Java program without compiling it with javac?

Since Java 11, java Main.java runs a single-file program directly, but it still compiles: the launcher compiles the source in memory first. Bytecode is always produced; it just isn't saved to disk.

Real-world scenario questions (asked in company interviews)

Real problems where knowing the compile → load → run pipeline makes the difference. Decide your answer first, then open the model answer.

E-commerce · after deployment1–3 years

“The first few hundred requests are slow”

After every deployment of the checkout service, the first few minutes show high response times and a few timeouts, then everything becomes fast. Nothing in the code is slow. Your manager asks why, and what can be done.

The interviewer is checking: do you know about JVM warm-up (interpreter → JIT), and practical ways to handle it?

Show a strong answer

This is JVM warm-up. A new JVM starts by interpreting bytecode and loading classes on first use. Only after code has run many times does the JIT compile it to optimised machine code. Caches and connection pools are also empty at first.

  • Use readiness checks plus a warm-up step that calls the main endpoints before the instance receives real traffic.
  • Roll out gradually: shift traffic to new instances a little at a time.
  • Pre-fill connection pools and caches at start-up.
  • Consider Class Data Sharing (AppCDS) to speed up class loading, or a GraalVM native image if start-up time is critical.

Avoid saying: “Java is just slow at the start, nothing can be done.”

Any company · production bugFresher

NoClassDefFoundError in production, but it compiled fine

The project compiles and all tests pass on your laptop. On the server, one feature fails with java.lang.NoClassDefFoundError: com/fasterxml/jackson/databind/ObjectMapper. A teammate says, “Impossible, it compiled!”

The interviewer is checking: do you understand that compile time and run time are separate, and that classes are loaded lazily at run time?

Show a strong answer

Compiling only proves the class was available to javac. At run time, the JVM's class loader must find the class again on the runtime classpath, and it only tries when the code first needs it. That's why only one feature fails.

  1. Check whether the dependency (here, Jackson) is actually inside the deployed jar or on the server's classpath. jar tf app.jar lists the jar's contents.
  2. Check the build: was the dependency marked provided or test scope in Maven, so it wasn't packaged?
  3. Fix the packaging (for example build a “fat jar” with Spring Boot or the Maven Shade plugin), redeploy and retest that feature.

Avoid: confusing this with ClassNotFoundException, or copying random jar files onto the server until the error goes away.

Banking · code reviewFresher

A static block that slows down start-up

In a code review you see a class RateTable whose static { } block downloads the latest interest rates over the network. Sometimes the application hangs for a long time when a customer first opens the loans page. Why does it happen at that moment, and what would you suggest?

The interviewer is checking: do you know when class initialisation happens, and the risks of doing heavy work in static blocks?

Show a strong answer

A static block runs during class initialisation, which happens the first time the class is actively used, here when the loans page first touches RateTable. That request waits for the whole download. If the download throws an exception, the class fails to initialise and later uses fail with NoClassDefFoundError.

  • Move the network call out of the static block into a normal service method with a timeout and error handling.
  • Load the rates at application start-up (or on a schedule) and cache them, with a sensible fallback if the download fails.
  • Keep static blocks for simple, fast, failure-free setup only.

Avoid saying: “Static code runs when the program starts.” It runs when the class is first used.

Startup · performance testing1–3 years

“My benchmark says Java is slower than Python”

A teammate times a method once with System.currentTimeMillis() around a single call, finds it slow, and proposes rewriting the service in another language. How would you respond?

The interviewer is checking: do you understand that JIT warm-up makes naive timing misleading, and do you know how to measure properly?

Show a strong answer

A single cold call mostly measures class loading and interpretation, not steady-state performance. The JIT hasn't compiled anything yet, and the JIT may also remove code whose result is never used, which distorts naive loops in the other direction.

  • Use a proper benchmark harness such as JMH (Java Microbenchmark Harness), which runs warm-up iterations, repeats measurements and prevents dead-code removal.
  • Compare realistic workloads (for example requests per second under load), not one call.
  • Profile to find the real bottleneck before deciding anything.

Avoid: drawing conclusions from one timed run, in any language.
