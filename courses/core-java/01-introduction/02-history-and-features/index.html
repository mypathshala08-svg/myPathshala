History and key features of Java

Java was not designed in a vacuum. Every famous “feature of Java” is an answer to a real problem that programmers faced in the 1990s. In this lesson you'll follow Java from a small team's experiment in 1991 to Java 25, learn each feature with the problem it solves, and watch the JVM catch a bug that C would miss.

1 The story

The viva question Riya couldn't explain

Lab viva day. The external examiner asked Riya, “List the features of Java.” She rattled off the list she had memorised: simple, object-oriented, robust, secure… Then came the follow-up: “Why is Java called robust?” Silence. After the viva she finds Arjun Sir in the staff room.

Riya

Sir, I knew all eleven words! But when he asked why Java is robust, I had nothing. They're just buzzwords to me.

Arjun Sir

That's because you learnt the answers without the questions. In 1991 programmers had three big headaches: too many different chips, programs crashing from memory bugs, and code starting to travel over networks. Each Java feature is a cure for one of those.

Riya

So “robust” isn't just a fancy word for “strong”?

Arjun Sir

Not at all. It means the JVM catches your mistakes before they silently damage memory. Let's start with where Java came from, then I'll show you the JVM catching a real bug.

2 Definition

Java's history and features in one place

Formal definition (write this in exams)

Java was developed by James Gosling and his team at Sun Microsystems, starting in 1991 as the Green Project. It was first called Oak, renamed Java in 1995, and released as JDK 1.0 in January 1996. Its key features, often called the Java buzzwords, are: simple, object-oriented, distributed, robust, secure, architecture-neutral, portable, interpreted, high-performance, multithreaded and dynamic.

In simple words

A small team at Sun wanted one language that could run on all kinds of gadgets safely. They took the good parts of C and C++, removed the dangerous parts, and added a translator (the JVM) on every machine. The “features of Java” are simply the list of promises that design gives you.

3 Types and ways to use it

The 12 features of Java, grouped by the problem they solve

Learning twelve words in a row is hard. Learning four problems is easy, and each problem brings its features with it.

Problem: too many machines

Platform independent, architecture neutral, portable. Compile once to bytecode, and the JVM on each machine runs it.

Runs anywhere

Problem: crashes and attacks

Robust and secure. No raw pointers, automatic memory cleanup, checked array access and verified bytecode.

Safe by design

Problem: speed

Interpreted, high performance and multithreaded. The JVM interprets bytecode, its JIT compiles busy code to machine code, and threads do many jobs at once.

Fast enough for banks

Problem: building big systems

Simple, object-oriented, distributed and dynamic. Familiar syntax, code organised as objects, built-in networking, and classes loaded when needed.

Teams and networks

Every feature: what it means and how Java achieves it

FeatureWhat it meansHow Java does it
1. SimpleEasy to learn if you know C/C++Same C-style syntax, but removed explicit pointers, operator overloading, multiple inheritance of classes and manual free(). (goto is a reserved word but unused.)

7. SecureUntrusted code can't easily harm your machineNo raw memory access, the bytecode verifier checks every class before it runs, and the class loader keeps classes separated.

9. High performanceFast, despite the extra JVM layerThe JIT (just-in-time) compiler turns frequently used bytecode into native machine code while the program runs.

4 Step by step

How Java grew: from Oak to Java 25

Each step shows what changed for programmers, and what changed behind the screen inside the JDK and JVM.

  1. 1991: The Green Project creates Oak

    James Gosling, Mike Sheridan and Patrick Naughton start a secret project at Sun to build software for smart consumer devices. Gosling designs a new language for it, called Oak.

    Consumer devices used many different chips. Rewriting C++ code for each chip was slow and error-prone, so Oak was compiled to an intermediate code that a small interpreter on each device could run. This is the seed of today's bytecode and JVM.

  2. 1992: The first demo device

    The team shows a handheld controller prototype called *7 (“Star Seven”), running Oak. The device never became a product.

    The demo proved the idea worked: one program, an interpreter on the device, and no rebuilding for its chip.

  3. 1995: Renamed Java, aimed at the internet

    The consumer-device market didn't take off, but the World Wide Web did. The language is renamed Java and announced on 23 May 1995, along with a web browser that could run small Java programs called applets.

    Applets meant running code downloaded from unknown websites. That's why the bytecode verifier and the sandbox were built in from the start. Browser applets were dropped years later, but the safety design stayed.

  4. 1996–2000: JDK 1.0, then “Java 2”

    JDK 1.0 ships in January 1996. J2SE 1.2 (1998) is branded “Java 2” and adds the Collections framework and Swing for desktop windows. J2SE 1.3 (2000) makes HotSpot the default JVM.

    Early JVMs mostly interpreted bytecode, so Java was called slow. JIT compilers became standard around Java 2, and HotSpot finds the “hot” (busy) methods and compiles them to machine code. That's how “interpreted” and “high performance” can both be true.

  5. 2004: Java 5, the big language upgrade

    Generics, the enhanced for-each loop, autoboxing, enums and annotations. The version name jumps from 1.4 to 5.0.

    Generics are checked by javac and then erased from the bytecode (called type erasure). So new code still ran on the same kind of JVM, and old programs kept working.

  6. 2006–2010: Open source, then Oracle

    Sun releases Java's source code as OpenJDK (2006–2007). Oracle buys Sun and takes over Java in January 2010.

    OpenJDK is now the shared source code that almost every JDK is built from, including Oracle JDK, Eclipse Temurin and Amazon Corretto. That's why they all behave the same.

  7. 2014: Java 8, lambdas and streams

    Java 8 adds lambda expressions, the Stream API and a new date-and-time library. It became one of the most widely used Java versions ever.

    Lambdas are compiled using a bytecode instruction called invokedynamic, which lets the JVM decide at run time how to build the lambda object. This is the “dynamic” feature at work.

  8. 2017–2018: Modules and a faster release train

    Java 9 adds the module system and JShell, an interactive Java prompt. From Java 10 (March 2018), a new version comes every six months. Java 11 (September 2018) is an LTS release.

    The JDK itself was split into modules, such as java.base, so smaller runtimes can be built that contain only the modules an application needs.

  9. 2021–2025: Modern Java LTS versions

    Java 17 (2021), Java 21 (2023, with virtual threads) and Java 25 (2025, with a simpler main method for beginners). LTS versions now come every two years.

    Virtual threads are lightweight threads managed by the JVM rather than the operating system. One server can run millions of them, which makes “multithreaded” much cheaper than before.
5 See it happen

“Robust and secure” in action: one bug, two languages

Riya stores 3 marks in an array, then makes a classic mistake: she writes to position 3, which doesn't exist (positions are 0, 1 and 2). Press Play to see what C does with this bug and what Java does.

Writing past the end of an array 6 steps
What you see
  1. Riya creates an array of 3 marks. The valid positions are 0, 1 and 2. Then she writes marks[3] = 99 by mistake.
  2. In C, the same code usually compiles and runs without any error. The bug stays hidden and can cause trouble much later.
  3. In Java, the program stops at once with ArrayIndexOutOfBoundsException, naming the exact line (line 4 of Main.java, the marks[3] = 99 line). It never prints “Saved”.
  4. With try/catch, Riya's program handles the error and keeps running. This is exception handling, one part of being robust.
  5. Riya sets marks = null when she's done. The screen only shows “Done”, but something important happens behind the screen.
  6. Together, these make Java robust and secure. These are exactly the points to write when an examiner asks “why”.
Behind the screen
  1. In Java, the array is an object in the heap that stores its own length (3). The variable marks on the stack only holds a reference to it.
  2. C has no such safety net. It works out the memory address for position 3 and writes 99 there, onto whatever happens to be next in memory.
  3. Java's iastore instruction makes the JVM check the index against the length first. 3 is not less than 3, so nothing is written and an exception object is created.
  4. When javac compiled the try/catch, it wrote an exception table into the .class file. The JVM uses it to jump to the catch block, and e points to the exception object.
  5. After marks = null, nothing refers to the array. The garbage collector frees that memory on its own. Forgetting to free memory is a common bug in C.
  6. Five safety layers together make Java robust (mistakes don't silently spread) and secure (code can't poke at raw memory).

6 Real-world use

Java's features at work in real systems

Features matter because real systems depend on them. Here's where each group of features shows up.

Watch it with an example: Tatkal booking at 10 AM

Three people book at the same second. See why multithreading (one of Java's key features) matters, and how Java stops two people getting the same seat.

Three bookings at the same second 5 steps
Animated example
  1. 10:00:00 AM: Asha, Ravi and Meena press Book at the same moment. All three requests reach the same booking server.
  2. Without threads: the server handles one request, then the next. If each takes 1 second, Meena waits 3 seconds. With lakhs of users, nobody would get a ticket.
  3. With threads: Java lets the server run many threads inside one program. Each request gets its own thread, so all three are handled at the same time.
  4. Safety: only 2 seats are left. The seat-count code is marked synchronized, so only one thread at a time can change it. No seat is sold twice.
  5. Result: Asha and Ravi get the last two seats; Meena goes to the waitlist. Fast and correct: this is why Java's built-in multithreading is listed as a key feature. (Simplified example.)

1. Build on a laptop, run on a server (platform independent)

Developers often write and test on Windows or Mac laptops, while the application runs in production on Linux servers or in the cloud. The same compiled .jar file goes to both, with no rebuild for the server.

Developer laptop→same .jar file→Linux server / cloud

2. Ticket booking at peak time (multithreaded)

When a booking window opens, thousands of people try to book at once. A Java backend handles each request on its own thread, and carefully controls the step that reserves a seat so two people can't get the same one.

Many users→One thread per request→Seat locked safely→Ticket

3. Servers that run for months (robust)

Payment and banking services run day and night. Because the garbage collector frees unused memory and bad array access is stopped at once, slow memory leaks and silent memory corruption, two common causes of long-running crashes in C programs, are far less likely.

Millions of requests→GC cleans up continuously→Service stays up

4. Bank cards and SIM cards (secure)

The chip in many bank and SIM cards runs Java Card. Applets on the chip are kept separate from each other by a firewall, so one applet can't read another's secret keys.

Card tapped→Isolated Java Card applet→Keys never leave the chip

5. Services talking over a network (distributed)

Large apps are often split into small services: one for login, one for payments, one for notifications. Java's built-in networking and HTTP client let these services call each other across machines.

Order service→HTTP call over network→Payment service

6. Plugins and mods (dynamic)

IDEs such as IntelliJ IDEA and Eclipse let you install plugins without reinstalling the editor. Java game mods work in a similar way. The JVM loads the new classes while the program is running.

Install plugin→Class loader loads new .class files→New feature appears

7. Old code still running (backward compatibility)

Many organisations have Java code written a decade or more ago. Because Java takes backward compatibility seriously, much of it runs on new JVMs with few or no changes, and gets the newer JVM's speed improvements for free.

Code compiled for Java 8→Runs on a Java 21 or 25 JVM→Faster GC and JIT

Examples are simplified to show where each feature fits. Each company's exact technology choices vary.

7 Run the code

See three features with your own eyes

This program shows platform independence and robustness in a few lines. Read the notes, then try the challenges in the live editor.

public class Main {
    public static void main(String[] args) {
        // Platform independent: the same code asks "where am I?"
        System.out.println("Running on: " + System.getProperty("os.name"));
        System.out.println("Java version: " + Runtime.version().feature());

        // Robust: Java checks every array index
        int[] marks = {78, 85, 92};
        try {
            System.out.println(marks[3]);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("Caught: " + e.getMessage());
        }
        System.out.println("Program still running!");
    }
}
Running on: Linux Java version: 21 Caught: Index 3 out of bounds for length 3 Program still running!

The first two lines depend on the machine. On a Windows laptop you might see Running on: Windows 11, and the version number is whatever JDK is installed. The same Main.class works on both.

  • System.getProperty("os.name")Asks the JVM which operating system it's running on. The code doesn't change, only the answer does.
  • Runtime.version().feature()Returns the main Java version number, such as 17, 21 or 25.
  • int[] marks = {78, 85, 92};An array of 3 whole numbers at positions 0, 1 and 2. Arrays get their own lesson in Module 4.
  • try { … }“Try this code, and watch for errors.” Exceptions are covered fully in Module 7.
  • catch (ArrayIndexOutOfBoundsException e)“If this kind of error happens, run this block instead of crashing.” e holds the details.
  • e.getMessage()The error's message: Index 3 out of bounds for length 3.

Interview and viva questions

Why is Java called robust?

Because it stops many errors early instead of letting them silently damage memory. javac does strong type checking, there's no pointer arithmetic, the JVM checks every array index, the garbage collector manages memory, and exception handling lets programs recover from errors.

Why doesn't Java support pointers?

Pointers let a program read or write any memory address, which causes crashes and security holes. Java uses references instead: they point to objects, but you can't do arithmetic on them or turn a number into one. The JVM manages the real addresses, and can even move objects around during garbage collection.

What's the difference between platform independent, architecture neutral and portable?

Architecture neutral: bytecode isn't tied to any CPU. Platform independent: the compiled program runs on any OS that has a JVM. Portable: it behaves the same everywhere too, because things like data-type sizes are fixed by the language. The first two are about running. Portable is about getting the same result.

Is Java 100% object-oriented?

No. It has 8 primitive types (byte, short, int, long, float, double, char, boolean) that are not objects, and static members belong to the class rather than any object. Wrapper classes such as Integer exist when you need an object version.

My textbook mentions the Security Manager. Is it still part of Java?

No longer in practice. The Security Manager was deprecated in Java 17 and permanently disabled in Java 24. Today Java's security rests on the bytecode verifier, the lack of raw memory access, the class loaders, and secure libraries for cryptography and TLS. For exams, mention the verifier and class loader first.

Which Java version should I learn in 2026?

Learn on a recent LTS version: Java 21 or Java 25. Everything in this course works on Java 21. Many companies still run Java 8, 11 or 17, but the basics are the same, so what you learn carries over.

Real-world scenario questions (asked in company interviews)

In company interviews, Java's features come up as real situations, not definitions. Each scenario below tests one feature from this lesson. Decide your answer first, then open the model answer.

Bank / insurance · legacy system1–3 years

Moving a ten-year-old app from Java 8 to Java 21

Your company runs a claims-processing application on Java 8. Management wants to move it to Java 21 for security updates and better performance. Your manager asks: “Java is backward compatible, so this is just a version change, right? How would you plan it?”

The interviewer is checking: do you know that “backward compatible” doesn't mean “zero changes”, and can you plan a safe upgrade?

Show a strong answer

Most Java 8 code runs on Java 21 unchanged, but a few things commonly break, so I'd plan it as a small project:

  1. Removed modules: Java 11 removed the bundled Java EE and CORBA modules, such as JAXB and JAX-WS. If the app uses them, we add them back as normal library dependencies.
  2. JDK internals: since Java 17, code or old libraries that reach into the JDK's internal classes fail. I'd run jdeps --jdk-internals on our jars to find them.
  3. Library upgrades: update frameworks and libraries to versions that support Java 21.
  4. Test and roll out in stages: run the full test suite on Java 21, then a test environment, then production, with a way to roll back.

Avoid saying: “Just change the JDK on the server, it'll work.” That is how production outages start.

E-commerce · flash saleFresher

Two customers bought the last phone

During a flash sale, only one phone was left in stock, but two customers both got an order confirmation. The code that reserves stock looks like this: if (stock > 0) { stock--; confirmOrder(); }. Why did this happen, and how would you fix it?

The interviewer is checking: do you understand that “multithreaded” brings real risks, and do you think beyond a single server?

Show a strong answer

This is a race condition. Each customer's request runs on its own thread. Both threads read stock = 1 at almost the same moment, both pass the if check, and both confirm the order. The check and the update are two separate steps.

  • Inside one JVM, the check and the update must happen as one step, for example in a synchronized method or with AtomicInteger.
  • In real systems, the app runs on several servers, so a lock in one JVM isn't enough. I'd let the database do it atomically: UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0, and confirm the order only if exactly one row was updated.
  • I'd also add a load test that fires many buy requests at once to prove the fix.

Avoid: “It rarely happens” or adding Thread.sleep(). Timing tricks hide race conditions; they don't fix them.

SaaS · production supportFresher

An exception in the production logs

Some customers report that their invoice page fails. The production log shows java.lang.ArrayIndexOutOfBoundsException: Index 5 out of bounds for length 5 at InvoiceService.java:142. Your lead asks how you'll handle it.

The interviewer is checking: your debugging approach. Do you find the root cause, or just hide the error?

Show a strong answer
  1. Read the stack trace: the type, the message (index 5 on an array of length 5) and the exact line, InvoiceService.java:142. Java's robustness gave us all of this for free.
  2. Find the pattern: which customers fail? Maybe only those with more than a certain number of invoice items.
  3. Reproduce it in a unit test using that kind of data.
  4. Fix the root cause. “Index 5 for length 5” often means an off-by-one loop such as i <= items.length instead of i < items.length, or code that assumed a fixed size.
  5. Keep the test so the bug can't come back, then deploy the fix.

Avoid: wrapping the code in try { … } catch (Exception e) { } and ignoring the error. The page stops failing, but customers silently get wrong invoices.

Any company · code reviewFresher

“Java is secure, so any jar is safe”

You need to read PDF files in your project. A teammate found a jar on an unknown website that does it, and says: “Java is a secure language, so it's fine to add.” Do you agree?

The interviewer is checking: do you know what Java's “secure” feature does and doesn't protect against?

Show a strong answer

No. Java's security features stop memory-level attacks, because there are no raw pointers and the bytecode is verified. They don't stop a library from doing harmful things with our application's permissions, such as reading files or sending data out. (The old Security Manager sandbox is permanently disabled since Java 24.)

  • Use well-known, maintained libraries from trusted repositories such as Maven Central. For PDFs, Apache PDFBox is a common choice.
  • Check the library's licence is allowed for company use.
  • Scan dependencies for known vulnerabilities with tools such as OWASP Dependency-Check or GitHub Dependabot, and keep them updated.

The Log4Shell vulnerability (2021) in Log4j, a very popular Java logging library, showed that even a trusted library can put thousands of companies at risk. Dependencies need care.

Avoid saying: “The JVM protects us from everything.”

Data / reporting teamFresher

Works on my laptop, fails on the server

Your monthly-report job runs fine on your Windows laptop. On the Linux server it fails with java.io.FileNotFoundException: Reports\march.csv (No such file or directory). The file is there, in a folder called reports. A teammate says, “Java is platform independent, so it must be a server problem.”

The interviewer is checking: do you know the difference between Java being portable and your code being portable?

Show a strong answer

The bytecode is fine. The problem is in our code's assumptions about Windows:

  • Path separator: Linux uses /, not \. On Linux, Reports\march.csv is treated as one file name containing a backslash.
  • Letter case: Linux file names are case-sensitive, so Reports and reports are different folders. Windows usually ignores the difference.
  • Fix: build paths with Path.of("reports", "march.csv"), which uses the right separator on each OS, read the base folder from configuration, and use one consistent naming style.

Avoid: blaming the server or Java. Platform independence covers bytecode and data types, not hard-coded paths.
