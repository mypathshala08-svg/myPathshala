Autoboxing and unboxing

In the last lesson you wrote Integer.valueOf(85) and m.intValue() by hand. Since Java 5 you rarely need to: the compiler does it for you. This is autoboxing (primitive → wrapper) and unboxing (wrapper → primitive). It makes code shorter, but it hides method calls, and hidden calls can throw NullPointerException or create millions of objects. You'll learn exactly what javac writes and where the traps are.

1 The story

The line that crashed with no object in sight

Riya's canteen app keeps stock in a HashMap<String, Integer>. Adding items works beautifully: stock.put("samosa", 40). Then a customer orders a “vada pav”, which was never added, and the app crashes on a line that has no dot and no object.

Riya

Sir, a NullPointerException needs something like obj.method() on null. My line is just stock.get(item) - 1!

Arjun Sir

The method call is there; you just can't see it. get returns an Integer. To subtract 1, Java needs an int, so the compiler quietly writes .intValue() for you. That's unboxing.

Riya

And “vada pav” isn't in the map, so get returned null…

Arjun Sir

…and the hidden null.intValue() blew up. The same trick runs the other way too: when you wrote put("samosa", 40), javac turned 40 into Integer.valueOf(40). That's autoboxing. Today we'll make the invisible calls visible.

2 Definition

What are autoboxing and unboxing?

Formal definition (write this in exams)

Autoboxing is the automatic conversion, done by the compiler, of a primitive value into an object of its corresponding wrapper class (for example int → Integer), when an object is expected. Unboxing is the reverse: the automatic conversion of a wrapper object into its primitive value when a primitive is expected. Introduced in Java 5, the compiler implements them with calls such as Integer.valueOf(int) and Integer.intValue(). Unboxing a null reference throws NullPointerException.

In simple words

You write Integer x = 5; and int y = x;, and the compiler adds the conversion code for you. Convenient, but the conversion is still a real method call.

Words you'll meet in this lesson

AutoboxingCompiler wraps a primitive: Integer x = 5; becomes Integer.valueOf(5).
UnboxingCompiler unwraps: int y = x; becomes x.intValue().
Syntactic sugarA shortcut in the language that the compiler expands into longer code.
javap -cA JDK tool that prints the bytecode inside a .class file, so you can see the hidden calls.
Overload resolutionHow javac picks between methods with the same name (Lesson 5.4). Boxing is its second choice.

Where it happens

AssigningInteger a = 10; (boxing) · int b = a; (unboxing)
Passing argumentslist.add(7) boxes 7 because add takes an Integer
ReturningA method returning Integer may return 0;
Arithmetic and comparisona + 1, a > 5, a++ unbox first (and a++ boxes the result again)
ConditionsBoolean ok = true; if (ok) … unboxes with booleanValue()

Exam tip: autoboxing only goes to the matching wrapper: int → Integer, never int → Long. Long l = 5; is a compile error (int cannot be converted to Long); write Long l = 5L;.

3 Types and ways to use it

Boxing, unboxing, and what javac writes

Autoboxing

Primitive in, object out. Integer x = 5; → Integer.valueOf(5).

int → Integer

Unboxing

Object in, primitive out. int y = x; → x.intValue().

Integer → int

Both in one line

x++ or x += 1 on an Integer: unbox, add, box a new object.

read-modify-write

The same code, written two ways

import java.util.ArrayList;

public class Main {
    public static void main(String[] args) {
        ArrayList<Integer> marks = new ArrayList<>();

        // What you write (Java 5+)
        marks.add(85);
        int first = marks.get(0);

        // What javac writes for you
        marks.add(Integer.valueOf(92));
        int second = marks.get(1).intValue();

        System.out.println(marks + " " + (first + second));
    }
}

There is no special “autobox” instruction. It's ordinary method calls that the compiler inserted, and because it uses valueOf, the Integer cache from Lesson 10.1 still applies.

Trap 1: unboxing null

import java.util.HashMap;

public class Main {
    public static void main(String[] args) {
        HashMap<String, Integer> stock = new HashMap<>();
        stock.put("samosa", 40);

        Integer v = stock.get("vada pav");        // null: not in the map
        System.out.println(v);                    // printing null is fine
        int safe = (v == null) ? 0 : v;           // check before unboxing
        System.out.println(safe);
        System.out.println(stock.getOrDefault("vada pav", 0));
        // int boom = stock.get("vada pav");      // NullPointerException
    }
}
null 0 0
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.HashMap.get(Object)" is null

Trap 2: == between two wrappers

public class Main {
    public static void main(String[] args) {
        Integer a = 1000, b = 1000;   // autoboxing uses valueOf: two objects
        int p = 1000;

        System.out.println(a == b);   // compares references
        System.out.println(a == p);   // one side is int, so a is unboxed
        System.out.println(a.equals(b));
    }
}
false true true

Trap 3: remove(1) on a list of Integers

import java.util.ArrayList;
import java.util.List;

public class Main {
    public static void main(String[] args) {
        List<Integer> ids = new ArrayList<>(List.of(10, 20, 30));

        ids.remove(1);                    // remove(int index): removes 20
        System.out.println(ids);

        ids.remove(Integer.valueOf(10));  // remove(Object): removes the value 10
        System.out.println(ids);
    }
}
[10, 30] [30]

javac prefers a method that needs no boxing, so remove(1) picks remove(int index). Overload resolution tries, in order: exact match or widening, then boxing/unboxing, then varargs.

Rule of thumb: let autoboxing make collection code readable, but keep calculations in primitives, and treat every unboxing of a value that might be null (map lookups, database fields, method results) as a place to check for null first.

4 Step by step

How javac handles total += price with wrappers

  1. javac sees the types

    Integer total = 0;
Integer price = 250;
total += price;
    Both are Integer. The + operator works only on primitives (or Strings), so javac plans conversions.

  2. Box the literals

    Integer total = 0; becomes Integer.valueOf(0), and 250 becomes Integer.valueOf(250). 0 comes from the cache; 250 is a new object.

  3. Unbox both operands

    total.intValue() and price.intValue() copy 0 and 250 onto the operand stack. If either variable were null, this is where the NullPointerException would happen.

  4. Add as ints

    An ordinary iadd instruction: 0 + 250 = 250, a primitive result.

  5. Box the result into a new object

    Integer.valueOf(250) creates another Integer object (250 is outside the cache), and total now points to it. The old object holding 0 is untouched: wrappers are immutable. In a loop that runs a million times, that's up to a million new objects.

Autoboxing and unboxing, made visible 6 steps
What you see
  1. You assign the number 0 to an Integer variable. No method call in sight.
  2. The same for 250.
  3. total += price reads like adding two numbers.
  4. Copying an Integer into an int looks like an ordinary assignment.
  5. none holds no object at all.
  6. This innocent-looking line throws NullPointerException. The right side shows the hidden call.
Behind the screen
  1. Autoboxing: javac replaces 0 with Integer.valueOf(0), which returns the cached object for 0.
  2. Integer.valueOf(250) creates a new object, because 250 is outside -128..127.
  3. += needs ints: javac unboxes both with intValue(), adds 0 + 250 as ints, then boxes 250 into a new object. total moves to it; the cached 0 is untouched.
  4. Unboxing: total.intValue() copies the value 250 into the primitive n, stored right in the frame.
  5. Assigning null needs no conversion: none simply holds no reference.
  6. int bad = none; becomes none.intValue(). Calling a method on null throws NullPointerException.
6 Real-world use

Autoboxing in real systems

Every time Java code puts numbers into collections, maps, streams or generic APIs, autoboxing is at work. Most of the time that's fine; a few places need care.

Watch it with an example: an exam result portal

Marks come from a database where an absent student's mark is NULL. Watch the averaging code survive one absent student, then see the version that crashes.

Averaging marks with an absent student 5 steps
Animated example
  1. Marks arrive as Integer objects. Meera was absent, so the database gave NULL, which becomes null in Java.
  2. For Riya's 78, the check passes and sum += m unboxes the Integer to add it.
  3. For Meera, m != null is false, so nothing is unboxed and she isn't counted.
  4. Average = 233 / 3 ≈ 77.67. Using 0 for Meera would have wrongly pulled it down to about 58.
  5. The tempting shortcut for (int m : marks) unboxes each element automatically, and crashes on Meera's null. (Simplified: real portals also record why a mark is missing.)

1. Counting with maps

Inventory, word counts, votes and page views are kept in Map<String, Integer>. Code like map.put(k, map.getOrDefault(k, 0) + 1) unboxes, adds and boxes on every update.

getOrDefault→unbox + 1 + box→put back

2. Nullable database columns

Entity classes map optional columns to Integer or Double fields. A business rule written as int d = order.getDiscount(); crashes on the first order without a discount.

NULL column→Integer field = null→check before unboxing

3. High-volume analytics

Summing sensor readings or transaction amounts in a Long or a List<Double> creates an object per value. Performance-sensitive code uses long, arrays, or primitive streams like IntStream (Lesson 14.3).

Hot loop→primitives, not wrappers→less garbage

4. Comparing IDs

Code that compares Integer or Long IDs with == passes tests with small IDs and fails in production with large ones. Teams use Objects.equals and code-review rules to catch it.

Long id1, id2→Objects.equals(id1, id2)→safe comparison

Examples are simplified. Frameworks and libraries add their own conversion layers on top.

7 Run the code

A canteen stock counter

import java.util.HashMap;

public class Main {
    static HashMap<String, Integer> stock = new HashMap<>();

    static String sell(String item, int qty) {
        Integer have = stock.get(item);           // may be null
        if (have == null) {
            return item + ": not on the menu";
        }
        if (have < qty) {                         // unboxing for <
            return item + ": only " + have + " left";
        }
        stock.put(item, have - qty);              // unbox, subtract, box
        return item + ": sold " + qty + ", left " + stock.get(item);
    }

    public static void main(String[] args) {
        stock.put("samosa", 40);                  // 40 is autoboxed
        stock.put("chai", 75);
        System.out.println(sell("samosa", 5));
        System.out.println(sell("chai", 80));
        System.out.println(sell("vada pav", 2));
    }
}
samosa: sold 5, left 35 chai: only 75 left vada pav: not on the menu
  • stock.put("samosa", 40)Autoboxing: javac writes Integer.valueOf(40).
  • Integer have = stock.get(item)Kept as Integer on purpose, so it can hold null.
  • have < qtyUnboxing: have.intValue() < qty. Safe, because null was ruled out above.
  • have - qtyUnbox, subtract as ints, box the result for put.

9 Quiz and revision

Check yourself

Quick revision

Lesson 10.2 in one screen

  • Autoboxing: primitive → wrapper, compiled to Integer.valueOf(…). Unboxing: wrapper → primitive, compiled to intValue() etc.
  • Happens in assignments, arguments, returns, arithmetic, comparisons and conditions. Since Java 5.
  • Only to the matching wrapper: Long l = 5; ✗, Long l = 5L; ✓.
  • Unboxing null → NullPointerException. Watch map lookups and nullable fields; use getOrDefault or a null check.
  • wrapper == wrapper compares references; wrapper == primitive unboxes. Use equals.
  • Overloads: exact/widening first, then boxing, then varargs. list.remove(1) removes index 1.
  • x++ on an Integer creates a new object. Use primitives in loops and sums.

Interview and viva questions

What is autoboxing and when was it introduced?

Automatic conversion of a primitive to its wrapper (and unboxing for the reverse), done by the compiler, introduced in Java 5 together with generics. The compiler inserts calls like Integer.valueOf and intValue(); the JVM has no special instruction for it.

Can autoboxing cause a NullPointerException?

Unboxing can. If a wrapper reference is null and it's used where a primitive is needed (int n = map.get(k);, total + v, if (flag) with a null Boolean), the hidden intValue()/booleanValue() call throws. Boxing itself never throws.

Why does Integer a = 127, b = 127; a == b give true but 128 gives false?

Autoboxing uses Integer.valueOf, which returns cached objects for -128 to 127. 128 is boxed into two separate objects, and == compares references.

How does boxing affect method overloading?

javac resolves overloads in three phases: (1) without boxing or varargs, allowing widening, (2) with boxing/unboxing, (3) with varargs. So f(5) prefers f(long) over f(Integer), and list.remove(1) picks remove(int).

Is autoboxing bad for performance?

Not in normal code. In hot loops or large data it creates many short-lived objects and adds unboxing work. Use primitives, primitive arrays, or IntStream/LongStream there, and measure before optimising.

P6Business problem

Shopping cart quantities

Add items to a cart map: pen, pen, book, pen. Use merge so first-time items start at 1, then print the cart.

Input
pen, pen, book, pen
Expected output
{pen=3, book=1}
Show solution and explanation 
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        Map<String, Integer> cart = new LinkedHashMap<>();
        String[] added = {"pen", "pen", "book", "pen"};
        for (String item : added) {
            cart.merge(item, 1, Integer::sum);
        }
        System.out.println(cart);
    }
}
{pen=3, book=1}

How it works: merge puts 1 for a new key, otherwise combines the old and new values with Integer::sum (a method reference, Lesson 14.1). No null is ever unboxed. (LinkedHashMap keeps insertion order; Lesson 11.6.)

P7Business problem

Optional discount from a nullable field

Orders have an Integer discountPct that may be null. Compute the final price for ₹1000 with 10% and with no discount.

Input
1000 with 10, 1000 with null
Expected output
900
1000
Show solution and explanation 
public class Main {
    static int finalPrice(int price, Integer discountPct) {
        int pct = (discountPct == null) ? 0 : discountPct;
        return price - price * pct / 100;
    }

    public static void main(String[] args) {

Sum one million sales of ₹1 each, first with a Long total, then with a long. Print both totals (the timing is up to you to measure).

Expected output

Real-world scenario questions (asked in company interviews)

Autoboxing bugs are favourites in interviews because the code looks correct. Read the line, then ask: where is the hidden call?

Retail · production bugFresher

Crash on a new product

The billing service crashes with NullPointerException at int qty = cart.get(sku) + 1; only when a customer adds a product for the first time. There's no method call on an object in that line. Explain.

The interviewer is checking: can you see the hidden unboxing?

Show a strong answer
  • cart.get(sku) returns Integer. For a new SKU it returns null.
  • + 1 needs an int, so javac inserted .intValue(): null.intValue() throws.
  • Fix: cart.getOrDefault(sku, 0) + 1, or better, cart.merge(sku, 1, Integer::sum).
  • Add a unit test for the first-time-add path.

Avoid: wrapping it in try/catch (NullPointerException). Fix the cause, not the symptom.

Fintech · code reviewJunior

Duplicate payments slip through

A duplicate check does if (newTxn.getAmountPaise() == lastTxn.getAmountPaise()), both returning Long. Small test amounts were caught; real ₹500 payments (50000 paise) are not. Why, and what's the fix?

The interviewer is checking: wrapper equality and the Long cache.

Show a strong answer
  • Long also caches only -128 to 127. 50000 creates distinct objects, so == is false.
  • Use Objects.equals(a, b), or long return types if the amount can never be null.
  • Prefer primitives for amounts in domain logic; it removes both the == trap and null unboxing.

Avoid: “just increase the cache size”. That hides the bug for some values only.

Analytics · performanceJunior

GC pauses in a reporting job

A nightly job sums 50 million values from a List<Double> into a Double total. GC logs show huge allocation rates. What would you change?

The interviewer is checking: awareness of boxing cost at scale.

Show a strong answer
  • Double total boxes a new object on every +=; the list itself holds 50 million Double objects.
  • Use double total, and if possible a double[] or DoubleStream instead of List<Double>.
  • Measure allocation before and after (profiler or GC logs) to prove the improvement.

Avoid: tuning GC flags first. Remove the needless objects, then tune.

Platform · API designMid

Should this method return int or Integer?

You're designing findDiscountPercent(String couponCode). Some codes are invalid. A teammate wants it to return Integer and use null for invalid. What do you think?

The interviewer is checking: null design and unboxing risk for callers.

Show a strong answer
  • Returning Integer with null invites callers to write int d = findDiscountPercent(c);, which crashes for invalid codes.
  • Better: return OptionalInt (or Optional<Integer>, Lesson 14.4), which forces callers to handle “absent”, or throw a clear exception for invalid codes.
  • If null is kept, document it and name the method to signal it, e.g. discountOrNull.

Avoid: returning 0 for invalid codes. A valid “0% discount” and an invalid code become indistinguishable.
