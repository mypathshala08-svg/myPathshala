try, catch and finally

Whatever happens at an ATM, it gives your card back. try, catch and finally let your code behave the same way: try the risky work, catch the problems you can handle, and finally clean up no matter what. You'll see exactly where control jumps, why catch order matters, how multi-catch saves code, the rare cases where finally doesn't run, and then practise with 11 problems.

1 The story

The ATM that always gives the card back

Riya tries to withdraw Rs 900 at the campus ATM. The screen says “Insufficient balance”. Annoying, but the machine still pushes her card out. Back in the lab she realises her own banking program does not do that: when a withdrawal fails, it skips the “return card” line along with everything else.

Riya

Sir, when the withdrawal throws an exception, my “return card” line is skipped. If I copy it into the catch block too, it feels wrong.

Arjun Sir

It is wrong: you'd have to copy it into every path, and one day you'd forget one. Put it in a finally block. Java runs finally after the try, whether the try succeeded, failed and was caught, or failed and wasn't caught at all.

Riya

So try is the risky work, catch is the plan B, and finally is the “no matter what” part?

Arjun Sir

Exactly. And when you have several plan Bs, the order of the catch blocks matters. Let's see why.

2 Definition

What are try, catch and finally?

Formal definition (write this in exams)

A try statement consists of a try block followed by zero or more catch clauses and an optional finally block (at least one catch or finally is required, unless it declares resources). If an exception is thrown in the try block, the first catch clause whose parameter type is the exception's class or a superclass of it is executed. The finally block is executed after the try and any catch block complete, whether they complete normally or abruptly (by an exception, return, break or continue).

In simple words

try: “attempt this.” catch: “if that kind of problem happens, do this instead.” finally: “and whatever happened, always do this at the end.”

Words you'll meet in this lesson

try blockThe code that might throw. It stops at the first exception.
catch clauseA handler for one type of exception (and its subclasses).
Catch parameterThe variable, like e, that receives the exception object.
finally blockClean-up code that runs on every path out of the try.
Multi-catchOne catch for several types: catch (A | B e). Java 7+.
Abrupt completionLeaving a block early through an exception, return, break or continue.

The rules at a glance

Valid shapestry-catch, try-finally, try-catch-finally, try-with-resources (Lesson 9.6). A try alone is a compile error.
Which catch runs?The first one, top to bottom, whose type matches. At most one catch runs per exception.
Order of catchesSubclass before superclass. A superclass first makes the later one unreachable: compile error.
Multi-catchcatch (NumberFormatException | ArithmeticException e). Types must not be related; e is implicitly final.
finally runs…after a normal try, after a catch, when nothing matches, and even after return, break, continue
finally does NOT runif System.exit() is called, or the JVM crashes or is killed first

Exam tip: “What prints?” questions love try { return 1; } finally { return 2; }. The method returns 2: a return in finally replaces the pending one. And if finally only changes a variable after return x;, the old value is still returned.

3 Types and ways to use it

Three shapes, three paths

try-catch

Handle a problem and carry on. Use when you can do something useful: use a default, show a message, skip a record.

Recover

try-catch-finally

Handle the problem and also clean up on every path: return the card, unlock the record, stop the timer.

Recover + clean up

try-finally

Don't handle it here; let it travel to the caller, but clean up first. The finally runs, then the exception continues.

Clean up, pass on

Where control goes: no exception, caught, not caught

public class Main {
    static void process(String qty) {
        try {
            System.out.println("  try: parsing " + qty);
            int q = Integer.parseInt(qty);
            System.out.println("  try: 100 / " + q + " = " + (100 / q));
        } catch (NumberFormatException e) {
            System.out.println("  catch: not a number");
        } finally {
            System.out.println("  finally: always runs");
        }
        System.out.println("  after the try statement");
    }

    public static void main(String[] args) {
        String[] inputs = {"4", "abc", "0"};
        for (String in : inputs) {
            System.out.println("Input " + in + ":");
            try {
                process(in);
            } catch (ArithmeticException e) {
                System.out.println("  main caught: " + e.getMessage());
            }
        }
    }
}

The return-in-finally trap: a return (or throw) inside finally replaces whatever was pending, including an exception. try { throw new IllegalStateException("Card declined"); } finally { return "Payment OK"; } returns "Payment OK" and the exception vanishes without a trace. Use finally only for clean-up, never to return values. javac -Xlint:finally warns: “finally clause cannot complete normally”.

4 Step by step

Writing a safe block, start to finish

  1. Wrap only the risky work in try

    try {
    withdraw(amount);
    System.out.println("Take your cash");
}
    javac records the bytecode range of the try block in the method's exception table. Code outside that range is not protected. Keep try blocks small so it is clear which line can fail.

  2. Add catch blocks, most specific first

    catch (NumberFormatException e) { … }   // subclass first
catch (IllegalArgumentException e) { … } // its parent after
    Each catch becomes a row in the exception table, in source order. The JVM takes the first row whose type matches. If the parent came first, the child's row could never be reached, so javac rejects it: exception NumberFormatException has already been caught.

  3. Same handling? Use multi-catch

    catch (NumberFormatException | ArrayIndexOutOfBoundsException e) {
    System.out.println("Bad line: " + e);
}
    One handler, several exception-table rows pointing to the same code. The types must be unrelated (otherwise: Alternatives in a multi-catch statement cannot be related by subclassing) and e cannot be reassigned.

  4. Put must-happen work in finally

    finally {
    System.out.println("Card returned");
}
    javac copies the finally code onto every exit path: after the try, after each catch, and into a hidden “any” handler that runs it and then rethrows the exception. You can see the copies with javap -c.

  5. Know the exceptions to “always”

    try {
    System.exit(0);       // JVM shuts down here
} finally {
    System.out.println("never printed");
}
    System.exit starts JVM shutdown and never returns, so control never reaches the finally code. A power cut, a killed process or a JVM crash also skip it. For real resources, the operating system frees what it can when the process ends.
5 See it happen

From try to catch to finally: both views

Left: the line that runs and the console. Right: which block is active, the exception table the JVM checks, and the exception object.

An ATM request of Rs 900 with only Rs 600 in the account 6 steps
What you see
  1. try: the request for Rs 900 starts, and withdraw(900) is called inside the try block.
  2. Throw: the balance is only Rs 600, so withdraw throws an IllegalStateException. Nothing prints yet.
  3. Skip: “Take your cash” is never printed. The try block stops at the line that failed.
  4. catch: the catch for IllegalStateException matches and prints the exception's message.
  5. finally: on this path too, the card is returned.
  6. Continue: the exception was handled, so the loop moves on to the next request.
Behind the screen
  1. Control is inside the try block. Calling withdraw pushes its frame on the stack.
  2. withdraw creates exception object #1 and throws it. It has no handler, so its frame is popped and the exception arrives back in the try block of the caller.
  3. The JVM scans the caller's exception table top to bottom. Row 1 covers the try block's range and its type matches, so control jumps to the catch code. The rest of the try is skipped.
  4. The catch parameter e now refers to #1. Only this catch runs.
  5. After the catch, the copy of the finally code that javac placed on this path runs. If no catch had matched, the hidden “any” row would run another copy and then rethrow.
  6. The exception has been handled, so nothing is pending. #1 is no longer referenced and the next statement runs as usual.
6 Real-world use

try, catch and finally in real systems

The pattern is everywhere a system must stay consistent when something fails halfway.

Watch it with an example: a seat lock that must always be released

A cinema app locks a seat while payment runs. Whether payment succeeds or fails, finally releases the lock, so the seat never stays stuck.

finally runs on success and on failure 6 steps
Animated example
  1. Lock: seat F7 is locked so nobody else can book it during payment.
  2. Run 1, try: pay(amount) succeeds. No exception, so the catch block is skipped.
  3. finally: runs anyway and unlocks F7 (the booking is saved elsewhere). Code in finally runs whether or not an exception happened.
  4. Run 2: another customer's payment times out inside pay() and throws PaymentException.
  5. catch: the rest of the try is skipped; the catch shows “Payment failed”.
  6. finally again: the seat is released, so someone else can book it. Without finally, a failed payment would leave seats locked forever. Locks, files and database connections are released this way (or with try-with-resources, Lesson 9.6).

1. Releasing locks

Code that locks a seat during booking, or a shared resource in a multithreaded program, unlocks it in finally. Forgetting to unlock after an exception would block everyone else.

lock()→try { book } finally { unlock() }→Seat free for others

2. Database transactions

Transfer money: debit one account, credit another. If anything throws in between, the catch rolls the transaction back so money is never lost halfway; finally returns the connection to the pool.

Transfer→try { commit } catch { rollback } finally { release }→All or nothing

3. Measuring time and counting requests

Services record how long each request took and whether it failed. The timer is stopped in finally, so slow failures are measured too, not only successes.

start = now→finally { record(now - start) }→Dashboards

4. Retrying flaky calls

Calls to payment gateways, SMS providers or other services sometimes time out. A loop with try/catch retries a few times before giving up, logging each attempt.

Call fails→catch → wait → retry→Success or clear failure

Examples are simplified. Real code usually uses try-with-resources (Lesson 9.6) for connections and files, and framework support for transactions and retries.

public class Main {
    static int balance = 1000;

    static void withdraw(int amount) {
        if (amount > balance) {
            throw new IllegalStateException("Insufficient balance");
        }
        balance -= amount;
    }

    public static void main(String[] args) {
        int[] requests = {400, 900, 500};
        for (int amount : requests) {
            System.out.println("Request: Rs " + amount);

                System.out.println("  Declined: " + e.getMessage());
            } finally {
                System.out.println("  Card returned");
            }
        }
        System.out.println("Balance: Rs " + balance);
    }
}

9 Quiz and revision

Check yourself

Quick revision

Lesson 9.2 in one screen

  • try = risky code; stops at the first exception. catch = handler for a type. finally = always runs.
  • Catches are checked top to bottom; only the first match runs.
  • Subclass catches must come before superclass catches, or it's a compile error.
  • Multi-catch A | B (Java 7): unrelated types, parameter is implicitly final.
  • finally runs after normal completion, after a catch, when nothing matches, and after return/break/continue.
  • finally is skipped only by System.exit or a JVM crash/kill.
  • Never return from finally: it replaces the pending value and can hide exceptions.

Interview and viva questions

Can we have a try block without a catch?

Yes, if it has a finally block (try-finally) or declares resources (try-with-resources). The exception is not handled there; finally runs and then the exception continues to the caller.

Why must a subclass exception be caught before its superclass?

The JVM picks the first matching catch. If the superclass came first, it would match every subclass exception too, so the subclass catch could never run. Java treats unreachable code as an error, so it refuses to compile.

When does finally not execute?

When the JVM stops before reaching it: System.exit() (or Runtime.halt()), a JVM crash, the process being killed, or the power going off. It also never runs if the try block never finishes, for example an infinite loop.

What happens if both try and finally throw exceptions?

The exception from finally wins and the original one is lost, just like with a return in finally. This is one reason try-with-resources (Lesson 9.6) exists: it keeps the original exception and attaches the closing failure as a suppressed exception.

How is finally implemented in bytecode?

javac copies the finally code onto every normal exit path (after the try, after each catch) and adds an exception-table entry of type “any” whose handler runs another copy of the finally code and then rethrows the exception with athrow. You can see the copies with javap -c.

public class Main {
    static int toIntOrDefault(String text, int def) {
        try {
            return Integer.parseInt(text);
        } catch (NumberFormatException e) {
            return def;
        }
    }

    public static void main(String[] args) {
        System.out.println(toIntOrDefault("250", 0));
        System.out.println(toIntOrDefault("25O", 0));
        System.out.println(toIntOrDefault("", -1));
    }
}
250 0 -1

How it works: if parseInt succeeds, the return inside try hands back the number. If it throws, that return never happens; control jumps to the catch, which returns the default. Every path returns a value, so the compiler is satisfied.

P5Medium

finally counts every attempt

Process a list of codes. Count successes and failures in the try and catch, and count every attempt in finally. Print all three counts.

Input
codes = {"10", "A1", "30", "", "50"}
Expected output
ok=3, failed=2, attempts=5
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String[] codes = {"10", "A1", "30", "", "50"};
        int ok = 0, failed = 0, attempts = 0;
        for (String c : codes) {
            try {
                Integer.parseInt(c);
                ok++;
            } catch (NumberFormatException e) {
                failed++;
            } finally {
                attempts++;
            }
        }
        System.out.println("ok=" + ok + ", failed=" + failed + ", attempts=" + attempts);
    }
}
ok=3, failed=2, attempts=5

How it works: exactly one of ok++ and failed++ runs per code, and attempts++ runs every time because it is in finally. A quick self-check: ok + failed == attempts. In real code, finally is used for things that must happen whatever the outcome: closing, unlocking, logging time taken.

P6Medium

Who wins: try's return or finally's?

Predict what each method returns. One shows that finally runs after the return value is decided; the other shows the dangerous return-in-finally.

Input
valueKept() and valueReplaced()
Expected output
finally changed x to 99
valueKept returns 10
valueReplaced returns 99
Show solution and explanation 
public class Main {
    static int valueKept() {
        int x = 10;
        try {
            return x;
        } finally {
            x = 99;
            System.out.println("finally changed x to " + x);
        }
    }

    @SuppressWarnings("finally")
    static int valueReplaced() {
        try {
            return 10;
        } finally {

public class Main {
    public static void main(String[] args) {
        String[] entries = {"10", "20", "x", "30"};

        int totalA = 0;
        for (String e : entries) {
            try {
                totalA += Integer.parseInt(e);
            } catch (NumberFormatException ex) {
                System.out.println("A: skipped " + e);

        int totalB = 0;

public class Main {
    public static void main(String[] args) {
        int[] price = {120, 75, 300};
        int[] product = {0, 2, 4, 1};
        String[] qty = {"5", "two", "1", "10"};
        int total = 0, rejected = 0;
        for (int i = 0; i < product.length; i++) {

            } catch (NumberFormatException e) {

            } catch (ArrayIndexOutOfBoundsException e) {
                rejected++;
                System.out.println("Line " + (i + 1) + ": unknown product " + product[i]);
            }
        }
        System.out.println("Order total: Rs " + total + " (" + rejected + " lines rejected)");
    }
}
Line 1: Rs 600 Line 2: bad quantity "two" Line 3: unknown product 4 Line 4: Rs 750 Order total: Rs 1350 (2 lines rejected)

How it works:

  1. Each line is handled in its own try, so a bad line never blocks good ones.
  2. total += amount runs only after both risky steps succeed, so a rejected line adds nothing.
  3. Different catch blocks give different, useful reasons. A real system would also validate the product number with an if before using it.
P10Business problem

Payment gateway retries

A payment gateway sometimes times out. Try to charge up to 3 times. Log each attempt in finally, stop as soon as one succeeds, and report the result. (The gateway is simulated: it fails on the first two attempts.)

Input
amount = Rs 1499, max attempts = 3
Expected output
Attempt 1: Gateway timeout
Attempt 1 logged
Attempt 2: Gateway timeout
Attempt 2 logged
Attempt 3: paid, id TXN1003
Attempt 3 logged
Payment complete
Show solution and explanation 
public class Main {
    static int calls = 0;

    static String charge(int amount) {
        calls++;
        if (calls < 3) {
            throw new IllegalStateException("Gateway timeout");
        }
        return "TXN" + (1000 + calls);
    }

    public static void main(String[] args) {
        String txn = null;
        for (int attempt = 1; attempt <= 3 && txn == null; attempt++) {
            try {
                txn = charge(1499);
                System.out.println("Attempt " + attempt + ": paid, id " + txn);
            } catch (IllegalStateException e) {
                System.out.println("Attempt " + attempt + ": " + e.getMessage());
            } finally {
                System.out.println("Attempt " + attempt + " logged");
            }
        }
        System.out.println(txn != null ? "Payment complete" : "Payment failed, please retry later");
    }
}
Attempt 1: Gateway timeout Attempt 1 logged Attempt 2: Gateway timeout Attempt 2 logged Attempt 3: paid, id TXN1003 Attempt 3 logged Payment complete

How it works:

  1. The loop condition txn == null stops retrying as soon as a charge succeeds.
  2. Failures are caught per attempt, so the loop can try again; the finally block logs every attempt, success or failure.
  3. charge uses throw to simulate the gateway failing (Lesson 9.4). Real retry code also waits a little longer between attempts and makes sure a payment is never charged twice.
P11Business problem

Settings file with safe defaults

An app reads settings as key=value lines. Numeric settings that are missing or broken must fall back to a default without stopping the app. Print the final settings and how many lines were read.

Input
lines = {"timeout=30", "retries=three", "port=8080", "pool"}
defaults: timeout 10, retries 2, port 80
Expected output
Ignoring "retries=three" (NumberFormatException)
Ignoring "pool" (ArrayIndexOutOfBoundsException)
timeout=30, retries=2, port=8080
4 lines read
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String[] lines = {"timeout=30", "retries=three", "port=8080", "pool"};
        int timeout = 10, retries = 2, port = 80;
        int read = 0;
        for (String line : lines) {
            try {
                String[] kv = line.split("=");
                int value = Integer.parseInt(kv[1]);
                if (kv[0].equals("timeout")) timeout = value;
                else if (kv[0].equals("retries")) retries = value;
                else if (kv[0].equals("port")) port = value;
            } catch (NumberFormatException | ArrayIndexOutOfBoundsException e) {
                System.out.println("Ignoring \"" + line + "\" (" + e.getClass().getSimpleName() + ")");
            } finally {
                read++;
            }
        }
        System.out.println("timeout=" + timeout + ", retries=" + retries + ", port=" + port);
        System.out.println(read + " lines read");
    }
}
Ignoring "retries=three" (NumberFormatException) Ignoring "pool" (ArrayIndexOutOfBoundsException) timeout=30, retries=2, port=8080 4 lines read

How it works:

  1. "retries=three" splits fine but parseInt("three") throws NumberFormatException.
  2. "pool" has no =, so split gives a 1-element array and kv[1] throws ArrayIndexOutOfBoundsException.
  3. Both are handled the same way, so a multi-catch keeps the code short. The default value stays in place for any setting that failed, and finally counts every line.

Real-world scenario questions (asked in company interviews)

Most production bugs around exceptions are about where the try is, what is caught and what finally does. Decide your answer first, then open the model answer.

Travel · seat booking1–3 years

Seats stay locked after a failed booking

A booking service locks a seat, charges the customer, then unlocks the seat as the last line of the method. When the payment call throws, customers find that seat shows as “locked” for everyone until the server restarts. What's the bug and the fix?

The interviewer is checking: do you know that clean-up belongs in finally?

Show a strong answer
  • The unlock is the last line, so when payment throws, the rest of the method, including the unlock, is skipped.
  • Fix: lock(); try { charge(); confirm(); } finally { unlock(); }. The lock is taken just before the try, so finally only unlocks what was really locked.
  • Also add a lock timeout as a safety net, and log the payment failure so it can be investigated.

Avoid: copying unlock() into every catch block. A new exception type or an early return would miss it.

Fintech · payments1–3 years

Failed payments reported as successful

A processPayment() method has finally { return "SUCCESS"; } “so the UI always gets a status.” Finance reports that some declined cards were shown to customers as paid. Explain.

The interviewer is checking: do you know that return in finally discards exceptions?

Show a strong answer
  • When the gateway throws a decline exception, finally still runs, and its return replaces the pending exception. The caller receives “SUCCESS” and the exception disappears without any log.
  • Return the real status from the try (success) and the catch (failure with reason); keep finally only for clean-up such as releasing connections or stopping a timer.
  • Enable -Xlint:finally or a static-analysis rule so this pattern fails the build.

Avoid: any return, break or throw inside finally.

E-commerce · code reviewFresher

One catch (Exception e) for everything

A checkout method catches Exception and always shows “Payment failed, try again.” Customers whose address pincode was invalid keep retrying the payment. How would you improve the handling?

The interviewer is checking: can you use multiple catch blocks to give different, useful responses?

Show a strong answer
  • Different problems need different responses: validation errors (bad pincode) should tell the user what to fix; payment declines should say so; a timeout can suggest retrying.
  • Use specific catch blocks, most specific first, and a final general catch only to log unexpected errors with their stack trace.
  • Better still, validate the address before starting payment, so that problem never reaches the payment code.

Avoid: one generic message for every failure. It hides the cause from both users and developers.

Logistics · batch import3+ years

Where to put the try in a nightly import

A nightly job imports 50,000 delivery records. Currently the whole loop is inside one try; one bad record aborts the rest. A teammate proposes a try around every single line inside the loop body. What do you propose?

The interviewer is checking: do you choose the try's scope deliberately?

Show a strong answer
  • One try around the whole loop is too coarse: an error in record 7 skips 49,993 good ones.
  • A try around every line is too fine: the code becomes unreadable and later lines run with half-processed data.
  • Put one try around the processing of one record (the unit of work). On failure, log the record id and reason, add it to an error file, and continue. Use finally for per-record counters or timing.
  • Abort the whole job only for failures that affect every record, such as the database being down, and stop if the error rate passes a threshold.

Avoid: deciding try placement by habit. Match it to the unit of work that can succeed or fail on its own.
