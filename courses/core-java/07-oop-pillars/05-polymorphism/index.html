Polymorphism: compile-time and runtime

One variable of type Notification can hold an SMS, an email or a WhatsApp message, and n.send() does the right thing for each. That's polymorphism: one name, many forms. You'll see which decisions javac makes at compile time (overloading), which the JVM makes at run time (overriding), how upcasting and downcasting work, how instanceof and Java 16's pattern matching keep casts safe, and then practise with 10 problems.

2 Definition

What is polymorphism?

Formal definition (write this in exams)

Polymorphism ("many forms") is the ability of a single method name or reference type to work with different forms. Java has two kinds. Compile-time (static) polymorphism is achieved by method overloading: the compiler selects the method from the number and declared types of the arguments. Runtime (dynamic) polymorphism is achieved by method overriding with a superclass reference: the JVM selects the method from the actual class of the object at run time, a process called dynamic method dispatch.

In simple words

"Send this message" means different things for SMS and email, but you give the same instruction. Overloading is one name for different inputs; overriding is one call for different objects.

Words you'll meet in this lesson

DowncastingParent-type reference cast back to a child type: (Sms) n. Needs a check.

Who decides what

Exam tip: remember the sentence "reference type decides what you can call; object type decides what actually runs". It answers most output-prediction questions on polymorphism. Overloading = compile time; overriding = run time.

4 Step by step

From upcast to safe downcast

  1. Upcast: store a child in a parent variable

    Notification n = new Sms();
    No conversion happens: the reference still points at the same Sms object. Only javac's view changes: through n you may call only what Notification declares.

  2. Call an overridden method

    n.send();      // "SMS sent"
    javac checks that Notification has send() and emits invokevirtual Notification.send. At run time the JVM reads the object's class (Sms) and runs the most specific send(), using a per-class method table so this is fast.

  3. Need a child-only method? Check first

    if (n instanceof Sms) {
    Sms s = (Sms) n;
    System.out.println(s.maxChars());
}
    instanceof asks the JVM about the object's real class. It's false for null, so it also protects against NullPointerException.

  4. Java 16+: pattern matching does both at once

    if (n instanceof Sms s) {
    System.out.println(s.maxChars());
}
    If the test is true, s is declared and already cast. It exists only where the test is known to be true. Standard since Java 16 (preview in 14 and 15).

  5. A wrong cast compiles, then fails

    Notification n = new Email();
Sms s = (Sms) n;     // ClassCastException at run time
    javac allows it because a Notification could be an Sms. Every cast is checked by the JVM (a checkcast instruction). Impossible casts, like Notification to String, are rejected at compile time: incompatible types.

What you see
  1. Upcast: an Sms is a Notification, so it can be stored in a Notification variable with no cast.
  2. Dynamic dispatch: n.send() prints SMS sent, the Sms version, although n is declared as Notification.
  3. Many forms: the same variable now holds an Email, and the same call prints Email sent.
  4. Reference type limits calls: maxChars() exists only in Sms. javac sees a Notification variable and refuses.
  5. instanceof: n holds an Email, so the test is false and the else branch runs. Nothing is cast.
  6. Bad downcast: forcing (Sms) n compiles, but the JVM finds an Email and throws ClassCastException.
Behind the screen
  1. The variable has a declared type (Notification) that javac uses; the object has a real class (Sms) that the JVM uses.
  2. javac checks send() exists in Notification. At run time the JVM looks up send in the object's class, Sms, and runs it.
  3. After n = new Email(), the same invokevirtual instruction finds Email's send().
  4. Method availability is decided at compile time from the declared type. The object's extra methods are invisible through n.
  5. instanceof is evaluated at run time on the object. Email is not an Sms, so the guarded code is skipped.
  6. A cast is a promise to javac, checked again by the JVM's checkcast. A broken promise throws ClassCastException.

Polymorphism in real systems

Polymorphism is what lets large systems add new types without editing old code.

9 Quiz and revision

Check yourself

Quick revision

Lesson 7.5 in one screen

  • Polymorphism = one name, many forms.
  • Compile-time: overloading, chosen by javac from declared argument types.
  • Runtime: overriding through a parent reference, chosen by the JVM from the object's class.
  • Reference type decides what you can call; object type decides what runs. Fields follow the reference type.
  • Upcasting is automatic; downcasting needs (Type) and can throw ClassCastException.
  • Guard downcasts with instanceof; it's false for null.
  • Java 16+: if (x instanceof Sms s) tests and casts in one step.

Interview and viva questions

What is dynamic method dispatch?

It's the mechanism by which a call to an overridden method through a superclass reference is resolved at run time, based on the actual object's class. javac emits an invokevirtual instruction naming the method; the JVM looks it up starting from the object's class (using per-class method tables) and runs the most specific version.

Why are static, private and final methods statically bound?

Static methods belong to the class, private methods aren't inherited, and final methods can't be overridden. In each case there's only one possible target, so the call can be fixed at compile time. Only overridable instance methods need run-time dispatch.

What is the difference between upcasting and downcasting?

Upcasting converts a child reference to a parent type (Animal a = dog;); it's implicit and always safe. Downcasting converts a parent reference to a child type (Dog d = (Dog) a;); it's explicit, needed to access child-only members, and fails with ClassCastException if the object isn't really that child type.

Is excessive instanceof a design smell?

Often, yes. A chain of if (x instanceof A) … else if (x instanceof B) usually means behaviour that should be an overridden method. Use instanceof for genuine special cases (one channel with an extra limit), not as a replacement for polymorphism. (Modern Java's sealed classes and pattern-matching switch make exhaustive type checks safer, but that's beyond this lesson.)

Are fields polymorphic in Java?

No. Field access is resolved at compile time from the reference's declared type. If parent and child both declare limit, parentRef.limit reads the parent's field even when the object is a child. That's another reason to keep fields private and access them through overridable methods.

P4Medium

Pattern matching for instanceof

public class Main {
    public static void main(String[] args) {
        Object[] values = {"Pune", 21, 3.7};

P5Medium

Avoid a ClassCastException

A fleet has trucks and bikes stored as Vehicle. Print the total capacity of the trucks only, safely, without any cast that could fail.

Input
Truck 9000 kg, Bike, Truck 6000 kg
Expected output
Truck capacity: 15000 kg (skipped 1)
Show solution and explanation 
class Vehicle { }

class Truck extends Vehicle {
    final int capacityKg;
    Truck(int capacityKg) { this.capacityKg = capacityKg; }
}

class Bike extends Vehicle { }

public class Main {
    public static void main(String[] args) {
        Vehicle[] fleet = { new Truck(9000), new Bike(), new Truck(6000) };

        int skipped = 0;

P8Business problem

Payment processing with special cases

A checkout processes a list of payments polymorphically with process(). Card payments additionally need an OTP step; only for those, call sendOtp() using pattern matching. Print the log for a card, a UPI and a cash-on-delivery payment.

Input
Card Rs 2499, UPI Rs 349, COD Rs 799
Expected output
OTP sent to registered mobile
Card charged Rs 2499.0
UPI collect request for Rs 349.0
Collect Rs 799.0 at the door
Collected online: Rs 2848.0
Show solution and explanation 
class Payment {
    protected final double amount;
    Payment(double amount) { this.amount = amount; }

    String process() { return "Processed Rs " + amount; }
}

class CardPayment extends Payment {
    CardPayment(double amount) { super(amount); }

    @Override
    String process() { return "Card charged Rs " + amount; }

    String sendOtp() { return "OTP sent to registered mobile"; }
}

class UpiPayment extends Payment {
    UpiPayment(double amount) { super(amount); }

    @Override
    String process() { return "UPI collect request for Rs " + amount; }
}

class CashOnDelivery extends Payment {
    CashOnDelivery(double amount) { super(amount); }

    @Override
    String process() { return "Collect Rs " + amount + " at the door"; }
}

public class Main {
    public static void main(String[] args) {
        Payment[] payments = { new CardPayment(2499), new UpiPayment(349), new CashOnDelivery(799) };
        double online = 0;
        for (Payment p : payments) {
            if (p instanceof CardPayment c) {
                System.out.println(c.sendOtp());
            }
            System.out.println(p.process());
            if (!(p instanceof CashOnDelivery)) {
                online += p.amount;
            }
        }
        System.out.println("Collected online: Rs " + online);
    }
}

How it works:

  1. The common step, process(), is polymorphic: each class supplies its own text.
  2. The extra OTP step exists only for cards, so it's a card-only method reached with instanceof CardPayment c.
  3. 2499 + 349 = 2848 is collected online; COD is excluded with a negated instanceof check.
P9Business problem

Payroll with a manager-only bonus

A monthly payroll loops over Employee[] and calls the overridden monthlyPay(). Managers also get Rs 2,000 per team member as a team bonus, available only on Manager. Print each line and the total.

Input
Employee "Anil" 40000; Manager "Kiran" 80000, team 6; Employee "Sara" 45000
Expected output
Anil   Rs 40,000.00
Kiran  Rs 100,000.00
Sara   Rs 45,000.00
Total  Rs 185,000.00
Show solution and explanation 
class Employee {
    protected final String name;
    protected final double basic;

    Employee(String name, double basic) {
        this.name = name;
        this.basic = basic;
    }

    double monthlyPay() { return basic; }
}

class Manager extends Employee {
    private final int teamSize;

    Manager(String name, double basic, int teamSize) {
        super(name, basic);
        this.teamSize = teamSize;
    }

    @Override
    double monthlyPay() { return basic * 1.10; }

    double teamBonus() { return teamSize * 2000; }
}

public class Main {
    public static void main(String[] args) {
        Employee[] staff = {
            new Employee("Anil", 40000), new Manager("Kiran", 80000, 6), new Employee("Sara", 45000)
        };
        double total = 0;
        for (Employee e : staff) {
            double pay = e.monthlyPay();
            if (e instanceof Manager m) {
                pay += m.teamBonus();
            }
            System.out.printf("%-6s Rs %,.2f%n", e.name, pay);
            total += pay;
        }
        System.out.printf("Total  Rs %,.2f%n", total);
    }
}
Anil Rs 40,000.00 Kiran Rs 100,000.00 Sara Rs 45,000.00 Total Rs 185,000.00

How it works:

  1. monthlyPay() is overridden: Kiran gets 80000 × 1.10 = 88,000 through dynamic dispatch.
  2. The team bonus exists only on Manager, so we downcast safely with pattern matching: 6 × 2,000 = 12,000.
  3. Total: 40,000 + 1,00,000 + 45,000 = 1,85,000.
P10Business problem

Delivery vehicles: who can take this order?

For a 25 kg order going 8 km, ask every vehicle in the fleet canTake(kg, km) (overridden per type) and print which vehicles qualify. Bikes carry up to 20 kg within 15 km; vans up to 500 kg any distance; drones up to 5 kg within 10 km.

Input
order 25 kg, 8 km; fleet: Bike, Van, Drone, Van
Expected output
Order: 25 kg, 8 km
  BIKE-1  no
  VAN-2  can take it
  DRONE-3  no
  VAN-4  can take it
Show solution and explanation 
class Vehicle {
    private static int counter = 0;
    protected final String id;

    Vehicle(String prefix) {
        counter++;
        id = prefix + counter;
    }

    boolean canTake(int kg, int km) { return false; }
}

class Bike extends Vehicle {
    Bike() { super("BIKE-"); }

    @Override
    boolean canTake(int kg, int km) { return kg <= 20 && km <= 15; }
}

class Van extends Vehicle {
    Van() { super("VAN-"); }

    @Override
    boolean canTake(int kg, int km) { return kg <= 500; }
}

class Drone extends Vehicle {
    Drone() { super("DRONE-"); }

    @Override
    boolean canTake(int kg, int km) { return kg <= 5 && km <= 10; }
}

public class Main {
    public static void main(String[] args) {
        Vehicle[] fleet = { new Bike(), new Van(), new Drone(), new Van() };
        int kg = 25, km = 8;
        System.out.println("Order: " + kg + " kg, " + km + " km");
        for (Vehicle v : fleet) {
            System.out.println("  " + v.id + (v.canTake(kg, km) ? "  can take it" : "  no"));
        }
    }
}
Order: 25 kg, 8 km BIKE-1 no VAN-2 can take it DRONE-3 no VAN-4 can take it

How it works:

  1. Each vehicle type owns its rule; the dispatcher only calls canTake.
  2. The static counter in the parent gives each vehicle a unique id across all types.
  3. 25 kg rules out the bike (20 kg) and the drone (5 kg); both vans qualify.

Real-world scenario questions (asked in company interviews)

Polymorphism removes if-else chains; misused casts bring crashes. Decide your answer first, then open the model answer.

Notifications · new channelFresher

Adding WhatsApp alerts

An order service sends alerts with if (type == SMS) sendSms(); else if (type == EMAIL) sendEmail(); in four different places. The product team wants WhatsApp added next sprint. What would you propose?

The interviewer is checking: can you replace type checks with runtime polymorphism?

Show a strong answer
  • Create a parent type Notification (or interface Channel) with send(message); SMS, email and WhatsApp classes override it.
  • The order service keeps a list of channels and calls channel.send(msg); dynamic dispatch picks the right implementation.
  • WhatsApp becomes a new class plus one line of configuration. The four if-else blocks disappear.

Avoid: adding a fifth else if to each of the four places.

Logistics · production crash1–3 years

ClassCastException after a new vehicle type

A dispatch job loops over List<Vehicle> and does Truck t = (Truck) v; because "all our vehicles are trucks". Operations added electric bikes yesterday, and the nightly job crashed with ClassCastException. How do you fix it properly?

The interviewer is checking: do you understand unsafe downcasts and the polymorphic alternative?

Show a strong answer
  • Immediate fix: guard with if (v instanceof Truck t) and handle other vehicles explicitly (skip with a log line, or a different path).
  • Better: move the behaviour the job needs (capacityKg(), canCarry(parcel)) into Vehicle as an overridable method, so no cast is needed at all.
  • Add a test with a mixed fleet so a new vehicle type can't break the job silently again.

Avoid: catching ClassCastException and ignoring it. That hides real data problems.

Fintech · code review1–3 years

The overload that never runs

A FeeCalculator has fee(Payment p) and a special fee(UpiPayment p) returning 0. Checkout calls calculator.fee(payment) where payment is declared as Payment. UPI users are being charged. Why?

The interviewer is checking: do you know overloads are chosen at compile time?

Show a strong answer
  • Overload resolution uses the declared type of the argument. The variable is a Payment, so javac always picks fee(Payment), even when the object is a UpiPayment.
  • Fix: move the rule onto the payment classes as an overridden method (payment.fee()), so the JVM dispatches on the object.
  • Alternatively use instanceof inside one method, but overriding scales better.

Avoid: assuming overloading behaves like overriding. Only overriding looks at the object.

SaaS · reporting3+ years

A 40-branch instanceof chain

A report exporter has one method with 40 instanceof branches, one per document type, each building the export differently. Every new document type means editing this method, and merge conflicts happen weekly. How would you refactor it?

The interviewer is checking: can you move type-specific behaviour to where it belongs?

Show a strong answer
  • Give the document hierarchy an overridable export(Exporter e) (or an interface Exportable), and move each branch into its own class.
  • If exporting must stay outside the documents (for example, many export formats), use a registry: a map from document type to an exporter object, with polymorphic exporter classes.
  • Migrate gradually: move branches one at a time behind tests, keeping the old method as a fallback until it's empty.

Avoid: a big-bang rewrite. Refactor incrementally with tests.
