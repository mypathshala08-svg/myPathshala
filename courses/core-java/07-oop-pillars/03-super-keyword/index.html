The super keyword

A child object is built on top of its parent part, so the parent's constructor must run first. The super keyword is how a child talks to its parent: super(...) calls the parent's constructor, super.method() reuses the parent's version of a method, and super.field reaches a hidden parent field. You'll see the hidden super() that javac inserts, the classic compile error it causes, the exact order constructors run in, and then practise with 10 problems.

1 The story

The validation Riya wrote twice

In the college ERP, Person's constructor checks that a name isn't empty and trims extra spaces. Riya's new Student extends Person constructor sets the name again, with the same checks copied in. Then the rule changes to "capitalise the first letter", and only Person gets the fix.

Riya

Sir, Student extends Person, but I still had to copy Person's name checks into Student's constructor.

Arjun Sir

You don't. A Student object has a Person part, and Person's constructor already knows how to build it. Write super(name); as the first line, and Person does its own job, with its own checks.

Riya

Why the first line?

Arjun Sir

Because you build a house from the foundation up. The parent part must be ready before the child's code touches anything. Java enforces that order, and if you forget, it quietly inserts super() for you.

2 Definition

What is the super keyword?

Formal definition (write this in exams)

super is a keyword used inside a subclass to refer to its immediate superclass. It has three uses: super(arguments) invokes a superclass constructor and must be the first statement of a constructor; super.method(...) invokes the superclass's version of a method, even if the subclass overrides it; and super.field accesses a superclass field hidden by a subclass field of the same name. If a constructor does not begin with this(...) or super(...), the compiler inserts a call to super().

In simple words

this means "me"; super means "the parent part of me". Use it to let the parent build its part, or to reuse what the parent already does.

3 Types and ways to use it

Three uses of super

super(args)

Call the parent's constructor so it builds its part of the object.

constructors only

super.method()

Reuse the parent's version, then add to it. Most useful with overriding (Lesson 7.4).

reuse, then extend

super.field

Reach a parent field that a child field with the same name hides.

rare; avoid hiding

All three in one program

class Product {
    String label = "product";
    double price;

    Product(double price) {
        this.price = price;
    }

    String describe() {
        return "Price Rs " + price;
    }
}

class Book extends Product {
    String label = "book";              // hides Product's label
    String author;

    Book(double price, String author) {
        super(price);                   // 1. parent constructor
        this.author = author;
    }

    String describe() {
        return super.describe() + " by " + author;   // 2. parent method
    }

    void labels() {
        System.out.println(label + " / " + super.label);   // 3. parent field
    }
}

public class Main {
    public static void main(String[] args) {
        Book b = new Book(399, "R. K. Narayan");
        System.out.println(b.describe());
        b.labels();
    }
}
Price Rs 399.0 by R. K. Narayan book / product

4 Step by step

What happens when you write new Student("Riya", 42)

  1. Memory for the whole object is set aside

    One object is created with room for Person's name and Student's roll, all at default values (null, 0).

    The new instruction allocates the object first. Constructors don't create objects; they initialise an object that already exists.

  2. The child constructor starts and immediately calls up

    Student(String name, int roll) {
    super(name);
    this.roll = roll;
}
    A frame for Student(...) is pushed, and its first instruction pushes a frame for Person(String) on top, both with this pointing at the same object.

  3. The chain reaches Object, then unwinds

    Person's constructor has no explicit super, so javac inserted super(): Object's constructor runs first. Then Person's body sets name.

    In the bytecode (javap -c), every constructor begins with invokespecial of its parent's <init>, even when you didn't write super.

  4. Field initializers, then the child's body

    class Car extends Vehicle {
    int seats = 5;              // runs after super(...) returns
    Car() { System.out.println("Car()"); }
}
    javac places the code of field initializers right after the super(...) call in every constructor. So the order is: parent constructor, then the child's field initializers, then the rest of the child's constructor body.

  5. Fix the classic compile error

    // Person has only Person(String name)
class Student extends Person {
    Student(int roll) { ... }          // ✗ hidden super() has no match
    Student(String n, int roll) {
        super(n);                      // ✓ call the constructor that exists
    }
}
    Either call an existing parent constructor explicitly, or add a no-argument constructor to the parent. The same error appears if the child has no constructor at all, because the default constructor also calls super().
5 See it happen

Called child to parent, built parent to child: both views

Left: the code being run and the console. Right: constructor frames on the stack and the one object on the heap.

new ElectricCar("MH-01-EV-7", 40) 6 steps
What you see
  1. new: Java calls ElectricCar's constructor, the class you named.
  2. super(regNo, 5): before doing anything else, ElectricCar's constructor calls Car's. Nothing has printed.
  3. super(regNo): Car's constructor calls Vehicle's. Vehicle's body is the first to complete, so its message prints first.
  4. Back in Car: Vehicle's constructor returned. Car sets seats and prints.
  5. Back in ElectricCar: finally the child sets its own field and prints.
  6. Done: called child → parent, completed parent → child. The finished object is assigned to e.
Behind the screen
  1. new allocates object #1 with every field at its default, then pushes ElectricCar's constructor frame.
  2. super(regNo, 5) pushes Car's constructor frame. Both frames work on the same object.
  3. Car's super(regNo) pushes Vehicle's frame; Vehicle's own hidden super() ran Object's constructor. Vehicle sets regNo.
  4. Vehicle's frame is popped. Car's constructor continues after its super line and sets seats.
  5. Car's frame is popped. ElectricCar's constructor sets batteryKwh.
  6. The last constructor frame is popped and main's e receives the reference to #1.
6 Real-world use

super in real systems

Wherever classes extend other classes, super keeps the parent's work in the parent.

Watch it with an example: the order in which constructors run

PremiumOrder extends Order. Creating one runs three constructors. super(…) always runs the parent's part first, so the parent's fields are ready before the child uses them.

new PremiumOrder("A-17") 6 steps
Animated example
  1. new PremiumOrder("A-17"): memory for all fields (parent's and child's) is created with defaults, then the child constructor starts.
  2. super(id): its first line calls the parent constructor. If you don't write super(…), Java inserts super() for you.
  3. All the way up: Order's constructor implicitly calls Object() first. The root always finishes first.
  4. Parent's part: back in Order, id and the creation time are set.
  5. Child's part: only now does PremiumOrder run its own line, priority = true. It can safely use id, because the parent already set it.
  6. Order of work: top-down: Object → Order → PremiumOrder. Base classes that stamp IDs and timestamps on every record rely on this.

1. Custom exceptions

A bank's InsufficientFundsException passes its message up with super(message), so getMessage() and the stack trace work as usual (Lesson 9.5).

new InsufficientFunds("…")→super(message)→getMessage() works

2. Extending, not replacing, behaviour

An SMS notification's format() calls super.format() for the standard header and body, then trims it to the SMS length. The common format is maintained in one place.

SmsNotification→super.format() + trim→160-char SMS

3. toString and equals in hierarchies

A child's toString() often starts with super.toString() so the parent's fields appear in logs without repeating them. The same pattern is used for equals in some codebases.

log(account)→super.toString() + extras→complete log line

4. Base classes that stamp every record

A base entity's no-argument constructor sets a created-at time. Every child constructor runs it through the implicit super(), so no record is ever missing it.

new Order(...)→implicit super()→createdAt filled

Examples are simplified. Frameworks also call constructors for you (for example when loading objects from a database), which is one reason many of them expect a no-argument constructor to exist.

A manager's pay, built on an employee's

class Employee {
    protected String name;
    protected double basic;

    Employee(String name, double basic) {
        this.name = name;
        this.basic = basic;
        System.out.println("Employee constructor: " + name);
    }

    double salary() {
        return basic;
    }

    String payslip() {
        return name + " | basic " + basic;
    }
}

class Manager extends Employee {
    private double allowance;

    Manager(String name, double basic, double allowance) {
        super(name, basic);
        this.allowance = allowance;
        System.out.println("Manager constructor: allowance " + allowance);
    }

    @Override
    double salary() {
        return super.salary() + allowance;
    }

    @Override
    String payslip() {
        return super.payslip() + " | allowance " + allowance + " | total " + salary();
    }
}

public class Main {
    public static void main(String[] args) {
        Manager m = new Manager("Kiran", 60000, 15000);
        System.out.println(m.payslip());
    }
}

  • @OverrideMarks a method that replaces the parent's version. Lesson 7.4 covers it fully.
  • super.salary() + allowanceReuses the parent's calculation, then adds the manager's part.
  • super.payslip() + ...The common payslip text stays in Employee; Manager only appends.

9 Quiz and revision

Check yourself

Quick revision

Lesson 7.3 in one screen

  • super(args): call the parent constructor; first statement only.
  • No explicit call → javac inserts super(); fails if the parent has no no-arg constructor.
  • Order: allocate object → parent constructor (up to Object) → child field initializers → child constructor body.
  • Output from constructors appears parent first, child last.
  • super.method(): reuse the parent's version inside an overriding method.
  • super.field: reach a hidden parent field. Better: avoid field hiding.
  • super can't be used in static code, and this(...) and super(...) can't both appear in one constructor.

Interview and viva questions

Why must super() be the first statement in a constructor?

So that the parent part of the object is fully initialised before the child's code uses it. If the child could run code first, it might call an inherited method that relies on parent fields that aren't set yet. (Newer Java versions relax this: previewed from Java 22 and standard from Java 25, statements that don't use the object being built may come before super(...). For Java 8–21 and for exams, treat "first statement" as the rule.)

What happens if you don't write super() in a constructor?

The compiler inserts super(); automatically. If the parent class has no accessible no-argument constructor, compilation fails with "constructor X in class X cannot be applied to given types". The fix is to call an existing parent constructor explicitly with the right arguments.

What is the difference between this() and super()?

this(...) calls another constructor of the same class; super(...) calls a constructor of the parent class. Both must be the first statement, so a constructor can have one or the other. Constructor chains inside a class using this(...) end at a constructor that (explicitly or implicitly) calls super(...).

How many objects are created when you instantiate a subclass?

One. The parent constructors don't create separate parent objects; they initialise the parent's section of the same object. That's why this inside the parent's constructor refers to the child object.

Is it a good idea to call an overridable method from a constructor?

No. The parent's constructor runs before the child's fields are initialised. If it calls a method the child overrides, the child's version runs and sees default values (0, null). That's a classic hidden bug; constructors should call only private or final methods.

P8Business problem

Fixed deposit account built on Account

Account(String no, double amount) rejects amounts below Rs 1,000. A FixedDeposit also has a tenure in months and a rate, and its summary() must show the parent's summary plus the maturity amount (simple interest). Create an FD of Rs 1,00,000 for 12 months at 7%.

Input
FD-501, Rs 100000, 12 months, 7%
Expected output
FD-501 | principal Rs 100000.0 | 12 months @ 7.0% | maturity Rs 107000.0
Show solution and explanation 
class Account {
    private final String no;
    protected final double amount;

    Account(String no, double amount) {
        if (amount < 1000) throw new IllegalArgumentException("Minimum Rs 1000");
        this.no = no;
        this.amount = amount;
    }

    String summary() {
        return no + " | principal Rs " + amount;
    }
}

class FixedDeposit extends Account {
    private final int months;
    private final double ratePercent;

    FixedDeposit(String no, double amount, int months, double ratePercent) {
        super(no, amount);
        this.months = months;
        this.ratePercent = ratePercent;
    }

    double maturity() {
        return amount + amount * ratePercent / 100 * months / 12;
    }

    @Override
    String summary() {
        return super.summary() + " | " + months + " months @ " + ratePercent + "% | maturity Rs " + maturity();
    }
}

public class Main {
    public static void main(String[] args) {
        FixedDeposit fd = new FixedDeposit("FD-501", 100000, 12, 7);
        System.out.println(fd.summary());
    }
}
FD-501 | principal Rs 100000.0 | 12 months @ 7.0% | maturity Rs 107000.0

How it works:

  1. super(no, amount) reuses Account's minimum-amount check; an FD of Rs 500 would be rejected by the parent before the child sets anything.
  2. super.summary() reuses the common text; the child only appends FD details.
  3. Simple interest: 1,00,000 × 7% × 12/12 = 7,000, so maturity is Rs 1,07,000.

    }
}

public class Main {
    public static void main(String[] args) {
        System.out.println("Normal: Rs " + new Delivery(12).charge());
        System.out.println("Express: Rs " + new ExpressDelivery(12).charge());
        System.out.println("Night express: Rs " + new NightExpress(12).charge());
    }
}
Normal: Rs 136.0 Express: Rs 204.0 Night express: Rs 304.0

How it works:

  1. Base charge: 40 + 8 × 12 = 136.
  2. Express: 136 × 1.5 = 204, computed by calling the parent's charge and adding the surcharge.
  3. Night express: Express's 204 + 100 = 304. If the per-km rate changes in Delivery, all three update together.
P10Business problem

Intern payroll with a stipend cap

Employee(String id, double monthlyPay) prints a joining message. An Intern is created with a stipend; if the stipend is above Rs 25,000 it is capped at 25,000 before being passed to the parent. Print the joining messages and both pays.

Input
Employee "E10" 55000; Intern "I07" stipend 30000
Expected output
Joined: E10 at Rs 55000.0
Joined: I07 at Rs 25000.0
E10 pay: 55000.0
I07 pay: 25000.0
Show solution and explanation 
class Employee {
    protected final String id;
    protected final double monthlyPay;

    Employee(String id, double monthlyPay) {
        this.id = id;
        this.monthlyPay = monthlyPay;
        System.out.println("Joined: " + id + " at Rs " + monthlyPay);
    }
}

class Intern extends Employee {
    private static final double CAP = 25000;

    Intern(String id, double stipend) {
        super(id, Math.min(stipend, CAP));
    }

    double pay() {
        return monthlyPay;
    }
}

public class Main {
    public static void main(String[] args) {
        Employee e = new Employee("E10", 55000);
        Intern i = new Intern("I07", 30000);
        System.out.println(e.id + " pay: " + e.monthlyPay);
        System.out.println(i.id + " pay: " + i.pay());
    }
}
Joined: E10 at Rs 55000.0 Joined: I07 at Rs 25000.0 E10 pay: 55000.0 I07 pay: 25000.0

How it works:

  1. Code can't run before super(...) in Java 8–21, but an expression inside its arguments can: Math.min(stipend, CAP) is evaluated first, then passed up.
  2. CAP is static, so it can be used there; an instance field of Intern could not be, because the object isn't initialised yet.
  3. The parent's joining message already shows the capped value, 25000.0.

Real-world scenario questions (asked in company interviews)

Constructor order and super calls cause surprisingly many production bugs. Decide your answer first, then open the model answer.

Banking · build failureFresher

"I only added a constructor to the parent"

A teammate adds Account(String accountNo) to the Account class so every account must have a number. Suddenly SavingsAccount and CurrentAccount, which they didn't touch, fail to compile. Explain why and how to fix it.

The interviewer is checking: do you know about the default constructor and the implicit super()?

Show a strong answer
  • Before the change, Account had no constructors, so javac gave it a default no-arg constructor. Once any constructor is declared, that default disappears.
  • The child constructors (or their default constructors) call super() implicitly, which no longer exists, hence "constructor Account in class Account cannot be applied to given types".
  • Fix: give each child a constructor that takes the account number and calls super(accountNo). That also enforces the new rule for every account type.

Avoid: adding an empty Account() just to make it compile. It defeats the "every account has a number" rule.

E-commerce · notifications1–3 years

The footer disappeared from SMS alerts

Notification.format() adds the order ID and a "Reply STOP to unsubscribe" footer required by regulations. SmsNotification overrides format() to shorten the text, and the footer is missing from all SMS messages. What likely happened?

The interviewer is checking: do you know when to extend the parent's behaviour with super.method()?

Show a strong answer
  • The override rebuilt the text from scratch instead of calling super.format(), so the parent's footer logic never runs for SMS.
  • Fix: String full = super.format(); return shorten(full);, with shortening that always keeps the footer.
  • Better design: make the parent's format() final and expose a smaller hook for the body (template method, Lesson 7.6), so no child can skip mandatory parts.

Avoid: copying the footer text into each child. The next regulation change would miss one.

SaaS · reports1–3 years

A null in the constructor that "can't be null"

Report's constructor calls init(). SalesReport overrides init() to use its field private final List<String> regions = List.of("North", "South"), and crashes with a NullPointerException on regions, although the field is initialised right there. Why?

The interviewer is checking: do you know the exact order of constructor execution?

Show a strong answer
  • Order: Report's constructor runs first (via super()), and it calls init(). Dynamic dispatch picks SalesReport's version, but SalesReport's field initializers haven't run yet, so regions is still null.
  • Fix: don't call overridable methods from constructors. Make init() private or final in Report, or do the setup in the child's own constructor after super(...).
  • Static analysis tools flag "overridable method call in constructor" for exactly this reason.

Avoid: "fixing" it with a null check inside init(). The design is the bug.

Fintech · exceptionsFresher

Error logs with "null" as the message

A payment service throws new PaymentDeclinedException("Card expired"), but logs show PaymentDeclinedException: null. The exception class stores the text in its own field msg. What's wrong?

The interviewer is checking: do you know to pass data up with super(...)?

Show a strong answer
  • getMessage() is inherited from Throwable and reads Throwable's own message field. The custom class never passed the text up, so the implicit super() left it null.
  • Fix: PaymentDeclinedException(String message) { super(message); } and remove the duplicate msg field.
  • Also pass the cause with super(message, cause) when wrapping another exception, so stack traces stay complete (Module 9).

Avoid: overriding getMessage() to return the private field. Let the parent do its job.
