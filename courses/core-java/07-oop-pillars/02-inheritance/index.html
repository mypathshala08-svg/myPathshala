Inheritance and types of inheritance

Student, Teacher and Staff all have a name, a phone number and a way to print contact details. Copying that code three times means fixing every bug three times. Inheritance lets a class take over another class's fields and methods with one word, extends. You'll see what an inherited object looks like in memory, the types of inheritance Java allows, why it refuses multiple parents, and then practise with 10 problems.

1 The story

Three classes, one copy-paste bug

Riya is building a small college ERP. She writes Student, then copies it to make Teacher and Staff: each has name, phone and printContact(). Then the principal asks for phone numbers to be printed with +91. She fixes it in Student, forgets Staff, and the notice board shows two formats.

Riya

Sir, three classes, the same three members, and I keep fixing bugs in one and forgetting the others.

Arjun Sir

Ask yourself: is a student a kind of person? Is a teacher? Then write Person once and say class Student extends Person. Student gets name, phone and printContact for free, and adds only roll number.

Riya

And the +91 fix?

Arjun Sir

One place, in Person. Every class that extends it gets the fix. That's inheritance, the second pillar.

2 Definition

What is inheritance?

Formal definition (write this in exams)

Inheritance is the mechanism by which one class (the subclass or child) acquires the fields and methods of another class (the superclass or parent), declared in Java with the extends keyword. It models an IS-A relationship, promotes code reuse, and is the basis for method overriding and runtime polymorphism. A Java class can extend exactly one class; every class that extends nothing implicitly extends java.lang.Object.

In simple words

A child class starts with everything the parent has and then adds its own extras. "A savings account is an account, plus interest."

Words you'll meet in this lesson

SuperclassThe parent (base) class being extended: Person.
SubclassThe child (derived) class: Student extends Person.
IS-AThe test for inheritance: "a Student is a Person" must make sense.
HAS-AComposition: one object holds another as a field. A car has an engine; it is not one.
Objectjava.lang.Object, the root of every class hierarchy.
Diamond problemAmbiguity when a class gets the same method from two parents.

Inheritance at a glance

Syntaxclass Student extends Person { … }
Direct parentsExactly one class. extends A, B is a compile error. A class can implement many interfaces (Lesson 7.7).
InheritedPublic and protected fields and methods; package-private ones too if both classes are in the same package
Private membersPresent inside the child object, but not accessible by name in the child's code. Reach them through inherited public methods.
ConstructorsNever inherited. The child writes its own and calls the parent's with super(...) (Lesson 7.3).
RootEvery class ends at Object, so every object has toString(), equals(), hashCode() and getClass()

Exam tip: Java supports single, multilevel and hierarchical inheritance with classes. Multiple and hybrid inheritance are supported only through interfaces. A common MCQ asks "Which inheritance is not supported by classes in Java?": the answer is multiple.

3 Types and ways to use it

The types of inheritance

Single

One child, one parent.
Savings extends Account

A ← B

Multilevel

A chain: grandchild → child → parent.
Manager extends Employee extends Person

A ← B ← C

Hierarchical

Many children share one parent.
Car, Bike, Truck extends Vehicle

A ← B, A ← C

Multilevel and hierarchical together

class Vehicle {
    String regNo;
    void start() { System.out.println(regNo + ": engine on"); }
}

class Car extends Vehicle {            // hierarchical: Car and Truck share Vehicle
    int seats;
}

class Truck extends Vehicle {
    int capacityKg;
}

class ReeferTruck extends Truck {      // multilevel: ReeferTruck → Truck → Vehicle
    int minTemp;
}

public class Main {
    public static void main(String[] args) {
        Car c = new Car();
        c.regNo = "MH-12-AB-1234";
        c.seats = 5;
        c.start();                     // inherited from Vehicle

        ReeferTruck r = new ReeferTruck();
        r.regNo = "MH-04-XY-9876";      // from Vehicle (two levels up)
        r.capacityKg = 8000;           // from Truck
        r.minTemp = -18;               // its own
        r.start();
        System.out.println(r.capacityKg + " kg at " + r.minTemp + " C");
    }
}
MH-12-AB-1234: engine on MH-04-XY-9876: engine on 8000 kg at -18 C

The diamond problem: if class C extends A, B were allowed and both A and B had hello(), which one should c.hello() run? And if A and B both extend a class with a field, does C get one copy or two? Java avoids this by allowing only one parent class. Interfaces can be combined because they carry no instance fields, and if two interfaces bring the same default method, Java forces the class to choose (Lesson 7.7). Writing class C extends A, B gives error: '{' expected.

4 Step by step

Building a small hierarchy

  1. Find what is common, and test IS-A

    Employee and Manager both have a name and a salary. Is a manager an employee? Yes. Is a car an engine? No, a car has an engine: use a field, not inheritance.

    Inheritance is a permanent, compile-time link. Use it only when the child truly is a special kind of the parent and can be used wherever the parent is expected.

  2. Write the parent once

    class Person {
    private String name;
    Person(String name) { this.name = name; }
    String getName() { return name; }
    void greet() { System.out.println("Hi, I am " + name); }
}
    The parent keeps its fields private (Lesson 7.1). Children will reach name only through getName() and greet().

  3. Extend it and add only what's new

    class Employee extends Person {
    private double salary;
    Employee(String name, double salary) {
        super(name);          // hand the name to Person's constructor
        this.salary = salary;
    }
}
    Constructors are not inherited, so Employee writes its own and first calls Person's with super(name). Lesson 7.3 covers this in detail.

  4. One object holds every level's fields

    Employee e = new Employee("Asha", 50000);
e.greet();   // Hi, I am Asha
    There is one object on the heap, not a Person object plus an Employee object. It has room for name (declared in Person) and salary (declared in Employee). When e.greet() is called, the JVM looks for greet in Employee, doesn't find it, and uses Person's.

  5. Everything ends at Object

    System.out.println(e instanceof Object);   // true
System.out.println(e.getClass().getSuperclass());   // class Person
    Person extends nothing, so javac makes it extend Object. That's why every object, even one from your own class, has toString(), equals() and getClass() (Lesson 10.3).

One object, many levels: both views

Person → Employee → Manager 6 steps
What you see
  1. Parent alone: a Person object has a name and a greet() method.
  2. Single inheritance: Employee extends Person. Calling e.greet() works although Employee's code never declares it.
  3. Multilevel: Manager extends Employee. One Manager object answers methods from all three classes.
  4. Private isn't accessible: name is private in Person, so even through a Manager, outside code can't read it directly.
  5. No multiple inheritance: listing two classes after extends doesn't even parse.
  6. Object at the root: a Manager is an Employee, a Person and an Object, all at once.
Behind the screen
  1. new Person("Ravi") creates one object with room for Person's field name.
  2. new Employee(...) creates one object with Person's name and Employee's salary. For greet(), the JVM searches Employee first, then its parent.
  3. A Manager object has three sections, one per class in the chain. There is no separate Person object or Employee object.
  4. name physically lives in the Manager object, but private means only code written inside Person can use the name name.
  5. With two parents, a call to greet() and inherited fields would be ambiguous: the diamond problem. Java allows one parent class.
  6. Object sits at the top of every chain. It contributes methods like toString(), not fields you can see.
6 Real-world use

Inheritance in real systems

Inheritance is common in libraries and frameworks. In business code, teams use it carefully and prefer composition when the IS-A test is doubtful.

Watch it with an example: finding a method up the hierarchy

SavingsAccount extends Account. When you call a method on a savings account, the JVM looks in SavingsAccount first, then moves up to Account, then Object.

Method lookup: child first, then parent 6 steps
Animated example
  1. The call: sa refers to a SavingsAccount object. Which class's code runs for addInterest()?
  2. Child first: the JVM looks in the object's own class, SavingsAccount, and finds it there.
  3. deposit(500): SavingsAccount doesn't define it…
  4. …so the search moves up to the parent, Account, where it is found. The child reuses the parent's code without copying it.
  5. toString(): neither SavingsAccount nor Account defines it…
  6. …so it is found in Object, the root of every class. Bank account types, exception classes and framework base classes all rely on this lookup. (The JVM caches the result, so it is fast.)

1. Java's own exception hierarchy

IOException extends Exception, which extends Throwable. Because of this chain, one catch (Exception e) can handle many specific errors (Module 9).

FileNotFoundException→IS-A IOException→caught by its parent type

2. Account types in banking

Savings and current accounts share an account number, holder and deposit logic in a parent class; each child adds its own rules (interest, overdraft limit).

Account→SavingsAccount extends Account→adds interest

3. Common fields for stored records

Many projects put fields every database record needs (id, created time, updated time) in one base class that all entity classes extend.

BaseEntity→Customer, Order extend it→same audit fields

4. Framework base classes

UI and testing frameworks often give you a base class to extend. Your class inherits the framework's lifecycle code and fills in only the parts specific to your screen or test.

Framework base class→class MyScreen extends …→reuse lifecycle

Examples are simplified. Deep hierarchies (five or more levels) become hard to change; many teams follow "favour composition over inheritance" and keep chains short.

9 Quiz and revision

Check yourself

Quick revision

Lesson 7.2 in one screen

  • Inheritance: a subclass gets the superclass's members with extends; it models IS-A.
  • Types with classes: single, multilevel, hierarchical. Multiple and hybrid: only via interfaces.
  • One parent class only: extends A, B doesn't compile (diamond problem).
  • Private members exist in the child object but aren't accessible by name; use the parent's methods.
  • Constructors are not inherited; the child calls the parent's with super(...).
  • new Child() creates one object holding every level's fields.
  • Every class ultimately extends Object.

Interview and viva questions

Why doesn't Java support multiple inheritance of classes?

To avoid the diamond problem and keep the language simple. If a class had two parents with the same method, a call would be ambiguous; if both inherited fields from a common ancestor, the object's layout would be unclear. Java allows multiple inheritance of type through interfaces, which have no instance fields, and resolves clashing default methods by forcing the class to override.

Is a private member inherited?

The private field is present in the child object (memory is set aside for it), but it is not inherited as an accessible member: the child's code can't name it. The child uses it indirectly through the parent's public or protected methods. Interviewers accept either wording if you explain this difference.

What is the difference between IS-A and HAS-A?

IS-A is inheritance: a SavingsAccount is an Account. HAS-A is composition: a Car has an Engine field. Composition is more flexible because the part can be replaced at run time and the classes stay loosely coupled.

Why are constructors not inherited?

A constructor's job is to initialise an object of its own class. A parent's constructor knows nothing about the child's extra fields, so letting new Child(...) use it would leave the child part uninitialised. Instead every child constructor calls a parent constructor first (explicitly or implicitly) and then sets up its own part.

When should you avoid inheritance?

When the IS-A test fails, when you only want to reuse a few methods, or when the parent may change often. Prefer composition then. A well-known example is Java's own java.util.Stack, which extends Vector: every stack also inherits methods like add(int index, E element) that break the last-in, first-out rule.

P6Medium

Private field, public door

Account has a private balance and a public deposit() and getBalance(). SavingsAccount extends Account adds addInterest(rate). Since the child can't touch balance directly, implement addInterest using the inherited methods.

Input
deposit 20000, interest 3.5%
Expected output
Balance after interest: 20700.0
Show solution and explanation 
class Account {
    private double balance;

    public void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

class SavingsAccount extends Account {
    void addInterest(double ratePercent) {
        double interest = getBalance() * ratePercent / 100;
        deposit(interest);
    }
}

public class Main {
    public static void main(String[] args) {
        SavingsAccount s = new SavingsAccount();
        s.deposit(20000);
        s.addInterest(3.5);
        System.out.println("Balance after interest: " + s.getBalance());
    }
}
Balance after interest: 20700.0

How it works: writing balance += interest in SavingsAccount would be a compile error: balance has private access in Account. Using getBalance() and deposit() keeps the parent's rules in force for the child too: encapsulation and inheritance working together.

P8Business problem

Savings and current accounts

A bank has savings accounts (4% yearly interest) and current accounts (overdraft up to Rs 10,000). Both share account number, balance and deposit. Write the classes and show a savings account earning one year's interest and a current account going into overdraft.

Input
Savings SB-01 deposit 50000, add yearly interest
Current CA-07 deposit 5000, withdraw 12000
Expected output
SB-01: Rs 52000.0
Withdraw 12000: true
CA-07: Rs -7000.0
Show solution and explanation 
class Account {
    private final String accountNo;
    protected double balance;

    Account(String accountNo) {
        this.accountNo = accountNo;
    }

    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    String summary() {
        return accountNo + ": Rs " + balance;
    }
}

class SavingsAccount extends Account {
    SavingsAccount(String no) { super(no); }

    void addYearlyInterest() {
        balance += balance * 0.04;
    }
}

class CurrentAccount extends Account {
    private static final double OVERDRAFT = 10000;

    CurrentAccount(String no) { super(no); }

    boolean withdraw(double amount) {
        if (balance - amount < -OVERDRAFT) return false;
        balance -= amount;
        return true;
    }
}

public class Main {
    public static void main(String[] args) {
        SavingsAccount s = new SavingsAccount("SB-01");
        s.deposit(50000);
        s.addYearlyInterest();
        System.out.println(s.summary());

        CurrentAccount c = new CurrentAccount("CA-07");
        c.deposit(5000);
        System.out.println("Withdraw 12000: " + c.withdraw(12000));
        System.out.println(c.summary());
    }
}
SB-01: Rs 52000.0 Withdraw 12000: true CA-07: Rs -7000.0

How it works:

  1. Common data and deposit/summary live in Account; each child adds only its own rule.
  2. balance is protected here so children can update it directly; accountNo stays private and read-only.
  3. 5000 − 12000 = −7000, which is within the Rs 10,000 overdraft, so the withdrawal is allowed.

        this.basic = basic;
    }

    double monthlyPay() {
        return basic + basic * 0.40;
    }
}

class ContractEmployee extends Employee {
    private final double hourlyRate;
    private final int hours;

    ContractEmployee(String id, String name, double hourlyRate, int hours) {
        super(id, name);
        this.hourlyRate = hourlyRate;
        this.hours = hours;
    }

    double monthlyPay() {
        return hourlyRate * hours;
    }
}

public class Main {
    public static void main(String[] args) {
        FullTimeEmployee f = new FullTimeEmployee("E101", "Anil", 40000);
        ContractEmployee c = new ContractEmployee("C207", "Sara", 600, 120);
        f.printSlip(f.monthlyPay());
        c.printSlip(c.monthlyPay());
    }
}
E101 Anil Rs 56,000.00 C207 Sara Rs 72,000.00

How it works:

  1. ID, name and payslip formatting are common, so they live in Employee. The pay rules differ, so each child has its own monthlyPay().
  2. %,.2f prints Indian-readable amounts with commas and two decimals; %-6s pads the name.
  3. Notice both children have a method with the same name. In Lesson 7.4 you'll declare it in the parent and override it, so a payroll loop can treat all employees alike.
P10Business problem

Delivery vehicles: can it carry the parcel?

A courier company has bikes (max 20 kg) and vans (max 800 kg, needs a driver with a commercial licence). All vehicles have a registration number and a canCarry(weight) check based on their limit. Check a 15 kg and a 120 kg parcel for one bike and one van.

Input
Bike MH-02-1111 (20 kg), Van MH-02-9999 (800 kg)
parcels 15 kg and 120 kg
Expected output
15 kg -> bike true, van true
120 kg -> bike false, van true
MH-02-9999 needs commercial licence: true
Show solution and explanation 
class DeliveryVehicle {
    private final String regNo;
    private final int maxKg;

    DeliveryVehicle(String regNo, int maxKg) {
        this.regNo = regNo;
        this.maxKg = maxKg;
    }

    boolean canCarry(int kg) {
        return kg <= maxKg;
    }

    String getRegNo() { return regNo; }
}

class Bike extends DeliveryVehicle {
    Bike(String regNo) { super(regNo, 20); }
}

class Van extends DeliveryVehicle {
    private final boolean commercialLicence = true;

    Van(String regNo) { super(regNo, 800); }

    boolean needsCommercialLicence() { return commercialLicence; }
}

public class Main {
    public static void main(String[] args) {
        Bike b = new Bike("MH-02-1111");
        Van v = new Van("MH-02-9999");
        int[] parcels = {15, 120};
        for (int kg : parcels) {
            System.out.println(kg + " kg -> bike " + b.canCarry(kg) + ", van " + v.canCarry(kg));
        }
        System.out.println(v.getRegNo() + " needs commercial licence: " + v.needsCommercialLicence());
    }
}
15 kg -> bike true, van true 120 kg -> bike false, van true MH-02-9999 needs commercial licence: true

How it works:

  1. The rule kg <= maxKg is the same for every vehicle, so it's written once in the parent. Children only supply their limit through super(regNo, 20).
  2. Van adds a behaviour the bike doesn't have. Hierarchical inheritance: two children, one parent.
  3. Adding a new vehicle type (a three-wheeler, 300 kg) is one small class.

Real-world scenario questions (asked in company interviews)

Inheritance saves code when the IS-A test holds and causes pain when it doesn't. Decide your answer first, then open the model answer.

Banking · account typesFresher

Designing savings and current accounts

A bank needs savings accounts (interest, minimum balance) and current accounts (overdraft limit, no interest). Both have account number, holder name, balance and deposit. How would you design the classes?

The interviewer is checking: can you find the common parent and keep each child's rules separate?

Show a strong answer
  • A parent Account with private accountNo, holder, balance, plus deposit() and getBalance().
  • SavingsAccount extends Account adds rate and addInterest(); CurrentAccount extends Account adds overdraftLimit.
  • Each child has its own withdraw rule (minimum balance vs overdraft), which is where overriding comes in (Lesson 7.4).
  • Both pass the IS-A test, and code that needs "any account" can accept Account.

Avoid: one class with a type field and if-else everywhere. Every new account type would change every method.

Logistics · fleet1–3 years

"ElectricTruck extends Truck, Battery"

A delivery company adds electric trucks. A developer wants ElectricTruck to extend both Truck and Battery to reuse chargeLevel(), and is surprised it doesn't compile. What do you suggest?

The interviewer is checking: do you know the single-parent rule and when to use composition?

Show a strong answer
  • Java allows one parent class. More importantly, a truck is not a battery; it has a battery.
  • Design: ElectricTruck extends Truck with a field private final Battery battery, and a method chargeLevel() that delegates to battery.level().
  • If many vehicle types need to be "chargeable", define an interface Chargeable and implement it (Lesson 7.7).

Avoid: making Battery the parent of Truck just to get the method. The hierarchy would make no sense.

E-commerce · catalogue1–3 years

The six-level product hierarchy

A catalogue has Product → Electronics → Mobile → Smartphone → AndroidPhone → FoldablePhone. Adding a "refurbished" option now needs a parallel set of classes for every level. What went wrong and how would you restructure?

The interviewer is checking: do you recognise when inheritance is being used for data that should be attributes?

Show a strong answer
  • The hierarchy encodes data (category, OS, form factor, condition) as classes. Every new dimension multiplies the number of classes.
  • Keep a shallow hierarchy only where behaviour truly differs, and model the rest as fields: category, attributes map, condition enum (Lesson 10.4).
  • Shared behaviour like pricing rules can be separate objects composed into the product.

Avoid: adding RefurbishedFoldablePhone and friends. Deep, wide hierarchies are hard to change.

SaaS · shared library3+ years

A parent-class change broke ten teams

Your platform team owns BaseService, which 40 services across ten teams extend. You add a validation step inside one of its methods, and several child services break because they depended on the old internal order of calls. How do you prevent this in future?

The interviewer is checking: do you understand that inheritance tightly couples children to the parent's internals?

Show a strong answer
  • This is the "fragile base class" problem: children depend on how the parent works, not just what it promises.
  • Prefer composition for shared libraries: services use helper objects instead of extending a base class.
  • Where inheritance stays, document which methods are meant to be overridden, make the rest final (Lesson 7.8), and use template methods with clear hooks (Lesson 7.6).
  • Version the library and run the dependent teams' tests before releasing.

Avoid: blaming the child teams. A widely extended base class is a public contract.
