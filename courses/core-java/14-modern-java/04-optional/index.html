Optional

NullPointerException is the most common crash in Java. It happens because a method quietly returned null and a caller forgot to check. Optional makes “there might be no result” part of the return type, and gives you safe ways to provide defaults, transform values and fail with clear errors. You'll learn how to use it well, and where not to use it.

Module 14 · Modern Java⏱ 20 minIntermediate9 practice problems
1 The story

The crash that only happened to new students

Riya's canteen app greets students by name: findStudent(roll).getName(). It works for everyone already registered. On admission day, the app crashes for every new student, because findStudent returns null for them.

Riya

Sir, I can add if (s != null) everywhere. But how will I remember every place?

Arjun Sir

You won't. Nobody does. Make the method return Optional<Student>. Then the type itself tells every caller: “this might be empty, handle it”.

Riya

And handling it means more ifs?

Arjun Sir

No: map, orElse, orElseThrow. Let's look inside the box.

2 Definition

What is Optional?

Formal definition (write this in exams)

java.util.Optional<T> is a container object that may or may not contain a non-null value of type T. It is intended mainly as a method return type where there may be no result, to make the absence explicit and avoid returning null. An Optional is created with Optional.of(value) (value must be non-null), Optional.ofNullable(value) or Optional.empty(). Its value is accessed through methods such as orElse, orElseGet, orElseThrow and ifPresent, and transformed with map, filter and flatMap, which return Optionals. Calling get() on an empty Optional throws NoSuchElementException.

In simple words

Optional is a gift box that might be empty. You're not allowed to assume there's something inside; you say what to do in both cases.

Words you'll meet in this lesson

EmptyAn Optional with no value. Not the same as null.
PresentAn Optional holding a non-null value.
FallbackThe value to use when empty: orElse("Guest").
Lazy fallbackorElseGet(supplier) computes it only when needed.
Fail fastorElseThrow: stop with a clear error when a value is required.
flatMapChain a step that itself returns an Optional.

Why not just call get()?

import java.util.*;

public class Main {
    public static void main(String[] args) {
        Optional<String> coupon = Optional.empty();
        System.out.println("isPresent: " + coupon.isPresent());
        try {
            System.out.println(coupon.get());
        } catch (NoSuchElementException e) {
            System.out.println("get() on empty: " + e.getMessage());
        }
        System.out.println("safe: " + coupon.orElse("no coupon"));
    }
}
isPresent: false get() on empty: No value present safe: no coupon

Use Optional for return values, not everywhere. Don't make fields, method parameters or collection elements Optional (List<Optional<X>>): it's not Serializable, adds noise, and an empty list is already a fine “nothing”. And never return null from a method whose type is Optional.

4 Step by step

What happens in find(id).map(f).orElse(d)

  1. The finder returns a box

    Optional<String> name = findName("98100");
    Inside: Optional.ofNullable(map.get(phone)): a box holding the name, or the shared empty box.

  2. map checks the box

    If a value is present, map calls your function and wraps the result (via ofNullable) in a new Optional. If empty, it returns empty without calling it.

  3. filter can empty it

    If you add .filter(test), a present value that fails the test becomes empty.

  4. orElse unwraps

    Present: return the value. Empty: return the fallback. Either way you get a plain value, never null (unless the fallback is null).

  5. Or fail clearly

    .orElseThrow(() -> new IllegalArgumentException("unknown id " + id))
    When there's no sensible default, throwing a meaningful exception at this point is much easier to debug than an NPE three methods later.
5 See it happen

null vs Optional: both views

Left: what the caller sees with null and with Optional. Right: the Optional objects on the heap and what each method does with a full or empty box.

Optional: both views 6 steps
What you see
  1. findByPhone returns a Customer, or null if the number isn't registered. The signature doesn't tell callers that.
  2. One caller forgets the null check and calls a method on it: NullPointerException in production.
  3. With Optional<Customer> the return type itself says “maybe”. The value sits inside a box.
  4. map(Customer::name) transforms the value if present; orElse("Guest") unwraps it.
  5. For an unknown number the method returns Optional.empty(): a box with nothing inside, but never null.
  6. map does nothing on an empty box, and orElse gives "Guest". Same code path, no if-null, no crash.
Behind the screen
  1. Optional.of(c) creates a small object (#1) whose value field refers to the Customer. It's an extra object, so don't wrap things in hot loops for no reason.
  2. Optional.empty() returns a single shared instance whose value is null. All empty Optionals of any type are that same object.
  3. map on a full box calls your function and wraps the result in a new Optional.
  4. map on the empty box doesn't call your function at all; it returns empty.
  5. orElse returns the value if present, otherwise the fallback.
  6. get() on an empty Optional throws NoSuchElementException: No value present. That's just a different crash, so prefer orElse, orElseGet, orElseThrow or ifPresent.
6 Real-world use

Optional in real systems

Data-access layers, configuration lookups and stream results are the most common places you'll meet Optional.

Watch it with an example: applying a coupon that may not exist

At checkout the app looks up the coupon code the user typed. It might be unknown, or expired. An Optional pipeline handles all cases in one chain.

Coupon lookup with Optional 5 steps
Animated example
  1. find(code) returns Optional<Coupon>; filter keeps it only if valid; map turns it into the discount; orElse(0) gives 0 otherwise.
  2. SAVE50 exists and is valid: the box flows through filter and map, and the user gets ₹50 off.
  3. OLD20 exists but has expired: filter returns an empty Optional, so map is skipped and orElse gives 0.
  4. HELLO doesn't exist: find returns empty, and every step passes the empty box along to orElse.
  5. The same four calls handle all three situations. The app can show “Coupon not valid” when the result is 0. (Illustrative codes.)

1. Database lookups

Repository methods like findById(id) in Spring Data return Optional<Customer>: the record may not exist.

findById(42)→Optional<Customer>→orElseThrow(NotFound)

2. Configuration

Optional settings get defaults; required ones fail at startup with a clear message.

config.get("timeout")→orElse("30s")→value

3. Stream results

findFirst, min, max and reduce return Optional because a stream can be empty.

today's orders→max(byAmount)→Optional<Order>

4. Optional user input

Coupons, referral codes and nicknames may or may not be supplied; Optional chains turn them into discounts or display names.

coupon code→filter(valid).map(off)→orElse(0)

Simplified: APIs that return many results return an empty list, not an Optional list.

7 Run the code

Greeting customers by phone number

import java.util.*;

public class Main {
    static Map<String, String> customers = Map.of("98100", "Asha", "98200", "Ravi");

    static Optional<String> findName(String phone) {
        return Optional.ofNullable(customers.get(phone));
    }

    public static void main(String[] args) {
        for (String phone : List.of("98100", "99999", "98200")) {
            String greeting = findName(phone)
                    .map(name -> "Welcome back, " + name)
                    .orElse("Welcome! Please sign up");
            System.out.println(phone + " -> " + greeting);
        }
        findName("98200").ifPresent(n -> System.out.println("Sending offer to " + n));
        findName("99999").ifPresentOrElse(
                n -> System.out.println("Sending offer to " + n),
                () -> System.out.println("No customer for 99999"));
    }
}
98100 -> Welcome back, Asha 99999 -> Welcome! Please sign up 98200 -> Welcome back, Ravi Sending offer to Ravi No customer for 99999
  • Optional.ofNullable(customers.get(phone))Map lookups return null when the key is missing; wrap at the boundary.
  • .map(name -> "Welcome back, " + name)Runs only when the customer exists.
  • .orElse("Welcome! Please sign up")The answer for unknown numbers.
  • ifPresentOrElse(..., ...)One action for present, another for empty.

9 Quiz and revision

Check yourself

Quick revision

Lesson 14.4 in one screen

  • Optional = a box that holds one non-null value or nothing; use it as a return type.
  • Create: of (non-null), ofNullable, empty.
  • Unwrap: orElse, orElseGet (lazy), orElseThrow.
  • Act: ifPresent, ifPresentOrElse. Avoid bare get().
  • Transform: map, filter, flatMap; empty passes through untouched.
  • Streams' findFirst, min, max return Optional.
  • Not for fields, parameters or collections; never return null as an Optional.

Interview and viva questions

What problem does Optional solve?

It makes the possible absence of a result explicit in a method's return type, so callers are forced to handle the empty case, reducing NullPointerExceptions. It also provides a fluent API (map, filter, orElse) for working with possibly-missing values.

Difference between orElse and orElseGet?

orElse(x) takes an already-evaluated value, so the expression is computed even when the Optional has a value. orElseGet(supplier) calls the supplier only when the Optional is empty. Use orElseGet when the default is expensive or has side effects.

Difference between map and flatMap on Optional?

map applies a function returning a plain value and wraps it; flatMap applies a function that already returns an Optional, avoiding Optional<Optional<T>>. Use flatMap to chain lookups that each may be empty.

Should you use Optional as a field or parameter?

Generally no. Optional isn't Serializable, adds allocation, and as a parameter it forces callers to wrap values. Prefer overloading or nullable parameters documented clearly for inputs, and plain nullable fields with Optional-returning getters.

Is Optional.get() bad?

It throws NoSuchElementException on empty, so isPresent() + get() is just a disguised null check. Prefer orElse/orElseThrow/ifPresent/map. Java 10 added orElseThrow() as a clearer name for the same behaviour as get().

P4Medium

orElse vs orElseGet

Show that orElse evaluates its argument even when a value is present, while orElseGet doesn't.

Input
(none)
Expected output
orElse:
  (loading default from server...)
dark
orElseGet:
dark
Show solution and explanation 
import java.util.Optional;

public class Main {
    static String loadDefault() {
        System.out.println("  (loading default from server...)");
        return "default";
    }

    public static void main(String[] args) {
        Optional<String> theme = Optional.of("dark");
        System.out.println("orElse:");
        System.out.println(theme.orElse(loadDefault()));
        System.out.println("orElseGet:");
        System.out.println(theme.orElseGet(Main::loadDefault));
    }
}
orElse: (loading default from server...) dark orElseGet: dark

How it works: orElse(x) receives an already-computed value, so loadDefault() runs first anyway. orElseGet takes a Supplier and calls it only when empty: use it when the fallback is expensive.

P5Medium

map and filter on Optional

From an optional email, keep it only if it ends with "@company.in", and return the part before @, else "external".

Input
asha@company.in / ravi@gmail.com
Expected output
asha, external
Show solution and explanation 
import java.util.Optional;

public class Main {
    static String userId(Optional<String> email) {
        return email.filter(e -> e.endsWith("@company.in"))
                    .map(e -> e.substring(0, e.indexOf('@')))
                    .orElse("external");
    }

    public static void main(String[] args) {
        System.out.println(userId(Optional.of("asha@company.in")) + ", " + userId(Optional.of("ravi@gmail.com")));
    }
}
asha, external

How it works: filter turns a full box empty if the test fails; map transforms only full boxes.

P6Medium

Optional from a stream

Find the first order above ₹5,000; print it or "none". Then find the cheapest order.

Input
450, 1200, 2600
Expected output
big: none, cheapest: 450
Show solution and explanation 
import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> orders = List.of(450, 1200, 2600);
        Optional<Integer> big = orders.stream().filter(o -> o > 5000).findFirst();
        Optional<Integer> cheapest = orders.stream().min(Integer::compare);
        System.out.println("big: " + big.map(String::valueOf).orElse("none") + ", cheapest: " + cheapest.orElse(0));
    }
}
big: none, cheapest: 450

How it works: stream methods that might have no answer (findFirst, min, max, reduce without identity) return Optional.

P7Business problem

Loyalty points or welcome bonus

Look up loyalty points by customer id; new customers get a 50-point welcome bonus. Use Optional.ofNullable on a map lookup.

Input
ids C1 (320 points), C9 (new)
Expected output
C1: 320, C9: 50

import java.util.*;

public class Main {
    static Map<String, Integer> points = Map.of("C1", 320, "C2", 75);

    static int pointsFor(String id) {
        return Optional.ofNullable(points.get(id)).orElse(50);

P8Business problem

Shipping charge rule chain

An order may have a pincode. If present and it starts with "4" (Maharashtra), shipping is ₹0; if present but elsewhere, ₹49; if missing, ask for it.

Input
pincodes 411001, 560001, none
Expected output
free shipping
Rs 49 shipping
please enter a pincode
Show solution and explanation 
import java.util.*;

public class Main {
    static String shipping(Optional<String> pin) {
        return pin.map(p -> p.startsWith("4") ? "free shipping" : "Rs 49 shipping")
                  .orElse("please enter a pincode");
    }

    public static void main(String[] args) {
        System.out.println(shipping(Optional.of("411001")));
        System.out.println(shipping(Optional.of("560001")));
        System.out.println(shipping(Optional.empty()));
    }
}
free shipping Rs 49 shipping please enter a pincode

How it works: map handles the “present” logic, orElse the “missing” case. (Illustrative rule.)

P9Business problem

Required config value

An app reads the GST rate from config. If it's missing, startup must fail with a clear message. Show both cases.

Input
config with and without gst.rate
Expected output
rate: 0.18
startup stopped: gst.rate missing in config
Show solution and explanation 
import java.util.*;

public class Main {
    static double gstRate(Map<String, String> config) {
        return Optional.ofNullable(config.get("gst.rate"))
                .map(Double::parseDouble)
                .orElseThrow(() -> new IllegalStateException("gst.rate missing in config"));
    }

    public static void main(String[] args) {
        System.out.println("rate: " + gstRate(Map.of("gst.rate", "0.18")));
        try {
            gstRate(Map.of());
        } catch (IllegalStateException e) {
            System.out.println("startup stopped: " + e.getMessage());
        }
    }
}
rate: 0.18 startup stopped: gst.rate missing in config

How it works: failing at startup with a precise message is far better than running with a wrong tax rate. orElseThrow makes “required” explicit.

Real-world scenario questions (asked in company interviews)

Optional questions test whether you can remove NPEs without making the code worse.

Production · NPEFresher

NullPointerException on the order-tracking page

The tracking page calls order.getRider().getPhone(). Orders that aren't assigned to a rider yet crash the page. How would you fix it so the page shows “Rider not assigned yet”?

The interviewer is checking: chaining optional relationships.

Show a strong answer
  • Make the getter honest: Optional<Rider> rider().
  • Page code: order.rider().map(Rider::phone).orElse("Rider not assigned yet").
  • Search for other callers of getRider(); the new type makes the compiler point them out.

Avoid: wrapping the whole page in try { … } catch (NullPointerException e).

Performance · defaultsJunior

Every request hits the pricing service

Code reads cachedPrice(id).orElse(pricingService.fetch(id)). Monitoring shows the pricing service is called on every request, even when the cache has the price. Why?

The interviewer is checking: orElse vs orElseGet.

Show a strong answer
  • orElse's argument is evaluated before the call, so fetch(id) always runs.
  • Use orElseGet(() -> pricingService.fetch(id)): the supplier runs only on a cache miss.

Avoid: adding an if-isPresent around it; orElseGet already expresses it.

Code review · misuseJunior

Optional everywhere

A pull request changes every entity field to Optional<...> and every method parameter too, “to remove nulls from the codebase”. Serialization of sessions now fails. What feedback would you give?

The interviewer is checking: knowing Optional's intended scope.

Show a strong answer
  • Optional is designed for return types. It's not Serializable, so fields break serialization and many frameworks.
  • Keep fields as plain (possibly null) references and expose Optional-returning getters for the optional ones.
  • For parameters, use overloads or validate non-null inputs with Objects.requireNonNull.

Avoid: approving because it “looks modern”.

API design · errorsMid

Empty Optional or exception?

A PaymentService.getPayment(id) is called from refunds (where the id must exist) and from a search box (where it may not). Should it return Optional<Payment> or throw when not found?

The interviewer is checking: designing for callers.

Show a strong answer
  • Return Optional<Payment> from the lookup: “not found” is a normal outcome for search.
  • Refunds call getPayment(id).orElseThrow(() -> new PaymentNotFound(id)), choosing their own exception and message.
  • One method serves both cases; each caller decides what absence means.

Avoid: returning null for search and throwing for refunds from two near-identical methods.
