Comparable vs Comparator

Java can sort numbers and Strings out of the box, but how should it sort students, orders or trains? You have to tell it. Comparable puts one natural order inside the class (compareTo). Comparator describes extra orders outside it (compare): by marks, by name, by date, highest first, ties broken by roll number. You'll learn both, how sorting algorithms call them, and the small bugs that make sorts go wrong.

1 The story

One class, three rank lists

The exam cell needs three printouts of the same students: by roll number for the attendance register, by marks (highest first) for the merit list, and by name for the certificate desk. Kabir calls Collections.sort(students) and gets a compile error.

Riya

Sir, Java sorts numbers and names fine. Why can't it sort students?

Arjun Sir

Because it doesn't know what “smaller” means for a student. Roll number? Marks? Name? You choose. If one order is the obvious, everyday one, like roll number, put it inside the class by implementing Comparable.

Riya

And the merit list and certificates?

Arjun Sir

Those are extra orders, so write them as Comparators outside the class and pass them to sort. One class, as many orders as the exam cell wants, and modern Java builds them in one line.

2 Definition

What are Comparable and Comparator?

Formal definition (write this in exams)

Comparable<T> (java.lang) is implemented by a class to define its natural ordering through the single method int compareTo(T other). Comparator<T> (java.util) is a separate object that defines an ordering through int compare(T a, T b), allowing multiple orderings and ordering of classes you can't modify. Both return a negative integer if the first argument comes before the second, zero if they are equal in the ordering, and a positive integer if it comes after. Sorting methods (Collections.sort, List.sort, Arrays.sort) and sorted collections (TreeSet, TreeMap, PriorityQueue) use the natural ordering unless a Comparator is supplied.

In simple words

Comparable: “this is how my objects are normally ordered”, written in the class. Comparator: “sort them this way for now”, written anywhere.

Words you'll meet in this lesson

Natural orderingThe one default order of a type: numbers ascending, Strings alphabetical.
Sort keyThe field you sort by: marks, name, date.
Tie-breakerA second key used when the first is equal.
Stable sortEqual elements keep their original relative order. Java's object sorts are stable.
LexicographicDictionary order by character codes: “Zoya” < “riya” because capitals come first.
Method referenceStudent::marks means “call marks() on each student” (Lesson 14.1).

Comparable: the natural order

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

class Student implements Comparable<Student> {
    final int roll;
    final String name;
    final int marks;

    Student(int roll, String name, int marks) {
        this.roll = roll;
        this.name = name;
        this.marks = marks;
    }

    @Override
    public int compareTo(Student other) {
        return Integer.compare(this.roll, other.roll);   // by roll number
    }

    @Override
    public String toString() { return roll + " " + name + " " + marks; }
}

public class Main {
    public static void main(String[] args) {
        List<Student> list = new ArrayList<>(List.of(
            new Student(21, "Om", 92), new Student(7, "Riya", 92), new Student(12, "Kabir", 78)));
        Collections.sort(list);                 // uses compareTo
        System.out.println(list);
    }
}
[7 Riya 92, 12 Kabir 78, 21 Om 92]

Comparators: any order you need

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class Student {
    final int roll; final String name; final int marks;
    Student(int roll, String name, int marks) { this.roll = roll; this.name = name; this.marks = marks; }
    int roll() { return roll; }
    String name() { return name; }
    int marks() { return marks; }
    @Override public String toString() { return roll + " " + name + " " + marks; }
}

public class Main {
    public static void main(String[] args) {
        List<Student> list = new ArrayList<>(List.of(
            new Student(21, "Om", 92), new Student(7, "Riya", 92), new Student(12, "Kabir", 78)));

        // 1. A Comparator written as a lambda (Lesson 14.1)
        list.sort((a, b) -> a.name.compareTo(b.name));
        System.out.println("By name:  " + list);

        // 2. Built with Comparator.comparing: marks high→low, ties by roll
        Comparator<Student> merit = Comparator.comparingInt(Student::marks).reversed()
                                              .thenComparingInt(Student::roll);
        list.sort(merit);
        System.out.println("Merit:    " + list);
    }
}
By name: [12 Kabir 78, 21 Om 92, 7 Riya 92] Merit: [7 Riya 92, 21 Om 92, 12 Kabir 78]

Strings: case matters

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>(List.of("riya", "Zoya", "Kabir"));
        Collections.sort(names);                              // natural: by char codes
        System.out.println(names);
        names.sort(String.CASE_INSENSITIVE_ORDER);           // a ready-made Comparator
        System.out.println(names);
        names.sort(Comparator.reverseOrder());
        System.out.println(names);
    }
}
[Kabir, Zoya, riya] [Kabir, riya, Zoya] [riya, Zoya, Kabir]

The subtraction trap

public class Main {
    public static void main(String[] args) {
        int a = -2_000_000_000, b = 2_000_000_000;
        System.out.println(a - b);                  // overflows: looks positive!
        System.out.println(Integer.compare(a, b));  // correct: negative
    }
}
294967296 -1

Don't write return this.x - other.x; in compareTo. For large or negative values the subtraction overflows and the sign flips, so the sort silently goes wrong. Use Integer.compare, Long.compare, Double.compare or Comparator.comparingInt.

Rule of thumb: give a class a natural order only if there's one obvious, stable order (IDs, dates, version numbers). Everything else is a Comparator, ideally a named constant like Student.BY_MERIT built with comparing(...).thenComparing(...).

4 Step by step

What sort does with your comparator

  1. You hand over the rule

    list.sort(merit);
    List.sort copies the elements into an array and calls Arrays.sort(array, merit).

  2. The algorithm picks pairs

    Java sorts objects with TimSort, a merge sort tuned for real data (it finds already-sorted runs). For tiny arrays it uses binary insertion sort. It decides which two elements to compare next.

  3. Your method answers: before, same or after

    For each pair it calls merit.compare(a, b) (or a.compareTo(b)). Your code never moves elements; it only answers with a sign. The algorithm moves them.

  4. About n log n questions

    Sorting n elements needs roughly n·log₂n comparisons: about 10,000 for 1,000 students. That's why a comparator should be cheap and must be consistent (if a < b and b < c then a < c), or TimSort may throw Comparison method violates its general contract!.

  5. Stable result, written back

    The sorted array is copied back into the list. Because the sort is stable, students with equal keys stay in their previous relative order, which lets you sort by a secondary key first and the primary key second if you want.

Behind the screen
  1. list.sort(merit) copies the list into an array and starts TimSort. For tiny arrays it looks for an ordered run and then inserts the rest.
  2. It asks merit.compare(Riya, Om). Marks are equal (92), so the tie-breaker compares rolls 7 and 21: −1. In merit order Riya comes first, so the first two elements form a descending run.
  3. Does the run continue? compare(Kabir, Riya): 78 vs 92 with reversed() gives +1, so no. The run is [Om, Riya].
  4. A descending run is reversed in place: [Riya, Om, Kabir].
  5. Kabir is inserted into the sorted part using binary search: compare(Kabir, Om) = +1, so he goes after Om, at the end.

6 Real-world use

Ordering in real systems

Every sorted screen, ranked list and priority queue in an app has a comparator behind it.

Watch it with an example: “Sort by” on a shopping app

The same four phones, re-sorted each time the shopper taps a different option. Each option is just a different Comparator.

One list, three comparators 4 steps
Animated example
  1. The search returns four phones in no particular order.
  2. “Price: low to high” uses comparingInt(Phone::price). A and C cost the same; the stable sort keeps A before C, as they were.
  3. “Rating” sorts by stars, highest first, using reversed().
  4. “Price: high to low” with a rating tie-breaker: C (★4.6) now comes before A (★4.2). (Simplified: real apps sort in the database and add a unique ID as the last tie-breaker.)

1. “Sort by” menus

Shopping and travel apps offer “price low to high”, “rating”, “newest”. Each option is a Comparator (often with a tie-breaker like product ID so the order is stable across pages).

user picks “Price ↑”→comparing(Product::price)→sorted results

2. Rankings and leaderboards

Exam results, sales leaderboards and cricket tables sort by a main score with tie-breakers (net run rate, then wins), exactly a thenComparing chain.

points ↓→thenComparing(nrr ↓)→league table

3. Priority processing

Support tickets by severity then age, hospital triage by condition, delivery jobs by deadline: a PriorityQueue with a Comparator always hands out the most urgent item next.

new ticket→PriorityQueue(bySeverity)→most urgent first

4. Natural orders in value types

Types like LocalDate, BigDecimal and app version numbers implement Comparable, so they sort correctly in TreeMaps and reports without extra code.

TreeMap<LocalDate, …>→compareTo→chronological report

Examples are simplified. Large lists are usually sorted by the database (ORDER BY) before reaching Java.

7 Run the code

Exam cell: three printouts from one list

import java.util.*;

class Student implements Comparable<Student> {
    final int roll;
    final String name;
    final int marks;

    Student(int roll, String name, int marks) {
        this.roll = roll;
        this.name = name;
        this.marks = marks;
    }

    int roll() { return roll; }
    String name() { return name; }
    int marks() { return marks; }

    @Override
    public int compareTo(Student o) { return Integer.compare(roll, o.roll); }

    @Override
    public String toString() { return String.format("%02d %-6s %d", roll, name, marks); }

    static final Comparator<Student> BY_MERIT =
        Comparator.comparingInt(Student::marks).reversed().thenComparing(Comparator.naturalOrder());
    static final Comparator<Student> BY_NAME =
        Comparator.comparing(Student::name, String.CASE_INSENSITIVE_ORDER);
}

public class Main {
    static void print(String title, List<Student> list) {
        System.out.println(title);
        for (Student s : list) System.out.println("  " + s);
    }

    public static void main(String[] args) {
        List<Student> students = new ArrayList<>(List.of(
            new Student(21, "Om", 92), new Student(7, "Riya", 92),
            new Student(12, "Kabir", 78), new Student(3, "zoya", 85)));

        Collections.sort(students);
        print("Register:", students);
        students.sort(Student.BY_MERIT);
        print("Merit list:", students);
        students.sort(Student.BY_NAME);
        print("Certificates:", students);
    }
}
Register: 03 zoya 85 07 Riya 92 12 Kabir 78 21 Om 92 Merit list: 07 Riya 92 21 Om 92 03 zoya 85 12 Kabir 78 Certificates: 12 Kabir 78 21 Om 92 07 Riya 92 03 zoya 85
  • implements Comparable<Student>The natural order: roll number. Collections.sort(students) uses it.
  • Integer.compare(roll, o.roll)Safe comparison; no subtraction overflow.
  • BY_MERITMarks high → low, ties broken by the natural order (roll).
  • BY_NAMECase-insensitive, so “zoya” doesn't jump after capitals.

9 Quiz and revision

Check yourself

Quick revision

Lesson 11.8 in one screen

  • Comparable (java.lang): compareTo(o) inside the class = one natural order.
  • Comparator (java.util): compare(a, b) outside = any number of orders, even for classes you can't edit.
  • Result sign: negative (before), 0 (same), positive (after).
  • Build comparators: comparing, comparingInt, thenComparing, reversed, nullsFirst/Last, naturalOrder, reverseOrder, String.CASE_INSENSITIVE_ORDER.
  • Use Integer.compare, never subtraction. Keep compareTo consistent with equals.
  • Used by Collections.sort, List.sort, Arrays.sort, TreeSet, TreeMap, PriorityQueue. Object sort = stable TimSort.

Interview and viva questions

Comparable vs Comparator: when do you use which?

Implement Comparable when the class has one obvious, natural order (ID, date, version). Use Comparators for every other order, for orders that depend on the situation (a screen's “sort by” choice), and for classes you don't own. Many classes have both: a natural order plus named comparators.

What does “consistent with equals” mean?

That compareTo returns 0 exactly when equals returns true. If not, sorted collections disagree with hash collections: a TreeSet may treat two unequal objects as duplicates, or keep two equal ones. BigDecimal is a famous exception: 2.0 and 2.00 compare as 0 but aren't equal.

Can you sort with a lambda?

Yes. Comparator is a functional interface, so list.sort((a, b) -> Integer.compare(a.marks, b.marks)) works, as does list.sort(Comparator.comparingInt(Student::marks)). Lambdas are covered in Lesson 14.1.

What is “Comparison method violates its general contract”?

TimSort throws this IllegalArgumentException when it detects an inconsistent comparator, e.g. one that isn't transitive, uses random values, or overflows with subtraction. Fix the comparator so it's a proper total order.

How do you sort in descending order?

list.sort(Comparator.reverseOrder()) for natural order, cmp.reversed() for a custom comparator, or Collections.sort(list, Collections.reverseOrder()).

import java.util.*;

class Product implements Comparable<Product> {

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<int[]> d = new ArrayList<>(List.of(new int[]{410210, 14}, new int[]{400703, 11}, new int[]{410210, 9}));

three long amounts

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Long> paise = new ArrayList<>(List.of(9_000_000_000L, -5L, 300L));

Real-world scenario questions (asked in company interviews)

Sorting questions in interviews check whether your orders are correct, stable and maintainable.

E-commerce · bugJunior

Products jump between pages

Search results are sorted by price and shown 20 per page. Users report the same product appearing on page 1 and page 2, and some never appearing. Many products share the same price. What's wrong?

The interviewer is checking: tie-breakers and deterministic ordering.

Show a strong answer
  • Ties by price have no defined order, so each page request (often a separate database query) may order equal-priced products differently.
  • Add a unique tie-breaker: comparing(Product::price).thenComparing(Product::id) in Java, or ORDER BY price, id in SQL.
  • Now every request produces the same total order, so pages don't overlap.

Avoid: blaming caching. The order itself is ambiguous.

Fintech · correctnessJunior

Large transactions sorted wrongly

A report sorts transactions by amount in paise using (a, b) -> (int) (a.paise - b.paise). Small amounts sort fine; crore-rupee transfers appear in random places. Why?

The interviewer is checking: overflow and casting in comparators.

Show a strong answer
  • The difference of two large long values cast to int overflows, so the sign can be wrong.
  • Use Long.compare(a.paise, b.paise) or Comparator.comparingLong(Txn::paise).
  • Add a test with very large and negative values; a broken comparator can even make TimSort throw.

Avoid: converting to double; precision issues follow.

Sports · designFresher

Points table for a cricket league

Rank teams by points (high first); if equal, by net run rate (high first); if still equal, by team name. Write the comparator.

The interviewer is checking: multi-level comparators.

Show a strong answer
  • Comparator.comparingInt(Team::points).reversed().thenComparing(Comparator.comparingDouble(Team::nrr).reversed()).thenComparing(Team::name).
  • Note that reversed() on a chain reverses everything before it, so reverse each key's comparator separately, as above.
  • Keep it as a named constant (e.g. Team.TABLE_ORDER) and unit-test tie cases.

Avoid: a long hand-written if/else compare method; it's easy to get a branch wrong.

Platform · designMid

Should Order implement Comparable?

A teammate wants Order implements Comparable<Order> comparing by total amount, “because we often sort by amount”. Do you agree?

The interviewer is checking: what a natural order should be.

Show a strong answer
  • Amount isn't a natural, unique order: two different orders can have the same amount, so compareTo wouldn't be consistent with equals, and TreeSet<Order> would drop orders.
  • If anything, the natural order should be the unique order ID or creation time. Sorting by amount should be a named Comparator (Order.BY_AMOUNT).
  • This keeps sorted collections and reports correct and explicit.

Avoid: making the most frequently used sort the natural order just for convenience.
