String class and immutability

Names, emails, OTP messages, invoice numbers: most data a program touches is text. In Java, text is a String object, and Strings have one rule that surprises every beginner: they never change. You'll see what that means in memory, why toUpperCase() seems to “not work”, why Java chose this design, and then practise with 11 problems.

Module 4 · Arrays and Strings⏱ 22 minBeginner11 practice problems
1 The story

The name that wouldn't change

Riya is making name badges for the college fest. Names must be printed in capitals. She writes name.toUpperCase(); and then System.out.println(name);. The badge still says riya.

Riya

Sir, toUpperCase() doesn't work! My name is still small letters.

Arjun Sir

It worked perfectly. It made a new String, “RIYA”, and handed it back to you. You just didn't catch it. Write name = name.toUpperCase();.

Riya

So it can't change the original “riya”?

Arjun Sir

No method can. Java Strings are immutable: once created, their characters never change. Every “change” gives you a new String. Today we'll see why Java chose that, and why it matters in real code.

2 Definition

What is a String?

Formal definition (write this in exams)

A String is an object of the final class java.lang.String that represents an immutable sequence of characters. Once a String object is created, its contents cannot be changed; methods such as toUpperCase(), concat() and replace() return a new String. Characters are indexed from 0 to length() - 1.

In simple words

A String is text written in permanent ink. You can read it, copy it, or make a new card with changes, but you can never edit the card you already have.

Words you'll meet in this lesson

String facts at a glance

Classjava.lang.String (imported automatically), declared final: no subclass can change its behaviour
Lengths.length() (a method, with brackets)
One characters.charAt(i) returns a char; valid i is 0 to length() - 1
Join"Hi " + name; any value joined to a String becomes text
“Changing” methodstoUpperCase, trim, replace, concat, substring … all return a new String
Inside (Java 9+)A private final byte[] holding the characters, with no method that writes to it

Exam tip: String s = "Hi"; s.concat("!"); System.out.println(s); prints Hi. The result of concat was thrown away. This exact question appears in many MCQ tests.

Why did Java make Strings immutable?

ReasonWhat it gives you
Sharing (String pool)Thousands of variables can safely share one "Pune" object, saving memory.
SecurityA file path, URL or username checked for safety can't be changed afterwards by other code.
Thread safetyMany threads can read the same String with no locks.
Fast HashMap keysThe hash code never changes, so String caches it and makes a reliable map key.

The cost: every “change” creates a new object. Building a long text with += inside a big loop creates thousands of throwaway Strings. For that, use StringBuilder (Lesson 4.6).

4 Step by step

What really happens when you “change” a String

  1. Create

    String name = "riya";
    A String object holding r-i-y-a exists on the heap; the variable name holds its address.

  2. Call a “changing” method

    name.toUpperCase();
    The method reads the old characters, creates a new String “RIYA”, and returns its address. Nobody stores it, so it becomes garbage.

  3. Catch the result

    name = name.toUpperCase();
    Now the variable name is updated to point to the new object. The variable changed; the old String did not.

  4. Read characters safely

    for (int i = 0; i < name.length(); i++) {
    System.out.println(name.charAt(i));
}
    charAt is read-only. There is no setCharAt on String; name.charAt(0) = 'r' doesn't even compile.

  5. Watch out for null

    String s = null; s.length(); compiles but throws NullPointerException. "" is safe: its length is 0.

    null means the variable refers to no object, so there is nothing to call length() on.
5 See it happen

Variables move, Strings stay: both views

Left: the code and what prints. Right: the variables on the stack and the String objects on the heap.

Immutability in memory 6 steps
What you see
  1. Create: name refers to the String “riya”.
  2. Call: toUpperCase() returns “RIYA”, but we didn't store it, so name is still “riya”.
  3. Reassign: storing the result makes name refer to “RIYA”.
  4. Share: other = name copies the reference. Both print “RIYA”.
  5. Join: name + " S" builds a new String. other still sees “RIYA”, because that object never changed.
  6. Try to edit: there is no way to assign into a String's characters. javac rejects it.
Behind the screen
  1. The variable stores only a reference; the characters live in a String object on the heap.
  2. toUpperCase() read “riya” and built a separate “RIYA” object. With no reference to it, the garbage collector can remove it.
  3. Assignment changes which object name points to. The old object is exactly as it was.
  4. Copying a String variable copies the reference. Since Strings never change, sharing is completely safe.
  5. Concatenation always creates a new String. That's why other is unaffected.
  6. The characters are stored in a private final byte[] that String never writes to after construction, and the class is final so no subclass can add a setter.
6 Real-world use

Strings in real systems

Almost all input and output is text, and immutability makes Strings safe to pass around everywhere.

Checking "Riya@2025" with charAt() 6 steps
Animated example
  1. A String is a sequence of chars with indexes 0 to length() − 1. Length 9 passes the first rule.
  2. i = 0: pw.charAt(0) is 'R'. Character.isUpperCase('R') is true → has a capital.
  3. i = 1 … 4: 'i', 'y', 'a', '@': not digits. The loop keeps going.

  6. Read-only: charAt only reads. A String object can never be changed after it is created; that's immutability.

1. Form input

Names, emails, phone numbers and addresses arrive as Strings. Code trims, validates and normalises them, each step returning a new, cleaner String.

" Riya@Mail.com "→trim().toLowerCase()→"riya@mail.com"

2. Messages and notifications

SMS, emails and push notifications are built by joining fixed text with values: names, amounts, masked numbers, links.

Template + values→"Hi " + name + …→SMS text

3. Keys in maps and caches

User IDs, product codes and session IDs are used as HashMap keys. Because a String can't change, its hash code stays the same and the entry is always found.

"SKU-1042"→map.get(key)→Product

4. Security checks

A file path or URL is checked (“is this allowed?”) and then used. If Strings could change, other code could swap the value between the check and the use. Immutability closes that gap.

Path→check, then open→Same path guaranteed

9 Quiz and revision

Check yourself

Quick revision

Lesson 4.3 in one screen

  • A String is an object of the final class java.lang.String: an immutable sequence of characters.
  • “Changing” methods return a new String: always write s = s.method();.
  • length() with brackets; charAt(i) for i from 0 to length() - 1.
  • + works left to right; once a String appears, the rest is joined as text.
  • Reassigning a variable moves the reference; the old String is untouched.
  • Why immutable: pool sharing, security, thread safety, cached hash codes.
  • Cost: heavy concatenation in loops creates many objects → use StringBuilder.

Interview and viva questions

Why are Strings immutable in Java?

So they can be safely shared from the String pool, used in security checks without being changed afterwards, read by many threads without locks, and used as HashMap keys with a hash code that can be cached because it never changes.

How is String made immutable internally?

The class is final (no subclass can add mutators), the character data is a private final array, no method writes to it after construction, and methods that “modify” return new String objects.

If Strings are immutable, how does s = s + "x" work?

It creates a new String containing the old characters plus "x" and stores its reference in s. The variable changes; the original object doesn't.

What is the difference between "" and null?

"" is a real String object with length 0; you can call methods on it. null means no object; calling any method throws NullPointerException.

Why are passwords often kept in char[] instead of String?

A String can't be erased: it stays in memory until garbage-collected and may show up in heap dumps or logs. A char[] can be overwritten with zeros as soon as it has been used. Swing's JPasswordField.getPassword() returns char[] for this reason.

P1Easy

Count the vowels

Count how many vowels (a, e, i, o, u, either case) a sentence has.

Input
text = "Java Is Fun To Learn"
Expected output
Vowels: 7
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String text = "Java Is Fun To Learn";
        int count = 0;
        for (int i = 0; i < text.length(); i++) {
            char ch = Character.toLowerCase(text.charAt(i));
            if (ch == 'a' || ch == 'e' || ch == 'i' || ch == 'o' || ch == 'u') {
                count++;
            }
        }
        System.out.println("Vowels: " + count);
    }
}
Vowels: 7

How it works: charAt(i) gives one char at a time, from index 0 to length() - 1. Lower-casing each character first means we only need to compare with five letters.

P3Easy

Palindrome check

Check whether a word reads the same forwards and backwards, ignoring case.

Input
word = "Malayalam"
Expected output
Malayalam is a palindrome
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String word = "Malayalam";
        String w = word.toLowerCase();
        boolean palindrome = true;
        for (int i = 0, j = w.length() - 1; i < j; i++, j--) {
            if (w.charAt(i) != w.charAt(j)) {
                palindrome = false;
                break;
            }
        }
        System.out.println(word + (palindrome ? " is" : " is not") + " a palindrome");
    }
}
Malayalam is a palindrome

How it works: two indexes move towards each other, comparing pairs. We stop at the first mismatch, and we only check half the word. toLowerCase() returns a new String, so we store it in w.

P5Medium

Change upper case letters to lower case and lower to upper. Leave other characters alone.

P7Medium

Anagram check

Two words are anagrams if they use exactly the same letters the same number of times. Check “listen” and “silent”.

Input
a = "listen", b = "silent"
Expected output
listen and silent are anagrams
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String a = "listen", b = "silent";
        boolean anagram = a.length() == b.length();
        int[] count = new int[26];
        for (int i = 0; anagram && i < a.length(); i++) {
            count[a.charAt(i) - 'a']++;
            count[b.charAt(i) - 'a']--;
        }
        for (int c : count) {
            if (c != 0) anagram = false;
        }
        System.out.println(a + " and " + b + (anagram ? " are" : " are not") + " anagrams");
    }
}
listen and silent are anagrams

How it works: ch - 'a' turns a lower-case letter into 0–25, an index into a counting array (Lesson 4.1). Letters of a add 1, letters of b subtract 1. If every count ends at 0, the letters match. One pass, no sorting.

P10Business problem

Validate a username

A sign-up form allows usernames that are 5 to 15 characters long, start with a letter, and contain only letters, digits or underscore. Check several usernames.

Input
"riya_99", "9lives", "ab", "hello world", "Kabir_Dev"
Expected output
riya_99 -> OK
9lives -> must start with a letter
ab -> must be 5-15 characters
hello world -> invalid character ' '
Kabir_Dev -> OK
Show solution and explanation 
public class Main {
    public static void main(String[] args) {
        String[] names = {"riya_99", "9lives", "ab", "hello world", "Kabir_Dev"};
        for (String u : names) {
            String problem = "";
            if (u.length() < 5 || u.length() > 15) {
                problem = "must be 5-15 characters";
            } else if (!Character.isLetter(u.charAt(0))) {
                problem = "must start with a letter";
            } else {
                for (int i = 0; i < u.length(); i++) {
                    char ch = u.charAt(i);
                    if (!(Character.isLetterOrDigit(ch) || ch == '_')) {
                        problem = "invalid character '" + ch + "'";
                        break;
                    }
                }
            }
            System.out.println(u + " -> " + (problem.isEmpty() ? "OK" : problem));
        }
    }
}
riya_99 -> OK 9lives -> must start with a letter ab -> must be 5-15 characters hello world -> invalid character ' ' Kabir_Dev -> OK

How it works: check the cheapest rule (length) first, then the first character, then every character. Returning a reason, not just true/false, lets the form tell the user what to fix. Real systems repeat this check on the server; never trust only the browser.

P11Business problem

Generate invoice numbers

Invoice numbers look like INV-2026-00042: a prefix, the year, and the serial number padded with zeros to 5 digits. Generate them for a few serials.

Input
year = 2026, serials = 7, 42, 1350, 98765
Expected output
INV-2026-00007
INV-2026-00042
INV-2026-01350

Show solution and explanation 
public class Main {

        int[] serials = {7, 42, 1350, 98765};

Real-world scenario questions (asked in company interviews)

String bugs in production often come from forgetting immutability. Decide your answer first, then open the model answer.

E-commerce · loginFresher

“Email not registered” for a registered user

Users who type " Riya@Mail.com" (with a space and capitals) can't log in, though they registered as riya@mail.com. The code has email.trim(); email.toLowerCase(); before the lookup. Why doesn't it work?

The interviewer is checking: do you know String methods return new Strings?

Show a strong answer
  • Both calls return new Strings that are thrown away; email is unchanged.
  • Fix: email = email.trim().toLowerCase();
  • Normalise the same way at sign-up and at login, so stored and typed values always match.
  • Add a unit test with spaces and mixed case.

Avoid: “The database is case-sensitive, change the database.” The code bug is the real cause.

Fintech · reports1–3 years

The CSV export that takes minutes

A transaction export builds a CSV with csv = csv + row + "\n"; inside a loop. With 1,000 rows it's instant; with 2 lakh rows it takes minutes and memory spikes. Explain and fix.

The interviewer is checking: do you connect immutability with the cost of repeated concatenation?

Show a strong answer

Each + creates a brand-new String and copies all the text so far. Row 1 copies a little, row 2 lakh copies almost the whole file: the total copying grows roughly with n², and millions of temporary Strings stress the garbage collector.

  • Use a StringBuilder and append each row: it grows one buffer instead of copying everything each time.
  • For big exports, write rows directly to the output stream or file instead of building one giant String.

Avoid: increasing the server's memory. The algorithm is the problem.

Security · credentials1–3 years

A password showed up in a heap dump

During a production memory investigation, a heap dump was shared with a vendor. A security review found users' plain-text passwords inside it. The login code stores the password in a String before hashing. What happened, and what would you change?

The interviewer is checking: do you understand that immutable Strings can't be wiped from memory?

Show a strong answer
  • A String can't be overwritten. It stays in memory until the garbage collector reclaims it, which may be much later, so a heap dump can capture it.
  • Keep secrets in a char[] (or byte[]) and overwrite it with Arrays.fill(pw, '\0') right after hashing.
  • Hash immediately with a password-hashing algorithm (bcrypt, scrypt, Argon2), never log request bodies with passwords, and restrict who can take and share heap dumps.

Avoid: “Set the String to null.” That removes the reference, not the characters in memory.

Backend · caching1–3 years

Why String makes a safe map key

A teammate asks: “Our cache uses HashMap<String, Product> keyed by SKU. Could we use our own mutable SkuCode class with a setter instead?” What do you explain?

The interviewer is checking: do you know why immutability matters for hash-based keys?

Show a strong answer
  • A HashMap puts an entry in a bucket chosen from the key's hash code. If a mutable key changes after insertion, its hash changes and get looks in the wrong bucket: the entry is “lost” though still in the map.
  • String is immutable, so its hash code never changes; Java even caches it after the first calculation, making lookups fast.
  • If a custom key class is needed, make it immutable (final fields, no setters) and implement equals and hashCode consistently.

Avoid: mutable keys “because we never change them”. Someone eventually will.
