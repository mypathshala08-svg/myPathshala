Class loaders and class loading

Your program doesn't load all its classes at start-up. The JVM pulls each class in the first time it is needed, checks it, gives its static fields default values, and only then runs its static initializer. You'll see every phase, learn the exact rules for when a static block runs, meet the three built-in class loaders and how they delegate, tell ClassNotFoundException from NoClassDefFoundError, and then practise with 8 problems.

1 The story

The static block that printed “too late”

Riya's team wrote a Config class whose static block prints “Config loaded” and reads settings. She expected the message as soon as the app started. Instead it appeared halfway through the logs, right before the first payment. And on the test server, a missing JAR made the app fail with NoClassDefFoundError, an error she had never seen in college.

Riya

Sir, why did “Config loaded” print so late? The app had been running for a minute.

Arjun Sir

Because the JVM loads classes lazily. A class's static block runs on its first active use: creating an object, calling a static method, or reading a non-constant static field. Nobody touched Config until the first payment.

Riya

And the NoClassDefFoundError on the test server?

Arjun Sir

The class was there when you compiled, but missing (or broken) when the JVM tried to load it. Let's follow a class from the .class file to “ready”, and both mysteries will make sense.

2 Definition

What is class loading?

Formal definition (write this in exams)

Class loading is the process by which the JVM makes a class available at run time. It has three phases. Loading: a class loader finds the binary representation (the .class bytes) and creates the class in the method area. Linking: verification checks the bytecode is valid and safe, preparation allocates static fields and sets them to default values, and resolution replaces symbolic references with direct ones (this may happen lazily). Initialization: the class's static initializer (<clinit>: static field initializers and static blocks, in source order) runs exactly once, on the class's first active use, after its superclass has been initialized.

In simple words

Before a new employee starts work: HR finds their file (loading), checks the documents (verify), gives them an empty desk (prepare), adds their phone number to the directory (resolve), and on their first real day they set up their desk (initialise), only once.

Words you'll meet in this lesson

Exam tip: a class is loaded and initialised at different moments. new Config[3] may load Config but does not initialise it, so its static block doesn't run. Initialisation happens at most once per class (per class loader), and a superclass is always initialised before its subclass.

3 Types and ways to use it

Three class loaders, one delegation rule

Bootstrap

Built into the JVM (native code). Loads the core classes of java.base: String, Object, ArrayList. Java shows it as null.

getClassLoader() == null

Platform

Java 9+ (replaced the Java 8 “extension” loader). Loads other JDK modules such as java.sql and java.xml.

"platform"

Application

Also called the system class loader. Loads your classes and libraries from the class path (-cp) or module path.

"app"

Watching loading vs initialisation

ClassNotFoundException vs NoClassDefFoundError

Static initializers are fragile: if one throws, the JVM wraps the exception in ExceptionInInitializerError and marks the class as failed. Every later use throws NoClassDefFoundError: Could not initialize class … until the JVM restarts. Keep static blocks small and never let them depend on things that can fail, like a network call.

4 Step by step

From .class file to a ready class

  1. Loading: find the bytes, with delegation

    new TaxConfig();   // first time TaxConfig is needed
    The application loader first asks its parent (platform), which asks the bootstrap loader. Neither has TaxConfig, so the application loader reads TaxConfig.class from the class path and defines the class. Delegation stops anyone from replacing core classes such as java.lang.String with their own.

  2. Verify

    The verifier checks the bytecode: correct types on the operand stack, no jumps outside the method, valid references to fields and methods.

    This is why a hand-edited or corrupted .class file fails with a VerifyError instead of crashing the JVM. JDK classes from the CDS archive are already verified, which helps start-up.

  3. Prepare

    static String state = loadState();   // state = null for now
static int gstPercent;               // 0
    Memory for static fields is allocated and set to defaults: 0, 0.0, false, null. Compile-time constants (static final int MAX = 100) already get their real value here. No Java code runs in this phase.

  4. Resolve

    Symbolic names in the constant pool (“method TaxConfig.loadState”) are turned into direct references.

    HotSpot resolves lazily: each reference is resolved the first time the instruction using it runs. That's also when a missing class referenced from your code surfaces as NoClassDefFoundError.

  5. Initialise: run <clinit> once

    static {
    gstPercent = state.equals("MH") ? 18 : 12;
}
    The superclass is initialised first. Then the static field initializers and static blocks run in source order, in one compiler-generated method <clinit>. The JVM takes a lock while doing this, so even with many threads it runs exactly once.
5 See it happen

One class, every phase: both views

Left: the code and the console. Right: the class loaders and the class's progress through the phases.

The life of class AppConfig 6 steps
What you see
  1. Load: creating an AppConfig[] makes the JVM load the class; -verbose:class prints a line.
  2. Link: the class is verified and prepared. The program continues and prints the array line.
  3. Not yet: arrays and class literals don't count as active use, so the static block hasn't run.
  4. Initialise: reading the non-constant static field env runs the static initializer: load(), then the static block.
  5. Once only: the class is ready; later reads just return the value.
  6. Failure: if the initializer throws, you get ExceptionInInitializerError once, then NoClassDefFoundError on every later use.
Behind the screen
  1. The application loader delegates to platform, which delegates to bootstrap. Neither knows Main$AppConfig, so the application loader reads it from the class path.
  2. Verification passes. Preparation creates the static fields: the constant gets 100 straight away; env gets null.
  3. The class is loaded and linked but not initialised. Its static block hasn't run.
  4. The getstatic for env is the first active use. References are resolved as they are used, and <clinit> runs: load() then the static block.
  5. env now holds "prod". The class is marked initialised; this never happens again for this class loader.
  6. If <clinit> throws, the class is marked erroneous. The first caller sees ExceptionInInitializerError; every later caller sees NoClassDefFoundError.
6 Real-world use

Class loading in real systems

You rarely write a class loader yourself, but every framework you use depends on these rules.

Watch it with an example: a shop loading its UPI payment plug-in

The checkout loads payment providers by name from a plug-in JAR. Watch delegation find the class, linking prepare it, and the static block run only when the first payment arrives.

Loaded on first payment, initialised once 6 steps
Animated example
  1. Start-up: the shop starts with both JARs on the class path, but UpiProvider isn't loaded: no one has needed it yet.
  2. First payment: the checkout loads the provider by name. The application loader first asks platform, which asks bootstrap. Neither knows a class called pay.UpiProvider.
  3. Found: the application loader reads the class from upi.jar and defines it.
  4. Linked: the bytecode is verified and the static field feePaise is prepared with its default, 0.
  5. Initialised: Class.forName also initialises the class, so the static initializer runs once: the fee becomes 200 paise and “UPI ready” is printed.
  6. Next payments: the class is already loaded and initialised, so nothing runs again. A provider whose JAR is missing fails with ClassNotFoundException, which the checkout can catch and report.

1. Application servers

A server such as Tomcat gives each deployed web app its own class loader, so two apps can use different versions of the same library. Undeploying an app should make its loader (and all its classes) unreachable; if something still references it, metaspace leaks.

WAR deployed→its own ClassLoader→Isolated classes

2. Database drivers and plug-ins

Old JDBC code loaded drivers with Class.forName("…Driver"), whose static block registered the driver. Modern drivers are found automatically through ServiceLoader, which also loads classes by name from JARs.

Driver JAR→ServiceLoader / forName→Registered driver

3. Lazy, thread-safe singletons

The holder-class idiom puts a singleton in a static field of a nested class. Because a class is initialised once, under a JVM lock, on first use, you get lazy creation and thread safety without synchronized.

getInstance()→Holder.INSTANCE→Created once

4. Faster start-up

Loading and verifying thousands of classes takes time, which matters for serverless functions and command-line tools. CDS archives (on by default for JDK classes) and application CDS (-XX:SharedArchiveFile) store pre-parsed classes to cut it down.

Cold start→CDS archive→Fewer ms to ready

5. Dependency problems at deploy time

A library compiled against version 2 of a JAR but deployed with version 1 fails with NoClassDefFoundError or NoSuchMethodError. Build tools (Maven, Gradle) can show the dependency tree to find the conflict.

Runtime error→mvn dependency:tree→Align versions

Examples are simplified. Frameworks such as Spring and Hibernate also generate classes at run time (proxies), which are loaded by the same rules.

  • Prepare = static fields get defaults; initialise = static initializers and blocks run, in source order, once.

Interview and viva questions

Explain the class loading process in Java.

A class loader finds the class's bytes and defines the class (loading). The JVM then links it: verifies the bytecode, prepares static fields with default values, and resolves symbolic references (often lazily). Finally it initialises the class by running its static field initializers and static blocks, once, on the first active use, after initialising its superclass.

What are the built-in class loaders and what is delegation?

Bootstrap (native, loads core java.base classes), platform (Java 9+, other JDK modules; the extension loader in Java 8) and application or system (the class path). Each loader first delegates to its parent; only if the parent can't find the class does it load it itself. This keeps core classes from being replaced and avoids loading the same class twice.

ClassNotFoundException vs NoClassDefFoundError?

ClassNotFoundException is a checked exception thrown when code explicitly loads a class by name and it isn't found. NoClassDefFoundError is an error thrown when a class that was available at compile time can't be found or initialised at run time, for example a missing JAR or a static initializer that failed earlier.

When exactly does a static block run?

Once, when the class is initialised: on its first active use, such as creating an instance, calling a static method, accessing a non-constant static field, calling Class.forName, initialising a subclass, or when it is the main class. Not when merely declaring a variable of the type, creating an array of it or reading a compile-time constant.

Can two classes with the same name exist in one JVM?

Yes, if different class loaders load them. A class's identity is its name plus its defining loader, so they are different types; casting one to the other throws ClassCastException. Application servers use this to isolate web applications.

P5Medium

Load a class by name, safely

Load classes by their names at run time with Class.forName. Report which exist instead of crashing.

            try {

P6Business problem

A bad config value breaks the class for good

A tax table reads its GST rate from a config string in a static initializer. The config contains "18%", which isn't a number. Show what happens on the first and second attempts to use the class.

Input
config value = "18%"
Expected output
attempt 1: java.lang.ExceptionInInitializerError
  cause: java.lang.NumberFormatException: For input string: "18%"
attempt 2: java.lang.NoClassDefFoundError: Could not initialize class Main$TaxTable
Show solution and explanation 
public class Main {
    static class TaxTable {
        static int gstPercent = Integer.parseInt("18%");
    }

    public static void main(String[] args) {
        for (int attempt = 1; attempt <= 2; attempt++) {
            try {
                System.out.println("GST: " + TaxTable.gstPercent);
            } catch (Throwable e) {
                System.out.println("attempt " + attempt + ": " + e);
                if (e instanceof ExceptionInInitializerError) {
                    System.out.println("  cause: " + e.getCause());
                }
            }
        }
    }
}
attempt 1: java.lang.ExceptionInInitializerError cause: java.lang.NumberFormatException: For input string: "18%" attempt 2: java.lang.NoClassDefFoundError: Could not initialize class Main$TaxTable

How it works:

  1. The first use runs the static initializer, which throws NumberFormatException. The JVM wraps it in ExceptionInInitializerError.
  2. The class is now marked as failed. Every later use throws NoClassDefFoundError: Could not initialize class …, without retrying. In a server, this means one bad config value breaks the feature until a restart.
  3. Validate configuration with clear errors before it reaches static initializers, or load it in a normal method that can be retried.
P7Business problem

The discount that came out as zero

A shop's pricing class computes FESTIVE_PRICE from BASE_PRICE, but declares them in the wrong order. Show the bug, then the fixed order.

Input
base price Rs 1000, festive discount 20%
Expected output
Buggy festive price: Rs 0
Fixed festive price: Rs 800
Show solution and explanation 
public class Main {
    static class BuggyPricing {
        static int festivePrice = discounted();   // runs first
        static int basePrice = 1000;              // not set yet!
        static int discounted() {
            return basePrice * 80 / 100;
        }
    }

    static class FixedPricing {
        static int basePrice = 1000;              // declared first
        static int festivePrice = discounted();
        static int discounted() {
            return basePrice * 80 / 100;
        }
    }

    public static void main(String[] args) {
        System.out.println("Buggy festive price: Rs " + BuggyPricing.festivePrice);
        System.out.println("Fixed festive price: Rs " + FixedPricing.festivePrice);
    }
}
Buggy festive price: Rs 0 Fixed festive price: Rs 800

How it works:

  1. During preparation, every static field gets its default value (0). During initialisation, the initializers run top to bottom.
  2. In BuggyPricing, discounted() runs while basePrice is still 0, so the festive price becomes 0, and stays 0 because it is computed only once.
  3. Declaring basePrice first fixes it. Making it static final int BASE_PRICE = 1000 (a constant) would also fix it, since constants are set before any initializer runs.

    }

    public static class UpiProvider implements Provider {
        public String pay(int amount) { return "UPI paid Rs " + amount; }
    }

    public static class CardProvider implements Provider {
        public String pay(int amount) { return "Card paid Rs " + amount; }
    }

    public static void main(String[] args) throws Exception {
        String[] enabled = {"Main$UpiProvider", "Main$CardProvider", "Main$CryptoProvider"};
        for (String className : enabled) {
            try {
                Class<?> c = Class.forName(className);
                Provider p = (Provider) c.getDeclaredConstructor().newInstance();
                System.out.println(p.pay(499));
            } catch (ClassNotFoundException e) {
                System.out.println("skipped unknown provider " + e.getMessage());
            }
        }
    }
}
UPI paid Rs 499 Card paid Rs 499 skipped unknown provider Main$CryptoProvider

How it works:

  1. Nested classes have binary names with a $, such as Main$UpiProvider.
  2. Class.forName loads and initialises the class; getDeclaredConstructor().newInstance() creates an object without a new in the source. This is how JDBC drivers, logging back-ends and framework plug-ins were traditionally wired in.
  3. A missing provider produces ClassNotFoundException, which we turn into a warning instead of a failed checkout.

Real-world scenario questions (asked in company interviews)

Class loading problems usually appear at deploy time, under pressure. Decide your answer first, then open the model answer.

Banking · deploymentFresher

Works on my machine, NoClassDefFoundError on the server

A loan-calculator service runs fine in the IDE. On the test server, the first EMI request fails with java.lang.NoClassDefFoundError: com/acme/util/MoneyFormatter. Start-up was fine. What is the likely cause and how do you check?

The interviewer is checking: do you know classes load lazily and what NCDFE means?

Show a strong answer
  • The code was compiled with MoneyFormatter available, but at run time the JAR containing it is missing from the class path. Because classes load lazily, the error appears only when the first EMI request needs the class, not at start-up.
  • Check the deployed package or class path (for example list the JAR's contents), and the build's dependency scope: a library marked “provided” or “test” is not packaged.
  • Also check the full stack trace: if it says “Could not initialize class”, the class exists but its static initializer failed earlier; look for the first ExceptionInInitializerError in the logs.

Avoid: catching the error and continuing.

E-commerce · configuration1–3 years

One bad property killed checkout until restart

A PricingRules class loads a properties file in a static block. After an ops change, a value became "15 percent". The first checkout failed with ExceptionInInitializerError; every checkout after that failed with NoClassDefFoundError, even after the file was corrected. Why didn't fixing the file help, and how would you redesign it?

The interviewer is checking: do you know a class is initialised only once, and that failure is permanent?

Show a strong answer
  • The static initializer threw NumberFormatException, so the JVM marked PricingRules as failed. It never re-runs a class's initializer, so the corrected file was never read; only a restart helps.
  • Redesign: load configuration in an ordinary method or a managed bean at start-up, validate every value with clear messages, and fail fast at start-up rather than on the first customer request.
  • For values that can change, support reloading with validation, keeping the last good configuration if the new one is invalid.

Avoid: putting I/O or parsing that can fail inside a static block.

SaaS · app server3+ years

Metaspace grows with every redeploy

An internal SaaS platform hot-redeploys a web app on Tomcat several times a day. After about 20 redeploys the server dies with OutOfMemoryError: Metaspace. Heap usage looks normal. Explain the mechanism and how you would find the cause.

The interviewer is checking: do you understand that classes are unloaded only when their class loader becomes unreachable?

Show a strong answer
  • Each deployment gets a new class loader, which loads its own copies of all the app's classes into metaspace. The old classes can be unloaded only when the old loader, every class it loaded and every object of those classes are unreachable.
  • Something outside the app still references the old loader: a JDBC driver registered in DriverManager, a thread the app started and never stopped, a ThreadLocal value on a server thread, or a static cache in a shared library.
  • Take a heap dump after a few redeploys, look for multiple web-app class loader instances, and follow the path to GC roots. Fix by deregistering drivers, stopping threads and clearing thread-locals on shutdown. Cap metaspace with -XX:MaxMetaspaceSize to fail early and visibly.

Avoid: simply raising the metaspace limit.

Payments · singleton design1–3 years

Lazy and thread-safe without locks

A payment SDK must create its expensive GatewayClient only when the first payment happens, and many threads may call getInstance() at the same moment. A colleague wrote a synchronized method with an if (instance == null) check. What alternative uses class loading rules, and why is it safe?

The interviewer is checking: can you apply initialisation guarantees to a real design?

Show a strong answer
  • Use the holder idiom: private static class Holder { static final GatewayClient INSTANCE = new GatewayClient(); } and getInstance() returns Holder.INSTANCE.
  • Holder is initialised on its first active use, the first call to getInstance(), so creation is lazy.
  • The JVM initialises a class under a lock and only once; other threads wait and then see the fully built instance. No synchronized on every call, so no lock cost afterwards.
  • An enum with a single constant is another safe option.

Avoid: double-checked locking without volatile; it is broken.
