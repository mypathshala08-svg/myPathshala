ExecutorService and thread pools

So far you created a new Thread for every job. Real servers never do that: thousands of tasks would mean thousands of threads. Instead they hand tasks to a thread pool, a few long-lived workers that take jobs from a queue. You'll use ExecutorService to run Runnables and Callables, get results back through Futures, set timeouts, shut pools down correctly, and meet CompletableFuture and virtual threads.

1 The story

One thread per order? The server disagrees

Riya's canteen app goes viral during exam week. Her server creates a new thread for every incoming order. At lunchtime 5,000 orders arrive in a minute, the server runs out of memory, and nobody gets lunch.

Riya

Sir, threads were supposed to make it faster!

Arjun Sir

Threads cost memory and switching time. Thousands of them help nobody. Keep a few workers and a queue of orders: each worker finishes an order and takes the next.

Riya

Do I write that queue and the workers myself?

Arjun Sir

No. Java has it ready: ExecutorService. You submit tasks; it runs them on a pool and gives you a Future for each result.

2 Definition

What are ExecutorService and thread pools?

Formal definition (write this in exams)

An executor separates task submission from task execution. java.util.concurrent.ExecutorService is an executor that manages a thread pool: a set of reusable worker threads that take submitted tasks from a queue and run them. Tasks are Runnable (no result) or Callable<V> (returns a V and may throw checked exceptions). submit() returns a Future<V>, which represents the pending result: get() waits for it, isDone() checks it, and cancel() attempts to stop the task. A pool is ended with shutdown() (finish queued tasks, accept no new ones) or shutdownNow() (interrupt running tasks).

In simple words

A thread pool is a call centre: a fixed team of agents (threads) and a waiting line (queue). You don't hire a new agent for every call. You get a ticket (Future) to collect your answer later.

Words you'll meet in this lesson

ExecutorServiceRuns tasks on a pool; you never call new Thread.
Thread poolReusable worker threads plus a task queue.
Callable<V>A task whose call() returns a value.
Future<V>A handle to a result that may not be ready yet.
shutdown()No new tasks; finish the queued ones; then the workers end.
CompletableFutureA Future you can chain steps onto, without blocking.

Exam tip: “A thread pool reuses a fixed number of threads to execute many tasks, reducing thread-creation overhead and limiting resource use.” And: Future.get() blocks; a failed task's exception arrives wrapped in ExecutionException.

3 Types and ways to use it

Pools and how they reuse threads

Five jobs, two workers

import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        for (int i = 1; i <= 5; i++) {
            int job = i;
            pool.submit(() -> System.out.println("job " + job + " on " + Thread.currentThread().getName()));
        }
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
job 1 on pool-1-thread-1 job 3 on pool-1-thread-1 job 4 on pool-1-thread-1 job 5 on pool-1-thread-1 job 2 on pool-1-thread-2

One real run. Your order of lines and which worker took which job will differ, but you'll only ever see two thread names.

Kinds of executors

Fixed pool

Exactly n workers. The default choice for steady server work.

newFixedThreadPool(n)

Single thread

One worker: tasks run one at a time, in submission order.

newSingleThreadExecutor()

Scheduled

Run after a delay or repeatedly: reminders, cleanups, reports.

newScheduledThreadPool(n)

Virtual threads

Java 21: very cheap threads, one per task, ideal for I/O-heavy work.

newVirtualThreadPerTaskExecutor()
Executors.newFixedThreadPool(n)          // n workers, unbounded queue: steady CPU/IO work
Executors.newCachedThreadPool()          // grows as needed, idle threads die: short bursts
Executors.newSingleThreadExecutor()      // one worker: tasks run strictly in order
Executors.newScheduledThreadPool(n)      // delays and repeats: schedule(task, 5, SECONDS)
Executors.newVirtualThreadPerTaskExecutor()  // Java 21: a cheap virtual thread per task

Always shut pools down. Pool threads are normal (non-daemon) threads. Forget shutdown() and your program never exits; in a server, forgetting it on short-lived pools leaks threads until memory runs out. Use try/finally, or in Java 21 a try-with-resources block (ExecutorService is AutoCloseable).

4 Step by step

The life of a submitted task

  1. Create the pool

    ExecutorService pool = Executors.newFixedThreadPool(4);
    A ThreadPoolExecutor object with an empty queue. Worker threads are started as the first tasks arrive.

  2. submit()

    Future<Integer> f = pool.submit(() -> fetchPrice("BuyNow"));
    The Callable is wrapped in a FutureTask. If a worker is free (or the pool may start one), it runs; otherwise it joins the queue. submit returns at once.

  3. A worker runs it

    The worker calls call(). The result (or the exception) is stored inside the FutureTask, which becomes done, and any thread waiting in get() is woken.

  4. The worker loops

    Instead of ending, the worker takes the next task from the queue, or waits for one (like the consumer in Lesson 12.5).

  5. shutdown()

    New submissions are rejected with RejectedExecutionException. Queued tasks still run. When the queue is empty, workers exit; awaitTermination lets you wait for that moment.
5 See it happen

Submit, queue, reuse: both views

Left: the code you write and the Futures you hold. Right: inside the pool, the task queue and two worker threads that never get replaced.

A thread pool at work 6 steps
What you see
  1. Executors.newFixedThreadPool(2) creates an ExecutorService with 2 worker threads that will be reused for every task.
  2. submit(task) hands over the job and returns immediately with a Future: a receipt for a result that isn't ready yet.
  3. A third task arrives while both workers are busy. It waits in the pool's queue; no extra thread is created.
  4. When a worker finishes task1, its Future becomes done, and the same worker immediately takes task3 from the queue.
  5. future.get() returns the result, waiting if the task hasn't finished. main never touches a Thread object.
  6. shutdown() stops accepting new tasks; the workers finish what's queued and then end. Without it, the pool's threads keep the JVM alive.
Behind the screen
  1. Inside, the pool keeps a task queue and up to 2 worker threads named pool-1-thread-1 and -2. Idle workers wait on the queue (like a consumer, Lesson 12.5).
  2. Submitted tasks are wrapped in FutureTask objects. Each worker takes one and runs its call().
  3. With both workers busy, task3 sits in the queue. This is how a pool limits how many threads exist, however many tasks arrive.
  4. Worker 1 finishes task1, stores the result in f1's FutureTask, and loops back to take task3. No thread was created or destroyed.
  5. All results are stored. get() on a completed Future returns at once.
  6. After shutdown(), the workers find the queue empty and closed, so they exit and become TERMINATED.
6 Real-world use

Pools power every Java server

Web servers, database connection handling, message consumers and schedulers are all built on executors.

Watch it with an example: a travel site searching three airlines

A flight search asks three airline APIs for prices at the same time, using a pool and Futures, and shows the cheapest. One airline is slow, so the search uses a timeout.

Fare search with Futures 5 steps
Animated example
  1. The user searches Pune → Delhi. The site must ask three airline APIs; each call takes a few hundred milliseconds.
  2. Each call is a Callable<Integer> submitted to a pool. Three Futures come back at once, all pending.
  3. IndiAir and SkyJet answer; their Futures complete. Because the calls overlapped, the wait was about as long as the slowest of them, not the sum.
  4. get(800, MILLISECONDS) on BlueWing's Future throws TimeoutException. The site cancels that task instead of making the user wait.
  5. The cheapest fare among the answers is shown. This is how comparison sites stay fast even when one partner is slow. (Illustrative times and prices.)

1. Web request handling

Servers like Tomcat keep a pool of request threads (often a couple of hundred). Each request borrows a worker and returns it when the response is sent.

HTTP request→request pool→response

2. Fan-out calls

A product page calls price, stock, reviews and delivery-estimate services at once and combines the answers with Futures or CompletableFuture.

4 services→CompletableFuture.allOf→one page

3. Scheduled jobs

Send EMI reminders every morning, clear expired carts every 10 minutes, refresh exchange rates every hour.

every 10 min→scheduleAtFixedRate→carts cleaned

4. Virtual threads for I/O

Since Java 21, services that mostly wait on databases and APIs can run one cheap virtual thread per request, handling far more concurrent requests with simple blocking code.

10,000 requests→virtual threads→few OS threads

Sizes and timings are illustrative. Frameworks such as Spring configure and manage these executors for you, but they are the same ExecutorService underneath.

7 Run the code

Three shop prices, fetched in parallel

import java.util.*;
import java.util.concurrent.*;

public class Main {
    static int fetchPrice(String shop) throws InterruptedException {
        Thread.sleep(100);                    // pretend network call
        return switch (shop) {
            case "Shopkart" -> 18999;
            case "BuyNow" -> 18499;
            default -> 19250;
        };
    }

    public static void main(String[] args) throws Exception {
        List<String> shops = List.of("Shopkart", "BuyNow", "MegaMart");
        ExecutorService pool = Executors.newFixedThreadPool(3);
        List<Future<Integer>> prices = new ArrayList<>();
        for (String s : shops) {
            prices.add(pool.submit(() -> fetchPrice(s)));
        }
        for (int i = 0; i < shops.size(); i++) {
            System.out.println(shops.get(i) + ": Rs " + prices.get(i).get());
        }
        pool.shutdown();
    }
}
Shopkart: Rs 18999 BuyNow: Rs 18499 MegaMart: Rs 19250
  • Executors.newFixedThreadPool(3)Three workers, so all three calls can run at the same time.
  • pool.submit(() -> fetchPrice(s))A Callable: it returns the price, and may throw InterruptedException (allowed in call()).
  • prices.get(i).get()Read results in shop order; each get waits only if that price isn't ready.
  • pool.shutdown()Lets the JVM exit once the workers are idle.

9 Quiz and revision

Check yourself

Quick revision

Lesson 12.6 in one screen

  • A thread pool = reusable workers + a task queue. Create it with Executors.newFixedThreadPool(n) and friends.
  • submit(Runnable | Callable) returns a Future; execute(Runnable) returns nothing.
  • Callable<V> returns a value and may throw checked exceptions.
  • get() waits; get(t, unit) may throw TimeoutException; failures come as ExecutionException.
  • invokeAll runs a list of Callables and returns Futures in the same order.
  • Always shutdown(); awaitTermination waits; submitting afterwards throws RejectedExecutionException.
  • CompletableFuture chains async steps; Java 21 virtual threads make one-thread-per-task cheap for I/O work.

Interview and viva questions

Why use a thread pool instead of creating threads?

Creating and destroying threads is costly, and unlimited threads exhaust memory and waste CPU on switching. A pool reuses a bounded number of threads, queues extra work, and centralises lifecycle management (shutdown, naming, error handling).

Difference between submit() and execute()?

execute(Runnable) comes from Executor and returns nothing; an exception in the task goes to the thread's uncaught-exception handler. submit() accepts Runnable or Callable and returns a Future; exceptions are captured and rethrown by get() as ExecutionException.

Difference between shutdown() and shutdownNow()?

shutdown() stops accepting tasks but lets queued and running tasks finish. shutdownNow() also interrupts running tasks and returns the list of tasks that never started. Neither waits; use awaitTermination for that.

How do you choose the pool size?

For CPU-bound work, about the number of cores (availableProcessors()). For I/O-bound work, more threads, roughly cores × (1 + wait time / compute time), or virtual threads. Always measure under realistic load.

What is the difference between Future and CompletableFuture?

A Future can only be polled or waited on with get(). A CompletableFuture can also be completed manually and lets you attach callbacks (thenApply, thenCombine, exceptionally) that run when the result arrives, so you can compose async steps without blocking threads.

Practice problems

Use pools, Callables and Futures instead of raw threads. Results are read from Futures in a fixed order, so every output is the same each run. The last three are business tasks.

P1Easy

Submit a Callable

Submit a Callable that returns 6 × 7 to a single-thread pool and print the result.

Input
(none)
Expected output
answer: 42

import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();

        System.out.println("answer: " + f.get());

P2Easy

Shutdown and awaitTermination

Submit 5 Runnables that each add their number to an AtomicInteger, shut down, wait, and print the sum.

Input
1..5
Expected output
sum = 15
Show solution and explanation 
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        AtomicInteger sum = new AtomicInteger();
        for (int i = 1; i <= 5; i++) {
            int n = i;
            pool.submit(() -> sum.addAndGet(n));
        }
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.SECONDS);
        System.out.println("sum = " + sum.get());
    }
}
sum = 15

How it works: shutdown() alone doesn't wait. awaitTermination blocks until the queued tasks are finished (or the timeout passes).

P4Medium

Exceptions come back through get()

A task divides by zero. Catch the ExecutionException from get() and print its cause.

Input
(none)
Expected output
task failed: java.lang.ArithmeticException: / by zero
Show solution and explanation 
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        Future<Integer> f = pool.submit(() -> 100 / 0);
        try {
            f.get();
        } catch (ExecutionException e) {
            System.out.println("task failed: " + e.getCause());
        }
        pool.shutdown();
    }
}
task failed: java.lang.ArithmeticException: / by zero

How it works: the exception happened on a worker thread. The pool catches it and stores it in the Future; get() rethrows it wrapped in ExecutionException. If you never call get(), the failure is silently lost.

P5Medium

Squares with invokeAll

Build Callables that square 2, 3, 4 and 5, run them with invokeAll, and print the results in order.

Input
2, 3, 4, 5
Expected output
4 9 16 25
Show solution and explanation 
import java.util.*;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        List<Callable<Integer>> jobs = new ArrayList<>();
        for (int n = 2; n <= 5; n++) {
            int x = n;
            jobs.add(() -> x * x);
        }
        ExecutorService pool = Executors.newFixedThreadPool(2);
        for (Future<Integer> f : pool.invokeAll(jobs)) {
            System.out.print(f.get() + " ");
        }
        System.out.println();
        pool.shutdown();
    }
}
4 9 16 25

How it works: invokeAll returns Futures in the same order as the tasks, however the workers scheduled them.

P6Medium

CompletableFuture pipeline

Compute a price of 400 asynchronously, add 18% GST with thenApply, and format it with another thenApply. Print with join().

Input
price 400
Expected output
Total with GST: Rs 472
Show solution and explanation 
import java.util.concurrent.CompletableFuture;

public class Main {
    public static void main(String[] args) {
        String bill = CompletableFuture.supplyAsync(() -> 400)
                .thenApply(p -> p * 118 / 100)
                .thenApply(t -> "Total with GST: Rs " + t)
                .join();
        System.out.println(bill);
    }
}
Total with GST: Rs 472

How it works: CompletableFuture lets you chain steps that run when the previous one completes, without blocking in between. By default it uses the shared ForkJoinPool. join() is like get() but throws an unchecked exception.

P7Business problem

Parallel GST for store branches

Three branches have daily sales of 25000, 18000 and 32000. Compute each branch's 18% GST in a Callable on a pool, then print each and the total GST.

Input
25000, 18000, 32000
Expected output
Pune: GST Rs 4500
Nagpur: GST Rs 3240
Nashik: GST Rs 5760
total GST: Rs 13500
Show solution and explanation 
import java.util.*;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        String[] branch = {"Pune", "Nagpur", "Nashik"};
        int[] sales = {25000, 18000, 32000};
        ExecutorService pool = Executors.newFixedThreadPool(3);
        List<Future<Integer>> gst = new ArrayList<>();
        for (int s : sales) gst.add(pool.submit(() -> s * 18 / 100));
        int total = 0;
        for (int i = 0; i < branch.length; i++) {
            int g = gst.get(i).get();
            total += g;
            System.out.println(branch[i] + ": GST Rs " + g);
        }
        System.out.println("total GST: Rs " + total);
        pool.shutdown();
    }
}
Pune: GST Rs 4500 Nagpur: GST Rs 3240 Nashik: GST Rs 5760 total GST: Rs 13500

How it works: results are summed on main from the Futures, so no shared variable or lock is needed. Collecting results through Futures is usually simpler than sharing state between tasks.

P8Business problem

Email batch with a bounded pool

Send 8 promotional emails using a pool of 2 workers. Each task returns true if the address contains "@". Count successes and failures.

Input
8 addresses, 2 invalid
Expected output
sent 6, failed 2
Show solution and explanation 
import java.util.*;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        String[] to = {"a@x.in", "b@x.in", "bad-address", "c@x.in", "d@x.in", "e@x.in", "oops", "f@x.in"};
        ExecutorService pool = Executors.newFixedThreadPool(2);
        List<Callable<Boolean>> sends = new ArrayList<>();
        for (String addr : to) sends.add(() -> addr.contains("@"));
        int ok = 0;
        for (Future<Boolean> f : pool.invokeAll(sends)) if (f.get()) ok++;
        pool.shutdown();
        System.out.println("sent " + ok + ", failed " + (to.length - ok));
    }
}
sent 6, failed 2

How it works: the pool size caps how many emails are sent at once, protecting the mail server, however many addresses there are. This is why pools are preferred over one thread per task.

P9Business problem

Seat confirmation with timeout fallback

A train-booking app asks two seat servers. The first answers at once (seat "B4-32"), the second hangs. Wait up to 150 ms for each; print the answer or "no reply", and cancel the hanging task.

Input
server 1 fast, server 2 hangs
Expected output
seat: B4-32
no reply, cancelled
Show solution and explanation 
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<String> s1 = pool.submit(() -> "B4-32");
        Future<String> s2 = pool.submit(() -> {
            Thread.sleep(10_000);
            return "S2-11";
        });
        for (Future<String> f : java.util.List.of(s1, s2)) {
            try {
                System.out.println("seat: " + f.get(150, TimeUnit.MILLISECONDS));
            } catch (TimeoutException e) {
                f.cancel(true);
                System.out.println("no reply, cancelled");
            }
        }
        pool.shutdown();
    }
}
seat: B4-32 no reply, cancelled

How it works: each server gets its own deadline. cancel(true) interrupts the stuck task so the worker is freed and shutdown() can finish.

Real-world scenario questions (asked in company interviews)

Executors are where most production concurrency lives, so interviewers probe how you size, protect and shut them down.

Backend · resource leakFresher

Thread count keeps climbing

Each time a report is requested, the code does Executors.newFixedThreadPool(4), submits the work and returns. After a day the service has 20,000 threads and crashes. What's wrong?

The interviewer is checking: pool lifecycle.

Show a strong answer
  • A new pool per request is never shut down, so its 4 threads live forever.
  • Create one shared pool at startup and reuse it; shut it down when the application stops.
  • If a short-lived pool is really needed, close it in finally (or try-with-resources in Java 21).

Avoid: calling System.gc(); live threads are never garbage collected.

Debugging · silent failureJunior

Refunds that silently never happen

Refund tasks are submitted with pool.submit(refundTask) and the Future is ignored. Some refunds never complete and nothing appears in the logs. Why, and how do you fix it?

The interviewer is checking: exception handling with submit().

Show a strong answer
  • submit captures exceptions inside the Future; if nobody calls get(), the failure is swallowed.
  • Catch and log inside the task (with refund id), or keep the Futures and check them, or use CompletableFuture with exceptionally/whenComplete.
  • Add retries and an alert for failed refunds.

Avoid: assuming “no error in the logs” means success.

Performance · sizingMid

Sizing pools for two kinds of work

An 8-core server does image compression (pure CPU) and calls a partner API (mostly waiting, ~200 ms). Both use one pool of 8 threads. API calls queue up and pages are slow. What would you change?

The interviewer is checking: CPU-bound vs I/O-bound sizing and isolation.

Show a strong answer
  • Separate the workloads into two pools, so slow API calls can't starve compression (bulkheading).
  • CPU pool ≈ 8 threads; I/O pool much larger (or virtual threads), since those threads mostly wait.
  • Add timeouts on API calls and bounded queues with a rejection policy.

Avoid: one giant pool of 500 threads for everything; CPU work would thrash.

Release · shutdownMid

Orders lost during deployment

During a deployment, the app is stopped while order-confirmation tasks are still in the executor's queue. Some customers never get confirmations. Design a graceful shutdown.

The interviewer is checking: shutdown(), awaitTermination() and durability.

Show a strong answer
  • On stop: stop taking new requests, call shutdown(), then awaitTermination(30, SECONDS); only then call shutdownNow() and log the tasks it returns.
  • For anything that must not be lost, store it durably first (database or message broker) and process from there, so a restart can resume.

Avoid: relying on an in-memory queue for work that must survive a restart.
