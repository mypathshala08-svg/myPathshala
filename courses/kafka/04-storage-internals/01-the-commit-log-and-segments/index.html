1 The story

Why is my data in “…3413.log”?

Before you start: 1.3 Architecture and 2.3 Batches.

🤔 Kafka stored 10,000 orders in a file named 00000000000000003413.log. Why that strange name?

A partition is not one big file. It is a chain of segments, each named after the first offset inside it. We forced Kafka to roll segments, listed every file it created, and found two tiny surprises: a minimum segment size, and index files that shrink when a segment is closed.

Kabir opens a broker’s data folder during an incident and sees files named 00000000000000003413.log, .index, .snapshot. Riya asks what each of them is.

Riya

Sir, in Lesson 1.3 each partition was a folder. Is all the data in one file?

No. A partition is a chain of segments. Kafka writes only to the newest one, the active segment. When it gets big or old enough, Kafka closes it and opens another.

Because deleting old data then means deleting a whole old file, not rewriting a giant one. Let’s make segments small so we can watch them roll.

2 Definition

The commit log and segments

Formal definition (write this in exams)

Each partition replica is stored as a log: an ordered sequence of segments in the partition directory. A segment consists of a .log file holding record batches and associated .index and .timeindex files, named by the segment’s base offset (20 digits). Only the last, active segment is appended to; Kafka rolls a new active segment when segment.bytes, segment.ms or the index size limit is reached. Closed segments are immutable and are the unit of retention, compaction and tiered-storage upload.

In simple words

A partition is a series of files. Kafka writes only to the newest file; when it is full or old, Kafka starts a new one named after the first record number it will hold. Old files are never changed, only deleted or cleaned as a whole.

Why, how, where

Why

One endless file could never be cleaned up cheaply: deleting old data would mean rewriting it. Segments let Kafka delete or compact whole files.

the problem it solves

How

Each partition appends to its active segment; when it reaches segment.bytes or segment.ms, Kafka closes it and starts a new one named after the next offset.

the mechanism

Where

Every Kafka topic; segment size affects retention granularity, file handles, recovery time and tiered storage uploads.

in real systems

When not

Very small segments create thousands of files and open handles; very large ones delay retention and compaction.

Dissect a partition folder

Segments at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A register with numbered notebooks

  • The order clerk writes in notebook #1 until it is full, then starts notebook #3413, named after the first order number in it. Old notebooks are closed and can be thrown away whole.

Intermediate The files in a partition folder

  • .log: the record batches (Lesson 2.3’s format). .index: offset → byte position. .timeindex: timestamp → offset (Lesson 4.2).
  • .snapshot: producer state (producer ids and sequences for idempotence, Lesson 2.5) at that segment boundary, so restarts do not need to scan everything.
  • leader-epoch-checkpoint and partition.metadata (topic id) for replication safety.

Advanced Roll rules and limits

  • A new segment is rolled when the active one would exceed segment.bytes (default 1 GiB; minimum 1 MiB in Kafka 4.x), or is older than segment.ms (7 days), or its index is full.
  • Indexes of the active segment are pre-allocated (segment.index.bytes, 10 MiB) and trimmed to their real size when the segment closes.
  • Each segment is a few open file handles; brokers with thousands of partitions need high ulimit -n and vm.max_map_count.

Myth vs reality: things many websites still say

  • Myth: A partition is one big file.
    Reality (Kafka 4.4): It is a chain of segment files.
    Proof: Step 2: three segments.
  • Myth: Segment names are random ids.
    Reality (Kafka 4.4): They are the base offset of the first record.
    Proof: Step 3: …3413.log starts at 3413.
  • Myth: You can set segments as small as you like.
    Reality (Kafka 4.4): Kafka 4.x enforces a 1 MiB minimum for segment.bytes.
    Proof: Step 1.

Exam tip: “How does Kafka store a partition on disk?” As a directory of segments; each has .log (record batches), .index (offset→position), .timeindex (time→offset), named by base offset; only the active segment is appended; roll on segment.bytes/segment.ms; retention and compaction work per closed segment.

Kafka 4.x rejects segment.bytes below 1 MiB (our first attempt failed with “Value must be at least 1048576”). Tiny segments were a common trick in old tutorials; with real traffic they mean huge file counts and slow restarts.

7 Run the code

Run the code: rolling segments

The roll rule with our lab’s batch size. Press Run, then try the challenges.

# A partition as a chain of segments
SEGMENT_BYTES = 1_048_576
segments = [[0, 0]]                      # [base_offset, size_bytes]
def append(offset, size):
    if segments[-1][1] + size > SEGMENT_BYTES:   # roll: next batch would not fit
        segments.append([offset, 0])
    segments[-1][1] += size

offset = 0
while offset < 10_000:
    append(offset, 3011)                 # one batch of 10 records, 3,011 bytes
    offset += 10

for base, size in segments:
    print(f"{base:020d}.log  {size:>9,} bytes")
print("active segment:", f"{segments[-1][0]:020d}.log")
00000000000000000000.log 1,047,828 bytes 00000000000000003480.log 1,047,828 bytes 00000000000000006960.log 915,344 bytes active segment: 00000000000000006960.log

9 Quiz and revision

Check yourself

Quick revision

Lesson 4.1 in one screen

  • Partition = chain of segments; only the active one is written.
  • Files: .log, .index, .timeindex, .snapshot, leader-epoch-checkpoint, partition.metadata.
  • Name = 20-digit base offset (lab: 0, 3413, 6830).
  • Roll: segment.bytes (1 GiB, min 1 MiB), segment.ms (7 days), index full.
  • Active indexes pre-allocated 10 MiB, trimmed on close.
  • Retention/compaction/tiering work on closed segments.

Interview and viva questions

Does Kafka fsync every write?

No. It writes to the OS page cache and relies on replication for durability; flush.messages/flush.ms exist but are rarely changed.

Can I read segment files directly?

Yes, with kafka-dump-log.sh, for debugging. Never edit them while the broker runs.

What is in partition.metadata?

The topic id, so a re-created topic with the same name cannot be confused with old data.

Do followers have the same segment names?

Usually the same offsets, but followers roll on their own; segment boundaries can differ between replicas.
