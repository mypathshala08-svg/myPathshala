Schema Registry and Avro

How do you stop bad data at the door? We run a Schema Registry, produce Avro, dissect the bytes, and watch a wrong type get rejected. All outputs are real.

1 The story

A contract for your messages

Before you start: 7.1 Connect.

🤔 Kafka stores bytes and never checks them. So what stops one team from sending "qty": "two" and breaking ten consumers?

A schema registry plus a serializer. The producer looks up (or registers) the schema, writes a 5-byte header (magic byte + schema id) and compact Avro bytes. Consumers fetch the schema by id and decode. In our lab one order took 20 bytes instead of 50 as JSON, and a bad record was rejected inside the producer, before it ever reached Kafka.

2 Definition

Schema Registry and Avro

Formal definition (write this in exams)

A schema registry is a service that stores versioned schemas under subjects, assigns each distinct schema a global id, and enforces compatibility rules. Schema-aware serializers validate and encode records (e.g. in Avro, Protobuf or JSON Schema) and prefix them with a magic byte and the schema id; deserializers resolve the id to the writer schema to decode.

In simple words

The registry is a shared rulebook for message shapes. Producers must follow the rules, and each message carries a tiny number saying which rule it follows, so consumers can read it.

Why, how, where

Why

Producers and consumers are deployed by different teams at different times. Without a shared contract, a field rename or type change silently breaks readers, and JSON repeats every field name in every message.

the problem it solves

How

The serializer registers/looks up the schema under a subject (default <topic>-value), gets a global id, and prefixes each message with magic byte 0 + 4-byte id. Deserializers cache id → schema. The registry stores schemas in the compacted _schemas topic and enforces compatibility rules on new versions.

the mechanism

Where

Any multi-team Kafka platform; Connect (AvroConverter/ProtobufConverter); CDC pipelines; data lakes that need typed columns. Implementations: Confluent Schema Registry, Apicurio, Karapace, AWS Glue Schema Registry.

in real systems

When not

Every client needs registry access (and its own auth). Data is no longer human-readable with plain console tools. Registry downtime blocks producers that see a new schema (cached ones keep working).

Dissect the bytes

Schemas at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The form with numbered boxes

  • Instead of writing “Item: idli, Quantity: 2” every time, everyone uses form #1, where box 1 is item and box 2 is quantity. You only write the form number and the values. The registry is the cupboard holding all form designs.

Intermediate The pieces

  • Schema: field names and types (Avro JSON, .proto, or JSON Schema). Subject: a named history of schemas, default <topic>-key / <topic>-value (TopicNameStrategy). Version: 1, 2, 3… per subject. Id: global and unique per distinct schema.
  • Serializer settings: auto.register.schemas (true by default; turn off in production and register via CI), use.latest.version.
  • REST: GET /subjects, /subjects/{s}/versions/latest, /schemas/ids/{id}, POST /subjects/{s}/versions, /config.

Advanced Under the hood

  • Wire format: byte 0 = 0, bytes 1–4 = big-endian schema id, then the payload (Protobuf adds message-index bytes).
  • Avro binary has no field names: ints/longs are zig-zag varints (2 → 04), strings are length + UTF-8 (08 69 64 6c 69 = 4, “idli”), doubles are 8 little-endian bytes.
  • RecordNameStrategy / TopicRecordNameStrategy allow several event types in one topic. The registry is a single-writer service backed by the _schemas topic; run several instances for availability.

Myth vs reality: things many websites still say

  • Myth: Kafka validates messages.
    Reality (Kafka 4.4): Kafka stores bytes; serializers validate.
    Proof: Step 6.
  • Myth: Schemas make messages bigger.
    Reality (Kafka 4.4): Avro: 20 vs 50 bytes.
    Proof: Step 3.
  • Myth: The whole schema travels with each message.
    Reality (Kafka 4.4): Only a 4-byte id.
    Proof: Step 3.

Exam tip: “What is Schema Registry?” Central store of versioned schemas per subject; serializers register/look up, write magic byte + schema id + Avro/Protobuf/JSON payload; deserializers fetch by id; compatibility checks on new versions; stored in _schemas.

    The registry keeps everything in the compacted _schemas topic; default compatibility is BACKWARD (Lesson 8.2).

  2. Step 2 · Produce with Avro

    schema = {"type": "record", "name": "Order", "fields": [id int, item string, qty int, price double]}
ser = AvroSerializer(SchemaRegistryClient({"url": SR}), json.dumps(schema))
p.produce("orders-81", value=ser(order, SerializationContext("orders-81", MessageField.VALUE)))
    == 2) producing with AvroSerializer auto-registered the schema GET /subjects -> ['orders-81-value'] latest version: 1 schema id: 2 type: AVRO
    The first produce registered the schema under subject orders-81-value: version 1, global id 1.

  3. Step 3 · Look at the bytes

    b = raw_value
print(b.hex(" "), b[0], int.from_bytes(b[1:5], "big"))
    == 3) the bytes on the wire (first record) hex: 00 00 00 00 02 02 08 69 64 6c 69 04 00 00 00 00 00 00 44 40 byte 0 magic = 0, bytes 1-4 schema id = 2, then 15 bytes of Avro data total 20 bytes vs 50 bytes as JSON: {"id": 1, "item": "idli", "qty": 2, "price": 40.0}
    Magic 0, schema id 1, then 15 bytes of Avro: 20 bytes in total, 60% smaller than the same order as JSON.

  4. Step 4 · Decode

    de = AvroDeserializer(SchemaRegistryClient({"url": SR}))
de(raw, SerializationContext("orders-81", MessageField.VALUE))
    == 4) decoding with AvroDeserializer (fetches schema id from the registry) {'id': 1, 'item': 'idli', 'qty': 2, 'price': 40.0} {'id': 2, 'item': 'dosa', 'qty': 1, 'price': 90.0} {'id': 3, 'item': 'thali', 'qty': 1, 'price': 150.0}
    The deserializer read id 1, fetched (and cached) the schema, and rebuilt the dicts.

  5. Step 5 · Without the registry

    print(raw_value[:24])
    == 5) a plain string consumer sees binary b'\x00\x00\x00\x00\x02\x04\x08dosa\x02\x00\x00\x00\x00\x00\x80V@'
    A plain consumer sees binary: readable text only for strings. Use schema-aware tools (kafka-avro-console-consumer, UI tools).

  6. Step 6 · Bad data stopped early

    ser({"id": 4, "item": "vada", "qty": "two", "price": 60.0}, ctx)
    == 6) wrong type is stopped in the producer, before Kafka TypeError: an integer is required on field qty
    The serializer refused the record in the producer process: Kafka and every consumer were protected.

Run the code: encode by hand

Rebuild the lab’s 20 bytes. Press Run, then try the challenges.

# Build the Confluent wire format by hand (Avro-style encoding)
import struct

def zigzag(n):                 # Avro int/long encoding
    n = (n << 1) ^ (n >> 63)
    out = b""
    while True:
        b = n & 0x7F; n >>= 7
        out += bytes([b | (0x80 if n else 0)])
        if not n: return out

def avro_string(s):
    data = s.encode()
    return zigzag(len(data)) + data

order = {"id": 1, "item": "idli", "qty": 2, "price": 40.0}
body = zigzag(order["id"]) + avro_string(order["item"]) + zigzag(order["qty"]) + struct.pack("<d", order["price"])
msg = b"\x00" + (1).to_bytes(4, "big") + body
print(msg.hex(" "), len(msg), "bytes")
00 00 00 00 01 02 08 69 64 6c 69 04 00 00 00 00 00 00 44 40 20 bytes
  • n = (n << 1) ^ (n >> 63)Zig-zag: small numbers stay small, also negatives.
  • msg = b"\x00" + (1).to_bytes(4, "big") + bodyMagic 0 + schema id 1.

Interview and viva questions

Is Schema Registry part of Apache Kafka?

No. It is a separate service (Confluent, Apicurio, Karapace, AWS Glue…).

What if the registry is down?

Clients with cached schemas keep working; new schemas cannot be registered or fetched.

Can the key also use Avro?

Yes, subject -key; many teams keep keys as simple strings.

How do I read Avro from the CLI?

kafka-avro-console-consumer (Confluent) or tools like kcat with -s avro and -r registry.

“Why use Schema Registry?”

The interviewer is checking: answer?

Show a strong answer

To share and enforce message schemas between producers and consumers: serializers validate, messages carry a schema id instead of the full schema, and the registry checks that new versions stay compatible.
