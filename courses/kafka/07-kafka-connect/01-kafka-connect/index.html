Kafka Connect: source and sink connectors

How do you move data into and out of Kafka without code? We run a Connect worker, stream a file with SMTs, and send a broken record to a DLQ. All outputs are real.

1 The story

Integration without writing code

Before you start: 6.2 DLQs.

🤔 Your team wrote 400 lines of Python to copy a file into Kafka, and another 400 to copy Kafka into a database. Kafka Connect does both with a JSON config and zero code.

Kafka Connect is a separate runtime (workers) that runs ready-made connectors: source connectors pull data into Kafka, sink connectors push it out. Converters turn bytes into data, SMTs reshape records on the way, and a dead letter queue catches bad ones. In our lab one REST call streamed a kitchen file into Kafka, appended lines arrived in seconds, and a broken JSON record went to the DLQ with headers telling exactly where it came from.

  • Workers, connectors, tasks: who does what.
  • Converters vs SMTs, and why schemas.enable changes your JSON.
  • Offsets, restarts and error handling (DLQ) in Connect.

2 Definition

Kafka Connect

Formal definition (write this in exams)

Kafka Connect is a framework and runtime for scalable, fault-tolerant data integration between Kafka and other systems. Workers run connectors (source or sink plugins) that are divided into tasks; records pass through converters (serialization) and optional single message transforms. In distributed mode, configuration, source offsets and status are stored in compacted Kafka topics and the cluster is managed via a REST API.

In simple words

Connect is a ready-made engine that copies data into Kafka (source) or out of Kafka (sink). You choose a connector, send a small JSON config, and it handles restarts, checkpoints and scaling for you.

Why, how, where

Why

Every system-to-Kafka integration needs the same hard parts: retries, offsets, scaling, restarts, schemas, error handling. Connect solves them once; you only configure.

the problem it solves

How

Workers form a group (like consumers) and share connectors’ tasks. A source task reads from the outside system and returns records; the worker converts and produces them. A sink task receives records the worker consumed and writes them out. Configs, offsets and status live in compacted Kafka topics; you manage everything through a REST API on port 8083.

the mechanism

Where

Databases (JDBC, Debezium CDC), S3/GCS/HDFS sinks, Elasticsearch/OpenSearch, Snowflake/BigQuery, MirrorMaker 2 (itself a set of connectors). Hundreds of connectors on Confluent Hub and open source.

in real systems

When not

Connectors are plugins (JARs) you must install on every worker (plugin.path). Complex per-record logic belongs in Kafka Streams/Flink, not in a chain of SMTs.

Dissect the envelope

Kafka Connect at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Plug adapters

  • Kafka is a power strip. Connectors are adapters: one for files, one for Postgres, one for S3. You don’t rewire the house; you plug in the right adapter and set a few switches.

Intermediate The parts

  • Worker: the JVM process (connect-distributed.sh). Several workers with the same group.id form a cluster and share tasks.
  • Connector: a config + plugin; it splits the job into up to tasks.max tasks, which do the copying.
  • Converter (key.converter, value.converter): bytes ↔ Connect data. JsonConverter with schemas.enable=true wraps every value in {"schema":…,"payload":…}; Avro/Protobuf converters use Schema Registry (Module 8).
  • SMT (single message transform): small per-record changes, e.g. HoistField, InsertField, MaskField, ReplaceField, TimestampConverter, RegexRouter, Filter + predicates.

Advanced Operations

  • Distributed mode stores state in connect-configs (1 partition), connect-offsets (25) and connect-status (5), all compacted. Standalone mode keeps offsets in a local file: dev only.
  • REST: PUT /connectors/{name}/config, GET …/status, POST …/restart?includeTasks=true, PUT …/pause, GET/PATCH/DELETE …/offsets (KIP-875, stop the connector first to change offsets).
  • Errors: errors.tolerance=none (default) fails the task; all skips bad records. Sinks can route them to errors.deadletterqueue.topic.name with __connect.errors.* headers. errors.retry.timeout retries transient failures.
  • Since Kafka 3.x/4.x workers use incremental cooperative rebalancing, so adding a worker moves only some tasks.

Myth vs reality: things many websites still say

  • Myth: Connect runs inside the broker.
    Reality (Kafka 4.4): It is a separate process/cluster.
    Proof: Container kc.
  • Myth: A restart re-reads everything.
    Reality (Kafka 4.4): Source offsets are stored.
    Proof: Step 5: position 53.
  • Myth: One bad record must stop the pipeline.
    Reality (Kafka 4.4): errors.tolerance + DLQ.
    Proof: Step 6.

Exam tip: “What is Kafka Connect?” Framework to move data in/out of Kafka with source/sink connectors; workers, connectors, tasks; converters, SMTs; distributed mode with config/offset/status topics; REST API; error tolerance and DLQ.

  3. Step 3 · File source, default converter

    curl -X PUT localhost:8083/connectors/file-raw/config -H "Content-Type: application/json" -d '{
  "connector.class": "org.apache.kafka.connect.file.FileStreamSourceConnector",
  "file": "/data/orders.txt", "topic": "orders-71-raw", "tasks.max": "1"}'
    == 3) file source, JsonConverter with schemas.enable=true (default) {"schema":{"type":"string","optional":false},"payload":"idli,2,40"} {"schema":{"type":"string","optional":false},"payload":"dosa,1,90"}
    Each line became a record wrapped in the schema/payload envelope.

  4. Step 4 · SMTs and plain JSON

    "value.converter.schemas.enable": "false",
"transforms": "wrap,tag",
"transforms.wrap.type": "org.apache.kafka.connect.transforms.HoistField$Value",
"transforms.wrap.field": "line",
"transforms.tag.type": "org.apache.kafka.connect.transforms.InsertField$Value",
"transforms.tag.static.field": "source",
"transforms.tag.static.value": "kitchen-file"
    == 4) same file with SMTs (HoistField + InsertField) and schemas.enable=false {"line":"idli,2,40","source":"kitchen-file"} {"line":"dosa,1,90","source":"kitchen-file"} {"line":"thali,1,150","source":"kitchen-file"}
    HoistField turned the string into a struct {line: …}; InsertField added source. Order matters: InsertField needs a struct, so wrap comes first.

  5. Step 5 · Live streaming and offsets

    curl -s localhost:8083/connectors/file-src/status
printf "vada,3,60\nlassi,2,90\n" >> orders.txt
curl -s localhost:8083/connectors/file-src/offsets
    == 5) status, then append 2 lines: streamed within seconds; source offset = file position connector RUNNING on kc:8083 | tasks [(0, 'RUNNING')] records in orders-71 now: 5 {"offsets":[{"partition":{"filename":"/data/orders.txt"},"offset":{"position":53}}]}
    Two appended lines arrived within seconds (3 → 5 records). The stored offset is the byte position 53 in the file: after a restart the task continues from there.

  6. Step 6 · Sink with a DLQ

    "errors.tolerance": "all",
"errors.deadletterqueue.topic.name": "dlq-71",
"errors.deadletterqueue.context.headers.enable": "true"
    == 6) sink with errors.tolerance=all and a dead letter queue out.txt: {item=idli, qty=2} {item=dosa, qty=1} dlq-71: __connect.errors.exception.class.name:org.apache.kafka.connect.errors.DataException __connect.errors.exception.message:Converting byte[] to Kafka Connect data failed due to serialization error: {item: broken sink task state: RUNNING __connect.errors.topic:bad-71 __connect.errors.partition:0 __connect.errors.offset:1 __connect.errors.connector.name:file-sink __connect.errors.stage:VALUE_CONVERTER
    Two good records were written; the broken one went to dlq-71 with headers: exception class and message, original topic bad-71, partition 0, offset 1, connector name and the failing stage VALUE_CONVERTER. The task kept RUNNING.

7 Run the code

Run the code: a mini pipeline

Connect’s steps in plain Python. Press Run, then try the challenges.

# A tiny Connect pipeline: source -> SMTs -> converter
import json
lines = ["idli,2,40", "dosa,1,90"]

def hoist(v):  return {"line": v}                        # HoistField$Value
def insert(v): return {**v, "source": "kitchen-file"}    # InsertField$Value

def convert(v, schemas=False):
    if schemas:
        return json.dumps({"schema": {"type": "struct"}, "payload": v})
    return json.dumps(v)

offset = 0
for ln in lines:
    print(convert(insert(hoist(ln))))
    offset += len(ln) + 1
print("stored source offset:", {"position": offset})
{"line": "idli,2,40", "source": "kitchen-file"} {"line": "dosa,1,90", "source": "kitchen-file"} stored source offset: {'position': 20}

  • offset += len(ln) + 1File source offset = byte position.

Interview and viva questions

Where do I get connectors?

Confluent Hub, Debezium, Apache Camel Kafka connectors, vendors, or write your own with the Connect API.

Does Connect need its own cluster?

It runs as separate worker processes; often a dedicated Connect cluster per team or use case.

Can SMTs filter records?

Yes: the Filter SMT with predicates (e.g. TopicNameMatches, HasHeaderKey).

Do source connectors support exactly-once?

Yes since Kafka 3.3 (KIP-618) when exactly.once.source.support=enabled and the connector supports it.
