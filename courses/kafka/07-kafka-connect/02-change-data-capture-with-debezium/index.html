Change data capture with Debezium

How do database changes become Kafka events without touching the app? We run Debezium on Postgres, read c/u/d events, flatten them, and stop Connect to prove nothing is lost. All outputs are real.

1 The story

Every database change becomes an event

Before you start: 7.1 Kafka Connect.

🤔 Can you turn every INSERT, UPDATE and DELETE in a database into a Kafka event, without touching the application or polling the table?

Yes: change data capture (CDC). Debezium reads the database’s own transaction log (Postgres WAL) through a replication slot, and emits one event per row change with before and after images. In our lab: 2 snapshot rows, then an insert, an update and a delete appeared as events with op codes c/u/d, the delete was followed by a tombstone, and a row inserted while Connect was down still arrived after restart.

  • Why log-based CDC beats polling and dual writes.
  • The Debezium event envelope: before, after, source, op.
  • Snapshots, replication slots, tombstones, flattening, and the outbox pattern.

TiffinGo’s orders live in Postgres. Delivery, billing and analytics teams all want to react when an order changes, without asking the orders team to change their code.

Kabir

Sir, the orders service writes to Postgres. Ten other teams want to know when an order changes. Should every team poll the orders table?

Arjun Sir

No. Polling misses deletes and hammers the DB. Postgres already writes every change to its WAL. Debezium reads that log and turns each change into a Kafka event.

Riya

And if Connect is down for an hour?

Arjun Sir

The replication slot keeps the WAL until Debezium confirms it. Nothing is lost; we’ll prove it by stopping the worker.

2 Definition

Change data capture with Debezium

Formal definition (write this in exams)

Change data capture (CDC) is the practice of capturing row-level changes from a database and publishing them as events. Debezium is an open-source set of Kafka Connect source connectors that perform log-based CDC: they take an initial consistent snapshot and then read the database transaction log (e.g. the Postgres WAL via a logical replication slot), emitting one record per change with before/after images, source metadata and an operation type, keyed by primary key.

In simple words

Debezium watches the database’s own diary of changes and turns each insert, update and delete into a Kafka message, in order, without the app doing anything.

Why, how, where

Why

Polling (SELECT … WHERE updated_at > x) misses deletes and intermediate updates and loads the DB. Writing to DB and Kafka in the app (dual write) can leave them inconsistent. The transaction log already has every committed change, in order.

the problem it solves

How

Debezium takes an initial consistent snapshot (op r), then streams from the log via a logical replication slot (pgoutput). Each change becomes a record keyed by the primary key, with before/after, source metadata (LSN, txId, table) and op c/u/d; deletes add a tombstone. Its position (LSN) is stored as the Connect source offset.

the mechanism

Where

Microservice data sync, cache invalidation, search indexing, feeding data lakes/warehouses in near real time, audit trails, and migrations off legacy DBs. Supported: Postgres, MySQL/MariaDB, SQL Server, Oracle, MongoDB, Db2 and more.

in real systems

When not

Needs DB settings (Postgres wal_level=logical, replication privileges). An inactive slot makes Postgres keep WAL forever: monitor slot lag. Full before images need REPLICA IDENTITY FULL.

Dissect a change event

CDC at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The bank passbook

  • Instead of checking your balance every minute to guess what happened, read the passbook: every deposit and withdrawal is printed in order. Debezium reads the database’s passbook (its log) and announces each line.

Intermediate The event

  • Topic name: <topic.prefix>.<schema>.<table> (ours: tiffingo.public.orders); key = primary key, so all changes of one row stay ordered in one partition.
  • op: r read (snapshot), c create, u update, d delete, t truncate. before/after row images; source has connector version, db, table, LSN, txId, timestamps.
  • After a delete Debezium sends a tombstone (same key, null value) so compacted topics drop the row entirely (Lesson 4.3).

Advanced Production

  • snapshot.mode (initial, no_data, when_needed, …) and incremental snapshots via a signal table let you re-snapshot big tables without stopping streaming.
  • ExtractNewRecordState SMT flattens the envelope to just the row (+ __op, __deleted) for sinks like JDBC/Elasticsearch.
  • Outbox pattern: the service writes business data and an event row to an outbox table in the same transaction; Debezium’s outbox router publishes those events. This avoids dual writes and exposes intentional events, not raw table rows.
  • Watch slot lag (pg_replication_slots.confirmed_flush_lsn vs current WAL), set heartbeat.interval.ms for quiet tables, and drop slots of deleted connectors. Schema changes flow as new event schemas: use Schema Registry (Module 8).

Myth vs reality: things many websites still say

  • Myth: CDC means polling the table.
    Reality (Kafka 4.4): Log-based CDC reads the WAL.
    Proof: Step 6 slot.
  • Myth: Deletes cannot be captured.
    Reality (Kafka 4.4): op d + tombstone.
    Proof: Step 4.
  • Myth: Downtime loses changes.
    Reality (Kafka 4.4): Slot + stored LSN resume.
    Proof: Step 8.

Exam tip: “How does Debezium CDC work?” Snapshot then stream from DB log (Postgres WAL via logical slot, pgoutput); events keyed by PK with before/after/source/op (r/c/u/d), tombstones; LSN stored as Connect offset; ExtractNewRecordState for sinks; outbox pattern; watch slot lag.

A stopped or deleted Debezium connector leaves its Postgres replication slot behind, and Postgres will keep WAL files until the disk fills and the database stops. Monitor slot lag and drop unused slots (pg_drop_replication_slot).

4 Step by step

From SQL to events

All outputs are real: Postgres 16, Debezium 3.7.0.Final on a Kafka 4.4.0 Connect worker, 3-broker lab.

  1. Step 1 · Prepare Postgres

    -- server started with: -c wal_level=logical
create table orders(id int primary key, item text, qty int, status text);
alter table orders replica identity full;
insert into orders values (1,'idli',2,'PLACED'),(2,'dosa',1,'PLACED');
    == 1) Postgres table (wal_level=logical) with 2 existing rows logical 1|idli|2|PLACED 2|dosa|1|PLACED
    wal_level=logical lets the WAL be decoded into row changes. REPLICA IDENTITY FULL puts all old columns into update/delete records.

  2. Step 2 · Register Debezium

    {"connector.class": "io.debezium.connector.postgresql.PostgresConnector",
 "database.hostname": "pg", "database.dbname": "tiffingo",
 "database.user": "postgres", "database.password": "…",
 "topic.prefix": "tiffingo", "plugin.name": "pgoutput",
 "slot.name": "tiffingo_slot", "table.include.list": "public.orders"}
    == 2) register the Debezium Postgres connector created pg-cdc -> io.debezium.connector.postgresql.PostgresConnector state RUNNING ['RUNNING']
    Debezium 3.7.0 on a Kafka 4.4 Connect worker. It creates the slot and a publication, snapshots the table, then streams.

  3. Step 3 · Change data

    insert into orders values (3,'thali',1,'PLACED');
update orders set status='COOKED' where id=1;
delete from orders where id=2;
    == 3) INSERT, UPDATE, DELETE in Postgres
    Plain SQL: the application does not know Kafka exists.

  4. Step 4 · The events

    kafka-console-consumer.sh --bootstrap-server k1:9092 --topic tiffingo.public.orders --from-beginning --formatter-property print.key=true
    == 4) the change events in topic tiffingo.public.orders (key | op before -> after) {"id":1} | op r None -> {'id': 1, 'item': 'idli', 'status': 'PLACED'} lsn 26737512 snapshot first {"id":2} | op r None -> {'id': 2, 'item': 'dosa', 'status': 'PLACED'} lsn 26737512 snapshot last {"id":3} | op c None -> {'id': 3, 'item': 'thali', 'status': 'PLACED'} lsn 26737552 snapshot false {"id":1} | op u {'id': 1, 'item': 'idli', 'status': 'PLACED'} -> {'id': 1, 'item': 'idli', 'status': 'COOKED'} lsn 26737800 snapshot false {"id":2} | op d {'id': 2, 'item': 'dosa', 'status': 'PLACED'} -> None lsn 26737968 snapshot false {"id":2} | TOMBSTONE (null value, for compaction)
    Two snapshot reads (r, snapshot first/last), then c, u and d, each with the LSN. The delete is followed by a tombstone for key {"id":2}.

  5. Step 5 · One full event

    … | grep '"op":"u"' | python3 -m json.tool
    == 5) one full event (the UPDATE), trimmed { "before": { "id": 1, "item": "idli", "qty": 2, "status": "PLACED" }, "after": { "id": 1, "item": "idli", "qty": 2, "status": "COOKED" }, "source": { "connector": "postgresql", "version": "3.7.0.Final", "db": "tiffingo", "table": "orders", "lsn": 26737800, "txId": 744, "ts_ms": 1793942559654 }, "transaction": null, "op": "u", "ts_ms": 1793942559657, "ts_us": 1793942559657782, "ts_ns": 1793942559657782508 }
    before and after differ only in status. source.txId 744 ties it to the Postgres transaction.

  6. Step 6 · The replication slot

    select slot_name, plugin, active, confirmed_flush_lsn from pg_replication_slots;
    == 6) Postgres side: the replication slot Debezium reads from tiffingo_slot|pgoutput|t|0/197FD30
    The slot is active and its confirmed_flush_lsn shows how far Debezium has acknowledged. Postgres keeps WAL from that point.

  7. Step 7 · Flatten for sinks

    "transforms": "unwrap",
"transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
"transforms.unwrap.add.fields": "op",
"transforms.unwrap.delete.tombstone.handling.mode": "rewrite"
    == 7) flatten with ExtractNewRecordState SMT (what most sinks want) {"id":3,"item":"thali","qty":1,"status":"PLACED","__deleted":"false","__op":"r"} {"id":1,"item":"idli","qty":2,"status":"COOKED","__deleted":"false","__op":"r"} {"id":3,"item":"thali","qty":3,"status":"PLACED","__deleted":"false","__op":"u"}
    A second connector (its own slot) snapshotted the current rows and then the qty update: just the row plus __op and __deleted.

  8. Step 8 · Survive downtime

    docker stop kc
psql -c "insert into orders values (4,'vada',3,'PLACED')"
docker start kc
    == 8) stop worker, change data, start again: no event lost (resumes from stored LSN) events now: 8 (6 from step 4 incl. tombstone, the qty update from step 7, and the new insert) c {'id': 4, 'item': 'vada', 'qty': 3, 'status': 'PLACED'} (inserted while the worker was stopped)
    The insert made while the worker was stopped arrived after restart: Debezium resumed from the LSN stored in connect-offsets, and the slot had kept the WAL.

7 Run the code

Run the code: change events

The CDC envelope in plain Python. Press Run, then try the challenges.

# Turn row changes into Debezium-style events
table = {1: {"item": "idli", "status": "PLACED"}}
events = []

def change(op, id, row=None):
    before = table.get(id)
    if op == "d":
        del table[id]
    else:
        table[id] = row
    events.append({"key": {"id": id}, "op": op, "before": before, "after": table.get(id)})
    if op == "d":
        events.append({"key": {"id": id}, "value": None})   # tombstone

change("c", 2, {"item": "dosa", "status": "PLACED"})
change("u", 1, {"item": "idli", "status": "COOKED"})
change("d", 2)
for e in events: print(e)
{'key': {'id': 2}, 'op': 'c', 'before': None, 'after': {'item': 'dosa', 'status': 'PLACED'}} {'key': {'id': 1}, 'op': 'u', 'before': {'item': 'idli', 'status': 'PLACED'}, 'after': {'item': 'idli', 'status': 'COOKED'}} {'key': {'id': 2}, 'op': 'd', 'before': {'item': 'dosa', 'status': 'PLACED'}, 'after': None} {'key': {'id': 2}, 'value': None}

Interview and viva questions

Does Debezium slow the database?

Slightly: logical decoding has some cost, far less than polling. The snapshot reads tables once.

What about schema changes?

New columns appear in events; with Schema Registry the schema evolves (Module 8).

MySQL?

Debezium reads the binlog (row format); concepts are the same.

Exactly-once?

At-least-once by default; consumers should be idempotent (upsert by key). Debezium supports Connect exactly-once source on some connectors.
