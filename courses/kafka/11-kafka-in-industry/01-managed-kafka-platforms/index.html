1 The story

Who runs your Kafka?

Before you start: 10.2 Sizing.

🤔 You have learned to run brokers, controllers, Connect, a registry, monitoring, security and DR. Most companies pay someone else to do all of it. Who, and what do they still leave to you?

Managed services run Kafka (or a Kafka-compatible engine) for you: Confluent Cloud, Amazon MSK, Google Cloud Managed Service for Apache Kafka, Azure Event Hubs (Kafka API), Aiven, Instaclustr, Redpanda Cloud, WarpStream and others. They take the servers; you still own topic design, partitions, keys, schemas, client configs, security policy and cost. We sized TiffinGo’s needs first: 19.5 MB/s in, 78 MB/s out, 6.8 TB stored, 24 partitions.

  • What “managed” takes off your plate, and what stays with you.
  • Deployment models: serverless, provisioned, BYOC; Kafka vs Kafka-compatible.
  • How to compare and choose, starting from your own numbers.

2 Definition

Managed Kafka platforms

Formal definition (write this in exams)

A managed Kafka platform is a service in which a provider operates the Kafka (or Kafka-protocol-compatible) infrastructure, including provisioning, scaling, upgrades, monitoring and often ecosystem components, under a serverless, provisioned or bring-your-own-cloud (BYOC) model. Users keep responsibility for data modelling, client configuration, access policy and cost management.

In simple words

Instead of running Kafka servers yourself, you rent Kafka from a provider. They keep it running; you still design topics, keys, schemas and permissions, and watch the bill.

Why, how, where

Why

Running Kafka well needs on-call engineers, upgrades, capacity planning and security work. For many teams that effort costs more than a managed bill.

the problem it solves

How

The provider runs brokers, storage, upgrades, monitoring and often Connect, a schema registry and stream processing; you connect with SASL_SSL/OAuth/IAM, create topics via API/Terraform, and pay by capacity, throughput, storage and network.

the mechanism

Where

Startups and most enterprises on public cloud; teams without Kafka specialists; regulated firms using BYOC to keep data in their own accounts.

in real systems

When not

Less control (broker configs, versions, plugins), possible cost surprises (cross-zone and egress traffic, partitions), and vendor-specific features that are hard to leave.

Your numbers first

Managed Kafka at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Own car, lease, taxi

  • Self-managed is owning a car (you service it). Provisioned is a lease (fixed size, someone services it). Serverless is a taxi (pay per ride). BYOC is a chauffeur driving your own car.

Intermediate The market (late 2026)

  • Apache Kafka, managed: Amazon MSK (standard and Express brokers), Google Cloud Managed Service for Apache Kafka, Aiven, Instaclustr and others.
  • Kafka-compatible engines: Confluent Cloud (its Kora engine), Azure Event Hubs (Kafka endpoint), Redpanda (C++ engine), WarpStream and other object-storage-based designs.
  • Extras differ: managed connectors, schema registry, Flink/stream processing, cluster linking, table formats (Iceberg/Delta). Confluent has been part of IBM since March 2026.

Advanced Choosing well

  • Start from your workload (lesson lab): ingress/egress MB/s, partitions, retention, latency SLO, number of client apps.
  • Cost drivers: throughput units or brokers, storage (tiered/object storage lowers it), network (cross-AZ replication and consumer egress often dominate), connectors and extras.
  • Check: Kafka version and feature support (KIP-848, share groups, transactions), security (private networking, IAM/OAuth), limits (partitions, message size), SLA, regions, exit path (MirrorMaker 2/replicators).

Myth vs reality: things many websites still say

  • Myth: Managed means no Kafka knowledge needed.
    Reality (Kafka 4.4): Topic, key, schema and client design stay with you.
    Proof: Hook.
  • Myth: Every “Kafka” service runs Apache Kafka.
    Reality (Kafka 4.4): Several are Kafka-compatible engines.
    Proof: Table.
  • Myth: Broker price is the main cost.
    Reality (Kafka 4.4): Network and storage often dominate.
    Proof: Scenario 2.

Exam tip: “Self-managed vs managed Kafka?” Managed removes ops (upgrades, scaling, monitoring) but limits control; models serverless/provisioned/BYOC; Apache Kafka vs compatible engines; size from MB/s, TB, partitions; cost = capacity + storage + network; check features and exit path.

4 Step by step

Size before you shop

All outputs are real: a small Python sizing script for TiffinGo’s planned workload (no vendor accounts used; service facts from public product pages, late 2026).

  1. Step 1 · Workload

    peak_msgs, size_kb, retention_days, rf = 20000, 1.0, 7, 3
mbps_in = peak_msgs * size_kb / 1024
mbps_out = mbps_in * consumer_groups
    == 1) workload peak 20,000 msg/s x 1.0 KB = 19.5 MB/s in, 78.1 MB/s out (4 groups) replication traffic (RF 3): 39.1 MB/s between brokers storage for 7 days (avg 40% of peak, compression 0.5, RF 3): 6.76 TB
    Out is 4× in because four groups read everything; replication adds 2× in between brokers (a cost line in many clouds).

  2. Step 2 · Partitions

    need = max(mbps_in / per_partition, consumers_wanted)
    == 2) partitions (target 10 MB/s per partition on the slowest side) producer side: 2 consumer side (1 group): 2 max consumers wanted: 24 choose: 24 partitions (room for 24 parallel consumers)
    Throughput alone needs 2 partitions; parallelism needs 24. Many managed tiers price or limit partitions, so this matters.

  3. Step 3 · Models

    serverless | provisioned | BYOC
    == 3) the same need, three ways to pay (shape, not prices) serverless (pay per GB/partition-hour): elastic, scale to zero-ish provisioned brokers (pay per broker-hour + storage): fixed capacity, you size BYOC (vendor runs it in your account): data stays in your VPC
    Same numbers, three pricing shapes. Ask each vendor to price this exact workload.

7 Run the code

Run the code: size it

Your numbers first. Press Run, then try the challenges.

# Size a Kafka workload before talking to vendors
import math
peak_msgs, size_kb, retention_days, rf, groups = 20000, 1.0, 7, 3, 4
avg_ratio, compression = 0.4, 0.5

mb_in = peak_msgs * size_kb / 1024
mb_out = mb_in * groups
tb = peak_msgs * avg_ratio * size_kb * compression * 86400 * retention_days * rf / 1024**3
print(f"in {mb_in:.1f} MB/s, out {mb_out:.1f} MB/s, stored {tb:.2f} TB")
print("partitions:", max(math.ceil(mb_in / 10), 24))
in 19.5 MB/s, out 78.1 MB/s, stored 6.76 TB partitions: 24
  • mb_out = mb_in * groupsEvery group reads everything: egress grows.
  • print("partitions:", max(math.ceil(mb_in / 10), 24))Parallelism often decides.

Interview and viva questions

Is Confluent the same as Apache Kafka?

Confluent was founded by Kafka’s creators and contributes heavily; Confluent Cloud runs its own Kafka-compatible engine and adds services. Since March 2026 Confluent is part of IBM.

Is Redpanda Kafka?

It implements the Kafka protocol in C++ without the JVM; clients work, but internals and some features differ.

Can I use Kafka Streams with managed Kafka?

Yes, it is a client library; check required features (transactions, KIP-1071).

What about on-prem?

Self-managed, or vendor platforms for Kubernetes (e.g. Strimzi operator, Confluent Platform).
