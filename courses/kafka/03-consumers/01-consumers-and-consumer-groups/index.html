1 The story

Three cooks, six counters

Before you start: 1.2 Queue vs pub-sub and Module 2.

🤔 600 orders arrived in only 3 trips. How does one poll() bring back 200 records?

A Kafka consumer does not ask for one message at a time. It fetches big chunks from partition leaders in the background, and each poll() hands you a slice. Then two colleagues joined the same group and Kafka split the 6 partitions 2-2-2 without anyone writing a single line of coordination code.

TiffinGo’s kitchen service reads all orders with one consumer. At lunch it falls behind. Kabir starts two more copies of the same program and wonders how they will avoid cooking the same order twice.

Riya

Sir, I wrote a consumer with a while True: poll() loop. Is it reading one message per call?

Arjun Sir

No. Behind poll() the client fetches large batches from each partition leader and keeps them in memory. Each call just hands you the next records. We will see 200 per call.

Kabir

And if we start more copies of the same program?

Arjun Sir

If they share the same group.id, one broker, the group coordinator, splits the partitions among them. Start them and watch the assignment change.

2 Definition

Consumers and consumer groups

Formal definition (write this in exams)

A Kafka consumer reads records by repeatedly polling; the client fetches batches of records from partition leaders and returns them to the application in order per partition. Consumers that share a group.id form a consumer group, coordinated by a broker acting as group coordinator, which tracks membership through heartbeats and ensures each partition is assigned to exactly one member. The group stores its progress as committed offsets in the internal topic __consumer_offsets.

In simple words

A consumer keeps asking Kafka for new records. Several consumers with the same group name become a team: one broker acts as the team manager and gives each member its own partitions, so no record is handled twice and the work is shared.

Why, how, where

Why

One consumer cannot keep up with a busy topic, and if it dies someone must take over. Groups share the work and recover automatically.

the problem it solves

How

Consumers with the same group.id register with a group coordinator broker; partitions are divided among members; each member fetches from its partitions’ leaders and polls records in batches.

the mechanism

Where

Every service that reads Kafka: kitchen and billing services, stream processors, sink connectors, Spark jobs.

in real systems

When not

A group cannot use more active members than partitions, and a member that stops polling is treated as dead.

Consumers at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Kitchen staff

  • Orders arrive on six counters (partitions). One cook can serve all six; when two more cooks join, the manager (coordinator) gives each cook two counters. Nobody serves the same counter twice.

Intermediate The poll loop

  • subscribe([topic]), then loop: poll() (one record) or consume(n) (up to n), process, commit (Lesson 3.3), repeat.
  • The client fetches in the background (fetch.min.bytes, fetch.max.wait.ms, max.partition.fetch.bytes); Java returns up to max.poll.records (500) per poll.
  • The group coordinator is the leader of the __consumer_offsets partition chosen by hashing the group id.

Advanced Liveness and states

  • A member is alive while it sends heartbeats (session.timeout.ms, 45 s default) and keeps calling poll within max.poll.interval.ms (5 min). Slow processing beyond that → the member is removed and its partitions move.
  • Group states: Empty, PreparingRebalance, CompletingRebalance, Stable, Dead (classic protocol); the new consumer protocol (KIP-848) uses Empty, Assigning, Reconciling, Stable.
  • Static membership (group.instance.id) lets a restarted pod keep its partitions without a rebalance, within the session timeout.

Myth vs reality: things many websites still say

  • Myth: Kafka pushes messages to consumers.
    Reality (Kafka 4.4): Consumers pull; the client fetches in the background.
    Proof: Step 1: 200 records per consume call.
  • Myth: ZooKeeper tracks consumer offsets.
    Reality (Kafka 4.4): Offsets live in __consumer_offsets; a broker coordinates the group.
    Proof: Step 4: coordinator k2.
  • Myth: You must code which consumer reads which partition.
    Reality (Kafka 4.4): The coordinator assigns automatically when you subscribe.
    Proof: Step 2: 2-2-2 split.

Exam tip: “How do consumer groups work?” Members with the same group.id register with a coordinator broker; partitions are assigned so each partition has one member; members heartbeat and poll within max.poll.interval.ms; offsets are committed to __consumer_offsets; failures or joins trigger a rebalance.

Long processing inside the poll loop (calling a slow API for each record) can exceed max.poll.interval.ms: the member is kicked out, its partitions move, and records are processed twice. Keep work per poll small, or hand it to worker threads while the loop keeps polling.

7 Run the code

Run the code: range assignment

The default strategy that produced our 2-2-2 split. Press Run, then try the challenges.

# A consumer group in miniature: the coordinator splits partitions with "range"
def range_assign(partitions, members):
    members = sorted(members)
    per, extra = divmod(len(partitions), len(members))
    out, i = {}, 0
    for k, m in enumerate(members):
        n = per + (1 if k < extra else 0)
        out[m] = partitions[i:i + n]
        i += n
    return out

parts = list(range(6))
print(range_assign(parts, ["kitchen-1"]))
print(range_assign(parts, ["kitchen-1", "kitchen-2", "kitchen-3"]))
print(range_assign(parts, ["k1", "k2", "k3", "k4"]))
{'kitchen-1': [0, 1, 2, 3, 4, 5]} {'kitchen-1': [0, 1], 'kitchen-2': [2, 3], 'kitchen-3': [4, 5]} {'k1': [0, 1], 'k2': [2, 3], 'k3': [4], 'k4': [5]}
  • per, extra = divmod(len(partitions), len(members))Each member gets an equal share; the first ones get one extra.

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.1 in one screen

  • Consumers pull; client fetches batches; poll/consume hands them out.
  • Lab: 600 records in 3 polls of 200.
  • Same group.id → coordinator assigns partitions (range: 2-2-2).
  • Coordinator = leader of hash(group) partition of __consumer_offsets (k2 here); state Stable.
  • Liveness: heartbeats (session.timeout 45 s) + poll within max.poll.interval (5 min).
  • Static membership: group.instance.id.

Interview and viva questions

Can one consumer read several topics?

Yes: subscribe(["a", "b"]) or a regex pattern; partitions of all topics are assigned within the group.

Is a consumer thread-safe?

No. Use one consumer per thread; the confluent-kafka and Java consumers must not be shared across threads.

What does auto.offset.reset=none do?

Throws an error if the group has no committed offset, forcing you to decide explicitly.

Why set client.id?

It appears in group descriptions, logs and metrics, so you can tell which pod owns which partitions.

Real-world scenario questions (asked in company interviews)

Consumer interview questions.

Any company · backendFresher

“What is a consumer group?”

Explain.

The interviewer is checking: answer?

Show a strong answer

Consumers sharing a group.id; the coordinator assigns each partition to one member so work is shared and fails over; each group keeps its own committed offsets, so different groups each get all records.

Avoid: “Consumers on the same machine.”

Food deliveryMid-level

Rebalance loop

A group keeps rebalancing every few minutes.

The interviewer is checking: diagnose?

Show a strong answer
  • Members exceed max.poll.interval.ms (slow processing).
  • Check logs for leaving the group.
  • Smaller batches or async workers.

Avoid: Raising partitions.

Data engineeringMid-level

Scaling

Lag grows; there are 4 partitions and 4 consumers.

The interviewer is checking: plan?

Show a strong answer
  • More consumers won’t help.
  • Add partitions (watch keys) or speed up processing.
  • Check per-partition lag for hot keys.

Avoid: “Add 4 more pods.”

PlatformSenior

Deploys

Rolling deploys cause minutes of paused consumption.

The interviewer is checking: design?

Show a strong answer
  • Static membership.
  • Cooperative or KIP-848 protocol (3.2).
  • Graceful close().

Avoid: Deploying all pods at once.
