2 Definition

Delivery guarantees

Formal definition (write this in exams)

Delivery semantics describe how many times a record’s processing takes effect in the presence of failures. At-most-once: offsets are committed before processing, so a failure may skip records. At-least-once: offsets are committed after processing, so a failure may repeat records. Exactly-once: each record’s effect occurs once; in Kafka it is provided for read-process-write pipelines within Kafka by idempotent producers and transactions with read_committed consumers, and for external systems by idempotent writes or by atomically storing results with offsets.

In simple words

If you save progress before doing the work, a crash can lose work. If you save after, a crash can repeat work. To get “once”, make repeats harmless or save the work and the progress together.

Why, how, where

Why

Crashes happen between “do the work” and “save progress”. Which one you do first decides whether you can lose or repeat work.

the problem it solves

How

Commit first → at-most-once. Work first, then commit → at-least-once. Make the work idempotent, or put output and offsets in one transaction → effectively exactly-once.

the mechanism

Where

Payments and invoices (at-least-once + dedup), metrics (at-most-once is fine), Kafka-to-Kafka pipelines (transactions).

in real systems

When not

No setting gives exactly-once for side effects outside Kafka (an SMS, an HTTP call) by itself: the external action must be idempotent.

Dissect the duplicate

Delivery guarantees at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Ticking the register

  • At-most-once: tick “done” first, then deliver. If you faint in between, the parcel is never delivered. At-least-once: deliver first, then tick. If you faint, someone delivers it again.

Intermediate In consumer code

  • At-most-once: commit, then process. Crash after commit → those records are skipped.
  • At-least-once: process, then commit (the usual choice; also what auto-commit gives in the normal case, though auto-commit can drift into at-most-once if processing is async).
  • Exactly-once (effectively): at-least-once + idempotent processing (dedup by a business id, upserts), or Kafka transactions for Kafka-to-Kafka pipelines.

Advanced Where each layer stands

  • Producer → broker: idempotence removes retry duplicates (2.5).
  • Consume → process → produce within Kafka: transactions commit output records and input offsets atomically; downstream consumers use isolation.level=read_committed (3.5). Kafka Streams enables this with processing.guarantee=exactly_once_v2.
  • Kafka → external system (DB, email): needs an idempotent sink or storing offsets in the same database transaction as the result.

Myth vs reality: things many websites still say

  • Myth: Kafka is exactly-once by default.
    Reality (Kafka 4.4): Default consumers are at-least-once (or at-most-once by mistake).
    Proof: Steps 2–3: 5 lost or 5 doubled.
  • Myth: Exactly-once means the SMS is sent once.
    Reality (Kafka 4.4): It covers Kafka outputs and offsets, not external calls.
    Proof: Scenario 2.
  • Myth: At-least-once means lots of duplicates.
    Reality (Kafka 4.4): Only the uncommitted work since the last commit repeats.
    Proof: Step 3: exactly 5 (21–25).

Exam tip: “Explain at-most/at-least/exactly-once in Kafka.” Commit before processing = at-most-once; process then commit = at-least-once; exactly-once = idempotent producer + transactions + read_committed (Kafka to Kafka) or idempotent/atomic sinks for external systems.

“Exactly-once” in Kafka means each input record’s effects on Kafka (output records and committed offsets) happen exactly once. It does not stop your code from calling an SMS gateway twice. Design external side effects to be idempotent (send with an idempotency key, upsert by id).

7 Run the code

Run the code: crash simulation

The same experiment as the lab, in pure Python. Press Run, then try the challenges.

# Simulate the crash: commit before vs after processing
def run(mode, n=50, batch=10, crash_after=25):
    sent, committed, done = [], 0, 0
    for attempt in range(2):                     # first run crashes, second continues
        pos = committed
        while pos < n:
            batch_ids = list(range(pos + 1, min(pos + batch, n) + 1))
            if mode == "atmost": committed = batch_ids[-1]
            crashed = False
            for i in batch_ids:
                sent.append(i); done += 1
                if attempt == 0 and done == crash_after: crashed = True; break
            if crashed: break
            if mode == "atleast": committed = batch_ids[-1]
            pos = batch_ids[-1]
    lost = sorted(set(range(1, n + 1)) - set(sent))
    twice = sorted(i for i in set(sent) if sent.count(i) > 1)
    return len(sent), lost, twice

for mode in ("atmost", "atleast"):
    total, lost, twice = run(mode)
    print(mode, "sent:", total, "lost:", lost, "twice:", twice)

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.4 in one screen

  • At-most-once: commit → process (lab: 5 lost, 26–30).
  • At-least-once: process → commit (lab: 5 twice, 21–25).
  • Duplicates = work since last commit; loss = committed but unprocessed.
  • Effectively once: at-least-once + idempotent processing (ids, upserts, idempotency keys).
  • Exactly-once in Kafka: idempotent producer + transactions + read_committed (3.5).
  • External side effects need their own idempotency.

Interview and viva questions

Which guarantee does auto-commit give?

Usually at-least-once, because it commits positions already returned by poll at the next poll. With async processing it can become at-most-once.

Is exactly-once slower?

Transactions add some latency (commit markers, coordinator round trips), typically small at reasonable batch sizes.

Does Spark give exactly-once with Kafka?

Spark Structured Streaming achieves end-to-end exactly-once with replayable sources, checkpoints and idempotent/transactional sinks.

Can a consumer get duplicates even with an idempotent producer?

Yes: producer idempotence prevents duplicate writes, not repeated reads after a consumer crash.

Real-world scenario questions (asked in company interviews)

Delivery semantics interview questions.

Any company · dataFresher

“at-least-once vs at-most-once?”

Explain with commits.

The interviewer is checking: answer?

Show a strong answer

At-most-once commits before processing, so a crash skips records. At-least-once commits after processing, so a crash repeats records. Most systems use at-least-once with idempotent processing.

Avoid: “Kafka decides it automatically.”

FintechMid-level

Duplicate invoices

Customers get duplicate invoices after crashes.

The interviewer is checking: fix?

Show a strong answer
  • Expected with at-least-once.
  • Idempotent sink keyed by invoice_id.
  • Commit smaller batches.

Avoid: Switching to at-most-once.

Data engineeringMid-level

Exactly-once claim

A vendor says “exactly-once SMS with Kafka”.

The interviewer is checking: evaluate?

Show a strong answer
  • Kafka EOS covers Kafka writes and offsets.
  • SMS needs an idempotency key or dedup store.

Avoid: Accepting the claim.

Ledger pipeline
