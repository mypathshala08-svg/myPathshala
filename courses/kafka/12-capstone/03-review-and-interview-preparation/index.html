1 The story

🤔 We killed a broker two seconds into processing 3,000 orders. How many of the 6,000 orders ended up missing or duplicated?

2 Definition

Review and interview preparation

Formal definition (write this in exams)

A production review verifies a streaming system against its requirements under failure: fault injection (e.g. broker termination during processing) followed by an independent audit that checks completeness and uniqueness of every record, plus a checklist covering data design, durability, error handling, security and operations. Interview preparation maps common questions to the concepts and evidence gathered in each lesson.

In simple words

Break your system on purpose, then count everything again. If the numbers still match, you understand it well enough to explain it in an interview.

Why, how, where

Why

Pipelines look correct when everything works. Failures (broker loss, coordinator moves, crashes mid-transaction) are where data is lost or doubled, and where interviews dig.

the problem it solves

How

Run the pipeline, inject a failure at a random moment, let it finish, then audit with an independent read_committed reader: every id present, exactly once. Repeat for each failure type. Then walk a checklist and practise explaining each decision.

the mechanism

Where

Release checklists, game days, architecture reviews, and interviews for data engineer, platform and backend roles.

in real systems

When not

A passing test proves only the failures you tried. Keep the audit script and run it after every change.

Review at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A fire drill

  • A building is safe only if people get out during a drill. A pipeline is correct only if the counts still match after you pull a plug.

Intermediate The review checklist

  • Data: keys and ordering, partitions from numbers, schemas and compatibility mode, retention/compaction.
  • Durability: RF 3, min ISR 2, acks=all, idempotence; EOS where duplicates matter; idempotent sinks otherwise.
  • Errors: DLQ with reasons, retries with backoff, alert on DLQ rate; poison-message handling.
  • Operations: lag-in-time alerts, URP/offline alerts, security (TLS, SASL, ACLs, quotas), DR plan and drills, upgrade path.

Advanced What our drill taught

  • The first run stopped after a fixed number of empty polls while the group coordinator and transaction coordinator on k3 failed over, and processed nothing: timeouts in your own loop can turn a 10-second hiccup into “done”. We changed the loop to run until the expected count or a generous deadline.
  • With k3 dead, RF 3 / min ISR 2 kept writes going, the transactional producer reconnected to a new coordinator, and the audit found every id once.

Myth vs reality: things many websites still say

  • Myth: If it works once, it works.
    Reality (Kafka 4.4): Test under failure.
    Proof: Step 1.
  • Myth: Exactly-once is a config flag.
    Reality (Kafka 4.4): A tested pattern with audits.
    Proof: Step 3.
  • Myth: “No data for a while” means done.
    Reality (Kafka 4.4): Failovers pause delivery.
    Proof: Level 3.

Exam tip: “How do you prove a Kafka pipeline is correct?” Fault injection (kill broker/processor), independent read_committed audit (every id once), checklists (keys, partitions, RF/min ISR/acks, EOS, DLQ, schemas, security, monitoring, DR), repeated after changes.

Do not end a processing loop on “no data for N polls” in tests or batch jobs: during coordinator failover a healthy consumer can receive nothing for 10+ seconds. Stop on an expected count, a deadline, or end offsets reached.

7 Run the code

Run the code: the audit

The check behind “exactly once”. Press Run, then try the challenges.

# Audit: every id exactly once across enriched + DLQ
enriched = list(range(1, 3729))                # pretend ids
dlq = list(range(3729, 6001))
expected = set(range(1, 6001))

all_ids = enriched + dlq
missing = expected - set(all_ids)
dupes = len(all_ids) - len(set(all_ids))
print("records", len(all_ids), "missing", len(missing), "duplicates", dupes)
print("exactly once:", not missing and dupes == 0)
records 6000 missing 0 duplicates 0 exactly once: True
  • missing = expected - set(all_ids)Completeness.
  • dupes = len(all_ids) - len(set(all_ids))Uniqueness.

Interview and viva questions

How often should we run drills?

Before major releases and regularly (e.g. quarterly game days), plus automated tests in CI with a test cluster.

Can I test without Docker?

Kafka Streams apps with TopologyTestDriver; client logic with mocks; but broker failures need a real cluster.

What is the most common interview topic?

Delivery semantics (acks, idempotence, EOS), consumer groups and rebalances, and partitions/ordering.

What next after this course?

Build your own pipeline, add Kafka Streams or Spark (Module 9), secure it (10.3) and add DR (10.4).
