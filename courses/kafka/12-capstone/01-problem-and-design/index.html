2 Definition

The capstone design

Formal definition (write this in exams)

The capstone is an end-to-end order pipeline: an Avro producer writes orders keyed by city to a replicated topic; an exactly-once processor (transactions, read_committed) enriches each order with prices from a compacted reference topic and writes it either to an enriched topic or to a dead letter queue with error headers; Kafka Connect copies enriched orders to a sink; monitoring tracks lag and counts.

In simple words

Orders go in, get prices added, good ones go to one topic and bad ones to a problem topic, and a connector copies the good ones out. Every order must end up in exactly one place.

Why, how, where

Why

Real projects fail on design, not syntax: wrong keys break ordering, too few partitions cap scale, a missing DLQ stops everything, a missing contract breaks consumers. Writing decisions down before coding prevents that.

the mechanism

Designing at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The story

  • Customers place orders; the kitchen needs them with prices; bad orders must not block good ones; nothing may be lost or counted twice; analytics wants a copy.

Intermediate The decisions

  • Key = city: order per city, spread across partitions (watch for hot keys, Lesson 2.2). 6 partitions: 6 parallel consumers.
  • RF 3, min ISR 2, acks=all, idempotence: survive one broker loss without losing writes (2.4, 2.5, 5.2).
  • Transactions + read_committed: each order lands once in enriched or DLQ, even across crashes (3.5). Compacted menu as a lookup table (4.3). Avro + registry (8.1). Connect sink (7.1).

Advanced At 100× scale

  • Partitions from measured rates (10.2); move the processor to Kafka Streams or Flink with state stores instead of an in-memory menu (9.2, 9.4); share groups for non-ordered side jobs (6.1).
  • Security per app (10.3), lag-in-seconds SLOs (10.1), a DR cluster with MirrorMaker 2 (10.4), and possibly a managed platform (11.1).

Myth vs reality: things many websites still say

  • Myth: More partitions are safer.
    Reality (Kafka 4.4): Size from needs: 6 here.
    Proof: Step 2.
  • Myth: Exactly-once is a broker setting.
    Reality (Kafka 4.4): It is a pattern: idempotence + transactions + read_committed.
    Proof: Decision table.
  • Myth: Design can wait until code works.
    Reality (Kafka 4.4): Keys and partitions are hard to change later.
    Proof: Review 1.

Exam tip: “Design an order pipeline with Kafka.” Requirements → partitions (rates, consumers), key (ordering), RF 3/min ISR 2/acks=all/idempotence, EOS processing, DLQ, compacted reference data, schemas, Connect sink, monitoring, security, DR.

  2. Step 2 · Derive decisions

    parts = max(math.ceil(mb / 5), req["consumers_max"])
    == 2) decisions derived cap-orders: 6 partitions (peak 0.98 MB/s, 6 consumers), key = city (order per city) durability: RF 3, min.insync.replicas 2, producer acks=all + idempotence (must_not_lose) retention: 7 days; cap-menu compacted (latest price per item) processing: read_committed + transactions (exactly-once into enriched + DLQ) errors: ~5% expected → cap-orders-dlq with x-error headers contract: Avro + Schema Registry (BACKWARD); sink: Kafka Connect SLO: alert if lag > 60 s of processing
    Throughput needs only 1 partition (under 1 MB/s); parallelism needs 6. Durability, processing and error choices follow from the flags.

  3. Step 3 · Topic plan

    for t, p, c in topics: print(t, p, "RF 3", c)
    == 3) topic plan cap-orders partitions 6 RF 3 delete, 7d, min ISR 2 cap-menu partitions 3 RF 3 compact cap-orders-enriched partitions 3 RF 3 delete, min ISR 2 cap-orders-dlq partitions 3 RF 3 delete, 30d
    Four topics, each with a reason. 12.2 creates exactly these.

7 Run the code

Run the code: derive a design

Each decision from one requirement. Press Run, then try the challenges.

# Requirements -> decisions (the capstone rules)
import math
req = {"peak_per_s": 2000, "kb": 0.5, "consumers": 6, "must_not_lose": True, "no_double": True, "bad_pct": 5}
mb = req["peak_per_s"] * req["kb"] / 1024
design = {
    "partitions": max(math.ceil(mb / 5), req["consumers"]),
    "replication": "RF 3, min ISR 2, acks=all, idempotence" if req["must_not_lose"] else "RF 2",
    "processing": "transactions + read_committed" if req["no_double"] else "at-least-once + idempotent sink",
    "errors": "DLQ" if req["bad_pct"] > 0 else "none",
}
for k, v in design.items(): print(f"{k:12s} {v}")
partitions 6 replication RF 3, min ISR 2, acks=all, idempotence processing transactions + read_committed errors DLQ

Interview and viva questions

Why not Kafka Streams for the processor?

You can; we used plain clients to show the transaction steps clearly. Streams with exactly_once_v2 is a good next step.

Why 3 partitions for enriched?

Lower volume after filtering and only analytics reads it; sized from need.

Where is security?

Add Lesson 10.3 (SASL_SSL, ACLs per app) before production.

Can I run it in Colab?

Yes, with a local Kafka as in Lesson 1.6; Connect and the registry need Docker or the jar files.

“How do you choose partitions and keys?”

Explain.

The interviewer is checking: answer?

Show a strong answer

Keys come from ordering needs (same key, same partition). Partitions from throughput per partition and how many consumers must work in parallel, plus growth.

Avoid: “Always 100.”
