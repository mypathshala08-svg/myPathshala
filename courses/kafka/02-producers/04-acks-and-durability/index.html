2 Definition

acks and durability

Formal definition (write this in exams)

The producer configuration acks defines when a write is acknowledged: 0 (no acknowledgement), 1 (after the leader appends the record) or all/-1 (after all members of the partition’s in-sync replica set have it). The topic/broker setting min.insync.replicas is the minimum ISR size required for acks=all writes; below it the leader rejects writes with NOT_ENOUGH_REPLICAS. Together with the replication factor and disabled unclean leader election, these settings determine durability and availability.

In simple words

acks is how many copies must confirm before the producer hears “saved”. min.insync.replicas is the minimum number of healthy copies Kafka requires before it even accepts an acks=all write.

Why, how, where

Why

Brokers fail. If a write is confirmed after only one copy exists and that broker dies, the “confirmed” record is gone.

the problem it solves

How

acks says how many replicas must have the record before the producer hears “OK”; min.insync.replicas sets how many in-sync copies must exist for acks=all to be accepted at all.

the mechanism

Where

Payments and orders: acks=all + RF 3 + min.insync 2. Metrics and telemetry: acks=1 or 0 for speed.

in real systems

When not

acks=all does not help if min.insync.replicas=1 and only the leader is in sync: then it behaves like acks=1.

Dissect the durability recipe

acks at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Courier receipts

  • acks=0: drop the parcel at the gate and walk away. acks=1: the reception desk signs. acks=all: reception and the two backup stores all sign before you get the receipt.

Intermediate The rules

  • acks=0: no response; offset unknown (-1); fastest, may lose data silently.
  • acks=1: the leader wrote it to its log; lost if the leader dies before followers copy it.
  • acks=all (= -1, default since Kafka 3.0): every replica currently in the ISR has it. With min.insync.replicas=2 at least 2 copies exist before success.

Advanced Deeper details

  • If ISR size < min.insync.replicas, the leader rejects acks=all writes with NOT_ENOUGH_REPLICAS (retriable): writes stop, reads continue. This trades availability for durability.
  • Consumers only see records below the high watermark (replicated to all ISR members), so acks=1 data that was never replicated is never shown to consumers before a leader change.
  • unclean.leader.election.enable=false (default) prevents an out-of-sync replica from becoming leader and silently dropping data. Kafka 4.x adds Eligible Leader Replicas (KIP-966, the Elr column in --describe) to pick a safe leader after failures.

Myth vs reality: things many websites still say

  • Myth: The default is acks=1.
    Reality (Kafka 4.4): Since Kafka 3.0 the default is acks=all (with idempotence).
    Proof: our producers used all by default.
  • Myth: acks=all means all 3 replicas, always.
    Reality (Kafka 4.4): It means all replicas currently in the ISR; min.insync.replicas sets the floor.
    Proof: Step 3: ISR of 2.
  • Myth: acks=0 records are dropped.
    Reality (Kafka 4.4): They are usually stored; you just never know.
    Proof: Step 4: offsets 2–3 used by acks=0 records.

Exam tip: “acks=0, 1, all?” 0 = no ack (fast, may lose), 1 = leader only (lost if leader dies before replication), all = all ISR (safe with RF 3 and min.insync.replicas=2). Below min ISR, acks=all writes fail with NOT_ENOUGH_REPLICAS. Keep unclean leader election off.

Do not set min.insync.replicas equal to the replication factor for important topics: then any single broker restart blocks writes (we did exactly that in Step 3 to show the refusal). The usual choice is RF 3 with min ISR 2.

Run the code: acks rules

The leader’s decision in a few lines. Press Run, then try the challenges.

# What each acks level waits for, and when it refuses
def write(acks, isr, min_isr):
    if acks == "all" and len(isr) < min_isr:
        return "NOT_ENOUGH_REPLICAS (refused)"
    if acks == "0":
        return "sent, no answer (offset unknown)"
    if acks == "1":
        return f"OK after leader {isr[0]}"
    return f"OK after all ISR {isr}"

for isr in ([1, 2, 3], [1, 2], [1]):
    print("ISR", isr)
    for acks in ("0", "1", "all"):
        print(f"   acks={acks:3} ->", write(acks, isr, min_isr=2))

Check yourself

Quick revision

Lesson 2.4 in one screen

  • acks 0 / 1 / all = none / leader / all ISR.
  • Lab: 58,005 / 48,900 / 37,133 records/s.
  • min.insync.replicas: below it acks=all → NOT_ENOUGH_REPLICAS (writes stop, reads go on).
  • Lab: ISR 2 < 3 → refused; acks=1 offsets 0,1; acks=0 offset None.
  • Recipe: RF 3, min ISR 2, acks=all, idempotence, unclean election off.
  • High watermark; ELR (KIP-966) in Kafka 4.x.

Interview and viva questions

Is acks=all slow?

It adds the time for followers to fetch, usually a few milliseconds on a good network. Batching and compression recover most throughput.

Does acks=all flush to disk?

No. Kafka relies on replication (copies in the page cache of several brokers) rather than fsync per write; flush settings exist but are rarely needed.

Where is min.insync.replicas set?

As a broker default or per topic (kafka-configs.sh). It has no effect on acks=0 or 1.

What does Elr mean in --describe?

Eligible Leader Replicas (KIP-966): replicas known to have all committed data that may safely become leader even if not in the current ISR.

Real-world scenario questions (asked in company interviews)

Durability interview questions.

Any company · dataFresher

“Explain acks.”

Compare 0, 1, all.

The interviewer is checking: answer?

Show a strong answer

acks=0: no acknowledgement, may lose silently. acks=1: leader wrote it; lost if the leader dies before replication. acks=all: all in-sync replicas have it; with RF 3 and min.insync.replicas 2 it survives a broker loss.

  • Do not lower the floor for payments.
