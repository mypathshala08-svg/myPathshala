Idempotent producer and retries

Retries keep data safe but can duplicate it. We create a real duplicate on a Kafka 4.4 cluster, read the producer id and sequence numbers on disk, and prevent it with the idempotent producer. All outputs are real.

1 The story

One payment, stored three times

Before you start: 2.4 acks and durability (ISR, acks=all).

🤔 One ₹75,000 payment was stored three times. Kafka did nothing wrong. Then we flipped one setting.

We froze one follower so acknowledgements were late. The producer thought its request was lost and retried: with idempotence off, the same payment landed at offsets 0, 1 and 2. With idempotence on, the broker recognised the retry and stored it once. You will see the producer id and sequence numbers that make the difference.

  • Why retries create duplicates in the first place.
  • The three numbers (producer id, epoch, sequence) the broker checks.
  • What idempotence does not protect you from.

A TiffinGo customer complains of a triple charge. The logs show the payment service called produce() only once. Kabir has to explain how Kafka ended up with three copies.

Riya

Sir, how can a payment be stored three times? The producer sent it once.

Arjun Sir

The producer sent it once, did not get an answer in time, and sent it again. And again. The broker had stored every attempt; only the answers were late.

Kabir

So should we turn retries off?

Arjun Sir

Then a short network blip loses payments. The real fix is idempotence: the broker remembers who sent what, using a producer id and sequence numbers, and ignores copies. Let’s create the duplicate for real, then prevent it.

2 Definition

Idempotent producer and retries

Formal definition (write this in exams)

An idempotent producer (enable.idempotence=true, default since Kafka 3.0) guarantees that retries do not introduce duplicates or reorder records within a partition for the lifetime of the producer session. The broker assigns a producer id and epoch; the producer attaches a monotonically increasing sequence number per partition to each batch. The partition leader tracks the most recent sequences per producer and rejects or acknowledges-without-append any batch whose sequence it has already written. Idempotence requires acks=all, retries enabled and at most 5 in-flight requests per connection.

In simple words

The broker remembers which producer sent which numbered batch. If the same numbered batch arrives again because of a retry, the broker says “OK, got it” but does not store it a second time.

Why, how, where

Why

Networks lose responses, not just requests. A producer that retries cannot know whether the first attempt was stored, so without help it may store the record twice.

the problem it solves

How

The broker gives each producer an id; the producer numbers every batch per partition. The broker keeps the last sequences and silently drops a batch it already has.

the mechanism

Where

On by default in every modern Kafka client: payments, orders, CDC, anything where a duplicate costs money.

in real systems

When not

It does not deduplicate across producer restarts or when your app calls produce() twice for the same business event: use transactions or business keys.

Dissect the evidence

Idempotence at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Numbered cheques

  • Each cheque from your chequebook has a number. If the bank receives cheque no. 17 twice, it pays only once. The producer id is your account; the sequence is the cheque number.

Intermediate How it works

  • On start, the producer gets a producer id (PID) and epoch from the broker (InitProducerId).
  • For every partition it numbers batches with a sequence 0, 1, 2 … The leader stores PID, epoch and sequences with each batch.
  • If a batch arrives with a sequence already stored, the leader returns success without appending again. A gap in sequences gives OUT_OF_ORDER_SEQUENCE_NUMBER.

Advanced Rules and limits

  • Requires acks=all, retries > 0 and max.in.flight.requests.per.connection ≤ 5; brokers keep state for the last 5 batches per producer per partition, which also keeps order on retries.
  • Without idempotence, max.in.flight > 1 plus retries can reorder records (batch 2 succeeds, batch 1 retried later).
  • A restarted producer gets a new PID, so re-sending after a crash is not deduplicated. For read-process-write pipelines use transactions (transactional.id, Lesson 3.5), which also fence old “zombie” producers via the epoch.
  • Retry pacing: retry.backoff.ms (100 ms) growing to retry.backoff.max.ms (1 s) with exponential backoff (KIP-580); everything stops at the delivery timeout.

Myth vs reality: things many websites still say

  • Myth: Duplicates only happen if the app sends twice.
    Reality (Kafka 4.4): Producer retries after a lost or late response also duplicate.
    Proof: Step 2: one produce(), three copies.
  • Myth: Idempotence uses a “request id”.
    Reality (Kafka 4.4): It uses a producer id, epoch and per-partition sequence numbers.
    Proof: Step 3: producerId 7001, baseSequence 0.
  • Myth: Idempotence gives exactly-once end to end.
    Reality (Kafka 4.4): Only within one producer session; restarts and consumers need more.
    Proof: Types table: restarts get a new PID.

Exam tip: “How does the idempotent producer work?” Broker assigns PID/epoch; producer numbers batches per partition; leader keeps last 5 sequences per PID and drops duplicates; requires acks=all, retries>0, max.in.flight ≤5; default since 3.0; covers retries within a session, not restarts (use transactions).

4 Step by step

Create a duplicate, then prevent it

All outputs are real: Kafka 4.4.0, 3 brokers; Python confluent-kafka; one-partition topics with replicas on brokers 1, 2, 3; follower k3 frozen with docker pause. Script: jobs/m2/l25_dup.py.

  1. Step 1 · Freeze a follower, idempotence OFF

    p = Producer({"bootstrap.servers": "k1:9092", "acks": "all", "enable.idempotence": False,
              "retries": 10, "request.timeout.ms": 3000, "retry.backoff.ms": 500})
p.produce(topic, key="user3@upi", value="pay Rs 75000 (t045)")
# meanwhile: docker pause k3  (a follower of this partition)
    == 1) idempotence OFF Topic: idem-off Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3 $ docker pause k3 (follower frozen; leader waits for it before acks=all) enable.idempotence=False: delivered after 8 s -> ['offset 2']
    Leader 1 appends at once but must wait for follower 3 (acks=all). Our request timed out after 3 s, so the producer retried, twice. About 8 s later the controller fenced the frozen broker (its session timed out), the ISR shrank and the leader finally answered “offset 2”.

  2. Step 2 · Look inside: three copies

    kafka-console-consumer.sh --topic idem-off --from-beginning --formatter-property print.offset=true
kafka-dump-log.sh --files /var/lib/kafka/data/idem-off-0/00000000000000000000.log
    records in the partition: Offset:0 pay Rs 75000 (t045) Offset:1 pay Rs 75000 (t045) Offset:2 pay Rs 75000 (t045) batches on disk (kafka-dump-log): baseOffset: 0 baseSequence: -1 lastSequence: -1 producerId: -1 producerEpoch: -1 baseOffset: 1 baseSequence: -1 lastSequence: -1 producerId: -1 producerEpoch: -1 baseOffset: 2 baseSequence: -1 lastSequence: -1 producerId: -1 producerEpoch: -1
    Offsets 0, 1, 2 all contain the same payment. The batches carry producerId: -1 and no sequence, so the broker had no way to know they were the same.

  3. Step 3 · Same failure, idempotence ON

    Producer({..., "enable.idempotence": True, ...})   # the default since Kafka 3.0
    == 2) idempotence ON (the default since Kafka 3.0) Topic: idem-on Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3 $ docker pause k3 (follower frozen; leader waits for it before acks=all) enable.idempotence=True: delivered after 9 s -> ['offset 0'] records in the partition: Offset:0 pay Rs 75000 (t045) batches on disk (kafka-dump-log): baseOffset: 0 baseSequence: 0 lastSequence: 0 producerId: 7001 producerEpoch: 0
    The producer again waited and retried, but now each attempt carried producerId 7001, sequence 0. The leader saw sequence 0 was already stored, answered success, and appended nothing new: one copy.

7 Run the code

Run the code: dedup by sequence

The leader’s check in a few lines. Press Run, then try the challenges.

# A leader that deduplicates by (producer id, sequence)
log, seen = [], {}            # seen[(pid, partition)] = last sequence written

def append(pid, seq, value, idempotent=True):
    if idempotent and seen.get(pid, -1) >= seq:
        return f"duplicate seq {seq}: not stored again"
    log.append(value)
    if idempotent:
        seen[pid] = seq
    return f"stored at offset {len(log) - 1}"

for attempt in range(3):                       # first try + 2 retries
    print("idempotent off:", append(None, -1, "t045", idempotent=False))
log.clear()
for attempt in range(3):
    print("idempotent on :", append(7001, 0, "t045"))
print("copies stored:", log.count("t045"))

9 Quiz and revision

Check yourself

Quick revision

Lesson 2.5 in one screen

  • Retries + lost/late response = duplicates (lab: offsets 0, 1, 2).
  • Idempotence: PID + epoch + per-partition sequence; leader skips seen sequences.
  • Lab: producerId 7001, baseSequence 0, one copy.
  • Needs acks=all, retries, in-flight ≤ 5; default since 3.0; keeps order on retry.
  • Not covered: producer restarts, app double-sends, consumer re-processing → transactions / business-key dedup.
  • Backoff 100 ms → 1 s; stop at delivery timeout.

Interview and viva questions

Does idempotence slow the producer?

Very little; the extra fields are a few bytes per batch and the broker check is cheap. It is on by default for that reason.

How long does the broker remember a producer id?

Until producer state expires (transactional.id.expiration.ms / producer.id.expiration.ms, about a day by default) if the producer stays idle.

Is idempotence per topic?

Per producer session and per partition: sequences are tracked separately for each partition the producer writes.

What is a zombie producer?

An old instance (e.g. after a network split) that keeps writing. Transactions bump the epoch so the broker rejects the zombie.

A producer whose retries cannot create duplicates: the broker assigns a producer id and the producer numbers batches per partition; the leader ignores a batch whose sequence it already wrote. Default since Kafka 3.0.
