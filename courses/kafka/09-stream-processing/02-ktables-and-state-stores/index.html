KTables and state stores

1 The story

State that survives a crash

Before you start: 9.1 Kafka Streams.

🤔 Your app counts orders per item in memory. The machine dies. Where do the counts come from on the new machine?

From Kafka itself. A KTable keeps its state in a local state store (RocksDB), and every change is also written to a compacted changelog topic. In our lab we deleted the whole local state folder, restarted, and the app restored 9 records from the changelog and answered dosa=3 idli=4 thali=2, exactly as before.

2 Definition

KTables and state stores

Formal definition (write this in exams)

A KTable is an abstraction of a changelog stream in which each record is an update (upsert) of the value for its key; a null value deletes the key. Aggregations (count, reduce, aggregate) and tables are materialized in state stores local to each task (RocksDB by default), which are made fault-tolerant by writing every update to a compacted changelog topic and restoring from it when a task starts on a new instance.

In simple words

A KTable keeps the latest value for each key, like a live tally. Kafka Streams stores it on local disk and also copies every change to a special Kafka topic, so it can be rebuilt anywhere.

Why, how, where

Why

Counting, summing, deduplicating and joining all need memory of the past. Keeping it only in RAM loses it on restart; an external database adds latency and a second system.

the problem it solves

How

Aggregations create a local state store per task. Every update is also produced to <app>-<store>-changelog (compacted). On restart or task move, the store is rebuilt from that topic. If the key changes first (groupBy), records go through a -repartition topic so all records of a key meet in one task.

the mechanism

Where

Live counters and dashboards, shopping carts, inventory, user profiles, deduplication, materialized views for microservices (queried via interactive queries).

in real systems

When not

Restoring large stores takes time: use standby replicas and persistent volumes. State is per task, so a query for a key must go to the instance that owns it.

The hidden topics

Tables at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The tally sheet

  • Each order is a tick (stream). The tally sheet shows the current total per dish (table). If the sheet is lost, you can redraw it by replaying the ticks, or faster, from a photocopy of the latest totals (the compacted changelog).

Intermediate The DSL

  • Stream–table duality: a table is the latest value per key of a stream; a table’s changes form a stream (toStream()).
  • groupByKey() keeps the key (no repartition); groupBy(...) re-keys → internal -repartition topic. Then count(), reduce(), aggregate() produce a KTable.
  • b.table("topic") reads a topic as a table; GlobalKTable gives every instance the full table (good for small lookup data).

Advanced Under the hood

  • Default store: RocksDB under state.dir, one per task; changelog topic is compacted with the same partition count as the input.
  • Record cache (statestore.cache.max.bytes, 10 MB default) batches updates; we set 0 to see every update. Downstream updates also leave on commit.
  • num.standby.replicas keeps warm copies on other instances for fast failover. Interactive queries: streams.store(...) reads local state; route remote keys with queryMetadataForKey.

Myth vs reality: things many websites still say

  • Myth: Stream state is lost on restart.
    Reality (Kafka 4.4): Rebuilt from the changelog.
    Proof: Step 5: 9 restored.
  • Myth: You need a database for counts.
    Reality (Kafka 4.4): State store + interactive queries.
    Proof: Scenario 2.
  • Myth: groupBy is free.
    Reality (Kafka 4.4): Re-keying costs a repartition topic.
    Proof: Step 2.

Exam tip: “KStream vs KTable? How is state fault tolerant?” Stream = events, table = latest per key; aggregations in local RocksDB stores per task; compacted changelog topic; restore on failover; standby replicas; groupBy re-key → repartition topic; interactive queries.

    kafka-console-consumer.sh … --topic item-counts-92 --from-beginning --formatter-property value.deserializer=…LongDeserializer
    == 3) the output topic is a changelog of the table (every update) idli=1 dosa=1 idli=2 thali=1 idli=3 dosa=2

  4. Step 4 · Restart with local state

    produce: Mumbai:dosa, Pune:thali, Delhi:idli
java -cp "out:libs/*" Kitchen92 12000
    == 4) 3 more orders, app restarted with its local state: counts continue restore item-counts from kitchen-92-item-counts-changelog-0 offsets 0..0 restored 0 records into item-counts restore item-counts from kitchen-92-item-counts-changelog-1 offsets 6..6 restored 0 records into item-counts app state RUNNING store item-counts: dosa=3 idli=4 thali=2
    The local RocksDB files were still there, so almost nothing to restore; counts continued to dosa=3, idli=4, thali=2.

  5. Step 5 · New machine

    rm -rf /tmp/kstate      # lose all local state
java -cp "out:libs/*" Kitchen92 15000
    == 5) local state deleted (new machine): store rebuilt from the changelog topic restore item-counts from kitchen-92-item-counts-changelog-0 offsets 0..0 restored 0 records into item-counts restore item-counts from kitchen-92-item-counts-changelog-1 offsets 0..9 restored 9 records into item-counts app state RUNNING store item-counts: dosa=3 idli=4 thali=2
    The store was rebuilt from the changelog: 9 records restored, same answer. This is how a task survives moving to another machine.

7 Run the code

Run the code: store + changelog

State, backup, restore. Press Run, then try the challenges.

# A KTable with a changelog, and restore after a crash
from collections import defaultdict
changelog = []                    # compacted topic (we keep all, compaction keeps last per key)
store = defaultdict(int)

def process(city, item):
    store[item] += 1
    changelog.append((item, store[item]))

for c, i in [("Mumbai","idli"),("Pune","dosa"),("Mumbai","idli"),("Delhi","thali"),("Pune","idli"),("Delhi","dosa")]:
    process(c, i)
print("store:", dict(store))

store = defaultdict(int)          # machine lost: local state gone
for k, v in changelog:            # restore
    store[k] = v
print("restored from", len(changelog), "changelog records:", dict(store))
store: {'idli': 3, 'dosa': 2, 'thali': 1} restored from 6 changelog records: {'idli': 3, 'dosa': 2, 'thali': 1}

  • for k, v in changelog: # restoreReplay keeps the latest value per key.

Lesson 9.2 in one screen

  • Aggregations → RocksDB store per task + compacted changelog.
  • groupBy re-key → repartition topic; groupByKey avoids it.

Interview and viva questions

Can I use an in-memory store?

Yes (Stores.inMemoryKeyValueStore); still backed by a changelog, but restored fully on every start.

How big can state be?

Limited by local disk per instance; RocksDB handles large stores, restore time grows with size.

Why did updates appear one by one?

We set the record cache to 0; by default caching batches updates and emits fewer.

KTable vs GlobalKTable?

KTable is partitioned; GlobalKTable copies the whole topic to every instance and supports joins on non-key fields.
