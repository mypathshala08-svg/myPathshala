What is Kafka?

Kafka is the “notice board” in the middle of modern apps: write each event once, let any number of services read it at their own pace, and replay history when needed. We prove it on a real Kafka 4.4 cluster and dissect what Kafka actually stores. All outputs are real.

The order app called the kitchen service, then billing, then the SMS service, then analytics, one after another. The SMS provider slowed down, and suddenly nobody could place an order.

Kabir

Sir, the SMS service was slow, so why did orders fail?

Arjun Sir

Because the order app was waiting for SMS. Every service was wired directly to every other one. One slow wire and the whole chain stops.

So we need something in the middle that just… holds the events?

Arjun Sir

2 Definition

What is Apache Kafka?

Formal definition (write this in exams)

Apache Kafka is an open-source, distributed event-streaming platform. It stores streams of records (events) in topics, each split into ordered, append-only, replicated partitions on a cluster of servers called brokers. Producers publish records, and consumers, organised in consumer groups, pull records at their own pace and track their position with offsets. Records are retained for a configured time or size regardless of consumption, which allows many independent readers, replay and high throughput with low latency.

In simple words

Kafka is a very fast, very safe “notice board” for events. Apps pin events on it once; any number of other apps read them whenever they want, and the events stay there for days so they can be read again.

Kafka at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The dabbawala notice board

  • Imagine a big notice board at the station. The order clerk pins a slip for every order. The kitchen, the cashier and the SMS boy each read the board and keep their own bookmark.
  • Slips are not torn off after reading, so a new helper can start from the first slip. Kafka is that board, built for millions of slips a second.

Intermediate The words

  • An event (record) is a fact: key o101, value {"status":"PAID"}, a timestamp and optional headers.
  • Events go into a named topic (order-events), which is split into partitions; each event gets an offset, its position number.
  • Producers write, consumers read, and consumers with the same group.id form a consumer group that keeps its own bookmarks (committed offsets).

Advanced What makes it different

  • Kafka is a distributed, replicated commit log: an append-only file per partition, copied to several brokers.
  • Reading does not delete. Data stays until the retention time or size is reached (7 days by default), so any number of groups can read, and re-read, independently.
  • Since Kafka 4.0 the cluster manages itself with KRaft (no ZooKeeper).

Myth vs reality: things many websites still say

  • Myth: Kafka deletes a message once it is consumed.
    Reality (Kafka 4.4): Messages stay until retention (default 7 days); any number of groups can read them.
    Proof: Step 4: 2 + 1 + 3 = 6 events still stored after two groups read them.
  • Myth: Kafka needs ZooKeeper.
    Reality (Kafka 4.4): Since Kafka 4.0 ZooKeeper is removed; KRaft controllers manage metadata.
    Proof: our 4.4 cluster runs with no ZooKeeper at all (Lesson 1.3).
  • Myth: Producers fire and forget by default.
    Reality (Kafka 4.4): Since Kafka 3.0 the default is acks=all with idempotence on.
    Proof: the dumped batch carries producerId 1000 and sequence numbers.

Exam tip: “What is Kafka?” Say: a distributed, partitioned, replicated commit log used as an event-streaming platform. Producers append records to topic partitions on brokers; consumers in groups pull and track offsets; records are retained by time/size, not deleted on read, so many consumers can read and replay independently.

Kafka is not a database you query (“give me order o101”) and not a good fit for a few messages per day. It shines when many events flow continuously and several systems need them. Also, Kafka keeps order only inside one partition, not across a whole topic (Lesson 1.4).

4 Step by step

One stream, many readers, replay

All outputs are real: Kafka 4.4.0 cluster of 3 brokers (KRaft) in Docker, Python client confluent-kafka 2.16. Topic order-events has 3 partitions. Script: lab jobs/m1/l11_events.py.

  1. Step 1 · The order app produces events

    p = Producer({"bootstrap.servers": "k1:9092,k2:9092,k3:9092"})
for oid, st, city, amt in events:
    p.produce("order-events", key=oid,
              value=json.dumps({"order": oid, "status": st, "city": city, "amount": amt}),
              callback=cb)          # cb prints partition and offset
p.flush()
    == 1) TiffinGo app produces 6 order events sent o101 PLACED -> partition 2 offset 0 sent o101 PAID -> partition 2 offset 1 sent o101 DELIVERED -> partition 2 offset 2 sent o102 PLACED -> partition 0 offset 0 sent o102 PAID -> partition 0 offset 1 sent o103 PLACED -> partition 1 offset 0
    Six events for three orders. All three events of o101 landed in partition 2 with offsets 0, 1, 2, because they share the same key: so they stay in order. The callback is Kafka’s receipt: “stored at partition X, offset Y”.

  2. Step 2 · The kitchen reads

    c = Consumer({"bootstrap.servers": BS, "group.id": "kitchen",
              "auto.offset.reset": "earliest"})
c.subscribe(["order-events"])
m = c.poll(1.0)           # pull, at the kitchen's own pace
    == 2) kitchen service reads kitchen got 6 events: o101:DELIVERED, o101:PAID, o101:PLACED, o102:PAID, o102:PLACED, o103:PLACED
    The kitchen is a consumer in group kitchen. It pulls events; Kafka never pushes. auto.offset.reset=earliest means “a new group starts from the oldest event”.

  3. Step 3 · Billing reads the same events

    read("billing")           # a different group.id
    == 3) billing service reads the SAME events independently billing got 6 events: o101:DELIVERED, o101:PAID, o101:PLACED, o102:PAID, o102:PLACED, o103:PLACED
    Billing gets all 6 again. Each consumer group has its own bookmark, so groups never steal events from each other. This is how one event serves many services.

  4. Step 4 · Reading did not delete anything

    lo, hi = c.get_watermark_offsets(TopicPartition("order-events", pt))
    == 4) events are not deleted after reading partition 0: first offset 0, next offset 2 -> 2 events still stored partition 1: first offset 0, next offset 1 -> 1 events still stored partition 2: first offset 0, next offset 3 -> 3 events still stored
    The partitions still hold 2 + 1 + 3 = 6 events after two groups read them. Kafka deletes only when retention expires (7 days by default), never because someone read the data.

  5. Step 5 · A new service replays history

    read("analytics")         # joins later, starts from the earliest offset
    == 5) a NEW analytics service joins tomorrow and replays from the start analytics got 6 events (full history)
    An analytics service that did not exist yesterday reads the full history. With a classic queue those messages would be gone. Replay is also how you fix a bug: correct the code and read again.

7 Run the code

Run the code: a topic in miniature

Kafka’s core idea in 20 lines of Python. Press Run, then try the challenges.

# A tiny model of a Kafka topic: an append-only list + one bookmark per group
log = []                       # the partition: events are only appended
bookmarks = {}                 # group.id -> next offset to read

def produce(event):
    log.append(event)
    return len(log) - 1        # the offset Kafka returns

def poll(group):
    pos = bookmarks.get(group, 0)          # new group starts at the earliest event
    batch = log[pos:]
    bookmarks[group] = len(log)            # commit the new position
    return batch

for e in ["o101 PLACED", "o102 PLACED", "o101 PAID"]:
    print("offset", produce(e), "<-", e)

print("kitchen  :", poll("kitchen"))
print("billing  :", poll("billing"))
produce("o101 DELIVERED")
print("kitchen  :", poll("kitchen"))       # only the new event
print("analytics:", poll("analytics"))     # full history
print("still stored:", len(log), "events")
offset 0 <- o101 PLACED offset 1 <- o102 PLACED offset 2 <- o101 PAID kitchen : ['o101 PLACED', 'o102 PLACED', 'o101 PAID'] billing : ['o101 PLACED', 'o102 PLACED', 'o101 PAID'] kitchen : ['o101 DELIVERED'] analytics: ['o101 PLACED', 'o102 PLACED', 'o101 PAID', 'o101 DELIVERED'] still stored: 4 events

  • print("still stored:", len(log), "events")Reading never removes events; only retention does.

9 Quiz and revision

Check yourself

Quick revision

Lesson 1.1 in one screen

  • Kafka = distributed, partitioned, replicated commit log for event streams.
  • Producer writes once; many consumer groups read independently.
  • Reading does not delete; retention (default 7 days) does.
  • Topic → partitions → offsets; same key → same partition → ordered.
  • Lab: 6 events, kitchen 6, billing 6, still stored 6, analytics replay 6.
  • Record = offset, timestamp, key, value, headers; producerId + sequence for idempotence.
  • Kafka 4.4.0 (Oct 2026), KRaft only.

Interview and viva questions

Is Kafka a message queue?

It can act like one (one consumer group sharing work, Lesson 1.2), but it is a log: messages stay after reading and many groups can read them. Kafka 4.x also adds share groups for true queue semantics (Lesson 6.1).

Why is Kafka so fast?

Sequential disk writes, batching, compression, the OS page cache and zero-copy transfer to consumers (Module 4).

Do I need Java to use Kafka?

Brokers run on Java, but clients exist for Python, Go, Node.js and others. This course uses Python clients.

Is Kafka free?

Apache Kafka is open source (Apache 2.0). Managed services such as Confluent Cloud, Amazon MSK or Aiven charge for hosting (Lesson 11.1).

What does “event streaming” mean?

Capturing events as they happen, storing them durably, and processing them continuously rather than in nightly batches.

“What is Kafka and why use it?”

Explain in one minute.

The interviewer is checking: answer?

Show a strong answer

Kafka is a distributed event-streaming platform: producers append events to topics split into partitions on brokers, and consumer groups read them independently using offsets. Events are kept for a retention period, so many services can read and replay them. It decouples services and handles very high throughput.

The interviewer is checking: fix?

  • SMS becomes a consumer group.
  • Slow SMS only increases its own lag.

Data engineeringMid-level

Queue or Kafka?

When would you not use Kafka?

The interviewer is checking: judgement?

Show a strong answer
  • Few messages per day or simple task queues: a simple queue may do.
  • Need to query current state: use a database.
  • Kafka when volume is high, many readers, or replay is needed.

Avoid: “Kafka for everything.”

PlatformSenior

Ordering

Payments for one account must be processed in order.

The interviewer is checking: design?

Show a strong answer
