2 Definition

Topics, partitions and offsets

Formal definition (write this in exams)

A topic is a named, logical stream of records divided into one or more partitions. Each partition is an ordered, immutable, append-only sequence of records, and each record in it is identified by a monotonically increasing 64-bit offset. Ordering is guaranteed only within a partition. The producer’s partitioner chooses the partition: for keyed records the default (Java) partitioner computes toPositive(murmur2(key)) % numPartitions; records with the same key therefore go to the same partition as long as the partition count is unchanged. Partitions are the unit of parallelism, replication and storage.

In simple words

A topic is split into partitions; each partition is a numbered list that only grows. The key decides which list an event joins, so events with the same key stay in order. Offsets are the numbers in each list.

Why, how, where

Why

One log on one machine cannot grow forever or be read by many workers at once. Partitions split a topic so it scales.

the problem it solves

How

The producer hashes the key (murmur2) and takes it modulo the partition count; the leader appends and assigns the next offset.

the mechanism

Where

Order IDs, user IDs, device IDs as keys; partitions as the unit of parallelism and of ordering.

in real systems

When not

Do not expect order across partitions, and do not change partition count of keyed topics casually.

Dissect the partition formula

Partitions and offsets at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Railway platforms

  • A topic is a station; partitions are its platforms. Every train for “Mumbai” always uses the same platform, so Mumbai trains leave in order.
  • An offset is a train’s serial number on its platform: 0, 1, 2 … Numbers on different platforms are unrelated.

Intermediate The rules

  • Offsets are per partition, start at 0 and only grow; they are never reused.
  • Order is guaranteed within a partition only. Consumers can start from the beginning, the end, or any offset.
  • With a key, the default partitioner uses murmur2(key) % partitions (Java client). Without a key, records are spread in “sticky” batches.

Advanced Sharp edges

  • Adding partitions changes % n, so existing keys can move (Mumbai: 1 → 4), breaking per-key order across the change. Partitions can never be reduced.
  • Different client libraries can use different default partitioners: librdkafka’s default (consistent_random, CRC32) differs from Java’s murmur2, so set partitioner=murmur2_random when Python and Java produce to the same keyed topic.
  • Few or skewed keys create hot partitions that limit throughput.

Myth vs reality: things many websites still say

  • Myth: Without a key, Kafka picks a random partition for every message.
    Reality (Kafka 4.4): Since Kafka 2.4 the producer uses sticky partitioning: it fills a batch for one partition, then switches.
    Proof: keyless sends are covered with real batches in Lesson 2.2.
  • Myth: Kafka keeps the whole topic in order.
    Reality (Kafka 4.4): Order is guaranteed only within a partition.
    Proof: Step 2: offsets restart at 0 in every partition.
  • Myth: You can reduce partitions later.
    Reality (Kafka 4.4): Partitions can only be increased.
    Proof: Step 6: InvalidPartitionsException.

Exam tip: “How does Kafka decide the partition and guarantee order?” Keyed records: hash(key) % partitions (murmur2 in the Java client), so same key → same partition → ordered by offset. No key: sticky/round-robin spreading. Order holds only within a partition, and increasing partitions remaps keys.

echo "Mumbai:o11" | kafka-console-producer.sh ...

7 Run the code

Run the code: the partitioner

The same function our lab matched against the real broker. Press Run, then try the challenges.

# Kafka's default (Java) partitioner, in pure Python
def murmur2(data):
    m, h = 0x5bd1e995, (0x9747b28c ^ len(data)) & 0xffffffff
    n = len(data) // 4
    for i in range(n):
        k = int.from_bytes(data[4*i:4*i+4], "little")
        k = (k * m) & 0xffffffff; k ^= k >> 24; k = (k * m) & 0xffffffff
        h = ((h * m) & 0xffffffff) ^ k
    rest = data[4*n:]
    if len(rest) == 3: h ^= rest[2] << 16
    if len(rest) >= 2: h ^= rest[1] << 8
    if len(rest) >= 1: h = ((h ^ rest[0]) * m) & 0xffffffff
    h ^= h >> 13; h = (h * m) & 0xffffffff; h ^= h >> 15
    return h

def partition(key, n):
    return (murmur2(key.encode()) & 0x7fffffff) % n

for city in ["Mumbai", "Pune", "Delhi", "Chennai"]:
    print(city, "-> 3 partitions:", partition(city, 3), "| 6 partitions:", partition(city, 6))
Mumbai -> 3 partitions: 1 | 6 partitions: 4 Pune -> 3 partitions: 0 | 6 partitions: 3 Delhi -> 3 partitions: 0 | 6 partitions: 3 Chennai -> 3 partitions: 0 | 6 partitions: 0

  • print(city, "-> 3 partitions:", partition(city, 3), "| 6 partitions:", partition(city, 6))Change n and keys can move.

9 Quiz and revision

Check yourself

Quick revision

Lesson 1.4 in one screen

  • Topic → partitions (ordered, append-only) → offsets (per partition, from 0).
  • Keyed: toPositive(murmur2(key)) % n (Java); same key → same partition.
  • Lab: Mumbai → P1 (o1,o4,o7,o10), others → P0, P2 empty.
  • Seek: --partition 1 --offset 2 → o7, o10.
  • 3 → 6 partitions: Mumbai → P4; order broken across change; never reduce.
  • librdkafka default partitioner differs; use murmur2_random for compatibility.

Interview and viva questions

How many partitions should a topic have?

Enough for peak consumer parallelism and throughput with headroom; too many add overhead. Lesson 10.2 gives a method.

Do offsets ever reset to 0?

No. Offsets keep growing; old records are deleted by retention, so the first available offset (log start offset) rises.

What if I send no key?

The producer spreads records using sticky partitioning: it fills a batch for one partition, then switches. Good spread, no ordering.

Is offset a byte position?

No, it is a record number. The broker’s .index file maps offsets to byte positions in the log (Lesson 4.2).

Real-world scenario questions (asked in company interviews)

Partitioning questions are interview favourites.

Any company · dataFresher

“What is an offset?”

Define it precisely.

The interviewer is checking: answer?

Show a strong answer

A per-partition, increasing number that identifies each record’s position. Consumers track the next offset to read; offsets are never reused, and order is guaranteed only within a partition.

Avoid: “A byte position in the topic.”

E-commerceMid-level

Ordering bug

Status updates of an order arrive out of order.

The interviewer is checking: diagnose?

Show a strong answer
  • Check the key: must be order_id.
  • Check for a recent partition increase.
  • Check mixed clients with different partitioners.

Avoid: “Kafka does not guarantee order.”

Data engineeringMid-level

Hot partition

One consumer lags while others idle.

The interviewer is checking: fix?

Show a strong answer
  • Inspect key distribution.
  • Use a higher-cardinality key or a compound key.
  • Salting only if per-key order is not needed.

Avoid: Adding consumers.

PlatformSenior

Changing partitions

A keyed topic must go from 12 to 48 partitions.

The interviewer is checking: plan?

Show a strong answer
  1. Create a new topic with 48 partitions.
  2. Dual-write or mirror, then switch consumers after draining.
  3. Or accept remap if per-key order across the switch is not needed.

Avoid: “Just alter it at peak time.”
