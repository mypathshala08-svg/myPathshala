Messaging models: queue vs pub-sub

2 Definition

Messaging models

Formal definition (write this in exams)

In point-to-point (queue) messaging each message is consumed by exactly one of the competing consumers, distributing work. In publish-subscribe messaging each message is delivered to every subscriber. Kafka generalises both through consumer groups: within a group, each partition is assigned to one member, so members share the load (queue semantics); across groups, every group independently receives all records (pub-sub semantics). Kafka 4.x additionally provides share groups, where multiple consumers cooperatively consume from the same partitions with per-record acknowledgement.

In simple words

Same group = share the work. Different groups = everyone gets a full copy. One Kafka topic can do both at the same time.

Why, how, where

Why

Some work must be done once (deliver an order); some news must reach everyone (order placed). Systems need both.

the problem it solves

How

Same group.id → partitions split among members. Different group.ids → each group reads all partitions with its own offsets.

the mechanism

Where

Worker pools (riders, email senders) and fan-out to many services (SMS, analytics, fraud).

in real systems

When not

Classic groups cannot use more workers than partitions, and cannot ack one record at a time: use share groups or retry topics.

Dissect the group assignment

Messaging models at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Two kinds of announcements

  • Queue: a token counter. Each token is served by one free counter clerk. Work is divided.
  • Pub-sub: a railway announcement. Everyone on the platform hears every message.

Intermediate How Kafka maps them

  • Queue = many consumers, one group.id. Each partition is given to one consumer in the group.
  • Pub-sub = several different group ids. Each group reads every partition with its own offsets.
  • Both at once is normal: riders shares work while sms and analytics each get everything.

Advanced Limits and the new queue

  • In a classic consumer group a partition has at most one consumer, so parallelism ≤ number of partitions; extra consumers sit idle.
  • Kafka 4.x adds share groups (KIP-932): many consumers can share one partition, with per-record acknowledgement and redelivery, like a traditional queue (Lesson 6.1). In our 4.4 cluster the feature is enabled (share.version=2).

Myth vs reality: things many websites still say

  • Myth: Kafka is only pub-sub, not a queue.
    Reality (Kafka 4.4): One consumer group behaves like a queue; Kafka 4.x also has share groups.
    Proof: Step 1: 12 orders delivered once across 3 riders.
  • Myth: More consumers always means more speed.
    Reality (Kafka 4.4): In a classic group, consumers beyond the partition count are idle.
    Proof: Step 3: r4 received 0 orders.
  • Myth: Every group gets a copy of the data on disk.
    Reality (Kafka 4.4): There is one copy of each partition; groups only store offsets.
    Proof: __consumer_offsets holds the bookmarks (Lesson 1.3).

Exam tip: “How does Kafka support both queue and pub-sub?” Consumers with the same group.id split the partitions (each record to one member); consumers in different groups each receive all records. Parallelism inside a group is limited by the partition count. Kafka 4.x share groups add queue semantics with per-record acks.

Adding consumers beyond the partition count does not speed up a classic group: in our lab the 4th rider received 0 orders. Plan partitions for your maximum parallelism. Also, with keyed data, one partition can get far more work than others (rider-C had 6 orders, rider-B only 2).

6 Real-world use

Both models at work

1. Dispatch workers

A pool of dispatch workers shares ride requests in one group.

Requests→one group→Each once

2. Payment fan-out

Ledger, SMS and fraud each subscribe with their own group.

Payments→many groups→All services

Email workers share a topic; scaling is limited by partitions.

Email jobs→group→Sent once

Alerts and storage read the same sensor stream independently.

Sensors→fan-out→Alerts + lake

7 Run the code

Run the code: assignment and fan-out

The rule behind the lab in a few lines. Press Run, then try the challenges.

# Assign partitions to consumers of one group (round-robin), then fan out to groups
partitions = {0: ["o4", "o5", "o7", "o9"], 1: ["o1", "o10"], 2: ["o2", "o3", "o6", "o8", "o11", "o12"]}

def assign(consumers):
    owned = {c: [] for c in consumers}
    for p in partitions:
        owned[consumers[p % len(consumers)]].append(p)
    return owned

def orders(parts):
    return [o for p in parts for o in partitions[p]]

group = assign(["rider-A", "rider-B", "rider-C", "rider-D"])
for c, parts in group.items():
    print(c, parts, len(orders(parts)), "orders")

for g in ["sms", "analytics"]:          # each group reads everything
    print(g, "gets", len(orders(partitions)), "orders")

9 Quiz and revision

Check yourself

Quick revision

Lesson 1.2 in one screen

  • Queue: each message to one consumer. Pub-sub: each message to all subscribers.
  • Kafka: same group.id = share partitions; different groups = full copies.
  • Lab: riders 4 + 2 + 6 = 12 once; sms 12, analytics 12; r4 idle with 0.
  • Parallelism in a group ≤ partitions.
  • Share groups (4.x): many consumers per partition, per-record ack.

Interview and viva questions

Does each group store a copy of the data?

No. There is one copy of each partition (plus replicas). Groups only store their offsets in the __consumer_offsets topic.

Can one consumer belong to several groups?

A consumer instance has one group.id. A service that needs two views runs two consumers.

Why not one partition per consumer always?

Partitions also cost broker resources and affect ordering; choose based on peak parallelism and throughput (Lesson 10.2).

Are share groups production-ready?

They are enabled in our Kafka 4.4 cluster (share.version 2). Check the release notes of your version and managed service before relying on them; Lesson 6.1 covers them in depth.

Real-world scenario questions (asked in company interviews)

Questions about queues, pub-sub and groups.

Any company · backendFresher

“Queue vs pub-sub?”

Explain both and Kafka’s approach.

The interviewer is checking: answer?

Show a strong answer

A queue delivers each message to one of several competing consumers; pub-sub delivers each message to all subscribers. Kafka uses consumer groups: members of one group split the partitions (queue), and each group gets all messages (pub-sub).

Avoid: Mixing up group and topic.

E-commerceFresher

Duplicate processing

Every order email is sent twice after scaling to 2 pods.

The interviewer is checking: cause?

Show a strong answer
  • Pods use different group.ids.
  • Use one group.id per service.

Avoid: Adding a dedup table first.

Data engineeringMid-level

Scaling limit

Adding consumers does not reduce lag.

The interviewer is checking: diagnose?

Show a strong answer
  • Consumers ≥ partitions: extras idle.
  • Increase partitions (keys remap) or speed up processing.
  • Check for a hot partition.

Avoid: “Add more consumers.”

PlatformSenior

Queue semantics

A team wants a job queue with per-message retry on Kafka.

The interviewer is checking: options?

Show a strong answer
  • Kafka 4.x share groups with acks and delivery count.
  • Or classic group + retry topic + DLQ (Lesson 6.2).
  • Or a dedicated queue system if volume is low.

Avoid: “Kafka cannot do queues.”
