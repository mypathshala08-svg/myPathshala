2 Definition

Kafka architecture

Formal definition (write this in exams)

A Kafka cluster consists of brokers that store topic partitions as replicated logs, and a controller quorum that manages cluster metadata using the KRaft protocol (Raft-based consensus, mandatory since Kafka 4.0). Each partition has a replication factor; one replica is the leader, serving produce and fetch requests, and the others are followers that replicate from it. Clients (producers, consumers, admin tools, Connect, Streams) discover leaders through the Metadata API and communicate with brokers over a versioned binary protocol on TCP.

In simple words

Kafka is a team of servers. Each partition is copied to several servers; one copy is in charge and the rest follow. A small built-in committee keeps track of who is in charge and replaces a failed leader automatically.

Why, how, where

Why

One server can fail or fill up. A cluster spreads partitions and keeps copies so no single machine matters.

the problem it solves

How

Brokers store partition replicas; one replica leads, others follow. A Raft quorum of controllers stores the cluster metadata and moves leadership on failure.

the mechanism

Where

Every Kafka deployment: on-premise, Kubernetes, and managed services such as Amazon MSK or Confluent Cloud.

in real systems

When not

A single broker is fine for learning, never for production: no copies, no failover.

Zoom in, layer by layer

Dissect a broker’s disk

Architecture at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A dabbawala network

  • Three stations (brokers) each keep a copy of every route book (partition). For each route one station is in charge (leader); the others copy its updates (followers).
  • A small committee (controllers) decides who is in charge. If a station closes, the committee picks another one at once.

Intermediate The parts

  • Broker: a server that stores partition replicas and serves clients. Cluster: brokers sharing one cluster.id.
  • Leader replica handles all reads and writes of a partition; followers fetch from it. Copies that are up to date form the ISR (in-sync replicas).
  • Controllers (KRaft) keep the metadata: topics, partitions, leaders, configs. In our lab each node is broker and controller (“combined mode”).

Advanced Under the hood

  • Metadata is itself a replicated log, __cluster_metadata, managed with the Raft consensus algorithm; one controller is the active leader (our lab: node 3, epoch 2).
  • Consumer offsets live in the internal topic __consumer_offsets (50 partitions by default); share-group state in __share_group_state.
  • Clients talk to brokers over a binary TCP protocol with versioned APIs (Produce, Fetch, Metadata …).

Myth vs reality: things many websites still say

  • Myth: ZooKeeper stores offsets and elects leaders.
    Reality (Kafka 4.4): Offsets live in __consumer_offsets; KRaft controllers elect leaders.
    Proof: Step 1 (quorum) and Step 3 (internal topics).
  • Myth: Brokers are stateless.
    Reality (Kafka 4.4): Brokers store partition data on disk; only metadata is handled by controllers.
    Proof: Step 4: 117 partition folders on one broker.
  • Myth: Producers ask ZooKeeper for broker IDs.
    Reality (Kafka 4.4): Clients get metadata from any broker via the Metadata API.
    Proof: the “find the leader” peel animation below.

Exam tip: “Explain Kafka architecture.” Brokers form a cluster and store partitions; each partition is replicated (RF) with one leader and followers; the ISR is the set of caught-up replicas. Since 4.0, KRaft controllers (a Raft quorum) store metadata in __cluster_metadata and handle leader election, replacing ZooKeeper. Clients bootstrap, fetch metadata, then talk directly to partition leaders.

6 Real-world use

Architecture choices in practice

1. Managed clusters

Cloud services run brokers and controllers for you; you choose brokers and storage (Lesson 11.1).

You→managed Kafka→Topics

2. Kafka on Kubernetes

Operators such as Strimzi run brokers and controllers as pods with rolling upgrades.

YAML→operator→Cluster

3. Multi-zone clusters

Replicas spread across availability zones (rack awareness) so a zone outage loses no data.

Brokers are restarted one at a time; ISR checks gate each step.

7 Run the code

Run the code: failover in miniature

The rule behind the lab’s failover. Press Run, then try the challenges.

# Leader failover in miniature
replicas = {"P0": [2, 3, 1], "P1": [3, 1, 2], "P2": [1, 2, 3]}   # first = preferred leader
alive = {1, 2, 3}

def leaders():
    return {p: next(b for b in r if b in alive) for p, r in replicas.items()}

def isr():
    return {p: [b for b in r if b in alive] for p, r in replicas.items()}

print("normal  :", leaders())
alive.discard(1)                          # docker stop k1
print("k1 down :", leaders(), isr()["P2"])
alive.add(1)                              # docker start k1
print("k1 back :", leaders())
normal : {'P0': 2, 'P1': 3, 'P2': 1} k1 down : {'P0': 2, 'P1': 3, 'P2': 2} [2, 3] k1 back : {'P0': 2, 'P1': 3, 'P2': 1}
  • return {p: next(b for b in r if b in alive) for p, r in replicas.items()}The first live replica in the list leads (the preferred leader when all are up).
  • alive.discard(1) # docker stop k1Broker 1 disappears: P2 moves to broker 2.

Interview and viva questions

Is ZooKeeper still needed?

No. Kafka 4.0 removed ZooKeeper; clusters must use KRaft. Older 3.x clusters migrate before upgrading (Lesson 5.4).

Do consumers read from followers?

By default consumers read from leaders. Kafka also supports fetching from the closest replica (rack-aware fetching) to save cross-zone traffic.

How fast is failover?

Usually a few seconds in a healthy cluster, depending on session timeouts and client retries; in our lab the new leader was in place within the 12 seconds we waited.

What is a bootstrap server?

Any broker address the client uses for its first Metadata request. List two or three so startup works even if one is down.

Real-world scenario questions (asked in company interviews)

Architecture questions interviewers ask.

Any company · dataFresher

“Explain Kafka architecture.”

Name the parts and how they relate.

The interviewer is checking: answer?

Show a strong answer

A cluster of brokers stores topic partitions; each partition is replicated with one leader and followers; the ISR is the caught-up set. KRaft controllers (since 4.0, replacing ZooKeeper) hold metadata and elect leaders. Clients bootstrap, get metadata, and talk directly to leaders.

Avoid: Describing ZooKeeper as current.

PlatformMid-level

Broker failure

A broker died. What happens to producers?

The interviewer is checking: answer?

Show a strong answer
  • Controllers elect new leaders from the ISR.
  • Producers get NOT_LEADER errors, refresh metadata and retry.
  • With RF 3 and acks=all no acknowledged data is lost.

Avoid: “Data on that broker is lost.”

PlatformMid-level

Patching

How do you upgrade brokers without downtime?

The interviewer is checking: steps?

Show a strong answer
  1. One broker at a time.
  2. Wait until ISR is full and no under-replicated partitions.
  3. Preferred leaders rebalance automatically.

Avoid: Restarting all brokers together.

PlatformSenior

Control plane

Design the controller setup for 40 brokers across 3 zones.

The interviewer is checking: design?

Show a strong answer
  • 3 or 5 dedicated controllers, one per zone (5 to survive 2 failures).
  • broker.rack per zone for replica placement.
  • Monitor quorum lag and active controller changes.

Avoid: Even number of controllers.
