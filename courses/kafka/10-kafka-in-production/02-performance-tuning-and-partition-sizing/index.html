1 The story

Faster without more brokers

Before you start: 10.1 Monitoring.

🤔 Same cluster, same data, same acks=all. One setting change took the producer from 16 MB/s to 64 MB/s. Which one, and why did compression make it slower?

Bigger batches and a little linger: 16.1 → 64.4 MB/s and average latency 1,727 → 212 ms. Then lz4 compression lowered throughput to 53 MB/s on our CPU-bound single VM, and bigger consumer fetches did not help either. Tuning is about finding your bottleneck, so we measure each change one at a time and size partitions with arithmetic, not guesses.

2 Definition

Performance tuning and partition sizing

Formal definition (write this in exams)

Performance tuning is the iterative process of identifying the limiting resource (client CPU, network, broker request handling, disk, replication) and adjusting producer, consumer, broker and OS settings to meet throughput and latency targets. Partition sizing chooses a partition count from measured per-partition throughput and the required consumer parallelism, balancing it against the per-partition overhead.

In simple words

Measure how fast things are, find what is slowest, change one setting, and measure again. Pick the number of partitions with simple arithmetic from how much data you have and how many consumers you want.

Why, how, where

Why

Defaults favour safety and moderate latency. At scale, a few settings decide whether you need 6 brokers or 20, and the wrong partition count is hard to undo (changing it re-maps keys).

the problem it solves

How

Measure with kafka-producer-perf-test and kafka-consumer-perf-test, read broker idle % and latencies, change one variable, measure again. Producer throughput comes from fewer, bigger requests; consumer throughput from parallel partitions; partitions from target MB/s and desired consumer parallelism.

the mechanism

Where

Capacity planning for launches and sales days, cost reduction, fixing latency SLO misses, choosing partition counts for new topics.

in real systems

When not

Every gain has a price: linger adds latency, compression costs CPU, more partitions cost memory, file handles, longer failovers and more metadata.

Sizing in one picture

Tuning at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Loading a truck

  • Sending each parcel on its own scooter is slow. Waiting a moment to fill a truck (linger, batch size) moves far more per trip. Shrinking parcels (compression) helps only if packing them does not take longer than driving.

Intermediate The knobs

  • Producer: batch.size (16 KB default), linger.ms (5 ms default since Kafka 4.0), compression.type (zstd/lz4), acks, buffer.memory, max.in.flight.requests.per.connection (≤ 5 with idempotence).
  • Consumer: fetch.min.bytes, fetch.max.wait.ms, max.partition.fetch.bytes, max.poll.records; and more consumers up to the partition count.
  • Broker: num.network.threads, num.io.threads, num.replica.fetchers, disks (JBOD/RAID), and the OS page cache (Kafka relies on it; don’t give the JVM all the RAM).

Advanced Partition sizing

  • partitions ≥ max(target MB/s ÷ producer MB/s per partition, target MB/s ÷ consumer MB/s per partition, desired consumer instances). Measure per-partition rates on your hardware; plan for 1–2 years of growth.
  • Costs of many partitions: more open files and memory, more replication fetches, longer leader elections and restarts, more metadata. KRaft raised cluster limits a lot, but per-broker counts in the low thousands are still a common guideline.
  • Adding partitions later changes key → partition mapping (ordering per key breaks across the change); plan keyed topics generously.

Myth vs reality: things many websites still say

  • Myth: Compression is always faster.
    Reality (Kafka 4.4): It costs CPU; on our VM lz4 was slower.
    Proof: Step 1.
  • Myth: More partitions are always better.
    Reality (Kafka 4.4): They cost memory, files and failover time.
    Proof: Scenario 2.
  • Myth: Bigger fetches always help consumers.
    Reality (Kafka 4.4): Not if processing is the limit.
    Proof: Step 3.

Exam tip: “How do you tune Kafka?” Measure with perf tools; producer batch.size/linger/compression/acks; consumer fetch sizes and parallelism; broker threads, disks, page cache; partitions = max(MB/s ÷ per-partition rates, consumers); one change at a time.

4 Step by step

One knob at a time

All outputs are real: Kafka 4.4.0, 3 brokers on one VM, 200,000 × 1 KB records, acks=all.

  1. Step 1 · Producer knobs

    kafka-producer-perf-test.sh --topic perf-12p --num-records 200000 --record-size 1000 --throughput -1 \
  --producer-props bootstrap.servers=k1:9092 acks=all batch.size=262144 linger.ms=20 [compression.type=lz4]
    == 1) producer: 200,000 x 1 KB, acks=all, one variable at a time (topic with 12 partitions) defaults (linger 5 ms, batch 16 KB, none): 16856.300042 records/sec (16.08 MB/sec), 1727.35 ms avg latency, 4130.00 ms max latency batch.size 256 KB + linger 20 ms: 67499.156261 records/sec (64.37 MB/sec), 211.52 ms avg latency, 597.00 ms max latency + compression lz4: 55648.302727 records/sec (53.07 MB/sec), 240.19 ms avg latency, 790.00 ms max latency
    Bigger batches and 20 ms linger: 4× throughput and 8× lower average latency (less queueing). lz4 cost more CPU than it saved here.

  2. Step 2 · Partitions

    same tuned producer → topic perf-1p (1 partition) vs perf-12p (12 partitions)
    == 2) partitions: same tuned producer, 1 partition vs 12 1 partition: 42372.881356 records/sec (40.41 MB/sec), 559.25 ms avg latency, 953.00 ms max latency 12 partitions: 65638.332786 records/sec (62.60 MB/sec), 88.48 ms avg latency, 435.00 ms max latency
    One partition = one leader and one batch queue: 40 MB/s. Twelve spread over 3 brokers: 63 MB/s and much lower latency.

  3. Step 3 · Consumer fetches

    kafka-consumer-perf-test.sh --bootstrap-server k1:9092 --topic perf-12p --messages 200000 [--command-config big-fetch.properties]
    == 3) consumer: read 200,000 records, default fetch vs bigger fetches defaults: 47.2376 MB/s, 49532.1942 msg/s, fetch time 303.7346 ms fetch.min.bytes 1 MB, max.partition.fetch 4 MB: 43.9992 MB/s, 46136.4787 msg/s, fetch time 195.8775 ms
    Bigger fetches did not raise throughput here: the single consumer thread was the limit. The fix for consumers is usually more consumers (up to partitions), or faster processing.

7 Run the code

Run the code: size partitions

The sizing formula. Press Run, then try the challenges.

# Partition sizing from measured rates
import math
target_mb_s = 60
produce_per_partition = 10     # measured MB/s
consume_per_partition = 5      # measured MB/s
consumers_wanted = 8
growth = 1.5                   # plan for 18 months

need = max(target_mb_s * growth / produce_per_partition,
           target_mb_s * growth / consume_per_partition,
           consumers_wanted)
print("partitions:", math.ceil(need))
partitions: 18

  • Lab: 16.08 → 64.37 MB/s (batch+linger); lz4 53.07; 1p 40.41 vs 12p 62.60; fetch no gain.

Interview and viva questions

Is acks=1 a tuning knob?

It lowers latency but risks data loss; tune batching first and keep acks=all for important data.

How big should the JVM heap be?

Often 6–8 GB for brokers; leave the rest of RAM to the page cache.

Which compression is best?

zstd usually compresses best, lz4 is fastest; measure with your data.

Can I reduce partitions?

No; you must create a new topic and migrate.
