1 The story

Is Kafka OK right now?

Before you start: 3.3 Lag.

🤔 Your consumer says it has received all 30,000 orders, yet the dashboard says it is 9,000 behind. Which one is lying?

Neither. Consumer lag is measured from committed offsets, while the client had already prefetched everything into memory. In our lab we produced 30,000 orders, ran a slow consumer, watched lag fall from 9,626 to 8,980, read broker health over JMX, paused a broker and saw UnderReplicatedPartitions jump from 0 to 3 and back.

2 Definition

Monitoring and consumer lag

Formal definition (write this in exams)

Kafka monitoring collects broker, controller and client metrics (exposed through JMX MBeans and client metric APIs) to track availability, throughput, latency and resource use. Consumer lag for a group and partition is the difference between the partition’s log-end offset and the group’s committed offset; it measures unprocessed (uncommitted) data, not data fetched by the client.

In simple words

Watch a few numbers: copies missing (URP), partitions with no leader (offline), exactly one controller, and how far each consumer group is behind (lag). Lag counts what has not been committed yet.

Why, how, where

Why

Kafka rarely fails loudly. A slow consumer, a lagging follower or a full disk shows up first as a number drifting. Watching the right numbers turns 2 a.m. outages into daytime tickets.

the problem it solves

How

Brokers expose metrics as JMX MBeans (e.g. kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions); clients expose their own metrics; lag = log-end offset − committed offset per partition, from kafka-consumer-groups or the Admin API. An exporter scrapes them into Prometheus/Grafana or your vendor’s monitoring.

the mechanism

Where

Every production cluster: on-call dashboards, SLOs for “orders processed within 1 minute”, capacity planning, and incident diagnosis.

in real systems

When not

Too many metrics hide the important ones. Lag in messages means little without throughput: 10,000 behind at 10,000/s is 1 s; at 50/s it is over 3 minutes.

Dissect a metric name

Monitoring at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A hospital ward

  • Nurses don’t read every chart; they watch pulse, oxygen and temperature. For Kafka: under-replicated partitions, offline partitions, one active controller, and consumer lag.

Intermediate The core metrics

  • Cluster: UnderReplicatedPartitions (should be 0), OfflinePartitionsCount (0), ActiveControllerCount (exactly 1 across the cluster), UncleanLeaderElectionsPerSec (0), under-min-ISR partitions.
  • Load: MessagesInPerSec, BytesIn/OutPerSec, RequestHandlerAvgIdlePercent and NetworkProcessorAvgIdlePercent (alert when below ~0.3), request latencies (Produce/Fetch TotalTimeMs p99).
  • Consumers: lag per group and partition (end − committed), plus records-lag-max in the client; better, lag converted to seconds.

Advanced Doing it well

  • Collect with a JMX exporter (Prometheus) or vendor agent; Kafka 4.x also supports client telemetry push (KIP-714) to the broker.
  • Alert on symptoms users feel (lag in seconds, URP for > 5 min, offline > 0), not on every metric. Add disk usage and growth (kafka-log-dirs), and ISR shrink/expand rates.
  • Lag tools (Burrow, Kafka Lag Exporter, vendor UIs) evaluate trends: lag rising while the consumer is “up” means it is too slow or stuck.

Myth vs reality: things many websites still say

  • Myth: Received means processed.
    Reality (Kafka 4.4): Lag counts committed offsets; clients prefetch.
    Proof: Step 2: rx 30,000, committed 733.
  • Myth: Every broker should report ActiveControllerCount 1.
    Reality (Kafka 4.4): Only the active one; the sum is 1.
    Proof: Step 3.
  • Myth: ISR shrink metrics catch every lost replica.
    Reality (Kafka 4.4): Fencing removes replicas too; watch URP.
    Proof: Step 4.

Exam tip: “How do you monitor Kafka?” Broker JMX: URP, offline partitions, active controller, request idle %, latencies, bytes in/out; consumer lag = end − committed per partition, convert to time; disk usage; exporters + alerts on symptoms.

    docker run … -e JMX_PORT=9101 apache/kafka:4.4.0

    == 3) broker metrics over JMX (broker 1) MessagesInPerSec (1-min rate): 103.03880788826503 BytesInPerSec (1-min rate): 20226.461590897226 UnderReplicatedPartitions: 0 ActiveControllerCount: 0 OfflinePartitionsCount: 0 RequestHandlerAvgIdlePercent: 0.9885573138049444 NetworkProcessorAvgIdlePercent: 1.0 Produce TotalTimeMs p99: 23.960000000000036
    All healthy: no URP, no offline partitions, request handlers 99% idle. ActiveControllerCount 0 on broker 1 is correct: the active controller is node 2 (Lesson 5.4); the sum across nodes must be 1.

  4. Step 4 · Break it

    docker pause k3; sleep 14   # then read URP; docker unpause k3
    == 4) break something: pause broker 3, watch the alert metric UnderReplicatedPartitions (k3 paused): 3 IsrShrinksPerSec count: 0 UnderReplicatedPartitions (k3 back): 0
    URP went to 3 and back to 0. IsrShrinksPerSec stayed 0 on broker 1: k3 left the ISR by controller fencing (Lesson 5.2), not by a leader-driven shrink, so watch URP, not only shrink rates.

  5. Step 5 · Disk

    kafka-log-dirs.sh --bootstrap-server k1:9092 --describe --topic-list orders-101
    == 5) disk per broker for the topic (kafka-log-dirs) broker 1: 6.40 MB in 3 partitions broker 2: 6.40 MB in 3 partitions broker 3: 6.40 MB in 3 partitions
    6.4 MB of 200-byte orders on each broker (RF 3 = three equal copies).

7 Run the code

Run the code: lag

Lag the way the tools compute it. Press Run, then try the challenges.

# Consumer lag per partition, and lag in time
end       = {0: 10447, 1: 9840, 2: 9713}
committed = {0: None,  1: None, 2: 733}
rate = 50                                  # records/s the group processes

for p in end:
    if committed[p] is None:
        print(f"p{p}: no committed offset yet ('-')")
        continue
    lag = end[p] - committed[p]
    print(f"p{p}: lag {lag} records = {lag / rate / 60:.1f} minutes behind")
p0: no committed offset yet ('-') p1: no committed offset yet ('-') p2: lag 8980 records = 3.0 minutes behind
  • lag = end[p] - committed[p]Lag = log end − committed.
  • print(f"p{p}: lag {lag} records = {lag / rate / 60:.1f} minutes behind")Convert to time for alerts.

9 Quiz and revision

Check yourself

Quick revision

Lesson 10.1 in one screen

  • Lag = end − committed; prefetched ≠ processed.
  • Core broker metrics: URP, offline, active controller (sum 1), idle %, p99 latencies.
  • Lab: lag 9,626 → 8,980; URP 0 → 3 → 0 with k3 paused; 6.4 MB per broker.
  • Alert on lag in time and stuck commits, URP for minutes, offline > 0.
  • JMX exporter → Prometheus/Grafana; KIP-714 client metrics.

Interview and viva questions

How do I enable JMX?

Set JMX_PORT (and KAFKA_JMX_OPTS) for the broker process; unset it for CLI tools in the same container.

What about consumers that commit rarely?

Lag looks high between commits; use processing metrics too.

Which tools show lag?

kafka-consumer-groups, Admin API, Burrow, Kafka Lag Exporter, vendor consoles.

Share groups lag?

Kafka 4.2 added share-partition lag metrics (KIP-1226).
