Round-robin over brokers, shifting the starting point for each partition, so no two copies of a partition share a broker and leaders are spread out. Let’s create a topic, count, and then move a partition by hand.

2 Definition

Brokers and replication

Formal definition (write this in exams)

Each partition is replicated to replication.factor brokers. The ordered replica list is chosen by the controller at topic creation (round-robin with shifted starting points, rack-aware when broker.rack is set) or given explicitly; the first replica is the preferred leader. The leader handles all produce and fetch requests; followers replicate by fetching from the leader. Replica placement can be changed online with kafka-reassign-partitions, which adds new replicas, waits for them to catch up, and removes old ones.

In simple words

Kafka keeps several copies of each partition on different brokers. One copy is in charge (leader); the others keep copying it. Kafka spreads copies and leaders evenly when you create a topic, and you can move copies later with a reassignment.

Why, how, where

Why

A single copy dies with its disk. Several copies on different machines (and racks) keep data safe and readable through failures.

the problem it solves

How

Each partition has replication.factor replicas on different brokers; the first live one in the list leads, the others fetch from it. The controller places replicas and you can move them with kafka-reassign-partitions.

the mechanism

Where

Every production topic (RF 3 is standard); multi-zone clusters with broker.rack; adding brokers and moving load.

in real systems

When not

RF cannot exceed the number of brokers; replicas cost disk and network (RF 3 = 3× storage).

Dissect a partition line

Replication at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Photocopies in three branches

  • Every important register is copied to three branch offices. One branch is “in charge” of writing in it; the others copy its new pages. If that branch closes, another one takes charge.

Intermediate The rules

  • replication.factor (topic setting; broker default default.replication.factor, 1 unless changed) = number of copies.
  • The replica list order matters: the first replica is the preferred leader. Followers send Fetch requests to the leader, like consumers.
  • Placement: round-robin with a shifting start so leaders and followers spread evenly; with broker.rack set, copies go to different racks/zones.

Advanced Moving and balancing

  • kafka-reassign-partitions.sh: generate or write a JSON plan, --execute, then --verify (which also clears throttles). New replicas copy data, join the ISR, and old ones are removed.
  • Use --throttle (bytes/s) to protect production traffic while copying large partitions.
  • Reassignment does not change the leader immediately: run a preferred-leader election (Lesson 5.3). Tools such as Cruise Control automate balancing.

Myth vs reality: things many websites still say

  • Myth: Adding brokers rebalances data automatically.
    Reality (Kafka 4.4): Partitions stay until you reassign them.
    Proof: Step 4 was a manual move.
  • Myth: Followers are pushed data by the leader.
    Reality (Kafka 4.4): Followers pull with Fetch requests, like consumers.
    Proof: Peel animation.
  • Myth: Reassignment also moves leadership.
    Reality (Kafka 4.4): Leadership changes only on election.
    Proof: Step 4: leader stayed 1.

Exam tip: “How does Kafka replication work?” Each partition has RF replicas on different brokers; first replica = preferred leader; leader serves reads/writes, followers fetch; placement round-robin and rack-aware; move replicas with kafka-reassign-partitions (execute, verify, throttle).

7 Run the code

Run the code: placing replicas

A simplified version of Kafka’s placement. Press Run, then try the challenges.

# Kafka-style replica placement: round-robin with a shifting start
def place(partitions, brokers, rf):
    plan = {}
    for p in range(partitions):
        first = p % len(brokers)
        shift = (p // len(brokers)) % (len(brokers) - 1) + 1     # vary follower order
        replicas = [brokers[first]]
        for k in range(1, rf):
            replicas.append(brokers[(first + k * shift) % len(brokers)])
        plan[p] = replicas
    return plan

plan = place(6, [1, 2, 3], 3)
for p, r in plan.items():
    print(f"P{p}: replicas {r}  preferred leader {r[0]}")
from collections import Counter
print("leaders per broker:", dict(Counter(r[0] for r in plan.values())))

Interview and viva questions

Can I change RF of an existing topic?

Yes, with a reassignment plan that lists more (or fewer) replicas per partition.

Do followers serve consumers?

By default no; with rack-aware fetching (client.rack + replica.selector.class) consumers can read from a nearby follower.

What is Cruise Control?

An open-source tool that monitors brokers and generates balancing plans; Kafka itself does not auto-balance replicas.

Does a replica store the same files?

Yes, its own segment files; segment boundaries can differ slightly between replicas.

Each partition has RF copies on different brokers. One is the leader for reads and writes; followers fetch from it. If the leader fails, an in-sync follower becomes leader. RF 3 with min ISR 2 is typical.
