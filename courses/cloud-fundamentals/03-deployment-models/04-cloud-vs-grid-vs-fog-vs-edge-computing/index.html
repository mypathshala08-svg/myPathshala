Cloud vs grid vs fog vs edge computing

Six ideas that are easy to mix up: cluster, grid, utility, cloud, fog and edge computing. 1 The story

Seven million readings an hour

Before you start: 3.1–3.3 and Lesson 5.1 (Regions and edge locations).

🤔 TiffinGo puts a temperature sensor in every delivery bag: hot food must stay above 60 °C. 2,000 bags send a reading every second. Should all 7 million readings a hour go to the cloud?

No — that is what edge and fog computing are for: filter and act close to the device, send only what matters to the cloud. And before cloud there were cluster, grid and utility computing — each solved a different problem and each survives inside today’s cloud. This lesson explains all six with the same pattern, animates one reading travelling sensor → edge → fog → cloud, and on your own account you build a small edge-to-cloud pipeline that sends only the alerts.

2 Definition

Cloud vs grid vs fog vs edge computing

Formal definition (write this in exams)

Cluster computing joins similar computers in one place into one system; grid computing coordinates distributed resources owned by different organisations for shared large-scale work; utility computing meters and bills computing like a public utility; cloud computing provides on-demand, self-service, elastic, metered access to pooled resources over the network (NIST); fog computing is a distributed layer between devices and the cloud that aggregates and processes data near its source; edge computing processes data at or next to the device that creates it.

In simple words

Cluster = many machines in one room as one; grid = many organisations sharing machines; utility = pay per use; cloud = rent IT services on demand; fog = a middle layer near devices; edge = process right at the device.

Say it in an interview

30-second answer you can speak:

  • “Edge processes at the device, fog is the layer between devices and cloud, and the cloud does storage, analytics and fleet management. For example, the phone checks food temperature, the kitchen gateway coordinates, the cloud learns.”
  • “Grid shares resources across organisations for batch science; cloud is one provider’s self-service, elastic, pay-per-use pool; utility computing is the billing model inside cloud.”

Type 1 · Cluster computing

Definition (say it in an interview): Cluster computing links a group of similar computers (nodes), usually in one location over a fast local network, so that they work together as a single system — for high performance (HPC), high availability (failover) or load balancing — under one administrative domain.

In plain words (no jargon): Many computers in one place connected tightly so they act like one powerful computer.

Analogy: A team of rowers in one boat: same boat, same rhythm, one direction.

How it works internally, step by step

  1. Install. Same OS/software on all nodes.
  2. Network. Fast interconnect.
  3. Scheduler. Slurm, YARN, Kubernetes.
  4. Split. Divide data/tasks.
  5. Combine. Gather results / fail over.

Words used above, in simple terms: node = one computer in a cluster · HPC = high-performance computing · scheduler = software that assigns work to nodes

For the experienced — did you know? Cluster placement groups (AWS), proximity placement groups (Azure) and compact placement (Google) exist to give cloud clusters the low-latency network HPC needs.

Use it when: a job can be split into parallel parts or a service needs failover within one site.
Avoid / be careful when: nodes are spread across the internet with slow, unreliable links — that is grid territory.

Type 2 · Grid computing

Definition (say it in an interview): Grid computing coordinates loosely coupled, geographically distributed and often heterogeneous resources owned by different organisations, through grid middleware, so they can be shared to solve large problems — typically batch scientific workloads — as a “virtual organisation”.

In plain words (no jargon): Computers owned by different organisations in different places shared together to run very large jobs.

Analogy: A national blood-donation network: hospitals in many cities share stock through a common system, each still owning its own bank.

How it works internally, step by step

  1. Join. Sites install middleware.
  2. Identity. Certificates for users and sites.
  3. Submit. Jobs to a broker.
  4. Match. Broker finds free resources.
  5. Collect. Results returned and stored.

Words used above, in simple terms: middleware = software that connects different systems · virtual organisation = a group sharing resources across institutions · volunteer computing = public donating idle PC time

Use it when: massive batch jobs can be split into independent tasks and organisations want to share idle capacity.
Avoid / be careful when: you need interactive services, fast responses or a commercial SLA — use cloud.

Type 3 · Utility computing

Definition (say it in an interview): Utility computing is a service-provisioning model in which computing resources (processing, storage, network) are metered and charged by usage, like a public utility such as electricity or water, instead of being bought as fixed assets.

In plain words (no jargon): Paying for computing the way you pay for electricity — only for what you use.

Analogy: Your electricity meter: you do not own the power station, you pay for the units you used this month.

How it works internally, step by step

  1. Meter. Collect usage records.
  2. Rate. Apply prices per unit.
  3. Aggregate. Per account / tag.
  4. Invoice. Monthly bill.
  5. Optimise. Use less, pay less.

Words used above, in simple terms: metering = measuring how much is used · opex = operating expenditure — ongoing spending · tariff = price list per unit

The billing model of every cloud provider; earlier: IBM and Sun “pay per CPU-hour” offerings in the early 2000s.

For the experienced — did you know? Utility computing is a pricing model, not a technology; exams like the distinction: cloud = utility billing + self-service + elasticity + broad access + pooling.

Use it when: usage varies and you prefer opex to capex.
Avoid / be careful when: usage is constant and very high for years — owning or committing may be cheaper.

Type 4 · Cloud computing

Definition (say it in an interview): Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources that can be rapidly provisioned and released with minimal management effort or service-provider interaction (NIST SP 800-145) — combining self-service, broad access, pooling, elasticity and metered (utility) billing.

In plain words (no jargon): Using computing services over the internet whenever you need them, paying only for what you use.

Analogy: A cab app: book any size of car in minutes, ride as long as you need, pay per trip — and the company handles the cars.

How it works internally, step by step

  1. Request. API / console.
  2. Provision. From shared pools.
  3. Run. Managed by provider (per service model).
  4. Scale. Elastic.
  5. Bill. Metered.

Words used above, in simple terms: elastic = grows and shrinks automatically · on-demand = available when requested, without waiting · Region = geographic group of data centres

Type 5 · Fog computing

Definition (say it in an interview): Fog computing (term popularised by Cisco around 2012) is a distributed layer of compute, storage and networking between end devices and the cloud — on gateways, routers, local servers or telco base stations — that aggregates, filters and processes data from many nearby devices and coordinates them, while forwarding selected data to the cloud.

In plain words (no jargon): A middle layer near the devices — like a local gateway — that collects and processes their data before the cloud.

Analogy: A local area manager between delivery riders and head office: collects reports from all riders in the area, solves local problems, and sends a daily summary upward.

How it works internally, step by step

  1. Connect. Devices to a gateway (MQTT, BLE, Wi-Fi).
  2. Aggregate. Combine streams.
  3. Decide. Local rules and coordination.
  4. Buffer. Store when uplink fails.
  5. Forward. Summaries to cloud.

Words used above, in simple terms: gateway = device connecting local devices to wider networks · MEC = multi-access edge computing at telecom base stations · aggregation = combining many readings into fewer

Use it when: many devices in an area need coordination, aggregation or low latency, but each device is too weak to do it alone.
Avoid / be careful when: devices are few and capable (edge alone suffices) or latency is not critical (cloud alone suffices).

Type 6 · Edge computing

Definition (say it in an interview): Edge computing places processing and storage at or very near the source of data — on the device itself or on hardware next to it — to reduce latency and bandwidth, keep working without connectivity and keep sensitive data local, sending only results or summaries to fog or cloud.

In plain words (no jargon): Processing data right where it is created — on the device or next to it — instead of sending it all far away.

Analogy: A cook tasting and adjusting salt at the stove instead of sending every spoonful to the head chef.

How it works internally, step by step

  1. Collect. Read sensors/cameras.
  2. Infer. Rules or small ML model.
  3. Act. Alert / control locally.
  4. Buffer. Store and forward.
  5. Update. New models/rules pushed from cloud.

Words used above, in simple terms: latency = delay between action and response · bandwidth = how much data a link can carry · inference = running a trained model to get a prediction

6 Explained part by part

Six factors that decide where to compute

Latency

What it is: Delay from event to decision.

Why it exists: Safety and UX need ms at the edge.

Where it is used: Alerts, video, control loops.

Bandwidth

What it is: How much data the link can carry.

Why it exists: Raw data is expensive to send.

Where it is used: Filter, compress, summarise.

Connectivity

What it is: Is the network always there?

Why it exists: Edge must work offline.

Where it is used: Store and forward.

Privacy

What it is: Where personal data goes.

Why it exists: Keep raw data local; send results.

Where it is used: Faces, health, location.

Compute power

What it is: What each tier can run.

Why it exists: Heavy ML training needs cloud.

Where it is used: Train in cloud, infer at edge.

Fleet management

What it is: Updating thousands of nodes.

Why it exists: Bugs at scale need safe rollouts.

Where it is used: OTA updates, canaries, rollback.

Myth vs reality: things many websites still say

  • Myth: Grid = cloud.
    Reality: Different owners, access and workloads.
    Proof: Type 2.
  • Myth: Edge replaces the cloud.
    Reality: Edge decides fast; cloud stores, learns and manages.
    Proof: Animation step 6.
  • Myth: Utility computing is a product.
    Reality: It is a pricing model.
    Proof: Type 3.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You build the edge-to-cloud path: a cloud ingest point, a simulated rider phone (edge) that filters 60 readings into a few alerts, and a usage check. Everything fits free tiers.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Create the cloud end: a message ingest point

    Pick your cloud.

    UI way — AWS Management Console

    1. IoT Core → Test → MQTT test client → Subscribe to a topic: tiffingo/bags/# → Subscribe. Keep this tab open.
    2. IoT Core needs no setup to receive messages from the CLI; real devices also need a registered thing and certificate.

    CLI way — the same thing with commands

    aws iot describe-endpoint --endpoint-type iot:Data-ATS --query endpointAddress --output text
aws iot create-thing --thing-name rider-phone-101

    You should see: an endpoint like a1b2c3…-ats.iot.ap-south-1.amazonaws.com and the new thing’s ARN.

    UI way — Azure portal

    1. IoT Hub → Create: resource group rg-edge, name tiffingo-hub-yourname, Central India, tier Free → Create.
    2. Devices → Add device rider-phone-101.

    CLI way — the same thing with commands

    az extension add --name azure-iot --upgrade
az group create -n rg-edge -l centralindia
HUB=tiffingo-hub-$RANDOM; az iot hub create -n $HUB -g rg-edge --sku F1 --partition-count 2
az iot hub device-identity create -n $HUB -d rider-phone-101

    You should see: JSON for the hub ("sku": {"name": "F1"}) and the device. Only one free F1 hub is allowed per subscription.

    UI way — Google Cloud console

    1. Pub/Sub → Topics → Create topic: bag-alerts, tick Add a default subscription → Create.
    2. Google retired Cloud IoT Core in 2023; devices or gateways now publish to Pub/Sub (directly or via a partner platform).

    CLI way — the same thing with commands

    gcloud pubsub topics create bag-alerts
gcloud pubsub subscriptions create bag-alerts-sub --topic=bag-alerts

    You should see: Created topic [projects/…/topics/bag-alerts] and the subscription.

    The cloud tier receives events; deciding which events to send is the edge’s job (next step).

  3. 2 · Run an “edge” filter and send only the alerts

    Pick your cloud.

    UI way — AWS Management Console

    1. Run the simulated phone on the right in CloudShell; it prints only alert lines.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Treating grid and cloud as the same.Both share resources.Grid: many owners, membership, batch. Cloud: one provider, self-service, pay per use.
Calling utility computing a technology.The word “computing”.It is a metering/pricing model inside cloud.
Streaming all raw sensor data to the cloud.Simplest to build.Filter and summarise at edge/fog.
Edge apps that fail without network.Cloud-first habits.Store-and-forward, local decisions.
Mixing up edge and fog.Vendors use “edge” for everything.Edge = at the device; fog = the layer between.
Building on Google Cloud IoT Core.Old tutorials.Retired Aug 2023 — use Pub/Sub or a partner platform.

Quick revision

Lesson 3.4 in one screen

  • Cluster: one site, tight network, one system.
  • Grid: many owners, middleware, batch.
  • Utility: metered pay-per-use model.
  • Cloud: on-demand, elastic, metered services.
  • Fog: layer between devices and cloud; edge: at the device.

Interview and viva questions

Edge or fog — which is the phone?

Edge (at the device); the kitchen gateway is fog.

Is cloud a kind of grid?

Related ideas, but cloud is provider-owned self-service with pay-per-use; grid is shared across organisations.

What replaced Google Cloud IoT Core?

Pub/Sub with partner device platforms.
