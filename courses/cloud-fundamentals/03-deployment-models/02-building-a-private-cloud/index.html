1 The story

Three weeks for one server

Before you start: 3.1 and Module 4 (virtualization).

🤔 The hospital chain has 40 servers in its Pune data centre. Departments email IT for a new server and wait three weeks. Is that a private cloud?

Not yet — it is a virtualized data centre. It becomes a private cloud when it gets the five NIST characteristics: self-service, broad network access, resource pooling, rapid elasticity and metering. This lesson shows the seven building blocks, follows a VM request through OpenStack step by step, compares six private-cloud platforms one by one, and on your own account you build the private-cloud “catalogue, quota and chargeback” ideas with public-cloud tools — free.

2 Definition

What it takes to build a private cloud

Formal definition (write this in exams)

Building a private cloud means adding to pooled, virtualized infrastructure the capabilities that satisfy the NIST cloud characteristics — on-demand self-service, broad network access, resource pooling with multi-tenancy, rapid elasticity and measured service — typically through a cloud management platform (such as OpenStack, VMware Cloud Foundation, Azure Local or Nutanix) that provides identity, APIs, a service catalogue, quotas, automation and metering, for the exclusive use of one organisation.

In simple words

Take your own servers and add a self-service portal, automatic building, fair limits and usage tracking, so teams can use them like a public cloud.

Say it in an interview

30-second answer you can speak:

  • “A private cloud is not just virtualization: it adds self-service, multi-tenancy with quotas, automation and metering — NIST’s five characteristics — for one organisation.”
  • “In OpenStack, Keystone authenticates, Nova checks quota and schedules, Glance supplies the image, Neutron the network, and KVM boots the VM.”

Type 1 · OpenStack

Definition (say it in an interview): OpenStack is an open-source cloud platform made of cooperating services — Keystone (identity), Nova (compute), Neutron (networking), Cinder (block storage), Glance (images), Swift (object storage), Horizon (dashboard) and others — that turns pools of commodity servers into an IaaS cloud with APIs, multi-tenancy and quotas.

In plain words (no jargon): Free software that turns a group of normal servers into your own AWS-like cloud.

Analogy: A modular kitchen from separate pieces: you choose every cabinet and fit them yourself — flexible and cheap to buy, but you need a good carpenter.

How it works internally, step by step

  1. Plan. Controllers, compute, storage nodes, networks.
  2. Deploy. Kolla-Ansible / Sunbeam / vendor installer.
  3. Storage. Usually Ceph for block, image and object.
  4. Tenants. Domains, projects, roles, quotas.
  5. Operate. Upgrades every 6-month release cycle.

Words used above, in simple terms: Nova = OpenStack compute service · Neutron = OpenStack networking service · Ceph = open-source distributed storage often used with OpenStack

Use it when: you need large scale, no licence fees, deep customisation, or AWS-like APIs on-premises.
Avoid / be careful when: the team is small and has no Linux/networking depth — operations are the real cost.

Type 2 · VMware Cloud Foundation (VCF)

Definition (say it in an interview): VMware Cloud Foundation is Broadcom’s integrated private-cloud platform combining vSphere (ESXi + vCenter) compute virtualization, vSAN software-defined storage, NSX software-defined networking and lifecycle and automation tooling, delivered as one subscription.

In plain words (no jargon): VMware’s complete package for turning your data centre into a private cloud.

Analogy: Buying a fully fitted branded kitchen from one company: everything matches and has one warranty — at a premium price.

How it works internally, step by step

  1. Hosts. ESXi on certified servers.
  2. Management. vCenter + SDDC Manager.
  3. Storage. vSAN pools local disks.
  4. Network. NSX virtual networks and firewalls.
  5. Automate. Catalogue and blueprints.

Words used above, in simple terms: vSphere = VMware’s virtualization platform · vSAN = VMware software-defined storage · NSX = VMware software-defined networking

Type 3 · Microsoft Azure Local

Definition (say it in an interview): Azure Local (formerly Azure Stack HCI) is Microsoft’s hyperconverged infrastructure solution that runs virtual machines, AKS clusters and selected Azure services on validated hardware in the customer’s data centre, managed through the Azure portal via Azure Arc and billed as an Azure subscription service.

In plain words (no jargon): Microsoft’s system for running a small Azure-managed cloud on your own servers.

Analogy: A franchise outlet: your own shop and staff, but the brand’s menu, systems and head-office dashboard.

How it works internally, step by step

  1. Buy. Validated nodes (OEM catalogue).
  2. Deploy. From the Azure portal.
  3. Register. Arc-enabled; appears as Azure resources.
  4. Run. VMs, AKS, Azure Virtual Desktop.
  5. Pay. Per physical core per month to Azure.

Words used above, in simple terms: HCI = hyperconverged infrastructure — compute and storage in the same nodes · Azure Arc = extends Azure management to non-Azure resources · validated = tested and certified by Microsoft

Type 4 · Nutanix and hyperconverged (HCI) platforms

Definition (say it in an interview): Hyperconverged infrastructure (HCI) combines compute, storage and virtualization in standard x86 nodes managed as one cluster by software; Nutanix Cloud Platform is a leading example, with its own AHV hypervisor, distributed storage and self-service management for private and hybrid clouds.

In plain words (no jargon): Ready-made boxes that each hold computing and storage, joined by software into one private cloud.

Analogy: Lego blocks: every block is the same shape, and you build a bigger structure by snapping on more.

How it works internally, step by step

  1. Nodes. Identical x86 servers with SSD/NVMe.
  2. Hypervisor. AHV (or ESXi).
  3. Distributed storage. Data copied across nodes (RF2/RF3).
  4. Manage. Single console (Prism).
  5. Scale. Add nodes online.

Words used above, in simple terms: hyperconverged = compute + storage + virtualization in each node · SAN = storage area network — a separate storage system · replication factor = how many copies of data are kept

Use it when: you want a simpler private cloud that grows in small steps without a separate storage array.
Avoid / be careful when: compute and storage needs grow very unevenly — you may buy disks you do not need with every node.

Type 5 · Apache CloudStack

Definition (say it in an interview): Apache CloudStack is an open-source IaaS platform that manages pools of hypervisor hosts (KVM, XenServer/XCP-ng, VMware) from a central management server, offering a self-service portal, APIs, multi-tenancy, networking and storage orchestration — generally simpler to deploy and operate than OpenStack.

In plain words (no jargon): Another free cloud software, simpler to set up, for building your own cloud.

Analogy: A ready-to-assemble flat-pack wardrobe: fewer choices than a custom carpenter, but you can build it yourself in a weekend.

How it works internally, step by step

  1. Install. Management server + MySQL.
  2. Add zone. Networks, primary/secondary storage.
  3. Add hosts. KVM or other hypervisors.
  4. Offerings. Define VM sizes and templates.
  5. Tenants. Accounts, domains, projects.

Words used above, in simple terms: zone = a data-centre-level unit in CloudStack · pod = a rack-level group of hosts · offering = a predefined VM size or service

Type 6 · Container private cloud (Kubernetes / OpenShift)

Definition (say it in an interview): A container-based private cloud uses Kubernetes — often packaged as Red Hat OpenShift, SUSE Rancher or VMware Tanzu — on the organisation’s own infrastructure to give teams self-service deployment of containerised applications, effectively a private PaaS, sometimes with VMs managed alongside (KubeVirt / OpenShift Virtualization).

In plain words (no jargon): A private cloud for containers, where developers deploy their apps themselves on company servers.

Analogy: A food court’s shared kitchen: every stall cooks its own dishes, but gas, water, cleaning and rules come from the food-court manager.

How it works internally, step by step

  1. Infra. Bare metal or VMs.
  2. Cluster. Control plane + workers.
  3. Platform. Registry, CI/CD, ingress, policies.
  4. Tenancy. Namespaces/projects + quotas.
  5. Operate. Upgrades, monitoring, backups.

Words used above, in simple terms: Kubernetes = open-source container orchestrator · namespace = a tenant space inside a cluster · KubeVirt = runs VMs inside Kubernetes

6 Explained part by part

Six things a private cloud must run

Service catalogue

What it is: Approved templates users can launch.

Why it exists: Self-service without chaos.

Where it is used: Flavors, images, blueprints.

Quotas

What it is: Per-team limits on vCPU, RAM, storage.

Why it exists: Fair sharing of fixed hardware.

Where it is used: Project quotas.

Metering

What it is: Usage per project over time.

Why it exists: Showback/chargeback, capacity planning.

Where it is used: Tags, usage reports.

Automation

What it is: Code that builds resources.

Why it exists: Minutes instead of weeks; no drift.

Where it is used: Terraform, Ansible, Heat.

Capacity management

What it is: Buying hardware ahead of demand.

Why it exists: A private cloud cannot burst beyond what you own.

Where it is used: Headroom targets, lead times.

Operations

What it is: Patching, upgrades, DR.

Why it exists: The hidden cost of private cloud.

Where it is used: 24×7 team, runbooks.

Myth vs reality: things many websites still say

  • Myth: Virtualization = private cloud.
    Reality: Self-service, quotas, automation and metering are also needed.
    Proof: NIST test.
  • Myth: Private cloud is always cheaper at scale.
    Reality: Only with high, steady utilisation and skilled staff.
    Proof: Deep dive sizing.
  • Myth: Open source means free.
    Reality: Operations and support are the real cost.
    Proof: Type 1.
7 Deep dive

Showback, sizing, OpenStack at home, failure modes

Showback vs chargeback

Showback reports each team’s usage and cost without billing them; chargeback actually transfers the cost to their budget. Start with showback — it changes behaviour (teams delete idle VMs) without accounting fights.

Sizing a small private cloud (worked example)

ItemValue
Demand200 VMs × 2 vCPU × 8 GiB
OvercommitCPU 4:1, RAM 1:1
Needed100 physical cores, 1.6 TiB RAM
Per host32 cores, 512 GiB
Hosts4 for load + 1 for failure (N+1) = 5
Storage3 replicas × 40 TB usable = 120 TB raw

N+1 and replicas mean you buy roughly 30–200% more raw capacity than you use — part of why private cloud is rarely cheaper unless utilisation is high and steady.

Try OpenStack at home (optional, needs a strong PC)

Canonical’s single-node OpenStack (“Sunbeam”) installs with snaps on Ubuntu Server LTS with about 4+ cores, 16 GB+ RAM and 100 GB+ disk. The flow is: sudo snap install openstack → sunbeam prepare-node-script --bootstrap | bash -x → sunbeam cluster bootstrap --accept-defaults → sunbeam configure --accept-defaults --openrc demo-openrc → sunbeam launch ubuntu --name test. Check Canonical’s current documentation for the exact snap channel and requirements before you start.

Private cloud failure modes

  • Capacity cliff: hardware lead times of 8–16 weeks; plan purchases on trend, not on full.
  • Control-plane outage: APIs down = no new VMs; run 3 controllers.
  • Upgrade debt: skipping releases makes upgrades risky; schedule them.
  • Shadow IT: if the portal is slow or restrictive, teams use public cloud anyway — measure request-to-VM time.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You cannot build an OpenStack cloud in a free account, but you can practise the four things that make a private cloud a cloud — dedicated hardware choices, a catalogue, quotas and showback — with free public-cloud tools. (Optional home OpenStack: see the deep dive.)

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · See what dedicated (private) hardware costs — read only

    Pick your cloud.

    UI way — AWS Management Console

    1. EC2 → Dedicated Hosts → Allocate Dedicated Host — look at the options, but do not allocate (billed per hour).

    CLI way — the same thing with commands

    aws ec2 describe-host-reservation-offerings --filter Name=instance-family,Values=m5 --max-items 3 \
  --query 'OfferingSet[].[InstanceFamily,PaymentOption,Duration,HourlyPrice]' --output table

    You should see: host reservation offerings for the m5 family with durations (seconds) and hourly prices — a whole physical server is far more than one small VM.

    UI way — Azure portal

    1. Host groups → Create → look at the options. A host group itself is free; do not add a dedicated host in the lab.

    CLI way — the same thing with commands

    az vm list-skus --location centralindia --resource-type hostGroups/hosts --query "[].name" -o tsv | head

    You should see: dedicated host SKUs such as DSv3-Type1, ESv5-Type1 — each is a whole physical server.

    UI way — Google Cloud console

    1. Sole-tenant nodes → Node templates → Create → browse node types; do not create a node group.

    CLI way — the same thing with commands

    gcloud compute sole-tenancy node-types list --filter="zone:asia-south1-a" --format="table(name,guestCpus,memoryMb)" | head

    You should see: node types like n2-node-80-640 (80 vCPU, 640 GB) — the unit you rent for dedicated hardware.

    Dedicated hardware in a public cloud is the “hosted private” model — compare that hourly price with one VM to see why it is reserved for licensing and compliance needs.

  3. 2 · Create a catalogue item (self-service template)

    Pick your cloud.

    UI way — AWS Management Console

    1. EC2 → Launch templates → Create launch template: name catalog-small-linux, Amazon Linux 2023, t3.micro, tag team=research → Create.
    2. Users can now launch only from approved templates (with IAM you can enforce that).

    CLI way — the same thing with commands

    AMI=$(aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query Parameter.Value --output text)
aws ec2 create-launch-template --launch-template-name catalog-small-linux \
  --launch-template-data "{\"ImageId\":\"$AMI\",\"InstanceType\":\"t3.micro\",\"TagSpecifications\":[{\"ResourceType\":\"instance\",\"Tags\":[{\"Key\":\"team\",\"Value\":\"research\"}]}]}"
aws ec2 describe-launch-templates --launch-template-names catalog-small-linux --query "LaunchTemplates[0].[LaunchTemplateId,LatestVersionNumber]" --output text

    You should see: lt-… 1 — a versioned catalogue item. Free; nothing runs until someone launches from it. (AWS Service Catalog adds portfolios and approvals on top.)

    UI way — Azure portal

    1. Template specs → Create template spec: resource group rg-private, name catalog-small-vnet, version 1.0, paste a small ARM/Bicep template → Create.

    CLI way — the same thing with commands

    az group create -n rg-private -l centralindia
cat > vnet.json <<'EOF'
{"$schema":"https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#","contentVersion":"1.0.0.0",
 "resources":[{"type":"Microsoft.Network/virtualNetworks","apiVersion":"2023-09-01","name":"team-vnet","location":"[resourceGroup().location]",
  "tags":{"team":"research"},"properties":{"addressSpace":{"addressPrefixes":["10.70.0.0/16"]}}}]}
EOF
az ts create -g rg-private -n catalog-small-vnet -v 1.0 -l centralindia --template-file vnet.json
az ts list -g rg-private --query "[].name" -o tsv

    You should see: catalog-small-vnet — a versioned template others can deploy with az deployment group create --template-spec <id>.

    UI way — Google Cloud console

    1. Instance templates → Create instance template: name catalog-small-linux, e2-small, Debian 12, label team=research → Create.

    CLI way — the same thing with commands

    gcloud compute instance-templates create catalog-small-linux --machine-type=e2-small \
  --image-family=debian-12 --image-project=debian-cloud --labels=team=research
gcloud compute instance-templates list --filter="name=catalog-small-linux"

    You should see: the template listed with machine type e2-small. Free until a VM is created from it.

    A service catalogue is the heart of a private cloud: approved, versioned templates instead of hand-built servers.

  4. 3 · Read your quotas (fair sharing of capacity)

    Pick your cloud.

    UI way — AWS Management Console

    1. Service Quotas → AWS services → Amazon Elastic Compute Cloud (Amazon EC2) → “Running On-Demand Standard (A, C, D, H, I, M, R, T, Z) instances”.

    CLI way — the same thing with commands

    aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A \
  --query "Quota.[QuotaName,Value]" --output text

    You should see: the quota name and your vCPU limit (new accounts often have small limits).

    UI way — Azure portal

    1. Search Quotas → Compute → filter Region Central India.

    CLI way — the same thing with commands

    az vm list-usage --location centralindia --query "[?contains(name.value,'cores')].{name:localName,used:currentValue,limit:limit}" -o table | head

    You should see: Total Regional vCPUs and per-family limits with current usage.

    UI way — Google Cloud console

    1. IAM & Admin → Quotas & system limits → filter “CPUs” and region asia-south1.

    CLI way — the same thing with commands

    gcloud compute regions describe asia-south1 --format="table(quotas.metric,quotas.limit,quotas.usage)" | head -12

    You should see: rows such as CPUS 24 0 — limit and usage per metric.

    A private cloud does the same per project. The difference: when you hit a private-cloud quota, someone may have to buy servers (weeks).

  5. 4 · Showback: see cost by team tag

    Pick your cloud.

    UI way — AWS Management Console

    1. Billing and Cost Management → Cost allocation tags → find team → Activate (appears after a tagged resource exists; takes up to 24 h).
    2. Cost Explorer → Group by Tag → team.

    CLI way — the same thing with commands

    aws resourcegroupstaggingapi get-resources --tag-filters Key=team,Values=research --query "ResourceTagMappingList[].ResourceARN" --output text
aws ce list-cost-allocation-tags --status Inactive --query "CostAllocationTags[?TagKey=='team']"

    You should see: the ARN of the launch template (tagged), and the team tag in the list once AWS has seen it in billing data.

    UI way — Azure portal

    1. Cost Management → Cost analysis → Group by → Tag → team.

    CLI way — the same thing with commands

    az resource list --tag team=research --query "[].{name:name,type:type}" -o table

    You should see: team-vnet only after you deploy the template spec; otherwise an empty list. Cost analysis by tag is in the portal (and the Cost Management APIs).

    UI way — Google Cloud console

    1. Billing → Reports → Group by → Label → team (labels flow into billing data).

    CLI way — the same thing with commands

    gcloud compute instance-templates describe catalog-small-linux --format="value(properties.labels)"

    You should see: team=research — every VM from this template carries it into billing reports.

    Showback is “measured service” from NIST: teams see what they use, and idle resources disappear.

Clean up and cost check

AWS: aws ec2 delete-launch-template --launch-template-name catalog-small-linux. Azure: az group delete -n rg-private --yes --no-wait. Google Cloud: gcloud compute instance-templates delete catalog-small-linux --quiet. Nothing in this lab costs money.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Calling a virtualized DC a private cloud.Marketing language.Test against NIST’s five characteristics.
Buying hardware for peak demand only.No N+1 and replica overhead in the plan.Size for peak + failure + replicas + growth lead time.
Small team running OpenStack from source.Free licence looks cheap.Use a supported distribution or a simpler platform.
No metering.Seen as optional.Showback from day one; it drives clean-up.
Portal slower than a ticket.Too many approvals.Pre-approve catalogue items within quota.
Ignoring upgrades.“If it works, don’t touch it.”Plan regular upgrades; skipped releases become migrations.

Interview and viva questions

Is VMware alone a private cloud?

Only if it adds self-service, quotas, automation and metering.

OpenStack or CloudStack?

OpenStack: bigger ecosystem, more complex. CloudStack: simpler to run.

Is private cloud cheaper?

Only with high, steady utilisation and skilled operations.
