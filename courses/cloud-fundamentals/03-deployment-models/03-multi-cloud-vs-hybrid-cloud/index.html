Multi-cloud vs hybrid cloud

Hybrid joins private and public; multi-cloud uses two or more public providers; most enterprises are both. Learn six real patterns — partitioned, analytics, edge, environment, business continuity, bursting — watch a cross-cloud failover with RTO and RPO, then on your own accounts plan networks, copy data, compare Kubernetes and prepare hybrid management.

1 The story

“What if AWS has a bad day?”

Before you start: 3.1 and 3.2.

🤔 TiffinGo’s investors ask: “What if AWS has a bad day?” The data team wants BigQuery. The hospital keeps its data on-premises. Is TiffinGo now hybrid, multi-cloud, or both?

Both — and the words mean different things. Hybrid joins private/on-premises with public cloud. Multi-cloud uses two or more public cloud providers. Most large companies are hybrid multi-cloud. This lesson gives six real architecture patterns (partitioned, analytics, edge, environment, business continuity, cloud bursting) one by one, animates a cross-cloud failover, and on your own accounts you plan non-overlapping networks, keep a copy of data in each cloud and find the portable layer — Kubernetes.

  • Multi-cloud is not automatically more reliable — it can double failure points.
  • Why “cloud-agnostic everything” often costs more than it saves.
  • The one design decision that makes hybrid and multi-cloud possible: IP planning.

At a board meeting, an investor asked what TiffinGo would do if its cloud provider failed. The data team wanted BigQuery, and the hospital link was already live. The team needed clear words before clear decisions.

Riya

The investor wants us on two clouds “in case one fails”. Should we run everything on AWS and Azure at the same time?

Arjun Sir

That doubles our work and our failure points. Ask first: which failure are we afraid of? A Region outage? Then a second AWS Region may be enough.

Kabir

But the data team really likes BigQuery.

Arjun Sir

That is a good multi-cloud reason: best service for a job. Analytics on Google, apps on AWS.

Riya

And the hospital link?

Arjun Sir

That is hybrid. So we are hybrid multi-cloud — on purpose, pattern by pattern.

2 Definition

Multi-cloud vs hybrid cloud

Formal definition (write this in exams)

Hybrid cloud is a composition of two or more distinct cloud infrastructures — typically private/on-premises and public — bound together to enable data and application portability (NIST). Multi-cloud is the use of cloud services from two or more public cloud providers within one organisation or architecture. An organisation that does both is said to be hybrid multi-cloud.

In simple words

Hybrid = your own servers plus a public cloud working together. Multi-cloud = using more than one public cloud company.

Say it in an interview

30-second answer you can speak:

  • “Hybrid joins private/on-prem and public cloud; multi-cloud uses several public providers. They are independent — many enterprises are hybrid multi-cloud.”
  • “I pick patterns deliberately: partitioned apps, analytics on the best platform, edge hybrid for sites, DR with tested RTO/RPO, bursting for batch — with one IdP, an IP plan and Kubernetes as the portable runtime.”

Type 1 · Partitioned multi-cloud

Definition (say it in an interview): In a partitioned multi-cloud architecture, different applications or components run on different public cloud providers according to which provider best fits each workload, with loose coupling (APIs, events) between them.

In plain words (no jargon): Different apps of the same company running on different cloud companies, each where it fits best.

Analogy: Shopping vegetables at the market, medicines at the pharmacy and electronics online — each from where it is best, linked only by your shopping list.

How it works internally, step by step

  1. Map apps. Boundaries and data flows.
  2. Choose provider. Per app, with reasons.
  3. Connect. APIs/events, private links where needed.
  4. Identity. One IdP federated to all clouds.
  5. Govern. Common tagging, security baseline, FinOps.

Words used above, in simple terms: loose coupling = parts depend on each other only through simple interfaces · IdP = identity provider — the system that logs users in · egress = data leaving a cloud, usually charged

Real-world example

Many enterprises are “multi-cloud by accident”: Microsoft 365 for productivity, AWS or Google Cloud for products — partitioned by default.

Real scenario (TiffinGo)

TiffinGo’s customer app runs on AWS; its staff email and documents run on Microsoft 365 with Entra ID; the ML recommendation model is trained on Google Cloud.

Products and cloud services

Any combination of AWS, Azure, Google Cloud, Oracle Cloud; integration through APIs, event buses, central identity (Entra ID, Okta).

For the experienced — did you know? Watch egress: every GB that crosses providers is billed on the way out (Lesson 5.5) — partition along data boundaries, not team boundaries.

Use it when: applications are clearly separable and each has a strong reason to be on a specific provider.
Avoid / be careful when: one application is split across providers with chatty traffic — latency and egress charges explode.

Type 2 · Analytics hybrid / multi-cloud

Definition (say it in an interview): The analytics hybrid and multi-cloud pattern keeps transactional workloads in their existing environment (on-premises or another cloud) while extracting their data into a cloud analytics platform for warehousing, reporting and machine learning.

In plain words (no jargon): Running your apps in one place and copying their data to another cloud that is better at analysing it.

Analogy: Cooking in your own kitchen but sending samples to a food-testing lab — the lab has better equipment for analysis.

How it works internally, step by step

  1. Extract. Exports, CDC streams.
  2. Transfer. Managed transfer services.
  3. Load. Warehouse / lakehouse.
  4. Model. BI, ML.
  5. Return. Results via API/reverse ETL.

Words used above, in simple terms: CDC = change data capture — streaming only the changes · warehouse = database built for analysis · reverse ETL = sending analytics results back to operational apps

Use it when: a different provider’s analytics service is clearly better or the data team already uses it.
Avoid / be careful when: data volumes are huge and change constantly — egress costs and freshness may favour analytics in the same cloud.

Type 3 · Edge hybrid

Definition (say it in an interview): The edge hybrid pattern runs time- and business-critical workloads locally at the edge of the network (stores, factories, kitchens) so they keep working with poor or no connectivity, while using the public cloud for everything else — central management, data aggregation, analytics and updates.

In plain words (no jargon): Running the urgent work at each local site and using the cloud for central control and analysis.

Analogy: Each dhaba cooks independently even if the phone lines are down, then sends the day’s accounts to head office when the line returns.

How it works internally, step by step

  1. Classify. What must work offline.
  2. Deploy. Same packages to all sites.
  3. Sync. Queue and forward when online.
  4. Manage. Central fleet management.
  5. Secure. Physical and device security.

Words used above, in simple terms: edge = computing close to where data is created · store-and-forward = save locally, send later · fleet = many identical devices or sites managed together

Use it when: sites need low latency to local equipment or must survive network outages.
Avoid / be careful when: all sites have reliable connectivity and nothing is time-critical — run centrally.

Type 4 · Environment hybrid

Definition (say it in an interview): The environment hybrid pattern runs development, testing (and sometimes staging) environments in the public cloud while keeping production in the existing data centre, using consistent tooling so code behaves the same in both.

In plain words (no jargon): Building and testing software in the cloud while the live system still runs in the company’s own data centre.

Analogy: Practising a dance in a rented hall that has mirrors and space, then performing on the home stage.

How it works internally, step by step

  1. Standardise. Containers / images.
  2. Automate. IaC creates environments.
  3. Data. Synthetic or masked test data.
  4. Pipeline. Same CI/CD to both.
  5. Promote. Release to on-prem production.

Words used above, in simple terms: staging = final test environment before production · synthetic data = realistic but fake data · masking = hiding sensitive values in test copies

For the experienced — did you know? Never copy real patient or customer data to test without masking — it breaks the rule that kept production on-premises in the first place.

Use it when: production cannot move yet but teams need fast, disposable environments.
Avoid / be careful when: environments differ (different OS, DB versions) — “works in test” bugs appear in production.

Type 5 · Business continuity (DR) hybrid / multi-cloud

Definition (say it in an interview): The business continuity pattern keeps a recovery environment — backups, a pilot light, a warm standby or a full active-active copy — in a different location (another Region, another provider, or the cloud for an on-premises primary), so that the business can recover within its RTO and RPO after a disaster.

In plain words (no jargon): Keeping a ready copy of your systems and data in another place so you can switch over after a disaster.

Analogy: Keeping a spare house key with a trusted neighbour in another street — useless if never tested, priceless when needed.

How it works internally, step by step

  1. Set targets. RTO and RPO per system.
  2. Choose tier. Backup → pilot light → warm → active-active.
  3. Replicate. Data continuously or on schedule.
  4. Automate. Runbooks / IaC.
  5. Test. Game days twice a year.

Words used above, in simple terms: RTO = recovery time objective — how long you can be down · RPO = recovery point objective — how much data you can lose · pilot light = minimal copy kept running, scaled up on disaster

Avoid / be careful when: a second Region of the same provider already meets the risk at a fraction of the effort.

Type 6 · Cloud bursting

Definition (say it in an interview): Cloud bursting is a hybrid pattern in which an application normally runs in a private environment and, when demand exceeds its capacity, the excess load is served by additional resources in a public cloud, which are released when demand falls.

In plain words (no jargon): Using your own servers normally and renting extra cloud servers only when demand is too high.

Analogy: A wedding family with a small house renting a banquet hall only for the reception night.

How it works internally, step by step

  1. Monitor. Capacity thresholds.
  2. Trigger. Queue length / utilisation.
  3. Launch. Pre-built images in the cloud.
  4. Route. Load balancer or scheduler sends overflow.
  5. Release. Scale cloud to zero after peak.

Words used above, in simple terms: burst = temporary overflow to extra capacity · stateless = no local data between requests · WAN = wide-area network link between sites

Use it when: workloads are stateless or batch, data can be moved or masked, and peaks are short.
Avoid / be careful when: the app needs low-latency access to a big on-prem database — the WAN link becomes the bottleneck.

6 Explained part by part

Six foundations of hybrid and multi-cloud

Identity federation

What it is: One identity provider trusted by every cloud and on-prem.

Why it exists: One login, one off-boarding, consistent roles.

Where it is used: Entra ID / Okta → AWS IAM Identity Center, Google Cloud.

Network & IP plan

What it is: Non-overlapping ranges, private links.

Why it exists: Without it, environments cannot be connected.

Where it is used: VPN, Direct Connect, ExpressRoute, Interconnect, cross-cloud interconnects.

Portable runtime

What it is: Containers / Kubernetes.

Why it exists: Same app package everywhere.

Where it is used: EKS, AKS, GKE; OpenShift.

Infrastructure as code

What it is: Same tool across providers.

Why it exists: Repeatable environments.

Where it is used: Terraform/OpenTofu, Pulumi.

Observability

What it is: Logs, metrics, traces in one place.

Why it exists: One view during incidents.

Where it is used: OpenTelemetry, Grafana, Datadog.

FinOps & governance

What it is: Costs and policies across providers.

Why it exists: Avoid surprises and drift.

Where it is used: FOCUS billing format, tags/labels, policy as code.

7 Deep dive

Lock-in, inter-cloud networking, control planes, data gravity

Lock-in: what it really is

Lock-in is the cost of leaving: rewriting code for different APIs, moving data (egress + time), retraining people, and contract terms. Avoiding every provider-specific service is also costly — you give up managed services and build them yourself. A balanced approach: use managed services freely, keep data in open formats, keep business logic in containers, document an exit plan for critical systems.

Networking between clouds

Options, from simplest: public internet with TLS; site-to-site VPN between clouds; partner interconnects through colocation exchanges; managed cross-cloud links (for example Google Cross-Cloud Interconnect to AWS, Azure, Oracle). Each adds cost but lowers latency and jitter.

Data gravity

Large data sets attract applications and services to wherever they live, because moving data is slow and costly. Design rule: put compute next to the biggest data, move small results instead of raw data.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. These steps are free or cost a few paise (tiny objects in storage). They build the foundations every hybrid or multi-cloud design needs: an IP plan, data copies, a portable runtime, and central management.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Plan non-overlapping networks (one block per cloud)

    Pick your cloud.

    UI way — AWS Management Console

    1. VPC → Create VPC → VPC only → name tiffingo-aws, CIDR 10.10.0.0/16.
    2. Write the plan down: AWS 10.10/16, Azure 10.20/16, Google 10.30/16, offices 192.168.x/24.

    CLI way — the same thing with commands

    aws ec2 create-vpc --cidr-block 10.10.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=tiffingo-aws}]' --query Vpc.VpcId --output text
aws ec2 describe-vpcs --query 'Vpcs[].[VpcId,CidrBlock,Tags[?Key==`Name`]|[0].Value]' --output table

    You should see: your new VPC with 10.10.0.0/16 next to the default VPC (172.31.0.0/16) — no overlap with the other clouds’ blocks.

    UI way — Azure portal

    1. Virtual networks → Create → rg rg-hybrid, name tiffingo-azure, address space 10.20.0.0/16.

    CLI way — the same thing with commands

    az group create -n rg-hybrid -l centralindia
az network vnet create -g rg-hybrid -n tiffingo-azure --address-prefixes 10.20.0.0/16 --subnet-name app --subnet-prefixes 10.20.1.0/24
az network vnet list --query "[].{name:name,space:addressSpace.addressPrefixes[0]}" -o table

    You should see: tiffingo-azure 10.20.0.0/16.

    UI way — Google Cloud console

    1. VPC network → Create VPC network → tiffingo-gcp, custom subnet app asia-south1 10.30.1.0/24.

    CLI way — the same thing with commands

    gcloud compute networks create tiffingo-gcp --subnet-mode=custom
gcloud compute networks subnets create app --network=tiffingo-gcp --region=asia-south1 --range=10.30.1.0/24
gcloud compute networks subnets list --network=tiffingo-gcp --format="table(name,region.basename(),ipCidrRange)"

    You should see: app asia-south1 10.30.1.0/24.

    An IP plan written before the first network saves months later: overlapping ranges cannot be routed between clouds or to the office.

  3. 2 · Keep a copy of data in each cloud (continuity basics)

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → Create bucket tiffingo-dr-<yourname> in Mumbai → Upload a small file menu-backup.json.

    CLI way — the same thing with commands

    echo '{"menu":"thali","price":150}' > menu-backup.json
B=tiffingo-dr-$RANDOM; aws s3 mb s3://$B --region ap-south-1
aws s3 cp menu-backup.json s3://$B/
aws s3api head-object --bucket $B --key menu-backup.json --query ETag --output text; md5sum menu-backup.json

    You should see: the S3 ETag and your local MD5 are the same hash — the copy is identical.

    UI way — Azure portal

    1. Storage accounts → Create (Standard, LRS, Central India) → Containers → dr → Upload the same file.

    CLI way — the same thing with commands

    echo '{"menu":"thali","price":150}' > menu-backup.json
SA=tiffingodr$RANDOM; az storage account create -n $SA -g rg-hybrid -l centralindia --sku Standard_LRS
az storage container create --account-name $SA -n dr --auth-mode login
az storage blob upload --account-name $SA -c dr -f menu-backup.json --auth-mode login
az storage blob show --account-name $SA -c dr -n menu-backup.json --auth-mode login --query properties.contentSettings.contentMd5 -o tsv

    You should see: a base64 MD5 of the file. (If --auth-mode login is denied, give yourself “Storage Blob Data Contributor” on the account.)

    UI way — Google Cloud console

    1. Cloud Storage → Create bucket tiffingo-dr-<yourname> in asia-south1 → Upload files.

    CLI way — the same thing with commands

    echo '{"menu":"thali","price":150}' > menu-backup.json
B=tiffingo-dr-$RANDOM; gcloud storage buckets create gs://$B --location=asia-south1
gcloud storage cp menu-backup.json gs://$B/
gcloud storage objects describe gs://$B/menu-backup.json --format="value(md5_hash)"

    You should see: the base64 MD5 — same file content as in the other clouds.

    Copies only help if you can restore them: in a real plan, schedule copies, keep them immutable, and test a restore.

  4. 3 · Find the portable layer: Kubernetes versions in each cloud

    Pick your cloud.

    UI way — AWS Management Console

    1. EKS → Add cluster → Create → look at the Kubernetes version list, then cancel (a cluster bills hourly).

    CLI way — the same thing with commands

    aws eks describe-cluster-versions --query 'clusterVersions[].[clusterVersion,versionStatus]' --output table

    You should see: the Kubernetes versions EKS supports and their status (standard / extended support).

    UI way — Azure portal

    1. Kubernetes services → Create → Kubernetes cluster → look at the version list, then cancel.

    CLI way — the same thing with commands

    az aks get-versions --location centralindia --query "values[].{version:version,support:capabilities.supportPlan[0]}" -o table

    You should see: supported AKS minor versions for Central India.

    UI way — Google Cloud console

    1. Kubernetes Engine → Clusters → Create → Release channel → see versions, then cancel.

    CLI way — the same thing with commands

    gcloud container get-server-config --location=asia-south1 --format="yaml(channels)"

    You should see: default and valid versions per release channel (Rapid, Regular, Stable).

    All three run upstream-conformant Kubernetes — the same container image and manifest can run on any of them. That is why Kubernetes is the usual multi-cloud runtime.

  5. 4 · Prepare central management for outside machines

    Pick your cloud.

    UI way — AWS Management Console

    1. Systems Manager → Hybrid activations → Create activation → limit 1 → Create. Note the Activation Code and ID (shown once).
    2. On an on-prem Linux server you would install the SSM Agent and register with them; it then appears in Fleet Manager as mi-….

    CLI way — the same thing with commands

    aws iam create-role --role-name SSMServiceRole --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ssm.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name SSMServiceRole --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
aws ssm create-activation --default-instance-name kitchen-01 --iam-role SSMServiceRole --registration-limit 1 --region ap-south-1

    You should see: ActivationId and ActivationCode. Registering standard on-prem nodes is free; advanced-tier features are paid.

    UI way — Azure portal

    1. Azure Arc → Machines → Add/Create → Add a single server → Generate script: resource group rg-hybrid, Central India, Linux.
    2. Running that script on a server installs the Connected Machine agent; the server then appears in Azure like a VM (policies, updates, monitoring).

    CLI way — the same thing with commands

    az extension add --name connectedmachine --upgrade
az provider register --namespace Microsoft.HybridCompute
az connectedmachine list -g rg-hybrid -o table

    You should see: the provider registering and an empty list until a server runs the onboarding script. Arc’s core server management is free; extras like Defender are paid.

    UI way — Google Cloud console

    1. Kubernetes Engine → Fleets → explore Register cluster → Attached — Google manages Kubernetes clusters elsewhere (EKS, AKS, on-prem), not individual servers.

    CLI way — the same thing with commands

    gcloud services enable gkehub.googleapis.com
gcloud container fleet memberships list

    You should see: an empty list — registering an outside cluster needs one (and GKE Enterprise pricing). Note the difference in approach: AWS/Azure manage servers; Google centres on Kubernetes fleets.

    Hybrid management = one control plane for machines that live outside the cloud.

Clean up and cost check

AWS: aws s3 rb s3://$B --force; aws ec2 delete-vpc --vpc-id <vpc-id>; aws ssm delete-activation --activation-id <id>; detach the policy and delete SSMServiceRole. Azure: az group delete -n rg-hybrid --yes --no-wait. Google Cloud: gcloud storage rm -r gs://$B; gcloud compute networks subnets delete app --region=asia-south1 --quiet; gcloud compute networks delete tiffingo-gcp --quiet.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Using hybrid and multi-cloud as synonyms.Both mean “more than one place”.Hybrid = private + public; multi-cloud = 2+ public providers.
Multi-cloud “for reliability” without failover tests.Assumed benefit.Define RTO/RPO, automate, run game days.
Splitting one chatty app across clouds.Team preferences.Partition along data boundaries; watch egress.
Same 10.0.0.0/16 everywhere.Defaults.Central IP plan before building networks.
Separate identities per cloud.Each team sets up its own.One IdP federated to all clouds.
Lowest-common-denominator design.Fear of lock-in.Use managed services; keep data portable and an exit plan.

14 Quiz and revision

Check yourself

Quick revision

Lesson 3.3 in one screen

  • Hybrid = private + public; multi-cloud = 2+ public providers; both = hybrid multi-cloud.
  • Patterns: partitioned, analytics, edge, environment, continuity, bursting.
  • Failover: replicate, health checks, runbook, DNS, fail back, test.
  • Foundations: identity, IP plan, Kubernetes, IaC, observability, FinOps.
  • Lock-in = cost of leaving; data gravity.

Interview and viva questions

Is multi-cloud always better?

No — it adds complexity; use it for clear reasons.

Does NIST define multi-cloud?

No — NIST defines hybrid; multi-cloud is an industry term.

What is data gravity?

Large data attracts compute; move results, not raw data.
