1 The story

Everything built, a third of the marks lost

Before you start: Modules 4–8 and Lesson 11.1.

🤔 Arjun finished every task in the lab exam — and lost a third of the marks. The examiner opened his web page and got a timeout.

His VM was running, nginx was installed, but port 80 was never opened. He had not verified from outside. Lab exams mark working results, not effort. This lesson gives you the seven kinds of lab tasks that cloud practical exams use, a plan–build–verify–evidence routine, twelve timed practice tasks with marking rubrics, and a full mock lab on your own account in AWS, Azure or Google Cloud.

  • Build only what the task asks — then prove it works from outside.
  • Keep evidence: command output, URLs, screenshots.
  • Clean up and stay inside free-tier limits.

Arjun’s lab exam had three tasks. He built all of them, but the web page timed out when the examiner tried it — port 80 had never been opened. He lost the biggest task’s marks.

Arjun Sir

M> The examiner checks the result. Your page did not load from outside — the firewall rule was missing.

2 Definition

Lab exam practice tasks

Formal definition (write this in exams)

A cloud lab exam is a time-limited practical assessment in which candidates build and configure resources — identities, compute, storage, networks, databases, functions, monitoring and budgets — in a cloud account to meet written requirements, and are marked on verifiable outcomes such as configuration, reachability, security and absence of unnecessary resources.

In simple words

You are given tasks and a cloud account; you build what each task asks and the examiner checks that it works.

Say it in an interview

30-second answer you can speak:

  • “In lab tasks I plan first, build the minimum, then verify from outside exactly as the user would — and I keep the commands so the work is repeatable.”
  • “If a VM build fails I fix the startup script and relaunch rather than debugging by hand — infrastructure should be reproducible.”

Type 1 · Identity tasks

Definition (say it in an interview): Identity tasks ask you to create users, groups or roles and give them exactly the permissions described — e.g. “create group auditors with read-only access”, “give the VM a role to read one bucket”, “enforce MFA” — and are marked by testing what the identity can and cannot do.

In plain words (no jargon): Tasks about who can do what in the account.

Analogy: Giving a guest a room key that opens only their room, then checking it does not open the next door.

How it works internally, step by step

  1. Read. Exact names and permissions.
  2. Create. User/group/role.
  3. Attach. Managed policy or role.
  4. Test. Allowed + denied action.
  5. Evidence. Policy listing + test output.

Words used above, in simple terms: managed policy = provider-written permission set · role assignment = Azure/GCP binding of role to identity at a scope · AccessDenied = the error that proves a deny

Type 2 · Compute tasks

Definition (say it in an interview): Compute tasks ask you to launch a virtual machine with given settings and make it serve something — usually a web page — which tests image and size selection, startup scripts, key pairs, firewall rules and public IPs.

In plain words (no jargon): Tasks where you start a server and make it serve a web page.

Analogy: Hiring a stall at a fair: right size, right place, stock it, then open the shutter so customers can see it.

How it works internally, step by step

  1. Size/image. Free-tier eligible.
  2. Script. User data / custom data / startup-script.
  3. Firewall. Port 80 (and 22 only if asked).
  4. Test. curl public IP.
  5. Evidence. ID, IP, output.

Words used above, in simple terms: user data = AWS startup script · cloud-init = Linux first-boot configuration, used by Azure custom data · startup-script = Google metadata key for boot scripts

Type 3 · Storage tasks

Definition (say it in an interview): Storage tasks ask you to create object storage and configure a feature — host a static website, enable versioning, add a lifecycle rule, share a file securely with a time-limited link — and are marked by testing the URL, the configuration and whether access is open or closed as required.

In plain words (no jargon): Tasks about storing files and sharing or publishing them.

Analogy: A locker room: get a locker with your number, put things inside, and either hand out a time-limited key or put a display window on it.

How it works internally, step by step

  1. Name. Globally unique.
  2. Upload. cp / upload.
  3. Feature. Website, versioning, lifecycle.
  4. Access. Policy / signed URL.
  5. Test. curl URL.

Words used above, in simple terms: static website = HTML served directly from storage · pre-signed / SAS / signed URL = time-limited link to one object · lifecycle rule = automatic tiering or deletion

Type 4 · Network tasks

Definition (say it in an interview): Network tasks ask you to create a virtual network with subnets, routing and firewall rules — e.g. “VPC 10.0.0.0/16 with a public subnet and a private subnet; only HTTP from the internet” — and are marked by inspecting the configuration and testing reachability.

In plain words (no jargon): Tasks about building a private network with controlled entry points.

Analogy: Planning a housing colony: plot numbers (CIDR), lanes (subnets), the main gate (internet gateway) and guards at each house (firewall rules).

How it works internally, step by step

  1. CIDR. Plan ranges.
  2. Network. VPC/VNet.
  3. Subnets. Public/private.
  4. Routes. IGW/NAT.
  5. Rules. SG/NSG/firewall.

Words used above, in simple terms: CIDR = address range notation, e.g. /24 = 256 addresses · internet gateway = AWS route to the internet · NSG = Azure network security group

Type 5 · Database tasks

Definition (say it in an interview): Database tasks ask you to create a managed database (relational or NoSQL), create a table, insert data and query it — testing engine choice, tier selection, network access and connection strings.

In plain words (no jargon): Tasks where you create a database and prove data goes in and comes out.

Analogy: Opening a ledger at a bank: pick the account type, open it, write the first entry, read it back.

How it works internally, step by step

  1. Engine. As named.
  2. Tier. Smallest / free.
  3. Access. Private or your IP only.
  4. Data. Create table, insert.
  5. Query. Read back.

Words used above, in simple terms: endpoint = database host name · free tier = limited free usage · provisioned vs on-demand = fixed capacity vs pay per request

Type 6 · Serverless tasks

Definition (say it in an interview): Serverless tasks ask you to deploy a function and connect it to a trigger — an HTTP endpoint, a storage upload or a schedule — and are marked by invoking it and checking its output and logs.

In plain words (no jargon): Tasks where code runs automatically when something happens.

Analogy: A doorbell: wire the button (trigger) to the bell (function), press it, and hear it ring (log).

How it works internally, step by step

  1. Runtime. As named.
  2. Code. Minimal handler.
  3. Trigger. HTTP/upload/schedule.
  4. Permissions. Execution role / identity.
  5. Logs. Show the line.

Words used above, in simple terms: handler = entry function · execution role = identity the function uses · cold start = first-invocation delay

Type 7 · Monitoring and cost tasks

Definition (say it in an interview): Monitoring and cost tasks ask you to set an alarm on a metric (e.g. CPU above 70%), create a budget with an alert, tag resources for cost allocation, or find something in logs — and are marked by inspecting the configuration and sometimes triggering the alarm.

In plain words (no jargon): Tasks about watching health and spending.

Analogy: A smoke alarm and a monthly household budget: both only help if someone is notified.

How it works internally, step by step

  1. Metric. Which one?
  2. Threshold. Value + period.
  3. Notify. Email/topic/action group.
  4. Budget. Amount + %.
  5. Tags. Apply + query.

Words used above, in simple terms: alarm = rule on a metric · budget = spending threshold with alerts · tag / label = key=value on resources

6 Explained part by part

Six parts of a lab exam

Task sheet

What it is: The list of tasks and marks.

Why it exists: Read fully before starting.

Where it is used: Underline names, sizes, Regions.

Account / sandbox

What it is: Where you build.

Why it exists: Limits and policies may apply.

Where it is used: Lab account, free tier or sandbox.

CLI + console

What it is: Two ways to build.

Why it exists: CLI is faster and repeatable.

Where it is used: Cloud Shell has CLIs ready.

Verification commands

What it is: curl, describe, list.

Why it exists: Prove each result.

Where it is used: Same test the examiner uses.

Evidence sheet

What it is: Outputs, IDs, URLs.

Why it exists: Protects your marks.

Where it is used: Copy as you go.

Cleanup plan

What it is: Reverse-order deletion.

Why it exists: No surprise bills.

Where it is used: Tags make it easy.

Myth vs reality: things many websites still say

  • Myth: Created means done.
    Reality: Working from outside means done.
    Proof: Story.
  • Myth: More resources = more marks.
    Reality: Extra resources can cost marks and money.
    Proof: Type 2.
  • Myth: Console is always faster.
    Reality: CLI is faster once practised, and repeatable.
    Proof: Parts.
7 Practice tasks

Twelve timed lab tasks with marking checks

Twelve timed tasks in the style of cloud lab exams. Do them in one cloud of your choice. Set a timer for each; mark yourself with the checks; delete everything at the end. Combine any three for a 60-minute mock.

Set 1 · Foundations

T1 · Read-only group (4 marks · 8 min)

Task: Create group auditors with read-only access and user intern1 in it.

Marking checks:

  • group exists with read-only policy/role
  • user is a member
  • user can list resources but a delete/create fails

Hint: Use the provider’s built-in read-only role; do not write a custom policy.

T2 · Web VM (10 marks · 15 min)

Task: Launch the smallest VM in Mumbai/Central India/asia-south1 that serves “Lab exam: hostname” on port 80. Tag/label it lab=exam.

Marking checks:

  • correct size and Region
  • page loads from outside
  • only ports 80 (and 22 if needed) open
  • tag/label present

Hint: Startup script + firewall; wait 60–90 s before testing.

T3 · Static website (6 marks · 10 min)

Task: Host an index.html with your name as a static website and submit the URL.

Marking checks:

  • URL loads from a browser
  • only the site objects are public
  • Region correct

Hint: S3 website + bucket policy / $web container / bucket web config + allUsers viewer.

T4 · Budget and tags (4 marks · 8 min)

Task: Create a monthly budget of ₹500 (or $5) with an 80% alert and list all resources tagged lab=exam.

Marking checks:

  • budget amount and threshold correct
  • notification configured
  • tag query output shows your VM

Hint: Budgets live at billing/account scope; tag queries use the tagging API or filters.

Set 2 · Core services

T5 · Versioned bucket (4 marks · 8 min)

Task: Create a bucket with versioning; upload notes.txt twice with different content; show both versions.

Marking checks:

  • versioning enabled
  • two versions listed
  • bucket private

Hint: list-object-versions / blob versions / --all-versions.

T6 · Time-limited share (4 marks · 6 min)

Task: Share one private file with a link that expires in 10 minutes.

Marking checks:

  • object still private
  • link works now
  • expiry 10 minutes

Hint: presign / SAS / signed URL.

T7 · NoSQL table (6 marks · 10 min)

Task: Create a NoSQL table students (key: roll) and insert three items; query one by key.

Marking checks:

  • table/container exists
  • three items
  • query returns the right item

Hint: DynamoDB / Cosmos DB / Firestore; on-demand or free tier.

T8 · HTTP function (6 marks · 12 min)

Task: Deploy a function returning “Hello Lab” over HTTP; give the URL and a log line.

Marking checks:

  • URL returns the text
  • function logs show the invocation
  • public access only if asked

Hint: Console inline editor is fastest under time pressure.

Set 3 · Network and operations

T9 · Custom network (8 marks · 15 min)

Task: Create network lab-vpc 10.20.0.0/16 with subnet 10.20.1.0/24; allow inbound 80 from anywhere and 22 only from your IP.

Marking checks:

  • CIDRs exact
  • rules exactly as asked
  • no extra open ports

Hint: Find your IP with curl -s ifconfig.me.

T10 · CPU alarm (4 marks · 8 min)

Task: Create an alarm when the VM’s CPU is above 70% for 5 minutes, notifying your email.

Marking checks:

  • metric, threshold and period correct
  • notification target set
  • alarm attached to the right VM

Hint: CloudWatch alarm + SNS / metric alert + action group / alert policy + channel.

T11 · Stop, resize, start (4 marks · 8 min)

Task: Stop the web VM, change it to the next size up, start it and verify the page still loads.

Marking checks:

  • new size shown
  • page loads after start
  • note whether the public IP changed

Hint: Public IPs often change after stop/start unless static.

T12 · Clean teardown (4 marks · 6 min)

Task: Delete everything you created and prove nothing tagged lab=exam remains.

Marking checks:

  • tag query returns nothing
  • no running VMs
  • buckets/budget removed as instructed

Hint: Delete in reverse order of dependencies; Azure: delete the resource group.

10 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. A full 30-minute mock lab with three marked tasks. Set a timer, do it in one cloud, and keep an evidence file (copy every output into evidence.txt). Costs: a few rupees if deleted the same day; free-tier VMs may be free.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Mock Task A: a web VM that the examiner can reach (10 marks)

    Pick your cloud.

    UI way — AWS Management Console

    1. EC2 → Launch instance → Amazon Linux 2023, t3.micro, tag lab=exam; Network settings → allow HTTP; Advanced details → User data = the script below → Launch.
    2. Open http://PUBLIC_IP in your browser.

    CLI way — the same thing with commands

    AMI=$(aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query Parameter.Value --output text)
SG=$(aws ec2 create-security-group --group-name lab-web --description "lab web" --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr 0.0.0.0/0 >/dev/null
cat > web.sh <<'EOF'
#!/bin/bash
dnf install -y nginx
echo "Lab exam: $(hostname)" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
EOF
ID=$(aws ec2 run-instances --image-id $AMI --instance-type t3.micro --security-group-ids $SG --user-data file://web.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=lab,Value=exam}]' --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --instance-ids $ID
IP=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)
sleep 90; curl -s http://$IP

    You should see: Lab exam: ip-172-31-… — the page, reached from outside. Save the instance ID, IP and this output as evidence.

    UI way — Azure portal

    1. Virtual machines → Create → Ubuntu 24.04, B1s, Central India; Inbound ports HTTP 80; Advanced → Custom data = the cloud-init below; tag lab=exam → Create.
    2. Open http://PUBLIC_IP.

    CLI way — the same thing with commands

    az group create -n rg-lab -l centralindia --tags lab=exam >/dev/null
cat > web.yaml <<'EOF'
#cloud-config
packages: [nginx]
runcmd:
  - echo "Lab exam: $(hostname)" > /var/www/html/index.html
EOF
az vm create -g rg-lab -n vm-lab --image Ubuntu2404 --size Standard_B1s --admin-username azureuser \
  --generate-ssh-keys --custom-data web.yaml --tags lab=exam --query publicIpAddress -o tsv
az vm open-port -g rg-lab -n vm-lab --port 80 >/dev/null
IP=$(az vm show -d -g rg-lab -n vm-lab --query publicIps -o tsv)
sleep 90; curl -s http://$IP

    You should see: Lab exam: vm-lab. If B1s is unavailable, pick another small size in the same Region and note it in your answer.

    UI way — Google Cloud console

    1. Compute Engine → Create instance → e2-micro, asia-south1-a, Debian 12; Firewall allow HTTP; Advanced → Automation → Startup script; label lab=exam → Create.
    2. Open http://EXTERNAL_IP.

    CLI way — the same thing with commands

    gcloud compute instances create vm-lab --zone=asia-south1-a --machine-type=e2-micro \
  --image-family=debian-12 --image-project=debian-cloud --tags=http-server --labels=lab=exam \
  --metadata=startup-script='#! /bin/bash
apt-get update && apt-get install -y nginx
echo "Lab exam: $(hostname)" > /var/www/html/index.html'
gcloud compute firewall-rules create allow-http-lab --allow=tcp:80 --target-tags=http-server
IP=$(gcloud compute instances describe vm-lab --zone=asia-south1-a --format='get(networkInterfaces[0].accessConfigs[0].natIP)')
sleep 90; curl -s http://$IP

    You should see: Lab exam: vm-lab. Timeout → check the firewall rule and network tag; default page → check the startup-script journal.

    This is the “verify from outside” habit from the story. Do not move on until curl shows your text.

  3. 2 · Mock Task B: a static website (6 marks)

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → Create bucket (Mumbai) → upload index.html → Properties → Static website hosting → Enable; Permissions → turn off Block Public Access for this bucket and add a GetObject policy.
    2. Open the website endpoint shown under Properties.

    CLI way — the same thing with commands

    B=lab-site-$RANDOM; aws s3 mb s3://$B --region ap-south-1
echo '<h1>Lab exam site</h1>' > index.html
aws s3 cp index.html s3://$B/
aws s3 website s3://$B --index-document index.html
aws s3api delete-public-access-block --bucket $B
aws s3api put-bucket-policy --bucket $B --policy "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Principal\":\"*\",\"Action\":\"s3:GetObject\",\"Resource\":\"arn:aws:s3:::$B/*\"}]}"
curl -s http://$B.s3-website.ap-south-1.amazonaws.com

    You should see: your <h1>Lab exam site</h1>. If the policy call fails with AccessDenied, account-level Block Public Access is on — say so in your answer.

    UI way — Azure portal

    1. Storage account → Static website → Enabled, index document index.html → upload index.html to the $web container.
    2. Open the Primary endpoint.

    CLI way — the same thing with commands

    SA=labsite$RANDOM; az storage account create -n $SA -g rg-lab -l centralindia --sku Standard_LRS --kind StorageV2 --tags lab=exam >/dev/null
echo '<h1>Lab exam site</h1>' > index.html
az storage blob service-properties update --account-name $SA --static-website --index-document index.html >/dev/null
az storage blob upload --account-name $SA -c '$web' -f index.html -n index.html >/dev/null
URL=$(az storage account show -n $SA -g rg-lab --query primaryEndpoints.web -o tsv); echo $URL; curl -s $URL

    You should see: the URL (https://labsite….z29.web.core.windows.net/) and your heading. The CLI may warn that it used the account key — fine for a lab.

    UI way — Google Cloud console

    1. Cloud Storage → Create bucket in asia-south1 → upload index.html → Permissions → Grant access → allUsers = Storage Object Viewer; bucket menu → Edit website configuration → index.html.
    2. Open the object’s public URL.

    CLI way — the same thing with commands

    B=lab-site-$RANDOM; gcloud storage buckets create gs://$B --location=asia-south1 --uniform-bucket-level-access --quiet
echo '<h1>Lab exam site</h1>' > index.html
gcloud storage cp index.html gs://$B
gcloud storage buckets update gs://$B --web-main-page-suffix=index.html
gcloud storage buckets add-iam-policy-binding gs://$B --member=allUsers --role=roles/storage.objectViewer >/dev/null
curl -s https://storage.googleapis.com/$B/index.html

    You should see: your heading. If the binding is refused, an organisation policy blocks public access — note it in your answer.

    Public access is correct here only because the task asked for a public website.

  4. 3 · Mock Task C: budget guard-rail and a final self-check (4 marks)

    Pick your cloud.

    UI way — AWS Management Console

    1. Billing → Budgets → Create budget → Cost budget, $5 monthly, alert at 80% actual to your email.
    2. Resource Groups & Tag Editor → Tag Editor → search tag lab=exam.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text)
aws budgets create-budget --account-id $ACC \
  --budget '{"BudgetName":"lab-exam","BudgetLimit":{"Amount":"5","Unit":"USD"},"TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[{"Notification":{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":80,"ThresholdType":"PERCENTAGE"},"Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]}]'
aws budgets describe-budget --account-id $ACC --budget-name lab-exam --query 'Budget.[BudgetName,BudgetLimit.Amount,TimeUnit]' --output text
aws resourcegroupstaggingapi get-resources --tag-filters Key=lab,Values=exam --query 'ResourceTagMappingList[].ResourceARN' --output text

    You should see: lab-exam 5.0 MONTHLY and the ARN of your tagged instance — configuration and tagging proven. Replace the email with yours.

    UI way — Azure portal

    1. Cost Management → Budgets → Add → 500 monthly; alert condition 80% actual to your email.
    2. All resources → filter tag lab=exam.

    CLI way — the same thing with commands

    az consumption budget create --budget-name lab-exam --amount 500 --category cost --time-grain monthly \
  --start-date $(date +%Y-%m-01) --end-date $(date -d '+1 year' +%Y-%m-01) >/dev/null
az consumption budget show --budget-name lab-exam --query "{name:name,amount:amount,grain:timeGrain}"
az resource list --tag lab=exam --query "[].{name:name,type:type}" -o table

    You should see: the budget (amount 500, Monthly) and a table with vm-lab, its disk, NIC, public IP, NSG and the storage account. Add the 80% email alert in the portal — the CLI command does not set notifications.

    UI way — Google Cloud console

    1. Billing → Budgets & alerts → Create budget → this project, ₹500, threshold 80% actual, email billing admins.
    2. Compute Engine → filter label lab:exam.

    CLI way — the same thing with commands

    BA=$(gcloud billing projects describe $(gcloud config get-value project) --format='value(billingAccountName)' | cut -d/ -f2)
gcloud billing budgets create --billing-account=$BA --display-name=lab-exam \
  --budget-amount=500INR --threshold-rule=percent=0.8
gcloud billing budgets list --billing-account=$BA --format='table(displayName,amount.specifiedAmount.units)'
gcloud compute instances list --filter='labels.lab=exam' --format='table(name,zone,status)'

    You should see: the budget row lab-exam 500 and your vm-lab RUNNING. The budget currency must match the billing account’s currency.

    Final self-check: re-run the curl commands from Tasks A and B — both must still work before you “submit”.

Clean up and cost check

AWS: aws ec2 terminate-instances --instance-ids $ID; aws ec2 wait instance-terminated --instance-ids $ID; aws ec2 delete-security-group --group-id $SG; aws s3 rb s3://$B --force; aws budgets delete-budget --account-id $ACC --budget-name lab-exam. Azure: az group delete -n rg-lab --yes --no-wait; az consumption budget delete --budget-name lab-exam. Google Cloud: gcloud compute instances delete vm-lab --zone=asia-south1-a --quiet; gcloud compute firewall-rules delete allow-http-lab --quiet; gcloud storage rm -r gs://$B; gcloud billing budgets list --billing-account=$BA then delete the budget by its ID with gcloud billing budgets delete.

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Not verifying from outside.Assuming “created” means “working”.curl after every task.
Opening every port “to be safe”.Panic.Only the ports the task names; extra rules can lose marks.
Debugging a broken VM by hand for 20 minutes.Sunk cost.Fix the script, terminate, relaunch.
Wrong Region or name.Not underlining values.Copy names from the task sheet; check the Region selector.
Deleting before marking.Tidiness habit.Clean up only when told.
No evidence.Rushing.Paste outputs into evidence.txt as you go.

Interview and viva questions

Can I use the console instead of the CLI?

Yes; the CLI is faster and repeatable once practised.

Which cloud should I practise in?

The one your exam or course uses; the routine is the same.

Will this cost money?

A few rupees if you delete the same day; use free-tier sizes.
