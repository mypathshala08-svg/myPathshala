2 Definition

Cloud design patterns

Formal definition (write this in exams)

Cloud design patterns are proven, reusable solutions to recurring problems in building scalable and resilient cloud systems — including load balancing (distribute requests across healthy instances), auto scaling (adjust capacity to demand), caching (cache-aside and edge caching to serve repeated reads from fast storage), queue-based load leveling, retry with exponential backoff and jitter, and the circuit breaker.

In simple words

Ready-made design ideas: share work across servers, add servers automatically, keep popular data close and in memory, buffer bursts, retry politely, and stop calling things that are broken.

Say it in an interview

30-second answer you can speak:

  • “For scale I combine a load balancer, an auto scaling group with target tracking, a cache-aside layer like ElastiCache for hot reads and a CDN for static content.”
  • “For resilience I put queues in front of slow work, use timeouts with exponential backoff and jitter for transient faults, and circuit breakers with fallbacks for failing dependencies.”

Type 1 · Load balancing

Definition (say it in an interview): The load balancing pattern places a balancer in front of a pool of interchangeable instances and distributes requests among the healthy ones using an algorithm — round robin, least outstanding requests/connections, weighted, or hash-based (sticky) — so no single instance is overloaded and failed instances are bypassed.

In plain words (no jargon): A dispatcher that sends each visitor to a server that is free and healthy, so the work is shared.

Analogy: The token system at a passport office: a dispatcher sends each person to whichever counter is free, and skips the counter whose officer is on leave.

How it works internally, step by step

  1. Register targets. Instances/containers/IPs in a target group or backend pool.
  2. Health checks. Only healthy targets receive traffic.
  3. Pick a target. Algorithm per request (L7) or per connection/flow (L4).
  4. Forward. Optionally terminate TLS and add headers (X-Forwarded-For).
  5. Drain. Deregistering targets finish in-flight requests first.

Words used above, in simple terms: round robin = take turns · least outstanding requests = the one with the fewest unfinished requests · sticky session = the same user always goes to the same server · connection draining = letting current requests finish before removal

TiffinGo’s ALB uses “least outstanding requests” because some API calls (order placement) take 10× longer than others (menu); round robin left one server choking while others idled.

Products and cloud services

For the experienced — did you know? Slow start mode gives a newly added instance a gradually increasing share of traffic — without it, a fresh instance with a cold cache and JIT compiler gets a full share instantly and can fail its first health checks under load.

Use it when: more than one instance serves the same workload.
Avoid / be careful when: you rely on sticky sessions for state — use an external session store instead.

Type 2 · Auto scaling

Definition (say it in an interview): The auto scaling pattern automatically adjusts the number of instances in a group to match demand using policies — target tracking on a metric, step rules, schedules or predictions — within minimum and maximum limits, working together with a load balancer and health checks.

In plain words (no jargon): The cloud adds servers automatically when the app gets busy and removes them when it gets quiet.

Analogy: A bank opening more counters when the queue grows and closing them in the quiet afternoon.

How it works internally, step by step

  1. Group. Launch template + min/max/desired.
  2. Policy. Target tracking (e.g. 50% CPU) or schedule.
  3. Alarm. Metric crosses the threshold.
  4. Act. Launch/terminate; register with LB after health checks.
  5. Cool down. Warm-up and cooldown prevent flapping.

Words used above, in simple terms: target tracking = keep a metric near a chosen value · cooldown = waiting time before another scaling action · flapping = scaling out and in repeatedly

Use it when: demand varies and the app tier is stateless.
Avoid / be careful when: start-up time is longer than the spike — pre-scale with schedules or keep warm capacity.

Type 3 · Cache-aside (lazy loading)

Definition (say it in an interview): The cache-aside pattern has the application check a cache before the data store: on a hit it returns the cached value; on a miss it reads the data store, writes the result into the cache with a time-to-live, and returns it; on updates it writes to the store and invalidates or updates the cache entry.

In plain words (no jargon): Keep a copy of popular data in fast memory. Look there first; only ask the slow database when the copy is missing or old.

Analogy: Keeping today’s menu written on a whiteboard at the counter: staff read the board instead of asking the chef every time — and rewrite it when the menu changes.

How it works internally, step by step

  1. Read. GET key from cache.
  2. Hit. Return immediately.
  3. Miss. Query the database, SET key with TTL, return.
  4. Update. Write to database, then delete (or update) the cache key.
  5. Evict. Memory full → least recently used keys removed.

Words used above, in simple terms: cache hit / miss = found / not found in the cache · TTL = time to live — when the cached copy expires · invalidation = removing a stale cached copy · eviction = the cache deleting old entries to free memory

Products and cloud services

Amazon ElastiCache (Redis OSS/Valkey, Memcached), MemoryDB, DynamoDB Accelerator (DAX); Azure Managed Redis; Google Memorystore; in-process caches.

For the experienced — did you know? When a hot key expires, thousands of requests can miss at once and stampede the database. Add jitter to TTLs, let one request refresh while others serve the stale value (“stale-while-revalidate”), or use request coalescing.

Use it when: data is read much more often than written and slightly stale data is acceptable.
Avoid / be careful when: every read must be perfectly fresh (balances, stock at checkout) — read from the database or use short TTLs and invalidation.

Type 4 · CDN / edge caching

Definition (say it in an interview): The edge caching pattern serves cacheable content — static files and, where possible, API responses — from a content delivery network’s edge locations close to users, controlled by cache headers and cache policies, offloading the origin and cutting latency.

In plain words (no jargon): Copies of your files are kept in many cities, so each user gets them from somewhere close — and your servers do less work.

Analogy: Regional warehouses of an e-commerce company: popular items ship from a nearby city instead of the central warehouse.

How it works internally, step by step

  1. Distribution. Origins (bucket, LB) and behaviours per path.
  2. Cache key. Path + chosen headers/cookies/query strings.
  3. TTL. From Cache-Control / policy.
  4. Invalidate or version. Purge paths or use new file names.
  5. Edge logic. Small functions for redirects, headers, A/B tests.

Words used above, in simple terms: Cache-Control = an HTTP header that says how long a response may be cached · cache key = what makes two requests “the same” · purge / invalidation = removing content from edge caches

Use it when: content is the same for many users — static assets, public pages, video, public API responses.
Avoid / be careful when: responses are personalised or private — or you cache errors and serve them to everyone.

Type 5 · Queue-based load leveling

Definition (say it in an interview): The queue-based load leveling pattern places a durable queue between a task producer and a service that processes the tasks, so bursts of requests are buffered and consumed at a sustainable rate, protecting the service from overload and keeping the producer responsive.

In plain words (no jargon): Put incoming jobs in a waiting line so the back end can work through them steadily instead of being flooded.

Analogy: A dam on a river: monsoon floods fill the reservoir, and the gates release water at a steady rate the canals can handle.

How it works internally, step by step

  1. Produce. Front end sends a message per task and replies at once.
  2. Store. The queue keeps messages durably.
  3. Consume. Workers poll, process, delete.
  4. Scale. Worker count follows queue depth.
  5. Fail safely. Retries and a dead-letter queue for poison messages.

Words used above, in simple terms: buffer = temporary storage that absorbs bursts · backlog = messages waiting in the queue · poison message = a message that always fails processing · DLQ = dead-letter queue — where failed messages are parked

Use it when: work can be done slightly later and arrives in bursts.
Avoid / be careful when: the user needs the result immediately in the same request.

Type 6 · Retry with exponential backoff and jitter

Definition (say it in an interview): The retry pattern handles transient faults by retrying failed operations; exponential backoff increases the wait between attempts (e.g. 100 ms, 200 ms, 400 ms…) and jitter randomises it so many clients do not retry simultaneously, with a maximum number of attempts and only for safe (idempotent) operations.

In plain words (no jargon): If something fails for a moment, try again — but wait a bit longer each time and add a random delay, so everyone does not retry at the same instant.

Analogy: Calling a busy customer-care number: if it is engaged, you wait a minute, then two, then four — and everyone else waits a different random time, so the line is not flooded at the same second.

How it works internally, step by step

  1. Classify. Retry only transient errors (timeouts, 429, 503).
  2. Wait. base × 2^attempt, capped.
  3. Jitter. random(0, wait) — “full jitter”.
  4. Limit. Max attempts and a total time budget.
  5. Idempotency. Safe to repeat — or use an idempotency key.

Words used above, in simple terms: transient fault = a short, temporary error · exponential backoff = waiting longer each time, doubling · jitter = random variation in the wait · idempotent = doing it twice has the same effect as once

Real-world example

The AWS Architecture Blog’s analysis “Exponential Backoff and Jitter” showed that adding full jitter dramatically reduces the total work and completion time compared with plain exponential backoff — the reason SDKs use it by default.

Real scenario (TiffinGo)

TiffinGo’s app retries a failed menu fetch up to 3 times with “full jitter” backoff; order placement retries carry an idempotency key so a retry never creates two orders. The AWS SDKs do this by default.

Products and cloud services

Built into AWS SDKs (standard/adaptive retry modes), Azure SDK retry policies, Google client libraries; libraries like Polly (.NET), resilience4j (Java), tenacity (Python).

For the experienced — did you know? Retries multiply across layers: 3 retries in the app × 3 in the SDK × 3 in the load balancer = up to 27 calls for one user click. Retry at one layer, close to the client, and use a retry budget.

Use it when: errors are transient — throttling (429), timeouts, brief network issues.
Avoid / be careful when: the error is permanent (400, 403) or the operation is not idempotent without a key — retries make it worse.

Type 7 · Circuit breaker

Definition (say it in an interview): The circuit breaker pattern wraps calls to a remote dependency and tracks failures; when failures exceed a threshold it opens and fails calls immediately (often with a fallback) for a period, then lets a few trial calls through (half-open) and closes again if they succeed — preventing cascading failures and giving the dependency time to recover.

In plain words (no jargon): If another service keeps failing, stop calling it for a while and use a backup plan, instead of waiting and getting stuck. Try again later.

Analogy: The electrical MCB in your house: when a fault draws too much current it trips at once to protect the wiring; you reset it after the fault is fixed.

How it works internally, step by step

  1. Wrap. All calls to the dependency go through the breaker.
  2. Count. Errors/timeouts in a rolling window.
  3. Open. Threshold reached → fail fast + fallback.
  4. Wait. Open for N seconds.
  5. Half-open. Trial calls decide close or re-open.

Words used above, in simple terms: cascading failure = one failure causing failures upstream · fallback = the backup behaviour when a call fails · timeout = the maximum time to wait for a reply · half-open = testing state after a pause

Netflix popularised circuit breakers with its open-source Hystrix library (2012); it is now in maintenance mode and the industry moved to resilience4j and to breakers built into service meshes like Istio/Envoy.

Real scenario (TiffinGo)

When the payment provider slowed to 8 seconds, TiffinGo’s threads all waited and the whole app froze. Now a breaker with a 2-second timeout opens after 5 failures; for 30 seconds checkout offers “pay on delivery”, and menu browsing stays fast.

Products and cloud services

Libraries: resilience4j, Polly, Hystrix (retired), Envoy/Istio outlier detection; managed: App Mesh successors/Service mesh policies, Azure API Management circuit breaker, Apigee; Step Functions error handling.

For the experienced — did you know? Every remote call needs a timeout shorter than the caller’s own timeout — otherwise the breaker never sees failures quickly enough, and threads pile up long before it opens.

Use it when: a call to another service can fail or slow down — payments, third-party APIs, other microservices.
Avoid / be careful when: there is no sensible fallback and the caller must wait — then use timeouts and clear errors instead.

6 Explained part by part

Six supporting ideas

Health check

What it is: Probe that decides if a target gets traffic.

Why it exists: Feeds load balancing and auto scaling.

Where it is used: LB target health, MIG autohealing.

Idempotency key

What it is: A unique ID per operation.

Why it exists: Makes retries safe (no double orders).

Where it is used: Payment APIs, SQS FIFO deduplication.

TTL

What it is: How long cached data is valid.

Why it exists: Balances freshness and load.

Where it is used: Redis EXPIRE, Cache-Control max-age.

Dead-letter queue

What it is: Holding area for failed messages.

Why it exists: Stops poison messages blocking work.

Where it is used: SQS DLQ, Service Bus DLQ, Pub/Sub dead-letter topic.

Timeout

What it is: Maximum wait for a call.

Why it exists: Without it, breakers and retries cannot work.

Where it is used: SDK and HTTP client settings.

Sharding

What it is: Splitting data across nodes by key.

Why it exists: Scales writes beyond one database.

Where it is used: DynamoDB partitions, Cosmos DB partition keys, Spanner splits.

Myth vs reality: things many websites still say

  • Myth: More retries = more reliable.
    Reality: Retries multiply load; use backoff, jitter and limits.
    Proof: Type 6.
  • Myth: Caching is free performance.
    Reality: It brings staleness and stampedes to manage.
    Proof: Type 3.
  • Myth: Auto scaling handles every spike.
    Reality: Instances take minutes; pre-scale and cache.
    Proof: Type 2.

  2. 1 · A load-balanced web tier across two zones

    Pick your cloud.

    UI way — AWS Management Console

    1. Create security group tiffingo-web-sg allowing HTTP 80 from anywhere (lab).
    2. Launch templates → tiffingo-web-lt: Amazon Linux 2023, t3.micro, that SG, Advanced details → User data = the script below.
    3. Target groups → tiffingo-tg (instances, HTTP 80, health check /). Load balancers → Application Load Balancer → internet-facing, AZs 1a + 1b, SG tiffingo-web-sg, listener 80 → tiffingo-tg.
    4. Auto Scaling groups → tiffingo-web-asg from the template, subnets 1a + 1b, attach to tiffingo-tg, desired/min 2, max 4, ELB health checks.

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
dnf install -y nginx
echo "<h1>served by $(hostname)</h1>" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
EOF
VPC=$(aws ec2 describe-vpcs --filters Name=is-default,Values=true --query 'Vpcs[0].VpcId' --output text)
SUBS=$(aws ec2 describe-subnets --filters Name=default-for-az,Values=true --query 'Subnets[0:2].SubnetId' --output text)
SG=$(aws ec2 create-security-group --group-name tiffingo-web-sg --description web --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr 0.0.0.0/0
aws ec2 create-launch-template --launch-template-name tiffingo-web-lt --launch-template-data \
  "{\"ImageId\":\"resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64\",\"InstanceType\":\"t3.micro\",\"SecurityGroupIds\":[\"$SG\"],\"UserData\":\"$(base64 -w0 web.sh)\"}"
TG=$(aws elbv2 create-target-group --name tiffingo-tg --protocol HTTP --port 80 --vpc-id $VPC --query 'TargetGroups[0].TargetGroupArn' --output text)
LB=$(aws elbv2 create-load-balancer --name tiffingo-alb --subnets $SUBS --security-groups $SG --query 'LoadBalancers[0].LoadBalancerArn' --output text)
aws elbv2 create-listener --load-balancer-arn $LB --protocol HTTP --port 80 --default-actions Type=forward,TargetGroupArn=$TG
aws autoscaling create-auto-scaling-group --auto-scaling-group-name tiffingo-web-asg --launch-template LaunchTemplateName=tiffingo-web-lt \
  --min-size 2 --max-size 4 --desired-capacity 2 --vpc-zone-identifier "$(echo $SUBS | tr ' ' ',')" \
  --target-group-arns $TG --health-check-type ELB --health-check-grace-period 120
DNS=$(aws elbv2 describe-load-balancers --load-balancer-arns $LB --query 'LoadBalancers[0].DNSName' --output text)
sleep 180; curl http://$DNS

    You should see: <h1>served by ip-172-31-…</h1> from the ALB DNS name, once both targets are healthy (about 3 minutes). The ALB costs a few rupees per hour — delete it after the lab.

    UI way — Azure portal

    1. Virtual machine scale sets → Create → rg-tiffingo, tiffingo-vmss, Central India, zones 1, 2, orchestration Uniform, Ubuntu 24.04, Standard_B1s, 2 instances.
    2. Networking → Load balancing options → Azure load balancer → create new; allow inbound HTTP 80. Advanced → Custom data = the Ubuntu script.
    3. After creation: load balancer → Health probes → add TCP 80; Load balancing rules → add port 80 → 80 using that probe.

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
apt-get update && apt-get install -y nginx
echo "<h1>served by $(hostname)</h1>" > /var/www/html/index.html
systemctl enable --now nginx
EOF
az group create --name rg-tiffingo --location centralindia
az network nsg create --resource-group rg-tiffingo --name web-nsg
az network nsg rule create --resource-group rg-tiffingo --nsg-name web-nsg --name http --priority 100 \
  --access Allow --protocol Tcp --destination-port-ranges 80
az vmss create --resource-group rg-tiffingo --name tiffingo-vmss --orchestration-mode Uniform --image Ubuntu2404 \
  --vm-sku Standard_B1s --instance-count 2 --zones 1 2 --lb-sku Standard --nsg web-nsg \
  --upgrade-policy-mode Automatic --custom-data web.sh --admin-username azureuser --generate-ssh-keys
LBN=$(az network lb list --resource-group rg-tiffingo --query '[0].name' --output tsv)
FE=$(az network lb frontend-ip list --resource-group rg-tiffingo --lb-name $LBN --query '[0].name' --output tsv)
BP=$(az network lb address-pool list --resource-group rg-tiffingo --lb-name $LBN --query '[0].name' --output tsv)
az network lb probe create --resource-group rg-tiffingo --lb-name $LBN --name http --protocol tcp --port 80
az network lb rule create --resource-group rg-tiffingo --lb-name $LBN --name http --protocol tcp --frontend-port 80 \
  --backend-port 80 --frontend-ip-name $FE --backend-pool-name $BP --probe-name http
IP=$(az network public-ip list --resource-group rg-tiffingo --query '[0].ipAddress' --output tsv)
sleep 120; curl http://$IP

    You should see: served by tiffingo-vmss000000 (or 000001) from the load balancer’s public IP.

    UI way — Google Cloud console

    1. Instance templates → web-tpl: e2-micro, Debian 12, network tag http-server, startup script = the Debian script.
    2. Instance groups → managed, multiple zones in asia-south1, 2 instances, port mapping http:80. Firewall: allow tcp:80 to tag http-server.
    3. Load balancing → Create load balancer → Application Load Balancer, public, global → backend = the group with an HTTP health check; frontend HTTP 80 → Create (ready in ~5 minutes).

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
apt-get update && apt-get install -y nginx
echo "<h1>served by $(hostname)</h1>" > /var/www/html/index.html
systemctl enable --now nginx
EOF
gcloud compute instance-templates create web-tpl --machine-type=e2-micro --image-family=debian-12 \
  --image-project=debian-cloud --tags=http-server --metadata-from-file=startup-script=web.sh
gcloud compute firewall-rules create allow-http-web --allow=tcp:80 --target-tags=http-server
gcloud compute instance-groups managed create web-mig --region=asia-south1 --template=web-tpl --size=2
gcloud compute instance-groups managed set-named-ports web-mig --region=asia-south1 --named-ports=http:80
gcloud compute health-checks create http web-hc --port=80
gcloud compute backend-services create web-bs --protocol=HTTP --port-name=http --health-checks=web-hc --global
gcloud compute backend-services add-backend web-bs --instance-group=web-mig --instance-group-region=asia-south1 --global
gcloud compute url-maps create web-map --default-service=web-bs
gcloud compute target-http-proxies create web-proxy --url-map=web-map
gcloud compute forwarding-rules create web-fr --global --target-http-proxy=web-proxy --ports=80
IP=$(gcloud compute forwarding-rules describe web-fr --global --format='value(IPAddress)')
sleep 300; curl http://$IP

    You should see: served by web-mig-xxxx from one global anycast IP (the first minutes may return 404/502 while the LB programs).

    One address in front, two servers in two zones behind it — the base of every scalable web tier.

  3. 2 · Add a target-tracking auto scaling policy

  4. 3 · Watch it balance — and route around a stopped server

    Pick your cloud.

    UI way — AWS Management Console

    1. Open the ALB DNS name in a browser and refresh several times: the hostname changes.
    2. Instances → stop one instance → Target groups → Targets: it becomes unhealthy/unused; the page keeps working from the other. Auto Scaling then replaces it.

    CLI way — the same thing with commands

    for i in $(seq 1 6); do curl -s http://$DNS; done | sort | uniq -c
V=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names tiffingo-web-asg --query 'AutoScalingGroups[0].Instances[0].InstanceId' --output text)
aws ec2 stop-instances --instance-ids $V
sleep 60; for i in $(seq 1 6); do curl -s http://$DNS; done | sort | uniq -c
aws elbv2 describe-target-health --target-group-arn $TG --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State]' --output table

    You should see: first two hostnames sharing the requests, then only one; target health shows the stopped one as unused/unhealthy, and the group launches a replacement.

    UI way — Azure portal

    1. Open http://PUBLIC-IP and refresh — two instance names alternate (new connections).
    2. Scale set → Instances → select one → Stop. The probe fails and the LB sends traffic only to the running instance.

    CLI way — the same thing with commands

    for i in $(seq 1 6); do curl -s http://$IP; done | sort | uniq -c
ID=$(az vmss list-instances --resource-group rg-tiffingo --name tiffingo-vmss --query "[0].instanceId" --output tsv)
az vmss stop --resource-group rg-tiffingo --name tiffingo-vmss --instance-ids $ID
sleep 30; for i in $(seq 1 6); do curl -s http://$IP; done | sort | uniq -c

    You should see: two hostnames, then one. (Azure Load Balancer hashes by connection 5-tuple, so curl’s new connections spread; a browser keeping one connection may stick.)

    UI way — Google Cloud console

    1. Open http://LB-IP and refresh — hostnames vary.
    2. VM instances → stop one group instance; Load balancing → web-lb → backend shows 1 of 2 healthy; the MIG restarts it to keep 2 running.
    3. Optional: backend web-bs → Edit → tick Enable Cloud CDN — caching at the edge with one switch.

    CLI way — the same thing with commands

    for i in $(seq 1 6); do curl -s http://$IP; done | sort | uniq -c
V=$(gcloud compute instance-groups managed list-instances web-mig --region=asia-south1 --format='value(instance.basename())' --limit=1)
Z=$(gcloud compute instance-groups managed list-instances web-mig --region=asia-south1 --format='value(instance.segment(-3))' --limit=1)
gcloud compute instances stop $V --zone=$Z
sleep 60; gcloud compute backend-services get-health web-bs --global --format='table(status.healthStatus[].instance.basename(),status.healthStatus[].healthState)'
gcloud compute backend-services update web-bs --enable-cdn --global     # optional: edge caching

    You should see: two hostnames, then health showing one UNHEALTHY while traffic continues from the other; the MIG brings the stopped VM back.

    Health checks connect the patterns: the load balancer stops sending traffic, the scaling group restores capacity.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Retrying everything, instantly, at every layer.Retries feel safe.Retry once per call chain with backoff + jitter; idempotency keys.
No timeouts on remote calls.Library defaults are minutes.Short explicit timeouts; circuit breakers around dependencies.
Caching without invalidation.TTL only.Delete keys on update; short TTLs for volatile data.
Sticky sessions instead of a session store.Quick fix for logins.Stateless app tier + Redis/DynamoDB sessions.
Scaling on CPU for I/O-bound apps.Default metric.Scale on requests per target, latency or queue backlog.
Queues without DLQs and age alarms.Happy-path testing.DLQ + alarm on oldest-message age.

14 Quiz and revision

Check yourself

Quick revision

Lesson 7.5 in one screen

  • LB algorithms: round robin, least outstanding, hash/sticky; health checks; draining.
  • Auto scaling: target tracking + schedules; scale on the right metric.
  • Cache-aside: check cache → DB on miss → set with TTL; invalidate on update; beware stampedes.
  • CDN edge caching: Cache-Control, versioned files.
  • Queue-based leveling: buffer bursts; DLQ; alarm on oldest age.
  • Retry: transient only, exponential backoff + jitter, limits, idempotency.
  • Circuit breaker: closed → open → half-open; timeouts first.

Interview and viva questions

Do I need all seven patterns?

No — apply each where its problem exists; most web apps use at least LB, auto scaling, caching and retries.

Redis or a CDN?

Both: CDN caches HTTP responses near users; Redis caches data next to the app.

Do AWS SDKs retry automatically?

Yes — with exponential backoff and jitter; configure limits rather than adding your own loops on top.
