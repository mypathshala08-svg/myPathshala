1 The story

Four customers, one question

Before you start: Modules 2, 3 and 10.1.

🤔 Four TiffinGo customers ask the same question in one week: a two-person start-up, a cooperative bank, a state health department and an engineering college. “Which cloud model should we use?” Should they all get the same answer?

No. The right deployment model (Module 3), service model (Module 2) and provider (10.1) depend on the organisation: its size, money, skills, regulations, data sensitivity and growth. This lesson works through seven organisation types one by one, animates the decision for one real scenario, and on your own account you use the providers’ review tools, set up cost allocation by department, and check that the services a scenario needs exist in India Regions.

  • The same app can be right on serverless for a start-up and wrong for a bank.
  • Why government and banks start with compliance, not with features.
  • A repeatable seven-question method you can use in any interview case study.

2 Definition

Organisational scenarios: which cloud model fits

Formal definition (write this in exams)

Choosing a cloud model for an organisation means analysing its users, data sensitivity, regulatory obligations, skills, budget structure, existing systems and growth, and from that selecting the deployment model (public, private, hybrid, community, multi-cloud, sovereign), the service model per workload (IaaS, PaaS, SaaS, serverless), the provider(s), and the governance needed to operate safely.

In simple words

Different organisations need different cloud setups; ask about their users, data, rules, skills and money first, then choose.

Say it in an interview

30-second answer you can speak:

  • “I start with constraints — data sensitivity and regulations — then skills and budget. A start-up gets public cloud and serverless; a bank gets India Regions, hybrid with core on-prem, CMKs and tested DR; government uses MeitY-empanelled offerings.”
  • “Then I choose service models per workload, pick providers by fit and skills, and define governance: identity, guard-rails, logging, budgets and an exit plan.”

Type 1 · Start-up

Definition (say it in an interview): A start-up typically chooses a single public cloud with serverless and PaaS services to ship quickly with a tiny team, uses startup credit programmes, avoids upfront spending, and optimises costs and architecture once product–market fit is clear.

In plain words (no jargon): New small companies: use ready-made cloud services to launch fast and pay only as they grow.

Analogy: A food truck: rent the vehicle, cook simple dishes fast, move to a restaurant only when the crowds are reliable.

How it works internally, step by step

  1. Credits. Apply to startup programmes.
  2. Managed first. Serverless/PaaS/SaaS.
  3. Guard-rails. Budgets, MFA, no root keys.
  4. Measure. Unit cost per order.
  5. Optimise. When usage is steady.

Words used above, in simple terms: MVP = minimum viable product · burn rate = money spent per month · product–market fit = customers clearly want the product

Type 2 · Small and medium business (SME)

Definition (say it in an interview): A small or medium business usually gets most value from SaaS (email, accounting, CRM, inventory) and simple PaaS hosting, avoids running servers, relies on a managed-service partner for setup, and focuses security effort on identity (MFA), backups and device protection.

In plain words (no jargon): Small businesses: use online software for most things and avoid running their own servers.

Analogy: A neighbourhood restaurant: buys gas, POS and delivery apps as services; the owner focuses on food, not on building tools.

How it works internally, step by step

  1. Identify. Business functions.
  2. SaaS. Choose products (2.3 checklist).
  3. Identity. One login with MFA.
  4. Backup. Export/backup SaaS data.
  5. Partner. Local MSP for support.

Words used above, in simple terms: MSP = managed service provider · SME = small and medium enterprise · Lightsail = AWS’s simplified VPS service

Type 3 · Large enterprise

Definition (say it in an interview): A large enterprise usually adopts hybrid and often multi-cloud operations: it builds a governed landing zone (account/subscription/project hierarchy, identity federation, network hub, guard-rails, logging), migrates application portfolios in waves using the 7 Rs, keeps some systems on-premises for years, and runs a cloud centre of excellence and FinOps practice.

In plain words (no jargon): Big companies: build strong cloud rules first, then move applications step by step, keeping some on-premises.

Analogy: Moving a big joint family into a new apartment complex: first agree on rules, keys and electricity meters, then move one family at a time.

How it works internally, step by step

  1. Strategy. Business case, CoE.
  2. Landing zone. Hierarchy, identity, network, logs.
  3. Portfolio. Assess, 7 Rs, waves.
  4. Operate. FinOps, security, SRE.
  5. Modernise. Replatform/refactor over time.

Words used above, in simple terms: landing zone = pre-built, governed cloud environment · CoE = cloud centre of excellence · FinOps = financial operations for cloud costs

Type 4 · Bank, insurer or fintech

Definition (say it in an interview): A regulated financial institution in India typically uses public cloud in Indian Regions (often hybrid with core systems on-premises or in a private cloud), driven by RBI directions on IT governance, outsourcing and payment-data localisation, with strong encryption and key control, multi-AZ and DR designs, audit rights in contracts and a documented exit strategy.

In plain words (no jargon): Banks and payment companies: follow RBI rules, keep payment data in India, and design for no downtime.

Analogy: A jewellery shop using a bank vault: fine to store gold there, but with insured contracts, inspection rights and a plan to move it if needed.

How it works internally, step by step

  1. Classify. Critical vs non-critical.
  2. Approve. Board/IT strategy committee.
  3. Design. India Regions, DR, CMKs.
  4. Contract. Audit rights, exit.
  5. Report. Incidents to CERT-In/RBI.

Words used above, in simple terms: outsourcing = using a third party for a service · exit strategy = plan to move away from a provider · core banking = main account and transaction system

Type 5 · Government or public-sector undertaking

Definition (say it in an interview): A government department or PSU typically uses community/government cloud offerings from MeitY-empanelled providers (MeghRaj), procured through tenders or GeM, with data hosted in India, strong security audits (often STQC/CERT-In-empanelled auditors) and architectures that handle citizen-scale peaks around deadlines.

In plain words (no jargon): Government offices: buy approved cloud services through official channels and keep data in India.

Analogy: A city’s water board: everyone depends on it, rules are strict, demand peaks every morning, and any outage is front-page news.

How it works internally, step by step

  1. Policy. Check cloud policy and empanelment.
  2. Procure. Tender/GeM.
  3. Secure. Audit, MFA, logging.
  4. Scale. Load test for deadlines.
  5. Operate. SLAs, helpdesk.

Words used above, in simple terms: GeM = Government e-Marketplace for procurement · NIC = National Informatics Centre · STQC = government testing and quality certification body

Type 6 · Hospital or health organisation

Definition (say it in an interview): A hospital or health organisation commonly runs hybrid: clinical systems and devices on-premises or at the edge for uptime and latency, with cloud used for patient apps, analytics, imaging archives, DR and AI; it applies strong privacy controls (DPDP, health-sector standards such as ABDM guidelines; HIPAA for US data), encryption, access logging and tested offline procedures.

In plain words (no jargon): Hospitals: keep critical medical systems close and always running, and use the cloud for apps, analysis and backup — with strict privacy.

Analogy: An ambulance service: lifesaving equipment must work in the van even with no network, while records sync to the central system later.

How it works internally, step by step

  1. Classify. Clinical vs non-clinical.
  2. Edge. Local for devices/critical.
  3. Cloud. Apps, archive, analytics, DR.
  4. Privacy. Consent, access logs, encryption.
  5. Drills. Downtime procedures.

Words used above, in simple terms: EHR = electronic health record · PACS = medical imaging archive system · ABDM = Ayushman Bharat Digital Mission

Type 7 · College, university or research institute

Definition (say it in an interview): A college or research institute typically combines public cloud sandboxes for teaching (education programmes, credits, auto-expiring accounts), cloud bursting from on-campus HPC clusters to cloud GPUs/CPUs for research deadlines, SaaS for email and learning platforms, and strict budget guard-rails because grants and fees are fixed.

In plain words (no jargon): Colleges: give students safe cloud practice accounts and let researchers rent big computers only when needed — within budget.

Analogy: A college lab with a booking sheet: students get time on equipment, big experiments book extra machines, and the lab manager watches the budget.

How it works internally, step by step

  1. Sandboxes. Per student/class.
  2. Guard-rails. Allowed services, Regions, sizes.
  3. Budgets. Alerts + auto-stop.
  4. Burst. HPC/GPU for research.
  5. Clean-up. End-of-semester deletion.

Words used above, in simple terms: sandbox = isolated practice environment · education credits = free cloud usage for learning · HPC = high-performance computing

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You run a structured design review, set up department cost allocation and check Regional service availability — the three checks every scenario answer needs. All free.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

    CLI way — the same thing with commands

    WL=$(aws wellarchitected create-workload --workload-name state-nutrition-app --description 'Scenario review' --environment PRODUCTION \
  --lenses wellarchitected --aws-regions ap-south-1 --review-owner you@example.com --client-request-token $RANDOM --query WorkloadId --output text)
aws wellarchitected list-answers --workload-id $WL --lens-alias wellarchitected --pillar-id security --max-results 5 --query 'AnswerSummaries[].[QuestionId,QuestionTitle]' --output table

    You should see: a workload ID and the first security questions (e.g. “How do you securely operate your workload?”). The tool is free.

    UI way — Azure portal

    1. Advisor → Advisor score shows scores per Well-Architected pillar; the Azure Well-Architected Review assessment (Microsoft Learn) gives a full questionnaire.

    CLI way — the same thing with commands

    SUB=$(az account show --query id -o tsv)
az rest --method get --url "https://management.azure.com/subscriptions/$SUB/providers/Microsoft.Advisor/advisorScore?api-version=2023-01-01" \
  --query "value[].{category:name,score:properties.lastRefreshedScore.score}" -o table

    You should see: scores per category (Cost, Security, Reliability, OperationalExcellence, Performance, Advisor) — empty or low on a new subscription with no resources.

    UI way — Google Cloud console

    1. Recommendations (Active Assist) groups findings by Architecture Framework pillars; use the framework’s checklists for the scenario review.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
for r in google.iam.policy.Recommender google.compute.instance.IdleResourceRecommender; do echo "== $r"; gcloud recommender recommendations list --project=$P --location=global --recommender=$r --format="value(description)" 2>/dev/null | head -3; done

    You should see: recommendation descriptions per recommender (possibly none on a quiet project).

    Reviews turn “it depends” into a checklist — use them for every scenario answer.

  3. 2 · Allocate costs by department (showback for any organisation)

    Pick your cloud.

    UI way — AWS Management Console

    1. Tag resources with department. Billing and Cost Management → Cost allocation tags → activate department → Cost Explorer can group by it.

    CLI way — the same thing with commands

    B=tg-dept-$RANDOM; aws s3 mb s3://$B --region ap-south-1
aws s3api put-bucket-tagging --bucket $B --tagging 'TagSet=[{Key=department,Value=district-pune}]'
aws ce update-cost-allocation-tags-status --cost-allocation-tags-status TagKey=department,Status=Active 2>&1 | tail -2
aws ce list-cost-allocation-tags --tag-keys department --query 'CostAllocationTags[].[TagKey,Status]' --output text

    You should see: department Active once AWS has seen the tag in billing data (new tags can take up to 24 hours to appear; activation may fail until then — retry tomorrow).

    UI way — Azure portal

    1. Policy → Assign policy → “Inherit a tag from the resource group if missing” → tag name department → system-assigned identity → Create. Tag the resource group.

    CLI way — the same thing with commands

    az group create -n rg-dept -l centralindia --tags department=district-pune
az policy assignment create -n inherit-dept -g rg-dept --policy ea3f2387-9b95-492a-a190-fcdc54f7b070 \
  --params '{"tagName":{"value":"department"}}' --mi-system-assigned --location centralindia
az storage account create -n tgdept$RANDOM -g rg-dept -l centralindia --sku Standard_LRS --query tags

    You should see: the new storage account automatically gets {"department": "district-pune"} (policy effects can take a few minutes to start).

    UI way — Google Cloud console

    1. Manage resources → select project → Labels → add department=district-pune. Labels flow into billing exports and reports.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud projects update $P --update-labels=department=district-pune
gcloud projects describe $P --format="value(labels)"

    You should see: department=district-pune.

    Every organisation type needs to know who spends what — tags/labels are the cheapest control.

  4. 3 · Check that the scenario’s services exist in India Regions

    Pick your cloud.

    UI way — AWS Management Console

    1. Open the AWS “Regional services” list → filter Asia Pacific (Mumbai) and (Hyderabad) → check each needed service.

    CLI way — the same thing with commands

    for s in lambda eks bedrock healthlake; do printf '%-12s ' $s; aws ssm get-parameters-by-path --path /aws/service/global-infrastructure/services/$s/regions --region us-east-1 \
  --query "Parameters[?Value=='ap-south-1' || Value=='ap-south-2'].Value" --output text; echo; done

    You should see: each service followed by the India Regions where it is available (blank = not in India yet — a design constraint).

    UI way — Azure portal

    1. Open “Products available by region” → choose Central India → search the products the scenario needs.

    CLI way — the same thing with commands

    for p in Microsoft.App:containerApps Microsoft.DBforPostgreSQL:flexibleServers Microsoft.HealthcareApis:workspaces; do ns=${p%%:*}; rt=${p##*:}
  printf "%-45s " $p; az provider show -n $ns --query "resourceTypes[?resourceType=='$rt'].locations[] | [?contains(@,'India')]" -o tsv | tr '\n' ' '; echo; done

    You should see: each resource type with the India Regions that support it.

    UI way — Google Cloud console

    1. Open the Google Cloud “Cloud locations” page → filter asia-south1 / asia-south2 → check products.

    CLI way — the same thing with commands

    gcloud run regions list --format="value(locationId)" | grep asia-south
gcloud ai models list --region=asia-south1 --limit=1 2>&1 | tail -1

    You should see: asia-south1/asia-south2 for Cloud Run, and whether Vertex AI responds in Mumbai (an error naming an unsupported location means “not available here”).

    Residency rules are useless if the service you need does not exist in that Region — check early.

Clean up and cost check

AWS: aws wellarchitected delete-workload --workload-id $WL --client-request-token $RANDOM; aws s3 rb s3://$B --force. Azure: az policy assignment delete -n inherit-dept -g rg-dept; az group delete -n rg-dept --yes --no-wait. Google Cloud: gcloud projects update $P --remove-labels=department.
