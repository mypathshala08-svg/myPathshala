2 Definition

Cloud careers and certifications

Formal definition (write this in exams)

Cloud careers span roles such as cloud support and administration, cloud/DevOps and platform engineering, solutions architecture, cloud security, data engineering, ML/AI engineering and FinOps; cloud certifications — offered by AWS, Microsoft, Google and vendor-neutral bodies at foundational, associate, professional and specialty levels — validate knowledge for these roles, and are most effective when combined with hands-on projects and strong fundamentals.

In simple words

Choose a cloud job role, learn the basics, earn the matching certificate, and build real projects you can show and explain.

Say it in an interview

30-second answer you can speak:

  • “I’m targeting a data-engineer role: I have Spark, Hive and Kafka from PGCP-BDA, I’m taking the AWS Data Engineer – Associate, and my portfolio has a deployed pipeline with CI/CD and monitoring.”
  • “Certifications show I know the services; my projects show I can build and debug them.”

Type 1 · Cloud support engineer / cloud administrator

Definition (say it in an interview): A cloud support engineer or administrator operates cloud environments day to day: managing identities and access, monitoring and responding to alerts, patching, backups and restores, cost hygiene and user requests, following runbooks and gradually automating routine work.

In plain words (no jargon): The person who keeps cloud systems running every day — users, alerts, backups and fixes.

Analogy: The facilities manager of an office building: lights, access cards, repairs and safety checks — every day.

How it works internally, step by step

  1. Skills. Linux/Windows, networking, IAM.
  2. Tools. Console, CLI, monitoring.
  3. Daily. Tickets, alerts, patching.
  4. Growth. Scripting, IaC.
  5. Next role. Cloud/DevOps engineer.

Words used above, in simple terms: runbook = step-by-step fix instructions · ticket = tracked request or issue · on-call = rota for responding out of hours

Type 2 · Cloud engineer / DevOps or platform engineer

Definition (say it in an interview): A cloud or DevOps/platform engineer builds and automates cloud infrastructure and delivery: infrastructure as code, CI/CD pipelines, container platforms, observability, reliability practices and internal developer platforms that let application teams ship safely.

In plain words (no jargon): An engineer who automates how cloud systems are built, tested and released.

Analogy: The engineer who designs the factory’s assembly line, so every product is built the same way, quickly and safely.

How it works internally, step by step

  1. Skills. Linux, Git, Python/Bash, networking.
  2. IaC. Terraform/Bicep/CloudFormation.
  3. Pipelines. GitHub Actions, CodePipeline.
  4. Platforms. Kubernetes, serverless.
  5. Reliability. SLOs, on-call.

Words used above, in simple terms: platform engineering = building internal tools/platforms for developers · SRE = site reliability engineering · CKA = Certified Kubernetes Administrator

Type 3 · Solutions architect

Definition (say it in an interview): A solutions architect designs cloud solutions that meet business and technical requirements — choosing services, deployment and service models, security, reliability and cost trade-offs — documents decisions, reviews designs against well-architected frameworks and guides teams and customers through implementation.

In plain words (no jargon): The person who designs the overall cloud system so it meets business needs safely and at the right cost.

Analogy: The architect of a housing project: understands the families’ needs, the land rules and budget, then draws a plan builders can follow.

How it works internally, step by step

  1. Requirements. Functional + non-functional.
  2. Options. Compare 2–3 designs.
  3. Review. Well-Architected.
  4. Document. Diagrams + ADRs.
  5. Guide. Delivery support.

Words used above, in simple terms: non-functional requirement = quality needs: performance, security, availability · pre-sales architect = architect who helps customers before purchase · reference architecture = reusable proven design

Type 4 · Cloud security engineer

Definition (say it in an interview): A cloud security engineer protects cloud environments by designing identity and access, guard-rails, encryption and network controls, deploying threat detection and posture management, responding to incidents and supporting compliance audits, increasingly by writing security as code.

In plain words (no jargon): An engineer who keeps cloud accounts, data and users safe from attacks and mistakes.

Analogy: The security head of a large mall: designs access cards and cameras, watches alarms and runs drills.

How it works internally, step by step

  1. Identity. SSO, least privilege.
  2. Guard-rails. SCPs, policies.
  3. Detection. GuardDuty, Defender, SCC, SIEM.
  4. Response. Runbooks, forensics.
  5. Compliance. Evidence, audits.

Words used above, in simple terms: SIEM = security information and event management · CSPM = cloud security posture management · security as code = security controls written in IaC/policy

Type 5 · Data engineer

Definition (say it in an interview): A data engineer builds and operates pipelines that ingest, transform and serve data — batch and streaming — into data lakes, warehouses and lakehouses on the cloud, ensuring quality, governance, cost efficiency and reliability for analytics and machine learning.

In plain words (no jargon): An engineer who builds the pipes that move and clean data so others can analyse it.

Analogy: The water-supply engineer of a city: collects water from many sources, cleans it, and delivers it reliably to every tap.

How it works internally, step by step

  1. SQL + Python. Core languages.
  2. Ingest. CDC, streams, files.
  3. Process. Spark, SQL, dbt.
  4. Store. Lake, warehouse, lakehouse.
  5. Govern. Quality, catalogues, cost.

Words used above, in simple terms: lakehouse = combination of data lake and warehouse · CDC = change data capture · dbt = tool for SQL transformations

Type 6 · ML / AI engineer

Definition (say it in an interview): An ML or AI engineer takes machine-learning and generative-AI models into production on the cloud: preparing data, training or fine-tuning, deploying endpoints, building retrieval-augmented and agentic applications, and monitoring quality, cost and safety (MLOps/LLMOps).

In plain words (no jargon): An engineer who puts AI models into real apps on the cloud and keeps them working well.

Analogy: A chef who not only creates a new recipe but also sets up the kitchen so it can be cooked the same way every day for thousands of customers.

How it works internally, step by step

  1. Data. Features, labelling.
  2. Train. Or use foundation models.
  3. Deploy. Endpoints, batch.
  4. GenAI. RAG, agents, evaluation.
  5. Monitor. Drift, cost, safety.

Words used above, in simple terms: MLOps = operations practices for ML · RAG = retrieval-augmented generation · drift = model accuracy falling as data changes

Type 7 · FinOps practitioner / cloud cost analyst

Definition (say it in an interview): A FinOps practitioner brings finance, engineering and business together to manage cloud spend: making costs visible and allocated, optimising usage and pricing (right-sizing, commitments, waste removal), forecasting, and tracking unit economics so cloud spending delivers business value.

In plain words (no jargon): Someone who helps companies understand and control what they spend on the cloud.

Analogy: A household budget planner who knows exactly which family member spends on what, cancels unused subscriptions and plans the next year’s expenses.

How it works internally, step by step

  1. Allocate. Tags, accounts, showback.
  2. Analyse. Trends, anomalies.
  3. Optimise. Rightsize, commit, schedule.
  4. Forecast. Budgets.
  5. Unit metrics. Cost per order/user.

Words used above, in simple terms: unit economics = cost per business unit, e.g. per order · commitment = Savings Plan/reservation/CUD · FOCUS = open standard for cloud billing data

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You start your career portfolio by publishing a site, and set up free-tier tracking so your weekly practice stays free.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Publish your portfolio site (on any — or all three — clouds)

    Pick your cloud.

    UI way — AWS Management Console

    1. AWS Amplify → Create new app → Deploy without Git → name portfolio, branch main → drag the zip of your folder → Save and deploy.
    2. Amplify gives an HTTPS URL like https://main.APPID.amplifyapp.com.

zip -q site.zip index.html
APPID=$(aws amplify create-app --name portfolio --query app.appId --output text)

read JOB URL < <(aws amplify create-deployment --app-id $APPID --branch-name main --query '[jobId,zipUploadUrl]' --output text)
curl -s -T site.zip "$URL"
aws amplify start-deployment --app-id $APPID --branch-name main --job-id $JOB --query jobSummary.status --output text
echo https://main.$APPID.amplifyapp.com

    You should see: PENDING then, a minute later, your page at the printed HTTPS URL. Amplify Hosting has a free allowance for small static sites.

    UI way — Azure portal

    1. Storage account (Central India) → Static website → Enabled, index index.html → Save → upload to the $web container.
    2. The primary endpoint is an HTTPS URL ending in web.core.windows.net.

  3. 2 · Track free-tier usage so practice never costs money

    Pick your cloud.

    UI way — AWS Management Console

    1. Billing and Cost Management → Free Tier shows each service’s usage against its free limit and a forecast.
    2. New accounts (since July 2025) get credits and a free plan; the Account plan page shows remaining credits and days.

    CLI way — the same thing with commands

    aws freetier get-free-tier-usage --region us-east-1 --query 'freeTierUsages[].[service,usageType,actualUsageAmount,limit]' --output table | head -15
aws freetier get-account-plan-state --region us-east-1 --query '[accountPlanType,accountPlanStatus,accountPlanRemainingCredits.amount]' --output text 2>&1 | tail -1

    You should see: a table of services with used vs limit, and (for free-plan accounts) your plan type, status and remaining credits.

    UI way — Azure portal

    1. Subscriptions → your subscription → Free services (Azure free account) shows usage of each 12-month free service; Cost analysis shows credit burn.

    CLI way — the same thing with commands

    az consumption usage list --top 10 --query "[].{service:consumedService,quantity:usageQuantity,cost:pretaxCost}" -o table 2>&1 | tail -12

    You should see: recent usage rows with quantity and cost (often 0 on free services). The Free services blade is the clearest view of 12-month limits.

    UI way — Google Cloud console

    1. Billing → Overview shows free-trial credits remaining and days left; Reports grouped by service shows where credits go.

    CLI way — the same thing with commands

    gcloud billing accounts list --format="table(name,displayName,open)"
gcloud billing projects describe $(gcloud config get-value project) --format="value(billingEnabled,billingAccountName)"

    You should see: your billing account(s) and whether this project is linked — then check credits and reports in the console.

    Combine this with the budget alert from step 0: safe practice is part of a professional habit.

Clean up and cost check

Keep your portfolio online if you like (costs paise). To remove: AWS aws amplify delete-app --app-id $APPID; Azure az group delete -n rg-portfolio --yes --no-wait; Google Cloud gcloud storage rm -r gs://$B.
