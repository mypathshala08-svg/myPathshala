Resource pooling and multitenancy

How can millions of customers share the same cloud hardware — and three rival kitchens share one app — safely? Learn resource pooling, tenancy models (silo, pool, bridge) and how to stop noisy neighbours and data leaks.

1 The story

Three rival kitchens, one software

Before you start: 5.1 and 4.6 (noisy neighbours, isolation).

🤔 Can three rival cloud kitchens safely use the same software, on the same servers, with the same database?

Yes — that is multitenancy, and it is how almost every SaaS product and every public cloud works. But it has two classic dangers we reproduced in the lab: a query that forgets WHERE tenant_id = … returned every kitchen’s orders, and three “noisy neighbours” on one CPU core made the same job 3.8× slower (0.22 s → 0.84 s) — until we gave them a lower CPU weight (0.23 s). This lesson explains resource pooling, the tenancy models, and how isolation really works.

  • Resource pooling: why one big shared pool beats many private ones.
  • Single-tenant vs multi-tenant, and the SaaS silo / bridge / pool models.
  • Noisy neighbours and data leaks — and the controls that stop them.

TiffinGo’s ordering software is so good that other cloud kitchens want to use it. Selling it as a service raises two questions: what to share, and how to keep each customer safe from the others.

Riya

Sir, three other cloud kitchens want to buy our ordering software. Do we build three copies?

Arjun Sir

You could — one copy each, called single-tenant. Or one shared system serving all three, called multi-tenant. Most SaaS products do the second; it is cheaper and easier to update.

Kabir

But Annapurna must never see Dabbawala’s orders. And if Dabbawala runs a huge sale, Annapurna should not slow down.

Arjun Sir

Exactly the two risks: data isolation and noisy neighbours. AWS solves the same problems for millions of customers on shared hardware — that is resource pooling. Let’s see both levels.

2 Definition

Resource pooling and multitenancy

Formal definition (write this in exams)

Resource pooling (NIST SP 800-145) is the characteristic in which a provider’s computing resources are pooled to serve multiple consumers using a multi-tenant model, with physical and virtual resources dynamically assigned and reassigned according to consumer demand and a sense of location independence. Multitenancy is an architecture in which a single instance of software or infrastructure serves multiple customers (tenants), each logically isolated from the others while sharing underlying resources.

In simple words

Pooling: the cloud keeps one big shared pile of computers and hands out pieces on demand. Multitenancy: many customers share the same system, each kept separate from the others.

Say it in an interview

30-second answer you can speak:

  • “Resource pooling means the provider’s compute, storage and network are shared among many customers and assigned dynamically on demand; customers choose a Region, not a specific machine. It is what gives the cloud its economies of scale.”
  • “Multitenancy is many customers sharing one system with logical isolation. In SaaS there are three models: silo — a stack per tenant, pool — everything shared with tenant IDs, and bridge — shared app with per-tenant schemas.”
  • “The two risks are data leaks and noisy neighbours; I enforce tenant isolation in the database with row-level security and use per-tenant quotas. In a lab, three noisy processes made a job 3.8× slower until I lowered their CPU weight.”

Type 1 · Resource pooling

Definition (say it in an interview): Resource pooling is the NIST essential characteristic in which the provider’s computing resources — processing, memory, storage and network bandwidth — are pooled to serve multiple consumers using a multi-tenant model, with physical and virtual resources dynamically assigned and reassigned according to demand, and with a sense of location independence.

In plain words (no jargon): Instead of each customer owning their own computers, the cloud company keeps one huge shared collection of computers and gives each customer a share when they need it — and takes it back when they don’t.

Analogy: A city’s electricity grid: power stations feed one shared grid; your house draws what it needs and you never know which station produced your electrons. No family builds its own power plant.

How it works internally, step by step

  1. Aggregate. Many servers, disks and network links are managed as one pool by virtualization and cloud software.
  2. Abstract. Customers request resources by size (2 vCPU, 8 GB), not by physical machine.
  3. Place. A scheduler picks where to run each request based on free capacity.
  4. Reclaim. When resources are released they return to the pool for others.
  5. Statistical multiplexing. Because customers peak at different times, total capacity needed is far less than the sum of everyone’s peaks.
  6. Location independence. You choose a Region or AZ, never a specific rack or host.

Words used above, in simple terms: NIST = the US standards body whose cloud definition everyone uses · scheduler = software that decides where to run things · statistical multiplexing = sharing works because not everyone peaks at the same time · location independence = you do not know or choose the exact machine

Real-world example

Pooling is the economic engine of cloud providers: AWS, Azure and Google buy servers by the hundreds of thousands and keep them busy across millions of customers whose demand peaks at different times — something no single company’s private servers can match.

Real scenario (TiffinGo)

Inside TiffinGo, the kitchen, billing and analytics teams used to own separate servers; billing ran out of capacity while analytics idled. Moving all three onto one pooled Kubernetes cluster lets billing borrow capacity at month-end.

Products and cloud services

The infrastructure of every public cloud; private clouds (OpenStack), Kubernetes clusters, VMware DRS clusters; in your account: Auto Scaling groups and serverless services draw from the provider’s pool.

For the experienced — did you know? Pooling is why “Insufficient capacity” errors exist: the pool is finite per AZ and instance type. Flexible designs (several instance types, several AZs, Spot with fallbacks) draw from more of the pool and fail less.

Use it when: demand varies over time or across teams — pooling turns idle capacity into shared headroom.
Avoid / be careful when: one workload needs guaranteed, unshared performance or hardware (then dedicate part of the pool).

Type 2 · Single tenancy (dedicated)

Definition (say it in an interview): Single tenancy means a resource — a physical server, an application instance or a database — serves exactly one customer (tenant); in the cloud it is offered as dedicated instances, dedicated hosts or single-tenant SaaS deployments, trading higher cost for stronger isolation and control.

In plain words (no jargon): One customer gets something entirely to themselves — their own server or their own copy of the software — with nobody else sharing it.

Analogy: An independent bungalow: your own walls, garden and meter — maximum privacy and control, maximum cost, and every repair is yours to schedule.

How it works internally, step by step

  1. Choose tenancy at launch. EC2 tenancy: default (shared), dedicated, or host.
  2. Hardware fenced off. Dedicated instances never share a physical server with other accounts.
  3. Dedicated Host control. You allocate a host, see its cores/sockets, and place instances on it (host affinity).
  4. Licensing. Per-core software licences can be counted against the host’s physical cores.
  5. Cost. You pay a dedicated premium (instances) or for the whole host whether full or not.

Words used above, in simple terms: tenant = one customer of a shared system · BYOL = bring your own licence · host affinity = keeping an instance on the same physical host · sole-tenant node = Google’s name for a dedicated physical server

Type 3 · Infrastructure multitenancy (public cloud)

Definition (say it in an interview): Infrastructure multitenancy is the public-cloud model in which workloads of many independent customers (accounts) share the same physical hosts, storage systems and networks, with logical isolation enforced by virtualization, network virtualization, identity and encryption.

In plain words (no jargon): Many different companies’ virtual computers run on the same physical machines in the cloud, but strong walls in software and hardware keep each company’s data and traffic completely separate.

Analogy: A large apartment complex: hundreds of families share land, lifts and water lines, but each flat has its own lock and meter; the building management (provider) guarantees one family cannot walk into another’s flat.

How it works internally, step by step

  1. Accounts are the top boundary. Each customer’s resources, identities and bills live in separate accounts.
  2. Compute isolation. The hypervisor gives each VM its own memory and vCPUs (Lesson 4.1 type 3).
  3. Network isolation. Each VPC is an overlay with its own tag; Nitro enforces security groups.
  4. Storage isolation. Volumes are encrypted and mapped only to their owner’s instances.
  5. Control-plane isolation. IAM evaluates every API call against the caller’s account.
  6. Core isolation. Different customers never share a CPU core’s hyper-threads (Lesson 4.6).

Words used above, in simple terms: account = the container for a customer’s resources and bill · VPC = your private virtual network · IAM = identity and access management · logical isolation = separation enforced by software, not separate hardware

Use it when: the default for nearly all cloud workloads — cheap, elastic, well isolated.
Avoid / be careful when: rules demand dedicated hardware (type 2), or you need protection from the provider itself (consider confidential computing).

Type 4 · SaaS silo model

Definition (say it in an interview): In the silo model each tenant of a SaaS application receives its own dedicated set of resources — application instances, database and often a separate cloud account or VPC — so no infrastructure is shared between tenants.

In plain words (no jargon): Each customer gets their own complete copy of the software and its own database and servers — nothing shared.

Analogy: Franchise outlets that each have their own kitchen, staff and stock: nothing is shared, quality issues stay local, but every new outlet costs a lot to open.

How it works internally, step by step

  1. Template the stack. Describe the full tenant environment as code.
  2. Onboard. Create an account/VPC and deploy the stack for each tenant.
  3. Isolate by default. Network, IAM and data are separate by construction.
  4. Operate N copies. Monitoring, backups and upgrades must cover every silo.
  5. Bill. Cost per tenant is directly visible per account.

Words used above, in simple terms: stack = all the resources one application needs · onboarding = adding a new customer to the system · account-per-tenant = one cloud account per customer

Use it when: few large tenants, strict compliance, or very different per-tenant performance needs.
Avoid / be careful when: you have thousands of small tenants — cost and operational effort per tenant become unmanageable.

Type 5 · SaaS pool model

Definition (say it in an interview): In the pool model all tenants share the same application instances and the same database tables, with every record tagged by a tenant identifier and isolation enforced logically by the application and, ideally, by database policies such as row-level security.

In plain words (no jargon): All customers use the same copy of the software and the same database. Each piece of data is labelled with its owner, and the software must always check that label.

Analogy: A shared office canteen with labelled lunch boxes: one kitchen, one fridge, everyone’s food on the same shelves — cheap and efficient, as long as nobody picks up a box without reading the name.

How it works internally, step by step

  1. Tag every row. Each table has tenant_id; it is part of keys and indexes.
  2. Carry tenant context. The tenant comes from the login token, not from user input.
  3. Filter every query. WHERE tenant_id = :tenant on every read and write.
  4. Enforce in the database. Row-level security policies make the database add the filter itself.
  5. Limit and meter. Rate limits and quotas per tenant protect the shared resources.

Words used above, in simple terms: tenant_id = the column naming which customer a row belongs to · row-level security = a database rule that hides rows a session may not see · partition key = the key DynamoDB uses to group items

Use it when: many small tenants, low price points, fast self-service onboarding.
Avoid / be careful when: strict regulatory isolation is required, or tenants differ hugely in size.

Type 6 · SaaS bridge model (hybrid)

Definition (say it in an interview): The bridge model mixes silo and pool: tenants share some layers (typically the application tier and database servers) while other layers are kept per tenant (typically a separate schema or database per tenant), balancing isolation and cost.

In plain words (no jargon): Customers share the same software, but each customer’s data is kept in its own separate section of the database.

Analogy: A co-working space: everyone shares the reception, cafeteria and meeting rooms, but each company has its own lockable cabin and filing cabinets.

How it works internally, step by step

  1. Shared application. One deployment serves all tenants.
  2. Map tenant to schema. A tenant catalogue maps tenant_id → schema/database.
  3. Connect per tenant. Each request uses the tenant’s schema (search_path or connection string).
  4. Migrate per schema. Schema changes run across all tenant schemas.
  5. Graduate. Large tenants move to their own database server.

Words used above, in simple terms: schema = a named set of tables inside a database · tenant catalogue = a lookup table of tenants and where their data lives · elastic pool = Azure SQL feature sharing resources among many databases

Avoid / be careful when: you have tens of thousands of tenants — thousands of schemas complicate migrations and connections.

Type 7 · Performance isolation (the noisy-neighbour problem)

Definition (say it in an interview): The noisy-neighbour problem occurs when one tenant’s heavy use of a shared resource — CPU, memory bandwidth, disk I/O, network or database — degrades performance for other tenants; performance isolation is the set of controls (quotas, weights, rate limits, reserved capacity, separation) that prevents it.

In plain words (no jargon): When many customers share the same machine, one customer using too much can slow everyone else down. Rules that give each customer a fair share stop this.

Analogy: One flat in a building running a loud party every night: everyone shares the walls, so everyone suffers — unless the society has noise rules and enforces them.

How it works internally, step by step

  1. Measure per tenant. Collect CPU, requests, queries and storage per tenant.
  2. Limit at the edge. Rate limits per tenant/API key at the gateway.
  3. Share fairly inside. cgroup weights/limits, Kubernetes requests/limits, separate thread pools.
  4. Queue heavy work. Per-tenant queues so one tenant’s backlog does not block others.
  5. Separate the heaviest. Move big tenants or heavy reports to their own capacity (bridge/silo).
  6. Provider level. Choose instance types with fixed performance or provisioned IOPS when steady performance matters.

Words used above, in simple terms: quota = a maximum amount a tenant may use · rate limit / throttling = a cap on requests per second · cgroup weight = a share of CPU relative to others · steal time = CPU time a VM lost to other VMs on the host

Why pooling is cheaper, what AWS shares between customers, shared responsibility for tenancy

Why pooling makes cloud cheaper: a small calculation

Suppose 100 companies each need up to 10 servers at their own peak, but on average use 3. Owning private capacity means buying 1,000 servers. If their peaks happen at different times, a shared pool might need only about 400 servers to serve everyone’s peaks with headroom — the provider buys fewer servers per customer and keeps them busier. That margin is part of what makes per-second pricing possible.

Shared responsibility for multitenancy

The provider guarantees isolation between accounts. Isolation between your own SaaS tenants is your responsibility: tenant context, data partitioning, per-tenant limits and per-tenant keys. AWS’s SaaS Lens (Well-Architected) and the “SaaS Factory” guidance describe these patterns in detail.

9 Real proof

Real proof: noisy neighbours and a tenant data leak

Steps 1–2 are real runs on our lab machine (10 Nov 2026); step 3 uses the moto AWS emulator.

  1. Step 1 · Noisy neighbours on one core (real)

    taskset -c 0 python3 job.py                       # tenant A alone
for i in 1 2 3; do taskset -c 0 python3 -c 'while True: pass' & done
taskset -c 0 python3 job.py                       # with 3 noisy tenants
# restart the neighbours with: nice -n 19 …        # low CPU weight
    == 1) tenant A alone on core 0 (seconds for the same job) 0.22 s == 2) three noisy tenants share core 0 with equal priority 0.84 s == 3) same neighbours, but given a low CPU weight (nice 19 ≈ a small cgroup cpu.weight) 0.23 s
    Same job, same core: 0.22 s alone, 0.84 s with three equal-priority neighbours, 0.23 s once neighbours get a low weight. Fair-share scheduling is the cure.

  2. Step 2 · Pool, bridge and silo data models (real)

    db.execute('select tenant_id, item from orders')                     # forgot the filter!
db.execute('select item, amount from orders where tenant_id=?', ('annapurna',))
db.execute("create view v_annapurna as … where tenant_id='annapurna'")
# bridge: one schema (attached DB) per tenant · silo: one DB file per tenant
    == 1) pool model: one shared table, every row tagged with tenant_id bug — a query that forgot the tenant filter returns: [('annapurna', 'order 1'), ('annapurna', 'order 2'), ('dabbawala', 'order 1'), ('ghar-ka-khana', 'order 1')] correct — tenant 'annapurna' only: [('order 1', 250), ('order 2', 180)] safer — a per-tenant view the app is forced to use: [('order 1', 250), ('order 2', 180)] == 2) bridge model: one database, one schema (here: attached DB) per tenant schemas: ['annapurna', 'dabbawala'] annapurna.orders: [('order 1', 250)] dabbawala.orders: [] == 3) silo model: a separate database file per tenant files: ['t_annapurna_silo.db', 't_dabbawala_silo.db', 't_ghar-ka-khana_silo.db']
    The first query is the most common multi-tenant bug — it returned every kitchen’s orders. Views or row-level security make the filter impossible to forget.

  3. Step 3 · Tag resources per tenant (emulator)

    aws ec2 run-instances … --tag-specifications 'ResourceType=instance,Tags=[{Key=tenant,Value=annapurna}]'
aws ec2 describe-instances --filters Name=tag:tenant,Values=annapurna
    == 1) two instances, each tagged with the SaaS tenant it serves -------------------------------------------------- | DescribeInstances | +----------------------+-----------+-------------+ | i-62e91e0f47d4b2e9b | m5.large | pool | | i-613938da89fd2966d | m5.large | annapurna | +----------------------+-----------+-------------+ == 2) find everything that belongs to one tenant i-613938da89fd2966d
    With a “tenant” tag on every resource you can find, secure and bill everything belonging to one customer.
10 Hands-on

Do it yourself, step by step

Every step has a UI way and a CLI way. Steps 1–2 run on your own computer; steps 3–4 use AWS (CLI outputs from the moto emulator). Dedicated tenancy costs extra — do not leave such instances running.

  1. 1 · Make and fix a noisy neighbour

    UI way — Task Manager / System Monitor

    1. Windows: start three copies of a CPU-heavy program (or a video export) and a game/benchmark; watch it slow down in Task Manager → Processes.
    2. Right-click the heavy programs in Details → Set priority → Below normal; the benchmark speeds up again.
    3. Linux desktop: System Monitor → right-click process → Change Priority.

    CLI way — the same thing with commands

    taskset -c 0 python3 job.py                        # alone
for i in 1 2 3; do taskset -c 0 python3 -c 'while True: pass' & done
taskset -c 0 python3 job.py                        # slower
pkill -f 'while True'
for i in 1 2 3; do taskset -c 0 nice -n 19 python3 -c 'while True: pass' & done
taskset -c 0 python3 job.py                        # fast again
pkill -f 'while True'
    == 1) tenant A alone on core 0 (seconds for the same job) 0.22 s == 2) three noisy tenants share core 0 with equal priority 0.84 s == 3) same neighbours, but given a low CPU weight (nice 19 ≈ a small cgroup cpu.weight) 0.23 s
    Priority/weight is the same idea as cgroup cpu.weight in containers and Kubernetes CPU requests.

  2. 2 · See a tenant data leak and stop it

    UI way — DB Browser for SQLite

    1. Install DB Browser for SQLite → New Database → run the SQL on the right in Execute SQL.
    2. Run the query without WHERE — every tenant appears. Then create the view and query only the view.

    CLI way — the same thing with commands

    CREATE TABLE orders(tenant_id, item, amount);
INSERT INTO orders VALUES ('annapurna','order 1',250),('annapurna','order 2',180),
                          ('dabbawala','order 1',300),('ghar-ka-khana','order 1',120);
SELECT tenant_id, item FROM orders;                                  -- leak!
CREATE VIEW v_annapurna AS SELECT item, amount FROM orders WHERE tenant_id='annapurna';
SELECT * FROM v_annapurna;
    == 1) pool model: one shared table, every row tagged with tenant_id bug — a query that forgot the tenant filter returns: [('annapurna', 'order 1'), ('annapurna', 'order 2'), ('dabbawala', 'order 1'), ('ghar-ka-khana', 'order 1')] correct — tenant 'annapurna' only: [('order 1', 250), ('order 2', 180)] safer — a per-tenant view the app is forced to use: [('order 1', 250), ('order 2', 180)]
    In PostgreSQL use row-level security: ALTER TABLE orders ENABLE ROW LEVEL SECURITY; CREATE POLICY p ON orders USING (tenant_id = current_setting('app.tenant'));

  3. 3 · Tag resources by tenant and find them

    UI way — AWS Management Console

    1. EC2 → Launch instances → Add additional tags → Key tenant, Value annapurna.
    2. Instances → search bar → tag:tenant = annapurna.
    3. Or Resource Groups & Tag Editor → Tag Editor → Region ap-south-1, tag key tenant → Search resources.

    CLI way — the same thing with commands

    aws ec2 run-instances --image-id $AMI --instance-type m5.large \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=tenant,Value=annapurna}]'
aws ec2 describe-instances --filters Name=tag:tenant,Values=annapurna \
  --query 'Reservations[].Instances[].InstanceId' --output text
    == 1) two instances, each tagged with the SaaS tenant it serves -------------------------------------------------- | DescribeInstances | +----------------------+-----------+-------------+ | i-62e91e0f47d4b2e9b | m5.large | pool | | i-613938da89fd2966d | m5.large | annapurna | +----------------------+-----------+-------------+ == 2) find everything that belongs to one tenant i-613938da89fd2966d
    Then activate “tenant” as a cost allocation tag (Billing → Cost allocation tags) to see cost per tenant in Cost Explorer.

  4. 4 · Choose dedicated tenancy (look at the option)

    UI way — AWS Management Console

    1. EC2 → Launch instances → Advanced details → Tenancy: Shared / Dedicated instance / Dedicated host.
    2. Dedicated Hosts: EC2 → Dedicated Hosts → Allocate Dedicated Host (Lesson 4.6).

    CLI way — the same thing with commands

    aws ec2 run-instances --image-id $AMI --instance-type m5.large --placement Tenancy=dedicated
aws ec2 describe-instances --query "Reservations[].Instances[].[InstanceId,Placement.Tenancy]"
    Only for practice on a real account: dedicated instances add an hourly fee — terminate immediately.

Clean up and cost check

pkill -f "while True" locally. AWS: terminate the tagged instances (Instance state → Terminate instance / aws ec2 terminate-instances).

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Taking tenant_id from a request parameter.Easy to code.Take it only from the authenticated token; users can change parameters.
Relying on every developer to add WHERE tenant_id.It works until someone forgets.Enforce with row-level security, views or IAM conditions.
No per-tenant limits.“Customers will behave.”Rate limits, quotas, queues per tenant; move heavy tenants out.
Buying Dedicated Instances “for security”.Misunderstanding shared tenancy.Shared hosts are isolated by the provider; dedicate only for licensing/compliance.
Silo for thousands of tiny tenants.Strong isolation feels safest.Pool small tenants; silo only the large or regulated ones.
Untagged resources in a multi-tenant account.Tags added “later”.Require a tenant tag at creation (tag policies); otherwise cost and cleanup per tenant are impossible.

13 Mini project

Build something with what you learned

Mini project: a tiny multi-tenant order API with three isolation levels

Goal: Build TiffinGo for Kitchens as a small API that supports pool, bridge and silo tenants — and prove isolation with tests.

Combines: This lesson + SQL + Docker + 4.5 (containers).

  1. API: FastAPI/Flask with GET /orders; read tenant from a signed JWT (use a fixed secret for the lab).
  2. Pool: PostgreSQL (Docker) table orders(tenant_id, …) with row-level security; set app.tenant per request.

  4. Silo: one tenant with its own database container; the catalogue stores its connection string.

  7. Cloud mapping: write which AWS services you would use for each part (Cognito, API Gateway usage plans, RDS RLS, Organizations for silo).

Quick revision

Lesson 5.2 in one screen

  • Pooling: shared, dynamically assigned resources with location independence → economies of scale.
  • Single tenancy = dedicated; multitenancy = shared with logical isolation.
  • Provider isolates accounts (hypervisor, Nitro, VPC, IAM, core isolation).
  • SaaS models: silo (stack per tenant), pool (tenant_id), bridge (schema per tenant).
  • Risks: data leaks (enforce RLS/IAM) and noisy neighbours (quotas, weights).
  • Lab: 0.22 s → 0.84 s with noisy neighbours → 0.23 s with low weight.

Interview and viva questions

Is my data safe on shared AWS hardware?

Yes for normal workloads: accounts are isolated by hypervisor, Nitro, VPC and IAM; use dedicated options only for licensing or explicit compliance needs.

Which SaaS model should a startup use?

Usually pool for small tenants, with a path to silo for large or regulated customers (a hybrid).

What is row-level security?

A database feature that automatically restricts which rows a session can see, so a missing filter in code cannot leak data.
