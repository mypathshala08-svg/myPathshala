2 Definition

Scalability, elasticity and cloud bursting

Formal definition (write this in exams)

Scalability is the ability of a system to handle increased load by adding resources, either by enlarging existing resources (vertical scaling) or adding more of them (horizontal scaling). Elasticity (NIST: rapid elasticity) is the ability to provision and release resources automatically and rapidly, outward and inward, commensurate with demand. Cloud bursting is a hybrid deployment model in which an application normally runs in a private environment and uses public-cloud resources when demand exceeds private capacity.

In simple words

Scalability: you can grow when needed. Elasticity: the cloud grows and shrinks for you automatically. Cloud bursting: borrow public-cloud capacity only when your own data centre is full.

Say it in an interview

30-second answer you can speak:

  • “Scalability is the ability to handle more load by adding resources — scaling up with bigger machines or out with more machines. Elasticity is doing it automatically in both directions so capacity follows demand.”
  • “In AWS I put stateless instances in an Auto Scaling group across two AZs behind an ALB, with target tracking — for example average CPU 50% — plus scheduled scaling for known events.”
  • “Cloud bursting is a hybrid pattern where on-premises capacity overflows into the public cloud during peaks. In a simulation of a Diwali day, elastic scaling used 144 server-hours instead of 528.”

Type 1 · Vertical scaling (scale up / down)

Definition (say it in an interview): Vertical scaling increases (or decreases) the capacity of a single resource — more vCPUs, memory, faster storage or network — by moving it to a larger (or smaller) size, without changing the number of instances.

In plain words (no jargon): Making one computer stronger — more processors or memory — instead of adding more computers.

Analogy: Replacing your auto-rickshaw with a mini-truck when deliveries grow: one bigger vehicle, same driver and routes — but there is a biggest truck, and if it breaks down, nothing moves.

How it works internally, step by step

  1. Pick a new size. Choose a larger instance type in the same family (or a different family).
  2. Stop or fail over. Most VMs must stop to change type; databases often fail over to a resized standby to minimise downtime.
  3. Change the type. The hypervisor places the VM on a host with enough capacity.
  4. Start. The same disk and configuration come back with more CPU/RAM.
  5. Check limits. Network and disk throughput also grow with instance size.

Words used above, in simple terms: instance type = a VM size, e.g. m7i.large = 2 vCPU, 8 GB · ceiling = the biggest size available · maintenance window = an agreed time for changes that may interrupt service

For the experienced — did you know? Bigger is not always proportionally faster: memory bandwidth, licensing per core and single-threaded parts of the app cap the gain. Measure before paying for 4× the cores.

Use it when: the software cannot be split across machines (many databases, legacy apps), or a quick fix is needed.
Avoid / be careful when: you hit the largest size, need high availability, or need to scale many times a day — prefer scaling out.

Type 2 · Horizontal scaling (scale out / in)

Definition (say it in an interview): Horizontal scaling increases (or decreases) capacity by adding (or removing) instances of a resource — servers, containers or database nodes — and distributing work among them, typically behind a load balancer.

In plain words (no jargon): Adding more computers that share the work, instead of making one computer bigger.

Analogy: Opening more billing counters in a supermarket at rush hour instead of hiring one super-fast cashier: more queues move at once, and if one counter closes, the others continue.

How it works internally, step by step

  1. Make the app stateless. Sessions in a cache/database, files in object storage, so any instance can serve any request.
  2. Put a load balancer in front. It spreads requests across healthy instances.
  3. Add instances. Launch more copies from the same image/template.
  4. Register. New instances join the target group after passing health checks.
  5. Remove. Drain connections and terminate instances when load falls.

Words used above, in simple terms: stateless = keeps no user data between requests on the server itself · load balancer = spreads requests across servers · target group = the set of instances a load balancer sends traffic to · read replica = a copy of a database that serves reads

Use it when: web and API tiers, workers, anything stateless — the default way to scale in the cloud.
Avoid / be careful when: the app stores session or files locally — move state to a database, cache or shared storage first.

Type 3 · Elasticity

Definition (say it in an interview): Elasticity (NIST: rapid elasticity) is the ability to provision and release resources automatically and quickly — scaling outward and inward with demand — so that available capacity closely matches the current workload and, to the consumer, appears unlimited.

In plain words (no jargon): The cloud automatically adds computers when more people use your app and removes them when fewer people use it — so you pay roughly for what you use.

Analogy: A rubber band around a bundle of papers: it stretches when you add papers and shrinks back when you remove them, always fitting the bundle.

How it works internally, step by step

  1. Measure demand. CPU, requests per target, queue depth, latency.
  2. Compare with a goal. A target or thresholds decide whether to add or remove.
  3. Provision quickly. New capacity comes from images/templates in minutes or seconds.
  4. Release quickly. Excess capacity is removed and stops being billed.
  5. Repeat continuously. The loop runs every minute.

Words used above, in simple terms: rapid elasticity = NIST’s name for this characteristic · provision = create and prepare a resource · scale in = remove capacity

Use it when: demand varies by hour, day or season — almost every customer-facing app.
Avoid / be careful when: capacity cannot start fast enough for sudden spikes (slow boot, cold caches) — keep a buffer or pre-scale.

Type 4 · Dynamic auto scaling (target tracking and step)

Definition (say it in an interview): Dynamic scaling adjusts capacity in response to live metrics: target tracking keeps a metric (e.g. average CPU or requests per target) at a chosen value, while step/simple scaling adds or removes fixed amounts when CloudWatch alarms cross defined thresholds.

In plain words (no jargon): The cloud watches a number — like how busy the servers are — and adds or removes servers automatically to keep that number at a level you chose.

Analogy: A cruise control in a car: you set 60 km/h and the car accelerates up hills and eases off downhill by itself (target tracking). Step scaling is like a rule: “if speed drops below 50, press harder; below 40, press much harder”.

How it works internally, step by step

  1. Choose the metric. CPU, ALB requests per target, queue backlog per instance, or a custom metric.
  2. Set the target or steps. Target tracking: one value. Step: thresholds and adjustments.
  3. Alarms watch. CloudWatch evaluates the metric every minute.
  4. Change desired capacity. The group launches or terminates instances within min/max.
  5. Warm-up and cooldown. New instances are excluded until ready; scale-in is deliberately slower than scale-out.

Words used above, in simple terms: desired capacity = how many instances the group should have now · min / max = limits the group never goes beyond · CloudWatch alarm = a rule that fires when a metric crosses a threshold · warm-up = time before a new instance’s metrics count

Type 5 · Scheduled and predictive scaling

Definition (say it in an interview): Scheduled scaling changes capacity at specified times for known demand patterns; predictive scaling uses machine learning on historical metrics to forecast demand and provision capacity in advance of expected peaks.

In plain words (no jargon): Adding servers before a busy time you already know about (or that the system has learned from past days), so customers never wait for servers to start.

Analogy: A restaurant that calls extra staff every Saturday evening (scheduled) — and a manager who studies the last month’s footfall to know that Tuesday lunch will be busy too (predictive).

How it works internally, step by step

  1. Scheduled: create an action. At a time (cron), set min/max/desired.
  2. Predictive: learn. The policy analyses at least a day (ideally two weeks) of history.
  3. Forecast. It predicts load for the coming hours.
  4. Pre-launch. Capacity is launched ahead so it is warm at the peak.
  5. Dynamic still runs. Target tracking adds more if the forecast was too low.

Words used above, in simple terms: cron = a way of writing schedules (minute hour day …) · forecast = a prediction of future load · pre-warm = start capacity before it is needed

Type 6 · Cloud bursting

Definition (say it in an interview): Cloud bursting is a hybrid-cloud deployment pattern in which an application runs in a private cloud or data centre and, when demand exceeds that capacity, the excess workload “bursts” into a public cloud, which is released when demand falls.

In plain words (no jargon): A company normally uses its own computers, and only when they are full does it temporarily rent extra computers from a public cloud.

Analogy: A wedding caterer with its own kitchen that rents a second commercial kitchen only for the peak wedding season.

How it works internally, step by step

  1. Connect networks. VPN or Direct Connect between data centre and VPC.
  2. Same images. Workers run from images/containers usable in both places.
  3. Watch the queue. A scheduler sees the private capacity is full.
  4. Launch cloud workers. Extra workers start in the cloud and pull jobs.
  5. Move data wisely. Send only what jobs need; return results.
  6. Release. Workers terminate when the queue empties.

Words used above, in simple terms: hybrid cloud = using private and public cloud together · Direct Connect = a private dedicated link to AWS · batch job = work processed in a queue, not interactively

Type 7 · Serverless scaling (scale to zero)

Definition (say it in an interview): Serverless scaling is automatic, per-request scaling by the platform: functions or serverless containers run as many concurrent copies as incoming events require, within account concurrency limits, and scale to zero when idle, with billing only for actual use.

In plain words (no jargon): You only upload code. The cloud runs as many copies as needed when requests come in and runs none when nothing is happening.

Analogy: Street-side food stalls that appear only when a festival crowd arrives and vanish when it leaves — no rent on quiet days.

How it works internally, step by step

  1. Event arrives. HTTP request, file upload, queue message.
  2. Find or create an environment. Warm environments are reused; otherwise a new one starts (cold start).
  3. Run in parallel. More simultaneous events → more environments, up to the concurrency limit.
  4. Throttle if needed. Beyond the limit, requests are throttled or queued.
  5. Scale to zero. Idle environments are removed.

Words used above, in simple terms: concurrency = how many copies run at the same moment · throttling = refusing or delaying requests over a limit · provisioned concurrency = environments kept warm in advance (paid)

Amdahl’s law: why adding servers stops helping

If 10% of the work for each request is serial (a single database lock, one shared counter), the maximum speed-up from adding more parallel servers is 10×, no matter how many you add. That is why scaling projects often end up redesigning the shared part — caches, queues, read replicas, sharding.

Kubernetes has two levels of autoscaling

  • Pods: the Horizontal Pod Autoscaler changes the number of pods by CPU/memory/custom metrics.
  • Nodes: Cluster Autoscaler or Karpenter adds VMs when pods cannot be scheduled and removes empty ones.
  • Both must be configured — scaling pods without nodes leaves pods “Pending”.

10 Hands-on

Do it yourself, step by step

Every step has a UI way and a CLI way. Step 1 runs on your own computer. Steps 2–4 use AWS (CLI outputs from the moto emulator). t3.micro instances are Free-Tier eligible; delete the group afterwards so instances stop.

  1. 1 · Feel horizontal scaling locally

    UI way — Docker Desktop

    1. Docker Desktop: run two containers from the same web image on ports 8081 and 8082 (Images → Run → Optional settings → host port).
    2. Open both in the browser; a load balancer would spread users across them.

    CLI way — the same thing with commands

    python3 l53_scale.py        # script in lab/jobs/m5 — starts 2 servers and load-tests 1 vs 2
    machine has 2 CPU cores; 120 requests, 8 at a time == 1) one server process (no scaling): 37.8 requests/s == 2) two server processes (scaled out): 99.5 requests/s → 2.6× throughput
    Same code, more copies, more throughput.

  2. 2 · Create an Auto Scaling group across two AZs

    UI way — AWS Management Console

    1. EC2 → Launch Templates → create menu-lt (AMI Amazon Linux 2023, t3.micro) — Lesson 4.4.
    2. EC2 → Auto Scaling Groups → Create Auto Scaling group → name menu-asg → template menu-lt → Next.
    3. Network: choose subnets in ap-south-1a and ap-south-1b → Next.
    4. Group size: Desired 2, Min 2, Max 10 → Next … Create Auto Scaling group.

    CLI way — the same thing with commands

    aws autoscaling create-auto-scaling-group --auto-scaling-group-name menu-asg \
  --launch-template LaunchTemplateName=menu-lt --min-size 2 --max-size 10 --desired-capacity 2 \
  --vpc-zone-identifier "subnet-aaa,subnet-bbb"
    == 1) Auto Scaling group: min 2, max 10, desired 2, across two AZs ----------------------------------- | DescribeAutoScalingGroups | +-----------+----+----+-----+-----+ | menu-asg | 2 | 2 | 10 | 2 | +-----------+----+----+-----+-----+
    On a real account use --vpc-zone-identifier with subnet IDs; the emulator run used --availability-zones.

  3. 3 · Add a target-tracking policy

    UI way — AWS Management Console

    1. Open menu-asg → Automatic scaling tab → Create dynamic scaling policy.
    2. Policy type Target tracking scaling → metric Average CPU utilization → target value 50 → instance warm-up 120 s → Create.
    3. Optional: Create scheduled action for Diwali 17:45 → Min 10.

    CLI way — the same thing with commands

    aws autoscaling put-scaling-policy --auto-scaling-group-name menu-asg --policy-name cpu50 \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{"PredefinedMetricSpecification":{"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50.0}'
aws autoscaling put-scheduled-update-group-action --auto-scaling-group-name menu-asg \
  --scheduled-action-name diwali --recurrence "45 12 * * *" --min-size 10   # cron is in UTC
    == 2) target tracking: keep average CPU at 50% cpu50 TargetTrackingScaling 50.0
    CloudWatch alarms for target tracking are created automatically — you will see them under CloudWatch → Alarms. 17:45 IST = 12:15 UTC (adjust the cron).

  4. 4 · Watch it scale (and scale back)

    UI way — AWS Management Console

    1. menu-asg → Details → Edit → Desired capacity 6 → Update.
    2. Activity tab: “Launching a new EC2 instance…” entries; Instance management tab: instances spread across both AZs.
    3. Set Desired back to 2 and watch instances terminate.

    CLI way — the same thing with commands

    aws autoscaling set-desired-capacity --auto-scaling-group-name menu-asg --desired-capacity 6
aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names menu-asg \
  --query 'AutoScalingGroups[].[DesiredCapacity,length(Instances)]' --output text
aws autoscaling describe-scaling-activities --auto-scaling-group-name menu-asg --max-items 5
    == 3) Diwali evening: scale out to 6 (what the policy would do when CPU stays high) 6 6
    On a real account, generate CPU load (e.g. stress-ng --cpu 2 via user data) to see the policy scale by itself.

Clean up and cost check

Console: select menu-asg → Actions → Delete (terminates its instances); delete the launch template. CLI: aws autoscaling delete-auto-scaling-group --auto-scaling-group-name menu-asg --force-delete; aws ec2 delete-launch-template --launch-template-name menu-lt.

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Scaling a stateful app horizontally.Sessions/files stored on the instance.Move state to a cache/DB/S3 first; then scale out.
Max size too low (or no max).Defaults left unchanged.Set max from load tests and budget; add AWS Budgets alerts.
Scaling on CPU for an I/O-bound app.CPU is the default metric.Use requests per target, latency or queue depth.
Expecting instant scale-out for sudden spikes.Boot + warm-up takes minutes.Pre-scale with scheduled/predictive scaling; use warm pools; keep headroom.
Aggressive scale-in causing flapping.Thresholds too close, no cooldown.Use target tracking; scale in slowly; set warm-up.
Scaling the web tier but not the database.The bottleneck moves.Load-test the whole path; add read replicas, caching, connection pooling.
Single AZ Auto Scaling group.Only one subnet chosen.Always select subnets in at least two AZs.

  1. ✔ capacity follows demand automatically, up and down

  3. Resource group

15 Quiz and revision

Check yourself

Quick revision

Lesson 5.3 in one screen

  • Scale up = bigger machine (ceiling, SPOF); scale out = more machines (stateless app).
  • Elasticity = automatic both ways; scalability = ability to grow.
  • Policies: target tracking (default), step, scheduled, predictive; warm-up and min/max.
  • Cloud bursting: private capacity overflows to public cloud.
  • Serverless scales per request and to zero; set max concurrency.
  • Lab: 1 → 2 server processes = 37.8 → 99.5 req/s; simulation 144 vs 528 server-hours (−73%).

Interview and viva questions

Is Auto Scaling free?

The feature is free; you pay for the instances and CloudWatch alarms/metrics beyond free limits.

Scale up or out first?

Out for web/API tiers; up for databases until replicas/sharding are needed.

Does Auto Scaling replace load balancing?

No — they work together: the load balancer spreads traffic, Auto Scaling changes how many targets exist.
