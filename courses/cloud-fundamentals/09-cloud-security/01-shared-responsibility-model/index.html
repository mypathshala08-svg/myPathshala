2 Definition

Shared responsibility model

Formal definition (write this in exams)

The shared responsibility model defines how security and compliance duties are divided between a cloud provider and its customer: the provider is responsible for security of the cloud (physical facilities, hardware, networking and the virtualization and managed-service layers it operates), and the customer is responsible for security in the cloud (data, identities and access, configuration, and — depending on the service model — operating systems, applications and network controls).

In simple words

The provider protects the cloud itself; you protect what you put in it and how you set it up. The more the provider manages, the less you do — but your data and users are always yours.

Say it in an interview

30-second answer you can speak:

  • “AWS secures the cloud — facilities, hardware, hypervisor, managed services — and the customer secures what’s in it: data, IAM, network rules and, for IaaS, the guest OS. The line moves up with PaaS and SaaS, but data and identities stay with the customer.”
  • “Patch management is a shared control: AWS patches hosts, we patch EC2 guests. RDS engine patching is AWS’s; Lambda runtime too.”

Type 1 · On-premises (the baseline)

Definition (say it in an interview): In an on-premises deployment the organisation is responsible for every security layer — physical facility, hardware, network, virtualization, operating systems, applications, identities and data — with no provider sharing the work.

In plain words (no jargon): When everything is in your own building, you protect everything yourself.

Analogy: Owning a house: locks, walls, wiring, CCTV and who gets a key are all your job.

How it works internally, step by step

  1. Physical. Access control, CCTV.
  2. Hardware. Firmware, disposal.
  3. Network. Firewalls, segmentation.
  4. Systems. OS and app patching.
  5. Data. Backups, encryption, access.

Words used above, in simple terms: colocation = renting space and power in someone else’s data centre · firmware = low-level software inside hardware · disposal = securely destroying old disks

For the experienced — did you know? Moving to cloud removes the bottom layers from your list — it does not remove the top ones.

Use it when: regulation or latency demands it — and you can staff 24×7 security.
Avoid / be careful when: you assume it is automatically safer — small teams rarely match provider physical and hardware security.

Type 2 · IaaS (VMs)

Definition (say it in an interview): In IaaS the provider secures the physical infrastructure, host operating systems and virtualization layer, while the customer is responsible for the guest operating system (patching, hardening), installed software, network controls such as security groups, identity and access, and data.

In plain words (no jargon): With rented virtual servers, the provider protects the machines underneath; you protect the system you install.

Analogy: Renting an unfurnished flat: the builder handles the structure and lift; your door lock, appliances and valuables are yours.

How it works internally, step by step

  1. Harden image. CIS benchmarks.
  2. Patch. Systems Manager / Update Manager / VM Manager.
  3. Network. Least-open SGs/NSGs/firewalls.
  4. Access. No SSH keys sprawl; use session tools.
  5. Data. Encrypt disks, back up.

Words used above, in simple terms: guest OS = the operating system inside your VM · hardening = removing unneeded services and settings · CIS benchmark = published secure-configuration guide

Many cloud ransomware cases began with internet-exposed VMs running unpatched software or open RDP/SSH — customer-side layers.

Real scenario (TiffinGo)

TiffinGo’s reporting VM on EC2: AWS keeps the host safe; TiffinGo must patch Ubuntu, close port 22 and back up the disk (Lesson 2.1).

Use it when: you need OS-level control — and accept OS-level duties.
Avoid / be careful when: nobody owns patching — unpatched VMs are the classic IaaS breach.

Type 3 · Containers (managed Kubernetes / CaaS)

Definition (say it in an interview): With managed container services, the provider secures the infrastructure and the Kubernetes control plane; the customer secures container images, cluster configuration (RBAC, network policies, admission rules), workload secrets and data — and, unless using a fully managed or serverless node option, upgrading worker nodes.

In plain words (no jargon): In managed container platforms, the provider runs the cluster brain; you look after your containers and their settings.

Analogy: A shared commercial kitchen: the owner maintains gas lines and fire systems; each cook keeps their own ingredients fresh and their station clean.

How it works internally, step by step

  1. Images. Scan, sign, minimal base.
  2. Nodes. Auto-upgrade or serverless nodes.
  3. RBAC. Least privilege.
  4. Network. Policies between pods.
  5. Secrets. External secret stores.

Words used above, in simple terms: control plane = the Kubernetes brain (API server, scheduler) · RBAC = role-based access control · node = a VM that runs your containers

Avoid / be careful when: images are pulled from anywhere unscanned, or everyone has cluster-admin.

Type 4 · PaaS

Definition (say it in an interview): In PaaS the provider additionally secures the operating system, runtime and platform services; the customer remains responsible for application code and dependencies, application configuration, identities and access, network exposure settings and data.

In plain words (no jargon): On a ready platform, the provider looks after the servers; you look after your app and its data.

Analogy: A serviced apartment: housekeeping and maintenance are included, but you still lock your suitcase and decide who you invite in.

How it works internally, step by step

  1. Dependencies. Scan and update libraries.
  2. Secrets. Key vaults, not env files in Git.
  3. Access. IAM + app auth.
  4. Exposure. Private endpoints where possible.
  5. Data. Backups and encryption settings.

Words used above, in simple terms: dependency = a library your code uses · CVE = a published, numbered vulnerability · private endpoint = access to a service over a private network address

Type 5 · Serverless / FaaS

Definition (say it in an interview): In serverless (FaaS) the provider secures all infrastructure, operating systems, runtimes and the isolation between functions; the customer secures function code and dependencies, input validation, the function’s IAM permissions, event-source configuration and data.

In plain words (no jargon): With serverless, the provider looks after nearly everything; you look after your code and what it is allowed to do.

Analogy: A food-delivery kitchen-for-hire: you only bring the recipe, but you decide who may order and what ingredients the cook may take from the store.

How it works internally, step by step

  1. Least privilege. One role per function.
  2. Inputs. Validate event data.
  3. Dependencies. Scan packages.
  4. Secrets. Secrets manager.
  5. Logging. Trace and alert.

Words used above, in simple terms: event source = what triggers a function (upload, queue, HTTP) · least privilege = only the permissions needed · injection = malicious input executed as code

Type 6 · SaaS

Definition (say it in an interview): In SaaS the provider secures the entire application and infrastructure; the customer remains responsible for its data, user accounts and authentication (MFA, SSO), access and sharing settings, device security of its users and how the application is configured.

In plain words (no jargon): With online software, the company runs the app; you control who uses it and what data goes in.

Analogy: A bank locker room: the bank guards the vault; you decide who gets your key and what you put in the locker.

How it works internally, step by step

  1. Identity. SSO + MFA.
  2. Lifecycle. Joiners, movers, leavers.
  3. Sharing. External sharing policies.
  4. Data. Retention, DLP, backups of exports.
  5. Audit. Admin and sign-in logs.

Words used above, in simple terms: SSO = single sign-on · DLP = data loss prevention — rules that stop sensitive data leaving · SSPM = SaaS security posture management

6 Explained part by part

Six ideas inside the model

Inherited controls

What it is: Controls fully handled by the provider.

Why it exists: You can rely on their audit reports.

Where it is used: Physical, environmental.

Shared controls

What it is: Both sides do their own part.

Why it exists: Patching, config, training split by layer.

Where it is used: Provider patches hosts; you patch guests.

Customer-specific controls

What it is: Only you can do them.

Why it exists: Data classification, user access.

Where it is used: Zone/Region choice, MFA.

Compliance reports

What it is: Third-party audits of the provider.

Why it exists: Evidence for your auditors.

Where it is used: AWS Artifact, Service Trust Portal, Compliance Reports Manager.

Secure defaults

What it is: Settings the provider turns on for you.

Why it exists: Reduce customer mistakes.

Where it is used: S3 Block Public Access on by default for new buckets.

Shared fate

What it is: Provider actively helps you configure securely.

Why it exists: Blueprints, guardrails, guidance.

Where it is used: Google’s term; landing zones.

Myth vs reality: things many websites still say

  • Myth: The cloud provider secures my data.
    Reality: You choose who can access it.
    Proof: Story.
  • Myth: SaaS means no security work.
    Reality: Users, MFA, sharing and data are yours.
    Proof: Type 6.
  • Myth: Private cloud avoids shared responsibility.
    Reality: You simply take every layer.
    Proof: Type 1.
7 Deep dive

Why breaches land on the customer side, guard-rails, audit reports

Why most breaches land on the customer side

Provider infrastructure is engineered, audited and attacked constantly, so failures there are rare. Customer-side layers change daily — new buckets, new users, new rules — made by many people. Industry analyses repeatedly find that the large majority of cloud security incidents involve customer misconfiguration or stolen credentials.

Using the provider’s audit reports

Your auditors will ask how you know the provider’s half is done. The answer: download its SOC 2 / ISO 27001 reports and certificates (practical step 1), check the services you use are in scope, and map their controls to yours. You do not audit the provider’s data centre yourself.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You check the provider’s half (audit reports) and secure your half (block public access, find exposure and excess permissions). Everything here is free.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Download the provider’s audit report (their half)

    Pick your cloud.

    UI way — AWS Management Console

    1. Search AWS Artifact → Reports → search “SOC 2” → open the report → accept the terms → Download report.
    2. Check that the services you use (EC2, S3, Lambda…) are listed in scope.

    CLI way — the same thing with commands

    aws artifact list-reports --query 'reports[?contains(name, `SOC`)].[name,id]' --output table --region us-east-1 | head -20

    You should see: a list of AWS SOC reports with IDs (AWS Artifact API; the console is the easiest way to download and accept the terms).

    UI way — Azure portal

    1. Open servicetrust.microsoft.com → sign in with your Azure account → Library / Certifications, reports → filter SOC → Download the Azure SOC 2 report.

    CLI way — the same thing with commands

    az account show --query "{tenant:tenantId,user:user.name}" -o table
# Service Trust Portal is web-only: open https://servicetrust.microsoft.com and sign in with this account.

    You should see: your tenant and user; the portal lists SOC, ISO 27001 and other reports to download.

    UI way — Google Cloud console

    1. Open cloud.google.com/security/compliance/compliance-reports-manager → choose a report (SOC 2, ISO 27001) → Download (some reports ask you to sign in and accept terms).

    CLI way — the same thing with commands

    gcloud config list account --format="value(core.account)"
# Compliance Reports Manager is web-based: sign in with this account to download reports.

    You should see: your account; the page lists Google Cloud audit reports and certificates.

    These reports are the evidence for the provider’s half. You never audit their data centre — you read their auditor’s report.

  3. 2 · Lock public access for the whole account (your half)

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → Block Public Access settings for this account → Edit → tick Block all public access → Save changes → type confirm.

    CLI way — the same thing with commands

    ACC=$(aws sts get-caller-identity --query Account --output text)
aws s3control put-public-access-block --account-id $ACC --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws s3control get-public-access-block --account-id $ACC

    You should see: all four settings true. Now nobody in this account can make a bucket public by mistake — the intern’s incident cannot repeat.

    UI way — Azure portal

    1. Storage accounts → each account → Configuration → Allow Blob anonymous access = Disabled → Save. (New accounts already default to disabled.)
    2. For the whole subscription, assign the built-in policy “Storage account public access should be disallowed”.

    CLI way — the same thing with commands

    az storage account list --query "[].{name:name,anonymous:allowBlobPublicAccess,tls:minimumTlsVersion}" -o table
# fix any account showing True:
# az storage account update -n NAME -g RG --allow-blob-public-access false --min-tls-version TLS1_2

    You should see: each storage account with False (or empty, which means disabled on new accounts) for anonymous access.

    UI way — Google Cloud console

    1. Cloud Storage → bucket → Permissions → Prevent public access → Enforce.
    2. With an organisation, set the org policy storage.publicAccessPrevention for all projects.

    CLI way — the same thing with commands

    B=tiffingo-srm-$RANDOM; gcloud storage buckets create gs://$B --location=asia-south1 --public-access-prevention
gcloud storage buckets describe gs://$B --format="value(public_access_prevention)"
gcloud storage buckets add-iam-policy-binding gs://$B --member=allUsers --role=roles/storage.objectViewer 2>&1 | tail -1

    You should see: enforced, and the attempt to grant allUsers fails with a precondition error — public access is impossible on this bucket.

    A guard-rail turns a duty (“remember not to make buckets public”) into a default nobody can forget.

  4. 3 · Find what is exposed or over-permitted

    Pick your cloud.

    UI way — AWS Management Console

    1. IAM → Access Analyzer → Create analyzer → type External access, zone of trust = current account → Create.
    2. Findings lists resources (buckets, roles, keys, queues) shared outside your account.

    CLI way — the same thing with commands

    aws accessanalyzer create-analyzer --analyzer-name account-external --type ACCOUNT
sleep 60; ARN=$(aws accessanalyzer list-analyzers --query "analyzers[0].arn" --output text)
aws accessanalyzer list-findings-v2 --analyzer-arn $ARN --query "findings[].[resourceType,resource,status]" --output table

    You should see: an empty table (nothing shared externally) or findings to review. External-access analysis is free.

    UI way — Azure portal

    1. Search Microsoft Defender for Cloud → Recommendations — the free foundational CSPM gives a secure score and fixes (e.g. “MFA should be enabled for accounts with owner permissions”).

    CLI way — the same thing with commands

    az security secure-scores list --query "[].{name:displayName,current:score.current,max:score.max}" -o table
az security assessment list --query "[?status.code=='Unhealthy'].displayName" -o tsv | head -10

    You should see: your secure score and up to 10 unhealthy recommendations (new subscriptions may take a few hours to be assessed).

    UI way — Google Cloud console

    1. IAM & Admin → IAM — the shield icon next to principals shows unused permissions; Recommendations suggests smaller roles.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud recommender insights list --project=$P --location=global --insight-type=google.iam.policy.Insight --format="table(description)" | head
gcloud recommender recommendations list --project=$P --location=global --recommender=google.iam.policy.Recommender --format="table(description)" | head

    You should see: insights such as “principal has not used N permissions in 90 days” and role-reduction recommendations (projects need some history before these appear).

    Posture tools check your half continuously — run them weekly, fix the top items.

Clean up and cost check

AWS: keep the account-level public-access block on (recommended); delete the analyzer if you want: aws accessanalyzer delete-analyzer --analyzer-name account-external. Azure: nothing created. Google Cloud: gcloud storage buckets delete gs://$B.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
“The provider secures my data.”Misreading the model.Data, identities and access are always the customer’s.
Same duties assumed for every service.One model for all.Check the line per service (EC2 vs RDS vs Lambda).
No one owns VM patching.Gap between dev and ops.Assign owners; automate with patch services.
Public storage for “quick sharing”.Convenience.Account-level block + pre-signed/signed URLs.
Ignoring provider bulletins.Assuming nothing to do.Subscribe to security bulletins and health events.
Auditors asked to “check the cloud”.No evidence collected.Provide provider audit reports + your own controls.
