2 Definition

Cloud security issues and threats

Formal definition (write this in exams)

Cloud security threats are potential events or actions that could compromise the confidentiality, integrity or availability of cloud resources and data — chiefly misconfiguration, compromised credentials and identities, insecure interfaces and APIs, vulnerable workloads and supply chains, denial-of-service attacks, ransomware and data destruction, and insider misuse — addressed through layered preventive, detective and responsive controls.

In simple words

The main ways cloud systems get attacked — mostly careless settings and stolen logins — and how to spot and stop them.

Say it in an interview

30-second answer you can speak:

  • “Most cloud incidents come from misconfiguration and stolen credentials, not provider breaches. I prevent with MFA, no static keys, org policies and immutable backups; detect with GuardDuty/Defender/SCC, posture tools and cost anomalies; and respond with runbooks.”
  • “For a leaked key: deactivate it, scope its activity in CloudTrail, remove persistence, contain resources, then fix the root cause.”

Type 1 · Misconfiguration

Definition (say it in an interview): Misconfiguration is an insecure setting of a cloud resource — public storage, open management ports, overly permissive access policies, disabled logging or encryption — that exposes data or systems, typically caused by human error, defaults left unchanged or missing guard-rails.

In plain words (no jargon): A wrong or careless setting that leaves data or servers open to the internet.

Analogy: Leaving the shop shutter half open overnight: nobody broke anything — the door was simply not closed.

How it works internally, step by step

  1. Prevent. Org policies, account-level blocks.
  2. Template. Secure IaC modules.
  3. Scan. IaC and posture scans.
  4. Detect. Config rules, alerts.
  5. Fix. Auto-remediation.

Words used above, in simple terms: posture = overall security state of your settings · CSPM = cloud security posture management · 0.0.0.0/0 = any IP address on the internet

Use it when: always assume it will happen — automate detection and prevention.
Avoid / be careful when: you rely on “people will be careful” — they will not, at scale.

Type 2 · Credential theft and account hijacking

Definition (say it in an interview): Credential theft is the compromise of passwords, access keys, tokens or session cookies — through leaks in code, phishing, password reuse or malware — allowing an attacker to use legitimate cloud APIs and consoles with the victim’s permissions, often without triggering traditional security tools.

In plain words (no jargon): Someone stealing a password or key and logging in as you.

Analogy: Someone copying your house key: the lock works perfectly — for them too.

How it works internally, step by step

  1. MFA. On every human account.
  2. No static keys. Roles, OIDC, managed identities.
  3. Scan. Repos for secrets.
  4. Detect. Unusual locations/APIs.
  5. Rotate. And expire credentials.

Words used above, in simple terms: access key = a long-lived API credential (ID + secret) · phishing = tricking someone into giving credentials · session token = short-lived proof of login

Products and cloud services

For the experienced — did you know? First 15 minutes after a leak: deactivate (not just delete) the key, check CloudTrail for what it did, look for new users/keys/roles the attacker created.

Use it when: always — identity is the cloud perimeter.
Avoid / be careful when: root/owner accounts are used daily or keys never expire.

Type 3 · Insecure interfaces and APIs

Definition (say it in an interview): Insecure APIs are application or management interfaces with weaknesses such as broken authentication, missing object-level authorisation, excessive data exposure, lack of rate limiting or injection flaws, allowing attackers to access or manipulate data and functions they should not.

In plain words (no jargon): Weak web interfaces that let attackers see or change data they shouldn’t.

Analogy: A delivery counter where anyone who says any order number gets handed that bag — no ID checked.

How it works internally, step by step

  1. Authenticate. Every call.
  2. Authorise. Per object, per user.
  3. Limit. Rate limits, quotas.
  4. Validate. Input schemas.
  5. Monitor. Abnormal patterns.

Words used above, in simple terms: BOLA = broken object-level authorisation — the top OWASP API risk · rate limiting = capping requests per client · WAF = web application firewall

A TiffinGo test showed /api/orders/1043 returned order 1043 to any logged-in user; changing the number revealed other customers’ addresses. Fixed by checking order ownership.

For the experienced — did you know? Test APIs as an attacker: call them with another user’s token and IDs — most BOLA bugs are found in minutes this way.

Use it when: any service exposes APIs — which is nearly every cloud app.
Avoid / be careful when: you trust the client app to hide IDs — attackers call APIs directly.

Type 4 · Vulnerable workloads and supply chain

Definition (say it in an interview): Vulnerable workloads are VMs, containers, functions or applications running software with known flaws — unpatched operating systems, outdated libraries, malicious or compromised dependencies (supply-chain attacks) — that attackers exploit to execute code, steal credentials (for example from the instance metadata service) or move laterally.

In plain words (no jargon): Programs with known security holes that haven’t been updated, which attackers use to get in.

Analogy: A building with a lock model known to be pickable: until you change the lock, every burglar who reads the news can open it.

How it works internally, step by step

  1. Inventory. Know what runs where (SBOM).
  2. Scan. Images, hosts, dependencies.
  3. Prioritise. Exposed + exploited first.
  4. Patch. Rebuild images often.
  5. Limit. Least privilege, IMDSv2.

Words used above, in simple terms: CVE = public ID for a known vulnerability · SBOM = software bill of materials — list of components · supply-chain attack = compromising a library or tool many people use

Log4Shell (CVE-2021-44228) in 2021 showed how one library flaw can affect millions of applications across every cloud at once.

An old image library in TiffinGo’s menu service had a remote-code-execution CVE; the container ran with a broad IAM role, so the risk was the whole account — fixed by patching and shrinking the role.

Products and cloud services

For the experienced — did you know? Vulnerability + exposure + permissions = risk. A critical CVE on an internal VM with no role is lower priority than a medium one on an internet-facing VM with admin rights.

Use it when: continuously — new CVEs appear daily.
Avoid / be careful when: images are built once and never rebuilt.

Type 5 · Distributed denial of service (DDoS)

Definition (say it in an interview): A DDoS attack floods an application or network with traffic from many sources (often botnets) to exhaust bandwidth, connections or compute so legitimate users cannot be served; attacks target network layers (L3/L4 floods) or application layers (L7 HTTP floods).

In plain words (no jargon): Attackers sending massive fake traffic to make a website too busy to work.

Analogy: Hundreds of fake customers crowding a shop’s entrance so real customers cannot get in.

How it works internally, step by step

  1. Edge. Serve via CDN/LB with built-in protection.
  2. Filter. WAF and rate limits.
  3. Scale. Auto scaling absorbs bursts.
  4. Hide origin. Only accept traffic from the edge.
  5. Plan. Response contacts, runbook.

Words used above, in simple terms: botnet = many infected devices controlled by an attacker · L7 = application layer (HTTP) · origin = your real servers behind the CDN

During a Diwali sale a competitor’s botnet sent HTTP floods at TiffinGo’s order page; CloudFront and AWS Shield Standard absorbed the network flood and a WAF rate-limit rule blocked the HTTP flood.

Products and cloud services

AWS Shield Standard (free) and Advanced, WAF, CloudFront; Azure DDoS Protection (network) and IP protection, Front Door + WAF; Google Cloud Armor, Cloud CDN.

For the experienced — did you know? Auto scaling without WAF turns a DDoS into a billing attack (“economic denial of service”) — filter before you scale.

Use it when: any public-facing app — use edge services and rate limits.
Avoid / be careful when: you expose origins directly with public IPs — attackers bypass the CDN.

Type 6 · Ransomware and data destruction

Definition (say it in an interview): Cloud ransomware is an attack in which, after gaining access, attackers encrypt, delete or exfiltrate data — storage objects, disks, snapshots, databases — and demand payment, often first deleting backups and disabling logging so recovery and investigation are harder.

In plain words (no jargon): Attackers locking or deleting your data and asking for money to give it back.

Analogy: A thief who first steals your spare keys and then changes all your locks, asking money for the new keys.

How it works internally, step by step

  1. Isolate backups. Separate account/subscription.
  2. Immutable. Vault/Object Lock.
  3. Least privilege. Few can delete.
  4. Detect. Mass delete/encrypt alerts.
  5. Test restore. Regularly.

Words used above, in simple terms: immutable = cannot be changed or deleted until a set time · exfiltration = copying data out to the attacker · double extortion = encrypt and threaten to leak

Attackers in cloud ransomware cases have used legitimate features — such as encrypting objects with keys they control — so it looks like normal API activity until the data is unreadable.

In a tabletop exercise, TiffinGo found that its backups lived in the same account with the same admin role — one stolen key could delete both. They moved backups to a separate, locked vault.

Products and cloud services

For the experienced — did you know? The test that matters: “Could our most powerful compromised credential delete our backups?” If yes, fix that before anything else.

Use it when: every account that holds important data.
Avoid / be careful when: backups are reachable by the same credentials that production uses.

Type 7 · Insider threats

Definition (say it in an interview): Insider threats come from people with legitimate access — employees, contractors, partners or former staff whose access was not removed — who misuse it maliciously (theft, sabotage) or negligently (mistakes, poor hygiene), and are hard to detect because their actions use valid credentials.

In plain words (no jargon): People inside the company misusing their access, on purpose or by mistake.

Analogy: A staff member with keys to the store room walking out with stock — or simply leaving the door open by mistake.

How it works internally, step by step

  1. Least privilege. Only what the role needs.
  2. SSO. Leaver disabled once, everywhere.
  3. Reviews. Quarterly access reviews.
  4. Separation. No single person can do everything.
  5. Audit. Logs + alerts on sensitive actions.

Words used above, in simple terms: de-provisioning = removing access when someone leaves · separation of duties = splitting critical tasks between people · access review = periodic check of who has what

7 Deep dive

MITRE ATT&CK, leaked-key runbook, defence in depth

MITRE ATT&CK for cloud

MITRE’s ATT&CK framework has cloud matrices (IaaS, SaaS, identity providers) describing attacker techniques: initial access with valid accounts, discovery via cloud APIs, persistence by creating new keys or roles, defence evasion by disabling logging, impact through resource hijacking (mining) or data destruction. Detection tools map their findings to these techniques.

Leaked-key runbook (first 15 minutes)

  1. Deactivate the key (keep it for investigation; delete later).
  2. Scope: search audit logs by key ID for every action since the leak.
  3. Persistence: look for new users, keys, roles, policies, Lambda functions, instances in all Regions.
  4. Contain: stop rogue resources (snapshot first for evidence), block IPs.
  5. Data: check data access logs; involve legal if personal data was accessed (India’s DPDP Act requires breach notification to the Data Protection Board and affected people).
  6. Prevent: remove static keys, add secret scanning, cost-anomaly alarms, SCPs blocking unused Regions.

Defence in depth

No single control stops everything. Layer them: identity (MFA, least privilege) → network (private endpoints, WAF) → workload (patched, minimal images) → data (encryption, immutable backups) → detection (threat detection, posture, cost anomalies) → response (runbooks, automation).

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You switch on attack detection (with sample findings, no real attack needed), hunt risky credentials, and add a cost alarm. GuardDuty and Defender plans use free trials — turn them off afterwards if you do not want charges.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Turn on threat detection and see sample attacks

    Pick your cloud.

    UI way — AWS Management Console

    1. GuardDuty → Get started → Enable GuardDuty (30-day free trial in each Region).
    2. Settings → Generate sample findings → Findings: open “UnauthorizedAccess:IAMUser/MaliciousIPCaller” or “CryptoCurrency:EC2/BitcoinTool.B!DNS”.

    CLI way — the same thing with commands

    DET=$(aws guardduty create-detector --enable --finding-publishing-frequency FIFTEEN_MINUTES --query DetectorId --output text)
aws guardduty create-sample-findings --detector-id $DET
sleep 20; aws guardduty list-findings --detector-id $DET --max-results 50 --query 'length(FindingIds)'
ID=$(aws guardduty list-findings --detector-id $DET --max-results 1 --query 'FindingIds[0]' --output text)
aws guardduty get-findings --detector-id $DET --finding-ids $ID --query 'Findings[0].[Type,Severity,Title]' --output text

    You should see: a few hundred sample findings and one example such as Recon:IAMUser/MaliciousIPCaller 5.0 API … was invoked from a known malicious IP (titles prefixed “[SAMPLE]”). Disable after the trial if you do not want charges.

    UI way — Azure portal

    1. Microsoft Defender for Cloud → Environment settings → subscription → turn on Servers plan (30-day trial) → Security alerts → Sample alerts → Create sample alerts.
    2. Open an alert: description, affected resource, MITRE ATT&CK tactic, remediation steps.

    CLI way — the same thing with commands

    az security pricing create -n VirtualMachines --tier standard
az security pricing show -n VirtualMachines --query "{plan:name,tier:pricingTier,trial:freeTrialRemainingTime}"
# create sample alerts from the portal (Security alerts → Sample alerts), then:
az security alert list --query "[].{name:alertDisplayName,severity:severity}" -o table | head

    You should see: tier Standard with trial time remaining, then sample alerts such as “[Sample alert] Suspicious process executed”. Set the plan back to Free after the lab: az security pricing create -n VirtualMachines --tier free.

    UI way — Google Cloud console

    1. Search Security Command Center → activate the Standard tier for your project (free) → Findings. Standard detectors flag misconfigurations such as public buckets and open firewalls; threat detection (Event Threat Detection) needs Premium.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud services enable securitycenter.googleapis.com
gcloud scc findings list projects/$P --location=global --filter="state=\"ACTIVE\"" --format="table(finding.category,finding.severity,finding.resourceName)" | head

    You should see: active findings such as OPEN_FIREWALL or PUBLIC_BUCKET_ACL (empty on a clean new project; findings appear after the first scan).

    Detection turns “found on Monday” into “paged at 2:05 am”.

  3. 2 · Hunt for old and risky credentials

    Pick your cloud.

    UI way — AWS Management Console

    1. IAM → Credential report → Download credentials report: check mfa_active, access_key_1_last_rotated and access_key_1_last_used_date for every user.
    2. Deactivate keys older than 90 days or never used; prefer roles and IAM Identity Center.

    CLI way — the same thing with commands

    aws iam generate-credential-report >/dev/null; sleep 5
aws iam get-credential-report --query Content --output text | base64 -d | cut -d, -f1,4,8,9,10,11 | head

    You should see: a table of users with password/MFA status and key rotation dates. Any key older than 90 days, or a root key (<root_account> with key active = true), is a finding to fix today.

    UI way — Azure portal

    1. Microsoft Entra ID → App registrations → each app → Certificates & secrets: check client secret expiry; switch to Federated credentials (Lesson 8.3) where possible.
    2. Users → Per-user MFA / Conditional Access: confirm MFA for all admins.

    CLI way — the same thing with commands

    for id in $(az ad app list --show-mine --query "[].appId" -o tsv); do
  az ad app credential list --id $id --query "[].{app:'$id',name:displayName,ends:endDateTime}" -o tsv
done

    You should see: each secret with its expiry date (empty if your apps use only federated credentials — the best case).

    UI way — Google Cloud console

    1. IAM & Admin → Service accounts → each account → Keys: user-managed JSON keys are long-lived — delete unused ones; use Workload Identity Federation instead.
    2. With an organisation, enforce iam.disableServiceAccountKeyCreation.

    CLI way — the same thing with commands

    for sa in $(gcloud iam service-accounts list --format="value(email)"); do
  gcloud iam service-accounts keys list --iam-account=$sa --managed-by=user --format="table[no-heading](name.basename(),validAfterTime,validBeforeTime)" | sed "s|^|$sa  |"
done

    You should see: one line per user-managed key with creation date — ideally none.

    Long-lived credentials are the attacker’s favourite door; each one you delete closes it.

  4. 3 · Add a cost-anomaly alarm (cryptojacking early warning)

    Pick your cloud.

    UI way — AWS Management Console

    1. Billing and Cost Management → Cost Anomaly Detection → Create monitor → AWS services → alert subscription: Immediate, threshold $10, your email.

    CLI way — the same thing with commands

    MON=$(aws ce create-anomaly-monitor --anomaly-monitor '{"MonitorName":"tiffingo-spend","MonitorType":"DIMENSIONAL","MonitorDimension":"SERVICE"}' --query MonitorArn --output text)
aws ce create-anomaly-subscription --anomaly-subscription "{\"SubscriptionName\":\"spend-spike\",\"MonitorArnList\":[\"$MON\"],\"Subscribers\":[{\"Type\":\"EMAIL\",\"Address\":\"you@example.com\"}],\"Frequency\":\"DAILY\",\"ThresholdExpression\":{\"Dimensions\":{\"Key\":\"ANOMALY_TOTAL_IMPACT_ABSOLUTE\",\"Values\":[\"10\"],\"MatchOptions\":[\"GREATER_THAN_OR_EQUAL\"]}}}"
aws ce get-anomaly-monitors --query 'AnomalyMonitors[].[MonitorName,MonitorType]' --output text

    You should see: tiffingo-spend DIMENSIONAL. Cost Anomaly Detection is free; it learns your normal spend and emails when a service suddenly costs more (immediate alerts need an SNS subscriber).

    UI way — Azure portal

    1. Cost Management → Cost alerts → Add → Anomaly alert → recipients → Create. Azure also shows detected anomalies in Cost analysis (smart views).

    CLI way — the same thing with commands

    SUB=$(az account show --query id -o tsv)
az rest --method get --url "https://management.azure.com/subscriptions/$SUB/providers/Microsoft.CostManagement/scheduledActions?api-version=2023-11-01" --query "value[].{name:name,kind:kind}" -o table

    You should see: your anomaly alert listed with kind InsightAlert after you create it in the portal.

    UI way — Google Cloud console

    1. Billing → Budgets & alerts → Create budget (e.g. ₹2,000/month) with 50/90/100% thresholds; Anomalies (if shown for your billing account) lists unusual spend automatically.

    CLI way — the same thing with commands

    BA=$(gcloud billing projects describe $(gcloud config get-value project) --format="value(billingAccountName)" | cut -d/ -f2)
gcloud billing budgets create --billing-account=$BA --display-name=spend-guard --budget-amount=2000INR \
  --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --threshold-rule=percent=1.0
gcloud billing budgets list --billing-account=$BA --format="table(displayName,amount.specifiedAmount.units)"

    You should see: the budget spend-guard 2000; alerts go to billing admins by email. (Use the currency of your billing account.)

    Cryptojacking almost always shows up on the bill first — make the bill page you.

Clean up and cost check

AWS: aws guardduty delete-detector --detector-id $DET (or keep it on — recommended for real accounts); keep the anomaly monitor (free). Azure: az security pricing create -n VirtualMachines --tier free; dismiss sample alerts. Google Cloud: keep the budget; SCC Standard is free.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Deleting a leaked key file from Git and moving on.Git history keeps it.Deactivate the key immediately, then investigate.
No one reads security emails.Alerts go to a personal inbox.Route findings to an on-call channel.
Backups in the same account with the same admin.Convenience.Separate, immutable backup vaults.
Auto scaling without WAF.Scaling seen as protection.Filter at the edge, then scale.
Ignoring unused Regions.“We only use Mumbai.”Block unused Regions; detection in all Regions.
Shared admin accounts.Simplicity.Individual identities, SSO, audit trails.
