1 The story

🤔 A customer in Pune taps “Order”. Before the order reaches TiffinGo’s database, it passes through at least six cloud networking services. Can you name them?

DNS finds the address, a CDN edge answers what it can, the request enters a virtual network through a gateway, a load balancer picks a healthy server, firewall rules decide what may pass, route tables send packets between subnets — and a private link or VPN connects the office. This lesson explains each building block, follows one request through all of them, and walks you through building a network with public and private subnets, firewall rules, private DNS and peering on your own AWS, Azure or Google Cloud account.

2 Definition

Cloud networking

Formal definition (write this in exams)

Cloud networking is the set of software-defined services that connect, isolate, protect and deliver cloud resources: virtual networks and subnets, routing and gateways, firewalls, load balancers, DNS, content delivery networks, and hybrid connectivity such as peering, VPNs and dedicated links — all configured through APIs on top of the provider’s physical network.

In simple words

The roads, gates, guards, signposts and phone book of the cloud — how traffic gets to your servers safely and quickly, and how your networks connect to each other and your office.

Say it in an interview

30-second answer you can speak:

  • “A VPC is an isolated virtual network with its own CIDR, split into public subnets — with a route to an internet gateway — and private subnets that reach out only via NAT.”
  • “Security groups are stateful allow-lists at the instance; NACLs are stateless allow/deny at the subnet. Users come in through Route 53, CloudFront and a load balancer; offices connect by VPN or Direct Connect.”

Type 1 · Virtual networks and subnets (VPC / VNet)

Definition (say it in an interview): A virtual network — Amazon VPC, Azure Virtual Network (VNet), Google Cloud VPC — is a logically isolated, software-defined private network in the cloud with its own IP address range (CIDR), divided into subnets in which resources receive private IP addresses; it is built on the provider’s overlay network (Lesson 4.3), so many customers can use the same address ranges without seeing each other.

In plain words (no jargon): Your own private network inside the cloud, with your own address numbers. You split it into smaller zones (subnets) for different kinds of servers.

Analogy: A gated housing society: the society has its own address range (Block A–D, flat numbers), outsiders cannot walk in, and each wing (subnet) has its own entrance rules.

How it works internally, step by step

  1. Choose a CIDR. E.g. 10.0.0.0/16 (65,536 addresses) from the private ranges 10/8, 172.16/12, 192.168/16.
  2. Create subnets. Smaller CIDRs per tier and AZ, e.g. /24 (256 addresses; AWS reserves 5).
  3. Overlay. The provider encapsulates your packets so your 10.0.x.x never clashes with another customer’s.
  4. Attach resources. Network interfaces get private IPs; public IPs are optional extras.
  5. Default network. New accounts have a default VPC/network — fine for labs, not for production.

Words used above, in simple terms: CIDR = a way to write an IP range, e.g. 10.0.0.0/16 · subnet = a smaller slice of the network · private IP = an address only reachable inside the network · overlay = a virtual network running on top of the physical one

Products and cloud services

Amazon VPC (regional, subnets per AZ), Azure Virtual Network (regional, subnets span zones), Google Cloud VPC (global, subnets per Region).

For the experienced — did you know? Plan CIDRs like real estate: Kubernetes pods (EKS VPC CNI) take one VPC IP per pod, so a /24 subnet can run out after a handful of nodes. Many outages of “no IP addresses available” are design-time mistakes, not traffic spikes.

Use it when: always — every IaaS design starts with a network plan: CIDR sizes, subnets per tier and per AZ, room to grow, no overlap with offices.
Avoid / be careful when: you pick a tiny or overlapping range (e.g. 192.168.1.0/24, same as the office) — peering and VPNs will fail later.

Type 2 · Routing and gateways (route tables, internet gateway, NAT)

Definition (say it in an interview): Route tables decide where packets leaving a subnet go, using rules of the form destination CIDR → target; gateways are the targets that connect the virtual network to other places — an internet gateway for two-way internet access with public IPs, a NAT gateway for outbound-only internet access from private IPs, and VPN/transit gateways for other networks.

In plain words (no jargon): Signposts inside the cloud network that say where each kind of traffic should go — to another server inside, out to the internet, or out through a one-way exit.

Analogy: Signboards at a society gate: “Blocks A–D → inside”, “everything else → main road”. The service lane for deliveries (NAT) lets staff go out shopping but no stranger can drive in through it.

How it works internally, step by step

  1. Local route. Every route table has the VPC range → local (traffic between subnets just works).
  2. Default route. 0.0.0.0/0 → IGW (public) or → NAT (private), or nothing (isolated).
  3. Longest prefix wins. A /24 rule beats a /16 rule beats 0.0.0.0/0.
  4. NAT. Replaces private source IPs with the NAT’s public IP; replies are mapped back.
  5. Association. Each subnet uses exactly one route table.

Words used above, in simple terms: route table = a list of “destination → where to send it” rules · internet gateway = the door between a VPC and the internet · NAT = network address translation — many private IPs share one public IP for outbound traffic · 0.0.0.0/0 = “any address” — the default route

Use it when: designing public/private tiers, forcing traffic through a firewall appliance, or connecting networks.
Avoid / be careful when: you give private servers public IPs “to make updates work” — use NAT or private endpoints instead.

Type 3 · Cloud firewalls (security groups, NSGs, firewall rules)

Definition (say it in an interview): Cloud firewalls filter traffic by protocol, port and source/destination: AWS security groups (stateful, allow-only, per network interface) and network ACLs (stateless, ordered allow/deny, per subnet), Azure network security groups (stateful, priority-ordered allow/deny, per subnet or NIC), and Google Cloud VPC firewall rules and policies (stateful, applied by network tags or service accounts).

In plain words (no jargon): Rules that say which kinds of traffic may reach each server. Everything not on the list is blocked.

Analogy: Security guards with a guest list at each flat door (security group) plus a gate guard for the whole wing (NACL/NSG): only listed visitors enter, and residents’ visitors may always leave.

How it works internally, step by step

  1. Default deny inbound. New security groups allow no inbound traffic and all outbound.
  2. Add allow rules. Protocol + port + source (CIDR, or another security group / tag).
  3. Stateful tracking. The connection is remembered; replies pass automatically.
  4. Evaluation. All SG rules are combined (any allow wins); NACL/NSG rules are checked in priority order.
  5. Logging. VPC Flow Logs / NSG flow logs / firewall logging show accepted and rejected traffic.

Words used above, in simple terms: port = a numbered door for a service, e.g. 443 for HTTPS · stateful = remembers connections, so replies are allowed · stateless = checks every packet on its own, both directions · allow-list = only listed things are allowed

For the experienced — did you know? Referencing a security group as the source (“allow from alb-sg”) is better than IP ranges: when the load balancer’s IPs change or scale out, the rule still matches exactly the right interfaces — and nothing else.

Use it when: always — every interface should have the tightest rules possible, referencing other groups rather than IP ranges.
Avoid / be careful when: you open 0.0.0.0/0 to admin ports (22, 3389) or databases — one of the most common causes of cloud breaches.

Type 4 · Load balancers

Definition (say it in an interview): A load balancer is a managed service that receives client connections on one address and distributes them across healthy targets (VMs, containers, IPs, functions) in one or more zones, using health checks; layer 4 balancers forward TCP/UDP connections, layer 7 balancers understand HTTP(S) and route by path, host or headers.

In plain words (no jargon): A traffic police officer for your app: all visitors come to one address, and it sends each one to a server that is free and healthy.

Analogy: The token counter at a busy bank: you take a token at one desk, and it sends you to whichever cashier is free — skipping the cashier on lunch break.

How it works internally, step by step

  1. Listener. Port/protocol it accepts (e.g. HTTPS 443) with a TLS certificate.
  2. Rules. L7: path/host/header conditions → target group.
  3. Target group. Registered targets with a health check (path, interval, thresholds).
  4. Distribution. Round robin / least outstanding requests (L7) or flow hash (L4) across AZs.
  5. Scale. The provider scales load balancer nodes automatically; global LBs use anycast IPs.

Words used above, in simple terms: layer 4 = works with TCP/UDP connections only · layer 7 = understands HTTP: URLs, headers, cookies · health check = a regular test request to see if a server is OK · TLS termination = decrypting HTTPS at the load balancer · anycast = one IP address announced from many places — users reach the nearest one

Use it when: more than one server serves the same app, or you need HTTPS termination, health-based failover or path routing.
Avoid / be careful when: a single dev server is enough — a load balancer has an hourly cost even when idle.

Type 5 · DNS (managed name service)

Definition (say it in an interview): DNS (Domain Name System) translates names such as api.tiffingo.in into IP addresses; cloud DNS services host authoritative zones (public or private to a virtual network) on globally distributed name servers and add routing policies — weighted, latency-based, geolocation and health-check failover.

In plain words (no jargon): The internet’s phone book: you type a name, DNS finds the number (IP address) of the server.

Analogy: The phone contacts app: you remember “Riya”, the phone remembers the number — and if Riya changes her number, you update one entry.

How it works internally, step by step

  1. Register a domain. With any registrar; point its name servers to the cloud DNS zone.
  2. Create records. A/AAAA (IP), CNAME (alias name), MX (mail), TXT (verification), alias records to cloud resources.
  3. Resolve. Resolvers walk root → TLD → authoritative servers and cache the answer.
  4. Routing policies. Weighted, latency, geo, failover using health checks.
  5. Private zones. Names that resolve only inside linked virtual networks.

Words used above, in simple terms: domain = a name you own, e.g. tiffingo.in · record = one entry: name → value · TTL = time to live — how long resolvers may cache an answer · authoritative = the server that holds the official answer

Use it when: every public app (your domain) and inside networks (private zones) so services find each other by name.
Avoid / be careful when: you hard-code IP addresses in apps — they change when servers or load balancers are replaced.

Type 6 · CDN and edge networking

Definition (say it in an interview): A content delivery network (CDN) caches and serves content from edge locations close to users, terminating TLS there and forwarding cache misses and dynamic requests to the origin over the provider’s backbone; edges also host web application firewalls, DDoS protection and small edge functions.

In plain words (no jargon): Copies of your website’s pictures and files kept in many cities, so each user gets them from somewhere nearby — faster and cheaper.

Analogy: Amul’s local milk booths: milk is not carried from Anand to every home each morning — it is stocked in nearby booths.

How it works internally, step by step

  1. Distribution. You create a distribution with one or more origins (S3, load balancer, any HTTPS server).
  2. Anycast/DNS. Users are routed to the nearest edge.
  3. Cache. Responses are cached by cache key (path, some headers) for the TTL.
  4. Miss. The edge (or regional cache) fetches from the origin over the backbone.
  5. Security. TLS, WAF rules, bot control and DDoS absorption at the edge.

Words used above, in simple terms: edge location / PoP = a data-centre site close to users · origin = where the original content lives · cache hit = answered from the stored copy · WAF = web application firewall — blocks malicious HTTP requests

Avoid / be careful when: content is private per user and cannot be cached — you still gain TLS and protection, but less speed.

Type 7 · Hybrid connectivity and private links

Definition (say it in an interview): Hybrid and inter-network connectivity links virtual networks to each other and to on-premises sites: peering (private routing between two VNets/VPCs), site-to-site VPN (encrypted IPsec tunnels over the internet), dedicated connections (private circuits such as AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect), transit hubs for many networks, and private endpoints that expose a service inside your network without public IPs.

In plain words (no jargon): Ways to connect your cloud network privately to another cloud network or to your office — through a secure tunnel over the internet or a dedicated cable.

Analogy: Roads between housing societies: a private gate between two neighbouring societies (peering), an armoured van on public roads (VPN), or your own private flyover (dedicated line).

How it works internally, step by step

  1. Plan addresses. No overlapping CIDRs between networks you connect.
  2. Peering. Request + accept; add routes on both sides; traffic stays on the backbone.
  3. VPN. Customer gateway (your router) ↔ virtual private gateway/VPN gateway; two IPsec tunnels for redundancy; BGP or static routes.
  4. Dedicated link. Order a port at a colocation or via a partner (e.g. in Mumbai); private VLAN to your VPCs.
  5. Hub. Transit Gateway / Virtual WAN / NCC connect many networks with central routing.

Words used above, in simple terms: peering = a private connection between two networks · IPsec = a standard for encrypted network tunnels · BGP = the protocol routers use to exchange routes · transitive = if A↔B and B↔C, then A↔C — peering is NOT

Use it when: offices or data centres must reach cloud resources privately, or several VPCs/accounts must talk to each other.
Avoid / be careful when: address ranges overlap (plan CIDRs first) or you expect peering to be transitive (A↔B and B↔C does not give A↔C).

6 Explained part by part

Six more pieces you will meet in every network

CIDR block

What it is: The address range of a network or subnet.

Why it exists: Decides how many addresses and whether networks can connect.

Where it is used: 10.0.0.0/16 VPC, /24 subnets.

Public IP / Elastic IP

What it is: An internet-routable address on an interface.

Why it exists: Needed only on internet-facing things — and billed on AWS.

Where it is used: Elastic IP, Azure Public IP, GCP external IP.

Network interface (ENI / NIC)

What it is: The virtual network card of a resource.

Why it exists: Firewalls and IPs attach here.

Where it is used: ENI, NIC, vNIC.

Flow logs

What it is: Records of accepted/rejected connections.

Why it exists: Troubleshooting and security investigations.

Where it is used: VPC Flow Logs, VNet flow logs, VPC Flow Logs (GCP).

Private endpoint

What it is: A private IP for a cloud service inside your network.

Why it exists: Reach S3, databases or SaaS without the internet.

Where it is used: Gateway/interface endpoints, Private Link, Private Service Connect.

Bastion / just-in-time access

What it is: A managed way to reach private servers.

Why it exists: No SSH/RDP ports open to the internet.

Where it is used: Session Manager, EC2 Instance Connect Endpoint, Azure Bastion, IAP TCP forwarding.

Myth vs reality: things many websites still say

  • Myth: A subnet is public because of its name.
    Reality: It is public because of its route to an internet gateway.
    Proof: Type 2.
  • Myth: Security groups can block one IP.
    Reality: They only allow; use NACLs / NSGs / WAF to deny.
    Proof: Type 3.
  • Myth: Peering connects everything to everything.
    Reality: It is not transitive.
    Proof: Type 7.
7 Deep dive

Subnet maths, shared responsibility and IPv6

Subnet maths in one minute

CIDRAddressesUsable on AWS (−5)Typical use
/1665,53665,531a whole VPC
/204,0964,091a large subnet (EKS nodes + pods)
/24256251a normal subnet
/281611smallest AWS subnet (e.g. a NAT/firewall)

AWS reserves the first four and the last address of every subnet (network, VPC router, DNS, future use, broadcast). Azure also reserves 5; Google Cloud reserves 4.

Shared responsibility in networking

The provider runs the physical network, the overlay, DDoS protection of its infrastructure and the managed services. You design CIDRs and subnets, write firewall and route rules, decide what is public, encrypt traffic and watch flow logs. Most network incidents in the cloud are configuration, not provider failures.

IPv6 in the cloud

All three clouds support dual-stack VPCs. IPv6 addresses are globally unique, so there is no NAT: AWS uses an egress-only internet gateway to give private-subnet IPv6 instances outbound-only access — the IPv6 version of a NAT gateway, without the per-GB charge.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. Nothing in these steps runs a VM; only a hosted zone and public IP lookups touch billing, and they cost nothing if deleted the same day.

  2. 1 · Build a network with public and private subnets

    Pick your cloud.

    UI way — AWS Management Console

    1. VPC → Create VPC → choose VPC and more (the wizard draws a preview).
    2. Name tiffingo, IPv4 CIDR 10.0.0.0/16, 2 AZs, 2 public + 2 private subnets, NAT gateways None (they cost money), VPC endpoints None.
    3. Create VPC → then open Route tables: the public one has 0.0.0.0/0 → igw-…, the private ones only local.

    CLI way — the same thing with commands

    VPC=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=tiffingo}]' --query Vpc.VpcId --output text)
PUB=$(aws ec2 create-subnet --vpc-id $VPC --cidr-block 10.0.1.0/24 --availability-zone ap-south-1a --query Subnet.SubnetId --output text)
PRIV=$(aws ec2 create-subnet --vpc-id $VPC --cidr-block 10.0.11.0/24 --availability-zone ap-south-1a --query Subnet.SubnetId --output text)
IGW=$(aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --internet-gateway-id $IGW --vpc-id $VPC
RT=$(aws ec2 create-route-table --vpc-id $VPC --query RouteTable.RouteTableId --output text)
aws ec2 create-route --route-table-id $RT --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW
aws ec2 associate-route-table --route-table-id $RT --subnet-id $PUB
aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC --query 'RouteTables[].Routes[].[DestinationCidrBlock,GatewayId]' --output table

    You should see: two route tables: the custom one with 0.0.0.0/0 → igw-… (associated with the public subnet) and the main one with only 10.0.0.0/16 → local (used by the private subnet).

    UI way — Azure portal

    1. Virtual networks → Create → resource group rg-tiffingo, name vnet-tiffingo, Region Central India.
    2. IP addresses tab: address space 10.1.0.0/16; edit the default subnet to public 10.1.1.0/24; Add a subnet private 10.1.2.0/24, tick Enable private subnet (no default outbound access).
    3. Review + create → Create.

    CLI way — the same thing with commands

    az group create --name rg-tiffingo --location centralindia
az network vnet create --resource-group rg-tiffingo --name vnet-tiffingo --address-prefix 10.1.0.0/16 \
  --subnet-name public --subnet-prefixes 10.1.1.0/24
az network vnet subnet create --resource-group rg-tiffingo --vnet-name vnet-tiffingo --name private \
  --address-prefixes 10.1.2.0/24 --default-outbound-access false
az network vnet subnet list --resource-group rg-tiffingo --vnet-name vnet-tiffingo --query "[].[name,addressPrefix]" --output table

    You should see: two subnets public 10.1.1.0/24 and private 10.1.2.0/24. Azure routes to the internet via system routes; a private subnet without default outbound access needs a NAT Gateway for outbound traffic.

    UI way — Google Cloud console

    1. VPC network → VPC networks → Create VPC network → name vpc-tiffingo, subnet creation mode Custom.
    2. Subnet public: Region asia-south1, range 10.2.1.0/24; Add subnet private: asia-south1, 10.2.2.0/24, Private Google Access On.
    3. Create → open Routes: a default route to the internet gateway and one subnet route per subnet.

    CLI way — the same thing with commands

    gcloud compute networks create vpc-tiffingo --subnet-mode=custom
gcloud compute networks subnets create public --network=vpc-tiffingo --region=asia-south1 --range=10.2.1.0/24
gcloud compute networks subnets create private --network=vpc-tiffingo --region=asia-south1 --range=10.2.2.0/24 --enable-private-ip-google-access
gcloud compute routes list --filter="network:vpc-tiffingo"

    You should see: two subnets and routes including 0.0.0.0/0 → default-internet-gateway. In Google Cloud “public” means a VM has an external IP — the subnets themselves are the same.

    Each cloud defines “public” differently: AWS by the route table, Azure by outbound access settings and public IPs, Google by whether a VM gets an external IP.

  3. 2 · Firewall rules: web open, SSH only from you

    Pick your cloud.

    UI way — AWS Management Console

    1. VPC → Security groups → Create security group → name tiffingo-web-sg, VPC tiffingo.
    2. Inbound: Add rule HTTP 80 from Anywhere-IPv4; Add rule SSH 22 from My IP → Create security group.
    3. Open Network ACLs and look at the default NACL: rule 100 allow all, rule * deny all.

    CLI way — the same thing with commands

    MYIP=$(curl -s https://checkip.amazonaws.com)/32    # in CloudShell this is CloudShell's IP, not your laptop's
SGW=$(aws ec2 create-security-group --group-name tiffingo-web-sg --description web --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SGW --protocol tcp --port 80 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SGW --protocol tcp --port 22 --cidr $MYIP
SGD=$(aws ec2 create-security-group --group-name tiffingo-db-sg --description db --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SGD --protocol tcp --port 5432 --source-group $SGW
aws ec2 describe-security-groups --group-ids $SGW $SGD --query 'SecurityGroups[].[GroupName,IpPermissions[].FromPort]' --output text

    You should see: two groups: web with ports 80 and 22, db with 5432 — whose source is the web security group, not an IP range.

    UI way — Azure portal

    1. Network security groups → Create → nsg-web, rg-tiffingo, Central India.
    2. Open it → Inbound security rules → Add: destination port 80, TCP, Allow, priority 100; add SSH 22 with source My IP address, priority 110.
    3. Subnets → Associate → vnet-tiffingo / public.

    CLI way — the same thing with commands

    MYIP=$(curl -s https://ifconfig.me)/32
az network nsg create --resource-group rg-tiffingo --name nsg-web
az network nsg rule create --resource-group rg-tiffingo --nsg-name nsg-web --name allow-http --priority 100 \
  --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 80
az network nsg rule create --resource-group rg-tiffingo --nsg-name nsg-web --name allow-ssh-me --priority 110 \
  --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 22 --source-address-prefixes $MYIP
az network vnet subnet update --resource-group rg-tiffingo --vnet-name vnet-tiffingo --name public --network-security-group nsg-web
az network nsg rule list --resource-group rg-tiffingo --nsg-name nsg-web --output table

    You should see: two custom rules (priority 100 and 110); Azure also shows default rules 65000–65500 (allow VNet, allow load balancer, deny all) with --include-default.

    UI way — Google Cloud console

    1. VPC network → Firewall → Create firewall rule → name tiffingo-allow-http, network vpc-tiffingo, ingress, allow, target tags web, source 0.0.0.0/0, TCP 80 → Create.
    2. Create another: tiffingo-allow-ssh, target tags web, source = your IP/32, TCP 22.
    3. Note the implied rules: deny all ingress, allow all egress.

    CLI way — the same thing with commands

    MYIP=$(curl -s https://ifconfig.me)/32
gcloud compute firewall-rules create tiffingo-allow-http --network=vpc-tiffingo --direction=INGRESS \
  --action=ALLOW --rules=tcp:80 --source-ranges=0.0.0.0/0 --target-tags=web
gcloud compute firewall-rules create tiffingo-allow-ssh --network=vpc-tiffingo --direction=INGRESS \
  --action=ALLOW --rules=tcp:22 --source-ranges=$MYIP --target-tags=web
gcloud compute firewall-rules list --filter="network:vpc-tiffingo"

    You should see: two rules that apply only to VMs carrying the network tag web. For SSH from the browser use IAP (source range 35.235.240.0/20) instead of opening 22 to the world.

    Admin ports (22/3389) should never be open to 0.0.0.0/0. The CloudShell / Cloud Shell IP is not your laptop’s IP — get yours from a “what is my IP” page when testing from your PC.

  4. 3 · Private DNS: give the database a name

    Pick your cloud.

    UI way — AWS Management Console

    1. Route 53 → Hosted zones → Create hosted zone → domain tiffingo.internal, type Private hosted zone, VPC: Mumbai / tiffingo → Create.
    2. Create record → name db, type A, value 10.0.11.10, TTL 300 → Create records.
    3. From any VM in the VPC: nslookup db.tiffingo.internal.

    CLI way — the same thing with commands

    ZONE=$(aws route53 create-hosted-zone --name tiffingo.internal --caller-reference tg-$(date +%s) \
  --vpc VPCRegion=ap-south-1,VPCId=$VPC --hosted-zone-config PrivateZone=true --query HostedZone.Id --output text)
aws route53 change-resource-record-sets --hosted-zone-id $ZONE --change-batch \
  '{"Changes":[{"Action":"CREATE","ResourceRecordSet":{"Name":"db.tiffingo.internal","Type":"A","TTL":300,"ResourceRecords":[{"Value":"10.0.11.10"}]}}]}'
aws route53 list-resource-record-sets --hosted-zone-id $ZONE --output table

    You should see: NS, SOA and your A record. Hosted zones cost $0.50/month, but a zone deleted within 12 hours of creation is not charged.

    UI way — Azure portal

    1. Private DNS zones → Create → rg-tiffingo, name tiffingo.internal → Create.
    2. Open it → Virtual network links → Add → link vnet-link to vnet-tiffingo.
    3. Recordsets → + Record set → name db, A, 10.1.2.10.

    CLI way — the same thing with commands

    az network private-dns zone create --resource-group rg-tiffingo --name tiffingo.internal
az network private-dns link vnet create --resource-group rg-tiffingo --zone-name tiffingo.internal \
  --name vnet-link --virtual-network vnet-tiffingo --registration-enabled false
az network private-dns record-set a add-record --resource-group rg-tiffingo --zone-name tiffingo.internal \
  --record-set-name db --ipv4-address 10.1.2.10
az network private-dns record-set a list --resource-group rg-tiffingo --zone-name tiffingo.internal --output table

    You should see: record db with 10.1.2.10. With --registration-enabled true VMs would register their own names automatically.

    UI way — Google Cloud console

    1. Network services → Cloud DNS → Create zone → type Private, zone name tiffingo-internal, DNS name tiffingo.internal, network vpc-tiffingo → Create.
    2. Add standard record → db, A, 10.2.2.10 → Create.

    CLI way — the same thing with commands

    gcloud dns managed-zones create tiffingo-internal --dns-name=tiffingo.internal. --visibility=private \
  --networks=vpc-tiffingo --description="TiffinGo private zone"
gcloud dns record-sets create db.tiffingo.internal. --zone=tiffingo-internal --type=A --ttl=300 --rrdatas=10.2.2.10
gcloud dns record-sets list --zone=tiffingo-internal

    You should see: NS, SOA and the A record (note the trailing dot in DNS names).

    Apps should connect to db.tiffingo.internal, not an IP — when the database moves, you change one record.

  5. 4 · Peer a second network (and see “not transitive”)

    Pick your cloud.

    UI way — AWS Management Console

    1. Create a second VPC analytics with CIDR 10.9.0.0/16 (must not overlap).
    2. Peering connections → Create peering connection → requester tiffingo, accepter analytics → Create → select it → Actions → Accept request.
    3. Add routes in both VPCs’ route tables: 10.9.0.0/16 → pcx-… and 10.0.0.0/16 → pcx-….

    CLI way — the same thing with commands

    VPC2=$(aws ec2 create-vpc --cidr-block 10.9.0.0/16 --query Vpc.VpcId --output text)
PCX=$(aws ec2 create-vpc-peering-connection --vpc-id $VPC --peer-vpc-id $VPC2 --query VpcPeeringConnection.VpcPeeringConnectionId --output text)
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id $PCX
aws ec2 create-route --route-table-id $RT --destination-cidr-block 10.9.0.0/16 --vpc-peering-connection-id $PCX
RT2=$(aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC2 --query 'RouteTables[0].RouteTableId' --output text)
aws ec2 create-route --route-table-id $RT2 --destination-cidr-block 10.0.0.0/16 --vpc-peering-connection-id $PCX
aws ec2 describe-vpc-peering-connections --vpc-peering-connection-ids $PCX --query 'VpcPeeringConnections[0].Status.Code' --output text

    You should see: active. Try creating a peering to a VPC with 10.0.0.0/16 again — it fails: overlapping CIDRs.

    UI way — Azure portal

    1. Create vnet-analytics with 10.9.0.0/16.
    2. vnet-tiffingo → Peerings → Add → remote vnet-analytics; tick allow access both ways → Add (Azure creates both directions).

    CLI way — the same thing with commands

    az network vnet create --resource-group rg-tiffingo --name vnet-analytics --address-prefix 10.9.0.0/16 --subnet-name s1 --subnet-prefixes 10.9.1.0/24
az network vnet peering create --resource-group rg-tiffingo --name tiffingo-to-analytics --vnet-name vnet-tiffingo \
  --remote-vnet vnet-analytics --allow-vnet-access
az network vnet peering create --resource-group rg-tiffingo --name analytics-to-tiffingo --vnet-name vnet-analytics \
  --remote-vnet vnet-tiffingo --allow-vnet-access
az network vnet peering list --resource-group rg-tiffingo --vnet-name vnet-tiffingo --query "[].[name,peeringState]" --output table

    You should see: Connected. Azure adds the routes for you (system routes), no route table edits needed.

    UI way — Google Cloud console

    1. Create a second network vpc-analytics (custom, subnet 10.9.1.0/24 in asia-south1).
    2. VPC network peering → Create connection → name tiffingo-to-analytics, your network vpc-tiffingo, peered network vpc-analytics → Create; repeat in the other direction.

    CLI way — the same thing with commands

    gcloud compute networks create vpc-analytics --subnet-mode=custom
gcloud compute networks subnets create a1 --network=vpc-analytics --region=asia-south1 --range=10.9.1.0/24
gcloud compute networks peerings create tiffingo-to-analytics --network=vpc-tiffingo --peer-network=vpc-analytics
gcloud compute networks peerings create analytics-to-tiffingo --network=vpc-analytics --peer-network=vpc-tiffingo
gcloud compute networks peerings list

    You should see: both peerings with STATE ACTIVE (the first shows INACTIVE until the second side is created).

    Peering is free to set up; traffic across zones/Regions is billed. Remember: peering is not transitive.

Clean up and cost check

AWS (order matters): delete the peering connection; delete the record and hosted zone; delete security groups; detach and delete the internet gateway; delete subnets, the custom route table and both VPCs — or simply Your VPCs → select → Actions → Delete VPC (deletes subnets, route tables, IGW and SGs with it). 10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Database in a public subnet with its port open.Default VPC, quick setup.Private subnet + SG allowing only the app SG.
Overlapping CIDRs (10.0.0.0/16 everywhere).Copying examples.Plan an IP address map across VPCs, offices and future peers.

Mini project: the TiffinGo network design

Goal: Design and build the network every later lesson will use.

Combines: This lesson + 5.1 (Regions/AZs) + 6.1 (compute) + 4.3 (network virtualization).

  6. Cost: list which parts cost money when idle (NAT, load balancer, public IPs, hosted zone).
  7. Clean up and screenshot empty lists.

14 Quiz and revision

Check yourself

Quick revision

Lesson 6.3 in one screen

  • VPC/VNet = private CIDR, cut into subnets; Google VPC is global, AWS/Azure regional.
  • Public subnet = route to IGW; private = no inbound route, outbound via NAT.
  • SG stateful allow-only per NIC; NACL stateless allow/deny per subnet; NSG and GCP firewall rules stateful with priorities.
  • LB: L7 (path/host) vs L4 (TCP/UDP); health checks.
  • DNS: records, TTL, private zones, routing policies; Route 53 100% SLA.
  • CDN: edge caching + TLS + WAF/DDoS.
  • Hybrid: peering (not transitive), VPN (IPsec), Direct Connect/ExpressRoute/Interconnect, hubs, private endpoints.

Interview and viva questions

Do I need a NAT gateway for the labs?

No — it costs money per hour. The labs show routing without one; production private subnets usually need NAT or endpoints.

Why 10.0.0.0/16?

It is a private range with room for 65,536 addresses; choose ranges that will not overlap with offices or other VPCs.

Is the default VPC bad?

Fine for learning; for production create your own with planned CIDRs and private subnets.
