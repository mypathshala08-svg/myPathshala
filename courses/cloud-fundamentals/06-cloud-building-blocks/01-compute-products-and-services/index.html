1 The story

Five jobs, one question: where should each run?

🤔 TiffinGo has five jobs to run: an order API, a menu website, photo resizing, a nightly sales report and a “dishes you may like” model. Should all five run on virtual machines?

No. Clouds offer a whole menu of compute products — virtual machines, bare-metal servers, Kubernetes, serverless containers, functions, app platforms, and batch/GPU services. They differ in one thing above all: how much you manage versus how much the provider manages. This lesson explains each, shows what happens inside the cloud when you click “Launch”, and walks you through launching a VM and a serverless container on your own AWS, Azure or Google Cloud account.

2 Definition

Cloud compute products and services

Formal definition (write this in exams)

Cloud compute services provide on-demand processing capacity in different forms of abstraction — virtual machines and bare-metal servers (IaaS), container orchestration and serverless containers, functions (FaaS), application platforms (PaaS), and batch and accelerated computing — each trading control for operational simplicity and billed by the resources and time consumed.

In simple words

Different ways to rent computing power: a whole server, a virtual server, a place to run containers, or just “run my code when something happens”.

Say it in an interview

30-second answer you can speak:

  • “Cloud compute ranges from IaaS — EC2, Azure VMs, Compute Engine — through containers on EKS/AKS/GKE or serverless containers like Fargate and Cloud Run, to functions such as Lambda and PaaS like App Service.”
  • “I choose the most managed option that fits: functions for events, PaaS or serverless containers for web apps, VMs when I need OS control, bare metal for licensing or my own hypervisor.”

Type 1 · Virtual machines (IaaS compute)

Definition (say it in an interview): A virtual machine (VM) instance is a software-defined server with its own operating system, virtual CPUs, memory, disks and network interfaces, created on demand from an image on a provider’s physical host and isolated from other VMs by a hypervisor. You choose the image and size and manage everything from the OS upward.

In plain words (no jargon): A computer you rent over the internet. You pick how big it is and which operating system it runs; it starts in a minute; you look after everything installed on it.

Analogy: Renting a furnished flat in a big building: your own lockable flat with your own kitchen, but the building, water and electricity belong to the owner.

How it works internally, step by step

  1. Pick an image. AMI (AWS), image (Azure/GCP): OS plus pre-installed software.
  2. Pick a size. Instance type / VM size sets vCPUs, memory, network and disk limits.
  3. Place and boot. The control plane picks a host in your AZ; the hypervisor boots it (see “How it works”).
  4. Attach storage and network. Root disk from the image, extra block disks, a network interface in your subnet.
  5. Operate. You patch, monitor, back up and scale (Auto Scaling groups / scale sets / MIGs).

Words used above, in simple terms: image = a saved template of an OS disk · instance type = the hardware size of the VM · vCPU = a virtual processor — usually one hardware thread · hypervisor = software that runs and isolates VMs

Real-world example

Amazon EC2 launched in 2006 and today offers hundreds of instance types; all current-generation types run on the AWS Nitro System, which moves networking, storage and security to dedicated cards so almost all of the host’s CPU goes to customer VMs.

Real scenario (TiffinGo)

TiffinGo’s order API runs on two m7i.large VMs in two AZs behind a load balancer (Lesson 5.3). The team installs Java, the app and a monitoring agent itself, and patches the OS every month.

Products and cloud services

Amazon EC2 (and Lightsail for simple fixed-price VPS), Azure Virtual Machines (and Virtual Machine Scale Sets), Google Compute Engine (and managed instance groups).

For the experienced — did you know? “vCPU” is not the same everywhere: on most x86 types a vCPU is one hyper-thread (half a physical core), but on AWS Graviton (ARM) instances a vCPU is a full physical core — so a 2-vCPU Graviton and a 2-vCPU Intel instance are not equal for CPU-heavy work.

Use it when: you need full control of the OS, any software, long-running servers, or a lift-and-shift of existing servers.
Avoid / be careful when: the job is short or event-driven (pay for idle time) or you do not want to patch operating systems.

Type 2 · Bare-metal servers

Definition (say it in an interview): A bare-metal instance gives a customer an entire physical server with no provider hypervisor in between, provisioned through the same cloud APIs as VMs, so the operating system — or the customer’s own hypervisor — runs directly on the hardware.

In plain words (no jargon): Instead of a slice of a server, you rent the whole physical machine. Nothing else runs on it.

Analogy: Renting a whole independent house instead of a flat: nobody else lives there, you can rebuild the inside as you like — and you pay for every room.

How it works internally, step by step

  1. Same API. You launch it like any instance (choose a .metal type).
  2. No provider hypervisor. The OS boots on the hardware; the Nitro cards still handle network/storage/security.
  3. Full hardware. All cores, memory and devices are yours.
  4. Your stack. Install your own hypervisor or OS tools if needed.
  5. Billing. Per second/hour like a VM, but for the whole machine.

Words used above, in simple terms: bare metal = a physical server with nothing virtual in between · nested virtualization = running VMs inside a VM · per-core licence = software priced per physical CPU core

For the experienced — did you know? On AWS, bare metal and VMs run on the same Nitro hardware: because the Nitro cards (not a software hypervisor) handle networking and storage, AWS can sell the very same server either as one .metal instance or as many VMs.

Use it when: licences need physical cores, you must run your own hypervisor or need hardware features a VM hides.
Avoid / be careful when: a normal VM would do — bare metal is large, slower to start and you lose some VM conveniences.

Type 3 · Managed Kubernetes and container orchestration

Definition (say it in an interview): Managed Kubernetes is a service in which the provider operates the Kubernetes control plane (API server, scheduler, etcd) with an SLA, while the customer’s containerised workloads run on worker nodes — VMs in the customer’s account or provider-managed capacity. Proprietary orchestrators such as Amazon ECS fill the same role.

In plain words (no jargon): A system that runs many containers for you across a group of servers — starting them, restarting them when they crash and adding more when busy. The cloud company runs the system’s “brain”.

Analogy: A food court: the management runs the building, electricity and seating plan (control plane); each stall (pod) is placed where there is space, and new counters are opened when queues grow.

How it works internally, step by step

  1. Create a cluster. The provider creates a highly available control plane.
  2. Add capacity. Node groups (VMs) or serverless node options.
  3. Describe the app. YAML manifests: Deployment (how many pods), Service (how to reach them).
  4. Schedule. The scheduler places pods on nodes with free CPU/memory.
  5. Self-heal and scale. Crashed pods restart; HPA adds pods, cluster autoscaler adds nodes.

Words used above, in simple terms: container = an app packed with everything it needs, sharing the host OS kernel · pod = the smallest unit Kubernetes runs — one or more containers · node = a machine (usually a VM) that runs pods · control plane = the part that decides what runs where

Use it when: you run many containerised services, want one consistent platform across clouds, or need Kubernetes features and tools.
Avoid / be careful when: you have one or two simple services — serverless containers (type 4) give the same result with far less to learn and operate.

Type 4 · Serverless containers

Definition (say it in an interview): Serverless container services run container images without the customer provisioning or managing servers or cluster nodes: you specify the image, CPU, memory and scaling rules; the provider supplies isolated compute, networking and often an HTTPS endpoint, and bills for the resources the containers use.

In plain words (no jargon): You give the cloud a packed app (a container). It runs it, gives you a web address and adds or removes copies with traffic. No servers to look after.

Analogy: Ordering from a cloud kitchen platform: you give the recipe (image); the platform finds kitchen space, cooks as many as are ordered and charges only for the cooking.

How it works internally, step by step

  1. Push an image. To a registry: Amazon ECR, Azure Container Registry, Artifact Registry (public images work too).
  2. Define the service. CPU, memory, port, environment variables, min/max instances.
  3. Platform runs it. Each task/instance gets isolated compute (Fargate uses Firecracker micro-VMs).
  4. Traffic. A managed endpoint or load balancer routes requests to healthy copies.
  5. Scale. Based on requests, CPU or queue length; to zero where supported.

Words used above, in simple terms: container image = a packaged app ready to run · registry = an online store of container images · task / revision = one running version of your container service · scale to zero = no copies running when there is no traffic

Products and cloud services

For the experienced — did you know? Cloud Run lets one instance handle many requests at once (concurrency, default 80) while Lambda handles one request per execution environment — so the same traffic can need far fewer Cloud Run instances, and costs behave differently.

Use it when: you have a containerised web app, API or worker and want no servers, simple scaling and a quick start.
Avoid / be careful when: you need special hardware, privileged access to the host or very long-running steady workloads where VMs with Savings Plans are cheaper.

Type 5 · Functions (Function as a Service)

Definition (say it in an interview): Function as a Service (FaaS) runs small pieces of code in response to events — HTTP requests, file uploads, queue messages, schedules — on fully managed, automatically scaled infrastructure, billed per invocation and execution time, with no cost when idle.

In plain words (no jargon): You write only a small piece of code and say “run this when X happens”. The cloud runs it, as many times as needed, and charges per run.

Analogy: A doorbell: nothing happens until someone presses it; each press rings once; ten visitors at once get ten rings.

How it works internally, step by step

  1. Upload code. A zip or container image plus a handler name and runtime (Python, Node.js, Java…).
  2. Connect a trigger. HTTP endpoint, storage event, queue, schedule.
  3. Invoke. The platform starts an execution environment (cold start) or reuses a warm one.
  4. Run and bill. Charged per request + GB-seconds (memory × time), per millisecond on Lambda.
  5. Scale. Parallel copies per event, up to a concurrency limit; idle → zero.

Words used above, in simple terms: event = a signal that something happened · trigger = the rule that connects an event to a function · cold start = extra delay when a new copy must start · GB-second = memory size × run time, the billing unit

Use it when: work is short, event-driven and bursty — glue between services, file processing, webhooks, scheduled tasks.
Avoid / be careful when: jobs run for long (Lambda max 15 minutes), need steady high throughput (often cheaper on containers/VMs) or very low latency on every call (cold starts).

Type 6 · App platforms (PaaS)

Definition (say it in an interview): An application platform (PaaS) runs web applications and APIs from source code or packages: the provider manages the operating system, language runtime, web server, load balancing, scaling and patching, while the customer manages the application code, its configuration and data.

In plain words (no jargon): You hand over your website’s code; the platform sets up and runs everything needed to put it online and keeps it updated.

Analogy: A tiffin-service kitchen you rent by the hour with stoves, gas and cleaning included: you bring only your recipe and ingredients.

How it works internally, step by step

  1. Choose a runtime. Python, Node.js, Java, .NET, PHP… (or a container).
  2. Deploy. From git, zip, or CI/CD; the platform builds it.
  3. Provision. Instances, load balancer, HTTPS certificate, health checks.
  4. Operate. Auto scaling rules, logs, OS and runtime patching by the provider.
  5. Release. Slots / versions / environments for blue-green deployments.

Words used above, in simple terms: runtime = the language engine your code needs, e.g. Python 3.12 · deployment slot = a second copy of the app for testing before going live · blue-green = two versions side by side; switch traffic between them

Use it when: you build a standard web app or API and want to spend time on code, not servers.

Type 7 · Batch, HPC and accelerated (GPU) compute

Definition (say it in an interview): Batch computing services schedule large numbers of jobs onto automatically provisioned compute and release it when done; accelerated computing instances add GPUs or other accelerators (e.g. AWS Trainium/Inferentia, Google TPUs) for parallel maths such as ML training, inference, rendering and simulation.

In plain words (no jargon): For very big jobs, the cloud quickly lends you many machines — or machines with powerful graphics chips (GPUs) for AI — and takes them back when the job is finished.

Analogy: A wedding caterer hiring extra cooks and big kadhais only for the wedding week, then sending them home.

How it works internally, step by step

  1. Define a job. A container image + command + CPU/memory/GPU needs.
  2. Queue. Jobs wait with priorities and dependencies.
  3. Provision. The service starts suitable instances (On-Demand or Spot, with GPUs if requested).
  4. Run in parallel. Array jobs split work into thousands of pieces; HPC uses fast networks (EFA, InfiniBand).
  5. Release. Instances terminate when the queue is empty; results land in storage.

Words used above, in simple terms: batch job = work that runs without a user waiting, e.g. overnight · GPU = a chip with thousands of small cores for parallel maths · HPC = high-performance computing — many machines working on one problem · array job = one job split into many similar pieces

6 Explained part by part

Parts of every VM: name, image, key, startup script, metadata, groups

Image (AMI / VM image)

What it is: The OS disk template the server starts from.

Why it exists: Every new server starts identical; golden images bake in your software.

Where it is used: AMIs, Azure Compute Gallery, GCE images.

Instance type / VM size

What it is: vCPU, memory, network and disk limits as one package.

Why it exists: Right-sizing is the biggest compute saving.

Where it is used: m7i.large · Standard_D2s_v5 · e2-standard-2.

Key pair / SSH key

What it is: Public key on the server, private key with you.

Why it exists: Password-less, safer login.

Where it is used: EC2 key pairs, Azure SSH keys, OS Login (GCP).

User data / custom data / startup script

What it is: A script that runs at first boot.

Why it exists: Automates installation — no manual setup.

Where it is used: cloud-init on Linux in all three clouds.

Instance metadata

What it is: A local endpoint (169.254.169.254) describing the instance.

Why it exists: Apps get their ID, Region and temporary credentials.

Where it is used: IMDSv2 on AWS (Lesson 4.6), Azure IMDS, GCE metadata server.

Groups of instances

What it is: Templates + scaling groups.

Why it exists: Self-healing and elastic fleets (Lesson 5.3).

Where it is used: Auto Scaling groups, VM Scale Sets, managed instance groups.

Myth vs reality: things many websites still say

  • Myth: Serverless means there are no servers.
    Reality: There are servers — you just do not manage them.
    Proof: Types 4–5.
  • Myth: A vCPU is a CPU core.
    Reality: Usually a hyper-thread; on Graviton a full core.
    Proof: Type 1 expert note.
  • Myth: Kubernetes is always the modern choice.
    Reality: For one or two services it is overhead.
    Proof: Type 3.

Instance families, burstable CPU credits, ARM chips and quotas

Burstable instances: CPU credits

T-family (AWS), B-series (Azure) and E2 shared-core (Google) give a baseline CPU share and let you burst above it using accumulated credits. Perfect for mostly idle servers; a busy server on a burstable type either slows to the baseline or (AWS “unlimited” mode) pays extra.

Graviton, Cobalt, Axion: ARM in the cloud

All three providers now design their own ARM server chips — AWS Graviton, Microsoft Azure Cobalt, Google Axion — offering better price-performance for many Linux workloads. Interpreted languages (Python, Node.js, Java) usually run unchanged; compiled code and containers need ARM builds.

Quotas: why “Launch” can fail on a new account

Each Region has service quotas (e.g. a vCPU limit for On-Demand instances, GPU limits often zero on new accounts). Errors like VcpuLimitExceeded (AWS), QuotaExceeded (Azure) or QUOTA_EXCEEDED (Google) mean: request an increase in Service Quotas / Quotas pages.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. Steps 1–4 take about 40 minutes; with clean-up, the cost is a few rupees of credit.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Launch a Linux VM that serves a web page

    Pick your cloud.

    UI way — AWS Management Console

    1. EC2 → Instances → Launch instances. Name: tiffingo-vm.
    2. Image: Amazon Linux 2023 AMI. Instance type: t3.micro (free-tier eligible).
    3. Key pair: Proceed without a key pair (we will use the browser connect) — or create one if you want SSH from your laptop.
    4. Network settings → Edit: keep the default VPC; Allow SSH traffic from Anywhere (lab only), tick Allow HTTP traffic from the internet.
    5. Advanced details → User data: paste the script on the right (the part between the EOF lines) → Launch instance.

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
dnf install -y nginx
echo "<h1>TiffinGo menu — served from $(hostname)</h1>" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
EOF
SG=$(aws ec2 create-security-group --group-name tiffingo-web --description "TiffinGo lab web" --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 80 --cidr 0.0.0.0/0
ID=$(aws ec2 run-instances --instance-type t3.micro --security-group-ids $SG \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --user-data file://web.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=tiffingo-vm}]' \
  --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --instance-ids $ID
IP=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)
sleep 60; curl http://$IP

    You should see: state Running, status checks 2/2 passed, and <h1>TiffinGo menu — served from ip-172-31-…</h1> from curl or in the browser at http://PUBLIC-IP. If the page does not load, wait a minute — user data is still installing nginx.

    UI way — Azure portal

    1. Virtual machines → Create → Azure virtual machine.
    2. Resource group: Create new rg-tiffingo; name tiffingo-vm; Region (Asia Pacific) Central India; image Ubuntu Server 24.04 LTS; size Standard_B1s.
    3. Authentication: SSH public key, username azureuser, Generate new key pair. Inbound ports: tick HTTP (80) and SSH (22).
    4. Advanced tab → Custom data: paste the Ubuntu script (between the EOF lines) → Review + create → Create → download the private key when asked.

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
apt-get update && apt-get install -y nginx
echo "<h1>TiffinGo menu — served from $(hostname)</h1>" > /var/www/html/index.html
systemctl enable --now nginx
EOF
az group create --name rg-tiffingo --location centralindia
az vm create --resource-group rg-tiffingo --name tiffingo-vm --image Ubuntu2404 \
  --size Standard_B1s --admin-username azureuser --generate-ssh-keys --custom-data web.sh
az vm open-port --resource-group rg-tiffingo --name tiffingo-vm --port 80
IP=$(az vm show --show-details --resource-group rg-tiffingo --name tiffingo-vm --query publicIps --output tsv)
sleep 60; curl http://$IP

    You should see: JSON output with "powerState": "VM running" and a publicIpAddress, then the TiffinGo heading from curl. If the B1s size is not offered in Central India for your subscription, pick another small size such as Standard_B2ats_v2.

    UI way — Google Cloud console

    1. Compute Engine → VM instances → Create instance (enable the Compute Engine API if asked).
    2. Name tiffingo-vm; Region asia-south1 (Mumbai), zone asia-south1-a; machine type e2-micro.
    3. OS and storage: Debian 12. Networking: tick Allow HTTP traffic.
    4. Advanced → Automation → Startup script: paste the Debian script (between the EOF lines) → Create.

    CLI way — the same thing with commands

    cat > web.sh <<'EOF'
#!/bin/bash
apt-get update && apt-get install -y nginx
echo "<h1>TiffinGo menu — served from $(hostname)</h1>" > /var/www/html/index.html
systemctl enable --now nginx
EOF
gcloud compute instances create tiffingo-vm --zone=asia-south1-a --machine-type=e2-micro \
  --image-family=debian-12 --image-project=debian-cloud --tags=http-server \
  --metadata-from-file=startup-script=web.sh
gcloud compute firewall-rules create allow-http --allow=tcp:80 --target-tags=http-server
IP=$(gcloud compute instances describe tiffingo-vm --zone=asia-south1-a --format='get(networkInterfaces[0].accessConfigs[0].natIP)')
sleep 60; curl http://$IP

    You should see: a table row with STATUS RUNNING and an EXTERNAL_IP, then the TiffinGo heading. Note: Google’s always-free e2-micro applies only in some US Regions; in Mumbai it uses your trial credit (a few rupees a day).

    User data / custom data / startup script runs once at first boot through cloud-init (Google uses its guest agent) — that is how fleets of identical servers are built without logging in.

  3. 2 · Look inside the running VM

    Pick your cloud.

    UI way — AWS Management Console

    1. Select the instance → Connect → EC2 Instance Connect → Connect — a terminal opens in the browser.
    2. Run curl -s http://169.254.169.254/latest/meta-data/instance-type -H "X-aws-ec2-metadata-token: $(curl -s -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')" → prints the type from the metadata service.
    3. Monitoring tab: CPU utilization graph; Actions → Monitor and troubleshoot → Get system log shows the boot log.

    CLI way — the same thing with commands

    aws ec2 describe-instances --instance-ids $ID \
  --query 'Reservations[0].Instances[0].[InstanceType,Placement.AvailabilityZone,State.Name,PrivateIpAddress]' --output table
aws ec2 get-console-output --instance-id $ID --latest --output text | tail -20     # boot log

    You should see: type t3.micro, an AZ such as ap-south-1a, state running; the boot log ends with cloud-init “finished” lines.

    UI way — Azure portal

    1. Open the VM → Operations → Run command → RunShellScript → enter systemctl is-active nginx; nproc; free -m → Run.
    2. Or Connect → SSH using the downloaded key: ssh -i key.pem azureuser@PUBLIC-IP.
    3. Monitoring → Metrics → Percentage CPU.

    CLI way — the same thing with commands

    az vm run-command invoke --resource-group rg-tiffingo --name tiffingo-vm --command-id RunShellScript \
  --scripts "systemctl is-active nginx; nproc; free -m"
az vm get-instance-view --resource-group rg-tiffingo --name tiffingo-vm \
  --query "instanceView.statuses[].displayStatus" --output tsv

    You should see: active, 1 vCPU and about 900 MB memory for B1s; “Provisioning succeeded” and “VM running”.

    UI way — Google Cloud console

    1. In VM instances click SSH next to the VM — a browser terminal opens.
    2. Run curl -s -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/machine-type.
    3. Open the VM → Observability tab for CPU and network graphs; Serial port 1 (console) shows the boot log.

    CLI way — the same thing with commands

    gcloud compute ssh tiffingo-vm --zone=asia-south1-a --command="systemctl is-active nginx; nproc; free -m"
gcloud compute instances get-serial-port-output tiffingo-vm --zone=asia-south1-a | tail -20

    You should see: active, 2 vCPUs (e2-micro has 2 shared vCPUs) and about 1 GB memory; startup-script lines in the serial log.

    Every cloud gives a VM a local metadata service at 169.254.169.254 — that is where the instance learns its own type, zone and temporary credentials.

  4. 3 · Resize it (vertical scaling)

    Pick your cloud.

    UI way — AWS Management Console

    1. Select the instance → Instance state → Stop instance → wait for Stopped.
    2. Actions → Instance settings → Change instance type → t3.small → Apply.
    3. Instance state → Start instance. Note: the public IP changes (use an Elastic IP when it must not).

    CLI way — the same thing with commands

    aws ec2 stop-instances --instance-ids $ID && aws ec2 wait instance-stopped --instance-ids $ID
aws ec2 modify-instance-attribute --instance-id $ID --instance-type "{\"Value\": \"t3.small\"}"
aws ec2 start-instances --instance-ids $ID && aws ec2 wait instance-running --instance-ids $ID
aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].[InstanceType,PublicIpAddress]' --output text

    You should see: t3.small and a new public IP — proof that stop/start may move the VM to another host.

    UI way — Azure portal

    1. Open the VM → Availability + scale → Size → pick Standard_B2s → Resize (Azure restarts the VM; if the size is not available it asks you to stop first).

    CLI way — the same thing with commands

    az vm resize --resource-group rg-tiffingo --name tiffingo-vm --size Standard_B2s
az vm show --resource-group rg-tiffingo --name tiffingo-vm --query hardwareProfile.vmSize --output tsv

    You should see: Standard_B2s. The public IP normally stays (it is a separate resource).

    UI way — Google Cloud console

    1. Stop the VM → Edit → Machine configuration → machine type e2-small → Save → Start / Resume.

    CLI way — the same thing with commands

    gcloud compute instances stop tiffingo-vm --zone=asia-south1-a
gcloud compute instances set-machine-type tiffingo-vm --zone=asia-south1-a --machine-type=e2-small
gcloud compute instances start tiffingo-vm --zone=asia-south1-a

    You should see: e2-small in the console; an ephemeral external IP may change after stop/start.

    Vertical scaling needs a restart in every cloud — one reason Lesson 5.3 prefers scaling out.

  5. 4 · Run a container without managing servers

    Pick your cloud.

    UI way — AWS Management Console

    1. Elastic Container Service → left menu Express mode.
    2. Image URI: public.ecr.aws/nginx/nginx:latest. Task execution role and Infrastructure role: Create new role for both.
    3. Create → watch the Resources tab; when done open the Application URL.

    CLI way — the same thing with commands

    ACCT=$(aws sts get-caller-identity --query Account --output text)
aws iam create-role --role-name ecsTaskExecutionRole --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs-tasks.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam create-role --role-name ecsInfrastructureRoleForExpressServices --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name ecsTaskExecutionRole \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy
aws iam attach-role-policy --role-name ecsInfrastructureRoleForExpressServices \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSInfrastructureRoleforExpressGatewayServices
sleep 20   # IAM roles take a few seconds to become usable
aws ecs create-express-gateway-service --service-name tiffingo-hello \
  --primary-container image=public.ecr.aws/nginx/nginx:latest \
  --execution-role-arn arn:aws:iam::$ACCT:role/ecsTaskExecutionRole \
  --infrastructure-role-arn arn:aws:iam::$ACCT:role/ecsInfrastructureRoleForExpressServices \
  --monitor-resources

    You should see: resources created one by one (service, load balancer, target group, scaling policy) and an Application URL like https://tiffingo-hello.ecs.ap-south-1.on.aws/ showing “Welcome to nginx!”. This creates a load balancer that costs money every hour — delete it in the cleanup.

    UI way — Azure portal

    1. Search Container Apps → Create → Container App.
    2. Resource group rg-tiffingo, name tiffingo-hello, Region Central India, new Container Apps environment.
    3. Container tab: tick Use quickstart image → Simple hello world container. Ingress: enabled, Accepting traffic from anywhere, target port 80 → Review + create → Create → open the Application Url.

    CLI way — the same thing with commands

    az containerapp up --name tiffingo-hello --resource-group rg-tiffingo --location centralindia \
  --image mcr.microsoft.com/k8se/quickstart:latest --target-port 80 --ingress external
az containerapp show --name tiffingo-hello --resource-group rg-tiffingo \
  --query properties.configuration.ingress.fqdn --output tsv

    You should see: a URL like https://tiffingo-hello.<random>.centralindia.azurecontainerapps.io showing the Azure Container Apps welcome page. If the CLI asks to install the containerapp extension, answer Y.

    UI way — Google Cloud console

    1. Cloud Run → Deploy container → Service.
    2. Test with a sample container (or image us-docker.pkg.dev/cloudrun/container/hello); name tiffingo-hello; Region asia-south1 (Mumbai).
    3. Authentication: Allow public access (unauthenticated) → Create → open the URL at the top.

    CLI way — the same thing with commands

    gcloud run deploy tiffingo-hello --image=us-docker.pkg.dev/cloudrun/container/hello \
  --region=asia-south1 --allow-unauthenticated
gcloud run services describe tiffingo-hello --region=asia-south1 --format="value(status.url)"

    You should see: “Service URL: https://tiffingo-hello-….asia-south1.run.app” and a page saying “It’s running!”. With no traffic it scales to zero instances.

    Same container, three platforms: Fargate behind a load balancer (AWS), Container Apps on a managed Kubernetes-based environment (Azure), Cloud Run on Google’s serverless infrastructure.

Clean up and cost check

AWS: ECS → Clusters → default → Services → select tiffingo-hello → Delete service; EC2 → select tiffingo-vm → Instance state → Terminate; then delete security group tiffingo-web. CLI: aws ecs delete-express-gateway-service --service-arn ARN (ARN from aws ecs list-services --cluster default); aws ec2 terminate-instances --instance-ids $ID; aws ec2 wait instance-terminated --instance-ids $ID; aws ec2 delete-security-group --group-id $SG.
Azure: Resource groups → rg-tiffingo → Delete resource group (removes the VM, disk, IP and container app together). CLI: az group delete --name rg-tiffingo --yes --no-wait.
Google Cloud: VM instances → select → Delete; Cloud Run → select → Delete; VPC network → Firewall → delete allow-http. CLI: gcloud compute instances delete tiffingo-vm --zone=asia-south1-a --quiet; gcloud run services delete tiffingo-hello --region=asia-south1 --quiet; gcloud compute firewall-rules delete allow-http --quiet.
Then check your bill page next day — it should show only a few rupees.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Everything on VMs “because we know VMs”.Habit.Use the decision path: most managed option that fits.
Picking a big instance “to be safe”.No measurement.Start small, watch CPU/memory, right-size (Compute Optimizer / Advisor / Recommender).
Forgetting stopped VMs still cost.Disks and IPs keep billing.Terminate/delete when done; delete disks and IPs too.
