1 The story

Nine service names in one diagram

Before you start: 6.1, 6.2 and 6.3.

🤔 AWS lists more than 200 services, Azure and Google Cloud a similar number. Do you need to learn them all?

No. Almost every service belongs to one of about a dozen categories, and each category answers one question: where does my code run, where does my data live, how do I analyse it, how do I secure it, how do I watch and automate it, how do parts talk to each other. Learn the categories and the one or two flagship services in each, and you can read any cloud architecture — and translate it between AWS, Azure and Google Cloud. This lesson builds that map, follows one TiffinGo order through eight services, and has you browse the catalogue, send messages through a queue and list everything you own on your own account.

2 Definition

Cloud products and solutions

Formal definition (write this in exams)

Cloud providers offer hundreds of products organised into families — compute, storage, networking, databases, analytics, AI/ML, security and identity, management and governance, developer tools, integration, IoT and more — which customers combine, often with Marketplace software and reference architectures, into solutions for business and industry problems.

In simple words

The cloud’s menu card: hundreds of services grouped into a dozen sections. Learn the sections and the main dish in each, and you can understand any cloud design.

Say it in an interview

30-second answer you can speak:

  • “I group cloud services into families — compute, storage, networking, databases, analytics, AI, security, management, DevOps and integration — and know the flagship in each for AWS, Azure and Google Cloud.”
  • “For a new requirement I ask which family, then prefer the most managed service that fits, and check limits and pricing.”

Type 1 · Managed databases

Definition (say it in an interview): Managed database services run database engines for you — provisioning, patching, backups, replication and failover — in several models: relational (SQL, transactions: RDS, Aurora, Azure SQL, Cloud SQL), NoSQL (key-value, document, wide-column, graph: DynamoDB, Cosmos DB, Firestore, Bigtable) and in-memory caches (ElastiCache, Azure Cache for Redis, Memorystore).

In plain words (no jargon): Databases that the cloud company runs for you: it installs them, backs them up, fixes them and keeps a spare copy ready. You just store and read your data.

Analogy: Renting a bank locker with a full-time locker staff, instead of buying your own safe and hiring a guard: you keep the valuables (data), they handle the locks, CCTV and backups.

How it works internally, step by step

  1. Choose engine and size. PostgreSQL/MySQL/SQL Server…, instance class or serverless capacity.
  2. Provisioned in your network. Placed in private subnets with security groups (Lesson 6.3).
  3. High availability. Synchronous standby in another AZ (Multi-AZ) with automatic failover.
  4. Backups. Automated daily snapshots + transaction logs → point-in-time restore.
  5. Scale. Read replicas, bigger instances, or automatic partitioning (NoSQL).

Words used above, in simple terms: relational = data in tables linked by keys, queried with SQL · NoSQL = databases that do not use fixed tables, built for scale · transaction = a group of changes that all succeed or all fail · read replica = a read-only copy that takes reporting load

Products and cloud services

Amazon RDS, Aurora, DynamoDB, ElastiCache, DocumentDB, Neptune; Azure SQL Database, Azure Database for PostgreSQL/MySQL, Cosmos DB, Azure Managed Redis; Cloud SQL, AlloyDB, Spanner, Firestore, Bigtable, Memorystore.

For the experienced — did you know? Aurora separates compute from storage: the database writes only redo log records to a storage layer that keeps six copies across three AZs and builds pages itself — which is why Aurora replicas can be added in minutes without copying the data.

Use it when: you need a database and do not want to run its servers — which is almost always.
Avoid / be careful when: you pick a NoSQL store for data full of relationships, or a relational database for unlimited simple key lookups at massive scale.

Type 2 · Analytics and big data

Definition (say it in an interview): Cloud analytics services collect, store, process and query large datasets: streaming ingestion (Kinesis, Event Hubs, Pub/Sub), data lakes on object storage, managed Spark/Hadoop and ETL (EMR, Glue, Dataproc, Databricks, Fabric), data warehouses and serverless SQL (Redshift, Athena, BigQuery, Fabric/Synapse), and BI tools (QuickSight, Power BI, Looker).

In plain words (no jargon): Services for big data: they collect lots of data, keep it cheaply, clean it and answer questions about it, often with charts.

Analogy: A sabzi mandi supply chain: trucks bring raw vegetables (ingest), the godown stores them cheaply (lake), workers sort and pack them (processing), and the shop shelf shows exactly what customers want (dashboard).

How it works internally, step by step

  1. Ingest. Batch uploads or real-time streams.
  2. Store. Raw and curated zones in object storage (open formats like Parquet, Iceberg, Delta).
  3. Catalogue. Glue Data Catalog / Unity Catalog / Dataplex describe tables and permissions.
  4. Process. Spark/Beam jobs on managed or serverless clusters.
  5. Serve. Warehouse or serverless SQL for analysts; BI dashboards for business users.

Words used above, in simple terms: data lake = a big store of raw files, usually object storage · data warehouse = a database optimised for analysis over huge tables · ETL = extract, transform, load — cleaning and moving data · Parquet = a compressed, column-based file format for analytics

Products and cloud services

Amazon Kinesis, MSK, S3, Glue, EMR, Athena, Redshift, QuickSight, Lake Formation; Azure Event Hubs, Data Lake Storage, Microsoft Fabric, Synapse, Azure Databricks, Power BI; Google Pub/Sub, Dataflow, Dataproc, BigQuery, Looker.

For the experienced — did you know? Google’s BigQuery separates storage and compute so completely that you can query petabytes without creating any cluster — you pay per TB scanned (or for reserved slots). Partitioning and clustering tables can cut both cost and time by 10× or more.

Use it when: you analyse more data than a single database should handle, or need reports without slowing the live app.
Avoid / be careful when: a few thousand rows fit in a spreadsheet or the app database — a data platform is overkill.

Type 3 · AI and machine learning

Definition (say it in an interview): Cloud AI and ML services come in three levels: pre-trained AI APIs (speech, vision, translation, document extraction), generative AI / foundation-model services that offer large language and image models through an API (Amazon Bedrock, Azure OpenAI in Microsoft Foundry, Vertex AI with Gemini), and ML platforms for building, training and deploying custom models (SageMaker AI, Azure Machine Learning, Vertex AI).

In plain words (no jargon): Cloud services that add “intelligence” to apps — reading text in photos, translating, chatting, writing, or predicting things from your own data.

Analogy: Food options: buy a ready-made sweet (AI API), order a custom cake from a famous baker by describing it (foundation model), or bake your own in a rented commercial kitchen (ML platform).

How it works internally, step by step

  1. Pick the level. API → foundation model (+ your data) → custom model.
  2. Call the API. Send text/image/audio; get a result; pay per request, character or token.
  3. Ground with your data. Retrieval-augmented generation (RAG): search your documents and add them to the prompt.
  4. Train (if needed). Managed notebooks and training jobs on GPUs; track experiments.
  5. Deploy and monitor. Endpoints, guardrails, evaluation, drift monitoring and cost limits.

Words used above, in simple terms: model = a program learned from data that makes predictions · foundation model / LLM = a large model trained on huge data, usable for many tasks · token = a piece of a word — the unit LLMs read and bill · RAG = adding your own documents to a model’s prompt

For the experienced — did you know? Most generative-AI cost is in tokens, and output tokens usually cost several times more than input tokens. Asking a model for short, structured answers (and caching repeated prompts) is often the biggest saving — bigger than switching providers.

Use it when: you need language, vision or prediction features — start with the highest level that solves the problem.
Avoid / be careful when: you train custom models when an API or a prompted foundation model already works — or send sensitive data without checking data-use and residency terms.

Type 4 · Security, identity and compliance

Definition (say it in an interview): Security and identity services control and protect access to cloud resources: identity and access management (users, roles, policies, single sign-on — IAM, Microsoft Entra ID, Cloud IAM), key and secret management (KMS, Key Vault, Secret Manager), threat detection and posture management (GuardDuty, Security Hub, Defender for Cloud, Security Command Center), and network/application protection (WAF, DDoS).

In plain words (no jargon): Services that check who you are, decide what you are allowed to do, lock data with keys, and raise an alarm when something looks suspicious.

Analogy: A hotel: the reception checks your ID (authentication), your key card opens only your room and the gym (authorisation), the safe in the room has its own key (KMS), and CCTV flags anyone trying every door (threat detection).

How it works internally, step by step

  1. Identities. Users, groups, roles, service accounts / managed identities.
  2. Authenticate. Passwords + MFA, SSO federation, short-lived tokens.
  3. Authorise. JSON policies or role assignments evaluated on every API call (default deny).
  4. Encrypt. KMS keys for data at rest; TLS in transit.
  5. Detect and respond. Findings from logs and behaviour → alerts, automated fixes.

Words used above, in simple terms: authentication = proving who you are · authorisation = deciding what you may do · MFA = multi-factor authentication — e.g. password + phone code · least privilege = only the permissions really needed

Use it when: always — identity is the new perimeter in the cloud; every other control depends on it.
Avoid / be careful when: you share root/owner credentials, use long-lived access keys on laptops, or grant “*” permissions to make an error go away.

Type 5 · Management, monitoring and governance

Definition (say it in an interview): Management and governance services observe and control cloud environments: monitoring of metrics, logs and traces with alarms (CloudWatch, Azure Monitor, Cloud Monitoring/Logging), audit logs of every API call (CloudTrail, Activity Log, Cloud Audit Logs), configuration and policy enforcement (AWS Config, Organizations SCPs, Azure Policy, Organization Policy), resource organisation and cost management.

In plain words (no jargon): Tools that show how everything is running, record every change people make, and enforce company rules across all cloud accounts.

Analogy: A building’s control room: CCTV and meters (monitoring), the visitor register (audit log), and the society rules notice board that the guard enforces (policy).

How it works internally, step by step

  1. Collect. Services publish metrics automatically; agents add OS metrics and app logs.
  2. Visualise and alert. Dashboards and alarms on thresholds or anomalies.
  3. Audit. Control-plane API calls logged by default (90 days in CloudTrail event history).
  4. Evaluate. Config rules / Azure Policy check resources continuously.
  5. Enforce. Organisation-level guardrails (SCPs, policies) and budgets.

Words used above, in simple terms: metric = a number over time, e.g. CPU % · log = a text record of an event · trace = the path of one request through many services · guardrail = a rule that prevents a risky action

Avoid / be careful when: logs are collected but never looked at, or log retention is so long that the logging bill exceeds the app bill.

Type 6 · DevOps tools and infrastructure as code

Definition (say it in an interview): Infrastructure as code (IaC) services create and update cloud resources from declarative templates kept in version control (CloudFormation/CDK, ARM/Bicep, Google Infrastructure Manager, and the cross-cloud Terraform/OpenTofu), while DevOps services automate building, testing and releasing software through pipelines (CodePipeline/CodeBuild, Azure DevOps, GitHub Actions, Cloud Build/Cloud Deploy).

In plain words (no jargon): Writing your servers, networks and databases as a text file, so a tool can build them exactly the same way every time — and automating how new app versions go live.

Analogy: A recipe card instead of “cook from memory”: anyone can make the same dal every time, changes are written down, and a new kitchen can be set up from the same card.

How it works internally, step by step

  1. Write. Declare resources and their settings in YAML/JSON/HCL/code.
  2. Plan. The tool computes the difference between the file and reality (change set / plan / what-if).
  3. Apply. It creates/updates/deletes resources in the right order.
  4. Version. Templates live in git; changes go through reviews.
  5. Pipeline. CI builds and tests code; CD deploys it through stages with approvals.

Words used above, in simple terms: IaC = infrastructure as code · declarative = you describe the end state, the tool works out the steps · drift = real resources differing from the template · CI/CD = continuous integration / continuous delivery

Type 7 · Application integration (messaging, events, APIs)

Definition (say it in an interview): Application integration services let independent components communicate reliably: message queues (SQS, Service Bus queues, Pub/Sub pull), publish/subscribe topics (SNS, Service Bus topics, Pub/Sub), event buses (EventBridge, Event Grid, Eventarc), API gateways (API Gateway, API Management, Apigee) and workflow orchestration (Step Functions, Logic Apps, Workflows).

In plain words (no jargon): Services that pass messages between parts of an app, so each part can work at its own speed and nothing is lost if one part is slow or down.

Analogy: The kitchen order spike at a dhaba: waiters pin order slips on a rail (queue); the cook takes the next slip when free. Nobody shouts across the room and no order is lost in the rush.

How it works internally, step by step

  1. Produce. A service sends a message/event (JSON) to a queue, topic or bus.
  2. Store durably. The service keeps it replicated until delivered.
  3. Deliver. Consumers poll (queue) or receive pushes (topic/bus).
  4. Acknowledge. Consumers delete/ack after processing; otherwise it reappears (visibility timeout).
  5. Handle failures. Retries, then a dead-letter queue for messages that keep failing.

Words used above, in simple terms: message = a small piece of data sent between services · decouple = make parts independent of each other · pub/sub = publish once, every subscriber receives it · dead-letter queue = a parking place for messages that keep failing

Real scenario (TiffinGo)

TiffinGo’s order service publishes “OrderPlaced” to a topic; the kitchen, delivery-partner and SMS services each get their own copy through queues. During the Diwali rush the kitchen queue grows to 4,000 messages and drains over 10 minutes — nothing is lost and the app stays fast.

Products and cloud services

Amazon SQS, SNS, EventBridge, API Gateway, Step Functions, MQ, AppSync; Azure Service Bus, Event Grid, Storage Queues, API Management, Logic Apps; Google Pub/Sub, Eventarc, Cloud Tasks, Apigee, API Gateway, Workflows.

For the experienced — did you know? Standard SQS queues deliver at least once and not always in order; FIFO queues give ordering and exactly-once processing within a limit of throughput. Consumers must therefore be idempotent — processing the same order message twice must not create two tiffins.

Use it when: components should not wait for each other, traffic is spiky, or one event must reach several systems.
Avoid / be careful when: a simple synchronous call is enough and you add queues “just in case” — every hop adds latency and things to monitor.

6 Explained part by part

Six words for reading any product page

Service family

What it is: A group of services that answer the same question.

Why it exists: Lets you read any architecture quickly.

Where it is used: The ten families above.

Flagship service

What it is: The most used service in a family.

Why it exists: Learn these first; exams focus on them.

Where it is used: S3, EC2, RDS, Lambda, IAM, CloudWatch…

Managed vs self-managed

What it is: Who runs the software.

Why it exists: Managed saves operations work; self-managed gives control.

Where it is used: RDS vs PostgreSQL on EC2.

Serverless

What it is: No servers to size; scales and bills per use.

Why it exists: Fits spiky, event-driven work.

Where it is used: Lambda, DynamoDB, Athena, BigQuery, Cloud Run.

Marketplace

What it is: Third-party software sold through the cloud bill.

Why it exists: Buy firewalls, databases, SaaS without new contracts.

Where it is used: AWS Marketplace, Azure Marketplace, Google Cloud Marketplace.

Industry solutions

What it is: Reference architectures for sectors.

Why it exists: Faster, compliant designs.

Where it is used: Solutions libraries, Well-Architected, Cloud Adoption Framework, Architecture Center.

Myth vs reality: things many websites still say

  • Myth: You must know every service.
    Reality: Know the families and flagships.
    Proof: The map.
  • Myth: Same name = same service.
    Reality: Compare features and limits.
    Proof: Translation table.
  • Myth: Products never change.
    Reality: They are renamed and retired regularly.
    Proof: Deep dive lifecycle table.
7 Deep dive

Translating architectures, product lifecycles and where to discover services

How to translate an architecture between clouds in five minutes

  1. Label each box with its family (compute, database, integration…).
  2. Find the matching service in the translation table above.
  3. Check the scope differences (Google VPC is global; Azure needs resource groups; AWS subnets are per AZ).
  4. Check identity: IAM roles ↔ managed identities ↔ service accounts.
  5. Check pricing models (Lesson 5.5) — equivalent services rarely cost the same.

Service lifecycles: products appear, get renamed and retire

Before an interview or exam, check the provider’s “what’s new” pages: older practice questions often mention retired products.

Where to discover services

  • AWS: the console’s [All services] menu and aws.amazon.com/products; Azure: [All services] in the portal and the Azure updates page; Google: the console’s navigation menu and the product overview page.
  • Architecture centres: AWS Architecture Center, Azure Architecture Center, Google Cloud Architecture Center — real reference designs by industry.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. These steps use free-tier-level messaging and catalogue/inventory APIs — no VMs.

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Explore the catalogue and enable a service

    Pick your cloud.

    UI way — AWS Management Console

    1. Console top search bar → type queue → see SQS, SNS, MQ with one-line descriptions.
    2. Click the ☆ next to Simple Queue Service to add it to Favorites; open All services and browse by category.
    3. AWS services need no “enabling” — they are available in every account (some, like Bedrock models, need access requests).

    CLI way — the same thing with commands

    aws ec2 describe-regions --query 'Regions[].RegionName' --output text | tr '\t' '\n' | head -5
aws ssm get-parameters-by-path --path /aws/service/global-infrastructure/regions/ap-south-1/services \
  --query 'Parameters[].Value' --output text | tr '\t' '\n' | wc -l    # services offered in Mumbai

    You should see: a list of Regions and a count of services available in Mumbai (well over 200).

    UI way — Azure portal

    1. Portal search bar → queue → Service Bus, Storage queues, Event Grid.
    2. All services → Categories → Integration. Hover a service → ☆ Favorite.
    3. Many services need a resource provider registered in your subscription: Subscriptions → your subscription → Resource providers → Microsoft.ServiceBus → Register.

    CLI way — the same thing with commands

    az provider list --query "[?registrationState=='Registered'].namespace" --output tsv | head
az provider register --namespace Microsoft.ServiceBus
az provider show --namespace Microsoft.ServiceBus --query registrationState --output tsv

    You should see: registered providers, then Registering → Registered for Microsoft.ServiceBus.

    UI way — Google Cloud console

    1. ☰ Navigation menu → View all products → search Pub/Sub → pin it.
    2. APIs & Services → Library → search “Cloud Pub/Sub API” → Enable.
    3. Google Cloud requires each service’s API to be enabled per project before first use.

    CLI way — the same thing with commands

    gcloud services list --enabled | head
gcloud services enable pubsub.googleapis.com
gcloud services list --available --filter="name:pubsub" --format="value(name)"

    You should see: enabled APIs, an “Operation … finished successfully” message, and pubsub.googleapis.com.

    Three clouds, three habits: AWS services are on by default, Azure registers resource providers, Google enables APIs per project.

  3. 2 · Decouple with a queue: send and receive an order

    Pick your cloud.

    UI way — AWS Management Console

    1. Simple Queue Service → Create queue → Standard, name tiffingo-kitchen → Create queue.
    2. Open it → Send and receive messages → body {"order":101,"dish":"thali"} → Send message.
    3. Poll for messages → open the message → Delete (the consumer’s “done”).

    CLI way — the same thing with commands

    Q=$(aws sqs create-queue --queue-name tiffingo-kitchen --query QueueUrl --output text)
aws sqs send-message --queue-url $Q --message-body '{"order":101,"dish":"thali"}'
MSG=$(aws sqs receive-message --queue-url $Q --wait-time-seconds 5)
echo "$MSG"
RH=$(echo "$MSG" | python3 -c 'import sys,json; print(json.load(sys.stdin)["Messages"][0]["ReceiptHandle"])')
aws sqs delete-message --queue-url $Q --receipt-handle "$RH"

    You should see: a MessageId after sending, the JSON body after receiving, and no output from delete. If you receive without deleting, the message reappears after the 30-second visibility timeout.

    UI way — Azure portal

    1. Storage account from Lesson 6.2 (or create one) → Queues → + Queue tiffingo-kitchen.
    2. Open it → Add message → {"order":101,"dish":"thali"} → OK.
    3. Dequeue message removes the oldest message (Service Bus offers the same with more features).

    CLI way — the same thing with commands

    az storage queue create --account-name $SA --name tiffingo-kitchen --auth-mode key
az storage message put --account-name $SA --queue-name tiffingo-kitchen --content '{"order":101,"dish":"thali"}' --auth-mode key
az storage message get --account-name $SA --queue-name tiffingo-kitchen --auth-mode key --output json
# delete with the id and popReceipt shown above:
# az storage message delete --account-name $SA --queue-name tiffingo-kitchen --id ID --pop-receipt RECEIPT --auth-mode key

    You should see: the message with an id and popReceipt; until deleted it becomes visible again after 30 seconds.

    UI way — Google Cloud console

    1. Pub/Sub → Topics → Create topic → ID tiffingo-orders, keep Add a default subscription → Create.
    2. Topic → Messages → Publish message → body {"order":101,"dish":"thali"} → Publish.
    3. Subscription → Messages → Pull → tick Enable ack messages → Ack.

    CLI way — the same thing with commands

    gcloud pubsub topics create tiffingo-orders
gcloud pubsub subscriptions create tiffingo-kitchen --topic=tiffingo-orders
gcloud pubsub topics publish tiffingo-orders --message='{"order":101,"dish":"thali"}'
gcloud pubsub subscriptions pull tiffingo-kitchen --auto-ack --limit=1

    You should see: a messageIds line after publishing and a table with the DATA after pulling. Add a second subscription and publish again — both get a copy (pub/sub fan-out).

    The producer never waits for the consumer — that is what keeps the app fast during Diwali.

  4. 3 · List everything you own (and tag it)

    Pick your cloud.

    UI way — AWS Management Console

    1. Resource Groups & Tag Editor → Tag Editor → Region ap-south-1, all resource types → Search resources.
    2. Select the queue → Manage tags of selected resources → add project = tiffingo → Save changes.
    3. Search again with tag project = tiffingo.

    CLI way — the same thing with commands

    aws sqs tag-queue --queue-url $Q --tags project=tiffingo
aws resourcegroupstaggingapi get-resources --tag-filters Key=project,Values=tiffingo \
  --query 'ResourceTagMappingList[].ResourceARN' --output text

    You should see: the ARN of the queue (and anything else you tagged).

    UI way — Azure portal

    1. All resources → filter by resource group rg-tiffingo → group by type.
    2. Select the storage account → Tags → project : tiffingo → Apply.
    3. Resource Graph Explorer lets you query all resources with KQL.

    CLI way — the same thing with commands

    az resource list --resource-group rg-tiffingo --query "[].[type,name]" --output table
az tag update --resource-id $(az storage account show --name $SA --query id --output tsv) --operation Merge --tags project=tiffingo
az resource list --tag project=tiffingo --query "[].name" --output tsv

    You should see: every resource in the group, then just the tagged ones.

    UI way — Google Cloud console

    1. IAM & Admin → Asset Inventory → Resource tab — every resource in the project.
    2. Add a label to the topic: Pub/Sub → topic → Labels → project: tiffingo.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud services enable cloudasset.googleapis.com
gcloud pubsub topics update tiffingo-orders --update-labels=project=tiffingo
gcloud asset search-all-resources --scope=projects/$P --query="labels.project:tiffingo" --format="value(name)"

    You should see: the topic’s full resource name. (Asset search can take a few minutes to see new resources.)

    Tags/labels are how companies find owners, split bills by team and clean up forgotten resources.

Clean up and cost check

AWS: SQS → select tiffingo-kitchen → Delete. CLI: aws sqs delete-queue --queue-url $Q.
Azure: delete the queue, or the whole resource group: az storage queue delete --account-name $SA --name tiffingo-kitchen --auth-mode key / az group delete --name rg-tiffingo --yes --no-wait.
Google Cloud: gcloud pubsub subscriptions delete tiffingo-kitchen; gcloud pubsub topics delete tiffingo-orders (also delete any default tiffingo-orders-sub created in the console).

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Trying to memorise all 200+ services.Exam anxiety.Learn the families and 1–2 flagships each; look up the rest.
Picking a service by name similarity across clouds.Names mislead (Azure Functions vs Cloud Run functions vs Lambda are close; Cosmos DB ≠ DynamoDB exactly).Compare features, limits and pricing, not names.
Using a database where a queue was needed (polling tables).Familiar tools.Use queues/topics for work hand-off and events.
Studying from old practice tests.Retired or renamed products.Check the lifecycle table and providers’ “what’s new”.
No tags.“We’ll add them later.”Tag every resource with project/owner/env from day one; enforce with policy.
Self-managing what a managed service does.Habit or fear of lock-in.Prefer managed unless a clear need (control, cost at scale, portability) says otherwise.
