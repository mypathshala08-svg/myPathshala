1 The story

The disk is full — again

Before you start: 6.1 Compute (step 3 reuses its VM) and 4.3 Storage virtualization.

🤔 TiffinGo stores order records, a shared “recipes” folder, 3 TB of food photos, seven-year-old GST invoices and nightly backups. Can one kind of cloud storage do all of that well?

No — clouds sell storage in different shapes: block disks for servers, shared file systems, object storage for unlimited files over HTTPS, cheap archive tiers, fast but temporary local disks, snapshots and backups, and services to move data in from offices and data centres. Each has a different speed, durability and price — Mumbai prices go from $0.025 to $0.0045 per GB-month for the same photo. This lesson explains every shape, shows what happens inside S3 when you upload a file, and walks you through buckets, lifecycle rules, disks, snapshots and share links on your own AWS, Azure or Google Cloud account.

2 Definition

Storage systems in the cloud

Formal definition (write this in exams)

Cloud storage services provide persistent, network-accessible capacity in several forms — block volumes attached to servers, shared file systems, and object storage accessed by API — with tiers that trade price for access speed, built-in redundancy across devices, zones or Regions, and pay-per-use billing by capacity, requests, retrieval and data transfer.

In simple words

Places in the cloud to keep data: disks for servers, shared folders, and an unlimited file store over the internet — each with cheaper “cold” options for old data.

Say it in an interview

30-second answer you can speak:

  • “Block storage like EBS is a network disk for one instance; file storage like EFS or Azure Files is a shared NFS/SMB file system; object storage like S3 stores objects in buckets over HTTPS with 11-nines durability.”
  • “I pick by access pattern, then use storage classes and lifecycle rules for cost, and snapshots/backups with immutability for protection.”

Type 1 · Block storage (cloud disks)

Definition (say it in an interview): Block storage provides raw storage volumes, divided into fixed-size blocks, that are attached to a server over the provider’s network and appear to the operating system as a local disk, which it formats with a file system. Volumes persist independently of the server, are replicated within one Availability Zone, and are sized and priced by capacity and performance (IOPS, throughput).

In plain words (no jargon): A hard disk in the cloud. You attach it to one server; the server uses it like its own disk. If the server is deleted, the disk can survive.

Analogy: A pen drive that only one laptop can use at a time — but stored in a safe locker room next door and copied automatically so it does not die.

How it works internally, step by step

  1. Create. Pick the AZ, size and type; the volume is replicated across devices inside that AZ.
  2. Attach. The hypervisor (Nitro card on AWS) presents it as an NVMe device to the VM.
  3. Use. The OS formats it (ext4, xfs, NTFS) and reads/writes blocks over the network.
  4. Performance. gp3: 3,000 IOPS and 125 MB/s baseline, raised independently of size; io2 for very high IOPS.
  5. Protect. Snapshots copy changed blocks incrementally to regional storage (type 6).

Words used above, in simple terms: block = a small fixed-size piece of a disk · IOPS = input/output operations per second — how many small reads/writes · throughput = MB per second for big reads/writes · mount = connect a disk to a folder in the OS

Real-world example

Amazon EBS launched in 2008; its gp3 type (2020) separated performance from size — before that, gp2 IOPS grew only with disk size, so people bought huge disks just for speed.

Real scenario (TiffinGo)

TiffinGo’s PostgreSQL server keeps its data on a 100 GiB gp3 EBS volume (3,000 IOPS baseline). Before Diwali they raise IOPS to 6,000 without downtime, and a daily snapshot goes to S3-backed storage.

Products and cloud services

Amazon EBS (gp3, io2, st1, sc1), Azure Managed Disks (Standard HDD/SSD, Premium SSD v2, Ultra), Google Persistent Disk and Hyperdisk.

For the experienced — did you know? An EBS volume lives in one AZ — you cannot attach a 1a volume to a 1b instance. To move it, snapshot (regional) and create a new volume in the other AZ. Azure ZRS disks and Google regional persistent disks are exceptions that replicate synchronously across two or three zones.

Use it when: a single server needs a fast, persistent disk — OS disks, databases, anything that expects a hard drive.
Avoid / be careful when: many servers must share the same files (use file storage) or you want to serve files to the internet (use object storage).

Type 2 · File storage (managed network file systems)

Definition (say it in an interview): Cloud file storage is a managed, shared file system accessed over network file protocols — NFS (Linux) or SMB (Windows) — that many servers can mount at the same time, with a familiar hierarchy of folders, file permissions and locking.

In plain words (no jargon): A shared network folder in the cloud. Many servers can open the same files at the same time, just like a shared drive in an office.

Analogy: The shared “Recipes” almirah in the office kitchen: every cook can open the same files, and the almirah grows if you add more.

How it works internally, step by step

  1. Create. A file system in a Region (or one AZ for cheaper options).
  2. Mount targets. Network endpoints in your subnets, protected by security groups.
  3. Mount. mount -t nfs4 … on Linux or map a drive letter (SMB) on Windows.
  4. Consistency. Locks and close-to-open consistency let many clients work safely.
  5. Billing. Per GB-month stored (EFS) or per provisioned capacity (Filestore, FSx, Azure Files premium).

Words used above, in simple terms: NFS = Network File System — Linux file sharing protocol · SMB = Server Message Block — Windows file sharing protocol · mount target = the network address servers use to reach the file system · Lustre = a very fast file system for HPC

Use it when: several servers or containers need the same files, or a lift-and-shift app expects a shared drive or home directories.
Avoid / be careful when: only one server uses the data (block is cheaper and faster) or files are served to users on the internet (object is far cheaper).

Type 3 · Object storage

Definition (say it in an interview): Object storage stores data as objects — the bytes, a unique key and metadata — in flat containers called buckets (S3, Cloud Storage) or containers in a storage account (Azure Blob), accessed through an HTTPS API, scaling to virtually unlimited capacity with very high durability and the lowest price per GB.

In plain words (no jargon): A giant online store for files of any size. Each file gets a name (key); programs save and fetch files over the internet; you never run out of space.

Analogy: A cloak room with token numbers: you hand over a bag, get a token (key), and later get the same bag back by showing the token — you never walk into the room or rearrange shelves.

How it works internally, step by step

  1. Bucket. Create it in a Region with a globally unique name.
  2. PUT. Upload an object with a key; metadata and encryption are applied (see “How it works”).
  3. Durable copies. S3 Standard spreads data over ≥3 AZs; Azure LRS keeps 3 copies in one datacentre, ZRS across zones, GRS also in the paired Region.
  4. GET / LIST. Read by key; list by prefix; byte-range reads for big files.
  5. Manage. Versioning, lifecycle rules, replication, access policies, event notifications.

Words used above, in simple terms: object = a file plus its name and labels · bucket = a top-level container for objects · key = the object’s full name, e.g. photos/2026/thali.jpg · durability = the chance your data is NOT lost — different from availability · ETag = a fingerprint of the object that S3 returns after an upload · erasure coding = splitting data into pieces plus spare pieces so lost ones can be rebuilt

Amazon S3 launched on 14 March 2006 as AWS’s first generally available service; it is designed for 99.999999999% durability — if you store 10 million objects, you can expect to lose one about every 10,000 years.

Real scenario (TiffinGo)

TiffinGo keeps 3 TB of food photos in an S3 bucket in Mumbai (≈ $77 a month at $0.025/GB). The mobile app uploads directly to S3 with short-lived signed URLs, and CloudFront serves the photos to customers.

Products and cloud services

Amazon S3, Azure Blob Storage (in a storage account), Google Cloud Storage; S3-compatible stores such as MinIO on-premises.

For the experienced — did you know? S3 became strongly consistent for all operations in December 2020 — before that, overwrites and deletes were only eventually consistent, and big data tools needed add-ons (like EMRFS consistent view) to avoid reading stale files.

Use it when: media, documents, logs, backups, data lakes, static websites — anything written once and read many times.
Avoid / be careful when: you need to edit parts of a file in place or run a database on it (use block), or need a POSIX file system (use file).

Type 4 · Cold and archive storage tiers

Definition (say it in an interview): Archive and cold storage classes keep rarely accessed data at a much lower price per GB in exchange for higher retrieval cost, slower access (from milliseconds to hours) and a minimum storage duration; lifecycle policies move objects between classes automatically by age.

In plain words (no jargon): Cheaper shelves for data you almost never open. Storing is very cheap, but getting the data back is slower and costs a little.

Analogy: Old school certificates: last year’s marksheet stays in the drawer, the Class 10 one goes to a trunk in the loft — cheap to keep, but you need a ladder and time to get it.

How it works internally, step by step

  1. Classes. Each class has a storage price, retrieval price, access time and minimum duration.
  2. Lifecycle rule. E.g. “after 30 days → IA, after 365 days → Deep Archive, delete after 8 years”.
  3. Transition. The service moves objects in the background; the key stays the same.
  4. Restore. Archive objects need a restore request (expedited/standard/bulk) before GET.
  5. Auto-tiering. S3 Intelligent-Tiering moves objects by observed access, for a small monitoring fee.

Words used above, in simple terms: lifecycle rule = automatic “move or delete after N days” instruction · retrieval fee = charge per GB read from a cold class · minimum duration = you pay for at least this many days even if you delete earlier · rehydrate / restore = bring archived data back to a readable tier

Use it when: data is kept for compliance, backup or history and read rarely — logs, old invoices, raw video, old backups.
Avoid / be careful when: data is read often or deleted soon — retrieval fees and minimum durations can make “cheap” tiers more expensive.

Type 5 · Local (ephemeral) instance storage

Definition (say it in an interview): Ephemeral (instance) storage is disk physically attached to the host that runs a VM — instance store on AWS, the temporary disk on Azure, Local SSD on Google Cloud — offering very high performance at no or low extra cost, but whose data is lost when the instance stops, is terminated, or the host fails.

In plain words (no jargon): A very fast disk inside the same machine as your server. Great for temporary work; everything on it disappears if the server stops.

Analogy: A whiteboard in the meeting room: fastest to write on, perfect during the meeting — and wiped clean when the next team comes in.

How it works internally, step by step

  1. Included. Comes with certain instance types (a “d” in the name, e.g. m7gd, or i-family).
  2. Attached locally. NVMe directly on the host — no network hop.
  3. Use. Format and mount like any disk (some AMIs do it automatically).
  4. Survives reboot. A reboot keeps data; stop/hibernate/terminate or host failure erases it.
  5. Protect by design. Replicate across nodes or keep the source of truth in S3/EBS.

Words used above, in simple terms: ephemeral = temporary — lasts only as long as the instance · NVMe = a very fast interface for SSDs · scratch space = a place for temporary working files · shuffle = data exchanged between nodes in Spark/Hadoop jobs

Use it when: data is temporary or can be rebuilt — caches, buffers, scratch space, replicated databases (Cassandra, Kafka with replicas).
Avoid / be careful when: you need the data after a stop or failure — use block storage or replicate it elsewhere.

Type 6 · Snapshots and backup

Definition (say it in an interview): A snapshot is a point-in-time, usually incremental copy of a volume or file system stored in durable regional storage; backup services automate snapshots and other copies with schedules, retention, encryption, cross-Region/account copies and restore testing, often across many services (VMs, disks, databases, file systems).

In plain words (no jargon): Automatic “save points” of your disks and databases. If something breaks or is deleted, you go back to yesterday’s save point.

Analogy: Taking a photo of your whiteboard every evening: tomorrow you only need to note what changed, but any photo shows the whole board as it was.

How it works internally, step by step

  1. Point in time. The snapshot captures the volume at one moment (crash-consistent; app-consistent with agents).
  2. Incremental. Only blocks changed since the previous snapshot are stored.
  3. Regional storage. Snapshots are stored outside the AZ, so they survive an AZ failure.
  4. Restore. Create a new volume (in any AZ of the Region) or copy to another Region.
  5. Policies. Schedules, retention, immutability (vault lock) and restore tests.

Words used above, in simple terms: snapshot = a point-in-time copy of a disk · incremental = copying only what changed · retention = how long backups are kept · immutable = cannot be changed or deleted, even by an admin, until the period ends

Products and cloud services

For the experienced — did you know? Deleting an old snapshot rarely frees what you expect: because snapshots are incremental, blocks still referenced by later snapshots are kept. Only blocks unique to the deleted snapshot are removed — so cost drops less than its “size” suggests.

Use it when: any data you cannot afford to lose — databases, VM disks, file systems — with retention matching business and legal needs.
Avoid / be careful when: you treat replication as backup: replication copies mistakes and deletions too; backups let you go back in time.

Type 7 · Hybrid storage and data transfer

Definition (say it in an interview): Hybrid storage services connect on-premises systems to cloud storage — for example a storage gateway that exposes a local file, volume or tape interface while keeping data in the cloud — and data transfer services move large datasets into the cloud online (agents, managed transfer) or offline using physical storage devices.

In plain words (no jargon): Tools that link your office’s storage to the cloud, and that move huge amounts of data into the cloud — over the internet or on shipped disks.

Analogy: A neighbourhood courier counter: you hand parcels over locally as always, and the courier quietly moves them to the big warehouse in the city.

How it works internally, step by step

  1. Gateway. A VM or appliance on-premises presents NFS/SMB/iSCSI/tape.
  2. Cache. Recently used data stays local for speed.
  3. Cloud backend. All data is stored as objects in S3 / Blob / Cloud Storage.
  4. Online transfer. Agents copy, verify and schedule transfers with bandwidth limits.
  5. Offline transfer. Ruggedised devices or drop-off locations for when “network time > shipping time”.

Words used above, in simple terms: gateway = a bridge between an on-prem protocol and a cloud service · iSCSI = block storage over a network · SFTP = secure file transfer protocol · offline transfer = moving data on physical devices

6 Explained part by part

Six properties to compare in any storage service

Durability

What it is: Probability that stored data is not lost over a year.

Why it exists: Decides whether you need extra copies.

Where it is used: S3/Blob/GCS designed for 11 nines; EBS io2 99.999%, gp3 99.8–99.9%.

Availability

What it is: Probability you can read/write right now.

Why it exists: An SLA number, different from durability (Lesson 5.4).

Where it is used: S3 Standard 99.9% SLA, One Zone-IA lower.

Redundancy option

What it is: How many copies, where.

Why it exists: Trade price against surviving an AZ or Region loss.

Where it is used: Azure LRS/ZRS/GRS/GZRS; GCS region/dual/multi-region; S3 Standard vs One Zone.

Performance

What it is: IOPS, throughput, latency.

Why it exists: Databases need IOPS; analytics needs throughput.

Where it is used: gp3/io2, Premium SSD v2/Ultra, Hyperdisk.

Encryption

What it is: Data encrypted at rest and in transit.

Why it exists: On by default for new data in S3, Blob and GCS.

Where it is used: SSE-S3/SSE-KMS, Azure SSE with platform or customer keys, CMEK.

Access control

What it is: Who can read/write.

Why it exists: Most data leaks are misconfigured buckets.

Where it is used: IAM + bucket policies, Block Public Access; Azure RBAC + SAS; GCS IAM + uniform access.

Myth vs reality: things many websites still say

  • Myth: Eleven nines means it is always available.
    Reality: Durability ≠ availability (99.9% SLA).
    Proof: Deep dive.
  • Myth: Replication is a backup.
    Reality: It replicates deletions too.
    Proof: Type 6.
  • Myth: Folders exist in S3.
    Reality: Only key prefixes.
    Proof: How it works, step 3.
7 Deep dive

Durability vs availability, Azure redundancy, erasure coding, request costs

Durability vs availability, with numbers

S3 Standard is designed for 99.999999999% durability (lose about 1 of 10 million objects every 10,000 years) but its SLA is 99.9% availability (Lesson 5.4). A short outage makes data unreachable, not lost. Block volumes are different: an EBS gp3 volume has an annual failure rate of 0.1–0.2% — that is why databases need snapshots.

Azure redundancy options in one table

OptionCopiesSurvives
LRS3 in one datacentredisk/server failure
ZRS3 across availability zonesa zone outage
GRSLRS + 3 in the paired Regiona Region disaster (failover needed)
GZRSZRS + 3 in the paired Regionzone and Region failures

Erasure coding: how 11 nines are possible

Instead of keeping three full copies, object stores split data into k data pieces plus m parity pieces (like RAID across many machines and AZs). Any k pieces rebuild the object, so several devices — or a whole AZ — can fail at once. Background processes constantly check checksums and repair lost pieces.

Request costs: the other half of the storage bill

Object storage charges per request too (PUT/LIST cost more than GET). A design that writes millions of tiny files can pay more for requests than for storage — batch small records into bigger files (e.g. Parquet) for analytics.

  2. 1 · Create a private bucket and upload a file

    Pick your cloud.

    UI way — AWS Management Console

    1. S3 → Create bucket → Region Asia Pacific (Mumbai); name tiffingo-photos-<yourname> (globally unique).
    2. Keep Block all public access ON, encryption default (SSE-S3) → Create bucket.
    3. Open the bucket → Upload → Add files → pick any small file (e.g. menu.txt) → Upload. Click the object and note its Object URL — opening it gives AccessDenied (private).

    CLI way — the same thing with commands

    B=tiffingo-photos-$RANDOM$RANDOM
aws s3 mb s3://$B --region ap-south-1
echo "Diwali thali — ₹249" > menu.txt
aws s3 cp menu.txt s3://$B/menu/menu.txt
aws s3 ls s3://$B --recursive --human-readable
aws s3api get-public-access-block --bucket $B

    You should see: make_bucket: …, upload: ./menu.txt to s3://…/menu/menu.txt, the object listed with its size, and all four public-access blocks true.

    UI way — Azure portal

    1. Storage accounts → Create → resource group rg-tiffingo, name tiffingo<yourname> (3–24 lowercase letters/digits), Region Central India, redundancy LRS → Review + create → Create.
    2. Open it → Data storage → Containers → + Container photos, access level Private.
    3. Open photos → Upload → choose a file → Upload.

    CLI way — the same thing with commands

    SA=tiffingo$RANDOM
az group create --name rg-tiffingo --location centralindia
az storage account create --name $SA --resource-group rg-tiffingo --location centralindia \
  --sku Standard_LRS --kind StorageV2 --allow-blob-public-access false
az storage container create --account-name $SA --name photos --auth-mode key
echo "Diwali thali — ₹249" > menu.txt
az storage blob upload --account-name $SA --container-name photos --name menu/menu.txt --file menu.txt --auth-mode key
az storage blob list --account-name $SA --container-name photos --auth-mode key --output table

    You should see: "provisioningState": "Succeeded", {"created": true} and a table row for menu/menu.txt in tier Hot.

    UI way — Google Cloud console

    1. Cloud Storage → Buckets → Create → name tiffingo-photos-<yourname>; location type Region → asia-south1 (Mumbai); class Standard.
    2. Access control: keep Enforce public access prevention ticked, Uniform access → Create.
    3. Upload files → pick a small file.

    CLI way — the same thing with commands

    B=tiffingo-photos-$RANDOM$RANDOM
gcloud storage buckets create gs://$B --location=asia-south1 --uniform-bucket-level-access --public-access-prevention
echo "Diwali thali — ₹249" > menu.txt

gcloud storage ls --long gs://$B/**

    You should see: Creating gs://…/, Copying file://menu.txt and the object listed with size and date.

    Bucket names are global (one namespace for everyone); the data still lives only in the Region you chose.

  3. 2 · Turn on versioning and a lifecycle rule

    Pick your cloud.

    UI way — AWS Management Console

    1. Bucket → Properties → Bucket Versioning → Edit → Enable → Save changes.
    2. Upload menu.txt again with different text → Objects → toggle Show versions: two versions.
    3. Management → Create lifecycle rule → name cool-then-archive, apply to all objects → transition current versions to Standard-IA after 30 days and Glacier Deep Archive after 365; expire noncurrent versions after 90 days → Create rule.

    CLI way — the same thing with commands

    aws s3api put-bucket-versioning --bucket $B --versioning-configuration Status=Enabled
echo "Diwali thali — ₹229 (offer)" > menu.txt && aws s3 cp menu.txt s3://$B/menu/menu.txt
aws s3api list-object-versions --bucket $B --prefix menu/ --query 'Versions[].[VersionId,IsLatest,Size]' --output table
aws s3api put-bucket-lifecycle-configuration --bucket $B --lifecycle-configuration '{"Rules":[{"ID":"cool-then-archive","Status":"Enabled","Filter":{"Prefix":""},"Transitions":[{"Days":30,"StorageClass":"STANDARD_IA"},{"Days":365,"StorageClass":"DEEP_ARCHIVE"}],"NoncurrentVersionExpiration":{"NoncurrentDays":90}}]}'
aws s3api get-bucket-lifecycle-configuration --bucket $B

    You should see: two versions (one IsLatest True) and the lifecycle rule echoed back.

    UI way — Azure portal

    1. Storage account → Data management → Data protection → tick Enable versioning for blobs → Save.
    2. Upload menu.txt again (overwrite) → open the blob → Versions tab shows the old one.
    3. Data management → Lifecycle management → Add a rule → name cool-then-archive → base blobs: modified more than 30 days ago → Move to cool storage; add 365 days → Move to archive storage → Add.

    CLI way — the same thing with commands

    az storage account blob-service-properties update --account-name $SA --resource-group rg-tiffingo --enable-versioning true
echo "Diwali thali — ₹229 (offer)" > menu.txt
az storage blob upload --account-name $SA --container-name photos --name menu/menu.txt --file menu.txt --overwrite --auth-mode key
az storage blob list --account-name $SA --container-name photos --include v --auth-mode key --query "[].{name:name, version:versionId, current:isCurrentVersion}" --output table
az storage account management-policy create --account-name $SA --resource-group rg-tiffingo --policy '{"rules":[{"enabled":true,"name":"cool-then-archive","type":"Lifecycle","definition":{"actions":{"baseBlob":{"tierToCool":{"daysAfterModificationGreaterThan":30},"tierToArchive":{"daysAfterModificationGreaterThan":365}}},"filters":{"blobTypes":["blockBlob"]}}}]}'

    You should see: two rows for menu/menu.txt (one current) and the policy JSON returned.

    UI way — Google Cloud console

    1. Bucket → Protection tab → Object versioning → Off → turn On.
    2. Upload menu.txt again → Objects → Show → Live and noncurrent objects.
    3. Lifecycle tab → Add a rule → Set storage class to Nearline → age 30 days → Create; add another: Archive at 365 days.

    CLI way — the same thing with commands

    gcloud storage buckets update gs://$B --versioning
echo "Diwali thali — ₹229 (offer)" > menu.txt && gcloud storage cp menu.txt gs://$B/menu/menu.txt
gcloud storage ls --all-versions gs://$B/menu/
cat > lc.json <<'EOF'
{"rule":[{"action":{"type":"SetStorageClass","storageClass":"NEARLINE"},"condition":{"age":30}},{"action":{"type":"SetStorageClass","storageClass":"ARCHIVE"},"condition":{"age":365}}]}
EOF
gcloud storage buckets update gs://$B --lifecycle-file=lc.json
gcloud storage buckets describe gs://$B --format="default(lifecycle_config)"

    You should see: two lines ending in #<generation> (two versions) and the two lifecycle rules.

    Versioning protects against accidental overwrite and delete; lifecycle rules keep the bill falling as data ages — both are one-time settings.

  4. 3 · Add a block disk to a VM and snapshot it

    Pick your cloud.

    UI way — AWS Management Console

    1. Use the VM from Lesson 6.1 (or launch one). Note its AZ under Networking.
    2. EC2 → Volumes → Create volume → gp3, 4 GiB, same AZ → Create volume.
    3. Select it → Actions → Attach volume → pick the instance → Attach. Connect and run lsblk, then sudo mkfs -t xfs /dev/nvme1n1 && sudo mkdir /data && sudo mount /dev/nvme1n1 /data.
    4. Select the volume → Actions → Create snapshot → Create snapshot.

    CLI way — the same thing with commands

    AZ=$(aws ec2 describe-instances --instance-ids $ID --query 'Reservations[0].Instances[0].Placement.AvailabilityZone' --output text)
VOL=$(aws ec2 create-volume --availability-zone $AZ --size 4 --volume-type gp3 --query VolumeId --output text)
aws ec2 wait volume-available --volume-ids $VOL
aws ec2 attach-volume --volume-id $VOL --instance-id $ID --device /dev/sdf
SNAP=$(aws ec2 create-snapshot --volume-id $VOL --description "tiffingo lab" --query SnapshotId --output text)
aws ec2 describe-snapshots --snapshot-ids $SNAP --query 'Snapshots[0].[State,VolumeSize,Progress]' --output text

    You should see: lsblk shows a 4G nvme1n1; the snapshot goes from pending to completed 100%.

    UI way — Azure portal

    1. Open the VM from Lesson 6.1 → Settings → Disks → Create and attach a new disk → 4 GiB Standard SSD → Apply.
    2. Connect and run lsblk (the new disk is usually sdc), then format and mount it.
    3. Disks → open the data disk → Create snapshot → name data1-snap → Review + create → Create.

    CLI way — the same thing with commands

    az vm disk attach --resource-group rg-tiffingo --vm-name tiffingo-vm --name data1 --new --size-gb 4 --sku StandardSSD_LRS
az vm run-command invoke --resource-group rg-tiffingo --name tiffingo-vm --command-id RunShellScript --scripts "lsblk"
az snapshot create --resource-group rg-tiffingo --name data1-snap --source data1
az snapshot show --resource-group rg-tiffingo --name data1-snap --query "[provisioningState,diskSizeGB]" --output tsv

    You should see: a 4G disk in lsblk; snapshot Succeeded 4.

    UI way — Google Cloud console

    1. Compute Engine → Disks → Create disk → name data1, zone asia-south1-a (same as the VM), 10 GB balanced → Create.
    2. Open the VM → Edit → Additional disks → Attach existing disk → data1 → Save. SSH and run lsblk.
    3. Snapshots → Create snapshot → source disk data1 → Create.

    CLI way — the same thing with commands

    gcloud compute disks create data1 --size=10GB --type=pd-balanced --zone=asia-south1-a
gcloud compute instances attach-disk tiffingo-vm --disk=data1 --zone=asia-south1-a
gcloud compute ssh tiffingo-vm --zone=asia-south1-a --command="lsblk"
gcloud compute snapshots create data1-snap --source-disk=data1 --source-disk-zone=asia-south1-a
gcloud compute snapshots list

    You should see: a 10G sdb in lsblk; snapshot data1-snap with STATUS READY.

    The disk must be in the same zone as the VM; the snapshot is regional — that is how you move a disk to another zone.

  5. 4 · Share a private file for one hour

    Pick your cloud.

    UI way — AWS Management Console

    1. Open the object → Object actions → Share with a presigned URL → 60 minutes → Create presigned URL → copy and open it in a private browser window.

    CLI way — the same thing with commands

    aws s3 presign s3://$B/menu/menu.txt --expires-in 3600
# open the printed URL in a browser; after 1 hour it returns AccessDenied

    You should see: a long URL with X-Amz-Expires=3600 and X-Amz-Signature=… that shows the file without making the bucket public.

    UI way — Azure portal

    1. Open the blob → Generate SAS → permissions Read, expiry 1 hour from now → Generate SAS token and URL → copy Blob SAS URL.

    CLI way — the same thing with commands

    END=$(date -u -d "+1 hour" +%Y-%m-%dT%H:%MZ)
az storage blob generate-sas --account-name $SA --container-name photos --name menu/menu.txt \
  --permissions r --expiry $END --https-only --full-uri --auth-mode key --output tsv

    You should see: a URL ending in ?se=…&sp=r&sig=… — a shared access signature valid for one hour.

    UI way — Google Cloud console

    1. Signed URLs need a service account in Google Cloud: IAM & Admin → Service accounts → Create service account url-signer.
    2. On the bucket → Permissions → Grant access → principal url-signer → role Storage Object Viewer.
    3. Give yourself Service Account Token Creator on url-signer, then run the CLI command (the console has no button for signed URLs).

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
gcloud iam service-accounts create url-signer
gcloud storage buckets add-iam-policy-binding gs://$B --member=serviceAccount:url-signer@$P.iam.gserviceaccount.com --role=roles/storage.objectViewer
gcloud iam service-accounts add-iam-policy-binding url-signer@$P.iam.gserviceaccount.com \
  --member=user:$(gcloud config get-value account) --role=roles/iam.serviceAccountTokenCreator
gcloud storage sign-url gs://$B/menu/menu.txt --duration=1h --impersonate-service-account=url-signer@$P.iam.gserviceaccount.com

    You should see: a table with a signed_url containing X-Goog-Signature. If you get a permission error, wait a minute for IAM to update and retry.

    Never make a bucket public to share one file: a signed URL / SAS gives one file, read-only, for a limited time.

Clean up and cost check

AWS: empty and delete the bucket (versioned objects too); detach and delete the volume; delete the snapshot. CLI: aws s3 rm s3://$B --recursive; aws s3api delete-objects --bucket $B --delete "$(aws s3api list-object-versions --bucket $B --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}')"; aws s3 rb s3://$B; aws ec2 detach-volume --volume-id $VOL; aws ec2 wait volume-available --volume-ids $VOL; aws ec2 delete-volume --volume-id $VOL; aws ec2 delete-snapshot --snapshot-id $SNAP.
Azure: Resource groups → rg-tiffingo → Delete resource group (storage account, disk, snapshot and VM together). CLI: az group delete --name rg-tiffingo --yes --no-wait.
Google Cloud: gcloud storage rm --recursive --all-versions gs://$B; gcloud storage buckets delete gs://$B; gcloud compute instances detach-disk tiffingo-vm --disk=data1 --zone=asia-south1-a; gcloud compute disks delete data1 --zone=asia-south1-a --quiet; gcloud compute snapshots delete data1-snap --quiet; gcloud iam service-accounts delete url-signer@$P.iam.gserviceaccount.com --quiet.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Making a bucket public to share a few files.Quickest way to “make it work”.Keep Block Public Access on; use signed URLs / SAS or CloudFront with origin access control.
Thinking replication or RAID is a backup.Copies feel safe.Replication copies deletions too; keep versioned, immutable, point-in-time backups.
Storing the only copy on instance store / temp disk.It looks like a normal disk.Ephemeral = lost on stop; keep data on block/object storage.

Disk in a different zone than the VM.Zones not checked.Create disks in the VM’s AZ; move via snapshot.
