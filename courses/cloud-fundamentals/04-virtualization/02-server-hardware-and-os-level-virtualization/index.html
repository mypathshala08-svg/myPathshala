2 Definition

Server, hardware and OS-level virtualization

Formal definition (write this in exams)

Server virtualization partitions a physical server into multiple isolated virtual servers. It can be implemented by hardware-level partitioning (firmware divides physical resources), hypervisor-based virtualization (each virtual machine runs its own guest OS on virtual hardware), or OS-level virtualization (the operating system kernel provides multiple isolated user-space instances — containers — using mechanisms such as Linux namespaces and cgroups). Hardware virtualization also denotes processor and device features (VT-x/AMD-V, SR-IOV) that support it.

In simple words

You can split a server with the hardware, with a hypervisor (VMs, each with its own OS), or inside the operating system itself (containers that share one kernel).

Say it in an interview

30-second answer you can speak:

  • “Server virtualization splits one physical server into isolated virtual servers. It can be done at the hardware level with partitions like IBM LPARs, with a hypervisor that runs full VMs, or at the OS level with containers.”
  • “OS-level virtualization uses Linux namespaces for isolation and cgroups for resource limits; containers share the host kernel, so they are megabytes in size and start in milliseconds.”
  • “For example, I ran Alpine Linux inside an Ubuntu host with unshare and chroot: the OS files were Alpine but the kernel version was the host’s.”

Type 1 · Hardware-level partitioning (LPAR)

Definition (say it in an interview): Hardware partitioning divides one large physical server’s processors, memory and I/O adapters into separate logical partitions (LPARs), each running its own operating system, with the boundaries enforced by the machine’s firmware rather than by a software hypervisor on top of an OS.

In plain words (no jargon): A very big, very expensive computer is cut into a few fixed sections using controls built into the machine itself. Each section then behaves like a completely separate computer with its own operating system.

Analogy: A big bungalow divided into flats with brick walls and separate electricity meters. Very private and predictable — but moving a wall needs planning, unlike curtains you can slide.

How it works internally, step by step

  1. One large machine. Mainframes and big Power servers have many processors, terabytes of memory and many I/O adapters.
  2. Firmware hypervisor is built in. The partition manager (PR/SM on IBM Z, PowerVM on Power) is part of the machine’s firmware — it is always there, below every OS.
  3. Admin defines partitions. On the Hardware Management Console (HMC) the admin assigns each LPAR dedicated or shared processors, an amount of memory and I/O adapters.
  4. Boundaries enforced by hardware/firmware. An LPAR cannot address memory or devices outside its assignment.
  5. Each LPAR boots its own OS. z/OS, AIX, IBM i or Linux; I/O can be dedicated, or shared through a Virtual I/O Server (VIOS) partition.
  6. Adjust carefully. Dynamic LPAR lets admins move processors and memory between running partitions within limits.

Words used above, in simple terms: firmware = software built into the hardware · LPAR = logical partition · mainframe = very large, highly reliable server used by banks and airlines · HMC = the admin console for IBM Power partitions · VIOS = a special partition that shares disks and network cards among other LPARs

For the experienced — did you know? On IBM Z the hypervisor z/VM itself runs inside an LPAR, so Linux guests there are virtualized twice — by design. IBM’s CP-67 and VM/370 (1960s–70s) are where the term “virtual machine” comes from.

Use it when: you run a very large, mission-critical server (banking, airline reservations, telecom billing) and need strict, predictable isolation.
Avoid / be careful when: you need hundreds of small, short-lived servers — VMs or containers are far more flexible and cheaper.

Type 2 · Full virtualization (binary translation)

Definition (say it in an interview): Full virtualization presents a complete simulation of the hardware so that an unmodified guest operating system runs exactly as on a real machine. On x86 before CPU support existed, the hypervisor achieved this by binary translation: rewriting the guest kernel’s sensitive instructions on the fly.

In plain words (no jargon): The operating system inside the VM is not changed at all and does not know it is in a VM. The hypervisor quietly watches the OS’s most powerful instructions and swaps the dangerous ones for safe versions just before they run.

Analogy: A live interpreter at a meeting: the speaker talks normally and never changes a word, while the interpreter quietly rephrases the few sentences that would cause trouble.

How it works internally, step by step

  1. Deprivilege the guest. The hypervisor runs the guest kernel in ring 1 instead of ring 0, so it cannot directly control the CPU.
  2. Run user code directly. Applications inside the VM (ring 3) run straight on the CPU.
  3. Translate kernel code. Before a block of guest kernel code runs, the translator scans it.
  4. Replace sensitive instructions. Instructions such as POPF that silently behave differently outside ring 0 are replaced with jumps into the hypervisor.
  5. Cache the result. Translated blocks are cached so the cost is paid once.
  6. Emulate devices. Disks and network cards are emulated in software (e.g. an old Intel e1000 NIC) so the guest’s standard drivers work.

Words used above, in simple terms: ring 0 / ring 3 = CPU privilege levels: 0 = most powerful (kernel), 3 = least (apps) · binary translation = rewriting machine code while the program runs · POPF = an x86 instruction that changes CPU flags · emulated device = a fake hardware device made by software

For the experienced — did you know? Classic x86 had about 17 “sensitive but unprivileged” instructions that broke the Popek–Goldberg virtualization rules — they did not trap, they just behaved differently. Binary translation existed purely to catch those 17.

Use it when: you must run an unmodified OS where hardware support is missing, or emulate a different CPU type.
Avoid / be careful when: performance matters — on modern CPUs hardware-assisted virtualization is faster and simpler.

Type 3 · Paravirtualization

Definition (say it in an interview): Paravirtualization is a technique in which the guest operating system is modified to know that it runs on a hypervisor, replacing privileged operations with explicit calls to the hypervisor (hypercalls) and using paravirtual device drivers, which reduces trapping and emulation overhead.

In plain words (no jargon): The operating system inside the VM is told the truth — “you are a virtual machine” — and is changed slightly so that, instead of touching hardware, it simply asks the hypervisor to do it.

Analogy: A hotel guest who phones reception for room service instead of walking into the kitchen: the guest knows the rules and asks politely, so nobody has to stop and catch him.

How it works internally, step by step

  1. Modify the guest. The guest kernel source (or just its drivers) is changed to be hypervisor-aware.
  2. Hypercalls replace privileged instructions. For page-table updates, timers or interrupts the kernel calls the hypervisor directly — like a system call one level down.
  3. Batch work. Many updates can be sent in one hypercall, cutting the number of expensive switches.
  4. Split drivers. A frontend driver in the guest places requests in a shared-memory ring; a backend driver in the hypervisor or a driver domain (Xen Dom0) performs the real I/O.
  5. Notify, do not trap. Event channels/doorbells tell the other side there is work, instead of trapping on every register access.
  6. Hybrid today. Modern VMs use hardware-assisted CPU virtualization plus paravirtual drivers (called PVHVM in Xen).

Words used above, in simple terms: hypercall = a request from the guest kernel to the hypervisor · Dom0 / driver domain = a privileged VM in Xen that owns the real devices · shared ring = a circular queue in memory both sides read and write · virtio = the standard paravirtual driver family for KVM

Use it when: I/O performance matters — paravirtual drivers are standard in every modern VM even when the CPU part is hardware-assisted.
Avoid / be careful when: you cannot modify or add drivers to the guest OS (closed, very old systems).

Type 4 · Hardware-assisted virtualization

Definition (say it in an interview): Hardware-assisted virtualization uses processor extensions — Intel VT-x and AMD-V — that add a separate privilege mode for the hypervisor, so unmodified guest kernels run in their normal ring 0 while sensitive operations automatically cause a VM exit to the hypervisor; companion features (EPT/NPT for memory, VT-d/AMD-Vi IOMMU for devices) reduce overhead further.

In plain words (no jargon): Modern processors were given a special “manager mode” for the hypervisor. The operating system in the VM runs normally, and whenever it tries something dangerous, the processor itself pauses it and hands control to the hypervisor.

Analogy: A building with automatic sensor doors: no guard has to watch every door. When someone tries to enter a restricted room, the door itself alerts security, who decides and lets the person continue.

How it works internally, step by step

  1. Enable VMX. The hypervisor executes VMXON (Intel) and enters VMX root mode — the new top privilege level.
  2. Create a VMCS per vCPU. A Virtual Machine Control Structure stores the guest’s registers, the host’s registers and which events must cause exits.
  3. Enter the guest. VMLAUNCH/VMRESUME switches the CPU into non-root mode; the guest kernel runs in its real ring 0.
  4. Run directly. Almost all guest instructions run natively at full speed.
  5. VM exit. On configured events (I/O ports, some registers, HLT, EPT violation) the CPU saves guest state to the VMCS and jumps to the hypervisor.
  6. Handle and resume. The hypervisor emulates or completes the operation and executes VMRESUME. EPT/NPT avoid exits for page-table changes; the IOMMU lets devices be given safely to VMs.

Words used above, in simple terms: VT-x / AMD-V = virtualization features in Intel / AMD CPUs · VMX root / non-root = hypervisor mode / guest mode · VMCS = a memory block holding one virtual CPU’s saved state and rules · VM exit / entry = switch from guest to hypervisor / back · EPT / NPT = hardware memory translation for VMs · IOMMU (VT-d) = hardware that limits which memory a device may access

Type 5 · OS-level virtualization (containers)

Definition (say it in an interview): OS-level virtualization is a method in which the operating-system kernel allows multiple isolated user-space instances — containers — to run on one host; each has its own view of processes, network, files and hostname (namespaces) and its own resource limits (cgroups), while all share the host kernel.

In plain words (no jargon): Instead of creating whole pretend computers, the operating system creates separate, locked rooms for programs. Each program sees only its own files and its own processes, but all rooms run on the same core of the operating system — so they are tiny and start almost instantly.

Analogy: A hostel: private lockable rooms for each student, quick and cheap to move into, but one shared kitchen and water tank — the kernel. If the kitchen breaks, every room is affected.

How it works internally, step by step

  1. Get the files. A container image (or here, a root filesystem) holds the OS files and the app — but no kernel.
  2. Isolate the view. The kernel creates new namespaces: PID (own process list), mount (own files), UTS (own hostname), network (own IP), IPC, user.
  3. Change the root. chroot/pivot_root makes the image’s folder the process’s “/”.
  4. Limit resources. cgroups cap CPU, memory and I/O for the group.
  5. Start the app. The app becomes PID 1 inside; every system call goes to the shared host kernel.
  6. Clean up. When the last process exits, the namespaces disappear.

Words used above, in simple terms: root filesystem = the folder tree an OS needs: /bin, /etc, /lib… · chroot = make a folder look like “/” to a process · namespace = a private view of one kind of system resource · cgroup = a resource limit for a group of processes · PID 1 = the first process; when it ends, the container ends

Type 6 · I/O virtualization (emulated, virtio, SR-IOV)

Definition (say it in an interview): I/O virtualization lets multiple virtual machines share physical input/output devices — network cards, disk controllers, GPUs — either by emulating a device in software, by paravirtual drivers (virtio) that exchange data through shared memory, or by hardware SR-IOV, where one PCIe device presents many lightweight virtual functions that are assigned directly to VMs.

In plain words (no jargon): Many virtual machines must share one real network card and one disk controller. There are three ways: the hypervisor pretends to be the card (slow), the VM uses a special driver that hands data over efficiently (fast), or the card itself splits into many mini-cards, one for each VM (fastest).

Analogy: A restaurant kitchen with one serving window: at first a waiter carries every plate (emulation), then a conveyor belt is added (virtio), and finally each table gets its own serving hatch straight from the kitchen (SR-IOV).

How it works internally, step by step

  1. Emulated device. The hypervisor presents a well-known old device (e.g. Intel e1000). Every register access by the guest driver causes a trap and is emulated in software.
  2. Paravirtual (virtio). The guest uses a virtio driver; requests are placed in shared-memory queues (virtqueues) and the host is notified once per batch.
  3. Host side. A backend (QEMU, vhost in the kernel, or hardware) processes the queue and talks to the real device.
  4. SR-IOV: physical and virtual functions. An SR-IOV device has one Physical Function (PF, managed by the host) and many Virtual Functions (VFs) — light PCIe devices.
  5. Assign a VF. The hypervisor assigns a VF to a VM; the IOMMU ensures the VF can access only that VM’s memory.
  6. Direct data path. Packets flow between the VM and the card without the hypervisor in the way — near bare-metal speed.

Words used above, in simple terms: I/O = input/output: network, disk and other device traffic · PCIe = the slot/bus where cards plug into a server · virtqueue = a shared queue for virtio requests · PF / VF = the full device / one lightweight slice of it · IOMMU = hardware guard for device memory access

Type 7 · GPU virtualization (passthrough, vGPU, MIG)

Definition (say it in an interview): GPU virtualization lets one physical graphics/AI accelerator be used by several virtual machines or containers — by passing the whole GPU to one VM, by time-slicing it among many (vGPU), or by partitioning it in hardware into isolated instances with dedicated memory and compute (e.g. NVIDIA Multi-Instance GPU, MIG).

In plain words (no jargon): Graphics and AI chips (GPUs) are very expensive. Instead of giving each user a whole one, the chip is shared: given whole to one machine, shared in turns, or cut into fixed slices.

Analogy: One big, expensive oven in a bakery: you can rent the whole oven, rent it by time slot, or rent one fixed shelf. Nobody buys a new oven for each small cake.

How it works internally, step by step

  1. Passthrough. The hypervisor gives the entire GPU to one VM using the IOMMU; the VM’s normal driver controls it directly.
  2. vGPU (mediated). A host driver time-slices the GPU among VMs; each VM sees a virtual GPU with a share of memory.
  3. MIG. On supported NVIDIA GPUs the hardware itself is split into up to 7 instances, each with dedicated memory, cache and compute units — strong isolation.
  4. Scheduler. In Kubernetes, the GPU device plugin advertises whole GPUs, MIG slices or time-sliced replicas to pods.
  5. Monitor. Use nvidia-smi / DCGM to see utilization per instance.

Words used above, in simple terms: GPU = a processor with thousands of small cores, used for graphics and AI · passthrough = giving a real device directly to one VM · MIG = NVIDIA’s hardware partitioning of one GPU · time-slicing = taking turns on the same hardware

Where it is used

  • AI inference serving
  • Virtual desktops for designers (VDI with GPU)
  • Data-science notebooks for many students
  • Cloud gaming

Real-world example

NVIDIA’s Multi-Instance GPU lets an A100 or H100 be split into up to seven isolated GPU instances, and Google Kubernetes Engine supports scheduling pods onto these MIG slices.

Real scenario (TiffinGo)

TiffinGo’s “dish photo quality” model needs only a fraction of a large GPU for inference. Using a MIG slice (or a fractional-GPU VM) instead of a whole GPU cuts the cost while keeping its memory separate from other jobs.

Products and cloud services

NVIDIA vGPU software, NVIDIA MIG (A100, H100 and later), AMD MxGPU, Kubernetes GPU time-slicing; cloud: GPU instances on EC2, Azure NV-series with fractional GPUs, GKE with multi-instance GPUs.

For the experienced — did you know? MIG isolation is in hardware — separate memory controllers and L2 cache slices — so one tenant cannot slow another’s memory bandwidth, unlike time-slicing where a busy neighbour still competes.

Use it when: GPUs are under-used by single jobs (inference, virtual desktops, notebooks).
Avoid / be careful when: training large models that need the full GPU and fast GPU-to-GPU links — use whole GPUs/passthrough.

7 Deep dive

Namespaces in detail, containers on Windows/macOS, and security

The 8 Linux namespaces

Containers are not always Linux on Linux

Docker Desktop on Windows and macOS runs a small Linux VM and starts containers inside it — a container still needs a Linux kernel. Windows containers need a Windows kernel. Services like AWS Fargate even run each task in its own micro-VM (Firecracker) to combine container speed with VM isolation.

Security note

Because containers share the host kernel, a kernel bug can let one container escape to the host. That is why multi-tenant clouds put containers of different customers in separate VMs or micro-VMs, and why you should run containers as a non-root user and drop capabilities.

9 Real proof

Real proof: containers by hand

All outputs are real, from our Ubuntu 24.04 lab machine on 10 Nov 2026 (util-linux unshare, Alpine 3.24.4 minirootfs).

  1. Step 1 · The namespaces a process lives in

    ls -l /proc/self/ns
    == 1) the namespaces every Linux process lives in cgroup cgroup:[4026531835] ipc ipc:[4026531839] mnt mnt:[4026531832] net net:[4026531833] pid pid:[4026531836] pid_for_children pid:[4026531836] time time:[4026531834] time_for_children time:[4026531834] user user:[4026531837] uts uts:[4026531838]
    Each number is a namespace ID. Processes with the same IDs share that view.

  2. Step 2 · The host’s view

    ps -e --no-headers | wc -l; hostname
    == 2) host view: how many processes and what hostname? processes: 71 hostname: vm
    70 processes, hostname vm.

  3. Step 3 · A new PID, UTS and mount namespace

    unshare --pid --uts --mount --fork --mount-proc \
  bash -c 'hostname tiffingo-box; hostname; ps -e -o pid,comm'
    == 3) start a shell in NEW pid, uts and mount namespaces (what Docker does) inside: hostname=tiffingo-box inside: processes visible: 1 bash 4 ps
    Inside: bash is PID 1 and sees only 2 processes; the hostname is its own.

  4. Step 4 · The host is untouched

    hostname
    == 4) back on the host: hostname unchanged host hostname: vm
    The UTS namespace kept the change inside.

  5. Step 5 · How fast?

    time unshare --pid --uts --mount --fork --mount-proc true
    == 5) time to start an isolated environment unshare start + exit: 5 ms
    No OS to boot — just new namespaces for a process.

  6. Step 6 · Alpine on Ubuntu: a container from scratch

    curl -O https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/x86_64/alpine-minirootfs-…tar.gz
mkdir rootfs && tar -xzf alpine-minirootfs-*.tar.gz -C rootfs
unshare --pid --uts --mount --fork --mount-proc=rootfs/proc chroot rootfs /bin/sh
    == 1) download a 3.5 MB Linux root filesystem: alpine-minirootfs-3.24.4-x86_64.tar.gz unpacked size: 8.7M == 2) enter it: new root (chroot) + new PID, hostname and mount namespaces OS inside: Alpine Linux v3.24 hostname: tiffingo-box kernel: 6.18.44-fc-v338 processes: PID COMMAND 1 ps == 3) on the host, the OS is different OS on host: Ubuntu 24.04.5 LTS kernel on host: 6.18.44-fc-v338
    Different OS files (Alpine), different hostname, own PID 1 — but the same kernel 6.18 as the Ubuntu host. That is OS-level virtualization in one line.
10 Hands-on

Do it yourself, step by step

Three parts. A: run and limit a container with Docker Desktop (UI) or the docker CLI. B: see what Docker does underneath — this layer has no UI. C: check hardware-assisted virtualization, paravirtual drivers and SR-IOV networking on your machine and in AWS. Part C AWS outputs come from the moto emulator, which uses AWS’s published instance-type data.

  1. A1 · Run an Alpine container

    UI way — Docker Desktop

    1. Install and open Docker Desktop.
    2. Top search bar: type alpine → Pull.
    3. Images → alpine → Run (▶) → open Optional settings → Container name tiffingo-box → Run.
    4. Containers → tiffingo-box → Exec tab → type cat /etc/os-release, hostname, ps.

    CLI way — the same thing with commands

    docker run -it --name tiffingo-box --hostname tiffingo-box alpine sh
# inside the container:
cat /etc/os-release     # Alpine
hostname                # tiffingo-box
ps                      # only sh (PID 1) and ps
uname -r                # the kernel of the machine Docker runs on
    On Windows/macOS uname -r shows the kernel of Docker Desktop’s hidden Linux VM — proof that containers need a Linux kernel underneath.

  2. A2 · Limit CPU and memory (cgroups)

    UI way — Docker Desktop

    1. Docker Desktop’s Run dialog has no per-container limit fields. Settings → Resources limits the whole Docker VM.
    2. After starting a container with limits (CLI on the right), open Containers → the container → Stats to watch CPU % and memory against the limit.

    CLI way — the same thing with commands

    docker run -d --name limited --cpus 0.5 --memory 256m nginx:alpine
docker stats --no-stream limited
docker inspect limited --format '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
    Expect the memory limit to show as 256MiB. Per-container limits are set in the CLI or a Compose file — the UI only displays them.

  3. B1 · Underneath: namespaces by hand (Linux only)

    UI way

    1. There is no UI for this layer — it is exactly what Docker Desktop and Kubernetes hide from you. Use the terminal on a Linux machine, WSL2 or a cloud VM.

    CLI way — the same thing with commands

    ls -l /proc/self/ns              # namespaces this shell lives in
lsns | head                      # all namespaces (Docker containers appear here)
sudo unshare --pid --uts --mount --fork --mount-proc \
  bash -c 'hostname lab-room; hostname; ps -e'
hostname                         # unchanged outside
    Own hostname, own process tree, same kernel — a container in one line. Lesson proof steps 3–6 show the real output.

  4. B2 · Underneath: a cgroup memory limit

    UI way

    1. No UI — Docker’s --memory flag writes exactly this setting for you.

    CLI way — the same thing with commands

    sudo systemd-run --scope -p MemoryMax=50M \
  python3 -c 'x = bytearray(200*1024*1024)'
# → killed: the cgroup allows only 50 MB
    The kernel’s out-of-memory killer stops only the process in that cgroup.

  5. C1 · Is hardware-assisted virtualization on?

    UI way — click by click

    1. Windows: Ctrl+Shift+Esc → Performance → CPU → Virtualization: Enabled.
    2. Inside a VM, the same screen shows Virtual machine: Yes.

    CLI way — the same thing with commands

    grep -c -E -w "vmx|svm" /proc/cpuinfo   # host: > 0 = VT-x / AMD-V available
lscpu | grep -i hypervisor              # inside a VM: hypervisor vendor
    Type 4 of this lesson. If it is disabled, every hypervisor on the machine is slower or refuses to run.

  6. C2 · Which paravirtual drivers is my VM using?

    UI way — click by click

    1. Windows VM: Device Manager → Network adapters — on EC2 you see Amazon Elastic Network Adapter; on KVM Red Hat VirtIO Ethernet Adapter.
    2. Storage controllers shows the NVMe or VirtIO SCSI controller.

    CLI way — the same thing with commands

    lspci | grep -i -E 'virtio|elastic|nvme'
ethtool -i eth0 | head -2          # driver: ena / virtio_net
ls /sys/bus/virtio/devices 2>/dev/null
    If you see e1000 or IDE instead, the VM is using slow emulated devices (type 6) — switch to virtio/ENA drivers.

  7. C3 · Hypervisor and SR-IOV networking per instance type (AWS)

    UI way — AWS Management Console

    1. AWS Console → EC2 → left menu Instance types.
    2. Search t2.micro, then m5.large; open each and read the Details (hypervisor) and Networking sections (ENA support, Network performance).
    3. Compare: old t2 = Xen, no ENA; current families = Nitro, ENA required.

    CLI way — the same thing with commands

    aws ec2 describe-instance-types --instance-types t2.micro t3.micro m5.large c6gn.large p4d.24xlarge \
  --query 'InstanceTypes[].[InstanceType,Hypervisor,NetworkInfo.EnaSupport,NetworkInfo.NetworkPerformance]' \
  --output table
    == 1) hypervisor, ENA (SR-IOV enhanced networking) and bandwidth per instance type -------------------------------------------------------------- | DescribeInstanceTypes | +--------------+--------+---------------+--------------------+ | c6gn.large | nitro | required | Up to 25 Gigabit | | m5.large | nitro | required | Up to 10 Gigabit | | p4d.24xlarge| nitro | required | 4x 100 Gigabit | | t2.micro | xen | unsupported | Low to Moderate | | t3.micro | nitro | required | Up to 5 Gigabit | +--------------+--------+---------------+--------------------+
    ENA is SR-IOV-based enhanced networking: “required” means the instance can only boot with the ENA driver. Free — this only reads information.

  8. C4 · GPUs available to rent

    UI way — AWS Management Console

    1. EC2 → Instance types → filter GPUs > 0, or search g5.xlarge → Accelerators section shows the GPU model, count and memory.

    CLI way — the same thing with commands

    aws ec2 describe-instance-types --instance-types g5.xlarge p4d.24xlarge \
  --query 'InstanceTypes[].[InstanceType,GpuInfo.Gpus[0].Manufacturer,GpuInfo.Gpus[0].Name,GpuInfo.Gpus[0].Count,GpuInfo.Gpus[0].MemoryInfo.SizeInMiB]' \
  --output table
    == 2) GPU instance types and their GPUs -------------------------------------------------- | DescribeInstanceTypes | +---------------+---------+-------+----+---------+ | g5.xlarge | NVIDIA | A10G | 1 | 22888 | | p4d.24xlarge | NVIDIA | A100 | 8 | 40960 | +---------------+---------+-------+----+---------+
    A whole A10G or eight A100s are passed through to your instance (type 7, passthrough). Only reading data — no cost. Launching GPU instances is expensive; check the price first.

Clean up and cost check

docker rm -f tiffingo-box limited (UI: Containers → select → Delete). Namespaces from unshare vanish when their shell exits. Part C only reads information and costs nothing.

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
“Containers are tiny VMs.”They look similar from outside.Containers share the host kernel; VMs have their own. Different OS families need VMs.
Running Linux containers directly on Windows and wondering how.Docker Desktop hides a Linux VM.Know that a Linux VM (WSL2/Hyper-V) runs underneath.
Running containers as root with all capabilities.Default images often use root.Use a non-root USER, drop capabilities, read-only filesystem where possible.
No memory limit on containers.Default is unlimited.Set --memory / Kubernetes limits so one container cannot starve the node.
Expecting SR-IOV/GPU passthrough to allow live migration.Directly assigned hardware is tied to one host.Plan maintenance windows or use cloud-managed instances.

  2. ✔ namespaces and cgroups
  3. DNS and DHCP
  4. SSH and SFTP

Why: Namespaces isolate what a process can see; cgroups limit what it can use.

2. A container on an Ubuntu host reports the same kernel version as the host because…
  1. it is a bug
  2. ✔ containers share the host kernel
  3. Docker copies the kernel
  4. the VM is paused

Why: OS-level virtualization isolates user space only; the kernel is shared (our lab: Alpine inside, kernel 6.18 on both).

3. Which is an example of hardware-level partitioning?
  1. Docker
  2. ✔ IBM LPAR
  3. VirtualBox
  4. Kubernetes

Why: LPARs are created by the machine’s firmware/hypervisor layer on IBM systems, each with its own OS.

4. SR-IOV is used to…
  1. encrypt disks
  2. ✔ let VMs use a slice of a physical device directly for fast I/O
  3. back up VMs
  4. balance load across regions

Why: The device exposes virtual functions assigned to VMs, bypassing the hypervisor in the data path.

13 Mini project

Build something with what you learned

Mini project: build your own tiny container runtime in 15 lines of shell

Goal: Write minibox.sh that runs any command inside an Alpine root filesystem with its own hostname, process tree, network and a memory limit — the core of Docker.

Combines: Linux namespaces + cgroups + chroot (Linux course) + Docker course.

  1. Download and unpack the Alpine minirootfs into rootfs/ (proof step 6).
  2. Script line 1: sudo systemd-run --scope -p MemoryMax=128M \ (cgroup limit).
  3. Line 2: unshare --pid --uts --mount --net --fork --mount-proc=rootfs/proc \ (namespaces).
  4. Line 3: chroot rootfs /bin/sh -c "hostname minibox; exec $*" (own root filesystem).
  5. Run ./minibox.sh ps, ./minibox.sh hostname, ./minibox.sh ip link, ./minibox.sh cat /etc/os-release.
  6. Compare with docker run --rm -it --memory 128m alpine sh on a machine with Docker: same features, plus images, overlayfs and networking.

You should see: Output showing Alpine, hostname minibox, PID 1 = your command, only a loopback network.

Interview and viva questions

Is Kubernetes a hypervisor?

No. It orchestrates containers across many machines; the containers use namespaces and cgroups on each machine.

Can a container run Windows on a Linux host?

No. It needs a Windows kernel, so use a VM.

Are containers secure enough?

For one team’s apps, yes with good practice; for strangers on one host, add VM isolation (Fargate, gVisor, Kata).
