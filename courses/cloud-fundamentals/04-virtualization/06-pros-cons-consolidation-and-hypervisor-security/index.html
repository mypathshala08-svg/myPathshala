2 Definition

Advantages, disadvantages, consolidation and hypervisor security

Formal definition (write this in exams)

Server consolidation is the practice of running multiple workloads, previously on separate physical servers, as virtual machines on fewer physical hosts to increase utilization and reduce hardware, energy and operating costs. Hypervisor security is the protection of the virtualization layer — the hypervisor, its virtual devices and its management interfaces — against threats such as VM escape, side-channel attacks between co-resident VMs, hyperjacking and management-plane compromise, so that isolation between virtual machines is preserved.

In simple words

Consolidation = fewer, busier machines instead of many idle ones. Hypervisor security = making sure the layer that separates VMs cannot be broken, bypassed or taken over.

Say it in an interview

30-second answer you can speak:

  • “Virtualization’s advantages are consolidation, isolation, fast provisioning, snapshots and DR, hardware independence and energy savings; the disadvantages are some overhead, the host as a single point of failure, noisy neighbours, VM sprawl, licensing complexity and a new attack surface.”
  • “Server consolidation means measuring real usage, right-sizing, placing VMs on fewer hosts with headroom and anti-affinity, migrating with P2V and retiring old hardware — in my lab five servers averaging 8.2% CPU fit on one host at 41%.”
  • “Key hypervisor threats are VM escape through device bugs like VENOM, side channels like Spectre and L1TF, hyperjacking and management-plane attacks; defences include minimal device models, sandboxing, core isolation, patching, secure boot and confidential computing.”

Type 1 · VM escape

Definition (say it in an interview): A VM escape is an attack in which code running inside a virtual machine exploits a vulnerability in the hypervisor or its emulated devices to execute code on the host, breaking isolation and potentially reaching other VMs on the same host.

In plain words (no jargon): Normally a program inside a virtual machine cannot touch anything outside it. A VM escape is when an attacker finds a bug that lets them break out of the VM and control the real machine underneath.

Analogy: A prisoner who finds a crack in the cell wall that leads into the guards’ room: from there, every other cell can be opened.

How it works internally, step by step

  1. Get a foothold. The attacker gains code execution inside one VM (stolen password, unpatched app) — or simply rents a VM in a public cloud.
  2. Probe the device model. They talk to virtual devices (disk, NIC, floppy, USB, graphics) through I/O ports and memory-mapped registers.
  3. Trigger a bug. Malformed input overflows a buffer in the emulation code running on the host.
  4. Run code in the host process. The attacker now runs code in the VMM process (e.g. QEMU).
  5. Try to go further. From there they try to read other VMs’ memory or files, or escalate to the host kernel.
  6. Defences. Sandboxing of the VMM process (separate user, seccomp, SELinux/AppArmor), minimal device sets, IOMMU, fast patching.

Words used above, in simple terms: exploit = code that abuses a bug · device model = the virtual hardware a hypervisor emulates · buffer overflow = writing past the end of a memory area · seccomp = a Linux filter that blocks dangerous system calls · sVirt = SELinux labels that confine each VM’s process

VENOM (2015) let code in a guest overflow a buffer in QEMU’s virtual floppy controller — a device almost nobody used — affecting Xen, KVM and VirtualBox hosts until patched; it is why modern platforms strip unused devices.

Real scenario (TiffinGo)

Suppose one of TiffinGo’s VMs is hacked through an old web plugin. If the host still exposed an old emulated floppy controller with a known bug, the attacker could try to escape to the host and reach the billing VM. Patched hosts, removed devices and sandboxed device processes stop this.

Products and cloud services

Real cases: VENOM (CVE-2015-3456, QEMU floppy controller), and VM-escape bugs regularly found in contests like Pwn2Own; defences: libvirt sVirt + seccomp, Firecracker jailer, minimal devices, prompt hypervisor patching (done by the provider in public clouds).

For the experienced — did you know? A VM-escape bug in the hypervisor is among the most valuable findings in security contests such as Pwn2Own, with prizes in the hundreds of thousands of dollars — a measure of how hard, and how damaging, they are.

Use it when: always assume it is possible: patch hypervisors quickly, remove unused virtual devices, and keep guests patched so attackers never get the first foothold.
Avoid / be careful when: you give guest VMs passthrough hardware or extra privileges without need — every extra device and permission is attack surface.

Type 2 · Side-channel attacks between VMs

Definition (say it in an interview): A side-channel attack extracts secret information not by breaking software isolation but by measuring physical effects of shared hardware — cache timing, branch prediction, power use — so that a VM can infer data processed by another VM running on the same CPU.

In plain words (no jargon): Two virtual machines can share the same tiny memory inside a processor chip. By very precisely timing its own work, one VM can sometimes guess what the other is doing — and leak secrets — without breaking any rules of the software.

Analogy: Guessing a neighbour’s PIN from the beeps of the ATM keypad: you never touch their card or the machine, you just listen carefully to something you both share.

How it works internally, step by step

  1. Co-location. Attacker and victim run on the same physical core or share caches.
  2. Prime. The attacker fills cache lines with its own data.
  3. Victim runs. The victim’s secret-dependent code evicts some lines.
  4. Probe. The attacker times reloading its data; slow = evicted = the victim touched that line.
  5. Infer. Repeated many times, patterns reveal bits of keys or memory (Spectre adds speculative execution to read beyond bounds).
  6. Defend. Flush buffers on VM switch, fence speculation, never share cores between tenants, dedicate hardware.

Words used above, in simple terms: cache = a small fast memory inside the CPU · SMT / hyper-threading = two threads sharing one physical core · speculative execution = the CPU guessing ahead and running instructions early · microcode = firmware inside the CPU that can be updated

Real-world example

When Meltdown and Spectre were disclosed in January 2018, AWS, Azure and Google patched and rebooted or live-migrated their entire fleets; AWS states that EC2 never lets vCPUs of different customers share a physical core’s hyper-threads.

Real scenario (TiffinGo)

If TiffinGo’s payment-signing VM shared a CPU core with a hostile VM, cache timing could leak bits of its signing key. Clouds prevent this by never letting two customers share a core and by patching CPU microcode; for extra assurance TiffinGo could use a Dedicated Host.

Products and cloud services

Spectre and Meltdown (2018), L1TF/Foreshadow (2018), MDS (2019); defences: CPU microcode updates, kernel mitigations, core scheduling (no SMT sharing between tenants), Dedicated Hosts / sole-tenant nodes, confidential VMs.

For the experienced — did you know? Run grep . /sys/devices/system/cpu/vulnerabilities/* on any instance: the kernel lists each known CPU issue and whether it is “Not affected”, “Mitigation: …” or “Vulnerable” — our lab shows 19 entries.

Use it when: you handle cryptographic keys or highly sensitive data on shared hardware — rely on provider core isolation, keep guests patched, consider dedicated or confidential instances.
Avoid / be careful when: turning off kernel mitigations “for performance” on shared systems.

Type 3 · Hyperjacking (malicious hypervisor)

Definition (say it in an interview): Hyperjacking is an attack in which an adversary installs a malicious hypervisor beneath an operating system, or replaces or tampers with the legitimate hypervisor, gaining control over all virtual machines and data above it while remaining hidden from them.

In plain words (no jargon): An attacker secretly slips a fake “manager program” underneath the operating system. From there it can watch and control everything, while the operating system has no idea.

Analogy: A fake building manager who quietly replaces the real one: residents keep living normally, unaware that someone now holds every master key and reads every letter.

How it works internally, step by step

  1. Gain high privilege. The attacker needs admin/root on the host, firmware access or physical access.
  2. Insert a layer. Install a thin malicious hypervisor that moves the running OS into a VM (Blue Pill idea), or plant a malicious module in the real hypervisor.
  3. Hide. The rogue layer intercepts what the OS sees, making itself invisible.
  4. Abuse. Read memory, steal keys, alter traffic of every VM.
  5. Defend: verify the chain. Secure Boot checks signatures of each boot stage; measured boot records hashes in a TPM for attestation; only signed modules allowed.

Words used above, in simple terms: UEFI Secure Boot = firmware feature that only starts signed boot software · TPM = a security chip that records measurements of what booted · attestation = proving to a remote party what software is running · VIB = a software package installed into VMware ESXi

Real scenario (TiffinGo)

If an attacker with physical or admin access replaced the hypervisor on TiffinGo’s on-premises host with a tampered build, every VM would be compromised. UEFI Secure Boot and TPM-based measured boot would refuse or flag the unsigned hypervisor.

Products and cloud services

Research proof-of-concept “Blue Pill” (2006); real-world: attackers deploying malicious vSphere Installation Bundles (VIBs) to ESXi hosts for persistence (reported in 2022); defences: UEFI Secure Boot, TPM/vTPM, measured boot and attestation, signed hypervisor packages, hardware roots of trust (AWS Nitro Security Chip).

For the experienced — did you know? Cloud providers anchor trust in their own hardware: the AWS Nitro Security Chip and Google’s Titan chip verify firmware and boot code before the host runs, so a customer never has to trust software it cannot see.

Use it when: you run your own hypervisors — enable Secure Boot for hosts, accept only signed packages and monitor for unexpected changes.
Avoid / be careful when: hosts allow unsigned modules or community packages, or admin access to hosts is widely shared.

Type 4 · Management-plane attacks

Definition (say it in an interview): A management-plane attack targets the interfaces used to administer the virtualized environment — hypervisor management consoles (vCenter, ESXi host client, Hyper-V Manager), cloud consoles, APIs and their credentials — so the attacker can create, change, snapshot, steal or destroy many VMs at once without breaking into any of them.

In plain words (no jargon): Rather than attacking each virtual machine, the attacker steals the “remote control” that manages all of them — an admin login or API key — and then controls everything at once.

Analogy: Instead of picking the lock of each flat, the thief steals the building manager’s master-key cabinet.

How it works internally, step by step

  1. Find the console. Scan the internet for exposed ESXi/vCenter, or search code repositories for leaked cloud keys.
  2. Get in. Exploit an unpatched flaw, guess/steal passwords, or use a leaked key.
  3. Act at scale. Snapshot and copy disks, change security groups, create crypto-mining VMs, encrypt or delete VMs.
  4. Hide. Disable logging or create new admin users.
  5. Defend. Private management networks, MFA everywhere, least privilege, short-lived credentials (IAM roles), patching, audit logs with alerts.

Words used above, in simple terms: management plane = the tools and APIs used to control infrastructure · MFA = multi-factor authentication: password + code/device · least privilege = give only the permissions needed · CloudTrail = AWS log of every API call

Products and cloud services

Defences: MFA, private admin networks, patching, IAM least privilege, AWS CloudTrail / Azure Activity Log monitoring.

For the experienced — did you know? In AWS the management plane is IAM. A single policy with "Action": "*" on a CI user is functionally equivalent to an internet-exposed vCenter — audit with IAM Access Analyzer and replace keys with roles.

Use it when: always: treat hypervisor consoles and cloud root/admin accounts as the crown jewels.
Avoid / be careful when: management ports are open to the internet, admin accounts are shared, or long-lived access keys are stored in code.

Type 5 · VM sprawl

Definition (say it in an interview): VM sprawl is the uncontrolled growth of virtual machines — created easily and then forgotten — that remain running or stored without an owner, patching or monitoring, increasing cost, licence exposure and attack surface.

In plain words (no jargon): Because making virtual machines is so easy, people make many and forget about them. The forgotten ones keep costing money and, since nobody updates them, become easy targets for attackers.

Analogy: A fridge in a shared office: everyone puts boxes in, nobody takes them out. Months later nobody knows whose they are, the space is full, and something has gone bad.

How it works internally, step by step

  1. Easy creation. Self-service lets anyone launch VMs in seconds.
  2. No ownership record. VMs are created without owner, project or expiry tags.
  3. Drift into neglect. People leave or projects end; VMs keep running.
  4. Risk builds. Missing patches, open ports, old credentials, licence and cost leakage.
  5. Defend. Tag policies (deny launch without tags), budgets and alerts, scheduled stop of non-production, periodic inventory and deletion.

Words used above, in simple terms: tag = a label (key = value) attached to a resource · tag policy = a rule requiring certain tags · budget alert = a notification when spend passes a limit · inventory = a list of everything that exists

Avoid / be careful when: test resources live in the same account as production with no tags or budgets.

Type 6 · Lateral movement between VMs

Definition (say it in an interview): Lateral movement is the technique attackers use after compromising one machine to move to other machines in the same environment — exploiting flat virtual networks, shared credentials and open ports — and it is contained by network segmentation and least-privilege access.

In plain words (no jargon): After breaking into one computer, attackers try to jump to the others nearby. If every computer can talk freely to every other, one break-in becomes a disaster.

Analogy: A burglar who enters through one unlocked flat and then walks freely through internal doors into every other flat, because nobody locked them.

How it works internally, step by step

  1. Initial compromise. One VM is hacked.
  2. Discover. The attacker scans the internal network for reachable hosts and ports.
  3. Harvest credentials. Passwords, SSH keys or cloud credentials found on the first VM.
  4. Move. Log in to or exploit the next VM; repeat.
  5. Defend. Segment networks (default deny), unique credentials, IAM roles instead of keys, monitoring of east-west traffic.

Words used above, in simple terms: east-west traffic = traffic between servers inside the data centre · segmentation = splitting a network into zones with rules between them · micro-segmentation = rules down to individual VMs or workloads · zero trust = never trust a connection just because it is internal

Products and cloud services

For the experienced — did you know? Security groups can reference other security groups: allow port 5432 on the db-sg only from app-sg, not from an IP range. New app instances are allowed automatically, nothing else ever is.

Use it when: always: design “default deny” between tiers and allow only required ports.
Avoid / be careful when: all VMs sit in one subnet with an “allow all inside” rule, or the same admin password is reused on every VM.

6 Explained part by part

Advantages, disadvantages and defences

Advantages

Server consolidation

What it is: Running many workloads as VMs on fewer physical hosts.

Why it exists: Typical servers were 5–15% busy; power, space and hardware were wasted.

Where it is used: Every virtualized data centre; our lab: 5 servers → 1 host.

Isolation

What it is: A crash or compromise in one VM does not directly affect others.

Why it exists: Mixing apps on one OS let one bad app break everything.

Where it is used: Separate VMs for web, database, test.

Fast provisioning and cloning

What it is: New servers from images in seconds–minutes (Lesson 4.4).

Why it exists: Buying and installing hardware took weeks.

Where it is used: Dev/test environments, Auto Scaling, VDI.

Snapshots, backup and DR

What it is: Whole-machine images can be copied, replicated and restarted elsewhere.

Why it exists: Rebuilding a physical server after a disaster took days.

Where it is used: EBS snapshots, VMware SRM, Azure Site Recovery, AWS Elastic Disaster Recovery.

Hardware independence and legacy support

What it is: VMs see standard virtual hardware, so they move between host models; old OSes keep running.

Why it exists: Old apps tied to dying hardware.

Where it is used: Running a Windows 2012 app on new servers; migrating between hosts.

Energy and green IT

What it is: Fewer, busier servers use less power and cooling.

Why it exists: Data centres use a large share of electricity.

Where it is used: Our calculation: ≈10,512 kWh/yr saved.

Disadvantages

Performance overhead

What it is: Some CPU, memory and I/O cost for the virtualization layer (small with VT-x, virtio, Nitro).

Why it exists: Trapping and emulation take time.

Where it is used: Latency-critical trading, HPC; use bare metal or SR-IOV.

Host is a single point of failure

What it is: One host failure stops all its VMs.

Why it exists: Consolidation puts eggs in one basket.

Where it is used: Mitigate with HA clusters, anti-affinity, multiple AZs.

Noisy neighbours / contention

What it is: VMs compete for CPU, cache, disk and network.

Why it exists: Overcommit and shared hardware.

Where it is used: Watch CPU-ready, steal time (%st in top); right-size; dedicated instances.

VM sprawl

What it is: Too many forgotten VMs because creating them is easy.

Why it exists: No cost or effort to create → no reason to delete.

Where it is used: Unpatched, unknown VMs become security holes and cost money; tag and expire them.

Licensing and skills complexity

What it is: Licences may count physical cores or hosts; admins need new skills.

Why it exists: Vendors price per socket/core/host.

Where it is used: Windows Server, Oracle, SQL Server on virtual hosts; Broadcom-era VMware licensing changes.

New attack surface

What it is: Hypervisor, virtual devices and management tools can be attacked.

Why it exists: More layers = more code.

Where it is used: VM escape, side channels, ESXi ransomware (figure above).

Defences you can choose

Confidential computing

What it is: VM memory encrypted by the CPU so even the host/hypervisor cannot read it.

Why it exists: Protect data in use from a compromised or curious host.

Where it is used: AMD SEV-SNP, Intel TDX; AWS Nitro Enclaves, Azure and GCP confidential VMs.

Dedicated host / sole tenancy

What it is: A whole physical server reserved for one customer.

Why it exists: Compliance and per-socket licensing; no neighbours.

Where it is used: AWS Dedicated Hosts, Azure Dedicated Host, GCP sole-tenant nodes.

Myth vs reality: things many websites still say

  • Myth: VMs are perfectly isolated.
    Reality: Device bugs and CPU side channels have broken isolation.
    Proof: Deep dive incidents.
  • Myth: Consolidation always saves money.
    Reality: Only after old servers are retired and licences checked.
    Proof: Animation step 5.
  • Myth: In the cloud, security is the provider’s job.
    Reality: Guest OS, IAM, network rules and encryption are yours.
    Proof: Shared-responsibility table.
  • Myth: A dedicated host is needed for security.
    Reality: Mostly for licensing/compliance; Nitro isolates well.
    Proof: Mistakes.
7 Deep dive

Real incidents, how clouds defend the hypervisor, shared responsibility, consolidation maths

Real incidents that shaped hypervisor security

YearNameWhat happenedLesson learned
2015VENOM (CVE-2015-3456)Buffer overflow in QEMU’s virtual floppy controller allowed guest-to-host code executionRemove unused virtual devices; sandbox device processes
2018Meltdown / SpectreCPU speculative execution leaked memory across processes and VMsHardware itself can break isolation; patch microcode + kernels
2018L1TF / ForeshadowLeaked L1 cache data between VMs on sibling hyper-threadsDo not share a core between untrusted VMs
2023ESXiArgs ransomwareMass attacks on internet-exposed, unpatched ESXi hosts (OpenSLP, CVE-2021-21974) encrypted VM filesNever expose management interfaces; patch hosts

How the big clouds defend the hypervisor

  • AWS Nitro: networking, storage and management moved to dedicated Nitro cards; a minimal KVM-based hypervisor; the Nitro system is designed with no operator access — no SSH or console for AWS staff to reach customer memory. Hypervisor updates are often applied live, without rebooting guests.
  • Core isolation: EC2 does not let vCPUs of different customers share a physical core’s hyper-threads; Azure and GCP use similar core scheduling.
  • Firecracker: tiny device model plus a jailer process for Lambda/Fargate micro-VMs.
  • Confidential VMs: memory encrypted by the CPU (AMD SEV-SNP, Intel TDX) on Azure, Google Cloud and AWS; AWS Nitro Enclaves isolate secrets inside an instance.

Consolidation maths you will be asked

Consolidation ratio = physical servers before ÷ hosts after (ours: 5:1; 10–20:1 is common). vCPU:pCPU overcommit of 3–4:1 is usual for general workloads but must be watched through CPU-ready/steal time. Plan hosts for N+1: if 4 hosts at 70% must survive one failure, the other 3 must absorb 4×70/3 ≈ 93% — too tight; aim for ≈60% or add a host.

  printf "%-12s %s\n" $f "$(cat $f)"
done

    == 1) CPU side-channel vulnerabilities the kernel knows about, and their status meltdown Not affected spectre_v1 Mitigation: usercopy/swapgs barriers and __user pointer sanitization spectre_v2 Mitigation: Enhanced / Automatic IBRS; IBPB: conditional; PBRSB-eIBRS: l1tf Not affected mds Not affected retbleed Not affected total vulnerability entries: 19
    The Linux kernel lists every known CPU side-channel issue and how it is handled on this machine: newer CPUs are “Not affected” by Meltdown, L1TF and MDS; Spectre needs software mitigations. Run this on any Linux VM — including an EC2 instance.

  2. Step 2 · The consolidation calculation

    apps = {"Mail": 8, "Website": 15, "Accounts": 5, "HR": 3, "Backup": 10}   # % CPU of one server each
print("before: 5 physical servers, average CPU used:", round(sum(apps.values())/5, 1), "%")
print("after : 1 host with 5 VMs, CPU used:", sum(apps.values()), "%")
watts = 300
print("power saved: 4 servers ×", watts, "W =", 4*watts, "W ≈", round(4*watts*24*365/1000), "kWh per year")
    == 2) server consolidation: five half-idle servers onto one host before: 5 physical servers, average CPU used: 8.2 % after : 1 host with 5 VMs, CPU used: 41 % (+ ~10% hypervisor/headroom target) power saved: 4 servers × 300 W = 1200 W ≈ 10512 kWh per year
    The 300 W per server is an assumption for a typical 1U server; replace it with your servers’ measured power. Remember the host also needs headroom.
10 Hands-on

Do it yourself, step by step

Part A checks and hardens your own machine; Part B hardens the virtualization settings that you control in AWS. Each step: UI way and CLI way. Part B outputs come from the moto AWS emulator; on a real account a Dedicated Host is billed per hour while allocated — release it right after the test.

  1. A1 · Check your CPU’s side-channel status (threat 2)

    UI way — Windows Security

    1. Windows: Windows Security → Device security → Core isolation details → see whether Memory integrity is on (it uses the Hyper-V hypervisor to protect the Windows kernel).
    2. Detailed CPU mitigation status on Windows needs PowerShell (CLI on the right).

    CLI way — the same thing with commands

    grep . /sys/devices/system/cpu/vulnerabilities/*

# Windows PowerShell (as admin):
Install-Module SpeculationControl; Get-SpeculationControlSettings
    == 1) CPU side-channel vulnerabilities the kernel knows about, and their status meltdown Not affected spectre_v1 Mitigation: usercopy/swapgs barriers and __user pointer sanitization spectre_v2 Mitigation: Enhanced / Automatic IBRS; IBPB: conditional; PBRSB-eIBRS: l1tf Not affected mds Not affected retbleed Not affected total vulnerability entries: 19
    Run it on your laptop and on a cloud VM and compare: “Not affected”, “Mitigation: …” or “Vulnerable”.

  2. A2 · Am I a VM, and is my host busy?

    UI way — click by click

    1. Windows VM: Task Manager → Performance → CPU shows Virtual machine: Yes.
    2. AWS: CloudWatch → Metrics → EC2 → CPUUtilization; for t3 instances also CPUCreditBalance (low credits look like “steal”).

    CLI way — the same thing with commands

    systemd-detect-virt      # kvm, amazon, microsoft, none…
top -bn1 | head -3       # %st = CPU stolen by the hypervisor for other VMs
vmstat 1 5               # last column “st”
    A high steal value means noisy neighbours or a burstable instance out of credits — right-size or move to a fixed-performance type.

  3. A3 · Remove devices you do not need (threat 1)

    UI way — VirtualBox

    1. VirtualBox: select the VM → Settings → Audio → untick Enable Audio.
    2. USB → untick Enable USB Controller.
    3. Storage → select any Floppy controller → Remove; System → Boot Order → untick Floppy.

    CLI way — the same thing with commands

    virsh dumpxml myvm | grep -E '<(disk|sound|input|controller) '
virsh edit myvm          # delete <sound>, floppy <disk>, unused <controller> entries
VBoxManage modifyvm myvm --audio-enabled off --usb-ohci off --usb-ehci off --usb-xhci off
    Smaller device model = smaller VM-escape attack surface (the VENOM lesson). Older VirtualBox versions use --audio none.

  4. B1 · Which hypervisor runs each instance type?

    UI way — AWS Management Console

    1. EC2 → Instance types → search t2.micro, t3.micro, m5.large → open each → Details shows Hypervisor: xen / nitro.

    CLI way — the same thing with commands

    aws ec2 describe-instance-types --instance-types t3.micro m5.large t2.micro \
  --query 'InstanceTypes[].[InstanceType,Hypervisor]' --output text
    == 1) which hypervisor does an instance type use? m5.large nitro t2.micro xen t3.micro nitro
    Prefer Nitro families: smaller hypervisor, I/O in dedicated hardware, no operator access.

  5. B2 · Encrypt every new EBS volume by default

    UI way — AWS Management Console

    1. EC2 → Dashboard → right panel Account attributes → Data protection and security.
    2. EBS encryption → Manage → tick Enable → Update EBS encryption.
    3. Repeat in every Region you use (the setting is per Region).

    CLI way — the same thing with commands

    aws ec2 get-ebs-encryption-by-default
aws ec2 enable-ebs-encryption-by-default
    == 2) encrypt every new EBS volume in this Region by default False True
    All new volumes and snapshots are encrypted with keys from AWS KMS (Key Management Service) — a stolen snapshot (threat 4) is useless without the key.

  6. B3 · Require IMDSv2 (threat 4: stolen credentials)

    UI way — AWS Management Console

    1. New instance: Launch instances → Advanced details → Metadata version → V2 only (token required).
    2. Existing instance: select it → Actions → Instance settings → Modify instance metadata options → IMDSv2 Required → Save.
    3. Account-wide default: EC2 → Dashboard → Account attributes → Data protection and security → IMDS defaults.

    CLI way — the same thing with commands

    aws ec2 run-instances --image-id $AMI --instance-type t3.micro \
  --metadata-options HttpTokens=required,HttpPutResponseHopLimit=1
# existing instance:
aws ec2 modify-instance-metadata-options --instance-id i-… --http-tokens required
    == 3) launch with IMDSv2 required (blocks SSRF-style metadata theft) i-b38ab9b9fa606d181 required 1
    Blocks the classic SSRF attack (tricking a web app into fetching a URL for the attacker) that steals an instance’s role credentials from the metadata service (Lesson 2.1).

  7. B4 · No neighbours: allocate a Dedicated Host

    UI way — AWS Management Console

    1. EC2 → Dedicated Hosts → Allocate Dedicated Host.
    2. Name tiffingo-host, instance family m5, AZ ap-south-1a, quantity 1 → Allocate.
    3. Release it straight away: select → Actions → Release host.

    CLI way — the same thing with commands

    aws ec2 allocate-hosts --availability-zone ap-south-1a --instance-family m5 --quantity 1
aws ec2 describe-hosts --host-ids $H \
  --query 'Hosts[].[HostId,AvailabilityZone,State,HostProperties.InstanceFamily]' --output text
aws ec2 release-hosts --host-ids $H
    == 4) a Dedicated Host: a whole physical server only for your account h-778a65930012d3e6f ap-south-1a available m5
    A whole physical server for your account (threat 2 defence, and for per-core licences). Expensive — only when required.

Clean up and cost check

Terminate the test instance (Instance state → Terminate instance) and release the Dedicated Host (Actions → Release host) — billing stops only after release. Keep EBS encryption by default and IMDSv2 on in real accounts.

11 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Consolidating without measuring peaks.Averages hide month-end spikes.Measure for weeks, size for peak + headroom, keep N+1.
Putting both database replicas on the same host.Placement left to defaults.Use anti-affinity rules / spread placement groups / different AZs.
Exposing ESXi or vCenter to the internet.Convenient remote admin.VPN or bastion only, MFA, patch quickly.
Leaving unused virtual devices (floppy, USB, sound) on server VMs.Default templates.Strip devices from templates; use virtio.
Never deleting test VMs (VM sprawl).Creating is free and easy.Tag owner + expiry; scheduled clean-up; AWS Config / budgets alerts.
Assuming the cloud patches your guest OS.The provider patches the hypervisor.Guest OS patching is yours (SSM Patch Manager, Azure Update Manager).

Exam-style questions with explanations

  1. more physical servers
  2. ✔ higher utilization and lower hardware, power and space costs
  3. no need for backups
  4. faster CPUs

Why: Many under-used servers become VMs on fewer, busier hosts.

2. An attacker’s code in a VM runs on the host through a virtual device bug. This is…
  1. phishing
  2. ✔ VM escape
  3. DDoS
  4. SQL injection

Why: VENOM (2015) is the classic example.

3. In AWS, who patches the hypervisor of EC2 hosts?
  1. the customer
  2. ✔ AWS
  3. both equally
  4. nobody

Why: Security “of” the cloud — physical hosts and virtualization — is AWS’s responsibility; the guest OS is yours.

4. A company must use per-physical-core software licences and see the host’s sockets/cores. Which option?
  1. Spot Instances
  2. ✔ Dedicated Hosts
  3. Lambda
  4. Reserved Instances only

Why: Dedicated Hosts give visibility of physical cores and sockets for bring-your-own-licence.

5. Which risk comes from VMs being too easy to create?
  1. side channel
  2. ✔ VM sprawl
  3. hyperjacking
  4. live migration

Why: Forgotten, unpatched VMs cost money and become entry points.

6. Which technology protects VM memory even from the host and hypervisor?
  1. VLAN
  2. ✔ Confidential computing (AMD SEV-SNP / Intel TDX)
  3. RAID 1
  4. NAT gateway

Why: The CPU encrypts guest memory with keys the hypervisor cannot read.

13 Mini project

Build something with what you learned

Mini project: a consolidation and security assessment report

Goal: Act as TiffinGo’s cloud consultant: measure five “servers”, design the consolidated layout, and produce a hardening checklist with evidence.

Combines: Lessons 4.1–4.6 + Linux performance tools + Module 9 security (later).

  1. Measure: run five Docker containers or five small VMs, each with a different load (stress-ng --cpu 1 --cpu-load 8, 15, 5, 3, 10); collect CPU with docker stats or sar every minute for an hour.
  2. Size and place: in a spreadsheet, compute averages and peaks, choose VM sizes, and place them on hosts at a 60% target with N+1. Mark anti-affinity pairs.
  3. Savings: extend consolidate.py to read your CSV and compute servers saved, kWh and ₹ per year (use your electricity tariff).
  4. Security evidence: on each Linux machine, save grep . /sys/devices/system/cpu/vulnerabilities/* and systemd-detect-virt.
  5. AWS checks: run practical B1–B3 on your account (or the emulator) and record EBS-encryption-by-default and IMDSv2 status for every instance (aws ec2 describe-instances --query "Reservations[].Instances[].MetadataOptions.HttpTokens").
  6. Report: one page each for savings, risks (use the threat map), and a 10-item hardening checklist (patching, MFA on management plane, no exposed ESXi, device minimization, encryption, IMDSv2, tagging/expiry, anti-affinity, backups, monitoring steal time).

Interview and viva questions

Is a VM safer than a container?

Generally the isolation boundary is stronger (own kernel), which is why clouds separate customers with VMs or micro-VMs; both still need patching and good configuration.

Do I need Dedicated Hosts on AWS?

Usually only for licensing (per-socket/core) or specific compliance rules.

Does consolidation hurt performance?

Only if overcommitted; size for peaks, monitor steal/ready time, and keep headroom.

What is hyperjacking?

Installing a malicious hypervisor beneath the OS (or replacing the real one) so it controls everything above; prevented with secure and measured boot.
