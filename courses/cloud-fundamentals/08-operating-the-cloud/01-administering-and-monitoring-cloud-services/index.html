2 Definition

Administering and monitoring cloud services

Formal definition (write this in exams)

Cloud monitoring is the continuous collection and analysis of metrics, logs, traces and events from cloud resources and applications to detect problems, understand behaviour and trigger responses; cloud administration is the ongoing management of those resources — configuration, access, patching, capacity, cost and change control — using provider tools such as Amazon CloudWatch and CloudTrail, Azure Monitor and Activity Log, and Google Cloud Monitoring, Logging and Audit Logs.

In simple words

Watching your cloud systems with numbers, records and alarms, so you find and fix problems before customers notice — and keeping track of every change.

Say it in an interview

30-second answer you can speak:

  • “Monitoring uses metrics to detect, logs and traces to explain, alarms to act, dashboards to see, and audit trails to know who changed what. In AWS that is CloudWatch, X-Ray and CloudTrail; in Azure, Azure Monitor, Application Insights and Activity Log; in Google Cloud, Cloud Monitoring, Logging, Trace and Audit Logs.”
  • “I alarm on user-facing symptoms — the four golden signals — and keep cause metrics on dashboards to avoid alert fatigue.”

Type 1 · Metrics

Definition (say it in an interview): A metric is a numeric measurement collected at regular intervals and stored as a time series — a value with a timestamp and dimensions (labels) such as instance ID or API name — used to observe trends, compute statistics (average, maximum, percentiles) and trigger alarms.

In plain words (no jargon): Numbers measured every minute, like CPU use or number of errors, kept so you can see trends.

Analogy: A car’s dashboard gauges: speed, fuel, temperature — numbers that change over time and warn you before the engine overheats.

How it works internally, step by step

  1. Emit. Built-in for managed services.
  2. Agent. Memory, disk, app metrics need an agent.
  3. Custom. Your own business metrics.
  4. Aggregate. Avg, sum, max, p50/p90/p99.
  5. Retain. Fine detail short-term, rolled up long-term.

Words used above, in simple terms: time series = values recorded over time · dimension = a label that splits a metric, e.g. by instance · p99 = 99th percentile — 99% of requests were faster than this

Use it when: you need cheap, fast signals for trends, capacity and alarms.
Avoid / be careful when: you need the details of a single event (who, which order) — that is a log.

Type 2 · Logs

Definition (say it in an interview): A log is a timestamped record of a discrete event written by an application, operating system or cloud service — for example an error, a request or a login — collected into a central store where it can be filtered, searched with queries and turned into metrics or alerts.

In plain words (no jargon): Written records of everything that happened, with the time, which you can search when something goes wrong.

Analogy: A shop’s daily register: every sale, refund and complaint written down with the time, so you can check later exactly what happened.

How it works internally, step by step

  1. Write. Structured JSON with request ID.
  2. Ship. Agent or built-in integration.
  3. Store. Log group / workspace / bucket.
  4. Query. Insights / KQL / Logging query.
  5. Retain. Set retention; archive old logs.

Words used above, in simple terms: structured log = log written as fields (JSON), easy to query · retention = how long logs are kept · KQL = Kusto Query Language used by Azure logs

Type 3 · Distributed traces

Definition (say it in an interview): A distributed trace records the path and timing of a single request as it travels through multiple services; it consists of spans (one per operation) linked by a shared trace ID, so engineers can see where latency or errors occur in a microservices system.

In plain words (no jargon): A record of one request’s journey through all services, showing how long each step took.

Analogy: Tracking a courier parcel: each hub scans it with the time, so you can see exactly where it waited two days.

How it works internally, step by step

  1. Instrument. SDK or OpenTelemetry auto-instrumentation.
  2. Propagate. Trace ID passed in headers.
  3. Sample. Keep a % of traces (all errors).
  4. Collect. Send to tracing backend.
  5. Analyse. Waterfall, service map.

Words used above, in simple terms: span = one timed operation inside a trace · sampling = keeping only some traces to save cost · OpenTelemetry = open standard for metrics, logs and traces

Type 4 · Alarms and notifications

Definition (say it in an interview): An alarm (alert) continuously evaluates a rule — a static threshold, anomaly band or log query — against a metric or log over an evaluation period, changes state when the rule is breached, and triggers notifications (email, SMS, chat, paging) or automated actions (scaling, restarts, runbooks).

In plain words (no jargon): Automatic rules that send a message (or fix something) when a number goes past a limit.

Analogy: A smoke detector: silent most of the time, loud the moment smoke crosses a level — and it should not go off every time you make toast.

How it works internally, step by step

  1. Choose signal. User-facing symptoms first.
  2. Threshold. Static, or anomaly detection.
  3. Window. M of N data points.
  4. Route. Severity → right channel.
  5. Runbook. Link what to do.

Words used above, in simple terms: threshold = the limit that triggers the alarm · alert fatigue = people ignore alerts because there are too many · runbook = step-by-step instructions for a known problem

Type 5 · Dashboards

Definition (say it in an interview): A dashboard is a curated set of visualisations (graphs, numbers, log tables, alarm states) of key metrics and logs, arranged on one screen so that people can assess system health quickly and share the same view during operations and incidents.

In plain words (no jargon): One screen with the most important graphs, so anyone can see quickly whether things are healthy.

Analogy: A railway station’s departure board: one glance tells you what is on time, delayed or cancelled.

How it works internally, step by step

  1. Audience. On-call, business, exec.
  2. Top row. User impact (golden signals).
  3. Next. Dependencies and capacity.
  4. Annotate. Deploys and incidents.
  5. As code. Store dashboard JSON in Git.

Words used above, in simple terms: widget = one graph or number on a dashboard · KPI = key performance indicator · annotation = a marker on a graph, e.g. “deploy at 8:30”

Type 6 · Audit trails (activity logs)

Definition (say it in an interview): An audit trail is a platform-generated record of management (control-plane) actions in a cloud account — which identity called which API, when, from which IP and with what result — used for security investigations, change tracking, alerting on risky actions and compliance.

In plain words (no jargon): Automatic records of who changed what in your cloud account, and when.

Analogy: The visitor register and CCTV at an office gate: who entered, when, and which room they went to.

How it works internally, step by step

  1. Enable. On by default for management events (90 days in AWS event history).
  2. Trail/export. To a bucket or workspace for long-term.
  3. Protect. Separate account, immutable storage.
  4. Alert. Root login, policy changes, deletes.
  5. Query. Investigate by user, resource, time.

Words used above, in simple terms: control plane = APIs that create/change resources · data plane = using the resource itself, e.g. reading an object · forensics = investigating what happened after an incident

Type 7 · Service health and advisors

Definition (say it in an interview): Service health tools report the provider’s own operational events — outages, degradations and scheduled maintenance — personalised to the services and Regions you use; advisors continuously check your configuration and recommend improvements for cost, security, reliability and performance.

In plain words (no jargon): The provider’s own status page for your account, plus automatic tips to save money and be safer.

Analogy: The airline’s flight-status app (is the delay theirs?) plus a mechanic’s checklist that tells you which tyres to change.

How it works internally, step by step

  1. Subscribe. Health alerts to your channel.
  2. Check. First step in every incident.
  3. Review. Advisor weekly.
  4. Act. Ticket each accepted recommendation.
  5. Track. Scores over time.

Words used above, in simple terms: scheduled maintenance = planned provider work that may affect you · personalised health = status filtered to your resources · recommendation = a suggested change with expected benefit

6 Explained part by part

Six things that make monitoring work

Monitoring agent

What it is: Software on VMs that sends OS metrics and logs.

Why it exists: Memory, disk space and app logs are not visible without it.

Where it is used: CloudWatch agent, Azure Monitor Agent, Ops Agent.

Notification channel

What it is: Where alerts go.

Why it exists: An alarm nobody receives is useless.

Where it is used: SNS topic, action group, notification channel.

Log retention

What it is: How long logs are kept.

Why it exists: Cost and compliance.

Where it is used: Never-expire by default in some services — set it.

Tags / labels

What it is: Metadata on resources.

Why it exists: Filter dashboards and costs by app/team.

Where it is used: app=orders, env=prod.

Runbook

What it is: What to do when an alarm fires.

Why it exists: Faster, calmer response.

Where it is used: Linked from the alarm description.

SLO

What it is: A target like 99.9% successful checkouts.

Why it exists: Decides what to alarm on and when to slow releases.

Where it is used: Error budget.

Myth vs reality: things many websites still say

  • Myth: The provider monitors my app.
    Reality: It monitors its infrastructure; your app is yours.
    Proof: Responsibility table.
  • Myth: More alerts = safer.
    Reality: Non-actionable alerts get ignored.
    Proof: Type 4.
  • Myth: CPU tells me if users are happy.
    Reality: Errors and latency do.
    Proof: Golden signals.
7 Deep dive

SLOs and error budgets, MTTx, admin routines, synthetics, costs

SLI, SLO, SLA and error budgets

An SLI is a measured indicator (e.g. % successful checkouts). An SLO is your internal target for it (99.9% per 30 days). An SLA is the contractual promise with penalties (Lesson 5.4). The error budget is 100% − SLO: 99.9% allows about 43 minutes of failures in 30 days. When the budget is spent, teams slow feature releases and fix reliability.

MTTD, MTTA, MTTR

MeasureMeaningImproved by
MTTDmean time to detectsymptom alarms, synthetic checks
MTTAmean time to acknowledgegood routing, on-call rota
MTTRmean time to restorerunbooks, rollbacks, logs + traces, audit trail

Administering the cloud: daily, weekly, monthly

  • Daily: alarms and incidents, failed backups, unusual spend, security findings.
  • Weekly: advisor recommendations, patch status (Systems Manager / Update Manager / VM Manager), access reviews for new admins.
  • Monthly: cost review by tag, quota headroom, alarm review (delete non-actionable ones), restore test of one backup.

Synthetic monitoring

Real-user signals need real users. Synthetic checks (CloudWatch Synthetics canaries, Application Insights availability tests, Cloud Monitoring uptime checks) call your site from outside every minute, so you know it is down at 3 am even with no traffic.

Monitoring costs to watch

Custom metrics (per metric per month), log ingestion (per GB), log retention (per GB-month), high-resolution metrics and dashboards beyond free counts. Free tiers cover labs; production bills are dominated by log volume.

9 Hands-on

Do it yourself, step by step

These labs run on your own cloud account — we cannot run them for you. Each step has three tabs (AWS, Azure, Google Cloud); pick the cloud you have and do both the UI way and the CLI way. Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end. You will set up the full chain: notification channel → logs → an alarm that really fires → audit trail. Everything fits free tiers (Google alerting may cost a few rupees — clean up the same day).

  1. 0 · Get ready: account, budget, CLI

    Pick your cloud.

    UI way — AWS Management Console

    1. Create an AWS account (aws.amazon.com → Create an AWS Account); choose the Free plan while learning.
    2. Never work as root: IAM Identity Center (or IAM) → create an admin user with MFA and sign in as that user.
    3. Billing and Cost Management → Budgets → Create budget → monthly cost budget, e.g. $5, alert by e-mail (Lesson 5.5).
    4. Top-right Region menu → Asia Pacific (Mumbai). Open CloudShell (terminal icon) — the AWS CLI is already signed in there.

    CLI way — the same thing with commands

    aws sts get-caller-identity          # who am I? (must NOT be the root user)
aws configure set region ap-south-1
aws configure list

    You should see: your account ID and an IAM user/role ARN — not “root”.

    UI way — Azure portal

    1. Create a free account at azure.microsoft.com/free (credit for the first 30 days).
    2. Search Cost Management → Budgets → Add → monthly budget, e.g. ₹400, alert at 80%.
    3. Open Cloud Shell (the >_ icon in the top bar) → choose Bash. The Azure CLI is already signed in.

    CLI way — the same thing with commands

    az account show --output table        # subscription in use
az account list-locations --query "[?name=='centralindia'].displayName" -o tsv

    You should see: your subscription name and state “Enabled”, then “Central India”.

    UI way — Google Cloud console

    1. Sign in at console.cloud.google.com and start the free trial (credit for 90 days).
    2. Create a project: project picker → New project → name tiffingo-lab.
    3. Billing → Budgets & alerts → Create budget → e.g. ₹400, alerts at 50/90/100%.
    4. Click Activate Cloud Shell (>_ icon). The gcloud CLI is already signed in.

    CLI way — the same thing with commands

    gcloud config set project tiffingo-lab      # use your real project ID
gcloud config set compute/region asia-south1
gcloud config list

    You should see: your account e-mail, the project and region asia-south1.

    Cloud Shell is the easiest CLI: free, in the browser, already logged in. On your laptop install the AWS CLI v2, Azure CLI or Google Cloud CLI and run aws configure / az login / gcloud init.

  2. 1 · Create an email notification channel

    Pick your cloud.

    UI way — AWS Management Console

    1. Simple Notification Service → Topics → Create topic → Standard, name ops-alerts → Create topic.
    2. Create subscription → protocol Email → your address → open the email and click Confirm subscription.

    CLI way — the same thing with commands

    TOPIC=$(aws sns create-topic --name ops-alerts --query TopicArn --output text)
aws sns subscribe --topic-arn $TOPIC --protocol email --notification-endpoint you@example.com
# confirm the email, then:
aws sns list-subscriptions-by-topic --topic-arn $TOPIC --query "Subscriptions[].[Endpoint,SubscriptionArn]" --output text

    You should see: your email with a real subscription ARN (not PendingConfirmation) after you click the link.

    UI way — Azure portal

    1. Monitor → Alerts → Action groups → Create: resource group rg-ops, name ops-alerts.
    2. Notifications → type Email/SMS message/Push/Voice → tick Email → your address → Review + create.

    CLI way — the same thing with commands

    az group create -n rg-ops -l centralindia
az monitor action-group create -g rg-ops -n ops-alerts --short-name opsalerts \
  --action email me you@example.com
az monitor action-group show -g rg-ops -n ops-alerts --query "emailReceivers[].{name:name,email:emailAddress,status:status}" -o table

    You should see: the receiver listed with status Enabled; Azure sends a “you’ve been added to an action group” email.

    UI way — Google Cloud console

    1. Monitoring → Alerting → Edit notification channels → Email → Add new → address + display name ops-alerts → Save.

    CLI way — the same thing with commands

    gcloud beta monitoring channels create --display-name=ops-alerts --type=email \
  --channel-labels=email_address=you@example.com
gcloud beta monitoring channels list --format="table(name,displayName,labels.email_address)"

    You should see: a channel named projects/…/notificationChannels/… with your email.

    Use a shared team address or chat integration in real life — not one person’s inbox.

  3. 2 · Write logs and search them

    Pick your cloud.

    UI way — AWS Management Console

    1. CloudWatch → Log groups → Create log group tiffingo-orders, retention 1 day.
    2. After the CLI writes events: Logs Insights → select the group → run the query shown in the sketch.

    CLI way — the same thing with commands

    aws logs create-log-group --log-group-name tiffingo-orders
aws logs put-retention-policy --log-group-name tiffingo-orders --retention-in-days 1
aws logs create-log-stream --log-group-name tiffingo-orders --log-stream-name api-1
NOW=$(date +%s000)
cat > events.json <<EOF
[{"timestamp":$NOW,"message":"{\"level\":\"INFO\",\"msg\":\"order placed\",\"order\":\"O-1\"}"},
 {"timestamp":$NOW,"message":"{\"level\":\"ERROR\",\"msg\":\"payment key invalid\",\"order\":\"O-2\"}"}]
EOF
aws logs put-log-events --log-group-name tiffingo-orders --log-stream-name api-1 --log-events file://events.json
sleep 5; aws logs filter-log-events --log-group-name tiffingo-orders --filter-pattern '{ $.level = "ERROR" }' --query "events[].message" --output text

    You should see: only the ERROR line: {"level":"ERROR","msg":"payment key invalid","order":"O-2"} — a JSON filter on structured logs.

    UI way — Azure portal

    1. Every Azure change is logged automatically: Monitor → Activity log → filter resource group rg-ops, last hour — you will see the action group you created.
    2. (Application logs go to a Log Analytics workspace — pay per GB — so the lab uses the free activity log.)

    CLI way — the same thing with commands

    az monitor activity-log list --resource-group rg-ops --offset 1h \
  --query "[].{time:eventTimestamp,op:operationName.localizedValue,by:caller,status:status.value}" -o table

    You should see: rows like “Create or update action group … Succeeded” with your email as caller.

    UI way — Google Cloud console

    1. Logging → Logs Explorer → after the CLI writes entries, run logName:"tiffingo-orders" AND severity>=ERROR.

    CLI way — the same thing with commands

    gcloud logging write tiffingo-orders '{"msg":"order placed","order":"O-1"}' --payload-type=json --severity=INFO
gcloud logging write tiffingo-orders '{"msg":"payment key invalid","order":"O-2"}' --payload-type=json --severity=ERROR
sleep 10; gcloud logging read 'logName:"tiffingo-orders" AND severity>=ERROR' --limit=5 --format="value(timestamp,jsonPayload.msg)"

    You should see: one line with a timestamp and payment key invalid.

    Structured (JSON) logs make queries exact: filter by field, not by guessing words.

  4. 3 · Build an alarm that really fires

    Pick your cloud.

    UI way — AWS Management Console

    1. CloudWatch → Alarms → Create alarm → metric TiffinGo / PaymentErrors (appears after the first put-metric-data) → Greater than 20, 1 of 1 data points, 1 minute → notify ops-alerts.
    2. Push a high value with the CLI and wait 1–3 minutes for the email.

    CLI way — the same thing with commands

    aws cloudwatch put-metric-data --namespace TiffinGo --metric-name PaymentErrors --value 3
aws cloudwatch put-metric-alarm --alarm-name payment-errors-high --namespace TiffinGo --metric-name PaymentErrors \
  --statistic Sum --period 60 --evaluation-periods 1 --threshold 20 --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching --alarm-actions $TOPIC --ok-actions $TOPIC
aws cloudwatch put-metric-data --namespace TiffinGo --metric-name PaymentErrors --value 41
sleep 120; aws cloudwatch describe-alarms --alarm-names payment-errors-high --query "MetricAlarms[0].[StateValue,StateReason]" --output text

    You should see: ALARM Threshold Crossed: 1 datapoint [41.0 …] was greater than the threshold (20.0) and an “ALARM” email. A few minutes later it returns to OK (missing data = not breaching) and sends “OK”.

    UI way — Azure portal

    1. Monitor → Alerts → Create alert rule → scope rg-ops → condition Activity log signal “Delete Virtual Network” → action group ops-alerts.
    2. Create and delete a test VNet to fire it (activity-log alerts are free).

    CLI way — the same thing with commands

    SUB=$(az account show --query id -o tsv)
AG=$(az monitor action-group show -g rg-ops -n ops-alerts --query id -o tsv)
az monitor activity-log alert create -g rg-ops -n vnet-deleted --scope /subscriptions/$SUB/resourceGroups/rg-ops \
  --condition category=Administrative and operationName=Microsoft.Network/virtualNetworks/delete \
  --action-group $AG
az network vnet create -g rg-ops -n test-vnet --address-prefixes 10.80.0.0/16
az network vnet delete -g rg-ops -n test-vnet

    You should see: the alert rule JSON, then within ~5 minutes an email “Activity log alert vnet-deleted” showing who deleted test-vnet.

    UI way — Google Cloud console

    1. Monitoring → Alerting → Create policy → condition Log match on logName:"tiffingo-orders" AND severity=ERROR → channel ops-alerts → notification rate limit 5 minutes.
    2. Write another ERROR log line to fire it. Check current Cloud Monitoring alerting pricing — one policy for a few hours costs at most a few rupees.

    CLI way — the same thing with commands

    P=$(gcloud config get-value project)
CH=$(gcloud beta monitoring channels list --filter='displayName=ops-alerts' --format='value(name)')
cat > policy.json <<EOF
{"displayName":"payment-errors","combiner":"OR",
 "conditions":[{"displayName":"error log","conditionMatchedLog":{"filter":"logName=\\"projects/$P/logs/tiffingo-orders\\" AND severity=ERROR"}}],
 "alertStrategy":{"notificationRateLimit":{"period":"300s"}},"notificationChannels":["$CH"]}
EOF
gcloud alpha monitoring policies create --policy-from-file=policy.json
gcloud logging write tiffingo-orders '{"msg":"payment key invalid","order":"O-3"}' --payload-type=json --severity=ERROR

    You should see: the policy created, then within a few minutes an incident email for payment-errors.

    An alarm you have never seen fire is an alarm you cannot trust — always test the full path to the inbox.

  5. 4 · Find out who changed what (audit trail)

    Pick your cloud.

    UI way — AWS Management Console

    1. CloudTrail → Event history → lookup attribute Event name = CreateTopic or PutMetricAlarm → open an event: user, time, source IP, request parameters.

    CLI way — the same thing with commands

    aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=PutMetricAlarm --max-results 3 \
  --query "Events[].[EventTime,Username,EventName]" --output table

    You should see: your user name and the time you created the alarm. Event history keeps 90 days of management events for free; create a trail to keep more.

    UI way — Azure portal

    1. Monitor → Activity log → filter Operation = “Delete Virtual Network” → open the event → JSON: caller, claims, httpRequest.clientIpAddress.

    CLI way — the same thing with commands

    az monitor activity-log list -g rg-ops --offset 1h \
  --query "[?contains(operationName.value,'virtualNetworks/delete')].{time:eventTimestamp,by:caller,status:status.value}" -o table

    You should see: the delete with your account as caller and status Succeeded.

    UI way — Google Cloud console

    1. Logs Explorer → query logName:"cloudaudit.googleapis.com%2Factivity" → expand an entry → protoPayload.authenticationInfo.principalEmail and methodName.

    CLI way — the same thing with commands

    gcloud logging read 'logName:"cloudaudit.googleapis.com%2Factivity" AND protoPayload.serviceName="monitoring.googleapis.com"' \
  --limit=5 --format="table(timestamp,protoPayload.authenticationInfo.principalEmail,protoPayload.methodName)"

    You should see: your email and methods like google.monitoring.v3.AlertPolicyService.CreateAlertPolicy.

    In real incidents this is step one after “what is broken”: “what changed just before?”

Clean up and cost check

AWS: aws cloudwatch delete-alarms --alarm-names payment-errors-high; aws logs delete-log-group --log-group-name tiffingo-orders; aws sns delete-topic --topic-arn $TOPIC (the custom metric expires by itself). Azure: az group delete -n rg-ops --yes --no-wait (removes the action group and alert rule). Google Cloud: gcloud alpha monitoring policies list --format="value(name)" → gcloud alpha monitoring policies delete <name>; gcloud beta monitoring channels delete <name>; gcloud logging logs delete tiffingo-orders.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Alarms only on CPU.Default metrics are infrastructure.Alarm on user symptoms: errors, latency, failed orders.
Alert fatigue.Every warning pages someone.Page only actionable symptoms; others to dashboards/tickets.
No memory/disk metrics on VMs.Agent not installed.Install CloudWatch agent / Azure Monitor Agent / Ops Agent.
Logs kept forever (or not at all).Default retention never set.Set retention per log group; archive what compliance needs.
Alarm never tested.Created and forgotten.Fire it on purpose (step 3); test after changes.
Audit logs in the same account attackers can reach.Default setup.Central, locked-down log archive account/project.

Interview and viva questions

CloudWatch vs CloudTrail?

CloudWatch = performance metrics, logs, alarms. CloudTrail = API activity / who did what.

Do I need tracing for a single app?

Usually not — logs and metrics suffice; tracing shines with microservices.

How do I avoid alert fatigue?

Page only on actionable user-facing symptoms; review alarms monthly.
