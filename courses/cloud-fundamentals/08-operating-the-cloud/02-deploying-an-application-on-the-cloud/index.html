1 The story

2 Definition

Deploying an application on the cloud

Formal definition (write this in exams)

Deploying an application on the cloud means taking a built, versioned artifact (code package or container image), placing it on a cloud runtime — virtual machines, an application platform, containers or functions — with environment-specific configuration and secrets, and releasing it to users through a strategy such as all-at-once, rolling, blue/green, canary or feature flags, with health checks, monitoring and a rollback path.

In simple words

Putting a new version of your app on cloud servers and moving users to it safely, so you can switch back quickly if something goes wrong.

Say it in an interview

30-second answer you can speak:

  • “I build once, store a versioned artifact, deploy it beside the current version, and release gradually — canary or blue/green — watching error rate and latency, with rollback as a traffic switch.”
  • “On AWS that is Lambda aliases or CodeDeploy; on Azure, App Service slots; on Google Cloud, Cloud Run revision traffic splitting.”

Type 1 · All-at-once (recreate / in-place)

Definition (say it in an interview): An all-at-once (recreate or in-place) deployment replaces the application on every instance at the same time, usually with a short outage, so that all users move from the old version to the new one together; rollback requires deploying the old version again.

In plain words (no jargon): Updating all servers to the new version at the same time.

Analogy: Changing all the bulbs in a hall at once with the main switch off: quick, but the room is dark for a moment, and if the new bulbs are faulty, nobody can see.

How it works internally, step by step

  1. Stop. Take instances out (or accept errors).
  2. Install. Deploy v2 everywhere.
  3. Start. Bring all back.
  4. Verify. Smoke test.
  5. Rollback. Redeploy v1 — slow.

Words used above, in simple terms: in-place = updating the existing servers rather than replacing them · downtime = time when the service is not available · smoke test = quick check that the basics work

Many early outages in companies’ histories came from all-at-once releases on Friday evenings — the origin of the “don’t deploy on Friday” joke.

Real scenario (TiffinGo)

Products and cloud services

For the experienced — did you know? If you must use it, at least keep the previous artifact ready and practise the redeploy — rollback speed is what matters.

Use it when: dev/test environments, or tiny apps where a short outage is acceptable.
Avoid / be careful when: customers use the system continuously — any bug hits 100% of them.

Type 2 · Rolling deployment

Definition (say it in an interview): A rolling deployment updates instances in batches: each batch is removed from the load balancer, updated to the new version, health-checked and returned before the next batch starts, so the service stays available, with old and new versions running side by side during the rollout.

In plain words (no jargon): Updating a few servers at a time while the others keep serving users.

Analogy: Repainting a hotel floor room by room: guests keep staying in the other rooms while a few are being painted.

How it works internally, step by step

  1. Batch size. e.g. 25% or 2 instances.
  2. Drain. Remove from load balancer.
  3. Update. New version.
  4. Check. Health check passes.
  5. Repeat. Next batch; stop on failure.

Words used above, in simple terms: batch = a group of instances updated together · drain = let current requests finish before removing a server · max surge = extra instances allowed during a rollout (Kubernetes)

TiffinGo’s order API on 6 VMs updates 2 at a time; if a batch fails its health check, the rollout stops with 4 VMs still on v1.

Products and cloud services

For the experienced — did you know? Database changes must be backward-compatible (expand → migrate → contract) because v1 and v2 read the same database during the roll.

Use it when: you want no downtime without paying for a full second environment.
Avoid / be careful when: v1 and v2 cannot run together (incompatible database changes) or you need instant rollback.

Type 3 · Blue/green deployment

Definition (say it in an interview): A blue/green deployment runs two identical production environments: “blue” serves live traffic while “green” receives the new version and is tested; traffic is then switched to green in one step (load balancer, DNS or slot swap), and blue is kept for instant rollback.

In plain words (no jargon): Keeping two copies of the system; you test the new copy and then switch all users to it at once.

Analogy: A second stage behind the curtain: the next act is fully set up and rehearsed, then the curtain opens on it in a second — and the old set is still there if needed.

How it works internally, step by step

  1. Clone. Create green identical to blue.
  2. Deploy. v2 to green.
  3. Test. Private URL / slot.
  4. Switch. Router/slot swap.
  5. Keep blue. Rollback = switch back.

Words used above, in simple terms: slot = a separate live copy of an App Service app with its own URL · swap = exchange which copy receives production traffic · CNAME swap = switching a DNS name between environments

Products and cloud services

For the experienced — did you know? Warm up green before the switch (slots can run warm-up requests) — a cold green environment causes a latency spike right after swap.

Use it when: instant, full rollback matters and you can afford a second environment briefly.
Avoid / be careful when: the database cannot serve both versions or the environment is huge and expensive to duplicate.

Type 4 · Canary release

Definition (say it in an interview): A canary release gradually shifts a small percentage of real production traffic to the new version (for example 10% → 50% → 100%), compares its health metrics with the old version at each step, and either promotes it or rolls back, limiting the impact of a bad release to a small share of users.

In plain words (no jargon): Sending only a few users to the new version first, and everyone else after it proves itself.

Analogy: Coal miners carried a canary: if the bird struggled, they left before the gas reached everyone. Here, 10% of requests are the canary.

How it works internally, step by step

  1. Deploy. v2 with 0% traffic.
  2. Shift. 5–10%.
  3. Analyse. Errors, latency, business KPIs.
  4. Step up. 25%, 50%, 100%.
  5. Auto-rollback. Alarm breach → 0%.

Words used above, in simple terms: blast radius = how many users a failure can affect · weighted routing = splitting traffic by percentages · canary analysis = automatic comparison of canary vs baseline

Products and cloud services

Lambda alias weighted routing + CodeDeploy canary, App Service traffic routing, Cloud Run revision traffic split, Container Apps revision weights, Argo Rollouts / Flagger on Kubernetes.

For the experienced — did you know? Pair canaries with automated rollback on alarms (CodeDeploy can do this for Lambda/ECS) — humans watching graphs at 2 am miss things.

Use it when: you want real-user proof with limited blast radius.
Avoid / be careful when: traffic is too low for meaningful comparison (10% of 20 requests tells you nothing) — use longer windows or synthetic tests.

Type 5 · Immutable deployment

Definition (say it in an interview): An immutable deployment never modifies running servers: each release is built into a new machine or container image, new instances are launched from it, and old instances are terminated after traffic moves — eliminating configuration drift and making every environment reproducible.

In plain words (no jargon): Building completely new servers for each version and throwing away the old ones, instead of changing them.

Analogy: Instead of repairing an old phone again and again, you get a new identical phone with everything installed from a backup image.

How it works internally, step by step

  1. Build. Image per release.
  2. Scan. Security scan the image.
  3. Launch. New instances.
  4. Shift. Traffic via LB.
  5. Terminate. Old instances.

Words used above, in simple terms: configuration drift = servers slowly becoming different through manual changes · golden image = a pre-built, approved machine image · instance refresh = Auto Scaling replacing instances with a new template

Products and cloud services

For the experienced — did you know? Pin images by digest (sha256), not just tag — a tag like :latest can point to different bits tomorrow.

Use it when: you want reproducible environments and to stop manual changes on servers.
Avoid / be careful when: you have stateful servers with local data — move data out first.

Type 6 · Feature flags (dark launches)

Definition (say it in an interview): Feature flags (toggles) are runtime switches in code that turn a feature on or off for all users or chosen segments without redeploying; they separate deployment from release, enable dark launches and instant kill switches, and are often combined with canary or A/B testing.

In plain words (no jargon): On/off switches in the app so a new feature can be turned on for some people — or off — without installing a new version.

Analogy: A new dish cooked and ready in the kitchen but not on the printed menu — waiters offer it only to regular customers until the chef is sure.

How it works internally, step by step

  1. Wrap. if flag(“subscription”) …
  2. Deploy. Flag default off.
  3. Target. Staff, city, % of users.
  4. Monitor. Errors and KPIs.
  5. Clean up. Remove the flag after full release.

Words used above, in simple terms: toggle = another word for a feature flag · kill switch = flag to turn a feature off instantly · dark launch = feature in production but hidden

6 Explained part by part

Six things every deployment needs

Artifact

What it is: The built, versioned package (zip or image).

Why it exists: Build once, deploy the same bits everywhere.

Where it is used: ECR / ACR / Artifact Registry, S3/Blob/GCS.

Configuration

What it is: Settings per environment.

Why it exists: Same artifact, different config (12-factor).

Where it is used: Env vars, App Configuration, Parameter Store.

Secrets

What it is: Passwords, API keys.

Why it exists: Never in code or images.

Where it is used: Secrets Manager, Key Vault, Secret Manager.

Health endpoint

What it is: A URL that says “I am ready”.

Why it exists: Platforms decide traffic from it.

Where it is used: /health returning 200.

Traffic router

What it is: Decides which version gets requests.

Why it exists: Enables canary, blue/green, rollback.

Where it is used: Alias weights, slot routing, revision split, LB.

Release record

What it is: Version, time, who, change.

Why it exists: Audit and incident investigation.

Where it is used: Deploy markers, change log.

Myth vs reality: things many websites still say

  • Myth: If it works on my laptop it will work in production.
    Reality: Config, data and scale differ.
    Proof: Canary.
  • Myth: Rollback means rebuilding the old code.
    Reality: Keep the old version deployed; switch traffic.
    Proof: Step 3.
  • Myth: Zero downtime needs Kubernetes.
    Reality: Slots, aliases and revisions do it too.
    Proof: Practical.

Database changes without downtime: expand and contract

  1. Expand: add the new column/table; old code ignores it.
  2. Deploy code that writes both old and new, reads new with fallback.
  3. Migrate existing data in the background.
  4. Contract: after all versions use the new shape, remove the old column.

9 Hands-on

Do it yourself, step by step

Stay inside free tier / credit limits, use the India Region (AWS ap-south-1 Mumbai · Azure Central India · Google asia-south1 Mumbai), and always do the Clean up step at the end.   2. 1 · Write the app and deploy v1

    Pick your cloud.

    UI way — AWS Management Console

    1. Lambda → Create function → Author from scratch, name tiffingo-menu, runtime Python 3.13 → Create.
    2. Paste the handler on the right into the editor → Deploy. Configuration → Environment variables → APP_VERSION=v1.
    3. Function URL comes in step 2 (on an alias), so rollback is a traffic switch.

    CLI way — the same thing with commands

    mkdir menu && cd menu
cat > lambda_function.py <<'EOF'
import os
def lambda_handler(event, context):
    v = os.environ.get("APP_VERSION", "v1")
    return {"statusCode": 200, "headers": {"Content-Type": "text/html"},
            "body": f"<h1>TiffinGo menu {v}</h1><p>Today: paneer thali</p>"}
EOF
zip -q fn.zip lambda_function.py
ROLE=$(aws iam create-role --role-name tiffingo-menu-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"lambda.amazonaws.com"},"Action":"sts:AssumeRole"}]}' --query Role.Arn --output text)
aws iam attach-role-policy --role-name tiffingo-menu-role --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
sleep 10
aws lambda create-function --function-name tiffingo-menu --runtime python3.13 --handler lambda_function.lambda_handler \
  --role $ROLE --zip-file fileb://fn.zip --environment 'Variables={APP_VERSION=v1}'
aws lambda wait function-active-v2 --function-name tiffingo-menu
aws lambda publish-version --function-name tiffingo-menu --query Version --output text

    You should see: 1 — version 1 is an immutable snapshot of code + configuration.

    1. App Services → Create → Web App: name tiffingo-menu-yourname, Code, Python 3.12, Central India, plan Free F1 → Create.

    CLI way — the same thing with commands

    mkdir menu && cd menu

  3. 2 · Deploy v2 beside v1 and release it to 10% (canary)

    Pick your cloud.

    UI way — AWS Management Console

    1. Configuration → set APP_VERSION=v2 → Versions → Publish new version (2).
    2. Aliases → Create alias live → version 1, Weighted alias version 2 at 10%.
    3. Alias → Configuration → Function URL → Create, auth type NONE.

    CLI way — the same thing with commands

    aws lambda update-function-configuration --function-name tiffingo-menu --environment 'Variables={APP_VERSION=v2}'
aws lambda wait function-updated-v2 --function-name tiffingo-menu
aws lambda publish-version --function-name tiffingo-menu --query Version --output text
aws lambda create-alias --function-name tiffingo-menu --name live --function-version 1 \
  --routing-config '{"AdditionalVersionWeights":{"2":0.1}}'
aws lambda add-permission --function-name tiffingo-menu --qualifier live --statement-id url --action lambda:InvokeFunctionUrl \
  --principal '*' --function-url-auth-type NONE
aws lambda add-permission --function-name tiffingo-menu --qualifier live --statement-id url-invoke --action lambda:InvokeFunction \
  --principal '*' --invoked-via-function-url
URL=$(aws lambda create-function-url-config --function-name tiffingo-menu --qualifier live --auth-type NONE --query FunctionUrl --output text)
for i in $(seq 20); do curl -s $URL | grep -o 'menu v[12]'; done | sort | uniq -c

    You should see: about 18 × menu v1 and 2 × menu v2 (random split). Public function URLs need both permissions shown.

    UI way — Azure portal

    1. Slots need Standard S1 or higher: Scale up (App Service plan) → S1 (about ₹8 per hour — scale back to F1 or delete afterwards).
    2. Deployment slots → Add slot staging → deploy v2 there → set staging Traffic % to 10.

    CLI way — the same thing with commands

    PLAN=$(az webapp show -g rg-deploy -n $APP --query appServicePlanId -o tsv)
az appservice plan update --ids $PLAN --sku S1
az webapp deployment slot create -g rg-deploy -n $APP --slot staging --configuration-source $APP
az webapp config appsettings set -g rg-deploy -n $APP --slot staging --slot-settings APP_VERSION=v2
zip -qr app.zip app.py requirements.txt
az webapp deploy -g rg-deploy -n $APP --slot staging --src-path app.zip --type zip
curl -s https://$APP-staging.azurewebsites.net/
az webapp traffic-routing set -g rg-deploy -n $APP --distribution staging=10

    You should see: the v2 heading from the staging URL (tested privately first — blue/green), then 10% of production traffic routed to staging (a cookie keeps each visitor on one side).

    UI way — Google Cloud console

    1. Cloud Run → service → Edit & deploy new revision → variable APP_VERSION=v2, untick Serve this revision immediately → Deploy.
    2. Revisions → Manage traffic → new revision 10%.

    CLI way — the same thing with commands

    gcloud run deploy tiffingo-menu --source . --region asia-south1 --set-env-vars APP_VERSION=v2 --no-traffic --tag green
gcloud run services describe tiffingo-menu --region asia-south1 --format="value(status.traffic)"
NEW=$(gcloud run revisions list --service tiffingo-menu --region asia-south1 --format="value(name)" --limit 1)
gcloud run services update-traffic tiffingo-menu --region asia-south1 --to-revisions $NEW=10
for i in $(seq 20); do curl -s $URL | grep -o "menu v[12]"; done | sort | uniq -c

    You should see: v2 reachable first at its own tag URL (https://green---tiffingo-menu-….run.app) with 0% traffic, then roughly 18 × v1 and 2 × v2.

    Deploy and release are now separate: v2 existed (and was testable) before any user saw it.

  4. 3 · Promote — then roll back in one command

    Pick your cloud.

    UI way — AWS Management Console

    1. Promote: alias live → version 2, remove weighting → Save.
    2. Roll back: alias live → version 1 → Save — instant.

    CLI way — the same thing with commands

    aws lambda update-alias --function-name tiffingo-menu --name live --function-version 2 --routing-config '{}'
curl -s $URL
# something wrong? roll back:
aws lambda update-alias --function-name tiffingo-menu --name live --function-version 1 --routing-config '{}'
curl -s $URL

    You should see: menu v2, then after the rollback menu v1 — no rebuild, no redeploy.

    UI way — Azure portal

    1. Deployment slots → Swap staging ⇄ production → Swap. Production now runs v2; the old v1 sits in staging.
    2. Roll back: swap again.

    CLI way — the same thing with commands

    az webapp traffic-routing clear -g rg-deploy -n $APP
az webapp deployment slot swap -g rg-deploy -n $APP --slot staging --target-slot production
curl -s https://$APP.azurewebsites.net/
# roll back:
az webapp deployment slot swap -g rg-deploy -n $APP --slot staging --target-slot production

    You should see: menu v2 on production after the swap; v1 again after swapping back. (APP_VERSION was a slot setting, so it stayed with each slot’s code.)

    UI way — Google Cloud console

    1. Manage traffic → new revision 100% → Save.
    2. Roll back: old revision 100%.

    CLI way — the same thing with commands

    gcloud run services update-traffic tiffingo-menu --region asia-south1 --to-latest
curl -s $URL
# roll back to the first revision:
OLD=$(gcloud run revisions list --service tiffingo-menu --region asia-south1 --format="value(name)" --sort-by=metadata.creationTimestamp --limit 1)
gcloud run services update-traffic tiffingo-menu --region asia-south1 --to-revisions $OLD=100
curl -s $URL

    You should see: menu v2, then menu v1 after rollback — the old revision was never deleted.

    Rollback is a traffic change measured in seconds because the old version is still deployed.

Clean up and cost check

AWS: aws lambda delete-function --function-name tiffingo-menu (removes versions, alias and URL); detach the policy and delete tiffingo-menu-role. Azure: az group delete -n rg-deploy --yes --no-wait (stops the S1 charge). Google Cloud: gcloud run services delete tiffingo-menu --region asia-south1 --quiet; delete the cloud-run-source-deploy repository in Artifact Registry to avoid storage charges.

10 Mistakes to avoid

Common mistakes, why they happen, how to fix them

Mistake or symptomWhy it happensHow to fix or avoid
Building separately for each environment.Different build commands.Build once; promote the same artifact with different config.
Secrets inside the code or image.Convenience.Secrets Manager / Key Vault / Secret Manager, injected at runtime.
Deleting the old version right after release.Tidiness.Keep it until the new one has proven itself.
Breaking database changes with rolling deploys.v1 and v2 share the DB.Expand → migrate → contract.
Canary without metrics.Nobody compares.Alarm-based automatic rollback.
Manual fixes on production servers.“Just this once.”Immutable deployments; change only through the pipeline.

Interview and viva questions

Canary or blue/green?

Canary tests with real users gradually; blue/green switches all at once after private tests. Both roll back instantly.

Do I need Kubernetes for zero downtime?

No — Lambda aliases, App Service slots and Cloud Run revisions do it.

What are feature flags for?

Releasing features without redeploying, and instant kill switches.
