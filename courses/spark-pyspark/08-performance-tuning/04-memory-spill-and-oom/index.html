Memory, spill and OOM

Spill keeps a job alive; OOM kills it. This lesson explains Spark’s unified memory model, then shrinks memory on purpose to produce real spill and a real OutOfMemoryError, and fixes both without adding memory. All outputs are real (PySpark 4.3.0).

1 The story

“Just give it more memory”

Before you start: cache and storage levels in 3.1, collect and the driver in 4.6, skew in 8.3.

TiffinGo’s “all orders per city” export crashed with java.lang.OutOfMemoryError. The on-call engineer doubled executor memory, and it crashed again the next week. The ranking job never crashed, but the UI showed gigabytes of “spill”.

Kabir

Sir, what is spill? Is it an error?

Arjun Sir

No. When a sort or aggregation fills its share of memory, Spark writes sorted chunks to local disk and merges them later. The job survives, only slower. OOM is when something must stay in memory as one piece and does not fit, like one giant list.

Riya

So more memory is not the answer?

Arjun Sir

Sometimes it is, but usually the fix is smaller pieces of work: more partitions, no giant groups, no collect to the driver. Today we shrink memory on purpose and watch spill and OOM happen. All outputs are real (PySpark 4.3.0).

2 Definition

Unified memory, spill and OOM

Formal definition (write this in exams)

Each executor JVM heap (spark.executor.memory) is split into 300 MB reserved memory, user memory for user data structures, and unified memory of (heap − 300 MB) × spark.memory.fraction (0.6). Unified memory is shared between execution (shuffles, sorts, hash joins and aggregations) and storage (cached blocks, broadcast variables); execution can evict cached blocks above spark.memory.storageFraction. When an operator cannot acquire more execution memory it spills its in-memory data to local disk and merges it later. An OutOfMemoryError happens when an object that cannot be spilled (a single huge row or group, a broadcast table, collected results on the driver) or non-heap usage exceeds the limits; containers can also be killed for exceeding memoryOverhead.

In simple words

Spark gives each executor a heap and uses about 60% of it (after 300 MB) for its own work and cache. When a sort or aggregation runs out of that space, it writes parts to disk and continues: that is spill, slow but safe. An out-of-memory error happens when something must fit in memory at once and does not.

Memory at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A kitchen counter

  • The counter is memory, the store room is disk. When the counter fills, the cook moves trays to the store room and brings them back later: slower, but dinner is served (spill).
  • If one wedding cake is bigger than the whole counter, nothing helps: it falls (OOM).

Intermediate The settings

  • spark.executor.memory (heap), spark.executor.memoryOverhead (off-heap, Python workers; default 10%, min 384 MB), spark.driver.memory, spark.driver.maxResultSize (1g).
  • spark.memory.fraction (0.6) for unified memory, spark.memory.storageFraction (0.5) protected for cache.
  • Spill shows as “Spill (Memory)” and “Spill (Disk)” in the stage page.

Advanced What the lab showed

  • Same sort: 3 GB no spill; 1 GB spilled 736 MiB (91 MiB on disk) and was slower.
  • With 64 partitions instead of 4, the 1 GB run did not spill at all.
  • collect_list per city (8 groups of ~600K strings) killed the 1 GB JVM; per customer (3,999 groups) it passed.

Exam tip: “Difference between spill and OOM?” Spill: an operator (sort, aggregation, join) ran out of execution memory and wrote data to local disk to continue; the job succeeds but slower, visible as Spill (Memory/Disk) in the stage page. OOM: memory needed at once exceeded what is available, e.g. a huge group in collect_list, a large broadcast, or collect() on the driver; fix the cause (more partitions, smaller groups, no collect) before adding memory.

3 Types and ways to use it

Common OOMs and their fixes

SymptomUsual causeFix
Driver OOM after collect() / toPandas()Result too big for the driverWrite to storage; limit; aggregate first (Lesson 4.6)
Driver OOM in a joinBroadcast of a big sideRemove hint / lower threshold (Lesson 8.2)
Executor OOM in one taskSkewed key, giant group (collect_list)Salt, smaller groups, avoid lists (8.3)
Heavy spill, slow stageToo few partitions for the dataMore shuffle partitions / AQE
“Container killed … exceeding memory limits”Off-heap: Python UDFs, Arrow, buffersRaise memoryOverhead; fewer cores per executor

Doubling spark.executor.memory hides the problem until the data doubles again. A single group that must be one Java object (one list, one row, one broadcast) grows with your data and will not fit at some point. Look for the one big thing first. Also note: bigger heaps mean longer garbage-collection pauses; executors of more than ~32–64 GB are rarely a good idea.

4 Step by step

Shrinking memory on purpose

All outputs are real: PySpark 4.3.0, local[2] (in local mode the driver JVM is also the executor, so spark.driver.memory is the heap), AQE off, 4 shuffle partitions. 5,000,000 orders, each with an extra 100-character string column. Spill numbers come from the REST API stage metrics.

  1. Step 1 · How big is unified memory?

    heap = sc._jvm.java.lang.Runtime.getRuntime().maxMemory() / 2**20
print(f"JVM heap {heap:.0f} MiB -> unified pool ~ (heap - 300) * 0.6 = {(heap-300)*0.6:.0f} MiB")
    ##### RUN A: driver 3g driver memory: 3g | memory.fraction: 0.6 (default) | storageFraction: 0.5 (default) JVM heap 3072 MiB -> unified pool ~ (heap - 300) * 0.6 = 1663 MiB
    With 3 GB the pool for execution and storage is about 1.6 GB. With 1 GB it is only 434 MiB, shared by 2 concurrent tasks. That is the budget every sort and aggregation competes for.

  2. Step 2 · The same sort at 3 GB and 1 GB

    wide = o.withColumn("pad", F.repeat(F.lit("x"), 100))
run("orderBy amount (4 partitions)", sink(wide.orderBy("amount")))
    # driver 3g == 1) global sort of 5M wide rows orderBy amount (4 partitions) : 9.09 s, tasks 8, spill mem 0.0 MiB disk 0.0 MiB orderBy amount (64 partitions) : 6.33 s, tasks 68, spill mem 0.0 MiB disk 0.0 MiB # driver 1g == 1) global sort of 5M wide rows orderBy amount (4 partitions) : 10.16 s, tasks 8, spill mem 736.0 MiB disk 91.4 MiB orderBy amount (64 partitions) : 6.54 s, tasks 68, spill mem 0.0 MiB disk 0.0 MiB
    At 3 GB: no spill. At 1 GB the same 4-partition sort spilled 736 MiB from memory, written as 91 MiB on disk (spill files are compressed, so “memory” is always bigger than “disk”), and took 10.16 s instead of 9.09 s. With 64 partitions each task sorted a 16x smaller piece, which fit: no spill even at 1 GB, and faster (6.54 s).

  3. Step 3 · An OutOfMemoryError

    wide.groupBy("city").agg(F.collect_list("pad").alias("l")) \
    .write.format("noop").mode("overwrite").save()
    # driver 1g == 2) collect_list per city (8 huge groups) java.lang.OutOfMemoryError: Java heap space FAILED: driver JVM died -> [Errno 111] Connection refused
    At 3 GB this passed. At 1 GB the JVM died with Java heap space, and Python lost its connection to it. Each city’s list (500K–1M strings of 100 characters, over 100 MB as Java objects) must exist as one value in one task, so it cannot be spilled. More partitions would not help: a group is never split.

  4. Step 4 · Fixing it without more memory

    run("count + sum per city (no list)", sink(wide.groupBy("city").agg(F.count("*"), F.sum("amount"))))
run("collect_list per customer",      sink(wide.groupBy("customer_id").agg(F.collect_list("pad"))))
run("top-5 per city via window",      sink(o.withColumn("r", F.row_number().over(w)).filter("r<=5")))
    == 3) fixes at 1g count + sum per city (no list) : 3.44 s, tasks 6, spill mem 0.0 MiB disk 0.0 MiB collect_list per customer (3999 small groups): 5.49 s, tasks 6, spill mem 192.1 MiB disk 1.2 MiB top-5 per city via window, not list : 5.62 s, tasks 6, spill mem 304.0 MiB disk 51.6 MiB
    Same 1 GB. Asking what is actually needed fixed it: count and sum need no list (3.44 s, no spill). Lists per customer are 3,999 small groups, so they spilled safely (192 MiB) and finished. And “top 5 per city” is a window plus a filter, which spills instead of crashing. Memory was the symptom; the giant group was the cause.

6 Real-world use

Memory tuning at work

1. Spill reviews

Stages where spill exceeds shuffle size get more partitions or a larger advisory size.

Spill metric→more partitions→No spill

2. Executor sizing

Platform teams pick 4–5 cores and 16–32 GB per executor so each task gets enough memory.

Node→cores + memory→Executor shape

3. Driver protection

maxResultSize stops accidental collects from killing shared notebooks.

collect()→maxResultSize→Clear error

4. Python-heavy jobs

Pandas UDF jobs set memoryOverhead explicitly instead of relying on the 10% default.

Pandas UDF→overhead 2–4 GB→Stable

5. Cache budgets

Cached tables are checked in the Storage tab so they do not starve execution memory.

cache()→Storage tab→Room for joins

Run the code: executor memory layout

Compute how an executor heap is divided. Press Run, then try the challenges.

# Spark executor memory layout (unified memory model)
heap_mb = 8 * 1024            # spark.executor.memory = 8g
fraction = 0.6                # spark.memory.fraction
storage_fraction = 0.5        # spark.memory.storageFraction
cores = 4                     # spark.executor.cores

usable = heap_mb - 300
unified = usable * fraction
print("user memory      :", round(usable * (1 - fraction)), "MB")
print("unified          :", round(unified), "MB")
print("protected storage:", round(unified * storage_fraction), "MB")
print("execution / task :", round(unified / cores), "MB (if no cache)")
print("overhead         :", max(384, round(heap_mb * 0.10)), "MB off-heap")
user memory : 3157 MB unified : 4735 MB protected storage: 2368 MB execution / task : 1184 MB (if no cache) overhead : 819 MB off-heap

  • print("execution / task :", round(unified / cores), "MB (if no cache)")Concurrent tasks share execution memory; each gets between 1/(2N) and 1/N of it.

9 Quiz and revision

Check yourself

Quick revision

Lesson 8.4 in one screen

  • Heap: 300 MB reserved, user (40%), unified (60%) = execution + storage.
  • Spill: execution memory full → sorted runs on disk; slow, not fatal.
  • Lab: 1 GB sort spilled 736 MiB (91 MiB disk); 64 partitions removed it.
  • OOM: an unspillable object (huge group, broadcast, collect) does not fit.
  • collect_list per city OOMed at 1 GB; per customer and window top-5 worked.
  • Python/Arrow memory is off-heap: spark.executor.memoryOverhead.
  • Fix the big thing first; then size memory. Avoid huge heaps (GC).

Interview and viva questions

How much executor memory should I give?

Common shapes are 4–5 cores with 16–32 GB per executor, then tune from spill and GC time in the UI.

Is spill always bad?

No. Some spill is normal for big sorts; worry when spill is many times the shuffle size or the stage is dominated by it.

What is GC time in the UI?

Time the JVM spent in garbage collection; above ~10% of task time suggests memory pressure or too many objects.

Does caching cause OOM?

Rarely; cached blocks are evicted or stored on disk depending on the storage level, but they reduce memory for execution.

Why does the driver need memory?

It holds plans, broadcast tables while building them, collected results and accumulators; keep heavy data off it.

Real-world scenario questions (asked in company interviews)

Any company · SparkFresher

“What is spill?”

Explain spill in Spark.

The interviewer is checking: is it an error?

Show a strong answer

When a sort, join or aggregation runs out of execution memory, Spark writes sorted chunks to local disk and merges them later. The job continues, slower. It appears as Spill (Memory) and Spill (Disk) in the stage page.

Avoid: Calling spill a failure.

Data engineeringMid-level

Heavy spill

A stage spills 50 GB for a 10 GB shuffle.

The interviewer is checking: what to do?

Show a strong answer
  • Increase shuffle partitions or the AQE advisory size so tasks are smaller.
  • Check for skew (one task spilling most).
  • Then consider executor memory or fewer cores per executor.

Avoid: Only adding memory.

Data engineeringMid-level

Executor OOM

One task fails with Java heap space.

The interviewer is checking: diagnose?

Show a strong answer
  1. Find the operation: collect_list, big row, broadcast, UDF state.
  2. Check task metrics for skew.
  3. Replace giant groups; salt; write partitioned output.

Avoid: Retrying with the same config.

PlatformSenior

Executor shape

Choose executor size for 64-core, 256 GB nodes.

The interviewer is checking: reasoning?

Show a strong answer
  • ~5 cores per executor → 12 executors per node (leave OS/daemon cores).
  • ~18 GB heap + overhead each, leaving node headroom.
  • Validate with spill, GC time and container kills.

Avoid: One giant executor per node.
