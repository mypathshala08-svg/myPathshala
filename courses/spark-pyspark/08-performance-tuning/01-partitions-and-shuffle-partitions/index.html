Partitions and shuffle partitions

Every partition is a task. This lesson measures how Spark picks input partitions, what 2,000 small files cost, the U-shaped curve of spark.sql.shuffle.partitions, and how repartition and coalesce place rows. All outputs are real (PySpark 4.3.0).

1 The story

Before you start: partitions and the shuffle in 2.4, small files in 5.3, AQE in 7.4.

TiffinGo’s nightly revenue job got slower after a new engineer set spark.sql.shuffle.partitions=2000 “for safety” and another job left 2,000 tiny Parquet files behind. Nothing failed; everything just crawled.

2 Definition

Partitions and shuffle partitions

Formal definition (write this in exams)

A partition is a chunk of a DataFrame processed by one task on one executor core. For file sources, Spark packs files into input partitions of at most spark.sql.files.maxPartitionBytes (128 MB by default), counting each file as at least spark.sql.files.openCostInBytes (4 MB) and spreading small inputs across defaultParallelism. After a wide transformation (groupBy, join, orderBy, window), the data is redistributed into spark.sql.shuffle.partitions partitions (200 by default), which Adaptive Query Execution can coalesce at run time. repartition() shuffles to a new number (optionally by column hash); coalesce() merges partitions without a shuffle and can only reduce the count.

In simple words

Spark splits data into partitions, and each partition becomes one task on one core. File reading decides the first partitions; every shuffle creates a new set (200 by default). Too few partitions leave cores idle or make tasks huge; too many add overhead for each tiny task.

Partitions at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Cutting a big pizza

  • Four friends, one pizza: four slices is perfect. One slice means three friends wait; 2,000 slices means everyone spends the evening picking crumbs.
  • A partition is a slice of data, a task is one friend eating it, a core is one friend.

Intermediate The settings

  • Reading files: spark.sql.files.maxPartitionBytes (128 MB) and spark.sql.files.openCostInBytes (4 MB).
  • After a shuffle: spark.sql.shuffle.partitions (200), merged by AQE (Lesson 7.4).
  • In code: repartition(n), repartition(n, col), coalesce(n), df.rdd.getNumPartitions().

Advanced What the lab showed

  • Same data: 2,000 small files took 4.06 s, 8 normal files 0.20 s (64 vs 5 tasks).
  • groupBy with AQE off: 16 partitions 1.82 s, 200 partitions 2.50 s, 2,000 partitions 8.13 s.
  • repartition(8, "city") filled only 6 partitions, unevenly (0.5M to 1.5M rows).

Exam tip: “How do you choose the number of partitions?” Aim for tasks of roughly 100–200 MB of input (or shuffle data) each and at least 2–3 tasks per core. Keep input files near 128 MB–1 GB, set spark.sql.shuffle.partitions high enough for the largest data and let AQE coalesce, use coalesce to reduce partitions before writing and repartition to increase them or redistribute by key.

coalesce(1) before a write looks harmless, but it also pulls the work before it into one task, because coalesce does not add a stage boundary. On a real cluster with many cores that turns a parallel job into a single-threaded one. If you need one output file after heavy work, prefer repartition(1) (one extra shuffle, but the heavy part stays parallel).

4 Step by step

Measuring partition counts

All outputs are real: PySpark 4.3.0, local[4] on a machine with 2 physical CPUs, 5,000,000 orders in 8 Parquet files (34.6 MiB). Tasks are counted from the Spark REST API; every timing is a warm run.

  1. Step 1 · Input partitions follow file size

    print(sc.defaultParallelism, spark.conf.get("spark.sql.files.maxPartitionBytes"))
for mpb in ("128MB", "16MB", "4MB"):
    spark.conf.set("spark.sql.files.maxPartitionBytes", mpb)
    print(mpb, spark.read.parquet(P).rdd.getNumPartitions())
    files: 8 | size MiB: 34.6 defaultParallelism: 4 | maxPartitionBytes: 134217728b == 1) input partitions follow file size maxPartitionBytes 128MB: 4 partitions maxPartitionBytes 16MB : 4 partitions maxPartitionBytes 4MB : 16 partitions
    With 128 MB and 16 MB we still got 4 partitions: Spark also divides small inputs across the 4 cores (34.6 MiB / 4 ≈ 8.7 MB per split), so the cap did not matter. Only when the cap fell below that (4 MB) did the count rise to 16.

  2. Step 2 · The small-files problem

    spark.read.parquet(P).repartition(2000).write.parquet(small)   # 2,000 files
d = spark.read.parquet(small)
run("count over 2000 small files", lambda: d.agg(F.sum("amount")).collect())
run("count over 8 normal files",   lambda: big.agg(F.sum("amount")).collect())
    == 2) many small files 2000 files -> 63 partitions (files packed, openCostInBytes 4194304b ) count over 2000 small files : 4.06 s, tasks 64, spill 0.0 MiB count over 8 normal files : 0.20 s, tasks 5, spill 0.0 MiB
    Exactly the same rows. Spark packed the 2,000 files into 63 partitions (each file is charged 4 MB of “open cost”), but still had to open 2,000 files and read 2,000 footers: 4.06 s vs 0.20 s, 20x slower. On S3 or ADLS each open is a network request, so the gap is bigger. Fix it at write time (Lesson 5.3) or compact the files.

  3. Step 3 · Shuffle partitions from 1 to 2,000

    spark.conf.set("spark.sql.adaptive.enabled", "false")   # see the raw effect
q = lambda: big.groupBy("customer_id", "order_date").agg(F.sum("amount")) \
                .write.format("noop").mode("overwrite").save()
for n in (1, 4, 16, 200, 2000):
    spark.conf.set("spark.sql.shuffle.partitions", n); q(); run(f"... {n}", q)
    == 3) shuffle partitions (AQE off to see the raw effect) groupBy, shuffle.partitions=1 : 2.55 s, tasks 5, spill 0.0 MiB groupBy, shuffle.partitions=4 : 1.93 s, tasks 8, spill 0.0 MiB groupBy, shuffle.partitions=16 : 1.82 s, tasks 20, spill 0.0 MiB groupBy, shuffle.partitions=200 : 2.50 s, tasks 204, spill 0.0 MiB groupBy, shuffle.partitions=2000 : 8.13 s, tasks 2004, spill 0.0 MiB groupBy, 200 + AQE : 2.23 s, tasks 8, spill 0.0 MiB
    A U-shaped curve. 1 partition: one core does all the reduce work (2.55 s). 4–16: best (1.82 s). 200: 204 tasks, mostly tiny (2.50 s). 2,000: 2,004 tasks and 2,000 shuffle files per map task: 8.13 s, 4.5x slower than the best. With AQE on, the 200 were coalesced to 8 tasks automatically.

  4. Step 4 · How rows land in partitions

    count = lambda d: sorted(d.groupBy(F.spark_partition_id()).count().rdd.map(lambda x: x[1]).collect())
print(count(big.repartition(8)))
print(count(big.repartition(8, "city")))
print(count(big.coalesce(2)))
    == 4) rows per partition repartition(8): [625000, 625000, 625000, 625000, 625000, 625000, 625000, 625000] repartition(8, city): [498646, 500086, 500552, 998365, 1000215, 1502136] coalesce(2): [2500000, 2500000]
    repartition(8) is round-robin: perfectly even. repartition(8, "city") hashes 8 cities into 8 buckets, but two cities collided and two buckets stayed empty: 6 partitions, from 0.5M to 1.5M rows. Hash partitioning on a low-cardinality column is uneven by nature. coalesce(2) just glued neighbours together.

  5. Step 5 · coalesce(1) vs repartition(1)

    h = lambda d: d.select(F.sha2(F.col("order_id").cast("string"), 256))
run("4 partitions",       lambda: sink(h(big)))
run("after coalesce(1)",  lambda: sink(h(big.coalesce(1))))
run("after repartition(1)", lambda: sink(h(big.repartition(1))))
    == 5) coalesce(1) before a heavy step heavy UDF-free calc, 4 partitions : 2.28 s, tasks 4, spill 0.0 MiB same after coalesce(1) : 2.12 s, tasks 1, spill 0.0 MiB same after repartition(1) : 3.02 s, tasks 5, spill 0.0 MiB
    Look at the task counts: coalesce(1) ran everything as 1 task; repartition(1) ran 4 parallel tasks for the hashing and then 1 to gather (5 tasks). Here coalesce was not slower, because the hash is cheap and our machine has only 2 physical CPUs. With an expensive step on a 100-core cluster, that single task is the whole job. Read the task count, not one timing.

6 Real-world use

Partition tuning at work

1. Nightly ETL

Shuffle partitions sized from the largest day’s shuffle data; AQE merges them on quiet days.

Shuffle size→÷ 128 MB→Partition count

2. Data lake compaction

Scheduled jobs rewrite small files into large ones so every reader gets faster.

Small files→repartition + write→Big files

3. Partitioned writes

repartition by the partition column before partitionBy keeps one file per folder instead of one per task.

repartition(col)→partitionBy(col)→Few files

4. Calling slow APIs

Increase partitions before a mapPartitions step that calls an external service, to raise concurrency.

Few partitions→repartition(64)→More calls in flight

5. Single-file exports

Small final results are written with repartition(1) after the heavy work is done.

Heavy work→repartition(1)→One CSV

Run the code: sizing shuffle partitions

A simple rule of thumb used by many teams. Press Run, then try the challenges.

# How many shuffle partitions? (simplified sizing rule)
shuffle_gb = 300            # shuffle write size seen in the Spark UI
target_mb = 128             # aim per task
cores = 200                 # executor cores in the cluster

by_size = shuffle_gb * 1024 // target_mb
by_cores = cores * 3        # at least 2-3 tasks per core
print("by size :", by_size)
print("by cores:", by_cores)
print("use     :", max(by_size, by_cores))

9 Quiz and revision

Check yourself

Quick revision

Lesson 8.1 in one screen

  • Partition = task = one core at a time.
  • Input splits: maxPartitionBytes (128 MB), openCostInBytes (4 MB), cores.
  • Small files: 2,000 files 4.06 s vs 8 files 0.20 s.
  • Shuffle partitions: U-curve; 16 → 1.82 s, 2,000 → 8.13 s; AQE 200 → 8 tasks.
  • Aim for ~128 MB per task and 2–3 tasks per core.
  • repartition(n, col) hashes; low cardinality = uneven or empty partitions.
  • coalesce(1) pulls upstream work into one task; prefer repartition(1) after heavy work.

Interview and viva questions

Should I always change spark.sql.shuffle.partitions?

Set it high enough for your biggest shuffle and let AQE coalesce it; on small data the default 200 with AQE is fine.

What is a good task duration?

Usually from a few seconds to a few minutes. Many tasks under 100 ms mean too many partitions; tasks of tens of minutes mean too few or skew.

Does repartition before a write help?

Yes, when you need fewer, bigger files or one file per output folder; it costs one shuffle.

Why does getNumPartitions differ from the files count?

Spark splits big files and packs small ones together into splits.

How does this work on Databricks?

Same settings; Databricks also offers auto-optimized shuffle and auto compaction on Delta tables.

Real-world scenario questions (asked in company interviews)

Partition sizing comes up in nearly every Spark performance interview.

Any company · SparkFresher

“repartition vs coalesce?”

Explain the difference.

The interviewer is checking: shuffle?

Show a strong answer

repartition(n) does a full shuffle and can increase or decrease partitions, giving even partitions (or hashed by a column). coalesce(n) merges existing partitions without a shuffle and can only decrease them; it may leave them uneven and can pull upstream work into fewer tasks.

Avoid: Saying coalesce is always better because it avoids a shuffle.

Data engineeringMid-level

Thousands of tiny tasks

A job’s stages each show 2,000 tasks of 20 ms.

The interviewer is checking: what to change?

Show a strong answer
  • Lower shuffle partitions to fit data size, or rely on AQE coalescing.
  • Check input file counts; compact small files.
  • In my test 2,000 → 16 partitions took 8.13 s → 1.82 s.

Avoid: Adding executors.

Data engineeringMid-level

Small files

Reads of a table are slow although it is only 30 GB.

The interviewer is checking: diagnose?

Show a strong answer
  1. Count files and average file size.
  2. Compact into 128 MB–1 GB files (repartition + overwrite, or OPTIMIZE).
  3. Fix the writer: repartition by partition columns before writing.

Avoid: Increasing maxPartitionBytes only.

PlatformSenior

Default settings

Set partition defaults for 300 batch jobs.

The interviewer is checking: strategy?

Show a strong answer
  • AQE on with a 64–256 MB advisory size; shuffle partitions sized for the biggest jobs.
  • Writers produce right-sized files; compaction for streaming outputs.
  • Dashboards on task duration and file size distributions.

Avoid: One hand-tuned number per job.
