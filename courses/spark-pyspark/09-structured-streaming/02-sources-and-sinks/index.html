Sources and sinks

Every streaming query reads from a source and writes to a sink. This lesson reads a real Kafka topic, parses its binary values, rate-limits batches with maxOffsetsPerTrigger, and writes to Parquet, PostgreSQL via foreachBatch, another Kafka topic and the console. All outputs are real (PySpark 4.3.0, Kafka 3.9).

1 The story

“Orders are in Kafka. Now what?”

Before you start: streaming basics in 9.1, JSON and schemas in 5.1, JDBC in 5.4.

TiffinGo’s app publishes every order as a JSON event to a Kafka topic. Three teams want it: analytics wants Parquet files in the lake, finance wants city totals in PostgreSQL, and the fraud team wants big orders on a separate topic.

Kabir

Sir, Kafka gives us bytes. How does Spark know what an order looks like?

Arjun Sir

The Kafka source always gives the same columns: key, value, topic, partition, offset, timestamp. You cast value to a string and parse the JSON with a schema. The offsets are what Spark stores in the checkpoint to know where it stopped.

Riya

And one stream can feed three sinks?

Arjun Sir

Each sink is its own streaming query with its own checkpoint. Today we run a real Kafka broker, control batch sizes with maxOffsetsPerTrigger, and write to files, PostgreSQL, Kafka and the console. All outputs are real (PySpark 4.3.0, Kafka 3.9).

2 Definition

Streaming sources and sinks

Formal definition (write this in exams)

A streaming source provides new data for each micro-batch together with offsets that identify its position. For end-to-end fault tolerance a source must be replayable: given offsets recorded in the checkpoint, it can return exactly the same data again (Kafka, files and table formats are; the socket source is not). A sink receives the result of each micro-batch. The file sink and table sinks are idempotent: they record committed batches in a log, so a replayed batch is not written twice. The Kafka sink is at-least-once. foreachBatch passes each micro-batch as a normal DataFrame with its batch_id to a user function, so any batch writer (JDBC, MERGE, multiple outputs) can be used; exactly-once then depends on making that function idempotent.

In simple words

A source gives Spark new data and a position (offset) so it can resume; a sink receives each batch’s results. Kafka and files can be replayed, so after a failure Spark re-reads the same data. File sinks ignore duplicate batches. With foreachBatch you can write each batch anywhere using the normal DataFrame writer.

Sources and sinks at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A courier hub

  • Parcels arrive on numbered conveyor belts (Kafka partitions); each parcel has a sticker number (offset).
  • The hub writes down the last sticker number it handled on each belt, so after a power cut it starts from the next one.
  • Outgoing vans are sinks: some can safely receive the same parcel twice (idempotent), some cannot.

Intermediate The API

  • Sources: kafka, files (json, csv, parquet, …), rate, socket (testing), Delta/Iceberg tables.
  • Sinks: files, kafka, foreachBatch, foreach, console and memory (debugging), tables via toTable.
  • Kafka options: kafka.bootstrap.servers, subscribe, startingOffsets, maxOffsetsPerTrigger.

Advanced What the lab showed

  • maxOffsetsPerTrigger=250 gave batches of 248, 248 and 104 rows (split across 3 partitions).
  • The Parquet sink wrote 600 rows in 9 files; foreachBatch wrote 3 city rows per batch to PostgreSQL.
  • The Kafka sink needed only key and value columns; 50 orders ≥ 450 reached big_orders.

Exam tip: “How do you read Kafka in Structured Streaming?” spark.readStream.format("kafka").option("kafka.bootstrap.servers", …).option("subscribe", topic).load(), then CAST(value AS STRING) and from_json with a schema. Control batch size with maxOffsetsPerTrigger and the first position with startingOffsets; offsets are stored in the checkpoint so restarts resume exactly. For sinks without native support, use foreachBatch and make it idempotent.

startingOffsets is read only when the checkpoint is new. Changing it to "earliest" on a running query to “reprocess everything” does nothing; you need a new checkpoint location. Also, Kafka support is not bundled with PySpark: add the spark-sql-kafka-0-10 package (and its dependencies) with --packages or --jars, or you get KAFKA_DATA_SOURCE_NOT_ENABLED.

4 Step by step

Kafka in, four sinks out

All outputs are real: PySpark 4.3.0, local[2], Apache Kafka 3.9 in Docker with a 3-partition topic orders, PostgreSQL 16 for the JDBC sink. Each sink is a separate query with its own checkpoint, run with availableNow so it stops when the topic is drained.

  1. Step 1 · Produce and look at the Kafka schema

    ev.write.format("kafka").option("kafka.bootstrap.servers", K).option("topic", "orders").save()   # 600 JSON events
raw = (spark.readStream.format("kafka").option("kafka.bootstrap.servers", K).option("subscribe", "orders")
         .option("startingOffsets", "earliest").option("maxOffsetsPerTrigger", 250).load())
raw.printSchema()
    == 1) produce 600 order events to Kafka topic 'orders' (3 partitions) == 2) read the topic as a stream: fixed Kafka schema root |-- key: binary (nullable = true) |-- value: binary (nullable = true) |-- topic: string (nullable = true) |-- partition: integer (nullable = true) |-- offset: long (nullable = true) |-- timestamp: timestamp (nullable = true) |-- timestampType: integer (nullable = true)

  2. Step 2 · File sink with a rate limit

    q = (orders.writeStream.format("parquet").option("path", D + "/out92")
        .option("checkpointLocation", D + "/ck92/files").trigger(availableNow=True).start())

    With maxOffsetsPerTrigger=250 the 600 messages were split into 3 batches (248, 248, 104; the limit is divided across partitions). The endOffset per partition is what goes into the checkpoint. The Parquet sink wrote 600 rows in 9 files (3 batches × 3 partitions) and keeps a _spark_metadata log so readers see only committed files.

  3. Step 3 · foreachBatch to PostgreSQL

    def to_pg(df, batch_id):
    out = df.groupBy("city").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")) \
            .withColumn("batch_id", F.lit(batch_id))
    out.write.jdbc(url, "city_rev_stream", mode="append", properties=props)
q2 = orders.writeStream.foreachBatch(to_pg).option("checkpointLocation", …).trigger(availableNow=True).start()
    == 4) foreachBatch -> PostgreSQL (one JDBC write per micro-batch) foreachBatch batch_id=0: 248 rows -> 3 city rows foreachBatch batch_id=1: 248 rows -> 3 city rows foreachBatch batch_id=2: 104 rows -> 3 city rows +------+------+-------+ | city|orders|revenue| +------+------+-------+ | Delhi| 200| 43100| |Mumbai| 200| 43200| | Pune| 200| 43400| +------+------+-------+
    Inside foreachBatch, df is a normal DataFrame: you can aggregate it and use the batch JDBC writer, which has no streaming version. Each batch wrote 3 city rows tagged with its batch_id; summing them gives 200 orders per city. Because this is a plain append, a replayed batch would be written twice: Lesson 9.5 shows the crash and the fix.

  4. Step 4 · Kafka sink and the console

    big = orders.filter("amount >= 450").select(F.col("order_id").cast("string").alias("key"),
                                            F.to_json(F.struct("order_id", "city", "amount")).alias("value"))
big.writeStream.format("kafka").option("kafka.bootstrap.servers", K).option("topic", "big_orders") \
   .option("checkpointLocation", …).trigger(availableNow=True).start()
    == 5) Kafka sink: enrich and write to topic 'big_orders' messages in big_orders: 50 +---+---------------------------------------------+ |k |v | +---+---------------------------------------------+ |450|{"order_id":450,"city":"Mumbai","amount":450}| |455|{"order_id":455,"city":"Delhi","amount":455} | +---+---------------------------------------------+ only showing top 2 rows == 6) console sink (debugging) ------------------------------------------- Batch: 0 ------------------------------------------- +---------+------+--------+------+------+ |partition|offset|order_id| city|amount| +---------+------+--------+------+------+ | 0| 0| 300|Mumbai| 300| | 0| 1| 301| Pune| 301| | 0| 2| 304| Pune| 304| +---------+------+--------+------+------+
    The Kafka sink expects a value column (string or binary) and optionally key; we serialised the row back to JSON. 50 big orders reached big_orders, readable as a batch. The console sink prints each batch; handy while developing, useless in production.

Sources and sinks at work

App events flow from Kafka into partitioned lake tables every minute.

Landing folder→file source→Clean table

Run the code: Kafka messages and offsets

What Spark does with each Kafka message and offset. Press Run, then try the challenges.

# Parsing Kafka messages (what from_json does for each row)
import json
messages = [
    (0, 0, b'{"order_id": 300, "city": "Mumbai", "amount": 300}'),
    (0, 1, b'{"order_id": 301, "city": "Pune", "amount": 301}'),
    (1, 0, b'{"order_id": 1, "city": "Pune", "amount": 1}'),
]
for partition, offset, value in messages:
    o = json.loads(value.decode("utf-8"))        # CAST(value AS STRING) + from_json
    print(partition, offset, o["order_id"], o["city"], o["amount"])

last = {}
for p, off, _ in messages:
    last[p] = off + 1                            # next offset to read, per partition
print("offsets to store in the checkpoint:", last)
0 0 300 Mumbai 300 0 1 301 Pune 301 1 0 1 Pune 1 offsets to store in the checkpoint: {0: 2, 1: 1}
  • o = json.loads(value.decode("utf-8")) # CAST(value AS STRING) + from_jsonKafka values are bytes; you decide how to decode and parse them.
  • last[p] = off + 1 # next offset to read, per partitionOffsets are tracked per partition; this is what makes Kafka replayable.

9 Quiz and revision

Check yourself

Quick revision

Lesson 9.2 in one screen

  • Kafka source: key, value (binary), topic, partition, offset, timestamp.
  • Parse with from_json(CAST(value AS STRING), schema).
  • maxOffsetsPerTrigger limits batch size (248/248/104).
  • File sinks: exactly-once via _spark_metadata; Kafka sink: at-least-once.
  • foreachBatch(df, batch_id) lets you use any batch writer.
  • One query + one checkpoint per sink.
  • startingOffsets only applies to a new checkpoint.

Interview and viva questions

Do I need a schema registry for Avro/Protobuf?

Spark has from_avro/from_protobuf; with a registry you usually strip the wire-format header or use a platform integration.

Can one query write to two sinks?

Use foreachBatch and write the batch twice (cache it first), or start two queries.

How do I write to a Delta or Iceberg table?

writeStream.format("delta") / toTable("name"); both are idempotent table sinks.

What does failOnDataLoss do?

Fails the query if offsets it needs were deleted by Kafka retention; set false only if losing data is acceptable.

Is foreach different from foreachBatch?

foreach calls your writer per row (open/process/close); foreachBatch gives a whole DataFrame per batch and is usually simpler and faster.
