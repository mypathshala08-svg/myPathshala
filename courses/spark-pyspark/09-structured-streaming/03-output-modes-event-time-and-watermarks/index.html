Output modes, event time and watermarks

Events arrive late and out of order. This lesson aggregates orders into 5-minute event-time windows over five controlled micro-batches and shows exactly what complete, update and append modes write, and how a watermark finalises windows, drops very late data and bounds state. All outputs are real (PySpark 4.3.0).

1 The story

“The 10:00 numbers changed at 10:25”

Before you start: streaming basics in 9.1, sources and foreachBatch in 9.2, dates and timestamps in 6.4.

TiffinGo’s live dashboard showed revenue per 5-minute window. Rider phones without network uploaded orders late, so the 10:00 window kept changing long after 10:05. Finance asked a simple question: when is a window final?

Kabir

Sir, why not group by the time the event reaches Kafka? Then nothing is late.

Arjun Sir

Then a phone that was offline would put a 10:02 order into the 10:25 window: wrong revenue. We group by event time, the time inside the record. Late data is normal; the question is how long to wait for it.

Riya

And Spark waits forever?

Arjun Sir

Without a watermark, yes: it keeps every window in state and can update any of them. With a watermark it can finalise windows, drop data that is too late, and free memory. Today we see this batch by batch, in all three output modes. All outputs are real (PySpark 4.3.0).

2 Definition

Output modes, event time and watermarks

Formal definition (write this in exams)

Event time is the timestamp embedded in a record, as opposed to processing time when Spark sees it. Event-time aggregations such as groupBy(window("event_time", "5 minutes")) keep per-window state across micro-batches so late, out-of-order records update the right window. A watermark, defined with withWatermark(col, delay), is computed as the maximum event time seen minus the delay; Spark guarantees that records newer than the watermark are processed, may drop records older than it, and removes state for windows that end before it. The output mode controls what each micro-batch writes: complete rewrites the whole result table, update writes only rows changed in this batch, and append writes only rows that will never change again, which for aggregations requires a watermark.

In simple words

Event time is when something really happened. Spark keeps window results in memory so late events can still be added. A watermark says “I will wait this long for late data”: after that a window is final, it can be written once, and its memory is freed. Output modes decide whether you write everything, only changes, or only final rows.

Event time at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Exam papers by post

  • Papers are dated when written (event time) but arrive by post over days (processing time).
  • The examiner announces: “I will accept papers up to 5 days after the latest date I have seen.” That rule is the watermark. Results are published once a date is safely past it.

Intermediate The API

  • df.withWatermark("event_time", "5 minutes") before a stateful operation.
  • groupBy(F.window("event_time", "5 minutes")) for event-time windows.
  • writeStream.outputMode("append" | "update" | "complete").

Advanced What the lab showed

  • append on an aggregation without watermark: STREAMING_OUTPUT_MODE.UNSUPPORTED_OPERATION.
  • With the watermark, each window was emitted once, when the watermark passed its end; state shrank to 2 rows.
  • A 10:03 order arriving after the 10:00 window was finalised was dropped (numRowsDroppedByWatermark = 1); without a watermark it changed 1419 to 9196.

Exam tip: “What is a watermark?” A threshold on event time, max(event_time) − allowed delay, that tells Spark how long to wait for late data. Windows ending before it are finalised: emitted in append mode and removed from state; records older than it may be dropped. It bounds state for streaming aggregations, deduplication and stream-stream joins, and is required for append mode with aggregations.

A watermark is a lower bound on what is kept, not an exact cut-off. In our run a 10:02 order arrived in the same batch that closed its window and was still counted, but a 10:03 order arriving one batch later was dropped. And append mode adds latency: a window is written only after the watermark passes its end, so the 10:00 window appeared two batches after its last event. Pick the delay from how late your data really is, not from how fast you want results.

7 Run the code

Run the code: a watermark in miniature

A simplified model of the lab’s append run. Press Run, then try the challenges.

# A watermark, batch by batch (5-minute windows, 5-minute delay)
batches = [[1, 2, 4], [6, 3, 11], [16, 2, 12], [22], [3, 24]]   # event minutes after 10:00
delay = 5
max_seen, wm, state, emitted = 0, None, {}, []

for b, events in enumerate(batches):
    for m in events:
        w = m // 5 * 5
        if wm is not None and w + 5 <= wm and w not in state:
            print(f"batch {b}: 10:{m:02d} dropped (window 10:{w:02d} already final)")
            continue
        state[w] = state.get(w, 0) + 1
    final = sorted(w for w in state if wm is not None and w + 5 <= wm)
    for w in final:
        emitted.append(w); del state[w]
    print(f"batch {b}: watermark {wm}, emitted {final}, state {sorted(state)}")
    max_seen = max(max_seen, max(events))
    wm = max_seen - delay
batch 0: watermark None, emitted [], state [0] batch 1: watermark -1, emitted [], state [0, 5, 10] batch 2: watermark 6, emitted [0], state [5, 10, 15] batch 3: watermark 11, emitted [5], state [10, 15, 20] batch 4: 10:03 dropped (window 10:00 already final) batch 4: watermark 17, emitted [10], state [15, 20]
  • wm = max_seen - delayThe watermark for the next batch: maximum event time seen so far minus the allowed delay.
  • final = sorted(w for w in state if wm is not None and w + 5 <= wm)A window is final once the watermark has passed its end; append mode writes it now, exactly once.

Lesson 9.3 in one screen

  • Watermark = max event time − delay; set with withWatermark.
  • complete: all rows; update: changed rows; append: final rows only.
  • append + aggregation needs a watermark (else UNSUPPORTED_OPERATION).

Interview and viva questions

Does the watermark use the latest event or the slowest partition?

By default the global watermark uses the minimum across multiple watermarks (multipleWatermarkPolicy=min) and the max event time per stream.

Can I use processing time instead?

Yes, current_timestamp() windows, but late data then lands in the wrong window.

Why did the last batch have no new data?

Spark runs a no-data batch to advance the watermark and emit or evict state.

Does update mode work with file sinks?

No, files support append only; use foreachBatch or a table format for upserts.

Is the delay in processing time?

No, it is in event time: “5 minutes behind the latest event time seen”.

Real-world scenario questions (asked in company interviews)

Watermarks and output modes are favourite advanced streaming questions.

Any company · SparkFresher

“Event time vs processing time”

Explain the difference.

The interviewer is checking: why it matters?

Show a strong answer

Event time is when the event happened (in the data); processing time is when Spark sees it. Grouping by event time puts late events in the correct window; grouping by processing time is simpler but wrong when data is delayed.

Avoid: Ignoring late data.

Data engineeringMid-level

“What is a watermark?”

Explain watermarks.

The interviewer is checking: effect on state?

Show a strong answer
  • max event time − allowed delay; set with withWatermark.
  • Windows older than it are finalised and removed from state.
  • In my test a very late row was dropped and state stayed at 2 rows.

Avoid: Saying it delays processing by the delay.

Data engineeringMid-level

Append mode error

append on a windowed count fails.

The interviewer is checking: why and fix?

Show a strong answer
  1. Append writes rows once; without a watermark nothing is ever final.
  2. Add withWatermark on the event-time column before groupBy.
  3. Or use update mode with an upserting sink.

Avoid: Switching to complete mode on a file sink.

Late data policy

Define a late-data policy for all streaming aggregates.

  • Track numRowsDroppedByWatermark.
