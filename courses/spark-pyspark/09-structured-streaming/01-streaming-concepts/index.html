2 Definition

Structured Streaming

Formal definition (write this in exams)

Structured Streaming is Spark’s stream processing engine built on the Spark SQL engine. A data stream is modelled as an unbounded input table to which new rows are appended; a query on it is written with the same DataFrame/SQL API as a batch query, and Spark runs it incrementally, by default as a series of micro-batches. Each micro-batch reads new data from the source (tracked as offsets), updates any state such as running aggregates, and writes results to a sink according to the output mode. A trigger decides when micro-batches run (as fast as possible, at fixed intervals, once over all available data, or continuously). Progress and offsets are stored in a checkpoint location, which allows end-to-end exactly-once results with replayable sources and idempotent sinks.

In simple words

Structured Streaming lets you write a normal DataFrame query and run it on data that keeps arriving. Spark treats the stream as a growing table, processes the new rows in small batches, remembers where it stopped, and keeps running totals up to date.

Streaming at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A bank passbook

  • You do not reprint the whole passbook after every deposit. The clerk prints only the new entries and the new balance.
  • The last printed line is the bookmark (checkpoint); the balance is the state.

Intermediate The API

  • spark.readStream.format(...).load() gives a streaming DataFrame (isStreaming = True).
  • Transform it like any DataFrame, then df.writeStream.format(...).outputMode(...).trigger(...).option("checkpointLocation", ...).start() returns a StreamingQuery.
  • Monitor with q.status, q.lastProgress, q.recentProgress; stop with q.stop() or wait with awaitTermination().

Advanced What the lab showed

  • An action like count() on a streaming DataFrame fails; only writeStream.start() runs it.
  • With a 2 s trigger and 50 rows/s, each batch read 100 rows and took about 0.4 s.
  • availableNow processed 3 files in 3 batches and stopped; rerun with the same checkpoint read only the new file.

Exam tip: “What is Structured Streaming?” A stream-processing engine on Spark SQL that treats a stream as an unbounded table and runs a DataFrame/SQL query on it incrementally in micro-batches (or continuous mode). You define source, transformations, sink, output mode and trigger; progress and state are saved in a checkpoint, giving fault tolerance and exactly-once results with replayable sources and idempotent sinks.

3 Types and ways to use it

Triggers

TriggerCodeBehaviourUse
Default(none)Next batch as soon as the previous endsLow latency
Fixed intervaltrigger(processingTime="2 seconds")One batch every intervalSteady load
Available nowtrigger(availableNow=True)All data available now, in several batches, then stopScheduled incremental jobs
Continuoustrigger(continuous="1 second")Long-running tasks, ms latencyExperimental; map-only

trigger(once=True) is deprecated; use availableNow=True, which respects rate limits such as maxFilesPerTrigger and splits the work into several batches. And always set a checkpointLocation on real sinks: without it Spark uses a temporary folder and a restart reprocesses everything from the start.

7 Run the code

Run the code: the micro-batch loop

A tiny model of what Spark does on every trigger. Press Run, then try the challenges.

# The micro-batch loop in miniature
incoming = [[3, 5], [2], [], [7, 1, 4]]        # new rows per trigger
checkpoint = {"offset": 0}
state = {"orders": 0, "revenue": 0}

for batch_id, rows in enumerate(incoming):
    state["orders"] += len(rows)
    state["revenue"] += sum(rows)
    checkpoint["offset"] += len(rows)
    print(f"batch {batch_id}: read {len(rows)} new -> {state}")
print("checkpoint:", checkpoint)
batch 0: read 2 new -> {'orders': 2, 'revenue': 8} batch 1: read 1 new -> {'orders': 3, 'revenue': 10} batch 2: read 0 new -> {'orders': 3, 'revenue': 10} batch 3: read 3 new -> {'orders': 6, 'revenue': 22} checkpoint: {'offset': 6}
  • state["orders"] += len(rows)Only the new rows are processed; the running totals are state.
  • checkpoint["offset"] += len(rows)The checkpoint records how far the source has been read, so a restart continues from here.

9 Quiz and revision

Check yourself

Quick revision

Lesson 9.1 in one screen

  • Stream = unbounded table; query runs incrementally in micro-batches.
  • readStream → transform → writeStream…start(); batch actions fail.
  • Triggers: default, processingTime, availableNow, continuous (experimental).
  • Lab: 2 s trigger → 100 rows/batch in ~0.4 s.
  • Monitor with status, lastProgress, recentProgress.
  • availableNow: all new data in batches, then stop; great for scheduled jobs.
  • Checkpoint stores offsets/state; restart reads only new data.

Interview and viva questions

Is Structured Streaming real-time?

Micro-batches give latencies from about a second upward; continuous mode and newer real-time modes target lower latency for simple queries.

What about DStreams (Spark Streaming)?

The old RDD-based API is legacy; use Structured Streaming for new work.

Do I need a schema for file streams?

Yes by default, so the schema does not change between batches; schema inference can be enabled but is risky.

Can I run several streaming queries in one app?

Yes; each start() creates a query; use spark.streams.awaitAnyTermination().

What does the memory sink do?

Keeps results in a driver-side table for testing; never use it for big data.

Real-world scenario questions (asked in company interviews)

Streaming basics are asked in every data engineering interview.

Any company · SparkFresher

“Batch vs streaming in Spark?”

Explain the difference.

The interviewer is checking: API?

Show a strong answer

Batch reads a fixed dataset once with spark.read. Structured Streaming reads with readStream, treats input as an unbounded table and runs the same DataFrame query incrementally in micro-batches via writeStream.start(), keeping offsets and state in a checkpoint.

Avoid: Saying streaming needs a totally different API.

Data engineeringMid-level

Scheduled incremental job

Process new files every hour without reprocessing old ones.

The interviewer is checking: design?

Show a strong answer
  • File stream with a schema and a checkpoint.
  • trigger(availableNow=True), scheduled hourly.
  • In my test a restart read only the new file.

Avoid: Tracking processed files in a custom table.

Data engineeringMid-level

Monitoring

How do you know a stream is healthy?

The interviewer is checking: metrics?

Show a strong answer
  1. lastProgress: input vs processed rows/s, batch duration.
  2. State size and watermark.
  3. StreamingQueryListener → metrics/alerts.

Avoid: Only checking that the job is running.

PlatformSenior

Streaming or batch?

A team asks for streaming for daily reports.

The interviewer is checking: advice?

Show a strong answer
  • Match latency needs to cost; daily needs no always-on stream.
  • availableNow gives incremental processing on a schedule.
  • Move to always-on only when latency demands it.

Avoid: Streaming everything by default.
