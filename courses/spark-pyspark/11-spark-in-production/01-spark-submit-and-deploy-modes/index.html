2 Definition

spark-submit and deploy modes

Formal definition (write this in exams)

spark-submit is the launcher for Spark applications. It takes the application file and its arguments, a master URL (local[*], spark://host:7077, yarn, k8s://…), resource options and dependencies, builds the configuration and starts the driver. The deploy mode decides where the driver runs: in client mode it runs in the submitting process, which must stay alive and reachable from the executors; in cluster mode the cluster manager starts the driver on a cluster node and the submitter can exit. Executors only see code and libraries shipped with the application (--py-files, --jars, --packages, --archives) or pre-installed on the nodes. Configuration precedence is: properties set in the application code (SparkConf/builder.config), then spark-submit flags and --conf, then the properties file (spark-defaults.conf).

In simple words

spark-submit starts your application on a cluster. In client mode the driver runs where you typed the command; in cluster mode it runs inside the cluster. Executors are separate processes on other machines, so you must ship your Python modules and libraries to them. Settings written in code win over command-line settings, which win over the defaults file.

spark-submit at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Sending a cook to another kitchen

  • The head chef (driver) plans; line cooks (executors) cook. If the recipe needs your secret masala, you must pack it in their bag (--py-files).
  • Client mode: the head chef stays at your desk. Cluster mode: the head chef moves into the restaurant too.

Intermediate The command

  • spark-submit --master … --deploy-mode client|cluster --py-files deps.zip --conf k=v --properties-file f.conf app.py args.
  • Resources: --driver-memory, --executor-memory, --executor-cores, --num-executors (YARN/K8s), --total-executor-cores (standalone).
  • Dependencies: --py-files, --jars, --packages, --archives (e.g. a packed virtualenv).

Advanced What the lab showed

  • Without --py-files the executors failed with ModuleNotFoundError; with the zip they computed GST.
  • A value set in code (12) beat --conf (100), which beat the properties file (50).
  • Python cluster mode on a standalone cluster is refused; use YARN or Kubernetes for that.

Exam tip: “Client vs cluster deploy mode?” In client mode the driver runs where spark-submit runs, so logs appear locally and the machine must stay connected to the executors; it suits interactive work. In cluster mode the driver runs inside the cluster, so the job survives the submitter disconnecting and is preferred for production on YARN and Kubernetes. Python applications cannot use cluster mode on a standalone cluster.

Settings in code win. Hard-coding spark.sql.shuffle.partitions or memory in SparkSession.builder.config(...) means operators cannot tune the job with --conf later (our 100 was silently ignored). Put environment-specific settings on the command line or in the properties file, keep only true requirements in code, and print the effective configuration at start-up.

4 Step by step

Submitting to a real cluster

All outputs are real: Spark 4.3.0 standalone cluster in Docker (1 master, 2 workers). The job sets spark.sql.shuffle.partitions=12 in code, prints its effective settings and runs a UDF that imports tiffin_utils.gst on the executors.

  1. Step 1 · The missing module

    spark-submit --master spark://spark-master:7077 /jobs/m11/submit_job.py
    ### 1) spark-submit job.py (no --py-files) deployMode: client | driver host: spark-master executor task failed: ModuleNotFoundError: No module named 'tiffin_utils'
    The driver started fine (the import is inside the function). The executors failed when they ran the task: tiffin_utils exists only next to the script on the submitting machine. Client mode: the driver ran on spark-master, where we typed the command.

  2. Step 2 · Shipping it with --py-files

    cd pkg && python -m zipfile -c ../tiffin_utils.zip tiffin_utils
spark-submit --master spark://spark-master:7077 --py-files /jobs/m11/tiffin_utils.zip /jobs/m11/submit_job.py
    ### 2) spark-submit --py-files tiffin_utils.zip job.py deployMode: client | driver host: spark-master spark.sql.shuffle.partitions = 12 spark.executor.memory = (unset) spark.app.name = tiffingo-submit-demo spark.eventLog.enabled = (unset) with GST: [(100, 105.0), (200, 210.0), (300, 315.0)]
    The zip was distributed with the application and put on every executor’s Python path: 100 → 105.0, 200 → 210.0. The printed settings show what was really used: 12 shuffle partitions (from code), no executor memory and no event log (not set anywhere).

  3. Step 3 · Three places for settings

    # defaults.conf: spark.executor.memory 1g, spark.sql.shuffle.partitions 50, spark.eventLog.enabled true
spark-submit … --properties-file defaults.conf \
  --conf spark.sql.shuffle.partitions=100 --conf spark.executor.memory=1500m \
  --py-files tiffin_utils.zip submit_job.py
    ### 3) spark-submit --properties-file defaults.conf --conf spark.sql.shuffle.partitions=100 --conf spark.executor.memory=1500m --py-files tiffin_utils.zip job.py deployMode: client | driver host: spark-master spark.sql.shuffle.partitions = 12 spark.executor.memory = 1500m spark.app.name = tiffingo-submit-demo spark.eventLog.enabled = true with GST: [(100, 105.0), (200, 210.0), (300, 315.0)]
    Precedence in action. spark.eventLog.enabled came from the file (only set there). spark.executor.memory: --conf 1500m beat the file’s 1g. spark.sql.shuffle.partitions: the code’s 12 beat both 100 and 50. That is exactly the story’s surprise.

  4. Step 4 · Cluster mode for Python on standalone

    spark-submit --master spark://spark-master:7077 --deploy-mode cluster /jobs/m11/submit_job.py
    ### 4) spark-submit --deploy-mode cluster job.py (standalone, Python) Exception in thread "main" org.apache.spark.SparkException: Cluster deploy mode is currently not supported for python applications on standalone clusters.
    Rejected immediately. Standalone cluster mode works for JVM applications only. For Python jobs that must outlive the submitter, use YARN or Kubernetes cluster mode (next lesson), or run client mode from a durable scheduler host.

Run the code: which setting wins?

The lab’s three configuration layers. Press Run, then try the challenges.

# Spark configuration precedence (simplified)
defaults_file = {"spark.executor.memory": "1g", "spark.sql.shuffle.partitions": "50", "spark.eventLog.enabled": "true"}
submit_conf   = {"spark.sql.shuffle.partitions": "100", "spark.executor.memory": "1500m"}
in_code       = {"spark.sql.shuffle.partitions": "12"}

effective = {}
for layer in (defaults_file, submit_conf, in_code):     # later layers win
    effective.update(layer)

for k, v in sorted(effective.items()):
    print(f"{k:30} = {v}")
spark.eventLog.enabled = true spark.executor.memory = 1500m spark.sql.shuffle.partitions = 12

Check yourself

Quick revision

Lesson 11.1 in one screen

  • spark-submit: master, deploy mode, resources, dependencies, app + args.
  • client mode: driver in the submitter; cluster mode: driver in the cluster.
  • Executors only have shipped code: --py-files, --archives, --packages, images.
  • Lab: no --py-files → ModuleNotFoundError; with it → 105.0, 210.0.
  • Precedence: code > --conf/flags > properties file (12 > 100 > 50).
  • Python cluster mode is not supported on standalone.
  • Keep environment settings out of code; print effective config.

Interview and viva questions

What does --packages do?

Downloads Maven artifacts (and dependencies) and adds them to driver and executor classpaths, e.g. spark-sql-kafka.

Can I pass arguments to my script?

Yes, anything after the application file is passed to it (sys.argv).

Where do I see the effective configuration?

Spark UI → Environment tab, or spark.sparkContext.getConf().getAll().

What is spark.pyspark.python?

The Python executable used by executors (and driver with spark.pyspark.driver.python).

Is local mode a deploy mode?

No, local[*] is a master URL: everything runs in one JVM, useful for development and tests.

Real-world scenario questions (asked in company interviews)

spark-submit questions check production readiness.

Any company · SparkFresher

“Client vs cluster mode”

Explain the two deploy modes.

The interviewer is checking: when to use?

Show a strong answer

Client mode runs the driver in the spark-submit process (good for shells, notebooks, debugging). Cluster mode runs the driver inside the cluster so the job continues if the submitter disconnects (good for production). On standalone, Python supports only client mode.

Avoid: Thinking executors run on the laptop in client mode.

Data engineeringMid-level

ModuleNotFoundError

Job works locally, fails on the cluster with ModuleNotFoundError.

The interviewer is checking: fix?

Show a strong answer
  • Executors lack the module; ship it with --py-files (zip/wheel).
  • Compiled libs: --archives packed env or a container image.
  • Pin versions in CI-built artifacts.

Avoid: Installing manually on each node.

Data engineeringMid-level

Ignored setting

A --conf value has no effect.

The interviewer is checking: why?

Show a strong answer
  1. Check the Environment tab for the effective value.
  2. Code (builder.config/SparkConf) overrides --conf.
  3. Some settings must be set before the session starts.

Avoid: Raising it further.

PlatformSenior

Submission standard

Define how teams submit Spark jobs.

The interviewer is checking: standard?

Show a strong answer
  • Cluster mode from the scheduler; versioned artifacts.
  • Per-env properties files; no env settings in code.
  • Event logs and history server for every job.

Avoid: Ad-hoc commands from laptops.
