Testing PySpark code

Spark jobs can compute the wrong numbers without failing. This lesson writes pytest tests for a fee transformation using a shared local SparkSession and pyspark.testing, reads a real failure diff, and places unit tests in a wider testing strategy. All outputs are real (PySpark 4.3.0, pytest).

1 The story

“Mumbai customers were charged ₹40”

Before you start: creating DataFrames and schemas in 4.2, columns and when in 4.3; basic pytest helps.

A small change to TiffinGo’s delivery-fee rules went to production on a Friday. Mumbai’s fee should have been ₹60, but a typo charged ₹40 to every Mumbai order all weekend. The job had run perfectly; it just computed the wrong numbers.

Kabir

Sir, how do you test a Spark job? It needs a cluster and terabytes of data.

Arjun Sir

The logic does not. Put each transformation in a function that takes a DataFrame and returns a DataFrame. Then test it with four hand-made rows on a local SparkSession, in seconds, on every commit.

Riya

And compare DataFrames how?

Arjun Sir

PySpark ships pyspark.testing with assertDataFrameEqual and assertSchemaEqual. Today we write five pytest tests for the fee function, including one that fails on purpose so you see the diff. All outputs are real (PySpark 4.3.0, pytest).

2 Definition

Testing PySpark code

Formal definition (write this in exams)

Testable PySpark code separates I/O (reading and writing data) from transformations, written as pure functions that take and return DataFrames. Unit tests call these functions on small DataFrames created in the test and compare the result with an expected DataFrame, using a local SparkSession (local[1], few shuffle partitions, UI disabled) created once per test session through a pytest fixture. PySpark’s pyspark.testing module provides assertDataFrameEqual, which compares rows (ignoring order by default, with tolerances for floating point) and reports differences, and assertSchemaEqual for column names, types and nullability. Integration tests add real reads and writes on small fixtures, and end-to-end runs on a staging cluster complete the test pyramid.

In simple words

Write each transformation as a function from DataFrame to DataFrame. In tests, build a few rows by hand, run the function on a local Spark, and compare the result with the rows you expect. PySpark has helpers that compare DataFrames and show exactly which rows differ.

Testing at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Tasting before serving

  • A cook tastes one spoon of the curry, not the whole pot. A unit test runs your recipe on four rows and checks the taste.
  • If the spoon is wrong, the whole pot would have been wrong.

Intermediate The tools

  • pytest with a scope="session" fixture that creates one SparkSession.builder.master("local[1]").
  • from pyspark.testing import assertDataFrameEqual, assertSchemaEqual (ignores row order by default, shows a diff).
  • Small input DataFrames built with spark.createDataFrame(rows, schema).

Advanced What the lab showed

  • Starting Spark cost 5.3 s once for the whole test session; 5 tests ran in 13.6 s.
  • The failing test printed both sides and marked the different row with !: Mumbai fee 60 vs 40.
  • The revenue test passed although rows came back in a different order.

Exam tip: “How do you test PySpark code?” Separate I/O from transformations; write transformations as DataFrame-in, DataFrame-out functions; unit-test them with pytest on small DataFrames using a session-scoped local SparkSession; compare with assertDataFrameEqual/assertSchemaEqual (or chispa); add integration tests for reads/writes and run everything in CI.

Useful options

Test against ConnectRun the suite with SPARK_REMOTE set (Lesson 11.3)

Starting a SparkSession costs seconds (5.3 s in our lab). Creating one per test turns a 15-second suite into minutes, and developers stop running it. Use one session-scoped fixture, keep inputs tiny, and avoid .collect() on big generated data in unit tests. Also beware of tests that only check counts: our fee bug would have passed a row-count test.

4 Step by step

Five tests for the fee rules

All outputs are real: PySpark 4.3.0, pytest, run with python -m pytest -q -s --durations=3 tests. Rule: free delivery from ₹500, otherwise ₹60 in Mumbai and ₹40 elsewhere.

  1. Step 1 · The function under test

    from pyspark.sql import DataFrame, functions as F

def add_delivery_fee(orders: DataFrame) -> DataFrame:
    """Free delivery from Rs 500; otherwise Rs 40 (Rs 60 for Mumbai)."""
    fee = (F.when(F.col("amount") >= 500, 0)
            .when(F.col("city") == "Mumbai", 60)
            .otherwise(40))
    return orders.withColumn("delivery_fee", fee).withColumn("total", F.col("amount") + F.col("delivery_fee"))

def city_revenue(orders: DataFrame) -> DataFrame:
    return orders.groupBy("city").agg(F.sum("amount").alias("revenue"))
    No reading, no writing, no SparkSession inside: just a DataFrame in and a DataFrame out. That is what makes it testable. The job’s main script reads the data, calls these functions and writes the result.

  2. Step 2 · One SparkSession for all tests

    import pytest, time
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    t = time.time()
    s = (SparkSession.builder.master("local[1]").appName("tests")
         .config("spark.sql.shuffle.partitions", "1")
         .config("spark.ui.enabled", "false").getOrCreate())
    print(f"\n[fixture] SparkSession started in {time.time() - t:.1f} s")
    yield s
    s.stop()
    pytest creates the session the first time a test asks for spark and reuses it for every other test. One partition, one core and no UI keep it light. In our run it started once in 5.3 s.

  3. Step 3 · The tests

    import pytest
from pyspark.testing import assertDataFrameEqual, assertSchemaEqual
from pyspark.sql.types import StructType, StructField, StringType, LongType, IntegerType
from transforms import add_delivery_fee, city_revenue

@pytest.fixture
def orders(spark):
    return spark.createDataFrame([(1, "Pune", 450), (2, "Mumbai", 300), (3, "Mumbai", 800), (4, "Delhi", 500)],
                                 "order_id long, city string, amount long")

def test_fee_rules(spark, orders):
    out = add_delivery_fee(orders).select("order_id", "delivery_fee", "total")
    expected = spark.createDataFrame([(1, 40, 490), (2, 60, 360), (3, 0, 800), (4, 0, 500)],
                                     "order_id long, delivery_fee int, total long")
    assertDataFrameEqual(out, expected)

def test_city_revenue_ignores_row_order(spark, orders):
    expected = spark.createDataFrame([("Delhi", 500), ("Mumbai", 1100), ("Pune", 450)], "city string, revenue long")
    assertDataFrameEqual(city_revenue(orders), expected)          # order of rows does not matter

def test_schema(orders):
    expected = StructType([StructField("order_id", LongType()), StructField("city", StringType()),
                           StructField("amount", LongType()), StructField("delivery_fee", IntegerType(), False),
                           StructField("total", LongType())])
    assertSchemaEqual(add_delivery_fee(orders).schema, expected)

def test_boundary_is_free(spark):
    df = spark.createDataFrame([(9, "Mumbai", 500)], "order_id long, city string, amount long")
    assert add_delivery_fee(df).first()["delivery_fee"] == 0

def test_wrong_expectation_shows_diff(spark, orders):     # deliberately wrong: Mumbai fee 40
    out = add_delivery_fee(orders).select("order_id", "delivery_fee")
    expected = spark.createDataFrame([(1, 40), (2, 40), (3, 0), (4, 0)], "order_id long, delivery_fee int")
    assertDataFrameEqual(out, expected)
    Four rows cover every branch: Pune under ₹500 (₹40), Mumbai under ₹500 (₹60), Mumbai over ₹500 (free) and exactly ₹500 (free, the boundary). assertDataFrameEqual compares whole DataFrames; assertSchemaEqual checks names and types, including that delivery_fee is a non-nullable int. The last test is deliberately wrong.

7 Run the code

Run the code: table-driven tests

The same rule and cases as the lab, in plain Python. Press Run, then try the challenges.

# The fee rule as plain Python, with table-driven tests
def fee(city, amount):
    if amount >= 500:
        return 0
    return 60 if city == "Mumbai" else 40

cases = [("Pune", 450, 40), ("Mumbai", 300, 60), ("Mumbai", 800, 0), ("Delhi", 500, 0), ("Mumbai", 499, 60)]
failed = 0
for city, amount, expected in cases:
    got = fee(city, amount)
    status = "ok " if got == expected else "FAIL"
    failed += got != expected
    print(f"{status} {city:7} {amount:4} -> {got} (expected {expected})")
print(len(cases) - failed, "passed,", failed, "failed")
ok Pune 450 -> 40 (expected 40) ok Mumbai 300 -> 60 (expected 60) ok Mumbai 800 -> 0 (expected 0) ok Delhi 500 -> 0 (expected 0) ok Mumbai 499 -> 60 (expected 60) 5 passed, 0 failed
  • cases = [("Pune", 450, 40), ("Mumbai", 300, 60), ("Mumbai", 800, 0), ("Delhi", 500, 0), ("Mumbai", 499, 60)]One row per branch plus the boundaries (499 and 500).

9 Quiz and revision

Check yourself

Quick revision

Lesson 11.4 in one screen

  • Separate I/O from transformations; test the transformations.
  • pytest + session-scoped local SparkSession (5.3 s once).
  • assertDataFrameEqual: row-order-insensitive diff; assertSchemaEqual for types.
  • One input row per branch plus boundaries.
  • Lab: 4 passed, 1 failed with DIFFERENT_ROWS (60 vs 40), 13.6 s.
  • Counts alone miss logic bugs.
  • Add integration and data-quality checks; run tests in CI.

Interview and viva questions

What about chispa?

A popular library with similar DataFrame assertions; pyspark.testing now covers the common cases built in.

Can I test with pandas instead of Spark?

For logic written in pandas UDFs, test the pandas function directly; for DataFrame code, use a local Spark.

How do I test code that reads files?

Write small fixture files into pytest’s tmp_path and point the reader at them (integration test).

Should tests use production data?

Not unit tests; use small, deliberate rows. Production samples belong in data-quality checks.

How do I test streaming code?

Use file or rate sources with availableNow and memory/foreachBatch sinks, as in Module 9’s labs.
