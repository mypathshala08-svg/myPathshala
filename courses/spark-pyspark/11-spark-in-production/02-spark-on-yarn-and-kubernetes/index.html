2 Definition

Spark on YARN and Kubernetes

Formal definition (write this in exams)

Spark supports several cluster managers. On Hadoop YARN, spark-submit uploads the application and Spark libraries to a staging directory (usually HDFS) and asks the ResourceManager to start an ApplicationMaster (AM) container; the AM then negotiates executor containers on NodeManagers. In cluster mode the driver runs inside the AM container; in client mode the AM only requests executors and the driver stays in the submitter. On Kubernetes, spark-submit creates a driver pod from a container image, and the driver creates executor pods through the Kubernetes API; dependencies are baked into the image or fetched from remote storage, configuration uses spark.kubernetes.* properties and pod templates, and dynamic allocation relies on shuffle tracking. In both, the cluster manager’s scheduler (queues, quotas, node health) decides when resources are granted.

In simple words

YARN and Kubernetes are shared resource managers. Spark asks them for containers (YARN) or pods (Kubernetes) for its driver and executors. Your Spark code stays the same; the submit command, packaging and log locations change. If the manager cannot grant resources, the job waits.

Cluster managers at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Renting rooms in a hotel

  • Standalone is your own house. YARN and Kubernetes are hotels: you ask reception (ResourceManager / API server) for rooms (containers / pods), and they decide who gets what.
  • If housekeeping marks a floor unusable, reception has no rooms to give and your booking waits.

Intermediate The commands

  • YARN: spark-submit --master yarn --deploy-mode cluster --num-executors 2 --executor-memory 768m app.py, with HADOOP_CONF_DIR set; logs via yarn logs -applicationId ….
  • Kubernetes: spark-submit --master k8s://https://<api-server> --deploy-mode cluster --conf spark.kubernetes.container.image=… local:///opt/app/app.py.
  • Inspect: yarn application -list, yarn node -list -all; kubectl get pods, kubectl logs.

Advanced What the lab showed

  • Cluster mode uploaded the Spark libs, script, pyspark.zip, py4j and config to HDFS staging, then ran the driver in container 000001.
  • The driver’s output was only visible through YARN logs.
  • A node above 90% disk use became UNHEALTHY; the application stayed ACCEPTED with 0% progress.

Exam tip: “How does Spark run on YARN?” spark-submit uploads jars, Python files and config to a staging dir, the ResourceManager starts an ApplicationMaster container, and the AM requests executor containers from NodeManagers. In cluster mode the driver runs in the AM; in client mode it runs in the submitter. On Kubernetes, the driver runs as a pod built from a Spark image and creates executor pods via the API server.

“ACCEPTED” or “Pending” is not an error, so nothing fails and nothing alerts. On YARN it means the queue or nodes cannot give the first container (unhealthy nodes, queue limits, an executor bigger than any node); on Kubernetes, pods stuck in Pending usually mean quota, node selectors or image pull problems. Check yarn node -list -all / kubectl describe pod before resubmitting, and add a timeout alert for jobs that do not start.

4 Step by step

A real YARN cluster in one container

All outputs are real: a Docker image with Hadoop 3.4.1 (HDFS NameNode + DataNode, YARN ResourceManager + NodeManager with 4 GB and 4 vcores) and Spark 4.3.0/PySpark. The job prints where its driver runs, groups 5 million rows and counts registered executors. Submitted with 2 executors of 1 core and 768 MB.

  1. Step 1 · Client mode

    export HADOOP_CONF_DIR=/opt/hadoop/etc/hadoop
spark-submit --master yarn --deploy-mode client --num-executors 2 \
  --executor-cores 1 --executor-memory 768m /jobs/m11/yarn_job.py
    == client mode Client: Submitting application application_1793860298532_0002 to ResourceManager Client: Application report for application_1793860298532_0002 (state: ACCEPTED) Client: Application report for application_1793860298532_0002 (state: RUNNING) master: yarn | deployMode: client | appId: application_1793860298532_0002 driver host: yarn | driver container: (none: client mode) groups: 7 executors registered: 2
    Spark found the ResourceManager through HADOOP_CONF_DIR, the application went ACCEPTED → RUNNING once the ApplicationMaster container started, and 2 executors registered. In client mode the driver ran in our shell: there is no YARN container ID for it, and its output appeared directly in the terminal.

  2. Step 2 · Cluster mode

    spark-submit --master yarn --deploy-mode cluster --num-executors 2 --executor-cores 1 \
  --executor-memory 768m --conf spark.yarn.appMasterEnv.PYSPARK_PYTHON=python3 /jobs/m11/yarn_job.py
    == cluster mode Client: Uploading resource file:/tmp/spark-…/__spark_libs__6156899551285634790.zip -> hdfs://…/.sparkStaging/<app>/__spark_libs__6156899551285634790.zip Client: Uploading resource file:/jobs/m11/yarn_job.py -> hdfs://…/.sparkStaging/<app>/yarn_job.py Client: Uploading resource file:…/pyspark/python/lib/pyspark.zip -> hdfs://…/.sparkStaging/<app>/pyspark.zip Client: Uploading resource file:…/pyspark/python/lib/py4j-0.10.9.9-src.zip -> hdfs://…/.sparkStaging/<app>/py4j-0.10.9.9-src.zip Client: Uploading resource file:/tmp/spark-…/__spark_conf__3098129070007018604.zip -> hdfs://…/.sparkStaging/<app>/__spark_conf__.zip Client: Submitting application application_1793860298532_0003 to ResourceManager Client: Application report for application_1793860298532_0003 (state: ACCEPTED) Client: Application report for application_1793860298532_0003 (state: RUNNING) Client: Application report for application_1793860298532_0003 (state: FINISHED) final status: SUCCEEDED
    Before asking for containers, the client uploaded five files to HDFS staging: the Spark jars zip, our script, pyspark.zip, py4j and the config zip. Every container on any node downloads them from there. The terminal only showed status reports, ending in final status: SUCCEEDED; the job’s own prints were elsewhere.

  3. Step 3 · Finding the driver’s output

    yarn logs -applicationId application_1793860298532_0003
ls $HADOOP_HOME/logs/userlogs/application_1793860298532_0003/
    == driver stdout (yarn logs, container 000001) master: yarn | deployMode: cluster | appId: application_1793860298532_0003 driver host: yarn | driver container: container_1793860298532_0003_01_000001 groups: 7 executors registered: 2 == containers of the application container_1793860298532_0003_01_000001 container_1793860298532_0003_01_000002 container_1793860298532_0003_01_000003
    The driver ran inside container 000001, the ApplicationMaster container; 000002 and 000003 were the executors. With log aggregation on, yarn logs collects all of them after the job. Knowing this is half of debugging on YARN.

  4. Step 4 · Stuck in ACCEPTED

    yarn application -list
yarn node -list -all
    $ yarn application -list application_1793860298532_0001 tiffingo-yarn-demo SPARK root root.default ACCEPTED UNDEFINED 0% N/A $ yarn node -list -all yarn:34797 UNHEALTHY yarn:8042 0 $ grep Disk nodemanager.log ERROR LocalDirsHandlerService: Most of the disks failed. 1/1 local-dirs usable space is below configured utilization percentage/no more usable space [ /tmp/hadoop-root/nm-local-dir : used space above threshold of 90.0% ]
    Our first attempt waited for minutes. The only NodeManager was UNHEALTHY: its disk was over YARN’s 90% utilisation threshold, so the ResourceManager had zero usable nodes and could not even start the ApplicationMaster. No exception, just ACCEPTED at 0%. Freeing disk space (and, in our lab, raising max-disk-utilization-per-disk-percentage) made the node RUNNING and the job started.

7 Run the code

Run the code: will YARN start it?

A simplified version of why our job waited. Press Run, then try the challenges.

# Will YARN start this application? (simplified scheduler check)
nodes = [{"name": "yarn:34797", "healthy": False, "free_mb": 4096, "free_vcores": 4}]
am_mb, exec_mb, overhead = 768, 768, 384
executors = 2

usable = [n for n in nodes if n["healthy"]]
need_am = am_mb + overhead
if not usable:
    print("state: ACCEPTED (no healthy node for the ApplicationMaster)")
elif max(n["free_mb"] for n in usable) < need_am:
    print("state: ACCEPTED (AM container does not fit)")
else:
    free = sum(n["free_mb"] for n in usable) - need_am
    got = min(executors, free // (exec_mb + overhead))
    print(f"state: RUNNING with {got} executor(s)")
state: ACCEPTED (no healthy node for the ApplicationMaster)
  • usable = [n for n in nodes if n["healthy"]]UNHEALTHY nodes (e.g. disk over 90%) get no containers at all.
  • need_am = am_mb + overheadEach container needs its memory plus overhead; YARN rounds up to its allocation increments.

  • Cluster mode: driver in the AM container; client mode: in the submitter.
  • spark-submit uploads libs, script, pyspark.zip, py4j, conf to HDFS staging.

Interview and viva questions

Do I need Hadoop installed to submit to YARN?

You need the cluster’s Hadoop configuration (HADOOP_CONF_DIR) and Spark built with YARN support; pip PySpark includes it.

What is the Spark Operator?

A Kubernetes operator that manages Spark jobs declared as SparkApplication resources, handling submission, restarts and monitoring.

Can I use --py-files on Kubernetes?

Yes, with remote URLs or files in the image, but baking dependencies into the image is the common practice.

Is YARN still relevant?

Yes, many on-premise and EMR/Dataproc deployments use it, while new platforms often choose Kubernetes.

Why did the lab not run Kubernetes?

Our sandbox cannot run containers inside containers, which local Kubernetes (kind/minikube) needs; the YARN parts are real runs.
