1 The story

Code your team can read, test and change

Before you start: 11.4 Testing.

🤔 Two PySpark scripts give the same numbers. One is 400 lines nobody dares touch; the other is five small functions with tests. Which one is faster?

Often neither: Spark optimises both into the same plan. The difference is everything else: reading, testing, changing. Some habits do change the plan: 20 withColumn calls built 21 Project nodes and took 220 ms just to construct, while one select built 2 nodes in 70 ms; isEmpty() answered in 0.12 s where count() > 0 took 0.31 s. Our TiffinGo transforms became a one-line .transform() chain with 2 passing pytest tests.

  • Structuring PySpark code as small DataFrame → DataFrame functions.
  • Habits that change plans: select vs withColumn, toDF, isEmpty, filter early.
  • Making code testable and configurable.

2 Definition

Writing clean, modular PySpark

Formal definition (write this in exams)

Modular PySpark structures a pipeline as small, pure transformation functions with the signature DataFrame → DataFrame, configured through parameters and composed with DataFrame.transform, with input/output isolated at the edges. Combined with plan-aware habits (batched column expressions, early filtering and projection, cheap existence checks), it yields code that is testable, reusable and efficient.

In simple words

Write each step as a small function that takes a table and returns a table, pass settings in, chain the steps, and test each one. A few habits also keep Spark’s plans small.

Why, how, where

Why

Pipelines live for years and change every month. Long notebook-style scripts hide bugs, cannot be tested, and are copied instead of reused. A few habits also keep Spark plans small and jobs cheap.

the problem it solves

How

Write each step as a pure function DataFrame → DataFrame; pass settings (prices, dates, paths) in; compose with df.transform(f); keep I/O at the edges (read at start, write at end); test each function with a tiny DataFrame. Prefer one select/withColumns over many withColumn, filter and select columns early, and use isEmpty() for existence checks.

the mechanism

Where

Every production job, shared team libraries, code reviews, and interviews that ask “how do you structure PySpark code?”.

in real systems

When not

Over-abstracting hurts too: keep functions small but meaningful, and check plans (explain) when performance matters.

Plan size at a glance

Clean PySpark at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A recipe card per step

  • Instead of one long story, write one card per step (wash, cut, cook). Anyone can test one card, swap it, or reuse it in another dish.

Intermediate The habits

  • Functions: def add_amount(prices): def _f(df): …; return _f → df.transform(add_amount(PRICES)).
  • Columns: build many columns with one select("*", …) or withColumns({…}); rename many with toDF(*names) or withColumnsRenamed.
  • Data volume: filter early, select only needed columns, push filters to the source (Parquet); isEmpty() / limit(1) instead of count() > 0.

Advanced Project shape

  • Package: transforms.py (pure functions), io.py (read/write), config.yaml, main.py (entrypoint wiring them), tests/; ship with --py-files or a wheel (Lesson 11.1).
  • Name intermediate DataFrames by meaning, avoid df1, df2; log row counts sparingly (each count is a job).
  • Reviews: read explain("formatted") for new jobs; watch for repeated scans, unexpected Exchanges and huge plans built in loops.

Myth vs reality: things many websites still say

  • Myth: Functions make Spark slower.
    Reality (Spark 4.3): Same optimised plan.
    Proof: Step 1.
  • Myth: withColumn in a loop is free.
    Reality (Spark 4.3): 21 nodes and 3× build time.
    Proof: Step 2.
  • Myth: count() is the way to check for rows.
    Reality (Spark 4.3): isEmpty() stops early.
    Proof: Step 4.

Exam tip: “How do you structure PySpark code?” Small pure DataFrame → DataFrame functions, parameters/config, DataFrame.transform chains, I/O at edges, tests per function; select/withColumns over looped withColumn, toDF for renames, filter/select early, isEmpty over count, explain for reviews.

4 Step by step

Refactor and measure

All outputs are real: PySpark 4.3.0, local[2], 2,000,000 synthetic orders, pytest 9.

  1. Step 1 · Small functions, one chain

    def only_valid(df):
    return df.filter((F.col("qty") > 0) & F.col("item").isNotNull())

def add_amount(prices):
    def _f(df):
        m = F.create_map(*[x for k, v in prices.items() for x in (F.lit(k), F.lit(v))])
        return df.withColumn("amount", F.col("qty") * m[F.col("item")])
    return _f

orders.transform(only_valid).transform(add_amount(PRICES)).transform(revenue_by_city)
    == 1) one readable chain of small functions orders.transform(only_valid).transform(add_amount(PRICES)).transform(revenue_by_city) +------+--------+ | city| revenue| +------+--------+ | Delhi|65000130| |Mumbai|65000040| | Pune|64999830| +------+--------+
    Two million orders, three readable steps. Prices come in as a parameter; “pizza” is not on the menu, so its amount is null and ignored by sum.

  2. Step 2 · select vs withColumn

    for i in range(20): d1 = d1.withColumn(f"c{i}", F.col("qty") + i)
d2 = orders.select("*", *[(F.col("qty") + i).alias(f"c{i}") for i in range(20)])
orders.withColumns({f"c{i}": F.col("qty") + i for i in range(20)})
    == 2) 20 x withColumn vs one select (analysed plan size, time to build the DataFrame) withColumn x20 : 21 Project nodes, built in 220 ms one select : 2 Project nodes, built in 70 ms withColumns : 2 Project nodes
    Same result columns; the loop builds 21 projections and takes 3× longer just to construct.

  3. Step 3 · Renaming

    orders.withColumnRenamed("city", "CITY").withColumnRenamed(...)...
orders.toDF(*[c.upper() for c in orders.columns])
    == 3) renaming many columns chained withColumnRenamed: 4 Project nodes orders.toDF(*cols) : 2 Project nodes -> ['CITY', 'ITEM', 'QTY']
    One projection for all names.

  4. Step 4 · Existence checks

    bad = orders.filter("qty = 0")
bad.count() > 0
not bad.isEmpty()
    == 4) 'is there any bad order?' count() > 0 vs isEmpty() count() > 0 : True 0.31 s (scans everything) isEmpty() : True 0.12 s (stops at the first row)
    isEmpty stops at the first matching row.

  5. Step 5 · Tests

    def test_amount_and_revenue(spark):
    df = spark.createDataFrame([("Pune", "idli", 2), ("Pune", "dosa", 1)], "city string, item string, qty int")
    out = df.transform(add_amount({"idli": 45, "dosa": 90})).transform(revenue_by_city).collect()
    assert [(r.city, r.revenue) for r in out] == [("Pune", 180)]
    == 5) unit tests for the transforms (pytest) 2 passed, 1 warning in 9.03s
    Each function is tested with three rows, no files, no cluster.

7 Run the code

Run the code: a transform chain

The same shape as the lab, in plain Python. Press Run, then try the challenges.

# DataFrame -> DataFrame style, with plain Python lists of dicts
def only_valid(rows):
    return [r for r in rows if r["qty"] > 0 and r["item"]]

def add_amount(prices):
    def _f(rows):
        return [{**r, "amount": r["qty"] * prices.get(r["item"], 0)} for r in rows]
    return _f

def revenue_by_city(rows):
    out = {}
    for r in rows: out[r["city"]] = out.get(r["city"], 0) + r["amount"]
    return out

def pipe(data, *steps):              # like df.transform(f).transform(g)...
    for s in steps: data = s(data)
    return data

orders = [{"city": "Pune", "item": "idli", "qty": 2}, {"city": "Pune", "item": None, "qty": 1}, {"city": "Delhi", "item": "dosa", "qty": 1}]
print(pipe(orders, only_valid, add_amount({"idli": 45, "dosa": 90}), revenue_by_city))
{'Pune': 90, 'Delhi': 90}

Interview and viva questions

Is withColumn bad?

No for a few columns; avoid it in long loops.

Where do UDFs go?

In the transforms module, with tests; prefer built-ins first.

Should every step be a function?

Group by meaning, not by line; three to ten steps per job is typical.

How do I test without a cluster?

local[1] SparkSession fixture (Lesson 11.4).
