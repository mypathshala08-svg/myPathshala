Delta Lake and Iceberg

Table formats turn Parquet folders into ACID tables. This lesson updates, deletes and merges rows in Delta Lake, reads its history and older versions, tests schema enforcement, and uses Apache Iceberg’s hidden partitioning, snapshots and schema/partition evolution. 1 The story

“We need to fix one order in a 2 TB folder”

Before you start: Parquet in 5.2, writing and small files in 5.3, tables and catalogs in 7.2.

A customer asked TiffinGo to correct one order’s status. The orders lived in plain Parquet files: to change one row, the team rewrote a whole day’s partition, and a reader ran during the rewrite and saw half the data. The same month, a job appended amounts as strings and broke every dashboard.

Kabir

Sir, Parquet is great. Why does it not support UPDATE?

Arjun Sir

Parquet files are immutable, and a folder of them has no idea which files belong together. Table formats like Delta Lake and Apache Iceberg add a log of commits: each change writes new files and then atomically records “these files are now the table”.

Riya

And readers never see half a change?

Arjun Sir

Exactly: ACID transactions on a data lake, plus history, time travel and schema checks. Today we try both formats. Neither supports Spark 4.3 yet, so this lab runs PySpark 4.1.1 with delta-spark 4.3.1 and Iceberg 1.12.0. All outputs are real.

2 Definition

Delta Lake and Apache Iceberg

Formal definition (write this in exams)

Open table formats store table data as Parquet files in object storage and add metadata that defines which files form each version of the table. Delta Lake keeps an ordered transaction log (_delta_log/ JSON commits with periodic checkpoints); Apache Iceberg keeps a tree of metadata files, manifest lists and manifests, referenced by a catalog. Writers commit new versions atomically with optimistic concurrency, giving ACID transactions, row-level UPDATE/DELETE/MERGE (by rewriting or marking affected files), time travel to earlier versions or snapshots, schema enforcement and controlled schema evolution. Iceberg adds hidden partitioning (partition transforms such as days(ts) derived from columns) and partition evolution. Both integrate with Spark through connector packages and SQL extensions.

In simple words

Delta Lake and Iceberg turn folders of Parquet files into real tables. A log records every change, so you can update and delete rows safely, readers never see half-finished writes, you can read older versions, and wrong data types are rejected.

Table formats at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A register at the library

  • Books (Parquet files) never change; a register lists which books are on the shelf right now.
  • To “edit” a book, you add a corrected copy and change the register in one stroke. Old register pages let you see the shelf as it was last week (time travel).

Intermediate The API

  • Delta: df.write.format("delta").save(path), DeltaTable.forPath(spark, path) with .update(), .delete(), .merge(), .history(); read option("versionAsOf", n).
  • Iceberg: catalog config, then SQL: CREATE TABLE … USING iceberg PARTITIONED BY (days(ts)), UPDATE, DELETE, MERGE INTO, VERSION AS OF, metadata tables like t.snapshots.
  • Schema: Delta mergeSchema; Iceberg ALTER TABLE … ADD/RENAME COLUMN, ADD PARTITION FIELD.

Advanced What the lab showed

  • Delta recorded WRITE, UPDATE, DELETE and MERGE as versions 0–3; version 0 is still readable.
  • Appending amount as a string was rejected; a new column needed mergeSchema.
  • Iceberg created ts_day=… folders from days(ts), travelled back to a snapshot, and changed its partitioning without rewriting old data.

Exam tip: “Why use Delta Lake or Iceberg instead of plain Parquet?” They add a transactional metadata layer: atomic commits (no partial reads), row-level updates/deletes/merges, time travel, schema enforcement and evolution, and efficient metadata-based pruning. Delta uses an ordered JSON transaction log; Iceberg uses snapshots with manifests and a catalog, and adds hidden partitioning and partition evolution.

Setting them up in Spark

Delta Lakepip install delta-spark (matches Spark minor version)spark.sql.extensions=io.delta.sql.DeltaSparkSessionExtension, spark.sql.catalog.spark_catalog=…DeltaCatalog
Icebergiceberg-spark-runtime-<spark>_2.13 jarspark.sql.extensions=…IcebergSparkSessionExtensions, spark.sql.catalog.lake=…SparkCatalog + type/warehouse

Table formats are tied to Spark versions. When we built this lesson, the newest Delta (4.4.1) supported Spark 4.2 and the newest Iceberg runtime targeted Spark 4.1, while PySpark was at 4.3. Platforms usually lag the newest Spark for this reason; check the compatibility matrix before upgrading Spark. Also, time travel only works while old files exist: VACUUM (Delta) and expire_snapshots (Iceberg) delete them.

7 Run the code

Run the code: replaying a transaction log

How a reader finds the files of any version. Press Run, then try the challenges.

# A transaction log in miniature: each commit lists files added and removed
log = [
    {"v": 0, "op": "WRITE",  "add": ["p0", "p1"], "remove": []},
    {"v": 1, "op": "UPDATE", "add": ["p2"],       "remove": ["p0"]},
    {"v": 2, "op": "DELETE", "add": ["p3"],       "remove": ["p1"]},
]

def files_at(version):
    files = set()
    for c in log:
        if c["v"] > version:
            break
        files |= set(c["add"])
        files -= set(c["remove"])
    return sorted(files)

for v in range(3):
    print("version", v, "->", files_at(v))
version 0 -> ['p0', 'p1'] version 1 -> ['p1', 'p2'] version 2 -> ['p2', 'p3']
  • files |= set(c["add"])Replay commits in order: files added become part of the table…
  • files -= set(c["remove"])…and removed files leave it, but stay on disk for time travel until vacuumed.

9 Quiz and revision

Check yourself

Quick revision

Lesson 11.5 in one screen

  • Table formats = Parquet files + transactional metadata.
  • Delta: _delta_log commits; Iceberg: snapshots, manifests, catalog.
  • UPDATE/DELETE/MERGE are atomic commits (lab versions 0–3).
  • Time travel: versionAsOf / VERSION AS OF while files are retained.
  • Schema enforcement rejects wrong types; mergeSchema / ALTER to evolve.
  • Iceberg hidden partitioning (days(ts)) and partition evolution.
  • Check format ↔ Spark version compatibility before upgrading.

Interview and viva questions

What is Delta UniForm?

A Delta feature that also writes Iceberg metadata so Iceberg readers can read Delta tables.

Do I need Databricks for Delta?

No, Delta Lake is open source and works with open-source Spark via delta-spark.

What catalog should Iceberg use?

Production setups use a REST catalog, Hive Metastore, AWS Glue or Nessie; the Hadoop catalog is for local tests.

How do I avoid many small files?

Run OPTIMIZE (Delta) or rewrite_data_files (Iceberg) regularly, and size writes well (Lesson 5.3).

What about Apache Hudi?

Another open table format with strong upsert/CDC features; the concepts are similar.
