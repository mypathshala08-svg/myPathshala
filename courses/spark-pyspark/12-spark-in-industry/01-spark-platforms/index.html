2 Definition

Spark platforms

Formal definition (write this in exams)

A Spark platform packages Apache Spark with infrastructure and services: cluster provisioning and autoscaling (or serverless execution), a curated runtime that fixes the Spark, Scala, Java and Python versions plus connectors, development tools (notebooks, IDE integration, Spark Connect), job orchestration, data catalogs and governance, table formats, security integration and monitoring. Platforms differ in how close they track open-source releases, in proprietary engine optimisations (for example vectorised native execution), in pricing (per instance-hour, per compute unit, per job or per data processed) and in portability. Applications written against the standard DataFrame and SQL APIs usually move between platforms with configuration changes; platform-specific features (proprietary SQL, catalogs, utilities) create lock-in.

In simple words

A Spark platform is Spark plus everything needed to run it in a company: machines that start and stop by themselves, a chosen Spark version, notebooks, schedulers, security and monitoring. Your DataFrame code mostly stays the same; you choose a platform for cost, convenience, version and the tools around it.

Spark platforms at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Cooking at home or eating out

  • Self-managed Spark is cooking at home: cheapest ingredients, all the work is yours. A managed platform is a restaurant: you order, they cook, you pay for the service.
  • Serverless is a food-delivery app: you do not even see a kitchen; you pay per dish.

Intermediate The main families

  • Lakehouse platforms: Databricks, Microsoft Fabric (notebooks, jobs, catalogs, Delta, governance).
  • Managed clusters / serverless: Amazon EMR (on EC2, EKS, Serverless), Google Dataproc and Serverless for Apache Spark, AWS Glue for ETL.
  • Self-managed: open-source Spark on Kubernetes (Spark Operator) or YARN.

Advanced What we measured and found

  • One job, zero code changes: same result on local[4], standalone and YARN; start-up 7.5 s, 10.7 s and 25.7 s.
  • Platform Spark versions lag open source: open-source 4.3.0; Databricks Runtime 19 has 4.2.0; Fabric Runtime 2.0 has 4.1; EMR 4.0.2; Dataproc Serverless runtime 3.0 has 4.0.1; Glue 5.1 is still on 3.5.6.

Exam tip: “How would you choose a Spark platform?” Start from requirements: data location and cloud, team skills, latency and scale, governance and security, required Spark version and table format, and cost model. Compare managed lakehouses (Databricks, Fabric), cloud-managed Spark (EMR, Dataproc, Glue) and self-managed Spark on Kubernetes. Keep code on standard DataFrame/SQL APIs and open table formats to stay portable, and benchmark a real workload before committing.

Check the Spark version before you plan features. In November 2026 a lesson written for Spark 4.3 could not run unchanged on AWS Glue (3.5.6), and even the newest Databricks runtime was one minor version behind open source. Also beware of “free” proprietary helpers (vendor-only SQL functions, file utilities, magic commands): they are convenient and they are what makes moving platforms expensive later.

4 Step by step

One job, three targets

All outputs are real: Spark 4.3.0. The job aggregates 20 million generated orders into 6 cities. It never mentions a cluster; only the --master given at launch changes. Our host has 2 physical CPUs, so the clusters are not faster here; the point is portability and start-up cost.

  1. Step 1 · The job

    spark = SparkSession.builder.appName("tiffingo-same-job").getOrCreate()
df = spark.range(0, 20_000_000, 1, 8).select((F.col("id") % 6).alias("city"), (F.col("id") % 500).alias("amount"))
r = df.groupBy("city").agg(F.sum("amount").alias("rev")).orderBy("city").collect()
    No master, no memory settings, no paths tied to a machine. This is what portable Spark code looks like: platform choices come from the launcher or the platform’s job definition.

  2. Step 2 · Local, standalone, YARN

    PYSPARK_SUBMIT_ARGS="--master local[4] pyspark-shell" python same_job.py
spark-submit --master spark://spark-master:7077 same_job.py
spark-submit --master yarn --num-executors 2 --executor-cores 1 --executor-memory 768m same_job.py
    ## local[4] (laptop-style) master=local[4] | session start 7.5 s | query 2.9 s | result rows 6 | first 830000166 ## standalone cluster (2 workers) master=spark://spark-master:7077 | session start 10.7 s | query 6.3 s | result rows 6 | first 830000166 ## YARN (client mode, 2 executors) master=yarn | session start 25.7 s | query 6.6 s | result rows 6 | first 830000166
    Identical result on all three (city 0 revenue 830,000,166). Start-up time grew with the amount of machinery: 7.5 s locally, 10.7 s on the standalone cluster, 25.7 s on YARN (staging files to HDFS, starting an ApplicationMaster, then executors). Managed platforms hide this with pre-warmed pools or serverless start-up, which is part of what you pay for.

  3. Step 3 · What the platform decides

    Databricks Runtime 19     -> Apache Spark 4.2.0  (Jul 2026)
Databricks Runtime 18 LTS -> Apache Spark 4.1.0  (Jun 2026)
Fabric Runtime 2.0        -> Apache Spark 4.1, Java 21, Python 3.13, Delta 4.2
Amazon EMR                -> Apache Spark 4.0.2 (GA 2026)
Serverless for Apache Spark runtime 3.0 -> Spark 4.0.1, Java 21, Python 3.12
AWS Glue 5.1              -> Apache Spark 3.5.6, Python 3.11
Apache Spark (OSS)        -> 4.3.0 (30 Oct 2026)
    From the platforms’ own pages (sources above). A feature from Lesson 12.3, such as Spark 4.3’s ASOF JOIN, simply does not exist yet on most platforms. Conversely, platforms add their own features (Photon, Unity Catalog, Lake Formation permissions) that open source does not have.

    "Lakehouse platform":   {"governance": 5, "low_ops": 5, "newest_spark": 4, "cost_small_jobs": 3, "portability": 3},

Interview and viva questions

Is Databricks Spark the same as Apache Spark?

It is built on Apache Spark and adds proprietary features (e.g. Photon engine, Unity Catalog); standard APIs behave the same.

Why do platforms lag open-source releases?

They test, patch and bundle connectors and security features before release, and support older runtimes (LTS) for stability.

What is an LTS runtime?

A runtime version supported for a long period with fixes, recommended for production jobs that should not change often.

Is Synapse Spark still a choice?

Microsoft’s current Spark investment is Fabric; check Microsoft’s lifecycle pages for Synapse runtimes.

Do I need a platform to learn Spark?

No: pip install pyspark and local mode (as in this course) cover almost everything.

Real-world scenario questions (asked in company interviews)

Platform questions show architectural maturity.

Any company · SparkFresher

“Name Spark platforms”

Which platforms run Spark?

The interviewer is checking: examples?

Show a strong answer

Databricks and Microsoft Fabric (lakehouse platforms), Amazon EMR and AWS Glue, Google Dataproc / Serverless for Apache Spark, and open-source Spark on Kubernetes or YARN. They run the same engine with different versions, tools and pricing.

Avoid: Thinking each has a different API.

Data engineeringMid-level

Runtime upgrade

Your platform offers a new LTS runtime.

The interviewer is checking: plan?

Show a strong answer
  • Read release notes and behaviour changes (e.g. ANSI mode).
  • Run the test suite and sample jobs on the new runtime.
  • Migrate job by job; keep rollback.

Avoid: Switching all jobs at once.

Data engineeringMid-level

Cost

Spark costs doubled this quarter.

The interviewer is checking: investigate?

Show a strong answer
  1. Cost per pipeline and idle time.
  2. Move spiky jobs to serverless; autoscale clusters.
  3. Tune the top jobs (Module 8).

Avoid: Buying reserved capacity first.

ArchitectureSenior

Platform strategy

Recommend a Spark platform for a growing company.

The interviewer is checking: approach?

Show a strong answer
  • Requirements and TCO (licences + people).
  • Benchmark a real pipeline on 2–3 candidates.
  • Open formats and standard APIs to keep exit options.

Avoid: Choosing by brand.
