Before Spark 3, TiffinGo’s platform team kept a spreadsheet of spark.sql.shuffle.partitions values per job: 200 was too many for small days and too few for festival days. One restaurant chain with most of the orders made a join run for an hour on a single task.

2 Definition

Adaptive Query Execution

Formal definition (write this in exams)

Adaptive Query Execution (AQE) re-optimises a query at run time using statistics collected from completed query stages, which are delimited by shuffles and broadcasts. After each stage materialises, Spark re-plans the remaining query with the actual output sizes. Its main optimisations are coalescing post-shuffle partitions into fewer partitions close to an advisory size, switching join strategies (sort-merge to broadcast hash join, or to shuffled hash join) when a side is found to be small, and optimising skew joins by splitting oversized partitions and replicating the matching partition of the other side. AQE is enabled by default since Spark 3.2 (spark.sql.adaptive.enabled).

In simple words

AQE lets Spark change its plan while the query runs. After each shuffle it knows the real data sizes, so it can merge tiny partitions, use a broadcast join when a table turns out small, and split a partition that is much bigger than the rest.

AQE at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Packing parcels

  • You booked 200 trucks before knowing the parcels. When they turn out to be few, you send 5 full trucks instead (coalescing).
  • A parcel you expected to be heavy is light: hand-carry it instead of booking a truck (switch to broadcast).
  • One giant parcel: split it across several trucks (skew join).

Intermediate The API

  • spark.sql.adaptive.enabled (true), …coalescePartitions.enabled, …advisoryPartitionSizeInBytes (64 MB).
  • spark.sql.adaptive.autoBroadcastJoinThreshold (defaults to the normal threshold), …skewJoin.enabled, …skewedPartitionFactor (5), …skewedPartitionThresholdInBytes (256 MB).
  • Plans show AdaptiveSparkPlan isFinalPlan=…, AQEShuffleRead coalesced, SortMergeJoin(skew=true).

Advanced What the lab showed

  • groupBy city: AQE off ran 204 tasks, on ran 5; 1.74 s → 0.62 s.
  • With static broadcast disabled, AQE still turned the join into a broadcast at run time: 0.89 s → 0.05 s.
  • A key with 60% of rows: 3.67 s without AQE, 2.57 s with coalescing only, 1.92 s with skew-join splitting.

Exam tip: “What does AQE do?” It re-optimises queries at run time using statistics from completed shuffle stages: it coalesces small shuffle partitions, converts sort-merge joins to broadcast joins when a side is small, and splits skewed partitions in joins. It is on by default since Spark 3.2; it reduces the need to hand-tune shuffle partitions but cannot fix every skew or bad data layout.

Settings worth knowing

AQE’s skew handling only kicks in when a partition is both 5× the median and over 256 MB by default, and only for joins (sort-merge and shuffled hash), not for aggregations. Our small lab had to lower the thresholds to see it. On real clusters check the final plan for skew=true; if a hot key still dominates, salt it (Lesson 8.3).

6 Real-world use

AQE at work

1. Jobs with changing volumes

Daily jobs whose input varies 10x between normal and festival days run well without per-day tuning.

Any day→AQE coalesce→Right task count

2. Ad-hoc SQL

Analyst queries with unpredictable filters get broadcast joins chosen from real sizes.

Ad-hoc query→runtime switch→Fast join

3. Marketplace data

Big sellers or restaurants create hot keys; AQE splits their join partitions.

Hot key→skew join→Balanced tasks

4. Fewer output files

Coalesced shuffle partitions also mean fewer, larger output files.

Shuffle→coalesce→Fewer files

5. Performance reviews

Engineers read final plans in the Spark UI to see which AQE rules fired.

Spark UI→final plan→Insight

7 Run the code

Run the code: coalescing partitions

A simplified model of Step 1. Press Run, then try the challenges.

# How AQE coalesces shuffle partitions (simplified)
sizes_kb = [2, 0, 1, 3, 0, 0, 2, 1] * 25           # 200 tiny partitions after a shuffle
target_kb = 64 * 1024                              # advisoryPartitionSizeInBytes = 64 MB

groups, current = [], 0
for s in sizes_kb:
    if current + s > target_kb and current:
        groups.append(current); current = 0
    current += s
groups.append(current)
print("planned partitions:", len(sizes_kb))
print("after coalescing  :", len(groups), "partition(s) of", groups, "KB")
planned partitions: 200 after coalescing : 1 partition(s) of [225] KB
  • target_kb = 64 * 1024 # advisoryPartitionSizeInBytes = 64 MBAdjacent small partitions are merged up to this size.

9 Quiz and revision

Check yourself

Quick revision

Lesson 7.4 in one screen

  • AQE re-plans at run time from real stage sizes; on by default since 3.2.
  • Coalescing: 204 tasks → 5, 1.74 → 0.62 s; plan AQEShuffleRead coalesced.
  • Join switching: SMJ → broadcast when a side is measured small (0.89 → 0.05 s).
  • Skew join: split big partitions (3.67 → 1.92 s), SortMergeJoin(skew=true).
  • Skew thresholds: 5× median and 256 MB by default; joins only.
  • Read the final plan (isFinalPlan=true) after running or in the Spark UI.
  • Set shuffle partitions high enough; tune the advisory size.

Interview and viva questions

Should I still set spark.sql.shuffle.partitions?

Yes, as an upper bound high enough for the biggest input; AQE merges partitions but does not create more (except when splitting skew).

Does AQE work with caching?

Yes, and cached data provides statistics; very complex plans may limit re-optimization.

Does AQE work in Structured Streaming?

Not for micro-batch streaming queries in general; it targets batch queries.

Can AQE make things slower?

Rarely; e.g. coalescing to too few partitions for a later heavy stage. Tune the advisory size or minPartitionNum.

What about dynamic partition pruning?

A separate optimization: filters from a dimension join prune partitions of a fact table at run time; it works together with AQE.

  • Check the final plan for AQEShuffleRead coalesced.

Data engineeringMid-level

Slow skewed join

One task of a join takes most of the time.

The interviewer is checking: skew handling?

Show a strong answer
  1. Check for SortMergeJoin(skew=true) in the final plan.
  2. If absent, compare partition sizes with skew thresholds; tune them.
  3. Fall back to salting or broadcasting the small side.

Avoid: Adding executors.

PlatformSenior

Platform defaults

Set Spark SQL defaults for hundreds of jobs.

The interviewer is checking: tuning strategy?

Show a strong answer
  • AQE on; shuffle partitions high; advisory size by cluster size.
  • Runtime broadcast threshold sized to executor memory.
  • Monitor final plans and task skew in the UI/history server.

Avoid: Turning AQE off for predictability.
