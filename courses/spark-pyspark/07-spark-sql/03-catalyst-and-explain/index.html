Catalyst and explain

Every DataFrame and SQL query passes through Catalyst. This lesson reads all four plans of a real join, shows the rewrites the optimizer makes (pushdown, pruning, constant folding, join strategy), whole-stage code generation, and the limits of optimization. All outputs are real (PySpark 4.3.0).

2 Definition

The Catalyst optimizer

Formal definition (write this in exams)

Catalyst is Spark SQL’s extensible query optimizer. A query from SQL or the DataFrame API passes through four phases: an unresolved (parsed) logical plan; analysis, which resolves names and types against the catalog; logical optimization, which applies rule-based rewrites such as predicate pushdown, column pruning, constant folding and filter combination (and cost-based join reordering when statistics are available); and physical planning, which chooses operators such as broadcast hash or sort-merge joins. The physical plan is then compiled by whole-stage code generation (Tungsten) into Java bytecode that fuses operators. With Adaptive Query Execution the physical plan can be revised at run time (Lesson 7.4). explain() displays these plans.

In simple words

Catalyst rewrites your query into the fastest plan it can find: it moves filters to the data, reads only needed columns, simplifies expressions and picks join methods. explain() shows you the result, so you can check what Spark will really do.

Catalyst at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A route planner

  • You tell the map app where to go; it reads the request (parse), checks the places exist (analyze), finds shortcuts (optimize) and picks roads and vehicles (physical plan).
  • Two people describing the same trip in different words get the same route.
  • A stop the app knows nothing about (a UDF) cannot be optimised around.

Intermediate The API

  • df.explain() (physical), explain(mode="extended") (all four), "formatted" (numbered operators with details), "cost" (statistics), "codegen" (generated Java).
  • In SQL: EXPLAIN [EXTENDED | FORMATTED | COST | CODEGEN] SELECT ….
  • Look for: PushedFilters, ReadSchema, join strategy, Exchange (shuffles), *(n) code-generated stages.

Advanced What the lab showed

  • Two filters written after a join were moved below it and into both scans; (1 + 1) + 798 became 800.
  • Parquet received 5 pushed filters and read 4 of 6 columns; the 2,000-row customer table was broadcast.
  • A “bad” and a “good” version of a query had identical optimized plans; a UDF filter pushed nothing.

Exam tip: “What does Catalyst do?” It turns DataFrame/SQL queries into an optimized physical plan in four phases: parse, analyze (resolve names via the catalog), optimize logically with rules (predicate pushdown, column pruning, constant folding, CBO join reordering with stats) and plan physically (choose join and aggregation strategies), then whole-stage code generation compiles it. Write clear code; check with explain().

Four plans for one join

All outputs are real: PySpark 4.3.0, local mode. The query joins 5,000,000 orders (Parquet) with 2,000 customers (CSV), adds GST, keeps Gold customers’ delivered orders above ₹800. Plan ids (#12) are removed for readability.

7 Run the code

Run the code: a toy optimizer

A simplified model of Step 2’s rewrites. Press Run, then try the challenges.

# A tiny optimizer: constant folding + predicate pushdown (toy model)
plan = ["scan orders", "scan customers", "join", "filter status = DELIVERED",
        "filter plan = Gold", "filter amount > 1 + 1 + 798"]

def optimize(plan):
    out, pushed = [], {"orders": [], "customers": []}
    for step in plan:
        if step.startswith("filter"):
            cond = step.replace("1 + 1 + 798", str(1 + 1 + 798))     # constant folding
            side = "customers" if "plan" in cond else "orders"     # which table owns the column
            pushed[side].append(cond)
        elif step != "join":
            out.append(step)
    return pushed, out + ["join"]

pushed, rest = optimize(plan)
print("pushed below join:", pushed)
print("remaining:", rest)
pushed below join: {'orders': ['filter status = DELIVERED', 'filter amount > 800'], 'customers': ['filter plan = Gold']} remaining: ['scan orders', 'scan customers', 'join']

  • side = "customers" if "plan" in cond else "orders" # which table owns the columnEach filter goes to the side whose columns it uses.

  • explain(mode=…): simple, extended, formatted, cost, codegen; SQL EXPLAIN ….
  • Rewrites: predicate pushdown (below joins, into scans), column pruning, constant folding (1+1+798 → 800).

Interview and viva questions

Is the order of my where/select calls important?

Usually not; Catalyst reorders filters and projections. It matters for things it cannot see through, like UDFs or caching points.

What is CBO?

Cost-based optimization: with ANALYZE statistics and spark.sql.cbo.enabled=true, Catalyst estimates cardinalities to reorder multi-way joins.

Can I see the plan that actually ran?

Yes: the SQL / DataFrame tab of the Spark UI, or explain() after an action (isFinalPlan=true).

Can Catalyst be extended?

Yes, with custom rules and strategies via SparkSessionExtensions (mostly in Scala); data sources can implement pushdown interfaces.

Does caching affect plans?

Yes: cached DataFrames appear as InMemoryRelation scans and later queries reuse them.
