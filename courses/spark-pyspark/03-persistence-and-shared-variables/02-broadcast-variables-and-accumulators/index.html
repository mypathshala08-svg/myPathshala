Broadcast variables and accumulators

Executors cannot see the driver’s variables. Spark offers two safe ways to share data with them: broadcast variables, read-only values sent once to every executor, and accumulators, counters that tasks add to. This lesson measures both on our cluster and tests every rule that decides whether an accumulator is right. All outputs are real (Spark 4.3.0).

2 Definition

Broadcast variables and accumulators

Formal definition (write this in exams)

Spark provides two kinds of shared variables. A broadcast variable wraps a read-only value created on the driver and distributes it efficiently to each executor once, where it is cached and shared by all tasks, instead of shipping a copy with every task’s closure. An accumulator is a variable that tasks can only add to through an associative and commutative operation, and whose value only the driver can read; Spark merges the updates of successful tasks. Updates performed inside actions are applied exactly once per task; updates inside transformations may be applied again if a stage is recomputed, so they are suitable for debugging and monitoring rather than exact results. Spark SQL uses broadcasting for broadcast hash joins, sending a small table to every executor so the large side does not need to be shuffled.

In simple words

A broadcast variable sends a read-only value (like a lookup table) to every executor once. An accumulator is a counter that tasks add to and the driver reads. Broadcasts make lookups and small-table joins fast; accumulators are exact inside actions, but can count twice inside transformations.

Shared variables at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Notice boards and tally sheets

  • A broadcast variable is a notice pinned once in every kitchen: all cooks read it, nobody changes it.
  • An accumulator is a tally sheet: cooks only add marks, and only the head chef reads the total.
  • Copying the whole notice into every order slip (a closure) works, but wastes paper and time.

Intermediate The API

  • b = sc.broadcast(value); tasks read b.value; free with b.unpersist() or b.destroy().
  • acc = sc.accumulator(0); tasks call acc.add(x); the driver reads acc.value. Custom types with AccumulatorParam.
  • For DataFrames, F.broadcast(small_df) asks for a broadcast hash join; Spark also does it automatically below spark.sql.autoBroadcastJoinThreshold (10 MB by default).

Advanced What the lab showed

  • A 400,000-entry dict in the closure: 14.8 s for 3 jobs and a 2.1 MiB pickled function shipped per job; as a broadcast: 8.2 s, shipped once.
  • After unpersist(), using the broadcast again failed in PySpark 4.3 (FileNotFoundError); after destroy(), Spark refused at once.
  • An accumulator inside map counted 1 bad row as 2 over two uncached actions; with cache or inside foreach it was exact; a failed and retried task was not double counted.

Exam tip: “What are broadcast variables and accumulators?” Shared variables: broadcast variables send a read-only value to each executor once (lookup tables, small-table joins); accumulators let tasks add to a value that only the driver reads (counters). Accumulators are guaranteed exactly-once only for updates made inside actions.

Accumulators are not a way to compute results. Use them for monitoring (how many rows were bad, how many API calls failed) and compute real totals with aggregations. In our lab, one bad row was reported as 2 simply because two actions recomputed the same uncached map.

4 Step by step

Measuring shared variables

All outputs are real: Spark 4.3.0 standalone cluster with two executors (Steps 1–4) and local mode with up to 3 attempts per task (Steps 5–7). Data: 2,000,000 generated order pairs, a 400,000-customer plan dictionary, orders_big, customers.csv and orders.csv.

  1. Step 1 · A lookup table in the closure vs a broadcast

    plans = {cid: R.choice(["Gold", "Silver", "Basic", "Basic"]) for cid in range(400_000)}
orders = sc.parallelize(range(2_000_000), 16).map(lambda i: (i % 400_000, (i * 7919) % 900 + 60))

for _ in range(3):      # A: dict captured by the lambda
    orders.map(lambda kv: (plans[kv[0]], kv[1])).reduceByKey(add).collect()

b = sc.broadcast(plans)
for _ in range(3):      # B: dict read through the broadcast
    orders.map(lambda kv: (b.value[kv[0]], kv[1])).reduceByKey(add).collect()
    broadcast: 8.2 s for 3 jobs same result: True
    Identical revenue per plan, 45% less time. With the dictionary in the closure, every job shipped the function together with the whole dictionary and every one of the 16 tasks unpickled its own copy. With a broadcast, each executor fetched it once and its Python workers reused it across tasks and jobs.

  2. Step 2 · What actually travelled

    grep "Block broadcast_.*_piece0 stored" driver.log
    closure version: one ~2.1 MiB broadcast of the pickled function per job broadcast_0_piece0 2.1 MiB broadcast_3_piece0 2.1 MiB broadcast_6_piece0 2.1 MiB broadcast_9_piece0 1982.0 KiB
    PySpark already protects you a little: a pickled function over 1 MB is sent as a broadcast automatically. That is the 2.1 MiB block created for each of the three closure jobs (broadcast 0, 3 and 6). Our explicit broadcast (9) was created once, and the three jobs that used it only shipped a small function holding a reference.

  3. Step 3 · The end of a broadcast: unpersist and destroy

    b.unpersist()
orders.map(lambda kv: b.value[kv[0]]).first()

    b.unpersist() then orders.map(lambda kv: b.value[kv[0]]).first() WARN TaskSetManager: Lost task 0.0 in stage 12.0 … PythonException FileNotFoundError: [Errno 2] No such file or directory: '…/broadcast_9_python' ERROR TaskSetManager: Task 0 in stage 12.0 failed 4 times; aborting job b.destroy() then the same map [INTERNAL_ERROR_BROADCAST] Attempted to use Broadcast(9) after it was destroyed (destroy at <unknown>:0) SQLSTATE: XX000
    unpersist() deletes the executors’ copies. The documentation says a later use re-sends it, but in PySpark 4.3 the Python workers looked for their local file and the task failed 4 times. destroy() also deletes the driver’s copy, and Spark refused at task-serialisation time. Practical rule: call them only when you are completely done with the variable, then drop the Python reference.

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")

With broadcasting disabled, both sides were shuffled for a sort-merge join (6.1 s). Same counts. On bigger clusters the gap grows with the size of the large side.   5. Step 5 · Accumulators inside transformations can double count

    bad = sc.accumulator(0)
def parse(l):
    f = l.split(",")
    if not f[5].isdigit():
        bad.add(1)
        return None
    return int(f[5])
amounts = lines.map(parse)
amounts.count(); amounts.filter(lambda x: x is not None).count()
print(bad.value)                                # no cache

amounts = lines.map(parse).cache()
amounts.count(); amounts.filter(lambda x: x is not None).count()
print(bad.value)                                # with cache
    1) inside a transformation, 2 actions, no cache: 2 (real bad rows: 1) 2) same, with cache(): 1
    orders.csv has exactly one row with amount = abc. Two actions on the uncached RDD ran parse twice per line (Lesson 2.3), so the accumulator said 2. With cache(), parse ran once: 1. Any recomputation (an evicted cache, a lost executor, a reused stage) can inflate counters updated in transformations.

  6. Step 6 · Exact inside actions, safe across retries

    bad.value = 0
lines.foreach(lambda l: bad.add(0 if l.split(",")[5].isdigit() else 1))

seen = sc.accumulator(0)
def flaky(x):
    seen.add(1)
    if TaskContext.get().partitionId() == 0 and TaskContext.get().attemptNumber() == 0:
        raise RuntimeError("simulated executor hiccup")
    return x
sc.parallelize(range(1000), 2).map(flaky).count()
    3) inside an action (foreach): 1 4) task 0 failed once and was retried: count = 1000 | accumulator = 1000
    Inside the foreach action, the count was exactly 1. In the second test, the first attempt of task 0 added to the accumulator and then failed; Spark retried it and the job counted 1,000 rows. The accumulator also said 1,000, not 1,001: updates from failed attempts are discarded. The danger is successful work done twice, not failures.

  7. Step 7 · A custom accumulator for data quality

    class CounterParam(AccumulatorParam):
    def zero(self, v): return {}
    def addInPlace(self, a, b):
        for k, v in b.items(): a[k] = a.get(k, 0) + v
        return a
reasons = sc.accumulator({}, CounterParam())
def check(l):
    f = l.split(",")
    if not f[5].isdigit(): reasons.add({"amount not a number": 1})
    if "/" in f[4]: reasons.add({"timestamp format": 1})
    if f[7] == "CANCELLED": reasons.add({"cancelled": 1})
lines.foreach(check)
    5) custom accumulator (dict of reasons): {'cancelled': 3063, 'amount not a number': 1, 'timestamp format': 1}
    One pass over the 50,001 orders produced a small report: 3,063 cancelled orders, one bad amount and one bad timestamp, the two broken rows from Lesson 1.1. zero gives each task an empty dict; addInPlace merges dicts and must be associative and commutative. Keep accumulator values small: they travel to the driver with every task result.

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.2 in one screen

  • Broadcast: sc.broadcast(v), read b.value; sent once per executor, shared by tasks.
  • Lab: dict in closure 14.8 s (2.1 MiB per job) vs broadcast 8.2 s (sent once). PySpark auto-broadcasts closures > 1 MB, but per job.
  • unpersist() / destroy() only when completely done (reuse failed in PySpark 4.3).
  • DataFrames: broadcast hash join for small tables (auto < 10 MB, or F.broadcast): 4.8 s vs 6.1 s sort-merge.
  • Accumulator: tasks add, driver reads; custom types via AccumulatorParam.
  • Exact in actions (foreach); may double count in transformations when recomputed (1 bad row → 2).
  • Failed task attempts are not counted (1,000, not 1,001). Use aggregations for business totals.

Interview and viva questions

How big can a broadcast be?

It must fit in the driver and in every executor’s memory, alongside tasks. Lookup tables of a few to a few hundred MB are typical; gigabyte-sized broadcasts usually cause memory problems.

Can I update a broadcast variable?

No. Broadcasts are read-only. To change the value, create a new broadcast (and destroy the old one when no running job uses it).

Are accumulators visible in the Spark UI?

Named accumulators (created with a name in Scala/Java) appear on the stage pages. PySpark accumulators are mainly read on the driver.

Why not just use a global variable?

Each task gets a copy of the closure, so changes never reach the driver (Lesson 2.2). Accumulators are designed to send updates back.

Does Spark SQL use broadcast variables internally?

Yes. BroadcastExchange in a plan sends the small side of a join to every executor as a hash table, the same mechanism as sc.broadcast.

Real-world scenario questions (asked in company interviews)

Shared-variable questions test whether you understand distribution.

Any company · SparkFresher

Broadcast variables

What is a broadcast variable and when do you use it?

The interviewer is checking: do you know the use case?

Show a strong answer

A read-only value, such as a lookup table, sent once to every executor and cached there, so tasks can read it without shipping it with every task. I use it for lookups in RDD code and Spark uses the same idea for broadcast joins with small tables. In our test it cut a lookup job from 14.8 to 8.2 s.

Avoid: Saying broadcast variables can be updated by tasks.

Data engineeringMid-level

Accumulator shows wrong count

An accumulator counting bad rows shows double the real number.

The interviewer is checking: do you know accumulator semantics?

Show a strong answer
  1. It is updated inside a transformation; the stage ran twice (two actions, no cache).
  2. Move the update into an action, cache the parsed data, or compute with filter().count().
  3. Use accumulators for monitoring, not results.

Avoid: Dividing the value by two.

Data engineeringMid-level

Small-table join is slow

Joining 5 billion orders with 2,000 customers takes long and shuffles a lot.

The interviewer is checking: do you know broadcast joins?

Show a strong answer
  • Check explain(): SortMergeJoin with shuffles of both sides.
  • Use F.broadcast(customers) or raise autoBroadcastJoinThreshold moderately.
  • Verify BroadcastHashJoin in the plan and less shuffle in the UI.

Avoid: Repartitioning the big table first.

PlatformSenior

Broadcast-related OOMs

After raising the broadcast threshold to 2 GB, drivers and executors crash.

The interviewer is checking: can you reason about memory?

Show a strong answer
  • The driver collects and builds the broadcast; every executor holds a copy next to its tasks.
  • Measure in-memory sizes; keep thresholds in tens to hundreds of MB.
  • Use sort-merge, bucketing or AQE for big-to-big joins.

Avoid: Raising memory everywhere without limits.
