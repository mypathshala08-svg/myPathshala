Checkpointing and fault tolerance

Spark recovers from failures by recomputing from lineage, but recomputation can be slow and lineages can grow too long. This lesson shows when a checkpoint helps, what it costs, and how it compares with a cache when a worker really disappears on our cluster. All outputs are real (Spark 4.3.0).

1 The story

“The lost worker took two hours with it”

Before you start: lineage in 2.3, worker loss in 1.3 and caching in 3.1.

TiffinGo’s fraud model scores every order with an expensive Python function, then joins the scores with ten other datasets. One night a cloud node was reclaimed during the joins. The cached scores on that node vanished and Spark quietly recomputed them: the job finished, two hours late.

Kabir

Sir, Spark recovered. Isn’t that what fault tolerance means?

Arjun Sir

It is. Spark rebuilds lost partitions from their lineage, as we saw in Lessons 1.3 and 2.3. But if rebuilding means re-running expensive work, or the lineage has grown very long, recovery is slow. A checkpoint writes the data to reliable storage and cuts the lineage there.

Riya

So should we checkpoint instead of caching?

Arjun Sir

They solve different problems, and a checkpoint has its own costs. Today we grow a lineage until it is long, checkpoint it, count how often the work runs, speed up a 400-step DataFrame, and stop a worker to compare cache with checkpoint. All outputs are real (Spark 4.3.0).

2 Definition

Checkpointing and Spark’s fault tolerance

Formal definition (write this in exams)

Spark achieves fault tolerance mainly through lineage: failed tasks are retried (up to spark.task.maxFailures, 4 by default), lost shuffle outputs and cached partitions are recomputed from their parent RDDs. Checkpointing saves the partitions of an RDD or DataFrame to files in a reliable checkpoint directory and replaces its lineage with a reference to those files, so later recovery reads the files instead of recomputing the chain. Reliable checkpoints of RDDs are lazy: they are written by an additional job after the first action, which recomputes the RDD unless it is persisted. Local checkpoints truncate lineage using executor-local storage and therefore do not survive executor loss. Checkpointing is used for very long lineages (iterative algorithms, loops of unions or joins), for expensive results that must survive failures, and in Structured Streaming to store progress and state.

In simple words

Spark recovers from failures by redoing lost work using lineage. A checkpoint saves data to safe storage and forgets the lineage, so recovery reads the saved files instead of redoing everything. It costs an extra write, so use it when lineages are long or recomputing is expensive.

Checkpointing at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Saving your game

  • Lineage is the list of moves from the start of the game; if you lose, you replay every move.
  • A cache is a quick save in memory: fast, but lost if the machine restarts.
  • A checkpoint is a save to the cloud: slower to make, but you restart from there, not from the beginning.

Intermediate The API

  • sc.setCheckpointDir(path) on reliable storage (HDFS, S3, shared disk), then rdd.checkpoint() or df.checkpoint().
  • RDD checkpoints are lazy and run as an extra job after the first action, recomputing the RDD unless it is cached. DataFrame checkpoint() is eager by default and returns a new DataFrame.
  • localCheckpoint() cuts lineage using executor storage only: fast, but not fault tolerant.

Advanced What the lab showed

  • 30 unions grew a lineage to 92 lines; after a checkpoint, 2 lines pointing at a ReliableCheckpointRDD of 34 files.
  • Without cache, checkpointing ran the work function 20,000 times for 10,000 elements; with cache 10,000.
  • After a worker was stopped, a cached RDD recomputed 200,000 expensive calls; a checkpointed one recomputed none and answered in 0.8 s.

Exam tip: “Cache vs checkpoint?” Cache keeps data on executors and keeps the lineage; it is fast but lost with the executor and recomputed from lineage. Checkpoint writes to reliable storage and truncates the lineage; it costs a write but survives failures and stops lineages from growing. Cache before checkpointing an RDD to avoid computing it twice.

A checkpoint is not a backup or a table. Files in the checkpoint directory are written in Spark’s internal format for this application; they are not meant to be read by other jobs and are not cleaned up automatically by default (spark.cleaner.referenceTracking.cleanCheckpoints is false). Put the directory on reliable storage, give it a lifecycle rule, and write real outputs as tables.

4 Step by step

Long lineages, checkpoints and a lost worker

All outputs are real: PySpark 4.3.0 in local mode (Steps 1–5) and on our standalone cluster with a checkpoint directory on storage shared by all containers (Step 6).

  1. Step 1 · Watching a lineage grow

    r = sc.parallelize(range(100_000), 4).map(lambda x: (x % 100, 1))
for i in range(30):
    r = r.mapValues(lambda v: v + 1)
print(len(r.toDebugString().decode().splitlines()))

day = sc.parallelize([(0, 1)], 1)
for i in range(30):                      # append one small batch per day
    r = r.union(day)
print(len(r.toDebugString().decode().splitlines()), r.getNumPartitions())
    30 x mapValues -> lineage lines: 2 (PySpark fuses narrow Python steps) + 30 x union -> lineage lines: 92 | partitions: 34
    Thirty mapValues did not grow the lineage at all: PySpark fused them into one Python step (Lesson 2.3). Thirty unions did: 92 lines and 34 partitions. Loops that union, join or reduce in every iteration (daily appends, graph algorithms, iterative ML) grow lineages like this. Long lineages make scheduling slower and recovery expensive.

  2. Step 2 · Checkpoint: lazy, then cut

    sc.setCheckpointDir("/root/lab/spark/data/ckpt")
r.checkpoint()
print(r.isCheckpointed())
r.count()
print(r.isCheckpointed(), r.getCheckpointFile())
print(r.toDebugString().decode())
    checkpoint() called; isCheckpointed: False after count(); isCheckpointed: True | file: <ckpt>/<uuid>/rdd-62 lineage now: (34) UnionRDD[62] at union at DirectMethodHandleAccessor.java:103 [] | ReliableCheckpointRDD[64] at count at l33_ckpt.py:20 [] files: <ckpt>/<uuid>/rdd-62/part-00000 … part-00033 (34 files)
    checkpoint() only marked the RDD. The next action computed it and wrote one file per partition (34) into a sub-folder with a random id for this SparkContext. The lineage now ends at a ReliableCheckpointRDD: 92 lines became 2. Any later action or recovery reads those files.

  3. Step 3 · A checkpoint computes the RDD twice, unless cached

    calls = sc.accumulator(0)
def work(x):
    calls.add(1); return x * 2
a = sc.parallelize(range(10_000), 4).map(work); a.checkpoint(); a.count()
b = sc.parallelize(range(10_000), 4).map(work).cache(); b.checkpoint(); b.count()
    no cache : work() calls = 20000 with cache: work() calls = 10000
    The action computed the RDD once for count(), then Spark started a separate job to write the checkpoint and computed it again: 20,000 calls for 10,000 elements. With cache() first, the checkpoint job read the cached partitions: 10,000 calls. The documentation’s advice, confirmed: persist an RDD before checkpointing it.

  4. Step 4 · localCheckpoint: fast, but not safe

    c = sc.parallelize(range(1000), 2).map(lambda x: x + 1)
c.localCheckpoint(); c.count()
print(c.toDebugString().decode())
    lineage: (2) PythonRDD[74] at RDD at PythonRDD.scala:59 [Disk Memory Deserialized 1x Replicated] | new files: 0
    The lineage was cut, but no files were written: the data sits in executor storage with a disk-and-memory level. Good for cutting very long lineages in iterative algorithms when speed matters more than surviving executor loss; if an executor dies, its locally checkpointed partitions cannot be rebuilt and the job fails.

  5. Step 5 · A DataFrame built in a loop

    def build(n, ck_every=None):
    df = spark.range(200_000).withColumn("v", F.lit(0))
    for i in range(n):
        df = df.withColumn("v", F.col("v") + F.col("id") % 7)
        if ck_every and (i + 1) % ck_every == 0:
            df = df.checkpoint()          # eager: writes now, returns a new DataFrame
    return df
    100 steps, checkpoint every None: 6.1 s plan lines 102 sum 59999400 200 steps, checkpoint every None: 4.6 s plan lines 202 sum 119998800 400 steps, checkpoint every None: 9.9 s plan lines 402 sum 239997600 400 steps, checkpoint every 50 : 5.7 s plan lines 1 sum 239997600
    Each withColumn added a node to the logical plan: 400 steps meant a 402-line plan that Catalyst had to analyse and optimise again and again, 9.9 s in total. Checkpointing every 50 steps kept the plan at one line (a scan of the checkpoint) and took 5.7 s, writes included. For small loops the checkpoint was not worth it; that is why it is a tool for long chains, not a habit.

  6. Step 6 · A worker dies: cache vs checkpoint

    sc.setCheckpointDir("/data/ckpt_cluster")          # shared by all containers
calls = sc.accumulator(0)
r = sc.parallelize(range(400_000), 8).map(expensive).cache()
if mode == "checkpoint":
    r.checkpoint()
r.count()                         # 1st action
# … docker stop sparklab-spark-worker-2-1 …
r.count()                         # 2nd action, one executor fewer
    cache: first count 400000 in 6.4 s, expensive() calls 400000 ERROR TaskSchedulerImpl: Lost executor 0 on 172.19.0.5: worker lost: 172.19.0.5:46785 got disassociated cache: after worker loss count 400000 in 1.9 s, extra expensive() calls 200000 checkpoint: first count 400000 in 7.8 s, expensive() calls 400000 ERROR TaskSchedulerImpl: Lost executor 0 on 172.19.0.5: worker lost: 172.19.0.5:36421 got disassociated checkpoint: after worker loss count 400000 in 0.8 s, extra expensive() calls 0
    Both runs lost executor 0 with half of the cached partitions. The cached-only RDD rebuilt those 4 partitions from lineage: 200,000 extra calls to the expensive function. The checkpointed RDD read its files from shared storage: 0 extra calls, 0.8 s. The first run with a checkpoint was slower (7.8 s vs 6.4 s) because of the extra write. Pay that when recomputation is expensive or workers are unreliable.

6 Real-world use

Checkpoints at work

1. Iterative algorithms

PageRank-style and connected-component jobs checkpoint every few iterations to keep lineage short.

Round n→checkpoint→Round n+1

2. Expensive feature steps

Costly feature computations are cached and checkpointed before long training or joining phases.

Features→checkpoint→Training

3. Streaming queries

Every Structured Streaming query keeps offsets and state in a checkpoint location to restart exactly where it stopped.

Kafka→checkpoint→Restart safely

4. Cheap, unreliable compute

Jobs on spot instances checkpoint expensive intermediate results so reclaimed nodes cost minutes, not hours.

Spot loss→read files→Continue

5. DataFrame loops

Code that builds DataFrames in loops checkpoints periodically to keep Catalyst’s plans small.

Loop→df.checkpoint()→Small plan

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.3 in one screen

  • Fault tolerance: task retries (maxFailures 4), recompute lost shuffle output and cached blocks from lineage.
  • sc.setCheckpointDir() on reliable storage; checkpoint() writes files and cuts the lineage (92 → 2 lines).
  • RDD checkpoints are lazy and use an extra job: cache first (20,000 → 10,000 calls).
  • localCheckpoint(): lineage cut, no files, not fault tolerant.
  • DataFrame checkpoint() is eager and resets long plans (400 steps: 9.9 s → 5.7 s).
  • Worker lost: cache-only recomputed 200,000 calls; checkpointed recomputed 0 (0.8 s).
  • Checkpoint files are internal and not cleaned by default; write real outputs as tables.

Interview and viva questions

Is a checkpoint the same as saving a table?

No. A checkpoint is for the running application: internal format, tied to a SparkContext, used to cut lineage and speed up recovery. To share data with other jobs, write a table (Parquet, Delta, Iceberg).

Does Structured Streaming use the same checkpoints?

It uses a checkpoint location for a different purpose: offsets, commits and state for exactly-once processing. That directory must never be deleted while the query is in use (Module 9).

Should I always checkpoint?

No. A checkpoint costs a full write and, without cache, a recomputation. Use it for long lineages and expensive results on unreliable infrastructure.

Can I read a checkpoint after restarting the application?

Not through the public RDD API in a new application; reliable checkpoints are meant for the application that wrote them. That is another reason to write tables for reuse.

What is speculative execution?

With spark.speculation=true, Spark starts a copy of tasks that run much slower than others and uses whichever finishes first. It helps with slow nodes, not with failures.

Real-world scenario questions (asked in company interviews)

Fault-tolerance questions show whether you know how Spark really recovers.

Any company · SparkFresher

“How is Spark fault tolerant?”

Explain Spark’s fault tolerance.

The interviewer is checking: do you know lineage and retries?

Show a strong answer

Failed tasks are retried; lost partitions, including shuffle output and cached data, are recomputed from lineage, the record of transformations. Checkpointing saves data to reliable storage and cuts the lineage so recovery reads files. In our test, a checkpointed RDD needed no recomputation after a worker was lost.

Avoid: “Spark replicates all data three times like HDFS.”

Data engineeringMid-level

Cache vs checkpoint

When do you use cache, checkpoint, or both?

The interviewer is checking: can you choose by goal?

Show a strong answer
  • Cache: reuse within the application, fast, lost with executors.
  • Checkpoint: cut long lineages, make expensive results survive failures; extra write.
  • Both: cache then checkpoint, so the checkpoint does not recompute.

Avoid: Checkpointing every DataFrame.

Data engineeringMid-level

Loop gets slower each iteration

A loop building a DataFrame slows down and the driver uses lots of CPU.

The interviewer is checking: do you recognise plan growth?

Show a strong answer
  1. Each iteration adds nodes; Catalyst re-analyses a growing plan.
  2. Checkpoint every n iterations, or restructure into fewer, wider steps.
  3. Measure: our 400-step loop went from 9.9 to 5.7 s.

Avoid: Adding executors (the driver is the bottleneck).

PlatformSenior

Recovery design on spot capacity

Nightly jobs on spot nodes often finish hours late.

The interviewer is checking: can you design for failure?

Show a strong answer
  • Driver on on-demand capacity; executors on spot.
  • Checkpoint expensive intermediate results to S3/HDFS; enable decommissioning to migrate blocks.
  • Write final results as tables; monitor recomputed tasks and stage retries.
