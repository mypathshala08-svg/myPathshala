1 The story

“Just cache everything”

Before you start: Lesson 2.3 (why every action recomputes) and 1.3 (executors).

After Module 2, Kabir has a new habit: he adds .cache() to every DataFrame. His morning report on TiffinGo’s five million orders got faster. Then one night the job died with “Command exited with code 52” on every executor, and nobody could explain why caching, of all things, broke it.

Kabir

Sir, caching made things faster. How can it crash a job?

Arjun Sir

Cached data takes executor memory, the same memory your tasks need to run. Spark offers several storage levels: memory only, memory and disk, disk only, serialised or not, replicated or not. Pick the wrong one, or cache data in partitions too big for the executor, and you trade speed for failures.

Riya

So when should we cache, and how?

Arjun Sir

Cache only what several actions reuse, choose a storage level that fits, check the Storage tab, and unpersist when done. Today we measure every level on our cluster with five million orders, look at the Storage tab, and reproduce Kabir’s crash. All outputs are real (Spark 4.3.0).

2 Definition

Persistence and storage levels

Formal definition (write this in exams)

Persistence (caching) instructs Spark to keep the computed partitions of an RDD or DataFrame on the executors after the first action that computes them, so later actions read them instead of recomputing the lineage. persist(level) chooses a storage level: whether to use memory, local disk or off-heap memory, whether to store objects serialised, and how many replicas to keep; cache() uses the default level (MEMORY_AND_DISK for DataFrames and Datasets, stored in Spark’s compressed in-memory columnar format; MEMORY_ONLY for RDDs). Cached blocks share executor memory with task execution and are evicted in least-recently-used order under pressure; with MEMORY_ONLY evicted partitions are recomputed, with MEMORY_AND_DISK they are written to local disk. Persistence is lazy, is lost with its executor, and should be released with unpersist().

In simple words

cache() or persist() keeps data on the executors after it is first computed, so the next actions are faster. You choose where: memory, disk or both. It uses memory that tasks also need, so cache only what you reuse and remove it when finished.

Caching at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Keeping cooked food on the counter

  • Without caching, every new order cooks the dish from scratch.
  • cache() keeps a cooked batch on the counter (memory); if the counter is full, some goes to the fridge (disk).
  • An overfull counter leaves no room to cook: the kitchen stops.

Intermediate The API

  • df.cache() = persist() with the default level: MEMORY_AND_DISK for DataFrames (deserialised, columnar), MEMORY_ONLY serialised for PySpark RDDs.
  • persist(StorageLevel.X): MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY, the _2 variants (two replicas), OFF_HEAP.
  • Caching is lazy: the first action fills it. SQL CACHE TABLE is eager; CACHE LAZY TABLE is not. Release with unpersist(), UNCACHE TABLE or spark.catalog.clearCache().

Advanced What the lab showed

  • The second query took 6.7 s uncached and 2.1–2.7 s with any storage level; filling the cache made the first query slower (21–29 s vs 15 s).
  • 5,000,000 rows with 128-character notes needed 651 MiB of cache over 32 partitions.
  • The same data in only 4 partitions killed every 1 GiB executor while caching (exit code 52 = OutOfMemoryError); the job was aborted after 4 attempts.

Exam tip: “cache() vs persist()?” cache() is persist() with the default level (MEMORY_AND_DISK for DataFrames, MEMORY_ONLY for RDDs). persist() lets you choose: MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY, replicated _2 levels or OFF_HEAP. Both are lazy and need an action to fill; release with unpersist().

A cache is not free. In our lab, the first query with caching took 21–29 s against 15 s without, because Spark had to build the cache. If a dataset is used once, or is as cheap to read from Parquet as from the cache, caching makes the job slower and steals memory from tasks.

Run the code: should I cache?

A small cost model with the timings measured in Step 4: caching costs extra once and saves time on every reuse. Press Run, then try the challenges.

# When does caching pay off? A cost model using the lab's timings
read_and_compute = 6.7     # s: a query without cache (2nd run, lab)
from_cache = 2.4           # s: a query reading the cache (lab: 2.1-2.7)
fill_extra = 6.2           # s: extra time to build the cache on first use (lab: 21.5 vs 15.3)

for uses in (1, 2, 3, 5, 10):
    no_cache = uses * read_and_compute
    cached = (read_and_compute + fill_extra) + (uses - 1) * from_cache
    better = "cache" if cached < no_cache else "no cache"
    print(f"{uses:2} uses: no cache {no_cache:5.1f} s | cache {cached:5.1f} s -> {better}")

Interview and viva questions

Is cache() the same as persist()?

Yes, cache() is persist() with the default storage level. Use persist() when you want a different level, such as DISK_ONLY.

Does caching survive the end of the application?

No. Cached blocks live in executors and disappear when the application stops or an executor is lost. To reuse data across jobs, write it to storage.

Why is a cached DataFrame so much smaller than the raw data?

Spark caches DataFrames in a columnar format with compression per column, so repeated values (cities, statuses) take very little space. Random strings, like our hashes, do not compress.

How much memory can caches use?

Executors share one unified region between execution and storage (spark.memory.fraction, 0.6 of the heap minus 300 MB by default). Caches can use most of it when tasks do not need it, and are evicted when tasks do (Lesson 8.4).

Should I cache before a write?

Only if the same DataFrame is also used by another action. A single write does not benefit from caching.

Data engineeringMid-level

When not to cache

A colleague caches every DataFrame. Is that good?

The interviewer is checking: do you know the costs?

Show a strong answer
  • Caching costs time to fill and memory that tasks need.
  • Cache only data reused by several actions; unpersist after.
  • For data used once, or cheap to reread from Parquet, caching makes jobs slower.

Avoid: “Caching is always good.”

PlatformMid-level

Executors exit with code 52

After adding cache(), executors die with exit code 52.

The interviewer is checking: can you diagnose memory problems?

Show a strong answer
  1. Exit code 52 = OutOfMemoryError in the executor JVM.
  2. Check cached size and partition sizes in the Storage/Stages tabs.
  3. Repartition to smaller partitions, use DISK_ONLY or MEMORY_AND_DISK, add executor memory, or drop the cache.

ArchitectureSenior

Caching strategy for a shared cluster

Many teams share a cluster; caches cause evictions and failures.

Show a strong answer
