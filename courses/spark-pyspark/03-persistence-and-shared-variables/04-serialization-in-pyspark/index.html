1 The story

The hidden tax of moving Python objects

Before you start: 3.2 Broadcast.

🤔 A one-line lambda that looks up a price from a dict. Why did Spark send 2.8 MB with every single task?

Because PySpark must serialize your function, and everything it captures, to send it to Python workers on the executors. The dict came along each time. With a broadcast the same function was 635 bytes. Serialization is the hidden tax in PySpark: code with cloudpickle, rows with pickle or Arrow. In our lab Arrow made toPandas() 6.5× faster (14.5 s → 2.2 s), while the old “use MarshalSerializer” advice made no measurable difference.

2 Definition

Serialization in PySpark

Formal definition (write this in exams)

Serialization converts objects to bytes for transfer or storage. PySpark serializes user functions and their closures with cloudpickle, transfers RDD records between the JVM and Python workers using batched pickle (or marshal) serializers, and uses Apache Arrow columnar batches for pandas conversions and vectorized UDFs. JVM-side data uses Spark’s internal binary formats or the configured JVM serializer (Java or Kryo).

In simple words

To run your Python code on many machines, Spark turns your function and data into bytes. What your function “carries” matters most; Arrow moves whole columns at once and is much faster than row by row.

Why, how, where

Why

Python objects live in one process. To run your function on 100 executors, or move records between Python and the JVM, Spark must turn them into bytes and back. That costs CPU, memory and network, and some objects cannot be turned into bytes at all.

the problem it solves

How

Your functions (and captured variables) are serialized with cloudpickle and shipped with each task. RDD records move between the JVM and Python workers as batched pickled bytes (AutoBatchedSerializer). DataFrame↔pandas transfers and pandas/Arrow UDFs use Apache Arrow columnar batches. JVM-only data (DataFrames, shuffles) uses Spark’s own binary formats; Kryo is a JVM option.

the mechanism

Where

Every UDF, map/filter lambda, broadcast, collect/toPandas and createDataFrame from Python objects.

in real systems

When not

Large captured objects inflate every task; unpicklable objects (locks, DB connections, sockets) fail; pickle is Python-only and trusts its input.

See the hidden payload

Serialization at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Packing for a trip

  • Every worker needs your recipe (function). If you tape the whole pantry (big dict) to each recipe card, every card becomes heavy. Better: put the pantry in each kitchen once (broadcast) and keep the card light.

Intermediate What PySpark uses

  • Functions: cloudpickle (can serialize lambdas and closures that plain pickle cannot).
  • RDD records: SparkContext(serializer=…), default CloudPickle/Pickle wrapped in AutoBatchedSerializer; MarshalSerializer only for simple built-in types.
  • DataFrames: stay in the JVM; Arrow is used for toPandas(), createDataFrame(pandas), pandas/Arrow UDFs and (Spark 4) Arrow-optimized Python UDFs (spark.sql.execution.arrow.pyspark.enabled, …pythonUDF.arrow.enabled).

Advanced Pitfalls

  • Closures capture referenced variables (and sometimes self): check size with pyspark.cloudpickle.dumps(f). Broadcast large read-only data.
  • Unpicklable objects (locks, connections, clients): create them inside mapPartitions/foreachPartition, once per partition.
  • Kryo (spark.serializer=org.apache.spark.serializer.KryoSerializer) affects JVM objects (RDDs of JVM types, shuffles in Scala jobs), not Python objects.

Myth vs reality: things many websites still say

  • Myth: MarshalSerializer makes PySpark fast.
    Reality (Spark 4.3): No clear gain in our fair test.
    Proof: Step 3.
  • Myth: Kryo speeds up PySpark UDFs.
    Reality (Spark 4.3): Kryo is JVM-side only.
    Proof: Table.
  • Myth: Small code = small tasks.
    Reality (Spark 4.3): Captured data rides along.
    Proof: Step 2: 2.8 MB.

Exam tip: “Why are serializers needed in PySpark?” To ship functions (cloudpickle) and data between driver, JVM and Python workers; MarshalSerializer (fast, limited types) vs PickleSerializer (any object); batched; Arrow for pandas/vectorized UDFs; avoid big closures (broadcast); Kryo is for JVM objects.

Do not copy “switch to MarshalSerializer” advice blindly: in our lab it was not faster once the JVM was warm, and it fails on custom classes. The big wins are avoiding large closures (broadcast instead), keeping work in DataFrames, and enabling Arrow for pandas transfers.

    Plain pickle cannot ship lambdas; cloudpickle can, and it ships everything they capture.

    SparkContext(conf=conf, serializer=MarshalSerializer())

  4. Step 4 · Unpicklable objects

    lock = threading.Lock()
sc.parallelize([1, 2]).map(lambda x: (x, lock)).collect()
    == 4) a closure that cannot be serialized Could not serialize object: TypeError: cannot pickle '_thread.lock' object fix: create the object inside the task (mapPartitions) or broadcast plain data

    bb = sc.broadcast(big)
h = lambda x: bb.value.get(x, 0)
    == 5) broadcast instead of capturing big data lambda using a broadcast: 635 bytes per task; data sent once per executor result: [2, 4, 6]
    The task closure shrinks to 635 bytes; the dict travels once per executor.

  6. Step 6 · Arrow for pandas

    spark.conf.set("spark.sql.execution.arrow.pyspark.enabled", arrow)
df.toPandas()   # 2,000,000 rows

Run the code: what a closure carries

Captured data travels with the function. Press Run, then try the challenges.

# What does a function carry? (pickle sizes in plain Python)
import pickle
prices = {f"item-{i}": i for i in range(50000)}

def make_lookup(table):
    return lambda name: table.get(name, 0)      # closure captures `table`

small = make_lookup({"idli": 45})
big = make_lookup(prices)
# cloudpickle would serialize the captured table; here we measure the table itself
print("captured small table:", len(pickle.dumps({"idli": 45})), "bytes")
print("captured big table:  ", len(pickle.dumps(prices)), "bytes  <- sent with every task")
print(small("idli"), big("item-7"))

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.4 in one screen

  • Functions → cloudpickle; RDD records → batched pickle/marshal; pandas ↔ Spark → Arrow.
  • Captured variables travel with every task: 2.8 MB vs 635 B with broadcast.
  • Marshal: simple types only; no clear win in a fair test.
  • Unpicklable objects (locks, clients) → create per partition.
  • Kryo is JVM-side; Arrow toPandas 14.5 → 2.2 s.

Interview and viva questions

Can I use Kryo for PySpark?

It only changes how the JVM serializes JVM objects; Python objects still use pickle/cloudpickle/Arrow.

Is pickle safe?

Only unpickle data you trust; Spark uses it internally between its own processes.

Why AutoBatchedSerializer?

It groups records into batches sized by speed, reducing per-record overhead.

Does Spark Connect change this?

UDFs are still pickled and run in Python workers on the server side.
