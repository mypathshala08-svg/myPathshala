UDFs

When built-in functions are not enough, you can run your own Python code. This lesson compares built-ins with classic, Arrow-optimised and pandas UDFs on 5 million rows, shows what UDFs hide from the optimizer, the null and type traps, and Spark 4’s SQL UDFs. All outputs are real (PySpark 4.3.0).

1 The story

“It is only three lines of Python”

Before you start: Arrow in 4.6, built-in text and date functions in 6.4.

Riya wrapped a three-line function that labels orders “low”, “mid” or “high” in a udf, because it was easier than remembering Spark functions. The nightly job slowed down by minutes, a filter on the label stopped skipping Parquet data, and one night it crashed on a null amount.

Riya

Sir, the function is trivial. Why is it slow?

Arjun Sir

Not the function: the trip. Each value leaves the JVM, is serialised to a Python worker, processed, and sent back. And Catalyst cannot see inside your function, so it cannot push filters down or simplify anything.

Kabir

Then why do UDFs exist at all?

Arjun Sir

Because sometimes you need a Python library. Then use the fastest kind. Today: the same logic as a built-in, a classic Python UDF, an Arrow-optimised UDF and a pandas UDF on 5 million rows; plans; pushdown; nulls and return types; and SQL UDFs in Spark 4. All outputs are real (PySpark 4.3.0).

2 Definition

User-defined functions

Formal definition (write this in exams)

A user-defined function (UDF) extends Spark SQL with custom logic. In PySpark, a Python UDF executes in Python worker processes: the executor JVM serialises input rows (with pickle, or with Apache Arrow for Arrow-optimised UDFs, the default since Spark 4.2), the worker evaluates the function and returns results. A pandas UDF (vectorised UDF) receives and returns batches as pandas Series via Arrow. UDFs are opaque to the Catalyst optimizer: predicates involving them cannot be pushed down to data sources, and their results are not used for constant folding or other rewrites; their declared return type must match the values returned. SQL UDFs (Spark 4.0) are defined with a SQL expression body and are inlined into the plan, so they run like built-in expressions.

In simple words

A UDF lets you run your own function on each row. Python UDFs are slow because data travels to Python and back, and Spark cannot optimise them. Use built-in functions first, a pandas UDF when you need Python libraries, and SQL UDFs to reuse expressions.

UDFs at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Asking a translator

  • Spark’s own functions speak Spark’s language: fast and understood by the planner.
  • A Python UDF is like sending every sentence to a translator in another room and waiting for the answer.
  • Arrow and pandas UDFs send a whole page at a time instead of one sentence.

Intermediate The API

  • F.udf(func, returnType, useArrow=…) or @udf; @pandas_udf("type") on a function from pd.Series to pd.Series.
  • For SQL: spark.udf.register("name", func, type); SQL UDFs: CREATE FUNCTION f(x INT) RETURNS … RETURN expr.
  • spark.sql.execution.pythonUDF.arrow.enabled is true by default since Spark 4.2.

Advanced What the lab showed

  • Same result: built-in 0.85 s, pickled Python UDF 3.50 s, Arrow UDF 2.31 s, pandas UDF 2.10 s.
  • A UDF in a filter disabled Parquet pushdown: 4.09 s vs under 1 s.
  • A UDF declared int returning 472.5 gave None (pickled) or 472 (Arrow), silently.

Exam tip: “Why avoid Python UDFs?” Data must be serialised between the JVM and Python workers, the function runs row by row in Python, and Catalyst treats it as a black box, so filters on it are not pushed down and no optimisation applies. In our lab the same label took 0.85 s as a built-in and 3.50 s as a pickled UDF; a UDF filter on Parquet lost pushdown and took 4.09 s.

A Python UDF receives None for nulls, and if its result does not match the declared type it may silently become null or be truncated rather than fail. Always handle None first, declare the exact return type, and test the UDF on edge cases (nulls, empty strings, unexpected types) before running it on production data.

4 Step by step

One label, five implementations

All outputs are real: PySpark 4.3.0 with pandas 3.0 and PyArrow, local mode with 4 cores, 5,000,000 cached orders. Each timing is the second run of a fresh query.

  1. Step 1 · Arrow for Python UDFs is on by default

    spark.conf.get("spark.sql.execution.pythonUDF.arrow.enabled")
    == 1) defaults pythonUDF.arrow.enabled: true
    Since Spark 4.2 regular Python UDFs use Arrow to move data to Python workers unless you pass useArrow=False or turn the setting off. Old jobs upgraded to Spark 4.2+ get this change automatically, including its different type coercion (Step 5).

  2. Step 2 · The same label four ways

    def band(a):
    return "high" if a >= 600 else "mid" if a >= 300 else "low"
plain = udf(band, "string", useArrow=False); arrowed = udf(band, "string", useArrow=True)
@pandas_udf("string")
def band_pd(a: pd.Series) -> pd.Series:
    return pd.cut(a, [-1, 299, 599, 10**9], labels=["low", "mid", "high"]).astype(str)
builtin = F.when(F.col("amount") >= 600, "high").when(F.col("amount") >= 300, "mid").otherwise("low")
    == 2) same result four ways, 5M rows built-in when() : 0.85 s [('high', 1998942), ('low', 1333511), ('mid', 1667547)] Python UDF (pickle) : 3.50 s [('high', 1998942), ('low', 1333511), ('mid', 1667547)] Python UDF (Arrow) : 2.31 s [('high', 1998942), ('low', 1333511), ('mid', 1667547)] pandas UDF : 2.10 s [('high', 1998942), ('low', 1333511), ('mid', 1667547)]
    All four gave identical counts. The built-in expression took 0.85 s; the classic pickled UDF 3.50 s (4x slower), the Arrow UDF 2.31 s, the vectorised pandas UDF 2.10 s. The gap grows with more columns and more complex plans, and on a cluster each executor needs Python workers too.

  3. Step 3 · A black box in the plan

    o.where(plain(F.col("amount")) == "high").select("order_id").explain()
o.where(builtin == "high").select("order_id").explain()
    == 3) the plan: a black box == Physical Plan == *(1) Project [order_id] +- *(1) Filter (pythonUDF0 = high) +- BatchEvalPython [band(amount)], [pythonUDF0] +- InMemoryTableScan [order_id, amount] == Physical Plan == *(1) Project [order_id] +- *(1) Filter CASE WHEN (amount >= 600) THEN true WHEN (amount >= 300) THEN false ELSE false END +- InMemoryTableScan [amount, order_id], [CASE WHEN (amount >= 600) THEN true WHEN (amount >= 300) THEN false ELSE false END]
    With the UDF, the plan has a BatchEvalPython node: rows go to Python, the result comes back as pythonUDF0 and only then is filtered. With the built-in, the condition is an ordinary expression that Spark could even push into the in-memory scan. Catalyst can rearrange and simplify only what it can see.

  4. Step 4 · UDFs stop pushdown

    p = spark.read.parquet(path)
upper_city = udf(lambda c: c.upper() if c else None, "string")
p.where(F.upper("city") == "PUNE").count()
p.where(upper_city("city") == "PUNE").count()
p.where(F.col("city") == "Pune").count()
    == 4) a UDF blocks pushdown on Parquet built-in : 498646 rows, 0.45 s, PushedFilters: [IsNotNull(city)], ReadSchema: struct<order_id:bigint,c UDF : 498646 rows, 4.09 s, PushedFilters: [], ReadSchema: struct<order_id:bigint,customer_id:int, plain filter: 498646 rows, 0.80 s, PushedFilters: [IsNotNull(city), EqualTo(city,Pune)], ReadSchema: stru
    All three found 498,646 Pune orders. The plain filter was pushed into the Parquet scan (EqualTo(city,Pune)); the built-in upper at least pushed IsNotNull; the UDF pushed nothing, so every row had to travel through Python: 4.09 s against well under a second.

  5. Step 5 · Nulls and return types

    d = spark.createDataFrame([(450,), (None,)], "amount INT")
d.select(plain("amount")).collect()
safe = udf(lambda a: None if a is None else band(a), "string")
for arrow in (False, True):
    wrong = udf(lambda a: a * 1.05, "int", useArrow=arrow)   # returns 472.5
    == 5) None and errors inside a UDF UDF on None: TypeError: '>=' not supported between instances of 'NoneType' and 'int' null-safe UDF: ['mid', None] declared int, returned 472.5, useArrow=False: [None] declared int, returned 472.5, useArrow=True: [472]
    A null reached the function as None and crashed it with a Python TypeError, failing the job. Handle None first. Worse, a function returning 472.5 while declared int gave None with pickling and 472 with Arrow: wrong either way, and with no error. The Spark 4.2 default switch to Arrow can change such results silently.

  6. Step 6 · SQL UDFs and registering for SQL

    spark.sql("CREATE OR REPLACE TEMPORARY FUNCTION gst(amount INT) RETURNS DOUBLE RETURN round(amount * 0.05, 2)")
spark.sql("SELECT gst(530) AS gst").show()
spark.sql("SELECT sum(gst(amount)) FROM orders")      # plan: any Python step?
spark.udf.register("band", band, "string")
spark.sql("SELECT band(amount) b, count(*) n FROM orders GROUP BY b ORDER BY b").show()
    == 6) SQL UDF (Spark 4) +----+ | gst| +----+ |26.5| +----+ sum(gst) over 5M: 127345063.74999955 1.03 s plan has a Python step: False == 7) register a Python UDF for SQL +----+-------+ | b| n| +----+-------+ |high|1998942| | low|1333511| | mid|1667547| +----+-------+
    A SQL UDF, new in Spark 4, packages an expression under a name; it is inlined into the plan, so the 5M-row sum ran with no Python step, like a built-in. spark.udf.register makes a Python UDF callable from SQL, with all the costs above. Prefer SQL UDFs for reusable business rules such as GST.

7 Run the code

Run the code: per-row calls cost time

A plain-Python illustration of why fewer, bigger calls are faster. Press Run, then try the challenges.

# Row-at-a-time vs batch processing (why pandas UDFs are faster)
import time
amounts = list(range(50, 950)) * 500             # 450,000 values

def band(a):
    return "high" if a >= 600 else "mid" if a >= 300 else "low"

t = time.time()
out1 = [band(a) for a in amounts]                # one call per value
t1 = time.time() - t

t = time.time()
cuts = {a: band(a) for a in set(amounts)}        # a "batch" trick: compute per distinct value
out2 = [cuts[a] for a in amounts]
t2 = time.time() - t
print(f"per row: {t1:.3f} s | batched: {t2:.3f} s | same: {out1 == out2}")
per row: 0.020 s | batched: 0.012 s | same: True
  • out1 = [band(a) for a in amounts] # one call per valueA classic Python UDF also pays serialisation per row.

9 Quiz and revision

Check yourself

Quick revision

Lesson 6.6 in one screen

  • Built-ins first: 0.85 s vs Python UDF 3.50 s on 5M rows.
  • Arrow-optimised Python UDFs are the default since 4.2 (2.31 s); pandas UDFs vectorise (2.10 s).
  • UDFs are black boxes: BatchEvalPython in the plan, no pushdown (4.09 s).
  • Handle None; a crash in Python fails the job.
  • Declare exact return types: 472.5 as int → None (pickle) or 472 (Arrow).
  • SQL UDFs (Spark 4) are inlined: no Python step.
  • For models: pandas UDF / mapInPandas with a broadcast model.

Interview and viva questions

Are Scala/Java UDFs faster?

Yes, they run in the JVM without serialisation, but they are still opaque to Catalyst. Built-ins remain best.

Can a UDF return a struct or array?

Yes; declare the type, e.g. "struct<band:string,score:double>" or "array<string>".

How do I mark a UDF non-deterministic?

udf(...).asNondeterministic(), so Spark does not assume it can call it any number of times with the same result.

Do UDFs work with Spark Connect?

Yes; Python UDFs are sent to the server and run in its Python workers. Dependencies must be available there.

What is a Python UDTF?

A table function (Spark 3.5+) that returns zero or more rows per input, decorated with @udtf; useful for splitting or expanding records.

Any company · PySparkFresher

“What is a UDF?”

Explain UDFs and when to use them.

The interviewer is checking: basics and costs?

Show a strong answer

A user-defined function runs custom logic on columns. Python UDFs run in Python workers, so data is serialised back and forth and Catalyst cannot optimise them. I use built-in functions first, pandas UDFs for vectorisable Python, and SQL UDFs for reusable expressions.

Avoid: “UDFs are the normal way to transform data.”
