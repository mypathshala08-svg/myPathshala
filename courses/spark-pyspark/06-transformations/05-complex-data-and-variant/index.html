Complex data and VARIANT

Orders contain lists of dishes, preference maps and nested objects, and app payloads arrive as JSON that changes with every release. This lesson works with arrays, maps and structs without exploding, parses JSON with a schema, and uses Spark 4’s VARIANT type for evolving payloads. All outputs are real (PySpark 4.3.0).

1 The story

“The app team changed the payload again”

Before you start: nested schemas in 4.2, JSON reading in 5.1.

TiffinGo’s app sends every order as a JSON string with dishes, coupons and rider details. Each release adds or changes a field. Kabir’s pipeline parses the payload with a fixed schema; when one release sent "items": "none" instead of a list, those orders came out with every field null, including the order id.

Kabir

Sir, one field was wrong. Why did the whole record become null?

Arjun Sir

from_json parses the record as a whole: if any field does not fit the schema, the record is null. Spark 4 offers another way: store the payload as VARIANT and extract fields one at a time, each with its own type.

Riya

And arrays inside the record? Do we always explode them?

Arjun Sir

Not always. Spark has functions that work inside arrays: transform, filter, aggregate. Today: arrays, maps and structs, explode and its variants, JSON strings with from_json, then VARIANT, and a speed test on a million payloads. All outputs are real (PySpark 4.3.0).

2 Definition

Complex types and VARIANT

Formal definition (write this in exams)

Spark SQL supports complex types: ARRAY<T> (ordered elements of one type), MAP<K, V> (key-value pairs) and STRUCT<…> (named fields), which can be nested. Higher-order functions such as transform, filter, exists and aggregate apply lambda expressions to array elements inside the JVM without exploding. explode produces one row per element (dropping rows with null or empty arrays), explode_outer keeps them with null. JSON text is parsed with from_json against a schema; in the default PERMISSIVE mode a record that does not match yields null. The VARIANT type (Spark 4.0, GA in 4.1) stores semi-structured data in a binary encoding without a fixed schema; parse_json creates it and variant_get/try_variant_get extract a path cast to a requested type.

In simple words

Columns can hold lists, maps and nested objects. Spark has functions to work inside lists without breaking them apart, and explode when you need one row per item. JSON can be parsed with a fixed schema, or stored as VARIANT and read field by field, which survives changing payloads.

Complex data at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A tiffin box

  • An order is a tiffin box with compartments (a struct), a list of dishes (an array) and a note card of preferences (a map).
  • Exploding is taking every dish out and putting it on its own plate.
  • VARIANT is accepting the box as it comes and opening only the compartments you need.

Intermediate The API

  • Types: ArrayType, MapType, StructType, VariantType (Spark 4.0+). Access: col[0], col["key"], col.field / "a.b".
  • Arrays: size, array_contains, transform, filter, aggregate, arrays_zip, explode/explode_outer/posexplode.
  • JSON: from_json, to_json, schema_of_json, get_json_object; VARIANT: parse_json, variant_get, try_variant_get, schema_of_variant, SQL v:path::type.

Advanced What the lab showed

  • explode gave 5 rows from 3 orders (the empty one vanished); explode_outer gave 6.
  • With from_json, the payload with "items": "none" became all-null; VARIANT still returned its order id.
  • Summing one field over 1M JSON strings took 1.9–2.4 s; over a stored VARIANT column, 0.62 s.

Exam tip: “explode vs explode_outer?” explode returns one row per array element and drops rows whose array is null or empty; explode_outer keeps those rows with a null element. In our lab 3 orders gave 5 rows with explode and 6 with explode_outer: the order with no dishes disappeared from the first.

explode multiplies rows and silently drops records with empty or null arrays. Before exploding, ask whether a higher-order function would do: totals, filters and lookups inside arrays (aggregate, filter, exists) keep one row per order and avoid a later re-aggregation.

Nested orders and changing payloads

All outputs are real: PySpark 4.3.0, local mode with 4 cores. Steps 1–5 use three small orders and payloads; Step 6 uses 1,000,000 generated JSON payloads.

  1. Step 1 · Working inside arrays

    o.select("order_id", F.size("dishes"), F.array_contains("dishes", "Dosa"),
    F.transform("prices", lambda p: p * 105 / 100), F.filter("prices", lambda p: p >= 60),
    F.aggregate("prices", F.lit(0), lambda acc, p: acc + p), F.arrays_zip("dishes", "prices"))

    Each function worked on the whole array, still one row per order: GST added to every price, cheap items filtered out, totals summed with aggregate, and dishes paired with prices by arrays_zip. The Python lambdas are translated into Spark expressions; they do not run in Python.

    Five dishes, five rows; order 9103 with an empty list vanished. explode_outer kept it as a sixth row with a null dish. posexplode also returned the position, useful when order inside the array matters.

  3. Step 3 · Maps and structs

    o.select("order_id", F.col("notes")["spice"], F.map_keys("notes"), "rider.name", F.col("rider.rating"))
    == 3) maps and structs +--------+------+----------------+----+------+ |order_id| spice| keys|name|rating| +--------+------+----------------+----+------+ | 9101|medium|[cutlery, spice]|Ravi| 4.8| | 9102| high| [spice]|Asha| NULL| | 9103| NULL| NULL|NULL| NULL| +--------+------+----------------+----+------+
    Map values are read by key (null if the key is missing); map_keys lists keys. Struct fields are read with a dot. A null struct gives null fields rather than an error, so 9103 (no rider) simply shows nulls.

  4. Step 4 · JSON strings with from_json

    raw.select(F.schema_of_json(F.lit(raw.first().payload)))
sch = "order_id INT, items ARRAY<STRUCT<dish: STRING, qty: INT>>, tip INT, coupon STRUCT<code: STRING, pct: INT>"
raw.select(F.from_json("payload", sch).alias("j")).select("j.order_id", "j.items", "j.tip", "j.coupon.code")
    == 4) JSON strings: from_json, schema_of_json, to_json schema_of_json (row 1): STRUCT<items: ARRAY<STRUCT<dish: STRING, qty: BIGINT>>, order_id: BIGINT, tip: BIGINT> +--------+------------+----+------+ |order_id|items |tip |code | +--------+------------+----+------+ |1 |[{Thali, 2}]|20 |NULL | |2 |[] |NULL|FEST20| |NULL |NULL |NULL|NULL | +--------+------------+----+------+ {"id":9,"tags":["a","b"]}
    schema_of_json inferred a schema from one example, which missed coupon because the first payload had none: never infer from a single record. With a full schema, missing fields became null. But payload 3, where items was the string "none", came back entirely null, order id included: one bad field cost the whole record.

  5. Step 5 · VARIANT

    v = raw.select(F.parse_json("payload").alias("v"))
v.select(F.variant_get("v", "$.order_id", "int"), F.variant_get("v", "$.items[0].dish", "string"),
         F.variant_get("v", "$.coupon.code", "string"), F.schema_of_variant("v"))
v.select(F.variant_get("v", "$.items", "array<struct<dish string, qty int>>"))
v.select(F.try_variant_get("v", "$.items", "array<struct<dish string, qty int>>"))
spark.sql("SELECT parse_json('{\"a\": 1}'):a::int AS a, …")
    == 5) VARIANT root |-- v: variant (nullable = true) +--------+-----+------+---------------------------------------------------------------------------------------+ |order_id|dish0|coupon|schema | +--------+-----+------+---------------------------------------------------------------------------------------+ |1 |Thali|NULL |OBJECT<items: ARRAY<OBJECT<dish: STRING, qty: BIGINT>>, order_id: BIGINT, tip: BIGINT> | |2 |NULL |FEST20|OBJECT<coupon: OBJECT<code: STRING, pct: BIGINT>, items: ARRAY<VOID>, order_id: BIGINT>| |3 |NULL |NULL |OBJECT<items: STRING, order_id: STRING> | +--------+-----+------+---------------------------------------------------------------------------------------+ variant_get strict: SparkRuntimeException [INVALID_VARIANT_CAST] The variant value `"none"` cannot be cast into `"ARRAY<STRUCT<dish: STRI … +------------+ |items | +------------+ |[{Thali, 2}]| |[] | |NULL | +------------+ +---+---+ | a| b| +---+---+ | 1| 20| +---+---+
    Parsed as VARIANT, every payload kept its own shape (schema_of_variant shows three different schemas). Each field was extracted independently: payload 3’s order id, sent as the string "3", came back as 3, while its odd items did not affect anything else. Asking for items as an array failed loudly with INVALID_VARIANT_CAST; try_variant_get returned null instead. SQL has a short path syntax v:a.b[1]::int.

  6. Step 6 · Speed on 1M payloads

    j.select(F.sum(F.get_json_object("payload", "$.amount").cast("int")))
j.select(F.sum(F.from_json("payload", "amount INT").amount))
j.select(F.sum(F.variant_get(F.parse_json("payload"), "$.amount", "int")))
vt = j.select(F.parse_json("payload").alias("v")).cache()
vt.select(F.sum(F.variant_get("v", "$.amount", "int")))
    == 6) speed: 1M JSON strings, one field get_json_object : sum 474665655, 2.08 s from_json (schema) : sum 474665655, 2.43 s parse_json + variant_get : sum 474665655, 1.90 s variant_get on stored VARIANT: sum 474665655, 0.62 s
    All three ways to read one field from JSON text took about 2 s, because each must parse the text. Once the payload was stored as VARIANT (here cached; in practice written to a Delta or Parquet table), reading the field took 0.62 s: VARIANT’s binary encoding lets Spark jump to the field. Parse once at ingestion, then query many times.

Run the code: record-level vs field-level parsing

A model of Steps 4–5. Press Run, then try the challenges.

# from_json vs VARIANT on a payload with one bad field (simplified model)
import json
payloads = ['{"order_id": 1, "items": [{"dish": "Thali", "qty": 2}]}',
            '{"order_id": "3", "items": "none"}']

def from_json(p):                        # all fields must fit the schema
    d = json.loads(p)
    if not isinstance(d.get("items"), list):
        return {"order_id": None, "items": None}
    return {"order_id": int(d["order_id"]), "items": d["items"]}

def variant_get(p, key, cast):          # each field on its own
    try:
        return cast(json.loads(p)[key])
    except (KeyError, ValueError, TypeError):
        return None

for p in payloads:
    print("from_json  :", from_json(p))
    print("variant_get:", variant_get(p, "order_id", int))
from_json : {'order_id': 1, 'items': [{'dish': 'Thali', 'qty': 2}]} variant_get: 1 from_json : {'order_id': None, 'items': None} variant_get: 3

9 Quiz and revision

Check yourself

Quick revision

Lesson 6.5 in one screen

  • ARRAY, MAP, STRUCT: c[0], c["k"], c.f.
  • Higher-order functions: transform, filter, exists, aggregate: no explode needed.
  • explode drops empty/null arrays (5 rows); explode_outer keeps them (6).
  • from_json + schema: one bad field → whole record null. Do not infer from one example.
  • VARIANT: parse_json, variant_get/try_variant_get, schema_of_variant, SQL v:a.b::int.
  • Parse once: stored VARIANT read in 0.62 s vs ~2 s from text.
  • Promote hot fields to typed columns; keep the VARIANT for the rest.

Interview and viva questions

Can I write VARIANT to Parquet?

Yes, Spark 4 writes VARIANT to Parquet and Delta. Check that readers (other engines) support it before sharing.

Is explode expensive?

It multiplies rows; any later aggregation must shuffle them. Use higher-order functions when one row per record is enough.

How do I flatten a struct into columns?

df.select("order_id", "rider.*").

Can I update a field inside a struct?

F.col("rider").withField("rating", F.lit(5.0)); dropFields removes fields.

Are Python lambdas in transform slow?

No: they are converted to Spark expressions, not executed in Python, as long as you use Column operations inside.
