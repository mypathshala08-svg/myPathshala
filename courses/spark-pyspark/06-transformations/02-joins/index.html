Joins

Joins are where most data bugs hide: rows quietly lost or multiplied. This lesson runs every join type, shows what null and duplicate keys do, how to avoid ambiguous columns, and how Spark chooses between broadcast and sort-merge joins. All outputs are real (PySpark 4.3.0).

1 The story

“Half our orders disappeared”

Before you start: broadcast joins in 3.2, nulls in 4.4.

Kabir joined 5 million orders with the customer table to add customer plans. The revenue dashboard dropped by half overnight. The next week a colleague joined orders with a city-to-state table that had Pune twice, and Pune’s revenue doubled.

Kabir

Sir, a join should just add columns. How can it change the number of rows?

Arjun Sir

An inner join keeps only rows with a match: orders whose customer is not in the customer table vanish. And every match produces a row: if a key appears twice on the right, each order with that key appears twice.

Riya

So which join should Kabir have used?

Arjun Sir

A left join, and a check that the right-hand key is unique. Today: all join types on a tiny example, null keys, ambiguous columns, duplicate keys, the cost of joining 5 million rows, and broadcast vs sort-merge joins. All outputs are real (PySpark 4.3.0).

2 Definition

Joins

Formal definition (write this in exams)

A join combines rows from two DataFrames whose join condition evaluates to true. An inner join returns matched pairs only; left/right/full outer joins also return unmatched rows of the left, right or both sides with nulls for the other side; a left semi join returns left rows that have a match (without right columns) and a left anti join left rows without a match; a cross join returns the Cartesian product. Each match produces one output row, so duplicate keys multiply rows. Null keys never satisfy an equality condition; eqNullSafe (<=>) treats nulls as equal. Spark chooses a physical strategy: a broadcast hash join when one side is estimated below spark.sql.autoBroadcastJoinThreshold (10 MB by default) or hinted, otherwise usually a sort-merge join, which shuffles and sorts both sides by the key.

In simple words

A join puts matching rows from two tables side by side. Inner keeps only matches, left keeps every row of the left table, anti finds rows with no match. Duplicate keys multiply rows and null keys never match. Small tables are sent to every executor (broadcast), big ones are shuffled.

Joins at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Matching two lists

  • An order slip says “restaurant 101”; the restaurant list says “101 = Desai Mess”. A join writes the name on the slip.
  • Inner: keep only slips whose restaurant is on the list. Left: keep all slips, blank name if unknown.
  • If the list has 101 twice, the slip is photocopied twice.

Intermediate The API

  • a.join(b, on, how); on is a column name, a list of names (no duplicate key columns) or an expression (a.k == b.k).
  • how: inner (default), left, right, full, left_semi, left_anti, cross (crossJoin).
  • Strategies: broadcast hash join (small side ≤ spark.sql.autoBroadcastJoinThreshold, 10 MB), sort-merge join, shuffled hash join; hint with F.broadcast(df).

Advanced What the lab showed

  • Null keys matched nothing with == but did with eqNullSafe.
  • An inner join with the 2,000-customer table kept 2,498,734 of 5,000,000 orders; a duplicate Pune key added 498,646 rows.
  • Joining 5M orders with customers: broadcast 0.8 s, sort-merge (broadcast off) 3.2 s.

Exam tip: “Why did my row count change after a join?” An inner join drops rows without a match (our 5M orders became 2.5M because half the customer ids were missing from the dimension), and duplicate keys on the other side multiply rows (one duplicate Pune row added 498,646). Use left joins for enrichment, check the right key is unique, and compare counts before and after.

After a.join(b, a.k == b.k) both k columns stay, and any other column with the same name (like city) becomes ambiguous. Join on a list of names (a.join(b, ["k"])) to keep one key column, and rename or alias the other duplicates before or right after the join.

    orders.join(rest, orders.rest_id == rest.rest_id).where(orders.rest_id.isNull()).count()
orders.join(rest, orders.rest_id.eqNullSafe(rest.rest_id)).where(orders.rest_id.isNull()).count()

    Order 4 and “Unknown Kitchen” both have a null id, yet == did not match them: null = null is unknown (Lesson 4.4). eqNullSafe matched them. Usually not matching nulls is what you want; use null-safe joins only when null is a real, meaningful key.

    orders.join(promos, "city").count()          # Pune has 3 promo codes

On real data, a lookup table with Pune entered twice turned 498,646 Pune orders into 997,292 rows: Pune revenue doubled. Check uniqueness before joining: dim.groupBy(key).count().where("count > 1").

    custs = spark.read.csv(".../customers.csv", header=True, inferSchema=True)   # 2,000 rows
big.join(custs, "customer_id")                    # strategy from the plan

    The orders reference 4,000 customer ids but the customer table holds 2,000: the inner join silently returned 2,498,734 of 5,000,000 rows, Kabir’s missing half. Use left to enrich. The small table was broadcast automatically (0.8 s); with broadcast disabled Spark used a sort-merge join and took 3.2 s. Two big sides always need a sort-merge join (4.5 s here).

  6. Step 6 · Semi and anti joins for questions

    custs.join(big, "customer_id", "left_anti").count()     # never ordered
custs.join(big, "customer_id", "left_semi").count()     # ordered at least once
    == 7) semi/anti: who never ordered? customers: 2000 | never ordered: 1 | ordered: 1999
    Semi and anti joins answer “exists?” questions without duplicating rows: each customer appears at most once however many orders they have. Far better than a join followed by distinct, and the right tool for finding orphans in data-quality checks.

6 Real-world use

Joins at work

1. Fact + dimensions

Order facts are enriched with customer, restaurant and date dimensions using left broadcast joins.

Facts→left + broadcast→Wide table

2. Orphan checks

left_anti joins list facts whose keys are missing in the dimension.

Facts→left_anti→Alerts

3. Applying changes

Full outer joins between snapshots find inserted, updated and deleted rows.

Old + new→full join→Changes

4. Audience building

Semi and anti joins pick customers who ordered last month but not this month.

Customers→semi / anti→Campaign list

5. Linking records

Self-joins on device or phone find accounts that share identifiers.

Accounts→self-join→Linked pairs

# Join semantics with plain Python lists
orders = [(1, 101), (2, 102), (3, 103), (4, None), (5, 109)]       # (order_id, rest_id)
rest = {101: "Desai Mess", 102: "Nair Bhojanalay", 103: "Patel Thali", 104: "Rao Tiffins"}

inner = [(o, rest[r]) for o, r in orders if r in rest]
left = [(o, rest.get(r)) for o, r in orders]
anti = [o for o, r in orders if r not in rest]

print("inner:", inner)
print("left :", left)
print("anti :", anti)

9 Quiz and revision

Check yourself

Quick revision

Lesson 6.2 in one screen

  • Types: inner (default), left, right, full, left_semi, left_anti, cross.
  • Inner joins drop unmatched rows: 5M → 2,498,734 with an incomplete dimension.
  • Duplicate keys multiply rows: Pune 498,646 → 997,292.
  • Null keys never match with ==; eqNullSafe if they should.
  • Join on a list to keep one key; alias other duplicates (AMBIGUOUS_REFERENCE).
  • Broadcast hash join for small sides (0.8 s; 0.3 s hinted) vs sort-merge (3.2 s).
  • Check row counts and key uniqueness around every join.

Interview and viva questions

What is the difference between left_semi and inner?

left_semi returns each left row at most once and no right columns; inner returns one row per match with columns from both.

How do I join on two columns?

a.join(b, ["city", "order_date"]) or an expression with &.

How do I do a self-join?

Alias both sides: a = df.alias("a"); b = df.alias("b"); a.join(b, F.col("a.phone") == F.col("b.phone")).

Can I join on a range condition?

Yes, but non-equi joins cannot use hash or sort-merge strategies and may become nested-loop joins: very slow on large data.

What if a join is slow because of one hot key?

That is skew; AQE can split skewed partitions, or use salting (Lesson 8.3).

Data engineeringMid-level

Broadcast vs sort-merge

When does Spark broadcast a table?

The interviewer is checking: join strategies?

Show a strong answer
  1. When one side is estimated under the threshold (10 MB) or hinted.
  2. Small side copied to executors, big side not shuffled.
  3. Otherwise sort-merge: both sides shuffled and sorted.

Avoid: “Spark always shuffles for joins.”
