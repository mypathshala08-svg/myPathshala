1 The story

The object behind every PySpark job

Before you start: 1.3 Architecture.

🤔 Every PySpark program has one object that talks to the cluster. You rarely create it yourself any more, so what is it, and what breaks if you make two?

The SparkContext. Since Spark 2 it hides inside the SparkSession, but it still owns the connection to the master, the executors, shipped files and Python modules. In our lab, a second SparkContext raised ValueError: Cannot run multiple SparkContexts at once; a CSV shipped with addFile appeared on both workers at $SPARK_HOME/work/app-…/menu_prices.csv; and an environment variable reached the executors but not the driver.

  • SparkConf, SparkContext and SparkSession: who creates whom.
  • Shipping files (SparkFiles) and Python modules (addPyFile) to executors.
  • The parameters and settings you will meet in old code and interviews.

2 Definition

SparkConf, SparkContext and SparkFiles

Formal definition (write this in exams)

SparkConf holds key–value Spark properties for an application. The SparkContext is the driver-side connection to a cluster manager: it requests executors, schedules jobs, and distributes files (addFile) and Python dependencies (addPyFile); only one may be active per process. The SparkSession wraps a SparkContext for the DataFrame and SQL APIs. SparkFiles resolves local paths of files distributed with addFile.

In simple words

SparkConf is your settings list, SparkContext is the live link to the cluster, and SparkSession is the friendly front door built on it. SparkFiles tells each worker where its copy of a shipped file is.

Why, how, where

Why

Every job needs settings (app name, master, memory) and a live connection to the cluster. Many jobs also need a lookup file or a helper module on every executor.

the problem it solves

How

You describe settings in a SparkConf; SparkSession.builder…getOrCreate() creates (or reuses) one SparkContext that registers with the master and gets executors. sc.addFile copies a file to every executor’s work folder, where SparkFiles.get(name) finds it; sc.addPyFile does the same for Python modules and puts them on the path.

the mechanism

Where

Every PySpark program; small lookup files (price lists, ML models, GeoIP databases) and shared helper code on clusters; reading old RDD-era code; interviews.

in real systems

When not

One active SparkContext per Python process. Big files belong in storage (S3, HDFS) or a broadcast, not addFile. For many dependencies use packaged environments (Lesson 11.1).

SparkConf, SparkContext and SparkFiles at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Booking a kitchen

  • The order form (SparkConf) says what you need. The booking (SparkContext) gets you the kitchen and staff. The restaurant manager (SparkSession) gives you the menu and recipes on top. If every cook needs the price list, you photocopy it to each station (addFile).

Intermediate The API

  • SparkConf().setAppName(…).setMaster(…).set(key, value), conf.get(key), conf.getAll(); chainable.
  • SparkSession.builder.config(conf=conf).getOrCreate(); spark.sparkContext exposes version, master, appName, applicationId, defaultParallelism, pythonVer, uiWebUrl.
  • sc.addFile(path) + SparkFiles.get(name) / SparkFiles.getRootDirectory(); sc.addPyFile(path) for .py/.zip/.egg; spark.executorEnv.NAME for environment variables.

Advanced Details that matter

  • Precedence: values set in code on SparkConf beat spark-submit --conf, which beats spark-defaults.conf. Leave master out of code so the same script runs locally and on clusters.
  • Old SparkContext(master, appName, sparkHome, pyFiles, environment, batchSize, serializer, conf, gateway, jsc, profiler_cls) parameters still exist; serializer and profiler_cls appear in Lessons 3.4 and 8.7.
  • Spark Connect clients (Lesson 11.3) have no SparkContext at all: use spark.addArtifacts instead of addFile/addPyFile there.

Myth vs reality: things many websites still say

  • Myth: SparkContext is obsolete.
    Reality (Spark 4.3): It lives inside every SparkSession.
    Proof: Step 2.
  • Myth: You can open one context per team.
    Reality (Spark 4.3): One per process.
    Proof: Step 3.
  • Myth: Env vars set in Spark reach the driver.
    Reality (Spark 4.3): executorEnv is executors only.
    Proof: Step 6.

Exam tip: “SparkContext vs SparkSession?” SparkSession (2.0+) is the unified entry point wrapping one SparkContext; SparkConf holds settings (code > submit > defaults); addFile + SparkFiles.get for data files, addPyFile/--py-files for code; one active context per process.

Do not create SparkContext(...) in library code or notebooks that may already have one: use SparkSession.builder.getOrCreate() (or SparkContext.getOrCreate()). And never rely on executor files from addFile being present on the driver path: on the driver use SparkFiles.getRootDirectory().

defaults = {"spark.app.name": "default", "spark.executor.memory": "1g"}
submit   = {"spark.master": "spark://spark-master:7077", "spark.executor.memory": "2g"}

Interview and viva questions

Do I need SparkContext for DataFrames?

No, use the SparkSession; the context is still there for RDDs, files and status.

addFile or broadcast?

Broadcast for Python data you already have in the driver; addFile for files a library must open by path.

Can I stop and recreate the context?

Yes: spark.stop(), then build again (needed to change static settings).

What about --files?

spark-submit --files is the command-line equivalent of addFile.
