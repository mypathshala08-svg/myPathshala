Spark architecture: driver, executors and cluster managers

Every Spark program, from a laptop test to a 1,000-node job, has the same parts: a driver, a cluster manager and executors. This lesson shows each one at work on our Docker cluster, including what happens when a machine disappears. All outputs and screenshots are real.

1 The story

“Who actually does the work?”

Before you start: Lesson 1.2. Coming from Hadoop? Driver ≈ ApplicationMaster’s planning role, executors ≈ long-lived containers that run many tasks.

Riya ran her first PySpark job on the lab cluster. It printed the right report, but she has questions: her laptop sent the code, yet the work happened “somewhere”. Kabir wonders what happens if one of the machines dies halfway, as it once did during a Hive load.

Riya

Sir, where does my Python code actually run?

Arjun Sir

Your main program runs in the driver. The driver asks a cluster manager for resources, gets executors on worker machines, splits the job into tasks and sends them out. Executors run the tasks and keep cached data. The driver collects the results.

Kabir

And if a worker dies?

Arjun Sir

Then the driver notices, and recomputes the lost pieces on the executors that are left, using the recorded lineage. We will stop a worker in the middle of a job and watch. Everything today runs on our Spark 4.3.0 standalone cluster in Docker: one master, two workers with 2 cores and 2 GiB each.

2 Definition

Driver, cluster manager and executors

Formal definition (write this in exams)

A Spark application consists of a driver process and a set of executor processes. The driver runs the application’s main program, creates the SparkSession (and SparkContext), converts operations into a directed acyclic graph of stages, and schedules their tasks onto executors. Executors are launched on worker nodes by a cluster manager (Spark standalone, Hadoop YARN or Kubernetes); each runs tasks in a number of concurrent slots (cores), keeps data cached in memory or on disk, and serves shuffle data to other executors. Applications are isolated from each other; in client deploy mode the driver runs where the job was submitted, in cluster mode inside the cluster. If an executor is lost, the driver recomputes the lost partitions from their lineage.

In simple words

Every Spark program has one boss (the driver) and many workers (executors). A cluster manager gives the driver its executors. The driver splits the job into tasks; executors run them. If an executor dies, the driver redoes its part.

Spark architecture at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A restaurant kitchen

  • The head chef (driver) reads the order and plans the dishes.
  • The kitchen manager (cluster manager) decides which cooks and stoves are free.
  • The cooks (executors) cook their parts in parallel. If a cook leaves, the head chef gives that part to another cook.

Intermediate The pieces and their jobs

  • Driver: runs your program, holds the SparkSession, builds the DAG, schedules tasks, tracks results. One per application.
  • Cluster manager: Spark standalone, YARN or Kubernetes (Mesos was removed in Spark 4.0); or none in local[*] mode.
  • Executors: JVM processes on workers with a number of cores (task slots) and memory; they run tasks, store shuffle files and cached blocks. For Python functions they start Python worker processes.

Advanced What the lab showed

  • The master granted two executors (2 cores, 1 GiB each) instantly; they registered with the driver about 8 s later; the first task started 2 s after that.
  • Submitting a Python app in cluster deploy mode to a standalone master was refused; client mode worked.
  • Stopping a worker mid-stage lost an executor and its shuffle files; after a 77 s fetch timeout Spark resubmitted the missing tasks and still returned 5,000,000.

Exam tip: “Explain Spark’s architecture.” A driver runs the main program, builds the DAG and schedules tasks; a cluster manager (standalone, YARN, Kubernetes) allocates executors on worker nodes; executors run tasks in parallel, cache data and exchange shuffle data. Failures are handled by recomputing lost partitions from lineage.

The driver is a single point of failure for its application. Executors can be replaced; a crashed driver ends the job. Keep the driver light: avoid collect() of large results, which pulls all the data into the driver’s memory (Lesson 4.6).

4 Step by step

Watching driver, master and executors work

All outputs are real: Spark 4.3.0 in Docker (Lesson 1.5 builds this cluster), one standalone master and two workers with 2 cores and 2 GiB each, plus a history server. Logs are shortened; nothing else is changed.

  1. Step 1 · Local mode: everything in one JVM

    for master in ["local[1]", "local[2]", "local[*]"]:
    spark = SparkSession.builder.master(master).getOrCreate()
    sc = spark.sparkContext
    execs = sc._jsc.sc().getExecutorMemoryStatus().size()
    print(master, sc.defaultParallelism, execs)
    spark.stop()
    local[1] defaultParallelism=1 JVMs holding executors=1 (the driver itself) local[2] defaultParallelism=2 JVMs holding executors=1 (the driver itself) local[*] defaultParallelism=2 JVMs holding executors=1 (the driver itself)
    In local mode there is no cluster manager: the driver JVM also acts as the only executor, and the number in brackets is the number of task slots. local[*] used all 2 cores of the lab machine. Perfect for learning and tests, but there is no fault tolerance across machines.

  2. Step 2 · Submit to the cluster: executors are granted

    spark-submit --master spark://spark-master:7077 \
  --conf spark.eventLog.enabled=true --conf spark.eventLog.dir=/opt/spark-events \
  /jobs/m1/city_report.py
    10:06:43 SparkContext: Running Spark version 4.3.0 10:06:45 Scheduler: Connected to Spark cluster with app ID app-20261102100645-0003 10:06:45 Scheduler: Granted executor ID app-20261102100645-0003/0 on hostPort 172.19.0.3:33931 with 2 core(s), 1024.0 MiB RAM 10:06:45 Scheduler: Granted executor ID app-20261102100645-0003/1 on hostPort 172.19.0.5:46419 with 2 core(s), 1024.0 MiB RAM 10:06:52 Scheduler: Registered executor (172.19.0.3:45308) with ID 0 10:06:53 Scheduler: Registered executor (172.19.0.5:36474) with ID 1
    The driver connected to the master, which granted one executor on each worker within the same second: 2 cores and 1 GiB each (1 GiB is the default spark.executor.memory). The executors took about 7–8 s to start their JVMs and register with the driver. Only then can tasks run.

  3. Step 3 · The driver hands out tasks

    # same run, scheduler lines only
    10:06:55 DAGScheduler: Got job 0 (csv) with 1 output partitions 10:06:55 DAGScheduler: Submitting 1 missing tasks from ResultStage 0 (csv) 10:06:55 TaskSetManager: Starting task 0.0 in stage 0.0 (TID 0) (172.19.0.3,executor 0, partition 0) 10:06:57 TaskSetManager: Finished task 0.0 in stage 0.0 (TID 0) in 1340 ms on 172.19.0.3 (executor 0) (1/1) 10:06:57 DAGScheduler: Job 0 finished: csv, took 1539.877927 ms 10:06:57 DAGScheduler: Got job 1 (csv) with 1 output partitions 10:06:57 DAGScheduler: Submitting 1 missing tasks from ResultStage 1 (csv) 10:06:57 TaskSetManager: Starting task 0.0 in stage 1.0 (TID 1) (172.19.0.5,executor 1, partition 0) 10:06:59 TaskSetManager: Finished task 0.0 in stage 1.0 (TID 1) in 2032 ms on 172.19.0.5 (executor 1) (1/1) 10:06:59 DAGScheduler: Job 1 finished: csv, took 2089.045547 ms 10:07:00 DAGScheduler: Submitting 1 missing tasks from ShuffleMapStage 2 (show)
    For each job the driver’s DAGScheduler creates stages and submits their tasks; the TaskSetManager places each task on a free slot. Job 0 ran on executor 0, job 1 on executor 1: the driver uses whichever slot is free. Our small CSV is one partition, so each stage had only one task. (Why one show() started four jobs is Lesson 1.4.)

  4. Step 4 · Who did the work?

    curl -s http://localhost:18080/api/v1/applications/<app-id>/executors
    driver spark-master:45129 cores 0 tasks 0 task time 22.1 s 1 172.19.0.4:38307 cores 2 tasks 2 task time 2.5 s 0 172.19.0.5:43919 cores 2 tasks 2 task time 3.2 s
    The driver ran 0 tasks: it only planned and scheduled. The two executors shared the four tasks. “task time” for the driver is simply its uptime. The same numbers are on the Executors tab shown above.

  5. Step 5 · Client vs cluster deploy mode

    spark-submit --master spark://spark-master:7077 --deploy-mode cluster /jobs/m1/city_report.py
    Exception in thread "main" org.apache.spark.SparkException: Cluster deploy mode is currently not supported for python applications on standalone clusters.
    In client mode (the default, Steps 2–4) the driver ran inside the container where we typed spark-submit. Cluster mode puts the driver inside the cluster, so you can disconnect; Spark’s standalone manager refuses it for Python applications. On YARN and Kubernetes, Python apps can run in cluster mode (Lesson 11.2).

  6. Step 6 · A worker disappears in the middle of a job

    docker stop sparklab-spark-worker-2-1
    10:08:49 INFO Executor updated: app-20261102100821-0005/0 is now LOST (worker lost: 172.19.0.3:37881 got disassociated) 10:08:49 ERROR TaskSchedulerImpl: Lost executor 0 on 172.19.0.3: worker lost: 172.19.0.3:37881 got disassociated 10:08:49 INFO DAGScheduler: Resubmitted ShuffleMapTask(13, 1), so marking it as still running. 10:08:49 INFO DAGScheduler: Resubmitted ShuffleMapTask(13, 3), so marking it as still running. 10:08:49 INFO DAGScheduler: Shuffle files lost for host: 172.19.0.3 (epoch 4 10:10:06 WARN TaskSetManager: Lost task 12.0 in stage 13.0 (TID 39) (172.19.0.5 executor 1): FetchFailed(BlockManagerId(0, 172.19.0.3, 41879, None), shuffleId=3, mapIndex 10:10:06 INFO DAGScheduler: ShuffleMapStage 13 failed in 77448 ms due to FetchFailedException 10:10:06 INFO DAGScheduler: Resubmitting ShuffleMapStage 12 and ShuffleMapStage 13 due to fetch failure 10:10:06 INFO DAGScheduler: Submitting 2 missing tasks from ShuffleMapStage 12 (…) Vector(0, 2) 10:10:07 INFO DAGScheduler: Submitting 8 missing tasks from ShuffleMapStage 13 (…) Vector(1, 3, 10, 11, 12, 13, 14, 15) 10:10:07 INFO DAGScheduler: Job 7 finished: first at /jobs/m1/failover.py:9, took 88.022926 ms cities: 8 | orders: 5000000
    We stopped one worker while stage 13 was running. The driver marked executor 0 as lost and knew its shuffle files were gone too. Tasks reading those files waited until the fetch timed out (77 s), then failed with FetchFailed. Spark resubmitted the 2 lost map tasks of stage 12 and the 8 affected tasks of stage 13 on the surviving executor, using lineage. The job finished with the correct 5,000,000 orders. Slower, but right.

6 Real-world use

Architecture decisions at work

1. Spark on existing Hadoop clusters

Companies with Hadoop run Spark on YARN next to Hive, sharing HDFS, queues and security.

spark-submit→YARN→Executors

2. Spark on Kubernetes

Cloud-native teams run drivers and executors as pods, often with the Spark Operator or EMR on EKS.

Job→K8s→Pods

3. Cheap executors, safe driver

AWS cites Krux running Spark on ephemeral EMR clusters with Spot instances; the driver stays on reliable nodes.

Spot→executors→Lower cost

4. Serverless Spark

EMR Serverless, Dataproc Serverless and Databricks serverless hide the cluster manager entirely.

Code→service→Executors on demand

5. Unit tests in local mode

CI pipelines run PySpark tests with local[2]: same code, one JVM (Lesson 11.4).

Test→local[2]→Pass

Examples are simplified.

Run the code: a tiny task scheduler

These programs model what the driver does with executors and slots. Press Run, then try the challenges.

# Simulate a driver scheduling tasks onto executor slots (round robin on free slots)
executors = {"exec-0": 2, "exec-1": 2}     # cores = task slots
tasks = [f"task-{i}" for i in range(8)]

slots = [e for e, cores in executors.items() for _ in range(cores)]
waves = [tasks[i:i + len(slots)] for i in range(0, len(tasks), len(slots))]
for w, wave in enumerate(waves):
    print(f"wave {w}:", ", ".join(f"{t}->{s}" for t, s in zip(wave, slots)))
print("waves needed:", len(waves))

Check yourself

Quick revision

Lesson 1.3 in one screen

  • Driver: main program, SparkSession, DAG, scheduling, results, UI :4040. One per app; single point of failure.
  • Cluster manager: standalone, YARN, Kubernetes (Mesos removed in 4.0); none in local[n].
  • Executors: JVMs on workers; cores = task slots; run tasks, cache data, serve shuffle files.
  • Lab: 2 executors × (2 cores, 1 GiB) granted instantly, registered ~8 s later; driver ran 0 tasks.
  • Client mode: driver where you submit; cluster mode: driver in the cluster (not for Python on standalone).
  • Worker lost → executor + shuffle files lost → FetchFailed (77 s) → resubmitted tasks → correct result.
  • Keep the driver light: no collect() of big data.

Interview and viva questions

Is the driver the same as the master?

No. The standalone master is the cluster manager shared by all applications. Each application has its own driver. In our lab both happened to run in the same container because we submitted from there.

How many executors should I use?

It depends on data size, cluster size and other users. Common starting points are 4–5 cores per executor and enough memory for the partitions each core processes. Dynamic allocation can add and remove executors automatically (Lesson 8.5).

Where does Python run on the cluster?

The driver runs your Python program. For DataFrame operations, executors run JVM code only. For Python functions (RDD lambdas, Python UDFs), each executor starts Python worker processes, which is why Python versions must match (Lesson 1.5).

What is the history server?

A web server that rebuilds the Spark UI from event logs after an application ends. Our lab runs one on port 18080; the screenshots in this lesson come from it.

Can one cluster run many applications?

Yes. Each application gets its own driver and executors, isolated from the others; the cluster manager shares machines between them.

Real-world scenario questions (asked in company interviews)

Architecture questions appear in every Spark interview.

Any company · SparkFresher

“Explain driver and executor”

What do the driver and executors do?

The interviewer is checking: do you know the roles?

Show a strong answer

The driver runs my main program, creates the SparkSession, builds the DAG and schedules tasks. Executors are processes on worker nodes that run those tasks in parallel, cache data and exchange shuffle data. A cluster manager such as YARN, Kubernetes or Spark standalone launches the executors.

Avoid: “The driver processes the data.”

Data engineeringMid-level

Driver OutOfMemoryError

A job fails with OutOfMemoryError in the driver.

The interviewer is checking: can you find the usual cause?

Show a strong answer
  1. Look for collect(), toPandas() or broadcast of large data.
  2. Write results from executors instead, or bring back a sample.
  3. Only then consider spark.driver.memory.

Avoid: Increasing driver memory first.

PlatformMid-level

Executor lost during a job

Logs show “Lost executor” and FetchFailedException, but the job succeeded slowly.

The interviewer is checking: do you understand recovery?

Show a strong answer
  • The executor and its shuffle files were lost; Spark recomputed missing map outputs from lineage.
  • Find why: spot interruption, OOM-killed container, node failure.
  • Mitigate: decommissioning, external shuffle service, right-sized memory.

Avoid: Ignoring it because the job passed.

ArchitectureSenior

Choose a cluster manager

A new platform must run Spark for 20 teams.

The interviewer is checking: can you compare managers?

Show a strong answer
  • YARN if Hadoop already exists; Kubernetes for container-based platforms and mixed workloads; serverless services to avoid operations.
  • Standalone only for small dedicated clusters.
  • Plan isolation (queues/namespaces), autoscaling and history server/log retention.

Avoid: Picking Mesos (removed in Spark 4.0).
