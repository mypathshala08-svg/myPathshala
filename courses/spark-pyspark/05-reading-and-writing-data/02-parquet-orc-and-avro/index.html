Parquet, ORC and Avro

The file format decides how much data Spark must read. This lesson compares text formats with the columnar formats Parquet and ORC and the row-based binary format Avro, and shows column pruning, predicate pushdown, schema evolution and compression in action. All outputs are real (PySpark 4.3.0).

1 The story

“Why is our storage bill so high?”

Before you start: text formats in 5.1.

TiffinGo kept every day’s orders as JSON in cloud storage because “it is readable”. A year later the bucket was huge, every dashboard query read every byte, and a simple “revenue in Pune” query took minutes on a large cluster.

Riya

Sir, JSON is easy to open and check. What is wrong with it?

Arjun Sir

Nothing, for exchanging data. For storing and querying it, it is the worst choice: every record repeats every column name as text, numbers are text, and to read one column Spark must parse whole records.

Kabir

So we switch to Parquet?

Arjun Sir

Parquet or ORC for analytics, Avro for row-by-row exchange such as Kafka messages. Today we write the same 5 million orders in CSV, JSON, Parquet, ORC and Avro, and measure size, query time, column pruning, row-group skipping, schema evolution and compression codecs. All outputs are real (PySpark 4.3.0).

2 Definition

Columnar and binary file formats

Formal definition (write this in exams)

Apache Parquet and Apache ORC are self-describing, columnar storage formats: a file is divided into row groups (Parquet) or stripes (ORC), and within each the values of every column are stored together, encoded (dictionary, run-length) and compressed, with min/max statistics in the metadata. Readers can therefore read only the needed columns (column pruning) and skip row groups whose statistics exclude a filter (predicate pushdown). Apache Avro is a row-oriented binary format with an embedded schema, designed for record-at-a-time serialization and schema evolution, commonly used for messages and data exchange. Parquet is Spark’s default data source format; Avro support is provided by the external spark-avro module. Spark preserves the schema in these files and can merge compatible schemas across files with mergeSchema.

In simple words

Parquet and ORC store each column separately, compressed and with statistics, so Spark reads only the columns and blocks a query needs. Avro stores whole rows in compact binary with its schema. Use Parquet or ORC for analytics, Avro for messages, and CSV/JSON only to exchange data.

File formats at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A filing cabinet

  • A CSV or JSON file is a pile of handwritten forms: to find all amounts you read every form.
  • Parquet and ORC keep one drawer per column (all amounts together), with a label on each folder saying the smallest and largest value inside.
  • To add up amounts in Pune you open only two drawers and skip folders whose labels show they cannot match.

Intermediate The API

  • df.write.parquet(path), .orc(path), .format("avro").save(path); read with spark.read.parquet/orc or format("avro").
  • Avro is a separate module: --packages org.apache.spark:spark-avro_2.13:4.3.0 (or --jars).
  • Options: compression (snappy, zstd, gzip…), mergeSchema; plans show PushedFilters and the columns read.

Advanced What the lab showed

  • 5M orders: JSON 557 MiB, CSV 218, Avro 79, Parquet 43, ORC 36.
  • “Sum of amount in Pune”: CSV 2.37 s, JSON 2.74 s, Avro 0.91 s, Parquet 0.47 s, ORC 0.37 s.
  • On data sorted by order_id, a point lookup read 80,000 rows instead of 3,880,000 thanks to row-group statistics.

Exam tip: “Why is Parquet faster than CSV?” It is columnar and binary: Spark reads only the needed columns (column pruning), skips row groups using min/max statistics (predicate pushdown), and reads compressed, typed data without parsing text. In our lab the same query took 0.47 s on Parquet against 2.37 s on CSV, from a file 5x smaller.

3 Types and ways to use it

Compression codecs

CodecParquet size (5M orders)WriteNotes
snappy (Parquet and Avro default)42.8 MiB1.9 sFast, moderate compression
zstd (ORC default in Spark 4)34.9 MiB2.0 sSmaller at similar speed: a good modern default
gzip35.4 MiB3.6 sSlow to write
uncompressed57.4 MiB1.8 sColumnar encoding still saves a lot

Compression inside Parquet and ORC is per column chunk, so the files stay splittable whatever the codec. That is different from a .csv.gz file (Lesson 5.1), which is read by a single task. Do not gzip Parquet files from the outside.

  2. Step 2 · The same query on each format

    df = reader(fmt)        # CSV and JSON with an explicit schema
df.where(F.col("city") == "Pune").agg(F.sum("amount")).collect()
    == 3) query: sum(amount) for Pune (one column + one filter) csv : 2.37 s json : 2.74 s parquet : 0.47 s orc : 0.37 s avro : 0.91 s
    Text formats must be parsed byte by byte; Avro avoids text parsing but still reads whole rows; Parquet and ORC read only city and amount, already typed and compressed. ORC was 6x faster than CSV and over 7x faster than JSON.

  3. Step 3 · Column pruning, measured

    df = reader(fmt)
    df.write.format("noop").mode("overwrite").save()                   # all columns
    df.select("amount").write.format("noop").mode("overwrite").save()  # one column

    Reading one column instead of six made Parquet 2.7x faster (0.46 → 0.17 s): the other columns were never touched. CSV also gained (the parser skips converting unused fields, Lesson 5.1) but still had to scan every byte. The plan shows it: FileScan parquet [city, amount] with PushedFilters: [IsNotNull(city), EqualTo(city,Pune)].

  4. Step 4 · Skipping row groups with statistics

    src.sortWithinPartitions("order_id").write.option("parquet.block.size", 8 * 2**20).parquet(sorted_path)
for path in (unsorted_path, sorted_path):
    spark.read.parquet(path).where(F.col("order_id") == 4_200_000).count()
# rows read: inputRecords from the REST API
    == 5) row-group skipping: a selective filter on a sorted column unsorted : 0.23 s, rows read 3,880,000 of 5,000,000 sorted by order_id : 0.16 s, rows read 80,000 of 5,000,000
    Every row group stores the min and max of each column. In the unsorted file, ids were spread so most row groups “might” contain 4,200,000: 3.88 million rows were read. After sorting within partitions, only the row group whose range contained the id was read: 80,000 rows. Sorting or clustering by the columns you filter on is what makes pushdown effective.

    No schema was given, yet types came back exactly (order_id: long, order_date: date): the schema lives in the file. When November added a coupon column, a plain read silently missed it (Spark used one file’s schema); mergeSchema combined both and filled October with null.   6. Step 6 · Compression codecs

    for codec in ("snappy", "zstd", "gzip", "uncompressed"):
    src.write.mode("overwrite").option("compression", codec).parquet(f"{OUT}/codec_{codec}")
    == 9) Parquet codecs snappy : 42.8 MiB, write 1.9 s, read 0.29 s zstd : 34.9 MiB, write 2.0 s, read 0.19 s gzip : 35.4 MiB, write 3.6 s, read 0.14 s uncompressed: 57.4 MiB, write 1.8 s, read 0.13 s
    zstd was 18% smaller than snappy at the same write speed; gzip was as small but almost twice as slow to write. Read times differ little at this size. Even uncompressed, Parquet (57 MiB) was a quarter of CSV, thanks to columnar encoding. Set it with option("compression", "zstd") or spark.sql.parquet.compression.codec.

6 Real-world use

File formats at work

1. Data lakes

S3, ADLS and GCS lakes store analytics tables as Parquet, usually under Delta Lake or Iceberg.

Raw→Parquet→Queries

2. Hive warehouses

Hive tables on Hadoop clusters are often ORC; Spark reads them with the same pruning and pushdown.

Hive table→ORC→Spark SQL

3. Streaming messages

Kafka topics carry Avro records with schemas in a schema registry; Spark decodes them with from_avro.

Kafka→Avro→Structured Streaming

4. Cost reduction

Converting JSON or CSV archives to Parquet with zstd cuts storage and scan costs on pay-per-byte engines.

JSON archive→Parquet + zstd→Lower bill

5. BI on Spark and Trino

Dashboards query Parquet through Spark SQL, Trino or Athena, which all use column pruning and statistics.

Parquet→pushdown→Dashboard

9 Quiz and revision

Check yourself

Quick revision

Lesson 5.2 in one screen

  • Columnar (Parquet, ORC): read only needed columns, skip blocks with min/max statistics.
  • Avro: binary rows with schema; external spark-avro module; good for messages.
  • 5M orders: JSON 557, CSV 218, Avro 79, Parquet 43, ORC 36 MiB.
  • Pune sum: CSV 2.37 s, JSON 2.74 s, Avro 0.91 s, Parquet 0.47 s, ORC 0.37 s.
  • Pushdown works when data is clustered: 80,000 vs 3.88M rows read.
  • Schema lives in the file; new columns need mergeSchema; type changes fail.
  • Codecs: snappy (default), zstd (smaller, same speed), gzip (slow write); still splittable.

Interview and viva questions

Parquet or ORC?

Both are excellent. Parquet is the default and most widely supported (Spark, Trino, pandas, DuckDB, Delta, Iceberg); ORC is common in Hive. Pick one per platform.

Why not always use mergeSchema?

It reads the footers of all files to combine schemas, which is slow on thousands of files. Table formats store the schema centrally instead.

What is a good file size?

Roughly 128 MB to 1 GB per file for large tables. Many tiny files are a problem of their own (Lesson 5.3).

Can I read Parquet without Spark?

Yes: pandas, PyArrow, DuckDB, Polars, Trino and most warehouses read Parquet directly.

How do I use Avro with Kafka?

Use from_avro/to_avro on the value column in Structured Streaming, usually with a schema registry (Module 9).

Real-world scenario questions (asked in company interviews)

File-format questions test whether you understand what Spark reads from disk.

Any company · SparkFresher

“Why Parquet?”

Why do data lakes use Parquet instead of CSV?

The interviewer is checking: do you know columnar benefits?

Show a strong answer

Parquet is columnar, binary, compressed and stores its schema and statistics. Spark reads only needed columns and skips row groups using min/max values. In my test 5M orders were 43 MiB as Parquet vs 218 MiB as CSV, and a filter query was about 5x faster.

Avoid: “It is just compressed CSV.”

Data engineeringMid-level

Predicate pushdown not helping

A filter on Parquet still reads most of the data.

The interviewer is checking: do you know when statistics help?

Show a strong answer
  • Check PushedFilters in the plan.
  • Min/max only help when values are clustered: sort or cluster by the filter column on write.
  • Measure rows read before and after (3.88M vs 80,000 in my test).

Avoid: Assuming pushdown always skips data.

Data engineeringMid-level

Avro vs Parquet

When would you choose Avro over Parquet?

The interviewer is checking: do you know row vs column use cases?

Show a strong answer
  1. Avro: row-oriented messages and exchange, Kafka with schema registry, schema evolution per record.
  2. Parquet: analytics scans of a few columns over many rows.
  3. Often both: Avro in Kafka, Parquet in the lake.

Avoid: Saying one is always better.

PlatformSenior

Lake cost reduction

Storage and query costs of the lake are rising fast.

The interviewer is checking: can you plan a format migration?

Show a strong answer
  • Convert JSON/CSV archives to Parquet with zstd; keep raw briefly.
  • Sort/cluster by common filters; target 128 MB–1 GB files.
  • Move to a table format for schema evolution and compaction.

Avoid: Only buying cheaper storage.
