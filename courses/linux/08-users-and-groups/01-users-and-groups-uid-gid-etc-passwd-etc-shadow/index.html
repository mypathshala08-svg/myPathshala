Users and groups: UID, GID, /etc/passwd, /etc/shadow, id, who, w and last

Linux decides who can read a file or run a command from two numbers: a user ID and group IDs. This lesson explains where they live, how to read the account files, and how admins, DBAs, DevOps, security and testers use id, getent, who, w and last.

The problem

A new developer joins and can read the payroll folder. A database stops after an update because the postgres account was locked. An auditor asks “who logged in at 3 a.m.?”. Every one of these is a question about users and groups. Linux decides everything (who can read a file, who can run a command, who owns a process) from two small numbers: a user ID and group IDs. 2 Definition

Users, groups, UID and GID

Formal definition (write this in exams)

A user is an account that can own files and run processes; the kernel identifies it by a number, the UID. A group is a named set of users with its own number, the GID; every user has one primary group and may belong to supplementary groups. Accounts are stored in /etc/passwd, password hashes and ageing rules in /etc/shadow, and groups in /etc/group.

In simple words

Linux decides who may do what by comparing the UID and GIDs of a process with the owner and group of a file.

Words you’ll meet in this lesson

UIDUser ID: the number the kernel uses for a user. root = 0.
GIDGroup ID: the number of a group.
Primary groupThe group in your passwd line; new files get it.
Supplementary groupExtra groups listed in /etc/group (sudo, docker…).
System accountAn account for a service (UID 1–999), usually no login.
HashA one-way scrambled form of a password.
ShellThe program started when the user logs in (/bin/bash, nologin).
NSSName Service Switch: where names are looked up (/etc/nsswitch.conf).

Users and groups at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: an office with ID cards and badges

Think of a company building.

  • Each person (user) has an employee number on their ID card: the UID.
  • Everyone belongs to one main department (primary group) and may carry extra badges (supplementary groups).
  • Doors (files and folders) only check numbers and badges.

Basic What you will type every day

  • whoami: your user name. id: your UID, GID and every group.
  • groups: just the group names.
  • getent passwd riya: one account’s line (works with LDAP too).
  • who / w: who is logged in now; last: login history.

Intermediate The account files and their fields

  • /etc/passwd: name:x:UID:GID:comment:home:shell. The x means “password is in shadow”. Readable by everyone because programs like ls need names.
  • /etc/shadow: name:hash:lastchange:min:max:warn:inactive:expire:. Readable only by root and the shadow group. ! or * instead of a hash means locked or no password.
  • /etc/group: group:x:GID:members. A user’s primary group is in passwd; extra groups list the user here.
  • UID 0 is root; 1–999 are system accounts (services such as www-data, postgres) with shell nologin; 1000+ are people (from /etc/login.defs).

Advanced Behind the screen: the kernel only knows numbers

  • Every process carries a real and effective UID and GID plus a list of supplementary GIDs (see /proc/self/status). Every inode stores one owner UID and one GID.
  • Names are a user-space convenience: ls, id and ps ask the C library, which follows /etc/nsswitch.conf (“files”, then maybe LDAP, SSSD or systemd-userdb) to turn numbers into names. getent uses the same path; cat /etc/passwd does not.
  • Group changes take effect at the next login: a running shell keeps the groups it started with (newgrp or log out and back in).
  • Hashes in shadow start with an algorithm id: $y$ yescrypt (Ubuntu 22.04+), $6$ SHA-512. They are salted and one-way; Linux checks a password by hashing what you type and comparing.
  • Login records are binary files: /var/run/utmp (now: who, w), /var/log/wtmp (history: last), /var/log/btmp (failed logins: sudo lastb), /var/log/lastlog.

Did you know? The account called nobody (UID 65534) owns nothing on purpose. Services that must run with no rights at all, such as some NFS requests, are mapped to it.

Exam tip: “What are the 7 fields of /etc/passwd?” → username : x (password in shadow) : UID : GID : comment (GECOS) : home directory : login shell.

Quick check Why is /etc/passwd readable by everyone?
Answer: Programs such as ls, ps and id must turn UIDs into names. The password hashes are not there: they are in /etc/shadow, readable only by root.
Common mistake
✗“whoami displays the current user ID and username”
✓whoami prints only the user name (riya). Use <code>id</code> or <code>id -u</code> for the number (1000).

Checked on Ubuntu 24.04: whoami prints the effective user name only, the same as id -un.

🟢 Read-onlyno sudo

/etc/passwd in system info / admin

  1. Situation: List the people (not services) on a server.

    awk -F: '$3>=1000 && $3<65534 {print $1, $3, $6}' /etc/passwd
    riya 1000 /home/riya aman 1001 /home/aman

    Why this way: UID 1000+ are human accounts (from /etc/login.defs). 65534 is nobody.

  2. Situation: Count accounts by login shell.

    cut -d: -f7 /etc/passwd | sort | uniq -c | sort -rn
    21 /usr/sbin/nologin 4 /bin/bash 1 /bin/sync

    Why this way: Most accounts are nologin services; only a few can log in. (Lesson 6.2.)

/etc/passwd in security

  1. Situation: Any extra account with UID 0 is a backdoor.

    awk -F: '$3==0 {print "UID 0:", $1}' /etc/passwd
    UID 0: root

    Why this way: Only root should appear. A second UID 0 account has full power under another name.

/etc/passwd in data administration

  1. Situation: Where does the postgres service account live?

    getent passwd postgres
    postgres:x:102:104:PostgreSQL administrator,,,:/var/lib/postgresql:/bin/bash

    Why this way: Home /var/lib/postgresql holds the data; the DBA switches to it with sudo -iu postgres (Lesson 8.4).

/etc/passwd in web servers

  1. Situation: Which user runs the web server?

    getent passwd www-data | cut -d: -f1,3,6,7
    www-data:33:/var/www:/usr/sbin/nologin

    Why this way: Web files must be readable by www-data, but never writable unless needed (Lesson 9.1).

/etc/shadow password hashes and ageing

🟢 Read-onlyno sudo

One line per account: name:hash:lastchange:min:max:warn:inactive:expire:. Dates are days since 1 January 1970. Only root and the shadow group can read it.

✓ Use it when
  • checking whether a password is set, locked or expired
  • security audits of password ageing
✗ Don’t use it when
  • viewing it with a normal account (permission denied)
  • copying hashes anywhere

/etc/shadow in security

  1. Situation: Accounts with an empty password field can log in without a password.

    sudo awk -F: '$2=="" {print "NO PASSWORD:", $1}' /etc/shadow; echo checked
    checked

    Why this way: Should print nothing. Lock such accounts with sudo passwd -l (Lesson 8.2).

  2. Situation: Password status of an account.

    sudo passwd -S riya
sudo passwd -S www-data
    riya P 2026-11-11 0 99999 7 -1 www-data L 2026-10-24 0 99999 7 -1

    Why this way: P = usable password, L = locked. Service accounts are locked: nobody can log in as them with a password.

/etc/shadow in system info / admin

  1. Situation: When does riya’s password expire?

    sudo chage -l riya
    Last password change : Nov 11, 2026 Password expires : never Password inactive : never Account expires : never Minimum number of days between password change : 0 Maximum number of days between password change : 99999 Number of days of warning before password expires : 7

    Why this way: 99999 days max = never. Companies often set 90 days (Lesson 8.2).

Common mistake
✗“/etc/passwd contains the passwords”
✓Since shadow passwords (decades ago) the second field is just <code>x</code>; hashes are in /etc/shadow (root only).

If you ever see a hash in /etc/passwd, that system is badly misconfigured: anyone could copy it and try to crack it offline.

id · whoami · groups · getent in devops / cloud

  1. Situation: A setup script must run as root.

    if [ "$(id -u)" -ne 0 ]; then echo 'please run with sudo' >&2; exit 1; fi; echo 'running as root'
    please run with sudo

    Why this way: Compare the number, not the name (the root account could be renamed). Here riya runs it, so it stops.

  2. Situation: With sudo the same check passes.

    sudo bash -c 'if [ "$(id -u)" -ne 0 ]; then echo no; else echo "running as $(whoami)"; fi'
    running as root

    Why this way: sudo runs the command with UID 0.

id · whoami · groups · getent in system info / admin

  1. Situation: Does the user have access to the group before a ticket is closed?

    id -Gn riya | tr ' ' '\n' | grep -qx sudo && echo 'riya is in sudo'
    riya is in sudo

    Why this way: grep -x matches the whole word, so “sudoers” would not count.

id · whoami · groups · getent in testing / qa

  1. Situation: Tests that must not run as root (they would hide permission bugs).

    [ "$(id -u)" = 0 ] && echo 'refusing to test as root' || echo "testing as $(id -un)"
    testing as riya

    Why this way: Running tests as root passes checks real users would fail.

Common mistake
✗Added to a group, but <code>id</code> in the open terminal does not show it
✓Log out and back in (or run <code>newgrp GROUP</code> / <code>su - $USER</code>); <code>id NAME</code> reads the files and already shows it.

A process gets its groups when it starts. Your old shell keeps the old list until a new login.

Undo and safety net

These commands only read. The danger is editing the account files by hand.

  • Broke /etc/passwd with an editor: Ubuntu keeps backups: /etc/passwd-, /etc/shadow-, /etc/group-. Check with sudo pwck and sudo grpck.
  • Need to edit safely: sudo vipw / sudo vigr lock the file and check it; better, use useradd/usermod (Lesson 8.2).
  • Removed yourself from sudo: Use another admin, or recovery mode (Lesson 17.1), then usermod -aG sudo NAME.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. cat /etc/shadow
    cat: /etc/shadow: Permission denied exit status: 1

    What it means: A normal user may not read password hashes.

    Fix: Use sudo, or sudo passwd -S NAME to see only the status.

  2. id priya
    id: ‘priya’: no such user exit status: 1

    What it means: No such account in passwd (or LDAP).

    Fix: Check the spelling with getent passwd | cut -d: -f1.

  3. getent group hr
    exit status: 2

    What it means: Prints nothing, exit 2: the group does not exist.

    Fix: Create it with sudo groupadd hr (Lesson 8.3).

Answer: /etc/shadow; sudo passwd -S NAME (L = locked).

Under the hood: id reads the account files

strace shows that id gets your numbers from the kernel, then opens /etc/nsswitch.conf, /etc/passwd and /etc/group only to print names.

Script it: user-report.sh

A small audit report: human accounts with their UID, groups and shell, plus a warning for any extra UID 0 account.

echo "USER      UID   SHELL       GROUPS"
awk -F: '$3>=1000 && $3<65534 {print $1, $3, $7}' /etc/passwd | while read -r u uid sh; do
  printf '%-9s %-5s %-11s %s\n' "$u" "$uid" "$sh" "$(id -Gn "$u" | tr ' ' ',')"
done
extra=$(awk -F: '$3==0 && $1!="root" {print $1}' /etc/passwd)
[ -n "$extra" ] && echo "WARNING: extra UID 0 accounts: $extra" || echo "OK: only root has UID 0"
USER UID SHELL GROUPS riya 1000 /bin/bash riya,sudo aman 1001 /bin/bash aman,finance OK: only root has UID 0

On a real server this lists every person and flags backdoor accounts.

Quick revision

Lesson 8.1 in one screen

  • Users have a UID, groups a GID; the kernel only uses the numbers. root = 0, services 1–999, people 1000+.
  • /etc/passwd: name:x:UID:GID:comment:home:shell, readable by all.
  • /etc/shadow: name:hash:last:min:max:warn:inactive:expire, root only. !/* = locked.
  • /etc/group: group:x:GID:members. One primary group (in passwd), many supplementary.
  • id, id -u, id -Gn, whoami, groups, getent passwd|group NAME.
  • who, w (now), last, sudo lastb, lastlog (history).
  • New groups apply at next login. Edit accounts with tools (8.2), not an editor; vipw, pwck.

Interview and viva questions

How do I list all users in Linux?

getent passwd (or cut -d: -f1 /etc/passwd). Humans: awk -F: '$3>=1000 && $3<65534' /etc/passwd.

What is the difference between /etc/passwd and /etc/shadow?

passwd lists accounts and is readable by all; shadow holds password hashes and ageing and is readable only by root.

How do I see which groups a user belongs to?

id USER or groups USER.

What is a UID?

The number the kernel uses to identify a user; root is 0.

How do I see who is logged in?

who or w (w also shows what each user is running).

How do I see login history?

last (successful), sudo lastb (failed), lastlog (latest per account).

Why does a new group not work in my terminal?

Groups are set at login; log out and in, or run newgrp GROUP.

Any company · basicsFresher

“Explain /etc/passwd.”

Asked in almost every Linux interview.

The interviewer is checking: do you know the fields?

Show a strong answer

Audit a server you have never seen

Show a strong answer
  • Extra UID 0: awk -F: '$3==0' /etc/passwd; empty passwords in shadow.

PlatformSenior

Same UID, different names on two servers

Files copied over NFS appear owned by the wrong person.

Interview and certification corner

What is the difference between a primary and a supplementary group?
Primary: one, from passwd, used for new files. Supplementary: extra groups in /etc/group.
How do you check whether a user is locked?
sudo passwd -S NAME (L) or ! at the start of the shadow hash.
Why is /etc/shadow separate?
So hashes are not readable by everyone.
whoami vs id?
whoami: name only; id: UID, GID, groups.
How do you see failed login attempts?
sudo lastb, or journalctl -u ssh / /var/log/auth.log.
What is UID 65534?
nobody: an account with no rights.
What does getent do?
Reads passwd/group/hosts through NSS, so it also sees LDAP users.
Where this appears in certification exams
  • RHCSA (EX200): “Create, delete, and modify local user accounts”: requires reading passwd, shadow and group.
  • LFCS: User and group management; system accounts.
  • CompTIA Linux+: User account files, UID/GID, who/w/last.
