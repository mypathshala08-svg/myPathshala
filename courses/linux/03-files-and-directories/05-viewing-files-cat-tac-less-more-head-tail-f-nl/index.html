2 Definition

cat, tac, head, tail, less, more, nl and wc

Formal definition (write this in exams)

cat (concatenate) writes files to standard output, one after another; tac does the same with the line order reversed. head and tail output the first or last part of files (by lines or bytes); tail -f keeps printing data appended to a file. less and more are pagers that display text one screen at a time. nl numbers lines and wc (word count) counts lines, words, characters and bytes.

In simple words

Small files: cat. Big files: less. Just the start or end: head / tail. Live logs: tail -f. Counting: wc.

Viewing files at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a long paper scroll

Imagine a file as a very long paper scroll.

  • cat unrolls the whole scroll onto the screen: fine for short notes.
  • head shows the top, tail the bottom: the newest lines of a log are at the bottom.
  • less is a window you slide up and down, with a search.

Basic The commands you will type every day

  • cat notes.txt prints a file; cat a.txt b.txt prints both, one after the other.
  • head file = first 10 lines; head -n 3 file = first 3. tail the same for the last lines.
  • less file: Space / b = page down / up, /word search, n next match, g / G top / bottom, q quit.
  • wc -l file counts lines; nl file or cat -n file numbers them.
  • tail -f app.log follows a log live; Ctrl+C stops it.

Intermediate The options that solve real problems

  • tail -n +2 data.csv = from line 2 to the end (skip the header); head -n -1 = all but the last line.
  • A range: head -n 1010 f | tail -n 11 = lines 1000–1010.
  • cat -A shows tabs as ^I, line ends as $, Windows carriage returns as ^M: the cause of many “invisible” bugs.
  • cat -s squeezes repeated blank lines; cat -b numbers only non-empty lines; nl does the same by default and has formats (-nrz, -w, -s, -bp).
  • tail -F = follow by name and retry: survives log rotation. --pid=PID stops when a process ends.

Advanced Behind the screen: why tail is fast

  • tail on a regular file does not read from the start: it lseek()s near the end and reads backwards until it has enough newlines. That is why tail on 2 GB is instant, while cat | tail reads all 2 GB.
  • head stops reading as soon as it has N lines, so it is instant too.
  • tail -f keeps the file descriptor open and uses inotify (or polling once per second) to notice growth. After rotation the old descriptor points to app.log.1; -F checks the name and reopens.
  • less reads only what it shows and builds a line index as you move; less +F follows like tail -f, Ctrl+C returns to normal scrolling.
  • wc -l counts newline characters: a last line without \n is not counted. -m counts characters (UTF-8 aware), -c bytes: different for Hindi or emoji.

Did you know? less was written in 1983–85 by Mark Nudelman because more could not scroll backwards. The joke name, “less is more”, stuck. It is still maintained by the same author forty years later, and man uses it to show every manual page.

Exam tip: “How do you view the last 100 lines of a log and keep watching it?” → tail -n 100 file, then tail -f file (or tail -n 100 -f); mention tail -F for rotated logs, Ctrl+C to stop, and less +F as an alternative.

Quick check Which command shows a CSV file without its header line?
Answer: tail -n +2 file.csv: from line 2 to the end.

Common mistake
✗cat 2GB.log | tail -n 50
✓tail -n 50 2GB.log

Through a pipe, tail cannot jump to the end: cat must push all 2 GB through it. Give the file name directly so tail can seek. (Same for “useless use of cat”: cat f | grep x → grep x f.)

Quick check Which two commands are instant on a 2 GB file, and why?
Answer: head (stops after N lines) and tail on a file name (jumps to the end). cat, tac, nl and wc must read everything.

Each command explained, then used in every field

cat · tac concatenate · reverse

🟢 Read-onlyno sudo

cat prints files in order, one after another; tac prints them with the last line first.

✓ Use it when
  • the file is short (fits on one screen)
  • joining files into one: cat a b > all
  • checking hidden characters: cat -A
✗ Don’t use it when
  • the file is long (use less, head or tail)
  • feeding one file into another command (give the file name to that command)
  • binary files (use file, strings, xxd)

Syntax: cat [OPTION]... [FILE]... · tac [FILE]...

catcommand-nnumber linesjan.csv feb.csvfiles, in order&gt; all.csvredirect to a file

Without a file name, cat reads the keyboard (stdin) until Ctrl+D, which is why cat > file creates a file (Lesson 3.1).

cat · tac in software development

  1. Situation: A script fails with “bad interpreter”: the file was saved on Windows.

    printf '#!/bin/bash\r\necho hi\r\n' > run.sh
cat -A run.sh
    #!/bin/bash^M$ echo hi^M$

    Why this way: ^M$ at each line end = Windows CRLF. Fix with sed -i "s/\r$//" run.sh or dos2unix.

  2. Situation: Check for trailing spaces in a config file.

    printf 'port=80  \nhost=db\n' > app.conf
cat -E app.conf
    port=80 $ host=db$

    Why this way: The $ marks the real line end: the spaces before it are visible now.

cat · tac in data analysis / engineering

  1. Situation: Merge monthly CSV exports into one file, keeping only the first header.

    printf 'id,amt\n1,10\n' > jan.csv; printf 'id,amt\n2,20\n' > feb.csv
{ cat jan.csv; tail -n +2 feb.csv; } > q1.csv
cat q1.csv
    id,amt 1,10 2,20

    Why this way: cat for the first file, tail -n +2 for the rest skips their headers. { …; } sends both into one file.

cat · tac in system info / admin

  1. Situation: Read the newest errors first from a log.

    tac app.log | grep -m 2 ERROR
    2026-11-06 10:00:09 ERROR disk full 2026-11-06 10:00:05 ERROR db timeout

    Why this way: tac reverses the order; grep -m 2 stops after the two newest errors.

cat · tac in security

  1. Situation: Look inside an unknown file safely, without running it.

    file /bin/ls | cut -c1-36
cat -v /bin/true | head -c 40; echo
    /bin/ls: ELF 64-bit LSB pie executab ^?ELF^B^A^A^@^@^@^@^@^@^@^@^@^C^@>^@^A^@

    Why this way: Binary files print garbage and can mess up the terminal; file tells you the type, and cat -v shows unprintable bytes as ^ and M- codes.

cat · tac in testing / qa

  1. Situation: Compare expected and actual output by eye, with line numbers.

    printf 'a\nb\nc\n' > expected.txt; printf 'a\nB\nc\n' > actual.txt
cat -n expected.txt actual.txt
    1 a 2 b 3 c 4 a 5 B 6 c

    Why this way: Numbers make it easy to point to a line. For real comparisons use diff (Lesson 6.3).

head · tail first lines · last lines

🟢 Read-onlyno sudo

head prints the first 10 lines, tail the last 10. Both accept other counts, bytes, and several files; tail can also start from a line number.

✓ Use it when
  • you need only the start (head) or the end (tail) of a file
  • huge files: both are instant on a file name
  • skipping headers, cutting a line range, sampling data
✗ Don’t use it when
  • you need lines in the middle by pattern (use grep, Lesson 6.1)
  • you want to scroll interactively (use less)

Syntax: head [-n N | -c N] [FILE]... · tail [-n N | -n +N | -c N] [FILE]...

head -c Nfirst N bytesfile signatures, binary headers
tail -n Nlast N lineslatest log entries
tail -n +Nfrom line N to the endskip a header
tail -c Nlast N byteschecking file endings
-q / -vhide / show “==> name <==” headersseveral files

head · tail in data analysis / engineering

  1. Situation: See the header and two rows of a CSV before loading it.

    head -n 3 students.csv
    id,name,city,marks 1,Asha,Pune,91 2,Ravi,Delhi,78

    Why this way: Always look at a sample first: separator, header names, quoting.

  2. Situation: Data rows only, without the header.

    tail -n +2 students.csv
    1,Asha,Pune,91 2,Ravi,Delhi,78 3,Meena,Chennai,85 4,Imran,Mumbai,66

    Why this way: +2 = start at line 2. Used before sort or awk so the header is not sorted with the data.

  3. Situation: Lines 1000 to 1010 of a big file.

    seq 1 2000 > big.txt
head -n 1010 big.txt | tail -n 11 | tr "\n" " "; echo
    1000 1001 1002 1003 1004 1005 1006 1007 1008 1009 1010

    Why this way: head stops at 1010, tail keeps the last 11 of those. (seq: Lesson 3.6.)

head · tail in system info / admin

  1. Situation: The first line of every config file in a folder.

    mkdir -p conf && echo 'port=80' > conf/web.conf && echo 'port=5432' > conf/db.conf
head -n 1 conf/*.conf
    ==> conf/db.conf <== port=5432 ==> conf/web.conf <== port=80

    Why this way: With several files head prints a “==> name <==” header for each; -q hides them.

head · tail in security

  1. Situation: Identify a file by its first bytes (“magic number”), whatever its extension.

    head -c 4 /bin/ls | od -c | head -1
    0000000 177 E L F

    Why this way: Executables start with \177 E L F. A “photo.jpg” that starts with ELF is a disguised program.

head · tail in data administration

  1. Situation: Check that a big SQL dump finished completely: look at its last lines.

    printf -- '-- MySQL dump\nINSERT INTO t VALUES (1);\n-- Dump completed on 2026-11-06\n' > night.sql
tail -n 1 night.sql
    -- Dump completed on 2026-11-06

    Why this way: mysqldump writes “Dump completed” as the last line. If it is missing, the dump was cut off.

head · tail in ml / ai

  1. Situation: Make a small sample of a dataset for quick experiments.

    seq 1 100000 > data.txt
head -n 1000 data.txt > sample.txt && wc -l sample.txt
    1000 sample.txt

    Why this way: A 1000-line sample loads in milliseconds; test the code on it, then run on the full data.

tail -f follow a growing file

🟢 Read-onlyno sudo

Prints the end of the file, then keeps running and prints every new line as soon as it is written. Stop with Ctrl+C.

✓ Use it when
  • watching a log while you reproduce a problem
  • waiting for a job to finish (“Dump completed”)
  • logs that are rotated: -F
✗ Don’t use it when
  • the log is in systemd’s journal (use journalctl -f, Lesson 18.2)
  • you need history, not live lines (use tail -n or less)

Syntax: tail -f FILE · tail -F FILE · tail -f --pid=PID FILE

OptionWhat it doesWhen to use it
-ffollow the open file (descriptor)most logs
-Ffollow by name, retry if it disappears or is replacedrotated logs (safer default)
-n N -fshow N old lines, then followcontext first
--pid=PIDstop when that process endswatching one job
-s Ncheck every N seconds (when polling)slow network file systems
several filesfollow all, with name headersweb + app logs together

First run (real output)

touch live.log
(for i in 1 2 3; do sleep 0.3; echo "order $i placed" >> live.log; done) &
timeout 1.5 tail -f live.log
order 1 placed order 2 placed order 3 placed

A background job writes three lines; tail -f prints each as it arrives. Here timeout stops it after 1.5 s; at the keyboard you press Ctrl+C.

tail -f in system info / admin

  1. Situation: Watch only errors, live, from a busy log.

    touch app.log
(sleep 0.3; echo "INFO ok" >> app.log; echo "ERROR db down" >> app.log; echo "INFO ok" >> app.log) &
timeout 1 tail -f app.log | grep --line-buffered ERROR
    ERROR db down

    Why this way: The pipe filters the stream; --line-buffered makes grep print each match at once instead of waiting for a full buffer.

tail -f in devops / cloud

  1. Situation: Follow both the web server and the application log during a deploy.

    Typical output (cannot be recorded on our build machine)

    sudo tail -F /var/log/nginx/error.log /var/log/myapp/app.log
    ==> /var/log/nginx/error.log <== 2026/11/06 10:12:01 [error] 812#812: *41 connect() failed ... ==> /var/log/myapp/app.log <== 2026-11-06 10:12:01 ERROR db pool exhausted

    Why this way: Several files in one window; -F keeps working when logrotate replaces them during the night.

tail -f in data administration

  1. Situation: Wait for a long restore and stop watching automatically when it ends.

    Typical output (cannot be recorded on our build machine)

    tail -f --pid=$(pgrep -n mysql) restore.log
    … table 41 of 42 restored … table 42 of 42 restored (tail exits by itself when the mysql restore process ends)

    Why this way: --pid ends tail when the process is gone, so a script can continue.

tail -f in testing / qa

  1. Situation: Reproduce a bug while watching the log in a second terminal.

    Typical output (cannot be recorded on our build machine)

    tail -n 0 -f app.log
    (empty: only lines written from now on appear) 2026-11-06 10:20:13 ERROR NullPointer at CartService:88

    Why this way: -n 0 hides old lines, so everything you see belongs to your test.

Common mistake
✗tail -f /var/log/app.log (left running across log rotation)
✓tail -F /var/log/app.log

-f follows the open file; after rotation that is app.log.1, which no longer grows. -F follows the name and reopens the new app.log.

nl in software development

  1. Situation: Numbered code for a review comment, with a clear separator.

    printf 'def f():\n    return 1\n' > f.py

    nl -bp'ERROR' app.log

nl in data analysis / engineering

🟢 Read-onlyno sudo

Counts lines, words and bytes (and characters with -m) of files or of its input.

Undo and safety net

These commands only read, but two traps exist.

  • A pager or tail -f seems stuck: press q in less/more, Ctrl+C in tail -f. Nothing is changed.
  • cat on a binary file garbled the terminal: type reset (or stty sane) and press Enter, even if you cannot see what you type.
  • cat a b > a: this empties a before cat reads it. Write to a new file: cat a b > all.
  • Typed cat with no file name: cat is waiting for keyboard input. Press Ctrl+D (or Ctrl+C).

Error messages decoded

The errors students see most with these commands. Each was really produced on our build machine, with its exit status.

  1. cat nofile.txt
    cat: nofile.txt: No such file or directory exit status: 1

    What it means: The file does not exist here.

    Fix: Check the name and folder with ls; use Tab completion.

  2. mkdir logs
cat logs
    cat: logs: Is a directory exit status: 1

    What it means: logs is a folder; cat prints files only.

    Fix: ls logs to see its content, then cat logs/app.log.

  3. head -n abc app.log
    head: invalid number of lines: ‘abc’ exit status: 1

    What it means: -n needs a number.

    Fix: head -n 20 app.log.

  4. tail /etc/shadow
    tail: cannot open '/etc/shadow' for reading: Permission denied exit status: 1

    What it means: Only root may read the password hash file.

    Fix: Use sudo only if you really need it, on your own system.

  5. echo hi > a.txt
cat a.txt b.txt > a.txt
cat a.txt
    cat: b.txt: No such file or directory exit status: 0

    What it means: bash emptied a.txt for > before cat read it; cat also complains about the missing b.txt.

    Fix: Never redirect into one of the input files; write to a new name.

  1. 1. How big is it?

    ls -lh file and wc -l file.

    Behind the screen: ls reads the inode size; wc reads the data.

  2. 2. Small? cat it

    Under ~50 lines: cat file (or cat -n).

    Behind the screen: read() the whole file, write() it to the terminal.

  3. 3. Big? Look at the edges

    head -n 20 for the structure, tail -n 50 for the latest.

    Behind the screen: head stops early; tail seeks to the end.

  4. 4. Need to explore? less

Following a log through rotation, and counting rows correctly

File descriptor, name and inode 5 steps
What you see
  1. tail -f prints each new order line.
  2. At midnight logrotate renames app.log and the application starts a new one.
  3. tail -f prints nothing more: it is watching the old, renamed file.
  4. tail -F reports “has been replaced; following new file” and continues.
  5. For logs that rotate, use -F.
Behind the screen
  1. tail -f keeps the file descriptor of the file it opened (inode A).
  2. Rotation is a rename (Lesson 3.2): inode A keeps its data under a new name.
  3. The application writes to a new inode B now called app.log.
  4. -F re-checks the name regularly and reopens it when the inode changes.
  5. Messages shown are the typical GNU tail messages.

Under the hood: tail jumps to the end

The real file-related system calls of tail -n 3 big.txt on a 2000-line file (8893 bytes).

strace -e trace=%file,%desc tail -n 3 big.txt
openat(AT_FDCWD, "big.txt", O_RDONLY) = 3 lseek(3, 0, SEEK_CUR) = 0 lseek(3, 0, SEEK_END) = 8893 lseek(3, 8192, SEEK_SET) = 8192 read(3, "\n1861\n1862\n1863\n1864\n1865\n1866\n1"..., 701) = 701 read(3, "", 0) = 0

Recorded with strace on our Ubuntu build machine; library loading lines are hidden. You can run the same on your PC after sudo apt install strace.

tail opens the file, asks where the end is (lseek … SEEK_END = 8893 bytes), jumps to 8192 and reads only the last 701 bytes, where it finds the last three newlines. The first 8 KB are never read. On 2 GB the work is the same: one seek, one small read.

Quick check Why does tail -f stop showing lines after a log rotation, while tail -F keeps working?
Answer: -f follows the file it opened (now renamed app.log.1); -F follows the name app.log and reopens the new file.

Script it: log-summary.sh

A small report on any log file: size, lines, errors, warnings and the last error. (Lesson 12.5 explains scripts; grep is Lesson 6.1.)

#!/bin/bash
log=${1:-app.log}
printf '2026-11-06 10:00:01 INFO start\n2026-11-06 10:00:05 ERROR db timeout\n2026-11-06 10:00:07 WARN slow\n2026-11-06 10:00:09 ERROR disk full\n' > "$log"   # demo data
[ -r "$log" ] || { echo "cannot read $log" >&2; exit 1; }
echo "file:     $log ($(wc -c < "$log") bytes)"
echo "lines:    $(wc -l < "$log")"
echo "errors:   $(grep -c ERROR "$log")"
echo "warnings: $(grep -c WARN "$log")"
echo "last error:"
grep ERROR "$log" | tail -n 1
file: app.log (134 bytes) lines: 4 errors: 2 warnings: 1 last error: 2026-11-06 10:00:09 ERROR disk full

[ -r "$log" ] checks that the file exists and is readable before anything else.

Puzzle answer Remember the question from the story? Open to check your guess.

tail -f follows the file it opened (its inode). At midnight logrotate renamed that file to app.log.1 and the application started writing to a new app.log. tail -f kept watching the renamed file, which no longer grows, so it showed nothing. tail -F (capital F) follows the name: it notices that app.log is now a different file and reopens it.

Interview and viva questions

How do you view a large file in Linux?

less file: it shows one screen at a time and does not load the whole file. Search with /word, quit with q.

How do you see the last lines of a log in real time?

tail -f file (or tail -F for logs that get rotated). Ctrl+C stops it.

What is the difference between less and more?

more mostly scrolls forward; less scrolls both ways, searches, follows (F) and opens big files quickly.

How do you print a specific range of lines?

head -n END file | tail -n COUNT, or sed -n START,ENDp file.

What is the difference between cat -n and nl?

cat -n numbers all lines; nl by default numbers only non-empty lines and has format options.

How do you count lines, words and characters?

wc -l, wc -w, wc -m (characters) and wc -c (bytes).

Why does wc -l report one line less than I see?

The last line has no newline character at the end; wc -l counts newlines.

Real-world scenario questions (asked in company interviews)

Interview questions about reading files, from fresher to senior rounds.

Any company · basicsFresher

“How do you see the last 100 lines of a log and keep watching it?”

A support engineer must check a live application log.

The interviewer is checking: do you know tail and its options?

Show a strong answer
  • tail -n 100 app.log, then tail -n 100 -f app.log to keep following.
  • Rotated logs: -F. Only errors: | grep --line-buffered ERROR.
  • Ctrl+C to stop.

Avoid: opening the file in vi on production.

Data team · validationJunior

The row counts do not match

The source says 10,000 rows; wc -l on the exported CSV says 10,000 too, but the database has 9,999.

The interviewer is checking: do you understand headers and newlines?

Show a strong answer
  1. wc -l counts the header too: 9,999 data rows + 1 header = 10,000 lines. The load is correct.
  2. Count data rows with tail -n +2 file | wc -l.
  3. Also check the last line ends with a newline (tail -c 1 file | od -c), and quoted fields with embedded newlines.

Avoid: reloading the data without understanding the difference.

Operations · on callMid-level

“tail -f shows nothing since midnight.”

An engineer says the application stopped logging at 00:00, but users are active.

The interviewer is checking: do you know log rotation?

Show a strong answer
  • logrotate renamed the file at midnight; tail -f still watches the old inode.
  • Use tail -F, or check with ls -li app.log* and lsof which file the app writes.
  • If the app itself still writes to the old file, logrotate needs copytruncate or a reload (Lesson 18.1).

Avoid: restarting the application first.

Platform · performanceSenior

Reading a 50 GB file efficiently

A script runs cat huge.log | tail -n 100 every minute and loads the disk.

The interviewer is checking: do you know which tools seek and which stream?

Show a strong answer
  • tail with a file name seeks to the end: tail -n 100 huge.log reads a few KB, not 50 GB.
  • Pipes remove that ability; avoid useless cat. head also stops early.
  • For repeated checks, follow with tail -F or use the journal / a log shipper instead of re-reading.

Avoid: buying faster disks.

Interview and certification corner

Difference between cat, less, head and tail?
cat prints the whole file; less pages through it; head prints the start; tail the end (and can follow with -f).
How do you skip a CSV header?
tail -n +2 file.csv.
tail -f vs tail -F?
-f follows the opened file descriptor; -F follows the name and reopens after rotation.
How do you print lines 50–60?
head -n 60 f | tail -n 11, or sed -n 50,60p f.
How do you find Windows line endings?
cat -A shows ^M$ at line ends (or file says “with CRLF line terminators”).
Why is tail fast on huge files?
It seeks to the end and reads backwards only as much as needed; it cannot do that through a pipe.
What does wc -l count exactly?
Newline characters, so a final line without \n is not counted.
Where this appears in certification exams
  • RHCSA (EX200): “Locate and interpret system log files and journals”; tail, less and wc are the everyday tools for it.
  • LFCS: Essential Commands and Operations: read and monitor log files from the command line.
  • CompTIA Linux+: Text viewing utilities (cat, head, tail, less, more, wc, nl) in file management objectives.
