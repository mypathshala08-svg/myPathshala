Redirection: >, >>, <, 2>, 2>&1, /dev/null and here-documents

One wrong character, > instead of >>, empties a whole log. This lesson explains every redirection operator: saving, appending, feeding files, capturing errors, combining streams, throwing output away and writing multi-line input inside scripts.

The problem

Riya’s nightly job writes 2,000 lines of output, a few of which are errors. She wants all of it saved in one log, kept from night to night, with yesterday’s lines not overwritten. She also needs to feed a 15-line SQL script to the database without creating a temporary file, and to silence one harmless warning. Three small operators do all of that: >>, 2>&1 and << EOF. One wrong character (> instead of >>) deletes the whole log.

  • feed files to commands with <, and capture errors with 2> and 2>>
  • combine both streams with 2>&1 or &>, and explain why the order matters
  • throw output away with /dev/null, and write multi-line input with here-documents (<< EOF) and here-strings (<<<)

2 Definition

Redirection, /dev/null and here-documents

Formal definition (write this in exams)

Redirection is a shell feature that changes where a command’s standard streams point before the command runs: to a file, from a file, or to another file descriptor. /dev/null is a special device file that discards everything written to it and returns end-of-file when read. A here-document supplies several lines written inside the script as a command’s standard input; a here-string supplies a single string.

In simple words

Tell the shell where input comes from and where output and errors go, before the command starts.

Redirection at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: buckets and taps

Think of a command as a water tank with taps.

  • > puts an empty bucket under the tap: whatever was in it before is poured away.
  • >> puts the same bucket back and tops it up.
  • < is a funnel: you pour a file into the tank.
  • /dev/null is the drain: water disappears and nothing fills up.

Basic The operators you will type every day

  • date > today.txt saves the output (replacing the file); date >> log.txt adds a line.
  • wc -l < names.txt feeds a file as input.
  • ls /nope 2> err.txt saves only the error; 2>> appends errors.
  • cmd > all.log 2>&1 saves results and errors (bash also has cmd &> all.log).
  • cmd > /dev/null 2>&1 runs quietly; 2>/dev/null hides only errors.

Intermediate Order, quoting and here-documents

  • Redirections are read left to right. 2>&1 means “make 2 point where 1 points now”. So > f 2>&1 sends both to f, but 2>&1 > f sends errors to the screen (where 1 pointed at that moment).
  • The shell creates or empties the target file before the command runs, even if the command then fails. So sort data.txt > data.txt empties data.txt before sort reads it.
  • A here-document << EOF feeds the following lines until a line with only EOF. $variables and $(commands) are expanded; with << 'EOF' they are kept literally; <<- removes leading tabs.
  • set -o noclobber makes > refuse to overwrite existing files; >| overrides it on purpose.
  • sudo cmd > /etc/file fails: the redirection is done by your shell, not by sudo. Use cmd | sudo tee /etc/file.

Advanced Behind the screen: open(), dup2() and more descriptors

  • > f = open("f", O_WRONLY|O_CREAT|O_TRUNC) + dup2(fd, 1); >> uses O_APPEND instead of O_TRUNC, so every write goes to the end, even with several writers.
  • 2>&1 is dup2(1, 2): copy descriptor 1 into 2. General form N>&M; N<>file opens for reading and writing; N>&- closes.
  • Here-documents are stored by bash in a temporary file or a pipe, then given to the command as stdin.
  • Process substitution <(cmd) turns a command’s output into a file name (/dev/fd/63): diff <(sort a) <(sort b). Glossary: process substitution.
  • &>, &>>, <<< and |& are bash extensions; in POSIX sh (dash on Ubuntu, used by /bin/sh scripts) write > f 2>&1 instead.

Did you know? > file with no command at all is a complete command: it creates an empty file, or empties an existing one. Admins use : > app.log to empty a big log that a program still has open, because deleting it with rm would not free the disk space until the program closes it (Lesson 3.3).

Exam tip: “What is the difference between > and >>, and how do you redirect both stdout and stderr to a file?” → > truncates (overwrites), >> appends; cmd > file 2>&1 (or &> file in bash); 2>&1 must come after > file.

Quick check What does echo hi > a.txt do if a.txt already has 100 lines?
Answer: It empties a.txt first, so afterwards a.txt contains only “hi”. Use >> to keep the 100 lines.

Common mistake
✗sort data.txt > data.txt
✓sort data.txt > sorted.txt && mv sorted.txt data.txt · or sort -o data.txt data.txt

The shell empties data.txt before sort starts, so sort reads an empty file and data.txt ends up empty (a real run gave 0 bytes). The same happens with grep, sed, cut and any command reading and writing the same file.

Quick check Which operator would you use for a log that must keep growing?
Answer: >> (append), usually with 2>&1.
4 Step by step

Each operator explained, then used in every field

All outputs were recorded on Ubuntu 24.04 as a normal user (riya, no sudo rights). Our build machine has no database server, so DBA examples use minisql.py, a 6-line Python program that reads SQL on stdin and runs it on SQLite: the redirections are exactly the ones you use with mysql or psql.

> redirect stdout, overwriting

🔴 Can destroy datano sudo

Sends stdout into a file. If the file exists it is emptied first; if not, it is created. > is short for 1>.

✓ Use it when
  • saving a command’s output as a new file or a fresh copy
  • reports regenerated every run
  • creating or emptying a file (> file)
✗ Don’t use it when
  • logs and anything you must keep (use >>)
  • the same file the command is reading
  • files owned by root (use sudo tee)

Syntax: command > file · command 1> file · > file (empty it) · command >| file

lscommand>stdout to … (overwrite)list.txttarget file

Spaces around > are optional: ls>list.txt works too.

OptionWhat it doesWhen to use it
cmd > filecreate or overwrite file with the outputreports, fresh copies
cmd 1> filethe same, with the stream number writtennext to 2> for clarity
> file / : > fileempty (or create) a filereset a log in place
set -o noclobbermake > refuse to overwriteinteractive safety
cmd >| fileoverwrite even with noclobberwhen you really mean it
cmd > "$dir/$name"quoted target pathnames with spaces
{ cmd1; cmd2; } > fileone redirection for a groupseveral commands, one file

> in system info / admin

  1. Situation: Save the list of installed shells as a fresh report.

    cat /etc/shells > shells_report.txt
wc -l shells_report.txt
    9 shells_report.txt

    Why this way: > gives a clean file every time the report runs.

  2. Situation: Empty a huge log file that a service still writes to, without deleting it.

    seq 1 100000 > app.log; ls -l app.log | awk '{print $5, $9}'
: > app.log
ls -l app.log | awk '{print $5, $9}'
    588895 app.log 0 app.log

    Why this way: rm would remove the name but the service keeps the old file open, so the disk space stays used. Emptying keeps the same file.

> in software development

  1. Situation: Generate a config file from a template in one go.

    { echo 'APP_ENV=prod'; echo "BUILD=$(date -d 2026-11-06 +%Y%m%d)"; } > .env
cat .env
    APP_ENV=prod BUILD=20261106

    Why this way: Braces group commands so one redirection captures all their output.

> in data analysis / engineering

  1. Situation: Save the filtered rows of a CSV as a new file.

    printf 'city,temp\nPune,31\nLeh,4\nGoa,33\n' > temps.csv
grep -v ',4$' temps.csv > warm.csv
cat warm.csv
    city,temp Pune,31 Goa,33

    Why this way: Never write to the input file (see the common mistake above); write a new one.

> in testing / qa

  1. Situation: Protect an expected-results file from being overwritten by accident.

    echo 'expected: 42' > expected.txt
set -o noclobber
echo 'oops' > expected.txt
echo "exit status $?"
cat expected.txt
    /home/riya/script.sh: line 3: expected.txt: cannot overwrite existing file exit status 1 expected: 42

    Why this way: With noclobber, > refuses to replace an existing file. Use >| to overwrite on purpose.

> in security

  1. Situation: Create a file that is private from the start.

    (umask 077; echo 'token=abc123' > secret.env)
stat -c '%A %n' secret.env
    -rw------- secret.env

    Why this way: > creates files with the umask permissions. Setting umask 077 in a subshell first means no one else can ever read it, not even for a moment (Lesson 9.3).

Common mistake
✗sudo echo "nameserver 1.1.1.1" > /etc/resolv.conf → Permission denied
✓echo "nameserver 1.1.1.1" | sudo tee /etc/resolv.conf (append: sudo tee -a)

Your own shell opens /etc/resolv.conf before sudo even starts, and you are not root. tee runs as root and opens the file itself.

>> redirect stdout, appending

🟡 Changes filesno sudo

Sends stdout to the end of a file, keeping what is already there. Creates the file if needed. Every write goes to the end, even when several programs append at once.

✓ Use it when
  • logs: every run adds to the end
  • collecting results from many commands or loops into one file
  • audit trails
✗ Don’t use it when
  • files that must start fresh each run (use >)
  • logs that grow forever without rotation (use logrotate, Lesson 13)

Syntax: command >> file · command >> file 2>&1 · command &>> file

OptionWhat it doesWhen to use it
cmd >> fileappend the outputlogs
cmd 2>> fileappend the errorserror logs
cmd >> file 2>&1append both streamscron jobs
cmd &>> filethe same in bashshort form
for … done >> fileappend a whole loopcollect results
echo "$(date +%F_%T) msg" >> logtimestamped log linesimple logging

First run (real output)

echo 'Mon: ok' > week.log
echo 'Tue: ok' >> week.log
echo 'Wed: disk 91%' >> week.log
cat week.log
Mon: ok Tue: ok Wed: disk 91%

>> in system info / admin

  1. Situation: A tiny log function for scripts, with timestamps.

    log() { echo "$(date -d '2026-11-06 02:00' '+%F %T') $*" >> backup.log; }
log 'backup started'
log 'backup finished'
cat backup.log
    2026-11-06 02:00:00 backup started 2026-11-06 02:00:00 backup finished

    Why this way: >> keeps every run. (The time is fixed here so the output stays stable; in real use: date '+%F %T'.)

>> in devops / cloud

  1. Situation: The crontab line every admin should know.

    Typical output (cannot be recorded on our build machine)

    0 2 * * * /opt/scripts/nightly.sh >> /var/log/nightly.log 2>&1
    (added with crontab -e: runs at 02:00 every night, results and errors appended to one log)

    Why this way: Append, both streams, absolute paths. This one line fixes the “log that vanished” and the “errors that went nowhere”.

>> in data analysis / engineering

  1. Situation: Collect results of a loop into one CSV.

    echo 'n,square' > squares.csv
for n in 1 2 3; do echo "$n,$((n*n))" >> squares.csv; done
cat squares.csv
    n,square 1,1 2,4 3,9

    Why this way: Header once with >, rows with >>. (Faster for big loops: redirect the whole loop once: done >> file.)

>> in security

  1. Situation: An append-only audit line for each login attempt (demo).

    for u in riya kabir; do echo "2026-11-06 login $u" >> audit.log; done
wc -l audit.log
    2 audit.log

    Why this way: Audit files are only ever appended to. Admins can enforce it with chattr +a (root): then even > fails.

>> in testing / qa

  1. Situation: Append each test result, then count failures.

    for t in t1 t2 t3; do
  if [ "$t" = t2 ]; then echo "$t FAIL" >> results.txt; else echo "$t PASS" >> results.txt; fi
done
grep -c FAIL results.txt
    1

    Why this way: One results file across all tests.

< redirect stdin from a file

🟢 Read-onlyno sudo

Connects a file to the command’s standard input. The shell opens the file; the command just reads stdin and never sees the file name.

✓ Use it when
  • a command reads only stdin, or you do not want the file name in the output
  • loading SQL or data files into a database client
  • reading a file line by line in a loop (while read … done < file)
✗ Don’t use it when
  • the command takes the file name itself (just give the name)
  • very large binary files to programs that expect text

Syntax: command < file · while read -r line; do …; done < file

OptionWhat it doesWhen to use it
cmd < filefile as stdintools reading stdin
wc -l < filecount without printing the nameclean numbers in scripts
mysql db < dump.sqlrun a SQL filerestores, migrations
while read -r l; do …; done < fileloop over linesprocess records
cmd < in > outinput and output togetherfilters
cmd < /dev/nullno input at allcron, ssh in loops

  1. Situation: Create tables and data from a SQL file (with mysql: mysql shop < schema.sql).

< in system info / admin

  1. Situation: Read a list of users line by line.

    printf 'asha\nravi\n' > users.txt

    would create user: asha would create user: ravi

    Why this way: The redirection is at the end of the loop, so the whole loop reads the file. -r keeps backslashes.

< in data analysis / engineering

  1. Situation: Feed numbers to a calculator program.

    echo '1250*18/100' > calc.txt

< in devops / cloud

  1. Situation: Run a remote command in a loop without ssh eating the list (typical bug).

    Typical output (cannot be recorded on our build machine)

    while read -r host; do ssh "$host" uptime < /dev/null; done < hosts.txt
    web01 10:30:01 up 12 days, load average: 0.20, 0.15, 0.10 web02 10:30:02 up 30 days, load average: 0.05, 0.08, 0.07

    Why this way: ssh reads stdin too, so without < /dev/null it swallows the rest of hosts.txt and the loop ends after the first host (or use ssh -n).

2> · 2>> redirect stderr

🟡 Changes filesno sudo

Sends standard error to a file (2> overwrites, 2>> appends). Results on stdout are not affected.

✓ Use it when
  • keeping a record of errors from long jobs
  • separating errors from results for different people
  • hiding expected errors (2>/dev/null)
✗ Don’t use it when
  • when you need errors and results in their real order (use 2>&1 into one file)
  • hiding errors you do not understand

Syntax: command 2> errors.txt · command 2>> errors.log · command 2>/dev/null

OptionWhat it doesWhen to use it
2> fileerrors to a file (overwrite)one run’s errors
2>> fileerrors appendedlong-term error log
2>/dev/nulldiscard errorsexpected errors only
> out 2> errtwo filesresults and errors apart
2> >(cmd)errors into a command (bash)colour or filter errors

2> · 2>> in system info / admin

  1. Situation: Search the whole file system as a normal user: results on screen, errors logged.

    find /etc -name 'host*' 2> find_errors.txt | head -n 3
echo "errors logged: $(wc -l < find_errors.txt)"
    /etc/hosts /etc/host.conf /etc/hostname errors logged: 5

    Why this way: Keep the error list instead of throwing it away: it tells you which folders you could not search.

2> · 2>> in software development

  1. Situation: Compiler warnings into a file to review later.

    printf 'x = 1\nprint(undefined_name)\n' > app.py
python3 app.py 2> run_errors.txt
echo "exit $?"; tail -n 1 run_errors.txt
    exit 1 NameError: name 'undefined_name' is not defined

    Why this way: Tracebacks go to stderr. Saving them keeps the screen clean in CI and gives you the full error to read.

2> · 2>> in devops / cloud

  1. Situation: Append each night’s errors to their own log, results elsewhere.

    for night in 1 2; do ls a.txt /missing_$night >> results.log 2>> errors.log; done
wc -l results.log errors.log
    2 results.log 2 errors.log 4 total

    Why this way: Two logs for two audiences: results for reports, errors for the on-call engineer.

2> · 2>> in testing / qa

  1. Situation: Assert that a command prints no errors.

    ls a.txt 2> err.txt > /dev/null
if [ -s err.txt ]; then echo 'FAIL: errors printed'; else echo 'PASS: no errors'; fi
    PASS: no errors

    Why this way: [ -s file ] is true when the file is not empty.

2>&1 · &> both streams together

🟡 Changes filesno sudo

2>&1 makes stderr point to wherever stdout points at that moment. Written after > file, both go into the file. Bash shortcuts: &> file, &>> file, and |& for pipes.

✓ Use it when
  • one complete log with results and errors in order
  • cron jobs, CI steps, background services
  • piping errors into grep too (2>&1 |)
✗ Don’t use it when
  • when other programs need clean stdout data (keep errors separate)
  • POSIX sh scripts with &> (write > file 2>&1)

Syntax: command > file 2>&1 · command >> file 2>&1 · command &> file · command 2>&1 | grep …

OptionWhat it doesWhen to use it
> file 2>&1both into file (overwrite)standard, works in every shell
>> file 2>&1both appendedcron and service logs
&> file / &>> filethe same in bashshort, interactive use
2>&1 | cmdboth into a pipegrep through errors
|& cmdthe same in bashshort form
2>&1 > filewrong order: errors to screen, results to fileonly to keep errors visible on purpose
> /dev/null 2>&1silence everythingquiet checks

2>&1 · &> in devops / cloud

  1. Situation: A CI step whose full output (warnings included) goes into the build log.

    python3 -c 'import sys; print("building"); print("warning: old API", file=sys.stderr); print("done")' >> build.log 2>&1
cat build.log
    warning: old API building done

    Why this way: One log in time order. (Order inside the file can still differ by buffering; see 5.1. Use python3 -u to keep it exact.)

2>&1 · &> in system info / admin

  1. Situation: Search through a command’s errors: errors must go into the pipe too.

    ls a.txt /nope1 /nope2 2>&1 | grep -c 'No such file'
    2

    Why this way: A pipe only carries stdout; 2>&1 first joins errors to it. Bash: ls … |& grep ….

2>&1 · &> in software development

  1. Situation: Keep only the errors and throw away the results: here the order is the trick.

    ls a.txt /nope 2>&1 > /dev/null | wc -l
    1

Common mistake
✗cat << EOF text EOF ← indented with spaces
✓cat << EOF text EOF ← the delimiter alone, at the start of the line (or use <<- with tabs)

Undo and safety net

Redirection can destroy data in one keystroke. Protect yourself.

  • Overwrote a file with >: there is no undo in the shell. Restore from backup or git (git checkout -- file). Prevent it: set -o noclobber in ~/.bashrc, then use >| when you mean it.
  • Emptied the input file (sort f > f): same as above. Write to a new file and mv it, or use sort -o f f, sed -i, or sponge (moreutils).
  • A here-doc swallowed the rest of the script: the closing EOF was indented or misspelled. Fix that line; bash warns “delimited by end-of-file”.
  • 2>/dev/null hid the real problem: run again without it, or log with 2>> instead.
  • A log file grows forever with >>: set up logrotate (Lesson 18.2); empty safely with : > file.

Error messages decoded

Redirection errors students see most. Each was really produced on our build machine as a normal user, with its exit status.

  1. echo hi > /root/test.txt
    /home/riya/script.sh: line 1: /root/test.txt: Permission denied exit status: 1

    What it means: Your shell cannot create a file in /root: you are not root.

    Fix: Write somewhere you own, or echo hi | sudo tee /root/test.txt.

  2. wc -l < no_such_file.txt
    /home/riya/script.sh: line 1: no_such_file.txt: No such file or directory exit status: 1

    What it means: The input file does not exist; the command never ran.

    Fix: Check the name and path (Tab completion helps).

  3. echo hi > /nodir/out.txt
    /home/riya/script.sh: line 1: /nodir/out.txt: No such file or directory exit status: 1

    What it means: The folder /nodir does not exist; > creates files, not folders.

    Fix: mkdir -p the folder first.

  4. set -o noclobber; echo x > a.txt; echo y > a.txt
    /home/riya/script.sh: line 2: a.txt: cannot overwrite existing file exit status: 1

    What it means: noclobber is on and a.txt exists.

    Fix: Use >| to overwrite on purpose, or >> to append.

  5. f=""; echo hi > $f
    /home/riya/script.sh: line 1: $f: ambiguous redirect exit status: 1

    What it means: The variable is empty, so bash has no file name: “ambiguous redirect”.

    Fix: Check the variable, and quote it: > "$f" gives the clearer “No such file or directory”.

  6. printf 'cat << EOF\nline\n  EOF\n' > t.sh; bash t.sh
    t.sh: line 3: warning: here-document at line 1 delimited by end-of-file (wanted `EOF') line EOF exit status: 0

    What it means: The closing EOF had spaces before it, so bash read to the end of the file.

    Fix: Put EOF alone at the start of the line.

5 See it happen

Why the order of 2>&1 matters, and the log that was saved

Left: what Riya sees. Right: where fd 1 and fd 2 point after each redirection.

Read left to right, like the shell 6 steps
What you see
  1. ls a.txt /nope > all.txt 2>&1
  2. The shell reads the redirections from left to right.
  3. Result: all.txt has the result and the error.
  4. ls a.txt /nope 2>&1 > all.txt
  5. Same words, different order.
  6. Result: the error is on the screen, only a.txt in the file.
Behind the screen
  1. Both descriptors start at the terminal.
  2. > all.txt re-points fd 1.
  3. 2>&1 copies where fd 1 points now: the file.
  4. Second try, fresh start.
  5. 2>&1 copies fd 1, which is still the screen.
  6. > all.txt then changes only fd 1.

Under the hood: > versus >>

The difference is one flag in the openat() system call: O_TRUNC (empty it) or O_APPEND (add to the end). Here bash runs echo x > a.txt; echo y >> a.txt.

strace -e trace=%file,%desc bash -c 'echo x > a.txt; echo y >> a.txt'
openat(AT_FDCWD, "a.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3 dup2(3, 1) = 1 write(1, "x\n", 2) = 2 dup2(10, 1) = 1 openat(AT_FDCWD, "a.txt", O_WRONLY|O_CREAT|O_APPEND, 0666) = 3 dup2(3, 1) = 1 write(1, "y\n", 2) = 2 dup2(10, 1) = 1

Redirection at work

1. Scheduled jobs and logs

Every cron job and many systemd scripts end in >> logfile 2>&1 so results and errors are kept in order.

Job→>> 2>&1→log

DBAs dump with > (often gzip-compressed through a pipe) and restore with < every night.

Script→here-doc→config file

Check→/dev/null→OK / alert

Quick revision

Lesson 5.2 in one screen

  • > overwrite (empties first), >> append; set -o noclobber + >|.
  • < file: file as stdin (no file name in the output); while read -r l; do …; done < file.
  • 2> / 2>>: errors; > out 2> err: two files.
  • > f 2>&1 (or &> f): both. Order matters: 2>&1 > f leaves errors on screen.
  • /dev/null: > /dev/null 2>&1 silence; 2>/dev/null hide errors; < /dev/null no input.
  • Here-doc << EOF (expanded), << 'EOF' (literal), <<- (tabs); EOF alone on its line.
  • Here-string <<< "$var"; process substitution <(cmd).
  • Never cmd f > f. Root files: | sudo tee [-a].

Interview and viva questions

What is the difference between > and >> in Linux?

> overwrites the file (it is emptied first); >> appends to the end. Both create the file if it does not exist.

How do I redirect both stdout and stderr to a file?

command > file 2>&1 (any shell), or command &> file in bash. To append: >> file 2>&1 or &>> file.

Why does the order of 2>&1 matter?

Redirections are applied left to right, and 2>&1 copies where stdout points at that moment. Put it after > file.

What does 2>/dev/null mean?

Send error messages (stream 2) to /dev/null, which throws them away.

What is a here-document?

A way to give several lines from the script as a command’s input: command << EOF … EOF. Quote EOF to stop variable expansion.

How do I write to a file that needs root?

echo "text" | sudo tee /path/file (or sudo tee -a to append). sudo echo text > file does not work.

How do I avoid overwriting files by accident?

set -o noclobber; then > refuses to overwrite existing files and >| forces it.

Real-world scenario questions (asked in company interviews)

Interview questions about redirection, from fresher to senior rounds.

Any company · basicsFresher

“What is the difference between > and >>?”

A very common first-round question.

The interviewer is checking: do you know overwrite vs append, and the risk?

Show a strong answer
  • > empties the file first, then writes; >> adds at the end. Both create the file.
  • Example: date >> log.txt for logs, ls > list.txt for a fresh list.
  • Safety: set -o noclobber, then >| to force.

Avoid: saying they are the same.

Operations · cronJunior

The log has results but never errors

A crontab line is ./sync.sh 2>&1 >> /var/log/sync.log. Failures never appear in the log.

The interviewer is checking: do you know that redirection order matters?

Show a strong answer
  1. Left to right: 2>&1 copied stdout while it still pointed to cron’s capture, not the log.
  2. Fix: >> /var/log/sync.log 2>&1.
  3. Test by forcing an error and checking the log.

Avoid: adding 2>> to a second file without understanding why.

Data team · DBAMid-level

The report that came out empty

A script runs grep -v test users.csv > users.csv to remove test accounts. Now users.csv is empty and the CRM import failed.

The interviewer is checking: do you understand when the shell opens files?

Show a strong answer
  • The shell truncates users.csv before grep starts, so grep reads nothing.
  • Restore from backup; then write to a temp file and mv it into place (atomic, Lesson 3.2), or use sed -i / sponge.
  • Add a check: abort if the new file is empty or much smaller.

Avoid: “run it again”, which keeps the file empty.

Platform · automationSenior

Provisioning script edits system files

A setup script must add a line to /etc/hosts and write /etc/app/app.conf with variables, as a non-root CI user with sudo.

The interviewer is checking: can you write system files safely from scripts?

Show a strong answer
  • echo "10.0.0.5 db01" | sudo tee -a /etc/hosts > /dev/null (tee prints too; silence it).
  • sudo tee /etc/app/app.conf > /dev/null << EOF with the template; quote EOF where $ must stay literal.
  • Make it idempotent: grep -q db01 /etc/hosts || …; prefer configuration tools (Ansible) at scale.

Avoid: sudo echo … > /etc/hosts, or running the whole script as root.

Interview and certification corner

What is the difference between > and >>?
> overwrites (truncates), >> appends.
How do you redirect stderr to stdout?
2>&1; put it after the stdout redirection: > file 2>&1.
What is /dev/null?
A device that discards writes and returns EOF on read.
How do you suppress all output of a command?
cmd > /dev/null 2>&1 (or &> /dev/null in bash).
What is a here-document?
Inline multi-line stdin: cmd << EOF … EOF; quoted EOF disables expansion.
Why does sudo echo x > /etc/file fail?
The redirection is done by the calling shell, not by sudo. Use tee.
What happens with sort file > file?
The file is emptied before sort reads it; the result is an empty file.
