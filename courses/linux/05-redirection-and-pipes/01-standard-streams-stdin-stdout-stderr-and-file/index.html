Standard streams: stdin, stdout, stderr and file descriptors

Every Linux command has one way in and two ways out: stdin (0) for input, stdout (1) for results and stderr (2) for errors. This lesson shows where they point, how to see them, and why keeping results and errors apart matters in every IT job.

2 Definition

stdin, stdout, stderr and file descriptors

Formal definition (write this in exams)

The standard streams are three communication channels that every process starts with: standard input (stdin, file descriptor 0) for reading input, standard output (stdout, fd 1) for normal output, and standard error (stderr, fd 2) for error and diagnostic messages. A file descriptor is a small non-negative integer that a process uses to refer to an open file, device, pipe or socket.

In simple words

One way in, two ways out: input on 0, results on 1, problems on 2.

Standard streams at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: the restaurant kitchen

Think of a cook in a restaurant kitchen.

  • Orders come in through one window: that is stdin, the input.
  • Finished plates go out through the serving hatch: that is stdout, the results.
  • Problems (“we are out of paneer”) go to the manager’s phone: that is stderr, the errors.
  • The cook never decides where the hatch leads. The restaurant (the shell) does, and it can move the hatch to a delivery van (a file) or to the next cook (a pipe).

Basic The three streams every command has

  • stdin, number 0: where a command reads input. Default: the keyboard.
  • stdout, number 1: where it writes normal results. Default: the screen.
  • stderr, number 2: where it writes errors and warnings. Default: also the screen.
  • Because stdout and stderr both go to the screen, they look like one stream. They are not: ls notes.txt /nope > out.txt moves only stdout, so the error still appears.
  • Commands such as cat, wc, sort, grep read stdin when you give them no file. If one seems to “hang”, it is waiting for you: type, then press Ctrl+D.

Intermediate File descriptors and the terminal

  • The numbers 0, 1, 2 are file descriptors (fd): small numbers a process uses to refer to its open files. A process can open more (3, 4, …).
  • In a terminal, all three point to the same device, the pseudo-terminal /dev/pts/0. See it with ls -l /proc/$$/fd ($$ = your shell’s process ID).
  • Programs behave differently when stdout is not a terminal: ls prints one name per line, grep --color=auto stops colouring. Test it yourself with [ -t 1 ].
  • In scripts, send your own error messages to stderr with echo "error: …" >&2, so callers can separate them.
  • Ctrl+D at the start of a line means “end of input” (EOF); Ctrl+C stops the program instead.

Advanced Behind the screen: the fd table, inheritance and buffering

  • The kernel keeps a file descriptor table for every process. A child process (every command you run) inherits a copy of its parent’s table, which is why commands start with the shell’s 0, 1 and 2.
  • Redirection is done by the shell before the command starts: it opens the file and copies the descriptor into position 1 (the dup2() system call). The program never knows: it just writes to fd 1.
  • Buffering: the C library sends stdout to a terminal line by line, but to a file or pipe in blocks (often 4–64 KB); stderr is unbuffered. That is why, in a file, errors can appear before output that was printed earlier (see “Under the hood”). Python: python3 -u or flush=True; other programs: stdbuf -oL.
  • /dev/stdin, /dev/stdout, /dev/stderr are links to /proc/self/fd/0, 1 and 2: a way to give a stream to programs that only accept file names.
  • The convention is POSIX: fd 0, 1, 2 (STDIN_FILENO, STDOUT_FILENO, STDERR_FILENO in C), used by every Unix-like system since the 1970s.

Did you know? Standard error was not in the first Unix versions. Errors went to stdout, so when Bell Labs started sending command output straight to the phototypesetter, error messages came out typeset on expensive photographic paper. stderr was added (around 1975) so that errors always reach a person instead of the next program or file.

Exam tip: “What are stdin, stdout and stderr, and what are their file descriptor numbers?” → 0 = standard input (keyboard), 1 = standard output (screen), 2 = standard error (screen); every process inherits them from its parent; > moves 1, 2> moves 2, < feeds 0.

Quick check Name the three streams with their numbers, and say which one > moves.
Answer: stdin 0, stdout 1, stderr 2. A plain > means 1>: only stdout. Errors (2) still reach the screen.

4 Step by step

Each stream explained, then used in every field

stdin (fd 0) standard input

🟢 Read-onlyno sudo

The stream a command reads from. Many commands read stdin whenever you give them no file: cat, wc, sort, grep, tr, read, python3, mysql.

✓ Use it when
  • a command should read data you type, paste, pipe or redirect
  • a script asks a question (read)
  • passing secrets without putting them on the command line
✗ Don’t use it when
  • the program already takes a file name (just give it the file)
  • cron jobs and background jobs: nobody is at the keyboard (use < /dev/null or a file)

Syntax: command (reads the keyboard) · command < file · cmd1 | command · command <<< "text"

The shell opens drinks.txt and connects it to fd 0 before wc starts.

stdin (fd 0) in system info / admin

  1. Situation: A script asks for a value; here the answer comes from a here-string so it can run unattended.

    read -r name <<< "Riya"
echo "Hello, $name"
    Hello, Riya

    Why this way: read reads one line from stdin. Interactively it waits for the keyboard; in automation you feed it.

  2. Situation: Stop a command from waiting for keyboard input in a cron job.

    cat < /dev/null; echo "cat finished at once, exit $?"
    cat finished at once, exit 0

    Why this way: /dev/null as stdin gives immediate end-of-file, so nothing can hang waiting for a person.

stdin (fd 0) in data analysis / engineering

  1. Situation: Sort numbers that arrive from another command, not from a file.

    printf '30\n4\n100\n' | sort -n
    4 30 100

    Why this way: sort reads stdin when given no file; -n sorts numerically.

  2. Situation: Add a header line in front of a CSV that streams in.

    echo 'id,city' > header.csv
printf '1,Pune\n2,Agra\n' | cat header.csv -
    id,city 1,Pune 2,Agra

    Why this way: The dash means “stdin goes here”: header first, then the piped rows.

stdin (fd 0) in software development

  1. Situation: A Python program that reads its input from stdin (like coding-test websites do).

    printf '12\n30\n8\n' | python3 -c 'import sys; print(sum(int(x) for x in sys.stdin))'
    50

    Why this way: Reading stdin means the same program works with typed input, files (< data.txt) and pipes.

stdin (fd 0) in data administration

  1. Situation: Load a SQL file into MySQL (Lesson: Advanced Java, JDBC module).

    Typical output (cannot be recorded on our build machine)

    mysql -u riya -p shop < schema.sql
    Enter password: (no output: the statements ran)

    Why this way: mysql reads SQL statements from stdin, so < file runs a whole script. The password prompt itself is written to the terminal, not read from the file.

stdin (fd 0) in security

  1. Situation: Hash a secret without putting it on the command line, where ps and the history would show it.

    secret='MyP@ss2026'
printf '%s' "$secret" | sha256sum
    299b02685c4ab92c295e1a0eb0125719f5a45dde9bc13b2deabdf65b0fc2fe64 -

    Why this way: Arguments are visible to every user in ps and in /proc/PID/cmdline; stdin is not. Many tools (docker login --password-stdin, kubectl) accept secrets on stdin for this reason.

stdin (fd 0) in testing / qa

  1. Situation: Test a program with fixed input every time.

    printf '2\n3\n' > input.txt
python3 -c 'a=int(input()); b=int(input()); print(a*b)' < input.txt
    6

    Why this way: The same input file gives the same result in every run: repeatable tests.

stdout (fd 1) standard output

🟢 Read-onlyno sudo

The stream for normal results. It goes to the screen by default and is what >, >> and | move. Programs can check whether it is a terminal and adjust their format.

✓ Use it when
  • every normal result: lists, reports, data for the next command
  • output you want to save (> file) or process (| next)
  • checking whether output goes to a person or to a program
✗ Don’t use it when
  • error messages and warnings (use stderr)
  • progress bars and prompts (stderr, so they do not end up in files)

stdout (fd 1) in system info / admin

  1. Situation: ls looks different when its output goes into a pipe.

    touch a.txt b.txt c.txt
ls | cat
    a.txt b.txt c.txt

    Why this way: On a terminal ls prints columns; when stdout is a pipe or file it prints one name per line, which is easier for programs. (Our recorder is not a terminal, so plain ls would look the same here; the screens below show the real terminal.)

stdout (fd 1) in software development

  1. Situation: A script that colours its output only for people.

    if [ -t 1 ]; then echo 'stdout is a terminal: use colours'; else echo 'stdout is a file or pipe: plain text'; fi
    stdout is a file or pipe: plain text

    Why this way: Here it prints “plain text” because the recorder captures the output. In your terminal it prints the first message. grep --color=auto and ls --color=auto use the same test.

stdout (fd 1) in data analysis / engineering

  1. Situation: Save a report and also count its lines: stdout can be reused.

    printf 'Pune 41\nAgra 39\n' > report.txt
cat report.txt
wc -l < report.txt
    Pune 41 Agra 39 2

    Why this way: Results on stdout can go anywhere: screen, file, next command.

stdout (fd 1) in devops / cloud

  1. Situation: Live logs from Python inside a container appear late.

    python3 -c 'import time
for i in range(2): print("tick", i, flush=True)' | cat
    tick 0 tick 1

    Why this way: When stdout is a pipe, Python buffers in blocks. flush=True, python3 -u or PYTHONUNBUFFERED=1 (common in Dockerfiles) make lines appear immediately.

stdout (fd 1) in testing / qa

  1. Situation: Capture a command’s output in a variable and compare it with the expected value.

    got=$(echo "OK")
[ "$got" = "OK" ] && echo "PASS: got $got"
    PASS: got OK

    Why this way: $( ) captures stdout (only stdout: errors are not captured). Lesson 5.4 covers it.

Common mistake
✗ls notes.txt /nope > out.txt (expecting “everything” in out.txt)
✓ls notes.txt /nope > out.txt 2> err.txt · or > all.txt 2>&1 (Lesson 5.2)

> is short for 1>. The error is on stream 2 and still goes to the screen.

stderr (fd 2) standard error

🟢 Read-onlyno sudo

The stream for error messages, warnings and diagnostics. It also goes to the screen, but it is not moved by > or |, and it is unbuffered, so errors appear immediately.

✓ Use it when
  • every error and warning your own scripts print
  • progress, prompts and debug messages
  • keeping results clean so the next program can use them
✗ Don’t use it when
  • real results (they belong on stdout)
  • very important events only in stderr: also log them to a file (Lesson 18.1)

stderr (fd 2) in software development

  1. Situation: Your script reports a problem the right way.

    f=config.yml
if [ ! -e "$f" ]; then echo "error: $f not found" >&2; fi
echo "result line" > result.txt
cat result.txt
    error: config.yml not found result line

    Why this way: >&2 sends the message to stderr. Anyone running ./script > result.txt still sees the error, and the result file stays clean.

  2. Situation: Python: print a warning on stderr and a result on stdout.

    python3 -c 'import sys; print("42"); print("warning: slow disk", file=sys.stderr)' > answer.txt
cat answer.txt
    warning: slow disk 42

    Why this way: Every language has both: Java System.err, Python sys.stderr, C fprintf(stderr, …).

stderr (fd 2) in system info / admin

  1. Situation: Search the whole system without “Permission denied” flooding the screen.

    find /etc -name 'host*' 2>/dev/null | head -n 3
    /etc/hosts /etc/host.conf /etc/hostname

    Why this way: Normal users cannot read some folders. The errors are expected, so 2>/dev/null hides them while results still flow.

stderr (fd 2) in devops / cloud

  1. Situation: curl prints the download on stdout and the progress meter on stderr.

    Typical output (cannot be recorded on our build machine)

    curl -o page.html https://example.com
    % Total % Received % Xferd Average Speed Time Time Time Current Dload Upload Total Spent Left Speed 100 1256 100 1256 0 0 4310 0 --:--:-- --:--:-- --:--:-- 4316

    Why this way: Progress goes to stderr so that curl URL > file or curl URL | jq get only the data. -s silences the meter; -sS keeps real errors.

stderr (fd 2) in testing / qa

  1. Situation: Check that a test failure message really goes to stderr.

    ls /nope 2> err.txt > out.txt
echo "stdout bytes: $(wc -c < out.txt), stderr: $(cat err.txt)"
    stdout bytes: 0, stderr: ls: cannot access '/nope': No such file or directory

    Why this way: Good command-line programs keep errors off stdout. Testing it prevents broken pipelines later.

stderr (fd 2) in security

  1. Situation: Audit scripts: keep error output for review instead of throwing it away.

    ls /root 2> audit_errors.log; echo "exit $?"; cat audit_errors.log
    exit 2 ls: cannot open directory '/root': Permission denied

    Why this way: Hiding errors with /dev/null can hide attacks or misconfiguration. Log them, then decide.

/proc/PID/fd the file descriptor table

🟢 Read-onlyno sudo

Linux shows every process’s open file descriptors as links in /proc/PID/fd. $$ is your shell, $! the last background job. exec can open or close descriptors in the current shell.

✓ Use it when
  • seeing which files, pipes and sockets a process has open
  • debugging “where is this program writing?”
  • opening extra descriptors (3, 4 …) in advanced scripts
✗ Don’t use it when
  • normal day-to-day work (you rarely need fd numbers above 2)
  • other users’ processes without sudo (you will get Permission denied)

Syntax: ls -l /proc/PID/fd · lsof -p PID · exec 3> file … exec 3>&-

/proc/PID/fd in system info / admin

  1. Situation: Where is a background job writing?

    sleep 30 > job.log 2> job.err &
ls -l /proc/$!/fd | sed -E "s/.* ([0-9]+ ->)/\1/" | grep -E "^[012] "

    0 -> /dev/null 1 -> /home/riya/lab/job.log 2 -> /home/riya/lab/job.err

    Why this way: fd 1 and 2 point to the files the shell opened. Very useful when a service “writes logs somewhere”.

/proc/PID/fd in software development

  1. Situation: Write a separate log channel on fd 3 while stdout stays for results.

    exec 3> debug.log
echo "result: 42"
echo "debug: step 1 done" >&3
exec 3>&-
echo "--- debug.log:"; cat debug.log
    result: 42 --- debug.log: debug: step 1 done

    Why this way: Advanced scripts use extra descriptors for logs or locks (flock). Always close them with 3>&-.

/proc/PID/fd in security

  1. Situation: Which network connections and files does a process hold open?

    sleep 30 &
lsof -p $! 2>/dev/null | awk 'NR==1 || $4 ~ /^[0-9]/' | awk '{print $4, $5, $NF}'
kill $!
    FD TYPE NAME 0r CHR /dev/null 1w REG /tmp/mp-shlesson/out.txt 2w REG /tmp/mp-shlesson/out.txt

    Why this way: lsof shows descriptors (FD column 0u, 1w …), their type and target. Incident responders use it to find unexpected sockets or deleted files a process still holds.

Undo and safety net

Streams cannot be “broken”, but a few things surprise beginners.

  • A command waits and nothing happens: it is reading stdin. Press Ctrl+D to end the input or Ctrl+C to cancel.
  • You closed stdout or stderr by mistake (exec 1>&- or exec 2>&-): the shell can no longer print. Type exec 1>/dev/tty 2>/dev/tty, or just close the terminal and open a new one.
  • The terminal shows garbage after cat on a binary file: type reset (blind if needed) and press Enter.
  • 2>/dev/null hid an important error: run the command again without it. Hide only errors you understand.

Error messages decoded

Stream-related errors students see most. Each was really produced on our build machine, with its exit status.

  1. wc -l < missing.txt
    /home/riya/script.sh: line 1: missing.txt: No such file or directory exit status: 1

    What it means: The shell could not open the file for stdin, so wc never even started.

    Fix: Check the name with ls. The message comes from bash, not from wc.

  2. echo hi >&4
    /home/riya/script.sh: line 1: 4: Bad file descriptor exit status: 1

    What it means: There is no file descriptor 4 open in this shell.

    Fix: Open it first (exec 4> file) or use 1 or 2.

  3. echo hi > /dev/full
    /home/riya/script.sh: line 1: echo: write error: No space left on device exit status: 1

    What it means: /dev/full is a test device that is always “full”: writing to stdout failed. Real disks give the same error when they fill up.

    Fix: Free disk space (df -h, Lesson 15.4). Good scripts check the exit status of writes.

  4. ls /nope
    ls: cannot access '/nope': No such file or directory exit status: 2

    What it means: A normal error message, printed on stderr; exit status 2 means a serious problem for ls.

    Fix: Check the path. Use 2> to log such errors.

Answer: echo "error: disk full" >&2

The fd table behind the screen 4 steps
What you see
  1. ls writes the result to stdout and the error to stderr; both show on screen.
  2. With > out.txt the result disappears into the file.
  3. With 2> err.txt the error disappears into its file.
  4. wc with no file reads the keyboard until Ctrl+D.
Behind the screen
  1. Every process starts with descriptors 0, 1, 2, copied from the shell.
  2. Redirection only changes where a descriptor points; ls does not know.
  3. Each stream is moved separately.
  4. Ctrl+D tells the terminal driver to deliver end-of-file to fd 0.

Under the hood: two streams, two numbers

The error goes to write(2, …) in four small pieces, immediately; the result goes to write(1, …) at the very end, because stdout to a file is buffered and only flushed when ls exits. That is why in a combined log file errors can appear before output that was produced earlier.

6 Real-world use

Standard streams at work

1. Scheduled jobs

With no terminal, unredirected output of cron jobs is mailed or lost; admins always redirect both streams to logs.

Job→stdout + stderr→log file

2. Containers and services

Docker and systemd collect a service’s stdout and stderr as its log (docker logs, journalctl). The 12-factor rule: apps write logs to stdout.

Tools print progress on stderr so that their stdout can be piped into the next program without garbage.

CI systems show stderr in red and keep stdout as the build output; test runners compare stdout with expected results.

Test→1 vs 2→report

Passwords and tokens are passed on stdin (--password-stdin) because command-line arguments are visible to other users.

Lesson 5.1 in one screen

Interview and viva questions

What are stdin, stdout and stderr in Linux?

The three standard streams every process starts with: standard input (fd 0, keyboard by default), standard output (fd 1, screen) and standard error (fd 2, screen).

Why does an error still appear on screen when I redirect output to a file?

Because > only redirects stdout (fd 1). Errors are written to stderr (fd 2); redirect them with 2> or combine with 2>&1.

What is a file descriptor?

A small number a process uses to refer to an open file, device, pipe or socket. 0, 1 and 2 are the standard streams; others start at 3.

How do I end input when a command is reading from the keyboard?

Press Ctrl+D at the start of a line (end of file). Ctrl+C cancels the command instead.

How do I print to stderr in a bash script?

echo "message" >&2 (or printf "…" >&2).

Why is my Python output delayed when I pipe it?

stdout is block-buffered when it is not a terminal. Use python3 -u, print(..., flush=True) or PYTHONUNBUFFERED=1.

How can I see which files a process has open?

ls -l /proc/PID/fd, or lsof -p PID.

  • Every process inherits them from its parent, the shell.
  • Example: ls good /bad > out.txt still shows the error, because > moves only 1.

Avoid: saying “0 is false, 1 is true”: that is exit codes, a different topic (5.4).

Operations · cronJunior

The nightly job that “never fails”

A cron job’s log is always clean, but the backups are missing. The crontab line is ./backup.sh > /var/log/backup.log.

The interviewer is checking: do you know where stderr goes without a terminal?

Show a strong answer
  1. Errors are on stderr, which was not redirected: cron mailed them to a local mailbox nobody reads.
  2. Fix: >> /var/log/backup.log 2>&1 (Lesson 5.2), and make the script exit non-zero on failure.
  3. Add a check that alerts when the log contains “error” or the backup file is missing.

Avoid: “the log is empty, so it worked”.

Product team · developerMid-level

Our CLI breaks other people’s pipelines

Users pipe your tool’s JSON into jq, but it fails: “parse error”. Your tool prints “Connecting…” and warnings.

The interviewer is checking: do you design command-line tools properly?

Show a strong answer
  • Data on stdout only; progress, prompts and warnings on stderr.
  • Non-zero exit status on failure; quiet by default when stdout is not a terminal (isatty(1)).
  • Offer -q/--json; add a test that stdout parses as JSON.

Avoid: telling users to delete the first line with sed.

Platform · containersSenior

Logs appear minutes late in the dashboard

A Python service in Docker shows no logs for minutes, then many at once. After a crash the last lines are missing.

The interviewer is checking: do you understand buffering?

Show a strong answer
  • stdout is block-buffered when it is not a terminal (a container log pipe).
  • PYTHONUNBUFFERED=1 / python -u, or flush per line; other runtimes: line-buffered loggers, stdbuf -oL.
  • Log to stdout/stderr and let the platform collect them (12-factor); never only to a file inside the container.

Avoid: adding sleep calls so the buffer fills faster.

Interview and certification corner

What are the file descriptor numbers of stdin, stdout and stderr?
0, 1 and 2.
Why does an error appear on screen after command > file?
> redirects only stdout; errors are on stderr.
How do you write to stderr in bash?
echo "msg" >&2.
How do you end input typed on the keyboard?
Ctrl+D (EOF) at the start of a line.
How can you check if a script’s output goes to a terminal?
[ -t 1 ] (isatty on fd 1).
Where can you see a process’s open file descriptors?
/proc/PID/fd, or lsof -p PID.
Why may output and errors appear in the wrong order in a log file?
stdout is buffered when writing to a file; stderr is not.
Where this appears in certification exams
  • RHCSA (EX200): “Use input-output redirection (>, >>, |, 2>, etc.)”: knowing the three streams is the base of this objective.
  • LFCS: Essential commands: use streams, pipes and redirects.
  • CompTIA Linux+: Standard input, output and error, file descriptors and redirection operators.
