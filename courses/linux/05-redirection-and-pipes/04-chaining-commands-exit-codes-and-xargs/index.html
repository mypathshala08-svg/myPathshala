Chaining commands: ;, &&, ||, exit codes, $( ) and xargs

Every Linux command ends with a number: 0 means it worked. This lesson shows how to read that number, how ; && and || decide what runs next, how $( ) puts output inside commands, and how xargs turns a list into arguments safely.

The problem

Riya’s deploy script has three steps: build, copy, restart. One night the build fails, but the script carries on, copies the half-built files to the server and restarts it. The website goes down. Linux had told her the build failed (every command returns an exit code) but her script never listened. Today: how to listen. && runs the next step only on success, || runs a fallback on failure, $? shows the code, $( ) puts one command’s output inside another, and xargs turns a list into arguments.

By the end of this page you will be able to:
  • read exit codes with $? and know what 0, 1, 2, 126, 127, 130 and 137 mean
  • chain commands with ; (always), && (on success) and || (on failure), and avoid the a && b || c trap
  • insert a command’s output into another command with $( ), and group commands with { } and ( )
  • turn lines into arguments with xargs, safely (-0, -I{}, -n, -r, -P, -p)

2 Definition

Exit codes, chaining, $( ) and xargs

Formal definition (write this in exams)

Every command returns an exit status (exit code), an integer 0–255, when it ends: 0 means success, any other value means failure. The shell stores it in $?. Command lists join commands: ; runs them in sequence, && runs the next only if the previous succeeded (AND list), || only if it failed (OR list). Command substitution $(cmd) replaces itself with cmd’s output. xargs builds and runs command lines from items read on standard input.

In simple words

Each command answers “worked” (0) or “failed” (not 0); ; && || decide what runs next; $( ) pastes output; xargs turns lines into arguments.

Chaining at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a railway signal

Think of trains and signals.

  • When a command finishes, it shows a signal: green (0, worked) or red (any other number, failed).
  • && is a track that is only used on green; || only on red.
  • ; is a track that ignores the signal completely.
  • xargs is a loading crane: it takes a list of items and loads them onto a command as arguments.

Basic The forms you will type every day

  • echo $? right after a command: 0 = success.
  • sudo apt update && sudo apt upgrade -y: upgrade only if the update worked.
  • mkdir -p logs && cd logs: enter the folder only if it was created.
  • ping -c1 server || echo "server down": a message only on failure.
  • echo "Today is $(date +%A)": a command’s output inside text.

Intermediate Codes, combinations and traps

  • Common codes: 0 success; 1 general failure (also grep “no match”); 2 misuse or serious trouble (bash syntax error, ls/grep cannot access a file); 126 not executable; 127 command not found; 128+N killed by signal N: 130 = Ctrl+C, 137 = kill -9, 141 = SIGPIPE; 124 = timeout.
  • && and || have equal priority and are read left to right. a && b || c runs c if a fails or if b fails, so it is not a true if-then-else.
  • { a; b; } groups in the current shell (spaces and the final ; are required); ( a; b ) runs in a subshell, so cd and variables inside do not leak out.
  • $(cmd) runs cmd and replaces itself with the output, minus trailing newlines. Quote it: "$(cmd)". Backticks `cmd` are the old form: hard to nest and read.
  • xargs reads words from stdin and runs the command with them as arguments. Names with spaces break it unless you use -print0 | xargs -0.

Advanced Behind the screen: wait(), status bytes and ARG_MAX

  • A process ends with exit(n); the parent collects it with wait(). Only the low 8 bits are kept, so codes are 0–255: exit 256 gives 0 and exit 300 gives 44 (real runs).
  • If a signal kills the process, bash reports 128 + the signal number. kill -l 9 shows the name (KILL).
  • $( ) forks a subshell with its stdout connected to a pipe, reads everything, waits, and strips trailing newlines. Its exit status becomes $? in x=$(cmd).
  • The kernel limits the total size of arguments (getconf ARG_MAX, about 2 MB): rm $(find …) fails with “Argument list too long” on huge lists. xargs splits the list into several command runs automatically.
  • xargs -P N runs N commands in parallel; find -exec … {} + is the built-in alternative to xargs.

Did you know? In the shell, 0 means true (success) and non-zero means false, the opposite of most programming languages, where 0 is false. The reason: there is only one way to succeed but many ways to fail, so the non-zero numbers are free to say which failure happened.

Exam tip: “What does $? contain, and what is the difference between ;, && and ||?” → $? = exit status of the last command (0 success). ; runs the next always; && only if the previous returned 0; || only if it returned non-zero. Example: mkdir d && cd d; ping -c1 h || echo down.

Quick check grep -q root /etc/passwd prints nothing. How do you know if it found root?
Answer: Check its exit code: echo $? prints 0 if it found a match, 1 if not, 2 on error. Or use it directly: grep -q root /etc/passwd && echo found.

$? exit status of the last command

🟢 Read-onlyno sudo

A special variable holding the exit code of the most recent command: 0 = success, 1–255 = failure. Every command, including echo and [ … ], changes it.

✓ Use it when
  • any time you need to know whether a command worked
  • scripts that must react to failure
  • commands that print nothing (grep -q, test, cmp -s)
✗ Don’t use it when
  • reading $? after another command ran (it is overwritten at once: save it first)
  • guessing: read the man page EXIT STATUS section

Syntax: command; echo $? · rc=$? · exit N (in your scripts)

ls /nopeany command;thenecho $?show its exit code

Read $? immediately: the next command replaces it.

OptionWhat it doesWhen to use it
echo $?show the last codequick check
rc=$?save it before it changesscripts
exit Nend your script with code Ntell the caller
return Nend a function with code Nfunctions
true / falsecommands that return 0 / 1tests, loops
if cmd; thenbranch on the code (no $? needed)clean scripts

$? in system info / admin

  1. Situation: Is a user in the system? grep prints nothing with -q; only the code answers.

    grep -q '^riya:' /etc/passwd; echo "riya: $?"
grep -q '^ghost:' /etc/passwd; echo "ghost: $?"
    riya: 0 ghost: 1

    Why this way: 0 = found, 1 = not found, 2 = error (e.g. file missing). Scripts branch on this.

  2. Situation: What killed my process?

    sleep 30 & pid=$!; kill -9 $pid; wait $pid; rc=$?
echo "exit code $rc = signal $((rc-128)) = $(kill -l $((rc-128)))"
    /home/riya/script.sh: line 1: 10888 Killed sleep 30 exit code 137 = signal 9 = KILL

    Why this way: 128 + 9 = 137: killed with SIGKILL, often the OOM killer when memory runs out (Lesson 18.4).

$? in software development

  1. Situation: Your script returns a meaningful code to whoever runs it (CI, cron, another script).

    printf '#!/bin/bash\n[ -f "$1" ] || { echo "missing: $1" >&2; exit 3; }\necho ok\n' > check.sh; chmod +x check.sh
./check.sh /etc/hostname; echo "code $?"
./check.sh /nope; echo "code $?"
    ok code 0 missing: /nope code 3

    Why this way: Pick codes and document them (3 = missing input). CI marks a job red on any non-zero code.

$? in devops / cloud

  1. Situation: timeout tells you whether a command hung.

    timeout 1 sleep 3; rc=$?
[ $rc -eq 124 ] && echo 'timed out after 1 s'
    timed out after 1 s

    Why this way: 124 is timeout’s own code. Save $? into a variable first; the [ ] test would overwrite it.

$? in testing / qa

  1. Situation: Are two output files identical? cmp -s prints nothing.

    echo 42 > expected.txt; echo 42 > got.txt; echo 41 > bad.txt
cmp -s expected.txt got.txt; echo "same: $?"
cmp -s expected.txt bad.txt; echo "different: $?"
    same: 0 different: 1

    Why this way: Test frameworks use exit codes the same way: 0 pass, non-zero fail.

&& · || · ; AND, OR and sequence

🟢 Read-onlyno sudo

a && b runs b only if a returned 0. a || b runs b only if a failed. a ; b runs both, always. They can be chained: a && b && c stops at the first failure.

✓ Use it when
  • steps that depend on each other: build && deploy
  • creating then entering: mkdir d && cd d
  • one-line conditions: test && action, test || message
✗ Don’t use it when
  • independent steps that should all run (use ; or new lines)
  • real if/else logic with two branches (use if … then … else)

Syntax: cmd1 && cmd2 · cmd1 || cmd2 · cmd1 ; cmd2 · cmd1 && cmd2 || cmd3

OptionWhat it doesWhen to use it
a && bb only if a succeededdependent steps
a && b && cstop at the first failurebuild pipelines
a || bb only if a failedfallbacks, messages
a || exit 1stop the script on failureguard a step
a ; balways bothindependent steps
[ -f f ] && cat ftest, then actone-line if
a && b || cnot if/else: c also runs if b failsonly when b cannot fail

&& · || · ; in system info / admin

  1. Situation: Update the package list and upgrade only if the update worked (the real command).

    Typical output (cannot be recorded on our build machine)

    sudo apt update && sudo apt upgrade -y
    Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease Reading package lists... Done … 0 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.

    Why this way: If apt update fails (no network), upgrading from an old list makes no sense, so && stops there.

  2. Situation: Change ownership, then permissions, as one unit (from your notes).

    touch file.txt
chown riya:riya file.txt && chmod 740 file.txt && stat -c '%U:%G %a' file.txt
    riya:riya 740

    Why this way: chmod runs only if chown worked. (Changing to another user would need sudo, Lesson 9.3.)

&& · || · ; in devops / cloud

  1. Situation: The deploy chain: each step only after the previous one succeeded.

    build()   { echo 'build ok'; }
test_()   { echo 'tests FAILED'; return 1; }
deploy()  { echo 'deployed!'; }
build && test_ && deploy || echo 'pipeline stopped, nothing deployed'
    build ok tests FAILED pipeline stopped, nothing deployed

    Why this way: Like a CI pipeline: the first failure stops the chain. The final || reports it.

  2. Situation: Check that a server answers, with a message on failure.

    curl -s -o /dev/null --max-time 3 http://localhost:9 || echo 'ALERT: service on port 9 is down'
    ALERT: service on port 9 is down

    Why this way: Port 9 has no service here, so curl fails and the alert prints.

&& · || · ; in software development

  1. Situation: Create a folder and work inside it, but never in the wrong place.

    mkdir -p build/out && cd build/out && pwd
    /home/riya/lab/build/out

    Why this way: If mkdir fails, cd is skipped; if cd fails, nothing runs in the wrong folder.

&& · || · ; in security

  1. Situation: Why ; is dangerous with cd and rm (demo with echo instead of rm).

    cd /no/such/dir 2> /dev/null ; echo "rm -rf * would now run in: $(pwd)"
cd /no/such/dir 2> /dev/null && echo 'never printed'
    rm -rf * would now run in: /home/riya/lab

    Why this way: With ; the delete runs in whatever folder you happen to be in. Always: cd dir && rm -rf ./*, or better rm -rf dir/*.

&& · || · ; in testing / qa

  1. Situation: The a && b || c trap, shown for real.

    true && false || echo 'c ran even though a succeeded (b failed)'
if true; then false; else echo 'never printed'; fi; echo "if/else: else did not run"
    c ran even though a succeeded (b failed) if/else: else did not run

    Why this way: In a && b || c, c runs when a fails or b fails. Use a real if/then/else when b can fail.

Common mistake
✗cd /var/app/tmp ; rm -rf *
✓cd /var/app/tmp && rm -rf ./* · or simply rm -rf /var/app/tmp/*

If the cd fails (typo, folder missing), ; still runs rm in the current folder, possibly your home or /. This has deleted real servers.

$( ) command substitution

🟢 Read-onlyno sudo

Runs the command inside and replaces itself with its standard output, with trailing newlines removed. Quote it ("$(cmd)") to keep spaces. Backticks `cmd` do the same but cannot nest easily.

✓ Use it when
  • putting a command’s output into a variable, a file name or a message
  • dates, counts and paths inside other commands
  • nested calls (each $( ) inside another)
✗ Don’t use it when
  • huge outputs (the whole output is held in memory)
  • lists of file names with spaces into for loops (use while read or find -print0)

Syntax: var=$(command) · "text $(command) text" · cmd "$(other)"

$((1 + 2))arithmetic, not a commandcalculations

    echo "$(hostname): kernel $(uname -r | cut -d- -f1), $(nproc) CPUs"

$( ) in data analysis / engineering

  1. Situation: Count rows and compute a percentage.

{ } · ( ) grouping commands

🟢 Read-onlyno sudo

{ a; b; } runs the commands in the current shell as one unit. ( a; b ) runs them in a subshell: cd, variables and exit inside do not affect your shell.

✓ Use it when
  • one redirection or one && for several commands
  • trying something in another folder without moving yourself (( ))
  • a block that runs only on failure: || { echo …; exit 1; }
✗ Don’t use it when
  • big logic: write a function or a script instead

{ } · ( ) in devops / cloud

  1. Situation: Stop the script with a clear message if a required file is missing.

    cfg=app.conf

{ } · ( ) in software development

  1. Situation: Build in a sub-folder without changing your own location.

xargs build command lines from stdin

🟡 Changes filesno sudo

Reads items (words or lines) from stdin and runs a command with them as arguments, as many as fit per run. -0 reads NUL-separated items (from find -print0), -I{} places each item where {} is, -n N gives N per run, -r skips the run if there is no input, -P N runs N at once, -p asks first, -t prints each command.

✓ Use it when
  • many items from a pipe must become arguments (rm, cp, grep, chmod)
  • very long lists (xargs splits them to avoid “Argument list too long”)
  • parallel work (-P)
✗ Don’t use it when
  • names that may contain spaces or newlines, unless you use -print0 | xargs -0
  • commands that read stdin themselves (just pipe into them)

Syntax: … | xargs [-0] [-r] [-n N] [-P N] [-I{}] [-t|-p] command [args]

| xargs cmdall items as arguments to cmdrm, grep, wc
-print0 | xargs -0NUL-separated: safe for any file namealways with find
-I{}one run per item, {} = the itemcp {} dest/, mv {} {}.bak
-n NN items per runbatching
-rdo not run if input is emptyavoid “rm: missing operand”
-P NN runs in parallelcompress, download
-t / -pprint / confirm each commandcheck before deleting

xargs in system info / admin

  1. Situation: Delete old .tmp files found by find, safely (names may contain spaces).

    touch 'old report.tmp' a.tmp keep.txt
find . -name '*.tmp' -print0 | xargs -0 -r rm -v

    Why this way: -print0 / -0 keep “old report.tmp” as one name; -r does nothing if find found nothing. (find -delete or -exec rm {} + also work, Lesson 13.2.)

  2. Situation: Why plain xargs breaks on spaces (real failure).

    touch 'my file.txt'
ls *.txt | xargs rm
    rm: cannot remove 'my': No such file or directory rm: cannot remove 'file.txt': No such file or directory

    Why this way: xargs split “my file.txt” into “my” and “file.txt”. Use find -print0 | xargs -0.

xargs in devops / cloud

  1. Situation: Back up each config file with a .bak copy.

    touch nginx.conf app.conf
ls *.conf | xargs -I{} cp {} {}.bak
ls *.bak
    app.conf.bak nginx.conf.bak

    Why this way: -I{} runs one cp per file with the name in two places.

  2. Situation: Compress logs in parallel, 2 at a time.

    for d in 1 2 3 4; do seq 1 20000 > app$d.log; done
ls app*.log | xargs -P 2 -n 1 gzip
ls app*.log.gz | wc -l
    4

    Why this way: -P 2 uses two CPU cores; -n 1 gives each gzip one file.

xargs in software development

  1. Situation: Search for TODO in all Python files listed by find.

    mkdir -p pkg; printf 'x=1  # TODO fix\n' > pkg/a.py; printf 'y=2\n' > pkg/b.py
find pkg -name '*.py' -print0 | xargs -0 grep -n TODO
    pkg/a.py:1:x=1 # TODO fix

    Why this way: grep gets all file names as arguments and prints file:line for each match.

xargs in data analysis / engineering

  1. Situation: Count lines of many CSV files, in batches of 2.

    seq 1 4 > jan.csv; seq 1 6 > feb.csv; seq 1 3 > mar.csv
ls *.csv | xargs -n 2 wc -l
    6 feb.csv 4 jan.csv 10 total 3 mar.csv

    Why this way: -n 2 shows how xargs splits a list into several runs (each with its own total).

xargs in security

  1. Situation: Ask before each risky action (-p), here answering “n” automatically.

    Typical output (cannot be recorded on our build machine)

    ls *.key | xargs -p -n 1 rm
    rm s1.key ?...n rm s2.key ?...y (only s2.key was deleted)

    Why this way: -p prints each command and waits for y. With no answer nothing is deleted. Use it when deleting by pattern.

Undo and safety net

Chaining decides what runs; a wrong operator can run the wrong thing.

  • ; ran a step after a failure: use && between dependent steps, or set -e in scripts (Lesson 12.6).
  • xargs deleted the wrong files: there is no undo for rm. Always run the list first without the command, or with xargs -t echo / -p.
  • xargs split names with spaces: use find … -print0 | xargs -0, or -d '\n'.
  • $? was overwritten: save it immediately: cmd; rc=$?.
  • a && b || c ran c unexpectedly: b failed. Use if/then/else.

Error messages decoded

Errors and codes students see most. Each was really produced on our build machine.

  1. mkdir reports; mkdir reports
    mkdir: cannot create directory ‘reports’: File exists exit status: 1

    What it means: The second mkdir fails because the folder exists (code 1). With ; the script carries on anyway.

    Fix: mkdir -p (no error if it exists), or && to stop.

  2. echo '' | xargs rm
    rm: missing operand Try 'rm --help' for more information. exit status: 123

    What it means: Empty input, but GNU xargs still ran rm once, with no file: “missing operand”. 123 is xargs’ code for “a command it ran failed”.

    Fix: xargs -r skips the run when there is no input.

  3. touch s.sh; ./s.sh
    /home/riya/script.sh: line 1: ./s.sh: Permission denied exit status: 126

    What it means: The file exists but is not executable: 126.

    Fix: chmod +x s.sh (Lesson 12.5) or bash s.sh.

  4. lss
    /home/riya/script.sh: line 1: lss: command not found exit status: 127

    What it means: Command not found: 127. A typo, or the program is not installed / not in PATH.

    Fix: Check the spelling; type cmd; install it (Lesson 14).

  5. { echo a; echo b }
    /home/riya/script.sh: line 3: syntax error: unexpected end of file

    What it means: The closing } is read as an argument of echo, so bash waits for the real end and hits end of input: syntax error, code 2.

    Fix: A ; (or newline) before }: { echo a; echo b; }.

  6. timeout 1 sleep 5
    exit status: 124

    What it means: timeout stopped the command after 1 s: 124.

    Fix: Not a bug in your code; handle 124 in scripts.

Script it: deploy.sh

Riya’s fixed deploy script: every step guarded, a clear message and a non-zero exit code on failure, a dated release name with $( ), and xargs to copy the built files.

#!/bin/bash
release="release_$(date -d 2026-11-06 +%F)"
build()  { mkdir -p dist && printf 'a\nb\n' | xargs -I{} touch dist/{}.html; }
tests()  { [ -f dist/a.html ] && [ -f dist/b.html ]; }
deploy() { mkdir -p "$release" && ls dist/*.html | xargs -I{} cp {} "$release"/; }

build  || { echo "build failed" >&2; exit 1; }
tests  || { echo "tests failed" >&2; exit 2; }
deploy || { echo "deploy failed" >&2; exit 3; }
echo "deployed $(ls "$release" | wc -l) files to $release"
deployed 2 files to release_2026-11-06

Each failure exits with its own code (1, 2, 3), so whoever runs the script (cron, CI) knows exactly which step failed.

Puzzle answer Remember the question from the story? Open to check your guess.

Both print “failed”. The first because mkdir really failed (no permission for /root). The second although true succeeded: false (the middle command) failed, and || reacts to any failure before it. So a && b || c is not if-then-else: c runs when a fails or when b fails. Use if a; then b; else c; fi when b can fail.

Quick check Why is find … -print0 | xargs -0 rm safer than ls | xargs rm?
Answer: Plain xargs splits items at spaces and newlines, so “my file.txt” becomes two wrong names. NUL bytes cannot occur in file names, so -print0/-0 keeps every name whole.

Quick revision

Lesson 5.4 in one screen

  • $? = last exit code: 0 success, 1–255 failure. Save it at once: rc=$?.
  • Codes: 1 general, 2 serious/misuse (ls, grep, syntax), 124 timeout, 126 not executable, 127 not found, 128+N signal (130 Ctrl+C, 137 kill -9, 141 SIGPIPE). Values wrap at 256.

  • Never cd dir ; rm …: use &&.
  • { a; b; } (same shell; spaces and final ;), ( a; b ) (subshell).

  • xargs: -print0 | xargs -0, -I{}, -n, -r, -P, -t/-p.

Interview and viva questions

What does $? mean in Linux?

It holds the exit status of the last command: 0 for success, a non-zero number (1–255) for failure.

What is the difference between ;, && and ||?

; runs the next command always, && only if the previous succeeded, || only if it failed.

Is a && b || c the same as if-then-else?

No. c also runs when b fails. Use if a; then b; else c; fi when b can fail.

What do exit codes 126 and 127 mean?

126: the file was found but is not executable. 127: command not found.

What is the difference between $( ) and backticks?

They do the same (command substitution); $( ) nests easily and is easier to read, so it is preferred.

Why does xargs fail on file names with spaces?

By default it splits at spaces and newlines. Use find … -print0 | xargs -0.

How do I fix “Argument list too long”?

The list is bigger than ARG_MAX; use find … -print0 | xargs -0 cmd or find -exec cmd {} +.

  2. Fix: cd "${LOGDIR:?not set}" && rm -rf ./*, or better rm -rf "${LOGDIR:?}"/* (Lesson 3.3).
  3. Add set -euo pipefail and test with an empty variable.

Avoid: “add sudo so it doesn’t fail”.

Data platform · opsMid-level

200,000 files and “Argument list too long”

A nightly job runs gzip /data/export/*.csv and started failing as the folder grew.

The interviewer is checking: do you know ARG_MAX and xargs?

Show a strong answer
  • The glob expands to more bytes than the kernel’s argument limit (ARG_MAX).
  • find /data/export -name '*.csv' -print0 | xargs -0 -r -P 4 gzip or find … -exec gzip {} +.
  • -P speeds it up; -r avoids errors on empty days; check the exit code.

Avoid: raising limits or splitting by hand.

Platform · CISenior

The pipeline is green but the release is broken

A CI step runs ./build.sh; ./test.sh | tee test.log and always passes.

The interviewer is checking: do you understand how CI reads exit codes?

Show a strong answer
  • The step’s code is tee’s (the last command), so test failures are hidden; ; also ignores build failures.
  • Use set -euo pipefail, && between steps, and fail with distinct exit codes.
  • Add a deliberately failing test to prove the pipeline goes red.

Avoid: reading the log by eye each time.

Interview and certification corner

What does $? contain?
The exit status of the last command (0 = success).
Difference between && and ||?
&& runs the next only on success; || only on failure.
What do 126, 127 and 130 mean?
Not executable; command not found; killed by Ctrl+C (128+2).
What is command substitution?
$(cmd): the command’s output is inserted into the command line.
Why is a && b || c dangerous?
c also runs if b fails; it is not a real if/else.
How do you pass find results to a command safely?
find … -print0 | xargs -0 cmd, or find -exec cmd {} +.
How do you stop a script at the first error?
set -e (plus -u and -o pipefail), or cmd || exit 1 on each step.
Where this appears in certification exams
  • RHCSA (EX200): “Use input-output redirection” and “conditionally execute code (use of: if, test, [], etc.)”: exit codes and && / || are the base.
  • LFCS: Essential commands: chaining, exit codes and xargs with find.
  • CompTIA Linux+: Command chaining (;, &&, ||), exit codes, command substitution and xargs.
