Watching processes: ps, pstree, top and htop

ps takes a snapshot, pstree shows the family tree and top shows a live, sorted view. This lesson teaches the columns that matter, finds a real CPU hog and memory hog, and explains load average.

The problem

3 a.m.: the website is slow and the server’s fan is screaming. Riya logs in and has two minutes to answer three questions: what is running, who started it, and which one is eating the CPU or the memory? Linux has a few tools for exactly this: ps takes a snapshot, pstree shows the family tree, top and htop show a live, sorted view. Reading their columns correctly (%CPU, RSS, VIRT, load average, STAT) is the difference between “I restarted everything” and “I found the one runaway process”.

By the end of this page you will be able to:
  • take snapshots with ps aux, ps -ef and ps -eo with your own columns and sort order
  • see who started what with pstree -p, ps --forest and pgrep -a
  • read and drive top: the summary lines, load average, %CPU, RES vs VIRT, and keys P, M, k, u, 1, q
  • know what htop adds, and avoid the classic mistakes (ps | grep matching itself, VIRT as memory use, load average vs CPU count)

2 Definition

ps, pstree, top and htop

Formal definition (write this in exams)

ps (process status) prints a one-time snapshot of selected processes with selected columns. pstree displays running processes as a tree of parents and children. top is an interactive, continuously updating view of processes sorted by resource use, with system summary lines (uptime, load average, tasks, CPU and memory). htop is a friendlier, colourful alternative to top with mouse support and scrolling.

In simple words

ps = a photo. pstree = a family tree. top/htop = a live video.

Watching processes at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: photo, family tree, video

Three tools, three questions.

Basic What you will type every day

  • ps aux: every process with user, %CPU, %MEM and command.
  • ps -ef: every process with PPID (the parent).
  • pgrep -a nginx: PIDs and commands whose name matches.
  • top: live list, busiest first. Press M for memory, P for CPU, q to quit.

Intermediate Columns that matter

  • %CPU in ps = CPU time ÷ lifetime (an average); in top = share of the last interval. 100% = one full core; 4 cores can show 400%.
  • RSS/RES = real memory in RAM (KiB). VSZ/VIRT = all address space reserved, often huge and harmless. SHR = shared part (libraries).
  • TIME / TIME+ = total CPU time used, not wall-clock time; ELAPSED/etime = how long it has run.
  • Load average (1, 5, 15 min) = average number of tasks running or waiting (R) plus those in disk wait (D). Compare it with nproc.
  • PR/NI = priority and nice value (Lesson 11.5); TTY ? = no terminal (a daemon).

Advanced Behind the screen: /proc and sampling

  • ps and top have no special access: they read /proc/PID/stat, status, cmdline and /proc/loadavg, /proc/meminfo. The kernel generates these files on demand.
  • top computes %CPU by reading each process’s CPU ticks twice and dividing by the interval; that is why the first frame of top -b -n 1 can differ from a later one.
  • Linux load average includes D-state tasks (waiting for disk/NFS), so high load with idle CPUs points to storage, not CPU.
  • Memory: RSS counts shared pages in every process that maps them, so adding RSS over processes over-counts. PSS (in /proc/PID/smaps_rollup) shares them fairly.
  • Threads: ps -eLf and top -H show each thread; Java and browsers have hundreds.

Did you know? ps aux | grep nginx always finds at least one process, even when nginx is not running: the grep nginx itself. That is why people write grep [n]ginx, or better, use pgrep -a nginx, which never matches itself.

Exam tip: “Which command shows a dynamic real-time view of running processes?” → top (or htop). “A static snapshot?” → ps.

Quick check A 4-core server has load average 3.5. Is it overloaded?
Answer: No: up to about 4 the cores can keep up. Compare load with nproc; also check whether the load is D-state (disk) or real CPU.
Common mistake
✗“VIRT 5.6 GB, this program uses 5.6 GB of RAM!”
✓Look at RES/RSS (real RAM), and %MEM

VIRT counts all reserved address space: mapped files, libraries, memory reserved but never touched. RES is what is really in RAM.

pstree · ps --forest the family tree

🟢 Read-onlyno sudo

pstree draws processes as a tree. -p adds PIDs, -a arguments, -u user changes, -s PID the parents of PID. Give a PID or user to show only that branch. ps -ef --forest gives a similar tree with all ps columns.

✓ Use it when
  • understanding who started what
  • finding the parent of a strange process
  • service and container trees
✗ Don’t use it when
  • huge trees without -p or a PID (too long)

pstree · ps --forest in security

  1. Situation: Who started this sleep? Walk up the tree.

    pstree -s -p $(pgrep -u riya -n -x sleep) | sed -E 's/^.*(bash\()/…\1/'
    process_api(1)---app.sh(28411)---sleep(28414)

    Why this way: -s shows the ancestors. In incident response, a shell whose ancestor is a web server is a red flag.

pstree · ps --forest in system info / admin

  1. Situation: The same with ps.

    ps -o pid,ppid,cmd --forest -g $(pgrep -n -f -u riya app.sh)
    PID PPID CMD 28454 1 /bin/bash ./app.sh 28456 28454 \_ sleep 300 28457 28454 \_ sleep 301

    Why this way: -g = process group (the script and its children); --forest draws the branches.

Common mistake
✗ps aux | grep nginx | wc -l (to count nginx processes)
✓pgrep -c nginx

The grep line itself is counted, so the answer is always one too many, and 1 when nginx is not running at all.

top live view

🟢 Read-onlyno sudo

top refreshes every 3 seconds. Summary: uptime and load average, task counts by state, CPU split (us user, sy system, ni nice, id idle, wa I/O wait, st steal), memory and swap. Keys: P CPU sort, M memory, T time, 1 per CPU, c full command, u user, k kill, r renice, H threads, q quit.

✓ Use it when
  • live firefighting
  • watching a process over time
  • batch logs (top -b)
✗ Don’t use it when
  • reading %CPU from the very first top -b frame
  • leaving top running in scripts without -n

Syntax: top [-u USER] [-p PID] [-o FIELD] [-d SEC] [-b -n N]

Undo and safety net

Watching never changes anything; only quitting matters.

  • Stuck inside top: press q (or Ctrl+C).
  • Pressed k in top by accident: press Esc or Enter on an empty PID to cancel.
  • Changed top’s layout and saved it (W): delete ~/.config/procps/toprc.
  • htop not installed: sudo apt install htop (Lesson 14.1), or use top.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. ps -o pid,cpu
    PID CPU 28559 - 28561 - 28565 - 28567 - 28568 - 28579 - 28581 - 28583 - 28585 - 28586 - 28587 - 28588 - 28592 - 28593 - exit status: 0

    What it means: Wrong column name (it is %cpu, pcpu).

    Fix: ps L lists all column names.

  2. ps --sort=cpu% -e
    error: unknown sort specifier Usage: ps [options] Try 'ps --help <simple|list|output|threads|misc|all>' or 'ps --help <s|l|o|t|m|a>' for additional help text. For more details see ps(1). exit status: 1

    What it means: Unknown sort key.

    Fix: --sort=-%cpu or -pcpu.

  3. top -n 1
    top: failed tty get exit status: 1

    What it means: Not a terminal: top needs -b in pipes and scripts.

    Fix: top -b -n 1.

  4. htop
    /home/riya/script.sh: line 1: htop: command not found exit status: 127

    What it means: htop is not installed (exit 127).

    Fix: sudo apt install htop, or top.

Quick check top shows wa 60.0. What is slow?
Answer: The disk (or network storage): CPUs are idle waiting for I/O. Look for D-state processes and use iostat/iotop (Lesson 15.4).

6 Real-world use

Watching processes at work

1. Incidents

The first minute of a slowness incident: top or ps sorted by CPU and memory, load vs nproc.

Alert→ps --sort→act

2. Health checks

Scripts and monitoring check that a process exists with pgrep and restart or alert if not.

Check→pgrep→alert

3. Security

Investigators trace an odd process to its parent: a shell under a web server or cron points to compromise.

Odd PID→pstree -s→contain

4. Capacity

Batch snapshots in cron show which process grew overnight (memory leaks).

Cron→top -b→trend

5. Java and DB tuning

top -H shows the thread using the CPU; its TID in hex finds it in a Java thread dump.

Hot thread→top -H→fix

Puzzle answer Remember the question from the story? Open to check your guess.

Load average counts tasks that are running or waiting, and on Linux also tasks in D state (uninterruptible disk/NFS wait). With CPUs 95% idle and a D-state process, the load comes from waiting for storage, not from the CPU. Check wa in top, D processes (ps -eo stat,pid,cmd | grep ^D) and the disk or NFS server.

Quick revision

Lesson 11.2 in one screen

  • ps aux (user, %CPU, %MEM, RSS) and ps -ef (PPID); ps -eo COLS --sort=-%cpu for scripts.
  • pgrep -a/-x/-f/-u/-c finds PIDs by name and never matches itself; ps | grep does.
  • pstree -p, -s PID for ancestors; ps -ef --forest.
  • top: load average, task states, us/sy/id/wa, memory; keys P M c 1 u k q; top -b -n 1 in scripts.
  • RSS = real RAM; VSZ = reserved; TIME = CPU time; %CPU 100 = one core.
  • Load = running + waiting + D-state; compare with nproc.

Interview and viva questions

What is the difference between ps aux and ps -ef?

Both list all processes. aux (BSD style) shows %CPU, %MEM, VSZ, RSS and STAT; -ef (System V style) shows PPID and start time.

How do I find the process using the most CPU?

ps -eo pid,%cpu,cmd --sort=-%cpu | head, or top (sorted by CPU by default).

How do I find the process using the most memory?

ps -eo pid,rss,cmd --sort=-rss | head, or press M in top.

What is load average?

The average number of tasks running, waiting for a CPU or in uninterruptible (disk) wait over 1, 5 and 15 minutes.

What is the difference between VIRT and RES in top?

VIRT is all reserved virtual memory; RES is the part actually in RAM.

How do I exit top?

Press q.

Is htop better than top?

It is friendlier (scrolling, mouse, colours, tree with F5); top is always installed and scriptable with -b.

What does ps aux show?
