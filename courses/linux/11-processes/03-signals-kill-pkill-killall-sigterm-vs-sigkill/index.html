Signals: kill, pkill and killall, SIGTERM vs SIGKILL, and trap

kill does not kill: it sends a signal. Learn the signals, why TERM comes before KILL, how to select processes by PID or name safely, and how trap lets your scripts clean up.

The problem

A report job has hung for an hour. Riya runs kill -9 on it, as she saw online. It disappears, but it leaves a half-written file, a lock file and a database connection that stay until morning. Her senior sighs: “Always ask nicely first.” Linux processes are stopped, paused, reloaded and told about events with signals: small numbered messages from the kernel or another process. SIGTERM (15) asks a program to finish cleanly; SIGKILL (9) removes it without warning; SIGHUP (1) often means “reload your config”; Ctrl+C sends SIGINT. This lesson shows each signal, the commands that send them (kill, pkill, killall), and trap, which lets your own scripts react.

By the end of this page you will be able to:
  • explain what a signal is and name the common ones: HUP, INT, QUIT, KILL, TERM, STOP, CONT, TSTP, USR1, CHLD
  • send signals by PID with kill, and by name or pattern with pkill and killall, safely
  • use the correct order: TERM first, wait, KILL only if needed, and read exit codes 130, 137, 143
  • handle signals in your own scripts with trap, including cleanup on EXIT

2 Definition

Signals and the kill commands

Formal definition (write this in exams)

A signal is a short, numbered notification the kernel delivers to a process to report an event or request an action (stop, reload, interrupt, continue). kill sends a signal to processes by PID, pkill by name or pattern, and killall by exact name. A process may handle, ignore or accept the default action of most signals; SIGKILL and SIGSTOP cannot be caught.

In simple words

A tap on the shoulder with a number. kill is the tap, not the killing.

Signals at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: ending a meeting

Ask, interrupt, or remove by force.

Basic What you will type

  • Ctrl+C: stop the command in front of you (SIGINT).
  • kill 4120: ask process 4120 to stop (SIGTERM).
  • kill -9 4120: force it (SIGKILL), only if TERM did not work.
  • pkill -x firefox: by name.

Intermediate Catch, ignore or default

  • For each signal a process can: run the default action (terminate, core dump, stop, continue, ignore), ignore it, or catch it with a handler.
  • KILL (9) and STOP (19) can never be caught or ignored.
  • A process killed by signal n has exit status 128 + n: 130 for INT, 137 for KILL, 143 for TERM.
  • You may signal only your own processes; root can signal any.
  • trap 'commands' SIGNAL catches signals in bash; trap … EXIT runs when the script ends for any reason except KILL.

Advanced Behind the screen: the kernel’s pending set

  • kill is the kill(2) system call: the kernel sets a bit in the target’s pending signal set (see SigPnd, SigBlk, SigIgn, SigCgt in /proc/PID/status).
  • When the process next returns from the kernel, the signal is delivered: its handler runs, or the default action happens.
  • A process in D state (uninterruptible disk/NFS wait) does not die even from KILL until the I/O returns.
  • A zombie (Z) is already dead; killing it does nothing. Its parent must wait() for it, or the parent must die so init adopts and reaps it.
  • The terminal driver turns keys into signals: Ctrl+C → INT, Ctrl+\ → QUIT, Ctrl+Z → TSTP, closing the terminal → HUP to the session.
  • systemd and Docker stop services with TERM, wait (90 s / 10 s), then KILL.

Did you know? On Solaris and some older Unix systems, killall really kills all processes (it is used at shutdown). Typing the Linux habit killall java as root there can take the whole machine down. On any unfamiliar system, prefer pkill.

Exam tip: “What is the difference between kill -9 and kill -15?” → 15 (TERM) asks the process to exit and can be caught, allowing cleanup; 9 (KILL) is handled by the kernel, cannot be caught, and gives no chance to clean up.

Quick check A process exited with status 143. What happened?
Answer: 143 − 128 = 15: it was terminated by SIGTERM.

kill -STOP PID · kill -CONT PID · Ctrl+Z pause and resume

🟡 Changes filesno sudo

STOP freezes a process (state T in ps); it uses no CPU but keeps its memory and open files. CONT lets it run again. Ctrl+Z sends TSTP, the catchable version, to the program in front of you; fg and bg continue it (Lesson 11.4).

✓ Use it when
  • pausing a heavy job for a while
  • freezing a process to inspect it
✗ Don’t use it when
  • stopping a process that holds a lock others need

trap 'cmds' SIGNAL… · trap … EXIT · trap - SIG · trap '' SIG trap in your scripts

🟢 Read-onlyno sudo

trap 'commands' TERM INT runs the commands when a signal arrives. EXIT is a bash pseudo-signal that runs when the script ends, normally or by a catchable signal. trap '' INT ignores a signal; trap - INT restores the default; trap -p shows the traps.

✓ Use it when
  • cleanup of temp and lock files
  • graceful shutdown of your own scripts
  • reload on HUP
✗ Don’t use it when
  • complex logic inside a handler
  • expecting EXIT to run after kill -9

Undo and safety net

A killed process cannot be brought back; its unsaved work is lost.

  • Killed the wrong process: restart it (systemctl restart, or the command); check its logs.
  • Lock or PID file left after kill -9: check nothing is running (pgrep), then remove the stale file.
  • Stopped (T) and forgotten: kill -CONT PID or fg.
  • Next time: preview with pgrep -a, send TERM, wait, check with kill -0.

6 Real-world use

Signals at work

1. Reloading servers without downtime

nginx -s reload, systemctl reload sshd and kill -HUP make daemons re-read their config while connections continue.

Edit config→HUP→new config live

2. Graceful shutdown in deployments

Kubernetes, Docker and systemd send TERM, wait a grace period, then KILL. Apps that trap TERM finish requests first.

Deploy→TERM → wait → KILL→no lost requests

3. Diagnosing crashes

Exit 137 in a container usually means the OOM killer (SIGKILL); 139 is SIGSEGV; 143 a normal stop.

Exit code→128+n→cause

4. Log rotation

logrotate sends USR1 or HUP so programs reopen their log files (Lesson 18.2).

Rotate→USR1→new log

5. Safe scripts

Backup and ETL scripts trap EXIT to remove temp files and locks, and INT/TERM to stop cleanly.

Start→trap→clean end

Build it step by step: a script that stops cleanly

Scenario: Riya grows a background job with proper signal handling.

  1. 1. No trap: TERM leaves the lock.

    cd ~; printf 'touch ~/lockjob.lock\nsleep 30\nrm -f ~/lockjob.lock\n' > lockjob.sh; bash lockjob.sh & p=$!; sleep 0.3; kill $p; sleep 0.2; ls lockjob.lock

  2. 2. trap EXIT + wait: the lock is removed.

    cd ~; rm -f lockjob.lock; printf 'touch ~/lockjob.lock\ntrap "rm -f ~/lockjob.lock" EXIT\nsleep 30 & wait $!\n' > lockjob.sh; bash lockjob.sh & p=$!; sleep 0.3; kill $p; sleep 0.2; ls lockjob.lock 2>&1
    ls: cannot access 'lockjob.lock': No such file or directory

  3. 3. A TERM message and the right status.

    cd ~; printf 'touch ~/lockjob.lock\ntrap "rm -f ~/lockjob.lock; echo cleaned" EXIT\ntrap "echo got TERM; exit 143" TERM\nsleep 30 & wait $!\n' > lockjob.sh; bash lockjob.sh & p=$!; sleep 0.3; kill $p; wait $p; echo "status $?"
    got TERM cleaned status 143

  4. 4. Verify: no lock, no leftover sleep.

Name, number and -s are the same

Three spellings of TERM.

V2

V3

Polite stop with a timeout, then force

The pattern systemd and Docker use.

V4

A process that ignores TERM

bash -c "trap '' TERM; sleep 2" & p=$!; sleep 0.3

TERM ignored: still alive KILL: status 137

Only KILL works against a program that ignores TERM.

V5

Kill a whole process group

setsid bash -c 'sleep 60 & sleep 61 & wait' & sleep 0.3; pg=$(pgrep -n -x bash -u riya); kill -TERM -- -$(ps -o pgid= -p $pg | tr -d ' '); sleep 0.3; echo "sleeps left: $(pgrep -c -f '^sleep 6[01]$')"

A negative PID means the whole group: parent and children.

V6

Script it: graceful-stop.sh

Stop every process matching a name: list them, send TERM, wait up to 5 seconds, KILL any that are left, and report each step.

name=${1:-demo-nap}
cp /bin/sleep ~/demo-nap; for i in 1 2; do (~/demo-nap 70 > /dev/null 2>&1 &); done; sleep 0.3   # demo targets
mapfile -t pids < <(pgrep -u "$USER" -x "$name")
[ ${#pids[@]} -eq 0 ] && { echo "no $name processes"; exit 0; }
echo "found ${#pids[@]} $name process(es)"
kill -TERM "${pids[@]}" 2>/dev/null
for t in 1 2 3 4 5; do
  left=$(pgrep -c -u "$USER" -x "$name")
  [ "$left" -eq 0 ] && { echo "all stopped after TERM (${t}s)"; exit 0; }
  sleep 1
done
pkill -KILL -u "$USER" -x "$name" && echo "forced $left with KILL"
found 2 demo-nap process(es) all stopped after TERM (3s)

Run without a name, so it starts and stops two demo processes (a copy of sleep called demo-nap).

Puzzle answer Remember the question from the story? Open to check your guess.

Ctrl+C sends INT and kill sends TERM; bash ends the script and runs the EXIT trap, so the lock is removed. kill -9 sends KILL, which the kernel carries out without running any code in the process: no trap, no cleanup, the lock stays. The fix is to send TERM first and use KILL only if the process does not stop; and to make the script check whether the PID in an old lock is still alive before refusing to start. kill nginx fails because kill takes PIDs; use pkill -x nginx or, for a service, systemctl reload/stop nginx.

Quick check What exit status does a process have after kill -9?
Answer: 137 (128 + 9).

Quick revision

Lesson 11.3 in one screen

  • A signal is a numbered message; kill sends one (TERM by default).
  • HUP 1 reload/hang-up, INT 2 Ctrl+C, QUIT 3, KILL 9, USR1 10, PIPE 13, TERM 15, CHLD 17, CONT 18, STOP 19, TSTP 20.
  • TERM first, wait, check with kill -0, KILL only if needed. KILL and STOP cannot be caught.
  • pkill/pgrep: -x exact, -f full command, -u user, -n/-o newest/oldest; preview with pgrep -a. killall: exact name.
  • Exit status 128+n: 130 INT, 137 KILL, 143 TERM; kill -l n translates.
  • trap 'cmds' TERM INT HUP; trap … EXIT for cleanup; trap '' SIG ignores; trap - SIG restores.

Interview and viva questions

What is a signal in Linux?

A numbered notification sent to a process by the kernel or another process, such as SIGTERM or SIGKILL.

What is the difference between kill -9 and kill -15?

15 (TERM) can be caught so the program can clean up; 9 (KILL) cannot be caught and stops it immediately.

How do I kill a process by name?

pkill -x name or killall name; preview with pgrep -a.

Why does a process not die with kill -9?

It is in D state (waiting on I/O) or a zombie that its parent has not reaped.

What does exit code 137 mean?

Killed by SIGKILL (128+9), often the OOM killer in containers.

How do I clean up when a bash script is stopped?

Use trap 'cleanup' EXIT (and INT/TERM).

What does kill -HUP do?

Sends SIGHUP; many daemons reload their configuration.

Real-world scenario questions (asked in company interviews)

Interview questions about signals, from fresher to senior rounds.

Any company · basicsFresher

“How do you kill a process?”

Very common.

The interviewer is checking: steps?

Show a strong answer
  • Find the PID: pgrep -a name / ps aux.
  • kill PID (TERM); check; kill -9 PID only if needed.
  • By name: pkill -x name.

Avoid: “kill -9 everything”.

Service companyJunior

App leaves a lock file after a restart

Ops use kill -9.

The interviewer is checking: fix?

Show a strong answer
  1. Use TERM and give it time.
  2. Add trap cleanup EXIT in scripts.
  3. On start, check if the PID in the lock is alive (kill -0) before refusing.

Avoid: deleting locks by hand every morning.

Cloud / KubernetesMid-level

Pods exit with code 137

Random restarts.

The interviewer is checking: cause?

Show a strong answer
  • 137 = SIGKILL: OOM killer or the grace period expired.
  • Check kubectl describe (OOMKilled) and memory limits.
  • Handle TERM to shut down within terminationGracePeriodSeconds.

Avoid: raising CPU limits.

PlatformSenior

kill -9 does not remove a process

State D in ps.

The interviewer is checking: why?

Show a strong answer
  • D = uninterruptible sleep in the kernel (often NFS or a dying disk).
  • The signal is pending until the I/O returns.
  • Fix the storage path; sometimes only a reboot clears it.

Avoid: kill -9 harder.
