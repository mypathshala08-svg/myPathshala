Quoting and expansion: single vs double quotes and escaping

Before running any command the shell rewrites it: variables, command output and wildcards are expanded, then the result is split into words. Quotes decide which steps happen. This lesson makes that visible and shows how to quote correctly.

The problem

Riya’s backup script works for months. Then a colleague saves a file called Q3 report.xlsx, with a space, and the script fails with “No such file: Q3” and “No such file: report.xlsx”. Another script prints a price as Price: 5 instead of Price: $5. A third one, meant to delete $dir/*, nearly deletes /* because $dir was empty. All three are quoting bugs. Before running any command, the shell rewrites your line: it expands $variables, $(commands), * wildcards and ~, then splits the result into words. Quotes decide which of those steps happen.

  • avoid word splitting and globbing bugs by quoting variables: "$var", "$@", "$(cmd)"
  • know the difference between $*, "$*", $@ and "$@", checked with real runs
  • combine quotes, print quotes inside quotes, and debug with printf '[%s]\n' and set -x

2 Definition

Quoting and expansion

Formal definition (write this in exams)

Quoting removes the special meaning of characters to the shell. Single quotes preserve every character literally. Double quotes preserve everything except $, ` and \ (so variable, command and arithmetic substitution still happen) and prevent word splitting and pathname expansion. A backslash quotes the single next character. Expansion is the rewriting the shell does to an unquoted line before running it.

In simple words

Single quotes: exactly as typed. Double quotes: fill in $, keep it one piece.

Quoting at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: envelopes

How your text travels to the command.

Basic What you will type every day

  • echo "Hello $USER": double quotes, the variable is filled in.
  • echo 'Cost: $5': single quotes, printed exactly.
  • cp "$file" "$dest": quote every variable that holds a name.
  • echo "She said \"hi\"": backslash before a quote inside the same kind of quotes.

Intermediate The rules

  • Single quotes: everything literal; a single quote cannot appear inside, not even as \'.
  • Double quotes: $var, ${…}, $(…), `…`, $((…)) and \ before $ ` " \ still work; no word splitting, no wildcards, no ~.
  • Backslash outside quotes protects the next character (a space, *, $).
  • $'…' (ANSI-C) understands \n \t \e \'.
  • "$@" gives each argument as its own word; "$*" joins them into one; unquoted $@/$* are split again at spaces.

Advanced Behind the screen: the order of expansions

  • For each line bash does: brace expansion → tilde → parameter, arithmetic and command substitution (left to right) → word splitting → pathname expansion (globbing) → quote removal. Full order in Lesson 12.11.
  • Word splitting uses IFS (space, tab, newline by default) and happens only on the results of unquoted expansions, never on text you typed.
  • Quote removal is last: the program never sees your quotes. echo "a" and echo a pass the same argument.
  • History expansion (!) runs before all of this in interactive shells, even inside double quotes (Lesson 12.3).
  • [[ … ]] does no word splitting or globbing on variables; [ … ] is an ordinary command, so it does (Lesson 12.8).

Did you know? Quotes are for the shell, not for the program. When you type grep "error" log.txt, grep receives error without quotes. That is why grep "my error" works: the quotes only told the shell to keep the two words together.

Exam tip: “Difference between single and double quotes in shell?” → Single quotes preserve the literal value of every character; double quotes allow $, ` and \ (variable, command and arithmetic substitution) but still prevent word splitting and globbing.

Quick check What does echo "Today is $(date +%A)" print, and what does the same with single quotes print?
Answer: Double: Today is Wednesday (the command runs). Single: Today is $(date +%A), literally.

✗echo "Using \"\$@\": \"$@\"" → claimed output: "arg1" "arg2"
✓Real output: Using "$@": "arg1 arg2"

Inside one double-quoted string, $@ is joined with spaces like $*. The difference between "$@" and "$*" only shows when they are used as separate arguments (a for loop, a command): see the $@ card below. Checked on our build machine.

Common mistake
✗“Without double quotes, $* expands to a single string”
✓Unquoted $* and $@ are split again at spaces into separate words; only "$*" is one string

Real run with the arguments "a b" and c: for x in $* gives three words a, b, c; for x in "$*" gives one: a b c; for x in "$@" gives two: a b and c.

"double quotes" expand, keep one word

🟢 Read-onlyno sudo

Inside double quotes, $var, ${var}, $(cmd), $((…)) and backticks are expanded; spaces, *, ?, ~ and single quotes are kept literally. Use \$, \", \\ and \` for the four special characters.

✓ Use it when
  • any variable that holds a file name, path or user input
  • command substitution results
✗ Don’t use it when
  • when you really want splitting or globbing (rare; use arrays instead)

Syntax: cmd "$var" · "$(cmd)" · "text with \"quotes\" and \$"

cpcopy"$f"one word"$dest/"one word

'single quotes' exactly as typed

🟢 Read-onlyno sudo

Everything between single quotes is literal: $, *, \, !, ". There is no way to put a single quote inside; close, add \', and reopen: 'it'\''s'.

✓ Use it when
  • text that must not change: prices, regex, awk and sed programs
  • commands to run later (ssh, cron)
✗ Don’t use it when
  • when you need a variable inside (use double quotes)

'single quotes' in devops / cloud

  1. Situation: Expand here or on the other side?

    bash -c "echo here: $USER"

Common mistake
✗rm -rf $dir/*
✓rm -rf "${dir:?dir is empty}"/* (and set -u)

If dir is empty, the line becomes rm -rf /*. ${dir:?msg} stops with an error when dir is empty or unset; quotes keep names with spaces safe. Lesson 12.6 adds set -u.

\ backslash · $'…' escape one character

🟢 Read-onlyno sudo

Outside quotes a backslash protects the next character: my\ file.txt, \*, \$. At the end of a line it joins the next line. $'…' understands C escapes: \n, \t, \', \\, \e.

✓ Use it when
  • one special character
  • file names with spaces typed by hand
  • tabs and newlines in text
✗ Don’t use it when
  • long strings full of backslashes (use single quotes)

"$@" vs "$*" vs $@ all the arguments

🟢 Read-onlyno sudo

"$@" expands to each positional parameter as a separate word, exactly as given. "$*" joins them into one word separated by the first character of IFS. Unquoted $@ and $* are split again at every space.

✓ Use it when
  • passing all of a script’s arguments on
  • loops over arguments
✗ Don’t use it when
  • $* and unquoted $@ (they break arguments with spaces)

Syntax: for a in "$@"; do …; done · other_cmd "$@"

"$@" vs "$*" vs $@ in devops / cloud

  1. Situation: A wrapper script that passes everything on.

    printf 'printf "[%%s]\\n" "$@"\n' > inner.sh
printf 'echo "wrapper got $# args"\nbash inner.sh "$@"\n' > wrap.sh
bash wrap.sh 'two words' one
    wrapper got 2 args [two words] [one]

    Why this way: "$@" is the only form that forwards arguments with spaces intact. Every wrapper, alias replacement and Docker entrypoint uses it.

"$@" vs "$*" vs $@ in software development

  1. Situation: Join arguments with commas.

    set -- apple banana 'dragon fruit'
( IFS=,; echo "$*" )
    apple,banana,dragon fruit

    Why this way: "$*" joins with the first character of IFS; the ( ) keeps the IFS change local.

Undo and safety net

Quoting mistakes are fixed by quoting; the damage is in what the command did.

  • A loop split a name with spaces: quote the variable; for lists of names use arrays or find -print0 | xargs -0.
  • An empty variable widened a command (rm, chmod): use ${var:?} and set -u; test with echo first.
  • The prompt shows > and waits: an unclosed quote; press Ctrl+C and retype.
  • Not sure what the shell made of a line: printf '[%s]\n' … or set -x (Lesson 12.6).

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. f="my report.txt"; cat $f
    cat: my: No such file or directory cat: report.txt: No such file or directory exit status: 1

    What it means: Unquoted: split into my and report.txt.

    Fix: cat "$f".

  2. echo 'it's'
    /home/riya/script.sh: line 1: unexpected EOF while looking for matching `''

    What it means: The quote in it's closed the string; the next one opens a new one that never ends.

    Fix: "it's" or 'it'\''s'.

  3. [ $name = Riya ]
    /home/riya/script.sh: line 1: [: =: unary operator expected exit status: 2

    What it means: Empty $name leaves [ = Riya ]: too few words.

    Fix: [ "$name" = Riya ].

  4. echo "${HOME"
    /home/riya/script.sh: line 2: unexpected EOF while looking for matching `"'

    What it means: Missing } in a ${ } expansion.

    Fix: "${HOME}".

Quick check Why does [ $name = Riya ] fail when name is empty, but [ "$name" = Riya ] works?
Answer: Unquoted, the empty value disappears and [ sees “= Riya”. Quoted, it sees an empty string "" as the first word.

6 Real-world use

Quoting at work

1. Backup and file scripts

Every path variable is quoted, because users create file names with spaces, brackets and dashes.

Name→"$f"→safe

2. Data pipelines

awk, sed and jq programs go in single quotes so $1 and $field reach the tool, not the shell.

Program→'...'→run

3. Wrappers and entrypoints

Docker entrypoints and tool wrappers end with exec "$@" to pass every argument unchanged.

Wrap→"$@"→exec

4. Safety in production

Famous outages were caused by rm -rf $DIR/ with an empty DIR. Quoting plus ${VAR:?} stops it.

Check→${v:?}→stop

5. Remote commands

Single quotes send the command to the server unexpanded; double quotes expand locally first.

Local→'...'→remote

Splitting and globbing

V4

A list in a variable vs an array

V5

Changing IFS for one read

IFS=: for read only: the /etc/passwd fields split at colons.

V6

Inside one double-quoted echo string both are joined with spaces: the output is "arg1 arg2", not "arg1" "arg2".

Quick revision

Lesson 12.4 in one screen

  • 'single' = all literal; "double" = $ ` \ still work, but no splitting, no wildcards, no ~.
  • Unquoted expansions are split at IFS (space, tab, newline) and globbed: quote every "$var" and "$(cmd)".
  • \ protects one character; $'…' understands \n \t \'.
  • "$@" = each argument whole (use it); "$*" = one string; $@/$* unquoted = split again.
  • Quotes are removed before the program runs; for names starting with -, use -- or ./.
  • Guard dangerous commands with ${var:?}; debug with printf '[%s]\n' and set -x.

Interview and viva questions

What is the difference between single and double quotes in bash?

Single quotes keep every character literal; double quotes still expand $variables, $(commands), arithmetic and backslash escapes, but prevent word splitting and globbing.

Why should I quote variables in bash?

Unquoted values are split at spaces and wildcards are expanded, which breaks file names with spaces and can widen commands like rm.

What is the difference between $@ and $*?

"$@" expands to each argument as a separate word; "$*" joins all arguments into one string. Unquoted, both are split again.

How do I put a single quote inside single quotes?

You cannot; close the quote, add \', and reopen: 'it'\''s', or use double quotes "it's".

How do I print a literal dollar sign?

Use \$ inside double quotes, or single quotes: 'Cost $5'.

What does $'...' mean in bash?

ANSI-C quoting: escapes like \n, \t and \' are turned into the real characters.

How do I handle a file name starting with a dash?

Use -- to end options (rm -- -file) or a path (./-file).

Interview and certification corner

What is word splitting?
Cutting the result of an unquoted expansion into words at IFS characters.
What is IFS?
Internal Field Separator: space, tab and newline by default.
$(cmd) vs backticks?
Same result; $( ) nests and reads better.

No, quotes stop globbing.

The empty value disappears; quote it.
