Shell options for safer scripts: set -e, set -u, set -x, set -o vi and unset

Bash is forgiving by default: scripts continue after errors, unknown variables are empty and pipes hide failures. This lesson switches on strict mode, shows each option’s traps, and debugs scripts with set -x.

The problem

Riya’s deploy script prints an error on line 3, “cp: cannot stat app.jar”, and then cheerfully continues: it stops the old version, deploys nothing, and prints “deploy done”. The website is down and the CI pipeline is green, because the last command succeeded. Another script used $BACKUP_DIR, which was never set, and wrote backups into /. Bash’s defaults are forgiving: keep going after errors, treat unknown variables as empty, ignore failures in the middle of pipelines. A few shell options turn a forgiving shell into a strict one: set -e, set -u, set -o pipefail, and set -x to see every line as it runs.

By the end of this page you will be able to:
  • make scripts stop at the first error with set -e, and know its exceptions and traps
  • catch typos and missing settings with set -u, and failures inside pipes with set -o pipefail
  • debug any script with set -x / bash -x and a better PS4; check syntax with bash -n
  • use set -o, set +o, noclobber, set -o vi, set -- and unset (variables and functions)

2 Definition

Shell options with set

Formal definition (write this in exams)

The set builtin turns shell options on (-x or -o NAME) and off (+x or +o NAME). errexit (-e) exits on the first failing command, nounset (-u) treats expansion of unset variables as an error, pipefail makes a pipeline fail if any of its commands fails, and xtrace (-x) prints each command before it runs. unset removes variables and functions.

In simple words

set -e = stop on error. set -u = stop on unknown variable. pipefail = pipes fail honestly. set -x = show me.

Words you’ll meet in this lesson

errexit (-e)Exit on the first failure.
nounset (-u)Unknown variable = error.

xtrace (-x)Print each command.

noclobber (-C)> will not overwrite.

Strict modeset -euo pipefail.

Shell options at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a factory line

Stop the line at the first broken part, and film every station.

Basic What you will type

  • Line 2 of every new script: set -euo pipefail.
  • Debugging: bash -x script.sh prints each command with + before running it.
  • Syntax only: bash -n script.sh.
  • set -o lists all options; set +x switches one off.

Intermediate The rules (and exceptions)

  • -e exits when a command fails, except: commands in if/while conditions, before &&/||, negated with !, and non-last parts of a pipe.
  • Under -e, ((count++)) with count=0 “fails” (the expression is 0), and var=$(false) exits; local var=$(false) does not.
  • -u makes using an unset variable an error; ${var:-default} and ${var-} are still allowed. $@ with no arguments is fine in bash ≥ 4.4.
  • pipefail: a pipeline’s status is the last non-zero status in it (default: only the last command).
  • -x prints each command after expansion, prefixed with $PS4 (default + ), to stderr.

Advanced Behind the screen: $- and SHELLOPTS

  • Single-letter options are in $- (e.g. hBeux); long names in $SHELLOPTS. set -o prints them; shopt holds bash’s other options (Lesson 12.3).
  • set -e is ignored inside a function called from an if or && context: the whole call becomes “checked”. This is why many experts prefer explicit checks plus trap … ERR (Lesson 12.10).
  • PS4='+ ${BASH_SOURCE}:${LINENO}: ' adds file and line numbers to the trace.
  • set -x output goes to stderr: exec 2>trace.log or BASH_XTRACEFD sends it to a file.
  • set -- replaces the positional parameters ($1, $2…); set with no arguments lists all variables and functions.

Did you know? set -o vi turns your command line into a tiny vi editor: press Esc, then b, w, dw, 0, $ work as in vim (Lesson 4.2). set -o emacs brings back the default keys.

Exam tip: “How do you debug a shell script?” → bash -x script.sh (or set -x inside it) to print every command as executed; bash -n to check syntax.

Quick check Your script has set -e. Does grep -q error log.txt || echo "no errors" stop the script when grep finds nothing?
Answer: No: a command before || is “checked”, so set -e ignores its failure.
Common mistake
✗set -e and then ((count++)) with count=0
✓count=$((count + 1)) or ((count++)) || true or ((++count))

((expression)) returns status 1 when the expression’s value is 0, and count++ evaluates to the OLD value (0). set -e then exits silently. This is the puzzle; checked on our build machine.

set -e (errexit) stop at the first error

🟢 Read-onlyno sudo

After set -e, the script exits as soon as a command returns non-zero, with that status. Failures in if/while conditions, before && or ||, after !, and in non-final pipe parts do not count.

✓ Use it when
  • every script that changes something (deploy, backup, delete)
  • scripts run by cron or CI
✗ Don’t use it when
  • commands you expect to fail sometimes (use || or if)
  • interactive shells (one typo closes the terminal)

Syntax: set -e · cmd || true · if cmd; then …; fi

setbuiltin-eerrexit-unounset-o pipefailpipes

set -euo pipefail = all three in one line.

OptionWhat it doesWhen to use it
set -eswitch online 2
cmd || trueallow this one to failoptional steps
if cmd; thenhandle failure yourselfdecisions
cmd || { echo msg; exit 1; }fail with a messageclarity
set +e … set -erelax for a blockrare

set -e (errexit) in devops / cloud

  1. Situation: Optional steps under set -e.

    cd ~/so; cat > opt.sh <<'EOF'
set -e
rm -f /tmp/nothing-here.tmp
grep -q error access.log || echo 'no errors found (ok)'
if ! grep -q 500 access.log; then echo 'no 500s'; else echo 'has 500s'; fi
echo finished
EOF
bash opt.sh; echo "status $?"
    no errors found (ok) has 500s finished status 0

    Why this way: || and if make failures “expected”, so set -e lets them pass.

set -e (errexit) in testing / qa

  1. Situation: The puzzle: ((count++)) at zero.

    bash -c 'set -e; count=0; ((count++)); echo "never printed"'; echo "status $?"
bash -c 'set -e; count=0; count=$((count+1)); echo "count=$count"'
    status 1 count=1

    Why this way: ((0)) is “false” (status 1), and count++ returns the old value 0. Use count=$((count+1)) or ((++count)).

set -u (nounset) unknown variable = error

🟢 Read-onlyno sudo

With set -u, expanding a variable that was never set stops the script with “unbound variable”. Optional values use a default: ${VAR:-default}, or ${VAR-} for “empty if unset”.

✓ Use it when
  • catching typos in variable names
  • required settings (paths, hosts)
✗ Don’t use it when
  • variables that are optional by design (give them a default)

Syntax: set -u · ${VAR:-default} · ${VAR:?message}

OptionWhat it doesWhen to use it
set -uswitch oncatch typos
${V:-x}x if unset or emptyoptional
${V-}empty if unsetquiet check
${V:?msg}stop with msgrequired
[ -n "${V-}" ]is it set?tests

echo "saving to $backpu_dir"
EOF
bash u.sh; echo "status $?"

A typo (backpu) would have saved to an empty path; set -u stopped it.

set -u (nounset) in system info / admin

  1. Situation: Optional settings with defaults.

    bash -c 'set -u; mode=${MODE:-dev}; echo "mode=$mode"'

    mode=dev mode=prod

set -o pipefail honest pipelines

🟢 Read-onlyno sudo

Normally a pipeline’s status is the last command’s. With pipefail it is the last non-zero status of any command in it, so set -e also catches failures in the middle. ${PIPESTATUS[@]} shows every part’s status.

✓ Use it when
  • pipes inside scripts
  • checking that every stage worked
✗ Don’t use it when
  • pipes where an early stage is allowed to stop early (head can cause SIGPIPE, status 141)

Syntax: set -o pipefail · echo "${PIPESTATUS[@]}"

OptionWhat it doesWhen to use it
set -o pipefailswitch onscripts
${PIPESTATUS[@]}all statusesdebugging
grep … | wc -lno match = failure!expect it
… | headmay give 141 (SIGPIPE)careful

set -o pipefail in devops / cloud

  1. Situation: Strict mode in one line.

    cd ~/so; printf 'set -euo pipefail\ngrep 500 access.log | wc -l\ngrep 999 access.log | wc -l\necho never\n' > strict.sh
bash strict.sh; echo "status $?"
    1 0 status 1

    Why this way: The second grep found nothing (status 1); pipefail + -e stopped the script. If “no match” is fine, write grep … || true.

Common mistake
✗#!/bin/bash -euo pipefail (all options in the shebang)
✓#!/bin/bash then on line 2: set -euo pipefail

Linux passes everything after the interpreter as ONE argument, so the shebang trick works for a single option at most; set on line 2 always works, and also when someone runs bash script.sh.

set -x · bash -x · PS4 see every line

🟢 Read-onlyno sudo

bash -x s.sh (or set -x inside) prints each command after expansion, prefixed by +, to stderr. Nesting adds more +. set +x stops it. PS4 changes the prefix, for example to show line numbers.

✓ Use it when
  • finding which line misbehaves
  • seeing variable values as they really are
✗ Don’t use it when
  • scripts that handle passwords (trace prints them)
  • leaving it on in production logs

Syntax: bash -x s.sh · set -x … set +x · PS4='+ line $LINENO: '

OptionWhat it doesWhen to use it
bash -x s.shtrace whole runquick debug
set -x / set +xtrace a partfocus
PS4='+ $LINENO: 'line numberslong scripts
2> trace.logtrace to a filekeep output clean
bash -nsyntax onlybefore running

  1. Situation: Line numbers in the trace.

set -x · bash -x · PS4 in security

  1. Situation: Trace leaks secrets.

    bash -xc 'token=s3cr3t-abc; curl_cmd="curl -H Authorization:$token"' 2>&1 | head -2
    + token=s3cr3t-abc + curl_cmd='curl -H Authorization:s3cr3t-abc'

    Why this way: set -x prints values. Turn it off around secrets (set +x) and never keep traces of production runs that use credentials.

set -o · noclobber · vi · set -- · unset more options

🟡 Changes filesno sudo

set -o lists options; set -o noclobber (-C) makes > refuse to overwrite (use >|). set -o vi switches line editing to vi keys. set -- a b sets $1 $2. unset NAME removes a variable, unset -f NAME a function.

✓ Use it when
  • checking or changing options
  • protecting files from >
  • vi keys on the command line
  • removing variables and functions
✗ Don’t use it when
  • noclobber in scripts that are meant to overwrite

Undo and safety net

Options are per shell; a new shell starts clean.

  • Typed set -e in your terminal: the next failing command closes it; set +e now, or just open a new terminal.
  • Script stops “for no reason” with -e: run bash -x to see the last line; look for ((x++)), grep with no match, $(…) failing.
  • set -u breaks on optional variables: give them defaults: ${VAR:-}.
  • Trace too noisy: wrap only the suspicious part in set -x … set +x.
  • noclobber blocks a needed overwrite: >| or set +C.

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. bash -c 'set -u; echo $undefined_var'
    bash: line 1: undefined_var: unbound variable exit status: 127

    What it means: set -u: the variable was never set.

    Fix: Set it, fix the typo, or use ${VAR:-default}.

  2. bash -c 'set -C; echo a > f.txt; echo b > f.txt'
    bash: line 1: f.txt: cannot overwrite existing file exit status: 1

    What it means: noclobber: > will not overwrite.

    Fix: >| if you really mean it.

  3. set -o nosuchoption
    /home/riya/script.sh: line 1: set: nosuchoption: invalid option name exit status: 2

    What it means: Unknown option name.

    Fix: set -o lists valid names.

  4. bash -n missing_fi.sh
    missing_fi.sh: line 3: syntax error: unexpected end of file exit status: 2

    What it means: Syntax: an if without fi.

    Fix: Close every if/fi, case/esac, do/done.

Each option tried in small variations, so you know exactly when it fires and when it does not.

set -e: fires or not?

V1

Five commands, five results

for c in 'false' 'false || true' 'if false; then :; fi' '! false' 'false | true'; do
  bash -c "set -e; $c; echo survived" > /dev/null && r=continues || r=STOPS
  printf '%-24s %s\n' "$c" "$r"
done
false STOPS false || true continues if false; then :; fi continues ! false continues false | true continues

Only the plain false stops a script; conditions, || , ! and non-last pipe parts are exempt.

V2

Command substitution

bash -c 'set -e; x=$(false); echo "x set"'; echo "plain assignment: $?"
bash -c 'set -e; f(){ local y=$(false); echo "local hides it"; }; f'; echo "local: $?"
plain assignment: 1 local hides it local: 0

x=$(false) stops; local y=$(false) does not (local itself succeeds): a famous trap.

V3

Functions called in a condition

bash -c 'set -e; f(){ false; echo "after false inside f"; }; if f; then echo yes; fi'
after false inside f yes

Inside a function used as an if condition, set -e is switched off: the echo still runs.

set -u variations

V4

Which forms are allowed

bash -uc 'echo "[${A-}] [${A:-def}] [${#}]"'
bash -uc 'echo "[$A]"' 2>&1 | sed 's/.*: A/A/'
[] [def] [0] A: unbound variable

${A-} and ${A:-def} are fine; plain $A is the error.

V5

Empty is not unset

bash -uc 'A=""; echo "empty but set: [$A]"'
empty but set: []

set -u only complains about variables that were never set.

Tracing variations

V6

Trace only one part

bash -c 'a=1
set -x
b=$((a+1))
set +x
echo "b=$b"' 2>&1
+ b=2 + set +x b=2

set -x … set +x around the suspicious lines (set +x itself is also traced).

V7

Trace into a separate file

bash -c 'exec 5> trace.txt; BASH_XTRACEFD=5; set -x; echo normal output'
echo '--- trace.txt:'; cat trace.txt
normal output --- trace.txt: + echo normal output

BASH_XTRACEFD sends the trace to another file descriptor; normal output stays clean.

V8

Trace with time stamps

PS4='+ $(date +%S)s line $LINENO: ' bash -xc 'sleep 1
echo done' 2>&1 | sed -E 's/[0-9]{2}s/SSs/'
+ SSs line 1: sleep 1 + SSs line 2: echo done done

Anything in PS4 is expanded for each line: seconds, line numbers, function names.

Script it: strict-template.sh

A starting template for every new script: strict mode, a numbered trace when DEBUG=1, required and optional settings, and a clear failure message.

set -euo pipefail
[ "${DEBUG:-0}" = 1 ] && { PS4='+ line $LINENO: '; set -x; }
log=${LOG:-/var/log/syslog}
out=${OUT:?set OUT to an output file}

echo "readable logs: $count, writing summary to $out"
/home/riya/script.sh: line 4: OUT: set OUT to an output file

Run without OUT (it must refuse), the safe way to see the guard.

Puzzle answer Remember the question from the story? Open to check your guess.

Under set -e, ((count++)) with count=0 evaluates to the old value 0, and (( )) returns status 1 when its result is 0. set -e treats that as a failure and exits silently with status 1, right after the first file. Use count=$((count + 1)) or ((++count)).

Quick revision

Lesson 12.6 in one screen

  • set -euo pipefail on line 2 of every script (not in the shebang).
  • -e exits on failure except in if/while conditions, before && / ||, after !, non-final pipe parts; beware ((x++)) at 0.
  • -u: unset variable = error; use ${V:-default} for optional and ${V:?msg} for required.
  • pipefail: any failing part fails the pipe; ${PIPESTATUS[@]} shows each.
  • bash -x / set -x … set +x, PS4 with $LINENO; bash -n for syntax; never trace secrets.
  • set -o lists; - on, + off; noclobber and >|; set -o vi; set --; unset / unset -f.

Interview and viva questions

What does set -e do in bash?

It makes the script exit immediately when a command fails (non-zero status), except in conditions and && / || lists.

What is set -euo pipefail?

Bash “strict mode”: exit on errors (-e), on unset variables (-u), and on failures anywhere in a pipeline (pipefail).

How do I debug a bash script?

Run bash -x script.sh (or set -x inside it) to print each command as it is executed; bash -n checks syntax.

How do I show line numbers in bash -x?

Set PS4='+ $LINENO: ' before running with -x.

Why does my script exit at ((i++))?

Under set -e, ((i++)) returns status 1 when i was 0. Use i=$((i+1)) or ((++i)).

What does set -o noclobber do?

It prevents > from overwriting existing files; >| forces the overwrite.

How do I unset a function?

unset -f NAME.

Practice lab: harden a script

Build the lab: job.sh has four weaknesses. Fix them, then run the checker.
