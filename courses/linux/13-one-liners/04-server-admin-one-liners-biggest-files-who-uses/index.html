The problem

Monday, 9:05 a.m. Three tickets land at once. “Disk 97% full on web01.” “The app won’t start: port 8080 already in use.” “Server feels slow, something is eating memory.” Riya has no fancy dashboards on this box, just SSH. Each ticket is answered by one or two classic admin one-liners: du and find for the biggest files, lsof, fuser and ss for who holds a port, ps --sort and top for CPU and memory hogs, df -i and lsof +L1 for the two disk-full traps that fool beginners. This lesson collects them, runs each on a real machine and explains every column.

By the end of this page you will be able to:
  • find what fills a disk with df, du -sh | sort -h and find -size, including inode exhaustion and deleted-but-open files
  • find which process uses a port or a file with lsof, fuser and ss, and stop it safely
  • rank processes by CPU and memory with ps --sort, top -b and /proc, and read RSS, %MEM and load correctly
  • check who is logged in and what changed recently, and combine everything into a quick health check

2 Definition

The admin one-liner toolkit

Formal definition (write this in exams)

Server admin one-liners are short command combinations for the most frequent operations questions: what fills a disk (df, du, find), which process holds a port or file (ss, lsof, fuser), which processes use the most CPU or memory (ps --sort, top -b), and who is logged in (who, w, last).

In simple words

Measure, rank biggest first, find the owner, then act.

Admin one-liners at four depths

Pick your depth. Completely new? Start at Very basic and climb one step at a time.

Very basic No jargon: a building manager

Each complaint has a meter to read and an owner to find.

Basic What you will type

  • df -h: how full each disk is.
  • du -sh * | sort -rh | head: biggest folders here.
  • sudo lsof -i :8080: who uses port 8080.
  • ps aux --sort=-%mem | head: memory hogs.

Intermediate Reading the numbers right

  • df asks the file system how many blocks are used; du adds up the files it can see. They differ when files are deleted but still open, or hidden under a mount point.
  • df -i: inodes. Millions of tiny files can fill the inode table while blocks are free (“No space left on device” at 40%).
  • du -x stays on one file system (does not count /proc or other disks).
  • RSS = memory really in RAM; VSZ = address space (much bigger, mostly not used). %CPU in ps is an average over the process lifetime; top shows the current rate.
  • Ports below 1024 and other users’ processes need sudo to see the PID.

Advanced Behind the screen: inodes, open files and sockets

  • Deleting a file removes its name; the blocks are freed only when the last name is gone and no process has it open (link count 0 + open count 0). A log still written by a running program keeps its space: lsof +L1 lists such files; restart the program or truncate via /proc/PID/fd/N.
  • ext4 reserves 5% of blocks for root (tune2fs -m), so users see “full” before df says 100%.
  • lsof and fuser read /proc/*/fd; ss reads sockets from the kernel via netlink (/proc/net/tcp is the older text view).
  • A socket in TIME_WAIT after a restart is not a process; SO_REUSEADDR lets the server bind again.
  • Memory: the kernel uses free RAM as page cache; free’s “available” column is the real headroom. The OOM killer picks by oom_score (Lesson 11.3: exit 137).

Did you know? The most common cause of “I deleted the log but the disk is still full” is a log file deleted by hand while the web server still writes to it. The fix is not deleting more files: it is systemctl reload nginx (so it reopens a new log) or emptying the file with : > access.log instead of deleting it.

Exam tip: “How do you find which process is using port 80?” → sudo ss -ltnp | grep ':80 ' (or sudo lsof -i :80, sudo fuser 80/tcp, netstat -ltnp on old systems).

Quick check df says 95% used, du of everything says much less. Name one likely cause.
Answer: Files deleted while still open by a process (check sudo lsof +L1); or files hidden under a mount point.
Common mistake
✗rm a huge log that a service is writing
✓: > /var/log/app/huge.log (truncate) · or rotate with logrotate and reload the service

rm only removes the name; the process keeps the space until it closes the file (real run: df unchanged, lsof +L1 shows it).

Common mistake
✗kill -9 whatever ss shows on the port
✓check what it is (ps -fp PID, systemctl status), stop it properly (systemctl stop / kill), or change your app’s port

The “stray” process may be the real production service.

df -h · du -sh * | sort -rh · du -xh --max-depth=1 · find -size what fills the disk

🟢 Read-onlyno sudo

Start with df -h to see which file system is full. Then drill down: du -xh --max-depth=1 DIR | sort -rh | head, and repeat on the biggest folder. Finally list big files with find DIR -xdev -type f -size +100M. sort -h understands K, M, G.

✓ Use it when
  • disk-full tickets
  • cleaning before backups
  • capacity checks
✗ Don’t use it when
  • du on / without -x (it walks /proc and other disks)
  • deleting before you know what it is

Syntax: df -h · du -xh --max-depth=1 /var | sort -rh | head · find / -xdev -size +500M

lsof +L1 · df -i · : > file the two disk-full traps

🟡 Changes filesno sudo

If a deleted file is still open, its space is not freed: lsof +L1 lists open files with link count 0. Fix: restart/reload the process, or truncate it through /proc/PID/fd/N. If df -i shows 100% inodes, the problem is the number of files; find folders with huge counts.

✓ Use it when
  • disk still full after rm
  • df and du disagree
  • “No space” with free blocks
✗ Don’t use it when
  • rm on logs a service is writing

Syntax: sudo lsof +L1 · df -i · : > /proc/PID/fd/N

ss -ltnp · lsof -i :PORT · fuser PORT/tcp · fuser -vm who uses a port or file

🟢 Read-onlyno sudo

✓ Use it when
  • “address already in use”
  • which service listens where
  • cannot unmount: device busy
✗ Don’t use it when

ps -eo … --sort=-%cpu / -rss · top -b -n1 · free -h CPU and memory hogs

Undo and safety net

Looking is harmless; deleting files and killing processes is not.

  • Deleted the wrong big file: restore from backup; next time move it to a holding folder first.
  • Killed the wrong process on a port: systemctl start SERVICE; check systemctl status.
  • Truncated a log by mistake: the old lines are gone; rotated copies (access.log.1, .gz) may still have them.
  • Habit: look (df/du/ss/ps) → identify (ps -fp, systemctl status) → act (rotate, stop, archive).

Error messages decoded

Errors students see most. Each was really produced on our build machine, with its exit status.

  1. du -sh /root
    du: cannot read directory '/root': Permission denied 4.0K /root exit status: 1

    What it means: No permission to read another user’s folder.

    Fix: sudo du -sh /root.

  2. lsof -i :1
    exit status: 1

    What it means: Nothing listens on port 1 (lsof exits 1).

    Fix: Check the port number.

  3. python3 -m http.server 8099 --bind 127.0.0.1 2>&1 | tail -1; exit ${PIPESTATUS[0]}
    OSError: [Errno 98] Address already in use

    What it means: The port is taken.

    Fix: Find the owner with lsof -i :8099.

  4. ss -ltnp
    /home/riya/script.sh: line 1: ss: command not found exit status: 127

    What it means: ss is not installed on this machine (package iproute2).

    Fix: sudo apt install iproute2, or use lsof -i.

  5. kill 1
    /home/riya/script.sh: line 1: kill: (1) - Operation not permitted exit status: 1

    What it means: PID 1 is systemd, not yours.

    Fix: Use the PID from lsof/ss.

6 Real-world use

Admin one-liners at work

1. Disk-full incidents

The classic: /var full at night because of logs, core dumps or forgotten backups; du drill-down finds it in minutes.

Alert→df → du → find→archive/rotate

2. “Deleted but still full”

A log removed by hand while nginx writes it; lsof +L1 shows it, a reload frees the space.

rm→lsof +L1→reload

3. Failed deployments

A new release cannot start because the old one still holds the port; ss/lsof shows the old PID.

Deploy fails→ss -ltnp→stop old

4. Slow servers

ps --sort finds the runaway report or the leaking worker; nice or restart fixes it (Lesson 11.5).

Slow→ps --sort→fix

5. Inode exhaustion

Mail queues, PHP sessions and caches create millions of tiny files; df -i reveals it.

No space?→df -i→clean

A quick server health check: disk and inode use with a warning threshold, memory available, load versus CPUs, the top CPU and memory processes, and whether given ports are in use.

warn=${WARN:-85}; ports=("${@:-8099 22}")
read -r -a ports <<< "${ports[*]}"
printf '%-8s %s\n' DISK "$(df -h --output=pcent,avail ~ | tail -1 | awk '{print $1" used, "$2" free"}')"
d=$(df --output=pcent ~ | tail -1 | tr -d ' %'); i=$(df --output=ipcent ~ | tail -1 | tr -d ' %')
[ "$d" -ge "$warn" ] && echo "  WARNING: disk above $warn%"; [ "$i" -ge "$warn" ] && echo "  WARNING: inodes above $warn%"
printf '%-8s %s MB available\n' MEMORY "$(free -m | awk 'NR==2{print $7}')"
printf '%-8s %s (CPUs: %s)\n' LOAD "$(cut -d' ' -f1-3 /proc/loadavg)" "$(nproc)"
printf '%-8s %s\n' TOP_CPU "$(ps -u "$USER" -o comm= --sort=-%cpu | head -1)"
printf '%-8s %s\n' TOP_MEM "$(ps -u "$USER" -o comm= --sort=-rss | head -1)"
for p in "${ports[@]}"; do printf '%-8s %s\n' "PORT $p" "$(lsof -t -i :"$p" > /dev/null 2>&1 && echo "in use by $(ps -o comm= -p "$(lsof -t -i :"$p" | head -1)")" || echo free)"; done

Puzzle answer Remember the question from the story? Open to check your guess.

1. The 20 GB log was deleted while a process still had it open: the name is gone, the blocks are not. sudo lsof +L1 shows it; reload or restart that service (or truncate it via /proc/PID/fd/N). 2. Quick revision

Lesson 13.4 in one screen

  • Disk: df -h (which), du -xh -d1 | sort -rh (where), find -size / -mtime (which files); df -i for inodes.
  • df ≠ du: deleted-but-open files (lsof +L1; reload or : > /proc/PID/fd/N) or files under a mount point.
  • Ports: sudo ss -ltnp | grep :P, sudo lsof -i :P (-t PID only), fuser P/tcp; check what it is before stopping.
  • Files busy: fuser -v FILE, fuser -vm MOUNT, lsof FILE / +D DIR.
  • Hogs: ps -eo pid,%cpu,%mem,rss,cmd --sort=-%cpu or -rss | head; top -b -n1; free -h “available”; load vs nproc.
  • People: who, w, last. Habit: look → identify → act; truncate logs instead of rm.

Interview and viva questions

How do I find what is using disk space in Linux?

df -h for the disk, then du -xh --max-depth=1 DIR | sort -rh | head, repeat on the biggest folder; find -size +100M for big files.

Why is my disk still full after deleting files?

A process still has the deleted file open; check sudo lsof +L1 and restart or reload it.

Why do I get "No space left on device" when df shows free space?

You ran out of inodes (df -i) or hit the reserved-blocks limit.

How do I find which process uses a port?

sudo ss -ltnp | grep :PORT, or sudo lsof -i :PORT, or sudo fuser PORT/tcp.

How do I find the top memory-consuming processes?

ps -eo pid,rss,%mem,cmd --sort=-rss | head, or top sorted by %MEM.

What is the difference between RSS and VSZ?

RSS is memory actually in RAM; VSZ is the whole address space, mostly unused.

Why is ss missing?

It is in the iproute2 package; install it or use lsof -i / netstat.

: > /proc/PID/fd/N.
What is an inode?
The record of one file; a fixed number per file system.
RSS vs VSZ?
RAM used vs address space.
How to see what is listening?
ss -ltnp (or netstat -ltnp).
What does fuser -vm /mnt do?
Lists processes using a mount point.
Where this appears in certification exams
  • RHCSA (EX200): Identify CPU/memory intensive processes; manage disks.
  • LFCS: Monitor disk, processes and network services.
  • CompTIA Linux+: df, du, lsof, ss, ps.
