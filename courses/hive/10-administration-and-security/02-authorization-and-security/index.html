2 Definition

Authentication, authorization and Hive security

Formal definition (write this in exams)

Authentication establishes the identity of a client connecting to HiveServer2 (Kerberos, LDAP, PAM, custom providers, or none). Authorization decides which operations that identity may perform. Hive’s SQL-standard based authorization (SQLStdHiveAuthorizerFactory) enforces SELECT, INSERT, UPDATE and DELETE privileges and object ownership on databases, tables and views, managed with GRANT, REVOKE and roles, and disables risky commands (dfs, ADD JAR, TRANSFORM, changing security settings) for non-admin users. Apache Ranger replaces it in most enterprise platforms with centrally managed policies, column masking, row-level filtering and audit logs, while Kerberos secures identities across Hadoop services.

In simple words

Authentication answers “who are you?”, authorization answers “what are you allowed to do?”. Hive can enforce table permissions with GRANT and REVOKE, or with Apache Ranger policies, but both only work if users are properly authenticated, usually with Kerberos or LDAP.

Words you’ll meet in this lesson

PrincipalA user, group or role that receives privileges.
RoleA named set of privileges; public and admin are built in.

OwnershipCreator of an object; needed e.g. to create tables in a database.
doAsRun file access as the end user (true) or the Hive service user (false).

Hive security at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A building with guards

  • Authentication is the ID card at the entrance: proving who you are.
  • Authorization is which rooms your card opens: what you may read or change.
  • Audit is the visitor log: who entered which room, and when.

Intermediate The options in Hive

  • Authentication (HiveServer2): hive.server2.authentication = NONE, LDAP, KERBEROS, PAM, CUSTOM; plus TLS for the connection.
  • Authorization: SQL-standard based (GRANT/REVOKE, roles public and admin), storage-based (file permissions), or Apache Ranger (central policies, masking, row filters, audit).
  • doAs: with hive.server2.enable.doAs=false queries access files as the Hive service user, which is required for SQL-standard and Ranger authorization to be meaningful.

Advanced What the lab showed

  • Listing hive in hive.users.in.admin.role on HiveServer2 was not enough: “hive doesn’t belong to role admin” until the metastore had the setting too.
  • Analysts were blocked from dfs, ADD JAR, TRANSFORM, CREATE TABLE and from switching authorization off; a permanent UDF still worked.
  • UPDATE on an ACID table asked for the DELETE privilege (Hive 4 splits updates into delete + insert). With authentication NONE, anyone typing -n hive became admin.

Exam tip: “How do you secure Hive?” Authenticate users at HiveServer2 (Kerberos or LDAP, with TLS), authorize with SQL-standard GRANT/REVOKE and roles or with Ranger policies (column masking, row filters, audit), set doAs=false so access goes through the authorizer, and expose sensitive data through views or masks.

3 Types and ways to use it

SQL-standard authorization commands

CommandWhoPurpose
SET ROLE ADMIN;Members of adminActivate admin privileges for the session
CREATE ROLE r; DROP ROLE r; SHOW ROLES;AdminManage roles
GRANT ROLE r TO USER u; REVOKE ROLE r FROM USER u;AdminMembership
GRANT SELECT, INSERT ON TABLE t TO ROLE r [WITH GRANT OPTION];Owner / adminPrivileges on tables and views
REVOKE SELECT ON TABLE t FROM ROLE r;Grantor / adminRemove privileges
SHOW CURRENT ROLES; SHOW ROLE GRANT USER u;Anyone (own) / adminCheck membership
SHOW GRANT [USER u | ROLE r] ON TABLE t;Anyone (own) / adminCheck privileges

In SQL-standard mode there are no column-level grants. Hide columns with views (as here) or use Ranger’s column policies and masking. And because Hive checks privileges on the view, analysts can read a view without any privilege on its base table.

In a real cluster these lines go into hive-site.xml.

  2. Step 2 · Surprise: the admin role lives in the metastore

    SET hive.security.authorization.enabled;
SHOW CURRENT ROLES;
SET ROLE ADMIN;

-- after adding -Dhive.users.in.admin.role=hive to the METASTORE too and restarting it:
SET ROLE ADMIN;
SHOW CURRENT ROLES;
    +-------------------------------------------+ | set | +-------------------------------------------+ | hive.security.authorization.enabled=true | +-------------------------------------------+ +---------+ | role | +---------+ | public | +---------+ FAILED: Execution Error, return code 40000 from org.apache.hadoop.hive.ql.ddl.DDLTask. hive doesn't belong to role admin +--------+ | role | +--------+ | admin | +--------+
    Roles and memberships are stored in the metastore (ROLES, ROLE_MAP). The metastore adds the users of hive.users.in.admin.role to the admin role from its own configuration; with the setting only on HiveServer2, ROLE_MAP stayed empty and SET ROLE ADMIN failed. Even admins start every session in the public role and must SET ROLE ADMIN explicitly.

  3. Step 3 · Deny by default

    SELECT COUNT(*) FROM customers;
    FAILED: HiveAccessControlException Permission denied: Principal [name=riya, type=USER] does not have following privileges for operation QUERY [[SELECT] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.customers]]
    With authorization on, a new user has only the public role and no privileges: the query is refused at compile time, naming the principal, the missing privilege and the object (hive.tiffingo.customers: catalog, database, table).

    Kabir could insert and check his row. His UPDATE was refused for missing DELETE, and still refused after an UPDATE grant. Hive 4 executes ACID updates as delete + insert (hive.split.update=true in our lab), and authorization checks those operations. Grant writers INSERT, UPDATE and DELETE together on tables they maintain.

  8. Step 8 · Why authentication matters

    SET hive.server2.authentication;              -- NONE in our lab
SET ROLE ADMIN;
SELECT current_user() AS who, COUNT(*) AS customers FROM customers;

-- clean-up: REVOKE ROLE analyst FROM USER riya;  then riya queries the view again
    hive.server2.authentication=NONE +-------+------------+ | who | customers | +-------+------------+ | hive | 2000 | +-------+------------+ +---------+---------------+-------------+----------+ | role | grant_option | grant_time | grantor | +---------+---------------+-------------+----------+ | public | false | 0 | | +---------+---------------+-------------+----------+ FAILED: HiveAccessControlException Permission denied: Principal [name=riya, type=USER] does not have following privileges for operation QUERY [[SELECT] on Object [type=TABLE_OR_VIEW, name=hive.tiffingo.v_customers_safe]]
    With hive.server2.authentication=NONE, HiveServer2 believes any user name a client sends. Anyone who types -n hive becomes admin and reads all 2,000 customers. Every grant above is only as strong as authentication: production clusters use Kerberos or LDAP (with TLS). Revoking the role took effect at once: Riya’s next query on the view was denied.

6 Real-world use

Hive security at work

1. Protecting personal data

Names, phones and addresses are hidden behind views or Ranger masks to meet privacy laws such as India’s DPDP Act and GDPR.

PII columns→view / mask→Compliant access

2. Team-based access

Analyst, engineer and data-science roles map to directory groups, so joining a team grants the right access automatically.

LDAP group→role→Privileges

3. Audit trails

Ranger audit logs record every allowed and denied access, used in security investigations and compliance reports.

Access→audit log→Evidence

4. Multi-tenant platforms

Different business units share one cluster but only see their own databases, enforced by policies.

Shared cluster→policies→Isolated tenants

5. Safer operations

Disabling dfs, ADD JAR and TRANSFORM for normal users prevents accidental or malicious use of cluster resources.

User→restricted→Stable cluster

7 Run the code

Run the code: model the authorizer

These programs model how SQL-standard authorization decides, using the grants from the lab. Press Run, then try the challenges.

# A tiny SQL-standard authorizer: roles, grants, and a check at "compile time"
grants = {("ROLE", "analyst"): {("v_customers_safe", "SELECT"), ("orders", "SELECT")},
          ("USER", "kabir"): {("orders_tx", "SELECT"), ("orders_tx", "INSERT")}}
roles = {"riya": {"public", "analyst"}, "kabir": {"public"}}

def allowed(user, obj, priv):
    principals = [("USER", user)] + [("ROLE", r) for r in roles.get(user, {"public"})]
    return any((obj, priv) in grants.get(p, set()) for p in principals)

for user, obj, priv in [("riya", "v_customers_safe", "SELECT"), ("riya", "customers", "SELECT"),
                        ("kabir", "orders_tx", "INSERT"), ("kabir", "orders_tx", "DELETE")]:
    print(f"{user:6} {priv:6} {obj:17}", "OK" if allowed(user, obj, priv) else "Permission denied")
riya SELECT v_customers_safe OK riya SELECT customers Permission denied kabir INSERT orders_tx OK kabir DELETE orders_tx Permission denied
  • principals = [("USER", user)] + [("ROLE", r) for r in roles.get(user, {"public"})]A user’s effective privileges are their own grants plus those of every active role.
  • return any((obj, priv) in grants.get(p, set()) for p in principals)One matching grant is enough; otherwise Hive raises HiveAccessControlException before running anything.

9 Quiz and revision

Check yourself

Quick revision

Lesson 10.2 in one screen

  • Authentication (who): hive.server2.authentication NONE/LDAP/KERBEROS/PAM/CUSTOM + TLS. Authorization (what): SQL standard, storage-based, Ranger.
  • SQL standard: hive.security.authorization.enabled=true, SQLStdHiveAuthorizerFactory, SessionStateUserAuthenticator, doAs=false.
  • Admins: hive.users.in.admin.role must be set on the metastore; then SET ROLE ADMIN per session.
  • Roles: CREATE ROLE, GRANT ROLE r TO USER u; privileges: GRANT SELECT|INSERT|UPDATE|DELETE ON TABLE t TO ROLE r; check with SHOW GRANT.
  • Deny by default: HiveAccessControlException at compile time. View privileges suffice for views. No column grants: use views or Ranger masks.
  • Blocked for users: dfs, ADD JAR, TRANSFORM, security SETs, CREATE TABLE without database ownership.
  • Hive 4 UPDATE needs DELETE (+ INSERT) privileges. Grants live in TBL_PRIVS / ROLE_MAP.
  • Ranger: central policies, column masking, row filters, tag policies, audit. Kerberos/LDAP first, or nothing is secure.

Interview and viva questions

Do Spark and Trino respect Hive’s SQL-standard grants?

No. Those grants are enforced inside HiveServer2. Spark reading the files or the metastore directly bypasses them. Platforms with several engines use Ranger plugins (or a cloud permission layer) and restrict direct file access.

What does doAs do?

With doAs=true, HiveServer2 accesses files as the end user, so HDFS permissions decide; with doAs=false, it uses the Hive service user and the authorizer decides. SQL-standard authorization and Ranger expect doAs=false, with the warehouse readable only by the Hive user.

How does Kerberos login work for Beeline?

The user runs kinit to get a ticket, then connects with a URL containing the server principal, e.g. jdbc:hive2://hs2.example.com:10000/default;principal=hive/_HOST@EXAMPLE.COM. No user name or password is typed; the ticket proves identity.

Can I mask a column without Ranger?

With SQL-standard authorization, create a view that applies a function (e.g. mask(phone) or concat('XXXXXX', substr(phone, -4))) and grant the view instead of the table. Ranger does this centrally without extra views.

What about encryption?

Use TLS for client connections to HiveServer2 (hive.server2.use.SSL), HDFS transparent encryption zones or object-store encryption for data at rest, and secure the metastore database connection.

Real-world scenario questions (asked in company interviews)

Security questions test whether you separate authentication from authorization and know the enterprise tools.

Any company · HiveFresher

“How do you give a user access to a table?”

Explain Hive’s GRANT model.

The interviewer is checking: do you know roles and privileges?

Show a strong answer

With SQL-standard authorization, an admin creates a role, grants privileges such as SELECT or INSERT on tables or views to the role, and grants the role to users. Users check their access with SHOW CURRENT ROLES and SHOW GRANT. In enterprise platforms the same is done with Ranger policies.

Avoid: Answering only with HDFS chmod.

Data platformMid-level

Hide personal columns

Analysts must analyse customers without seeing names or phone numbers.

The interviewer is checking: can you combine views and grants, or masking?

Show a strong answer
  1. Create a view without (or masking) the personal columns.
  2. Grant SELECT on the view to the analyst role; no grant on the base table.
  3. With Ranger: a column masking policy instead of extra views; audit access.

Avoid: “Ask analysts not to select those columns.”

Data engineeringMid-level

UPDATE permission denied

A loader with INSERT and UPDATE privileges gets “does not have [DELETE]” on an UPDATE.

The interviewer is checking: do you know how Hive executes updates?

Show a strong answer
  • Hive 4 runs ACID updates as delete + insert; authorization checks those operations.
  • Grant DELETE (and INSERT) as well to the loader role.
  • Review the privilege set for all writers.

Avoid: Making the loader an admin.

ArchitectureSenior

Securing a shared data lake

Hive, Spark and Trino share one metastore; 500 users; personal data. Design security.

The interviewer is checking: can you design end-to-end security?

Show a strong answer
  • Kerberos (or LDAP + TLS for BI) everywhere; doAs=false; warehouse files readable only by service users.
  • Ranger policies for Hive, HDFS and Trino: masking, row filters, tag-based PII policies, audit.
  • Roles from directory groups; regular access reviews; encryption in transit and at rest.

Avoid: Relying on SQL-standard grants while Spark reads files directly.
