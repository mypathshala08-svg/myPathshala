MERGE and slowly changing dimensions

Every night TiffinGo’s app database sends changed customers: upgrades, moves, closed accounts and sign-ups. MERGE applies them to a Hive ACID table in one statement and one transaction. When finance also wants history, the same statement can maintain a slowly changing dimension type 2. 2 Definition

MERGE and slowly changing dimensions

Formal definition (write this in exams)

MERGE is a DML statement that synchronises a target transactional table with a source relation using a join condition. For each source row that matches a target row, the first applicable WHEN MATCHED clause updates or deletes the target row; for each source row without a match, a WHEN NOT MATCHED clause inserts a new row. The whole statement executes as one transaction. A slowly changing dimension (SCD) is a dimension table whose attributes change over time: type 1 overwrites old values, type 2 keeps full history by adding a new row per change with validity dates and a current flag, and type 3 keeps a limited history in additional columns.

In simple words

MERGE compares new data with a table by key and, in one statement, updates the rows that changed, deletes the ones marked for removal and inserts the new ones. SCD is the name for the ways of keeping (or not keeping) old values of things like a customer’s city or plan.

MERGE and SCD at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Updating an address book

  • You get a list of changes. For each person: if they are already in your book, change their entry; if not, add them; if they asked to be removed, cross them out.
  • MERGE does exactly this for a whole table in one go.
  • Sometimes you must not lose the old entry (“where did she live last year?”). Then you close the old entry with an end date and add a new one: that is SCD type 2.

Intermediate The MERGE statement

  • MERGE INTO target t USING source s ON t.key = s.key, then up to three clauses: WHEN MATCHED [AND cond] THEN UPDATE SET …, WHEN MATCHED [AND cond] THEN DELETE, WHEN NOT MATCHED [AND cond] THEN INSERT VALUES (…).
  • The target must be a full ACID table (7.1); the source can be any table, view or subquery.
  • SCD type 1: overwrite the old value (no history). Type 2: keep every version with eff_from, eff_to, is_current. Type 3: keep the previous value in an extra column.
  • Add a change condition (t.plan <> s.plan OR …) so unchanged rows are not rewritten.

Advanced Hive specifics we verified

  • Cardinality check: if two source rows match one target row, Hive fails the MERGE (“Cardinality Violation in Merge statement”, hive.merge.cardinality.check=true). The target stayed unchanged. De-duplicate the source first.
  • One MERGE wrote two delete_deltas and two deltas under one write id: atomic. Untouched rows kept their old ROW__ID.
  • SCD2 in one MERGE: a changed row must both close the old version (MATCHED) and insert a new one (NOT MATCHED). The trick: feed changed rows twice, once with the real key and once with a NULL join key, which can never match.
  • Re-running the same SCD2 MERGE changed nothing (9 rows, 7 current): it is idempotent, so a failed night can simply be re-run.

Exam tip: “What is SCD type 2 and how do you implement it in Hive?” Explain the validity columns, then the MERGE: match current rows on the key and close them when attributes differ; insert new versions using a NULL join key for changed rows plus the real key for new rows. Mention that the target must be an ACID table and that duplicate source keys cause a cardinality violation.

RuleWhy
Target must be full ACID (ORC, transactional=true)MERGE writes deltas and delete deltas

Comparisons with <> ignore NULLs: if the old city is NULL and the new one is Pune, t.city <> s.city is NULL, not true, and the change is missed. In real jobs compare with NOT (t.city <=> s.city) (null-safe equality) or compare a hash of all columns.

WHEN NOT MATCHED THEN INSERT VALUES (s.customer_id, s.name, s.city, s.plan);

INSERT INTO stg2 VALUES (2,'Ananya Iyer','Mumbai','Gold'), (3,'Arjun Nair','Pune','Gold'),
  (4,'Gurpreet Das','Bengaluru','Basic'), (7,'Kavya Reddy','Hyderabad','Silver');
    -- 6 rows, all current, valid from 2026-10-01 to 9999-12-31
    Every version has a validity range. “9999-12-31” is a common convention for “still valid”, so a simple BETWEEN works in joins. The staging table holds the same changes as before, without the delete.

  6. Step 6 · The SCD2 MERGE with a NULL join key

    MERGE INTO dim_customer_hist t
USING (
  SELECT s.customer_id AS join_key, s.customer_id, s.name, s.city, s.plan FROM stg2 s
  UNION ALL
  SELECT CAST(NULL AS INT) AS join_key, s.customer_id, s.name, s.city, s.plan
  FROM stg2 s JOIN dim_customer_hist d ON s.customer_id = d.customer_id AND d.is_current
  WHERE s.city <> d.city OR s.plan <> d.plan
) u
ON t.customer_id = u.join_key AND t.is_current
WHEN MATCHED AND (t.city <> u.city OR t.plan <> u.plan)
  THEN UPDATE SET eff_to = DATE '2026-10-26', is_current = false
WHEN NOT MATCHED THEN INSERT VALUES (u.customer_id, u.name, u.city, u.plan,
  DATE '2026-10-27', DATE '9999-12-31', true);
SELECT * FROM dim_customer_hist ORDER BY customer_id, eff_from;

    -- run exactly the same MERGE again
SELECT COUNT(*) AS rows_after_rerun, SUM(IF(is_current, 1, 0)) AS current_rows
FROM dim_customer_hist;

    Still 9 rows with 7 current. The current rows now equal the staging values, so the change condition is false everywhere and the NULL-key branch selects nothing. An idempotent job can be safely re-run after a failure, which matters for nightly pipelines.

  8. Step 8 · Why type 2: the plan at order time

    -- point in time: the version valid on the order date
SELECT h.plan AS plan_then, COUNT(*) AS orders FROM orders o
JOIN dim_customer_hist h ON o.customer_id = h.customer_id
 AND o.order_date BETWEEN h.eff_from AND h.eff_to
WHERE o.customer_id = 2 GROUP BY h.plan;

-- current version only
SELECT h.plan AS plan_now, COUNT(*) AS orders FROM orders o
JOIN dim_customer_hist h ON o.customer_id = h.customer_id AND h.is_current
WHERE o.customer_id = 2 GROUP BY h.plan;

5 See it happen

How MERGE decides what to do with each row

Left: real Beeline output. Right: how MERGE routes each row.

Upserts, cardinality and SCD2 5 steps
What you see
  1. A single MERGE with DELETE, UPDATE and INSERT clauses.
  2. The result: two updates, one insert, one delete, one row untouched.
  3. Duplicate keys in the source make the MERGE fail; nothing changes.
  4. SCD2 keeps the old versions with closed date ranges.
  5. A point-in-time join splits Ananya’s orders by the plan she had then.
Behind the screen
  1. Hive joins source and target on the key, then routes each row to a clause.
  2. The first clause whose condition is true decides the action; all actions commit together.
  3. A target row may be changed by only one source row.
  4. A NULL join key forces the second copy of a changed row into the INSERT branch.
  5. Each order is matched to the version whose eff_from–eff_to range contains its date.

6 Real-world use

MERGE and SCD at work

1. Syncing OLTP databases

Change data from MySQL, PostgreSQL or Oracle is merged into the warehouse every night or hour, keeping Hive tables close to the source.

Change events→MERGE→Synced table

2. Customer and product history

Banks, insurers and retailers keep SCD2 dimensions for customers, branches and products so that reports use the attributes valid at transaction time.

Attribute change→close + insert→Point-in-time reports

3. De-duplicated event loads

When a source re-sends events, a MERGE with only WHEN NOT MATCHED THEN INSERT adds new event ids and ignores repeats.

Re-sent events→NOT MATCHED → INSERT→No duplicates

4. Audits and regulators

Auditors ask what a customer’s risk category or address was on a given date; SCD2 answers without restoring old backups.

Question about the past→BETWEEN eff dates→Answer

5. Closed accounts

Instead of deleting closed accounts, many teams MERGE an is_deleted flag, so history and joins stay complete.

op = D→UPDATE flag→History kept

# MERGE in plain Python: route each source row to a clause
target = {1: ("Bengaluru", "Silver"), 2: ("Mumbai", "Basic"), 3: ("Mumbai", "Gold"),
          4: ("Bengaluru", "Basic"), 5: ("Bengaluru", "Basic"), 6: ("Pune", "Basic")}
source = [(2, "Mumbai", "Gold", "U"), (3, "Pune", "Gold", "U"), (4, "Bengaluru", "Basic", "U"),
          (6, None, None, "D"), (7, "Hyderabad", "Silver", "I")]

for cid, city, plan, op in source:
    if cid in target:                                   # WHEN MATCHED
        if op == "D":
            del target[cid]; print(cid, "DELETE")
        elif target[cid] != (city, plan):              # AND changed
            target[cid] = (city, plan); print(cid, "UPDATE")
        else:
            print(cid, "no change")
    else:                                               # WHEN NOT MATCHED
        target[cid] = (city, plan); print(cid, "INSERT")
print(target)

Quick revision

Lesson 7.2 in one screen

  • MERGE INTO t USING s ON key WHEN MATCHED [AND c] THEN UPDATE SET … | DELETE WHEN NOT MATCHED [AND c] THEN INSERT VALUES (…).
  • Target = full ACID table; source = anything. One statement = one write id = one transaction.
  • First applicable clause wins: put DELETE (op = 'D') before UPDATE.
  • Add a change condition to UPDATE; use null-safe <=> or hashes for NULLs.
  • Cardinality violation: one target row matched by two source rows → whole MERGE fails, nothing applied. De-duplicate with ROW_NUMBER.
  • SCD1 overwrite · SCD2 eff_from / eff_to / is_current · SCD3 previous-value column.
  • SCD2 MERGE: source = all rows with real key ∪ changed rows with NULL key; match on key AND is_current; close on MATCHED, insert on NOT MATCHED.
  • Idempotent: re-run gave 9 rows, 7 current. Check one current row per key.
  • Point-in-time join: o.date BETWEEN h.eff_from AND h.eff_to (14 Basic + 5 Gold vs 19 “Gold”).

Interview and viva questions

Can I MERGE into an Iceberg table?

Yes. Hive 4 supports MERGE on Iceberg tables with the same syntax, writing Iceberg delete files and data files instead of Hive deltas (Lesson 7.3). This is useful when Spark or Trino also read the table.

Is MERGE faster than a separate UPDATE, DELETE and INSERT?

Usually yes: it reads the source and target once, and it is one transaction instead of three, so readers never see a half-applied change. The cost is a join between source and target, so filter the target (partitions, is_current) in the ON clause.

How do I choose eff_from for a change?

Use the time the change happened in the source system if you have it (from CDC), otherwise the load date. Keep the convention consistent, and make eff_to the day before the next version’s eff_from (or use half-open ranges, eff_from ≤ date < eff_to) so versions never overlap.

Should every dimension be SCD2?

No. Keep history only for attributes that matter for analysis (plan, city, segment). Fast-changing or irrelevant attributes (last login time) belong in a separate table or SCD1, otherwise the dimension grows a new version for every small change.

What does MERGE do with rows in the target that are not in the source?

Nothing. Hive’s MERGE has no WHEN NOT MATCHED BY SOURCE clause. To delete target rows that disappeared from a full extract, add an explicit delete marker to the source or run a separate DELETE … WHERE key NOT IN (…).

Real-world scenario questions (asked in company interviews)

MERGE and SCD questions are standard for data engineering roles, often as a whiteboard exercise.

Any company · SQLFresher

“What is an upsert?”

Explain upsert and how to do it in Hive.

The interviewer is checking: do you know MERGE and its requirement?

Show a strong answer

Update the row if its key exists, insert it if not. In Hive: MERGE INTO target t USING source s ON t.id = s.id WHEN MATCHED THEN UPDATE SET … WHEN NOT MATCHED THEN INSERT VALUES (…), where the target is a transactional ORC table. It runs as one transaction.

Avoid: Describing INSERT OVERWRITE of the whole table as an upsert.

Data engineeringMid-level

MERGE fails with a cardinality violation

The nightly MERGE fails: “Cardinality Violation in Merge statement”.

The interviewer is checking: do you know the cause and the fix?

Show a strong answer
  1. The source has more than one row for some keys (several CDC events, or a bad join).
  2. Find them: GROUP BY key HAVING COUNT(*) > 1.
  3. Keep the latest per key with ROW_NUMBER in the source subquery; the target was not changed, so just re-run.

Avoid: Setting hive.merge.cardinality.check=false, which makes the result unpredictable.

AnalyticsMid-level

Design an SCD2 customer dimension

Design a customer dimension that answers “which plan was the customer on when they ordered?”.

The interviewer is checking: can you design columns, load logic and queries?

Show a strong answer
  • Columns: business key, attributes, eff_from, eff_to (9999-12-31 for current), is_current; optionally a surrogate key.
  • Load: MERGE closing changed current rows and inserting new versions (NULL-key trick), idempotent.
  • Query: join facts on key AND fact_date BETWEEN eff_from AND eff_to; test one current row per key.

Avoid: Storing only the current value and trying to rebuild history from logs later.

PlatformSenior

Large nightly MERGE too slow

A MERGE of 50 lakh changes into a 2-billion-row ACID table takes 4 hours.

The interviewer is checking: can you optimise reads, writes and table health?

Show a strong answer
  • Prune the target in ON (partitions, is_current), send only real changes (hash compare).
  • Check deltas and compaction status; compact after the merge.
  • Consider partitioning the target by the column most changes are filtered on, or Iceberg with merge-on-read deletes.

Avoid: Running the MERGE more often without measuring where the time goes.
