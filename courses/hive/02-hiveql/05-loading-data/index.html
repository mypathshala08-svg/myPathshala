Loading data: LOAD, INSERT, CTAS and multi-insert

There are two families of loading in Hive. LOAD DATA only copies or moves files into the table folder: instant, and completely trusting. INSERT, CTAS and the multi-insert run a query and write fresh files in the table’s format. This lesson loads the same file twice, loads a JSON file into a CSV table, writes three tables in one scan and shows how one-row inserts create small files. All outputs are real, from Hive 4.2.1.

Today you will learn every way to fill a table: LOAD (copy or move), INSERT INTO and OVERWRITE, CREATE TABLE AS SELECT and the multi-insert that writes three tables in one scan. And how to make loads safe to re-run.

2 Definition

Loading data into Hive tables

Formal definition (write this in exams)

Data enters a Hive table in two ways. LOAD DATA [LOCAL] INPATH 'path' [OVERWRITE] INTO TABLE t is a pure file operation: it copies (LOCAL) or moves files into the table’s location without parsing or validating them. INSERT INTO | OVERWRITE TABLE t SELECT …, INSERT INTO t VALUES …, CREATE TABLE … AS SELECT (CTAS) and the multi-table form FROM src INSERT … INSERT … run a query whose results are serialized in the target table’s format and written as new files; OVERWRITE replaces existing data, INTO appends.

In simple words

LOAD just puts files into the table’s folder: quick, but nothing is checked. INSERT and CTAS run a query and write fresh files in the table’s own format. OVERWRITE replaces, INTO adds.

Words you’ll meet in this lesson

LOCALWith LOAD: the path is on HiveServer2’s local disk and the file is copied. Without: the path is in the cluster file system and the file is moved.
OVERWRITEDelete the existing data of the table (or partition) before writing.
CTASCREATE TABLE … AS SELECT: new table with the query’s columns and rows.
Multi-insertFROM src INSERT … INSERT …: read the source once, write several tables.
IdempotentRunning it twice gives the same result as once. Essential for retried jobs.
Staging directory.hive-staging_…: where INSERT writes before moving files into place.
Small filesMany tiny files in a table: slow to list and read. Each INSERT … VALUES adds one.
copy_NSuffix Hive adds when a file of the same name already exists in the table folder.

Loading data at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Putting groceries in a cupboard

  • LOAD DATA = putting the bags in the cupboard as they are. Fast, no checking. Put the same bag twice and you have two.
  • INSERT … SELECT = cooking: take ingredients from one cupboard, prepare them, store the dish in another.
  • OVERWRITE = empty the shelf first, then put the new food in. Running it twice gives the same result.
  • CTAS = buy a new box and fill it in one step.

Intermediate What each statement does

  • LOAD DATA LOCAL INPATH 'p' INTO TABLE t: copies files from the HiveServer2 machine’s local disk into the table folder.
  • LOAD DATA INPATH 'p' INTO TABLE t: moves files that are already in the table’s file system (HDFS, or here the local FS).
  • … OVERWRITE INTO TABLE: removes the old files first.
  • INSERT INTO t SELECT … appends query results; INSERT OVERWRITE TABLE t SELECT … replaces them. Both run a Tez job and write new files (000000_0, …).
  • INSERT INTO t VALUES (…): a few literal rows; each statement makes a new small file.
  • CREATE TABLE t STORED AS ORC AS SELECT … (CTAS): creates the table from the query’s columns and fills it.
  • FROM src INSERT … INSERT …: one scan of src, several targets.

Advanced The details that bite in production

  • LOAD does not validate anything: loading a JSON file into a CSV table succeeded and produced NULL ids.
  • skip.header.line.count applies to every file in the folder: the first line of the JSON file was silently dropped (2,119 rows, not 2,120).
  • File names: a second file with the same name becomes …_copy_1; repeated INSERTs make 000000_0_copy_1, _copy_2: the start of the small-files problem.
  • Staging: INSERT writes to a .hive-staging_… folder first and moves the files in at the end, so readers never see half-written results.
  • Statistics: CTAS and INSERT update numRows automatically (8 rows for city_sales), which helps the optimiser.
  • Idempotency: INSERT OVERWRITE and LOAD … OVERWRITE give the same result when re-run; INSERT INTO and LOAD … INTO do not.

Exam tip: “Difference between LOAD DATA LOCAL and LOAD DATA.” LOCAL copies a file from the local file system of the HiveServer2 host; without LOCAL the file is moved within HDFS. Add: LOAD does not validate the data, OVERWRITE replaces existing files, and INSERT … SELECT is used when data must be transformed or converted to another format.

Landing → raw

What you see
  1. Kabir loads the customer file: 2,000 rows.
  2. The job is retried and loads the same file again: 4,000 rows, no warning.
  3. He switches to LOAD without LOCAL and with OVERWRITE: 2,000 rows again, but the source file is gone from incoming.

Behind the screen
  1. LOCAL copies the file from HiveServer2’s disk into the table folder.
  2. The name already exists, so the copy is renamed customers_day1_copy_1.csv. Both files are read.
  3. OVERWRITE deletes the old files; without LOCAL the source file is moved (renamed), not copied.
  4. LOAD never parses. The JSON lines become rows with NULL ids, and the header rule removes one line from each file.
  5. One Map vertex reads the source once and routes rows to three outputs, staged and then moved into place.
  6. Each INSERT writes at least one new file. Many tiny files slow down listing and reading.

Real-time scenario 1

The retried job that doubled revenue

Retries are normal in schedulers. Loads must be written so that a retry is harmless. (Row counts illustrative.)

Idempotent loads 5 steps
Animated example
  1. The nightly job appends one day of orders with INSERT INTO.
  2. A retry appends the same day again. Revenue for that day doubles silently.
  3. INSERT OVERWRITE of exactly the day being loaded makes a retry replace the data.
  4. Tables that receive updates use MERGE on the business key.
  5. A count vs distinct-key check after each load catches duplicates immediately.
Real-time scenario 2

From raw text to a curated ORC table

The workhorse of Hive pipelines is INSERT OVERWRITE … SELECT from a raw table.

Raw to curated 5 steps
Animated example
  1. The raw external text table is fine for landing but slow and untyped for reports.
  2. One INSERT OVERWRITE casts, filters and writes the data in ORC.
  3. Readers get typed, compressed data, and the job is safe to re-run.
  4. The same job counts rows it rejects: in our data, 2 orders (an amount “abc” and a date in the wrong layout).
  5. A typical night: files land, curation runs, then mart tables are rebuilt.
Real-time scenario 3 · advanced

How INSERT … VALUES creates a small-files problem

One file per statement is harmless three times and disastrous a hundred thousand times. (Volumes illustrative.)

Small files 5 steps
Animated example
  1. A job inserts a few rows every minute with INSERT … VALUES.
  2. After 90 days the table has 129,600 tiny files; queries spend their time opening files.
  3. Batch the writes so each insert writes large files.
  4. Rewrite existing small files into large ones, or rely on compaction for ACID and Iceberg tables.
  5. Hive is a batch engine; streams should be landed and compacted, not inserted row by row.
6 Real-world use

Loading in daily pipelines

1. Nightly curated tables

Most warehouse jobs are INSERT OVERWRITE … SELECT from raw into curated tables, partition by partition. A failed night is simply re-run.

Raw→INSERT OVERWRITE→Curated ORC

2. Splitting a big feed

A payments feed is split into UPI, card and wallet tables in one multi-insert, reading terabytes once instead of three times.

Payments feed→Multi-insert→3 tables

3. Analyst working tables

Analysts create a filtered copy with CTAS (“orders of the Diwali week”) in their sandbox and explore it quickly, without touching shared tables.

Big table→CTAS→Sandbox table

4. Moving landed files

When a transfer tool drops a ready-made file in HDFS, LOAD DATA INPATH … OVERWRITE moves it into the table in milliseconds, with no job.

Transfer tool→LOAD (move)→Table

5. Post-load quality checks

After every load a job compares row counts with the source and with distinct keys, and stops the pipeline if they differ.

Load→Checks→Publish or stop

Run the code: simulate loads on a table folder

A dictionary plays the table folder: file name → rows. The functions copy Hive’s rules for INTO, OVERWRITE and file naming. Then you will build a multi-insert router and an idempotency check. Press Run, then try the challenges.

# A table folder and what each load does to it
folder = {}

def load_into(name, rows):            # LOAD DATA ... INTO
    new = name
    n = 1
    while new in folder:              # same name exists -> name_copy_1, _copy_2, ...
        stem, ext = name.rsplit(".", 1)
        new = f"{stem}_copy_{n}.{ext}"; n += 1
    folder[new] = rows

def load_overwrite(name, rows):       # LOAD DATA ... OVERWRITE INTO
    folder.clear()
    folder[name] = rows

load_into("customers_day1.csv", 2000)
load_into("customers_day1.csv", 2000)          # the retried job
print(folder, "->", sum(folder.values()), "rows")
load_overwrite("customers_day2.csv", 2000)
print(folder, "->", sum(folder.values()), "rows")
{'customers_day1.csv': 2000, 'customers_day1_copy_1.csv': 2000} -> 4000 rows {'customers_day2.csv': 2000} -> 2000 rows

  • folder.clear()OVERWRITE deletes the existing files first. That is what makes it safe to re-run.

Interview and viva questions

Does LOAD DATA convert my CSV into ORC if the table is ORC?

No. LOAD only moves or copies files; the table would then contain CSV files that the ORC reader cannot read, and queries fail or return garbage. To convert, create a text table over the CSV (or load into one) and run INSERT … SELECT into the ORC table.

Is LOAD DATA LOCAL “local” to my laptop?

It is local to the HiveServer2 host (the machine or container running HiveServer2), not to the computer where Beeline runs. In our lab both happen inside the hiveserver2 container. On a cluster you normally put files into HDFS or object storage first (with hdfs dfs -put or a transfer tool) and then use LOAD DATA INPATH or simply point an external table at the folder.

Why did INSERT … VALUES take seconds for two rows?

Each INSERT is a full query: it is compiled, a Tez job runs, files are written to a staging folder and moved into place. That overhead is the same for 2 rows or 2 million rows. Hive is built for large batch writes; for frequent small writes use batching or a system designed for it.

What is the difference between CTAS and CREATE TABLE LIKE?

CREATE TABLE … LIKE copies another table’s definition and creates an empty table. CTAS creates a table from a query’s result columns and fills it with the rows. CTAS fails if the table already exists; to refresh an existing table use INSERT OVERWRITE instead.

How do I stop small files from piling up?

Write in batches, prefer INSERT OVERWRITE of whole partitions, enable Hive’s merge settings so jobs combine small output files, and periodically rewrite (compact) tables that collected many files. ACID and Iceberg tables have compaction built in. Module 5 covers this in detail.

print(big, pune, total)
[1, 4] [1, 3] 4

How it works: [1, 4] [1, 3] 4. A row can go to several targets in a multi-insert, as order 1 does.

P5Medium

Find duplicate ids

Print ids that appear more than once after a load.

Input
[7, 8, 9, 8, 10, 7]
Expected output
[7, 8]
Show solution and explanation 
ids = [7, 8, 9, 8, 10, 7]
seen, dups = set(), set()
for i in ids:
    (dups if i in seen else seen).add(i)
print(sorted(dups))
[7, 8]

How it works: [7, 8]. In Hive: GROUP BY id HAVING COUNT(*) > 1.

P6Medium

Rows rejected by casts

A raw table has 50,002 rows; the curated INSERT keeps rows where id, amount and timestamp are not NULL; 50,000 rows arrive. What share was rejected?

Input
50,002 → 50,000
Expected output
rejected 2 rows (0.0040%)
Show solution and explanation 
raw, cur = 50_002, 50_000
print(f"rejected {raw - cur} rows ({(raw - cur) / raw:.4%})")
rejected 2 rows (0.0040%)

How it works: 2 rows (0.0040%), exactly orders 150001 and 150002 from our dataset.

P7Business problem

Cost of a duplicated day

A retry duplicated one day of 48,000 orders worth an average Rs 290. By how much was reported revenue inflated?

Input
48,000 × Rs 290
Expected output
inflated by Rs 13,920,000
Show solution and explanation 
orders, avg = 48_000, 290
print(f"inflated by Rs {orders * avg:,}")
inflated by Rs 13,920,000

How it works: Rs 1,39,20,000 (13.92 million). One INSERT INTO in a retried job can misreport a crore of revenue.

P8Business problem

Small files after a year

A job inserts once per minute, creating one file each time. How many files after a year, and after switching to hourly batches?

Input
per minute vs per hour, 365 days
Expected output
per minute: 525600
per hour  : 8760
Show solution and explanation 
print("per minute:", 60 * 24 * 365)
print("per hour  :", 24 * 365)
per minute: 525600 per hour : 8760

How it works: 525,600 files versus 8,760. Batching is a 60× reduction before any compaction.

Real-world scenario questions (asked in company interviews)

Loading questions test practical pipeline experience. Expect to explain LOAD vs INSERT and how you avoid duplicates.

Any company · basicsFresher

“How do you load a CSV into Hive?”

The interviewer asks for the steps to get a CSV from your laptop into a Hive ORC table.

The interviewer is checking: do you know LOAD vs INSERT and formats?

Show a strong answer
  1. Copy the file to HDFS (hdfs dfs -put) or object storage.
  2. Create a text table (external, with the right delimiter and header skip) over that folder, or LOAD the file into one.
  3. Create the ORC table and run INSERT OVERWRITE TABLE orc_t SELECT … FROM text_t to convert and type the data.

Avoid: “LOAD DATA straight into the ORC table”: LOAD does not convert formats.

Data engineering · reliabilityMid-level

Numbers doubled after a retry

A dashboard shows double sales for one day. The scheduler log shows the nightly Hive task ran twice.

The interviewer is checking: do you understand idempotent loads?

Show a strong answer
  • The task used INSERT INTO (or LOAD … INTO), so the retry appended the same day again.
  • Fix the data: re-run that day with INSERT OVERWRITE of its partition.
  • Fix the job: overwrite exactly the slice it loads, or MERGE on keys; add a post-load duplicate check.

Avoid: disabling retries; failures will still happen, so loads must be re-runnable.

Platform · performanceMid-level

One source, many tables

A job runs five INSERT … SELECT statements over the same 2 TB table to build five region tables. It takes three hours.

The interviewer is checking: do you know multi-insert?

Show a strong answer
  • Rewrite as FROM big_table INSERT OVERWRITE TABLE r1 SELECT … WHERE … INSERT OVERWRITE TABLE r2 ….
  • The source is read once instead of five times; output writing cost stays the same.
  • Also consider one partitioned table by region instead of five tables (Module 5).

Avoid: adding more nodes before removing the four extra scans.

Operations · small filesMid-level

Queries slowed down over months

An events table that started fast now takes minutes. The table folder has 300,000 files of a few KB each.

The interviewer is checking: can you connect loading style to the small-files problem?

Show a strong answer
  1. Each INSERT (especially frequent INSERT … VALUES or tiny batches) created new files.
  2. Compact: rewrite partitions with INSERT OVERWRITE … SELECT and merge settings, or run compaction for ACID/Iceberg tables.
  3. Prevent: batch writes, target files of hundreds of MB, monitor file counts per partition.

Avoid: blaming the cluster size.
