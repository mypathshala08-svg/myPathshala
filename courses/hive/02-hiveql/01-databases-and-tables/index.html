2 Definition

Databases and tables in Hive

Formal definition (write this in exams)

In Hive a database (synonym: schema) is a named namespace for tables, recorded in the metastore and mapped by default to the directory <warehouse>/<database>.db. A table is a metastore entry that describes data files by their columns and data types, row format (SerDe and delimiters), storage format (input/output format), location, table type (managed or external) and table properties. Tables are created with CREATE TABLE and inspected with DESCRIBE [FORMATTED] and SHOW CREATE TABLE.

In simple words

A database is a named folder for tables. A table is a description, kept in the metastore, of how to read some files as rows and columns: which columns, what types, how lines are split, what format the files have and where they are.

Words you’ll meet in this lesson

DDLData Definition Language: statements that create, change or drop objects (CREATE, ALTER, DROP).
NamespaceA space where each name is unique. Two databases can each contain a table called orders.
Qualified namedatabase.table, for example tiffingo.customers. Works from any current database.
WarehouseThe root folder for databases and managed tables (hive.metastore.warehouse.dir).

Databases and tables at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Shelves and labelled boxes

  • A database is a shelf with a name, like tiffingo.
  • A table is a labelled box on that shelf: the label lists the columns (name, city, plan…), the box holds the data files.
  • Two shelves can each have a box called orders; you say which one with shelf.box, for example tiffingo.orders.
  • USE tiffingo; means “I am standing at this shelf now”, so you can write just orders.

Intermediate What Hive records

  • CREATE DATABASE adds a row in the metastore table DBS and a folder <warehouse>/<name>.db, for us file:/opt/hive/data/warehouse/tiffingo.db.
  • CREATE TABLE records the columns and types, the row format (how a line becomes columns: a SerDe and a delimiter), the file format (TEXTFILE, ORC, Parquet…), the location and table properties.
  • Without LOCATION the table folder is <db folder>/<table>.
  • Names are not case-sensitive and are stored in lower case; Customers and customers are the same table.

Advanced Details that matter at work

  • Hive 4 table translation: with the default hive.create.as.acid=false, a plain CREATE TABLE that is not transactional is stored as EXTERNAL_TABLE with external.table.purge=TRUE and TRANSLATED_TO_EXTERNAL=TRUE. It behaves like a managed table (DROP deletes data) but is not ACID. Lesson 2.2 explains why.
  • Table properties (TBLPROPERTIES) carry behaviour: skip.header.line.count, transactional, compression, statistics such as numFiles and totalSize.
  • Patterns: in Hive 4 SHOW TABLES LIKE uses SQL wildcards: 'cust%' matched, 'tif*' matched nothing in our run.
  • Safety: DROP DATABASE refuses a non-empty database unless you add CASCADE, which drops every table in it. IF EXISTS / IF NOT EXISTS make scripts safe to re-run.
  • Temporary tables live only for your session and are invisible to others.

Exam tip: “Write the syntax of CREATE TABLE in Hive.” CREATE [EXTERNAL] [TEMPORARY] TABLE [IF NOT EXISTS] [db.]name (col type [COMMENT '…'], …) [COMMENT '…'] [PARTITIONED BY (…)] [ROW FORMAT DELIMITED FIELDS TERMINATED BY ','] [STORED AS format] [LOCATION 'path'] [TBLPROPERTIES (…)]; Then name what goes to the metastore (schema, format, location) and that no data is moved by CREATE.

3 Types and ways to use it

Ways to create databases and tables

CREATE TABLE (columns)

You list the columns and types, and optionally row format, file format, location and properties. The most common form.

Everyday

CREATE TABLE … LIKE

Copies another table’s definition (columns, format, properties) without any data. CREATE TABLE customers_copy LIKE customers.

Same shape

CREATE TABLE … AS SELECT

CTAS: creates the table from a query’s result, columns and data together. Lesson 2.5.

From a query

CREATE EXTERNAL TABLE

Describes files that something else owns; DROP leaves the files. Lesson 2.2.

Shared files

CREATE TEMPORARY TABLE

Lives only for your session, visible only to you. Good for intermediate steps.

Scratch

CREATE DATABASE … LOCATION

Puts a database folder somewhere other than the warehouse, for example a team bucket.

4 Step by step

Create the TiffinGo database and its first table

All outputs are real, from the Hive 4.2.1 lab of Lesson 1.5.

  1. Step 1 · Create a database with a comment and an owner

    CREATE DATABASE IF NOT EXISTS tiffingo
  COMMENT 'TiffinGo food delivery data'
  WITH DBPROPERTIES ('owner_team'='data-eng');
SHOW DATABASES;
    +----------------+ | database_name | +----------------+ | default | | tiffingo | +----------------+
    IF NOT EXISTS makes the statement safe to run twice. The comment and properties are stored in the metastore and help the next person understand what the database is for.

  2. Step 2 · See where it lives

    DESCRIBE DATABASE EXTENDED tiffingo;
    | db_name | comment | location | owner_name | parameters | | tiffingo | TiffinGo food delivery data | file:/opt/hive/data/warehouse/tiffingo.db | hive | {owner_team=data-eng} | (columns trimmed)
    The location is <warehouse>/tiffingo.db. On a real cluster it would start with hdfs:// or s3a://. Hive 4 also prints a managedlocation column (same folder here).

  3. Step 3 · Create the customers table

    USE tiffingo;
CREATE TABLE customers (
  customer_id INT COMMENT 'unique id',
  name STRING, city STRING, state STRING,
  joined_on DATE,
  plan STRING COMMENT 'Gold, Silver or Basic')
COMMENT 'TiffinGo customers'
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE
TBLPROPERTIES ('skip.header.line.count'='1');
DESCRIBE customers;
    +--------------+------------+------------------------+ | col_name | data_type | comment | +--------------+------------+------------------------+ | customer_id | int | unique id | | name | string | | | city | string | | | state | string | | | joined_on | date | | | plan | string | Gold, Silver or Basic | +--------------+------------+------------------------+
    Three parts: the columns, how a line is split (ROW FORMAT DELIMITED with commas), and the file format. skip.header.line.count=1 tells readers to ignore the CSV header line.

  4. Step 4 · Put data in and query it

    LOAD DATA LOCAL INPATH '/data/tiffingo/customers/customers.csv' INTO TABLE customers;
SELECT plan, COUNT(*) AS n FROM customers GROUP BY plan ORDER BY n DESC;
    +---------+------+ | plan | n | +---------+------+ | Basic | 999 | | Gold | 517 | | Silver | 484 | +---------+------+
    999 + 517 + 484 = 2,000 customers, so the header line was skipped correctly. LOAD DATA copied the file into the table folder (Lesson 2.5 covers loading in depth).

  5. Step 5 · Read everything Hive knows

    DESCRIBE FORMATTED customers;
    | # Detailed Table Information | | | Database: | tiffingo | | Owner: | hive | | Location: | file:/opt/hive/data/warehouse/tiffingo.db/customers | | Table Type: | EXTERNAL_TABLE | | Table Parameters: | | | | TRANSLATED_TO_EXTERNAL TRUE | | | external.table.purge TRUE | | | numFiles 1 | | | skip.header.line.count 1 | | | totalSize 91618 | | # Storage Information | | | SerDe Library: | org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe | | InputFormat: | org.apache.hadoop.mapred.TextInputFormat | (trimmed)
    Surprise: we wrote CREATE TABLE, but the type is EXTERNAL_TABLE with TRANSLATED_TO_EXTERNAL and external.table.purge=TRUE. Hive 4 stores non-transactional “managed” tables this way; DROP still deletes the files. Details in Lesson 2.2.

  6. Step 6 · Get the full DDL

    SHOW CREATE TABLE customers;
    CREATE EXTERNAL TABLE `customers`( `customer_id` int COMMENT 'unique id', `name` string, … , `plan` string COMMENT 'Gold, Silver or Basic') COMMENT 'TiffinGo customers' ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe' WITH SERDEPROPERTIES ( 'field.delim'=',', 'serialization.format'=',') STORED AS INPUTFORMAT 'org.apache.hadoop.mapred.TextInputFormat' OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat' LOCATION 'file:/opt/hive/data/warehouse/tiffingo.db/customers' TBLPROPERTIES ( 'TRANSLATED_TO_EXTERNAL'='TRUE', 'external.table.purge'='TRUE', 'skip.header.line.count'='1', …)
    ROW FORMAT DELIMITED … STORED AS TEXTFILE is shorthand: Hive expands it into a SerDe class, an input format and an output format. Save this output in Git; it recreates the table exactly.

CREATE TABLE customers (id INT);
SELECT * FROM tiffingo.customer;
DROP DATABASE tiffingo;

Errors 5 steps
Animated example

6 Real-world use

Databases and tables in daily work

1. Layered warehouses

Most companies keep raw landing data, cleaned tables and report tables in separate databases. A table’s database tells you how much you can trust it.

Files arrive→raw → curated → mart→Reports

2. DDL in version control

Teams keep every CREATE TABLE in Git (often taken from SHOW CREATE TABLE). Changes are reviewed like code and the same file builds dev, test and production.

Pull request→Review DDL→Deploy

3. One database per environment

On a shared cluster, dev_tiffingo, test_tiffingo and tiffingo hold the same tables. A --hivevar db=… switch points the same script at each.

Script→${db}.orders→Right environment

4. Data discovery

Data catalogue tools read databases, tables, column comments and properties from the metastore. Good comments written at CREATE time become documentation everyone can search.

COMMENT→Metastore→Catalogue search

5. Scratch work without clutter

Analysts use CREATE TEMPORARY TABLE for intermediate steps. The table disappears when the session ends, so shared databases stay clean.

Big query→Temp table→Final result

Examples are simplified. Naming conventions differ between companies.

7 Run the code

Run the code: a metastore in a dictionary

A Python dictionary plays the metastore: databases contain tables, tables contain columns and a location. It is a toy, but it follows the same rules: unique names per database, default folders under the warehouse, and metadata separate from data. Press Run, then try the challenges.

# A tiny metastore: databases hold tables, tables hold metadata
warehouse = "file:/opt/hive/data/warehouse"
metastore = {"default": {}}

def create_database(db):
    if db in metastore:
        print("already exists:", db); return
    metastore[db] = {}
    print("created", db, "at", f"{warehouse}/{db}.db")

def create_table(db, table, columns):
    if table in metastore[db]:
        raise ValueError(f"AlreadyExistsException: {db}.{table}")
    metastore[db][table] = {"columns": columns, "location": f"{warehouse}/{db}.db/{table}"}

create_database("tiffingo")
create_table("tiffingo", "customers", [("customer_id", "int"), ("name", "string"), ("plan", "string")])
for col, typ in metastore["tiffingo"]["customers"]["columns"]:
    print(f"{col:12} {typ}")
print(metastore["tiffingo"]["customers"]["location"])
created tiffingo at file:/opt/hive/data/warehouse/tiffingo.db customer_id int name string plan string file:/opt/hive/data/warehouse/tiffingo.db/customers
  • metastore[db] = {}Like a row in DBS: the database exists as soon as it is recorded. Hive also creates the folder tiffingo.db.
  • raise ValueError(f"AlreadyExistsException: {db}.{table}")Table names are unique within a database. The real error is AlreadyExistsException.
  • "location": f"{warehouse}/{db}.db/{table}"Without a LOCATION clause, a table folder is created inside its database folder.

Quick revision

Lesson 2.1 in one screen

  • Database = namespace; metastore row in DBS; folder <warehouse>/<db>.db. Synonym: schema.
  • Table = columns + types + row format (SerDe, delimiter) + file format + location + type + TBLPROPERTIES.
  • CREATE DATABASE IF NOT EXISTS db COMMENT … WITH DBPROPERTIES (…) · USE db · SHOW DATABASES LIKE 'tif%'.
  • DESCRIBE t (columns) · DESCRIBE FORMATTED t (everything) · SHOW CREATE TABLE t (full DDL).
  • Forms: plain, LIKE (shape only), CTAS (Lesson 2.5), EXTERNAL (2.2), TEMPORARY (session only).
  • TBLPROPERTIES ('skip.header.line.count'='1') skips CSV headers.
  • Hive 4: non-transactional CREATE TABLE → EXTERNAL_TABLE + external.table.purge=TRUE + TRANSLATED_TO_EXTERNAL.
  • Errors: Table not found (compile time), AlreadyExistsException, Database … is not empty (use CASCADE carefully). Use qualified names db.table in scripts.

Interview and viva questions

Is a Hive database the same as a database in MySQL?

Not quite. In MySQL a database contains tables whose data the MySQL server stores and manages. In Hive a database is mainly a namespace and a default folder; the data is ordinary files in HDFS or object storage that other tools can also read. Hive treats DATABASE and SCHEMA as synonyms.

What is the difference between DESCRIBE, DESCRIBE EXTENDED and DESCRIBE FORMATTED?

DESCRIBE lists columns, types and comments. DESCRIBE EXTENDED adds all table details in one long, hard-to-read line. DESCRIBE FORMATTED shows the same details neatly in sections: detailed table information (location, owner, type, parameters) and storage information (SerDe, input/output format, buckets). Engineers use FORMATTED.

Why did my CREATE TABLE become an EXTERNAL_TABLE?

Hive 4 keeps “managed” tables for transactional (ACID) data. When hive.create.as.acid is false and the table is not transactional, the metastore stores it as an external table with external.table.purge=TRUE and marks it TRANSLATED_TO_EXTERNAL=TRUE. It behaves like a classic managed table for DROP (files are deleted), but it is not ACID. Lesson 2.2 compares the types.

Can I rename a database?

Not with a simple command in most Hive versions; you can change a database’s properties, owner and (in newer versions) location with ALTER DATABASE. Teams usually create the new database and move or recreate tables. Choose database names carefully at the start.

Should I use USE or qualified names?

Use USE when exploring interactively. In scheduled scripts, views and shared code, write db.table everywhere so the meaning does not depend on the current database. Many teams also pass the database name as a variable (--hivevar db=…) to run the same script in dev and production.

P3Easy

Qualify a name

Write a function that returns db.table, using the current database when no database is given.

Input
current = tiffingo · names: orders, mart.daily_sales
Expected output
tiffingo.orders mart.daily_sales
Show solution and explanation 
current = "tiffingo"
def qualify(n):
    return n if "." in n else f"{current}.{n}"
print(qualify("orders"), qualify("mart.daily_sales"))
tiffingo.orders mart.daily_sales

How it works: tiffingo.orders and mart.daily_sales. The same rule decides which table an unqualified query reads.

P7Business problem

Storage per database

totalSize values (bytes) from DESCRIBE FORMATTED are given per table. Sum them per database and print in MB.

Input
tiffingo.customers 91,618 · tiffingo.orders 3,086,726 · tiffingo_raw.orders 3,086,726
Expected output
tiffingo      3.03 MB
tiffingo_raw  2.94 MB
Show solution and explanation 
sizes = {"tiffingo.customers": 91618, "tiffingo.orders": 3086726, "tiffingo_raw.orders": 3086726}
per_db = {}
for name, b in sizes.items():
    db = name.split(".")[0]
    per_db[db] = per_db.get(db, 0) + b
for db, b in per_db.items():
    print(f"{db:13} {b / 1024 / 1024:.2f} MB")
tiffingo 3.03 MB tiffingo_raw 2.94 MB

How it works: 3.03 MB and 2.94 MB. The same sum on a real warehouse shows which layer costs most storage. totalSize is only reliable when statistics are up to date.

P8Business problem

Naming policy check

The policy says table names are lower_snake_case, start with a letter and are at most 40 characters. Check these names.

Input
daily_sales, DailySales, 2024_orders, customer_lifetime_value_by_city_and_month_v2
Expected output
daily_sales                                    ok
DailySales                                     violates policy
2024_orders                                    violates policy
customer_lifetime_value_by_city_and_month_v2   violates policy
Show solution and explanation 
import re
names = ["daily_sales", "DailySales", "2024_orders", "customer_lifetime_value_by_city_and_month_v2"]
for n in names:
    ok = bool(re.fullmatch(r"[a-z][a-z0-9_]*", n)) and len(n) <= 40
    print(f"{n:46} {'ok' if ok else 'violates policy'}")
daily_sales ok DailySales violates policy 2024_orders violates policy customer_lifetime_value_by_city_and_month_v2 violates policy

How it works: Only daily_sales passes. A check like this in code review avoids names that are hard to type, sort or search.

Real-world scenario questions (asked in company interviews)

Interviewers use simple DDL to see whether you understand what Hive stores and where. These come up for freshers and mid-level roles.

Any company · basicsFresher

“What happens when you create a table in Hive?”

The interviewer asks you to explain CREATE TABLE in Hive to someone who knows only MySQL.

The interviewer is checking: do you separate metadata from data?

Show a strong answer
  1. Hive writes the table’s definition to the metastore: columns and types, row format (SerDe and delimiter), file format, location, table type and properties.
  2. It creates an empty folder (unless a LOCATION is given). No data is moved or checked.
  3. Data is added later by LOAD DATA, INSERT or by placing files in the location; the schema is applied when the data is read (schema on read).

Avoid: saying the table is “created in Hive’s storage engine”; Hive has no storage engine of its own.

Data engineering · investigationFresher

Where does this table really read from?

A report shows yesterday’s numbers twice. You suspect the table is reading the wrong folder.

The interviewer is checking: do you know the commands that reveal a table’s storage?

Show a strong answer
  • Run DESCRIBE FORMATTED (or SHOW CREATE TABLE) and read Location, Table Type, SerDe and properties.
  • List the location (hdfs dfs -ls) and check for duplicate or unexpected files.
  • Check that the report uses a qualified name, so it is not reading a same-named table in another database.

Avoid: rewriting the query before checking what the table points at.

Platform · Hive 4 upgradeMid-level

Why did our managed tables become external?

After an upgrade to Hive 4, DESCRIBE FORMATTED shows EXTERNAL_TABLE with TRANSLATED_TO_EXTERNAL for tables created with plain CREATE TABLE. A colleague worries data will be kept after DROP.

The interviewer is checking: do you know Hive’s managed vs external rules in version 3 and later?

Show a strong answer
  • Since Hive 3, managed tables are meant for ACID (transactional) data. Non-transactional managed tables are translated to external tables with external.table.purge=TRUE.
  • Because purge is TRUE, DROP still deletes the files: behaviour matches the old managed table.
  • If the team wants ACID features (UPDATE, DELETE, MERGE), create tables as transactional ORC, or set hive.create.as.acid as a policy decision.

Avoid: claiming it is a bug or that DROP is now safe.

Operations · safetyMid-level

Someone ran DROP DATABASE … CASCADE

A sandbox clean-up script ran DROP DATABASE tiffingo CASCADE on the wrong environment.

The interviewer is checking: do you understand the blast radius and prevention?

Show a strong answer
  1. CASCADE dropped every table; managed and purge-enabled external tables lost their files, plain external tables kept them.
  2. Recovery: HDFS trash or snapshots, object-store versioning, or a metastore database backup plus re-creating DDL from Git.
  3. Prevention: separate permissions per database, no CASCADE in automated scripts, environment name passed explicitly and checked, and backups of the metastore.

Avoid: “just restore the metastore”: metadata without files, or files without metadata, are both incomplete.
