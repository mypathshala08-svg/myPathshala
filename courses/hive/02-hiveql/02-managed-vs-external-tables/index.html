Managed vs external tables

DROP TABLE can delete your data or leave it untouched, depending on who owns it. This lesson creates three tables over the same TiffinGo orders (external, plain and ACID managed), updates a row, truncates, drops all three and inspects the folders after every step. You will also see two real incidents: a purge flag that deletes a shared folder, and a DROP that leaves orphan files. All outputs are real, from Hive 4.2.1.

1 The story

“I only dropped the table. Where did the data go?”

Before you start: finish Lesson 2.1, where a plain CREATE TABLE turned into an EXTERNAL_TABLE. This lesson explains why.

Kabir and Riya each clean up a test table on the TiffinGo lab. Both type DROP TABLE. Riya re-creates hers a minute later and all 50,002 orders are still there. Kabir re-creates his and gets zero rows: the folder in the warehouse is gone.

Kabir

Sir, we ran the same command. Why did my data disappear and hers did not?

Arjun Sir

Because Hive has two kinds of ownership. For Riya’s table Hive owns only the label: the metadata. The files belong to someone else, so DROP removes the label and leaves the files. That is an external table. For your table Hive owned the label and the box: DROP removed both.

Riya

So I should always use external tables to be safe?

Arjun Sir

Not always. Hive can only offer some features when it owns the files: UPDATE, DELETE, MERGE, TRUNCATE, automatic clean-up. And Hive 4 adds a twist: your plain CREATE TABLE was stored as an external table with a purge flag, which makes DROP delete files anyway.

Kabir

Three kinds, then. How do I tell them apart before I drop something?

Arjun Sir

DESCRIBE FORMATTED: look at Table Type, external.table.purge and transactional. Today we will create all three over the same orders, change one row, drop them and look at the folders after each step.

2 Definition

Managed and external tables

Formal definition (write this in exams)

A managed (internal) table is a table whose data files Hive owns: they are stored under the warehouse directory, written only through Hive, and deleted with the table on DROP TABLE; in Hive 3 and later managed tables are transactional (ACID). An external table is a table for which Hive owns only the metadata: its LOCATION may be any path, other tools may write the files, and DROP TABLE removes only the metadata unless the property external.table.purge is true.

In simple words

Managed: Hive owns the table and the files, so dropping the table deletes the data. External: Hive only describes files that belong to someone else, so dropping the table leaves the data. In Hive 4 a plain CREATE TABLE gives an external table with “purge” switched on, which also deletes data on DROP.

Managed and external at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A rented flat and your own house

  • External table = a flat you rent. You put your name on the door (the metadata). When you leave, you take the name plate; the flat and its furniture (the files) stay for the owner.
  • Managed table = your own house. When you sell it, everything inside goes too.
  • Hive can renovate a house it owns (UPDATE, DELETE), but it must not change someone else’s flat.

Intermediate The three kinds you will meet in Hive 4

  • MANAGED_TABLE (transactional): created with TBLPROPERTIES ('transactional'='true'), usually ORC. Lives in the warehouse; supports INSERT, UPDATE, DELETE, MERGE; DROP deletes metadata and files.
  • EXTERNAL_TABLE with external.table.purge=TRUE: what a plain CREATE TABLE becomes (marked TRANSLATED_TO_EXTERNAL). Lives in the warehouse; INSERT and TRUNCATE work, UPDATE/DELETE do not; DROP deletes the files.
  • EXTERNAL_TABLE (plain): created with CREATE EXTERNAL TABLE … LOCATION. Files anywhere; DROP keeps them; TRUNCATE, UPDATE and DELETE are refused.

Advanced Why Hive 3 and 4 work this way

  • Since Hive 3, “managed” means Hive controls every write, so it can offer transactions: each write creates a delta_… folder, deletes create delete_delta_… folders, and readers see a consistent snapshot. Other tools must not write there directly.
  • Non-transactional tables cannot give those guarantees, so the metastore stores them as external (hive.create.as.acid=false is the default in our lab; with it set to true, plain CREATE TABLE makes ACID tables).
  • DROP is a metastore operation that then deletes files as the metastore’s user. If that user lacks permission, the table disappears but the files stay (we reproduced this: “Failed to delete … it still exists” in the metastore log).
  • external.table.purge can be changed with ALTER TABLE … SET TBLPROPERTIES: flipping it to true on a shared folder is a classic way to delete someone else’s data.

Exam tip: “Differentiate managed and external tables.” Give four points: who owns the data, default location (warehouse vs any LOCATION), effect of DROP (data deleted vs kept), and when to use each (Hive-only data vs data shared with other tools). For Hive 3/4 add: managed tables are ACID, and external.table.purge makes DROP delete external data.

4 Step by step

Three tables over the same orders, then three DROPs

All outputs are real (Hive 4.2.1 lab). The 50,002 orders file sits in /data/tiffingo/orders_ext.

  1. Step 1 · An external table over existing files

    CREATE EXTERNAL TABLE orders_ext (
  order_id INT, customer_id INT, restaurant_id INT, city STRING,
  order_ts TIMESTAMP, amount INT, payment STRING, status STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION 'file:///data/tiffingo/orders_ext';
    Hive records the definition and the folder; the 3 MB file is not moved. From now on Hive, and any other tool, can read it.

  2. Step 2 · A plain table and an ACID table, filled from it

    CREATE TABLE orders_plain (order_id INT, city STRING, amount INT);
CREATE TABLE orders_acid  (order_id INT, city STRING, amount INT)
  STORED AS ORC TBLPROPERTIES ('transactional'='true');
INSERT INTO orders_plain SELECT order_id, city, amount FROM orders_ext WHERE city = 'Thane';
INSERT INTO orders_acid  SELECT order_id, city, amount FROM orders_ext WHERE city = 'Thane';
SELECT 'ext' AS t, COUNT(*) FROM orders_ext
UNION ALL SELECT 'plain', COUNT(*) FROM orders_plain
UNION ALL SELECT 'acid', COUNT(*) FROM orders_acid;
    +--------+--------+ | t | _c1 | +--------+--------+ | acid | 4820 | | plain | 4820 | | ext | 50002 | +--------+--------+
    Both new tables hold the 4,820 Thane orders. The INSERT … SELECT ran as a Tez job and wrote new files into each table’s warehouse folder.

  3. Step 3 · Ask each table what it is

    DESCRIBE FORMATTED orders_ext;    -- and orders_plain, orders_acid
    orders_ext | Location: | file:/data/tiffingo/orders_ext | Table Type: | EXTERNAL_TABLE | | EXTERNAL TRUE orders_plain | Location: | file:/opt/hive/data/warehouse/tiffingo.db/orders_plain | Table Type: | EXTERNAL_TABLE | | TRANSLATED_TO_EXTERNAL TRUE | | external.table.purge TRUE orders_acid | Location: | file:/opt/hive/data/warehouse/tiffingo.db/orders_acid | Table Type: | MANAGED_TABLE | | transactional true (lines picked from three outputs)
    Three answers: plain external, external with purge (translated by Hive 4), and a true managed transactional table. These three lines decide what DROP will do.

  4. Step 4 · Look at the files

    cd /opt/hive/data/warehouse/tiffingo.db
find orders_plain orders_acid -type f -not -name ".*"
    orders_acid/delta_0000001_0000001_0000/bucket_00000_0 orders_acid/delta_0000001_0000001_0000/_orc_acid_version orders_plain/000000_0
    The plain table got one ordinary file. The ACID table got a delta folder named after transaction 1 (delta_<min txn>_<max txn>_<statement>) containing an ORC bucket file.

  5. Step 5 · Change one row

    UPDATE orders_acid  SET amount = 999 WHERE order_id = 100010;
UPDATE orders_plain SET amount = 999 WHERE order_id = 100010;
    +-----------------------+-------------------+---------------------+ (SELECT after the update) | orders_acid.order_id | orders_acid.city | orders_acid.amount | +-----------------------+-------------------+---------------------+ | 100012 | Thane | 300 | | 100010 | Thane | 999 | +-----------------------+-------------------+---------------------+ Error: Error while compiling statement: FAILED: SemanticException [Error 10297]: Attempt to do update or delete on table orders_plain that is not transactional
    The ACID table accepts the UPDATE (order 100010 now shows 999); the plain table refuses at compile time. Behind the screen the update wrote two new folders (Step 6 in the animation): orders_acid, orders_acid/delete_delta_0000002_0000002_0000, orders_acid/delta_0000001_0000001_0000, orders_acid/delta_0000002_0000002_0001.

  6. Step 6 · Try TRUNCATE on the external table

    TRUNCATE TABLE orders_ext;
    Error: Error while compiling statement: FAILED: SemanticException [Error 10146]: Cannot truncate non-managed table orders_ext.
    Hive refuses to empty files it does not own. TRUNCATE on orders_plain (purge) worked in our lab and left 0 rows.

  7. Step 7 · Drop all three and look again

    DROP TABLE orders_ext;
DROP TABLE orders_plain;
DROP TABLE orders_acid;
SHOW TABLES;
    +------------+ | tab_name | +------------+ | customers | +------------+ $ ls /opt/hive/data/warehouse/tiffingo.db customers $ ls -la /data/tiffingo/orders_ext -rw-r--r-- 1 root root 3085976 Oct 26 10:30 orders.csv
    The warehouse folders of orders_plain and orders_acid are gone. orders.csv in the external location is untouched; re-running the CREATE EXTERNAL TABLE from Step 1 returned 50,002 rows immediately.

Real-time scenario 1

The purge flag that deleted a shared folder

External tables protect shared files only while purge is off. Follow a realistic incident and the guard rails that prevent it.

Shared folders 5 steps
Animated example
  1. A connector writes event files to a landing folder; a Hive external table reads them.
  2. Someone sets external.table.purge to true so that DROP “cleans up”.
  3. Months later a clean-up script drops the table and the folder is deleted, connector files included.
  4. We reproduced this in the lab: after the property change and DROP, the folder no longer existed.
  5. Keep purge off on shared folders, restrict ALTER, protect landing data with snapshots, and check before dropping.
Real-time scenario 2

DROP succeeded, but the files stayed

This happened in our lab before we fixed folder permissions. It also happens on real clusters.

Orphan files 5 steps
Animated example
  1. DROP first removes the table from the metastore, then deletes the folder as the metastore’s user.
  2. If the user may not delete the files, the second step fails but the client still sees success.
  3. Only the metastore log tells the truth: Failed to delete … it still exists.
  4. The files are now orphans: no table uses them, and a future table on the same path would read them.
  5. Fix permissions, monitor the logs and run a regular orphan check.

6 Real-world use

Where each type is used

1. Landing zones

Files arriving from apps, payment gateways or partners land in a folder that ingestion tools own. Hive external tables let analysts query them the same day without copying.

Source system→External table→Analysts

2. Tables that get corrected

Order status changes from DELIVERED to REFUNDED days later. A managed ACID table takes a nightly MERGE of changes instead of rewriting the whole table.

Changes→MERGE into ACID→Current orders

3. Multi-engine data lakes

When Spark writes Parquet and Hive, Trino and BI tools read it, the tables are external so no single engine can delete the data by accident. Newer lakes use Iceberg tables for safe concurrent writes.

Spark writes→External / Iceberg→Many readers

4. Work tables in pipelines

A nightly job builds intermediate tables and drops them at the end. Because they are purge tables, DROP removes the files and storage does not fill up.

Step 1→Work table→DROP at end

5. Pre-upgrade audits

Before moving to Hive 3 or 4, platform teams list every table’s type, purge flag and location, because the meaning of “managed” changed and DROP behaviour must stay what users expect.

Inventory→Check types→Safe upgrade

Examples are simplified. Policies differ between companies.

Run the code: the rules of ownership

These programs encode what you observed in the lab: which tables lose their files on DROP, which statements each type accepts, and how an ACID table records changes as new folders. Press Run, then try the challenges.

# What does DROP TABLE delete? The rule Hive 4 follows.
tables = {
    "orders_ext":   {"type": "EXTERNAL_TABLE", "purge": False},
    "orders_plain": {"type": "EXTERNAL_TABLE", "purge": True},   # plain CREATE TABLE in Hive 4
    "orders_acid":  {"type": "MANAGED_TABLE",  "purge": None},
}

def drop_deletes_files(t):
    return t["type"] == "MANAGED_TABLE" or t["purge"] is True

for name, t in tables.items():
    action = "metadata + files" if drop_deletes_files(t) else "metadata only"
    print(f"DROP {name:13} -> deletes {action}")
DROP orders_ext -> deletes metadata only DROP orders_plain -> deletes metadata + files DROP orders_acid -> deletes metadata + files

  • return t["type"] == "MANAGED_TABLE" or t["purge"] is TrueThe whole rule in one line: managed, or external with purge, means DROP deletes files.

Interview and viva questions

Is “internal table” the same as “managed table”?

Yes. Older books and many interview questions say internal table; Hive’s metadata calls it MANAGED_TABLE. In Hive 3 and later managed tables are transactional, so “internal” also implies ACID in modern Hive.

Can I convert an external table into a managed one?

The table type is stored as a property (EXTERNAL=TRUE/FALSE) that ALTER TABLE can change, and the metastore accepted the change in our lab. But a managed table in Hive 4 is expected to be transactional, and a text table in a shared folder cannot become ACID in place. The safe way is to create a new transactional table, copy the rows with INSERT … SELECT, verify, and swap names.

Does DROP on a managed table go to the trash?

On HDFS with trash enabled, dropped data is moved to the user’s .Trash folder for a configured time, which allows recovery; DROP TABLE … PURGE skips the trash. Object stores have no HDFS trash, so use bucket versioning or backups there. Our local lab has no trash.

Why does Hive 4 translate my table to external instead of making it managed?

Managed tables are reserved for data whose every write Hive controls, so it can offer ACID transactions. A non-transactional table cannot give those guarantees, so the metastore stores it as external with purge on: you keep the old “DROP deletes data” behaviour without pretending it is ACID. Setting hive.create.as.acid=true makes plain CREATE TABLE produce ACID tables instead.

Can Spark read Hive managed ACID tables?

Not with plain Spark readers: they would see delta and delete_delta folders and could return deleted or duplicated rows. Spark needs a connector that understands Hive ACID, or the data should be in an external format built for many engines, such as Iceberg (Module 7). This is a common reason teams keep shared tables external.

[1, 3, 4, 5, 6] 5
Show solution and explanation 
inserted = set(range(1, 7))
deleted, readded = {2, 5}, {5}
visible = (inserted - deleted) | readded
print(sorted(visible), len(visible))
[1, 3, 4, 5, 6] 5

How it works: 5 rows: id 2 is gone, id 5 is visible in its new version. An update is a delete plus an insert.

P5Medium

Which statements will fail?

Given a list of (statement, table type), print which would fail on Hive 4.

Input
TRUNCATE/EXTERNAL · UPDATE/EXTERNAL+purge · DELETE/MANAGED · TRUNCATE/EXTERNAL+purge
Expected output
TRUNCATE on EXTERNAL        fails
UPDATE   on EXTERNAL+purge  fails
DELETE   on MANAGED         works
TRUNCATE on EXTERNAL+purge  works
Show solution and explanation 
ok = {("TRUNCATE", "EXTERNAL"): False, ("UPDATE", "EXTERNAL+purge"): False,
      ("DELETE", "MANAGED"): True, ("TRUNCATE", "EXTERNAL+purge"): True}
for (stmt, kind), works in ok.items():
    print(f"{stmt:8} on {kind:15} {'works' if works else 'fails'}")
TRUNCATE on EXTERNAL fails UPDATE on EXTERNAL+purge fails DELETE on MANAGED works TRUNCATE on EXTERNAL+purge works

How it works: Matches the lab: external refuses TRUNCATE; only ACID managed tables accept UPDATE and DELETE; TRUNCATE works on purge tables.

P6Medium

Find shared-folder risks

Flag tables with purge on whose location starts with /landing/ or /shared/.

Input
a: /landing/x purge · b: /warehouse/… purge · c: /shared/y no purge
Expected output
RISK: a /landing/x
Show solution and explanation 
tables = {"a": ("/landing/x", True), "b": ("/warehouse/t.db/b", True), "c": ("/shared/y", False)}
for n, (loc, purge) in tables.items():
    if purge and loc.startswith(("/landing/", "/shared/")):
        print("RISK:", n, loc)
RISK: a /landing/x

How it works: Only a is risky: a DROP would delete a shared landing folder.

An orphan check finds 340 GB of folders with no table. Storage costs Rs 1.8 per GB per month. What is the yearly cost of leaving them?

P8Business problem

Trash saves the day

HDFS trash keeps deleted files for 1,440 minutes. A wrong DROP happened at 09:10 and was noticed at 18:40 the next day. Can it be restored from trash?

Input
interval 1,440 min · 09:10 day 1 → 18:40 day 2
Expected output
minutes since DROP: 2010 | restorable: False
Show solution and explanation 
elapsed = (24 * 60 - (9 * 60 + 10)) + (18 * 60 + 40)
print("minutes since DROP:", elapsed, "| restorable:", elapsed <= 1440)
minutes since DROP: 2010 | restorable: False

How it works: 2,010 minutes > 1,440, so the trash has been emptied. Teams with critical tables add snapshots or versioning, and alert on DROP of important tables.

Real-world scenario questions (asked in company interviews)

“Managed vs external” is one of the most-asked Hive interview questions. Strong answers include Hive 3/4 behaviour and a real incident.

Any company · basicsFresher

“Managed vs external: which would you use?”

The interviewer gives two datasets: clickstream files written by a Kafka job, and a cleaned orders table that needs refunds applied.

The interviewer is checking: can you connect table type to ownership and features?

Show a strong answer
  • Clickstream: external table on the Kafka job’s folder, purge off, because another system owns the files and DROP must not delete them.
  • Orders: managed ACID table (ORC, transactional) so refunds can be applied with UPDATE or MERGE.
  • Mention that in Hive 3/4 managed means transactional, and that a plain CREATE TABLE becomes external with purge in Hive 4.

Avoid: “external is always safer”: you lose UPDATE, DELETE, MERGE and TRUNCATE.

Operations · incidentMid-level

A shared folder disappeared after a DROP

The marketing team’s landing folder vanished. The audit log shows a DROP TABLE on a table in a sandbox database.

The interviewer is checking: do you know the purge flag and how to investigate?

Show a strong answer
  1. Check the dropped table’s last DDL: it was external but had external.table.purge=true and pointed at the shared folder.
  2. Restore from HDFS trash or snapshots (or object-store versioning) quickly, before trash expiry.
  3. Prevent: no purge on shared paths, restrict ALTER TABLE properties, separate sandbox paths, alert on DROP of tables with purge on non-warehouse paths.

Avoid: blaming HDFS; the metastore did exactly what the table properties said.

Platform · upgradeMid-level

Upgrading from Hive 2 to Hive 4

Your company has 3,000 Hive 2 managed text tables. What changes for users after an upgrade to Hive 4?

The interviewer is checking: do you know the managed-table changes since Hive 3?

Show a strong answer
  • Managed tables are now ACID; non-transactional managed tables are typically migrated to external tables with purge (the upgrade tooling does this), so DROP still deletes data.
  • Plain CREATE TABLE in Hive 4 makes external purge tables unless hive.create.as.acid is enabled.
  • Other engines must not write into ACID table folders; shared tables should stay external (or move to Iceberg).
  • Audit: list each table’s type, purge flag and location before and after.

Avoid: “nothing changes, it is the same SQL”.

Data engineering · debuggingFresher

Rows appear that should be deleted

A Spark job reads the folder of a Hive ACID table and reports refunded orders that Hive no longer shows.

The interviewer is checking: do you understand delta and delete_delta files?

Show a strong answer
  • ACID tables record deletes in delete_delta folders; Hive merges them when reading.
  • A plain Spark file reader sees all files, so deleted and old versions of rows appear.
  • Read through Hive (or an ACID-aware connector), or publish a shared copy in an external format (ORC/Parquet or Iceberg) for other engines.

Avoid: blaming the data; the reader is not ACID-aware.
