Hive architecture and the metastore

Hive is a team of services: HiveServer2 takes your SQL, the compiler plans it with help from the metastore, YARN supplies workers and HDFS holds the files. This lesson draws the full architecture, follows one query through it step by step, opens the metastore’s database, and turns a red dashboard into a two-minute diagnosis.

2 Definition

Hive architecture: components and the path of a query

Formal definition (write this in exams)

The Hive architecture consists of: clients (Beeline, JDBC/ODBC applications) that connect to HiveServer2; the Driver, which controls the lifecycle of a query inside HiveServer2; the Compiler and Optimizer, which parse the HiveQL statement, validate it against the Metastore and produce an optimised execution plan; the Metastore, a service backed by a relational database that stores the metadata of databases, tables, columns, partitions and their storage locations; an execution engine (Apache Tez by default) that runs the plan as a directed acyclic graph of tasks in YARN containers; and the storage layer (HDFS or cloud object storage) where the data files reside in formats such as ORC, Parquet or text.

In simple words

You send SQL to HiveServer2. Hive checks the table details in the metastore, makes a plan, and asks YARN for workers. The workers read the files from HDFS. The result comes back to you. Metadata lives in the metastore; data lives in the files.

The big picture

Numbers show the order of the main arrows: 1 client sends SQL · 2 compiler reads metadata · 3 plan submitted to YARN · 4 containers read and write files · 5 results come back through HiveServer2.

Words you’ll meet in this lesson

HiveServer2The Hive service that accepts client connections (Thrift, JDBC/ODBC) and runs queries. Default port 10000.
DriverThe part of HiveServer2 that controls one query from compile to fetch.
CompilerTurns HiveQL text into an execution plan after checking names and types with the metastore.
Metastore (HMS)Service and database that store table definitions: names, columns, types, partitions, locations. Port 9083.
DAGDirected acyclic graph: tasks (vertices) connected by data flow (edges), with no cycles. Tez runs one DAG per query.
Execution engineRuns the plan on the cluster: Tez (default), MapReduce (deprecated), or Spark.
ThriftA cross-language RPC framework. Hive services talk to clients and to each other through it.
SerDeCode that reads and writes the bytes of a file as columns. Chosen by the table’s file format.

Hive’s architecture at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A restaurant

  • Customer (client): you, with Beeline or a dashboard.
  • Waiter (HiveServer2): takes your order, checks you are allowed in, and returns your food.
  • Head chef (Driver + Compiler): reads the order and writes the cooking plan.
  • Recipe book and register (Metastore): knows which dishes (tables) exist and in which pantry shelf (folder) the ingredients are.
  • Cooks (YARN containers, Tez): do the cooking in parallel, close to the ingredients.
  • Pantry (HDFS / S3): holds the ingredients (files).

Intermediate What each component does and where it listens

  • HiveServer2 (HS2): Thrift service for JDBC/ODBC and Beeline, port 10000 (HTTP mode 10001, web UI 10002). Handles sessions, authentication (Kerberos, LDAP) and runs a Driver for each query.
  • Compiler: parses HiveQL, checks every table and column against the metastore (semantic analysis), builds a logical plan, optimises it and creates a physical plan: a DAG of tasks.
  • Metastore (HMS): Thrift service on port 9083 backed by a relational database (MySQL, PostgreSQL, …). Holds databases, tables, columns, partitions, file formats, locations and statistics.
  • Execution engine: Tez (default) runs the DAG on YARN; the ResourceManager grants containers, NodeManagers start them.
  • Storage: the data files in HDFS or cloud object storage, read through a file format and a SerDe.
  • Helpers: ZooKeeper for finding live HS2 instances, Apache Ranger for permissions, optional LLAP daemons for cached, faster queries.

Advanced Design choices, deployment and failure behaviour

  • Metastore modes: embedded (Derby inside the same JVM; one user only, for learning), local (metastore code inside HS2, external database), remote (separate metastore service, shared by many engines; the production choice).
  • The metastore is a single point of truth and a possible bottleneck: every query’s compile step calls it. Tens of thousands of partitions in one table make planning slow. Production sites run two or more HMS instances behind a load balancer, with a replicated database.
  • HS2 is stateful per session (current database, settings, temporary tables); a load balancer needs session stickiness, or clients use ZooKeeper-based discovery.
  • The Driver is not a separate process; it runs inside HS2. Only the metastore, HS2 and the cluster are separate services you start and monitor.
  • Authorisation (who may read which table) is usually checked in HS2 using Ranger policies, while HDFS permissions add a second layer under the files.
  • Failure map: HS2 down → nobody can connect. Metastore down → connections work, queries fail at compile time. YARN full → query waits (ACCEPTED). HDFS or DataNode problem → tasks fail or are slow.

Exam tip: For “Explain Hive architecture with a neat diagram” draw: Clients → HiveServer2 (Driver, Compiler, Optimizer) → Execution engine (Tez on YARN) → HDFS, and a separate Metastore + RDBMS that the compiler consults. Label the numbered flow (submit, get metadata, plan, execute, fetch). Add one line: “Metadata in the metastore, data in HDFS.”

3 Types and ways to use it

Three ways to run the metastore, and what each Hive service does

Embedded metastore

Metastore code and a Derby database run inside the HiveServer2 JVM. One session at a time. Fine for a first experiment on a laptop; never for sharing.

Learning only

Local metastore

Metastore code runs inside HiveServer2, but the database is separate (for example MySQL). Many sessions work; every HS2 talks to the database directly.

Small setups

Remote metastore

The metastore is its own service on port 9083 in front of the database. HiveServer2, Spark, Trino and others call it. Can run several copies for availability.

Rule of thumb for outages: “cannot connect” → HiveServer2. “Table or database not found” with a working connection → metastore (or its database). “Query waits” → YARN. “File not found / permission denied” → HDFS.

4 Step by step

One query, step by step through the architecture

  1. The client sends SQL to HiveServer2

    beeline -u jdbc:hive2://hs2.tiffingo.in:10000/default -n meera
    Beeline opens a Thrift connection on port 10000, authenticates (for example with Kerberos or LDAP) and opens a session that remembers the current database and settings. If port 10000 is closed, you never get past this step.

  2. The Driver starts the query; the Compiler asks the metastore

    import sqlite3
ms = sqlite3.connect(":memory:")
ms.executescript("""
CREATE TABLE DBS  (DB_ID INT, NAME TEXT);
CREATE TABLE TBLS (TBL_ID INT, DB_ID INT, TBL_NAME TEXT, TBL_TYPE TEXT, SD_ID INT);
CREATE TABLE SDS  (SD_ID INT, LOCATION TEXT, INPUT_FORMAT TEXT);
CREATE TABLE COLUMNS_V2 (SD_ID INT, COLUMN_NAME TEXT, TYPE_NAME TEXT, IDX INT);
INSERT INTO DBS VALUES (1, 'default');
INSERT INTO SDS VALUES (10, 'hdfs://nn1:8020/data/orders', 'TextInputFormat');
INSERT INTO TBLS VALUES (100, 1, 'orders', 'EXTERNAL_TABLE', 10);
INSERT INTO COLUMNS_V2 VALUES (10,'id','int',0),(10,'city','string',1),(10,'amount','int',2);
""")
q = """SELECT t.TBL_NAME, s.LOCATION FROM TBLS t JOIN SDS s ON t.SD_ID = s.SD_ID
       JOIN DBS d ON d.DB_ID = t.DB_ID WHERE d.NAME = 'default' AND t.TBL_NAME = 'orders'"""
print(ms.execute(q).fetchone())
    ('orders', 'hdfs://nn1:8020/data/orders')
    To compile SELECT … FROM orders, the compiler needs to know what orders is. It calls the metastore, which looks in its database (here a simplified imitation of the real DBS, TBLS and SDS tables) and returns the location.

  3. The metastore also returns the columns

    import sqlite3
ms = sqlite3.connect(":memory:")
ms.executescript("""
CREATE TABLE DBS  (DB_ID INT, NAME TEXT);
CREATE TABLE TBLS (TBL_ID INT, DB_ID INT, TBL_NAME TEXT, TBL_TYPE TEXT, SD_ID INT);
CREATE TABLE SDS  (SD_ID INT, LOCATION TEXT, INPUT_FORMAT TEXT);
CREATE TABLE COLUMNS_V2 (SD_ID INT, COLUMN_NAME TEXT, TYPE_NAME TEXT, IDX INT);
INSERT INTO DBS VALUES (1, 'default');
INSERT INTO SDS VALUES (10, 'hdfs://nn1:8020/data/orders', 'TextInputFormat');
INSERT INTO TBLS VALUES (100, 1, 'orders', 'EXTERNAL_TABLE', 10);
INSERT INTO COLUMNS_V2 VALUES (10,'id','int',0),(10,'city','string',1),(10,'amount','int',2);
""")
q = """SELECT t.TBL_NAME, s.LOCATION FROM TBLS t JOIN SDS s ON t.SD_ID = s.SD_ID
       JOIN DBS d ON d.DB_ID = t.DB_ID WHERE d.NAME = 'default' AND t.TBL_NAME = 'orders'"""
print(ms.execute(q).fetchone())
print(ms.execute("SELECT COLUMN_NAME, TYPE_NAME FROM COLUMNS_V2 WHERE SD_ID = 10 ORDER BY IDX").fetchall())
    ('orders', 'hdfs://nn1:8020/data/orders') [('id', 'int'), ('city', 'string'), ('amount', 'int')]
    Column names and types come back too, so the compiler can check that city exists and that SUM(amount) is valid on an integer. This is the semantic analysis step.

  4. Errors appear at compile time, before any cluster work

    metastore = {("default", "orders"): {"cols": ["id", "city", "amount"]}}
def compile_query(db, table, cols):
    meta = metastore.get((db, table))
    if meta is None:
        return f"SemanticException: Table not found {db}.{table}"
    bad = [c for c in cols if c not in meta["cols"]]
    return f"Invalid column {bad[0]}" if bad else "plan OK"
print(compile_query("default", "orders", ["city"]))
print(compile_query("default", "orders", ["town"]))
print(compile_query("default", "ordres", ["city"]))
    plan OK Invalid column town SemanticException: Table not found default.ordres
    A wrong table or column name is caught here in a fraction of a second, without using a single YARN container. Real Hive reports “Table not found” or “Invalid column reference”.

  5. The plan is a small graph of stages

    plan = ["Map 1: TableScan orders -> Filter -> partial GroupBy",
        "Reducer 2: final GroupBy -> FileSink"]
for i, stage in enumerate(plan, 1):
    print(i, stage)
    1 Map 1: TableScan orders -> Filter -> partial GroupBy 2 Reducer 2: final GroupBy -> FileSink
    After optimisation the plan is a DAG: a map vertex that reads and partially aggregates, and a reducer vertex that finishes. Lesson 1.4 opens this up with EXPLAIN.

  6. YARN grants containers; tasks read HDFS

    containers = {"Map 1": 16, "Reducer 2": 1}
node_free = 6
for vertex, n in containers.items():
    run_now = min(n, node_free)
    print(f"{vertex}: needs {n}, starts {run_now}, waits {n - run_now}")
    Map 1: needs 16, starts 6, waits 10 Reducer 2: needs 1, starts 1, waits 0
    The engine asks the ResourceManager for containers. If the queue has fewer free than needed, some tasks wait their turn. Finished results go back through HiveServer2 to the client.
5 See it happen

One query travelling through the architecture

Left: what Beeline prints. Right: which Hive component is working at that moment. Follow the glowing boxes and arrows.

One query across the architecture 7 steps
What you see
  1. Meera starts Beeline and points it at HiveServer2, port 10000.
  2. She is connected and types her query.
  3. Hive reports compiling and semantic analysis: names and types are being checked.
  4. Compiling is complete. Only now does Hive begin to use the cluster.
  5. Tez tasks start: first the 16 map tasks, then the reducer.
  6. All tasks complete and Hive fetches the results.
  7. Three rows appear. The whole trip took about 21 seconds (illustrative).
Behind the screen
  1. The client connects to HiveServer2. A session is created and the user is authenticated.
  2. The Driver takes the statement and controls everything that happens to it from now on.
  3. The compiler asks the metastore (which reads its relational database) for the table’s location, columns and format.
  4. The optimiser finishes the plan. A typo in a table name would have failed back at step 3, without any cluster use.
  5. The engine submits the DAG to YARN. The ResourceManager grants containers.
  6. Containers run on worker nodes and read the table’s files from HDFS.
  7. Result data is written to a temporary location and streamed back by HiveServer2 to Beeline.

Three live scenarios follow: diagnosing a real outage from its symptom, the three metastore deployment modes, and a look inside the metastore’s database.

Real-time scenario 1

Tuesday’s outage: which component is it?

Four different error messages, one per component. Learn to read the symptom and jump straight to the right place.

Reading symptoms 5 steps
Animated example
  1. The dashboard cannot open a connection to port 10000. That is HiveServer2: is the process running and is the port listening?
  2. The connection works but the table is not found. The metastore (or its database) is not answering, or the table was never created.
  3. The query is accepted but never starts. YARN has no free containers for that queue.
  4. The query starts but tasks fail reading files. Look at HDFS: path, permissions, DataNodes.
  5. Memorise the four pairs. On Tuesday morning Arjun Sir found the metastore’s MySQL database had run out of disk space.
Real-time scenario 2

Embedded, local or remote: why production uses a remote metastore

The same catalogue can be deployed in three ways. See what breaks as more users and engines arrive.

Metastore deployment modes 5 steps
Animated example
  1. Embedded mode runs the metastore and a Derby database inside HiveServer2. It is the quickest way to start on a laptop.
  2. A second user trying to connect is refused because Derby allows one process to open the database.
  3. Local mode puts the database outside (MySQL), so many sessions work, but every HiveServer2 contains metastore code.
  4. Remote mode runs the metastore as a service on port 9083. Hive, Spark and Trino all call it; two copies give high availability.
  5. The metastore’s database is the platform’s memory. If it is lost, the table definitions go with it, even though the data files remain. Back it up.
Real-time scenario 3 · advanced

What does CREATE TABLE really write?

A look inside the metastore’s relational database. Table names follow the real Hive schema (DBS, TBLS, SDS, COLUMNS_V2, PARTITIONS); columns are simplified.

Inside the metastore database 5 steps
Animated example
  1. Meera runs CREATE EXTERNAL TABLE. No data file is touched.
  2. The metastore stores a few rows: the database, the table with its type, the storage descriptor with the location and the columns.
  3. Adding a partition adds one row to PARTITIONS, pointing to its own folder.
  4. ANALYZE TABLE stores statistics such as row counts and distinct values, which the optimiser uses.
  5. The metastore holds small data but is asked constantly. Very large partition counts and a slow database are classic reasons for slow query planning.
6 Real-world use

Architecture knowledge in daily work

1. First 5 minutes of an incident

The on-call engineer checks which ports answer: 10000 (HiveServer2), 9083 (metastore), 8088 (YARN). The first silent port tells them which team to wake up.

Alert→Check ports→Right owner

2. Backing up the metastore

Because the metastore database is the platform’s memory, platform teams back it up every night and test restores. The data files may be safe in HDFS, but without the metastore nobody knows what they are.

Metastore DB→Backup→Restore test

3. One catalogue for many tools

A company adds Spark and Trino. Instead of redefining every table, they point both at the existing remote metastore. Every table is immediately visible, with the same names and locations.

Remote HMS→Spark + Trino→No duplicate tables

4. Who may read what

Security teams define policies such as “marketing may read orders but not customers.phone”. HiveServer2 checks them for every query; HDFS permissions protect the raw files underneath.

Policy→HiveServer2 check→Allowed / denied

5. Slow compile times

A table with 300,000 partitions makes every query spend half a minute in compilation before any task starts, because the metastore returns a huge list. The team reduces partitions and tunes the metastore database.

Many partitions→Slow planning→Fewer partitions

Examples are simplified. Port numbers are Hive defaults; your platform may differ.

7 Run the code

A tiny metastore: the catalogue behind every Hive query

This program builds a simplified metastore in SQLite, using table names from the real Hive schema (DBS, TBLS, SDS, COLUMNS_V2, PARTITIONS). The function describe() does what the compiler does at the start of every query: it looks up a table’s type, location and columns. Then try the challenges.

import sqlite3
ms = sqlite3.connect(":memory:")
ms.executescript("""
CREATE TABLE DBS  (DB_ID INT, NAME TEXT);
CREATE TABLE TBLS (TBL_ID INT, DB_ID INT, TBL_NAME TEXT, TBL_TYPE TEXT, SD_ID INT);
CREATE TABLE SDS  (SD_ID INT, LOCATION TEXT);
CREATE TABLE COLUMNS_V2 (SD_ID INT, COLUMN_NAME TEXT, TYPE_NAME TEXT, IDX INT);
CREATE TABLE PARTITIONS (PART_ID INT, TBL_ID INT, PART_NAME TEXT);
INSERT INTO DBS VALUES (1, 'default'), (2, 'sales');
INSERT INTO SDS VALUES (10, 'hdfs://nn1:8020/data/orders'), (11, 'hdfs://nn1:8020/warehouse/sales.db/targets');
INSERT INTO TBLS VALUES (100, 1, 'orders', 'EXTERNAL_TABLE', 10), (101, 2, 'targets', 'MANAGED_TABLE', 11);
INSERT INTO COLUMNS_V2 VALUES (10,'id','int',0),(10,'city','string',1),(10,'amount','int',2),(11,'city','string',0),(11,'target','int',1);
""")

def describe(db, table):
    row = ms.execute("""SELECT t.TBL_TYPE, s.LOCATION, t.SD_ID FROM TBLS t
                        JOIN SDS s ON s.SD_ID = t.SD_ID JOIN DBS d ON d.DB_ID = t.DB_ID
                        WHERE d.NAME = ? AND t.TBL_NAME = ?""", (db, table)).fetchone()
    if row is None:
        raise SystemExit(f"Table not found: {db}.{table}")
    cols = ms.execute("SELECT COLUMN_NAME, TYPE_NAME FROM COLUMNS_V2 WHERE SD_ID = ? ORDER BY IDX", (row[2],)).fetchall()
    return row[0], row[1], cols

kind, loc, cols = describe("default", "orders")
print("type    :", kind)
print("location:", loc)
print("columns :", cols)
type : EXTERNAL_TABLE location: hdfs://nn1:8020/data/orders columns : [('id', 'int'), ('city', 'string'), ('amount', 'int')]
  • JOIN SDS s ON s.SD_ID = t.SD_IDThe table row points to a storage descriptor (SDS) that holds the location. In the real schema the SDS also holds the file format and SerDe.
  • raise SystemExit("Table not found …")If the table is not in the metastore the compiler stops at once: no cluster is used.
  • ORDER BY IDXColumns are returned in definition order; the schema is applied to files by position.

  • The Driver runs inside HiveServer2 and controls each query’s lifecycle.
  • The compiler parses, then semantic analysis uses the metastore, then plans and optimises (Calcite).
  • Metastore = service + RDBMS. Stores tables, columns, types, locations, partitions, statistics. Metadata, not data.
  • Modes: embedded (Derby, one user), local, remote (production, shared with Spark and Trino).
  • Symptoms: cannot connect → HS2; table not found → metastore; ACCEPTED → YARN; file/permission → HDFS.
  • Back up the metastore database: losing it loses the table definitions, not the files.

Interview and viva questions

What is the difference between HiveServer2 and the metastore?

HiveServer2 is the query service: it accepts client connections, compiles and runs queries. The metastore is the catalogue service: it stores and returns metadata about databases, tables, columns and partitions. HiveServer2 calls the metastore during compilation; Spark and Trino can call it directly without using HiveServer2.

Is the metastore the same as the data warehouse?

No. The metastore holds only metadata in a relational database. The warehouse is the data itself: files in HDFS or object storage (managed tables live under the warehouse directory, external tables anywhere).

What happens if the metastore database is lost?

The files in HDFS remain, but Hive no longer knows which tables exist, their columns, formats or partitions. You would have to restore from a backup, or recreate external tables and repair partitions by hand. That is why the metastore database is backed up and often replicated.

Why does Hive need Derby, MySQL or PostgreSQL?

The metastore needs a transactional relational database to store its many small metadata rows reliably and query them quickly. Derby is bundled for quick tests; MySQL, PostgreSQL, Oracle or SQL Server are used in real deployments.

Where does the Driver run?

Inside the HiveServer2 process. It is a logical component that coordinates compile, optimise, execute and fetch for each query, not a separate service you start.

Which component?

Write a function that returns the component to check for a symptom string, and test four symptoms.

Real-world scenario questions (asked in company interviews)

Architecture questions are favourites in Hive and data engineering interviews. Each of these is built from a real situation.

Operations · troubleshootingFresher

Every dashboard failed at 9 a.m.

Users report two errors: “could not open connection” on some tools and “table not found” on others. How do you approach it?

The interviewer is checking: can you map symptoms to components instead of restarting everything?

Show a strong answer
  1. Separate the symptoms. “Could not open connection” is the client failing to reach HiveServer2: check that the process is up and that port 10000 is listening.
  2. “Table not found” with a working connection points to the metastore: check port 9083 and its database (disk space, connections).
  3. Fix in that order, and confirm with a simple SHOW TABLES and a small SELECT.

Avoid: restarting every service at once; you lose the evidence and may make it worse.

Any company · conceptsFresher

“Where is my data: in Hive or in HDFS?”

A colleague asks whether the data of a table is “inside Hive”.

The interviewer is checking: do you separate metadata from data?

Show a strong answer
  • The data is files in HDFS or object storage at the table’s location.
  • The metadata (table name, columns, location, format, partitions) is in the metastore database.
  • HiveServer2 and the engine are the services that connect the two when a query runs.

Avoid: saying that Hive stores the data in its own database.

Data platform · designMid-level

Sharing tables with Spark

The data science team wants to use Spark on the same tables analysts query with Hive. How do you set it up?

The interviewer is checking: do you know the metastore is the shared catalogue?

Show a strong answer
  • Run (or use) a remote metastore service and configure Spark’s Hive support to use its URI (hive.metastore.uris).
  • Spark then sees the same databases and tables with no redefinition; it reads the same files.
  • Plan permissions (Ranger, HDFS ACLs) so both engines respect the same access rules.

Avoid: copying tables or creating duplicate definitions in Spark.

Operations · reliabilityMid-level

Metastore high availability

The business wants to avoid a single point of failure in the Hive platform. What would you do for the metastore?

The interviewer is checking: do you understand that the metastore is both a service and a database?

Show a strong answer
  1. Run two or more metastore service instances behind a load balancer or a list in hive.metastore.uris.
  2. Make the metastore database highly available (replication with automatic failover) and back it up regularly, testing restores.
  3. Monitor disk, connections and slow queries on the database; large partition counts need attention too.

Avoid: adding metastore instances while leaving a single, unbacked-up database underneath.
