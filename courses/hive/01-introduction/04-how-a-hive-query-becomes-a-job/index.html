How a Hive query becomes a job

Between pressing Enter and the first container starting, a small factory inside HiveServer2 parses your SQL, checks it, rewrites it to do less work, cuts it into stages at every shuffle and hands the stages to YARN. This lesson walks through each phase with a real example, compares MapReduce and Tez, and teaches you to read EXPLAIN before spending cluster time.

Hive did. Between the moment you press Enter and the first container starting, a small factory runs inside HiveServer2. Think of a restaurant order slip: you write “one thali, no onion”. Kabir

2 Definition

Query compilation and execution in Hive

Formal definition (write this in exams)

Query compilation in Hive is the process by which HiveServer2 converts a HiveQL statement into an executable plan in five phases: parsing into an abstract syntax tree; semantic analysis against the metastore, producing a logical plan of operators; optimisation by rule-based transformations and a cost-based optimiser (Apache Calcite); generation of a physical plan, a directed acyclic graph (DAG) of vertices connected by edges at each shuffle boundary; and execution of that DAG by an engine such as Apache Tez as tasks in YARN containers. The plan can be inspected with the EXPLAIN statement without running the query.

In simple words

Hive reads your SQL, checks it, rewrites it to do less work, cuts it into stages at every place where data must be regrouped (the shuffle), and hands those stages to YARN to run as many small parallel tasks. EXPLAIN shows the stages before anything runs.

Words you’ll meet in this lesson

ASTAbstract syntax tree: the query text as a tree of clauses (SELECT, FROM, WHERE, …).
OperatorOne step of a plan: TableScan, Filter, Select, Group By, Join, Reduce Sink, File Sink.
VertexA Tez stage (“Map 1”, “Reducer 2”): many identical tasks working on different pieces of data.
EdgeA data connection between vertices. A SIMPLE_EDGE is a shuffle; a BROADCAST_EDGE sends a small table to all tasks.
Reduce SinkThe operator that ends a vertex: it partitions rows by key and sends them over the shuffle.
Predicate pushdownApplying a filter as early as possible, ideally inside the file reader, to avoid reading rows at all.
Cost-based optimiserChooses among equivalent plans using table statistics (row counts, distinct values).
EXPLAINA statement that prints the plan of a query without executing it.

From SQL to tasks at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A restaurant order

  • You write the order (the SQL). It says what you want, not how to cook it.
  • The waiter checks it (parse + analyse): are the dishes on the menu? That is the metastore check.
  • The head chef improves the plan (optimise): “peel only the vegetables we need, and start the sauce while the rice boils”.
  • Stations are assigned (the DAG): one station per kind of work, in order.
  • Cooks work in parallel (tasks in containers), and the plate comes back to you.

Intermediate The five phases

  • 1 · Parse: the HiveQL text becomes an abstract syntax tree (AST). Syntax errors (a missing comma) are reported here.
  • 2 · Semantic analysis: tables, columns and types are checked with the metastore, and the AST becomes a logical plan: a tree of operators such as TableScan, Filter, Select, Group By, Reduce Sink and File Sink.
  • 3 · Optimisation: rule-based rewrites (push filters down, read only needed columns, skip partitions, fold constants) and cost-based optimisation (choose join order and join type using statistics), done with Apache Calcite.
  • 4 · Physical plan: the operator tree is cut at every Reduce Sink (where data must be shuffled) into vertices. Vertices joined by edges form a DAG: Map 1 → Reducer 2 → Reducer 3.
  • 5 · Execute: the Tez AM runs in YARN, starts tasks in containers (one task per input split in a map vertex, a chosen number in reducer vertices), moves data along the edges and writes the result.

Advanced What the optimiser and engine really do

  • Predicate pushdown: the WHERE filter is moved as close to the data as possible; with ORC/Parquet whole stripes or row groups are skipped using min/max statistics.
  • Column pruning: only columns used by the query are read; with a columnar format the others are never touched.
  • Partial (map-side) aggregation: each map task first aggregates its own rows (mode: hash); the reducer finishes (mode: mergepartial). The shuffle then carries a few rows per city instead of millions.
  • Join strategies: a shuffle join repartitions both tables by key; a map (broadcast) join sends a small table to every task and needs no shuffle. Hive chooses automatically when a table is small enough (hive.auto.convert.join).
  • ORDER BY is a total sort: it needs a single reducer (or merge) at the end, which can be a bottleneck on huge data; SORT BY and DISTRIBUTE BY sort per reducer only.
  • Tez vs MapReduce: MapReduce ran one job per stage and wrote every intermediate result to HDFS. Tez runs the whole DAG as one job and streams data between vertices, usually with far fewer disk writes. Vectorised execution processes batches of rows at a time.
  • Reducer parallelism is estimated from input size (for example bytes per reducer) and can be adjusted automatically at run time; the “4” in our story came from such an estimate.

Exam tip: “Explain how a Hive query is executed.” Give the five phases in order (parse → semantic analysis with metastore → logical plan and optimisation → physical plan / DAG → execution on Tez/YARN), name one optimisation (predicate pushdown or partial aggregation) and mention EXPLAIN. A neat flow diagram earns the marks.

3 Types and ways to use it

Plans, engines and the EXPLAIN family

Tez (default)

One DAG per query, data streamed between vertices, container re-use, vectorised execution. The standard engine in modern Hive.

hive.execution.engine=tez

MapReduce (deprecated)

One MapReduce job per stage with intermediate results in HDFS. You will still meet it in old clusters and old tutorials.

Legacy

Hive on Spark

Optional engine that runs the plan on Spark. Rare today; most teams use Spark SQL directly instead.

Rare

LLAP

Long-lived daemons that cache data and keep code warm, so short queries skip container start-up. Works with Tez.

4 Step by step

Following one query through the five phases

  1. Phase 1 · Parse the text

    query = "SELECT city, SUM(amount) FROM orders WHERE amount > 100 GROUP BY city ORDER BY 2 DESC"
words = ["SELECT", "FROM", "WHERE", "GROUP BY", "ORDER BY"]
parts, rest = {}, query
for w in reversed(words):
    head, _, tail = rest.partition(w)
    if tail:
        parts[w], rest = tail.strip(), head
print(parts)
    {'ORDER BY': '2 DESC', 'GROUP BY': 'city', 'WHERE': 'amount > 100', 'FROM': 'orders', 'SELECT': 'city, SUM(amount)'}
    Hive’s real parser (built with ANTLR) produces an abstract syntax tree. This toy splits the clauses to show the idea: a query is a set of named parts. A missing comma or misspelt keyword fails here with a “ParseException”.

  2. Phase 2 · Analyse and build the operator tree

    plan = [("TableScan", "orders"), ("Filter", "amount > 100"), ("Select", "city, amount"),
        ("GroupBy(hash)", "sum(amount) by city"), ("ReduceSink", "key = city"),
        ("GroupBy(merge)", "sum by city"), ("ReduceSink", "sort by total desc"), ("FileSink", "result")]
for op, arg in plan:
    print(f"{op:15}{arg}")
    TableScan orders Filter amount > 100 Select city, amount GroupBy(hash) sum(amount) by city ReduceSink key = city GroupBy(merge) sum by city ReduceSink sort by total desc FileSink result
    The analyser asks the metastore about orders, confirms city and amount exist, and writes the query as a chain of operators. Note that Filter comes before Group By, although SQL text puts WHERE after FROM and SELECT first.

  3. Phase 3 · Optimise

    The optimiser rewrites the tree. Three rewrites matter in this query: the filter is pushed into the scan, only two columns are read (city, amount), and a partial aggregation is added before the shuffle (step 4).

    None of these change the answer; all of them reduce work. The cost-based optimiser also decides join order and join type from table statistics, which is why ANALYZE TABLE matters.

  4. Phase 4 · Cut into vertices at every shuffle

    plan = ["TableScan", "Filter", "Select", "GroupBy(hash)", "ReduceSink",
        "GroupBy(merge)", "Select", "ReduceSink", "Select", "FileSink"]
vertices, current = [], []
for op in plan:
    current.append(op)
    if op == "ReduceSink":
        vertices.append(current); current = []
vertices.append(current)
for i, v in enumerate(vertices, 1):
    print(f"vertex {i}:", " -> ".join(v))
    vertex 1: TableScan -> Filter -> Select -> GroupBy(hash) -> ReduceSink vertex 2: GroupBy(merge) -> Select -> ReduceSink vertex 3: Select -> FileSink
    Every ReduceSink ends a vertex, because data must be regrouped across machines there. Our query has three: Map 1 (scan, filter, partial aggregation), Reducer 2 (final aggregation) and Reducer 3 (global sort).

  5. Why the partial aggregation matters

    rows = 12_000_000
cities = 38
maps = 16
print("shuffle rows without map-side aggregation:", rows)
print("shuffle rows with map-side aggregation  :", maps * cities)
    shuffle rows without map-side aggregation: 12000000 shuffle rows with map-side aggregation : 608
    Without it, 12 million rows would cross the network. With it each of 16 map tasks sends at most 38 rows (one per city): 608 rows. Hive calls it mode: hash in EXPLAIN.

  6. Phase 5 · Execute on Tez: how many tasks?

    import math
input_gb, bytes_per_reducer_gb = 1.8, 0.5
reducers = max(1, math.ceil(input_gb / bytes_per_reducer_gb))
print("estimated reducers:", reducers)
    estimated reducers: 4
    A map vertex gets one task per input split (16 here), reducer vertices get a number estimated from data size, and the final sort uses one. YARN grants containers and Tez runs them. Total in our story: 16 + 4 + 1 = 21 tasks.

What you see

Behind the screen
  1. Phase 1 · Parse: the SQL text is the input to the parser.
  2. The parser builds a tree whose branches are the clauses: FROM, SELECT, WHERE, GROUP BY, ORDER BY.
  3. Phase 2 · Analyse: the tree becomes a chain of operators, and every name is checked with the metastore. Notice that Filter comes before Group By.
  4. Phase 3 · Optimise: push the filter into the scan, read only two columns, aggregate partially on each map task.

Three live scenarios follow: MapReduce versus Tez, what the optimiser saves, and the difference between shuffle joins and map joins.

Real-time scenario 1

MapReduce vs Tez: the same plan, a different engine

The same three-stage plan can run on two engines. Compare how they move data between stages.

Engines compared 5 steps
Animated example
  1. Our query has three stages. The plan is the same whichever engine runs it.
  2. MapReduce runs each stage as a separate job and writes the output to HDFS before the next job reads it.
  3. Tez runs the whole plan as one DAG and streams data between vertices without writing it to HDFS in between.
  4. Tez also adds vectorised execution, container re-use and run-time adjustment of reducer counts.
  5. You can check your engine with SET hive.execution.engine; modern Hive reports tez.
Real-time scenario 2

What the optimiser saves: reading and shuffling

Follow the amount of data read and shuffled as each optimisation is applied to the same query. Numbers are illustrative to show the order of magnitude.

Optimiser savings 5 steps
Animated example
  1. Without optimisation Hive would read every column of every row and shuffle all qualifying rows.
  2. Column pruning: only city and amount are needed, so with a columnar format 80% of the bytes are never read.
  3. Predicate pushdown: stripes or row groups whose statistics show no amount above 100 are skipped.
  4. Partial aggregation: each map task sums its own rows first, so only a few hundred rows are shuffled.
  5. In EXPLAIN look for the Filter, Select, Group By (mode hash) and Reduce Output operators to confirm all this happens.
Real-time scenario 3 · advanced

Shuffle join, map join and skew

Joins are where plans differ most. See how Hive picks a join strategy and what can go wrong.

Join strategies 5 steps
Animated example
  1. A 2 TB orders table joins a tiny cities table. Hive must choose how.
  2. Shuffle join: both tables are repartitioned by the join key and matched in reducers. The big table crosses the network.
  3. Map (broadcast) join: the tiny table is copied to every map task, which joins locally. No reducers, no shuffle of the big table.
  4. Hive picks automatically if statistics show a table fits within the configured size. Fresh statistics matter.
  5. Skew: if one key is far more common than the others, one reducer gets most of the work and the whole stage waits for it.
6 Real-world use

Reading plans in daily work

1. Check before you schedule

Before putting a report in the nightly schedule, an engineer runs EXPLAIN and checks that the filter is early, partitions are pruned and no huge shuffle join is planned. It takes a second and saves hours.

New report→EXPLAIN→Fix or schedule

2. The reducer that never finishes

In the Tez progress table, 199 of 200 reducers finish in a minute; one runs for an hour. That is skew: one key has most rows. The team adds a salt to the key or handles the hot key separately.

Progress table→One slow reducer→Skew handling

3. Fresh statistics, better plans

After a big load, the optimiser still believes a table has 10,000 rows and chooses a map join that runs out of memory. Running ANALYZE TABLE … COMPUTE STATISTICS after loads gives it the true sizes.

Big load→ANALYZE TABLE→Correct join type

4. Finding the slow stage

The Tez UI shows each vertex’s time and tasks. If Reducer 3 takes 90% of the run time, the sort at the end is the bottleneck, and the fix is a different design, not a bigger cluster.

Slow query→Tez UI→Slowest vertex

5. Cost control on the cloud

Cloud bills depend on how long containers run. A plan that reads 2 TB instead of 120 GB costs real money every night. Teams review the plans of their most expensive jobs first.

Cloud bill→Read volume→Rewrite the query

7 Run the code

Run a query plan by hand: Map 1, Reducer 2, Reducer 3

This program executes the plan from the lesson on the 8 sample orders split into three blocks: a map task per block (scan, filter, partial aggregation), a reducer that merges the partial sums, and a final reducer that sorts. Then try the challenges: count the shuffled rows, make AVG correct, take the top 2, and see a classic mistake.

# SELECT city, SUM(amount) AS total FROM orders WHERE amount > 100 GROUP BY city ORDER BY total DESC
orders = [(1, "Pune", 220), (2, "Thane", 150), (3, "Pune", 180), (4, "Mumbai", 310),
          (5, "Thane", 90), (6, "Pune", 60), (7, "Mumbai", 140), (8, "Pune", 100)]
blocks = [orders[0:3], orders[3:6], orders[6:8]]        # three HDFS blocks

def map_task(block):                       # Map 1: scan, filter, partial group by
    partial = {}
    for _id, city, amount in block:
        if amount > 100:
            partial[city] = partial.get(city, 0) + amount
    return partial

partials = [map_task(b) for b in blocks]
print("Map 1 outputs      :", partials)

merged = {}                                # Reducer 2: merge partial sums
for p in partials:
    for city, v in p.items():
        merged[city] = merged.get(city, 0) + v
print("Reducer 2 merged   :", merged)

result = sorted(merged.items(), key=lambda kv: -kv[1])   # Reducer 3: total order
print("Reducer 3 (sorted) :", result)
Map 1 outputs : [{'Pune': 400, 'Thane': 150}, {'Mumbai': 310}, {'Mumbai': 140}] Reducer 2 merged : {'Pune': 400, 'Thane': 150, 'Mumbai': 450} Reducer 3 (sorted) : [('Mumbai', 450), ('Pune', 400), ('Thane', 150)]
  • if amount > 100:The filter runs inside the map task, right at the scan (predicate pushdown). Rows that fail it are never shuffled.
  • partial[city] = partial.get(city, 0) + amountPartial aggregation: each map task sums its own rows (mode: hash in EXPLAIN).
  • sorted(merged.items(), key=lambda kv: -kv[1])ORDER BY needs all results together, so it happens in a final single-reducer stage.

Interview and viva questions

What are the phases of query processing in Hive?

Parsing (HiveQL to AST), semantic analysis using the metastore (AST to a logical plan of operators), optimisation (rule-based and cost-based, using Calcite), physical plan generation (a DAG of vertices cut at shuffle boundaries) and execution by an engine such as Tez on YARN, followed by fetching the results through HiveServer2.

How do I know how many tasks a query will use?

EXPLAIN shows the vertices; the number of map tasks depends on the number of input splits (roughly the data size divided by the split size) and reducer tasks are estimated from the data volume and can be adjusted at run time. The actual counts appear in the Tez progress table and in the Tez UI.

What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN only compiles and prints the plan with estimates. EXPLAIN ANALYZE actually runs the query and then shows real row counts next to the estimates, so you can find where the optimiser’s statistics were wrong.

Why does my simple query take 20 seconds on a tiny table?

Fixed overheads dominate: compiling, getting a Tez session and containers from YARN, starting tasks and returning results. They are the same for 1 MB or 1 TB. Interactive-latency features such as LLAP reduce them, and engines like Trino are often used for fast interactive queries.

What is a cost-based optimiser and why do I run ANALYZE TABLE?

The cost-based optimiser (built with Apache Calcite) compares possible plans using table and column statistics such as row counts and distinct values, to choose join order and join type. Without up-to-date statistics it guesses, which can lead to a slow shuffle join or a map join that runs out of memory. ANALYZE TABLE … COMPUTE STATISTICS refreshes them.

How it works: 200 splits make about 200 map tasks. Larger splits give fewer, longer tasks; smaller splits give more, shorter ones.

P4Medium

Reducer estimate

Hive estimates reducers as input size ÷ 256 MB per reducer, with a maximum of 1,009. For 10 GB, 600 GB and 1 TB of reducer input, print the estimates.

Input
10 GB · 600 GB · 1,024 GB
Expected output
10 GB -> 40 reducers
600 GB -> 1009 reducers
1024 GB -> 1009 reducers
Show solution and explanation 
import math
for gb in [10, 600, 1024]:
    est = min(1009, max(1, math.ceil(gb * 1024 / 256)))
    print(gb, "GB ->", est, "reducers")
10 GB -> 40 reducers 600 GB -> 1009 reducers 1024 GB -> 1009 reducers

How it works: The cap protects the cluster from an enormous number of tiny tasks. The numbers are a model of Hive’s estimate; exact defaults depend on version and settings.

P5Medium

Average of two blocks, the right way

Block 1 has 3 rows with average 100; block 2 has 2 rows with average 400. Compute the true overall average and the wrong “average of averages”.

Input
(3, 100) and (2, 400)
Expected output
wrong: 250.0 | right: 220.0
Show solution and explanation 
blocks = [(3, 100.0), (2, 400.0)]
wrong = sum(a for _, a in blocks) / len(blocks)
right = sum(n * a for n, a in blocks) / sum(n for n, _ in blocks)
print("wrong:", wrong, "| right:", right)
wrong: 250.0 | right: 220.0

How it works: Right: (300 + 800) ÷ 5 = 220. Averaging the averages gives 250. That is why distributed AVG keeps (sum, count) pairs.

P6Medium

Filter early or late?

A table has 10 million rows; 2% pass the filter. How many rows are processed by the group-by if the filter runs first versus last?

Input
10,000,000 rows · 2% pass
Expected output
filter first: 200000 rows grouped
filter last : 10000000 rows grouped
Show solution and explanation 
rows = 10_000_000
print("filter first:", int(rows * 0.02), "rows grouped")
print("filter last :", rows, "rows grouped")
filter first: 200000 rows grouped filter last : 10000000 rows grouped

How it works: 200,000 versus 10,000,000. Hive pushes filters down automatically, but a filter written on a computed column or after a join can sometimes defeat it: always check EXPLAIN.

P7Business problem

Cloud cost of a scan

A job reads 2,000 GB at a cost of Rs 0.4 per GB scanned. After partition pruning and column pruning it reads 120 GB. How much does one run cost before and after, and what is saved over 30 nightly runs?

Input
2,000 GB → 120 GB at Rs 0.4/GB
Expected output
before: Rs 800.0 | after: Rs 48.0
saved in 30 runs: Rs 22560
Show solution and explanation 
before, after, rate = 2000, 120, 0.4
print("before: Rs", before * rate, "| after: Rs", after * rate)
print("saved in 30 runs: Rs", round((before - after) * rate * 30))
before: Rs 800.0 | after: Rs 48.0 saved in 30 runs: Rs 22560

How it works: Rs 800 versus Rs 48 per run; Rs 22,560 saved in a month for one job. Small plan improvements add up across hundreds of jobs.

P8Business problem

Skew check

Reducer run times in minutes are [3, 4, 3, 62, 4]. Compute the median, the maximum and flag skew if the maximum is more than 5 times the median.

Input
[3, 4, 3, 62, 4]
Expected output
median 4 | max 62 | skew: True
Show solution and explanation 
times = [3, 4, 3, 62, 4]
med = sorted(times)[len(times) // 2]
print("median", med, "| max", max(times), "| skew:", max(times) > 5 * med)
median 4 | max 62 | skew: True

How it works: The job takes 62 minutes because of one reducer, though the median is 4. This is the signature of a skewed key.

Real-world scenario questions (asked in company interviews)

Questions about query execution show up in every Hive interview. Each of these starts from something you would really see on a cluster.

Any company · conceptsFresher

“What happens when I run a query in Hive?”

The interviewer says: “Walk me through everything between pressing Enter and getting the result.”

The interviewer is checking: can you describe the phases and the components in order?

Show a strong answer
  1. Beeline sends the statement to HiveServer2; the Driver starts the query.
  2. The compiler parses it, checks tables and columns with the metastore, builds a logical plan and optimises it.
  3. The physical plan, a DAG of vertices, is submitted to YARN, where Tez runs tasks in containers reading blocks from HDFS.
  4. Results are written to a temporary location and fetched back through HiveServer2.

Avoid: jumping straight to “it runs MapReduce”; mention the compile phases and the metastore.

Performance · tuningMid-level

One reducer runs for an hour

A nightly query has 200 reducers. 199 finish in two minutes; one takes an hour.

The interviewer is checking: do you recognise skew and know where to look?

Show a strong answer
  • This is data skew: one key has far more rows than the others, so the reducer that receives it is overloaded.
  • Confirm in the Tez UI (task times per vertex) and with a GROUP BY key ORDER BY COUNT(*) DESC query on the join or group key.
  • Fix options: filter or handle the hot key separately, salt the key, enable Hive’s skew-join settings, or change the design so the hot key is spread out.

Avoid: adding more reducers: the single hot key still goes to one reducer.

Performance · tuningFresher

A join that should be fast is slow

A report joins a 2 TB orders table with a 200 KB cities table and takes 40 minutes. EXPLAIN shows a shuffle join (SIMPLE_EDGE on both sides).

The interviewer is checking: do you know map joins and statistics?

Show a strong answer
  1. The small table should be broadcast (map join). Hive chooses this when it believes the table is under the threshold, using statistics.
  2. Run ANALYZE TABLE cities COMPUTE STATISTICS (and for columns) so the optimiser sees the real size, then re-check EXPLAIN for a BROADCAST_EDGE.
  3. Verify hive.auto.convert.join is on and the threshold is suitable for your memory per container.

Avoid: rewriting the query before checking the statistics and the plan.

Operations · costMid-level

EXPLAIN before scheduling

A colleague wants to schedule a new report that scans a 3-year, 60 TB table. How do you review it?

The interviewer is checking: do you use EXPLAIN as a pre-flight check?

Show a strong answer
  • Run EXPLAIN EXTENDED and confirm partitions are pruned (only the needed dates are listed) and only the required columns are read.
  • Look for early filters, partial aggregation, and the join strategy of any joins; check the number of vertices and shuffle edges.
  • Estimate the data read; if it is large, ask whether a summary table or a narrower date range would answer the same question.

Avoid: scheduling first and looking at the bill afterwards.
