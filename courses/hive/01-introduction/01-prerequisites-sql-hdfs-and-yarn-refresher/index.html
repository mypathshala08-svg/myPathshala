2 Definition

What exactly should I know before Hive?

Formal definition (write this in exams)

The prerequisites of Apache Hive are three bodies of knowledge. First, relational querying with SQL: tables, rows and columns, SELECT, WHERE, aggregation with GROUP BY, and JOINs. Second, the Hadoop Distributed File System (HDFS): files split into replicated blocks, with a NameNode that holds the metadata and DataNodes that hold the blocks. Third, YARN and the MapReduce model: a ResourceManager that grants containers on NodeManagers, and a processing pattern of map, shuffle and reduce that works in parallel on blocks. A basic familiarity with the Linux command line is useful for the hands-on panels.

In simple words

Know how to ask questions of a table with SQL. Know that big files are cut into blocks and stored on many computers (HDFS). Know that a manager (YARN) lends out workers and that the workers count their own piles first and then combine the counts (MapReduce). That is all. You do not need to write Java.

Words you’ll meet in this lesson

Table, row, columnA table is a grid. A row is one record (one order). A column is one field (city, amount).
AggregateA function that turns many rows into one value: SUM, COUNT, AVG, MAX.
JOINCombining rows of two tables where a key matches, e.g. orders with customers on cust_id.
BlockA fixed-size piece of a file in HDFS (128 MB by default). The unit of storage and of parallel work.
ReplicationKeeping several copies of each block on different machines (default 3).
NameNode / DataNodeThe HDFS master that knows where every block is / the workers that store the blocks.
ContainerA reserved bundle of memory and CPU cores on one machine, granted by YARN, in which a task runs.
Map, shuffle, reduceProcess each block in parallel (map), group the partial results by key across the network (shuffle), combine them per key (reduce).

The three prerequisites at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A school

  • SQL is the way you ask the school office a question: “How many students are in each class?” You say what you want, not how to count.
  • HDFS is the school’s huge archive. Files are too big for one cupboard, so they are cut into pieces and kept in many cupboards (DataNodes). One register (the NameNode) knows which piece is where. Every piece has two spare copies.
  • YARN is the principal’s office: it decides which classroom (computer) and how many helpers a task may use. A container is one booked classroom with a fixed amount of memory and CPU.
  • MapReduce is the way the work is done: many helpers each count their own pile (map), then the partial counts are sent to one person per topic (shuffle) who adds them up (reduce).

Intermediate How the three work together

  • A SQL query names a table and says what to compute. SQL does not say where the data lives or how many machines to use.
  • On a cluster the table is a set of files in HDFS. Each file is cut into blocks (128 MB by default), and each block lives on 3 DataNodes.
  • To compute, something must read those blocks. YARN gives containers on the machines near the blocks (data locality), so the code travels to the data and not the other way around.
  • Each container reads its block (map), sends partial results to the right reducer (shuffle by key), and the reducers produce the final answer (reduce), which is written back to HDFS or returned to you.
  • Hive’s whole job is to write that Java / Tez program for you from your SQL. You will see exactly how in Lesson 1.4.

Advanced Details that matter in production

  • Block size and parallelism: a 1 GB file is 8 blocks of 128 MB, so up to 8 map tasks can run at once. Millions of tiny files mean millions of tiny tasks, the classic small files problem.
  • Replication (default 3) gives fault tolerance and more places to run a task near its data. It also triples raw storage.
  • The NameNode keeps all metadata in RAM. Every file, directory and block is an object. This is why Hive layouts that create very many small files hurt the whole cluster, not only your query.
  • A container is a bundle of memory and vcores on one NodeManager. A query that asks for more than the queue allows waits in the ACCEPTED state; it is not “slow”, it is queued.
  • Shuffle is the expensive step: data moves over the network and is sorted by key. Joins and group-bys are shuffle-heavy; Modules 5 and 8 of this course are mostly about avoiding unnecessary shuffles.
  • SQL semantics carry over, but not transactions’ speed: a Hive query takes seconds to minutes even on small data, because starting distributed work has fixed costs.

Exam tip: Q: “What are the prerequisites for learning Hive?” A: SQL (because HiveQL is SQL-like), HDFS (because table data is stored as files in HDFS), YARN and MapReduce (because queries run as distributed jobs on YARN), and basic Linux. Then add one sentence: “Hive does not replace Hadoop, it sits on top of it.”

4 Step by step

One question, five moves: from SQL to an answer on a cluster

  1. SQL: you ask a question, not a method

    import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id INT, city TEXT, amount INT)")
rows = [(1, "Pune", 220), (2, "Thane", 150), (3, "Pune", 180), (4, "Mumbai", 310),
        (5, "Thane", 90), (6, "Pune", 60), (7, "Mumbai", 140), (8, "Pune", 100)]
db.executemany("INSERT INTO orders VALUES (?, ?, ?)", rows)
for city, total in db.execute("SELECT city, SUM(amount) FROM orders GROUP BY city ORDER BY city"):
    print(city, total)
    Mumbai 450 Pune 560 Thane 240
    You wrote what you want (total per city). You did not say how to loop, where the rows are or how many computers to use. That freedom is why SQL became the language of data, and why Hive wants to speak it.

  2. HDFS: a big file is cut into blocks

    import math
size_mb, block_mb = 400, 128
blocks = math.ceil(size_mb / block_mb)
print("blocks:", blocks)
print("sizes :", [min(block_mb, size_mb - i * block_mb) for i in range(blocks)], "MB")
    blocks: 4 sizes : [128, 128, 128, 16] MB
    A 400 MB file becomes four blocks: three full 128 MB blocks and one 16 MB block. The last block is only as big as its data; HDFS does not waste the space. Each block can be worked on by a different machine at the same time.

  3. HDFS: every block is copied to three machines

    nodes = ["DN1", "DN2", "DN3", "DN4"]
for b in range(1, 5):
    copies = [nodes[(b - 1 + k) % 4] for k in range(3)]
    print(f"B{b} ->", copies)
    B1 -> ['DN1', 'DN2', 'DN3'] B2 -> ['DN2', 'DN3', 'DN4'] B3 -> ['DN3', 'DN4', 'DN1'] B4 -> ['DN4', 'DN1', 'DN2']
    Real HDFS also considers racks, but the idea is the same: no two copies of a block on one machine. If DN2 dies, every block still has at least two living copies. The NameNode’s map of “block → machines” is what makes any of this findable.

  4. YARN: containers are the unit of work

    node_gb, container_gb = 8, 2
print("containers per node:", node_gb // container_gb)
print("containers on 3 nodes:", 3 * (node_gb // container_gb))
    containers per node: 4 containers on 3 nodes: 12
    Each NodeManager offers its memory and cores. YARN carves them into containers (here 2 GB each). A query that needs 10 containers gets them if the cluster has them, and waits if not.

  5. MapReduce: count your own pile, then combine

    blocks = [[("Pune", 220), ("Thane", 150), ("Pune", 180)],
          [("Mumbai", 310), ("Thane", 90), ("Pune", 60)],
          [("Mumbai", 140), ("Pune", 100)]]
partials = []
for b in blocks:                      # map: each block summed on its own
    d = {}
    for city, amt in b:
        d[city] = d.get(city, 0) + amt
    partials.append(d)
final = {}
for d in partials:                    # shuffle + reduce: combine by city
    for city, amt in d.items():
        final[city] = final.get(city, 0) + amt
print(partials)
print(final)
    [{'Pune': 400, 'Thane': 150}, {'Mumbai': 310, 'Thane': 90, 'Pune': 60}, {'Mumbai': 140, 'Pune': 100}] {'Pune': 560, 'Thane': 240, 'Mumbai': 450}
    Each block is summed locally (map). Then the partial sums for the same city are brought together and added (shuffle + reduce). Because each block is processed independently, 3 blocks can be 3 parallel tasks, and 3,000 blocks can be 3,000. This is the engine under every Hive query.
5 See it happen

The same GROUP BY: what you see, and what the cluster does

Left: the analyst’s screen. Right: the cluster. Use the same 8 sample orders you ran in step 1, now spread over three blocks.

One GROUP BY: what you see, and what the cluster does 6 steps
What you see
  1. Kabir types the same question he ran on SQLite, now on the full 2 TB orders table.
  2. The query starts. The progress bar moves; he does not know about blocks or containers.
  3. Hive reports 55%. Tasks are running on many machines at once.
  4. Done in 22 seconds. (Time is illustrative.)
  5. Three rows appear: Mumbai 450, Pune 560, Thane 240. Exactly what the small SQL example gave.
  6. The difference is only scale: the same SQL now runs on a cluster.
Behind the screen
  1. The orders file is already cut into blocks stored on different DataNodes. We show 3 blocks and 8 rows to keep it small.
  2. YARN grants one container per block, on the machine that holds the block (data locality). A map task starts in each.
  3. Each map task adds up the amounts per city for its own block only. These are partial sums.
  4. Partial sums are sent across the network so that all values for one city meet at one reducer. This is the shuffle.
  5. Each reducer adds the partial sums it received: Pune 400+60+100 = 560, Thane 150+90 = 240, Mumbai 310+140 = 450.
  6. The three result rows are written out and shown to the user. In Hive, writing this program is the system’s job, not yours.

Three live scenarios follow: how HDFS keeps a file safe, how YARN shares containers (and why queries wait), and an advanced look at why joins are expensive.

Real-time scenario 1

HDFS: one file, four blocks, twelve copies

TiffinGo uploads a 400 MB order log. Follow it from one file to blocks on four machines, then see what happens when one machine dies.

A file inside HDFS 5 steps
Animated example
  1. A 400 MB file called orders.csv is copied into HDFS.
  2. HDFS cuts it into blocks of 128 MB. The fourth block is only 16 MB because that is all that is left.
  3. Each block is copied to three different DataNodes. Block B1 sits on DataNode 1, 2 and 3, and so on. (Illustrative placement; real HDFS also considers racks.)
  4. The NameNode keeps the map of which DataNodes hold each block. It never stores the data itself.
  5. DataNode 2 fails. The NameNode notices the missing heartbeat and every block still has at least two living copies. It will re-copy the lost ones in the background.
Real-time scenario 2

YARN: lending out containers, and why queries wait

Three TiffinGo teams run Hive queries on a tiny three-node cluster. Each box is a 2 GB container slot. Watch the ResourceManager share them.

Containers in action 5 steps
Animated example
  1. The cluster offers 12 container slots of 2 GB each (3 nodes × 8 GB ÷ 2 GB).
  2. Job A, a Hive query, asks for 4 containers and gets them straight away.
  3. Job B asks for 6 containers and gets them. Ten of the twelve slots are now busy.
  4. Job C asks for 4 containers, but only 2 are free. It starts with 2 and the rest wait in the queue.
  5. Job A finishes. Its containers are released and job C’s waiting containers start. In a real cluster this is why a Hive query can sit in the “ACCEPTED” state for a while.
Real-time scenario 3 · advanced

Why a JOIN is harder than a GROUP BY

A join must bring matching rows of two tables to the same place. On a cluster that means a shuffle of both tables. This is the single most important reason Hive performance work exists.

A distributed join 5 steps
Animated example
  1. The orders table sits on node 1 and the customers table on node 2. SQL says JOIN, but the matching rows are on different machines.
  2. Map step: each mapper emits its rows as (join key, row). Order o1 becomes (1, o1); customer Asha becomes (1, Asha).
  3. Shuffle: the key decides the reducer (here key mod 2). Keys 1 and 2 go to different reducers, but every row for one key ends up in one place.
  4. Reduce step: each reducer pairs the order rows with the customer row for its key. The join result is complete.
  5. The price of this is moving both tables over the network. Later lessons show how to avoid it with map joins, bucketing and partitioning, and how skewed keys can overload one reducer.
6 Real-world use

Where these three skills show up in daily Hive work

1. An analyst moves from MySQL to a data lake

A bank’s analyst has used MySQL for years. On the new platform the same SELECT … GROUP BY works in Hive, but the data is files in HDFS. Knowing SQL makes the first week easy; knowing blocks explains why “only 3 files” can be slower than “300 files”.

SQL skill→Same query→Files in HDFS

2. “Why did my query start 400 tasks?”

A data engineer sees 400 map tasks for a 50 GB table. Because 50 GB is only about 400 blocks of 128 MB, that is expected: one task per block. If the same data were 40,000 tiny files, there would be 40,000 tasks and the job would crawl.

Table size→Blocks→Map tasks

3. The query that “does nothing”

At month end, many teams submit reports together. A Hive query shows state ACCEPTED for ten minutes: it is waiting for YARN containers, not stuck. Admins give each team a queue so that one team cannot take everything.

Many queries→YARN queue→Wait or run

4. Interview screening

Hive interviews usually start with SQL (rank, window functions, joins), then ask “what happens when I run this on 1 TB?”. Candidates who can explain map, shuffle and reduce in plain words stand out.

SQL round→Cluster round→Offer

5. Cloud bills and sizing

On a cloud cluster the number of containers you keep alive is money. Understanding that a query needs “blocks ÷ containers” rounds of work helps teams decide how big a cluster to rent for the night batch.

Data size→Parallelism→Cluster size and cost

9 Quiz and revision

Check yourself

Quick revision

Lesson 1.1 in one screen

  • SQL: SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY; JOIN matches rows on a key.
  • HDFS: big files are cut into blocks (128 MB), each copied 3 times on different DataNodes.
  • NameNode = metadata master (RAM). DataNode = stores blocks. Clients read bytes directly from DataNodes.
  • YARN: ResourceManager (cluster brain) + NodeManagers (per machine). Work runs in containers (memory + vcores).
  • MapReduce: map (per block, parallel) → shuffle (group by key over the network) → reduce (combine per key).
  • One map task per block: 1 GB ≈ 8 blocks ≈ 8 map tasks. Many tiny files = many tiny tasks.
  • Joins and group-bys need a shuffle; the shuffle is the expensive step.
  • Hive does not replace Hadoop. It writes the distributed program for you from SQL.

Interview and viva questions

Do I need to know Java to learn Hive?

No. You write HiveQL, which is SQL-like. Java only matters when you write custom functions (UDFs) in a later module, and even then Python and other options exist.

How much SQL do I really need before Hive?

Comfortable use of SELECT, WHERE, GROUP BY, ORDER BY and INNER/LEFT JOIN is enough to start. Window functions and subqueries come up later and are taught when needed.

Do I need to install Hadoop before starting?

No. All concepts in this course can be followed from the lessons and the in-browser Python examples. The “Run on your PC” panels are optional; they show real commands for learners who have built the Hadoop lab.

What is the difference between a YARN container and a Docker container?

A YARN container is a reservation of memory and CPU on one node, granted by the ResourceManager, in which a task process runs. A Docker container is a packaged, isolated runtime environment. YARN can optionally launch tasks inside Docker containers, but the two ideas are different.

Why does HDFS use such large blocks (128 MB) compared with a normal file system (4 KB)?

Large blocks keep the number of blocks, and therefore the NameNode’s metadata and the disk seek overhead, small, and they make streaming reads of large files efficient. It suits big sequential scans, which is what analytics does.

q = "SELECT city, SUM(amount) FROM orders WHERE amount >= 100 GROUP BY city HAVING SUM(amount) > 300 ORDER BY city"
print(db.execute(q).fetchall())
[('Mumbai', 310), ('Pune', 320)]

How it works: WHERE removes small orders before grouping (Pune keeps 220 + 100 = 320, Thane keeps 150, Mumbai 310). HAVING then keeps groups above 300: Mumbai and Pune.

P5Medium

Left join to find cities with no orders

Find the cities in the cities table that have no orders at all.

Input
cities: Pune, Thane, Nashik · orders: Pune, Pune, Thane
Expected output
[('Nashik',)]
Show solution and explanation 
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE cities (city TEXT)")
db.execute("CREATE TABLE orders (city TEXT)")
db.executemany("INSERT INTO cities VALUES (?)", [("Pune",), ("Thane",), ("Nashik",)])
db.executemany("INSERT INTO orders VALUES (?)", [("Pune",), ("Pune",), ("Thane",)])
q = "SELECT c.city FROM cities c LEFT JOIN orders o ON c.city = o.city WHERE o.city IS NULL"
print(db.execute(q).fetchall())
[('Nashik',)]

How it works: A LEFT JOIN keeps every row from the left table; where no order matches, the right side is NULL. Filtering on IS NULL finds the unmatched cities. This anti-join pattern is common in Hive too.

P6Medium

Which DataNode holds what?

With 4 DataNodes and blocks B1..B4, place 3 replicas of each block on consecutive DataNodes (round robin). Then simulate DN2 failing and list blocks that still have at least one copy.

Input
nodes DN1..DN4, 4 blocks, replication 3
Expected output
B1 ['DN1', 'DN2', 'DN3'] -> alive: ['DN1', 'DN3']
B2 ['DN2', 'DN3', 'DN4'] -> alive: ['DN3', 'DN4']
B3 ['DN3', 'DN4', 'DN1'] -> alive: ['DN3', 'DN4', 'DN1']
B4 ['DN4', 'DN1', 'DN2'] -> alive: ['DN4', 'DN1']
Show solution and explanation 
nodes = ["DN1", "DN2", "DN3", "DN4"]
place = {f"B{b}": [nodes[(b - 1 + k) % 4] for k in range(3)] for b in range(1, 5)}
down = "DN2"
for blk, where in place.items():
    alive = [n for n in where if n != down]
    print(blk, where, "-> alive:", alive)
B1 ['DN1', 'DN2', 'DN3'] -> alive: ['DN1', 'DN3'] B2 ['DN2', 'DN3', 'DN4'] -> alive: ['DN3', 'DN4'] B3 ['DN3', 'DN4', 'DN1'] -> alive: ['DN3', 'DN4', 'DN1'] B4 ['DN4', 'DN1', 'DN2'] -> alive: ['DN4', 'DN1']

How it works: Every block lost at most one copy, so all four blocks are still readable. The NameNode would now re-replicate the under-replicated ones.

P7Business problem

How many map tasks?

A table is 50 GB (51,200 MB) stored as one large file with 128 MB blocks. How many map tasks will a full scan start? What if the same data were stored as 40,000 files of about 1.3 MB each?

Input
51,200 MB; 128 MB blocks; or 40,000 small files
Expected output
one big file : 400 map tasks
40,000 files : 40000 map tasks (at least one per file)
Show solution and explanation 
import math
total_mb, block = 51200, 128
print("one big file :", math.ceil(total_mb / block), "map tasks")
print("40,000 files :", 40000, "map tasks (at least one per file)")
one big file : 400 map tasks 40,000 files : 40000 map tasks (at least one per file)

How it works: 400 tasks versus 40,000. Each task has start-up overhead, so the small-files layout is far slower even though the data is identical. Modules 2 and 3 show how Hive avoids this.

P8Business problem

Queue planning for month-end

Month-end reports need 12 queries at the same time. Each needs 90 GB of containers. How much memory must the queue own? How many queries can run if it owns only 400 GB?

Input
12 queries × 90 GB; queue of 400 GB
Expected output
memory needed: 1080 GB
queries running in 400 GB: 4 | waiting: 8
Show solution and explanation 
need = 12 * 90
print("memory needed:", need, "GB")
fit = 400 // 90
print("queries running in 400 GB:", fit, "| waiting:", 12 - fit)
memory needed: 1080 GB queries running in 400 GB: 4 | waiting: 8

How it works: 1,080 GB are needed to run all together. With 400 GB only 4 run and 8 wait; they are not failing, they are queued. Admins use this calculation to size queues and to decide whether to stagger the reports.

Real-world scenario questions (asked in company interviews)

Interviewers for Hive roles usually begin with the prerequisites. These situations test whether you can connect SQL, HDFS and YARN.

Any company · conceptsFresher

“What happens to my GROUP BY on a cluster?”

The interviewer says: “You wrote SELECT city, SUM(amount) … GROUP BY city on a 2 TB table. Walk me through what happens underneath, without naming any tool.”

The interviewer is checking: do you understand parallel partial work, the shuffle and the reduce, rather than just SQL syntax?

Show a strong answer
  1. The table is stored as blocks on many machines. A task is started for each block, close to where the block is stored.
  2. Each task adds up the amounts per city for its own block (map).
  3. The partial sums are sent over the network so that all values for one city arrive at the same reducer (shuffle).
  4. Each reducer adds the partial sums for its cities and writes the final rows (reduce).

Avoid: saying “the database loads the whole table and loops over it”.

Operations · troubleshootingFresher

The query is not running

An analyst says: “My report has been stuck at ACCEPTED for 15 minutes. Is Hive broken?”

The interviewer is checking: can you tell waiting for capacity from failure?

Show a strong answer
  • ACCEPTED means YARN has the application but has not yet given it its first container; the queue is probably full of other jobs.
  • Check the ResourceManager UI (port 8088): which queue, how much is used, who is using it.
  • Options: wait, ask for a larger queue share, reduce the query’s container size or parallelism, or reschedule heavy reports.

Avoid: killing and resubmitting the job repeatedly; that sends it to the back of the queue again.

Data platform · designMid-level

Millions of tiny files

A team lands 40,000 small files a day (about 1 MB each) into HDFS and complains that every query is slow and the NameNode is using lots of memory.

The interviewer is checking: do you connect block size, tasks and NameNode memory?

Show a strong answer
  1. Each file is at least one block object and one task: 40,000 files means 40,000 tiny tasks with start-up overhead each.
  2. The NameNode keeps every file and block as an object in RAM, so millions of small files can exhaust its heap.
  3. Fix: compact files into larger ones (for example hourly or daily), store in a columnar format, and design the writers to produce fewer, larger files.

Avoid: adding more worker nodes; the bottleneck is the number of files, not the number of workers.

Any company · conceptsFresher

“Is Hive a database?”

The interviewer asks: “Hive has tables and SQL. So is it a database like MySQL?”

The interviewer is checking: do you know that Hive provides SQL on top of Hadoop rather than its own storage and engine?

Show a strong answer
  • Not quite. Hive stores table definitions in a metastore, while the data stays as files in HDFS (or cloud storage).
  • Queries are turned into distributed jobs on YARN, so they are built for large scans and take seconds or minutes, not milliseconds.
  • It is great for analytics on big data, and not designed for thousands of tiny transactions per second like MySQL. (We study this in detail in Lesson 1.2.)

Avoid: a flat “yes” or “no”; explain what is the same (SQL) and what is different (storage and engine).
