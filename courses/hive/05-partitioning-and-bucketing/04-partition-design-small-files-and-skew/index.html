Partition design, small files and skew

Partitions and buckets speed Hive up only when the layout fits the data. This lesson measures what happens when it does not: too many partitions (2,000 tiny folders), small files from frequent loads, and skew where one key owns 37.5% of the rows. Then it fixes each one with tools you can run today. All outputs are real, from Hive 4.2.1.

2 Definition

Layout design, the small files problem and data skew

Formal definition (write this in exams)

Partition design is the choice of partition (and bucket) columns so that common queries prune most data while each partition remains large enough to be read efficiently. The small files problem occurs when a table consists of many files much smaller than the storage block size, which increases NameNode (or object store) metadata load, task start-up and file-open overhead. Data skew is an uneven distribution of rows across keys, so that the partitions of a shuffle (or the partitions or buckets of a table) receive very different amounts of data and the slowest task determines the job’s run time.

In simple words

A good layout prunes a lot but keeps folders and files big. Too many partitions or too many tiny files make every query open more files than needed. Skew means one key has far more rows than the others, so one task does most of the work while the rest wait.

Words you’ll meet in this lesson

Over-partitioningSo many partitions that each one holds very little data.

CompactionRewriting many small files into fewer large ones.
hive.merge.tezfilesMerge small output files at the end of a Tez job (default false).

StragglerThe last, slow task that keeps the whole job waiting.

Layout design at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Shelves, boxes and one overloaded worker

  • Too many partitions: a shelf with 2,000 boxes, each holding one sheet. Finding anything means opening many boxes.
  • Small files: every small delivery adds a new envelope to the box. Eventually the box is full of envelopes, each with a few lines.
  • Skew: eight workers share the work by first letter, but half the parcels start with “A”. One worker is still busy long after the others go home.

Intermediate The rules of thumb

  • Partition column: used in most filters, with a number of values that keeps each partition large (in production, hundreds of MB or more). Dates are the classic choice; ids almost never are.
  • Count before you choose: distinct values × years of history = partitions. 2,000 customers gave 2,000 folders and 2,000 files on day one.
  • Small files come from frequent small inserts, many tasks writing to many partitions, and streaming. Fix with fewer, bigger writes, DISTRIBUTE BY the partition key, hive.merge.tezfiles=true, or periodic compaction by rewriting partitions.
  • Skew: check the top keys first: SELECT key, COUNT(*) … ORDER BY 2 DESC LIMIT 10.

Advanced What Hive 4.2.1 really did in our lab

  • ALTER TABLE … CONCATENATE was refused (Error 30034: managed tables only), and a plain CREATE TABLE in Hive 4 makes an external table (Lesson 2.2). Rewriting the partition with INSERT OVERWRITE … SELECT from itself merged 8 files into 1.
  • hive.merge.tezfiles is false by default; turning it on merged 4 output files into 1 in the same statement (threshold hive.merge.smallfiles.avgsize = 16 MB).
  • GROUP BY already aggregates in the map tasks (hive.map.aggr=true), which shrinks most GROUP BY skew. hive.groupby.skewindata=true adds a second reduce stage that first spreads keys randomly.
  • Skewed tables: SKEWED BY (restaurant_id) ON (0) STORED AS DIRECTORIES stored the big key in its own folder; a query for it read 30,000 rows, other keys read the 50,000 in the default folder.
  • Skew joins: hive.optimize.skewjoin (default false) handles keys above hive.skewjoin.key (100,000 rows) with a follow-up map join.

Exam tip: “What is the small files problem in Hadoop/Hive and how do you fix it?” Say: many files much smaller than the block size overload the NameNode and add task and file-open overhead; fix by writing fewer, larger files (batching, DISTRIBUTE BY partition key, merge settings) and by compacting existing partitions. For skew, mention identifying hot keys, map-side aggregation, hive.groupby.skewindata, skew join settings and salting.

4 Step by step

Measure each problem, then fix it

All outputs are real, from the Hive 4.2.1 lab (database tiffingo).

  1. Step 1 · Over-partitioning: partition by customer_id

    CREATE TABLE orders_by_cust (order_id INT, city STRING, order_ts TIMESTAMP,
  amount DECIMAL(10,2))
PARTITIONED BY (customer_id INT) STORED AS ORC;

INSERT OVERWRITE TABLE orders_by_cust PARTITION (customer_id)
SELECT order_id, city, order_ts, amount, customer_id FROM orders;
-- Error 20004: too many dynamic partitions (limit 100 per node)

SET hive.exec.max.dynamic.partitions=3000;
SET hive.exec.max.dynamic.partitions.pernode=3000;
-- run the INSERT again
SELECT COUNT(*) AS partitions FROM (SELECT DISTINCT customer_id FROM orders_by_cust) x;
    +-------------+ | partitions | $ ls …/orders_by_cust | wc -l → 2000 folders, 2000 files file sizes: min 707, median 858, max 1047 bytes
    The default limits stopped the first try, a hint that something is off. After raising them: 2,000 folders, each with one file under 1.1 KB. On HDFS every file and folder is an object in NameNode memory, whatever its size.

  2. Step 2 · Measure the cost

    SELECT city, COUNT(*), SUM(amount) FROM <table> GROUP BY city;
-- run 3 times on each table, median shown
    table partitions data files bytes on disk GROUP BY city (median of 3 runs) orders 0 1 437,536 3.2 s orders_by_day 30 30 409,088 3.4 s orders_by_cust 2,000 2,000 1,723,882 7.3 s
    Same 50,000 rows. The customer-partitioned table is 4 times bigger on disk (each ORC file carries its own header, footer and statistics) and the full query takes more than twice as long, because Hive lists 2,000 partitions and opens 2,000 files. Partitioning by date (30 partitions) cost almost nothing.

  3. Step 3 · Small files from frequent loads

    CREATE TABLE events_small (order_id INT, city STRING, amount DECIMAL(10,2))
PARTITIONED BY (order_date DATE) STORED AS ORC;

-- every 3 hours a job appends the latest orders:
INSERT INTO events_small PARTITION (order_date='2026-10-05')
SELECT order_id, city, amount FROM orders
WHERE order_date = '2026-10-05' AND hour(order_ts) < 3;
-- … 7 more runs for 03–05, 06–08, …, 21–23
    $ ls -l …/events_small/order_date=2026-10-05/ (after 8 INSERT INTO runs) 1452 000000_0 1354 000000_0_copy_1 1429 000000_0_copy_2 1480 000000_0_copy_3 1455 000000_0_copy_4 1363 000000_0_copy_5 1420 000000_0_copy_6 1347 000000_0_copy_7 8 files · 11,300 bytes · INPUT_FILES_Map_1: 8
    Each INSERT INTO adds a new file (_copy_1, _copy_2 …) instead of changing the old ones. One day already has 8 files; a year of 3-hourly loads would be 2,920 files for one table, and every query on a day must open all of them.

  4. Step 4 · Compact: CONCATENATE refused, rewrite works

    ALTER TABLE events_small PARTITION (order_date='2026-10-05') CONCATENATE;

-- rewrite the partition from itself instead:
INSERT OVERWRITE TABLE events_small PARTITION (order_date='2026-10-05')
SELECT order_id, city, amount FROM events_small WHERE order_date = '2026-10-05';
    Error: Error while compiling statement: FAILED: SemanticException [Error 30034]: Concatenate/Merge can only be performed on managed tables $ ls -l …/events_small/order_date=2026-10-05/ 7520 000000_0 1 file · 7,520 bytes · INPUT_FILES_Map_1: 1 · COUNT 1621 · SUM 467410.00 (unchanged)
    CONCATENATE (a fast ORC/RCFile stripe merge) works only on managed tables, and Hive 4 turned our plain CREATE TABLE into an external one. Rewriting the partition reads it once and writes one file: 8 files and 11,300 bytes became 1 file and 7,520 bytes, with the same count and sum. Schedule this for “closed” partitions, such as yesterday.

  5. Step 5 · Prevent small files at write time

    SET mapreduce.job.reduces=4;
INSERT OVERWRITE TABLE events_small PARTITION (order_date='2026-10-06')
SELECT order_id, city, amount FROM orders WHERE order_date = '2026-10-06'
DISTRIBUTE BY rand();           -- 4 reducers → 4 files

SET hive.merge.tezfiles=true;   -- then run the same INSERT again
    -- SET hive.merge.tezfiles=false; (default) 2141 000000_0 2025 000001_0 2108 000002_0 2118 000003_0 -- SET hive.merge.tezfiles=true; 7682 000000_0
    Four reducers wrote four 2 KB files. With hive.merge.tezfiles=true Hive added a merge step and wrote one 7.5 KB file, because the average file was below hive.merge.smallfiles.avgsize (16 MB). For dynamic partition inserts, DISTRIBUTE BY the partition column does the same job: each partition is written by one reducer.

  6. Step 6 · Skew: find the hot key

    -- a cloud-kitchen chain joins: 30,000 extra orders under restaurant_id 0
SELECT restaurant_id, COUNT(*) AS n,
       ROUND(100 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS pct
FROM orders_skew GROUP BY restaurant_id ORDER BY n DESC LIMIT 4;

-- rows per reducer if keys are hashed into 8 reducers
SELECT pmod(murmur_hash(restaurant_id), 8) AS reducer, COUNT(*) AS rows_to_reducer
FROM orders_skew GROUP BY pmod(murmur_hash(restaurant_id), 8) ORDER BY reducer;
    +----------------+--------+-------+ | restaurant_id | n | pct | +----------------+--------+-------+ | 0 | 30000 | 37.5 | | 40 | 1010 | 1.3 | | 65 | 1008 | 1.3 | | 10 | 992 | 1.2 | +----------------+--------+-------+ +----------+------------------+ | reducer | rows_to_reducer | +----------+------------------+ | 0 | 6821 | | 1 | 35419 | | 2 | 6737 | | 3 | 4398 | | 4 | 7966 | | 5 | 5821 | | 6 | 5141 | | 7 | 7697 | +----------+------------------+
    One restaurant owns 37.5% of the rows; the next is at 1.3%. With rows routed by key, reducer 1 gets 35,419 rows while the others get 4,398–7,966: the job waits for that one task. (The second query only illustrates the routing; Hive’s shuffle uses its own hash, but every row of a key always goes to the same reducer.)

  7. Step 7 · Hive’s skew tools

    SET hive.groupby.skewindata;   SET hive.optimize.skewjoin;   SET hive.map.aggr;

SET hive.groupby.skewindata=true;
EXPLAIN SELECT restaurant_id, SUM(amount) FROM orders_skew GROUP BY restaurant_id;

CREATE TABLE orders_lb (order_id INT, customer_id INT, restaurant_id INT,
  city STRING, amount DECIMAL(10,2))
SKEWED BY (restaurant_id) ON (0) STORED AS DIRECTORIES
STORED AS ORC;
INSERT OVERWRITE TABLE orders_lb SELECT * FROM orders_skew;
    hive.groupby.skewindata=false · hive.optimize.skewjoin=false · hive.map.aggr=true -- default plan: Reducer 2 <- Map 1 (SIMPLE_EDGE) -- with skewindata=true: Reducer 2 <- Map 1 (SIMPLE_EDGE) Reducer 3 <- Reducer 2 (SIMPLE_EDGE) $ find …/orders_lb -type f ./HIVE_DEFAULT_LIST_BUCKETING_DIR_NAME/000000_0 ./restaurant_id=0/000000_0 SELECT COUNT(*) AS n FROM orders_lb WHERE restaurant_id = 0; result 30000 · RECORDS_IN 30000 · INPUT_FILES 2 SELECT COUNT(*) AS n FROM orders_lb WHERE restaurant_id = 40; result 1010 · RECORDS_IN 50000 · INPUT_FILES 2
    Even the default plan has a Group By in Map 1: map-side aggregation turns 30,000 rows of restaurant 0 into one partial sum per task, so GROUP BY skew is usually mild. skewindata adds Reducer 3 (spread randomly first, then combine). The skewed table put restaurant 0 in its own folder: querying it read 30,000 rows, while any other restaurant read the 50,000 in the default folder.

Why the layout goes bad, and how to fix it

Over-partitioning, small files and skew 5 steps
What you see
  1. Partitioning by customer needed raised limits and created 2,000 partitions.
  2. The same data took 4× the disk and twice the query time.
  3. Small inserts left 8 tiny files; CONCATENATE was refused; a rewrite merged them.
  4. One restaurant has 37.5% of rows; one reducer gets 35,419 of them.
  5. Two-stage GROUP BY and a skewed table are Hive’s built-in answers.
Behind the screen
  1. Every partition is a folder and a file, however few rows it holds.
  2. Each ORC file carries fixed metadata, and each query lists and opens every file.
  3. INSERT INTO never modifies existing files; it only adds new ones.
  4. Rows are sent to reducers by key, so a hot key overloads one reducer.
  5. Map-side partial sums and a random first stage spread the hot key’s work.

6 Real-world use

Layout work in real teams

1. Table design reviews

Many data platform teams review new big tables before creation: partition column, expected data per partition, bucket count and file format.

Proposal→size estimate→Approved layout

2. Scheduled compaction

Pipelines that load often run a nightly job that rewrites yesterday’s partitions into large files, keeping NameNode and query costs stable.

Small files→rewrite partition→Few big files

3. Storage health dashboards

Admins track average file size and files per partition from the metastore statistics (numFiles, totalSize) and alert on tables that drift into small files.

Metastore stats→files & sizes→Alerts

4. Marketplaces and hot sellers

E-commerce and food delivery data often has a few giant sellers or a NULL / “unknown” key with many rows. Teams handle them separately or salt them in joins.

Top-key check→skew handling→Balanced tasks

5. NULL join keys

Rows with a NULL foreign key all hash to the same place. Filtering them out before the join (they never match anyway) often removes the worst skew.

Join input→WHERE key IS NOT NULL→Even shuffle

Interview and viva questions

What file size should I aim for?

On HDFS, files near the block size (128 or 256 MB) are a common target; on cloud object stores, files of a few hundred MB work well. The exact number matters less than avoiding thousands of KB-sized files. Hive’s own merge defaults (merge below 16 MB average, into about 256 MB) are a sensible guide.

Why do small files hurt the NameNode?

The HDFS NameNode keeps every file, folder and block in memory, roughly 150 bytes each. A billion tiny files can exhaust it even if the data itself is small. Every query also pays to list, open and read the footer of each file.

Is skew a problem for map tasks too?

Much less. Map tasks split input by file and block, not by key, so they get similar amounts of data. Skew appears when rows are shuffled by key: GROUP BY, JOIN, DISTRIBUTE BY, window PARTITION BY and dynamic partition inserts with DISTRIBUTE BY.

Should I use hive.groupby.skewindata all the time?

No. It adds a stage to every GROUP BY, which costs time when there is no skew, and it does not support every query shape (for example several DISTINCT aggregates on different columns). Use it for specific queries with known hot keys.

Do Iceberg tables fix these problems?

They help a lot: hidden partitioning avoids wrong filters, partition specs can change without rewriting old data, and compaction is a built-in procedure. You still have to pick a sensible partition granularity and handle skew in joins. Module 7 covers Iceberg in Hive.

P6Medium

Pick the coarser partition

Choose day or month partitioning so that partitions are at least 100 MB.

Input
daily data 12 MB
Expected output
day 12 MB too small
month 360 MB OK
Show solution and explanation 
daily = 12
for name, days in [("day", 1), ("month", 30)]:
    print(name, daily * days, "MB", "OK" if daily * days >= 100 else "too small")
day 12 MB too small month 360 MB OK

How it works: Monthly partitions (360 MB) are healthy; daily ones (12 MB) are too small. Queries for one day still prune to one month and use ORC statistics inside.

Real-world scenario questions (asked in company interviews)

Layout questions separate people who used Hive in production from people who read about it. Expect numbers.

Any company · HadoopFresher

“What is the small files problem?”

Explain the small files problem and two ways to fix it.

The interviewer is checking: do you know the cause and both prevention and cure?

Show a strong answer

Many files much smaller than the block size overload the NameNode, which holds metadata for every file in memory, and slow queries because each file must be listed, opened and read. Prevent it by writing fewer, larger files (batch loads, DISTRIBUTE BY the partition key, hive.merge.tezfiles). Cure it by compacting: rewrite partitions with INSERT OVERWRITE, CONCATENATE for managed ORC tables, or ACID/Iceberg compaction.

Avoid: “Increase the block size”, which does not reduce the number of files.

Data engineeringMid-level

The partitioned table got slower

A colleague re-partitioned a table by (date, store_id) with 5,000 stores. Full-month reports became slower.

The interviewer is checking: can you reason with partition counts and sizes?

Show a strong answer
  1. Count partitions (30 × 5,000 = 150,000 a month) and average file size.
  2. Explain: listing and opening that many tiny files outweighs pruning.
  3. Propose: partition by date only; bucket or sort by store_id; rely on ORC statistics; compare with counters.

Avoid: Adding more memory to HiveServer2.

E-commerceMid-level

One task runs for an hour

A daily join of orders and sellers finishes 99% of tasks in five minutes, then one task runs for an hour.

The interviewer is checking: do you recognise skew and know the remedies?

Show a strong answer
  • Find the hot key: top sellers by row count; check NULL keys too.
  • If sellers is small, force a map join; otherwise try hive.optimize.skewjoin, or salt the hot keys.
  • Filter NULL keys before joining; measure the slowest task again.

Avoid: “Add more reducers”: the hot key still goes to just one of them.

PlatformSenior

A near-real-time table

Product wants orders queryable within 5 minutes in Hive, and the table must stay fast for a year.

The interviewer is checking: can you design for both freshness and file health?

Show a strong answer
  • Partition by date; land 5-minute batches (accepting small files for today).
  • Merge within each job (hive.merge.tezfiles) and compact yesterday nightly; monitor files per partition.
  • Better long-term: an ACID or Iceberg table with automatic compaction; document the freshness and cost trade-off.

Avoid: Partitioning by minute to “make queries faster”.
