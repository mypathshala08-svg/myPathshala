Dynamic partitions and MSCK REPAIR TABLE

Static partitions need one statement per value. Dynamic partitions let Hive read the value from the data and create the folders itself, so a month is one statement. The reverse problem, folders written by other tools that Hive does not know about, is solved with MSCK REPAIR TABLE. Both are powerful and both have sharp edges; we hit five of them in the lab. 2 Definition

Dynamic partitions and partition repair

Formal definition (write this in exams)

In a dynamic partition insert the partition clause names the partition columns without values, INSERT OVERWRITE TABLE t PARTITION (col) SELECT …, col FROM src, and Hive determines each row’s partition from the trailing columns of the SELECT, creating partitions as needed. It is controlled by hive.exec.dynamic.partition, hive.exec.dynamic.partition.mode (strict requires at least one static partition column) and limits on the number of partitions created. MSCK REPAIR TABLE compares the partition directories under a table’s location with the partitions registered in the metastore and adds (and optionally drops) metastore entries so that they match.

In simple words

Dynamic partitions let Hive decide which folder each row goes to, using a column of the data, so one statement can fill a month of partitions. MSCK REPAIR does the reverse job: when folders were created outside Hive, it tells the metastore about them.

Dynamic partitions and MSCK at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Hive sorts the letters for you

  • Static partition: you put every letter into the box you choose. Dynamic partition: you hand Hive the whole pile and it reads the address on each letter, opening a new box when it needs one.
  • Write PARTITION (order_date) without a value, and put order_date last in the SELECT.
  • MSCK REPAIR TABLE is the opposite direction: boxes already exist on the shelf, and Hive writes them into its register (the metastore).

Intermediate The settings and the rules

  • hive.exec.dynamic.partition (default true) and hive.exec.dynamic.partition.mode. In our Hive 4.2.1 lab the default mode is nonstrict; many tutorials, written for older versions, say strict. In strict mode at least one partition column must be static (Error 10096).
  • Dynamic partition columns are matched by position: they must be the last SELECT columns, in the same order as in PARTITION (…). Static levels must come before dynamic ones: PARTITION (order_date='…', city).
  • Limits: hive.exec.max.dynamic.partitions (1000 per statement) and hive.exec.max.dynamic.partitions.pernode (100 per task). They stop a bad column from creating thousands of folders.
  • A NULL value goes to __HIVE_DEFAULT_PARTITION__ (hive.exec.default.partition.name).

Advanced MSCK in Hive 4.2.1: options and edges

  • MSCK REPAIR TABLE t [ADD | DROP | SYNC PARTITIONS]. Plain MSCK = ADD: it registers new col=value folders but never removes entries whose folders are gone. DROP removes those; SYNC does both.
  • A folder that does not follow col=value made MSCK fail (“Invalid partition name”) because hive.msck.path.validation=throw by default; skip ignores such folders, ignore tries to use them anyway.
  • SYNC treated a partition we had added with a custom LOCATION as missing and dropped it. Keep custom locations out of tables you SYNC.
  • A partition whose folder was deleted made every query on the table fail (“Input path does not exist”) until it was repaired.
  • Hive 4’s metastore also has a background partition-management task that can discover partitions for tables with the discover.partitions=true property (vendor platforms such as Cloudera switch it on for external tables). Our external table in plain Apache 4.2.1 did not have the property, so we used MSCK.

Exam tip: “Static vs dynamic partitioning” and “What does MSCK REPAIR TABLE do?” are standard questions. For dynamic, mention the two settings, that the partition column goes last in the SELECT, and the max-partition limits. For MSCK, say it syncs folders on HDFS with partition entries in the metastore, typically after files are copied in from outside Hive.

Back-fill, three traps, then repair the click table

    Dynamic partitions are on and the mode is nonstrict in 4.2.1, so this works without any SET. One statement created 30 partitions. INSERT OVERWRITE replaces only the partitions that the query writes.

  2. Step 2 · Strict mode, the older default

    SET hive.exec.dynamic.partition.mode=strict;
INSERT OVERWRITE TABLE orders_dyn PARTITION (order_date)
SELECT order_id, customer_id, city, order_ts, amount, payment, status, order_date

    Strict mode demands at least one static column, for example PARTITION (order_date='2026-10-05', city). Many clusters (and many tutorials) still use strict, which is why you so often see SET hive.exec.dynamic.partition.mode=nonstrict at the top of scripts.

  3. Step 3 · Trap 1: the wrong column last

    CREATE TABLE pay_by_mode (order_id INT, amount DECIMAL(10,2))
PARTITIONED BY (payment STRING) STORED AS ORC;

INSERT OVERWRITE TABLE pay_by_mode PARTITION (payment)
SELECT order_id, payment, amount          -- oops: amount is last
FROM orders WHERE order_date = '2026-10-05';

SELECT COUNT(*) AS partitions FROM (SELECT DISTINCT payment FROM pay_by_mode) x;
SELECT payment, order_id, amount FROM pay_by_mode ORDER BY order_id LIMIT 3;
    +-------------+ | partitions | +-------------+ | 69 | +-------------+ +----------+-----------+---------+ | payment | order_id | amount | +----------+-----------+---------+ | 480.00 | 100005 | NULL | | 170.00 | 100047 | NULL | | 230.00 | 100065 | NULL | +----------+-----------+---------+
    Hive matched columns by position: payment went into the amount column (and became NULL, since “UPI” is not a number), and every distinct amount became a partition: 69 folders like payment=480.00. No error, no warning.

  4. Step 4 · Re-running correctly does not clean up

    INSERT OVERWRITE TABLE pay_by_mode PARTITION (payment)
SELECT order_id, amount, payment FROM orders WHERE order_date = '2026-10-05';
SHOW PARTITIONS pay_by_mode;      -- 73 rows: 69 bad + 4 good

ALTER TABLE pay_by_mode DROP PARTITION (payment < 'A');
SHOW PARTITIONS pay_by_mode;
    +-----------------+ | partition | +-----------------+ | payment=100.00 | | … (69 numeric) | | payment=Card | | payment=COD | | payment=UPI | | payment=Wallet | +-----------------+ +-----------------+ | partition | +-----------------+ | payment=Card | | payment=COD | | payment=UPI | | payment=Wallet | +-----------------+
    A dynamic INSERT OVERWRITE replaces only the partitions it writes; the 69 wrong ones stayed and would still show up in every GROUP BY payment. Digits sort before letters, so payment < 'A' dropped exactly the numeric folders. On a real table, recreate it or drop the bad partitions explicitly.

  5. Step 5 · Trap 2: NULL values and the default partition

    CREATE TABLE cust_by_ref (customer_id INT, name STRING)
PARTITIONED BY (ref_city STRING) STORED AS ORC;
INSERT OVERWRITE TABLE cust_by_ref PARTITION (ref_city)
SELECT customer_id, name, IF(customer_id % 4 = 0, NULL, city)
FROM customers WHERE customer_id <= 40;

SHOW PARTITIONS cust_by_ref;
SELECT COUNT(*) AS null_rows FROM cust_by_ref WHERE ref_city IS NULL;
SELECT COUNT(*) AS by_name FROM cust_by_ref
WHERE ref_city = '__HIVE_DEFAULT_PARTITION__';
    +--------------------------------------+ | partition | +--------------------------------------+ | ref_city=Bengaluru | | ref_city=Chennai | | ref_city=Delhi | | ref_city=__HIVE_DEFAULT_PARTITION__ | | ref_city=Hyderabad | | ref_city=Mumbai | | ref_city=Navi Mumbai | | ref_city=Pune | | ref_city=Thane | +--------------------------------------+ +------------+ | null_rows | +----------+ | by_name | +----------+ | 10 | +----------+
    Ten customers had no referral city. Their rows went into ref_city=__HIVE_DEFAULT_PARTITION__, and in our lab IS NULL found 0 of them while the folder name found all 10. Replace NULLs before inserting, e.g. coalesce(city, 'UNKNOWN').

INSERT OVERWRITE TABLE orders_dyn PARTITION (order_date) SELECT …, order_date FROM orders;

How Hive picks folders, and how MSCK syncs them 5 steps
What you see
  1. One dynamic INSERT creates all 30 date partitions.
  2. With the wrong column last, every amount became a partition.
  3. NULL values land in __HIVE_DEFAULT_PARTITION__, which IS NULL did not find.
  4. Folders written outside Hive appear only after MSCK REPAIR.
  5. A badly named folder breaks MSCK; SYNC also dropped a custom-location partition.
Behind the screen
  1. Hive reads the trailing SELECT column of each row and writes the row into that partition folder.
  2. Partition columns are taken by position, so a wrong order puts the wrong data into the folder names.
  3. There is no folder name for NULL, so Hive uses a special default name.
  4. MSCK lists the folders under the table location and adds the missing ones to the metastore.
  5. ADD only adds; DROP and SYNC remove entries without a matching col=value folder.

6 Real-world use

Dynamic partitions and MSCK at work

1. Back-fills and migrations

When a team moves a flat table to a partitioned one, or re-partitions by a new column, a dynamic INSERT OVERWRITE does it in one statement per chunk.

Old table→dynamic INSERT→Partitioned table

2. Late-arriving events

Mobile apps upload events days late. A dynamic insert puts each event into its own event-date partition instead of the day it arrived.

Event batch→PARTITION (event_date)→Correct days

3. Restores and cluster migrations

After copying a warehouse folder tree to a new cluster with DistCp or restoring from backup, teams recreate the table DDL and run MSCK REPAIR to register all partitions again.

Copied folders→MSCK REPAIR→Queryable table

4. Ingestion from other tools

Spark jobs, Kafka connectors and copy tools write date folders; the pipeline then adds the new partition to the metastore so Hive, Trino and Spark SQL can see it.

Writer job→ADD PARTITION→Visible to SQL

5. Data quality checks

Teams alert when a __HIVE_DEFAULT_PARTITION__ folder appears or when a dynamic insert creates far more partitions than expected: both usually mean bad input.

Insert→partition count check→Alert

# A dynamic partition insert: the LAST column of each row picks the folder
rows = [(100004, 180, "2026-10-03"), (100001, 530, "2026-10-17"),
        (100002, 500, "2026-10-20"), (100013, 340, "2026-10-03")]

table = {}
for *data, part in rows:                       # SELECT ..., order_date  (last!)
    folder = f"order_date={part}"
    if folder not in table:
        print("creating", folder)
    table.setdefault(folder, []).append(tuple(data))

print(len(table), "partitions")
for f, r in sorted(table.items()):
    print(f, r)

Interview and viva questions

Should I always use dynamic partitions?

Use dynamic inserts for back-fills and when one batch spans several partitions. For a normal daily job that loads one known day, a static partition is clearer, cheaper (each task writes one folder) and safer, because a bad date in the data cannot create unexpected partitions.

Why does a dynamic insert sometimes create many small files?

Every task writes one file into every partition it touches. With 100 map tasks and 30 days you can get 3,000 files. Adding DISTRIBUTE BY order_date sends each day to one reducer, so each partition gets one file. Lesson 5.4 covers small files in detail.

Is MSCK REPAIR TABLE slow?

It lists every folder under the table location, so its cost grows with the number of partitions, and on cloud object stores listing is slow. For daily ingestion, ALTER TABLE … ADD IF NOT EXISTS PARTITION for the new day is much cheaper. Use MSCK for one-off repairs and restores.

Does MSCK work on managed tables?

Yes, it compares folders with the metastore for any partitioned table. In practice it is used mostly for external tables, because data for managed tables normally arrives through Hive itself, which registers partitions as it writes.

Do Spark and Trino see partitions added by MSCK?

Yes. They read the same metastore, so once a partition is registered every engine can prune and read it. Spark has its own MSCK REPAIR TABLE / ALTER TABLE … RECOVER PARTITIONS that writes to the same metastore.

P7Business problem

Daily registration script

Generate the ALTER statements for the days that arrived since the last run.

Input
last registered 2026-10-03, today 2026-10-06
Expected output

Show solution and explanation 
from datetime import date, timedelta
last, today = date(2026, 10, 3), date(2026, 10, 6)
d = last + timedelta(days=1)
while d < today:
    print(f"ALTER TABLE app_clicks ADD IF NOT EXISTS PARTITION (dt='{d}');")

How it works: Two statements (10-04 and 10-05). Cheaper than MSCK on a table with years of folders, and safe to repeat.

Real-world scenario questions (asked in company interviews)

Dynamic partitions and MSCK appear in both fresher and data engineer interviews, usually with a “what went wrong” twist.

Any company · HiveFresher

“Static vs dynamic partitioning”

Explain the difference and when you would use each.

The interviewer is checking: do you know how the value is chosen and the settings involved?

Show a strong answer

Static: the value is written in the statement, e.g. PARTITION (dt='2026-10-05'); good for daily loads of a known day. Dynamic: PARTITION (dt) without a value, and Hive takes it from the last SELECT column, creating partitions as needed; good for back-fills. Dynamic needs hive.exec.dynamic.partition=true, and strict mode requires at least one static column. Limits: 1000 per statement, 100 per node by default.

Avoid: Saying dynamic is “always better”.

Data engineeringMid-level

Hundreds of strange partitions appeared

After a new back-fill job, SHOW PARTITIONS lists values like payment=480.00.

The interviewer is checking: do you know that dynamic partitions are positional?

Show a strong answer
  1. Check the SELECT: the partition column was not last.
  2. Drop the bogus partitions (or recreate the table); a corrected OVERWRITE does not remove them.
  3. Generate column lists from metadata, and alert when a load creates more partitions than expected.

Avoid: “Hive must have a bug”, without reading the SELECT.

Data platformMid-level

The table is empty after a migration

Files were copied to the new cluster and the table was recreated with the same DDL, but SELECT COUNT(*) returns 0.

The interviewer is checking: do you know the metastore holds the partition list?

Show a strong answer
  • The new metastore has the table but no partitions.
  • Run MSCK REPAIR TABLE t (set hive.msck.path.validation=skip if odd folders exist), then check counts per partition.
  • Re-add partitions with custom locations using ALTER … ADD PARTITION … LOCATION.

Avoid: “Reload all data”.

Analytics platformSenior

Every query on a table fails

Queries on the clicks table fail with “Input path does not exist”. A cleanup job ran last night.

The interviewer is checking: can you repair metastore/storage drift safely?

Show a strong answer
  • Identify missing folders: compare SHOW PARTITIONS with a listing of the location.
  • Drop exactly those partitions with ALTER TABLE … DROP PARTITION (plain MSCK only adds; SYNC may also drop custom-location partitions).
  • Change the cleanup job to drop partitions through Hive, so files and metadata go together.

Avoid: Running MSCK … SYNC on a production table without checking which partitions it will drop.
