1 The story

“Can we fix this without copying 200 TB?”

Before you start: Iceberg basics (7.3), the multi-engine test (11.1) and object storage (11.2).

After Lessons 11.1 and 11.2, TiffinGo’s platform team has a list: Spark sees an empty orders table, Trino overcounts, files dropped into S3 need MSCK, and commits on object storage copy every file. The architects propose a lakehouse on Apache Iceberg. The first question from management is about cost.

Kabir

Sir, do we have to rewrite all our tables to use Iceberg?

Arjun Sir

Not all. Iceberg keeps the data in ordinary Parquet, ORC or Avro files and adds its own metadata: snapshots, manifests and a schema with column IDs. For an external table, Hive 4 can write that metadata around the existing files: an in-place migration.

Riya

And transactional tables?

Arjun Sir

Those carry Hive’s delta and delete-delta folders, which Iceberg does not understand, so they must be copied. Today we migrate both kinds in our Hive 4.2.1 lab, evolve the partitioning, change rows, travel back in time, roll back, and check every result in Trino. All outputs are real.

2 Definition

Lakehouse tables and migrating Hive to Iceberg

Formal definition (write this in exams)

A lakehouse stores data in open file formats in a data lake or object store and adds an open table format, such as Apache Iceberg, Delta Lake or Apache Hudi, that provides warehouse features: atomic commits, row-level changes, schema and partition evolution, snapshots and time travel, readable by many engines through a shared catalogue. Migrating Hive tables to Iceberg means creating Iceberg metadata for a table, either around its existing data files (in-place migration, possible for external Parquet, ORC and Avro tables) or by rewriting the data into a new Iceberg table (copy migration, required for Hive ACID tables), followed by validation and switching every reader and writer to the Iceberg table.

In simple words

A lakehouse keeps data in open files and adds a table format such as Iceberg for transactions and history. Hive external tables can become Iceberg tables in place; ACID tables must be copied.

Lakehouse migration at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A new index for the same library

  • The books (data files) stay on the shelves. Iceberg writes a new, exact index of which books belong to the table.
  • Every change creates a new version of the index, so you can open yesterday’s version.
  • A book placed on the shelf without updating the index is not part of the table.

Intermediate The two migration paths in Hive 4

  • In place: ALTER TABLE t SET TBLPROPERTIES ('storage_handler'=…) with Hive’s Iceberg storage handler class, for external Parquet, ORC or Avro tables. Metadata only.
  • Copy: CREATE TABLE … STORED BY ICEBERG AS SELECT … (or INSERT into a new table) for managed ACID tables, other formats, or when you also want a new layout.
  • After either path: validate counts and sums in every engine, then switch readers and writers.

Advanced What the lab showed

  • In-place migration added 4 metadata files and rewrote 0 data files; the counts were identical.
  • The ACID table was refused (“Converting … transactional hive table to iceberg table is not allowed”); CTAS gave 5,000,001 rows, and Trino now agreed.
  • After migration, files copied into the folder stayed invisible even after MSCK REPAIR: only Iceberg’s manifests define the table.

Exam tip: “How do you migrate a Hive table to Iceberg?” External Parquet/ORC/Avro tables in place by setting the storage_handler table property to Hive’s Iceberg storage handler, which only writes metadata. Managed ACID tables with CTAS … STORED BY ICEBERG. Then validate counts and checksums in every engine and move readers and writers.

In-place migration changes the table for every engine at once. Engines without Iceberg support (Spark without the Iceberg runtime, older tools reading folders directly) stop seeing correct data, and writers that still drop files into folders write into the void. Migrate readers and writers in the same change window.

4 Step by step

Migrating real tables, checking every number

All outputs are real: Hive 4.2.1 with its bundled Iceberg 1.9.1, and Trino 476 from Lesson 11.1 reading through its iceberg catalog on the same metastore.

  1. Step 1 · A typical external Hive table

    CREATE EXTERNAL TABLE orders_mig (
  order_id INT, customer_id INT, city STRING, amount DECIMAL(10,2), status STRING)
PARTITIONED BY (order_date DATE) STORED AS PARQUET
LOCATION '/opt/hive/data/warehouse/tiffingo.db/orders_mig';
INSERT OVERWRITE TABLE orders_mig PARTITION (order_date)
SELECT order_id, customer_id, city, amount, status, order_date FROM orders
WHERE order_date BETWEEN '2026-10-01' AND '2026-10-07';
SELECT COUNT(*) AS n, SUM(amount) AS amt FROM orders_mig;
    +--------+-------------+ | n | amt | +--------+-------------+ | 11631 | 3415600.00 | +--------+-------------+
    Seven daily partitions, one Parquet file each. We record the count and the sum before migrating: these two numbers are the validation baseline.

  2. Step 2 · Migrate in place

    ALTER TABLE orders_mig SET TBLPROPERTIES (
  'storage_handler'='org.apache.iceberg.mr.hive.HiveIcebergStorageHandler');
SELECT COUNT(*) AS n, SUM(amount) AS amt FROM orders_mig;
    +--------+-------------+ | n | amt | +--------+-------------+ | 11631 | 3415600.00 | +--------+-------------+ $ find orders_mig -type f ./metadata/00000-05cee382-c2cb-4b75-b2f0-df764041a5ec.metadata.json ./metadata/00001-dec3245f-668d-43c4-8cd3-2bc8a003cee5.metadata.json ./metadata/53fbb13d-3205-4ad5-ab5b-589184641ae5-m0.avro ./metadata/snap-6356967414929367428-1-53fbb13d-3205-4ad5-ab5b-589184641ae5.avro ./order_date=2026-10-01/000000_0 ./order_date=2026-10-02/000000_0 ./order_date=2026-10-03/000000_0 ./order_date=2026-10-04/000000_0 ./order_date=2026-10-05/000000_0 ./order_date=2026-10-06/000000_0 ./order_date=2026-10-07/000000_0
    Identical numbers. The seven data files were not touched; Hive added a metadata/ folder with two metadata JSON files, one manifest and one manifest list. That is the whole migration. The partition folders keep their old names; Iceberg no longer needs them, because the manifests list every file.

  3. Step 3 · What the table definition became

    SHOW CREATE TABLE orders_mig;
    CREATE EXTERNAL TABLE `orders_mig`( … `order_date` date) PARTITIONED BY SPEC (`order_date`) ROW FORMAT SERDE 'org.apache.iceberg.mr.hive.HiveIcebergSerDe' STORED BY 'org.apache.iceberg.mr.hive.HiveIcebergStorageHandler' LOCATION 'file:/opt/hive/data/warehouse/tiffingo.db/orders_mig' TBLPROPERTIES ( 'MIGRATED_TO_ICEBERG'='true', 'current-snapshot-summary'='{"added-data-files":"7","added-records":"11631", … "iceberg-version":"Apache Iceberg 1.9.1 …"}', 'format-version'='2', 'metadata_location'='file:/…/orders_mig/metadata/00001-dec3245f-….metadata.json', 'schema.name-mapping.default'='[ {"field-id" : 1, "names" : [ "order_id" ]}, … ]', 'table_type'='ICEBERG', 'write.delete.mode'='merge-on-read', 'write.format.default'='parquet', 'write.update.mode'='merge-on-read', …)
    The storage handler and SerDe are Iceberg’s, the partition is now a PARTITIONED BY SPEC, and the first snapshot records 7 files and 11,631 rows. format-version 2 allows row-level deletes; merge-on-read writes small delete files instead of rewriting data. schema.name-mapping.default lets Iceberg read the old Parquet files, which have column names but no Iceberg field IDs.

  4. Step 4 · ACID tables cannot migrate in place

    ALTER TABLE orders_tx SET TBLPROPERTIES (
  'storage_handler'='org.apache.iceberg.mr.hive.HiveIcebergStorageHandler');

CREATE TABLE orders_tx_ice STORED BY ICEBERG STORED AS PARQUET AS SELECT * FROM orders_tx;
SELECT COUNT(*) AS n FROM orders_tx_ice;
SELECT order_id, status FROM orders_tx_ice WHERE order_id > 999000000 ORDER BY order_id;

-- Trino
SELECT COUNT(*) AS n FROM iceberg.tiffingo.orders_tx_ice;
    Error: Error while compiling statement: FAILED: Execution Error, return code 40013 from org.apache.hadoop.hive.ql.ddl.DDLTask. Unable to alter table. MetaException(message:Converting non-external, temporary or transactional hive table to iceberg table is not allowed.) +----------+ | n | +----------+ | 5000001 | +----------+ +------------+------------+ | order_id | status | +------------+------------+ | 999000010 | CANCELLED | +------------+------------+ -- Trino n --------- 5000001 (1 row)
    Hive refused to convert the transactional table. The copy did what Lesson 11.1 could not: Hive applied all deletes and updates while reading, so the new table has 5,000,001 rows with order 999000010 once, CANCELLED. Trino now returns 5,000,001 too, where it returned 5,000,004 from the ACID table. One table format, one answer.

  5. Step 5 · Change the partitioning without rewriting

    ALTER TABLE orders_mig SET PARTITION SPEC (month(order_date));
INSERT INTO orders_mig SELECT order_id, customer_id, city, amount, status, order_date
FROM orders WHERE order_date BETWEEN '2026-10-08' AND '2026-10-14';

SELECT spec_id, `partition`, record_count FROM tiffingo.orders_mig.files ORDER BY spec_id, record_count;
    +----------+----------------------------------------------------+---------------+ | spec_id | partition | record_count | +----------+----------------------------------------------------+---------------+ | 0 | {"order_date":"2026-10-02","order_date_month":null} | 1617 | | 0 | {"order_date":"2026-10-05","order_date_month":null} | 1621 | | 0 | {"order_date":"2026-10-01","order_date_month":null} | 1641 | | 0 | {"order_date":"2026-10-07","order_date_month":null} | 1662 | | 0 | {"order_date":"2026-10-03","order_date_month":null} | 1668 | | 0 | {"order_date":"2026-10-06","order_date_month":null} | 1678 | | 0 | {"order_date":"2026-10-04","order_date_month":null} | 1744 | | 1 | {"order_date":null,"order_date_month":681} | 11751 | +----------+----------------------------------------------------+---------------+
    Seven small daily files stay in spec 0; the new week went into one monthly file under spec 1 (681 is months since 1970, i.e. October 2026). Queries filtering on order_date prune both layouts, because Iceberg partitions are hidden: users never write the partition column. In plain Hive, changing the partition scheme means rewriting the whole table. (partition is a reserved word, hence the backticks.)

  6. Step 6 · Row-level changes become snapshots

    DELETE FROM orders_mig WHERE status = 'CANCELLED' AND order_date = '2026-10-03';
UPDATE orders_mig SET amount = amount + 10
WHERE order_id = (SELECT MIN(order_id) FROM orders_mig WHERE order_date = '2026-10-10');

SELECT snapshot_id, operation, summary['added-records'] AS added,
       summary['deleted-records'] AS deleted, summary['added-position-deletes'] AS pos_del
FROM tiffingo.orders_mig.snapshots ORDER BY committed_at;
    +--------+-------------+ | n | amt | +--------+-------------+ | 23276 | 6869400.00 | +--------+-------------+ +----------------------+------------+--------+----------+----------+ | snapshot_id | operation | added | deleted | pos_del | +----------------------+------------+--------+----------+----------+ | 6356967414929367428 | append | 11631 | NULL | NULL | | 8935160337224414664 | append | 11751 | NULL | NULL | | 7700454950423225386 | delete | NULL | NULL | 106 | | 7073719229572187090 | overwrite | 1 | NULL | 1 | +----------------------+------------+--------+----------+----------+
    DML works on the migrated table, with no transactional property. The DELETE wrote one position-delete file for 106 rows; the UPDATE wrote one new row and one position delete. Four snapshots: migration, the new week, the delete and the update. 23,382 − 106 = 23,276 rows.

  7. Step 7 · Time travel, rollback, and Trino agrees

    SELECT COUNT(*) AS n, SUM(amount) AS amt FROM orders_mig FOR SYSTEM_VERSION AS OF 8935160337224414664;
-- Trino, before the rollback
SELECT COUNT(*) AS n, SUM(amount) AS amt FROM iceberg.tiffingo.orders_mig;

ALTER TABLE orders_mig EXECUTE ROLLBACK(8935160337224414664);
SELECT COUNT(*) AS n, SUM(amount) AS amt FROM orders_mig;
SELECT snapshot_id, is_current_ancestor FROM tiffingo.orders_mig.history;
-- Trino, after
SELECT COUNT(*) AS n FROM iceberg.tiffingo.orders_mig;
    +--------+-------------+ | n | amt | +--------+-------------+ | 23382 | 6899030.00 | +--------+-------------+ -- Trino, before the rollback n | amt -------+------------ 23276 | 6869400.00 (1 row) +--------+-------------+ | n | amt | +--------+-------------+ | 23382 | 6899030.00 | +--------+-------------+ +----------------------+----------------------+ | snapshot_id | is_current_ancestor | +----------------------+----------------------+ | 6356967414929367428 | true | | 8935160337224414664 | true | | 7700454950423225386 | false | | 7073719229572187090 | false | | 8935160337224414664 | true | +----------------------+----------------------+ -- Trino, after n ------- 23382 (1 row)
    Time travel read the state before the DELETE: 23,382 rows. Trino saw the current state with exactly Hive’s count and sum. The rollback moved the table pointer back; the history shows the DELETE and UPDATE snapshots as no longer ancestors, and Trino immediately read 23,382. Undoing a bad load is one statement, not a restore from backup.

  8. Step 8 · The folder is no longer the table

    cp orders_mig/order_date=2026-10-01/000000_0 orders_mig/order_date=2026-10-15/000000_0

MSCK REPAIR TABLE orders_mig;
SELECT COUNT(*) AS n FROM orders_mig;
    +--------+ | n | +--------+ | 23382 | +--------+
    In Lesson 11.2, a file copied into a new folder became visible after MSCK. Here it stays invisible: Iceberg reads only the files listed in its manifests. That protects the table from half-written or stray files, but it means every writer must commit through an Iceberg-aware engine. Upstream jobs that “just drop files” must change during the migration.

  9. Step 9 · What each migration path costs

    -- in place, on an external ORC copy
ALTER TABLE ob_copy SET TBLPROPERTIES ('storage_handler'='org.apache.iceberg.mr.hive.HiveIcebergStorageHandler');
-- copy
CREATE TABLE ob_ctas STORED BY ICEBERG STORED AS ORC AS SELECT * FROM orders_big;
    orders_big: 5,000,000 rows, 9.9 MB ORC (wall time incl. ~3.5 s Beeline start) method time data files rewritten rows after in-place (SET TBLPROPERTIES) 4.4 s 0 (metadata added) 5,000,000 CTAS ... STORED BY ICEBERG 16.7 s all (new 9.9 MB) 5,000,000
    Both tables returned 5,000,000 rows. The in-place migration took about one second beyond Beeline’s start-up, because it only writes metadata; the copy reads and writes every row, so its cost grows with the data. At 200 TB the difference is hours of cluster time and double storage until the old table is dropped. Use in place where you can, copy where you must.

Interview and viva questions

Can I go back after an in-place migration?

Not with a single built-in statement in our version. Because the data files are unchanged, you can recreate a plain external table on the same location as an emergency path, but files written after the migration may live in new folders and contain delete files. Test on a copy and keep the old DDL.

Iceberg, Delta or Hudi?

For Hive users Iceberg is the natural choice: Hive 4 supports it natively and Trino, Spark, Flink and the big cloud warehouses read it. Delta Lake fits Databricks-centred platforms; Hudi is strong for CDC upserts. Interoperability layers such as Delta UniForm and Apache XTable reduce lock-in.

Do I still need the Hive metastore?

Iceberg needs a catalogue to store the current metadata pointer. The Hive metastore is one option and is already there after a Hive migration; REST catalogues such as Apache Polaris, AWS Glue or Unity Catalog are others.

What about snapshot growth?

Every commit adds a snapshot and files. Schedule snapshot expiry and compaction (Lesson 7.3) so storage and planning time stay under control, while keeping enough history for rollback.

Why did Spark not appear in this lesson?

In Lesson 11.1, Spark 3.5’s Iceberg catalog could not talk to the Hive 4 metastore because of the metastore client version. With a compatible client or a REST catalogue, Spark reads the same Iceberg tables.

Real-world scenario questions (asked in company interviews)

Lakehouse and migration questions are common for senior data roles in 2026.

Any company · lakehouseFresher

“What is a lakehouse?”

Explain a lakehouse and where Hive fits.

The interviewer is checking: do you know table formats?

Show a strong answer

Data stays in open files (Parquet/ORC) in a lake or object store; a table format such as Iceberg adds transactions, snapshots, schema and partition evolution; a shared catalogue lets Hive, Spark, Trino and others use the same tables. Hive 4 creates and queries Iceberg tables natively and its metastore can be the catalogue.

Avoid: Saying a lakehouse is a product you buy.

Data engineeringMid-level

Migrate a Hive table to Iceberg

An external ORC table of 50 TB must become Iceberg with minimal downtime.

The interviewer is checking: do you know in-place migration?

Show a strong answer
  1. Record per-partition counts and sums.
  2. Migrate in place with the Iceberg storage handler: metadata only, no data copy.
  3. Validate in every engine, then switch writers to Iceberg-aware commits.

Avoid: Copying 50 TB with CTAS when in place is possible.

PlatformMid-level

Rows written but not visible

After migration, an upstream job’s new files do not appear in queries.

The interviewer is checking: do you understand manifests?

Show a strong answer
  • The job still writes files into folders; Iceberg ignores files not in its manifests (MSCK does not help).
  • Change the job to write through Spark, Flink, Hive or Trino with the Iceberg catalogue.
  • Short-term: register files with an add_files procedure after validating their schema.

Avoid: Running MSCK REPAIR again.

ArchitectureSenior

Plan a warehouse-to-lakehouse migration

800 Hive tables, 150 ACID, Spark and Trino users, cloud move planned.

The interviewer is checking: can you sequence the work?

Show a strong answer
  • Inventory; waves: external in place, ACID by copy with name swap; catalogue choice (HMS vs REST) up front.
  • Automated validation per partition in every engine; maintenance jobs for snapshot expiry and compaction.
  • Combine with the cloud move: Iceberg removes rename-based commits on object storage.

Avoid: Migrating everything in one weekend without validation.
