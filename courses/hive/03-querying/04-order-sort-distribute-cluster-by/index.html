ORDER BY, SORT BY, DISTRIBUTE BY and CLUSTER BY

Hive has four ways to order data, and interviewers love asking about them. Instead of describing them, this lesson runs all four on the same twelve TiffinGo orders with three reducers and opens the files each reducer wrote. You will see why SORT BY gave three overlapping sorted files, why ORDER BY wrote one, and how DISTRIBUTE BY with SORT BY gives you per-city order. All outputs are real, from Hive 4.2.1.

1 The story

“The file is sorted… but Rs 530 is at the bottom”

Before you start: know what a reducer and the shuffle are (Lesson 1.4) and how INSERT OVERWRITE DIRECTORY works (Lesson 2.6).

Kabir exports the twelve newest orders sorted by amount, highest first, for the finance team. He used SORT BY amount DESC because a colleague said it is faster than ORDER BY. Finance replies with a screenshot: three files, each sorted, but the Rs 530 order sits alone in the last file, after Rs 40.

Kabir

Sir, SORT BY and ORDER BY both sort. Why did I get three files?

Arjun Sir

Because Hive gives you four ordering tools, and they answer different questions. ORDER BY promises one total order, so it must bring all rows to one reducer. SORT BY only sorts within each reducer, so with three reducers you get three sorted pieces. DISTRIBUTE BY decides which reducer each row goes to, and CLUSTER BY does both distribute and sort on the same column.

Riya

So SORT BY is useless?

Arjun Sir

Not at all. It is exactly what you want when the next step works per group, like writing one sorted file per city, or feeding a script that processes each customer’s orders in time order. We will run all four on the same twelve orders with three reducers and open the files they write.

2 Definition

ORDER BY, SORT BY, DISTRIBUTE BY and CLUSTER BY

Formal definition (write this in exams)

ORDER BY guarantees a total ordering of the query result and is executed with a single final reducer. SORT BY sorts rows within each reducer only, giving a partial order when several reducers run. DISTRIBUTE BY controls how rows are partitioned among reducers: rows with equal distribute-key values are sent to the same reducer, without sorting. CLUSTER BY col is shorthand for DISTRIBUTE BY col SORT BY col (ascending).

In simple words

ORDER BY sorts the whole result (one reducer does it). SORT BY sorts each reducer’s share separately. DISTRIBUTE BY decides which reducer gets which rows. CLUSTER BY distributes and sorts by the same column.

Words you’ll meet in this lesson

Total orderEvery row is in order relative to every other row.
Partial orderRows are ordered only inside groups (here: inside each reducer’s output).
ReducerA task after the shuffle; each one writes its own output file (000000_0, 000001_0 …).
Hash partitioninghash(key) mod number-of-reducers decides the reducer for a row.
Top-NORDER BY … LIMIT n: only the n best rows are needed.
Strict modeSafety checks that reject risky queries, such as ORDER BY without LIMIT.
NULLS FIRST/LASTWhere NULL values go in the sort order.
mapred.reduce.tasksA setting that fixes the number of reducers (−1 = let Hive estimate).

Ordering at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Sorting exam papers

  • ORDER BY: one teacher collects every paper and sorts the whole pile. Correct, but one person does all the work.
  • SORT BY: three teachers each sort the papers they happened to receive. Three neat piles, but not one ordered pile.
  • DISTRIBUTE BY section: all papers of section A go to teacher 1, B to teacher 2… Nobody sorts yet.
  • CLUSTER BY section: same distribution, and each teacher sorts by section.

Intermediate The four clauses

  • ORDER BY col [ASC|DESC] [NULLS FIRST|LAST]: total order of the final result; uses a single reducer for the sort.
  • SORT BY col: each reducer sorts its own rows; no global order.
  • DISTRIBUTE BY col: rows with the same value go to the same reducer (by hash); no sorting.
  • CLUSTER BY col = DISTRIBUTE BY col SORT BY col, ascending only. For descending or a different sort column, write DISTRIBUTE BY + SORT BY yourself.
  • Number of reducers for SORT/DISTRIBUTE/CLUSTER: estimated from data size or set with mapred.reduce.tasks (we used 3).

Advanced Details tested on Hive 4.2.1

  • With mapred.reduce.tasks=3, ORDER BY still wrote one file; SORT BY, DISTRIBUTE BY and CLUSTER BY wrote three.
  • Strict mode: hive.strict.checks.orderby.no.limit=true rejects ORDER BY without LIMIT (“disabled for safety reasons”); it is false by default.
  • NULL order: hive.default.nulls.last=true (default) puts NULLs last in ASC and first in DESC; override with NULLS FIRST/LAST.
  • Positions: ORDER BY 2 DESC works by default (hive.orderby.position.alias=true), unlike GROUP BY 1.
  • Top-N: ORDER BY … LIMIT 10 lets each task keep only its top rows before the final merge, so it is cheap even on big data.
  • DISTRIBUTE BY uses a hash of the value: which city lands in which file is not alphabetical (Delhi alone in file 0).

Exam tip: “Differentiate ORDER BY, SORT BY, DISTRIBUTE BY and CLUSTER BY.” A four-row table: ORDER BY = total order, one reducer; SORT BY = sorted per reducer, partial order; DISTRIBUTE BY = same key to same reducer, unsorted; CLUSTER BY = DISTRIBUTE BY + SORT BY on one column, ascending only. Add “ORDER BY needs LIMIT in strict mode”.

3 Types and ways to use it

Which ordering for which job?

ORDER BY … LIMIT

Top 10 restaurants by revenue, latest 50 orders. Cheap: each task keeps its own top rows; the final reducer merges a few.

Most common

ORDER BY (whole result)

A small final report that people read. Fine for thousands of rows; dangerous for billions (one reducer).

Small results

DISTRIBUTE BY + SORT BY

Write one sorted file per city, or feed a TRANSFORM script that needs each customer’s orders together and in time order.

Per-key work

CLUSTER BY

Short form when you distribute and sort by the same column, ascending. Also used before writing bucketed tables in older Hive.

  3. Step 3 · DISTRIBUTE BY: same city, same file

    … SELECT city, amount FROM orders WHERE order_id < 100013 DISTRIBUTE BY city;

  4. Step 4 · CLUSTER BY: distribute and sort by city

    … SELECT city, amount FROM orders WHERE order_id < 100013 CLUSTER BY city;

The same 12 rows, four ways 5 steps
What you see
  1. SORT BY with three reducers writes three files; the 530 order ends up alone in the third file.
  2. ORDER BY writes a single file in total order.
  3. DISTRIBUTE BY city puts all Mumbai and Pune orders in the same file, unsorted.
  4. CLUSTER BY city sorts each file by city.
  5. DISTRIBUTE BY city with SORT BY city, amount DESC gives each city’s orders from highest to lowest.
Behind the screen
  1. Rows go to reducers without a key, and each reducer sorts only its own rows.
  2. All rows meet in one reducer for the final sort.
  3. hash(city) chooses the reducer, so every row of a city meets in one place.
  4. Each reducer receives whole cities and sorts them by city name.
  5. The sort key can differ from the distribute key, giving any order within each group.

6 Real-world use

Ordering in real pipelines

1. Leaderboards

Top restaurants by rating, top customers by spend, latest failed payments: ORDER BY with LIMIT stays fast on any table size.

Big table→ORDER BY … LIMIT→Top-N list

2. Per-customer processing

Session building, churn features and fraud scoring scripts need each customer’s events together and in time order: DISTRIBUTE BY customer SORT BY time.

Events→DISTRIBUTE + SORT→Script / UDF

3. Better-compressed files

Writing ORC data sorted by a filter column (SORT BY city, order_date) makes min/max statistics tight, so later queries skip more data.

INSERT …→SORT BY→Skippable stripes

4. Cluster guard rails

Shared clusters enable strict checks so a single careless ORDER BY on a billion rows cannot block a reducer slot for hours.

Query→Strict mode→Rejected early

5. Readable reports

Reports that sort descending add NULLS LAST so missing values do not crowd the top of the page.

Report→ORDER BY … NULLS LAST→Readable list

Run the code: reducers by hand

These programs imitate the shuffle: a hash of the distribute key picks a reducer, each reducer sorts its own rows, and ORDER BY merges everything into one list. Press Run, then try the challenges. (Python’s simple hash differs from Hive’s, so cities may land on other reducers than in the lab.)

# Simulate 3 reducers: DISTRIBUTE BY city, then SORT BY within each reducer
rows = [("Mumbai", 530), ("Mumbai", 500), ("Pune", 410), ("Thane", 300), ("Mumbai", 180),
        ("Pune", 40), ("Mumbai", 590), ("Delhi", 310), ("Pune", 460), ("Thane", 250)]
R = 3

reducers = [[] for _ in range(R)]
for city, amount in rows:
    r = sum(city.encode()) % R            # a simple hash of the key
    reducers[r].append((city, amount))

for i, part in enumerate(reducers):
    part.sort(key=lambda x: (x[0], -x[1]))      # SORT BY city, amount DESC
    print(f"reducer {i}:", part)
reducer 0: [('Delhi', 310), ('Mumbai', 590), ('Mumbai', 530), ('Mumbai', 500), ('Mumbai', 180), ('Pune', 460), ('Pune', 410), ('Pune', 40)] reducer 1: [('Thane', 300), ('Thane', 250)] reducer 2: []

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.4 in one screen

  • ORDER BY: total order, final sort in one reducer; use with LIMIT on big data.
  • SORT BY: sorted within each reducer; files overlap; no global order.
  • DISTRIBUTE BY k: same k → same reducer (hash), unsorted; several keys can share a reducer.
  • CLUSTER BY k = DISTRIBUTE BY k SORT BY k, ascending only. Not the same as bucketing (CLUSTERED BY … INTO n BUCKETS).
  • DISTRIBUTE BY k SORT BY k, x DESC: per-key groups in any order.
  • Reducers for SORT/DISTRIBUTE/CLUSTER: estimated or mapred.reduce.tasks; ORDER BY ignores it for the final sort.
  • hive.strict.checks.orderby.no.limit (default false), hive.default.nulls.last (true: NULLs last ASC, first DESC), NULLS FIRST|LAST, ORDER BY 2 allowed.
  • Top-N (ORDER BY … LIMIT n) is cheap: local top-n per task, small final merge.

Interview and viva questions

Is SORT BY faster than ORDER BY?

For large data, yes, because many reducers sort in parallel, but it answers a different question: you get several individually sorted outputs, not one ordered result. If you need the overall top rows, use ORDER BY with LIMIT; if you need per-key order for a later step, use DISTRIBUTE BY with SORT BY.

What is the difference between CLUSTER BY and CLUSTERED BY?

CLUSTER BY is a query clause that distributes and sorts rows for that query only. CLUSTERED BY (col) INTO n BUCKETS is part of CREATE TABLE and fixes how a table’s data is split into bucket files permanently (Module 5). The names are similar; the purposes are not.

Does the order of rows survive into the next query?

No. Tables have no guaranteed row order. Even if you write sorted files, a later SELECT without ORDER BY may read them in parallel and return rows in any order. Sorting files is still useful for compression and data skipping, not for result order.

How many reducers will Hive use?

By default Hive estimates from the input size (bytes per reducer) up to a maximum, and Tez can adjust it at run time. You can fix it with mapred.reduce.tasks (we used 3 to make the effect visible). ORDER BY still uses one reducer for its final total sort.

Can I sort by a column that is not selected?

Usually yes for ORDER BY on simple queries, but with SELECT DISTINCT or GROUP BY the sort columns must be among the selected or grouped expressions. For SORT BY and DISTRIBUTE BY, the columns must be available in the rows reaching the reducer. When in doubt, select the column too.

Show solution and explanation 
print("Rs", 12 * 3 * 60 * 12, "per year")
Rs 25920 per year

How it works: Rs 25,920 a year in reducer time, plus fewer blocked jobs for other teams.

Real-world scenario questions (asked in company interviews)

The four ordering clauses are a classic Hive interview topic. Good answers use evidence like reducer output files.

Any company · conceptsFresher

“ORDER BY vs SORT BY?”

The interviewer asks for the difference and when you would use each.

The interviewer is checking: do you know the reducer-level behaviour?

Show a strong answer
  • ORDER BY gives a total order using a single final reducer; fine with LIMIT or small results.
  • SORT BY sorts within each reducer; with several reducers the overall output is only partially ordered.
  • Use SORT BY with DISTRIBUTE BY when downstream processing works per key.

Avoid: “SORT BY is just a faster ORDER BY”.

Operations · performanceMid-level

A job stuck at 99%

An export with ORDER BY event_time over 2 billion rows stays at 99% for hours.

The interviewer is checking: can you diagnose a single-reducer bottleneck?

Show a strong answer
  1. ORDER BY funnels everything to one reducer for the final sort.
  2. Ask whether a total order is needed; usually LIMIT, per-key sorting or none is enough.
  3. Enable hive.strict.checks.orderby.no.limit on shared clusters.

Avoid: adding more reducers: ORDER BY still uses one for the final sort.

Data engineering · designMid-level

Per-customer processing

A Python TRANSFORM script must see each customer’s events together and in time order.

The interviewer is checking: do you know DISTRIBUTE BY + SORT BY?

Show a strong answer
SELECT TRANSFORM (customer_id, event_ts, event)
USING 'python3 sessions.py' AS (customer_id, session_id, events)
FROM (SELECT customer_id, event_ts, event FROM events
      DISTRIBUTE BY customer_id
      SORT BY customer_id, event_ts) t;

Avoid: CLUSTER BY customer_id alone: events would not be in time order.

Data platform · termsFresher

CLUSTER BY vs CLUSTERED BY

A candidate mixes up CLUSTER BY in a query and CLUSTERED BY in CREATE TABLE.

The interviewer is checking: do you separate query-time and storage-time concepts?

Show a strong answer
  • CLUSTER BY: query clause = DISTRIBUTE BY + SORT BY, for that query only.
  • CLUSTERED BY … INTO n BUCKETS: table property; data stored in n bucket files by hash of the column (Module 5).

Avoid: treating them as the same feature.
