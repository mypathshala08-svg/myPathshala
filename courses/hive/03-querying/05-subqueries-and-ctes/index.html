Subqueries, CTEs and UNION

Real questions need several steps: compute revenue per city, then the average, then compare. Hive lets one query use another in FROM, in WHERE and as named steps with WITH. This lesson rewrites a nested report as readable CTEs, reproduces the famous NOT IN trap that returns zero rows, and compares lists with UNION, INTERSECT and EXCEPT. All outputs are real, from Hive 4.2.1.

1 The story

“Which cities beat the average city, and by how much?”

Riya inherits a 40-line report query with three levels of brackets: revenue per city, then the average of those revenues, then the cities above average. Nobody dares to touch it. She also has a bug: a “cities without orders” check returns nothing, although Nashik clearly has no orders.

Riya

Sir, can a query use the result of another query?

Arjun Sir

In three places. In FROM, a subquery is a temporary table. In WHERE, a subquery answers a question such as “is this customer in the Gold list?”. And with WITH, a common table expression, you give each step a name and read the query top to bottom like a recipe.

Kabir

And her empty result?

Arjun Sir

That is the most famous trap in SQL: NOT IN with a NULL in the list returns no rows at all. We will reproduce it, then fix it with NOT EXISTS. Today you will also stack results with UNION, find common rows with INTERSECT and differences with EXCEPT.

2 Definition

Subqueries, CTEs and set operations

Formal definition (write this in exams)

A subquery is a SELECT statement nested inside another statement: in the FROM clause as a derived table (which must be aliased), or in WHERE/HAVING (and in Hive 4 the SELECT list) as an IN, EXISTS or scalar subquery, optionally correlated with the outer query. A common table expression (CTE) defines named, statement-scoped result sets with WITH name AS (SELECT …). Set operations combine results of compatible queries: UNION ALL (all rows), UNION [DISTINCT], INTERSECT and EXCEPT/MINUS.

In simple words

You can use one query’s result inside another: as a temporary table, as a list to check against, or as a single number to compare with. WITH lets you name each step. UNION, INTERSECT and EXCEPT combine two result lists like set operations.

Words you’ll meet in this lesson

Derived tableA subquery in FROM, used like a table: FROM (SELECT …) r.
Correlated subqueryA subquery that refers to the outer row: WHERE o.customer_id = c.customer_id.
Scalar subqueryReturns exactly one value, e.g. the overall average.
CTECommon table expression: WITH name AS (…), valid for one statement.
InliningReplacing a CTE or view by its query text during compilation.
MaterialisationComputing a CTE once into a temporary table and reusing it.
Set operationUNION, INTERSECT, EXCEPT: combine two results with the same columns.
NOT IN trapA NULL in the NOT IN list makes the condition NULL for every row.

Subqueries at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A question inside a question

  • “Show the Gold customers’ orders” needs a list first (who is Gold?) and then a filter. The inner question is a subquery.
  • A CTE (WITH name AS (…)) is the same idea with a label, like writing intermediate results on a whiteboard with headings.
  • UNION stacks two lists; INTERSECT keeps what is on both; EXCEPT keeps what is only on the first.

Intermediate Where subqueries can go in Hive

  • FROM (subquery) alias: a derived table. Hive requires the alias (ParseException without it in our lab).
  • WHERE col [NOT] IN (subquery), WHERE [NOT] EXISTS (subquery): correlated subqueries can refer to the outer row.
  • Scalar subqueries returning one value: in WHERE and HAVING (amount > (SELECT AVG(amount) * 2.5 FROM orders)), and in Hive 4 also in the SELECT list (tested).
  • WITH a AS (…), b AS (…) SELECT …: later CTEs can use earlier ones; a CTE exists only for that statement.
  • UNION ALL keeps duplicates; UNION (= UNION DISTINCT) removes them; INTERSECT, EXCEPT and MINUS are supported (distinct by default). Both sides must have the same number of compatible columns.

Advanced How Hive runs them

  • IN/EXISTS subqueries become joins: semi joins for IN/EXISTS, anti joins for NOT EXISTS. Check EXPLAIN.
  • NOT IN and NULL: x NOT IN (a, b, NULL) is never true (it is NULL when x is not a or b), so the whole query returns nothing. NOT EXISTS ignores NULLs.
  • CTE materialisation: a CTE is normally inlined like a view. If it is referenced at least hive.optimize.cte.materialize.threshold times (3 in our lab), Hive computes it once into a temporary table.
  • UNION needs an extra de-duplication shuffle; prefer UNION ALL when duplicates are impossible or wanted.
  • Scalar subqueries must return at most one row; otherwise the query fails at run time.

Exam tip: “What is a subquery? Give two types.” Define it as a query inside another, then show a FROM-clause subquery (with alias) and a WHERE-clause subquery with IN or EXISTS. Mention that Hive converts IN/EXISTS into semi joins and that CTEs (WITH) make long queries readable.

3 Types and ways to use it

Subquery forms and set operations

FROM-clause subquery

A temporary table inside one query. Must have an alias: FROM (…) r.

Derived table

IN / NOT IN

Membership in a list. Safe with IN; dangerous with NOT IN when the list can contain NULL.

Lists

EXISTS / NOT EXISTS

Correlated yes/no test per row. The safe way to write anti joins.

Existence

Scalar subquery

One value: thresholds, averages, maximums. Allowed in WHERE, HAVING and (Hive 4) SELECT.

Single value

WITH (CTE)

Named steps, top to bottom. Can chain: later CTEs read earlier ones.

Readability

UNION ALL / UNION

Stack results; UNION removes duplicates with an extra shuffle.

Combine

INTERSECT / EXCEPT

Common rows / rows only in the first result; MINUS is a synonym for EXCEPT.

Compare

Never write WHERE id NOT IN (SELECT id FROM other) unless other.id is declared or filtered NOT NULL. One NULL and the query silently returns zero rows. NOT EXISTS gives the expected answer.

From nested brackets to named steps

All outputs are real, from the Hive 4.2.1 lab.

  1. Step 1 · A subquery in FROM (with its alias)

    SELECT city, revenue
FROM (SELECT city, SUM(amount) AS revenue FROM orders GROUP BY city) r
WHERE revenue > 2000000 ORDER BY revenue DESC;

-- the same without the alias r:
SELECT city, revenue FROM (SELECT city, SUM(amount) AS revenue FROM orders GROUP BY city)
WHERE revenue > 2000000;

    The inner query is a temporary table with a column called revenue, which the outer WHERE can filter, something impossible in one level (Lesson 3.1). Hive insists on a name for the derived table.

  2. Step 2 · IN, EXISTS and scalar subqueries in WHERE

    SELECT COUNT(*) AS gold_orders FROM orders
WHERE customer_id IN (SELECT customer_id FROM customers WHERE plan = 'Gold');

SELECT COUNT(*) AS big_spenders FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.customer_id = c.customer_id AND o.amount >= 800);

SELECT order_id, amount FROM orders
WHERE amount > (SELECT AVG(amount) * 2.5 FROM orders)
ORDER BY amount DESC LIMIT 3;
    +--------------+ | gold_orders | +--------------+ | 13014 | +--------------+ +---------------+ | big_spenders | +---------------+ | 51 | +---------------+ +-----------+---------+ | order_id | amount | +-----------+---------+ | 142088 | 880.00 | | 112253 | 880.00 | | 136040 | 880.00 | +-----------+---------+
    Gold customers placed 13,014 orders; 51 customers have at least one order of Rs 800 or more (a correlated EXISTS); and the scalar subquery computes 2.5 × the average once, then filters.

  3. Step 3 · The NOT IN trap

    -- no NULL in the list:
SELECT city FROM city_targets WHERE city NOT IN (SELECT DISTINCT city FROM orders);
-- one NULL added to the list:
SELECT city FROM city_targets WHERE city NOT IN
  (SELECT city FROM (SELECT DISTINCT city FROM orders
                     UNION ALL SELECT CAST(NULL AS STRING) AS city) x);
-- NOT EXISTS with the same list:
SELECT city FROM city_targets t WHERE NOT EXISTS
  (SELECT 1 FROM (… same list with NULL …) x WHERE x.city = t.city);
    +---------+ | city | +---------+ | Nashik | +---------+ +-------+ | city | +-------+ +-------+ +---------+ | city | +---------+ | Nashik | +---------+
    Same question, three answers. With a NULL in the list, 'Nashik' NOT IN (…, NULL) is NULL, not true, so no row survives. NOT EXISTS ignores the NULL and still returns Nashik. This is Riya’s bug.

  4. Step 4 · The same report as named steps (CTEs)

    WITH city_rev AS (SELECT city, SUM(amount) AS revenue FROM orders
                  WHERE status = 'DELIVERED' GROUP BY city),
     avg_rev  AS (SELECT AVG(revenue) AS avg_revenue FROM city_rev)
SELECT c.city, c.revenue, ROUND(c.revenue / a.avg_revenue, 2) AS vs_avg
FROM city_rev c CROSS JOIN avg_rev a
WHERE c.revenue > a.avg_revenue ORDER BY c.revenue DESC;
    +------------+-------------+---------+ | c.city | c.revenue | vs_avg | +------------+-------------+---------+ | Mumbai | 2712610.00 | 1.60 | | Bengaluru | 2499060.00 | 1.47 | | Pune | 2148270.00 | 1.27 | +------------+-------------+---------+
    avg_rev reads city_rev, and the final SELECT reads both. Mumbai earns 1.60 × the average city’s delivered revenue. Each step can be tested alone by selecting from it.

  5. Step 5 · Scalar subqueries in SELECT and HAVING (Hive 4)

    SELECT t.city, (SELECT COUNT(*) FROM orders o WHERE o.city = t.city) AS n
FROM city_targets t ORDER BY t.city LIMIT 3;

SELECT city, SUM(amount) FROM orders GROUP BY city
HAVING SUM(amount) > (SELECT AVG(amount) * 8000 FROM orders);
    +------------+-------+ | t.city | n | +------------+-------+ | Bengaluru | 9298 | | Delhi | 5472 | | Hyderabad | 5979 | +------------+-------+ +------------+-------------+ | city | _c1 | +------------+-------------+ | Bengaluru | 2724070.00 | | Mumbai | 2941120.00 | +------------+-------------+
    A correlated scalar subquery in the SELECT list counts orders per target city; Hive rewrites it into a join and aggregation. HAVING can compare groups with a scalar subquery too.

  6. Step 6 · UNION ALL vs UNION

    SELECT city FROM city_targets UNION ALL SELECT city FROM restaurants WHERE restaurant_id <= 3;
SELECT city FROM city_targets UNION     SELECT city FROM restaurants WHERE restaurant_id <= 3;
    10 rows with UNION ALL (Thane, Mumbai, Thane, Mumbai, Pune, …) +------------+ | city | +------------+ | Bengaluru | | Delhi | | Hyderabad | | Mumbai | | Nashik | | Pune | | Thane | +------------+
    7 targets + 3 restaurants = 10 rows with UNION ALL, duplicates included. UNION removes duplicates: 7 distinct cities, at the cost of an extra shuffle.

  7. Step 7 · INTERSECT, EXCEPT, MINUS

    SELECT DISTINCT city FROM orders INTERSECT SELECT city FROM city_targets;
SELECT city FROM city_targets EXCEPT SELECT DISTINCT city FROM orders;
SELECT DISTINCT city FROM orders MINUS  SELECT city FROM city_targets;
    +------------+ | city | +------------+ | Bengaluru | | Delhi | | Hyderabad | | Mumbai | | Pune | | Thane | +------------+ +---------+ | city | +---------+ | Nashik | +---------+
    Six cities have both orders and targets; Nashik has a target but no orders; Chennai and Navi Mumbai have orders but no target: the same answers the joins gave in Lesson 3.3, written as set operations.

Named steps, and the NULL trap 5 steps
What you see
  1. Riya rewrites the nested report with two named CTEs.
  2. The materialisation threshold is 3; city_rev is used twice, so Hive inlines it.
  3. Three cities beat the average city’s delivered revenue.

Behind the screen
  1. orders feeds city_rev (8 rows), which feeds avg_rev (1 row); the final SELECT uses both.
  2. CTEs are expanded like views; a CTE referenced at least 3 times would be computed once into a temporary table.
  3. Each city’s revenue is divided by the average; only ratios above 1 pass the WHERE.
  4. NOT IN expands to a chain of <> comparisons joined by AND; one comparison with NULL makes the whole result NULL.
  5. NOT EXISTS asks whether a matching row exists. NULL never matches, so it cannot hide the answer.

6 Real-world use

Subqueries and CTEs in real work

1. Readable reporting SQL

Analytics teams write reports as chains of CTEs (filter → aggregate → compare), which code reviewers can follow and test step by step.

Raw tables→CTE chain→Report

2. Segment filters

Marketing defines segments (Gold customers, lapsed users) as subqueries; campaign queries filter orders or events with IN or EXISTS.

Segment→IN / EXISTS→Campaign list

3. Missing-record checks

Payments without orders, deliveries without payments: NOT EXISTS checks run daily and are robust to NULLs in the other table.

Two tables→NOT EXISTS→Exceptions

4. Testing query changes

Before replacing a production query, teams run old EXCEPT new and new EXCEPT old; both must be empty for the change to ship.

Old vs new→EXCEPT ×2→Ship if empty

5. Combining sources

Orders from the app and from partner platforms land in separate tables; a UNION ALL view combines them with a source column for reports.

App + partners→UNION ALL→One order view

orders = [("Mumbai", 590), ("Pune", 410), ("Mumbai", 530), ("Thane", 300),
          ("Pune", 460), ("Delhi", 310), ("Mumbai", 500), ("Thane", 250)]

city_rev = {}                                         # WITH city_rev AS (... GROUP BY city)
for city, amount in orders:
    city_rev[city] = city_rev.get(city, 0) + amount

avg_rev = sum(city_rev.values()) / len(city_rev)     # avg_rev AS (SELECT AVG(revenue) ...)

for city, rev in sorted(city_rev.items(), key=lambda kv: -kv[1]):   # final SELECT

Run on your PC: errors and settings

Two common errors and one setting. Outputs are real, from Hive 4.2.1.

1 · UNION with different columns

SELECT city FROM city_targets UNION ALL SELECT city, region FROM city_targets;
Error: Error while compiling statement: FAILED: SemanticException Schema of both sides of union should match.

Both sides of a set operation need the same number of columns with compatible types. Add a NULL or constant column to the shorter side if needed.

2 · When are CTEs materialised?

SET hive.optimize.cte.materialize.threshold;
+--------------------------------------------+ | set | +--------------------------------------------+ | hive.optimize.cte.materialize.threshold=3 | +--------------------------------------------+

A CTE referenced at least 3 times in a query is computed once into a temporary table; otherwise it is inlined like a view. Materialising saves repeated work for expensive CTEs.

3 · Derived tables need a name

SELECT city, revenue FROM (SELECT city, SUM(amount) AS revenue FROM orders GROUP BY city)
WHERE revenue > 2000000;
Error: Error while compiling statement: FAILED: ParseException line 1:90 cannot recognize input near 'WHERE' 'revenue' '>' in subquery source

Add an alias after the closing bracket: … GROUP BY city) r WHERE ….

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.5 in one screen

  • Subquery in FROM = derived table, alias required.
  • IN, EXISTS (correlated allowed) in WHERE; Hive turns them into semi joins; NOT EXISTS → anti join.
  • Scalar subquery (one value) in WHERE, HAVING and, in Hive 4, the SELECT list.
  • NOT IN + NULL in the list → zero rows. Use NOT EXISTS or filter NULLs inside the subquery.
  • WITH a AS (…), b AS (…): named, statement-scoped steps; later CTEs can use earlier ones. Inlined unless used ≥ hive.optimize.cte.materialize.threshold (3) times.
  • UNION ALL keeps duplicates; UNION removes them (extra shuffle). Same column count and compatible types required.
  • INTERSECT (common), EXCEPT / MINUS (first minus second), distinct by default.
  • Prove a refactor: (old EXCEPT new) and (new EXCEPT old) both empty.

Interview and viva questions

Is a CTE faster than a subquery?

Usually neither: Hive inlines a CTE just like a subquery, so the plan is the same. The benefit is readability and testability. A CTE used many times can be materialised (threshold setting), which may help or hurt depending on its cost; check EXPLAIN.

Can I use a CTE in another query later?

No. A CTE exists only for the statement it belongs to. To reuse logic, create a view (logic only, Module 9) or a table (stored result) with CTAS.

Why does NOT IN behave strangely with NULL?

x NOT IN (a, b, NULL) means x <> a AND x <> b AND x <> NULL. The last comparison is NULL, so the whole condition is NULL when x is neither a nor b, and WHERE keeps only TRUE. NOT EXISTS asks whether a matching row exists, which NULLs cannot satisfy, so it gives the intuitive answer.

UNION or UNION ALL in pipelines?

UNION ALL whenever the inputs cannot overlap or duplicates are meaningful (most pipelines, e.g. combining app and partner orders). UNION adds a de-duplication shuffle; use it only when you really need distinct rows, and consider whether a key-based de-duplication (ROW_NUMBER, Lesson 3.6) is more correct.

Do INTERSECT and EXCEPT treat NULLs as equal?

Set operations compare whole rows and treat NULLs in the same position as matching for the purpose of duplicates and comparison, unlike the = operator. This makes them handy for comparing two result sets that contain NULLs.

P5Medium

NOT IN vs NOT EXISTS

For x = 5 and lists [1, 2] and [1, 2, None], compute NOT IN (three-valued) and NOT EXISTS.

Input
x = 5
Expected output
[1, 2] NOT IN: True | NOT EXISTS: True
[1, 2, None] NOT IN: None | NOT EXISTS: True
Show solution and explanation 
def not_in(x, lst):
    if x in [v for v in lst if v is not None]: return False
    return None if None in lst else True
for lst in ([1, 2], [1, 2, None]):
    print(lst, "NOT IN:", not_in(5, lst), "| NOT EXISTS:", not any(v == 5 for v in lst if v is not None))

How it works: With None in the list NOT IN is unknown (None) while NOT EXISTS stays True.

print("NOT IN with a NULL:", 0)
NOT EXISTS: 380 NOT IN with a NULL: 0

How it works: 380 versus 0: a silent business failure caused by one NULL.

P8Business problem

Revenue share above average

What share of total delivered revenue comes from the three above-average cities (Mumbai 27.13 lakh, Bengaluru 24.99, Pune 21.48; total 135.55 lakh)?

Input
real delivered revenue in lakh
Expected output
54.3% of delivered revenue from 3 of 8 cities
Show solution and explanation 
top = 27.13 + 24.99 + 21.48
print(f"{top / 135.55:.1%} of delivered revenue from 3 of 8 cities")
54.3% of delivered revenue from 3 of 8 cities

How it works: About 54.3%, from the real delivered revenue. CTEs make such follow-up questions a one-line change to the final SELECT.

Real-world scenario questions (asked in company interviews)

Subquery questions test SQL depth. The NOT IN trap and CTE readability come up again and again.

Any company · SQLFresher

“Write it with a subquery”

Find cities whose total revenue is above the average city revenue.

The interviewer is checking: can you layer queries correctly?

Show a strong answer
WITH city_rev AS (SELECT city, SUM(amount) AS revenue FROM orders GROUP BY city)
SELECT city, revenue
FROM city_rev
WHERE revenue > (SELECT AVG(revenue) FROM city_rev);

Avoid: AVG(amount) of orders instead of the average of city revenues.

Data qualityMid-level

A query suddenly returns zero rows

A NOT IN query that worked for months returns nothing after a source system change.

The interviewer is checking: do you know NOT IN with NULLs?

Show a strong answer
  1. Check the subquery column for NULLs: a single NULL makes NOT IN unknown for every row.
  2. Rewrite with NOT EXISTS, or add WHERE col IS NOT NULL inside the subquery.
  3. Add monitoring for sudden drops to zero.

Avoid: “Hive lost the data”.

Analytics engineeringMid-level

Refactoring a legacy query

You must change a 200-line nested query and prove the result did not change.

The interviewer is checking: do you have a safe refactoring method?

Show a strong answer
  • Rewrite as CTEs, one per logical step, and test each step’s row counts.
  • Compare old and new with EXCEPT in both directions plus COUNT(*).
  • Keep the final query in version control with a short description of each CTE.

Avoid: “it looks the same to me”.

Data engineeringFresher

Combining two order sources

App orders and partner orders are in two tables with the same columns. Build one view for reporting.

The interviewer is checking: do you choose UNION ALL vs UNION correctly?

Show a strong answer
  • Use UNION ALL with a source column: SELECT …, 'app' AS source FROM app_orders UNION ALL SELECT …, 'partner' FROM partner_orders.
  • UNION would waste a shuffle and could merge genuinely different orders that look identical.
  • De-duplicate by business key (order id) if overlaps are possible.

Avoid: UNION “to be safe”.
