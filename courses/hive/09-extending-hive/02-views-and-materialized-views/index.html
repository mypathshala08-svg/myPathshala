Views and materialized views

Views let many reports share one definition; materialized views let them share one result, and Hive 4 can use that result automatically. This lesson builds both for TiffinGo, then makes the MV stale on purpose to see what Hive does: refuse it, use it inside a time window, and rebuild it incrementally or fully. All outputs are real, from Hive 4.2.1.

1 The story

“Twelve reports, one join, copied twelve times”

Before you start: ACID tables (7.1), EXPLAIN CBO (8.1) and the CBO (8.2).

Every TiffinGo report starts with the same join of orders and customers and the same daily totals by city. When the definition of a “Gold order” changed last month, Kabir had to fix twelve copies, and missed two.

Kabir

Sir, can I write the join once and let reports use it like a table?

Arjun Sir

That is a view: a saved query with a name. It stores no data; Hive pastes its definition into every query that uses it. If the work itself is expensive, a materialized view stores the result as a real table, and Hive 4 can even rewrite queries on the base table to read it, without changing the reports.

Riya

And when new orders arrive?

Arjun Sir

Then the materialized view is stale. We will see exactly what Hive does about that: refuse to use it, use it anyway inside a time window, and rebuild it incrementally or fully. All outputs are real, from Hive 4.2.1, including a few rules the tutorials leave out.

2 Definition

Views and materialized views

Formal definition (write this in exams)

A view is a named, stored query (CREATE VIEW name AS SELECT …) recorded in the metastore as a VIRTUAL_VIEW; it holds no data, and references to it are expanded into the underlying query at compile time. A materialized view (CREATE MATERIALIZED VIEW) stores the query result as a managed table and records the state of its source tables. When the sources are transactional, the cost-based optimiser can automatically rewrite queries to use an up-to-date materialized view (hive.materializedview.rewriting), and ALTER MATERIALIZED VIEW … REBUILD refreshes it, incrementally when only inserts occurred since the last rebuild.

In simple words

A view is a saved query you can select from like a table; it always shows current data. A materialized view saves the query’s result, so reading it is fast, but it must be rebuilt when the source data changes. Hive can use a materialized view automatically to speed up queries on the base tables.

Views at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A saved recipe vs a cooked dish

  • A view is a saved recipe: every time you use it, Hive cooks the query again from the base tables.
  • A materialized view is a cooked dish kept in the fridge: fast to serve, but it gets old when new ingredients arrive.
  • Both let many reports share one definition.

Intermediate How they behave

  • CREATE VIEW v AS SELECT …: stored in the metastore as text (VIRTUAL_VIEW); queries on v are expanded into the base query. No data, always current.
  • CREATE MATERIALIZED VIEW mv AS SELECT …: stores the result (ORC, transactional) and its source tables’ snapshot.
  • Rewriting: with hive.materializedview.rewriting=true, Calcite replaces matching parts of a query with the MV.
  • Refresh: ALTER MATERIALIZED VIEW mv REBUILD, incremental when possible.

Advanced What the lab showed

  • SELECT * views freeze the column list at creation; dropping the base table broke the view only when it was queried.
  • An MV with rewriting was refused on an external source (“cannot be enabled if the materialized view uses non-transactional tables”); DISABLE REWRITE worked.
  • Rewriting read 240 rows instead of 5,000,000. After an INSERT the stale MV was ignored; a 10-minute window made Hive use it and return an outdated total. Incremental rebuild after INSERT, full rebuild after DELETE.

Exam tip: “Difference between a view and a materialized view in Hive?” A view stores only the query and is expanded when used, so it is always current but saves no work. A materialized view stores the result, needs REBUILD after source changes, and with transactional sources can be used automatically by the optimiser through query rewriting.

4 Step by step

From a view to a self-refreshing summary

All outputs are real, from Hive 4.2.1. orders_tx is a transactional copy of the 5,000,000-row table from Lesson 8.4.

  1. Step 1 · A view for Gold orders

    CREATE OR REPLACE VIEW v_gold_orders AS
SELECT o.order_id, o.order_date, o.amount, c.city, c.customer_id
FROM orders o JOIN customers c ON o.customer_id = c.customer_id
WHERE c.plan = 'Gold';

SELECT city, COUNT(*) AS n, SUM(amount) AS rev FROM v_gold_orders
WHERE order_date = '2026-10-05' GROUP BY city ORDER BY rev DESC LIMIT 3;
    +------------+------+-----------+ | city | n | rev | +------------+------+-----------+ | Bengaluru | 100 | 26600.00 | | Mumbai | 71 | 19270.00 | | Pune | 60 | 18090.00 | +------------+------+-----------+
    Exactly the answer of Lesson 8.1’s long query (Bengaluru 100, Mumbai 71, Pune 60), now with a two-line report. The definition of “Gold order” lives in one place.

  3. Step 3 · Two view traps: SELECT * and dropped tables

CREATE VIEW v_cust_all AS SELECT * FROM cust_copy;
ALTER TABLE cust_copy ADD COLUMNS (plan STRING);
DESCRIBE cust_copy;
DESCRIBE v_cust_all;
SHOW CREATE TABLE v_cust_all;

DROP TABLE cust_copy;
SELECT * FROM v_cust_all LIMIT 1;

    SELECT * was expanded into three named columns at creation, so the new plan column never appears in the view. Dropping the base table succeeded silently; the view only failed when someone queried it. List columns explicitly in views, and check dependent views (EXPLAIN DEPENDENCY, lineage tools) before dropping tables.

  4. Step 4 · Materialized views need transactional sources

    CREATE MATERIALIZED VIEW mv_ext AS SELECT city, COUNT(*) AS n FROM orders GROUP BY city;   -- orders is external

CREATE MATERIALIZED VIEW mv_ext DISABLE REWRITE AS SELECT city, COUNT(*) AS n FROM orders GROUP BY city;
SHOW MATERIALIZED VIEWS;
    Error: Error while compiling statement: FAILED: SemanticException Automatic rewriting for materialized view cannot be enabled if the materialized view uses non-transactional tables +----------+------------------+-----------------+----------------------+ | mv_name | rewrite_enabled | mode | incremental_rebuild | +----------+------------------+-----------------+----------------------+ | mv_ext | No | Manual refresh | Not available | +----------+------------------+-----------------+----------------------+
    Hive refused automatic rewriting on an external source: it cannot know when external files change, so it could never tell whether the MV is up to date. With DISABLE REWRITE the MV was created, but only as a stored result you query by name, with “Manual refresh” and incremental rebuild “Not available”.

  5. Step 5 · An MV on a transactional table, and rewriting

    CREATE MATERIALIZED VIEW mv_city_day AS
SELECT city, order_date, COUNT(*) AS n, SUM(amount) AS rev
FROM orders_tx GROUP BY city, order_date;
SHOW MATERIALIZED VIEWS;
SELECT COUNT(*) AS mv_rows FROM mv_city_day;

-- a report written against the BASE table:
EXPLAIN CBO SELECT city, SUM(amount) AS rev, COUNT(*) AS n FROM orders_tx
WHERE order_date BETWEEN '2026-10-01' AND '2026-10-07' GROUP BY city ORDER BY rev DESC LIMIT 3;
    +--------------+------------------+-----------------+----------------------+ | mv_name | rewrite_enabled | mode | incremental_rebuild | +--------------+------------------+-----------------+----------------------+ | mv_city_day | Yes | Manual refresh | Available | +--------------+------------------+-----------------+----------------------+ +----------+ | mv_rows | +----------+ | 240 | +----------+ CBO PLAN: HiveSortLimit(sort0=[$1], dir0=[DESC], fetch=[3]) HiveProject(city=[$0], rev=[$1], n=[CAST(COALESCE($2, 0:BIGINT)):BIGINT]) HiveAggregate(group=[{0}], agg#0=[sum($3)], agg#1=[sum($2)]) HiveFilter(condition=[BETWEEN(false, $1, 2026-10-01:DATE, 2026-10-07:DATE)]) HiveTableScan(table=[[tiffingo, mv_city_day]], table:alias=[tiffingo.mv_city_day])
    5,000,000 orders became 240 rows (8 cities × 30 days). The report never mentions the MV, yet the plan scans mv_city_day: Calcite proved the query can be answered from it, rolled the daily totals up to cities, and turned COUNT(*) into SUM(n) (the COALESCE(…, 0) keeps empty groups at 0).

  6. Step 6 · Same answer, far fewer rows

    SET hive.query.results.cache.enabled=false;   -- measure honestly
SET hive.tez.exec.print.summary=true;
-- the same report with hive.materializedview.rewriting=true, then false
    +------------+--------------+---------+ | city | rev | n | +------------+--------------+---------+ | Mumbai | 66960000.00 | 231900 | | Bengaluru | 63740000.00 | 219300 | | Pune | 52265000.00 | 176200 | +------------+--------------+---------+ rewriting=true RECORDS_IN_Map_1: 240 Time taken: 1.074 seconds rewriting=false RECORDS_IN_Map_1: 5000000 Time taken: 1.103 seconds run 1 rewriting=true 0.946 seconds run 1 rewriting=false 1.14 seconds run 2 rewriting=true 1.101 seconds run 2 rewriting=false 1.136 seconds run 3 rewriting=true 0.922 seconds run 3 rewriting=false 1.06 seconds
    Identical results with and without the MV (we compared them). The MV run read 240 rows instead of 5,000,000. On our single-node lab both ran in about 1 second, because 5 million ORC rows are cheap and start-up dominates; on billions of rows or with joins in the MV, the difference becomes minutes.

  7. Step 7 · Staleness: correct by default, stale by choice

    INSERT INTO orders_tx VALUES (999000001, 7, 'Pune', 1000.00, DATE '2026-10-03', 'DELIVERED');
EXPLAIN CBO SELECT … ;                                -- same report
DESCRIBE FORMATTED mv_city_day;                        -- after a second insert

SET hive.materializedview.rewriting.time.window=10min;
SELECT … ;                                             -- uses the MV
SET hive.materializedview.rewriting.time.window=0min;
SELECT … ;                                             -- base table
    | HiveTableScan(table=[[tiffingo, orders_tx]], table:alias=[orders_tx]) | | Outdated for Rewriting: | Yes | NULL | -- with a 10-minute window: | HiveTableScan(table=[[tiffingo, mv_city_day]], table:alias=[tiffingo.mv_city_day]) | +------------+--------------+---------+ | city | rev | n | +------------+--------------+---------+ | Mumbai | 66960000.00 | 231900 | | Bengaluru | 63740000.00 | 219300 | | Pune | 52265000.00 | 176200 | +------------+--------------+---------+ -- fresh (base table): +------------+--------------+---------+ | city | rev | n | +------------+--------------+---------+ | Mumbai | 66960000.00 | 231900 | | Bengaluru | 63740000.00 | 219300 | | Pune | 52266000.00 | 176201 | +------------+--------------+---------+
    After the insert, Hive marked the MV Outdated for Rewriting and quietly went back to orders_tx: correct, but slow again. With a 10-minute staleness window it used the MV anyway and returned Pune 176,200 orders and 52,265,000, while the truth was 176,201 and 52,266,000. A window is a deliberate trade of freshness for speed; agree on it with the report’s owners.

  8. Step 8 · Rebuild: incremental after INSERT, full after DELETE

    EXPLAIN CBO ALTER MATERIALIZED VIEW mv_city_day REBUILD;     -- after the INSERT
ALTER MATERIALIZED VIEW mv_city_day REBUILD;

DELETE FROM orders_tx WHERE order_id = 999000001;
EXPLAIN CBO ALTER MATERIALIZED VIEW mv_city_day REBUILD;     -- after the DELETE
ALTER MATERIALIZED VIEW mv_city_day REBUILD;
    -- after INSERT CBO PLAN: HiveProject(orders_tx.city=[$0], orders_tx.order_date=[$1], n=[CAST(COALESCE($2, 0:BIGINT)):BIGINT], rev=[$3]) HiveAggregate(group=[{0, 1}], agg#0=[sum($2)], agg#1=[sum($3)]) HiveProject(city=[$0], order_date=[$1], $f2=[$2], $f3=[$3]) HiveUnion(all=[true]) HiveProject(city=[$0], order_date=[$1], $f2=[$2], $f3=[$3]) HiveAggregate(group=[{2, 4}], agg#0=[count()], agg#1=[sum($3)]) HiveFilter(condition=[<(1, $8.writeid)]) HiveTableScan(table=[[tiffingo, orders_tx]], table:alias=[orders_tx]) HiveProject(city=[$0], order_date=[$1], n=[$2], rev=[$3]) HiveTableScan(table=[[tiffingo, mv_city_day]], table:alias=[tiffingo.mv_city_day]) -- after DELETE CBO PLAN: HiveProject(orders_tx.city=[$0], orders_tx.order_date=[$1], n=[$2], rev=[$3]) HiveAggregate(group=[{2, 4}], agg#0=[count()], agg#1=[sum($3)]) HiveTableScan(table=[[tiffingo, orders_tx]], table:alias=[orders_tx]) incremental rebuild: RECORDS_IN_Map_1: 5000001 RECORDS_IN_Map_6: 240 Time taken: 2.143 seconds full rebuild (after DELETE): RECORDS_IN_Map_1: 5000000 Time taken: 2.147 seconds
    After an INSERT, the rebuild plan is incremental: aggregate only rows with a newer writeid than the last build, UNION them with the existing MV rows and re-aggregate. After a DELETE it is a full recomputation. In our lab both still scanned all 5,000,000 rows of orders_tx (the writeid filter is applied after reading) and took about 2.1 s; the incremental one saved the aggregation work, not the scan.

6 Real-world use

Views and MVs at work

1. A semantic layer

Views give business names and agreed definitions (“active customer”, “Gold order”) on top of raw tables.

Raw tables→views→Shared metrics

2. Column and row restriction

Views without personal columns, or filtered to one region, are granted to analysts instead of base tables.

Table→restricted view→Safe access

3. BI acceleration

Materialized views pre-aggregate fact tables so dashboards get fast answers through automatic rewriting.

Fact table→MV→Fast tiles

4. Schema migrations

When tables are renamed or split, views with the old names keep existing reports working during the transition.

Old name→view→No broken reports

5. Pre-joined datasets

MVs that pre-join facts with dimensions save repeated joins for data science feature queries.

Facts + dims→MV join→Fast features

7 Run the code

Run the code: build, use and rebuild an MV

These programs model what Hive did in the lab: store an aggregate, roll it up, go stale and rebuild. Press Run, then try the challenges.

# A materialized view as a dictionary: (city, day) -> (count, revenue)
orders = [("Pune", "10-03", 500), ("Pune", "10-03", 700), ("Mumbai", "10-03", 400),
          ("Pune", "10-04", 300), ("Mumbai", "10-05", 900)]

mv = {}
for city, day, amt in orders:                       # CREATE MATERIALIZED VIEW ... GROUP BY city, day
    n, rev = mv.get((city, day), (0, 0))
    mv[(city, day)] = (n + 1, rev + amt)

# A query "by city" rewritten to roll up the MV: COUNT(*) becomes SUM(n)
by_city = {}
for (city, day), (n, rev) in mv.items():
    c, r = by_city.get(city, (0, 0))
    by_city[city] = (c + n, r + rev)
print("MV rows:", len(mv), "  base rows:", len(orders))
print(by_city)
MV rows: 4 base rows: 5 {'Pune': (3, 1500), 'Mumbai': (2, 1300)}
  • mv[(city, day)] = (n + 1, rev + amt)The MV keeps one row per (city, day): our real MV turned 5,000,000 orders into 240 rows.
  • by_city[city] = (c + n, r + rev)Rewriting rolls daily rows up to cities. COUNT(*) on the base table becomes SUM(n) on the MV, as the real plan showed.

9 Quiz and revision

Check yourself

Quick revision

Lesson 9.2 in one screen

  • View: stored, expanded SQL (VIRTUAL_VIEW); no data; always current. Name columns, avoid SELECT *.
  • Dropping a base table does not drop views; they fail when queried. Check dependents first.
  • MV: CREATE MATERIALIZED VIEW mv AS SELECT … stores the result; SHOW MATERIALIZED VIEWS.
  • Rewriting needs transactional sources; otherwise DISABLE REWRITE.
  • Rewriting is automatic (hive.materializedview.rewriting=true): lab 240 vs 5,000,000 rows; COUNT(*) → SUM(n).
  • Stale: Outdated for Rewriting → ignored at window 0; …rewriting.time.window allows stale answers.
  • REBUILD: incremental (UNION of new writeids) after INSERT; full after DELETE/UPDATE.
  • Hive 4 results cache returns identical queries instantly; disable it when measuring.

Interview and viva questions

Can I INSERT into a view?

No. Hive views are read-only. Load the base tables; the view shows the new data automatically.

Can a materialized view use Iceberg tables?

Yes, in Hive 4 Iceberg tables can be MV sources and MVs can be stored as Iceberg; Cloudera documents incremental rebuilds for Iceberg MVs. Check your version’s documentation and EXPLAIN the rebuild.

Is there an automatic rebuild?

Hive can schedule queries (CREATE SCHEDULED QUERY … EXECUTED AS … AS ALTER MATERIALIZED VIEW mv REBUILD) when the scheduled-query service is running. Many teams instead add the REBUILD as the last step of their load job.

Do views slow queries down?

No: a view is expanded into the query and optimised as a whole, so filters on the view are pushed into the base tables. Very deep stacks of views make plans hard to read, though.

What about Spark and Trino?

Both can read Hive views stored in the metastore with some limitations (the SQL dialect must be understood by the engine). Hive materialized views and their rewriting are specific to Hive; other engines just see a table.

Real-world scenario questions (asked in company interviews)

Views and MVs come up in both SQL rounds and design rounds.

Any company · HiveFresher

“View vs table?”

Explain what a view is and when to use one.

The interviewer is checking: do you know views store no data?

Show a strong answer

A view is a stored SELECT with a name. It holds no data; Hive expands it into the query each time, so it always shows current data. Views simplify repeated joins, give one definition of a business rule, and restrict columns for security. A table stores data and must be reloaded to change.

Avoid: Saying views are faster than tables.

Data engineeringMid-level

Materialized view not used

You created an MV but EXPLAIN shows queries still read the base table.

The interviewer is checking: do you know the rewriting rules?

Show a strong answer
  1. Check that the sources are transactional and rewriting is enabled (SHOW MATERIALIZED VIEWS).
  2. Check “Outdated for Rewriting” in DESCRIBE FORMATTED; rebuild or set a window.
  3. Check the query can be derived from the MV’s grain and columns.

Avoid: “Query the MV by name in every report.”

AnalyticsMid-level

Dashboard numbers lag behind

Finance says yesterday’s last orders are missing from a dashboard served by an MV.

The interviewer is checking: can you explain staleness?

Show a strong answer
  • The MV was not rebuilt after the last load and the staleness window allowed it to be used.
  • Rebuild after each load; reduce or remove the window for finance-critical reports.
  • Document the freshness of each dashboard.

Avoid: Blaming the source system first.

ArchitectureSenior

Speed up 200 dashboards

Design an acceleration layer for 200 dashboards on large transactional fact tables.

The interviewer is checking: can you design MVs as a layer?

Show a strong answer
  • Find common grains from query logs; build a few MVs at those grains with additive measures.
  • Rebuild in the load pipeline; set windows per business tolerance; monitor “Outdated” status.
  • Verify rewriting with EXPLAIN CBO in CI; keep views as the semantic layer on top.

Avoid: One MV per dashboard.
