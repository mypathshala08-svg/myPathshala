TRANSFORM with Python scripts

The last lesson of Module 9 runs Python inside Hive queries with TRANSFORM. 1 The story

“Our data scientists write Python, not Java”

Before you start: DISTRIBUTE BY and SORT BY (3.4), Java UDFs (9.1) and reading failures (8.5). Basic Python helps.

Riya’s team has a Python function that labels each order with a meal slot and computes GST. The data platform team says Hive UDFs must be Java (Lesson 9.1). Riya does not want to rewrite working Python code.

Riya

Sir, can Hive call my Python function directly?

Arjun Sir

Not as a function, but as a stream. SELECT TRANSFORM (cols) USING 'python3 script.py' AS (…) starts your script inside each task, writes every row to its standard input as a tab-separated line, and reads its standard output back as rows. It is the Hadoop Streaming idea inside SQL.

Kabir

That sounds too easy. What is the catch?

Arjun Sir

Several, and we will hit each one in the lab: all output columns are strings unless you declare types, NULL arrives as \N, a Hive 4 setting silently removed our SORT BY and gave wrong answers, crashes show up as a vague “Error 20001”, Windows line endings break scripts, and the script was 6× slower than plain SQL. All outputs are real, from Hive 4.2.1; the scripts are in the course lab folder.

2 Definition

TRANSFORM and custom scripts

Formal definition (write this in exams)

SELECT TRANSFORM (expr, …) USING 'command' [AS (col [type], …)] streams the selected rows through an external program. Hive serialises each row as a line of tab-separated text (NULL as \N) to the program’s standard input and deserialises each line of its standard output into a row, by default as STRING columns. The program, shipped to tasks with ADD FILE (or ADD ARCHIVE), runs once per task; placing TRANSFORM over a subquery with DISTRIBUTE BY and SORT BY makes it act as a reducer over grouped, ordered rows. The older keywords MAP and REDUCE are aliases for TRANSFORM.

In simple words

TRANSFORM lets a Hive query send its rows, as lines of text, to a script in Python or any other language, and read the script’s printed lines back as a table.

TRANSFORM at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Passing notes through a window

  • Hive writes each row on a slip of paper (one text line) and passes it to your program.
  • Your program reads the slip, writes an answer slip, and passes it back.
  • Hive turns the answer slips back into a table. Any language that reads and prints lines works.

Intermediate The rules of the stream

  • Columns are joined with tabs, rows end with a newline; NULL is written as \N.
  • AS (a, b) gives string columns; AS (a INT, b DECIMAL(10,2)) casts them.
  • ADD FILE ships the script to every task; it runs in the task’s working directory.
  • For “reducer” scripts, rows must arrive grouped and sorted: DISTRIBUTE BY key SORT BY key, order in a subquery.

Advanced What the lab showed

  • Hive 4.2.1 removed the subquery’s SORT BY (hive.remove.orderby.in.subquery=true): the plan changed from SHUFFLE to PARTITION_ONLY_SHUFFLE and the script returned 63 wrong rows instead of 3.
  • A Python exception surfaced in Beeline only as [Error 20001]; the traceback was in the task log. A CRLF script gave [Error 20003] and env: ‘python3\r’.
  • On 5,000,000 rows: TRANSFORM about 9.4 s vs SQL CASE about 1.5 s, identical results. Plans with scripts are “not optimized by CBO”.

Exam tip: “How do you use a Python script in Hive?” ADD FILE the script, then SELECT TRANSFORM (cols) USING 'python3 script.py' AS (out_cols). Hive writes rows as tab-separated lines to stdin and reads stdout back; NULL is \N; outputs are strings unless typed. For reducer-style scripts use DISTRIBUTE BY / SORT BY in a subquery. Debug with the task’s stderr log.

Two shapes of scripts

Map + reduceMapper subquery inside a reducer queryBoth of the aboveClassic Hadoop Streaming jobs

In Hive 4, hive.remove.orderby.in.subquery is true: ORDER BY / SORT BY inside a subquery may be dropped as “useless”. Reducer scripts then see unsorted, interleaved rows and produce wrong results without any error. Set it to false for such queries, and check the plan for SHUFFLE rather than PARTITION_ONLY_SHUFFLE.

4 Step by step

A Python mapper, a Python reducer, and their traps

All outputs are real, from Hive 4.2.1 (Python 3.9 in the HiveServer2 container, where Tez runs its tasks in our lab).

  1. Step 1 · The mapper script

    #!/usr/bin/env python3
"""Hive TRANSFORM mapper: order_id, order_ts, amount -> order_id, slot, gst
Hive sends one tab-separated line per row; NULL arrives as \\N."""
import sys

def slot(hour):
    if 6 <= hour < 11:  return "breakfast"
    if 11 <= hour < 16: return "lunch"
    if 16 <= hour < 19: return "snacks"
    if 19 <= hour < 23: return "dinner"
    return "late-night"

for line in sys.stdin:
    order_id, ts, amount = line.rstrip("\n").split("\t")
    s = slot(int(ts[11:13])) if ts != "\\N" else "\\N"
    gst = f"{float(amount) * 0.05:.2f}" if amount != "\\N" else "\\N"
    print(f"{order_id}\t{s}\t{gst}")
    A plain Python program: read lines from sys.stdin, split on tabs, print tab-separated results. It must handle \N (Hive’s NULL) itself, and it never imports anything Hive-specific, so you can test it from a shell with printf '1\t2026-10-05 20:10:00\t530.00\n' | python3 slot.py.

  2. Step 2 · Run it from Hive

    ADD FILE /data/scripts/slot.py;
SELECT TRANSFORM (order_id, order_ts, amount)
       USING 'python3 slot.py'
       AS (order_id, slot, gst)
FROM orders WHERE order_id <= 100005;
    +-----------+------------+--------+ | order_id | slot | gst | +-----------+------------+--------+ | 100001 | dinner | 26.50 | | 100002 | dinner | 25.00 | | 100003 | breakfast | 20.50 | | 100004 | breakfast | 9.00 | | 100005 | snacks | 24.00 | +-----------+------------+--------+
    ADD FILE copies the script into each task’s working directory, so USING refers to it by its bare name. Each output line became one row with the three names given in AS.

  3. Step 3 · Everything is a string, unless you say otherwise

    CREATE TEMPORARY TABLE t1 AS SELECT TRANSFORM (order_id, order_ts, amount)
  USING 'python3 slot.py' AS (order_id, slot, gst) FROM orders WHERE order_id <= 100002;
DESCRIBE t1;
CREATE TEMPORARY TABLE t2 AS SELECT TRANSFORM (order_id, order_ts, amount)
  USING 'python3 slot.py' AS (order_id INT, slot STRING, gst DECIMAL(10,2)) FROM orders WHERE order_id <= 100002;
DESCRIBE t2;
    +-----------+------------+----------+ | col_name | data_type | comment | +-----------+------------+----------+ | order_id | string | | | slot | string | | | gst | string | | +-----------+------------+----------+ +-----------+----------------+----------+ | col_name | data_type | comment | +-----------+----------------+----------+ | order_id | int | | | slot | string | | | gst | decimal(10,2) | | +-----------+----------------+----------+
    Without types, order_id and gst are strings: sorting and arithmetic would behave like text (“9.00” > “26.50”). Typed AS lets Hive convert them; a value that cannot be converted becomes NULL silently (Lesson 8.5).

  4. Step 4 · A reducer script needs grouped, sorted input

    #!/usr/bin/env python3
"""Hive TRANSFORM reducer: rows arrive grouped and sorted by customer_id, order_ts.
Emits customer_id, orders, average hours between consecutive orders."""
import sys
from datetime import datetime

def flush(cid, times):
    gaps = [(b - a).total_seconds() / 3600 for a, b in zip(times, times[1:])]
    avg = f"{sum(gaps) / len(gaps):.1f}" if gaps else "\\N"
    print(f"{cid}\t{len(times)}\t{avg}")

current, times = None, []
for line in sys.stdin:
    cid, ts = line.rstrip("\n").split("\t")
    if cid != current and current is not None:
        flush(current, times)
        times = []
    current = cid
    times.append(datetime.strptime(ts[:19], "%Y-%m-%d %H:%M:%S"))
if current is not None:
    flush(current, times)
    This script assumes that all orders of one customer arrive together and in time order: it keeps the current customer and flushes when the key changes. That is exactly what DISTRIBUTE BY customer_id SORT BY customer_id, order_ts should guarantee.

  5. Step 5 · The Hive 4 trap: the SORT BY disappeared

    ADD FILE /data/scripts/gaps.py;
FROM (SELECT customer_id, order_ts FROM orders WHERE customer_id IN (7, 15, 1492)
      DISTRIBUTE BY customer_id SORT BY customer_id, order_ts) t
SELECT TRANSFORM (customer_id, order_ts) USING 'python3 gaps.py'
       AS (customer_id INT, orders INT, avg_gap_hours DOUBLE);
-- first rows of 63
    +--------------+---------+----------------+ | customer_id | orders | avg_gap_hours | +--------------+---------+----------------+ | 15 | 2 | -219.4 | | 7 | 1 | NULL | | 15 | 2 | 560.2 | | 7 | 1 | NULL | | 1492 | 2 | -384.1 | | 7 | 1 | NULL | | 1492 | 3 | -172.6 | | 7 | 1 | NULL | | 1492 | 1 | NULL | … -- EXPLAIN: the shuffle into the script Plan not optimized by CBO because the statement uses scripts command:python3 gaps.py <-Map 1 [CUSTOM_SIMPLE_EDGE] vectorized PARTITION_ONLY_SHUFFLE [RS_11]
    Three customers should give three rows. We got 63, with negative gaps. The plan shows why: PARTITION_ONLY_SHUFFLE routes rows by customer but does not sort. Hive 4’s default hive.remove.orderby.in.subquery=true treated the subquery’s SORT BY as unnecessary. No error, no warning. Note also “Plan not optimized by CBO because the statement uses scripts”.

  6. Step 6 · Fix it, and check against SQL

    SET hive.remove.orderby.in.subquery=false;
-- same query as Step 5

-- cross-check in plain SQL:
SELECT customer_id, COUNT(*) AS orders,
  ROUND((unix_timestamp(MAX(order_ts)) - unix_timestamp(MIN(order_ts))) / 3600 / (COUNT(*) - 1), 1) AS avg_gap_hours
FROM orders WHERE customer_id IN (7, 15, 1492) GROUP BY customer_id ORDER BY customer_id;
    +--------------+---------+----------------+ | customer_id | orders | avg_gap_hours | +--------------+---------+----------------+ | 7 | 29 | 25.2 | | 15 | 27 | 24.3 | | 1492 | 41 | 17.3 | +--------------+---------+----------------+ <-Map 1 [SIMPLE_EDGE] vectorized SHUFFLE [RS_11] +--------------+---------+----------------+ | customer_id | orders | avg_gap_hours | +--------------+---------+----------------+ | 7 | 29 | 25.2 | | 15 | 27 | 24.3 | | 1492 | 41 | 17.3 | +--------------+---------+----------------+
    With the setting off, the plan shows a real SHUFFLE (sorted) and the script returns 3 rows: 29, 27 and 41 orders with average gaps of 25.2, 24.3 and 17.3 hours, exactly what plain SQL computes (the average gap is (last − first) / (n − 1)). Always validate a script against a SQL calculation on a sample.

    Beeline only says Error 20001 (“may have crashed with an error”). The real reason, the Python traceback, goes to the task’s stderr: order 112253 had amount 880.00. A missing interpreter gives Error 20000 and “Cannot run program”. A script with Windows (CRLF) line endings, run through its shebang, fails with Error 20003; the log shows env: ‘python3\r’.   8. Step 8 · The cost of streaming

    -- 5,000,000 rows (orders_ts_big), results cache off, two runs each
SELECT slot, COUNT(*) AS n FROM (
  SELECT TRANSFORM (order_id, order_ts, amount) USING 'python3 slot.py' AS (order_id, slot, gst)
  FROM orders_ts_big) t GROUP BY slot ORDER BY slot;

SELECT slot, COUNT(*) AS n FROM (
  SELECT CASE WHEN hour(order_ts) BETWEEN 6 AND 10 THEN 'breakfast' … ELSE 'late-night' END AS slot
  FROM orders_ts_big) t GROUP BY slot ORDER BY slot;
    | slot | n | | breakfast | 1034300 | | dinner | 834000 | | late-night | 1451400 | | lunch | 1066200 | | snacks | 614100 | run 1 SQL CASE 1.605 seconds run 1 TRANSFORM 9.405 seconds run 2 SQL CASE 1.429 seconds run 2 TRANSFORM 9.349 seconds
    Identical results (we compared them), but TRANSFORM took about 9.4 s against 1.5 s for the SQL CASE: every row was turned into text, piped to Python, parsed, printed and parsed back, and none of it was vectorised. Use TRANSFORM for logic that only exists in Python (a library, a model), not for what SQL already does.

# What Hive does around your script, simulated in Python
rows = [(100001, "2026-10-05 20:10:00", "530.00"), (100003, None, "410.00")]

def to_line(row):                       # Hive -> script: tabs, \N for NULL
    return "\t".join("\\N" if v is None else str(v) for v in row)

def slot_script(line):                  # the user's script (simplified slot.py)
    oid, ts, amt = line.split("\t")
    slot = "\\N" if ts == "\\N" else ("dinner" if 19 <= int(ts[11:13]) < 23 else "other")
    return f"{oid}\t{slot}\t{float(amt) * 0.05:.2f}"

for r in rows:
    line = to_line(r)
    out = slot_script(line)
    print(repr(line), "->", out.split("\t"))   # Hive splits the output back into columns

1 · Look at exactly what a script receives

SELECT TRANSFORM (order_id, CAST(NULL AS STRING), city, 'a b')
       USING 'cat -A' AS (raw_line)
FROM orders WHERE order_id <= 100002;

cat -A makes invisible characters visible: ^I is a tab, \N is NULL, $ is the end of the line. Spaces inside values are kept. The best first step when a script misbehaves.

2 · CLUSTER BY groups, but does not sort by time

ADD FILE /data/scripts/gaps.py;
FROM (SELECT customer_id, order_ts FROM orders WHERE customer_id IN (7, 15, 1492)
      CLUSTER BY customer_id) t
SELECT TRANSFORM (customer_id, order_ts) USING 'python3 gaps.py'
       AS (customer_id INT, orders INT, avg_gap_hours DOUBLE);
+--------------+---------+----------------+ | customer_id | orders | avg_gap_hours | +--------------+---------+----------------+ | 7 | 29 | -16.0 | | 15 | 27 | 11.3 | | 1492 | 41 | -8.0 | +--------------+---------+----------------+

The counts are right (each customer arrived as one group), but the gaps are wrong, even negative: CLUSTER BY customer_id sorts only by the key, not by order_ts. A reducer script needs DISTRIBUTE BY key SORT BY key, time (with the subquery sort kept).

Interview and viva questions

Where does the script run?

Inside each task (map or reduce) on the worker nodes, in the task’s working directory, using the interpreter installed there. Every node needs the same Python version and packages, or you ship an environment with ADD ARCHIVE.

Can a script return more or fewer rows than it receives?

Yes. It may print zero, one or many lines per input line; Hive just reads whatever comes out. A reducer script usually prints one line per group.

How do I debug a script?

Run it locally with the lines Hive would send (use USING 'cat -A' to see them), print debug messages to stderr (never stdout, which becomes data), and read the task log for tracebacks.

Is TRANSFORM allowed on secured clusters?

Often not. With SQL-standard based authorization, Hive rejects queries with a transform clause (“Query with transform clause is disallowed in current configuration”), because scripts can run arbitrary programs. Ranger-secured platforms usually restrict it too.

What is the modern alternative?

Spark SQL with Python UDFs, especially vectorised pandas UDFs, reads the same metastore tables and runs Python far more efficiently. Many teams keep TRANSFORM only for legacy jobs.

print(sum(gaps) / len(gaps), (t[-1] - t[0]) / (len(t) - 1))
22.5 22.5

How it works: Both formulas give 22.5: the SQL cross-check used (last − first) / (n − 1).

Parse typed output

Convert script output lines to typed tuples like AS (id INT, slot STRING, gst DECIMAL).

Input
two lines
Expected output
[(100001, 'dinner', Decimal('26.50')), (100004, 'breakfast', Decimal('9.00'))]
Show solution and explanation 
from decimal import Decimal
lines = ["100001\tdinner\t26.50", "100004\tbreakfast\t9.00"]
print([(int(a), b, Decimal(c)) for a, b, c in (l.split("\t") for l in lines)])
[(100001, 'dinner', Decimal('26.50')), (100004, 'breakfast', Decimal('9.00'))]

How it works: What Hive does when AS declares types; unconvertible values become NULL.

P8Business problem

Migration plan

Order three legacy streaming jobs for migration.

Input
jobs with daily runtime and type
Expected output
sessions.py   90 min -> window functions
clean.py      40 min -> SQL / UDF
score.py      20 min -> Spark pandas UDF
Show solution and explanation 
jobs = [("sessions.py", 90, "reducer"), ("clean.py", 40, "mapper"), ("score.py", 20, "model")]
for name, mins, kind in sorted(jobs, key=lambda j: -j[1]):
    target = "window functions" if kind == "reducer" else "SQL / UDF" if kind == "mapper" else "Spark pandas UDF"
    print(f"{name:12} {mins:>3} min -> {target}")
sessions.py 90 min -> window functions clean.py 40 min -> SQL / UDF score.py 20 min -> Spark pandas UDF

How it works: Start with the longest job; reducer logic like gaps.py often becomes LAG() over (PARTITION BY … ORDER BY …).

Real-world scenario questions (asked in company interviews)

TRANSFORM questions check streaming basics and whether you know when not to use it.

Any company · HiveFresher

“Can Hive run Python?”

Explain how to use a Python script in a Hive query.

The interviewer is checking: do you know TRANSFORM and the stream format?

Show a strong answer

Yes, through TRANSFORM. ADD FILE ships the script; SELECT TRANSFORM (cols) USING 'python3 script.py' AS (outputs) sends each row as a tab-separated line to the script’s stdin and reads its stdout lines back as rows. NULL arrives as \N and outputs are strings unless typed. Native UDFs, by contrast, must be Java.

Avoid: Saying Hive supports Python UDFs natively.

Data engineeringMid-level

Script results wrong after an upgrade

A sessionisation script gives different numbers after moving to Hive 4, without errors.

The interviewer is checking: can you find an ordering problem?

Show a strong answer
  1. EXPLAIN: look for PARTITION_ONLY_SHUFFLE instead of SHUFFLE before the Transform Operator.
  2. Check hive.remove.orderby.in.subquery (true in Hive 4); set it to false for this job.
  3. Use DISTRIBUTE BY key SORT BY key, time and cross-check a sample with SQL.

Avoid: Rewriting the script before checking the input order.

AnalyticsMid-level

Error 20001

A query with a TRANSFORM script fails with “Error 20001: … may have crashed with an error”.

The interviewer is checking: do you know where script errors go?

Show a strong answer
  • Read the task log (stderr) for the Python traceback.
  • Reproduce locally with the same input lines (USING 'cat -A' shows them).
  • Handle \N and malformed values in the script; log bad rows to stderr instead of crashing.

Avoid: Re-running the query unchanged.

PlatformSenior

Retire TRANSFORM

A platform has 40 TRANSFORM jobs and is enabling SQL-standard authorization. Plan the change.

The interviewer is checking: can you plan a migration?

Show a strong answer
  • Inventory jobs by runtime and type (mapper, reducer, model).
  • Mappers → SQL or Java UDFs; reducers → window functions; models → Spark Python/pandas UDFs.
  • Validate each rewrite against the old output on samples before enabling authorization.

Avoid: Turning authorization on first and fixing failures later.
