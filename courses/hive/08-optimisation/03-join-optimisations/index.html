Join optimisations: map join, bucket map join, SMB and skew join

Joins are where most Hive time goes. This lesson runs one join four ways (shuffle, map, bucket map and SMB) and measures what moves, then builds a skewed table with one customer holding 40% of the orders. Along the way it finds the conditions most tutorials leave out: table type, sorting and ACID. All plans and counters are real, from Hive 4.2.1.

2 Definition

Join optimisations in Hive

Formal definition (write this in exams)

Hive executes an equi-join with one of several physical algorithms. The shuffle (common) join repartitions both inputs by the join key and joins them in reducers. A map join (broadcast join) loads the smaller input into an in-memory hash table on every task processing the larger input, avoiding the shuffle; Hive converts joins automatically when the estimated size of the small inputs is below hive.auto.convert.join.noconditionaltask.size. When both tables are bucketed on the join key, a bucket map join sends each task only the matching bucket of the small table, and when they are also sorted on the key with the same number of buckets, a sort-merge-bucket (SMB) join merges the buckets directly. Skew join handling separates heavily repeated keys so they do not overload one task.

In simple words

Hive can join tables in different ways. The slow, general way sends both tables over the network. Faster ways copy a small table to every worker, or use matching buckets so each worker only needs a slice. The plan shows which one Hive picked.

Words you’ll meet in this lesson

Join optimisation at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Matching two lists

  • To join orders with customers, Hive must bring each order and its customer to the same place.
  • Shuffle join: both lists are sorted into piles by customer_id and sent over the network. Works for any size, but moves a lot of data.
  • Map join: if one list is small, give a full copy to every worker. No piles needed.

Intermediate The four methods and their conditions

  • Shuffle (common / merge) join: default fallback. Both sides go through SIMPLE_EDGE to a reducer running Merge Join Operator.
  • Map (broadcast) join: small side under hive.auto.convert.join.noconditionaltask.size (10,000,000 bytes in our lab); BROADCAST_EDGE, Map Join Operator.
  • Bucket map join: both tables bucketed on the join key with compatible counts; each big-table task gets only its bucket of the small table (CUSTOM_EDGE, BucketMapJoin:true).
  • SMB join: both bucketed and sorted on the key, same bucket count: merge bucket i with bucket i inside the map task (Merge Join Operator + Dummy Store).

Advanced What the lab showed

  • Bucketed, sorted external tables never got a bucket map or SMB join; managed transactional tables did.
  • Full ACID tables cannot be SORTED BY (“cannot support full ACID functionality since it is sorted”); SMB worked with insert-only tables.
  • Shuffle join moved 342,929 bytes vs 31,867 for the map join. /*+ MAPJOIN */ hints are ignored by default. Skew settings did not change the Tez plan; splitting the hot key did the job.

Exam tip: “Explain map join, bucket map join and SMB join.” Map join: small table copied to every task, no shuffle; automatic below a size threshold. Bucket map join: both tables bucketed on the join key (compatible counts); each task loads only its bucket of the small table. SMB: both bucketed and sorted on the key with the same bucket count; buckets are merged, so neither side must fit in memory. Verify in EXPLAIN.

4 Step by step

Four join methods, real plans and counters

All outputs are real, from the Hive 4.2.1 lab. Plans keep the lines that identify the join; counters come from SET hive.tez.exec.print.summary=true.

  1. Step 1 · Shuffle (merge) join

    SET hive.auto.convert.join=false;
EXPLAIN SELECT c.city, COUNT(*), SUM(o.amount)
FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.city;
    Reducer 2 <- Map 1 (SIMPLE_EDGE), Map 4 (SIMPLE_EDGE) Reducer 3 <- Reducer 2 (SIMPLE_EDGE) <-Reducer 2 [SIMPLE_EDGE] Merge Join Operator [MERGEJOIN_19] (rows=50000 width=203) <-Map 1 [SIMPLE_EDGE] vectorized TableScan [TS_0] (rows=50000 width=116) <-Map 4 [SIMPLE_EDGE] vectorized TableScan [TS_3] (rows=2000 width=95)
    Both tables are read by their own map vertex (Map 1, Map 4) and shuffled by customer_id (SIMPLE_EDGE) into Reducer 2, where the Merge Join Operator joins rows with the same key. A third vertex groups by city. This works for any size, but every row of both tables crosses the network.

  2. Step 2 · Map join (the default here)

    EXPLAIN SELECT c.city, COUNT(*), SUM(o.amount)
FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.city;
    Map 1 <- Map 3 (BROADCAST_EDGE) Reducer 2 <- Map 1 (SIMPLE_EDGE) <-Map 1 [SIMPLE_EDGE] vectorized Map Join Operator [MAPJOIN_26] (rows=50000 width=203) <-Map 3 [BROADCAST_EDGE] vectorized TableScan [TS_3] (rows=2000 width=95) <-Select Operator [SEL_25] (rows=50000 width=116) TableScan [TS_0] (rows=50000 width=116)
    With the default settings customers (2,000 rows) is under the 10,000,000-byte limit, so Map 3 broadcasts it to every task of Map 1, which joins in memory. The join needs no reducer; one shuffle remains for GROUP BY.

    The hint asked Hive to hold orders (50,000 rows) in memory. Hive ignored it and still streamed orders (SEL_25, rows=50000) and broadcast customers. Old tutorials rely on MAPJOIN and STREAMTABLE hints; in Hive 4 the cost-based decision wins unless you set hive.ignore.mapjoin.hint=false.

In Hive 4.2.1 our external bucketed tables were never joined bucket by bucket, most likely because Hive cannot guarantee that files written outside it follow the bucketing.

  8. Step 8 · A skewed key

  CASE WHEN order_id % 10 < 4 THEN 7 ELSE customer_id END AS customer_id, amount FROM orders;

Behind the screen
  1. Both inputs are repartitioned by key so equal keys meet in one reducer.
  2. Every map task builds a hash table of the small side and streams the big side through it.
  3. Bucket i of the big table only needs bucket i of the small one.
  4. Sorted buckets are merged like two sorted lists.
  5. Hash partitioning sends every row of a key to the same task.

6 Real-world use

Join optimisation at work

1. Fact-to-dimension joins

Reports join a huge fact table with small dimensions (stores, plans, dates); map joins keep them shuffle-free.

Fact + dims→broadcast→Fast report

2. Large-to-large joins

Orders with payments or clicks with sessions: tables bucketed (and sorted) on the key avoid repeated full shuffles.

Same buckets→bucket / SMB→Less shuffle

3. Marketplaces and telecom

A few sellers or cell towers dominate the data; hot keys are split out or salted so one task does not hold up the job.

Hot key→split / salt→Even tasks

4. Incident response

Map-join memory failures are traced to stale statistics or a grown dimension, fixed with ANALYZE or a threshold change.

Failure→EXPLAIN + stats→Stable job

5. Code review

Reviewers check the join type in the plan and ask why a large shuffle join is needed before a job goes live.

New job→join check→Approved

Examples are simplified.

9 Quiz and revision

Check yourself

Quick revision

Lesson 8.3 in one screen

  • Shuffle join: SIMPLE_EDGE from both sides into a reducer, Merge Join Operator. Always works; moves most data.
  • Map join: small side under hive.auto.convert.join.noconditionaltask.size (10 MB in lab) → BROADCAST_EDGE. Lab: 31,867 vs 342,929 bytes.
  • Bucket map join: both bucketed on the key → CUSTOM_EDGE, MULTICAST, BucketMapJoin:true, one task per bucket.
  • SMB: bucketed + sorted, same count → Merge Join in the Map vertex with Dummy Store; no join shuffle.
  • Lab conditions: external bucketed tables got no bucket join; full ACID cannot be sorted; insert-only sorted tables gave SMB.
  • Hints (MAPJOIN, STREAMTABLE) are ignored by default (hive.ignore.mapjoin.hint=true).
  • Skew: find hot keys with GROUP BY … ORDER BY COUNT(*) DESC; map join or split/salt the hot key. Skew settings did not change the Tez plan in 4.2.1.
  • Never disable auto map joins globally; fix statistics (8.2) or adjust the threshold per query.

Interview and viva questions

Is a map join always faster?

Only when the small side is genuinely small. Every task builds the hash table, so a large “small side” costs memory and broadcast time, and if it does not fit, tasks fail or spill. That is why the threshold exists and why stale statistics (Lesson 8.2) are dangerous.

What is the difference between a bucket map join and an SMB join?

A bucket map join still builds a hash table, but of one bucket of the small table per task. An SMB join needs both tables sorted as well, and merges the buckets without any hash table, so neither side has to fit in memory. SMB is the choice for two large tables.

Why did Hive not use bucket joins for our external tables?

Hive can only rely on bucketing if every file follows the bucketing scheme. Files of external tables may be written by other tools. In Hive 4.2.1 our external bucketed tables never got a bucket map or SMB join, while managed transactional tables did. Behaviour can differ between versions, so verify with EXPLAIN.

How do I join on more than one key or a non-equal condition?

Map, bucket and SMB joins work for equi-joins on the bucketing keys. Non-equi conditions (BETWEEN, <) can be added after the join or, in Hive 4, used in the ON clause, but they generally lead to shuffle or cross-product style plans; check EXPLAIN and keep such joins on small inputs.

What is salting?

Adding a random number (0…N-1) to the hot key on the big side and replicating the matching rows of the other side N times, so the hot key is spread over N tasks. It needs no special Hive feature and works in every engine.

P6Medium

Join method from facts

Choose a join method from table facts.

Input
size of small side, bucketing, sorting
Expected output
map join | SMB join | shuffle join
Show solution and explanation 
def choose(small_bytes, both_bucketed, both_sorted, threshold=10_000_000):
    if small_bytes <= threshold: return "map join"
    if both_bucketed and both_sorted: return "SMB join"
    if both_bucketed: return "bucket map join (if one bucket fits)"
    return "shuffle join"
print(choose(190_000, False, False), "|", choose(5e9, True, True), "|", choose(5e9, False, False))
map join | SMB join | shuffle join

How it works: A simplification of Hive’s choice; the real decision also depends on table type and settings, so always confirm in EXPLAIN.

Broadcast traffic

illustrative

Real-world scenario questions (asked in company interviews)

Join optimisation is the most asked Hive performance topic in interviews.

Any company · HiveFresher

“What is a map join?”

Explain the map join and when Hive uses it.

The interviewer is checking: do you know why it is fast and its limit?

Show a strong answer

In a map join the small table is loaded into a hash table on every task that reads the big table, so the join happens in the map phase without shuffling the big table. Hive converts joins automatically when the small side is under hive.auto.convert.join.noconditionaltask.size. In EXPLAIN it appears as BROADCAST_EDGE and Map Join Operator.

Avoid: Saying it is for any join.

Data engineeringMid-level

Bucketed but no bucket join

You bucketed two tables on customer_id, but EXPLAIN still shows a broadcast or shuffle join.

The interviewer is checking: do you know the real conditions?

Show a strong answer
  1. Check both tables are bucketed on the join key with compatible counts (and sorted, for SMB).
  2. Check the table type: in our Hive 4.2.1 lab external bucketed tables never got bucket joins; managed transactional ones did.
  3. Check the size: if the small side fits, a plain map join may be chosen instead (often fine).

Avoid: “Add more buckets.”

AnalyticsMid-level

One reducer never ends

A join job is stuck at 99% for an hour with one running task.

The interviewer is checking: can you diagnose and fix skew?

Show a strong answer
  • Find hot keys: GROUP BY key ORDER BY COUNT(*) DESC LIMIT 10 on the big side.
  • If the other side is small, make sure a map join is used.
  • Otherwise join the hot keys separately (UNION ALL) or salt them; verify results match.

Avoid: Raising the reducer count, which does not split one key.

PlatformSenior

Two 2 TB tables joined hourly

Design storage so the hourly join avoids a full shuffle.

The interviewer is checking: can you design for SMB?

Show a strong answer
  • Bucket and sort both tables on the join key with the same number of buckets (sized ~1 GB per bucket).
  • Use a table type Hive trusts for bucketing (managed; insert-only if sorted), write only through Hive.
  • Verify the SMB plan in CI, and keep statistics fresh.

Avoid: Relying on map joins for two large tables.
