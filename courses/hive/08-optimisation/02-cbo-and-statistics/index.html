1 The story

“Why does Hive think there are only 3 Gold customers?”

In Lesson 8.1, EXPLAIN ANALYZE showed Kabir that Hive expected 3 Gold customers when there were 517. Riya wants to know where such numbers come from, and whether a wrong guess can really make a query slow.

Riya

Because it decides the plan before reading any data: join order, map join or shuffle join, number of reducers. For that it uses statistics stored in the metastore: row counts, sizes, and per column the number of distinct values, nulls, minimum and maximum. 2 Definition

The cost-based optimiser and statistics

Formal definition (write this in exams)

Hive’s cost-based optimiser (CBO), enabled by hive.cbo.enable=true, uses Apache Calcite to rewrite a query’s logical plan and to choose join order and join algorithms by comparing estimated costs. The costs are derived from statistics kept in the Hive Metastore at table, partition and column level: row counts and sizes (basic statistics) and, per column, number of distinct values, nulls, minimum and maximum. Statistics are collected automatically when data is written through Hive (hive.stats.autogather, hive.stats.column.autogather) or explicitly with ANALYZE TABLE … COMPUTE STATISTICS [FOR COLUMNS], and can also answer some queries directly (hive.compute.query.using.stats).

In simple words

Before running a query, Hive estimates how many rows each step will produce, using facts about the data stored in the metastore. The optimiser picks the plan with the lowest estimated cost. If the facts are missing or old, the estimates and the plan can be badly wrong; ANALYZE TABLE refreshes them.

Statistics at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A shopkeeper’s guess

  • Before packing for a trip, you guess how many bags you need. Hive does the same before running a query: it guesses how many rows each step will produce.
  • The guesses come from statistics: facts about each table saved in the metastore, like “50,000 rows” or “30 different dates”.
  • Good statistics → good plan. Missing or old statistics → Hive can pick a slow plan.

Intermediate What is stored and how it is used

  • Table / partition (basic) stats: numRows, numFiles, totalSize, rawDataSize. Seen with DESCRIBE FORMATTED or SHOW TBLPROPERTIES.
  • Column stats: distinct_count (NDV), num_nulls, min/max, avg_col_len/max_col_len, true/false counts. Seen with DESCRIBE FORMATTED t col.
  • Gathered automatically on INSERT (hive.stats.autogather, hive.stats.column.autogather) or by hand with ANALYZE TABLE … COMPUTE STATISTICS [FOR COLUMNS].
  • Selectivity rules of thumb: col = v → rows / NDV; ranges → interpolated between min and max; values are assumed evenly spread.

Advanced What the lab showed

  • Tbl:COMPLETE means statistics exist, not that they are correct: after an INSERT with autogather off, Hive said COMPLETE with 100 rows for a 2,000-row table.
  • Statistics alone flipped a join: stale stats → map join; fresh stats → shuffle (merge) join, same SQL, same threshold.
  • Even complete stats mislead: equality on our DATE column was estimated at half the table (25,000 for 1,621), and skewed values (Pune) are under-estimated. A partition gave an exact 1,621.

Exam tip: “What is CBO in Hive and why does it need statistics?” CBO (Calcite) chooses join order and join types by estimated cost; costs come from row counts and column statistics in the metastore. Collect them with ANALYZE TABLE … COMPUTE STATISTICS and … FOR COLUMNS, or automatically on INSERT. Check with DESCRIBE FORMATTED and in EXPLAIN (Tbl:/Col: COMPLETE, PARTIAL or NONE).

COMPLETE in EXPLAIN only says that statistics are present. If files were added outside Hive (external tables), or an INSERT ran with autogather off, the numbers can be old and Hive will not notice. Refresh statistics as part of every load job.

Run the code: estimate like the optimiser

These programs reproduce the optimiser’s arithmetic with the real numbers from the lab. Press Run, then try the challenges.

# How Hive estimates a filter from column statistics (simplified)
num_rows = 50000
ndv = {"city": 8, "plan": 3, "customer_id": 2000}
amount_min, amount_max = 40, 880                # real min / max from DESCRIBE FORMATTED

def eq_estimate(col):                           # col = value
    return round(num_rows / ndv[col])

def range_estimate(lo):                         # amount > lo, even spread
    return round(num_rows * (amount_max - lo) / (amount_max - amount_min))

print("city = 'Pune'  :", eq_estimate("city"), " (real 7,930)")
print("amount > 500   :", range_estimate(500), " (real 5,642)")
print("plan = 'Gold' on 2,000 customers:", round(2000 / ndv["plan"]), " (real 517)")
city = 'Pune' : 6250 (real 7,930) amount > 500 : 22619 (real 5,642) plan = 'Gold' on 2,000 customers: 667 (real 517)
  • return round(num_rows / ndv[col])Equality: rows divided by the number of distinct values. 50,000 / 8 = 6,250, exactly what EXPLAIN printed for Pune.
  • return round(num_rows * (amount_max - lo) / (amount_max - amount_min))Ranges: a straight line between min and max, assuming values are evenly spread. With the real min 40 and max 880 this gives 22,619, exactly Hive’s estimate.

Interview and viva questions

Does ANALYZE TABLE lock or slow down the table?

It reads the data (except NOSCAN) and writes only metadata. Queries can keep running. On big tables analyse new partitions only, and list the important columns in FOR COLUMNS to save time.

Are statistics gathered automatically?

For data written through Hive (INSERT, CTAS, and in Hive 4 also column statistics on INSERT), yes, when autogather is on. Not for files placed by other tools: Spark (unless it updates Hive statistics), DistCp, hdfs dfs -put, or LOAD DATA in some cases.

What are KLL histograms in Hive 4?

Hive 4 can store KLL sketches as histograms for numeric columns (hive.stats.kll.enable). They are meant to improve range estimates on skewed data. In our lab, switching it on and re-analysing did not change the estimates of our queries, so measure on your own data before relying on it.

Does Spark use Hive statistics?

Spark SQL reads table statistics from the metastore when its own CBO is enabled, and has its own ANALYZE TABLE command that writes statistics in Spark’s format. Engines do not always read each other’s column statistics, so analyse with the engine that will query the table.

Can I set statistics by hand?

Yes, for example ALTER TABLE t SET TBLPROPERTIES ('numRows'='…') or ALTER TABLE … UPDATE STATISTICS. It is useful for testing plans, but in production hand-written numbers become stale too; prefer ANALYZE.

Real-world scenario questions (asked in company interviews)

Statistics questions separate people who tune by guessing from people who read plans.

Any company · HiveFresher

“What is the CBO in Hive?”

Explain the cost-based optimiser.

The interviewer is checking: do you connect CBO with statistics?

Show a strong answer

The cost-based optimiser, based on Apache Calcite, chooses join order and join methods by estimating the cost of different plans. Costs come from statistics in the metastore: row counts and column statistics like distinct values, nulls, min and max. Gather them with ANALYZE TABLE … COMPUTE STATISTICS and … FOR COLUMNS; check them with DESCRIBE FORMATTED and in EXPLAIN.

Avoid: Describing CBO without mentioning statistics.

Data engineeringMid-level

Join started failing with out-of-memory

A daily join suddenly fails in map tasks with memory errors. The SQL did not change; a dimension table grew a lot.

The interviewer is checking: can you connect a memory failure to statistics?

Show a strong answer
  1. EXPLAIN: is the dimension broadcast (BROADCAST_EDGE, Map Join)? What size does the plan think it has?
  2. Compare numRows/totalSize in the metastore with reality: likely stale (files written by another tool).
  3. ANALYZE the table; the planner switches to a shuffle join. Add ANALYZE to the loading job.

Avoid: Only raising container memory.

AnalyticsMid-level

Estimates wrong even with statistics

EXPLAIN ANALYZE shows estimates 10× off on a table with full column statistics.

The interviewer is checking: do you know the limits of statistics?

Show a strong answer
  • Statistics are averages: skewed values and correlated filters break the even-spread assumption.
  • Check whether the filter is on a partition column (exact counts) or could be.
  • If the plan choice is still right, accept the gap; if not, use hints or settings for that query, or redesign (partitioning, skew handling).

Avoid: “Run ANALYZE again” when statistics are already fresh.

PlatformSenior

Statistics policy

Define how statistics are maintained across a warehouse fed by Hive, Spark and file drops.

The interviewer is checking: can you design a process, not a one-off fix?

Show a strong answer
  • Autogather on for Hive writes; per-partition ANALYZE … FOR COLUMNS (key columns) at the end of every non-Hive load.
  • Nightly health check comparing numRows with sampled counts; alert on large gaps.
  • Plan checks in CI flag Col:NONE/PARTIAL on critical tables.

Avoid: Analysing every table nightly regardless of change.
