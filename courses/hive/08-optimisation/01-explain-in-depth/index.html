2 Definition

EXPLAIN and the query plan

Formal definition (write this in exams)

EXPLAIN displays the execution plan Hive generates for a statement without running it: the stages (on Tez, a DAG of vertices connected by edges) and, for each vertex, the tree of operators (TableScan, Filter, Select, Join, Group By, Reduce Output, Limit, File Output) with estimated row counts and data sizes derived from table and column statistics. Variants add information: ANALYZE executes the query and shows actual row counts, CBO shows the cost-based optimiser’s logical plan, VECTORIZATION explains vectorised execution, DEPENDENCY lists inputs, LOCKS lists the locks a statement would take, and EXTENDED adds physical details.

In simple words

EXPLAIN prints Hive’s plan for your query: which tables it reads, how it joins and groups, how the work is split into Tez stages, and how many rows it expects at each step. It is the first thing to look at when a query is slow.

Words you’ll meet in this lesson

OperatorOne step of the plan: TableScan, Filter, Join, Group By …
VertexA Tez stage: Map n or Reducer n, run by many tasks.
EdgeHow data flows between vertices: SIMPLE (shuffle), BROADCAST …
ShuffleRows sent across the network, grouped by key, to reducers.
Estimaterows= in EXPLAIN: what statistics predict.
ActualThe second number in EXPLAIN ANALYZE (estimate/actual).
CBOCost-based optimiser (Apache Calcite) that picks join order and methods.
Top N KeyOperator that drops rows early when only the top N are needed.

Reading plans at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A recipe card

  • SQL says what you want; the plan says how Hive will cook it: which tables to read, in which order to join, where to group and sort.
  • EXPLAIN + your query prints the plan without running it. Read it from the bottom up: tables at the bottom, final result at the top.
  • Each step is an operator: TableScan (read), Filter (WHERE), Select (columns), Join, Group By, Limit, File Output.

Intermediate Vertices, edges and estimates

  • Hive on Tez runs a DAG of vertices: Map n (read files) and Reducer n (after a shuffle). Map 1 <- Map 4 (BROADCAST_EDGE) means Map 4’s output is sent whole to every Map 1 task: a map join.
  • Edges: SIMPLE_EDGE (shuffle by key), BROADCAST_EDGE (copy to all), CUSTOM_SIMPLE_EDGE / CUSTOM_EDGE (special routing).
  • (rows=25000 width=172) are estimates from statistics. Tbl:COMPLETE, Col:NONE says table stats exist but column stats do not.
  • A map-side Group By (partial, hash mode) feeds a reducer-side Group By (mergepartial): aggregation in two phases.

Advanced Every EXPLAIN form we used

  • EXPLAIN ANALYZE runs the query: rows=estimate/actual. Our plan guessed 3 Gold customers (actual 517) and 25,000 orders on one day (actual 1,621).
  • EXPLAIN CBO [COST] shows the Calcite logical plan the cost-based optimiser chose, with its own row estimates and costs.
  • SET hive.explain.user=false switches to the classic stage view with full Statistics lines and Group By modes.
  • EXPLAIN VECTORIZATION [ONLY] SUMMARY|DETAIL, EXPLAIN DEPENDENCY, EXPLAIN LOCKS, EXPLAIN EXTENDED, EXPLAIN AST answer narrower questions.

Exam tip: “How do you analyse a slow Hive query?” Start with EXPLAIN: read vertices and edges, find the join type (map join vs shuffle join), compare estimated rows with reality (EXPLAIN ANALYZE), check statistics (Col:NONE is a warning), partition pruning (EXPLAIN DEPENDENCY) and vectorisation. Then change one thing and compare.

  1. Step 1 · The query and its answer

    SELECT c.city, COUNT(*) AS n, SUM(o.amount) AS rev
FROM orders o JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_date = '2026-10-05' AND c.plan = 'Gold'
GROUP BY c.city ORDER BY rev DESC LIMIT 3;

5 See it happen

Reading a real plan

Left: real EXPLAIN output. Right: how to read it.

From SQL to a Tez DAG 5 steps
What you see
  1. The plan starts with the vertex dependencies: four Tez vertices.
  2. At the bottom, the scans and filters, with row estimates.
  3. The join, the two-phase aggregation and the top-3 limit.
  4. EXPLAIN ANALYZE shows estimates that are far from reality.
  5. EXPLAIN CBO shows the logical plan chosen by Calcite.
Behind the screen
  1. Map vertices read files; reducers receive shuffled rows; the broadcast edge copies a small input to every task.
  2. Data enters at the TableScans; filters are pushed as close to the scans as possible.
  3. The map join probes a hash table; partial aggregates shrink data before the shuffle.
  4. Estimates come from statistics; missing or uniform-assumption stats produce big errors.
  5. Hive parses SQL, Calcite optimises the logical plan, then Hive builds the physical Tez plan.

9 Quiz and revision

Check yourself

Quick revision

Lesson 8.1 in one screen

  • EXPLAIN compiles and prints the plan; it does not run the query. EXPLAIN ANALYZE runs it and prints rows=estimated/actual.
  • Read bottom-up: TableScan → Filter → Select → Join → Group By → Reduce Sink → … → File Output.
  • Vertices: Map = reads data, Reducer = after a shuffle. BROADCAST_EDGE = small side copied (map join); SIMPLE_EDGE = shuffle.
  • TableScan line: Tbl:COMPLETE, Col:NONE tells you which statistics exist. Missing column stats → bad estimates.
  • EXPLAIN CBO [COST]: the Calcite plan with row counts and cumulative cost, before physical operators.
  • hive.explain.user=false gives the classic stage view with Statistics lines; VECTORIZATION shows whether each vertex is vectorised and why not.
  • DEPENDENCY lists input tables and partitions (check pruning); LOCKS lists locks for ACID statements; FORMATTED gives JSON.
  • Review checklist: partitions read, join type, number of shuffles, estimate gaps ≥10×, vectorisation, Col:NONE.

Interview and viva questions

Why are there several kinds of EXPLAIN?

Each answers a different question. Plain EXPLAIN: what will run. ANALYZE: how good were the estimates. CBO: what did the optimiser decide and why (costs). VECTORIZATION: is the fast path used. DEPENDENCY: which partitions. LOCKS: what will be locked. In practice you use plain EXPLAIN most and ANALYZE when the plan looks right but the query is slow.

Is EXPLAIN ANALYZE safe on production?

It runs the full query, so it costs the same as running it. For INSERT statements check the docs for your version and test on a copy: the point is to collect actual counts, not to write data. For very long queries, run it on a sample or a smaller partition.

Why does the CBO plan show 272,144 join rows while the physical plan shows 27,500?

They are estimates from different stages with different inputs (the CBO used its own selectivity for the date filter, 6,750 rows, and its own join formula). Neither was close to the real 427. Use the estimates to find where statistics are missing, not as exact predictions.

What is the Top N Key operator?

An optimisation for ORDER BY … LIMIT: tasks drop rows that cannot reach the top N before shuffling them. In our plan it appeared before the final shuffle with top n:3.

Does Tez UI or the Hive web UI show the same thing?

They show the executed DAG with real counters per vertex and task (time, records, spills). EXPLAIN is what Hive planned; the UIs show what happened. Lesson 8.5 uses both to troubleshoot slow queries.

Real-world scenario questions (asked in company interviews)

Plan reading is asked at every level; seniors are expected to explain estimates and costs.

Any company · HiveFresher

“How do you see how Hive will run a query?”

Explain EXPLAIN and what you look for.

The interviewer is checking: do you know EXPLAIN and the basic parts of a plan?

Show a strong answer

Prefix the query with EXPLAIN. It shows the stages and, on Tez, the vertices (Map and Reducer) and their edges, and inside each vertex the operators: TableScan, Filter, Join, Group By, Reduce Sink and so on, read bottom-up. I check which tables and partitions are read, the join type and the number of shuffles.

Avoid: Saying EXPLAIN runs the query.

Data engineeringMid-level

Same query, different speed

A join query took 2 minutes last month and 20 minutes now. Nothing changed in the SQL.

The interviewer is checking: can you use plans to find a regression?

Show a strong answer
  1. Compare EXPLAIN now with the old plan (saved or from logs): look for a map join turned into a shuffle join, or more partitions read.
  2. Run EXPLAIN ANALYZE and find the first estimate off by 10× or more.
  3. Check statistics of that table (Col:NONE, stale numRows) and refresh them with ANALYZE.

Avoid: Increasing memory and reducers without looking at the plan.

AnalyticsMid-level

Report reads the whole table

A daily report filters one date but scans every partition.

The interviewer is checking: do you know how to prove and fix lost pruning?

Show a strong answer
  • Prove it with EXPLAIN DEPENDENCY: input_partitions lists all of them.
  • Look for an OR with a normal column or a non-deterministic function on the partition column.
  • Rewrite so the partition condition stands alone (AND, or UNION ALL of two queries).

Avoid: “Add more partitions.”

PlatformSenior

Plan reviews as a team practice

Set up a lightweight plan review for the 20 most expensive queries.

The interviewer is checking: can you turn plan reading into a process?

Show a strong answer
  • Store EXPLAIN (FORMATTED for tooling) of each query in the repo; diff it in CI against a test environment with production-like statistics.
  • Checklist: partitions read, join strategy, shuffles, Col:NONE, vectorisation, estimate gaps from a weekly EXPLAIN ANALYZE sample.
  • Keep statistics fresh as part of the load jobs, so plans stay stable.

Avoid: Reviewing only when users complain.
