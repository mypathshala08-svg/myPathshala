2 Definition

Troubleshooting Hive queries

Formal definition (write this in exams)

Troubleshooting a Hive query means locating the query and stage responsible for a problem, determining whether it is a compile-time error (parsing, semantic analysis, strict checks), a runtime failure (task or vertex failure, resource limits, timeouts), a performance problem (plan, statistics, data layout, skew, resources) or a correctness problem (silent NULLs, duplicates, wrong joins), and then fixing the root cause. The main evidence comes from SHOW PROCESSLIST, EXPLAIN, the Tez vertex summary and counters (hive.tez.exec.print.summary), HiveServer2 and Tez task logs, and the nested Caused by chain of exceptions.

In simple words

When a query is slow or fails, find which query and which step is the problem, read the actual cause in the error message, and fix that cause: the plan, the statistics, the files, the data or a setting. Guessing and adding memory usually does not help.

Words you’ll meet in this lesson

Compile-time errorRejected before running: syntax, semantics, strict checks.
Runtime failureA task or vertex failed while running.
Task attemptOne try of a task; Tez retries a failing task.
Root causeUsually the last “Caused by” in the stack.
Strict checksSettings that block risky queries before they run.
CounterA number Tez records per vertex: records, files, bytes, spills.
Small filesMany tiny files that cost time to open and track.
Silent NULLA failed conversion that returns NULL instead of an error.

Troubleshooting at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A doctor’s routine

  • A doctor asks where it hurts, runs tests, then treats the cause, not the symptom. Do the same with queries.
  • Slow and failed are different problems: slow needs measuring (plan, counters); failed needs reading the error.
  • Most error messages repeat themselves; the real reason is usually near the end.

Intermediate Tools and where they point

  • Running now: SHOW PROCESSLIST, KILL QUERY 'id', YARN / Tez UI.
  • Slow: EXPLAIN (8.1), statistics (8.2), join type (8.3), vectorisation and task counts (8.4), counters like INPUT_FILES, SPILLED_RECORDS, SHUFFLE_BYTES.
  • Failed: the Hive error code, “Vertex failed”, task attempts, the last Caused by.
  • Prevented: strict checks for Cartesian products, partition filters, ORDER BY without LIMIT; limits on dynamic partitions; query timeouts.

Advanced What the lab showed

  • A failing expression made Map 1 fail 4 task attempts, then the vertex, then the DAG; the cause was one line: ASSERT_TRUE(): assertion failed.
  • 300 small ORC files: the same 5,000,000-row query took about 1.7 s vs 1.0 s after rewriting into one file, though Tez grouped all 300 splits into one task. CONCATENATE refused: “only … managed tables”.
  • Bad casts, division by zero, invalid dates and decimal overflow all returned NULL without any error.

Exam tip: “How do you troubleshoot a slow Hive query?” Reproduce and measure (Tez summary, counters), read the plan (EXPLAIN / ANALYZE), check statistics, join strategy, partition pruning, vectorisation, file counts and skew, change one thing at a time, and compare. For failures, read the last “Caused by” first.

Eight real problems, produced and solved

All outputs are real, from the Hive 4.2.1 lab. Long Java messages are shortened with “…”.

  1. Step 1 · Find what is running

    -- session 1: a runaway self-join on 5,000,000 rows
SELECT COUNT(*) FROM orders_big_txt a JOIN orders_big_txt b ON a.customer_id = b.customer_id;

-- session 2:
SHOW PROCESSLIST;     -- selected columns
    +-----------+------------------+----------------------------------------------------------+---------+------------------+--------------+ | User Name | Execution Engine | Query ID | State | Elapsed Time (s) | Runtime (s) | +-----------+------------------+----------------------------------------------------------+---------+------------------+--------------+ | hive | tez | hive_20261027114151_acf33829-3758-4648-b9f7-99c5ef4540af | RUNNING | 13 | Not finished | +-----------+------------------+----------------------------------------------------------+---------+------------------+--------------+
    Hive 4’s SHOW PROCESSLIST lists open sessions with the running Query ID, state and elapsed time. The query joins each customer’s 2,500 rows with the same 2,500 rows: about 12.5 billion pairs, a classic accidental explosion.

  2. Step 2 · Kill it

    KILL QUERY 'hive_20261027114151_acf33829-3758-4648-b9f7-99c5ef4540af';

-- what session 1 sees:
    Error: Query was cancelled. User invoked KILL QUERY (state=01000,code=0)
    The victim session gets Query was cancelled. User invoked KILL QUERY and its Tez DAG is stopped. Admins (or the query’s owner) can kill by Query ID, without restarting HiveServer2. In our lab the KILL statement itself did not return to its client promptly, so run it from a separate session and check PROCESSLIST again.

  3. Step 3 · Read a task failure from the bottom

    SELECT COUNT(*) FROM orders WHERE assert_true(amount < 800) IS NULL;
-- the error, with the repeated stack traces removed
    FAILED: Execution Error, return code 2 from org.apache.hadoop.hive.ql.exec.tez.TezTask. Vertex failed, vertexName=Map 1, vertexId=vertex_1793101675014_0001_1_00, diagnostics=[Task failed, taskId=task_1793101675014_0001_1_00_000000, … TaskAttempt 0 failed, TaskAttempt 1 failed, TaskAttempt 2 failed, TaskAttempt 3 failed (each with): Caused by: org.apache.hadoop.hive.ql.metadata.HiveException: ASSERT_TRUE(): assertion failed. Vertex did not succeed due to OWN_TASK_FAILURE, failedTasks:1 killedTasks:0 DAG did not succeed due to VERTEX_FAILURE. failedVertices:1 killedVertices:1
    The first line only says that Map 1 failed (return code 2 is a runtime failure). Tez retried the task 4 times (attempts 0–3), each failing with the same last “Caused by”: ASSERT_TRUE(): assertion failed, because some orders have amount ≥ 800. Then the vertex failed (OWN_TASK_FAILURE) and the DAG was stopped. In real jobs the last “Caused by” names the bad UDF, the corrupt file or the out-of-memory error; retries do not help with bad data.

    Three SemanticExceptions, raised at compile time, before any resource is used: a join without a condition (2,000 × 2,000 = 4,000,000 pairs here, billions in production), a full scan of a partitioned table, and a global sort without LIMIT. Each message names the setting. Note that hive.mapred.mode=strict alone was enough to block the ORDER BY.

  5. Step 5 · Runtime limits: dynamic partitions and timeouts

    SET hive.exec.dynamic.partition.mode=nonstrict;
SET hive.exec.max.dynamic.partitions.pernode=10;
INSERT INTO dp_test PARTITION (order_date) SELECT order_id, amount, order_date FROM orders;

SET hive.query.timeout.seconds=1s;
SELECT customer_id, COUNT(DISTINCT city), SUM(amount) FROM orders_big_txt GROUP BY customer_id;
    Caused by: org.apache.hadoop.hive.ql.metadata.HiveFatalException: [Error 20004]: Fatal error occurred when node tried to create too many dynamic partitions. The maximum number of dynamic partitions is controlled by hive.exec.max.dynamic.partitions and hive.exec.max.dynamic.partitions.pernode. Maximum was set to 10 partitions per node, number of dynamic partitions on this node: 11 Error: Query timed out after 0 seconds (state=,code=0)
    The insert would create 30 daily partitions, but one task may create only 10: Error 20004 stops it at the 11th, with the numbers in the message. Raise the limit only after checking that the partition column is right (a timestamp instead of a date can create millions). The timeout cancelled the query after 1 second; the message rounds it down to “0 seconds”.

  6. Step 6 · Slow because of 300 small files

    -- orders_frag: 5,000,000 rows written by 300 reducers with hive.merge.tezfiles=false
SET hive.tez.exec.print.summary=true;
SELECT city, COUNT(*), SUM(amount) FROM orders_frag GROUP BY city;

ALTER TABLE orders_frag CONCATENATE;

SET hive.merge.tezfiles=true;
INSERT OVERWRITE TABLE orders_frag SELECT * FROM orders_frag;
    table files INPUT_FILES_Map_1 RAW_INPUT_SPLITS_Map_1 query time (2 runs) orders_frag before 300 300 300 1.806 seconds 1.706 seconds orders_frag after 1 1 1 1.046 seconds 0.976 seconds Error: Error while compiling statement: FAILED: SemanticException [Error 30034]: Concatenate/Merge can only be performed on managed tables
    The counters show the problem: INPUT_FILES_Map_1: 300. Tez grouped all 300 splits into one task, yet the query took about 1.7 s against 1.0 s for the same data in one file: opening and reading 300 file footers costs time (and on HDFS, NameNode memory). CONCATENATE was refused because the table is external; rewriting it with hive.merge.tezfiles=true produced 1 file.

  7. Step 7 · Wrong results without any error

    SELECT CAST('12a' AS INT) AS bad_cast, 10 / 0 AS div_zero,
       CAST('2026-13-45' AS DATE) AS bad_date, CAST(99999 AS DECIMAL(4,2)) AS overflow;
    +-----------+-----------+-----------+-----------+ | bad_cast | div_zero | bad_date | overflow | +-----------+-----------+-----------+-----------+ | NULL | NULL | NULL | NULL | +-----------+-----------+-----------+-----------+
    Four mistakes, four NULLs, no error and no warning. In a SUM or COUNT(col) these rows just disappear, so a dashboard shows smaller totals. Check NULL counts after every load (COUNT(*) - COUNT(col)), and compare row counts between source and target.

6 Real-world use

Troubleshooting at work

1. On-call runbooks

Data platform teams keep runbooks: how to find a query, kill it, read the error and rerun a partition safely.

Alert→runbook→Resolved

2. Guard rails on shared clusters

Strict checks, query timeouts and partition limits stop one user’s mistake from consuming the whole cluster.

Risky SQL→rejected→Cluster safe

3. Job monitoring

Counters such as records read, input files and spilled records are exported per job and charted to catch slow drifts.

Counters→trend→Early warning

4. Data quality checks

NULL rates, row counts and duplicate keys are checked after every load, catching silent conversion errors.

Load→DQ checks→Trusted numbers

5. Small-file housekeeping

Scheduled jobs find tables with many small files and rewrite or compact them before queries and the NameNode suffer.

File scan→merge→Healthy tables

# Read a Hive/Tez error the way an on-call engineer does: last "Caused by" first
error = """FAILED: Execution Error, return code 2 from org.apache.hadoop.hive.ql.exec.tez.TezTask. Vertex failed, vertexName=Map 1
TaskAttempt 0 failed
Caused by: java.lang.RuntimeException: org.apache.hadoop.hive.ql.metadata.HiveException: Hive Runtime Error while processing row
Caused by: org.apache.hadoop.hive.ql.metadata.HiveException: Hive Runtime Error while processing row
Caused by: org.apache.hadoop.hive.ql.metadata.HiveException: ASSERT_TRUE(): assertion failed.
DAG did not succeed due to VERTEX_FAILURE. failedVertices:1 killedVertices:1"""

lines = error.split("\n")
causes = [l for l in lines if l.startswith("Caused by")]
kind = "runtime (return code 2)" if "return code 2" in lines[0] else "compile time"
print("kind      :", kind)
print("vertex    :", lines[0].split("vertexName=")[1])
print("root cause:", causes[-1].split(": ", 2)[-1])
kind : runtime (return code 2) vertex : Map 1 root cause: ASSERT_TRUE(): assertion failed.

  • kind = "runtime (return code 2)" if "return code 2" in lines[0] else "compile time"Compile-time errors (SemanticException, code 40000/100xx) happen before any task; return code 2 means a task failed at run time.

Run on your PC: a data quality check and two quick diagnostics

Small queries that belong in every troubleshooting toolkit. Outputs are real, from Hive 4.2.1.

1 · How many values become NULL, and does the fix work?

SELECT COUNT(*) AS total_rows,
       COUNT(CAST(a AS DECIMAL(10,2))) AS cast_ok,
       COUNT(*) - COUNT(CAST(a AS DECIMAL(10,2))) AS became_null,
       COUNT(CAST(regexp_replace(a, ',', '') AS DECIMAL(10,2))) AS cast_ok_after_fix
FROM (SELECT stack(5, '1,250.00', '300.00', 'N/A', '99.5', '2,000') AS a) s;

Check yourself

Quick revision

Lesson 8.5 in one screen

  • Method: find (PROCESSLIST, counters) → read (last “Caused by”) → fix the cause → measure again.
  • SHOW PROCESSLIST shows Query IDs; KILL QUERY 'id' cancels (“Query was cancelled. User invoked KILL QUERY”).
  • Compile-time (SemanticException) vs runtime (return code 2, Vertex failed, task attempts 0–3).
  • Strict checks: cartesian.product, no.partition.filter (Error 10056), orderby.no.limit; or hive.mapred.mode=strict.
  • Limits: hive.exec.max.dynamic.partitions[.pernode] (Error 20004), hive.query.timeout.seconds.
  • Small files: INPUT_FILES 300 → 1.7 s vs 1 file → 1.0 s; CONCATENATE only on managed tables; rewrite with hive.merge.tezfiles=true.
  • Silent NULLs: bad casts, /0, invalid dates, decimal overflow → NULL; check COUNT(*) - COUNT(col) after loads.
  • Counters: RECORDS_IN, INPUT_FILES, GROUPED_INPUT_SPLITS, SPILLED_RECORDS, SHUFFLE_BYTES(_TO_DISK), DESERIALIZE_ERRORS, CREATED_FILES.

Interview and viva questions

Where are the full logs?

HiveServer2 writes its log (often under /tmp/<user>/hive.log or the service log directory); Beeline shows a summary, and with --verbose=true or INFO lines more detail. Task logs live with the Tez containers: in YARN, yarn logs -applicationId application_… or the Tez UI. The Query ID links all of them.

What does “return code 2” mean?

It is the code HiveServer2 reports when the Tez (or MapReduce) task of the query failed at run time. It says nothing about why; the reason is in the diagnostics that follow, typically the last “Caused by”.

How do I find out of memory errors?

Look for java.lang.OutOfMemoryError, “Container killed … running beyond physical memory limits”, or map-join memory messages in the task diagnostics. Common fixes: correct statistics so a big table is not broadcast (8.2/8.3), larger hive.tez.container.size with heap about 80%, or less data per task.

Is it safe to just raise limits like max dynamic partitions?

Only after checking why the limit was hit. Partitioning by a high-cardinality column (a timestamp, a user ID) can create millions of tiny partitions and overload the metastore. The limit is often protecting you.

Does Hive keep a history of queries?

HiveServer2’s web UI (port 10002) shows recent and running queries with their plans and timings. Distributions add query history tables and tools (for example Hue, Cloudera’s query history). In our lab the sys database was not installed, so we used PROCESSLIST and logs.

print([l for l in lines if l.startswith("Caused by")][-1].split("HiveException: ")[-1])
ASSERT_TRUE(): assertion failed.

How it works: The same idea works with grep on a log: grep "Caused by" hive.log | tail -1.

P5Medium

Classify by error code

Map Hive error codes to categories.

Input
10056, 20004, 30034, 40000
Expected output
10056 -> semantic analysis (strict check)
20004 -> runtime, retry unlikely to help
30034 -> other (concatenate rule)
40000 -> generic, retry may help
Show solution and explanation 
codes = {10056: "semantic analysis (strict check)", 20004: "runtime, retry unlikely to help", 30034: "other (concatenate rule)", 40000: "generic, retry may help"}
for c, k in codes.items():
    print(c, "->", k)
10056 -> semantic analysis (strict check) 20004 -> runtime, retry unlikely to help 30034 -> other (concatenate rule) 40000 -> generic, retry may help

How it works: Hive’s ErrorMsg ranges: 1xxxx semantic analysis, 2xxxx runtime errors where retries are unlikely to help, 3xxxx errors with no retry advice, 4xxxx errors where a retry may help. The text after the code is what matters most.

P6Medium

NULL rate jump

Alert when today’s NULL rate is more than 5 points above the 7-day average.

Input
rates
Expected output
ALERT (avg 0.11%, today 6.1%)
Show solution and explanation 
history = [0.001, 0.0012, 0.0009, 0.001, 0.0011, 0.001, 0.0012]
today = 0.061
avg = sum(history) / len(history)
print("ALERT" if today - avg > 0.05 else "ok", f"(avg {avg:.2%}, today {today:.1%})")
ALERT (avg 0.11%, today 6.1%)

How it works: A relative check catches format changes that a fixed threshold would miss.

Real-world scenario questions (asked in company interviews)

Troubleshooting is where interviews become practical; walk through your method out loud.

Any company · HiveFresher

“A Hive query failed. What do you do?”

Describe your first steps.

The interviewer is checking: do you read errors methodically?

Show a strong answer

Check whether it failed at compile time (SemanticException: fix the SQL or the setting it names) or at run time (return code 2, Vertex failed). For runtime failures I read the last “Caused by” in the diagnostics or the task logs, which names the real reason: bad data, a UDF error, memory. I fix that cause and rerun only what failed.

Avoid: Rerunning repeatedly without reading the error.

Data engineeringMid-level

A query got slow

A daily query went from 5 to 40 minutes.

The interviewer is checking: can you measure before changing settings?

Show a strong answer
  1. Compare counters with an older run: RECORDS_IN, INPUT_FILES, SHUFFLE_BYTES, SPILLED_RECORDS.
  2. Compare EXPLAIN plans: pruning, join type, statistics (Col:NONE, stale numRows).
  3. Fix the cause found (filter, statistics, small files, skew), one change at a time.

Avoid: Doubling container memory first.

AnalyticsMid-level

Numbers look wrong

Revenue on the dashboard dropped 12% but no job failed.

The interviewer is checking: do you know silent failure modes?

Show a strong answer
  • Check NULL counts and row counts per load; failed casts become NULL silently.
  • Check duplicates per key after joins (fan-out) and late-arriving partitions.
  • Fix the conversion, reload affected partitions, add a data quality check.

Avoid: Assuming the business changed.

PlatformSenior

Protecting a shared cluster

Design guard rails for a cluster used by 300 analysts and 50 ETL jobs.

The interviewer is checking: can you prevent problems, not only fix them?

Show a strong answer
  • Strict checks on (cartesian, partition filter, ORDER BY without LIMIT), query timeouts on ad-hoc queues, sensible dynamic partition limits.
  • Queues or workload management separating ETL and ad-hoc; counters exported and charted per job.
  • Runbooks: PROCESSLIST/KILL, reading failures, partition reruns, small-file housekeeping, data quality checks.

Avoid: Relying on users to write safe SQL.
