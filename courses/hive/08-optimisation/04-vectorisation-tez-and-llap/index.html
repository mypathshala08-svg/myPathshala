1 The story

“The plan is right. Why is it still slow?”

Before you start: how a query becomes a Tez job (1.4), ORC (6.2) and reading plans (8.1).

Kabir has a good plan now: right statistics, right join. But the platform team says many queries still waste CPU, start too few or too many tasks, and wait for containers. Arjun Sir builds a 5-million-row copy of orders to measure what the execution engine itself can do.

Riya

Sir, what does “vectorized” in the plan actually change?

Arjun Sir

Instead of pushing one row at a time through every operator, Hive pushes a batch of 1,024 rows stored column by column. Each operator runs a tight loop over arrays, which modern CPUs love. On our 5-million-row table it made the map work about 6× faster.

Kabir

And Tez tuning? I see dozens of settings online.

Arjun Sir

Most of them control three things: how many map tasks (split grouping), how many reducers (bytes per reducer, auto parallelism), and how much memory each container gets. We will change each and count the tasks. And LLAP, the long-lived daemons with a cache, we will try to switch on and see exactly what it needs. All outputs are real, from Hive 4.2.1.

2 Definition

Vectorisation, Tez tuning and LLAP

Formal definition (write this in exams)

Vectorised query execution processes rows in batches (VectorizedRowBatch, 1,024 rows by default) stored as column vectors, so operators such as scans, filters, expressions and aggregations run as loops over primitive arrays instead of per-row object calls; it is enabled with hive.vectorized.execution.enabled and works best with ORC and Parquet input. Tez tuning adjusts how the DAG is executed: input split grouping (number of map tasks), reducer parallelism, container memory and container reuse. LLAP (Live Long and Process) is an optional layer of persistent daemons that execute query fragments with an in-memory columnar cache and fast start-up, coordinated by Tez and discovered through ZooKeeper.

In simple words

Vectorisation makes each task faster by handling 1,024 rows at a time. Tez tuning decides how many tasks run and how much memory they get. LLAP keeps worker processes running all the time, with a data cache, so interactive queries start and finish quickly.

Execution speed at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Carrying bricks

  • Carrying one brick at a time is slow; carrying a stack of 1,024 bricks at once is much faster. Vectorisation does that with rows.
  • Tez decides how many workers (tasks) to use. Too few: slow. Too many: time wasted starting them.
  • LLAP keeps workers always running and remembers recent data, so short queries start instantly.

Intermediate The settings behind them

  • hive.vectorized.execution.enabled (map) and hive.vectorized.execution.reduce.enabled: process VectorizedRowBatches of 1,024 rows. Best with ORC and Parquet; check EXPLAIN VECTORIZATION.
  • Map tasks: Tez groups input splits between tez.grouping.min-size and tez.grouping.max-size.
  • Reducers: estimated shuffle bytes / hive.exec.reducers.bytes.per.reducer (256 MB default), capped by hive.exec.reducers.max (1,009); hive.tez.auto.reducer.parallelism lowers the count at run time; mapreduce.job.reduces forces it.
  • Memory: hive.tez.container.size and hive.tez.java.opts (heap about 80% of the container).

Advanced What the lab showed

  • Vectorised vs row mode on 5,000,000 rows: Map 1 about 300–400 ms vs 2,250–2,400 ms; whole query about 1.0 s vs 3.0 s, three runs each.
  • A UDF without a vector version still ran through the VectorUDFAdaptor (2.1 s); forbidding the adaptor made the map side non-vectorised (3.4 s) with an explicit notVectorizedReason.
  • Split grouping changed Map 1 from 1 to 8 tasks; bytes-per-reducer changed Reducer 2 from 1 to 8, auto parallelism cut it to 2. LLAP mode failed without a ZooKeeper registry.

Exam tip: “What is vectorisation in Hive?” Processing 1,024 rows at a time as column vectors instead of row by row, which cuts per-row overhead and uses the CPU efficiently. Enable with hive.vectorized.execution.enabled=true, best with ORC/Parquet, verify with EXPLAIN VECTORIZATION (look for Execution mode: vectorized and notVectorizedReason).

EXPLAIN VECTORIZATION EXPRESSION SELECT md5(city) AS x, COUNT(*) FROM orders_big GROUP BY md5(city);

SET hive.vectorized.adaptor.usage.mode=none;
EXPLAIN VECTORIZATION ONLY SUMMARY SELECT md5(city) AS x, COUNT(*) FROM orders_big GROUP BY md5(city);
-- and timing both
    hive.vectorized.adaptor.usage.mode=all selectExpressions: VectorUDFAdaptor(md5(city)) -> 8:string usesVectorUDFAdaptor: true usesVectorUDFAdaptor: false -- adaptor.usage.mode=none notVectorizedReason: Select expression for SELECT operator: UDF GenericUDFBridge ==> md5 (Column[city]) not supported vectorized: false vectorized: true run 1 adaptor.usage.mode=all 2.081 seconds run 1 adaptor.usage.mode=none 3.47 seconds run 2 adaptor.usage.mode=all 2.21 seconds run 2 adaptor.usage.mode=none 3.424 seconds
    md5 has no vector implementation, so Hive wrapped it: VectorUDFAdaptor(md5(city)) converts each batch to rows for that one expression and keeps everything else vectorised (about 2.1 s).   6. Step 6 · Changing the number of tasks

    -- orders_big_txt: the same 5,000,000 rows as one 246 MB text file
SELECT customer_id, COUNT(*) AS n, SUM(amount) FROM orders_big_txt GROUP BY customer_id;
-- run once per setting below, with hive.tez.exec.print.summary=true
    -- defaults Map 1 tasks: 1 Reducer 2 tasks: 1 query time: 3.394 seconds SET tez.grouping.max-size=16777216; SET tez.grouping.min-size=8388608; Map 1 tasks: 8 Reducer 2 tasks: 1 query time: 4.824 seconds SET hive.exec.reducers.bytes.per.reducer=100000; Map 1 tasks: 1 Reducer 2 tasks: 8 query time: 4.82 seconds SET hive.exec.reducers.bytes.per.reducer=100000; SET hive.tez.auto.reducer.parallelism=true; Map 1 tasks: 1 Reducer 2 tasks: 2 query time: 3.714 seconds SET mapreduce.job.reduces=6; Map 1 tasks: 1 Reducer 2 tasks: 6 query time: 4.483 seconds
    The 246 MB file has 8 input splits of up to 32 MB. By default Tez grouped them into 1 map task; with tez.grouping.max-size at 16 MB no two splits could be grouped, so 8 map tasks ran (grouping merges splits, it never cuts them). Bytes per reducer at 100,000 gave 8 reducers (the estimated shuffle is about 765 KB: 6,171 rows × 124 bytes). With auto reducer parallelism on as well, Tez lowered the reducer count at run time after seeing the real data, ending with 2. mapreduce.job.reduces=6 forced 6. On one machine every extra task cost time; on a cluster it buys parallelism.

    EXPLAIN SELECT order_id, city, amount FROM orders_big WHERE city = 'Pune' LIMIT 5;

Execution tuning at work

1. CPU savings on ETL

Keeping heavy ETL on ORC/Parquet with vectorisation cuts CPU hours, which on cloud clusters is directly money.

ORC + vector→fewer CPU s→Lower bill

2. Right-sized parallelism

Auto reducer parallelism and split grouping keep tasks large enough to be efficient and many enough to finish on time.

Estimates→task counts→On-time SLAs

3. Interactive analytics

Distributions such as Cloudera Data Warehouse offer LLAP-based virtual warehouses for BI tools.

BI tool→LLAP→Seconds

4. Fixing container failures

Tasks killed for exceeding memory are fixed with container size and heap settings, or by reducing map-join sizes.

Killed task→memory tuning→Stable job

Fetch-task conversion lets analysts preview tables with SELECT … LIMIT instantly, without using cluster resources.

Run the code: batches, tasks and reducers

These programs model what Hive’s execution settings compute, using the lab numbers. Press Run, then try the challenges.

# Row-at-a-time vs batch-at-a-time, the idea behind vectorisation
import time
N = 1_000_000
amount = [i % 840 + 40 for i in range(N)]

t0 = time.perf_counter()
total = 0
for a in amount:                     # row mode: one step per row
    if a > 100:
        total += a
row_ms = (time.perf_counter() - t0) * 1000

t0 = time.perf_counter()
total2 = 0
for s in range(0, N, 1024):          # vectorised: one step per batch of 1,024
    batch = amount[s:s + 1024]
    total2 += sum(a for a in batch if a > 100)
vec_ms = (time.perf_counter() - t0) * 1000
print("same result:", total == total2)
print(f"row loop {row_ms:.0f} ms, batch loop {vec_ms:.0f} ms (Python, illustrative)")
same result: True row loop 75 ms, batch loop 41 ms (Python, illustrative)
  • for s in range(0, N, 1024): # vectorised: one step per batch of 1,024Hive’s VectorizedRowBatch holds 1,024 rows as column arrays. In Java the gain comes from tight loops over primitive arrays; Python only shows the structure.
  • print(f"row loop {row_ms:.0f} ms, batch loop {vec_ms:.0f} ms (Python, illustrative)")Python timings say little about Java. The real measurement is in Step 3: 300–400 ms vs about 2,300 ms.

Interview and viva questions

What exactly does LLAP add over Tez containers?

Daemons that are already running (no JVM start-up), a shared in-memory columnar cache of ORC/Parquet data across queries, an I/O elevator that reads and decodes data asynchronously, and fine-grained fragment scheduling. Tez still plans and coordinates the DAG. It shines for many short interactive queries; for large batch ETL plain Tez containers are often enough.

Is vectorisation always on?

In Hive 4 it is enabled by default for map and reduce sides. It can still fall back per vertex: unsupported UDFs (with the adaptor forbidden), some complex types or expressions, or input formats without vector support. Check EXPLAIN VECTORIZATION for key jobs.

Should I set mapreduce.job.reduces for every query?

No. A fixed number is right for one data size only. Prefer correct statistics, a sensible bytes-per-reducer value and auto reducer parallelism; force a count only for a specific query with a known reason.

What are Tez sessions and container reuse?

HiveServer2 can keep Tez application masters (sessions) open and reuse containers between tasks and queries, avoiding start-up cost. Settings such as hive.server2.tez.initialize.default.sessions (false in our lab), hive.server2.tez.sessions.per.default.queue and Tez’s container reuse control this. It is a cheaper step towards interactive latency than LLAP.

What is hive.exec.parallel?

It let independent stages of a MapReduce plan run at the same time. On Tez the whole query is one DAG and independent vertices already run concurrently, so it matters little in Hive 4.

Real-world scenario questions (asked in company interviews)

Execution tuning questions test whether you measure before you tune.

Any company · HiveFresher

“What is vectorised execution?”

Explain vectorisation and how to check it.

The interviewer is checking: do you know batches and EXPLAIN VECTORIZATION?

Show a strong answer

Instead of one row at a time, operators process batches of 1,024 rows stored as column vectors, which reduces per-row overhead and uses the CPU better. It is on by default in Hive 4 and works best with ORC or Parquet. I check it with EXPLAIN VECTORIZATION: “Execution mode: vectorized” per vertex, or a notVectorizedReason.

Avoid: Confusing it with parallelism across tasks.

Data engineeringMid-level

Job slowed after adding a UDF

A job became about 3× slower after a custom UDF was added.

The interviewer is checking: can you find a vectorisation fallback?

Show a strong answer
  1. EXPLAIN VECTORIZATION on old and new SQL: look for vectorized: false and notVectorizedReason naming the UDF.
  2. Check hive.vectorized.adaptor.usage.mode; the adaptor keeps the rest vectorised.
  3. Replace the UDF with built-in functions or write a vectorised UDF.

Avoid: Adding more containers.

PlatformMid-level

Thousands of tiny reducers

A job runs 1,009 reducers that each process a few MB and writes thousands of small files.

The interviewer is checking: do you know how reducer counts are chosen?

Show a strong answer
  • Reducers = estimated shuffle / bytes-per-reducer, capped at hive.exec.reducers.max: the estimate is too high (statistics).
  • Enable hive.tez.auto.reducer.parallelism so Tez trims at run time.
  • Fix statistics; raise bytes-per-reducer if the target is too small.

Avoid: Hard-coding mapreduce.job.reduces for every job.

ArchitectureSenior

Interactive SQL for 200 analysts

Design Hive for BI dashboards with a 3-second target alongside nightly ETL.

The interviewer is checking: do you know LLAP and its costs?

Show a strong answer
  • LLAP daemons with cache for BI (needs ZooKeeper, dedicated memory), or pre-warmed Tez sessions as a lighter option.
  • Workload management resource plans to separate BI and ETL.
  • ORC with good layout and statistics, vectorisation verified; consider an MPP engine if latency targets are strict.

Avoid: “Just add nodes.”
