Text, SequenceFile and Avro tables

Every Hive table stores its rows in some file format, and the choice decides size, speed and what happens when the data changes. Kabir writes the same 50,000 orders in all six formats, compares their sizes (from 4.3 MB down to 0.44 MB), then solves a real bug: a partner added a column and a text table silently shifted values, while an Avro table read everything correctly. 1 The story

“Why does the report show a city called Gold?”

Before you start: you need row formats and SerDes (2.4) and loading data (2.5).

A partner company sends TiffinGo customer files every week. This week the city report suddenly shows two new cities, Gold and Basic. Nobody changed the Hive table. Kabir opens the CSV and sees that the partner added a plan column in the middle.

Kabir

Sir, the query didn’t fail. It just put the plan into the city column!

Arjun Sir

A text table has no idea what the columns are called. Hive splits each line at the commas and takes the third value as city, whatever it is. Formats like Avro store the schema inside every file, so Hive can match fields by name and fill a default for fields that old files don’t have.

Riya

So which format should we use for everything?

Arjun Sir

It depends on the job. Today we write the same 50,000 orders in all six formats Hive supports and compare their sizes and their first bytes, compress text files, and look at the two row formats you will meet in older systems and data exchange: SequenceFile and Avro. 2 Definition

Hive file formats

Formal definition (write this in exams)

A file format (storage format) defines how a table’s rows are encoded in its data files. In Hive it is declared with STORED AS (TEXTFILE, SEQUENCEFILE, RCFILE, AVRO, ORC, PARQUET, JSONFILE) or with explicit INPUTFORMAT/OUTPUTFORMAT classes and a SerDe. TEXTFILE stores delimited plain text; SEQUENCEFILE is Hadoop’s binary key/value container with optional record or block compression; AVRO is a row-oriented binary format whose files embed a JSON schema, supporting schema evolution through reader/writer schema resolution. Formats differ in size, read speed, splittability, type support and schema handling.

In simple words

The file format is how Hive writes your rows to disk. Text is easy to read but big and fragile. SequenceFile is Hadoop’s simple binary box. Avro is a binary row format that carries its own schema, so it survives columns being added. ORC and Parquet (next lessons) store data by column for fast analytics.

File formats at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The same data, packed differently

  • A file format is the way rows are written to disk. A text file is what you see in Notepad: values separated by commas, one row per line.
  • Binary formats (SequenceFile, Avro, ORC, Parquet) are not readable in Notepad, but they are smaller, faster to read and can store types and schemas.
  • You choose the format with STORED AS when you create a table. If you say nothing, Hive 4.2.1 uses TEXTFILE (hive.default.fileformat).

Intermediate Row formats vs column formats

  • Row-oriented: TEXTFILE, SEQUENCEFILE, AVRO store one whole row after another. Good for writing records one by one and for exchanging data.
  • Column-oriented: RCFILE, ORC, PARQUET group values of the same column together. Good for analytics that read a few columns of many rows; they compress much better.
  • Self-describing: Avro, ORC and Parquet store the schema in the file. Text does not, so text tables read values by position.
  • Splittable: several tasks can read one big file in parallel. Plain text is splittable; a .gz text file is not; bzip2 text is; SequenceFile, Avro, ORC and Parquet are, because they compress in blocks with sync markers.

Advanced What Hive 4.2.1 did in our lab

  • Defaults: hive.default.fileformat=TextFile and hive.exec.compress.output=false, so a plain CTAS into TEXT, SEQUENCEFILE, RCFILE or AVRO wrote uncompressed files. ORC used ZLIB by default (hive.exec.orc.default.compress).
  • SequenceFile was the largest (4.34 MB, bigger than the 3.74 MB text file): it wraps each text row in a key/value record.
  • Avro wrote the full JSON schema into the file header; Hive turned each column into a nullable union ["null","int"] with default null.
  • ALTER TABLE … SET FILEFORMAT ORC changes only metadata: the existing text file then failed with “Malformed ORC file … Invalid postscript” until the data was rewritten.

Exam tip: Frequently asked: “Name the file formats supported by Hive and compare them.” Give the six, split them into row (Text, SequenceFile, Avro) and columnar (RCFile, ORC, Parquet), and add one strength each: text is human-readable, SequenceFile is a binary key/value container, Avro supports schema evolution, ORC and Parquet compress well and skip data using statistics.

4 Step by step

One dataset, six formats

All outputs are real, from the Hive 4.2.1 lab (database tiffingo).

  1. Step 1 · What do you get without STORED AS?

    SET hive.default.fileformat;
SET hive.exec.compress.output;
SET hive.exec.orc.default.compress;
    | hive.default.fileformat=TextFile | | hive.exec.compress.output=false | | hive.exec.orc.default.compress=ZLIB |
    A table created without STORED AS is a plain text table, with fields separated by the invisible character \001 (Ctrl-A) unless you give ROW FORMAT DELIMITED, and output is not compressed unless you ask. ORC is the exception: it has its own compression setting, ZLIB by default. (Some vendor distributions change these defaults to ORC; always check your cluster.)

  2. Step 2 · Write the same 50,000 orders six ways

    CREATE TABLE f_text    STORED AS TEXTFILE     AS SELECT * FROM orders;
CREATE TABLE f_seq     STORED AS SEQUENCEFILE AS SELECT * FROM orders;
CREATE TABLE f_rc      STORED AS RCFILE       AS SELECT * FROM orders;
CREATE TABLE f_avro    STORED AS AVRO         AS SELECT * FROM orders;
CREATE TABLE f_orc     STORED AS ORC          AS SELECT * FROM orders;
CREATE TABLE f_parquet STORED AS PARQUET      AS SELECT * FROM orders;
-- then: ls -l each table folder, and look at the first bytes of each file
    format (CTAS of 50,000 orders, Hive defaults) file size first bytes TEXTFILE 3,735,865 100001^A1932^A35^AMumbai… (^A = \001 delimiter) SEQUENCEFILE 4,336,792 SEQ…org.apache.hadoop.io.BytesWritable RCFILE 2,019,223 RCF…hive.io.rcfile.column.number AVRO 2,510,687 Obj…avro.schema {"type":"record"… ORC 437,536 ORC… PARQUET 1,093,857 PAR1…
    Same rows, very different files. SequenceFile is the largest: it stores each text row inside a binary key/value record. Avro saves space by storing numbers in binary. The columnar formats win clearly; ORC is 8.5 times smaller than text. Each binary format starts with its own magic bytes, which is how tools recognise a file.

  3. Step 3 · Compress text files, and why .gz hurts parallelism

    SET hive.exec.compress.output=true;
SET mapreduce.output.fileoutputformat.compress.codec=org.apache.hadoop.io.compress.GzipCodec;
CREATE TABLE f_text_gz STORED AS TEXTFILE AS SELECT * FROM orders;
-- repeated with BZip2Codec and SnappyCodec
SELECT COUNT(*), SUM(amount) FROM f_text_gz;
    SET hive.exec.compress.output=true; + codec file size TEXTFILE + GzipCodec 000000_0.gz 724,632 TEXTFILE + BZip2Codec 000000_0.bz2 468,562 TEXTFILE + SnappyCodec 000000_0.snappy 1,242,996 +--------+--------------+ | _c0 | _c1 | +--------+--------------+ | 50000 | 14721180.00 | +--------+--------------+
    Hive reads compressed text transparently, using the file extension to pick the codec. Gzip shrank the file 5×, bzip2 8×. The catch: a .gz (or plain .snappy) text file cannot be split, so one task must read the whole file, however large. bzip2 is splittable but very slow (Lesson 6.3 measures it). That is why big data teams compress inside container formats instead.

  4. Step 4 · SequenceFile: Hadoop’s binary container

    SET hive.exec.compress.output=true;
SET mapreduce.output.fileoutputformat.compress.codec=org.apache.hadoop.io.compress.SnappyCodec;
SET io.seqfile.compression.type=BLOCK;
CREATE TABLE f_seq_snappy STORED AS SEQUENCEFILE AS SELECT * FROM orders;
    f_seq (no compression) 4,336,792 bytes SEQ…org.apache.hadoop.io.BytesWritable… f_seq_snappy (BLOCK snappy) 1,384,953 bytes
    A SequenceFile is a list of binary key/value records with sync markers, so it stays splittable even when compressed. BLOCK compression compresses many records together (much better than RECORD). Hive stores the row in the value and leaves the key empty. It was the classic way to pack many small files into one; for analytics today, prefer ORC or Parquet.

  5. Step 5 · Avro carries its schema

    DESCRIBE f_avro;
-- first bytes of the data file:
$ head -c 400 …/f_avro/000000_0
    +----------------+----------------+----------+ | col_name | data_type | comment | +----------------+----------------+----------+ | order_id | int | | | customer_id | int | | | restaurant_id | int | | | city | string | | | order_ts | timestamp | | | order_date | date | | | amount | decimal(10,2) | | | payment | string | | | status | string | | +----------------+----------------+----------+ Obj..avro.schema..{"type":"record","name":"f_avro","namespace":"tiffingo","fields":[ {"name":"order_id","type":["null","int"],"default":null}, {"name":"customer_id","type":["null","int"],"default":null}, … {"name":"order_ts","type":["null",{"type":"long","logicalType":"timestamp-millis"}],"default":null}, …
    Every Avro file begins with Obj, then its writer schema in JSON. Hive generated it from the table: each column is a union with null (Hive columns are nullable) and has a default. Timestamps became timestamp-millis longs and decimals became bytes with precision and scale.

  6. Step 6 · The partner adds a column: a text table reads by position

    -- part-v1.csv: 1,Aarav Desai,Bengaluru
-- part-v2.csv: 4,Diya Patil,Gold,Pune        (plan added before city)
CREATE EXTERNAL TABLE cust_txt (customer_id INT, name STRING, city STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION 'file:///data/tiffingo/cust_txt';
SELECT * FROM cust_txt ORDER BY customer_id;
    +-----------------------+----------------+----------------+ | cust_txt.customer_id | cust_txt.name | cust_txt.city | +-----------------------+----------------+----------------+ | 1 | Aarav Desai | Bengaluru | | 2 | Ananya Iyer | Mumbai | | 3 | Arjun Nair | Mumbai | | 4 | Diya Patil | Gold | | 5 | Ishaan Khan | Basic | +-----------------------+----------------+----------------+
    No error and no warning. The third value of each line goes into city, so Diya’s plan “Gold” became her city, and the real city “Pune” was silently dropped as an extra field. This is exactly the bug in Kabir’s report.

  7. Step 7 · The same change in Avro: read by name, default for old files

    -- part-v1.avro written with schema {customer_id, name, city}
-- part-v2.avro written with schema {customer_id, name, plan, city}
CREATE EXTERNAL TABLE cust_avro STORED AS AVRO
LOCATION 'file:///data/tiffingo/cust_avro'
TBLPROPERTIES ('avro.schema.literal'='{"type":"record","name":"customer",
  "fields":[{"name":"customer_id","type":"int"},{"name":"name","type":"string"},
  {"name":"plan","type":"string","default":"Basic"},{"name":"city","type":"string"}]}');
SELECT * FROM cust_avro ORDER BY customer_id;
    +------------------------+-----------------+-----------------+-----------------+ | cust_avro.customer_id | cust_avro.name | cust_avro.plan | cust_avro.city | +------------------------+-----------------+-----------------+-----------------+ | 1 | Aarav Desai | Basic | Bengaluru | | 2 | Ananya Iyer | Basic | Mumbai | | 3 | Arjun Nair | Basic | Mumbai | | 4 | Diya Patil | Gold | Pune | | 5 | Ishaan Khan | Basic | Thane | +------------------------+-----------------+-----------------+-----------------+
    Hive gave Avro the table’s schema as the reader schema. For each file, Avro matched fields by name with that file’s writer schema: old v1 records have no plan, so they got the default “Basic”; v2 records kept “Gold” and the correct city. Rule for safe evolution: new fields need a default.

  8. Step 8 · Trap: SET FILEFORMAT does not convert data

    CREATE TABLE ff_trap STORED AS TEXTFILE AS
  SELECT order_id, city, amount FROM orders WHERE order_id < 100004;
ALTER TABLE ff_trap SET FILEFORMAT ORC;
SELECT * FROM ff_trap;

-- fix: rewrite the data in the new format
INSERT OVERWRITE TABLE ff_trap SELECT order_id, city, amount FROM orders WHERE order_id < 100004;
SELECT * FROM ff_trap;
    Error: java.io.IOException: java.lang.RuntimeException: ORC split generation failed with exception: org.apache.orc.FileFormatException: Malformed ORC file file:/opt/hive/data/warehouse/tiffingo.db/ff_trap/000000_0. Invalid postscript. +-------------------+---------------+-----------------+ | ff_trap.order_id | ff_trap.city | ff_trap.amount | +-------------------+---------------+-----------------+ | 100001 | Mumbai | 530.00 | | 100002 | Mumbai | 500.00 | | 100003 | Pune | 410.00 | +-------------------+---------------+-----------------+
    After the ALTER, Hive tried to read the old text file as ORC and could not find an ORC postscript (the small trailer every ORC file ends with, Lesson 6.2). Rewriting the rows produced a real ORC file. In production, convert with CTAS into a new table, compare counts, then swap names.

Behind the screen
  1. Text stores every value as characters, one row per line.
  2. Columnar formats group similar values and compress them well.
  3. Row formats keep each row together; columnar formats keep each column together.
  4. Delimited text has no schema, so fields are matched by position.
  5. Avro compares the file’s writer schema with the table’s reader schema, field by field.

6 Real-world use

Row formats at work

1. Landing files from other systems

Banks, telecoms and government portals often exchange CSV or fixed-width text. Teams land them in external TEXTFILE tables before converting.

Partner file→TEXTFILE table→Convert to ORC

2. Streaming and Kafka pipelines

Avro is the common message format with a schema registry; connectors write Avro files to the lake, and Hive tables read them with the same schemas.

Kafka topic→Avro files→Hive table

3. Data contracts between teams

An Avro schema file is a written agreement: producers may only make compatible changes, so consumers never break silently.

Producer→schema rules→Safe consumers

4. Legacy Hadoop jobs

Older MapReduce pipelines still produce SequenceFiles, for example packing millions of small images or logs into a few large files.

Small files→SequenceFile→Fewer, bigger files

5. Warehouse modernisation

Teams moving old clusters to new ones convert RCFile and text tables into ORC or Parquet with CTAS, often cutting storage by several times.

Old tables→CTAS→ORC / Parquet

Examples are simplified.

Run the code: position vs name

These programs show how formats store and find values: by position in text, by name in Avro, and how compression changes size. Press Run, then try the challenges.

# Why a text table breaks when a column is inserted: it reads by POSITION
table_columns = ["customer_id", "name", "city"]
lines = ["1,Aarav Desai,Bengaluru",          # v1 file
         "4,Diya Patil,Gold,Pune"]           # v2 file: plan added before city

for line in lines:
    values = line.split(",")
    row = {col: values[i] for i, col in enumerate(table_columns)}   # by position
    print(row)

# Avro-style: each record carries field NAMES, missing fields get the default
records = [{"customer_id": 1, "name": "Aarav Desai", "city": "Bengaluru"},
           {"customer_id": 4, "name": "Diya Patil", "plan": "Gold", "city": "Pune"}]
for r in records:
    print({c: r.get(c, "Basic" if c == "plan" else None) for c in ["customer_id", "name", "plan", "city"]})

$ ls -l …/f_avro_deflate
f_avro 2,510,687 bytes (codec: null) f_avro_deflate 772,457 bytes (codec: deflate, read back from the file header)

Avro compresses blocks of records inside the file, so it stays splittable. Deflate cut the file to less than a third. Avro also supports Snappy and other codecs.

3 · Compressed text is read transparently

SELECT COUNT(*), SUM(amount) FROM f_text_gz;
+--------+--------------+ | _c0 | _c1 | +--------+--------------+ | 50000 | 14721180.00 | +--------+--------------+

Hive picked the gzip codec from the .gz extension. The totals match the original orders table: 50,000 rows and ₹1,47,21,180.

9 Quiz and revision

Check yourself

Quick revision

Lesson 6.1 in one screen

  • STORED AS TEXTFILE · SEQUENCEFILE · RCFILE · AVRO · ORC · PARQUET (· JSONFILE). Default in 4.2.1: TEXTFILE, delimiter \001.
  • Row: Text, SequenceFile, Avro · Column: RCFile, ORC, Parquet.
  • Real sizes (50,000 orders): Seq 4.34 MB · Text 3.74 · Avro 2.51 · RC 2.02 · Parquet 1.09 · ORC 0.44.
  • Output not compressed by default (hive.exec.compress.output=false); ORC uses ZLIB by default.
  • Splittable: text yes, .gz/.snappy text no, bzip2 yes (slow); SequenceFile, Avro, ORC, Parquet yes (block compression + sync markers).
  • Magic bytes: SEQ · RCF · Obj · ORC · PAR1.
  • Avro: schema in the file; table schema via avro.schema.literal / avro.schema.url; fields matched by name; new fields need a default.
  • Text: no schema → matched by position → silent shifts when columns change.
  • SET FILEFORMAT changes metadata only → rewrite data with CTAS / INSERT OVERWRITE.

Interview and viva questions

Which format should I use for a new Hive table?

For analytics tables, ORC (the most optimised format in Hive, required for Hive ACID tables) or Parquet (when Spark, Trino or Impala also read the table). Use text only for raw landing data, and Avro for data exchanged between systems or streams where the schema changes over time.

Is RCFile still used?

Rarely for new work. RCFile was the first columnar format in Hive; ORC was designed as its successor with better compression, statistics and indexes. You will still find RCFile tables in older warehouses, and converting them to ORC with CTAS usually reduces storage.

Can Hive read JSON files?

Yes: STORED AS JSONFILE or the JsonSerDe (Lessons 2.4 and 4.3). JSON is self-describing like Avro but text-based, larger and slower to parse, and every record repeats the field names.

Does Avro schema evolution work for Parquet and ORC too?

Partly. ORC and Parquet tables in Hive support adding columns at the end with ALTER TABLE … ADD COLUMNS, and old files return NULL for the new column. Renames and reordering are handled differently by each format and engine, so test them. Iceberg tables (Module 7) track columns by id and handle evolution most safely.

Why did SequenceFile come out larger than text?

Hive writes each row as a record with a length header and an empty key, plus sync markers, and in our lab nothing was compressed. With BLOCK compression it dropped to 1.38 MB. SequenceFile’s advantage was never size; it was a simple, splittable binary container for MapReduce.

Any company · HiveFresher

“Which file formats does Hive support?”

List them and compare them briefly.

Values in the wrong columns

Show a strong answer

PlatformMid-level

One job runs on a single task

A daily 20 GB CSV.gz file takes hours to process; the job has just one map task.

The interviewer is checking: do you understand splittability?

Show a strong answer
  • gzip files cannot be split, so one task reads all 20 GB.
  • Ask the producer for several smaller files, or a splittable container (Avro/Parquet), or convert once with a single job and process the ORC copy.
  • bzip2 is splittable but slow; prefer container formats.

Avoid: “Increase the number of mappers”, which cannot split a gzip stream.

ArchitectureSenior

Choosing formats for a new lake

Design the formats for a new data lake that receives partner CSVs, Kafka events and serves BI and data science.

The interviewer is checking: can you assign formats by purpose?

Show a strong answer
  • Raw zone: keep files as received (CSV/JSON/Avro), short retention.
  • Events: Avro with a schema registry; compatible-change rules.
  • Curated: ORC (Hive ACID needs) or Parquet (multi-engine), compressed with Snappy or ZSTD, partitioned by date (Module 5); consider Iceberg for evolution and updates (Module 7).

Avoid: One format for everything.
