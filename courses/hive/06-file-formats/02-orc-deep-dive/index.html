2 Definition

ORC (Optimized Row Columnar)

Formal definition (write this in exams)

ORC is a self-describing, typed, columnar file format for Hadoop workloads. An ORC file consists of stripes of rows, each containing an index section (row-group statistics and stream positions, optionally bloom filters), the column data streams and a stripe footer, followed by a file footer (schema, stripe locations, column statistics) and a postscript (compression parameters and footer length). Light-weight encodings (run-length, dictionary) and a general-purpose codec (ZLIB, Snappy, LZ4, ZSTD) reduce size. Column statistics at file, stripe and row-group level, plus optional bloom filters, allow predicate pushdown: skipping data that cannot match a query’s filter.

In simple words

ORC stores a table column by column, compresses each column, and writes a summary (min, max, count, sum) for every 10,000 rows. When your WHERE clause cannot match a summary, Hive skips those rows entirely.

Words you’ll meet in this lesson

StripeA big block of rows (default target 64 MB) with its own index and data.
Row groupEvery 10,000 rows of a stripe; the unit of skipping.
PostscriptThe last bytes of the file: how to read the footer. Ends with “ORC”.
Column statisticscount, hasNull, min, max, sum per column, per file / stripe / row group.
RLE v2Run-length encoding for integers: sorted ids shrink to a few bytes.
Dictionary encodingStore each distinct string once and refer to it by number.
Predicate pushdown (PPD)Passing WHERE conditions to the reader so it skips data.
Bloom filterA compact bit set that says “definitely not here” or “maybe here”.

ORC at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A book with a contents page and an index

  • An ORC file stores each column separately and compresses it, so reading two columns does not touch the other seven.
  • It also writes a “contents page”: for each column, the smallest and largest value, the count and the sum, for the whole file and for every block of 10,000 rows.
  • When you ask for amount > 900 and the contents page says the maximum is 880, Hive skips the whole file without reading a single row.

Intermediate The structure of an ORC file

  • Stripes: large horizontal slices of rows (default target 64 MB). Each stripe has an index section, a data section (one or more streams per column) and a stripe footer.
  • Row groups: every 10,000 rows (orc.row.index.stride) the row index records min/max/count/sum per column and positions to jump to.
  • File footer (schema, stripe list, file statistics) and postscript (compression, footer length, ends with “ORC”) sit at the end, so a reader starts from the last bytes.
  • Encodings: integers use run-length encoding v2 (sorted ids compress to almost nothing); low-cardinality strings use a dictionary.
  • Predicate pushdown: with hive.optimize.index.filter=true (default) Hive passes WHERE conditions to the ORC reader, which skips files, stripes and row groups.

Advanced What helps skipping, measured in our lab

  • Statistics only help when values are clustered. Unsorted customer_id: every row group has min 1 max 2000 → 50,000 rows read. Sorted: 10,000.
  • Bloom filters (orc.bloom.filter.columns) answer “is this value possibly here?” per row group. With 1,000-row groups they cut a lookup from 50,000 to 30,000 rows, and grew the index from 890 bytes to 65,439 bytes.
  • A smaller orc.row.index.stride alone did nothing for an unsorted column.
  • amount > 900 was eliminated before any task ran (0 splits): split generation read the file statistics.
  • ORC is also the format for Hive ACID tables (Module 7) and enables vectorised reading in batches of rows.

Exam tip: “Explain the ORC file structure” is a classic. Draw stripes (index data, row data, stripe footer), then the file footer and postscript. Mention the three levels of statistics (file, stripe, row group of 10,000 rows), lightweight encodings plus compression, predicate pushdown and bloom filters, and that ORC is required for Hive ACID tables.

    Exactly as the index predicted: 3 of 5 row groups read (30,000 rows) for 4 matching orders. For amount > 900 the file maximum is 880, so Hive created no splits at all. With pushdown off, both queries read all 50,000 rows and return the same answers, only slower.

  6. Step 6 · The customer lookup: unsorted vs sorted

    CREATE TABLE orders_sorted STORED AS ORC AS
  SELECT * FROM orders ORDER BY customer_id;

SELECT COUNT(*) AS n FROM f_orc         WHERE customer_id = 1492;
SELECT COUNT(*) AS n FROM orders_sorted WHERE customer_id = 1492;
    SELECT COUNT(*) AS n FROM f_orc WHERE customer_id = 1492; result 41 · RECORDS_IN 50000 SELECT COUNT(*) AS n FROM orders_sorted WHERE customer_id = 1492; result 41 · RECORDS_IN 10000
    Same 41 orders. Sorted, each row group covers a narrow range of customers (real min–max: 1–404, 404–800, 800–1205, 1205–1604, 1604–2000), so only the group whose min–max includes 1492 is read. Sorting is free at query time but costs a sort when writing, and you can sort by only one order, so pick the column your filters use most.

  TBLPROPERTIES ('orc.bloom.filter.columns'='customer_id',
                 'orc.row.index.stride'='1000') AS SELECT * FROM orders;

SELECT COUNT(*) AS n FROM orders_stride WHERE customer_id = 1492;
SELECT COUNT(*) AS n FROM orders_bloom  WHERE customer_id = 1492;

5 See it happen

How the ORC reader decides what to read

Left: real orcfiledump and Beeline output. Right: what the ORC reader does.

Footer, stripes, statistics and skipping 5 steps
What you see
  1. orcfiledump shows the writer, compression, row count and stripes.
  2. Sorted ids take 161 bytes; small text columns use dictionaries.
  3. Pushdown read 30,000 rows for amount > 870 and nothing for amount > 900.
  4. Sorting by customer cut a lookup from 50,000 rows to 10,000.
  5. A bloom filter cut the unsorted lookup to 30,000 rows.
Behind the screen
  1. A reader starts at the postscript, reads the footer, then jumps to the stripes it needs.
  2. Each stripe has index, data and footer; each column is a separate compressed stream.
  3. The reader compares the filter with each row group’s min and max and skips impossible groups.
  4. When data is sorted, each group covers a narrow range, so most groups are ruled out.
  5. Each group’s bloom filter can prove a value is absent; groups that might contain it are read.

  2. Write it sorted with DISTRIBUTE BY and SORT BY.

Animated example

  2. Add a bloom filter on that column.
  3. In our lab: 30,000 rows read instead of 50,000.
  4. Bloom filters shine when a value appears in only a few groups.

6 Real-world use

ORC at work

1. The default for Hive warehouses

Large Hive warehouses store curated tables in ORC with ZLIB or ZSTD; many vendor distributions make ORC the default for managed tables.

Curated data→STORED AS ORC→Fast scans

2. Transactional tables

Hive’s UPDATE, DELETE and MERGE work on ORC tables: base and delta files are ORC, and compaction rewrites them (Module 7).

Changes→ORC deltas→Compaction

3. Point lookups on big tables

Telecom and payments teams add bloom filters on phone numbers, card ids or transaction ids so investigation queries skip most of the data.

Id lookup→bloom filter→Few row groups

4. Layout tuned for queries

Teams write partitions sorted by the main filter column (customer, device, store) so ORC statistics skip most row groups.

Nightly load→sorted write→Selective stats

5. Shared with other engines

Spark, Trino and Presto read ORC natively and use the same statistics and bloom filters, so a well-written ORC table speeds up every engine.

ORC files→same statistics→Any engine

# How ORC row-group statistics let a reader skip data
groups = [  # (min, max) of amount per 10,000-row group: real values from orcfiledump
    (40, 840), (40, 880), (40, 840), (40, 880), (40, 880)]

def can_match(lo, hi, threshold):          # WHERE amount > threshold
    return hi > threshold

for threshold in [870, 900]:
    read = [i for i, (lo, hi) in enumerate(groups) if can_match(lo, hi, threshold)]
    print(f"amount > {threshold}: read groups {read} -> {len(read) * 10000} rows")
amount > 870: read groups [1, 3, 4] -> 30000 rows amount > 900: read groups [] -> 0 rows

  • read = [i for i, (lo, hi) in enumerate(groups) if can_match(lo, hi, threshold)]Groups that cannot match are skipped without being decompressed.

Check yourself

Quick revision

Lesson 6.2 in one screen

  • Layout: stripes (index · data streams · stripe footer) → file footer (schema, stripes, stats) → postscript (ends with “ORC”).
  • Statistics at 3 levels: file, stripe, row group (10,000 rows, orc.row.index.stride).
  • Encodings: RLE v2 for numbers (sorted ids → 161 bytes), dictionary for low-cardinality strings; then ZLIB (default) / Snappy / LZ4 / ZSTD.
  • Inspect: hive --orcfiledump [--rowindex cols] file.
  • PPD (hive.optimize.index.filter=true): amount > 870 → 30,000 rows; amount > 900 → 0 splits; off → 50,000.
  • Clustering matters: unsorted lookup 50,000 rows; sorted 10,000.
  • Bloom filters (orc.bloom.filter.columns, fpp 0.05): lookup 30,000; index 890 → 65,439 bytes. For = / IN only.
  • Keep stripes large (64 MB default); tiny stripes made the file 7% bigger.
  • ORC → vectorised reading (batches of 1,024 rows) and Hive ACID tables.

Interview and viva questions

Does Hive read the whole ORC file to find the statistics?

No. It reads the last bytes (postscript and footer), which contain the file and stripe statistics and the stripe locations. Row-group indexes sit at the start of each stripe and are read only for stripes that might match.

Which filters can be pushed down into ORC?

Comparisons of a column with constants: =, <, >, <=, >=, BETWEEN, IN, IS NULL, and AND/OR/NOT combinations of these. Filters with functions on the column (upper(city) = 'PUNE') or comparisons between two columns cannot use the statistics; Hive still applies them, after reading.

Should I sort every ORC table?

Sort tables that are read with selective filters on one main column (customer, device, store), and only by that column. Sorting costs a shuffle at write time, and a second sort order is impossible in the same file. Tables read only by date partition and full aggregates do not need it.

How is ORC different from Parquet?

Both are columnar with statistics and compression. ORC has row-group indexes every 10,000 rows, built-in bloom filters and is the format for Hive ACID; Parquet is the most common format in Spark and cloud tools and organises data in row groups and pages. Lesson 6.3 compares them on the same data.

What is the “ORC split strategy”?

How Hive plans tasks for ORC files: ETL reads file footers while planning (enables skipping whole files and stripes, good for few large files), BI does not (faster planning for many small files), HYBRID chooses between them based on file count and size. Our 0-split result shows footers being used at planning time.

Real-world scenario questions (asked in company interviews)

ORC internals come up in senior Hive and data engineering interviews, usually as “why is this slow” or “explain the structure”.

Any company · HiveFresher

“Why is ORC faster than text?”

Explain why queries on ORC tables are faster than on text tables.

The interviewer is checking: do you know columnar storage, compression and statistics?

Show a strong answer

ORC stores columns separately, so a query reads only the columns it needs; values are typed and encoded (RLE, dictionary) and compressed, so far fewer bytes are read (0.44 MB vs 3.74 MB for our orders); and statistics at file, stripe and 10,000-row level let Hive skip data that cannot match the WHERE clause. It also supports vectorised reading.

Avoid: Saying only “ORC is compressed”.

AnalyticsMid-level

ORC lookup still slow

Point lookups by customer on an ORC table read the whole table.

The interviewer is checking: do you understand that statistics need clustered data?

Show a strong answer
  1. Check counters (RECORDS_IN) and orcfiledump --rowindex: every group spans the full id range.
  2. Rewrite partitions sorted by customer_id (DISTRIBUTE BY + SORT BY), or add a bloom filter if the data must stay in time order.
  3. Measure again: our lab went from 50,000 to 10,000 (sorted) or 30,000 (bloom) rows.

Avoid: “ORC already has indexes, so it must be the network.”

Data engineeringMid-level

A filter that does not push down

A query with WHERE upper(city) = 'PUNE' reads everything, while city = 'Pune' skips groups.

The interviewer is checking: do you know which predicates can use statistics?

Show a strong answer
  • Functions on the column hide it from the ORC reader; it can compare only column vs constant.
  • Clean the data at load time (store normalised values) and filter on the raw column.
  • Verify with counters before and after.

Avoid: Adding more bloom filters, which have the same limitation.

PlatformSenior

Designing an ORC table for mixed workloads

A 2-billion-row events table is queried by date ranges, by device id lookups and by full daily aggregates.

The interviewer is checking: can you combine partitioning, sorting, bloom filters and codec choice?

Show a strong answer
  • Partition by event date (Module 5); sort within each partition by device_id if lookups dominate, else keep time order and add a bloom filter on device_id.
  • Keep 64 MB stripes and the 10,000 stride; choose ZSTD or ZLIB for size, Snappy/LZ4 for speed (6.3).
  • Validate with orcfiledump and counters on one partition before rewriting everything.

Avoid: Bloom filters on every column “to be safe”.
