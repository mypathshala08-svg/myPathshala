2 Definition

An idempotent, incremental Hive ETL pipeline

Formal definition (write this in exams)

An ETL pipeline extracts data from sources, transforms it (typing, validation, de-duplication, conforming, modelling) and loads it into target tables. An incremental pipeline processes only one load (here one load_date) per run, and an idempotent pipeline produces the same final state whether a run executes once or several times. In Hive this is achieved by writing recomputable data with INSERT OVERWRITE of the affected partitions and changing data with key-based MERGE on transactional tables, guarded by conditions such as “only newer versions”, and verified by reconciliation: matching counts and totals between layers.

In simple words

Each night the script handles only that night’s files, puts everything in the right place, and can be run again safely. Then we prove the numbers match from raw to gold.

Words you’ll meet in this lesson

IdempotentRunning twice gives the same result as running once.
UpsertUpdate the row if the key exists, insert it if not: MERGE.
QuarantineA table of rejected rows with the reason.
BackfillRunning the pipeline for past dates, here 31 loads.
ReconciliationChecking that counts and sums agree between layers.
Point-in-time joinJoin to the dimension version valid at the event time.
hivevarA variable passed to a script: --hivevar load_date=2026-10-05.
Touched datesEvent dates that received rows in this load.

Building the warehouse at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A kitchen that runs every night

  • Each night new ingredients arrive (files). The script washes them (types and checks), throws spoiled ones into a labelled bin (quarantine), updates the stock list (MERGE) and plates the dishes (gold).
  • If the cook repeats a step by mistake, the dishes must not double: that is idempotence.

Intermediate The Hive tools used, all from earlier modules

  • INSERT OVERWRITE … PARTITION for anything that can be recomputed per load (staging, quarantine, deliveries, gold).
  • MERGE on ACID tables for rows that change over time: fact_orders (upsert) and dim_customer (SCD type 2).
  • Window functions to pick the newest version, --hivevar to pass the load date, STACK for the audit rows, EXPLAIN DEPENDENCY to prove pruning.

Advanced What makes it production-grade

  • Every step is idempotent and proven so by re-running 15 and 3 October: every count and sum unchanged.
  • Three-way reconciliation: raw valid orders = fact rows (47,553), fact net revenue = gold net revenue (₹1,53,95,190), rejects = 112.
  • Late data handled by rebuilding exactly the order dates a load touched.

Exam tip: “How do you make a Hive load re-runnable?” Overwrite partitions instead of appending; use MERGE with a business key for changing rows; ignore versions that are not newer; never use plain INSERT INTO on a fact table unless a re-run deletes the previous output first.

INSERT INTO on a fact table is the most common cause of doubled numbers after a re-run. If you must append, record the load in an audit table and make the job refuse to run twice for the same date.

Building, loading and testing the warehouse

  4. Step 4 · Type, validate and quarantine

    -- 2. type, validate and tag every raw row of this load
INSERT OVERWRITE TABLE stg_orders
SELECT CAST(o.order_id AS BIGINT), CAST(o.customer_id AS INT), CAST(o.restaurant_id AS INT),
       CAST(o.order_ts AS TIMESTAMP), CAST(o.amount AS DECIMAL(10,2)), o.payment, o.status,
       CAST(o.updated_at AS TIMESTAMP), TO_DATE(CAST(o.order_ts AS TIMESTAMP)),
       CONCAT_WS(',', o.order_id, o.customer_id, o.restaurant_id, o.order_ts, o.amount, o.payment, o.status, o.updated_at),
       CASE WHEN CAST(o.order_id AS BIGINT) IS NULL              THEN 'bad order_id'
            WHEN CAST(o.customer_id AS INT) IS NULL              THEN 'missing customer'
            WHEN CAST(o.order_ts AS TIMESTAMP) IS NULL           THEN 'bad order_ts'
            WHEN CAST(o.amount AS DECIMAL(10,2)) IS NULL         THEN 'bad amount'
            WHEN CAST(o.amount AS DECIMAL(10,2)) <= 0            THEN 'non-positive amount'
            WHEN r.restaurant_id IS NULL                         THEN 'unknown restaurant'
            WHEN o.status NOT IN ('DELIVERED', 'CANCELLED', 'REFUNDED') THEN 'bad status'
       END
FROM raw_orders o
LEFT JOIN dim_restaurant r ON CAST(o.restaurant_id AS INT) = r.restaurant_id
WHERE o.load_date = '${hivevar:load_date}';

  5. Step 5 · Upsert orders with MERGE

    -- 4. upsert orders: newest version per order wins; resends and duplicates change nothing
MERGE INTO fact_orders t
USING (SELECT * FROM (SELECT s.*, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) AS rn
                      FROM stg_orders s WHERE reject_reason IS NULL) x WHERE rn = 1) s
ON t.order_id = s.order_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN
  UPDATE SET status = s.status, amount = s.amount, updated_at = s.updated_at, load_date = DATE '${hivevar:load_date}'
WHEN NOT MATCHED THEN
  INSERT VALUES (s.order_id, s.customer_id, s.restaurant_id, s.order_ts, s.amount, s.payment, s.status,
                 s.updated_at, DATE '${hivevar:load_date}', s.order_date);

SELECT COUNT(*) AS orders, COUNT(DISTINCT order_id) AS distinct_ids, SUM(IF(status='DELIVERED',1,0)) AS delivered,
       SUM(IF(status='CANCELLED',1,0)) AS cancelled, SUM(IF(status='REFUNDED',1,0)) AS refunded FROM fact_orders;
-- reconcile with raw: distinct order ids that pass every rule
SELECT COUNT(DISTINCT order_id) AS valid_raw_orders FROM raw_orders o JOIN raw_restaurants r
  ON CAST(o.restaurant_id AS INT) = r.restaurant_id
WHERE CAST(o.amount AS DECIMAL(10,2)) > 0 AND CAST(o.order_ts AS TIMESTAMP) IS NOT NULL
  AND CAST(o.customer_id AS INT) IS NOT NULL;
SELECT order_id, order_date, status, updated_at, load_date FROM fact_orders WHERE order_id IN (5006782, 5007134);

    ROW_NUMBER() keeps one row per order inside a load (a file contains duplicates, and Hive’s MERGE fails if two source rows match one target row). s.updated_at > t.updated_at makes re-sent rows harmless.   6. Step 6 · Customers as SCD type 2

    -- 5. customers: SCD type 2 (close the old version, insert the new one)
MERGE INTO dim_customer t
USING (
  SELECT c.customer_id AS join_key, c.* FROM
    (SELECT * FROM (SELECT CAST(customer_id AS INT) AS customer_id, name, city, plan, CAST(updated_at AS TIMESTAMP) AS updated_at,
                           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) AS rn
                    FROM raw_customers WHERE load_date = '${hivevar:load_date}') z WHERE rn = 1) c
  UNION ALL
  SELECT NULL AS join_key, c.* FROM
    (SELECT * FROM (SELECT CAST(customer_id AS INT) AS customer_id, name, city, plan, CAST(updated_at AS TIMESTAMP) AS updated_at,
                           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) AS rn
                    FROM raw_customers WHERE load_date = '${hivevar:load_date}') z WHERE rn = 1) c
  JOIN dim_customer d ON d.customer_id = c.customer_id AND d.is_current
  WHERE c.updated_at > d.valid_from                     -- only changes newer than what we hold
    AND (d.city <> c.city OR d.plan <> c.plan OR d.name <> c.name)
) s
ON t.customer_id = s.join_key
WHEN MATCHED AND t.is_current AND s.updated_at > t.valid_from
               AND (t.city <> s.city OR t.plan <> s.plan OR t.name <> s.name) THEN
  UPDATE SET valid_to = s.updated_at, is_current = false
WHEN NOT MATCHED THEN
  INSERT VALUES (s.customer_id, s.name, s.city, s.plan, s.updated_at, TIMESTAMP '9999-12-31 00:00:00', true);

SELECT customer_id, city, plan, valid_from, valid_to, is_current FROM dim_customer
WHERE customer_id IN (1033, 1380) ORDER BY customer_id, valid_from;

  9. Step 9 · Gold: rebuild only the dates a load touched

    -- 7. gold: rebuild only the order dates this load touched (late rows and refunds touch old dates)
INSERT OVERWRITE TABLE gold_city_daily PARTITION (order_date)
SELECT r.city, COUNT(*),
       SUM(IF(f.status = 'DELIVERED', 1, 0)), SUM(IF(f.status = 'CANCELLED', 1, 0)), SUM(IF(f.status = 'REFUNDED', 1, 0)),
       SUM(IF(f.status <> 'CANCELLED', f.amount, 0)),
       SUM(IF(f.status = 'DELIVERED', f.amount, 0)),
       ROUND(100 * AVG(IF(f.payment = 'UPI', 1, 0)), 2),
       ROUND(AVG((UNIX_TIMESTAMP(d.delivered_ts) - UNIX_TIMESTAMP(f.order_ts)) / 60), 1),
       ROUND(PERCENTILE_APPROX((UNIX_TIMESTAMP(d.delivered_ts) - UNIX_TIMESTAMP(f.order_ts)) / 60, 0.9), 1),
       f.order_date
FROM fact_orders f
JOIN dim_restaurant r ON r.restaurant_id = f.restaurant_id
LEFT JOIN fact_deliveries d ON d.order_id = f.order_id
WHERE f.order_date IN (SELECT DISTINCT order_date FROM stg_orders WHERE reject_reason IS NULL)
GROUP BY r.city, f.order_date;

SELECT step, row_count FROM etl_audit WHERE load_date = DATE '2026-10-10' ORDER BY step;
SELECT g.total AS gold_net, f.total AS fact_net, g.total - f.total AS diff

# The nightly logic of fact_orders, in Python: MERGE with "newer wins"
fact = {}                      # order_id -> (status, updated_at, order_date)
loads = {
    "10-05": [("5006782", "DELIVERED", "10-05 22:59", "10-05"),
              ("5006782", "DELIVERED", "10-05 22:59", "10-05")],   # duplicate line
    "10-06": [("5006782", "DELIVERED", "10-05 22:59", "10-05")],   # re-sent
    "10-09": [("5006782", "REFUNDED",  "10-09 14:47", "10-05")],   # status change
}
for load, rows in loads.items():
    newest = {}
    for oid, st, upd, od in rows:                 # ROW_NUMBER() ... rn = 1
        if oid not in newest or upd > newest[oid][1]:
            newest[oid] = (st, upd, od)
    for oid, (st, upd, od) in newest.items():     # MERGE
        if oid not in fact or upd > fact[oid][1]:
            fact[oid] = (st, upd, od)
    print(load, fact)

Interview and viva questions

Why not one big INSERT OVERWRITE of the whole fact table every night?

It works for small tables and is perfectly idempotent. But the cost grows with history, not with the day’s changes, and you lose the ability to update rows in place. MERGE on an ACID table touches only changed rows; at TiffinGo’s real scale that is the difference between minutes and hours.

Why does the MERGE not filter the target by order_date?

Late rows and refunds can belong to any earlier date, so the target cannot be pruned without knowing a limit. At large scale you add one, for example AND t.order_date >= DATE_SUB(load_date, 30), and send older corrections through a separate repair job.

Could Spark do this instead of Hive?

Yes. The design (layers, keys, idempotent steps, SCD 2, touched dates) is engine-independent. Spark with Iceberg or Delta tables is a common choice today; Hive ACID tables are reliably read only by Hive (Lesson 11.1), which matters if Trino must read the fact.

Why keep load_date inside fact_orders?

It tells you which load last changed each order. When a number changes, you can see which night’s file caused it, and a faulty load can be found and repaired.

What about deletes in the source?

Our source never deletes orders; it changes their status. If a source sends deletes (an op column with D), add a WHEN MATCHED AND s.op = 'D' THEN DELETE branch to the MERGE, or mark the row as deleted to keep history.

  3. Fix: only apply changes newer than the current valid_from; rebuild the dimension by replaying loads in order.

Avoid: Deleting the bad rows by hand without fixing the MERGE.

Late data and dashboards

Dashboards for yesterday change during the next three days. Users complain.

The interviewer is checking: do you understand late data trade-offs?

Show a strong answer
  • Explain why: late orders, refunds and delivery events are applied to their event date (5 dates touched by one load in our lab).
  • Offer a “day closed after N days” flag in gold, and show both provisional and final numbers.
  • Keep correctness: never freeze numbers by ignoring late rows.

Avoid: Loading late rows into today’s date to keep yesterday stable.
