NoSQL databases: key-value, document, wide-column and graph

One food-delivery app can use five databases: PostgreSQL for money, Redis for carts, MongoDB for menus, Cassandra for rider GPS and Neo4j for referrals. In this lesson you meet the four NoSQL families, compare them with SQL, watch a cache save a flash sale, design a Cassandra table around its query, and catch a cashback fraud ring with a graph.

1 The story

Five databases for one app?

Kabir draws TiffinGo’s architecture from their tech blog for his notes. He expects one database. He finds five: PostgreSQL, Redis, MongoDB, Cassandra and Neo4j. In college they learned only MySQL and normalisation.

Kabir

Sir, why five databases? Couldn’t they keep everything in one MySQL database with good indexes?

Arjun Sir

For a small app, yes. But imagine two lakh carts updating every second during a sale, menus whose fields differ for every kitchen, and every rider sending a location every five seconds. A single relational database would struggle with some of these jobs, or cost a fortune.

Riya

So the others are “NoSQL” databases? Does that mean they don’t use SQL at all?

Arjun Sir

“NoSQL” today means not only SQL. They drop some relational features, like fixed schemas or joins, to gain others: massive scale, flexible documents, millisecond look-ups, or easy relationship queries. There are four big families: key-value, document, wide-column and graph.

Kabir

And the orders stay in PostgreSQL?

Arjun Sir

Exactly. Money needs strict transactions, which relational databases do best. Choosing the right store for each job is called polyglot persistence. Today you’ll see a cache save a flash sale, design a Cassandra table around its queries, and catch a fraud ring with a graph.

2 Definition

What is a NoSQL database?

Formal definition (write this in exams)

A NoSQL (“not only SQL”) database is a non-relational database that stores data in models other than fixed relational tables, typically to achieve horizontal scalability, flexible schemas and high performance for specific access patterns. The four main families are key-value stores, document stores, wide-column stores and graph databases. Many NoSQL systems relax strict ACID guarantees in favour of availability and partition tolerance (BASE), often offering tunable or eventual consistency.

In simple words

NoSQL databases are databases that don’t force every record into the same table shape. Some store simple key → value pairs, some store whole JSON documents, some store huge numbers of rows spread across many machines, and some store connections between things. Each one is very good at one kind of job.

Words you’ll meet in this lesson

Key-value pairA unique key and its value: otp:9876 → 482913.
DocumentA self-contained JSON-like record that can have nested fields and lists.
Partition keyThe part of a key that decides which machine stores the row.
Clustering keyIn wide-column stores, the order of rows inside a partition (for example by time).
Node / edgeIn a graph: a thing (account, phone) and a relationship between two things (USES, REFERS).
DenormalisationCopying data into several places so each read needs no joins.
TTL (time to live)An automatic expiry time on a key or row.
Polyglot persistenceUsing several kinds of databases in one system, each for what it does best.

The four families and well-known examples

Key-valueRedis, Amazon DynamoDB, Memcached, etcd · caches, sessions, carts, rate limits, OTPs
DocumentMongoDB, Couchbase, Google Firestore, Azure Cosmos DB · catalogues, user profiles, content, app data
Wide-columnApache Cassandra, Apache HBase, ScyllaDB, Google Bigtable · time series, IoT, event logs, messaging
GraphNeo4j, Amazon Neptune, TigerGraph · fraud rings, recommendations, social networks, knowledge graphs

NoSQL at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Four kinds of storage cupboards

  • Key-value is a cloakroom: give a token (key), get your item (value) instantly. Example: Redis storing cart:U9 → {thali: 1}.
  • Document is a file folder per customer: each folder holds a whole form with nested sections, and two folders can have different fields. Example: MongoDB storing a kitchen with its whole menu inside.
  • Wide-column is a giant register split into many books by a key: each rider’s book holds his location pages in time order. Example: Cassandra storing GPS pings per rider.
  • Graph is a friendship map: dots (people, phones, accounts) connected by lines (shares, refers, pays). Example: Neo4j finding who is connected to whom.

Simple rule: money and strict rules → relational (SQL). Speed by key → key-value. Flexible records → document. Huge write streams → wide-column. Relationships → graph.

Intermediate Model data around your queries

  • Access patterns first: in NoSQL you list the questions the app will ask (“get a rider’s last 50 positions”) and shape the data to answer each one with a single look-up. Relational design normalises first and joins later.
  • Denormalisation: data is copied where it is read (a kitchen’s name stored inside each order document) to avoid joins, accepting extra storage and harder updates.
  • Embed or reference (documents): embed things read together and bounded in size (a menu inside a kitchen); reference things that grow without limit (all orders of a kitchen).
  • Partition key (wide-column, key-value at scale): decides which machine holds the data. A good key spreads load evenly and keeps one query on one partition.
  • TTL: many NoSQL stores can expire data automatically (carts after 30 minutes, OTPs after 5 minutes).

Advanced ACID vs BASE, tunable consistency and storage engines

  • ACID vs BASE: relational databases promise Atomicity, Consistency, Isolation, Durability. Many NoSQL systems chose BASE (Basically Available, Soft state, Eventually consistent) to stay available and fast across many machines. Modern MongoDB and DynamoDB do support multi-document transactions, at a cost.
  • Tunable consistency: Cassandra lets each query choose how many replicas must answer. With N replicas, if read replicas R plus write replicas W is greater than N, every read sees the latest write (more in Lesson 3.4).
  • Storage engines: B-trees (most relational databases) are good at reads and updates in place; LSM trees (Cassandra, HBase, RocksDB) turn writes into fast sequential appends and merge files in the background, which suits huge write volumes.
  • Hot partitions: one celebrity account or one city can overload a single partition. Fix with better keys or by splitting (bucketing) hot keys.
  • NewSQL: distributed SQL databases (Google Spanner, CockroachDB, YugabyteDB, TiDB) scale out like NoSQL while keeping SQL and ACID transactions.

Exam tip: Answer “types of NoSQL databases” with all four families: data model, example product, typical use, plus one line each on schema flexibility, horizontal scaling and BASE vs ACID. Add a short SQL vs NoSQL comparison table for full marks.

3 Types and ways to use it

Key-value, document, wide-column and graph

Key-value

A giant dictionary. Get or set by key in about a millisecond. Values are opaque blobs; no queries on their contents.

Fastest look-ups

Document

JSON-like documents with nesting and flexible fields. Query and index by fields inside the document.

Flexible records

Wide-column

Rows grouped into partitions by key and sorted inside each partition. Built for huge write volumes across many nodes.

Massive writes

Graph

Nodes and relationships stored directly. Multi-hop questions (“friends of friends”) are fast and natural.

NoSQL is not “better” than SQL. Most companies keep money in a relational database and add NoSQL stores around it. In interviews, always justify a NoSQL choice by the access pattern and scale, not by fashion.

4 Step by step

One order across five databases

  1. Key-value: Riya’s cart in Redis

    import time
cache = {}
def set_key(k, v, ttl):
    cache[k] = (v, time.time() + ttl)
def get_key(k):
    v, exp = cache.get(k, (None, 0))
    return v if time.time() < exp else None
set_key("cart:U9", {"thali": 1, "lassi": 2}, ttl=1800)
set_key("otp:9876", "482913", ttl=-1)          # already expired
print(get_key("cart:U9"), get_key("otp:9876"))
    {'thali': 1, 'lassi': 2} None
    A cart is read and written by one key, many times a minute, and is useless after half an hour. A key-value store with a TTL does exactly this in about a millisecond, and the expired OTP disappears by itself.

  2. Document: each kitchen is one document

    kitchens = [
    {"_id": "K11", "name": "Annapurna", "veg": True, "menu": [{"dish": "thali", "price": 220}]},
    {"_id": "K12", "name": "Spice Box", "veg": False, "menu": [{"dish": "biryani", "price": 280}], "halal": True},
]
veg = [k["name"] for k in kitchens if k["veg"]]
print("veg kitchens:", veg, "| K12 extra field halal:", kitchens[1].get("halal"))
    veg kitchens: ['Annapurna'] | K12 extra field halal: True
    The menu lives inside the kitchen document, so one read fetches the whole page. Kitchens can have extra fields (like halal) without changing a schema for everyone.

  3. Wide-column: rider pings partitioned by rider

    pings = {}   # partition key = rider, rows kept sorted by time
for rider, t, lat in [("R7", 3, 18.52), ("R9", 1, 19.07), ("R7", 1, 18.50), ("R7", 2, 18.51)]:
    pings.setdefault(rider, []).append((t, lat))
    pings[rider].sort()
print("R7 partition:", pings["R7"])
print("latest for R7:", pings["R7"][-1])
    R7 partition: [(1, 18.5), (2, 18.51), (3, 18.52)] latest for R7: (3, 18.52)
    Each rider’s pings live together in one partition, kept sorted by time. “Latest position of R7” reads one partition, even when there are billions of pings in total spread over many nodes.

  4. Graph: who referred whom

    refers = {"Riya": ["Kabir", "Meera"], "Kabir": ["Arjun"], "Meera": [], "Arjun": ["Zoya"]}
level1 = refers["Riya"]
level2 = [p for f in level1 for p in refers[f]]
print("referred by Riya:", level1, "| their referrals:", level2)
    referred by Riya: ['Kabir', 'Meera'] | their referrals: ['Arjun']
    Relationships are stored directly, so “referrals of my referrals” is a short walk. In SQL each extra hop is another self-join on a large table.

  5. Relational: the payment itself

    When Riya pays ₹420, the order row, the payment row and the wallet balance change together inside one PostgreSQL transaction: all or nothing.

    This is where ACID matters most. If the payment fails half-way, nothing is saved. That is why money stays in a relational database.

  6. Polyglot persistence

    One order touched five databases, each doing what it does best. Events from all of them also flow into the data lake for analytics.

    The cost: more systems to run, monitor and keep in sync. Teams add a new database only when an access pattern truly needs it.

What Riya sees, and which database answers 6 steps
What you see
  1. Riya opens the app and is greeted by name; it already knows her area.
  2. She opens Annapurna Kitchen and sees its full menu and rating.
  3. She adds a thali and two lassis; the cart updates instantly with every tap.

Behind the screen

  2. The kitchen page is one MongoDB document containing name, rating and the nested menu.
  3. The cart is a Redis key updated on every tap, with a 30-minute expiry (TTL).
  4. The payment and order are written in one PostgreSQL ACID transaction: either both are saved or neither is.
  5. The rider’s phone writes a location every five seconds into Cassandra, partitioned by rider and sorted by time.
  6. A two-hop graph query finds dishes her friends ordered. (Timings are typical, not exact.)
6 Real-world use

Real-time scenarios: NoSQL under pressure

Three live scenarios: a key-value cache that saves a flash sale, a Cassandra table designed around its query, and an advanced graph search that exposes a fraud ring.

Real-time scenario 1

Flash sale: a key-value cache saves the database

At midnight a sale starts and everyone opens the same few kitchen pages. Watch the cache-aside pattern take the load off the database.

Cache-aside with Redis 5 steps
Animated example
  1. Two lakh page views a second all ask the database for the same popular menus. Its CPU saturates and pages slow to three seconds.
  2. Cache-aside: the app first asks Redis. On a miss it reads the database and saves the result in Redis with a short expiry (TTL).
  3. For the next minute, every request for that menu is a hit, served from memory in about a millisecond.
  4. With a 99% hit ratio, only 2,000 of the 2 lakh reads per second reach the database.
  5. When data changes, the app deletes (invalidates) the cached key; the short TTL also limits how stale data can get. (Numbers are illustrative.)
Real-time scenario 2

Designing a Cassandra table around its query

TiffinGo stores every rider’s GPS ping, crores per day. Support agents need “the last 50 positions of rider R77”. Watch a natural-looking table fail, and a query-first design succeed.

Partition key design 5 steps
Animated example
  1. The first design partitions rider pings by city, with time as the clustering key.
  2. Partitions are badly unbalanced: Mumbai’s is several times bigger than the others and grows without limit, so one node is overloaded. This is a hot partition.
  3. Worse, the support query must scan the whole Mumbai partition and filter for one rider, reading millions of rows to return fifty.
  4. The better key is (rider_id, day): many small, similar-sized partitions spread evenly, each with rows sorted newest first.
  5. The query becomes a single-partition read of the first 50 rows: milliseconds at any scale. In NoSQL you design the table for the query, not the other way round. (Sizes are illustrative.)
Real-time scenario 3 · advanced

Catching a cashback fraud ring with a graph

A promotion gives ₹500 to every new user. Fraudsters create many accounts. Each account looks innocent alone; the fraud only shows up in the connections between them.

Graph traversal 5 steps
Animated example
  1. Accounts are nodes, and so are the phones, UPI ids and devices they use. An edge means “this account used this phone”.
  2. Account A1 claims the new-user cashback. Alone, it looks normal.
  3. Following edges: A1 shares a phone number with A2.
  4. Continuing: A2 shares a UPI id with A3, and A3 shares a device with A4. Four “new” accounts belong to one ring, so all four claims are held. A5 is untouched.
  5. A graph database answers this with one traversal in milliseconds. In SQL each hop is another self-join on very large tables, which gets slow quickly as hops increase.

NoSQL in Indian products you use

1. Caches, OTPs and rate limits: key-value

Payment, food and shopping apps use Redis or similar stores for sessions, carts, OTPs with expiry and “max 5 attempts per minute” rate limits.

Request→Redis by key (~1 ms)→Answer

2. Product catalogues: document stores

Phones, sarees and groceries have completely different attributes. Shopping platforms store each product as a document with its own fields and nested variants.

Seller upload→Document per product→Search + product page

3. Messages and IoT: wide-column

Chat histories, smart-meter readings and vehicle telemetry are huge append-only streams read by key and time. Wide-column stores such as Cassandra and HBase are built for this.

Devices→Partition by device + day→Recent history

4. Fraud and recommendations: graphs

Banks and fintechs look for rings of accounts sharing devices and identifiers; e-commerce and social apps recommend “people also bought” from relationship graphs.

Events→Graph of entities→Ring alerts, suggestions

Run it on your PC: key-value, documents and a graph

Python's standard library includes a real on-disk key-value store (dbm) and SQLite with JSON functions. This program uses them to store carts by key with an expiry, query JSON kitchen documents by their fields, and find a fraud ring in a small graph. Save it as nosql_lab.py in an empty folder and run it.

NoSQL ideas with the standard library

"""Three NoSQL ideas using only Python's standard library:
1. a real key-value store on disk (dbm) used as a shopping-cart store
2. JSON documents queried with SQLite's JSON functions (a document-store style)
3. a small graph searched for a fraud ring"""
import dbm, json, sqlite3
from collections import deque

# ---- 1. Key-value: carts stored by key, with an expiry time
with dbm.open("carts_db", "c") as kv:
    now = 1_000_000                       # fixed clock so the output is repeatable
    kv["cart:U9"] = json.dumps({"items": {"thali": 1, "lassi": 2}, "expires": now + 1800})
    kv["cart:U12"] = json.dumps({"items": {"dosa": 1}, "expires": now - 5})   # already expired
    for key in [b"cart:U9", b"cart:U12", b"cart:U99"]:
        raw = kv.get(key)
        if raw is None:
            print(key.decode(), "-> not found")
            continue
        cart = json.loads(raw)
        state = "expired" if cart["expires"] < now else "live"
        print(key.decode(), "->", cart["items"], f"({state})")

# ---- 2. Documents: each kitchen is one JSON document with a nested menu
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE kitchens (doc TEXT)")
docs = [
    {"_id": "K11", "name": "Annapurna", "city": "Pune", "veg": True,
     "menu": [{"dish": "thali", "price": 220}, {"dish": "lassi", "price": 100}]},
    {"_id": "K12", "name": "Spice Box", "city": "Pune", "veg": False,
     "menu": [{"dish": "biryani", "price": 280}], "delivery_partner": "own riders"},
    {"_id": "K13", "name": "Udupi Corner", "city": "Mumbai", "veg": True,
     "menu": [{"dish": "dosa", "price": 150}, {"dish": "filter coffee", "price": 60}]},
]
db.executemany("INSERT INTO kitchens VALUES (?)", [(json.dumps(d),) for d in docs])
rows = db.execute("""
    SELECT json_extract(doc, '$.name'), json_array_length(doc, '$.menu')
    FROM kitchens
    WHERE json_extract(doc, '$.city') = 'Pune' AND json_extract(doc, '$.veg') = 1
""").fetchall()
print("\nVeg kitchens in Pune (name, dishes on menu):", rows)
extra = db.execute("SELECT json_extract(doc, '$.name') FROM kitchens WHERE json_extract(doc, '$.delivery_partner') IS NOT NULL").fetchall()
print("Documents with an extra field nobody planned for:", extra)

# ---- 3. Graph: accounts linked by shared phones and UPI handles
edges = [("A1", "phone:98xx01"), ("A2", "phone:98xx01"), ("A2", "upi:x@ok"), ("A3", "upi:x@ok"),
         ("A3", "device:D7"), ("A4", "device:D7"), ("A5", "phone:77xx22")]
graph = {}
for a, b in edges:
    graph.setdefault(a, set()).add(b)
    graph.setdefault(b, set()).add(a)
start, seen, queue = "A1", {"A1"}, deque(["A1"])
while queue:
    node = queue.popleft()
    for nxt in graph[node]:
        if nxt not in seen:
            seen.add(nxt)
            queue.append(nxt)
ring = sorted(n for n in seen if n.startswith("A"))
print("\nAccounts connected to A1 through shared phones, UPI ids or devices:", ring)

9 Quiz and revision

Check yourself

Quick revision

Lesson 2.4 in one screen

  • NoSQL = not only SQL: non-relational models, flexible schemas, horizontal scaling.
  • Key-value (Redis, DynamoDB) · Document (MongoDB) · Wide-column (Cassandra, HBase) · Graph (Neo4j).
  • SQL: fixed schema, joins, ACID, vertical scaling. NoSQL: flexible, denormalised, horizontal, often BASE/tunable.
  • Model from queries: denormalise; embed small, bounded children; reference unbounded ones.
  • Partition key spreads data and load; avoid hot partitions; clustering key sorts rows inside.
  • Cache-aside: check cache → on miss read DB and store with TTL → invalidate on change.
  • Quorum: R + W > N for read-your-latest-write. LSM trees for heavy writes. Polyglot persistence = right store per job.

Interview and viva questions

What are the types of NoSQL databases? Give examples.

Key-value stores (Redis, Amazon DynamoDB, Memcached) map unique keys to values for very fast look-ups, used for caches, sessions and carts. Document stores (MongoDB, Couchbase, Firestore) hold JSON-like documents with nested, flexible fields, used for catalogues and profiles. Wide-column stores (Cassandra, HBase, Bigtable) organise rows into partitions sorted by clustering keys across many nodes, used for time series, logs and messaging. Graph databases (Neo4j, Amazon Neptune) store nodes and relationships, used for fraud detection, recommendations and social networks.

Differentiate SQL and NoSQL databases.

SQL databases use tables with predefined schemas, support joins and ACID transactions, and typically scale vertically with read replicas. NoSQL databases use key-value, document, wide-column or graph models, allow flexible schemas, scale horizontally, denormalise data around access patterns and often offer eventual or tunable consistency. SQL suits transactional systems and ad-hoc analysis; NoSQL suits very high scale, flexible data and specific access patterns.

What is the CAP-related trade-off in NoSQL databases?

In a distributed database, when the network partitions, a system must choose between consistency (every read sees the latest write) and availability (every request gets a response). Many NoSQL systems, such as Cassandra, favour availability with tunable consistency, while others, such as HBase, favour consistency. Lesson 3.4 explains the CAP theorem in detail.

When should you not use NoSQL?

When you need complex multi-table transactions (payments, accounting), rich ad-hoc queries and joins across many entities, or strong consistency everywhere without careful design, and when the data comfortably fits a single well-indexed relational database. Adding a NoSQL store also adds operational complexity.

What is polyglot persistence?

Using several kinds of data stores in one system, each chosen for a specific workload: for example a relational database for orders and payments, Redis for caching and sessions, a document store for catalogues, a wide-column store for event history, and a search engine for text search.

Get with a default

keys cart:U9, cart:U99

Expired keys

Each key has an expiry time. At time 100, print the keys still alive.

Expected output

Print people two hops from Riya who are not already her friends.

P6Advanced

Hit ratio needed

The database handles at most 3,000 reads per second. Traffic is 2,00,000 reads per second. What minimum cache hit ratio is needed?

Input
3,000 vs 2,00,000
Expected output
Minimum hit ratio: 98.5%
Show solution and explanation 
db_max, traffic = 3000, 200000
needed = 1 - db_max / traffic
print(f"Minimum hit ratio: {needed * 100:.1f}%")
Minimum hit ratio: 98.5%

How it works: Only misses reach the database, so misses must stay at or below 3,000 per second.

P7Advanced

Quorum settings

For N = 5 replicas, print every (W, R) pair with R + W > N where both are between 1 and 5, and the smallest such R for W = 3.

Input
N = 5
Expected output
15 valid pairs
smallest R for W=3: 3
Show solution and explanation 
N = 5
pairs = [(w, r) for w in range(1, 6) for r in range(1, 6) if r + w > N]
print(len(pairs), "valid pairs")
print("smallest R for W=3:", min(r for w, r in pairs if w == 3))
15 valid pairs smallest R for W=3: 3

How it works: Stronger writes (bigger W) allow lighter reads (smaller R), and the other way round.

P8Business problem

Redis memory for sessions

5 crore daily users, 30% active at peak, each session is 2 KB. How many GB of cache memory are needed (add 30% overhead)?

Input
5 crore, 30%, 2 KB, +30%
Expected output
Memory needed: 37 GB
Show solution and explanation 
users = 5_00_00_000

P9Business problem

Cache saving

Each database read costs Rs 0.002 in compute; a cache read costs Rs 0.0001. With 1 crore reads a day and a 95% hit ratio, print the daily cost with and without the cache.

Input
1 crore reads, 95% hits
Expected output
Without cache: Rs 20000
With cache   : Rs 1950
Show solution and explanation 
reads = 1_00_00_000
no_cache = reads * 0.002
with_cache = reads * 0.95 * 0.0001 + reads * 0.05 * 0.002

Real-world scenario questions (asked in company interviews)

NoSQL design questions from real interviews and projects. Decide your answer first, then open the model answer.

System design · storage choiceFresher

SQL or NoSQL for a new feature?

A ride-hailing app wants to store (a) payments, (b) the live location of every driver, updated every 4 seconds, (c) driver profiles with optional documents, and (d) “riders who travel similar routes”. Which store for each?

The interviewer is checking: can you justify a database choice from access patterns?

Show a strong answer
  • Payments: relational (PostgreSQL/MySQL): ACID transactions.
  • Live locations: key-value (Redis) keyed by driver for the current position, plus a wide-column store (Cassandra) partitioned by driver and day for history.
  • Driver profiles: document store (MongoDB): flexible optional fields.
  • Similar routes: a graph or batch analytics in the lake, depending on how real-time it must be.

Then mention the cost of running several systems and keeping them consistent.

Avoid: choosing NoSQL because it is “faster” or “modern”, or MongoDB for money transfers without discussing transactions.

Data modelling · Cassandra1–3 years

A Cassandra table keeps timing out

A messages table uses PRIMARY KEY (group_id, sent_at). A few huge groups now time out on reads, and their nodes run hot.

The interviewer is checking: do you understand partition sizing and hot partitions?

Show a strong answer

Huge groups create unbounded partitions that live on one set of replicas. Re-key to bound partition size, for example PRIMARY KEY ((group_id, month), sent_at) or add a bucket number for very active groups. Read the latest bucket first and page backwards. Monitor partition sizes and set alerts on large partitions. Migrate by dual-writing to the new table and backfilling.

Avoid: adding more nodes, which doesn’t split a single hot partition.

Reliability · caching1–3 years

Customers see old prices

After adding a Redis cache in front of the product database, some customers see yesterday’s prices for hours.

The interviewer is checking: do you know cache invalidation and TTL trade-offs?

Show a strong answer
  1. Set a sensible TTL so stale entries expire (minutes, not days).
  2. On every price update, delete or update the cache key in the same code path (cache-aside invalidation), or publish a change event that cache updaters consume.
  3. For the final checkout price, always read from the source database.
  4. Monitor hit ratio and staleness.

Avoid: disabling the cache entirely, or caching prices with no expiry.

Fundamentals · interviewFresher

“What is the difference between SQL and NoSQL?”

A standard opening question in data engineering interviews.

The interviewer is checking: can you compare them fairly, with examples and trade-offs?

Show a strong answer

SQL databases store data in tables with fixed schemas, support joins and strong ACID transactions, and usually scale vertically (plus read replicas). NoSQL databases use other models (key-value, document, wide-column, graph), allow flexible schemas, scale horizontally across many nodes, and are designed around specific access patterns, often with relaxed or tunable consistency. Use SQL for transactional systems and complex ad-hoc queries; use NoSQL for very high scale, flexible records, low-latency key look-ups, time series or relationship-heavy queries. Many systems use both.

Avoid: saying NoSQL has no schema at all, or that SQL can’t scale.
