2 Definition

The capstone: a mini lakehouse pipeline

Formal definition (write this in exams)

A capstone project is an end-to-end project that integrates the skills of a course into one working system. Here it is a batch data pipeline implementing the medallion architecture: raw ingestion, a bronze layer of source data in a columnar format partitioned by date, a silver layer of deduplicated, validated and privacy-protected records, and a gold layer of aggregated business tables, with a data quality gate, idempotent partition overwrites and reproducible outputs.

In simple words

You build a small but complete data pipeline on your own computer: messy raw data goes in, clean trustworthy business numbers come out, and running it again never creates duplicates. It uses the same design real companies use, only smaller.

Words you’ll meet in this lesson

Medallion architectureBronze (raw), silver (clean), gold (business-ready) layers in a lake or lakehouse.
Partition overwriteReplacing one partition (one date folder) completely on each run, which makes the step idempotent.
Quarantine tableWhere rows that fail quality checks are kept for review instead of being dropped silently.
ReproducibilityAnyone running the same code on the same inputs gets the same outputs.
pyarrowThe Python library for Apache Arrow tables and Parquet files, used here as a small local engine.
Hive-style partitionsFolders named column=value (for example date=2026-10-19) that engines read as a column.
BackfillRe-running the pipeline for past dates, safe only when steps are idempotent.
READMEThe front page of the project: what, why, how to run, results and decisions.

The brief

Input3 days of food-delivery orders as JSON lines, about 20,000 rows a day, with duplicates, missing cities and invalid quantities
OutputGold tables: revenue and order count by city per day; revenue by dish; plus a printed report
RulesQuality gate at 2%; no raw phone numbers after bronze; identical results on re-run; one command to run
ToolsPython 3 and pyarrow (pip install pyarrow); optional: DuckDB, PySpark, Airflow for extensions

The capstone at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Build it and run it

  • Generate three days of raw orders with realistic problems (duplicates, missing cities, zero quantities).
  • Store raw data as files, then as Parquet in folders named date=YYYY-MM-DD (bronze).
  • Clean it (silver): remove duplicates, quarantine bad rows, replace phone numbers with keys.
  • Summarise it (gold): revenue by city per day and revenue by dish, then print a report.

Intermediate Make it reliable

  • Idempotency: each step overwrites its own date partition, so re-running gives identical results.
  • Quality gate: the run stops if more than 2% of rows fail checks; quarantined rows are kept for review.
  • Repeatability: fixed random seeds per day, so anyone can reproduce your numbers.
  • Logging: each step logs row counts, so a reviewer can follow where rows went.
  • README: problem, architecture diagram, how to run, results, decisions and limitations.

Advanced Take it towards production

  • Swap pyarrow for PySpark or DuckDB; store tables in Delta Lake or Iceberg for ACID MERGE and time travel.
  • Schedule each step as a task in an Airflow DAG with retries, backfills and alerts.
  • Ingest from Kafka instead of files for a streaming bronze layer; keep the batch gold for finance.
  • Move storage to object storage (S3, ADLS, GCS or local MinIO), add tests and CI, data contracts and cost notes.

Exam tip: Describe an end-to-end pipeline using the medallion architecture: the purpose of each layer, the data quality checks in silver, how partitioning and idempotent overwrites make re-runs safe, and how the design maps to Spark, Delta Lake and Airflow in production.

4 Step by step

Building the pipeline

  1. Extract: land the raw data

    extract(day) writes one JSON-lines file per day into lake/raw/, with duplicates, missing cities and zero quantities, exactly like a real export.

    Keeping raw data unchanged means you can always rebuild every later layer if a bug is found.

  2. Bronze: Parquet partitioned by date

    day = "2026-10-19"
print(f"lake/bronze/orders/date={day}/part-0.parquet")
    lake/bronze/orders/date=2026-10-19/part-0.parquet
    Columnar files compress well and read fast; date folders let later steps and queries touch only the days they need. The folder is deleted and rewritten each run, so it is idempotent.

  3. Silver: deduplicate

    ids = ["A", "B", "A", "C", "B"]
seen, keep = set(), []
for i in ids:
    if i not in seen:
        seen.add(i); keep.append(i)
print(keep, "removed", len(ids) - len(keep))
    ['A', 'B', 'C'] removed 2
    Retries create duplicate orders. Keeping the first occurrence of each order_id removes them; in Spark or Delta you would use dropDuplicates or MERGE.

  4. Silver: quality gate and masking

    rows, bad = 21_429 - 150, 100
print(f"failure rate {bad / rows:.2%}", "-> continue" if bad / rows <= 0.02 else "-> STOP")
    failure rate 0.47% -> continue
    Rows with qty ≤ 0 or no city go to quarantine. Above 2% the pipeline stops. Phone numbers become salted-hash customer keys, so analysts never see them.

  5. Gold: business tables

    gold() reads all silver partitions, groups by date and city and by dish, and writes two small Parquet tables for dashboards.

    Gold tables are small, fast and named in business language, the only layer most users ever query.

  6. Prove it: re-run and compare

    The script runs the whole pipeline a second time and checks that the gold table is identical.

    This one check demonstrates idempotency, the property interviewers ask about most for pipelines.

Real-time scenario 2

Break it on purpose: append vs overwrite

The fastest way to understand idempotency is to break it. Change the write to append and watch retries and backfills multiply revenue.

Idempotent writes 5 steps
Animated example
  1. The first run writes 19 October’s silver and gold data: about ₹44 lakh of revenue (₹43.96 lakh, the sum of the four cities in the report).
  2. An orchestrator retries the task after a timeout. If the step appends, the same day’s rows are written again and revenue doubles.
  3. A backfill re-runs the day once more. The dashboard now shows three times the real figure, with no error anywhere.
  4. With partition overwrite (the capstone’s design: delete the date folder, then write), each run replaces the day completely.
  5. Retries and backfills become safe. In Delta Lake you would use replaceWhere for a date or MERGE on order_id; in Iceberg, overwrite-partitions or MERGE.
Real-time scenario 3 · advanced

From your laptop to a production lakehouse

Reviewers often ask: “How would this work at 1,000 times the data?” Watch each part of the capstone map to its production equivalent.

Scaling the design 5 steps
Animated example
  1. Raw JSON files become a Kafka topic or an export landing in object storage; pyarrow becomes PySpark on a managed cluster.
  2. Plain Parquet folders become Delta Lake or Iceberg tables, adding ACID commits, MERGE for upserts, schema enforcement and time travel.
  3. The loop over dates becomes an Airflow DAG with tasks for bronze, silver and gold, retries, alerts and backfills by date.
  4. Print statements become structured logs, metrics and alerts, and quality checks move into a tool such as Great Expectations or dbt tests. The local folder becomes S3, ADLS or GCS with IAM.
  5. The architecture itself does not change, which is exactly why this capstone is a strong portfolio piece: it proves you understand the design, not just one tool.

7 Run the code

The whole pipeline in miniature

This browser version uses only plain Python: raw records go through bronze, silver and gold as lists and dictionaries, with deduplication, a quality gate and masking. Then try the challenges: idempotent partitions, a new quality rule, a new gold table, a broken gate and a reconciliation check.

import hashlib
raw = [  # order_id, date, city, qty, price, phone
    ("A1", "10-19", "Pune", 1, 140, "9876543210"), ("A2", "10-19", "Thane", 2, 120, "9123456780"),
    ("A1", "10-19", "Pune", 1, 140, "9876543210"), ("A3", "10-19", None, 1, 220, "9988776655"),
    ("A4", "10-19", "Pune", 0, 60, "9090909090"), ("A5", "10-19", "Thane", 1, 220, "9811122233"),
]
bronze = {"10-19": list(raw)}                       # one partition per date

seen, silver, quarantine = set(), [], []
for oid, day, city, qty, price, phone in bronze["10-19"]:
    if oid in seen:
        continue                                    # duplicate from a retry
    seen.add(oid)
    if city is None or qty <= 0:
        quarantine.append(oid)
        continue
    key = hashlib.sha256(("salt:" + phone).encode()).hexdigest()[:8]
    silver.append((oid, day, city, qty * price, key))

gold = {}
for oid, day, city, amount, key in silver:
    gold[city] = gold.get(city, 0) + amount
print("silver:", len(silver), "| quarantine:", quarantine)
print("gold revenue by city:", gold)
silver: 3 | quarantine: ['A3', 'A4'] gold revenue by city: {'Pune': 140, 'Thane': 460}

  • key = hashlib.sha256(("salt:" + phone).encode()).hexdigest()[:8]Phones never reach silver; a salted hash keeps customers countable.

Run it on your PC: the full capstone pipeline

Install pyarrow once (pip install pyarrow), save this as capstone_pipeline.py in an empty folder and run it. It creates a lake/ folder with raw, bronze, silver (orders and quarantine) and gold layers for three days, prints a report, then re-runs everything and proves the results are identical. Open the folders to see the partitions.

Raw → bronze → silver → gold, then an idempotency test

"""Capstone: a mini lakehouse pipeline on your PC.
raw JSON lines -> bronze Parquet (partitioned by date) -> silver (clean, dedup,
quality gate, masked PII) -> gold (daily city revenue, top dishes) -> report.
Every step is idempotent: run the script twice and the results are identical.
Needs: pip install pyarrow"""
import hashlib, json, os, random, shutil, time
import pyarrow as pa
import pyarrow.compute as pc
import pyarrow.parquet as pq

LAKE = "lake"
DATES = ["2026-10-17", "2026-10-18", "2026-10-19"]
CITIES = ["Pune", "Mumbai", "Thane", "Nashik"]
DISHES = {"Veg thali": 140, "Paneer roll": 120, "Dal khichdi": 110, "Chicken biryani": 220, "Poha": 60}


def inr(n):
    """Indian digit grouping: 1117740 -> 11,17,740"""
    s = str(int(n))
    head, tail = s[:-3], s[-3:]
    groups = []
    while len(head) > 2:
        groups.insert(0, head[-2:])
        head = head[:-2]
    return ",".join(([head] if head else []) + groups + [tail])


def log(step, msg):
    print(f"[{step:7}] {msg}")


def extract(day):
    """Simulate the app's raw export: JSON lines with real-world problems."""
    rnd = random.Random(day)                      # same day -> same data (repeatable)
    path = f"{LAKE}/raw/orders_{day}.jsonl"
    os.makedirs(os.path.dirname(path), exist_ok=True)
    rows = []
    for i in range(rnd.randint(18_000, 22_000)):
        dish = rnd.choice(list(DISHES))
        rows.append({"order_id": f"{day[-5:].replace('-', '')}-{i:06d}", "ts": f"{day}T{rnd.randint(7, 22):02d}:{rnd.randint(0, 59):02d}:00",
                     "city": rnd.choice(CITIES), "dish": dish, "qty": rnd.choice([1, 1, 1, 2, 3]),
                     "price": DISHES[dish], "phone": f"9{rnd.randint(100000000, 999999999)}"})
    for r in rnd.sample(rows, 60):
        r["qty"] = 0                              # invalid quantity
    for r in rnd.sample(rows, 40):
        r["city"] = None                          # missing city
    rows += rnd.sample(rows, 150)                 # retries create duplicates
    with open(path, "w") as f:
        for r in rows:
            f.write(json.dumps(r) + "\n")
    return path, len(rows)


def bronze(day, raw_path):
    """Raw copy as Parquet, one folder per date. Overwrite = idempotent."""
    rows = [json.loads(line) for line in open(raw_path)]
    table = pa.Table.from_pylist(rows)
    out = f"{LAKE}/bronze/orders/date={day}"
    shutil.rmtree(out, ignore_errors=True)
    os.makedirs(out)
    pq.write_table(table, f"{out}/part-0.parquet")
    return table


def silver(day, table):
    """Deduplicate, check quality, mask PII. Stop if too many rows fail."""
    seen, keep = set(), []
    ids = table.column("order_id").to_pylist()
    for i, oid in enumerate(ids):
        if oid not in seen:
            seen.add(oid)
            keep.append(i)
    dedup = table.take(keep)
    dupes = table.num_rows - dedup.num_rows
    good_mask = pc.and_(pc.greater(dedup["qty"], 0), pc.is_valid(dedup["city"]))
    good, bad = dedup.filter(good_mask), dedup.filter(pc.invert(good_mask))
    fail_rate = bad.num_rows / dedup.num_rows
    if fail_rate > 0.02:
        raise RuntimeError(f"quality gate failed for {day}: {fail_rate:.2%}")
    keys = [hashlib.sha256(("salt:" + p).encode()).hexdigest()[:10] for p in good["phone"].to_pylist()]
    good = good.drop(["phone"]).append_column("customer_key", pa.array(keys))
    good = good.append_column("amount", pc.multiply(good["qty"], good["price"]))
    for name, t in [("orders", good), ("quarantine", bad.drop(["phone"]))]:
        out = f"{LAKE}/silver/{name}/date={day}"
        shutil.rmtree(out, ignore_errors=True)
        os.makedirs(out)
        pq.write_table(t, f"{out}/part-0.parquet")
    return good, dupes, bad.num_rows, fail_rate


def gold():
    """Business tables built from all silver partitions."""
    orders = pq.read_table(f"{LAKE}/silver/orders", columns=["date", "city", "dish", "amount", "customer_key"])
    orders = orders.set_column(0, "date", pc.cast(orders["date"], pa.string()))   # partition column -> plain text
    by_city = orders.group_by(["date", "city"]).aggregate([("amount", "sum"), ("amount", "count")])
    by_city = by_city.sort_by([("date", "ascending"), ("amount_sum", "descending")])
    by_dish = orders.group_by("dish").aggregate([("amount", "sum")]).sort_by([("amount_sum", "descending")])
    os.makedirs(f"{LAKE}/gold", exist_ok=True)
    pq.write_table(by_city, f"{LAKE}/gold/daily_city_revenue.parquet")
    pq.write_table(by_dish, f"{LAKE}/gold/dish_revenue.parquet")
    return by_city, by_dish, orders.num_rows


def run():
    start = time.time()
    for day in DATES:
        raw_path, n_raw = extract(day)
        log("extract", f"{day}: {n_raw:,} raw rows")
        t = bronze(day, raw_path)
        good, dupes, bad, rate = silver(day, t)
        log("silver", f"{day}: {good.num_rows:,} clean, {dupes} duplicates removed, {bad} quarantined ({rate:.2%})")
    by_city, by_dish, n = gold()
    log("gold", f"{n:,} orders across {len(DATES)} days -> 2 gold tables")
    return by_city, by_dish, round(time.time() - start, 1)


if __name__ == "__main__":
    shutil.rmtree(LAKE, ignore_errors=True)
    by_city, by_dish, secs = run()
    print("\nRevenue by city, 2026-10-19 (Rs):")
    for r in by_city.to_pylist():
        if r["date"] == "2026-10-19":
            print(f"  {r['city']:7} {inr(r['amount_sum']):>11}  ({inr(r['amount_count'])} orders)")
    print("Top dishes, all 3 days (Rs):")
    for r in by_dish.to_pylist()[:3]:
        print(f"  {r['dish']:16} {inr(r['amount_sum']):>11}")
    first = pq.read_table(f"{LAKE}/gold/dish_revenue.parquet").to_pylist()
    print("\nRe-running the whole pipeline to test idempotency...")
    run()
    second = pq.read_table(f"{LAKE}/gold/dish_revenue.parquet").to_pylist()
    print("Gold identical after re-run:", first == second)
    files = sum(len(fs) for _, _, fs in os.walk(LAKE))
    print(f"Lake folder: {files} files under ./{LAKE}/")

Problem statement

Expected output

Approach

Quick revision

Lesson 7.1 in one screen

  • Raw (unchanged) → bronze (Parquet by date) → silver (dedup, quality gate, quarantine, masked PII) → gold (business tables).
  • Hive-style partitions: lake/bronze/orders/date=YYYY-MM-DD/ enable pruning and per-day rewrites.
  • Idempotency: overwrite the date partition (or MERGE); never blind append. Prove it by re-running.
  • Reconcile: raw = clean + duplicates + quarantined, for every day.
  • Quality gate at 2%: continue and alert below it, stop above it.
  • Production map: Kafka/exports, Spark, Delta/Iceberg, Airflow, monitoring, object storage.
  • README: problem, diagram, how to run, reconciliation, decisions, results, limitations.

Interview and viva questions

What is a good capstone project for big data or data engineering?

An end-to-end pipeline that ingests realistic messy data, stores it in layers (bronze, silver, gold) using a columnar format partitioned by date, applies deduplication and data quality checks with quarantine, protects personal data, produces business tables, and is idempotent and reproducible. It should run with one command and have a README with architecture, results and decisions.

Can I build a big data pipeline without a cluster?

Yes. The architecture matters more than the size: Python with pyarrow, DuckDB or Polars can process millions of rows on a laptop using the same layers, partitions and quality rules. You can later run the same design on Spark and cloud storage, and explain how it would scale in interviews.

What is the medallion architecture?

A layered lakehouse design: bronze holds raw data in a better storage format, silver holds cleaned, deduplicated and conformed data, and gold holds aggregated, business-ready tables. Each layer is rebuilt from the previous one, which makes debugging and reprocessing straightforward.

How do I make a data pipeline idempotent?

Design each step so that re-running it for the same input gives the same result: overwrite the output partition for the processed date, or use MERGE/upsert on a business key, deduplicate inputs, and avoid side effects such as blind appends or sending duplicate notifications. Test it by running the step twice and comparing outputs.

What should a data engineering project README include?

The problem, an architecture diagram, exact steps to run, the data sources and quality rules, a row reconciliation or validation summary, key design decisions and trade-offs, the results, and limitations with next steps. Add screenshots or sample output and a test or CI badge if available.

Real-world scenario questions (asked in company interviews)

Questions reviewers and interviewers ask about capstone projects. Decide your answer first, then open the model answer.

Capstone reviewFresher

“Walk me through your pipeline.”

A reviewer opens your capstone repository and asks for a two-minute walkthrough.

The interviewer is checking: can you explain design and data flow clearly?

Show a strong answer

Problem → layers → numbers → decisions: “Three days of orders land as JSON in raw. Bronze stores them as Parquet partitioned by date. Silver removes 150 duplicates a day by order_id, quarantines about 0.5% invalid rows behind a 2% gate and replaces phones with hashed keys. Gold has revenue by city and dish. Every step overwrites its date partition, so re-runs are identical; the script proves it by re-running. Next I’d move to Delta Lake and Airflow.”

Avoid: reading the code line by line.

Reliability1–3 years

“What happens if the silver step fails halfway?”

The reviewer asks about partial failures.

The interviewer is checking: do you understand atomicity and recovery?

Show a strong answer

In the capstone, a failed write may leave a partly written folder, but the next run deletes and rewrites that date, so it self-heals. In production, write to a temporary location and move atomically, or use Delta Lake or Iceberg, where a commit is atomic: readers see the old version until the new one is complete. Orchestrator retries are safe because the step is idempotent.

Avoid: saying “it won’t fail”.

Scale1–3 years

“What if each day had 50 crore rows?”

The reviewer asks how the design changes at 25,000 times the volume.

The interviewer is checking: can you separate design from engine?

Show a strong answer

The layers, partitioning, quality gate and idempotent writes stay. Changes: run on Spark with many partitions instead of one Python process; dedup with dropDuplicates or MERGE; use Delta or Iceberg tables; partition by date (and maybe city) with file compaction; read silver incrementally for gold; store in object storage; add monitoring and cost controls.

Avoid: proposing a different architecture for every tool.

PrivacyFresher

“Why hash phone numbers instead of deleting them?”

The reviewer asks about the customer_key column.

The interviewer is checking: can you explain pseudonymisation and its limits?

Show a strong answer

Analysts need to count distinct and repeat customers without seeing phone numbers. A salted hash gives the same key for the same phone, so joins and counts work. It is pseudonymisation, not anonymisation: with the salt someone could re-identify customers, so the salt must be secret (a secrets manager, not the code) and access to bronze, which still has phones, must be restricted.

Avoid: claiming hashing makes the data anonymous.
