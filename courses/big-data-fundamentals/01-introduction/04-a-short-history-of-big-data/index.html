A short history of big data: from one server to the lakehouse

Hadoop, Hive, Spark, Kafka, Delta Lake… each tool was built because the one before it hit a wall. In this lesson you follow five eras in about twenty-five years, see what users saw and what engineers built in each, watch the same question get answered in five eras, and learn why in-memory processing replaced MapReduce. After this, the whole ecosystem will make sense as one story.

2 Definition

How did big data begin?

Formal definition (write this in exams)

Modern big data technology traces back to Google’s research papers on the Google File System (2003), MapReduce (2004) and Bigtable (2006), which described how to store and process web-scale data on clusters of commodity machines that tolerate failure. Open-source implementations such as Apache Hadoop (2006) spread the approach, followed by NoSQL databases, SQL-on-Hadoop, stream processing (Kafka), in-memory processing (Spark), cloud data warehouses and, most recently, the lakehouse.

In simple words

Around 2003 Google had more data than any one computer could hold, so it worked out how to use thousands of cheap computers together and published how. Others copied the idea for free (Hadoop). Every big data tool since then was built to fix a weakness of the ones before it.

Words you’ll meet in this lesson

Research paperA public write-up of how a system works. Google, Amazon and others published papers that the open-source world then implemented.
Open sourceSoftware whose code is free to use, read and change, usually managed by a foundation such as Apache.
Apache Software FoundationThe non-profit that hosts Hadoop, Spark, Kafka, Hive, Cassandra, Iceberg and hundreds of other projects.
Commodity hardwareOrdinary, inexpensive servers instead of special fault-tolerant machines.
In-memory processingKeeping data in RAM between steps instead of writing it to disk each time.
Separation of storage and computeStoring data in one place (object storage) and renting processing power separately, only when needed.
LakehouseLake storage plus table formats that add database features (transactions, updates, time travel).

The history at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Five eras in one breath

  1. Before 2000, one big database: companies kept data in one powerful server (Oracle, IBM DB2, mainframes) and built data warehouses for reports.
  2. 2003–2008, the Google papers and Hadoop: Google showed how to store and process the whole web on thousands of cheap machines. Hadoop copied the idea as free, open-source software.
  3. 2008–2014, more tools for more jobs: SQL on Hadoop (Hive), NoSQL databases (HBase, Cassandra, MongoDB), streaming (Kafka) and faster in-memory processing (Spark).
  4. 2010s, the cloud: rent storage (Amazon S3) and warehouses (BigQuery, Redshift, Snowflake) by the hour instead of buying servers.
  5. Today, the lakehouse and AI: one copy of data in open formats (Delta Lake, Iceberg) serving reports, streaming and machine learning, increasingly queried in plain language.

Intermediate Who built what, and why

  • Google GFS (2003): a file system that splits huge files into large blocks and keeps 3 copies on different cheap machines. Became HDFS.
  • Google MapReduce (2004): a way to process those blocks in parallel (map), then group and combine results (reduce), with automatic re-runs on failure. Became Hadoop MapReduce.
  • Google Bigtable (2006): a giant sorted table spread across machines. Inspired HBase and, with Amazon’s Dynamo paper (2007), Cassandra.
  • Facebook Hive (2008): analysts knew SQL, not Java, so Hive turned SQL into MapReduce jobs.
  • LinkedIn Kafka (2011): a durable log that many systems can publish to and read from in real time.
  • UC Berkeley Spark (2009, Apache top-level 2014): keeps data in memory between steps, so repeated steps and machine learning run far faster than MapReduce.
  • Netflix Iceberg, Uber Hudi, Databricks Delta Lake (2017–2019): table formats that give files in a lake database-like features.

Advanced The forces behind each shift

  • Hardware economics: disk prices per GB fell by more than a million times between 1980 and the 2010s, so keeping everything became cheaper than deciding what to throw away.
  • Commodity clusters beat big iron: many ordinary servers plus software that expects failure (replication, re-execution) cost far less than one fault-tolerant supercomputer.
  • Disk vs memory: as RAM got cheaper, engines moved intermediate results from disk (MapReduce) to memory (Spark), trading memory for 10–100× faster iterative jobs.
  • Separation of storage and compute: cloud object storage plus on-demand compute let teams scale each independently and pay per use. This is why modern warehouses and lakehouses look the way they do.
  • Latency expectations: users went from accepting next-day reports to expecting live dashboards and instant fraud checks, which pushed streaming (Kafka, Flink) into the mainstream.
  • Regulation and trust: privacy laws (Europe’s GDPR in 2018, India’s DPDP Act in 2023) made governance, lineage and deletion first-class requirements.

4 Step by step

Twenty-five years in six steps

  1. 2000: one server and a nightly report

    A bank keeps every transaction in one large Oracle database. A data warehouse is loaded each night, and managers read reports the next morning.

    It works while data is gigabytes. When it grows, the only answer is a bigger, far costlier server. That is scaling up, and it has a ceiling.

  2. 2003–2004: Google writes down its secret

    Google’s index of the web is far too big for any server. Its engineers store files as 64 MB blocks with 3 copies across thousands of cheap machines (GFS), and process them with two simple functions, map and reduce.

    The key ideas: expect failure, move code to data, and let a framework handle splitting, scheduling and retries. Google published both papers.

  3. 2006–2008: Hadoop makes it free

    Doug Cutting and Mike Cafarella build an open-source version for their web-search project. Yahoo! hires Cutting and runs it at huge scale. It becomes Apache Hadoop: HDFS + MapReduce.

    Now any company can run a cluster on ordinary servers. Facebook adds Hive so analysts can write SQL instead of Java MapReduce code.

  4. 2009–2014: faster and more varied

    MapReduce writes to disk after every step, so jobs with many steps are slow. Spark keeps data in memory. Kafka carries events in real time. NoSQL databases serve apps that need millisecond look-ups.

    The single “Hadoop stack” becomes an ecosystem of specialised tools, each solving one weakness of the original.

  5. 2012 onwards: rent, don’t buy

    Instead of running their own clusters, companies store data in cloud object storage and query it with warehouses billed by usage: BigQuery, Redshift, Snowflake.

    Storage and compute are separated: keep petabytes cheaply, and rent 100 machines for 10 minutes when a query needs them.

  6. Today: one copy for everything, and AI on top

    Table formats (Delta Lake, Iceberg, Hudi) add transactions and updates to files in the lake. The same tables feed dashboards, streaming jobs and ML models, and AI assistants turn questions into SQL.

    This is the lakehouse. Under the hood, it still uses the 2003 ideas: blocks, copies, parallel tasks and re-running failed work.

Five forces that created big data

Big data didn’t appear because someone invented Hadoop. Five changes in the world made it necessary, and each one still shapes how platforms are built.

Why it happened 5 steps
Animated example
  1. Cheap storage: the cost of a GB of disk fell by more than a million times over about three decades. Companies started keeping every click and log, which created the volume.

Real-time scenario 3 · advanced

Why Spark replaced MapReduce for most jobs

Machine learning and graph algorithms repeat the same calculation many times over the same data. Watch the two engines run a 5-step job, and see how Spark still recovers from a failure without saving every step to disk.

Disk between steps vs memory 5 steps
Animated example
  1. An iterative job: each pass improves a model using the result of the previous pass. Both engines start the first step together.
  2. MapReduce writes each step’s output to HDFS, with 3 copies, then reads it back for the next step. Spark keeps the intermediate data in memory across steps.
  3. Spark has finished all five steps while MapReduce is still waiting on disk for step 3.
  4. For iterative work, avoiding the disk round-trips often makes Spark 10–100 times faster. That is why the Spark paper caught on so quickly.
  5. Fault tolerance without saving every step: Spark records the lineage (the recipe used to build each piece of data), so when a machine fails it recomputes only the lost piece from its parent. (Timings are illustrative.)

History you can see in today’s job descriptions

1. Banks and telecom still run Hadoop clusters

Many large Indian banks and telecom companies built on-premises Hadoop clusters in the 2010s. They still run HDFS and Hive for regulatory reports and are gradually moving to Spark, cloud or lakehouse platforms. Knowing both worlds is valuable.

On-prem HDFS + Hive→Migration to Spark / cloud→Lakehouse

2. Start-ups are born “streaming-first”

Food-delivery, ride-hailing and fintech start-ups founded after 2015 usually put Kafka (or a cloud equivalent) at the centre from day one, because their products are real-time.

App events→Kafka→Live features + lake

3. New platforms are lakehouses

Teams building fresh platforms today usually choose cloud object storage with Delta Lake or Iceberg tables and Spark or SQL engines on top, instead of a separate lake and warehouse.

Object storage→Open table format→BI + ML

4. AI raises the bar on data quality

Companies training or grounding AI models need well-documented, high-quality, legally collected data. Data engineers with governance and lineage skills are in demand because of this latest shift.

Raw data→Clean, governed tables→AI models

Interview and viva questions

Explain the evolution of big data technologies.

Before 2000 data lived in single relational databases and warehouses that scaled up. Google's GFS (2003) and MapReduce (2004) papers showed how to store and process data on clusters of commodity machines; Hadoop (2006) implemented them as open source. Hive added SQL, and NoSQL stores (HBase, Cassandra, MongoDB) served fast look-ups. Spark brought in-memory processing and Kafka real-time streams. Cloud platforms separated storage from compute (S3, BigQuery, Redshift, Snowflake). Today lakehouses use open table formats (Delta Lake, Iceberg, Hudi) to serve BI, streaming and ML from one copy of the data.

Why was Hadoop named Hadoop?

Doug Cutting named it after his son's toy elephant, which is why the logo is a yellow elephant.

What problems of MapReduce did Spark solve?

MapReduce writes intermediate results to disk between steps, is hard to program (low-level map and reduce functions), and is slow for iterative and interactive work. Spark keeps intermediate data in memory, plans whole multi-step jobs as a DAG, recovers lost data through lineage, and offers high-level APIs (DataFrames, SQL, streaming, MLlib).

Is Hadoop dead?

Hadoop MapReduce is rarely used for new work, but HDFS, YARN and Hive still run in many enterprises, and their ideas live on in Spark, cloud object storage and lakehouses. Many companies are migrating from on-premises Hadoop to cloud or lakehouse platforms, so the knowledge remains useful.

What is the lakehouse and how is it different from earlier architectures?

Earlier platforms kept raw data in a lake and a separate, cleaned copy in a warehouse. A lakehouse stores data once in open formats on cheap object storage and adds a table layer (Delta Lake, Iceberg, Hudi) that provides transactions, schema enforcement, updates and time travel, so the same tables serve BI, streaming and machine learning.

Hive was created at Facebook Kafka was created at LinkedIn Spark was created at UC Berkeley Iceberg was created at Netflix

How it works: Dictionary look-up by key.

P5Medium

Tools per era

Given each tool's year, count how many belong to each era: before 2009, 2009–2018, 2019 onwards.

Input
Hadoop 2006, Hive 2008, Kafka 2011, Spark 2014, Snowflake 2015, Delta 2019, Iceberg 2018
Expected output
{'Hadoop era': 2, 'Specialised + cloud': 4, 'Lakehouse': 1}
Show solution and explanation 
tools = {"Hadoop": 2006, "Hive": 2008, "Kafka": 2011, "Spark": 2014,
         "Snowflake": 2015, "Delta": 2019, "Iceberg": 2018}
eras = {"Hadoop era": 0, "Specialised + cloud": 0, "Lakehouse": 0}
for name, y in tools.items():
    if y < 2009:
        eras["Hadoop era"] += 1
    elif y < 2019:
        eras["Specialised + cloud"] += 1
    else:
        eras["Lakehouse"] += 1
print(eras)
{'Hadoop era': 2, 'Specialised + cloud': 4, 'Lakehouse': 1}

How it works: An if/elif chain puts each year into exactly one bucket.

P6Advanced

Follow the chain of inspiration

Each tool points to the one that inspired it. Print the chain from Delta Lake back to the start.

Input
Delta Lake ← Hive tables ← Hadoop ← GFS
Expected output
Delta Lake <- Hive tables <- Hadoop <- GFS
Show solution and explanation 
inspired_by = {"Delta Lake": "Hive tables", "Hive tables": "Hadoop", "Hadoop": "GFS"}
tool = "Delta Lake"
chain = [tool]
while tool in inspired_by:
    tool = inspired_by[tool]
    chain.append(tool)
print(" <- ".join(chain))
Delta Lake <- Hive tables <- Hadoop <- GFS

How it works: A while loop follows links until a tool has no recorded parent.

P7Advanced

Disk round-trips saved

An iterative job has 8 steps. MapReduce writes 100 GB with 3 copies and reads it back between every pair of steps, at 2 GB/s. Print the total disk time in minutes that Spark avoids by keeping the data in memory.

Input
8 steps, 100 GB, 3 copies, 2 GB/s
Expected output
Seconds per gap: 200.0
Minutes saved: 23.3
Show solution and explanation 
steps, gb, copies, speed = 8, 100, 3, 2
per_gap = (gb * copies + gb) / speed
total = (steps - 1) * per_gap
print("Seconds per gap:", per_gap)
print("Minutes saved:", round(total / 60, 1))
Seconds per gap: 200.0 Minutes saved: 23.3

How it works: Between each pair of steps MapReduce writes (with copies) and reads the data. 7 gaps × 200 s ≈ 23 minutes of pure disk time.

Buy a bigger server or rent the cloud?

A big server costs Rs 90 lakh and lasts 5 years. The same work in the cloud costs Rs 1,200 per hour, and the job runs 4 hours a day. Compare the 5-year cost.

Input
Rs 90 lakh · Rs 1,200/hour × 4 h/day × 365 × 5
Expected output
Server, 5 years: Rs 9000000
Cloud, 5 years : Rs 8760000
Cheaper: cloud
Show solution and explanation 
server = 90_00_000
cloud = 1200 * 4 * 365 * 5
print("Server, 5 years: Rs", server)

P9Business problem

Migration progress

A bank is moving 120 Hive jobs from Hadoop to a lakehouse. It moves 8 jobs a week. How many weeks until done, and what percentage is done after 6 weeks?

import math

Real-world scenario questions (asked in company interviews)

History questions that interviewers use to test real understanding. Decide your answer first, then open the model answer.

Interview · fundamentalsFresher

“Why was Hadoop created?”

An interviewer opens with: “In two minutes, why was Hadoop created and what problem did it solve?”

The interviewer is checking: do you understand the problem behind the tool, not just its name?

Show a strong answer

Around 2003 web-scale data no longer fitted on one machine, and scaling up was too expensive and had a ceiling. Google published GFS and MapReduce, showing how to store data as replicated blocks on many cheap machines and process it in parallel with automatic retries. Hadoop (2006) implemented these ideas as open source: HDFS for storage and MapReduce for processing, later YARN for resource management.

Avoid: listing Hadoop components without saying what problem they solve.

Platform modernisation1–3 years

An old Hadoop cluster and a cloud proposal

Your company runs a 10-year-old on-premises Hadoop cluster with Hive jobs. Leadership asks whether to move to a cloud lakehouse.

The interviewer is checking: can you weigh history, cost and risk instead of following fashion?

Show a strong answer
  • List what runs today: Hive SQL, MapReduce jobs, Spark jobs, downstream reports and their deadlines.
  • Compare total cost: hardware refresh, admin staff and licences versus cloud storage and compute.
  • Check rules: data that must stay in India (choose an Indian cloud region), security and audit needs.
  • Plan in phases: copy data to object storage, convert tables to Parquet/Delta or Iceberg, move Hive SQL to Spark SQL, run both systems in parallel and compare outputs before switching off.

Avoid: “Hadoop is old, so throw it away tomorrow” or “it works, never touch it”.

System design · reasoning1–3 years

Why not just use MapReduce today?

A teammate says, “Spark is just faster MapReduce, so the ideas are the same.” The interviewer asks you to agree or disagree.

The interviewer is checking: do you know what Spark actually changed, and what it kept?

Show a strong answer

Partly agree. Spark keeps the core ideas: partitioned data, parallel tasks, a shuffle for grouping, and re-running failed work. It changed three things: it keeps intermediate data in memory instead of writing to HDFS after every step, it builds a DAG of many steps and optimises the whole plan, and it recovers using lineage instead of replicated intermediate files. It also offers high-level APIs (DataFrames, SQL, streaming, MLlib) instead of hand-written map and reduce functions.

Avoid: saying they are completely different, or that Spark doesn’t need fault tolerance.

Career · learning planFresher

“Should I still learn Hadoop in 2026?”

A junior asks you whether learning Hadoop is a waste of time now that lakehouses exist.

The interviewer is checking: can you give balanced, practical advice?

Show a strong answer

Learn the ideas deeply (HDFS blocks and replication, MapReduce, YARN), because Spark, cloud storage and lakehouses are built on them and interviews still ask them. Spend most hands-on time on Spark, SQL, Kafka, a cloud platform and a table format. Many large Indian enterprises still run Hadoop, so knowing it helps with migration projects.

Avoid: dismissing old tools completely, or spending months on MapReduce Java code.
