Distributed computing basics for big data

Hadoop, Spark and Kafka all rest on one simple pattern: split the data, process the pieces at the same time on many machines, and combine the small results, while surviving machines that fail. This lesson builds that pattern step by step in Python you can run, and shows the traps that make distributed answers wrong.

2 Definition

What is distributed computing?

Formal definition (write this in exams)

Distributed computing is a model in which a task is divided into smaller parts that are processed in parallel on multiple independent computers (nodes) connected by a network. The nodes coordinate by passing messages, and the system presents the combined result as if one computer had done the work. Key ideas are partitioning of data, parallel processing, data locality, aggregation of partial results, and fault tolerance through replication and re-execution.

In simple words

Cut a huge job into pieces, give each piece to a different computer, let them all work at the same time, then put the answers together. If one computer breaks, give its piece to another.

Words you'll meet in this lesson

Partition / blockOne piece of the data. HDFS splits files into blocks; Spark calls them partitions.
Master (coordinator)The node that plans the work, assigns tasks and tracks progress.
WorkerA node that does the actual processing of one or more partitions.
TaskOne unit of work: “process partition 7”. A job is made of many tasks.
Data localityRunning a task on the node that already stores its data, so data doesn't travel over the network.
AggregationCombining the small partial results from workers into the final answer.
ReplicationKeeping copies of each partition on different nodes so a failure doesn't lose it.
StragglerA slow task that delays the whole job, often because its partition is much bigger (data skew).

The five-step pattern

1. PartitionSplit the data into blocks and spread them across nodes (with copies)
2. ScheduleThe master assigns one task per block, preferably on the node that holds it
3. Process in parallelEach worker processes only its own block, at the same time as all others
4. CombineSmall partial results are sent over the network and merged
5. RecoverIf a worker fails, its task is re-run on another node that has a copy

Distributed computing at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Teamwork with rules

Distributed computing is teamwork with strict rules. Think of a wedding kitchen: one head cook (the master) plans the menu and gives each cook (a worker) one dish. Everyone cooks at the same time, and the head cook puts the plates together at the end.

  • You use it daily: a UPI payment touches your app's servers, your bank, NPCI and the receiver's bank. A Google search is answered by thousands of machines, each searching its own slice of the web.
  • The golden rules: split fairly, work in parallel, send back small answers, and have a plan when someone drops out.

Intermediate How the coordination actually works

  • Heartbeats: every worker tells the master “I'm alive, task 60% done” every few seconds. No heartbeat for a while → the worker is treated as failed and its task is re-run elsewhere.
  • Combiners: each worker first combines its own results (local counts) so that only small summaries travel over the network.
  • Shuffle: when results must be grouped by key across machines (all Mumbai orders together), data is exchanged between workers. This network-heavy step is often the slowest part of a job.
  • Easy vs tricky aggregations: sum, count, min and max combine directly. An average needs (sum, count) pairs; distinct counts need sets (or estimates); a median needs much more care.
  • Speculative execution: if one task runs much slower than the rest, the master starts a backup copy on another node and uses whichever finishes first.

Advanced Partial failure, skew and the fallacies of distributed computing

  • Partial failure: in one computer, things work or crash together. In a cluster, some parts fail while others keep going, and a silent node may be dead, slow or just cut off. A timeout can't tell which.
  • Idempotent tasks: because a task may run twice (a retry plus a “dead” worker that comes back), outputs must be written so that running twice gives the same result, for example by committing only one attempt per task.
  • Data skew: one hot key (one city, one celebrity's account) makes one partition huge. Fixes: split the hot key into sub-keys (salting), choose a better partition key, or handle the hot key separately.
  • No global clock: each machine's clock drifts a little, so “which event happened first” across machines is hard. Systems use sequence numbers or logical clocks instead.
  • The fallacies of distributed computing (from engineers at Sun Microsystems): it is wrong to assume the network is reliable, latency is zero, bandwidth is infinite, the network is secure, the topology doesn't change, there is one administrator, transport cost is zero, and the network is the same everywhere. Every big data tool is designed around these.
  • Module 3 goes deeper into partitioning, replication, consistency and the CAP theorem.

Exam tip: Learn the pattern as partition → parallel process → aggregate, plus the two supporting ideas data locality (“move computation to data”) and fault tolerance (replication + re-execution). This is the foundation of MapReduce, which you'll study in the Hadoop course.

4 Step by step

Count chai orders on three machines

  1. Partition the data

    orders = ["chai", "samosa", "chai", "poha", "chai", "samosa"]
blocks = [orders[0:2], orders[2:4], orders[4:6]]
print(blocks)
    [['chai', 'samosa'], ['chai', 'poha'], ['chai', 'samosa']]
    In a real cluster, a 30 GB file becomes 240 blocks of 128 MB, and each block is stored on three different nodes.

  2. Each machine counts only its block

    block = ["chai", "poha"]           # machine 2's block
counts = {}
for item in block:
    counts[item] = counts.get(item, 0) + 1
print(counts)
    {'chai': 1, 'poha': 1}
    All three machines run this at the same time, each on the block stored on its own disk. Nothing is sent over the network yet: that's data locality.

  3. Send back small results

    Machine 1 sends {'chai': 1, 'samosa': 1}, machine 2 sends {'chai': 1, 'poha': 1}, machine 3 sends {'chai': 1, 'samosa': 1}.

    Each block may be 128 MB, but its partial result is a few bytes: one number per item. The network carries the small summaries, not the data.

  4. Combine

    partials = [{"chai": 1, "samosa": 1}, {"chai": 1, "poha": 1}, {"chai": 1, "samosa": 1}]
total = {}
for p in partials:
    for item, n in p.items():
        total[item] = total.get(item, 0) + n
print(total)
    {'chai': 3, 'samosa': 2, 'poha': 1}
    The same answer as counting all six orders on one machine. Counts combine by simple addition, which is why counting is the classic first distributed program.

  5. A machine fails

    Machine 2 crashes halfway through its block.

    The master notices that machine 2 stopped reporting (it misses its regular heartbeat). Another node holds a copy of block 2, so the master re-runs just that one task there. Blocks 1 and 3 are not redone.
5 See it happen

A distributed job: what Riya sees, and what the cluster does

Step through the six frames. Left: the job's progress page. Right: the master and four workers.

Split, process, survive, combine 6 steps
What you see
  1. Riya submits a job that counts orders in a 512 MB file. She doesn't choose machines; she just submits.
  2. The page shows four tasks running at the same time.
  3. Task 3 turns red: worker lost. The other three continue.
  4. Task 3 starts again automatically. Three tasks are already finished.
  5. All four tasks finish, and the results are being combined.
  6. The job succeeds. The totals are exactly what one machine would have produced, even with the failure.
Behind the screen
  1. The master splits the work into four tasks and assigns each to the worker that already stores the block: data locality.
  2. All four workers process their own block in parallel. Nothing big moves over the network.
  3. Worker 3 stops sending heartbeats. The master marks task 3 as failed. Tasks 1, 2 and 4 are not affected.
  4. Worker 1 holds a replica of block 3, so the master re-runs only task 3 there.
  5. Each worker sends back a tiny partial result: a few counts, not 128 MB of data.
  6. The master aggregates the partial results into the final answer.

6 Real-world use

Real-time scenarios: a cluster at work

Three live scenarios: whether to move the data or the program, a job held up by one giant partition, and an advanced one about a worker that goes silent and then comes back.

Real-time scenario 1

Move the data, or move the program?

A worker needs to process a 100 GB block stored on another machine. It could copy the data over the network, or the program could be sent to the machine that has the data. Watch the difference.

Data locality 5 steps
Animated example
  1. The choice: node A has the program; node B has the 100 GB block. Copy the data, or send the program?
  2. Copy the data: 100 GB over a 1 Gbps link (about 125 MB/s) …
  3. … takes about 14 minutes, and while it happens the network is busy for everyone else. Multiply by hundreds of blocks and the network becomes the bottleneck.
  4. Send the program: the code is a few kilobytes and arrives almost instantly.
  5. Result: node B processes the data from its own disk and returns a tiny result. This is data locality, a core design idea of Hadoop and Spark.
Real-time scenario 2

Data skew: one giant partition holds up the whole job

TiffinGo's daily report splits orders by city, one city per worker. Mumbai has six times more orders than any other city. Watch the progress bars, then see two standard fixes.

Task progress per worker 5 steps
Animated example
  1. Start: the data is partitioned by city, one city per worker. It looks fair, but Mumbai's partition is 12 GB and the others are 2 GB.
  2. 2 minutes: four workers are done. W5 has finished only a sixth of Mumbai.
  3. 12 minutes: the job ends only when W5 ends. Four machines were idle for 10 minutes. This is data skew, and W5 is a straggler.
  4. Fix 1, salting: Mumbai's orders are split into sub-keys Mumbai-1 to Mumbai-6 and spread over all workers. Each worker gets about 4 GB and the job finishes in about 4 minutes. The six Mumbai results are added at the end.
  5. Fix 2, speculative execution: when the data is fair but one machine is slow (say, a failing disk), the master runs a backup copy of that task on a free worker and keeps the first result. (Times are illustrative.)
Real-time scenario 3 · advanced

Slow or dead? The worker that came back

A cluster has no way to look inside a silent machine. Watch how heartbeats and timeouts handle a worker that goes quiet, and the surprising bug that appears when it comes back.

Heartbeats, timeouts and retries 5 steps
Animated example
  1. Heartbeats: each worker sends a small “I'm alive, here's my progress” message to the master every 3 seconds. W3 is running task 7.
  2. Silence: W3's heartbeats stop. The master cannot know whether W3 crashed, is overloaded, or has lost its network connection.
  3. Timeout: after 30 seconds without a heartbeat, W3 is treated as failed. Task 7 is re-run on W4, which has a replica of the same data block.
  4. The surprise: W3 was only cut off from the network. It reconnects and also finishes task 7. Without care, the same orders would be counted twice.
  5. The fix: task outputs go to a temporary location, and the master commits exactly one attempt per task. Running a task twice now gives the same final result: the task is idempotent. (Timings are illustrative.)

Where distributed computing runs every day

1. Spark and Hadoop jobs

A Spark job is exactly this lesson: the driver (master) splits the data into partitions, executors (workers) process them in parallel, and failed tasks are retried. Hadoop MapReduce does the same with map and reduce tasks.

Big file→Partitions → parallel tasks → combine→Result

2. Distributed databases

Databases like Cassandra and MongoDB split tables across nodes by key (called sharding): customers A–M on some nodes, N–Z on others, each with replicas. A query for one customer goes straight to the right node.

Query by customer id→Route to the shard that owns it→Fast reply

3. Event streams with Kafka

Kafka splits each stream of events into partitions stored on different brokers, with replicas. Many consumers read different partitions in parallel, so millions of events per second can be handled.

Events→Partitions on many brokers→Parallel consumers

4. Content delivery networks (CDNs)

Videos and images are copied to servers in many cities, and your phone fetches from the nearest one. That's replication and locality applied to users instead of processing.

Video→Copies in many cities→Nearest server answers

5. Large-scale testing and builds

Big software companies run thousands of automated tests on every code change. They are split across many machines and run in parallel, so results come back in minutes instead of hours.

10,000 tests→Split across 200 machines→Report in minutes

Examples are simplified to show the pattern. Real systems add many more details.

7 Run the code

A tiny cluster in Python

Twelve canteen orders, three “machines”. The program partitions the data, lets each machine count only its own block, then combines the partial counts. On a real cluster the three counts would run at the same time on different computers. Then try the challenges: real parallel speed-up, a failure, Amdahl's law, a straggler and the average-of-averages trap.

orders = ["chai", "samosa", "chai", "vada pav", "chai", "poha",
          "samosa", "chai", "coffee", "chai", "samosa", "poha"]
machines = 3

# 1. PARTITION: split the data into one block per machine
size = len(orders) // machines
blocks = [orders[i * size:(i + 1) * size] for i in range(machines)]

# 2. PROCESS: each machine counts only its own block
def count_block(block):
    counts = {}
    for item in block:
        counts[item] = counts.get(item, 0) + 1
    return counts

partials = [count_block(b) for b in blocks]
for i, p in enumerate(partials, 1):
    print("Machine", i, "->", p)

# 3. COMBINE: merge the small partial results
total = {}
for p in partials:
    for item, n in p.items():
        total[item] = total.get(item, 0) + n
print("Final     ->", total)
Machine 1 -> {'chai': 2, 'samosa': 1, 'vada pav': 1} Machine 2 -> {'chai': 2, 'poha': 1, 'samosa': 1} Machine 3 -> {'coffee': 1, 'chai': 1, 'samosa': 1, 'poha': 1} Final -> {'chai': 5, 'samosa': 3, 'vada pav': 1, 'poha': 2, 'coffee': 1}
  • orders[i * size:(i + 1) * size]Slicing gives machine 1 items 0–3, machine 2 items 4–7, machine 3 items 8–11: one partition each.
  • def count_block(block):The same small function is sent to every machine. Shipping code to the data is data locality.
  • partials = [count_block(b) for b in blocks]Here the calls run one after another. On a cluster each call runs on a different node at the same time.
  • total[item] = total.get(item, 0) + nCounts combine by adding. That is why counting is the classic first distributed program.

Run it on your PC: use all your CPU cores

A plain Python loop uses one core. This program counts prime numbers below 20 lakh, first on one core, then split into blocks and run on all your cores with multiprocessing. It is a real parallel program on one machine, using the same split–process–combine pattern a cluster uses across machines. Save it as use_all_cores.py.

Split the work across cores

import os, time
from multiprocessing import Pool


def count_primes(block):
    """Count the prime numbers in one block (a range of numbers)."""
    lo, hi = block
    count = 0
    for n in range(max(lo, 2), hi):
        if all(n % d for d in range(2, int(n ** 0.5) + 1)):
            count += 1
    return count


if __name__ == "__main__":           # needed on Windows for multiprocessing
    cores = os.cpu_count()
    N = 2_000_000
    step = N // cores
    blocks = [(i * step, (i + 1) * step) for i in range(cores)]

    start = time.time()
    serial = sum(count_primes(b) for b in blocks)
    t1 = time.time() - start
    print(f"Serial   (1 core) : {serial} primes in {t1:.1f} s")

    start = time.time()
    with Pool(cores) as pool:
        parallel = sum(pool.map(count_primes, blocks))
    t2 = time.time() - start
    print(f"Parallel ({cores} cores): {parallel} primes in {t2:.1f} s")
    print(f"Speed-up: {t1 / t2:.1f}x")

    # Big numbers take longer to test, so the last block is the slowest.
    # Many small blocks spread the work more evenly between the cores.
    small = N // (cores * 8)
    many = [(i * small, (i + 1) * small) for i in range(cores * 8)]
    start = time.time()
    with Pool(cores) as pool:
        balanced = sum(pool.map(count_primes, many))
    t3 = time.time() - start
    print(f"Parallel, {len(many)} small blocks: {balanced} primes in {t3:.1f} s, speed-up {t1 / t3:.1f}x")

# In a terminal:  python use_all_cores.py
Serial (1 core) : 148933 primes in 7.0 s Parallel (2 cores): 148933 primes in 4.9 s Speed-up: 1.4x Parallel, 16 small blocks: 148933 primes in 4.4 s, speed-up 1.6x

Recorded on a small 2-core cloud machine. On a 4- or 8-core laptop the speed-up will be larger, and your times will differ. Notice two real-world lessons: the answer is identical every time, and the speed-up is less than the number of cores, partly because bigger numbers take longer to test, so the last block is a straggler. Many smaller blocks balance the work better.

Check yourself

Quick revision

Lesson 1.3 in one screen

  • Heartbeats + timeouts detect failed workers; failed tasks are re-run on a node with a replica.
  • Data skew: one hot key makes one huge partition (a straggler). Fix with salting or a better key; slow machines get speculative backup tasks.
  • Retries mean a task can run twice, so outputs must be idempotent (commit one attempt per task).
  • Distributed computing: many networked nodes work on parts of one job in parallel and combine the results.
  • Pattern: partition → process in parallel → aggregate.
  • Data locality: send the small program to the big data, not the reverse.
  • Master–worker (HDFS, Spark, YARN) vs peer-to-peer (Cassandra).
  • Fault tolerance: heartbeats detect failures; replicas let failed tasks re-run elsewhere.
  • Combine carefully: sums and counts add up; average of averages is wrong; distinct counts need sets.
  • Stragglers: the job waits for the slowest task. Amdahl's law: speed-up ≤ 1 ÷ serial fraction.

Interview and viva questions

What is distributed computing? How is it different from parallel computing on one machine?

Parallel computing runs parts of a task at the same time, often on cores sharing one machine's memory. Distributed computing spreads the task across separate computers connected by a network, each with its own memory and disk, coordinating by messages. It scales further and survives machine failures, but must deal with network delays and partial failures.

Explain data locality and why it matters in Hadoop.

Data locality means scheduling a task on the node that already stores its data block. Network bandwidth across a cluster is much scarcer than local disk bandwidth, so moving a few kilobytes of code instead of gigabytes of data saves time and avoids congestion. Hadoop's scheduler prefers node-local, then rack-local, then remote placement.

How does a distributed system handle the failure of a node?

Workers send heartbeats to a coordinator. When heartbeats stop, the node is marked dead. Its data is still available because blocks are replicated on other nodes, and its unfinished tasks are re-run on nodes holding those replicas. Tasks are designed to be idempotent so re-running them doesn't corrupt results.

What is Amdahl's law?

It gives the maximum speed-up from parallelising a job: speed-up = 1 ÷ ((1 − p) + p ÷ n), where p is the parallel fraction and n the number of processors. The serial part sets a hard limit: if 5% is serial, the job can never run more than 20× faster.

What are the main challenges of distributed systems?

Partial failures (some nodes fail while others work), network latency and lost messages, keeping replicas consistent, uneven work (skew and stragglers), coordinating many nodes, and combining partial results correctly. Frameworks like Hadoop and Spark handle much of this for the programmer.

What is data skew and how do you fix it?

Data skew happens when one partition key has far more data than others, so one task runs much longer and the whole job waits for it. Fixes include salting the hot key (splitting it into several sub-keys and combining their results later), choosing a partition key with more even values, handling the hot keys separately (for example, broadcasting a small table in a join), and in Spark enabling adaptive query execution, which can split skewed partitions automatically.

Input
[1200, 950, 1430, 880]
Expected output
Total: 4460
Show solution and explanation 
print("Total:", sum([1200, 950, 1430, 880]))
Total: 4460

How it works: Sums combine by adding: the simplest kind of aggregation.

P4Medium

Global maximum from local maximums

Each machine finds the largest bill in its block. Combine them to get the largest bill overall.

Input
blocks [120, 450, 80], [990, 30], [300, 710]
Expected output
Local: [450, 990, 710]
Global max: 990
Show solution and explanation 
blocks = [[120, 450, 80], [990, 30], [300, 710]]
local_max = [max(b) for b in blocks]
print("Local:", local_max)
print("Global max:", max(local_max))
Local: [450, 990, 710] Global max: 990

How it works: Max of maxes is correct (unlike average of averages), so each node only needs to send one number.

P5Medium

Amdahl's law

95% of a job can run in parallel. Print the speed-up on 20 machines and the limit.

Input
p = 0.95, n = 20
Expected output
Speed-up: 10.26
Limit: 20 x
Show solution and explanation 
p, n = 0.95, 20
print("Speed-up:", round(1 / ((1 - p) + p / n), 2))
print("Limit:", round(1 / (1 - p)), "x")
Speed-up: 10.26 Limit: 20 x

How it works: Even 5% serial work caps the speed-up at 20×; on 20 machines you get about 10×.

P6Advanced

Which workers are dead?

The master marks a worker as dead if its last heartbeat is more than 30 seconds old. Given the last heartbeat time of each worker and the current time, print the dead workers and the tasks to re-run.

Input
now = 1000 s
Expected output
Dead workers: ['W3', 'W5']
Tasks to re-run: [4, 5, 7]
Show solution and explanation 
now = 1000
last_beat = {"W1": 998, "W2": 990, "W3": 955, "W4": 999, "W5": 960}
tasks = {"W1": [1, 2], "W2": [3], "W3": [4, 5], "W4": [6], "W5": [7]}
TIMEOUT = 30
dead = [w for w, t in last_beat.items() if now - t > TIMEOUT]
rerun = [task for w in dead for task in tasks[w]]
print("Dead workers:", dead)
print("Tasks to re-run:", rerun)
Dead workers: ['W3', 'W5'] Tasks to re-run: [4, 5, 7]

How it works: W3 has been silent 45 s and W5 40 s, both over the 30 s timeout. Their tasks are re-scheduled on healthy workers that hold replicas of the same blocks.

P7Advanced

Commit one attempt per task

Because of retries, the same task can report results more than once. Keep only the first result for each task id, and print the correct total.

Input
results (task, attempt, orders)
Expected output
Naive total  : 670
Correct total: 435
Show solution and explanation 
results = [(1, "a", 120), (2, "a", 95), (3, "a", 140),
           (3, "b", 140), (4, "a", 80), (2, "b", 95)]
committed = {}
for task, attempt, orders in results:
    if task not in committed:
        committed[task] = (attempt, orders)
naive = sum(r[2] for r in results)
correct = sum(o for _, o in committed.values())
print("Naive total  :", naive)
print("Correct total:", correct)
Naive total : 670 Correct total: 435

How it works: Adding every report counts tasks 2 and 3 twice. Committing one attempt per task makes retries harmless: this is the idempotent output idea from scenario 3.

P8Business problem

Copy the data or move the code?

A job needs 500 GB that sits on another node. The network gives 10 Gbps (about 1,250 MB/s). Print the copy time in minutes. Sending the 10 KB program takes well under a second.

Input
500 GB, 1250 MB/s
Expected output
Copying data: 6.8 minutes
Show solution and explanation 
mb = 500 * 1024
print("Copying data:", round(mb / 1250 / 60, 1), "minutes")
Copying data: 6.8 minutes

How it works: About 7 minutes of a fully busy link for one block. Data locality avoids this entirely.

P9Business problem

When does the job finish?

Six tasks run on six workers at the same time. Their times are 4, 5, 4, 21, 5 and 4 minutes. Print the job time and the average task time.

Input
[4, 5, 4, 21, 5, 4]
Expected output
Job time: 21 minutes
Average task: 7.2 minutes
Show solution and explanation 
times = [4, 5, 4, 21, 5, 4]
print("Job time:", max(times), "minutes")
print("Average task:", round(sum(times) / len(times), 1), "minutes")
Job time: 21 minutes Average task: 7.2 minutes

How it works: The straggler (21 min) decides the job time, not the average (7.2 min). Fix the skew or run a backup copy of the slow task.

P10Business problem

Distinct customers across stores

Three stores report the customer ids they served. Print the number of distinct customers overall. (Adding the three counts would be wrong.)

Input
store ids with overlaps
Expected output
Sum of counts (wrong): 8
Distinct customers   : 5
Show solution and explanation 
stores = [{"C1", "C2", "C3"}, {"C2", "C4"}, {"C1", "C4", "C5"}]
print("Sum of counts (wrong):", sum(len(s) for s in stores))
print("Distinct customers   :", len(set().union(*stores)))
Sum of counts (wrong): 8 Distinct customers : 5

How it works: Customers who visit several stores would be counted more than once. Combine the sets, then count.

Real-world scenario questions (asked in company interviews)

Distributed-computing problems that show up in real jobs and interviews. Decide your answer first, then open the model answer.

Retail analytics · correctnessFresher

The national average bill is wrong

Each region computes its average bill value and sends it to head office, which averages the 10 regional averages for the national figure. Finance says the number doesn't match their records.

The interviewer is checking: do you know which results can be combined, and how to combine averages correctly?

Show a strong answer

An average of averages gives every region equal weight, even though regions have very different numbers of bills.

  • Each region should send (total value, number of bills).
  • Head office adds the totals and the counts, then divides once.
  • Medians and distinct counts need similar care: they can't be combined by simple addition either.

Avoid: “weighting by region size” using population or guesses instead of the actual counts.

E-commerce · Spark job1–3 years

199 tasks finish in 2 minutes, one takes 40

A daily job groups orders by seller. The Spark UI shows 199 tasks finishing in about 2 minutes and one task running for 40 minutes. Adding more machines didn't help.

The interviewer is checking: can you recognise data skew and stragglers, and explain why more machines don't fix them?

Show a strong answer

One partition holds far more data than the others, probably a few huge sellers. The job waits for that straggler; extra machines only speed up tasks that were already fast.

  • Check record counts per key to confirm the skew.
  • Split hot keys (add a random “salt” to spread one seller across several partitions, then combine).
  • Pre-aggregate before the big grouping so less data moves.
  • Enable the engine's skew-handling features where available.

Avoid saying: “Just add more nodes.”

Any company · conceptsFresher

“Why not copy all the data to one powerful machine first?”

A teammate suggests copying 50 TB from the cluster to one large server each night to run the report there, “because it's simpler”.

The interviewer is checking: do you understand data locality and network limits, with numbers?

Show a strong answer

At 10 Gbps (about 1.25 GB/s), copying 50 TB takes roughly 11–12 hours of a fully busy link, before any processing, and the single server then hits the walls from Lesson 1.2.

  • Process the data where it lives: run the report as a distributed job on the cluster.
  • Move only the small results (aggregates) to the reporting server or dashboard.
  • Consider processing only the new day's data incrementally.

Avoid: ignoring network transfer time when comparing designs.

Fintech · reliability1–3 years

A worker died at 90% of the job

A 3-hour nightly job runs on 50 workers. At 2 h 40 min, one worker's machine reboots. A junior engineer wants to restart the whole job from the beginning. What should happen instead, and what must the job's code guarantee?

The interviewer is checking: do you know task-level retry and idempotency?

Show a strong answer

Frameworks like Spark and MapReduce re-run only the failed tasks on other nodes using replicated data; finished tasks are not redone. The job finishes a few minutes late, not three hours late.

  • Task output must be idempotent: if a task runs twice, its result is written once (for example, write to a temporary location and commit atomically).
  • Avoid side effects inside tasks (sending emails or payments) that would repeat on retry.
  • For very long pipelines, add checkpoints between stages.

Avoid: designs where a retry double-counts money or sends duplicate notifications.
