Partitioning and sharding: splitting data across machines

When one table is too big for one machine, you split it: that is partitioning, and when the parts live on different servers, sharding. In this lesson you choose a partition key, route queries to one shard or all of them, see why adding a shard can move 80% of your data (and how consistent hashing cuts that to about 20%), and watch a viral offer overload a single shard.

Then one shard gets overloaded while others sit idle, or simple queries suddenly have to ask every machine. Today you’ll see what happens when a shard is added, why one celebrity kitchen can melt a shard, and why partitioning by date makes “today” a hotspot.

2 Definition

What are partitioning and sharding?

Formal definition (write this in exams)

Partitioning divides a large dataset into smaller, independent subsets called partitions, so that storage and processing can be spread across resources. Horizontal partitioning splits rows by the value of a partition key; when the partitions live on different servers it is called sharding. Common strategies are range partitioning (contiguous key ranges), hash partitioning (a hash function of the key) and directory/list partitioning (an explicit mapping). Vertical partitioning splits columns into separate tables.

In simple words

Partitioning means cutting a huge table into smaller pieces by some rule, for example by user id or by date. Sharding is when those pieces are put on different machines, so each machine stores and handles only part of the data.

Partitioning at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Shelves in a library, coaches in a train

  • Partitioning means splitting a big collection into smaller parts. A library splits books across shelves; a train splits passengers across coaches.
  • Range: shelf 1 for A–F, shelf 2 for G–M. Easy to find a range (“all books starting with C”), but some shelves can get crowded.
  • Hash: a formula turns each name into a number and picks a shelf. Books spread evenly, but “all books starting with C” means checking every shelf.
  • Directory: a notebook at the entrance lists which shelf each book is on. Flexible, but the notebook must always be available.

The key question: which field decides the shelf? Choose the one most queries use, with many different values.

Intermediate Strategies, keys and where partitioning shows up

  • Horizontal vs vertical: horizontal partitioning splits rows (sharding when the parts are on different machines); vertical partitioning splits columns into separate tables or stores.
  • Good partition key: high cardinality (many distinct values), even distribution, and present in most queries. User id is often good for an app; city is usually poor (few values, very uneven).
  • Routing: a router or the client library computes the shard from the key. Queries with the key go to one shard; queries without it must ask every shard and merge results (scatter-gather).
  • Everywhere in big data: HDFS blocks, Spark partitions, Kafka topic partitions (ordering is guaranteed only within one partition), Cassandra and DynamoDB partition keys, and date folders in a lake (date=2026-10-19/) used for pruning.

Advanced Rebalancing, consistent hashing and hot keys

  • The mod-N problem: with hash(key) % N, changing N from 4 to 5 moves about 80% of keys, a huge data migration.
  • Consistent hashing: place shards and keys on a ring; each key belongs to the next shard clockwise. Adding a shard moves only about 1/N of keys. Virtual nodes (many points per shard) keep the load even. Used in Cassandra, DynamoDB and many caches.
  • Fixed partitions: another approach (Kafka, Elasticsearch, Couchbase) creates many more partitions than machines up front and moves whole partitions when nodes join.
  • Hot keys: one huge customer or one viral event overloads one shard. Fixes: split the key with a suffix (key + random 0–9), cache it, or give it a dedicated shard.
  • Secondary indexes: a local index per shard makes writes cheap but reads scatter-gather; a global index partitioned by the indexed field makes reads cheap but writes touch several shards.
  • Cross-shard work: joins and transactions across shards are slow and complex, so data that is used together should share a partition key (for example user id on both orders and payments).

Exam tip: Define partitioning and sharding, then explain range, hash and directory partitioning with one example and one advantage and disadvantage each. Mention how to choose a partition key and the hot-spot problem. A small diagram of keys going to shards earns extra marks.

4 Step by step

Sharding an orders table

  1. Pick the partition key

    TiffinGo’s app mostly asks “show this user’s orders” and “place an order for this user”. So the orders table is partitioned by user_id.

    The key decides everything else: balance, which queries are fast, and which queries must visit every shard.

  2. Hash partitioning spreads users evenly

    import hashlib
def shard_for(user, n=4):
    return int(hashlib.md5(user.encode()).hexdigest(), 16) % n
for u in ["U9", "U42", "U777", "U1001"]:
    print(u, "-> shard", shard_for(u))
    U9 -> shard 1 U42 -> shard 0 U777 -> shard 2 U1001 -> shard 2
    A stable hash (here MD5; never Python’s hash(), which changes between runs) turns each user id into a big number; % 4 picks one of four shards. Similar ids land on different shards, so load spreads evenly.

  3. Range partitioning keeps dates together

    ranges = [("2026-01", "2026-03", "P0"), ("2026-04", "2026-06", "P1"),
          ("2026-07", "2026-09", "P2"), ("2026-10", "2026-12", "P3")]
def part_for(month):
    return next(p for lo, hi, p in ranges if lo <= month <= hi)
print("2026-10 ->", part_for("2026-10"), "| 2026-02 ->", part_for("2026-02"))
    2026-10 -> P3 | 2026-02 -> P0
    For analytics, ranges of dates are natural: a report on October reads only P3. The catch: every new order goes into the newest range, so one partition takes all the writes.

  4. The trouble with % N when you grow

    import hashlib
h = lambda k: int(hashlib.md5(k.encode()).hexdigest(), 16)
keys = [f"U{i}" for i in range(1000)]
moved = sum(1 for k in keys if h(k) % 4 != h(k) % 5)
print(f"mod-N, 4 -> 5 shards: {moved / len(keys):.0%} of keys move")
    mod-N, 4 -> 5 shards: 79% of keys move
    Going from 4 to 5 shards changes hash % N for most keys, so most of the data would have to move. Consistent hashing reduces this to roughly one fifth (see scenario 1).

  5. Directory partitioning for special cases

    directory = {"tenant_acme": "shard-A", "tenant_bigbazaar": "shard-B", "tenant_small_1": "shard-C"}
print(directory["tenant_bigbazaar"])
directory["tenant_bigbazaar"] = "shard-D"     # move a big tenant to its own shard
print(directory["tenant_bigbazaar"])
    shard-B shard-D
    A lookup table lets you place big customers deliberately and move them without rehashing anyone else. It is common in multi-tenant SaaS products. The directory itself must be fast and highly available.

  6. Queries with and without the key

    “Orders of U42” goes to one shard. “All orders from Pune today” has no user id, so the router asks all shards and merges the results.

    Scatter-gather works, but it gets slower and costlier as shards grow. Such analytical questions are better answered from a data lake or warehouse copy partitioned by date.

6 Real-world use

Real-time scenarios: partitions under pressure

Three live scenarios: adding a shard with and without consistent hashing (real numbers), a viral offer that overloads one shard, and an advanced look at the date-partitioning trade-off.

Real-time scenario 1

Adding a fifth shard: who has to move?

These numbers come from the program in “Run it on your PC”: 3,000 users on 4 shards, then a 5th shard is added. Compare simple hash % N with consistent hashing.

Rebalancing 5 steps
Animated example
  1. 3,000 users are spread over 4 shards. Traffic grows, so a fifth shard is added.
  2. With hash(user) % N, changing N from 4 to 5 changes the shard for 80% of users. Almost all data must be copied while the system is live.
  3. Consistent hashing places shards (and many virtual points per shard) on a ring. Each key goes to the next shard point clockwise.
  4. A new shard takes over only the keys on its own arcs of the ring; every other key stays put.
  5. Only 22% of users move, close to the ideal of one in five. Cassandra, DynamoDB and many caches use this idea.
Real-time scenario 2

One viral offer melts one shard

Orders are sharded by kitchen. Then one famous kitchen announces a ₹1 biryani offer at 8 pm. Watch the CPU of each shard.

Hot key 5 steps
Animated example
  1. On a normal day kitchens are spread evenly, so every shard runs at around 40% CPU.
  2. The viral offer sends a flood of orders for one kitchen id. Every one of them hashes to shard 1, which hits 100% while the others stay calm.
  3. Adding more shards changes nothing for this key: one key always maps to exactly one shard.
  4. Split the hot key: append a random suffix 0–9 so the kitchen’s orders spread over ten sub-keys on different shards; reads combine the parts.
  5. Caching the menu and queueing order writes smooth the burst further. (Load figures are illustrative.)
Real-time scenario 3 · advanced

Partitioning by date: great for reports, bad for writes

Range partitioning by date makes date-range reports fast, but it creates a moving hotspot: every new row lands in the newest partition. Watch the trade-off and the composite-key fix.

Range hotspots 5 steps
Animated example
  1. Orders are range-partitioned by month: July, August, September, October.
  2. A report on October reads only the October partition and skips the rest: partition pruning.
  3. But every new order belongs to the current month, so all writes hit one partition while the others sit idle. The hotspot moves forward every month.
  4. A composite key adds a hash bucket in front of the date: new orders spread over four buckets, and a date-range query reads four small pieces instead of one.
  5. In practice each system is partitioned for its job: the live database by user id, the lake by date, and time-series stores by bucket plus time.

Partitioning in real systems

1. Payment and order databases sharded by user

Large payment apps and marketplaces shard their transactional databases by user or merchant id, so a user’s history and new payments stay on one shard, and add shards as users grow.

Request with user_id→Router → one shard→Fast, isolated

2. Kafka topics with many partitions

An orders topic might have 48 partitions keyed by order id, so 48 consumers can process in parallel while each order’s events stay in order within its partition.

Producers→48 partitions by key→48 consumers

3. Lake tables partitioned by date

Almost every analytics table in a lake is partitioned by event date (sometimes also region), so daily jobs and reports scan only the days they need.

Daily data→date=… folders→Pruned queries

4. Distributed caches and NoSQL rings

Cassandra, DynamoDB and distributed caches place keys on a consistent-hash ring, so nodes can be added or replaced with only a small share of keys moving.

Key→Position on ring→Owner node

Route orders to shards

Orders are routed to 4 shards by a stable hash of the user id. The program prints how many orders land on each shard, then answers one query that has the shard key and one that doesn't. Then try the challenges: range partitioning, choosing a key, mod-N rebalancing, consistent hashing and hot keys.

    return int(hashlib.md5(key.encode()).hexdigest(), 16) % n

shards = {0: [], 1: [], 2: [], 3: []}
for oid, user, city in orders:

for s, rows in shards.items():
    print(f"shard {s}: {rows}")

# With the shard key: ask one shard
target = shard_for("U9")

# Without the shard key: ask every shard (scatter-gather)

Run it on your PC: four real shards with SQLite

This program creates four SQLite database files, routes 20,000 orders to them by a hash of the user id, then compares a query with the shard key (one database) and one without it (all four). Finally it measures how many users would move when a fifth shard is added, with % N and with consistent hashing. Only the standard library is used. Save it as shard_lab.py and run it.

Shards, routing and rebalancing

"""Four real SQLite database files used as shards.
Orders are routed by a hash of the user id. Then we compare a query that uses the
shard key with one that doesn't, and measure how many keys move when a shard is added."""
import bisect, hashlib, os, random, sqlite3

SHARDS = 4
os.makedirs("shards", exist_ok=True)


def h(text):
    """A stable hash (Python's built-in hash() changes between runs)."""
    return int(hashlib.md5(text.encode()).hexdigest(), 16)


conns = []
for i in range(SHARDS):
    path = f"shards/orders_{i}.db"
    if os.path.exists(path):
        os.remove(path)
    c = sqlite3.connect(path)
    c.execute("CREATE TABLE orders (order_id TEXT, user_id TEXT, city TEXT, amount INT)")
    conns.append(c)

random.seed(11)
cities = ["Pune", "Mumbai", "Thane", "Nashik"]
for n in range(20_000):
    user = f"U{random.randint(1, 3000)}"
    shard = h(user) % SHARDS
    conns[shard].execute("INSERT INTO orders VALUES (?, ?, ?, ?)",
                         (f"O{n}", user, random.choice(cities), random.randint(50, 900)))
for c in conns:
    c.commit()

print("Rows per shard:", [c.execute("SELECT COUNT(*) FROM orders").fetchone()[0] for c in conns])

# Query 1: by the shard key -> exactly one shard
user = "U42"
shard = h(user) % SHARDS
rows = conns[shard].execute("SELECT COUNT(*), SUM(amount) FROM orders WHERE user_id = ?", (user,)).fetchone()
print(f"\nOrders of {user}: ask shard {shard} only -> {rows[0]} orders, Rs {rows[1]}")

# Query 2: not by the shard key -> ask every shard and merge (scatter-gather)
parts = [c.execute("SELECT COUNT(*) FROM orders WHERE city = 'Pune'").fetchone()[0] for c in conns]
print(f"Orders from Pune: ask all {SHARDS} shards {parts} -> total {sum(parts)}")

# Adding a fifth shard: how many users would have to move?
users = [f"U{i}" for i in range(1, 3001)]
moved_mod = sum(1 for u in users if h(u) % 4 != h(u) % 5)

def ring(nodes, vnodes=100):
    points = sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vnodes))
    return [p for p, _ in points], [n for _, n in points]

def owner(key, r):
    keys, names = r
    i = bisect.bisect(keys, h(key)) % len(keys)
    return names[i]

r4, r5 = ring(["S0", "S1", "S2", "S3"]), ring(["S0", "S1", "S2", "S3", "S4"])
moved_ring = sum(1 for u in users if owner(u, r4) != owner(u, r5))
print(f"\nAdding a 5th shard, users that must move:")
print(f"  hash % N          : {moved_mod} of {len(users)} ({moved_mod / len(users):.0%})")
print(f"  consistent hashing: {moved_ring} of {len(users)} ({moved_ring / len(users):.0%})")

Interview and viva questions

What is sharding and why is it used?

Sharding is horizontal partitioning of a database across multiple servers: each shard stores a subset of rows chosen by a partition (shard) key. It is used when data size or write throughput exceeds what one server can handle, because each shard stores and serves only part of the data, and shards can be added as the system grows.

Compare range and hash partitioning.

Range partitioning assigns contiguous key ranges to partitions, which makes range queries efficient and data easy to reason about, but can create hotspots (for example all new dates in one partition) and uneven sizes. Hash partitioning assigns rows by a hash of the key, giving an even distribution and avoiding ordering hotspots, but range queries must visit every partition and plain mod-N hashing makes adding partitions expensive.

How do you choose a good partition key?

Choose a key with high cardinality and an even distribution of data and traffic, that appears in most queries so they can be routed to a single partition, and that keeps data used together (such as a user's orders and payments) on the same partition. Avoid low-cardinality keys like city or status and monotonically increasing keys like timestamps for write-heavy tables.

What is consistent hashing?

A technique where both nodes and keys are hashed onto a circular space (a ring); each key belongs to the first node clockwise from its position. When a node is added or removed, only the keys in the affected arc move, about 1/N of all keys, instead of most keys as with hash mod N. Virtual nodes (many ring positions per physical node) even out the load. It is used in Cassandra, DynamoDB and distributed caches.

What problems does sharding introduce?

Queries without the shard key become scatter-gather, joins and transactions across shards are complex and slow, hot keys can overload a shard, rebalancing data when adding shards is operationally hard, and secondary indexes must be designed as local (cheap writes, scattered reads) or global (cheap reads, more expensive writes).

Practice problems

Partitioning exercises, from routing a key to sizing Kafka partitions. The last two are business tasks.

P1Easy

Shard for an id

Numeric customer ids are sharded with id % 6. Print the shard of each id.

Input
101, 256, 999, 1200
Expected output
101 -> shard 5
256 -> shard 4
999 -> shard 3
1200 -> shard 0
Show solution and explanation 
for cid in [101, 256, 999, 1200]:
    print(cid, "-> shard", cid % 6)
101 -> shard 5 256 -> shard 4 999 -> shard 3 1200 -> shard 0

How it works: The remainder of division picks the shard.

P2Easy

Range lookup

Partitions: P0 for ids 1–1000, P1 for 1001–2000, P2 for 2001–3000. Print the partition of id 1500.

Input
1500
Expected output
P1
Show solution and explanation 
ranges = [("P0", 1, 1000), ("P1", 1001, 2000), ("P2", 2001, 3000)]
print(next(p for p, lo, hi in ranges if lo <= 1500 <= hi))
P1

How it works: Find the range that contains the id.

P3Easy

Rows per partition

Count orders per city partition.

Input
6 orders
Expected output
{'Pune': 2, 'Mumbai': 3, 'Thane': 1}
Show solution and explanation 
cities = ["Pune", "Mumbai", "Pune", "Thane", "Mumbai", "Mumbai"]
counts = {}
for c in cities:
    counts[c] = counts.get(c, 0) + 1
print(counts)
{'Pune': 2, 'Mumbai': 3, 'Thane': 1}

How it works: Uneven counts reveal a poor partition key.

P4Medium

Skew ratio

Given rows per shard, print the skew (largest ÷ average) and whether it is above 1.5.

Input
[120, 95, 300, 110]
Expected output
1.92 unbalanced
Show solution and explanation 
rows = [120, 95, 300, 110]
skew = max(rows) / (sum(rows) / len(rows))
print(round(skew, 2), "unbalanced" if skew > 1.5 else "ok")
1.92 unbalanced

How it works: A skew of 1.0 is perfect; large values mean one shard does most of the work.

P5Medium

Scatter-gather merge

Each shard returns its top-2 orders by amount. Merge them into the global top-3.

Input
3 shards
Expected output
[('O5', 990), ('O1', 900), ('O3', 880)]
Show solution and explanation 
shard_results = [[("O1", 900), ("O7", 650)], [("O3", 880), ("O9", 300)], [("O5", 990), ("O2", 410)]]
merged = sorted([r for res in shard_results for r in res], key=lambda r: -r[1])
print(merged[:3])
[('O5', 990), ('O1', 900), ('O3', 880)]

How it works: The router combines partial answers; each shard only needs to send its own top results.

P6Advanced

Keys moved with mod-N

For numeric ids 1–1000, print how many change shard when going from 5 to 6 shards with id % N.

Input
ids 1–1000
Expected output
831 of 1000 move
Show solution and explanation 
moved = sum(1 for i in range(1, 1001) if i % 5 != i % 6)
print(moved, "of 1000 move")
831 of 1000 move

How it works: Most keys move, which is why systems prefer consistent hashing or fixed logical partitions.

P7Advanced

Logical to physical shards

1,024 logical shards are spread over 4 servers; one server is added. Move whole logical shards so all 5 servers have nearly equal counts, and print how many logical shards moved.

Input
1024 logical, 4 → 5 servers
Expected output
target per server: [205, 205, 205, 205, 204]
logical shards moved: 204 (20%)
Show solution and explanation 
logical = 1024
before = [logical // 4] * 4
target = [logical // 5 + (1 if i < logical % 5 else 0) for i in range(5)]
moved = sum(max(0, b - t) for b, t in zip(before, target[:4]))
print("target per server:", target)
print("logical shards moved:", moved, f"({moved / logical:.0%})")
target per server: [205, 205, 205, 205, 204] logical shards moved: 204 (20%)

How it works: With many small logical shards, growth moves only the minimum amount of data: about one fifth here.

P8Business problem

Kafka partitions for throughput

A topic must handle 60 MB/s at peak. One consumer processes 4 MB/s. Plan 50% headroom. How many partitions (and consumers) are needed?

Input
60 MB/s, 4 MB/s per consumer, +50%
Expected output
23 partitions
Show solution and explanation 
import math
print(math.ceil(60 * 1.5 / 4), "partitions")
23 partitions

How it works: Each partition is read by at most one consumer in a group, so partitions set the maximum parallelism.

P9Business problem

Shards for a growing table

The orders table is 6 TB and grows 250 GB a month. Each shard server should hold at most 2 TB. How many shards are needed now and in 2 years?

Input
6 TB, +250 GB/month, 2 TB per shard
Expected output
now: 3 shards | in 2 years: 6 shards
Show solution and explanation 
import math
now = 6
later = now + 0.25 * 24
print("now:", math.ceil(now / 2), "shards | in 2 years:", math.ceil(later / 2), "shards")
now: 3 shards | in 2 years: 6 shards

How it works: Plan the shard count (and the rebalancing method) for growth, not just for today.

Real-world scenario questions (asked in company interviews)

Partitioning decisions from real systems and interviews. Decide your answer first, then open the model answer.

System design · partitioningFresher

Choose a shard key for a chat app

A chat app stores messages. The main screens are “messages in this conversation, newest first” and “my conversations”. Messages reach crores per day. How would you partition the messages table?

The interviewer is checking: can you choose a key from the access pattern and spot hotspots?

Show a strong answer

Partition by conversation_id (all messages of a chat together, so one query reads one partition), clustered by time descending. Bound partition size for huge group chats by adding a time bucket: (conversation_id, month). Keep “my conversations” in a separate table partitioned by user_id. Avoid partitioning by date (write hotspot) or by user for messages (a conversation would span many partitions).

Avoid: picking a key without saying which queries it serves.

Operations · rebalancing1–3 years

We need to go from 8 to 12 shards

A sharded MySQL setup uses user_id % 8. Growth means you need 12 shards. How do you migrate safely?

The interviewer is checking: do you understand the cost of mod-N resharding and safe migration steps?

Show a strong answer
  1. Recognise that changing the modulus moves most users. Consider moving to a directory-based or consistent-hash scheme, or to many logical shards (for example 1,024) mapped onto physical servers, so future growth moves whole logical shards.
  2. Copy data to the new layout in the background, then dual-write new changes to old and new locations.
  3. Verify counts and checksums per user range.
  4. Switch reads gradually, then writes; keep a rollback path.
  5. Finally, clean up the old copies.

Avoid: changing the modulus in production and copying everything in one big bang.

Streaming · Kafka1–3 years

Order events are processed out of order

Consumers sometimes process “order delivered” before “order placed” for the same order. The topic has 12 partitions and producers don’t set a message key.

The interviewer is checking: do you know how Kafka partitioning affects ordering?

Show a strong answer

Without a key, messages are spread across partitions, and Kafka guarantees order only within one partition. Set the message key to order_id so all events for an order go to the same partition and are consumed in order by one consumer. Choose enough partitions for the needed parallelism, and watch for hot keys. Changing partition count later remaps keys, so plan it up front.

Avoid: adding a sleep in consumers or using a single partition for everything.

Fundamentals · interviewFresher

“What is the difference between partitioning and replication?”

Interviewers often ask this to check basic distributed-systems vocabulary.

The interviewer is checking: can you separate splitting data from copying data?

Show a strong answer

Partitioning (sharding) splits data into parts so each node stores and processes only a subset; it increases capacity and throughput. Replication stores copies of the same data on several nodes; it increases availability, durability and read capacity. Real systems use both: each partition is replicated (for example HDFS blocks with 3 replicas, Kafka partitions with a replication factor, Cassandra partitions on several nodes).

Avoid: using the two words as if they mean the same thing.
