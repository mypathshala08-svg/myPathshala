Scaling up vs scaling out (and back-of-envelope estimation)

2 Definition

Scalability and back-of-envelope estimation

Formal definition (write this in exams)

Scalability is the ability of a system to handle increasing load by adding resources while maintaining acceptable performance. Vertical scaling (scaling up) increases the capacity of a single machine; horizontal scaling (scaling out) adds more machines and distributes load among them, typically behind a load balancer. A back-of-envelope estimate is a quick, approximate calculation of load, storage, bandwidth and machine count using rounded numbers and explicit assumptions, used to judge the feasibility and scale of a design.

In simple words

Scaling means keeping a system fast as more people use it. You can buy a bigger machine (scale up) or add more machines (scale out). A back-of-envelope estimate is quick, rough arithmetic with round numbers that tells you roughly how big the system must be.

Scaling and estimation at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A bigger jug or more stalls

  • Scaling up (vertical): the lemonade stall buys a bigger jug and a faster juicer. Simple, but there is a biggest jug, and if the one stall closes, nobody gets lemonade.
  • Scaling out (horizontal): open more stalls and send customers to whichever is free. Needs a person at the gate (a load balancer), but you can keep adding stalls.
  • Estimation recipe: (1) how many things per day, (2) divide by about 1 lakh seconds for “per second”, (3) multiply by a peak factor, (4) multiply by size for storage, (5) divide by what one machine handles for machine count.

Handy facts: a day has 86,400 seconds, call it 1 lakh. 1 crore = 107. 1 KB × 1 crore ≈ 10 GB.

Intermediate Stateless services, load balancers and autoscaling

  • Stateless vs stateful: a stateless service keeps nothing between requests (any server can answer any request), so it scales out by adding copies. A stateful one (a database, a cache, a session held in memory) must split or copy its data first, which is much harder.
  • Move state out: keep sessions in Redis and data in databases, so web and API servers stay stateless.
  • Load balancer: spreads requests across servers (round robin, least connections) and stops sending traffic to unhealthy ones.
  • Scaling databases: read replicas for read-heavy traffic, then sharding (splitting data across machines, Lesson 3.2) when writes outgrow one machine.
  • Autoscaling: add or remove machines based on a metric (CPU above 60%, queue length, requests per second), with a minimum and maximum. Scale up early for known peaks; new machines take minutes to start.
  • Headroom: plan to run at 50–70% of capacity, so a spike or a failed machine doesn’t push you over the edge.

Advanced Why scaling out has limits

  • Universal Scalability Law (Neil Gunther): throughput with N machines ≈ N ÷ (1 + α(N−1) + βN(N−1)). α is contention (waiting for a shared resource, like Amdahl’s serial part); β is coherence (machines talking to each other to stay in agreement). With β > 0, adding machines beyond a point reduces throughput.
  • Little’s law: items in the system = arrival rate × time each spends inside (L = λW). At 5,000 requests/s and 200 ms each, about 1,000 requests are in flight at any moment, which sizes thread pools and connections.
  • Tail latency at scale: if one request fans out to 100 servers and each is slow 1% of the time, 1 − 0.99100 ≈ 63% of requests hit at least one slow server. Large systems watch p99 latency, not the average.
  • Cost per unit: measure cost per thousand orders, not just total cost; good scaling keeps it flat or falling as volume grows.

Exam tip: For “vertical vs horizontal scaling”, give the definition, a comparison table (cost, limit, failure impact, complexity, examples) and one example each (a bigger database server; adding web servers behind a load balancer). For estimation questions, always write your assumptions first, then show each step with units.

3 Types and ways to use it

Four ways to scale

Vertical (scale up)

Bigger CPU, more RAM, faster disks on one machine. No code changes. Hits a ceiling; single point of failure.

Bigger machine

Horizontal (scale out)

More identical machines behind a load balancer. Near-linear growth for stateless work; needs distributed design for data.

More machines

Diagonal

Scale up each node to a sensible size, then scale out with many of them. What most real clusters do.

Both

Elastic (autoscaling)

The number of machines follows demand automatically: more at 8 pm on Diwali, fewer at 4 am.

4 Step by step

A complete estimate for 10 crore orders a day

  1. Write your assumptions

    10 crore orders on Diwali day · peak hour is 5× the average · each order record ≈ 1 KB · one API server handles ≈ 400 orders/s (from a load test) · keep 3 copies of data.

    Assumptions first, out loud. If one is wrong, the interviewer (or your manager) can correct it and the rest of the calculation still stands.

  2. Orders per second, average and peak

    orders_per_day = 10_00_00_000          # 10 crore
avg_per_s = orders_per_day / 1_00_000    # ~1 lakh seconds in a day
peak_per_s = avg_per_s * 5               # Diwali dinner peak
print("average:", avg_per_s, "orders/s | peak:", peak_per_s, "orders/s")
    average: 1000.0 orders/s | peak: 5000.0 orders/s
    Dividing by about 1 lakh seconds turns “per day” into “per second”. Systems must handle the peak, not the average.

  3. Storage per day and per year

    orders_per_day = 10_00_00_000
kb_per_order = 1
gb_per_day = orders_per_day * kb_per_order / 1024 / 1024
tb_per_year = gb_per_day * 365 / 1024
print(f"{gb_per_day:.0f} GB/day, {tb_per_year:.0f} TB/year, {tb_per_year * 3:.0f} TB with 3 copies")
    95 GB/day, 34 TB/year, 102 TB with 3 copies
    About 95 GB a day is manageable; the yearly total with copies, around 100 TB, is what drives cost. Add indexes, logs and events and the real figure is several times larger.

  4. Servers at the peak

    peak_per_s = 5000
per_node = 400            # orders/s one API server can handle (measured)
target_load = 0.6         # keep 40% headroom
import math
print("API servers at peak:", math.ceil(peak_per_s / (per_node * target_load)))
    API servers at peak: 21
    Divide the peak by what one server handles at the target load. The API tier is stateless, so these servers scale out behind a load balancer.

  5. Network bandwidth

    peak_per_s, kb = 5000, 1
mb_per_s = peak_per_s * kb / 1024
print(f"incoming: {mb_per_s:.1f} MB/s = {mb_per_s * 8:.0f} Mbps")
    incoming: 4.9 MB/s = 39 Mbps
    Order data alone is small for the network. Images, app events and replication traffic usually dominate bandwidth, so estimate them separately.

  6. Concurrency with Little’s law

    arrival = 5000          # requests per second
time_inside = 0.2       # seconds each request spends in the system
print("requests in flight:", int(arrival * time_inside))
    requests in flight: 1000
    At the peak about 1,000 requests are in progress at once. That sizes database connection pools and thread counts: too few and requests queue, too many and the database is overwhelmed.

6 Real-world use

Real-time scenarios: scaling in practice

Three live scenarios: a two-minute capacity estimate, a cart that vanishes when servers are added, and an advanced look at why more machines can mean less speed.

Real-time scenario 1

Estimating Diwali day in two minutes

Watch Kabir answer the interview question line by line. Every step is simple arithmetic with round numbers; the skill is the order of the steps and writing down the assumptions.

The estimation recipe 5 steps
Animated example
  1. Write the given number: 10 crore orders on the day.
  2. Divide by about 1 lakh seconds: around 1,000 orders per second on average, and about 5,000 per second at the dinner peak.
  3. Multiply by the record size: at 1 KB per order, about 95 GB a day.
  4. Over a year, with three copies for safety, that is roughly 100 TB, which tells you storage is a cost to plan for.
  5. Servers: 5,000 per second ÷ (400 per server × 60% target load) ≈ 21 API servers at peak. Say the assumptions aloud so they can be challenged.
Real-time scenario 2

Why Riya’s cart vanished when we added servers

Scaling out is easy only for stateless services. Watch what happens to a cart stored in a server’s memory when a second and third server are added.

Stateful vs stateless 5 steps
Animated example
  1. With one server, keeping Riya’s cart in that server’s memory works perfectly.
  2. Two more servers are added. The load balancer sends her next tap to API 2, which has no idea what is in her cart. The cart appears empty.
  3. A quick fix is sticky sessions: always route Riya to API 1. But if API 1 restarts, the cart is lost, and some servers end up much busier than others.
  4. The real fix is to move the state out: carts live in Redis, so every API server is stateless and any server can handle any request.
  5. Now scaling out is simply adding identical copies, and servers can be replaced or removed at any time without losing anything.
Real-time scenario 3 · advanced

When 64 machines are slower than 32

Adding machines is not free: they wait for shared resources and must talk to each other to stay in agreement. The Universal Scalability Law shows the effect. Watch throughput as a job grows from 8 to 64 nodes.

Universal Scalability Law 5 steps
Animated example
  1. With 8 nodes the job runs about 6.4 times faster than on one node. Some time is lost waiting for shared resources such as one database or one lock: contention.
  2. With 16 nodes, about 10 times faster. Each extra node adds less than the one before.
  3. Around 32 nodes the curve peaks near 12×. The nodes now spend a lot of time exchanging messages to stay consistent.
  4. With 64 nodes throughput falls to about 10×: slower than 32. The cost of every node coordinating with every other node grows faster than the work added: coherence.
  5. The fix is design, not hardware: partition data so nodes work independently, remove global locks, batch messages and avoid chatty synchronisation. (Curve uses α = 0.03, β = 0.0008 for illustration.)

Scaling decisions at real companies

1. Sale days and cricket finals: pre-scaling

Shopping and streaming apps scale out days in advance of known peaks (festive sales, IPL finals), run load tests at several times the expected traffic, and keep autoscaling as a safety net.

Forecast peak→Load test + pre-scale→Autoscale on the day

2. Databases: scale up, add replicas, then shard

A start-up’s single PostgreSQL server is first moved to a larger machine, then given read replicas for reports, and only when writes outgrow it is the data sharded or moved to a distributed database.

Bigger DB→Read replicas→Sharding

3. Spark clusters that grow per job

Data platforms start a cluster for a nightly job, let it autoscale from a few nodes to dozens while the heavy step runs, and shut it down afterwards, because storage lives separately in object storage.

Job starts→Autoscale workers→Cluster shuts down

4. System-design interviews

Most data and backend interviews include an estimation step: users, requests per second, storage per year, bandwidth and machine count, with stated assumptions. The method matters more than the exact number.

Assumptions→Round-number maths→Design choices

Run it on your PC: an estimate calibrated by your own CPU

Good estimates start from a measurement. This program first measures how many order events one core of your computer can parse and validate in a second, then uses that number to estimate the cores, nodes and storage needed for 10 crore orders a day. Only the standard library is used. Save it as capacity_estimator.py and run it.

Measure, then estimate

"""Back-of-envelope capacity plan, calibrated with a real measurement on your PC.
Step 1 measures how many order events one CPU core can parse and validate per second.
Step 2 uses that number to estimate the machines needed for a festival peak."""
import json, math, time

# ---- assumptions (change these)
ORDERS_PER_DAY = 10_00_00_000      # 10 crore orders a day
PEAK_FACTOR = 5                     # peak hour is 5x the average rate
EVENTS_PER_ORDER = 20               # clicks, status updates, pings per order
BYTES_PER_EVENT = 500
CORES_PER_NODE = 16
HEADROOM = 0.6                      # run nodes at 60% so spikes and failures are absorbed

def inr(x):
    """Indian digit grouping: 115741 -> 1,15,741"""
    s = str(round(x))
    head, tail = s[:-3], s[-3:]
    while len(head) > 2:
        tail = head[-2:] + "," + tail
        head = head[:-2]
    return (head + "," + tail) if head else tail


# ---- step 1: measure one core
event = json.dumps({"order_id": "O1043", "user": "U9", "city": "Pune", "amount": 420,
                    "items": [{"dish": "thali", "qty": 1}, {"dish": "lassi", "qty": 2}], "ts": 1792411000})
n, start = 0, time.perf_counter()
while time.perf_counter() - start < 1.0:
    e = json.loads(event)
    ok = e["amount"] > 0 and e["city"] and len(e["items"]) > 0
    n += 1
per_core = n / (time.perf_counter() - start)
print(f"Measured: one core parses and checks about {inr(per_core)} events per second")

# ---- step 2: estimate
events_day = ORDERS_PER_DAY * EVENTS_PER_ORDER
avg_eps = events_day / 86_400
peak_eps = avg_eps * PEAK_FACTOR
cores = peak_eps / (per_core * HEADROOM)
nodes = math.ceil(cores / CORES_PER_NODE)
storage_tb_day = events_day * BYTES_PER_EVENT / 1024**4

print(f"\nEvents per day      : {events_day / 1e7:.0f} crore")
print(f"Average events / s  : {inr(avg_eps)}")
print(f"Peak events / s     : {inr(peak_eps)}")
print(f"Cores needed at peak: {cores:.1f}  (at {HEADROOM:.0%} target load)")
print(f"Nodes ({CORES_PER_NODE} cores each): {nodes}")
print(f"Raw event storage   : {storage_tb_day:.2f} TB per day, {storage_tb_day * 365:.0f} TB per year")
print("\nReal services do far more work per event (network, database, logging),")
print("so production capacity is usually 10-100x higher than this lower bound.")

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.1 in one screen

  • Scale up = bigger machine (simple, ceiling, single point of failure). Scale out = more machines + load balancer.
  • Stateless tiers scale out by adding copies; move state to Redis/databases. Databases: scale up → read replicas → shard.
  • Autoscale on CPU/queue/RPS with min and max; pre-scale for known peaks; keep 30–50% headroom.
  • Estimation recipe: per day → ÷ 1 lakh → × peak factor → × size → ÷ per-machine capacity. State assumptions.
  • Handy: 1 crore × 1 KB ≈ 10 GB; 1 Gbps ≈ 125 MB/s; 1 year ≈ 3 crore seconds.
  • Little's law: L = λW. USL: contention (α) and coherence (β) limit scaling.
  • Fan-out amplifies tail latency: 1 − (1 − p)N. Watch p99, not the average.

Interview and viva questions

Differentiate vertical and horizontal scaling.

Vertical scaling adds resources (CPU, RAM, disk) to a single machine; it is simple and needs no code changes, but cost rises steeply, there is a hard upper limit and the machine remains a single point of failure. Horizontal scaling adds more machines and spreads the load with a load balancer or data partitioning; it scales much further and tolerates failures, but requires stateless services or distributed data design. Real systems usually combine both.

What is a back-of-envelope estimation and why is it useful?

A quick calculation using rounded numbers and stated assumptions to estimate load (requests per second), storage, bandwidth and machine count. It shows early whether a design is feasible, which resource is likely to be the bottleneck and roughly what it will cost, before any detailed work. It is a standard part of system-design interviews.

How do you scale a database?

First optimise queries and indexes and scale the server up to a sensible size. Add caching for hot reads and read replicas for read-heavy workloads. When writes or data size outgrow one machine, partition (shard) the data across servers by a key, or move to a distributed database designed for horizontal scaling.

What is autoscaling?

Automatically adjusting the number of running instances based on metrics such as CPU utilisation, request rate or queue length, within configured minimum and maximum limits. It keeps performance steady during peaks and saves cost during quiet periods; for predictable peaks, teams schedule scale-ups in advance because new instances take time to start.

Why doesn't doubling the machines always halve the time?

Because part of the work can't be parallelised (Amdahl's law), machines wait on shared resources (contention), and they must communicate and coordinate (coherence), which grows with the number of machines. The Universal Scalability Law models these effects; beyond an optimal size, adding machines can even reduce throughput.

95 GB

How it works: KB ÷ 1024 = MB, ÷ 1024 again = GB.

P7Advanced

Slow pages from fan-out

A search page queries 40 shards in parallel; each shard is slow 0.5% of the time. What percentage of pages are slow?

Input
40 shards, 0.5%
Expected output
18.2 %
Show solution and explanation 
print(round((1 - (1 - 0.005) ** 40) * 100, 1), "%")

Autoscaling vs fixed fleet

Peak needs 40 servers for 4 hours a day; the other 20 hours need 10. A server costs Rs 30 per hour. Compare the daily cost of a fixed 40-server fleet with autoscaling.

Show solution and explanation

Real-world scenario questions (asked in company interviews)

Scaling and estimation questions from interviews and production incidents. Decide your answer first, then open the model answer.

System design · estimationFresher

Estimate storage for a photo feature

A food app will let users attach up to 2 photos to each review. 50 lakh reviews are written a day and 20% include photos. Estimate storage per year.

The interviewer is checking: can you structure an estimate with clear assumptions and units?

Show a strong answer

Assume 1.5 photos per review that has photos, 3 MB per photo, plus 2 thumbnails of 100 KB. Photos per day = 50 lakh × 20% × 1.5 = 15 lakh. Storage per day ≈ 15 lakh × 3.2 MB ≈ 4.6 TB. Per year ≈ 1.7 PB before replication (object storage handles durability internally). Then discuss: compress or resize images, move old photos to cheaper tiers, serve through a CDN.

Avoid: jumping to a number without assumptions, or forgetting thumbnails and tiers.

Scaling · architecture1–3 years

The API is slow at 8 pm every day

A delivery app’s API slows down every evening. Adding more API servers didn’t help.

The interviewer is checking: do you find the real bottleneck before scaling?

Show a strong answer
  1. Check where time goes: API CPU, database CPU and connections, cache hit ratio, external calls.
  2. If the database is the bottleneck, more API servers just add more database connections and make it worse.
  3. Fixes: cache hot reads, add read replicas, tune slow queries and indexes, pool connections, scale the database up; shard if writes are the limit.
  4. Then autoscale the stateless tier with a sensible maximum.

Avoid: adding servers blindly; scaling the wrong tier.

Reliability · statelessness1–3 years

Users get logged out randomly

After moving from one server to five behind a load balancer, users complain of random logouts and empty carts.

The interviewer is checking: do you recognise in-memory session state?

Show a strong answer

Sessions and carts are stored in each server’s memory, so requests landing on another server don’t find them. Move session state to a shared store (Redis) or use signed tokens (JWT) for authentication, and store carts in Redis or the database. Avoid relying on sticky sessions, which break when servers restart and unbalance load.

Avoid: increasing session timeouts or pinning all users to one server.

Performance · advanced3+ years

Doubling the cluster made the job slower

A distributed job ran in 40 minutes on 50 nodes. On 100 nodes it took 55 minutes.

The interviewer is checking: do you understand contention and coordination costs?

Show a strong answer

Look for shared bottlenecks (one metadata service, one database, a global lock, a single reducer) and coordination overhead (shuffles that grow with node count, many small tasks, frequent synchronisation). Measure stage by stage. Fixes include fewer, larger partitions, reducing shuffles (broadcast small tables, pre-partition data), removing global locks, and choosing the node count near the measured optimum rather than “as many as possible”.

Avoid: assuming linear scaling and adding even more nodes.
