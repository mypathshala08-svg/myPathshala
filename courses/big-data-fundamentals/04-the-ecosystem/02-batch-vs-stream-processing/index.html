Batch vs stream processing: now or later?

Your live score updates within a second of every ball; tomorrow's newspaper has the full scorecard. Both come from the same data, processed in two different ways. This lesson shows when to use batch and when to use stream processing, how windows turn an endless stream into answers, and how real systems deal with events that arrive late.

2 Definition

What are batch and stream processing?

Formal definition (write this in exams)

Batch processing processes a bounded, finite set of data that has been collected over a period, usually on a schedule, producing results with high throughput but high latency (minutes to hours). Stream processing processes unbounded data continuously, event by event (or in very small micro-batches) as it arrives, producing results with low latency (milliseconds to seconds). Stream processors typically group events into windows and keep state between events.

In simple words

Batch: collect everything first, then process it in one go, like doing a week's laundry on Sunday. Stream: process each item the moment it arrives, like washing each cup as soon as you finish your tea.

Words you'll meet in this lesson

Bounded dataData with a start and an end: yesterday's orders, last month's payments.
Unbounded dataData that never ends: clicks, payments, GPS pings, sensor readings.
LatencyHow long after an event its result is available.
ThroughputHow many events are processed per second.
WindowA slice of a stream to calculate over: “runs in this over”, “orders in the last 5 minutes”.
StateWhat a stream processor remembers between events: running totals, recent payments of a card.
Event timeWhen something actually happened (the ball was bowled).
Processing timeWhen the system received or processed it, which can be later.
Micro-batchProcessing a stream in tiny batches every few seconds, as Spark Structured Streaming does by default.

Batch and stream at a glance

BatchBounded data · scheduled (hourly, nightly) · latency minutes–hours · simpler, cheaper, easy to re-run · Spark, Hive, MapReduce, dbt
StreamUnbounded data · always running · latency milliseconds–seconds · needs state, windows, late-data handling · Flink, Kafka Streams, Spark Structured Streaming

Batch vs stream at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Bucket vs tap

Batch is filling a bucket and carrying it once: efficient, but you wait. Stream is drinking straight from the tap: instant, but the tap must always be running.

  • Batch examples: salary credited on the 1st, electricity bill each month, college result after all papers are checked, the morning sales report.
  • Stream examples: live cricket score, UPI fraud check before money leaves, OTP delivery, a cab's live location on the map.

The one question: how old can the answer be before it is useless? Seconds → stream. Hours or days → batch.

Intermediate Latency, throughput and windows

  • Trade-off: batch maximises throughput and simplicity; stream minimises latency but runs 24×7 and is harder to build and test.
  • Windows turn an endless stream into finite groups: tumbling (fixed, non-overlapping: runs per over), sliding (overlapping: orders in the last 5 minutes, updated every minute) and session (a user's activity until a 30-minute gap).
  • Event time vs processing time: a payment made at 10:00:00 may reach the system at 10:00:05, or later. Correct results group by event time.
  • Micro-batch vs true streaming: Spark Structured Streaming processes small batches every few seconds (or less); Flink processes each event as it arrives. Both are “streaming” for most business needs.
  • Tools: batch with Spark/Hive/dbt scheduled by Airflow; streams with Kafka plus Flink, Kafka Streams or Spark Structured Streaming.

Advanced Late data, guarantees and state

  • Out-of-order and late events are normal (phones offline, network retries). A watermark tells the processor “I believe all events up to time T have arrived”; windows close at the watermark, and an allowed lateness policy decides what happens to events that come after: update the result, send to a side output, or drop.
  • Delivery guarantees: at-most-once (may lose events), at-least-once (may duplicate), exactly-once (each event affects the result once), achieved with checkpointed state plus idempotent or transactional sinks.
  • State and checkpoints: running totals and per-card histories live in a state store that is periodically checkpointed, so a crashed job resumes without losing or double-counting.
  • Backpressure: when a downstream step is slow, the stream must slow the input instead of running out of memory.
  • Reprocessing: fixing a bug in a stream job means replaying old events from Kafka or the lake. This leads directly to the Lambda and Kappa architectures (Lesson 4.4).

  2. Over 2, ball 2: wicket. The score becomes 10/1 instantly.
  3. End of over 2: the app shows 10 runs this over.

Behind the screen
  1. The ball event enters Kafka. The stream processor updates its state (total = 6) and pushes the new score to phones in under half a second.
  2. For the wicket, only the wickets counter changes. A stream processor keeps a few numbers of state, not the whole match.

Real-time scenarios where the choice matters

Real-time scenario 1

A stolen phone: stream stops it, batch reports it

Real-time scenario 2

One timeline, three windows

The same food orders from one office building between 13:00 and 13:40. Watch how tumbling, sliding and session windows group them differently, and why each answers a different business question.

Tumbling, sliding, session 5 steps
Animated example
  1. The events: ten orders from one building between 13:00 and 13:40, bunched at lunch with a gap afterwards.
  2. Tumbling: fixed 10-minute buckets that never overlap. Each order is counted once: 4, 4, 0 and 2.

Real-time scenario 3 · Advanced

The order from the tunnel: late data and watermarks

A passenger on a local train orders food at 18:58, just as the train enters a tunnel. The phone stays offline for 4 minutes and the event reaches the system at 19:02. Which minute should it count in, and how long should the system wait?

Event time, processing time, watermark 5 steps
Animated example
  1. 18:58: the passenger orders in the tunnel. The phone can't send the event yet.
  2. 19:02: the event arrives. Its event time is 18:58 but its processing time is 19:02. Grouping by processing time would put it in the wrong window.
  3. The stream processor uses a watermark: the latest event time seen minus an allowed delay (here 3 minutes). The 18:55–19:00 window stays open until the watermark passes 19:00.
  4. The late event arrived before the watermark, so it is counted in the correct window: 4 orders, not 3. The price is a result published a few minutes later.
  5. Every streaming system chooses a balance between speed and completeness, and decides what to do with events that arrive after the watermark.

Which one do real companies use?

1. Stock market: stream

Price ticks arrive many times per second. Trading platforms update charts, trigger stop-loss orders and run risk checks on the stream. End-of-day settlement and tax reports are batch.

Price ticks→Stream: alerts, stop-loss→Batch: EOD reports

2. Payroll: batch

Salaries are computed once a month from attendance, leave and tax data. Nobody needs them every second; correctness and an audit trail matter far more. A scheduled batch job is the right tool.

Monthly attendance→Batch job on the 28th→Salary on the 1st

3. Factory sensors: stream

Machines report temperature and vibration every second. A stream job raises an alert when readings stay above a limit for 30 seconds, before a breakdown. Weekly maintenance planning runs as batch on the same data.

Sensor readings→Sliding-window alert→Stop the machine

4. Live streaming apps: both

The “watching now” counter and buffering alerts come from a stream of player heartbeats. Royalty payments and next-day “top shows” lists come from batch jobs over the complete data.

Player heartbeats→Stream counter + batch reports→Live number + reports

5. Online ads: stream for spend, batch for bills

Click events are streamed so a campaign stops spending the moment its daily budget is used. Advertisers' monthly invoices are computed in batch after de-duplicating and removing fraudulent clicks.

Ad clicks→Stream: budget cap · Batch: invoice→Accurate bill

Examples are simplified; real systems combine both styles. Rules and numbers shown are illustrative.

The same orders, processed two ways

Six orders arrive during the day. The stream job updates its answer with every event; the batch job waits for the complete list and answers once. Compare when each answer is available. Then try windows, a fraud rule, late events and duplicates in the challenges.

orders = [  # (minute, kitchen, amount)
    (1, "K12", 120), (1, "K11", 90), (2, "K12", 250),
    (3, "K12", 180), (3, "K13", 60), (4, "K12", 140),
]

# STREAM: update the answer as each event arrives
def stream_job(events):
    total = 0
    for minute, kitchen, amount in events:
        total = total + amount
        print(f"[stream  @ minute {minute}] +{amount:>3} from {kitchen} -> running total Rs {total}")

# BATCH: wait until all data is collected, then process it in one go
def batch_job(all_orders):
    total = sum(amount for _, _, amount in all_orders)
    busiest = max(set(k for _, k, _ in all_orders),
                  key=lambda k: sum(a for _, kk, a in all_orders if kk == k))
    print(f"[batch   @ end of day] {len(all_orders)} orders, Rs {total}, busiest kitchen {busiest}")

Run it on your PC: a live score stream in your terminal

This program generates a “live” ball every 0.3 seconds and processes it as a stream: the score updates immediately, and a 6-ball tumbling window closes at the end of every over. After the last ball it prints a batch summary computed from the complete data. Save it as live_score.py and watch it scroll.

Watch a stream being processed

import random, time

random.seed(27)
OUTCOMES = [0, 0, 1, 1, 1, 2, 4, 6, "W"]


def ball_stream(overs=3):
    """An endless-looking stream of balls, one every 0.3 s (sped up)."""
    for over in range(1, overs + 1):
        for ball in range(1, 7):
            time.sleep(0.3)
            yield over, ball, random.choice(OUTCOMES)


# STREAM processing: update the answer the moment each ball arrives
total, wickets, over_runs, per_over = 0, 0, 0, []
start = time.time()
for over, ball, result in ball_stream():
    if result == "W":
        wickets += 1
    else:
        total += result
        over_runs += result
    print(f"{time.time() - start:4.1f}s  ball {over - 1}.{ball}  {str(result):>2}   score {total}/{wickets}")
    if ball == 6:                       # the "over" window closes
        print(f"        --- over {over}: {over_runs} runs ---")
        per_over.append(over_runs)
        over_runs = 0

# BATCH processing: after the match, compute from the complete data
print("Batch summary after the match:", per_over, "| run rate", round(total / len(per_over), 2))

Quick revision

Lesson 4.2 in one screen

  • Batch: bounded data, scheduled, high latency, high throughput, simpler. Stream: unbounded, continuous, low latency, needs state.
  • Decide by: how old can the answer be before it is useless?
  • Windows: tumbling (fixed, no overlap) · sliding (overlapping, recent) · session (ends after a gap).

  • Watermark = how long to wait for late events; a trade-off between speed and completeness.
  • Guarantees: at-most-once (loss), at-least-once (duplicates), exactly-once (neither).

Interview and viva questions

Differentiate batch processing and stream processing.

Batch processes a bounded dataset collected over time, on a schedule, with high throughput and latency of minutes to hours (daily reports, billing, model training). Stream processing handles unbounded data continuously as events arrive, with latency of milliseconds to seconds, keeping state and using windows (fraud detection, live dashboards, alerts). Batch is simpler and cheaper; stream is faster but harder to build and operate.

What are windows in stream processing? Explain their types.

Windows divide an endless stream into finite groups for calculation. Tumbling windows are fixed-size and non-overlapping (orders per minute). Sliding windows are fixed-size but overlap, moving forward in small steps (payments in the last 5 minutes, every 30 seconds). Session windows grow with activity and close after a gap of inactivity (a user's visit).

What is the difference between event time and processing time?

Event time is when an event actually occurred, recorded at the source. Processing time is when the system processes it. Network delays and offline devices make them differ, so correct aggregations group by event time and use watermarks to handle late events.

What is a watermark?

A watermark is the stream processor's estimate that all events up to a certain event time have arrived, usually the maximum event time seen minus an allowed delay. When the watermark passes the end of a window, the window is finalised; events arriving later are handled by an allowed-lateness policy.

What is micro-batching?

Processing a stream as a series of very small batches, every few seconds or less, as Spark Structured Streaming does by default. It reuses batch machinery and gives good throughput with near-real-time latency; event-at-a-time engines like Flink can reach lower latency.

Click times are given in minutes. A session ends after a gap of more than 20 minutes. Print the number of sessions.

Input
[0, 5, 8, 40, 42, 90]
Expected output
Sessions: 3
Show solution and explanation 
clicks = [0, 5, 8, 40, 42, 90]
sessions = 1
for prev, cur in zip(clicks, clicks[1:]):
    if cur - prev > 20:
        sessions = sessions + 1
print("Sessions:", sessions)
Sessions: 3

How it works: Each gap larger than the limit starts a new session window.

P7Advanced

At-least-once to exactly-once

The same event ids may be delivered more than once. Print the number of unique events and how many duplicates were dropped.

Input
[e1, e2, e2, e3, e1, e4]
Expected output
Unique: 4 | duplicates dropped: 2
Show solution and explanation 
events = ["e1", "e2", "e2", "e3", "e1", "e4"]
unique = []
for e in events:
    if e not in unique:
        unique.append(e)
print("Unique:", len(unique), "| duplicates dropped:", len(events) - len(unique))
Unique: 4 | duplicates dropped: 2

How it works: De-duplicating by a unique id turns at-least-once delivery into exactly-once results.

P8Business problem

Always-on stream vs nightly batch

A stream job needs 4 nodes running 24 hours a day; a nightly batch needs 20 nodes for 2 hours. A node costs Rs 30 per hour. Print the monthly (30-day) cost of each (illustrative).

Input
Rs 30/node-hour
Expected output
Stream: Rs 86400
Batch : Rs 36000
Show solution and explanation 
stream = 4 * 24 * 30 * 30
batch = 20 * 2 * 30 * 30
print("Stream: Rs", stream)
print("Batch : Rs", batch)
Stream: Rs 86400 Batch : Rs 36000

How it works: Streams cost money every hour. Pay for real time only where it creates real value.

P9Business problem

Did we meet the 1-second promise?

The bank promises a fraud decision within 1,000 ms. Given decision times, print the percentage that met the promise.

Input
[80, 95, 120, 1500, 70, 90, 2100, 85]
Expected output
75 % within 1 second
Show solution and explanation 
times_ms = [80, 95, 120, 1500, 70, 90, 2100, 85]
ok = sum(1 for t in times_ms if t <= 1000)
print(round(ok / len(times_ms) * 100), "% within 1 second")
75 % within 1 second

How it works: Streaming systems are judged by latency targets (SLAs), usually measured as percentages like this.

Real-world scenario questions (asked in company interviews)

Situations where choosing batch or stream, or handling time correctly, is the real test. Decide your answer first, then open the model answer.

Retail · requirementsFresher

“Make the daily sales report real-time”

A store manager asks for the daily sales report, which is read once each morning, to be built on Kafka and Flink “because real-time is modern”.

The interviewer is checking: do you choose based on the business need, not on fashion?

Show a strong answer

Ask how the report is used. If it is read once at 9 am, an answer at 6 am is as good as one at 8:59:59. A nightly batch job is cheaper, simpler to test and easy to re-run.

  • If the manager actually needs intraday decisions (restocking during a sale), offer an hourly batch or a small live counter for just that metric.
  • Keep stream processing for cases where a late answer loses money or customers.

Avoid: building a 24×7 streaming system for a report nobody reads in real time.

Fintech · fraud1–3 years

Fraud is found the next morning

A wallet company's fraud report runs every night. Losses keep growing because stolen accounts are emptied within minutes. Design the change.

The interviewer is checking: can you design a basic streaming flow with state, windows and a fallback to batch?

Show a strong answer
  1. Publish every payment attempt to Kafka before it is completed.
  2. A stream processor (Flink or Spark Structured Streaming) keeps per-account state: recent payments, known devices, usual location.
  3. Apply rules and a model score over sliding windows (for example, payments in the last 2 minutes) and return allow, hold or block within the latency budget.
  4. Keep the nightly batch job to retrain the model and tune rules on full history.
  5. Monitor latency and false positives; blocking genuine customers has a cost too.

Avoid: running the nightly job every 5 minutes and calling it real time; it still can't stop a payment in progress.

Payments · correctness1–3 years

The live revenue counter is higher than the bank's figure

A streaming dashboard shows ₹1.02 crore for today; the settlement file says ₹1.00 crore. The stream job restarted twice today after crashes.

The interviewer is checking: do you understand delivery guarantees and how restarts cause duplicates?

Show a strong answer

The pipeline is probably at-least-once: after each crash it re-read events since its last checkpoint and counted some twice.

  • Make results idempotent: de-duplicate on transaction id, or write with upserts keyed by id.
  • Use the engine's checkpointing with transactional or idempotent sinks for exactly-once results.
  • Reconcile daily against the settlement file and alert on differences.

Avoid: “fixing” the dashboard by subtracting an estimated difference.

Mobile gaming · late data3+ years

Players' events arrive hours late

A mobile game sends events when the phone is online. Players on flights or in villages with weak signal send events hours later. Hourly “active players” counts keep changing after they are published.

The interviewer is checking: event time, watermarks, allowed lateness and how batch corrects stream results.

Show a strong answer
  • Aggregate by event time (from the phone), not by arrival time.
  • Set a watermark that matches business needs, e.g. 10 minutes, and publish hourly counts as provisional.
  • Send events later than the allowed lateness to a side output instead of dropping them.
  • Run a nightly batch job over the complete data in the lake to publish final numbers. That is the Lambda idea from Lesson 4.4.
  • Guard against wrong device clocks: reject or clamp event times far in the future.

Avoid: waiting hours before showing any number, or silently dropping late events.
