Data pipelines and orchestration (Apache Airflow basics)

Scripts that run on a timer will happily publish zeros when an earlier step fails. In this lesson you learn how orchestration with tools like Apache Airflow turns separate jobs into a reliable pipeline: a DAG of tasks with dependencies, retries, alerts and quality gates. You'll watch a 2 am failure recover by itself, backfill a week safely and handle data that arrives days late.

2 Definition

What are data pipelines and orchestration?

Formal definition (write this in exams)

A data pipeline is a sequence of automated steps that moves data from sources to destinations, transforming and validating it on the way (for example extract → validate → transform → load). Orchestration is the automated coordination of those steps: scheduling runs, enforcing dependencies, passing parameters such as the logical date, handling retries and timeouts, alerting on failure and recording run history. In Apache Airflow, a pipeline is defined in Python as a DAG (directed acyclic graph) of tasks.

In simple words

A pipeline is a chain of jobs that turns raw data into something useful, like yesterday’s revenue table. An orchestrator such as Airflow runs the chain in the right order, waits when a step isn’t ready, retries steps that fail, and alerts people when something is really wrong.

Words you’ll meet in this lesson

DAGDirected acyclic graph: tasks joined by one-way arrows, with no loops.
Task / operatorOne step in a DAG; an operator is a template for a kind of step (Python, SQL, Spark, Bash).
SensorA task that waits for a condition, such as a file arriving or another DAG finishing.
ScheduleWhen runs are created, often written as cron: 0 1 * * * = 1:00 every day.
Logical dateThe period of data a run is responsible for, independent of when it actually runs.
BackfillRunning a pipeline for past logical dates.
IdempotentGives the same result however many times it is run for the same input.
Incremental loadProcessing only new or changed data since the last run.

An Airflow DAG (example)

This is what the daily orders pipeline looks like in Airflow 3 using the TaskFlow style. It is shown for reading; it needs an Airflow installation to run.

from datetime import datetime, timedelta
from airflow.sdk import dag, task      # Airflow 2.x: from airflow.decorators import dag, task

@dag(schedule="0 1 * * *",                         # every day at 1:00 am
     start_date=datetime(2026, 10, 1),
     catchup=False,
     default_args={"retries": 3, "retry_delay": timedelta(minutes=5)})
def daily_orders():

    @task
    def extract(ds=None):                           # ds = the logical date, e.g. "2026-10-19"
        return f"s3://lake/bronze/orders/date={ds}/"

    @task
    def validate(path):
        ...                                         # row counts, nulls, negative amounts
        return path

    @task
    def transform(path):
        ...                                         # submit a Spark job: bronze -> silver -> gold

    transform(validate(extract()))

Pipelines and orchestration at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A recipe, a cook and a kitchen manager

  • A pipeline is a recipe: steps in order. Buy vegetables → wash → chop → cook → serve.
  • Dependencies: you can’t chop before the vegetables arrive. In data, you can’t transform before you extract.
  • A timer (cron) is an alarm that says “start chopping at 7:30”, even if the vegetables never came.
  • An orchestrator (Airflow) is a kitchen manager: it starts each step only when the previous one is done, tries again if the shop was closed, and tells the owner if dinner will be late, instead of serving an empty plate.

Intermediate Airflow building blocks

  • DAG: the pipeline as a directed acyclic graph of tasks, written in Python, with a schedule.
  • Task / operator: one step (run SQL, call an API, submit a Spark job, run Python). Sensors wait for something, such as a file landing in S3.
  • Scheduler and executor: the scheduler decides which tasks are ready; the executor runs them on workers.
  • Logical date (data interval): each run processes one period of data, for example 19 October, even if it actually runs at 1 am on 20 October or a week later during a backfill.
  • Retries, timeouts and alerts are settings, not code you write each time.
  • Airflow orchestrates; it doesn’t crunch: heavy work runs in Spark, a warehouse or dbt; Airflow tells them when to run and checks the result.
  • Similar tools: Dagster, Prefect, Azure Data Factory, AWS Step Functions, and managed Airflow (Amazon MWAA, Google Cloud Composer, Astronomer).

Advanced Idempotency, backfills and reliability

  • Idempotent tasks: running a task twice for the same logical date gives the same result. Write by overwriting the date partition (or MERGE on keys), never by blind appends.
  • Backfill: re-run past logical dates after a bug fix or a new column. Only possible cleanly if tasks are idempotent and parameterised by date, not by “now”.
  • Incremental loads: process only new or changed data (by date partition or a watermark column such as updated_at) instead of everything every night.
  • Late data: events can arrive days late. Common fix: each run also reprocesses the last N days, which is safe because tasks are idempotent.
  • Quality gates: row-count, null and range checks between tasks stop bad data from being published (Great Expectations, dbt tests, Soda).
  • Operations: SLAs and alerts for late pipelines, lineage to see what depends on what, and keeping DAG files light so the scheduler stays fast.

Exam tip: Define a data pipeline and orchestration, draw a small DAG (extract → validate → transform → load), and explain scheduling, dependencies, retries, backfill and idempotency. Name Apache Airflow with its parts: DAG, operator, sensor, scheduler, executor.

Write every task as a function of the logical date: “process orders for {ds} and overwrite date={ds}”. That one habit makes retries, re-runs and backfills safe, and it is the most common thing interviewers check in pipeline design questions.

4 Step by step

Building a reliable daily pipeline

  1. Draw the DAG

    dag = {"extract": [], "validate": ["extract"], "transform": ["validate"],
       "publish": ["transform"], "email_report": ["publish"]}
done, order = set(), []
while len(order) < len(dag):
    for task, deps in dag.items():
        if task not in done and all(d in done for d in deps):
            order.append(task); done.add(task)
print(" -> ".join(order))
    extract -> validate -> transform -> publish -> email_report
    Each task lists what it depends on; the orchestrator works out a valid order (a topological sort) and runs independent tasks in parallel when it can.

  2. Parameterise by logical date

    import datetime
logical = datetime.date(2026, 10, 19)
path = f"s3://lake/bronze/orders/date={logical}/"
print("this run reads and writes only:", path)
    this run reads and writes only: s3://lake/bronze/orders/date=2026-10-19/
    The 19 October run reads and writes only 19 October’s partition, whether it runs at 1 am on the 20th or during a backfill next month.

  3. Extract with retries

    The source API sometimes times out at night. The extract task is set to retries=3 with a 5-minute delay (often growing each time: exponential backoff).

    Most night-time failures are temporary: a busy API, a network blip, a restarting database. Retries turn them into short delays instead of morning emergencies.

  4. Validate before publishing

    rows = [120, 340, -90, 410]
checks = {"has rows": len(rows) > 0, "no negative amounts": all(r >= 0 for r in rows)}
print(checks, "-> PUBLISH" if all(checks.values()) else "-> STOP and alert")
    {'has rows': True, 'no negative amounts': False} -> STOP and alert
    A quality gate between transform and publish stops impossible data (a negative amount, zero rows, a sudden 90% drop) and alerts someone. Publishing nothing is better than publishing wrong numbers.

  5. Publish idempotently

    partitions = {}
def publish(day, revenue):
    partitions[day] = revenue          # overwrite the day’s partition
publish("2026-10-19", 850); publish("2026-10-19", 850)   # re-run
print(partitions, "total:", sum(partitions.values()))
    {'2026-10-19': 850} total: 850
    Overwriting the date partition means a retry or a re-run produces the same result. With appends, every re-run would add the day’s revenue again.

  6. Monitor, alert, backfill

    Airflow records every run. If Sunday failed, an alert goes out, the dashboard shows “data delayed”, and once fixed, the team clears and re-runs Sunday: a one-day backfill.

    Good pipelines are judged on the bad days: how fast failures are noticed, how clearly they are reported and how safely they are repaired.

6 Real-world use

Real-time scenarios: pipelines on bad days

Three live scenarios: a failure that retries can’t fix, a week-long backfill after a bug, and an advanced look at logical dates and late-arriving data.

Real-time scenario 1

A failure that retries can’t fix

Retries fix most night-time hiccups. But on Diwali night the source database is overloaded for hours. Watch how a well-built pipeline fails safely and recovers.

Failing safely 5 steps
Animated example
  1. The extract task fails and retries with growing delays (5, 10, 20 minutes), giving the busy source time to recover.
  2. After the last retry it is marked failed, and every downstream task is marked “upstream failed” instead of running on missing data.
  3. An alert with a link to the logs pages the on-call engineer.
  4. The dashboard shows “Sunday data delayed” instead of a wrong ₹0, so managers don’t make decisions on bad numbers.
  5. When the source is healthy, the engineer clears the failed task. It and all downstream tasks re-run for Sunday’s logical date, and the numbers are published.
Real-time scenario 2

Backfilling a week after a bug fix

A bug under-counted wallet payments for seven days. The code is fixed; now the past must be repaired. Watch why idempotent tasks make a backfill safe, and appends make it a disaster.

Backfill 5 steps
Animated example
  1. For seven days, a conversion bug published revenue that was too low. The fix is now in the code.
  2. A backfill re-runs the fixed DAG for each logical date from 13 to 19 October, each run touching only its own day.
  3. If the publish step appended rows, the corrected rows would be added on top of the wrong ones, roughly doubling every day.
  4. Because publish overwrites each date partition, each day is replaced by its correct value, and running the backfill twice changes nothing.
  5. Tables built from these days (weekly and monthly summaries) are re-run too, in dependency order. (Figures are illustrative.)
Real-time scenario 3 · advanced

Logical dates, late data and sensors

Real data doesn’t arrive on time. Orders from phones that were offline can show up days later. Watch how logical dates, a reprocessing window and a sensor keep daily numbers correct.

Time in pipelines 5 steps
Animated example
  1. Each run is responsible for one data interval. The run with logical date Sunday covers all of Sunday, midnight to midnight.
  2. It actually starts on Monday at 1 am, once Sunday is complete. Every task uses the logical date, so the same run gives the same answer if repeated later.
  3. On Tuesday, phones that were offline upload 1,200 orders that happened on Sunday. Sunday’s published revenue is now too low.
  4. A common fix: every daily run also re-processes the last three days. Because tasks overwrite their date partitions, re-processing is safe and late data is absorbed.
  5. A sensor can also make a run wait until the source signals that a day is complete (for example a _SUCCESS marker file) before extracting.

Where orchestration runs every day

1. Nightly business reporting

Most companies run hundreds of nightly DAGs: copy yesterday’s data from app databases, build silver and gold tables in Spark or dbt, check quality and refresh dashboards before offices open.

App DBs→Airflow DAGs→Morning dashboards

2. Machine-learning retraining

Recommendation and fraud models are retrained on a schedule: build features, train, evaluate against the current model, and deploy only if better, all as one orchestrated pipeline.

Features→Train → evaluate→Deploy if better

3. Regulatory and finance reports

Banks, NBFCs and e-commerce firms produce daily and monthly regulatory and tax reports with strict deadlines. Orchestrators track SLAs and alert long before a deadline is missed.

Ledgers→Checked pipeline→Filed on time

4. Keeping streaming systems healthy

Even real-time platforms need scheduled jobs: compacting small files, reprocessing late data, rebuilding aggregates, and running data-quality checks on stream outputs.

Stream output→Scheduled maintenance→Clean tables
7 Run the code

A pipeline as a DAG, run in order

The pipeline is a dictionary of tasks and the tasks each depends on. The program finds a valid order (a topological sort), runs each task for one logical date, retries a flaky step, and stops downstream tasks if something fails for good. Then try the challenges: parallel branches, quality gates, idempotent publishing, backfills and incremental loads.

dag = {"extract": [], "validate": ["extract"], "transform": ["validate"], "publish": ["transform"]}
attempts_needed = {"extract": 2}            # extract fails once, then works
RETRIES = 3

def order(dag):
    done, out = set(), []
    while len(out) < len(dag):
        for t, deps in dag.items():
            if t not in done and all(d in done for d in deps):
                out.append(t); done.add(t)
    return out

logical_date = "2026-10-19"
for task in order(dag):
    for attempt in range(1, RETRIES + 1):
        if attempt >= attempts_needed.get(task, 1):
            print(f"{logical_date} {task:9} success (attempt {attempt})")
            break
        print(f"{logical_date} {task:9} failed, retrying")
    else:
        print(f"{task} failed for good: downstream skipped, alert sent")
        break
2026-10-19 extract failed, retrying 2026-10-19 extract success (attempt 2) 2026-10-19 validate success (attempt 1) 2026-10-19 transform success (attempt 1) 2026-10-19 publish success (attempt 1)
  • dag = {"extract": [], "validate": ["extract"], "transform": ["validate"], "publish": ["transform"]}Each task lists its upstream tasks. That is all an orchestrator needs to know the order.
  • if t not in done and all(d in done for d in deps):A task is ready only when every task it depends on has finished.
  • for attempt in range(1, RETRIES + 1):Retries handle temporary failures such as timeouts without waking anyone up.
  • else:The for … else runs only if no attempt succeeded: stop the pipeline instead of running on missing data.

Run it on your PC: a tiny orchestrator with retries and backfills

This program defines a four-task DAG, runs it in dependency order for a logical date, retries a flaky extract step, and publishes one JSON file per day into a warehouse folder. Then it backfills three days twice to prove that re-running is safe. Only the standard library is used. Save it as mini_orchestrator.py and run it.

DAG order, retries, idempotent backfill

"""A tiny orchestrator: tasks with dependencies, run in order, with retries,
one output partition per logical date, and a backfill that re-runs safely."""
import json, os, random

random.seed(1)
os.makedirs("warehouse", exist_ok=True)

ORDERS = {  # pretend source system: orders per day
    "2026-10-17": [120, 340, 90], "2026-10-18": [200, 150], "2026-10-19": [410, 80, 60, 300],
}
DAG = {"extract": [], "validate": ["extract"], "transform": ["validate"], "publish": ["transform"]}


def topo_order(dag):
    done, order = set(), []
    while len(order) < len(dag):
        for task, deps in dag.items():
            if task not in done and all(d in done for d in deps):
                order.append(task)
                done.add(task)
    return order


def run_task(task, day, state, flaky):
    if task == "extract":
        if flaky and random.random() < 0.6:      # the source API sometimes times out
            raise TimeoutError("source API timed out")
        state["rows"] = ORDERS[day]
    elif task == "validate":
        assert all(a > 0 for a in state["rows"]), "negative amount"
    elif task == "transform":
        state["summary"] = {"day": day, "orders": len(state["rows"]), "revenue": sum(state["rows"])}
    elif task == "publish":
        # idempotent: overwrite this day's partition instead of appending
        with open(f"warehouse/daily_{day}.json", "w") as f:
            json.dump(state["summary"], f)


def run_dag(day, flaky=False, retries=3, verbose=True):
    state = {}
    for task in topo_order(DAG):
        for attempt in range(1, retries + 1):
            try:
                run_task(task, day, state, flaky)
                if verbose:
                    print(f"  {day} {task:9} ok" + (f" (attempt {attempt})" if attempt > 1 else ""))
                break
            except Exception as e:
                print(f"  {day} {task:9} failed: {e}" + ("; retrying" if attempt < retries else "; giving up"))
        else:
            print(f"  {day} downstream tasks skipped, alert sent")
            return
    if not verbose:
        print(f"  {day} all tasks ok -> {state['summary']}")


print("Task order:", topo_order(DAG))
print("\nNightly run for 2026-10-19 (flaky source):")
run_dag("2026-10-19", flaky=True)

print("\nBackfill 2026-10-17 to 2026-10-19 (run twice to prove it is safe):")
for run in (1, 2):
    print(f" run {run}:")
    for day in ORDERS:
        run_dag(day, verbose=False)
files = sorted(os.listdir("warehouse"))
total = sum(json.load(open("warehouse/" + f))["revenue"] for f in files)
print(f"\nPartitions in warehouse: {files}")
print(f"Total revenue across partitions: Rs {total} (not doubled, because publish overwrites)")

Interview and viva questions

What is a data pipeline?

A data pipeline is an automated sequence of steps that moves data from one or more sources to destinations, typically extracting, validating, transforming and loading it, so that it is available in a usable form (for example, a daily revenue table for dashboards). Pipelines can be batch (scheduled) or streaming (continuous).

What is Apache Airflow and what are its main components?

Apache Airflow is an open-source platform for authoring, scheduling and monitoring workflows as DAGs written in Python. Its main components are the scheduler (creates runs and decides which tasks are ready), the executor and workers (run tasks), the metadata database (stores run and task state), the web server/UI (monitoring and manual actions), and DAG files containing tasks built from operators and sensors.

What does idempotent mean in data pipelines and why is it important?

An idempotent task produces the same result no matter how many times it runs for the same input or logical date. It is important because tasks are retried after failures, re-run manually and backfilled; without idempotency these would duplicate or corrupt data. Common techniques are overwriting date partitions, MERGE/upsert on keys and deduplication.

What is the difference between scheduling and orchestration?

Scheduling only starts jobs at given times. Orchestration also manages dependencies between tasks, passes parameters such as logical dates, retries failures, enforces timeouts and SLAs, alerts on problems, records history and supports backfills across many systems.

How do you handle late-arriving data in batch pipelines?

Process data by event date into date partitions, and have each run reprocess a window of recent days (for example the last 3 days) using idempotent overwrites or MERGE, so late records are included. Use sensors or completeness markers to wait for sources, and monitor how late data typically arrives to choose the window.

Failed tasks and their victims

Input
DAG of 5 tasks
Expected output
['enrich', 'report']
Show solution and explanation 
dag = {"extract": [], "clean": ["extract"], "enrich": ["clean"], "report": ["enrich"], "audit": ["extract"]}
failed = {"clean"}

while changed:
    changed = False
    for t, deps in dag.items():

P6Advanced

Detect a DAG cycle

A DAG must have no cycles. Print whether the graph has one.

Input
a → b → c → a
Expected output
cycle!
Show solution and explanation 
graph = {"a": ["b"], "b": ["c"], "c": ["a"]}
def has_cycle(g):
    visiting, done = set(), set()
    def visit(n):
        if n in visiting:
            return True
        if n in done:
            return False
        visiting.add(n)
        found = any(visit(m) for m in g[n])
        visiting.discard(n); done.add(n)
        return found
    return any(visit(n) for n in g)
print("cycle!" if has_cycle(graph) else "no cycle")
cycle!

How it works: Airflow refuses DAGs with cycles, because no valid order exists.

Real-world scenario questions (asked in company interviews)

Pipeline and orchestration questions from real teams and interviews. Decide your answer first, then open the model answer.

Pipeline designFresher

Design a daily sales pipeline

Orders live in a PostgreSQL database. Finance wants yesterday’s revenue by city on a dashboard by 8 am every day.

The interviewer is checking: can you design a simple, reliable, orchestrated pipeline?

Show a strong answer
  1. Airflow DAG scheduled at 1 am, parameterised by the logical date.
  2. Extract yesterday’s orders (by updated_at) to the lake as bronze/orders/date=….
  3. Validate: row count vs the source, no negative amounts, no null cities.
  4. Transform to a gold table revenue_by_city, overwriting that date’s partition.
  5. Publish to the dashboard; on failure, retries then an alert and a “delayed” banner.
  6. Add an SLA alert if not done by 7 am.

Avoid: a cron job per script with no dependencies or checks.

Reliability · idempotency1–3 years

Re-running a job doubled the numbers

A failed job was re-run manually and the monthly revenue report now shows twice the real amount for that day.

The interviewer is checking: do you understand idempotency and how to make pipelines safe to re-run?

Show a strong answer

The load step appends rows, so each run adds the day again. Make the task idempotent: write to a date partition and overwrite it (INSERT OVERWRITE or replace the folder), or use MERGE on a unique key. Deduplicate the affected day, then re-run once more to prove nothing changes. Add a check that compares row counts with the source.

Avoid: asking people to “be careful not to run it twice”.

Airflow · concepts1–3 years

Why does the 19 Oct run happen on 20 Oct?

A new teammate is confused: the DAG run labelled 2026-10-19 started at 1 am on 20 October, and their task that uses datetime.now() processed the wrong day.

The interviewer is checking: do you understand logical dates and data intervals?

Show a strong answer

In Airflow, a run’s logical date marks the start of the data interval it processes. A daily run for 19 October can only start after the interval ends, so it runs on 20 October. Tasks must use the run’s logical date (ds, data_interval_start) rather than now(), so that retries and backfills process the intended day.

Avoid: changing the schedule to run “earlier” or hard-coding yesterday’s date.

Architecture · toolsFresher

“Should Spark run inside Airflow?”

A teammate wants to load a 200 GB dataset into a Python task inside Airflow because “Airflow already runs Python”.

The interviewer is checking: do you know what an orchestrator is for?

Show a strong answer

No. Airflow should coordinate work, not do heavy processing. Its workers are sized for many small tasks, and big in-memory work there will crash workers and slow the scheduler. Use Airflow to submit a Spark job (on Databricks, EMR, Dataproc or Kubernetes), a warehouse SQL statement or a dbt run, wait for it, check the result and move on.

Avoid: scaling Airflow workers to hundreds of GB of RAM to process data in tasks.
