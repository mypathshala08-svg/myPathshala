2 Definition

What is the big data ecosystem?

Formal definition (write this in exams)

The big data ecosystem is the collection of tools and services that together form a data platform: they ingest data from sources, store it at scale, process it in batch or in real time, make it available for querying and analysis, serve the results to people and applications, and orchestrate, monitor and govern every step. Each tool specialises in one or two of these layers, and a working platform combines several of them into data pipelines.

In simple words

No single tool does everything. A data platform is a team of tools: one brings data in, one keeps it, one cleans and calculates, one answers questions, one draws the charts, and one acts as the manager who decides what runs when.

The six layers at a glance

1. IngestCollect data from apps, databases and devices · Kafka, NiFi, Debezium, Flume, Sqoop (older)
2. StoreKeep data safely at huge scale · HDFS, Amazon S3 / Azure ADLS / Google Cloud Storage, HBase, Cassandra
3. ProcessClean, join, aggregate · Spark, Flink, MapReduce (older), Kafka Streams, dbt
4. Query & analyseAnswer questions with SQL · Hive, Trino/Presto, Spark SQL, Snowflake, BigQuery, Redshift
5. Visualise & serveShow results to people and apps · Power BI, Tableau, Superset, APIs, ML models
6. Orchestrate & governSchedule, monitor, secure, catalogue · Airflow, Oozie (older), YARN/Kubernetes, data catalogs

The same map at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The restaurant kitchen

Think of TiffinGo's data platform as a big restaurant kitchen:

  • Ingest = the delivery van that brings vegetables every few minutes.
  • Store = the store-room and fridge. Everything is kept, even things you might need later.
  • Process = the cooks who wash, cut and cook raw vegetables into dishes.
  • Query = the order counter, where anyone can ask “how many thalis today?”
  • Visualise = the menu board and the plated food: results people can see.
  • Orchestrate = the head chef with a timetable: dal must be ready before rice is served.

If you remember the kitchen, you can place any tool. That is all you need for now.

Intermediate What each layer must handle, and how to pick a tool

  • Ingest must cope with many sources and bursts. Use Kafka for continuous events (orders, clicks), CDC tools like Debezium to copy database changes, and file or API pulls for daily batches.
  • Store must be cheap, huge and safe. Raw files go to HDFS or cloud object storage (S3, ADLS, GCS); fast lookups by key go to NoSQL (HBase, Cassandra).
  • Process splits into batch (Spark on yesterday's data) and stream (Flink or Spark Streaming on events as they arrive). That's Lesson 4.2.
  • Query gives analysts SQL: Hive/Trino on lake files, or a warehouse like Snowflake or BigQuery for clean tables.
  • Orchestrate: Airflow runs the daily DAG: check data arrived → Spark job → load warehouse → refresh dashboard, and retries failures.

Quick rule: “Need it live?” → stream tools. “Need SQL?” → query engine or warehouse. “Need it every night at 2 am?” → orchestrator.

Advanced How real platforms are designed today

  • Storage and compute are separated. Data sits in object storage; Spark, Trino or a warehouse start compute only when needed, and scale independently. Old Hadoop clusters tied both to the same machines.
  • Open table formats (Apache Iceberg, Delta Lake, Apache Hudi) add database features (transactions, schema changes, time travel) to files in a lake. This is the lakehouse idea, covered in Lesson 4.3.
  • Resource managers moved: many teams now run Spark and Flink on Kubernetes instead of Hadoop's YARN. Kafka 4.0 removed its ZooKeeper dependency in favour of its built-in KRaft mode.
  • Legacy you will still meet: MapReduce, Sqoop (retired by Apache in 2021), Flume and Oozie appear in exams and older clusters, but are rarely chosen for new projects.
  • Managed vs self-hosted: cloud services (EMR, Dataproc, Databricks, BigQuery) trade higher unit prices and some lock-in for far less operations work. The right answer depends on team size, scale and cost.
  • Governance is a layer, not an afterthought: a catalog (what data exists), lineage (where it came from), access control and data-quality checks.

Exam tip: Draw the layered architecture: sources → ingestion → storage → processing (batch + stream) → query/analysis → visualisation, with orchestration and governance down the side. Name two tools per layer. This one diagram answers most “explain the Hadoop / big data ecosystem” questions.

Kafka is not Airflow. A common beginner mix-up: Kafka moves data continuously; Airflow schedules jobs and moves no data itself. One is the delivery van, the other is the head chef's timetable.

4 Step by step

Follow one TiffinGo order through all six layers

  1. Source: the app creates an event

    {"order_id": 90017, "user": "kabir", "kitchen": "K12", "city": "Pune",
 "item": "veg thali", "amount": 120, "ts": "2026-10-19T12:31:08"}
    The moment Kabir taps Place order, the app sends this event. At lunch rush thousands of phones send events like this every minute.

  2. Ingest: Kafka receives it

    kafka-console-producer --topic orders --bootstrap-server broker1:9092
    The event is appended to the orders topic. Kafka doesn't process it; it keeps events in order, durably, and lets many systems read them: the live dashboard, the fraud checker and the lake loader.

  3. Store: raw copy in the lake

    s3://tiffingo-lake/raw/orders/date=2026-10-19/hour=12/part-0003.json
    A loader writes Kafka events into the lake every few minutes, in folders by date and hour. Raw data is never changed, so it can always be reprocessed if a bug is found later.

  4. Process: Spark cleans and joins

    orders = spark.read.json("s3://tiffingo-lake/raw/orders/date=2026-10-19/")
kitchens = spark.read.parquet("s3://tiffingo-lake/clean/kitchens/")
daily = (orders.dropDuplicates(["order_id"])
               .join(kitchens, "kitchen")
               .groupBy("city", "kitchen_name").sum("amount"))
daily.write.mode("overwrite").parquet("s3://tiffingo-lake/gold/daily_sales/date=2026-10-19/")
    This is real PySpark (you'll write it in the Spark course). Spark splits the day's files across many executors, removes duplicate events, joins kitchen names and totals sales, exactly the partition → process → combine pattern from Lesson 1.3.

  5. Query: SQL on the result

    SELECT city, SUM(amount) AS revenue
FROM gold.daily_sales
WHERE date = '2026-10-19'
GROUP BY city ORDER BY revenue DESC;
    Trino, Hive or a warehouse runs this SQL directly over the Parquet files or loaded tables. Analysts never need to know where the files live.

  6. Visualise and orchestrate

    The Power BI dashboard refreshes, and the city manager sees yesterday's sales at 6 am.

    Behind all of it, an Airflow DAG ran at 2 am: check raw data arrived → run Spark job → check row counts → load warehouse → refresh dashboard. If Spark fails, Airflow retries it and alerts the on-call engineer.

Where you'll see the ecosystem at work

1. Food delivery: live ETAs

Rider GPS pings every few seconds go through Kafka to a stream processor that updates arrival times. The same pings are stored in the lake and used overnight to retrain the ETA model.

GPS pings→Kafka → Flink · lake → Spark→ETA on your phone

Core banking databases are copied nightly with CDC into the lake, Spark builds risk and compliance tables, and orchestrated jobs produce the reports banks must file with regulators on time.

Core banking DB→CDC → lake → Spark → warehouse→Regulatory report

Smart meters send readings every 15 minutes. Utilities ingest them as streams, store years of history for billing disputes, and run batch jobs to forecast demand and find power theft patterns.

7 Run the code

Build a tiny data platform in Python

Each function below plays the role of one layer. ingest accepts every event like Kafka, store keeps raw copies like a data lake, process cleans like Spark, serve answers a question like a SQL engine, and the last three lines are the orchestrator. Notice how the corrupted event and the wrong data type are handled in process, never by changing the raw copy.

import json

raw_events = [
    '{"order": 1, "city": "Pune", "item": "thali", "amount": 120}',
    '{"order": 2, "city": "Mumbai", "item": "biryani", "amount": 250}',
    '{"order": 3, "city": "Pune", "item": "thali", "amount": 120}',
    '{"order": 4, "city": "Pune", "item": "dosa", "amount": "90"}',
    'CORRUPTED###',
]

def ingest(events):                 # like Kafka: accept everything, in order
    print("INGEST :", len(events), "events received")
    return list(events)

def store(events, lake):            # like a data lake: keep the raw copy
    lake["raw/orders"] = events
    print("STORE  :", len(events), "raw events saved")

def process(lake):                  # like Spark: parse, clean, fix types
    clean = []
    for e in lake["raw/orders"]:
        try:
            r = json.loads(e)
        except json.JSONDecodeError:
            continue                # skip broken events (real systems log them)
        r["amount"] = int(r["amount"])
        clean.append(r)
    lake["clean/orders"] = clean
    print("PROCESS:", len(clean), "clean rows")

def serve(lake):                    # like Hive / a warehouse: answer a question
    by_city = {}
    for r in lake["clean/orders"]:
        by_city[r["city"]] = by_city.get(r["city"], 0) + r["amount"]
    print("SERVE  : revenue by city ->", by_city)

# ORCHESTRATE: like Airflow, run each layer in the right order
lake = {}
store(ingest(raw_events), lake)
process(lake)
serve(lake)
INGEST : 5 events received STORE : 5 raw events saved PROCESS: 4 clean rows SERVE : revenue by city -> {'Pune': 330, 'Mumbai': 250}
  • lake["raw/orders"] = eventsThe raw copy is saved before cleaning. If the cleaning code has a bug, you fix it and reprocess from raw. That is why lakes keep raw data.
  • except json.JSONDecodeError:One broken event must not stop the platform. The processing layer skips it; real pipelines also write it to an error table for checking.
  • r["amount"] = int(r["amount"])Order 4 sent the amount as text "90". Fixing types is a typical processing job.
  • store(ingest(raw_events), lake)The last three lines are the orchestrator: they decide the order. Swap process and serve and see what breaks.

Interview and viva questions

Explain the Hadoop / big data ecosystem.

A big data platform is built in layers. Ingestion tools (Kafka, Flume, Sqoop, NiFi) bring data in; storage (HDFS, HBase, cloud object storage) keeps it; processing engines (MapReduce, Spark, Flink) transform it in batch or streaming mode; query tools (Hive, Pig historically, Trino) give SQL access; visualisation tools present it; and coordination and scheduling (YARN, ZooKeeper, Oozie/Airflow) manage resources and workflows. Each tool specialises in one layer and they are combined into pipelines.

What is the difference between Kafka and Airflow?

Kafka is a distributed, durable event log: it moves streams of events continuously from producers to consumers. Airflow is a workflow orchestrator: it schedules and monitors batch tasks (like a Spark job) in dependency order. Kafka carries data; Airflow carries none, it only tells other tools when to run.

What is a data pipeline?

A sequence of steps that moves data from sources to a useful destination: extract or ingest, store, transform (clean, join, aggregate) and load into a place where it is queried or served. Pipelines can be batch (scheduled) or streaming (continuous).

Why do companies use managed cloud services instead of running Hadoop themselves?

Managed services remove the work of installing, patching, scaling and monitoring clusters, let compute scale up and down with demand, and separate storage from compute. The trade-offs are cost at large steady scale, less control, and some dependence on one provider.

What is the role of orchestration and governance in the ecosystem?

Orchestration schedules pipelines, runs tasks in the right order, retries failures and alerts people. Governance makes data trustworthy and safe: catalogues of what data exists, lineage of where it came from, access control, and data-quality checks.

P4Medium

Find the bottleneck stage

Given stage durations, print the slowest stage and its share of the total time.

Input
ingest 5, store 20, spark 900, load 60, refresh 15 (seconds)
Expected output

Show solution and explanation 
stages = {"ingest": 5, "store": 20, "spark": 900, "load": 60, "refresh": 15}

How it works: Speed up the bottleneck first; improving a 5-second stage changes almost nothing.

Skipped: ['features', 'report', 'model', 'email']
Show solution and explanation 
downstream = {"clean": ["features", "report"], "features": ["model"],
              "report": ["email"], "model": [], "email": []}
to_skip, queue = [], ["clean"]
while queue:
    task = queue.pop(0)
    for nxt in downstream[task]:
        if nxt not in to_skip:
            to_skip.append(nxt)
            queue.append(nxt)
print("Skipped:", to_skip)
Skipped: ['features', 'report', 'model', 'email']

How it works: A breadth-first walk over the DAG: exactly how an orchestrator marks tasks as upstream_failed.

P7Advanced

Hot and cold storage tiers

Data is kept 30 days in fast “hot” storage (Rs 2 per GB-month) and then moved to “cold” archive (Rs 0.3 per GB-month) for 1 year. With 100 GB arriving per day, print the monthly cost once the system is full (illustrative prices).

Input
100 GB/day, hot 30 days, cold 365 days
Expected output
Hot : 3000 GB
Cold: 36500 GB
Monthly cost: Rs 16950
Show solution and explanation 
hot_gb = 100 * 30
cold_gb = 100 * 365
cost = hot_gb * 2 + cold_gb * 0.3
print("Hot :", hot_gb, "GB")
print("Cold:", cold_gb, "GB")
print("Monthly cost: Rs", round(cost))
Hot : 3000 GB Cold: 36500 GB Monthly cost: Rs 16950

How it works: Most data is cold. Tiering is a standard storage-layer design decision.

P8Business problem

Is the dashboard fresh?

Each dashboard must be updated within its freshness limit (hours). Print which ones are stale.

Input
sales: 5h old, limit 24 · fraud: 2h old, limit 1 · stock: 30h old, limit 24
Expected output
sales  OK
fraud  STALE
stock  STALE
Show solution and explanation 
dashboards = {"sales": (5, 24), "fraud": (2, 1), "stock": (30, 24)}
for name, (age, limit) in dashboards.items():
    print(f"{name:6}", "OK" if age <= limit else "STALE")
sales OK fraud STALE stock STALE

How it works: Freshness checks are a governance task: someone must notice before the business does.

P9Business problem

Self-hosting needs 2 engineers at Rs 1.5 lakh/month each plus Rs 1 lakh of servers. A managed service costs Rs 3.2 lakh/month and needs 0.5 engineer. Print both monthly costs (illustrative).

as given

Real-world scenario questions (asked in company interviews)

Questions that test whether you understand the ecosystem, not just its names. Decide your answer first, then open the model answer.

Any company · first weekFresher

“Walk me through our platform diagram”

In your first week, your lead points at a diagram with 25 logos and asks you to explain how data flows from the mobile app to the CEO's dashboard.

The interviewer is checking: can you organise tools by job and tell a clear story, instead of listing names?

Show a strong answer

Follow one record through the layers, naming the tool at each step:

  1. Source → ingest: the app sends events to Kafka.
  2. Store: a loader writes raw events into the lake (S3/HDFS), partitioned by date.
  3. Process: Spark cleans, de-duplicates and joins them nightly; Flink handles the live path.
  4. Query: results land in warehouse tables; analysts use SQL.
  5. Visualise: the BI dashboard reads those tables.
  6. Orchestrate and govern: Airflow schedules the nightly steps; the catalog documents the tables.

Avoid: reading the logos left to right without saying what each one does.

Startup · tool confusionFresher

“Can't we just use Kafka to schedule our nightly jobs?”

A product manager notices Kafka is already installed and asks why the team also needs Airflow.

The interviewer is checking: do you know the difference between moving data and orchestrating work?

Show a strong answer

Kafka moves events continuously from producers to consumers; it has no idea of “run the Spark job at 2 am, then load the warehouse, retry three times if it fails”. Airflow does exactly that: schedules, dependencies, retries, alerts and a history of every run. They solve different problems and are commonly used together.

Avoid: claiming one tool can replace every layer.

E-commerce · debugging1–3 years

At 11 am the dashboard still shows the day before yesterday

The sales head complains the dashboard is a day behind. Nobody received an alert. Where do you look, and in what order?

The interviewer is checking: can you debug a pipeline layer by layer, starting from the orchestrator?

Show a strong answer
  1. Orchestrator first: did last night's DAG run? Which task failed or is still running? Why was no alert sent?
  2. Ingestion: did yesterday's raw files arrive in the lake (count, size, partition)? Is the Kafka loader lagging?
  3. Processing: did the Spark job fail, or succeed with zero rows?
  4. Load and serve: was the warehouse table updated? Did the dashboard refresh, or is it cached?
  5. Fix, re-run from the failed task, then fix the missing alert and add a freshness check.

Avoid: re-running the whole pipeline blindly before knowing which layer broke.

Telecom · cloud migration3+ years

Moving an on-premises Hadoop cluster to the cloud

A telecom company runs a 200-node Hadoop cluster (HDFS, YARN, Hive, Spark, Oozie). Leadership wants to move to the cloud. What maps to what, and what really changes?

The interviewer is checking: do you understand the architectural shift, not only the product names?

Show a strong answer
  • Mapping: HDFS → object storage; YARN → managed Spark or Kubernetes; Hive tables → a catalog over the lake or a cloud warehouse; Oozie → Airflow (managed).
  • Real change: storage and compute separate. Clusters become temporary: start for a job, shut down after. Cost moves from fixed hardware to pay-per-use, so idle clusters and inefficient queries now cost real money.
  • Plan: migrate data in waves, run old and new in parallel and compare outputs, convert to columnar formats, set up access control and cost monitoring from day one.

Avoid: “lift and shift” of the same always-on 200 nodes into cloud VMs, which usually costs more and gains little.
