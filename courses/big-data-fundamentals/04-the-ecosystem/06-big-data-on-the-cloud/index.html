Big data on the cloud: AWS, Azure and GCP

The cloud lets a two-person team build a data platform in a weekend, and a careless query rack up lakhs in a day. In this lesson you learn the same building blocks on AWS, Azure and Google Cloud, watch a serverless query scale out and vanish, cut a monthly bill from ₹50 lakh to ₹2.4 lakh, survive a spot machine disappearing mid-job, and see why payment data must stay in Indian regions.

2 Definition

Big data on the cloud

Formal definition (write this in exams)

Cloud computing provides on-demand access to computing resources (storage, compute, networking and managed software services) over the internet, billed by usage. For big data, public clouds such as Amazon Web Services (AWS), Microsoft Azure and Google Cloud Platform (GCP) offer managed object storage, distributed processing, data warehouses, streaming and orchestration services that scale elastically. Service models range from IaaS (virtual machines you manage) through PaaS / managed services to serverless offerings billed per query or job, with storage and compute typically separated.

In simple words

Instead of buying and running your own servers, you rent storage and processing from a cloud company and pay only for what you use. Each cloud offers ready-made services for storing lake data, running Spark, querying with SQL and handling streams, so a small team can build a big data platform in days.

Big data on the cloud at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Renting instead of buying

  • Buying servers is like buying a car: big cost up front, it sits idle most of the day, and you maintain it.
  • The cloud is like a ride-hailing app: book exactly the size you need, for as long as you need, and pay per use. Need 200 cars for one hour? Possible.
  • Managed services mean someone else runs the engine: you get storage, Spark, SQL and Kafka-like streaming as ready services, not machines to install.
  • Regions are the cities where the cloud has data centres. Indian companies usually choose Mumbai, Hyderabad, Pune, Chennai or Delhi regions.

Intermediate The same building blocks on every cloud

  • Storage: object storage is the foundation of every cloud lake (S3, ADLS Gen2, Cloud Storage).
  • Processing: managed Spark (EMR, Databricks, Dataproc), serverless ETL (Glue), or Apache Beam pipelines (Dataflow).
  • SQL: warehouses (Redshift, Synapse/Fabric, BigQuery, Snowflake) and serverless SQL directly over lake files (Athena, BigQuery external tables).
  • Streaming: managed event streams (Kinesis, MSK, Event Hubs, Pub/Sub, Confluent Cloud).
  • Orchestration and governance: managed Airflow (MWAA, Cloud Composer), Data Factory, Step Functions; catalogs (Glue Data Catalog, Unity Catalog, Purview, Dataplex).
  • Provisioned vs serverless: provisioned means you choose and pay for machines by the hour; serverless means you just submit work and pay per query, job or data processed.

Advanced Cost, lock-in, security and data residency

  • The four meters: storage (per GB-month), compute (per node-hour or per TB scanned), requests (per thousand API calls) and egress (data leaving a region or cloud, often the hidden cost).
  • FinOps habits: tag every resource with an owner, set budgets and alerts, partition and use columnar formats, auto-terminate idle clusters, autoscale, and use spot / preemptible capacity (much cheaper, but the cloud can take it back at short notice) for fault-tolerant work.
  • Lock-in: proprietary services are convenient but hard to leave. Open formats (Parquet, Delta Lake, Iceberg) and open engines (Spark, Kafka APIs, Airflow) keep options open.
  • Shared responsibility: the provider secures the data centres and services; you secure your data: least-privilege IAM roles, encryption, private network endpoints, no public buckets.
  • Data residency: Indian rules (for example the RBI’s 2018 requirement to store payment-system data in India) and company policies decide which regions data may live in; disaster recovery is often set up across two Indian regions.

4 Step by step

Building a small cloud data platform

  1. Pick a region and create the lake bucket

    Kabir creates a bucket in the Mumbai region with folders by zone: bronze/, silver/, gold/, versioning on, encryption on, public access blocked.

    The region decides latency, price and legal residency. Security settings are your job under the shared-responsibility model.

  2. Stream app events into the lake

    App events flow into a managed stream (Kinesis, MSK, Event Hubs or Pub/Sub) and a delivery service writes them to bronze/ every few minutes as compressed files.

    No Kafka brokers to patch. The trade-off: you pay per shard, partition or GB, and you accept the provider’s limits.

  3. Catalog the tables

    A crawler or a table format registers the files as tables (schema, partitions, location) in a catalog so SQL engines and Spark can find them by name.

    The catalog is what turns a bucket of files into a lake people can query, and where access permissions are managed.

  4. Transform with managed Spark

    nodes, rate = 20, 40       # node-hours at illustrative Rs 40
print("always on :", nodes * 24 * 30 * rate, "rupees/month")
print("3 h a day :", nodes * 3 * 30 * rate, "rupees/month")
    always on : 576000 rupees/month 3 h a day : 72000 rupees/month
    A managed Spark cluster (EMR, Databricks, Dataproc) or a serverless Spark job builds silver and gold tables. Starting it only for the job instead of leaving it on is the easiest big saving.

  5. Query with serverless SQL, carefully

    lake_tb, scan_fraction = 40, 0.01
price_per_tb = 450       # illustrative rupees per TB scanned
print("SELECT * (whole table):", lake_tb * price_per_tb, "rupees per query")
print("one day, 2 columns    :", lake_tb * scan_fraction * price_per_tb, "rupees per query")
    SELECT * (whole table): 18000 rupees per query one day, 2 columns : 180.0 rupees per query
    Per-TB-scanned engines reward Parquet, partitions and selecting only needed columns. The same question can cost a hundred times less with a good layout.

  6. Watch the bill like a metric

    Every resource is tagged with a team and project; a budget alert fires at 80% of the monthly limit; a weekly report shows the most expensive queries and idle resources.

    In the cloud, cost is an engineering metric, just like latency and errors. Teams that watch it daily rarely get bill shocks.

One serverless query: what Kabir sees, and what the cloud does

What Kabir sees, and what the cloud does 6 steps
What you see
  1. Kabir writes a query for yesterday’s revenue by city and presses Run.
  2. It is queued for about a second.
  3. Running for a few seconds.
  4. Four result rows appear after 9 seconds.
  5. Under the result: 14 GB scanned, cost about ₹6.
  6. Afterwards the workspace is idle, and nothing is being billed for compute.
Behind the screen
  1. There is no cluster waiting: the serverless SQL service receives the query text.
  2. The planner reads the catalog and finds that only one date partition can match.
  3. The service starts about 200 workers for a few seconds; each reads part of the Parquet files from object storage, only the two needed columns.
  4. Partial results are combined into four rows.
  5. The bill is based on bytes scanned: 14 GB at an illustrative ₹450 per TB is about ₹6.
  6. Workers are released immediately. Only the stored data keeps costing money, which is the separation of storage and compute in action. (Numbers are illustrative.)

FinOps in five steps 5 steps
Animated example
  1. The first version stores CSV, lets analysts run SELECT * hundreds of times a day on a pay-per-scan engine, and keeps a 20-node cluster running all day. Scans alone cost ₹43 lakh.
  2. Rewriting to Parquet, partitioning by date and selecting only needed columns cuts the data each query reads by 40 times. The bill falls to ₹8.3 lakh.
  3. The Spark cluster is started only for the 3-hour nightly job and terminated afterwards: ₹3.3 lakh.

Real-time scenario 2

A spot worker disappears in the middle of the job

Spot (or preemptible) machines are spare cloud capacity at a deep discount, with one catch: the provider can take them back at short notice. Watch why they suit Spark batch jobs.

Spot capacity 5 steps
Animated example
  1. The nightly job runs with the driver on a normal on-demand machine and eight workers on spot capacity.
  2. The cloud needs its capacity back. Worker 3 gets a short warning (typically a couple of minutes or less) and is taken away.
  3. Spark detects the lost executor and re-runs the tasks that worker was handling on the remaining workers, recomputing any lost data from its lineage.
  4. The cluster manager asks for a replacement node, often trying a different machine type or zone.
  5. The job finishes a few minutes late but costs far less. Rule of thumb: spot for stateless, retryable work (Spark workers, batch); on-demand for drivers, databases and anything that can’t be interrupted.
Real-time scenario 3 · advanced

Where may the data live? Residency, DR, egress and lock-in

Choosing a cloud region is not only about price and speed. Watch four decisions an Indian fintech data team must get right before writing any pipeline.

Region and risk decisions 5 steps
Animated example
  1. Someone proposes moving the payments lake to a cheaper foreign region. For payment-system data this is not allowed: the RBI’s 2018 direction requires it to be stored only in India. Regions are a compliance decision.
  2. Disaster recovery is therefore set up across two Indian regions, for example Mumbai and Hyderabad, with asynchronous replication and a rehearsed switch-over.
  3. Data leaving a region or cloud is charged per GB (egress). A daily full copy of 60 TB elsewhere is expensive; copy incrementally and only what is needed.
  4. To avoid being locked in, keep the data in open formats (Parquet with Delta Lake or Iceberg) and prefer open engines and APIs, even when using managed services.
  5. Security is shared: the provider protects the infrastructure, while the team must block public access, encrypt data, use least-privilege roles and private endpoints, and keep audit logs.

How Indian companies use the cloud for data

1. Start-ups: cloud-native from day one

Food, travel, ed-tech and fintech start-ups build lakes on object storage with managed Spark or a SaaS platform, a cloud warehouse for BI and managed Kafka, without owning a single server.

Apps→Managed cloud services→Dashboards + ML

2. Banks and insurers: hybrid

Regulated companies often keep core systems on premises and use cloud regions in India for analytics, ML and customer apps, with strict controls on what data moves where.

Core banking (on-prem)→Controlled transfer→Cloud analytics in India

3. FinOps teams

Larger companies run FinOps practices: tagging, monthly cost reviews per team, rightsizing, spot usage targets and alerts on expensive queries, because cloud spend can rival salaries.

Usage data→Tags + budgets + reviews→Lower unit cost

4. Hadoop to cloud migrations

Many enterprises are moving older on-premises Hadoop clusters to cloud lakehouses: data copied to object storage, Hive tables converted to Delta or Iceberg, jobs moved to managed Spark.

On-prem HDFS→Copy + convert→Cloud lakehouse

Run it on your PC: estimate and shrink a cloud bill

This program estimates the monthly bill of a small cloud data platform (storage, SQL scans, a Spark cluster and data transfer) with illustrative prices, then applies five fixes one by one: columnar files and partitions, auto-shutdown, spot workers and keeping data in region. A cloud bill, before and after FinOps

"""Estimate a monthly cloud bill for a small data platform, and see what
partitioning, columnar files, spot instances and auto-shutdown save.
All prices are ILLUSTRATIVE round numbers in rupees, not a real price list."""

PRICE = {
    "storage_per_tb_month": 1_900,     # object storage, standard tier
    "scan_per_tb": 450,                # serverless SQL, charged per TB scanned
    "node_hour_on_demand": 40,         # one Spark worker node
    "node_hour_spot": 12,              # same node as spot / preemptible capacity
    "egress_per_tb": 7_000,            # data sent out of the cloud region
}
LAKE_TB = 60
QUERIES_PER_DAY = 400
NIGHTLY_NODES, NIGHTLY_HOURS = 20, 3


def bill(scan_tb_per_query, spot, cluster_always_on, egress_tb):
    storage = LAKE_TB * PRICE["storage_per_tb_month"]
    scans = scan_tb_per_query * QUERIES_PER_DAY * 30 * PRICE["scan_per_tb"]
    rate = PRICE["node_hour_spot"] if spot else PRICE["node_hour_on_demand"]
    hours = 24 if cluster_always_on else NIGHTLY_HOURS
    compute = NIGHTLY_NODES * hours * 30 * rate
    egress = egress_tb * PRICE["egress_per_tb"]
    return {"storage": storage, "queries": scans, "compute": compute, "egress": egress}


def show(name, b):
    total = sum(b.values())
    parts = ", ".join(f"{k} {v / 1e5:.1f}L" for k, v in b.items())
    print(f"{name:37} Rs {total / 1e5:6.1f} lakh/month  ({parts})")
    return total


before = show("1. Naive: CSV, SELECT *, always on", bill(0.8, False, True, 5))
step2 = show("2. + Parquet, partitions, columns", bill(0.02, False, True, 5))
step3 = show("3. + cluster only for the 3-hour job", bill(0.02, False, False, 5))
step4 = show("4. + spot workers", bill(0.02, True, False, 5))
after = show("5. + keep data in-region (no egress)", bill(0.02, True, False, 0))
print(f"\nSaving: {(1 - after / before) * 100:.0f}% of the original bill")

Interview and viva questions

What are the benefits of cloud computing for big data?

Elastic scaling to handle peaks and shrinking afterwards, pay-per-use pricing without large upfront hardware purchases, managed services that remove installation and maintenance work, separation of storage and compute so each scales independently, global regions for low latency and disaster recovery, and fast experimentation with new tools.

Compare the big data services of AWS, Azure and GCP.

For storage: Amazon S3, Azure Data Lake Storage Gen2/Blob, Google Cloud Storage. Managed Spark/Hadoop: Amazon EMR and AWS Glue, Azure Databricks/Fabric/HDInsight, Google Dataproc. Data warehouses: Amazon Redshift, Azure Synapse Analytics/Microsoft Fabric, Google BigQuery. Streaming: Amazon Kinesis and MSK, Azure Event Hubs, Google Pub/Sub. Orchestration: Amazon MWAA and Step Functions, Azure Data Factory, Google Cloud Composer. Databricks, Snowflake and Confluent run on all three.

What is serverless in the context of big data?

A model where you submit queries or jobs without choosing or managing servers; the provider allocates capacity automatically and bills by usage, such as per TB scanned (Athena, BigQuery on-demand), per job or per second of processing (serverless Spark, Dataflow). It is convenient for spiky workloads but needs care to control costs.

How do you control cloud costs for a data platform?

Tag resources by team and project, set budgets and alerts, use columnar formats and partitioning to reduce scans, select only needed columns, build aggregate tables for dashboards, auto-terminate idle clusters and autoscale, use spot capacity for fault-tolerant jobs, apply storage lifecycle tiers, reduce egress, and review the most expensive queries and resources regularly (FinOps).

What is vendor lock-in and how can it be reduced?

Lock-in is the difficulty and cost of moving away from a provider because your data, code and processes depend on its proprietary services. It can be reduced by keeping data in open formats (Parquet, Delta Lake, Iceberg), using open engines and APIs (Spark, Kafka protocol, Airflow, standard SQL), infrastructure-as-code, and isolating provider-specific code behind clear interfaces.

Real-world scenario questions (asked in company interviews)

Cloud questions from real projects and interviews. Decide your answer first, then open the model answer.

Cloud architectureFresher

Design a small analytics platform on a cloud

A start-up wants daily dashboards from app events and its PostgreSQL database, on any one cloud, with a tiny team.

The interviewer is checking: can you assemble the standard building blocks and justify them?

Show a strong answer
  • Ingest: app events to a managed stream, delivered to object storage; database changes extracted nightly (or with change data capture).
  • Store: object storage lake with bronze/silver/gold zones, Parquet with Delta Lake or Iceberg, in an Indian region.
  • Process: serverless or managed Spark jobs, or SQL/dbt in a cloud warehouse.
  • Serve: warehouse or serverless SQL for BI dashboards.
  • Orchestrate: managed Airflow.
  • Govern and secure: catalog, IAM roles, encryption, budgets and tags from day one.

Avoid: listing ten services without explaining how data flows or what it costs.

FinOps · cost1–3 years

The query bill tripled this month

Serverless SQL costs tripled. Data volume grew only 10%.

The interviewer is checking: can you investigate and fix cloud cost problems?

Show a strong answer
  1. Find the top queries by bytes scanned and who ran them (query history, cost reports by tag).
  2. Look for SELECT *, missing partition filters, dashboards refreshing every minute and new unpartitioned tables.
  3. Fix the layout: Parquet, partitions, clustering; create small aggregate tables for dashboards.
  4. Add guardrails: per-user or per-workgroup scan limits, required partition filters, budget alerts.
  5. Share a weekly cost report with teams.

Avoid: switching to a bigger fixed cluster without finding what changed.

Compliance · data residency1–3 years

Can we use a cheaper overseas region?

A fintech’s finance team notices that an overseas region is cheaper and asks to move the payments analytics lake there.

The interviewer is checking: do you know that region choice is a compliance decision?

Show a strong answer

Payment-system data in India must be stored in India under the RBI’s 2018 direction on storage of payment system data, and other data may have contractual or DPDP-related obligations. Keep the lake in Indian regions, use a second Indian region for disaster recovery, and reduce cost through layout, lifecycle tiers, reserved or committed-use discounts and spot capacity instead. Involve the compliance team before moving any regulated data.

Avoid: deciding on price alone.

Fundamentals · interviewFresher

“What are the advantages and risks of cloud for big data?”

A common question in data engineering interviews.

The interviewer is checking: can you give a balanced answer with examples?

Show a strong answer

Advantages: elasticity (scale up for peaks and down afterwards), pay-per-use, managed services that save operations work, separation of storage and compute, global regions, fast experimentation. Risks: uncontrolled costs (scans, idle clusters, egress), vendor lock-in, security misconfiguration (public buckets, broad permissions), data-residency rules, and dependence on provider outages. Mitigations: FinOps practices, open formats, least-privilege security, region planning and multi-zone designs.

Avoid: saying only “the cloud is cheaper”.
