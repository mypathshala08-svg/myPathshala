Reduce-side join

MapReduce has no JOIN keyword, but it has something just as good: the shuffle. Map both data sets to the same key, tag where each record came from, and the reducer receives every matching record together. This lesson joins 5 lakh real orders with the menu and reads the counters that show why the reducer must be careful.

1 The story

Orders know the item, the menu knows the category

The canteen manager wants revenue per category: drinks, snacks, breakfast, meals. The 5 lakh orders in student_orders.csv only say dosa or chai; the category lives in a second file, menu.csv. In SQL this is one JOIN. In MapReduce there is no JOIN keyword, and the two files are read by different map tasks on different workers. Riya has to find a way to bring every order and its menu row to the same place.

Riya

Sir, MapReduce only groups by one key. How do I combine two different files?

Arjun Sir

Make the item the key for both files. The shuffle doesn't care which file a pair came from: every pair with key dosa goes to the same reduce call. You only have to tag each value so the reducer knows which side it came from.

Kabir

And I removed coffee from the menu on purpose. Let's see what a join does with orders that have no menu row.

Arjun Sir

Good. We will also catch something that surprises most people: the menu row does not always arrive first. Our counters will prove it.

2 Definition

Reduce-side join

Formal definition (write this in exams)

A reduce-side join (also called a repartition join) combines two or more data sets on a common key inside the reduce phase. Each input is read by its own mapper (configured with MultipleInputs), which emits the join key as the map output key and the record, tagged with its source, as the value. The shuffle partitions and groups all pairs by the join key, so a single reduce call receives every record of every data set that shares that key. The reducer separates the values by tag, typically buffers one side in memory, and emits the combined records according to the join type (inner, left outer, right outer or full outer). It works for inputs of any size and needs no pre-sorting or co-partitioning, at the cost of shuffling all records of all inputs across the network.

In simple words

Both files are mapped to (join key, labelled record). Hadoop's shuffle brings everything with the same key to one reducer, and the reducer glues the matching records together.

Words you'll meet in this lesson

Joins at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Matching name tags

  • Two lists: the bill book (who ordered what) and the price board (which item is which category).
  • Every slip from both lists gets a coloured sticker (the tag) and is dropped into a box labelled with the item name (the key).
  • One person opens the dosa box, finds the one price-board slip and writes “meal” on every order slip in that box.
  • A box with order slips but no price-board slip (coffee) is the interesting case: throw them away (inner join) or keep them with a blank (outer join).

Intermediate How the job is wired

  • MultipleInputs.addInputPath(job, orders, TextInputFormat.class, OrderMapper.class) and the same for the menu with MenuMapper. No setMapperClass.
  • Both mappers must emit the same key and value types: (Text item, Text tagged).
  • The reducer loops over the values once: menu values set category, order values go into a list. After the loop it writes each order with the category.
  • Values arrive in no guaranteed order. In our run the menu row came first for only 3 of 7 items, so the order list is not optional.

Advanced Costs and refinements

  • Everything is shuffled: all 5 lakh orders crossed the network just to meet 7 menu rows. That is the price of a reduce-side join.
  • Memory: the reducer buffers one side. Buffer the smaller side per key; here that would be the menu, but you can only do that if the menu arrives first.
  • Secondary sort fixes the order: put the tag in a composite key (item, tag), sort the menu tag before the order tag, and partition and group by item only. Then the menu row is always first and orders can be streamed without a list (Lesson 9.7).
  • Skew: chai has 149,669 orders, thali 30,292. One reducer gets the chai group whatever you do; salting the key or a map-side join (Lesson 9.6) avoids that.

Exam tip: For “Explain reduce-side join”, write: both mappers emit (join key, tagged record); the shuffle groups by join key; the reducer separates by tag, buffers one side and emits combinations. Add one drawback (all data is shuffled; buffering can run out of memory) and when to use it (both data sets are large).

One item's journey through the join

Six steps for the item dosa, and what happens to coffee.

Tag, shuffle, buffer, join 6 steps
What you see
  1. The job reads two inputs: 3 splits of orders and 1 split of menu.
  2. Every record, from both files, becomes one map output pair.
  3. All 24.4 MB are shuffled; the reducer sees 8 item groups.
  4. The menu row was first in only 3 of 7 groups.
  5. 459,636 orders joined; 40,364 coffee orders had no menu row.
  6. Each output row is an order with its category appended.
Behind the screen
  1. Each input has its own mapper: three order map tasks and one menu map task.
  2. Both emit the item as key and a tagged value: O| for orders, M| for menu.
  3. The shuffle merges pairs from all four map tasks into one group per item.
  4. The menu row can be anywhere in the group, so the orders are kept in a list until it shows up.
  5. Once the category is known, every buffered order is written with it. Coffee has no menu row and is dropped.
  6. The output is one file of joined rows, one per order with a matching menu row.
6 Real-world use

Reduce-side joins at work

1. Transactions with customer accounts

A bank joins a day's card transactions (hundreds of millions) with the accounts table (crores of rows) on account number. Both sides are too large for memory, so the join is shuffled.

Transactions + accounts→key = account no.→Enriched transactions

2. Clickstream with user profiles

E-commerce sites join page-view logs with user profiles to attribute views to segments (city, device, plan). Hive's default “common join” for two big tables is exactly this pattern.

Logs + users→key = user_id→Views per segment

3. Data quality checks

An anti join (records with no match) finds orphans: orders for items missing from the master list, payments for closed accounts. The unmatched count is reported every night.

Facts + master data→anti join→Orphan report

4. Inside SQL engines

A JOIN between two large tables in Hive or Spark SQL becomes a shuffle join: both sides repartitioned by the join key, then joined per partition. Reading “Exchange hashpartitioning” in a Spark plan means this lesson.

JOIN … ON→shuffle both sides→Joined table

Simplified; organisations differ in tools and policies.

7 Run the code

Simulate a reduce-side join

Two small inputs, tagged map output, a shuffle that mixes the order of values (as Hadoop does), and a reducer that joins. Change JOIN to "left" to keep orders without a menu row.

import random
random.seed(4)
orders = ["1,S1413,dosa,45", "2,S0973,samosa,18", "3,S0007,coffee,20", "4,S0001,dosa,45", "5,S0002,chai,15"]
menu = ["chai,drink", "samosa,snack", "dosa,meal", "thali,meal"]
JOIN = "inner"

pairs = [(o.split(",")[2], "O|" + o) for o in orders]          # OrderMapper
pairs += [(m.split(",")[0], "M|" + m.split(",")[1]) for m in menu]  # MenuMapper

groups = {}
for k, v in pairs:                                             # shuffle: group by item
    groups.setdefault(k, []).append(v)
for k in groups:
    random.shuffle(groups[k])                                  # values arrive in no fixed order

for item in sorted(groups):                                    # reducer
    category, buffered = None, []
    for v in groups[item]:
        if v.startswith("M|"):
            category = v[2:]
        else:
            buffered.append(v[2:])
    for o in buffered:
        if category is not None:
            print(o + "," + category)
        elif JOIN == "left":
            print(o + ",")                                     # no menu row: empty category
5,S0002,chai,15,drink 4,S0001,dosa,45,meal 1,S1413,dosa,45,meal 2,S0973,samosa,18,snack

Reduce-side join

// JoinReduceSide.java: reduce-side join of orders with the menu.
// Both inputs are mapped to (item, tagged record); the reducer meets them per item and writes
// every order with its category added.
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.MultipleInputs;
import org.apache.hadoop.mapreduce.lib.input.TextInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class JoinReduceSide {
  enum Join { ORDERS_JOINED, ORDERS_WITHOUT_MENU, MENU_FIRST, MENU_NOT_FIRST }

  // orders: order_id,student_id,time,item,amount   ->  (item, "O|whole line")
  public static class OrderMapper extends Mapper<LongWritable, Text, Text, Text> {
    private final Text item = new Text(), val = new Text();
    @Override
    protected void map(LongWritable k, Text line, Context ctx) throws IOException, InterruptedException {
      item.set(line.toString().split(",")[3]);
      val.set("O|" + line);
      ctx.write(item, val);
    }
  }

  // menu: item,category,price,counter   ->  (item, "M|category")
  public static class MenuMapper extends Mapper<LongWritable, Text, Text, Text> {
    private final Text item = new Text(), val = new Text();
    @Override
    protected void map(LongWritable k, Text line, Context ctx) throws IOException, InterruptedException {
      String[] f = line.toString().split(",");
      item.set(f[0]); val.set("M|" + f[1]);
      ctx.write(item, val);
    }
  }

  // For one item: one menu record and thousands of order records, in NO particular order
  public static class JoinReducer extends Reducer<Text, Text, Text, NullWritable> {
    private final Text out = new Text();
    @Override
    protected void reduce(Text item, Iterable<Text> vals, Context ctx) throws IOException, InterruptedException {
      String category = null;
      List<String> orders = new ArrayList<>();         // must buffer: the menu record may arrive last
      boolean first = true;
      for (Text v : vals) {
        String s = v.toString();
        if (s.startsWith("M|")) {
          category = s.substring(2);
          ctx.getCounter(first ? Join.MENU_FIRST : Join.MENU_NOT_FIRST).increment(1);
        } else orders.add(s.substring(2));
        first = false;
      }
      if (category == null) { ctx.getCounter(Join.ORDERS_WITHOUT_MENU).increment(orders.size()); return; }
      for (String o : orders) { out.set(o + "," + category); ctx.write(out, NullWritable.get()); }
      ctx.getCounter(Join.ORDERS_JOINED).increment(orders.size());
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();   // orders menu out
    Job job = Job.getInstance(conf, "reduce-side join");
    job.setJarByClass(JoinReduceSide.class);
    MultipleInputs.addInputPath(job, new Path(rest[0]), TextInputFormat.class, OrderMapper.class);
    MultipleInputs.addInputPath(job, new Path(rest[1]), TextInputFormat.class, MenuMapper.class);
    job.setReducerClass(JoinReducer.class);
    job.setMapOutputKeyClass(Text.class);
    job.setMapOutputValueClass(Text.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(NullWritable.class);
    FileOutputFormat.setOutputPath(job, new Path(rest[2]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Interview and viva questions

What is a reduce-side join in Hadoop?

A join performed in the reduce phase. Each input has a mapper that emits the join key as the map output key and the record, tagged with its source, as the value. The shuffle sends all records with the same key to one reduce call, where the reducer separates them by tag and emits the joined records. It handles inputs of any size but shuffles all data.

What is the difference between a map-side join and a reduce-side join?

A reduce-side join shuffles both data sets by the join key and joins in the reducer; it works for any sizes. A map-side join loads the small data set into every mapper's memory (via the distributed cache) and joins while reading the large one, with no shuffle; it needs one side small enough to fit in memory. In our lab both produced the same 459,636 rows; the map-side join took 18.9 s instead of 24.8 s.

Why do reduce-side joins need buffering?

The values for a key come from several map tasks and are merged in no guaranteed order, so the reducer may see many records from one side before the matching record from the other side. It must keep them in memory until the loop is complete, unless secondary sort is used to make one side arrive first.

How do you do an outer join in MapReduce?

The map side is unchanged. In the reducer, after separating the values by tag, emit unmatched records too: for a left outer join, emit every left-side record with empty fields if the right side is missing; for a right outer join, the reverse; for a full outer join, both.

How do you handle skew in a reduce-side join?

A key with very many records sends them all to one reducer, which becomes slow or runs out of memory. Options: filter out junk keys like NULL, buffer only the smaller side and stream the larger with secondary sort, split (salt) the hot key across several reducers while replicating the small side, or use a map-side join when one side is small.

P8Advanced

Salting a hot key

Split chai into 3 reducers by appending a salt to the key on the order side, and replicate the menu row to all 3 salts. Show that every chai order still gets its category.

Input
5 chai orders
Expected output
chai#0 ['1,chai,15,drink', '4,chai,15,drink']
chai#1 ['2,chai,15,drink', '5,chai,15,drink']
chai#2 ['3,chai,15,drink']
Show solution and explanation 
orders = [f"O|{i},chai,15" for i in range(1, 6)]
groups = {}
for n, o in enumerate(orders):
    groups.setdefault(f"chai#{n % 3}", []).append(o)            # salt orders
for s in range(3):
    groups.setdefault(f"chai#{s}", []).append("M|drink")       # replicate menu row
for key in sorted(groups):
    cat = next(v[2:] for v in groups[key] if v.startswith("M|"))
    print(key, [v[2:] + "," + cat for v in groups[key] if v.startswith("O|")])
chai#0 ['1,chai,15,drink', '4,chai,15,drink'] chai#1 ['2,chai,15,drink', '5,chai,15,drink'] chai#2 ['3,chai,15,drink']

How it works: Three smaller groups instead of one; the small side is copied to every salt. Spark's skew-join handling does the same.

Real-world scenario questions (asked in company interviews)

Joins are among the most asked MapReduce and Spark interview topics: how they work, what they cost and what goes wrong.

Concepts · joinsFresher

“How do you join two datasets in MapReduce?”

Asked right after word count.

The interviewer is checking: key choice, tagging and the shuffle.

Show a strong answer
  • Reduce-side: both mappers emit (join key, tagged record) via MultipleInputs; the shuffle groups by key; the reducer separates by tag and combines.
  • Map-side: if one side is small, load it in every mapper from the distributed cache and join while reading; no shuffle.
  • Mention the trade-off: reduce-side works for any sizes but shuffles everything.
Debugging · dataExperienced

The joined output has fewer rows than the orders table

Finance says revenue in the joined report is lower than in the raw orders.

The interviewer is checking: inner join semantics and counters.

Show a strong answer
  • An inner join drops records without a match: check a counter for unmatched keys (our lab: 40,364 coffee orders, no menu row).
  • Fix the master data, or switch to a left outer join so unmatched rows appear with blanks.
  • Add a reconciliation check: joined + unmatched = input.
Internals · orderingExperienced

“My join reducer works in testing but loses rows in production”

The reducer writes orders as soon as it has the category, and assumes the dimension row comes first.

The interviewer is checking: value order is not guaranteed.

Show a strong answer
  • Values for a key are merged from many map tasks in no fixed order; with one map task in testing it looked ordered.
  • Buffer one side until the loop ends, or make the order deterministic with secondary sort: composite key (join key, tag), partition and group on the join key.
  • Add a counter for “dimension not first” to detect it.
Performance · skewExperienced

One reducer of a join runs for hours; the other 199 finish in minutes

Joining page views with users; one user_id is the anonymous value “0”.

The interviewer is checking: skew diagnosis and fixes.

Show a strong answer
  • Check reduce input records per task: one key holds most records.
  • Filter or handle the junk key separately; salt hot keys and replicate the small side; or use a map-side join if the users table fits in memory.
  • In Spark, adaptive query execution can split skewed partitions automatically.
