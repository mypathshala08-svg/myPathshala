Counters

Counters are the job's built-in tally sheet: every task counts, Hadoop adds the counts up, and the driver reads the totals. This lesson uses them to answer questions without writing a single output file, turns one into a data-quality gate, and then breaks the 120-counter limit on purpose to see why counters are not for per-key data.

1 The story

Five lakh orders, no output file, all the answers

The canteen manager wants three quick numbers from September: how many orders per category, how busy each hour was, and how much money each category made. Riya starts writing a reducer. Arjun Sir stops her: “You don't need an output file for twenty numbers. Let the map tasks count, and read the counts in the driver.” The job finishes with no part files at all, and prints every answer. Then Kabir adds “one counter per student, just to see”, and the same job dies after a few seconds.

Riya

Sir, so counters are just a free way to get totals?

Arjun Sir

Almost. Every task keeps its own little counters, sends them to the MRAppMaster with its heartbeat, and the framework adds them up. You already read 54 of them after your first job in Lesson 8.1, and you made your own in Lesson 8.3 to count bad records.

Kabir

Then why did my per-student version crash? It's the same code with one more line.

Arjun Sir

Because counters live in memory in every task, the MRAppMaster and the JobHistory Server. Hadoop allows only 120 of them per job. 2,000 students is a dataset, not a counter. Today we see what counters are good for, how to read them in the driver, how to make a job fail on bad data, and where the limit bites.

2 Definition

Counters

Formal definition (write this in exams)

A counter in Hadoop MapReduce is a named, job-wide long integer that tasks increment while they run and the framework aggregates. Counters are organised in groups. Hadoop maintains built-in counters (file system, job, task/framework, input and output format, shuffle errors); programs define custom counters either as Java enum constants (the enum class is the group) or as dynamic counters named by two strings, group and counter, at run time. Each task attempt keeps its counters locally and reports them to the ApplicationMaster with its progress updates; the job's final values are the sum over the successful attempt of every task, so counts from failed or killed attempts are not included. The driver can read the final values through Job.getCounters(). The number of counters per job is limited (mapreduce.job.counters.max, 120 by default), because every counter is kept in memory by tasks, the ApplicationMaster and the JobHistory Server.

In simple words

Counters are tally marks every task makes on its own sheet. Hadoop collects the sheets, adds them up, and gives you the totals at the end. Use them for a few dozen facts about the job (records read, bad rows, rows per category), never for one tally per customer.

Counters at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Tally marks on many sheets

  • Each map task is a clerk with a tally sheet: one line per category, a mark for every order.
  • From time to time the clerk shows the sheet to the supervisor (the MRAppMaster), who keeps a running total.
  • At the end the supervisor hands you the totals. You never read the orders yourself.
  • A sheet for each of 2,000 students would not fit the supervisor's desk. Hadoop's desk holds 120 lines.

Intermediate Built-in, enum and dynamic

  • Built-in: 54 of them printed after our first job (Lesson 8.1). The most useful: Map input/output records, Reduce input groups, Spilled Records, HDFS bytes read/written, Launched/Failed/Killed tasks, Data-local map tasks.
  • Enum: enum Category { DRINK, SNACK, BREAKFAST, MEAL, UNKNOWN } then ctx.getCounter(Category.DRINK).increment(1). The group name is the enum's class name, OrderCounters$Category.
  • Dynamic: ctx.getCounter("Orders by hour", "14").increment(1). Flexible, but a typo silently makes a new counter, and the number of names must stay small.
  • Reading: after waitForCompletion, job.getCounters().findCounter(...) or loop over getGroup(name).

Advanced What the framework guarantees

  • Final counters come only from the successful attempt of each task. A map that failed half-way and was retried is not counted twice, and the killed copy from speculative execution adds nothing.
  • While the job runs, counters are approximate (they arrive with heartbeats). Decide on final values only.
  • Every counter costs memory in every task, the MRAppMaster and the JobHistory Server, and travels in every progress report. That is why mapreduce.job.counters.max is 120 and the number of groups is limited (50 by default).
  • Counters are not a side channel for results. Anything keyed by a value with many possibilities (student, item, URL) belongs in the job's output.

Exam tip: For “What are counters in MapReduce? Give an example”, name the two kinds of custom counters (enum and dynamic) with one line of code each, two built-in counters (Map input records, Reduce input groups), and one use: counting malformed records so the driver can fail the job.

Good and bad uses of custom counters

Data quality

Malformed lines, missing fields, unknown items. Lesson 8.3: HEADER 42, WRONG_FIELDS 94, BAD_AMOUNT 107.

good

Small category totals

Orders per category, per hour, per status code: a bounded, small set of names.

good

Join diagnostics

Rows that found or did not find a partner (Lesson 9.5: ORDERS_WITHOUT_MENU 40,364).

good

One per key

Per student, per product, per URL: unbounded names hit the 120 limit or bloat memory. Write output instead.

bad

Counters are visible in many places: printed by waitForCompletion(true), in the ResourceManager UI while running (port 8088), in the JobHistory UI and REST API afterwards (port 19888), and from the shell with mapred job -counter <job-id> <group> <name>.

A job whose only result is its counters

Run on the Module 8 lab cluster with counters_lab.sh (in “Run it on your PC”). The data is student_orders.csv: 5 lakh orders, 2,000 students, September 2026.

  1. Count in the mapper

    ctx.getCounter(c).increment(1);                                   // enum: Category.DRINK …
ctx.getCounter("Orders by hour", f[2].substring(11, 13)).increment(1);   // dynamic
ctx.getCounter("Revenue (Rs)", c.name()).increment(Long.parseLong(f[4]));
    A counter is a long, so it can add more than 1 at a time: the revenue counters add each order's amount. The mapper writes no key-value pairs at all.

    job.setNumReduceTasks(0);
job.setOutputFormatClass(NullOutputFormat.class);    // no output files at all
boolean ok = job.waitForCompletion(false);           // false: don't print progress and counters
    No reducer, no output folder, no part files. With waitForCompletion(false) Hadoop doesn't print its own counter dump, so the driver prints exactly what it wants.

    findCounter(TaskCounter.MAP_INPUT_RECORDS) reads a built-in counter; getGroup(Category.class.getName()) lists our enum group. The four categories add up to exactly 5,00,000.

  4. Dynamic counters: hours and money

  5. Use a counter as a quality gate

  System.out.println("unknown items found!");
  System.exit(2);                                  // the scheduler sees a failure
}
    UNKNOWN was 0, so the exit code was 0. In a nightly pipeline (Oozie, Airflow) a non-zero exit stops the next step from loading bad data.

  6. One counter per student

    hadoop jar mr9.jar OrderCounters -D counters.perStudent=true /user/hadoop/data/student_orders.csv
    exit code: 1 job FAILED, map input records = 0 Diagnostics : Task failed task_1792643020992_0036_m_000002 Error: org.apache.hadoop.mapreduce.counters.LimitExceededException: Too many counters: 121 max=120
    Each map task met hundreds of students within seconds; at the 121st counter the task threw an exception. Every retry failed the same way; once one map task had failed 4 times, the job was failed and the other attempts killed. Because only successful attempts count, the driver read 0 map input records.

Don't raise mapreduce.job.counters.max to make per-key counters “work”. Counters are held in memory by every task, the MRAppMaster and the JobHistory Server, and sent with every heartbeat. Per-key numbers are the job's output: write them with a reducer.

5 See it happen

How counters travel

Six steps: tasks count locally, report with heartbeats, a failed attempt is thrown away, the driver reads the totals, and a per-student counter breaks the limit.

From task to driver 6 steps
What you see
  1. The job is submitted; the driver chose not to print progress.
  2. While it runs, counters can be watched in the ResourceManager UI.
  3. If an attempt fails and is retried, the final counts are still right.
  4. The driver prints the category counters it read with getCounters().
  5. Dynamic counters give the busiest hour and revenue; the quality gate passes.
  6. One counter per student: the 121st counter fails every attempt and the job.
Behind the screen
  1. Each map task counts in its own memory as it reads orders.
  2. With each progress update, tasks send their counters to the MRAppMaster.
  3. A failed attempt's counts are thrown away; its retry counts again from zero.
  4. When the job ends, the final totals go to the driver and are archived.
  5. The driver checks a quality counter and chooses its exit code.
  6. Per-student names pass 120 counters in every task, so every attempt fails.
6 Real-world use

Counters at work

1. Quality gates in nightly pipelines

An ingestion job counts malformed rows; the driver compares them with the input count and exits non-zero above a threshold, so the scheduler doesn't publish a broken day.

Raw files→counters: GOOD / BAD→Publish or stop

2. Job monitoring and alerting

Operations teams scrape counters from the JobHistory REST API (records in and out, spilled records, GC time) and alert when a daily job suddenly reads half its usual input.

JobHistory REST→Compare with yesterday→Alert

3. Reconciliation

Joins and lookups count rows that found no partner, so finance teams can reconcile totals before reports go out.

Orders + master data→MATCHED / UNMATCHED→Reconciliation report

4. The same idea in Spark

Spark's accumulators play the role of counters, and Hive shows MapReduce or Tez counters for every query. The rules carry over: few names, read final values only.

Tasks→accumulators→Driver reads totals

Simplified; organisations differ in tools and policies.

Enum and dynamic counters, read by the driver

// OrderCounters.java: a map-only job that only counts. Enum counters, dynamic counters,
// and reading every counter back in the driver after the job.
// -D counters.perStudent=true adds one dynamic counter per student (to hit the counter limit)
import java.io.IOException;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Counter;
import org.apache.hadoop.mapreduce.CounterGroup;
import org.apache.hadoop.mapreduce.Counters;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.TaskCounter;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.NullOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class OrderCounters {
  enum Category { DRINK, SNACK, BREAKFAST, MEAL, UNKNOWN }

  public static class M extends Mapper<LongWritable, Text, NullWritable, NullWritable> {
    private boolean perStudent;
    @Override
    protected void setup(Context ctx) { perStudent = ctx.getConfiguration().getBoolean("counters.perStudent", false); }

    @Override
    protected void map(LongWritable k, Text line, Context ctx) {
      String[] f = line.toString().split(",");          // order_id,student_id,time,item,amount
      String item = f[3];
      Category c;
      switch (item) {
        case "chai": case "coffee": c = Category.DRINK; break;
        case "samosa": case "vada pav": c = Category.SNACK; break;
        case "poha": case "idli": c = Category.BREAKFAST; break;
        case "dosa": case "thali": c = Category.MEAL; break;
        default: c = Category.UNKNOWN;
      }
      ctx.getCounter(c).increment(1);                             // enum counter
      ctx.getCounter("Orders by hour", f[2].substring(11, 13)).increment(1);   // dynamic counter: group, name
      ctx.getCounter("Revenue (Rs)", c.name()).increment(Long.parseLong(f[4]));
      if (perStudent) ctx.getCounter("Orders by student", f[1]).increment(1);
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "order counters");
    job.setJarByClass(OrderCounters.class);
    job.setMapperClass(M.class);
    job.setNumReduceTasks(0);
    job.setOutputFormatClass(NullOutputFormat.class);            // no output files at all
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    boolean ok = job.waitForCompletion(false);                   // false: don't print progress and counters

    // The driver reads the final counters and decides what to do with them
    Counters cs = job.getCounters();
    long in = cs.findCounter(TaskCounter.MAP_INPUT_RECORDS).getValue();
    System.out.println("job " + (ok ? "SUCCEEDED" : "FAILED") + ", map input records = " + in);
    for (String group : new String[] {OrderCounters.Category.class.getName(), "Orders by hour", "Revenue (Rs)"}) {
      CounterGroup g = cs.getGroup(group);
      System.out.println("[" + g.getDisplayName() + "]");
      for (Counter c : g) System.out.printf("  %-10s %,d%n", c.getDisplayName(), c.getValue());
    }
    if (cs.findCounter(Category.UNKNOWN).getValue() > 0) { System.out.println("unknown items found!"); System.exit(2); }
    System.exit(ok ? 0 : 1);
  }
}

Interview and viva questions

What are counters in Hadoop MapReduce?

Counters are named long values that tasks increment while a job runs and the framework aggregates into job totals. Hadoop provides built-in counters (records read and written, bytes, spills, launched and failed tasks) and lets programs define their own, typically to count categories or data-quality problems.

What is the difference between enum counters and dynamic counters?

Enum counters are Java enum constants passed to context.getCounter(Enum); the enum class becomes the group and names are checked at compile time. Dynamic counters are created with context.getCounter(String group, String name), so names can be decided at run time, for example one counter per hour. Dynamic names must still stay few, because of the counter limit.

How do you read counters in the driver?

After job.waitForCompletion() returns, call job.getCounters() to get a Counters object. Use findCounter(TaskCounter.MAP_INPUT_RECORDS) or findCounter(MyEnum.X) for a single value, or getGroup("name") to loop over a group. The driver can then print the values or decide its exit code.

What is the limit on the number of counters?

mapreduce.job.counters.max limits a job to 120 counters by default, and mapreduce.job.counters.groups.max to 50 groups. Exceeding it throws LimitExceededException in the task (“Too many counters: 121 max=120” in our lab) and the job fails. The limit exists because counters are kept in memory by tasks, the ApplicationMaster and the JobHistory Server.

Are counters from failed task attempts included?

No. The job's final counters are aggregated from the successful attempt of each task, so retries and speculative copies do not inflate the totals. While a job is still running, the displayed values are progress snapshots and can change.

P6Medium

Merge with a retry

Merge these attempt counters into job counters, ignoring failed and killed attempts.

Input
4 attempts
Expected output
{'BAD': 8}
Show solution and explanation 
attempts = [("SUCCEEDED", {"BAD": 3}), ("FAILED", {"BAD": 2}), ("SUCCEEDED", {"BAD": 5}), ("KILLED", {"BAD": 1})]
total = {}
for state, cs in attempts:
    if state == "SUCCEEDED":
        for k, v in cs.items():
            total[k] = total.get(k, 0) + v
print(total)
{'BAD': 8}

How it works: BAD = 8. Adding all attempts would wrongly give 11.

P8Advanced

Counters vs output for skewed students

Instead of per-student counters, find the 3 students with the most orders from (student, orders) pairs, the way a reducer's output would be used.

Input
a few (student, orders) rows
Expected output
S0003 4031
S0002 4015
S0007 3934
Show solution and explanation 
rows = [("S0001", 3899), ("S0007", 3934), ("S1413", 184), ("S0002", 4015), ("S0003", 4031)]   # real counts from Lessons 9.1 and 9.7

How it works: Per-key numbers come from the job's output (a reducer keyed by student), then any sort or top-N runs on that output. No counter limit involved.

Real-world scenario questions (asked in company interviews)

Counters come up in interviews as “how do you track bad records?” and in debugging questions about strange numbers.

Concepts · basicsFresher

“How would you count malformed records in a MapReduce job?”

A standard question after you explain mappers.

The interviewer is checking: custom counters and what to do with them.

Show a strong answer
  • Define an enum (e.g. GOOD, BAD_FORMAT, BAD_AMOUNT) and call context.getCounter(Quality.BAD_FORMAT).increment(1) when skipping a row.
  • After the job, read job.getCounters() in the driver and fail the pipeline if bad rows exceed a threshold.
  • Optionally write the bad rows themselves to a side output (MultipleOutputs) for inspection.
Debugging · limitsExperienced

A job fails with “Too many counters: 121 max=120”

It started after a developer added counters “for every product”.

The interviewer is checking: knowing the right fix, not just the property.

Show a strong answer
  • Unbounded dynamic counter names (one per product) hit mapreduce.job.counters.max.
  • Raising the limit is the wrong fix: counters live in memory in every task, the AM and the history server.
  • Move per-product numbers into the job output (a reducer keyed by product) and keep counters for a small, fixed set of facts.
Internals · retriesExperienced

“Our task was retried twice. Are the counters triple-counted?”

An analyst doubts the record counts in the job report.

The interviewer is checking: attempt-level aggregation.

Show a strong answer
  • No: final job counters sum only the successful attempt of each task; failed and killed attempts are excluded.
  • Values seen while the job runs are snapshots and may include in-progress attempts.
  • Side effects are a different story: writes to external systems from a failed attempt are NOT undone, which is why tasks should be idempotent.
Operations · monitoringExperienced

The nightly report was published with half the data

An upstream feed delivered only some files, and the job “succeeded”.

The interviewer is checking: using counters as guardrails.

Show a strong answer
  • Compare Map input records (or HDFS bytes read) with the previous run or an expected range, and exit non-zero on a large drop.
  • Collect counters from the JobHistory REST API into monitoring and alert on anomalies.
  • Also validate inputs before the job (expected file count, _SUCCESS markers from upstream).
