Secondary sort

Inside a reduce group, values arrive in no particular order. Secondary sort makes the shuffle sort them for you: put the sort field into the key, then partition and group by the natural key only. This lesson builds it for 2,000 students' orders on a real cluster and shows what goes wrong when one piece is missing.

1 The story

The first and the last order

The canteen manager wants three facts for every one of 2,000 students: the first order of September, the last one, and the longest break between two orders. Riya writes a reducer that loops over a student's orders. The answers are nonsense: the “first” order it prints is from 14 September and the “last” from the 7th. In Lesson 8.5 she had already seen why: inside one key, values arrive in no particular order (chai [104221, 150350, 113456]).

Riya

Easy fix, Sir: I'll put the 184 orders in an ArrayList and sort them in the reducer.

Arjun Sir

For S1413, fine. Our heaviest student has 3,899 orders; a web user can have millions of clicks. Sorting in the reducer means holding all of them in a 300 MB heap. Hadoop is already sorting terabytes for you in the shuffle, on disk if needed. Let it sort by time as well.

Kabir

But the shuffle sorts by key, and the key is the student.

Arjun Sir

So we make the time part of the key: (student, time). Then we tell Hadoop two things: send all keys of one student to the same reducer, and treat them as one group. That's secondary sort. Our job gave 2,000 correct lines; without the grouping part it gave 490,794 useless ones.

2 Definition

Secondary sort

Formal definition (write this in exams)

Secondary sort is a MapReduce design pattern that delivers the values of each key to the reducer in a defined order, using the framework's shuffle sort instead of sorting in memory. The mapper emits a composite key made of the natural key (the grouping field, e.g. student) and the secondary field (e.g. time) — the value-to-key conversion. Three settings complete it: the sort comparator (the composite key's compareTo, or setSortComparatorClass) orders keys by natural key and then secondary field; a custom partitioner that uses only the natural key, so all records of one natural key reach the same reducer; and a grouping comparator (setGroupingComparatorClass) that compares only the natural key, so consecutive keys with the same natural key form one reduce() call whose values are already in secondary order.

In simple words

Put the field you want sorted (time) into the key next to the field you want grouped (student). Hadoop sorts by both, but you tell it to send and group by the student only. Each reduce() call then gets one student's orders, oldest first.

Secondary sort at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The attendance register

  • The office sorts all canteen slips by roll number and then by time, in one big pile. That's the sort comparator.
  • All slips of roll number S1413 go to the same clerk, whatever the time on them. That's the partitioner.
  • The clerk treats all consecutive S1413 slips as one bundle, not one bundle per time. That's the grouping comparator.
  • The clerk only has to read the top slip (first order) and keep reading to the last one; nothing to sort by hand.

Intermediate The three pieces in code

  • Key: StudentTime implements WritableComparable; compareTo compares student, then time.
  • Partitioner: (k.student.hashCode() & Integer.MAX_VALUE) % n. If it used the whole key, S1413's orders would be spread over every reducer.
  • Grouping comparator: a WritableComparator subclass comparing student only, set with job.setGroupingComparatorClass(StudentGrouping.class).
  • Leave out the partitioner and you get wrong answers once there are 2+ reducers. Leave out the grouping comparator and every distinct (student, minute) becomes its own call: 490,794 in our lab.

Advanced What really happens while you iterate

  • The framework reuses one key object. As you step through the values, it deserializes the next record's key into the same object: key.time changes on every step, while key.student stays the same within the group.
  • That is why our mapper also puts the time in the value: reading the value is the clear, safe way. You can read key.time inside the loop, but never keep a reference to the key and expect it to stay put.
  • For descending order (latest first) add a sort comparator with setSortComparatorClass that reverses the time part, keeping the grouping on student.
  • For speed, production code often uses a raw comparator that compares serialized bytes without creating objects. Correctness first, then that optimisation.

Exam tip: For “What is secondary sort in MapReduce?”, list the four parts: composite key (natural key + secondary field), sort comparator, partitioner on the natural key, grouping comparator on the natural key. Then say why: values are otherwise unordered and sorting them in reducer memory does not scale.

Secondary sort does not fail loudly when a piece is missing. Without the partitioner, results are wrong only when there are 2+ reducers; without the grouping comparator the output just gets bigger. Always check Reduce input groups: it must equal the number of natural keys (2,000 here).

5 See it happen

From mixed-up orders to one sorted group

Six steps for two students: map emits composite keys, the partitioner routes by student, the shuffle sorts by (student, time), grouping makes one call per student.

Composite key, partition, sort, group 6 steps
What you see
  1. The job starts: three map tasks read the orders.
  2. Every order becomes one map output record with a (student, time) key.
  3. The reducer merges the sorted outputs of the three maps.
  4. 500,000 records arrive in only 2,000 groups: one per student.
  5. Each student's line is computed in a single pass.
  6. Without the grouping comparator, there is a group per (student, minute).
Behind the screen
  1. The mapper emits (student, time) keys; the time has moved from the value into the key.
  2. The custom partitioner looks only at the student, so S1413 goes to one reducer.
  3. The shuffle sorts keys by student, then time, using the key's compareTo.
  4. The grouping comparator compares only the student, so all S1413 keys form one group.
  5. The reducer walks the group once; the shared key object's time changes as it goes.
  6. Without grouping, each (student, minute) is a separate call: 490,794 of them.
6 Real-world use

Secondary sort at work

1. Web and app sessionization

Clickstream jobs sort each user's events by timestamp and cut a new session whenever the gap exceeds 30 minutes, to count sessions, session length and bounce rate.

Click logs→key (user, time)→Sessions per user

2. Running balances in banking

Transactions of each account, sorted by posting time, give the running balance and the first overdraft moment without loading an account's full history into memory.

Transactions→key (account, time)→Statements

3. Top-N per group

Best-selling products per store or top scorers per exam centre: sort by (group, value descending) and keep the first N values of each group.

Sales→key (store, −revenue)→Top 10 per store

4. Memory-safe reduce-side joins

Adding a tag to the key so the small table's row sorts first lets the reducer stream the big side without buffering it, the fix for the buffering seen in Lesson 9.5.

Menu + orders→key (item, tag)→Streamed join

Simplified; organisations differ in tools and policies.

Simulate composite key, partition and grouping

This model does what the framework does: sort map output by the full key (student, time), send each key to a reducer by the student only, then cut groups where the student changes. Switch GROUP_BY_STUDENT to False to see a job without a grouping comparator.

orders = [("S1413", "09-14 15:30", "dosa"), ("S0001", "09-01 08:15", "poha"),
          ("S1413", "09-01 14:18", "vada pav"), ("S0001", "09-01 08:09", "poha"),
          ("S1413", "09-30 16:30", "samosa"), ("S0001", "09-01 08:15", "thali")]
REDUCERS = 3
GROUP_BY_STUDENT = True

def partition(student):                       # natural key only
    return sum(map(ord, student)) % REDUCERS

for r in range(REDUCERS):
    mine = [o for o in orders if partition(o[0]) == r]
    mine.sort(key=lambda o: (o[0], o[1]))     # sort comparator: student, then time
    groups = []
    for student, time, item in mine:
        same = groups and (groups[-1][0] == student if GROUP_BY_STUDENT
                           else groups[-1][0] == (student, time))
        if not same:
            groups.append([student if GROUP_BY_STUDENT else (student, time), []])
        groups[-1][1].append(f"{time} {item}")
    for key, vals in groups:
        print(f"reducer {r}: reduce({key}) -> first {vals[0]!r}, last {vals[-1]!r}, {len(vals)} values")

Secondary sort job

// FirstLastOrder.java: secondary sort. For every student: first order, last order and the
// longest gap between two orders, reading the orders in time order WITHOUT sorting in the reducer.
// Key = (student, time): sorted by both, partitioned and grouped by student only.
import java.io.DataInput;
import java.io.DataOutput;
import java.io.IOException;
import java.time.Duration;
import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.io.WritableComparable;
import org.apache.hadoop.io.WritableComparator;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Partitioner;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class FirstLastOrder {

  public static class StudentTime implements WritableComparable<StudentTime> {
    String student = "", time = "";
    public StudentTime() { }
    @Override public void write(DataOutput out) throws IOException { out.writeUTF(student); out.writeUTF(time); }
    @Override public void readFields(DataInput in) throws IOException { student = in.readUTF(); time = in.readUTF(); }
    @Override public int compareTo(StudentTime o) {               // the SORT order: student, then time
      int c = student.compareTo(o.student);
      return c != 0 ? c : time.compareTo(o.time);
    }
    @Override public int hashCode() { return student.hashCode(); }
    @Override public boolean equals(Object o) { return o instanceof StudentTime && compareTo((StudentTime) o) == 0; }
  }

  // 1. Partition by student only, so all of a student's orders reach the same reducer
  public static class StudentPartitioner extends Partitioner<StudentTime, Text> {
    @Override public int getPartition(StudentTime k, Text v, int n) { return (k.student.hashCode() & Integer.MAX_VALUE) % n; }
  }

  // 2. Group by student only, so one reduce() call gets ALL of a student's orders (already time-sorted)
  public static class StudentGrouping extends WritableComparator {
    public StudentGrouping() { super(StudentTime.class, true); }
    @Override public int compare(WritableComparable a, WritableComparable b) {
      return ((StudentTime) a).student.compareTo(((StudentTime) b).student);
    }
  }

  public static class M extends Mapper<LongWritable, Text, StudentTime, Text> {
    private final StudentTime key = new StudentTime();
    private final Text val = new Text();
    @Override
    protected void map(LongWritable k, Text line, Context ctx) throws IOException, InterruptedException {
      String[] f = line.toString().split(",");          // order_id,student_id,time,item,amount
      key.student = f[1]; key.time = f[2];
      val.set(f[2] + " " + f[3]);
      ctx.write(key, val);
    }
  }

  public static class R extends Reducer<StudentTime, Text, Text, Text> {
    private static final DateTimeFormatter F = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm");
    private boolean sorted = true;
    @Override
    protected void reduce(StudentTime k, Iterable<Text> vals, Context ctx) throws IOException, InterruptedException {
      String first = null, last = null, prev = null, gapFrom = null, gapTo = null;
      long n = 0, maxGap = -1;
      for (Text v : vals) {                              // arrives in time order thanks to the sort
        String s = v.toString();
        if (first == null) first = s;
        if (prev != null) {
          if (s.substring(0, 16).compareTo(prev.substring(0, 16)) < 0) sorted = false;   // compare the time part only
          long gap = Duration.between(LocalDateTime.parse(prev.substring(0, 16), F), LocalDateTime.parse(s.substring(0, 16), F)).toMinutes();
          if (gap > maxGap) { maxGap = gap; gapFrom = prev.substring(0, 16); gapTo = s.substring(0, 16); }
        }
        prev = s; last = s; n++;
      }
      ctx.write(new Text(k.student), new Text(n + " orders | first " + first + " | last " + last
          + " | longest gap " + (maxGap / 60) + " h (" + gapFrom + " -> " + gapTo + ")"));
    }
    @Override
    protected void cleanup(Context ctx) { System.err.println("values were in time order in every group: " + sorted); }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "first last order (secondary sort)");
    job.setJarByClass(FirstLastOrder.class);
    job.setMapperClass(M.class);
    job.setReducerClass(R.class);
    job.setPartitionerClass(StudentPartitioner.class);
    if (conf.getBoolean("ss.grouping", true)) job.setGroupingComparatorClass(StudentGrouping.class);
    job.setMapOutputKeyClass(StudentTime.class);
    job.setMapOutputValueClass(Text.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Example 1BeginnerDesign · key

Design the key for “latest score per student”

Problem statement

Exam attempts look like student,subject,attempt_time,score. For each (student, subject) you need the score of the latest attempt. What is the natural key, the secondary field, and which value do you read in the reducer?

Input
4 attempts
Expected output
S1 java latest 09-05 score 55
S1 maths latest 09-20 score 78
S2 maths latest 09-11 score 90

Approach

9 Quiz and revision

Check yourself

Quick revision

Lesson 9.7 in one screen

  • Values in a reduce group are unordered; sorting them in reducer memory does not scale.
  • Composite key = natural key + secondary field (value-to-key conversion); compareTo sorts by both.
  • Partitioner on the natural key only; grouping comparator (setGroupingComparatorClass) on the natural key only.
  • Optional sort comparator (setSortComparatorClass) for descending or custom order.
  • Lab: 5 lakh orders → 2,000 groups and lines; S1413 first 09-01 14:18, last 09-30 16:30, gap 22 h. Without grouping: 490,794 groups.
  • The key object is reused: its secondary field changes as you iterate values.
  • Uses: first/last event, sessionization, top-N per group, joins with the small side first.

Interview and viva questions

What is secondary sort in Hadoop MapReduce?

A pattern that makes the values of each reduce group arrive in a chosen order. The mapper emits a composite key (natural key plus the field to sort by), the sort comparator orders by both, a custom partitioner uses only the natural key and a grouping comparator compares only the natural key, so each reduce() call receives one natural key with its values already sorted by the secondary field.

What is the difference between the sort comparator and the grouping comparator?

The sort comparator decides the order of all keys in the shuffle (by default the key's compareTo). The grouping comparator decides which consecutive sorted keys are passed to the same reduce() call. In secondary sort the sort comparator uses the whole composite key and the grouping comparator uses only the natural key.

Why do we need a custom partitioner for secondary sort?

The default HashPartitioner hashes the whole key. With a composite key, records of the same natural key but different secondary values could go to different reducers, so no reducer would see the complete group. A partitioner on the natural key keeps them together.

Can I just sort the values in the reducer instead?

Only if every group is small enough to fit in the reducer's heap. You must copy each value out of the reused object into a list, which costs memory proportional to the largest group. Secondary sort uses the framework's disk-backed sort and keeps memory constant.

How is secondary sort done in Spark or Hive?

Spark uses repartitionAndSortWithinPartitions with a partitioner on the natural key and an ordering on the composite key. Hive uses DISTRIBUTE BY natural_key SORT BY natural_key, field. SQL window functions with PARTITION BY ... ORDER BY express the same idea.

P6Medium

First and last per group

Given sorted (student, time) records, print each student's first and last time in one pass.

Input
5 sorted records
Expected output
S0001 08:09 20:47
S1413 14:18 16:30
Show solution and explanation 
recs = [("S0001", "08:09"), ("S0001", "08:15"), ("S0001", "20:47"), ("S1413", "14:18"), ("S1413", "16:30")]
cur, first, last = None, None, None
for s, t in recs + [(None, None)]:
    if s != cur:
        if cur:
            print(cur, first, last)
        cur, first = s, t
    last = t

Real-world scenario questions (asked in company interviews)

Secondary sort is a favourite question for experienced Hadoop and Spark engineers.

Concepts · basicsFresher

“Are reducer values sorted in MapReduce?”

A quick check question.

The interviewer is checking: keys vs values.

Show a strong answer
  • Keys are sorted by the shuffle; values for one key are not in any guaranteed order.
  • To get ordered values, use secondary sort: composite key, partitioner and grouping comparator on the natural key.
Design · patternExperienced

Each customer's transactions must be processed in time order

Some customers have crores of transactions; the reducer heap is 4 GB.

The interviewer is checking: all three pieces and why.

Show a strong answer
  • Map emits key (customer, timestamp), value = transaction.
  • Partitioner and grouping comparator on customer only; sort comparator on (customer, timestamp).
  • The reducer streams each customer's transactions in order with constant memory; verify with Reduce input groups = number of customers.
Debugging · outputExperienced

A sessionization job's output has 50 times more rows than users

It ran successfully; the numbers look wrong.

The interviewer is checking: recognising a missing grouping comparator.

Show a strong answer
  • Check Reduce input groups: if it is near the number of (user, timestamp) pairs, the grouping comparator is missing or wrong.
  • Set job.setGroupingComparatorClass with a comparator on the user only.
  • Also check the partitioner: wrong results appear with 2+ reducers if it hashes the whole key.
Internals · reuseExperienced

“Inside the loop over values, can I read the time from the key?”

A follow-up after you explain secondary sort.

The interviewer is checking: object reuse.

Show a strong answer
  • Yes: the framework deserializes each record's key into the same key object, so key.time changes on each step.
  • But don't keep references to the key or values; copy the fields you need.
  • Putting the field in the value too (as our job does) makes the code clearer.
