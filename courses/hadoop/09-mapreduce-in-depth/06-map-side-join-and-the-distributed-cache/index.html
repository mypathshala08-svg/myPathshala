Map-side join and the distributed cache

When one side of a join is small, the cheapest join moves nothing but that small side. This lesson ships a menu file to every map task with Hadoop's distributed cache, joins 5 lakh orders while they are read, and compares it with the reduce-side join of Lesson 9.5 on the same cluster and data.

1 The story

Give every worker a copy of the menu card

The reduce-side join from Lesson 9.5 worked, but Riya keeps looking at one counter: 24,448,645 bytes shuffled. Five lakh orders crossed the network just so each could meet one line of a menu that has seven lines. Kabir laughs: “It's like sending every customer to the head office to ask what category a samosa is. Just print the menu card and stick it on every counter.”

Arjun Sir

When one side of a join is small, don't move the big side to meet it. Move the small side to every map task instead. Hadoop has a built-in delivery service for exactly that: the distributed cache.

Riya

So each map task loads the menu into memory once, and then looks up every order as it reads it?

Arjun Sir

Exactly. A map-only job: no shuffle, no sort, no reducer. Today we ran it on the same 5 lakh orders and got the same 459,636 joined rows, about six seconds faster, with nothing crossing the network.

Kabir

And the catch, I'm guessing, is that the menu must fit in memory.

Arjun Sir

That is the one rule. A seven-line menu fits anywhere. A 50 GB customer table does not, and then you are back to the reduce-side join.

2 Definition

Map-side join and the distributed cache

Formal definition (write this in exams)

A map-side join combines records from two data sets inside the map phase, without a shuffle. In its most common form, the replicated (or broadcast) join, the smaller data set is copied to every map task, loaded into an in-memory hash table in setup(), and each record of the larger data set is joined by a lookup as it is read; the job can be map-only. The copy is delivered by the distributed cache: files registered with Job.addCacheFile() or the -files, -archives and -libjars generic options are downloaded from HDFS by each NodeManager once per node into a local cache, and made available to every container of the job, optionally under a symlink name given after #. A second form, the composite (sort-merge) map-side join, needs no memory but requires both inputs to be sorted by the join key and partitioned identically into the same number of files.

In simple words

Give every worker its own copy of the small table, keep it in a dictionary, and add the matching column to each big-table row while reading it. Nothing is sent to a reducer, so it is fast, as long as the small table really is small.

Map-side join at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A menu card on every counter

  • Each counter (map task) gets a printed copy of the menu card (the small table).
  • When an order comes in, the counter reads the category off its own card and writes the bill at once. No one walks to the head office.
  • This only works because the card is small. If the “card” were a phone book of every student, you couldn't print one for every counter.

Intermediate How the job is built

  • Driver: job.addCacheFile(new URI("/user/hadoop/data/menu.csv#menu")) and job.setNumReduceTasks(0).
  • setup(): open ./menu (the symlink), read every line into a HashMap<item, category>. It runs once per map task, not once per record.
  • map(): look up the item; if found, write the order plus its category; if not, increment a counter. Each line is handled on its own, so the output keeps the input order.
  • Output: one part-m-NNNNN per map task, unsorted. Our three files were 9.0 MB, 9.0 MB and 2.8 MB because the third split was the short tail of the file.

Advanced Where it breaks and what else exists

  • Memory: the hash table lives in the map JVM's heap (300 MB in our lab, -Xmx300m). Java objects take several times the file size, so a 100 MB file can need 300–500 MB of heap. Measure, and raise mapreduce.map.memory.mb and -Xmx together if needed.
  • Inner vs outer: unmatched big-side rows can be dropped (inner) or written with an empty value (left outer). Unmatched small-side rows can't be reported, because no single task sees all big-side rows.
  • Composite join: if both inputs are already sorted by the key and split into the same number of identically partitioned files (for example, outputs of two jobs with the same partitioner and reducer count), CompositeInputFormat merges them in the map with no memory limit.
  • Today: Hive converts joins with a small table into a map join automatically (hive.auto.convert.join), and Spark does a broadcast hash join below spark.sql.autoBroadcastJoinThreshold (10 MB by default). Same idea, same memory rule.

Exam tip: For “Explain map-side join”, give: small table shipped with the distributed cache, loaded into a hash map in setup(), lookup in map(), no reducer and no shuffle; the condition (small side fits in memory); and the alternative for two big tables (reduce-side join, or a composite join when both are sorted and identically partitioned).

Three ways to put a file in the distributed cache

addCacheFile (driver)

job.addCacheFile(new URI("/data/menu.csv#menu")). The file must already be in HDFS. Our JoinMapSide uses this.

Java

-files (command line)

-files menu.csv,lookup.py: local or HDFS files, uploaded to the staging folder for you. Lesson 9.8 ships menu.csv to Python scripts this way.

any job

-archives

-archives dict.zip#dict: a zip, tar or jar that is unpacked on each node; tasks see a folder.

many files

-libjars

-libjars gson.jar: extra jars added to the task classpath, for libraries your mapper needs.

code

-files, -archives and -libjars only work if your main() passes the arguments through GenericOptionsParser (or implements Tool and runs via ToolRunner). All our programs do, which is why -D options also worked in Modules 8 and 9.

A replicated join that works on test data can fail in production when the “small” table grows: every map task holds its own full copy in heap, so the job dies with OutOfMemoryError or containers are killed for exceeding memory. Check the small side's size in the driver (or in your scheduler) and fall back to a reduce-side join above a limit.

6 Real-world use

Map-side joins at work

1. Enriching transactions with a code table

Billions of UPI or card transactions get the bank name and branch city from a few-MB IFSC or merchant-category table, joined in memory on every mapper.

Transactions→broadcast lookup→Enriched rows

2. Geo-tagging web logs

A GeoIP range file shipped with -files lets each mapper convert client IPs to city and state while parsing log lines.

Access logs→-files geoip.csv→Visits per city

3. Hive and Spark do it for you

A Hive query joining a fact table with a small dimension table becomes a map join automatically; Spark SQL broadcasts tables under 10 MB by default. Knowing the idea helps you read their plans and fix out-of-memory errors.

SQL JOIN→small table broadcast→No shuffle of the big side

4. Bucketed tables for big-big joins

Two large tables bucketed and sorted on the same key into the same number of files (Hive sort-merge-bucket join) can be joined file by file in the map phase: the composite join idea.

Bucket 7 of A+Bucket 7 of B→Merged in one map

Simplified; organisations differ in tools and policies.

Simulate a broadcast join, split by split

Every “map task” below gets its own copy of the small table, builds a dictionary once (its setup()), and joins its own split. There is no shuffle step at all, and each task's output keeps its input order.

menu_lines = ["chai,drink,15,A", "samosa,snack,18,B", "dosa,meal,45,D", "idli,breakfast,30,C"]
splits = [["1,S1413,2026-09-14 15:30,dosa,45", "2,S0973,2026-09-26 20:11,samosa,18"],
          ["3,S0007,2026-09-01 13:37,coffee,20", "4,S0002,2026-09-03 08:10,chai,15"],
          ["5,S0042,2026-09-09 14:05,idli,30"]]
joined = without_menu = 0
for n, split in enumerate(splits):
    category = {}                                   # setup(): once per map task
    for line in menu_lines:
        f = line.split(",")
        category[f[0]] = f[1]
    out = []
    for order in split:                             # map(): once per record
        cat = category.get(order.split(",")[3])
        if cat is None:
            without_menu += 1
            continue
        joined += 1
        out.append(order + "," + cat)
    print(f"part-m-0000{n}: {out}")
print("ORDERS_JOINED =", joined, " ORDERS_WITHOUT_MENU =", without_menu)

The map-side join

// JoinMapSide.java: map-side join, a map-only job. The small menu is shipped to every map task
// with the distributed cache and loaded into a HashMap in setup(); orders are joined as they are read.
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;
import java.net.URI;
import java.util.HashMap;
import java.util.Map;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class JoinMapSide {
  enum Join { ORDERS_JOINED, ORDERS_WITHOUT_MENU }

  public static class JoinMapper extends Mapper<LongWritable, Text, Text, NullWritable> {
    private final Map<String, String> category = new HashMap<>();
    private final Text out = new Text();

    @Override
    protected void setup(Context ctx) throws IOException {
      URI[] files = ctx.getCacheFiles();
      System.err.println("cache files: " + java.util.Arrays.toString(files));
      // "#menu" in the URI makes YARN create a symlink called "menu" in the task's working directory
      try (BufferedReader r = new BufferedReader(new FileReader("menu"))) {
        String line;
        while ((line = r.readLine()) != null) {
          String[] f = line.split(",");
          category.put(f[0], f[1]);
        }
      }
      System.err.println("menu loaded in setup(): " + category.size() + " items, working dir = " + new java.io.File(".").getAbsolutePath());
    }

    @Override
    protected void map(LongWritable k, Text line, Context ctx) throws IOException, InterruptedException {
      String cat = category.get(line.toString().split(",")[3]);
      if (cat == null) { ctx.getCounter(Join.ORDERS_WITHOUT_MENU).increment(1); return; }
      ctx.getCounter(Join.ORDERS_JOINED).increment(1);
      out.set(line + "," + cat);
      ctx.write(out, NullWritable.get());
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();   // orders menu out
    Job job = Job.getInstance(conf, "map-side join");
    job.setJarByClass(JoinMapSide.class);
    job.addCacheFile(new URI(rest[1] + "#menu"));     // ship the menu to every task, linked as ./menu
    job.setMapperClass(JoinMapper.class);
    job.setNumReduceTasks(0);                         // no reducer, so no shuffle at all
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(NullWritable.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[2]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Example 1BeginnerSizing · memory

Can the student table be broadcast?

Problem statement

The college wants every order joined with its student's department. The student file has 20,000 lines of about 60 bytes. Map tasks have a 300 MB heap. Assuming a hash map entry costs about 5× the raw line, does it fit comfortably (under half the heap)?

Input
20,000 × 60 B · 5× overhead · 300 MB heap
Expected output
raw 1.14 MB -> about 5.7 MB of heap; fits: True

Approach

  1. Raw size = lines × bytes per line.
  2. Heap needed ≈ raw × 5.
  3. Compare with half the heap.

Which join for which pair of tables?

Problem statement

Pick a join method for each: (a) 2 TB of orders with an 8-line menu; (b) 2 TB of orders with 1.5 TB of payments, both written by jobs with 200 reducers using the same partitioner on order_id, sorted; (c) 2 TB of orders with 1.5 TB of complaints, no special layout.

  • Output: one part-m per map task, in input order (no sort).
  • Rule: small side must fit in the map heap (Java objects take several times the file size).
  • Two big tables: reduce-side join, or composite join if both are sorted and identically partitioned.
  • Modern equivalents: Hive map join, Spark broadcast hash join (10 MB default threshold).

Interview and viva questions

What is a map-side join in Hadoop?

A join performed in the map phase without a shuffle. In the replicated form, the smaller data set is distributed to every map task (usually with the distributed cache), loaded into memory in setup(), and each record of the larger data set is joined by a lookup. The job can be map-only, so it avoids sorting and transferring data to reducers.

What is the distributed cache in Hadoop?

A mechanism to make read-only files, archives and jars available to all tasks of a job. Files are registered with Job.addCacheFile() or the -files, -archives and -libjars options; each NodeManager downloads them from HDFS once per node (localization) and links them into each container's working directory, optionally under a name given after # in the URI.

When should I use a map-side join instead of a reduce-side join?

When one input is small enough to fit in each map task's memory (with room to spare), or when both inputs are already sorted by the join key and partitioned identically. Otherwise use a reduce-side join, which works for any sizes but shuffles both inputs.

Why is a map-side join faster?

It avoids the shuffle: no map output sorting and spilling, no network transfer to reducers, no merge and no reduce tasks. In our lab the reduce-side join moved 24.4 MB across the network and took 24.8 s; the map-side join moved nothing and took 18.9 s for the same 459,636 rows.

What happens if the small table is too big for a map-side join?

Each map task holds its own full copy in heap, so the tasks fail with OutOfMemoryError or are killed by YARN for exceeding container memory, and retries fail the same way. Increase map memory only if the table is moderately sized; otherwise switch to a reduce-side join or pre-partition both inputs for a composite join.

P8Advanced

Composite join by hand

Two inputs are sorted by order_id and split into the same 2 partitions. Merge-join partition by partition without loading either fully into memory.

Input
2 × 2 sorted partitions
Expected output
1 dosa UPI
3 chai UPI
4 idli card
6 thali UPI
Show solution and explanation 
A = [[(1, "dosa"), (3, "chai")], [(4, "idli"), (6, "thali")]]
B = [[(1, "UPI"), (2, "cash"), (3, "UPI")], [(4, "card"), (6, "UPI")]]
for pa, pb in zip(A, B):
    i = j = 0
    while i < len(pa) and j < len(pb):
        if pa[i][0] == pb[j][0]:
            print(pa[i][0], pa[i][1], pb[j][1]); i += 1; j += 1
        elif pa[i][0] < pb[j][0]:
            i += 1
        else:
            j += 1
1 dosa UPI 3 chai UPI 4 idli card 6 thali UPI

How it works: Orders 1, 3, 4 and 6 are joined, walking both sorted lists once. This only works because both sides use the same partitioning and sort order.

Real-world scenario questions (asked in company interviews)

Join strategies are a favourite interview topic for data engineers, from MapReduce to Spark.

Concepts · joinsFresher

“What is the difference between a map-side and a reduce-side join?”

Asked in almost every Hadoop interview.

The interviewer is checking: where the join happens and the condition.

Show a strong answer
  • Reduce-side: both inputs are mapped to (join key, tagged record) and shuffled; the reducer combines them. Works for any sizes but moves all data.
  • Map-side: the small table is broadcast with the distributed cache and looked up in each mapper; no shuffle, often map-only.
  • Condition: the small side fits in mapper memory (or both inputs are sorted and identically partitioned for a composite join).
Operations · memoryExperienced

A map-side join job that ran for a year now fails with OutOfMemoryError

Every map attempt fails four times; nothing in the code changed.

The interviewer is checking: that you suspect the growing small side.

Show a strong answer
  • Check the size of the cached file: the “small” table has probably grown. Each task holds a full copy in heap.
  • Short term: raise mapreduce.map.memory.mb and -Xmx together, or load only the needed columns and rows.
  • Long term: add a size check in the driver and fall back to a reduce-side join above a threshold, as Hive and Spark do automatically.
Internals · cacheExperienced

“How does a file added with -files reach the mapper?”

A follow-up after you mention the distributed cache.

The interviewer is checking: the localization path.

Show a strong answer
  • The client uploads local files to the job's staging directory in HDFS and records them in job.xml.
  • Before launching containers, each NodeManager downloads (localizes) the files once into its local cache.
  • Each container gets a symlink in its working directory, so the task opens the file by its plain name.
Design · modernExperienced

“Spark is doing a sort-merge join with a 3 MB table. Why, and how do you fix it?”

A slow Spark job joins a fact table with a small lookup table.

The interviewer is checking: broadcast joins beyond MapReduce.

Show a strong answer
  • Spark broadcasts only when it knows the table is below spark.sql.autoBroadcastJoinThreshold (10 MB default); missing statistics or a filtered subquery can hide the size.
  • Use a broadcast hint (broadcast(df) or /*+ BROADCAST(t) */) or compute statistics.
  • It is the same idea as the MapReduce replicated join: ship the small side, avoid shuffling the big side.
