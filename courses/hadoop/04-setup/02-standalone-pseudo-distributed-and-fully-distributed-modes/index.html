Standalone, pseudo-distributed and fully distributed modes

The Hadoop you download can run as a simple local program, as a one-machine cluster, or as a real multi-machine cluster. Which one you get depends on a handful of settings. This lesson runs the same job in all three modes on a real Hadoop 3.5.0 install, shows what jps and the configuration report in each, and explains when each mode is used at work.

2 Definition

Hadoop's three run modes

Formal definition (write this in exams)

Hadoop can run in three modes. Standalone (local) mode is the default after unpacking: Hadoop runs as a single Java process, uses the local file system (fs.defaultFS = file:///) and runs MapReduce with the local job runner (mapreduce.framework.name = local); no daemons are started. Pseudo-distributed mode runs every daemon on one machine, each in a separate JVM, with HDFS (fs.defaultFS = hdfs://localhost:9000, dfs.replication = 1) and YARN (mapreduce.framework.name = yarn), simulating a one-node cluster. Fully distributed mode runs the master daemons and worker daemons on separate machines, with configuration pointing to the master hosts, a workers file listing the worker hosts, and normal replication (default 3). This is the mode used in production.

In simple words

Standalone: Hadoop as a simple program on your files, for testing code. Pseudo-distributed: a full, tiny cluster on one computer, for learning. Fully distributed: a real cluster on many computers, for work.

Modes at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A cricket match three ways

  • Standalone is practising alone in the nets: you check your shots, but it isn't a match.
  • Pseudo-distributed is a match where one person plays every position, running from bowler to keeper. All the rules apply, just on one body.
  • Fully distributed is a real team: each player on their own position, and if one gets injured, a substitute comes in.

Intermediate What actually changes

  • Standalone: hadoop jar … reads input/ from your Linux folder, runs all tasks in one JVM, and writes output/ back to the Linux folder.
  • Pseudo: you edit core-site.xml, hdfs-site.xml, mapred-site.xml, yarn-site.xml; format the NameNode; run start-dfs.sh and start-yarn.sh; files now live in HDFS and jobs go through YARN.
  • Fully: the same files point to the master's host name instead of localhost; the workers file lists the workers; the same configuration is copied to every node.
  • The commands you type (hdfs dfs -put, hadoop jar) are the same in pseudo and fully distributed modes.

Advanced Details that catch people out

  • In standalone mode, hadoop fs -ls / lists your Linux root folder, because the default file system is file:///.
  • Pseudo mode needs dfs.replication = 1: with the default 3 and one DataNode, every block would be reported as under-replicated.
  • Without settings, the NameNode keeps its data in /tmp/hadoop-<user>, which may be cleaned on reboot. Set dfs.namenode.name.dir and dfs.datanode.data.dir for anything you want to keep.
  • Fully distributed on one physical machine is possible with containers (Docker) or VMs: each container is a separate “machine” with its own host name and IP.
  • Unit tests often use a MiniDFSCluster / MiniYARNCluster: an in-process mini cluster, a fourth “mode” used only by developers.

Exam tip: For “Explain the modes of Hadoop installation”, draw a three-column table: standalone (single JVM, local FS, no daemons, for debugging), pseudo-distributed (all daemons on one machine in separate JVMs, HDFS replication 1, for learning/testing), fully distributed (masters and workers on separate machines, replication 3, for production). Add the key property that changes: fs.defaultFS.

4 Step by step

Run the same job in all three modes

Every output below is from a real run of Hadoop 3.5.0 on Ubuntu 24.04 with OpenJDK 17. Full installation commands are in Lesson 4.3; here we focus on what changes between the modes.

  1. Standalone: run an example job on local files

    cd ~/hadoop-3.5.0
mkdir input && cp etc/hadoop/*.xml input
hadoop jar share/hadoop/mapreduce/hadoop-mapreduce-examples-3.5.0.jar \
    grep input output 'dfs[a-z.]+'
cat output/*
ls output
    1 dfsadmin _SUCCESS part-r-00000
    The grep example counts words matching dfs[a-z.]+ in Hadoop's own XML files. input and output are ordinary Linux folders.

  2. Standalone: prove there is no cluster

    jps
hdfs getconf -confKey fs.defaultFS
hdfs getconf -confKey mapreduce.framework.name
hadoop fs -ls /
    9241 Jps file:/// local drwxr-xr-x - root root 4096 2026-10-21 05:12 /bin drwxr-xr-x - root root 4096 2026-10-21 05:12 /etc drwxr-xr-x - root root 4096 2026-10-21 05:12 /home …
    No daemons. The default file system is the local disk, so hadoop fs -ls / shows the Linux root folder, owned by root, not an HDFS folder.

  3. Pseudo-distributed: change the settings

    <configuration>
    <property>
        <name>fs.defaultFS</name>
        <value>hdfs://localhost:9000</value>
    </property>
</configuration>
    <configuration>
    <property>
        <name>dfs.replication</name>
        <value>1</value>
    </property>
</configuration>
    These two files are exactly what the official Apache single-node guide uses. mapred-site.xml and yarn-site.xml (to run jobs on YARN) are shown in Lesson 4.3 and explained in Lesson 4.4.

  4. Pseudo-distributed: format and start

    hdfs namenode -format
start-dfs.sh
start-yarn.sh
jps
    Storage directory /tmp/hadoop-riya/dfs/name has been successfully formatted. Starting namenodes on [localhost] Starting datanodes Starting secondary namenodes [vm] Starting resourcemanager Starting nodemanagers 5584 SecondaryNameNode 5283 NameNode 6567 Jps 6120 ResourceManager 5384 DataNode 6221 NodeManager
    Five daemons, five JVMs, one machine (here named vm). The numbers are process IDs and will differ on your machine.

  5. Pseudo-distributed: same job, now on HDFS and YARN

    hdfs getconf -confKey fs.defaultFS
hdfs getconf -confKey dfs.replication
hdfs dfs -mkdir -p /user/riya/input
hdfs dfs -put etc/hadoop/*.xml input
hadoop jar share/hadoop/mapreduce/hadoop-mapreduce-examples-3.5.0.jar \
    grep input output 'dfs[a-z.]+'
hdfs dfs -cat output/*
    hdfs://localhost:9000 1 … INFO mapreduce.Job: Job job_1792559666229_0001 completed successfully … 1 dfsadmin 1 dfs.replication
    The job now runs through YARN (it has a job ID). The result has a second line, dfs.replication, because the hdfs-site.xml you just edited is one of the input files: the data changed, not the program.

  6. Fully distributed: many nodes

    docker compose up -d --scale datanode=3
docker compose exec namenode hdfs dfsadmin -printTopology
docker compose exec namenode hdfs getconf -confKey dfs.replication
    Rack: /default-rack 172.18.0.4:9866 (mpcluster-datanode-1.mpcluster_default) In Service 172.18.0.6:9866 (mpcluster-datanode-3.mpcluster_default) In Service 172.18.0.7:9866 (mpcluster-datanode-2.mpcluster_default) In Service 3
    Three DataNodes, each a separate container with its own IP address, and replication back to 3. On real servers the only difference is that each DataNode is a separate computer, listed in the workers file.

hdfs namenode -format erases the HDFS namespace. Run it once when you create a cluster, never on a cluster that holds data you need.

5 See it happen

From one process to a cluster

On the left, the real terminal output at each step. On the right, the processes and machines behind it.

Standalone → pseudo → fully distributed 6 steps
What you see
  1. Standalone. The example job runs and prints a result. It looks like Hadoop is “working”.
  2. But jps shows no daemons, and the default file system is file:///: the job ran as one ordinary program on local files.
  3. Pseudo-distributed. Two settings change: HDFS on localhost:9000 and replication 1. Then a one-time format.
  4. The start scripts launch five daemons. jps now lists each one as a separate Java process.
  5. The same job runs through YARN, reading and writing HDFS. (The extra result line comes from the edited hdfs-site.xml in the input.)
  6. Fully distributed. On the Docker practice cluster, three DataNodes report in, each on its own address.
Behind the screen
  1. One Java process reads input/ from the Linux disk, runs map and reduce inside itself, and writes output/.
  2. Nothing keeps running afterwards. There is no HDFS to store data in and no YARN to schedule work.
  3. The configuration now points to HDFS on this machine. Formatting creates an empty namespace for the NameNode.
  4. HDFS daemons and YARN daemons start, each in its own JVM. It is a real cluster, with exactly one node.
  5. YARN runs the job in containers. With replication 1, each block exists once, so there is no protection against a disk failure.
  6. Masters and workers live on separate machines (here, containers with separate IPs). Replication 3 spreads every block over three nodes.

6 Real-world use

Which mode, where?

1. Developers test logic locally

Before a MapReduce or Spark job reaches the cluster, developers run it in local mode on a small sample, often inside automated tests. Bugs in the logic show up in seconds, without waiting for a cluster.

Sample data→Local run in tests→Then the cluster

2. Integration tests on a one-node cluster

Build pipelines start a pseudo-distributed cluster or an in-process mini cluster, run the job end to end against real HDFS and YARN APIs, check the output, and shut it down.

Code change→One-node cluster test→Merge

3. Multi-node clusters in containers

Teams use Docker Compose or Kubernetes to start throw-away multi-node clusters for development and training. The Apache Hadoop project itself publishes the apache/hadoop images used in this course.

One laptop→Many containers→Real distributed behaviour

4. Production: always fully distributed

Companies run several fully distributed clusters: a small one for development, one for testing upgrades, and the large production cluster. Changes move through them in that order.

Dev cluster→Test cluster→Production

Simplified; organisations differ in tools and policies.

7 Run the code

Work out the mode from the settings

The mode is decided by a few configuration values. This function reads them (here typed in as dictionaries, exactly as hdfs getconf printed them on our three test machines) and names the mode.

def mode(conf):
    fs = conf.get("fs.defaultFS", "file:///")
    if fs.startswith("file:"):
        return "standalone"
    host = fs.split("//")[1].split(":")[0]
    if host in ("localhost", "127.0.0.1"):
        return "pseudo-distributed"
    return "fully distributed (NameNode on " + host + ")"

machines = {
    "fresh unpack": {},
    "Riya's WSL": {"fs.defaultFS": "hdfs://localhost:9000", "dfs.replication": "1"},
    "Docker cluster": {"fs.defaultFS": "hdfs://namenode", "dfs.replication": "3"},
}
for name, conf in machines.items():
    print(f"{name:15} -> {mode(conf)}")
fresh unpack -> standalone Riya's WSL -> pseudo-distributed Docker cluster -> fully distributed (NameNode on namenode)
  • fs = conf.get("fs.defaultFS", "file:///")If the setting is missing, Hadoop uses its default: file:///, the local disk. That is why a fresh unpack is standalone.
  • host = fs.split("//")[1].split(":")[0]hdfs://localhost:9000 → after // is localhost:9000 → before : is localhost.
  • "Docker cluster": {"fs.defaultFS": "hdfs://namenode", "dfs.replication": "3"},No port means the default NameNode RPC port, 8020.

Run it on your machine: which mode am I in?

This script asks Hadoop for its settings and lists the running daemons, then names the mode. Save it as which_mode.sh (Hadoop's bin must be on your PATH). The three outputs below are from real runs.

Standalone: a fresh unpack

#!/usr/bin/env bash
# which_mode.sh: which Hadoop mode is this machine in?
fs=$(hdfs getconf -confKey fs.defaultFS 2>/dev/null)
fw=$(hdfs getconf -confKey mapreduce.framework.name 2>/dev/null)
daemons=$(jps | awk '$2 != "Jps" {print $2}' | sort | tr '\n' ' ')
echo "fs.defaultFS             : $fs"
echo "mapreduce.framework.name : $fw"
echo "daemons on this machine  : ${daemons:-none}"
case "$fs" in
  file:*)                              echo "MODE: standalone (local files, no daemons)" ;;
  hdfs://localhost*|hdfs://127.0.0.1*) echo "MODE: pseudo-distributed (every daemon on this machine)" ;;
  hdfs://*)                            echo "MODE: fully distributed (NameNode at ${fs#hdfs://})" ;;
esac

What does replication 1 really risk?

Problem statement

A team keeps 2 TB of test data on a pseudo-distributed node (replication 1, one disk). Assume a disk has a 2% chance of failing in a year. Compare the chance of losing data within a year with a 3-node cluster at replication 3, assuming failures are independent and a failed disk is replaced and re-replicated within a day.

Input

Expected output

Approach

  2. Three copies: all three must fail within the same day of repair. Per-day failure chance = 2% / 365.

Interview and viva questions

What are the modes of Hadoop?

Standalone (local) mode: a single JVM with the local file system and no daemons, used for debugging. Pseudo-distributed mode: all Hadoop daemons run on one machine in separate JVMs with HDFS and YARN, used for learning and testing. Fully distributed mode: daemons run on separate master and worker machines, used in production.

What is the default mode of Hadoop?

Standalone (local) mode. Without configuration, fs.defaultFS is file:/// and mapreduce.framework.name is local.

What is the difference between standalone and pseudo-distributed mode?

Standalone runs everything inside one Java process on local files, with no HDFS or YARN. Pseudo-distributed runs the real daemons (NameNode, DataNode, ResourceManager, NodeManager…) as separate processes on one machine, so jobs use HDFS and YARN just as on a cluster.

Which configuration files change between modes?

core-site.xml (fs.defaultFS), hdfs-site.xml (dfs.replication and storage folders), mapred-site.xml (mapreduce.framework.name=yarn) and yarn-site.xml (ResourceManager host, shuffle service), plus the workers file for fully distributed mode.

Can I run fully distributed mode on one laptop?

Yes, with containers or virtual machines: each container or VM is a separate node with its own host name and IP. The Docker practice cluster in Lesson 4.3 does exactly this.

Why do I need to format the NameNode?

Formatting creates an empty HDFS namespace (the fsimage and a new cluster ID) in the NameNode's storage folder. It is done once when creating a cluster; formatting again erases the namespace and makes existing DataNodes incompatible.

Is pseudo-distributed mode fault tolerant?

No. There is one DataNode and one copy of each block, so a disk failure loses data and a crash stops everything.

Given a pseudo-distributed configuration, produce the fully distributed one for a NameNode host nn1 and 3 workers.

Input
fs.defaultFS=hdfs://localhost:9000 · dfs.replication=1 · workers=localhost
Expected output
fs.defaultFS    : hdfs://localhost:9000  ->  hdfs://nn1:8020
dfs.replication : 1  ->  3
workers         : ['localhost']  ->  ['worker1', 'worker2', 'worker3']
Show solution and explanation 
pseudo = {"fs.defaultFS": "hdfs://localhost:9000", "dfs.replication": "1", "workers": ["localhost"]}
fully = dict(pseudo)
fully["fs.defaultFS"] = "hdfs://nn1:8020"
fully["dfs.replication"] = "3"
fully["workers"] = ["worker1", "worker2", "worker3"]
for k in pseudo:
    print(f"{k:16}: {pseudo[k]}  ->  {fully[k]}")
fs.defaultFS : hdfs://localhost:9000 -> hdfs://nn1:8020 dfs.replication : 1 -> 3 workers : ['localhost'] -> ['worker1', 'worker2', 'worker3']

How it works: Three things change: the NameNode address, the replication factor and the workers list. The same files are then copied to every node.

P7Business problem

Time saved by testing locally first

A developer's job has a bug found only after 3 attempts. Each cluster attempt takes 15 minutes (queue + run); a local-mode attempt on sample data takes 1 minute. How much time does testing locally first save if the 3 failing attempts are local and only the final run uses the cluster?

Input
3 failed attempts · 15 min on cluster · 1 min local · 1 final cluster run
Expected output
cluster only 60 min, local first 18 min, saved 42 min
Show solution and explanation 
cluster_only = 4 * 15
local_first = 3 * 1 + 15
print(f"cluster only {cluster_only} min, local first {local_first} min, saved {cluster_only - local_first} min")
cluster only 60 min, local first 18 min, saved 42 min

How it works: 60 minutes against 18: 42 minutes saved per bug, and the shared cluster is not wasted on broken jobs.

P8Advanced

Find the misconfigured worker

Workers report the NameNode address they use. List the workers that will not join the cluster whose NameNode is hdfs://nn1:8020.

Input
w1: hdfs://nn1:8020 · w2: hdfs://localhost:9000 · w3: hdfs://nn1:8020 · w4: file:///
Expected output
will not join: ['w2', 'w4']
Show solution and explanation 
expected = "hdfs://nn1:8020"
workers = {"w1": "hdfs://nn1:8020", "w2": "hdfs://localhost:9000",
           "w3": "hdfs://nn1:8020", "w4": "file:///"}
bad = [w for w, fs in workers.items() if fs != expected]
print("will not join:", bad)
will not join: ['w2', 'w4']

How it works: w2 looks for a NameNode on itself and w4 has no HDFS setting at all (standalone defaults), so neither registers with nn1.

Real-world scenario questions (asked in company interviews)

Interviewers use the modes to check whether you understand what a cluster really is, not just the names.

Learning · conceptsFresher

“My job ran, so my Hadoop cluster works”

A fresher says they installed Hadoop and ran the example job successfully. When asked, jps shows only “Jps”.

The interviewer is checking: can you tell standalone mode from a real cluster?

Show a strong answer
  • The job ran in standalone mode: one JVM, local files, no HDFS or YARN.
  • Proof: no daemons in jps, and hdfs getconf -confKey fs.defaultFS prints file:///.
  • For a one-node cluster, set fs.defaultFS=hdfs://localhost:9000, dfs.replication=1, YARN settings, format the NameNode, then start-dfs.sh and start-yarn.sh.
Admin · HDFSFresher

Every block is under-replicated on the test machine

On a single-machine setup, hdfs fsck / reports all blocks as under-replicated.

The interviewer is checking: do you connect replication to the number of DataNodes?

Show a strong answer
  • Replication is probably still the default 3 while there is only one DataNode.
  • Set dfs.replication=1 in hdfs-site.xml for new files, and change existing files with hdfs dfs -setrep -w 1 /path.
  • Explain that this is only acceptable for test data: one copy means no protection.
Admin · cluster buildExperienced

A new DataNode never appears in the NameNode UI

You add a fourth worker to a fully distributed cluster. Its DataNode process is running, but the NameNode still shows 3 live DataNodes.

The interviewer is checking: a systematic check of configuration and connectivity.

Show a strong answer
  • On the new node, check hdfs getconf -confKey fs.defaultFS: a leftover localhost value (pseudo config) is common.
  • Check that the NameNode host name resolves and port 8020 is reachable from the worker.
  • Read the DataNode log in $HADOOP_HOME/logs for errors such as “Incompatible clusterIDs” (an old data folder from another cluster).
  • Make sure the host is in the workers file (and in any include file) and the configuration is the same as on other nodes.
Engineering · testingExperienced

Which mode would you use for which stage?

A team lead asks how you would test a new MapReduce job before it runs on the production cluster.

The interviewer is checking: do you know the purpose of each mode?

Show a strong answer
  • Unit tests in local mode on small samples: fast feedback on logic.
  • Integration tests on a one-node or mini cluster: real HDFS and YARN APIs, file formats and configuration.
  • A run on a fully distributed test cluster with realistic data size, then production.
  • Each stage catches different problems: logic, integration, then scale and performance.
