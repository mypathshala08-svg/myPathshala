Configuration files and web UIs

Every Hadoop behaviour you will tune later, from replication to task memory, is a configuration property. This lesson explains the layers those properties come from, which value wins, and how to ask a running daemon what it is really using. It also tours the web UIs and the /conf and /jmx endpoints that engineers open first when something looks wrong. All outputs and screenshots are from a real Hadoop 3.5.0 cluster.

1 The story

Who decides the value: the jar, the file, or you?

Kabir's Docker cluster has dfs.replication=3 in its settings. He uploads a file with -D dfs.replication=2 and gets 2 copies. Then he marks the setting final, sure it can't be changed now, uploads again with -D dfs.replication=2, and still gets 2. Riya asks: “If a final setting can be changed, what does final even mean?”

Arjun Sir

Think of it in layers. Hadoop ships with a default for every one of its settings, inside its jar files. Your *-site.xml files override those defaults. And a client or job can set a value on top, for its own work, with -D.

Kabir

And final?

Arjun Sir

final protects a value against configuration files loaded later, for example the job.xml that comes with every submitted job. Your -D didn't load a file; it set the value directly in your own client, so it still won. That's exactly what we saw: 2 copies.

Riya

So how do I know which value a daemon is really using?

Arjun Sir

Ask it. Each daemon's web UI has a /conf page that lists every setting and which file it came from. Today: the files in etc/hadoop, the layers, the settings you'll change most, and the web UIs you'll open every day.

2 Definition

Hadoop configuration and web UIs

Formal definition (write this in exams)

Hadoop configuration is a set of name–value properties loaded in layers by the Configuration class: read-only defaults (core-default.xml, hdfs-default.xml, yarn-default.xml, mapred-default.xml, packaged in the jars), then site files in $HADOOP_CONF_DIR (by default $HADOOP_HOME/etc/hadoop: core-site.xml, hdfs-site.xml, yarn-site.xml, mapred-site.xml), then values set by programs or on the command line (-D). A later resource overrides an earlier one unless the earlier one marked the property <final>true</final>. Shell scripts (hadoop-env.sh, yarn-env.sh, mapred-env.sh) set environment variables such as JAVA_HOME and heap sizes; workers lists worker hosts. Each daemon also runs an embedded web server (NameNode 9870, DataNode 9864, ResourceManager 8088, NodeManager 8042, JobHistory Server 19888) with status pages and the /conf, /jmx and /logs endpoints.

In simple words

Hadoop has a default for everything. You change what you need in four XML files. A single command can change a setting just for itself. And every daemon has a web page where you can see its state and the settings it is really using.

Configuration at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner School rules, class rules, today's rule

  • The school rulebook (defaults) covers everything: “uniform every day”.
  • Your class teacher (site files) can change some rules for the class: “sports shoes on Friday”.
  • For one event (-D), a rule can change for that day only.
  • A rule marked final by the principal can't be changed by a later notice from a teacher.

Intermediate The files in etc/hadoop

  • core-site.xml: settings shared by everything (default file system, I/O, security).
  • hdfs-site.xml: NameNode and DataNode (replication, block size, storage folders, addresses).
  • yarn-site.xml: ResourceManager and NodeManagers (hosts, memory and cores per node, shuffle service).
  • mapred-site.xml: MapReduce jobs (framework, task memory, history server).
  • hadoop-env.sh / yarn-env.sh / mapred-env.sh: environment (Java, heap sizes, log and PID folders).
  • workers (hosts), capacity-scheduler.xml (YARN queues), log4j.properties (logging).

Advanced Rules that matter in production

  • Server vs client settings: dfs.replication and dfs.blocksize are applied by the client that writes a file; changing the NameNode's file does not change existing files or other clients.
  • Restart to apply: daemons read their site files at start-up. Some settings can be refreshed (hdfs dfsadmin -refreshNodes, yarn rmadmin -refreshQueues); most need a restart.
  • Same files everywhere: every node must have the same configuration; cluster managers push it and track versions.
  • final is for administrators protecting cluster-wide values from job configurations (job.xml), not a lock against code running in the same client.
  • Values can use ${other.property} and ${env.VAR}; units such as 256m or 30s are accepted by many properties.

Exam tip: For “Explain Hadoop configuration files”, list the four site files with one example property each (fs.defaultFS, dfs.replication, yarn.resourcemanager.hostname, mapreduce.framework.name), mention hadoop-env.sh (JAVA_HOME) and workers, and state the rule: site files override the defaults, and final properties cannot be overridden by later resources.

5 See it happen

One property, four layers

Follow dfs.replication through Kabir's experiments. Each terminal line is from the real run in Part 4.

Where does dfs.replication come from? 6 steps
What you see
  1. Inside Hadoop's jar, hdfs-default.xml says replication is 3.
  2. The running NameNode's /conf page shows the value 3 and its source: hdfs-site.xml (the cluster's own setting, also 3).
  3. Kabir writes one file with -D dfs.replication=2: that file gets 2 copies.
  4. -setrep changes the existing file to 3 copies and waits until the NameNode has made them.
  5. With final=true in the site file, -D still sets 2: final protects against later files, not a direct setting.
  6. Every file remembers the replication and block size it was written with.
Behind the screen
  1. The bottom layer always exists: every property has a default in the jars.
  2. Site files sit on top. Here the cluster's own file says 3 as well, so only the source changes.
  3. A client's -D sits on top of both, for that client's own work only.
  4. Replication of an existing file is changed with setrep, which tells the NameNode to add or remove copies.
  5. final stops later configuration files from overriding the value. A value set directly with -D or in code is not a file, so it still applies.
  6. The result is stored per file: four files, each with the settings it was written with.

Try it yourself: settings in the playground

The upload controls are settings a client sends: Block is dfs.blocksize and Replication is dfs.replication. Change them per upload and compare the files in the NameNode metadata tab.

6 Real-world use

Configuration and UIs at work

1. Configuration under version control

Site files live in Git or in the cluster manager, with a history of every change. A change is reviewed, pushed to all nodes, and followed by a rolling restart, one node at a time.

Change + review→Push to all nodes→Rolling restart

2. Per-job tuning without touching the cluster

A heavy nightly job asks for more memory per task and a specific queue with -D options, while every other job keeps the cluster defaults.

Cluster defaults→Job overrides→Only that job changes

3. Monitoring from /jmx

Monitoring systems (Prometheus exporters, Grafana dashboards, cluster managers) poll the daemons' /jmx endpoints for live DataNodes, capacity, missing blocks and queue usage, and page the on-call engineer when thresholds are crossed.

/jmx→Dashboards→Alerts

4. The UIs are the first stop in an incident

When users say “jobs are slow”, engineers open the ResourceManager UI (queues full? nodes lost?) and the NameNode UI (dead DataNodes? safe mode? disk full?) before reading any log.

Complaint→RM + NN UIs→Then logs

Simplified; organisations differ in tools and policies.

7 Run the code

Merge configuration layers like Hadoop does

This program loads three layers in order (defaults, site file, command line) and keeps the last value for each property, unless an earlier layer marked it final and the later layer is a file. It also records the source, like the /conf page.

layers = [
    ("hdfs-default.xml", "file", {"dfs.replication": "3", "dfs.blocksize": "134217728"}, set()),
    ("hdfs-site.xml", "file", {"dfs.replication": "1"}, {"dfs.replication"}),
    ("job.xml", "file", {"dfs.replication": "5", "dfs.blocksize": "268435456"}, set()),
]

conf, source, final = {}, {}, set()
for name, kind, props, finals in layers:
    for key, value in props.items():
        if key in final and kind == "file":
            print(f"ignored {key}={value} from {name} (final)")
            continue
        conf[key], source[key] = value, name
    final |= finals

for key in conf:
    print(f"{key:16} = {conf[key]:>10}  [{source[key]}]")
ignored dfs.replication=5 from job.xml (final) dfs.replication = 1 [hdfs-site.xml] dfs.blocksize = 268435456 [job.xml]
  • ("hdfs-site.xml", "file", {"dfs.replication": "1"}, {"dfs.replication"}),The site file sets replication to 1 and marks it final (the last item is the set of final names).
  • if key in final and kind == "file":A later file cannot override a final property. (Values set directly, like -D, are not files: try challenge 2.)
  • final |= finalsFinals are added only after the layer is loaded, so they protect against later layers.

Run it on your PC: a configuration report from a live NameNode

With your cluster from Lesson 4.3 running, this program reads the NameNode's /conf page and reports how many settings come from each file, plus the value and source of four important ones. Save it as conf_report.py and run it on the same computer.

Where do the NameNode's 1,752 settings come from?

# conf_report.py: which settings is the NameNode really using, and from which file?
import urllib.request
import xml.etree.ElementTree as ET
from collections import Counter

URL = "http://localhost:9870/conf"           # NameNode web UI
root = ET.fromstring(urllib.request.urlopen(URL).read())

props = {}
for p in root.iter("property"):
    props[p.findtext("name")] = (p.findtext("value"), p.findtext("source"))

print(f"{len(props)} properties loaded")
for source, n in Counter(src for _, src in props.values()).most_common():
    print(f"{n:>5}  {source}")

print()
for key in ["fs.defaultFS", "dfs.replication", "dfs.blocksize", "dfs.namenode.name.dir"]:
    value, source = props.get(key, ("(not set)", "-"))
    print(f"{key:24} = {value}   [{source}]")

Interview and viva questions

What are the main configuration files in Hadoop?

core-site.xml (common settings such as fs.defaultFS), hdfs-site.xml (HDFS: replication, block size, storage folders, addresses), yarn-site.xml (YARN: ResourceManager host, NodeManager resources, auxiliary services), mapred-site.xml (MapReduce: framework, task memory, history server), plus hadoop-env.sh, yarn-env.sh and mapred-env.sh for environment variables, and workers for the list of worker hosts.

What is the difference between core-default.xml and core-site.xml?

core-default.xml ships inside Hadoop's jars and holds the default for every core property; it is read-only reference. core-site.xml is your file in etc/hadoop that overrides the defaults you want to change.

What is a final property in Hadoop?

A property marked <final>true</final> cannot be overridden by configuration resources loaded later, for example the job.xml of a submitted job. Administrators use it to protect cluster-wide values. It does not stop a program from setting the value directly in its own configuration object.

How do I check the value of a configuration property?

Use hdfs getconf -confKey <name> for the merged value seen by the client, or open http://<daemon-host>:<port>/conf to see what a running daemon uses, including the source file.

What are the default web UI ports in Hadoop 3?

NameNode 9870, SecondaryNameNode 9868, DataNode 9864, ResourceManager 8088, NodeManager 8042, MapReduce JobHistory Server 19888. (Hadoop 2 used 50070 for the NameNode and 50075 for DataNodes.)

Do I need to restart Hadoop after changing configuration?

Usually yes: daemons read site files at start-up. Some changes can be refreshed without a restart, for example hdfs dfsadmin -refreshNodes for include/exclude lists and yarn rmadmin -refreshQueues for scheduler queues. Client-side settings take effect on the next command.

Can I change the replication of an existing file?

Yes, with hdfs dfs -setrep <n> <path> (-w waits for completion). Changing dfs.replication in hdfs-site.xml only affects files written afterwards by clients that use that file.

copy2.csv: 2 replicas, 128 MB blocks, 4.5 MB

How it works: copy2.csv: 2 replicas, 128 MB blocks, 4.5 MB of data.

Parse a property line

Extract the name, value and source from a real /conf line.

import re

P7Business problem

Cost of the 90% disk rule

A 20-node cluster has 12 disks of 4 TB per node. The NodeManager disk check marks a disk bad above 90% use. How much raw capacity (TB) sits in that last 10% across the cluster?

Input
20 nodes × 12 × 4 TB · 10%
Expected output
raw 960 TB, top 10% = 96 TB
Show solution and explanation 
raw_tb = 20 * 12 * 4
print(f"raw {raw_tb} TB, top 10% = {raw_tb * 0.10:.0f} TB")
raw 960 TB, top 10% = 96 TB

How it works: 96 TB of 960 TB. That headroom is deliberate: full disks cause failed tasks and slow writes, so admins alert well before 90%.

P8Advanced

Unit-aware sizes

Many properties accept units (k, m, g, t). Convert "128m", "1g", "512k" and "134217728" to bytes.

Input
128m · 1g · 512k · 134217728
Expected output
      128m -> 134,217,728 bytes
        1g -> 1,073,741,824 bytes
      512k -> 524,288 bytes
 134217728 -> 134,217,728 bytes
Show solution and explanation 
def to_bytes(v):
    units = {"k": 1, "m": 2, "g": 3, "t": 4}
    if v[-1].lower() in units:
        return int(v[:-1]) * 1024 ** units[v[-1].lower()]
    return int(v)
for v in ["128m", "1g", "512k", "134217728"]:
    print(f"{v:>10} -> {to_bytes(v):,} bytes")
128m -> 134,217,728 bytes 1g -> 1,073,741,824 bytes 512k -> 524,288 bytes 134217728 -> 134,217,728 bytes

How it works: 128m = 134,217,728; 1g = 1,073,741,824; 512k = 524,288; and a plain number is already bytes.

Real-world scenario questions (asked in company interviews)

Configuration questions are about reasoning: where does a value come from, and how do you prove it?

Admin · configFresher

“I changed dfs.replication to 2 but files still have 3 copies”

An admin edited hdfs-site.xml on the NameNode host. New uploads from the edge node still show replication 3 and old files are unchanged.

The interviewer is checking: client-side vs server-side settings.

Show a strong answer
  • Replication is chosen by the writing client per file. The edge node still has its own hdfs-site.xml with 3.
  • Update and distribute the configuration to clients (and all nodes); verify with hdfs getconf -confKey dfs.replication on the edge node.
  • Existing files keep their replication; change them with hdfs dfs -setrep -w 2 /path if needed.
Admin · troubleshootingFresher

“How do you know which value a daemon is using?”

Two engineers disagree about the NodeManager memory setting on a worker.

The interviewer is checking: do you know how to check instead of guessing?

Show a strong answer
  • Open http://<worker>:8042/conf: it shows the value the running NodeManager loaded, and its source file.
  • Compare with the file on disk; if they differ, the daemon was not restarted after the change.
  • The ResourceManager Nodes page also shows each node's total memory and vcores.
Platform · governanceExperienced

Users keep overriding a cluster setting in their jobs

Some teams submit jobs with very large task memory, starving others. The platform team wants to stop job configurations from overriding certain values.

The interviewer is checking: what final does and does not do, and the right tools for limits.

Show a strong answer
  • Mark cluster-wide values final in the site files on the nodes, so a job's job.xml cannot override them there.
  • Know its limit: a client can still set a value directly in its own process, so final is not a security control.
  • Enforce limits on the server side: YARN's maximum allocation (yarn.scheduler.maximum-allocation-mb) and queue capacities in the scheduler.
  • Monitor usage per queue and review exceptions.
Operations · monitoringExperienced

Set up basic monitoring for a new cluster

A small company has just built a Hadoop cluster and has no monitoring yet.

The interviewer is checking: do you know where the metrics come from and what matters?

Show a strong answer
  • Collect metrics from each daemon's /jmx endpoint (or a Prometheus exporter that reads it).
  • Alert on: dead DataNodes, missing or under-replicated blocks, HDFS capacity, safe mode, NodeManagers lost or unhealthy, queue usage and failed applications.
  • Dashboards for trends (capacity growth, job durations) and links to the NameNode and ResourceManager UIs for investigation.
