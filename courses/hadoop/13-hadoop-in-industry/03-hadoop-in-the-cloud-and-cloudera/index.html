Hadoop in the cloud, and Cloudera

Most new Hadoop-style work now runs on clusters that exist only while a job runs, reading data from cloud object storage. Many regulated companies still run Cloudera in their own data centres, often with the cloud on the side. This lesson explains the cloud pattern, compares the managed services as of October 2026, and puts numbers on always-on versus per-job clusters using measurements from our lab.

1 The story

A cluster that exists for three hours a night

Kabir's new company streams cricket and films. Every night a job crunches the day's viewing logs into recommendations. Their old Hadoop cluster ran 24 hours a day for a job that needed three. Now the logs sit in cloud object storage. At 1 AM a script creates 20 machines, runs the job, writes the results back and deletes the machines. The data stays; the cluster does not.

2 Definition

Hadoop in the cloud

Formal definition (write this in exams)

Hadoop in the cloud means running Hadoop-ecosystem engines (YARN, Spark, Hive, Trino, HBase and others) on rented virtual machines or containers, usually as a managed service such as Amazon EMR, Google Cloud Dataproc or Azure HDInsight, with data kept in object storage (Amazon S3, Google Cloud Storage, Azure Data Lake Storage) accessed through Hadoop file-system connectors (s3a://, gs://, abfs://) instead of HDFS. This separation of compute and storage allows clusters to be created per job (transient), resized automatically (autoscaling) and run partly on discounted interruptible capacity (spot or preemptible instances), while table metadata lives in a shared catalog. Cloudera provides a commercial distribution of the same open-source stack for on-premises data centres and public clouds, with central management, security and governance.

In simple words

The data sits in cheap cloud storage that never switches off. When there is work, you rent a cluster for an hour, point it at the data, and delete it afterwards. Cloudera sells the same Hadoop tools, packaged and supported, for companies that run their own servers.

Words you'll meet in this lesson

Architecture at a glance

Left: the classic cluster, where every worker stores blocks and runs containers. Right: the cloud pattern, where storage is a service and clusters are temporary.

The cloud at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Renting a kitchen by the hour

  • An always-on cluster is like owning a big kitchen that you use for three hours a day. Rent, electricity and staff are paid all day.
  • In the cloud the ingredients (data) stay in a cold store that never closes. You rent a kitchen (a cluster) when it is time to cook, and hand it back after.
  • The recipes (Spark, Hive, MapReduce) are the same. Only the kitchen is temporary.

Intermediate What changes when storage leaves the cluster

  • Paths: hdfs://namenode/data becomes s3a://bucket/data, gs://bucket/data or abfs://container@account.dfs.core.windows.net/data. Jobs barely change.
  • Locality: blocks are no longer on the worker, so every read crosses the network. Cloud networks are fast, and engines read columnar files (Lesson 10.2), so this is usually fine.
  • Renames are slow: in object stores a "rename" copies the data. Classic MapReduce output commit renames folders, so use the cloud-aware committers (for example the S3A "magic" committer) or table formats like Iceberg that commit by writing metadata.
  • Metadata must be shared: because clusters are deleted, the metastore or catalog runs outside them (Glue, a managed Hive metastore, an Iceberg REST catalog).

Advanced Elasticity, interruption and governance

  • Autoscaling watches pending YARN containers (Lesson 11.3) and adds workers; it removes them when the queue is empty, after graceful decommissioning (Lesson 6.4 idea).
  • Spot/preemptible workers are much cheaper but can disappear. MapReduce and Spark rerun lost tasks (Lesson 8.6), so put them on task-only nodes and keep the AM and driver on regular nodes.
  • Security moves from Kerberos keytabs (Lesson 12.5) to cloud identity (IAM roles), though Kerberos and Ranger still appear on long-running clusters and in Cloudera.
  • Cost governance becomes engineering: tags, budgets, auto-termination of idle clusters, lifecycle rules that move old objects to colder storage classes.

Animated example: one night on a transient cluster

A streaming company's nightly job 6 steps
Animated example
  1. 01:00: a scheduler (Airflow, say) asks the cloud for a cluster; four workers boot from a managed image.
  2. 01:06: Spark reads the day's logs directly from object storage; the shared catalog tells it where the table lives.
  3. 01:20: YARN has many pending containers, so autoscaling adds four cheaper spot workers.
  4. 03:40: results are committed as an Iceberg table. One spot worker was reclaimed; its tasks reran elsewhere.
  5. 04:00: the job is done and the cluster is terminated. Data and table definitions remain in storage and the catalog.
  6. The bill: only the hours the machines existed, plus storage. (Illustrative story; times and sizes are examples.)

The most common cloud waste is a cluster nobody remembered to stop. Every managed service has an auto-termination or idle-timeout setting; turn it on before the first job, and tag clusters with an owner and a cost centre.

4 Step by step

Deciding with numbers

We did not create cloud resources for this lesson, so there is no cloud lab output here. Instead we feed numbers we measured on our own cluster into a small calculator, cloud_vs_onprem.py, with prices clearly marked as illustrative.

  1. Measure your own throughput first

    DistCp, 5 files, 162 MB, prod → DR          25.5 s   (Lesson 12.2)
TestDFSIO write, 1 task                     113 MB/s (Lesson 12.3)
TestDFSIO write, 6 tasks, aggregate         ~210 MB/s on one shared laptop disk
Spark on YARN, item revenue, wall time      ~46–50 s incl. executor start (Lesson 13.2)
    Cloud sizing starts with how fast your jobs and copies really are. Our laptop numbers are small, but the method is the same on a 200-node cluster.

  2. Compare compute: always-on vs per-night

    always_on = workers * 24 * 30 * NODE_HOUR
transient = workers * (job_hours + 0.25) * 30 * NODE_HOUR
    always-on 20 workers : Rs 576,000 transient, 3h15m a night : Rs 78,000 (14% of always-on) transient, 4 core + 16 spot: Rs 40,560 (7%)
    The ratio is what matters: 3 h 15 min of 24 h is 14%. Spot workers cut it further. Prices are placeholders: check the provider's price page.

  3. Compare storage: three copies on disks vs object storage

    hdfs = data_tb * 3 / 0.7 * DISK_TB_MONTH   # x3 copies, disks at most 70% full
obj  = data_tb * OBJECT_TB_MONTH
    HDFS: 429 TB of raw disk : Rs 385,714 object storage, 100 TB : Rs 170,000
    100 TB in HDFS needs about 429 TB of raw disk (three copies, 30% headroom, Lesson 12.3). Erasure coding (Lesson 7.3) or Parquet compression (Lesson 10.2) shrink both sides.

  4. Estimate the move

    mb_s = gbps * 1000 / 8 * 0.7      # 70% of the link usable
    at our lab's DistCp speed (6.4 MB/s): 191 days over a 1 Gbps link at 70% use (88 MB/s): 13.9 days over a 10 Gbps link at 70% use (875 MB/s): 1.4 days
    Migration is often limited by the network link, not by Hadoop. Large moves use dedicated links or physical transfer appliances, and DistCp with -update catches up the changes made during the copy.

  5. Change the paths, not the logic

    spark-submit job.py hdfs://namenode/user/hadoop/data/student_orders.csv   # our lab
spark-submit job.py s3a://canteen-data/orders/                              # AWS
spark-submit job.py gs://canteen-data/orders/                               # Google Cloud
    The Hadoop FileSystem API (Lesson 6.5) hides the store behind a URI scheme. What changes is configuration: credentials come from cloud roles, and output commit uses a cloud-aware committer.

Copying data to the cloud is easy; copying it back can cost a lot (data egress is usually billed) and take weeks. Decide early which copy is the master and keep the other in sync with DistCp -update or snapshot-diff (Lesson 12.2).

5 See it happen

The same job, two lifecycles

Six steps of one nightly job: on a long-running on-premises cluster (left in each picture) and on a transient cloud cluster.

On-prem vs cloud job lifecycle 6 steps
What you see
  1. On-prem the cluster is always running; in the cloud the job starts by creating one with auto-termination on.
  2. The job itself is the same; only the input URI changes from hdfs:// to s3a://.
  3. On-prem most maps read local blocks; in the cloud every read crosses the network.
  4. When work piles up, on-prem jobs wait in the queue; the cloud cluster grows with spot workers.
  5. Committing output differs: an HDFS rename is cheap, an object-store rename is a copy, so cloud jobs use special committers or table formats.
  6. Afterwards the on-prem cluster idles and the cloud cluster is deleted. (Costs illustrative.)
Behind the screen
  1. On-prem the workers are already up; in the cloud a few workers boot from a managed image.
  2. Both run YARN and Spark; one reads HDFS, the other object storage through the s3a connector.
  3. On-prem tasks find their blocks on the same node; cloud tasks stream data over the network.
  4. On-prem a full queue means waiting; the cloud cluster adds spot workers for the peak.
  5. On-prem the committer renames a temporary folder; in the cloud the commit writes metadata instead of renaming.
  6. On-prem the machines idle until the next run; the cloud cluster is gone and only storage remains.

Interview and viva questions

Is Hadoop still used in the cloud?

Its pieces are. Managed services such as Amazon EMR and Google Dataproc run YARN, Spark, Hive, HBase and other Hadoop-ecosystem projects, and Hadoop's FileSystem connectors (s3a, gs, abfs) are how those engines read cloud storage. What is used less is HDFS as the main store: data usually lives in object storage and clusters are temporary.

What is the difference between HDFS and Amazon S3 for Hadoop jobs?

HDFS stores blocks on the cluster's own disks with three copies, gives data locality and cheap renames, but lives and dies with the cluster. S3 is a separately billed object store, independent of any cluster, without data locality and where a rename is a copy. Jobs switch by changing hdfs:// to s3a:// and using a suitable committer.

What is a transient cluster?

A cluster created for a job or a batch window and deleted when the work finishes. Because the data is in object storage and table definitions are in a shared catalog, nothing is lost when the machines go away, and you pay only for the hours they ran.

What does Cloudera offer today?

A supported distribution of the open-source data stack (Hadoop, Hive, Impala, Spark, HBase, Kafka, Ranger, Atlas and others) for your own data centres (Cloudera Base on premises, with 7.3.2 announced in March 2026 as an LTS release supported through 2032) and for public clouds, managed with Cloudera Manager. Hortonworks merged into Cloudera in 2019, and MapR's platform became HPE Ezmeral Data Fabric.

Should a company move its Hadoop cluster to the cloud?

It depends on utilisation, data rules and skills. Bursty or mostly idle workloads usually save money on transient cloud clusters; steady, heavily used clusters may be cheaper on owned hardware; regulated data may need to stay in a specific location. Many organisations choose a hybrid. Compare with your own measured throughput and real prices, and treat this lesson's numbers as illustrative.

Transient clusters cost 15 extra minutes per run. Above how many busy hours a day does always-on become cheaper, if spot gives no discount?

Input
hours + 0.25 vs 24
Expected output
6 transient cheaper
12 transient cheaper
18 transient cheaper
23 transient cheaper
23.75 always-on cheaper or equal
24 always-on cheaper or equal
Show solution and explanation 
for h in [6, 12, 18, 23, 23.75, 24]:
    print(h, "transient cheaper" if h + 0.25 < 24 else "always-on cheaper or equal")
6 transient cheaper 12 transient cheaper 18 transient cheaper 23 transient cheaper 23.75 always-on cheaper or equal 24 always-on cheaper or equal

How it works: Only above 23.75 hours: without other differences, per-run clusters win almost always on compute; in practice storage, start-up delays and staff time decide.

P5Medium

Spot savings

A nightly job uses 10 workers for 5 hours at ₹40/hour; 8 of them can be spot at 60% off (illustrative). What is the monthly saving?

Input
10 workers · 5 h · 30 nights
Expected output
Rs 60,000 -> Rs 31,200, saving Rs 28,800
Show solution and explanation 
full = 10 * 5 * 30 * 40
spot = 2 * 5 * 30 * 40 + 8 * 5 * 30 * 40 * 0.4
print(f"Rs {full:,.0f} -> Rs {spot:,.0f}, saving Rs {full - spot:,.0f}")
Rs 60,000 -> Rs 31,200, saving Rs 28,800

How it works: ₹60,000 → ₹31,200, saving ₹28,800 a month (illustrative), as long as reruns after reclaimed workers stay rare.

Input

P8Advanced

Pick the platform

Write a function that suggests on-prem, cloud or hybrid from three answers: data must stay on own premises (yes/no), average utilisation (0–1), burstiness (low/high).

Input
3 inputs
Expected output
(True, 0.8, 'high') -> hybrid: regulated data on-prem, masked data to the cloud for peaks
(False, 0.15, 'high') -> cloud with transient clusters
(False, 0.85, 'low') -> compare carefully: steady load can be cheaper on owned hardware
(True, 0.5, 'low') -> on-prem (e.g. Cloudera Base)
Show solution and explanation 
def suggest(on_prem_rule, utilisation, burst):
    if on_prem_rule and burst == "high":
        return "hybrid: regulated data on-prem, masked data to the cloud for peaks"
    if on_prem_rule:
        return "on-prem (e.g. Cloudera Base)"
    if utilisation > 0.7 and burst == "low":
        return "compare carefully: steady load can be cheaper on owned hardware"
    return "cloud with transient clusters"
for case in [(True, 0.8, "high"), (False, 0.15, "high"), (False, 0.85, "low"), (True, 0.5, "low")]:
    print(case, "->", suggest(*case))
(True, 0.8, 'high') -> hybrid: regulated data on-prem, masked data to the cloud for peaks (False, 0.15, 'high') -> cloud with transient clusters (False, 0.85, 'low') -> compare carefully: steady load can be cheaper on owned hardware (True, 0.5, 'low') -> on-prem (e.g. Cloudera Base)

How it works: A simple rule of thumb in code. Real decisions also weigh skills, contracts and exit costs.

Real-world scenario questions (asked in company interviews)

Cloud-migration and platform questions are common for senior data engineers and architects.

Cloud · basicsFresher

“How is running Spark on EMR or Dataproc different from our Hadoop cluster?”

An interviewer checks whether you understand the cloud pattern.

The interviewer is checking: compute–storage separation.

Show a strong answer
  • Same engines (YARN, Spark, Hive), but data in object storage via s3a:// or gs://, not HDFS.
  • Clusters can be transient and autoscaled; you pay per hour; spot workers for task nodes.
  • Differences to handle: no data locality, renames are copies (use the right committer), shared catalog outside the cluster.
Migration · designExperienced

Plan the migration of a 1 PB on-prem cluster to the cloud

Hundreds of Hive tables, nightly Spark and MapReduce jobs, a 6-month deadline.

The interviewer is checking: phasing and risk control.

Show a strong answer
  • Inventory tables, jobs, owners and dependencies; decide what to retire.
  • Bulk copy with DistCp in waves, keep in sync with -update or snapshot-diff; migrate the metastore.
  • Move jobs table by table with parallel runs and result comparison; then switch, then decommission. Estimate network time first (1 PB at 10 Gbps ≈ 2 weeks of pure transfer).
Cost · operationsExperienced

“Our cloud bill doubled after moving off Hadoop. Why?”

A manager expected savings.

The interviewer is checking: cloud cost habits.

Show a strong answer
  • Lift-and-shift kept always-on clusters sized for peak; enable autoscaling, auto-termination and spot task nodes.
  • Check egress, small files and full-table scans (use Parquet/ORC, partitioning).
  • Tag resources per team and set budgets and alerts.
Platform · strategyArchitect

A bank asks: Cloudera on-prem, cloud, or both?

Regulated customer data, steady ETL, bursty data-science work.

The interviewer is checking: balanced reasoning without legal claims.

Show a strong answer
  • Start from data rules (confirmed with compliance), then utilisation and burst patterns.
  • Steady, regulated workloads fit on-prem (e.g. Cloudera Base with Ranger/Atlas); bursts fit cloud with masked data.
  • Plan one identity, one catalog and one policy model across both, or the hybrid becomes two silos.
