The Hadoop ecosystem: Hive, HBase, ZooKeeper and more

Hadoop itself is HDFS, YARN and MapReduce. Around it grew a family of projects that let analysts write SQL, apps look up single rows, pipelines ingest events and admins secure everything. This lesson maps them by layer, marks which are alive and which retired, and runs SQL on our own cluster to show the MapReduce pattern still inside.

2 Definition

The Hadoop ecosystem

Formal definition (write this in exams)

The Hadoop ecosystem is the set of open-source projects built to work with the core Hadoop components — the HDFS distributed file system, the YARN resource manager and the MapReduce processing framework. It includes storage and table layers (HBase, Ozone, Apache Iceberg/Delta Lake/Apache Hudi), a shared metastore for table definitions, processing engines (Tez, Spark, Flink), SQL engines (Hive, Impala, Trino, Spark SQL, Drill), coordination (ZooKeeper), ingestion (Kafka, NiFi), workflow scheduling, security and governance (Ranger, Knox, Atlas) and cluster management tools. These components read and write data in HDFS or compatible storage and usually run their work as YARN applications, so one cluster can serve batch, interactive SQL, streaming and low-latency lookups.

In simple words

Hadoop is the ground floor: a place to keep huge files and a way to share machines. The ecosystem is everything built on that floor so that different people can use the data in their own way: SQL for analysts, fast lookups for apps, pipelines for engineers.

Architecture at a glance

The ecosystem in layers, bottom to top. Everything runs on HDFS (or cloud object storage) and most of it runs inside YARN containers. Grey boxes are retired or dormant projects you will still meet in older clusters and job descriptions.

The ecosystem at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A railway station, not a train

  • Think of HDFS as the tracks and YARN as the station master who decides which platform each train gets.
  • MapReduce was the first train. Later came faster trains (Tez, Spark) on the same tracks.
  • Hive and Trino are ticket counters that speak SQL; HBase is the enquiry window that answers one question instantly; ZooKeeper is the signal system everybody trusts.
  • Some counters closed over the years (Sqoop, Oozie) and new ones opened (Airflow, Iceberg). The tracks stayed.

Intermediate One job per project

  • Hive: SQL tables over files; the Hive Metastore became the shared catalogue every engine reads.
  • HBase: random reads and writes by row key on top of HDFS, e.g. a delivery app looking up a restaurant by ID.
  • ZooKeeper: who is the active NameNode (Lesson 7.1), which HBase server owns which rows, Kafka's older controller.
  • Kafka: a durable log of events (orders, clicks) that pipelines read in order. NiFi: drag-and-drop data flows.
  • Spark / Tez / Flink: engines that replaced MapReduce for most jobs; Flink for continuous streams.
  • Ranger, Knox, Atlas: access policies, a secure gateway, and lineage/catalog (Lesson 12.5).

Advanced How they map onto the core

  • Almost every engine is a YARN application: its own ApplicationMaster plus containers (Lesson 11.2). Our Spark SQL query ran exactly like that.
  • Data lives in HDFS files; the metastore only stores schema + location, which is why one table can be read by Hive, Spark and Trino.
  • Engines still follow map → shuffle → reduce; Spark's plan shows partial aggregation, an Exchange (shuffle) and final aggregation.
  • HBase is the exception: long-running RegionServers keep data in memory and write HFiles to HDFS; it uses ZooKeeper, not YARN, for coordination.

Exam tip: For “Explain the Hadoop ecosystem”, draw three layers (storage HDFS, resource management YARN, processing engines) and place 6–8 projects with one line each: Hive (SQL), HBase (NoSQL, random access), ZooKeeper (coordination), Spark (in-memory processing), Kafka (ingestion), Ranger (security). Mention that Sqoop and Oozie are retired.

4 Step by step

SQL on Hadoop, on our own cluster

We added Spark 4.0.4 (downloaded from dlcdn.apache.org) to the Module 8 lab's namenode container and ran spark-sql on YARN with three 512 MB executors. The SQL file is in “Run it on your PC”.

  1. Define a table over an existing HDFS file

    CREATE TABLE canteen.orders (order_id BIGINT, student STRING, ts STRING, item STRING, amount INT)
  USING csv OPTIONS (path 'hdfs://namenode/user/hadoop/data/student_orders.csv');
    Time taken: 0.753 seconds
    Nothing was copied. The metastore stored the columns and the file location: under a second.

  2. Look at what the metastore knows

    DESCRIBE TABLE EXTENDED canteen.orders;
    Type EXTERNAL Provider csv Location hdfs://namenode/user/hadoop/data/student_orders.csv Serde Library org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe
    EXTERNAL means dropping the table leaves the file alone. The Hive class names show where the metastore idea came from.

  3. Ask a business question

    SELECT item, count(*) AS orders, sum(amount) AS revenue
FROM canteen.orders GROUP BY item ORDER BY revenue DESC;
    thali 30292 2423360 dosa 49927 2246715 chai 149669 2245035 vada pav 69754 1395080 … coffee 40364 807280 Time taken: 11.084 seconds, Fetched 8 row(s)
    The same numbers our Java jobs produced in Module 9, written as one SQL statement. Thali earns most with the fewest orders.

  4. A second question, no new code

    SELECT substr(ts, 12, 2) AS hour, count(*) AS orders
FROM canteen.orders GROUP BY 1 ORDER BY orders DESC LIMIT 3;
    14 62213 13 56026 08 55852 Time taken: 2.838 seconds, Fetched 3 row(s)
    Lunch (13–14 h) and breakfast (08 h) are the rush hours. With Java MapReduce this would be a new Mapper, Reducer and jar.

  5. See MapReduce inside the plan

    EXPLAIN SELECT item, count(*) FROM canteen.orders GROUP BY item;
    +- HashAggregate(keys=[item#14], functions=[count(1)]) +- Exchange hashpartitioning(item#14, 200) +- HashAggregate(keys=[item#14], functions=[partial_count(1)]) +- FileScan csv spark_catalog.canteen.orders[item#14] … ReadSchema: struct<item:string>
    Read from the bottom: scan only the item column, count per item inside each task (a combiner, Lesson 9.1), shuffle by hash of item (Lesson 9.2), add the partial counts (the reduce).

Our lab did not run Apache Hive itself: Hive 4.2 needs JDK 21 while the Hadoop image has JDK 17, and the Hive 4.1 download was too slow. Spark SQL uses the same table-and-metastore model, so the steps carry over; on a real cluster you would type the same SQL into Hive's Beeline.

5 See it happen

One SQL query through the stack

Six steps of our real spark-sql run: what the terminal showed, and which ecosystem layer did the work.

SQL → plan → YARN → HDFS 6 steps
What you see
  1. spark-sql starts as a YARN application in the default queue.
  2. The CREATE TABLE takes under a second: it only writes a definition.
  3. DESCRIBE shows an external table pointing at the HDFS file, with Hive classes.
  4. EXPLAIN shows partial aggregation, a hash shuffle and the final aggregation.
  5. The query returns 8 rows in 11.1 s; thali earns the most.
  6. A second question about rush hours takes 2.8 s: executors are already running.
Behind the screen
  1. The driver asks the ResourceManager for three executor containers, like any YARN application.
  2. CREATE TABLE touches only the metastore; HDFS is not read.
  3. DESCRIBE reads columns, location and format back from the metastore.
  4. The optimizer builds a plan with a combiner-like partial count, a hash shuffle and a final count.
  5. Executors read HDFS splits near the data, count locally and shuffle by item.
  6. The second query reuses the running executors, so it finishes in under 3 s.

7 Run the code

Pick the right tool, then run a GROUP BY by hand

Part one is a tiny rule engine: describe a requirement and it suggests ecosystem projects. Part two does what our SQL engine did for GROUP BY item: partial counts per task (map + combine), a shuffle by key, and a final sum (reduce).

RULES = [  # (keyword in the requirement, suggestion)
    ("sql", "Hive / Spark SQL / Trino over metastore tables"),
    ("single row", "HBase (get by row key)"),
    ("events", "Kafka, then Spark or Flink"),
    ("update", "Iceberg / Delta / Hudi table format"),
    ("schedule", "Airflow (Oozie is retired)"),
    ("leader", "ZooKeeper"),
    ("access", "Ranger policies + Kerberos"),
]
def pick(req):
    return [tool for key, tool in RULES if key in req.lower()] or ["plain HDFS files + Spark"]

for r in ["Analysts need SQL on 3 years of bills",
          "App must fetch a single row per customer in 10 ms",
          "Clickstream events every second, update totals"]:
    print(f"{r[:44]:44} -> {pick(r)}")

# GROUP BY item, the way the plan executed it
tasks = [["chai", "dosa", "chai"], ["thali", "chai"], ["dosa", "chai", "thali"]]
partial = []
for t in tasks:                               # HashAggregate partial_count, per task
    counts = {}
    for item in t:
        counts[item] = counts.get(item, 0) + 1
    partial.append(counts)
print("partial counts:", partial)
final = {}
for counts in partial:                        # Exchange (shuffle by item) + final count
    for item, n in counts.items():
        final[item] = final.get(item, 0) + n
print("final        :", dict(sorted(final.items())))

Interview and viva questions

What are the main components of the Hadoop ecosystem?

The core is HDFS (storage), YARN (resource management) and MapReduce (processing). Around it: Hive and other SQL engines (Spark SQL, Trino, Impala), HBase for low-latency key access, ZooKeeper for coordination, Spark, Tez and Flink as processing engines, Kafka and NiFi for ingestion, Airflow for scheduling, Ranger, Knox and Atlas for security and governance, and table formats such as Apache Iceberg.

What is the difference between Hive and HBase?

Hive is a SQL engine over files: good for scanning and aggregating large tables, with query times of seconds to minutes. HBase is a NoSQL store for reading and writing individual rows by key in milliseconds. Many systems use both: HBase to serve applications, Hive or Spark for analytics.

Is Sqoop still used?

Apache Sqoop was retired to the Apache Attic in June 2021, and Amazon EMR stopped including it from release 7.4.0. Older clusters may still run it, but new pipelines usually use Spark JDBC reads or change-data-capture into Kafka.

Why does Hadoop need ZooKeeper?

Distributed services must agree on facts such as which NameNode is active or which HBase server owns which rows, even when machines fail. ZooKeeper provides a small, replicated, strongly consistent store with watches and ephemeral nodes that these services use for leader election, locks and configuration.

What is the Hive metastore?

A service and database holding table and partition definitions: column names and types, storage format, and file locations. Hive, Spark, Trino, Impala and others share it, so a table defined once can be queried by many engines.

P8Advanced

Mini metastore

Build a dict-based metastore with create, describe and drop; EXTERNAL drop keeps files, MANAGED drop deletes them.

Input
2 tables
Expected output
tables: {} files left: {'/data/orders.csv'}
Show solution and explanation 
files = {"/data/orders.csv", "/warehouse/menu"}
ms = {"orders": ("EXTERNAL", "/data/orders.csv"), "menu": ("MANAGED", "/warehouse/menu")}
def drop(t):
    kind, loc = ms.pop(t)
    if kind == "MANAGED":
        files.discard(loc)
drop("orders"); drop("menu")
print("tables:", ms, "files left:", files)
tables: {} files left: {'/data/orders.csv'}

How it works: Only the external table's file survives, the same rule Hive and Spark follow.

Real-world scenario questions (asked in company interviews)

Ecosystem questions test whether you know what each tool is for, and what is current.

Concepts · mapFresher

“Draw the Hadoop ecosystem”

A whiteboard question in most big-data interviews.

The interviewer is checking: layers and one purpose per tool.

Show a strong answer
  • Bottom: HDFS (or object storage); middle: YARN; top: engines (MapReduce, Tez, Spark) and SQL (Hive, Trino).
  • Side services: HBase for key lookups, ZooKeeper for coordination, Kafka for ingestion, Airflow for scheduling, Ranger for security.
  • Mention what changed: Sqoop and Oozie retired; Iceberg-style table formats are now common.
Design · storageExperienced

“Hive or HBase for our customer 360 view?”

The app needs one customer instantly; analysts need segments over all customers.

The interviewer is checking: access patterns.

Show a strong answer
  • Point reads by key with low latency → HBase (row key design, avoid hot spots).
  • Scans and aggregations → Parquet/Iceberg tables queried with Hive, Spark or Trino.
  • Feed both from the same pipeline; don't force one store to do both jobs.
Operations · migrationExperienced

Your cluster still runs Sqoop and Oozie

Both are retired. The manager asks what to do and how risky it is.

The interviewer is checking: awareness and a safe plan.

Show a strong answer
  • Retired means no releases or security fixes; vendors may still ship them for a while, but plan to leave.
  • Sqoop → Spark JDBC or CDC into Kafka; Oozie → Airflow DAGs calling the same jobs.
  • Migrate in waves with side-by-side runs and output comparison; retire the old ones last.
Internals · enginesFresher

“Does Hive still use MapReduce?”

A follow-up after you mention Hive.

The interviewer is checking: engines vs SQL layer.

Show a strong answer
  • Hive is a SQL layer; the execution engine is pluggable. Hive 4 encourages Tez; MapReduce was the original engine.
  • Whatever the engine, a GROUP BY becomes partial aggregation, a shuffle by key and a final aggregation.
  • Spark SQL showed exactly this in our EXPLAIN output.
