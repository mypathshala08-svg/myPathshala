Hadoop vs Spark

Spark did not replace Hadoop; it replaced MapReduce. In this lesson Spark runs on our own YARN cluster and reads our HDFS files, gives exactly the same answers as our MapReduce job, and shows inside its plan the map, combiner and shuffle you already know. Then we measure where it wins: five passes over the same data take 199 s as MapReduce jobs and 35 s with Spark caching.

1 The story

Five questions, the same data

The canteen manager has five questions about the same 90 lakh orders: how many orders above ₹0, above ₹18, above ₹20, above ₹25, above ₹30. Riya writes them as five MapReduce jobs: 199 seconds. Kabir installs Apache Spark on the very same cluster, tells it to keep the data in memory after the first pass, and asks the same five questions: 35 seconds. Same HDFS, same YARN, same three workers.

Riya

So Spark is the new Hadoop? Should we throw HDFS and YARN away?

Arjun Sir

No. Look where Spark ran: its executors were YARN containers, and it read the file from HDFS. Spark replaced MapReduce, the processing engine. Storage and resource management stayed. Most "Hadoop clusters" today are HDFS + YARN running Spark, Hive on Tez, and a few old MapReduce jobs.

Kabir

And the speed-up isn't magic. Spark builds the whole job as a graph, keeps intermediate data in memory instead of writing it to HDFS between steps, and reuses the same executors for every step. The more passes, the bigger the win.

2 Definition

Apache Spark, and how it relates to Hadoop

Formal definition (write this in exams)

Apache Spark is a distributed data processing engine that represents a computation as a directed acyclic graph (DAG) of transformations over partitioned datasets (RDDs, and the higher-level DataFrames and Datasets). Transformations are lazy: nothing runs until an action (such as collect or write) asks for a result. The DAG is cut into stages at shuffle boundaries; each stage runs as parallel tasks, one per partition, inside long-lived executor processes coordinated by a driver. Intermediate results can be kept in memory (caching/persistence), and lost partitions are recomputed from their lineage. For DataFrames and SQL, the Catalyst optimizer rewrites the plan (column pruning, predicate pushdown, partial aggregation) and the Tungsten engine executes it with compact binary memory layouts and generated code. Spark has no storage or cluster manager of its own: it commonly runs on Hadoop YARN and reads HDFS, or runs on Kubernetes or its standalone manager with cloud object storage.

In simple words

Spark is a faster engine you can plug into a Hadoop cluster instead of MapReduce. You describe the whole job once; Spark plans it, runs it in executors that stay alive, and keeps data in memory between steps instead of writing it to disk after every step.

Words you'll meet in this lesson

DriverThe process that runs your program, builds the DAG and schedules tasks.
ExecutorA long-lived JVM (on YARN: a container) that runs tasks and caches data.
RDDResilient Distributed Dataset: partitions plus the lineage to rebuild them.
DataFrameA table with a schema; written as SQL or column expressions and optimized by Catalyst.
Transformation / actionLazy steps (map, filter, groupBy) vs the call that runs them (collect, count, write).
StageTasks that run without a shuffle; a shuffle (Exchange) starts a new stage.
cache / persistKeep a dataset in executor memory (or memory and disk) for reuse.
LineageThe recipe of transformations; Spark recomputes lost partitions from it.

Spark vs MapReduce at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A kitchen that keeps the ingredients out

  • MapReduce is a cook who puts every ingredient back in the cold store after each step, then fetches it again for the next step.
  • Spark keeps what it will need again on the counter (memory), plans the whole recipe before starting, and keeps the same helpers (executors) for the whole meal.
  • Both cook in the same kitchen: the store room is HDFS and the head chef handing out stoves is YARN.

Intermediate The same ideas, new names

  • map/filter are the same functions. reduceByKey is map output + combiner + shuffle + reducer in one call; Spark combines on the map side automatically (the plan shows partial_count).
  • The shuffle is called an Exchange in the plan; hashpartitioning(item, 200) is the HashPartitioner from Lesson 9.2 with 200 partitions.
  • An input split becomes a partition (our 4.7 MB file: 2 partitions); a container runs an executor, which runs many tasks, one after another, without starting a new JVM.
  • The MapReduce ApplicationMaster role is played by Spark's driver (with a small AM on YARN to request executors).

Advanced Where the speed comes from, and where it doesn't

  • No HDFS between steps: a multi-stage job is one application; shuffle files stay on local disk and stage outputs are not written to HDFS with replication 3.
  • Long-lived executors: no JVM and container start-up per task or per job; our 5 MapReduce jobs paid that 5 times.
  • Caching + lineage: reuse data across passes; if an executor dies, only lost partitions are recomputed.
  • Catalyst/Tungsten: read only needed columns (ReadSchema item, amount), aggregate in compact binary form, generate code.
  • Limits: memory is finite (spills to disk), a single one-pass scan of a huge file is disk-bound for both engines, and a badly partitioned shuffle is slow in any engine.

Exam tip: For "Compare Hadoop MapReduce and Spark", say first that Spark is an engine that usually runs on Hadoop (YARN, HDFS), then compare: disk vs memory between steps, one job per step vs one DAG, JVM per task vs long-lived executors, re-run task vs lineage recomputation, Java API vs SQL/Python/Scala/R + streaming + ML. Give one number: 5 passes took 199 s with MapReduce and 35.3 s with cached Spark on the same cluster.

Animated example: a fraud model that needs ten passes

Ten passes over UPI transactions 6 steps
Animated example
  1. 09:00: the fraud team's model needs ten passes over the same 30 days of transactions. Costs are in units from our lab's ratio (MapReduce 40 per pass, cached Spark about 3.5).
  2. MapReduce: every pass is a new job that starts containers, reads HDFS, computes and writes three copies of its output.
  3. Afternoon: ten passes cost about 400 units, mostly spent reading and writing, not computing.
  4. Spark: the first pass reads HDFS and caches the data in the executors (our lab: 21.4 s against about 40 s for one MapReduce pass).
  5. Passes 2–10 come from memory at about 3.5 units each; the executors never restart.
  6. Result: about 75 units instead of 400, roughly 5× faster, on the same cluster. (Illustrative scenario built on our measured ratio.)

Spark does not need YARN. It also runs on Kubernetes and on its own standalone manager, usually reading cloud object storage (S3, GCS, ADLS) instead of HDFS. On Hadoop clusters and on EMR, Dataproc and Cloudera it normally runs on YARN, exactly as in our lab.

4 Step by step

The same job three ways, on our cluster

We unpacked spark-4.0.4-bin-hadoop3 in the namenode container and pointed it at our Hadoop configuration. No Spark daemons were started: YARN starts everything per application.

  1. Submit to YARN

    export SPARK_HOME=/tmp/opt/spark-4.0.4-bin-hadoop3 HADOOP_CONF_DIR=/opt/hadoop/etc/hadoop
$SPARK_HOME/bin/spark-submit --master yarn --num-executors 3 --executor-memory 512m \
  --executor-cores 1 --driver-memory 512m item_revenue_spark.py /user/hadoop/data/canteen_orders.csv
    spark-submit wall time 46 s (includes starting the YARN application and 3 executors)
    --master yarn makes the client ask our ResourceManager for an application, exactly like hadoop jar. The driver runs here (client mode); the AM and 3 executors run in containers on the workers.

  2. The RDD way: MapReduce thinking

    .map(lambda line: line.split(","))
.filter(lambda f: len(f) == 3 and f[0] != "order_id")
.map(lambda f: (f[1], (1, int(f[2]))))                  # map: (item, (1, amount))
.reduceByKey(lambda a, b: (a[0] + b[0], a[1] + b[1]))   # combine + shuffle + reduce
    RDD chai 50170 752550 RDD dosa 49948 2247660 … RDD job took 7.4 s, partitions: 2
    The same mapper and reducer as ItemRevenue.java, in four lines, with the same answers. Two partitions = two input splits of the 4.7 MB file.

  3. The DataFrame way: SQL thinking

    df = spark.read.csv(path, header=True, inferSchema=True)
df.groupBy("item").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")).orderBy("item")
    | chai| 50170| 752550| | dosa| 49948|2247660| DataFrame job took 11.3 s
    You say what, Catalyst decides how. It took longer here because inferSchema reads the file once just to guess types; with a declared schema it reads once.

  4. Read the plan: find MapReduce inside

    Sort [item ASC]
+- Exchange rangepartitioning(item, 200)
   +- HashAggregate(keys=[item], functions=[count(1), sum(amount)])          ← reduce
      +- Exchange hashpartitioning(item, 200)                               ← shuffle
         +- HashAggregate(keys=[item], functions=[partial_count(1), partial_sum(amount)])   ← combiner
            +- FileScan csv [item, amount] ReadSchema: struct<item:string,amount:int>   ← map + column pruning
    Bottom to top: read only two columns, partially aggregate inside each map task (the combiner of Lesson 9.1), shuffle by hash of item (Lesson 9.2), finish the aggregate, then a second shuffle to sort globally.

  5. Five passes: no cache vs cache

    no cache: 19.8, 15.6, 13.5, 13.6, 12.8 s  = 75.3 s
cache   : 21.4,  4.2,  3.7,  3.3,  2.7 s  = 35.3 s
    Without cache Spark re-reads HDFS every pass, but executors stay alive, so it is already far faster than starting five jobs. With persist(MEMORY_AND_DISK) pass 1 costs a bit more (it fills the cache); later passes skip HDFS completely.

  6. The MapReduce way: five jobs

    for k in 1 2 3 4 5; do hadoop jar mr.jar ItemRevenue orders_x30.csv /out/iter$k; done
    MapReduce pass 1: 39 s … pass 5: 41 s MapReduce: 5 passes took 199 s
    Each job starts an ApplicationMaster and new map and reduce JVMs, reads 140 MB from HDFS and writes its result with replication 3. Nothing is reused between jobs.

Our numbers come from three workers sharing one laptop. Absolute times will differ on real hardware; the shape will not: the more passes over the same data, the bigger Spark's advantage. For a single pass over a huge file, both engines are limited by disks and the gap shrinks.

MapReduce vs Spark, same cluster 6 steps
What you see
  1. spark-submit asks our ResourceManager for an application; 46 s wall time including start-up.
  2. The RDD job gives exactly the Lesson 8.1 numbers in 7.4 s.
  3. The DataFrame plan: scan two columns, partial aggregate, shuffle, final aggregate.
  4. Five passes without cache: 75.3 s; each pass re-reads HDFS.
  5. Five passes with cache: 35.3 s; passes 2–5 take 2.7–4.2 s.
  6. Five MapReduce jobs over the same file: 199 s.
Behind the screen
  1. The driver asks YARN for an application master and three executor containers, which stay up for the whole application.
  2. Two partitions become two map tasks inside the executors; their combined output is shuffled to a reduce task.
  3. Catalyst prunes columns and aggregates before the shuffle, the same idea as a combiner.
  4. Without cache each pass re-reads the HDFS blocks, but no new JVMs are started.
  5. With cache, pass 1 stores the partitions in executor memory and later passes skip HDFS.
  6. MapReduce runs five separate jobs: five times the start-up, the HDFS read and the HDFS write.
6 Real-world use

Spark on Hadoop at work

Versions as of October 2026: Spark 4.2 (July 2026), 4.1 and 4.0 are current lines and 3.5 is the long-term line with security fixes until November 2027. Managed platforms often lag: Amazon EMR 7.14 ships Spark 3.5.8, Google Dataproc 2.3.37 ships Spark 3.5.3 and Cloudera Base 7.3.2 ships Spark 3.5 (sources below).

1. Fraud and risk models in fintech

Payment and lending companies train models on months of transactions with many passes over the same data; MLlib or Spark-prepared features with cached DataFrames replaced chains of MapReduce jobs.

Transactions (HDFS)→Spark ML, cached→Risk scores

2. Rewriting nightly ETL in telecom

Operators that once ran call-record summaries as dozens of chained MapReduce jobs rewrite them as one Spark SQL application, removing the HDFS writes between steps.

CDR files→one Spark DAG→Billing tables

3. Near-real-time dashboards in e-commerce

During a festival sale, Spark Structured Streaming reads orders from Kafka in micro-batches and updates sales per city every minute: something MapReduce was never built for.

Kafka→Structured Streaming→Dashboard

4. Interactive analysis in healthcare research

Researchers query de-identified hospital records with Spark SQL from notebooks; queries that took minutes as MapReduce return in seconds when tables are cached and stored as Parquet (Lesson 10.2).

Parquet on HDFS→Spark SQL→Notebook charts

5. Both engines side by side in government data platforms

Large public-sector clusters keep old, stable MapReduce jobs (and tools like DistCp) running while all new work is written in Spark on the same YARN queues; migration happens job by job.

Old MR jobs+New Spark jobs→One YARN cluster

Simplified; organisations differ in tools and policies. Sources: endoflife.date/apache-spark, Amazon EMR 7.x versions, Dataproc 2.3 versions, Cloudera Base 7.3.2.

7 Run the code

A model of k passes, fitted to our runs

The per-pass times below are our measurements. The model predicts any number of passes; check that k = 5 gives back the lab totals (199 s, 75.3 s, 35.3 s). It leaves out Spark's one-time application start-up (about 46 s in our lab), which MapReduce pays inside every pass.

# Per-pass times measured on our lab (5 passes over 9 M orders, 140 MB)
MR_PASS = 199 / 5                     # every pass is a new MapReduce job: start + read + write
NOCACHE_FIRST, NOCACHE_NEXT = 19.8, (15.6 + 13.5 + 13.6 + 12.8) / 4
CACHE_FIRST, CACHE_NEXT = 21.4, (4.2 + 3.7 + 3.3 + 2.7) / 4

def mapreduce(k):
    return k * MR_PASS

def spark(k, cache):
    if cache:
        return CACHE_FIRST + (k - 1) * CACHE_NEXT
    return NOCACHE_FIRST + (k - 1) * NOCACHE_NEXT

for k in [1, 5, 10, 20]:
    mr, nc, c = mapreduce(k), spark(k, False), spark(k, True)
    print(f"{k:>2} passes: MapReduce {mr:6.1f} s | Spark {nc:6.1f} s | Spark+cache {c:5.1f} s | {mr / c:4.1f}x")
1 passes: MapReduce 39.8 s | Spark 19.8 s | Spark+cache 21.4 s | 1.9x 5 passes: MapReduce 199.0 s | Spark 75.3 s | Spark+cache 35.3 s | 5.6x 10 passes: MapReduce 398.0 s | Spark 144.7 s | Spark+cache 52.7 s | 7.6x 20 passes: MapReduce 796.0 s | Spark 283.4 s | Spark+cache 87.4 s | 9.1x
  • MR_PASS = 199 / 5 # every pass is a new MapReduce job: start + read + writeFive ItemRevenue jobs took 39, 39, 39, 41 and 41 s: about 40 s each, every time.
  • CACHE_FIRST, CACHE_NEXT = 21.4, (4.2 + 3.7 + 3.3 + 2.7) / 4Pass 1 pays for reading and filling the cache; the next passes cost about 3.5 s.
  • return CACHE_FIRST + (k - 1) * CACHE_NEXTThe cached line grows slowly, so the advantage grows with every extra pass.

import sys, time
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName("item revenue (spark)").getOrCreate()
path = sys.argv[1]

t = time.time()
rdd = (spark.sparkContext.textFile(path)
       .map(lambda line: line.split(","))
       .filter(lambda f: len(f) == 3 and f[0] != "order_id")
       .map(lambda f: (f[1], (1, int(f[2]))))                       # map: (item, (1, amount))
       .reduceByKey(lambda a, b: (a[0] + b[0], a[1] + b[1])))       # shuffle + reduce (with map-side combine)
for item, (n, total) in sorted(rdd.collect()):
    print(f"RDD  {item:9} {n:>8} {total:>10}")
print(f"RDD job took {time.time() - t:.1f} s, partitions: {rdd.getNumPartitions()}")

t = time.time()
df = spark.read.csv(path, header=True, inferSchema=True)
out = df.groupBy("item").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")).orderBy("item")
out.show()
print(f"DataFrame job took {time.time() - t:.1f} s")
out.explain()
spark.stop()

Five passes, without and with cache

# iterative_spark.py: five passes over the same 140 MB (9 million orders).
# Pass k counts orders per item with amount >= threshold k. With cache(), only pass 1 reads HDFS.
import sys, time
from pyspark import StorageLevel
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("five passes (spark)").getOrCreate()
cache = sys.argv[2] == "cache"
orders = (spark.sparkContext.textFile(sys.argv[1])
          .map(lambda l: l.split(","))
          .filter(lambda f: f[0] != "order_id")
          .map(lambda f: (f[1], int(f[2]))))
if cache:
    orders = orders.persist(StorageLevel.MEMORY_AND_DISK)
total = time.time()
for k, threshold in enumerate([0, 18, 20, 25, 30], 1):
    t = time.time()
    counts = orders.filter(lambda p, th=threshold: p[1] >= th).map(lambda p: (p[0], 1)).reduceByKey(lambda a, b: a + b).collect()
    print(f"pass {k}: amount >= {threshold:2}: {sum(c for _, c in counts):>9,} orders, {time.time() - t:5.1f} s")
print(f"cache={cache}: 5 passes took {time.time() - total:.1f} s")
spark.stop()

Will the data fit in the cache?

Problem statement

A telecom company wants to cache 2 TB of call records (CSV) for a 10-pass analysis. It has 100 executors of 16 GB. Spark's unified memory is (heap − 300 MB) × 0.6, shared by cache and execution. Stored as a columnar cache, the data is roughly the size of Parquet (our Lesson 10.2 ratio: 4.4 MB Parquet for 19.4 MB CSV). Does it fit?

Input
2 TB CSV · 100 × 16 GB executors · ratio 4.4/19.4
Expected output
memory 942 GB, data cached ~464 GB, fits: True

Approach

  1. Usable memory per executor = (16,384 − 300) × 0.6 MB.
  2. Total = per executor × 100.
  3. Cached size ≈ 2 TB × Parquet ratio.

9 Quiz and revision

Check yourself

Quick revision

Lesson 13.2 in one screen

  • Spark is a DAG engine with lazy transformations, actions, long-lived executors, a driver, caching and lineage; Catalyst and Tungsten optimize DataFrames and SQL.
  • Spark usually runs on Hadoop: YARN containers for executors, HDFS for data. It replaced MapReduce, not HDFS or YARN.
  • Mapping: map/filter = map, reduceByKey = combiner + shuffle + reduce, Exchange = shuffle, partition = split, executor = container.
  • Lab: same answers as Lesson 8.1; RDD 7.4 s, DataFrame 11.3 s; spark-submit 46 s including start-up.
  • Lab, 5 passes over 9 M orders: MapReduce 199 s; Spark 75.3 s; Spark + cache 35.3 s (passes 2–5: 2.7–4.2 s).
  • Spark wins most on iterative, interactive and streaming work; a single huge scan is disk-bound for both.
  • Oct 2026: Spark 4.2/4.1/4.0 current, 3.5 LTS to Nov 2027; EMR 7.14, Dataproc 2.3 and Cloudera 7.3.2 ship Spark 3.5.

Interview and viva questions

Is Spark a replacement for Hadoop?

Spark replaces Hadoop MapReduce as the processing engine, not Hadoop as a whole. Spark has no storage or resource manager of its own, so on most Hadoop clusters it runs on YARN and reads HDFS. It can also run on Kubernetes or its standalone manager with cloud object storage, which is how many new platforms use it.

Why is Spark faster than MapReduce?

Spark plans a whole multi-step job as one DAG, keeps intermediate data in memory or on local disk instead of writing it to HDFS between steps, reuses long-lived executors instead of starting a JVM per task, can cache datasets across passes, and optimizes DataFrame/SQL plans with Catalyst and Tungsten. In our lab, five passes took 199 s with MapReduce and 35.3 s with cached Spark.

Is MapReduce still used?

Yes, but mostly for existing jobs and tools built on it, such as DistCp and Hadoop Archive. New batch, SQL, machine learning and streaming work is usually written in Spark (or Hive on Tez, Flink, Trino), often running on the same YARN cluster as the old MapReduce jobs.

What is the difference between an RDD and a DataFrame?

An RDD is a distributed collection of objects transformed with functions you write; Spark cannot see inside those functions. A DataFrame is a table with a schema, written with SQL or column expressions, which the Catalyst optimizer can rewrite (for example reading only needed columns and aggregating before the shuffle). DataFrames are the recommended API for most work.

Does Spark need more memory than MapReduce?

Usually yes. Executors are long-lived and use memory for caching and for shuffles and joins; when memory runs short Spark spills to disk, and badly sized executors can fail with out-of-memory errors. MapReduce streams data through short-lived tasks and needs less memory, at the cost of disk I/O between steps.

P5Medium

Word count, Spark style

Simulate flatMap → map → reduceByKey on three lines.

Input
3 lines of feedback
Expected output
[('chai', 2), ('cold', 1), ('dosa', 1), ('hot', 1), ('late', 1), ('was', 3)]
Show solution and explanation 
lines = ["chai was hot", "dosa was cold", "chai was late"]
words = [w for line in lines for w in line.split()]       # flatMap
pairs = [(w, 1) for w in words]                           # map
counts = {}
for w, n in pairs:                                        # reduceByKey
    counts[w] = counts.get(w, 0) + n
print(sorted(counts.items()))
[('chai', 2), ('cold', 1), ('dosa', 1), ('hot', 1), ('late', 1), ('was', 3)]

How it works: The same three steps as Lesson 8.6's WordCount.java, written as one chain in Spark: lines.flatMap(split).map(lambda w: (w, 1)).reduceByKey(add).

P8Advanced

Recompute from lineage

Three cached partitions; executor 2 dies and loses partition 1. Recompute only that partition from its lineage and check the total is unchanged.

Input
3 partitions, lineage = filter ≥ 18 then double
Expected output
recomputed 1 partition; total same: True
Show solution and explanation 
source = [[15, 18, 20], [25, 30, 45], [18, 80, 15]]
lineage = lambda part: [x * 2 for x in part if x >= 18]
cache = [lineage(p) for p in source]
before = sum(map(sum, cache))
cache[1] = None                              # executor lost
recomputed = 0
for i, p in enumerate(cache):
    if p is None:
        cache[i] = lineage(source[i]); recomputed += 1
print("recomputed", recomputed, "partition; total same:", sum(map(sum, cache)) == before)
recomputed 1 partition; total same: True

How it works: Only the lost partition is rebuilt, from its source block and its recipe. MapReduce instead re-runs the failed task from its HDFS input.

Real-world scenario questions (asked in company interviews)

Hadoop vs Spark is asked in almost every big data interview, often as a trap: the best answers start by saying Spark usually runs on Hadoop.

Concepts · basicsFresher

"Hadoop or Spark: which is better?"

An opening question in a data engineering interview.

The interviewer is checking: that you know they are not alternatives.

Show a strong answer
  • Hadoop is storage (HDFS) + resources (YARN) + an engine (MapReduce); Spark is an engine, commonly running on YARN and HDFS.
  • As engines, Spark is faster for multi-step, iterative and interactive work: memory between steps, long-lived executors, Catalyst.
  • Example: on one cluster, five passes took 199 s as MapReduce jobs and 35 s with cached Spark.
Internals · plansExperienced

"Explain this Spark plan in MapReduce terms"

The interviewer shows FileScan → HashAggregate(partial) → Exchange → HashAggregate.

The interviewer is checking: real understanding of shuffles.

Show a strong answer
  • FileScan with a narrow ReadSchema is the map input with column pruning.
  • The partial aggregate is a combiner inside each map task; Exchange hashpartitioning is the shuffle with a hash partitioner.
  • The final aggregate is the reducer; a stage boundary sits at each Exchange.
Operations · memoryExperienced

A Spark job that was fast in testing fails with executor OOM in production

The team cached a large DataFrame and joins it with another.

The interviewer is checking: memory sizing and options.

Show a strong answer
  • Check executor memory vs cached size (Storage tab in the Spark UI), skewed keys, and shuffle partition counts.
  • Use MEMORY_AND_DISK, cache only what is reused, cache columnar DataFrames rather than object RDDs, raise memory or partitions.
  • Fix skew (salting, AQE skew join) and broadcast small tables (Lesson 9.6).
Architecture · migrationLead

"Should we rewrite all our MapReduce jobs in Spark?"

A company has 400 stable MapReduce jobs on a Hadoop cluster.

The interviewer is checking: pragmatic migration thinking.

Show a strong answer
  • Not all at once: rank jobs by cluster-hours and business value; rewrite the heaviest and the multi-step chains first.
  • Run old and new side by side on the same YARN queues and compare outputs row by row before switching.
  • Keep jobs that are one-pass, stable and cheap; write all new work in Spark SQL/DataFrames.
