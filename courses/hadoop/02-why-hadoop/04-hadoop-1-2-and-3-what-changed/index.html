Hadoop 1, 2 and 3: what changed

Hadoop kept its core ideas but changed its architecture twice. Hadoop 1 had one JobTracker doing everything and fixed slots that wasted resources. Hadoop 2 introduced YARN and a standby NameNode, so many engines could share a bigger, safer cluster. Hadoop 3 added erasure coding, extra standbys, GPU scheduling and newer Java. This lesson explains each change, why it was needed, and the details (like ports) that trip people up in real work.

2 Definition

Hadoop 1, 2 and 3

Formal definition (write this in exams)

Hadoop 1 (1.x, first stable release December 2011) consists of HDFS with a single NameNode and MapReduce v1, in which one JobTracker performs both cluster resource management and job scheduling/monitoring, and TaskTrackers run tasks in fixed map and reduce slots. Hadoop 2 (2.x, GA October 2013) introduces YARN, separating resource management (ResourceManager, NodeManagers) from per-application logic (ApplicationMaster), so MapReduce becomes one of many YARN applications; it also adds HDFS High Availability and Federation. Hadoop 3 (3.x, GA December 2017) requires Java 8 or later and adds HDFS erasure coding, more than two NameNodes for HA, new default ports outside the Linux ephemeral range, YARN Timeline Service v2, opportunistic containers and support for resource types such as GPUs.

In simple words

Hadoop 1: one boss (JobTracker) ran every job and every machine, and only MapReduce could run. Hadoop 2: YARN split the boss into a resource manager plus a small manager for each job, so any engine can share the cluster, and the NameNode got a backup. Hadoop 3: saves storage with erasure coding, allows more backups, uses modern hardware like GPUs, and needs a newer Java.

The versions at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner One principal, or a principal and many class teachers

  • Hadoop 1: one principal personally plans every class, every period and every exam for the whole school. Fine for a small school; impossible for a huge one.
  • Hadoop 2: the principal only assigns classrooms and time (resources). Each class has its own class teacher (ApplicationMaster) who plans that class. Any subject can be taught, not just one.
  • Hadoop 3: the same school, run more efficiently: smaller storerooms (erasure coding), more vice-principals ready to take over (standby NameNodes), science labs with special equipment (GPUs).

Intermediate What exactly changed between 1 and 2

  • JobTracker split in two: the ResourceManager (cluster-wide resources) and one ApplicationMaster per job (task scheduling, retries, progress).
  • Slots → containers: Hadoop 1 nodes had, say, 8 map and 4 reduce slots. If only map tasks were waiting, the reduce slots sat empty. YARN containers can run either kind of task.
  • Beyond MapReduce: any framework that writes an ApplicationMaster can run: Spark, Tez (used by Hive), Flink, and others.
  • HDFS HA: an active and a standby NameNode share the edit log through JournalNodes; ZooKeeper-based failover controllers switch automatically.
  • Federation: several NameNodes can split the namespace (for example /user and /data) so metadata scales beyond one machine's RAM.
  • Default block size 128 MB.

Advanced What Hadoop 3 added, and why it matters

  • Erasure coding: with the RS-6-3 policy, 6 data cells get 3 parity cells: 1.5× storage and tolerance of 3 lost cells, versus 3× for replication. Costs CPU and network to rebuild, so it suits cold data.
  • More than two NameNodes: with three NameNodes and five JournalNodes the cluster survives two NameNode failures.
  • Ports: defaults moved out of the Linux ephemeral range (32768–61000) to avoid clashes; for example the NameNode web UI moved from 50070 to 9870.
  • YARN: Timeline Service v2, opportunistic containers, resource types (GPUs, FPGAs), Docker containers, and Router-based Federation for very large clusters.
  • Cloud storage: much better S3A, Azure and other connectors, so Hadoop tools can read and write object storage directly.
  • Intra-DataNode disk balancer (hdfs diskbalancer) evens out data across the disks inside one node.

Exam tip: The classic question “Differentiate Hadoop 1 and Hadoop 2” expects a table: JobTracker + TaskTracker vs ResourceManager + NodeManager + ApplicationMaster, slots vs containers, MapReduce only vs many engines, NameNode SPOF vs HA, single namespace vs federation, ~4,000 nodes vs much larger, 64 vs 128 MB default block. Add 2–3 Hadoop 3 lines (erasure coding, multiple standbys, Java 8+, port changes) to stand out.

4 Step by step

Why Hadoop 1's JobTracker hit a wall

  1. One process, every decision

    In Hadoop 1, every TaskTracker heartbeats to the JobTracker, and the JobTracker decides every task placement for every running job.

    It also keeps the progress, counters and history of all jobs in its own memory. The more nodes and jobs, the more work for this single process.

  2. Count the load

    nodes, hb_interval_s = 4000, 3
tasks_running = 40000
print(nodes // hb_interval_s, "heartbeats per second, tracking", tasks_running, "tasks")
    1333 heartbeats per second, tracking 40000 tasks
    Around 4,000 nodes and 40,000 concurrent tasks is where Hadoop 1 clusters typically topped out. Beyond that the JobTracker became slow or unstable.

  3. Slots waste resources

    Each node had fixed map slots and reduce slots. During a map-heavy phase, reduce slots sat idle even though maps were waiting.

    Utilisation suffered, and an admin had to guess the right map/reduce split for every node.

  4. Hadoop 2 splits the JobTracker

    The ResourceManager only tracks free resources and hands out containers. Each job's ApplicationMaster (running in an ordinary container on a worker) handles its own tasks.

    The heavy, per-job work is now spread across the cluster. The ResourceManager stays small and fast, so clusters can grow much larger.

  5. Any engine can join

    Spark, Tez and others ship their own ApplicationMaster. YARN doesn't care what runs inside a container.

    This is why “Spark on YARN” is so common: one cluster, one storage layer, many engines, shared fairly through queues.
5 See it happen

The same two jobs on Hadoop 1 and on Hadoop 2

A map-heavy job and a Spark job arrive at a 3-node cluster. Left: Hadoop 1 with a JobTracker and slots. Right: Hadoop 2 with YARN and containers.

JobTracker and slots vs YARN and containers 6 steps
Hadoop 1
  1. Hadoop 1: a single JobTracker and three TaskTrackers. Each node has 2 map slots and 2 reduce slots, fixed by configuration.
  2. A job with 12 map tasks arrives. Only the 6 map slots can take them.
  3. Six maps wait in the queue while six reduce slots sit empty: they may only run reduce tasks.
  4. A Spark job arrives. Hadoop 1 runs only MapReduce, so it needs a separate cluster.
  5. On a big cluster, the JobTracker tracks every task of every job and becomes the bottleneck and a single point of failure.
  6. Result: half the slots used, one engine, one overloaded master.
Hadoop 2 (YARN)
  1. Hadoop 2: a ResourceManager and three NodeManagers. Each node offers containers that can run any kind of task.
  2. The MapReduce job gets an ApplicationMaster (violet), which asks for containers for its map tasks.
  3. Four more maps start in containers that Hadoop 1 would have kept empty for reducers. Nothing is reserved for a task type that isn't running.
  4. The Spark job gets its own ApplicationMaster and executors (orange) on the same cluster.
  5. Per-job decisions are made by each ApplicationMaster, so the ResourceManager stays light and the cluster can grow.
  6. Every container is in use, by two different engines, on one shared cluster.

6 Real-world use

Version changes in real projects

1. Upgrading from Hadoop 2 to 3

Upgrade projects check Java versions, rewrite scripts for the new shell, update firewall rules and monitoring for the new ports, test jobs on staging, and use HDFS rolling upgrades so the cluster stays available.

Hadoop 2.x→Test + rolling upgrade→Hadoop 3.x

2. Cutting storage cost with erasure coding

Companies with years of rarely read data apply an erasure-coding policy to archive directories, roughly halving the raw disk needed for them while keeping hot data replicated.

Cold directories→hdfs ec -setPolicy→~1.5× instead of 3×

3. Three NameNodes for critical clusters

Platforms that must keep HDFS available through maintenance and failures run one active and two standby NameNodes (Hadoop 3), so one can be patched while another still protects the cluster.

Active NN→2 standbys + 5 JournalNodes→Survives 2 failures

4. GPUs on YARN for machine learning

Hadoop 3.1 added GPU scheduling to YARN, so ML teams can train models on the same cluster that stores their data, requesting GPUs like memory and CPU.

Training job→YARN container with GPU→Model

5. Reading old tutorials safely

Much online material was written for Hadoop 1 or 2. Knowing the version differences lets you spot outdated advice: JobTracker commands, port 50070, 64 MB blocks, or Java 7 instructions.

Old guide→Check version clues→Adapt for 3.x

7 Run the code

Slots vs containers: measure the waste

In Hadoop 1, each node has fixed map slots and reduce slots. This program fills them with a map-heavy workload and measures how much of the cluster is idle, then does the same with YARN-style containers that can run either kind of task.

nodes = 10
map_slots, reduce_slots = 8, 4          # Hadoop 1: fixed per node
containers = map_slots + reduce_slots    # Hadoop 2: same capacity, any task type

maps_waiting, reduces_waiting = 200, 10

h1_used = min(maps_waiting, nodes * map_slots) + min(reduces_waiting, nodes * reduce_slots)
h2_used = min(maps_waiting + reduces_waiting, nodes * containers)

total = nodes * containers
print(f"Hadoop 1: {h1_used} of {total} busy ({h1_used / total:.0%})")
print(f"Hadoop 2: {h2_used} of {total} busy ({h2_used / total:.0%})")
Hadoop 1: 90 of 120 busy (75%) Hadoop 2: 120 of 120 busy (100%)
  • map_slots, reduce_slots = 8, 4In Hadoop 1, an admin fixed these numbers per node. A reduce slot could never run a map task.
  • h1_used = min(...) + min(...)Map tasks can only use map slots and reduce tasks only reduce slots, so each is capped separately.
  • h2_used = min(maps_waiting + reduces_waiting, nodes * containers)With containers, any waiting task can use any free capacity.

How many NameNodes and JournalNodes for a given safety level?

Problem statement

JournalNodes work by majority: with J JournalNodes the cluster tolerates (J − 1) ÷ 2 JournalNode failures. With N NameNodes (one active), it tolerates N − 1 NameNode failures. For each target, print the smallest setup that survives that many failures of each kind.

Input

Expected output

Approach

  1. NameNodes needed = failures + 1.
  2. JournalNodes needed = 2 × failures + 1 (an odd number, for a majority).

Interview and viva questions

What are the differences between Hadoop 1 and Hadoop 2?

Hadoop 1 used a single JobTracker for both resource management and job scheduling, with TaskTrackers offering fixed map and reduce slots, ran only MapReduce, had a single NameNode (a SPOF) and scaled to about 4,000 nodes. Hadoop 2 introduced YARN: a ResourceManager for cluster resources, NodeManagers on each node, and an ApplicationMaster per job, using flexible containers. It supports engines beyond MapReduce, adds NameNode High Availability and HDFS Federation, scales further and uses a 128 MB default block size.

What new features came in Hadoop 3?

HDFS erasure coding (about 1.5× storage overhead instead of 3× for suitable data), support for more than two NameNodes, a minimum of Java 8, default ports moved out of the ephemeral range (NameNode UI on 9870), a rewritten shell, YARN Timeline Service v2, opportunistic containers, resource types such as GPUs and FPGAs (3.1), Docker container support, Router-based Federation, an intra-DataNode disk balancer and much improved cloud storage connectors.

Why was the JobTracker a bottleneck?

It received heartbeats from every TaskTracker, scheduled every task of every job, tracked their progress and counters, and kept job history in memory. As clusters and job counts grew, one process could not keep up, and if it failed all running jobs were lost.

Is the Secondary NameNode a backup NameNode?

No. It periodically merges the NameNode's edit log into the fsimage (checkpointing) so the edit log does not grow forever and restarts are faster. It cannot take over if the NameNode fails. Automatic failover requires HA with a standby NameNode.

What is the difference between replication and erasure coding?

Replication stores full copies of each block (3× storage) and reads are simple and fast. Erasure coding splits data into data cells and computes parity cells (for example 6 + 3); any 6 of the 9 cells can rebuild the data. It needs about 1.5× storage but costs CPU and network to encode and rebuild, so it is best for cold, large files.

P2Easy

Erasure coding overhead

Print the storage overhead of RS-6-3 and RS-3-2 erasure coding.

Input
RS-6-3 · RS-3-2
Expected output
RS-6-3: 1.50x

P7Business problem

Should we upgrade to Hadoop 3 for storage savings?

A 2 PB cluster (raw) is full. 60% of the stored data is cold. Switching cold data from 3× replication to 1.5× erasure coding frees raw disk. The alternative is buying new nodes of 144 TB at Rs 18 lakh each. How much hardware spending does the upgrade avoid?

Input
2,048 TB raw · 60% cold · node 144 TB = Rs 18 lakh
Expected output
Freed 614 TB raw = 4 nodes = Rs 72 lakh avoided
Show solution and explanation 
import math
raw = 2048
data = raw / 3
cold = data * 0.60
freed = cold * 3 - cold * 1.5
nodes = math.floor(freed / 144)
print(f"Freed {freed:.0f} TB raw = {nodes} nodes = Rs {nodes * 18} lakh avoided")
Freed 614 TB raw = 4 nodes = Rs 72 lakh avoided

How it works: About 614 TB freed, 4 nodes (Rs 72 lakh) not bought, using illustrative prices. Weigh it against upgrade effort and the CPU cost of erasure coding.

P8Business problem

Consolidate separate MapReduce and Spark clusters

A company runs a 40-node Hadoop 1 cluster for MapReduce and a separate 30-node cluster for Spark. Peak usage is 30 nodes and 20 nodes, at different times of day. With one YARN cluster, the worst-case need is the larger peak plus a quiet share of 6 nodes from the other, plus 20% spare. How many nodes are needed?

Input
peaks 30 and 20 at different times · quiet share 6 · +20%
Expected output
Nodes needed: 44 instead of 70
Show solution and explanation 
import math
need = max(30, 20) + 6
print("Nodes needed:", math.ceil(need * 1.2), "instead of", 40 + 30)
Nodes needed: 44 instead of 70

How it works: 44 instead of 70 nodes. Sharing one cluster across engines was a major business reason for YARN.

Real-world scenario questions (asked in company interviews)

Version questions show up in almost every Hadoop interview. These scenarios turn the comparison table into practical answers.

Any company · conceptsFresher

“Explain the difference between Hadoop 1 and 2 in two minutes.”

The classic question. The interviewer wants the main differences and the reason behind them.

The interviewer is checking: do you know why YARN exists, not just its name?

Show a strong answer
  • Problem: in Hadoop 1, one JobTracker did resource management and scheduled every task of every job. It limited clusters to about 4,000 nodes, was a single point of failure, used fixed map/reduce slots (wasting capacity) and could only run MapReduce.
  • Fix (Hadoop 2): YARN split it: the ResourceManager manages resources; each job has its own ApplicationMaster; NodeManagers run flexible containers. Result: bigger clusters, better utilisation, and Spark, Tez and others on the same cluster.
  • Also in Hadoop 2: NameNode HA (active + standby) and Federation.

Avoid: saying “Hadoop 2 removed MapReduce”. MapReduce still exists; it runs as a YARN application.

Operations · troubleshootingFresher

“The NameNode web page won't open”

A colleague installed Hadoop 3.4 from a tutorial and says HDFS is running, but http://localhost:50070 shows “connection refused”.

The interviewer is checking: do you know the practical version differences?

Show a strong answer
  • Hadoop 3 moved the NameNode UI to 9870. Try http://localhost:9870.
  • Confirm with jps that the NameNode process is running, and check dfs.namenode.http-address in hdfs-site.xml.
  • The tutorial was probably written for Hadoop 2: double-check its other settings too (Java version, script names, ports for DataNodes).

Avoid: reinstalling Hadoop before checking the port.

Plan an upgrade from Hadoop 2.10 to 3.x

The interviewer is checking: can you think through compatibility and risk, not just “install the new version”?

  1. Inventory: Java version, every job and its libraries (Hive, Spark, custom jars), scripts using old shell behaviour, monitoring and firewalls using old ports.
  2. Compatibility: pick a 3.x release supported by your Hive and Spark versions; upgrade Java first.
  3. Staging: build a staging cluster on the target version and run real jobs on copies of data.
  4. Upgrade: back up NameNode metadata, use an HA rolling upgrade for HDFS where supported, then YARN, keeping a rollback path until finalised.
  5. After: update ports in monitoring, then consider Hadoop 3 features like erasure coding for cold data.

Avoid: upgrading production directly, or enabling erasure coding everywhere on day one.

Banking · availability3+ years

Two NameNodes or three?

A bank's HDFS cluster uses HA with two NameNodes. Last month, while the standby was down for patching, the active NameNode's server failed, and HDFS was unavailable for an hour.

The interviewer is checking: do you know what Hadoop 3 added for availability and how quorums work?

Show a strong answer
  • With two NameNodes, maintenance on one leaves no protection. Hadoop 3 supports more than two NameNodes: with one active and two standbys, one can be patched while another still protects the cluster.
  • Pair it with five JournalNodes (a majority of 3 must be alive) to tolerate two JournalNode failures as well.
  • Run the NameNodes on different racks and power feeds, and schedule maintenance one node at a time.

Avoid: “Use the Secondary NameNode as a third backup.” It cannot take over.
