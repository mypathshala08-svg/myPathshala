How Hadoop solved each problem

Every component of Hadoop exists because of a specific problem: data that doesn't fit, disks that die, jobs that take days, a jammed network, mountains of plumbing code, and a master that must not fail. This lesson maps each problem to its fix, runs a tiny MapReduce in Python so you see exactly which part you write and which part Hadoop does, and ends with the problems Hadoop never solved, which is why Spark and other tools exist.

2 Definition

Hadoop's architecture as a set of answers

Formal definition (write this in exams)

Apache Hadoop consists of four core modules. Hadoop Common: shared libraries and utilities. HDFS: a distributed file system that splits files into large blocks, replicates each block across DataNodes and racks, and keeps metadata on a NameNode, providing scalable, fault-tolerant, high-throughput storage. YARN (since Hadoop 2): a cluster resource manager that allocates CPU and memory as containers to many applications. MapReduce: a programming model and engine in which user-defined map and reduce functions are executed in parallel near the data, with the framework handling partitioning, scheduling, shuffling, sorting and failure recovery.

In simple words

Hadoop is four pieces. HDFS stores huge files safely across many machines. MapReduce processes them in parallel. YARN decides which job gets which machines' CPU and memory. Common holds the shared code. Each piece was built to fix a specific problem of big data.

The architecture at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A courier company

  • HDFS is the warehouse network: parcels (blocks) stored in many warehouses (nodes), each parcel copied to three warehouses in different areas.
  • The NameNode is the head office register: it knows which warehouse holds which parcel, but never touches the parcels.
  • MapReduce is the sorting work: every warehouse sorts its own parcels by city at the same time (map), then all parcels for one city go to one hub (shuffle) to be counted (reduce).
  • YARN is the staff manager: it decides which team uses which warehouse workers today.

Intermediate How the pieces work together on one job

  • You copy a file into HDFS: the NameNode picks DataNodes, the client writes blocks to them in a pipeline.
  • You submit a job: YARN starts an ApplicationMaster for it.
  • The ApplicationMaster asks the NameNode where the input blocks are, then asks YARN for containers on those nodes.
  • Map tasks read their local blocks; outputs are shuffled to reducers; reducers write results back to HDFS.
  • Throughout, heartbeats let the masters notice failures and re-run work.

Advanced What Hadoop did not solve (and what came next)

  • Latency: MapReduce jobs take seconds to start and write intermediate data to disk. Interactive SQL came from Impala, Presto/Trino, Hive LLAP and cloud warehouses.
  • Iterative algorithms (machine learning, graph processing) reread data in every pass. Spark keeps working data in memory and became the main engine.
  • Streaming: MapReduce is batch-only. Kafka, Flink and Spark Structured Streaming handle real-time data.
  • Small files: every file and block costs NameNode memory. Mitigations: bigger files, HAR/SequenceFiles, compaction, federation.
  • Updates: HDFS files are write-once. Table formats like Apache Iceberg, Delta Lake and Hudi added updates and deletes on top of files.
  • Operations and security: running Kerberos, Ranger, upgrades and capacity planning takes skilled staff. Managed cloud services reduced this burden.

Exam tip: For “Explain the core components of Hadoop”, name all four (Common, HDFS, YARN, MapReduce), give each one's job in one line, and connect each to the problem it solves. Adding one line on Hadoop's limitations (latency, small files, iterative jobs) shows real understanding.

4 Step by step

A word count, and which Hadoop part handles each step

  1. Store: put the file in HDFS

    hdfs dfs -put pages.txt /data/pages.txt
    HDFS splits the file into 128 MB blocks and writes 3 replicas of each to DataNodes on two racks. Solves: doesn't fit and disks die.

  2. Map: each task reads one block

    def map_words(line):
    return [(w, 1) for w in line.lower().split()]
print(map_words("Pune Delhi Pune"))
    [('pune', 1), ('delhi', 1), ('pune', 1)]
    Your only code. MapReduce runs one copy per block, in parallel, on nodes that hold the blocks (locality). Solves: too slow and network jammed.

  3. Shuffle and sort: group by key

    pairs = [("pune", 1), ("delhi", 1), ("pune", 1)]
groups = {}
for k, v in sorted(pairs):
    groups.setdefault(k, []).append(v)
print(groups)
    {'delhi': [1], 'pune': [1, 1]}
    Done entirely by the framework: map outputs are partitioned by key, copied over the network to reducers and sorted. Solves: too much plumbing.

  4. Reduce: combine each key's values

    def reduce_count(word, ones):
    return word, sum(ones)
print(reduce_count("pune", [1, 1]))
    ('pune', 2)
    Your second function. Reducers write results back to HDFS, replicated like any other file.

  5. Recover: a node dies halfway

    A DataNode with three running map tasks loses power.

    YARN and the ApplicationMaster re-run those tasks on other nodes, reading other replicas. The job finishes. Solves: tasks fail mid-job.
5 See it happen

Six problems, six fixes: the board and the cluster

Each frame takes one line from Riya's board. Left: the problem as a user feels it. Right: the Hadoop mechanism that fixes it.

Problem → Hadoop mechanism 6 steps
The problem
  1. Storage: 400 TB of data and disks of 4 TB. No single machine can hold it.
  2. Reliability: with one copy, a dead disk means lost data and a failed job.
  3. Speed: one machine reading 400 TB takes days.
  4. Network: pulling all the data to a central place saturates the network.
  5. Complexity: distribution code dwarfs the actual business logic.
  6. Growth: adding machines forces a painful manual re-shard.
Hadoop's fix
  1. HDFS cuts the file into blocks and spreads them, so capacity is the sum of every node's disks.
  2. Replication: each block lives on three nodes; when one dies, the NameNode makes a new copy from the others.
  3. MapReduce runs one task per block, all at the same time, so reading 400 TB takes minutes, not days.
  4. Locality: tasks run where their blocks are, so input data doesn't cross the network.
  5. The programming model: you write two small functions; Hadoop handles everything around them.
  6. Growth: a new DataNode registers and starts receiving blocks. The NameNode tracks blocks individually, so no re-sharding.

6 Real-world use

Which fix matters most, by industry

1. Telecom: cheap, safe storage for years

Regulations require keeping call and data records for years. HDFS on commodity disks with replication (or erasure coding for old data) is far cheaper per TB than enterprise storage.

Records→HDFS + replication / EC→Retained for years

2. Banking: finishing the batch window

End-of-day risk and reconciliation jobs must finish before morning. Parallel processing near the data and automatic retries make the deadline reliable, even when nodes fail at night.

Day's transactions→Parallel jobs + retries→Ready by 6 am

3. E-commerce: schema-on-read for app events

App events change format every few weeks as new features ship. Storing them raw in HDFS and applying a schema at query time (Hive, Spark) means nothing is lost when the format changes.

Raw events→Stored as-is→Schema applied by queries

4. Many teams, one cluster

With YARN, the fraud team's Spark jobs, the BI team's Hive queries and nightly MapReduce jobs share one cluster, each in its own queue with guaranteed capacity (Module 11).

Many teams→YARN queues→One shared cluster

5. Always-on data platforms

When dashboards and pipelines depend on HDFS around the clock, NameNode High Availability turns a master failure from an outage into a short pause.

Active NN fails→Standby takes over→Pipelines continue

Examples are simplified descriptions of common patterns.

7 Run the code

A tiny MapReduce, in 20 lines of Python

This is the whole MapReduce idea on one machine. map_fn and reduce_fn are the only parts you would write in Hadoop; run_job plays the framework: it splits the input, runs every map, shuffles and sorts by key, and runs every reduce.

def map_fn(line):                        # YOU write this
    city, amount = line.split(",")
    return [(city, int(amount))]

def reduce_fn(city, amounts):            # YOU write this
    return city, sum(amounts)

def run_job(lines, splits=2):            # HADOOP does this part
    parts = [lines[i::splits] for i in range(splits)]
    mapped = [kv for part in parts for line in part for kv in map_fn(line)]
    groups = {}
    for k, v in sorted(mapped):          # shuffle and sort by key
        groups.setdefault(k, []).append(v)
    return [reduce_fn(k, vs) for k, vs in groups.items()]

orders = ["Pune,240", "Delhi,120", "Pune,60", "Goa,300", "Delhi,80"]
print(run_job(orders))
[('Delhi', 200), ('Goa', 300), ('Pune', 300)]
  • def map_fn(line):Map: turn one input record into zero or more (key, value) pairs. Here: (city, amount).
  • parts = [lines[i::splits] for i in range(splits)]Split the input into pieces, like HDFS blocks. lines[i::2] takes every second line starting at i.
  • for k, v in sorted(mapped):Shuffle and sort: all values with the same key end up together, in key order.
  • return [reduce_fn(k, vs) for k, vs in groups.items()]Reduce: called once per key with the list of all its values.

Quick revision

Lesson 2.3 in one screen

  • Four core modules: Common (shared code), HDFS (storage), YARN (resources), MapReduce (processing).
  • Doesn't fit → HDFS blocks. Disks die → 3 replicas, re-replication, checksums.
  • Too slow → parallel map tasks. Network → data locality.
  • Plumbing → you write map + reduce; framework does splits, scheduling, shuffle and sort, retries.
  • Growth → add nodes; NameNode tracks each block; balancer spreads data.
  • Hadoop 2: YARN (many engines, better scale) + NameNode HA. Hadoop 3: erasure coding, multiple standbys.

  • Not solved by MapReduce: low latency, iterative ML, streaming, small files, in-place updates → Spark, Flink, Trino, Iceberg/Delta/Hudi.

Interview and viva questions

What are the core components of Hadoop?

Hadoop Common (shared libraries, configuration and utilities), HDFS (distributed storage with a NameNode for metadata and DataNodes for blocks), YARN (resource management with a ResourceManager, NodeManagers and per-application ApplicationMasters) and MapReduce (the batch processing model and engine that runs on YARN).

How does Hadoop achieve scalability?

By scaling out: HDFS spreads blocks over any number of DataNodes and the NameNode tracks each block individually, so adding nodes adds capacity without re-sharding. MapReduce creates one task per input split, so more nodes means more tasks run in parallel. YARN schedules resources across all nodes.

Which part of a MapReduce job is handled by the framework?

Computing input splits, scheduling map tasks near their data, running the map tasks, partitioning, spilling, sorting and shuffling map outputs to reducers, merging them, running reduce tasks, writing output to HDFS, tracking progress and counters, and retrying failed or slow tasks. The developer supplies the map and reduce functions and job configuration.

What problems does Hadoop not solve well?

Low-latency queries and point lookups, iterative and interactive workloads with MapReduce, real-time streaming, very large numbers of small files, and in-place updates of records. Other tools fill these gaps: HBase for lookups, Spark for iterative and in-memory work, Flink/Kafka for streaming, Trino/Impala for interactive SQL, and table formats such as Iceberg, Delta Lake and Hudi for updates.

Why was YARN introduced?

In Hadoop 1 the JobTracker handled both resource management and job tracking, which limited cluster size and allowed only MapReduce jobs. YARN separated these: the ResourceManager manages resources for the whole cluster, and each application has its own ApplicationMaster. This improved scalability and let other engines like Spark and Tez share the same cluster.

Real-world scenario questions (asked in company interviews)

Interviewers often test architecture knowledge by giving you a problem and asking which part of Hadoop handles it.

Any company · architectureFresher

“Walk me through what happens when I run a Hadoop job.”

The interviewer wants the end-to-end flow, naming which component does what, for a job that reads a file in HDFS and writes results.

The interviewer is checking: can you connect HDFS, YARN and MapReduce into one story?

Show a strong answer
  1. The file is already in HDFS: blocks on DataNodes, metadata on the NameNode.
  2. The client submits the job to the ResourceManager, which starts an ApplicationMaster in a container.
  3. The AM computes input splits from block locations and asks YARN for containers on (or near) those nodes.
  4. NodeManagers launch map tasks; each reads its block locally and writes partitioned, sorted output to local disk.
  5. Reducers shuffle (fetch) their partitions from all mappers, merge them and run reduce, writing output to HDFS.
  6. The AM tracks progress and re-runs failed tasks; when done, it reports success and exits.

Avoid: mentioning the JobTracker for a modern cluster (that was Hadoop 1).

ML team · architecture1–3 years

The ML training job takes 14 hours in MapReduce

A data scientist implemented a training algorithm with 30 iterations as 30 chained MapReduce jobs over the same 2 TB data set. It takes 14 hours.

The interviewer is checking: do you know which problems MapReduce did not solve, and what replaced it?

Show a strong answer
  • Each MapReduce job rereads the 2 TB from HDFS and writes its results back to HDFS, so 30 iterations mean about 60 full passes over disk, plus job start-up each time.
  • Move it to Spark on the same YARN cluster: load the data once, cache() it in executor memory, and iterate in memory. Spark MLlib already has many algorithms.
  • Keep HDFS as the storage; only the engine changes.

Avoid: “Add more nodes.” The waste is in the repeated I/O, not the lack of machines.

Platform team · capacity1–3 years

Each team wants its own cluster

Three departments each ask for a separate 30-node Hadoop cluster so that “others don't slow us down”. Finance asks whether that is necessary.

The interviewer is checking: do you understand what YARN was built for?

Show a strong answer
  • Separate clusters sit idle outside each team's busy hours, and data must be copied between them.
  • One shared cluster with YARN queues (Capacity or Fair Scheduler) gives each team a guaranteed share, lets them borrow idle capacity, and keeps one copy of shared data.
  • Isolation concerns are handled with queue limits, pre-emption, and per-team security (Kerberos, Ranger policies).
  • Separate clusters can still make sense for strict regulatory isolation or very different software versions.

Avoid: dismissing the teams' concern; explain how queues address it.

Banking · data correction1–3 years

“Just update the wrong rows in HDFS”

A bug wrote wrong interest amounts into 5,000 rows of a 2 TB table stored as files in HDFS. A manager asks you to “run an UPDATE on those rows”.

The interviewer is checking: do you know HDFS is write-once, and how updates are handled in practice?

Show a strong answer
  • HDFS files can't be edited in the middle. Plain Hive tables on files are corrected by rewriting the affected partitions (for example only the dates involved).
  • Modern table formats (Apache Iceberg, Delta Lake, Hudi) or Hive ACID tables support UPDATE/MERGE by writing new files and tracking which rows are current.
  • Fix the bug first, then reprocess from raw data if possible, keeping the raw layer unchanged.

Avoid: suggesting editing HDFS blocks directly.
