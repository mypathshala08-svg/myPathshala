Troubleshooting playbook

When a Hadoop cluster misbehaves, the error message usually names the layer that broke: the network, HDFS, YARN, the job or security. This lesson reproduces four real incidents on our lab, then turns every failure we met in this course into a playbook: a method, a layered checklist and a table from message to first command.

1 The story

Four alerts, one morning

Kabir has just joined the platform team. On his first on-call morning four messages arrive within an hour: an analyst gets “Connection refused”, the ingestion job can't create a folder, a report fails with “No live nodes contain current block”, and a second report has been sitting in ACCEPTED for twenty minutes while the cluster is half empty. He wants to restart everything. Arjun Sir asks him to open the playbook instead.

Kabir

Shall I just restart the NameNode and the ResourceManager? That fixes most things, right?

Arjun Sir

A restart hides the evidence and sometimes makes things worse: a restarted NameNode spends minutes in safe mode. Read each message first. Every one of them names a layer: the network, HDFS, YARN, or the job itself. Find the layer, then run the one command that confirms it.

Riya

So the four alerts are four different problems?

Arjun Sir

Yes, and none of them needs a restart. Today we reproduce all four on our lab, then build a playbook from every real failure we met in this course, so that next time the message itself tells you where to look.

2 Definition

A troubleshooting playbook

Formal definition (write this in exams)

A troubleshooting playbook (or runbook) is a documented, repeatable procedure for diagnosing and resolving operational incidents in a system. For Hadoop it combines a method (establish the symptom, its scope and recent changes; gather evidence from logs and metrics; form and test a hypothesis; apply the smallest safe fix; verify; record the incident) with a layered checklist that follows the dependency order of the platform: network and name resolution, HDFS (NameNode state and safe mode, DataNodes, block health), YARN (ResourceManager, NodeManagers, queues and limits), the application (ApplicationMaster, task attempts, input data) and security (authentication and authorisation). Each known symptom is mapped to its likely causes and the first command that confirms or rules them out. Incidents are closed with a blameless postmortem that improves the playbook, monitoring and automation.

In simple words

A doctor doesn't operate on everyone who says “it hurts”. They ask where, since when, what changed, look at test results, and then treat. A playbook is that routine written down for Hadoop: read the message, find the layer, run one command to confirm, fix the smallest thing, and write down what you learned.

Words you'll meet in this lesson

Troubleshooting at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Read the message, find the layer

  • Every Hadoop error message contains a clue word. Connection refused, UnknownHost: network or address. safe mode, block, replica: HDFS. queue, container, ACCEPTED: YARN. Exception at YourClass.java:27: your job.
  • Ask three questions before touching anything: what exactly fails, who else is affected, and what changed recently.
  • Never “just restart”. Look first, then change one thing.

Intermediate The method, step by step

  • Symptom: copy the exact message and time. Scope: one job, one user, one node, one queue, everyone?
  • Changes: a deploy, a config edit, a new data source, a node added or removed. Most incidents follow a change.
  • Evidence: hdfs dfsadmin -report, fsck, yarn node -list -all, yarn application -status, yarn logs, JMX metrics.
  • Hypothesis and one test that proves or disproves it. Then the smallest safe fix, then verify with the same command that showed the problem.

Advanced Operating like a platform team

  • Turn every incident into a playbook entry and, where possible, an alert (Lesson 12.4) or an automated check.
  • Separate mitigation (get the report out) from root cause (why the queue was too small). Track the second as a ticket.
  • Write blameless postmortems with a timeline, the detection gap (our stale-DataNode alert came 296 s late), and concrete follow-ups.
  • Practise: game days and DR drills (Lesson 12.2) find gaps before real incidents do.

Exam tip: For “How do you troubleshoot a failed Hadoop job?”, give the method (symptom → scope → recent changes → logs and metrics → hypothesis → smallest fix → verify → postmortem), the layer order (network, HDFS, YARN, application, security) and two real examples with their first command, e.g. safe mode → hdfs dfsadmin -safemode get; stuck in ACCEPTED → yarn application -status.

4 Step by step

Four incidents on our lab

Run with trouble_lab.sh on the Module 8 lab (in “Run it on your PC”). Each step creates one incident, shows the exact message, and undoes it.

  1. A. Connection refused

    hdfs dfs -ls hdfs://namenode:9000/
    Call From namenode/172.22.0.2 to namenode:9000 failed on connection exception: java.net.ConnectException: Connection refused
    The machine answered, but nothing listens on port 9000. “Refused” means the host exists and the port is wrong or the daemon is down; “UnknownHost” would mean the name itself is wrong. Check hdfs getconf -confKey fs.defaultFS (8020 here) and jps.

  2. B. Safe mode

    hdfs dfsadmin -safemode enter
hdfs dfs -mkdir /incident_b
hdfs dfs -cat /user/hadoop/data/menu.csv | head -1
hdfs dfsadmin -safemode leave
    Safe mode is ON Cannot create directory /incident_b. Name node is in safe mode. chai,drink,15,A Safe mode is OFF
    Writes fail, reads work: HDFS is read-only. Before leaving safe mode by hand, find out why it's on (-safemode get, NameNode log): after a restart it waits for enough block reports, and forcing it off with missing DataNodes can expose missing blocks.

  3. C. The only replica is on a stopped DataNode

    hdfs dfs -D dfs.replication=1 -put -f menu.csv /incident_c.csv
hdfs fsck /incident_c.csv -files -blocks -locations
docker exec lab8-worker2-1 hdfs --daemon stop datanode
hdfs dfs -cat /incident_c.csv
    DatanodeInfoWithStorage[172.22.0.6 the only replica is on worker2; stopping its DataNode No live nodes contain current block the read gave up after 16 s DataNode back: chai,drink,15,A
    fsck … -locations showed the one replica's address. With replication 1 there is no second copy, so the client tries, waits and gives up. Starting the DataNode made the block available again: no data was lost, only unavailable. With replication 3 this read would have succeeded.

  4. D. A job stuck in ACCEPTED on a half-empty cluster

    yarn application -list
yarn application -status application_…_0019
curl -s http://resourcemanager:8088/ws/v1/cluster/scheduler
    application_1792661456575_0018 RUNNING application_1792661456575_0019 ACCEPTED Diagnostics : … Application is added to the scheduler and is not yet activated. Queue's AM resource limit exceeded. queue default | AM limit 768 MB | AM used 512 MB
    yarn.scheduler.capacity.maximum-am-resource-percent is 0.1 by default: 10% of 6,144 MB ≈ 614 MB, which the scheduler rounds up to 768 MB. One 512 MB ApplicationMaster fits; a second would need 1,024 MB. The cluster had memory free, but the queue had no ApplicationMaster room.

  5. Write it down

    Title       Nightly report stuck in ACCEPTED (incident D)
Impact      report 48 min late, 1 queue, no data loss
Timeline    01:00 submitted · 06:05 noticed · 06:09 diagnosed · 06:16 mitigated
Root cause  queue AM limit (10%) filled by a long-running job
Detection   no alert for "ACCEPTED too long"  ← gap
Actions     alert on ACCEPTED > 15 min · AM percent 0.1 → 0.3 for reports · job timeout
    Blameless: it records what the system allowed, not who submitted the long job. The detection gap and the actions are the most valuable lines.

Under pressure, change one thing at a time and verify with the command that showed the problem. Two changes at once and you won't know which fixed it, or which made it worse.

5 See it happen

From message to layer to fix

Six steps through the four real incidents and the method that solved each one.

Four incidents 6 steps
What you see
  1. A: the client gets “Connection refused” for port 9000.
  2. B: a mkdir fails in safe mode while a read still works.
  3. C: the only replica sits on worker2; with its DataNode stopped the read gives up after 16 s.
  4. D: the second job waits in ACCEPTED because of the queue's ApplicationMaster limit.
  5. The fixes are small: leave safe mode on purpose, start the DataNode.
  6. Every incident ends with a written entry that makes the next one faster.
Behind the screen
  1. The problem is in front of everything: the client is knocking on a port where nothing listens.
  2. The NameNode is up but in safe mode: it serves reads and refuses changes.
  3. worker2 holds the only replica; once it's down no DataNode can serve the block.
  4. The queue's ApplicationMaster budget (10% → 768 MB) is used by one AM; the second AM would exceed it.
  5. Leaving safe mode and starting the DataNode fix B and C; D waits for the first job or a bigger AM percent.
  6. Each incident lived in exactly one layer. Finding the layer is most of the work.
6 Real-world use

Playbooks at work

1. On-call in a payments company

Every alert links to a runbook entry: what it means, the first command, the safe mitigation, and whom to call. The on-call engineer follows it before improvising.

Alert→Runbook entry→Mitigate, then root cause

2. Blameless postmortems at an e-commerce company

After a festive-sale incident, the team writes a timeline and actions without naming a culprit. The actions (an alert, a quota, a test) are tracked like features.

Incident→Timeline + causes→Tracked actions

3. Game days at a telecom operator

The platform team breaks things on purpose in staging (stop a DataNode, fill a queue, expire a ticket) and times how long the on-call team needs to diagnose each one with the playbook.

Planned failure→Diagnose with playbook→Fix the gaps

4. Automated health checks at a government data platform

Steps that are always the same (safe mode? missing blocks? lost NodeManagers? apps stuck in ACCEPTED?) run as a script every few minutes and post a summary, so humans start with the evidence.

Script→Same first commands→Summary in chat

5. Support tickets in a university research cluster

Students must attach the application ID, the exact message and the output of yarn application -status. Most tickets are solved from that alone, without logging in.

Student ticket→App ID + message→Answer from the table

Simplified; organisations differ in tools and policies.

7 Run the code

A symptom matcher for real error messages

The first step of every incident is reading the message. This matcher holds a few playbook rules (a pattern, the layer, the likely cause and the first command) and applies them to real messages from our lab.

import re
RULES = [
    (r"Connection refused",              "network", "wrong port or daemon down",       "getent hosts; jps"),
    (r"UnknownHostException",            "network", "name not resolvable",             "getent hosts <name>"),
    (r"in safe mode",                    "HDFS",    "NameNode is read-only",           "hdfs dfsadmin -safemode get"),
    (r"No live nodes contain",           "HDFS",    "every replica's DataNode is down", "hdfs fsck <path> -locations"),
    (r"AM resource limit exceeded",      "YARN",    "queue's ApplicationMaster limit",  "yarn application -status"),
    (r"Java heap space",                 "job",     "task heap too small",             "yarn logs (attempt)"),
    (r"cannot authenticate via",         "security","no Kerberos ticket",              "klist"),
]

def diagnose(message):
    for pattern, layer, cause, first in RULES:
        if re.search(pattern, message, re.IGNORECASE):
            return layer, cause, first
    return "unknown", "not in the playbook yet", "read the full log; add a rule"

messages = [
    "Call From namenode/172.22.0.2 to namenode:9000 failed on connection exception: java.net.ConnectException: Connection refused",
    "Cannot create directory /incident_b. Name node is in safe mode.",
    "No live nodes contain current block",
    "Application is added to the scheduler and is not yet activated. Queue's AM resource limit exceeded.",
    "Illegal partition for chai (4)",
]
for m in messages:
    layer, cause, first = diagnose(m)
    print(f"{layer:8} | {cause:32} | {first}")

Example 4AdvancedDiagnose · data

A bank's report fails with Java heap space only on month end

Problem statement

A bank's reconciliation job succeeds every day but fails on the last day of the month with Error: Java heap space in one reduce task. Daily data is 40 GB; month-end adds a 25× spike for one account type. What is the likely cause and the first command?

Input
one reducer · month end · 25× one key
Expected output
normal reducer 0.8 GB, hot reducer 10.8 GB

Approach

  1. Only one reduce task fails: think skew (Lesson 8.5).
  2. A reducer holding all values of one hot key in memory runs out of heap.
  3. First: the failed attempt's log and the reduce input records per task.

9 Quiz and revision

Check yourself

Quick revision

Lesson 12.6 in one screen

  • Method: symptom → scope → recent changes → evidence → hypothesis → smallest safe fix → verify → postmortem.
  • Layers in order: network/DNS → HDFS → YARN → job → security; stop at the first broken one.
  • Connection refused = host reached, port wrong or daemon down; UnknownHost = the name doesn't resolve.
  • Safe mode: reads work, writes fail; find why before forcing -safemode leave.
  • “No live nodes contain current block”: every replica's DataNode is down; fsck -locations.
  • ACCEPTED on an idle cluster: check yarn application -status diagnostics (AM limit, queue limits).
  • Job errors: yarn logs of the failed attempt gives the exception and line (Lesson 11.5).
  • Blameless postmortem: timeline, root cause, detection gap, tracked actions; add a playbook rule and an alert.

Interview and viva questions

How do you troubleshoot a Hadoop cluster problem?

Record the exact error and time, establish the scope (one job, user, node, queue or the whole cluster) and what changed recently. Then check the layers in order: network and name resolution, HDFS (NameNode state, safe mode, DataNodes, blocks with dfsadmin -report and fsck), YARN (yarn node -list -all, application status and queue limits), the job (yarn logs of the failed attempt) and security (klist, permissions). Apply the smallest safe fix, verify with the same command, and write a postmortem.

Why is my YARN application stuck in ACCEPTED?

The scheduler has accepted it but cannot start its ApplicationMaster. Common causes are the queue's AM resource limit (maximum-am-resource-percent, 10% by default), the queue or user limit being used up, no NodeManager with enough free memory, or node labels that no node matches. yarn application -status shows the diagnostics, e.g. “Queue's AM resource limit exceeded.”

What does “Name node is in safe mode” mean?

The NameNode is read-only: it serves reads but refuses changes to the namespace. It enters safe mode at startup until enough DataNodes have reported their blocks (99.9% by default), or when an administrator turns it on. Check with hdfs dfsadmin -safemode get and find out why before leaving it by hand.

What does “Could not obtain block” or “No live nodes contain current block” mean?

The client could not read any replica of a block, usually because the DataNodes holding all replicas are down or unreachable. Use hdfs fsck <path> -files -blocks -locations to see where the replicas are, bring those DataNodes back, and check that important data has replication 3.

What is a blameless postmortem?

A written review after an incident that records the timeline, impact, root cause, why detection was late and the follow-up actions, without blaming individuals. It assumes people acted reasonably with the information they had and focuses on changing the system so the incident can't repeat.

Build a timeline

Input

Expected output

    first = n.split()[0]
    if ":" not in first:
        continue

P8Advanced

A tiny rule engine with priorities

Some messages match several rules (a Java heap space inside a failed Streaming task). Return the most specific rule (longest pattern).

Input
rules + message
Expected output
subprocess failed -> streaming script crashed
Show solution and explanation 
import re
rules = {"Java heap space": "task heap too small", "subprocess failed": "streaming script crashed", "failed": "something failed"}
msg = "PipeMapRed.waitOutputThreads(): subprocess failed with code 1"
hits = [p for p in rules if re.search(p, msg)]
best = max(hits, key=len)
print(best, "->", rules[best])
subprocess failed -> streaming script crashed

How it works: “subprocess failed” beats the generic “failed”: specific rules first, generic ones as a fallback.

Real-world scenario questions (asked in company interviews)

Troubleshooting questions test method more than memory. Interviewers want to hear how you think under pressure.

Method · basicsFresher

“A user says HDFS is down. What do you do?”

A classic open question.

The interviewer is checking: method before action.

Show a strong answer
  • Get the exact message and time; check the scope: can I and other users list HDFS?
  • Check the NameNode (jps, web UI, hdfs dfsadmin -report, -safemode get) and the DataNodes.
  • If only that user fails, look at their client config and network (Connection refused, UnknownHost); if everyone fails, it's the NameNode or safe mode.
YARN · queuesExperienced

Jobs stuck in ACCEPTED, cluster 40% used

The business is waiting for a report.

The interviewer is checking: queue limits, not “add nodes”.

Show a strong answer
  • yarn application -status diagnostics: e.g. “Queue's AM resource limit exceeded” or user limit reached.
  • Scheduler REST/UI for that queue: AM limit vs AM used, capacity vs used, user limits.
  • Mitigate (kill or move a stuck job), then fix: raise maximum-am-resource-percent for queues with many small jobs, add an alert for long ACCEPTED times.
HDFS · dataExperienced

fsck reports missing blocks after a rack power failure

One rack of 20 nodes went down; it's back now, but 30 blocks are still missing.

The interviewer is checking: calm recovery, not deleting data.

Show a strong answer
  • hdfs fsck / -list-corruptfileblocks to list the files; -locations shows where replicas should be.
  • Check that all DataNodes of the rack really came back (dfsadmin -report), with all their disks mounted; missing disks are a common cause.
  • Only for blocks that are truly gone: restore from DR/backup (Lesson 12.2) or re-ingest; never run fsck -delete first.
Operations · cultureLead

“The same incident happened three times this quarter”

A director asks why.

The interviewer is checking: postmortems that lead to change.

Show a strong answer
  • Each time it was mitigated but the root-cause action wasn't owned or finished: track postmortem actions like product work.
  • Add detection (an alert), prevention (a quota, a config check in CI) and a playbook rule, so the fourth time is short or impossible.
  • Keep reviews blameless so people report near-misses early.
