Why companies run many clusters

Large companies rarely run one Hadoop cluster. They run a fleet: production, a disaster-recovery copy in another region, staging, development and sandboxes, sometimes split by business unit or by country. This lesson explains why, what the clusters must share, what a fleet costs, and builds a two-cluster fleet in our lab, including the mistake we made on the way.

2 Definition

A cluster fleet

Formal definition (write this in exams)

A multi-cluster deployment (or cluster fleet) is a set of independently operated Hadoop clusters, each with its own NameNode(s), ResourceManager and failure domain, run by one organisation for different purposes such as production, disaster recovery, staging and development, tenant or business-unit isolation, data residency and scale. Clusters exchange data through replication tools such as DistCp and share cross-cutting services: identity (Kerberos realms with trust), authorization policies (Apache Ranger), metadata (Hive Metastore, data catalog) and monitoring. Unlike HDFS federation, where several NameNodes share one set of DataNodes and one cluster ID, separate clusters share no storage and fail independently.

In simple words

Companies keep several Hadoop clusters for the same reasons a hospital keeps a backup generator and a separate training room: safety, testing, isolation and rules. The clusters copy data to each other and share logins, permissions and monitoring.

Intermediate The reasons, one by one

  • Safety: a DR cluster in another region survives a data-centre loss. HA (Lesson 7.1) protects against a dead NameNode, not a flooded building.
  • Change control: upgrades, new configs and new jobs are tried on staging first.
  • Isolation: queues (Lesson 11.3) share one cluster's CPU, but a runaway job can still fill HDFS or overload the NameNode. A separate cluster cannot.
  • Rules: some data must stay in a country or a network zone. In India, for example, the RBI requires payment-system data to be stored in India, so a global company may keep a separate Indian cluster (check the current rules with your compliance team).
  • Scale and organisation: one NameNode's memory limits the number of files (Lesson 7.5); mergers and separate budgets bring their own clusters.

Advanced Running a fleet

  • Shared identity: each cluster can have its own Kerberos realm, with cross-realm trust so a user's ticket works everywhere (Lesson 12.5).
  • Shared metadata: one Hive Metastore or catalog per environment so a table means the same thing on prod and DR.
  • Fleet inventory: a script or tool that asks every NameNode and ResourceManager for version, cluster ID, capacity and health (our fleet.py), feeding one dashboard (Lesson 12.4).
  • Configuration as code: generate every cluster's *-site.xml from one repository to stop drift.
  • Unique names: host names, nameservice IDs and cluster IDs must differ across clusters, or clients reach the wrong one, exactly as ours did.

Exam tip: For “Why do organisations run multiple Hadoop clusters?”, list at least four reasons (DR, dev/test/staging, isolation of workloads, data residency, scale), name the tool that moves data between them (DistCp), and mention the shared services (Kerberos, Ranger, metastore, monitoring). Distinguish this from HDFS federation.

Animated example: from one cluster to a fleet

A payments company grows a fleet 6 steps
Animated example
  1. Year 1: a single production cluster runs reports, ETL and developers' experiments.
  2. Year 2: a test job deletes a production folder, so developers get their own small cluster.
  3. Year 3: the regulator wants a recovery plan; a DR cluster in another city receives hourly DistCp copies.
  4. Year 4: an upgrade breaks a production job; upgrades are now rehearsed on a staging cluster first.

A rule of thumb: add a cluster when you need a separate failure domain, a separate change schedule or a separate legal boundary. If you only need fair sharing of CPU and memory, queues (Lesson 11.3) are cheaper.

5 See it happen

Two clusters, one network mistake

Six steps from our lab: the wrong way to join clusters, the fix, and the first fleet report.

Joining two clusters 6 steps
What you see
  1. We connect every prod container to the other cluster's network.
  2. The next job retries ten times and fails: Connection refused.
  3. We undo it and use the DR cluster with distinct names instead.
  4. Only the three workers join; prod names still resolve to prod.
  5. The fleet report lists both clusters and all three NameNodes.
  6. The first real copy to DR succeeds: 5 files, 170 MB (Lesson 12.2).
Behind the screen
  1. Joining a network gives each container a second address and makes its names visible there.
  2. The client resolved resourcemanager to the RM's second address; the RM only listens on its first.
  3. The DR cluster uses names that don't exist in prod.
  4. Only workers, where copy tasks run, sit on both networks.
  5. fleet.py reads each NameNode's JMX: version, cluster ID, nodes, files.
  6. DistCp's map tasks on the workers read from prod and write to DR.
6 Real-world use

Fleets at work

1. Banking: prod and DR in two cities

Banks keep a recovery copy of critical data in a second region and rehearse failover regularly; auditors ask for proof of the drills.

Prod (Mumbai)→Hourly DistCp→DR (Hyderabad)

2. E-commerce: isolating the sale-day pipeline

During a big sale, order and inventory pipelines run on a cluster that analysts cannot touch; experiments go to a sandbox fed with curated copies.

Orders→Prod cluster→Sandbox copies

3. Payments: data residency

Global payment companies keep Indian payment data on clusters in India to meet RBI's storage rule, while other regions run their own clusters.

Indian payments→India cluster→Aggregates only abroad

4. Telecom: blue-green upgrades

An operator builds a new cluster on the new Hadoop version, copies data and moves jobs one by one, keeping the old cluster as a fallback for a month.

Old cluster→Copy + move jobs→New cluster

5. Media and research: ephemeral clusters

Video and genomics teams start a cloud cluster for a nightly batch over data in object storage and delete it after, paying only for hours used.

Object storage→Cluster for 3 hours→Results, cluster gone

Simplified; organisations differ in tools, policies and regulations.

A fleet inventory and a cluster decision helper

The first part mimics fleet.py: one record per NameNode, then a summary per cluster ID (federated namespaces share one). The second part turns the reasons from this lesson into a simple decision helper.

fleet = [  # what fleet.py printed in our lab
    {"name": "prod (lab8)", "cluster": "CID-01fef50a", "version": "3.5.0", "dns": 3, "files": 1680, "used_mb": 4769},
    {"name": "dr ns canteen", "cluster": "campus-cluster", "version": "3.5.0", "dns": 3, "files": 15, "used_mb": 541},
    {"name": "dr ns hostel", "cluster": "campus-cluster", "version": "3.5.0", "dns": 3, "files": 4, "used_mb": 541},
]
clusters = {}
for nn in fleet:
    c = clusters.setdefault(nn["cluster"], {"namenodes": 0, "files": 0, "used_mb": nn["used_mb"], "dns": nn["dns"]})
    c["namenodes"] += 1
    c["files"] += nn["files"]
for cid, c in clusters.items():
    print(f"{cid:15} {c['namenodes']} NameNode(s)  {c['dns']} DataNodes  {c['files']:>5} files  {c['used_mb']:>5} MB")
versions = {nn["version"] for nn in fleet}
print("versions in the fleet:", versions, "-> no drift" if len(versions) == 1 else "-> DRIFT")

Check yourself

Quick revision

Lesson 12.1 in one screen

  • A fleet = several independent clusters: prod, DR, staging, dev, sandboxes, ephemeral cloud clusters.
  • Reasons: site failure (DR), change control (staging), isolation, data residency (e.g. RBI payment-data storage in India), NameNode scale, mergers, budgets.
  • Queues share compute; quotas limit space; only a separate cluster gives a separate failure domain.
  • Shared services: Kerberos realms with trust, Ranger, Hive Metastore/catalog, monitoring.
  • Federation (7.2) = one cluster ID, shared DataNodes; separate clusters fail independently.
  • Lab: prod CID-01fef50a (3 DNs, 1,680 files) + DR campus-cluster (2 namespaces); joining every container to both networks broke name resolution.
  • Unique host names, nameservice IDs and cluster IDs across the fleet; configuration as code to avoid drift.

Interview and viva questions

Why do companies run multiple Hadoop clusters?

To survive the loss of a data centre (a DR cluster in another region), to test upgrades and code safely (staging and development clusters), to isolate workloads that interfere with each other, to meet data-residency rules, to work around the scale limits of one NameNode, and for organisational reasons such as mergers or separate budgets. Data moves between them with DistCp, and they share identity, authorization and metadata services.

What is the difference between HDFS federation and multiple clusters?

Federation runs several NameNodes over one shared set of DataNodes with one cluster ID, to scale the namespace. Multiple clusters have separate NameNodes, DataNodes and cluster IDs, so they fail independently and can be in different places, versions or legal zones.

What is a disaster recovery cluster in Hadoop?

A second cluster, usually in another region, that receives regular copies of critical data (with DistCp, often snapshot-based) and can take over the important jobs if the production site is lost. Its recovery point is the time since the last successful copy.

How do users log in to many Hadoop clusters?

Each cluster uses Kerberos, either in one shared realm or in separate realms with cross-realm trust, so a user's ticket is accepted on every cluster. Authorization is kept consistent with central Ranger policies.

Is it better to have one big cluster or many small ones?

One big cluster uses hardware more efficiently and keeps data in one place; many clusters give isolation, separate change schedules, DR and legal separation at the cost of copies and operational work. Most large organisations combine a few big shared clusters with smaller special-purpose ones.

always = 50 * 24 * 30 * 60
ephemeral = 50 * (3 + 0.25) * 30 * 90
print(f"always-on Rs {always:,.0f}, ephemeral Rs {ephemeral:,.0f} per month")
always-on Rs 2,160,000, ephemeral Rs 438,750 per month

How it works: ₹21.6 lakh vs ₹4.4 lakh: for a few hours a day, an ephemeral cluster is far cheaper even at a higher hourly rate.

Real-world scenario questions (asked in company interviews)

Fleet questions appear in senior data-engineering and platform interviews.

Architecture · basicsFresher

“Why would a company need more than one Hadoop cluster?”

A common opening question for platform roles.

The interviewer is checking: breadth of reasons.

Show a strong answer
  • Disaster recovery in another region; dev/test/staging for safe changes.
  • Isolation of critical workloads from ad-hoc ones; data residency; NameNode scale limits.
  • Data moves with DistCp; identity, Ranger policies and metadata are shared.
Design · trade-offsExperienced

Analysts keep breaking the nightly pipeline

Ad-hoc queries on prod fill HDFS and slow the NameNode at night.

The interviewer is checking: choosing the cheapest effective isolation.

Show a strong answer
  • Queues for compute, space and name quotas for their folders as a first step.
  • If NameNode load or tooling needs differ, a sandbox cluster fed with curated copies.
  • Keep one catalog and Ranger policies so tables mean the same thing in both.
Operations · incidentExperienced

After connecting two clusters, jobs fail with “Connection refused”

The RM is up; the error names an IP nobody recognises.

The interviewer is checking: networking and naming in multi-cluster setups.

Show a strong answer
  • Check what the host name resolves to on the client; a multi-homed server may be reached on an address it doesn't listen on.
  • Use unique host names and nameservice IDs per cluster; bind servers to 0.0.0.0 or set bind-host properties if multi-homing is required.
  • Only give the machines that need it (workers running copies) access to both networks.
Governance · fleetLead

Seven clusters, four Hadoop versions, nobody knows which

You take over a platform team after an incident on a forgotten cluster.

The interviewer is checking: fleet management habits.

Show a strong answer
  • Build an inventory from each NameNode/RM (version, cluster ID, capacity, owner) and a single dashboard.
  • Configuration as code, one release train, staging rehearsal for every upgrade.
  • Retire or merge clusters without a clear purpose; document DR drills.
