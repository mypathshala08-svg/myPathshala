DistCp and disaster recovery

A second cluster only protects you if it holds the right data. This lesson copies a production folder to a real DR cluster with DistCp, catches the classic silent skip, keeps the copy in sync with -update, -delete and snapshot diffs, and runs a failover drill that shows exactly what a disaster would cost.

2 Definition

DistCp and disaster recovery

Formal definition (write this in exams)

DistCp (distributed copy) is a Hadoop tool that copies large directory trees within or between clusters by running a map-only MapReduce job: the client builds a listing of source files, splits it into chunks, and each map task copies its files directly from source DataNodes to destination DataNodes, verifying checksums. Options control incremental behaviour (-update copies files whose size or checksum differ, -overwrite copies unconditionally, -delete removes target files missing from the source, -diff applies a snapshot difference), what metadata is preserved (-p), parallelism (-m) and bandwidth (-bandwidth). Disaster recovery (DR) is the set of plans, copies and procedures that let a service resume at another site after the primary site is lost. It is measured by the recovery point objective (RPO), the maximum acceptable data loss expressed as time, and the recovery time objective (RTO), the maximum acceptable time to restore service.

In simple words

DistCp is cp for clusters: many map tasks copy files in parallel. DR means keeping a second copy far away and knowing how to switch to it. RPO = how much data you can lose; RTO = how long you can be down.

DR at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A spare key with a neighbour

  • You keep a spare house key with a neighbour in another street. If you lose yours, you can still get in: that is DR.
  • If you changed the lock last week and forgot to give the neighbour the new key, the spare is useless. A stale copy is the risk DistCp -update protects against.
  • How old the spare may be is the RPO; how long it takes to walk over and get it is the RTO.

Intermediate How DistCp decides what to copy

  • No option: if a file with the same name exists at the target, it is skipped. Our changed menu.csv was skipped.
  • -update: copy if the target is missing, or if size or checksum differ. menu.csv was copied (143 bytes).
  • -overwrite: copy everything again, always.
  • -delete (with -update or -overwrite): delete target files not present at the source.
  • -diff s1 s2: ask the NameNode what changed between two snapshots, replay renames and deletes, copy only new or modified files.

Advanced What production DR adds

  • Metadata too: Hive/Impala tables need their metastore replicated (schemas, partitions), not just HDFS files.
  • Checksums across settings: HDFS file checksums depend on block size and checksum type. Copy with -pb (preserve block size) or use dfs.checksum.combine.mode=COMPOSITE_CRC; -skipcrccheck hides real corruption and is a last resort.
  • Across versions and clouds: webhdfs:// works between different Hadoop versions; s3a:// and abfs:// targets copy to cloud storage.
  • Drills: a DR plan that was never tested is a guess. Teams run the real jobs on DR a few times a year and measure the actual RTO.

Exam tip: For "What is DistCp and how is it used for DR?", say: a map-only MapReduce job that copies files in parallel between clusters; incremental with -update (size + checksum) and -delete; snapshot-based with -diff; and define RPO and RTO with one example.

DR designs

Backup only

Copies on cheaper storage (another cluster, cloud). Protects data, but restoring and rebuilding compute takes days: long RTO.

cheapest

Active–passive

A DR cluster kept in sync (nightly or hourly DistCp). Jobs move there on failover. RPO = sync interval.

most common

Active–active

Both sites ingest and serve; data is written to both or replicated continuously. Low RPO/RTO, highest cost and complexity.

critical systems

Cloud as DR

DistCp to s3a:// or abfs://; spin up a cloud cluster only during a disaster.

pay when used

Animated example: when Chennai floods

An insurer's DR night 6 steps
Animated example
  1. 01:00: the nightly snapshot-diff DistCp copies the day's changes from Chennai to the Pune DR cluster.
  2. Daytime: new claims keep arriving, but only Chennai has them until the next sync.
  3. 19:00: a flood takes the Chennai data centre offline.
  4. 19:40: following the runbook, the team points jobs and users at the Pune NameNode.
  5. 20:30: service is back (RTO 1.5 hours), but claims written since 01:00 are lost (RPO 18 hours).
  6. Afterwards: hourly snapshots and diff syncs cut the possible loss to about one hour. (Illustrative scenario.)

Run DistCp from the cluster with spare YARN capacity and, when versions differ, from the newer one, reading the older cluster over webhdfs://. In our lab the maps ran on prod's workers, the only machines that could reach both clusters.

4 Step by step

Two clusters, one nightly sync, one drill

Prod is the Module 8 cluster; DR is the federation cluster from Lesson 7.2 (hdfs://nn-canteen:8020). Commands run on a prod worker, which join_clusters.sh connects to both networks.

  1. First full copy

    hadoop distcp /prod/canteen hdfs://nn-canteen:8020/dr/
    exit 0, took 25540 ms Bytes Copied=169964453 Files Copied=5 Launched map tasks=5
    A map-only job: the client listed 5 files, YARN ran 5 copy maps on prod's workers, and each map streamed blocks from prod DataNodes into DR DataNodes, then compared checksums.

  2. A day later: plain DistCp again

    hadoop distcp /prod/canteen hdfs://nn-canteen:8020/dr/
    Bytes Copied=70147 Files Copied=1 Files Skipped=4 143 /dr/canteen/menu.csv 5093962 /dr/canteen/feedback.txt
    Only the new file was copied. The changed menu.csv (same name, same size) and the deleted feedback.txt were left as they were, and the job still reported success.

  3. -update, then -update -delete

    hadoop distcp -update /prod/canteen hdfs://nn-canteen:8020/dr/canteen
hadoop distcp -update -delete /prod/canteen hdfs://nn-canteen:8020/dr/canteen
hdfs dfs -cat hdfs://nn-canteen:8020/dr/canteen/menu.csv | head -1
    Bytes Copied=143 Files Copied=1 Files Skipped=4 ... Files Skipped=5 chai,drink,18,A
    With -update, source and target paths are the folders themselves. Size was equal, but the checksums differed, so menu.csv was copied. -delete then removed feedback.txt from DR.

  4. Sync only a snapshot difference

    hdfs dfs -createSnapshot /prod/canteen s1     # and s1 on the DR copy
hdfs dfs -mv  .../orders_day31.csv .../orders_2026-10-31.csv ; put orders_2026-11-01.csv
hdfs dfs -createSnapshot /prod/canteen s2
hdfs snapshotDiff /prod/canteen s1 s2
hadoop distcp -update -diff s1 s2 /prod/canteen hdfs://nn-canteen:8020/dr/canteen
    M . + ./orders_2026-11-01.csv R ./orders_day31.csv -> ./orders_2026-10-31.csv exit 0, took 15085 ms Bytes Copied=28086 Files Copied=1 Launched map tasks=1
    DistCp asked the NameNode for the diff instead of comparing every file. The rename was applied as a rename on DR (no bytes copied) and only the new 28 KB file travelled. On millions of files this is the difference between hours of listing and minutes.

  5. Throttle the copy

    hadoop distcp -bandwidth 1 /prod/canteen/student_orders.csv hdfs://nn-canteen:8020/dr/throttled.csv
    exit 0, took 34192 ms Bytes Copied=19418699
    At 1 MB/s per map, 19.4 MB needs at least 19 s of copying plus job start-up. Throttling protects the link between sites during business hours.

  6. Disaster drill

    hadoop jar mr.jar ItemRevenue hdfs://nn-canteen:8020/dr/canteen/canteen_orders.csv hdfs://nn-canteen:8020/dr/report
hdfs dfs -put day32.csv /prod/canteen/orders_2026-11-02.csv      # written after the last sync
    completed successfully chai 50170 752550 dosa 49948 2247660 idli 49984 1499520 prod files: 7 DR files: 6 missing on DR: orders_2026-11-02.csv
    The Lesson 8.1 report gives identical numbers from DR data. But anything written after the last sync exists only on prod: if prod were gone now, that file would be lost. That gap is the RPO.

Never point a scheduled sync at the wrong direction or the wrong folder with -delete: it will faithfully delete everything the source doesn't have. Test every new sync command on a scratch folder first, and keep snapshots on the target so a bad run can be undone.

What you see
  1. The first copy moves all 5 files, 170 MB, with 5 map tasks in 25.5 s.
  2. Run again without options: only the new file is copied; the changed menu is skipped.
  3. With -update, the menu's checksum mismatch is noticed and 143 bytes are copied.

  5. The snapshot diff sync copies one 28 KB file and replays a rename.
  6. The drill runs the report on DR; one file written after the sync is missing.
Behind the screen
  1. DR becomes an exact copy: each map copies one file and verifies it.
  2. Prod changed the menu, added a file and deleted one; plain DistCp only notices the new name.
  3. -update compares size and checksum; equal sizes are not enough to skip.
  4. -delete removes target files that no longer exist at the source.
  5. With snapshots, only the listed changes are applied: a rename and one new file.
  6. DR can run the same jobs, but always lags prod by the time since the last sync.
6 Real-world use

DistCp and DR at work

1. Bank: regulator-mandated DR

Banks must show a tested DR plan. Transaction history in HDFS is synced to a second data centre several times a day, and failover drills are run and reported every quarter.

Hourly snapshots→distcp -diff→DR site + drill report

2. Telecom: migrating to a new cluster

When a telecom moves petabytes of call records from an old Hadoop distribution to a new cluster, DistCp over webhdfs:// copies data while both run; repeated -update runs shrink the final cut-over window.

Old cluster→distcp -update (repeat)→New cluster

3. E-commerce: archive to the cloud

Old order data is copied to object storage (s3a:// or abfs://) with DistCp, verified, and then deleted from the on-prem cluster to free disks.

HDFS (cold data)→distcp → s3a://→Cheap object storage

4. Analytics team: refreshing a test cluster

A masked sample of production data is copied to the development cluster every week so new jobs are tested on realistic data without touching prod.

Prod (masked)→distcp -update -delete→Dev cluster

5. Healthcare: two regions, active–active

A hospital chain ingests records in two regions and replicates each region's data to the other, so either site can serve all reports if one goes down.

Region A ⇄ Region B→scheduled two-way sync→Either site serves

Simplified; organisations differ in tools and policies.

7 Run the code

Decide like DistCp

This model reproduces our second run. Each file has a size and a checksum. Plain DistCp only checks whether the name exists at the target; -update also compares size and checksum; -delete removes target files the source no longer has.

prod = {"canteen_orders.csv": (4692009, "c1"), "menu.csv": (143, "m2"),
        "orders_day31.csv": (70147, "d1"), "orders_x30.csv": (140759640, "x1"),
        "student_orders.csv": (19418699, "s1")}
dr = {"canteen_orders.csv": (4692009, "c1"), "menu.csv": (143, "m1"),
      "feedback.txt": (5093962, "f1"), "orders_x30.csv": (140759640, "x1"),
      "student_orders.csv": (19418699, "s1")}

def plan(src, dst, update=False, delete=False):
    copy, skip = [], []
    for name, (size, crc) in src.items():
        if name not in dst:
            copy.append(name)
        elif update and dst[name] != (size, crc):   # size OR checksum differs
            copy.append(name)
        else:
            skip.append(name)
    gone = [n for n in dst if n not in src] if delete else []
    return copy, skip, gone

for opts in [{}, {"update": True}, {"update": True, "delete": True}]:
    c, s, g = plan(prod, dr, **opts)
    print(opts or "no options", "-> copy", c, "| skipped", len(s), "| delete", g)
no options -> copy ['orders_day31.csv'] | skipped 4 | delete [] {'update': True} -> copy ['menu.csv', 'orders_day31.csv'] | skipped 3 | delete [] {'update': True, 'delete': True} -> copy ['menu.csv', 'orders_day31.csv'] | skipped 3 | delete ['feedback.txt']

Interview and viva questions

What is DistCp in Hadoop?

DistCp (distributed copy) copies large amounts of data within or between clusters. It runs as a map-only MapReduce job: the client lists the source files, and map tasks copy them in parallel from source DataNodes to destination DataNodes, verifying checksums. It supports incremental copies (-update, -delete), snapshot-based syncs (-diff), preserving metadata (-p) and throttling (-bandwidth).

What is the difference between -update and -overwrite in DistCp?

With -update, a file is copied only if it is missing at the target or its size or checksum differs. With -overwrite, every file is copied again even if it is identical. Without either, files whose names already exist at the target are skipped, even if their content changed.

What are RPO and RTO?

The recovery point objective (RPO) is the maximum acceptable amount of data loss, measured as the time since the last good copy. The recovery time objective (RTO) is the maximum acceptable time to restore service after a disaster. Sync frequency drives RPO; automation and drills drive RTO.

How do you do disaster recovery for HDFS?

Keep a second cluster (or cloud storage) at another site, sync data with scheduled DistCp runs (ideally snapshot-based with -diff), replicate metadata such as the Hive metastore, document a failover runbook (DNS, job configs, access) and test it with regular drills. Commercial tools (for example Cloudera Replication Manager) automate the same steps.

Why does DistCp fail with a checksum mismatch between clusters?

HDFS file checksums are computed from block-level checksums, so they depend on block size and checksum type. If source and target use different settings, the checksums differ even for identical data. Preserve block size and checksum type (-pbc) or use the COMPOSITE_CRC combine mode; use -skipcrccheck only when you verify the data another way.

P8Advanced

Build a copy plan from a snapshot diff

Given a snapshotDiff report with +, -, M and R lines, produce the list of DR actions and the bytes to copy.

Input
diff lines + sizes
Expected output
[('copy', './a.csv'), ('delete', './old.csv'), ('rename', './x.csv', './y.csv'), ('copy', './menu.csv')] 28229 bytes
Show solution and explanation 
diff = ["M\t.", "+\t./a.csv", "-\t./old.csv", "R\t./x.csv -> ./y.csv", "M\t./menu.csv"]
size = {"./a.csv": 28086, "./menu.csv": 143}
plan, nbytes = [], 0
for line in diff:
    kind, path = line.split("\t")
    if path == ".":
        continue
    if kind in "+M":
        plan.append(("copy", path)); nbytes += size[path]
    elif kind == "-":
        plan.append(("delete", path))
    elif kind == "R":
        plan.append(("rename",) + tuple(path.split(" -> ")))
print(plan, nbytes, "bytes")
[('copy', './a.csv'), ('delete', './old.csv'), ('rename', './x.csv', './y.csv'), ('copy', './menu.csv')] 28229 bytes

How it works: Copy a.csv and menu.csv (28,229 bytes), delete old.csv, rename x.csv to y.csv: everything else is untouched.

Real-world scenario questions (asked in company interviews)

DistCp and DR questions come up in data platform and Hadoop admin interviews.

Tools · basicsFresher

"How do you copy data between two Hadoop clusters?"

A standard question for any Hadoop role.

The interviewer is checking: DistCp and its key options.

Show a strong answer
  • Use DistCp: a map-only MapReduce job that copies files in parallel and verifies checksums.
  • For repeated syncs use -update (size + checksum) and -delete; for big folders use snapshots with -diff.
  • Throttle with -bandwidth, preserve metadata with -p, use webhdfs:// across Hadoop versions.
Incident · dataExperienced

The DR copy has old data, but every nightly job "succeeded"

An auditor finds that a reference table on DR is three months out of date.

The interviewer is checking: DistCp default semantics and verification.

Show a strong answer
  • Plain DistCp skips files whose names already exist; a file rewritten with the same name was never copied again.
  • Fix the job: -update (and -delete if DR must mirror deletions), or snapshot-based -diff syncs.
  • Add verification: compare file counts and checksums (hdfs dfs -checksum) for key folders, and alert on differences.
Design · DRExperienced

Design DR for a 2 PB cluster with RPO 1 hour

A payments company asks for a plan and its cost drivers.

The interviewer is checking: RPO/RTO thinking and incremental replication.

Show a strong answer
  • Seed DR once (staged DistCp or shipped disks), then hourly snapshots with distcp -update -diff on the changed folders.
  • Replicate the Hive metastore and configs; keep a runbook for DNS, job schedulers and access; run quarterly drills.
  • Size the link for the hourly change rate with headroom; monitor sync lag as a first-class alert.
Concepts · RPO/RTOFresher

"What is the difference between backup and disaster recovery?"

Often asked together with RPO and RTO.

The interviewer is checking: data protection vs service continuity.

Show a strong answer
  • Backup keeps copies of data so it can be restored; restoring and rebuilding compute may take days (long RTO).
  • DR keeps a ready site that can take over the service within the RTO, with data no older than the RPO.
  • Many teams need both: DR for outages, backups or snapshots for mistakes (a bad -delete is replicated to DR too).
