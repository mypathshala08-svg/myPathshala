2 Definition

A batch pipeline, stage by stage

Formal definition (write this in exams)

A batch data pipeline is a sequence of jobs that turns raw input into trusted outputs. Each stage reads the previous stage's output and writes its own: bronze (raw, immutable), a staging or cleansing step that applies data quality rules and deduplication, silver (cleaned, typed, conformed, partitioned by business date) and gold (aggregated tables for consumers). A production pipeline is idempotent (re-running a stage for the same input gives the same output), observable (counters and logs for every rule) and verified by automated acceptance checks before results are published.

In simple words

Each stage does one job and leaves its result in its own folder. If something is wrong you re-run that stage, it overwrites its old output, and the checks tell you whether the numbers are right.

The pipeline at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner What each stage does

  • Clean: reads every raw line, throws out broken and test lines (but counts them), and keeps one copy of each order.
  • Silver: stores the clean orders in a compact, typed format, one folder per day.
  • Gold: small summary tables: money per canteen per day, item sales, busy hours, UPI check.

Intermediate How the clean job works

  • The mapper parses each line; a good line becomes order_id TAB file_day TAB raw; a broken line gets the key ~BAD.
  • The shuffle brings every copy of an order_id to the same reducer, sorted by key (Lesson 8.4).
  • The reducer keeps the copy from the earliest file, adds the category and price check from menu.csv, and writes OK lines; ~BAD lines pass through as BAD.
  • Every rule increments a counter by printing reporter:counter:capstone,NAME,n to stderr (Lesson 9.8).

Advanced Production details that matter

  • Schema on read, explicitly: Spark reads the TSV with a 14-column string schema. Without it Spark guesses the column count from a sample, and a file that starts with a 3-column BAD line breaks the table.
  • Dynamic partition overwrite: spark.sql.sources.partitionOverwriteMode=dynamic lets silver_gold.py 2026-09-14 replace only that day.
  • Left join for reconciliation: UPI orders LEFT JOIN gateway SUCCESS; rows with no match are the gaps. An inner join would hide exactly the problem we look for.
  • Gold is small: coalesce(1) writes one file per gold table, so consumers don't read 200 tiny files.

Exam tip: For "explain a MapReduce job you wrote", describe key and value: "Mapper emits order_id as key so all copies of an order meet in one reducer; the reducer keeps the earliest copy (dedupe) and counts DUPLICATE, LATE and other rules with counters. 104 maps, 3 reducers, 357,215 records shuffled, 354,135 orders out."

Animated example: three copies of one order meet in a reducer

Deduplication as a shuffle 6 steps
Animated example
  1. A map task reading the file of 12 September emits order …00377 with its file day.
  2. The same order also sits in another split and in the file of 14 September, so two more copies are emitted.
  3. The partitioner sends every record with the same key to the same reducer, whichever mapper produced it.
  4. The reducer receives keys in sorted order, so all three copies come one after another.
  5. It keeps the copy with the earliest file day and adds 2 to DUPLICATE.
  6. On the full data: 357,215 records shuffled into 354,136 keys (354,135 orders plus the ~BAD key). (Simplified to one order; real splits hold thousands.)

Test the shuffle logic with a tiny file that contains the hard cases (two copies in one file, a copy in the next file, a broken line) and know the expected output by heart. When the big run disagrees, run the tiny file first.

Our first version read the cleaned TSV without a schema. Spark takes the number of columns from the first line it samples; if that line is a 3-field BAD line, every OK line is cut to 3 columns. Always give an explicit schema for text inputs that mix record types, or split them into separate outputs.

5 See it happen

One late order through the whole pipeline

Order KHR-0912-04461 (one idli, ₹30, UPI), a real row from our data: sold on Saturday 12 September at 18:25, arrived in Monday's file. Left: the row as you would see it at each stage. Right: where the work happens on the cluster.

From raw line to gold 6 steps
What you see
  1. The raw line sits in Monday's Kharghar file, exactly as the till sent it.
  2. The mapper emits the order_id as key, plus the file day and the raw line.
  3. The reducer keeps it (no other copy), adds category breakfast, and flags it late because it arrived on the 14th.
  4. Spark writes it with real types into the folder of the day it was sold: dt=2026-09-12.
  5. Gold counts it on Saturday, not Monday, and matches its UPI payment.
  6. The checks confirm all 2,100 late orders were kept on their own days.
Behind the screen
  1. The file is one small block with three replicas, so YARN can run its map task on any worker: all 104 maps were data-local.
  2. Each map container starts a JVM that pipes lines into our Python mapper; Hadoop tells it the file name through an environment variable.
  3. Each of the 3 reducers pulls its share from every map (104 × 3 = 312 shuffles) and writes one part file.
  4. Spark's executors read the parts, cast types and write one folder per business day.
  5. Aggregations shuffle by day and canteen; the UPI check is a left join; gold tables are tiny.
  6. The checks read everything back and compare with truth.json. Nothing is published on a FAIL.
6 Real-world use

The same pipeline shape at work

1. Food delivery: restaurant payouts

Orders from the app are deduplicated, matched with payment-gateway settlements and refunds, and turned into a weekly payout per restaurant. A left join finds orders with no settlement before money is paid out.

Orders + gateway files→dedupe, reconcile→Payout file

2. Electricity: smart-meter billing

Meters re-send readings after network outages. The pipeline dedupes on meter ID + reading time, bills on the reading date, and quarantines impossible values for field engineers.

Meter batches→dedupe on key, event time→Monthly bills

3. Retail: price-compliance reports

Every sale is compared with the price valid that day. Stores billing old prices (like our Panvel till) appear in a gold table with the rupee gap, and the store systems team gets a ticket.

Sales + price history→date-range join, flag→Compliance table

4. Ed-tech: daily learning dashboards

App events are cleaned, stored by day in Parquet and aggregated into lessons watched per course per day. A backfill after a tracking bug overwrites only the affected days.

App events→silver by dt, overwrite→Dashboards

5. Banking: regulatory returns

Before a report goes to the regulator, automated checks compare its totals with the general ledger. A single FAIL stops publication, the same gate as our check.py.

Transactions→aggregate + reconcile + checks→Filed report

Simplified; organisations differ in tools and policies. Kadak Canteens and its data are fictional.

7 Run the code

The whole pipeline in 40 lines

A miniature of our pipeline: the mapper, the shuffle (sorted), the reducer and one gold table, on eight raw lines from two files. The rules are the real ones.

files = {"09-12": ["K-0912-1,2026-09-12 08:10:00,KHR,S1,chai,1,15,UPI",
                   "K-0912-2,2026-09-12 13:05:00,KHR,S2,thali,1,80,UPI",
                   "K-0912-2,2026-09-12 13:05:00,KHR,S2,thali,1,80,UPI",
                   "K-0912-3,2026-09-12 13:40:00,KHR,S3,dosa"],
         "09-14": ["K-0912-4,2026-09-12 17:55:00,KHR,S4,vada pav,2,40,UPI",
                   "K-0914-1,2026-09-14 08:02:00,KHR,S5,maggi,1,30,CASH",
                   "K-0914-2,2026-09-14 09:15:00,KHR,TEST,idli,1,30,CASH",
                   "K-0912-2,2026-09-12 13:05:00,KHR,S2,thali,1,80,UPI"]}
menu = {"chai": "drink", "thali": "meal", "dosa": "meal", "vada pav": "snack", "idli": "breakfast"}
count = {}

def mapper(file_day, line):
    f = line.split(",")
    if len(f) != 8:
        count["MALFORMED"] = count.get("MALFORMED", 0) + 1
        return []
    if f[3] == "TEST":
        count["TEST_ORDER"] = count.get("TEST_ORDER", 0) + 1
        return []
    return [(f[0], file_day, line)]

pairs = [p for day, lines in files.items() for line in lines for p in mapper(day, line)]
pairs.sort()                                   # the shuffle and sort
clean, i = [], 0
while i < len(pairs):                          # the reducer: one group per order_id
    j = i
    while j < len(pairs) and pairs[j][0] == pairs[i][0]:
        j += 1
    file_day, line = min((d, l) for _, d, l in pairs[i:j])
    count["DUPLICATE"] = count.get("DUPLICATE", 0) + (j - i - 1)
    f = line.split(",")
    late = file_day > f[1][5:10]
    clean.append((f[1][:10], f[4], menu.get(f[4], "unknown"), int(f[6]), late))
    i = j

gold = {}
for dt, item, cat, amount, late in clean:
    gold[dt] = gold.get(dt, 0) + amount
print("counters:", count)
print("clean   :", clean)
print("gold    :", gold)
counters: {'MALFORMED': 1, 'TEST_ORDER': 1, 'DUPLICATE': 2} clean : [('2026-09-12', 'chai', 'drink', 15, False), ('2026-09-12', 'thali', 'meal', 80, False), ('2026-09-12', 'vada pav', 'snack', 40, True), ('2026-09-14', 'maggi', 'unknown', 30, False)] gold : {'2026-09-12': 135, '2026-09-14': 30}
  • return [(f[0], file_day, line)]Key = order_id, plus the file day: exactly what clean_mapper.py prints, as a tuple.
  • pairs.sort() # the shuffle and sortSorting puts every copy of an order next to the others, like Hadoop's shuffle.
  • file_day, line = min((d, l) for _, d, l in pairs[i:j])Earliest file wins; the other copies are counted as DUPLICATE.
  • late = file_day > f[1][5:10]Sold on the 12th, first seen in the 14th's file: late, but counted on the 12th.

2 · Silver and gold (Spark on YARN)

# silver_gold.py: cleaned text -> silver Parquet (partitioned by day) -> gold KPI tables
import sys
from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder.appName("capstone-silver-gold")
         .config("spark.sql.sources.partitionOverwriteMode", "dynamic")   # re-runs replace only their days
         .config("spark.sql.shuffle.partitions", "6").getOrCreate())
spark.sparkContext.setLogLevel("ERROR")
B = "hdfs://namenode/capstone"
cols = ["status", "order_id", "dt", "ts", "college", "student_id", "item", "category", "qty", "amount",
        "pay_mode", "late", "unknown_item", "undercharged"]

schema = ", ".join(c + " STRING" for c in cols)          # read everything as text first, then cast
raw = spark.read.schema(schema).option("sep", "\t").csv(f"{B}/stage/clean")   # BAD rows fill 3 columns
orders = (raw.where("status = 'OK'").drop("status")
          .withColumn("ts", F.to_timestamp("ts")).withColumn("dt", F.to_date("dt"))
          .withColumn("qty", F.col("qty").cast("int")).withColumn("amount", F.col("amount").cast("int"))
          .withColumn("late", F.col("late") == "1").withColumn("unknown_item", F.col("unknown_item") == "1")
          .withColumn("undercharged", F.col("undercharged").cast("int")))
days = sys.argv[1:]                                    # optional: only these days (a backfill)
if days:
    orders = orders.where(F.col("dt").isin(days))
orders.write.mode("overwrite").partitionBy("dt").parquet(f"{B}/silver/orders")
raw.where("status = 'BAD'").select("order_id", "dt").toDF("file_day", "raw_line") \
   .write.mode("overwrite").json(f"{B}/quarantine/orders")

pay = spark.read.json(f"{B}/bronze/payments").withColumn("dt", F.to_date(F.substring("ts", 1, 10)))
pay.write.mode("overwrite").partitionBy("dt").parquet(f"{B}/silver/payments")

o = spark.read.parquet(f"{B}/silver/orders")
p = spark.read.parquet(f"{B}/silver/payments")
ok = p.where("status = 'SUCCESS'").select("order_id", F.col("amount").alias("paid"))
upi = o.where("pay_mode = 'UPI'").join(ok, "order_id", "left")          # every UPI order, paid or not
gold = {
  "daily_college": o.groupBy("dt", "college").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")),
  "item_mix": o.groupBy("college", "item", "category").agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")),
  "hourly": o.groupBy(F.hour("ts").alias("hour")).agg(F.count("*").alias("orders")),
  "upi_recon": (o.where("pay_mode = 'UPI'").groupBy("college").agg(F.sum("amount").alias("pos_upi"))
                .join(p.join(o.select("order_id", "college"), "order_id").groupBy("college").agg(
                      F.sum(F.when(F.col("status") == "SUCCESS", F.col("amount")).otherwise(0)).alias("gateway_success"),
                      F.sum(F.when(F.col("status") == "REFUNDED", F.col("amount")).otherwise(0)).alias("refunds"),
                      F.sum(F.when(F.col("status") == "FAILED", 1).otherwise(0)).alias("failed_attempts")), "college")
                .withColumn("gap", F.col("pos_upi") - F.col("gateway_success"))),
  "upi_gaps": (upi.where("paid IS NULL").groupBy("dt", "college", F.hour("ts").alias("hour"))
               .agg(F.count("*").alias("orders"), F.sum("amount").alias("unconfirmed"))),
}
for name, df in gold.items():
    df.coalesce(1).write.mode("overwrite").parquet(f"{B}/gold/{name}")

print("== silver.orders ==")
o.agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue"), F.countDistinct("dt").alias("days"),
      F.sum(F.col("late").cast("int")).alias("late"), F.sum(F.col("unknown_item").cast("int")).alias("unknown"),
      F.sum("undercharged").alias("undercharged")).show()
print("== gold.daily_college: month by canteen ==")
spark.read.parquet(f"{B}/gold/daily_college").groupBy("college").agg(F.sum("orders").alias("orders"),
      F.sum("revenue").alias("revenue")).orderBy(F.desc("revenue")).show()
print("== gold.upi_recon ==")
spark.read.parquet(f"{B}/gold/upi_recon").orderBy("college").show()
print("== gold.upi_gaps: UPI orders with no SUCCESS from the gateway ==")
spark.read.parquet(f"{B}/gold/upi_gaps").orderBy("dt", "college", "hour").show()
print("== gold.hourly: top 3 hours ==")
spark.read.parquet(f"{B}/gold/hourly").orderBy(F.desc("orders")).show(3)
print("== gold.item_mix: maggi and Panvel chai ==")
spark.read.parquet(f"{B}/gold/item_mix").where("item = 'maggi' or (college = 'PNL' and item = 'chai')").show()

Interview and viva questions

How did you remove duplicates in MapReduce?

The mapper emits order_id as the key with the file day and the raw line as the value. The shuffle sends all records with the same key to the same reducer, sorted, so the copies arrive together. The reducer keeps the copy from the earliest file and increments a DUPLICATE counter by the number of extra copies.

How do you make a Spark job idempotent?

Write output partitioned by business date and use overwrite with dynamic partition overwrite mode, so each run replaces exactly the partitions it produces. Never append blindly. Then a retry or backfill for a day gives the same result as the first run.

What is the difference between silver and gold?

Silver holds cleaned, typed, deduplicated records at the original grain (one row per order). Gold holds aggregated tables designed for specific consumers and questions, such as revenue per canteen per day.

How do you reconcile two datasets?

Agree a key and a measure, join from the system that should be complete (left join), and compare per group: counts and amounts. Explain every difference with a category (refunds, failed attempts) and report what is left as a gap with its exact keys, dates and amounts.

Why use counters instead of print statements?

Counters are aggregated by the framework across all tasks, keep only successful attempts, appear in the job output and history server, and can be checked automatically. Prints in hundreds of task logs cannot be summed reliably.

Real-world scenario questions (asked in company interviews)

Questions interviewers ask after you describe a pipeline like this one.

Debugging · dataFresher

"Your dashboard shows yesterday's revenue doubled. What happened?"

Nothing changed in the code; the scheduler retried a failed run.

The interviewer is checking: idempotency.

Show a strong answer
  • The retry appended the same day again: the first attempt had already written part of its output.
  • Fix the data by overwriting that day's partition; fix the job by writing per-day partitions with overwrite (dynamic mode) instead of append.
  • Add a check: today's row count within a range and no duplicate keys, so it fails before the dashboard.
MapReduce · designFresher

"How would you remove duplicates from 100 files where a copy can be in another file?"

Follow-up: "And which copy do you keep?"

The interviewer is checking: key choice and determinism.

Show a strong answer
  • Key by the business key (order_id); the shuffle groups all copies in one reducer whatever file they came from.
  • Keep a deterministic copy: earliest arrival (file day), so re-runs pick the same one and lateness is measured.
  • Count extra copies in a counter; in Spark the same is a window with row_number() over order_id ordered by file day.
Reconciliation · financeExperienced

"Finance says UPI collections don't match the bank. Investigate."

The difference is a few thousand rupees in a month.

The interviewer is checking: structured reconciliation.

Show a strong answer
  • Left join POS UPI orders to gateway records on order_id; classify: confirmed, failed-then-paid, refunded, unconfirmed.
  • Group the unconfirmed by day, shop and hour: one cluster (ours: 201 orders, Nerul, 22 Sept 13:00) means an outage or a file missing, not random loss.
  • Send the exact list to the gateway; add a daily gold table and alert so it is caught the next day, not at month-end.
Engineering · qualityExperienced

"How do you test a data pipeline?"

The team has unit tests for code but numbers still go wrong.

The interviewer is checking: testing data, not only code.

Show a strong answer
  • Unit-test the logic on tiny files with known edge cases (duplicate in the next file, broken line, unknown item); run mapper | sort | reducer locally.
  • On every run, check conservation (in = out + rejected), uniqueness of keys, and totals against an independent source.
  • Gate publication on those checks and keep the quarantine so failures are explainable.
