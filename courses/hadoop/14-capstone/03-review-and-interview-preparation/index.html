2 Definition

A project review, and a project story

Formal definition (write this in exams)

A production-readiness review examines a data pipeline before it is relied on, across five areas: correctness (acceptance tests, reconciliation, conservation of records), performance and scalability (job time, task counts, behaviour at expected growth), reliability (behaviour under task, node and disk failures; idempotent re-runs), cost and capacity (storage, replication, cluster size) and operability (counters, logs, alerts, runbooks). Every change made during the review must be regression-tested: the new version must produce results proven equal to the old one. In interviews the same project is presented with the STAR method: Situation, Task, Action and Result, with measured numbers.

In simple words

Before trusting a pipeline, check that it is right, fast enough, survives failures, does not waste money and can be run by someone else. Every improvement must give exactly the same answers. Then tell the story: what was the problem, what did you do, what did it achieve.

The review at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner What a review asks

  • Is it right? 10/10 checks, and the numbers add up.
  • Is it fast enough? Today yes; at 40 canteens the 104 tiny files become 1,040 a month.
  • Does it survive failures? We broke a worker on purpose to find out.
  • Can you explain it? In two minutes, with numbers, to an interviewer.

Intermediate Why the two speed-ups went wrong

  • Keys in Streaming: with plain TextInputFormat the keys (byte offsets) are discarded and only the lines are piped to the mapper. With CombineTextInputFormat our mapper received key TAB line until we set stream.map.input.ignoreKey=true. Our mapper split on commas, so the "order_id" was offset TAB order_id and its key was the offset.
  • File name per task: Streaming copies the job configuration into the environment (dots become underscores) when it starts the Python process. With combined splits one Python process reads many files, so mapreduce_map_input_file holds one name for all of them. 44,546 extra orders looked late.
  • The real fix: stop depending on file names. Put the lineage (file day) into the data during compaction, then any engine and any split size gives the same answer.

Advanced Reliability on a tiny cluster

  • Task failures are routine: YARN re-ran the killed attempts on other nodes and the counters of failed attempts were discarded, so totals stayed exact.
  • With 3 DataNodes and replication 3, losing one leaves no spare node for an open write pipeline. The client's default policy tries to replace the bad node and gives up: "Failed to replace a bad datanode on the existing pipeline due to no more good datanodes being available to try". The AM's job-history file died; the client could not fetch the final status.
  • hdfs-default.xml notes that on extremely small clusters (3 nodes or less) administrators may want policy NEVER: keep writing to the remaining nodes. On normal clusters keep DEFAULT.
  • Lesson for operators: the client's exit code is not the job's result. Check yarn application -status (FINISHED / SUCCEEDED) and the output.

Exam tip: When asked "how do you know an optimisation is safe?", answer: run old and new on the same input and compare every counter and a checksum of the sorted output; ours matched exactly (md5 e4cb8704…), while two faster versions failed the comparison.

Animated example: a fast job that was wrong

CombineTextInputFormat meets Python 6 steps
Animated example
  1. The baseline is correct but slow: each tiny file gets a map task, and each task spends most of its 20 seconds starting a JVM and Python.
  2. With CombineTextInputFormat, Streaming sends "byte offset TAB line" to Python. The mapper keeps everything before the first comma, so the order_id it prints starts with the offset; the key becomes a number. (Offset shown is illustrative.)
  3. Unrelated orders now share keys and are "deduplicated": the counters are obviously wrong.
  4. Telling Streaming to ignore the key fixes the lines, but the file name comes from an environment variable set when Python starts, so one name covers many files.
  5. Everything matches truth except LATE: 46,646 instead of 2,100.
  6. The fix: compaction writes the file day into every line; the job reads 4 files, runs 4 maps and produces byte-identical output.

Keep a "golden" output from a trusted run (counters + checksum of sorted output). Every change, even a config change, must reproduce it before it ships.

Our first drill command was pkill -9 -f YarnChild inside bash -c '…'. The shell's own command line contains "YarnChild", so pkill killed the shell before it could stop the DataNode. Writing the pattern as [Y]arnChild matches the processes but not the command that contains it.

5 See it happen

The failure drill: the log and the cluster

Our second drill (with the fix), second by second. Left: the client's terminal. Right: what YARN and HDFS do on the three workers.

Killing worker2 mid-job 6 steps
What you see
  1. The clean job starts: 104 map tasks queued.
  2. About 70 seconds in, we break worker2.
  3. Four running attempts on worker2 die: "Killed by external signal".
  4. The job keeps going; progress continues from where it was.
  5. It completes successfully: 108 map attempts for 104 maps, and every counter is exactly right.
  6. The output is byte-identical to the baseline. Recovery cost about 70 seconds.
Behind the screen
  1. Map tasks run on all three workers; every input block has a replica on each worker.
  2. Meanwhile the ApplicationMaster writes the job-history file through a pipeline of the three DataNodes.
  3. We kill worker2's task JVMs and its DataNode. The AM reschedules the failed attempts; readers use the other replicas.
  4. The history file's pipeline lost a node. With only 3 DataNodes there is no replacement; policy NEVER lets the write continue on two.
  5. Only successful attempts contribute counters, so the totals are exact.
  6. In the first drill, without the setting, the history file failed: the client reported failure although YARN and the data said success. (Container squares are symbolic.)
6 Real-world use

Reviews and interviews at work

1. Production-readiness reviews

Many data teams require a checklist before a pipeline is scheduled in production: tests and reconciliation, run time at expected volume, failure behaviour, alerts, a runbook and an owner, much like our table.

New pipeline→review + evidence→Scheduled in prod

2. Platform upgrades

Before upgrading Hadoop, Spark or a library, teams re-run key jobs on a fixed input and compare outputs and counters with a golden run, the same comparison that caught our combine bugs.

Upgrade→compare with golden run→Approve

3. Failure drills ("game days")

Operations teams switch off nodes, disks or whole racks in a planned window to prove that jobs recover and alerts fire, and they often find surprises like our job-history problem.

Planned failure→watch recovery→Fix + runbook

4. Product-company interviews

Interviews often include a project deep dive: one project, many follow-ups ("why that key?", "what if 10×?", "what broke?"). One project known to the last number beats five listed on a CV.

Your project→STAR + numbers + bug story→Design follow-ups

5. Service-company and campus interviews

Expect concept questions across the stack (HDFS, MapReduce, YARN, Hive, Spark) plus "explain your project". The question bank in this lesson maps each common question to the lesson that answers it.

7 Run the code

Why one file name for many files breaks "late"

A simulation of our second combine attempt. One Python process reads lines from three files but is told only one file name at start-up, as Streaming does with its environment.

files = {"orders_KHR_2026-09-12.csv": ["KHR-0912-1,2026-09-12", "KHR-0912-2,2026-09-12"],
         "orders_KHR_2026-09-14.csv": ["KHR-0912-9,2026-09-12", "KHR-0914-1,2026-09-14"],
         "orders_KHR_2026-09-15.csv": ["KHR-0915-1,2026-09-15"]}

def late_count(lines_with_day):
    return sum(1 for fday, line in lines_with_day if fday > line.split(",")[1])

# baseline: one process per file, each knows its own file name
per_file = [(name[-14:-4], line) for name, lines in files.items() for line in lines]
# combined split: one process, one file name for the whole split (here: the last file)
told = list(files)[-1][-14:-4]
combined = [(told, line) for lines in files.values() for line in lines]
# fix: the file day travels inside every line (compaction)
tagged = [(name[-14:-4], line) for name, lines in files.items() for line in lines]

print("one file per map :", late_count(per_file))
print("combined, env var:", late_count(combined))
print("lineage in data  :", late_count(tagged))
one file per map : 1 combined, env var: 4 lineage in data : 1
  • told = list(files)[-1][-14:-4]Like mapreduce_map_input_file: fixed when the process starts, wrong for the other files in the split.
  • tagged = [(name[-14:-4], line) for name, lines in files.items() for line in lines]compact.py does this with input_file_name(): each line carries its own file day.

Check yourself

Quick revision

Lesson 14.3 in one screen

  • Review areas: correctness, idempotency, performance, scalability, reliability, cost, operability, security.
  • Baseline: 104 maps × ~19.7 s, 4 min 39 s; the work per map was tiny: start-up dominated.
  • Combine #1: 3 maps, 38 s, wrong (offset keys). Combine #2 (ignoreKey): 44 s, LATE 46,646 (env var once per task).
  • Fix: compact.py tags each line with its file day → 4 maps, 53 s, identical counters and md5 e4cb8704…
  • Drill: killed tasks + DataNode: attempts re-ran, output identical; 3-node history-file failure fixed with policy NEVER.
  • Sizing: ~6 GB raw a year at 40 canteens; files, not bytes, are the scaling problem.
  • Interview: STAR with numbers, one hard bug, one failure story, one design trade-off.

Interview and viva questions

Walk me through your capstone project.

Situation: four college canteens sent 130 daily files a month (POS orders, UPI payments, a menu) and could not trust their totals. Task: daily revenue per canteen, item mix, peak hours and UPI reconciliation, proven correct. Action: landed raw files in HDFS, wrote a MapReduce Streaming job keyed on order_id to deduplicate and apply quality rules with counters, used Spark to write Parquet silver partitioned by day and five gold tables, and wrote ten acceptance checks against a trusted total. Result: 10/10 checks, ₹43,710 of undercharging and a ₹6,854 UPI gap found, and the clean job cut from 4 min 39 s to 53 s with byte-identical output.

What was the hardest problem?

Making the clean job faster. Packing small files with CombineTextInputFormat made it 7× faster but wrong: the Python mapper received byte-offset keys, and after fixing that the input-file environment variable named only one file per combined split, so 46,646 orders looked late instead of 2,100. Counters and acceptance checks caught both; the fix was compacting the files and writing each line's source day into the data.

How does Hadoop handle a node failure during a job?

The ApplicationMaster re-runs failed or lost task attempts on other nodes, and HDFS readers switch to other replicas. Counters from failed attempts are discarded, so results stay exact. In our drill 4 attempts were killed, 108 launched for 104 maps, and the output was byte-identical. On a 3-DataNode cluster open writes can fail when one DataNode dies unless the replace-datanode-on-failure policy is NEVER.

How do you prove that an optimisation did not change the results?

Run old and new versions on the same input, compare every counter and a checksum of the sorted output, and run the acceptance checks. Keep that golden output for future changes.

Why did you use both MapReduce and Spark?

MapReduce made deduplication explicit as a shuffle on order_id and shows the classic Hadoop job model many companies still run; Spark was better for typed columns, Parquet, joins and several aggregations in one job. In a new project I would likely do it all in Spark (dropDuplicates or a window) with the same rules and checks.

What would you change for production?

Schedule it in Airflow with retries and an SLA; compact daily; move silver to a table format such as Iceberg for safe corrections; add Kerberos and Ranger for access to student IDs; alert on check failures and on the UPI gap table; write a runbook that includes checking the YARN final status, not only the client exit code.

Plan a failure test matrix

List failure drills for the pipeline with what to observe, and print them as a checklist.

Input
components
Expected output
1. kill a map task JVM    -> attempt re-runs, counters exact

for i, (what, observe) in enumerate(drills, 1):
    print(f"{i}. {what:<22} -> {observe}")

Operations · reliabilityExperienced

"Your scheduler marked the job failed, but the data looks complete. What do you do?"

The client exited with an error at the very end.

The interviewer is checking: not trusting a single signal.

Show a strong answer
  • Check the application's final state in YARN (in our drill: FINISHED / SUCCEEDED), the output's _SUCCESS marker, counters and checks.
  • Read the AM log: ours showed the job-history file lost its write pipeline when a DataNode died on a 3-node cluster.
  • Decide from the checks (the job is idempotent, so a re-run is safe anyway); fix the root cause and add it to the runbook.
