The Reducer

The reducer is where the answer for each key is computed and written. This lesson shows exactly how it is called, how keys are dealt to reducers, what the number of reducers does to your output, and the one Java habit (copying values) that every Hadoop programmer learns the hard way, all with real runs on the Module 8 cluster.

1 The story

Three desks, one of them empty

Riya's item revenue job works, but it has one reducer doing all the adding. “Let's use three,” says Kabir, and reruns it with -D mapreduce.job.reduces=3. Three output files appear. The first one is empty. The second holds four items, the third holds two. Then Riya writes a small reducer that lists the first three order IDs of each item, and every item shows the same ID three times. Two surprises, both caused by how a reducer really works.

Riya

Sir, three reducers and one of them did nothing? Isn't Hadoop supposed to divide the work equally?

Arjun Sir

Hadoop divides keys, not work. Each key goes to reducer hash(key) % 3. With only six keys, the dice fell four, two and zero. With crores of keys it evens out; with a few keys, or one huge key, it doesn't.

Kabir

And the repeated IDs? I saved the values in a list, just like in any Java program.

Arjun Sir

The reducer gives you an Iterable that reads the values off a sorted stream, and it puts each one into the same Text object. You saved three references to one object, which ended up holding the last value. Copy what you keep. Today: how the reducer is called, how many to run, where its output goes, and these two traps.

2 Definition

The Reducer

Formal definition (write this in exams)

In Hadoop MapReduce, a Reducer is the user class, extending org.apache.hadoop.mapreduce.Reducer<KEYIN, VALUEIN, KEYOUT, VALUEOUT>, whose reduce(key, Iterable<VALUEIN> values, Context context) method is called once for every distinct intermediate key in its partition, in sorted key order, with all the values for that key. A job has mapreduce.job.reduces reduce tasks (default 1); the Partitioner (by default HashPartitioner, (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks) decides which reduce task receives each key. Each reduce task runs setup() once, reduce() per key and cleanup() once, and writes its output through the job's OutputFormat to one file, part-r-NNNNN, which the output committer moves into the output directory when the task succeeds. The values are delivered as a single-pass iterator that reuses one value object, and their order within a key is not defined.

In simple words

A reducer gets one key at a time, with every value for that key, and writes the answer for that key. The number of reducers decides how many output files you get, and the hash of each key decides which reducer it lands on.

The Reducer at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Counting desks

  • On counting day each desk is responsible for some candidates. A rule fixed in advance says which desk gets which candidate, so every slip for a candidate reaches the same desk.
  • A desk takes one candidate's pile at a time, adds it up, writes one line, and moves to the next candidate in alphabetical order.
  • With few candidates, some desks may get none. That desk still opens, and still files an empty result sheet.

Intermediate How reduce() is called

  • setup(context) runs once, then reduce(key, values, context) once per key, in sorted key order, then cleanup(context) once.
  • values is an Iterable over a merged, sorted stream on disk and in memory. You can loop over it once; there is no going back.
  • Each step of the loop overwrites the same Text or IntWritable object. Use the value immediately, or copy it (new Text(v), v.get()) if you keep it.
  • The order of values inside one key is not guaranteed: our correct run listed chai's IDs as 104221, 150350, 113456. If you need them ordered, that is a secondary sort (Lesson 9.7).

Advanced How many reducers, and what they write

  • Default is 1. Set it with job.setNumReduceTasks(n) or -D mapreduce.job.reduces=n. Hadoop's own guideline: about 0.95 or 1.75 × (nodes × containers per node): 0.95 finishes in one wave, 1.75 lets fast nodes take a second wave for better balance.
  • Too few: each reducer is huge and slow. Too many: many tiny output files (Lesson 7.5) and task overhead.
  • Partitioning is by key, so one hot key (say 60% of all orders are chai) goes to one reducer no matter how many you add. Fixes: combiners (9.1), custom partitioners (9.2), salting keys.
  • Each reduce task writes to _temporary/…/attempt_…; when it succeeds the FileOutputCommitter (algorithm version 2 in our logs) moves the file into the output folder. After all tasks, _SUCCESS is written. Output goes to HDFS with normal replication (3 here).
  • With 0 reducers there is no shuffle and no sort: map output is written straight to HDFS as part-m-NNNNN.

Exam tip: For “What is the role of the Reducer?” write: receives each key with all its values (after shuffle and sort), called once per key in sorted order, output written to HDFS as part-r-NNNNN, number set by setNumReduceTasks (default 1), keys assigned by the Partitioner (hash % n). Mention that 0 reducers gives a map-only job.

  1. The reducer we are running

    public static class SumReducer extends Reducer<Text, IntWritable, Text, Text> {
  protected void reduce(Text item, Iterable<IntWritable> amounts, Context ctx) … {
    long orders = 0, revenue = 0;
    for (IntWritable a : amounts) { orders++; revenue += a.get(); }
    ctx.write(item, new Text(orders + "\t" + revenue));
  }
}
    The four type parameters: input key Text, input value IntWritable (they must match the map output), output key Text, output value Text. a.get() copies the number out at once, so object reuse does no harm here.

    return h

  6. The object-reuse trap

    for (Text id : ids) {
  first3.add(copy ? new Text(id) : id);   // without a copy: the SAME object 3 times

}
    -- copy (correct) -- no copy (-D sample.copy=false) chai [104221, 150350, 113456] chai [113456, 113456, 113456] dosa [78778, 213441, 200658] dosa [200658, 200658, 200658] idli [101007, 50991, 101001] idli [101001, 101001, 101001]
    The iterator reuses one Text; after three steps it holds the third ID, and all three list entries point to it. Notice too that the correct IDs are not in order: values arrive in no defined order within a key.

Never collect all values of a key into a list unless you know the key is small. A hot key with crores of values will exhaust the reducer's heap (ours had 300 MB). Aggregate as you iterate, or keep only what you need.

5 See it happen

Three reducers and one reused object

Six steps: keys are partitioned, each reducer is called per key, files are committed, then the object-reuse bug in slow motion.

Inside the reduce phase 6 steps
What you see
  1. The job is submitted with three reduce tasks.
  2. All three reducers finish; together they saw 6 key groups.
  3. Three output files: one is empty.
  4. File 1 holds four items, sorted by key.
  5. The sampling reducer without copies prints the same ID three times per item.
  6. With a copy of each value, the three IDs are different (and in no particular order).
Behind the screen
  1. Every map output pair gets a partition number from the hash of its key.
  2. Each reducer fetches only its own partition from every map: reducer 0's partition is empty.
  3. Each reducer calls reduce() once per key, in sorted key order.
  4. Each task writes one file under _temporary; the committer moves it into /out/red_3 and _SUCCESS is written.
  5. The iterator fills ONE Text object again and again; a list of references sees only the last value.
  6. Copying each value keeps three different objects.
6 Real-world use

Reducers at work

1. Sizing reducers for nightly aggregates

Teams set the reducer count from cluster capacity and output size, aiming for output files of a few hundred MB each, so the result is neither one giant file nor thousands of tiny ones.

Output size→reduces ≈ size / 256 MB→Healthy files

2. Hunting skewed reducers

When a job sits at “reduce 99%” for an hour, one reducer usually has a hot key (a default city, a null customer ID). Engineers find it from the reducer counters and fix it with combiners, salting or a custom partitioner.

One slow reducer→Reduce input records per task→Find the hot key

3. Map-only ETL

Cleaning, filtering and format conversion jobs set reducers to 0 and skip the whole shuffle, often halving the run time. DistCp is a map-only job too.

Raw files→map-only job→part-m-* files

4. Code reviews catch object reuse

“Copy Writables you keep” is a standard review check in Hadoop teams; the same reuse appears in Hive UDFs and in Spark when reading Hadoop input formats.

list.add(value)→review→list.add(new Text(value))

Simplified; organisations differ in tools and policies.

7 Run the code

Partition, group and reduce like Hadoop

This model deals keys to reducers with Hadoop's real Text hash, groups values per key, and calls a reduce function once per key in sorted order. Its partitions match the files our cluster wrote.

pairs = [("samosa", 18), ("vada pav", 20), ("poha", 25), ("samosa", 18), ("chai", 15),
         ("idli", 30), ("dosa", 45), ("chai", 15), ("poha", 25), ("idli", 30)]

def text_hash(s):                         # Hadoop's Text.hashCode()
    h = 1
    for b in s.encode():
        h = (31 * h + b) & 0xffffffff
    return h

def partition(key, n):                    # HashPartitioner
    return (text_hash(key) & 0x7fffffff) % n

def reduce_fn(key, values):
    return f"{key}\t{len(values)}\t{sum(values)}"

R = 3
parts = [{} for _ in range(R)]
for k, v in pairs:
    parts[partition(k, R)].setdefault(k, []).append(v)

for r in range(R):
    lines = [reduce_fn(k, parts[r][k]) for k in sorted(parts[r])]
    print(f"part-r-{r:05d}:", lines if lines else "(empty)")
part-r-00000: (empty) part-r-00001: ['chai\t2\t30', 'dosa\t1\t45', 'samosa\t2\t36', 'vada pav\t1\t20'] part-r-00002: ['idli\t2\t60', 'poha\t2\t50']

  • lines = [reduce_fn(k, parts[r][k]) for k in sorted(parts[r])]Each reducer handles its keys in sorted order, one reduce() call per key.
  • print(f"part-r-{r:05d}:", lines if lines else "(empty)")Reducer 0 gets no keys but still writes a file: our part-r-00000 was 0 bytes.

First three order IDs per item

// SampleOrders.java: for each item, list the first 3 order ids the reducer sees.
// Run with -D sample.copy=false to see the famous "object reuse" bug.
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class SampleOrders {
  public static class M extends Mapper<LongWritable, Text, Text, Text> {
    private final Text item = new Text(), id = new Text();
    @Override
    protected void map(LongWritable k, Text line, Context ctx) throws IOException, InterruptedException {
      String[] f = line.toString().split(",");
      if (f.length != 3 || f[0].equals("order_id")) return;
      item.set(f[1]); id.set(f[0]);
      ctx.write(item, id);
    }
  }

  public static class R extends Reducer<Text, Text, Text, Text> {
    @Override
    protected void reduce(Text item, Iterable<Text> ids, Context ctx) throws IOException, InterruptedException {
      boolean copy = ctx.getConfiguration().getBoolean("sample.copy", true);
      List<Text> first3 = new ArrayList<>();
      for (Text id : ids) {
        first3.add(copy ? new Text(id) : id);       // without a copy we keep the SAME object 3 times
        if (first3.size() == 3) break;
      }
      ctx.write(item, new Text(first3.toString()));
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "sample orders");
    job.setJarByClass(SampleOrders.class);
    job.setMapperClass(M.class);
    job.setReducerClass(R.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

How a reducer walks through its keys

A reducer's input is one sorted stream of (key, value) pairs. Grouping means: keep reading while the key stays the same, then call reduce for that key.

Example 1BeginnerSizing · count

How many reducers for this cluster?

Problem statement

A cluster has 20 workers, each able to run 6 reduce containers at once. Using Hadoop's guideline of 0.95 or 1.75 × total containers, what are the two candidate reducer counts?

Input

Expected output
one wave : 114

Approach

  2. 0.95 × total: all reducers start in one wave.
  3. 1.75 × total: two waves, better load balancing.

A job with 50 reducers shows 49 reducers finishing in 2 minutes and one running for 60. The reducer counters show “Reduce input records” of about 2 lakh for most tasks and 9 crore for the slow one. What is the cause, and roughly how much faster could the job be if the load were spread evenly?

Interview and viva questions

What does the Reducer do in Hadoop MapReduce?

After the shuffle and sort, each reduce task receives a partition of the intermediate keys. For each key, in sorted order, Hadoop calls reduce(key, values, context) with all the values for that key. The reducer typically aggregates them and writes output records, which go to one file per reduce task (part-r-NNNNN) in HDFS.

How do I set the number of reducers?

In the driver call job.setNumReduceTasks(n), or pass -D mapreduce.job.reduces=n on the command line when the driver uses GenericOptionsParser or ToolRunner. The default is 1. The Hadoop documentation suggests 0.95 or 1.75 times (nodes × maximum containers per node); in practice also aim for output files of reasonable size.

Why are some reducer output files empty?

Keys are assigned to reducers by the partitioner, by default (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks. If no key hashes to a given partition, that reducer receives nothing but still writes its (empty) part file. In our lab, 6 keys and 10 reducers left 4 files empty.

Why do I get the same value repeated when I store reducer values in a list?

Hadoop reuses a single Writable instance for the values of the Iterable and refills it at every step. Storing the object stores a reference to that one instance, which ends up holding the last value. Store a copy instead, for example new Text(value) or the primitive from value.get().

Can a MapReduce job have zero reducers?

Yes. With setNumReduceTasks(0) the job is map-only: there is no shuffle or sort, and each map task writes its output directly to the output directory as part-m-NNNNN. This is used for filtering, cleaning and conversion jobs.

P4Medium

Single pass

Write a reducer that returns count, sum and max of a key's values in ONE loop over an iterator.

Input
iterator of amounts
Expected output
('dosa', 4, 175, 45)
Show solution and explanation 
def reduce_fn(key, values):
    n = s = 0
    m = None
    for v in values:
        n += 1; s += v
        m = v if m is None or v > m else m
    return key, n, s, m
print(reduce_fn("dosa", iter([45, 45, 40, 45])))
('dosa', 4, 175, 45)

How it works: One pass is all you get; keep running totals instead of a list.

P8Advanced

Salting a hot key

chai has 9 lakh records and the other keys 50,000 each. Salt chai into 4 sub-keys (chai#0 … chai#3) and show the load per reducer drops, then combine the salted totals.

Input
record counts per key
Expected output
largest group before: 900000 after: 225000
chai recombined: 900000
Show solution and explanation 
counts = {"chai": 900_000, "dosa": 50_000, "idli": 50_000, "poha": 50_000}
salted = {}
for k, c in counts.items():
    parts = 4 if k == "chai" else 1
    for i in range(parts):
        key = f"{k}#{i}" if parts > 1 else k
        salted[key] = c // parts
print("largest group before:", max(counts.values()), "after:", max(salted.values()))
total_chai = sum(v for k, v in salted.items() if k.startswith("chai#"))
print("chai recombined:", total_chai)

How it works: The biggest reduce group drops from 9 lakh to 2.25 lakh records; a small second step adds chai#0 … chai#3 back to 9 lakh.

Real-world scenario questions (asked in company interviews)

Reducer questions test whether you have actually written MapReduce code: partitioning, reducer count and object reuse come up again and again.

Concepts · partitioningFresher

“How does Hadoop decide which reducer gets a key?”

A standard follow-up after explaining word count.

The interviewer is checking: the Partitioner and its guarantee.

Show a strong answer
  • The Partitioner; by default HashPartitioner: (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks.
  • Guarantee: all values of one key go to the same reducer, so reduce sees the complete group.
  • Side effect: load depends on key distribution; few keys or a hot key give uneven reducers (we saw files of 0, 79 and 38 bytes).
Coding · bugExperienced

A reducer collects values into a list and all entries are identical

Code review of a reducer that builds a list of the last 10 transactions per customer.

The interviewer is checking: knowledge of Writable reuse.

Show a strong answer
  • Hadoop reuses one key and one value object while iterating; the list stores references to the same instance.
  • Fix: add a copy (new Text(v), WritableUtils.clone, or extract primitives).
  • Also check memory: collecting all values of a hot key can exhaust the heap; keep only what is needed.
Performance · skewExperienced

The job is stuck at “reduce 99%” for an hour

All but one reducer finished quickly.

The interviewer is checking: skew diagnosis and fixes.

Show a strong answer
  • Compare “Reduce input records” and shuffle bytes per reduce task; one task with far more input means a hot key.
  • Find the key (sample the map output or count keys in a quick job); often null or a default value.
  • Fix: filter or handle the junk key, use a combiner, salt the hot key and merge in a second step, or a custom partitioner. More reducers alone won't help.
Design · outputFresher

“I need one sorted output file. Do I set 1 reducer?”

An analyst wants a single report file sorted by customer.

The interviewer is checking: trade-offs between one reducer and total order.

Show a strong answer
  • 1 reducer works for small outputs, but all data passes through one task: slow for big outputs.
  • For large data use TotalOrderPartitioner (sampled key ranges), so files 0 … n−1 are in order and can be concatenated.
  • Or keep many reducers and sort/merge downstream (getmerge only concatenates, it does not sort).
