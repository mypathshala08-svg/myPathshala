Thinking in MapReduce

MapReduce asks you for two small functions and does the rest: it runs your map on every block where it is stored, groups the results by key, and runs your reduce once per key. This lesson builds that way of thinking and runs a real job on a three-worker cluster with HDFS and YARN, reading every number Hadoop reports.

2 Definition

MapReduce

Formal definition (write this in exams)

MapReduce is a programming model and an execution framework for processing large data sets in parallel on a cluster. The programmer supplies two functions: a map function, applied independently to every input record, that turns a key-value pair (k1, v1) into zero or more intermediate pairs list(k2, v2); and a reduce function that receives each intermediate key with all its values, (k2, list(v2)), and produces the output list(k3, v3). Between them the framework performs the shuffle and sort: it partitions the intermediate pairs by key, transfers them to the reducers and sorts them so all values of a key arrive together. The framework also splits the input, schedules map tasks close to their data (data locality), re-executes failed tasks and writes the output to a distributed file system. In Hadoop 2 and later, MapReduce jobs run on YARN, with one MRAppMaster per job.

In simple words

You describe what to do with one record (map) and how to combine everything that shares a key (reduce). Hadoop runs the map on every block in parallel, groups the results by key, and runs the reduce once per key.

Words you'll meet in this lesson

JobOne complete MapReduce program run: input, map, shuffle, reduce, output.
TaskA unit of work: one map task per input split, one reduce task per partition.
Task attemptOne execution of a task. A task can have several (retries, speculation).
Key-value pairThe only data shape MapReduce knows, e.g. ("chai", 15).
Intermediate dataMap output: written to the worker's local disk, not HDFS.
ShuffleMoving and sorting map output so each key reaches one reducer.
MRAppMasterThe per-job manager on YARN that asks for containers and tracks tasks.
Speculative executionRunning a backup attempt of a slow task; the first to finish wins.

MapReduce at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Counting day

  • Every counting table (a worker) counts only the machines on its own table: that is map. Nobody carries all votes to one hall.
  • Partial totals are sorted by candidate and sent to the right desk: that is the shuffle.
  • Each desk adds the partial totals of one candidate: that is reduce. Ten tables or a thousand, the method doesn't change.
  • If one table's counter falls ill, another counter recounts that table only. Hadoop does the same with a failed task.

Intermediate What you write, what Hadoop does

  • You write: a Mapper (map(key, value, context)), a Reducer (reduce(key, values, context)) and a small driver that sets input, output and classes.
  • Hadoop does: splits the input (Lesson 8.2), starts one map task per split on a node that holds the block, sorts and spills map output, copies it to reducers, merges and groups by key (Lesson 8.4), writes part-r-NNNNN files and _SUCCESS.
  • Map tasks never talk to each other, and neither do reduce tasks. That independence is what lets Hadoop run them anywhere and rerun any one of them.
  • For our job: map turns “1002,vada pav,20” into (“vada pav”, 20); reduce turns (“vada pav”, [20, 20, …]) into vada pav 49986 999720.

Advanced Thinking in keys

  • The design question is always: what is the key? Everything that must be combined has to share a key, because only values with the same key ever meet.
  • Map output is the expensive part: it is sorted, written to local disk, and sent over the network. Emit as little as possible (filter early, use compact types, add a combiner in Lesson 9.1).
  • Reducers see each key once, with its values in no guaranteed order. Anything that needs order inside a key needs a secondary sort (Lesson 9.7).
  • MapReduce fits batch jobs that scan everything once. Iterative work (machine learning, graph algorithms) and interactive queries pay the disk write between steps on every pass, which is why Spark and Tez took over those jobs.

Exam tip: For “Explain MapReduce with an example”, write the two signatures map(k1, v1) → list(k2, v2) and reduce(k2, list(v2)) → list(k3, v3), name the shuffle and sort in between, and show one record passing through all three (e.g. “1002,vada pav,20” → (vada pav, 20) → vada pav 49986 999720).

3 Types and ways to use it

Common MapReduce patterns

Most MapReduce programs are one of a handful of patterns. The difference is what the map emits as key and value.

Client

Computes the splits, uploads the jar and configuration to HDFS, submits the application to the ResourceManager. Our log: “number of splits:4”.

your terminal

MRAppMaster

Runs in the first container. Requests one container per task, preferring nodes that hold each split, and tracks progress, failures and speculation.

Map and reduce tasks

Each runs in its own container (a YarnChild JVM) on a NodeManager. Our lab: map containers of 384 MB.

many per job

JobHistory Server

after the job

Big Data Fundamentals Lesson 3.1 and Hadoop Lesson 3.2 showed the life of a job from far away. This module opens it up, one stage per lesson.

The same model lives on in newer tools. A Hive GROUP BY or a Spark reduceByKey still does map, shuffle by key, reduce; they just keep more in memory and chain steps without writing to HDFS in between.

4 Step by step

Our first MapReduce job, on a real cluster

This module uses a new lab cluster with YARN: a NameNode, a ResourceManager, a JobHistory Server and three workers, each running a DataNode and a NodeManager, so map tasks can run where their blocks are. The setup is in “Run it on your PC”.

  1. Write the map and the reduce

    // map: one CSV line in, one (item, amount) pair out
String[] f = line.toString().split(",");
if (f.length != 3 || f[0].equals("order_id")) return;
item.set(f[1]);  amount.set(Integer.parseInt(f[2]));
ctx.write(item, amount);

// reduce: one item and ALL its amounts in, one line out
for (IntWritable a : amounts) { orders++; revenue += a.get(); }
ctx.write(item, new Text(orders + "\t" + revenue));
    Neither function knows how big the file is or how many machines exist. That is the whole point: the same code runs on 4.7 MB or 4.7 TB.

    Four blocks, four map tasks running at the same time on three workers, each next to its block. Map 0 lagged, so the MRAppMaster launched a speculative copy on worker3; the original finished first and the copy was killed. Same code, no change.

  6. Be honest about speed

    4.7 MB  plain Python, one process        0.1 s
4.7 MB  MapReduce job on 3 workers       25 s
403 MB  one Java process reading HDFS    5.9 s   (Lesson 6.5)
422 MB  MapReduce job, 4 maps            68 s
    On a laptop-sized cluster, MapReduce is slower: starting containers, sorting, writing map output to disk and copying it costs tens of seconds. It wins when the data is far bigger than one machine can read in time: 10 TB at 200 MB/s is 14 hours for one machine, but under 2 minutes for 500 machines reading their own blocks in parallel.

The output folder must not exist. Hadoop refuses to start a job whose output directory is already there, so it can never overwrite results by accident. Delete it first (hdfs dfs -rm -r /out/item_revenue) or write to a new folder.

5 See it happen

One job across three workers

Six steps of the 422 MB job: submit, map where the blocks are, a speculative copy, shuffle, reduce, output.

Map, shuffle, reduce 6 steps
What you see
  1. The client splits the 422 MB file into 4 pieces and submits the job to YARN.
  2. Map progress climbs as four map tasks run at the same time.
  3. Three maps finish around 29–31 s; map 0 is slower and holds the job back.
  4. Maps are done; the reducer has fetched their output and is adding up.
  5. Done. Five map attempts were launched for four maps: one was killed.
  6. The output: one line per item, keys in sorted order.
Behind the screen
  1. The MRAppMaster asks YARN for one container per split, preferring the nodes that store each block.
  2. Each map runs next to a copy of its block: Data-local map tasks=5 in the counters.
  3. Map 0 runs slower, so a speculative backup starts on worker3. Whichever finishes first is used.
  4. The reducer copies the sorted map outputs from every worker: this is the shuffle.
  5. The reducer gets each item once with all its amounts and adds them.
  6. The reducer writes its file to HDFS and the job marks the folder with _SUCCESS.

6 Real-world use

MapReduce at work

1. Building a search index

MapReduce was created at Google to rebuild its web index: map emits (word, page) for every page, reduce builds the list of pages per word. Hadoop's first users (Nutch, Yahoo!) did the same.

Crawled pages→map: (word, page)→reduce: posting lists

2. Telecom and bank batch jobs

Nightly jobs summarise billions of call detail records or card transactions per customer: a classic summarization with the customer number as key.

Records (HDFS)→key = customer→Totals per customer

3. Log analytics

Web and app logs from thousands of servers land in HDFS; jobs count errors, users and page views per hour. Facebook and Yahoo! ran tens of thousands of such jobs a day in the 2010s.

Logs→key = (hour, page)→Dashboards

4. Under SQL engines

Hive originally compiled every SQL query into MapReduce jobs; a GROUP BY item is our job. Today Hive runs on Tez and most new work uses Spark, but the map → shuffle → reduce shape is the same.

GROUP BY→map + shuffle + reduce→Result table

Simplified; organisations differ in tools and policies.

7 Run the code

Simulate map, shuffle and reduce

This is the same job as ItemRevenue.java, written as three plain Python steps so you can see the data between them. Hadoop does the shuffle for you; here we do it with a dictionary.

lines = ["order_id,item,amount", "1001,samosa,18", "1002,vada pav,20", "1003,poha,25",
         "1004,samosa,18", "1005,chai,15", "1006,poha,25", "1007,chai,15", "1008,chai,15"]

def map_fn(line):                       # one record in, zero or more (key, value) pairs out
    f = line.split(",")
    if f[0] == "order_id":
        return []
    return [(f[1], int(f[2]))]

def reduce_fn(item, amounts):           # one key with ALL its values in
    return (item, len(amounts), sum(amounts))

mapped = [pair for line in lines for pair in map_fn(line)]
print("map output :", mapped[:4], "...")

groups = {}                             # the shuffle: group by key, then sort keys
for k, v in mapped:
    groups.setdefault(k, []).append(v)
print("shuffled   :", dict(sorted(groups.items())))

for item in sorted(groups):
    print("reduce     :", reduce_fn(item, groups[item]))
map output : [('samosa', 18), ('vada pav', 20), ('poha', 25), ('samosa', 18)] ... shuffled : {'chai': [15, 15, 15], 'poha': [25, 25], 'samosa': [18, 18], 'vada pav': [20]} reduce : ('chai', 3, 45) reduce : ('poha', 2, 50) reduce : ('samosa', 2, 36) reduce : ('vada pav', 1, 20)
  • if f[0] == "order_id":The header line produces no pair at all: that is why Map input records (300,001) was one more than Map output records (300,000).
  • groups = {} # the shuffle: group by key, then sort keysIn Hadoop this is the shuffle and sort: partition, copy across the network, merge, sort by key.
  • return (item, len(amounts), sum(amounts))The reducer sees every value of one key together, so counting and summing is trivial.

Item revenue as a MapReduce job

// ItemRevenue.java: orders per item and revenue per item, as a MapReduce job (new API).
// Input lines: order_id,item,amount      Output: item <TAB> orders <TAB> revenue
import java.io.IOException;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.IntWritable;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.Reducer;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class ItemRevenue {

  public static class OrderMapper extends Mapper<LongWritable, Text, Text, IntWritable> {
    private final Text item = new Text();
    private final IntWritable amount = new IntWritable();

    @Override
    protected void map(LongWritable offset, Text line, Context ctx) throws IOException, InterruptedException {
      String[] f = line.toString().split(",");
      if (f.length != 3 || f[0].equals("order_id")) return;     // skip header / broken lines
      item.set(f[1]);
      amount.set(Integer.parseInt(f[2]));
      ctx.write(item, amount);                                  // ("samosa", 18)
    }
  }

  public static class SumReducer extends Reducer<Text, IntWritable, Text, Text> {
    @Override
    protected void reduce(Text item, Iterable<IntWritable> amounts, Context ctx) throws IOException, InterruptedException {
      long orders = 0, revenue = 0;
      for (IntWritable a : amounts) { orders++; revenue += a.get(); }
      ctx.write(item, new Text(orders + "\t" + revenue));      // samosa  50012  900216
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();   // accepts -D key=value
    Job job = Job.getInstance(conf, "item revenue");
    job.setJarByClass(ItemRevenue.class);
    job.setMapperClass(OrderMapper.class);
    job.setReducerClass(SumReducer.class);
    job.setMapOutputKeyClass(Text.class);
    job.setMapOutputValueClass(IntWritable.class);
    job.setOutputKeyClass(Text.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

9 Quiz and revision

Check yourself

Quick revision

Lesson 8.1 in one screen

  • map(k1, v1) → list(k2, v2); shuffle and sort by key; reduce(k2, list(v2)) → list(k3, v3).
  • You write Mapper, Reducer and a driver; Hadoop splits input, schedules tasks near data, shuffles, retries and writes output.
  • One map task per input split; reducers = mapreduce.job.reduces (default 1); output files part-r-NNNNN + _SUCCESS.
  • Lab: 4.7 MB → 1 map, 25 s (Python: 0.1 s); 422 MB → 4 maps on 3 workers, all data-local, 68 s; one speculative attempt killed.
  • Map output goes to local disk, not HDFS; the output folder must not exist before the job.
  • Design question: what is the key? Only values with the same key ever meet.
  • Good fit: big batch scans and aggregations. Poor fit: iterative and interactive work (use Spark, Tez).

Interview and viva questions

What is MapReduce in Hadoop?

MapReduce is Hadoop's programming model and framework for batch processing. You write a map function that turns each input record into key-value pairs and a reduce function that combines all values of each key. The framework splits the input, runs map tasks in parallel on the nodes that store the data, shuffles and sorts the intermediate pairs by key, runs reduce tasks and writes the result to HDFS, retrying failed tasks automatically.

What are the phases of a MapReduce job?

Input splitting and reading (InputFormat and RecordReader), the map phase, the shuffle and sort (partitioning, spilling, copying, merging), the reduce phase and output writing (OutputFormat). An optional combiner can run on map output before the shuffle.

Is MapReduce still used?

Classic Java MapReduce is rarely chosen for new projects; Spark, Hive on Tez, Flink and cloud warehouses are more common. It still runs in many established Hadoop clusters (including tools like DistCp and Hadoop Archive, which are MapReduce jobs), and its model of map, shuffle by key and reduce underlies all of those newer engines, so it remains a core interview and design topic.

Why is MapReduce slow for small data?

Every job starts an ApplicationMaster and task JVMs in YARN containers, sorts and writes map output to local disk and copies it over the network. That fixed overhead is tens of seconds; in our lab a 4.7 MB file took 25 s against 0.1 s in plain Python. The model pays off when the data is too big for one machine to read in time.

What is speculative execution in MapReduce?

When a task runs noticeably slower than others of the same job, the MRAppMaster can start a duplicate attempt on another node. Whichever attempt finishes first is used and the other is killed. It protects jobs from slow nodes; it is controlled by mapreduce.map.speculative and mapreduce.reduce.speculative (both true by default).

P8Advanced

Top-N per mapper

Each map task keeps only its local top 2 items by revenue; the reducer merges them into the global top 2. Compare with the true top 2 for these two maps.

Input
2 maps, partial revenue per item
Expected output
true top 2: [('dosa', 1750), ('idli', 700)]
from local top 2s: [('dosa', 1750), ('poha', 700)]
Show solution and explanation 
m1 = {"dosa": 900, "idli": 600, "chai": 300}
m2 = {"dosa": 850, "poha": 700, "idli": 100}
total = {}
for m in (m1, m2):
    for k, v in m.items():
        total[k] = total.get(k, 0) + v
print("true top 2:", sorted(total.items(), key=lambda x: -x[1])[:2])
local = [sorted(m.items(), key=lambda x: -x[1])[:2] for m in (m1, m2)]
merged = {}
for top in local:
    for k, v in top:
        merged[k] = merged.get(k, 0) + v
print("from local top 2s:", sorted(merged.items(), key=lambda x: -x[1])[:2])
true top 2: [('dosa', 1750), ('idli', 700)] from local top 2s: [('dosa', 1750), ('poha', 700)]

How it works: Wrong answer: map 2 dropped idli's 100, so idli shows 600 instead of 700 and poha takes second place. Local top-N is only safe when each key's full total is known in one place, e.g. after a first job that sums per item; then a second step picks the top N.

Real-world scenario questions (asked in company interviews)

MapReduce basics appear in every Hadoop interview, usually as “explain with an example” and “design a job for X”.

Concepts · basicsFresher

“Explain MapReduce with word count”

The most common opening question.

The interviewer is checking: the three phases and who does what.

Show a strong answer
  • Map: for each line, emit (word, 1). Runs in parallel, one task per split, near the data.
  • Shuffle and sort (framework): all pairs with the same word go to the same reducer, sorted by key.
  • Reduce: sum the ones for each word and write (word, count) to HDFS, one part file per reducer.
Design · keysFresher

Design a job: average order value per city per month

Input: order_id, city, date, amount.

The interviewer is checking: composite keys and correct averaging.

Show a strong answer
  • Key = (city, yyyy-mm); value = amount (or (amount, 1) if a combiner will be used).
  • Reducer: sum and count, then divide once. Never average averages.
  • One output line per city-month; the number of reducers decides the number of output files.
Operations · performanceExperienced

“Our MapReduce job on 2 GB takes 3 minutes. Python on a laptop takes 20 seconds.”

A manager asks why Hadoop is “slow”.

The interviewer is checking: fixed overhead vs scale.

Show a strong answer
  • Each job pays fixed costs: AM and container start-up, JVM launch, sort and spill to disk, shuffle over the network.
  • For 2 GB that overhead dominates; for 20 TB the parallel read across hundreds of nodes dominates and wins by far.
  • Options: don't use a cluster for small data, use uber mode for tiny jobs, or move to Spark/Hive on Tez for interactive work.
Internals · failuresExperienced

“The job counters show Killed map tasks=1 but the job succeeded. Is something wrong?”

A junior engineer is worried after reading the counters.

The interviewer is checking: speculation vs failure.

Show a strong answer
  • Killed is not failed: with speculative execution the slower of two attempts is killed once the other succeeds.
  • Check the attempt diagnostics (“Speculation: … succeeded first!”) in the JobHistory UI or REST API.
  • Failed task attempts (non-zero exit codes) would show up as “Failed map tasks” and are retried up to 4 times by default.
