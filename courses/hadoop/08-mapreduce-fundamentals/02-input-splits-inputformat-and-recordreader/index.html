Input splits, InputFormat and RecordReader

Before a single map task runs, Hadoop has already decided how many there will be and which bytes each one reads. This lesson opens up that decision (the InputFormat and its splits) and the reader inside each map task that turns bytes into records, using a small job that reports exactly what every split saw.

The piece of code that reads a split, the RecordReader, follows one rule: finish the line you started, even if it means reading a few bytes from the next block, and skip the half line you start in, because the previous reader already took it.

2 Definition

Input splits, InputFormat and RecordReader

Formal definition (write this in exams)

An InputFormat describes how a MapReduce job reads its input. It has two responsibilities: getSplits(), run by the client at job submission, divides the input into InputSplits, logical byte ranges (for files, a FileSplit of path, start offset, length and the hosts that store the data), each processed by exactly one map task; and createRecordReader(), run inside each map task, returns a RecordReader that turns the bytes of one split into key-value records for the mapper. For FileInputFormat the split size is max(minSize, min(maxSize, blockSize)), and a final piece of up to 10% extra (the split slop, 1.1) is merged into the previous split. The default TextInputFormat uses a LineRecordReader that yields the byte offset of each line as key (LongWritable) and the line as value (Text); it completes a line that crosses the end of the split and skips the partial first line of a split that does not start at offset 0, so every line is read exactly once.

In simple words

Before the job starts, Hadoop divides the input into pieces (splits), one per map task, usually one per block. Inside each map task a reader cuts its piece into records, carefully handling lines that cross the edges.

Splits and readers at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Cutting a notebook for five friends

  • You tear a 100-page register into five bundles by page number: that's the split. You didn't read it, you just counted pages.
  • A sentence can run from page 20 onto page 21. Friend 1 reads on until the sentence ends; friend 2 ignores the half sentence at the top of page 21 and starts at the next full one: that's the RecordReader.
  • Nobody misses a sentence and nobody reads one twice.

Intermediate What the client and the task each do

  • Client, at submit time: InputFormat.getSplits() lists files, asks the NameNode for block locations and builds FileSplits. Our log: “Total input files to process : 1”, “number of splits:5”. The split list is uploaded with the job, and the MRAppMaster requests one container per split, preferring its hosts.
  • Map task: createRecordReader() opens the file, seeks to the split's start and calls map() once per record.
  • TextInputFormat records: key = byte offset of the line (LongWritable), value = the line without the newline (Text). The offsets in our SplitPeek output are exactly these keys.
  • Size: splitSize = max(minSize, min(maxSize, blockSize)). Default minSize 1 byte, maxSize unlimited, so splitSize = block size.

Advanced Edge rules that explain odd counts

  • Slop 1.1: while the remaining bytes are more than 1.1 × splitSize, cut a full split; the rest becomes the last split. 140,759,640 / 134,217,728 = 1.049, so orders_x30's two blocks gave one split, reading 6.2 MB of block 2 remotely or locally wherever the split ran.
  • maxsize smaller than a block gives more maps than blocks (more parallelism, more overhead). minsize bigger than a block gives fewer, bigger maps that span blocks and lose some locality.
  • LineRecordReader: a split not starting at 0 throws away everything up to the first newline; every reader keeps reading while the line it is about to start begins at or before its end offset. Together this assigns each line to exactly one split.
  • Non-splittable input (gzip, or isSplitable() returning false): one split per file, whatever its size. Module 10 compares codecs and splittability.
  • Splits are computed per file: 10,000 small files give at least 10,000 splits (Lesson 7.5), unless you use CombineTextInputFormat.

Exam tip: For “Difference between a block and an input split”, write: a block is the physical unit HDFS stores (128 MB, replicated); a split is the logical unit one map task processes, computed by the InputFormat, usually equal to a block but adjustable by min/max split size, and records that cross a block boundary are read whole by the RecordReader of the split where they start.

The settings that change the number of maps

Block size

Decided when the file is written (-D dfs.blocksize=…). Our 1 MB-block copy gave 5 maps.

physical

split.maxsize

mapreduce.input.fileinputformat.split.maxsize: cap below the block size for more maps. 1 MB gave the same 5 splits.

more maps

split.minsize

mapreduce.input.fileinputformat.split.minsize: raise above the block size for fewer maps. 256 MB turned 4 splits into 2.

fewer maps

Compression

A gzip file can't be entered in the middle: always 1 split per file. bzip2 and container formats can be split.

splittable?

You cannot set the number of map tasks directly in the new API: it follows the splits. To change it, change the split size or the block size. The number of reduce tasks, on the other hand, is simply mapreduce.job.reduces (Lesson 8.5).

Don't “fix” a slow job by setting split.maxsize very low. Our 4.7 MB file in five 1 MB splits started five JVMs for work one map does in seconds. Smaller splits help only when each map does heavy work per record.

Splits and the boundary line 6 steps
What you see
  1. The client lists the input and computes 5 splits before anything runs.
  2. YARN starts 5 map tasks, one per split.
  3. Map 0 starts at byte 0, so its first record is at offset 0.
  4. Map 0's last record starts 12 bytes before the end of its split.
  5. Map 1 starts 2 bytes after its split's start.
  6. Every line was read exactly once: 300,001 records in total.
Behind the screen
  1. getSplits() turns the file into byte ranges with their hosts. Nothing is read yet.
  2. Each map task creates a LineRecordReader for its own split.
  3. Map 0 starts at byte 0. Keys are byte offsets: the header at 0, the first order at 21.
  4. The line 71484,poha,25 starts inside split 0, so map 0 reads it fully, crossing into block 2.
  5. Map 1 discards the partial line before its first newline and starts with 71485.
  6. The rule: a line is read by the split in which it starts.
6 Real-world use

Splits at work

1. The single giant gzip file

A vendor sends a 40 GB .gz file daily. The job gets one map task that runs for hours while the rest of the cluster sits idle. Teams recompress to a splittable format (bzip2, or Parquet/ORC with block compression) or ask for many smaller files.

40 GB .gz→1 split→Recompress

2. NLineInputFormat for heavy rows

A file of 5,000 lines, each naming a large image or a model to score. As one 50 KB split it would be one map; NLineInputFormat with N = 50 gives 100 maps working in parallel.

5,000 lines→N = 50→100 maps

3. Combining small files

Daily folders with thousands of small log files are read with CombineTextInputFormat and a max split size of 256 MB, so a job runs a few dozen maps instead of thousands.

8,000 files→CombineTextInputFormat→~40 maps

4. Tuning map count for CPU-heavy jobs

A parsing job spends 90% of its time on CPU. Lowering split.maxsize to 64 MB doubles the number of maps and uses every core; for an I/O-bound job the same change only adds overhead.

128 MB splits→maxsize 64 MB→2× maps

Simplified; organisations differ in tools and policies.

7 Run the code

Compute splits like FileInputFormat

This is the core of FileInputFormat.getSplits() for one file: the split size formula and the 1.1 slop rule. The file sizes are the real ones from our lab, and the printed counts match the job logs.

MB = 1024 * 1024
SLOP = 1.1

def get_splits(length, block=128 * MB, min_size=1, max_size=2**63 - 1):
    split_size = max(min_size, min(max_size, block))
    splits, start, remaining = [], 0, length
    while remaining / split_size > SLOP:
        splits.append((start, split_size))
        start += split_size
        remaining -= split_size
    if remaining:
        splits.append((start, remaining))
    return splits

print("B", get_splits(files["canteen_orders.csv"], block=1 * MB))
print("D", len(get_splits(files["orders_x30.csv"])), "split(s)")

print("F", len(get_splits(files["orders_x90.csv"], min_size=256 * MB)), "split(s) with minsize 256 MB")

Run it on your PC: peek inside every split

Use the Module 8 lab from Lesson 8.1 (lab8). SplitPeek.java is a map-only job that writes one line per split. splits_lab.sh runs it six ways. It takes about 3 minutes.

A job that reports its own split

// SplitPeek.java: a map-only job that reports, for every input split, where it starts,
// how long it is, which hosts hold it, the first and last record offsets, and the record count.
import java.io.IOException;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.input.FileSplit;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class SplitPeek {
  public static class PeekMapper extends Mapper<LongWritable, Text, NullWritable, Text> {
    private long first = -1, last = -1, records = 0;
    private String lastLine = "";

    @Override
    protected void map(LongWritable offset, Text line, Context ctx) {
      if (first < 0) first = offset.get();
      last = offset.get();
      lastLine = line.toString();
      records++;
    }

    @Override
    protected void cleanup(Context ctx) throws IOException, InterruptedException {
      FileSplit s = (FileSplit) ctx.getInputSplit();
      String host = java.net.InetAddress.getLocalHost().getHostName();
      ctx.write(NullWritable.get(), new Text(String.format(
          "split start=%d length=%d | records=%d first_offset=%d last_offset=%d last_line=%s | ran_on=%s",
          s.getStart(), s.getLength(), records, first, last, lastLine, host)));
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "split peek");
    job.setJarByClass(SplitPeek.class);
    job.setMapperClass(PeekMapper.class);
    job.setNumReduceTasks(0);                     // map-only: one output file per map task
    job.setOutputKeyClass(NullWritable.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Example 3AdvancedTuning · size

Pick a split size for a 10 GB job

Problem statement

A 10 GB text file, 128 MB blocks, on a cluster with 40 free map containers. Each map has a fixed 6 s start-up and processes 50 MB/s. Compare 128 MB splits, 256 MB splits (split.minsize) and 64 MB splits (split.maxsize).

Input
10 GB · 40 containers · 6 s start · 50 MB/s
Expected output
 64 MB: 160 maps, 4 waves, ~29 s
128 MB:  80 maps, 2 waves, ~17 s
256 MB:  40 maps, 1 waves, ~11 s

Approach

  1. Maps = size / split size; waves = maps / 40.
  2. Time per map = 6 s + split / 50 MB/s.
  3. Total ≈ waves × time per map.

Lesson 8.2 in one screen

  • InputFormat: getSplits() on the client, createRecordReader() in each map task.
  • One map task per split; a split is a byte range (FileSplit: path, start, length, hosts), not a copy of data.

Interview and viva questions

What is the difference between an HDFS block and an input split?

A block is the physical unit HDFS stores and replicates (128 MB by default). An input split is a logical byte range computed by the job's InputFormat; one map task processes one split. By default a split equals a block, but split.minsize and split.maxsize change that, and the RecordReader reads records that cross block boundaries whole, so a split's records may extend slightly into the next block.

How is the number of mappers decided in Hadoop?

By the number of input splits that the InputFormat computes. For FileInputFormat it depends on the file sizes, block size, mapreduce.input.fileinputformat.split.minsize and split.maxsize, the 1.1 split slop, and whether files are splittable. You cannot set the number of map tasks directly in the new API.

How does Hadoop handle records that cross block boundaries?

The LineRecordReader of a split that does not start at byte 0 skips everything up to the first newline, because that partial line belongs to the previous split. Every reader keeps reading while the next line starts at or before the end of its split, so it finishes a line that crosses the boundary by reading a few bytes of the next block. Each line is therefore processed exactly once.

What does TextInputFormat pass to the mapper?

For each line, a LongWritable key holding the byte offset where the line starts in the file, and a Text value holding the line without its line terminator. The offset is often ignored by the mapper.

Why does my job have only one mapper for a large file?

Usually because the file is compressed with a non-splittable codec such as gzip, the InputFormat marks it as not splittable, or split.minsize is set larger than the file. A file just slightly bigger than one block (up to 10% more) also gets a single split because of the split slop.

P8Advanced

A full LineRecordReader check

Generate 1,000 order lines, cut them into 7 equal byte ranges, read each with the boundary rule, and verify that every line is read exactly once.

Input
1,000 lines · 7 splits
Expected output
1000 lines read; True
Show solution and explanation 
import random
random.seed(1)
items = ["chai", "dosa", "poha", "idli"]
data = "".join(f"{1000 + i},{random.choice(items)},{random.randint(10, 50)}\n" for i in range(1000))
size = len(data) // 7 + 1
seen = []
for start in range(0, len(data), size):
    end = start + size
    pos = 0 if start == 0 else data.index("\n", start) + 1
    while pos <= end and pos < len(data):
        nl = data.index("\n", pos)
        seen.append(data[pos:nl]); pos = nl + 1
print(len(seen), "lines read;", len(set(seen)) == 1000 and len(seen) == 1000)
1000 lines read; True

How it works: 1000 lines read exactly once, whatever the cut points. Try other split counts.

Real-world scenario questions (asked in company interviews)

Splits come up whenever an interviewer asks how many mappers a job will have, or why a job is slow.

Concepts · basicsFresher

“Block vs input split?”

A classic Hadoop interview question.

The interviewer is checking: physical vs logical.

Show a strong answer
  • Block: physical storage unit of HDFS, fixed size, replicated, cut by bytes.
  • Split: logical unit of work for one map task, computed by the InputFormat at submission; usually one block.
  • Records crossing a block edge are read whole by the split they start in; min/max split size can make splits differ from blocks.
Internals · recordsFresher

“A line is split across two blocks. Does the mapper get half a line?”

Follow-up to the first question.

The interviewer is checking: the LineRecordReader rule.

Show a strong answer
  • No. The reader of the first split reads past its end to finish the line (a remote read of a few bytes if needed).
  • The reader of the next split skips its partial first line, because it belongs to the previous split.
  • So each line is processed exactly once; only the split starting at byte 0 doesn't skip.
Performance · tuningExperienced

A job on one 50 GB file runs with a single mapper for 3 hours

The cluster is mostly idle while it runs.

The interviewer is checking: splittability diagnosis.

Show a strong answer
  • Check “number of splits” in the client log; one split for 50 GB almost always means a non-splittable codec (gzip) or a custom isSplitable() returning false.
  • Fix upstream: write splittable files (bzip2, or Parquet/ORC/Avro with block compression) or many smaller gzip files.
  • Short term: decompress once into HDFS as plain text, or repartition with a one-off job.
Tuning · map countExperienced

“How do you increase or decrease the number of mappers?”

Often asked right after “how is the number of mappers decided”.

The interviewer is checking: knowing which knob does what.

Show a strong answer
  • More maps: lower mapreduce.input.fileinputformat.split.maxsize (or write with a smaller block size).
  • Fewer maps: raise split.minsize, or use CombineTextInputFormat for many small files.
  • Mention the trade-off: more maps add start-up overhead; fewer, bigger maps lose locality and parallelism.
