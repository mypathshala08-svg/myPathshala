2 Definition

The Mapper

Formal definition (write this in exams)

In Hadoop's org.apache.hadoop.mapreduce API, a Mapper is a class extending Mapper<KEYIN, VALUEIN, KEYOUT, VALUEOUT>. For every input split the framework creates one map task, instantiates the Mapper, and calls its run() method, which calls setup(context) once, then map(key, value, context) once for every record produced by the split's RecordReader, and finally cleanup(context) once. The map method may emit zero, one or many intermediate key-value pairs with context.write(); their types must match KEYOUT and VALUEOUT and be Hadoop Writable types. The Context also gives access to the job configuration, the input split, counters and status reporting. When the number of reduce tasks is zero (a map-only job), map output is written directly to the output format without being sorted or shuffled.

In simple words

A Mapper is a small class Hadoop runs once per piece of the input. It gets one line at a time, decides what (if anything) to send on, and can count things along the way. Map tasks never share variables, so each one only knows about its own piece.

The Mapper at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A ticket checker at the gate

  • Picture a checker at a college fest gate. People come one by one (records). For each one she decides: let in, fix the name on the pass, or turn away.
  • She has a clicker for each reason she turns someone away (counters). At the end, the clickers from all gates are added up.
  • Before the first visitor she sets up her table (setup); after the last she packs up (cleanup). Each gate (map task) works on its own queue and never talks to the others.

Intermediate The class and its lifecycle

  • class CleanMapper extends Mapper<LongWritable, Text, NullWritable, Text>: in = (byte offset, line), out = (nothing, cleaned line).
  • Hadoop's built-in run() is: setup(ctx); while (ctx.nextKeyValue()) map(ctx.getCurrentKey(), ctx.getCurrentValue(), ctx); cleanup(ctx);. You override the three methods you need.
  • map() can return without writing (filter), write once (transform) or write many times (word count writes one pair per word).
  • A field in the Mapper (like our calls counter) lives for one task only. Three tasks gave three separate counts in the logs; only counters are totalled for the whole job.

Advanced Writing mappers that are fast and correct

  • Reuse output objects: create one Text as a field and set() it each time instead of new Text() per record. context.write() serializes immediately, so reuse is safe and saves garbage collection over crores of records.
  • The input value is reused by Hadoop: the same Text object holds every line. If you store it in a list, copy it (new Text(value)) or you'll keep many references to one object (Lesson 8.5 shows this bug in a reducer).
  • Skip or fail? Skip and count bad records when the data is expected to be messy. Throw an exception when bad data means something is badly wrong: a task that throws is retried (4 attempts by default) and then fails the job.
  • Expensive setup goes in setup(): reading a lookup file, compiling a regex, opening a connection. Doing it in map() repeats it 3 lakh times.
  • Map output is what gets sorted and shuffled: emit only the fields you need.

Exam tip: For “Explain the Mapper class lifecycle”, write run() = setup() once → map() once per record → cleanup() once, state that there is one Mapper instance per map task (per input split), and give one use of each: setup to load configuration, map to transform or filter, cleanup to emit totals or close resources.

Don't use a static or instance field to count across the whole job: each map task runs in its own JVM, often on another machine, so fields are never shared. Use counters for job-wide numbers, and keep counters to a few dozen names; they are held in memory by the MRAppMaster (the default limit is 120 counters).

5 See it happen

Three map tasks, one lifecycle each

Six steps of the cleaning job: setup, records flowing through map(), counters, cleanup and the final totals.

setup → map → cleanup 6 steps
What you see
  1. The client computes 3 splits, so YARN will run 3 map tasks.
  2. Each task starts by calling setup() once and logs which split it got.
  3. map() is called for every line: good lines are written, bad ones counted, “Vada Pav ” repaired.
  4. With no reducer, each task writes its own part-m file directly; nothing is sorted or spilled.
  5. After its last line, each task calls cleanup() once. This task saw 137,786 lines.
  6. Hadoop adds up the counters of all three tasks: every one of the 300,302 lines is accounted for.
Behind the screen
  1. Hadoop creates a fresh Mapper object inside each map task, one per split.
  2. Each task calls setup() exactly once. Load lookup data or read settings here.
  3. map() runs once per line. The calls field is private to its task; counters go to the MRAppMaster.
  4. Map-only: every task writes its own part-m file to HDFS, no sort and no shuffle.
  5. cleanup() runs once at the end. The three local counts differ; none of them is the job total.
  6. Only counters are totalled across tasks: 300,059 good and 243 dropped lines.
6 Real-world use

Mappers at work

1. Landing-zone cleaning

The first job in many pipelines is map-only: validate each record from source systems, standardise formats, and drop or quarantine bad rows while counters feed a data-quality dashboard.

Raw files→Map-only validation→Clean zone + counts

2. Counters as pipeline gates

The driver reads counters after waitForCompletion() and stops the pipeline when too many records are bad, instead of loading half-broken data into reports.

Job done→job.getCounters()→Continue or alert

3. Format conversion and masking

Map-only jobs convert text into compact formats and mask personal data (for example the middle digits of a phone number) before analysts can see it.

Text logs→Map: parse + mask→Avro / Parquet

4. Enrichment with a lookup table

A small reference file (store codes → city) is loaded into a HashMap in setup(), and every record is enriched in map() with no reducer. Lesson 9.6 builds on this with the distributed cache.

Records→setup: load lookup · map: add city→Enriched records

Simplified; organisations differ in tools and policies.

7 Run the code

Simulate a Mapper with setup, map, cleanup and counters

This Python class mirrors CleanOrders.CleanMapper. The run() method is what Hadoop's own Mapper.run() does: setup once, map per record, cleanup once. Counters are a dictionary here.

class CleanMapper:
    def setup(self, ctx):
        self.calls = 0
        print("setup() for split", ctx["split"])

    def map(self, key, line, ctx):
        self.calls += 1
        f = line.split(",")
        if f[0] == "order_id":
            ctx["counters"]["HEADER"] += 1; return
        if len(f) != 3:
            ctx["counters"]["WRONG_FIELDS"] += 1; return
        try:
            amount = int(f[2].strip())
        except ValueError:
            ctx["counters"]["BAD_AMOUNT"] += 1; return
        if amount <= 0:
            ctx["counters"]["BAD_AMOUNT"] += 1; return
        ctx["counters"]["GOOD"] += 1
        ctx["out"].append(f"{f[0]},{f[1].strip().lower()},{amount}")

    def cleanup(self, ctx):
        print("cleanup(): map() was called", self.calls, "times")

    def run(self, records, ctx):                 # what Hadoop's Mapper.run() does
        self.setup(ctx)
        for key, value in records:
            self.map(key, value, ctx)
        self.cleanup(ctx)

The cleaning mapper and the lab run

// CleanOrders.java: a map-only job. Keeps good orders, counts bad ones with custom counters,
// and logs the Mapper lifecycle (setup -> map ... -> cleanup) to the task log.
import java.io.IOException;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class CleanOrders {
  enum Quality { GOOD, HEADER, WRONG_FIELDS, BAD_AMOUNT }

  public static class CleanMapper extends Mapper<LongWritable, Text, NullWritable, Text> {
    private final Text out = new Text();
    private long calls = 0;

    @Override
    protected void setup(Context ctx) {
      System.err.println("setup()   once, before the first record. split = " + ctx.getInputSplit());
    }

    @Override
    protected void map(LongWritable offset, Text line, Context ctx) throws IOException, InterruptedException {
      calls++;
      String[] f = line.toString().split(",");
      if (f[0].equals("order_id")) { ctx.getCounter(Quality.HEADER).increment(1); return; }
      if (f.length != 3) { ctx.getCounter(Quality.WRONG_FIELDS).increment(1); return; }
      int amount;
      try { amount = Integer.parseInt(f[2].trim()); }
      catch (NumberFormatException e) { ctx.getCounter(Quality.BAD_AMOUNT).increment(1); return; }
      if (amount <= 0) { ctx.getCounter(Quality.BAD_AMOUNT).increment(1); return; }
      ctx.getCounter(Quality.GOOD).increment(1);
      out.set(f[0] + "," + f[1].trim().toLowerCase() + "," + amount);
      ctx.write(NullWritable.get(), out);
    }

    @Override
    protected void cleanup(Context ctx) {
      System.err.println("cleanup() once, after the last record. map() was called " + calls + " times");
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "clean orders");
    job.setJarByClass(CleanOrders.class);
    job.setMapperClass(CleanMapper.class);
    job.setNumReduceTasks(0);
    job.setOutputKeyClass(NullWritable.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

Example 3AdvancedPerformance · reuse

Why setup() and object reuse matter

Problem statement

A mapper compiles a regex and creates a new Text for every record. Compiling costs 20 µs, creating an object 0.2 µs plus garbage-collection work. For 2.7 crore records, how much time goes to work that could be done once?

Input
27,000,000 records · 20 µs + 0.2 µs per record
Expected output
in map(): 545 s of CPU; in setup(): 0.00008 s

Approach

  1. Per-record waste × records.
  2. Move the compile to setup() and reuse one Text field.

Quick revision

Lesson 8.3 in one screen

  • Mapper<KEYIN, VALUEIN, KEYOUT, VALUEOUT>; text input = (LongWritable offset, Text line).
  • run() = setup() once → map() per record → cleanup() once; one Mapper object per map task.

Interview and viva questions

What is the Mapper in Hadoop MapReduce?

The Mapper is the user class that processes input records. Hadoop runs one map task per input split; inside it, the Mapper's setup() is called once, map() once for every key-value record from the RecordReader, and cleanup() once. map() emits intermediate key-value pairs through the Context, which are then partitioned, sorted and shuffled to reducers (or written directly as output in a map-only job).

What are setup() and cleanup() used for in a Mapper?

setup() runs once per map task before any record: use it to read configuration values, load small lookup files, compile patterns or open resources. cleanup() runs once after the last record: use it to emit results aggregated inside the task (in-mapper combining) and to close resources.

What is a map-only job?

A job with the number of reduce tasks set to 0 (job.setNumReduceTasks(0)). The output of each map task is written directly by the OutputFormat as part-m-NNNNN files, skipping the sort, spill, shuffle and reduce phases. It suits filtering, cleaning, format conversion and enrichment.

How do you create custom counters in MapReduce?

Define a Java enum (enum Quality { GOOD, BAD }) and call context.getCounter(Quality.GOOD).increment(1), or use context.getCounter("group", "name"). The framework sums counters from all task attempts that succeed and shows them in the job output, the web UI and job.getCounters() in the driver.

Why does Hadoop use Writable types instead of Java types?

Writable types (Text, IntWritable, LongWritable…) serialize compactly to a byte stream with write() and readFields(), are fast to compare in their serialized form during the sort, and can be reused and refilled with set() to avoid creating objects for every record. Keys must be WritableComparable so they can be sorted.

orders = [("chai", 15), ("dosa", 45), ("chai", 15), ("poha", 25), ("dosa", 45), ("chai", 15)]

P8Advanced

Mapper with a lookup in setup()

Load a price list once in setup() and flag orders whose amount does not match the menu price, using a counter.

Input
menu + 5 orders
Expected output
{'OK': 3, 'WRONG_PRICE': 2}
Show solution and explanation 
class PriceCheck:
    def setup(self):
        self.menu = {"chai": 15, "samosa": 18, "dosa": 45}      # e.g. read from a small file
        self.counters = {"OK": 0, "WRONG_PRICE": 0}
    def map(self, line):
        oid, item, amount = line.split(",")
        key = "OK" if self.menu.get(item) == int(amount) else "WRONG_PRICE"
        self.counters[key] += 1
m = PriceCheck(); m.setup()
for line in ["1,chai,15", "2,dosa,40", "3,samosa,18", "4,chai,20", "5,dosa,45"]:
    m.map(line)
print(m.counters)
{'OK': 3, 'WRONG_PRICE': 2}

How it works: OK 3, WRONG_PRICE 2. The menu is loaded once per task, not once per line; Lesson 9.6 ships such files to every task with the distributed cache.

Real-world scenario questions (asked in company interviews)

Mapper questions test whether you have written real MapReduce code: lifecycle, types, counters and the reuse trap.

Concepts · lifecycleFresher

“What methods does a Mapper have, and when are they called?”

A standard question after “explain MapReduce”.

The interviewer is checking: setup, map, cleanup, run, and one object per task.

Show a strong answer
  • run() drives the task: setup() once, map() for every record of the split, cleanup() once.
  • One Mapper instance per map task; tasks don't share fields.
  • setup for configuration and lookups, cleanup for emitting in-task totals and closing resources.
Data quality · designFresher

The job fails with NumberFormatException after 40 minutes

One line in 3 crore has “N/A” as the amount.

The interviewer is checking: defensive mappers and counters.

Show a strong answer
  • Catch the parse error, increment a BAD_AMOUNT counter and skip (or write the line to a side output for review).
  • In the driver, read the counters and fail the pipeline only if the bad ratio exceeds an agreed threshold.
  • Throwing in map() makes the task retry 4 times on the same line and then kills the whole job.
Debugging · object reuseExperienced

A mapper that buffers lines outputs the same line again and again

The code adds each value to an ArrayList and emits the list in cleanup().

The interviewer is checking: knowing that Hadoop reuses input objects.

Show a strong answer
  • The RecordReader refills the same Text object for every record, so the list holds many references to one object, which ends up holding the last line.
  • Fix: store copies (new Text(value) or value.toString()).
  • Also check the buffer size: holding a whole split in memory can exceed the container's heap.
Performance · designExperienced

“Our cleaning job has 200 reducers that just write what they receive. Can it be faster?”

An inherited ETL job validates records and passes them through an identity reducer.

The interviewer is checking: map-only jobs.

Show a strong answer
  • If nothing needs grouping or sorting, set the reducers to 0: no spill, sort or shuffle, often several times faster.
  • Output becomes one part-m file per map task; if file count matters, tune split size or compact later.
  • Keep data-quality numbers in counters and check them in the driver.
