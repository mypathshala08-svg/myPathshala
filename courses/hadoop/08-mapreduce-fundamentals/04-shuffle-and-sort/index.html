Shuffle and sort

Between map() writing a pair and reduce() receiving it, Hadoop partitions, sorts, spills to disk, merges, copies over the network and merges again. This lesson opens that box on a real cluster: the same job with three sort-buffer sizes, the task logs that show every spill and merge pass, and the counters that tell you what it cost.

1 The story

The sorting room between two teams

Riya runs the same item-revenue job three times on the 140 MB orders file. Same input, same code, same answer each time. Only one setting changes: the size of the map task's sort buffer. With 16 MB the map task writes its output to disk 18 times and then has to merge those 18 files in two passes. With 200 MB it writes twice. Kabir asks the obvious question: why does a map task write anything to disk at all, if the answer is just six lines?

Arjun Sir

In Lesson 8.1 we said “Hadoop groups by key for you”. Today we open that box. It is called the shuffle and sort, and it is usually the most expensive part of a job: the map output is sorted, written to the worker's local disk, copied over the network to the reducers, and merged again.

Riya

So the map writes to disk because the buffer is too small to hold everything?

Arjun Sir

Partly. Even with a huge buffer the output must land on disk, because the reducers run later, maybe on other machines, and the map task's JVM exits when it is done. The NodeManager keeps serving that file to whichever reducer asks for it.

2 Definition

Shuffle and sort

Formal definition (write this in exams)

The shuffle and sort is the phase of a MapReduce job, carried out by the framework, that moves intermediate key-value pairs from map tasks to reduce tasks so that each reducer receives all values of its keys, sorted by key. On the map side, output pairs are assigned a partition by the Partitioner (by default HashPartitioner: (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks), collected in an in-memory circular buffer (mapreduce.task.io.sort.mb), sorted by partition and key, optionally passed through a combiner, and spilled to local disk whenever the buffer reaches mapreduce.map.sort.spill.percent (0.80); spill files are merged (mapreduce.task.io.sort.factor streams at a time) into one partitioned, sorted output file per map task. On the reduce side, fetcher threads copy the reducer's partition from every map over HTTP from the NodeManager's ShuffleHandler, merge the segments in memory and on disk, and present each key with an iterator over its values to the reduce() method.

In simple words

Each map sorts its output into labelled piles, one pile per reducer, and leaves them on its worker's disk. Each reducer collects its pile from every map, merges them into one sorted stream, and then calls your reduce once per key.

Shuffle and sort at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The post office sorting room

  • Every map is a post office collecting letters. It doesn't send them one by one: it drops them into bags, one bag per destination city (a partition per reducer), sorted by street (key).
  • When the counter table is full, the clerk ties up a bundle and puts it in the back room (a spill). At closing time all bundles for a city are combined into one sorted bag (the merge).
  • Each city's van (a reducer) visits every post office and picks up only its own bag (the fetch), then merges the bags so the postman walks each street once (reduce).

Intermediate The steps and the settings

  • Partition: every context.write(k, v) gets a partition number from the Partitioner, immediately.
  • Buffer: pairs go into the io.sort.mb buffer. At 80% full a background thread sorts it by (partition, key), runs the combiner if any, and spills one file. The map keeps writing into the remaining 20% meanwhile.
  • Merge: at the end the spills are merged, at most io.sort.factor (10) at a time, into file.out plus an index of where each partition starts. 18 spills needed an extra pass; 5 or 2 did not.
  • Fetch: after 5% of maps finish, reducers start; 5 fetchers per reducer download their partition from each finished map over HTTP (port 13562).
  • Merge and reduce: fetched segments are merged (in memory first, spilling to disk when needed); the final merge feeds reduce() directly, one key at a time.

Advanced Reading the counters like an engineer

  • Spilled Records counts records written to local disk anywhere in the job. Ideal is 2 × map output (map writes once, reducer once): 18,000,000 here, only possible when the map spills exactly once.
  • With 2–10 spills the map writes each record twice (spill + final merge) and the reducer once: 3 × 9,000,000 = 27,000,000, our 64 MB and 200 MB runs.
  • With 18 spills the merge needed an intermediate pass that rewrote 9 of the 18 segments: 31,354,091 − 27,000,000 = 4,354,091 extra records, about half the data written a third time.
  • Materialized bytes (108 MB) exceed raw map output bytes (90 MB for this file) because each record carries key and value lengths in the intermediate file format.
  • Fixes in order of effect: emit less (filter, combiner, compact types), compress map output (mapreduce.map.output.compress, Module 10), then tune io.sort.mb so a map spills once or twice.

Exam tip: For “Explain shuffle and sort in MapReduce”, draw two boxes: map side (partition → buffer → sort → spill → merge, local disk) and reduce side (fetch over HTTP → merge → reduce, keys in sorted order). Name three settings: io.sort.mb, sort.spill.percent 0.80, io.sort.factor 10.

The hooks you can plug into the shuffle

Partitioner

Decides which reducer gets a key. Default: hash of the key modulo reducers. Custom ones in Lesson 9.2.

which reducer

Sort comparator

Decides the order of keys. Default: the key type's natural order (Text compares bytes).

which order

Combiner

A mini-reduce run on each spill on the map side, to shrink the data before it travels. Lesson 9.1.

less data

Grouping comparator

Decides which consecutive keys share one reduce() call. Used for secondary sort, Lesson 9.7.

which group

The shuffle is all-to-all: with M maps and R reducers there are M × R pieces to copy. 1,000 maps and 200 reducers mean 2 lakh small HTTP fetches. That is why the number of reducers and the size of map output matter so much for big jobs.

    hdfs dfs -cat /out/shuf_16/part-r-00000
    chai 1505100 22576500 dosa 1498440 67429800 idli 1499520 44985600 poha 1496730 37418250 samosa 1500630 27011340 vada pav 1499580 29991600

A bigger io.sort.mb is not free: the buffer lives inside the map task's heap. Our maps had -Xmx300m; setting io.sort.mb close to or above that makes the task die with an OutOfMemoryError (values above 2047 MB are rejected outright as invalid). Raise the container memory and the heap together.

5 See it happen

From context.write() to reduce()

Six steps of the shuffle for the 16 MB run: fill, spill, merge, serve, fetch, reduce.

Shuffle and sort 6 steps
What you see
  1. The map task starts with a 16 MB buffer; a spill starts at 80% full.
  2. The buffer fills and spills 18 times during the map.
  3. 18 spill files are too many for one 10-way merge: one extra pass first.
  4. The map finishes with one sorted output file of 108 MB on its local disk.
  5. The reducer fetches exactly those bytes.
  6. The reducer writes six lines; Spilled Records shows the cost of the extra merge pass.
Behind the screen
  1. Every context.write() goes into the circular buffer with its partition number.
  2. At 80% a background thread sorts the buffer by partition and key and writes a spill file to local disk.
  3. The merger combines at most 10 files per pass: first 9 into 1, then the final 10.
  4. The result is one file per map, sorted, with an index of where each reducer's partition starts.
  5. The reducer's fetchers download their partition from each map's NodeManager.
  6. The fetched pieces are merged into one sorted stream; reduce() is called once per key.
6 Real-world use

The shuffle at work

1. Tuning slow nightly jobs

Platform teams compare Spilled Records with map output records. A ratio well above 3 means extra merge passes; raising the sort buffer (with container memory) or compressing map output often cuts minutes from big jobs.

Counters→io.sort.mb, compression→Fewer disk writes

2. Diagnosing skew

One reducer runs for hours while the others finish in minutes: one key (a popular product, a null customer ID) got most of the shuffle. Our 3-reducer run showed the small version: 4 items to one reducer, none to another.

Hot key→one huge partition→Salting / custom partitioner

3. Sorting benchmarks

TeraSort, the classic Hadoop benchmark, is almost pure shuffle: map reads, the framework sorts and shuffles terabytes, reduce writes. Clusters are tuned and compared on it.

teragen→terasort (shuffle)→teravalidate

4. The same shuffle in Spark

Spark's groupBy and join also write sorted, partitioned shuffle files to local disk, and on YARN they can be served by an external shuffle service in the NodeManager, just like mapreduce_shuffle.

Stage 1 tasks→shuffle files→Stage 2 tasks

Simplified; organisations differ in tools and policies.

7 Run the code

Simulate the map-side sort buffer, spills and merge

A tiny map task: the buffer holds only 4 pairs, so it spills often. Each spill is sorted by (partition, key). At the end the spills are merged with at most FACTOR files per pass, just like io.sort.factor.

import heapq
BUFFER, FACTOR, REDUCERS = 4, 3, 2
pairs = [("samosa", 18), ("chai", 15), ("poha", 25), ("dosa", 45), ("chai", 15),
         ("idli", 30), ("samosa", 18), ("chai", 15), ("vada pav", 20), ("poha", 25)]

def part(key):                                  # same formula as Hadoop's HashPartitioner on Text
    h = 1
    for b in key.encode():
        h = (31 * h + b) & 0xFFFFFFFF
    return (h & 0x7FFFFFFF) % REDUCERS

spills, buf, written = [], [], 0
for k, v in pairs:
    buf.append((part(k), k, v))
    if len(buf) == BUFFER:                      # buffer full: sort and spill
        spills.append(sorted(buf)); written += len(buf); buf = []
if buf:
    spills.append(sorted(buf)); written += len(buf)
print(len(spills), "spills:", [[k for p, k, v in s] for s in spills])

passes = 0
while len(spills) > 1:                          # merge at most FACTOR files per pass
    group, spills = spills[:FACTOR], spills[FACTOR:]
    merged = list(heapq.merge(*group))
    written += len(merged); passes += 1
    spills.append(merged)
print("merge passes:", passes, "| records written to disk on the map side:", written)
for p, k, v in spills[0]:
    print("partition", p, k, v)

  • def part(key): # same formula as Hadoop's HashPartitioner on TextText.hashCode() is WritableComparator.hashBytes: start at 1, multiply by 31, add each (signed) byte. ASCII bytes are positive, so this matches exactly.
  • if len(buf) == BUFFER: # buffer full: sort and spillHadoop spills at 80% (spill.percent), in a background thread, while the map keeps writing.

Interview and viva questions

What is shuffle and sort in MapReduce?

It is the framework phase between map and reduce. Map output pairs are partitioned by key, sorted and written to the map node's local disk; each reducer then copies its partition from every map over HTTP, merges the copies into one sorted stream and calls reduce once per key with all its values. The programmer does not write it, but can customise it with a partitioner, sort and grouping comparators and a combiner.

What is a spill in Hadoop MapReduce?

Map output is first collected in an in-memory circular buffer of mapreduce.task.io.sort.mb. When it reaches mapreduce.map.sort.spill.percent (80% by default), a background thread sorts the contents by partition and key, runs the combiner if one is set, and writes them to a spill file on local disk. At the end of the map, all spill files are merged into one output file.

Where is the intermediate output of a map task stored?

On the local disk of the node that ran the map task (in the NodeManager's local directories), not in HDFS. It is temporary and served to reducers by the NodeManager's shuffle service. If that node fails before the reducers have fetched it, the map task is re-executed elsewhere.

What is the role of the partitioner?

It decides which reducer receives each intermediate key, so that all values of a key reach the same reducer. The default HashPartitioner computes (key.hashCode() & Integer.MAX_VALUE) % numReduceTasks. A custom partitioner can balance load or route ranges of keys to reducers (for example for a total sort).

Are keys sorted in the final output of a MapReduce job?

Within each reducer's output file, yes: the reducer processes keys in sorted order. Across output files there is no global order with the default hash partitioner, because keys are spread by hash. A global order needs one reducer or a range partitioner such as TotalOrderPartitioner.

    print(spills, "spills ->", passes, "pass(es)")
2 spills -> 1 pass(es) 5 spills -> 1 pass(es) 10 spills -> 1 pass(es) 18 spills -> 2 pass(es) 40 spills -> 5 pass(es)

How it works: 1 pass up to 10 spills, 2 for 18 (our log: 9 merged first, then the last 10). Hadoop chooses the first pass size cleverly so the final pass has exactly 10.

P3Easy

Pieces to fetch

Our 422 MB job had 4 maps and 1 reducer: “Shuffled Maps =4”. How many pieces would 4 maps and 3 reducers create?

Input
maps × reducers
Expected output
4 and 12
Show solution and explanation 
print(4 * 1, "and", 4 * 3)

How it works: 4 and 12: every reducer fetches one piece from every map.

P4Medium

Partition a new item

The canteen adds “pav bhaji” and “masala chai”. Which of 3 reducers will each go to?

Input
HashPartitioner on Text
Expected output
pav bhaji 2
masala chai 0
Show solution and explanation 
def p(s, r):
    h = 1
    for b in s.encode():
        h = (31 * h + b) & 0xFFFFFFFF
    return (h & 0x7FFFFFFF) % r
for item in ["pav bhaji", "masala chai"]:
    print(item, p(item, 3))
pav bhaji 2 masala chai 0

How it works: The partition depends only on the bytes of the key and the number of reducers, so you can predict it before running the job.

Materialized bytes

Map output bytes were 89,999,580 and materialized bytes 107,999,586 for 9,000,000 records. How many extra bytes per record does the intermediate format add?

print((107_999_586 - 89_999_580) / 9_000_000, "bytes per record")

Merge three sorted lists of keys without sorting the combined list.

import heapq

P7Business problem

Is a bigger buffer worth it?

A nightly job runs 2,000 maps. Raising io.sort.mb from 100 to 300 MB saves 3 s per map (fewer spills) but each map container grows by 256 MB. The cluster has spare memory only for 1,800 maps at once at the bigger size (vs 2,000 now). Which is faster overall if each map takes 60 s?

Input
2,000 maps · 60 s vs 57 s · 2,000 vs 1,800 slots
Expected output
now 60 s, bigger buffer 114 s
Show solution and explanation 
import math
now = math.ceil(2000 / 2000) * 60
big = math.ceil(2000 / 1800) * 57
print(f"now {now} s, bigger buffer {big} s")
now 60 s, bigger buffer 114 s

How it works: 60 s vs 114 s: the saving per task is lost because the maps no longer fit in one wave. Tuning must consider the whole cluster.

P8Advanced

Simulate slowstart

10 maps finish at seconds 20, 22, 25, 30, 31, 33, 40, 41, 45, 60. Reducers start when slowstart × maps have finished. When do they start for 0.05, 0.5 and 1.0, and how many seconds of copying can overlap the maps?

Input
finish times, slowstart
Expected output
slowstart 0.05: reducers start at 20 s, can copy for 40 s while maps run
slowstart 0.5: reducers start at 31 s, can copy for 29 s while maps run
slowstart 1.0: reducers start at 60 s, can copy for 0 s while maps run
Show solution and explanation 
import math
done = [20, 22, 25, 30, 31, 33, 40, 41, 45, 60]
for s in (0.05, 0.5, 1.0):
    need = max(1, math.ceil(s * len(done)))
    start = sorted(done)[need - 1]
    print(f"slowstart {s}: reducers start at {start} s, can copy for {60 - start} s while maps run")
slowstart 0.05: reducers start at 20 s, can copy for 40 s while maps run slowstart 0.5: reducers start at 31 s, can copy for 29 s while maps run slowstart 1.0: reducers start at 60 s, can copy for 0 s while maps run

How it works: Early start overlaps copying with slow maps, but the reducer holds its container while waiting; busy clusters often raise slowstart to 0.8 or so.

Real-world scenario questions (asked in company interviews)

The shuffle is where performance and skew questions come from, at every level of experience.

Concepts · basicsFresher

“What happens between the mapper and the reducer?”

A standard follow-up to word count.

The interviewer is checking: partition, sort, spill, fetch, merge.

Show a strong answer
  • Each pair gets a partition (HashPartitioner), goes into the sort buffer, is sorted by partition and key and spilled to local disk; spills are merged into one file per map.
  • Reducers fetch their partition from every map over HTTP (NodeManager ShuffleHandler), merge them and call reduce once per key, in sorted order.
  • A combiner can shrink data on the map side before it travels.
Performance · countersExperienced

Spilled Records is 5 times Map output records

A long-running aggregation job; the team asks what to tune.

The interviewer is checking: reading counters, buffer and merge settings.

Show a strong answer
  • Ideal is 2×; 3× means several spills; 5× means extra merge passes (more spills than io.sort.factor) on map or reduce side.
  • Reduce map output first: combiner, filter early, compact keys, compress map output (Snappy/LZ4).
  • Then raise io.sort.mb (and the map heap/container) and io.sort.factor; check the task logs for “Merging N intermediate segments”.
Skew · partitioningExperienced

99 reducers finish in 3 minutes, one runs for 2 hours

A join on customer_id; many records have customer_id = NULL.

The interviewer is checking: hot keys and how the partitioner routes them.

Show a strong answer
  • All values of one key go to one reducer: the NULL key is one giant partition. Check the reducer's “Reduce input records” and shuffle bytes.
  • Filter or handle NULLs separately; salt hot keys (key + random suffix) and aggregate in two steps; or a custom partitioner.
  • More reducers do not help: the hot key still lands on one of them.
Failures · shuffleExperienced

Reducers fail with “Too many fetch failures” after a node dies

The job eventually succeeds but takes twice as long.

The interviewer is checking: where map output lives.

Show a strong answer
  • Map output is on the dead node's local disk, not HDFS, so reducers can't fetch it.
  • After repeated fetch failures the MRAppMaster marks those maps failed and reruns them elsewhere; reducers then fetch the new output.
  • The delay is the rerun of finished maps; healthy disks, NodeManager monitoring and blacklisting bad nodes reduce it.
