Erasure coding

Three replicas are simple and fast, but they triple the disk bill. Hadoop 3 added erasure coding: split data into pieces, compute parity, and survive the same failures with far less space. This lesson stores one file both ways on a real cluster, kills DataNodes until the data is lost, and explains which data should and should not be erasure-coded.

1 The story

Paying three times for data nobody reads

The university's finance office looks at the storage bill. Five years of old exam scans, canteen logs and CCTV exports sit in HDFS, read maybe once a year for audits. Every byte is stored three times. 400 TB of data uses 1.2 PB of disk. “Can't we keep fewer copies of the old stuff?” Riya says replication 2 would be risky. Arjun Sir has a better idea, borrowed from the same mathematics that lets a scratched DVD still play.

Arjun Sir

Since Hadoop 3, HDFS supports erasure coding. Instead of copying a block three times, it cuts the data into pieces and computes extra parity pieces with Reed-Solomon mathematics. With the policy RS-3-2, 3 data pieces get 2 parity pieces: any 2 of the 5 can be lost, and the data can still be rebuilt.

Riya

Same safety as three copies, but 167% instead of 300%?

Arjun Sir

For large, cold files, yes. But nothing is free: reading after a failure means calculating the missing data, a small file gains nothing, and you need enough DataNodes and racks. Today we store the same file both ways on our 5-node cluster, kill DataNodes one by one, and see exactly where erasure coding wins and where it doesn't.

2 Definition

Erasure coding in HDFS

Formal definition (write this in exams)

Erasure coding (EC) is a data protection method that encodes k data units into n = k + m units by adding m parity units, such that the original data can be reconstructed from any k of the n units. HDFS (since Hadoop 3.0) applies EC per directory through an erasure coding policy (e.g. RS-6-3-1024k: Reed-Solomon codec, 6 data and 3 parity units, 1 MB cells). Files under the directory are written in striped layout: data is split into cells distributed round-robin over the k data internal blocks of a block group, and parity cells are computed for each stripe and stored in m parity internal blocks, each internal block on a different DataNode (and rack where possible). Storage overhead is (k + m) / k and up to m simultaneous failures are tolerated; missing units are reconstructed by decoding on read or in the background.

In simple words

Split the data into 3 parts, compute 2 “recovery” parts, put all 5 on different machines. Any 2 machines can die and the data can be recomputed from the other 3. It costs 1.67× space instead of 3×.

Erasure coding at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A puzzle with spare clues

  • Three friends each keep one page of a secret recipe (data). Two more friends keep clue cards made by mixing the pages (parity).
  • If any two friends lose their paper, the remaining three can work out the full recipe.
  • Photocopying the recipe three times also works, but uses far more paper.

Intermediate How HDFS stores and reads an EC file

  • Set a policy on a directory: hdfs ec -setPolicy -path /ec -policy RS-3-2-1024k. New files below it are erasure-coded; existing files are not converted.
  • The client cuts the file into 1 MB cells, writes them round-robin to 3 data internal blocks, computes 2 parity cells per stripe, and writes all 5 in parallel to 5 DataNodes.
  • hdfs dfs -du shows the real cost: 140,760,270 bytes of data use 235,132,110 bytes of disk (1.67×), vs 422,280,810 (3×) with replication.
  • Reading normally fetches the 3 data blocks; if some are missing, the client fetches parity and decodes on the fly.

Advanced Trade-offs experienced engineers weigh

  • Small files: a 15-byte file under RS-3-2 used 45 bytes, the same 3× as replication: one data cell plus two full parity cells. EC only saves space for files spanning several cells.
  • Data locality: a striped file's bytes are spread over many nodes, so map tasks can't read a whole split locally. EC suits cold, rarely processed data better than hot data.
  • Recovery cost: rebuilding a lost replica copies one block; rebuilding an EC unit reads k units over the network and uses CPU (ISA-L native libraries speed this up).
  • Cluster shape: RS-6-3 needs 9 DataNodes, and rack fault tolerance needs enough racks; hdfs ec -verifyClusterSetup checks this. Our 2-rack lab got a warning for RS-3-2.
  • Operations: EC files can't be appended to in older releases and some features (e.g. hflush/hsync semantics) differ; check your version's documentation before using EC for active data.

Exam tip: For “Explain erasure coding in Hadoop 3”, give: the idea (k data + m parity, survive any m losses), the RS-6-3 example (9 units, 1.5× overhead vs 3×), striped layout with cells and block groups, the command hdfs ec -setPolicy, and two disadvantages (CPU/network cost of reconstruction, poor fit for small files and hot data).

    docker stop lab5-datanode-4 lab5-datanode-5
hdfs dfs -get -f /ec/orders_x30.csv /tmp/ec2.csv ; md5sum /tmp/ec2.csv

    Identical bytes, decoded from the surviving units. The 63 s were mostly waiting: right after the stop, the NameNode still listed the two DataNodes as live, so the client spent a 60 s connect timeout before using parity. In another run done a little later, the same read took 2 s.

  5. Lose a third DataNode

    docker stop lab5-datanode-3
hdfs dfs -get -f /ec/orders_x30.csv /tmp/ec3.csv

    Three of five units missing, more than the 2 parity units: the EC file is unreadable. The replicated copy still read fine, because with only 5 DataNodes some of its replicas survived on the 2 remaining nodes. Equal fault tolerance on paper (2 failures each); in this case replication happened to survive a third.

Never set an EC policy on folders with many small files, or on hot data that jobs read all day. Check verifyClusterSetup first, and keep enough racks: an EC policy without rack diversity can lose data to a single rack failure.

What you see
  1. The admin sets RS-3-2 on the /ec folder.

  3. -du shows 1.67× instead of 3× raw space.

Behind the screen
  1. RS-3-2 needs five internal blocks on five different DataNodes.
  2. The client cuts data into 1 MB cells, writes them round-robin to three data blocks, and computes two parity cells for each stripe.
  3. Every 3 MB of data costs 5 MB of disk: 1.67×. Three replicas would cost 9 MB.
  4. Two DataNodes are lost. Any 3 of the 5 units are enough to rebuild each stripe.
  5. With a third loss only two units remain, fewer than the three needed: the data is lost until nodes return.
  6. A tiny file fills only part of one cell, but both parity cells are as big as that cell: no saving.
6 Real-world use

Erasure coding at work

1. Cold and archival data

Clusters apply RS-6-3 to folders of old partitions, logs and backups that are rarely read, cutting raw storage for that data roughly in half compared with 3× replication.

Data older than N months→Copy into EC folder→1.5× instead of 3×

2. Hot and cold in one cluster

Today's and this month's partitions stay replicated for fast local reads; a scheduled job moves older partitions into an EC directory and updates the table's location.

Hot: replication→Monthly move job→Cold: EC

3. Planning racks for EC

Architects size racks so each block group spreads widely: with RS-6-3 across 9 or more racks, a whole rack failure costs at most one unit per group.

Policy→verifyClusterSetup→Rack plan

4. The same idea everywhere

Cloud object stores and many storage systems also use erasure coding internally to achieve high durability without full copies; HDFS brought the technique to Hadoop clusters.

Data→k data + m parity→Durable, cheaper

Simplified; organisations differ in tools and policies.

7 Run the code

Parity you can compute: XOR erasure coding

HDFS's simplest policy, XOR-2-1, computes one parity cell as the XOR of two data cells. Lose any one of the three and XOR the other two to get it back. Reed-Solomon does the same idea with more parity. Run it, then lose a different cell.

d1 = b"order_id,item,amount\n1,chai,20\n"
d2 = b"2,poha,30\n3,dosa,40\n4,idli,30\n"
size = max(len(d1), len(d2))
d1, d2 = d1.ljust(size, b"\0"), d2.ljust(size, b"\0")     # cells are padded to equal size

parity = bytes(a ^ b for a, b in zip(d1, d2))            # XOR-2-1: one parity cell
print("stored cells:", len(d1), "+", len(d2), "+", len(parity), "bytes")

lost = "d2"                                               # a DataNode dies
rebuilt = bytes(a ^ p for a, p in zip(d1, parity))        # d1 XOR parity = d2
print("rebuilt", lost, "correct:", rebuilt == d2)
print(rebuilt.rstrip(b"\0").decode())
print(f"overhead: {(len(d1) + len(d2) + len(parity)) / (2 * size):.2f}x")
stored cells: 31 + 31 + 31 bytes rebuilt d2 correct: True 2,poha,30 3,dosa,40 4,idli,30 overhead: 1.50x
  • parity = bytes(a ^ b for a, b in zip(d1, d2)) # XOR-2-1: one parity cellXOR has a handy property: if p = a ⊕ b, then a = p ⊕ b and b = p ⊕ a. One parity cell protects against one loss.
  • rebuilt = bytes(a ^ p for a, p in zip(d1, parity)) # d1 XOR parity = d2Reconstruction is computation, not copying: the reader needs the surviving cells and CPU time.
  • print(f"overhead: {(len(d1) + len(d2) + len(parity)) / (2 * size):.2f}x")3 cells stored for 2 cells of data: 1.5×, versus 3× with replication. RS-6-3 also reaches 1.5× but survives 3 losses.

Interview and viva questions

What is erasure coding in Hadoop?

A storage method introduced in Hadoop 3 in which file data is split into data units and parity units are computed with an algorithm such as Reed-Solomon. The units are stored on different DataNodes, and the original data can be reconstructed from any k of the k + m units. It gives similar or better fault tolerance than 3× replication at around 1.4–1.67× storage.

What are the disadvantages of erasure coding?

Reconstruction needs network reads from several nodes and CPU for decoding; reads lose data locality because data is striped across nodes; small files gain no space; it needs at least k + m DataNodes and enough racks; and some write features behave differently from replicated files. It is best for large, cold data.

How do you enable erasure coding on a directory?

Enable the policy if needed (hdfs ec -enablePolicy -policy RS-6-3-1024k), check the cluster with hdfs ec -verifyClusterSetup, then run hdfs ec -setPolicy -path /dir -policy RS-6-3-1024k. Files created afterwards in that directory are erasure-coded; existing files must be copied to be converted.

What is a block group?

In striped erasure coding, the set of k data and m parity internal blocks that together store a range of a file. Each internal block is stored on a different DataNode and has an ID derived from the group ID.

Replication or erasure coding: how do you choose?

Use replication for hot data, small files and data read with locality by many jobs. Use erasure coding for large files that are rarely read, such as archives, old partitions and backups, where storage savings matter more than read performance.

P1Easy

Overhead formula

Print the overhead (k+m)/k for RS-3-2, RS-6-3 and RS-10-4.

Input
3 policies
Expected output
RS-3-2: 1.67x
RS-6-3: 1.50x
RS-10-4: 1.40x
Show solution and explanation 
for k, m in [(3, 2), (6, 3), (10, 4)]:
    print(f"RS-{k}-{m}: {(k + m) / k:.2f}x")
RS-3-2: 1.67x RS-6-3: 1.50x RS-10-4: 1.40x

How it works: 1.67×, 1.50×, 1.40×.

P3Easy

Internal block indexes

Internal block IDs are the group ID plus the index. Given the five IDs from fsck, print each index and whether it holds data or parity (k = 3).

Input
-9223372036854775728 … -9223372036854775724
Expected output
-9223372036854775728 index 0 data
-9223372036854775727 index 1 data
-9223372036854775726 index 2 data
-9223372036854775725 index 3 parity
-9223372036854775724 index 4 parity
Show solution and explanation 
ids = [-9223372036854775728 + i for i in range(5)]
group = ids[0]
for b in ids:
    i = b - group
    print(b, "index", i, "data" if i < 3 else "parity")
-9223372036854775728 index 0 data -9223372036854775727 index 1 data -9223372036854775726 index 2 data -9223372036854775725 index 3 parity -9223372036854775724 index 4 parity

How it works: Indexes 0–2 are data, 3–4 parity: consecutive IDs in one block group.

P4Medium

XOR recovery

Data cells a = b"HDFS", b = b"EC!!"; parity p = a XOR b. Rebuild a from b and p.

Input
two 4-byte cells
Expected output
b'HDFS'
Show solution and explanation 
a, b = b"HDFS", b"EC!!"
p = bytes(x ^ y for x, y in zip(a, b))
print(bytes(x ^ y for x, y in zip(b, p)))
b'HDFS'

How it works: b"HDFS": XOR parity is the simplest erasure code.

P5Medium

Readable or not?

Input
0 to 4 lost
Expected output
0 lost -> readable
1 lost -> readable
2 lost -> readable
3 lost -> readable
4 lost -> LOST
Show solution and explanation 
k, m = 6, 3

P8Advanced

Placement check

Given rack assignments of the 5 internal blocks, check whether losing any single rack loses more than m = 2 units.

Input
5 units over 2 racks
Expected output
worst rack holds 3 units -> a rack failure loses data
Show solution and explanation 
from collections import Counter
racks = ["r1", "r1", "r2", "r2", "r2"]           # rack of each internal block
worst = max(Counter(racks).values())
print("worst rack holds", worst, "units ->", "safe" if worst <= 2 else "a rack failure loses data")
worst rack holds 3 units -> a rack failure loses data

How it works: With 2 racks, one holds 3 units: exactly why verifyClusterSetup asked for 3 racks for RS-3-2.

Real-world scenario questions (asked in company interviews)

Erasure coding questions are common in Hadoop 3 interviews, especially for platform and administrator roles.

Hadoop 3 · featuresFresher

“What's new in Hadoop 3 for storage?”

A common Hadoop 2 vs 3 question.

The interviewer is checking: erasure coding and its trade-offs.

Show a strong answer
  • Erasure coding: e.g. RS-6-3 stores 1.5× instead of 3× and tolerates 3 failures.
  • Also: more than two NameNodes for HA, intra-DataNode disk balancer, and other improvements.
  • Mention when not to use EC: small files, hot data needing locality.
Capacity · decisionExperienced

Storage is 85% full; buying disks takes 4 months

A 2 PB cluster, mostly replicated. 60% of data is older than a year and rarely read.

The interviewer is checking: practical EC adoption.

Show a strong answer
  • Identify cold, large-file folders; check verifyClusterSetup for RS-6-3 (nodes and racks).
  • Create EC folders, copy cold partitions with distcp, verify checksums/row counts, repoint tables, delete originals.
  • Moving 1.2 PB of data from 3× to 1.5× frees roughly 1.8 PB of raw space; do it in batches off-peak.
Performance · troubleshootingExperienced

Jobs on EC data are slower and network traffic jumped

After converting a frequently queried table to EC, morning jobs take 40% longer.

The interviewer is checking: locality and decode costs.

Show a strong answer
  • Striped files have no node-local splits: every read pulls cells from several DataNodes over the network.
  • Any failed node forces decoding, which costs CPU (check that native ISA-L acceleration is enabled).
  • Keep hot tables replicated; apply EC only after data cools down.
Concepts · reliabilityFresher

“Is EC as safe as replication?”

A manager's question before approving EC.

The interviewer is checking: fault tolerance with conditions.

Show a strong answer
  • RS-6-3 tolerates 3 simultaneous losses per block group vs 2 for replication 3, at half the space.
  • Conditions: enough DataNodes and racks so units are spread out, and capacity for reconstruction traffic.
  • Real demo: data survived 2 lost DataNodes with an identical checksum under RS-3-2, and failed only at the third.
