HDFS federation

HA protects the NameNode from failure, but not from its own limits: every file and block lives in one NameNode's memory. Federation runs several independent NameNodes, each owning part of the folder tree, on the same DataNodes. This lesson builds a two-NameNode cluster, looks at the block pools on a DataNode's disk, and shows what works and what doesn't across namespaces.

1 The story

When one NameNode's memory is not enough

The university cluster is a success. The canteen project, the hostel system, exam results and research labs all store data in it. Now there are hundreds of millions of files. The NameNode keeps every file and block in RAM, its heap is already huge, garbage-collection pauses are getting longer, and every team's jobs queue up behind the same NameNode. Adding DataNodes adds disk, but not a single extra byte of NameNode memory. HA (Lesson 7.1) gave the NameNode a spare, but the spare has exactly the same limits.

Arjun Sir

The answer is HDFS federation. Instead of one NameNode for everything, we run several independent NameNodes, each owning part of the namespace: one for /canteen, one for /hostel. They don't talk to each other at all.

Riya

Then each one needs its own DataNodes?

Arjun Sir

No, that's the clever part. The same DataNodes serve all of them. Each NameNode gets its own block pool on every DataNode, so storage is shared and grows for everyone. Clients see one tree through a mount table. Today we start two NameNodes on the same three DataNodes, look inside a DataNode's disk, try to move a file between them, and switch one NameNode off.

2 Definition

HDFS federation

Formal definition (write this in exams)

HDFS federation scales the namespace layer horizontally by running multiple independent NameNodes, each managing its own namespace volume: a namespace (directory tree and file metadata) plus a block pool (the set of blocks belonging to that namespace). NameNodes do not coordinate with each other. All NameNodes share one cluster ID and the same set of DataNodes; each DataNode registers with every NameNode, stores blocks of each pool in a separate directory (current/BP-…), and sends heartbeats and block reports per pool. Clients obtain a unified view through a client-side mount table (ViewFS, viewfs://) or through Router-Based Federation (RBF), where stateless routers forward requests according to a shared mount table. Each nameservice may itself be highly available.

In simple words

Several NameNodes split the folder tree between them, like several librarians each responsible for different sections, while all the bookshelves (DataNodes) are shared. A map tells clients which librarian to ask for which folder.

Federation at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A library with several librarians

  • One librarian can only remember so many books. So the library hires a second: one for science, one for arts.
  • Both use the same shelves. Each shelf has a science corner and an arts corner (block pools).
  • A signboard at the entrance says which librarian to ask for which section (mount table). If the arts librarian is on leave, science books can still be borrowed.

Intermediate How it is set up and used

  • Format each NameNode with the same cluster ID (hdfs namenode -format -clusterId campus-cluster); list all nameservices in dfs.nameservices so DataNodes register with every NameNode.
  • Each NameNode only knows its own files: hdfs dfs -ls -R hdfs://nn-canteen:8020/ showed only /canteen.
  • With a ViewFS mount table, hdfs dfs -ls / shows /canteen, /hostel, /tmp as one tree.
  • Moving a file between namespaces is a copy (distcp or cp) plus delete, not a rename.

Advanced What architects weigh

  • Why: NameNode heap grows with objects (files, folders, blocks); a common rule of thumb is roughly 150 bytes per object, so hundreds of millions of objects need very large heaps. RPC load also concentrates on one process. Federation splits both.
  • ViewFS vs RBF: ViewFS puts the mount table in every client's configuration (changes must reach every client); RBF keeps it in a shared state store behind routers, so clients use one address and admins can move mount points centrally.
  • Federation + HA: independent. A large cluster may have 4 nameservices, each with an active and standby NameNode.
  • Costs: more NameNodes to run and monitor, uneven growth between namespaces, and no atomic rename across them. Choosing the split (by team, by data domain) matters.

Exam tip: For “Explain HDFS federation”, draw two NameNodes with separate namespaces and block pools, shared DataNodes with one folder per block pool, and a mount table on top. Contrast with HA: HA = availability of one namespace; federation = scalability of the namespace.

Unifying the namespaces

ViewFS

Mount table in the client's core-site.xml (fs.viewfs.mounttable.*). Simple, no extra servers; every client needs the same config.

client-side

Router-Based Federation

hdfs dfsrouter processes with a shared state store; hdfs dfsrouteradmin -add /canteen nsc /canteen. Clients talk to routers.

server-side

Direct URIs

hdfs://nn-hostel:8020/hostel: works, but hard-codes which namespace holds the data.

avoid

Split by

Team, business domain or data type (e.g. /user vs /warehouse vs /tmp), so each namespace grows predictably.

design

Putting /tmp and other small-file-heavy, high-churn folders on their own namespace is a classic use of federation: their constant creates and deletes no longer slow down the NameNode that serves production data.

  5. No rename across namespaces

    hdfs dfs -mv /canteen/orders.csv /hostel/orders.csv
    mv: Renames across Mount points not supported
    A rename is a metadata change inside one NameNode. Two NameNodes can't do it atomically together, so you must copy and delete. Plan the namespace split so that jobs don't need to move data across it.

  6. Switch one NameNode off

    docker stop lab72-nn-canteen-1
hdfs dfs -ls /hostel
hdfs dfs -ls /canteen
    -rw-r--r-- 3 hadoop supergroup 538894 2026-10-21 15:58 /hostel/rooms.csv -ls: java.net.UnknownHostException: nn-canteen
    Failure isolation: the hostel namespace keeps working. The canteen namespace is unavailable (in our Docker lab the stopped container's name no longer resolves). In production, each nameservice would also be HA.

Federation does not make one namespace bigger or faster: a single folder tree still lives in one NameNode. If one team's namespace outgrows its NameNode, you must split that tree further (or reduce small files, Lesson 7.5).

One client, two NameNodes, shared DataNodes

Six steps from our lab: writing to two mount points, looking at the DataNode, and losing one NameNode.

Federation in action 6 steps
What you see
  1. The client writes the orders file to /canteen.
  2. It writes the rooms file to /hostel, with the same command style.
  3. Listing / shows one tree with three mount points.
  4. On a DataNode's disk, there are two block pool folders, one per NameNode.
  5. Moving a file from /canteen to /hostel is refused.
  6. With the canteen NameNode stopped, /hostel still works and /canteen fails.
Behind the screen
  1. The mount table routes /canteen to nn-canteen, which places blocks in its pool on the DataNodes.
  2. /hostel goes to nn-hostel; its blocks go to the other pool on the same DataNodes.
  3. The root listing is built by the client from the mount table.
  4. Each DataNode stores both pools in separate folders and sends a block report per pool to the right NameNode.
  5. The NameNodes share nothing but DataNodes and the cluster ID, so a cross-namespace rename can't be done.
  6. One NameNode stopping affects only its own namespace.
6 Real-world use

Federation at work

1. Very large clusters

Organisations whose HDFS holds hundreds of millions to billions of files have publicly described running many NameNodes with federation, often behind routers, because no single NameNode heap could hold their namespace.

Billions of files→Many nameservices→One view via routers

2. Isolating noisy workloads

Scratch and staging folders with millions of short-lived files get their own namespace, so their churn doesn't slow the NameNode that serves production tables.

/tmp, /staging→Separate NameNode→Stable prod latency

3. Moving data without changing paths

With Router-Based Federation, admins can copy a folder to a less loaded namespace and then repoint its mount entry. Users keep using the same path.

distcp→Update mount table→Same path, new NameNode

4. Multi-tenant platforms

Shared enterprise clusters give big business units their own namespace for isolation and capacity planning, while sharing DataNodes, YARN and operations.

Business units→One namespace each→Shared storage

Simplified; organisations differ in tools and policies.

7 Run the code

A mount table that routes paths to NameNodes

ViewFS is essentially a longest-prefix lookup: the path's mount point decides which NameNode answers. This program routes a few paths and refuses a rename across mount points, like our real cluster did.

mounts = {"/canteen": "hdfs://nn-canteen:8020/canteen",
          "/hostel":  "hdfs://nn-hostel:8020/hostel",
          "/tmp":     "hdfs://nn-hostel:8020/tmp"}

def resolve(path):
    best = max((m for m in mounts if path == m or path.startswith(m + "/")), key=len, default=None)
    if best is None:
        raise FileNotFoundError(path + " is not under any mount point")
    return mounts[best] + path[len(best):]

def rename(src, dst):
    s, d = resolve(src), resolve(dst)
    if s.split("/")[2] != d.split("/")[2]:
        return "mv: Renames across Mount points not supported"
    return f"renamed inside {s.split('/')[2]}"

for p in ["/canteen/orders.csv", "/hostel/rooms.csv", "/tmp/x"]:
    print(f"{p:22} -> {resolve(p)}")
print(rename("/canteen/orders.csv", "/hostel/orders.csv"))
print(rename("/hostel/rooms.csv", "/tmp/rooms.csv"))
/canteen/orders.csv -> hdfs://nn-canteen:8020/canteen/orders.csv /hostel/rooms.csv -> hdfs://nn-hostel:8020/hostel/rooms.csv /tmp/x -> hdfs://nn-hostel:8020/tmp/x mv: Renames across Mount points not supported renamed inside nn-hostel:8020
  • best = max((m for m in mounts if path == m or path.startswith(m + "/")), key=len, default=None)The longest matching mount point wins, so nested mounts (e.g. /data and /data/logs) work.
  • if s.split("/")[2] != d.split("/")[2]:Different NameNodes behind source and target: no single NameNode can rename atomically. Our cluster printed exactly this message.
  • print(rename("/hostel/rooms.csv", "/tmp/rooms.csv"))Interesting: /hostel and /tmp are on the same NameNode here, so the logic allows it. Real ViewFS is stricter by default and refuses renames between any two different mount points.

Example 1BeginnerSizing · heap

When does one NameNode stop being enough?

Problem statement

A NameNode server can give the NameNode at most 192 GB of heap. Using the rule of thumb of 150 bytes per object, how many objects fit, and how many files is that if, on average, each file brings 0.1 folders and 1.5 blocks with it?

Input
192 GB · 150 B/object · 2.6 objects per file
Expected output
1.37 billion objects -> about 529 million files

Approach

  1. Objects = heap / 150 bytes.
  2. Each file costs 1 + 0.1 + 1.5 = 2.6 objects.
  3. Files = objects / 2.6.

Quick revision

Lesson 7.2 in one screen

  • Federation = several independent NameNodes, each with its own namespace and block pool, sharing DataNodes.
  • Same cluster ID (-clusterId at format); dfs.nameservices lists all; DataNodes register with each.
  • DataNode disk: one current/BP-… folder per namespace (lab: 2.5 M canteen, 572 K hostel).
  • Unified view: ViewFS (client mount table) or RBF (routers + state store).
  • No rename across namespaces (“Renames across Mount points not supported”); copy + delete instead.
  • Failure isolation: one NameNode down affects only its namespace; combine with HA per nameservice.
  • Why: NameNode heap ~150 bytes/object (rule of thumb) and RPC load; split busy or small-file-heavy trees.

Interview and viva questions

What is HDFS federation?

A way to scale the HDFS namespace by running multiple independent NameNodes. Each manages its own namespace and block pool, while all of them share the same DataNodes, which store blocks for every pool in separate directories. Clients see a unified namespace through ViewFS or Router-Based Federation.

What is the difference between HDFS HA and federation?

HA provides availability for one namespace: an active and standby NameNode hold the same metadata and the standby takes over on failure. Federation provides scalability and isolation: several NameNodes hold different parts of the namespace. They can be combined, with each federated nameservice running as an HA pair.

What is ViewFS?

A client-side file system (viewfs://) that uses a mount table in the client configuration to map paths like /canteen and /hostel to directories in different HDFS namespaces, giving one logical tree.

What is Router-Based Federation?

A server-side approach introduced in Hadoop 2.9/3.0: stateless router processes accept client requests on one address and forward them to the right nameservice using a mount table kept in a shared state store. Mount points can be changed centrally without updating clients.

Does federation increase the size limit of a single directory tree?

No. Each namespace still lives in one NameNode. Federation helps when the overall namespace can be split into separate subtrees across NameNodes.

P8Advanced

Mount table resolver

Implement longest-prefix resolution with nested mounts /data → nn1 and /data/logs → nn2.

Input
2 nested mounts
Expected output
/data/sales/x -> nn1
/data/logs/app.log -> nn2
/data/logsheet.csv -> nn1
Show solution and explanation 
mounts = {"/data": "nn1", "/data/logs": "nn2"}
def ns(path):
    return mounts[max((m for m in mounts if path == m or path.startswith(m + "/")), key=len)]
for p in ["/data/sales/x", "/data/logs/app.log", "/data/logsheet.csv"]:
    print(p, "->", ns(p))
/data/sales/x -> nn1 /data/logs/app.log -> nn2 /data/logsheet.csv -> nn1

How it works: /data/logs/app.log goes to nn2; /data/logsheet.csv still goes to nn1 because the match is on whole path components.

Real-world scenario questions (asked in company interviews)

Federation questions appear in senior Hadoop administrator and platform architect interviews.

HDFS · conceptsFresher

“HA and federation: what's the difference?”

Often asked right after HA.

The interviewer is checking: availability vs scalability.

Show a strong answer
  • HA: same namespace on an active and standby NameNode; protects against NameNode failure.
  • Federation: different namespaces on independent NameNodes sharing DataNodes; scales metadata and isolates workloads.
  • They combine: each federated nameservice can be an HA pair.
Operations · capacityExperienced

NameNode heap at 90% and GC pauses growing

A 600-million-object namespace on one HA pair; RPC queue times are rising during the day.

The interviewer is checking: options in order of effort.

Show a strong answer
  • First reduce objects: find small-file-heavy folders, compact them, clean /tmp and old data, use HAR or table compaction.
  • Tune heap and GC; consider Observer NameNodes for read-heavy load.
  • If growth continues, federate: move high-churn trees (/tmp, staging, a big tenant) to a new nameservice, behind routers so paths don't change.
Design · ViewFS vs RBFExperienced

Rolling out federation to 2,000 client machines

You add a second nameservice. Edge nodes, Spark jobs, Airflow workers and BI tools all access HDFS.

The interviewer is checking: client configuration management.

Show a strong answer
  • With ViewFS, every client needs the new mount table; any stale config breaks paths. Manageable with strong config management.
  • With Router-Based Federation, clients point to the routers once; mount changes are made centrally with dfsrouteradmin.
  • Run several routers behind a nameservice for availability, and monitor the state store.
TroubleshootingExperienced

A new NameNode is up, but no DataNode registers with it

The second NameNode shows 0 live DataNodes; DataNode logs show an incompatible cluster ID.

The interviewer is checking: cluster ID and block pools.

Show a strong answer
  • The new NameNode was formatted without the existing cluster ID, so DataNodes refuse it.
  • Reformat the empty new NameNode with -clusterId <existing id> (from any DataNode's VERSION file), add it to dfs.nameservices, and refresh DataNodes (dfsadmin -refreshNamenodes).
  • Never reformat a NameNode that already holds data.
