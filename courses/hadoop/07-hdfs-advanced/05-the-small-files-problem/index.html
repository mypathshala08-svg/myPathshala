The small files problem

HDFS is built for big files. Store the same data as thousands of tiny files and the NameNode's memory, every client call and every job pay for it. This lesson measures the cost on a real cluster with 10,000 files against one, explains where the time and memory go, and fixes it with a Hadoop Archive and better writing habits.

1 The story

Ten thousand files, three hundred kilobytes

The canteen billing app was changed to write one CSV file per order into HDFS. It looked tidy: o_1.csv, o_2.csv, … After one busy morning there are 10,000 files with only 339 KB of data between them. Uploading them took almost five minutes, reading them back took 15 seconds, and the cluster admin calls Riya: the NameNode just gained 20,000 new objects to keep in memory. The same data as one file uploads in 2 seconds and costs the NameNode 2 objects.

Arjun Sir

This is the famous small files problem. HDFS was designed for a few million large files. Every file, folder and block is an object in the NameNode's memory, and every file needs its own calls to the NameNode and its own pipeline to DataNodes. A 33-byte file costs the NameNode about as much as a 128 MB one.

Riya

Then the data size doesn't matter at all?

Arjun Sir

For the NameNode, hardly. For jobs, small files also mean one map task per file, so 10,000 tiny tasks that spend more time starting than working. Today we measure all of it, and then fix it: pack the files into a Hadoop Archive, and see why the real fix is to never write them in the first place.

2 Definition

The small files problem

Formal definition (write this in exams)

The small files problem refers to the degradation of HDFS and processing performance when data is stored as a large number of files significantly smaller than the HDFS block size. Because the NameNode keeps every file, directory and block as an object in memory (commonly estimated at roughly 150 bytes each), the number of files rather than the volume of data determines NameNode heap use, RPC load and the time for listings, block reports and restarts. Each small file also requires separate metadata operations and a separate block write and read, and frameworks typically create at least one input split (and task) per file, so job overhead grows with file count. Mitigations include writing larger files at the source, periodic compaction, container formats (SequenceFile, Avro, Parquet), Hadoop Archives (HAR), and input formats that combine files (CombineFileInputFormat).

In simple words

HDFS keeps a catalogue card for every file and block. Millions of tiny files mean millions of cards, endless trips to the catalogue, and thousands of tiny jobs, even if all the files together are small. Store fewer, bigger files.

Small files at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A library that registers every page

  • Imagine a library that makes a catalogue card for every book. Fine. Now someone donates 10,000 single-page leaflets: 10,000 cards, 10,000 shelf slots.
  • The librarian's card box (NameNode memory) fills up, and finding anything takes longer, even though the leaflets together are thinner than one book.
  • Binding the leaflets into one volume (compaction or an archive) needs one card.

Intermediate Where the cost comes from

  • NameNode memory: each file + block ≈ 2 objects. Our 10,000 files added 20,000 objects; the big file added 2.
  • RPCs: each file needs create, addBlock, complete, plus a DataNode pipeline. That is why the upload took 281 s instead of 2 s, even in one JVM.
  • Reading: one getBlockLocations and one DataNode connection per file: 15.2 s vs 1.9 s.
  • Jobs: MapReduce and Spark create about one split per file. 10,000 files → about 10,000 tasks, each lasting milliseconds after seconds of start-up.

Advanced How teams fix it

  • At the source: buffer and write larger files (e.g. a file per hour per partition, not per event); streaming sinks with sensible flush intervals.
  • Compaction jobs: Spark coalesce/repartition, Hive merge settings, or table-format commands (Delta OPTIMIZE, Iceberg rewrite_data_files) on a schedule.
  • Containers: SequenceFile or Avro with filename as key; Parquet tables instead of per-record files.
  • HAR: for archives that must keep file names but are rarely read. HAR files are immutable and add an index lookup on read.
  • Guardrails: name quotas (Lesson 7.4) on landing folders, monitoring of average file size per folder, and federation for unavoidable churn (Lesson 7.2).

Exam tip: For “What is the small files problem in Hadoop and how do you solve it?”, give the two costs (NameNode memory, roughly 150 bytes per object; one map task per file), one number (e.g. 10,000 files vs 1 file), and three solutions: HAR, SequenceFile/combining, CombineFileInputFormat, plus “write bigger files at source”.

Measuring and fixing small files

  3. Same bytes, very different object counts

    hdfs dfs -count -v /small /big
hdfs dfs -du -s /small /big
hdfs fsck /small ; hdfs fsck /big
    DIR_COUNT FILE_COUNT CONTENT_SIZE PATHNAME 1 10000 338894 /small 1 1 338894 /big 338894 1016682 /small 338894 1016682 /big Total blocks (validated): 10000 (avg. block size 33 B) Total blocks (validated): 1 (avg. block size 338894 B)
    Identical bytes on DataNode disks (HDFS blocks are only as big as their data, so no disk is wasted there). The difference is entirely in the NameNode: 10,000 blocks averaging 33 bytes.

  4. Read everything back

    hdfs dfs -cat '/small/*.csv' | wc -l
hdfs dfs -cat /big/big.csv | wc -l
    20000 read 10000 files: 15168 ms 20000 read 1 file: 1892 ms
    Same 20,000 lines. The small files needed 10,000 location lookups and 10,000 DataNode connections: 8 times slower, and that's with one client and no job framework.

  5. Fix: pack them into a Hadoop Archive

    hadoop archive -archiveName orders.har -p /small /archives
hdfs dfs -ls /archives/orders.har
hdfs dfs -count -v har:///archives/orders.har ; hdfs dfs -cat har:///archives/orders.har/o_42.csv
    archive job took 24 s -rw-r--r-- 3 hadoop supergroup 0 2026-10-21 16:39 /archives/orders.har/_SUCCESS -rw-r--r-- 3 hadoop supergroup 834555 2026-10-21 16:39 /archives/orders.har/_index -rw-r--r-- 3 hadoop supergroup 388 2026-10-21 16:39 /archives/orders.har/_masterindex -rw-r--r-- 3 hadoop supergroup 338894 2026-10-21 16:39 /archives/orders.har/part-0 1 10000 338894 har:///archives/orders.har order_id,item,amount 42,chai,20
    The archive job (a MapReduce job, here in local mode) packed all data into one part-0 file plus an index. Through har:// the 10,000 names still exist and can be read individually.

  6. Delete the originals and check the NameNode

    hdfs dfs -rm -r -skipTrash /small
    removed /small NameNode after HAR, without /small: FilesTotal 49 BlocksTotal 35
    From over 10,000 files and blocks back to 49 and 35: the archive costs the NameNode 4 files. The trade-off: archives are immutable, and each read first consults the index.

A compaction or archive job must finish and be verified before deleting the originals, and readers must be switched to the new location. Delete first and a failed job means lost data.

6 Real-world use

Small files at work

1. Nightly compaction of streaming data

Streaming jobs write small files all day for freshness; a nightly Spark or table-format job rewrites yesterday's partitions into files of a few hundred MB.

Stream: many small files→Compaction job→Few large files

2. Monitoring average file size

Platform teams scan the namespace (from fsimage with the Offline Image Viewer, Lesson 5.4) to rank folders by file count and average size, and ask the owners of the worst offenders to fix their writers.

fsimage → oiv→Files per folder→Owners fix writers

3. Archiving old logs and documents

Years of small log or document files that must stay individually retrievable are packed into HAR archives (or containers) so they stop costing NameNode memory.

Old small files→hadoop archive→har:// access

4. IoT and per-event uploads redesigned

Systems that once wrote one file per sensor reading switch to a message queue (Kafka) and write hourly files per device group, cutting file counts by orders of magnitude.

Per-event files→Kafka + batching→Hourly files

Simplified; organisations differ in tools and policies.

7 Run the code

Count the NameNode's work for small and big files

This model counts NameNode objects (files + blocks), NameNode calls and map tasks for the same data stored as many small files or a few big ones. The cost per object comes from the common rule of thumb of about 150 bytes of heap.

import math
BLOCK = 128 * 1024 * 1024
HEAP_PER_OBJECT = 150                       # bytes, rule of thumb

def cost(total_bytes, n_files):
    size = total_bytes / n_files
    blocks_per_file = max(1, math.ceil(size / BLOCK))
    objects = n_files * (1 + blocks_per_file)
    calls = n_files * (2 + blocks_per_file)   # create + complete + addBlock per block
    tasks = n_files * blocks_per_file         # about one split per block (one per small file)
    return objects, calls, tasks, objects * HEAP_PER_OBJECT

data = 338_894
for n in [10_000, 1]:
    o, c, t, heap = cost(data, n)
    print(f"{n:>6} files: {o:>6} objects, {c:>6} NameNode calls, {t:>6} map tasks, ~{heap / 1024:.0f} KB heap")
10000 files: 20000 objects, 30000 NameNode calls, 10000 map tasks, ~2930 KB heap 1 files: 2 objects, 3 NameNode calls, 1 map tasks, ~0 KB heap
  • objects = n_files * (1 + blocks_per_file)Each file is at least two objects: the file and its block. Our lab: +10,000 files and +10,000 blocks.
  • calls = n_files * (2 + blocks_per_file) # create + complete + addBlock per blockEach file needs its own create, addBlock and complete calls, the reason 10,000 uploads took 281 s.
  • tasks = n_files * blocks_per_file # about one split per block (one per small file)Frameworks create about one split per file: 10,000 tiny tasks, mostly start-up overhead.

Interview and viva questions

What is the small files problem in Hadoop?

When data is stored as many files much smaller than the block size, the NameNode must keep an object in memory for each file and block, handle separate RPCs for each, and jobs create a task per file. Memory, NameNode load and job overhead grow with the number of files, not the amount of data, which limits scalability and performance.

How do you solve the small files problem?

Prevent it by writing larger files (batching, sensible streaming intervals, fewer reducers). Clean up existing data with compaction jobs that rewrite small files into large ones, Hadoop Archives (HAR) for rarely accessed data, or container formats like SequenceFile/Avro/Parquet. Use CombineFileInputFormat to reduce task counts when reading.

What is a Hadoop Archive (HAR)?

An archive created by the hadoop archive command (a MapReduce job) that packs many files into a few large part files plus index files. The original paths remain readable through the har:// file system, while the NameNode stores only the archive's few files. HAR files are immutable.

Do small files waste DataNode disk space in HDFS?

Not in the way local file systems do: an HDFS block replica only occupies the bytes it contains. In our lab, 10,000 small files and one big file used the same raw bytes. The waste is in NameNode memory, RPC load and job overhead.

What file size should data in HDFS have?

As a guideline, hundreds of MB to a few GB per file: at least around the block size (128 MB) and big enough that jobs have reasonably sized splits, while not so big that a single file limits parallelism (for non-splittable formats).

print(f"{files * 2:,} objects -> {files * 2 * 150 / 1024**3:.1f} GB")
87,600,000 objects -> 12.2 GB

How it works: 8.76 crore objects, about 12 GB of heap from a single application.

P8Advanced

Compaction planner

Given partition sizes (MB) and file counts, plan how many output files each partition needs at a 256 MB target, and how many objects are saved.

Input
3 partitions
Expected output
dt=2026-10-19: 2880 -> 22 files
dt=2026-10-20: 2880 -> 24 files
dt=2026-10-21: 1500 -> 2 files
objects saved: 14424
Show solution and explanation 
import math
parts = {"dt=2026-10-19": (5400, 2880), "dt=2026-10-20": (6100, 2880), "dt=2026-10-21": (300, 1500)}
saved = 0
for p, (mb, files) in parts.items():
    out = max(1, math.ceil(mb / 256))
    saved += (files - out) * 2
    print(f"{p}: {files} -> {out} files")
print("objects saved:", saved)
dt=2026-10-19: 2880 -> 22 files dt=2026-10-20: 2880 -> 24 files dt=2026-10-21: 1500 -> 2 files objects saved: 14424

How it works: 22 + 24 + 2 output files; about 14,424 objects saved. Real compaction jobs also respect sort order and table formats.

Real-world scenario questions (asked in company interviews)

The small files problem is one of the most asked Hadoop interview topics, from freshers to architects.

HDFS · basicsFresher

“Why is HDFS bad at small files?”

Almost guaranteed in a Hadoop interview.

The interviewer is checking: NameNode memory and task overhead.

Show a strong answer
  • Every file and block is an object in NameNode RAM (~150 bytes each); millions of tiny files exhaust the heap.
  • Each file means separate NameNode calls and DataNode connections, and one map task per file.
  • Fixes: bigger files at source, compaction, HAR or SequenceFiles, CombineFileInputFormat.
Streaming · designExperienced

A Spark Streaming job writes 50,000 files an hour

Analysts' queries on the output table get slower each week; the NameNode heap keeps growing.

The interviewer is checking: write-side and cleanup-side fixes.

Show a strong answer
  • Reduce output partitions per micro-batch (coalesce) and increase the trigger interval if freshness allows.
  • Use a table format (Delta/Iceberg/Hudi) and schedule compaction (OPTIMIZE / rewrite) for closed partitions.
  • Monitor average file size per partition and alert when it drops.
Operations · cleanupExperienced

Find the folders causing the most NameNode load

The cluster has 40 crore objects; you must find who owns them without hammering the NameNode.

The interviewer is checking: offline analysis.

Show a strong answer
  • Fetch the latest fsimage (hdfs dfsadmin -fetchImage) and convert it with the Offline Image Viewer to a delimited file.
  • Aggregate by folder: file count, total size, average size; rank by file count with small average size.
  • Work with owners: compaction or HAR for old data, writer fixes for new data, name quotas on landing folders.
Concepts · trade-offsFresher

“HAR or SequenceFile?”

A follow-up after you list solutions.

The interviewer is checking: when each fits.

Show a strong answer
  • HAR keeps the original paths readable through har:// with no code change for readers; good for archives. It is immutable and reading has index overhead.
  • SequenceFile packs files as key-value records (name → bytes); efficient and splittable for MapReduce, but readers must use the container.
  • For tabular data, compaction into Parquet is usually better than both.
