Move the code, not the data

The single most important idea behind Hadoop fits in five words: move the code, not the data. This lesson shows why with real numbers (a day of copying versus minutes of processing), how Hadoop uses block locations to send each task to a node that already holds its data, what node-local, rack-local and off-rack mean, and how to check locality in a real job. Then switch locality off in the playground and watch the network fill up.

2 Definition

Data locality: move the code, not the data

Formal definition (write this in exams)

Data locality is the principle of running a computation on, or as close as possible to, the node where its input data is stored, instead of transferring the data across the network to the computation. In Hadoop, the scheduler uses the block locations reported by HDFS to place each task on a node that holds a replica of its input block (node-local or data-local); if none is free, on another node in the same rack (rack-local); and only as a last resort elsewhere (off-rack). This minimises network traffic, which is usually the scarcest resource in a cluster.

In simple words

Data is huge and the network is slow, but programs are tiny. So Hadoop sends the program to the machines that already have the data, and each machine works on what is on its own disks. Only small results travel over the network.

Coming from Big Data Fundamentals? Its lesson Distributed computing basics introduced “move the program, not the data” as a general idea. Here you will see exactly how Hadoop does it: block locations, node-local and rack-local tasks, and the counters that prove it.

Words you'll meet in this lesson

Data localityRunning a task where its data already is.
Node-local (data-local)The task runs on a node that holds a replica of its block. No network needed for input.
Rack-localThe task runs on another node in the same rack. Data crosses only the rack switch.
Off-rackThe task runs in a different rack. Data crosses the shared core network.
Input splitThe piece of input one map task processes; usually one HDFS block.
Delay schedulingWaiting a short time for a slot on a node with the data, rather than starting the task somewhere else at once.
Network distanceHadoop's measure of “how far”: 0 same node, 2 same rack, 4 other rack.
Short-circuit readWhen the task is on the same node as the block, it can read the file directly from local disk, skipping the DataNode network path.

Locality at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The census enumerator

  • India's census does not bring every family to one office to be counted.
  • It sends enumerators (the “program”) to every area. Each one counts the families there (the “data”).
  • Only the totals travel back to the district office, then the state, then Delhi.
  • Moving people would take forever; moving a few counters and some forms is easy. Hadoop works the same way.

Intermediate How Hadoop places tasks near the data

  • When a job starts, it asks the NameNode for the locations of every input block (each block has 3 replicas, so 3 candidate nodes).
  • The ApplicationMaster asks YARN for containers on those nodes. If one of them has a free slot, the map task runs there: node-local.
  • If all three are busy, YARN may wait briefly (delay scheduling), then try a node in the same rack, then anywhere.
  • After the job, the counters show how well it went, for example Data-local map tasks=118 and Rack-local map tasks=10.
  • Three replicas help locality too: three places a task could run locally instead of one.

Advanced Where locality breaks down, and the modern view

  • Shuffle can't be local: map outputs must travel to the reducers. Locality saves the input read, not the shuffle. Combiners (Module 9) shrink what is shuffled.
  • Small files: thousands of tiny blocks mean thousands of tiny tasks; scheduling overhead dominates (Module 7).
  • Hot spots: if everyone reads the same popular file, its 3 holders are overloaded. Raise replication for such files.
  • Cloud object storage: with data in S3/GCS/ADLS and compute on separate VMs, there is no node-local option. It works because cloud data-centre networks are very fast and storage is built for parallel reads. Many teams now accept this trade: cheaper, elastic compute in exchange for less locality.
  • Spark uses the same idea through “preferred locations” for each partition, and also caches data in memory on the executors.

Exam tip: “Explain data locality in Hadoop” is a favourite question. Give the definition, the three levels (node-local → rack-local → off-rack), why it matters (network is the bottleneck; code is small, data is big), and how HDFS block locations and replication make it possible.

Ways systems put compute near data

Co-located storage and compute

Every worker runs both a DataNode and a NodeManager, so the CPU sits next to the disks. Classic on-premises Hadoop.

Hadoop default

Locality-aware scheduling

The scheduler is told where each block is and prefers those nodes, with delay scheduling to wait for a local slot.

YARN, Spark

Push filters down

Ask the storage to drop rows and columns early (for example Parquet column pruning), so less data is read and moved at all.

Read less

Combine before sending

Sum or count locally first, then send only the partial results. The MapReduce combiner does this.

Send less

Disaggregated (cloud)

Storage and compute are separate services. Locality is traded for elasticity, helped by very fast networks.

Modern cloud

You can check locality for any finished MapReduce job: open it in the JobHistory web UI or run mapred job -status <job-id> and look at the job counters. If most map tasks are not data-local, look for busy nodes, a misconfigured rack script, or too few replicas.

4 Step by step

How Hadoop sends one map task to its data

  1. The job asks: where is the input?

    block_locations = {               # what the NameNode answers
    "blk_1": ["dn1", "dn4", "dn5"],
    "blk_2": ["dn2", "dn4", "dn6"],
}
print(block_locations["blk_1"])
    ['dn1', 'dn4', 'dn5']
    The client computes the input splits (normally one per block) and records the nodes that hold each one. This list travels with the job.

  2. The ApplicationMaster asks for containers on those nodes

    For the task of blk_1, it asks YARN: “a container on dn1, dn4 or dn5, or failing that, on /rack1 or /rack2.”

    YARN resource requests can name specific hosts and racks. The scheduler tries to satisfy the most local one first.

  3. Only the program travels

    The job jar (say 50 KB) and the configuration are copied to the chosen node, and the task JVM starts there.

    Hadoop puts job files in HDFS and each NodeManager downloads them once per job, shared by all tasks on that node. Even with 1,000 tasks, this is tiny compared with the input data.

  4. The task reads its block from local disk

    The map task opens blk_1. Because dn1 itself holds a replica, the HDFS client reads it from dn1's disk.

    With short-circuit local reads enabled, the task reads the block file straight from disk without going through the DataNode's network socket, which is faster still.

  5. Only small results leave the node

    The map task writes its output (for example counts per city) to dn1's local disk. Reducers fetch only these small outputs.

    128 MB of logs might become a few KB of counts. That is the shuffle: the only big network step of a MapReduce job, and much smaller than moving the input.
5 See it happen

Same report, two ways: what Kabir sees, and what crosses the network

First the old way (copy all data to one server), then the Hadoop way (send the program to the data). Left: Kabir's terminal. Right: what moves across the cluster.

Move the data vs move the code 6 steps
What you see
  1. Old way: Kabir's script copies the week's 10 TB of logs from 40 servers to one reporting server. The estimate says over 21 hours.
  2. Next morning the copy finishes and counting takes under an hour. About 22 hours in total, almost all of it moving data.
  3. Hadoop way: the logs already sit in HDFS on the 40 nodes. Kabir submits a small job jar. 10 TB in 128 MB blocks gives 81,920 input splits.
  4. Thousands of map tasks run at the same time across the cluster, each on its own block.
  5. The counters show that about 97% of map tasks were data-local and the rest rack-local. The job takes 41 minutes.
  6. Same data, same servers. Moving the code instead of the data turned a day into minutes. (Times are illustrative.)
Behind the screen
  1. The old way pulls every node's data through the rack switches and the core switch into one server. All links fill up.
  2. For hours the network is the bottleneck. The report server's CPU mostly waits, and other jobs suffer too.
  3. The Hadoop way: the job jar (tens of KB) is sent to the nodes that hold the blocks. That is all that crosses the network at the start.
  4. Each node's map tasks read the blocks on its own disks, all nodes at once. No input data crosses the core switch.
  5. When a node's slots are busy, a task may run on a neighbour in the same rack (rack-local). Data crosses only the rack switch.
  6. The only big network step is the shuffle of map outputs, which are tiny here (counts per city).

6 Real-world use

Where moving the code wins

1. Log analysis

Web and app servers write billions of log lines a day into HDFS. Counting errors, sessions or orders per city runs where the logs are stored; only the totals move.

Logs in HDFS→Map tasks on each node→Small totals

2. Scanning transactions for fraud rules

A bank re-checks months of card and UPI transactions against new fraud rules. Each node filters its own blocks and sends back only the suspicious rows, a tiny fraction of the data.

All transactions→Filter where stored→Few suspicious rows

3. Columnar formats: move less from disk too

Hive and Spark queries on Parquet or ORC files read only the columns a query needs and skip blocks whose min/max values can't match. Locality cuts network; columnar formats cut disk reads (Module 10).

Query→Read needed columns→Less I/O

4. Cloud: when locality is given up on purpose

Many companies keep data in cloud object storage and spin up compute clusters per job. There is no node-local read, but the cloud network is fast and the cluster can be deleted afterwards. Knowing locality helps you understand that trade-off.

Object storage→Fast network reads→Elastic compute

5. Tuning a slow job

When a job is slow, one of the first things an engineer checks is the locality counters. A sudden drop in data-local tasks often points to a full cluster, a broken rack script, or data written with replication 1.

Slow job→Check counters→Fix placement

7 Run the code

Move the data or move the code? Do the maths

Compare the time to bring all the data to one machine with the time to send a small program to every node and let each read its own share in parallel. Then try the challenges, including a tiny locality-aware scheduler.

data_tb = 10
nodes = 40
network_gbps = 10          # link into the single reporting server
local_read_gb_s = 1.0      # each node, many disks in parallel
jar_kb = 50

move_data_h = data_tb * 1024 * 8 / network_gbps / 3600
move_code_s = jar_kb * 8 / 1024 / 1024 / network_gbps
local_min = data_tb * 1024 / nodes / local_read_gb_s / 60

print(f"Move the data : {move_data_h:.1f} hours of transfer")
print(f"Move the code : {move_code_s:.5f} s to send the jar")
print(f"Then each node reads its share in {local_min:.1f} minutes")
Move the data : 2.3 hours of transfer Move the code : 0.00004 s to send the jar Then each node reads its share in 4.3 minutes
  • move_data_h = data_tb * 1024 * 8 / network_gbps / 3600TB → GB (× 1024), bytes → bits (× 8), ÷ link speed in Gbit/s = seconds, ÷ 3600 = hours.
  • move_code_s = jar_kb * 8 / 1024 / 1024 / network_gbpsThe same formula for a 50 KB jar: KB → Gbit is ÷ 1024 ÷ 1024 after × 8.
  • local_min = data_tb * 1024 / nodes / local_read_gb_s / 60Each node reads only its own 1/40th of the data, and all nodes read at the same time.

Interview and viva questions

What is data locality and why is it important in Hadoop?

Data locality means running computation on the node where the data is stored. In Hadoop, map tasks are scheduled on DataNodes that hold a replica of their input split. It matters because network bandwidth, especially between racks, is much more limited than the combined disk bandwidth of the cluster. Moving a small program to many nodes avoids moving terabytes of data.

What are the levels of data locality?

Node-local (data-local): the task runs on a node with a replica. Rack-local: the task runs on another node in the same rack, reading over the rack switch. Off-rack: the task runs in a different rack, reading through the core network. The scheduler prefers them in that order.

How does the scheduler know where the data is?

When a job is submitted, the input format computes splits and asks the NameNode for the block locations of each split. The ApplicationMaster includes these hosts and racks in its container requests to the ResourceManager, which tries to allocate containers on those nodes.

What can cause poor data locality?

A busy or full cluster (no free slots on the right nodes), very small files or uneven block placement, replication factor 1, a wrong or missing rack topology script, newly added empty nodes before running the balancer, or reading data that is not in HDFS at all (for example cloud object storage).

Does Spark use data locality?

Yes. Spark records preferred locations for each partition (for HDFS input, the block locations) and its scheduler waits a short time (spark.locality.wait) for a slot at the best locality level: process-local, node-local, rack-local, then any.

P3Easy

Classify placements

A task's block is on dn2 (rack r1). Classify running the task on dn2, dn3 (r1) and dn7 (r2).

Input
block on dn2 · rack {dn2: r1, dn3: r1, dn7: r2}
Expected output
dn2 node-local
dn3 rack-local
dn7 off-rack
Show solution and explanation 
rack = {"dn2": "r1", "dn3": "r1", "dn7": "r2"}
for n in ["dn2", "dn3", "dn7"]:
    kind = "node-local" if n == "dn2" else "rack-local" if rack[n] == rack["dn2"] else "off-rack"
    print(n, kind)
dn2 node-local dn3 rack-local dn7 off-rack

How it works: Same node, same rack, other rack: the three levels of locality.

P4Medium

Closest replica to read

A client on dn6 must read a block whose replicas are on dn1, dn5 and dn9. Using Hadoop's distance (0, 2, 4), print the replica it should read.

Input
client dn6 · replicas dn1, dn5, dn9 · racks r1: dn1-dn4, r2: dn5-dn8, r3: dn9
Expected output
dn5
Show solution and explanation 
rack = {"dn1": "r1", "dn5": "r2", "dn6": "r2", "dn9": "r3"}
def dist(a, b):
    return 0 if a == b else 2 if rack[a] == rack[b] else 4
reps = ["dn1", "dn5", "dn9"]
print(min(reps, key=lambda r: dist("dn6", r)))
dn5

How it works: HDFS clients sort replicas by network distance and read the closest: dn5, in the same rack.

P6Medium

Network saved by locality

P8Business problem

Should the hot file get more replicas?

Real-world scenario questions (asked in company interviews)

Locality questions that interviewers use to separate people who have memorised definitions from people who understand clusters.

Analytics team · architectureFresher

“Let's copy the data to the BI server every night”

The BI team asks for the full 15 TB clickstream table to be copied from Hadoop to their reporting database every night, so their dashboards can query it. The dashboards show daily totals per city and product.

The interviewer is checking: do you apply “move the code, not the data” to a real request?

Show a strong answer
  • 15 TB a night over a 10 Gbps link is over 3 hours of a saturated network, and the BI database must store it all.
  • The dashboards need aggregates. Compute them on the cluster (Hive/Spark job) and export only the summary tables, probably a few GB.
  • If analysts need ad-hoc detail, let them query the cluster directly with Hive, Impala or Spark SQL, or a query engine like Trino that reads the data in place.

Avoid: agreeing to copy everything “because the BI tool needs it”.

Platform team · performance1–3 years

Data-local tasks dropped from 95% to 55%

Last month, jobs on the cluster were 95% data-local. This week they are 55% and the core switch uplinks are saturated. Nothing in the job code changed.

The interviewer is checking: can you list concrete causes of poor locality and how to verify each?

Show a strong answer
  1. New nodes added without balancing: data sits on old nodes, but free slots are on new ones. Run the balancer.
  2. Rack script changed or broken: check hdfs dfsadmin -printTopology.
  3. Cluster busier: more concurrent jobs mean fewer free slots on the right nodes; review queue capacities and delay-scheduling settings.
  4. Data written with replication 1 (to save space) leaves only one local candidate per block. Check with hdfs fsck.
  5. Input moved to object storage or another cluster, where node-local reads are impossible.

Avoid: “Buy a faster core switch” before finding the cause.

Cloud migration · design3+ years

“If locality is so important, why does everyone use S3?”

During a migration discussion, a senior engineer argues against moving from on-prem HDFS to cloud object storage: “We'll lose data locality and everything will be slow.”

The interviewer is checking: do you understand that locality is a trade-off, not a law?

Show a strong answer
  • True: reads become network reads. But cloud data-centre networks are very fast and object stores serve many parallel reads well.
  • In return: compute and storage scale separately, clusters can be created per job and deleted, and storage is cheap and highly durable.
  • Mitigations: columnar formats (read less), partitioning and predicate pushdown, caching layers, and right-sized instances with high network bandwidth.
  • Benchmark the key jobs on both before deciding.

Avoid: treating either side as always right. Measure the workload.

Any company · conceptsFresher

Explain data locality to a non-technical manager

Your manager, who is not technical, asks why the Hadoop cluster can process 10 TB in under an hour when copying 10 TB to one server takes a whole day.

The interviewer is checking: can you explain a core idea simply and correctly?

Show a strong answer

“Imagine a census. Bringing every family to one office would take forever. Instead, we send counters to every area, they count locally at the same time, and only the totals travel back. Our cluster does the same: the data already lives on 40 machines, so we send the small counting program to each machine, all 40 work in parallel on their own part, and only small results come back.”

Avoid: jargon such as “node-local container allocation” with a non-technical audience.
