Hadoop architecture: HDFS, YARN, MapReduce and Common

Hadoop is not one program. It is a team of long-running Java processes, called daemons, spread across master and worker machines, held together by four XML configuration files. This lesson opens up a real cluster layer by layer: which daemon runs where, what it does, how it talks to the others and on which port, so that the output of jps and the web UIs make sense at a glance.

2 Definition

Hadoop's architecture, daemon by daemon

Formal definition (write this in exams)

A Hadoop cluster is a layered, master–worker system of long-running Java processes (daemons). The storage layer (HDFS) consists of a NameNode, which manages the namespace and block map, and DataNodes, which store blocks; with High Availability it adds a standby NameNode, JournalNodes and ZKFailoverControllers. The resource layer (YARN) consists of a ResourceManager, which allocates containers cluster-wide, and NodeManagers, which launch and monitor containers on each worker. The processing layer consists of applications such as MapReduce, each run by its own ApplicationMaster; the JobHistory Server keeps records of finished MapReduce jobs. Hadoop Common provides the shared libraries, RPC, configuration and security on which all daemons are built. Daemons communicate through RPC and periodic heartbeats and are configured through core-site.xml, hdfs-site.xml, yarn-site.xml and mapred-site.xml.

In simple words

Hadoop is not one program but a team of programs. On the master machines run the “managers”: the NameNode (knows where every file block is) and the ResourceManager (decides who gets CPU and memory). On every worker run two “staff members”: a DataNode (stores blocks) and a NodeManager (runs tasks). They talk to each other all the time, and four XML files tell each of them where the others are.

The architecture at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A hospital

  • The records office (NameNode) knows which file is in which cupboard, but holds no files itself.
  • The cupboards in every ward (DataNodes) hold the actual files, with copies in other wards.
  • The bed manager (ResourceManager) decides which patient gets which bed and how many nurses.
  • Each ward's in-charge (NodeManager) sets up the beds the bed manager approved and reports back.
  • Each patient's doctor (ApplicationMaster) plans that one patient's treatment and asks for beds as needed.
  • The hospital rule book (Common + config files) is the same in every ward.

Intermediate How the daemons talk to each other

  • DataNode → NameNode: registration, heartbeats every 3 s, block reports. The NameNode answers with commands (copy, delete).
  • NodeManager → ResourceManager: heartbeats with free memory/CPU and container status. The RM answers with containers to start or kill.
  • Client → NameNode: “create this file”, “where are the blocks of that file?”. Client → DataNodes: the actual bytes. The NameNode never carries file data.
  • Client → ResourceManager: submit an application. ApplicationMaster → RM: ask for containers. AM → NodeManagers: start containers.
  • Reducers → NodeManagers' shuffle service: fetch map outputs over HTTP.

Advanced Design details that matter in production

  • Masters are out of the data path: clients read and write blocks directly from DataNodes, so the NameNode handles only small metadata calls. That's how one NameNode serves thousands of nodes.
  • Control vs data traffic: RPC (small, frequent) and data transfer (large, streaming) use different ports and can be tuned separately.
  • Co-location: DataNode and NodeManager on the same worker make data locality possible. Separating them (compute-only nodes) is possible but loses locality.
  • Same configuration everywhere: the XML files are usually managed centrally (Ambari, Cloudera Manager, Ansible) and pushed to every node; a mismatch is a classic source of strange errors.
  • Each daemon has its own log under $HADOOP_HOME/logs (for example hadoop-<user>-namenode-<host>.log), which is the first place to look when something fails.

4 Step by step

Bringing a cluster up, daemon by daemon

  1. Every node gets the same configuration

    import xml.etree.ElementTree as ET
xml = """<configuration><property><name>fs.defaultFS</name>
<value>hdfs://nn1:8020</value></property></configuration>"""
for p in ET.fromstring(xml).iter("property"):
    print(p.findtext("name"), "=", p.findtext("value"))
    fs.defaultFS = hdfs://nn1:8020
    Every Hadoop configuration file is a list of <property> name–value pairs. Every daemon and client reads them at start-up, so they all agree on where the masters are.

  2. Start HDFS: the NameNode first

    The admin runs start-dfs.sh. The NameNode loads its saved metadata (fsimage + edit log) and waits in safe mode.

    The NameNode knows the files and their blocks, but not yet where the blocks are. That information is never saved; it comes fresh from the DataNodes.

  3. DataNodes start and report

    On each worker a DataNode starts, registers with the NameNode and sends a block report.

    When enough blocks have been reported (99.9% by default), the NameNode leaves safe mode and allows writes. Module 5 explains safe mode in detail.

  4. Start YARN

    The admin runs start-yarn.sh. The ResourceManager starts; each NodeManager registers with how much memory and how many vcores it offers.

    The RM now knows total cluster capacity, for example 40 nodes × 192 GB. Its web UI on port 8088 shows it.

  5. Start the JobHistory Server, then check

    mapred --daemon start historyserver
jps
    On a single-machine (pseudo-distributed) test cluster, jps should list NameNode, DataNode, SecondaryNameNode, ResourceManager, NodeManager and JobHistoryServer. If one is missing, its log file says why. You'll do this yourself in Module 4.
5 See it happen

A cluster starting up: what the admin sees, and which daemons appear

Follow a small cluster (one master, three workers) from power-on to ready. Left: the admin's terminal. Right: the daemons on each machine.

From power-on to ready 6 steps
What you see
  1. Before start-up, jps shows only itself: no Hadoop daemons are running.
  2. start-dfs.sh starts the NameNode on the master, a DataNode on each host in the workers file, and the Secondary NameNode.
  3. The NameNode starts in safe mode (read-only) until enough DataNodes have reported their blocks, then leaves it.
  4. start-yarn.sh starts the ResourceManager and a NodeManager on every worker.
  5. The JobHistory Server starts. jps on the master now lists all master daemons (PIDs differ on every machine).
  6. The web UIs confirm 3 live DataNodes and 3 active NodeManagers. Jobs can run.
Behind the screen
  1. Four machines are powered on, but no Hadoop daemon is running yet.
  2. HDFS starts: the NameNode and Secondary NameNode on the master, one DataNode per worker.
  3. Each DataNode registers and sends a block report. The NameNode builds its map of block locations in memory.
  4. YARN starts: the ResourceManager on the master and a NodeManager next to each DataNode. Each NodeManager tells the RM how much memory and CPU it can offer.
  5. The JobHistory Server joins the master. Typical small layout: 4 daemons on the master, 2 on each worker.
  6. Both layers are running. Clients can now store files and submit jobs.

6 Real-world use

Architecture knowledge in daily work

1. First check in any incident

When jobs fail on one node, an engineer logs in and runs jps. If the NodeManager is missing, the node offers no containers; if the DataNode is missing, its blocks are unavailable. The daemon's log file then explains why.

Alert→jps + daemon log→Restart or fix

2. Firewall and security reviews

Security teams ask exactly which ports each node needs open. The daemon-and-port table in this lesson is what platform engineers hand them, with web UIs restricted to admin networks.

Port list→Firewall rules→Only needed ports open

3. Cluster managers show the same picture

Management tools like Apache Ambari or Cloudera Manager display every host with its roles (NameNode, DataNode, NodeManager…), their health and their configuration, the same architecture you learned today with a dashboard on top.

Hosts→Roles per host→Health + config

4. Connecting tools to the cluster

Spark, Hive, Airflow and BI tools need the cluster's core-site.xml and hdfs-site.xml (and yarn-site.xml to submit jobs). Copying these files to an edge node is how new tools are connected.

Config files→Client tool→Reads HDFS, submits to YARN

5. Capacity and health dashboards

Monitoring systems scrape metrics from each daemon (NameNode heap, DataNode disk, NodeManager memory) and graph them per layer, so teams see whether storage or compute is running out.

Daemon metrics→Monitoring→Alerts per layer

Examples are simplified. Port numbers are Apache defaults; distributions may differ.

7 Run the code

Read a Hadoop configuration file

Every Hadoop setting lives in XML files like this hdfs-site.xml. This program reads it the way Hadoop does and turns it into a dictionary. Then try the challenges: find the NameNode, plan which daemons go on which host, and catch a configuration mistake.

import xml.etree.ElementTree as ET

hdfs_site = """<configuration>
  <property><name>dfs.replication</name><value>3</value></property>
  <property><name>dfs.namenode.name.dir</name><value>/data/nn</value></property>
  <property><name>dfs.datanode.data.dir</name><value>/data/1/dn,/data/2/dn</value></property>
  <property><name>dfs.blocksize</name><value>134217728</value></property>
</configuration>"""

conf = {p.findtext("name"): p.findtext("value")
        for p in ET.fromstring(hdfs_site).iter("property")}

print("Replication :", conf["dfs.replication"])
print("Block size  :", int(conf["dfs.blocksize"]) // 1024 // 1024, "MB")
print("DataNode disks:", conf["dfs.datanode.data.dir"].split(","))
Replication : 3 Block size : 128 MB DataNode disks: ['/data/1/dn', '/data/2/dn']
  • ET.fromstring(hdfs_site).iter("property")Parse the XML and visit every <property> element, as Hadoop's Configuration class does.
  • conf = {p.findtext("name"): p.findtext("value") ...}A dictionary comprehension: property name → value. All values are strings.
  • int(conf["dfs.blocksize"]) // 1024 // 1024134217728 bytes = 128 MB, the Hadoop 2/3 default.

Check yourself

Quick revision

Lesson 3.1 in one screen

  • Hadoop = a team of Java daemons, not one program.
  • HDFS: NameNode (metadata, 8020 RPC, 9870 UI) + DataNodes (blocks, 9866/9867/9864).
  • HA helpers: JournalNodes (8485), ZKFC (8019), ZooKeeper (2181). Non-HA: Secondary NameNode (9868).
  • YARN: ResourceManager (8032/8030/8031, UI 8088) + NodeManagers (UI 8042, shuffle 13562).
  • MapReduce: one ApplicationMaster per job in a container; JobHistory Server (19888) for finished jobs.
  • Worker = DataNode + NodeManager (locality). Masters stay out of the data path.
  • Config: core-site.xml (fs.defaultFS), hdfs-site.xml, yarn-site.xml, mapred-site.xml, workers.
  • Start order: start-dfs.sh → safe mode exit → start-yarn.sh → history server. Check with jps.

Interview and viva questions

What are the daemons in a Hadoop cluster?

HDFS: NameNode, DataNodes, and either a Secondary NameNode (non-HA) or a standby NameNode with JournalNodes and ZKFailoverControllers (HA). YARN: ResourceManager and NodeManagers (optionally a Timeline Server). MapReduce: a per-job MRAppMaster running in a container and the JobHistory Server. ZooKeeper is a separate service used for HA.

Why does the NameNode not handle file data?

Keeping the master out of the data path means it only answers small metadata requests (open, create, block locations), while the large data transfers happen directly between clients and DataNodes in parallel. This lets one NameNode serve thousands of DataNodes without becoming a bandwidth bottleneck.

What is in core-site.xml, hdfs-site.xml, yarn-site.xml and mapred-site.xml?

core-site.xml: settings shared by all components, most importantly fs.defaultFS. hdfs-site.xml: HDFS settings such as dfs.replication, dfs.blocksize, NameNode and DataNode directories, HA settings. yarn-site.xml: ResourceManager address, NodeManager resources, aux-services, scheduler. mapred-site.xml: mapreduce.framework.name=yarn and MapReduce tuning such as memory and the number of reducers.

How do you check whether Hadoop daemons are running?

Run jps on each node to see the Java processes; use hdfs dfsadmin -report for live and dead DataNodes; yarn node -list for NodeManagers; and open the web UIs (NameNode 9870, ResourceManager 8088). If a daemon is missing, read its log in $HADOOP_HOME/logs.

Why do DataNode and NodeManager run on the same machine?

So that tasks launched by the NodeManager can read blocks stored by the local DataNode. This co-location is what makes data locality, and therefore Hadoop's performance, possible.

P8Business problem

Master heap budget

Expected output

Year 2: ~244 GB NameNode heap

Real-world scenario questions (asked in company interviews)

Architecture questions in interviews are usually practical: what runs where, how they talk, and what you check when something breaks.

Operations · troubleshootingFresher

Jobs never use one of the workers

The HDFS UI shows 10 live DataNodes, but the YARN UI shows only 9 active NodeManagers. Jobs never run tasks on worker w7.

The interviewer is checking: do you know that storage and compute are separate daemons on the same node?

Show a strong answer
  1. On w7, run jps: the DataNode is running but the NodeManager isn't (or it is unhealthy).
  2. Read the NodeManager log under $HADOOP_HOME/logs: common causes are a wrong yarn.resourcemanager.hostname, a full local disk (marked unhealthy), or a memory setting larger than the machine.
  3. Fix and start it: yarn --daemon start nodemanager, then confirm with yarn node -list.

Avoid: restarting the whole cluster for one missing daemon.

Any company · conceptsFresher

“Does all data go through the NameNode?”

The interviewer says: “If the NameNode is the master, surely every byte you read passes through it, right?”

The interviewer is checking: do you understand why masters stay out of the data path?

Show a strong answer
  • No. The client asks the NameNode only for metadata: which blocks make up the file and which DataNodes hold them.
  • The client then reads (or writes) the bytes directly from the DataNodes, choosing the closest replica.
  • This keeps the NameNode's work small and lets thousands of clients transfer data in parallel. The same is true of YARN: the ResourceManager hands out containers but never touches job data.

Avoid: drawing data arrows through the NameNode in an architecture diagram.

Platform team · configuration1–3 years

Spark on the edge node can't find HDFS

A data scientist installs Spark on a new edge node. spark.read.csv("/data/sales") fails with “File does not exist” even though hdfs dfs -ls /data/sales works on other nodes.

The interviewer is checking: do you know how clients find the cluster?

Show a strong answer
  • Spark doesn't know the cluster: without core-site.xml, the default file system is the local disk (file:///), so /data/sales is looked up locally.
  • Copy the cluster's core-site.xml, hdfs-site.xml and yarn-site.xml to the edge node and point HADOOP_CONF_DIR (and Spark) at them, or use a full URI like hdfs://nn1:8020/data/sales.
  • In a managed cluster, add the node as a “gateway” host so the manager keeps the client configuration in sync.

Avoid: copying the data to the edge node.

Infrastructure · design1–3 years

Put the NameNode and ResourceManager on one server?

To save money on a new 30-node cluster, someone proposes running the NameNode, ResourceManager, JobHistory Server and also a DataNode on one master server.

The interviewer is checking: do you understand the resource needs and failure impact of master daemons?

Show a strong answer
  • For small clusters, NameNode + ResourceManager + JobHistory on one well-equipped master is common and acceptable.
  • But not a DataNode/NodeManager on the master: tasks would compete with the NameNode for memory and disk, and a runaway task could slow or crash the master.
  • Separate the masters as the cluster grows (NameNode heap needs grow with files), and add HA (a second master, JournalNodes on three machines) when uptime matters.

Avoid: treating master servers like ordinary workers.
