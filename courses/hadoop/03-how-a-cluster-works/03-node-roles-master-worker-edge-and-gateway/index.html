Node roles: master, worker, edge and gateway

Every machine in a Hadoop cluster has a role, and respecting the roles is what keeps a cluster healthy. This lesson explains master nodes (protected coordinators), worker nodes (storage and compute managed by YARN), edge or gateway nodes (where users and tools connect) and utility nodes (supporting services), what runs on each, what hardware they need, and how companies lay them out for clusters of 5, 50 and 500 machines.

1 The story

“Don't log in to the NameNode!”

On his third day, Kabir needs to run a quick script on the cluster. He finds the host name of the biggest, most powerful server, the NameNode, logs in to it, and starts a Python job that reads a large file into memory. Five minutes later the whole team's chat lights up: “HDFS is slow!”, “NameNode GC pauses!”, “Who is on nn1?” His lead calls him over, calm but firm.

Arjun Sir

Kabir, which machine did you use?

Kabir

The one with the most RAM… nn1. I thought it would be fastest.

Arjun Sir

It is the most important machine in the cluster. The NameNode keeps all of HDFS's metadata in its memory. Your script took memory and CPU from it, so it paused, and every user's reads and writes waited.

Riya

So where should he have run it?

Arjun Sir

On an edge node, the machine built for people. Every cluster has roles: masters that coordinate and must be protected, workers that store and compute and are managed by YARN, utility nodes for supporting services, and edge nodes where users and tools connect. Today you'll learn each role, what runs on it, and how companies lay them out for small and large clusters.

Kabir

And I'll never touch nn1 again.

2 Definition

Node roles in a Hadoop cluster

Formal definition (write this in exams)

Nodes in a Hadoop cluster are assigned roles according to the services they run. Master nodes host the coordinating daemons (NameNode and its standby, ResourceManager, JobHistory Server, and in HA setups JournalNodes and ZKFCs) and are provisioned for reliability. Worker nodes (historically “slave” nodes) host DataNodes and NodeManagers and provide the cluster's storage and compute capacity. Edge nodes (also called gateway or client nodes) host client libraries, configuration and tools, and are the controlled entry point for users and applications; they run no core daemons. Utility (management) nodes host supporting services such as ZooKeeper, the Hive Metastore and its database, HiveServer2, Oozie, security and cluster-management servers.

In simple words

Masters are the managers: few, important, protected. Workers are the staff: many, doing the storage and processing. Edge nodes are the reception desk where people come in to submit work. Utility nodes run the helper services everyone else depends on. Users only ever log in at reception.

Roles at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A hospital again

  • Masters = the records office and the bed manager. If they stop, everyone stops, so nobody else is allowed to use their desks.
  • Workers = the wards, where the actual work happens. There are many, and one can close for repairs.
  • Edge node = reception. Visitors come here, not into the records office or the operating theatre.
  • Utility = the pharmacy and the IT room: support services the whole hospital relies on.

Intermediate What runs where in a typical medium cluster

  • master1: active NameNode, ZKFC, JournalNode, ZooKeeper.
  • master2: standby NameNode, ZKFC, JournalNode, ZooKeeper, ResourceManager.
  • master3 / utility: JournalNode, ZooKeeper, standby ResourceManager, JobHistory Server, Hive Metastore + database, HiveServer2.
  • edge1–2: HDFS/YARN/Hive/Spark clients, Hue or Jupyter, scheduler workers; user logins.
  • worker1–N: DataNode + NodeManager (and, for HBase, a RegionServer).
  • The three JournalNodes and three ZooKeeper servers sit on three different machines so the cluster survives losing any one of them.

Advanced Why roles are kept separate

  • Blast radius: a user's runaway process on a master can pause the NameNode (long Java garbage-collection pauses) and stall the whole cluster.
  • Resource accounting: work on workers must go through YARN so it is counted, queued and limited. A script started by hand on a worker steals memory YARN thinks is free, and containers get killed.
  • Security: only edge nodes are reachable from the corporate network; masters and workers sit on a private cluster network. Users get Kerberos tickets on the edge node.
  • Upgrades and failures: workers are replaced like identical parts; masters are changed carefully, one at a time, with failover.
  • Cloud versions: managed services keep the same roles: Amazon EMR has a primary node, core nodes (HDFS + YARN) and task nodes (YARN only); Google Dataproc has master and worker nodes plus optional secondary workers.

Exam tip: For “Explain the types of nodes in a Hadoop cluster”, list master, worker (slave), edge/gateway and utility, the daemons on each, and one reason each is separated (masters protected, workers managed by YARN, edge as the controlled entry point). A small layout diagram earns full marks.

4 Step by step

Designing the roles for a 30-node cluster

  1. Decide what must be highly available

    TiffinGo's dashboards depend on HDFS all day, so they want NameNode and ResourceManager HA.

    HA means two NameNodes, two ResourceManagers, three JournalNodes and three ZooKeeper servers, spread over three machines so any one can fail.

  2. Place the masters

    masters = {
    "m1": ["NameNode (active)", "ZKFC", "JournalNode", "ZooKeeper"],
    "m2": ["NameNode (standby)", "ZKFC", "JournalNode", "ZooKeeper", "ResourceManager"],
    "m3": ["JournalNode", "ZooKeeper", "ResourceManager (standby)", "JobHistoryServer"],
}
print(sum(1 for roles in masters.values() if "JournalNode" in roles), "JournalNodes")
    3 JournalNodes
    Put m1, m2 and m3 on different racks and power feeds. The active NameNode gets the lightest load of other services.

  3. Add utility services

    Hive Metastore with its database and HiveServer2 go on a utility node (or on m3 in a small cluster).

    The metastore database holds every table definition: back it up and give it a standby, or every Hive and Spark SQL query stops.

  4. Add edge nodes

    Two edge nodes with the client configuration, Hive Beeline, spark-submit, Jupyter and the Airflow workers.

    Two, so users can keep working while one is patched. Only these two are reachable from the office network.

  5. Everything else is a worker

    total, masters, utility, edge = 30, 3, 1, 2
print(total - masters - utility - edge, "workers (DataNode + NodeManager)")
    24 workers (DataNode + NodeManager)
    The workers provide all storage and compute, so capacity planning (Lesson 1.3) is done on these 24, not on all 30.
5 See it happen

One Hive query: what Riya does on the edge node, and which role does what

Riya runs a SQL query from the edge node. Left: her screen. Right: the request travelling through each kind of node.

A query through every role 6 steps
What you see
  1. Riya logs in to edge1 and connects Beeline (the Hive client) to HiveServer2.
  2. She types a GROUP BY query on the orders table.
  3. The query is running. She sees only a progress message.
  4. Progress shows map and reduce tasks. They run somewhere on the cluster, not on her machine.
  5. The result table appears.
  6. From start to finish, Riya used only the edge node. Every other role worked on her behalf.
Behind the screen
  1. The edge node runs only the client (Beeline). It sends the query to HiveServer2 on the utility node over JDBC (port 10000 by default).
  2. HiveServer2 asks the Hive Metastore (also on the utility node, backed by a database) where the orders table lives in HDFS and what its columns are.
  3. It then talks to the masters: the NameNode for the files' block locations, the ResourceManager to start an ApplicationMaster for the query.
  4. Map and reduce tasks run in containers on the workers, mostly on the nodes holding the table's blocks.
  5. Results flow back through HiveServer2 to Riya's Beeline session on the edge node.
  6. Every role did one job. None of the work ran on the edge node or on a master.

6 Real-world use

Roles in real platforms

1. Cluster managers assign roles

In Cloudera Manager or Apache Ambari, an admin builds a cluster by assigning roles to hosts (“NameNode on m1”, “DataNode on all workers”, “Gateway on edge1”). The tool installs, configures and monitors each role.

Host list→Role assignment→Running cluster

2. Cloud clusters keep the same roles

Amazon EMR has a primary node (masters), core nodes (HDFS + YARN) and task nodes (YARN only, safe to remove). Google Dataproc has master and worker nodes, with optional secondary (preemptible) workers that add compute only.

Primary→Core (data + compute)→Task (compute only)

3. Data science on edge nodes

Analysts open Jupyter or Hue on an edge node and submit Spark or Hive work to YARN. Their notebooks never run heavy processing on the edge itself; the cluster does it.

Notebook on edge→spark-submit / Hive→Workers compute

4. Incident reviews

A common root cause in incident reports: “a user ran a script on a master” or “a manual process on workers exhausted memory, so YARN killed containers”. The fix is usually access control: logins only on edge nodes.

Outage→Root cause: wrong role→Restrict logins

5. Quorum services on separate machines

ZooKeeper and JournalNodes are always placed on three (or five) different machines and racks, so the majority survives a failure. Putting all three on one host is a classic design-review mistake.

3 hosts→Majority of 2→Survives 1 failure

Simplified. Exact role layouts differ by distribution and company.

7 Run the code

Plan the roles for a cluster

This program assigns roles to the machines of a cluster: three masters for HA, one utility node, two edge nodes, and workers for the rest. Then it prints the plan. Try the challenges to check a layout for mistakes.

def plan(total, ha=True):
    masters = 3 if ha else 1
    utility, edge = 1, 2 if total >= 20 else 1
    workers = total - masters - utility - edge
    roles = {}
    for i in range(1, masters + 1):
        roles[f"master{i}"] = "master"
    roles["util1"] = "utility"
    for i in range(1, edge + 1):
        roles[f"edge{i}"] = "edge"
    for i in range(1, workers + 1):
        roles[f"worker{i}"] = "worker"
    return roles

roles = plan(30)
summary = {}
for host, role in roles.items():
    summary[role] = summary.get(role, 0) + 1
print(summary)
{'master': 3, 'utility': 1, 'edge': 2, 'worker': 24}
  • masters = 3 if ha else 1High availability needs three machines for the JournalNode and ZooKeeper majorities; without HA, one master.
  • utility, edge = 1, 2 if total >= 20 else 1Tuple assignment: utility = 1, and edge is 2 for bigger clusters, 1 for small ones.
  • workers = total - masters - utility - edgeEvery remaining machine is a worker: storage and compute.

9 Quiz and revision

Check yourself

Quick revision

Lesson 3.3 in one screen

  • Master: NameNode(s), ResourceManager(s), JobHistory, JournalNodes, ZKFC. Few, reliable, protected.
  • Worker: DataNode + NodeManager. Many, identical, replaceable. All work goes through YARN.
  • Edge / gateway: client tools + configs, user logins, notebooks, schedulers. No core daemons.
  • Utility: ZooKeeper, Hive Metastore + DB, HiveServer2, Oozie, Ranger, cluster manager.
  • Quorum services (ZooKeeper, JournalNodes) on 3 or 5 different hosts; NameNodes on different racks.
  • Layouts: 1 node (learning) · small: 1 master + edge + workers · medium: 3 masters, utility, 2 edges · large: dedicated masters, federation.
  • Cloud: EMR primary / core / task; Dataproc master / primary workers / secondary workers.
  • Rule of thumb: users only on edge nodes.

Interview and viva questions

What is an edge node in Hadoop?

A machine that has the Hadoop client libraries, configuration files and tools (hdfs, yarn, hive/beeline, spark-submit, notebooks) but runs no core cluster daemons. It is the controlled entry point for users and applications: they log in there, interact with HDFS and submit jobs, while the work runs on the workers. It is often the only cluster host reachable from the corporate network.

What runs on master nodes?

The coordinating services: the active and standby NameNodes (with ZKFCs), JournalNodes for the shared edit log, the ResourceManager(s), the JobHistory Server, and often ZooKeeper. In non-HA clusters, the Secondary NameNode. Masters are sized for memory and reliability and protected from user workloads.

Why not run DataNodes on master nodes?

Storage and compute work on a master competes with the master daemons for memory, CPU and disk I/O, risking pauses or crashes that affect the whole cluster. It also makes masters harder to maintain, because taking one down would also remove data and compute capacity.

How many ZooKeeper servers should a cluster have?

An odd number, usually 3 for most clusters and 5 for large or critical ones, each on a different host and ideally on different racks. ZooKeeper needs a majority to operate, so 3 servers tolerate one failure and 5 tolerate two; 4 servers still tolerate only one.

How do node roles map to cloud services like EMR?

EMR's primary node runs the master services; core nodes run HDFS DataNodes and YARN NodeManagers; task nodes run only NodeManagers, so they can be scaled in and out freely. Dataproc similarly has master nodes, primary workers (HDFS + YARN) and optional secondary workers (compute only, often preemptible).

Real-world scenario questions (asked in company interviews)

Role questions are about judgement: where things should run, and what to do when someone breaks the rules.

Platform team · designFresher

Lay out roles for a 20-node cluster

You have 20 identical servers and the business wants HDFS to keep running even if one master fails. How do you assign roles?

The interviewer is checking: do you know which services need HA and how to place quorums?

Show a strong answer
  • 3 masters on different racks: active NameNode + ZKFC on m1, standby NameNode + ZKFC on m2, and JournalNode + ZooKeeper on all three; ResourceManager (and a standby) on m2/m3; JobHistory on m3.
  • 1 utility node for Hive Metastore + database and HiveServer2 (or on m3 if budget is tight).
  • 1–2 edge nodes for users and tools.
  • 14–15 workers with DataNode + NodeManager.

Avoid: putting DataNodes on the masters “to use the disks”.

Operations · incidentFresher

Containers keep getting killed on one worker

Tasks on worker w12 are often killed with “running beyond physical memory limits” or the node runs out of memory. Other workers are fine.

The interviewer is checking: do you consider work happening outside YARN?

Show a strong answer
  1. Log in (as an admin) and check what else is running: top often shows a user's script, a stray Python process or a forgotten service on that worker.
  2. YARN offers memory based on configuration; anything running outside YARN takes memory YARN believes is free, so the OS or YARN kills containers.
  3. Stop the stray process, move the user to the edge node, and restrict logins on workers.
  4. If nothing extra is running, check the node's memory settings against its real RAM.

Avoid: simply raising container memory for all jobs.

Security · access1–3 years

Analysts want SSH access to every node

The analytics team asks for SSH to all cluster machines “to debug jobs faster”.

The interviewer is checking: can you meet the real need while protecting the cluster?

Show a strong answer
  • Give access to edge nodes only. Masters and workers stay on the private cluster network, reachable by admins.
  • Provide what they actually need for debugging: the ResourceManager and JobHistory UIs, yarn logs -applicationId for container logs (with log aggregation on), and the Spark History Server.
  • Use Kerberos and Ranger so their permissions are the same whatever tool they use.

Avoid: a flat “no” without offering the tools that solve their problem.

Cloud · cost1–3 years

Scale down an EMR cluster safely

An EMR cluster has 10 core nodes and 30 task nodes. Overnight, the load drops. Your manager asks you to remove 25 nodes to save money.

The interviewer is checking: do you know which cloud roles hold data?

Show a strong answer
  • Remove task nodes first: they run only YARN, so removing them loses no HDFS data (running tasks are retried elsewhere).
  • Removing core nodes means decommissioning their DataNodes so HDFS can copy their blocks away first, which is slow and risky if done in bulk.
  • Better still, keep data in S3 and size HDFS (core nodes) small, so the cluster can shrink freely, or use managed autoscaling.

Avoid: terminating core nodes directly; with replication 3 on a small cluster you can lose blocks.
