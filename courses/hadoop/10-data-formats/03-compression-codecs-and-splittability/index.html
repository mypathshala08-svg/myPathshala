Compression codecs and splittability

Compression saves disk, network and I/O, but every codec trades size against CPU, and only some can be split across map tasks. This lesson measures six Hadoop codecs on the same file, shows on a real cluster which compressed files Hadoop can split, and compresses the shuffle and the job output.

1 The story

One gzip file, one lonely map task

Kabir wanted to save space, so he gzipped a whole year of canteen orders into one file before loading it into HDFS. The file shrank to a quarter of its size. Then the nightly job, which used to start hundreds of map tasks, started exactly one. That single task read the whole file from start to end while every other worker sat idle. Riya asks Arjun Sir whether compression was a mistake.

Arjun Sir

Compression was not the mistake. The choice of codec and where you used it was. Every codec trades size against speed, and only some can be split, which means a map task can start reading in the middle of the file.

Riya

So which one should we use?

Arjun Sir

It depends on the place: input files, the shuffle between map and reduce, the final output, or inside a container format like Parquet. Today we measure six codecs on 194 MB of orders, run the same job on each compressed file, and compress a shuffle from 60 MB down to 13 KB.

2 Definition

Compression codecs and splittability

Formal definition (write this in exams)

A compression codec in Hadoop is an implementation of org.apache.hadoop.io.compress.CompressionCodec that creates compressing output streams and decompressing input streams for one algorithm, such as DEFLATE, gzip, bzip2, LZ4, Snappy or Zstandard. CompressionCodecFactory selects the codec for an input file from its extension (.gz, .bz2, .zst…), so jobs read compressed text transparently. A codec is splittable if a reader can start decompressing at an arbitrary position in the stream, which Hadoop expresses with SplittableCompressionCodec; among the built-in codecs only bzip2 is. A file compressed with a non-splittable codec becomes a single input split, however many HDFS blocks it spans. Compression can be applied to job input, to intermediate map output (mapreduce.map.output.compress), to job output (mapreduce.output.fileoutputformat.compress), and inside container formats that compress block by block and therefore remain splittable.

In simple words

A codec makes files smaller, at some CPU cost. Some codecs (gzip) must be read from the very first byte, so a big gzip file gets only one map task. Fast codecs suit the shuffle; strong ones suit cold storage; containers like Parquet and ORC give you compression and splitting together.

Compression at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Packing a suitcase

  • Squeezing clothes tightly (bzip2) fits the most, but takes long to pack and unpack. Folding loosely (Snappy, LZ4) is quick but takes more space.
  • gzip is like vacuum-sealing the whole suitcase as one bag: to get one shirt, you open everything from the start.
  • bzip2 and container formats pack in separate pouches: anyone can open pouch 3 without touching pouches 1 and 2. That is splittability.

Intermediate What happens in a job

  • The input format asks CompressionCodecFactory for a codec by extension. If the codec is not splittable, isSplitable() returns false and the whole file is one split (our .gz, .zst, .snappy runs).
  • bzip2 marks every compressed block with a 48-bit pattern, so a reader can scan forward from a split's start to the next block. That gave our .bz2 file 4 maps.
  • Map output is compressed when spilled and decompressed by the reducer after the shuffle. It never leaves Hadoop, so pick the fastest codec: Snappy, LZ4 or Zstandard.
  • Job output compression produces part-r-00000.gz. Choose it with the next reader in mind: a later job reading one big gzip part gets one map again.

Advanced How teams choose

  • Data that jobs read often: store it in Parquet or ORC (Snappy or ZSTD inside). Compression is per page or stripe, so files stay splittable (Lessons 10.1, 10.2).
  • Raw text that must stay text: many files around the block size each (one per map), or bzip2 if it must be one big file.
  • Shuffle: mapreduce.map.output.compress=true with Snappy, LZ4 or ZSTD; almost always a win on real networks.
  • Cold archives: stronger levels of gzip, bzip2 or ZSTD; CPU is spent once and storage is saved for years.
  • Native libraries matter: without them Hadoop falls back to slower Java code, or fails for codecs with no Java version. Check with hadoop checknative.

Exam tip: For “Which compression codecs are splittable in Hadoop and why does it matter?”, answer: among the built-ins only bzip2 (it implements SplittableCompressionCodec); gzip, Snappy, LZ4 and Zstandard files are read by a single map task, which removes parallelism and data locality. Mention that container formats (SequenceFile, Avro, Parquet, ORC) compress internally per block and stay splittable.

Where you can compress

Input files

Hadoop decompresses by extension automatically. Non-splittable codecs mean one map per file, so keep each file near the block size.

read side

Map output

mapreduce.map.output.compress=true + …map.output.compress.codec. Less spill I/O and network. Our shuffle: 60 MB → 13 KB with ZSTD.

shuffle

Job output

mapreduce.output.fileoutputformat.compress=true + …compress.codec. Gives part-r-00000.gz.

write side

Inside containers

SequenceFile BLOCK, Avro blocks, Parquet pages, ORC stripes: compressed in pieces, still splittable.

best of both

hdfs dfs -text decompresses any file Hadoop has a codec for, and also decodes SequenceFiles and Avro. Use it instead of -cat to peek at compressed data.

5 See it happen

gzip vs bzip2 on the same data

Six steps: how a gzip file and a bzip2 file become splits and map tasks.

Splits from compressed files 6 steps
What you see
  1. The gzip file takes 6 blocks of 8 MB in HDFS.
  2. The job plans only one split for it.
  3. One map reads all 6 blocks: 30 s on our small cluster.
  4. The bzip2 file takes 4 blocks.
  5. The job plans 4 splits, one per block.
  6. Four maps give the same answer. On big files that parallelism is what matters.
Behind the screen
  1. A gzip stream is one long compressed sequence; there is no place in the middle where decoding can start.
  2. GzipCodec is not splittable, so the input format makes one split for the whole file.
  3. A single map reads all six blocks, most of them from other nodes.
  4. bzip2 compresses in blocks of up to 900 KB, each starting with a recognisable marker.
  5. BZip2Codec implements SplittableCompressionCodec, so every HDFS block becomes a split.
  6. Each map finds the first marker after its split start and reads to the first marker after its end (like lines in Lesson 8.2).
6 Real-world use

Compression at work

1. Cluster-wide shuffle compression

Platform teams set mapreduce.map.output.compress=true with Snappy, LZ4 or ZSTD in mapred-site.xml for every job; Spark does the same for its shuffle by default (LZ4).

Map output→fast codec→Less disk and network

2. Data lakes in Parquet with ZSTD or Snappy

Tables are stored as Parquet or ORC with Snappy or ZSTD inside. Many teams moved from Snappy to ZSTD for 20–40% smaller files at similar read speed.

Raw CSV/JSON→Parquet + ZSTD→Smaller, splittable, columnar

3. Landing zones with many gzip files

Logs and exports often arrive as gzip. Ingestion keeps them as many files of a few hundred MB each (one map each), then converts them to a columnar format.

Hourly .gz files→one map per file→Parquet tables

4. Cold archives

Data kept for compliance (years of transactions) is compressed hard once: bzip2 when it must stay splittable text, or high-level ZSTD inside containers.

Old partitions→strong codec→Cheaper storage

Simplified; organisations differ in tools and policies.

7 Run the code

Compare codecs on a CSV sample

Python ships three of the algorithms Hadoop uses: zlib (DEFLATE, the algorithm inside gzip), bz2 (bzip2) and lzma (xz, not a Hadoop codec but a useful “maximum squeeze” reference). Snappy, LZ4 and Zstandard need extra packages, so the lab numbers stand in for them.

import zlib, bz2, lzma, random, time
random.seed(1)
items = {"chai": 15, "coffee": 20, "samosa": 18, "vada pav": 20, "poha": 25, "idli": 30, "dosa": 45, "thali": 80}
rows = []
for oid in range(1, 20001):
    item = random.choice(list(items))
    rows.append(f"{oid},S{random.randint(1, 2000):04d},2026-09-{random.randint(1, 30):02d} {random.randint(8, 20):02d}:{random.randint(0, 59):02d},{item},{items[item]}")
data = ("\n".join(rows) + "\n").encode()
print(f"original {len(data):,} bytes")

for name, compress, decompress in [("zlib (gzip)", zlib.compress, zlib.decompress),
                                   ("bz2", bz2.compress, bz2.decompress),
                                   ("lzma (xz)", lzma.compress, lzma.decompress)]:
    t0 = time.perf_counter(); c = compress(data); t1 = time.perf_counter()
    assert decompress(c) == data
    t2 = time.perf_counter()
    print(f"{name:12} {len(c):>8,} bytes  {100 * len(c) / len(data):5.1f}%  compress {1000 * (t1 - t0):6.1f} ms  decompress {1000 * (t2 - t1):5.1f} ms")
original 751,116 bytes zlib (gzip) 185,729 bytes 24.7% compress 57.0 ms decompress 4.4 ms bz2 126,647 bytes 16.9% compress 72.8 ms decompress 27.3 ms lzma (xz) 143,888 bytes 19.2% compress 498.5 ms decompress 10.5 ms

Compress one file with every Hadoop codec

// CodecBench.java: compress and decompress one local file with each Hadoop codec, single thread.
// Usage: hadoop CodecBench <file>
import java.io.*;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.io.IOUtils;
import org.apache.hadoop.io.compress.*;
import org.apache.hadoop.util.ReflectionUtils;

public class CodecBench {
  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    File in = new File(args[0]);
    Class<?>[] codecs = {DefaultCodec.class, GzipCodec.class, BZip2Codec.class, SnappyCodec.class, Lz4Codec.class, ZStandardCodec.class};
    System.out.printf("%-14s %12s %7s %10s %10s %11s%n", "codec", "bytes", "ratio", "compress", "decompress", "splittable");
    System.out.printf("%-14s %,12d %7s%n", "(original)", in.length(), "100%");
    for (Class<?> c : codecs) {
      CompressionCodec codec = (CompressionCodec) ReflectionUtils.newInstance(c, conf);
      File out = new File(in.getPath() + codec.getDefaultExtension());
      long t0 = System.nanoTime();
      try (InputStream is = new FileInputStream(in); OutputStream os = codec.createOutputStream(new FileOutputStream(out))) {
        IOUtils.copyBytes(is, os, 1 << 16);
      }
      long t1 = System.nanoTime();
      try (InputStream is = codec.createInputStream(new FileInputStream(out)); OutputStream os = OutputStream.nullOutputStream()) {
        IOUtils.copyBytes(is, os, 1 << 16);
      }
      long t2 = System.nanoTime();
      System.out.printf("%-14s %,12d %6.1f%% %8.1f s %8.1f s %11s%n", codec.getDefaultExtension(), out.length(),
          100.0 * out.length() / in.length(), (t1 - t0) / 1e9, (t2 - t1) / 1e9,
          codec instanceof SplittableCompressionCodec ? "yes" : "no");
    }
  }
}

Approach

  1. Raw disk = data × replication.

  3. Compare.

Quick revision

Lesson 10.3 in one screen

  • Compression trades CPU for less disk, network and I/O. Ratio and speed vary hugely between codecs.
  • Lab, 194 MB CSV: bzip2 16.5% (24 s), gzip 23.5% (14.5 s), ZSTD 25.9% (1.4 s), LZ4 37.8% (0.7 s), Snappy 42% (0.7 s).
  • Only bzip2 is splittable among built-ins. Lab with 8 MB blocks: plain 24 splits, .gz/.zst/.snappy 1, .bz2 4.
  • CompressionCodecFactory picks the codec by extension; hdfs dfs -text decompresses for you.
  • Map output: mapreduce.map.output.compress=true + Snappy/LZ4/ZSTD. Lab shuffle 60 MB → 2.8 MB → 13 KB.
  • Job output: mapreduce.output.fileoutputformat.compress=true + codec → part-r-00000.gz.
  • Best for data read often: Parquet/ORC (or SequenceFile/Avro) with compression inside: compact AND splittable.

Interview and viva questions

Which compression formats are splittable in Hadoop?

Among the codecs shipped with Hadoop only bzip2 (BZip2Codec) is splittable. gzip, DEFLATE, Snappy, LZ4 and Zstandard files are each processed by a single map task. LZO becomes splittable only after building an index with the separate hadoop-lzo project. Container formats such as SequenceFile, Avro, Parquet and ORC remain splittable whatever codec they use internally, because they compress block by block.

Why is gzip not splittable?

A gzip file is one continuous DEFLATE stream: decoding any part requires the state built from everything before it, and there are no markers where a reader could safely begin. A map task assigned the middle of the file could not decompress it, so Hadoop makes the whole file one split.

How do I enable compression in a MapReduce job?

For intermediate data set mapreduce.map.output.compress=true and mapreduce.map.output.compress.codec (for example org.apache.hadoop.io.compress.SnappyCodec). For the final output set mapreduce.output.fileoutputformat.compress=true and mapreduce.output.fileoutputformat.compress.codec, or call FileOutputFormat.setCompressOutput and setOutputCompressorClass in the driver. Compressed input is detected automatically from the file extension.

Which codec should I use in Hadoop?

For the shuffle, a fast codec: Snappy, LZ4 or Zstandard. For data that jobs read often, a columnar container (Parquet or ORC) with Snappy or Zstandard. For plain text that must be one large splittable file, bzip2. For archives, a high compression level of Zstandard, gzip or bzip2. Always test on your own data, because ratios depend heavily on content.

What are native libraries in Hadoop?

libhadoop.so and system libraries (zlib, libzstd, libbz2) that implement compression and other functions in C for speed. hadoop checknative lists which are loaded. Without them Hadoop uses slower Java implementations where they exist, and codecs without a Java version fail.

P8Advanced

Split planner with locality

Write a function that, for a file size, block size and codec, returns the number of map tasks and how many blocks must be read remotely (assuming each splittable map is data-local and a single map is local only to block 1).

Input
file, block, codec
Expected output
none     400 maps,    0 blocks read over the network
bzip2    400 maps,    0 blocks read over the network
gzip       1 maps,  399 blocks read over the network
snappy     1 maps,  399 blocks read over the network
zstd       1 maps,  399 blocks read over the network
Show solution and explanation 
import math
SPLITTABLE = {"none": True, "bzip2": True, "gzip": False, "snappy": False, "zstd": False}

def plan(size_mb, block_mb, codec):
    blocks = math.ceil(size_mb / block_mb)
    if SPLITTABLE[codec]:
        return blocks, 0
    return 1, blocks - 1

for codec in SPLITTABLE:
    maps, remote = plan(50 * 1024, 128, codec)
    print(f"{codec:7} {maps:4} maps, {remote:4} blocks read over the network")
none 400 maps, 0 blocks read over the network bzip2 400 maps, 0 blocks read over the network gzip 1 maps, 399 blocks read over the network snappy 1 maps, 399 blocks read over the network zstd 1 maps, 399 blocks read over the network

How it works: For 50 GB: 400 maps and no remote reads when splittable, versus 1 map pulling 399 blocks over the network for gzip, Snappy or ZSTD.

Real-world scenario questions (asked in company interviews)

Compression questions are common for data engineers: splittability, codec choice and where to compress.

Concepts · splittabilityFresher

“Why does my job on a 30 GB .gz file run only one mapper?”

A classic first question about compression.

The interviewer is checking: splittable vs non-splittable codecs.

Show a strong answer
  • gzip is one DEFLATE stream with no restart points, so the input format makes one split for the whole file.
  • Fixes: recompress with bzip2, split the data into many gzip files near the block size, or convert to Parquet/ORC.
  • Also mention lost data locality: one map reads most blocks over the network.
Performance · shuffleExperienced

A join job's shuffle saturates the network

Reducers spend most of their time in the copy phase.

The interviewer is checking: map output compression and other shuffle reducers.

Show a strong answer
  • Enable mapreduce.map.output.compress with Snappy, LZ4 or ZSTD; cheap CPU for much less network.
  • Add a combiner if the reduce is an aggregation, and emit compact types.
  • If one side is small, use a map-side join and skip the shuffle (Lesson 9.6).
Design · storageExperienced

Choose a storage format and codec for a new data lake

Analysts query a few columns; data arrives as gzipped JSON.

The interviewer is checking: container formats vs raw compressed files.

Show a strong answer
  • Land the gzip files as they come, then convert to Parquet or ORC with Snappy or ZSTD.
  • Columnar + compression per page/stripe gives small, splittable files and column pruning.
  • Keep file sizes around 128 MB–1 GB and compact small files.
Operations · debuggingExperienced

A job with Zstandard works locally but fails on the cluster

Tasks fail with ClassNotFoundException or “native zstd library not available”.

The interviewer is checking: native libraries and task classpaths.

Show a strong answer
  • Run hadoop checknative on the worker nodes; install libzstd or the Hadoop native build if missing.
  • Ship missing jars (for example zstd-jni for Parquet) with -libjars or install them cluster-wide.
  • Read the failed attempt's diagnostics in the JobHistory UI or yarn logs, not just the client output.
