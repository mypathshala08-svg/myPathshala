Blocks (and how they differ from splits)

HDFS stores every file as fixed-size blocks, cut at exact byte counts with no regard for lines or records. MapReduce then divides the work into input splits that follow those blocks but always deliver whole records. This lesson shows both on a real cluster: a canteen order sliced in two by a block boundary, and the job counters proving every order was still read exactly once.

2 Definition

HDFS blocks (and input splits)

Formal definition (write this in exams)

An HDFS block is the unit in which a file is stored and replicated: a file is divided into blocks of a fixed size (dfs.blocksize, default 128 MB in Hadoop 2 and 3), chosen per file by the writing client; every block except the last is full, and the last block occupies only as much space as its data. Each block is replicated independently and placed on DataNodes by the NameNode. An input split is a logical division of the input for MapReduce: one split is processed by one map task. FileInputFormat creates splits that by default match block boundaries, and the RecordReader (e.g. LineRecordReader) ensures records crossing a boundary are read whole by exactly one split.

In simple words

Blocks are how HDFS chops a file for storage: by size, not by meaning. Splits are how a job divides the work: about one per block, but always in whole records.

Blocks and splits at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A long train and its coaches

  • A file is a long train. HDFS cuts it into coaches of equal length (blocks), even if a passenger's seat gets split by the cut.
  • Each coach is parked in three different stations (replicas).
  • Ticket checkers (map tasks) each take a coach. A checker who finds a passenger half in the next coach walks over and checks the whole passenger; the next checker ignores that half.

Intermediate Why big blocks?

  • A disk spends a few milliseconds seeking before it can read. With large blocks, reading takes much longer than seeking, so disks work at full speed.
  • Fewer blocks mean less NameNode memory and fewer map tasks to schedule.
  • Too big and you get too few map tasks (little parallelism) for medium files.
  • So 128 MB is a balance; 256 MB is common for very large tables, smaller sizes are rarely useful.

Advanced Splits in detail

  • Split size = max(minSize, min(maxSize, blockSize)); with defaults it equals the block size.
  • A small last piece (up to 10% larger than a split) is merged into the previous split (SPLIT_SLOP = 1.1).
  • Non-splittable inputs (e.g. a gzip file) become one split however many blocks they have (Lesson 10.3).
  • Each split carries the hosts of its block, so YARN can run the map task where the data is (locality).
  • Reading the end of a boundary record can be a small remote read from another DataNode.

Exam tip: “Differentiate HDFS block and input split”: block = physical division for storage, fixed size (128 MB), may cut a record, replicated; split = logical division for processing, one per map task, respects record boundaries, usually equals one block. Draw a record crossing a block boundary and show which split reads it.

5 See it happen

How map 0 and map 1 share order 71484

The real bytes around the first block boundary of canteen_1mb.csv, and what each map task's RecordReader does with them.

Blocks cut bytes, splits keep records 6 steps
What you see
  1. The real bytes: the block boundary falls inside order 71484, between “2” and “5”.
  2. Map task 0 reads its split, record by record, from the start of the file.
  3. At the end of its split it is in the middle of a record, so it keeps reading into block 1 until the line ends: it gets the whole “71484,poha,25”.
  4. Map task 1 starts at byte 1,048,576. Because it is not the first split, it throws away everything up to the first newline.
  5. Its first record is the complete order 71485.
  6. The real job counters add up to every line of the file: no record lost, none read twice.
Behind the screen
  1. The file sits in HDFS as five blocks; each is replicated on three DataNodes.
  2. FileInputFormat creates one split per block, and YARN runs one map task per split.
  3. Map 0 reads past its split's end into block 1 to finish the last record. Sometimes that block is on another machine: a small remote read.
  4. Map 1 starts at its block, skipping the first partial line that map 0 already handled.
  5. The rule is the same at every boundary.
  6. Result: five map tasks for five blocks. The file written with 128 MB blocks gave one split and one map task.

6 Real-world use

Blocks and splits at work

1. Bigger blocks for huge tables

Teams writing multi-terabyte fact tables often use 256 MB blocks (and matching Parquet row groups), halving block counts and NameNode load while keeping enough parallelism.

Huge table→256 MB blocks→Fewer objects

2. Tuning splits, not blocks

When a CPU-heavy job needs more parallel tasks, engineers lower the job's maximum split size instead of rewriting data with smaller blocks.

Slow job→Smaller splits→More map tasks

3. Unsplittable files

A 10 GB gzip log is 80 blocks but one split, so one map task reads it all. Ingestion teams store logs in splittable formats (bzip2, or Parquet/ORC with Snappy) to avoid this.

One .gz→One mapper→Use splittable formats

4. Same idea in Spark

When Spark reads files from HDFS, its initial partitions come from the same Hadoop input splits, so block size also affects how many tasks a Spark stage starts with.

HDFS blocks→Splits→Spark partitions

Simplified; organisations differ in tools and policies.

7 Run the code

Cut a file into blocks, then read it in splits

This program stores a small CSV in 32-byte “blocks” (as HDFS would with a tiny block size), shows how lines get cut, then reads each split with Hadoop's two rules: skip the partial first line unless you are split 0 and finish the record that starts inside your split.

data = "1001,samosa,18\n1002,vada pav,20\n1003,poha,25\n1004,dosa,45\n1005,chai,15\n"
BLOCK = 32
blocks = [data[i:i + BLOCK] for i in range(0, len(data), BLOCK)]
for i, b in enumerate(blocks):
    print(f"block {i}: {b!r}")

for i in range(len(blocks)):
    start, end = i * BLOCK, min((i + 1) * BLOCK, len(data))
    pos = start if i == 0 else data.index("\n", start - 1) + 1
    records = []
    while pos < end:
        nl = data.index("\n", pos)
        records.append(data[pos:nl])
        pos = nl + 1
    print(f"split {i}: {records}")
block 0: '1001,samosa,18\n1002,vada pav,20\n' block 1: '1003,poha,25\n1004,dosa,45\n1005,c' block 2: 'hai,15\n' split 0: ['1001,samosa,18', '1002,vada pav,20'] split 1: ['1003,poha,25', '1004,dosa,45', '1005,chai,15'] split 2: []
  • blocks = [data[i:i + BLOCK] for i in range(0, len(data), BLOCK)]Blocks are cut every 32 characters, wherever that falls. Look for cut-off orders in the output.
  • pos = start if i == 0 else data.index("\n", start - 1) + 1Rule 1: every split except the first skips to just after the first newline at or after its start (looking one byte back, in case the split starts exactly at a line).
  • while pos < end:Rule 2: a record that starts before the end of the split belongs to it, even if it ends in the next block.

Run it on your PC: predict Hadoop's split counters exactly

This script applies HDFS block cutting and Hadoop's LineRecordReader rules to the real canteen_orders.csv (from make_canteen.py, Lesson 4.3) with 1 MB blocks. Save it as blocks_and_splits.py next to the CSV and run it. Then compare with the job counters in Part 4.

Blocks, splits and the cut record, without Hadoop

# blocks_and_splits.py: cut a file into HDFS-style blocks, then count records per split
# the way Hadoop's LineRecordReader does (no Hadoop needed).

FILE = "canteen_orders.csv"
BLOCK = 1024 * 1024                       # same as -D dfs.blocksize=1048576
data = open(FILE, "rb").read()
size = len(data)
starts = list(range(0, size, BLOCK))
print(f"{FILE}: {size:,} bytes -> {len(starts)} blocks of up to {BLOCK:,} bytes")

for i, start in enumerate(starts):
    end = min(start + BLOCK, size)
    pos = start
    if start != 0:                        # not the first split: skip the partial first line
        pos = data.index(b"\n", start - 1) + 1
    records = 0
    while pos < end:                      # a record that STARTS inside the split belongs to it
        nl = data.find(b"\n", pos)
        pos = size if nl == -1 else nl + 1
        records += 1
    print(f"split {i}: bytes {start:>7}-{end - 1:>7}  records {records:>6}")

cut = BLOCK                               # show the line broken by the first block boundary
line_start = data.rindex(b"\n", 0, cut) + 1
line_end = data.index(b"\n", cut)
print("record cut by block 0/1:", data[line_start:cut], "+", data[cut:line_end])

Interview and viva questions

What is a block in HDFS?

The unit in which HDFS stores and replicates a file. Files are divided into blocks of dfs.blocksize bytes (128 MB by default); each block is stored on several DataNodes. Only the last block of a file may be smaller, and it uses only the space it needs.

Why is the HDFS block size so large?

To make reading efficient on disks (the time to transfer a block is much larger than the time to seek to it) and to keep the number of blocks, and so the NameNode's memory and the number of tasks, small.

What is the difference between a block and an input split?

A block is a physical division of a file for storage. An input split is a logical division of the input for processing by one map task. Splits usually match blocks, but the RecordReader makes sure records crossing block boundaries are read whole by exactly one split.

Does a small file occupy a full 128 MB block?

No. A 1 MB file uses about 1 MB of disk per replica. It does, however, cost one file object and one block object in NameNode memory, which is why many small files are a problem.

Can I change the block size of an existing file?

Not in place. Block size is fixed when the file is written; to change it, rewrite the file (for example copy it with -D dfs.blocksize=… or with distcp).

How many map tasks will my job have?

By default one per input split, and splits follow blocks: a 1 GB file with 128 MB blocks gives 8 map tasks. Split size settings, the 10% slop rule, unsplittable compression and combined input formats can change this.

P8Advanced

Record reader for a boundary

Implement the two RecordReader rules for a list of split boundaries and return records per split for the given text.

Input
"aa\nbbbb\ncc\ndddddd\ne\n" · splits at 0, 5, 12
Expected output
split 0 [0,5): ['aa', 'bbbb']

Show solution and explanation 
data = "aa\nbbbb\ncc\ndddddd\ne\n"
bounds = [0, 5, 12, len(data)]
for i in range(len(bounds) - 1):
    start, end = bounds[i], bounds[i + 1]
    pos = start if start == 0 else data.index("\n", start - 1) + 1
    recs = []
    while pos < end:
        nl = data.index("\n", pos)
        recs.append(data[pos:nl]); pos = nl + 1
    print(f"split {i} [{start},{end}):", recs)

How it works: Split 0 gets aa and bbbb (bbbb crosses byte 5), split 1 gets cc and dddddd, split 2 gets e. Each record appears once.

Choose a block size for a new 2 PB table

A team will write a 2 PB fact table, scanned mostly in full each night.

The interviewer is checking: trade-offs, not a memorised number.

Show a strong answer
  • Large, fully scanned data favours bigger blocks, e.g. 256 MB: half the block objects, longer efficient reads.
  • Check parallelism: 2 PB / 256 MB is still about 80 lakh blocks, plenty of tasks.
  • Align file format units (Parquet row groups / ORC stripes) with the block size so a task's data sits in one block.
  • Keep file sizes large too; block size does not help if writers produce small files.

“A 1 KB file wastes 128 MB, right?”

A student claims small files waste disk because each takes a full block.

The interviewer is checking: what really costs with small files.

Show a strong answer
  • No: a block file is only as big as its data (plus a tiny checksum file). The 4.5 MB file used 4.5 MB per replica, not 128 MB.
  • The real cost is metadata: every file and block is an object in NameNode memory, and each small file usually becomes its own map task.
  • So small files are a NameNode and scheduling problem, not a disk problem.
