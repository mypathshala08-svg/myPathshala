fsimage, edit log and checkpointing

The NameNode answers every request from memory, yet it survives restarts without losing a single file. The trick is an fsimage snapshot plus an edit log of every change since, merged regularly by a checkpoint. In this lesson you read the real metadata files of a running cluster, decode the edit log entries of your own commands, and watch the SecondaryNameNode take a checkpoint, then learn why skipping checkpoints has caused hours-long outages.

The NameNode keeps the whole namespace in memory. To survive a restart it writes two things to disk. The fsimage is a photograph of the entire namespace at one moment. The edit log is a diary: every single change after that moment, each with a transaction number.

Kabir

Why not just update the photo every time something changes?

Arjun Sir

Because the photo can be gigabytes. Rewriting it for every mkdir would be far too slow. Appending one line to the diary is cheap. But the diary grows for ever, and on restart the NameNode must replay all of it. So every so often someone takes a new photo: loads the old photo, applies the diary, saves the result. So the SecondaryNameNode isn't a backup NameNode?

Arjun Sir

No. Its name is the most misleading in Hadoop. Today we'll read the diary entries of our own commands and watch a real checkpoint happen.

2 Definition

fsimage, edit log and checkpointing

Formal definition (write this in exams)

The NameNode persists its namespace in two kinds of files in dfs.namenode.name.dir. The fsimage (fsimage_<txid>) is a complete, checkpointed image of the namespace (inodes, directories, permissions, file-to-block lists) as of a given transaction ID. The edit log (edits_<start>-<end> segments and one edits_inprogress_<start>) is a write-ahead log recording every namespace-changing operation (e.g. OP_MKDIR, OP_ADD, OP_CLOSE, OP_RENAME, OP_DELETE) with a transaction ID; an operation is acknowledged only after it is logged. At start-up the NameNode loads the latest fsimage and replays the edits that follow it. Checkpointing merges the fsimage with subsequent edits into a new fsimage, keeping restart time short; it is done by the SecondaryNameNode (non-HA), or the Standby NameNode (HA), or manually with hdfs dfsadmin -saveNamespace. It is triggered every dfs.namenode.checkpoint.period (3600 s) or after dfs.namenode.checkpoint.txns (1,000,000) uncheckpointed transactions, whichever comes first.

In simple words

fsimage = a full photo of all folders and files. Edit log = a diary of every change since that photo. Checkpoint = take a fresh photo so the diary can start again, which makes restarts fast.

Checkpointing at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A bank passbook

  • The bank's yearly statement is the fsimage: your full balance on 31 March.
  • Every deposit and withdrawal after that is a line in the passbook: the edit log.
  • To know today's balance, start from the statement and add every line. If the passbook has 10 lakh lines, that takes long.
  • So the bank prints a fresh statement now and then (a checkpoint) and starts a new passbook.

Intermediate How a checkpoint works (non-HA)

  • The SecondaryNameNode asks the NameNode to roll its edit log: the current segment is closed, a new one starts.
  • It downloads the latest fsimage and the closed edit segments over HTTP.
  • It loads the fsimage into memory, applies the edits, and writes a new fsimage.
  • It uploads the new fsimage to the NameNode, which keeps it and deletes older images and edits beyond the retention limit.
  • The NameNode never stops serving clients during this.

Advanced Production details

  • The SecondaryNameNode needs about as much memory as the NameNode, because it loads the whole namespace.
  • With HA there is no SecondaryNameNode: the Standby NameNode checkpoints, and edits go to JournalNodes (Lesson 7.1).
  • Write metadata to several directories (comma-separated dfs.namenode.name.dir) on different disks; losing all copies of the fsimage and edits loses the file system.
  • If checkpoints silently fail for weeks, edits pile up and the next restart can take hours. Monitor “Last Checkpoint Time” / transactions since checkpoint.
  • Back up the fsimage regularly (it can be fetched with hdfs dfsadmin -fetchImage).

Exam tip: “Explain the role of the SecondaryNameNode”: it is not a standby or backup NameNode. It performs periodic checkpoints: rolls the edit log, downloads fsimage + edits, merges them, and uploads a new fsimage, so that the edit log stays small and the NameNode restarts quickly. Mention the defaults: every 1 hour or 10 lakh transactions.

5 See it happen

One checkpoint, step by step

The real file names from the lab, around the checkpoint at transaction 66.

SecondaryNameNode checkpoint 6 steps
What you see
  1. The latest photo is fsimage_…064. New changes go into the in-progress segment.
  2. Every segment begins and ends with a marker transaction. Nobody changed anything in these two minutes, so 65 and 66 are just the markers (the 42-byte file in step 1).
  3. Checkpoint time: the SecondaryNameNode asks the NameNode to roll the log. Segment 65–66 is closed; new changes go to edits_inprogress_…067.
  4. The SecondaryNameNode downloads the closed segment (and the fsimage if it doesn't already have it) and loads them.
  5. It writes fsimage_…066 and uploads it. The NameNode now has a newer photo.
  6. If the NameNode restarts now, it loads fsimage_…066 and replays only the edits from 67 onwards.
Behind the screen
  1. The NameNode serves clients from memory and appends every change to the in-progress edits.
  2. Each operation is written to the edit log before the client gets its answer: that's what makes it durable.
  3. The SecondaryNameNode triggers a checkpoint: the NameNode rolls the edit log.
  4. The SecondaryNameNode fetches the fsimage and closed edits and replays them in its own memory.
  5. It saves the result as a new fsimage and sends it back. Clients were never interrupted.
  6. Restart now needs only the new image plus the few edits written since.
6 Real-world use

Metadata files in production

1. The slow-restart incident

A classic outage: checkpoints fail silently (a misconfigured or dead SecondaryNameNode), edits grow to crores of transactions, and the next NameNode restart takes hours of replay. Monitoring the time since the last checkpoint prevents it.

Checkpoint fails→Edits pile up→Hours to restart

2. Storage reports from the fsimage

Platform teams fetch the fsimage daily, convert it with oiv, and load it into Hive or Spark to report file counts and sizes per team, small-file hotspots and stale data, all without querying the live NameNode.

fetchImage→oiv → table→Usage dashboard

3. Several copies of the metadata

Before HA was common, admins listed two local disks and an NFS mount in dfs.namenode.name.dir, so a disk failure couldn't destroy the only fsimage and edits. With HA, JournalNodes keep the edit log on several machines.

Every edit→Written to all dirs→Survives a disk

4. Clean checkpoint before maintenance

Before a planned restart or upgrade, admins enter safe mode and run saveNamespace so the NameNode comes back with almost nothing to replay, and they keep a copy of that fsimage as a rollback point.

Safe mode→saveNamespace→Fast, safe restart

Simplified; organisations differ in tools and policies.

7 Run the code

Rebuild a namespace from a photo and a diary

This program does what a NameNode does at start-up: load the fsimage (a dictionary of paths), then replay each edit after it, in transaction order. The edits are the five real operations from Part 4.

fsimage_txid = 66
fsimage = {"/user/hadoop/data": "dir",
           "/user/hadoop/data/canteen_orders.csv": "file"}
edits = [
    (68, "OP_MKDIR", "/user/hadoop/data/edits_demo", None),
    (69, "OP_ADD", "/user/hadoop/data/edits_demo/hello.txt", None),
    (70, "OP_CLOSE", "/user/hadoop/data/edits_demo/hello.txt", None),
    (71, "OP_RENAME_OLD", "/user/hadoop/data/edits_demo/hello.txt",
         "/user/hadoop/data/edits_demo/namaste.txt"),
    (72, "OP_DELETE", "/user/hadoop/data/edits_demo", None),
]

ns = dict(fsimage)
for txid, op, path, dst in edits:
    if txid <= fsimage_txid:
        continue
    if op == "OP_MKDIR":
        ns[path] = "dir"
    elif op == "OP_ADD":
        ns[path] = "file (open)"
    elif op == "OP_CLOSE":
        ns[path] = "file"
    elif op == "OP_RENAME_OLD":
        ns[dst] = ns.pop(path)
    elif op == "OP_DELETE":
        ns = {p: k for p, k in ns.items() if p != path and not p.startswith(path + "/")}
    print(f"txid {txid}: {op:14} -> {len(ns)} paths")
print(sorted(ns))
txid 68: OP_MKDIR -> 3 paths txid 69: OP_ADD -> 4 paths txid 70: OP_CLOSE -> 4 paths txid 71: OP_RENAME_OLD -> 4 paths txid 72: OP_DELETE -> 2 paths ['/user/hadoop/data', '/user/hadoop/data/canteen_orders.csv']
  • if txid <= fsimage_txid:Edits already contained in the fsimage are skipped. Only transactions after the image's txid are replayed.
  • ns[path] = "file (open)"OP_ADD creates the file while it is being written; OP_CLOSE marks it complete.
  • ns = {p: k for p, k in ns.items() if p != path and not p.startswith(path + "/")}Deleting a directory removes everything below it too.

Run it on your PC: watch your commands land in the edit log

This script makes four changes in HDFS, then decodes the newest edit log segments with hdfs oev and prints only the transactions your commands created. Save it as edit_log_report.py in the hdfs-lab folder and run it while the cluster is up.

Your commands, as NameNode transactions

# edit_log_report.py: make a few changes in HDFS, then read them back from the NameNode's edit log.
# Run in the hdfs-lab folder while the cluster is up.
import json
import subprocess
import xml.etree.ElementTree as ET

NAME_DIR = "/tmp/hadoop-hadoop/dfs/name/current"

def nn(*cmd):
    return subprocess.run(["docker", "compose", "exec", "-T", "namenode", *cmd],
                          capture_output=True, text=True).stdout

def last_txid():
    url = "http://namenode:9870/jmx?qry=Hadoop:service=NameNode,name=NameNodeInfo"
    info = json.loads(json.loads(nn("curl", "-s", url))["beans"][0]["JournalTransactionInfo"])
    return int(info["LastAppliedOrWrittenTxId"])

before = last_txid()
print("last transaction before our changes:", before)
for cmd in (["hdfs", "dfs", "-mkdir", "-p", "data/demo"],
            ["hdfs", "dfs", "-touchz", "data/demo/order.txt"],
            ["hdfs", "dfs", "-mv", "data/demo/order.txt", "data/demo/order_old.txt"],
            ["hdfs", "dfs", "-rm", "-r", "-skipTrash", "data/demo"]):
    nn(*cmd)

# a checkpoint may have closed the segment meanwhile, so read the newest two edit files
files = nn("bash", "-c", f"ls {NAME_DIR} | grep ^edits_ | tail -2").split()
for f in files:
    nn("hdfs", "oev", "-i", f"{NAME_DIR}/{f}", "-o", "/tmp/edits.xml")
    for rec in ET.fromstring(nn("cat", "/tmp/edits.xml")).iter("RECORD"):
        data = rec.find("DATA")
        txid = int(data.findtext("TXID"))
        path = data.findtext("PATH") or data.findtext("SRC") or ""
        dst = data.findtext("DST")
        if txid > before and path:
            print(f"txid {txid:>4}  {rec.findtext('OPCODE'):15} {path}"
                  + (f" -> {dst}" if dst else "") + f"   [{f}]")

How many edits per day?

Problem statement

A cluster's jobs create 30 lakh files a day (each create is OP_ADD + OP_CLOSE plus a few block allocations, about 5 transactions in total) and delete as many. Deleting is one transaction per path. How many transactions per day, and how often is the 10 lakh-transaction checkpoint trigger reached?

Input
30,00,000 creates × 5 tx · 30,00,000 deletes × 1 tx · trigger 10,00,000
Expected output
18,000,000 transactions/day -> count trigger 18 times/day, time trigger 24 times/day

Approach

  1. Transactions = creates × 5 + deletes × 1.
  2. Checkpoints by count = transactions / 10 lakh.
  3. Compare with the hourly trigger (24 a day).

Interview and viva questions

What are fsimage and edit log in HDFS?

The fsimage is a persistent snapshot of the entire file system namespace at a certain transaction ID. The edit log records every change made after that snapshot. Together they let the NameNode rebuild its in-memory namespace after a restart.

What is checkpointing in HDFS?

Merging the latest fsimage with the edit log that follows it to produce a new fsimage, so that the edit log stays short and restarts are fast. It is done periodically by the SecondaryNameNode (or Standby NameNode in HA).

Is the SecondaryNameNode a backup of the NameNode?

No. It only creates checkpoints. If the NameNode fails, the SecondaryNameNode cannot serve clients. Its latest checkpoint can help recover metadata, but it may be missing recent edits. Automatic takeover requires HA with a Standby NameNode.

How often does a checkpoint happen?

By default every 3600 seconds (dfs.namenode.checkpoint.period) or when 1,000,000 transactions have accumulated (dfs.namenode.checkpoint.txns), whichever comes first. The SecondaryNameNode checks the transaction count every 60 seconds.

Does the fsimage contain block locations?

No. It contains each file's list of blocks but not which DataNodes hold them. Locations come from DataNode block reports after start-up.

How can I read an fsimage or edits file?

With the offline viewers: hdfs oiv -p XML|Delimited -i fsimage_N -o out for images, and hdfs oev -i edits_file -o out.xml for edit logs. Run them on copies, not on files the NameNode is using.

What happens if the edit log is lost?

All namespace changes since the last checkpoint are lost: files created or renamed after it disappear from the namespace, even though their blocks may still be on DataNodes. That is why edits are written to several directories or JournalNodes.

P8Advanced

Detect a stuck checkpoint

Given (time, last checkpoint txid, current txid) samples, alert if the checkpoint txid has not changed for more than 2 hours while transactions keep increasing.

Input
samples every hour
Expected output
ALERT: no checkpoint for 3 h, 3,499,500 edits pending
Show solution and explanation 
samples = [(0, 500, 900), (1, 500, 1_200_000), (2, 500, 2_400_000), (3, 500, 3_500_000)]
first = next(t for t, cp, cur in samples if cp == samples[-1][1])
t_now, cp, cur = samples[-1]
if t_now - first > 2 and cur > cp:
    print(f"ALERT: no checkpoint for {t_now - first} h, {cur - cp:,} edits pending")
ALERT: no checkpoint for 3 h, 3,499,500 edits pending

How it works: The checkpoint txid has been stuck at 500 for 3 hours while 35 lakh edits accumulated: the SecondaryNameNode is failing.

Real-world scenario questions (asked in company interviews)

Interviewers love the SecondaryNameNode because its name misleads so many candidates.

HDFS · conceptsFresher

“The NameNode crashed. Can the SecondaryNameNode take over?”

A very common trick question.

The interviewer is checking: that you know what the SecondaryNameNode actually does.

Show a strong answer
  • No. The SecondaryNameNode only merges the fsimage and edit log into checkpoints; it never serves clients.
  • Restart the NameNode (it loads its fsimage + edits). If its metadata disks are lost, the SecondaryNameNode's latest checkpoint can be used to recover, losing edits since that checkpoint.
  • Automatic takeover needs HA: an active and a standby NameNode with shared edits on JournalNodes.
Operations · incidentExperienced

The NameNode has been “starting” for two hours

After a planned restart the NameNode UI shows Startup Progress stuck in “Loading edits”.

The interviewer is checking: root cause and prevention.

Show a strong answer
  • It is replaying a very large edit log, which means checkpoints haven't been happening. Check the SecondaryNameNode/Standby logs and the last checkpoint time.
  • Let it finish (interrupting makes it start again). Afterwards fix the checkpoint process: memory, connectivity on port 9868/9870, disk space for checkpoint.dir.
  • Prevent: alert on time and transactions since the last checkpoint; before planned restarts run saveNamespace in safe mode.
Design · durabilityExperienced

Why is every change written to the edit log before it's acknowledged?

An interviewer asks why the NameNode doesn't just update memory and write a snapshot every minute.

The interviewer is checking: write-ahead logging.

Show a strong answer
  • Memory is lost on a crash. If changes were only in memory, a crash would forget every file created since the last snapshot, even though clients were told “success”.
  • Appending a small record to a log (and syncing it) is cheap; rewriting a multi-GB image is not. So: log first, then apply, then acknowledge.
  • Snapshots (checkpoints) only exist to keep the log short. Databases use the same idea (write-ahead log + checkpoints).
Analytics · metadataFresher

Find the folders with the most small files, without slowing the NameNode

A manager wants a report of small files per team across a 40-crore-file namespace.

The interviewer is checking: that you know the offline fsimage approach.

Show a strong answer
  • Running hdfs dfs -ls -R or -count over everything would load the NameNode heavily.
  • Instead download the latest image (hdfs dfsadmin -fetchImage), convert it with hdfs oiv -p Delimited, and analyse the table with Hive or Spark: count files under 1 MB per top-level folder or owner.
  • Schedule it daily to track progress.
