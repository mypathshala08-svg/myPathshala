NameNode and DataNode

HDFS splits work between one master and many workers. The NameNode knows every file, folder and block and where each block lives; DataNodes store the blocks as ordinary files and serve them. In this lesson you open both on a real four-DataNode cluster, follow one file from its path to the actual block files on disk, and learn what each daemon must have to stay healthy.

1 The story

“Where is my file, really?”

Riya uploaded canteen_orders.csv to HDFS yesterday. Today she asks a simple question nobody in the lab can answer: on which disk, of which machine, are those bytes? Kabir opens a shell on one DataNode, digs through folders, and finds a file called blk_1073741825. He runs head on it. Out come order_id,item,amount and Riya's orders, as plain text.

Riya

So HDFS is just… files on ordinary Linux disks?

Arjun Sir

Exactly. A DataNode stores each block as an ordinary file in its own folders. What makes it a distributed file system is the NameNode: it keeps the whole directory tree, who owns what, and which blocks make up each file. Kabir

Arjun Sir

The bytes are still on the disks, but nobody knows which blk_ file belongs to which file. That's why the NameNode's metadata is protected so carefully, and why HA exists. Today we open both: the NameNode's metadata folder and a DataNode's block folder, on a real cluster with four DataNodes in two racks.

2 Definition

NameNode and DataNode

Formal definition (write this in exams)

HDFS has a master–worker architecture. The NameNode manages the file system namespace (the tree of directories and files with their permissions, owners, replication factor and the ordered list of blocks of each file) and regulates client access. It persists the namespace in the fsimage and edit log, and keeps it in memory together with the block map (block → DataNodes holding a replica), which it rebuilds from DataNode block reports. DataNodes, usually one per worker machine, store blocks as files on their local disks (each with a .meta checksum file), serve read and write requests from clients directly, create, delete and copy replicas when the NameNode instructs, and send heartbeats and block reports to the NameNode. File data never passes through the NameNode.

In simple words

The NameNode is the index of a huge library: it knows every book's title and on which shelves its pages are. DataNodes are the shelves that hold the pages. Readers ask the index where to go, then fetch pages straight from the shelves.

NameNode and DataNode at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The library and its index

  • A big book is torn into chapters (blocks) and each chapter is photocopied three times onto different shelves (DataNodes).
  • The index card (NameNode) says: “Canteen orders: chapter 1 on shelves 1, 2 and 4.”
  • A reader reads the card, then walks to the shelf. The librarian at the index never carries pages.

Intermediate What each daemon does

  • NameNode: create/delete/rename files and folders, check permissions, choose DataNodes for new blocks, track replicas, order re-replication when one is lost.
  • DataNode: store and checksum blocks, stream data to and from clients, forward blocks in the write pipeline, delete or copy blocks on command.
  • Client (your hdfs dfs, Spark, Hive): asks the NameNode for metadata, then talks to DataNodes for data.

Advanced Details that matter in production

  • The block map is not saved in the fsimage. After a restart the NameNode waits for block reports (safe mode, Lesson 5.6).
  • NameNode heap grows with the number of objects, not bytes: 10 crore tiny files hurt far more than 1 PB in big files (the small-files problem, Lesson 7.5).
  • DataNodes spread blocks over all disks listed in dfs.datanode.data.dir; a failed disk can be tolerated (dfs.datanode.failed.volumes.tolerated).
  • Clusters with very large namespaces split it across several NameNodes with federation; each namespace gets its own block pool on the same DataNodes.

Exam tip: “Explain the roles of NameNode and DataNode”: NameNode = master, namespace + metadata (fsimage, edit log, block map), handles client metadata requests, directs replication; DataNode = worker, stores blocks, serves reads/writes, sends heartbeats (every 3 s) and block reports. Add: data flows client ↔ DataNode, never through the NameNode.

5 See it happen

Following one file from its name to the disk

On the left, the commands from Part 4. On the right, which daemon answers and what it holds.

From path to bytes 6 steps
What you see
  1. -ls shows a normal-looking file: owner, size, replication 3. This answer comes only from the NameNode.
  2. fsck asks the NameNode for the file's blocks and where each replica is.
  3. On the NameNode's disk there is no data: just the fsimage, the edit log and identity files.
  4. On a DataNode's disk: the block as a plain file, plus its checksum file.
  5. The block's bytes are literally the CSV text Riya uploaded.
  6. The NameNode also tracks every DataNode: rack, capacity, last heartbeat and number of blocks.
Behind the screen
  1. The NameNode answers from its in-memory namespace: path, owner, size, replication.
  2. It also knows the file's blocks and, from the block map, which DataNodes hold each replica.
  3. Only the namespace is saved to disk (fsimage + edit log). The block map lives in memory only.
  4. On each chosen DataNode, the replica is a data file and a checksum file.
  5. When you read, the client gets locations from the NameNode and the bytes straight from a DataNode.
  6. DataNodes keep the NameNode up to date with heartbeats and block reports, which is how the block map is (re)built.

6 Real-world use

NameNodes and DataNodes in production

1. NameNode sizing is about objects

Large companies size NameNode memory by the number of files, directories and blocks, not by petabytes. Teams that create millions of tiny files are asked to compact them because they cost NameNode heap.

Objects→Heap needed→Server size

2. Workers packed with disks

DataNode servers commonly hold 12 or more large disks, each listed in dfs.datanode.data.dir. A dead disk is swapped while the node keeps serving from the others.

Disk fails→Node keeps running→Hot-swap

3. Protecting the metadata

Admins write the NameNode metadata to more than one disk (a comma-separated dfs.namenode.name.dir), run HA, and back up the fsimage regularly. Losing it means losing the meaning of every block.

fsimage + edits→Several copies→Backups

4. Daily health checks

On-call engineers start the day with the NameNode UI or hdfs dfsadmin -report: live and dead DataNodes, remaining capacity, missing and under-replicated blocks.

Report→Spot problems→Act before users notice

Simplified; organisations differ in tools and policies.

namespace = {
    "/user/hadoop/data/canteen_orders.csv": {"owner": "hadoop", "repl": 3,

    "/user/hadoop/data/canteen_1mb.csv": {"owner": "hadoop", "repl": 3,
                                          "blocks": ["blk_1073741826", "blk_1073741827"]},
}
block_map = {
    "blk_1073741825": ["datanode-1", "datanode-2", "datanode-4"],
    "blk_1073741826": ["datanode-1", "datanode-3", "datanode-4"],
    "blk_1073741827": ["datanode-1", "datanode-2", "datanode-4"],

def locate(path):
    meta = namespace[path]
    print(path, "owner", meta["owner"], "replication", meta["repl"])
    for blk in meta["blocks"]:
        print("  ", blk, "->", ", ".join(block_map.get(blk, [])) or "MISSING")

Run it on your PC: find the real block files of an HDFS file

This script asks the NameNode (via fsck) where each block of a file is, finds the matching Docker container for each DataNode IP, and checks the block file on that container's disk. Save it as where_is_my_file.sh in the hdfs-lab folder.

From an HDFS path to block files on DataNode disks

#!/usr/bin/env bash
# where_is_my_file.sh: show the real block files behind one HDFS file
# usage: bash where_is_my_file.sh /user/hadoop/data/canteen_orders.csv
file=$1
docker compose exec -T namenode hdfs fsck "$file" -files -blocks -locations 2>/dev/null |
  grep -o 'blk_[0-9]*_[0-9]* len=[0-9]*\|[0-9.]*:9866' | while read -r item; do
    case "$item" in
      blk_*) blk=$(echo "$item" | cut -d_ -f1-2); echo "$item";;
      *) ip=${item%:9866}
         c=$(docker ps --format '{{.Names}}' | while read n; do
               docker inspect -f "{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}} $n" "$n"; done |
             awk -v ip="$ip" '$1==ip {print $2}')
         path=$(docker exec "$c" find /tmp/hadoop-hadoop/dfs/data -name "$blk" 2>/dev/null)
         size=$(docker exec "$c" stat -c %s "$path")
         echo "   on $c  ($ip)  file size $size bytes";;
    esac
  done

Example 1BeginnerCapacity · NameNode

How much heap for the NameNode?

Problem statement

An insurance company stores 40 lakh files averaging 300 MB each (128 MB blocks) in 50,000 directories. Using the rule of thumb of 150 bytes per object, estimate NameNode heap. Then double it for safety and growth.

Input
40,00,000 files · 300 MB each · 128 MB blocks · 50,000 dirs · 150 B per object
Expected output
objects 16,050,000  heap ~2.2 GB  with headroom ~4.5 GB

Approach

  1. Blocks per file = ceil(300 / 128) = 3.
  2. Objects = files + directories + blocks.
  3. Heap = objects × 150 bytes, then × 2 for headroom.

Interview and viva questions

What is the difference between NameNode and DataNode?

The NameNode is the master that stores metadata: the directory tree, permissions, which blocks make up each file and where they are. DataNodes are workers that store the actual blocks on local disks, serve reads and writes, and report to the NameNode with heartbeats and block reports.

Does the NameNode store data?

No. It stores only metadata. File contents are stored as blocks on DataNodes, and clients read and write those blocks directly from and to DataNodes.

Where does a DataNode store blocks?

In the folders listed in dfs.datanode.data.dir, under current/<block pool ID>/current/finalized/, as files named blk_<id> with a matching blk_<id>_<generation stamp>.meta checksum file.

What happens if the NameNode fails?

Without high availability, the whole file system becomes unavailable until the NameNode is restarted (the data stays on DataNodes but cannot be located). With HA, a standby NameNode takes over automatically.

How does the NameNode know where blocks are?

From block reports: each DataNode reports all its blocks when it starts and periodically afterwards (every 6 hours by default), plus incremental reports when blocks are added or removed.

How much memory does a NameNode need?

It depends on the number of files, directories and blocks. A common rule of thumb is about 150 bytes per object, so 10 crore objects need roughly 14 GB of heap, plus headroom.

Can there be more than one NameNode?

Yes: in HA there is one active and one or more standby NameNodes for the same namespace, and with federation several independent NameNodes each manage part of the namespace on the same DataNodes.

P8Advanced

Rebuild the block map

After a restart the NameNode only has the namespace. Build the block map from three block reports and print each block's replica count.

Input
dn1: b1,b2 · dn2: b1,b3 · dn3: b2,b3,b1
Expected output
b1 ['dn1', 'dn2', 'dn3'] 3 replicas
b2 ['dn1', 'dn3'] 2 replicas
b3 ['dn2', 'dn3'] 2 replicas
Show solution and explanation 
reports = {"dn1": ["b1", "b2"], "dn2": ["b1", "b3"], "dn3": ["b2", "b3", "b1"]}
block_map = {}
for dn, blocks in reports.items():
    for b in blocks:
        block_map.setdefault(b, []).append(dn)
for b in sorted(block_map):
    print(b, block_map[b], len(block_map[b]), "replicas")
b1 ['dn1', 'dn2', 'dn3'] 3 replicas b2 ['dn1', 'dn3'] 2 replicas b3 ['dn2', 'dn3'] 2 replicas

How it works: b1 has 3 replicas, b2 and b3 have 2 each. This is exactly how the block map is rebuilt at start-up (Lessons 5.5 and 5.6).

Real-world scenario questions (asked in company interviews)

Interviewers use NameNode and DataNode questions to see whether you understand where metadata ends and data begins.

HDFS · conceptsFresher

“Does a 1 TB file pass through the NameNode when I upload it?”

A classic first-round question.

The interviewer is checking: the split between the metadata path and the data path.

Show a strong answer
  • No. The client asks the NameNode to create the file and allocate blocks; the NameNode returns DataNode addresses.
  • The client streams bytes to the first DataNode, which forwards them along a pipeline to the others.
  • The NameNode only records metadata (and later learns of finished replicas). That is why one NameNode can serve thousands of DataNodes.
Admin · memoryExperienced

NameNode heap keeps climbing, but the cluster is only 30% full

Disk usage is low, yet the NameNode needs more and more heap and garbage collection pauses are getting longer.

The interviewer is checking: do you know heap depends on object count?

Show a strong answer
  • Check files and blocks (NameNode UI, FilesTotal/BlocksTotal in /jmx) and find directories with millions of small files (hdfs dfs -count).
  • Compact small files (merge into larger Parquet/ORC files, use HAR or larger batches in ingestion).
  • Short term: increase heap and tune GC; long term: fix the sources of small files, add quotas, or federate the namespace.
Troubleshooting · diskExperienced

“Someone deleted blk_ files on a DataNode to free space”

A junior admin removed some old-looking blk_ files from a full DataNode disk.

The interviewer is checking: what HDFS does when replicas vanish behind its back.

Show a strong answer
  • Those were live replicas. The DataNode will report them missing (block scanner or next block report), and the NameNode will re-replicate from other copies if any exist.
  • Run hdfs fsck / -list-corruptfileblocks and check for missing blocks; files whose every replica was deleted are lost.
  • Prevent it: free space with HDFS commands (delete data, lower replication of cold data, add disks, run the balancer), never inside the DataNode folders.
Design · hardwareFresher

Choose hardware for master and worker nodes

You have budget for 1 master and 10 workers. What do you prioritise for each?

The interviewer is checking: that you match hardware to each role.

Show a strong answer
  • NameNode: plenty of RAM for the heap, reliable disks (RAID) for metadata, redundant power and network; disk capacity is not important.
  • DataNodes: many large disks (JBOD, no RAID), enough RAM and cores for YARN tasks, good network.
  • Plan for a standby NameNode (HA) as soon as the cluster matters.
