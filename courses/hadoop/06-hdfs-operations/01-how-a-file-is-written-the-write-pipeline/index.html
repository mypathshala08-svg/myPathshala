How a file is written: the write pipeline

When you write a file to HDFS with replication 3, your client uploads the data only once: the DataNodes copy it along a pipeline. This lesson follows a real 134 MB upload through the client, NameNode and DataNode logs, packet by packet, and then breaks it on purpose by killing DataNodes during a write to show how HDFS recovers without failing the upload.

Arjun Sir

No. The client sent each byte once. The NameNode only chose three DataNodes; the client then opened a pipeline: it streams 64 KB packets to the first DataNode, which writes each packet to its disk and forwards it to the second, which does the same for the third. Arjun Sir

Exactly, and the copies are made at the same time, not one after another. Today we'll read the real logs of this pipeline: the NameNode choosing nodes, the packets, the acknowledgements, and what happens when we kill a DataNode in the middle of a block.

2 Definition

The HDFS write pipeline

Formal definition (write this in exams)

To write a file, the client calls create on the NameNode, which checks permissions and that the file doesn't exist, records it in the namespace (with a lease for the writer) and returns an output stream. As data is written, the client's DataStreamer asks the NameNode to allocate a block; the NameNode returns a new block ID and a list of DataNodes chosen by the placement policy, ordered as a pipeline. The client splits data into packets (about 64 KB of data, made of 512-byte chunks each with a 4-byte checksum) and sends them to the first DataNode, which stores and forwards each packet to the next, and so on. Acknowledgements return in the reverse direction; the client keeps each packet in an ack queue until all DataNodes in the pipeline have acknowledged it. When a block is full the pipeline is closed and a new block is allocated. Finally the client calls complete, and the NameNode closes the file once the minimum replication is reached. If a DataNode fails, the client removes it, the NameNode bumps the block's generation stamp, and writing continues on the remaining DataNodes; the block is re-replicated later.

In simple words

The NameNode picks three DataNodes. The client sends the data in small packets to the first one, which passes them to the second, which passes them to the third. Each packet is confirmed by all three before the client forgets it.

The write pipeline at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A bucket chain

  • Villagers pass buckets of water hand to hand. Each person also fills their own pot from every bucket before passing it on.
  • The water carrier (client) walks only to the first person. The supervisor (NameNode) just decided who stands in the chain.
  • When the last person shouts “got it”, the shout travels back, and the carrier knows that bucket is safe.

Intermediate Step by step

  • create: NameNode checks and records the file; client gets a lease.
  • addBlock: NameNode returns block ID + 3 DataNodes (placement policy, Lesson 5.3).
  • Pipeline setup: client connects to DN1, which connects to DN2, which connects to DN3.
  • Streaming: packets flow down; each DataNode verifies checksums, writes to disk, forwards; acks flow up.
  • Next block: when 128 MB are written, close the pipeline and repeat addBlock.
  • complete: NameNode marks the file closed; put renames ._COPYING_ to the final name.

Advanced Failures and guarantees

  • Setup failure (a DataNode can't be reached): the client abandons the block, excludes that node, and asks for a new block.
  • Failure while streaming: unacknowledged packets go back to the data queue, the bad DataNode is removed, the NameNode bumps the generation stamp, and streaming resumes on the survivors; under-replication is fixed afterwards.
  • Visibility: readers see data up to the last completed block, or what hflush() has pushed; hsync() also forces it to disk.
  • Single writer, append only: HDFS files can't be edited in the middle.

Exam tip: “Explain the anatomy of a file write in HDFS”: client → create() → NameNode checks and adds the file → client's DataStreamer asks for blocks → NameNode returns a list of DataNodes → pipeline DN1 → DN2 → DN3 → data sent as packets; ack queue holds packets until all DataNodes acknowledge → close() → complete() on the NameNode. Mention failure handling and the default rack-aware placement.

5 See it happen

A block travels down the pipeline

The first block of orders_x30.csv, using the real log lines from step 1 to 3.

Writing blk_1073741840 6 steps
What you see
  1. The client asks the NameNode to create the file (under a temporary name).
  2. The client asks for a block; the NameNode picks three DataNodes: the local one (.4) and two in the other rack.
  3. The client connects only to .4. Each DataNode connects to the next one.
  4. Packets stream down; each packet is acknowledged by all three DataNodes.
  5. After 2,083 packets the block is full. Each DataNode tells the NameNode it has a finished replica.
  6. The second block repeats the process; then the file is completed and renamed.
Behind the screen
  1. Only metadata goes to the NameNode: the file is created and the client gets a lease.
  2. For each block, the NameNode chooses DataNodes using the rack-aware policy.
  3. The client opens a connection to dn-1, which opens one to dn-3, which opens one to dn-4.
  4. Data (blue) flows down; acks (green) flow back. A packet leaves the ack queue only when all three have it.
  5. When the block is complete, each DataNode reports its replica to the NameNode in an incremental block report.
  6. The file is closed. The client's network sent the data once; the DataNodes shared the copying.
6 Real-world use

The write pipeline at work

1. Bulk ingestion from edge nodes

Daily exports land on an edge node and are pushed with hdfs dfs -put or DistCp. The edge node's network link limits speed, but each byte leaves it only once; replication is the DataNodes' work.

Edge node→Pipeline→3 replicas

2. Logs written while still open

Log collectors and streaming sinks keep a file open for minutes and call hflush() regularly so readers can see recent lines before the file is closed.

Write→hflush→Visible to readers

3. One slow disk slows many writes

A pipeline moves at the speed of its slowest DataNode. Operations teams watch per-DataNode write latency and exclude or repair slow nodes, because one bad disk can delay every job that writes through it.

Slow disk→Slow acks→Slow jobs

4. Jobs survive DataNode failures

When a DataNode dies during a big job, thousands of task writes recover their pipelines exactly as in step 4 and carry on; the NameNode restores full replication afterwards. Users usually never notice.

Node dies→Pipelines recover→Re-replication later

Simplified; organisations differ in tools and policies.

7 Run the code

Simulate a pipeline with acknowledgements

This program sends packets down a three-DataNode pipeline. Each packet stays in the ack queue until every DataNode has stored it. Watch which packets are still unacknowledged at each step.

from collections import deque

pipeline = ["dn-1", "dn-3", "dn-4"]
stored = {dn: [] for dn in pipeline}
data_queue = deque(range(5))          # packet numbers 0..4
ack_queue = deque()

while data_queue or ack_queue:
    if data_queue:
        p = data_queue.popleft()
        for dn in pipeline:            # dn-1 stores and forwards, and so on
            stored[dn].append(p)
        ack_queue.append(p)
        print(f"sent packet {p}  waiting for acks: {list(ack_queue)}")
    if len(ack_queue) > 1 or not data_queue:
        done = ack_queue.popleft()     # acks come back in order
        print(f"  ack for packet {done} from {len(pipeline)} DataNodes")

for dn, packets in stored.items():
    print(dn, "has", packets)

Interview and viva questions

How does a client write a file to HDFS?

It asks the NameNode to create the file, then for each block asks for a list of DataNodes. It streams the block as packets to the first DataNode, which stores and forwards them to the second, which forwards to the third. Acknowledgements come back along the pipeline. When all data is written, the client tells the NameNode the file is complete.

Does the data pass through the NameNode during a write?

No. The NameNode only handles metadata: creating the file, allocating blocks and recording finished replicas. Data flows from the client to DataNodes and between DataNodes.

What happens if a DataNode fails during a write?

The client detects the error, removes that DataNode from the pipeline, moves unacknowledged packets back to the data queue, gets a new generation stamp for the block from the NameNode, and continues with the remaining DataNodes (possibly adding a replacement). The NameNode re-replicates the block later.

What is the generation stamp?

A version number attached to each block (the part after the last underscore in blk_1073741847_1024). It is increased during pipeline recovery or append so that replicas left behind on failed DataNodes are recognised as stale and deleted.

When can other clients read a file that is being written?

They can always see the file, and data in completed blocks. Data in the block being written becomes visible after hflush() (or when the block or file is closed). Only one client can write to a file at a time.

Why is data sent in packets instead of whole blocks?

So that DataNodes can start forwarding while still receiving, keeping all three copies moving at once, and so that a failure only requires resending a few small packets, not a whole 128 MB block.

P8Advanced

Simulate recovery with resend

Simulate 6 packets where dn-3 fails after acknowledging packet 2. Count packets each surviving DataNode stores, including resent ones (stored once each).

Input
6 packets · dn-3 fails after packet 2
Expected output
{'dn-1': [0, 1, 2, 3, 4, 5], 'dn-3': [0, 1, 2], 'dn-4': [0, 1, 2, 3, 4, 5]}
Show solution and explanation 
pipeline = ["dn-1", "dn-3", "dn-4"]
stored = {d: set() for d in pipeline}
for p in range(6):
    if p == 3:
        pipeline.remove("dn-3")
    for d in pipeline:
        stored[d].add(p)
print({d: sorted(s) for d, s in stored.items()})
{'dn-1': [0, 1, 2, 3, 4, 5], 'dn-3': [0, 1, 2], 'dn-4': [0, 1, 2, 3, 4, 5]}

How it works: dn-1 and dn-4 hold all 6 packets; dn-3 only 0–2, a stale partial replica that the generation stamp lets HDFS discard.

Real-world scenario questions (asked in company interviews)

The write path is a favourite deep-dive question. Real log lines make your answer stand out.

HDFS · internalsFresher

“Walk me through what happens when I run hdfs dfs -put”

The classic anatomy-of-a-write question.

The interviewer is checking: the order of steps and who talks to whom.

Show a strong answer
  • Client asks the NameNode to create file._COPYING_; NameNode checks permissions and existence and grants a lease.
  • For each block the NameNode returns a block ID and three DataNodes (local, other rack, same rack as the second).
  • Client streams ~64 KB packets to DN1, which stores and forwards to DN2, then DN3; acks return; packets wait in the ack queue until all confirm.
  • After the last block the client calls complete; the NameNode closes the file; put renames it to the final name.
HDFS · failureExperienced

A DataNode crashes during a large write. Does the job fail?

A Spark job is writing 2 TB when a worker node reboots.

The interviewer is checking: pipeline recovery details.

Show a strong answer
  • Each affected writer detects the failure (bad ack or timeout), removes the DataNode, puts unacknowledged packets back in its data queue and asks the NameNode to update the pipeline.
  • The NameNode bumps the block's generation stamp so the dead node's partial replica is stale; writing continues on the survivors (a replacement may be added depending on the policy).
  • The NameNode re-replicates the block afterwards. The job continues; only tasks running on the rebooted node itself are retried by YARN/Spark.
Performance · writesExperienced

Writes became slow cluster-wide after one disk started failing

Job write stages are 3× slower than last week. No DataNode is dead.

The interviewer is checking: that you know a pipeline runs at the speed of its slowest member.

Show a strong answer
  • Every write that includes the slow DataNode waits for its acks, so one bad disk slows many pipelines.
  • Look at DataNode metrics/logs for slow writes (e.g. “Slow BlockReceiver write data to disk” warnings) and the NameNode's slow-node reports.
  • Fix: mark the failing volume bad or decommission the node, replace the disk; consider enabling slow-node detection and exclusion.
Design · consistencyFresher

“Can two programs write to the same HDFS file at once?”

A student wants two scripts to append to one log file in HDFS.

The interviewer is checking: single-writer semantics and leases.

Show a strong answer
  • No. HDFS gives one writer a lease on a file; a second writer gets an exception until the lease is released or expires.
  • Design instead: each writer writes its own file (e.g. one per task or per hour) in the same directory, and readers process the directory.
  • This is exactly how MapReduce and Spark output works: part-00000, part-00001, …
