How a file is read

Reading a file from HDFS is a conversation with the NameNode followed by direct transfers from DataNodes. This lesson shows both on a real cluster: which DataNode serves each block depending on where the client runs, how every 512 bytes are checked, and what happens when we corrupt a replica on purpose: the reader gets correct data anyway, and HDFS repairs itself within seconds.

1 The story

Nearest copy first, and never trust a damaged one

Kabir reads the 5-block canteen file twice: once from the namenode container, once from datanode-2. From the namenode container the blocks come from datanode-2, then datanode-3 three times, then datanode-1. From datanode-2, every single block comes from datanode-2 itself. Then Riya does something wicked: she overwrites one byte of a block file on datanode-2's disk with an X, and reads again from datanode-2. A warning appears: Found Checksum error … at 499712. Yet the file that comes out is byte-for-byte identical to the original.

Arjun Sir

A read has two parts. First the client asks the NameNode “where are the blocks of this file?”. The NameNode answers with every block's replica locations, sorted by distance from the client. Then the client reads each block directly from the first DataNode in that list.

Kabir

And from the namenode container there was no “nearest”?

Arjun Sir

Right: it isn't a DataNode, and all three replicas were equally far, so the order was shuffled to spread the load. From datanode-2, its own disk is always closest. And the corrupted byte? Every 512 bytes of a block has a checksum. The client verified it, saw a mismatch, quietly fetched that part from another replica, and told the NameNode the copy on datanode-2 was bad. A few seconds later the NameNode had made a fresh copy elsewhere and deleted the bad one.

2 Definition

The HDFS read path

Formal definition (write this in exams)

To read a file, the client calls open; the DFSInputStream asks the NameNode (getBlockLocations) for the locations of the file's blocks, in batches. For each block the NameNode returns the DataNodes holding a replica, sorted by network distance from the client (local node, then same rack, then other racks; equal distances are shuffled). The client connects to the closest DataNode and streams the block directly; at a block boundary it moves to the best DataNode for the next block. Data is verified with checksums (one per 512 bytes) as it is read. On a checksum error or a DataNode failure, the client reads from the next replica, remembers the bad DataNode for that stream, and reports corrupt replicas to the NameNode (reportBadBlocks), which schedules re-replication from a good replica and deletes the corrupt one. The NameNode serves only metadata; data never passes through it.

In simple words

Ask the NameNode where the pieces are, then fetch each piece from the nearest machine that has it, checking every 512 bytes. If a piece is broken or a machine doesn't answer, use another copy and tell the NameNode.

The read path at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A library with photocopies

  • You ask the index desk: “Where is chapter 1?” The librarian lists shelves holding copies, the nearest first.
  • You walk to the nearest shelf and read it there. The librarian never fetches pages.
  • If a page is smudged, you take another copy and tell the librarian, who replaces the smudged one.

Intermediate Step by step

  • open(): client asks the NameNode for block locations of the first part of the file.
  • read(): connect to the first (closest) DataNode for block 0 and stream it, verifying checksums.
  • At the end of block 0, pick the best DataNode for block 1 (maybe a different one), and so on.
  • For long files, ask the NameNode for more locations as needed.
  • close(): release connections.

Advanced Robustness and performance

  • Failures: a DataNode that doesn't respond is added to the stream's dead-node list and the next replica is used.
  • Corruption: detected end-to-end by the client (checksums were created by the writer), so disk, network and memory errors are all caught.
  • DataNodes also run a background block scanner that finds corrupt replicas nobody has read for weeks.
  • Data locality in MapReduce and Spark is the same idea: put the task where the closest replica is distance 0.
  • Hedged reads (optional) start a second read from another replica if the first is slow.

Exam tip: “Explain the anatomy of a file read in HDFS”: client open() → NameNode returns block locations sorted by proximity → client reads each block directly from the nearest DataNode, verifying checksums → moves to the next block → on error, tries another replica and reports the bad block → close(). Stress that the NameNode never sends data.

If every replica of a block is corrupt or unavailable, the read fails with a BlockMissingException and fsck marks the file CORRUPT. Replication protects against independent failures, not against writing bad data in the first place.

5 See it happen

A read that survives a corrupt replica

Steps 3 to 6 from the lab, frame by frame.

Reading canteen_1mb.csv from datanode-2 6 steps
What you see
  1. Normally a client on datanode-2 reads every block from datanode-2 itself.
  2. We damage one byte of one replica on datanode-2's disk.
  3. The next read detects the damage: the 512-byte chunk at offset 499,712 fails its checksum.
  4. Still, the output is identical to the original file: the client read that block from another replica.
  5. The client reported the bad replica; the NameNode copied a good one to datanode-4.
  6. Three healthy replicas, none on datanode-2: the corrupt copy was deleted.
Behind the screen
  1. The NameNode sorted dn-2 first for this client, so it reads from its own machine.
  2. The replica on dn-2 now has one wrong byte; its stored checksums still describe the original data.
  3. The client recomputes the checksum of each 512-byte chunk as it reads; chunk 976 doesn't match.
  4. It discards that data and reads the block from the next replica in the list.
  5. It reports the corrupt replica; the NameNode schedules a copy from a good replica to dn-4.
  6. The corrupt replica on dn-2 is invalidated (deleted). The block is fully protected again.
6 Real-world use

The read path at work

1. Data-local tasks

Schedulers place map and Spark tasks on nodes holding a replica, so most reads are distance 0, like step 3. Job counters such as “Data-local map tasks” show how well this worked.

Block on dn-2→Task on dn-2→Local read

2. Short-circuit reads for fast engines

Interactive SQL engines and HBase enable short-circuit local reads so they read block files straight from disk, skipping the DataNode's network stack and cutting latency.

Local block→Read file directly→Lower latency

3. Silent disk errors caught

On thousands of disks, bit rot and bad sectors happen. Checksum errors show up as WARN lines and DataNode metrics; the data is healed automatically, and repeated errors on one disk tell admins to replace it.

Bad sector→Checksum error→Replace replica, then disk

4. Verifying copies between clusters

After copying data to a DR cluster, teams compare hdfs dfs -checksum (or let DistCp do it) instead of reading terabytes back to compare.

Copy→Compare checksums→Proven identical

Simplified; organisations differ in tools and policies.

7 Run the code

Sort replicas by distance, like the NameNode

This program computes the network distance from a client to each replica (0 same node, 2 same rack, 4 other rack) and sorts the replica list, shuffling ties as HDFS does. Try it for a client on a DataNode and for one outside the racks.

import random
random.seed(3)
rack = {"dn-1": "/rack1", "dn-2": "/rack1", "dn-3": "/rack2", "dn-4": "/rack2"}

def distance(client, dn):
    if client == dn:
        return 0
    if rack.get(client) == rack[dn]:
        return 2
    return 4

def sorted_replicas(client, replicas):
    shuffled = random.sample(replicas, len(replicas))     # ties in random order
    return sorted(shuffled, key=lambda dn: distance(client, dn))

replicas = ["dn-1", "dn-2", "dn-3"]
for client in ["dn-2", "dn-4", "edge-node"]:
    order = sorted_replicas(client, replicas)
    print(f"{client:9} reads from {order[0]}   (order {order})")
dn-2 reads from dn-2 (order ['dn-2', 'dn-1', 'dn-3']) dn-4 reads from dn-3 (order ['dn-3', 'dn-2', 'dn-1']) edge-node reads from dn-3 (order ['dn-3', 'dn-1', 'dn-2'])
  • if rack.get(client) == rack[dn]:A client that is not in any rack (like an edge node or our namenode container) never matches, so every replica is distance 4.
  • shuffled = random.sample(replicas, len(replicas)) # ties in random orderShuffling before a stable sort keeps the distance order but randomises equal distances, spreading load. That is why the off-cluster read used several DataNodes.

Interview and viva questions

How does a client read a file from HDFS?

It opens the file, which asks the NameNode for the locations of the file's blocks. For each block, the NameNode lists the DataNodes holding replicas sorted by distance from the client. The client reads each block directly from the closest DataNode, verifying checksums, then moves to the next block.

How does HDFS choose which replica to read?

The NameNode sorts replicas by network distance from the client: same node first, then same rack, then other racks, using the rack topology. Replicas at the same distance are shuffled so load is spread. The client tries them in that order.

How does HDFS detect corrupted data?

Writers compute a CRC checksum for every 512 bytes, stored in the .meta file next to each block replica. Readers recompute and compare. DataNodes also verify blocks in the background with the block scanner.

What happens when a client finds a corrupt block?

It reads that part from another replica, so the application still gets correct data, and reports the corrupt replica to the NameNode. The NameNode marks it corrupt, creates a new replica from a good copy and deletes the bad one.

What are short-circuit local reads?

When the client and the replica are on the same machine and dfs.client.read.shortcircuit is enabled (with a domain socket path), the client reads the block file directly from local disk using a file descriptor passed by the DataNode, avoiding the TCP data path.

Does reading put load on the NameNode?

Only for metadata: open and block location lookups. The data transfer itself is between client and DataNodes, which is why HDFS reads scale with the number of DataNodes.

Saving by locality

Core network capacity costs Rs 8 lakh per 10 Gbit/s per year. Without locality, a cluster would need 40 Gbit/s of core capacity; with locality, 4 Gbit/s. What is the yearly saving?

P8Advanced

Read with corruption and failover

Simulate reading 3 blocks with sorted replicas, where some replicas are corrupt and some DataNodes dead. Return the serving DataNode per block and the list of bad-block reports.

Input
3 blocks · corrupt {(1, dn-2)} · dead {dn-3}
Expected output
served: {0: 'dn-2', 1: 'dn-1', 2: 'dn-2'}  reported bad: [(1, 'dn-2')]
Show solution and explanation 
locs = {0: ["dn-2", "dn-1", "dn-3"], 1: ["dn-2", "dn-3", "dn-1"], 2: ["dn-3", "dn-2", "dn-1"]}
corrupt, dead = {(1, "dn-2")}, {"dn-3"}
served, reports = {}, []
for b, nodes in locs.items():
    for dn in nodes:
        if dn in dead:
            continue
        if (b, dn) in corrupt:
            reports.append((b, dn)); continue
        served[b] = dn; break
print("served:", served, " reported bad:", reports)
served: {0: 'dn-2', 1: 'dn-1', 2: 'dn-2'} reported bad: [(1, 'dn-2')]

How it works: Block 0 from dn-2, block 1 from dn-1 (after the corrupt dn-2 copy and dead dn-3), block 2 from dn-2. One bad-block report: block 1 on dn-2.

Real-world scenario questions (asked in company interviews)

Read-path questions test whether you understand locality and integrity, two of HDFS's core promises.

HDFS · internalsFresher

“Explain how HDFS reads a file”

The anatomy-of-a-read question.

The interviewer is checking: NameNode vs DataNode roles and replica choice.

Show a strong answer
  • Client opens the file; the NameNode returns block locations, each list sorted by distance from the client.
  • The client reads each block directly from the nearest DataNode, verifying 512-byte checksums, then moves to the next block.
  • On failure or checksum error it uses the next replica and reports bad replicas. The NameNode never transfers data.
Operations · integrityExperienced

Logs show many “Found Checksum error” warnings from one DataNode

Jobs still succeed, but the warnings keep appearing for different blocks on the same host.

The interviewer is checking: that you treat it as a hardware signal.

Show a strong answer
  • Clients are reading around corrupt replicas and HDFS re-replicates them, so data is safe for now.
  • Repeated errors on one host point to a failing disk, controller or memory. Check which volume the blocks are on, SMART data, kernel logs.
  • Mark the volume failed or decommission the node, replace the hardware, and run fsck to confirm no file has lost all good replicas.
Performance · localityExperienced

Reads from BI tools on the edge node are slow; jobs are fast

Analysts pull large files to an edge node and complain about speed.

The interviewer is checking: remote reads vs local reads.

Show a strong answer
  • The edge node isn't a DataNode, so every read is remote and limited by its network link; jobs read locally on DataNodes.
  • Move the heavy work into the cluster (Hive/Spark queries returning small results) instead of copying raw data out.
  • If raw transfers are needed: faster edge-node networking, parallel readers, or columnar formats so less data is read.
HDFS · reliabilityFresher

“If a disk silently flips a bit, will my report be wrong?”

A manager worries about silent data corruption.

The interviewer is checking: end-to-end checksums.

Show a strong answer
  • No (unless every replica is bad). Each 512 bytes has a checksum created when the data was written; readers verify it.
  • A mismatch makes the client read another replica and report the bad one, which HDFS replaces.
  • Real demo: one byte changed on disk → “Found Checksum error … at 499712” → output identical to the original.
