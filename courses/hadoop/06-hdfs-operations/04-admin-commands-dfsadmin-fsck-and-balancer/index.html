Admin commands: dfsadmin, fsck and balancer

Servers come and go: disks fail, new machines arrive. This lesson shows the tools that keep HDFS healthy through all of it, on a real 5-node cluster: dfsadmin to see and control the cluster, fsck to prove every block is safe, decommissioning to retire a DataNode without risk, and the balancer to spread data onto a new node.

1 The story

Retire one server, welcome another

Monday at the canteen-analytics team. Datanode-4's disk is throwing errors and must go back to the vendor, and a new server has arrived. Riya's first idea: switch datanode-4 off and plug the new one in. Her lead, Arjun, stops her. Switching a node off makes HDFS panic-copy its blocks only after 10 minutes, and until then some blocks have one copy fewer. The new server would sit almost empty while the old ones stay full. There are proper tools for both jobs, and a third one to prove that nothing was lost.

Arjun Sir

Just switching datanode-4 off would be a small disaster on purpose. The NameNode can't tell “retired” from “crashed”, so it waits until the node is declared dead and only then copies its blocks. Decommissioning tells it first: “copy everything this node holds to others, and tell me when it's safe”. On our lab that took one minute.

Riya

And the new server?

Arjun Sir

HDFS never moves existing blocks by itself. New files will use the new node, but the old data stays where it is. The balancer moves blocks from fuller nodes to emptier ones. And after all that, fsck confirms every file still has all its replicas. Today we run all of it.

2 Definition

HDFS administration tools

Formal definition (write this in exams)

hdfs dfsadmin is the administration client for the NameNode: it reports cluster capacity and DataNode status (-report), controls safe mode (-safemode), reloads the include/exclude host lists (-refreshNodes), shows the rack topology (-printTopology), and manages checkpoints, quotas and balancer bandwidth. hdfs fsck checks the health of the namespace: for each file it compares the expected replication with the live replicas and reports missing, corrupt, under- and over-replicated blocks, without repairing anything unless asked (-move, -delete). Decommissioning retires a DataNode by listing it in the file named by dfs.hosts.exclude and running -refreshNodes; the NameNode re-replicates all its blocks to other nodes before marking it Decommissioned. The balancer (hdfs balancer) moves block replicas from over-utilised to under-utilised DataNodes until every node's utilisation is within -threshold percent of the cluster average, never reducing a block's replication or breaking rack placement.

In simple words

dfsadmin is the dashboard and control panel, fsck is the health check-up, decommission is a proper farewell for a server, and the balancer is the shelf-arranger who moves boxes from crowded shelves to empty ones.

Words you'll meet in this lesson

DecommissionRetire a DataNode after copying its blocks elsewhere.
Exclude fileThe file named by dfs.hosts.exclude: nodes listed there are decommissioned.
refreshNodesTells the NameNode to re-read the include/exclude files, without a restart.
RecommissionRemove a node from the exclude file and refresh: it becomes Normal again.
UtilisationHow full a DataNode is: used space as a % of its capacity.
ThresholdBalancer target: every node within this many % of the average (default 10).
IterationOne round of balancer planning and block moves.
Maintenance modeShort planned downtime for a node without copying all its blocks.

Defaults and limits (Hadoop 3.5.0, from the lab)

Balancer threshold10% by default; allowed range 1.0 to 100.0 (“Expecting a number in the range of [1.0, 100.0]”)
Balancer bandwidthdfs.datanode.balance.bandwidthPerSec = 104857600 (100 MB/s per DataNode)
Concurrent movesdfs.datanode.balance.max.concurrent.moves = 100
Gives up after5 iterations with no block moved (“max idle iteration = 5”)

fsckRead-only by default; -move / -delete change files

Admin tools at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner Like moving house

  • Decommission: before you leave a flat, you pack and move everything out. Only then do you hand back the keys.
  • Balancer: a new cupboard arrives empty; you move some things into it so no cupboard overflows.
  • fsck: walking through the house with the inventory list to check nothing is missing.

Intermediate The admin routine

  • Daily: hdfs dfsadmin -report (dead nodes? capacity?) and hdfs fsck / (HEALTHY?).
  • Retire a node: add it to the exclude file → -refreshNodes → wait for Decommissioned → stop it.
  • Add a node: start the DataNode (it registers itself) → run hdfs balancer, ideally at night.
  • Investigate a file: hdfs fsck path -files -blocks -locations -racks.

Advanced What experienced admins watch for

  • Decommission needs somewhere to put the copies: with 3 racks and replication 3, retiring a whole rack can stall placement.
  • A decommission stuck at “still has 1 blocks to replicate” usually means a block whose copies can't be placed (bad target, full disks, open files).
  • The balancer is safe to stop at any time (Ctrl+C); moved blocks stay moved. Raise -setBalancerBandwidth only when jobs are quiet.
  • Recommissioned nodes often lose their replicas as “excess” and come back nearly empty: plan a balancer run.
  • fsck on / of a huge cluster is heavy for the NameNode; run it on sub-trees or off-peak.

Exam tip: “What is decommissioning? How do you add and remove DataNodes?” Removing: add the host to dfs.hosts.exclude, run hdfs dfsadmin -refreshNodes, wait for status Decommissioned (blocks re-replicated), then stop the node. Adding: install Hadoop with the same configuration, start the DataNode (add it to dfs.hosts if an include list is used, then refreshNodes), and run the balancer.

3 Types and ways to use it

The commands you will actually use

ToolCommandWhat it tells or does

Ways to take a DataNode out

Decommission

Copies every block away first. For permanent removal. Took 48 to 60 s in our lab.

Safe, slow

Maintenance mode

For a reboot or short repair: blocks with enough other replicas are not copied; the node comes back with its data.

Planned, short

Just stop it

HDFS treats it as a failure: dead after about 10.5 minutes, then re-replication. Fine for crashes, wrong for planned work.

Unplanned

Stop many at once

Several nodes holding all replicas of a block = missing data. Always one at a time, or decommission together.

Dangerous

Run hdfs dfsadmin and hdfs balancer -help with no other arguments for the exact usage of your version. The balancer's own help describes the threshold as “Percentage of disk capacity”.

  8. Speed limits and mistakes

    hdfs dfsadmin -setBalancerBandwidth 52428800
hdfs balancer -threshold 0.5
hdfs dfsadmin -saveNamespace
    Balancer bandwidth is set to 52428800 Expecting a number in the range of [1.0, 100.0]: 0.5 saveNamespace: Safe mode should be turned ON in order to create namespace image.
    52428800 bytes = 50 MB/s per DataNode, applied at once. The threshold must be at least 1%. -saveNamespace is only allowed in safe mode, so the namespace doesn't change while it is written.

Never decommission (or stop) more nodes at once than your replication can survive, and never put every node of a rack in the exclude file unless the other racks have room for all those blocks. Watch -report -decommissioning until it is empty.

5 See it happen

Decommission, then balance

Block A lives on dn-2, dn-4 and dn-5. We retire dn-4, then add an empty dn-6.

Retire a node and fill a new one 6 steps
What you see
  1. Datanode-4 is Normal and holds 11 blocks.
  2. We list it in the exclude file and refresh: no restart needed.
  3. Status changes to “Decommission in progress”.
  4. 52 seconds later: Decommissioned, and fsck shows nothing under-replicated.
  5. A new, empty node appears; the balancer calls it underutilised.
  6. 8 blocks (914.72 MB) move to it in the first iteration.
Behind the screen
  1. Block A has 3 replicas: dn-2, dn-4, dn-5.
  2. dn-4 is marked decommissioning. Its replicas no longer count towards the 3, but it still serves reads.
  3. The NameNode asks dn-2 to copy A to dn-3, respecting rack placement.
  4. Every block of dn-4 now has 3 replicas elsewhere: Decommissioned.
  5. dn-6 joins with an empty disk. The average utilisation is far above its 0%, so it is underutilised.
  6. The balancer copies block B to dn-6 and deletes one source replica: still 3 copies, just better spread.
6 Real-world use

Admin tools at work

1. Hardware refresh

A bank replaces 200 five-year-old DataNodes. New nodes are added and balanced first; old ones are decommissioned a few at a time, each batch confirmed with fsck before the next. Users notice nothing.

Add new→Balance + decommission→Remove old

2. Night-time balancing

Teams schedule hdfs balancer -threshold 10 at night and raise the bandwidth for those hours with -setBalancerBandwidth, then lower it before office jobs start.

Scheduler→balancer→Even disks by morning

3. Monitoring and alerts

Monitoring reads the same numbers as -report (dead nodes, missing and under-replicated blocks) from the NameNode's metrics and pages the on-call engineer when missing blocks are above zero.

NameNode metrics→Alert rules→On-call

4. Patching without copying terabytes

For a 20-minute OS patch, admins put a node into maintenance mode instead of decommissioning it, so HDFS doesn't copy its many terabytes away and back.

Maintenance→Patch + reboot→In service

Simplified; organisations differ in tools and policies.

7 Run the code

A balancer in 30 lines

This program does what hdfs balancer does, simplified: compute each node's utilisation (used ÷ capacity) and the cluster average, then move 128 MB blocks from the fullest node to the emptiest until every node is within the threshold of the average.

cap = {"dn-1": 4000, "dn-2": 4000, "dn-3": 4000, "dn-6": 4000}    # MB
used = {"dn-1": 3200, "dn-2": 3072, "dn-3": 2944, "dn-6": 0}
threshold = 10          # percent
block = 128             # MB

def util(n):
    return 100 * used[n] / cap[n]

def average():
    return 100 * sum(used.values()) / sum(cap.values())

moves = 0
while True:
    avg = average()
    src = max(used, key=util)
    dst = min(used, key=util)
    if util(src) - avg <= threshold and avg - util(dst) <= threshold:
        break
    used[src] -= block
    used[dst] += block
    moves += 1

print(f"average {average():.1f}%  moves {moves}  ({moves * block} MB)")
for n in cap:
    print(f"  {n}: {util(n):5.1f}%")
average 57.6% moves 15 (1920 MB) dn-1: 60.8% dn-2: 60.8% dn-3: 60.8% dn-6: 48.0%
  • return 100 * used[n] / cap[n]Utilisation is a percentage of capacity, not a block count. That is why a big new disk with 0 blocks is “underutilised”.
  • if util(src) - avg <= threshold and avg - util(dst) <= threshold:Balanced = every node within ±threshold of the average. Here 10%, the default; the real tool accepts 1 to 100.
  • used[src] -= blockA real move copies the block to the target and then deletes the source replica, so replication never drops.

Run it on your PC: retire a node, fill a new one

Two scripts for the hdfs-lab folder. The first decommissions a DataNode and prints its status every few seconds until it is Decommissioned, checks fsck and recommissions it. The second starts a sixth DataNode with its own small disk and runs the balancer. First add HDFS-SITE.XML_dfs.hosts.exclude=/opt/hadoop/etc/hadoop/dfs.exclude to the config file and recreate the namenode (docker compose up -d).

Decommission and recommission one DataNode

#!/usr/bin/env bash
# decommission_watch.sh: retire one DataNode safely and watch HDFS copy its blocks away.
# Needs dfs.hosts.exclude=/opt/hadoop/etc/hadoop/dfs.exclude in the NameNode's hdfs-site.xml.
# Run from the hdfs-lab folder:  bash decommission_watch.sh 172.19.0.4
IP=${1:?give the DataNode IP}
NN="docker exec lab5-namenode-1"
status() { $NN hdfs dfsadmin -report 2>/dev/null | grep -m1 -A20 "^Name: $IP:" |
           grep -E "Decommission Status|Num of Blocks" | sed 's/ : /: /' | paste -sd'|' | sed 's/|/,  /'; }
echo "before:  $(status)"
$NN bash -c "echo $IP > /opt/hadoop/etc/hadoop/dfs.exclude"
$NN hdfs dfsadmin -refreshNodes
start=$(date +%s)
while true; do
  s=$(status); echo "t=$(( $(date +%s) - start ))s  $s"
  [[ $s == *"Status: Decommissioned"* ]] && break
  sleep 5
done
$NN bash -c "hdfs fsck / 2>/dev/null | grep -E 'Status:|Under-replicated|Number of data-nodes'"
echo "### recommission"
$NN bash -c "> /opt/hadoop/etc/hadoop/dfs.exclude"
$NN hdfs dfsadmin -refreshNodes
sleep 10; echo "after:   $(status)"

Check yourself

Quick revision

Lesson 6.4 in one screen

  • hdfs dfsadmin -report: capacity, dead nodes, missing / under-replicated blocks, per-node status.
  • hdfs fsck path -files -blocks -locations -racks: health from metadata; read-only by default.
  • Decommission: host in dfs.hosts.exclude → -refreshNodes → Decommission in progress → Decommissioned → stop. Lab: 52 s and 60 s.
  • Recommission: remove from the exclude file + refresh; excess replicas are deleted, so the node may come back empty.
  • New nodes are not filled automatically: run hdfs balancer [-threshold 10].
  • Balanced = every node within threshold % (of capacity) of the average; range 1 to 100.
  • Lab balancer: 8 blocks, 914.72 MB in 16 s; then “Out of space” and exit after 5 idle iterations.
  • Bandwidth: 100 MB/s per node by default; change live with -setBalancerBandwidth.

Interview and viva questions

What is DataNode decommissioning in HDFS?

The safe way to remove a DataNode. You list it in the exclude file (dfs.hosts.exclude) and run hdfs dfsadmin -refreshNodes. The NameNode copies all its block replicas to other nodes while it keeps serving reads. When every block has enough replicas elsewhere, its status becomes Decommissioned and it can be shut down.

How do you add a new DataNode to a running cluster?

Install Hadoop with the cluster's configuration on the new machine and start the DataNode; it registers with the NameNode on its own. If an include file (dfs.hosts) is used, add it there and run -refreshNodes. Then run the balancer so existing data spreads onto it.

What does the HDFS balancer do?

It moves block replicas from DataNodes whose utilisation is above the cluster average to those below it, until every node is within the threshold (default 10%) of the average. Each move copies the block to the target and then removes one source replica, respecting rack placement, so replication is unchanged.

Is it safe to stop the balancer in the middle?

Yes. Each block move is complete or not done at all; stopping the balancer leaves the cluster partly balanced but fully consistent. You can rerun it later.

What is the difference between fsck in Linux and hdfs fsck?

Linux fsck checks and repairs a local file system's structures. hdfs fsck reports HDFS health from the NameNode: missing, corrupt and under-replicated blocks per file. It does not repair; HDFS repairs replicas itself, and -move or -delete only deal with files that have lost all good replicas.

Why is a decommission stuck in progress?

Usually some blocks cannot get new replicas: not enough nodes or racks for the placement policy, full disks, a failing target node, or files still open for writing. The NameNode log shows lines like “still has 1 blocks to replicate”, and hdfs fsck or -report -decommissioning help find them.

P8Advanced

Decommission planner

Simulate decommissioning dn-4: for each of its blocks choose a target node that does not already hold the block, prefers keeping replicas on 2 racks, and has the most free space. Print the plan.

Input
4 blocks · 2 racks · free space per node
Expected output
A copy to dn-1 racks [1, 2]
B copy to dn-2 racks [1, 2]
D copy to dn-2 racks [1, 2]
Show solution and explanation 
rack = {"dn-1": 1, "dn-2": 1, "dn-3": 2, "dn-4": 2, "dn-5": 2}
free = {"dn-1": 50, "dn-2": 80, "dn-3": 30, "dn-5": 60}
blocks = {"A": ["dn-2", "dn-4", "dn-5"], "B": ["dn-4", "dn-1", "dn-3"], "D": ["dn-4", "dn-3", "dn-5"]}
for b, nodes in blocks.items():
    if "dn-4" not in nodes:
        continue
    keep = [n for n in nodes if n != "dn-4"]
    racks = {rack[n] for n in keep}
    cands = [n for n in free if n not in keep]
    if len(racks) == 1:                       # all others on one rack: need the other rack
        cands = [n for n in cands if rack[n] not in racks]
    target = max(cands, key=free.get)
    free[target] -= 1
    print(b, "copy to", target, "racks", sorted(racks | {rack[target]}))
A copy to dn-1 racks [1, 2] B copy to dn-2 racks [1, 2] D copy to dn-2 racks [1, 2]

How it works: A goes to dn-1 (dn-2 and dn-5 already span both racks, so the most free space wins after dn-2 is excluded). B goes to dn-2. D (left only on rack 2) must go to rack 1: dn-2. Real NameNodes apply the same ideas with more rules.

Real-world scenario questions (asked in company interviews)

Admin questions separate people who have run a cluster from people who have only read about one.

HDFS · operationsFresher

“How do you remove a DataNode from a cluster?”

The classic commissioning and decommissioning question.

The interviewer is checking: exclude file, refreshNodes, waiting for completion.

Show a strong answer
  • Add the host to the file named by dfs.hosts.exclude, run hdfs dfsadmin -refreshNodes.
  • Watch -report until the status is Decommissioned; the NameNode copies all its blocks meanwhile. Then stop the DataNode and remove it.
  • Confirm with hdfs fsck /: HEALTHY, 0 under-replicated. Never just switch it off.
Operations · capacityExperienced

New nodes added last month are almost empty

Old DataNodes are at 92% and jobs fail with disk-full errors, while 10 new nodes are at 8%.

The interviewer is checking: that HDFS never rebalances existing data on its own.

Show a strong answer
  • Only new writes land on new nodes; existing blocks stay put. Run hdfs balancer -threshold 10 (or lower).
  • Run it off-peak, raise -setBalancerBandwidth at night, and repeat until balanced.
  • Short term, free space on the full nodes (old temp data, trash) so jobs stop failing.
TroubleshootingExperienced

Decommission has been “in progress” for a day

The NameNode log repeats “still has 1 blocks to replicate”.

The interviewer is checking: placement constraints and stuck blocks.

Show a strong answer
  • Find the block in the log (BlockStateChange lines show its replicas) and its file with hdfs fsck.
  • Typical causes: no node/rack where a replica may go (small cluster, whole rack being retired), full or failing target disks, a file still open for writing, or replication higher than the node count.
  • Fix the cause: add capacity, close or recover the file, lower its replication; in our lab a broken target node kept failing until its pending copy timed out (5 minutes) and another node was chosen.
HDFS · healthFresher

“What does hdfs fsck tell you?”

A quick check of whether you know what fsck reads and changes.

The interviewer is checking: read-only report vs repair.

Show a strong answer
  • For a path: files, blocks, replicas (with -files -blocks -locations -racks), and totals of missing, corrupt, under- and over-replicated blocks; status HEALTHY or CORRUPT.
  • It reads NameNode metadata only and changes nothing unless you pass -move or -delete.
  • HDFS repairs under-replicated blocks itself; fsck tells you whether anything is beyond repair.
