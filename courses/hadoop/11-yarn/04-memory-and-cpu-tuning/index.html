Memory and CPU tuning

YARN hands out memory and CPU in containers of fixed steps, and inside each container a JVM has its own, smaller heap. This lesson measures both on our three-worker cluster: how requests are rounded, how many containers fit, when CPU counts, and how a heap that is too small fails a job. Then it sizes a real production server with the same rules.

2 Definition

YARN memory and CPU tuning

Formal definition (write this in exams)

Memory and CPU tuning in YARN is the configuration of how much of each node's resources YARN may allocate and how large each container and its process may be. Each NodeManager advertises a capacity (yarn.nodemanager.resource.memory-mb, yarn.nodemanager.resource.cpu-vcores), which must leave room for the operating system and co-located daemons. Applications request containers of a given memory and number of virtual cores; the scheduler normalizes each request up to a multiple of yarn.scheduler.minimum-allocation-mb and rejects requests above the maximum allocation. A resource calculator decides which dimensions are compared: the DefaultResourceCalculator uses memory only, while the DominantResourceCalculator uses memory and CPU (Dominant Resource Fairness). Inside a container, the JVM heap (-Xmx, set via mapreduce.map.java.opts or a heap-to-container ratio) must be smaller than the container, leaving room for off-heap memory; exceeding the heap raises an OutOfMemoryError, while exceeding the container's physical memory causes the NodeManager to kill it when memory checks are enabled.

In simple words

Decide how much of each machine YARN may hand out, what size the pieces are, and how big the Java program inside each piece may grow. Pieces too big: few tasks run at once. Pieces too small: tasks crash.

Tuning at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A hostel's rooms and beds

  • A hostel building (node) has 2048 sq ft that the warden (YARN) may rent out; the rest is corridors and the warden's office (OS and daemons).
  • Rooms come only in fixed sizes of 256 sq ft. Ask for 384 and you get 512: the room size is rounded up.
  • Inside your room, your cupboard (heap) is smaller than the room. If you stuff more clothes than the cupboard holds, it bursts (Java heap space), even if the room has space.
  • Bigger rooms mean fewer students fit in the building: 12 rooms of 512 vs 6 of 1024 in our cluster.

Intermediate The settings and how they connect

  • Node: yarn.nodemanager.resource.memory-mb and …cpu-vcores say what a NodeManager offers. Ours: 2048 MB, 2 vcores.
  • Scheduler: yarn.scheduler.minimum-allocation-mb (step) and …maximum-allocation-mb (cap). A 1100 MB request became 1280 MB.
  • Job: mapreduce.map.memory.mb (container) and mapreduce.map.java.opts=-Xmx… (heap). Rule of thumb: heap ≈ 80% of the container. Since Hadoop 3 you may set only the container and let mapreduce.job.heap.memory-mb.ratio (0.8) derive the heap.
  • AM: yarn.app.mapreduce.am.resource.mb (ours 512) is a container too, and counts against the cluster.

Advanced CPU, fairness and safety nets

  • With the DefaultResourceCalculator (the default for the Capacity Scheduler), vcores are recorded but not enforced in placement: our nodes got 12 containers with 1 vcore each on 6 real vcores.
  • The DominantResourceCalculator compares each request on its dominant share (memory or CPU). Our cluster then ran only 6 containers and left half the memory free: CPU had become the limit.
  • Placement is only half the story: to stop a process from using more than its share, NodeManagers use memory checks (yarn.nodemanager.pmem-check-enabled) or Linux cgroups for memory and CPU. Our lab has the memory checks switched off.
  • Tiny jobs can run in uber mode (mapreduce.job.ubertask.enable): all tasks inside the AM's container, saving container start-ups.

Exam tip: For “How do you configure memory for MapReduce on YARN?”, draw the stack (node RAM → yarn.nodemanager.resource.memory-mb → container mapreduce.map.memory.mb → heap -Xmx ≈ 80%), mention rounding to minimum-allocation-mb, and give the two failure modes: Java heap space (heap too small) and container killed for exceeding physical memory (heap or off-heap too big for the container).

DefaultResourceCalculator

Compares memory only. Simple, and fine when all jobs have similar CPU needs. Our lab: 12 containers on 6 vcores, CPUs oversubscribed 2×.

DominantResourceCalculator

Each request is judged by its largest share of the cluster. Mixes of CPU-heavy and memory-heavy jobs are shared fairly. Our lab: 6 containers, CPU full, memory half used.

Animated example: sizing a telecom billing job

A telecom operator processes call detail records (CDRs) every night on 20 workers with 96 GB each for YARN. Follow one wrong guess and its fix.

From request to running containers 6 steps
Animated example
  1. The developer asks for 3000 MB map containers with a 2400 MB heap.
  2. With a 1024 MB minimum allocation, YARN rounds 3000 up to 3072 MB.
  3. Each 96 GB node fits 32 such containers: 640 maps run at once on 20 nodes.
  4. The maps load a big lookup table and fail with “Java heap space”: the heap, not the container, is too small.
  5. The fix raises the container to 4096 MB and the heap to 80% of it.
  6. The job succeeds with 24 containers per node. Bigger containers mean fewer at once.

Size containers from the task's real needs, not from the node. Look at “Peak Map Physical memory” and GC time in the job counters (Lesson 8.1 showed about 290 MB for a 4.7 MB file), add headroom, and round to your minimum allocation.

  4. Switch to the DominantResourceCalculator (and crash the RM first)

    Now every container's dominant share is CPU (1 of 2 vcores is 50% of a node, 512 of 2048 MB only 25%). Each node takes 2 containers, half the memory stays free. Safer for CPU-heavy work, but half as many tasks at once here.

  6. Make a map run out of heap, then fix it

    hadoop jar mr11.jar HeapHog -D mapreduce.map.java.opts=-Xmx64m \
  -D mapreduce.input.fileinputformat.split.maxsize=33554432 /user/hadoop/data/orders_x30.csv /out/hog64

  -D mapreduce.input.fileinputformat.split.maxsize=33554432 /user/hadoop/data/orders_x30.csv /out/hog300
    -Xmx64m: failed with state FAILED 7 Error: Java heap space Failed map tasks=10 Launched map tasks=15 kept 415,675 lines; heap used 54 MB of max 64 MB -Xmx300m: completed successfully Launched map tasks=5 kept 2,147,952 lines; heap used 222 MB of max 300 MB
    HeapHog keeps every line in a list (a common bug: collecting instead of streaming). A 32 MB split holds about 21 lakh lines, roughly 100 bytes each once they are Java objects. With 64 MB of heap only the small last split survived; each big split failed 4 times and the job was failed. 300 MB was enough: the container (512 MB) had room for it.

Raising -Xmx without raising the container is a trap. In our lab the memory checks are off, so a too-big heap would simply eat into other containers' memory. On a production cluster with pmem-check or cgroups, the NodeManager kills the container (“is running beyond physical memory limits … Killing container”, exit code 143). We did not reproduce that message here.

6 Real-world use

Tuning at work

1. Telecom: nightly billing on fixed-size containers

Billing jobs join call records with tariff tables. Platform teams set a standard map size (e.g. 4 GB, heap 80%) and let only a few approved jobs ask for more, so the cluster packs predictably.

Job profile→Standard container size→Predictable waves

2. Hospital analytics: CPU-heavy and memory-heavy jobs together

Image-feature extraction burns CPU; patient-record joins need memory. With the DominantResourceCalculator neither kind can starve the other by grabbing only one resource.

Mixed workloads→DominantResourceCalculator→Fair CPU + memory

3. E-commerce sale day: watching GC before it hurts

Before a big sale, data teams replay a day of clickstream and check “GC time elapsed” and peak memory counters. Jobs spending more than about 10% of task time in GC get bigger heaps or smaller splits.

Rehearsal run→Counters: GC, peak memory→Resize before the sale

4. Spark on YARN: executor memory plus overhead

A Spark executor asks YARN for spark.executor.memory plus spark.executor.memoryOverhead (by default 10%, at least 384 MB), then rounded up. An 8 GB executor becomes about a 9 GB container: forget the overhead and the sizing math is off.

executor 8g→+ overhead 819 MB→container 9216 MB

5. Banking reports: many tiny jobs

Hundreds of small reconciliation jobs each read a few MB. Uber mode, or moving them out of MapReduce entirely, avoids paying a container start-up per task.

Tiny job→ubertask: tasks in the AM→Seconds saved per job

Simplified; organisations differ in tools and policies.

7 Run the code

A container sizing calculator

This reproduces our lab: round each request up to the minimum allocation, then pack containers onto nodes by memory only (DefaultResourceCalculator) or by memory and CPU (DominantResourceCalculator). The AM goes first, as in YARN.

import math
MIN_MB = 256
NODES = [{"mb": 2048, "vc": 2} for _ in range(3)]

def normalize(mb):
    return math.ceil(mb / MIN_MB) * MIN_MB          # always rounded UP

def pack(map_mb, n_maps, am_mb=512, use_cpu=False):
    free = [dict(n) for n in NODES]
    asks = [normalize(am_mb)] + [normalize(map_mb)] * n_maps
    placed = 0
    for ask in asks:
        for n in free:
            if n["mb"] >= ask and (not use_cpu or n["vc"] >= 1):
                n["mb"] -= ask
                n["vc"] -= 1
                placed += 1
                break
    used = sum(2048 - n["mb"] for n in free)
    return placed, used

for mb in [300, 384, 600, 1100]:
    print(f"map asks {mb:4} MB -> granted {normalize(mb)} MB")
print("384 MB maps, memory only:", pack(384, 24))
print("1024 MB maps, memory only:", pack(1024, 24))
print("384 MB maps, DRF (CPU too):", pack(384, 24, use_cpu=True))
map asks 300 MB -> granted 512 MB map asks 384 MB -> granted 512 MB map asks 600 MB -> granted 768 MB map asks 1100 MB -> granted 1280 MB 384 MB maps, memory only: (12, 6144) 1024 MB maps, memory only: (6, 5632) 384 MB maps, DRF (CPU too): (6, 3072)

A map that keeps every line in memory

// HeapHog.java: a deliberately memory-hungry map-only job. Each map task keeps EVERY line it reads
// in a list (a common real-world bug: collecting instead of streaming), then writes how many it kept.
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;
import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.Path;
import org.apache.hadoop.io.LongWritable;
import org.apache.hadoop.io.NullWritable;
import org.apache.hadoop.io.Text;
import org.apache.hadoop.mapreduce.Job;
import org.apache.hadoop.mapreduce.Mapper;
import org.apache.hadoop.mapreduce.lib.input.FileInputFormat;
import org.apache.hadoop.mapreduce.lib.output.FileOutputFormat;
import org.apache.hadoop.util.GenericOptionsParser;

public class HeapHog {
  public static class M extends Mapper<LongWritable, Text, NullWritable, Text> {
    private final List<String> kept = new ArrayList<>();
    @Override
    protected void map(LongWritable k, Text line, Context ctx) { kept.add(line.toString()); }
    @Override
    protected void cleanup(Context ctx) throws IOException, InterruptedException {
      Runtime r = Runtime.getRuntime();
      String msg = String.format("kept %,d lines; heap used %d MB of max %d MB", kept.size(),
          (r.totalMemory() - r.freeMemory()) >> 20, r.maxMemory() >> 20);
      System.err.println(msg);
      ctx.write(NullWritable.get(), new Text(msg));
    }
  }

  public static void main(String[] args) throws Exception {
    Configuration conf = new Configuration();
    String[] rest = new GenericOptionsParser(conf, args).getRemainingArgs();
    Job job = Job.getInstance(conf, "heap hog");
    job.setJarByClass(HeapHog.class);
    job.setMapperClass(M.class);
    job.setNumReduceTasks(0);
    job.setOutputKeyClass(NullWritable.class);
    job.setOutputValueClass(Text.class);
    FileInputFormat.addInputPath(job, new Path(rest[0]));
    FileOutputFormat.setOutputPath(job, new Path(rest[1]));
    System.exit(job.waitForCompletion(true) ? 0 : 1);
  }
}

9 Quiz and revision

Check yourself

Quick revision

Lesson 11.4 in one screen

  • Stack: physical RAM → reserve for OS/daemons → yarn.nodemanager.resource.memory-mb → containers → JVM heap (-Xmx ≈ 80%) + off-heap.
  • Requests round UP to yarn.scheduler.minimum-allocation-mb: lab 300/384 → 512, 600 → 768, 1100 → 1280 MB.
  • Packing: 384 MB maps → 12 containers (6144 MB); 1024 MB maps → 6 (5632 MB, 512 MB stranded).
  • DefaultResourceCalculator = memory only (12 vcores handed out on 6); DominantResourceCalculator = memory + CPU (6 containers).
  • “Java heap space” → raise -Xmx (and the container) or stop collecting data in memory; “beyond physical memory” → bigger container or smaller heap.
  • Setting any CAPACITY-SCHEDULER.XML_ key in the apache/hadoop image rewrites the whole file: repeat the queues.
  • Spark on YARN: container = executor memory + overhead (max 384 MB, 10%), rounded up.

Interview and viva questions

How do you calculate the number of containers per node in YARN?

Take the memory the NodeManager offers (yarn.nodemanager.resource.memory-mb) and divide by the container size after rounding it up to a multiple of yarn.scheduler.minimum-allocation-mb. If the DominantResourceCalculator is used, also divide the node's vcores by the vcores per container and take the smaller number. Remember the ApplicationMaster also occupies a container.

What is the difference between mapreduce.map.memory.mb and mapreduce.map.java.opts?

mapreduce.map.memory.mb is the size of the YARN container for a map task: what YARN reserves and enforces. mapreduce.map.java.opts sets JVM options such as -Xmx, the maximum heap inside that container. The heap must be smaller than the container, typically about 80% of it, to leave room for off-heap memory.

What is the DominantResourceCalculator in YARN?

A resource calculator for the Capacity Scheduler that considers both memory and CPU. Each request is compared on its dominant share, the larger of its memory and CPU fractions, following Dominant Resource Fairness. The default DefaultResourceCalculator compares memory only, so CPU can be oversubscribed.

Why does YARN give a container more memory than requested?

The scheduler normalizes every request up to a multiple of yarn.scheduler.minimum-allocation-mb (and a similar increment for the Fair Scheduler). In our lab, with a 256 MB minimum, a 384 MB request became 512 MB and 600 MB became 768 MB.

How do you fix “Container is running beyond physical memory limits”?

The task process (heap plus off-heap) used more memory than its container. Either increase the container size (mapreduce.map.memory.mb or mapreduce.reduce.memory.mb) while keeping the heap around 80% of it, or reduce the heap or off-heap use (smaller buffers, less data held in memory). For Spark, raise spark.executor.memoryOverhead.

P8Advanced

DRF on our lab

Simulate DRF packing on our 3 nodes (2048 MB, 2 vcores) for an AM of 512 MB/1 vcore and 24 maps of 384 MB/1 vcore (rounded to 512). How many containers and how much memory are used?

Input
3 nodes · 1 AM + 24 maps
Expected output
6 containers, 3072 MB
Show solution and explanation 
nodes = [[2048, 2] for _ in range(3)]
placed = used = 0
for mb in [512] + [512] * 24:
    for n in nodes:
        if n[0] >= mb and n[1] >= 1:
            n[0] -= mb; n[1] -= 1; placed += 1; used += mb
            break
print(placed, "containers,", used, "MB")
6 containers, 3072 MB

How it works: 6 containers, 3072 MB: exactly the lab's “running containers 6 | memory 3072 of 6144 MB”.

Real-world scenario questions (asked in company interviews)

Memory and CPU sizing questions come up in every Hadoop and Spark platform interview, usually with a failure story attached.

YARN · basicsFresher

“What is the difference between container memory and heap memory?”

A standard opening question for YARN.

The interviewer is checking: the two limits and how they relate.

Show a strong answer
  • Container memory (mapreduce.map.memory.mb) is what YARN reserves on a node and can enforce.
  • Heap (-Xmx in mapreduce.map.java.opts) is the JVM\'s object space inside that container, about 80% of it.
  • Heap too small → OutOfMemoryError; heap plus off-heap too big → the NodeManager kills the container.
Operations · failuresExperienced

Jobs fail with “Java heap space” after a data volume increase

Nothing changed in the code; input doubled after a new region was added.

The interviewer is checking: diagnosis before throwing memory at it.

Show a strong answer
  • Find which tasks fail (map or reduce) and why: a reducer with a hot key, or code that collects values into a list.
  • Fix the code if it buffers data; reduce split size or add reducers to spread load.
  • If memory is really needed, raise the container and the heap together, keeping the 80% ratio.
Capacity · designExperienced

Size YARN for a new 40-node cluster of 256 GB / 48-core machines

Each node also runs a DataNode and an HBase RegionServer with a 32 GB heap.

The interviewer is checking: reserves, steps and CPU.

Show a strong answer
  • Reserve OS (~8 GB), DataNode (~4 GB), NodeManager (~2 GB) and RegionServer (32 GB + overhead): about 200 GB for YARN.
  • Pick a minimum allocation (e.g. 2 GB) and standard container sizes that divide the pool; keep 2–4 cores for daemons.
  • Use the DominantResourceCalculator if CPU-heavy jobs share the cluster; enable cgroups for isolation.
YARN · CPUFresher

“The ResourceManager UI shows more vcores used than the cluster has. Is it broken?”

A junior admin sees 12 vcores in use on a 6-vcore cluster.

The interviewer is checking: resource calculators.

Show a strong answer
  • Not broken: the Capacity Scheduler\'s DefaultResourceCalculator places containers by memory only, so vcores are recorded but not limited.
  • Switch to the DominantResourceCalculator so CPU is respected; in our lab that cut 12 containers to 6.
  • For real CPU isolation, enable the LinuxContainerExecutor with cgroups.
