Logs and debugging

A failed job leaves logs on every machine it touched. YARN collects them into HDFS so you can read any container's log from one terminal. This lesson takes one real failed job and walks from the vague client error to the exact line of code and the exact input record, then shows where every kind of log lives and how to read them quickly.

2 Definition

Logs and debugging on YARN

Formal definition (write this in exams)

A YARN cluster produces two kinds of logs. Daemon logs are written by the long-running services (ResourceManager, NodeManager, NameNode, DataNode, JobHistory Server) into $HADOOP_LOG_DIR. Container logs (stdout, stderr and syslog) are written by each application container into the NodeManager's local log directories (yarn.nodemanager.log-dirs) while it runs. With log aggregation enabled (yarn.log-aggregation-enable), each NodeManager uploads the container logs of a finished application into one file per node under yarn.nodemanager.remote-app-log-dir in HDFS (default /tmp/logs/<user>/…) and deletes the local copies; they are kept for yarn.log-aggregation.retain-seconds. The yarn logs command and the web UIs of the ResourceManager (port 8088), NodeManagers (8042) and the MapReduce JobHistory Server (19888) read them. Debugging a failed application means moving from the client's summary to the application diagnostics, then to the failed task attempt's log, its exception and source line, and finally to the input that caused it.

In simple words

Every container writes a diary on the machine where it ran. When the job ends, YARN collects all those diaries into HDFS, so you can read any of them from one terminal with yarn logs. Debugging is reading them in the right order.

Logs at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner A hospital file

  • Every patient (container) gets notes written by the nurse on their ward (NodeManager). The hospital's own registers (daemon logs) are separate.
  • When the patient is discharged, the notes go to the central records room (HDFS). Anyone with permission can ask for them by patient number (yarn logs -applicationId).
  • A doctor reads the summary first (diagnostics), then the detailed notes of the bad night (the failed attempt's syslog).

Intermediate The commands you'll use

  • yarn application -status <app>: final state and diagnostics.
  • yarn logs -applicationId <app> -show_application_log_info: which containers left logs, on which node.
  • yarn logs -applicationId <app> -containerId <c> -log_files syslog: one container, one file.
  • yarn logs -applicationId <app> -am 1: the ApplicationMaster's log (first attempt).
  • -D mapreduce.map.log.level=DEBUG: more detail from map tasks, for one run only.

Advanced Operating logs on a big cluster

  • Aggregation creates one HDFS file per node per app: a busy cluster can add lakhs of files a day. Retention (retain-seconds) and the newer IndexedFile format keep this under control (Lesson 7.5's small files problem again).
  • yarn.nodemanager.delete.debug-delay-sec (600 in our lab) keeps local container directories for a while after an app ends, so you can inspect files a task left behind.
  • Daemon logs rotate by size (log4j); ship them to a central system (ELK, Loki, Splunk) so you can search across machines and over time.
  • Change a running daemon's log level without a restart: yarn daemonlog -setlevel host:8088 <logger> DEBUG, and set it back afterwards.

Exam tip: For “How do you debug a failed MapReduce job on YARN?”, list the order: client error → yarn application -status diagnostics → yarn logs of the failed attempt's container (syslog/stderr) → exception and line number → find the input record → fix and add a guard (counter). Mention log aggregation to HDFS and the JobHistory UI on port 19888.

4 Step by step

From FAILED to the bad record, on our cluster

We run the revenue job from Lesson 8.1 on the messy file from Lesson 8.3. ItemRevenue skips lines with the wrong number of fields, but it has no check for a bad amount. The whole session is logs_lab.sh in “Run it on your PC”.

  1. Read what the client says

    hadoop jar mr.jar ItemRevenue /user/hadoop/data/dirty_orders.csv /out/dbg
    Error: java.lang.NumberFormatException: For input string: "abc" Failed map tasks=10 Job job_1792655556966_0006 failed with state FAILED due to: Task failed task_1792655556966_0006_m_000001 Task Id : attempt_1792655556966_0006_m_000000_0, Status : FAILED Task Id : attempt_1792655556966_0006_m_000000_1, Status : FAILED Task Id : attempt_1792655556966_0006_m_000000_2, Status : FAILED
    Each failed attempt is retried (up to 4 per task). Ten failed attempts and one task that used up all its tries ended the job. The client prints only the first line of each error.

  2. Ask the ResourceManager

    yarn application -status application_1792655556966_0006
    State : FINISHED Final-State : FAILED Tracking-URL : http://historyserver:19888/jobhistory/job/job_1792655556966_0006 Diagnostics : Task failed task_1792655556966_0006_m_000001 Job failed as tasks failed. failedMaps:1 failedReduces:0 killedMaps:0 killedReduces: 0
    State FINISHED but Final-State FAILED: YARN ran the application to its end; the application itself reports failure. The tracking URL now points to the JobHistory Server.

  3. See which containers left logs

    yarn logs -applicationId application_1792655556966_0006 -show_application_log_info
hdfs dfs -ls -R /tmp/logs/hadoop | grep application_1792655556966_0006
    Application State: Completed. Container: container_1792655556966_0006_01_000006 on worker1_36427 Container: container_1792655556966_0006_01_000010 on worker1_36427 Container: container_1792655556966_0006_01_000005 on worker2_40977 … 108540 /tmp/logs/hadoop/bucket-logs-tfile/0006/application_1792655556966_0006/worker1_36427 142851 /tmp/logs/hadoop/bucket-logs-tfile/0006/application_1792655556966_0006/worker2_40977
    Log aggregation packed all containers of this app from one node into one HDFS file. No need to log in to any worker.

  4. Read the failed attempt's syslog

    yarn logs -applicationId application_1792655556966_0006 \
  -containerId container_1792655556966_0006_01_000002 -log_files syslog
    WARN [main] org.apache.hadoop.mapred.YarnChild: Exception running child : java.lang.NumberFormatException: For input string: "abc" at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67) at ItemRevenue$OrderMapper.map(ItemRevenue.java:27) at ItemRevenue$OrderMapper.map(ItemRevenue.java:18)
    Read the stack trace from the top and stop at the first line that is your code: ItemRevenue.java:27, the Integer.parseInt(f[2]) line.

  5. Find the record

    hdfs dfs -cat /user/hadoop/data/dirty_orders.csv | grep -n -m3 ",abc$"
    1715:901714,chai,abc 6142:906141,chai,abc 6433:906432,chai,abc
    The exception message gave the bad value, so a search finds it. In a huge file, use the split range from the syslog to search only that part.

  6. Check the ApplicationMaster's view

    yarn logs -applicationId application_1792655556966_0006 -am 1 -log_files syslog | grep -E "Job failed|JOB_FAILED|diagnostics"
    JobImpl: Job failed as tasks failed. failedMaps:1 failedReduces:0 killedMaps:0 killedRedu… JobHistoryEventHandler: In stop, writing event JOB_FAILED RMCommunicator: Setting job diagnostics to Task failed task_1792655556966_0006_m_000001
    The AM decided the job had failed, wrote the JOB_FAILED event for the JobHistory Server and sent the diagnostics we saw in step 2. If the AM itself crashes, this is the log to read.

  7. Turn up the detail when you need it

    hadoop jar mr.jar ItemRevenue -D mapreduce.map.log.level=DEBUG /user/hadoop/data/canteen_orders.csv /out/lvl
    map.log.level=INFO: map container syslog has 82 lines map.log.level=DEBUG: map container syslog has 2134 lines
    26 times more lines from one small map task. DEBUG is useful for one run; left on for a production job, it fills disks and the HDFS log directory.

Don't fix a data failure by raising mapreduce.map.maxattempts or rerunning: a bad record fails every attempt the same way. Fix the code (validate, count, skip) or the data.

5 See it happen

Following the logs of one failed job

Six steps through our lab's failed job: what you type, and where YARN gets the answer from.

From FAILED to the bad line 6 steps
What you see
  1. The client shows failed attempts and the job's FAILED state.
  2. The ResourceManager's record names the task that ran out of attempts.
  3. yarn logs lists every container that left logs, per node.
  4. The failed attempt's syslog has the exception and the line of our code.
  5. The bad value from the message leads straight to the input lines.
  6. The fix is in the code: Lesson 8.3's CleanOrders counted 107 bad amounts and finished.
Behind the screen
  1. The failing code runs in task containers on the workers; the MRAppMaster retries each attempt and tells the client.
  2. When the AM gives up, it unregisters from the ResourceManager with a final status and diagnostics.
  3. Each NodeManager aggregates the app's container logs into one HDFS file per node.
  4. yarn logs reads just the container and file you ask for from those HDFS files.
  5. The input file lives in HDFS as well, so the bad value can be searched from the same terminal.
  6. Always the same order: client, ResourceManager, container log, code line, data, fix.
6 Real-world use

Logs at work

1. Bank and payments on-call

Settlement and reconciliation jobs run overnight with hard deadlines. Runbooks list the exact yarn logs commands, and every data guard writes a counter that an alert watches.

Alert→diagnostics → container log→Fix before 06:00

2. E-commerce platform teams

During a sale, hundreds of jobs run per hour. Daemon logs from every node are shipped to a central search system, so “which NodeManager went unhealthy at 21:04?” takes seconds.

Daemon logs→log shipper→Central search

3. Telecom cluster administrators

Thousands of jobs a day mean lakhs of aggregated log files. Admins tune retention and use the indexed log format so the log directory doesn't become a small-files problem (Lesson 7.5).

Aggregated logs→retain-seconds, IFile→Healthy NameNode

4. Healthcare and insurance data feeds

Hospital and claims files arrive from many partners in slightly different formats. Jobs log the file and offset of every rejected record and keep counts, so partners get exact error reports.

Partner files→validate + log + count→Error report

5. Data science teams on shared clusters

Analysts running Hive, Spark and MapReduce jobs use the ResourceManager and history UIs (Spark has its own History Server) to see why their job is slow or killed, without asking the admin for shell access.

Slow job→RM UI → attempt → logs→Self-service fix

Simplified; organisations differ in tools and policies. Scenario details are illustrative.

7 Run the code

Find the first exception in a log

These are real lines from our failed job's client output and map syslog. The parser finds the failed attempts, the first exception, and the first stack frame that is our code rather than Java or Hadoop.

log = """Task Id : attempt_1792655556966_0006_m_000000_0, Status : FAILED
Error: java.lang.NumberFormatException: For input string: "abc"
Task Id : attempt_1792655556966_0006_m_000000_1, Status : FAILED
Task Id : attempt_1792655556966_0006_m_000000_2, Status : FAILED
WARN [main] org.apache.hadoop.mapred.YarnChild: Exception running child : java.lang.NumberFormatException: For input string: "abc"
\tat java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
\tat ItemRevenue$OrderMapper.map(ItemRevenue.java:27)
\tat ItemRevenue$OrderMapper.map(ItemRevenue.java:18)"""

FRAMEWORK = ("java.", "javax.", "org.apache.hadoop.", "sun.", "jdk.")
attempts, exception, user_frame = [], None, None
for line in log.splitlines():
    if line.startswith("Task Id :") and "FAILED" in line:
        attempts.append(line.split()[3].rstrip(","))
    if exception is None and "Exception" in line and ":" in line and not line.strip().startswith("at "):
        exception = line[line.find("java."):]
    s = line.strip()
    if s.startswith("at ") and user_frame is None:
        method = s[3:]
        if not method.startswith(FRAMEWORK):
            user_frame = method
print("failed attempts:", len(attempts), attempts[-1])
print("exception      :", exception)
print("your code      :", user_frame)
failed attempts: 3 attempt_1792655556966_0006_m_000000_2 exception : java.lang.NumberFormatException: For input string: "abc" your code : ItemRevenue$OrderMapper.map(ItemRevenue.java:27)
  • FRAMEWORK = ("java.", "javax.", "org.apache.hadoop.", "sun.", "jdk.")Frames from Java and Hadoop tell you where the error surfaced; the first frame from your own classes tells you what to fix.
  • if exception is None and "Exception" in line and ":" in line and not line.strip().startswith("at "):Read the FIRST exception. Later ones are often consequences (a task failing, then the job failing).
  • if not method.startswith(FRAMEWORK):The first frame from our own code: class ItemRevenue$OrderMapper, method map, file ItemRevenue.java, line 27.

Every attempt of a job, from the JobHistory REST API

# attempts.sh JOB_ID : every task attempt of a finished job (node, time, state), from the JobHistory REST API
J=$1; ID=${J#job_}
for kind in m r; do
  for t in $(curl -s http://historyserver:19888/ws/v1/history/mapreduce/jobs/$J/tasks | grep -o "task_${ID}_${kind}_[0-9]*" | sort -u); do
    curl -s http://historyserver:19888/ws/v1/history/mapreduce/jobs/$J/tasks/$t/attempts | python3 -c '
import sys, json
t = json.load(sys.stdin)["taskAttempts"]["taskAttempt"]
for a in (t if isinstance(t, list) else [t]):
    node = a["nodeHttpAddress"].split(":")[0]
    print("%-40s %-9s %-8s %5.1f s  %s" % (a["id"], a["state"], node, a["elapsedTime"] / 1000, a.get("diagnostics", "")[:70]))'
  done

Quick revision

Lesson 11.5 in one screen

  • Daemon logs (RM, NM, NN, DN, JobHistory) stay on each machine in $HADOOP_LOG_DIR; container logs are stdout, stderr, syslog.
  • Log aggregation uploads finished apps' container logs to HDFS (/tmp/logs/<user>/…), one file per node; kept retain-seconds.
  • yarn logs -applicationId with -show_application_log_info, -containerId, -log_files, -am 1.
  • Order: client error → yarn application -status diagnostics → failed attempt syslog → first exception + your frame → input record → fix + counter.
  • Lab: NumberFormatException "abc" at ItemRevenue.java:27; bad line 1,715 901714,chai,abc; Final-State FAILED, failedMaps:1.
  • UIs: ResourceManager 8088, NodeManager 8042, JobHistory 19888 (Spark has its own History Server).
  • DEBUG only when needed: 82 → 2,134 lines per map in our lab; -D mapreduce.map.log.level=DEBUG for one run, yarn daemonlog -setlevel for a daemon.

Interview and viva questions

How do I see the logs of a YARN application?

Run yarn logs -applicationId <id> after the application finishes (log aggregation must be enabled). Add -containerId and -log_files syslog (or stderr) to see one container's file, -am 1 for the ApplicationMaster, and -show_application_log_info to list containers. While it runs, use the ResourceManager UI on port 8088 and follow the links to each container's logs on its NodeManager (port 8042).

Where are YARN container logs stored?

While the container runs, in the NodeManager's local log directories (yarn.nodemanager.log-dirs, under userlogs/application_…/container_…). After the application finishes, with log aggregation enabled, each NodeManager uploads them to HDFS under yarn.nodemanager.remote-app-log-dir (default /tmp/logs) and deletes the local copies after yarn.nodemanager.delete.debug-delay-sec.

Why does yarn logs say the logs are not available?

Common reasons: the application is still running (logs are aggregated at the end; use the NodeManager UI), log aggregation is disabled, the logs were already deleted by retention, or you are not the owner. Without aggregation the logs stay on each NodeManager's local disk.

What is the difference between syslog, stderr and stdout in a container?

syslog is Hadoop's own log4j output from the task (framework messages and the full stack trace of a failure); stderr receives anything written to System.err and, for Streaming, the script's errors; stdout receives System.out. In MapReduce, data goes through the context, never stdout.

How do I change the log level of a Hadoop job or daemon?

For one MapReduce job, pass -D mapreduce.map.log.level=DEBUG (and mapreduce.reduce.log.level or yarn.app.mapreduce.am.log.level). For a running daemon, use yarn daemonlog -setlevel host:port logger LEVEL (or hadoop daemonlog); it lasts until the daemon restarts. Permanent changes go in log4j.properties.

P8Advanced

Retention planner

Given per-day aggregated log volume and HDFS budget, find the longest retention in whole days, for replication 3 and 2.

Input
180 GB/day · 12 TB budget
Expected output
replication 3: 22 days, yarn.log-aggregation.retain-seconds=1900800
replication 2: 34 days, yarn.log-aggregation.retain-seconds=2937600
Show solution and explanation 
per_day_gb, budget_tb = 180, 12
for rep in (3, 2):
    days = int(budget_tb * 1024 // (per_day_gb * rep))
    print(f"replication {rep}: {days} days, yarn.log-aggregation.retain-seconds={days * 86400}")
replication 3: 22 days, yarn.log-aggregation.retain-seconds=1900800 replication 2: 34 days, yarn.log-aggregation.retain-seconds=2937600

How it works: 22 days at replication 3, 34 at replication 2. Logs matter less than business data, so some teams accept lower replication for them.

Real-world scenario questions (asked in company interviews)

Debugging questions test whether you have actually run jobs on a cluster. Interviewers want an order of steps, not guesses.

Debugging · basicsFresher

“Your MapReduce job failed. What do you do?”

The most common practical question.

The interviewer is checking: a systematic order and the right commands.

Show a strong answer
  • Read the client output, then yarn application -status for the diagnostics and the failed task.
  • yarn logs -applicationId … -containerId … -log_files syslog (or the JobHistory UI) for the failed attempt; find the first exception and the first frame of my code.
  • Find the input (the split is in the syslog), reproduce on a sample in local mode, fix, and add a counter for bad records.
Operations · logsFresher

“yarn logs says no logs found for my application”

A colleague's job finished an hour ago.

The interviewer is checking: how log aggregation works.

Show a strong answer
  • Check that log aggregation is enabled (yarn.log-aggregation-enable) and look in HDFS under the remote app log dir (/tmp/logs/<user>).
  • Check the user: you can only read your own app's logs unless you are an admin; pass -appOwner.
  • If aggregation is off, the logs are on each NodeManager's local disk until they are deleted; if retention already removed them, they are gone.
Operations · on-callExperienced

A nightly job fails at 2 AM; rerunning it fails again

The report is due at 6 AM.

The interviewer is checking: data errors vs infrastructure errors, and a safe fix.

Show a strong answer
  • Same task failing with the same exception on different nodes = data or code, not a bad machine; different errors on one node = infrastructure.
  • Locate the bad split and record, decide with the business: quarantine bad rows (count + side output) or stop; test the fix on that split.
  • Afterwards: alert on the bad-row counter, contract with the data provider, and a runbook entry.
Platform · designExperienced

The NameNode is slowing down; /tmp/logs has 80 lakh files

An admin notices the aggregated log directory is huge.

The interviewer is checking: log aggregation as a small-files problem.

Show a strong answer
  • Each app writes one file per node it used; thousands of apps a day × many nodes × long retention gives millions of files.
  • Shorten yarn.log-aggregation.retain-seconds, use the IndexedFile (IFile) log aggregation format, and keep DEBUG off by default.
  • Ship logs that must be kept longer to a log platform or object storage instead of HDFS.
