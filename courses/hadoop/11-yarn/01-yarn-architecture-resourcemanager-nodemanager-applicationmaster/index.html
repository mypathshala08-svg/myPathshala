YARN architecture: ResourceManager, NodeManager, ApplicationMaster

2 Definition

YARN: Yet Another Resource Negotiator

Formal definition (write this in exams)

YARN is Hadoop's cluster resource-management and job-scheduling layer, introduced in Hadoop 2. It separates resource management from application logic. A single ResourceManager (RM) per cluster arbitrates all resources; it consists mainly of the Scheduler, which allocates resources to applications according to capacities, queues and policies, and the ApplicationsManager, which accepts job submissions, starts each application's first container and restarts it on failure. A NodeManager (NM) on every worker launches and monitors containers, reports node health and resource use to the RM through heartbeats, and runs auxiliary services such as the MapReduce shuffle. Each application has its own ApplicationMaster (AM), which runs in a container, negotiates further containers from the Scheduler using resource requests (memory, virtual cores, locality, priority) and works with NodeManagers to execute and monitor its tasks. A container is an allocation of memory and CPU on one node in which one process runs.

In simple words

The ResourceManager is the cluster's bookkeeper of free memory and CPU. NodeManagers start and watch processes on each machine. Every job brings its own manager, the ApplicationMaster, which asks for “boxes” of memory and CPU (containers) and runs its tasks inside them.

Words you'll meet in this lesson

ApplicationsManagerPart of the RM that accepts submissions and starts (and restarts) each AM.
NodeManager (NM)YARN worker on each machine: launches, monitors and kills containers. UI port 8042.
ApplicationMaster (AM)One per application: asks for containers, runs and tracks tasks. For MapReduce: MRAppMaster.

YARN at three levels

Pick your level. New to this? Start at Beginner and climb.

Beginner The hotel

  • The front desk (ResourceManager) knows which rooms are free on every floor but carries no luggage.
  • Each floor manager (NodeManager) opens rooms, checks nobody is breaking the rules (using too much memory) and tells the desk every few moments what is free.
  • Every tour group brings a tour leader (ApplicationMaster). The leader gets a room first, then asks the desk for more rooms for the group and tells each member what to do.
  • A room is a container: a fixed amount of memory and CPU for one process.

Intermediate What each part does in a real job

  • Client: uploads the jar and configuration to HDFS and calls the RM on port 8032 (ClientRMService).
  • ApplicationsManager: accepts the application, asks the Scheduler for the AM's container and has a NodeManager start it.
  • ApplicationMaster: registers with the RM on port 8030, then calls allocate() repeatedly: “4 containers of 512 MB, preferably on the hosts that hold these blocks.” It also reports progress and finally unregisters.
  • Scheduler: on each NodeManager heartbeat (port 8031, ResourceTrackerService) it looks for a waiting request that fits the node's free space and grants a container.
  • NodeManager: receives the container launch from the AM, localizes the jar, starts the process (a YarnChild JVM), monitors it and reports when it exits.

Advanced Why the design scales

  • In Hadoop 1 one JobTracker did both: scheduling the cluster and tracking every task of every job. At around 4,000 nodes it became the bottleneck, and fixed map/reduce slots wasted capacity (Lesson 2.4).
  • YARN keeps the RM small: it tracks containers, not tasks. Task tracking, retries and speculation live in each AM, so the work spreads across the cluster.
  • Because the AM is application code, any framework can run on YARN: MapReduce, Spark, Tez (Hive), Flink, Hive LLAP. They share one cluster and one set of queues.
  • The RM can run in High Availability: an active and a standby RM with ZooKeeper for leader election, and running applications survive a failover (work-preserving restart).
  • The Scheduler is pluggable: FIFO, Capacity (default in Apache Hadoop) or Fair. Lesson 11.3 measures all three.

Exam tip: For “Explain YARN architecture”, draw the RM (Scheduler + ApplicationsManager), NodeManagers with containers, one ApplicationMaster per application, and number the steps: submit → AM container → AM registers and requests containers → NMs launch tasks → AM unregisters. Add one line: the RM manages resources, the AM manages the application.

Animated example: a 10 AM rush on a shared cluster

IRCTC-style Tatkal analytics on YARN 6 steps
Animated example
  1. 10:05: five minutes of Tatkal bookings are in HDFS; an analyst submits a report job to the ResourceManager.
  2. The ApplicationsManager picks a node with 1 GB free and has its NodeManager start the job's ApplicationMaster.
  3. The AM looks at its input, finds 6 splits and asks the Scheduler for 6 containers of 2 GB, preferably where the blocks are.
  4. Each NodeManager heartbeat reports free space; the Scheduler grants 4 containers. Node 4 is full with the booking service.
  5. When the booking traffic drops, node 4 frees memory and the last two containers are granted.
  6. 10:12: the report is ready. The AM unregisters and every container goes back to the pool. (Numbers illustrative.)

YARN shares one cluster between very different workloads: a booking service's batch jobs, a fraud model's Spark job and an analyst's Hive query all ask the same ResourceManager. How it chooses between them (queues and schedulers) is Lesson 11.3.

5 See it happen

From hadoop jar to five containers

Six steps of our 422 MB job, as the terminal shows them and as YARN handles them.

Containers on demand 6 steps
What you see
  1. The client connects to the ResourceManager on port 8032.
  2. The application is accepted and its first container, the AM, runs on worker1.
  3. The AM computes 4 splits: 4 map tasks to place.
  4. Mid-job the cluster has 5 containers out, 2,560 MB of 6,144.
  5. On worker1, next to the DataNode and NodeManager: the AM and one map task.
  6. The job finishes and every container is released.
Behind the screen
  1. The client calls the ResourceManager's ClientRMService. The RM manages 6,144 MB.
  2. The ApplicationsManager gets a container for the AM and the worker1 NodeManager starts it.
  3. The AM registers on port 8030 and requests 4 containers; each 384 MB request becomes 512 MB.
  4. As NodeManagers heartbeat, the Scheduler places the 4 maps on worker1, worker2 (two) and worker3.
  5. The AM contacts each NodeManager, which starts a YarnChild JVM for the map task.
  6. When all tasks are done the AM unregisters and all 2,560 MB return to the pool.
6 Real-world use

YARN at work

1. Bank: one cluster, many engines

An Indian bank runs nightly MapReduce reconciliation, Hive reports for branches and a Spark fraud-scoring job on the same nodes. YARN gives each its containers from one pool instead of three separate clusters.

MR + Hive + Spark→ResourceManager→Shared workers

2. Telecom: call records at month end

Billing jobs for crores of call records ask for thousands of containers once a month; during the rest of the month the same capacity runs network analytics.

CDRs in HDFS→Billing AM→Bills per customer

3. E-commerce: a streaming job that never ends

A clickstream job runs for weeks as a Flink or Spark Streaming application on YARN. If its AM dies, the ApplicationsManager restarts it in a new container.

Clicks (Kafka)→Long-running AM→Live dashboards

4. Government data platform: RM high availability

A state e-governance analytics platform runs two ResourceManagers with ZooKeeper. When the active RM's server is patched, the standby takes over and running jobs continue.

RM1 active→ZooKeeper election→RM2 active

5. University research cluster: fair use

An IIT-style research cluster reads the RM REST API every few minutes to show each department how many container-hours it used, the same /ws/v1/cluster/metrics data we read in the lab.

RM REST API→Usage script→Monthly report

7 Run the code

Be the ResourceManager for one job

This model keeps the RM's books for our lab: three NodeManagers with 2,048 MB each, a 256 MB minimum allocation, one AM of 512 MB and four maps asking for 384 MB. Containers are granted as NodeManagers heartbeat in, one per heartbeat, in the order they arrived in our run.

import math
MIN_ALLOC = 256                                   # yarn.scheduler.minimum-allocation-mb
nodes = {"worker1": 2048, "worker2": 2048, "worker3": 2048}
used = {n: 0 for n in nodes}

def normalize(mb):                                # round UP to a multiple of the minimum
    return math.ceil(mb / MIN_ALLOC) * MIN_ALLOC

requests = [("AM", 512)] + [(f"map{i}", 384) for i in range(4)]
heartbeats = ["worker1", "worker2", "worker3", "worker1", "worker2"]   # who reported free space next

for (name, ask), node in zip(requests, heartbeats):
    size = normalize(ask)
    if used[node] + size <= nodes[node]:
        used[node] += size
        print(f"{name:5} asks {ask} MB -> gets {size} MB on {node}")

print("per node:", used)
print("allocated", sum(used.values()), "of", sum(nodes.values()), "MB in", len(requests), "containers")
AM asks 512 MB -> gets 512 MB on worker1 map0 asks 384 MB -> gets 512 MB on worker2 map1 asks 384 MB -> gets 512 MB on worker3 map2 asks 384 MB -> gets 512 MB on worker1 map3 asks 384 MB -> gets 512 MB on worker2 per node: {'worker1': 1024, 'worker2': 1024, 'worker3': 512} allocated 2560 of 6144 MB in 5 containers
  • return math.ceil(mb / MIN_ALLOC) * MIN_ALLOCThe Scheduler normalizes every request: 384 MB becomes 512 MB, which is why 4 maps + AM held 2,560 MB.
  • heartbeats = ["worker1", "worker2", "worker3", "worker1", "worker2"] # who reported free space nextThe Scheduler assigns containers when a NodeManager heartbeats and reports free space.
  • if used[node] + size <= nodes[node]:A container must fit entirely on one node: YARN never splits a container across machines.

Example 1BeginnerHealthcare · capacity

Will a hospital chain's job run in one wave?

Problem statement

A hospital chain analyses scan metadata with a job of 50 map tasks of 2 GB each. Its YARN cluster has 10 NodeManagers offering 32 GB each. How many 2 GB containers fit at once, and does the job run in a single wave (keep one 2 GB container for the AM)?

Input
10 nodes × 32 GB · 50 maps × 2 GB · AM 2 GB
Expected output
16 per node, 160 in the cluster, 159 for maps -> one wave: True

Approach

  1. Containers per node = node memory / container size.
  2. Cluster containers = per node × nodes.
  3. Subtract the AM and compare with 50.

How long until YARN notices a dead node?

Problem statement

A telecom billing cluster: NodeManagers heartbeat every 1 s; the RM declares a node LOST after 600 s without heartbeats (yarn.nm.liveness-monitor.expiry-interval-ms). 9 Quiz and revision

Check yourself

Quick revision

Lesson 11.1 in one screen

  • ResourceManager = Scheduler (who gets what) + ApplicationsManager (accept apps, start/restart AMs). One active per cluster; HA with ZooKeeper.
  • NodeManager per worker: launches and monitors containers, heartbeats to the RM, runs the shuffle service and log aggregation.
  • ApplicationMaster per application: requests containers (size, locality, priority), runs and retries tasks. MRAppMaster, Spark AM/driver, Tez AM.
  • Container = memory + vcores on one node, one process. Requests are rounded up to the minimum allocation.
  • Lab: 3 NMs × (2,048 MB, 2 vcores) = 6,144 MB, 6 vcores; one job held 5 containers, 2,560 MB (AM 512 + 4 × 512).
  • Ports: 8088 RM UI/REST, 8032 clients, 8030 AMs, 8031 NMs, 8042 NM UI.
  • YARN tracks containers, not tasks: that is why it scales and runs any framework.

Interview and viva questions

What are the main components of YARN?

The ResourceManager (with its Scheduler and ApplicationsManager), a NodeManager on every worker, one ApplicationMaster per application, and containers, which are allocations of memory and CPU on a node in which processes run. Optionally a Timeline Server stores application history.

What is the difference between the ResourceManager and the ApplicationMaster?

The ResourceManager is a single cluster-wide service that decides how much memory and CPU each application gets and where. The ApplicationMaster belongs to one application: it asks the ResourceManager for containers and decides which tasks run in them, tracks their progress and retries failures.

What is a container in YARN?

A container is a slice of one node's resources, a given amount of memory and virtual cores, granted by the ResourceManager to an application. The NodeManager starts one process in it (for example a map task JVM or a Spark executor) and enforces its limits.

Why was YARN introduced in Hadoop 2?

In Hadoop 1 the JobTracker both scheduled the cluster and tracked every task of every job, which limited clusters to around 4,000 nodes, and fixed map and reduce slots wasted resources. YARN moves per-job work to ApplicationMasters and replaces slots with flexible containers, so clusters scale further and can run frameworks other than MapReduce.

Can Spark run on YARN?

Yes. In cluster mode the Spark driver runs inside the ApplicationMaster container and executors run in other containers; in client mode the driver runs on the submitting machine and a small AM only requests executors. Hive on Tez, Flink and many other frameworks run on YARN the same way.

Practice problems

YARN architecture exercises using the real numbers from our cluster.

P1Easy

Cluster totals

Each of 3 NodeManagers offers 2,048 MB and 2 vcores. What are the cluster totals the RM reports?

Input
3 × (2048 MB, 2 vcores)
Expected output
6144 MB, 6 vcores
Show solution and explanation 
print(3 * 2048, "MB,", 3 * 2, "vcores")
6144 MB, 6 vcores

How it works: 6,144 MB and 6 vcores: totalMB and totalVirtualCores in /ws/v1/cluster/metrics.

P2Easy

Explain 2,560 MB

Show how one AM of 512 MB and four maps asking 384 MB add up to 2,560 MB.

Input
AM 512 · 4 × 384 → rounded
Expected output
2560
Show solution and explanation 
import math
map_size = math.ceil(384 / 256) * 256
print(512 + 4 * map_size)
2560

How it works: Each map is rounded to 512 MB: 512 + 4 × 512 = 2,560.

P3Easy

Share of the cluster

What percentage of the cluster's memory did the job hold?

Input
2,560 of 6,144 MB
Expected output
42%
Show solution and explanation 
print(f"{2560 / 6144:.0%}")
42%

How it works: About 42%: the rest was free for other applications.

P4Medium

Round these requests

With a 256 MB minimum, what do requests of 100, 256, 300, 600 and 1,100 MB become?

Input
5 requests
Expected output
100 -> 256
256 -> 256
300 -> 512
600 -> 768
1100 -> 1280
Show solution and explanation 
import math
for ask in [100, 256, 300, 600, 1100]:
    print(ask, "->", math.ceil(ask / 256) * 256)
100 -> 256 256 -> 256 300 -> 512 600 -> 768 1100 -> 1280

How it works: 256, 256, 512, 768 and 1,280 MB. Lesson 11.4 confirms these on the cluster.

P5Medium

Place on heartbeats

Free memory: w1 512, w2 2048, w3 1024. Heartbeats arrive w1, w2, w3, w2. Place four 1,024 MB containers.

Input
3 nodes, 4 heartbeats
Expected output
granted on w2
granted on w3
granted on w2
still waiting: 1 {'w1': 512, 'w2': 0, 'w3': 0}
Show solution and explanation 
free = {"w1": 512, "w2": 2048, "w3": 1024}
waiting = 4
for node in ["w1", "w2", "w3", "w2"]:
    if waiting and free[node] >= 1024:
        free[node] -= 1024; waiting -= 1
        print("granted on", node)
print("still waiting:", waiting, free)
granted on w2 granted on w3 granted on w2 still waiting: 1 {'w1': 512, 'w2': 0, 'w3': 0}

How it works: w1 has no room; w2, w3 and w2 again get one each; one request waits for the next heartbeat with space.

P6Medium

Count the daemons

A cluster has 2 masters (RM + NameNode on one, standby RM on the other) and 50 workers. How many YARN daemons run?

Input
2 RMs + 50 NMs
Expected output
52 YARN daemons (plus one AM per running application)
Show solution and explanation 
print(2 + 50, "YARN daemons (plus one AM per running application)")
52 YARN daemons (plus one AM per running application)

How it works: 52 long-running daemons; AMs and task containers come and go with applications.

P7Business problem

One cluster or three?

Three teams each want their own 20-node cluster, each busy about 30% of the time. With one shared 30-node YARN cluster, average demand is 3 × 20 × 0.3 nodes. Compare node counts.

Input
3 × 20 nodes at 30%
Expected output
separate: 60 nodes; shared average demand: 18 nodes -> a 30-node shared cluster leaves headroom
Show solution and explanation 
separate = 3 * 20
avg_demand = 3 * 20 * 0.3
print(f"separate: {separate} nodes; shared average demand: {avg_demand:.0f} nodes -> a 30-node shared cluster leaves headroom")
separate: 60 nodes; shared average demand: 18 nodes -> a 30-node shared cluster leaves headroom

How it works: 60 nodes vs 30: sharing through YARN queues halves the hardware (illustrative; peak overlaps need planning, Lesson 11.3).

P8Advanced

Worst-case AM memory

maximum-am-resource-percent is 0.1 by default in the Capacity Scheduler. On our 6,144 MB cluster, how many 512 MB AMs can run at once, and what happens to more applications?

Input
6144 MB · 10% · 512 MB AMs
Expected output
AM limit 614 MB -> 1 AM(s) at once (YARN always allows at least one)
Show solution and explanation 
limit = 6144 * 0.1
print(f"AM limit {limit:.0f} MB -> {int(limit // 512)} AM(s) at once (YARN always allows at least one)")
AM limit 614 MB -> 1 AM(s) at once (YARN always allows at least one)

How it works: Only one 512 MB AM fits under 614 MB; further applications stay ACCEPTED until it finishes. This protects clusters from filling up with AMs that have no room for tasks.

Real-world scenario questions (asked in company interviews)

YARN architecture questions come up in every Hadoop and Spark interview.

Architecture · basicsFresher

“Explain the YARN architecture”

Asked in almost every big data interview.

The interviewer is checking: the roles and how they talk.

Show a strong answer
  • ResourceManager (Scheduler + ApplicationsManager) manages cluster resources; NodeManagers run containers on each worker.
  • Each application has an ApplicationMaster that requests containers and manages its own tasks.
  • Flow: submit → AM container → AM registers and requests containers → NMs launch tasks → AM unregisters.
Operations · stuck jobsExperienced

Jobs stay in ACCEPTED and never start

The RM UI shows 15 applications ACCEPTED, cluster memory 40% used.

The interviewer is checking: AM limits and container sizing.

Show a strong answer
  • ACCEPTED means the AM container hasn't been allocated: check the queue's maximum-am-resource-percent and the queue's capacity, not just total free memory.
  • Check that the AM size fits on a single node (free memory may be fragmented across nodes) and is not above maximum-allocation-mb.
  • Look at the application's diagnostics in the RM UI; they name the limit that blocks it.
Design · sizingExperienced

“Our nodes have 128 GB RAM. What should yarn.nodemanager.resource.memory-mb be?”

A new cluster is being set up.

The interviewer is checking: leaving room for everything that isn't a container.

Show a strong answer
  • Subtract the OS, DataNode, NodeManager and other agents (often 8–16 GB), and any co-located services such as HBase.
  • Give the rest to YARN, e.g. about 100–112 GB, and set the minimum allocation so common container sizes divide it evenly.
  • Set vcores to the cores available to containers and use the DominantResourceCalculator if CPU matters (Lesson 11.4).
Reliability · failuresExperienced

“What happens if the ApplicationMaster or the ResourceManager dies?”

A follow-up after the architecture question.

The interviewer is checking: recovery at each level.

Show a strong answer
  • AM dies: the ApplicationsManager starts a new attempt (yarn.resourcemanager.am.max-attempts, default 2); the MapReduce AM can recover finished tasks from its history.
  • RM dies: with RM HA, the standby becomes active through ZooKeeper; with work-preserving recovery running containers continue.
  • NodeManager dies: after the liveness timeout its containers are reported lost and AMs rerun those tasks elsewhere.
